# Resources and the Uniform Interface

_Module 7.1a — RESTful API Design & Implementation_

## The Problem

A ticketing product, three years old. The HTTP API grew one endpoint at a time, each added by whoever needed it:

```
POST /api/getTickets
POST /api/getTicketDetail
POST /api/createTicket
POST /api/updateTicketStatus
POST /api/assignTicket
POST /api/searchTickets
POST /api/deleteTicket
```

Everything is `POST`. Everything returns `200 OK` with a body shaped like `{"success": true|false, "data": …, "error": …}`. This is not a strawman — it's one of the most common API designs in existence, and it works. Clients call it. It does the thing.

Then three incidents happen in the same quarter.

**The duplicate tickets.** The mobile client gives up after 10 seconds. The server finished at 10.4. The client retries `createTicket`, and now there are two tickets. Support files a bug: "fix the retry logic." But there is no rule the client could follow. Is retrying `updateTicketStatus` safe? Probably. `assignTicket`? Depends what it does. From outside, every endpoint is the same opaque POST, so the HTTP library has exactly two options — retry everything and create duplicates, or retry nothing and fail on a flaky train connection. Both are wrong, and the information needed to choose isn't anywhere in the protocol.

**The dashboard that melts the database.** The ops dashboard polls `getTickets` every five seconds. Forty tabs are open across the support team. That's eight identical queries per second hitting Postgres. There's a CDN in front of the app and a reverse proxy behind it — both have caches, both are forwarding every one of those requests, because they must: a POST might change something. The fix takes a sprint — add Redis, add an invalidation path, then chase the bug where a status change takes sixty seconds to appear on screen. Two caches that were already deployed sat idle through all of it.

**The monitoring that showed 100% success.** An integration's credentials expired on a Friday. For fifty hours the API returned `200 OK` with `{"success": false, "error": "unauthorized"}` — about 40,000 times. The gateway dashboard showed a 0.0% error rate all weekend. Every alert was green. The customer found it on Monday.

Three unrelated incidents, one shape. In each case a **generic component** — a retry layer, a cache, a metrics pipeline — needed one small fact that only the application knew:

- *Is it safe to send this again?*
- *Is this a read?*
- *Did this fail, and whose fault was it?*

And in each case the application had no way to say it, so the fix was to write application-specific code inside something that was supposed to be application-agnostic.

Here is the part that stings: HTTP has had a standard answer for all three questions since the nineties. This API can't use any of it, because it isn't speaking HTTP. It's using HTTP as an envelope for a private protocol in which every operation is an opaque function call named in the URL path.

## What It Is

The fix has a name: the **uniform interface**, which is the central constraint of REST.

The idea is small. Give the things in your system identity — a URL each. Act on them using a fixed, tiny set of methods whose meanings are defined by the protocol rather than by you. Report outcomes with status codes from a shared set. Treat the JSON you send back as one possible *representation* of the thing, not the thing itself.

What you get in exchange is the answer to the three incidents above:

```
   POST /api/getTickets                GET /tickets?status=open

   browser cache   ✗  opaque           browser cache   ✓  it's a read
   CDN             ✗  must forward     CDN             ✓  cacheable
   proxy retry     ✗  might duplicate  proxy retry     ✓  safe by definition
   gateway metric  ✗  always 200       gateway metric  ✓  status class
```

Nothing in the right-hand column knows what a ticket is. That's the whole point. Uniform semantics are what let four components that have never heard of your domain do useful, correct work on your traffic.

Two disambiguations, because the word is overloaded:

**"REST" as commonly used** means JSON over HTTP with plural nouns in the path. **REST as Fielding defined it** additionally requires hypermedia — responses carry the links describing what you can do next. Almost nothing in production does the second part, which is a real argument covered in 7.1b. This article is about the constraint that nearly everyone agrees is worth having.

**REST vs. RPC** is not a question of URL aesthetics. You can write `/api/createTicket` and you can write `POST /tickets`, and the difference isn't tidiness — it's whether the protocol's own semantics are load-bearing. An RPC design deliberately treats HTTP as dumb transport and rebuilds retry, caching, and error signaling inside the payload. Sometimes that's the right call (see Alternatives). It should be a choice.

## Recognizing the Problem

- Your client libraries either retry nothing, or retry everything and occasionally create duplicates.
- Your error rate dashboard is green during a known outage.
- Every endpoint is `POST`, or every endpoint is `GET` including the destructive ones.
- A CDN or gateway sits in the request path and is configured to pass everything through.
- Support asks "did it save?" and the only way to know is to read application logs.
- Two clients ask the same question with two different endpoint names, because nobody could find the first one.
- Your API docs are a list of function names with no discernible pattern, and new endpoints keep getting added rather than existing ones being reused.
- Adding a cache means adding Redis, always, even for data that changes hourly and is identical for all callers.
- A `500` alert fires and the cause turns out to be a user typing a malformed date.
- The integration guide contains the sentence "check the `success` field, not the HTTP status."

## How It Works

### Resources, not procedures

A resource is anything worth naming: a ticket, a user's notification settings, a monthly invoice PDF, the current set of open tickets. Its identity is its URL, and that identity is stable regardless of what you send back for it.

The representation is the bytes — today, usually JSON. The distinction sounds academic until it earns its keep: the same resource can have several representations (`application/json`, `text/csv`, `application/pdf`), chosen by the `Accept` header, without minting a second URL like `/tickets/42/asPdf`.

The shape that falls out of this is the collection/item pair:

```
/tickets                  the collection
/tickets/8f21             one item
/tickets/8f21/comments    a sub-collection scoped to that item
```

A few rules of thumb that save arguments later:

- **Nest for containment, not for convenience.** `/tickets/8f21/comments` is right because a comment doesn't exist outside its ticket. `/users/3/tickets` is a filtered view of a global collection, and it's usually better as `/tickets?assignee=3` — otherwise you end up maintaining two paths to the same rows with two sets of permission checks that drift.
- **Stop at two levels.** `/orgs/1/projects/4/tickets/9/comments/2` is a path where five of the six segments are ignored by the lookup, and any of them being wrong is a bug you'll never see because the last id is unique anyway.
- **Identifiers are opaque to clients.** If they're sequential integers you have leaked your growth rate and handed everyone an enumeration attack; that's a decision, not a default.

### The verb vocabulary, and the two properties that matter

There are effectively five methods, and what distinguishes them is not "create/read/update/delete" but two protocol-level properties:

| Method | Safe | Idempotent | Typically cacheable |
|---|---|---|---|
| GET / HEAD | yes | yes | yes |
| PUT | no | yes | no |
| DELETE | no | yes | no |
| POST | no | **no** | rarely |
| PATCH | no | **no** | no |

**Safe** means it doesn't change anything the client is responsible for. A safe request can be sent speculatively, prefetched, crawled, and cached.

**Idempotent** means N identical requests leave the server in the same state as one. Note carefully: *the same state*, not *the same response*. `DELETE /tickets/8f21` returning `204` and then `404` is perfectly idempotent — the resource is gone either way. This is the property a generic retry layer needs, and it's why a proxy can safely re-send a PUT after a timeout but not a POST.

That table is the entire content of the first incident. A client library that knows nothing about tickets can implement "retry on timeout if the method is idempotent" and be correct.

### The gap: POST, and the idempotency key

Creation is the operation you most want to retry — network failures cluster around the slow, important writes — and it's the one method the protocol declares non-idempotent. That's not an oversight. `POST /tickets` means "create a new one," and the server genuinely cannot tell a retry from a customer who wants a second identical ticket.

The standard repair is to let the *client* supply the identity of the operation:

```
POST /payments
Idempotency-Key: 5f6d2c1e-9b2a-4d0c-8f17-3e5a0c9d1b44
```

The client generates that key once per logical operation and reuses it for every retry of that operation. The server stores the key alongside the result. A second arrival with a known key doesn't re-execute — it replays the stored response.

Three details decide whether this works or quietly doesn't:

- **Scope the key to the caller** (and to the tenant), or one client's UUID collision becomes another client's wrong answer.
- **Store the key in the same transaction as the effect.** Writing the payment row and then writing the idempotency record is the dual-write problem from 6.1 wearing a new hat: crash in between and the retry creates a second payment.
- **Handle concurrent duplicates**, not just sequential ones. Two retries can be in flight simultaneously. A unique index on the key is what makes the second one lose; what it does after losing — wait, or return `409` — is a design decision you should make on purpose.

An expiry is required too. Keys are kept for hours or days, not forever, and the documented window is part of your API contract because it's the client's deadline for finishing its retries.

### Status codes as a shared vocabulary

The class is more important than the code:

- **2xx** — it worked.
- **3xx** — look elsewhere, or nothing has changed since you last asked.
- **4xx** — the request was wrong. Retrying it unchanged will fail again.
- **5xx** — the server was wrong. Retrying might work.

The 4xx/5xx boundary is the one that costs money when you get it wrong, because it decides two automated behaviors at once: whether a retry is pointless, and whether someone gets paged. A validation failure returned as `500` wakes an engineer at 3am to look at a user's typo. An outage returned as `200` is the third incident.

The specific codes that carry real information:

- `201 Created` with a `Location` header — the client now knows the URL of what it made.
- `202 Accepted` — you took the work, it isn't done; pair with a status URL (Module 10).
- `204 No Content` — succeeded, nothing to say.
- `400` vs `422` — malformed versus well-formed but semantically wrong. Pick one convention and write it down; the distinction matters less than the consistency.
- `401` vs `403` — "I don't know who you are" versus "I know, and no." Clients act differently: one refreshes a token, the other shows an error.
- `403` vs `404` for a resource belonging to another tenant. Returning `404` hides existence; returning `403` confirms it. This is a security decision, and multi-tenant systems generally want the `404`.
- `409 Conflict` — the request collided with the current state.
- `412 Precondition Failed` — the conditional request you made didn't hold (7.4).
- `429` with `Retry-After` — slow down, and here's how long (Module 18).
- `503` with `Retry-After` — temporarily unavailable, retry later.

And the corresponding discipline: don't invent meanings for codes, don't return 200 with an error body, and don't use 500 as the default for anything unexpected without checking whether it was actually the caller's fault.

### The operations that aren't CRUD

This is where resource modeling gets genuinely hard, and where pretending otherwise produces the worst APIs. "Cancel the order." "Run the report." "Send the invoice." "Merge these two accounts." None of these is obviously a noun.

Three legitimate answers:

**1. It's really a field.** If cancelling an order means setting a status and nothing else, `PATCH /orders/42` with `{"status": "cancelled"}` is honest and simple. The server validates the transition.

**2. The action is itself a thing worth naming.** If a cancellation has a reason, an actor, a timestamp, a refund attached, and an audit requirement — then it *is* an entity, and modeling it as one is not a trick:

```
POST /orders/42/cancellations   → 201, with the cancellation's own URL
POST /reports                   → 202, Location: /reports/9c3 (poll it)
```

This works especially well for long-running work, because the job becomes a resource you can GET for progress and DELETE to cancel.

**3. Admit it's a verb.** Google's own API design guidance defines "custom methods" — `POST /orders/42:cancel` — for exactly the cases where the resource-oriented form is contorted. One honest verb is better than a fictional noun invented to launder it. `POST /accounts/merges` with two ids in the body is a resource in name only, and every reader will have to decode it.

The failure mode to avoid is not "using a verb." It's inventing resources that exist only in the URL — that nothing in your domain, database, or conversation ever refers to — and then having to explain them forever.

## When It's Appropriate

- **You have clients you don't control.** Partners, customers' integrations, a public API. They arrive with generic tooling and existing expectations, and every convention you share is documentation you don't have to write.
- **Browsers and mobile apps are first-class callers.** The caching and conditional-request machinery is already in the platform; using it is free performance.
- **The domain is genuinely resource-shaped.** Documents, records, configuration, media, CRUD-heavy admin surfaces — most business software.
- **You want the infrastructure ecosystem.** CDNs, API gateways, rate limiters keyed on route, WAFs, `curl`, Postman, OpenAPI generators, and observability that groups by method + route + status. All of it assumes these semantics.
- **The API will outlive its current clients.** Conventions are what make an endpoint written in 2021 usable in 2027 by someone who can't ask you about it.

## When It's Unnecessary or Overkill

- **One internal service, one client team, one deploy pipeline.** If both sides ship together, a typed RPC contract gives you more safety with less ceremony.
- **The domain is actually procedural.** A geocoder, a query engine, a rendering service, a pricing calculator. Forcing nouns onto `POST /calculations` adds a layer of translation nobody benefits from.
- **Everything is authenticated and per-user.** Then most responses are `Cache-Control: private, no-store`, and the shared-cache half of the argument doesn't apply to you. The retry and status-code halves still do — which is worth noticing, because they're the ones that prevented two of the three incidents.
- **Chasing hypermedia purity** when no client will ever follow a link (7.1b).
- **High-volume internal traffic where the serialization cost matters.** JSON text over HTTP/1.1 has a real per-call price; gRPC exists for this.

## Trade-offs

Once you have it, here's the bill.

- **Every new operation now begins with a modeling discussion.** Most are ten seconds; a few consume a whole design review and produce a URL nobody loves. This is a permanent, recurring tax on delivery speed, and it's the main reason teams drift back to verb endpoints when they're in a hurry.
- **Chattiness.** Resources are sized by the domain; screens are sized by the design. A detail page needing a ticket, its comments, its attachments, and the assignee's profile is four round trips — on mobile, four times a 150ms RTT before anything renders. Every remedy compromises the model: compound representations, `?include=comments,assignee`, a purpose-built endpoint for that screen, a backend-for-frontend, or GraphQL (Module 8). This is REST's largest practical cost, and it's structural rather than a mistake you can avoid.
- **Partial updates are genuinely unsettled.** PUT requires the whole representation, which means a client that fetched, edited one field, and put it back can silently overwrite a concurrent change (the fix is conditional requests, 7.4). PATCH is under-specified: JSON Merge Patch can't distinguish "set to null" from "leave alone," and JSON Patch can but is verbose enough that few clients use it correctly.
- **Idempotency keys are infrastructure.** A table, an expiry policy, a uniqueness constraint, a concurrency rule, and a documented window. Small, but it's yours to operate.
- **Caching becomes a correctness surface.** The moment you emit `Cache-Control: public`, a wrong cache key or a missing `Vary` is a cross-tenant data leak rather than a performance bug. Shared caches are the highest-consequence configuration in the request path.
- **Some things have no natural HTTP shape.** Bulk operations (7.3d), transactions spanning resources, multi-step workflows, and streaming all require either a convention you invent or a different protocol. The uniform interface is uniform precisely because it refuses to grow to fit these.
- **Discoverability doesn't come for free.** Consistent URLs make an API *learnable*, not self-describing. You still need documentation (7.2).

## Alternatives

- **RPC over HTTP** — JSON-RPC, or the pragmatic `POST /service.Method` style. Gains: direct mapping from functions, no modeling tax, naturally expresses actions. Gives up: everything in the diagram above. Best when both sides are yours.
- **tRPC and similar** — RPC with types derived from the server implementation, so the client breaks at compile time. Excellent inside a TypeScript monorepo; irrelevant across an organizational boundary.
- **gRPC** — a schema-first contract, efficient binary framing, real streaming, generated clients in every language. Costs: not directly callable from a browser without a proxy, not inspectable with ordinary HTTP tooling, and your existing observability sees one method and one code for all of it. Strong fit for internal service-to-service (Module 23, Module 36).
- **GraphQL** — the direct answer to chattiness: the client states exactly what it needs in one round trip. Gives up HTTP caching, per-endpoint rate limiting, and status-code semantics, and introduces query-cost analysis as a new operational concern. Module 8.
- **Asynchronous APIs** — webhooks (Module 17) and message queues (Module 10). For anything fire-and-forget or long-running, a request/response API is the wrong shape regardless of how it's designed.
- **JSON:API, OData, and similar conventions** — specifications layered on top of REST that fix the parts REST leaves open: filtering, sorting, pagination, relationships, error format. You get real tooling and zero bikeshedding; you pay in spec surface and in awkwardness whenever your domain doesn't match their assumptions.

## How to Achieve It

You can't renumber a live API. The path is additive, and each step is worth doing alone.

**Level 0 — stop expanding the problem.** New endpoints follow the new convention. Existing ones are frozen, not fixed. A written one-page convention (or an OpenAPI document, 7.2) is what makes this stick, because the alternative is re-litigating plural nouns in every code review.
*Signal you're here:* two endpoints doing the same thing under different names.

**Level 1 — give reads a GET.** Add `GET /tickets` next to `POST /api/getTickets`, serving the same data. Nothing breaks; clients migrate when convenient. You immediately get browser and CDN caching, safe automatic retries, and a route that shows up honestly in latency percentiles.
*Signal to move on:* a cache you're operating by hand, or read traffic dominating your database load.

**Level 2 — honest status codes on the new surface.** Do not retrofit these onto old endpoints: clients that check `success` and ignore the status will break in ways you can't see. New routes get real codes from day one, and your monitoring gets pointed at those routes first.
*Signal to move on:* an incident that your dashboards missed.

**Level 3 — idempotency keys on the paths where duplicates hurt.** Payments, order placement, message sending, provisioning. Not on everything — on the handful of operations where a duplicate is a customer-visible problem or costs money.
*Signal to move on:* one confirmed duplicate in production. That's the whole business case.

**Level 4 — conditional requests where concurrent edits collide.** `ETag` on the resource, `If-Match` required on writes, `412` when it doesn't hold. This is the lost-update fix and it's the direct continuation of the optimistic-locking discussion from Module 6.5. Covered in 7.4.
*Signal you need it:* two users editing the same record and one silently losing.

**Level 5 — retire the old surface.** Log per-endpoint, per-client usage, publish a deprecation schedule, and turn off what nobody calls. This is its own discipline (Module 33).

## Implementation

Go, for one reason: the standard library's HTTP types make method dispatch and status handling explicit rather than framework magic, which is what this article is about.

Here's the idempotency mechanism, since it's the part with a subtle failure mode.

```go
type IdemStore interface {
    // Reserve atomically claims the key; found=true means someone already has it.
    Reserve(ctx context.Context, tx *sql.Tx, tenant, key string) (prior []byte, found bool, err error)
    Complete(ctx context.Context, tx *sql.Tx, tenant, key string, body []byte) error
}

func (h *Handler) CreatePayment(w http.ResponseWriter, r *http.Request) {
    key := r.Header.Get("Idempotency-Key")
    if key == "" {
        writeProblem(w, http.StatusBadRequest, "Idempotency-Key header is required")
        return
    }
    tenant := TenantFromContext(r.Context())

    tx, err := h.db.BeginTx(r.Context(), nil)
    if err != nil {
        writeProblem(w, http.StatusServiceUnavailable, "try again")
        return
    }
    defer tx.Rollback()

    prior, found, err := h.idem.Reserve(r.Context(), tx, tenant, key)
    switch {
    case err != nil:
        writeProblem(w, http.StatusServiceUnavailable, "try again")
        return
    case found && prior != nil:
        // Completed earlier. Replay the stored response verbatim.
        w.Header().Set("Idempotent-Replay", "true")
        w.WriteHeader(http.StatusCreated)
        w.Write(prior)
        return
    case found:
        // Claimed but not finished: a duplicate is in flight right now.
        w.Header().Set("Retry-After", "1")
        writeProblem(w, http.StatusConflict, "a request with this key is in progress")
        return
    }

    payment, err := h.payments.Create(r.Context(), tx, tenant, req)
    // ...
    body, _ := json.Marshal(payment)

    // Same transaction as the effect. This is the line the whole mechanism rests on.
    if err := h.idem.Complete(r.Context(), tx, tenant, key, body); err != nil { /* ... */ }
    if err := tx.Commit(); err != nil { /* ... */ }

    w.Header().Set("Location", "/payments/"+payment.ID)
    w.WriteHeader(http.StatusCreated)
    w.Write(body)
}
```

Two asides worth more than the code around them.

**`Reserve` and `Complete` are in the caller's transaction on purpose.** Put the idempotency record in Redis, or in its own transaction, and you have reintroduced the dual write from 6.1 — a crash between the payment commit and the key write means the retry charges the customer twice. That is the exact bug the mechanism was built to prevent, so the storage choice isn't an implementation detail.

**The `found && prior == nil` branch is the concurrent case**, and it's the one most implementations miss because it doesn't show up in sequential testing. A unique index on `(tenant, key)` is what makes `Reserve` atomic; returning `409` says "your other attempt is still running." Returning `500` here would be actively harmful, since it invites the client to retry into the same collision.

And the status decision, isolated, because getting it wrong is what produces both false pages and invisible outages:

```go
func statusFor(err error) int {
    switch {
    case errors.Is(err, ErrNotFound):        return http.StatusNotFound   // or 403 — see above
    case errors.Is(err, ErrValidation):      return http.StatusUnprocessableEntity
    case errors.Is(err, ErrVersionConflict): return http.StatusPreconditionFailed
    case errors.Is(err, ErrQuotaExceeded):   return http.StatusTooManyRequests
    case errors.Is(err, context.DeadlineExceeded): return http.StatusGatewayTimeout
    default:                                 return http.StatusInternalServerError
    }
}
```

The default matters most. Everything not explicitly classified becomes a `500`, which means it becomes a page — and that's the correct bias. An unclassified error is, by definition, something you didn't anticipate. The failure to avoid is the opposite default, where unknown errors become `400` and a genuine outage looks like a stream of misbehaving clients.

## Further Reading

- **RFC 9110, _HTTP Semantics_** — the actual definitions of safe, idempotent, and cacheable, and the status code registry. Supersedes RFC 7231. §9.2 is two pages and settles most method arguments.
- **RFC 9111, _HTTP Caching_** — what `Cache-Control`, `Vary`, and freshness actually mean to the intermediaries in your path.
- **Roy Fielding, _Architectural Styles and the Design of Network-based Software Architectures_ (2000), ch. 5** — the original. Short, and clearer than its reputation.
- **Google API Improvement Proposals**, particularly AIP-121 (resource-oriented design) and AIP-136 (custom methods) — the most honest published treatment of what to do when an operation isn't a noun.
- **Microsoft REST API Guidelines** — a large, opinionated convention document; useful as a menu of decisions you'll otherwise make ad hoc.
- **Stripe's idempotent requests documentation** — the reference implementation of the pattern, including their retention window and error behavior.
- **_RESTful Web APIs_, Richardson & Amundsen** — the book that takes hypermedia seriously, which sets up 7.1b.
- **RFC 9457, _Problem Details for HTTP APIs_** — the standard error body, covered properly in 7.3b.

A TypeScript sibling would be worth writing here, and not for parity: in a typed monorepo the route definition can generate the client, which moves the contract from convention into the compiler, and it changes the argument for the uniform interface — you gain safety inside the boundary that the uniform interface was providing across it. Not yet written.

---

The habit to carry out of this: whenever a generic component in your request path needs application-specific knowledge to do its generic job, you are not using the protocol you are running on. A CDN configured to bypass, a retry policy hardcoded per endpoint, a dashboard that reads response bodies — each of those is a small fact the application knew and never said out loud.
