# Pagination, Filtering, and Sorting

_Module 7.3c — RESTful API Design & Implementation_

## The Problem

`GET /orders?page=3&per_page=50`, sorted newest first. It was written when the table had two thousand rows and it was correct. Four million rows later, four separate things are wrong with it.

**Deep pages are slow, and no index fixes it.** Page 1 returns in 4ms. Page 500 takes 900ms. Page 5,000 times out. The query plan is fine — it's using the index — but `LIMIT 50 OFFSET 250000` means the database walks 250,050 index entries and throws away 250,000 of them. The work is proportional to how far in you are, and that's the definition of the operation, not a tuning failure.

**A nightly export returns some orders twice and misses others.** The export script pages through the whole collection. Between its request for page 1 and page 2, three new orders arrive:

```
t0   sorted desc by id:  [100 99 98 … 51] 50 … 1
     page 1 (offset 0)  → 100 … 51

     three rows inserted

t1   sorted desc by id:  [103 102 101 100 … 1]
     page 2 (offset 50) → 53 52 51 50 … 4
                          ^^ ^^ ^^  already returned on page 1
```

Everything shifted down by three, so three rows are returned twice. When rows are *deleted* mid-scan the shift runs the other way and rows are silently skipped — which is worse, because duplicates get caught by a unique key on import and skips get caught by nobody. The reconciliation team found it four months later.

**The count is the slowest part of the request.** The page itself takes 4ms; `SELECT count(*)` with the same filters takes 1.2 seconds. It exists to render "Showing 1–50 of 4,183,209" above a page-number widget that no user has ever clicked past page 3.

**Identical requests return different rows.** Sorting by `created_at`, a bulk import gave 200 orders the same timestamp. Within that tie, row order is whatever the plan happens to produce, and it changes when statistics change. The same page requested twice is not the same page.

Meanwhile the filters grew the way filters do. `?status=open`. Then `?status=open,pending`. Then `?created_after=`. Then `?amount_gt=`. Then a customer needs `status = open OR (status = pending AND amount > 1000)` and there's no way to express it, so someone proposes a `filter` parameter with a small expression syntax.

Underneath all five: **a collection endpoint is a query interface**, and three things were never decided — what "position" in the collection means, what makes a result stable, and how much query power is being exposed.

## What It Is

Two strategies, and the difference is what "where I am" means.

**Offset pagination** says *skip the first N rows of the result set.* Position is an index into a list that is being rewritten while you read it.

**Keyset pagination** — also called seek, cursor, or page-token pagination — says *give me the rows after this specific point in the ordering.* Position is a value, not a count. The value is packaged into an opaque **cursor** that the client passes back verbatim.

```sql
-- offset: position is a number
ORDER BY created_at DESC, id DESC LIMIT 50 OFFSET 250000

-- keyset: position is a row
WHERE (created_at, id) < ('2026-03-01T10:00:00Z', '8f21')
ORDER BY created_at DESC, id DESC LIMIT 50
```

One disambiguation, because the word collides: a **cursor** here is a client-held token encoding a sort position. It is not a database cursor — the server-side kind that holds an open transaction and a live result set. Those don't survive across stateless HTTP requests, and reaching for them is a recurring wrong turn.

## Recognizing the Problem

- Page load time grows with page number.
- An export or sync job produces duplicate rows, or a record count that doesn't reconcile.
- The same request, repeated, returns rows in a different order.
- `count(*)` dominates the endpoint's latency profile.
- `?per_page=100000` is a request anyone can make and your server will try to serve.
- The list of query parameters on one endpoint has passed a dozen, and several are `_gt` / `_lt` variants.
- A customer asks for a filter combination you can't express and you're considering a syntax for it.
- Someone added a sortable column and a table started timing out.
- Your infinite-scroll UI occasionally shows the same item twice.
- A support question begins "why does page 4 sometimes skip an order?"

## How It Works

### Why offset costs what it costs

The database cannot skip rows it hasn't examined. Even with a perfect index, `OFFSET 250000` means traversing 250,000 index entries to find where to start. Cost is linear in page number, which means the last page is always the most expensive one — and the last page is exactly what exports and scrapers request.

Keyset replaces "skip N" with a range predicate that the index can satisfy directly. Every page costs the same as the first, because the index seeks straight to the anchor.

### Every sort must be a total order

This is the precondition, and it's the part most often missing.

If two rows can compare equal under your `ORDER BY`, their relative order is undefined and may vary between executions. Under offset pagination that shows up as ties randomly duplicated and skipped across the page boundary. Under keyset it's worse: the anchor `created_at < '…10:00:00Z'` skips *all* rows sharing that timestamp, or, with `<=`, returns them forever.

The fix is one line and it's non-negotiable: **append a unique column to every sort.**

```sql
ORDER BY created_at DESC, id DESC
```

Then `(created_at, id)` is unique, the row comparison is exact, and both strategies behave. Every sortable field the API offers needs this treatment, and the composite index has to match.

### What goes in a cursor

The sort key values of the last row returned, plus enough context to detect misuse:

```json
{ "k": ["2026-03-01T10:00:00Z", "8f21"], "s": "created_at:desc", "f": "a3f1c8" }
```

`s` is the sort, `f` is a fingerprint of the filters. Both exist because a cursor issued under `status=open` and replayed against `status=closed` produces results that are neither — the range predicate is anchored in a different ordering than the one being scanned. Detect the mismatch and return `400` with an `invalid_cursor` code (7.3b) rather than silently returning nonsense.

Two properties:

**Opacity is the contract.** Base64 is encoding, not encryption, and clients will decode it if they're curious — but the documented contract is that cursors are passed back verbatim and never constructed. That's what lets you change the sort key, add a tiebreaker, or switch strategies without breaking anyone (7.1b).

**A cursor is untrusted input.** It arrives in a URL from whoever wants to send one. Anything inside it must be validated exactly like a request body (7.3a), and nothing trust-bearing may be *derived* from it — tenant scoping is composed server-side from the authenticated principal, never read out of the cursor. If the cursor must carry something sensitive, sign it; the usual answer is to design it so it doesn't have to.

### What keyset gives up, honestly

| | offset | keyset |
|---|---|---|
| Jump to page 47 | yes | no |
| "Page 3 of 91" | yes, with a count | no |
| Cost per page | grows | constant |
| Stable across inserts | no | yes, for immutable sort keys |
| Arbitrary sort fields | any | needs a matching index |
| Paging backwards | yes | yes, with the comparison reversed |
| Bookmarkable page URL | yes | only the current position |

"No jump-to-page" is the real cost, and it's a product decision, not a technical one. If the UI has numbered page buttons, keyset can't serve it. The common resolution is offset with a hard cap — page numbers up to 10,000 rows, `400` beyond — which covers human browsing while refusing the traversals that hurt.

### Drift isn't fully solved, by anything

Keyset prevents the shift problem because the anchor doesn't move. It does not make the result set immutable. If a row's sort key changes while you're paging — you're sorting by `updated_at` and someone edits a record you've already passed — that row jumps ahead of your anchor and you'll see it twice. A row edited ahead of your anchor moves behind it and you'll never see it.

The options, in order of practicality:

1. **Sort by an immutable key** (`created_at, id`) for anything that must be scanned completely. This is why exports should never sort by `updated_at`.
2. **Filter to a point in time** — an explicit `as_of` bound, so the scan targets a range that can't grow.
3. **Snapshot the result set** into a job and serve pages from it — which is really an export (see Alternatives).

Transaction-level snapshots don't apply: repeatable read across a sequence of independent HTTP requests would mean holding a transaction open for the duration of a client's scroll.

### Counts are optional and usually not worth what they cost

Three honest answers:

- **`hasMore`** — request `limit + 1` rows, return `limit`, and report whether the extra one existed. Free, and it's what infinite scroll and "Next" buttons actually need.
- **An estimate** — `reltuples`-style statistics or the planner's row estimate. Fast, unfiltered or roughly filtered, and it wobbles between requests, which confuses users who watch the number change.
- **An exact count** — a second full query over the filtered set. Correct, expensive, and increasingly expensive as the table grows.

Cap it if you need something: display "10,000+" above a threshold. A product requirement for an exact filtered count on a large table is a requirement for a materialized counter or an asynchronously computed number, not for a `count(*)` in the request path.

### Filtering: a spectrum, not a binary

1. **Fixed parameters** — `?status=open&assignee=3`. Every shape is known, every shape can be indexed, nothing to parse.
2. **Field plus operator** — `?amount[gte]=1000&created_at[lt]=2026-03-01`. Still enumerable, still mappable to indexes, a small parser.
3. **An expression language** — RSQL/FIQL, OData `$filter`, JSON:API filters, Mongo-style JSON predicates. Arbitrary boolean combinations over allowed fields.
4. **Passthrough to the database.** Never.

Each step up multiplies the number of *query shapes* you must serve — and every query shape is a query plan you're implicitly promising to keep fast. At level 1 you can look at every plan. At level 3 you can't, because the set is combinatorial, so the guarantees have to come from limits instead: an allowlist of filterable fields, an allowlist of operators per field, a bound on expression complexity, and a statement timeout that turns a pathological query into a `504` rather than a stalled connection pool.

This is the same argument as GraphQL query cost analysis (Module 8), arriving from a different direction. Exposing query power means taking on query planning as a public-facing concern.

One rule regardless of level: **filters compose with authorization by construction.** Tenant scope is added to the query by the server; a `tenant_id` filter accepted from a client is a data breach waiting for someone to try it.

### Sorting has an index cost per option

Every sortable field needs a composite index ending in the tiebreaker, and multi-field sorts need one per combination you permit. Sorting by a joined or computed column is where cost explodes — that's a sort of the whole result set with no index to help, and it's the usual cause of "we added a column to the sort dropdown and the page died."

Allowlist sortable fields. Document the default. Make the default stable.

## When It's Appropriate

**Keyset** when:
- The collection grows without bound — orders, events, messages, audit logs (Module 19).
- The access pattern is "load more" or infinite scroll.
- Anyone is scanning the whole collection: exports, syncs, partner integrations.
- The natural sort is by time, which is also the immutable-key case that makes drift disappear.

**Offset** when:
- The collection is genuinely bounded — a few thousand rows, an admin table, a tenant's own records.
- Numbered pages are a stated product requirement.
- The endpoint is internal and low-traffic, and simplicity is worth more than constant cost.

**Level 2–3 filtering** when callers are partners or analysts whose queries you can't anticipate, or when the surface is explicitly a reporting one. **Level 1** for everything else — most APIs never need more, and the ones that do are usually asking for a search engine (Module 12), where faceting, relevance, and arbitrary combination are the native model rather than something bolted onto a transactional store.

## When It's Unnecessary or Overkill

- **Collections with a real bound.** A user's API keys, a tenant's webhook subscriptions, the seven statuses in an enum. Return all of them. Paginating a list that cannot exceed fifty items adds a cursor, a `Link` header, and a client loop for nothing.
- **Building a filter DSL for two consumers with three filters between them.** The expression parser will outlive the requirement.
- **Cursors on an admin screen whose entire design is page numbers.** You'd be removing a feature to fix a problem that table doesn't have.
- **Exact counts nobody renders.** Check the UI before paying for one.
- **Signing cursors that contain only a public sort key** from a query already scoped server-side. Validate them; encryption is a different requirement.

## Trade-offs

- **Keyset trades random access for constant cost.** No jump-to-page, no total pages, no bookmarkable "page 12" URL. If any of those are product requirements, this is a product conversation.
- **Cursors couple you to an index.** Every allowed sort needs a composite index matching it, so adding a sortable field is a database decision wearing an API decision's clothes.
- **Cursors expire in practice.** Filter changes, sort changes, and schema changes all invalidate them, so clients need a restart path and a documented error, and any UI that stores a cursor across sessions needs to handle rejection.
- **Result drift is inherent to stateless paging over mutable data.** Keyset narrows it to rows whose sort key changes; only an immutable sort key removes it. No strategy makes a moving collection look still.
- **Paginated responses cache badly.** Every cursor is a distinct URL, contents shift, and hit rates are low. The caching benefits from 7.1a mostly don't apply to collection endpoints.
- **Filter expressiveness is public query-planner surface.** Unindexed combinations, timeouts, and a denial-of-service vector that costs the attacker one request and you a table scan. The mitigations — allowlists, complexity limits, timeouts — are permanent operational work.
- **Paging is a poor bulk transport even when it's fast.** Four million rows at 50 per page is 80,000 round trips. Constant cost per page doesn't rescue that; it's the wrong shape for the job.
- **Expansion multiplies per-page work.** `?include=customer,items` on a 50-row page is an N+1 unless batched (Module 6.4), and it's how a cheap page becomes an expensive one.

## Alternatives

- **Return everything**, for genuinely bounded collections.
- **Streaming responses** — NDJSON over chunked transfer, one row at a time. One request, constant memory on both ends, no cursor. Fragile over flaky networks because there's no resume, which is exactly what cursors buy.
- **An async export job** — `POST /exports` → `202` → poll → download a file (Modules 10 and 11). The correct answer to "give me all four million rows," and worth offering explicitly, because otherwise someone will build it out of your paginated endpoint at 3am.
- **A change feed** — `?since=<watermark>` plus tombstones for deletions. Consumers maintaining a mirror of your data have a *different requirement* from consumers browsing it, and serving both with one paginated endpoint satisfies neither. Related to change data capture (Module 38.4).
- **A search index** (Module 12) once filtering, faceting, and relevance are the point rather than an afterthought.
- **GraphQL Relay connections** — a standardized `edges`/`pageInfo`/`cursor` model. Same mechanics as everything above, with the conventions already settled.

## How to Achieve It

**Level 0 — bound the request.** Default page size, maximum page size, `400` beyond it. One afternoon, and it removes the `?per_page=100000` class of incident entirely.
*Signal you're here:* a client can ask for the whole table.

**Level 1 — make every sort a total order.** Append the primary key to each allowed `ORDER BY`, add the composite indexes. This fixes non-deterministic ties immediately and is a prerequisite for everything below.
*Signal you need it:* identical requests returning different rows.

**Level 2 — emit `Link: rel="next"` with an opaque cursor**, alongside the existing offset parameters. Nothing breaks; clients that follow the link get the new behavior (7.1b, level 0).
*Signal to move on:* a client hand-building `?page=N`.

**Level 3 — implement `next` with keyset, and cap offset.** Deep offsets return `400` past a threshold. Deep paging stops being slow by stopping being possible.
*Signal to move on:* the p99 on your list endpoint being owned by page numbers in the thousands.

**Level 4 — replace exact counts with `hasMore`**, keeping exact counts only where a specific screen requires one, and capping the display.
*Signal you're here:* `count(*)` visible in your slow query log.

**Level 5 — allowlist filterable and sortable fields**, with an index per allowed sort, per-field operators, and a statement timeout. Publish the allowlist in the spec (7.2).
*Signal to move on:* an outage caused by a filter combination nobody had run before.

## Implementation

Java with plain JDBC, because the mechanism here *is* the SQL and an ORM would hide the two details that matter most.

The cursor, and its encoding:

```java
record Cursor(Instant createdAt, UUID id, String sort, String filterHash) {

    String encode() {
        return Base64.getUrlEncoder().withoutPadding()
            .encodeToString(JSON.writeValueAsBytes(this));
    }

    static Cursor decode(String raw, String sort, String filterHash) {
        Cursor c;
        try { c = JSON.readValue(Base64.getUrlDecoder().decode(raw), Cursor.class); }
        catch (Exception e) { throw new DomainException("invalid_cursor", 400); }

        if (!c.sort().equals(sort) || !c.filterHash().equals(filterHash)) {
            throw new DomainException("invalid_cursor", 400,
                "Cursor does not match the current sort or filters");
        }
        return c;
    }
}
```

The query:

```java
static final String PAGE = """
    SELECT id, created_at, status, amount_minor
      FROM orders
     WHERE tenant_id = ?
       AND (?::text IS NULL OR status = ?)
       AND (created_at, id) < (?, ?)
     ORDER BY created_at DESC, id DESC
     LIMIT ?
    """;

List<Order> rows = jdbc.query(
    cursor == null ? PAGE.replace("AND (created_at, id) < (?, ?)", "") : PAGE,
    ps -> bind(ps, tenantId, status, cursor, limit + 1),   // one extra row
    orderMapper);

boolean hasMore = rows.size() > limit;
if (hasMore) rows = rows.subList(0, limit);
```

And the response:

```java
if (hasMore) {
    Order last = rows.get(rows.size() - 1);
    String next = new Cursor(last.createdAt(), last.id(), sort, filterHash).encode();
    response.addHeader("Link", "</orders?cursor=" + next + ">; rel=\"next\"");
}
```

Four asides, because each is a place implementations go wrong.

**The row comparison has to stay a row comparison.** `(created_at, id) < (?, ?)` is the form that lets the planner seek directly into the index on `(tenant_id, created_at DESC, id DESC)`. Expanding it by hand into `created_at < ? OR (created_at = ? AND id < ?)` is logically identical and plans badly on several engines — the `OR` defeats the index seek and you get a scan. It's a pure syntax difference with an order-of-magnitude consequence.

**`limit + 1` is how you avoid a count.** One extra row answers "is there a next page" exactly, for free, with no second query.

**The first-page branch is genuinely awkward and worth doing explicitly.** Conditional SQL assembly is unpleasant; sentinel values (`'infinity'`, a max UUID) are worse, because they look clever right up until a real row equals the sentinel. Two named statements, or a query builder, are both better than pretending one string covers both cases.

**Nothing security-relevant comes out of the cursor.** `tenant_id` is bound from the authenticated principal on every call. A cursor carrying a tenant id would be a client-supplied authorization claim, which is the whole of the vulnerability.

One piece of ecosystem knowledge worth having: Spring Data 3.1+ implements this natively as `ScrollPosition.keyset()` returning a `Window<T>`, and it enforces the tiebreaker requirement by demanding a unique sort property. Knowing the mechanism above is what lets you tell whether the framework's version is doing what you need — particularly around filter fingerprinting, which it leaves to you.

## Further Reading

- **Markus Winand, _Use The Index, Luke_ — "Paging Through Results"** and the companion **use-the-index-luke.com/no-offset** — the clearest available treatment of why offset costs what it costs, with plans.
- **PostgreSQL documentation on row constructor comparison** — the exact semantics of `(a, b) < (c, d)`, which is not the same as comparing the columns individually.
- **Google AIP-158, _Pagination_** — the `page_token` / `page_size` conventions, including the recommendation that page size be advisory rather than guaranteed.
- **The GraphQL Cursor Connections Specification** — the most fully specified cursor model in public use, worth reading even for a REST API.
- **JSON:API pagination** and **Stripe's list pagination** (`starting_after`, `has_more`) — two real, documented, long-lived designs at opposite ends of the formality scale.
- **PostgreSQL's row count estimation techniques** (`reltuples`, planner estimates) — for the cheap-approximate-count option.
- **RSQL/FIQL** and **OData `$filter`** — read these before designing a filter syntax, mostly to calibrate how much specification a query language actually requires.

A TypeScript sibling would add something specific: ORMs like Prisma and Drizzle expose cursor pagination as a first-class option, and seeing how they handle — or quietly fail to handle — the tiebreaker and the filter fingerprint is instructive precisely because the SQL is hidden. The interesting question is what the abstraction leaves to you. Not yet written.

---

The habit to carry: a collection endpoint is a query interface, and every parameter you add to it is a promise about a query plan. Before adding a filter or a sort option, ask which index serves it — and if the answer is "none, but the table is small," write down what "small" means, because that assumption is the one that expires silently.
