# Error Responses

_Module 7.3b — RESTful API Design & Implementation_

## The Problem

A client engineer is writing the failure handling for a payments integration. For every failed request they need to decide four things: retry or not, show the user something or not, alert someone or not, and if it's a user-facing error, what to say.

Here is what the API actually returns, collected over two days of testing:

```json
400  {"error": "Invalid request"}
404  {"message": "Not found"}
422  {"errors": [{"field": "amount", "msg": "must be positive"}]}
402  {"code": 4021, "detail": "Do not honour"}
500  Internal Server Error                     ← text/plain, from the proxy
502  <html><head><title>502 Bad Gateway</title>…
```

Six shapes. Three of them come from code nobody at the company wrote — a framework default, a gateway, a load balancer. No single handler can parse this.

So the client does what every client does in this situation:

```js
if (body?.error?.includes("insufficient funds")) { showTopUpPrompt(); }
else if (res.status === 400) { showGenericError(); }
```

Which produces the next three incidents.

**A copy edit breaks production.** Someone rewords the message to "Insufficient balance" for consistency with the dashboard. The string match fails. Users stop seeing the top-up prompt and start seeing a generic error, and nothing in any test caught it because the API's behavior didn't change — only its prose did.

**The same condition arrives two ways.** A declined card returns `402` from the charge endpoint and `400` from the subscription endpoint, because they were written by different people two years apart. The client's retry logic treats one as retryable.

**`400` is thirty conditions wearing one hat.** Bad date format, expired card, subscription already cancelled, amount over the tenant's limit — all `400`, all needing different UI. The status code tells the client whose fault it was and nothing else, so the client is back to reading message strings.

Then the failure in the other direction. To help with debugging, someone adds detail to the error body. Now `500`s include a stack trace and a fragment of SQL, and the `403` says *"user alice@corp.com does not have role billing:write"* — which confirms an email address is registered and names your internal permission scheme to anyone who asks.

And through all of it, when a customer reports "the payment failed around 3pm," support has no way to find the request. Nothing in the response identifies it.

The underlying shape: **a status code is about five bits of information.** It says who was at fault and roughly why (7.1a). Everything else the caller needs — which of thirty conditions, which field, whether to retry, what to tell the user, how to reference this later — has to travel in the body, and nobody ever designed the body.

## What It Is

What's needed is a **standard error representation**: one body shape, used by every endpoint, carrying a machine-readable identifier for the condition alongside human-readable text.

The standard is **RFC 9457, Problem Details for HTTP APIs** (which obsoletes RFC 7807). It defines a media type, `application/problem+json`, and a small set of members:

```json
{
  "type":     "https://api.example.com/problems/insufficient-funds",
  "title":    "Insufficient funds",
  "status":   402,
  "detail":   "The card ending 4242 was declined for a charge of $142.00.",
  "instance": "/payments/8f21",

  "code":     "insufficient_funds",
  "traceId":  "01J9F7K2QН3XZ4",
  "retryable": false
}
```

`type` identifies the *kind* of problem and is the stable part. `title` is a short human summary of that kind. `detail` is about this specific occurrence. `instance` identifies the occurrence. Anything else — the last three fields here — is an extension member, and extensions are where most of the practical value lives.

The framing that makes the rest of this article follow: **an error response has three audiences**, and almost every mistake in error design comes from serving one audience with a field meant for another.

| Audience | Needs | Field |
|---|---|---|
| The **program** | To branch: retry, re-auth, show a specific screen | A stable machine code |
| The **end user** | To know what to do next | A message — often localized, often better written by the client |
| The **engineer** | To find out what happened | A correlation id pointing into logs — *not* the failure's details |

The first incident above — branching on message text — is the program being forced to use the user's field, because its own field didn't exist. The leak is the engineer's needs being met in a response the user's browser can read.

## Recognizing the Problem

- Client code matches on message substrings.
- Two endpoints return different status codes for the same business condition.
- Your `400` responses cover more than a dozen distinguishable situations.
- Support cannot locate the log line for a customer's failed request.
- A production `500` body contains a class name, a file path, or SQL.
- Clients retry things that will never succeed, or give up on things that would.
- The mobile app shows a raw server message in a dialog, in English, to a French user.
- Nobody can list the error conditions your API can produce.
- The error format differs between your handlers, your auth middleware, and your gateway.
- Changing a validation message requires checking whether any client depends on it.

## How It Works

### The code is the contract; the message is not

The machine-readable identifier — whether you use the RFC's `type` URI or a short `code` string — is API surface, exactly like a field name. Adding new ones is backward compatible. Renaming or removing one is a breaking change (Module 33).

The message text is explicitly *not* contract, and saying so in your documentation is what frees you to improve it. That freedom only exists if clients have something else to branch on.

The design question, then, is what set of codes to define, and there's a single rule that answers it:

> **A condition deserves its own code when a client would do something different about it.**

Not when it's a different exception class. Not when it happens in a different module. If `card_expired` and `card_declined` both lead to the same "update your payment method" screen, they can share a code. If `insufficient_funds` produces a top-up prompt while `card_declined` produces a card form, those are two codes.

The common failure is exposing your internal exception hierarchy one-to-one. That's a catalogue designed around your code structure, which means it changes when you refactor, and it's both too detailed in places nobody branches and too coarse in the places they do.

### Field-level errors

For validation failures (7.3a), the client needs locations, not just a condition. This is an extension member:

```json
{
  "type": "https://api.example.com/problems/validation-failed",
  "title": "Validation failed",
  "status": 422,
  "code": "validation_failed",
  "errors": [
    { "pointer": "/parcels/2/weightGrams", "code": "out_of_range",
      "message": "must be between 1 and 30000" },
    { "pointer": "/currency", "code": "unsupported_value",
      "message": "must be one of USD, EUR, GBP" }
  ]
}
```

JSON Pointer (RFC 6901) handles nesting and array indices, which is what makes this work for anything beyond flat forms. Each entry gets its own code, for the same reason the top level does: a client rendering a form may want to treat "missing" differently from "malformed."

### Three signals about retrying, and only one of them is yours to invent

- **Status class** — coarse and universal. `4xx` won't help, `5xx` might.
- **`Retry-After`** — authoritative, and a header, not a body field. Mandatory with `429` and `503` (Module 18).
- **An explicit hint** for genuinely ambiguous cases. A `409` from a version conflict is retryable after refetching; a `409` from "this order is already shipped" never is. That distinction can't be derived from anything else.

The mistake worth avoiding is building a retry protocol in the body when the header already exists. Emit `Retry-After`, and use a body field only for the retryability the header can't express.

### Correlation is the cheapest thing in this article

Every error response carries a trace or request id that matches the one in your logs and traces (Module 19). Support pastes it into a search and finds the request.

It's safe to expose precisely because it's meaningless to anyone without log access — which is the same property that makes it useless as an attack aid. The cost is one field; the payoff is that "it failed around 3pm" stops being an investigation.

### The asymmetry between 4xx and 5xx

**`4xx` bodies can be specific.** The caller already knows what they sent; telling them exactly what was wrong with it reveals nothing they didn't have.

**`5xx` bodies should be generic.** The caller can do nothing with the detail, and detail is where leaks live. A `5xx` should carry a title, a status, and a trace id, and nothing else. Everything you wanted to put in that body belongs in the log line the trace id points to.

Never in any body: stack traces, SQL, internal hostnames, class or file names, library versions. And two disclosure decisions that need a deliberate answer rather than a default:

- **Existence.** Whether a `404` or a `403` is correct for another tenant's resource (7.1a), and whether "no such user" and "wrong password" are distinguishable. Both are security choices that make errors less helpful on purpose.
- **Enumeration in validation errors.** `"must be one of USD, EUR, GBP"` is excellent developer experience and does disclose your configuration. Usually fine; occasionally not.

### The errors you didn't write

This is the part most error-handling work misses, and it's why the problem section had six shapes instead of two:

```
client ──► CDN ──────► gateway ─────► your app
             │            │              └── handlers: problem+json    ✓
             │            ├── auth plugin 401: {"message": "…"}        ✗
             │            └── 413 payload too large, gateway default   ✗
             └── 502 HTML when it can't reach the gateway at all       ✗
```

Your application handles the errors it generates. It cannot handle the ones produced when it is never reached: gateway timeouts, request-size rejections, auth middleware, TLS failures, load balancer error pages.

Three things follow. Shape what you can — most gateways support custom error responses. Document what you can't. And require every client to handle *"the body is not JSON"* as a case, because at some point it won't be, and a client that assumes otherwise fails with a parse error that hides the real problem.

## When It's Appropriate

- **Any API whose clients branch on failures** — which, in practice, is any API with a UI in front of it.
- **Public and partner APIs**, where the error catalogue is a documented part of the product and support cost scales directly with how legible it is.
- **Domains with many distinguishable business failures** — payments above all, then provisioning, compliance checks, and anything with a workflow state machine.
- **Multiple client platforms.** The message/code split matters most when three clients each render their own copy in their own locales.
- **Anywhere support is fielding "it failed" reports.** The correlation id alone justifies the work.

## When It's Unnecessary or Overkill

- **A small internal service whose only caller logs and gives up.** A status code and a sentence is fine.
- **Full RFC vocabulary for a handful of conditions.** `{"code": "...", "message": "..."}` used consistently beats partial conformance to problem+json. Consistency is the property doing the work; the media type is how you get ecosystem support for it.
- **A unique code per internal failure mode.** Codes nobody branches on are a catalogue you maintain for nothing.
- **Server-side localization** when you control the clients. They know the user's locale, their platform's formatting rules, and their own UI copy standards. Localize on the server when your callers are scripts, CLIs, and partners who'll surface your text directly.
- **Dereferenceable `type` URIs** before you have documentation to put behind them. A `type` URI that returns 404 is worse than a bare string code.

## Trade-offs

- **The code catalogue becomes surface you version.** It only grows, it can't be renamed, and every addition needs documenting. That's a permanent maintenance stream in exchange for clients that don't parse prose.
- **Helpfulness and disclosure trade against each other,** endpoint by endpoint, forever. There's no setting that's right globally, and the safest choice is often the one that produces a worse developer experience.
- **Localization has no comfortable home.** Server-side means locale negotiation, a translation pipeline, and UX copy moving into the backend release cycle. Client-side means every client maintains a code-to-message table that silently falls behind when you add a code — and the fallback for an unknown code has to be something.
- **You don't control the whole surface.** Shaping gateway, middleware, and proxy errors is real work, partly blocked on infrastructure you may not own, and it's never quite complete.
- **Rich errors aren't always producible.** A failure halfway through a transaction may have nothing structured to say; a timeout has nothing at all. The generic fallback has to be good, because it will be common.
- **Codes can couple clients to your internals.** Too specific and a refactor becomes a breaking change; too coarse and clients go back to parsing messages. The "what does the client do differently" rule is the only reliable way to sit between them.
- **High-volume `4xx`s cost something.** Expired-token `401`s at scale multiply body size and log volume. Keep the common ones small.

## Alternatives

- **Status code, empty body.** Entirely adequate for internal CRUD where failure handling is "log it." Stops being adequate the moment a human sees the result.
- **A bespoke envelope** — `{"success": false, "error": {"code", "message"}}`. Functionally equivalent, widely used, and gives up the media type and any tooling that recognizes it. Note the distinct mistake of wrapping *successful* responses the same way, which throws away the status code entirely (7.1a).
- **GraphQL's `errors` array.** Partial success is native — some fields resolve, some don't — which is genuinely better for compound queries, at the cost of `200 OK` on failures and infrastructure that can no longer see error rates. Module 8.
- **gRPC's status codes plus `google.rpc` error details.** Worth studying even if you'll never use gRPC: `ErrorInfo` (reason + domain + metadata), `BadRequest.FieldViolation`, `RetryInfo`, `QuotaFailure`, `PreconditionFailure` is the most carefully designed error taxonomy in wide use, and it maps onto problem+json extensions almost directly.
- **Framework defaults.** The do-nothing option, and precisely what produced the six shapes at the top.

## How to Achieve It

**Level 0 — one shape, one place.** A single global handler that converts every failure, including unhandled exceptions, into the same body. Add a trace id to all of them.
*Signal you're here:* more than two error shapes in your own responses.

**Level 1 — stop leaking.** Strip stack traces and internal identifiers from production `5xx`s; make the generic fallback carry a trace id and nothing else.
*Signal to move on:* an error body containing a class name.

**Level 2 — find the codes clients already need.** Grep client code for message-string matching. Every hit is a condition that needed a code and didn't have one — that's the inventory, and it's better than any list you'd design from the server side.
*Signal to move on:* a message change that broke a client.

**Level 3 — field-level errors for validation**, with JSON Pointer locations, aggregated (7.3a).

**Level 4 — shape the errors you don't own.** Gateway defaults, auth middleware, size limits. Document whatever remains, and confirm clients handle non-JSON bodies.
*Signal you need it:* an HTML error page reaching a mobile client.

**Level 5 — publish the catalogue.** Codes in the OpenAPI document (7.2), each `type` URI resolving to real documentation, and a CI gate against removing one.

## Implementation

Go, picking up directly from the `statusFor(err)` sketch in 7.1a — that function chose a status; this is the whole response.

```go
type Problem struct {
    Type     string   `json:"type"`
    Title    string   `json:"title"`
    Status   int      `json:"status"`
    Detail   string   `json:"detail,omitempty"`
    Code     string   `json:"code"`
    TraceID  string   `json:"traceId"`
    Errors   []Field  `json:"errors,omitempty"`
    Retryable *bool   `json:"retryable,omitempty"`
}

type Field struct {
    Pointer string `json:"pointer"`
    Code    string `json:"code"`
    Message string `json:"message"`
}
```

A domain error carries what the boundary needs to render it:

```go
type DomainError struct {
    Code       string   // stable: "insufficient_funds"
    Status     int
    Detail     string   // safe to show the caller
    Fields     []Field
    Retryable  *bool
    cause      error    // logged, never serialized
}

func (e *DomainError) Error() string { return e.Code }
func (e *DomainError) Unwrap() error { return e.cause }
```

And one place turns any error into a response:

```go
func WriteError(w http.ResponseWriter, r *http.Request, err error) {
    traceID := trace.IDFromContext(r.Context())

    var de *DomainError
    if errors.As(err, &de) {
        log.Warn("request failed", "code", de.Code, "trace", traceID, "err", err)
        writeProblem(w, Problem{
            Type: "https://api.example.com/problems/" + de.Code,
            Title: titles[de.Code], Status: de.Status, Detail: de.Detail,
            Code: de.Code, TraceID: traceID,
            Errors: de.Fields, Retryable: de.Retryable,
        })
        return
    }

    // Unknown: log everything, say nothing.
    log.Error("unhandled error", "trace", traceID, "err", err)
    writeProblem(w, Problem{
        Type:   "https://api.example.com/problems/internal-error",
        Title:  "Internal server error",
        Status: 500,
        Code:   "internal_error",
        TraceID: traceID,
    })
}

func writeProblem(w http.ResponseWriter, p Problem) {
    w.Header().Set("Content-Type", "application/problem+json")
    w.WriteHeader(p.Status)
    json.NewEncoder(w).Encode(p)
}
```

Three asides.

**The default branch is where every leak in this article would happen.** The temptation is `Detail: err.Error()` — it's one word, it makes debugging easier, and it's how SQL fragments and internal hostnames reach customers. The `cause` field exists so that information has somewhere to go: `Unwrap` keeps it available to `errors.Is` and to the log line, and `json` tags keep it out of the response.

**`titles` is a map from code to short text, and it lives next to the catalogue, not next to the error site.** That's what makes the catalogue enumerable — you can print the full list of codes your API can emit, which is what 7.2 needs in order to document them and what CI needs in order to gate removals. Constructing titles ad hoc at each `return` site means nobody can ever produce that list.

**`Retryable` is a pointer on purpose.** Three states: yes, no, and *not stated* — where the client should fall back to the status class. A bare `bool` would silently claim "not retryable" for every error that never considered the question, which is worse than saying nothing, because clients would believe it.

## Further Reading

- **RFC 9457, _Problem Details for HTTP APIs_** — short, and it obsoletes RFC 7807, so check which one a library implements before adopting it.
- **RFC 6901, _JSON Pointer_** — the location syntax for field-level errors.
- **Google's API design guide, "Errors"**, and the `google.rpc` error detail types — the best-designed error taxonomy in general use, and directly transferable to problem+json extensions.
- **Stripe's error and decline-code reference** — a real catalogue at scale, and the clearest demonstration of codes defined by what the client should do rather than by internal structure.
- **Twilio's error catalogue** — an example of dereferenceable `type`-style URIs, where each code resolves to a page with causes and fixes.
- **Zalando's RESTful API Guidelines**, error handling section — opinionated, specific, and easy to adapt into a Spectral ruleset (7.2).
- **OWASP's guidance on improper error handling** — the disclosure half, with the specific leaks worth grepping your responses for.

A Java sibling is worth writing: Spring 6 ships `ProblemDetail` and `ErrorResponseException` as framework types, and `@ControllerAdvice` makes the global handler a first-class construct — which changes the shape of the problem, because exception-driven flow means the "unknown error" path catches things thrown from deep inside libraries you didn't write, and the default-branch discipline above becomes much harder to hold. Not yet written.

---

The habit to carry: when you're deciding how much to put in an error body, ask which of the three audiences each field is for. A field the program can't branch on, a user can't act on, and an engineer can't search on isn't helping anyone — and if it describes how your server is built, it's actively working against you.
