# Conditional Requests

_Module 7.4a — RESTful API Design & Implementation_

## The Problem

Two incidents, from different teams, that turn out to be the same question.

### The edit that vanished

Two support agents work the same ticket.

```
14:02  Agent A  GET  /tickets/8f21   → priority: low, assignee: unassigned
14:03  Agent B  GET  /tickets/8f21   → priority: low, assignee: unassigned
14:05  Agent A  PUT  /tickets/8f21   → priority: HIGH, assignee: unassigned
14:06  Agent B  PUT  /tickets/8f21   → priority: low,  assignee: B
```

B's request is well-formed, authorized, and valid. It succeeds. A's escalation is gone, silently — B never saw it, A never learns, and the audit log shows two successful saves.

This is the lost update from Module 6.5, but the version that lives inside a database transaction doesn't reach here. The race spans three minutes, two HTTP requests, and no transaction at all. A row version column solves it only if the version makes the round trip to the client and back — which means the real question is how it travels.

And notice what makes `PUT` structurally vulnerable: it carries a full representation that the client read at some earlier moment. Every `PUT` implicitly means *"set this resource to what I believe it should be, based on what I saw N seconds ago,"* and the server has no idea what N is.

### The poll that transfers nothing new

A mobile client refreshes a ticket every 30 seconds. Ninety-five percent of the time, nothing has changed. Each poll transfers 14KB, runs a database read, and serializes JSON. Ten thousand clients at two polls a minute is 333 requests per second of near-identical payloads — and on the client side, bytes that cost battery and mobile data.

### The same question, twice

> **Has this changed since I last saw it?**

- Asked before *sending* a response: if not, don't send it again.
- Asked before *applying* a write: if it has, don't let me overwrite blindly.

HTTP answers both with one mechanism, and the fact that it's one mechanism is the reason to use the protocol's version rather than inventing a `version` field in your JSON.

## What It Is

A **conditional request** carries a precondition that the server evaluates before acting.

The server first hands the client a **validator** — an opaque token identifying the current version of a representation:

```
200 OK
ETag: W/"42"
```

The client sends it back in a precondition header:

| Header | Question | Used with | On failure |
|---|---|---|---|
| `If-None-Match` | Is it still this? Then skip the body | `GET` | `304 Not Modified` |
| `If-Match` | Is it still this? Then apply my write | `PUT` / `PATCH` / `DELETE` | `412 Precondition Failed` |
| `If-Modified-Since` | Time-based `If-None-Match` | `GET` | `304` |
| `If-Unmodified-Since` | Time-based `If-Match` | writes | `412` |
| `If-None-Match: *` | Does it not exist yet? | `PUT` (create-only) | `412` |

Two clarifications that prevent most of the confusion:

**An `ETag` is not required to be a hash.** It's an opaque string. A row version, a sequence number, or a UUID regenerated on each write are all valid — and cheaper.

**Validators identify representations, not resources.** The same ticket rendered as JSON and as XML are two representations and need two validators, which is why content negotiation and `Vary` are entangled with this.

## Recognizing the Problem

- Two users edit the same record and one edit disappears with no error.
- "Who changed this back?" appears in your support queue.
- A polling client transfers the same payload dozens of times an hour.
- Mobile users report battery or data usage out of proportion to what the app does.
- A `PUT` endpoint accepts a representation the client fetched an hour ago without comment.
- Your API has a `version` field in JSON bodies that clients are expected to echo back.
- Bandwidth costs scale with poll frequency rather than with change frequency.
- A dashboard refresh reliably produces identical responses.
- Automation and a human write the same resource, and the automation always wins.

## How It Works

```
                    ETag: W/"42"
   server ──────────────────────────────► client stores it
                                                 │
          ┌──────────────────────────────────────┤
          │  If-None-Match: W/"42"   still 42? don't resend  →  304
          └  If-Match:      W/"42"   still 42? then apply    →  200 / 412
```

One token, two questions, opposite polarity. That symmetry is the whole design.

### Choosing a validator

| Source | Cost | Accuracy |
|---|---|---|
| **Row version column** | Free — you likely have it from 6.5 | Exact, monotonic |
| **`updated_at` timestamp** | Free | Resolution-limited; two writes in the same millisecond collide; clock skew across nodes |
| **Hash of the rendered body** | Requires rendering it | Exact, including embedded data |
| **Composite** (max version across included entities) | Cheap query | Correct for aggregates — and required for them |

The composite row is the one that gets skipped, and it's the most common ETag bug in production. If `GET /tickets/8f21` returns the ticket *with its comments embedded*, then an ETag derived from the ticket row alone will not change when a comment is edited. Clients hold stale data indefinitely and every layer of the system reports it as working. **The validator must cover everything the representation includes** — no exceptions, and it's worth writing a test that edits an embedded entity and asserts the ETag moved.

### Strong versus weak

`"42"` is strong: byte-for-byte identical. `W/"42"` is weak: semantically equivalent.

JSON APIs are almost always honestly weak — key order, whitespace, and any timestamp rendered at serialization time can vary without the resource changing. Range requests need strong validators; conditional GET and `If-Match` work fine with weak ones. Compression in the path also complicates byte-identity, which is another reason `W/` is usually the truthful choice.

### The read path, and what a 304 actually saves

```
GET /tickets/8f21
→ 200 OK, ETag: W/"42", Cache-Control: private, no-cache        [14 KB]

GET /tickets/8f21    If-None-Match: W/"42"
→ 304 Not Modified                                              [~200 B, no body]
```

Here is the accounting most treatments skip: **a 304 saves bandwidth and serialization. It does not automatically save the database read.** To know that version 42 is still current, the server has to find out the current version — and if that means loading the row exactly as it would for a `200`, you've saved the JSON encoding and the transfer, and nothing else.

That's still a real win on mobile and at CDN scale. It is not the win people assume when they say "we added ETags for performance." Making a 304 genuinely cheap requires the validator to be readable without doing the full work: a version cached in Redis keyed by resource id (Module 13), a narrow `SELECT version` before the full load, or a CDN answering the revalidation entirely.

Measure it. The difference between "we save 14KB" and "we save the request" is an order of magnitude, and only one of them is true by default.

### The write path

```
GET /tickets/8f21                          → 200, ETag: W/"42"
                                             (someone else writes → 43)
PUT /tickets/8f21   If-Match: W/"42"       → 412 Precondition Failed
```

The server maps this straight onto the mechanism from 6.5:

```sql
UPDATE tickets SET …, version = version + 1
 WHERE id = ? AND tenant_id = ? AND version = 42
```

Zero rows affected means the precondition failed. This is optimistic concurrency control expressed in the protocol rather than in your JSON schema, which means a generic HTTP client, a proxy, and a developer reading the wire can all understand it without knowing your domain (7.1a).

**Require it rather than supporting it.** If a `PUT` arrives without `If-Match` on a resource where lost updates matter, return `428 Precondition Required` (RFC 6585). Optional preconditions mean the safe path is opt-in, and every client written in a hurry gets last-writer-wins semantics — which is the first incident, unchanged.

`PATCH` narrows the window considerably, since a client sends only the fields it touched, and independent fields don't collide. `PATCH` with `If-Match` is still correct; `PATCH` without it is "last writer wins, per field," which is frequently acceptable and should be a decision you documented rather than a default you inherited.

`DELETE` takes `If-Match` too, and it's the difference between "delete this ticket" and "delete this ticket as I last saw it."

`If-None-Match: *` on a `PUT` means *only if it doesn't already exist* — the create-safe form when clients generate their own ids.

### Collections are harder than they look

An ETag for `GET /tickets` can be built from `max(updated_at)` plus a row count, and it will be wrong in an instructive way: deleting a row doesn't advance the maximum, and if the count is also part of it, a simultaneous insert and delete cancel out. Add per-user filtering and pagination cursors (7.3c) and the validator has to cover those too.

Collection validators are viable, and they're fiddly enough that they should be a deliberate project rather than an afternoon's addition.

### One distributed failure worth knowing

If reads come from a replica and writes go to the primary, a client that writes and immediately re-reads can receive an ETag *older* than the write it just made. Its next conditional write then fails with a spurious `412`, and the client's retry loop looks like a concurrency conflict that no other party caused.

The fixes are the usual read-your-writes ones — route reads to the primary for a short window after a write, or pin the session — but the symptom is unusual enough to be worth recognizing (Module 38.1).

## When It's Appropriate

- **Any resource with more than one writer.** Multiple agents, a user plus an automation, a UI plus an integration. `If-Match` is the cheapest correct answer to a class of bug that otherwise produces no error at all.
- **Polling clients**, especially mobile ones, where most polls return unchanged data.
- **Large representations** where re-transfer is the dominant cost.
- **Content behind a CDN**, where revalidation is answered at the edge and never reaches you — the largest available win, and the one case where a 304 genuinely saves the whole request.
- **Config and document resources** edited through forms, where an overwritten field is a silent data loss rather than a visible error.

## When It's Unnecessary or Overkill

- **Append-only resources.** Events, logs, audit records — nothing to overwrite, nothing to revalidate.
- **Small responses.** A 300-byte JSON body against a 304 with its headers saves almost nothing; the round trip dominates either way.
- **Data that changes on every request.** Every conditional GET returns `200`, and you've added header overhead to buy nothing.
- **Validators that cost as much as the response.** Hashing a freshly rendered 2MB report on every poll to avoid sending it is work you did anyway.
- **Single-writer resources** — with the caveat that "one user, one device" expires the moment they open a second tab.
- **As a substitute for push.** Conditional GET makes polling cheaper; it does not make polling fresh. If latency to change matters, the answer is WebSockets or SSE (Module 9), not a more efficient poll loop.

## Trade-offs

- **Aggregate validators are a standing correctness hazard.** Every time someone adds an embedded relation to a representation, the ETag silently stops covering all of it. This needs a test, not a convention.
- **304s may not reduce server load** unless you design specifically for cheap validator reads. Claiming the win without measuring it is the common error.
- **`If-Match` moves conflict resolution to the client.** Refetch, re-apply, retry — or a merge UI, or a "this changed while you were editing" dialog. That's real client work and a genuine UX decision about whose edit survives.
- **Requiring preconditions breaks existing clients.** `428` on a resource that previously accepted bare `PUT`s is a breaking change and needs a per-resource rollout with a deprecation window (Module 33).
- **ETags are a tracking vector.** A stable, per-client validator is a persistent identifier a browser will faithfully return; this is a documented privacy concern, and it's a reason to derive validators from resource state rather than anything client-specific.
- **Intermediaries interfere.** Proxies and CDNs may strip, rewrite, or add their own ETags — particularly around compression, where the body they cache isn't the body you produced. Test through the real path, not against localhost.
- **Mixing validator types surprises people.** When both `If-Match` and `If-Unmodified-Since` are present, both must pass, and timestamp resolution means the weaker one can fail a request the strong one would have allowed.
- **Two writers can still both lose.** Under contention, `412`-retry loops can livelock, and the client that retries fastest wins. If contention is routine rather than occasional, optimistic concurrency is the wrong model and pessimistic locking or a merge strategy is the honest answer (6.5).

## Alternatives

- **A version field in the body** — `{"version": 42}` echoed back, `409` on mismatch. Functionally equivalent for your own clients, simpler for teams who find headers awkward, and invisible to every cache, proxy, and generic tool in the path. A reasonable choice made for the wrong reason more often than not.
- **Pessimistic locking** — explicit checkout with a lease and an expiry (6.5). Fits long edit sessions on documents, where discovering a conflict at save time is too late to be useful. Costs you lock expiry handling and an unlock UX.
- **Last-writer-wins with field-level `PATCH`.** Often correct for independent fields, quietly wrong for dependent ones — a status and its reason, a price and its currency.
- **Operational transforms or CRDTs**, when the requirement is that both edits *apply* rather than that one is rejected. Collaborative editing, Module 9.3.
- **Push instead of poll** — SSE, WebSockets (Module 9), or webhooks (Module 17). Removes the revalidation case entirely rather than optimizing it.
- **Delta endpoints** — `?since=<watermark>` for clients maintaining a mirror (7.3c). A different requirement from revalidating one resource, and better served separately.

## How to Achieve It

**Level 0 — emit `ETag` on single-resource GETs** from the version column you already have, plus `Cache-Control: private, no-cache`. No behavior change; nothing breaks; clients that understand it start benefiting immediately.
*Signal you're here:* you have a version column and it never leaves the server.

**Level 1 — honor `If-None-Match` and return `304`.** Then measure what it saved, before anyone writes it up as a performance improvement.
*Signal to move on:* polling traffic visible in your bandwidth bill.

**Level 2 — honor `If-Match` on writes**, mapping to the versioned `UPDATE`, returning `412`.
*Signal you need it:* one confirmed lost update. That's the whole business case.

**Level 3 — require `If-Match` where it matters**, returning `428` when absent, rolled out resource by resource with client communication.
*Signal to move on:* a client that supports preconditions and another that doesn't, writing the same resources.

**Level 4 — fix aggregate validators** so the ETag covers every entity the representation embeds, with a test per aggregate endpoint.
*Signal you need it:* a stale-data report that nobody can reproduce.

**Level 5 — make validators cheap to read** — a cached version keyed by resource id — if 304 volume justifies it (Module 13).

## Implementation

TypeScript, because the mechanism is small enough that the interesting parts are the edge cases rather than the framework.

The read path:

```ts
router.get("/tickets/:id", async (req, res) => {
  const row = await db.oneOrNone(
    `select id, version, title, priority, assignee_id, updated_at
       from tickets where id = $1 and tenant_id = $2`,
    [req.params.id, req.tenant]);
  if (!row) return WriteError(res, notFound());

  const etag = `W/"${row.version}"`;
  res.setHeader("ETag", etag);
  res.setHeader("Cache-Control", "private, no-cache");

  if (matchesAny(req.headers["if-none-match"], etag)) {
    return res.status(304).end();
  }
  res.json(serializeTicket(row));
});
```

The write path:

```ts
router.put("/tickets/:id", async (req, res) => {
  const ifMatch = req.headers["if-match"];
  if (!ifMatch) {
    return problem(res, 428, "precondition_required",
      "This resource requires an If-Match header carrying the ETag you last read.");
  }
  const expected = parseVersion(ifMatch);        // W/"42" → 42
  const input = UpdateTicket.parse(req.body);    // 7.3a

  const result = await db.result(
    `update tickets
        set title = $1, priority = $2, assignee_id = $3,
            version = version + 1, updated_at = now()
      where id = $4 and tenant_id = $5 and version = $6`,
    [input.title, input.priority, input.assigneeId,
     req.params.id, req.tenant, expected]);

  if (result.rowCount === 0) {
    const exists = await db.oneOrNone(
      `select 1 from tickets where id = $1 and tenant_id = $2`,
      [req.params.id, req.tenant]);
    return exists
      ? problem(res, 412, "precondition_failed",
          "The ticket changed since you loaded it. Refetch and reapply your changes.")
      : WriteError(res, notFound());
  }

  res.setHeader("ETag", `W/"${expected + 1}"`);
  res.status(204).end();
});
```

Four asides.

**`rowCount === 0` is ambiguous and must be disambiguated.** It means either "the version didn't match" or "the row is gone." A client told `412` for a deleted resource will refetch, get a `404`, and have no idea what to do; a client told `404` for a version conflict loses the retry path. The second query costs one indexed lookup on a path that's already failing.

**Returning the new `ETag` on the write saves the client a round trip.** Without it, any client intending a second edit must `GET` again purely to learn the new version — which, on a form with an autosave, doubles your request volume for no reason.

**`matchesAny`, not string equality.** `If-None-Match` may carry a comma-separated list, and it may be `*`. Naive comparison works in testing and fails against real HTTP clients and CDNs that legitimately send several validators.

**The weak marker is honest, not decorative.** `W/` is correct here because the version says the *resource* is unchanged; it says nothing about byte-identical JSON, and any change to the serializer would break a strong claim. Reserve strong validators for byte-stable content — stored files, generated documents — where range requests might matter.

The trap this code leaves open is the aggregate one. The moment `serializeTicket` starts embedding comments, `version` is the wrong validator and the ETag becomes a lie. The fix is to derive it from everything included:

```sql
select t.*, greatest(t.version, coalesce(max(c.version), 0)) as etag_version
  from tickets t left join comments c on c.ticket_id = t.id
 where t.id = $1 and t.tenant_id = $2
 group by t.id
```

## Further Reading

- **RFC 9110 §8.8 (validators) and §13 (conditional requests)** — the authoritative text, including precedence rules when multiple preconditions are present. Obsoletes RFC 7232, which is what most older blog posts cite.
- **RFC 9111 §4.3, _Validation_** — how revalidation actually flows through caches, and what `no-cache` means as distinct from `no-store` and `max-age=0`.
- **RFC 6585** — the definition of `428 Precondition Required`, and the argument for requiring preconditions rather than offering them.
- **MDN's conditional requests documentation** — the most readable summary of header interactions, with browser behavior noted.
- **Mark Nottingham's caching writing** — particularly on the difference between `no-cache` and `max-age=0`, which is the single most commonly inverted pair of directives in production configs.
- **Module 6.5** for the database-side mechanism this maps onto, and **Module 9** for the push alternatives that make revalidation unnecessary.

A Java sibling has a specific and useful thing to show: Spring provides `ShallowEtagHeaderFilter`, which computes an ETag by hashing the fully rendered response — so it saves bandwidth while doing every bit of the work first, which is exactly the misunderstanding this article warns about, sitting in the framework as a default-looking option. Pair that with JPA's `@Version` and `ETag`/`If-Match` support in `ResponseEntity`, and the Java version of this article is largely about knowing which of three built-in mechanisms is actually doing what you think. Not yet written.

---

The habit to carry: when a client reads something and later writes it back, there is always a window in between, and something has to cross it. Either the version travels with the data and comes back, or the window is invisible — and invisible windows don't produce errors, they produce quiet disagreements about what the data used to say.
