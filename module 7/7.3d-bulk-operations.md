# Bulk Operations

_Module 7.3d — RESTful API Design & Implementation_

## The Problem

A partner syncs their CRM into yours every night: ten thousand contacts, one `POST /contacts` at a time.

The arithmetic is unkind. Ten thousand round trips at 80ms is thirteen minutes of wall clock spent almost entirely on network latency. Each request carries its own TLS resumption, its own token validation, its own transaction, its own audit row — overhead that dwarfs the two-millisecond insert it wraps. At request 500 your rate limiter starts returning `429` (Module 18). The partner responds by adding thirty threads of concurrency, which fixes their runtime and turns their nightly sync into a small denial-of-service against your write path.

So you add `POST /contacts/batch` that accepts an array. It ships in a sprint. Then the questions start arriving, and none of them was in the design document.

**Item 4,312 has an invalid email.** What happens to the other 9,999? There are three defensible answers and the endpoint implements whichever one fell out of the code.

**What status code describes 9,700 successes and 300 failures?** `200` claims it worked. `400` claims it didn't. Both are lies, and every client's error handling is built on the status class (7.1a, 7.3b).

**The partner's HTTP client times out at 30 seconds and retries.** The batch was half applied. They now have an unknown number of duplicate contacts, and the `Idempotency-Key` from 7.1a doesn't save them, because the key record was going to be written by the transaction that timed out.

**Which items failed?** The response is an array of 10,000 results matched positionally to the request. The partner dedupes their input before sending, the arrays stop lining up, and they report the wrong rows to their own users.

**The batch takes 40 seconds; the load balancer's idle timeout is 30.** The work completed. The client got a `504` and no result body. There is now no way for them to find out what happened except to re-read everything.

**One batch holds a write transaction open for 40 seconds**, keeping locks, blocking vacuum, and occupying a connection. One tenant's import degrades every other tenant's latency.

The shape underneath: a bulk endpoint looks like an *optimization* — fewer round trips for the same work — but it silently changes the **semantics**. Atomicity, error reporting, retry safety, and duration were all decided for you by the single-item endpoint. In a batch, every one of them becomes a design decision, and skipping the decision doesn't avoid it; it just makes the answer accidental.

## What It Is

A **bulk (or batch) operation** is one request carrying many independent operations over the same resource type.

Three things get called this, and they have genuinely different requirements:

- **Batch** — N independent operations that may partially succeed. Importing contacts. The subject of most of this article.
- **Atomic multi-write** — N operations that must all apply or none. Two sides of a double-entry ledger. Here atomicity is a *correctness* requirement, not a convenience, and partial success is a bug rather than a feature.
- **Bulk ingest** — a volume large enough that it can't be a request at all. A file, a job, a status resource.

Most bad bulk endpoints are one endpoint being asked to be all three.

A fourth, distinct thing: **bulk-by-query** — `POST /contacts/bulk-delete` with a filter rather than a list. That's not a batch of known items, it's an operation on an unbounded set selected server-side, and it carries a different risk profile entirely (see below).

## Recognizing the Problem

- A client loops over single-item calls and your rate limiter is what tells you.
- A bulk endpoint returns `200` for a request where most items failed.
- Clients ask which items succeeded, and your answer involves counting array positions.
- A retry after a timeout produced duplicates and nobody can say how many.
- One tenant's import shows up in everyone else's p99.
- Your batch size limit is a round number nobody derived from anything.
- A `504` from a batch is followed by a support ticket asking what state the data is in.
- The same endpoint is used for 5 items and for 50,000.
- Per-request metrics show a healthy success rate while per-item outcomes do not.
- Nobody can state, from documentation, whether the endpoint is atomic.

## How It Works

### Three failure policies, and the API must pick one

| Policy | Semantics | Client burden | Fits |
|---|---|---|---|
| **All-or-nothing** | One transaction; any failure applies nothing | Lowest — fix and resend the same payload | Small batches, items with cross-item invariants, ledgers |
| **Best-effort** | Each item independent; every item gets a result | Highest — reconcile results, retry the failed subset | Imports, syncs, independent rows |
| **Fail-fast** | Applies up to the first failure, then stops | Worst — must determine where it stopped | Ordered dependent operations; rarely what anyone wants |

This is a documented contract, not an implementation detail. Some APIs let the client choose (`"onError": "abort" | "continue"`), which is genuinely useful and doubles your test matrix.

One implementation detail that shapes the choice more than people expect: **on PostgreSQL, a failed statement aborts the whole transaction.** Continue-on-error inside a single transaction therefore requires a `SAVEPOINT` per item and a rollback to it on failure — which works, and costs enough that at real batch sizes you end up chunking into separate transactions instead. That's how "best-effort" quietly stops being atomic even in the parts you assumed were.

### Status codes can't express partial success, and that's the real cost

`207 Multi-Status` exists (RFC 4918, from WebDAV). It is poorly supported by client libraries, widely misunderstood, and rarely worth the explanation.

The common design is `200 OK` with a per-item result array, where the top-level status means *the batch was processed*, not *everything worked*. Which directly contradicts the principle from 7.1a that the status class tells generic infrastructure whether something failed. A `200` hiding 3,000 failures is the green-dashboard incident, reintroduced on purpose.

Three things make it tolerable:

- **Summary counts at the top level** (`"succeeded": 9700, "failed": 300`) so a client can branch without walking the array.
- **Return `422` when nothing succeeded.** Total failure is unambiguous, it's the common case for a malformed integration, and it gives the status class back for the situation clients most need it.
- **Instrument per item, not per request.** Your success-rate metric must count item outcomes, or your dashboards will lie exactly the way the status code does (Module 19).

And note what all-or-nothing buys here: it keeps the ordinary contract. `200` means applied, `4xx` means nothing applied, no body parsing required. That's a real argument for atomic batches whenever the batch is small enough to fit in a short transaction.

### Address items by client-supplied reference, never by position

```json
{ "items": [ { "ref": "csv-row-4312", "email": "a@example.com" } ] }
```

```json
{ "succeeded": 9700, "failed": 300,
  "results": [
    { "ref": "csv-row-4312", "status": "error",
      "error": { "code": "validation_failed", "errors": [
        { "pointer": "/email", "code": "invalid_format", "message": "not a valid address" } ] } }
  ] }
```

The `ref` is the client's own key — a CSV row number, a local UUID, their primary key. It means results are order-independent, the server may reorder or deduplicate internally, retrying only the failed subset is trivial, and each failure is just the error shape from 7.3b in a list.

Positional matching works until the first time either side changes the array, and then it fails silently by reporting the wrong rows.

### Idempotency has two levels, and batches need both

Request-level `Idempotency-Key` (7.1a) is correct and sufficient **for all-or-nothing batches** — one transaction, one key record, committed together.

For best-effort batches it isn't, because the request partially executed. Replaying a stored response is impossible when the response was never stored, and re-executing duplicates everything that already succeeded. The fix is per-item identity:

- **An idempotency key per item**, stored per item, or
- **A natural key with upsert semantics** — `external_id` unique per tenant, `INSERT … ON CONFLICT DO UPDATE`.

The second is usually the better design. It makes every item idempotent by construction, so a retry of the entire batch is safe with no key infrastructure at all, and a partner who resends yesterday's file gets updates rather than duplicates. Sync-shaped data almost always has a natural key already.

Skipping this is the single most common bulk-endpoint defect, and it only appears under the conditions — a timeout mid-batch — that nobody tests.

### Size limits come from a timeout budget

```
per-item p99: 8ms          gateway idle timeout: 30s
                           ├──────────────────────────────┤
  1,000 items   ████                    8s   safe
  2,500 items   ██████████             20s   tight
  5,000 items   ████████████████████   40s   504 — and the work was done
```

Derive the cap; don't pick a round number. Publish both an item count limit and a payload byte limit, and reject over them with a clear code (`413`, or `400` with `batch_too_large`). The interesting failure isn't the rejected request — it's the accepted one that finishes after the client stopped listening, because then the work is done and nobody knows it.

Also cap what the work does to everyone else: chunk internally so no transaction spans the whole batch, and remember that a batch of 500 counted as one request against a rate limit lets a caller do 500× their quota. Weight rate limiting by item count (Module 18).

### When it should have been a job

If a batch cannot reliably finish inside the request timeout, it isn't a request:

```
POST /imports        → 202 Accepted, Location: /imports/9c3
GET  /imports/9c3    → { status: "running", processed: 4200, failed: 12 }
GET  /imports/9c3/results.ndjson
```

Now duration is unbounded, progress is observable, results are downloadable rather than crammed into a response body, and a client disconnect costs nothing. This is Module 10's territory, with the file handling of Module 11 and optionally a webhook on completion (Module 17).

The signal to cross over: file uploads, tens of thousands of rows, or per-item work that calls something external whose latency you don't control.

### Bulk-by-query needs different guardrails

`POST /contacts/bulk-delete` with `{"filter": {"status": "stale"}}` is an operation whose scope is computed on the server. Nobody knows how many rows it touches until it runs, there's no per-item feedback, and a wrong filter is a data-loss incident rather than an error.

The protections that actually help: a dry-run mode returning the affected count, a required `expectedCount` the server verifies before executing, a hard cap above which it must become an async job, and an audit record of the filter itself (Module 24).

## When It's Appropriate

- **Per-request overhead dominates the work.** Auth, TLS, rate-limit accounting, and audit costing more than the insert is the case bulk exists for.
- **Imports and syncs from another system**, where the client naturally holds a file or a change set.
- **Bulk edits in a UI** — "select all 400, change owner" is one user action and should be one request.
- **Mobile or offline clients flushing a queue** of accumulated local changes on reconnect.
- **Cross-item invariants.** Both legs of a transfer, a reassignment that must not leave records orphaned. Here an atomic batch is the only correct design, and round trips aren't the point.

## When It's Unnecessary or Overkill

- **Small N over a reused connection.** With HTTP/2 multiplexing and keep-alive, ten sequential calls are not the problem people remember from HTTP/1.0. Measure before designing.
- **When the real gap is a different endpoint.** "Bulk fetch" often means a missing filter (7.3c); "bulk sync" often means a missing change feed. Building a batch endpoint to paper over those leaves both problems in place.
- **Best-effort semantics on a domain that needs atomic** — or the reverse. The more complicated policy isn't the safer one.
- **A bulk variant of every resource for symmetry.** Each is a separate semantic contract to document, test, and support.
- **A bulk endpoint that's clearly an import.** If the answer is always "10,000 rows from a file," build the job and skip the intermediate.

## Trade-offs

- **You give up the status-code contract.** Clients must parse bodies to learn whether anything worked, and every generic monitor in your path now under-reports failure. Item-level metrics are mandatory, not nice to have.
- **Complexity moves to the client.** Reconciliation loops, retry-the-failed-subset logic, and a results file to store. You've made your endpoint cheaper by making every integration harder.
- **The test matrix expands sharply:** empty batch, single item, duplicate refs, duplicate natural keys within one batch, all-fail, mixed, over-cap, timeout mid-batch, retry after partial application. Most bulk bugs live in the last three.
- **Long transactions are a shared resource problem** — locks, replication lag, vacuum, connection occupancy. Chunking fixes it and costs you atomicity, so you're choosing which guarantee to keep.
- **Fairness.** One tenant's large batch can monopolize workers and connections. Bulk endpoints usually need their own concurrency limit per tenant.
- **Observability degrades.** One trace spanning 10,000 operations is unreadable; logging every item is expensive. Sampling plus aggregate outcome counters is the workable compromise (Module 19).
- **Response bodies get large.** Ten thousand results is megabytes. Returning only failures plus counts is the usual answer, and it means success detail — the assigned ids — is lost unless you return those too.
- **Bulk endpoints attract load they weren't designed for.** They are the path of least resistance, so they grow into import pipelines without acquiring any of an import pipeline's guarantees. The cap is what prevents this; raising the cap when clients complain is how it happens anyway.

## Alternatives

- **Connection reuse and client-side concurrency.** HTTP/2, keep-alive, and a bounded worker pool eliminate most of the round-trip cost without changing your API's semantics at all. Genuinely the first thing to try.
- **An async import job** — `202`, a job resource, downloadable results (Modules 10, 11, 17). The right answer above the timeout budget.
- **Collection `PATCH` with JSON Patch (RFC 6902).** Standardized, expresses ordered heterogeneous operations, and has essentially no story for per-operation error reporting.
- **Protocol-level batching** — OData `$batch`, JSON-RPC batch requests, or several mutations in one GraphQL document. Generic multiplexing instead of a bespoke endpoint per resource; GraphQL runs mutations serially and treats partial failure as native (Module 8).
- **Message queue ingestion.** The client publishes; you consume at your own rate. For internal high-volume producers this removes batching, backpressure, and timeout concerns in one move (Modules 10, 37).
- **Data pipeline ingestion** — a file dropped in object storage, or change data capture from the source system (Modules 11, 38). Once volume is measured in millions of rows, an HTTP API is not the transport.

## How to Achieve It

**Level 0 — measure before building.** Confirm that per-request overhead, not the work itself, is the bottleneck, and check whether the client is reusing connections. A surprising share of "we need bulk" is "we need keep-alive."
*Signal you're here:* a client loop and a rate limiter fighting.

**Level 1 — cap and publish.** Maximum items, maximum bytes, both derived from your timeout budget. Reject clearly.
*Signal you need it:* a batch that finished after the client gave up.

**Level 2 — choose and document one failure policy.** Default to all-or-nothing if the batch fits a short transaction; it preserves the status-code contract and the simplest client story.
*Signal to move on:* clients asking what state their data is in.

**Level 3 — require a per-item `ref`, return per-item results** in the standard error shape (7.3b), with summary counts at the top.
*Signal you need it:* anyone matching results by array position.

**Level 4 — make items individually idempotent** via natural-key upsert or per-item keys, *before* offering best-effort semantics. This ordering matters: best-effort without item idempotency is a duplicate generator.
*Signal to move on:* the first retry-after-timeout incident.

**Level 5 — instrument per item**, and alert on item failure rate rather than request failure rate.

**Level 6 — when the cap stops being enough, build the async import** rather than raising the cap.

## Implementation

Go, continuing the thread from 7.1a and 7.3b — the `Problem` type from the error article is reused directly as the per-item error, which is most of the point of having standardized it.

```go
type BatchRequest struct {
    Items []BatchItem `json:"items"`
}
type BatchItem struct {
    Ref   string       `json:"ref"`
    Input ContactInput `json:"contact"`
}
type ItemResult struct {
    Ref    string   `json:"ref"`
    Status string   `json:"status"`          // "created" | "updated" | "error"
    ID     string   `json:"id,omitempty"`
    Error  *Problem `json:"error,omitempty"` // 7.3b
}
```

Envelope checks first — these fail the *whole* request, because they make the response unaddressable:

```go
if len(req.Items) == 0 || len(req.Items) > maxBatchItems {
    WriteError(w, r, &DomainError{Code: "batch_size_invalid", Status: 400,
        Detail: fmt.Sprintf("batch must contain between 1 and %d items", maxBatchItems)})
    return
}
seen := make(map[string]struct{}, len(req.Items))
for _, it := range req.Items {
    if _, dup := seen[it.Ref]; dup || it.Ref == "" {
        WriteError(w, r, &DomainError{Code: "duplicate_ref", Status: 400,
            Detail: "each item requires a unique ref"})
        return
    }
    seen[it.Ref] = struct{}{}
}
```

Then parse everything before writing anything — pure checks, no I/O, same parser as the single-item endpoint (7.3a):

```go
results := make([]ItemResult, 0, len(req.Items))
valid := make([]BatchItem, 0, len(req.Items))

for _, it := range req.Items {
    if err := ParseContact(it.Input); err != nil {
        results = append(results, ItemResult{Ref: it.Ref, Status: "error", Error: problemFor(err)})
        continue
    }
    valid = append(valid, it)
}
```

And apply in chunks, each its own transaction:

```go
for _, chunk := range chunks(valid, chunkSize) {
    err := h.db.InTx(ctx, func(tx *sql.Tx) error {
        for _, it := range chunk {
            // ON CONFLICT (tenant_id, external_id) DO UPDATE …
            id, created, err := h.contacts.Upsert(ctx, tx, tenant, it.Input)
            if err != nil { return fmt.Errorf("ref %s: %w", it.Ref, err) }
            results = append(results, ItemResult{Ref: it.Ref, ID: id,
                Status: map[bool]string{true: "created", false: "updated"}[created]})
        }
        return nil
    })
    if err != nil {
        markChunkFailed(&results, chunk, err)   // every ref in the chunk gets the same error
    }
    metrics.BatchItems.Add(float64(len(chunk)), statusLabel(err))
}
```

Four asides.

**The chunk is the atomicity boundary, and that's the published contract.** Items in a failed chunk all report failure even if some would have succeeded alone — that's the price of not using a savepoint per item, and the client's `ref`-keyed retry makes it recoverable. What's unacceptable is not saying which it is; "partially atomic in chunks of 500" is a fine contract and an awful surprise.

**`Upsert` on `(tenant_id, external_id)` is what makes the retry safe.** No idempotency keys, no stored responses — resending the entire batch after a `504` converts every already-applied item into a no-op update. If the domain has no natural key, this article's hardest requirement returns and you need per-item keys instead.

**Validation runs before any write** so a client that sent garbage learns everything wrong with the payload in one response, and so that the number of items reaching the database is known up front. It also means no partial state exists for purely structural failures.

**The metric is per item.** `metrics.BatchItems.Add(len(chunk), …)` rather than one counter increment for the request. Without this, a batch endpoint returning `200` with 3,000 failures produces a perfect success-rate graph — the identical failure from 7.1a's third incident, arriving through a door you built yourself.

## Further Reading

- **RFC 4918 §13, `207 Multi-Status`** — read it to understand precisely what it specifies and why it rarely fits a JSON API.
- **Google AIP-233 (_Batch methods: create_) and AIP-231 (_batch get_)** — including the explicit recommendation that batch operations be atomic by default, and the naming conventions that go with it.
- **Elasticsearch's `_bulk` API** — NDJSON in, per-item results out, partial success as the normal case. The clearest working model of best-effort batching at scale.
- **Salesforce Bulk API 2.0** and **Shopify's bulk operations** — two mature designs that both concluded large batches must be asynchronous jobs with downloadable results.
- **Stripe's approach**: no general batch endpoint, per-request idempotency keys, and an emphasis on client concurrency. Worth studying as a deliberate decision not to build this.
- **PostgreSQL `INSERT … ON CONFLICT`** and **`SAVEPOINT`** documentation — the two mechanisms underneath item-level idempotency and continue-on-error respectively.
- **RFC 6902, _JSON Patch_** — for the collection-`PATCH` alternative.

A Java sibling has a genuinely different story to tell here: with JPA, `saveAll` batches at the JDBC level while a single constraint violation poisons the persistence context and the surrounding transaction, so per-item error reporting requires either savepoints or a deliberate retreat to plain JDBC with `addBatch`/`executeBatch` and `BatchUpdateException.getUpdateCounts()`. The ORM makes the easy path — all-or-nothing — easier, and the best-effort path substantially harder, which is a good illustration of a framework quietly choosing your API's semantics. Not yet written.

---

The habit to carry: whenever a request carries more than one unit of work, four questions come with it — what happens if one fails, what the client is told, what a retry does, and how long it may run. A single-item endpoint answers all four by accident. A batch endpoint answers them on purpose, or it answers them badly.
