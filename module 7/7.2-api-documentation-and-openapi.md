# API Documentation and the OpenAPI Contract

_Module 7.2 — RESTful API Design & Implementation_

## The Problem

A logistics partner is integrating with your shipments API. Four endpoints. Their engineer is nine time zones away, so each question costs a day.

Week one:

> Is `customer_id` required on create?

It's optional in the request model. It's also `NOT NULL` in the database, with a default applied in a service method three layers down, which is why it appears to work in your tests.

> What are the possible values of `status`?

There are seven. Six are in an enum; the seventh, `partially_delivered`, was added last spring as a string literal in one branch of a switch.

> What does a validation error look like?

Depends on the endpoint. Two of them return `{"error": "..."}`, one returns a field-keyed object, and one returns the framework's default, which includes a stack trace in staging.

> Is `amount` a number or a string?

A string, because it's money and someone was right about floating point. Nothing says so.

Three weeks later they're live. Two of their fields are wrong and they'll find out in production.

Meanwhile, there *is* documentation: a Confluence page written fourteen months ago by an engineer who has since moved teams. It's accurate about three of the four endpoints. One field was renamed in a refactor and the page still shows the old name — so the partner used the old name, got a `400`, assumed they'd made a mistake, and burned two days.

And inside the company, the same problem wears different clothes. The mobile team wrote their model types by hand from a sample response pasted into Slack. They typed `total` as a number because the sample happened to show `142.00`. Rounding bugs surfaced four months later in a currency that uses three decimal places.

The shape underneath all of it: **the API's contract exists, but only as an emergent property of running code.** There are three copies of it — the server, the docs page, and each client's hand-written model — and no mechanism anywhere that makes them agree or tells anyone when they stop.

## What It Is

The fix is an **API description**: a single machine-readable document that states, precisely, what the API accepts and returns. For HTTP APIs the de facto standard is **OpenAPI**.

The word *machine-readable* is doing all the work. A Confluence page describes the API to humans and nothing can check it. A description document describes the API to programs, and programs can then generate the human docs, generate the clients, validate the traffic, mock the server, and — the part that actually solves the problem above — **fail a build when the code and the description disagree**.

A small disambiguation: **Swagger** was the original name and now refers to the tool family (Swagger UI, Swagger Codegen); **OpenAPI** is the specification itself, currently 3.x, whose schema language is JSON Schema. People use both words for both things.

And a distinction worth keeping straight: a *description* is not *documentation*. The description is structured data. Rendered reference docs are one artifact generated from it — an important one, and not the only one, and not sufficient on its own (see the end of How It Works).

## Recognizing the Problem

- Integration questions arrive that can only be answered by reading server code.
- The docs page has a "last updated" date more than a quarter old.
- Client teams hand-write model types from example payloads pasted into chat.
- Two endpoints represent the same concept differently — money, dates, ids — and nobody noticed until a bug.
- The error body format varies by endpoint.
- A Postman collection circulates as a file attachment and is, in practice, the real documentation.
- Nobody can answer "what changed in the API last release?" without reading a diff.
- A frontend team is blocked waiting for a backend endpoint that isn't built yet.
- You can't produce a complete list of your own endpoints.
- Someone asks whether removing a field is safe, and the honest answer is a shrug.

## How It Works

### The document

An OpenAPI document is mostly three things: **paths** (each with operations, parameters, request bodies, and responses), **components/schemas** (reusable data shapes referenced by `$ref`), and **securitySchemes**. Shapes are JSON Schema, so constraints like `required`, `enum`, `format`, `minimum`, and `pattern` come along for free.

That's the whole model. The interesting part isn't the syntax — it's what becomes possible once the document exists.

### One document, many consumers

```
                    ┌── Redoc / Scalar ────► reference docs for humans
                    ├── openapi-generator ─► typed clients (TS, Kotlin, Swift)
  openapi.yaml ─────├── Prism ─────────────► mock server (frontend unblocked)
                    ├── API gateway ───────► request validation at the edge
                    ├── schemathesis ──────► generated test cases, fuzzing
                    └── oasdiff ───────────► CI gate on breaking changes
```

Each of those replaces work someone is currently doing by hand:

- **Reference docs** with a "try it" console, regenerated on every merge. The fourteen-month-old page problem stops existing.
- **Generated clients** mean the mobile team's `total` is a string because the schema says so, not because someone read a sample correctly.
- **Mock servers** let the frontend and the partner start on day one against a server that returns schema-valid responses. This is often the single largest schedule win, and it's the one teams most often skip.
- **Edge validation** — the gateway rejects malformed requests before they reach your code, using the same schema your docs come from.
- **Generated tests**, including property-based ones that send every boundary value your schema permits. These find the endpoints that `500` on an empty array.
- **Breaking-change detection** in CI: diff the proposed spec against the published one and fail the build on an incompatible change. Compatibility becomes a gate rather than a habit.

### Where the document comes from

This is the real decision, and there are three answers.

**Code-first.** The spec is generated from the implementation — annotations, decorators, or types. springdoc for Spring, FastAPI, tsoa or zod-to-openapi for TypeScript, swaggo for Go.

*Strength:* the shapes are never wrong, because they're derived from the thing that runs.
*Weakness:* it can only describe what the type system knows. An enum enforced in a service method, a field that's conditionally required, the `409` your business rule throws — none of that appears unless you annotate it by hand, which is exactly where drift creeps back in. Generated specs tend to be shape-accurate and meaning-empty.

**Design-first.** The document is the source of truth, written and reviewed before implementation; the code is validated against it.

*Strength:* API design becomes a reviewable artifact rather than an emergent consequence of handler code. Cross-team parallelism is real — frontend mocks against it immediately. It's the only approach that works well when several teams or a partner must agree before anyone builds.
*Weakness:* discipline and tooling. Without enforcement the code drifts from the spec just as easily as docs drift from code — you've relocated the problem, not solved it.

**Traffic-derived.** Infer a spec from recorded production traffic. Useful exactly once: mapping an undocumented legacy API you inherited. It tells you what clients *did* send, not what's allowed, so it's an inventory, not a contract.

The choice matters less than this: **whichever direction the document flows, something in CI has to fail when code and document disagree.** A spec no test consumes is a Confluence page in YAML — same staleness, more syntax.

### What a spec cannot say

Even a perfect OpenAPI document is silent about most of what an integrator needs:

- **Sequencing.** "Create a customer, then a payment method, then a subscription." No schema expresses that.
- **Semantics.** What `pending` means, and what causes the transition out of it.
- **Guarantees.** Ordering, idempotency windows, eventual consistency, when a `202` actually completes.
- **Operational contract.** Rate limits, retry guidance, timeouts, deprecation policy.
- **Conditional validity.** Some of it is expressible with `oneOf` and discriminators, most of it awkwardly, and the awkward version is unreadable.

So prose documentation doesn't go away. The division is stable and worth stating explicitly: **the spec is the reference, the guide is the teaching.** Reference tells you the shape of `POST /subscriptions`. A guide tells you why you'd call it and what to do when it returns `402`. Teams that generate a spec and delete their written docs replace one failure with another.

## When It's Appropriate

- **Any API with a consumer outside the team that built it.** That's the threshold, and it's lower than most teams assume — a second team in the same company qualifies.
- **Public and partner APIs.** Non-negotiable. Integration support load is a direct, measurable cost, and reference docs plus a mock server cut it sharply.
- **Several client languages.** Codegen pays per language. Web, iOS, Android, plus partners in whatever they use — that's four hand-written model layers you stop maintaining.
- **Parallel development across teams.** The mock server is the mechanism; the spec is what makes it possible before the backend exists.
- **Gateway-fronted architectures**, where schema validation, routing, and rate-limit configuration can all consume the same document.
- **Regulated or audited environments** that need a documented, versioned interface as evidence.

## When It's Unnecessary or Overkill

- **One internal service, one client, one repository.** A shared types package or tRPC gives you stronger guarantees — compile-time, not runtime — with less machinery.
- **GraphQL or gRPC.** Both already have a schema that serves this purpose; adding OpenAPI would be a second description of the same API, and second descriptions drift. The principle transfers, the tooling doesn't.
- **A pre-product-market-fit API changing daily with no external consumer.** The cost is immediate and the benefit is deferred. Revisit when the second consumer appears.
- **Generating SDKs in eight languages you have no intention of supporting.** Every published SDK is a support commitment.
- **Full design-first review ceremony for internal CRUD endpoints.** Reserve the process for surfaces that are expensive to change.

## Trade-offs

- **You're maintaining a second artifact,** or accepting annotation noise in the first. Code-first handlers can double in length under `@Schema`, `@ApiResponse`, and example annotations, and the signal-to-noise ratio in the controller gets meaningfully worse.
- **Generated SDKs become products.** Versioning, publishing, release notes, issue triage, and the quality of the generator's output in each language — some are idiomatic, some produce code your users will complain about. Teams frequently end up hand-wrapping generated clients, which is the worst of both.
- **Shape validity is not correctness.** "It conforms to the spec" is a much weaker statement than it sounds. A response with every field of the right type can still be wrong, and a schema-driven test suite will pass on it happily.
- **Breaking-change tools detect structural breaks, not semantic ones.** Changing `amount` from cents to dollars, or narrowing what a status value means, sails through every diff tool. The gate is real and its coverage is partial.
- **Specs get large and unpleasant.** Thousands of lines, `$ref` chains across bundled files, and a linter (Spectral) required to keep conventions consistent. This is ordinary once the API is nontrivial, and it surprises teams who expected a small YAML file.
- **Expressiveness pressure distorts the API.** When something can't be modeled cleanly, the temptation is to reshape the endpoint to fit the schema language rather than accept a spec that under-describes it.
- **"Try it out" consoles pointed at production** are a live request generator with your users' data behind it. Default them to a sandbox, or turn them off.
- **Examples rot independently of schemas.** They're free-text blobs that nothing validates unless you make it validate them, and stale examples mislead faster than stale prose because they look authoritative.

## Alternatives

- **GraphQL introspection / SDL** — the schema is inherent to the system; documentation and tooling are byproducts rather than an artifact you maintain. Module 8.
- **gRPC and Protobuf** — the `.proto` file is the contract, and code generation is the primary workflow rather than an add-on.
- **TypeSpec** — a concise DSL that emits OpenAPI (and JSON Schema, and Protobuf). Increasingly the pragmatic design-first choice, because hand-writing large OpenAPI YAML is genuinely unpleasant and this removes most of that objection.
- **Smithy** — AWS's service modeling language, same idea at a larger scale, with protocol independence as a first-class goal.
- **Consumer-driven contract testing (Pact)** — inverts the direction: each consumer declares what it actually relies on, and the provider's build verifies those expectations. It answers a question OpenAPI can't — *which parts of my contract does anyone actually use?* — and it complements a spec rather than replacing it.
- **AsyncAPI** — the equivalent for event-driven interfaces: queues, streams, webhooks. If your integration surface is half webhooks (Module 17), an OpenAPI document covers half your API.
- **Executable examples** — Postman collections, `.http` files, `curl` snippets in the README. Excellent supplements, especially for onboarding; useless as a contract because nothing enforces them.
- **Well-written prose alone.** Always necessary, never sufficient, and the whole problem section is what happens when it's the only thing you have.

## How to Achieve It

**Level 0 — generate a spec from the running code, however rough, and publish it.** Even a 60%-accurate spec beats a fourteen-month-old page, and the first thing it produces is an inventory: a list of endpoints, several of which nobody remembers writing.
*Signal you're here:* you can't enumerate your own API surface.

**Level 1 — render docs from it in CI, at a stable URL, and retire every other source.** Redirect the Confluence page. Two documentation sources is strictly worse than one bad one, because readers can't tell which is current.
*Signal to move on:* someone answers an integration question with a screenshot of code.

**Level 2 — make divergence fail the build.** Validate responses against the spec in integration tests, or validate requests at the edge in a non-production environment first. This is the step that converts a document into a contract, and it's the one that matters most.
*Signal to move on:* a client found a divergence before you did.

**Level 3 — gate breaking changes.** Diff each PR's spec against the published one and fail on incompatible changes, with an explicit override for deliberate ones. Compatibility stops being a matter of whether the reviewer happened to notice.
*Signal to move on:* your first accidental breaking change.

**Level 4 — serve the consumers.** A mock server for the frontend team, generated clients for the languages you'll genuinely support, examples that are tested rather than pasted.
*Signal you're here:* two client teams hand-writing the same models.

**Level 5 — design-first for new surfaces.** The spec is written and reviewed before implementation starts, for anything public or cross-team. Existing endpoints stay code-first; this is not a migration.
*Signal you need it:* an API design mistake that was expensive to reverse after shipping.

## Implementation

Java and Spring, because the code-first approach's strength and its exact blind spot are both unusually visible there: Bean Validation constraints are already in the DTO, and springdoc lifts them into the spec automatically — so validation and description are genuinely one artifact, right up until they aren't.

```java
public record CreateShipmentRequest(
    @NotNull @Schema(description = "Customer placing the shipment", example = "cus_8f21")
    String customerId,

    @NotNull @Positive
    @Schema(description = "Declared value in minor units", example = "14200")
    Long declaredValueMinor,

    @NotNull @Pattern(regexp = "^[A-Z]{3}$")
    String currency,

    @Size(max = 50) List<@Valid ParcelRequest> parcels
) {}
```

`@NotNull` becomes `required`. `@Positive` becomes `exclusiveMinimum`. `@Pattern` becomes `pattern`. `@Size` becomes `maxItems`. None of that can go stale, because the validator and the description are the same annotations.

Now the controller, and the part that can:

```java
@PostMapping("/shipments")
@ApiResponse(responseCode = "201", description = "Created")
@ApiResponse(responseCode = "409", description =
    "Currency does not match the customer's account currency")
@ApiResponse(responseCode = "422", description = "Validation failed",
    content = @Content(schema = @Schema(implementation = ProblemDetail.class)))
public ResponseEntity<ShipmentResponse> create(
    @Valid @RequestBody CreateShipmentRequest req,
    @RequestHeader("Idempotency-Key") String idempotencyKey) { … }
```

**Every one of those `@ApiResponse` lines is hand-maintained prose.** The `409` exists because a service method three layers down compares currencies and throws. Nothing derives it; delete the annotation and the spec is still valid, still generated, still wrong. This is the code-first blind spot in one screen: constraints expressible in the type system are free and permanent, and everything else is a comment that happens to be machine-readable.

The gate that keeps it honest is not in the application at all:

```bash
# CI, on every PR
mvn -q spring-boot:run &                     # start the app
curl -s localhost:8080/v3/api-docs.yaml > build/openapi.yaml

oasdiff breaking docs/openapi.yaml build/openapi.yaml --fail-on ERR
cp build/openapi.yaml docs/openapi.yaml      # committed spec moves forward with the code
```

Two asides on that.

**The committed spec is the published contract; the generated one is the current truth.** Diffing them is what turns "we should keep docs updated" into a red build. A removed field, a narrowed enum, a newly-required parameter — each fails here, in the PR, with the author still holding context, rather than in a partner's production a month later.

**Response validation belongs in the integration tests**, not only in the diff. `oasdiff` compares two specs to each other; it has no opinion on whether the server obeys either one. A test that asserts every response conforms to the schema is what closes that loop, and it is the single highest-value piece of this whole apparatus — everything else is convenience, that one is the contract.

## Further Reading

- **The OpenAPI Specification 3.1** (spec.openapis.org) — the actual document; 3.1 aligns the schema language with JSON Schema 2020-12, which is the version difference that matters.
- **JSON Schema 2020-12** — because most of a spec's real content is schema, and the keyword reference is where the expressiveness questions get answered.
- **Spectral** — spec linting with custom rulesets. The way to enforce naming, error-format, and pagination conventions across a large API without review comments.
- **oasdiff** (and openapi-diff) — breaking-change detection suitable for a CI gate.
- **Prism** — mock server from a spec, including request validation against it.
- **Schemathesis** — property-based testing generated from a spec; finds the boundary values nobody wrote a test for.
- **openapi-generator** — the codegen workhorse, with the honest caveat that output quality varies a great deal by target language.
- **TypeSpec** and **Smithy** — design-first modeling languages that emit OpenAPI, worth evaluating before hand-writing a large YAML document.
- **Pact** — consumer-driven contract testing, for the "which fields does anyone actually depend on" question.
- **AsyncAPI** — the event-driven counterpart, relevant once webhooks are part of your surface (Module 17).
- **GitHub's published OpenAPI description** — a large, real, maintained spec to read when you want to see how the conventions hold up at scale.

A TypeScript sibling has something genuine to add here, and it's the inverse of the Java blind spot: with `zod` plus `zod-to-openapi`, a single schema object is simultaneously the runtime validator, the static type, and the spec fragment — so there is no annotation layer to drift, and the interesting question becomes what happens to the business rules that still live outside it. Not yet written.

---

The habit to carry forward: the test of an API description isn't whether it's accurate today. It's what happens when it becomes wrong. If the answer is "nothing, until a client notices," you have documentation. If the answer is "a build fails," you have a contract — and everything else in this article is downstream of that one difference.
