# Hypermedia and Discoverability

_Module 7.1b — RESTful API Design & Implementation_

## The Problem

An order management product with four clients: a web app, an iOS app, an Android app, and a partner integration built by a logistics company you've never met.

Each of them needs to answer the same question before rendering a screen: **should the Cancel button be here?**

The server knows. The rule lives in the cancellation endpoint, where it's enforced properly. But the clients need the answer *before* the user clicks, so each one reimplements it:

```js
const canCancel = order.status === "pending"
  || (order.status === "processing" && !order.shipment);
```

That code is now in four places, three of which you don't deploy.

In March, finance adds a rule: orders above $10,000 in `processing` require an approval workflow, so self-service cancellation is disabled for them. You update the endpoint, which now returns `409` for those orders. Correctly.

What happens next is entirely predictable. The web app ships the new rule on Tuesday. iOS ships two weeks later after review. Android ships when that team's sprint allows. The partner integration never ships it — they built it in 2023 and the engineer who wrote it has left. For the next year, some customers see a Cancel button that always fails, and your support queue absorbs it.

Two more variations of the same failure, because it isn't only about buttons:

**URLs become permanent.** You want to move invoice storage behind a different service, so `/invoices/{id}/pdf` should become a URL on a storage host. Every client has that path compiled in as a string. The move is now a coordinated release across four clients and a partner, so it doesn't happen, and the old path is proxied forever.

**Pagination is a contract nobody agreed to.** Clients build `?page=3&per_page=50` by hand. When the collection grows and offset pagination starts timing out, you want cursors (7.3c). That's a one-line server change and a breaking change for everyone.

Underneath all three is one thing: **the client holds a copy of knowledge that belongs to the server** — what is currently possible, and where things are. Every time that knowledge changes, it has to be redeployed into clients on their release schedule, not yours.

Now imagine the response answering the question directly:

```json
{
  "id": "8f21",
  "status": "processing",
  "total": "142.00",
  "_links": {
    "self":   { "href": "/orders/8f21" },
    "cancel": { "href": "/orders/8f21/cancellations", "method": "POST" },
    "invoice":{ "href": "https://files.example.com/i/8f21.pdf" }
  }
}
```

The client's rule collapses to: *if there's a `cancel` link, show the button.* The March change ships once, on the server, and the 2023 partner integration gets it for free.

## What It Is

This is **hypermedia**, and in REST's vocabulary the constraint is HATEOAS — hypertext as the engine of application state. It's the part of Fielding's REST that 7.1a deliberately set aside, and the part almost nobody implements.

The idea: a response carries not only the data but the set of transitions currently available from it, as links. A client starts at a single entry point and navigates by following links it finds, rather than by constructing URLs from knowledge baked in at compile time.

The existence proof is the thing you're reading this in. A browser knows nothing about banking, and it operates your bank. It was never updated when your bank added a feature. It couples to `<a href>` and `<form>`, not to the bank.

One distinction worth making immediately, because both get called "discoverability" and they solve different problems:

- **OpenAPI (7.2) describes what is possible in general, at build time.** It's how a developer or a code generator learns the API's shape.
- **Hypermedia says what is possible for this resource, for this user, right now, at runtime.** It's how a running client learns that *this particular order* can be cancelled.

They're complements, and only the second one solves the March problem.

## Recognizing the Problem

- A client contains a function named `canCancel`, `isEditable`, or `availableActions`, and so does the server.
- A rule change requires a coordinated release across clients you don't control.
- "Button visible, then `403` on click" is a recurring support category.
- Two clients disagree about what a user is allowed to do, and both are partly right.
- You can't move or rename an endpoint because a mobile version from two years ago is still in the wild.
- Clients string-concatenate URLs from ids.
- Changing pagination strategy is a breaking change.
- Each new client integration re-derives the same entitlement logic from your docs.
- A plan upgrade takes effect on the server immediately, but the UI still hides the feature until a refresh of something else.

## How It Works

### Link relations are the contract

The URL is not what the client couples to. The **relation name** is.

```json
"_links": {
  "next":   { "href": "/orders?cursor=eyJpZCI6..." },
  "cancel": { "href": "/orders/8f21/cancellations", "method": "POST" }
}
```

The client knows what `next` and `cancel` mean. It has no opinion about the strings inside `href`, which means you can change them whenever you like. That inversion is the entire mechanism: coupling moves from URL structure (yours to maintain forever) to a small vocabulary of names (stable by design).

Standard relations — `self`, `next`, `prev`, `first`, `last`, `edit`, `related` — are registered with IANA. Domain-specific ones like `cancel` are yours, and convention is to either document them or namespace them as URIs.

### Links live in HTTP too, not just in bodies

Two pieces of hypermedia are already standard, already understood by tooling, and cost nothing:

```
201 Created
Location: /orders/8f21

200 OK
Link: </orders?cursor=eyJpZCI6...>; rel="next"
```

RFC 8288 `Link` headers work for any content type, including binary responses, and GitHub's API has driven pagination this way for over a decade. If you adopt one thing from this article, adopt these two.

### Affordances: a link is not always enough

`cancel` with an `href` tells a client *where*. Sometimes it needs *how*: which method, which fields, what's required.

Formats differ mainly in how far they go here:

| Format | What it adds | Cost |
|---|---|---|
| Ad-hoc `links` object | href + rel, maybe method | Nothing; no tooling either |
| **HAL** | `_links`, `_embedded` for inlined related resources | Minimal, widely understood |
| **HAL-FORMS** | Adds templates: method, content type, field list | Slightly more to generate |
| **JSON:API** | Links, relationships, plus a full spec for pagination/filtering/errors | Large spec surface, strong tooling |
| **Siren** | First-class `actions` with typed fields — a form, essentially | Verbose; niche adoption |
| **HTML** | All of the above, plus a universal client that already exists | You're rendering server-side now |

That last row is not a joke. htmx and Hotwire are hypermedia systems where the generic client is the browser, and they are by far the most widely deployed HATEOAS implementations in the world.

### Deriving links from the rule that's enforced

This is the part that determines whether a hypermedia API is useful or actively harmful.

A link is a **claim** that an operation will succeed. If the link generator and the endpoint's authorization check are two separate pieces of code, they will drift, and both directions of drift are bad:

- **Link present, request rejected** — you've reproduced the original problem, with extra steps.
- **Link absent, request would have succeeded** — an invisible feature. Nobody reports this, because nobody knows it exists.

The discipline is that one predicate answers both questions: the route guard asks it before executing, and the serializer asks it before emitting the link. Never trust the link itself as authorization — a client can POST to any URL it can guess.

```
client decides                          server decides
──────────────                          ──────────────
GET /orders/8f21                        GET /orders/8f21
→ { status: "processing" }              → { status: "processing",
                                             _links: { cancel: {…} } }

if (status === "pending"                if ("cancel" in order._links)
    || (status === "processing"           show(CancelButton)
        && !shipment
        && total < 10_000
        && user.role !== "viewer"))
  show(CancelButton)

  ×4 clients, ×4 release cycles           ×1, deployed at 14:02
```

## When It's Appropriate

- **Clients you can't update in lockstep.** Partner integrations, public APIs, mobile apps with a long tail of installed versions. The cost of a rule change is proportional to how many clients must ship it; hypermedia makes that number one.
- **Workflow-shaped domains.** Orders, claims, approvals, onboarding, moderation queues, deploy pipelines. Anywhere the user-visible question is "what can I do with this now," the answer is a state machine that already exists on the server, and duplicating it is pure cost.
- **Entitlement and plan gating.** Whether a feature is available depends on the tenant's plan (Module 15), which the client has no business evaluating.
- **Collection navigation, always.** Cursor pagination is only non-breaking if clients treat the cursor as opaque and follow `next`. This is the one place hypermedia has essentially won.
- **Generic or server-driven clients.** Admin consoles rendered from responses, htmx-style applications, internal tools generated from the API.
- **Long-lived URL spaces.** If you expect to reorganize services behind the API over years, links are what buy you the freedom to do it.

## When It's Unnecessary or Overkill

- **One first-party SPA deployed alongside the server.** The client is a build artifact from the same repository, shipped in the same pipeline. URL coupling costs nothing because both sides change together — and you'd rather have compile-time types than runtime links.
- **A read-only data API with no state-dependent actions.** If every caller can do everything to everything, there's nothing to advertise.
- **Full Siren machinery when two links would do.** The gap between `Link: rel="next"` and a complete affordance vocabulary is enormous, and most of the value is in the first inch.
- **The dream of the fully generic client.** It's worth saying plainly: no useful client has ever been written that discovers a domain it doesn't already understand. A client following links still needs to know what an order *is*, what `cancel` means, and what to render. Hypermedia removes coupling to URLs and to rule logic. It does not remove coupling to your domain, and arguments for HATEOAS that imply otherwise are why a generation of engineers concluded it was impractical.

## Trade-offs

- **Every read now runs every authorization check.** Emitting a `cancel` link requires evaluating the cancellation policy. A list endpoint returning 50 orders with 5 candidate actions each is 250 policy evaluations per request, where previously there were zero. If those checks hit the database, you've turned a cheap list into an N+1 (Module 6.4), and the standard fixes — batch-loading the policy inputs, caching per request — are now mandatory rather than optional.
- **Responses become user-specific, which breaks shared caching.** Two users fetching the same order get different links. That's `Cache-Control: private` at best, and it quietly gives back part of what 7.1a bought. Splitting data and affordances into separate responses recovers the caching and costs a round trip. There's no free version of this.
- **Payload growth.** Link blocks routinely double the size of a small resource. On mobile, over a slow connection, for a list of 100 items, that's measurable.
- **Two clients, one of them yours, disagreeing about the format.** There is no winner among HAL, JSON:API, Siren, and homegrown. Whichever you pick, most tooling won't know it, and your OpenAPI document will describe `_links` as an object with unspecified keys.
- **Typed clients get worse.** A generated TypeScript or Java client can give you `order.status` with a type. `order._links.cancel` is optional-by-nature — that's the point — so every call site handles absence, and codegen has nothing to generate for a link that may or may not be there.
- **Debugging moves.** "Why is the button missing?" is no longer a frontend question. It's a question about a predicate inside the serializer, and you need request-level visibility into which policies returned false.
- **It doesn't solve versioning.** Field semantics, required attributes, and representation shape still change in ways that break clients. Links free up your URL space; they don't free up your data contract (Module 33).
- **Partial adoption is normal but needs to be legible.** Half a hypermedia API — links on three endpoints, hardcoded paths everywhere else — is fine as a migration state and confusing as a permanent one, because clients can't tell which parts are authoritative.

## Alternatives

- **A `permissions` or `actions` array.** `{"actions": ["cancel", "refund"]}` — no hrefs, no format debate, trivially typed, and it solves the March problem completely. It doesn't free your URL space, which is the smaller of the two benefits for most teams. This is the pragmatic 80% answer and deserves to be the default starting point.
- **A capabilities endpoint.** `GET /me/capabilities` returning what this user can do globally. Works for coarse, plan-level gating; wrong for per-resource state, since capability depends on *which* order.
- **OpenAPI plus generated clients (7.2).** Build-time discovery. Strictly better for onboarding developers, strictly useless for runtime state.
- **Server-driven UI.** The maximal version: the server returns the screen — components, layout, actions — and the client renders it. Used heavily by mobile-first companies to avoid app-store release cycles. Enormous flexibility, and you've now written a UI framework and a rendering protocol.
- **HTML over the wire** (htmx, Hotwire, Turbo). If your only client is a browser, this is hypermedia with the client already written, and it makes most of this article's trade-offs disappear. It also makes your API a UI, which forecloses the partner integration.
- **Ship clients faster.** Sometimes the honest answer. If all four clients are yours and release weekly, the coupling is cheap and the indirection isn't worth it.

## How to Achieve It

**Level 0 — use the HTTP that's already standard.** `Location` on every `201`. `Link: rel="next"` on every paginated collection, with an opaque cursor. Costs a day, and it's what makes 7.3c's pagination change non-breaking later.
*Signal you're here:* clients constructing `?page=N` themselves.

**Level 1 — advertise available actions as names.** Add an `actions: ["cancel", "refund"]` array, generated from the same predicates the endpoints enforce. Clients switch from duplicated rules to checking membership.
*Signal to move on:* a "button shown, request rejected" support ticket, or a rule change that needed four releases.

**Level 2 — promote actions to links with hrefs.** Now URLs are free to move, and a client following links survives your reorganization.
*Signal to move on:* an endpoint you want to relocate and can't.

**Level 3 — add templates where forms are dynamic.** HAL-FORMS or Siren-style field descriptions, for cases where the *inputs* to an action vary by state or tenant — required fields on a cancellation reason, say.
*Signal you need it:* client-side form definitions that differ per plan or per workflow state.

**Level 4 — a single entry point.** `GET /` returns the root link set; clients hardcode one URL and discover everything else. Worth doing only if levels 1–3 are already paying off, and mostly for public APIs.

The path is genuinely incremental, and stopping at level 1 or 2 is a legitimate destination rather than a failure to finish.

## Implementation

TypeScript, because the mechanism that matters here is a single policy definition consumed by two places, and the type system makes the "these must stay in sync" requirement structural rather than aspirational.

```ts
type Policy<T> = {
  rel: string;
  href: (r: T) => string;
  method: "POST" | "PATCH" | "DELETE";
  allowed: (r: T, actor: Actor) => boolean;
};

const orderPolicies: Policy<Order>[] = [
  {
    rel: "cancel",
    href: (o) => `/orders/${o.id}/cancellations`,
    method: "POST",
    allowed: (o, actor) =>
      actor.can("orders:write") &&
      (o.status === "pending" ||
        (o.status === "processing" && !o.shipmentId && o.totalCents < 1_000_000)),
  },
  // refund, reopen, …
];
```

One consumer builds the representation:

```ts
function serializeOrder(order: Order, actor: Actor) {
  const _links: Record<string, { href: string; method?: string }> = {
    self: { href: `/orders/${order.id}` },
  };
  for (const p of orderPolicies) {
    if (p.allowed(order, actor)) {
      _links[p.rel] = { href: p.href(order), method: p.method };
    }
  }
  return { id: order.id, status: order.status, total: order.total, _links };
}
```

The other enforces it, and this is the half that must exist:

```ts
router.post("/orders/:id/cancellations", async (req, res) => {
  const order = await orders.load(req.params.id, req.tenant);
  const policy = orderPolicies.find((p) => p.rel === "cancel")!;

  if (!policy.allowed(order, req.actor)) {
    return problem(res, 409, "This order can no longer be cancelled");
  }
  // …
});
```

Three asides.

**The link is advertising, never authorization.** The guard above is not redundant with the serializer — a client can POST to a URL it guessed, read from a log, or cached from an earlier state. Every implementation that treats link presence as permission has a vulnerability, and it's usually found by someone replaying a request from yesterday.

**`allowed` must not touch the database.** In `serializeOrder` it runs once per order per policy, so a query inside it turns a 50-item list into 250 round trips. Everything the predicate needs — the shipment flag, the actor's permission set — has to be loaded in the same batch as the orders themselves. This is the trade-off from the section above showing up as a concrete constraint on how policies may be written, and it's worth enforcing in review, because the version that queries works perfectly in a single-item test.

**The status code on rejection tells a story.** Returning `409 Conflict` rather than `403 Forbidden` for a state-based refusal distinguishes "you never could" from "you can't now" — which is exactly what a client needs to decide between showing an error and refreshing the resource to pick up new links.

## Further Reading

- **RFC 8288, _Web Linking_** — the `Link` header, and the model for relation types. Short.
- **IANA Link Relations registry** — check here before inventing a relation name; `next`, `edit`, `describedby`, and `related` probably already cover it.
- **draft-kelly-json-hal** and the **HAL-FORMS** specification — the smallest format that's actually a format.
- **JSON:API** — a full specification covering links, relationships, pagination, filtering, and errors together. Worth reading even if you don't adopt it, as a catalogue of decisions.
- **Siren** — for the affordance-with-fields model, which nothing else expresses as directly.
- **Roy Fielding, "REST APIs must be hypertext-driven" (2008)** — the blog post that drew the line, and the origin of most arguments on this topic.
- **Martin Fowler, "Richardson Maturity Model"** — the standard ladder (URIs → verbs → hypermedia), useful mainly as shared vocabulary in design discussions.
- **_Hypermedia Systems_, Gross, Stepinski & Akşimşek** — the htmx authors' book; the strongest modern case for hypermedia, made from the HTML side.
- **The GitHub REST API root endpoint** — a live level-4 entry point you can `curl` right now, and their pagination `Link` headers are the canonical example of level 0 done right.

A Java sibling would add something real here: Spring HATEOAS turns link assembly into a framework concern with `RepresentationModelAssembler` and method-reference-based URL building, which removes the hand-written `href` functions above entirely — and correspondingly makes the policy-drift problem *easier* to hide, since the links are generated somewhere the authorization code isn't. Not yet written.

---

The habit worth taking away: whenever you find the same conditional on both sides of a network boundary, ask which side owns it. The answer is almost always the server, and the question of how the client finds out is smaller than it looks — a list of allowed action names, returned with the data, solves most of it before any specification is involved.
