# Input Validation at the Boundary

_Module 7.3a — RESTful API Design & Implementation_

## The Problem

An expense reporting API. `POST /expenses` takes an amount, a currency, a date, a category, and an optional receipt id.

Validation for that endpoint currently lives in five places, and each was added by someone reasonable:

- The **gateway** validates against the OpenAPI schema: `amountMinor` is an integer, `currency` matches `^[A-Z]{3}$`.
- The **request DTO** has `@NotNull` and `@Positive`.
- The **service** checks that the category is one the tenant configured, that the date isn't in the future, and that the amount is under the tenant's per-expense policy limit.
- The **repository** does a lookup to confirm the receipt exists and belongs to this tenant.
- The **database** has `NOT NULL`, a `CHECK (amount_minor > 0)`, and a foreign key.

Nothing here is wrong, exactly. And yet:

**A typo silently succeeds.** A client sends `"ammount_minor": 4500` instead of `"amountMinor"`. The JSON parser ignores unknown properties, the field is absent, a default of `0` is applied somewhere, and the API returns `201 Created` for an expense of nothing. No error is produced at any of the five layers. The user finds out at month end.

**A second entrance skips four of the five layers.** The CSV bulk importer, written a year later, builds entities and calls the repository directly — reasonably, since it isn't an HTTP request. It skips the gateway, the DTO, and the service. Rows land with a `category` that no longer exists in the tenant's configuration. Three weeks later `GET /expenses` starts returning `500` for one customer, because the response serializer assumes every expense's category resolves to a name.

**A failure the user can't act on.** Someone attaches the same receipt twice. The unique index rejects it, the exception propagates, and the client receives:

```
500 Internal Server Error
{"error":"ERROR: duplicate key value violates unique constraint \"expenses_tenant_receipt_uniq\""}
```

That's an internal schema name, a 5xx that pages an engineer for a user mistake (7.1a), and no indication of what to do differently.

Three failures, three different-looking bugs, and one cause: **"validation" is being used as a single word for four genuinely different kinds of check**, which get scattered across whichever layer the author happened to be in. Some need no information at all. Some need a database read. One of them can't be done correctly outside a transaction. Treating them as one concern is what puts them in five places and guarantees that some entrances miss some of them.

## What It Is

The idea is **validation at the boundary**: untrusted input is checked once, at the point where it enters the system, and converted into a value that downstream code can trust unconditionally.

The sharper version of this has a name — **parse, don't validate**. The difference is in the signature. A validator has the shape `check(input) → boolean`: you learn something, then carry on holding the same untrusted thing, and every later piece of code has to either re-check or take it on faith. A parser has the shape `parse(input) → Command | Errors`: on success you're holding a *different value*, one whose type means the checks already passed. Code downstream can't forget to validate, because it never receives anything that needs validating.

Two neighbors to keep separate, because conflating them is how validation ends up doing database queries:

- **Authorization** — whether *this caller* may do this — is not validation. A well-formed request from someone who isn't allowed to make it is a `403`, not a `422`, and the check belongs with the policy logic (7.1b).
- **Output encoding** is not input sanitization. You don't strip `<script>` from stored text to prevent XSS; you encode at render time, because the same string is safe in JSON and dangerous in HTML. Module 20.

## Recognizing the Problem

- A field name typo produces a `201` instead of an error.
- Database constraint violations reach clients as `500`s, complete with index names.
- The same business rule appears in a controller, a service, and a job, with three slightly different conditions.
- A background job or importer creates records the public API would have rejected.
- Error responses report one problem at a time, so fixing a form takes six round trips.
- `null` and "field absent" are treated the same, so clients can't clear an optional value.
- Someone asks where a rule is enforced and the answer takes ten minutes to find.
- A validation rule was changed in one place and an old code path still enforces the old one.
- Reading a record fails because it was written in a state the reader assumes is impossible.

## How It Works

### Four kinds of check, and where each belongs

| Kind | Example | Needs | Home |
|---|---|---|---|
| **Syntactic** | Valid JSON, correct `Content-Type`, within size limit | nothing | Framework or gateway → `400`, `413`, `415` |
| **Structural** | Required fields, types, formats, ranges, enum membership, array length | nothing | The boundary parser → `422` |
| **Contextual** | Receipt exists, belongs to this tenant, category is configured | reads | Application service → `404` / `422` |
| **Concurrent invariant** | This receipt isn't already claimed; the budget isn't exceeded | the transaction | Database constraint → `409` |

The first two need no information beyond the request itself, which is why they can be done once, at the edge, deterministically, and with complete error reporting. The third needs the current state of the system. The fourth needs the current state *and* a guarantee it won't change underneath you.

That last row is the one teams get wrong, and it's worth being blunt about: a contextual check is always a TOCTOU race.

```java
if (!receiptAlreadyClaimed(receiptId)) {   // true at 14:02:03.100
    insertExpense(...);                    // another request inserted at .101
}
```

The `if` is a UX affordance — it produces a nice error most of the time. It is not enforcement. If a duplicate genuinely matters, the unique constraint is the check and the `if` is decoration. This is the optimistic-locking argument from Module 6.5 arriving in a new place, and the practical consequence is that you need *both*: the read for a good message, the constraint for correctness, and a translation from constraint violation back into the same error shape so the client can't tell which one fired.

### One boundary, and what actually counts as one

The trap in the problem section wasn't that validation was missing. It was that the HTTP controller isn't the only entrance:

```
   HTTP request  ─┐
   CSV import    ─┼──►  parse ──► Command ──► service ──► repository ──► DB constraints
   queue consumer─┤       ▲                                                  ▲
   admin tool    ─┘   one place                                     last line of defence
```

If the rules live in request DTO annotations, they are bound to HTTP, and every non-HTTP entrance gets none of them. The fix is to put the parse step at the **application service boundary** — the parser produces a command object, and the HTTP layer is one adapter that calls it. The importer and the queue consumer are other adapters.

This also settles a recurring argument about layering. The controller's job is protocol: content negotiation, status codes, header handling, mapping errors to a response shape. It is not the place where domain rules live, and once you notice that the same rules are needed by three non-HTTP callers, that stops being a stylistic preference.

### Three ways input passes validation and still isn't what the client meant

**Unknown properties.** Most parsers ignore them by default, which converts a client-side typo into silent data loss. Rejecting unknown fields (`additionalProperties: false`, Jackson's `FAIL_ON_UNKNOWN_PROPERTIES`, a strict schema) turns that into an immediate, obvious error.

But strictness has a real cost, and it isn't symmetric between internal and public APIs. During a rolling deploy, a client that already knows about a new field will send it to an old instance that doesn't. A partner on last year's SDK may send fields you removed. RFC 9413 is worth reading here — the modern position is that liberal acceptance postpones failures rather than preventing them, but the decision still comes down to who your callers are. Internal APIs with lockstep deploys: reject. Public APIs with a long client tail: ignore unknowns, and say so in your docs so nobody mistakes silence for acceptance.

**Coercion.** `"25"` becoming `25`, `"false"` becoming `false`, a float quietly truncating to an int. Coercion is genuinely useful for query parameters, which are always strings, and a liability in request bodies, where a type mismatch usually means the client is confused. Configure the two differently.

**`null` versus absent.** For `PATCH` these mean different things — "set this to nothing" and "don't touch it" — and most parsing layers collapse them. If your API supports partial updates, this distinction needs to survive parsing, which usually means an explicit three-state representation rather than an optional field (7.1a).

### Errors the client can act on

Two properties matter, and both are frequently missed:

**Aggregate.** Fail on the first error and a client with six problems needs six round trips. Collect all structural errors and return them together. This requires a parser that accumulates rather than throws, which is a property to check for when choosing one.

**Locate.** Each error needs a machine-readable field path (JSON Pointer works well), a stable error code the client can branch on, and a human message. `"Invalid input"` is not an error report.

What not to include: internal identifiers (index names, table names, class names), and the offending value itself when it might be sensitive. The response format for all of this is the subject of 7.3b.

### Validation is also an attack surface

The same layer that protects you can be the vulnerability:

- **Unbounded inputs.** No `maxLength` on a string, no `maxItems` on an array, no body size limit — each is a memory exhaustion vector reachable by anyone with a `curl` command.
- **Deep nesting.** A thousand-deep JSON array can blow the parser's stack before your code runs. Depth limits belong in the parser configuration.
- **Catastrophic regex backtracking.** A `pattern` constraint applied to attacker-controlled input can take exponential time. Validating email addresses with a clever regex is the classic instance.
- **Mass assignment.** Binding a request body straight onto a persistent entity lets a caller set `role`, `tenantId`, or `isAdmin` by adding a field. The command-object separation described above is not only a layering preference — it's the control that makes this impossible.

## When It's Appropriate

Boundary validation itself isn't optional; the question is how much rigor is worth it. The full discipline — parse into distinct types, one shared entrance, no re-checking downstream — earns its cost when:

- **Callers are untrusted or numerous.** Public APIs, partner integrations, anything reachable from a browser.
- **The same operation has more than one entrance.** This is the single strongest signal, and it's usually already true by the time anyone looks.
- **Invalid states are expensive.** Money, health records, legal documents, anything where a bad row has to be found and repaired by hand later.
- **The code will outlive its authors.** "Someone will remember to check" is false over a two-year horizon.
- **Reads assume more than writes enforce.** If your serializers, reports, or downstream consumers assume invariants, those invariants must be established at write time or they'll be discovered at read time, in production.

## When It's Unnecessary or Overkill

- **Wrapping every string in its own type.** Reserve distinct types for values with real invariants — money, identifiers, email addresses, tenant ids — and let names stay strings. The discipline is valuable; applied uniformly it's ceremony.
- **Re-validating in every layer.** Defensive re-checks downstream add noise, drift from the original rule, and produce inconsistent errors depending on where they fire. If the type says it's valid, trust it; that's what it's for.
- **Expressing contextual rules in the schema.** Cross-field conditionals are already awkward in JSON Schema; database-dependent rules are impossible. Attempts to force them produce validators that run queries, which is the layering violation that made the original mess.
- **Strict unknown-field rejection on a public API** with clients you don't control.
- **Tenant-configurable validation.** Once rules are data rather than code — per-tenant required fields, custom categories — this stops being boundary validation and becomes a small rules engine with its own versioning and testing story. Worth recognizing early, because the incremental path from annotations to that is unpleasant.

## Trade-offs

- **The rules exist in more than one artifact.** The published schema (7.2), the parser, and the database constraints all encode overlapping truths. Generating some from others helps for structural rules and does nothing for contextual ones, so some duplication is permanent; the goal is that it's deliberate and tested, not that it's zero.
- **Strictness makes changes breaking.** Every constraint you enforce narrows the set of accepted requests, and narrowing is a breaking change (Module 33). An API that validates aggressively is harder to evolve than one that doesn't — that's a real cost, not just a virtue.
- **Parsing into types costs boilerplate**, and fights ORMs and serialization frameworks that want plain field-mapped objects. Expect a mapping layer, and expect occasional friction with tooling that assumes it can construct your types by reflection.
- **Error aggregation is slower and more complex** than short-circuiting, and it requires the parser to keep going after a failure — which means a value that failed can't be used to evaluate later rules.
- **Detailed errors leak information.** Reporting which enum values are valid, or that a referenced id exists but belongs to another tenant, tells an attacker things. The `403`-versus-`404` decision from 7.1a recurs here at field granularity.
- **Edge validation duplicates knowledge into infrastructure.** Validating at the gateway from your OpenAPI document is excellent defence in depth, and it means a schema change now requires a deploy of something you may not own, plus your application stops seeing traffic it could have handled or logged.
- **Per-item validation dominates bulk endpoints.** Validating 10,000 rows synchronously is a timeout; that's a design constraint on bulk operations rather than a tuning problem (7.3d).

## Alternatives

- **Gateway-enforced schema validation** driven by the OpenAPI document. Requests that don't conform never reach your code. Strong as a layer, dangerous as the only one — internal callers usually bypass it.
- **Annotation-based validation** (Jakarta Bean Validation, class-validator). Declarative, framework-integrated, well understood, and weakest exactly where the hard cases are: cross-field conditions, and being welded to the HTTP request object rather than the domain command.
- **Database constraints as the primary enforcement.** Unattractive error messages, and the only approach that's actually race-free. Not an alternative so much as the layer nothing else can replace — see the concurrency row above.
- **Schema-as-parser libraries** (zod, io-ts, valibot, Pydantic). A single declaration that produces the runtime check and the static type together, which is what makes parse-don't-validate cheap enough to do everywhere.
- **Accept-then-validate-asynchronously.** For imports and bulk submissions: accept with `202`, validate per-row in the background, report results as a job resource. Changes the UX contract entirely and is the only thing that works at volume (Module 10, 7.3d).

## How to Achieve It

**Level 0 — make failures honest.** Every validation failure returns a `4xx` with a field path. No constraint violation reaches a client verbatim. This is a day of work and removes a category of false pages.
*Signal you're here:* a `500` whose cause was a malformed date.

**Level 1 — aggregate and standardize.** One error shape across the whole API, all structural errors reported at once (7.3b).
*Signal to move on:* a client engineer complaining about fixing one field at a time.

**Level 2 — move the parse step behind the controller.** Define command objects; the controller maps HTTP to a command and back. Point the importer and the queue consumer at the same entrance.
*Signal you need it:* any second entrance to an operation — that's the whole trigger.

**Level 3 — give the invariant-bearing values their own types.** Money, identifiers, tenant-scoped references. Downstream signatures take those types, so a missed check becomes a compile error rather than a runtime one.
*Signal to move on:* a bug caused by a valid-looking value used in the wrong place — a tenant id passed where a user id belonged.

**Level 4 — derive the published schema from the same definition** so the gateway, the docs, and the parser can't disagree about structural rules (7.2).

**Level 5 — push the race-sensitive rules into constraints** and translate violations back into the standard error shape, so that the `409` a client sees from a genuine race is indistinguishable from the one produced by the friendly pre-check.

## Implementation

TypeScript, because a schema-as-parser library makes the difference between validating and parsing visible in the types rather than in commentary.

One definition, at the application boundary:

```ts
export const CreateExpense = z.object({
  amountMinor: z.number().int().positive().max(1_000_000_00),
  currency:    z.enum(["USD", "EUR", "GBP", "JPY"]),
  spentOn:     z.coerce.date().max(new Date(), { message: "cannot be in the future" }),
  category:    z.string().min(1).max(64),
  receiptId:   z.string().uuid().optional(),
  note:        z.string().max(2_000).optional(),
}).strict();

export type CreateExpense = z.infer<typeof CreateExpense>;
```

The HTTP adapter does protocol work and nothing else:

```ts
router.post("/expenses", async (req, res) => {
  const parsed = CreateExpense.safeParse(req.body);
  if (!parsed.success) {
    return problem(res, 422, "Validation failed", {
      errors: parsed.error.issues.map((i) => ({
        field: "/" + i.path.join("/"),   // JSON Pointer
        code: i.code,
        message: i.message,
      })),
    });
  }
  const expense = await expenses.create(req.tenant, req.actor, parsed.data);
  res.status(201).location(`/expenses/${expense.id}`).json(expense);
});
```

And the importer — the entrance that caused the original incident — calls the same parser, differing only in what it does with the failures:

```ts
for (const [rowNumber, row] of rows.entries()) {
  const parsed = CreateExpense.safeParse(mapCsvRow(row));
  if (!parsed.success) { report.reject(rowNumber, parsed.error.issues); continue; }
  await expenses.create(tenant, systemActor, parsed.data);
}
```

The service signature is `create(tenant, actor, input: CreateExpense)`. There is no overload taking a raw row, and that absence is the design.

Three asides.

**`.strict()` is the line that would have caught `ammount_minor`.** Without it the typo parses cleanly into an object missing a required field — or worse, into one where the field has a default. With it, the client gets a `422` naming the unrecognized property. Whether you want it depends entirely on the caller tail discussed above; what you don't want is to have never decided.

**The contextual checks are deliberately not here.** Whether the category is configured for this tenant, and whether the receipt is already claimed, need reads — so they live in `expenses.create`, after parsing, where the transaction is. The claim check is backed by a unique index, and the handler translates that violation into the same `409` shape as the friendly pre-check, because from the client's side those are the same event.

**Inferred types are structural, which weakens the guarantee.** `z.infer` gives a plain object type, so any code can construct a `CreateExpense` literal that skips the parser — the compiler won't object. Branded types (`.brand<"CreateExpense">()`) close that hole by making the type unconstructible outside the parser, at the cost of friction everywhere you build test fixtures. Worth it for money and identifiers; usually not worth it for every request shape. Languages with nominal types get this for free, which is the main thing a Java or Go version of this code would show differently.

## Further Reading

- **Alexis King, "Parse, don't validate" (2019)** — the essay that named the distinction. Haskell examples, entirely language-independent argument.
- **RFC 9413, _Maintaining Robust Protocols_** — the IETF's reconsideration of Postel's law, and the best available treatment of the strict-versus-lenient decision.
- **JSON Schema validation keyword reference** — what's expressible, what isn't, and why cross-field conditions are painful.
- **OWASP Input Validation Cheat Sheet** and the **ReDoS** page — the attack-surface half, with concrete limits worth copying.
- **Jakarta Bean Validation specification** — the annotation model, including validation groups, which is how the Java ecosystem handles context-dependent rule sets.
- **zod / valibot / io-ts documentation** — for the parser-as-schema pattern, including error accumulation behavior, which differs between them in ways that matter for the aggregation requirement.
- **Yaron Minsky, "Effective ML" / "Making illegal states unrepresentable"** — the design argument behind level 3.

A Java sibling is genuinely worth writing here, because Bean Validation inverts the article's central move: annotations attach rules to the request DTO, which binds them to the HTTP layer and makes the "one entrance for all callers" property harder to achieve rather than easier — and validation groups, `@Valid` cascade behavior, and the `ConstraintValidator` escape hatch are a distinct set of trade-offs worth laying out on their own. Not yet written.

---

The habit to carry: when you find the same rule enforced in three layers, the question isn't which layer is correct. It's which of the four kinds of check it is — because that determines the only layer where it *can* be correct, and the copies in the other two are either error messages or decoration.
