# Payload and Transfer Efficiency

_Module 7.4b — RESTful API Design & Implementation_

## The Problem

A project management app. The task list screen calls `GET /projects/42/tasks?limit=50`.

Each task in the response carries thirty-odd fields: the full markdown description (2KB on average), a custom fields object, an embedded assignee, an embedded project repeated identically fifty times, an attachments array, and timestamps. The response is 1.4 MB.

The screen renders four things per row: title, assignee avatar, due date, status. About 200 bytes of the 28KB per row is used. The rest is transferred, parsed, allocated, and discarded.

On a 4G connection at a realistic 5 Mbps that's roughly two seconds of transfer before anything renders. On a low-end Android device, parsing 1.4MB of JSON is another noticeable chunk. The server spent its time fetching and serializing thirty columns for rows that needed five.

Someone enables gzip. The response drops to about 180KB, because JSON with repeated keys and prose compresses beautifully. Transfer time falls to a quarter of a second and everyone declares victory — **but the server still fetched and serialized 1.4MB, and the client still parses 1.4MB after decompressing it.** Compression fixed the wire and neither end.

Meanwhile the detail screen has the opposite problem. It needs one task plus its comments and its attachments, and gets them in three round trips, because the representation that was too big for the list is too small for the detail.

So the obvious fix ships: `?fields=id,title,assignee.name` and `?include=comments,attachments`. Six months later:

- Every screen requests a different field set, so every response is a distinct cache entry and the hit rate collapses.
- `?include=comments` on a 50-row page runs fifty extra queries.
- The OpenAPI schema can no longer describe the response (7.2), so generated clients can't type it.
- Someone requests `?include=comments.author.organization` and one HTTP request produces about 2,500 database queries.

The shape underneath: **a large response has three separate costs — bytes on the wire, work on the server, work on the client — and they respond to different remedies.** Compression touches one of them. Everything that touches all three makes the response shape a client-controlled variable, which costs you caching, typing, documentation, and a query-cost problem you didn't have before.

## What It Is

There isn't one technique here; there's a family, and they're often conflated:

- **Compression** — the same data, fewer bytes on the wire.
- **Representation design** — different representations for different uses; a list item is not a detail view.
- **Sparse fieldsets** — the client selects which fields it wants.
- **Expansion / includes** — the client pulls related resources into one response.
- **Streaming** — deliver incrementally instead of all at once.

And two failure modes that pull in opposite directions:

**Over-fetching** — each item carries more than the caller needs.
**Under-fetching** — each response carries too little, so the caller makes more requests.

Almost every fix for one worsens the other. That tension is the subject.

## Recognizing the Problem

- A list endpoint returns a field no list screen displays.
- Response sizes are measured in megabytes for a page of rows.
- The same nested object appears identically dozens of times in one response.
- Mobile users report slow screens that profile as parse time, not network.
- A detail screen makes three or four requests before it can render.
- Your cache hit rate fell after adding a query parameter.
- `?include=` requests appear in the slow query log with fifty near-identical statements.
- Egress is a visible line on the cloud bill.
- Nobody can say whether compression is actually being applied in production.
- Two clients need two shapes and the proposal is a third query parameter.

## How It Works

### Three costs, and what each remedy actually touches

```
                           wire bytes   server CPU/IO   client parse
  compression                  ✓              ✗              ✗
  narrower representation      ✓              ✓              ✓
  sparse fieldsets             ✓             ✓*              ✓      (*only if pushed into SQL)
  includes                    ✗ bigger      ✗ more         ✗ more   — buys round trips instead
```

Compression is the only one with no design consequences, and it fixes exactly one column. Everything else is a trade, and the asterisk on sparse fieldsets is where most implementations quietly fail: trimming fields *after* loading the row saves bytes and nothing else.

### Compression

Almost always someone else's job. It belongs at the reverse proxy, gateway, or CDN, not in your handler — and the first thing to do is check whether it's already on, because double compression and compressing something the CDN then re-compresses are both real.

- **gzip** is universal. **Brotli** compresses better, at higher CPU cost on the highest levels — excellent for content you can pre-compress. **Zstandard** is fast at good ratios and increasingly available. Negotiated by `Accept-Encoding`.
- **Don't compress** already-compressed payloads (images, video, archives) or tiny bodies — below roughly a kilobyte the framing overhead exceeds the savings.
- **JSON compresses very well** — 70–90% is typical, because the keys repeat on every row. This is also the argument against shortening field names to save space: compression already removes that redundancy, and you've traded readability for nothing.
- **BREACH and CRIME** are worth knowing before adopting "just enable gzip everywhere." When a compressed response contains both a secret and attacker-influenced input, response size leaks information about the secret. This mostly bites HTML with reflected parameters and CSRF tokens rather than JSON APIs, but the mitigations — don't reflect user input alongside secrets, or add per-response length randomization — are cheaper to apply than to retrofit.
- **Compressed requests** are rarely supported. If you accept them, bound the decompressed size; a decompression bomb is a few kilobytes of upload and a gigabyte of memory.

### Design the representations before adding knobs

The cheapest fix in this whole article usually isn't a query parameter. It's noticing that a list item and a detail view are **two different representations** and letting them be:

```
GET /tasks          → summary: id, title, status, due, assignee ref
GET /tasks/8f21     → full: everything
```

Two documented shapes. Both cacheable. Both expressible in the spec. Both typeable by generated clients. No query-cost surface. It feels less flexible than field selection, and for the large majority of applications it is flexible enough — and it preserves every property 7.1a and 7.2 were built on.

If more variation is genuinely needed, the next step should be **named presets** rather than arbitrary selection:

```
GET /tasks?view=summary
GET /tasks?view=board      ← the fields the kanban screen needs
```

A small closed set of shapes keeps cache keys few, keeps the spec accurate, and keeps the server's projections known in advance.

### Sparse fieldsets, if you must

`?fields=id,title,assignee.name`, or JSON:API's `fields[tasks]=`.

The mechanics that make it worth doing: parse the list, check it against an **allowlist**, and translate it into the actual `SELECT` columns. If the projection doesn't reach the database, you've saved transfer and left the server's cost untouched.

The costs that come with it:

- **Cache fragmentation.** Every distinct field set is a distinct URL and a distinct entry. Hit rates fall roughly with the number of combinations in use.
- **The response type becomes a subset**, and OpenAPI has no good way to say "these fields, or those." Generated clients end up with everything optional, which pushes null checks into every call site.
- **Client code diverges per screen**, because the same model object arrives populated differently depending on what was asked for.
- **Nested selection multiplies all of the above** and is where the parser stops being small.

### Includes, and the query cost they hide

`?include=assignee,comments` addresses under-fetching. The cost model is simple and unforgiving: **each include must be one batched query per page, not one per row.** Collect the ids, issue a single `WHERE id IN (…)`, stitch in memory. Anything else is the N+1 from Module 6.4 with a query parameter in front of it.

Then three limits, all mandatory:

- **An allowlist** of includable relations per endpoint.
- **A depth cap.** `comments.author.organization` is a tree, and each level multiplies.
- **A breadth cap**, because five includes on a 50-row page is five batched queries that each have to stay fast.

Without these you have built GraphQL's query-cost problem without GraphQL's query-cost tooling (Module 8), and the same reasoning as 7.3c's filters applies: exposing query power means taking on query planning as public surface.

### HTTP/2 and /3 changed the arithmetic

Much of the "fewer, bigger requests" instinct dates from HTTP/1.1, where six connections per host and head-of-line blocking made every extra request expensive. With multiplexing and header compression, many small parallel requests are dramatically cheaper than they used to be.

What did *not* get cheaper is a **dependent** sequence — request A, read its ids, request B. Latency still compounds on waterfalls. So the modern version of the chattiness argument is narrower than the 2015 version: parallel requests are close to free, sequential ones are not, and the fix for a waterfall is an include or a purpose-built endpoint, not a general field-selection system.

Measure on the protocol you actually serve before designing around round-trip counts.

### Streaming, and binary formats

**Streaming** (NDJSON over chunked transfer) drops time-to-first-byte and bounds memory on both ends for large collections. The catch is error handling: once you've sent `200` and half the rows, a failure has nowhere to go except an in-band error record or a trailer, and most client libraries handle neither well.

**Binary formats** — Protobuf, MessagePack, CBOR — are smaller and faster to parse than JSON. After gzip the *size* advantage narrows considerably for JSON-shaped data, which people consistently overestimate; the parse-speed advantage is the more durable one. The cost is losing human readability and every tool that assumes JSON, which is why this generally lands internally (gRPC, Modules 23 and 36) rather than on a public API.

**Serialization cost itself** is often the largest server-side component for big responses, and it's invisible in database metrics. Reflection-heavy mappers, building whole object graphs before writing, and re-rendering identical immutable resources on every request are the usual causes. The cheapest fix for the last one is upstream in 7.4a: a `304` skips serialization entirely.

## When It's Appropriate

- **Mobile and low-bandwidth clients**, where both transfer and parse are visible to users.
- **Large collection responses**, especially ones containing prose or blobs.
- **Egress-cost-sensitive workloads** — bandwidth is a real line item at volume.
- **Public APIs with heterogeneous consumers**, where presets or includes prevent every client fetching everything.
- **Screens with genuinely different needs** — the list/detail split, which is nearly universal and nearly always worth doing.

## When It's Unnecessary or Overkill

- **Internal APIs on a fast network with small payloads.** Enable compression, stop there.
- **Field selection where two named representations would do.** This is the most common overshoot in the article.
- **Optimizing bytes when the bottleneck is database time** or a downstream call. Measure first; payload work frequently targets the wrong cost.
- **Binary encoding for a public JSON API.** The tooling loss outweighs the post-compression size win.
- **Building an include DSL for one client you control.** Add the fields, or add an endpoint for that screen.
- **Shortening field names.** Compression already handles the repetition; you've made the API unreadable to buy nothing.

## Trade-offs

- **Client-controlled shape costs you caching, typing, and specification accuracy at once.** Those three are not independent — they all derive from the response shape being knowable in advance, and field selection removes exactly that.
- **Includes are a denial-of-service surface.** Deep or wide expansion is cheap for the caller and expensive for you, so allowlists, caps, and statement timeouts are load-bearing rather than defensive.
- **Presets ossify.** Once `?view=summary` is published, its contents are contract: adding a field is safe, removing one is breaking (Module 33). You've created a second API surface to version.
- **Two representations mean two serializers**, two sets of tests, and drift — a field added to the detail view and forgotten in the summary is a bug report six weeks later.
- **Compression costs CPU per response.** At high request rates on large bodies this is measurable; pre-compress what's static, tune levels rather than defaulting to maximum, and consider zstd where clients support it.
- **Streaming complicates everything downstream** — error handling, client libraries, proxies that buffer, and any middleware that wants a `Content-Length`.
- **Payload optimization can mask the real problem.** Fifty rows at 28KB might mean the page size is wrong (7.3c), or that a 2KB markdown description has no business being in a list row at all. Fix the representation before building machinery to trim it.
- **Every knob is permanent support surface.** A field-selection parameter is forever, including the combinations nobody anticipated.

## Alternatives

- **GraphQL** (Module 8) — client-shaped responses taken seriously, with query cost analysis, persisted queries, and batching tooling built for exactly the problems `?fields=` and `?include=` create. Worth stating plainly: if you're designing a field-selection and expansion DSL, you're building a less complete GraphQL. That may be the right call — but it should be a decision, not a drift.
- **Backend-for-frontend** — one endpoint per screen, shape owned by the server. Keeps caching, typing, and cost control; costs a layer and couples an API to a UI.
- **Conditional requests** (7.4a) — the cheapest payload optimization is not sending the payload.
- **Caching and CDN** (7.1a, Module 13) — cheaper still is not reaching the origin.
- **Push and deltas** — SSE or WebSockets (Module 9), or a `?since=` change feed (7.3c). Don't re-send what didn't change.
- **Smaller pages.** Frequently the entire fix, and it requires no new concepts.

## How to Achieve It

**Level 0 — measure the three costs separately.** Transfer time, server time, client parse time. Most payload work targets whichever one is easiest to change rather than whichever one is binding.
*Signal you're here:* a plan to "reduce payload size" with no number attached to why.

**Level 1 — verify compression is on, at the edge, in production.** Check `Content-Encoding` on a real response through the real CDN. Exclude tiny and already-compressed bodies.
*Signal you need it:* nobody can say where compression happens.

**Level 2 — remove the heavy field nobody displays.** The 2KB description in a list row. This is usually the single biggest win in the article and it requires no API knobs.
*Signal to move on:* a response where one field is most of the bytes.

**Level 3 — split list and detail representations**, document both, and make the summary genuinely summary.
*Signal to move on:* a list endpoint whose response equals its item endpoint's.

**Level 4 — named presets** if variation persists. Closed set, documented, each with a known projection.
*Signal you need it:* three screens wanting three shapes of the same resource.

**Level 5 — includes, with an allowlist, batched loading, and depth and breadth caps.**
*Signal to move on:* a client making a dependent request waterfall.

**Level 6 — reconsider the architecture.** If clients keep needing new shapes, the answer is GraphQL or a BFF, not a seventh query parameter.

## Implementation

Go, because the two things that matter here — whether the projection reaches the database, and whether includes are batched — are both about what SQL actually runs, and this shows it without a framework in the way.

Presets as a closed, server-owned map:

```go
var views = map[string][]string{
    "summary": {"id", "title", "status", "due_on", "assignee_id"},
    "board":   {"id", "title", "status", "due_on", "assignee_id", "labels"},
    "full":    {"id", "title", "status", "due_on", "assignee_id", "labels",
                "description", "custom_fields", "created_at", "updated_at", "version"},
}

func columnsFor(view string) ([]string, error) {
    cols, ok := views[view]
    if !ok {
        return nil, &DomainError{Code: "unknown_view", Status: 400,
            Detail: "view must be one of: summary, board, full"}
    }
    return cols, nil
}
```

The query builds its column list from that map and never from the request:

```go
cols, err := columnsFor(view)
if err != nil { WriteError(w, r, err); return }

q := fmt.Sprintf(
    `SELECT %s FROM tasks WHERE project_id = $1 AND tenant_id = $2
      ORDER BY due_on, id LIMIT $3`,
    strings.Join(cols, ", "))
```

And includes, batched by construction:

```go
var includable = map[string]bool{"assignee": true, "labels": true, "comments": true}

func (h *Handler) expand(ctx context.Context, tenant string, tasks []Task, includes []string) error {
    if len(includes) > maxIncludes {
        return &DomainError{Code: "too_many_includes", Status: 400}
    }
    for _, inc := range includes {
        if !includable[inc] {
            return &DomainError{Code: "unknown_include", Status: 400,
                Detail: fmt.Sprintf("%q cannot be included on this endpoint", inc)}
        }
        switch inc {
        case "assignee":
            ids := distinctAssigneeIDs(tasks)                       // dedupe first
            users, err := h.users.ByIDs(ctx, tenant, ids)           // ONE query
            if err != nil { return err }
            attachAssignees(tasks, users)
        case "comments":
            taskIDs := idsOf(tasks)
            byTask, err := h.comments.ByTaskIDs(ctx, tenant, taskIDs) // ONE query
            if err != nil { return err }
            attachComments(tasks, byTask)
        }
    }
    return nil
}
```

Four asides.

**The difference between a projection and an SQL injection is one map lookup.** Column names come from `views`, a constant the server owns. The moment a client-supplied string is interpolated into a `SELECT` list — even "validated" by a regex — you've handed over query construction. If you ever move from presets to arbitrary field selection, this allowlist is the part that must survive the change.

**Trimming after loading saves bytes, not work.** The version of this code that selects `*` and drops fields during serialization gets the transfer win and none of the I/O or serialization win — and it's the default behavior of most repository layers and ORMs, so it's what you get unless you deliberately do otherwise.

**Deduplicating ids before the batched fetch matters more than it looks.** Fifty tasks routinely share five assignees; `distinctAssigneeIDs` turns a 50-element `IN` list into a 5-element one, and it stops the response from repeating the same user object fifty times — which is where a surprising share of the original 1.4MB came from.

**There is no compression code here on purpose.** It belongs at the edge, and a handler that gzips independently will at best duplicate work and at worst produce a body that no longer matches the `ETag` computed upstream (7.4a). Confirm where it happens; don't add a second place.

## Further Reading

- **RFC 9110 §8.4 and §12.5.3** — `Content-Encoding`, `Accept-Encoding`, and how negotiation is meant to work.
- **RFC 7932 (Brotli)** and **RFC 8878 (Zstandard)** — mostly for the trade-off tables between compression level, speed, and ratio.
- **The BREACH disclosure** and OWASP's guidance on compression side channels — read before enabling compression on responses that mix secrets with reflected input.
- **Google AIP-157, _Partial responses_**, and `google.protobuf.FieldMask` — a fully designed field-selection mechanism, including the parts that are unpleasant. Useful as a reality check before building one.
- **JSON:API sparse fieldsets** — the other widely deployed convention, and worth comparing to field masks.
- **RFC 9113 (HTTP/2)** and **RFC 9114 (HTTP/3)**, particularly header compression and multiplexing — the basis for re-examining any round-trip-count argument written before 2018.
- **Module 6.4** for the N+1 that includes reintroduce, **Module 8** for what GraphQL does with the same problem, and **Module 13** for the caching that field fragmentation undermines.

A Java sibling would show something the Go version can't: with JPA, the natural path loads full entities and trims during serialization, so the byte win arrives and the work win doesn't — and getting the projection into the SQL requires constructor expressions or interface-based projections that many teams never reach for. The framework makes the ineffective version the default one, which is exactly the trap this article warns about, installed by the tooling rather than by the developer. Not yet written.

---

The habit to carry: before optimizing a response, decide which of the three costs you're paying. "The payload is too big" is not a diagnosis — it's three different problems wearing the same complaint, and the remedy that fixes one of them can leave the other two untouched while adding a parameter you'll support for years.
