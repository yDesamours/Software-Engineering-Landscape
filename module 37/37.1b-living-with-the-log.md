# Living With the Log: Event Versioning, Snapshots and Replay

_Module 37.1b — Event-Driven Architecture_

## The Problem

Suppose you run the gift-card ledger from 37.1a, two years later. The store holds about 120 million events across 14 million card streams, and it's worked well. Then, within one quarter, the business asks for four ordinary things, and each one turns out to be expensive.

**Multi-currency.** The chain expands to the UK, so amounts need a currency. A developer changes `Redeemed` from `amount` (euros, as a decimal) to `amountMinor` (a whole number of cents) plus `currency`, updates the code, and the tests pass. The deploy goes out. Jackson, asked to fill in a `long amountMinor` that isn't in an old event, quietly uses 0. So every redemption recorded before the change now folds as €0. Balances jump back to what they were before customers spent anything. It takes four hours to notice, and €31,000 is spent a second time. The tests passed because every test event was produced by the current code. No test contained an event shaped the way the old code wrote them.

**A new report.** Finance wants liability broken down by region. That's a new projection, which has to process all 120 million events from the start. The first attempt applies one event per transaction, at about 3,000 events per second: eleven hours.

**Rebuilding everything.** While moving the store to a new database cluster, the team resets every subscription to position zero and replays. One of those subscriptions sends "Your card has been loaded" emails. It sends 2.1 million of them, going back two years. The email provider suspends the account after a wave of spam complaints, and receipts for real purchases stop going out for a day. Meanwhile the existing liability report is empty for the eleven hours its rebuild takes, and it's month-end.

**Payroll cards.** Some corporate customers use reloadable cards for staff canteens: a weekly top-up and a redemption most days. Five years of that is about 3,000 events. A handful of fleet fuel cards have 40,000. Loading those streams takes up to 1.8 seconds, and they're loaded on every swipe.

2.4 named these as event sourcing's permanent costs: versioning, snapshotting, replay. This is what they look like when they arrive.

## What It Is

Keeping an event store healthy over years comes down to four disciplines:

- **Event versioning.** New code has to read every event old code ever wrote, because stored events are never migrated the way tables are.
- **Correcting history.** Mistakes in past events are fixed by appending new events, not by editing old ones.
- **Snapshots.** A saved copy of one aggregate's state at some version, so loading reads the snapshot plus the events after it instead of the whole stream.
- **Replay.** Running a projection from the beginning of the log to build a new read model, or rebuild a broken one, safely and fast enough.

Two distinctions matter throughout:

- **A snapshot is not a projection.** A snapshot is a private cache of one aggregate's state, used when handling commands. Deleting every snapshot must be safe, just slower. A projection is a read model other code queries.
- **Projections are not reactors.** A projection only writes its own read model, so running it twice produces the same tables. A **reactor** does something in the world: sends an email, calls an API, publishes to another service. Replaying a reactor repeats those effects. The email incident was a reactor treated as a projection.

## Recognizing the Problem

- Event classes are edited in place, and nobody can say which shapes older events actually have in the store.
- Missing fields quietly become zero, null or an empty string when events are read.
- Test fixtures are built by the current code, never loaded from stored examples.
- Someone has proposed an `UPDATE` on the events table.
- Rebuilding a projection means truncating it and waiting while it's empty.
- Nobody knows how long a full replay takes.
- One subscription framework runs read models and email senders alike, with the same reset button.
- Command latency depends on how old the customer's account is.
- Snapshots are written, but no one knows what happens to them when the aggregate's state class changes.

## How It Works

### Stored events are a schema you can't migrate

A table can be migrated: run `ALTER TABLE`, backfill, done. An event store's history is deliberately immutable, so every shape an event has ever had stays in the store, and the current code has to read all of them.

Changes fall into three kinds:

- **Additive, with an obvious meaning when absent.** A new optional field. Old events simply don't have it. Decide explicitly what "absent" means (a missing `channel` means `"till"`, because the website came later) and write that down in the reader, not in a default buried in a library.
- **Structural.** A rename, a unit change, one field split into two, two events merged. Old events have a different shape, and the current code shouldn't have to know about it. This calls for upcasting.
- **A change of meaning.** If `CardExpired` used to mean the balance was forfeited and a new law says expiry no longer forfeits it, that isn't a new version of the same event. It's a new event type (`CardDeactivated`), and old `CardExpired` events keep their old meaning. Reusing the name rewrites history silently.

There are five strategies, cheapest first:

- **Tolerant reader.** Ignore unknown fields and give absent ones a documented meaning. This covers additive changes, which are most changes.
- **Versioned types, handled side by side.** `Redeemed.v1` and `Redeemed.v2` are separate classes, and `evolve` handles both. It's honest, but domain code accumulates every historical shape forever.
- **Upcasting.** At the boundary where stored events are read, a chain of small functions turns each older version into the next one, v1 → v2 → v3, before the domain sees it. Domain code only ever knows the current shape. This is the default answer for structural changes. Two rules keep it safe:
  - An upcaster only looks at the raw event and its metadata. It must never look up current state, such as today's exchange rate or the store's current region, or the same event reads differently on different days.
  - Every version must be upcastable forever. You don't get to delete the v1 upcaster once v3 exists.
- **Copy and transform.** Write a new stream, or a new store, with the events transformed, then switch over. It's the only way to change stream boundaries, such as splitting one stream into several. It's a real migration with a cutover, so keep the original archived and treat this as a last resort.
- **Rewriting events in place.** Don't. The only legitimate case is legal erasure, covered below.

Internal events can evolve through upcasting because only your own code reads them. Events published to other services are a contract with readers you don't control, so their evolution follows different rules (37.2c). This is one strong reason not to publish internal events as they are.

Whatever the strategy, keep a **sample of every stored shape**: a JSON file per event type and version, taken from the real store, checked into the test suite. A test reads each sample through the upcasters and the strict deserializer. The multi-currency incident would have failed that test the moment the class changed.

### Correcting history: compensate, don't edit

Suppose a promotion bug loaded 3,100 cards with €500 instead of €50. The tempting fix is an `UPDATE` on those events. Don't. Append a correction:

```
v1 CardIssued
v2 Loaded        { amountMinor: 50000 }   ← the bug
v3 LoadCorrected { amountMinor: -45000, reason: "PROMO-212 overload", causation: "INC-4471" }
```

The balance is right from v3 onward, and the history now tells the true story: what happened, when it was noticed, and what was done about it. Projections apply `LoadCorrected` like any other event. Reports as of a date before the correction still show what the business believed then, which is exactly what an auditor wants to see.

This is also how accounting ledgers work, and for the same reason.

### Snapshots

A snapshot stores an aggregate's state at a stream version. Loading reads the latest snapshot, then only the events after it:

```
without:  read v1 ─────────────────────────────── v3,000   fold 3,000 events
with:     snapshot @ v2,800 ─► read v2,801 … v3,000       fold 200 events
```

What makes snapshots safe:

- **Measure first.** Most gift cards have around six events, and folding six events costs nothing. Snapshots are for the long tail: here, the payroll and fuel cards. A rough threshold is a few hundred events, or when stream load time shows up in the latency budget.
- **Take them off the command path.** A subscription watches stream versions and writes a snapshot when a stream has grown, say, 200 events since the last one. Commands never wait for a snapshot to be written.
- **Treat them as a cache, never as truth.** When the state's shape changes, don't upcast old snapshots. Discard them, and let loading fall back to the full stream until a new snapshot is written.
- **Invalidate them when the fold changes, not just when the state class changes.** A snapshot bakes in the result of every `evolve` call up to its version. Fix a bug in `evolve`, and every old snapshot still carries the buggy result, while fresh loads don't. Two cards with identical histories then have different balances. Stamp each snapshot with a state version that changes whenever the state class or `evolve` changes, and ignore snapshots from other versions.

The alternative to snapshotting a long stream is to make it stop being long. **Closing the books**: at year end, append `PeriodClosed { balance }` to the card's stream, then start a new stream, `giftcard-7F3K2-2027`, whose first event is `BalanceBroughtForward`. Old streams become read-only and can be archived. It changes stream identity, so something has to point from the card to its current stream, but for streams that grow without end, it's cleaner than snapshots forever.

### Replay and rebuilding projections

Projections get rebuilt for four reasons: a new read model, a bug fixed in an existing one, a change to a read model's schema, and moving the store. Each rebuild is a catch-up subscription starting from position zero (37.1a). How you run it decides whether it's routine or an outage.

**Build alongside, then switch.** Don't truncate the live read model. Build version 2 into new tables while version 1 keeps serving. When version 2 has caught up, meaning its lag is near zero, switch reads to it (a view, an alias or a config flag), and drop version 1 later.

```
events ─┬─► liability_v1 ──► serving reads        (keeps running)
        └─► liability_v2 ──► catching up from 0
                                   │  lag ≈ 0
                                   ▼
                           switch reads to v2, retire v1
```

**Make it fast enough to be routine.** Arithmetic first: 120 million events at 3,000 per second is 11 hours. Most of that time is per-event overhead: one transaction and one round trip per event. Applying events in batches of a few thousand per transaction, writing with bulk inserts or upserts, and creating secondary indexes after the load commonly gets that rebuild to 30,000–50,000 events per second, well under an hour. A projection whose output is per stream (per card, per region) can also be split into several workers by hashing the stream ID, with each worker keeping its own checkpoint.

**Never replay a reactor.** Reactors start from "now" when they're created, and their checkpoints are left alone by rebuilds and store migrations. Make that a property of the code, not a note on a runbook: the rebuild tool should only accept projections. Idempotency keys derived from the event ID (37.2a, 17.1) are the second line of defense, so that an accidental replay is rejected by the email provider instead of reaching customers.

**Keep projections deterministic.** A projection that joins today's store table to find a redemption's region will put a store that moved regions last month in the wrong region for every historical redemption on the next rebuild. Put the facts a projection needs into the event when it's written (the redemption carries its store's region), or join reference data by date, as it was when the event happened.

**Replay is also the versioning test.** A full rebuild reads every event the store has. If any stored shape can't be read, the rebuild finds it. Run one regularly in a staging environment, before an incident forces one in production.

**Answering "as of" questions.** "Liability on 31 December" is a replay that stops at that date, or a projection that keeps validity ranges. Filter by `occurredAt` or `recordedAt` deliberately (37.1a): one answers "what was true on the day," the other "what we knew on the day." Finance usually wants the first, auditors sometimes the second.

### Streams over time: archiving and erasure

- **Archiving.** Streams that are closed (books closed, cards expired and settled) can move to cheaper storage. On Postgres, partition the events table by recorded month and move or export old partitions. KurrentDB, since version 25, can move completed data files to object storage and read them back transparently when needed.
- **Retention.** Some streams can be deleted outright when their legal retention period ends. Decide that by stream category, and write it down.
- **Erasure.** Personal data inside immutable events is handled by encrypting it with a per-person key and destroying the key on request, so the events remain but that data becomes unreadable. That's **crypto-shredding** (2.4, 34.1a). Keep personal data out of events where possible, and reference the person by ID instead.

## When It's Appropriate

- **Upcasting** the first time a change is structural rather than additive: a rename, a unit change, a split. Doing it before then is premature.
- **Samples of stored shapes in tests** from the first production event. It's cheap, and it's the only reliable defense against the multi-currency incident.
- **Separating projections from reactors** before the first rebuild, move or reset, which is to say from the start.
- **Build-alongside rebuilds** once a rebuild takes longer than anyone would accept a report being empty. At the gift-card scale, that's hours, not minutes.
- **Snapshots** when a measured subset of streams has hundreds of events or more and their load time matters: the payroll and fuel cards, not the typical card.
- **Closing the books** when streams grow without end by design, and the business already thinks in periods, such as accounts, ledgers and subscriptions.

## When It's Unnecessary or Overkill

- **An upcasting framework before the first structural change.** A tolerant reader covers additive changes.
- **Snapshots on short streams.** A snapshot for a six-event stream costs more to write and invalidate than the fold it saves. Snapshotting everything is a common way to add a cache-invalidation bug for no gain.
- **Build-alongside rebuilds of small projections.** If a rebuild takes four minutes, truncate and rebuild during a quiet hour.
- **Copy and transform for a field rename.** An upcaster is one small function. A migration is a project.
- **Parallel replay before batching.** Batching usually gets most of the speedup with none of the coordination.

## Trade-offs

- **Upcasters accumulate forever.** Each is small, but the chain only grows, and every read of an old event pays for its transformations.
- **Snapshots add an invalidation problem.** A snapshot that should have been discarded and wasn't produces state that exists nowhere in the events. It's the hardest kind of bug to find, because re-reading the events looks correct.
- **Rebuild time grows with history.** A rebuild that takes an hour this year takes two in three years. Replay speed is a capacity plan, not a one-off optimization.
- **Build-alongside doubles storage and write load** for the rebuild's duration, on the same database that's serving traffic.
- **The projection/reactor split is a discipline.** One reactor registered as a projection brings back the email incident.
- **Closing the books adds indirection:** a pointer to the current stream, and "the card's history" now spans several streams.
- **Correcting instead of editing** means projections, reports and support tools all have to understand correction events, including ones added years after the mistakes they fix.

## Alternatives

- **Weak schema only.** Some teams never upcast. They store events as loosely typed documents, read them tolerantly, and handle old shapes in code where needed. It works for small systems, and gets messy as the variations pile up.
- **A schema registry with compatibility checks** (Avro or Protobuf with Confluent Schema Registry, for example). CI refuses an incompatible event change before it ships. It fits published events best (37.2c), and it can guard internal ones too.
- **Keep aggregates in memory instead of snapshotting.** Actor frameworks such as Akka and Orleans keep an active aggregate loaded between commands, so a long stream is read once per activation rather than once per command. They usually pair this with snapshots for cold starts.
- **Recompute reports in a warehouse.** Export events to a warehouse and compute reports with SQL. A "rebuild" is then a query, and the warehouse's scale does the work (16.4).
- **Store state normally.** If versioning and replay are costing more than the history is worth, 2.4's alternatives are still there. Moving an aggregate off event sourcing is a legitimate decision.

## How to Achieve It

1. **From the first event:** type names with versions, tolerant reading with written-down meanings for absent fields, strict deserialization for required ones, and stored samples of each shape in tests. Projections and reactors registered separately.
2. **At the first structural change:** add an upcaster pipeline at the read boundary, and a sample of the new shape. _Next when:_ a rebuild takes longer than a report can be empty.
3. **Rebuild alongside:** new tables, catch up, switch, retire. Batch the replay. Record events per second, so the next rebuild's duration is a number rather than a guess. _Next when:_ some streams' load time shows up in command latency.
4. **Snapshots for the long streams only,** written by a subscription and stamped with a state version. Consider closing the books instead where the business already thinks in periods. _Next when:_ storage, backup time or restore time starts to hurt.
5. **Archive closed streams,** and decide retention per category.

## Implementation

Java 21, with Jackson. Sealed interfaces and records give the same exhaustive `switch` over events that 2.4 showed in TypeScript. Jackson's tree model is where upcasting naturally goes, and its lenient defaults are what caused the multi-currency incident.

### Upcasting at the read boundary

```java
sealed interface GiftCardEvent permits Issued, Loaded, Redeemed, LoadCorrected, Frozen {}
record Redeemed(long amountMinor, String currency, String storeId, String region)
        implements GiftCardEvent {}

interface Upcaster {
    String type();      // "GiftCardRedeemed"
    int fromVersion();  // turns this version into fromVersion + 1
    ObjectNode apply(ObjectNode data, EventMetadata meta);
}

final class RedeemedV1ToV2 implements Upcaster {
    public String type() { return "GiftCardRedeemed"; }
    public int fromVersion() { return 1; }

    public ObjectNode apply(ObjectNode d, EventMetadata meta) {
        BigDecimal euros = d.remove("amount").decimalValue();
        d.put("amountMinor", euros.movePointRight(2).longValueExact());
        d.put("currency", "EUR"); // every v1 event predates the UK launch
        return d;
    }
}

final class EventReader {
    private final Map<String, Upcaster> chain; // keyed by type + ":" + fromVersion
    private final ObjectMapper strict = JsonMapper.builder()
        .enable(DeserializationFeature.FAIL_ON_MISSING_CREATOR_PROPERTIES)
        .enable(DeserializationFeature.FAIL_ON_NULL_FOR_PRIMITIVES)
        .build();

    GiftCardEvent read(StoredEvent e) {
        ObjectNode data = e.data().deepCopy();
        int version = e.schemaVersion();
        for (Upcaster u; (u = chain.get(e.type() + ":" + version)) != null; version++) {
            data = u.apply(data, e.metadata());
        }
        return strict.treeToValue(data, classFor(e.type(), version));
    }
}
```

The strict mapper is the other half of the fix. Upcasting handles the shapes you know about. `FAIL_ON_MISSING_CREATOR_PROPERTIES` turns a shape you forgot into an exception at load time, instead of a balance that's quietly wrong. Failing to load one card is an incident. Loading 14 million cards wrongly is a bigger one.

The v2 → v3 upcaster that added `region` couldn't look up each store's current region, for the determinism reason from How It Works. It reads a dated store-to-region table as of the event's `occurredAt`, which is metadata, not current state.

Each file in `src/test/resources/events/` is a real stored event, one per type and version (`GiftCardRedeemed.v1.json`, `.v2.json`...). A parameterized test runs every one through `EventReader.read`. Adding a version without a sample, or changing a record so an old sample no longer reads, fails the build.

### Loading with snapshots

```java
static final int STATE_VERSION = 7; // bump when GiftCardState OR evolve() changes

Loaded<GiftCardState> load(String streamId) {
    Optional<Snapshot> snap = snapshots.latest(streamId)
        .filter(s -> s.stateVersion() == STATE_VERSION); // other versions are ignored

    GiftCardState state = snap.map(s -> s.state(GiftCardState.class))
                              .orElse(GiftCardState.EMPTY);
    long version = snap.map(Snapshot::streamVersion).orElse(0L);

    for (StoredEvent e : store.read(streamId, version + 1)) {
        state = GiftCardState.evolve(state, reader.read(e));
        version = e.streamVersion();
    }
    return new Loaded<>(state, version); // version is the expected version for append
}
```

That last line replaces 37.1a's `history.length`, which stopped being the stream version once loading could start partway through.

The command handler's check for an already-processed command ID (37.1a) also needs a fix here. It used to scan the whole history, and now it only sees events after the snapshot. Keep recent command IDs in the state itself (the last 50, say), or look them up in the store by metadata. A snapshot shouldn't make an old retry look new.

### Projections, reactors, and a rebuild that only accepts one of them

```java
sealed interface Subscriber permits Projection, Reactor {}

// Writes only its own tables, inside the transaction it's given. Safe to replay.
non-sealed interface Projection extends Subscriber {
    String name();
    void apply(Tx tx, GiftCardEvent event, EventMetadata meta);
}

// Acts on the world. Starts from "now", and is never replayed.
non-sealed interface Reactor extends Subscriber {
    void react(GiftCardEvent event, EventMetadata meta);
}

final class Rebuilder {
    // Takes a Projection, not a Subscriber: a reactor can't be passed in.
    void rebuild(Projection p, String targetSchema) {
        db.createSchemaLike(p.name(), targetSchema);         // e.g. liability_v2
        subscriptions.catchUpFromZero(p, targetSchema, 5_000); // 5,000 events per transaction
        awaitLagBelow(p, targetSchema, Duration.ofSeconds(2));
        db.repointView(p.name(), targetSchema);              // reads switch here
        // retire the old schema after a day of watching
    }
}
```

The parameter type does the same job `pgx.Tx` did in 37.2a: the mistake can't compile. The migration that sent 2.1 million emails reset every subscription in a list. With this split, "every subscription" isn't a list that exists.

`repointView` is the whole switch because readers query a view, never the underlying tables directly. That's a small decision made on day one that makes every later rebuild a non-event.

## Further Reading

- **Greg Young, _Versioning in an Event Sourced System_** (Leanpub, free). The source for the strategies above, including weak schema, upcasting and copy-and-transform, and the reasons to avoid rewriting in place. Read it before the first structural change.
- **Michiel Overeem, Marten Spoor and Slinger Jansen, "The Dark Side of Event Sourcing: Managing Data Conversion"** (SANER 2017), and **Overeem et al., "An Empirical Characterization of Event Sourced Systems and Their Schema Evolution — Lessons from Industry"** (_Journal of Systems and Software_, 2021). Research on how teams actually handle this, and which approaches hurt later.
- **Axon Framework reference guide, "Event Upcasting."** A mature upcaster chain on an intermediate representation, much like the one above.
- **Marten documentation:** event versioning and upcasting, and rebuilding projections with the async daemon.
- **Mathias Verraes, "Forgettable Payloads" and "Crypto-Shredding"** (verraes.net, 2019). Two short patterns for personal data in immutable logs.
- **Martin Fowler, "Tolerant Reader"** (martinfowler.com). The reading side of additive change, in two pages.
- **Oskar Dudycz, event-driven.io.** Practical posts on event schema versioning, and on why snapshots are often added before they're needed.
- **Kurrent documentation:** archiving (KurrentDB 25.0 and later) and scavenging.
- **Jackson documentation: `DeserializationFeature`.** Worth reading once in full, to see what your deserializer does silently by default.
- **In this collection:** 2.4 (the costs named up front), 33.1a (the compatibility contract, for APIs), 34.1a (erasure obligations), 37.1a (the store this builds on), 37.2a (idempotency for reactors), 37.2c (versioning published events), 16.4 (warehouses).

A **Go** sibling would be worth writing for the replay half. A partitioned rebuild, with workers split by stream hash, each keeping its own checkpoint and writing batches, is where Go's goroutines and channels make the shape of the work visible: bounded parallelism, backpressure between reading and writing, and exactly where per-stream ordering is kept. It would also show the other thing Go changes. With no sealed types, the "projections only" rule in `Rebuilder` becomes a convention checked by tests rather than by the compiler. Not yet written.

---

State-based systems forget their past and pay for it once. Event-sourced systems remember it and pay for that every year. Every habit in this article is a way of keeping that yearly cost predictable: no event nobody can read, no rebuild nobody has timed, and no replay that reaches a customer.
