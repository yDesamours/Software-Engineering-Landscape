# Publishing Reliably: The Dual Write, the Transactional Outbox and the Idempotent Consumer

_Module 37.2a — Event-Driven Architecture_

## The Problem

Suppose you run a ticketing platform for concerts and theatre. When someone buys seats, the `orders` service records the purchase in Postgres. Four other services then need to react:

- **tickets** issues QR codes and emails them to the buyer
- **seat-map** marks the seats as sold in the read model buyers browse
- **loyalty** credits points
- **finance** posts the sale to the ledger

The team connects them through Kafka. `orders` publishes `TicketsPurchased`, and the other four consume it. The first version publishes inside the transaction:

```go
tx := db.Begin()
insertOrder(tx, order)
producer.Publish("tickets.purchased", event)
tx.Commit()
```

**Incident one: tickets for seats nobody bought.** During a big on-sale, two buyers race for the same seats. The database runs these transactions as `SERIALIZABLE`, so one of them fails at commit with a serialization error. By then its event has already been published. `tickets` emails a perfectly valid QR code to a buyer whose order never existed. At the venue, 37 pairs of people hold tickets for the same seat.

The team moves the publish after the commit:

```go
tx.Commit()
producer.Publish("tickets.purchased", event)
```

**Incident two: paid orders with no tickets.** About 0.03% of orders, roughly 310 a month, now commit and never produce an event. The losses cluster in two places. Deploys: Kubernetes kills a pod after its grace period, sometimes between the commit and the publish. And one 40-second Kafka leader election, during which `Publish` returned an error that the handler logged before returning `200`, because the order was already committed and nothing else seemed possible. Support gets a "resend tickets" button. Finance starts a weekly reconciliation because the ledger is short by those same orders.

The team adds retries: if the publish fails, retry with backoff for up to a minute.

**Incident three: double points.** A publish times out, but the broker had actually written the message and only the acknowledgement was lost. The retry writes it again. `loyalty` credits points twice for 1,900 orders in one week. Meanwhile the retries live in the pod's memory, so a deploy still loses them.

Three fixes, and each moved the failure somewhere else. Two systems that share no transaction can't be updated atomically by ordering the calls cleverly:

```
  publish ──► commit                 commit ──► publish
       crash or abort here               crash here
              │                              │
              ▼                              ▼
     event, but no order              order, but no event
       (phantom ticket)                (paid, no ticket)

  retry the publish ──► ack lost, broker already has it ──► duplicate
```

## What It Is

This is the **dual-write problem**: one logical change has to land in two systems that share no transaction, and every ordering of the two writes leaves a window where a crash, timeout or rollback makes them disagree.

The standard fix is the **transactional outbox**. The service doesn't publish during the request at all. It writes the event as a row in an `outbox` table in its own database, in the same transaction as the business change. A separate **relay** reads committed outbox rows and publishes them, retrying until the broker acknowledges each one. The event exists if and only if the change committed, because both are one commit.

Retrying until acknowledged means some events are delivered more than once, so the outbox needs a partner on the receiving side: the **idempotent consumer**. The consumer records which events it has already applied, in the same transaction as the effect, and skips an event it has seen. Delivery is at-least-once; the effect happens once. People call the combination "effectively once," which is the only kind of exactly-once available across two systems.

Three neighbors get confused with this:

- **Event sourcing** (2.4, 37.1a) isn't an outbox. In an outbox design, the tables are the truth and events are notifications about changes to them. In event sourcing, the events are the truth. Event sourcing avoids the dual write for a simple reason: there is only one write.
- **Change data capture** (38.4) is one way to build the relay, by reading the database's write-ahead log. Pointed at your business tables instead of an outbox, CDC publishes your schema rather than your intent: it can say `status` went from 2 to 3, not that the buyer requested a refund.
- **Kafka's exactly-once semantics** make a read-process-write cycle within Kafka atomic. Your Postgres commit can't join that transaction, so it doesn't solve this problem.

## Recognizing the Problem

- A function commits to the database and then calls a broker, an HTTP API or an email provider, or does it the other way round.
- Downstream systems sometimes act on records that don't exist in the source.
- Records exist that downstream never heard about, and the gaps cluster around deploys, broker failovers or network trouble.
- There's an admin button or script to "resend" or "replay" events for a specific record.
- A reconciliation job exists because two systems drift apart.
- A `catch` around a publish logs the error and carries on.
- Consumers occasionally process the same event twice, and nobody can say why.
- Someone proposed wrapping the publish in retries, and duplicates appeared.

## How It Works

The whole flow:

```
┌─────────────── orders service ───────────────┐
│  one transaction                              │
│  ┌──────────┐   ┌──────────┐                  │
│  │ orders   │   │ outbox   │ ◄── same commit  │
│  └──────────┘   └────┬─────┘                  │
└──────────────────────┼────────────────────────┘
                       │ relay reads committed rows,
                       │ publishes, waits for ack,
                       │ marks published
                       ▼
                 ┌───────────┐  key = order id
                 │   Kafka   │  (one partition per order)
                 └─────┬─────┘
          ┌────────────┼─────────────┐
          ▼            ▼             ▼
      tickets       loyalty       finance
   inbox + effect  inbox + effect  inbox + effect
   in one txn      in one txn      in one txn
```

### What goes in the outbox row

- **An integration event, not the domain object.** Serialize a deliberate, versioned contract (`tickets.purchased.v1`), not the `Order` struct. The struct will change for internal reasons; consumers shouldn't break when it does.
- **The data as of the write.** Capture the payload inside the transaction. A relay that stores only an order ID and reads the order at publish time sends whatever the order looks like then, which may be two changes later.
- **An event ID generated by the producer.** A UUID assigned once, when the row is written, survives every retry unchanged. It's what consumers deduplicate on. An ID assigned by the relay or the broker changes on retry and makes deduplication impossible.
- **The aggregate ID and its version.** The ID becomes the partition key, so all events for one order stay in order. The version lets consumers detect gaps and ignore stale events.
- **Context as data.** The W3C `traceparent` header so the trace continues across the broker (19.2b). The tenant. The actor who caused the change, recorded as a fact about the event, not as a credential the consumer can act with (36.1b makes this distinction for service calls).

### Two ways to read the outbox

| | Polling publisher | Log tailing (CDC) |
|---|---|---|
| **How** | Query unpublished rows every N ms, publish, mark published | Read the write-ahead log (Debezium, or Postgres logical decoding), publish inserts to the outbox table |
| **Latency** | Poll interval, typically 50–500 ms | Tens of milliseconds |
| **Order** | Order of the query, with a trap (next section) | Commit order, from the log itself |
| **Load** | Queries plus an update per row on the primary | A replication slot. No queries, no updates |
| **Operations** | A loop in your service | A connector cluster, and a slot that fills the disk if the connector stops |
| **Cleanup** | Delete published rows later | Delete rows right after insert, or skip the table: Postgres's `pg_logical_emit_message` writes the event straight to the log |

Polling is where almost everyone should start. It's a loop you can read and debug. Move to log tailing when polling load or latency actually hurts, not in advance.

### The trap in `WHERE id > last_published`

The obvious polling query keeps a cursor and asks for rows with a higher ID. It loses events.

Sequence values are handed out when a row is inserted, but rows become visible when their transaction commits, and those two orders differ:

```
txn A: insert outbox id=100 ───────────── (slow) ───────────── commit
txn B:           insert outbox id=101 ── commit
relay:                                       reads id > 99 → sees 101
                                             publishes 101, cursor = 101
relay:                                                              reads id > 101
                                                                    → 100 is never seen
```

Three ways around it:

- **Track state per row.** Select rows `WHERE published_at IS NULL`, with a partial index so the query stays cheap. A row that commits late is simply picked up on the next poll.
- **Only read below the oldest open transaction.** Postgres can report the oldest transaction still in progress (`pg_snapshot_xmin(pg_current_snapshot())`). Rows written by transactions older than that can no longer be joined by late ones. This keeps a cheap cursor, at the cost of subtle code.
- **Read the log.** CDC sees commits in commit order, so the problem doesn't arise.

### Order per key, never global

Consumers need events for one order in order: `TicketsPurchased` before `TicketsRefunded`. They almost never need a global order across unrelated orders, and nothing in this pipeline could provide one cheaply.

Per-key order holds in the database for a structural reason: every transaction that emits an event for an order also updates that order's row, and row locks serialize those transactions. So the order's events are inserted, and commit, in version order.

The relay is where that order is easiest to lose:

- **Several relays taking rows with `FOR UPDATE SKIP LOCKED`** looks like free scaling. It isn't. Relay A takes version 1 of order 7, relay B takes version 2, and B publishes first. Skip-locked batching suits a job queue (Module 10), where rows are independent, not an ordered event stream.
- **One active relay** is enough for thousands of events per second. A Postgres advisory lock makes a second instance a warm standby.
- **Partitioned relays** hash the aggregate ID into N buckets with one relay per bucket, once one relay truly isn't enough.
- **On the broker,** key each message by aggregate ID so all its events land on one partition. Kafka's idempotent producer (on by default since 3.0) keeps retries from reordering messages within a partition.

### Delivery is at-least-once, so consumers must be idempotent

Duplicates aren't an edge case. They're guaranteed, from several sources:

- The relay crashes after the broker acknowledges but before it marks the row published, and publishes again after restart.
- A consumer applies the effect and crashes before committing its offset, and gets the message again.
- A consumer group rebalances mid-batch.
- Someone replays a topic to rebuild a read model.

Three consumer strategies, by what the effect is:

- **An inbox table.** Insert the event ID into `inbox` and apply the effect in one transaction. If the insert conflicts, the event was already applied: skip it and acknowledge. This works for any effect in the consumer's own database.
- **Effects that are naturally idempotent.** Write "points from order 812 = 40" with a unique key on the source, not "add 40 points." Update a read model with `WHERE version < $new` so a duplicate or stale event changes nothing. That version check also absorbs reordering, which an inbox alone doesn't.
- **Effects outside your database.** An email or a card charge can't join your transaction. Pass an idempotency key derived from the event ID to the provider (17.1), so a second call is recognized there. If the provider doesn't support one, record "about to send" before acting and accept that a crash in that gap can still produce one duplicate or one missing send. Decide which is worse.

A consumer that emits events of its own uses an outbox too. The pattern chains: inbox in, outbox out, at every hop.

### Keeping it healthy

- **The one alert that matters is the age of the oldest unpublished row.** Relay throughput can look fine while one row has been stuck for an hour.
- **Poison events.** An event the broker rejects forever (too large, say) stops the relay if the relay stops on errors, and preserving order means it should. After a few attempts, park the row, page someone, and skip only that aggregate's later events. Parking silently breaks per-key order for that aggregate.
- **Cleanup.** Delete published rows after a few days, or partition the table by day and drop old partitions. An outbox table that grows forever becomes the slowest table in the database, and in Postgres a steady stream of inserts, updates and deletes needs vacuum keeping up.
- **Latency.** If the poll interval is too slow for users, issue a `NOTIFY` in the same transaction as the insert. Postgres delivers it only after commit, so the relay wakes immediately and still polls periodically as a safety net.

## When It's Appropriate

- **Losing the message leaves the system wrong.** Paid orders need tickets, sales need ledger entries, cancellations need seats released. Even 0.03% is hundreds of customers a month, each one a support ticket, and a reconciliation job that has to exist forever.
- **Several independent services react to one change.** Four consumers of `TicketsPurchased` means the producer can't call them one by one in the request without inheriting all their failure modes (36.3a).
- **A change feeds a derived store in another system.** A search index, a cache or an analytics warehouse has to reflect every committed order, not most of them.
- **The request can't wait for downstream work.** A checkout that returns in 200 ms shouldn't block on email, loyalty and finance. It commits one transaction and returns.
- **Moderate volume.** A single polling relay comfortably handles hundreds to low thousands of events per second on ordinary Postgres, which covers most products.

## When It's Unnecessary or Overkill

- **The "consumer" lives in the same database.** In a monolith, write the ledger row and the loyalty row in the same transaction as the order. If the work should happen later, a jobs table processed by a worker (Module 10) is a local outbox already, without a broker.
- **Loss is acceptable.** Analytics events can run a fraction of a percent low (16.1a). Live UI updates are recoverable when clients detect gaps and resync (9.4). Neither needs this machinery.
- **Low volume with reconciliation you need anyway.** Twenty invoices a day, sent by a nightly job that compares "should have been sent" with "was sent," is simpler than an outbox and just as correct.
- **The aggregate is about to become event-sourced.** Then the event store's subscriptions do this job (37.1a).
- **Events nobody consumes.** An outbox makes publishing cheap and reliable, and teams respond by publishing every `UPDATE`. Each event type is a contract you now maintain. Publish what a consumer needs.

## Trade-offs

- **Every write gets heavier.** Each business transaction inserts an extra row with a JSON payload, then the relay updates it and something deletes it. On a hot table, that write amplification is measurable.
- **A new process to run.** The relay needs deploying, monitoring, alerting and an owner. When it stops, nothing fails loudly: events quietly pile up.
- **Latency.** Downstream sees changes after the poll interval plus broker time. Anything that must be visible in the same request can't go through this path.
- **Duplicates are pushed to every consumer.** Each consumer carries an inbox or idempotent effects, and one careless consumer reintroduces incident three.
- **Order limits parallelism.** Keeping per-key order means one relay, or a partitioning scheme, and a poison event can stall a key or the whole stream.
- **It only covers one database.** The outbox works because it shares a transaction with the business change. A change spread across two databases is still a distributed transaction, which is a saga (37.4a).
- **Events become a schema.** Consumers depend on payload shape, and changing it needs the same care as an API change (33.1a).

## Alternatives

- **One transaction in a monolith.** If the reactions can live in one database, do them in one transaction. This is the strongest option whenever it's available.
- **Listen to yourself.** Publish the event first, and have the service consume its own event to update its database. There's only one write, to the broker. But the service's own state now lags its own requests (read-your-writes breaks), and it can't reject an invalid order after announcing it, so validation has to happen before publishing, against state that may be stale.
- **Two-phase commit (XA).** A distributed transaction across the database and broker. Kafka and most modern brokers don't take part, and where it's available it adds a coordinator whose failures can leave locks held.
- **CDC on business tables.** No outbox, no application change. You get row changes without intent, and consumers couple to your table layout.
- **Event sourcing.** The log is the store, so there's nothing to keep in sync (37.1a). Adopt it for the history, not to avoid an outbox.
- **Best effort plus reconciliation.** Publish after commit, accept rare loss, run a sweep that finds and republishes gaps. Honest and sometimes enough, as long as the sweep genuinely exists and someone watches it.
- **Durable execution engines** such as Temporal, which persist each step of a workflow and retry it (37.4b). They solve a larger problem, and include this one.
- **An outbox you don't write yourself.** Spring Modulith's event publication registry, MassTransit and NServiceBus outboxes in .NET, Watermill's forwarder in Go, and Debezium's outbox event router all implement the pattern. You still need to understand ordering, duplicates and cleanup, but you don't write the loop.

## How to Achieve It

1. **List your dual writes.** Search for functions that commit and then call a broker, an HTTP API, a mailer or a cache. For each, ask what happens if the process dies between the two calls. Most answers will be "nothing much." Keep the ones where the answer is money, access or a customer promise.
2. **Outbox one critical event.** Add the table, write `TicketsPurchased` into it in the business transaction, and run a single polling relay with an advisory lock. Keep the old direct publish disabled rather than deleted until the relay has run cleanly for a while. _Next when:_ the relay is healthy and you trust it.
3. **Make the consumers idempotent.** Add inboxes or idempotent effects before anyone relies on the new path, because duplicates start on day one. _Next when:_ every consumer of the event has been tested against a deliberately duplicated and reordered stream.
4. **Operate it.** An alert on oldest-unpublished age, parking with a page for poison events, and cleanup of published rows. _Next when:_ the outbox is proven and other teams want the same guarantee.
5. **Move the rest across, and scale only if needed.** Migrate other critical events one by one. If relay load or latency starts to hurt, partition the relay by key, or move to log tailing with Debezium (38.4). Many systems never need this step.

## Implementation

Go, with pgx. Go passes the transaction around as an explicit value, so "written in the same transaction" is something you can see in a function signature rather than something a framework arranges out of sight.

### The table

```sql
CREATE TABLE outbox (
  id                bigserial   PRIMARY KEY,
  event_id          uuid        NOT NULL UNIQUE,
  aggregate_type    text        NOT NULL,
  aggregate_id      text        NOT NULL,
  aggregate_version bigint      NOT NULL,
  event_type        text        NOT NULL,   -- 'tickets.purchased.v1'
  payload           jsonb       NOT NULL,
  headers           jsonb       NOT NULL DEFAULT '{}',  -- traceparent, tenant, actor
  created_at        timestamptz NOT NULL DEFAULT now(),
  published_at      timestamptz,
  attempts          int         NOT NULL DEFAULT 0,
  last_error        text
);

-- Keeps the relay's query cheap no matter how many published rows remain.
CREATE INDEX outbox_pending ON outbox (id) WHERE published_at IS NULL;
```

### Writing the event with the change

```go
func (s *Orders) Purchase(ctx context.Context, cmd PurchaseCmd) (string, error) {
	tx, err := s.db.Begin(ctx)
	if err != nil {
		return "", err
	}
	defer tx.Rollback(ctx) // no-op once committed

	order, err := reserveSeats(ctx, tx, cmd) // inserts the order, bumps its version
	if err != nil {
		return "", err
	}

	evt := TicketsPurchasedV1{
		OrderID: order.ID, ShowID: order.ShowID, Seats: order.Seats,
		BuyerID: cmd.BuyerID, AmountMinor: order.TotalMinor, Currency: order.Currency,
	}
	if err := appendOutbox(ctx, tx, "order", order.ID, order.Version,
		"tickets.purchased.v1", evt, headersFrom(ctx)); err != nil {
		return "", err
	}
	return order.ID, tx.Commit(ctx) // order and event: both or neither
}

// Takes pgx.Tx, not the pool. Nothing can call this outside a transaction.
func appendOutbox(ctx context.Context, tx pgx.Tx, aggType, aggID string, version int64,
	eventType string, payload any, headers map[string]string) error {

	body, err := json.Marshal(payload) // the data as of now, not as of publish time
	if err != nil {
		return err
	}
	hdr, _ := json.Marshal(headers)
	_, err = tx.Exec(ctx, `
		INSERT INTO outbox (event_id, aggregate_type, aggregate_id, aggregate_version,
		                    event_type, payload, headers)
		VALUES ($1, $2, $3, $4, $5, $6, $7)`,
		uuid.New(), aggType, aggID, version, eventType, body, hdr)
	return err
}
```

The parameter type is the design. A shared interface that both `pgx.Tx` and the pool satisfy would be more convenient, and it would also let someone call `appendOutbox` with the pool, commit the event on its own, and bring back incident one. Keep the parameter narrow.

`headersFrom(ctx)` injects the current trace context through OpenTelemetry's propagator and adds the tenant and acting user. Without it, every consumer's trace starts from nothing, and "why did this ticket email go out late?" has no trace to follow.

### The relay

```go
// Run by one instance at a time; the others wait on pg_try_advisory_lock.
// Per-order ordering depends on that.
func (r *Relay) publishBatch(ctx context.Context) (int, error) {
	rows, err := r.db.Query(ctx, `
		SELECT id, event_id, aggregate_id, event_type, payload, headers
		FROM outbox
		WHERE published_at IS NULL AND attempts < $1
		ORDER BY id
		LIMIT 200`, maxAttempts)
	if err != nil {
		return 0, err
	}
	batch, err := pgx.CollectRows(rows, pgx.RowToStructByPos[outboxRow])
	if err != nil {
		return 0, err
	}

	for i, m := range batch {
		err := r.pub.Publish(ctx, Message{ // waits for the broker's ack (acks=all)
			Topic: topicFor(m.EventType), Key: m.AggregateID,
			ID: m.EventID, Value: m.Payload, Headers: m.Headers,
		})
		if err != nil {
			r.db.Exec(ctx, `UPDATE outbox SET attempts = attempts + 1, last_error = $2
			                WHERE id = $1`, m.ID, err.Error())
			return i, err // stop: later events must not overtake this one
		}
		// A crash right here publishes m again after restart. That's the
		// at-least-once guarantee, and why every consumer deduplicates.
		if _, err := r.db.Exec(ctx,
			`UPDATE outbox SET published_at = now() WHERE id = $1`, m.ID); err != nil {
			return i, err
		}
	}
	return len(batch), nil
}
```

Three details carry the correctness:

- **`published_at IS NULL`, not `id > cursor`.** A row whose transaction commits late is picked up next time instead of skipped forever.
- **`Publish` must block until the broker acknowledges.** Most Kafka clients default to an asynchronous producer that returns before the write is durable. Marking the row published before the acknowledgement arrives recreates incident two, just more rarely.
- **Stopping on the first error preserves order and makes one bad event stall everything.** The `attempts < $1` condition eventually parks the row so the stream moves on. At that point per-key order for that one order is broken, so parking has to page someone. A refinement is to skip only rows whose `aggregate_id` matches a parked row.

### An idempotent consumer

```go
func (h *Loyalty) Handle(ctx context.Context, m Message) error {
	var evt TicketsPurchasedV1
	if err := json.Unmarshal(m.Value, &evt); err != nil {
		return Permanent(err) // dead-letter it; retrying won't fix a bad payload
	}

	return pgx.BeginFunc(ctx, h.db, func(tx pgx.Tx) error {
		tag, err := tx.Exec(ctx, `
			INSERT INTO inbox (consumer, event_id) VALUES ('loyalty', $1)
			ON CONFLICT DO NOTHING`, m.ID)
		if err != nil {
			return err
		}
		if tag.RowsAffected() == 0 {
			return nil // already applied; acknowledge and move on
		}
		_, err = tx.Exec(ctx, `
			INSERT INTO points_ledger (buyer_id, source, points) VALUES ($1, $2, $3)`,
			evt.BuyerID, "order:"+evt.OrderID, pointsFor(evt))
		return err
	})
	// The caller commits the Kafka offset only after Handle returns nil.
}
```

If two consumer instances get the same event at once, during a rebalance for example, the second `INSERT` waits on the unique index until the first transaction commits, then conflicts and skips. The database resolves the race; no extra locking is needed.

Here a `UNIQUE (source)` constraint on `points_ledger` would make the ledger idempotent by itself, which is the naturally idempotent option from How It Works. The inbox is for effects without a natural key.

The inbox's retention has to outlast every way a message can come back. If the topic keeps 30 days and someone replays it from the start to rebuild a read model, an inbox trimmed to 7 days lets 23 days of duplicates through.

## Further Reading

- **Chris Richardson, microservices.io:** the "Transactional outbox," "Polling publisher," "Transaction log tailing" and "Idempotent consumer" pattern pages. Short and precise, and his book _Microservices Patterns_ (Manning, 2018), chapter 3, covers them in depth.
- **Gunnar Morling, "Reliable Microservices Data Exchange With the Outbox Pattern"** (Debezium blog, 2019). The log-tailing version end to end, from the author of Debezium's outbox event router.
- **Debezium documentation: "Outbox Event Router."** How a CDC connector turns outbox inserts into routed, keyed messages.
- **Pat Helland, "Life beyond Distributed Transactions: An Apostate's Opinion"** (CIDR 2007; revised in ACM Queue, 2016). The argument for why systems at scale give up distributed transactions, and why idempotent messaging takes their place.
- **Martin Kleppmann, _Designing Data-Intensive Applications_,** chapter 11, especially the discussion of dual writes and change data capture.
- **Apache Kafka documentation:** the idempotent producer and transactions (KIP-98). Useful mostly for learning precisely what Kafka's exactly-once covers and what it doesn't.
- **PostgreSQL documentation:** advisory locks, `LISTEN`/`NOTIFY`, `pg_current_snapshot()` and `pg_logical_emit_message`.
- **In this collection:** 2.3 and 2.4 (where this seam first appeared), 9.4 (persist, then notify), 14.1, 16.1a (when loss is acceptable), 17.1 (idempotency keys), 19.2b (tracing across queues), 36.3a (why not call consumers inline), 37.1a (event stores), 37.4a (sagas), 38.4 (CDC).

A **Java** sibling would be worth writing, around Spring Modulith's event publication registry. It records each event in the database in the same transaction as the change and marks it complete per listener, which is an outbox and an inbox built into the framework. It's the clearest case of the pattern made invisible: the useful questions become which settings decide whether incomplete publications are retried on restart, and what happens to ordering once listeners run asynchronously. Not yet written.
