# Stream Processing: State, Windows, Event Time and Late Data

_Module 37.3a — Event-Driven Architecture_

## The Problem

Suppose you run an e-scooter sharing service: 30,000 scooters in four cities. Each ride produces events (`TripStarted`, `TripEnded`, location pings) that reach Kafka through the scooters' mobile connections. Operations wants a live view of demand: **rides ending in each zone, per five minutes.** Two teams depend on it. Fleet crews use it to move scooters to where people are finishing rides, and a pricing service uses it to set surge prices.

The first version is an ordinary consumer (37.2b) that keeps counts in a `HashMap` keyed by zone and minute, and writes totals to a dashboard table. Four things go wrong.

**The counts are in the wrong windows.** Scooters in tunnels, garages and underground stations lose signal and buffer their events. When they reconnect, the backlog arrives in a burst. The consumer counts by the time it receives an event, so at 08:03 it counts rides that ended at 07:40. The 08:00–08:05 window for a downtown zone shows a spike of 90 rides; the true number was 31. Pricing surges prices for rides that ended twenty minutes earlier, somewhere else.

**The counts vanish on restart.** Every deploy wipes the `HashMap`, and the dashboard drops to zero for the current window. The team moves the counts to Redis: one increment per event, over the network. At the evening peak of about 3,000 events per second, the consumer falls 20 minutes behind, mostly waiting on Redis.

**Two answers for the same window.** They fix the time problem by counting by the event's own timestamp, and emit an updated count every time a window changes. The dashboard now shows each window's count climbing, as expected. But the billing team's consumer, which pays fleet contractors per ride, adds up every update instead of keeping the latest. A window updated 40 times is paid 40 times. Meanwhile finance's nightly batch report disagrees with the stream by 3%: events arriving more than ten minutes late are silently discarded, and nobody counts them.

**The join matches nothing.** Pricing needs each ride's zone surcharge, which lives in a `zones` topic. They join rides to zones and get almost no matches. The rides topic is keyed by trip ID with 24 partitions; the zones topic is keyed by zone ID with 6. A join looks up matching keys in matching partitions, and here neither lined up.

Each incident is a stream-processing problem solved by hand, badly: time, state, completeness and co-partitioning.

## What It Is

**Stream processing** is computing continuously over an unbounded stream of events, updating results as events arrive, instead of running a query over a finished dataset. Its operations come in two kinds:

- **Stateless** operations look at one event at a time: filter, transform, route. They scale like any consumer (37.2b).
- **Stateful** operations remember things across events: counts, sums, joins, deduplication, pattern detection. They need state that survives restarts, moves with partitions, and can be rebuilt.

And three ideas turn out to be central:

- **Event time vs processing time.** When something happened, versus when the processor saw it. They differ, sometimes by hours.
- **Windows.** An unbounded stream has no "total," so aggregates are computed over windows of time.
- **Completeness.** Since events arrive late, a processor has to decide when a window is done: how long to wait, and what to do with events that arrive after that.

Engines such as **Kafka Streams** and **Apache Flink** provide state, time handling and exactly-once processing, so that each of those isn't rebuilt by hand.

Neighbors:

- **A consumer** (37.2b) handles events independently. Once it keeps meaningful state across events, it's become a stream processor, whether or not it uses an engine.
- **Batch processing** answers the same questions over a finished dataset, later, with complete data. The two often run side by side: the stream for fast approximate answers, batch for authoritative ones.
- **Streaming databases** (Materialize, RisingWave) and **Flink SQL** express stream processing as SQL views kept up to date incrementally. Same ideas, different interface.

## Recognizing the Problem

- A consumer keeps counts, sums or recent events in memory or in a cache, and restarts lose or corrupt them.
- Results are grouped by when events arrived rather than when they happened.
- Devices, mobile apps or partner systems send events that can be delayed by minutes or hours.
- A per-event call to Redis or a database is the main thing slowing a consumer down.
- Downstream systems add up repeated results for the same period.
- A real-time dashboard and a nightly report disagree, and nobody knows by how much or why.
- A join between two topics matches less than it should.
- "How long should we wait for stragglers?" has no written answer.

## How It Works

### State lives next to the processing

A stream processor splits the work by input partition, like a consumer group. Each task keeps its state in a **local store** on the same machine, often RocksDB on disk, so reading and updating a count is a local operation, not a network call. That's what removes the Redis bottleneck.

To survive failures, every change to a local store is also written to a **changelog topic** in Kafka. When a task moves to another machine, the new owner rebuilds the store by reading the changelog. Flink does the equivalent with periodic **checkpoints** of all state to durable storage.

```
trips.ended (by tripId) ─► re-key by zone ─► repartition topic (by zoneId)
                                                    │
                                    ┌───────────────┴───────────────┐
                                    ▼                               ▼
                              task 0: zones A–F               task 1: zones G–M
                              local store  ⇄ changelog        local store ⇄ changelog
                                    │                               │
                                    └──────────► zone-stats.5m ◄────┘
```

- **Grouping by a new key means a shuffle.** Trips arrive keyed by trip ID, but counting per zone needs every ride for a zone in one task. The engine writes the re-keyed events to an internal **repartition topic** and reads them back. That's extra traffic and storage, and it's why choosing keys well at the source (37.2b) matters.
- **Restoring state takes time.** A task with 20 GB of state can take minutes to rebuild from its changelog, and it can't process events meanwhile. **Standby replicas** keep warm copies on other instances, so a failover takes seconds instead.

### Three clocks

- **Event time:** when it happened, recorded by the source. The scooter's clock when the ride ended.
- **Ingestion time:** when Kafka received it (the record timestamp).
- **Processing time:** when the processor handles it.

Windows over processing time are simple and wrong whenever delays vary, which was the first incident. Windows over event time give the right answer, and force the question of when a window is finished.

Event time has its own trap: **device clocks are wrong.** A scooter with a dead clock battery reports 1970. One with a bad sync reports next Thursday. Validate event timestamps against ingestion time, and clamp or reject values outside a tolerance, or a single bad clock distorts everything (see the Implementation).

### Windows

| Window | Shape | Scooter example |
|---|---|---|
| **Tumbling** | Fixed, non-overlapping: 08:00–08:05, 08:05–08:10 | Rides ending per zone per 5 minutes |
| **Hopping** | Fixed length, overlapping: 15-minute windows every 5 minutes | A smoother demand signal for pricing |
| **Sliding** | Defined by distance between events: any two events within 2 minutes | Two unlocks of the same scooter within 2 minutes (a join window) |
| **Session** | Activity separated by a gap: ends after 30 minutes of inactivity | A rider's session across several short rides |

Each event can belong to several hopping windows, which multiplies state and output. Sessions have no fixed end, so a session can grow and merge with another when a late event bridges the gap between them.

### When is a window done? Watermarks and grace

Out-of-order events mean a processor can never be certain it has seen everything for 08:00–08:05. It needs a rule for when to stop waiting:

- **Flink uses watermarks.** A watermark is a statement that no events older than time T are expected any more. A common strategy is "the largest event time seen, minus the maximum expected disorder." With 2 minutes of allowed disorder, when an event from 08:07 arrives, the watermark moves to 08:05 and the 08:00–08:05 window can close.
- **Kafka Streams tracks stream time.** Stream time is the largest event timestamp a task has seen. A window closes when stream time passes its end plus a **grace period.**

Both make the same trade-off: **waiting longer is more complete and later.** A 2-minute grace period catches most delayed scooters and delays every result by 2 minutes. Waiting 30 minutes would catch nearly everything and make the "live" dashboard half an hour old.

Both also stall when **a partition goes quiet.** If no events arrive at 03:00, time doesn't advance and the last windows never close. Flink handles this by marking sources idle after a timeout, so they stop holding the watermark back. In Kafka Streams, stream time only moves when events arrive, so quiet periods need either a periodic heartbeat event or acceptance that the final window of the night closes when the morning's first event arrives.

### Late data: choose a policy

An event arriving after its window closed is **late.** Four policies, often combined:

- **Drop it, and count it.** Kafka Streams drops late records and records them in a metric. That's acceptable only if someone watches the metric. The finance discrepancy was dropped events that nobody measured.
- **Send it aside.** Flink can route late events to a **side output**, and from there to a topic for correction or review.
- **Update the result.** Keep the window's state a while longer (Flink's allowed lateness) and emit a corrected result when a late event arrives. Consumers then have to handle corrections.
- **Reconcile in batch.** Let the stream be fast and approximate, and let a nightly batch over complete data be the authoritative answer. Pricing and fleet crews use the stream; paying contractors and finance use the batch.

The last option is usually right for money. A stream answers "roughly what's happening now"; a ledger needs "exactly what happened," and those have different completeness requirements.

### Emitting results: every change, or once at the end

- **Emit on every update.** Each new event produces an updated count for its window. It's the lowest latency, and the output is a **changelog of results**: consumers must replace the value for that window key, never add it. Adding updates was the billing incident.
- **Emit once, at close.** Hold results until the window closes (Kafka Streams' `suppress`, Flink's default for event-time windows). Each window produces exactly one result, at the cost of window length plus grace in latency.

Choose per consumer: the dashboard wants updates, contractor payments want final results. Whichever you choose, write results keyed by window (zone plus window start), so a repeat is an overwrite, not a double count.

### Streams, tables and joins

A stream of changes and a table of current values are two views of the same thing: replay the stream and you get the table, and record every change to a table and you get the stream. Kafka Streams names the two views `KStream` and `KTable`. A compacted state topic (37.2c) is a table stored as a stream.

Joins come in three kinds:

- **Stream to table:** enrich each ride with its zone's current surcharge. Each event looks up the latest value in the table. By default that's the latest value when the event is processed, not when it happened; newer Kafka Streams versions support versioned tables for looking up the value at the event's time.
- **Stream to stream:** match events from two streams within a window, such as an unlock and a payment authorization within 2 minutes. Both sides are buffered for the window's length.
- **Table to table:** keep a joined table up to date as either side changes.

Joins require **co-partitioning**: both inputs keyed by the join key, with the same number of partitions, so matching keys end up in the same task. That was the fourth incident. The fixes are to re-key one side (another repartition topic), or, for small reference data such as 400 zones, use a **global table**, which is copied in full to every instance and needs no co-partitioning.

### Exactly-once, and where it ends

Kafka Streams' `exactly_once_v2` commits a task's state updates, its output events and its input offsets in one Kafka transaction. A crash never produces a count that was updated but not emitted, or emitted twice. Flink achieves the same with checkpoints and transactional sinks.

That guarantee covers Kafka to Kafka. A sink outside Kafka, such as the dashboard's Postgres table or a pricing API, is outside the transaction, so it gets at-least-once delivery and needs idempotent writes: upsert by window key (37.2a).

### Patterns over sequences

Some questions aren't aggregates but sequences: "a scooter unlocked, didn't move, and locked again within 60 seconds, five times in an hour, on one account." That pattern suggests someone abusing free unlocks. **Complex event processing** detects such sequences per key. Flink's CEP library expresses them as patterns with time limits. In Kafka Streams, the equivalent is a small state machine per key, with timers to expire partial matches. Either way, it's stateful stream processing whose state is "how far through the pattern this key has got."

### Changing the logic: reprocessing

A bug fix or a new aggregation needs results recomputed from history. The approach is the same as rebuilding a projection (37.1b): run the new version under a **new application ID**, with fresh state, from the start of the retained input, into a new output topic, then switch consumers across. This only works if the input is still retained (37.2b), which is one of the strongest reasons for long retention on source topics.

### Choosing an engine

| | Runs as | Good fit | Watch for |
|---|---|---|---|
| **Kafka Streams** | A library inside your service | Kafka in, Kafka out; teams that deploy ordinary services | Kafka only; stream time stalls on quiet partitions; state restoration on rebalance |
| **Apache Flink** | Its own cluster, or a managed service | Rich time handling (watermarks, idleness, late side outputs), many sources and sinks, large state, Flink SQL | A distributed system to operate, with its own checkpointing and upgrade concerns |
| **Spark Structured Streaming** | Micro-batches on Spark | Organizations already running Spark | Latency in seconds, not milliseconds |
| **Streaming databases** (Materialize, RisingWave) | A database | Teams that want SQL views kept up to date | Another database; less control over time semantics |
| **A consumer and a database** | Your service | Simple stateless work, or small state | You build state, time and exactly-once yourself, as the scooter team did |

## When It's Appropriate

- **Results need to be fresh in seconds to minutes,** and would be stale by the time a batch finishes. Surge pricing every five minutes is the example; hourly batch would miss every peak.
- **Volume makes per-event database calls the bottleneck.** 3,000 events per second of counting belongs in local state, not in 3,000 network round trips.
- **Events arrive out of order,** and the answer depends on when things happened.
- **Joins or enrichment across streams** have to happen continuously, as events arrive.
- **Sequence detection** (fraud, abuse, anomalies) has to act while it's still useful.

## When It's Unnecessary or Overkill

- **Hourly or daily reports.** A warehouse query over a finished dataset is simpler, complete, and easier to fix (16.4).
- **Stateless transformations.** Filtering and reformatting are an ordinary consumer's job.
- **Low volume.** A few events per second can be counted with an upsert in Postgres. A query every minute over an indexed table is a legitimate "stream processor."
- **Dashboards where minutes of lag are fine.** Materialized views refreshed every minute, or a warehouse on a short schedule, may be enough.
- **A Flink cluster for one aggregation.** If the job fits in Kafka Streams inside an existing service, it doesn't need its own platform.

## Trade-offs

- **Latency against completeness, always.** Every window has a grace period or watermark, and every choice either delays results or drops late events.
- **State is operational weight.** Changelogs, restoration time, disk on every instance, standby replicas, and rebalances that pause processing while state moves.
- **Repartitioning costs** network traffic and storage, every time a computation groups by a different key.
- **Stream results are provisional.** Consumers have to understand updates, corrections and late-data policy. Most bugs are in consumers that assume one final number.
- **Two answers.** A stream and a batch over the same data will differ, and the difference needs to be expected, measured and explained.
- **Debugging is harder.** A wrong count depends on arrival order, time progress and state from hours ago, which is hard to reproduce outside production.
- **Reprocessing needs retained input** and a way to run two versions side by side.

## Alternatives

- **Batch in a warehouse** (16.4), run every few minutes if needed. The simplest correct answer for anything that doesn't need seconds.
- **Micro-batches:** a job that reads the last N minutes of events every N minutes. Easy to understand, and it handles late data by rerunning a period.
- **A streaming database or Flink SQL,** when the logic fits SQL and the team would rather write views than topologies.
- **Maintained aggregates in the source database:** update a counter row in the same transaction as each ride. It works at modest volume, is exact, and has no time semantics to get wrong, because it uses the database's own order.
- **Lambda architecture:** a stream for speed and a batch for correctness, each built separately. The reconciliation policy above is a lighter version; the full form means maintaining the logic twice.

## How to Achieve It

1. **Decide the time semantics before the technology.** Which timestamp is event time, how late events can plausibly be, what happens to later ones, and who needs final answers versus live ones.
2. **One job in an engine.** Move the most important stateful computation into Kafka Streams inside an existing service: event time, a grace period from measured lateness, results keyed by window, idempotent sinks. _Next when:_ the job's state survives restarts and its late-event count is being watched.
3. **Reconcile.** Add the batch comparison, and publish how far the stream and batch differ. Use the stream for decisions that tolerate approximation, the batch for money. _Next when:_ more jobs, joins or sources join in.
4. **Operate state.** Standby replicas, alerts on restoration time and lag, exactly-once for Kafka-to-Kafka stages, and a reprocessing procedure with new application IDs.
5. **Choose a platform deliberately.** Move to Flink when you need its time handling, more sources and sinks, or state beyond what services comfortably hold. Consider SQL-based options when most jobs are aggregations and joins.

## Implementation

Java with Kafka Streams: the library ships with Kafka, runs inside an ordinary service, and exposes every decision above (timestamps, windows, grace periods, suppression, global tables) as an explicit call.

### Event time, with a guard against bad clocks

```java
final class TripEndedAt implements TimestampExtractor {
    private static final long MAX_FUTURE_SKEW_MS = Duration.ofMinutes(5).toMillis();

    @Override
    public long extract(ConsumerRecord<Object, Object> rec, long partitionTime) {
        if (rec.value() instanceof TripEnded t && t.endedAt() != null) {
            long eventTime = t.endedAt().toEpochMilli();
            long received  = rec.timestamp();         // when Kafka got it
            // A clock set to next week would push stream time forward and make
            // every other scooter's events "late". Trust the scooter only so far.
            return Math.min(eventTime, received + MAX_FUTURE_SKEW_MS);
        }
        return rec.timestamp();                        // no event time: use arrival
    }
}
```

The clamp matters more than it looks. Stream time is the largest timestamp a task has seen, so one event from the future closes every open window early, and everything genuinely current is then dropped as late. An event time in the far past is only one late event; one in the future is an outage.

### Rides per zone per five minutes

```java
StreamsBuilder b = new StreamsBuilder();

KStream<String, TripEnded> trips = b.stream("trips.ended",
    Consumed.with(Serdes.String(), tripSerde).withTimestampExtractor(new TripEndedAt()));

// ~400 zones: small enough to copy to every instance, so no co-partitioning needed.
GlobalKTable<String, Zone> zones = b.globalTable("zones.state",
    Consumed.with(Serdes.String(), zoneSerde));

trips
    .join(zones,
          (tripId, trip) -> trip.endZoneId(),               // which zone to look up
          (trip, zone)   -> new ZonedTrip(trip, zone))
    .groupBy((tripId, zt) -> zt.zoneId(),                    // re-key: a repartition topic
             Grouped.with(Serdes.String(), zonedTripSerde))
    .windowedBy(TimeWindows.ofSizeAndGrace(Duration.ofMinutes(5), Duration.ofMinutes(2)))
    .aggregate(ZoneStats::empty,
               (zoneId, zt, stats) -> stats.add(zt),
               Materialized.with(Serdes.String(), statsSerde)) // local store + changelog
    .suppress(Suppressed.untilWindowCloses(Suppressed.BufferConfig.unbounded()))
    .toStream()
    .map((w, stats) -> KeyValue.pair(
        w.key() + "@" + w.window().startTime(),              // one key per zone and window
        stats.forWindow(w.window().startTime(), w.window().endTime())))
    .to("zone-stats.5m", Produced.with(Serdes.String(), statsSerde));
```

What each incident became:

- **Wrong windows:** the timestamp extractor puts each ride in the window when it ended.
- **Lost state and the Redis bottleneck:** `aggregate` keeps counts in a local store backed by a changelog, so restarts restore it and nothing crosses the network per event.
- **Double counting:** `suppress` emits one result per window after the 2-minute grace period, and the output key (`zone@start`) makes any repeat an overwrite. The live dashboard can read the same aggregation without `suppress`, as a second output of updates.
- **The empty join:** the zones table is global, so every instance holds all 400 zones and no key alignment is needed. A table with millions of rows would instead need re-keying both sides to the same key and partition count.

`BufferConfig.unbounded()` holds every open window in memory until it closes. With 400 zones and a 7-minute span, that's a few thousand small entries. With millions of keys it would need a bounded buffer and a decision about what happens when it fills.

Late rides, those arriving more than 2 minutes after their window closed, are dropped, and Kafka Streams counts them in its dropped-records metric. That metric needs an alert, and the nightly batch provides the correct totals for contractor payments.

### Configuration

```java
props.put(StreamsConfig.APPLICATION_ID_CONFIG, "zone-stats-v3");  // new version = new ID = fresh state
props.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG, StreamsConfig.EXACTLY_ONCE_V2);
props.put(StreamsConfig.NUM_STANDBY_REPLICAS_CONFIG, 1);          // warm state on another instance
```

The application ID names the consumer group, the changelog topics and the repartition topics. Changing it runs the new logic from scratch alongside the old, which is how reprocessing works. Reusing it after changing the topology can attach new code to old state that no longer matches.

Exactly-once covers `trips.ended` → state → `zone-stats.5m`. The service that copies `zone-stats.5m` into the dashboard's Postgres table still upserts by the `zone@start` key, because that last step is outside the Kafka transaction.

## Further Reading

- **Tyler Akidau, "Streaming 101" and "Streaming 102"** (O'Reilly Radar, 2015). The clearest introduction to event time, windows, watermarks and triggers. Then **Akidau, Chernyak and Lax, _Streaming Systems_** (O'Reilly, 2018) for the full treatment.
- **Akidau et al., "The Dataflow Model"** (VLDB 2015). The paper behind most modern engines' time semantics: what, where, when and how results are computed.
- **Martin Kleppmann, _Designing Data-Intensive Applications_,** chapter 11: stream processing, time, joins and fault tolerance.
- **Jay Kreps, "Questioning the Lambda Architecture"** (O'Reilly Radar, 2014). The argument for reprocessing with one codebase instead of maintaining a stream and a batch separately.
- **Kafka Streams documentation:** core concepts (time, stream-table duality, state), windowing and grace periods, and suppression.
- **Apache Flink documentation:** "Timely Stream Processing," generating watermarks (including idleness), allowed lateness and side outputs, and the CEP library.
- **Materialize and RisingWave documentation,** for the streaming-database approach.
- **In this collection:** 37.2b (partitions, retention, consumers), 37.2c (state topics and contracts), 37.1b (rebuilding projections), 37.2a (idempotent sinks), 16.4 (the warehouse, for batch reconciliation).
