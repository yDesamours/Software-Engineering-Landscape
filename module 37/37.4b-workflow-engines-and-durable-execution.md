# Workflow Engines and Durable Execution

_Module 37.4b — Event-Driven Architecture_

## The Problem

Suppose you run the vacation-rental platform from 37.4a, a year later. The booking saga works: a table of saga rows, conditional transitions, commands through the outbox, and a scanner for deadlines. It worked well enough that every other long-running process was built the same way:

- **Security deposits:** release 14 days after checkout, unless the host files a damage claim, in which case wait up to 7 days for a resolution.
- **Host onboarding:** identity verification, listing review, payout setup. Reminders after 3, 7 and 14 days, and the listing suspended after 30.
- **Disputes:** evidence windows, escalation after 5 days, refunds.
- **Monthly payouts,** with retries against the payment provider.

That's nine flows, each with its own state table, transition code, deadline scanner, retry and backoff logic, and "stuck items" admin page. About a third of the team's code is this plumbing. Then three things happen.

**A new step shifts every in-flight flow.** The deposit flow gains a damage inspection between "checkout" and "wait 14 days." A developer inserts it into the step list. The saga rows store the current step as an index into that list, so 3,400 deposits that were at step 2, "waiting 14 days," are now at step 2, "request inspection," and the next scanner run sends 3,400 inspection requests for stays that ended weeks ago. Deposits that were at step 3 skip the wait and are released immediately, including 60 with damage claims about to be filed.

**Nobody can say why.** A host asks why her payout from March never arrived. Answering takes an engineer two days: the payouts table says `FAILED_RETRYING`, the retry count says 14, and the reason is spread across logs from three services, some of which have already been deleted.

**The onboarding flow becomes a state machine nobody trusts.** "Wait for verification, or remind after 3, 7 and 14 days, and suspend after 30, unless the host withdraws, or support grants an extension, which restarts the reminders" turns into 11 states, 3 timers per host, and transitions tested one at a time. A support extension granted between two reminder scans produces a suspension the next morning for a host who was just told she had another week.

Each flow is a sequence of steps with waits, retries, and branches, which is exactly what ordinary code expresses well. The team keeps rebuilding, in tables, what a program would say in a few lines, if the program could survive a crash in the middle of a 14-day wait.

## What It Is

**Durable execution** lets you write a long-running process as ordinary code (sequential steps, loops, `try`/`catch`, and `sleep` for 14 days) and have it survive crashes, deploys and restarts. The engine records the result of every step in a persisted **event history**. If the process running the code dies, another worker loads the history, runs the code again from the start, and uses the recorded results instead of repeating finished steps, until it reaches the point where the previous run stopped. Then it carries on.

Engines that work this way include Temporal (and Cadence, its predecessor), Restate, DBOS, Inngest, Azure Durable Functions and, since December 2025, AWS Lambda durable functions. A second family defines workflows declaratively rather than as code: AWS Step Functions as JSON state machines, and Camunda with BPMN diagrams. The problems they solve are the same; the tools differ in whether the flow is written in code or described as a model.

Two kinds of code make up a workflow:

- **Workflow code** decides what happens next. It must be deterministic, because it runs again during every replay.
- **Activities** do the actual work: calling the payments API, writing to a database, sending an email. They're retried according to a policy, and their results are recorded in the history.

Neighbors:

- **A saga** (37.4a) is the pattern: steps, compensations, a pivot. A workflow engine is one way to implement its orchestrator, with the state, timers, retries and history provided for you.
- **A job queue** (Module 10) runs single tasks with retries. A workflow coordinates many steps over time, with state between them.
- **Event sourcing** (37.1a) is what the engine does internally: a workflow's state is rebuilt by replaying its history. The engine event-sources your orchestrator so you don't have to.
- **A cron scheduler** (10.3) starts things on a timetable. A workflow's timers belong to one execution: "14 days after this checkout."

## Recognizing the Problem

- Several tables exist whose main columns are `state`, `step`, `attempt` and `due_at`, each with its own scanner job.
- Retry, backoff and timeout logic is reimplemented for each process.
- Changing a process's steps requires a data migration for everything currently in progress.
- "What happened to this one, and why?" means searching logs across services.
- Processes wait for people (approvals, verifications, responses) for days or weeks.
- Timers are built from `due_at` columns scanned every minute, and bugs appear around scans and restarts.
- A "stuck items" admin page exists for more than one process.

## How It Works

### History and replay

Each workflow execution has a history: an append-only list of what happened.

```
depositWorkflow(booking 88312)
 1  WorkflowStarted        { bookingId: 88312, depositId: "dep_41" }
 2  TimerStarted           14 days
 3  SignalReceived         damageClaimFiled { amountMinor: 18000 }
 4  TimerCanceled
 5  TimerStarted           7 days
 6  SignalReceived         claimResolved { amountMinor: 12000 }
 7  ActivityScheduled      payments.captureDeposit(12000)
 8  ActivityCompleted      { captureId: "cap_9" }
 9  ActivityScheduled      payments.releaseDeposit(remaining)
    ← worker crashes here
```

A new worker picks the workflow up and runs `depositWorkflow` from the top. When the code starts the 14-day timer, the engine sees event 2 in the history and doesn't start a new one. When the code waits for a claim, event 3 supplies it. When it calls `captureDeposit`, event 8 supplies the result without calling payments again. At `releaseDeposit`, the history has a scheduled activity with no result, so the engine waits for it to finish or retries it, and the code continues from there as if nothing had happened.

That's also the answer to the payout question: the history is a complete record of every step, input, result, retry and signal for that execution.

### Determinism: the rule that makes replay work

During replay, the workflow code must make the same calls, in the same order, with the same inputs, as it did the first time. Otherwise the engine can't match code to history, and fails the workflow with a **non-determinism error.** So workflow code must not:

- Read the clock or generate random values or UUIDs directly. Use the engine's versions, which are recorded.
- Call networks, databases or files. That's what activities are for.
- Read configuration or environment values that can change between runs.
- Depend on unordered iteration, such as a Go map, to decide what to call.
- Start threads or goroutines outside the engine's own concurrency primitives.

SDKs help to different degrees. Temporal's TypeScript SDK runs workflow code in a sandbox that replaces `Date` and `Math.random` with deterministic versions. The Go SDK has no sandbox, and relies on conventions and a static checker. Lambda durable functions check that each operation's name and type match the checkpoint log on replay.

### Timers, signals and queries

- **Durable timers.** `sleep("14 days")` costs nothing while it waits: no process holds it. The engine wakes the workflow when it's due.
- **Signals** deliver external events into a running workflow: a host's damage claim, a support extension. Human steps are just signals with timeouts around them.
- **Queries** read a workflow's current state for a support screen, without changing it. Some engines also offer **updates**, a signal that returns a result.

The onboarding flow's 11 states become a loop: wait for verification or the next reminder time, send a reminder, and restart the schedule when an extension arrives. The extension-versus-suspension race disappears because signals and timers are processed one at a time, in history order, by the same code.

### Activities: retries, timeouts, and what the engine doesn't solve

Each activity call has a **retry policy** (initial interval, backoff, maximum interval, maximum attempts, and error types that shouldn't be retried, such as a declined card) and **timeouts**: how long one attempt may run, how long all attempts together may take, and a heartbeat interval so a crashed long-running activity is noticed quickly (10.2a).

What the engine does **not** do is make side effects happen exactly once. An activity can call the payments API successfully and crash before the result is recorded, and the engine will retry it. Activities are at-least-once, like everything else in this module, so each must carry an idempotency key, derived from the workflow ID and step, that the payments provider recognizes (17.1). The participant-side guards from 37.4a (idempotency, compensation arriving before its step, late steps refused) still belong in each participant.

Workflows do remove one piece of work: the outbox (37.2a) for anything a workflow drives. An activity that fails is retried until it succeeds or the workflow deals with it, so "committed but never published" can't happen between workflow steps. Events that leave a service on its own initiative, outside any workflow, still need the outbox.

### Sagas in code

The booking saga from 37.4a becomes a `try`/`catch` with a list of compensations (see the Implementation). The pivot is a visible line of code: compensations are registered before it and not after. The saga table, attempt numbers and deadline scanner become the engine's job. The design decisions (the order of steps, which step is the pivot, what each compensation costs) remain yours.

### Changing code while executions are running

This is the problem from the first incident, and engines don't make it go away; they make it explicit. A deposit workflow started three weeks ago will replay its history against whatever code the workers are running today. If today's code calls `requestInspection` where the history recorded a 14-day timer, replay fails.

Four ways to handle it:

- **Patching.** Branch in the code on a named patch: new executions take the new path, and replays of older executions take the old one. When no execution started before the patch is still open, remove the old branch. Temporal calls these `patched` and `deprecatePatch`.
- **Pinned versions.** Each execution runs to completion on the code version that started it. New deploys only take new executions. Temporal's worker versioning can pin executions to worker deployments; Lambda durable functions pin each execution to the function version it started on. Old versions have to keep running until their last execution finishes, which can be months.
- **A new workflow type.** `depositWorkflowV2` for new executions, the old one left running until empty.
- **Continue-as-new.** Long-lived workflows periodically end and restart themselves with their current state as input, which also gives them a point to pick up new code.

Whichever you choose, **test it by replay.** Export histories from production regularly and replay them against new code in CI. A change that breaks determinism fails the build instead of 3,400 workflows.

### Histories grow

A workflow that loops forever, such as a subscription that renews monthly, or a host account whose onboarding reminders never end, accumulates history, and engines limit history size. Temporal warns as histories approach tens of thousands of events. Use continue-as-new for long-running loops, and keep large payloads out of histories: store documents in object storage and pass references. Histories contain every activity's inputs and results, which often include personal data. Encrypt payloads (Temporal supports a codec for this), and include history retention in your data map (34.1a).

### The engine is a critical dependency

Workflow engines are stateful services with their own databases: Cassandra, Postgres or MySQL for self-hosted Temporal, or a managed service. Every workflow step goes through them, so an engine outage stops every process at once, and each step adds some latency, typically milliseconds to tens of milliseconds. Workers are your own processes, deployed like any other service. Managed offerings (Temporal Cloud, Step Functions, Lambda durable functions, Azure Durable Functions) trade operational work for per-action pricing, and should be costed at your real step volume.

### The landscape

| Style | Examples | Flow defined as | Good fit |
|---|---|---|---|
| **Replay-based durable execution** | Temporal, Cadence, Restate, Azure Durable Functions, Lambda durable functions | Ordinary code with an SDK | Complex branching, loops, many timers and signals; teams that want flows in code review |
| **Durable steps in your database** | DBOS, Inngest | Code, with steps checkpointed to Postgres or a hosted service | Smaller teams that want durability without a separate cluster |
| **Declarative state machines** | AWS Step Functions (Standard runs up to a year; Express up to 5 minutes) | JSON state definitions (Amazon States Language) | Flows that mostly call AWS services; visible execution graphs |
| **BPMN process engines** | Camunda | Diagrams business people can read | Processes the business owns and changes, with audit needs |

## When It's Appropriate

- **Several long-running processes with timers, retries and human steps.** Nine flows with their own tables and scanners is the example. One would not be.
- **Waits measured in days or weeks,** with many executions waiting at once: 3,400 deposits in their 14-day window at any moment.
- **Processes that change while executions are in flight,** where versioning has to be deliberate.
- **Support and audit need a per-execution history:** "what happened to this one, and why?"
- **Sagas with many steps and compensations,** where the orchestrator table from 37.4a is growing a scheduler, a retry system and a history view of its own.

## When It's Unnecessary or Overkill

- **One short saga.** The table-based orchestrator in 37.4a is a few hundred lines you fully understand, with no new infrastructure.
- **Single tasks with retries.** A job queue (Module 10) is simpler.
- **Short synchronous request paths.** An engine adds a round trip per step; a checkout that must answer in 200 ms shouldn't run as ten workflow steps.
- **Two-step flows** that an outbox and an idempotent consumer handle (37.2a).
- **Self-hosting a stateful cluster** without the capacity to run one. Use a managed service or a database-backed library, or don't adopt one yet.
- **"Everything becomes a workflow."** Once an engine is available, teams move simple request handling into workflows and pay latency and cost for durability they don't need.

## Trade-offs

- **Determinism is a permanent discipline.** Every developer touching workflow code has to know the rules, and violations appear only at replay, often weeks later.
- **Versioning in-flight code is real work:** patches accumulate until old executions drain, or old worker versions run for months.
- **A new critical dependency** on the path of every business process it runs.
- **Lock-in.** Workflow code is written against one engine's SDK and semantics. Moving engines means rewriting the workflows, and draining or migrating in-flight executions.
- **Histories hold data.** They grow, cost storage, and contain personal and financial data that retention and erasure rules apply to.
- **Testing needs the engine's test tools:** time-skipping test environments and replay tests, beyond ordinary unit tests.
- **Cost at scale.** Managed engines charge per action or step, which adds up for high-volume flows.
- **Side effects are still at-least-once.** Teams sometimes assume the engine made them exactly-once, and skip idempotency keys.

## Alternatives

- **The table-based orchestrator** from 37.4a: less infrastructure, full control, and all the plumbing is yours.
- **Job queues with scheduled jobs** (Module 10), for processes that are really one step and a delay.
- **Choreography** (37.4a), for short flows between services that shouldn't depend on a central engine.
- **BPMN engines,** when the business wants to read and change process models itself.
- **Reconciliation loops:** periodically compare desired and actual state and repair differences. No workflow at all, and very robust, for processes that are really state convergence.

## How to Achieve It

1. **Pick one flow with timers and human steps,** such as deposits, and run it on an engine: a managed service, or a local development server to start. Keep its activities idempotent, with keys derived from the workflow ID. Leave the other flows alone.
2. **Decide the versioning policy before the first change,** whether patching or pinned versions, and add replay tests with production histories to CI. _Next when:_ a code change to a running flow has gone out safely.
3. **Make executions visible.** Searchable attributes (booking ID, host ID), alerts on failed and long-running executions, and a support view built on queries. _Next when:_ support can answer "what happened?" without an engineer.
4. **Move the other flows across,** one at a time, retiring their tables and scanners. Keep the outbox for events that leave services outside workflows.
5. **Review cost and ownership.** Engine capacity or managed spend, history retention, payload encryption, and who owns the platform.

## Implementation

TypeScript, with Temporal's TypeScript SDK. Its sandbox makes the determinism rules part of the runtime rather than a convention, and it lets the three most important ideas (durable timers, sagas in code, and patching) fit in a few lines each.

### The deposit flow: timers and signals

```ts
import { condition, defineQuery, defineSignal, proxyActivities, setHandler } from "@temporalio/workflow";
import type * as acts from "./activities";

const payments = proxyActivities<typeof acts>({
  startToCloseTimeout: "30 seconds",
  retry: { initialInterval: "1s", backoffCoefficient: 2, maximumInterval: "10m",
           nonRetryableErrorTypes: ["DepositAlreadySettled"] },
});

export const damageClaimFiled = defineSignal<[Claim]>("damageClaimFiled");
export const claimResolved = defineSignal<[Resolution]>("claimResolved");
export const depositStatus = defineQuery<string>("depositStatus");

export async function depositWorkflow(d: DepositRef): Promise<void> {
  let claim: Claim | undefined;
  let resolution: Resolution | undefined;
  let status = "held";
  setHandler(damageClaimFiled, (c) => { claim ??= c; });  // first claim wins
  setHandler(claimResolved, (r) => { resolution = r; });
  setHandler(depositStatus, () => status);

  // Hosts can claim for 14 days after checkout. Waiting costs nothing.
  if (!(await condition(() => claim !== undefined, "14 days"))) {
    status = "releasing";
    await payments.releaseDeposit(d.depositId, `${d.bookingId}:release`);
    status = "released";
    return;
  }

  status = "in_dispute";
  const resolved = await condition(() => resolution !== undefined, "7 days");
  const captureMinor = resolved ? resolution!.amountMinor : 0; // unresolved: the guest keeps it
  if (captureMinor > 0) {
    await payments.captureDeposit(d.depositId, captureMinor, `${d.bookingId}:capture`);
  }
  await payments.releaseDeposit(d.depositId, `${d.bookingId}:release`);
  status = "settled";
}
```

This is the whole deposit process: the 14-day window, the claim, the 7-day resolution window, and the default when nobody resolves it. The table version needed a state table, a scanner, retry logic and an admin page. The support screen calls the `depositStatus` query.

The last argument to each activity is its idempotency key, built from the booking, so a retried capture after a lost response is recognized by the payments service instead of charging twice.

### The booking saga, in code

```ts
export async function bookingWorkflow(req: BookingRequest): Promise<BookingResult> {
  let decision: "approved" | "declined" | undefined;
  setHandler(hostDecision, (d) => { decision ??= d; });

  const compensations: Array<() => Promise<unknown>> = [];
  try {
    await calendar.hold(req);       compensations.unshift(() => calendar.release(req));
    await payments.authorize(req);  compensations.unshift(() => payments.voidAuthorization(req));
    await hosts.requestApproval(req); compensations.unshift(() => hosts.withdraw(req));

    const answered = await condition(() => decision !== undefined, "24 hours");
    if (!answered || decision === "declined") {
      throw ApplicationFailure.nonRetryable(answered ? "host declined" : "host did not answer");
    }
    await payments.capture(req);    // the pivot: no compensation is registered after this line
  } catch (err) {
    await CancellationScope.nonCancellable(async () => {
      for (const undo of compensations) await undo(); // activities with unlimited retries
    });
    return { status: "not_booked" };
  }

  await operations.scheduleCleaning(req); // after the pivot: retried until done
  await notify.bookingConfirmed(req);
  return { status: "confirmed" };
}
```

Compare this with 37.4a's step list, `OnReply` state machine and deadline scanner. The engine now owns the saga's state, attempt numbers and timeout. The race between the host's late approval and the 24-hour timeout is gone, because the signal and the timer are processed in history order by one execution.

Compensations run in a non-cancellable scope, so cancelling the workflow partway through compensation can't leave dates held. The compensation activities use a retry policy without a maximum attempt count, because a compensation that gives up is worse than either outcome.

What didn't change: the calendar participant still needs its row per saga, which handles repeated holds, a release arriving before its hold, and a hold arriving after its release (37.4a). The engine retries activities, and the participants make those retries safe.

### Changing a running flow: a patch

```ts
// Added after the inspection incident. Deposits already in progress replay without it.
if (patched("inspect-before-claim-window")) {
  await operations.requestInspection(d.bookingId, `${d.bookingId}:inspection`);
}
if (!(await condition(() => claim !== undefined, "14 days"))) {
```

Executions started before the deploy have no record of this branch in their history, so on replay `patched` returns false and they continue as they were: the 3,400 deposits in progress keep their original path. New executions record the patch and take the new branch. Once every pre-patch deposit has finished, which here is at most 21 days after the deploy, the code changes to `deprecatePatch`, and later the `if` is removed. The alternative is pinning each execution to the worker version that started it, and keeping old workers running until their executions finish.

### Replay tests in CI

```ts
import { Worker } from "@temporalio/worker";

test("current workflow code replays recent production histories", async () => {
  for (const history of await loadHistories("test/histories/deposit/*.json")) {
    // Throws a determinism error if the code no longer matches what happened.
    await Worker.runReplayHistory(
      { workflowsPath: require.resolve("../src/workflows") }, history);
  }
});
```

A weekly job exports a sample of recent histories from production, covering each branch: released, claimed, resolved, unresolved. The test replays each against the code on the branch. Inserting the inspection step without `patched` fails this test with a determinism error that names the history and the mismatched step. That's the first incident, caught in a pull request.

## Further Reading

- **Temporal documentation:** workflow definitions and deterministic constraints, activities and retry policies, signals and queries, versioning (patching and worker versioning), and replay testing.
- **AWS Lambda durable functions documentation,** and the AWS Durable Execution SDK developer guide's "Key concepts." Checkpoint and replay, executions of up to one year, and version pinning, as AWS implements them.
- **AWS Step Functions documentation:** Standard vs Express workflows, and the Amazon States Language.
- **Microsoft, "Durable Functions: orchestrator function code constraints."** One of the clearest lists of what breaks replay, and why.
- **Restate and DBOS documentation.** Two different approaches: a durable-execution server, and durability as a library on Postgres.
- **Bernd Rücker, _Practical Process Automation_** (O'Reilly, 2021). Workflow engines, BPMN, and orchestration in real organizations.
- **Hector Garcia-Molina and Kenneth Salem, "Sagas"** (1987), again. Long-running processes were the original problem.
- **In this collection:** 37.4a (the saga pattern and participant guards), 37.1a (event sourcing, which the engine does internally), 37.2a (the outbox, and where workflows replace it), 10.2a and 10.3 (retries and schedulers), 17.1 (idempotency keys), 34.1a (data in histories).

A **Go** sibling would be worth writing with Temporal's Go SDK, because Go has no sandbox. Determinism depends on the developer: `workflow.Now` instead of `time.Now`, `workflow.Go` instead of `go`, selectors instead of `select`, sorted keys instead of map iteration, and a static checker in CI to catch mistakes. Seeing the rules as things you must remember, rather than things the runtime enforces, makes it clearer what the TypeScript sandbox quietly does. Not yet written.

---

When a process waits for days, retries for hours, and changes while it's running, its state is the hardest thing in the system to get right. Either write that state machine deliberately and own it, or hand it to an engine and own the determinism and versioning rules instead. Just don't let it grow one scanner at a time.
