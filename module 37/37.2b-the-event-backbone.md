# The Event Backbone: Partitions, Consumer Groups, Lag and Dead Letters in a Log

_Module 37.2b — Event-Driven Architecture_

## The Problem

Suppose you run a parcel-delivery network: 40 depots, scanners on every conveyor and in every van, about 2 million parcels a day. Every scan becomes an event on one Kafka topic, `parcel-events`: `Received`, `Sorted`, `LoadedOnVan`, `OutForDelivery`, `Delivered`, `DeliveryFailed`. Four services consume it:

- **tracking** keeps the page customers refresh
- **notifications** sends SMS and email ("your parcel arrives today")
- **billing** charges the senders' accounts
- **analytics** measures delivery times against promises

The outbox from 37.2a gets events onto the topic reliably. Over one peak season, getting them off it goes wrong in five ways.

**Delivered, then out for delivery.** Producers didn't set a key, so events went to partitions round-robin. A parcel's `OutForDelivery` and `Delivered` land on different partitions, and tracking reads one partition faster than the other. For about 4% of parcels, the page shows "Delivered" and then, a minute later, "Out for delivery." Keying by parcel ID fixes it. Then, in November, someone raises the partition count from 12 to 48 to handle peak, and for the next few hours the same reordering comes back.

**Forty pods, twelve working.** On Black Friday, notifications falls 50 minutes behind. Operations scales it from 12 pods to 40. Lag keeps growing. The topic had 12 partitions at the time, and each partition goes to exactly one consumer in the group, so 28 pods sit idle.

**The rebalance spiral.** The SMS provider slows to about 2 seconds per call. Notifications polls 500 events at a time, so one batch now takes over 16 minutes, far past the consumer's 5-minute limit between polls. Kafka assumes the consumer is dead and removes it from the group. Its partitions move to other pods, which re-read the uncommitted batch and resend its SMS. Those pods are now slower too, and they get removed as well. The cycle runs for an hour, and 90,000 customers get the same text two or three times.

**One event stops a partition.** A scanner firmware update sends `weightGrams` as the string `"1.2kg"`. Billing's handler throws, the consumer retries the same event, throws again, and never moves past it. Partition 7, one parcel in 48, stops being billed for six hours. The lag alert looked at average lag across all partitions, which barely moved. Someone "fixes" it by catching the exception and continuing, and billing now silently skips any event it can't parse.

**The long weekend.** Analytics is down from Friday night to Tuesday morning. The topic keeps events for 3 days. When analytics restarts, its saved position no longer exists in the log. It's configured to jump to the newest event in that case, so it starts from Tuesday. Four hours of Friday night's deliveries vanish from the delivery-time report without any error.

None of these is exotic. Each is a default, or a property of logs, that nobody chose.

## What It Is

An **event backbone** is a shared, retained, partitioned log that many services publish to and consume from independently. Kafka is the common example. Redpanda, Azure Event Hubs and Amazon MSK speak the same protocol, and NATS JetStream and RabbitMQ Streams are logs built differently.

The vocabulary, all of which the incidents above depend on:

- A **topic** is a named log, split into **partitions**. Each partition is ordered on its own; there's no order across partitions.
- A **key** decides which partition an event goes to. The same key always goes to the same partition, as long as the partition count doesn't change.
- An **offset** is an event's position in its partition.
- A **consumer group** is one logical subscriber. Each partition is read by exactly one consumer in the group at a time. Different groups read the same events independently.
- A **committed offset** is how far a group has got in each partition. It's the group's resume point.
- **Lag** is the distance between the newest event and the committed offset.
- **Retention** is how long events stay: time, size or, with **compaction**, the latest event per key.

Two neighbors from earlier modules:

- **9.4** chose between a bus, a queue and a log for pushing live updates to screens, where losing a message is survivable.
- **Module 10** covered work queues: jobs that any worker can take, acknowledged one at a time, where order doesn't matter.

This article is about the third job: a durable record of business events that several services each process fully, in order per entity, and can re-read.

## Recognizing the Problem

- Producers publish without a key, or with a key nobody chose deliberately.
- Someone has increased a topic's partition count to add throughput.
- Scaling a consumer out didn't reduce its lag.
- Logs mention consumers leaving the group, or `max.poll.interval.ms`, and duplicate side effects appear at the same time.
- One partition's lag climbs while the others stay flat.
- Lag alerts use a sum or an average, or count events rather than time.
- Error handlers catch and continue, with nowhere for the failed event to go.
- Nobody knows what a consumer does when its saved position has been deleted by retention.
- Consumers use auto-commit and process events asynchronously.

## How It Works

### The key decides the order

Kafka orders events within a partition, and nothing else. The producer computes `hash(key) mod partitions`, so the key is the unit of ordering:

- **Key by the entity whose events must stay in order.** Usually the aggregate ID, the same thing as the stream in 37.1a: the parcel ID here.
- **No key means no order.** Round-robin spreads load nicely and makes every consumer see events for one parcel in any order.
- **A key that's too coarse creates hot partitions.** Keying by depot keeps all of a depot's events in order, which nobody needed. The busiest depot's partition then gets six times the average traffic, and one consumer carries it.
- **Changing the partition count moves keys.** With 12 partitions, parcel `P-88` hashes to partition 5. With 48, it hashes to 29. Its old events are still being read from 5 while new ones arrive on 29, and a consumer can read 29 first. That's the November reordering. Kafka can add partitions but not remove them. The safe options are to choose the count generously at creation, or to create a new topic with the new count and move producers and consumers across deliberately.

On the producer side, Kafka's idempotent producer, on by default, stops retries from reordering or duplicating events within a partition (37.2a).

### Consumer groups: partitions cap parallelism

```
parcel-events (6 partitions)
 p0 p1 p2 p3 p4 p5
  │  │  │  │  │  │
  ├──┼──┼──┼──┼──┼──► group "billing":        c1: p0 p1   c2: p2 p3   c3: p4 p5
  │  │  │  │  │  │
  └──┴──┴──┴──┴──┴──► group "notifications":  c1..c6: one partition each
                                               c7, c8: idle, no partition to read
```

Within a group, consumers compete for partitions. Between groups, every event goes to every group. Two numbers follow:

- **A group can't use more consumers than there are partitions.** The partition count is a ceiling on parallelism set when the topic was created, and it's the first thing to check before scaling a consumer.
- **Throughput is roughly partitions × what one consumer does.** If notifications handles 150 events per second per consumer and peak is 4,000 per second, it needs at least 27 partitions. Leave headroom for next year's peak, because adding partitions later reorders keys.

When one consumer per partition still isn't enough, and the partition count can't sensibly grow:

- **Process different keys in parallel within a partition.** Events for different parcels in one partition don't depend on each other. Libraries such as Confluent's Parallel Consumer run them concurrently while keeping each key in order, and track which offsets are safe to commit.
- **Make each call cheaper.** Batch the SMS provider calls, or make them asynchronous with a bounded number in flight.
- **Use share groups when order doesn't matter.** Since Kafka 4.2, share groups let many consumers read the same partitions, with per-event acknowledgement and delivery counts, like a queue (Module 10). They're meant for events processed one at a time rather than as an ordered stream. That rules out billing, but could suit a "send receipt" worker.

### Committing: when is an event done?

The committed offset is the only record of progress, and it's per partition, not per event.

- **Commit after processing:** at-least-once. A crash repeats some events, so handlers must be idempotent (37.2a).
- **Commit before processing:** at-most-once. A crash loses events.
- **Auto-commit** commits on a timer during `poll`. With processing done synchronously inside the loop, that behaves like commit-after-processing. With processing handed to another thread, it commits events that haven't been handled yet, and a crash loses them. Turn it off for anything that matters and commit explicitly.

A committed offset is the next event to read, not the last one handled. Committing the handled offset instead of offset + 1 repeats one event per partition on every restart. It's harmless with idempotent handlers, and a sign nobody checked.

### Rebalances

When consumers join, leave, crash or miss their deadline, the group redistributes partitions. That's a **rebalance**. Partitions that move are re-read from their last committed offset, so any processed but uncommitted events are processed again.

- **The old protocol stopped the whole group.** Every consumer gave up every partition and waited while the group reassigned them. Cooperative rebalancing (Kafka 2.4) moved only the partitions that had to move, but still coordinated through the clients.
- **The newer protocol (KIP-848) is broker-driven and incremental.** It's been generally available since Kafka 4.0, enabled per consumer with `group.protocol=consumer`, and expected to become the default in 5.0. Consumers keep working on unaffected partitions throughout.
- **The slow-handler spiral** happens regardless of protocol. If a consumer doesn't call `poll` within `max.poll.interval.ms` (5 minutes by default), it's considered stuck and removed. The fix is to bound the work per poll: fewer events per poll (`max.poll.records`), a time budget for external calls, or pausing a partition while slow work finishes, so the consumer keeps polling. A consumer that stays in the group processes each event once; one that's repeatedly removed processes some events three times.
- **Commit on revocation.** A rebalance listener that commits finished work when partitions are taken away cuts down what the next owner repeats.
- **Static membership** (`group.instance.id`) lets a restarting pod come back without triggering a rebalance, which makes rolling deploys quiet.

### Lag is the health signal, per partition, in time

Lag in events is hard to interpret: 40,000 events is two seconds at peak and an hour overnight. Measure **lag in time**, meaning the age of the oldest event not yet committed, and alert on the **worst partition**, not the average.

The shape of lag tells you what's wrong:

- **All partitions rising together:** the group is too slow overall. Scale it, up to the partition count.
- **One partition rising, others flat:** that partition is stuck, on a poison event, a hot key or a hung consumer. Scaling won't help.
- **Lag in a sawtooth pattern, with repeated work:** rebalances.

### Failures in a log: you can't skip one event

In a work queue (10.2a), a failed message is set aside and the rest carry on. In a log, the committed offset is a single position per partition. There's no committing past event 5,001 while 5,000 is unresolved, unless you decide what happens to 5,000. Classify the error first (10.2a), because the two kinds need opposite handling:

- **Transient** (a database timeout, a provider's `503`): **block and retry in place.** Back off and retry the same event. The partition stalls, and ordering is preserved. It's the right choice when waiting will fix it, provided the lag alert fires while you wait.
- **Terminal** (a payload that can't be parsed, a violated invariant, a bug): **dead-letter it.** Publish the event to a **dead-letter topic** (`parcel-events.billing.dlt`) with the error, the original partition and offset, and the consumer's name in headers. Commit, and move on. Retrying a malformed weight won't fix it.

Dead-lettering breaks per-key order. If `Received` for parcel P-88 is dead-lettered, and `Delivered` for P-88 is processed afterwards, billing charges for a parcel it never registered. The fix is to **park the key**: after an event for P-88 is dead-lettered, send P-88's later events to the dead-letter topic too, until someone fixes and redrives them together. The partition keeps moving; only that one parcel waits.

Some teams add **delayed retry topics** between the main topic and the dead-letter topic (retry after 1 minute, then after 10) so transient errors don't block the partition. Spring Kafka supports this directly. It has the same ordering problem, fixed by the same key parking.

A dead-letter topic needs three more things, or it's just a slower way to lose data (10.2a):

- **An owner, and an alert whenever it isn't empty.**
- **A redrive tool** that fixes or re-publishes events to the main topic and clears their parked keys.
- **Handling for events that fail before your code runs.** A payload the deserializer can't read fails inside the client, so your handler's error handling never sees it. Consuming raw bytes and deserializing in your own code keeps that failure in the path that dead-letters.

### Retention, compaction, and consumers that fall off the end

Retention decides two things: how long a consumer can be down without losing events, and how far back a new consumer can start.

When a group's committed offset has been deleted by retention, the consumer's `auto.offset.reset` setting decides what happens:

- **`latest`** skips to new events. Everything in between is silently lost: the long weekend.
- **`earliest`** re-reads everything still retained. That's safe only if handlers are idempotent and replaying days of events is affordable.
- **`none`** fails with an error. For a consumer whose output matters, this is the right default. A human decides, instead of a config default nobody remembers.

Set retention longer than the longest outage you'd tolerate without intervention, a long weekend plus margin, and alert well before lag in time approaches retention. **Tiered storage**, which moves older log segments to object storage, makes weeks or months of retention affordable.

**Compacted topics** keep only the latest event for each key, forever, and delete a key when its latest event is a tombstone (a null value). A compacted `parcel-status` topic is effectively a table: a new service reads it from the start and gets the current status of every parcel without replaying months of scans. It's current state, not history. For history, use a normal topic with long retention, or an event store (37.1a).

### Choosing the backbone

| | Unit of order | Unit of parallelism | Replay | Failed messages |
|---|---|---|---|---|
| **Kafka** (and compatible) | partition, by key | partitions per group; share groups for queue-style use | yes, within retention | block, or a dead-letter topic you build |
| **NATS JetStream** | stream subject | consumers; per-message ack | yes | per-message redelivery with a maximum, then an advisory |
| **RabbitMQ** quorum queues / streams | queue / stream | consumers per queue | streams: yes; queues: no | per-message reject with a dead-letter exchange |
| **SNS → SQS** (AWS) | FIFO message group | consumers per queue | limited (SNS FIFO archiving) | per-message redrive to a dead-letter queue |
| **Google Pub/Sub** | ordering key | subscribers | seek to a timestamp or snapshot | per-message dead-letter topic |

The split that matters: **logs with partitions** give ordered, replayable, high-throughput streams, and make you handle failures and parallelism yourself. **Queues with per-message acknowledgement** handle failures and scaling one message at a time, and make ordering and replay the hard parts. Pick based on which of those your consumers need most.

## When It's Appropriate

- **Several independent services consume the same events,** each at its own pace. Four groups on `parcel-events` is exactly this.
- **Per-entity order matters,** as with `OutForDelivery` before `Delivered`, and the entity is a natural key.
- **Replay is needed,** by new services starting from history, rebuilt read models (37.1b) or reprocessing after a bug fix.
- **Volume is in the thousands of events per second or more,** where a database-backed queue starts to strain. 2 million parcels × about 8 scans each is roughly 16 million events a day, averaging about 185 per second and reaching several thousand at peak.

## When It's Unnecessary or Overkill

- **One consumer.** A work queue (Module 10), or the outbox table read directly by a worker, is simpler.
- **Dozens of events a minute.** A Postgres table with `SKIP LOCKED`, or an event store's subscriptions (37.1a), carries this with no new infrastructure.
- **Jobs, not events.** "Resize this image" is a task for any worker. Per-message acknowledgement and retries (Module 10, or share groups) fit it better than partitions.
- **Running Kafka yourself for a few hundred events per second.** A managed service, or a simpler broker, costs less than learning to operate brokers, partitions and upgrades in production.
- **Dead-letter topics before any consumer has a real terminal error.** Start with block-and-alert, and add dead-lettering when the first poison event shows up.

## Trade-offs

- **Partition count is hard to change.** Too few caps parallelism; adding more later reorders keys. The number is effectively a capacity plan fixed on the day the topic is created.
- **Order and parallelism pull against each other.** Every way past the partition cap either preserves per-key order with extra machinery, or gives order up.
- **One bad event can stop a partition.** Blocking protects order at the cost of a stall; dead-lettering keeps the partition moving at the cost of order, unless keys are parked.
- **Rebalances cause repeated work** and, in the worst case, spirals. Consumer timeouts and batch sizes become things to tune and monitor.
- **The backbone is shared infrastructure.** A noisy producer or a mis-sized topic affects every team that uses it, which needs ownership: topic naming, quotas, retention defaults.
- **Retention is a cost and a promise.** Longer retention costs storage and means consumers can come to depend on history being there.
- **Everything published becomes a contract** with consumers you may not know about (37.2c).

## Alternatives

- **Work queues** (Module 10, share groups): per-message acknowledgement and easy scaling, with no ordering or replay.
- **SNS fan-out to SQS queues:** one queue per consuming service, each with its own dead-letter queue and retries, with ordering per message group on FIFO queues. It suits AWS-hosted systems that don't need a long, replayable history.
- **Event store subscriptions** (37.1a): if events already live in an event store, each consumer can subscribe directly, with no broker in between.
- **The database as the backbone:** an outbox table that consumers poll with their own checkpoints. It's viable at low volume within one team, and it couples consumers to your database.
- **Direct calls:** the producer calls each consumer's API. It's simpler until one consumer is slow (36.3a).

## How to Achieve It

1. **Correct basics.** Key every event by its aggregate ID. Turn off auto-commit and commit after processing. Make every handler idempotent (37.2a). Set `auto.offset.reset=none` for consumers whose output matters.
2. **Size and observe.** Choose partition counts from peak throughput with headroom, and write down why. Alert on lag in time, for the worst partition. _Next when:_ the first poison event stalls a partition, or a slow dependency causes rebalances.
3. **Error handling.** Classify errors. Block and retry for transient ones; dead-letter topics with key parking for terminal ones. Deserialize in your own code. Build a redrive tool and give the dead-letter topics an owner.
4. **Rebalance hygiene.** Bound work per poll, commit on revocation, use static membership for rolling deploys, and move to the broker-driven protocol on Kafka 4.x. _Next when:_ a consumer needs more parallelism than its partitions allow.
5. **Beyond the partition cap.** Process keys in parallel within partitions, or move order-insensitive work to share groups. Increase partition counts only through a planned migration to a new topic.

## Implementation

Java, with the plain Kafka consumer. It's Kafka's reference client, and it shows every decision this article is about (polling, pausing, seeking and committing) as an explicit call instead of a framework annotation.

### Configuration that's chosen, not inherited

```java
Properties p = new Properties();
p.put("group.id", "billing");
p.put("group.protocol", "consumer");             // broker-driven incremental rebalances (Kafka 4.x)
p.put("group.instance.id", podName);             // static membership: restarts don't rebalance
p.put("enable.auto.commit", "false");            // commit after handling, explicitly
p.put("auto.offset.reset", "none");              // fail loudly if our position was deleted
p.put("max.poll.records", "100");                // bounded work per poll
p.put("key.deserializer",   StringDeserializer.class.getName());
p.put("value.deserializer", ByteArrayDeserializer.class.getName()); // parse in our own code
```

Each line corresponds to one of the incidents above. The byte-array deserializer is the least obvious. A malformed payload now reaches the handler as bytes and fails there, where it can be dead-lettered, instead of failing inside `poll` in a way the loop can't get past.

### The poll loop: block on transient errors, dead-letter terminal ones, park the key

```java
while (running) {
    ConsumerRecords<String, byte[]> batch = consumer.poll(Duration.ofMillis(500));
    backoff.resumeDue(consumer);                        // un-pause partitions whose wait is over

    for (TopicPartition tp : batch.partitions()) {
        long nextToCommit = -1;

        for (ConsumerRecord<String, byte[]> rec : batch.records(tp)) {
            try {
                if (parked.contains(rec.key())) {       // an earlier event for this parcel failed
                    deadLetter(rec, "key parked");
                } else {
                    billing.handle(ParcelEvent.parse(rec.value()), rec.key());
                }
                nextToCommit = rec.offset() + 1;        // the next offset to read, not this one
            } catch (TransientException e) {
                consumer.seek(tp, rec.offset());        // read this event again after the wait
                backoff.pause(consumer, tp, e);         // this partition waits; the rest continue
                break;
            } catch (Exception terminal) {              // bad data or a bug: waiting won't fix it
                deadLetter(rec, terminal);
                parked.add(rec.key());                  // later events for this parcel follow it
                nextToCommit = rec.offset() + 1;
            }
        }
        if (nextToCommit >= 0) {
            consumer.commitSync(Map.of(tp, new OffsetAndMetadata(nextToCommit)));
        }
    }
}
```

Four details make this safe:

- **`pause`, not `sleep`.** A paused partition returns no events, but the loop keeps calling `poll`, so the consumer stays in the group while it waits. Sleeping in the loop for a backoff is exactly how a consumer misses `max.poll.interval.ms` and starts the rebalance spiral.
- **`deadLetter` has to be confirmed before the commit.** It sends synchronously (`producer.send(...).get()`), with the original topic, partition, offset, key, consumer name and error in headers. Committing first and publishing afterwards is 37.2a's dual write again. In this order, a crash between the two produces a duplicate in the dead-letter topic, which is harmless.
- **`parked` has to survive restarts.** An in-memory set is forgotten on the next deploy, and P-88's `Delivered` would be billed while its `Received` sits in the dead-letter topic. Keep parked keys in a small table, or a compacted topic keyed by parcel ID, and have the redrive tool clear a key only after redriving all of that key's events in order.
- **A rebalance listener completes the picture.** In `onPartitionsRevoked`, commit whatever `nextToCommit` has reached, and drop pause state for partitions that are leaving. Without it, the next owner repeats up to a full batch.

A **Go** sibling with NATS JetStream would be worth writing, because per-message acknowledgement changes the poison-event story. Comparing the two shows the core trade: logs protect order and make you handle failure; queues handle failure and make you protect order. Not yet written.

---

Every log-based system chooses, for each consumer, what happens when one event can't be processed: wait, skip, or set it aside. Defaults make that choice silently, and the incidents above were all silent choices. Make it deliberately, for each consumer, before the first bad event arrives.
