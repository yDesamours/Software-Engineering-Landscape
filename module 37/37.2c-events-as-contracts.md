# Events as Contracts: Integration Events, Schemas and Registries

_Module 37.2c — Event-Driven Architecture_

## The Problem

Suppose you run an online grocery service. Customers book a delivery slot, fill a basket, and a warehouse team picks the order, substituting items that are out of stock. The `orders` service publishes events to Kafka. Six other services consume them: picking, payments, loyalty, marketing, the data warehouse, and customer notifications.

Early on, the orders team took the easy route: whenever an order changed, it serialized the `Order` entity to JSON and published it as `OrderUpdated`. Within a year there are four incidents.

**A refactor breaks five teams.** The orders team replaces a free-text `address` string with structured fields (`line1`, `postcode`, `geo`) for a new routing feature. It's an internal change; their tests pass. The next morning, marketing's segmentation job, the warehouse's delivery-area report and notifications' SMS templates all break. Two of those consumers were unknown to the orders team. Nobody had agreed to a contract, but five services depended on one.

**Eleven updates, no meaning.** An order changes about eleven times on its way through picking: items picked, substituted, weighed, repriced. Each change is another `OrderUpdated` carrying the whole order. Loyalty only wants to know when an order was delivered and what the customer paid, so it compares each `OrderUpdated` with the previous one and watches for `status` becoming `DELIVERED`. Then the orders team adds `PARTIALLY_DELIVERED`, for orders where a crate was left behind. Loyalty's comparison never sees `DELIVERED` for those orders, and 6% of customers stop earning points.

**The registry said it was compatible.** After the refactor incident, the teams adopt Avro and a schema registry. Months later, orders removes a field no longer used, `slotLegacyCode`. The registry accepts the change: its default rule, `BACKWARD`, allows removing fields. Orders deploys. Picking is still running the previous schema, in which `slotLegacyCode` is required and has no default. Every event fails to deserialize, and the warehouse stops receiving orders for 40 minutes on a Saturday morning.

**The address in nine places.** Every `OrderUpdated` carries the customer's name, address and phone number. A customer asks to be erased. Their data now sits in nine consumer databases, three analytics copies and a topic with 90-day retention.

Each incident is the same mistake seen from a different side: the orders team published its internal model instead of designing a contract.

## What It Is

An **event contract** is what a producer promises to consumers it may never meet:

- **Meaning:** which business fact the event states, in the business's words.
- **Schema:** its fields, their types and units, and how they're allowed to change.
- **Guarantees:** its key (what's ordered, 37.2b), how it's delivered (at least once, 37.2a), and how long it's kept.
- **Owner:** the team that answers for it and decides how it changes.

The distinction this article rests on: **domain events** are internal. They describe what happened inside a service's model, and they change whenever the model does (37.1b). **Integration events** are the deliberately designed subset that crosses service boundaries. A service translates domain events into integration events at its edge, the way an API translates internal objects into responses.

Two neighbors:

- **17.1b** designed payloads for webhooks sent to other companies: thin vs fat, envelopes, version guards. The same questions apply here, and its answers aren't repeated. What's different inside the company is scale and tooling: many internal consumers on shared topics, a registry that can enforce compatibility, and the ability to see who reads what.
- **33.1a** set out which changes break an API, and why a response can safely widen but not narrow. An event is always a "response": producers write, consumers read. Its rules apply, with one addition. Consumers also read old events from the log when they replay, so compatibility has to hold backwards across time as well as forwards across deploys.

## Recognizing the Problem

- A topic carries a serialized entity, and the event type is `SomethingUpdated`, `Changed` or `Saved`.
- Consumers compare consecutive events to work out what actually happened.
- An internal refactor needs another team's approval, or breaks them without warning.
- Nobody can list every consumer of a topic, or the fields each one reads.
- A registry is in place, and nobody knows which compatibility mode it enforces or why.
- Events contain names, addresses or phone numbers that most consumers never use.
- Event types sound like instructions (`SendWelcomeEmail`, `ReserveStock`), and the producer checks whether something happened afterwards.
- A shared library of event classes forces several services to deploy together.

## How It Works

### Translate at the edge: domain events in, integration events out

```
 orders service                                            topic: orders.v1
┌─────────────────────────────────────────────┐
│ domain events              translation      │
│  LineAdded            ──► (private)         │
│  LineRemoved          ──► (private)         │
│  ItemSubstituted      ──► ItemSubstituted ──┼──► picking, notifications
│  PickingCompleted     ──► OrderReadyToShip ─┼──► payments, notifications
│  DeliveryConfirmed    ──► OrderDelivered ───┼──► loyalty, payments, warehouse
│  AddressNormalized    ──► (private)         │
└─────────────────────────────────────────────┘      written via the outbox (37.2a)
```

Translation does three jobs:

- **It decides what's public.** Most domain events stay private. A basket's line-by-line churn before checkout is the orders team's business, not six other teams'.
- **It decouples shape.** The public event has its own schema, versioned deliberately, so the internal model can change freely. The address refactor would have changed one translation function and nothing else.
- **It can combine or split.** One public event may summarize several domain events, as `OrderDelivered` does for delivery confirmation plus final pricing.

Publishing integration events through the outbox (37.2a) keeps them consistent with the state change. The translation runs inside the same transaction, which is also a good reason to keep it cheap and free of side effects.

### Events state business facts

Name events as past-tense facts in the business's language: `OrderPlaced`, `ItemSubstituted`, `OrderDelivered`, `OrderCancelled`. Each type means one thing, and a consumer subscribes to the facts it cares about. Loyalty reads `OrderDelivered` and never needs to know what a status field looks like.

`OrderUpdated`, carrying the whole entity, publishes your table's change log. It forces every consumer to reconstruct meaning by comparing states, and each one reconstructs it slightly differently. When the producer adds a status, as `PARTIALLY_DELIVERED` showed, every one of those reconstructions is silently wrong.

**State transfer is legitimate when it's named as such.** Some consumers genuinely want current state, not facts: a search index of orders, or a warehouse table of order status. Give them a separate **state topic**, compacted and keyed by order ID, where each message is the full current public view of the order (37.2b). Name it so nobody mistakes it for a business event: `orders.state.v1`, next to `orders.v1`. Facts and state are two different contracts, and each is easier to keep when they're kept apart.

**Commands disguised as events** are the opposite mistake. `ReserveStock` published "as an event" by orders, with orders then waiting to see whether stock was reserved, is a request to the inventory service using the wrong channel. The test: **would the producer be fine if nobody listened?** `OrderPlaced` passes: orders did its job, and anyone may react. `ReserveStock` fails. Send it as a command to the service that owns it, through its API or its own queue, and expect a reply. When several services have to act in sequence and undo each other on failure, that's a saga (37.4a).

### What goes in, and what stays out

17.1b's reasoning applies: include what defines this fact, plus identifiers for everything else. Two internal considerations add to it:

- **Every field is a promise to consumers you haven't met.** Once something is in a published schema, removing it is a breaking change. Start small. Adding a field later is cheap; removing one never is.
- **Personal data goes everywhere the event goes,** and stays there for the topic's retention and every consumer's retention. Refer to the customer by ID. Put the address in the event only where a consumer truly needs it at that moment (the delivery route), and mark personal fields in the schema so data maps (34.1a) can find them. For fields that must travel and later be erasable, crypto-shredding (37.1b) applies here too.

### Schemas, formats and registries

A **schema registry** stores every version of every event schema. Producers register the schema they write; each message carries the schema's ID, and consumers fetch the matching schema to read it. On registration, the registry checks the new version against earlier ones under a **compatibility mode**, and rejects it if the check fails.

The modes, and which side must deploy first:

| Mode | What it guarantees | Allowed changes (Avro) | Deploy first |
|---|---|---|---|
| `BACKWARD` (the registry's default) | New readers can read data written with the previous schema | Remove fields; add fields with defaults | Consumers |
| `FORWARD` | Readers on the previous schema can read data written with the new one | Add fields; remove fields that had defaults | Producer |
| `FULL` | Both | Add or remove fields that have defaults | Either |
| `…_TRANSITIVE` | The same, checked against every earlier version, not just the last | | |

Read that table with the Saturday incident in mind. Producers of integration events almost always deploy on their own schedule, before their consumers. That needs `FORWARD`. The default, `BACKWARD`, protects the opposite direction: new consumers rewinding to read old data. That matters too, because logs are replayed (37.1b). An integration topic needs both directions, across all history, which is **`FULL_TRANSITIVE`**. It's strict: fields can only be added or removed if they have defaults. That strictness is what makes an event safe to publish to consumers you don't control.

Each format has its own traps:

- **Avro:** a field without a default can never be removed safely under `FULL`. Give fields defaults from the start, or accept that they're permanent. Adding a value to an **enum** fails on older readers unless their schema declared an enum default (supported since Avro 1.9). Declare one, such as `UNKNOWN`, in version 1.
- **Protobuf:** compatibility is by field number. Never reuse a number, and mark removed ones `reserved`. Unknown enum values survive as numbers in proto3, so readers must handle values they don't recognize.
- **JSON Schema:** whether adding a field is compatible depends on whether the schema allows additional properties. Closed schemas (`additionalProperties: false`) make every added field a breaking change for existing readers.

What no registry can check: **meaning.** Changing `amount` from euros to cents, reusing a status for something new, or starting to send `OrderDelivered` for partial deliveries all pass every compatibility check. 33.1a called this the part below the waterline. Treat semantic changes as breaking, and give them a new event type.

### Breaking changes: a new event, not a new shape

When a change can't be compatible, publish a new version alongside the old one instead of changing it in place:

1. Add `orders.v2` (or the `OrderPlaced.v2` type), and publish both versions from the same outbox transaction.
2. Consumers move across in their own time. Unlike HTTP API readers (33.2a), topic readers are visible: consumer groups and access permissions list exactly who still reads `orders.v1`.
3. When the last group has moved, stop publishing v1, then retire it after its retention period.

Dual publishing costs storage and some producer code for the migration period. It's the price of not coordinating six teams' deploys.

### Knowing who depends on what

- **Who reads a topic:** consumer groups and access control lists answer it. Require consumers to be granted access, and the list keeps itself.
- **Which fields they read:** nothing in Kafka records it. **Consumer-driven contract tests** close the gap. Each consumer states, in a test, which events and fields it relies on (Pact supports this for messages). The producer's build checks every consumer's expectations before merging. Removing `slotLegacyCode` would have failed that check, naming picking as the reason.
- **What exists:** a **catalog** of every topic, event type, owner, key, retention and personal-data marking. **AsyncAPI** is the standard format for describing event-driven interfaces, and tools such as EventCatalog turn those descriptions into a searchable site. Generate it from the registry and the repository, so it can't quietly drift from reality.

### A shared envelope

Agree once, across the company, on metadata that every event carries: event ID, type, source, time, subject, trace context (19.2b), tenant and actor. The **CloudEvents** standard defines these attributes and how they map onto Kafka message headers, which keeps the payload schema purely about the business fact. 17.1b covered CloudEvents for webhooks; inside the company, the argument for it is stronger, because every consumer and tool can rely on the same headers.

## When It's Appropriate

- **Translation and integration events** as soon as a second team consumes a service's events. Before that, the consumer can be told to wait for a real contract.
- **A schema registry** once there are several producers and consumers on shared topics, and a bad change could stop another team's service, as it did the warehouse. Compare: six consumers, three of them owned by other teams, and weekly deploys.
- **`FULL_TRANSITIVE`** for integration topics read by several teams and replayed. **`BACKWARD`** or **`FORWARD`** for a topic with one consumer owned by the same team, which can pick its deploy order.
- **Consumer-driven contract tests** when producers keep being surprised by consumers they didn't know about, or by the fields those consumers use.
- **A state topic** when several consumers keep local copies of an entity and would otherwise compare facts to rebuild it.

## When It's Unnecessary or Overkill

- **A registry for one producer and one consumer in one team.** A typed shared schema in the repository and a test that reads old samples (37.1b) do the same job.
- **Integration events inside one deployable.** Modules within a monolith can share domain events; the boundary that needs a contract is between independently deployed services.
- **`FULL_TRANSITIVE` on internal, short-lived topics** that are never replayed. The strictness buys nothing, and the default is fine.
- **A catalog platform before there are a dozen event types.** A README per topic, next to its schemas, is enough to start.
- **Contract tests between two services owned by the same team,** which change in the same pull request anyway.

## Trade-offs

- **Translation is code to write and maintain.** Every public event needs mapping, tests, documentation and an owner. It's the cost of being able to refactor freely.
- **Designing facts takes more thought than dumping state.** Someone has to decide what `OrderDelivered` means, including partial deliveries, before publishing it.
- **Strict compatibility slows change.** Under `FULL_TRANSITIVE`, removing a field is a migration project, not an edit.
- **Consumers still depend on meaning,** which no tool checks. Compatibility tooling can create false confidence.
- **Dual publishing during breaking changes** doubles traffic and storage for the migration period, and the old version lingers until the slowest consumer moves.
- **The registry becomes shared infrastructure.** If producers can't fetch or register schemas when it's down, it's on every write path. Clients cache schemas, but new schema versions can't be registered while it's unavailable.
- **Small events push work to consumers.** A consumer that needs data an event left out has to call the producer or keep its own copy (17.1b).

## Alternatives

- **A shared library of event classes.** Easy, and it couples every consumer's build and deploy to the producer's releases. It tends to turn into a distributed monolith (2.1).
- **JSON with documentation.** Works for a small number of teams with good habits, until the first undocumented change breaks someone.
- **APIs for queries, events only for notifications.** Consumers get a thin event and call the producer's API for details. The API carries the contract, and API versioning (33.1) handles change, at the cost of load on the producer.
- **Change data capture into a warehouse for analytics** (38.4). Analytics consumers often need tables, not events. Giving them CDC keeps business events small and free of reporting concerns.
- **Data products** in a data-mesh setup: a team publishes curated datasets for analytics with their own contracts, separate from operational events.

## How to Achieve It

1. **Stop publishing entities.** Add a translation layer, and start with the two or three facts consumers actually use. Keep `OrderUpdated` running alongside them for existing consumers, and get it on the deprecation path.
2. **Agree on the envelope and name the owner** of each topic. Write down, for each event, its meaning, key and retention. _Next when:_ more than one team produces or consumes events on shared topics.
3. **Add a registry,** with `FULL_TRANSITIVE` on integration topics, and a CI step that tests every schema change against the registry before merging. _Next when:_ producers are surprised by who reads which field.
4. **Add consumer-driven contract tests** for the busiest topics, and control access so consumer lists are accurate. Move entity snapshots onto state topics.
5. **Generate a catalog** (AsyncAPI) from the registry and the repositories. Put breaking changes through the new-version-and-dual-publish path, with retirement tracked by consumer group.

## Implementation

TypeScript. The translation layer benefits from TypeScript's mapped types: the compiler makes the producer decide, for every domain event, whether and how it's published. The schema and the CI check are plain Avro and HTTP.

### A translation the compiler won't let you skip

```ts
type OrderDomainEvent =
  | { type: "LineAdded"; orderId: string; sku: string; qty: number }
  | { type: "LineRemoved"; orderId: string; sku: string }
  | { type: "ItemSubstituted"; orderId: string; wanted: string; given: string; at: string }
  | { type: "DeliveryConfirmed"; orderId: string; customerId: string;
      deliveredLines: number; totalLines: number; paidMinor: number; currency: string; at: string }
  | { type: "AddressNormalized"; orderId: string; address: StructuredAddress };

// One entry per domain event type. Adding a type without an entry doesn't compile.
type Translation = {
  [K in OrderDomainEvent["type"]]:
    (e: Extract<OrderDomainEvent, { type: K }>) => IntegrationEvent[];
};

const toIntegration: Translation = {
  LineAdded: () => [],          // basket churn before checkout: private
  LineRemoved: () => [],
  AddressNormalized: () => [],  // an internal refactor, not a business fact

  ItemSubstituted: (e) => [{
    type: "orders.ItemSubstituted", version: 1, key: e.orderId,
    data: { orderId: e.orderId, requestedSku: e.wanted, substitutedSku: e.given, occurredAt: e.at },
  }],

  DeliveryConfirmed: (e) => [{
    type: "orders.OrderDelivered", version: 1, key: e.orderId,
    data: {
      orderId: e.orderId,
      customerId: e.customerId,   // a reference, not a name or an address
      completeness: e.deliveredLines === e.totalLines ? "COMPLETE" : "PARTIAL",
      paidMinor: e.paidMinor, currency: e.currency, occurredAt: e.at,
    },
  }],
};
```

Private events are written as explicit empty arrays, not left out. "We decided this isn't public" is then a visible line in a code review, not an accident of omission.

`completeness` is the `PARTIALLY_DELIVERED` lesson built into the contract. A partial delivery is still `OrderDelivered`, and the event says which kind it was. Loyalty decides what that means for points, instead of inferring it from a status it doesn't own.

### The schema, written to evolve

```json
{
  "type": "record", "name": "OrderDelivered", "namespace": "grocer.orders.v1",
  "fields": [
    { "name": "orderId",      "type": "string" },
    { "name": "customerId",   "type": "string" },
    { "name": "completeness", "type": { "type": "enum", "name": "Completeness",
        "symbols": ["UNKNOWN", "COMPLETE", "PARTIAL"], "default": "UNKNOWN" } },
    { "name": "paidMinor",    "type": "long" },
    { "name": "currency",     "type": "string" },
    { "name": "occurredAt",   "type": { "type": "long", "logicalType": "timestamp-millis" } },
    { "name": "deliveryWindow", "type": ["null", "DeliveryWindow"], "default": null }
  ]
}
```

Two choices here pay off later. The enum's `default` lets a future `RETURNED_AT_DOOR` value reach older readers as `UNKNOWN` instead of failing them. `deliveryWindow` was added in version 2 as an optional field with a default, which is compatible in both directions. `orderId`, `customerId` and `paidMinor` have no defaults, which makes them permanent under `FULL_TRANSITIVE`. That's intended: an `OrderDelivered` without them wouldn't mean anything.

### Checking compatibility before merging, not at deploy

```ts
// CI step: run for every changed schema file under schemas/
const subject = "orders.v1-grocer.orders.v1.OrderDelivered";
const registry = process.env.SCHEMA_REGISTRY_URL;

async function checkCompatible(schemaFile: string): Promise<void> {
  const res = await fetch(
    `${registry}/compatibility/subjects/${encodeURIComponent(subject)}/versions?verbose=true`,
    {
      method: "POST",
      headers: { "Content-Type": "application/vnd.schemaregistry.v1+json" },
      body: JSON.stringify({ schema: await readFile(schemaFile, "utf8") }),
    });
  const { is_compatible, messages } = await res.json();
  if (!is_compatible) {
    throw new Error(`${schemaFile} breaks existing readers:\n${messages.join("\n")}`);
  }
}
```

Posting to `/versions`, without a version number, checks the candidate against whatever the subject's mode requires: under a `…_TRANSITIVE` mode, every earlier version. It's the same check registration would run, moved from deploy time to pull-request time. On the Saturday of the incident, the registry did its job; it just did it at the moment of deploying, under the wrong mode. This moves both the check and the mode into review.

The mode itself is set once per subject (`PUT /config/{subject}` with `{"compatibility": "FULL_TRANSITIVE"}`), and belongs in infrastructure-as-code next to the topic's definition. A mode set by hand, or left at the default, is how the incident started.

## Further Reading

- **Martin Fowler, "What do you mean by 'Event-Driven'?"** (martinfowler.com, 2017). Separates event notification, event-carried state transfer, event sourcing and CQRS. The distinction between fact events and state topics comes from here.
- **Mathias Verraes, "Passive-Aggressive Events"** and related posts on event design (verraes.net). Short and precise on commands disguised as events.
- **Adam Bellemare, _Building Event-Driven Microservices_** (O'Reilly), the chapters on event design and schemas. Practical treatment of data contracts on Kafka.
- **Confluent documentation: "Schema Evolution and Compatibility"** and the Schema Registry API reference. The exact rules for each mode and format, including the note that `BACKWARD` is the default because it allows rewinding consumers.
- **Apache Avro specification:** schema resolution, and enum defaults.
- **Protocol Buffers documentation: "Updating a Message Type"** and `reserved` fields.
- **CloudEvents specification** and its Kafka protocol binding (CNCF).
- **AsyncAPI specification** (asyncapi.com), and **EventCatalog** for publishing a catalog from it.
- **Pact documentation: message pacts.** Consumer-driven contracts for asynchronous messages.
- **In this collection:** 17.1b (payload shape, envelopes, version guards), 33.1a (the compatibility contract), 33.2a (deprecation lifecycle), 34.1a (data maps), 37.1b (internal event versioning, crypto-shredding), 37.2a (the outbox), 37.2b (keys, compacted topics), 37.4a (sagas, for commands that need replies), 38.4 (CDC for analytics).

A **Java** sibling would be worth writing, around Spring Modulith's `@Externalized` events and Avro-generated classes. It shows the translation layer from the framework's side: which internal events become public, how they're mapped to generated schema classes, and the risk that a generated class makes the public schema feel like just another internal type to edit. Not yet written.

---

Every event you publish is an API whose callers you can't see and whose old responses stay in the log. Design it like one: say which fact it states, promise only what you're willing to keep, and check the promise before merging, not after the deploy.
