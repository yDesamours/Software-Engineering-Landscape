# Designing an Event Store: Streams, Expected Versions and Subscriptions

_Module 37.1a — Event-Driven Architecture_

## The Problem

Suppose you run gift cards and store credit for a retail chain: 1,400 stores plus a website. The history of a card is the product. Customers dispute balances ("where did my €50 go?"). Finance has to report outstanding liability at any past date. Unused balances fall under expiry rules that depend on exactly when each load and redemption happened. After reading 2.4, the team event-sources the `GiftCard` aggregate. A card's state is a fold over its events, and the store is one table:

```sql
CREATE TABLE events (
  id         bigserial PRIMARY KEY,
  card_id    text,
  type       text,
  data       jsonb,
  created_at timestamptz DEFAULT now()
);
```

A redemption loads the card's events, folds them into a balance, checks the balance, and inserts a `Redeemed` event. It ships. Four incidents follow over the next year.

**The double spend.** A customer redeems a card at a till and online in the same second. Both requests read a balance of €50. Both decide €40 is fine. Both insert. The card ends at −€30. It's rare until a fraud ring notices and scripts parallel redemptions against cards bought with stolen payment details: €18,000 over one weekend. The team had assumed that append-only meant no conflicts. An append-only log has exactly the same lost-update problem as `UPDATE`. It just loses the check instead of the value.

```
till:    read card (v3, €50) ── decide: redeem €40 ── append ✓
online:  read card (v3, €50) ── decide: redeem €40 ── append ✓
                                                        └─► balance −€30
```

**The retry that charged twice.** The team adds a version check (below), and the race is gone. Then a till's request times out during a network blip. The append had succeeded; only the response was lost. The till retries automatically, and the retry now fails with a version conflict, because the stream has moved on: its own first attempt moved it. The till shows "Redemption failed." The cashier presses redeem again, which is a new request, and it succeeds. The customer is charged twice.

**The stream everyone writes to.** A corporate customer buys a €500,000 program spread across 6,000 employee cards, with one rule: total spending can't exceed the budget. To enforce it, the team puts every card in the program into one stream, `program-8841`. In December, thousands of employees shop at once. Every append races every other append for the same stream version, most attempts conflict and retry, and tills see nine-second redemptions and timeouts.

**The report that's short.** Finance's liability report is a projection that reads `WHERE id > $checkpoint`. At month-end it disagrees with the sum of card balances by 0.01%, and the auditors ask why. It's the sequence-gap trap from 37.2a in a new place: a slow transaction's event got a lower ID, committed after the projection had moved past it, and was never read.

None of these are about event sourcing as an idea. Each one is a missing guarantee in the store.

## What It Is

An **event store** is a database built around four operations:

```
append(stream, expectedVersion, events)  → new version, or a conflict
read(stream, fromVersion)                → one stream's events, in order
readAll(fromPosition)                    → every event, in a stable global order
subscribe(fromPosition)                  → readAll, then keep going as new events commit
```

Every event has two numbers:

- A **stream version**: its place within its own stream (1, 2, 3...). Appends are checked against it, which is how decisions stay consistent.
- A **global position**: its place across all streams. Subscriptions track it, which is how projections and integrations see every event exactly where it belongs.

Getting the first number right prevents incidents one and two. Getting the second right prevents incident four. Stream design, meaning what goes in one stream, decides whether incident three happens.

Three neighbors look like event stores and aren't:

- **Kafka** stores events durably and in order, but it can't reject an append because a key has moved on since you read it. There's no expected version per key. Reading one card's history means scanning a partition shared with thousands of other cards. It's a good way to distribute events from a store, and a poor store for decisions.
- **An outbox table** (37.2a) holds notifications briefly until they're published. An event store holds the truth permanently.
- **An audit table** records what happened next to the real state. Nothing is rebuilt from it, so nothing breaks when it's incomplete.

## Recognizing the Problem

- Your events table has no unique constraint on (stream, version), or has no version column at all.
- Handlers load, decide and append, with nothing checking that the stream didn't change in between.
- A retried command can return an error for something that actually succeeded.
- One stream receives appends from many users at once, and conflict or retry counts rise with traffic.
- Projections track progress with `id > last` or a timestamp.
- A projection's totals drift slightly from the aggregates it's built from.
- After appending, code publishes to a broker in a separate step.
- Events don't record which command caused them, or when the business action actually happened, as opposed to when the row was written.

## How It Works

### Streams are consistency boundaries

A stream usually holds one aggregate instance: `giftcard-7F3K2`. The prefix before the dash is the stream's **category**, which subscriptions use to filter.

The stream is the unit that appends are checked against, so two rules follow:

- **Everything an invariant depends on must be in one stream.** "Balance can't go negative" needs every load and redemption for the card in the card's stream.
- **Everything in one stream is serialized.** Two decisions about the same stream can't both succeed if they started from the same version.

So size streams by invariants, not by nouns. This is the aggregate-sizing question from 2.3, and in an event store it has a direct performance cost.

Conflicts become the norm when appends arrive faster than a decision takes. Roughly: appends per second × seconds from read to append. The program stream in December saw about 40 redemptions per second with 50 ms from read to append. That's two decisions in flight at any moment, so most attempts conflict and retry, which makes each decision slower and conflicts more likely. A hot stream has four ways out:

- **Rethink the invariant.** Allocate each card an allowance from the budget. Redemptions check only their card's stream. The program stream only sees allocations, which are rare.
- **Reserve in chunks.** Each store or card claims budget in blocks of €500 and spends locally.
- **Make the limit soft.** Allow a small overspend and reconcile afterwards, if the business accepts that.
- **Serialize deliberately.** Route every command for the stream through one worker or a pessimistic lock. Conflicts go away and throughput is capped at one decision at a time.

Streams can also grow long. A card with ten years of history, or any stream with thousands of events, gets slow to load. Snapshots and "closing the books" into a new stream are covered in 37.1b.

### Expected version: optimistic concurrency on append

Every append says which version it decided against. If the stream is still at that version, the events are written at the next versions. If not, the append is rejected and nothing is written.

There are four common modes:

- **An exact version.** The normal case: "I read version 3."
- **No stream.** For creation. Two concurrent "issue card" commands for the same ID can't both succeed.
- **Stream exists.** Appends only if the stream is there, whatever its version.
- **Any.** No check at all. Only safe for events no decision depends on, such as attaching a note. It's the mode that quietly brings incident one back, so make it hard to reach for.

On a conflict, the right response is to reload, run the decision again against the new state, and append the new result. Retrying the same events blindly defeats the check: the second decision may have to be different, for example "insufficient balance."

In a relational database, the check can be a unique index on (stream, version). Two appends claiming version 4 of the same stream can't both commit, and the database decides which one wins.

### The unknown outcome, and idempotent commands

A timeout leaves the caller not knowing whether the append happened. With expected versions, a naive retry of a successful append gets a conflict, and a conflict looks like failure. That's incident two.

The fix is to give every command an ID, generated by the client (the till) and kept the same across retries. That's the idempotency key from 17.1. Record the command ID in each event's metadata. Then **check for it before deciding, not at append time.** If the stream already contains events caused by this command, return the recorded outcome instead of deciding again. The order matters: a retry that decides first will decide against the balance its own first attempt already reduced, and may refuse something that actually succeeded.

The stream is the natural place to deduplicate, because the command's result lives there permanently. There's no separate table with a retention window to get wrong. Unique event IDs derived from the command ID add a second check at the database, and dedicated stores such as KurrentDB detect a retried append carrying the same event IDs themselves.

### Two positions, and why the global one is hard

```
stream giftcard-A:   v1 ────────── v2 ──────────────── v3
stream giftcard-B:          v1 ────────── v2
global position:     1      2      3      4            5
```

Stream versions are easy: the append check assigns them. Global positions are hard because many streams append concurrently, and a subscription needs an order with one property: **nothing ever appears behind a position the subscriber has already passed.** In a relational database, a sequence doesn't provide that. Positions are assigned when rows are inserted, and rows become visible when they commit (37.2a). There are four ways around it:

- **Serialize appends.** Take one lock for every append, so commit order equals position order. It's simple and correct, and it caps the store at one append at a time. Depending on commit latency, that's a few hundred to a couple of thousand appends per second, which is plenty for many systems.
- **Order by transaction ID, and read only behind the oldest open transaction.** Postgres can record each row's transaction ID (`pg_current_xact_id()`) and report the oldest transaction still running (`pg_snapshot_xmin(pg_current_snapshot())`). Subscribers read events from transactions older than that, ordered by (transaction ID, position). A transaction below that line has finished, so no event can later appear there. Appends stay concurrent. The cost is that any long transaction anywhere in the database, such as a slow report or a session left idle in a transaction, holds back every subscription until it ends.
- **Detect gaps and wait.** When a reader sees a missing position, it waits briefly for that transaction to commit or roll back, then moves past it. It's simple, but a transaction that commits after the wait is skipped for good: incident four, made rarer.
- **Use a single-writer log.** Dedicated stores like KurrentDB write every event through one ordered log, so the problem doesn't exist.

### Subscriptions

A **catch-up subscription** reads from its saved position through history, then keeps going as new events commit. Rebuilding a projection and running it live use the same code, which is what makes replay (37.1b) manageable.

Where the checkpoint is saved decides the delivery guarantee:

- **The projection's tables are in the same database as the store.** Save the checkpoint in the same transaction as the projection's writes. Each event is applied exactly once, with no inbox needed.
- **The projection lives elsewhere,** such as a search index or a cache. Save the checkpoint after the write succeeds. A crash in between repeats events, so writes must be idempotent: upsert keyed by stream, and ignore versions older than the one stored (37.2a).

Each subscriber keeps its own checkpoint, so a slow projection doesn't hold back the others. Watch lag per subscriber, not per store. An event a projection can't handle stops that projection at that position. Parking it and moving on puts a known error in the read model, so alert either way.

**Competing consumers** spread one subscription over several workers for throughput, and lose ordering unless events are routed by stream, so all of one card's events go to the same worker. KurrentDB's persistent subscriptions offer strategies that pin streams to workers. Most projections don't need this. A single worker per projection is simpler and usually fast enough.

**Filtering** by category or event type lets a projection read only `giftcard-*` streams, or only `Redeemed` events, without scanning everything.

**The store is its own outbox.** Publishing to Kafka for other services is one more subscription with its own checkpoint, at-least-once, and consumers deduplicate on event ID. The dual write from 37.2a never happens, because there was only ever one write.

### What each event carries

Settle the envelope early, because events written without a field never get it:

- **Event ID**, stream ID, stream version and global position.
- **Type**, with a version, such as `GiftCardRedeemed.v1`. How types evolve is 37.1b.
- **Data**: the business facts.
- **Command ID**: what caused this, and the key for idempotent retries.
- **Correlation and causation IDs**: which user action this belongs to, and which command or event directly caused it. These let you trace a chain of reactions across streams.
- **Actor and tenant.**
- **Recorded at vs occurred at.** When the store wrote the event, and when the business action happened. A till that was offline for three hours syncs its redemptions late. Liability and expiry rules care about when the customer paid, not when the row arrived.

### Where the store lives

| Option | Fits when | Watch for |
|---|---|---|
| **Tables in your Postgres**, hand-built | One to a few event-sourced aggregates, and projections in the same database | You own concurrency, global ordering and subscription code |
| **A library on Postgres**: Marten (.NET), Emmett (Node), Message DB | The same, without writing the store yourself | Each library's ordering and gap-handling choices; read them |
| **A dedicated store**: KurrentDB, Axon Server | Event sourcing is the main storage model across services, with many long-lived subscriptions | Another database to run and back up |
| **DynamoDB with conditional writes** | You're on AWS and want managed, per-stream appends | A condition on (stream, version) gives the append check, but DynamoDB Streams only orders per key, so a global subscription order needs building |
| **Kafka alone** | Rarely | No per-key expected version, and reading one stream means scanning a partition |

## When It's Appropriate

This article assumes the decision to event-source was already made, for the reasons in 2.4. The question here is what the store needs to guarantee, and where to build it.

- **Build on your existing Postgres** when one or a few aggregates are event-sourced, appends are in the hundreds to low thousands per second, the team already runs Postgres, and most projections can live in the same database with exactly-once checkpoints. The gift-card ledger is this case: about 60 redemptions per second at peak, spread across millions of card streams.
- **Use a library** when you'd otherwise write the store yourself, and one exists for your stack.
- **Adopt a dedicated store** when event sourcing spans several services, dozens of subscriptions need to be managed, positioned and filtered server-side, or append rates outgrow a serialized relational store.

## When It's Unnecessary or Overkill

- **Building a store for a system that shouldn't be event-sourced.** 2.4's cheaper answers (an audit table, temporal tables, CDC) come first.
- **A general-purpose event-store framework before there's a second aggregate.** Write the dozen lines one aggregate needs. Generalize when a second one arrives with different needs.
- **Global-ordering machinery with no cross-stream reader.** If every read is "load this stream," and nothing subscribes across streams, per-stream versions are enough. That's rarely true for long, since reporting always wants a projection.
- **Transaction-ID ordering at 20 appends per second.** Serialize appends and stop there.
- **A dedicated store for one aggregate.** It's another database with its own backups, upgrades, monitoring and on-call knowledge.

## Trade-offs

- **Stream boundaries are hard to move.** They fix both what can be enforced and what contends. Changing them later means migrating events into new streams, for data that is meant to be immutable.
- **Global ordering costs something whichever way you build it:** throughput with a single lock, stalls behind long transactions with transaction-ID ordering, and rare skipped events with gap timeouts.
- **Subscriptions are processes to operate.** Each has a checkpoint, a lag, and a way to get stuck on one event.
- **Current state is only queryable through projections.** "Which cards have more than €100 and haven't been used this year?" is a question for a read model, not for the store.
- **Stream names and event type names are forever.** Whatever you call things in the first month is in the log for good.
- **A hand-built store is infrastructure you own,** including tests that prove concurrent appends really conflict and subscribers really see every event. These bugs don't show up in single-user testing.
- **Storage only grows.** Archiving old streams and erasing personal data inside immutable events need designing (34.1a, and 37.1b for archiving).

## Alternatives

- **State stored normally, with an outbox** (37.2a). Current state in tables, integration events published reliably, and history through an audit table. It covers most of what teams want from event sourcing, at a fraction of the cost.
- **Pessimistic locking per stream.** `SELECT ... FOR UPDATE` on a streams row before deciding. No conflicts or retries, at the cost of holding a lock while deciding. It suits hot streams better than optimistic appends do.
- **Kafka as the log, with a separate state store.** Commands are validated against a state store, and events are published to Kafka as the record. Without a per-key append check, the validation and the append can disagree under concurrency, so it needs a single writer per key, usually a Kafka Streams application partitioned by that key.
- **A managed event store** (Kurrent Cloud, Axon Server's hosted offering). Someone else runs the database; your design problems stay the same.

## How to Achieve It

1. **One table, one aggregate, correct appends.** An events table with a unique (stream, version) constraint and a unique event ID. An append function with expected versions, a handler that reloads and decides again on conflict, and serialized appends for global order. Projections in the same database, with checkpoints saved in the same transaction. _Next when:_ it's in production, and clients retry.
2. **Idempotent commands.** Command IDs from the client, recorded in metadata, checked before deciding. _Next when:_ the envelope needs to hold more than the first version did.
3. **Settle the envelope.** Correlation, causation, actor, tenant, recorded-at and occurred-at, while there are still only a few months of events without them.
4. **Operate the subscriptions.** Lag per subscriber, alerts, and a policy for events a projection can't handle. _Next when:_ serialized appends limit throughput, or lock waits show up in append latency.
5. **Scale the ordering, or the store.** Switch to transaction-ID ordering, with `idle_in_transaction_session_timeout` set and an alert on subscription lag. When event sourcing spreads across services, or subscriptions become a platform of their own, move to a dedicated store. Many systems stop at step 4.

## Implementation

TypeScript with node-postgres. Nearly all the correctness is in two SQL details: a unique index that is the concurrency check, and a `WHERE` clause that makes global order safe. TypeScript keeps the code around them short, and continues the event model and fold from 2.4.

### The tables

```sql
CREATE TABLE events (
  global_position bigserial   PRIMARY KEY,
  tx_id           xid8        NOT NULL DEFAULT pg_current_xact_id(),
  stream_id       text        NOT NULL,
  stream_version  bigint      NOT NULL,
  event_id        uuid        NOT NULL UNIQUE,
  type            text        NOT NULL,
  data            jsonb       NOT NULL,
  metadata        jsonb       NOT NULL,  -- commandId, correlationId, actor, occurredAt...
  recorded_at     timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT one_event_per_version UNIQUE (stream_id, stream_version)
);
CREATE INDEX events_in_commit_safe_order ON events (tx_id, global_position);

CREATE TABLE checkpoints (
  subscriber      text   PRIMARY KEY,
  tx_id           xid8   NOT NULL DEFAULT '0',
  global_position bigint NOT NULL DEFAULT 0
);
```

The `UNIQUE (stream_id, stream_version)` constraint is the whole optimistic-concurrency mechanism. Everything else in `append` just translates its errors.

### Appending with an expected version

```ts
type ExpectedVersion = number | "no_stream"; // no "any": make skipping the check hard

export class WrongExpectedVersion extends Error {}

export async function append(
  streamId: string, expected: ExpectedVersion, events: NewEvent[],
): Promise<number> {
  const from = expected === "no_stream" ? 0 : expected;
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    for (const [i, e] of events.entries()) {
      await client.query(
        `INSERT INTO events (stream_id, stream_version, event_id, type, data, metadata)
         VALUES ($1, $2, $3, $4, $5, $6)`,
        [streamId, from + i + 1, e.id, e.type, e.data, e.metadata],
      );
    }
    await client.query("COMMIT");
    return from + events.length;
  } catch (err) {
    await client.query("ROLLBACK");
    if (isUniqueViolation(err, "one_event_per_version")) {
      throw new WrongExpectedVersion(`${streamId} moved past ${expected}`);
    }
    throw err;
  } finally {
    client.release();
  }
}
```

`"no_stream"` needs no special case. Inserting version 1 fails if any version 1 exists.

The index catches a stale expected version, not an invented one. A caller that passes 7 for a stream at version 3 would write version 8 and leave a hole. Expected versions should only ever come from a read. A `max(stream_version)` check inside the transaction turns that convention into a guarantee.

### The command handler

```ts
export async function redeem(cmd: RedeemCard): Promise<void> {
  const streamId = `giftcard-${cmd.cardId}`;

  for (let attempt = 1; ; attempt++) {
    const history = await readStream(streamId);

    // A retry of a command that already succeeded: report success, don't decide again.
    if (history.some((e) => e.metadata.commandId === cmd.commandId)) return;

    const state = history.reduce(evolve, EMPTY); // the fold from 2.4
    const newEvents = decide(state, cmd);        // throws InsufficientBalance, CardFrozen...

    try {
      await append(streamId, history.length, envelope(newEvents, cmd));
      return;
    } catch (err) {
      if (!(err instanceof WrongExpectedVersion) || attempt === 3) throw err;
      // Another redemption got there first. Reload and decide against the new balance.
    }
  }
}
```

That handler covers all three decision-side incidents:

- **The double spend** becomes a conflict. The second redemption reloads, sees €10, and `decide` refuses it.
- **The till's automatic retry** finds its own command ID in the stream and returns success. The command ID has to come from the till and stay the same across retries. An ID generated by the server per request can't recognize anything.
- **The program stream's pressure** shows up here first, as the conflict branch running hot. A metric on that branch warns you before tills time out.

`history.length` is the expected version only because versions start at 1 and have no gaps. Once snapshots arrive in 37.1b, it becomes the snapshot's version plus the events read after it.

### A catch-up subscription

```ts
export async function runProjection(name: string, apply: Apply): Promise<never> {
  for (;;) {
    const applied = await withTransaction(async (tx) => {
      const cp = await tx.one(
        `SELECT tx_id, global_position FROM checkpoints WHERE subscriber = $1 FOR UPDATE`,
        [name]);

      const batch = await tx.many(
        `SELECT * FROM events
          WHERE (tx_id, global_position) > ($1::xid8, $2)
            AND tx_id < pg_snapshot_xmin(pg_current_snapshot())
          ORDER BY tx_id, global_position
          LIMIT 500`,
        [cp.tx_id, cp.global_position]);

      for (const e of batch) await apply(tx, e); // writes the read model in this transaction

      const last = batch.at(-1);
      if (last) {
        await tx.none(
          `UPDATE checkpoints SET tx_id = $2, global_position = $3 WHERE subscriber = $1`,
          [name, last.tx_id, last.global_position]);
      }
      return batch.length;
    });
    if (applied === 0) await sleep(200);
  }
}
```

The `tx_id < pg_snapshot_xmin(...)` condition is what prevents incident four. It only reads events from transactions that have already finished, so nothing can later appear behind the checkpoint. That's why ordering is by (transaction ID, position) rather than by position alone.

The read-model writes and the checkpoint update commit together, so each event is applied exactly once. A crash rolls both back, and the batch runs again from the same checkpoint. `FOR UPDATE` on the checkpoint row means a second copy of the same projection waits instead of applying the batch twice.

The cost is the one from How It Works: a long-running transaction anywhere in the database holds `pg_snapshot_xmin` back, and every subscription stops advancing until it ends. Set `idle_in_transaction_session_timeout`, keep reporting queries on a replica, and alert on subscription lag, since that's how this shows up.

## Further Reading

- **Kurrent documentation (KurrentDB, formerly EventStoreDB):** the pages on appending events (expected revisions and idempotence), catch-up subscriptions and persistent subscriptions. The clearest description of what a purpose-built store guarantees, useful even if you build on Postgres.
- **Marten documentation, the event store and async daemon sections.** A mature Postgres-backed store, with a detailed account of how it tracks a high-water mark and handles gaps.
- **Message DB documentation** (the Eventide project). A small Postgres message store whose `write_message` function with an expected version is worth reading in full; it's short.
- **Oskar Dudycz, event-driven.io.** Practical posts on optimistic concurrency in event stores and on Postgres sequence gaps and global ordering; he maintains the Emmett library.
- **Martin Kleppmann, _Designing Data-Intensive Applications_,** chapter 7 (lost updates and compare-and-set, the family expected versions belong to) and chapter 11 (logs as a basis for derived data).
- **Vaughn Vernon, "Effective Aggregate Design," part 1.** Sizing consistency boundaries, which is the same decision as sizing streams.
- **PostgreSQL documentation:** `xid8`, `pg_current_xact_id()`, `pg_current_snapshot()` and `pg_snapshot_xmin()`, and `idle_in_transaction_session_timeout`.
- **Amazon DynamoDB documentation: condition expressions.** The per-stream append check on a managed key-value store.
- **In this collection:** 2.3 (aggregate boundaries), 2.4 (the fold, and whether to event-source at all), 17.1 (idempotency keys), 37.2a (the outbox, sequence gaps, idempotent consumers), 37.1b (versioning, snapshots, replay).

A **Java** sibling with the Axon Framework would be worth writing. Axon loads aggregates, checks sequence numbers and runs tracking event processors for you. Those processors split one subscription into segments by aggregate identifier, which parallelizes a projection while keeping each aggregate's events in order. That's the competing-consumers problem above, solved by the framework, and a useful look at what it decides on your behalf. Not yet written.

---

An append-only log doesn't remove concurrency. It moves it to one question per write: which version did you decide against? The store's job is to make every write answer that question, and every reader able to trust the order the answers arrive in.
