# Who's Asking? Connecting the Help Desk to Your Product

_Module 27.1a — Customer Support Integration_

## The Problem

Suppose you run payroll software for small businesses. About 3,000 employers use it. Support is eight agents, three of them an outsourced overnight team, working in a hosted help desk that takes email and runs a chat widget inside the product. Nobody designed the connection between the help desk and the product. It grew, one reasonable shortcut at a time.

**Email in, guesswork out.** A ticket arrives from `dana.k@gmail.com`: "Payroll didn't run for two people this week." The help desk knows the address and nothing else. The agent searches the admin tool by email and finds nothing, because Dana logs in with her work address. About 30% of tickets look like this. Bookkeepers are worse: one bookkeeper manages payroll for 14 employers, so her address matches 14 accounts. The first reply to a third of all tickets is some version of "Which company is this about?", and the median ticket needs three exchanges before anyone starts on the actual problem.

**The nightly field sync.** To help, an engineer writes a cron job that copies 38 attributes per employer onto the help desk's organization records: plan, monthly revenue, employee count, last payroll total, bank account last four, owner phone, and so on. It works for a while. Then:

- A customer upgrades at 10:00. At 14:00 an agent sees "Basic" on the ticket and tells them the feature they're asking about isn't on their plan.
- The overnight contractors are restricted in the admin tool to non-financial views (26.3a). In the help desk they see every employer's payroll totals, because the help desk has its own, much simpler, permission model.
- An employer closes their account and asks for erasure. The erasure run (24.4) clears the product and the backups. The help desk still has the 38 fields and two years of tickets, some with pay stubs attached.

**The chat widget's identity.** The widget is started from the browser with `chat.identify({ email: user.email, name: user.name })`. A security researcher reports that anyone can open developer tools, call `identify` with someone else's email, and load that person's conversation history, including a screenshot of an employee's pay stub. Worse, the agent sees the conversation as coming from the account owner. A week before the report, someone had used exactly this to ask an agent to change an employer's deposit account. It was only caught because the agent happened to follow the callback procedure.

**The sidebar with one key.** An engineer builds a help-desk sidebar app that shows the account summary and has an "Extend trial" button. It calls the admin API with a single service key stored in the app's settings. Every agent, including the contractors, now has whatever that key can do. The audit log records every action as `helpdesk-integration`. When 40 trials are extended by mistake one evening, nobody can say who clicked.

Each failure is an unanswered question the connection should have answered:

1. **Who is this person, and which account is this about?** And how sure are we?
2. **What should the agent see, and how fresh must it be?** And who else ends up holding a copy?
3. **When the agent does something from the ticket, who is acting?**

## What It Is

This is **help-desk integration**: connecting a hosted ticketing or conversation system to your product so that each conversation is attached to a known person and account, with a recorded level of trust, and agents get product context and actions without leaving the ticket.

The organizing idea is a split of ownership. **The help desk owns conversations**: messages, assignment, queues, response-time targets, macros. **Your product owns everything about the customer**: accounts, entitlements, personal data, and the operations that change them. The integration is the seam between them, and most of its failures come from one side quietly taking over the other's job. The 38-field sync made the help desk a second, stale, poorly protected customer database. The shared-key sidebar made it a second admin tool with none of the first one's controls.

The integration isn't a replacement for the admin surface from Module 26. It's a client of it, with the same permissions, the same named operations and the same audit trail, shown in a different place.

## Recognizing the Problem

- The first reply to many tickets asks which account or company the customer means.
- Agents keep four tabs open (help desk, admin, billing provider, logs) and copy account IDs between them.
- Customer data in the help desk disagrees with the product, and agents have learned which one to trust.
- The in-app chat identifies users with values set in browser JavaScript and never checked by your server.
- Your help desk holds fields that your own admin tool would mask or restrict for the same agent.
- Nobody has checked whether erasure requests reach the help desk.
- Actions taken from a help-desk app show up in your audit log as a service account.
- Routing rules ("enterprise customers go to the priority queue") depend on an agent reading the ticket first, because the help desk doesn't know the plan.

## How It Works

There are four seams: identity coming in, context going to the agent, actions coming back, and events flowing between the systems.

### 1. Identity: claimed versus verified

Every channel gives you some statement about who's writing. The question is who vouches for it.

- **Email** gives you a sender address. It's a claim. Mail authentication (SPF, DKIM, DMARC) makes forging a domain harder, but it doesn't tell you the person controls a login in your product, and most help desks don't enforce it on inbound mail anyway.
- **Phone** gives you a number and whatever the caller says.
- **The in-app widget and logged-in web forms** can give you a verified identity, because the person has already signed in to your product. But only if your server says so. Anything set in browser JavaScript is still a claim, just one that looks official.

Verification in the widget works by having your server sign a short-lived token saying who the user is, and giving it to the widget. The help desk checks the signature with a secret or key it shares with you. Values the user can edit in the browser can't produce a valid signature.

```
Browser                 Your server                  Help desk
   │  signed-in session      │                           │
   ├───── GET /chat-token ──►│                           │
   │                         │ sign {user_id, account_id,│
   │◄──── short-lived JWT ───┤       exp: 10 min}        │
   │                                                     │
   ├──────── widget.login(jwt) ─────────────────────────►│ verify signature
   │                                                     │ → "verified user 8812,
   │◄──────── that user's history only ──────────────────┤    account 4417"
```

Three details matter more than the mechanism.

**Identify by stable internal ID, not email.** Emails change and get reused. A person who leaves a company and whose address is reassigned would otherwise inherit their conversation history.

**Include the account the user is looking at.** The bookkeeper with 14 employers is signed in to one of them when she opens chat. Put that account in the token and the "which company?" question disappears for every in-app conversation.

**Record the trust level on the ticket.** A ticket is `verified` (signed token), `claimed-matched` (email matches exactly one user), `claimed-ambiguous` (matches several) or `unknown`. The trust level then drives what the agent may do. Reading public help content is fine for anyone. Discussing account details needs a match. Changing bank details, contact emails or who can log in needs verification. For a claimed ticket that asks for something sensitive, the answer is a verification step, such as a link that opens the product and confirms the request from inside a signed-in session, instead of the agent judging how convincing the email sounds.

### 2. Context: push what rules need, pull what people read

There are two ways to get product data in front of an agent, and they're good at different things.

**Push** copies fields into the help desk's own records (user and organization fields). The help desk can then act on them without a human: route enterprise tickets to a priority queue, apply a four-hour response target to paid plans, flag customers whose payment is failing. Pushed data is stale by however long your sync takes, lives in the vendor's system under the vendor's permission model, and is one more place erasure has to reach.

**Pull** fetches data when an agent opens the ticket, through a sidebar app that calls your API. It's fresh, it goes through your permission checks, it isn't stored in the vendor's system, and you can show anything the admin tool can show. But automation can't use it, because nothing exists until a person looks.

The usual answer is both, with a strict rule for which goes where:

```
            PUSH (few fields, on change)            PULL (live, per view)
            ─────────────────────────────           ──────────────────────────
  who uses  help-desk rules & automation            the agent reading the ticket
  examples  account_id, plan_tier, region,          payroll status, recent runs,
            sla_class, in_dunning                   employees, entitlements, errors
  freshness seconds (event-driven)                  now
  lives in  vendor + you                            you only
  guarded   vendor roles                            your permissions (26.3a)
```

Pushed fields should be the handful that automation genuinely needs, sent when they change (an event on plan change or payment failure) rather than nightly, and chosen so they're low-sensitivity. `plan_tier: "growth"` is fine to hold in a vendor's system. Last payroll total isn't, and no routing rule needs it. Every pushed field also goes on the list your erasure process works through.

### 3. Actions: the agent acts, not the integration

Anything the agent can do from the ticket (extend a trial, resend an invite, open impersonation) should be the same named operation the admin tool uses (26.1a), called as the agent.

That needs a chain of identity: the help desk tells your API which agent is looking, and your API maps that agent to a staff identity it already knows. The cleanest version has both the help desk and your admin tool sign staff in through the same identity provider, so "agent 391 in the help desk" and "staff member priya@" are provably the same person, and offboarding one offboards both. Your API then applies your permissions, not the help desk's roles. The overnight contractor sees in the sidebar exactly what she'd see in the admin tool, because it's the same check.

The ticket also becomes useful as a scope. Ticket-scoped access from 26.3a ("you may see this account because you have an open ticket from it") falls out naturally: the sidebar request carries the ticket ID, your API checks that the ticket belongs to that account, and the ticket ID is recorded as the reason on every read and action. Deep links out of the ticket, into the full customer view or into impersonation (26.1b), carry the same ticket reference.

### 4. Events in both directions

The help desk can notify you when tickets are created, updated and solved, usually via webhooks. Those events belong on the account timeline (26.2a) and feed health signals: three open tickets and a failing payment in the same week is a different account from one with neither. Handle them as any inbound webhook (Module 17): check the signature, expect duplicates and out-of-order delivery, and store the ticket ID rather than copies of the messages.

Your product can also write to the help desk: add an internal note when a payroll run fails for an account that has an open ticket, or tag tickets linked to a known incident. Linking many tickets to one engineering issue, and closing the loop when it's fixed, is its own problem and gets 27.1b.

## When It's Appropriate

- **Hundreds of tickets a week** and a measurable share of agent time spent finding the account. At 400 tickets a week, two minutes of lookup each is more than 13 agent-hours.
- **People who belong to several accounts**: bookkeepers, agencies, consultants, parent companies. Email matching can't work for them.
- **An in-app widget that shows conversation history** or lets users discuss account details. Verified identity is required from day one here. It's a security control, not a convenience.
- **Tiered service**, where response targets or queues depend on plan or contract. That's what pushed routing fields are for.
- **Agents with different access levels**, especially outsourced teams, where the help desk's permission model is too coarse to be where access is decided.
- **Regulated or sensitive data** (payroll, health, finance), where every copy in a vendor's system is an access, retention and erasure obligation.

## When It's Unnecessary or Overkill

- **Twenty tickets a week, answered by the people who built the product.** They know the customers. A saved admin search by email is enough.
- **A sidebar that duplicates the admin tool.** If agents live in the admin tool anyway and the help desk is just an inbox, a deep link from ticket to admin, carrying the ticket ID, gets most of the value for an afternoon's work.
- **Pushing everything "in case it's useful".** If no rule uses a field, it shouldn't be pushed. Pushing it only creates a stale, leaky copy.
- **Building your own help desk** to avoid integration work. Assignment, queues, response targets, email threading, satisfaction surveys and reporting are a product in themselves. Owning conversations is rarely the part that makes your product different.

The one piece that isn't optional at any size: **if the widget shows history or accepts account-changing requests, identity must be verified server-side.**

## Trade-offs

- **The sidebar fails when you do.** A pulled sidebar depends on your API being up, and ticket volume peaks exactly when your product is down. Design the degraded state: pushed fields, the account ID, and a link that works once the admin tool is back.
- **Verification only covers signed-in users.** Visitors on the pricing page and users locked out of their accounts, a large share of urgent tickets, are still unverified. You need an explicit, slower path for them, and agents need to recognize which path they're on.
- **Two identity systems to keep aligned.** Mapping help-desk agents to staff identities is another single sign-on integration, and ideally automated provisioning (SCIM). Without it, an offboarded contractor can keep a working help-desk seat that still reaches your API.
- **Every pushed field is an obligation in someone else's system.** It needs masking, retention rules and erasure. The vendor's permission model is usually coarser than yours, so a field in the help desk is effectively visible to every agent.
- **Coupling to the vendor.** Routing rules keyed on your fields, sidebar apps built on the vendor's app framework, and webhook formats all make switching help desks a project. Keeping logic on your side (your API decides; the sidebar just displays) limits this.
- **Secrets that break things when rotated.** The widget signing secret and webhook secrets need rotation, and rotating naively logs every chat user out or drops events. Support two secrets during a changeover.
- **Latency on every ticket view.** A sidebar that makes six calls to assemble the account view makes agents wait each time they open a ticket. One purpose-built summary endpoint beats reusing six admin endpoints.

## Alternatives

**Link-only integration.** Tickets carry the account ID and a link into the admin tool, and agents work there. It needs no sidebar, no agent-identity chain and no pushed data beyond the ID. It's slower for agents but has far fewer moving parts, and it's often the right first step and sometimes the right last one.

**The vendor's off-the-shelf connectors.** Most help desks have apps that sync from a CRM or billing provider. They're fine for push-only routing fields from those systems. They don't know your product's state (why payroll didn't run) and can't call your operations as the agent.

**One vendor for help desk and CRM.** Platforms that combine support with sales and success tooling reduce the number of seams between vendors. They don't remove the seam that matters most here, the one between conversations and your product's data.

**Support inside the product.** Building messaging into your own app keeps all data in your systems and makes identity trivial. It's worth considering only when conversations are tightly bound to product objects (support threads attached to a specific payroll run, say) and you're prepared to rebuild what help desks already provide.

## How to Achieve It

**L0 — Account ID on every ticket where you know it, plus a deep link to the admin tool.** Set by the widget, by exact email matches, or by the agent. *Signal to move on:* agents still asking "which company?" on in-app conversations.

**L1 — Verified widget identity, with user ID and current account in a server-signed token.** Record the trust level on the ticket. If the widget already shows history, this is a security fix: do it before anything else. *Signal:* sensitive requests arriving by email that agents can't safely handle.

**L2 — Trust-level rules and a verification path.** Sensitive changes require a verified ticket; claimed tickets get a link that confirms the request from inside the product. *Signal:* routing that depends on an agent reading the ticket first.

**L3 — A small set of pushed routing fields, sent on change.** Plan tier, region, service level, payment status. At the same time, remove any wide sync that already exists and add the help desk to the erasure process. *Signal:* agents keeping the admin tool open next to every ticket.

**L4 — A read-only sidebar that pulls a summary, called as the agent, scoped to the ticket.** Your permissions decide what it shows. *Signal:* the same few actions requested from engineers or done by switching tabs.

**L5 — Actions in the sidebar through named operations,** recorded with the agent as actor and the ticket as reason. Ticket events flow back onto the account timeline. *Signal:* many tickets about the same underlying bug, which is where 27.1b starts.

## Implementation

TypeScript on Node, using the `jose` library for JWTs. Two pieces carry the idea: a server-signed identity for the widget, and a sidebar endpoint that acts as the agent rather than as the integration. Claim names below are illustrative; each help desk documents the exact claims and signing algorithm it expects.

**Signing the widget identity:**

```ts
import { SignJWT } from "jose";

const key = new TextEncoder().encode(process.env.CHAT_SIGNING_SECRET!);

// Called from the signed-in app. The session, not the request body,
// decides who the user is.
app.get("/chat-token", requireSession, async (req, res) => {
  const { user, currentAccount } = req.session;

  const token = await new SignJWT({
    external_id: user.id,          // stable internal ID, not email
    email: user.email,             // display only
    account_id: currentAccount.id, // the account they're looking at
    name: user.displayName,
  })
    .setProtectedHeader({ alg: "HS256", kid: process.env.CHAT_KEY_ID! })
    .setIssuedAt()
    .setExpirationTime("10m")
    .sign(key);

  res.json({ token });
});
```

> **Aside — where the old bug lived.** The original `chat.identify({ email })` ran entirely in the browser, so the user controlled every value. Here the only thing the browser controls is whether it asks for a token. It can't change what the token says. Two quieter traps: the signing secret must never ship in front-end code, which sounds obvious until a build step inlines every `process.env` value; and the `kid` header is what lets you run two secrets during a rotation without logging everyone out.

**The sidebar endpoint, acting as the agent:**

```ts
import { jwtVerify } from "jose";

app.get("/support/sidebar", async (req, res) => {
  // 1. The help desk vouches for which agent and which ticket.
  const { payload } = await jwtVerify(bearer(req), helpdeskKey, {
    issuer: HELPDESK_ISSUER, audience: "payroll-sidebar",
  });
  const agentId = String(payload.agent_id);
  const ticketId = String(payload.ticket_id);

  // 2. Map the agent to a staff identity we manage (same IdP, SCIM-provisioned).
  const staff = await staffDirectory.byHelpdeskAgent(agentId);
  if (!staff?.active) return res.status(403).end();

  // 3. The account comes from our record of the ticket, set when it was
  //    verified or matched — never from a query parameter.
  const ticket = await tickets.get(ticketId);
  if (!ticket?.accountId) return res.json({ state: "unmatched", trust: ticket?.trust });

  // 4. Same permission check and data-class masking as the admin tool,
  //    with the ticket as scope and reason (26.3a).
  const ctx = { actor: staff, reason: { kind: "ticket", id: ticketId } };
  await authorize(ctx, "account.summary.read", { accountId: ticket.accountId, ticketId });

  const summary = await supportSummary(ctx, ticket.accountId); // one purpose-built read
  res.json({ state: "ok", trust: ticket.trust, summary });
});
```

> **Aside — the shared-key version.** The earlier sidebar skipped steps 1 and 2 and called the admin API with one service key. That turns every agent into the most privileged agent, and every audit entry into "the integration". A subtler version of the same mistake is to verify the help desk's token but take `account_id` from the sidebar's query string. Any agent could then read any account by editing a URL, regardless of which ticket is open. Tie the account to the ticket, and the ticket to how its identity was established.

Actions follow the same shape: verify, map the agent, authorize against the ticket's account, then call the named operation from 26.1a with `ctx`, so the audit entry names the person and the ticket.

## Further Reading

- **Zendesk developer documentation**, particularly authenticating end users in messaging (signed JWTs for the widget) and the Zendesk Apps Framework for sidebar apps, including how apps make authenticated requests to your servers.
- **Intercom's documentation on Messenger security and identity verification**, a clear account of why browser-supplied identity must be backed by a server-generated signature or token.
- **RFC 7519 (JSON Web Token) and RFC 8725 (JWT Best Current Practices).** The second covers algorithm confusion, audience and issuer checks, and key handling, all of which apply directly to the two tokens above.
- **OWASP Top 10, A01: Broken Access Control**, for the "account ID from the query string" class of bug, and the **OWASP Authentication Cheat Sheet** for account recovery paths, which is where unverified support channels usually get attacked.
- **RFC 8693 (OAuth 2.0 Token Exchange)**, the standard way to turn "the help desk says agent 391" into a token your API trusts as that staff member, if a signed request per call isn't enough.
- **SCIM (RFC 7643 and 7644)**, for provisioning and deprovisioning agent identities from one place.
- Within this map: authentication in **4**, webhooks and signatures in **17**, erasure and audit logs in **24.4**, named operations and masking in **26.1a**, impersonation in **26.1b**, the account timeline in **26.2a**, ticket-scoped permissions in **26.3a**, privacy obligations in **34**, and escalation to engineering in **27.1b**.

A **Java** sibling would be worth writing on the agent-identity chain. With Spring Security and Spring Authorization Server, the sidebar request can be turned into a proper token exchange: the help desk's assertion goes in, a short-lived token for the staff member comes out, and every downstream admin service checks that token with its usual resource-server configuration. That shows how "acting as the agent" extends past one endpoint into a set of services, which the single TypeScript handler above hides. Not yet written.

---

The habit to take from this: **every place a customer can reach you is an authentication boundary, including the ones staffed by people.** When you add a support channel, ask who vouches for the identity arriving through it, and make the answer visible to the person who has to act on it.
