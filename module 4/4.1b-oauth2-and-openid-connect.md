# Delegated Identity: OAuth 2.0 and OpenID Connect

_Module 4.1 — Authentication & Authorization_

## The Problem

You're building a scheduling tool. Point it at a team, it reads everyone's calendar and proposes the meeting slots that are actually free. To do that, it needs to read each person's Google Calendar.

The direct approach is a form with two fields: Google email, Google password. The user types them in, you store them, and a worker logs into Google as that person and pulls the calendar.

Count what just became true.

**You are holding a credential that grants everything.** You wanted read access to calendars. You received the ability to read their email, download their Drive, see their photos, spend money with their saved cards, and change the password to lock them out of their own life. There is no dial on a password.

**You must store it reversibly.** Passwords are supposed to be hashed with something slow and one-way (Module 4.2). You can't do that here, because you have to replay the original. Encrypted at rest is the best available answer, and the key is on the same machine. Your database is now a pile of working Google passwords, which makes you a far more attractive target than your product alone would justify.

**Google cannot tell you apart from the user.** Every action is logged as the user. If your worker goes haywire and deletes a thousand events, the audit trail says the user did it.

**The user cannot revoke you specifically.** Their only lever is changing the Google password, which signs them out of every device they own and does nothing about the window before they think to do it.

**And it doesn't work anyway.** The account has MFA, so your login gets challenged. Google sees a sign-in from a datacenter IP in a region the user has never visited and blocks it. The whole design falls over on contact with a provider that takes security seriously — which is every provider now.

```
  PASSWORD SHARING                          DELEGATION
  user ──password──► your app               user ──password──► Google
                        │                                        │  "Allow Acme Scheduler
                        ▼                                        ▼   to view your calendar?"
                     Google                       your app ◄──scoped token──┘

  your app can do anything,                 your app can read calendars only,
  forever, indistinguishable                until revoked, attributably,
  from the user                             and never saw the password
```

What's needed is a way for a user to hand a third party a **narrow, revocable, attributable** slice of their account — without that third party ever touching the credential.

### The second problem, which looks like the first

Separately, you'd like users to sign into *your* app with a "Continue with Google" button. Not because you want their calendar, but because you'd rather not run password infrastructure at all: no storage, no reset emails, no credential-stuffing defence, no breach liability.

These two problems feel like one problem. They are not, and the distance between them is where a specific, serious class of bug lives. The first asks for *access to a resource*. The second asks for *an assertion about who someone is*. One protocol does the first. A layer on top does the second. Conflating them was the industry's default mistake for about five years.

## What It Is

**OAuth 2.0** is a framework for delegated authorization: a user grants an application limited access to their account at some other service, without sharing credentials with that application.

It names four roles, and keeping them straight makes everything else legible:

| role | who that is in the calendar example |
|---|---|
| **resource owner** | the user whose calendar it is |
| **client** | your scheduling app |
| **authorization server** | Google's login and consent system — issues tokens |
| **resource server** | the Google Calendar API — accepts tokens |

The authorization server and the resource server are often the same company and almost never the same service. Splitting them in your head is what lets you see that "where you log in" and "what the token opens" are separate concerns, which is the whole reason a token can be scoped.

**OpenID Connect (OIDC)** is a thin standard layer on top of OAuth 2.0 that adds identity. Its addition is the **ID token**: a signed JWT, addressed specifically to your application, that says *this provider authenticated this user, at this time, in response to your request*.

### The confusion that matters

**OAuth is not authentication, and an access token is not a login.**

An access token means "the bearer may read this calendar." It doesn't say who the bearer is. Critically, it doesn't say *who it was issued to*. So if your login works by "accept whatever access token I'm handed and call the provider's `/userinfo` endpoint with it," then any other application the user ever authorized holds a credential that logs into your app as that user. A malicious app collects tokens legitimately, replays them at your callback, and becomes your users. This is the token-substitution attack, and it's not exotic — it's the natural consequence of using a credential that carries no audience as if it were an assertion.

The ID token fixes exactly this. It has an `aud` claim containing *your* client id and a `nonce` tying it to *your* request. A token minted for someone else fails verification.

So:

- **ID token** — for you, the client. Proves identity. Verify it, read it, then throw it away.
- **Access token** — for the resource server. Opens an API. Never inspect it for identity; often it's opaque and there's nothing to inspect.

Sending an ID token to an API as a bearer credential, or deriving identity from an access token, are the two halves of the same misunderstanding, and both appear in production constantly.

## Recognizing the Problem

- You have a form asking for a password to a service you don't operate.
- There's a column called something like `provider_password`, encrypted, with a decrypt on the read path.
- You want login but don't want to own password storage, reset flows, breach notification, or credential-stuffing defence.
- A prospect's security questionnaire asks "do you support SSO?" and you don't know whether they mean SAML or OIDC. (They mean "against our Okta/Entra tenant," and they'll accept either.)
- An enterprise customer asks what happens to access when they fire someone, and your answer is "they should tell us."
- You run three first-party apps and users log into each one separately.
- Your customers' integrations use API keys that are long-lived, all-powerful, and pasted into a Zapier config.
- Someone proposed "just use OAuth" for your own SPA calling your own API, and nobody could say what it would improve.
- You call `/userinfo` with an access token to decide who is logging in.
- A partner wants to act on behalf of your users, and the current answer is that they ask users for their password.

## How It Works

### The authorization code flow

This is the flow. Everything else in OAuth is a variation for a client type that can't do this one.

```
 browser                      your server               authorization server
   │ 1. click "Connect Google"    │                              │
   │─────────────────────────────►│                              │
   │ 2. 302 → /authorize?client_id=…&redirect_uri=…&scope=…      │
   │         &state=…&nonce=…&code_challenge=…                   │
   │◄─────────────────────────────┤                              │
   │ 3. log in, see consent screen ─────────────────────────────►│
   │ 4. 302 → https://you/callback?code=abc&state=…              │
   │◄────────────────────────────────────────────────────────────┤
   │ 5. GET /callback?code=abc    │                              │
   │─────────────────────────────►│ 6. POST /token               │
   │                              │    code + client_secret + code_verifier
   │                              │─────────────────────────────►│
   │                              │ 7. { access_token, refresh_token, id_token }
   │                              │◄─────────────────────────────┤
   │ 8. Set-Cookie: your session  │                              │
   │◄─────────────────────────────┤                              │

        ── front channel: the browser, visible, tamperable ──
        ══ back channel: server to server, TLS, authenticated ══
```

The single most important structural fact: steps 2–5 happen in the **front channel**, through a browser the user controls and an attacker may influence. Step 6 happens in the **back channel**, directly between your server and the provider.

That's why the `code` exists. The valuable thing — the token — never travels through the browser. What travels through the browser is a short-lived, single-use voucher that is worthless without the client secret (or PKCE verifier) held on your server. Early OAuth had a flow that skipped this and returned the token directly in the URL fragment; it's deprecated now, because tokens in URLs end up in browser history, server logs, and `Referer` headers.

### Each parameter is a defence

Nothing in that URL is decoration. Each one closes a specific attack:

- **`state`** — an unguessable value you generate, stash, and check on return. Without it, an attacker can complete their own authorization, capture the resulting `code`, and feed it to a logged-in victim's browser — silently linking the *attacker's* Google account to the *victim's* account on your app. From then on the attacker logs in as the victim. This is login CSRF, and skipping `state` is the most common OAuth implementation bug.
- **`redirect_uri`** — registered in advance, matched exactly by the provider. Loose matching plus any open redirect on your domain equals code exfiltration.
- **`code`** — single use, valid for seconds to a minute. Replay it and the provider should revoke the whole grant.
- **PKCE** (`code_challenge` / `code_verifier`) — you send a hash on the way out and the preimage on the exchange. If someone intercepts the code, they still can't exchange it. Invented for mobile apps, where the "client secret" is in a binary anyone can download, and now recommended for every client type including confidential server-side ones.
- **`nonce`** — you generate it, it's echoed inside the ID token, you check it matches. Stops a previously captured ID token being replayed at your callback.

### Confidential and public clients

A server-side app can hold a secret. Anything shipped to the user — a single-page app, a mobile binary, a desktop app — cannot, no matter how well you obfuscate it. That distinction is called *confidential* versus *public*, and it determines whether you're issued a client secret and whether PKCE is optional or the only thing protecting you.

It's also the argument for the **backend-for-frontend** pattern: rather than have your SPA hold tokens in browser storage where any script can reach them, let a small server component of yours do the flow, hold the tokens, and give the browser an ordinary session cookie. The SPA then never handles a token at all.

### Scopes and consent

The scope string is what makes delegation narrow: `calendar.readonly` rather than "everything." Two things to internalise about scopes.

They are **defined by the provider, not by you**, and they're coarse — a handful of buckets, not your permission model. Scopes answer "what part of the provider's API may this token touch." They do not answer "may this user edit this document in my app." That's Module 4.3, and it stays yours.

And sensitive scopes come with **process**. Google's restricted scopes require a security assessment before you can go past a small user cap. That's a schedule item measured in weeks, discovered by many teams the week before launch.

### Verifying the ID token

Signature against the provider's JWKS; `iss` matches the expected issuer; `aud` contains your client id; `exp` is in the future; `nonce` matches what you sent. A library does this — but only if you tell it who you are, so it's worth knowing what it's checking.

Then, from the claims: **`sub` is the identifier, not `email`.** `sub` is stable and unique within that issuer. Email addresses get changed, reassigned inside companies, and — on some providers — asserted without verification. Your identity table's unique key is the pair `(issuer, subject)`. Using email instead is the second-most-common mistake in this article, and it's an account-takeover bug rather than a mere inconvenience: if a provider lets someone claim an unverified address, and you link on email, they inherit the matching account.

### Refresh tokens and offline access

If you only wanted login, you're done at the ID token — discard everything else. If you need to call the provider's API later, when the user isn't present, you need a refresh token, and providers gate this deliberately. Google issues one only when you ask for offline access and force a consent prompt; some providers rotate them on every use; some expire them after a period of inactivity; some invalidate them when the user changes their password. There is no portable answer, which is why every provider integration accumulates a small file of notes.

### The other grants, and when they show up

- **Client credentials** — no user involved at all. A service authenticates as itself and gets a token. This is what people mean by "our microservices use OAuth," and it's a different problem from everything above.
- **Device authorization grant** — for TVs, CLIs, and anything without a usable browser: display a short code, have the user enter it on their phone, poll until they do.
- **Token exchange** — swap one token for a narrower or differently-audienced one, so a service acting on a user's behalf downstream doesn't forward a token meant for it.
- **Resource owner password credentials** — the app collects the password and trades it for a token. This is the anti-pattern from the top of this article wearing a protocol's clothes. It's deprecated. Don't.

### Discovery

Providers publish `/.well-known/openid-configuration`: endpoints, supported scopes, signing algorithms, and the JWKS URL. This is why a generic library can integrate with a provider it's never heard of given one URL and a client id, and why key rotation at the provider doesn't require a deploy on your side.

## When It's Appropriate

- **A user's data lives at another provider and you need it.** Calendar, email, repositories, payment history, ad accounts. There is no alternative and there shouldn't be — every serious provider has closed the password path.
- **You'd rather not operate password infrastructure.** Storage, reset flows, breach response, credential stuffing, MFA, and the social-engineering surface of account recovery all become the provider's problem. For a small team this is a genuine reduction in what you're on the hook for.
- **Enterprise B2B sales.** The buyer's security team requires that access be controlled from their identity provider, and the compelling part isn't login — it's *deprovisioning*. When someone is terminated in the HR system, access to your product ends, without a support ticket. That's a purchasing requirement you'll meet sooner than you expect.
- **Several first-party applications, one identity.** A web app, a mobile app, and an admin console against one authorization server: sign in once, and the identity is defined in one place.
- **You're exposing an API to third parties.** Integrations get scoped, expiring, individually revocable tokens instead of static keys that do everything forever.
- **Machine-to-machine credentials you want centrally managed.** Client credentials gives short-lived, scoped, revocable service identities instead of a shared secret in twelve environment files.

## When It's Unnecessary or Overkill

**Your own SPA talking to your own API on your own domain.** Running the full dance between two components you control, both deployed by you, adds redirects, browser token storage, refresh logic, and a new class of security bug — to replace a session cookie that already worked. "We use OAuth internally" frequently decodes to "we reimplemented sessions with more moving parts and worse revocation." If you want the structure anyway, use a backend-for-frontend so the browser still just holds a cookie.

**Standing up your own authorization server for one application and 300 users.** You've taken on consent UI, client registration, token endpoints, key rotation, and a component attackers specifically enjoy — to serve one client that could have used a session.

**Client credentials inside a service mesh that already does mTLS.** The mesh gives every service a cryptographic identity for free, verified at the transport layer. Adding a token dance on top buys you scopes you probably aren't enforcing.

**Five social providers at launch.** Each is an integration with its own quirks, its own account-linking case, and its own support path. Pick one, or start with none and add the one your users actually ask for.

**Using scopes as your permission system.** They're too coarse and they're not yours. Your authorization model stays in your application.

## Trade-offs

- **You no longer own the front door.** If the provider is down, nobody signs in — including your support team trying to help. If the provider changes policy, deprecates an API, suspends your app pending review, or decides your use of a scope now needs an audit, that's your roadmap now.
- **Account linking becomes a permanent product problem.** One human, three identities: a Google login, a password account, and a corporate SSO identity, all with the same email. Link them automatically and you've built a takeover path through weak email verification. Don't link them and you get duplicate accounts, missing data, and a support queue. There is no design that avoids the question — only designs that answer it deliberately.
- **Support burden moves rather than disappearing.** "I signed up with Google and now password reset says there's no account." Someone has to handle that, in the UI and in a help doc.
- **OAuth is a framework, not a protocol.** Providers differ on refresh-token behaviour, `sub` stability, whether email is returned, whether logout does anything, and how strictly `redirect_uri` is matched. Every integration accrues quirks, and "we're standards-compliant" doesn't mean interchangeable.
- **Session lifetime is now negotiated between two systems.** The user signs out of Google; your session continues, because it's yours. Front-channel and back-channel logout specs exist and are unevenly implemented. The revocation-window question from the previous article comes back one level up, now with a party you don't control on the other side.
- **Redirects are in your critical login path**, including on mobile, where handing off to a system browser and back is the least reliable part of the experience.
- **Privacy and disclosure.** The provider learns when each of your users signs in. In some markets and some verticals, that's a compliance conversation.
- **Lock-in at the identity layer is unusually sticky.** Hosted identity providers price per monthly active user, which scales with your success, and migrating means re-establishing an identity mapping for every user you have.
- **Implementation mistakes are account takeovers, not degradations.** A missing `state` check, a wildcard `redirect_uri`, an unverified ID token — each is full compromise of arbitrary accounts. This is one of the places where "use the well-maintained library, don't write it from the spec" is straightforwardly correct advice.

## Alternatives

First, the neighbours people mix up with this, since they all involve logging in somewhere else:

- **SAML 2.0** is the older federation standard: XML assertions, browser POST bindings, certificates exchanged out of band. Conceptually it's the same shape — an identity provider signs an assertion your service provider verifies — with worse ergonomics and deeper roots in enterprise IT. If you sell to large organizations you will eventually implement both, because some customers' IdPs are configured by people who have done SAML for fifteen years.
- **"Social login," "SSO," and "federation"** are not three mechanisms. Social login is OIDC with a consumer provider. Enterprise SSO is OIDC or SAML with a workforce provider. Federation is the general name for the arrangement. The machinery is the same; what differs is who runs the identity provider and what they're contractually obliged to do.

And the genuinely different approaches to the same problem:

- **Own the password yourself**, hashed properly (Module 4.2). Still a legitimate choice, especially consumer-facing, where a hard dependency on a third party for every login is a real availability decision.
- **Passwordless: magic links, passkeys, WebAuthn.** Removes the password without introducing a third-party dependency on the identity itself. Covered next in this module.
- **API keys** for machine clients. Simple, understood, and fine when the client is a script with a narrow job — as long as you can scope and rotate them.
- **Mutual TLS** for service-to-service identity inside infrastructure you control.
- **Buy, self-host, or build the authorization server.** Hosted (Auth0, Okta, Entra ID, Cognito, Clerk) trades per-user cost and lock-in for not operating it. Self-hosted (Keycloak, Ory, Zitadel) trades operational burden for control, and makes identity a tier-0 service you're now on call for. Building it is justified roughly when identity is your product.
- **An enterprise SSO broker** (WorkOS and similar). One integration on your side, N customer identity providers on theirs, including the SAML ones. For a small team facing per-customer SSO configuration, this is usually the honest answer — the work isn't the protocol, it's the long tail of customer IT departments.

## How to Achieve It

**Level 0 — password login, with the right data model.** Don't defer this. From day one, split `users` from `identities`:

```
users(id, …)
identities(id, user_id, issuer, subject, email, email_verified, UNIQUE(issuer, subject))
```

A local password is just one row with `issuer = 'local'`. Retrofitting this later means a migration across every account while people are logging in; adding it now costs one table. Same cheap-hedge logic as the tenant column in Module 1.1.
*Signal you skipped it:* your users table has a `google_id` column, and someone is about to propose `github_id`.

**Level 1 — add one OIDC provider.** Authorization code flow with PKCE, a maintained library, exact redirect URIs, verified state and nonce. Decide the linking rule explicitly and write it down: link to an existing account only when `email_verified` is true and the email matches, otherwise create a new account or ask the user to confirm.
*Signal:* measurable drop-off at the password field, or one enterprise prospect.

**Level 2 — make linking a first-class feature.** A settings page listing connected identities, with add and remove, and a rule that you can't remove the last remaining way to sign in. Tell the user at sign-in time which method they used before, rather than letting them discover it through a failed reset.
*Signal:* the first duplicate-account ticket, which arrives about two weeks after level 1.

**Level 3 — per-tenant enterprise SSO.** Route by email domain to a tenant-specific connection; support OIDC and SAML; add SCIM so provisioning and deprovisioning are automatic; decide whether SSO is *enforced* for a domain, because "SSO available but password still works" satisfies nobody's security review. Budget for the fact that this is per-customer configuration work forever, and consider a broker before deciding it's a week of work.
*Signal:* a security questionnaire with a mandatory SSO row.

**Level 4 — become an authorization server.** Third parties act on your users' behalf: client registration, consent screens, scope design, token and revocation endpoints, and a security posture appropriate to a component whose compromise is everyone's compromise. Use a proven implementation.
*Signal:* partners asking for integration, or a public API with an app marketplace.

## Implementation

Go, because `golang.org/x/oauth2` with `go-oidc` keeps every step visible — no framework absorbs the flow into configuration, so the parameters and the checks stay where you can see them.

### Setup

```go
// Discovery: fetches /.well-known/openid-configuration and caches the JWKS.
provider, err := oidc.NewProvider(ctx, "https://accounts.google.com")

conf := &oauth2.Config{
    ClientID:     os.Getenv("GOOGLE_CLIENT_ID"),
    ClientSecret: os.Getenv("GOOGLE_CLIENT_SECRET"),
    Endpoint:     provider.Endpoint(),
    RedirectURL:  "https://app.example.com/auth/google/callback",
    Scopes:       []string{oidc.ScopeOpenID, "email", "profile"},
}

// The verifier is configured with OUR client id — that's the aud check.
verifier := provider.Verifier(&oidc.Config{ClientID: conf.ClientID})
```

### Starting the flow

```go
func start(w http.ResponseWriter, r *http.Request) {
    state := randString(32)
    nonce := randString(32)
    pkce  := oauth2.GenerateVerifier()

    // Short-lived, HttpOnly, Secure, SameSite=Lax, ~10 minutes.
    setTempCookie(w, "oidc_state", state)
    setTempCookie(w, "oidc_nonce", nonce)
    setTempCookie(w, "oidc_pkce", pkce)

    http.Redirect(w, r, conf.AuthCodeURL(state,
        oidc.Nonce(nonce),
        oauth2.S256ChallengeOption(pkce),
    ), http.StatusFound)
}
```

Those three values have to survive a round trip through the provider and come back to a *different request* — possibly, in a load-balanced deployment, to a different instance. Holding them in a process-local map works perfectly in development and fails intermittently in production, which is the same lesson as level 1 of the previous article, arriving five minutes into a different feature. Signed short-lived cookies or a shared store; never process memory.

### The callback

```go
func callback(w http.ResponseWriter, r *http.Request) {
    stateCookie, err := r.Cookie("oidc_state")
    if err != nil || stateCookie.Value != r.URL.Query().Get("state") {
        http.Error(w, "invalid state", http.StatusBadRequest)
        return  // ← skipping this is login CSRF: attacker links their identity to this session
    }
    pkce, _ := r.Cookie("oidc_pkce")

    // Back channel. The client secret never touched the browser.
    tok, err := conf.Exchange(r.Context(), r.URL.Query().Get("code"),
        oauth2.VerifierOption(pkce.Value))
    if err != nil { http.Error(w, "exchange failed", 502); return }

    rawIDToken, ok := tok.Extra("id_token").(string)
    if !ok { http.Error(w, "no id_token", 502); return }

    // Signature against the provider's JWKS, plus iss, aud, exp.
    idToken, err := verifier.Verify(r.Context(), rawIDToken)
    if err != nil { http.Error(w, "invalid id_token", 401); return }

    nonceCookie, _ := r.Cookie("oidc_nonce")
    if idToken.Nonce != nonceCookie.Value {
        http.Error(w, "nonce mismatch", 401); return
    }

    var claims struct {
        Email         string `json:"email"`
        EmailVerified bool   `json:"email_verified"`
        Name          string `json:"name"`
    }
    _ = idToken.Claims(&claims)

    // Identity key is (issuer, subject). Never email.
    userID, err := resolveUser(idToken.Issuer, idToken.Subject, claims.Email, claims.EmailVerified)
    if err != nil { http.Error(w, "cannot resolve user", 500); return }

    startSession(w, userID)   // ← your own session. Everything from here is the previous article.
    http.Redirect(w, r, "/", http.StatusFound)
}
```

Three things worth stopping on.

**`verifier.Verify` is where OIDC differs from OAuth**, in one line. It checks that this assertion was addressed to your client id. Replace it with "call `/userinfo` using `tok.AccessToken`" and you've built the token-substitution vulnerability from the top of this article, and it will pass every test you write, because in the happy path both approaches return the right user.

**`resolveUser` is where the product decision lives**, not the protocol. Look up `(issuer, subject)`; if found, done. If not, and `EmailVerified` is true and an account with that email exists, you may link — and "may" is a policy you should be able to state out loud, because it's the difference between a smooth experience and an account-takeover path. If the email is unverified, do not link on it under any circumstances; create a separate account or ask the user to prove ownership.

**`startSession` is the end of the protocol.** OIDC answered one question — who is this, right now — and the answer has a shelf life of that single moment. From here, your own session carries the identity, with your own expiry, your own revocation, and your own device list. The access token is only worth keeping if you're going to call the provider's API; if all you wanted was login, discard it and the refresh token with it, and you've eliminated an entire category of stored credential.

## Further Reading

- **RFC 6749, _The OAuth 2.0 Authorization Framework_.** Read §1 for the roles and §4.1 for the code flow; the rest is reference material you'll return to.
- **RFC 9700 / BCP 240, _Best Current Practice for OAuth 2.0 Security_ (2025).** Updates 6749, 6750 and 6819, and deprecates the modes that turned out to be indefensible. If you read one document here, read this one — it's where current practice actually lives, and it's substantially different from what a 2013 tutorial will tell you.
- **RFC 7636, _Proof Key for Code Exchange_.** Short, and the mechanism is easy to hold in your head once you've seen it written out.
- **The OAuth 2.1 draft.** Consolidates 6749, PKCE, and the security BCP into one document with the deprecated grants removed. Useful as a summary of the current consensus even while it's a draft.
- **OpenID Connect Core 1.0.** §2 (the ID token), §3.1 (the code flow), and §15 (implementation considerations). Plus the Discovery spec for the well-known endpoint.
- **The specs you'll actually meet on the job:** RFC 8414 (authorization server metadata), RFC 7662 (token introspection, for opaque access tokens), RFC 8628 (device grant), RFC 9126 (pushed authorization requests), RFC 8693 (token exchange).
- **"OAuth 2.0 for Browser-Based Applications" (IETF draft).** The current guidance for SPAs, and the clearest published argument for the backend-for-frontend pattern.
- **Aaron Parecki, _OAuth 2.0 Simplified_, and oauth.net.** The readable path in. Start here if the RFCs feel like the wrong entry point, then go back to RFC 9700.

A **TypeScript** sibling would earn its place, aimed at the browser-based case specifically. Go's server-side flow makes the mechanism clear precisely because it never has to answer the hardest question in modern OAuth: when the client is a single-page app, where do the tokens live? The BFF pattern, the token-in-memory-plus-silent-renewal pattern, and the reasons the ecosystem moved away from refresh tokens in browser storage are a genuinely different article, and the framework layer (`next-auth`/`auth.js`, `oidc-client-ts`) is where most developers will actually meet these decisions. Not yet written.

---

The habit to carry out of this article is to ask, of any identity system you meet: **who is asserting what, to whom, and how long is the assertion good for?** OAuth's access token asserts permission to a resource server. OIDC's ID token asserts an identity to one specific client, once. SAML's assertion does the same thing in XML. A session cookie asserts a past login to your own server. Once you can name the asserter, the audience, and the lifetime, the protocol diagrams stop being things to memorize and start being things you can derive — and the bugs, which are almost always a missing audience check or an assertion trusted longer than it deserved, become visible in code review.
