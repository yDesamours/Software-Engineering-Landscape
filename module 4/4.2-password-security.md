# Password Security

_Module 4.2 — Authentication & Authorization_

## The Problem

Design every part of this from the assumption that the table has already leaked. Not because you expect it to, but because every decision here only pays out in that scenario. A backup on a misconfigured bucket, a read-only SQL injection, a compromised analytics replica, a departing contractor — the mechanism doesn't matter. Two million rows, in someone else's hands.

What happens next depends entirely on what's in the password column.

**Plaintext.** Two million accounts, plus the credentials to however many other sites those people reused them on. This still happens.

**MD5 or SHA-256, no salt.** A single consumer GPU computes something on the order of ten billion SHA-256 hashes per second. Worse, identical passwords produce identical hashes, so the attacker sorts the dump by hash frequency and the most common value is `123456` — cracking it once breaks every account that shared it. Precomputed tables mean much of the work was done years ago by someone else.

**SHA-256 with a per-user salt.** Precomputation is dead and each account must be attacked separately. That sounds like a lot until you do the arithmetic. The attacker doesn't try random strings; they try a list of the ten thousand most common passwords, because humans choose from a small, well-studied distribution.

```
  2,000,000 accounts × 10,000 common passwords = 2 × 10^10 hashes

  one consumer GPU, single SHA-256:  ~10^10 per second
  ────────────────────────────────────────────────────────
  time to try every common password against every account:   ~2 seconds
```

Two seconds. The salt did its job perfectly and it bought you nothing, because the job it does is preventing *amortization*, not making any individual guess expensive.

**A password hashing function.** Now the same attack:

```
  bcrypt, cost 12:      ~1,000–2,000 guesses/sec on that GPU  →  months
  Argon2id, 64 MiB:     comparable per-guess cost, but the memory
                        requirement resists the custom hardware that
                        makes GPUs and ASICs cheap in the first place
```

The whole discipline compresses into one sentence: **salting stops the attacker from attacking everyone at once; a slow hash makes each individual guess cost something.** You need both, and only the second one is a dial.

### The constraint that makes this interesting

Here's what turns a copy-paste decision into an engineering one. The cost you impose on the attacker, you also pay — on every single login, on your own hardware, out of your own capacity budget.

At 200 milliseconds per verification and 50 logins per second, you're spending ten CPU-seconds per second on nothing but password checking. That's ten cores, permanently, doing deliberately wasted work. Turn the dial up and you get more attacker-time per leaked row and less headroom, plus a denial-of-service vector: anyone who can post garbage to your login endpoint can make you burn that CPU on their behalf.

So the question is never "what's the strongest setting." It's "what's the most expensive setting I can afford, given my login rate and my hardware," and the answer changes as both change.

## What It Is

A **password hashing function** — bcrypt, scrypt, Argon2 — is a one-way transformation that is *deliberately expensive*, takes a per-user salt, and exposes tunable cost parameters so the expense can be raised as hardware gets faster.

Two distinctions, because both cause real bugs:

**Hashing is not encryption.** Encryption is reversible by design. If your system can ever display a user's password back to them, you built the wrong thing, and the fact that it's "encrypted at rest" doesn't save you — the key is on the machine that does the decrypting. The correct answer to "I forgot my password" is a reset, never a retrieval.

**A fast hash is not a password hash.** SHA-256 and BLAKE3 are excellent at what they're for: integrity, deduplication, content addressing, and — as in the first article of this module — hashing high-entropy secrets like session tokens, where speed is a feature because there's nothing to guess. Passwords are the opposite case: low entropy, drawn from a predictable distribution, so the only defence is making each attempt cost something. Using SHA-256 here isn't a weaker choice within the same category; it's the wrong category.

## Recognizing the Problem

- Your system can email a user their existing password, or show it to a support agent. It's reversible, which means it's already lost.
- The password column holds 32 or 64 hexadecimal characters. That's MD5 or SHA-256, and there's no room in it for parameters.
- There's no salt column, and the stored value isn't in a format that embeds one.
- Login verification takes 3 milliseconds. Whatever it's doing, it isn't a password hash.
- Your work factor was chosen when the service launched and nobody has revisited it since.
- The signup form requires an uppercase letter, a digit, and a symbol; forbids spaces; caps length at 16; and blocks paste.
- Reset tokens don't expire, can be reused, or came from a non-cryptographic random source.
- Completing a password reset leaves every existing session logged in.
- `POST /login` returns "no account with that email" for unknown users and "incorrect password" for known ones.
- Rate limiting is per account only — so an attacker making one attempt against each of a million accounts sails straight through.
- Changing a password doesn't require the current one, and changing an email doesn't notify the old address.
- The password reset flow doesn't ask for a second factor, while the login flow does.

## How It Works

### Salt

A random value per user, generated at registration, stored in plain sight next to the hash. It isn't secret and doesn't need to be. Its only job is to ensure that work done against one account is worthless against every other — which kills precomputed tables and kills the "crack the most popular hash once" attack in one move. Every modern password hashing function generates and embeds it for you; if you're writing salt-handling code yourself, you've probably picked the wrong primitive.

### Work factor

- **bcrypt** takes a cost, which is a base-2 logarithm of iterations: cost 12 is twice the work of 11. On current server hardware, cost 12 lands somewhere around 200–300ms — measure it rather than trusting that sentence.
- **scrypt** takes `N`, `r`, `p` — iterations, block size, parallelism — and was the first widely used memory-hard design.
- **Argon2** takes memory (`m`), time (`t`), and parallelism (`p`) as separate dials, which is the main practical reason to prefer it: you can raise memory cost without raising latency proportionally.

Calibration is an experiment, not a lookup. Pick a latency budget — 200 to 500ms is the usual range for interactive login — then measure on hardware resembling production and choose the highest parameters that fit. A laptop with a fast single-core and no other load will tell you a comfortable lie.

### Memory hardness, and why Argon2 is the default recommendation

The honest version of this argument isn't "Argon2 is newer." It's about what an attacker can buy.

Compute parallelism is cheap and getting cheaper. A GPU has thousands of cores; an FPGA or ASIC can be built to do one specific computation at absurd throughput for a fraction of the power. bcrypt already resists this better than a plain hash, because its memory access pattern is awkward for GPUs — that was a deliberate design choice in 1999 and it has aged remarkably well.

Memory is different. Requiring 64 MiB per guess means an attacker running a thousand guesses in parallel needs 64 GiB of fast memory, and that constraint doesn't fall to specialized silicon the way raw arithmetic does. Memory-hardness changes the *economics* of building attack hardware, not just the speed of running it. That's the argument, and it's why Argon2id — the hybrid variant, resistant to both side-channel and time-memory-tradeoff attacks — is the current default recommendation.

bcrypt remains a defensible choice, particularly in an ecosystem where it's the well-audited option. The gap between bcrypt at a sensible cost and Argon2id at sensible parameters is much smaller than the gap between either of them and SHA-256.

### The encoded hash string

This is the detail that makes everything else maintainable:

```
$argon2id$v=19$m=65536,t=3,p=4$c29tZXNhbHQ$RdescudvJCsgt3ub+b+dWRWJTmaaJObG
 └ algorithm ┘ └ parameters ─┘ └── salt ──┘ └────────── digest ───────────┘
```

The algorithm and its parameters travel *with* the hash, in one column. That single design choice is what allows a system to hold rows produced by four different settings over eight years and verify all of them correctly — because each row says how to verify itself.

Which unlocks the only workable upgrade path.

### Upgrading, when you can't read what you stored

You can't rehash a password you don't have. But at exactly one moment you do have it: the instant a user successfully logs in.

```
verify(submitted, stored)
  └─ success ──► are stored parameters below current policy?
                     └─ yes ──► rehash(submitted) with current parameters, save
```

Every successful login is an opportunity to silently upgrade that row. Raise the parameters, deploy, and the population migrates itself over the following weeks as people return.

For accounts that never return, there's a second technique worth knowing, because it's the only way to fix a plaintext or MD5 catastrophe *today* rather than over a year: hash the existing stored value with the new function and record that it's wrapped. `argon2(md5(password))` is as strong as `argon2(password)` against an offline attack, even though the inner hash is worthless on its own. On the next successful login, unwrap and store a clean hash. This lets you stop the bleeding in one migration instead of waiting for user behaviour.

### Pepper

A pepper is a secret value, held outside the database — in a KMS, an HSM, or at minimum an environment variable — mixed in before or after hashing, usually by HMAC-ing the password with it first.

The property it buys is narrow and specific: a leak of the *database alone* yields nothing crackable. That covers a real and common class of incident — SQL injection, an exposed backup, a replica with weak access control — where the attacker never reaches the application's secrets.

The cost is real too. Rotating a pepper means re-peppering every row, which requires the same login-driven or wrapped migration described above. Losing it locks out every user permanently. And it buys nothing at all if the secret ends up in the same database, the same config table, or the same compromised host as everything else.

Reasonable position: worth it when your database and your application secrets genuinely have different exposure, which is more often true than teams assume once managed databases and read replicas are involved. Not worth contorting your deployment for.

### One sharp edge worth knowing

bcrypt only considers the first 72 bytes of input, and some implementations truncate at a null byte. This matters more than it sounds: if you ever hash something longer — a passphrase, or a concatenation like `username + password` — the tail is silently ignored, and inputs sharing a 72-byte prefix become interchangeable. This has caused real authentication bypasses at real companies. If you need to accept long inputs with bcrypt, pre-hash with SHA-256 and **base64 the digest first**, so no null bytes reach bcrypt. Argon2 has no such limit.

### Policy: what the evidence actually supports

Composition rules — one uppercase, one digit, one symbol — fail for a reason worth understanding. They don't expand the space users choose from; they constrain it in *predictable* ways. Told to add a capital and a digit, people produce `Password1`, then `Password1!`. Cracking tools have encoded those transformations as rule sets for two decades. The policy converts a bad password into a slightly longer bad password and makes the user resent you.

What holds up:

- **Length is the lever.** Eight characters absolute minimum, twelve or more as the encouraged floor. Support long passphrases — 64 characters or more — and cap somewhere reasonable (a few hundred) only to bound the work you'll do hashing.
- **Allow everything.** All Unicode, spaces, emoji. Every character you forbid is a rule an attacker's tooling gets to apply for free.
- **Never block paste.** It's the single most direct way to push users away from password managers, which are the best thing that's happened to real-world password security.
- **Check against breach corpora.** A password that appears in a known dump is compromised no matter how many symbols it has. This is the highest-value single check in the section, and the k-anonymity range APIs let you do it without transmitting anything sensitive: send five characters of the hash prefix, receive a list of suffixes, match locally.
- **Check context-specific words** — your product name, the user's email local part, their company name. `acmecorp2026` passes any composition rule and is in the first thousand guesses of a targeted attack.
- **Don't force periodic rotation.** Mandatory 90-day expiry produces `Summer2026!` → `Autumn2026!` and pushes secrets onto sticky notes. Rotate on evidence of compromise, not on a calendar.
- **Estimate strength, don't count entropy.** Character-class entropy math assumes random selection, which is false for human-chosen passwords. A pattern-matching estimator that recognizes dictionary words, keyboard walks, dates, and leetspeak substitutions gives a far more honest number and better user feedback.

### The reset flow is a login flow

Password reset is the most attacked part of this entire article, because it is a complete, alternative route to a session — and it is routinely built with less care than the front door it bypasses.

The mechanics:

- Token from a cryptographic random source, 128+ bits.
- **Stored hashed**, for the same reason as session tokens in the first article: your reset table shouldn't be a list of live account-takeover credentials.
- Single use, short expiry — 15 to 60 minutes.
- Invalidated when used, when another is requested, and when the password changes by any other route.
- The response to "send me a reset email" is identical whether or not the account exists. Otherwise it's an account enumeration endpoint.
- Rate-limit generation, or you've built a free email-bombing service pointed at your own domain's reputation.
- On success, **invalidate every existing session** for that user — and every refresh token, and every remembered device. If someone is resetting because they were compromised, leaving the attacker's session alive defeats the entire exercise.
- Notify the user on every reset, and notify the *old* address on every email change. This is often how a takeover gets caught.

And the thing teams miss: **if login requires a second factor and reset doesn't, you don't require a second factor.** The attacker takes the path with fewer checks. A reset must demand at least as much proof as a login — which usually means MFA during reset, with recovery codes as the documented alternative. That's the same point the previous article made about recovery paths, arriving from the other direction.

### Rate limiting and stuffing defences

Three different limits, because they catch different attacks:

- **Per account** catches brute force against one target. Exponential backoff is better than a hard lockout, because a hard lockout is a denial-of-service weapon: anyone who knows a target's email can lock them out at will.
- **Per IP** catches a noisy single-source attack, and nothing else. Credential stuffing arrives from residential proxy networks with one attempt per address.
- **Globally, across the endpoint** catches the case from the top of this article: 40,000 attempts, every one against a different account, none of them tripping a per-account counter. A baseline failure rate with an alarm on deviation is what makes that visible at all.

Layered on top: a challenge (CAPTCHA or proof-of-work) once traffic looks anomalous rather than for everyone; device and network reputation; and **checking the submitted password against breach corpora at login time**, not just at registration, so you can force a change when a user's long-standing password shows up in a new dump.

Two implementation details matter more than they look. Rate-limit *before* the expensive hash, or the limiter is also the thing consuming your CPU. And return identical errors and similar timing for "no such user" and "wrong password" — which usually means verifying against a dummy hash when the user doesn't exist, so the response time doesn't answer a question you declined to answer in words.

The general algorithms here — fixed window, sliding window, token bucket, and doing any of it correctly across many instances — are Module 18. What's specific to authentication is the layering above and the ordering relative to hashing.

## When It's Appropriate

If you store passwords, all of this is table stakes rather than a decision. The genuine decisions are narrower:

- **Higher parameters** when login volume is low relative to account value — an admin console, a financial product, a system with a thousand users and a large blast radius. There's no reason for 200ms when you could afford 800ms.
- **Peppering** when your database's exposure is meaningfully different from your application secrets' exposure. Managed databases, read replicas, and third-party backup tooling all widen that gap.
- **Strict policy and aggressive breach checking** when accounts are valuable enough that user friction is the cheaper cost.

## When It's Unnecessary or Overkill

**When you shouldn't hold passwords at all.** If federating to an identity provider is viable for your users, the strongest version of this article is to delete it. That's the previous article, and it's frequently the right call.

**Parameters tuned past what you can serve.** Argon2id at 1 GiB and 500ms looks excellent in a config file and means an attacker with a script and a spare afternoon can exhaust your memory by posting junk to `/login`. The dial has a ceiling and the ceiling is your capacity.

**Peppering with the secret in the same database.** You've added a migration burden and an outage risk for no change in threat model.

**Slow hashing for high-entropy secrets.** Session tokens, API keys, reset tokens, and webhook signing secrets are 128+ random bits — there's nothing to guess, so a fast hash is correct and Argon2 is wasted latency on your hottest path. This is the mirror image of the mistake at the top of the article, and it's just as common once a team learns the lesson and over-applies it.

**Rotation policies and composition rules generally.** They fail on evidence, not on principle. If a compliance regime mandates them, comply — but don't add them voluntarily believing they help.

## Trade-offs

- **CPU and memory on the login path**, permanently, as a capacity line item — and a denial-of-service surface that has to be rate-limited ahead of the hash.
- **Parameters decay.** Hardware gets faster; your cost setting doesn't. There's no mechanism that reminds you, so it needs to be a recurring calendar item with an owner, which means it will be skipped unless someone writes it down.
- **Upgrades depend on user behaviour.** Login-driven rehashing never reaches dormant accounts, and those are exactly the accounts nobody notices are weak.
- **Pepper couples authentication to key management.** Rotation is a migration; loss is an extinction event.
- **Strict policy costs conversions**, measurably, at signup — the one place in the funnel where friction is most expensive.
- **Lockouts are a weapon.** Any per-account limit strict enough to stop an attacker is strict enough for an attacker to use against your users. Throttling and challenges degrade more gracefully than locking.
- **Reset flows are permanent operational load** — deliverability, support tickets, and a steady trickle of social-engineering attempts aimed at whoever handles them.
- **And the ceiling on all of it:** none of this protects against phishing, against a reused password leaked elsewhere, or against malware on the user's machine. Password hashing limits the blast radius of *your* breach. It does nothing about the other three, which is why the previous article exists and why "we hash properly" is an answer to exactly one question.

## Alternatives

- **Don't store passwords.** Federate (4.1b) or go passwordless (4.1c). Strictly fewer secrets to protect.
- **Augmented PAKEs — SRP, OPAQUE.** The server stores a verifier and never learns the password, even during a successful login. The client proves knowledge through a key exchange, so there's nothing to intercept at the TLS terminator, nothing in a request log, and nothing for a compromised server to silently harvest. Genuinely stronger, genuinely real — and the ecosystem support is thin, the flows don't fit ordinary form posts, and server-side policy checks (breach lookup, minimum length on the real value) become awkward or impossible. Worth knowing about; rarely the pragmatic choice today.
- **HSM-backed verification.** Do the final HMAC inside a hardware module so the pepper can't be extracted even from a fully compromised host. Strong, expensive, and mostly seen in finance.
- **Managed identity as a service.** Someone else's problem, at a per-user price, with the lock-in noted in 4.1b.
- **Encourage password managers** by not fighting them: allow paste, allow length, allow every character, and don't impose rotation. This is a real security intervention with no engineering cost, and most password policies are actively working against it.

## How to Achieve It

**Level 0 — stop the bleeding.** If passwords are plaintext, MD5, or an unsalted fast hash, wrap every row in a real password hashing function in a single migration today, and unwrap on next login. Don't wait for a redesign.
*Signal you're here:* the hash column is 32 or 64 hex characters.

**Level 1 — one column, measured parameters.** Argon2id or bcrypt, parameters chosen by measuring on production-like hardware against a latency budget, and the full encoded string in one column. Add the rehash-on-successful-login check at the same time — it costs four lines now and is what makes every future parameter increase a config change.
*Signal you skipped it:* raising the work factor would require a migration.

**Level 2 — fix the policy.** Remove composition rules, raise the minimum length, allow everything, unblock paste, drop forced rotation, add a breach-corpus check at registration and password change. This is the cheapest improvement in the module and it improves signup conversion at the same time.
*Signal:* your rules produce `Password1!` and your users tell you so.

**Level 3 — harden reset.** Hashed single-use tokens, short expiry, uniform responses, generation rate limits, full session invalidation on success, notification emails, and a second factor at least as strong as the one login requires.
*Signal:* reset currently bypasses MFA — go look, it probably does.

**Level 4 — layer the stuffing defences.** Per-account backoff, per-IP limits, a global baseline with alerting, challenges on anomaly, and breach checking at login with a forced change when a match appears.
*Signal:* you can't distinguish a stuffing wave from a traffic spike.

**Level 5 — reduce what you hold.** Pepper from a KMS if the threat model justifies it, and more importantly, start moving users to federated or passwordless authentication so the password becomes a fallback rather than the primary credential.
*Signal:* you're maintaining all of the above and it's nobody's full-time job.

## Implementation

Java, because Spring Security's `PasswordEncoder` abstraction is the clearest existing implementation of the idea that made this whole article tractable — that a stored hash should describe how to verify itself — and because it turns migration into a default rather than a project.

### The stored format, with an identifier

```java
@Bean
PasswordEncoder passwordEncoder() {
    Map<String, PasswordEncoder> encoders = Map.of(
        "argon2", new Argon2PasswordEncoder(16, 32, 1, 1 << 16, 3),  // salt, hash, p, m=64MiB, t
        "bcrypt", new BCryptPasswordEncoder(12),
        "sha256", new MessageDigestPasswordEncoder("SHA-256")        // legacy: verify only
    );
    return new DelegatingPasswordEncoder("argon2", encoders);
}
```

What gets stored is prefixed:

```
{argon2}$argon2id$v=19$m=65536,t=3,p=4$c29tZXNhbHQ$RdescudvJCsgt3...
{bcrypt}$2a$12$N9qo8uLOickgx2ZMRZoMye...
{sha256}8d969eef6ecad3c29a3a629280e686cf...
```

Three generations of decisions living in one column, each self-describing, all verifiable. New hashes are written with the first encoder; old ones are routed by their prefix to something that can still check them. The bcrypt row carries its own cost inside `$12$`, which is the same idea one layer down — the format was designed for this in 1999, and the paper that introduced it was titled "A Future-Adaptable Password Scheme" for precisely this reason.

The `sha256` entry is deliberate: it exists so legacy rows can be *verified once*, at which point they're immediately replaced. It should be deleted from the map the moment the last one is gone.

### Choosing parameters by measuring

```java
// Run on hardware resembling production, under representative load.
for (int memoryKiB : new int[]{ 1 << 14, 1 << 15, 1 << 16, 1 << 17 }) {
    var encoder = new Argon2PasswordEncoder(16, 32, 1, memoryKiB, 3);
    long start = System.nanoTime();
    for (int i = 0; i < 20; i++) encoder.encode("correct horse battery staple");
    System.out.printf("m=%d KiB -> %d ms%n", memoryKiB, (System.nanoTime() - start) / 20_000_000);
}
```

Two things this measurement has to account for that a naive run won't. It should happen on the target hardware, because a developer laptop's single-core performance and idle memory bandwidth will suggest parameters your production instances can't sustain. And the number to plan against isn't the latency — it's latency × peak logins per second, which is the share of your total CPU and memory this consumes at your busiest moment. Ten cores of permanent password hashing is a legitimate cost; discovering it during a Monday-morning login surge is not.

### The login path

```java
public Optional<UserId> authenticate(String email, String submitted) {
    var user = users.findByEmail(email);

    if (user.isEmpty()) {
        encoder.matches(submitted, DUMMY_HASH);   // same work, same timing
        return Optional.empty();                   // same error as a wrong password
    }

    if (!encoder.matches(submitted, user.get().passwordHash())) {
        return Optional.empty();
    }

    // Only moment the plaintext exists — the only chance to upgrade this row.
    if (encoder.upgradeEncoding(user.get().passwordHash())) {
        users.updateHash(user.get().id(), encoder.encode(submitted));
    }
    return Optional.of(user.get().id());
}
```

The dummy-hash branch is doing two jobs at once. It equalizes response time, so the endpoint doesn't answer "does this email have an account?" through a stopwatch — and by returning the identical error, it doesn't answer in words either. Getting one right and not the other is common and pointless; enumeration only needs one channel.

`upgradeEncoding` is the payoff for the prefixed format. It compares the stored hash's declared algorithm and parameters against the configured default and says whether this row is behind. Raising the work factor is now a one-line config change plus patience, rather than a project.

Note carefully where this method sits, though. It does no rate limiting, and it's expensive by design — so something in front of it must reject abusive traffic *before* this code runs, or the protection becomes the attack surface. The limiter belongs at the edge of the request, not inside the verification.

## Further Reading

- **RFC 9106, _Argon2 Memory-Hard Function for Password Hashing_.** The specification, with concrete recommended parameter sets for both high-memory and constrained environments. Start with the recommendations section.
- **OWASP, _Password Storage Cheat Sheet_.** The practical, currently-maintained parameter guidance for Argon2, bcrypt, scrypt and PBKDF2. This is the page to check annually, because the numbers move.
- **NIST SP 800-63B, _Authentication and Lifecycle Management_.** The source of the evidence-based policy position: length over composition, no mandatory rotation, breach-list screening. Useful for the conversation where someone insists on a symbol requirement.
- **Niels Provos and David Mazières, "A Future-Adaptable Password Scheme" (USENIX, 1999).** The bcrypt paper. Short, readable, and the entire idea of the article is in the title.
- **The Password Hashing Competition and the Argon2 design rationale.** Why memory-hardness, what time-memory tradeoff attacks look like, and why Argon2id is the hybrid recommendation rather than i or d.
- **Dan Wheeler, "zxcvbn: Low-Budget Password Strength Estimation" (USENIX, 2016).** Makes the case that entropy math is the wrong model for human-chosen passwords, and provides the better one.
- **Have I Been Pwned, Pwned Passwords API documentation.** The k-anonymity range query, explained in five minutes. Implement it the same day you read it.
- **The OPAQUE specification (IETF CFRG).** Worth reading to understand what "the server never sees the password" actually requires, even if you don't adopt it.

A **TypeScript** sibling would earn its place for one specific reason. On the JVM, an expensive-by-design function running per request is handled by the thread pool and shows up as saturation — unpleasant, but localized. On Node, Argon2 is a native addon, and calling it synchronously blocks the event loop for 200ms, stalling *every* concurrent request, not just the one logging in. The non-local latency signature that Module 1.3 described in the abstract has one of its most common real-world causes right here, and the async-plus-worker-pool shape of the fix is a genuinely different article. Not yet written.

---

The habit to carry out of this one: **assume the dump has already happened, and ask what it's worth.** That reframing makes every decision here derivable rather than memorized — why salts exist, why slowness is a feature, why the work factor has to be revisited, why the reset table deserves the same care as the password column, and why the best version of this article is the one where you're not storing passwords in the first place. And when you tune the dial, remember it points both ways: every millisecond you spend making an attacker's offline work harder is a millisecond you spend on every honest login, forever.
