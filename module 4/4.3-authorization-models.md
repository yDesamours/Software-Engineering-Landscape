# Authorization Models

_Module 4.3 — Authentication & Authorization_

## The Problem

Authentication happens once, at one endpoint, and a small team can get it right. Authorization happens on every request, at every endpoint, against every object, forever — written by whoever happened to be writing that endpoint that week. That asymmetry is the whole story, and it's why this is where production security bugs actually live.

Here's the shape it takes, on a project-management product, over about a year.

**Month one.** There are two kinds of people: the person who set up the account, and everyone else.

```go
if !user.IsAdmin { forbidden(w); return }
```

This is fine. It's honest about the domain, it's readable, it works.

**Month four.** A customer wants someone to handle invoices without being able to delete projects. You add `IsBilling`. Then a customer wants read-only access for a contractor: `IsViewer`. Three booleans, eight combinations, of which four are nonsense and nobody has written down which four.

**Month eight.** You do the obvious refactor to a `role` column: `owner`, `admin`, `member`, `viewer`. Much better. Then a customer asks for "can invite people but can't see billing," so you add `manager`. Then another wants "billing but also member." Now it's `billing_member`. Roles are coarse buckets, and every request for a slightly different bucket creates a new one, which is a role explosion — and each one has to be handled everywhere.

**Month twelve.** There are 200 endpoints. The checks were written independently, so they disagree: some compare against a role string, some against a list of role strings, some against a boolean that was never removed. Three handlers spell the admin check differently and one of them is subtly wrong. A new endpoint ships with no check at all.

Notice what happened with that last one. **Nothing failed.** No error, no test failure, no alert. A missing authorization check is invisible — the endpoint works perfectly, for everyone. The absence of a restriction announces itself only when someone exploits it.

**Month fourteen.** The real incident.

```
GET /invoices/4417
  ✓ user is authenticated
  ✓ user has the billing role
  → 200 OK
```

Invoice 4417 belongs to a different customer. Every check passed. The role check answered "may this person look at invoices?" — yes, they're the billing person at their company. Nobody wrote the check that answers "may this person look at *this* invoice?"

That's the distinction the whole article turns on:

```
  request:  DELETE /documents/8823   from user u_91

  ① may this user delete documents at all?        ← role / permission check
  ② may this user delete THIS document?           ← object / relationship check
  ③ is this document even in their tenant?        ← isolation check

  A system that answers only ① returns 200 and deletes a stranger's file.
```

Almost every authorization tutorial teaches ①. Broken object-level authorization — failing at ② — has sat at the top of OWASP's API security list for years, because it's the failure that's easiest to write and hardest to notice. And ③ is the version of ② that turns a bug into a disclosure event with legal consequences.

## What It Is

**Authorization** is deciding whether a principal may perform an action on a resource, in some context. Every model in this article is an answer to one question: *what does that decision depend on?*

- **ACL (access control list)** — the decision depends on an explicit entry attached to the object. "u_91 may read document 8823." Oldest model, still exactly right for sharing-heavy products.
- **RBAC (role-based)** — permissions are bundled into roles, roles are assigned to users. The decision depends on **who you are**.
- **ABAC (attribute-based)** — the decision is computed from attributes of the subject, the resource, the action, and the environment. It depends on **facts**: department, clearance, data classification, time of day, IP range.
- **ReBAC (relationship-based)** — the decision depends on **how you're connected to the object**, through a graph: you're an editor of the folder that contains the document, or a member of a group that was granted access.

**PBAC** and "policy engines" aren't a fifth model so much as an implementation style: express any of the above as policy *data*, evaluated at runtime, rather than as branches in application code.

### Two clarifications worth making early

**"RBAC or ABAC?" is rarely the real question.** Almost every mature system is RBAC with conditions attached — "editor, but only within projects they're a member of" — which is technically attribute-based and nobody calls it that. The genuinely consequential decisions are elsewhere: where the check runs, what data it needs, and what happens on the endpoint where someone forgets to write it.

**Permissions are not entitlements.** "May this user delete projects?" and "does this customer's plan include the audit log?" feel like the same check and have completely different lifecycles. One changes when an admin edits a member's role; the other changes when a subscription is upgraded, downgraded, or goes past due (Module 1.1, Module 15). Merging them into one permission table is easy at first and unpleasant to unpick later, because a plan downgrade then has to rewrite per-user grants. Keep them as two questions that a route may ask separately.

## Recognizing the Problem

- Changing what a customer's users can do requires a code change and a deploy.
- You can't answer "who can read this document?" without grepping the codebase.
- An endpoint shipped with no authorization check and nothing caught it — not review, not tests, not monitoring.
- The same conceptual check is spelled three different ways in three files, and one of them is wrong.
- Customers are asking for custom roles.
- You've written `if resource.OwnerID != user.ID` by hand in forty places.
- You look at a handler that takes an id from the URL and can't tell, quickly, whether it verifies tenancy.
- The frontend hides a button, and the underlying API endpoint doesn't check anything.
- Permissions live in a JWT and a role change takes an hour to take effect.
- You need "can view, but only their own team's records" and the role system has nowhere to put "their own."
- An auditor asks what a specific user could access on a specific past date and there's no way to reconstruct it.
- Support can impersonate customers, and nothing is recorded when they do.
- List endpoints filter by tenant, and single-object endpoints fetch by primary key.

That last pair is worth checking today. It's the most common form of the month-fourteen bug, and it comes from the filtering being a natural part of writing a list query and an easily forgotten extra step when fetching one row.

## How It Works

### One decision function

Whatever model you choose, the shape is:

```
can(subject, action, resource, context) -> allow | deny
```

Everything that follows is about how that function is computed, where it's called, and how you guarantee it's called at all. Keeping deciding separate from enforcing is the structural idea — the same one as Module 2.2's layers, applied to a cross-cutting concern.

### RBAC, done properly

The schema everyone converges on:

```
users ──< role_assignments >── roles ──< role_permissions >── permissions
              │
              └─ scope: which organization / workspace / project
```

Three things distinguish an RBAC implementation that lasts from one that doesn't.

**Check permissions, not roles.** `can(user, "invoice:read")` rather than `user.Role == "billing"`. Roles then become an editable bundle — data, not code — so adding a role or moving a permission between roles is a configuration change rather than a search-and-replace across 200 handlers. This one rule prevents most of the month-eight mess.

**Scope role assignments to a container.** A user isn't "an admin"; they're an admin *of workspace 12*. Global roles in a multi-tenant system are the defect that produces cross-tenant admin access, and it's structurally invisible because the role check passes.

**Permissions name a verb and a resource type**: `document:read`, `member:invite`, `billing:manage`. Resist making them finer than your product actually distinguishes — each one is a thing you must document, display in a UI, test, and support forever.

### Object-level checks

This is the part RBAC does not do for you, and it needs data, which means it's a query.

Two strategies, and the interesting thing is which one is easy to forget:

**Fetch, then check.** Load the object, compare it to the subject, return 403 or 404. Simple, obvious, one extra read, and it works uniformly for single-object routes.

**Scope the query.** `WHERE tenant_id = $1 AND (owner_id = $2 OR ...)`. The object is never loaded if the user can't see it. Faster, and it's the only approach that scales to list endpoints — you cannot fetch-then-check a page of 200 rows without 200 checks.

Most teams end up with both, applied inconsistently: scoping on lists, forgotten on `GET /thing/:id`. The durable fix isn't discipline; it's making the unscoped query hard to write — a repository layer that requires a tenant context, or the database-level backstop below.

One detail that matters more than it seems: **404 or 403?** Returning 403 for an object the user can't see confirms it exists. For anything where existence itself is sensitive — a private repository, another customer's invoice — return 404. For objects within the user's own tenant that they merely lack permission for, 403 is more useful and leaks nothing.

### ReBAC, and why it exists

RBAC handles "all editors can edit all documents in this project." It handles poorly: this one document shared with one external person; a folder whose permissions cascade to everything inside; a group that contains another group; "anyone with the link can comment."

Those needs produce a permission table that grows with the product of users and objects, and application code that walks hierarchies by hand. The alternative is to store relationships as tuples:

```
(document:8823, viewer,  user:u_91)
(folder:44,     editor,  group:design)
(document:8823, parent,  folder:44)
(group:design,  member,  user:u_57)
```

plus rules that define derived relations — `viewer of a document = its explicit viewers + viewers of its parent folder`. A check becomes a bounded graph traversal. This is the Zanzibar model, and it's what sits under Google Drive-shaped products; open implementations exist if you need one.

It buys enormous flexibility and brings a genuinely hard problem with it: the relationship graph is a distributed cache, and if a revocation and a content change are applied in different orders in different places, you can serve new content to someone whose access was just removed. Zanzibar solves this with consistency tokens, and the fact that a paper needed to name and solve it should tell you how much subtlety is hiding in "just check the graph."

### ABAC and externalized policy

Policy as data: a rule language, evaluated by an engine, with rules living outside application code.

```
allow if subject.department == resource.department
     and resource.classification <= subject.clearance
     and context.time within business_hours
```

This earns its place when rules change on a different schedule than code, when several services must apply one consistent policy, or when the people who own the rules aren't the people who deploy the application — regulated environments, most of all.

The trap: the language is the easy part. **Policy needs data**, and the data lives in your application's database. An engine that has to call back for the resource's department and the subject's clearance on every decision has added a network hop and kept every coupling it promised to remove. The implementations that work either push the needed facts into the engine's own store, or evaluate policy in-process as a library.

### Row-level security: the backstop

Postgres can enforce authorization inside the database. A policy attached to a table is added to every query against it, whether or not the application remembered to:

```sql
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON documents
  USING (tenant_id = current_setting('app.tenant_id')::uuid);
```

Now a handler with a forgotten `WHERE` clause returns zero rows instead of someone else's data. That's a different kind of guarantee from anything above: it doesn't depend on remembering.

What it costs is real, and most of it is operational. The setting has to be established per transaction and must not leak across pooled connections (the implementation section shows exactly how that goes wrong). Policies appear in every query plan, so they need to be indexable. Debugging "why did this return nothing" acquires a new possible answer. Migrations and background jobs run as roles that may bypass policies, which is both necessary and a hole to guard. And an ORM that doesn't know about any of this will fight you.

It's best understood as defence in depth rather than your primary mechanism: the application should still scope its queries, and RLS is what catches the day it doesn't.

### Where the check runs

```
  edge / gateway     coarse: is this user authenticated, is this route allowed at all
        │
  route middleware   declared permission per route — default deny
        │
  service layer      object-level: load the resource, evaluate can(user, action, resource)
        │
  repository         tenant scoping, enforced structurally
        │
  database (RLS)     isolation that survives a forgotten clause
```

Each layer catches something the one above can't. The gateway can't do object-level checks because it doesn't have the object. The service layer can, but only if someone wrote the call. The database catches the case where nobody did.

### Making omission impossible

This is the highest-leverage practice in the article, and it's a hundred lines of code.

Register every route with a declared permission — including an explicit `Public` marker for the ones that need none. Then write a test that enumerates the router's registered routes and fails the build if any route lacks a declaration. A new endpoint now cannot ship without someone consciously choosing an answer.

That converts the month-twelve failure from "invisible until exploited" into "red build in CI." Nothing else in this article changes the economics of authorization bugs as much, because the problem was never that people choose wrong — it's that they don't know they're choosing.

### Audit and impersonation

Authorization decisions are the raw material of an audit trail. Log the interesting ones — denials, privileged actions, permission changes — with subject, action, resource, decision, and reason.

Support impersonation deserves specific handling: it should be an explicit capability, time-boxed, logged with **both** identities (who acted, and as whom), visible to the customer, and blocked from a defined set of actions. Impersonation implemented as "set the session's user id to theirs" is indistinguishable, afterwards, from the account being compromised.

## When It's Appropriate

- **Plain tenancy plus ownership** — no roles at all — is genuinely enough for many single-purpose products. Do this before anything else, not instead of thinking.
- **RBAC** fits nearly everything else, and fits B2B especially well because customers already think in job titles. It holds up while roles stay in the low tens, permissions are stable, and per-object sharing is rare.
- **RBAC with scoped assignments and conditions** — the practical default for multi-tenant SaaS. "Editor within the projects they belong to" covers an enormous share of real requirements.
- **ACLs** when sharing is occasional and explicit: a few objects, granted to a few named people.
- **ReBAC** when sharing *is* the product: nested containers, inherited permissions, link sharing, groups within groups. The tell is a customer asking to grant access to one object without changing anyone's role.
- **ABAC / externalized policy** when rules are owned by someone other than the engineering team, change independently of releases, or must be identical across many services. Also when decisions genuinely depend on environmental facts — region, classification, time.
- **RLS** in a shared-schema multi-tenant database where a cross-tenant leak is an existential event and the team is too large for every query to be reviewed by someone who remembers.

## When It's Unnecessary or Overkill

**A policy engine for an application with three roles.** You've added a deployable, a second language, and a distribution problem in exchange for a `switch` statement you could read.

**A Zanzibar-style service for a product with no sharing.** The model's power is entirely in relationships and inheritance. Without those, it's a slow key-value store with a novel query language.

**Custom roles before a customer asks.** It sounds like flexibility and it's a combinatorial explosion of states you now support, test, and explain — plus a migration every time your permission set changes.

**RLS when each tenant has its own database.** The isolation is already physical (Module 5).

**Externalized policy while the facts stay in your application database.** The coupling you were removing is still there, now with a network hop in front of it.

**ABAC whose attributes are all derived from role.** You've built an interpreter to evaluate constants.

**Permissions so fine-grained nobody can configure them.** Forty-two toggles produce customers who enable everything, which is worse than five roles they understand.

## Trade-offs

- **Your authorization model becomes a product surface.** It shows up in the UI, in documentation, in sales conversations, and in support. Changing it later is a data migration *plus* a customer-visible behaviour change — one of the one-way doors Module 2.5 says to write down.
- **Per-object checks cost queries.** A list of 200 items with a per-item check is an N+1 problem that arrives specifically at authorization. Batch the check or push it into the query.
- **Caching permissions gives stale authority.** Exactly the revocation-window trade from the first article in this module, one level up: cache a permission set for five minutes and a revocation takes five minutes. Fine for most things; not fine for the "remove a departing employee right now" case that makes customers ask about it.
- **Externalized policy adds a component to the critical path** and a second language to test, version, and roll out — and policy rollouts are deployments with the same blast radius as code.
- **RLS interacts badly with connection pooling and migrations**, both of which are solvable and neither of which is obvious in advance.
- **ReBAC brings consistency problems** that don't exist when the check is a join in the same transaction as the read.
- **Testing is genuinely hard.** The space of (subject, action, object) is too large to enumerate, so coverage means invariants and negative tests — "a member of tenant A gets 404 for every object in tenant B" — rather than cases. Most suites test only that the allowed path works, which is the half that fails loudly anyway.
- **Over-restriction is also a failure mode.** Authorization that's too tight produces shared admin accounts, credentials passed around in chat, and permanent elevation "temporarily" granted. A model people route around is a security regression, not a conservative default.

## Alternatives

- **One database per tenant** (Module 5). Removes an entire category of this problem by making cross-tenant access physically impossible, and costs you operational multiplicity.
- **Capability tokens.** Instead of looking up whether a subject may act, carry the authority in an unforgeable, scoped, short-lived token — a signed download URL, a share link, a one-time upload grant. The authority travels with the request instead of being reconstructed from a database. This is the same family as the self-contained tokens in 4.1a, and it has the same properties: fast, decentralized, and awkward to revoke.
- **Buy an authorization service.** Managed and open implementations exist for both the ReBAC model and the policy-engine model. You get a tested implementation of a genuinely subtle system; you take on a network call in every request path, their data model, and a second source of truth to keep in sync.
- **Enforce in the database and nowhere else.** Viable for smaller systems with a single database and no service tier, and unusually robust — the guarantee holds regardless of which code path arrives. Fragile if you later add services that don't go through that database.

## How to Achieve It

**Level 0 — tenancy and ownership, enforced structurally.** Before any role system: every query carries a tenant scope, applied in one place rather than remembered per call site, and every single-object route verifies the object belongs to the caller's tenant.
*Signal you're behind:* you have roles, and you can't state confidently that cross-tenant access is impossible.

**Level 1 — permissions as data.** Named permissions, roles as bundles stored in the database, call sites checking permissions rather than role strings. Roles become editable without a deploy.
*Signal:* a list of role names in a conditional.

**Level 2 — one decision function, and default deny.** Route a single `can()` through the codebase; register every route with a declared permission; add the test that fails the build on an undeclared route.
*Signal:* an endpoint reached production without a check. It has.

**Level 3 — scope and conditions.** Role assignments attached to a workspace or project rather than globally; object-level checks consulting membership, ownership, or containment.
*Signal:* a requirement of the form "X, but only their own Y."

**Level 4 — add the backstop, or change models.** Turn on row-level security for the tables where a leak is unacceptable. If per-object sharing has become a core feature, this is the point to evaluate ReBAC rather than growing the permission table further.
*Signal:* a near-miss cross-tenant incident, or customers asking to share individual objects with people outside their role structure.

**Level 5 — externalize and audit.** A policy engine when multiple services need one consistent answer, plus a durable log of authorization decisions good enough to reconstruct what a given user could access on a given past date.
*Signal:* compliance asks that question, or the second service starts reimplementing the first one's rules.

## Implementation

Go, because the two mechanisms worth seeing here — a route registry that can be tested for completeness, and the transaction-scoped variable that makes row-level security work — are both things that explicit code shows clearly and a framework tends to hide.

### The decision function

```go
type Action string

const (
    DocumentRead   Action = "document:read"
    DocumentDelete Action = "document:delete"
    BillingManage  Action = "billing:manage"
)

// Coarse: does this subject hold the permission anywhere in this workspace?
func (a *Authz) Can(ctx context.Context, s Subject, act Action, ws WorkspaceID) bool {
    perms, err := a.permsFor(ctx, s.UserID, ws)   // role assignments → permissions
    if err != nil { return false }                 // errors deny, always
    return perms.Has(act)
}

// Fine: may this subject perform it on this specific object?
func (a *Authz) CanOn(ctx context.Context, s Subject, act Action, doc *Document) bool {
    if doc.TenantID != s.TenantID { return false }        // ③ isolation
    if !a.Can(ctx, s, act, doc.WorkspaceID) { return false } // ① capability
    if act == DocumentDelete && doc.OwnerID != s.UserID {     // ② object rule
        return a.Can(ctx, s, "document:delete_any", doc.WorkspaceID)
    }
    return true
}
```

The `err != nil` branch is not boilerplate. An authorization check that fails open when the database is slow is a vulnerability that only appears during incidents — precisely when nobody is reading logs carefully. Deny on error, every time, and let the request fail visibly.

Note also that the tenant comparison sits at the top of `CanOn` rather than being assumed. It's redundant if the query was scoped correctly. It's the thing that saves you when it wasn't.

### Default deny, enforced by a test

```go
type Route struct {
    Method, Pattern string
    Requires        Action        // "" means explicitly public
    Public          bool
}

var routes = []Route{
    {Method: "GET",    Pattern: "/documents/{id}", Requires: DocumentRead},
    {Method: "DELETE", Pattern: "/documents/{id}", Requires: DocumentDelete},
    {Method: "POST",   Pattern: "/login",          Public: true},
}
```

```go
func TestEveryRouteDeclaresAuthorization(t *testing.T) {
    for _, r := range router.Registered() {       // from the router itself
        decl, ok := lookup(routes, r.Method, r.Pattern)
        if !ok {
            t.Errorf("route %s %s has no authorization declaration", r.Method, r.Pattern)
            continue
        }
        if decl.Requires == "" && !decl.Public {
            t.Errorf("route %s %s requires nothing and is not marked public", r.Method, r.Pattern)
        }
    }
}
```

This is the highest-value code in the article and it took twenty lines. It doesn't verify that the declared permission is the *right* one — no test can — but it makes forgetting entirely impossible, and forgetting is the failure mode that actually ships. The `Public: true` marker matters as much as the permission: it forces the author to state that they thought about it.

What this still can't catch is the object-level rule. A route can declare `DocumentRead` correctly and then load the document by primary key with no ownership check. That's what the next section is for.

### Row-level security, and the bug that eats it

```sql
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON documents
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid);
```

```go
func (r *Repo) WithTenant(ctx context.Context, tenant TenantID,
                          fn func(*sql.Tx) error) error {
    tx, err := r.db.BeginTx(ctx, nil)
    if err != nil { return err }
    defer tx.Rollback()

    // SET LOCAL: scoped to this transaction, discarded on commit or rollback.
    if _, err := tx.ExecContext(ctx,
        "SET LOCAL app.tenant_id = $1", tenant.String()); err != nil {
        return err
    }
    if err := fn(tx); err != nil { return err }
    return tx.Commit()
}
```

`SET LOCAL`, inside a transaction, is load-bearing, and the alternative is one of the most dangerous bugs in this entire module.

Plain `SET app.tenant_id` applies to the *session* — which, behind a connection pool, is a connection that gets handed back and reused. The next request to borrow it belongs to a different customer and inherits the previous tenant's setting. Every query then silently returns the wrong tenant's rows, intermittently, under load, in a pattern that never reproduces in development where the pool has one idle connection and one tenant. `SET LOCAL` is discarded when the transaction ends, which is why every read has to happen inside one.

Two more things to get right or the policy is theatre. The role your application connects as must not be the table owner and must not have `BYPASSRLS` — owners are exempt from their own policies by default, so a service running as the owner has RLS enabled and inapplicable. And `current_setting('app.tenant_id', true)` returns NULL when unset, which makes the policy match nothing; that's the correct failure direction, and it's worth a test that runs a query outside `WithTenant` and asserts it returns zero rows.

## Further Reading

- **OWASP API Security Top 10.** Broken object-level authorization and broken function-level authorization occupy two of the top five positions, with concrete examples. This is the empirical backing for the shape of this article.
- **Sandhu et al., "Role-Based Access Control Models" (IEEE Computer, 1996)**, and the later NIST RBAC standard. The model in its original form, including the role-hierarchy and separation-of-duty parts that most implementations skip and some regulated domains require.
- **NIST SP 800-162, _Guide to Attribute Based Access Control_.** The clearest treatment of the PDP/PEP/PIP decomposition, which is the vocabulary every policy engine's documentation assumes you already have.
- **Pang et al., "Zanzibar: Google's Consistent, Global Authorization System" (USENIX ATC, 2019).** The ReBAC paper. Read §2 for the data model and the section on consistency for the "new enemy" problem — it's the clearest explanation of why distributed authorization is harder than it looks.
- **PostgreSQL documentation, _Row Security Policies_.** Short, and covers the owner-exemption and `BYPASSRLS` behaviours that turn a policy into decoration.
- **Open Policy Agent / Rego documentation, and the AWS Cedar language reference.** Two different answers to "policy as data" — Rego general and dataflow-oriented, Cedar deliberately constrained so policies can be formally analyzed. Reading both clarifies the trade being made.
- **Open implementations worth studying even if you don't adopt them:** OpenFGA and SpiceDB for Zanzibar-style ReBAC, Casbin and Cerbos for policy-based enforcement. The data models are the education.
- **Norm Hardy, "The Confused Deputy" (1988).** Two pages, from 1988, explaining why authority carried with a request behaves differently from authority looked up by identity — the argument underneath capability tokens and signed URLs.

A **TypeScript** sibling would show something Go's explicitness hides. In an ORM-centric stack, the natural enforcement point is the data layer itself — a client extension or middleware that injects the tenant filter into every query, so scoping becomes structural rather than remembered. That's a genuinely better answer for the forgotten-`WHERE`-clause problem than anything in this article, and it brings its own failure mode: when the scoping is invisible, the code paths that legitimately need to bypass it (admin tooling, background jobs, migrations) become the interesting attack surface, and they're easy to write by accident. Not yet written.

---

The question to carry out of this article is not which model to pick. It's: **what happens on the endpoint nobody thought about?**

Every design here is really an answer to that. Checks written inline in handlers answer "it's wide open." A registry with default deny answers "it doesn't ship." Repository-level scoping answers "it returns nothing." Row-level security answers "the database refuses." Those are four different postures toward the same inevitability, which is that on a long enough timeline, someone forgets — and the system's real authorization model is whatever is true in that moment, not whatever is written in the design document.
