# Sessions and Tokens

_Module 4.1 — Authentication & Authorization_

## The Problem

Start with the login endpoint you've already written.

```
POST /login
{ "email": "dana@acme.io", "password": "…" }
→ 200 OK
```

The server looked the user up, ran the submitted password through bcrypt, compared it to the stored hash, and said yes. At that instant, the server knows exactly who this is.

Then the response goes out, and the process moves on to other people's requests. Two seconds later:

```
GET /invoices/4417
```

Nothing in that request says who sent it. HTTP carries no memory between requests — that's not an oversight, it's the design. The server that just authenticated Dana has no idea this is Dana. There isn't even a stable "server" to remember: the next request may land on a different instance, in a different availability zone, in a process that started after the login happened.

So the knowledge established at login has to be **carried by the client, on every subsequent request**. The only question is what to carry.

### The obvious answer, and the four things wrong with it

Send the credentials every time. HTTP has a header for exactly this:

```
Authorization: Basic ZGFuYUBhY21lLmlvOmh1bnRlcjI=
```

It works. Every request is self-describing, the server needs no memory at all, and you can stop reading. Except:

**1. The password is now on the wire constantly.** A secret's exposure scales with how many times you handle it. Sent once at login, it passes through your TLS terminator, your framework, and your password-verification function — that's three places it could leak. Sent on every request, it also lives in the browser's memory for the whole session, in the mobile app's keychain, in the reverse proxy's access log the day someone enables verbose logging, and in the crash dump from last Tuesday.

**2. Verification is deliberately, expensively slow.** bcrypt and Argon2 are slow on purpose — that's the entire mechanism (Module 4.2). Tuned correctly, a single verification costs something like 100ms of CPU. At 200 requests per second, you need roughly twenty cores doing nothing but re-proving something you already proved.

```
  per-request cost with Basic auth        per-request cost with a session
  ┌──────────────────────────┐            ┌──┐
  │ bcrypt  ~100 ms          │            │  │ lookup ~0.3 ms
  └──────────────────────────┘            └──┘
```

**3. You cannot revoke it.** Logout is a lie — the client forgets the password, the password keeps working. An employee leaves, a laptop is stolen, a phishing page collects a credential: your only lever is forcing a password change, which also signs the user out of every device they own and does nothing about the thirty seconds before they notice.

**4. It's all-or-nothing and forever.** There's no "this credential is valid for ten minutes," no "this one may read but not write," no "this one is for the mobile app specifically." One secret, full power, unlimited lifetime.

### What the failures ask for

Each complaint is a requirement:

- something **issued at login**, so the password is handled once
- **cheap to verify**, so it's not on the expensive path
- that **expires on its own**
- that can be **revoked** before it expires
- that can be **scoped** — narrower than the password it stands in for
- and is **disposable**, so throwing it away is a real logout

That thing is what every authentication system, underneath the acronyms, is actually building.

## What It Is

The substitute credential is a **session token**: a string issued after successful authentication, presented on subsequent requests, and accepted by the server as proof of the earlier login.

There are exactly two ways to build one, and the difference is *where the truth lives*.

```
REFERENCE TOKEN                           SELF-CONTAINED TOKEN
truth on the server                       truth inside the token

 client                                    client
  │ Cookie: sid=8f3c9a…                     │ Authorization: Bearer eyJ…
  ▼                                         ▼
 server ──lookup──►┌──────────────┐        server ──verify signature──► (no I/O)
                   │  sessions    │
 "who is 8f3c9a…?" │ 8f3c9a → u_91│        "did I sign this, and
                   │ a01b47 → u_44│         is it still in date?"
                   └──────────────┘
 the token means nothing by itself         the token says who you are
 revoke: delete the row                    revoke: nothing to delete
 cost: one store round-trip per request    cost: microseconds of CPU
```

A **reference token** (also: session identifier, opaque token) is a meaningless random string. It's a pointer. All the actual state — which user, which tenant, when it was created, when it dies — sits in a store the server owns.

A **self-contained token** carries its own claims and a cryptographic signature proving the server minted it. The best-known format is the **JWT** (JSON Web Token). Verification is local: check the signature, check the expiry, done.

Everything else in this article follows from that one difference.

### Two confusions worth killing immediately

**Authentication is not authorization.** Authentication answers *who is this?* Authorization answers *may they do this?* This article is only about carrying the answer to the first one from request to request. What you do with the identity once you have it — roles, permissions, row-level rules — is Module 4.3, and keeping them separate matters more than it sounds like it should: most "auth bugs" that reach production are authorization bugs in systems whose authentication was flawless.

**"Cookies vs JWT" is a category error**, and you will hear it constantly. A cookie is a *transport* — a way for the browser to attach a string to requests automatically. A JWT is a *format* — a way to encode and sign claims. They're on different axes. You can put a JWT in a cookie (common, often correct). You can send an opaque session id in an `Authorization` header (also fine). The real questions are two independent ones: *where does the truth live* (this article), and *how does the string travel* (below). Conflating them is why so many teams end up with `localStorage` tokens they didn't need and a revocation problem they didn't want.

## Recognizing the Problem

Signals that this decision is already costing you, whether or not you made it deliberately:

- Your logout button clears client state, and a token copied beforehand still works.
- Someone asked "when does that revocation take effect?" and the honest answer was a duration, not "now."
- A user's role, plan, or tenant changed, and it doesn't apply until they log out and back in.
- You added a second app instance and users started getting logged out at random — sessions were in process memory.
- Your load balancer is configured for sticky sessions. That's a session-storage decision wearing a networking costume.
- Your `Authorization` header crossed a few kilobytes and something in the stack started returning `400` on requests that used to work.
- You put permissions in the token to avoid a database call, then added a database call to check whether the token is still good.
- Support asked which devices an account is signed in from, and there's no record that a login ever happened.
- You're running bcrypt on requests other than `POST /login`.
- A user changed their password after a phishing scare and the attacker's existing session kept working.
- Two services verify the same token and disagree about what it means, because each implemented verification separately.

## How It Works

### Reference tokens

**Generate.** Take at least 128 bits from a cryptographically secure random source. That's the whole security property: the token must be unguessable and must mean nothing. Not an incrementing integer, not a hash of the user id, not `Math.random()`, not a UUID from a library that doesn't promise a CSPRNG.

**Store.** Write a record keyed by the token: user id, created-at, expiry, and whatever else is useful — tenant, device description, IP, last-seen. Anything you put here is state you can change *without the client's cooperation*, which is the entire point of the family.

**Store a hash of it, not the token.** The sessions table is a table of live credentials. If it leaks — a backup on an open bucket, a read-replica with loose access, an SQL injection that only reads — every one of them is a working login. Hash the token with SHA-256 and store that. On each request, hash the presented token and look up the hash. The token is already high-entropy random, so a fast hash is correct here; the slow KDFs in Module 4.2 exist for low-entropy secrets like passwords.

**Verify.** One store lookup per request. On Redis in the same availability zone that's roughly 0.2–1 ms; a primary-key hit in Postgres is in the same range. Against a request that already does three queries and renders a response, it disappears.

**Revoke.** Delete the row. Effective on the next request, everywhere, with no coordination.

### Self-contained tokens

The claims go in the payload, and a signature over the whole thing proves authenticity.

```
eyJhbGciOiJFZERTQSIsImtpZCI6IjIwMjYtMDgifQ . eyJzdWIiOiJ1XzkxIiwiZXhwIjoxNzg… . 4f9d2b7c…
└─────────────── header ──────────────────┘  └────────── payload ──────────┘  └ signature ┘
      algorithm + which key signed it            the claims: subject,            computed over
                                                 expiry, issuer, audience        header + payload
                                                 — base64, NOT encrypted
```

**The payload is readable by anyone holding the token.** Base64 is an encoding, not a cipher. Paste one into any decoder and the claims come out. Signing proves the token wasn't *altered*; it hides nothing. Never put anything in a token you wouldn't hand to the user — and the user is not always the person you think, because tokens end up in logs, in `Referer` headers, in browser history, and in bug reports. (Encrypted tokens exist — JWE — and are almost never what you actually want; the usual right answer is to not put the secret in the token.)

**Signing comes in two shapes, and the choice is about trust, not cryptography.** With a shared secret (HMAC, `HS256`), anyone who can verify can also mint. That's fine inside one service. With a key pair (`EdDSA`, `ES256`, `RS256`), the issuer holds the private key and verifiers only need the public one, published at a well-known URL as a JWKS. The moment a second party verifies your tokens, you want asymmetric — otherwise "let them check tokens" and "let them forge tokens" are the same grant.

**Verification** is: check the signature against a key you chose, then check the claims — `exp` in the future, `iss` is who you expect, `aud` is *you*. Local, no I/O, microseconds.

**Revocation is where the family runs out of road.** There is nothing to delete. A token that says `exp: 14:30` will be accepted until 14:30 by every service that trusts it, no matter what happened to the account at 14:05. That gap is not a bug to be fixed later; it's a structural property you are choosing.

### The hybrid, and what it actually buys

The standard response is to make the gap small and bounded:

- an **access token** — self-contained, short-lived (5–15 minutes), presented to APIs
- a **refresh token** — long-lived, single-purpose, and *a reference token*: it means nothing on its own, it's stored server-side, and its only power is to be exchanged for a new access token

```
      issued                     revoked                     expires
        │                           │                           │
  ──────┼───────────────────────────┼───────────────────────────┼──────►
        │◄─── accepted by every service that trusts the key ───►│
                                    │◄──── exposure window ────►│
                                              = access token TTL
                                    │
                                    └─ refresh is checked against the store,
                                       so the *next* refresh fails
```

Be clear-eyed about what happened here. Revocation didn't become immediate; it became bounded by the access-token TTL. You are paying a refresh round-trip every ten minutes to buy a ten-minute worst case, and you've reintroduced a server-side session store — the refresh token *is* one — while keeping the self-contained token on the fast path. That's a real, defensible engineering trade. It is not "stateless authentication."

**Refresh tokens should rotate.** Each exchange issues a new refresh token and invalidates the old one. If an already-used one is ever presented again, that means two parties hold copies, which means theft: kill the entire family of tokens descended from that login and force a re-authentication. Rotation with reuse detection is the mechanism that turns a stolen long-lived credential from permanent access into a detectable event.

### Where the string lives in a browser

Independent of format, and worth getting right.

A cookie with `HttpOnly` is unreadable from JavaScript. `localStorage` is readable by any script running on your origin — including one injected through a compromised npm dependency or a stored-XSS bug. That's the usual argument, and it's correct, but the usual conclusion is overstated: if an attacker can execute JavaScript on your origin, `HttpOnly` prevents them from *exfiltrating* the token, not from *using* it — they can simply make the requests from the victim's browser, with the cookie attached automatically. `HttpOnly` converts "steal the credential and use it from anywhere, forever" into "act as the user while their tab is open," which is a meaningful downgrade in blast radius, not a cure.

Cookies bring a cost of their own: they're attached automatically, which is exactly what CSRF exploits. `SameSite=Lax` (the modern default) stops the common cross-site form-post attack; `SameSite=Strict` or explicit anti-CSRF tokens cover the rest. The `__Host-` name prefix is worth knowing — a cookie named `__Host-sid` is only accepted by browsers if it's `Secure`, path `/`, and has no `Domain` attribute, which prevents a compromised subdomain from planting a session cookie on your main site.

## When It's Appropriate

**Reach for reference sessions when:**

- The client is a browser and you control the origin, or a set of subdomains under one parent. The cookie mechanism does the work for you.
- You need to answer operational questions about live logins: *who is signed in, from where, since when, and log this one out.* A session store answers these by existing. Nothing else does.
- Revocation latency needs to be seconds, not minutes. Admin tooling, anything financial, anything with support-staff impersonation, anything where an account takeover is an incident you'll have to write up.
- The lookup is noise. At 5,000 requests/sec, a single Redis node handling one lookup per request is running at a small fraction of its capacity, in a system that's already doing far more work per request than that.
- You already run Redis or Postgres, and you are not running an identity provider.

For most single-product web applications, this is the correct default, and the fact that it's unfashionable doesn't change that.

**Reach for self-contained tokens when:**

- **A verifier can't reach your session store.** Another team's service, a CDN edge worker, a function in a different cloud account, a partner integration. This is the original problem JWTs were designed for, and when you have it, nothing else is as clean.
- **Fan-out is high.** One user request touches twelve services, each of which must independently establish who the caller is. Twelve store lookups versus twelve signature verifications is a real difference, and the twelve-way dependency on one store is a bigger one.
- **You aren't the issuer.** You've integrated Okta, Entra ID, Auth0, Cognito, or Keycloak, and they hand you signed tokens. You consume the format because it's the interoperable one. This is probably the most common legitimate reason in practice, and it's a consequence of a different decision (Module 4.1's OAuth/OIDC article), not a decision you're making here.
- **The client has no cookie jar.** Machine-to-machine calls, CLI tools, server-side integrations.
- **Verification must survive the issuer being down.** If the auth service is unreachable, signature checks still work; store lookups don't.
- **The grant is short-lived and single-purpose by nature.** A pre-signed download link, a one-time upload authorization, an email confirmation link, a webhook callback credential. These expire faster than you'd ever want to revoke them, which makes the family's one weakness irrelevant. Self-contained tokens are excellent at things that die young.

## When It's Unnecessary or Overkill

**JWTs in a single-origin monolith with a browser front end.** You took on revocation latency, key management, token bloat, and a whole class of verification bugs in order to avoid a sub-millisecond lookup against a datastore you were already querying four times in the same request. This is the single most common unnecessary adoption in the whole module.

**"Stateless, so we can scale horizontally."** The app tier is stateless either way — you achieve that by moving sessions *out of process memory* into a shared store, which is level 1 below and takes an afternoon. Your application already can't serve a request without talking to a database. One more key-value read does not change its architecture. The word "stateless" is doing persuasive work here that the engineering doesn't support.

**Access/refresh token machinery with one service and one database.** You've built a protocol to solve a distribution problem you don't have, and every client now needs refresh logic, concurrent-refresh handling, and a retry path for the 401-then-refresh-then-replay dance.

**Rolling your own token format when you're already behind an identity provider.** Consume theirs.

**Stuffing claims in to avoid a database call you then make anyway.** If the request needs the user's current plan, current permissions, or current tenant membership — all of which change — you'll be reading them fresh regardless. The token is then carrying a stale copy of data you're not using, and someone will eventually trust it.

**Building sessions at all for a pure machine-to-machine API.** A signed request (AWS SigV4 style) or mutual TLS has no login, no session, and no logout. Don't invent a lifecycle that the client doesn't have.

## Trade-offs

**What reference sessions cost you once you have them:**

- **The session store is on the critical path of every authenticated request.** Its availability is now your availability. Redis down means logged out, everywhere, instantly — so it needs replication, failover, and a plan for what the app does during a failover window (usually: fail closed, which means an outage).
- **Latency floor.** Every request pays a network round-trip before doing anything useful. Same-AZ it's negligible; cross-AZ or cross-region it stops being negligible quickly, and that's the kind of thing that's decided by an infrastructure change made by someone who doesn't know sessions live there.
- **Cross-domain gets awkward.** Cookies are scoped to a domain. The moment you have a second product on a different apex domain, you're doing redirect dances or moving to a token model anyway.
- **Sharing means sharing the store.** Letting a second service authenticate users means giving it credentials to your session store — which is also write access to everyone's sessions.
- **Sliding expiry writes.** Naively updating `last_seen` on every request converts a read-mostly store into a write-heavy one at full request volume.

**What self-contained tokens cost you once you have them:**

- **The revocation window is permanent.** Not a defect to fix in v2. Everything from here is about bounding it.
- **Claims go stale silently.** A role removed, a tenant membership revoked, a subscription downgraded, an account suspended — the token keeps asserting the old truth, confidently, with a valid signature.
- **Key management is real, ongoing operational work.** Key ids in the header, a JWKS endpoint, an overlap period where both old and new keys verify, a rotation runbook, and a plan for the day a key leaks. Set this up before launch or you'll be doing it during an incident.
- **A large footgun surface.** Accepting the algorithm named in the token (`alg: none`; RSA-public-key-as-HMAC-secret confusion). Not checking `aud`, so a token minted for one service is replayed against another. Not checking `exp`. Ignoring clock skew. Every one of these has caused real breaches, which is why RFC 8725 exists and is worth reading front to back — it's short, and it's a list of things that have already gone wrong.
- **Size.** Every request carries the token. A few claims is a few hundred bytes; a token with group memberships and permissions can reach kilobytes, and proxies have header limits (nginx defaults to 8KB across all headers). This failure arrives as intermittent `400`s for your largest, most important customers — the ones in the most groups.
- **You still can't list active sessions.** The feature "sign out of all devices" requires knowing what the devices are, which requires storing something, which is the thing you were avoiding.

**What neither of them fixes:** a bearer token is a bearer token. Whoever holds it is you. Theft — through XSS, a malicious extension, a proxy that logs headers, a leaked mobile backup — defeats both families equally. Mitigations live on a different axis: short lifetimes, cookie flags, binding the token to a key the client holds (DPoP) or to a TLS client certificate, and detecting anomalous use. Choosing a format is not a theft-prevention strategy.

## Alternatives

- **A signed stateless cookie.** Rails, Django and Flask have shipped this for years: a small payload plus a signature, stored in a cookie. It's a self-contained token that isn't a JWT, with no algorithm negotiation, no `alg: none`, and a framework-managed key. If both the issuer and the verifier are you, JWT's interoperability — its actual selling point — is worth nothing, and this gets you the same properties with fewer sharp edges.
- **PASETO, or Branca.** Same idea as JWT with the cryptographic agility removed: a version number selects one fixed algorithm suite, so the entire confusion-attack class doesn't exist. Fewer libraries, less ecosystem, less interop pressure — a good fit when you're issuing to yourself but want a documented format.
- **Delegate issuance entirely.** Don't build a login at all; consume identity from an OIDC provider and let it own credentials, MFA, and session lifetime. Covered next in this module.
- **Per-request signatures instead of sessions.** AWS SigV4 and HTTP Message Signatures have the client sign each request with a secret that never crosses the wire. Nothing to steal in transit, no session lifecycle, and replay protection built in — at the cost of client complexity that only makes sense for machine callers.
- **Mutual TLS.** The transport authenticates the client. Common inside service meshes and in regulated B2B integrations; useless for consumer browsers.
- **Proof-of-possession over bearer.** DPoP (RFC 9449) and mTLS-bound tokens don't replace either family — they attach a token to a key the client holds, so a stolen token alone is worthless. This is the direction the ecosystem is moving for high-value credentials.

## How to Achieve It

Incremental path, with the signal that says it's time for the next step.

**Level 0 — the framework's session, in process memory.** Every web framework ships one. It's correct and it's enough for a single process.
*Signal to move:* you're about to run two instances, or you've noticed that every deploy logs everyone out.

**Level 1 — move the store out of the process.** Redis or a `sessions` table. This is an afternoon's work and it delivers most of what people believe JWTs deliver: any instance can serve any request, deploys don't sign anyone out, and you can scale the app tier freely.
*Signal you've arrived:* you can kill any app server without anyone noticing.

**Level 2 — make the store earn its keep.** Hash session ids at rest. Record device, IP, created-at, last-seen. Enforce *both* an idle timeout and an absolute one. Invalidate every session for a user when their password changes or MFA is reset. Now "sign out everywhere," "these are your active devices," and "revoke that laptop" are small features rather than architecture changes.
*Signal:* the first support ticket about a lost phone.

**Level 3 — introduce a self-contained token at the one boundary that needs it.** Not everywhere. Keep the browser on cookies; issue a short-lived signed token to the service that can't reach your store, minted by the service that can.
*Signal:* you are about to hand another team credentials to your session store.

**Level 4 — become a real issuer.** Asymmetric keys, `kid` in the header, a published JWKS endpoint, a documented rotation procedure with an overlap window, clock-skew tolerance, and one shared verification library so twelve services can't implement twelve subtly different checks.
*Signal:* more than a couple of verifiers, or any verifier you don't employ.

**Level 5 — stop issuing.** Move to an identity provider and consume its tokens. Everything above becomes someone else's operational problem, and you inherit their model instead. → the OAuth 2.0 / OIDC article.

**Migrating between families:** accept both during the transition. Verification is a chain — try the cookie, then the bearer token — and you cut over by changing what you *issue*, letting the old credentials age out naturally. Flipping both sides at once means logging out your entire user base on a Tuesday afternoon.

## Implementation

TypeScript, because the mechanism is small enough to show in full and Node's standard library exposes the primitives directly rather than behind a framework abstraction.

### Issuing a reference session

```ts
import { randomBytes, createHash } from "node:crypto";

const IDLE_MS     = 14 * 24 * 60 * 60 * 1000;  // 14 days without use
const ABSOLUTE_MS = 90 * 24 * 60 * 60 * 1000;  // 90 days, no matter what

const fingerprint = (token: string) =>
  createHash("sha256").update(token).digest("hex");

async function createSession(userId: string, req: Request) {
  const token = randomBytes(32).toString("base64url");   // 256 bits, OS CSPRNG
  const key = `sess:${fingerprint(token)}`;

  await redis.hset(key, {
    userId,
    createdAt: Date.now(),
    lastSeenAt: Date.now(),
    absoluteExpiry: Date.now() + ABSOLUTE_MS,
    ua: req.headers["user-agent"] ?? "",
    ip: clientIp(req),
  });
  await redis.expire(key, IDLE_MS / 1000);

  return token;   // the raw token goes to the client; only its hash is stored
}
```

Two things are load-bearing here and both are easy to get wrong.

`randomBytes` reads the operating system's CSPRNG. Swapping in `Math.random()` or a UUID from a non-crypto source produces a string that *looks* identical and is guessable — and the bug is invisible in every test you will ever write, because functionally it works perfectly.

Storing `fingerprint(token)` rather than `token` means the record is not itself a credential. A dump of this store gives an attacker hashes of tokens they still don't have. It costs one `sha256` per request, which is measured in microseconds.

### Attaching it to the client

```ts
res.cookie("__Host-sid", token, {
  httpOnly: true,    // not readable from document.cookie
  secure: true,      // HTTPS only
  sameSite: "lax",   // not sent on cross-site form posts
  path: "/",         // required by the __Host- prefix
  maxAge: IDLE_MS,
});
```

Four flags, each closing a specific hole. The `__Host-` prefix is the one people miss: it makes the browser refuse this cookie unless it's `Secure`, path `/`, and has no `Domain` attribute — which stops a compromised subdomain from writing a session cookie that your main site will read.

### Reading it back

```ts
async function authenticate(req, res, next) {
  const token = req.cookies["__Host-sid"];
  if (!token) return next();                       // anonymous, not an error

  const key = `sess:${fingerprint(token)}`;
  const s = await redis.hgetall(key);
  if (!s.userId) return next();

  if (Date.now() > Number(s.absoluteExpiry)) {     // idle TTL is Redis's job;
    await redis.del(key);                          // the absolute cap is ours
    return next();
  }

  req.userId = s.userId;

  // Sliding expiry — but don't write on every single request.
  if (Date.now() - Number(s.lastSeenAt) > 60_000) {
    await redis.hset(key, "lastSeenAt", Date.now());
    await redis.expire(key, IDLE_MS / 1000);
  }
  next();
}
```

The throttle on the last write is not a micro-optimization. The obvious version refreshes the expiry on every request; at 5,000 requests/sec that's 5,000 writes/sec to your session store, replicated and persisted, to maintain a timestamp that nobody needs at finer than minute granularity. It's the difference between a read-mostly store and a write-saturated one, and it's the most common reason a session store starts showing up in latency graphs.

Note also what this middleware does *not* do: it never returns 401. It establishes identity when identity is present and moves on. Whether a particular route requires a user, and which user, is a separate decision made later — that separation is what Module 4.3 is about.

### The self-contained version

```ts
import { SignJWT, jwtVerify, createRemoteJWKSet } from "jose";

const token = await new SignJWT({ tid: tenantId })
  .setProtectedHeader({ alg: "EdDSA", kid: activeKey.id })
  .setSubject(userId)
  .setIssuer("https://auth.example.com")
  .setAudience("https://billing.example.com")   // this token is for ONE service
  .setExpirationTime("10m")
  .setJti(randomBytes(16).toString("base64url"))
  .sign(activeKey.privateKey);
```

And, in the service that consumes it:

```ts
const JWKS = createRemoteJWKSet(new URL("https://auth.example.com/.well-known/jwks.json"));

const { payload } = await jwtVerify(token, JWKS, {
  issuer: "https://auth.example.com",
  audience: "https://billing.example.com",
  algorithms: ["EdDSA"],     // allowlist — never trust the token's own `alg`
  clockTolerance: 30,        // seconds; machine clocks disagree
});
```

The `algorithms` allowlist is the single most important line. Without it, a library may honour whatever the token's header claims — historically including `none`, and including "treat my RSA public key, which is public, as an HMAC secret." Both turn "verify this signature" into "accept anything."

The `audience` check is the second. A token minted for the billing service and replayed against the admin service is a privilege escalation that looks, to a naive verifier, like a perfectly valid login.

And now the honest part. Revocation:

```ts
if (await redis.exists(`revoked:${payload.jti}`)) throw new Error("revoked");
```

One line, and the store lookup you were avoiding is back. But look at what it actually costs: a revocation entry only needs to outlive the token, so with a 10-minute TTL the denylist holds ten minutes of revocations — typically a handful of entries, cacheable in process memory for a few seconds, and harmless if the check is skipped during a Redis outage because the tokens expire on their own anyway. That's a genuinely different bargain from a lookup that *must* succeed on every request. If you're going to use self-contained tokens, this is the shape that works: short lifetimes make the store optional rather than critical.

## Further Reading

- **RFC 6265, _HTTP State Management Mechanism_** — the cookie specification. The revision in progress (6265bis) is where `SameSite` and the `__Host-`/`__Secure-` prefixes are defined; read that one for anything modern.
- **RFC 7519, _JSON Web Token_** — the format itself. Short. Read it before arguing about it.
- **RFC 8725, _JSON Web Token Best Current Practices_** — twenty pages, and effectively a catalogue of every way JWT verification has been broken in the field. If you deploy JWTs without reading this, you are choosing to rediscover its contents.
- **RFC 9449, _OAuth 2.0 Demonstrating Proof of Possession (DPoP)_** — how to make a stolen token useless without the client's key. The direction of travel for high-value credentials.
- **OWASP, _Session Management Cheat Sheet_ and _Authentication Cheat Sheet_** — concrete, current, and organized as checklists you can actually run against an implementation.
- **NIST SP 800-63B, _Digital Identity Guidelines: Authentication and Lifecycle Management_** — the session-management section is the rare source that gives defensible *numbers* for idle and absolute timeouts, tied to assurance levels. Useful when someone asks why the timeout is 14 days and not 30.
- **Sven Slootweg (joepie91), "Stop using JWT for sessions" (2016)** — the canonical version of the argument in this article's "unnecessary or overkill" section, plus the follow-up answering the standard objections. Opinionated, and largely right.
- **The PASETO specification** — worth twenty minutes even if you never adopt it, because its design rationale is a precise inventory of what's wrong with algorithm agility.

A sibling article in **Java** would earn its place here. Spring Security makes the reference-versus-self-contained choice a matter of swapping one bean — `SecurityContextRepository` — which is convenient and hides exactly the property this article is trying to make visible; and its `SessionRegistry` turns "list and terminate a user's sessions" and "limit concurrent logins" into framework configuration rather than a schema decision. Seeing where a mature framework has already made these choices for you, and what it costs to disagree with it, is a different lesson from building it up out of `randomBytes`. Not yet written.

---

Both families are answering the same two questions, and it's worth carrying them out of this article as a habit: **where does the truth about "is this still valid" live, and how long are you willing for a copy of it to be wrong?** Reference sessions say: on the server, and never. Self-contained tokens say: in the token, and for up to its lifetime. Refresh-token hybrids say: on the server for the long-lived credential, ten minutes for the short one. Every authentication design you will meet — SSO assertions, API keys, signed URLs, OAuth grants — is some position on those two axes, and once you can locate it there, the acronyms stop mattering very much.
