# Which Service Is Calling? Workload Identity, mTLS and Acting for Users

_Module 36.1b — Advanced Microservices Patterns_

## The Problem

This continues the property-management platform from 36.2a and 36.2b. After those articles, traffic *entering* the platform is in good shape. The gateway verifies each caller and mints a short-lived token for one service at a time, and the BFFs call services as the user.

Traffic *between* services still runs on two older assumptions. Anything that arrives from inside the cluster is trusted. And when it isn't, one shared secret called `INTERNAL_API_KEY`, the same value in every service's environment, proves a request is "internal." Three incidents show what those assumptions cost.

**The request that came from inside.** `accounts` has an endpoint, `GET /internal/residents/export?account=…`, that returns every resident of a management company as CSV, including names, phone numbers, emails and move-in dates. It exists for a nightly reporting job. It has no authentication, because it's only reachable from inside the cluster.

`documents` has a feature for new customers: "import leases from your old system," which fetches a PDF from a URL the property manager types in. Its HTTP client has no egress controls, which is 17.1c's SSRF lesson, learned there for webhooks and not applied here.

An attacker who had phished one small management company's staff login imported a "document" from `http://accounts.internal/internal/residents/export?account=…`, once for each of 60 other companies' account IDs, which appear in public listing URLs. `documents` fetched each export from inside the cluster, where `accounts` trusted it, and stored the CSV as a document the attacker could download. The attacker downloaded 60 companies' resident lists before anyone noticed. `accounts` behaved exactly as designed. **Being inside the network was the credential**, and `documents` would make a request from inside on behalf of anyone.

**The key that was everywhere.** A debug log line in `messaging` printed outbound request headers, including `X-Internal-Key` (19.1b). The log store was readable by about 60 engineers and two contractors, and the key opened every internal endpoint of every service. Rotating it meant changing the value in six services at once, since any service with the old value would be locked out, and any service with the new value would be rejected by services still on the old one. The rotation took three weeks and two coordinated deploys, and has never been done since. Throughout the investigation, nobody could answer the first question: which calls in the access logs actually came from `messaging`? Every internal call looked the same.

**The service that did what it was told.** The first fix is to give every service its own identity and have `payments` accept calls only from the services it expects. `leases` is allowed to call `POST /autopay` to set up rent collection when a lease starts. Weeks later, the lease app gets a feature letting residents change their own autopay bank account. The `leases` endpoint reads the lease ID from the request body, and calls `payments`:

```
leases → payments   POST /autopay   { leaseId: "L-8812", paymentMethod: "pm_attacker" }
```

`payments` checks the caller and sees `leases`, which is allowed. The resident had put someone else's lease ID in the request, and `leases` hadn't checked that the resident was on that lease. `payments` switched another household's rent to an attacker's bank account. Two months of rent from three units went to the wrong account before a management company's reconciliation caught it.

`payments` authenticated the caller correctly, and it asked only half the question. It knew *which service* was calling. It didn't know *on whose behalf*, so it lent `leases`' full authority to whichever user managed to steer `leases`. This is the **confused deputy** problem, named by Norm Hardy in 1988, and it appears as soon as services trust each other.

## What It Is

**Workload identity** gives each running service a cryptographic identity, issued automatically by the platform based on what the workload *is* (which service account, namespace or deployment), rather than a secret someone copied into its environment. A service proves its identity by presenting a short-lived credential signed by an authority the other side trusts.

The common standard is **SPIFFE** (Secure Production Identity Framework for Everyone):

- A **SPIFFE ID** names a workload: `spiffe://homes.example/ns/payments/sa/payments`.
- An **SVID** (SPIFFE Verifiable Identity Document) is the credential that proves it: an X.509 certificate with the ID in its SAN, or a signed JWT.
- **SPIRE** is the reference implementation that issues and rotates SVIDs. Service meshes such as Istio and Linkerd issue SPIFFE-compatible identities of their own, and cloud platforms have equivalents: GKE Workload Identity, and IAM roles for EKS pods.

**Mutual TLS (mTLS)** is TLS where *both* sides present certificates. The server learns the client's identity from a certificate it has verified, not from an IP address or a header. With workload identity, those certificates are the SVIDs, rotated every hour or so without anyone touching them.

Two identities travel with a request that was started by a user, and a service needs both:

- **The caller:** which service is making this call, proven by mTLS.
- **The subject:** which user, if any, the call is made for, proven by a token the caller can't forge. The standard mechanism is **OAuth 2.0 Token Exchange** (RFC 8693), whose tokens can carry an `act` ("actor") claim meaning "this user, acted for by this service."

Put together, this is what "zero trust" means in practice. Nothing is trusted because of where it is on the network. Every call proves who is calling and for whom, and is authorized on both.

## Recognizing the Problem

- Internal endpoints are unauthenticated because they're only reachable from inside the cluster or the VPC.
- Firewall rules or network policies are the only thing between one service and another's admin endpoints.
- One shared key, token or password authenticates all internal calls.
- Rotating a service credential requires coordinated deploys, so it doesn't happen.
- Access logs can't say which service made a call.
- A service accepts a user ID in a request body or header from another service and acts on it.
- A service's credentials can call every endpoint of every other service.
- Static cloud access keys sit in services' environment variables.
- Any feature fetches URLs chosen by users (imports, previews, webhooks) from inside the network.

## How It Works

### Why the network isn't an identity

"Only reachable from inside" assumes everything inside is trustworthy, and three ordinary things break that:

- **SSRF.** Any service that fetches a user-supplied URL makes requests from inside on a stranger's behalf. That covers imports, link previews, webhooks and PDF rendering (17.1c).
- **A compromised workload.** A vulnerable dependency (Module 31) in one service gives an attacker a foothold inside. From there, a flat network lets them reach everything.
- **Networks change.** A peering connection, a debugging port-forward that becomes permanent, a VPN for a contractor. The boundary is only as good as its least careful change.

Network policies still help, as defense in depth, by limiting which pods can open connections to which. But they identify callers by address, and addresses are shared, reused and spoofable within a network. They can't say *who* is calling, only *from where*.

### Workload identity: issued, attested, short-lived

Compare two ways for `leases` to prove it's `leases`:

| | Shared or per-service secret | Workload identity |
|---|---|---|
| Where it comes from | someone generated it and put it in config | the platform issues it to the running workload |
| How the issuer knows who you are | it doesn't: whoever holds the secret is "leases" | attestation: the node and the orchestrator confirm this process is the `leases` service account in the `leases` namespace |
| Lifetime | months or years | about an hour, rotated automatically |
| If it leaks | valid until someone rotates it everywhere | expires within the hour; nothing to rotate by hand |
| What logs show | "internal" | `spiffe://homes.example/ns/leases/sa/leases` |

**Attestation** is the key difference. SPIRE's agent on each node asks the kernel which process is connecting, and asks Kubernetes which pod and service account that process belongs to. It issues an SVID only if the answers match a registration entry. No human handles the credential, so there's nothing to paste into a log or a chat.

Simpler options sit along the same line. **Kubernetes projected service account tokens** are JWTs with an audience and an expiry, issued per pod and verifiable through the cluster's token review API or its published keys. They're a reasonable first step without SPIRE or a mesh. **Cloud workload identity** lets a pod call cloud APIs with no static keys at all, the same move as 30's OIDC federation for CI.

### mTLS: identity on every connection

With SVIDs as certificates, every connection between services authenticates both ends:

```
leases                                         payments
  │ ── ClientHello ─────────────────────────────► │
  │ ◄──────── server cert: spiffe://…/payments ── │   leases checks: is this payments?
  │ ── client cert: spiffe://…/leases ──────────► │   payments checks: is this a workload in our trust domain?
  │                                               │   then, per endpoint: may leases call this?
  │ ═══════ encrypted, both identities known ════ │
```

Three decisions come with it:

- **Verify the server too.** The client should require that it's talking to `payments`, not just to *any* workload with a valid certificate. Otherwise a compromised service can impersonate another by answering on its address.
- **Short lifetimes replace revocation.** Revoking certificates is notoriously unreliable (CRLs and OCSP). A one-hour certificate that's never renewed after a compromise stops working within the hour.
- **Where TLS terminates matters.** mTLS identifies the *connection*. If a proxy in between terminates TLS, such as a load balancer that isn't part of the mesh, the service behind it sees the proxy's identity, not the caller's. Across such hops, use a **JWT-SVID** in a header instead: a signed identity token scoped to one audience, verified by the receiver.

A mesh (36.1a) does all of this in the sidecar or node proxy without code changes, and passes the verified peer identity to the application in a header that only the local proxy can set. The article shows it in code so the mechanism is visible. The decisions are the same either way.

### Authorizing callers: default deny, per endpoint

Knowing the caller is only useful if something decides what that caller may do. Write it down per service, per endpoint:

```
payments
  POST /autopay               ← leases
  POST /refunds               ← support-tools
  GET  /balance               ← resident-bff, staff-bff, leases
  GET  /internal/reconcile    ← reconciliation-job
  everything else             ← nobody
```

This allowlist lives with `payments`, as code or as mesh policy (Istio's `AuthorizationPolicy`). Two properties matter:

- **Default deny.** A new endpoint is callable by nobody until someone adds a line. The export endpoint in the first incident would have been reachable only by the reporting job, so `documents` would have been rejected, however it got the URL.
- **Least privilege, visible in review.** "Why can `messaging` call `payments`?" becomes a question in a pull request instead of something discovered in an incident.

### The second identity: acting for a user

Caller authorization answers "may `leases` call `POST /autopay` at all?" It can't answer "may *this resident* change *this lease's* autopay?" That needs the user, in a form `leases` can't invent.

**Never pass a user ID as data.** `{ userId: "u_81723" }` in a request body from another service means "trust me," the same problem as 36.2a's headers, one hop further in.

**Exchange tokens instead.** When `leases` needs to call `payments` for a user, it presents two things to an internal **security token service** (STS): the user's token, as received from the gateway, and its own identity, via mTLS. The STS checks a policy (may `leases` act for users toward `payments`, with scope `autopay:write`?) and returns a new token:

```json
{
  "sub": "user:u_81723",
  "acct": "mgmt_2231",
  "aud": "payments",
  "scope": "autopay:write",
  "act": { "sub": "spiffe://homes.example/ns/leases/sa/leases" },
  "exp": 1790000060
}
```

It lasts 60 seconds, is valid only at `payments`, carries only the scope this call needs, and says exactly who is acting for whom. If `payments` in turn calls another service for the same user, the exchange repeats and the `act` claims nest, preserving the whole chain for audit.

`payments` then authorizes **both**:

1. **The caller**, from mTLS: `leases` may call `POST /autopay`.
2. **The subject**, from the token: `u_81723` is the payer on lease `L-8812`. `payments` checks this against its own data.

It also checks that **the token's actor is the connection's peer**. A token saying "acted for by `leases`" presented over a connection from `messaging` is a stolen token. The formal version of this binding is certificate-bound tokens (RFC 8705), where the token carries a hash of the certificate it was issued to.

In the third incident, the resident's token would have named `u_81723`. `payments` would have found that `u_81723` isn't the payer on `L-8812` and returned `403`, however trusted `leases` was.

### Calls with no user

Some calls aren't made for anyone: the nightly reconciliation, a retention job, a cache warmer. They use the service's own identity, with permissions scoped to exactly that job. Two rules:

- **Jobs don't impersonate users.** Minting a user token for a batch job hides who actually did the work, and gives the job every permission every user has. Make "system, acting for itself" an explicit identity with its own narrow allowlist.
- **Asynchronous work carries the subject as data, not as authority.** A queued job that must act "for" a user later records the user ID for audit, and the consumer authorizes the work with its own service identity and explicit rules. A user token doesn't survive a queue: it expires, and replaying it later is the wrong model anyway (Module 10).

### Operating it

- **Rotation has to keep working.** If SPIRE's server or the mesh's certificate authority is down longer than certificates live, every certificate expires and all internal traffic stops. Set lifetimes long enough to outlast a control-plane outage (agents cache and renew at half-life), and alert on time until expiry per workload.
- **Clocks matter.** Certificates and 60-second tokens both depend on synchronized clocks. A node whose clock drifts a few minutes rejects valid credentials. Monitor NTP like any dependency.
- **Migrate in permissive mode.** Meshes can accept both plaintext and mTLS while services are enrolled, which Istio calls `PERMISSIVE`, then require mTLS with `STRICT` once traffic confirms every caller has an identity. Switching straight to strict is how migrations cause outages.
- **Log identities.** Every access log line records the caller's SPIFFE ID and, when present, the subject. The first question of any investigation, who called this, becomes a query.

## When It's Appropriate

- **Workload identity and mTLS:** once there are several services, and especially when any of them handles personal data or money, fetches user-supplied URLs, or runs third-party code.
- **Per-endpoint caller allowlists:** as soon as services expose anything beyond read-only public data to each other, particularly admin, export and bulk endpoints.
- **Token exchange with actor claims:** whenever one service performs actions on user-owned objects in another service because a user asked, such as payments, messaging on someone's behalf, or documents.
- **Cloud workload identity:** as soon as a static cloud key exists in a service's configuration.

## When It's Unnecessary or Overkill

- **A monolith and its database.** There are no service-to-service calls to authenticate. Database credentials from a secrets manager (or IAM database auth) and TLS to the database are enough.
- **SPIRE when a mesh already issues identities.** Istio and Linkerd provide SPIFFE-compatible certificates and rotation. Running a second identity system alongside means two sources of truth.
- **Token exchange for calls that have no user.** A reconciliation job calling `payments` needs its own identity and an allowlist, not a delegation token.
- **Per-endpoint policy between two services owned by one team**, deployed together, with no sensitive endpoints. mTLS with a trust-domain check is proportionate. Add endpoint rules when a third service or a sensitive endpoint appears.

## Trade-offs

- **A new critical dependency.** The identity control plane (SPIRE server, mesh CA, STS) is now in the path of all internal traffic. Its outage becomes everyone's outage once certificates or tokens expire.
- **Harder debugging.** "Connection reset" or "bad certificate" replaces "connection refused," and the cause may be a clock, an expired bundle, a missing registration entry or a policy rule. Teams need tooling that shows *why* a handshake or policy check failed.
- **Latency and CPU.** TLS handshakes cost a few milliseconds and some CPU. With connection reuse the steady-state cost is small, but short-lived connections and cold pools pay it repeatedly. Token exchange adds a call to the STS, usually cached for the token's lifetime.
- **Policy is more code to own.** Caller allowlists and exchange policies drift like any configuration. A rule nobody remembers adding is as dangerous as a firewall rule nobody remembers adding.
- **Token exchange centralizes power.** The STS can mint tokens for any user toward any service. Its signing keys and policies need the same care as the gateway's (36.2a).
- **It doesn't fix bugs in the deputy.** The third incident's `leases` endpoint still failed to check lease membership. Delegation turned that bug from a theft into a `403`, but `leases` still has to validate its own input.

## Alternatives

- **Network segmentation only.** Network policies, security groups, separate VPCs. Cheap, useful as a layer, and blind to SSRF, compromised workloads and anything else inside the boundary.
- **Per-service API keys.** Better than one shared key: logs show the caller and a leak affects one service. It still means long-lived secrets, manual rotation and no attestation. Often a practical intermediate step.
- **Forwarding the user's token unchanged.** Services verify the gateway's token directly. It's simple and preserves the user, but the token has the wrong audience and too many scopes, and it says nothing about which service is presenting it (36.2a).
- **Signed internal headers without mTLS.** A JWT-SVID or a gateway-style minted token on each call. It works across proxies that terminate TLS, and doesn't encrypt the connection by itself. It's often combined with mTLS rather than replacing it.
- **A service mesh** (36.1a) provides mTLS, identities, rotation and caller policy with no code changes. That's usually the fastest route to this article's first half. Subject authorization, meaning which user may touch which object, stays in the application either way.

## How to Achieve It

**Level 1: stop trusting location.** Inventory internal endpoints, especially exports, admin and bulk operations. Replace the shared key with per-service credentials so logs show callers. Add egress controls to every feature that fetches user-supplied URLs (17.1c). *Signal for the next step:* credentials are still long-lived secrets that someone has to rotate.

**Level 2: workload identity and mTLS.** Issue SPIFFE identities through a mesh or SPIRE. Enable mTLS in permissive mode, then strict. Log peer identities. Replace static cloud keys with workload identity federation. *Signal:* every service can still call every endpoint.

**Level 3: caller authorization.** Default-deny allowlists per service and endpoint, reviewed like code, enforced in mesh policy or middleware. *Signal:* services act on user-owned objects because another service asked.

**Level 4: delegation.** An internal STS for token exchange with actor claims, tokens bound to the caller's identity, subject authorization in the service that owns the data, and explicit system identities for jobs.

## Implementation

Go with `go-spiffe` (v2), because the SPIFFE project's own libraries are in Go, and because Go's `crypto/tls` shows exactly where identity enters: in the handshake's verification callback, before any handler runs. The example is `payments`: an mTLS server, a caller allowlist, a check that binds the delegation token to the connection, and the client side in `leases`.

**The server: certificates from the Workload API, and only workloads in our trust domain:**

```go
var (
	trustDomain = spiffeid.RequireTrustDomainFromString("homes.example")
	leasesID    = spiffeid.RequireFromString("spiffe://homes.example/ns/leases/sa/leases")
	supportID   = spiffeid.RequireFromString("spiffe://homes.example/ns/support/sa/support-tools")
	reconcileID = spiffeid.RequireFromString("spiffe://homes.example/ns/payments/sa/reconciliation-job")
)

func main() {
	ctx := context.Background()

	// Talks to the local SPIRE agent over a Unix socket. Fetches this workload's
	// certificate and the trust bundle, and keeps both rotated in the background.
	source, err := workloadapi.NewX509Source(ctx)
	if err != nil {
		log.Fatal(err)
	}
	defer source.Close()

	mux := http.NewServeMux()
	mux.Handle("POST /autopay", callers(leasesID)(http.HandlerFunc(setAutopay)))
	mux.Handle("POST /refunds", callers(supportID)(http.HandlerFunc(refund)))
	mux.Handle("GET /internal/reconcile", callers(reconcileID)(http.HandlerFunc(reconcile)))
	// Anything not registered is 404; nothing is reachable by default.

	srv := &http.Server{
		Addr:      ":8443",
		Handler:   mux,
		TLSConfig: tlsconfig.MTLSServerConfig(source, source, tlsconfig.AuthorizeMemberOf(trustDomain)),
	}
	log.Fatal(srv.ListenAndServeTLS("", "")) // certificates come from the source, not files
}
```

**Caller authorization, per endpoint:**

```go
type peerKey struct{}

func callers(allowed ...spiffeid.ID) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			id, err := x509svid.IDFromCert(r.TLS.PeerCertificates[0]) // verified in the handshake
			if err != nil || !slices.Contains(allowed, id) {
				http.Error(w, "caller not allowed", http.StatusForbidden)
				return
			}
			next.ServeHTTP(w, r.WithContext(context.WithValue(r.Context(), peerKey{}, id)))
		})
	}
}
```

> **Aside — `AuthorizeMemberOf` is authentication, not authorization.** The TLS config accepts any workload in `homes.example`, which only proves the caller is one of ours. Every workload in the trust domain passes that check, including the compromised one. The per-endpoint list is what would have stopped `documents` from reaching an export endpoint, and it has to be default-deny: a handler registered without `callers(…)` is callable by every service. A test that walks the mux and fails on any route without an allowlist makes that impossible to forget.

**Both identities, and the binding between them:**

```go
func setAutopay(w http.ResponseWriter, r *http.Request) {
	caller := r.Context().Value(peerKey{}).(spiffeid.ID) // who is calling: proven by mTLS

	claims, err := delegation.Verify(r.Header.Get("Authorization"), delegation.Expect{
		Audience: "payments",
		Scope:    "autopay:write",
	})
	if err != nil {
		http.Error(w, "invalid delegation", http.StatusUnauthorized)
		return
	}
	if claims.Actor != caller.String() { // token issued to leases, presented by someone else
		http.Error(w, "token not issued to this caller", http.StatusUnauthorized)
		return
	}

	var req struct{ LeaseID, PaymentMethod string }
	if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
		http.Error(w, "bad request", http.StatusBadRequest)
		return
	}

	// On whose behalf: the user must be the payer on this lease, by payments' own records.
	if !payers.IsPayer(r.Context(), claims.Subject, req.LeaseID) ||
		!methods.OwnedBy(r.Context(), req.PaymentMethod, claims.Subject) {
		http.Error(w, "forbidden", http.StatusForbidden)
		return
	}
	// … set autopay; the audit log records subject, actor and caller.
}
```

> **Aside — where the confused deputy is stopped.** `leases` still has its bug: it never checked that the resident was on lease `L-8812`. But `payments` no longer lends `leases` its authority. It checks the user named in a token that `leases` couldn't have minted for a different user, against records `payments` owns. The attack now needs the victim's token, not just a lease ID. Both checks stay: `leases` should fix its validation, and `payments` shouldn't rely on it.

**The client side in `leases`: verify the server, exchange the user's token:**

```go
var paymentsID = spiffeid.RequireFromString("spiffe://homes.example/ns/payments/sa/payments")

func newPaymentsClient(source *workloadapi.X509Source) *http.Client {
	return &http.Client{
		Timeout: 2 * time.Second, // 36.3a
		Transport: &http.Transport{
			// Only payments may answer: a valid certificate for any other workload is rejected.
			TLSClientConfig: tlsconfig.MTLSClientConfig(source, source, tlsconfig.AuthorizeID(paymentsID)),
		},
	}
}

func setAutopayFor(ctx context.Context, userToken string, leaseID, method string) error {
	// The STS authenticates leases by mTLS, checks its exchange policy, and returns a
	// 60-second token: sub = the user, act = leases, aud = payments, scope = autopay:write.
	tok, err := sts.Exchange(ctx, sts.Request{
		SubjectToken: userToken,
		Audience:     "payments",
		Scope:        "autopay:write",
	})
	if err != nil {
		return err
	}
	return postJSON(ctx, paymentsClient, "https://payments.internal:8443/autopay", tok,
		map[string]string{"leaseId": leaseID, "paymentMethod": method})
}
```

With these pieces, the three incidents play out differently. The SSRF from `documents` reaches `accounts` over a connection with `documents`' identity, and the export endpoint allows only the reporting job. The leaked key doesn't exist; the nearest equivalent is a certificate that expires within the hour, and every log line names its caller. The autopay change reaches `payments` with the resident's own identity, which isn't the payer on that lease.

The habit to take from this: for every call between services, ask two questions. Who is calling, and how do I know without trusting the network? And for whom, and how do I know without trusting the caller? If either answer is "because it came from inside," that's the next incident.
