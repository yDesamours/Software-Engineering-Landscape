# The Front Door: What an API Gateway Should and Shouldn't Do

_Module 36.2a — Advanced Microservices Patterns_

## The Problem

Suppose you build software for property management. About 3,000 management companies use it to run 180,000 rental units. Their residents pay rent, sign leases and report broken dishwashers through a mobile app. Staff use a web app. Since last year, partners such as accounting and insurance products integrate through a public API.

Behind all three sits one API gateway in front of six services: `accounts`, `leases`, `payments`, `maintenance`, `documents` and `messaging`. The platform team runs the gateway. It terminates TLS, validates login tokens and API keys, applies rate limits, and forwards each request with two headers the services rely on: `X-User-Id` and `X-Account-Id`, the management company the request acts for. Services read those headers and trust them, because "only the gateway can reach us."

Three incidents over a year show three different ways a gateway goes wrong.

**The header anyone could send.** When the partner API launched, it got its own route group in the gateway. The standard identity plugin removes any `X-User-Id` or `X-Account-Id` a client sends before setting the verified ones, and it was attached per route group. The partner group got the API-key plugin instead, which *adds* `X-Account-Id` from the key and removes nothing.

An insurance partner's engineer, debugging their integration, copied headers from a browser session into a script, including an `X-Account-Id` for a different management company. The request reached `leases` with two `X-Account-Id` headers, the partner's and the gateway's. The service's framework read the first one. Over nine days, the partner's integration pulled 11,000 lease records belonging to 40 other management companies. The partner's engineer noticed the unfamiliar addresses and reported it. Every affected customer had to be notified.

No single service was wrong by its own rules. Everything depended on the same three assumptions: every route strips the headers, nothing reaches a service except through the gateway, and nothing inside ever sets those headers from user input. Nobody had written those assumptions down, so nobody noticed when one route quietly broke the first.

**The gateway that became the monolith.** Over two years, the gateway's configuration accumulated more and more:

- field renames so that version 2 of the mobile app would keep working
- a Lua plugin that calls `payments` to add a `lateFee` badge to lease responses
- a rule that routes the largest customer's traffic to a dedicated pool
- a response cache for maintenance categories
- a plugin that merges three calls into one for the staff dashboard

Every feature now needed a gateway change, and the platform team had a three-week queue. Then a change to the late-fee plugin threw on leases with no payment history. The plugin ran on every lease response, so the whole lease API returned `500` for 25 minutes. Deploying the gateway had become the riskiest deploy in the company, and it was owned by a team that understood none of the business logic inside it.

**The shared thing everything depends on.** The gateway validates request bodies against the OpenAPI schema (7.2), and to do that it buffers each request body in memory. On the 1st of the month, when leases start and rent is due, a large management company ran a bulk move-in: 400 residents, each uploading ID scans and photos through the app's document endpoint, which also went through the gateway.

Gateway pods ran out of memory and restarted. The remaining pods took their traffic and ran out of memory too. That's the load-redistribution cascade from 36.3a, at the front door. For 18 minutes on rent day, nothing worked: not documents, not leases, and not `payments`, the service with the most traffic that day and nothing to do with uploads.

## What It Is

An **API gateway** is a reverse proxy at the boundary between external clients and your services. It's a single entry point that handles concerns common to every request, so each service doesn't implement them differently. Its core jobs:

- **Routing:** mapping a public host, path and version to the service that handles it.
- **Edge security:** TLS, authenticating external credentials, coarse authorization, CORS, request size limits, bot and abuse rules.
- **Traffic control:** rate limits and quotas (Module 18), timeouts and deadlines (36.3a), canary routing (30.2).
- **Observability:** access logs, request IDs, and the start of the trace (19.2b).

It helps to keep the neighbors apart, since vendors use these names loosely:

- A **load balancer** distributes connections or requests across instances of one service. A gateway usually sits behind or includes one.
- An **ingress controller** is Kubernetes' mechanism for getting traffic into a cluster. The newer **Gateway API** standardizes that configuration, and many gateways implement it.
- A **service mesh** (36.1a) handles traffic *between* services (east-west). The gateway handles traffic *entering* (north-south).
- A **backend-for-frontend** (36.2b) shapes and combines responses for one client type. It's application code, owned by the client's team.
- **API management** platforms (Apigee, Azure API Management, Kong's enterprise tier) add a developer portal, key issuance, usage plans and billing for external APIs on top of a gateway.

The short version of this article: **a gateway should know about protocols, not about your business.** Everything that goes wrong in the incidents above is either a protocol job done carelessly or a business job put in the wrong place.

## Recognizing the Problem

- Services read `X-User-Id`, `X-Account-Id` or similar headers and verify nothing about them.
- Services are reachable without going through the gateway (a pod IP, an internal load balancer, a peered network), and nothing checks.
- New routes are public unless someone remembers to attach authentication.
- Gateway changes wait in one team's queue, or the gateway team reviews business logic it doesn't understand.
- Gateway plugins or scripts call services, or contain words from your domain ("lease," "invoice," "late fee").
- The gateway configuration has rules for named customers.
- Uploads, long-running requests or streams fail at the gateway's limits, and exception routes accumulate.
- A gateway deploy has caused an outage of a service unrelated to the change.
- The opposite problem, with no gateway: every service implements token validation, CORS and rate limiting a little differently, and one of them gets it wrong.

## How It Works

### What belongs at the edge

Use one test: **would this rule change if the business changed, or only if the protocol changed?** Protocol rules belong in the gateway. Business rules belong in services.

| At the gateway | Not at the gateway |
|---|---|
| TLS termination, HTTP/2 and HTTP/3 | anything that calls another service |
| routing by host, path, version, and canary weight | reshaping bodies for a client (36.2b) |
| verifying credentials: sessions, OAuth tokens, API keys | fine-grained authorization: "may this user see this lease?" (7.1b) |
| coarse authorization: authenticated, has scope `leases:read` | per-customer special cases |
| rate limits and quotas (18) | combining several calls into one response (36.2b) |
| body size limits, timeouts, the request deadline (36.3a) | caching that depends on who the user is and what they may see |
| request IDs, starting the trace (19.2b) | validation that needs a database read (7.2) |
| CORS, security headers, WAF and bot rules | anything with a domain word in its name |

Two rows deserve a note. **Coarse authorization** at the gateway is a first filter: "this API key has no `leases` scope" can be rejected cheaply at the edge. Whether *this* user may read *this* lease depends on data only `leases` has, so that decision stays in the service. **Schema validation** at the edge (7.2) is useful defense in depth. Treat it as a filter, not the only check: services still parse their own input, because internal callers never pass through the gateway.

### Handing identity to services

The gateway authenticates the external credential. The question is how it tells services who the caller is, in a form they can check. Three designs:

**1. Plain headers** (`X-User-Id: 81723`). Simple, and safe only while three conditions hold at once:

- every route, on every gateway, removes any client-supplied copy of those headers before setting its own
- no service is reachable except through the gateway: network policy, not convention
- no internal component ever sets those headers from something a user controls, such as a URL fetched on a user's behalf (SSRF) or a header copied through from an inbound webhook

Each condition erodes quietly: a new route group, a debugging port-forward that becomes permanent, a new internal tool. The first incident broke only the first condition, and that was enough.

**2. Forward the external token**, and every service verifies it. Services check a real signature, which is a big improvement. But the external token was issued for the public API. It may live for an hour, it carries every scope the client has, and every service that receives it can replay it anywhere else that accepts it.

**3. The gateway mints an internal token.** After verifying the external credential, the gateway issues a short-lived signed token, 60 seconds or so, containing what services need: the subject, the account, scopes, how the caller authenticated, and which client or partner made the request. Its audience is the specific upstream service. Services verify the signature against the gateway's published keys. This is the standard shape of **token exchange** (RFC 8693), and it's what Module 5 recommended for carrying tenant context between services: something the receiver can *check*, rather than something it must *believe*.

Use the third design, and still **strip, then set** at the gateway. Remove every incoming header in your internal namespace, whatever the route's plugins, before adding anything. A client-supplied internal token fails verification anyway, and stripping it means it never gets as far as a log line.

What happens next, when `leases` calls `payments` on the same user's behalf, is service-to-service identity: whose authority the call carries and how `payments` knows. That's 36.1b.

### Routes: declared, default-deny, owned by their service

The route table is a security boundary and a product surface, so treat it like code:

- **Default deny.** A path that isn't declared doesn't exist: the gateway returns `404` without contacting any service. Nothing becomes public because a service happened to add an endpoint.
- **Authentication is declared per route, with no default.** Every route states its mode: user session, API key, public, or authenticated by the service itself (inbound webhooks from providers, verified by signature in the service, per 17.2b). "Public" has to be written out, and CI can require a security review for it.
- **Routes live with the service that owns them.** Each team declares its routes in its own repository, and the gateway configuration is assembled from them. The Kubernetes Gateway API models this split: the platform team owns the `Gateway` (listeners, TLS, which namespaces may attach) and each team owns the `HTTPRoute` objects for its service. The platform team owns the door. Teams own their rooms.
- **Configuration changes are deploys.** They go through review, a canary and a rollback path, like code. A gateway config change can take down everything at once, which makes it more dangerous than most code.

### The gateway is the biggest shared resource you have

Every request passes through the gateway, so it's where 36.3a's lessons matter most:

- **Per-route timeouts and body limits**, not one global value. A 30-second timeout suited to report exports is 29 seconds too long for rent payment status. A 1 MB body limit is right for JSON and wrong for documents.
- **Stream, don't buffer.** A gateway that reads whole bodies into memory turns request size into memory pressure. If a plugin needs the body, such as schema validation, restrict it to routes with small, bounded bodies.
- **Large uploads skip the gateway.** Hand out pre-signed upload URLs (11.1a), so the bytes go straight to object storage and the gateway only handles the small request that authorizes the upload. That alone would have prevented rent day.
- **Set the deadline here.** The gateway is where 36.3a's deadline starts: the route's timeout becomes the budget passed to the service, and a client can't set its own.
- **Retry carefully, if at all.** A gateway retry multiplies with every retry below it (18.3). Retry only idempotent requests, only on connection failures that happened before the service received anything, and only if services don't retry the same calls.
- **Separate fleets for separate traffic.** First-party apps, the partner API and inbound provider webhooks have different volumes, limits and risk. Run them as separate gateway deployments, even from the same configuration. Then a partner's runaway integration or a webhook storm can't exhaust the gateway that handles rent payments. It's a bulkhead at the edge.
- **Capacity for losing instances.** Size the fleet so it survives losing a third of its pods at peak, and spread pods across zones. The gateway's availability is the upper bound on everything behind it (Module 1).

### Versions and transformations

Routing by version is a protocol job: `/v2/leases` goes to the new deployment, and a header selects a canary. **Rewriting bodies** so old clients keep working is a business job. It encodes knowledge of what a field means, so it rots in a place its owners never look. Keep compatibility in the service, which can serve both shapes from tested code (Module 33), or in a BFF owned by the client's team (36.2b).

### Choosing one

The main options:

- **Managed cloud gateways:** AWS API Gateway, Azure API Management, Google's API Gateway and Apigee. No servers to run, pricing per million requests, and limits you don't control (payload sizes, timeouts, plugin models).
- **Self-hosted proxies:** Envoy (directly, or via Envoy Gateway), NGINX, HAProxy, Kong and Traefik. You operate them, and you control latency, limits and extensions (Lua, WebAssembly or native filters).
- **Middleware in the application**, for a monolith or a handful of services. A load balancer plus shared middleware *is* a gateway, without a separate hop.

Questions that decide it: who operates and upgrades it, what it costs per request at your volume, how much latency it adds (typically a millisecond or a few), whether its configuration can live as code in each team's repository, and whether its extension model tempts people to put business logic in it. A powerful scripting engine is a feature and a risk.

## When It's Appropriate

- **Several services exposed to external clients.** At around three, duplicated edge concerns (auth, CORS, limits) start drifting apart, and a shared door pays for itself.
- **Several client types or a public API**: first-party apps, partners and webhooks with different credentials, limits and risk.
- **Minted internal tokens** as soon as services make authorization decisions from identity, which is nearly always, and especially with multiple tenants (Module 5).
- **Separate gateway fleets** once one traffic class can plausibly overwhelm another: a public partner API next to your own app is the common case.
- **API management features** (portal, key issuance, usage plans) when external developers are a product audience, not just a few partners you know by name.

## When It's Unnecessary or Overkill

- **A monolith behind a load balancer.** Middleware in the application does every edge job with no extra hop. Add a gateway when there's more than one thing behind the door.
- **An API management platform for three partners.** Issue keys by hand, document the API well, and add a portal when onboarding partners becomes a bottleneck.
- **A gateway in front of internal-only traffic.** Service-to-service calls don't need to go out through the front door and back in. That's the mesh's job, or simply direct calls with verified identity (36.1a, 36.1b).
- **Edge schema validation on everything.** Restrict it to routes with small bodies and stable schemas. Elsewhere it duplicates the service's own parsing and adds buffering.

## Trade-offs

- **Another hop.** A millisecond or a few of latency on every request, plus another component to monitor and patch.
- **Shared fate.** Every service's availability is capped by the gateway's. Separate fleets and generous capacity reduce this, and nothing removes it.
- **Configuration is powerful and global.** One wrong line affects every route. Treat config changes as deploys, with canaries.
- **Ownership tension.** A central team owning the gateway becomes a queue. Teams owning their routes need guardrails that keep them from weakening shared rules.
- **Minted tokens make the gateway an issuer.** Its signing key can impersonate anyone to any service, so it needs a key management service, rotation and an audit trail. Short token lifetimes make revocation unnecessary, and make clock skew matter.
- **Managed gateways trade control for convenience.** Their limits on payload size, timeouts and extensions become your product's limits, and pricing per request can dominate at high volume.
- **Edge checks create a false sense of security.** A validated request at the gateway is no reason for a service to skip its own checks. Internal callers, jobs and future entrances never pass through the door.

## Alternatives

- **No gateway, shared libraries instead.** Each service uses a common middleware package for auth, CORS and limits. It works well with few services in one language, and drifts as languages and versions multiply.
- **Mesh ingress.** Istio's ingress gateway or the mesh's own edge proxy, when a mesh already exists (36.1a). It shares configuration and identity with east-west traffic, but has less API-management tooling.
- **A CDN or edge platform** (Cloudflare, Fastly, CloudFront with functions) doing TLS, WAF, caching and even token checks close to users. It's often in front of a gateway rather than replacing it.
- **A BFF per client** (36.2b) behind a thin gateway. The gateway does protocol work, and each client's team owns the code that shapes its responses. This is the usual answer to the second incident.
- **GraphQL at the edge** (Module 8, 40.1). A single endpoint that composes data from services. It moves routing into a schema and needs its own limits on query cost.

## How to Achieve It

**Level 1: one door with default deny.** All external traffic enters through the gateway. Undeclared paths return `404`, and every route declares its authentication mode explicitly. Services are reachable only from the gateway, enforced by network policy. *Signal for the next step:* services still trust plain identity headers.

**Level 2: verifiable identity.** The gateway strips its internal namespace from every request, then mints a short-lived, audience-scoped internal token. Services verify it against the gateway's published keys and stop reading plain headers. *Signal:* gateway changes wait in one team's queue, or business logic is appearing in plugins.

**Level 3: owned routes, protocol only.** Routes live in each service's repository and are assembled with CI checks (auth mode required, public routes reviewed). Business logic moves out of plugins into services or BFFs. Config changes deploy with canaries. *Signal:* one traffic class affects another, or uploads and long requests fight gateway limits.

**Level 4: the gateway as a bulkhead.** Separate fleets per traffic class. Per-route timeouts, body limits and deadlines. Streaming by default. Uploads through pre-signed URLs. Capacity planned for losing pods at peak.

## Implementation

TypeScript on Node, with `jose` for tokens. This is a minimal gateway core that shows the decisions, not a production proxy; in production those decisions are configuration in Envoy, Kong or a managed gateway. Three pieces: the route table, the request pipeline, and verification on the service side.

**Routes, declared with no defaults:**

```ts
type Auth =
  | { kind: "user"; scopes?: string[] }      // first-party session or OAuth access token
  | { kind: "apiKey"; scopes: string[] }     // partner API
  | { kind: "public" }                       // must be written out; CI requires review
  | { kind: "service"; reason: string };     // e.g. provider webhooks, verified by signature in the service

type Route = {
  method: "GET" | "POST" | "PUT" | "PATCH" | "DELETE";
  path: URLPattern;                          // e.g. new URLPattern({ pathname: "/v1/leases/:id" })
  upstream: URL;                             // http://leases.internal
  auth: Auth;
  timeoutMs: number;                         // becomes the request's deadline (36.3a)
  maxBodyBytes: number;
  owner: string;                             // routes are assembled from each team's repository
};
```

> **Aside — the route type is the policy.** There's no optional `auth` field, so a route without an authentication decision doesn't compile, and `"public"` is a string someone had to type. The `"service"` mode exists because some routes really are authenticated downstream, such as provider webhooks whose signature covers the raw body (17.2b). Making that an explicit, reasoned exception is better than leaving the route with no auth and a comment.

**The pipeline, strip then set:**

```ts
const INTERNAL = /^(x-internal-|x-user-|x-account-|x-deadline-|x-forwarded-)|^(traceparent|tracestate)$/i;
const DROP = new Set(["host", "connection", "keep-alive", "transfer-encoding", "upgrade",
                      "te", "trailer", "proxy-authorization", "content-length"]);

export async function handle(req: IncomingMessage, res: ServerResponse) {
  const route = match(req.method!, req.url!);
  if (!route) return reply(res, 404, "not_found");              // undeclared paths don't exist

  if (Number(req.headers["content-length"] ?? 0) > route.maxBodyBytes)
    return reply(res, 413, "payload_too_large");                // before reading a byte

  const who = await authenticate(route.auth, req);              // session, JWT or API key lookup
  if (who.result === "unauthenticated") return reply(res, 401, "unauthenticated");
  if (who.result === "forbidden") return reply(res, 403, "insufficient_scope");

  const headers = new Headers();
  for (const [name, value] of Object.entries(req.headers)) {
    if (value === undefined || INTERNAL.test(name) || DROP.has(name)) continue;  // strip…
    if (name === "authorization" && route.auth.kind !== "service") continue;     // external credential stops here
    headers.set(name, Array.isArray(value) ? value.join(", ") : value);
  }
  if (who.result === "ok")                                                       // …then set
    headers.set("x-internal-identity", await mint(who.principal, route));
  headers.set("x-deadline-ms", String(route.timeoutMs - 50));
  headers.set("x-forwarded-for", clientIp(req));                // set, never append
  headers.set("x-request-id", randomUUID());

  const clientGone = new AbortController();
  res.on("close", () => { if (!res.writableFinished) clientGone.abort(); });
  const signal = AbortSignal.any([AbortSignal.timeout(route.timeoutMs), clientGone.signal]);

  try {
    const upstream = await fetch(new URL(req.url!, route.upstream), {
      method: req.method, headers, signal, redirect: "manual",
      body: hasBody(req) ? Readable.toWeb(capped(req, route.maxBodyBytes)) : undefined,
      duplex: "half",                                           // stream the body; never buffer it
    });
    res.writeHead(upstream.status, responseHeaders(upstream.headers));
    upstream.body ? Readable.fromWeb(upstream.body).pipe(res) : res.end();
  } catch (e) {
    reply(res, (e as Error).name === "TimeoutError" ? 504 : 502, "upstream_unavailable");
  }
}
```

> **Aside — `x-forwarded-for` is set, not appended.** Appending to whatever the client sent lets anyone choose the "client IP" your rate limits and audit logs use. Only the outermost proxy you operate should write it, and if a CDN or load balancer sits in front of the gateway, `clientIp()` must trust exactly that many hops and no more. The same logic applies to `traceparent`: it's dropped here and the trace starts at the gateway, as 19.2b decided for the public edge.

**Minting the internal token:**

```ts
const key = await importPKCS8(await kms.privateKeyPem("gateway-identity"), "EdDSA");

async function mint(p: Principal, route: Route): Promise<string> {
  return new SignJWT({
      acct: p.accountId,              // the management company this request acts for
      scp: p.scopes,
      amr: p.method,                  // "session" | "oauth" | "api_key"
      cid: p.clientId,                // which app or partner, for audit and per-client rules
    })
    .setProtectedHeader({ alg: "EdDSA", kid: KEY_ID })
    .setSubject(p.userId ?? `client:${p.clientId}`)
    .setIssuer("https://gateway.internal")
    .setAudience(route.upstream.hostname)   // valid at leases.internal and nowhere else
    .setIssuedAt()
    .setExpirationTime("60s")
    .sign(key);
}
```

**On the service side, verify instead of believing:**

```ts
const GATEWAY_KEYS = createRemoteJWKSet(new URL("https://gateway.internal/.well-known/jwks.json"));

export async function requireIdentity(req: Request, res: Response, next: NextFunction) {
  const token = req.header("x-internal-identity");
  if (!token) return res.status(401).end();
  try {
    const { payload } = await jwtVerify(token, GATEWAY_KEYS, {
      issuer: "https://gateway.internal",
      audience: "leases.internal",
      algorithms: ["EdDSA"],
      maxTokenAge: "90s",                    // 60 s lifetime plus clock tolerance
    });
    req.identity = {
      userId: payload.sub!,
      accountId: payload.acct as string,
      scopes: payload.scp as string[],
      client: payload.cid as string,
    };
    next();
  } catch {
    res.status(401).end();                   // forged, expired, or meant for another service
  }
}
```

> **Aside — the audience is doing real work.** A token minted for `leases` is rejected by `payments`, so a token that ends up in a log line, an error report or a compromised service can't be replayed across the system, and it expires in a minute anyway. That also means `leases` can't just forward it when it calls `payments` for the same user. It needs a new token that records both who the user is and which service is acting for them. That's the confused-deputy problem, and it's 36.1b's subject.

With these pieces, the first incident can't recur: the partner's extra header is stripped before anything reads it, and `leases` ignores headers entirely in favor of a token only the gateway can sign. The second and third incidents need the rest of the article, not more code: business logic moved out to BFFs (36.2b), document uploads moved to pre-signed URLs, and a separate gateway fleet for the partner API.

## Further Reading

- **Chris Richardson, "Pattern: API Gateway / Backends for Frontends,"** microservices.io, and _Microservices Patterns_ (Manning, 2018), chapter 8. The standard description of the gateway's responsibilities and the variants.
- **Sam Newman, _Building Microservices_, 2nd ed.** (O'Reilly, 2021), chapters on communication and security. Clear on keeping gateways thin and on where authorization belongs.
- **RFC 8693, "OAuth 2.0 Token Exchange."** The standard for swapping an external token for one scoped to an internal audience.
- **Kubernetes Gateway API documentation**, especially the role-oriented model: `GatewayClass`, `Gateway` and `HTTPRoute`, and who owns each.
- **OWASP API Security Top 10**, particularly broken object-level authorization (the first incident's consequence) and improper inventory management (undeclared and forgotten routes).
- **Envoy documentation on `x-forwarded-for` and trusted hops**, for the exact rules about which proxy may set what.
- **The `jose` library documentation** (panva/jose), for `SignJWT`, `jwtVerify` and remote key sets.
