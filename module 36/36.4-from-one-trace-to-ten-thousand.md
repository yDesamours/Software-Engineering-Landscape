# From One Trace to Ten Thousand: Reading Architecture from Traces

_Module 36.4 — Advanced Microservices Patterns_

## The Problem

This is the property-management platform again, after 36.1a. It has 14 services on a mesh, with OpenTelemetry in every service, `traceparent` forwarded on every hop, and the Collector setup from 19.3a: span metrics from 100% of spans, and tail sampling that keeps every error, every slow trace, and a uniform 5% of everything else. Tracing works. Engineers open a trace during an incident and read its waterfall, as 19.2b taught.

What they don't do is ask questions of **all** the traces at once. Four questions from one quarter went unanswered because of that, or were answered wrongly.

**"What depends on what?"** The architecture diagram in the wiki shows 14 services and 22 arrows between them. A security review of `payments` asks which services call it. The team answers from the diagram: `leases`, `support-tools` and the two BFFs. The mesh policy from 36.1a is built on that answer and switched to strict. Within minutes, the nightly reporting job fails. `reporting` calls `payments` directly about three million times a day. Everyone had believed it read a replica. Someone added the direct calls two years ago for "just the current balance."

**"Where should we spend a quarter on latency?"** The resident home screen's p99 was 1.4 seconds. The `accounts` team spent a quarter halving their p99, from 80 ms to 40 ms, and it was real, measurable work. The home screen's p99 didn't move. `accounts` runs in parallel with `payments`, which calls a ledger service that takes 700 ms at the tail. On the home screen, `accounts` finished early and waited. Making a service faster only helps if the request is waiting for it.

**"Why did rent day hurt this month?"** On the 1st, `messaging` ran at three times its usual load, and nothing in its own code had changed. Three weeks earlier, a BFF release had moved the unread-count lookup inside a loop over the resident's buildings. Calls from each home screen to `messaging` went from 1 to about 14. At normal load nobody noticed: latency barely moved, and every call succeeded. The first sign was on the 1st, when traffic peaked. Every trace since the release had shown the change. No one was looking at traces in bulk.

**"Why are 3% of lease signings slow?"** About 3% of `POST /leases/:id/sign` requests take more than five seconds. Engineers opened a dozen slow traces. Some showed time in `documents`, some in `accounts`, and some were mostly gaps. Each trace told a different story. After a week the ticket said "intermittent, cause unknown." The pattern existed, but only across hundreds of traces, not inside any single one.

Each question had an answer in the data the team already had. They were treating traces as a way to inspect **one request**, when a large set of traces is also a record of **how the system actually behaves**: its real dependencies, its real critical paths, and how its call patterns change with each release.

## What It Is

**Aggregate trace analysis** means asking questions across many traces instead of reading one. It answers architectural questions from observed behavior rather than from diagrams, code or memory. It has four main forms:

1. **The service graph:** the dependencies that actually occur, derived from parent-child relationships between spans in different services, with call rates, errors and latency on each edge.
2. **Critical-path analysis:** for each request, which spans the end-to-end latency actually waited on, aggregated across many requests into "where the time goes" for an endpoint.
3. **Call-shape tracking:** how many calls of each kind one request makes (its fan-out), per endpoint and release, so structural changes are visible when they ship rather than when they hurt.
4. **Group comparison:** what distinguishes one set of traces (slow, failed, from one tenant) from a baseline set. Which attributes, spans and shapes appear much more often in one than in the other.

This builds on Module 19. Reading one trace is 19.2b. The pipeline that produces span metrics and sampled traces is 19.3a. This article is about using what that pipeline collects to make **design decisions**: what to optimize, what to decouple, what's safe to remove, and whether the system still has the shape you intended.

## Recognizing the Problem

- The architecture diagram is maintained by hand, and nobody is sure it's current.
- "What calls this service?" or "what breaks if this is down?" is answered from memory, or with `grep`.
- A performance project improved a service's latency and the endpoints users care about didn't change.
- Regressions in call patterns (loops, extra lookups, new dependencies) are found through incidents.
- Investigations consist of opening slow traces one by one and looking for something that stands out.
- Nobody knows who still calls a deprecated endpoint (Module 33).
- A dependency between services exists in production but in nobody's design.
- Services call each other in a cycle, and nobody decided they should.

## How It Works

### The service graph: dependencies as they are

Every cross-service call produces a pair of spans: a `CLIENT` span in the caller and a `SERVER` span in the callee, with the server span's parent being the client span. For queues, `PRODUCER` and `CONSUMER` spans are linked the same way, or through span links (19.2b). Collect those pairs across all traces and you have the dependency graph, with counts, error rates and latency percentiles on each edge.

Two ways to build it:

- **From spans in the pipeline.** The OpenTelemetry Collector's `servicegraph` connector, and Grafana Tempo's metrics generator, pair client and server spans as they arrive and emit edge metrics from 100% of traffic. This is the right source for rates.
- **From stored traces.** Jaeger's dependency view and ad-hoc queries over stored traces. Useful for exploring, but biased by sampling (below).

The mesh (36.1a) produces edges too, from its proxies, without application instrumentation. Mesh edges show which services connect. Trace edges also show **why**: which endpoint of the caller, handling which inbound request, made the call. That difference matters for the next questions.

What the real graph typically shows that the diagram doesn't:

- **Undocumented edges**, like `reporting → payments`. They're often the most fragile dependencies, because nobody designed for them.
- **Dead edges and dead endpoints.** An edge the diagram shows with zero calls in 30 days, or an endpoint with no callers at all. These are candidates for removal, with evidence.
- **Cycles.** `messaging → leases → messaging`, within one request, means the two services can't be deployed, scaled or reasoned about independently. It's the distributed monolith from 2.1, and it shows up in the graph as a loop.
- **Fan-in hot spots.** A service everything depends on, whose outage is everyone's outage. These are where 36.3a's bulkheads and 36.3b's breakers matter most.
- **Depth.** The longest chain from an entry point to a leaf. Every hop adds latency and a failure point.

### Blast radius and "who calls this?"

With the graph built from traces, where each edge knows the entry point that started the request, two questions become queries instead of meetings:

- **"What breaks if `ledger` is down?"** Walk the graph backwards from `ledger` to every entry point that reaches it, and list the user-facing endpoints. It's the list of what to test in a drill (36.3a), and what to mark as degraded on a status page.
- **"Who still calls `GET /v1/balance`?"** Group server spans for that route by the caller's service and version. The answer is a list of owners to contact before removal (Module 33), and a number that shows whether the migration is progressing.

### Critical path: where the waiting actually is

A trace's **critical path** is the chain of work the end of the request actually waited on. Anything that ran in parallel and finished early is off the path. Making it faster changes nothing about end-to-end latency.

```
home screen, one trace                           critical path (bold)

resident-bff  ████████████████████████████████   ▓▓▓                          ▓▓
  accounts     ████                                  (finished early: off the path)
  payments     ██████████████████████████            ▓▓▓▓
    ledger       ███████████████████████                ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓
  messaging    ██████                                (off the path)
```

The standard algorithm walks backwards from the end of the root span. At each step it follows the child that finished last before the current point, attributes the gap after that child to the parent's own work, moves into the child, then jumps to the child's start and repeats. The result divides the request's duration among the spans that were actually on the path.

For **one** trace, this tells you what to look at. Aggregated across **thousands** of traces for one endpoint, it tells you where to invest: "on the home screen, `ledger` accounts for 61% of critical-path time at p99, `payments` itself for 14%, and `accounts` for 2%." That's the analysis the `accounts` project needed before it started. Uber published its version of this, CRISP, from running it over millions of traces.

Two refinements:

- **Aggregate by percentile band.** Where the time goes at p50 and at p99 are often different: the median waits on the database, the tail waits on a retry. Analyze the band whose latency you want to change.
- **Handle asynchronous children.** A span that starts inside a request and ends after the request returned, such as a fire-and-forget publish or a background refresh, wasn't waited on. It must be excluded, or it will appear on the critical path. Clock skew between machines (19.2b) makes the boundaries fuzzy, so allow a tolerance.

### Call shape: structural change per release

A request's **call shape** is how many calls of each kind it makes: for a home screen, 1 to `payments`, 1 to `leases`, 1 to `messaging`, and so on. Shapes change when code changes, often by accident, as in the rent-day example. Latency often doesn't move at normal load, and success rates don't move at all. So watch the shape directly:

- **Calls per request, per endpoint, per edge, per release.** From span metrics: the number of `messaging` server spans for requests whose root is `GET /home`, divided by the number of `GET /home` requests, grouped by the BFF's `service.version`. A jump from 1 to 14 on the day of a release is a finding before it's an incident.
- **Repeated identical calls within one trace:** the same operation on the same service, many times, with only an argument varying. That's the N+1 from Module 8 and 36.2b, detected from data instead of code review.
- **Sequential calls that could be parallel:** sibling spans that don't overlap in time, with no data dependency between them. The staircase from 19.2b, found across thousands of traces rather than noticed in one.

This is the observability version of a performance test: you don't need to predict the regression if you watch the thing that regresses.

### Group comparison: what's different about the slow ones?

For "why are 3% slow?", reading individual traces fails because each slow trace is slow partly for its own reasons. Comparing **groups** finds what they share. Take the slow traces and a baseline of normal ones, extract features from each, and rank features by how much more often they appear in the slow group:

- **Attributes:** tenant, app version, region, pod, feature flag variant, input size (`lease.addenda_count`).
- **Structure:** which span names appear, how many times, and how deep the trace goes.
- **Timing:** which service's share of the critical path is larger.

For lease signing, the comparison showed that 94% of slow traces had more than 30 addenda, compared with 4% of the baseline, and that slow traces contained one `documents.render_page` span per page. Rendering was per page and sequential. No single trace said "the number of pages matters." The difference between the groups did. Honeycomb's BubbleUp and similar features in other tools do this interactively. The underlying computation is simple, as the implementation shows.

### Sampling decides what you can conclude

Traces are sampled (19.3a), and **the sample is biased on purpose**: tail sampling keeps every error and every slow trace, plus a uniform fraction of the rest. That's the right policy for incidents, and it's a trap for analysis:

- **Rates and shares need unbiased data.** Error rates, calls per request and critical-path shares computed from tail-sampled traces are wildly skewed toward failures. Use **span metrics**, computed from 100% of spans before sampling, for rates. For analysis that needs whole traces, such as critical paths and call shapes, use **only the uniform baseline sample**, weighted by its sampling rate.
- **Group comparison needs a fair baseline.** Compare the slow group against the uniform sample, not against "everything stored," or the baseline is itself full of slow and failed traces.
- **Record the sampling decision on the trace.** A trace should say why it was kept (baseline, error or latency) and at what rate, so analysis can include or weight it correctly. OpenTelemetry's sampling threshold in `tracestate` and "adjusted count" conventions exist for this.

### Gaps in the data are gaps in the graph

Aggregate analysis inherits every instrumentation gap. A service without tracing is invisible, and so are its edges. An uninstrumented database, cache or third-party API appears only as time inside its caller. A broken propagation point, such as a queue that drops `traceparent`, splits one request into two unrelated traces and removes an edge. Before trusting "nothing calls this," check that the things that might call it are instrumented, and compare with mesh-level edges, which don't depend on the application forwarding context.

### From analysis to rules: architecture checks

Once the graph and call shapes are data, the intended architecture can be written as **checks** against it. In _Building Evolutionary Architectures_, Neal Ford, Rebecca Parsons and Patrick Kua call these **fitness functions**:

- No cycles between services within a request.
- Only `leases`, `support-tools`, the BFFs and `reconciliation-job` may call `payments`, which is the same list as 36.1b's policy, checked against observed traffic.
- Nothing calls `legacy-billing`.
- `GET /home` makes at most 10 calls in total, and at most 1 to each service.
- Maximum call depth from any entry point is 4.

Run them daily over the last day's span metrics and baseline traces, and alert when one fails. The diagram in the wiki stops being a claim and becomes a test.

## When It's Appropriate

- **Service graphs from traces:** once there are more services than one person can hold in their head, around ten, or whenever access policies (36.1b, 36.1a) are about to be built from a list of callers.
- **Critical-path analysis:** before any performance project on a composed endpoint, and whenever several services contribute to one user-facing latency.
- **Call-shape tracking per release:** for the handful of endpoints that dominate traffic or cost, where a hidden fan-out change would matter at peak.
- **Group comparison:** for any "some requests are slow or failing and we don't know why" investigation, before reading traces one at a time.
- **Architecture checks:** once the intended dependencies are agreed and worth protecting, especially after a decoupling effort you don't want to regress.

## When It's Unnecessary or Overkill

- **A monolith with a database and a cache.** The "graph" has three nodes, and a profiler answers where time goes better than traces do.
- **A few services owned by one team** that deploys them together. The team knows the graph, and reading individual traces is enough.
- **Architecture checks before the architecture is settled.** Rules written during a migration fail constantly and get ignored. Write them for the shape you've reached, not the one you're heading toward.
- **Custom analysis code when the backend already does it.** Jaeger's dependency and critical-path views, Tempo's service graph and TraceQL, and commercial tools' comparison features cover most needs. Write code for the questions they don't answer.

## Trade-offs

- **Storage and query cost.** Analysis needs more traces kept longer than incident response does: a uniform baseline retained for weeks, not just errors kept for days.
- **Sampling bias is easy to get wrong.** Numbers computed from the wrong sample are confidently wrong. Every analysis needs to state which sample it used and how it was weighted.
- **Instrumentation gaps become false conclusions.** "Nothing calls this" may mean "nothing instrumented calls this." Deleting an endpoint on that evidence alone is a risk.
- **Clock skew distorts critical paths.** Spans from different machines don't share a clock, so child spans can appear to start before their parents or end after them (19.2b). Algorithms need clamping and tolerances, and results near boundaries are approximate.
- **Attributes carry data.** Group comparison works best with rich attributes such as tenant, input sizes and flags, which raises the same questions about personal data in telemetry as 19.1b.
- **Checks need owners.** A fitness function that fails and alerts nobody, or everybody, is ignored within a month.

## Alternatives

- **Declared dependencies in a service catalog** (Backstage and similar). The intended graph, maintained by owners. It's the right place for ownership and intent, and it drifts from reality without something observed to compare against. Use both, and alert on differences.
- **Static analysis** of code and configuration: client libraries imported, URLs in config. It finds dependencies that exist in code but haven't been exercised yet, and misses dynamic ones and the actual rates.
- **Mesh telemetry without traces** (36.1a). Edges, rates and latency with no application instrumentation, but no causality: it can't say which inbound request caused an outbound call, so there are no critical paths and no call shapes per endpoint.
- **Network flow logs and eBPF tools.** Connection-level dependencies for everything, including uninstrumented services and databases. Coarse, and useful for filling gaps.
- **Profiling** (continuous profilers). Where time goes *inside* a process, which traces show only as unexplained gaps.
- **Reading individual traces.** Still the right tool for understanding one request. It's the wrong tool for questions about the population.

## How to Achieve It

**Level 1: the real graph.** Enable service-graph metrics in the Collector or the tracing backend. Compare the result with the documented diagram, and investigate every difference, especially undocumented edges into sensitive services. *Signal for the next step:* a latency project is being planned, or has failed to move an end-to-end number.

**Level 2: critical paths and a fair sample.** Keep a uniform baseline sample, record sampling decisions on traces, and run critical-path aggregation for the top user-facing endpoints at p50 and p99. Use it to choose performance work. *Signal:* regressions in call patterns are found through incidents.

**Level 3: call shapes and comparison.** Track calls per request per endpoint and release from span metrics, with alerts on jumps. Use group comparison (tool or code) as the first step in "some requests are slow" investigations. *Signal:* agreed architectural rules keep being broken without anyone noticing.

**Level 4: architecture as checks.** Write fitness functions for cycles, allowed callers, forbidden dependencies, maximum depth and fan-out budgets. Run them daily against observed traffic, with owners for each rule, and reconcile the observed graph with the service catalog.

## Implementation

TypeScript, as offline analysis over spans exported from the tracing backend. Most backends can export traces as OTLP JSON or through a query API, and a script is often the fastest way to ask a question the UI doesn't. Three pieces: edges for the service graph, critical-path attribution, and group comparison. The span shape is simplified:

```ts
type Span = {
  traceId: string; id: string; parent?: string;
  service: string; name: string;                 // "payments", "GET /balance"
  kind: "SERVER" | "CLIENT" | "PRODUCER" | "CONSUMER" | "INTERNAL";
  start: number; end: number;                    // ms
  error: boolean; attrs: Record<string, string | number>;
};
type Trace = { root: Span; spans: Span[]; children: Map<string, Span[]>; weight: number };
// weight = 1 / sampling probability, for traces from the uniform baseline only
```

**Edges, from server spans whose parent is in another service:**

```ts
export function serviceGraph(traces: Trace[]) {
  const edges = new Map<string, { calls: number; errors: number; via: Set<string> }>();
  for (const t of traces) {
    const byId = new Map(t.spans.map((s) => [s.id, s]));
    for (const s of t.spans) {
      if (s.kind !== "SERVER" && s.kind !== "CONSUMER") continue;
      const caller = s.parent ? byId.get(s.parent) : undefined;
      if (caller?.service === s.service) continue;              // in-process, not an edge
      const key = `${caller?.service ?? "external"} → ${s.service}`;
      const e = edges.get(key) ?? { calls: 0, errors: 0, via: new Set() };
      e.calls += t.weight;                                      // weighted: an estimate, not a count
      if (s.error) e.errors += t.weight;
      e.via.add(`${t.root.service} ${t.root.name}`);            // which entry points use this edge
      edges.set(key, e);
    }
  }
  return edges;
}
```

> **Aside — a missing parent isn't an entry point.** A server span with no parent in the trace is labeled `external` here. In practice that's either a real entry point or a caller that didn't propagate context, such as a queue consumer that dropped `traceparent` or an uninstrumented job. `reporting → payments` would have appeared as `external → payments` if `reporting` had never been instrumented. Count the `external` edges into internal-only services: each one is either an attack surface or an instrumentation gap, and both need a look.

**Critical-path attribution for one trace:**

```ts
export function criticalPath(t: Trace, tolerance = 5): Map<string, number> {
  const acc = new Map<string, number>();
  const add = (s: Span, ms: number) => {
    const key = `${s.service} ${s.name}`;
    acc.set(key, (acc.get(key) ?? 0) + Math.max(0, ms));
  };

  const walk = (span: Span, until: number) => {
    let cursor = Math.min(until, span.end);
    const kids = (t.children.get(span.id) ?? [])
      .filter((c) => c.kind !== "PRODUCER" && c.end <= span.end + tolerance)  // not awaited: off the path
      .sort((a, b) => b.end - a.end);                                         // latest finisher first
    for (const child of kids) {
      if (child.start >= cursor) continue;         // ran alongside something later on the path
      const childEnd = Math.min(child.end, cursor);
      add(span, cursor - childEnd);                // the parent's own work after this child
      walk(child, childEnd);
      cursor = child.start;
    }
    add(span, cursor - span.start);                // the parent's own work before its first child
  };

  walk(t.root, t.root.end);
  return acc;                                      // ms on the critical path, per service and operation
}
```

Summed over the baseline traces for `GET /home` in the p99 band, and divided by the total, this gives "ledger 61%, payments 14%, accounts 2%," which is the table the latency project needed.

> **Aside — the tolerance is for clocks, and it's a guess.** The filter that drops children ending after their parent treats them as fire-and-forget. With clock skew between machines, a child that was awaited can appear to end a few milliseconds after its parent and be wrongly dropped. A 5 ms tolerance is a heuristic, not a rule. Where skew is large, it's more reliable to use the caller's `CLIENT` span timings, which come from one clock, and treat the callee's `SERVER` span only as a breakdown of the time inside it.

**Group comparison, against a fair baseline:**

```ts
type Feature = (t: Trace) => string[];

export const features: Feature = (t) => [
  `tenant=${t.root.attrs["account.id"]}`,
  `app=${t.root.attrs["app.version"]}`,
  `addenda>${bucket(Number(t.root.attrs["lease.addenda_count"] ?? 0))}`,     // 0, 10, 30, 100
  ...countBy(t.spans, (s) => `${s.service} ${s.name}`)
    .map(([op, n]) => `${op} ×${bucket(n)}`),                                // structure: repeated calls
];

export function compare(slow: Trace[], baseline: Trace[], f = features) {
  const share = (ts: Trace[]) => {
    const total = ts.reduce((n, t) => n + t.weight, 0);
    const m = new Map<string, number>();
    for (const t of ts) for (const k of new Set(f(t))) m.set(k, (m.get(k) ?? 0) + t.weight / total);
    return m;
  };
  const inSlow = share(slow), inBase = share(baseline);
  return [...inSlow]
    .map(([feature, s]) => ({ feature, slow: s, baseline: inBase.get(feature) ?? 0 }))
    .filter((d) => d.slow >= 0.3 && d.slow - d.baseline >= 0.25)   // common in slow, rare in normal
    .sort((a, b) => (b.slow - b.baseline) - (a.slow - a.baseline));
}
```

For the lease signings, the top rows read `addenda>30: 94% vs 4%` and `documents render_page ×30: 91% vs 3%`. A week of reading traces had missed that, and it took a few seconds to compute. `baseline` must come from the uniform sample. Comparing against all stored traces would compare slow traces with a set already full of slow traces, and shrink every difference.

- **Jaeger documentation** on the dependency graph, trace comparison and critical-path highlighting.
