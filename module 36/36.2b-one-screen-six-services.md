# One Screen, Six Services: API Composition and Backends for Frontends

_Module 36.2b — Advanced Microservices Patterns_

## The Problem

This continues the property-management platform from 36.2a. Residents use a mobile app, staff use a web app, and partners use a public API, all through one gateway in front of six services: `accounts`, `leases`, `payments`, `maintenance`, `documents` and `messaging`.

The resident app's home screen shows six things:

- rent due and the current balance (`payments`)
- the lease summary (`leases`)
- open maintenance requests with the assigned vendor's name (`maintenance`, then `accounts` for the vendor)
- unread messages and building announcements (`messaging`)
- documents waiting for a signature (`documents`)

**First, the phone did the composition.** The app made seven calls: five in parallel, then the maintenance list, then one `accounts` lookup per open request to get the vendor's name. On a 4G connection with around 120 ms of round-trip time, the screen took 2.9 seconds at the median to load. Every new app release that touched the home screen needed changes coordinated with three backend teams. Old app versions stayed installed for years and kept making whatever calls they were built with.

36.2a described the next step: the platform team put an aggregation plugin in the gateway, and it became part of the gateway monolith. After that incident, the team moved composition out of the gateway, and it went wrong three more times.

**The aggregation service for everyone.** The first replacement was one new service, `aggregator`, owned by the platform team. It served the resident app, the staff web app and some partner endpoints. Within a year it had 40 endpoints. The mobile team needed small responses for cellular networks. The web team needed wide tables for staff screens. Both queued for the same team. A change made for the staff dashboard renamed a field that the resident app also read, and the app's maintenance tab went blank for anyone who hadn't updated. It was the gateway problem again, one hop further in.

**`Promise.all` on rent day.** The home-screen endpoint fetched its six sections with `Promise.all`. On the 1st of the month, a `messaging` deploy made its unread-count endpoint return errors for 12 minutes. `Promise.all` rejects as soon as any promise rejects, so the whole home screen failed. Residents opened the app to check their rent, on the one day most of them do, and got "Something went wrong." Support calls tripled. Rent was never unavailable. The screen was all-or-nothing, and nobody had decided that it should be.

**The filter that leaked entry instructions.** Listing maintenance requests by unit required a staff scope, so the aggregator called `maintenance` with its own service account, fetched the building's open requests, and kept only the resident's own:

```ts
requests.filter((r) => r.unitLabel.includes(resident.unitLabel))
```

A resident of unit 4B also saw 14B's and 24B's requests. Maintenance requests include entry instructions: "key in the lockbox, code 4471, the dog is friendly." For three weeks, residents of the building's high-rise tower could see how to get into their neighbors' apartments. `maintenance` had authorized correctly: it was asked, by a trusted service, for every request in the building. The authorization decision had quietly moved into a string comparison in a service that was only meant to arrange data on a screen.

## What It Is

**API composition** means building one response from several services' data, so the client makes one request instead of many. Something has to do that composing, and there are four common places:

- **The client.** Fine on a fast network with few calls, and painful on mobile, where each round trip is expensive and old versions live forever.
- **The gateway.** Tempting and wrong, as 36.2a showed: it puts screen-specific logic in the one component everyone shares.
- **A backend-for-frontend (BFF).** A small service built for one client experience, such as the resident app or the staff web app, and **owned by the team that builds that client**. The pattern was named at SoundCloud and described by Sam Newman.
- **A graph.** GraphQL (Module 8), where the client describes the shape it wants and resolvers fetch from services. At scale this becomes federation across teams' subgraphs (40.1).

A BFF is defined more by who owns it than by what code it contains. The resident app team can change the home screen's response in the same sprint as the screen, without asking anyone. That's the point of the pattern, and it's why "one aggregation service for all clients" isn't a BFF.

One boundary makes this work. **A BFF knows about screens. Services know about the business.** The BFF decides that the home screen shows the balance next to the next due date. `payments` decides whether rent is overdue and what the late fee is. When business rules drift into a BFF, they end up duplicated across every client's BFF, slightly differently.

## Recognizing the Problem

- A mobile screen makes many calls in sequence, and its load time is mostly round trips.
- Client teams wait on backend teams for changes that only affect the shape of a response.
- One "aggregation" or "experience" API serves several clients, and a change for one breaks another.
- One unavailable service blanks a screen that could have shown everything else.
- A composition service calls other services with its own credentials rather than the user's.
- Authorization-looking code lives in a BFF: filtering lists by user, account or unit.
- Business rules (late fees, eligibility, status calculations) are implemented in a BFF or a client.
- A composed endpoint's p99 is much worse than any of its dependencies' p99.
- Response shapes for old app versions are handled in the gateway, or not at all.

## How It Works

### One BFF per client experience

Give each distinct client experience its own BFF, owned by that client's team:

```
resident app ──► resident-bff (mobile team) ──┐
staff web    ──► staff-bff (web team)       ──┼──► accounts, leases, payments,
partner API  ──────────────────────────────────┘    maintenance, documents, messaging
                  (no BFF: partners get the services' own, stable APIs)
```

"Distinct experience" is a judgment call. An iOS app and an Android app that show the same screens usually share one BFF. A resident app and a staff dashboard don't: their data, sizes and release cycles are different. The **partner API usually has no BFF at all.** Partners need stable, general resources, versioned carefully (Module 33), not responses shaped around your app's screens.

A BFF's endpoints follow screens, `GET /home` and `GET /maintenance/:id`, not resources. That's deliberate. The client team can move a field from one screen to another by changing their own code in both places.

### Parallel where possible, batched where not

A composed endpoint's latency is set by its **critical path**: the longest chain of calls that depend on each other. Independent calls run in parallel. Dependent calls run in sequence. Everything else is waste.

```
naive                                           composed

balance ────────┤                               balance ────────┤
lease ────┤                                     lease ────┤
messages ────┤                                  messages ────┤
documents ──┤                                   documents ──┤
maintenance ───────┤                            maintenance ───────┤
                   vendor 1 ──┤                                    vendors [1..5] ──┤
                              vendor 2 ──┤                                   (one call)
                                    … ×5
```

The naive version's vendor lookups are an N+1, the problem Module 8 solved for resolvers, now running over HTTP between services, where each call costs milliseconds. The fix is the same: collect the keys, then make one batch call (`GET /vendors?ids=…`). This means the services you compose from need **batch endpoints**. When a BFF needs one, ask the owning team for it. Don't loop.

### The tail grows with fan-out

A screen that needs six calls has to wait for the slowest of the six. If each service's p99 is 200 ms, the chance that all six calls are faster than 200 ms is `0.99⁶ ≈ 94%`. About 6% of home screens hit at least one service's p99, so the screen's p99 is set by its services' p99.8 or worse. Jeffrey Dean and Luiz André Barroso's "The Tail at Scale" is the classic account. It's why a composed endpoint is almost always slower at the tail than anything it calls.

Three things keep it bounded:

- **A budget for each call, inside the request's deadline** (36.3a). Optional sections get tight budgets. The screen's deadline caps everything.
- **Hedging idempotent reads** (36.3a) for the dependencies with the worst tails, within a small cap.
- **Fewer calls on the hottest screens.** For a screen everyone opens, such as the home screen on the 1st, consider a precomputed read model, discussed below.

### Partial responses, by design

Decide for each section of the screen whether it's **required** or **optional** (36.3a), and let the response say what happened:

```json
{
  "rent":        { "amountDue": 184500, "dueDate": "2026-10-01", "status": "due" },
  "lease":       { "unit": "4B", "endsOn": "2027-06-30" },
  "maintenance": { "status": "ok", "items": [ ... ] },
  "messages":    { "status": "unavailable" },
  "documents":   { "status": "ok", "items": [] }
}
```

- **Required sections** fail the request. Without the balance and the lease, the home screen has nothing useful to show, and a clear error beats a misleading page.
- **Optional sections** fail alone. The client renders a small "couldn't load messages" placeholder, and the rest of the screen works.
- **The shape is explicit.** A section is `ok` or `unavailable`, not silently empty. An empty list and a failed call must look different to the client, or residents will read "no documents to sign" when the truth is "we don't know."

Two operational consequences. The endpoint returns `200` when optional sections fail, so count degraded sections as their own metric, per screen and section (36.3a). And what an unavailable section shows, whether a placeholder, a cached value or nothing, is the fallback decision from 36.3b, made per screen.

### Call with the user's identity, and let services authorize

The leak happened because the BFF called `maintenance` with **more authority than the user had**, then tried to narrow the result itself. Two rules:

1. **Call services as the user.** Use the identity the gateway verified (36.2a), exchanged for a token for each service the BFF calls (36.1b). Then `maintenance` returns only what this resident may see, using the authorization logic it already owns and tests.
2. **If a service can't answer the question a screen needs, fix the service.** "List my requests" was missing from `maintenance`, so the BFF built it from "list the building's requests" plus a filter. The right fix was a resident-scoped endpoint in `maintenance`, which is where the rule about who may see what already lived.

A BFF may filter or reshape for display: hiding closed requests, sorting by date. It must never be the only thing between one user and another user's data.

Two related traps:

- **Caching across users.** A BFF cache keyed by building, holding data fetched with elevated rights, leaks in exactly the same way. Cache per user or per authorization context, or cache only data that's the same for everyone who can see it (Module 13). This is the shared-DataLoader bug from Module 8, one layer up.
- **Logging whole responses.** A BFF sees everything a screen shows, which makes its logs a concentrated store of personal data (19.1b).

### Business rules stay in services

The late-fee badge from 36.2a's gateway plugin is a good test case. It shouldn't move into the resident BFF, because the staff BFF needs the same number, and partners' accounting integrations need it too. It belongs in `payments`: `GET /balance` returns `status: "overdue"` and `lateFee: 7500`. Each BFF displays those values its own way.

A useful check: if two BFFs would have to implement the same calculation, it's a business rule, and it belongs in the service that owns the data.

### Old app versions

Mobile apps stay installed for years. The BFF is where old response shapes live:

- **Read the app version** from a header on every request, and keep adapters for the versions still supported, in the mobile team's code, where they can be tested next to the screens that use them.
- **Set a minimum supported version**, and have the BFF tell older apps to update. This bounds how many shapes you maintain. Without it, the adapters only accumulate.
- **Measure by version.** A shape can be removed when traffic from the versions that use it drops below a threshold you've agreed on, which is the deprecation process from Module 33 applied to your own client.

### When composition should be precomputed

For the busiest screens, composing on every request may be the wrong design. A **home-screen read model** can be updated from events emitted by each service, such as `payment.recorded`, `request.updated` or `message.posted`, and stored as one document per resident (23.2b, Module 38). Loading the screen becomes one lookup. The costs are the usual ones for read models: data that's seconds old, a projector to operate, and a rebuild process. The benefit is that the screen's latency no longer depends on six services' tails. It's worth it for a screen opened by every resident on the 1st, and not for a settings page.

## When It's Appropriate

- **A BFF:** when a client, especially a mobile one, needs data from several services per screen, and its team ships on a different schedule from the service teams.
- **One BFF per experience:** as soon as two clients need meaningfully different shapes, sizes or release cycles, such as a resident app and a staff dashboard.
- **Partial responses:** on any composed screen where some sections are useful without others.
- **Batch endpoints on services:** as soon as any composer needs "these N things."
- **Precomputed read models:** for a few high-traffic screens whose inputs change far less often than they're read.

## When It's Unnecessary or Overkill

- **One client, one or two services.** The client calls them directly, or a single backend does the work. A BFF adds a service to run for no benefit.
- **A web app on a fast network with HTTP/2**, where a few parallel calls cost little and the web team owns the backend anyway.
- **A BFF per platform when the screens are identical.** iOS and Android with the same design share one BFF. Duplicating it doubles the maintenance for nothing.
- **A BFF for partners.** They need stable, documented resources, not your screens.
- **Precomputing screens that are rarely opened.** A read model for the lease-renewal settings page is infrastructure without traffic to justify it.

## Trade-offs

- **More services to run.** Each BFF is a deployable with its own on-call, dependencies, security patches and capacity planning, owned by a client team that may not have run services before.
- **Duplication across BFFs.** Some composition logic appears in both the resident and staff BFFs. That's acceptable for presentation, and a warning sign for business rules.
- **Another hop.** A BFF adds a network hop between the gateway and the services. It usually saves far more than it costs by removing round trips from the client, but only if it runs close to the services.
- **Tail latency amplifies.** A composed endpoint's p99 is worse than its dependencies' p99, and it gets worse with every section added.
- **Partial responses are harder for clients.** Every screen needs a designed state for each section being unavailable, and the app must handle them all.
- **A new place for authorization mistakes.** A BFF sees a lot, and one broad credential or cross-user cache turns it into a leak.
- **Version adapters accumulate** unless a minimum supported version is enforced.

## Alternatives

- **Client-side composition.** Simplest, and fine for web clients on fast networks. It's worst for mobile, where every screen's latency becomes a sum of round trips, and every old app version is frozen with its calls.
- **Gateway aggregation.** Some gateways can merge several upstream calls into one response. Acceptable for a simple, stable merge of two calls, and a slide back toward 36.2a's monolith for anything screen-specific.
- **GraphQL** (Module 8). The client describes the shape, and one schema serves many clients, so you don't need a BFF per experience. You pay in query cost limits, resolver batching and authorization spread across the graph (8.3a, 8.3b, 8.4). Many teams use GraphQL *as* their BFF, one per experience.
- **Federated GraphQL** (40.1). Each service team owns a subgraph, and a router composes them. It's a composition layer shared across teams, with the governance that implies.
- **Precomputed read models** (23.2b, Module 38), for the hottest screens, as above.

## How to Achieve It

**Level 1: one BFF for the client that hurts most.** Usually the mobile app. Owned by that client's team, with screen-shaped endpoints, independent calls in parallel, and user identity passed through. *Signal for the next step:* one service's outage blanks whole screens, or tail latency complaints start.

**Level 2: partial responses and budgets.** Classify sections as required or optional, give each call a budget inside the request deadline, return explicit section statuses, and count degraded sections. *Signal:* the BFF loops over calls, or filters by user.

**Level 3: batch endpoints and service-side authorization.** Replace loops with batch calls, add missing user-scoped endpoints to services, remove service accounts and cross-user caches from the BFF, and move business rules back to the services that own the data. *Signal:* a second client with different needs, or app-version handling spreading through the code.

**Level 4: a BFF per experience, and precomputed hot screens.** A separate BFF for each distinct client, version adapters with an enforced minimum version, and read models for the few screens that dominate traffic.

## Implementation

TypeScript on Node, because BFFs are usually written by client teams in their own language, and for web and React Native teams that's TypeScript. The example is `resident-bff`'s home endpoint: required and optional sections, budgets inside the request deadline, one batch call instead of a loop, and every call made as the user.

**An optional section that fails alone:**

```ts
type Section<T> = { status: "ok"; data: T } | { status: "unavailable" };

async function optional<T>(
  name: string,
  budgetMs: number,
  request: AbortSignal,                      // the request's deadline, from the gateway (36.3a)
  fetchIt: (signal: AbortSignal) => Promise<T>,
): Promise<Section<T>> {
  const signal = AbortSignal.any([request, AbortSignal.timeout(budgetMs)]);
  try {
    return { status: "ok", data: await fetchIt(signal) };
  } catch (err) {
    if (request.aborted) throw err;          // the whole request ran out of time: not this section's fault
    degraded.inc({ screen: "home", section: name, reason: reasonOf(err) });
    return { status: "unavailable" };        // never an empty list: "we don't know" ≠ "none"
  }
}
```

**The home screen:**

```ts
export async function home(req: BffRequest): Promise<HomeScreen> {
  const { signal } = req;
  const svc = servicesAs(req.identity);      // tokens exchanged per service (36.1b); no service account

  // Required: why residents open the app on the 1st. If these fail, the screen fails.
  const rent = svc.payments.balance({ signal });
  const lease = svc.leases.current({ signal });

  // Optional: each has its own budget and fails alone.
  const maintenance = optional("maintenance", 400, signal, async (s) => {
    const open = await svc.maintenance.myOpenRequests({ limit: 5, signal: s });  // resident-scoped
    const ids = [...new Set(open.flatMap((r) => (r.vendorId ? [r.vendorId] : [])))];
    const vendors = ids.length ? await svc.accounts.vendorsByIds(ids, { signal: s }) : new Map();
    return open.map((r) => ({                                                   // one batch call, not N
      id: r.id,
      title: r.title,
      status: r.status,
      vendor: r.vendorId ? vendors.get(r.vendorId)?.displayName ?? null : null,
    }));
  });
  const messages = optional("messages", 250, signal, (s) => svc.messaging.unreadSummary({ signal: s }));
  const documents = optional("documents", 250, signal, (s) => svc.documents.awaitingMySignature({ signal: s }));

  const [b, l, m, msg, docs] = await Promise.all([rent, lease, maintenance, messages, documents]);
  // Only `rent` or `lease` can reject; the optional sections always resolve.

  return {
    rent: { amountDue: b.amountDue, dueDate: b.dueDate, status: b.status, lateFee: b.lateFee },
    lease: { unit: l.unitLabel, endsOn: l.endDate },
    maintenance: m,
    messages: msg,
    documents: docs,
  };
}
```

> **Aside — `status` and `lateFee` come from `payments`.** The BFF displays them and computes neither. If the resident BFF decided "overdue" from `dueDate < today`, the staff BFF would need the same rule, and the two would disagree the first time a grace period, a holiday or a payment plan existed. Arranging values on a screen is the BFF's job. Deciding what they mean isn't.

> **Aside — when a required call fails first.** If `payments` rejects, `Promise.all` rejects immediately while the other four calls are still in flight. Make sure the framework aborts the request's signal when the handler returns, so those calls are cancelled rather than finishing for nobody, which is 36.3a's abandoned work again. And don't switch to `Promise.allSettled` for everything just to be safe: that turns required sections into optional ones without anyone deciding it.

**Old app versions, at the edge of the BFF:**

```ts
const MIN_SUPPORTED = "5.2.0";

export function forAppVersion(screen: HomeScreen, version: string) {
  if (semver.lt(version, MIN_SUPPORTED)) throw new UpgradeRequired(MIN_SUPPORTED);  // app shows "please update"
  if (semver.lt(version, "6.0.0")) return homeV5(screen);  // 5.x reads `balance`, not `rent`
  return screen;
}
```

With these pieces, the rent-day incident becomes a messages placeholder on an otherwise working screen, and a `degraded{section="messages"}` alert. The leak can't happen: the BFF has no credential that sees other residents' requests, and `maintenance` owns the question of whose requests are whose.

- **Phil Calçado, "The Back-end for Front-end Pattern (BFF),"** 2015. The SoundCloud account from someone who was there.

- **Netflix Technology Blog, "Embracing the Differences: Inside the Netflix API Redesign"** (2012). An early large-scale case for client-specific API layers.
- **OWASP API Security Top 10**, especially broken object-level authorization, the class of bug the maintenance leak belongs to.

Worth seeing in **Java** as a sibling, with virtual threads and structured concurrency (`StructuredTaskScope`, still a preview API in recent releases): a scope that fails when any required task fails cancels the others automatically, and optional sections run as tasks whose failure the scope is told to tolerate. The distinction this article makes by hand, required versus optional and cancelling what's left, becomes the shape of the code. Not yet written.

The habit to take from this: for every screen, write down what it shows when each of its sources is missing, and whose rules decide what each user may see. The first answer belongs to the BFF. The second never does.
