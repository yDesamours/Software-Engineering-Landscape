# Infrastructure as Code: Infrastructure You Can Read, Review and Rebuild

_Module 30 · CI/CD Pipelines · 30.4b_

## The Problem

Suppose a 15-engineer analytics SaaS has run on AWS for three years. Everything was set up through the web console, by whoever needed it at the time: the network, the Postgres database, the load balancers, the S3 buckets, the IAM roles, the container cluster. The application pipeline is excellent (Module 30 so far): images built once, promoted by digest, canaried into production. The infrastructure those images run on has no pipeline at all. Four things happen in one year.

**A second region takes six weeks.** A large European customer requires their data to stay in the EU (Module 34). The team needs a copy of production in `eu-central-1`. Nobody can list everything production consists of: dozens of security-group rules, IAM policies edited at 2 a.m. during incidents, database parameters tuned once and forgotten. Rebuilding by clicking takes six weeks of comparing console screens. The new region's first week of real traffic surfaces a missing database parameter (`max_connections` had been raised in production two years earlier) as connection errors under load.

**Staging isn't production, in ways nobody chose.** Staging was built by a different engineer, a year after production. It has a different load balancer TLS policy, a different database instance class, and no read replica. A bug in how the application handles replica lag never appears in staging, because staging has no replica. The team only learns what the differences are when one of them causes an incident.

**A temporary change, eight months old.** During an incident, an engineer opened the database's port 5432 to the whole internet to debug from home, intending to close it afterward. Eight months later, an external scan finds a Postgres instance reachable from anywhere. Nothing ever recorded that the rule existed, so nothing prompted anyone to remove it.

**Nobody knows who changed it, or why.** A customer's monthly exports disappear from S3. An object-lifecycle rule deletes files older than 90 days. Nobody remembers creating it. The cloud audit log shows who created it, a year ago, but not why, and the person has left. Was it deliberate cost control, or a mistake? Is it safe to remove? Nobody can say.

All four share a cause. The infrastructure existed only as its current state. There was no description of what it _should_ be, so there was nothing to reproduce from, nothing to compare environments against, nothing to review before a change, and no history explaining why things are the way they are.

## What It Is

This is **infrastructure as code (IaC)**: describing infrastructure in version-controlled files, and using a tool to create and update real resources to match them. The files become the source of truth. Changing infrastructure means changing the files, which gets the same review, history and automation as application code.

Most modern IaC is **declarative**: the files describe the desired end state ("a Postgres 17 instance of this class, reachable only from the app's security group"), and the tool works out what actions turn the current state into that one. The alternative is **imperative**: a script of steps ("create an instance, then add a rule"). Declarative definitions can be applied repeatedly and converge on the same result. An imperative script that ran halfway, or runs against infrastructure that has changed, does something nobody predicted.

A few neighbors:

- **Provisioning vs configuration management.** Provisioning tools (Terraform, OpenTofu, Pulumi, CloudFormation) create and configure cloud resources: networks, databases, clusters. Configuration management tools (Ansible, Chef, Puppet) install and configure software _on_ servers. With containers (30.4a), much of what configuration management did moves into the image, and servers become replaceable.
- **Immutable infrastructure.** Instead of modifying running servers in place, build a new image and replace them. IaC declares the infrastructure; images carry the software. Together they mean nothing in production is ever hand-modified.
- **GitOps** (30.2a) is IaC plus an agent that continuously reconciles reality to the repository, rather than applying only when someone runs the tool.
- **Compose** (30.4a) describes containers on one machine for development and tests. It doesn't provision infrastructure.

## Recognizing the Problem

- Nobody can list everything production consists of without clicking through the console.
- Recreating an environment (for disaster recovery, a new region, a new customer) would take weeks.
- Staging and production differ in ways nobody chose and nobody can enumerate.
- Infrastructure changes are made in the console, and "who changed this, and why?" has no good answer.
- "Temporary" changes made during incidents are still in place.
- The cloud audit log is the only record of infrastructure changes.
- A new engineer learns the infrastructure by asking people, not by reading anything.
- You have IaC, but people still make changes in the console, and the code no longer matches reality.

## How It Works

### 1. Desired state, plan, apply

A declarative IaC tool runs a loop with three inputs: the code (what should exist), a record of what the tool created last time (the state), and the real infrastructure (what exists now). From those it computes a **plan**, a list of actions, then **applies** it.

```
code (desired)  ──┐
state (last known)├──► plan:  + create   security group rule
reality (actual) ──┘           ~ update   db parameter max_connections 100 → 400
                               -/+ replace load balancer (listener protocol changed)
                               - destroy  s3 lifecycle rule
                         │
                         ▼
                      review  ──►  apply  ──►  reality now matches code
```

The plan is what makes IaC safer than clicking. Every change is visible, in full, before it happens.

### 2. Review the plan, not just the code

A one-line change to the code can produce a plan that destroys a database. The code diff is not enough to review; the plan is the thing to read. The most important words in any plan are **replace** ("forces replacement") and **destroy**.

Some attributes can't be changed in place: changing them means destroying the resource and creating a new one. For a stateless load balancer that's a brief blip. For a database, it's data loss. Renaming things is a subtler case. If a resource is renamed in the code, from `aws_db_instance.main` to `aws_db_instance.primary`, the tool sees one resource removed and a new one added. The plan says: destroy the old database, create an empty new one.

The protections are layered, because any one of them can be skipped:

- **Refactoring declarations** (`moved` blocks in Terraform and OpenTofu, aliases in Pulumi) tell the tool that a renamed resource is the same one.
- **Tool-level guards** (`prevent_destroy`) make the tool refuse any plan that would delete a resource.
- **Provider-level guards** (the cloud provider's own deletion protection on databases and buckets) refuse the deletion even if the tool asks.
- **Pipeline rules** can require extra approval for any plan containing replacements or deletions.

### 3. State: the map from code to reality

Terraform, OpenTofu and Pulumi keep a **state file** that maps each resource in the code to a real resource ID and records its last-known attributes. The tool needs it to know which real database `aws_db_instance.primary` refers to, to notice that a resource removed from the code should be destroyed, and to avoid querying every attribute of everything on each run.

State creates its own obligations:

- **Keep it remote, shared and locked.** A state file on someone's laptop means nobody else can safely change that infrastructure, and two people applying at once can corrupt it or leave it inconsistent. Use a remote backend (object storage, or the tool's hosted service) with locking so only one apply runs per state at a time.
- **Treat it as a secret.** State records resource attributes, which can include generated passwords, private keys and connection strings, often in plain text. Encrypt it at rest, restrict read access as tightly as production credentials, and prefer resources that keep secrets in a secret manager rather than in attributes. OpenTofu can also encrypt state client-side.
- **Never edit it by hand except as a last resort.** The tools provide commands for moving, importing and removing resources from state. Hand-editing is how state stops matching reality.

Tools built on a provider's own engine (AWS CloudFormation and the CDK on top of it, Azure Bicep) keep state inside the provider, so there's no file to manage or protect. The trade-off is that you depend on that provider's engine for everything, including its error messages and its speed.

### 4. Drift: when reality changes behind the code's back

**Drift** is any difference between the code and reality caused by changes made outside the tool: console clicks, incident fixes, other automation. IaC doesn't prevent drift; it makes it _detectable_. Run a plan on a schedule (nightly is typical) against each state; a non-empty plan with no code change means reality has drifted. Terraform and OpenTofu's `plan -detailed-exitcode` exits with code 2 when changes are pending, which makes this a simple scheduled job with an alert.

When drift is found, there are two correct responses: revert reality to match the code (the next apply does this), or change the code to match reality if the change was right. The wrong response is ignoring it, which lets code and reality diverge until nobody trusts a plan.

Two nuances:

- **Some attributes change legitimately.** An autoscaling group's current instance count changes constantly. Tell the tool not to manage those attributes (`ignore_changes`), or it will fight the autoscaler on every apply.
- **The tool only sees what it manages.** A security-group rule added in the console as a separate rule, rather than a change to a rule the tool created, is a resource the tool has never heard of. The plan stays empty. That's exactly how the open port 5432 would slip past drift detection, and why cloud-side scanning (AWS Config, a cloud security posture tool) is a complement, not a duplicate.

The working rule most teams adopt: **the console is for reading; the code is for writing.** Remove routine write access from human accounts, keep an audited break-glass role for emergencies, and require that every emergency change is written into code afterward (or reverted) within a day or two.

### 5. Structure: how much goes in one state

One state for everything is the easy start and becomes a problem. Every plan reads every resource, so plans get slow. Every apply can touch anything, so a mistake in the DNS change can affect the database. And everyone contends for one lock.

Split states along **lifecycle and ownership**: the network (changes rarely, affects everything) separately from data stores (rarely changed, dangerous to change) separately from each service's compute (changes often). Split by environment too, so a staging change can't touch production state at all. States reference each other through outputs (the network state exposes subnet IDs; the service state reads them).

Too many tiny states bring their own cost: wiring between them, ordering of applies, and changes that have to be coordinated across several. A useful heuristic is one state per thing that one team changes together, at one rate.

### 6. Environments from the same code

The staging-vs-production problem goes away once both are built from the same definitions with explicit parameters. Put shared definitions in **modules** (reusable, parameterized groups of resources, roughly functions for infrastructure) and instantiate them once per environment:

```
modules/postgres/        one definition of "our Postgres setup"
environments/staging/    postgres: db.t4g.medium, single-AZ, no replica
environments/production/ postgres: db.r6g.xlarge, multi-AZ, 1 replica
```

Now the differences between environments are exactly the parameter differences, in two files anyone can diff. Some differences are deliberate (size, cost). Others turn out to matter: the missing replica in staging is suddenly a visible line, and whether staging should have one is a decision someone can make.

Separate directories and states per environment are the common default. Tool features that switch environments within one directory (Terraform's workspaces) exist, and make it easier to apply to the wrong environment by accident.

### 7. Modules without over-abstraction

Modules are how a platform team encodes good defaults once: encryption on, deletion protection on, no public access, standard tags. They're also easy to overdo. A module wrapping a single resource and exposing all 40 of its settings as variables adds a layer to read through and removes nothing. A good module has a small interface that reflects a decision ("a Postgres database for a service," with size and redundancy as inputs) and hides the rest. Version shared modules like libraries, so a change to one doesn't silently alter every environment that uses it.

### 8. IaC in the pipeline

Infrastructure changes get the same treatment as application changes, and 30.3a's trust rules apply with extra force, because an IaC pipeline can create and destroy anything.

- **Plan on pull request.** Every PR that touches infrastructure runs a plan with read-only credentials and posts it to the PR. Reviewers review the plan, not just the code.
- **Apply on merge, from a trusted context.** Only reviewed code on main applies, using short-lived OIDC credentials bound to a protected environment (30.3a), never stored keys.
- **Apply exactly what was approved.** The PR's plan was computed against state at PR time; by merge, other changes may have landed. So re-plan on main, save that plan to a file, get approval on _that_ plan, and apply the saved file. The tool refuses to apply a saved plan if the state changed since it was made.
- **One apply per state at a time.** State locking enforces it; a pipeline concurrency group makes it orderly.
- **Policy as code.** Automated checks on the plan block known-dangerous configurations before a human even looks: a database security group open to `0.0.0.0/0`, an unencrypted bucket, a public S3 ACL. Open Policy Agent (with Conftest), Checkov and Trivy's configuration scanning all evaluate plans or code against rules like these. The open-port incident becomes a failed check on the PR that tries to introduce it.

### 9. Adopting IaC for infrastructure that already exists

Nobody starts from zero. Existing resources can be **imported**: the tool is told that a real resource corresponds to a definition in code, and records it in state. Terraform and OpenTofu's `import` blocks can generate a first draft of the configuration from the real resource.

The test of a correct import is an **empty plan**: once imported, the code matches reality exactly, and the tool wants to change nothing. Any difference in the plan is either something the code got wrong or real drift to decide about. Import one component at a time, starting with what matters most or changes most, and never with a plan that isn't empty.

## Choosing a Tool

The concepts above apply across tools. The main differences are the language you write in and where state lives.

| Tool                                   | Language                                  | State                           | Notes                                                                                                                   |
| -------------------------------------- | ----------------------------------------- | ------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **Terraform / OpenTofu**               | HCL (declarative configuration language) | State file, remote backend      | Largest provider ecosystem, multi-cloud. OpenTofu is the open-source fork created after Terraform's 2023 license change; they remain largely compatible |
| **Pulumi**                             | TypeScript, Python, Go, Java, C#          | State file or hosted service    | Real programming languages: loops, types, tests, IDE support. Also more room for cleverness that's hard to review       |
| **AWS CDK / CloudFormation**           | TypeScript and others, compiled to CloudFormation templates | Managed by AWS                  | No state file to manage. AWS only; limited by CloudFormation's own speed and behavior                                  |
| **Azure Bicep / ARM**                  | Bicep (declarative DSL)                   | Managed by Azure                | Azure's equivalent of CloudFormation                                                                                     |
| **Crossplane**                         | Kubernetes resources                      | Kubernetes                      | Cloud infrastructure as Kubernetes objects, continuously reconciled; fits teams already running GitOps (30.2a)          |
| **Ansible**                            | YAML playbooks                            | None (acts on current state)    | Mainly configuration management; can provision, without a state or plan model                                            |

The decisive questions are usually: one cloud or several (Terraform/OpenTofu and Pulumi span providers; CDK and Bicep don't); whether the team would rather write a constrained configuration language or a general-purpose one; and whether a state file to manage is an acceptable cost for what the tool provides.

## When It's Appropriate

- **More than one environment,** where parity between them matters (30.2a).
- **Anything you'd have to rebuild:** disaster recovery (Module 24), a new region for data residency, a dedicated environment for a large customer. IaC turns a six-week rebuild into an apply.
- **More than one person changing infrastructure,** where review and history prevent surprises like the lifecycle rule.
- **Compliance and audit requirements,** where "every infrastructure change was reviewed, and here's the record" is a question someone will ask.
- **Security-sensitive configuration** such as network rules, IAM and encryption, where policy checks on plans catch mistakes before they exist.

## When It's Unnecessary or Overkill

- **A single app on a platform-as-a-service** (Render, Fly.io, Vercel, Heroku) with a handful of settings. The platform is already the abstraction. A few documented settings may be all there is.
- **Short-lived experiments** that will be deleted within days. Clicking is faster, as long as they actually get deleted.
- **Resources that change every minute,** like autoscaled instances or ephemeral preview environments created by other automation. Declare the group or the template, not the members.
- **A module for everything.** Wrapping every resource type in an internal module before there's a second user adds layers without adding decisions.
- **A dozen states for three people and a few dozen resources.** Split states when plans get slow or blast radius becomes a real worry, not in advance.

## Trade-offs

- **Small changes get slower.** A one-line console change becomes a branch, a plan, a review and an apply. That's the point for most changes, and it's genuinely painful during incidents, which is why break-glass access with a codify-afterward rule exists.
- **State is a new liability.** It's a file whose loss, corruption or exposure causes real damage: lost track of resources, broken applies, leaked secrets.
- **Plans can be misread.** A reviewer who skims past "forces replacement" approves data loss. The safety of IaC depends on people reading plans, supported by guards and policy checks that don't depend on them.
- **Applies can fail halfway.** Some resources get created, others don't, and state reflects the partial result. Declarative tools recover by re-running, but a half-applied change can leave production in an in-between state for as long as it takes to fix.
- **The tool and its providers become dependencies.** Provider upgrades can change behavior or deprecate resources, and switching tools later means migrating state and rewriting definitions.
- **Code and console fight each other** until the team commits to one being the source of truth. A tool that reverts emergency fixes on its next apply is an unpleasant surprise during an incident.
- **Abstractions hide what's created.** A three-line module call can create 30 resources. Great for consistency, and harder to reason about when one of them is the problem.

## Alternatives

- **Console changes plus documentation.** Runbooks and change logs describing what was configured. It works for very small setups, and documentation drifts from reality faster than code does, with no way of detecting it.
- **Imperative scripts using the cloud CLI.** Better than clicking, since they're repeatable and reviewable. But they aren't idempotent: running one twice, or against changed infrastructure, can fail or duplicate resources, and they have no concept of deletion or drift.
- **A platform that removes the infrastructure.** PaaS and serverless platforms (Module 41) take most infrastructure decisions away, in exchange for control and sometimes cost.
- **Configuration management for server fleets.** Ansible, Chef or Puppet converging long-lived servers to a declared configuration. It's still right for fleets that can't be made immutable, and is increasingly replaced by images plus provisioning.

## How to Achieve It

1. **Set up remote state and codify one new thing.** The next piece of infrastructure anyone needs gets created through IaC, not the console. _Signal:_ the team has made a real change through a plan and apply.
2. **Import what matters most.** Usually the network and the databases. Import one component at a time; each is done when its plan is empty. _Signal:_ the resources you'd least like to lose are defined in code and protected by deletion guards.
3. **Move plan and apply into the pipeline.** Plan on PR, apply on merge with OIDC and environment protection, saved plans applied exactly. _Signal:_ nobody runs apply from a laptop.
4. **Make the console read-only.** Remove routine write access from human accounts; add an audited break-glass role. _Signal:_ infrastructure changes appear only in the repository's history.
5. **Detect drift.** Nightly plans on every state with alerts on non-empty results, plus cloud-side scanning for what the tool doesn't manage. _Signal:_ drift is found in hours, not months.
6. **Add policy checks** for the mistakes you've actually made (public databases, unencrypted storage), then the common ones from the scanners' defaults. _Signal:_ a PR reintroducing the open-port rule fails before review.
7. **Build environments from shared modules,** and split states as plans get slow or blast radius grows. _Signal:_ a new environment is a new parameter file and an apply.

## Implementation

HCL for Terraform and OpenTofu (the examples work in both), because the declarative, plan-and-state model this article describes is clearest in the tool that made it standard. The pipeline around it is GitHub Actions.

### An environment: state backend and a module call

```hcl
# environments/production/data/main.tf
terraform {
  required_version = ">= 1.10"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 6.0" }
  }

  backend "s3" {
    bucket       = "acme-tf-state"
    key          = "production/data.tfstate" # one state: production data stores
    region       = "eu-west-1"
    encrypt      = true
    use_lockfile = true # S3-native state locking
  }
}

module "analytics_db" {
  source = "../../../modules/postgres"

  name                  = "analytics-prod"
  instance_class        = "db.r6g.xlarge"
  multi_az              = true
  max_connections       = 400 # the parameter the new region was missing
  vpc_id                = data.terraform_remote_state.network.outputs.vpc_id
  app_security_group_id = data.terraform_remote_state.network.outputs.app_sg_id
}
```

The staging environment has the same file with different values. The difference between the two files is the complete list of how staging differs from production, and `max_connections` is now one of the lines someone deliberately set.

### The module: safe defaults and protections

```hcl
# modules/postgres/main.tf
resource "aws_db_instance" "this" {
  identifier                  = var.name
  engine                      = "postgres"
  engine_version              = "17"
  instance_class              = var.instance_class
  allocated_storage           = 100
  multi_az                    = var.multi_az
  parameter_group_name        = aws_db_parameter_group.this.name
  vpc_security_group_ids      = [aws_security_group.db.id]
  storage_encrypted           = true
  manage_master_user_password = true # password lives in Secrets Manager, not in state
  deletion_protection         = true # AWS refuses deletion, whatever the tool asks

  lifecycle {
    prevent_destroy = true # the tool refuses to plan a deletion
  }
}

# This resource used to be named "main". Without this block,
# the rename plans as: destroy the database, create an empty one.
moved {
  from = aws_db_instance.main
  to   = aws_db_instance.this
}

resource "aws_security_group" "db" {
  name   = "${var.name}-db"
  vpc_id = var.vpc_id
}

# The only way in: from the application's security group, on Postgres's port.
resource "aws_vpc_security_group_ingress_rule" "from_app" {
  security_group_id            = aws_security_group.db.id
  referenced_security_group_id = var.app_security_group_id
  ip_protocol                  = "tcp"
  from_port                    = 5432
  to_port                      = 5432
}
```

Every service that asks for "a Postgres database" through this module gets encryption, deletion protection, a secret-managed password, and network access only from its application. None of that depends on someone remembering it.

> **Where drift detection goes blind.** Because ingress rules here are separate resources, a rule added in the console (the incident's `0.0.0.0/0` on 5432) is a resource this state has never heard of, and the nightly plan stays empty. Managing rules inline on the security group instead would let the tool notice and remove extra rules, at the cost of the tool also removing rules other automation adds. Either way, pair drift detection with a cloud-side check that looks at reality directly, such as an AWS Config rule for security groups open to the world.

### The pipeline: plan on PR, apply the approved plan on merge

```yaml
# .github/workflows/infra-production-data.yml
on:
  pull_request:
    paths: ["infra/environments/production/data/**", "infra/modules/**"]
  push:
    branches: [main]
    paths: ["infra/environments/production/data/**", "infra/modules/**"]

permissions: {}
defaults:
  run:
    working-directory: infra/environments/production/data

jobs:
  plan:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-24.04
    environment: infra-plan # OIDC role: read the cloud account and state
    permissions: { contents: read, id-token: write, pull-requests: write }
    steps:
      - uses: actions/checkout@<full-commit-sha> # v4
      - uses: aws-actions/configure-aws-credentials@<full-commit-sha> # v4
        with: { role-to-assume: "arn:aws:iam::123456789012:role/infra-plan", aws-region: eu-west-1 }
      - uses: hashicorp/setup-terraform@<full-commit-sha> # v3
      - run: terraform init -input=false
      - run: terraform plan -input=false -lock=false -out=tfplan
      - run: terraform show -json tfplan > plan.json && conftest test plan.json # policy as code
      - run: terraform show -no-color tfplan > plan.txt # posted to the PR for review

  apply:
    if: github.event_name == 'push'
    runs-on: ubuntu-24.04
    environment: infra-production # write role; required reviewers approve this run
    concurrency: tf-production-data # one apply per state, queued in order
    permissions: { contents: read, id-token: write }
    steps:
      - uses: actions/checkout@<full-commit-sha> # v4
      - uses: aws-actions/configure-aws-credentials@<full-commit-sha> # v4
        with: { role-to-assume: "arn:aws:iam::123456789012:role/infra-apply", aws-region: eu-west-1 }
      - uses: hashicorp/setup-terraform@<full-commit-sha> # v3
      - run: terraform init -input=false
      - run: terraform plan -input=false -out=tfplan # re-plan against current state
      - run: terraform show -json tfplan > plan.json && conftest test plan.json
      - run: terraform apply -input=false tfplan # applies exactly this saved plan
```

The PR plan is for review. The apply job re-plans because main may have moved since the PR's plan was made, and applies the saved plan file, not a fresh one. If the state changes between those two steps, the tool refuses the stale plan instead of doing something nobody reviewed. The PR plan runs with `-lock=false` because it only reads; the apply takes the lock.

> **What this doesn't yet guard.** As written, the `infra-production` reviewers approve the job before its plan exists; they're approving the merge, not this exact plan. For stricter control, split the apply into two jobs: one that plans and uploads `tfplan` as an artifact, and a second, behind the environment's required reviewers, that downloads and applies it, so the approval is given with the plan in front of the approver. A plan file contains resource attributes, so the artifact needs the same care as state (short retention, restricted access).

Drift detection is a third job on a nightly schedule that runs `terraform plan -detailed-exitcode` with the read-only role, treating exit code 2 (changes pending) as an alert and exit code 1 as a failure.

## Further Reading

- **Kief Morris, _Infrastructure as Code_** (O'Reilly; second edition 2020). The book on the practice independent of tools: stacks, environments, testing infrastructure, and how to structure it as it grows.
- **Yevgeniy Brikman, _Terraform: Up & Running_** (O'Reilly, third edition 2022). The practical guide to state, modules, environments and team workflows, most of which applies to OpenTofu too.
- **Terraform and OpenTofu documentation:** "Refactoring" (`moved` blocks), "Import," "The lifecycle meta-argument," and the S3 backend (including `use_lockfile`). **OpenTofu, "State and plan encryption."**
- **Martin Fowler, "SnowflakeServer"** and **Kief Morris, "ImmutableServer"** (martinfowler.com, 2012 and 2013). Short essays naming the problem this article opens with, and the alternative to it.
- **Open Policy Agent** and **Conftest** documentation, and **Checkov**, for writing and running policy checks against plans.
- **AWS Well-Architected Framework, Operational Excellence pillar,** "Perform operations as code." A provider's framing, useful when making the case internally.
- Within this collection: **3.4** for configuration and secrets, **20.3** for secrets management, **24** for disaster recovery (where rebuildable infrastructure pays off), **30.2a** for GitOps and environment parity, **30.3a** for OIDC and pipeline trust, **30.4a** for images as the immutable half of infrastructure, **34** for data residency.

A TypeScript sibling using Pulumi or the AWS CDK would be worth writing, because writing infrastructure in a general-purpose language changes what's easy and what's dangerous. Loops, functions, types and unit tests replace HCL's constrained expressions, so a module becomes a class with a typed interface, and "does every database have deletion protection?" can be a test rather than a policy file. The CDK also shows a different state model entirely: it synthesizes CloudFormation templates and leaves state to AWS, with no state file anywhere. The dangers change too: infrastructure defined by arbitrary code can be much harder to predict from a diff, which makes reviewing the plan even more important. Not yet written.

---

The habit worth carrying out of this article: **ask whether you could rebuild it.** For any piece of infrastructure you depend on, could you recreate it tomorrow, in another region, from something you can read? And could you say why each setting is what it is? If the honest answer is "we'd click through the console and hope," the infrastructure is only as reliable as the memory of whoever last touched it. IaC doesn't make infrastructure simpler. It makes it knowable, and every other practice in this module, from reviewable changes to parity between environments to fast recovery, depends on that.
