# Keeping the Pipeline Fast: Feedback Time as a Budget

_Module 30 · CI/CD Pipelines · 30.1b_

## The Problem

Suppose 30 engineers work on an event-ticketing platform: a TypeScript monorepo with 11 packages (a checkout API, a seating service, an admin web app, shared libraries). Eighteen months ago the pipeline took six minutes. Nobody decided it should take 45. Each addition was reasonable: a typecheck step, a Postgres-backed integration suite, Playwright tests for checkout after a bad incident. Today every pull request runs this, in one job, in order:

```
waiting for a runner          2m
checkout + npm install        6m   no cache; 1,900 packages
build all 11 packages         5m
lint                          3m
typecheck                     4m
unit tests                    6m
integration tests            10m   Postgres from scratch, 312 migrations
end-to-end (Playwright)       9m
                             ───
                             45m   every PR, including a one-line CSS change
```

What 45 minutes does to a team isn't obvious from the number.

**Changes get bigger.** Nobody wants to pay 45 minutes three times, so three small PRs become one large one. Larger PRs are reviewed less carefully and conflict more, which is exactly what CI was supposed to prevent (30.1a).

**Feedback arrives after attention has moved on.** An engineer pushes, starts something else, and finds out 45 minutes later that a lint rule failed. That failure was knowable in the first two minutes. Now it costs a context switch back, a fix, and another 45 minutes. A typo can eat an afternoon.

**The merge queue can't keep up.** The team merges about 25 PRs a day, mostly between 10:00 and 18:00, so roughly three an hour arrive at the queue. A queue that tests one merge at a time finishes 1.3 an hour:

```
arriving:   ███ 3 PRs/hour
finishing:  █▎  1.3 PRs/hour (60 ÷ 45)

queue depth over the day:
10:00  ▏
12:00  ███▍
14:00  ██████▊
16:00  ██████████▏
18:00  █████████████▌  → ~14 PRs still waiting at 18:00
```

Speculative builds (30.1a) help, but every failure throws away the builds queued behind it, and those builds took 45 minutes each. The queue gets turned off "temporarily," and main starts breaking again.

**People route around it.** `[skip ci]` appears in commit messages. Someone asks whether the Playwright suite could be made optional. The CI bill, at 30 engineers × several pushes a day × 45 minutes, has become a line item a finance person asked about.

The pipeline hasn't failed at verifying anything. It's failed at arriving in time to matter.

## What It Is

This is **pipeline feedback time**, and treating it as a budget rather than an outcome. Kent Beck's "ten-minute build" from Extreme Programming is the classic version of the budget: long enough to do real verification, short enough that people wait for it instead of starting something else.

Two numbers matter, and they're different:

- **Time to first failure.** How long before a broken change gets its first red signal. This should be minutes, because most failures are cheap ones (formatting, lint, a type error).
- **Time to verdict.** How long before a change is known to be good enough to merge. This bounds how fast the team and the merge queue can move.

The techniques that improve them fall into four families: **don't wait** (order and parallelize), **don't redo** (cache), **don't run what can't be affected** (select), and **don't block on what can wait** (move work out of the merge path). There's a fifth thing that isn't a technique: keeping the budget from quietly growing back.

Making the tests themselves faster (fewer sleeps, less I/O, better fixtures) overlaps with this and belongs to testing and performance work (Modules 21 and 22). Flaky tests, which add time through retries and re-runs, are 21.5. This article is about the pipeline around the tests.

## Recognizing the Problem

- People push and go to lunch, or push several times before looking at results.
- A lint or formatting failure is reported 20+ minutes after the push.
- A change to one package, or to a README, runs everything.
- Every job starts by downloading the same dependencies from the internet.
- The pipeline is one long job, and nobody knows which step is the slowest without reading logs.
- Merge-queue depth climbs through the day, or the queue was turned off for being slow.
- `[skip ci]`, "make it optional," or "it's just the e2e suite" come up regularly.
- Nobody knows what the pipeline took six months ago, or has a target for it.

## How It Works

### 1. Measure the critical path first

A pipeline is a graph of steps, and its duration is its longest path through that graph, not the sum of its steps. Before optimizing anything, get three measurements: duration per step (median and 90th percentile, since the slow tail is what people remember), time spent waiting for a runner, and which steps are on the critical path.

In the ticketing pipeline everything is on the critical path, because it's a single job. Once steps are parallel, speeding up anything off the critical path changes nothing. It's the most common wasted optimization.

### 2. Don't wait: order, split, parallelize

**Fail fast.** Put cheap, frequently failing checks first. Formatting, lint and typecheck together take a few minutes and catch most broken pushes, so they should report before the integration suite even starts.

**Split the single job into a graph.** Lint, typecheck and unit tests don't depend on each other; they only depend on installed dependencies. Integration and end-to-end tests depend on a build. Declare those dependencies and let independent steps run at once:

```
             ┌─ lint ─────────┐
install ──┬──┼─ typecheck ────┤
          │  └─ unit (per pkg)┤
          │                   ├──► verdict
          └─ build ──┬─ integration ×3 shards ─┤
                     └─ e2e smoke ×2 shards ───┘
```

**Shard long suites.** Split one test suite across several machines. Shard by recorded duration, not by file count: dividing 400 test files into four groups of 100 gives one shard all the slow database tests, and the suite is as slow as its slowest shard. Several test runners and CI platforms can split by historical timing data (CircleCI's `tests split --split-by=timings`, Knapsack for several frameworks); the basic runner flags (`--shard=1/4` in Vitest, Jest and Playwright) split by file, which is a fine start.

Parallelism has a ceiling. Every extra job pays its own setup (runner start, checkout, install), so a two-minute suite split eight ways is mostly setup. And **fail-fast across jobs is a choice with a cost**: cancelling sibling jobs on the first failure saves capacity but shows only one failure at a time, so a PR with a lint error and a broken test needs two round trips. For PR checks, running siblings to completion is usually the better default.

### 3. Don't redo: caching

Most of any pipeline is recomputing things that haven't changed. Caching reuses them, and the whole difficulty is knowing when a cached result is still valid. There are two kinds of cache, and they fail differently.

**Caches where the key guarantees correctness.** The classic example is the dependency download cache: key it on a hash of the lockfile (plus OS and toolchain version), and a different lockfile gets a different cache. If the key misses an input, you restore stale content. The good news for package caches specifically is that a strict install (`npm ci`) still verifies against the lockfile, so a stale download cache costs time, not correctness. Caching `node_modules` itself is faster and loses that protection.

**Content-addressed caches, where each entry guards itself.** Build tools with task caching (Turborepo, Nx, Gradle, Bazel) compute a hash of each task's inputs (source files, dependency outputs, declared environment variables, tool versions) and store the output under that hash. Before running a task, they hash its inputs and look up the result. The CI-level cache key barely matters here, because restoring an old store can only produce hits for inputs that genuinely match. It just affects hit rate.

The failure mode is the same in both, and it's the dangerous one: **an input the hash doesn't know about.** A test that reads an environment variable that isn't declared, a build that embeds a file outside the package, a script that fetches something from the network. The tool hashes everything it can see, finds a match, restores last week's green result, and the change that should have failed passes. A cache that produces false greens is worse than no cache, because it breaks the "same inputs, same verdict" rule from 30.1a in the other direction.

Three habits keep caches honest:

- **Declare inputs explicitly,** and prefer tools that exclude undeclared environment variables rather than silently ignoring them.
- **Make the cache disposable.** Deleting every cache should make the pipeline slower, never different. Occasionally run with caching off and compare.
- **Share a remote cache, but control who writes to it.** A remote cache shared between CI and developer machines is where the biggest wins are: a developer's `build` restores what CI already built. But anyone who can write to it can plant an output under a real input hash. Common practice is that CI on trusted branches writes and everyone else reads. How that trust boundary works on CI platforms is 30.3a.

### 4. Don't run what the change can't affect

A README change shouldn't run Playwright. A change to the admin app shouldn't run the seating service's tests. There's a ladder of increasingly precise, increasingly risky ways to skip work.

**Path filters** run a job only when files under certain paths change. They're simple and coarse, and they rot: someone adds a dependency between two directories and the filter doesn't know.

**Affected-graph selection** uses the monorepo's dependency graph. Find the packages containing changed files, then walk the graph backward to everything that depends on them, and run tasks only for that set. A change to a shared `pricing` library runs checkout and admin (which import it) but not seating. `nx affected` and Turborepo's `--affected` do this; Module 29.4 covers monorepo tooling generally.

**Test impact analysis** goes further, down to individual tests: record which source files each test executes, then run only the tests that touched what changed. At very large scale, companies use predictive models trained on past failures to pick which tests a change is likely to break (Google and Meta have both published this work).

All selection trades speed for the risk of a **false negative**: skipping something that would have failed. The graph only knows declared dependencies. It doesn't know that one package reads another's fixture file through a relative path, or that a root config file changes every package's behavior. The safeguards are standard:

- **Files outside any package count as "everything."** The root lockfile, shared compiler and lint config, CI definitions. Treat unknown files as affecting everything, and list specifically what can be ignored (`docs/`, `*.md`), not the reverse.
- **Keep a full run somewhere.** Run everything on main after merge, or nightly. Selection decides what blocks a PR; it shouldn't decide what's ever tested.

### 5. Faster environments

Sometimes the fastest fix is making each step start from a better place.

- **Bigger runners.** Doubling CPU often nearly halves a CPU-bound test run, and an engineer's waiting time is usually far more expensive than the difference in runner price. It's worth checking this before building anything clever.
- **Prebuilt images.** A job container image with the toolchain and system dependencies baked in removes minutes of setup from every job (30.4a covers building such images).
- **Faster test databases.** The integration suite runs 312 migrations before its first test. Instead: migrate once, then clone the result. Postgres can create a database from a template almost instantly (`CREATE DATABASE test_7 TEMPLATE app_migrated`), which gives every shard or worker its own clean database in seconds. Service containers from a prebuilt image with migrations already applied do the same at the container level.
- **Warm, self-hosted runners** keep caches and images on local disk between jobs. They're fast, and they're infrastructure you now operate and secure (30.3a).

### 6. Don't block on what can wait

Not every check needs to run before merge. The question from 30.1a applies: does this check need to block _this_ change? A useful split:

| When            | What runs                                                         | Budget          |
| --------------- | ----------------------------------------------------------------- | --------------- |
| Every PR push   | Format, lint, typecheck, affected unit tests, integration, e2e smoke | Under ~10 min   |
| Merge queue     | The same set on the merge commit                                  | Same            |
| After merge     | Full, unselected run of everything; full e2e suite                | Under ~30 min   |
| Nightly         | Mutation tests, long e2e matrix, load tests, dependency audits    | Hours are fine  |

Moving a suite to post-merge is a real trade: it can now break main, which brings back 30.1a's rules (make it loud, revert first). It works when those suites rarely fail for reasons the PR checks would miss. It fails when post-merge becomes the place for tests nobody wants to wait for and nobody watches.

### 7. Keep it from growing back

Pipelines get slow the way they got slow in the first place: one reasonable addition at a time. Give the pipeline a stated budget ("PR verdict at p90 under 10 minutes"), a chart of its trend, an alert when it crosses the line, and an owner. A new blocking suite then has to fit the budget or pay for itself by making something else faster. Without that, this article's work lasts about a year.

## When It's Appropriate

- **Verdicts over roughly 10–15 minutes** for a PR, or first failure over about 5. That's where people start switching tasks instead of waiting.
- **Merge-queue depth that grows through the day,** because arrival rate exceeds queue throughput. This is the sharpest signal, because it measures actual lost throughput.
- **Monorepos with many packages,** where most changes touch a small part of the graph: affected-only selection and task caching pay for themselves quickly.
- **Integration suites dominated by setup** (migrations, seed data, container startup), where template databases or prebuilt images cut minutes with no loss of coverage.
- **A CI bill that someone has asked about.** Caching and selection cut compute as well as time.

## When It's Unnecessary or Overkill

- **A five-minute pipeline.** A remote cache, affected-graph selection and timing-based sharding cost more to set up and understand than they save. Parallelize the obvious jobs and stop.
- **Selection in a single-package repository.** If every change affects the whole package, there's nothing to skip.
- **Micro-optimizing off the critical path.** Shaving a minute from lint when integration tests take eight changes nothing.
- **Clever engineering before a bigger runner.** Spending a week on caching to save what a larger machine would save for a small monthly cost is usually the wrong trade, at least as a first step.

## Trade-offs

- **Caches add a new way to be wrong.** A false green from an undeclared input is hard to spot, because the job looks exactly like a correct cache hit. Every cache needs someone who understands its keys.
- **Selection adds false negatives.** Skipped tests that would have failed show up later, on main or in production, far from the change that caused them. The full post-merge run catches them, which means accepting that main will occasionally break.
- **Parallelism costs money and capacity.** Eight shards pay eight setups. Speculative merge-queue builds multiply that again. It's usually worth it, and it isn't free.
- **Pipeline configuration becomes a program.** A graph of jobs, a matrix computed from a script, conditional steps and several cache layers is code that's hard to test, review and debug. The single slow job was at least understandable.
- **Post-merge suites weaken the guarantee.** Every check moved out of the merge path is one that can now break main.
- **Remote caches are a supply-chain surface.** A writable shared cache is a way to get code into builds without a commit.

## Alternatives

- **Buy hardware.** Bigger or more runners are often the cheapest first improvement, with no correctness risk. They stop helping once the pipeline is dominated by waiting (network downloads, sleeps) or by serial steps.
- **A hermetic build system.** Bazel and similar systems make caching and selection a property of the build itself: every input is declared, sandboxed and hashed, so caching is correct by construction. It's a large adoption cost, and it pays off at large, multi-language codebases.
- **Accept a slow pipeline and batch.** Some teams run a slow, thorough pipeline post-merge only, and merge with lighter checks. It's a legitimate choice (30.1a's "post-merge only" alternative) for teams that can revert fast.
- **Faster tests.** Fixing the tests themselves (shared expensive setup, real network calls, sleeps) is often more durable than orchestrating around them. See Modules 21 and 22.

## How to Achieve It

1. **Measure.** Per-step durations, runner wait, the critical path. Set a budget. _Signal to continue:_ you can say which three steps cost the most.
2. **Split and cache the basics.** Break the single job into parallel jobs, cache dependency downloads keyed on the lockfile, run cheap checks first. This is often a day's work and halves the verdict. _Signal:_ first failure arrives in a few minutes; the long pole is now one or two suites.
3. **Fix the long pole's setup.** Template databases, prebuilt images, bigger runners for the heaviest job. _Signal:_ the slowest suite spends most of its time running tests, not preparing to.
4. **Shard the long pole,** by timing if the split is uneven. _Signal:_ shards finish within a minute or so of each other.
5. **Move work out of the blocking path.** Full suites post-merge, expensive ones nightly, each with an owner. _Signal:_ post-merge failures are rare and fixed quickly. If they're frequent, the PR checks are missing something and should get it back.
6. **Add task caching and affected-only selection,** with a full run on main. This is the biggest win in a monorepo and the one with the most failure modes, so it comes after the simpler steps. _Signal:_ a typical PR runs a fraction of the graph, and full runs on main almost never find something PR checks missed.
7. **Track the budget.** Trend chart, alert, owner.

## Implementation

TypeScript on GitHub Actions, in a monorepo using npm workspaces and Turborepo. Two pieces: a script that computes the affected packages, and a workflow that turns them into parallel jobs.

### Which packages could this change affect?

```ts
// scripts/affected.ts — prints a JSON array of workspace package names
import { execSync } from "node:child_process";

type Pkg = { name: string; location: string; dependencies?: object; devDependencies?: object };
const sh = (cmd: string) => execSync(cmd, { encoding: "utf8" }).trim();

const pkgs: Pkg[] = JSON.parse(sh("npm query .workspace"));
const names = pkgs.map((p) => p.name);

const base = sh("git merge-base HEAD origin/main");
const IGNORED = [/^docs\//, /\.md$/];
const changed = sh(`git diff --name-only ${base} HEAD`)
  .split("\n")
  .filter((f) => f && !IGNORED.some((re) => re.test(f)));

const owner = (file: string) => pkgs.find((p) => file.startsWith(p.location + "/"));

// Anything outside a package (root lockfile, tsconfig.base.json, CI config) could affect everything.
if (changed.some((f) => !owner(f))) done(names);

// Reverse edges: for each package, who depends on it?
const dependents = new Map<string, string[]>();
for (const p of pkgs)
  for (const dep of Object.keys({ ...p.dependencies, ...p.devDependencies }))
    if (names.includes(dep)) dependents.set(dep, [...(dependents.get(dep) ?? []), p.name]);

const affected = new Set(changed.map((f) => owner(f)!.name));
const stack = [...affected];
while (stack.length > 0)
  for (const d of dependents.get(stack.pop()!) ?? [])
    if (!affected.has(d)) (affected.add(d), stack.push(d));

done([...affected]);

function done(list: string[]): never {
  console.log(JSON.stringify(list));
  process.exit(0);
}
```

The important line is the one that gives up. When a changed file doesn't belong to any package, the script can't reason about it, so it selects everything. The list of safely ignorable files is short and explicit; everything unknown runs.

> **What the graph can't see.** Edges come from `package.json` dependencies only. If the admin app's tests read `../seating/fixtures/venue.json` by relative path, a change to that fixture skips the admin tests. That's why the full run on main exists. `nx affected` and `turbo --affected` build a richer graph (including per-package lockfile changes), and this script shows the mechanism rather than replacing them.

### The workflow

```yaml
# .github/workflows/ci.yml (trimmed: triggers and SHA pins as in 30.1a)
jobs:
  plan:
    runs-on: ubuntu-24.04
    outputs:
      packages: ${{ steps.affected.outputs.packages }}
    steps:
      - uses: actions/checkout@<sha>
        with: { fetch-depth: 0 } # merge-base needs history
      - id: affected
        run: echo "packages=$(npx tsx scripts/affected.ts)" >> "$GITHUB_OUTPUT"

  test:
    needs: plan
    if: needs.plan.outputs.packages != '[]'
    runs-on: ubuntu-24.04
    strategy:
      fail-fast: false # show every failure, not just the first
      matrix:
        package: ${{ fromJSON(needs.plan.outputs.packages) }}
    steps:
      - uses: actions/checkout@<sha>
      - uses: actions/setup-node@<sha>
        with: { node-version-file: .nvmrc, cache: npm } # download cache, keyed on lockfile
      - uses: actions/cache@<sha>
        with:
          path: .turbo/cache
          key: turbo-${{ runner.os }}-${{ github.sha }}
          restore-keys: turbo-${{ runner.os }}- # any older store is safe to restore
      - run: npm ci
      - run: npx turbo run lint typecheck test --filter=${{ matrix.package }} --cache-dir=.turbo/cache

  verdict: # the ONE check branch protection requires
    needs: [plan, test]
    if: always()
    runs-on: ubuntu-24.04
    steps:
      - run: echo '${{ toJSON(needs) }}' | jq -e 'all(.[]; .result == "success" or .result == "skipped")'
```

The two cache steps show the two kinds of cache from mechanism 3. The npm download cache is keyed on the lockfile hash, and a strict `npm ci` still protects correctness. The Turborepo store is keyed on the commit only so a new store gets saved; `restore-keys` restores the most recent older one, which is safe because every entry inside is addressed by the hash of its own inputs. The key only decides hit rate.

> **Why the `verdict` job.** Matrix job names change with the matrix (`test (checkout-api)`, `test (seating)`), so they can't be listed as required checks. And a job skipped by its `if` counts as passing a required check. Without an aggregating job, branch protection would either require names that sometimes don't exist or miss failures entirely. `if: always()` makes `verdict` run even when something it needs has failed, so it can report that failure instead of being skipped itself. It's the same class of bug as 30.1a's missing `merge_group` trigger: a check that looks configured and doesn't enforce anything.

Integration and end-to-end jobs follow the same shape, with a `shard: [1, 2, 3]` matrix and `--shard=${{ matrix.shard }}/3`, both listed under `verdict`'s `needs`.

## Further Reading

- **Kent Beck, _Extreme Programming Explained_** (2nd ed., Addison-Wesley, 2004). The origin of the ten-minute build, and the argument for why the number is about human attention, not machines.
- **Jez Humble and David Farley, _Continuous Delivery_** (Addison-Wesley, 2010), chapter 5, "Anatomy of the Deployment Pipeline." The commit stage versus later stages, which is this article's pre-merge/post-merge split.
- **Memon et al., "Taming Google-Scale Continuous Testing"** (ICSE-SEIP 2017). Test selection when running everything is impossible, and what goes wrong.
- **Machalica et al., "Predictive Test Selection"** (ICSE-SEIP 2019). Meta's approach to choosing tests with a model trained on past failures.
- **GitHub Docs, "Caching dependencies to speed up workflows."** Key and `restore-keys` semantics, and how caches are scoped between branches.
- **Turborepo docs, "Caching" and "Using environment variables,"** and **Nx docs, "Run only tasks affected by a PR."** How task hashing decides what an input is.
- **Bazel docs, "Remote caching" and "Hermeticity."** The model that makes caching correct by construction, even if you never adopt Bazel.
- Within this collection: **30.1a** for determinism and gates, **21.5** for flaky tests and retries, **29.4** for monorepo tooling, **30.3a** for cache and runner trust, **30.4a** for prebuilt CI images.

A Java sibling built around Gradle would be worth writing, because Gradle makes task-level caching an explicit part of the build language. Tasks declare `@Input`, `@InputFiles` and `@OutputDirectory`, and the build cache and "up-to-date" checks follow from those declarations. That makes the undeclared-input failure mode concrete and inspectable: Gradle can tell you _why_ a task missed the cache, and the typical causes (absolute paths, timestamps in outputs, non-normalized classpaths) are a different and very JVM-specific set of problems from anything in npm. Not yet written.

---

The habit worth carrying out of this article: **treat feedback time as a property you design, not one you observe.** Every check added to a pipeline makes a claim on everyone's attention for as long as the pipeline exists. Ask what it costs on the critical path before asking whether it's useful. Nearly every check is useful, and that is exactly how pipelines reach 45 minutes.
