# Container Images as the Build Artifact

_Module 30 · CI/CD Pipelines · 30.4a_

## The Problem

Suppose a team runs a document-signing SaaS: a TypeScript API on Node.js, deployed as containers to Kubernetes with autoscaling. The Dockerfile was written two years ago by whoever got the first deploy working, and it hasn't changed much since:

```dockerfile
FROM node:20
WORKDIR /app
COPY . .
RUN npm install
RUN npm run build
RUN rm -f .env
CMD npm start
```

It works, in the sense that the application runs. Over a few months, five problems surface, and all of them trace back to those seven lines.

**A secret that was deleted and still shipped.** An engineer's local `.env` held a real API key for the e-signature provider. `COPY . .` copied it into the image, and `RUN rm -f .env` was added later to "remove" it. But an image is a stack of layers, and a later layer can only hide a file from an earlier one, never erase it. The key was in every image built for two years, including the ones shipped to a customer for an on-premises trial. A scanner found it by extracting the layers.

**Scaling up takes three minutes.** The image is 1.9 GB: the full `node:20` base (a complete Debian with compilers and hundreds of libraries), every development dependency, the TypeScript sources, and `.git`. At 9:00 on Monday, traffic triples and the autoscaler adds nodes. Each new node has to pull 1.9 GB before a single pod can start. For three minutes, the existing pods absorb the spike alone.

**Every build reinstalls everything.** Docker reuses a cached layer only if nothing it depends on has changed. `COPY . .` comes before `npm install`, so any change to any file, including a comment, invalidates the dependency layer, and every build runs a full `npm install`: seven minutes of a CI pipeline (30.1b) spent downloading the same packages.

**640 vulnerabilities, almost none relevant.** The image scanner reports 640 known vulnerabilities, 11 of them critical. Nearly all are in OS packages the application never uses: image-processing libraries, compilers, a version control system. Nobody can find the handful that matter in that list, so nobody looks at it.

**Every pod takes 30 seconds to stop.** `CMD npm start` is shell form, so the container's first process is a shell, which starts npm, which starts Node. When Kubernetes sends SIGTERM during a deploy, it goes to the process at the top of that chain, which doesn't pass it on. Nothing shuts down gracefully. After 30 seconds Kubernetes sends SIGKILL, dropping whatever was in flight. Every deploy is slow, and loses requests in exactly the way 30.2b describes.

The Dockerfile was treated as setup, a script to get things running. It's actually the definition of the production artifact: what 30.2a promotes by digest, what 30.3a signs, what scales up under load. Every weakness in it ships.

## What It Is

A **container image** is a build artifact that packages an application together with its runtime and the operating-system files it needs, as an immutable, content-addressed bundle. When the pipeline's artifact is an image, the question "what exactly runs in production?" has a precise answer: this digest, containing these files.

Structurally, an image is an ordered stack of **layers** (each one a set of filesystem changes, stored as a compressed archive and identified by the hash of its content), plus a configuration (entrypoint, user, environment, labels), plus a manifest listing both. The format is an open standard (the OCI Image Specification), so images built by any tool run on any compliant runtime.

A few distinctions:

- **Image vs container.** The image is the artifact; a container is a running process created from it, with the image's layers as a read-only filesystem and a thin writable layer on top.
- **Container vs virtual machine.** Containers share the host's kernel and isolate processes with kernel features. They're far lighter than VMs and have a weaker isolation boundary.
- **Dockerfile vs image.** A Dockerfile is one way to build an image, and the most common. Buildpacks, Jib, ko and Nix are others (see Alternatives).
- **This article vs Module 3.2.** Using containers to run databases and services on a developer's laptop is 3.2's subject. This article is about the image that goes to production. Orchestration (Kubernetes, ECS) is outside both.

## Recognizing the Problem

- Images are over a gigabyte for a service whose own code is a few megabytes.
- `docker history` shows `COPY . .` near the top, or files deleted in a later layer.
- `.dockerignore` doesn't exist, or doesn't mention `.git`, `.env` or `node_modules`.
- Every image build reinstalls dependencies, even when only application code changed.
- The base image is referenced by a floating tag (`node:20`, `python:3`, `latest`).
- The image contains compilers, the project's source, test files and dev dependencies.
- Containers run as root.
- `CMD` or `ENTRYPOINT` uses shell form, and pods take the full grace period to stop.
- Secrets are passed to builds as `ARG` or `ENV`.
- The vulnerability scan output is long enough that nobody reads it.
- New nodes take minutes to start serving because of image pulls.

## How It Works

### 1. Layers are additive, and that explains most of the rules

Each instruction that changes the filesystem (`COPY`, `RUN`, `ADD`) creates a new layer on top of the previous ones. Three consequences follow, and most Dockerfile advice is one of them.

**Nothing is ever deleted.** A file added in one layer and removed in the next is hidden from the running container, and still present in the image, downloadable by anyone who can pull it. The deleted `.env` is the textbook case. The same goes for build tools removed after use, and for credentials fetched and then deleted. The only safe approach is to never put such files in a layer that ships.

**Layers are cached by what produced them.** When building, the builder reuses a cached layer if the instruction and all of its inputs are unchanged, and the layer before it was reused too. The first changed layer invalidates everything after it. So order instructions from least to most frequently changing: base image, system packages, dependency manifests, dependency install, then application source. Copy only `package.json` and the lockfile before installing, and a source change leaves the dependency layer cached.

**Layers are shared.** Images on the same base share its layers, on disk and in pulls. A node that already has the base layers only downloads what differs, which is one reason a stable base and a thin application layer on top make scale-up fast.

### 2. Multi-stage builds: build with everything, ship almost nothing

Building needs a lot: compilers, the TypeScript toolchain, dev dependencies, headers for native modules. Running needs very little: the runtime, production dependencies, compiled output. A **multi-stage build** uses separate stages for each within one Dockerfile. The final image starts from a fresh base and copies in only the build stage's output, so nothing from the build stage's layers ships unless it's copied explicitly.

```
stage "build"  (node, full toolchain, dev deps, src/)     ~1.2 GB, discarded
      │  COPY --from=build  dist/  node_modules/ (prod only)
      ▼
stage "runtime" (minimal base + node runtime)             ~180 MB, shipped
```

This is the single biggest improvement for most images: smaller, fewer vulnerabilities, no source, no build tools, and no build secrets in the shipped layers.

### 3. Choosing a base image

The base image is most of what ships. It decides the image's size, its vulnerability count, and what's available when you need to debug. Roughly from largest to smallest:

- **Full distribution images** (`node:22`, `python:3.13`). Convenient for building, with compilers and common libraries included. Rarely the right runtime base.
- **Slim variants** (`node:22-bookworm-slim`). The same distribution with most packages removed. A reasonable default runtime base that still has a shell and package manager.
- **Alpine-based images.** Very small, built on musl libc instead of glibc. Native modules compiled for glibc won't load, some prebuilt binaries don't exist for musl, and DNS resolution and memory allocation behave differently in ways that occasionally surface as production bugs. It's often fine, and a source of surprises when it isn't.
- **Distroless images** (Google's `gcr.io/distroless/*`). Just the runtime and its essential libraries: no shell, no package manager. Very small attack surface, and nothing for an attacker who gets code execution to use.
- **`scratch`.** Empty. Suitable for fully static binaries (typical for Go), which then need only CA certificates and time-zone data copied in.

The cost of smaller is debuggability. With no shell in the image, you can't `exec` into a container and poke around. Kubernetes ephemeral debug containers (`kubectl debug`) attach a separate image with tools to a running pod, which covers most of what a shell was for.

Whatever the base, **pin it by digest**, not tag. `node:22-bookworm-slim` is rebuilt regularly with security patches, so the same Dockerfile produces different images on different days, which is 30.1a's determinism problem. Pinning means those patches arrive as bot PRs you merge, rather than never arriving (a forgotten pin) or arriving unannounced (a floating tag).

### 4. What goes into the build context

Everything in the directory sent to the builder, the **build context**, can end up in the image through a careless `COPY`. A `.dockerignore` file excludes paths from it: at minimum `.git`, `.env*`, local `node_modules`, build output, and test artifacts. Excluding local `node_modules` matters for correctness as well as size: they were installed for the developer's OS and CPU, and may contain native modules built for macOS.

Secrets needed _during_ the build (a token for a private package registry) must not travel as `ARG` or `ENV`. Build arguments are recorded in the image's metadata and history, and environment variables persist into the running container. **Build secrets** (BuildKit's `RUN --mount=type=secret`) mount a file for the duration of one instruction, and it's never written to a layer. Runtime configuration and secrets arrive when the container starts, never at build time, as 30.2a requires: no environment names in the artifact.

### 5. Build caching beyond one machine

Layer ordering fixes caching on a machine that keeps its cache. CI runners are often ephemeral (30.3a), so the cache vanishes with them. Two BuildKit features address that:

- **Cache mounts** (`RUN --mount=type=cache,target=/root/.npm npm ci`) give a package manager a persistent download cache across builds, even when the layer itself has to be rebuilt. They're never written into the image.
- **External cache storage** (`--cache-to` / `--cache-from` with a registry or the CI platform's cache) exports layer cache from one build and imports it in the next, on a different runner.

This is 30.1b's caching, with 30.3a's rule attached: a release build that imports layer cache written by an untrusted PR build can ship that PR's content. Scope the cache so release builds import only what trusted builds exported, or have release builds skip cache import.

### 6. Running correctly inside the container

A small image can still misbehave at runtime. Four things matter.

**Signals and PID 1.** The first process in a container runs as PID 1, and Linux treats PID 1 specially: signals whose default action is "terminate" are ignored unless the process installs a handler. Shell-form `CMD npm start` makes a shell PID 1, which doesn't forward SIGTERM to the application. Exec form (`CMD ["node", "dist/server.js"]`) makes the application itself PID 1, so it receives the signal, and it must then handle SIGTERM explicitly with 30.2b's shutdown sequence. If the application spawns child processes, a tiny init process (tini, or `docker run --init`) forwards signals and reaps exited children.

**A non-root user.** By default a container's process runs as root, which becomes much more dangerous if it escapes the container or mounts something sensitive. Set `USER` to an unprivileged account; Kubernetes can enforce it (`runAsNonRoot`).

**An immutable filesystem.** The application shouldn't write to its own image. Running with a read-only root filesystem, with explicit writable mounts for temp files, turns "the app writes somewhere unexpected" from a hidden behavior into an immediate error.

**One concern per container.** A container is one process with one lifecycle. Running a web server and a background worker in the same container means neither can be scaled, restarted or health-checked independently.

### 7. How the runtime shapes the image

Each runtime has its own natural image shape. In brief:

- **Go** compiles to a static binary with `CGO_ENABLED=0`. The final image can be `scratch` or distroless static, often under 20 MB. It needs only CA certificates for TLS and time-zone data if the code loads locations.
- **JVM languages** need a JVM in the image. The main levers are a trimmed runtime (`jlink`), layered JARs so dependency layers stay cached while application classes change, and memory settings that respect the container's limit rather than the host's.
- **Node.js and Python** ship an interpreter plus a dependency tree that's often larger than the application. The levers are installing production dependencies only, and making sure native modules are compiled against the same libc and CPU architecture the runtime image uses.

### 8. Size, scanning and what the numbers mean

Size matters mainly for **pull time**, which is on the critical path whenever a node is added or a pod lands somewhere its image isn't cached: autoscaling, recovery, cold starts in serverless container platforms. Registry storage and CI time are secondary.

Vulnerability scanners (Trivy, Grype, and those built into registries) match every package in the image against known vulnerabilities. The count is a poor measure of risk: a critical flaw in a library the application never loads matters much less than a moderate one in the HTTP parser it uses on every request. Smaller images make the report short enough to reason about, which is the real benefit. Use 30.1a's gate rules: block on _new, fixable, high-severity_ findings; track the rest. Generate an **SBOM** (software bill of materials, a machine-readable list of everything in the image) at build time, so "are we affected by this new vulnerability?" becomes a query rather than an investigation.

### 9. Images for more than one CPU architecture

ARM servers (AWS Graviton, Ampere) are often cheaper for the same performance, and Apple Silicon laptops are ARM too. A **multi-architecture image** is a list of per-architecture images under one tag or digest; the runtime pulls the one matching its CPU. BuildKit builds these with `--platform linux/amd64,linux/arm64`, either by emulation (slow for heavy builds) or on native runners for each architecture. Native modules and prebuilt binaries in the dependency tree have to exist for every target.

### 10. Compose: several containers, one definition

**Docker Compose** describes a set of containers (application, database, cache, test runner), with networking between them and startup ordering, in one file. It's the standard way to run integration tests against real dependencies in CI, and to give developers the same environment (Module 3.2). It isn't a production orchestrator: it runs on one host, with no scheduling across machines, no rolling deploys, and no self-healing beyond restart policies.

One detail causes most Compose flakiness: `depends_on` waits for a dependency's container to _start_, not for it to be _ready_. A database container starts well before it accepts connections. `condition: service_healthy`, combined with a healthcheck on the dependency, makes Compose wait for readiness.

## When It's Appropriate

- **Deploying to a container platform** (Kubernetes, ECS, Cloud Run, Fly.io, and similar). The image is the artifact, and every improvement here reaches production directly.
- **Autoscaling services** where new capacity has to serve traffic quickly: image size is on the critical path of every scale-up.
- **Anything distributed outside your control:** on-premises editions, images published for customers. What's in the layers is effectively public.
- **Teams whose CI time is dominated by image builds,** where layer ordering, cache mounts and external cache storage recover minutes per run (30.1b).
- **Compose,** for integration tests in CI that need real databases, queues or other services, and for local development parity.

## When It's Unnecessary or Overkill

- **Chasing the last megabytes.** Going from 1.9 GB to 180 MB changes scale-up time. Going from 180 MB to 140 MB almost never matters. Stop when pulls stop being noticeable.
- **Distroless or `scratch` everywhere, by rule.** For an internal tool that someone debugs by exec-ing into it weekly, a slim base with a shell may be the better trade.
- **Multi-architecture builds without ARM targets.** They double build work and add a class of native-module problems. Add them when an ARM deployment target or a meaningful ARM cost saving is real.
- **Containers where the platform wants something else.** Function platforms that take a zip file, or a single Go binary deployed to a few VMs, may not benefit from an image at all (Module 41).
- **Hand-written, heavily tuned Dockerfiles for many similar services.** A shared base image, a template, or a builder like Buildpacks usually beats 40 bespoke Dockerfiles each tuned separately.

## Trade-offs

- **Minimal images are harder to debug.** No shell, no package manager, no `curl`. Ephemeral debug containers cover most needs, and they're one more tool people have to know about during an incident.
- **Pinned bases go stale unless updated.** A digest pin with no update process ships last year's OS vulnerabilities indefinitely. Pinning is safe only with a bot and a habit of merging its PRs.
- **Multi-stage Dockerfiles are code.** Stage names, targets, cache mounts and copy paths make a Dockerfile that needs an owner and review. The seven-line version was at least readable.
- **Small bases can change behavior.** Alpine's musl, distroless's missing utilities, and a read-only filesystem each surface bugs that didn't exist on the full image, usually at runtime.
- **Build caching carries trust.** Shared layer caches and cache mounts speed up builds and create a path for untrusted content into releases if scoped carelessly (30.3a).
- **Build time and image size can pull against each other.** A multi-stage build with more steps can be slower than a naive one when uncached. Caching usually more than makes up for it, but only if the cache survives between CI runs.
- **Scanning produces work.** Every new finding in a base image asks for triage, even when the answer is "not reachable, not relevant."

## Alternatives

- **Cloud Native Buildpacks** (buildpacks.io). Detect the language and produce a well-structured image from source, with no Dockerfile. Base-image patches can be applied by **rebasing** existing images onto a new base without rebuilding. It's opinionated, and much easier to get right across many services.
- **Language-specific image builders.** Jib for Java, ko for Go. These build images directly from the language's build tool, without Docker, with sensible layering and reproducible output by default.
- **Nix or Bazel.** Build images from a fully declared dependency graph, which gives bit-for-bit reproducible images. This is powerful, and a large ecosystem to adopt.
- **No container at all.** A static binary copied to VMs, a function package for a serverless platform, or a PaaS that builds from source. Each is a legitimate artifact, and each gives up the "one image runs anywhere" property.

## How to Achieve It

1. **Audit what already shipped.** Run `docker history` and a secret scanner over current and past images. Rotate anything found, since it's been exposed for as long as the image has existed. _Signal:_ you know what's in the layers you've already distributed.
2. **Add a `.dockerignore` and reorder layers.** Dependency manifests, install, then source. _Signal:_ a code-only change rebuilds in seconds, not minutes.
3. **Go multi-stage.** Build in one stage, copy output into a slim runtime stage. _Signal:_ no source, compilers or dev dependencies in the final image; size drops by an order of magnitude.
4. **Fix runtime behavior.** Exec-form `CMD`, a SIGTERM handler, a non-root `USER`. _Signal:_ pods stop in a second or two during deploys, not after the grace period.
5. **Pin the base by digest and automate updates.** _Signal:_ base-image patches arrive as PRs and get merged within days.
6. **Move build secrets to secret mounts,** and runtime configuration out of the image. _Signal:_ no credentials in `docker history` or image metadata.
7. **Scan, generate an SBOM, and gate on new fixable high-severity findings** in CI. _Signal:_ the scan report is short enough that someone reads it.
8. **Add CI layer caching with trust scoping,** and multi-architecture builds if there's an ARM target.

## Implementation

TypeScript on Node.js, because it's the runtime where the naive image and the careful one differ most: a large dependency tree, dev dependencies needed only to build, native modules, and PID 1 behavior that catches people out.

### The Dockerfile

```dockerfile
# syntax=docker/dockerfile:1

# ---- build: full toolchain, dev dependencies, sources ----
FROM node:22-bookworm-slim@sha256:<digest> AS build
WORKDIR /app

# Dependency manifests first: this layer stays cached until the lockfile changes.
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci

# Sources after: a code change rebuilds from here down.
COPY tsconfig.json ./
COPY src ./src
RUN npm run build && npm prune --omit=dev

# ---- runtime: node runtime and production output only ----
FROM gcr.io/distroless/nodejs22-debian12@sha256:<digest> AS runtime
WORKDIR /app
COPY --from=build /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
COPY package.json ./

USER nonroot
EXPOSE 8080
CMD ["dist/server.js"]

# Last, so a new commit doesn't invalidate any layer above.
ARG GIT_SHA
LABEL org.opencontainers.image.revision=$GIT_SHA
```

The two stages differ in everything except the Debian release: `bookworm` in the build stage, `debian12` (the same release) in the runtime stage. The distroless Node image's entrypoint is the `node` binary itself, so `CMD` lists only the script, in exec form, and Node runs as PID 1.

> **Why the Debian releases must match.** `npm ci` compiles native modules (bcrypt, sharp, database drivers) against the build stage's glibc. Copy those `node_modules` onto a runtime base with an older glibc, or onto Alpine's musl, and the module fails to load at startup, or on the first request that uses it. The build succeeds, and the image fails in production. Keep both stages on the same distribution release, or build native modules in a stage that matches the runtime.

> **Node as PID 1 ignores SIGTERM unless it handles it.** Exec form fixes the signal-forwarding problem, and then Node is PID 1, where Linux ignores the default "terminate" action. The application must register `process.on("SIGTERM", …)` and run 30.2b's shutdown sequence. Without that handler, this image behaves exactly like the shell-form one: 30 seconds, then SIGKILL.

The `npmrc` secret mount exists only while `npm ci` runs, so a private-registry token never reaches a layer. The build supplies it with `docker build --secret id=npmrc,src=$HOME/.npmrc`. The commit is recorded as a standard OCI label, since `.dockerignore` keeps `.git` out of the build context. It's passed with `--build-arg GIT_SHA=$(git rev-parse HEAD)`.

The `.dockerignore` next to it is short and does a lot:

```
.git
.env*
node_modules
dist
coverage
```

### Compose for integration tests in CI

```yaml
# compose.test.yaml — real Postgres, the real image, a test runner
services:
  db:
    image: postgres:17@sha256:<digest>
    environment:
      POSTGRES_PASSWORD: test
    healthcheck:
      test: ["CMD", "pg_isready", "-U", "postgres"]
      interval: 2s
      retries: 15

  api:
    build: . # the same image that ships
    environment:
      DATABASE_URL: postgres://postgres:test@db:5432/postgres
    depends_on:
      db: { condition: service_healthy } # accepting connections, not just started
    healthcheck: # no curl in distroless, but node is there
      test:
        - CMD
        - /nodejs/bin/node
        - -e
        - "fetch('http://localhost:8080/readyz').then(r => process.exit(r.ok ? 0 : 1), () => process.exit(1))"
      interval: 2s
      retries: 15

  tests:
    build: { context: ., target: build } # the build stage has the test tooling
    command: ["npm", "run", "test:integration"]
    environment:
      API_URL: http://api:8080
    depends_on:
      api: { condition: service_healthy }
```

CI runs `docker compose -f compose.test.yaml up --build --exit-code-from tests`, which exits with the test runner's status. The `api` service builds the runtime stage, which is the image that ships, so the integration tests exercise the production artifact rather than a development variant. The tests run from the `build` stage, which still has dev dependencies and sources.

> **The healthcheck is a small program because the image has no tools.** A typical `curl -f http://localhost:8080/readyz` would fail in distroless, since `curl` doesn't exist. The Node one-liner uses the runtime that's already in the image. Kubernetes doesn't use Dockerfile or Compose healthchecks at all: it probes over HTTP from outside the container (30.2b), so this matters only for Compose and plain Docker.

## Further Reading

- **Docker documentation: "Multi-stage builds," "Docker build cache," "Build secrets," and "Building best practices."** The authoritative source for layer caching rules, cache mounts and secret mounts.
- **OCI Image Format Specification** (github.com/opencontainers/image-spec). What an image actually is: layers, config, manifests, and the standard label names.
- **GoogleContainerTools/distroless** on GitHub. What's in each distroless image, including the `nonroot` user and the per-runtime variants.
- **Node.js Docker best practices** (the `docs/BestPractices.md` file in the `nodejs/docker-node` repository). Node-specific guidance on signals, users and image variants.
- **Liz Rice, _Container Security_** (O'Reilly, 2020). How containers are isolated, what running as root actually risks, and image security in depth.
- **Kubernetes documentation, "Debug Running Pods" (ephemeral containers).** How to debug an image with no shell.
- **Trivy, Grype and Syft** documentation, for scanning and SBOM generation.
- **Cloud Native Buildpacks** (buildpacks.io), **ko** (ko.build) and **Jib** documentation, for building images without writing Dockerfiles.
- Within this collection: **3.2** for Docker in local development, **30.1a** for pinning and gate rules, **30.1b** for build caching, **30.2a** for promoting images by digest, **30.2b** for graceful shutdown and probes, **30.3a** for cache trust, provenance and runner isolation, **41** for serverless packaging.

A Java sibling would be worth writing, because the JVM makes the image a different problem. Spring Boot's layered JARs split dependencies from application classes so the large, stable layer stays cached across builds. `jlink` builds a trimmed Java runtime containing only the modules the application uses. JVM memory ergonomics have to be told about the container's limit (`-XX:MaxRAMPercentage`), or heap sizing and garbage collection misbehave under Kubernetes memory limits. And class-data sharing and similar features trade image size for startup time, which matters for exactly the scale-up problem above. Jib builds all of this without a Dockerfile. Not yet written.

---

The habit worth carrying out of this article: **read an image as what it is, not what its Dockerfile says.** Run `docker history`, list what's in the final layer, check which user it runs as and what PID 1 is. The Dockerfile describes intentions, and layers record everything that ever happened during the build, including the file you deleted. Whatever is in the layers is what production runs, what customers download, and what an attacker gets.
