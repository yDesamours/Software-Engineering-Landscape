# Progressive Deployment: Controlling Who Gets the New Version

_Module 30 · CI/CD Pipelines · 30.2b_

## The Problem

Suppose 40 engineers build an online-ordering platform used by 3,000 restaurants. They've done the work in 30.2a: one artifact per commit, promoted by digest, about 15 production deploys a day to Kubernetes. Deploys are small and routine. Traffic peaks sharply at lunch and dinner, around 2,000 requests a second. Four things still go wrong.

**Every deploy drops some requests.** Each rollout replaces pods a few at a time, and during each one about 0.3% of requests fail with a 502. No single deploy looks like an incident on a dashboard. But 15 deploys a day, some at peak, means customers regularly hit "something went wrong" at checkout, and support tickets cluster around deploy times without anyone connecting them.

**A bad change reaches everyone before anyone notices.** A change to tax calculation has a bug that only triggers for restaurants with a particular combination of delivery zones and tax rules. It passes CI and staging, because no staging restaurant has that configuration. The rollout reaches 100% in four minutes. Health checks stay green: the service is up and answering quickly, with the wrong numbers. For 25 minutes, affected orders show wrong totals, until a restaurant owner phones support.

**Undoing a deploy takes as long as doing it.** The rollback is another rollout: new pods of the old version, replacing the new ones a few at a time. At peak, with pods that take time to warm up, that's 12 minutes of continued wrong totals after someone decides to roll back.

**Two versions disagree mid-rollout.** A deploy adds a field to the menu API and, in the same release, a new web bundle that reads it. For the six minutes the rollout takes, some API requests reach new pods and some reach old ones. A customer's browser loads the new bundle from one request and gets an old API response on the next. The menu page shows an error for anyone unlucky.

Deploys are small and frequent, which fixed the problems in 30.2a. But each deploy still exposes everyone to the new version almost at once, is judged mainly by customers, and is undone at the same speed it was done. What's missing is control over **exposure**: how much traffic the new version gets, how fast that grows, and what evidence decides whether it grows at all.

## What It Is

These are **deployment strategies**: ways of moving production traffic from one version of a service to another. The ones worth knowing are recreate, rolling update, blue-green, canary (with or without automated analysis), shadow traffic, and wave or cell-based rollouts. Together they're often called **progressive delivery**, a term James Governor of RedMonk popularized in 2018 for rollouts that increase exposure step by step, based on evidence.

Two neighbors need separating once, here.

- **A canary is not an A/B test.** A canary asks "is the new version _broken_?" It runs for minutes to hours, compares health and correctness, and should find no difference. An A/B test asks "is variant B _better_ for the business?" It runs for days or weeks, compares user behavior, and hopes to find a difference. They use different statistics, different durations and different decision-makers, and running one as the other gives unreliable answers to both.
- **Deployment strategies control exposure to a binary; feature flags control exposure to behavior.** A deployment canary protects every change, including the ones nobody would think to flag: dependency upgrades, a new Go version, a refactor, a config library change. A flag rollout protects a specific feature, for chosen users, independently of deploys (Module 3.4, and 26.2b for staged rollouts to customers). The tax change could have been protected by either. Most teams need both.

## Recognizing the Problem

- Error-rate spikes line up with deploy markers on dashboards (or would, if deploys were marked).
- Bad deploys are discovered by customers, support or restaurant owners, not by the system.
- Health checks were green during an incident where the service was returning wrong answers.
- Rolling back takes as long as deploying, or longer.
- There's no way to send 1% of production traffic to a new version.
- Errors appear only _during_ a rollout and disappear when it finishes.
- Deploys are watched manually by the author staring at a dashboard, or not watched at all.
- Nobody can say which version served a particular failing request.

## How It Works

### 1. Recreate: the baseline

Stop every instance of the old version, then start the new one. It's simple, uses no extra capacity, and never runs two versions at once. It also means downtime on every deploy. It's legitimate for internal tools, batch systems, and services where two versions truly must never overlap (some single-writer systems). Everything else below exists to avoid its downtime or its all-at-once exposure.

### 2. Rolling update: the default, done properly

Replace instances in batches: start some new ones, wait until they're ready, stop some old ones, repeat. Kubernetes Deployments do this by default, controlled by `maxSurge` (extra pods allowed during the rollout) and `maxUnavailable` (pods allowed to be missing).

A rolling update is only lossless if every instance **starts** and **stops** correctly, and the dropped 502s came from getting the stop wrong. The shutdown has to happen in this order:

```
SIGTERM arrives
   │
   ├─ 1. stop reporting ready        (probes now fail)
   ├─ 2. keep serving, and wait      load balancers and proxies still have this
   │                                 instance in their lists; removal propagates
   │                                 over several seconds
   ├─ 3. stop accepting, finish      in-flight requests complete
   │     in-flight work
   └─ 4. exit
```

Step 2 is the one teams leave out, because it looks like a pointless sleep. In Kubernetes, the pod receiving SIGTERM and the pod being removed from the service's endpoints happen at the same time, not in sequence, and every proxy and load balancer learns about the removal on its own schedule. An instance that exits immediately on SIGTERM drops whatever traffic arrives in those seconds. On the starting side, **readiness** has to mean "can serve real traffic now": caches warmed, connection pools open, not just "the process is running." (Readiness versus liveness probes are covered in Module 19.2.)

Rolling updates need no duplicate environment and little extra capacity. Their limits are the other three incidents:

- **Exposure isn't controlled.** The share of traffic on the new version is just the share of instances replaced so far, and it reaches 100% as fast as the rollout goes.
- **Judgment stops at health checks.** A rollout pauses when new pods fail readiness. It can't notice wrong answers.
- **Rollback is another rollout,** at the same speed.

### 3. Mixed versions: true of every strategy except recreate

For the length of any rolling, canary or wave rollout, two versions serve production at once, and a single user can hit both. The menu incident is this, and it's the same compatibility rule as 30.2a's migrations, applied to everything else in flight: each version must work with the other's API responses, messages, cache entries and client code. Specific tactics help:

- **Serve old frontend assets alongside new ones.** Content-hashed asset filenames (`app.3f9c1.js`) let both bundles exist at once, and clients keep using the one they loaded.
- **Ship readers before writers.** Deploy the API that can serve a new field, then the client that reads it, as separate deploys.
- **Pin a user to one version** for the length of a rollout (session affinity, or hashing a user ID in the router) when compatibility is expensive.

### 4. Blue-green: switch everything, switch back instantly

Run two complete production environments. "Blue" serves traffic. Deploy the new version to "green," which is idle, and test it there: it's real production infrastructure, with real configuration, taking no user traffic. Then switch the router so all traffic goes to green at once. Blue stays running, untouched, as the rollback target.

```
before switch            after switch             rollback
router ──► blue (v1)     router ──► green (v2)    router ──► blue (v1)
          green (v2) idle          blue (v1) idle            green (v2) idle
```

Its strengths are speed and cleanliness. Rollback is a router change, so seconds rather than minutes. Only one version serves traffic at any moment, apart from the switch itself. And the new version can be exercised in production before any user reaches it.

Its costs are specific. You need double capacity, at least during each deploy. And the switch exposes everyone at once: blue-green makes a bad deploy fast to undo, not small. The tax bug would still have hit every affected order until someone noticed; it would just have stopped faster. Green also starts cold (empty caches, fresh connection pools, unwarmed JIT on some runtimes), so a switch at peak can produce a latency spike on its own. Both environments share the database, so schema compatibility still applies. And long-lived connections on blue (WebSockets, streams, Module 9) don't move when the router does; they must be drained or closed deliberately.

### 5. Canary: expose a little, look, then expose more

Send a small share of traffic to the new version, compare it to the current version, and increase the share in steps only while the evidence is good:

```
weight    1% ──(10 min)──► 10% ──(10 min)──► 50% ──(10 min)──► 100%
             analysis        analysis          analysis
             │ fail?         │ fail?           │ fail?
             ▼               ▼                 ▼
           weight → 0%, rollout aborted, stable version keeps serving
```

Aborting a canary is as fast as blue-green's switch back, because the stable version never stopped serving: the router sets the canary's share to zero. And most of the time, a bad version only ever touches the first step's share of traffic.

How traffic gets split matters:

- **By instance count.** One new pod out of 20 is roughly 5%. It needs no special routing, but the share is coarse and moves in instance-sized jumps.
- **By weight at the router.** An ingress controller, load balancer or service mesh sends a precise percentage, independent of instance counts (Module 36.1 covers meshes). This is what allows starting at 1%.
- **By cohort.** Route specific users, tenants or regions to the canary: internal staff first, then a few friendly restaurants, then everyone. This gives stable, sticky assignment and a gentler first audience, at the cost of that audience not representing all traffic.

Per-request splitting means a user can hit the canary on one request and the stable version on the next. That's fine for stateless APIs and confusing for anything a user sees change between clicks, which is the mixed-version problem again. Hashing a user or session ID to decide keeps each user on one side.

### 6. Canary analysis: the part that makes canaries worth it

A canary nobody judges is a slow rollout. Watching dashboards by hand works for a while, and then people get bored, deploy at dinner, or watch the wrong graph. **Automated canary analysis** replaces that with a judge that compares metrics and decides to promote, hold or abort. Several choices decide whether it's trustworthy.

**Compare against a baseline running at the same time.** Comparing the canary to yesterday, or to the minutes before the deploy, mixes in traffic changes, time of day and whatever else is happening. The only fair comparison is the canary against the current version serving the same traffic mix in the same minutes. Netflix's practice (in Kayenta, their open-source analysis tool) goes further: deploy a fresh _baseline_ of the old version, the same size as the canary, and compare those two, because a brand-new instance differs from long-running ones (cold caches, fresh memory) in ways that have nothing to do with the code change.

**Measure the right things.** Error rate and latency percentiles catch crashes and slowness. Saturation (CPU, memory, pool usage) catches leaks early. None of them catch wrong answers. The tax bug is only visible in a **semantic** or business metric: average order total per region, the rate of orders flagged for price mismatch, checkout completion. Each service should have one or two metrics that say "it's doing the right thing," not just "it's up."

**Respect how little data a canary has.** At 1% of 2,000 requests a second, the canary sees 20 a second, or 12,000 in ten minutes. That's plenty to detect a doubled error rate. At 1% of a service taking 10 requests a minute, the canary sees one request every ten minutes, and "no errors" means nothing. A judge must be able to say **wait**, meaning not enough evidence yet, rather than only pass or fail. For small traffic, canary steps must be bigger or longer, or the service needs a different strategy.

**Beware of looking too often.** Checking every 30 seconds and aborting on the first reading that looks significant raises false alarms far above what one check's threshold suggests, because each look is another chance to see noise. Evaluate at fixed points, or use stricter thresholds when evaluating continuously.

### 7. Where traffic routing doesn't apply

Not everything receives requests through a router.

- **Queue consumers and background workers** (Module 10) have no traffic weight to set. Run a fraction of consumers on the new version, and they take roughly that fraction of messages, or route specific partitions or tenants to them. Judge on job failure rate, processing time and dead-letter volume. A bad worker can write wrong data before anyone judges it, so treat writes from canary workers as the risky part.
- **Scheduled batch jobs** run once; there's nothing to split. Run the new version in dry-run mode against real input, or compare its output to the old version's before switching.
- **Schema migrations** are global by nature. You can't migrate 1% of a table's schema. That's why 30.2a's expand/contract discipline exists: it makes the migration safe for every version any strategy might run.

### 8. Shadow traffic: exposure without users

**Shadowing** (also called traffic mirroring or a dark launch) copies real production requests to the new version, discards its responses, and compares them to the current version's. Users are never exposed. It's the strongest pre-release evidence available for a rewrite, such as a new search backend or a pricing engine rewritten in another language, because it tests against the real, messy distribution of production requests. Twitter's Diffy tool compared responses this way, filtering out fields that legitimately differ (timestamps, IDs).

It only works cleanly for requests without side effects. Mirroring a "place order" request would place two orders, so writes must be stubbed or skipped. It also doubles load on the shadowed path and on everything that path calls.

### 9. Waves, rings and cells: canaries for infrastructure

At larger scale, the same idea applies to whole slices of infrastructure. Deploy to one **cell** (an isolated copy of the stack serving a subset of customers), or one availability zone, or one region, let it **bake**, check health, then continue to the next wave, usually growing each wave. Amazon's published practice starts with a single instance ("one-box"), then one availability zone, then regions in waves, with automated rollback at every stage. The blast radius of a bad deploy is bounded by the size of the first wave, and problems that only show up at the infrastructure level (a new version that's fine per request but overloads a regional dependency) have a chance to appear.

### Choosing between them

| Strategy         | Extra capacity           | Controls exposure       | Undo speed          | Two versions live  | Complexity  |
| ---------------- | ------------------------ | ----------------------- | ------------------- | ------------------ | ----------- |
| Recreate         | None                     | No (all at once, after downtime) | A full redeploy | Never              | Lowest      |
| Rolling          | Small (`maxSurge`)       | No, only rollout speed  | Another rollout     | During rollout     | Low         |
| Blue-green       | Double, during deploys   | No (all at switch)      | Seconds             | Only at the switch | Medium      |
| Canary           | Small, plus a baseline   | Yes, by step            | Seconds             | Throughout         | Medium–high |
| Shadow           | Double on the mirrored path | No user exposure at all | Nothing to undo   | Yes, invisibly     | High        |
| Waves / cells    | Per cell                 | Yes, by cell            | Per cell            | Throughout         | High        |

## When It's Appropriate

- **Lossless rolling updates: every stateless service.** Correct readiness and shutdown have no real downside and fix the dropped-request problem outright.
- **Canaries with automated analysis** when traffic is high enough for evidence to accumulate in minutes (roughly: the first step sees thousands of requests in its bake time), and a bad deploy is expensive: payment and ordering paths, anything customers transact through.
- **Blue-green** when rollback must be near-instant but traffic is too low for canary statistics, or when mixed versions are genuinely unacceptable, and double capacity during deploys is affordable.
- **Shadow traffic** for rewrites and migrations of read-heavy paths, where the question is "does the new one give the same answers on real requests?"
- **Waves or cells** once there are multiple regions or cells to deploy across, and a bad deploy reaching all of them at once is the risk to control.

## When It's Unnecessary or Overkill

- **Canaries on low-traffic services.** At a few requests a minute, a canary step learns nothing in any reasonable bake time. Use rolling or blue-green with good alerting, and put risky behavior behind flags.
- **Automated analysis before you have trustworthy metrics.** A judge fed noisy, inconsistently labeled metrics blocks good deploys and passes bad ones. Get metrics and deploy markers right first (Module 19).
- **Blue-green for a stateless service that rolls cleanly,** where rolling back in a couple of minutes is acceptable. It doubles capacity to save a couple of minutes.
- **A service mesh adopted just to get canaries.** Many ingress controllers and load balancers do weighted routing on their own; a mesh brings much more than that, at a matching cost (Module 36.1).
- **Long bake times on every change.** A five-step canary with 20-minute bakes makes every deploy take well over an hour. Tune bake time to how long a typical failure takes to show up, not to caution.

## Trade-offs

- **Deploys get slower.** Every bake step adds wall-clock time. That pulls against 30.2a's small, frequent deploys: slow deploys queue up, the concurrency group skips versions, and batches grow again. Bake times are a real cost, paid on every deploy.
- **Capacity costs money.** Blue-green doubles capacity during deploys; canaries with a fresh baseline add two groups of instances; shadowing doubles load on a whole path.
- **Mixed versions are permanent.** Every strategy except recreate and a clean blue-green switch means compatibility discipline for APIs, messages, caches and clients, forever.
- **The judge can be wrong both ways.** False aborts from noisy metrics stall deploys and teach people to override. False passes from too little traffic or the wrong metrics give confidence the evidence doesn't support.
- **1% is still real people.** For some failures, like wrong prices charged, data corrupted or duplicate emails sent, a 1% canary is still an incident. A canary limits damage; it doesn't prevent it.
- **Debugging needs the version everywhere.** When two versions serve at once, every log line, trace span and metric must carry the version, or incidents become arguments about which one served the failing request (Module 19).
- **More moving parts.** Weighted routing, rollout controllers, analysis templates, and per-service metric definitions are configuration that must be written, reviewed and kept correct for every service.

## Alternatives

- **Feature flags alone.** Deploy everything with a plain rolling update, and roll out risky behavior through flags. This works well for flagged changes and misses the rest: dependency upgrades, runtime updates, refactors and config changes can all break production without touching a flag.
- **Fast rollback plus good alerting.** Lossless rolling updates, clear deploy markers, alerts on error rates and one or two business metrics, and a practiced rollback. Many teams never need more, especially at moderate traffic.
- **More pre-production verification.** Load tests, production-like data in staging, contract tests. This complements progressive delivery and can't replace it, because staging will never contain the one restaurant whose configuration triggers the bug.

## How to Achieve It

1. **Make rolling updates lossless.** Readiness that means ready, the shutdown sequence above, a grace period long enough for it. _Signal:_ no error-rate bump at deploy markers, even at peak.
2. **Make deploys visible.** Deploy markers on dashboards, and a version label on every metric, log line and trace. _Signal:_ "which version served this?" has an immediate answer.
3. **Run a manual canary.** Deploy one instance of the new version, compare its metrics to the rest by version label, then continue the rollout. _Signal:_ the team has caught at least one bad deploy this way, and knows which graphs actually matter.
4. **Automate it.** Weighted routing and a rollout controller (Argo Rollouts, Flagger, or a cloud provider's equivalent), with analysis on error rate and latency, and automatic abort. _Signal:_ deploys proceed without anyone watching, and aborts are rare and real.
5. **Add semantic metrics** to the analysis for services where wrong answers are the dangerous failure. _Signal:_ a correctness bug like the tax change aborts at the first step.
6. **Add waves or cells** once there are regions or cells to spread across. Use blue-green and shadowing where their specific strengths are needed, rather than as defaults.

## Implementation

Go, for the service side and the canary judge, with a short Argo Rollouts definition connecting them. The rollout controllers in the Kubernetes ecosystem are themselves written in Go, and an analysis step written as a small Go program fits that ecosystem naturally.

### Shutting down without dropping requests

```go
func main() {
	var ready atomic.Bool
	mux := http.NewServeMux()
	mux.HandleFunc("/readyz", func(w http.ResponseWriter, _ *http.Request) {
		if !ready.Load() {
			http.Error(w, "not ready", http.StatusServiceUnavailable)
			return
		}
		w.WriteHeader(http.StatusOK)
	})
	mux.Handle("/", ordersHandler())

	srv := &http.Server{Addr: ":8080", Handler: mux}
	go func() {
		if err := srv.ListenAndServe(); !errors.Is(err, http.ErrServerClosed) {
			log.Fatal(err)
		}
	}()

	warmUp() // open DB pools, prime caches: ready means able to serve, not just running
	ready.Store(true)

	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, os.Interrupt)
	defer stop()
	<-ctx.Done()

	ready.Store(false)           // 1. stop advertising readiness
	time.Sleep(10 * time.Second) // 2. keep serving while routers notice we're leaving

	shutdownCtx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
	defer cancel()
	if err := srv.Shutdown(shutdownCtx); err != nil { // 3. finish in-flight requests
		log.Printf("forced shutdown: %v", err)
	}
}
```

The sleep covers propagation: in Kubernetes the pod is removed from the service's endpoints concurrently with SIGTERM, and every proxy catches up on its own schedule. (Kubernetes also supports a `preStop` hook that sleeps before SIGTERM is sent, which achieves the same thing outside the process.) Flipping readiness matters for anything that health-checks the instance directly, such as some external load balancers.

> **Two ways this still drops traffic.** First, Kubernetes sends SIGKILL when `terminationGracePeriodSeconds` expires, 30 seconds by default. The sleep plus the shutdown timeout here are exactly 30, so any slow request gets killed. Set the grace period comfortably above the sum, such as 45. Second, `Shutdown` doesn't close or wait for hijacked connections, which includes WebSockets. Long-lived connections need `srv.RegisterOnShutdown` to tell them to finish, and clients that reconnect well (Module 9).

### A canary judge that can say "wait"

```go
type Counts struct{ Requests, Errors float64 }

type Verdict int

const (
	Wait Verdict = iota // not enough evidence yet
	Pass
	Fail
)

// judgeErrors compares the canary's error rate to a baseline serving
// the same traffic in the same window.
func judgeErrors(canary, baseline Counts, minRequests float64) Verdict {
	if canary.Requests < minRequests || baseline.Requests < minRequests {
		return Wait
	}
	pc := canary.Errors / canary.Requests
	pb := baseline.Errors / baseline.Requests
	pooled := (canary.Errors + baseline.Errors) / (canary.Requests + baseline.Requests)
	if pooled == 0 {
		return Pass // no errors anywhere
	}
	se := math.Sqrt(pooled * (1 - pooled) * (1/canary.Requests + 1/baseline.Requests))
	z := (pc - pb) / se

	// Fail only if the canary is worse by a margin that matters
	// AND the difference is unlikely to be noise (about 99%, one-sided).
	if pc-pb > 0.001 && z > 2.33 {
		return Fail
	}
	return Pass
}
```

This is a two-proportion test, and each line maps to one of mechanism 6's choices. The minimum sample produces `Wait` instead of a false pass at low traffic. The comparison is against a concurrent baseline, not a historical number. The practical margin (0.1 percentage points) stops a statistically significant but trivial difference from blocking deploys at high traffic. The same shape works for a semantic metric: count orders flagged for price mismatch as "errors," and the tax bug fails the first step. Latency needs a test that compares distributions rather than proportions; Kayenta uses the Mann-Whitney U test for that.

> **Pass means "no evidence of harm."** It doesn't mean "proven safe." A 1% step that passes after ten minutes has shown the canary isn't dramatically worse on the metrics it checked, for the traffic it saw. That's why weights increase in steps, with analysis at each one, rather than jumping from 1% to 100%.

### Wiring it into a rollout

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: orders-api
spec:
  strategy:
    canary:
      stableService: orders-api-stable
      canaryService: orders-api-canary
      trafficRouting:
        nginx:
          stableIngress: orders-api # weighted routing at the ingress
      analysis:
        templates:
          - templateName: canary-judge # runs the Go judge; a Fail aborts
        startingStep: 1
      steps:
        - setWeight: 1
        - pause: { duration: 10m }
        - setWeight: 10
        - pause: { duration: 10m }
        - setWeight: 50
        - pause: { duration: 10m }
```

The rollout controller sets ingress weights, and runs the analysis template in the background from the first step. The template can run the judge as a Kubernetes Job; if it reports a failure, the controller sets the canary's weight to zero and marks the rollout aborted. A `Wait` result maps to the judge being inconclusive, and the rollout holds instead of advancing. Flagger offers the same model with different configuration.

A TypeScript/Node sibling would be worth writing, because graceful shutdown is where Node differs most from this article's Go example. `server.close()` stops accepting new connections, but historically waited indefinitely for idle keep-alive connections to close. Recent Node versions close idle connections on `close()` and add `closeAllConnections()`, and which behavior you get depends on version. Containers started with `npm start` add another trap: the process receiving SIGTERM as PID 1 may be npm rather than Node, and whether the signal reaches your code depends on how the container starts. Those are real, Node-specific reasons for dropped requests during rolling updates. Not yet written.

---

The habit worth carrying out of this article: **for every deploy, know how many people it can hurt before you'll find out.** With a plain rolling update the answer is everyone, and "finding out" means a customer. With a lossless rolling update it's still everyone, just without the dropped requests. With a judged canary it's 1% of traffic for ten minutes, if the metrics can see the failure. Progressive delivery is mostly about making that number small and that detection automatic, and being honest about which failures your metrics can't see.
