# Continuous Integration: What "Green" Has to Mean

_Module 30 · CI/CD Pipelines · 30.1a_

## The Problem

Suppose a team of 14 engineers builds scheduling software for veterinary clinics. One TypeScript repository, about 25 pull requests merged a day. They "have CI": every pull request runs typecheck, lint and tests, and a green check is required before merging. Over one month, four things happen.

**Two green PRs, one red main.** On Tuesday morning, PR A renames `getSlots(clinicId)` to `getAvailableSlots(clinicId, range)` and updates every caller. PR B, opened the same morning, adds a new caller of `getSlots` in the reminders module. B's checks run and pass at 10:40. A's checks pass at 11:15, and A merges. B is approved at 11:30 and merges too, because its check is still green. Main no longer compiles. Neither PR was wrong. B's check had tested B against a version of main that stopped existing 15 minutes before B merged.

**Red without a change.** The next Monday, a PR that edits only a README fails typecheck, in a date-handling file nobody has touched in months. The lockfile had been in `.gitignore` since an argument about merge conflicts two years earlier, so every CI run resolved `^3.8.0` fresh. Over the weekend the date library published 3.9.0 with stricter types. The engineer re-runs the job, it fails again, and a Slack thread works out the cause an hour later. The lesson the team actually learns is broader and worse: _red doesn't necessarily mean it's you._ The re-run button gets pressed a lot after that.

**Red hides red.** Back to Tuesday: B's author leaves at noon for a vet appointment of her own. Every PR now fails on the same compile error. By mid-afternoon people are merging with an admin override, "known failure, not mine." One of those merges breaks the reminder job's tests, but main is already red, so nobody sees a new failure. Main is fixed Wednesday evening. Thursday morning it's red again for a reason nobody recognizes, and attributing it across two days of overridden merges takes most of the day.

**The gate everyone routes around.** A required check enforces 80% line coverage for the whole codebase. A one-line fix for a double-booking bug is blocked at 79.6%, because a PR the day before deleted a well-tested module and dragged the average down. The engineer fixing the bug adds a test that calls three functions and asserts nothing, and the check goes green. Meanwhile the lint job reports 1,140 warnings, doesn't block anything, and has never been read.

The team believed a green check meant _main, with this change, works._ What it actually meant was:

```
"green" = this branch
          + some earlier version of main
          + whatever dependency versions resolved that day
          passed whichever checks happened to be required
```

Every incident above lives in the gap between those two sentences.

## What It Is

This is the territory of **continuous integration (CI)**: the practice of merging everyone's work into a shared mainline frequently, at least daily, with each merge verified by an automated build and tests, and a team commitment that mainline stays working.

Three parts of that definition carry weight, and the tooling only provides one of them.

- **Frequently.** Integration cost grows faster than branch age. Two branches that each lived a day conflict in a handful of lines. Two that each lived three weeks conflict in their assumptions. A team with long-lived branches and a CI server running tests on them has automated testing, not integration; the integration still happens all at once, at merge time, unverified.
- **Verified.** The automation's job is to answer one question about each merge: does mainline still work? Not "does this branch work."
- **Committed.** A broken mainline is the team's first priority. This is a working agreement, and no CI product ships with it.

Two neighbors get confused with CI. A **CI server** (GitHub Actions, GitLab CI, Jenkins; see 30.3a) is the machine that runs the checks, and having one says nothing about whether you practice CI. **Continuous delivery** (30.2a) starts where this article stops: taking the verified mainline and making it deployable at any moment. The branching side of the same practice, trunk-based development and short-lived branches, is Module 29's subject. This article is about what the verification has to guarantee to be worth trusting.

## Recognizing the Problem

- PRs that were green get merged, and main goes red.
- "Just re-run it" is something people say, and the re-run button is part of the normal workflow.
- A PR that changes only documentation can fail.
- Nobody can tell you which Node, JDK or Go version CI uses without opening the logs.
- Main has been red for over an hour and nobody is visibly working on it, or people merge anyway.
- The same commit, run twice, has produced different results.
- A required check is regularly bypassed with an admin override, or gamed with tests that assert nothing.
- The pipeline has a warnings section nobody reads.
- Branches live for weeks, and there's a named event where they all get merged ("merge week," "integration sprint").

## How It Works

Four mechanisms close the gap between what green claims and what it proves. The first two are technical, the third is about which checks you trust, and the fourth is the team agreement.

### 1. Test the merge result, not the branch

What will exist after merging is `main + this change`, so that's what needs testing. There's a ladder of increasingly correct ways to do it.

**Test the branch head.** Wrong from the start: it tests code that will never exist on its own.

**Test the merge at the time the check runs.** GitHub's `pull_request` event does this by default, building a temporary merge of the branch into the current base. It's correct when the check runs and goes stale the moment anything else merges. That's the Tuesday incident.

**Require the branch to be up to date before merging.** Branch protection refuses to merge unless the PR's check ran against the current main. This is fully correct, and it serializes merges: every merge invalidates every other open PR's check, so they all rebase and re-run. At a few merges a day that's fine. At 25 a day with a 12-minute pipeline, engineers spend their afternoons in a rebase-and-wait loop, and whoever's pipeline finishes first wins.

**Use a merge queue.** Approved PRs join a queue instead of merging directly. The queue builds speculative merge commits in order: main plus the first PR, main plus the first two, and so on, in parallel. Each PR merges only when the commit containing it and everything ahead of it is green.

```
main ──●
       │   queue: speculative builds, running in parallel
       ├── [main + A]            ✓ ──► merge A
       ├── [main + A + B]        ✗ ──► eject B, notify its author
       └── [main + A + B + C]    ✗     (B's failure, not C's)
              rebuilt as [main + A + C]   ✓ ──► merge C
```

Nothing reaches main without having been tested as exactly the commit main will become. Graydon Hoare named this the "not rocket science rule" when he built it for the Rust project: _automatically maintain a repository of code that always passes all the tests._ GitHub's merge queue, GitLab's merge trains, and tools like Mergify and Bors implement it.

Queues add two refinements at scale. **Batching** tests several PRs as one commit to save CI capacity, then bisects the batch if it fails. **Keeping a post-merge build on main anyway** catches what a queue can't: a PR merged by an admin override, or a check that isn't deterministic (below), which passed in the queue and fails on main.

### 2. Same inputs, same result

A check is only informative if its result depends on the change. That requires every input of the build to be either in the repository or pinned from it.

| Input                     | How it changes without a commit                                  | Pin it with                                                                                       |
| ------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Dependency versions       | New releases inside `^` / `~` ranges                             | A committed lockfile, installed strictly (`npm ci`, `pnpm install --frozen-lockfile`, `go.sum`)   |
| Language toolchain        | The runner's default moves; `node:lts` points at a new major     | A version file in the repo (`.nvmrc`, `.tool-versions`, `toolchain` in `go.mod`)                  |
| Runner OS and tools       | `ubuntu-latest` moves to a new release; images update weekly     | A named image version, or run the job in a container image pinned by digest                       |
| CI plugins and actions    | Version tags like `@v4` can be moved to different code           | Pin by commit SHA (and why that matters for security is in 30.3a)                                 |
| External services         | Network calls, third-party APIs, the clock, random seeds         | Fakes, service containers pinned by digest, injected clocks and fixed seeds                       |
| Test order, shared state  | Parallelism, leftover data, timing                               | Isolation per test; flaky-test handling is covered in 21.5                                        |

The objection is that pinning freezes you on old versions. It doesn't stop change; it **gives each change its own PR.** A dependency bot (Renovate, Dependabot) opens "bump date-lib to 3.9.0," the stricter types fail _that_ PR, and the person looking at the failure knows exactly what caused it. Nobody's README edit is involved. The same goes for toolchain and image upgrades: they become ordinary, reviewable, revertible changes instead of weather.

Full bit-for-bit reproducibility, where two builds of the same commit produce identical artifacts, is a stricter goal worth knowing about (it's what supply-chain verification builds on; see Further Reading). For CI's purpose the bar is lower and non-negotiable: **the same commit gets the same verdict.**

### 3. Decide what blocks

A required check is a promise to every author: _if this fails, it's about your change, and you can fix it._ A check earns a place on the blocking list only if it's all three of these.

- **Deterministic.** Same commit, same verdict (mechanism 2).
- **Attributable.** It fails because of something in this change, not the state of the whole codebase.
- **Actionable.** The author can fix the failure within their change.

Compile, typecheck, and unit and integration tests pass easily. The trouble is almost always elsewhere:

- **Formatting shouldn't be a debate or a gate.** Run the formatter automatically (pre-commit hook or editor, Module 3.2) and have CI only check that the output is already formatted. Nobody argues with a machine that fixes it for them.
- **Lint rules are errors or they don't exist.** A warnings tier is where rules go to die: nothing forces anyone to read it, the count only grows, and a real problem in warning 1,141 is invisible. Promote a rule to an error, or delete it.
- **Codebase-wide metrics fail attribution.** "Coverage ≥ 80%" is a property of the whole repository, so it can fail a PR that didn't lower it (the double-booking fix). Gate on the change instead: coverage of the lines this PR touched, or a **ratchet**, which records the current value as a baseline and fails only if the change makes it worse. Improvements lower the baseline and stay locked in.
- **Existing findings are a backlog, not a gate.** Turning on a security scanner or a strict type rule on a large codebase reveals hundreds of findings nobody in the current PR created. Baseline them, block only new ones, and burn down the rest separately (Module 31 on static analysis, Module 20 on security scanning).
- **Slow or noisy checks run elsewhere.** Mutation testing, full end-to-end suites and load tests are valuable and usually too slow or too variable to block every PR. Run them nightly or post-merge, with an owner who looks at the results.

Two configuration details bite teams that get all of this right. First, the blocking list lives in branch-protection settings, separately from the pipeline. Rename a job and GitHub will wait forever for the old required name to report; remove it from the list and it silently becomes optional. Second, an emergency needs a **break-glass path**: a way to merge past a failing gate that's logged, names who used it, and triggers a follow-up. If break-glass is used weekly, the gates are wrong, not the engineers.

### 4. Keep mainline green

Everything so far reduces how often main breaks. This mechanism is about what happens when it does anyway, and it's the part the tooling can't provide.

**Red main is the first priority.** Not "high priority." Every minute it's red, every other PR is either blocked or tested against a broken base, and new failures hide behind the existing one (Wednesday's reminder job).

**Revert first, investigate second.** The fastest way to green is usually undoing the change that broke it. The author can re-land it with a fix. A common agreement: the author has ten minutes to fix forward; after that, anyone may revert without asking, and nobody takes it personally.

**Make red loud.** A post-merge failure on main posts to the team channel and names the commits involved. A red build that notifies nobody is just a color.

**Don't pile on.** While main is red, merges pause (a merge queue does this automatically, because nothing can pass on a broken base). If a failure truly can't be fixed quickly, quarantine that one test on purpose, with an owner and a ticket, rather than letting everyone learn to ignore red.

And back to "frequently": merging daily means merging work that isn't finished. That's what feature flags (Module 3.4) and branch by abstraction (Module 29) are for. Incomplete code can live on main, dark, without waiting on a branch for three weeks.

## When It's Appropriate

- **More than two or three people committing to one codebase.** The semantic-conflict problem starts when the second person merges, and grows with merge rate.
- **Anything deployed from main.** If main feeds deployment (30.2a), a broken main is a broken release pipeline, not just a nuisance.
- **Dependency-heavy ecosystems.** A Node project with 900 transitive packages gets a new version of something almost every day. Strict lockfile installs and a dependency bot aren't optional there.
- **A merge queue, specifically, when "require up to date" starts hurting.** Roughly: more than 10–15 merges a day into one branch, or a pipeline long enough that people routinely lose the race to merge. The symptom to watch for is engineers rebasing the same approved PR three times in an afternoon.
- **Ratchets, when adopting a rule on an existing codebase.** Enabling strict null checks on 400 files, or a new lint rule with 2,000 existing violations, is exactly where "block only what's new" works.

## When It's Unnecessary or Overkill

- **A merge queue for a two-person team,** or any team where semantic conflicts happen once a quarter. "Require up to date" costs nothing at five merges a week.
- **Every tool as a blocking check.** Each blocking check is a tax on every change. A pipeline with 14 required checks, three of which fail for reasons nobody can explain, trains people to override, which is worse than having fewer checks.
- **Coverage targets as a goal.** A number like 80% is a reasonable alarm and a poor objective. Past a point, the tests written to reach it test nothing (Tuesday's assertion-free test).
- **Heavy process on a throwaway spike or prototype.** A lockfile and a test run are still cheap. A queue, ratchets and a formal revert policy aren't needed for code that will be deleted in two weeks.

What doesn't become overkill at any size: pinned inputs. Even a solo developer is helped by "the same commit gets the same verdict."

## Trade-offs

- **A merge queue adds latency and becomes critical path.** An approved PR now waits for its queue build, typically one pipeline length or more. When CI is down or slow, nobody can merge at all. And a failing PR ahead of yours delays yours while the queue rebuilds.
- **Speculative builds cost capacity.** Building main+A, main+A+B and main+A+B+C in parallel runs the pipeline several times per merge. Batching reduces that and adds bisecting when a batch fails.
- **Pinning moves the cost to update PRs.** Someone has to keep merging the dependency bot's PRs. If they pile up, you drift into a big-bang upgrade six months later, and security patches wait behind the queue of routine bumps. Pinning is only safe with a habit of updating.
- **Strict gates slow emergencies.** The break-glass path has to exist, and every use of it is a small hole in the guarantee.
- **"Stop the line" interrupts people.** Reverting someone's change costs them rework and can feel personal until the norm is established. Teams that don't agree on it explicitly tend to drift back to "someone will fix it."
- **Daily integration means incomplete work on main.** That relies on feature flags, which bring their own debt: dead flags, combinations nobody tested (Module 3.4).
- **Every check you add is paid on every change, forever.** The pipeline's length and the list of required checks both tend to grow, and each addition looks cheap on its own. How to keep it fast is 30.1b.

## Alternatives

- **Nightly builds.** The predecessor to CI: build and test main once a day. Breakage is found up to a day late, spread across dozens of commits, which makes attribution slow. Still reasonable for checks too expensive to run per change.
- **Post-merge only.** Commit to main and let CI check afterward, fixing or reverting fast. This works for small, high-trust teams with fast builds, and it's how many large organizations split things: a fast pre-merge suite, plus expensive suites after merge with automatic culprit-finding (Google's pre-submit/post-submit split). It trades a brief red main for merge speed.
- **A human integrator.** One person or a release team merges everyone's branches on a schedule. It concentrates integration knowledge and becomes a bottleneck; a merge queue is essentially this role automated.
- **Local verification only.** Pre-push hooks running the test suite. Useful for fast feedback (Module 3.2) and not a substitute: local machines differ, and nothing enforces it.

## How to Achieve It

Most teams already have "tests run on PRs." The path from there:

1. **Make it deterministic.** Commit and enforce the lockfile, pin the toolchain in a file, name the runner image, add a dependency bot. _Signal it worked:_ failures unrelated to the change disappear, and re-runs stop fixing things. If main still goes red after green PRs, what remains is mostly semantic conflicts.
2. **Make the blocking list honest.** One list, in branch protection, matching the pipeline. Promote or delete every warning. Replace codebase-wide thresholds with diff-based checks or ratchets. Agree on revert-first, and wire post-merge failures on main to the team channel. _Signal:_ overrides become rare, and when main breaks, it's green again within the hour.
3. **Require branches to be up to date.** This removes semantic conflicts entirely at low merge rates. _Signal to move on:_ people complain about re-testing approved PRs, or merges queue up informally in chat ("I'm merging next, don't touch main").
4. **Adopt a merge queue.** Keep the post-merge build on main as a backstop. _Signal:_ nobody rebases approved PRs by hand anymore, and red-after-green on main is close to zero.
5. **Measure integration frequency.** Track how long branches live before merging. If the median is over a day or two, the bottleneck is how work is sliced, not CI: smaller PRs, flags, branch by abstraction (Module 29).

Step 1 is often a day's work and fixes the largest share of lost trust. Steps 3 and 4 are one settings change each, once 1 and 2 have made the verdict reliable. A queue built on non-deterministic checks just ejects random PRs.

## Implementation

TypeScript on GitHub Actions. The pipeline itself is YAML, so the TypeScript here is the ratchet; the workflow shows where the pinning and the merge-result testing live.

### The workflow

```yaml
# .github/workflows/ci.yml
name: ci
on:
  pull_request: # early feedback on the PR
  merge_group: # the queue's speculative merge commit
  push:
    branches: [main] # post-merge backstop

jobs:
  verify: # this name is what branch protection requires
    runs-on: ubuntu-24.04 # named release, not ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@<commit-sha> # pinned by SHA, see 30.3a
      - uses: actions/setup-node@<commit-sha>
        with:
          node-version-file: .nvmrc # toolchain version lives in the repo
          cache: npm
      - run: npm ci # fails if package-lock.json and package.json disagree
      - run: npm run format:check
      - run: npm run typecheck
      - run: npx eslint . --format json --output-file lint.json || true
      - run: npx tsx scripts/ratchet.ts lint.json
      - run: npm test
```

Two things in this file fail quietly if they're missing.

> **The `merge_group` trigger.** Without it, the workflow never runs on the queue's commit, the required `verify` check never reports, and every PR in the queue waits until it times out. It looks like a stuck queue, not a missing line.

> **`ubuntu-24.04` pins the OS release, not the image.** GitHub still updates that image's installed tools weekly. For most jobs that's acceptable, because the tools that matter (Node, the package manager) are pinned separately. If you need the whole environment fixed, run the job in a `container:` image referenced by digest.

### The ratchet

```ts
// scripts/ratchet.ts — fail only if this change makes things worse
import { readFileSync } from "node:fs";

type Counts = Record<string, number>; // file path -> error count

const report: { filePath: string; errorCount: number }[] = JSON.parse(
  readFileSync(process.argv[2], "utf8"),
);
const current: Counts = Object.fromEntries(
  report.filter((r) => r.errorCount > 0).map((r) => [relative(r.filePath), r.errorCount]),
);
const baseline: Counts = JSON.parse(readFileSync("ratchet-baseline.json", "utf8"));

const worse = Object.entries(current).filter(([f, n]) => n > (baseline[f] ?? 0));
const better = Object.entries(baseline).filter(([f, n]) => (current[f] ?? 0) < n);

for (const [f, n] of worse) console.error(`✗ ${f}: ${baseline[f] ?? 0} → ${n}`);
for (const [f] of better) console.error(`↓ ${f} improved: run "npm run ratchet:update" and commit`);

process.exit(worse.length > 0 || better.length > 0 ? 1 : 0);

function relative(p: string) {
  return p.replace(process.cwd() + "/", "");
}
```

The design choices are all about attribution:

- **Per file, not a global total.** A global count lets someone fix three errors in one file and add three in another, and the total can't say whose file got worse.
- **Improvements also fail until the baseline is updated.** That's what makes it a ratchet rather than a threshold: if a fix isn't written into the committed baseline, a later PR can quietly undo it. The failure message tells the author exactly what to run.

> **A failure mode worth knowing:** renaming or moving a file with existing errors makes it look like a brand-new file with new errors. A real implementation either matches by content or lets a rename update the baseline in the same PR. ESLint's built-in bulk suppressions and tools like Betterer handle these cases; the script shows the mechanism, not a replacement for them.

## Further Reading

- **Martin Fowler, "Continuous Integration"** (martinfowler.com, substantially revised in 2024). The canonical description of the practice, including why a CI server on long-lived branches isn't CI.
- **Graydon Hoare, "The Not Rocket Science Rule Of Software Engineering"** (2014, graydon2.dreamwidth.org). Short history of testing the merge result before it lands, and the origin of Bors.
- **Sundaresan et al., "Keeping Master Green at Scale"** (EuroSys 2019). Uber's SubmitQueue: how a merge queue works when thousands of changes a day compete, with speculation and conflict prediction.
- **Jez Humble and David Farley, _Continuous Delivery_** (Addison-Wesley, 2010), chapter 3. The practices behind CI, including "don't check in on a broken build" and the revert-first norm, from the book that leads into 30.2.
- **Forsgren, Humble and Kim, _Accelerate_** (IT Revolution, 2018). The research linking trunk-based development and CI to delivery performance, useful when you need to justify the discipline to someone else.
- **GitHub Docs, "Managing a merge queue,"** and **GitLab Docs, "Merge trains."** The concrete configuration, including the `merge_group` trigger.
- **reproducible-builds.org.** The stricter, bit-for-bit goal, and why it matters for supply-chain verification.
- Within this collection: **21.5** for flaky tests and test reporting, **29** for trunk-based development and code review, **3.4** for feature flags, **31** for static analysis and technical-debt tracking, and **30.1b** for keeping the pipeline fast.

A Go sibling would be worth writing, because Go's toolchain takes over much of what this article builds by hand. `go.sum` verifies every dependency against a checksum database, the `toolchain` line in `go.mod` pins and even downloads the compiler version, and `go test` caches results keyed by a hash of the test's inputs, so an unchanged package's tests don't rerun. That shifts the CI question from "how do I make the build deterministic" to "which inputs does the Go cache not see" (environment variables, files read at runtime, network), which is a different and more interesting set of failures. Not yet written.

---

The habit worth carrying out of this article: **when a check goes red, ask what it was actually testing.** Which commit, which dependency versions, which toolchain, against which version of main. If you can't answer from the repository alone, the check isn't telling you about your change, and the team will eventually stop listening to it. A pipeline is only as useful as people's trust in its verdict, and that trust is lost much faster than it's rebuilt.
