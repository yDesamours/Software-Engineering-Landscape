# Continuous Delivery: Making Deployment Boring

_Module 30 · CI/CD Pipelines · 30.2a_

## The Problem

Suppose eight engineers build a B2B expense-reporting product in Go. CI works well: main is green, the pipeline is fast (30.1). Getting main into production is another story. Every second Thursday is release day, run by Priya, the one engineer who has done it enough times to trust herself. She follows a 23-step wiki page. Over one quarter, four releases go wrong in four different ways.

**The build that was never tested.** Configuration was baked into the Docker image at build time: the Dockerfile copies `config/$ENV.yaml` into the image, so there's a staging image and a separately built production image from the same commit. Staging passed QA on Tuesday. On Thursday the production build copied a `prod.yaml` whose indentation error made the payment-provider webhook secret an empty string. Nothing had ever loaded that file before. Card payments stopped confirming for 40 minutes. Staging and production shared a commit. They didn't share a binary.

**Sixty changes, one symptom.** A release carries two weeks of work: 60 merged PRs. After one deploy, report exports are slow for large customers. Which of the 60? Rolling back means rolling back all of them, including a fix promised to a customer that morning. It takes a day and a half of bisecting in staging to find a missing index.

**The rollback that couldn't.** A release includes a migration renaming `expenses.amount` to `amount_cents`. A bug surfaces an hour later, and Priya redeploys the previous version. It crashes on startup: the old code queries `amount`, which no longer exists. The migration made the deploy one-way, and nobody knew until they needed the other direction.

**The release branch.** A half-finished approval-workflow feature was merged to main three weeks ago, visible to any user who clicks the right menu. So release day starts by cutting a release branch from an older commit and cherry-picking the 50 changes that _should_ ship. The result is a combination of commits that never existed on main, which CI therefore never tested.

These have a common shape. The team deploys rarely because deploys are risky, and deploys are risky because they're rare: big batches, manual steps, one person, untested paths. Every failure makes the next release more cautious and therefore bigger.

## What It Is

This is **continuous delivery (CD)**: the practice of keeping the software releasable at all times, so that deploying any version that passed the pipeline is a routine, automated, low-risk action anyone on the team can trigger.

Three distinctions matter.

- **Continuous delivery vs continuous deployment.** In continuous delivery every passing change _can_ go to production with one action, and a person decides when. In **continuous deployment** there's no decision: every change that passes the pipeline goes to production automatically. Continuous deployment requires continuous delivery, and adds trust in your automated checks and monitoring. Both abbreviate to "CD," which causes real confusion in conversations about whether a team "does CD."
- **Deployment vs release.** **Deploying** puts a version of the code into production. **Releasing** exposes behavior to users. Feature flags (Module 3.4) separate the two: code can be deployed dark and released later, to some users, and unreleased without a deploy. Most of what makes frequent deploys safe comes from this separation.
- **CD vs CI.** Continuous integration (30.1a) keeps main working. Continuous delivery keeps main _deployable_, which is a stronger claim: it covers packaging, configuration, database schema, and the deployment process itself.

How to shift traffic onto a new version gradually (rolling, blue-green, canary) is 30.2b. This article is about what has to be true before that question is even interesting.

## Recognizing the Problem

- There's a release day, a release checklist, or a release person.
- Merged changes wait days or weeks before reaching production.
- Nobody can answer "which commit is running in production?" without asking someone or reading a deploy log.
- Each environment gets its own build, or images are tagged by environment (`app:staging`, `app:prod`) and overwritten.
- Rollback has never been practiced, or nobody is sure it would work after the last migration.
- Migrations are run by hand, or run automatically by the application on startup across every replica.
- Unfinished features force release branches, cherry-picks or "code freeze."
- Hotfixes follow a different, faster, less-checked path than normal changes.
- Deploys happen outside working hours "to be safe."

## How It Works

### 1. The deployment pipeline: stages of evidence about one artifact

A deployment pipeline takes one change from commit to production through stages, each one more expensive and more realistic than the last. Each stage gathers more evidence about the same thing.

```
commit ──► build ──► [artifact: expenses@sha256:4f1c…]
                             │
             ┌───────────────┼──────────────────┬───────────────────┐
             ▼               ▼                  ▼                   ▼
        unit + integ     staging deploy      smoke tests        production deploy
        (30.1)           same artifact       against staging    same artifact
```

Two properties make this work. The artifact is built exactly once, and every stage after that operates on the same one. And there is exactly one path to production: the pipeline. If people can also deploy from their laptops, "what's running?" stops being answerable, and the pipeline's evidence stops describing production.

That includes hotfixes. An emergency path that skips stages is the path that gets used under the most pressure, with the least review. A fast pipeline (30.1b) is what makes "hotfixes go through the normal pipeline" a realistic rule instead of a wish.

### 2. Build once, promote the artifact

An artifact (a container image, a binary, a JAR) is **immutable** and identified by content, not by name. For container images that's the digest: `expenses@sha256:4f1c…` refers to exactly one image forever, while a tag like `expenses:staging` or `expenses:latest` is a movable pointer. Tags are fine as labels for humans. What gets deployed and recorded is the digest.

Anything that differs between environments stays out of the artifact and arrives at deploy or run time: configuration from the environment, secrets from a secret store (Module 3.4). The Twelve-Factor App calls this separating _build_, _release_ (artifact + config) and _run_. A useful test: the artifact should contain no environment names at all. The release-day incident was a violation of exactly this. The staging build and the production build were different programs, and only one of them had ever been tested.

The artifact should also know what it is. Embed the commit it was built from and expose it (a `/version` endpoint, a log line on startup, a metric label). Then "which commit is running in production?" is answered by production itself, and the pipeline can verify that what's running after a deploy is what it meant to deploy.

**Promotion** is the act of moving an artifact to the next environment. It can be push-based (the pipeline runs a deploy command) or pull-based: in **GitOps**, each environment's desired state lives in a Git repository, promotion is a commit that changes the digest for that environment, and an agent in the cluster (Argo CD, Flux) makes reality match. GitOps gives you an audit trail and a revert button for free, at the cost of another system to run. It's a way to do promotion, not a different practice.

### 3. What staging is for (and what it can't tell you)

A pre-production environment earns its place by exercising what tests can't: the real deployment mechanism, real infrastructure wiring, migrations against a realistic schema, configuration loading. Parity matters most for those things. Staging should use the same artifact, the same deploy process and the same migration process as production.

Other differences are unavoidable. Staging has less data, less traffic, different data shapes, and no real customers doing surprising things. The slow report exports would never have shown up there, because no staging account had 200,000 expenses. Be explicit about what staging can't tell you, because that's what production has to be watched for (Module 19, and the progressive techniques in 30.2b).

A shared staging environment can also become a queue: one team's broken deploy blocks everyone's testing. **Ephemeral preview environments**, created per PR and destroyed after, remove the queue for testing changes in isolation, and cost infrastructure and setup time. They complement a stable staging environment rather than replacing it.

### 4. Small batches

The single most effective way to make deploys safe is to make each one small. Compare:

```
Release every 2 weeks:   60 changes per deploy
  something breaks → suspects: 60   rollback undoes: 60   diff to read: ~6,000 lines

Deploy every merge:      1–3 changes per deploy
  something breaks → suspects: 1–3  rollback undoes: 1–3  diff to read: ~100 lines
```

A small deploy is easier to test, easier to attribute, and easier to undo. It also changes how people behave: the engineer who wrote the change is still thinking about it when it reaches production, and watches it land. Frequency is the goal, not a side effect. DORA's research on delivery performance consistently finds that teams deploying more often also have lower change failure rates, not higher.

Batch size is set by deploy frequency, and deploy frequency is set by how expensive a deploy is. That's why all the automation matters: a 23-step manual process can only run every two weeks.

### 5. Deploy is not release

For main to be deployable at every commit, unfinished work has to be on main without being visible. Feature flags do this (Module 3.4 for flag types and lifecycle, 26.2b for staged rollouts to customers). The approval workflow would have been merged behind a flag that was off in production, so there'd be nothing to cherry-pick around and no need for a release branch.

Separating the two also gives you a second, faster undo. A misbehaving feature behind a flag can be turned off in seconds without a deploy, which is faster and safer than any rollback.

### 6. Migrations: where code and data meet

Code deploys are atomic per process, but schema changes and code changes never happen at the same instant. During any deploy there's a window where old code runs against the new schema, or new code against the old one. With several replicas rolling out one by one (30.2b), both versions run at once. And after a rollback, old code runs against whatever schema the new version left behind.

So every schema change must be compatible with **both the currently running version and the next one**. The technique that achieves this is **expand/contract** (also called parallel change). Renaming `amount` to `amount_cents` becomes a sequence of separately deployed steps:

```
deploy 1  expand    add column amount_cents (nullable)
deploy 2            code writes both columns, reads amount_cents with fallback to amount
          backfill  copy amount → amount_cents for old rows (a background job, Module 10)
deploy 3            code reads and writes only amount_cents
deploy 4  contract  drop column amount   (days later, once no rollback target reads it)
```

Every step is safe to roll back to the one before it. The one-way door is only the final contract step, and by then nothing needs the old column. Module 6.3 covers zero-downtime migrations in depth (locks, large-table backfills, tools).

Two operational rules follow:

- **Run migrations as their own pipeline step,** before the new code deploys, not on application startup. Startup migrations race across replicas, tie a failed migration to a failed deploy halfway through a rollout, and make the migration's timing depend on when a pod happens to restart.
- **Ship migrations in the artifact.** The migration step runs the same artifact (or one built from the same commit) that's about to deploy, so staging tests exactly the migrations production will run.

### 7. Rollback and roll forward

When a deploy goes wrong there are two ways out, and it's worth deciding in advance which one you rely on.

**Rollback** redeploys the previous artifact. It's fast and needs no new code, but only works if three things hold: the previous artifact still exists (retention), the schema is still compatible with it (expand/contract), and the configuration is too. Some effects can't be rolled back at all: emails sent, payments captured, events published, data written in a new format that old code can't read.

**Roll forward** means fixing the problem and deploying the fix. It handles the cases rollback can't, and it's only fast if the pipeline is. With a 45-minute pipeline, rolling forward means 45 minutes of broken production.

Most teams want both, plus flags as the fastest option for behavior changes. The part teams skip is **practicing**: a rollback path that's never been exercised fails at the worst moment, which is what happened on the `amount` release. Some teams deploy the previous version to staging as a routine pipeline step, specifically to prove it still works.

### 8. Approvals that mean something

In continuous delivery, a person decides when to deploy to production. That approval is worth having when the approver knows something the pipeline doesn't: a customer demo in progress, a marketing launch, a traffic peak. It's pure latency when it's a rubber stamp on a change nobody reviewing it has looked at.

Compliance requirements such as separation of duties ("the author can't be the only person who put this in production") are often satisfiable without a manual gate: required code review by someone else, plus a pipeline that records which reviewed commit produced which artifact and when it was deployed. That record is better evidence than a click, and Module 34 covers the compliance side.

## When It's Appropriate

- **Any hosted product with a team larger than one or two,** where merged work waits days or more before reaching users.
- **Teams whose releases are big because they're infrequent,** with the incident pattern above: unattributable failures, painful rollbacks, a release person.
- **Anywhere hotfixes are scary.** If the emergency path is different from the normal one, both need work.
- **Continuous deployment specifically,** once the pipeline is trusted, monitoring can detect a bad deploy within minutes (Module 19), and rollback or flags can undo one within minutes. Commonly: a web product deploying 10+ times a day.

## When It's Unnecessary or Overkill

- **Continuous deployment for software you don't control the rollout of.** Mobile apps pass through store review and sit on devices for months. On-premises products are installed by customers on their schedule. Continuous delivery (to internal or beta tracks) still applies; deploying every commit to users doesn't.
- **An elaborate multi-environment promotion chain for a small internal tool.** Build once, deploy by digest, one staging environment at most. Five environments for five users is ceremony.
- **Continuous deployment without the ability to see a bad deploy.** Automatic deploys with weak monitoring aren't continuous deployment; they're automatic outages. Get observability and fast undo first.
- **Expand/contract for data you can afford to take offline.** A table used only by a nightly batch job can often be changed in one step during a quiet window.

## Trade-offs

- **The automation is real work, and it's never finished.** Deploy scripts, artifact storage and retention, environment management, and the pipeline itself are software someone maintains.
- **More deploys means the deploy mechanism must be robust.** A deploy process that fails 2% of the time is tolerable twice a month and intolerable 20 times a day.
- **Schema changes get slower per change.** A rename that was one migration becomes four deploys over several days. You trade speed on individual changes for safety on every deploy.
- **Backward compatibility becomes a permanent discipline.** Not just for schemas: API responses, event formats (Module 37), cache entries and queue messages all have old and new versions in flight at once.
- **Flags bring their own debt.** Every flag is a branch in the code, and flag combinations nobody tested are a real failure mode (Module 3.4).
- **Parity costs money.** A staging environment that exercises real infrastructure is real infrastructure, and preview environments multiply it.
- **Frequent deploys change who needs to pay attention.** The author watches their change land, which is good, and is also an expectation that has to be agreed and supported with dashboards and alerts.

## Alternatives

- **Release trains.** Deploy on a fixed schedule (weekly, or every few days) with whatever is ready. It's a legitimate middle ground when deploys have a real fixed cost (mobile store submissions, customer-scheduled maintenance windows), and still benefits from building once and decoupling release with flags.
- **Release branches for maintained versions.** Software that must support several versions at once (on-premises products, libraries) needs branches per supported version and backported fixes. That's a requirement of the product, not a lack of discipline, and continuous delivery applies to each branch's own releases.
- **Manual, infrequent releases with heavy verification.** Appropriate where each release is genuinely expensive to undo, like firmware or safety-critical systems. The cost is the big-batch problem, accepted deliberately and paid for with far more pre-release testing.

## How to Achieve It

1. **Script the deploy.** Turn the wiki page into one command anyone can run, still triggered by hand. _Signal:_ someone other than Priya has deployed, and nobody needed to ask her anything.
2. **Build once, deploy by digest.** Remove environment-specific content from the artifact, move it to runtime config, embed the commit, and verify it after each deploy. _Signal:_ staging and production run the same digest, and "what's running?" is one request away.
3. **Move migrations into the pipeline,** as their own step, and adopt the compatibility rule: every migration works with the current and next version. _Signal:_ you've practiced a rollback in staging after a migration, and it worked.
4. **Deploy every merge to staging automatically.** _Signal:_ staging is never more than a few minutes behind main.
5. **Deploy to production often, with one action.** Aim for daily, then per merge. _Signal:_ deploys have fewer than a handful of changes each, and a bad one is attributed within minutes.
6. **Put unfinished work behind flags,** and retire release branches and cherry-picks. _Signal:_ main is deployable at every commit, and "code freeze" stops being a word the team uses.
7. **Optionally, remove the manual approval.** That's continuous deployment. Do it once monitoring catches bad deploys reliably and 30.2b's progressive techniques limit how many users a bad one reaches.

To measure progress, DORA's four delivery metrics fit well: deployment frequency, lead time from commit to production, change failure rate, and time to recover from a failed deploy.

## Implementation

Go, because the Go toolchain embeds the source revision into every binary on its own. That makes "the artifact knows what it is" a property of the build rather than a convention. The pipeline around it is GitHub Actions.

### The artifact knows its commit

```go
// buildinfo.go — which commit is this binary?
package main

import (
	"encoding/json"
	"net/http"
	"runtime/debug"
)

type Build struct {
	Commit   string `json:"commit"`
	Time     string `json:"commit_time"`
	Modified bool   `json:"modified"`
	Go       string `json:"go"`
}

func readBuild() Build {
	b := Build{Commit: "unknown"}
	info, ok := debug.ReadBuildInfo()
	if !ok {
		return b
	}
	b.Go = info.GoVersion
	for _, s := range info.Settings {
		switch s.Key {
		case "vcs.revision":
			b.Commit = s.Value
		case "vcs.time":
			b.Time = s.Value
		case "vcs.modified":
			b.Modified = s.Value == "true"
		}
	}
	return b
}

func versionHandler(b Build) http.HandlerFunc {
	return func(w http.ResponseWriter, _ *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		json.NewEncoder(w).Encode(b)
	}
}
```

`go build` inside a Git checkout stamps `vcs.revision`, `vcs.time` and `vcs.modified` into the binary, and `go version -m ./expenses` prints them without running it. The binary contains no environment names; everything environment-specific is read from environment variables and the secret store at startup.

> **Where this silently breaks:** building inside Docker with `.git` listed in `.dockerignore`, which is common and sensible. The build context has no repository, so nothing gets stamped and every image reports `unknown`. Either pass the commit in explicitly (`-ldflags "-X main.commit=$SHA"`, with the `Build` type falling back to it) or have the pipeline check the stamp before pushing. The pipeline below checks, so an unidentifiable artifact never reaches a registry.

### Build once, promote by digest

```yaml
# .github/workflows/deliver.yml
on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-24.04
    outputs:
      digest: ${{ steps.push.outputs.digest }}
    steps:
      - uses: actions/checkout@<sha>
      - run: |                                   # refuse unidentifiable builds
          go build -o expenses ./cmd/expenses
          go version -m expenses | grep -q "vcs.revision=${{ github.sha }}"
          go version -m expenses | grep -q "vcs.modified=false"
      - uses: docker/build-push-action@<sha>
        id: push
        with:
          context: .                              # Dockerfile copies the built binary
          push: true
          tags: ghcr.io/acme/expenses:${{ github.sha }}   # a label for humans

  staging:
    needs: build
    runs-on: ubuntu-24.04
    environment: staging
    concurrency: deploy-staging
    env:
      IMAGE: ghcr.io/acme/expenses@${{ needs.build.outputs.digest }}
    steps:
      - uses: actions/checkout@<sha>              # for the ops/ scripts
      - run: ops/migrate --env staging --image "$IMAGE"   # expand-only, before code
      - run: ops/deploy  --env staging --image "$IMAGE"
      - run: ops/smoke   --env staging --expect-commit "${{ github.sha }}"

  production:
    needs: [build, staging]
    runs-on: ubuntu-24.04
    environment: production    # required reviewers here = continuous delivery; none = continuous deployment
    concurrency: deploy-production
    env:
      IMAGE: ghcr.io/acme/expenses@${{ needs.build.outputs.digest }}
    steps:
      - uses: actions/checkout@<sha>
      - run: ops/migrate --env production --image "$IMAGE"
      - run: ops/deploy  --env production --image "$IMAGE"
      - run: ops/smoke   --env production --expect-commit "${{ github.sha }}"
```

Every deploy step refers to the image by digest from the `build` job, never by tag, so staging and production are provably the same bytes. The smoke step calls `/version` and fails unless the running commit is the one being promoted, which catches a deploy that "succeeded" while the old version kept serving. The migration runs from the same image, as its own step, before the code that needs it.

> **Concurrency groups skip versions on purpose.** GitHub keeps at most one running and one pending run per concurrency group; a newer pending run replaces an older one. If three merges land during one production deploy, the next deploy takes the newest and the middle one is never deployed on its own. That's usually right for deploys ("get to the latest"), and it means batch size grows when deploys are slow. One more reason deploy speed matters.

## Further Reading

- **Jez Humble and David Farley, _Continuous Delivery_** (Addison-Wesley, 2010). The book that defined the practice: the deployment pipeline, build once, and managing environments and data. Chapters 5, 10 and 12 map onto this article.
- **Adam Wiggins, _The Twelve-Factor App_** (12factor.net), factors III ("Config") and V ("Build, release, run"). The shortest statement of keeping environment out of the artifact.
- **Danilo Sato, "Parallel Change"** (martinfowler.com, 2014), and **Scott Ambler and Pramod Sadalage, _Refactoring Databases_** (Addison-Wesley, 2006). The expand/contract technique, for code and for schemas.
- **Forsgren, Humble and Kim, _Accelerate_** (IT Revolution, 2018), and the annual **DORA State of DevOps reports** (dora.dev). The evidence that frequent, small deploys go with lower failure rates, and the four metrics.
- **Beyer et al., _Site Reliability Engineering_** (O'Reilly, 2016), chapter 8, "Release Engineering." Hermetic builds, artifact identity and release process at Google scale.
- **OpenGitOps principles** (opengitops.dev), with the **Argo CD** and **Flux** documentation, for pull-based promotion.
- **Go documentation, `runtime/debug.ReadBuildInfo` and `go help buildinfo`**, for what gets stamped and when.
- Within this collection: **3.4** for configuration, secrets and flags, **6.3** for zero-downtime migrations, **26.2b** for staged feature rollouts, **19** for the monitoring that makes deploys observable, **30.2b** for progressive deployment, **30.4a** for container images as artifacts, **34** for compliance.

A Java sibling with Spring Boot would be worth writing, because the framework's defaults push against this article in a specific way. Spring Boot runs Flyway or Liquibase migrations automatically on application startup when either is on the classpath, which is convenient and is precisely the startup-migration coupling warned about above: every replica attempts the migration, and a slow migration becomes a slow, possibly failing, rollout. That article would be about turning that default off, running migrations as a separate job from the same artifact, and using Spring profiles without letting them turn into per-environment builds. Not yet written.

---

The habit worth carrying out of this article: **for any deploy, ask how you'd undo it before you do it.** Previous artifact still there? Schema still compatible? Any effects that can't be taken back? If the honest answer is "we'd have to figure it out," the deploy is riskier than it looks, however small the change. Teams that deploy confidently many times a day aren't braver than teams with release day. They've made every deploy small and every deploy reversible, so there's much less to be brave about.
