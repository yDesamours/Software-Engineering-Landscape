# Rows Are Not Operations: Building the Admin Surface

_Module 26.1a — Admin Dashboard & Internal Tools_

## The Problem

Suppose you run appointment-scheduling software for small medical clinics. Two years in, there are about 900 paying clinics, a support team of six, and nine engineers. Nobody ever decided to build admin tooling. It accumulated, in three layers:

- **Engineers with production SQL access.** There's a bastion host, a shared `fixes.sql` file of snippets, and a Slack channel called `#support-eng` where support posts requests.
- **A generated admin panel.** The web framework scaffolds a screen for every table: list, filter, edit any column, delete. Support got access to it in year one "so they stop blocking on engineers."
- **An `is_superuser` flag** on user accounts in the main product. Superusers see extra buttons, and can open any clinic's workspace.

One quarter of what that produces:

- **The queue.** `#support-eng` gets about 40 requests a week: extend a trial, move a user to another clinic, resend an invite that bounced, undo an accidental cancellation. Each takes an engineer ten minutes plus a context switch. That's most of one engineer, and customers still wait a day and a half for an answer.
- **The bad `UPDATE`.** An engineer extends a trial with `UPDATE subscriptions SET trial_ends_at = '2026-07-01' WHERE clinic_id = 4417 OR status = 'trialing'`. The `OR` was meant to be `AND`. 212 trials are extended, and it takes two days to reconstruct which ones were meant to be.
- **Edits that break invariants.** A support agent upgrades a clinic by changing `plan_id` on the subscription row in the generated admin. The product now shows Pro features, but the billing provider was never told, so the clinic keeps paying for Basic. Downgrades are worse: changing the column skips the code that removes seats above the new limit, so a Basic clinic ends up with 14 active staff accounts on a 5-seat plan.
- **The phone call.** Someone rings support claiming to be a practice manager who lost access to her email. The agent helpfully changes the email address on her account in the generated admin. It wasn't her. The attacker resets the password and downloads the clinic's appointment list, which contains patient names. No notification went to the old address, because the product's "change email" flow, which sends one, was never involved.
- **The unanswerable question.** A clinic says its time zone changed by itself last Tuesday and a day of appointments shifted by an hour. Nobody can say who changed it. The generated admin keeps no history, and the SQL console keeps none either.
- **The payload.** A new signup names their clinic `<img src=x onerror=...>`. Nothing happens in the product, which escapes output. But the generated admin's list view has a "rich" column renderer that doesn't, and the first support agent to scroll past that row runs the attacker's script inside the most privileged session in the company.
- **Six tabs per ticket.** To answer "why was I charged twice?" an agent opens the generated admin, the billing provider's dashboard, the log search, the help desk, the clinic's workspace as superuser, and a Slack thread asking an engineer to check the job queue.

The thread through all of these: **the admin surface grew from the shape of the database rather than from the jobs your staff actually do.** The database knows about rows and columns. Your staff do operations, like "extend this trial" or "move this user", and every one of those operations has rules that live in application code, not in the table.

## What It Is

The thing missing here is an **admin surface**, also called a back office or internal tool: the application your own staff use to operate the product on customers' behalf.

The reframe that matters is that it's **a second product.** Its users are employees, its unit of work is an **operation** rather than a row, and it holds more power than anything customers can touch. It deserves product design, not scaffolding.

One neighbor is worth separating right away, because the word "admin" covers both. **Tenant administration** is the customer's own admin settings: the practice manager inviting staff, changing the plan, setting the clinic's time zone. That's customer-facing, scoped to one tenant, and governed by the product's normal rules and roles (4.3). **Staff administration**, the subject of this module, is your company acting across tenants, often with the power to step outside those rules. They need different identity systems, different permissions and different threat models. A lot of early bugs come from building one as a flag inside the other, like the `is_superuser` flag above.

Observability dashboards (19) and BI dashboards (16.5) are also "internal tools," but they answer questions about the system. The admin surface changes things.

## Recognizing the Problem

- Engineers get a steady stream of "can you just run a query for…" requests from support or sales.
- There's a file, a wiki page or a pinned message full of SQL snippets for common fixes.
- Support, success or sales staff have production database credentials.
- Your admin panel is a generic editor over your tables, and changing a column there skips logic that the product runs.
- Nobody can say who changed a record, or when, or why.
- Answering one support ticket takes four or more tools.
- Staff admin access is a flag on a normal customer account, on the same domain and session as the product.
- Customer-supplied text (names, notes, uploaded file names) renders inside admin screens.
- A fix only an engineer can apply is the standard answer to a common customer problem.

## How It Works

A working admin surface has five parts. The first two are the reading and writing halves; the other three make the writing half safe.

```
   customer app        admin app               DON'T:  admin app
        │                  │                              │
        │         ┌────────┴────────┐                     │ generic edit
        ▼         ▼                 ▼                     ▼
   ┌───────────────────────┐   read models /       ┌──────────────┐
   │  domain services      │   provider APIs       │   database   │
   │  (billing, seats,     │                       └──────────────┘
   │   membership, email)  │                        invariants skipped,
   └──────────┬────────────┘                        no audit, no notify
              ▼
        ┌──────────┐
        │ database │
        └──────────┘
```

**1. The read side: find anything, see everything about it.** Most admin work is looking, not changing. Two features carry it:

- **Search on every identifier people actually have.** Email, domain, clinic name, user ID, invoice number, the billing provider's customer ID, the last four digits of a card, a request ID from an error message. Support gets tickets in the customer's words, not in your primary keys.
- **One account page** that brings together identity and members, plan and billing state (fetched from the provider or a synced copy, not re-derived), usage against limits, recent errors and failed jobs for that tenant, open tickets, and recent admin actions taken on this account. The six-tab ticket becomes one tab.

Read access is still access. Personal data on these pages should be **masked by default and revealed on request with a reason**, which is both a privacy control and a way to make browsing leave a trace. Viewing a patient list is an action worth logging, even if it changes nothing.

**2. The write side: named operations, not field edits.** Each thing staff are allowed to do is a named operation, such as `ExtendTrial`, `ChangePlan`, `MoveUserToClinic`, `ResendInvite`, `IssueCredit` or `RestoreCancelledSubscription`. Each one calls **the same domain services the product uses**, so the rules run: the billing provider gets told, seats get enforced, the old email address gets notified. This is the Command pattern (2.5, Part 4) in its most practical form.

Each operation declares its own metadata:

- **Input schema**, so the form is generated and the input validated.
- **Required permission** (26.3 covers how to structure these).
- **Risk level**, which drives how much friction it gets.
- **Preconditions** ("only trialing subscriptions", "only if the user has no future appointments assigned").
- **A preview**: what will change, stated in business terms. "Trial ends 14 June instead of 31 May. No charge until then."
- **Whether it's reversible**, and if so, what the reverse operation is.

A generic field editor still has a place, but a narrow one: reference data and configuration with no invariants attached, like the list of supported countries or the text of a banner. For anything with business rules, the absence of a generic editor is the feature.

**3. Guardrails proportional to risk.** Friction is a cost (see Trade-offs), so it should scale with what can go wrong:

- **Low risk** (resend an invite): one click, logged.
- **Consequential** (change a plan, issue a credit): a **reason**, ideally a ticket link, plus a confirmation that shows the preview.
- **High risk** (change a login email, export a tenant's data, delete an account): the above, plus a customer notification where relevant, and possibly **approval by a second person** (26.3).
- **Bulk** (anything across many accounts): a **dry run** that lists the exact affected set, a cap on how many rows one run may touch, and execution as a background job (10) that can be paused and reports progress. The 212-trial `UPDATE` would have shown "212 subscriptions will change" before anything happened.

There's a subtle point about previews. The preview is computed at one moment and executed at another, and the account may change in between. The operation has to **recheck its preconditions at execution time**, and ideally refuse to run if the state it previewed no longer holds. What the agent confirmed should be what runs.

**4. Data fixes as reviewed code.** Some repairs are genuinely one-off: a bug corrupted 300 rows and they need recomputing. Building a UI for that is waste, and running it by hand in a SQL console is how the bad `UPDATE` happened. The middle path is a **data-fix runner**: the fix is a script in the repository, reviewed like any other change, run through a tool that defaults to dry-run, wraps the work in a transaction, enforces a row limit, and records who ran it, what it touched and the commit it came from. A useful rule of thumb: the third time the same fix script is run, it becomes a named operation.

**5. Separation from the customer product.** The admin surface is the most valuable thing an attacker can reach, and it should be built like it:

- **A separate deployment on a separate origin** (`admin.internal.example.com`, not `/admin` on the product domain), so no cookies, sessions or client-side state are shared, and a routing mistake in the product can't expose it.
- **Staff identity from your workforce identity provider**, with SSO and phishing-resistant MFA, not a flag on a customer account. When someone leaves the company, access ends with their workforce account.
- **Network restriction** where practical: VPN, an identity-aware proxy, or device posture checks.
- **Treat every piece of customer data as hostile when rendering it.** This is the one most teams miss. Your product escapes a clinic name when showing it to that clinic. The admin surface shows every tenant's input to your most privileged users, so an unescaped field there is **stored XSS aimed at your staff**. Attackers do this deliberately. It's called **blind XSS**: they plant payloads in signup forms, support messages and file names, and wait for them to be rendered in someone's back office. Escape everything, set a strict Content Security Policy, and be especially wary of "rich" renderers, previews of uploaded HTML or SVG, and admin tools built from third-party components.

Finally, every operation writes an **audit record in the same transaction** as the change it records, with who, what, which account, the reason, and the before-and-after values. 24.4 covers audit logs in general, and 26.3 covers auditing admins specifically.

## When It's Appropriate

- **The request stream reaches engineers.** Roughly, more than 10 to 20 support-driven data requests a week, or when the queue wait becomes something customers mention.
- **Non-engineers need to change customer state.** As soon as a support or success team exists, they need a way to act that doesn't involve database credentials.
- **The data is sensitive.** Health, financial or children's data makes "who looked at this, and why" a question you'll be asked by a customer, an auditor or a regulator.
- **You're heading into a compliance process.** SOC 2, ISO 27001 and HIPAA audits all ask how staff access customer data, how that access is reviewed, and how changes are logged. "Engineers use a shared SQL console" does not pass.
- **Support volume makes lookup time matter.** At 50 or more tickets a day, cutting a minute of tab-switching from each one is most of a person.

## When It's Unnecessary or Overkill

- **The founders are the support team.** With three people who all have production access and a handful of customers, a SQL console used with discipline (read replica for reads, explicit transactions, check the row count before commit) is fine. Building a polished admin now means guessing which operations will matter.
- **Before you know the recurring operations.** The list of named operations should come from counting real requests, not from imagining them. Building 30 operations up front mostly produces 25 that are never used.
- **For rare operations.** Something that happens twice a year belongs in the data-fix runner, not in a custom screen that has to be maintained through every schema change.
- **Heavy permission and approval machinery for a small, trusted team.** Six support agents who all need the same abilities don't need a fine-grained role matrix or two-person approval for credits under $50. Add that when the team, the contractors or the risk grows.
- **Rebuilding what vendors already give you.** Your billing provider's dashboard already does refunds, disputes and invoice history well. Link to it from the account page instead of rebuilding it.

## Trade-offs

- **It's a second product to maintain.** Every change to the domain, such as a new plan type or a new seat rule, now has an admin side too. Admin surfaces decay quietly because nobody outside the company complains about them.
- **Named operations are slower to add than SQL.** That's the point, but if adding one takes a week, pressure pushes people back to the console and to the "just this once" credentials. The cost of adding an operation has to stay low: a registry, generated forms, and a small amount of code per operation.
- **Friction gets routed around.** Too many confirmations, required fields and approvals, and people will share accounts, keep old credentials, or ask the one engineer who still has database access. Guardrails need to be calibrated by risk, and the friction itself is worth watching.
- **Concentrated power is a target.** Everything that makes staff effective makes a compromised staff account catastrophic. The 2020 Twitter incident, in which attackers phoned employees, obtained credentials, and used an internal tool to take over high-profile accounts, is the canonical example. The admin surface raises the stakes of your workforce security.
- **Calling domain services means inheriting their failure modes.** An operation that changes a plan now makes a call to the billing provider. That call can fail after your database change has been written, or succeed after your transaction rolls back. The dual-write problem from 17.1 and 10 applies here too (see the aside in the Implementation section).
- **Low-code builders move logic out of review.** Internal-tool platforms are fast, but queries and business logic written in their editors often skip code review, tests and version control. And if the tool connects straight to your database with broad credentials, you've rebuilt the generated admin with a nicer UI.

## Alternatives

**Framework-generated admins** (Django admin, Rails tools like ActiveAdmin or Avo, Laravel's Filament, AdminJS, React Admin). Very fast to start, and excellent for reference data. Django's own documentation says its admin is meant as an internal management tool, not a front end for the whole application. They become dangerous when they're used as a field editor over entities with rules. Most support **custom actions**, which is the way to use them well: turn off editing for invariant-bearing fields and expose the named operations as actions that call your services.

**Low-code internal-tool builders** (Retool, Appsmith, Budibase, ToolJet). Good when the team building admin tools is small and the operations are mostly composition of existing APIs. Point them at your **internal API**, where the operations and their rules live, not at the database.

**Reviewed scripts with no UI.** For an engineering-heavy company with little support volume, the data-fix runner alone (level L1 below) can carry a long way.

**Make it self-serve instead.** Every recurring admin operation is evidence that the product is missing something. "Change my login email" should be a verified flow the customer runs, not a support request. "Undo my cancellation" can be a button with a grace period. The best admin operation is one that's no longer needed. Tracking operation counts (L5 below) gives you this list for free.

## How to Achieve It

**L0 — engineers with SQL, plus conventions.** Reads on a replica, writes in explicit transactions with a row-count check before commit, snippets kept in the repository rather than a chat thread. This is fine for longer than people think.

**L1 — a data-fix runner.** Scripts in the repository, reviewed, dry-run by default, row-capped, logged. *Signal:* the first bad `UPDATE`, or the same snippet run a third time.

**L2 — a read-only account page with search.** No writes yet, which makes it cheap and safe. *Signal:* support asks engineers to look things up, not only to change them.

**L3 — named operations for the top recurring requests.** Count a month of `#support-eng` and the ticket history, build the ten most frequent, each with a reason, a preview and an audit record. Then **remove support's database and generic-editor write access**, which is the step that actually changes behavior. *Signal:* engineers spending more than a few hours a week on requests, or the first invariant-breaking edit.

**L4 — separate deployment, workforce SSO, per-operation permissions, approvals for the dangerous ones, and impersonation** (26.1b, 26.3). *Signal:* a compliance audit, a support team growing past about ten, or the first outsourced or contract support staff.

**L5 — close the loop.** Measure how often each operation runs and why (the reason field is data), and move the most frequent into self-serve product features. *Signal:* the same operation is in the top three month after month.

## Implementation

TypeScript, because the core idea is a type: an operation that carries its own schema, permission, risk and preview, so the runner can apply the same guardrails to all of them.

```ts
import { z } from "zod";

type Risk = "low" | "consequential" | "high";

interface AdminOperation<I, R> {
  name: string;
  input: z.ZodType<I>;
  permission: string;        // e.g. "billing.trial.extend" (26.3)
  risk: Risk;
  // Business-level description of what will change. Also returns a
  // fingerprint of the state it looked at, so execute can check it.
  preview(ctx: OpContext, input: I): Promise<{ summary: string; stateHash: string }>;
  execute(ctx: OpContext, input: I): Promise<R>;
}

export const extendTrial: AdminOperation<
  { clinicId: string; newEndDate: string }, void
> = {
  name: "ExtendTrial",
  input: z.object({ clinicId: z.string(), newEndDate: z.string().date() }),
  permission: "billing.trial.extend",
  risk: "consequential",

  async preview(ctx, { clinicId, newEndDate }) {
    const sub = await ctx.billing.getSubscription(clinicId);
    if (sub.status !== "trialing") throw new PreconditionFailed("Not in trial");
    return {
      summary: `Trial ends ${newEndDate} instead of ${sub.trialEndsAt}. No charge until then.`,
      stateHash: hash([sub.id, sub.status, sub.trialEndsAt]),
    };
  },

  // The same service the product's own trial logic uses: the billing
  // provider is updated and the clinic's reminder emails are rescheduled.
  // No UPDATE on the subscriptions table anywhere in admin code.
  async execute(ctx, { clinicId, newEndDate }) {
    await ctx.billing.extendTrial(clinicId, newEndDate);
  },
};
```

The runner is where the guardrails live, once, for every operation:

```ts
export async function runOperation<I, R>(
  op: AdminOperation<I, R>,
  staff: StaffUser,
  raw: unknown,
  confirm: { reason?: string; previewedStateHash: string },
): Promise<R> {
  if (!staff.can(op.permission)) throw new Forbidden(op.name);
  const input = op.input.parse(raw);
  if (op.risk !== "low" && !confirm.reason) throw new ReasonRequired();

  return db.transaction(async (tx) => {
    const ctx = contextFor(tx, staff);

    // Recheck at execution time. If the account changed since the agent
    // saw the preview, what they confirmed is no longer what would run.
    const now = await op.preview(ctx, input);
    if (now.stateHash !== confirm.previewedStateHash) throw new StaleConfirmation();

    const result = await op.execute(ctx, input);

    // Same transaction as the change: if the change commits, so does the record.
    await tx.insert(adminAudit).values({
      staffId: staff.id, operation: op.name, input,
      reason: confirm.reason, summary: now.summary, at: new Date(),
    });
    return result;
  });
}
```

> **Aside: the transaction doesn't cover the billing provider.** `ctx.billing.extendTrial` calls an external API, so the database transaction can't make it atomic with the audit row. If the provider call succeeds and the commit fails, the trial is extended with no record; if the order is reversed, you have a record of something that didn't happen. The usual fix is the one from 10 and 17.1: write the intent (and the audit row) in the transaction, and let an outbox worker make the provider call with an idempotency key derived from the operation's ID, so retries can't extend twice.

The data-fix runner is small by comparison: a script exports a `select` that returns the affected IDs and an `apply` that fixes one of them. The runner prints the count and a sample in dry-run mode, refuses to run if the count exceeds the script's declared `maxRows`, and records the commit hash with each run. The row cap is the line of code that would have stopped the 212-trial mistake.

## Further Reading

- **The New York State Department of Financial Services report on the 2020 Twitter incident** (October 2020). The clearest public account of how attackers reached accounts through internal admin tooling, and what the remediation looked like.
- **Django's admin documentation**, particularly the note on its intended use and the sections on `readonly_fields` and admin actions. A good model of how to constrain a generated admin.
- **OWASP's Cross-Site Scripting Prevention Cheat Sheet and Content Security Policy Cheat Sheet.** Read them from the viewpoint of an admin page that renders every tenant's input.
- **PortSwigger's Web Security Academy on stored XSS**, and write-ups on blind XSS against back-office panels. They show why the admin surface is where stored XSS pays off for attackers.
- **Martin Fowler's writing on the Command pattern and on Command Query Separation.** The conceptual basis for operations-not-rows, and for keeping the read side and the write side distinct.
- Within this map: the Command pattern in **2.5**, product roles in **4.3**, tenant isolation in **5**, background jobs for bulk operations in **10**, the dual-write problem and idempotency in **17.1**, audit logs in **24.4**, impersonation and suspension in **26.1b**, support tooling in **26.2**, and admin permissions and approvals in **26.3**.

A Python sibling using Django would add something this article can only describe: how far a generated admin can be pushed toward the model above. Read-only fields for everything with rules, custom actions that call services, per-action permissions, and the admin log. Seeing what it gives you for free, and exactly where it stops, is the most useful input to the build-versus-generate decision. Not yet written.

---

The habit worth carrying forward: **every time someone asks an engineer to run a query, count it.** Each one is either a missing operation or a missing product feature, and the count tells you which to build first. The admin surface you end up with should be shaped by what your staff actually do all day, not by the columns in your tables.
