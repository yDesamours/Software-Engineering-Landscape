# Accepting Uploads

_Module 11.1a — File Storage & Management_

## The Problem

A construction-inspection app. Field engineers walk a site, photograph defects, and attach a short drone video to the report. The endpoint is the one everybody writes first:

```
POST /inspections/8812/attachments      multipart/form-data
  → buffer the body
  → write to /var/uploads/{uuid}.mp4
  → INSERT INTO attachments (...)
  → 201
```

It works perfectly in the office.

**Then there are two pods.** The file was written to the local disk of whichever instance served the upload, and downloads hit the other one about half the time. The first instinct — a shared network volume — trades a correctness bug for a single point of failure with worse latency. The real lesson is smaller and permanent: **the local filesystem is per-instance state, and an application that writes to it is no longer horizontally scalable.**

**Then there's the site.** 4G at 1.2 Mbps, a 180MB video: about twenty minutes. For all twenty of those minutes the request is open, holding a request worker, a proxy connection, and a slot in every pool between them. The body arrives at the *client's* pace, so the server's effective concurrency is now a function of its users' network quality. Forty engineers on bad links is forty occupied workers, and nothing about your hardware changes that.

**Then the proxy limits.** A body-size cap and a read timeout, both of which somebody raises after the first incident. Raising them is how you find out they were the thing protecting you.

**Then the connection drops at 170MB.** There is no resume. The engineer starts again, on the same link, with the same probability of failure. Past a certain file size and a certain connection quality, the upload may simply never succeed — the same arithmetic that made 10.4a's four-hour job never finish, applied to bytes.

**And you pay for all of it twice.** Every byte travels client → your application → object storage. You're billed for the ingress, you burn application CPU and memory on a copy, and the application contributed nothing to the transfer.

**Then the orphan.** Once the bytes do go to object storage, there are two writes in two systems with no transaction between them:

```
PUT s3://…/8812.mp4   ✓        INSERT INTO attachments  ✗   →  180MB nobody references, billed monthly, forever
PUT s3://…/8812.mp4   ✗        INSERT INTO attachments  ✓   →  a row whose thumbnail is a broken image
```

This is 10.1a's dual write in a new costume, and it's the part that survives every other fix in this article. A file is two facts — some bytes and a record describing them — living in two systems that cannot commit together.

## What It Is

The response to the first five problems is to take the application out of the byte path entirely: the client uploads **directly to the object store**, and the application's role is reduced to granting permission and recording what happened.

Permission is granted with a **pre-signed URL** — a URL with the application's credentials baked into a signature, scoped to one operation, one object key, an expiry, and (if you construct it correctly) a set of conditions the request must satisfy. The client gets no long-lived credentials and can't do anything with the URL except the one thing it authorizes.

That turns an upload into a three-step **handshake**:

```
  client                    app                     object store
    │   POST /uploads         │                           │
    ├────────────────────────▶│  create record (pending)  │
    │◀────────────────────────┤  return signed URL + key  │
    │                                                     │
    │   PUT bytes  ────────────────────────────────────▶ │
    │                                                     │
    │   POST /uploads/:id/complete                        │
    ├────────────────────────▶│  verify object exists ───▶│
    │◀────────────────────────┤  mark ready               │
```

Worth separating from its neighbour now: this is an *upload* credential. The signed URLs that control who may **download** an object — expiry, tokenization, CDN signing — are a different mechanism solving a different problem, and they're 11.4's subject.

## Recognizing the Problem

- An `uploads/` directory on an application server, and a deployment that can't be scaled past one replica because of it.
- Request timeouts and proxy body limits that have been raised more than once.
- p99 request duration on one endpoint that correlates with nothing you control.
- Users who can't upload from anywhere except good wifi, and a support answer that says so.
- An object store whose size grows faster than your database's row count.
- Broken thumbnails for records that definitely exist.
- No way to resume, so large uploads are retried from zero.
- Memory spikes on the web tier shaped exactly like file sizes.
- A client-supplied filename appearing anywhere in a storage key.
- Nobody can say what fraction of stored objects are referenced by a live row.

## How It Works

**Create the record first.** The app inserts a row in `pending` state, generates the key itself, and returns the signed URL. Ordering matters and this is the safe one: it means every possible failure leaves a *sweepable* artifact — a pending row with no object, or (if the client uploads and vanishes) an object whose row you can still find. The unsafe ordering is uploading first and inserting afterwards, which produces objects with no record of ever having existed.

**The server names the key, always.** Never interpolate a client-supplied filename into it. A key built from user input is path traversal, object overwriting, and cross-tenant access in one line. Generate something opaque and tenant-prefixed — `t/{tenantId}/att/{uuid}` — and keep the original filename as *metadata*, to be used when serving the download.

**Constrain the signature, not just the client.** A signed URL is a capability, and it should authorize the narrowest possible thing: one method, one key, a short expiry, and conditions on content type and size. This is where the two S3-style mechanisms differ in a way that matters — a signed `PUT` cannot constrain the body size, so a URL you issued for a 5MB photo will cheerfully accept a 5GB file, whereas a signed POST policy carries a `content-length-range` the storage service enforces for you. Validating size after the fact means you've already paid to store it.

**Treat "done" as a claim.** The client saying it finished is not evidence. Verify: a `HEAD` on the object gives you size, content type, and an ETag to compare against what you authorized. The sturdier version of the same idea is to let the storage service tell you — a bucket event notification enqueuing a job (Module 10) — which also covers the client that closed the tab between the upload and the confirmation.

**Content type and extension are claims too.** Both are chosen by the client. If what happens next depends on the format — thumbnailing, text extraction, rendering inline — sniff the leading bytes server-side and trust that instead. And if a file will ever be served back to a browser, the combination of an attacker-chosen content type and an inline disposition is the oldest file-upload vulnerability there is.

**Large files: chunk them.** Multipart upload splits a file into parts uploaded independently, in parallel, each retryable on its own, with the whole thing assembled by the storage service at the end. It is 10.4a's chunking applied to bytes, and it buys exactly the same properties: resumability, bounded rework, and a per-part failure that doesn't discard the successful parts. Two practical notes — the parts of an abandoned multipart upload are invisible in the bucket listing and *billed indefinitely* unless a lifecycle rule aborts them, and progress reporting belongs to the client, which is the only participant that knows how many bytes have actually left the device.

**Scanning and validation happen after the bytes land, not during.** Upload into a quarantine bucket or a `pending` prefix, enqueue a job to scan and validate, then promote. Anything else puts an antivirus engine in the request path, and 10.1a already covered how that ends.

**Then reconcile.** Because nothing can make the two writes atomic, the durable answer is 10.3a's: a periodic sweep that converges.

```
pending rows older than the longest plausible upload, with no object   →  delete the row
objects with no row, older than a safety window                        →  delete the object
```

That safety window is not optional. An object younger than your maximum upload duration may be an upload in progress, and a garbage collector that deletes it is worse than the garbage it was collecting.

## When It's Appropriate

- **Files above a few megabytes**, where holding a request for the duration of the transfer is a real cost.
- **Users on unreliable connections** — mobile, field work, anywhere a 20-minute transfer has a meaningful chance of dying.
- **High upload volume**, where the bandwidth bill for proxying is a line item and the doubled transfer is pure waste.
- **Anything above ~100MB**, where resumable multipart stops being a nicety.
- **Untrusted content** — direct upload into quarantine keeps unscanned bytes out of your application process entirely, which is a security posture as much as a performance one.

## When It's Unnecessary or Overkill

- **Small files.** A 200KB avatar or a CSV import under a megabyte can stream through the app in well under a second. You keep validation in one place, skip CORS configuration, skip the confirm step, skip orphan collection, and the client is a single form post.
- **Server-to-server uploads.** If your own backend is the uploader, it already has credentials and there's nothing to pre-sign.
- **When the bytes must be transformed on the way in** and cannot be reprocessed later — rare, but it exists, and direct upload gives you no interception point.
- **Very small files where a second system is the bigger cost.** A signature image or a thumbnail under ~100KB in a database column removes the dual-write problem completely, backs up with everything else, and is transactional. It stops being a good idea quickly with size, but "put it in the database" is a real answer at the bottom of the range, not a joke.
- **Prototypes.** Local disk is fine until there are two of anything.

## Trade-offs

- **The client gets more complicated.** Three calls instead of one, CORS on the bucket, retry and resume logic, and an SDK on the browser or device. That complexity is real and it's the main thing you're buying with.
- **A pre-signed URL is a bearer token that looks like a link.** It ends up in analytics, in logs, in screenshots, in a chat message. Short expiries and narrow scopes are the whole defence.
- **No interception point.** Nothing of yours sees the bytes before they're stored, which is why quarantine and asynchronous validation stop being optional.
- **Two systems, permanently.** Even with reconciliation, "the file exists" is two questions, and your code has to tolerate the window where the answers differ. Every download path needs a story for a record whose object isn't ready.
- **More states in the model.** `pending`, `ready`, `failed`, `quarantined`, and a UI that can render each one honestly.
- **Local development gets heavier** — MinIO or an emulator, plus CORS config nobody remembers, and signed-URL bugs that only show up against the real service.
- **Deletion is now a distributed operation.** Deleting a row doesn't delete the bytes; deleting the bytes doesn't update the row. Both need to happen, in an order, with a sweep to catch the failures.

## Alternatives

- **Proxy through the app, but stream it.** Never buffer the whole body: read the multipart stream and write to storage as it arrives, with a hard size limit on the reader. Keeps one code path and one validation point, and costs you only the doubled transfer. For small-to-medium files this is a perfectly good permanent answer.
- **A resumable upload protocol.** tus is an open spec with mature client and server implementations, giving pause/resume across sessions and network changes without you designing the chunk protocol.
- **Provider-native direct upload.** Cloudinary, Mux, Uploadcare and similar hand you a signed upload target plus a processing pipeline. You trade portability and cost control for not building any of this.
- **Storage event notifications instead of a confirm call.** Let the bucket tell you, and the client's confirmation becomes a latency optimization rather than a correctness requirement.
- **The database, for genuinely small files.** One system, one transaction, no orphans.
- **Don't accept the file.** Link to the source, accept a URL, or integrate with where the document already lives. The cheapest upload pipeline is the one that doesn't exist.

## How to Achieve It

**Level 0 — measure the distribution.** p50 and p99 file size, upload rate, and the client bandwidth you actually see. A p99 of 400KB and a p99 of 400MB are different articles.
_Signal you're here:_ a plan to "move uploads to S3" with no number attached.

**Level 1 — get off the local filesystem.** Stream through the app to object storage, with a size cap. No client changes, and it removes the per-instance state problem immediately.
_Signal you need it:_ more than one replica, or a shared volume holding user data.

**Level 2 — pre-signed uploads with a server-generated key** and a pending record created before the URL is issued.
_Signal you need it:_ request duration tracking file size, or bandwidth costs that are visibly doubled.

**Level 3 — verify server-side.** Confirm the object exists with the size and type you authorized; enforce limits in the signature rather than after the fact.
_Signal you need it:_ you are trusting a client's word about what it uploaded.

**Level 4 — resumable multipart for large files**, plus a lifecycle rule that aborts incomplete uploads.
_Signal you need it:_ uploads that fail more often as they get bigger, or a storage bill that exceeds the size of everything you can list.

**Level 5 — quarantine, asynchronous scanning and processing, and an orphan reconciliation sweep** with its safety window.
_Signal you need it:_ untrusted content, or the inability to say how much of your bucket is referenced.

## Implementation

**TypeScript**, because the interesting part spans both ends of the handshake and it's worth seeing them in one language.

Step one — create the record, then sign:

```ts
app.post("/inspections/:id/uploads", async (req, res) => {
  const { filename, contentType, size } = req.body;

  if (size > 200 * 1024 * 1024) return res.status(400).json({ error: "too large" });

  const key = `t/${req.tenantId}/att/${randomUUID()}`;

  const { rows: [att] } = await db.query(
    `insert into attachments
       (inspection_id, tenant_id, storage_key, original_name, status)
     values ($1, $2, $3, $4, 'pending') returning id`,
    [req.params.id, req.tenantId, key, filename]
  );

  const post = await createPresignedPost(s3, {
    Bucket: QUARANTINE_BUCKET,
    Key: key,
    Expires: 900,
    Conditions: [
      ["content-length-range", 1, 200 * 1024 * 1024],
      ["eq", "$Content-Type", contentType],
    ],
  });

  res.json({ uploadId: att.id, url: post.url, fields: post.fields });
});
```

> **Aside 1.** `createPresignedPost` rather than a signed `PUT`, specifically for `content-length-range`. A signed PUT carries no size condition, so a URL issued for a 200MB video will accept a 20GB one — and you find out when the storage bill arrives, because by then you're being charged to keep it. The `size` check on the request body is a courtesy to the client; the condition in the policy is the part the storage service actually enforces.

> **Aside 2.** `randomUUID()`, not `filename`. The original name is preserved in a column, where it can be used later for a `Content-Disposition` header. The moment a client-supplied string reaches a storage key, you own path traversal, object overwriting, and — with a tenant prefix built from user input — cross-tenant writes.

Step two happens entirely in the browser, and it's the only participant that can report progress:

```ts
const form = new FormData();
Object.entries(fields).forEach(([k, v]) => form.append(k, v as string));
form.append("file", file);

const xhr = new XMLHttpRequest();
xhr.upload.onprogress = (e) => setProgress(e.loaded / e.total);
xhr.open("POST", url);
xhr.send(form);
```

Step three — the confirm, which does not believe the client:

```ts
app.post("/uploads/:id/complete", async (req, res) => {
  const att = await loadPendingAttachment(req.params.id, req.tenantId);

  let head;
  try {
    head = await s3.send(new HeadObjectCommand({
      Bucket: QUARANTINE_BUCKET, Key: att.storage_key,
    }));
  } catch {
    return res.status(409).json({ error: "no object at that key" });
  }

  await db.query(
    `update attachments
        set status = 'uploaded', byte_size = $2, content_type = $3
      where id = $1 and status = 'pending'`,
    [att.id, head.ContentLength, head.ContentType]
  );

  await enqueue(db, "attachment.scan", { attachmentId: att.id });
  res.json({ status: "uploaded" });
});
```

> **Aside 3.** The `HEAD` is the whole point of this endpoint — everything else is bookkeeping. Note also what `status = 'uploaded'` isn't: it isn't `ready`. The scan job promotes it out of quarantine, and until then nothing serves those bytes to anyone. Better still, don't depend on this endpoint at all: a bucket event notification enqueuing the same job makes the confirm a latency optimization, and covers the engineer whose phone died between the upload finishing and the app hearing about it.

And the sweep, which is the only thing that makes the two systems agree in the long run:

```sql
-- pending far longer than any upload could take, with nothing behind it
select id, storage_key from attachments
 where status = 'pending'
   and created_at < now() - interval '24 hours';
```

> **Aside 4.** Run the reverse direction too — list objects, look for keys with no row — and give it a grace window at least as long as your longest permitted upload. An object with no row might be an upload that is still in flight, and a collector that deletes those is strictly worse than the garbage it was cleaning up. This is 10.3a's convergence sweep, doing here what it was always going to have to do: fix up two systems that can never commit together.

## Further Reading

- **AWS S3 documentation, "Creating a POST policy"** and **"Sharing objects with presigned URLs"** — the conditions vocabulary, and the precise difference between the POST and PUT forms that Aside 1 depends on.
- **AWS S3 documentation, "Uploading and copying objects using multipart upload"**, plus the lifecycle rule for aborting incomplete multipart uploads — the second link is the one that saves money nobody realises they're spending.
- **Google Cloud Storage, "Resumable uploads"** — a different and arguably clearer design for the same problem, worth reading as a contrast even on AWS.
- **tus.io protocol specification** — resumable uploads as an open protocol, short enough to read in a sitting, with the offset negotiation spelled out.
- **OWASP File Upload Cheat Sheet** — extension and content-type validation, storage location, and the serving-side hazards that upload decisions create.
- **MDN, "Using XMLHttpRequest: Monitoring progress"** — why upload progress is still the one thing `fetch` doesn't give you cleanly, and what the alternatives are.
- **AWS S3 documentation, "CORS configuration"** — the step that makes direct browser uploads fail in a way that looks like an authentication bug for about an hour.

A Go sibling would earn its place, and for a reason that changes the recommendation rather than just the syntax: with `multipart.Reader`, `io.Copy` and `http.MaxBytesReader`, streaming a file through the application to object storage costs a few kilobytes of buffer and almost no CPU, which moves the size threshold at which direct-to-storage is worth its client complexity. The Level 1 answer stays viable a lot longer there. Not yet written.

---

The habit to carry out of this: a file is never one thing. It's bytes in one system and a record in another, and every question in this module — uploading, serving, deleting, migrating, backing up — is really a question about which of the two you write first, and how you find the ones that end up disagreeing.
