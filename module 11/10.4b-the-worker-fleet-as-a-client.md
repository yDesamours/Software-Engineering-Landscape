# The Worker Fleet as a Client

_Module 10.4b — Background Jobs & Task Queues_

## The Problem

A property-listings marketplace. Agents upload listings; the fleet generates image derivatives, geocodes addresses, and pushes updates to a dozen portal partners. Twenty worker processes, and on the first of the month the backlog grows faster than it drains.

The fix is obvious and takes thirty seconds: scale the worker deployment from 20 replicas to 60.

Ninety seconds later, the **website** is down.

```
FATAL: sorry, too many clients already
```

Nobody had ever added up the fleet's footprint, because there had never been a reason to:

```
web           6 pods  × pool 20  =  120
workers      60 pods  × pool 10  =  600     ← was 200 a minute ago
scheduler                        =   10
admin console                    =   10
a BI tool someone connected      =    ?
                                  ─────
                                    740+    against max_connections = 200
```

Scaling a worker deployment looks like a local change — more of the same thing, doing the same work faster. It isn't. **A worker fleet is a client of every dependency your system has, and the replica count is a multiplier applied to all of them at once.**

The follow-on symptoms arrive over the next hour.

**Shrinking the pools doesn't fix throughput.** Pools go from 10 to 3. Connections fit. Now every job waits for a permit before it can do anything, p99 job duration quadruples, and total throughput is roughly what it was at 20 replicas. The fleet was never the binding constraint; the database was, and the fleet size was only ever controlling how loudly you asked.

**The geocoding provider blocks the API key.** Sixty workers × 5 concurrent jobs is 300 in-flight requests against a contract that says 50 per second. The 429s trigger 10.2a's retries, retries add load, and by the time someone reads the provider's email, the key is suspended for an hour and listings are stale. Your queue's concurrency was a rate limit toward that provider all along; it just wasn't configured as one, or measured, or known.

**Worker pods start getting OOM-killed.** The image job loads a 40-megapixel TIFF and peaks at 1.2GB resident. Eight workers to a node with 8GB works for the average job and not for that one. Then the interesting part: the killed worker's lease expires, the job is redelivered, and it kills a different pod. And another.

```
job 88213  →  pod A  ✗ OOMKilled  →  redelivered
           →  pod B  ✗ OOMKilled  →  redelivered
           →  pod C  ✗ OOMKilled  →  …
```

At-least-once delivery plus a job that kills its host is a rolling outage that walks the fleet, and it presents as a crash loop with no obvious cause because the logs die with the process.

**And the autoscaler makes everything worse, on purpose.** It scales on queue depth. The database is saturated, so jobs take longer, so depth grows, so the autoscaler adds workers, so the database gets more saturated. The control loop is wired to respond to a symptom by increasing its cause.

```
        ┌────────────────────────────────────┐
        ▼                                    │
  DB saturated → jobs slower → depth ↑ → more workers
```

## What It Is

The discipline is **resource budgeting**: for each resource the fleet consumes — database connections, memory, file descriptors, third-party quota — knowing the maximum the fleet can demand, and enforcing it somewhere other than in a spreadsheet.

The reframing that makes it tractable: stop thinking of worker count as the control. The number you actually care about is **concurrency per resource** — how many jobs may be touching the geocoder, or the primary database, or a gigabyte of image buffer, at the same time. Replica count is a crude proxy for all of those at once, which is exactly why turning it up breaks things in unrelated places.

The named pattern for partitioning by resource is the **bulkhead**: a fixed allocation per dependency, so that exhausting one cannot sink the rest of the ship.

Two neighbours to separate. This is not 10.2b — that partitioned capacity between *workloads* so one tenant's exports couldn't starve another's emails. This partitions the fleet's demand across *dependencies*, and the two axes are independent. And this is not Module 18's rate limiting, which is about limits you impose on your callers; this is about limits you are subject to, including several that nobody told you about.

## Recognizing the Problem

- Connection exhaustion in the web tier during a batch window.
- A worker replica count nobody is willing to change.
- Provider 429s that correlate with your queue draining rather than with your traffic.
- OOMKilled pods with no correlated deploy, and the same job id shortly before each one.
- Adding workers makes job latency worse.
- Database CPU that tracks queue depth rather than user traffic.
- A `max_connections` that has been raised more than once.
- Nobody can state how many concurrent calls the system can make to any given dependency.
- Autoscaling events every few minutes in both directions.
- A capacity calculation that exists, on a wiki page, last edited two years ago.

## How It Works

**1. Do the arithmetic, per resource.** Fleet concurrency is `replicas × per-process concurrency`. Multiply that by the footprint of one job: connections held, peak memory, in-flight sockets, provider permits. Then add every *other* consumer of each resource — web tier, scheduler, admin console, migrations, the analytics tool. The binding constraint is almost never CPU; it's connections, a quota, or memory.

**2. Size pools with Little's Law, not optimism.** Concurrency = throughput × latency. If a job holds a connection for 20ms and the fleet must sustain 1,000 jobs/sec, the connections genuinely in use are `1000 × 0.02 = 20` — across the entire fleet. A pool of 50 per process does not buy fifty times the throughput; it converts a queue you can see (jobs waiting for a permit, with a metric) into a queue you can't (work queued inside the database, where it shows up as everyone's latency). Past the point where the database is saturated, a bigger pool makes things strictly worse.

The corollary: **pool size per process should be about the number of jobs that process runs concurrently.** Five concurrent jobs, a pool of five or six. Any more is pre-allocating for a concurrency you don't have.

**3. Put a permit in front of each dependency.** A fleet-wide semaphore: at most 40 concurrent geocode calls, at most 8 concurrent image renders, at most 200 jobs touching the primary. Fleet-wide is the operative word — an in-process semaphore counts one process and silently multiplies by the replica count, which is 10.2b's `Semaphore` lesson arriving from the resource side.

There's a low-tech version that's often better: **queue partitioning is dependency partitioning.** Assign job types to queues by which resource they exhaust — `images` (memory), `geocode` (provider quota), `db-heavy` (connections) — and fix the worker count per queue. The limit is then enforced by the size of a worker pool, which is a thing you already understand and monitor, and it costs no coordination round trip.

**4. Know whether the limit is rate or concurrency.** "50 requests per second" and "50 in flight" are different constraints needing different mechanisms — a token bucket for the first, a semaphore for the second. Match whichever the provider actually publishes. Worth knowing: a concurrency limit is self-correcting when a dependency slows down, because in-flight requests take longer and throughput drops automatically. A rate limit is not — it keeps firing 50/sec into a service that's dying. When you're unsure, or when the dependency is fragile, limit concurrency.

**5. Treat memory as a per-process, per-job-type property.** Sizing nodes for the average job guarantees failure on the p99 job. The options, roughly in order of preference: don't hold it all in memory (stream, tile, resize progressively); give memory-heavy jobs their own queue and their own node type; set a container limit so one job takes down one worker instead of a node; and cap attempts so a job that OOMs is dead-lettered before it can walk the fleet. That last one is worth stating explicitly — 10.2a's attempt limit protects your infrastructure, not just your data.

**6. Autoscale on the right signal, with a ceiling.** Scale on the age of the oldest ready job (10.2b, Level 0), never on depth alone. Cap `maxReplicas` at the number your arithmetic permits, because an autoscaler with a higher ceiling than your connection budget will eventually find the cliff on a night when nobody is watching. And never autoscale a consumer on a metric that adding consumers makes worse: if the bottleneck is downstream, growth is a positive feedback loop. The advanced form of the answer is **adaptive concurrency** — an AIMD controller that raises in-flight limits while latency is flat and cuts them when it isn't, discovering the dependency's real capacity instead of asking you to configure it.

## When It's Appropriate

- **Before the first time you scale a fleet to clear a backlog.** That action is the single most common trigger for the outage at the top of this article, and it is always taken under pressure.
- **Any fleet that can autoscale.** An autoscaler is a machine for spending a budget you may not have written down.
- **A database shared between web and workers**, which is nearly every system before it's large.
- **Any metered or quota'd third party** — geocoding, OCR, payments, mapping, LLM APIs. Especially where the quota is contractual and the penalty is suspension rather than a 429.
- **Heterogeneous memory profiles**, where one job type is an order of magnitude heavier than the rest.

## When It's Unnecessary or Overkill

- **Four workers against a generous database.** Do the arithmetic once, write it in the README next to the replica count, and stop.
- **Elastic dependencies where you're a rounding error.** Don't build a bulkhead around S3. Reserve this for resources with a real ceiling you can hit.
- **A fixed fleet with a stable workload.** If nothing scales automatically and deploys don't change counts, the budget is a one-time calculation, not a system.
- **Adaptive concurrency before static limits.** Controllers that discover the limit are excellent and are not a substitute for knowing that 60 × 10 > 200. Do the arithmetic first; it's free and it catches most of it.
- **When the honest answer is "the backlog will take three hours."** Sometimes the capacity is what it is, and the work is communicating the lag rather than engineering around it.

## Trade-offs

- **Every limit is a new place work waits**, and waiting that isn't instrumented looks exactly like slowness. Measure permit-wait and pool-wait time separately from work time, or the next investigation will blame the wrong component.
- **Partitioning costs utilization** — the same trade as 10.2b, restated: the image pool sits idle while the geocode pool is saturated, and you bought predictability with it.
- **Fleet-wide permits need shared state**, which means a round trip in the hot path and a new dependency that can itself fail. That forces a decision nobody enjoys: if the limiter is unavailable, do you fail open or closed? Fail-open on a limiter protecting a fragile third party recreates the incident you built it for; fail-closed on one protecting an elastic resource causes an outage you didn't need. It's a per-dependency choice, not a global one.
- **Static budgets go stale.** Someone bumps replicas, a library upgrade changes a default pool size, a new service starts sharing the database. The calculation is only as good as its last review, which argues for enforcing it in code rather than documenting it.
- **Connection poolers break session-scoped features.** PgBouncer in transaction mode is the standard answer at fleet scale, and it quietly invalidates advisory locks (10.3a), `LISTEN`/`NOTIFY` (10.1a), session variables, and some prepared-statement patterns. Two earlier articles' mechanisms depend on things a pooler takes away — that's a real coupling, not a footnote.
- **Serverless doesn't remove this problem**, it removes pooling. One database connection per concurrent invocation, with no process to hold a pool, is the canonical connection-exhaustion story; the fix is another pooling layer in front.

## Alternatives

- **Buy capacity.** A larger database instance, a higher provider tier, more memory per node. Frequently cheaper than the engineering, and instantly reversible.
- **A connection pooler** — PgBouncer, pgcat, RDS Proxy — which decouples client count from server backends and is the reason large fleets can exist at all.
- **Read replicas.** Most job work is reads; moving them off the primary changes the arithmetic more than any limiter will.
- **Remove the dependency from the hot path.** Cache geocodes (addresses don't move), batch provider calls, precompute derivatives on upload rather than per listing update.
- **Circuit breakers** (36.3) for when the dependency is *down* rather than merely full — a different failure needing a different response.
- **Adaptive concurrency control** — Netflix's concurrency-limits, Envoy's adaptive concurrency filter — when static numbers are wrong at both ends of the daily cycle.
- **Accept the lag.** Publish the backlog, set expectations, and don't scale.

## How to Achieve It

**Level 0 — write the footprint table.** Every consumer of every constrained resource, with its maximum. Most teams discover an unexpected consumer and a number that already exceeds the limit under conditions they haven't hit yet.
_Signal you're here:_ nobody can state the fleet's maximum possible connection count.

**Level 1 — match pool size to job concurrency, and set an explicit replica ceiling.** Two small numbers, derived rather than defaulted.
_Signal you need it:_ a pool size that came from a tutorial.

**Level 2 — instrument saturation, not just throughput.** Pool-wait time, permit-wait time, provider 429 rate, per-job peak RSS, and the oldest-job age per queue.
_Signal you need it:_ "the database is slow" with no wait-time metric to confirm or refute it.

**Level 3 — partition queues by the resource they exhaust**, with fixed worker counts per queue. The cheapest bulkhead available, and it reuses machinery you already have.
_Signal you need it:_ one job type's spike affecting job types that share nothing with it except the fleet.

**Level 4 — fleet-wide permits for external dependencies**, with an explicit fail-open or fail-closed decision per dependency.
_Signal you need it:_ 429s that correlate with your own scaling events.

**Level 5 — adaptive concurrency, and autoscaling on oldest-job age with the bottleneck's health as a brake.**
_Signal you need it:_ static limits that are too conservative at 3am and too aggressive at peak.

## Implementation

**Java.** Chosen because this is where the material is best codified — HikariCP's pool-sizing guidance is the reference argument for the arithmetic above, and Resilience4j gives the bulkhead a name and an implementation.

Pool size is derived from job concurrency, not chosen:

```java
int jobConcurrency = 5; // jobs in flight per worker process

HikariConfig cfg = new HikariConfig();
cfg.setMaximumPoolSize(jobConcurrency + 1);
cfg.setConnectionTimeout(2_000); // fail fast rather than queue invisibly
```

> **Aside 1.** `jobConcurrency + 1`, not 50, and not the framework default. Little's Law says the connections actually in use are throughput × hold time; if a job holds one for 20ms, a fleet doing 1,000 jobs/sec needs about 20 connections *in total*. A large pool doesn't add capacity the database doesn't have — it moves the queue from your process, where you can measure the wait, into the server, where the wait becomes everyone's latency. The 2-second `connectionTimeout` is part of the same idea: a job that can't get a connection should fail and be retried with backoff (10.2a), not block a worker indefinitely.

The budget becomes a startup assertion, so it can't silently go stale:

```java
int maxReplicas = Integer.parseInt(env("WORKER_MAX_REPLICAS"));
int dbBudget    = Integer.parseInt(env("DB_CONNECTION_BUDGET")); // workers' share

int worstCase = maxReplicas * cfg.getMaximumPoolSize();
if (worstCase > dbBudget) {
    throw new IllegalStateException(
        "fleet may open " + worstCase + " connections; budget is " + dbBudget);
}
```

> **Aside 2.** This is the highest-value ten lines in the article. A capacity calculation on a wiki page is true on the day it's written; a deployment that refuses to start is true on the day someone doubles the replica count to clear a backlog at 2am. Note that it needs the *ceiling*, not the current count — the failure mode is the autoscaler's maximum, not today's value.

The permit in front of the geocoder has to be fleet-wide:

```java
try (Permit p = permits.acquire("geocode", Duration.ofSeconds(30))) {
    return geocoder.lookup(address);
}
```

Behind that, a Redis sorted set of permit ids scored by expiry, with a Lua script that atomically drops expired entries, counts what's left, and adds one if there's room.

> **Aside 3.** Permits expire, which makes them leases, which makes them 10.3a's problem in a new costume: a process that dies holding a permit must not hold it forever, and a process whose permit expires while its HTTP call is still in flight is exceeding the limit without knowing it. Set the TTL comfortably above the call's own timeout and accept a small overshoot — a permit system that is approximately right is enormously better than a replica count that is exactly wrong. And decide, per dependency, what happens when Redis is unreachable: fail-closed here (jobs retry, the backlog grows, the provider stays up) is right for a fragile quota, and would be wrong for a permit guarding something elastic.

A `java.util.concurrent.Semaphore` or Resilience4j's `Bulkhead` is the right tool for the in-process half of this — capping concurrent image renders per JVM, where the constraint is that process's heap:

```java
// container limit 2GB, one render peaks at 1.2GB → one at a time, per process
Bulkhead renders = Bulkhead.of("render", BulkheadConfig.custom()
    .maxConcurrentCalls(1)
    .maxWaitDuration(Duration.ZERO) // don't hold a worker waiting; let it take other work
    .build());
```

> **Aside 4.** Memory limits are per-process, so this is the one place an in-process semaphore is exactly the right scope. Two container-level details matter more than the code: set an explicit memory limit so a bad job kills one worker rather than a node, and set `-XX:MaxRAMPercentage` so the JVM sizes its heap against the container rather than the host — a default-configured JVM on a large node will happily plan for memory the cgroup will never give it, and the kernel resolves the disagreement with SIGKILL. Then cap attempts on that job type, so a genuinely poisonous job is dead-lettered after three pods rather than after all sixty.

## Further Reading

- **HikariCP wiki, "About Pool Sizing"** — the benchmark, the formula, and the counterintuitive core result that smaller pools go faster. The single most useful page on this topic.
- **PostgreSQL wiki, "Number Of Database Connections"** — why a connection is expensive, and the guidance a pooler exists to work around.
- **PgBouncer documentation, "Pooling modes"** — what transaction mode gives you and precisely which session-scoped features it takes away.
- **Michael Nygard, _Release It!_** — Bulkhead, and the broader treatment of how resource exhaustion in one component propagates into an unrelated one. The vocabulary this article uses is largely his.
- **Netflix, "Performance Under Load" and the `concurrency-limits` library** — adaptive concurrency with AIMD, and the argument that the correct limit is not a constant.
- **Resilience4j documentation, "Bulkhead"** — semaphore versus thread-pool bulkheads, and why the choice matters for how waiting behaves.
- **Brendan Gregg, _Systems Performance_ (the USE method)** — utilization, saturation, errors, applied per resource. The discipline that turns "the database is slow" into a measurement.
- **AWS documentation on RDS Proxy and Lambda database connections** — the serverless restatement of the same arithmetic, for when the fleet has no processes to pool with.

A Go sibling would be worth writing, because two things it offers change the shape of the solution: `golang.org/x/sync/semaphore` is *weighted*, so a job that costs three units of a resource can say so rather than being approximated by a separate queue, and `GOMEMLIMIT` gives the runtime a soft memory ceiling that makes a heavy job degrade into GC pressure instead of an OOM kill. Not yet written.

---

The habit to carry out of this: for each dependency your jobs touch, be able to answer two questions — how many concurrent operations can the fleet aim at it, and where is that number enforced. "Replicas times pool size, enforced nowhere" is a real answer, and it means the limit exists, nobody has seen it, and the autoscaler is authorized to spend it.
