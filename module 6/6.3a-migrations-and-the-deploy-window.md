# Migrations and the Deploy Window

_Module 6.3a — Database Design & Data Management_

## The Problem

Two failures, and the second one is the interesting one.

### Nobody knows what the schema is

A four-year-old product. Someone asks whether `users.locale` is nullable. The answer takes forty minutes, because:

- Staging has a `users.locale` column with a default of `'en'`.
- Production has one without a default, because the column was added by hand during an incident in March and the staging version was added later from a script someone wrote from memory.
- There's a `schema.sql` in the repository, last updated eleven months ago.
- One developer's local database has three columns nobody else has.

This part is solved, and has been for fifteen years: schema changes go in the repository, in order, applied by a tool that records what it has applied. Flyway, Liquibase, Alembic, golang-migrate, Rails, Django, Prisma — the differences between them are smaller than the difference between using one and not. If you aren't doing this, do it before reading further; everything below assumes it.

### Deploying is not an instant

Now the part that keeps going wrong even at teams who do all of the above correctly.

A rename. `users.name` should be `users.full_name`. The migration is one line, it's reviewed, it's in the repository, and it runs as part of the deploy.

```
13:04:00   migration runs   ALTER TABLE users RENAME COLUMN name TO full_name
13:04:01   every running pod starts failing:  column "name" does not exist
13:04:40   first new pod becomes ready
13:06:10   rollout completes
```

Two minutes and ten seconds of total outage, for a rename. And if the new version fails its health checks, the deploy system rolls the *code* back and does nothing about the *schema*, so the outage doesn't end — it continues until someone writes and applies the reverse migration by hand, under pressure, at 13:09.

The same shape, three other ways:

- **Add `NOT NULL` with no default.** Every insert from the still-running old code fails, because old code doesn't set a column it doesn't know about.
- **Drop a column.** The old code still selects it — and if you use an ORM, it selects it whether or not anything reads it.
- **Tighten a constraint.** Old code writes a value that was legal when it started the request and isn't by the time it commits.

The mistake in all four is the same, and it isn't the SQL:

```
     a deploy is a window, not a moment

     t0 ─── migration ─── pods rolling ─────────────── t1
            new schema    new schema         new schema
            old code      old + new code     new code
                     └──────────┬──────────┘
                     every migration incident lives in here
```

And that window is longer than it looks. It includes however long a rolling deploy takes, plus the queue consumers that restart on a different schedule, plus the canary you're leaving on the old version for an hour, plus the one pod that didn't terminate, plus the cron job that started before the migration and finishes after it. It also *reopens* every time you roll back, which can be any time in the next week.

So the rule the rest of this article unpacks: **the schema in production must work with the code currently running, and the code you deploy must work with the schema currently applied.** Both directions, at every instant, including during rollbacks.

## What It Is

A **migration** is a versioned, ordered, immutable change to the schema, checked into the same repository as the code that depends on it, applied by an automated process that records what it has already applied.

Each word there is load-bearing. *Ordered*, because schema changes aren't commutative. *Immutable*, because a migration that ran in production cannot be edited — editing it changes what happens on a fresh database while leaving production untouched, which is how environments diverge in a way that's invisible until it isn't. *Recorded*, because the database is the only authority on what has actually been applied to it.

Two distinctions to fix now.

**Schema migration versus data migration.** `ALTER TABLE … ADD COLUMN` is a fast metadata operation. `UPDATE users SET full_name = name` on 200 million rows is a long-running job that touches every row, generates enormous write-ahead log, and must be resumable. They look similar — both are "SQL you run once during a release" — and putting the second one inside a migration script is the single most common way a deploy holds a lock for forty minutes. Backfills are jobs, not migrations.

**Imperative versus declarative.** Flyway-style tools apply an ordered list of changes you wrote. Atlas, Prisma, and Liquibase's declarative mode take a description of the schema you *want* and compute the difference. Declarative removes a real category of pain (ordering, merge conflicts, drift detection) and introduces a different one: the tool decides how to get from here to there, and "drop the column and add a new one" is a perfectly valid diff for what you intended as a rename. With declarative tooling the reviewable artifact is the generated plan, not the schema file.

## Recognizing the Problem

Your migration process is the thing that's broken if:

- Deploys need a maintenance window "because of the database."
- Someone has a psql session open to production during releases.
- Staging and production schemas differ and nobody can say by how much.
- Rolling back a deploy leaves the system broken rather than fixed.
- Migrations are applied by a person, at a time coordinated in chat.
- The minute after a deploy you see `column … does not exist` or `null value in column … violates not-null constraint`.
- Two branches add migration `0047`, and the fix is renumbering one of them.
- Nobody has ever run a down migration, and everybody believes they work.
- A migration timed out halfway through the deploy pipeline, and the current state of production is "some of it."

The signal that distinguishes this article's problem from 6.3b's: **here the errors come from application code, immediately, and name a column.** If instead everything is hanging and nothing is erroring, that's a lock, and that's the next article.

## How It Works

### The history table

The tool keeps a table — `flyway_schema_history`, `schema_migrations`, whatever it's called — listing every migration applied, when, and a checksum of its contents. On each run it compares the repository against that table and applies the difference in order.

The checksum is the underrated part. It turns "someone edited a migration that already ran" from a silent divergence into a loud failure. Tools offer a repair command to overwrite the recorded checksum; every use of it is a decision to stop knowing whether your environments match.

Two operational details that matter more than they sound:

- **Migrations must not run concurrently.** Five pods starting at once will all try. Most tools take a database advisory lock for exactly this; if yours doesn't, the migration belongs in a release step that runs once, not in application startup.
- **Ordering by timestamp rather than sequence number** removes the renumber-on-merge conflict, at the cost of allowing two migrations to be developed in ignorance of each other and applied in an order neither author tested. Both models have this problem; only one of them makes it visible at merge time.

### Expand and contract

The rename can't be done in one step, so it's done in six, and the sequence generalizes to every destructive change. It's also called parallel change.

```
  1. EXPAND      add full_name (nullable)                       schema only
  2. DUAL WRITE  code writes both columns, reads name           deploy
  3. BACKFILL    copy name → full_name in batches               job
  4. READ SWITCH code reads full_name, still writes both        deploy
  5. STOP WRITE  code stops writing name                        deploy
  6. CONTRACT    drop name                                      schema only
```

Every arrow between two steps is a state that production sits in for hours or days, and every one of those states works with the step before it and the step after it. That's the whole design goal — at no point is there a version of the code that can't run against the schema, in either direction.

Some steps merge for smaller changes. A nullable additive column is step 1 and nothing else. The full six matter when the column is large, the table is hot, or the old and new representations genuinely differ (splitting `name` into `given_name` and `family_name` is the same dance with a transformation in step 3).

Two things routinely go wrong in this sequence.

**Step 5 is skipped,** because after step 4 everything works and the ticket is closed. Now the old column is still being written by code nobody is reading, indefinitely, and the next person to look at the schema can't tell whether it's live.

**Step 6 is never done at all.** This is the most common outcome of adopting expand/contract, and the reason schemas accumulate `name_old`, `settings_v2`, and eleven nullable columns that should have been `NOT NULL` years ago. The countermeasure is unglamorous: write the contract ticket, with a date, in the same pull request as the expand.

### Additive is safe; destructive is safe only when nothing is looking

From the compatibility rule, the whole taxonomy falls out:

- **Safe in one step:** adding a nullable column, adding a new table, adding an index (with the caveats in 6.3b), adding a permissive constraint.
- **Safe only after readers are gone:** dropping a column or table, renaming anything, narrowing a type.
- **Safe only after writers are gone:** adding `NOT NULL`, adding a unique constraint, tightening a check.

"Readers" and "writers" mean *every deployed artifact*, which includes the API, the workers, the cron jobs, the analytics job someone wrote in 2024, and the reporting tool connecting directly to a replica. The most common surprise in step 6 is a consumer nobody remembered.

ORMs complicate "readers" specifically, because they usually select every mapped column regardless of what the caller uses. That's the subject of *Implementation*.

### Rollback is mostly a fiction

Down migrations feel like the answer to all of this, and they mostly aren't.

**DDL is reversible; data is not.** The down migration for "add a column" is "drop the column" — which also destroys everything written to it since, which is precisely the data that accumulated during the incident you're now rolling back from. The down migration for "drop a column" cannot restore its contents at all.

**They're never tested.** A down migration runs in development, if ever. The first time it runs in production is during an incident, from a file written months earlier by someone reasoning about a schema state that no longer exists.

**They don't compose.** Rolling back three deploys means running three down migrations in reverse order against data that has changed under all three.

The practical stance is: **roll forward.** If a deploy is bad, deploy a fix — which is fast if your changes are additive, because the schema didn't need to change and the previous code still works against it. Expand/contract isn't just a way to avoid downtime; it's what makes rollback possible at all, because every intermediate state is compatible with the one before.

Keep down migrations where they're trivially correct and genuinely needed — local development, resetting a feature branch. Don't build a release process that depends on them.

## When It's Appropriate

The full ceremony is proportional to what a mistake costs, which mostly means table size and whether anyone is watching:

- **Six steps and a week:** a hot table with millions of rows, a rolling deploy across many instances, multiple independent consumers, and a destructive change. Renaming a column on `orders` in a 24/7 product.
- **Two steps and an afternoon:** a moderately sized table, a destructive change, but a single service with a short rollout. Expand, deploy, backfill, switch, drop next week.
- **One step, right now:** additive changes to anything; any change at all to a 500-row configuration table on an internal admin tool at 02:00; anything pre-launch. Renaming a column on a table with no traffic is one line, and dressing it up in six deploys is a cost with no corresponding risk.

The question to ask isn't "is this change destructive" but "how many running processes have an opinion about this column, and how long does it take all of them to stop having one."

## When It's Unnecessary or Overkill

- **Expand/contract for an additive nullable column.** It's already compatible in both directions; there's nothing to sequence.
- **Writing down migrations for everything.** Effort spent on a mechanism you've decided not to rely on, which then rots and misleads.
- **Approval gates on every migration.** The observable effect is that people batch twelve schema changes into one release, which is strictly more dangerous than twelve small ones.
- **Dual-writing to a second table** when a nullable column on the existing one would do.
- **Avoiding migrations by putting everything in a JSON column.** You've traded a schema change you do once for a branch in every read path, forever (6.2a).

## Trade-offs

**Expand/contract stretches one change across days and multiple deploys,** and for that whole period production runs code that writes two representations of the same fact. That's a copy with an owner and no reconciliation job (6.2a), living in your system by design, and it's where the subtle bugs land — a code path that writes only the old column, a queue consumer deployed on a different cadence, an admin tool that bypasses the dual-write entirely.

**Half-finished migrations accumulate.** Every skipped contract step is permanent ambiguity in the schema. After three years the cost isn't storage, it's that nobody can tell which columns are real.

**Immutability means mistakes are appended, not fixed.** A migration with a bug that already ran in production gets corrected by a *new* migration. The broken one stays in the repository forever, and every fresh database runs it and then the fix.

**Migrations in the deploy path serialize deploys,** and a long one can hit the pipeline's timeout and be killed mid-statement. That failure mode is one of the reasons backfills don't belong there.

**Declarative tooling moves the risk rather than removing it.** No ordering conflicts, no forgotten drift — and a diff engine that will cheerfully plan a drop-and-recreate. The generated plan has to be reviewed with the same attention an imperative migration would get.

**Multiple databases multiply everything.** Schema-per-tenant or sharded deployments mean the migration runs N times, fails partway on tenant 23 (5.1), and now two schema versions exist simultaneously — which the application must tolerate, not just the deploy process.

**Testing is harder than it looks.** A migration that passes against an empty CI database tells you the syntax is valid and nothing else. Anything involving locks, volume, or existing bad data needs a production-shaped dataset to be meaningfully tested.

## Alternatives

- **Declarative schema management** (Atlas, Prisma Migrate, Liquibase declarative). Better drift detection and no ordering pain; review the plans.
- **ORM auto-synchronization** — Hibernate's `ddl-auto=update`, TypeORM's `synchronize`. Excellent in development, and it should never be enabled in production: it never renames (it drops and adds), it never removes, its output isn't reviewable, and there's no record of what it did.
- **A maintenance window.** For a B2B product used in one time zone during business hours, "Sunday at 03:00" is a legitimate engineering answer that removes most of this article. Say so out loud rather than performing zero-downtime ceremony that nobody needs.
- **Feature flags** (3.4) as the companion technique. They decouple "the new code is deployed" from "the new code is active," which shrinks the window in which both behaviours matter and makes step 4 revertible without a deploy.
- **Blue/green at the database level** — two schemas and a cutover. Viable for read-mostly systems, and it founders on the same problem as everything else: writes that arrive during the cutover have to go somewhere.

## How to Achieve It

1. **Establish a known state.** Baseline the current production schema as migration zero, check it in, and then remove DDL privileges from human accounts in production. The second half is what makes the first half stay true.
2. **One migration per logical change,** reviewed like code, named for what it does.
3. **Apply automatically in a release step,** once, under a lock — not from application startup on every pod.
4. **Default to additive.** Treat any destructive statement in a pull request as requiring an explanation of who still reads that column.
5. **Sequence destructive changes as expand/contract, and create the contract ticket in the same pull request as the expand,** with a date. This is the step that determines whether your schema is comprehensible in three years.
6. **Move backfills out of migrations** into batched, resumable, throttled jobs (6.3b).
7. **Roll forward.** Design so that the previous code version works against the new schema, which makes a code-only rollback sufficient.
8. **Test migrations against realistic data** — a restored, anonymized copy — especially anything that adds a constraint to existing rows.

The one-question version, worth asking on every schema pull request: **if we roll the code back ten minutes after this runs, does production work?** If the answer is no, the change needs to be split.

## Implementation

Java, because JPA makes the compatibility rule concrete in a way explicit SQL doesn't — it decides what your queries select without asking you.

Steps 2 through 4 of the rename, in the application:

```java
@Entity
public class User {
    @Id Long id;

    @Column(name = "name")
    private String legacyName;        // step 5 removes this field

    @Column(name = "full_name")
    private String fullName;

    public void setFullName(String v) {
        this.fullName = v;
        this.legacyName = v;          // dual write, steps 2–4
    }

    public String getFullName() {
        return fullName != null ? fullName : legacyName;   // steps 2–3
    }
}
```

The fallback in the getter is what makes step 3 optional-ish rather than blocking: rows written before the expand still have only `name`, and reads work throughout the backfill instead of after it. It comes out in step 4, once the backfill is verified — and "verified" means a query counting rows where `full_name IS NULL AND name IS NOT NULL` returns zero, not that the job logged success.

The dual write belongs in the setter, or in a single service method, precisely because it will otherwise be missed. Grep the codebase for other paths that write `legacyName` directly; the CSV importer usually does.

Now the part that's specific to ORMs and catches people out. Hibernate generates:

```sql
select u.id, u.name, u.full_name from users u where u.id = ?
```

for every load of that entity, including the loads that only want `id`. So **dropping the `name` column breaks every running pod that still has `legacyName` on the entity, whether or not any code reads it.** The ordering that follows is the opposite of how most teams sequence it:

1. Deploy the code with the field removed. *Then*
2. run the migration that drops the column.

Deploying the field removal and the `DROP COLUMN` in the same release puts both events inside the window — old pods with the field, new schema without the column — and produces exactly the 13:04 incident. Schema-first is correct for additive changes and backwards for destructive ones.

Two related traps in the same neighbourhood:

- `@Column(name = "full_name")` means the *field* can be renamed freely without touching the database, and the database column can be renamed by changing one annotation. Convenient, and it makes it very easy to ship a "rename" that is actually a destructive schema change disguised as a one-line diff.
- `spring.jpa.hibernate.ddl-auto` must be `validate` or `none` in production. `validate` is the better choice: it fails at startup when the entity and the schema disagree, which converts a runtime error in one endpoint at 13:04 into a failed health check that stops the rollout.

## Further Reading

- **"Evolutionary Database Design," Martin Fowler and Pramod Sadalage** (martinfowler.com), and the book it grew into, **_Refactoring Databases_** (Ambler & Sadalage). The original statement of migrations as versioned refactorings, and still the clearest argument for why the schema belongs to the application's repository.
- **"ParallelChange," Danilo Sato** (martinfowler.com/bliki). Expand/contract as a general technique, not a database one — the same sequence applies to APIs and message formats, which is worth noticing when you reach Module 33.
- **Flyway documentation** on versioned versus repeatable migrations, baselining, checksums, and the repair command. Reading what `repair` actually does is the fastest way to understand why immutability matters.
- **Atlas documentation** for the declarative model, particularly its treatment of destructive-change detection and migration linting — a good look at where human judgment has to be reinserted when a tool computes the plan.
- **GitLab's database migration style guide** (part of their public development documentation). One of the few detailed public accounts of running migrations continuously against a large production database, including their separation of regular and post-deployment migrations, which is essentially step 6 given a home.
- **Stripe's "Online Migrations at Scale"** — the four-phase dual-write migration described end to end on a live system, including the verification step that most write-ups skip.

A **TypeScript** sibling, built on Prisma Migrate, would show the declarative half of this. There, the artifact under review is a schema file, and the phases of a rename have to be expressed as a sequence of schema-file states with hand-written SQL inserted where the diff engine would otherwise plan a drop-and-add — `@map` doing the job `@Column(name=…)` does above. The genuinely different content is what happens when the generated plan and the intended change diverge, and where a team is supposed to catch that: not in the migration file, which was generated, but in a review step that has to exist on purpose. Not yet written.

---

The habit: **read every schema change twice, once forwards and once backwards.** Forwards is "does the new code work against this?", which everyone checks. Backwards is "does the code that is running right now work against this, and will it still work if we roll back in ten minutes?", which is where the incidents are.

Next is the other half of the window — what happens when the `ALTER` itself is the outage, because it took a lock, or rewrote two hundred million rows while everybody waited.
