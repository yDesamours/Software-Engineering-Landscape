# N+1 and the ORM's Queries

_Module 6.4a — Database Design & Data Management_

## The Problem

An order list endpoint. Fifty orders per page. The code is the kind that passes review without anyone pausing:

```java
List<Order> orders = orderRepository.findByMerchantId(merchantId);
for (Order o : orders) {
    render(o.getReference(),
           o.getCustomer().getName(),      // ← field access
           o.getItems().size());           // ← field access
}
```

It takes 900 ms. The investigation goes to the database first, and finds nothing:

- Slowest query on the endpoint: **0.4 ms.**
- Database CPU: **8%.**
- No lock waits, no sequential scans, every index in use.
- Total time the database spent working on this request: **about 40 ms.**

Every query is fast. The endpoint is slow. Those two facts coexist because of what's actually happening:

```
   what the code says                 what the database receives
   ──────────────────                 ──────────────────────────
   findByMerchantId(…)                SELECT … FROM orders WHERE merchant_id = ?
   for o in orders:
       o.getCustomer().getName()      SELECT … FROM customers WHERE id = ?      ×50
       o.getItems().size()            SELECT … FROM order_items WHERE order_id=? ×50

   one loop, two field accesses       101 round trips
                                      40 ms of database work
                                      860 ms of waiting for the network
```

At roughly 8 ms per round trip — driver overhead, network hop to another availability zone, connection pool handoff, result parsing — the 101 trips are the entire response time. Nothing is slow. There is just an enormous amount of *not-slow*.

Three things make this the defining performance bug of ORM-based systems.

**It's invisible at the call site.** `o.getCustomer()` is a field access. It looks exactly like reading memory. There is no syntactic difference between the version of this loop that issues one query and the version that issues 101.

**It's fine locally.** On a laptop, the database is on the same machine and a round trip is 0.1 ms, so 101 of them cost 10 ms and nobody notices. The bug is created in an environment where it cannot be observed.

**It multiplies.** Once the loop nests — orders, then each order's items, then each item's product — 50 orders with 4 items each becomes 50 + 200 + 200 queries, and the endpoint's latency is now a polynomial in the page size.

So somebody sets every association to eager loading, and the second failure arrives. The list query becomes a six-table join returning 50 × 4 × 2 = 400 rows to describe 50 orders (the fan-out from 6.2a), transferring 8 MB to render a table with four columns. Worse, eager is declared on the *mapping*, not the query — so the endpoint that only counts orders now also loads every customer, and so does the one that just checks a status.

Both failures come from one missing idea. The ORM's job is to make rows look like objects, and it succeeds: **I/O becomes indistinguishable from memory access.** Everything in this article is about putting the cost back where you can see it.

## What It Is

**N+1** is the pattern where fetching a collection of N things issues one query for the collection and one more per element — 1 + N. It is not a bug in the ORM. It's lazy loading working precisely as designed.

Lazy loading exists for a real reason: you cannot eagerly load an object graph, because following every association transitively from an order reaches the customer, their other orders, their addresses, the merchant, the merchant's other customers, and eventually most of the database. Something has to stop, and "stop at the first reference, fetch on demand" is the only rule that works without knowing the query.

Two disambiguations, both worth having now.

**N+1 is not an ORM problem; it's a fan-out-of-round-trips problem.** The same shape appears as an HTTP call per item in a loop, a GraphQL resolver that runs per field per row (Module 8), and a microservice call per element (Modules 23 and 36). If you learn to recognize it here, you recognize it everywhere, and the fix is always the same idea: turn N requests for one thing into one request for N things.

**Lazy versus eager is the wrong axis.** It's presented as a choice of default, and both defaults are wrong — lazy gives you 101 queries, eager gives you a six-table join on endpoints that needed two columns. The real answer is that **the fetch strategy belongs to the query, not to the mapping**, and every mature ORM has a mechanism for that. Most teams never use it because the mapping-level setting is the one the tutorial mentions.

## Recognizing the Problem

N+1:

- The endpoint is slow and every query in the slow log is fast.
- Latency scales linearly with the number of items in the response — twenty-five per page is exactly half as slow as fifty.
- Database CPU is low while application threads are waiting.
- The same query text appears in `pg_stat_statements` with a tiny mean time and an enormous call count.
- It's fast on a laptop and slow in production. This one is nearly diagnostic on its own.
- The log for a single request is a burst of identical `SELECT … WHERE id = ?` with different parameters.
- Nobody knows how many queries the endpoint issues. If that number isn't measured, assume it's wrong.

Over-eager fetching, which is the same problem's overcorrection:

- One query returns tens of thousands of rows to produce a page of twenty.
- Memory and GC pressure spike on list endpoints.
- The generated `SELECT` has eighty columns and the response has four.
- Response time is high and *flat* — no better for one row than for fifty.
- Hibernate logs `HHH000104: firstResult/maxResults specified with collection fetch; applying in memory`, which means your pagination is happening in the JVM after loading everything. That warning is one of the most expensive lines of log output in the industry, and almost nobody reads it.

## How It Works

### Lazy loading is a proxy

When an entity is loaded, its to-one associations become proxy objects and its collections become wrapper objects, both holding a reference to the persistence session. The first method call that needs real data triggers a query, transparently. That transparency is the feature and the entire problem: the trigger point is a dereference, and dereferences don't look like I/O in any language.

A consequence people meet the hard way: outside the session, the proxy can't load anything, which produces `LazyInitializationException`. The usual "fix" is to keep the session open for the whole request (open-session-in-view), which resolves the exception by pinning a database connection for the duration of rendering — including the JSON serialization, including whatever the template does. That's the connection-slot arithmetic from 5.2b, arriving through a configuration default that ships enabled.

### Four ways to fetch the same data

For the order list, in queries and rows:

```
  strategy         round trips   rows transferred   notes
  ──────────────   ───────────   ────────────────   ────────────────────────────
  lazy (default)      1 + 50         50 + 50        the opening incident
  join fetch          1              400            fan-out; pagination breaks
  batch fetch         2              50 + 200       parents, then children IN (…)
  projection          1              50             only the columns rendered
```

**Join fetch** pulls the association in the same query. Correct for to-one associations and for single-entity fetches. For to-many it multiplies rows, and — the trap worth memorizing — **it silently breaks pagination**: the database's `LIMIT 50` would cut across a partially-loaded order, so Hibernate loads the entire result set and paginates in memory. The endpoint keeps working and gets slower every month.

**Batch fetch** is usually the right default for lists. Load the parents, collect their ids, load all children in one `IN (…)` query, stitch them together in memory. Two queries regardless of N. This is `@BatchSize` / `default_batch_fetch_size` in Hibernate, `Preload` in GORM, `include` in Prisma, and the DataLoader pattern in the GraphQL world — the same mechanism with four names.

**Projection** is the fix that usually goes unconsidered: don't load entities at all. Select exactly the columns the response contains, into a DTO. One query, one row per result, no persistence context, no lazy proxies, no dirty tracking, and no possibility of an accidental N+1 because there's nothing to dereference. For a read endpoint with a fixed response shape, this is almost always correct, and it's how "we had to drop the ORM" is usually avoided.

### The write side has its own surprises

Less famous than N+1 and roughly as expensive:

- **Dirty checking turns reads into writes.** At flush time the session compares every loaded entity against its original state and issues updates for anything that changed — including changes made accidentally, and including a setter called with an equal value if equality is implemented carelessly.
- **Updates write every column by default.** So updating one field rewrites the whole row, which touches every index on every changed column and forfeits the HOT-update optimization from 6.2b. Hibernate's `@DynamicUpdate` changes this, at the cost of a new prepared statement per column combination.
- **`saveAll` is N inserts,** unless JDBC batching is switched on *and* the statements are contiguous — interleaving inserts of two entity types silently breaks batching into single statements.
- **The first-level cache grows forever within a session.** A batch job looping over a million rows keeps every entity it has touched, and runs out of memory somewhere around row 400,000. Batch jobs need periodic `clear()` or a stateless session.

### The same bug one layer up

Once you can see it, the shape recurs: a GraphQL resolver that runs `getUser(id)` per row of a list; a service that calls an inventory API per line item; a Lambda that fetches a config per event. Each is 1 + N round trips caused by iterating a collection, and each is fixed by batching the N into one call. The DataLoader pattern exists because GraphQL makes this mistake structurally unavoidable at the framework level, and it is the batch-fetch idea generalized.

## When It's Appropriate

Which strategy, and when:

- **Lazy, for write paths and single-entity work.** Loading one order to change its status and navigating two references is what lazy loading is good at. The N is one.
- **Join fetch, for to-one associations and for `findById` with a known graph.** One query, no multiplication.
- **Batch fetch, as the default for any list endpoint that renders associated data.** Two queries at any N, no fan-out, pagination intact.
- **Projection, for read endpoints with a fixed shape** — list views, exports, reports, anything paginated, anything whose response is a table.
- **Raw SQL, when the query is the product** — window functions, recursive CTEs, aggregations, bulk updates, anything where you'd be fighting the mapping to express what the database does natively.

The ORM as a whole earns its place where the work is CRUD-shaped over a substantial entity model with real transactional write paths: mapping, identity, change tracking, lifecycle callbacks, and migration tooling are genuine value, and hand-rolling them is a project nobody budgets for.

## When It's Unnecessary or Overkill

- **Optimizing an endpoint that returns five rows.** Six queries is six queries.
- **Abandoning the ORM because of N+1.** Hand-written SQL has exactly the same bug the moment someone writes a loop; what you lose is the mapping layer, and what you keep is the problem.
- **Eager fetching as a global setting.** It converts a per-endpoint problem into an every-endpoint problem.
- **Reaching for a second-level cache to fix N+1.** You've made 101 queries cheap instead of making them one, and bought cache invalidation (Module 13) in exchange.
- **Building a bespoke data mapper** because the ORM was used without reading its fetching documentation.
- **Query-count golf on an admin page opened twice a week.**

## Trade-offs

**Per-query fetch plans put the strategy at the call site, where it can drift.** The endpoint is tuned; six months later someone adds a field to the DTO that dereferences an unfetched association, and the N+1 is back with no visible change to the query. This is why the defence is a test that counts queries, not a code review that reads them.

**Projections mean two representations.** An entity for writes and a DTO for reads, plus mapping between them. That's real duplication, and it's also the seed of a useful structure — read models shaped by the response and write models shaped by invariants is CQRS in its mildest form (2.4), and most systems benefit from it well before they'd describe themselves as doing CQRS.

**Batch fetching still isn't one query,** and the `IN (…)` list has practical limits: very large lists degrade, and varying list lengths generate a different prepared statement each time, which thrashes the plan cache. Batch sizes in the tens are a reasonable default for a reason.

**Dropping to SQL costs the mapping, the portability, and the refactoring safety,** and leaves you maintaining two idioms in one codebase. That's frequently worth it; it isn't free.

**The abstraction leaks in both directions.** To use an ORM well you must understand the ORM *and* the SQL it generates — more to know than either alone. The claimed benefit of "you don't have to think about SQL" is the source of the bug this article is about.

**Open-session-in-view trades a development-time exception for a production-time connection leak.** Turning it off produces `LazyInitializationException` during development, which is the failure arriving early and cheaply, in the place where it can be fixed.

## Alternatives

- **Typed query builders** — jOOQ, Kysely, sqlc, sqlx. SQL you write, with types the compiler checks, and no persistence context to surprise you. The best middle ground for read-heavy systems, and increasingly the default choice for new services.
- **Entities for writes, SQL projections for reads.** The single most useful structural answer, and the one that resolves most ORM arguments by giving each side the workload it's good at.
- **Database views** for stable read shapes, mapped as read-only entities (6.2a).
- **DataLoader-style request-scoped batching** — mandatory in GraphQL, useful anywhere a service is called per item.
- **A derived read store** (6.1) when the read shape has genuinely diverged from the write shape.

## How to Achieve It

1. **Count queries per request, and put the number somewhere visible.** An interceptor that logs "GET /orders — 103 queries, 41 ms DB, 912 ms total" turns an invisible bug into an obvious one. This is the highest-leverage item on this list by a distance.
2. **Make every association lazy in the mapping.** No exceptions; eager is a query-level decision.
3. **Set a global batch fetch size** — `default_batch_fetch_size: 25` or equivalent. It doesn't design anything, it just converts an accidental 1+50 into 1+2 while you're not looking. Cheap insurance.
4. **Choose a strategy per endpoint** from the four above, based on the shape of the response.
5. **Assert on query counts in tests.** `assertThat(queries).isLessThan(5)` on the list endpoint is a regression test for a bug class that otherwise only reappears in production.
6. **Disable open-session-in-view** and return DTOs from the transactional boundary. The exceptions you get on the way are the point.
7. **Drop to SQL deliberately** where the query is the product — and keep those queries in one place rather than scattered.

## Implementation

Java and JPA, because this is where the mechanisms are most fully developed and the traps most concrete.

The mapping stays lazy, always:

```java
@ManyToOne(fetch = FetchType.LAZY)  private Customer customer;
@OneToMany(mappedBy = "order", fetch = FetchType.LAZY) private List<OrderItem> items;
```

Then the endpoint decides. For a single order with its graph, a join fetch:

```java
@Query("""
    select o from Order o
      join fetch o.customer
      left join fetch o.items
     where o.id = :id""")
Optional<Order> findByIdWithGraph(@Param("id") Long id);
```

One query, no multiplication that matters at N=1. Now the trap, because the same annotation on a list method is a different thing entirely:

```java
// Do not do this with pagination.
@Query("select o from Order o left join fetch o.items where o.merchantId = :m")
List<Order> findPage(@Param("m") Long m, Pageable page);   // ← silently broken
```

`left join fetch` on a collection plus `LIMIT` cannot both be correct — cutting the result at 50 rows would truncate an order's items — so Hibernate resolves it by fetching *every* matching order, materializing the whole graph in the JVM, and slicing there. It logs `HHH000104` and returns correct results, which is why this survives for years. If you need both the collection and pagination, use two queries: page the ids, then fetch the graph for those ids.

For list endpoints, batch fetching is the low-drama default:

```yaml
spring.jpa.properties.hibernate.default_batch_fetch_size: 25
```

The 1 + 50 becomes 1 + 2: the parent query, then `… where order_id in (?, ?, … ×25)` twice. No mapping change, no query change, no fan-out. Treat it as a safety net rather than a design — it makes accidents cheap, it doesn't make them intentional.

And the version most list endpoints should actually use, which stops loading entities at all:

```java
public record OrderRow(String reference, String customerName, long itemCount) {}

@Query("""
    select new com.example.OrderRow(o.reference, c.name, count(i))
      from Order o
      join o.customer c
      left join o.items i
     where o.merchantId = :m
     group by o.reference, c.name""")
Page<OrderRow> findRows(@Param("m") Long m, Pageable page);
```

One query, fifty rows, three columns. No persistence context, so no lazy proxies to trigger, no dirty checking at flush, and no way for a later change to this DTO to reintroduce an N+1 without the compiler noticing — because there's nothing to dereference.

Two configuration lines worth changing on day one of any project:

```yaml
spring.jpa.open-in-view: false            # stop pinning a connection through rendering
spring.jpa.properties.hibernate.jdbc.batch_size: 50   # make saveAll actually batch
```

The first will produce `LazyInitializationException` in places that were quietly holding connections through JSON serialization. Each one is a bug being reported at development time instead of as pool exhaustion under load.

## Further Reading

- **_High-Performance Java Persistence_, Vlad Mihalcea**, and his blog. The definitive treatment of everything above — fetch strategies, batching, dirty checking, identity, and the generated SQL for each. If you use JPA seriously, this is the reference.
- **Hibernate User Guide, the Fetching chapter.** Fetch strategies, batch fetching, subselect fetching, and entity graphs, stated by the implementation.
- **Martin Fowler, _Patterns of Enterprise Application Architecture_** — Lazy Load, Identity Map, Unit of Work. The patterns every ORM implements, described before any of these tools existed, which makes the trade-offs easier to see without a vendor in the way.
- **"The Vietnam of Computer Science," Ted Neward.** The long-form argument that the object-relational mismatch is structural rather than a tooling gap. Worth reading once for the framing, even where you disagree with the conclusion.
- **DataLoader (github.com/graphql/dataloader).** Request-scoped batching and caching in about 300 lines, and the clearest statement of "turn N requests for one thing into one request for N things."
- **Spring Data JPA documentation on projections,** interface-based and class-based, including the closed-projection optimization that narrows the generated `SELECT`.
- **jOOQ's manual and Lukas Eder's writing on SQL.** The strongest case for the other side, and a good corrective if the ORM has started to feel mandatory.

A **TypeScript** sibling built on Prisma would reveal something structural. Prisma has no lazy loading — relations are fetched only when named in `include` or `select` — which eliminates the accidental dereference entirely and moves the mistake somewhere else: `await` inside a `for` loop, resolvers in a GraphQL layer, and `include` trees that fan out unboundedly because the cost of nesting one more level is one more line. The interesting content is what changes when the ORM refuses to hide I/O: the bug becomes visible but not impossible, the fixes become explicit batching rather than configuration, and the projection advice above becomes the default rather than the optimization. Not yet written.

---

The habit: **treat every dereference that crosses a relationship as a query until proven otherwise.** In an ORM-based codebase, `a.getB().getC()` is not a data structure being traversed; it's a distributed system call with no syntax to mark it.

And the measurement that makes the habit unnecessary: put the query count for each request next to its latency, in development, where everyone sees it. Almost nobody does this, and almost every team that starts finds something in the first hour.
