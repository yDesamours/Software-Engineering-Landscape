# Normalization and Denormalization

_Module 6.2a — Database Design & Data Management_

## The Problem

An online store, eighteen months in. The schema started clean:

```sql
customers(id, name, email, …)
orders(id, customer_id, status, placed_at)
order_items(id, order_id, product_id, quantity)
products(id, name, price_cents)
```

The order list page joined four tables, someone found it slow, and the fix was obvious: copy what the page needs onto the order.

```sql
orders(id, customer_id, customer_name, customer_email,
       total_cents, item_count, status, placed_at)
```

The page got fast. Then, over the next year and a half, four tickets arrive that nobody connects to each other.

**Ticket 1.** A customer changes their email address. The marketing export reads `orders.customer_email` and mails the old one. Filed as an export bug.

**Ticket 2.** Someone fixes the export with a nightly job that syncs `orders.customer_email` from `customers`. Two weeks later finance opens a ticket: invoices from 2024 now show the company's *current* legal name, and an invoice is supposed to show the entity that was billed at the time. Filed as a sync bug, in the exact opposite direction.

**Ticket 3.** Support notices that `total_cents` disagrees with the sum of the order's items on about 0.4% of orders. Nobody can say when it started. It turns out three code paths insert order items — checkout, the admin console, and a CSV importer — and two of them update the total.

**Ticket 4.** A promotion creates 80,000 orders in an hour. Afterwards, a few hundred have an `item_count` of 3 when they have 4 items. Two concurrent inserts both read 3, both wrote 4.

Four tickets, and they look like one problem — "we denormalized too much" — but they're three different problems with three different fixes:

- `customer_email` should never have been a single column. Marketing wants *the customer's current address*, which is a join. The invoice wants *the address as of the sale*, which is a permanent historical fact. One column was asked to be both.
- `total_cents` is a genuine copy with no owner. Three writers, no rule, no test.
- `item_count` has an owner and a broken update: a read-modify-write race that is invisible in every test, because tests run one request at a time.

And the reflex correction — "normalize it all back, take the join" — makes things worse in one specific place. `order_items` has no `unit_price`; it joins to `products` for the price. Refund a 2024 order today and you refund it at today's price. That's not redundancy waiting to be eliminated; it's a missing column.

So the question isn't normalized versus denormalized. It's: **for every fact in the schema, is there exactly one place that owns it, and does every copy have a rule that keeps it right?**

## What It Is

**Normalization** organizes a schema so that each fact is stored in exactly one place. The normal forms are the precise version of that, and for practical purposes 3NF compresses to one sentence: *every non-key column depends on the key, the whole key, and nothing but the key.* Higher forms exist (BCNF, 4NF) and matter in a handful of schemas; if you satisfy 3NF and your keys are sensible you are almost certainly fine.

The point of normalization is not tidiness. It's the elimination of three specific failures, which are worth being able to name because they're what you're trading away later:

- **Update anomaly** — a fact stored in six rows, updated in four.
- **Insert anomaly** — you can't record a supplier until they have a product, because supplier data lives in the products table.
- **Delete anomaly** — removing the last product for a supplier erases the supplier.

**Denormalization** is deliberately storing a fact in more than one place so a read gets cheaper. Deliberately is the operative word: nearly all of the damage in practice comes from denormalization that nobody decided on, added one column at a time to make a page faster.

One distinction to fix before anything else, because it's the one that generated two opposite bug reports above:

**A snapshot is not a denormalized copy.** `order_items.unit_price_cents` looks like a copy of `products.price_cents`, and it isn't. It's a different fact — *the price at which this thing was sold* — that happened to have the same value at one instant. It has no synchronization obligation because it was never a copy. Copies must be kept fresh; snapshots must never be touched again. Getting these two confused produces bugs in both directions: stale invoices in one, rewritten history in the other.

## Recognizing the Problem

Under-normalized — a fact is in more places than anyone is tracking:

- The same value appears in three tables and updating it means remembering all three.
- A support answer starts with "well, it depends which screen you're looking at."
- Columns named `tag1`, `tag2`, `tag3`, or a `tags` column holding `"red,large,sale"`.
- A `status` column whose meaning depends on a `type` column.
- Two rows in a table can disagree about something that has only one true value.

Copies with no owner — subtler and more common:

- You can name the column that goes stale but not the code that maintains it.
- `git grep` finds one place that writes it and three places that should.
- Nobody has ever run a query comparing the copy to the source.
- The copy is maintained in the application for some paths and by a nightly job for others.

Over-normalized for your actual access pattern:

- Every page render joins seven tables and all seven are on the critical path.
- You built an entity-attribute-value table, and now queries construct SQL from strings and nothing can be indexed properly.
- You can't sort or paginate a list without computing an aggregate first.

And the usual misdiagnosis: the endpoint is slow because it runs 600 queries, not because it runs one query with joins. That's Module 6.4, and no amount of schema change fixes it.

## How It Works

Two costs move in opposite directions, and it helps to know their real sizes rather than their reputations.

**A join's cost is usually small and bounded.** Fetching an order and looking up its customer by primary key is an index lookup — tens of microseconds, from cache. The folklore that "joins are slow" mostly comes from three things that aren't the join: missing indexes, joins in a loop issued by an ORM, and fan-out.

Fan-out is worth seeing, because it produces wrong answers rather than slow ones:

```
orders ⋈ order_items ⋈ shipments

  1 order  ×  4 items  ×  2 shipments  =  8 rows returned

  SUM(order_items.price) over that result counts every item twice
  COUNT(DISTINCT …) "fixes" it, and quietly costs a sort
```

**A copy's cost is not paid at write time; it's paid as an obligation.** The extra `UPDATE` is trivial. What's expensive is that every current and future write path must know about the copy, and nothing in the database, the type system, the compiler, or the test suite will tell you when one doesn't. The failure is silent and permanent.

So the useful frame is ownership rather than shape:

```
              normalized                    copy
              ──────────                    ────
 write        one row                       one row + N copies
 read         join (indexed, ~µs)           no join
 correctness  free                          an obligation in every write path,
                                            enforced by nothing
 failure      slow                          wrong, silently, starting some
                                            Tuesday nobody remembers
```

That asymmetry is the whole argument. A normalized schema fails in a way you can see on a dashboard. A denormalized one fails in a way you find out about from a customer.

### The three species of copied value

Almost every denormalization argument gets confused because these are treated as one thing.

**1. Snapshot.** A historical fact captured at a moment: unit price at sale, tax rate applied, shipping address the parcel actually went to, name on the invoice, the terms the customer accepted. Never updated, never synchronized, no drift possible, no measurement needed to justify it. If the business would care about the value *as it was*, it's a snapshot — and storing only a foreign key is a bug regardless of how fast the join is.

**2. Cache.** A genuinely redundant copy maintained for read speed: `comment_count`, `order.total_cents`, `last_message_at` on a conversation. This is the only species with a synchronization problem, and everything in *Trade-offs* below is about it.

**3. Structural.** Collapsing a 1:1 relationship into one table, or storing a small collection inline as JSON instead of as a child table. There's no duplicated fact here — just a decision about how the data is physically grouped, driven by whether the pieces are always read and written together. That's the aggregate-boundary question from 6.1, and it's the same question whether the store is a document database or a `jsonb` column.

Naming tells you which species you're in, and it's free: `unit_price_at_sale` is unambiguously a snapshot, `cached_item_count` is unambiguously not. `price` is how you get ticket 2.

## When It's Appropriate

Start normalized. Denormalize for one of these reasons, ideally with a number attached:

- **The fact is a snapshot.** Immediately, always, without measuring. This is the most common *missing* denormalization, and the only one whose absence is a correctness bug rather than a performance one.
- **You need to filter, sort, or paginate on a derived value.** This is the strongest performance argument by a wide margin, and it's structural rather than a matter of constants: you cannot index an aggregate that lives in another table. "Orders over $500, newest first, 50 per page" requires the total to be a column on `orders` with an index on it. No amount of query tuning gets around that, because keyset pagination needs something to seek on.
- **The read/write ratio is lopsided and the aggregate is expensive.** A subscriber count read on every page render and changed a few times an hour. Recomputing 400,000 rows per render to save one write per hour is the wrong direction.
- **The join can't happen.** The other side lives in a different service or a different store (6.1), so the choice isn't join-versus-copy, it's copy-versus-network-call-in-a-loop.
- **The row is read enormously more often than written and the copy is tiny.** A denormalized `tenant_id` on a deep child table so that the isolation predicate doesn't require a three-level join is a good trade (5.2a) — and note it's usually a snapshot too, since rows don't change tenants.

## When It's Unnecessary or Overkill

- **Denormalizing before measuring.** The join was 0.2 ms and the page was slow for an unrelated reason. This is the common case.
- **Denormalizing to fix an N+1.** The schema isn't the problem; the ORM's fetch strategy is (6.4).
- **Copying a value you have no plan to maintain.** An unmaintainable copy is worse than a slow join, because a slow join is never wrong. If you can't name the owner, don't add the column.
- **Using the schema as a cache.** If the value tolerates staleness and is read hot, a cache with a TTL (Module 13) is a copy whose drift is bounded by design and whose failure mode is a cache miss. A denormalized column's drift is unbounded and its failure mode is a wrong number on an invoice.
- **EAV.** An entity-attribute-value table is normalization taken past the point where the database can help you: no types, no constraints, no useful indexes, and queries assembled as strings. `jsonb` with a check constraint on the known keys is almost always better for genuinely variable attributes, and a real column is better for everything else.
- **Denormalizing for a report.** Reports are batch, tolerate staleness, and can run against a replica or a materialized view. They rarely justify changing the shape of the transactional schema.

## Trade-offs

For the cache species specifically, the costs that arrive with the column:

**Every copy needs an owner, an update path, and a backfill.** The backfill is the one people forget while planning: adding `comment_count` to 40 million posts means computing it for all of them, in batches, without holding a lock for an hour (Module 6.3).

**Concurrency introduces a race that tests won't find.** Read-modify-write on a counter loses updates under any isolation level below `SERIALIZABLE`. The fix — an atomic in-place increment — is one line, and it's the subject of *Implementation* below, along with the two problems it doesn't fix.

**Atomic increments serialize writers on one row.** Every writer touching the same counter queues behind a row lock. That's invisible at 10/s and a hard throughput ceiling at 10,000/s on one popular entity — the viral-post problem. The standard escape is sharded counters (N rows summed on read), which trades a cheap read for a cheaper write, exactly inverting the reason you denormalized.

**Drift is silent.** Nothing errors. The only way to know is a reconciliation query that compares copy to source, run on a schedule, alerting when it returns anything. Without that, your knowledge of correctness is a belief.

**Transactions get wider.** Maintaining the copy in the same transaction as the source extends how long locks are held, which couples unrelated writers on hot rows. Maintaining it outside the transaction reintroduces the dual-write problem from 6.1 inside a single database.

**Reverse operations are easy to miss.** Increments get written; the decrement for a cancellation, refund, soft-delete, or merge is what goes missing. When you see a counter drift in one direction only, this is why.

**Schema evolution multiplies.** Adding a field to the source now means adding it to N copies plus a backfill for each, and any query that reads only the copy silently returns the old shape until every one is found.

## Alternatives

Ordered by who owns correctness, which is the axis that matters. The further down, the more drift is possible:

**The database owns it.**
- *Do nothing.* An index and a well-written join. The default, and the right answer more often than it feels like.
- *Generated columns.* `total_cents bigint GENERATED ALWAYS AS (qty * unit_price_cents) STORED` — indexable, cannot drift, and the database refuses any attempt to write it. Restricted to values derivable from the same row, which excludes aggregates, and that restriction is exactly why it can't be wrong.
- *Triggers.* Can maintain cross-row aggregates, and they catch the code path you forgot, including the manual `UPDATE` someone ran in a console. The cost is logic that doesn't appear in your application's source, executes inside every write's transaction, and surprises whoever debugs it in two years. Reasonable for one or two invariants that must never be violated; unreasonable as a general strategy.

**A scheduled job owns it.**
- *Materialized views.* The whole derived result, refreshed on a schedule. Staleness is bounded and explicit, which is often a feature. `REFRESH MATERIALIZED VIEW CONCURRENTLY` requires a unique index and still rewrites everything, so this fits minutes-scale staleness over moderate data, not per-request freshness.
- *Summary tables.* A materialized view you refresh incrementally by hand: more code, but you can update only what changed.

**The application owns it.**
- *Maintained in code, verified by reconciliation.* The most flexible and the most fragile. Only sound if the reconciliation job exists from day one.

**Somewhere else entirely.**
- *A cache* (Module 13) when the value tolerates staleness, or *a derived store* (6.1) when the problem is the shape of the read rather than the location of the truth. Event-sourced projections (2.4) are the far end of the same idea: the copy is rebuilt from the log rather than maintained in place.

## How to Achieve It

1. **Classify the fact before writing the column.** Snapshot, cache, or structural. Name the column so the next person can't get it wrong.
2. **Normalize and ship.** With correct indexes, this carries further than most teams expect.
3. **When a read hurts, find out what's actually slow.** Query plan first. Is it the join, the N+1, or the fan-out? Three different fixes, and two of them aren't schema changes.
4. **If it's genuinely the aggregate — and especially if you need to sort or paginate on it — materialize it,** choosing the owner as close to the database as the value allows: generated column if same-row, trigger if cross-row and the invariant is critical, job if staleness is acceptable, application code last.
5. **Write the reconciliation query in the same pull request as the column.** Not later. It takes four lines and it is the only thing that converts "we believe this is correct" into "this was correct at 04:00."
6. **Alert on nonzero drift, and treat a nonzero result as a bug in the write path,** not as a number to be corrected. Fixing the data without finding the path guarantees a repeat.

The signal to move from one step to the next is always a measurement, and the signal that you skipped a step is a reconciliation job you've never run.

## Implementation

Go, because there's no ORM and no annotation in the way — the transaction is a variable, and the race is visible on the page.

```go
// The obvious version, and the one that produced ticket 4.
var count int
tx.QueryRow(`SELECT item_count FROM orders WHERE id = $1`, orderID).Scan(&count)
tx.Exec(`UPDATE orders SET item_count = $1 WHERE id = $2`, count+1, orderID)
```

Two requests arrive at once. Under `READ COMMITTED` — the default in Postgres and in most people's mental model — both read 3, both write 4, and one item vanishes from the count. Nothing errors, no test catches it, because tests run one request at a time. (Raising isolation to `SERIALIZABLE` makes one transaction abort instead, which is a real fix with real costs; Module 6.5 covers that choice.)

```go
// Concurrency-safe: the read and the write are one statement,
// and the row lock is held by the database for the duration.
tx.Exec(`UPDATE orders SET item_count = item_count + 1 WHERE id = $1`, orderID)
```

Correct under concurrency, and still wrong in two ways worth naming here rather than in the abstract.

**It isn't idempotent.** A client that times out after the commit and retries adds two. Any at-least-once path — a queue consumer, a webhook handler, a retrying HTTP client — will eventually double-count. Deltas need an idempotency key; the alternative doesn't.

**It serializes.** Every writer for that order queues on that row. Fine for an order with four items, a throughput wall for a counter on a popular shared entity.

```go
// Idempotent: recompute from the owner, inside the same transaction.
tx.Exec(`
    UPDATE orders o
       SET item_count = (SELECT count(*) FROM order_items WHERE order_id = o.id)
     WHERE o.id = $1`, orderID)
```

Run it once or five times, the answer is the same, and it self-heals a row that had drifted. It costs a `count(*)` over the child rows on every write, which is nothing at 40 items and unacceptable at 40 million. That's the actual axis: **recompute when the aggregate is small and bounded, delta-plus-idempotency-key when it isn't.** Orders have a natural ceiling on items; a global event counter doesn't.

And the four lines that make the column trustworthy:

```sql
SELECT o.id, o.item_count, count(i.id) AS actual
  FROM orders o
  LEFT JOIN order_items i ON i.order_id = o.id
 GROUP BY o.id, o.item_count
HAVING o.item_count <> count(i.id);
```

Zero rows, nightly, on a replica. Anything else is a write path that doesn't know about the column — which is the only bug that was ever really happening. If you've never run this query, you don't have a denormalized column; you have an unverified claim.

## Further Reading

- **"A Simple Guide to Five Normal Forms in Relational Database Theory," William Kent (1983).** Four pages, no notation, and it still explains the normal forms better than most textbook chapters. Worth reading once properly so that 3NF stops being a slogan.
- **_Designing Data-Intensive Applications_, Martin Kleppmann** — chapter 2 on data models, which frames normalization as a question about where relationships live rather than a rule to follow.
- **PostgreSQL documentation:** generated columns, materialized views (including the `CONCURRENTLY` requirements), and the trigger chapter. Read the generated-columns restrictions specifically — the limits are what make the guarantee worth having.
- **_Developing Time-Oriented Database Applications in SQL_, Richard Snodgrass** (freely available from the author). The serious treatment of the snapshot species: valid time versus transaction time, and how to model facts that change without lying about the past.
- **Firestore/Datastore documentation on distributed counters.** The clearest short statement of the hot-row contention problem and the sharded-counter answer, with the read-cost trade made explicit.
- **Martin Fowler's bliki entry on DDD Aggregate.** The structural-denormalization question stated as a modeling one: what has to change together, and what merely tends to be read together.

A **TypeScript** sibling would reveal something Go can't. The snapshot-versus-cache distinction that generated two opposite bug reports is, in a structurally typed language, enforceable at compile time: a branded `Snapshot<T>` whose fields are `readonly` and whose constructor is the only writer makes "sync the invoice address from the customer record" a type error rather than a code review someone has to be awake for. The same trick can make a cached column unreadable except through a function that also knows how to recompute it. That's a genuinely different answer to the problem — moving the obligation from discipline into the type system — and it's only available where the types survive into the code the developer reads. Not yet written.

---

The habit to carry: for every column in a schema, you should be able to answer **who owns this value, and what happens if a write path forgets about it.** Snapshots answer trivially — nobody owns it, nothing happens, it's history. Normalized columns answer trivially — the table owns it, there's nowhere else to forget. It's only the third category, the copies, where the answer takes thought, and the schemas that stay correct for years are the ones where somebody thought about it before adding the column rather than after the fourth ticket.
