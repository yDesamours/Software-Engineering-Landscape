# Indexing Strategies

_Module 6.2b — Database Design & Data Management_

## The Problem

An orders table, 200 million rows. The page is the merchant dashboard: *this merchant's pending orders, newest first, fifty per page.*

```sql
SELECT * FROM orders
 WHERE merchant_id = 7 AND status = 'pending'
 ORDER BY placed_at DESC
 LIMIT 50;
```

It takes 2.4 seconds. Everyone knows the fix.

**Attempt 1.** `CREATE INDEX ON orders(status)`. No change. The plan still shows a sequential scan, and the index is simply ignored. Forty percent of orders are `pending`, and reading 80 million random rows through an index is slower than reading the whole table in order. The index isn't broken; it's being correctly declined.

**Attempt 2.** `CREATE INDEX ON orders(merchant_id)`. Down to 180 ms. Better — but the plan shows 84,000 rows read to return 50. Every one of this merchant's orders is fetched, all of them are sorted by `placed_at`, and then 83,950 are thrown away.

**Attempt 3.** `CREATE INDEX ON orders(merchant_id, status, placed_at DESC)`. 0.4 ms, 50 rows read. The database walks straight to the merchant's pending orders, which are already in the right order, and stops after fifty.

Same three columns in all three attempts. A factor of 6,000 between the first and the last, decided entirely by which columns are in the index and in what order.

Now run the other half of the story forward. That was one query; there are thirty on this table. Two years later:

- `orders` has 11 indexes. Their combined size is larger than the table.
- Bulk import throughput has roughly halved, gradually, with no code change anyone can point to.
- Four of the indexes are prefixes of other indexes and answer nothing the longer ones don't.
- Two have never been used by any query in the last ninety days.
- Nobody deletes any of them, because nobody can prove which one some quarterly report depends on.

Both halves are the same missing idea. An index is not a setting that makes a table faster. **It's a second, ordered copy of part of your data, that the database maintains on every single write** — and everything in this article follows from taking that literally.

## What It Is

An index is a separate data structure, kept sorted by the columns you name, that lets the database find matching rows without examining all of them. In a relational store it's almost always a B-tree (the mechanics of B-trees versus LSM trees are in 6.1).

The framing that makes the trade-offs derivable: 6.2a spent an article on copies of data that need an owner, an update path, and a reconciliation job. **An index is the one copy you don't have to maintain.** The database keeps it correct for you, transactionally, with no drift and no possibility of a write path forgetting. You pay for that guarantee in write amplification and storage rather than in vigilance, which is an excellent trade — but it is a payment, and it recurs on every write for as long as the index exists.

Two neighbours worth separating now:

**Constraints versus indexes.** A `UNIQUE` constraint and a `PRIMARY KEY` are enforced *using* an index, which is why they speed up lookups as a side effect. The reverse doesn't hold: a plain index enforces nothing. If uniqueness matters, declare the constraint rather than creating a unique index and hoping — the constraint is documentation the database enforces.

**Clustered versus secondary.** In MySQL's InnoDB, the table *is* the primary-key B-tree, and every secondary index stores the primary key rather than a row location — so a secondary index lookup costs two tree descents, and a fat primary key makes every secondary index fat. In Postgres, the table is a heap and all indexes are equal, pointing at physical row locations. This difference changes how you choose primary keys, and it's the largest single behavioural divergence between the two engines.

## Recognizing the Problem

You need an index (or a better one):

- The plan for a hot query says `Seq Scan` on a large table.
- `EXPLAIN ANALYZE` shows `rows removed by filter` in the tens of thousands.
- A query with `ORDER BY … LIMIT 20` reads six figures of rows.
- Deleting one parent row takes seconds, because the foreign key column on the child table is unindexed.
- Latency on a query grew smoothly with the table, with no code change — the classic signature of a scan.

Your index exists and isn't helping:

- The plan doesn't mention it at all.
- It's used, but `rows` in the plan is orders of magnitude larger than what's returned.
- It's used for the filter and there's still a `Sort` node above it.
- The column is wrapped in a function or a cast in the `WHERE` clause.
- The filter is `LIKE '%term%'`, which no B-tree can serve — a leading wildcard means the sort order is useless.

You have too many:

- Writes are slower than reads on a table that's mostly written.
- `pg_stat_user_indexes` shows indexes with `idx_scan = 0` after a full business cycle.
- Two indexes share a leading column and one is a strict prefix of the other.
- The index set is larger than the table and none of it fits in cache.

## How It Works

### Why a correct index gets ignored

The planner is doing arithmetic, not obeying instructions. An index scan finds matching entries cheaply, but each entry then requires fetching the actual row — a random read. A sequential scan reads everything, in order, at the disk's best speed, and modern storage plus read-ahead makes sequential throughput enormous.

```
   fraction of the table matched
   0%                        ~5–10%                        100%
   │                            │                             │
   │◀── index scan wins ───────▶│◀──── sequential scan wins ──▶│
        (few random reads)           (why read 80M rows one
                                      at a time when you can
                                      read them all in order?)
```

The crossover point is fuzzy and depends on row width, caching, and storage, but the shape is the thing to internalize: **an index only helps when it eliminates most of the table.** This is *selectivity*, and it's why the index on `status` did nothing. A column with three roughly equal values can never be selective on its own, no matter how large the table gets.

Two consequences worth carrying:

- If the planner won't use an index you're sure about, check the estimated row count in `EXPLAIN` against reality first. A bad estimate — stale statistics, a correlation the planner can't see, a parameter value far from typical — is the usual cause, and the fix is statistics, not the index.
- A low-cardinality column is still useful *inside* a composite index, and it can be very useful in a partial index. It's just useless alone.

### Composite indexes and why order decides everything

An index on `(merchant_id, status, placed_at DESC)` is sorted by all three, in that order:

```
  (7, paid,    2026-03-02)
  (7, paid,    2026-03-01)
  (7, pending, 2026-03-04)   ← WHERE merchant_id=7 AND status='pending'
  (7, pending, 2026-03-03)     lands exactly here, and walks downward
  (7, pending, 2026-03-01)     through rows already in the right order
  (8, cancel,  2026-02-27)
  (8, paid,    2026-03-04)
  …
```

From this picture the rules stop being things to memorize:

- **Leftmost prefix.** The index serves `merchant_id`, or `merchant_id + status`, or all three. It cannot serve `status` alone, because `pending` rows are scattered through the entire index in merchant order.
- **Equality first, then range or sort.** Once a column is used for a *range* (`placed_at > …`), everything after it in the index is no longer in a usable order. So: columns compared with `=` go first, then the one column you range or sort on.
- **The sort comes free, or it doesn't come at all.** Matching rows are already ordered by `placed_at DESC`, so `ORDER BY placed_at DESC LIMIT 50` reads exactly 50 entries and stops. Get the direction wrong and the database must read all matches and sort them — which is attempt 2, and it's the difference between 50 rows and 84,000.
- **Order by selectivity only after the above.** Among several equality columns, the more selective one first is a mild win. It is far less important than getting equality-before-range right, and putting a low-cardinality column first is fine if that's what the queries need.

A composite index also serves as every one of its prefixes, which is where those four redundant indexes came from: once `(merchant_id, status, placed_at)` exists, a separate index on `(merchant_id)` earns nothing and costs a write on every insert.

### Getting the row without fetching the row

An index entry holds the indexed columns plus a pointer. If the query needs a column the index doesn't have, the database must go fetch the row from the table. When the index happens to contain *everything* the query needs, that fetch disappears — an **index-only scan**, often several times faster.

That's what `INCLUDE` is for: extra columns carried in the index leaves for the sake of coverage, without participating in the sort order or in uniqueness.

```sql
CREATE INDEX ON orders (merchant_id, status, placed_at DESC)
       INCLUDE (total_cents, customer_name);
```

One caveat specific to Postgres: it can't tell from the index alone whether a row is visible to your transaction, so it consults the visibility map. On a table with heavy recent write activity and lazy autovacuum, "index-only" scans quietly go back to fetching rows. If an index-only scan is load-bearing, vacuum behaviour on that table becomes load-bearing too.

### Indexing less on purpose

**Partial indexes** cover a subset of rows:

```sql
CREATE INDEX ON orders (merchant_id, placed_at DESC) WHERE status = 'pending';
```

If 0.3% of orders are pending, this index is 0.3% of the size, stays in memory, and — the part that matters more — **is only written when a pending row changes.** Rows that are inserted as `paid` never touch it. This is the highest-leverage index type most teams never reach for, and it fits the extremely common shape where a small, hot, short-lived subset is queried constantly and a huge cold archive never is.

**Expression indexes** index a computed value:

```sql
CREATE INDEX ON users (lower(email));
```

Necessary because `WHERE lower(email) = $1` cannot use an index on `email` — the wrapped column has an unknown order. The general rule is that any function or cast applied to the column in the `WHERE` clause disqualifies a plain index on it. This is also how implicit casts silently kill performance: comparing a `bigint` column to a string parameter forces a conversion, and the index goes unused with no warning anywhere.

### Other index types, briefly

- **GIN** — inverted index for values that contain multiple searchable items: `jsonb` keys, array elements, full-text lexemes, trigrams. This is what makes `LIKE '%term%'` indexable (via `pg_trgm`), and what makes `WHERE data @> '{"k":"v"}'` fast.
- **GiST** — geometric and range data: overlapping ranges, nearest-neighbour, PostGIS.
- **BRIN** — stores only min/max per block range. Microscopic (megabytes for a terabyte table), and useful only when the physical row order correlates with the column — which is exactly true for append-only timestamped data. Pairs naturally with partitioning (6.2c).
- **Hash** — equality only, no ordering, rarely worth choosing over a B-tree.
- **Vector/ANN** — approximate nearest neighbour, a different question entirely (Module 39).

## When It's Appropriate

- **A frequent query filters on a selective combination.** The clearest case, and the one where you should reach for a composite matching the access shape rather than single-column indexes and hope.
- **Foreign key columns on the child table.** Postgres does not create these for you. Without one, deleting or updating a parent row scans the entire child table while holding locks, and `ON DELETE CASCADE` turns a small delete into an outage. This is the most commonly missing index in real schemas.
- **Sort and pagination keys.** If a list is paginated, the index must match the `ORDER BY` exactly, direction included — see *Implementation*.
- **Uniqueness.** Declared as a constraint, indexed as a consequence.
- **A skewed hot predicate** — partial index, as above.
- **A hot read path that needs three columns** — covering index, when the fetch is measurably the cost.

The numbers that justify one look like: *this query runs 4,000 times a minute, reads 200,000 rows, and returns 50.* Not: *this query feels slow.*

## When It's Unnecessary or Overkill

- **Small tables.** Below a few thousand rows, a sequential scan of a cached table is faster than anything else, and the planner knows it.
- **Low-cardinality columns alone.** Booleans, three-value status columns. Use them inside a composite or as a partial index predicate.
- **Queries that run twice a day.** A report that takes four seconds at 03:00 does not need an index that taxes ten million writes.
- **"Just in case" indexes on every column.** Each one is permanent write cost against a hypothetical query.
- **Write-heavy tables read only by analytics.** The index belongs on the replica or the derived store (6.1), not on the table taking the writes.
- **Before reading the plan.** If the endpoint issues 600 queries, indexing one of them changes nothing you'll notice (6.4).
- **Redundant prefixes.** Before adding index number N, check whether an existing index already starts with those columns.

## Trade-offs

**Write amplification is the headline cost.**

```
INSERT one row into a table with 11 indexes:

  heap      1 row written
  indexes  11 separate B-trees, each needing a random write,
           each possibly splitting a page
  WAL       all of the above, logged
```

Reads got faster; every insert, update, and delete got slower, permanently, and the slowdown is spread across the whole application rather than attached to the feature that asked for the index.

**Updates are worse than they look.** When an update changes a row, Postgres can sometimes avoid touching indexes entirely (a HOT update) — but only if no indexed column changed *and* there's free space on the same page. So indexing a frequently-updated column costs far more than indexing a static one, and a table with no slack (`fillfactor` 100) loses the optimization exactly when it's needed most.

**Indexes compete for memory with your data.** What matters isn't table size, it's whether the working set fits in the buffer cache. Adding six indexes to a hot table can evict the data those indexes point to, and the net effect is slower.

**Build cost is a production event.** `CREATE INDEX` takes a lock that blocks writes for the duration — minutes to hours on a large table. `CREATE INDEX CONCURRENTLY` avoids that, takes roughly twice as long, cannot run inside a transaction, and leaves behind an `INVALID` index if it fails, which then has to be dropped and retried. This belongs in the migration discussion (6.3), but it's why "just add an index" is not a five-minute task at scale.

**Unique indexes serialize conflicting writers,** and any index on a monotonically increasing column concentrates every insert on the same right-edge pages, which becomes lock contention at high write rates.

**Bloat and maintenance.** Indexes accumulate dead entries and grow; `REINDEX CONCURRENTLY` exists and needs to be scheduled by somebody.

**And the organizational cost, which is the one that produced the eleven.** Adding an index is a visible fix for a visible problem. Removing one is invisible work with a small chance of causing an incident. That asymmetry is why index sets only ever grow unless someone deliberately runs the usage query.

## Alternatives

- **Fix the query.** A rewrite that removes a function from the `WHERE` clause, or eliminates a fan-out join (6.2a), or replaces `OFFSET` with keyset pagination, frequently beats any index.
- **Fix the N+1.** Module 6.4. Vastly more common than a missing index as the cause of a slow endpoint.
- **Denormalize so the value becomes indexable.** You cannot index an aggregate in another table; materializing it (6.2a) is what makes an index on it possible.
- **Materialized views,** which carry their own indexes and shift the cost to a refresh schedule.
- **Partitioning** (6.2c). Partition pruning eliminates entire chunks of the table before any index is consulted, and smaller per-partition indexes are cheaper to maintain.
- **A replica** for the reporting queries, so their index needs don't tax the write path.
- **A different store** (6.1) when the required access shape isn't a B-tree question at all — relevance ranking, or aggregating four columns of two billion rows.
- **Nothing.** A four-second query twice a day is not a problem; it's a line in a log.

## How to Achieve It

1. **Get the real plan for the real query.** `EXPLAIN (ANALYZE, BUFFERS)` with production-like parameter values. The two things to read first are estimated-versus-actual row counts (a large gap means the planner is working from bad information, and no index fixes that) and the buffer counts (which tell you what was actually read).
2. **Write down the access shape in one line:** which columns are equality-filtered, which one is ranged or sorted, which columns are returned. If you can't write that line, you're not ready to create the index.
3. **Build the composite in that order** — equality columns, then the range/sort column with its direction, then `INCLUDE` for coverage if the fetch is measurably costing you.
4. **Consider a partial index** if the queried subset is a small and stable fraction of the rows.
5. **Create it `CONCURRENTLY`**, then confirm from the plan that it's actually used. An index that exists and isn't used is pure cost.
6. **Measure the write side afterwards,** not just the read side. Insert latency and replication lag are where the bill shows up.
7. **Once per quarter, list the indexes with zero scans** and drop them — checking replicas too, since a read-replica-only query won't appear in the primary's statistics, and giving a long enough window to include monthly and quarterly jobs.

## Implementation

TypeScript, because the single most common way an application defeats a perfectly good index is pagination, and that's application code rather than schema.

The index from the opening is `(merchant_id, status, placed_at DESC)`. Here's the standard way to render page N:

```ts
const rows = await sql`
  SELECT * FROM orders
   WHERE merchant_id = ${merchantId} AND status = 'pending'
   ORDER BY placed_at DESC
   LIMIT 50 OFFSET ${page * 50}`;
```

The index is used. The query is still wrong in two ways.

**`OFFSET` reads and discards.** Page 400 means the database walks 20,000 index entries, fetches 20,000 rows, throws away 20,000 rows, and returns 50. Page 1 is 0.4 ms and page 400 is 800 ms, so the endpoint's latency depends on a number in the URL — which is also a small denial-of-service surface, since the offset is usually user-controlled.

**It silently skips rows.** If an order is inserted between the user's request for page 3 and page 4, everything shifts down by one and one row is never shown. If one is deleted, a row appears twice. Nobody reports this as a bug; they report that the export is missing an order.

The fix is to seek instead of count — remember where the last page ended and start there:

```ts
const rows = await sql`
  SELECT * FROM orders
   WHERE merchant_id = ${merchantId} AND status = 'pending'
     AND (placed_at, id) < (${cursor.placedAt}, ${cursor.id})
   ORDER BY placed_at DESC, id DESC
   LIMIT 50`;
```

Every page costs the same 50 index entries, at any depth, and concurrent inserts can't shift the window. Three details do the work:

- **`(placed_at, id) < (…, …)` is a row comparison, not two conditions.** Writing `placed_at <= $1 AND id < $2` is the classic bug in this pattern: it drops every row from an earlier timestamp whose id happens to be larger. The tuple form compares lexicographically, which is exactly how the index is sorted.
- **The tiebreaker is required.** `placed_at` isn't unique, so without `id` a page boundary landing inside a group of identical timestamps loses or repeats rows. The cursor must define a total order.
- **The `ORDER BY` must match the index exactly, direction included** — and so the index needs `id` on the end too: `(merchant_id, status, placed_at DESC, id DESC)`. A mismatch in direction on the tiebreaker alone reintroduces a sort over the whole result set, which is the entire cost you were avoiding.

The trade is real and worth stating: keyset pagination cannot jump to page 50, and it can't show "page 12 of 400" without a separate count. For infinite scroll, feeds, exports, and API cursors — which is most pagination — that's no loss. For an admin table with numbered page links over a few thousand rows, `OFFSET` is fine and simpler.

## Further Reading

- **"Use The Index, Luke!" (use-the-index-luke.com), Markus Winand.** The free web version of _SQL Performance Explained_, and the best single resource on this topic in any format. The chapters on composite column order and on "why is my index not used" are the long form of two sections above.
- **PostgreSQL documentation, the Indexes chapter** — index types, multicolumn indexes, partial and expression indexes, index-only scans and the visibility map, and `CREATE INDEX CONCURRENTLY`. Also "Using EXPLAIN" in the Performance Tips chapter, which is short and repays reading properly once.
- **MySQL Reference Manual, "Optimization and Indexes" and the InnoDB clustered index section** — worth reading even if you use Postgres, because the clustered-index model changes primary-key choice in ways that don't transfer.
- **`pg_stat_user_indexes` and `pg_stat_statements`** in the Postgres monitoring documentation. The first tells you which indexes nobody uses; the second tells you which queries to index for. Most teams have neither answer written down.
- **"Pagination Done the Right Way," Markus Winand** — the keyset technique with the failure cases spelled out.
- **depesz's "Explaining the unexplainable" series** — a plan-node-by-plan-node walkthrough, which is the missing manual for `EXPLAIN` output.

A **Java** sibling would expose something this article can only gesture at. Spring Data's `Pageable` makes `OFFSET` the path of least resistance — it's the parameter type the framework hands you — and returning a `Page` rather than a `Slice` issues a second `COUNT(*)` over the entire filtered set on every single request, which on a large table is frequently more expensive than the page query it accompanies. Neither cost appears anywhere in the repository interface. The interesting content is how to express a keyset cursor through Spring Data without abandoning it, and what JPA's implicit fetch and ordering behaviour does to index usage generally. Not yet written.

---

The habit worth carrying out of this: **before creating an index, state the access shape in one sentence** — these columns equal, this one ranged or sorted, these returned. If the sentence is hard to write, the index will be wrong, and you'll find out by adding a second one.

And once a quarter, ask the opposite question, because nobody ever asks it on their own: which of these indexes has nothing read from it, and what is it costing on every write?
