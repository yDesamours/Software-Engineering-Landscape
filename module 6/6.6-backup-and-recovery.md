# Backup and Recovery

_Module 6.6 — Database Design & Data Management_

## The Problem

14:12 on a Thursday. A cleanup script intended for a staging database runs against production:

```sql
DELETE FROM subscriptions WHERE ended_at IS NOT NULL;
```

The `WHERE` clause is correct and the target database is not. 1.4 million rows, including every active subscription whose previous term had ended — which is most of them. It commits.

Someone notices at 14:31. Here is the next four hours, and every step of it is a discovery that should have been made earlier.

**"We have backups."** A nightly logical dump at 02:00. Restoring it loses twelve hours of every customer's work, not just the deleted rows. Nobody had ever stated how much data the business was willing to lose, so nobody had noticed that the answer implied by the backup schedule was "up to a day."

**"We have a replica."** The replica applied the same `DELETE` forty milliseconds later, faithfully and correctly. A replica is a copy of your mistakes with excellent latency.

**"The managed service takes snapshots."** It does, every six hours, and it supports point-in-time recovery. This is the thing that saves the day, and nobody on the call knows the procedure, because the procedure has never been run.

**The restore takes three hours and forty minutes.** 2.1 TB to provision, copy, and replay. Nobody had measured this, so the answer given to the CEO at 14:45 — "maybe half an hour?" — was invented.

**And the restore goes to a new instance.** Which raises the question nobody has thought about: the last ninety minutes contain real customer writes that have nothing to do with the incident. Cutting over to the restored copy discards them. Keeping the live database means extracting 1.4 million rows from the restored copy and merging them back — against live sequences, live foreign keys, and rows that have since been recreated by customers. There is no script for that. It gets written at 17:00, by a tired person.

**Meanwhile everything else is at "now."** The search index still contains the deleted subscriptions. Object storage has files for them. The billing provider has its own opinion. Restoring the database to 14:11 does not restore anything else to 14:11.

Two numbers were never written down, and one procedure was never run. That's the entire incident.

And there's a quieter version of the same failure, which is worse because it produces no incident until it produces a catastrophe. The nightly dump has been *succeeding* for fourteen months — exit code 0, file present, monitoring green. It has also been writing to a volume that fills at around 60%, so every file since March is truncated. **A backup job's exit code tells you that a file was written. It tells you nothing about whether a database can be recovered from it.**

## What It Is

Two numbers define the design, and both are business decisions rather than technical ones:

- **RPO — Recovery Point Objective.** How much data you can afford to lose, expressed as time. A nightly backup is an RPO of 24 hours. Continuous archiving is an RPO of seconds.
- **RTO — Recovery Time Objective.** How long you can afford to be down before you're recovered. This is not the restore command's runtime; it's detection, decision, restore, verification, and cutover.

Everything else follows from those two. The mechanisms:

- **Logical backup** (`pg_dump`, `mysqldump`) — a stream of statements that recreates the data. Portable across versions and platforms, selective (one table, one schema, one tenant), and slow to restore at scale because it rebuilds indexes and revalidates constraints. Exactly one point in time.
- **Physical backup** (`pg_basebackup`, pgBackRest, volume snapshots) — the actual files. Fast, whole-cluster, tied to the engine version and often the platform, and the necessary foundation for point-in-time recovery.
- **Continuous archiving** — shipping the write-ahead log as it's produced. This is what turns "the state at 02:00" into "the state at any instant since 02:00," and it's what takes RPO from hours to seconds.
- **Point-in-time recovery (PITR)** — restore a base backup, then replay the log up to a chosen timestamp, transaction id, or named restore point.

Three things that get mistaken for backups and are not:

**Replication is not backup.** It protects against a machine, a disk, or an availability zone failing. It replicates logical damage — a bad `DELETE`, a bad migration, a corrupting application bug — perfectly and immediately. Every incident in this article's opening survives replication untouched.

**A snapshot you've never restored is not a backup.** It's a file with a promising name.

**High availability is not disaster recovery.** HA answers "a machine died"; DR answers "the data is wrong, or the region is gone." They use different mechanisms and are frequently conflated in planning documents.

## Recognizing the Problem

- You cannot state your RPO and RTO as numbers.
- Nobody has restored a production backup this quarter. Or ever.
- Monitoring alerts when the backup job fails, and would say nothing if the job stopped running entirely, or if the file was 4 KB.
- Backups live in the same cloud account, with the same credentials, as the database. One compromised key, or one wrong command, destroys both.
- The restore procedure is a wiki page rather than a script, and its author is the person who'd also be running the incident.
- "We're on a managed service, it's handled" — with no one able to say what the retention window is.
- There is no way to restore one tenant, or one table, without restoring everything.
- After a restore, your search index, object storage, and cache would disagree with the database, and there's no plan for that.
- Retention is "forever," or unknown, and nobody has checked it against either the bill or the legal obligation.

## How It Works

### Match the mechanism to the threat

| Threat | Replica | Snapshot / base backup | PITR | Offsite immutable copy |
|---|---|---|---|---|
| Disk or instance failure | ✅ | ✅ | ✅ | ✅ |
| Availability zone loss | ✅ | ✅ | ✅ | ✅ |
| Region loss | only if cross-region | if copied | if copied | ✅ |
| Bad `DELETE` / bad migration | ❌ | ✅ (to last snapshot) | ✅ (to the second before) | ✅ |
| Slow logical corruption from a bug | ❌ | only if retained long enough | only if retained long enough | ✅ |
| Credential compromise / ransomware | ❌ | ❌ if same account | ❌ if same account | ✅ |

Reading down the "replica" column is the fastest way to see why most teams' actual protection is narrower than they believe. Reading across the bottom row is why the offsite copy needs *different credentials*, not merely a different region.

### PITR, and the knob that controls RTO

```
   base backup        WAL  WAL  WAL  WAL  WAL  WAL  WAL  WAL   →  now
   (Sun 02:00) ────────┴────┴────┴────┴────┴────┴────┴────┴──
                                            ↑
                                    recover to 14:11:58
                                    (one second before the DELETE)

   RPO = how far behind the archive is   (seconds, if archiving continuously)
   RTO = copy the base backup + replay every WAL segment since it
```

The second line is the part people miss. **Replay time grows with the distance from the last base backup.** A weekly base backup with six days of log to replay can take longer to recover than the database took to produce the data. Taking base backups more often is the direct lever on RTO, and it's a cost decision: more storage, more I/O, shorter recovery.

Finding the recovery target is its own small problem. "One second before the bad statement" requires knowing when the bad statement ran, which means the audit log or the query log (Module 19) is part of your recovery capability. Recovering to a transaction id is more precise than a timestamp when you have it.

### The restore is the product

A restore isn't finished when the database accepts connections. It's finished when the application is serving correct data, which includes: statistics regenerated (or the first hour has terrible plans — 6.4b), caches cold and repopulating, connection strings or DNS repointed, and someone having verified that the data is actually right.

Two platform-specific traps worth knowing:

- **Cloud volume snapshots restore "instantly" and hydrate lazily.** The volume is available in minutes and its blocks are fetched from object storage on first read, so the database is up and unusably slow for hours. If your RTO assumed the fast number, your RTO is wrong.
- **Logical restores rebuild indexes and validate constraints.** On a large database this dominates the restore time, and it's the reason logical dumps are a poor primary strategy past a few hundred gigabytes — while remaining the best tool for restoring *one table*.

### Partial restore is a different capability

"Restore the whole cluster to 14:11" and "give this one customer their data back" are not the same operation, and the second one is what customers actually ask for.

The realistic path is always: restore the full backup to a scratch instance, then extract what you need and merge it into the live database. That merge is where the difficulty lives — foreign key ordering, sequences that have moved on, rows the customer has recreated in the meantime, and the question of what to do when a restored row conflicts with a current one. None of that is hard; all of it takes hours to work out under pressure, and about ninety minutes to work out in advance.

If your contracts promise per-tenant recovery — and enterprise contracts often do — that script needs to exist and to have been run once against real data.

### There is no global point in time

Your database, your object storage, your search index, your cache, and your payment provider each have their own timeline. Restoring one to 14:11 leaves the others at 17:30.

The rule that makes this tractable is the one from 6.1 and 6.2a: **exactly one system of record per fact, and every derived store rebuildable from it.** Then recovery has a defined shape — restore the system of record, rebuild everything downstream — and the rebuild script is a thing you already have, because you wrote it when you added the derived store. If a derived store turns out to hold something authoritative, discovering that during a restore is the worst possible moment.

External systems can't be restored at all, which makes reconciliation — comparing your state against the provider's and repairing the difference — part of the recovery procedure rather than an afterthought.

### Verification is the only evidence

Backups are a claim about the future. The only evidence for the claim is a restore that happened.

The verifiable properties, in increasing order of usefulness:

- The file exists and is the expected size. Catches the truncated dump.
- The backup is internally consistent (`pg_verifybackup`, checksum validation). Catches storage corruption.
- A restore completes on a scratch instance. Catches almost everything else.
- The restored database answers semantic questions correctly — known row counts within tolerance, a specific record present, a smoke query returning the expected value. Catches the backup that restores fine and is missing large objects, or a schema, or the last four hours.

And the byproduct that matters most: **the elapsed time of that automated restore is your real RTO.** Not an estimate. Publish it, watch it grow with the database, and let it be the thing that triggers "we need more frequent base backups."

## When It's Appropriate

Calibrate to the two numbers, and price each tier honestly:

- **Internal tool, RPO 24h, RTO a working day.** A nightly logical dump to object storage in a different account, with a monthly restore test. Genuinely sufficient, and cheap enough that having less is just carelessness.
- **SaaS with paying customers, RPO minutes, RTO about an hour.** Managed PITR plus automated snapshots, copied cross-region, retention covering the time it takes to *notice* corruption — which for a subtle bug is weeks, not days — plus a rehearsed runbook and a per-tenant extraction script.
- **Financial or regulated, RPO near zero.** Synchronous replication so a commit isn't acknowledged until a second node has it, plus everything above, plus a standby in another region, plus drills with an audit trail.
- **Protecting specifically against human error.** A delayed replica — a standby deliberately kept an hour behind — is the cheapest, fastest recovery available for exactly the opening scenario: the bad statement hasn't been applied there yet, and promoting it takes minutes rather than hours.

## When It's Unnecessary or Overkill

- **Cross-region synchronous replication for an internal admin tool.** You've paid latency on every write for a threat nobody priced.
- **Building your own backup tooling** when a managed service or a mature tool (pgBackRest, WAL-G, Barman, XtraBackup) does it correctly. This is not the place for original work.
- **Backing up derived data.** Search indexes, caches, and materialized projections should be rebuilt, not restored. Backing them up costs storage and creates the restore-time inconsistency you were trying to avoid.
- **Seven years of nightly full backups "just in case."** That's a storage bill and, once personal data is involved, a compliance liability with a deletion obligation attached (Module 34).
- **A three-region hot standby when the promise is a 24-hour RTO.**
- **Second-level RPO for data that's reconstructible** from an upstream system that still has it.

## Trade-offs

**Backups load the primary.** A logical dump holds a long transaction — blocking vacuum and pinning a snapshot for its whole duration (6.3b) — and physical backups compete for I/O. Take them from a replica where you can.

**Continuous archiving creates a new outage mode.** If the archive destination becomes unwritable, the primary cannot recycle write-ahead log segments and its disk fills, which stops the database. The failure of your backup system becomes the failure of your database. Archive lag needs an alert, and it's the least-loved alert in most systems until the day it matters.

**RPO near zero costs write latency.** Synchronous commit means every transaction waits for a second node. That's the correct trade for a ledger and a poor one for an activity feed, which is why RPO should be set per system rather than globally.

**Shorter RTO costs money continuously** — more frequent base backups, warm standbys, provisioned capacity waiting to be used.

**Restore testing costs real time and real money,** every week, forever. Not testing costs everything, once.

**Immutable backups collide with deletion obligations.** Object-lock retention is what protects you from ransomware and from a compromised administrator, and it also means a GDPR erasure request cannot be honoured inside the backups. The usual resolution is a documented policy — erasure applies to live systems, backups expire on a stated schedule, and restored data is re-scrubbed — and it is a genuine tension rather than a solved problem (Module 34).

**Encryption adds a dependency you must also survive.** A backup you cannot decrypt is not a backup. The key has to be recoverable under the same disaster that made you reach for the data, which means the key management system is in scope for your DR plan.

## Alternatives

- **Managed point-in-time recovery** (RDS, Aurora, Cloud SQL, and equivalents). For most teams this is the right answer and the correct amount of original engineering is zero. Know your retention window and your actual restore time; both are configurable, and both defaults are frequently wrong for the business.
- **A delayed replica.** Underused, and the best single defence against operator error.
- **Logical replication into a separate account or cluster**, which gives an independent copy with independent credentials and can lag deliberately.
- **Soft deletes and append-only design.** The cheapest recovery is the one where nothing was destroyed — a `deleted_at` column turns the opening incident into an `UPDATE` that takes four seconds. Not universally applicable, and enormously effective where it is.
- **An audit log or event stream** you can replay to rebuild state (Modules 2.4 and 37), which is backup as an architectural property rather than an operational one.
- **Per-tenant export as a product feature.** Built once, it serves data portability obligations (Module 34), customer onboarding and offboarding, *and* the partial restore path.

## How to Achieve It

1. **Write down RPO and RTO per system,** agreed with someone who owns the budget. This is the step that's skipped, and every subsequent decision is unjustifiable without it.
2. **Map threats to mechanisms** using the table above, and state explicitly in writing what your replicas do not cover.
3. **Use the managed or mature tool.** Configure retention to cover how long it takes to *notice* a subtle problem, not how long it takes to notice an outage.
4. **Put one copy in a different account and region, with object lock and separate credentials.**
5. **Automate a weekly restore to a scratch instance,** with semantic assertions, and record the elapsed time. That number is your RTO.
6. **Alert on backup age and restore-test age,** not on job exit codes.
7. **Turn the runbook into a script, and rehearse it with someone who didn't write it.** That rehearsal tests the documentation, which is the part that actually fails.
8. **Decide the cross-store story in advance:** which system is authoritative, what gets rebuilt, and where the rebuild script lives.
9. **Write the per-tenant extraction path before a customer asks for it.**
10. **Review retention against cost and against law,** on a schedule.

## Implementation

The code here is deliberately thin, because the substance of this topic is procedure rather than programming. Two pieces are worth writing yourself.

The first is the verification job — restore, assert, and publish the duration:

```ts
async function verifyLatestBackup() {
  const started = Date.now();

  const instance = await restoreLatestSnapshotToScratch();   // provider API
  const sql = connect(instance);

  // Semantic assertions. "The server started" proves almost nothing.
  const [{ n }] = await sql`SELECT count(*)::int AS n FROM subscriptions`;
  assert(n > expectedMin, `subscriptions: ${n}, expected > ${expectedMin}`);

  const [{ ok }] = await sql`
    SELECT count(*) = 1 AS ok FROM tenants WHERE id = ${canaryTenantId}`;
  assert(ok, 'canary tenant missing from restored backup');

  const [{ latest }] = await sql`SELECT max(created_at) AS latest FROM events`;
  assert(age(latest) < RPO_TARGET, `restored data is ${age(latest)} old`);

  await drop(instance);

  metrics.gauge('backup.restore_seconds', (Date.now() - started) / 1000);
  metrics.gauge('backup.verified_at', Date.now());
}
```

Three things that make this worth more than it looks.

**The assertions are semantic.** A restore that completes and yields a database missing its large objects, or one schema, or the last four hours, passes every structural check. A canary row and a freshness check catch it.

**The duration is recorded as a metric, not a log line.** Watch it grow. When it crosses the RTO you promised, that's an alert about a commitment, not a performance regression.

**Alert on `verified_at` age.** A verification job that stops running produces no failures at all, which is indistinguishable from success in any monitoring that only watches for errors. The same logic applies to the backup itself: alert on the age of the newest backup, never on the exit code of the job that was supposed to create it.

The second piece is the extraction path, which you want to have written calmly:

```sql
-- On the scratch instance restored to just before the incident.
\copy (SELECT * FROM subscriptions WHERE tenant_id = :tenant) TO 'subs.csv' CSV

-- On live, into a staging table first — never straight into the real one.
CREATE TEMP TABLE subs_restore (LIKE subscriptions INCLUDING ALL);
\copy subs_restore FROM 'subs.csv' CSV

INSERT INTO subscriptions
SELECT * FROM subs_restore
ON CONFLICT (id) DO NOTHING;          -- the customer may have recreated some
```

`ON CONFLICT DO NOTHING` encodes a decision that has to be made consciously: current data wins over restored data. The alternative — restored wins — is occasionally correct and always needs to be someone's explicit choice. Parent tables go before children, and sequences need setting forward afterwards if the restored rows carry ids above the current value.

## Further Reading

- **PostgreSQL documentation, chapter 26, "Backup and Restore."** All three approaches — SQL dump, file system level, continuous archiving — with the PITR configuration and recovery target options stated precisely. Also `pg_verifybackup`, the data checksums setting, and the `amcheck` extension for detecting corruption before it reaches a backup.
- **pgBackRest, WAL-G, or Barman documentation** if you're self-hosting, and Percona XtraBackup for MySQL. Read the restore chapter first; that's the one you'll need under pressure.
- **_Site Reliability Engineering_ (Google), chapter 26, "Data Integrity: What You Read Is What You Write."** The strongest available argument that recovery rather than backup is the goal, with a layered model of defences and a frank account of how their own systems have failed.
- **GitLab's 2017 database incident postmortem.** An operator deleted a directory on the wrong server, and then five separate backup and replication mechanisms were each found not to work. Read it once a year.
- **Your cloud provider's documentation on snapshot restore performance and lazy hydration,** and on object lock / immutable retention. Both are directly load-bearing for the RTO and ransomware sections above and both are easy to assume rather than check.
- **Kleppmann, _Designing Data-Intensive Applications_, chapter 5.** Replication properly explained, which is the background needed to see clearly why it isn't a backup.

A **Go** sibling would be worth writing for the tenant-restore tool specifically, which is a real program rather than a script: walking the foreign-key graph to derive a safe insert order, handling cycles, streaming rather than materializing a large tenant, advancing sequences, making the whole thing resumable and idempotent so a failure halfway doesn't require starting over, and producing a reconciliation report of what was restored, skipped, and conflicted. Every team eventually writes some version of this, usually at 17:00 during an incident. Not yet written.
