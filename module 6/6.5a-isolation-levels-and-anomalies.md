# Isolation Levels and the Anomalies They Allow

_Module 6.5a — Database Design & Data Management_

## The Problem

Three transactions that are correct, atomic, durable, and produce wrong data.

### One: the balance that doesn't add up

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 7;      -- 100
-- application computes 100 - 30 = 70
UPDATE accounts SET balance = 70 WHERE id = 7;
COMMIT;
```

Two withdrawals of 30 arrive at the same moment.

```
  T1: BEGIN
  T1: SELECT balance → 100
                            T2: BEGIN
                            T2: SELECT balance → 100
  T1: UPDATE balance = 70
  T1: COMMIT
                            T2: UPDATE balance = 70
                            T2: COMMIT

  withdrawn: 60          balance: 70          errors: none
```

Both transactions committed. Both were atomic. Neither violated a constraint. Thirty pounds left the system without leaving the account.

### Two: the rule that both transactions checked

An on-call rota with one rule: at least one doctor must remain on call. The code checks before releasing:

```sql
BEGIN;
SELECT count(*) FROM doctors WHERE on_call AND shift_id = 4;   -- 2, fine
UPDATE doctors SET on_call = false WHERE id = :me;
COMMIT;
```

Two doctors click at the same time. Both read 2. Both release. Nobody is on call.

This one matters because the obvious fix for the first problem doesn't touch it. There's no lost update — the two transactions wrote *different rows*. An atomic `UPDATE … SET x = x - 1` doesn't apply. Locking the row you're writing doesn't help, because the row that made the decision wrong is someone else's. Each transaction read a state the other one invalidated, and neither has any way to notice.

### Three: the check that passed twice

```sql
SELECT 1 FROM bookings WHERE room_id = 3 AND period && '[14:00,15:00)';
-- no rows, so:
INSERT INTO bookings (room_id, period) VALUES (3, '[14:00,15:00)');
```

Two requests, both find nothing, both insert. The room is double-booked. The thing being checked for *didn't exist yet when it was checked*, which is why no row-level mechanism can catch it.

### What these have in common

All three pass every test, because tests run one transaction at a time. All three appeared only after the service ran on more than one instance. And none of them is a misuse of transactions: they are the documented, standard-conforming behaviour of the isolation level nearly every database uses by default.

The idea to discard is that a transaction is a concurrency strategy. **A transaction gives you atomicity and durability unconditionally. Isolation is a dial, and its default position permits anomalies that silently corrupt data.** The rest of this article is which anomalies, at which settings, and what to do instead.

## What It Is

ACID, stated honestly, because two of the four letters are routinely misread:

- **Atomicity** — all of the transaction's writes take effect, or none do. This is the property everyone means when they say "transaction," and it is not in question in any of the three failures above.
- **Consistency** — the odd one out. It means *your* constraints and invariants hold, which is a property of what you declared and what your application does, not something the database supplies on its own. It's in the acronym largely because the acronym needed a vowel.
- **Isolation** — how much concurrent transactions are allowed to see of each other. A dial with four settings.
- **Durability** — a committed transaction survives a crash. With caveats worth knowing: "committed" by default means written and flushed locally, which is not the same as acknowledged by a replica. On failover, transactions that were committed on the old primary and not yet replicated are gone. `synchronous_commit` is where that trade lives.

The four isolation levels, and the anomalies each permits:

| | Dirty read | Non-repeatable read | Phantom | **Lost update** | **Write skew** |
|---|---|---|---|---|---|
| Read Uncommitted | possible\* | yes | yes | yes | yes |
| **Read Committed** | no | yes | yes | **yes** | **yes** |
| Repeatable Read / Snapshot | no | no | no\** | no\** | **yes** |
| Serializable | no | no | no | no | no |

\* Postgres doesn't implement Read Uncommitted separately; it behaves as Read Committed.
\** In Postgres's snapshot-based Repeatable Read. MySQL's Repeatable Read is a different mechanism with different guarantees.

The two bolded columns are the ones that matter most and the ones the SQL standard doesn't define. The standard's taxonomy — dirty, non-repeatable, phantom — was written around a particular lock-based implementation, and it misses the failure modes that actually bite modern MVCC systems. Lost update is problem one above. Write skew is problems two and three.

Two disambiguations worth fixing now.

**Isolation is not atomicity.** Almost everyone who says "we wrapped it in a transaction" is talking about atomicity, which was never the issue. The bugs live one letter over.

**The same level name means different things on different engines.** Postgres defaults to Read Committed and implements Repeatable Read as snapshot isolation. MySQL/InnoDB defaults to Repeatable Read and enforces it with next-key locks, which prevents some phantoms the Postgres version doesn't and produces deadlocks where Postgres produces serialization errors. SQL Server's default is lock-based Read Committed, with snapshot behaviour available as an option. Portability of the *word* is not portability of the *guarantee*.

## Recognizing the Problem

- A counter, balance, or quantity drifts under load and never in tests.
- Two rows exist that shouldn't both exist: two bookings for one slot, two primary contacts, nobody on call, an inventory count below zero.
- An invariant is enforced by "check, then write" in application code.
- A report assembled from several queries in one request doesn't internally reconcile — the totals were read at different instants.
- Logs contain `could not serialize access due to concurrent update` (SQLSTATE 40001) or `deadlock detected` (40P01), and something swallows them.
- The bug appeared when you went from one instance to four, or when a retry was added, or when traffic doubled.
- Someone has written a comment that says "there's a small race here but it's unlikely."

That last one is usually accurate about the probability and wrong about the consequence.

## How It Works

### Snapshots, and when you get a new one

Under MVCC, a write doesn't overwrite a row; it creates a new version. Each transaction reads from a *snapshot* — the set of versions committed as of some instant — so readers never block writers and writers never block readers. Everything below follows from one question: **when is that snapshot taken?**

**Read Committed takes a new snapshot for every statement.** So two `SELECT`s in the same transaction can legitimately return different data, and a value you read in statement one may be obsolete by statement three. That's not a bug, it's the level's definition, and it's why problem one above is permitted: the `SELECT` and the `UPDATE` saw different worlds.

There's a subtlety in how writes behave here that catches people. If an `UPDATE` reaches a row currently being updated by another transaction, it waits for that transaction to finish, and then — rather than using its original snapshot — **re-evaluates its `WHERE` clause against the newly committed version.** So `UPDATE accounts SET balance = balance - 30 WHERE id = 7 AND balance >= 30` is genuinely safe at Read Committed, while the read-compute-write version is not. Same isolation level, same two transactions, different outcome, entirely because of where the arithmetic happened.

**Repeatable Read takes one snapshot for the whole transaction.** Every statement sees the same consistent picture, which fixes read skew and makes multi-query reports internally consistent. For writes, Postgres detects when your snapshot has been invalidated by a concurrent update to a row you're writing, and aborts you with a serialization error rather than losing the update. So lost update is prevented — but by *failing*, which means it's only prevented if the application retries.

**Serializable adds tracking of what you read.** Postgres implements Serializable Snapshot Isolation: on top of the snapshot, it records read dependencies between concurrent transactions and aborts one whenever the pattern of reads and writes could produce a result no serial ordering would. That's what catches write skew — the on-call transactions read rows the other one then wrote, forming a dependency cycle, so one is aborted.

```
   Read Committed     snapshot per statement     ← the world can change mid-transaction
   Repeatable Read    snapshot per transaction   ← your reads are stable; others' writes are invisible
   Serializable       + read dependency tracking ← your reads are also *protected*
```

The progression is: what you see, then what you saw, then what you decided based on what you saw.

### The retry loop is not optional

At Repeatable Read and Serializable, transactions are aborted *as the mechanism*. There is no version of this where you turn on a stronger level and everything simply works; the database's contract is "I will refuse the ones that would be wrong, and you will run them again."

Which means:

- The retry must restart the **entire** transaction, reads included. Reusing values read during the failed attempt reproduces exactly the anomaly the abort prevented.
- Retries must be bounded, with jittered backoff, and alert on exhaustion. Under heavy contention, immediate retries make contention worse.
- Anything non-transactional inside the transaction — an email, a payment call, a message published to a broker — will happen again. Those belong outside the transaction or in an outbox (6.1).

Teams that skip this adopt Serializable, see serialization errors surface as 500s, and revert. The retry wrapper is the prerequisite, not the follow-up.

### Isolation is not the only tool, and often not the best one

For each anomaly there's usually a cheaper answer than raising the level, because the database can enforce some invariants directly and an enforced constraint can't be raced:

| Problem | Cheapest correct fix |
|---|---|
| Lost update on one row | Do the arithmetic in SQL: `SET balance = balance - 30 WHERE balance >= 30` |
| Conditional update | Compare-and-set: put the precondition in the `WHERE` and check the affected row count |
| Duplicate by exact value | `UNIQUE` index. The database does this correctly at any isolation level |
| Overlapping ranges | Exclusion constraint: `EXCLUDE USING gist (room_id WITH =, period WITH &&)` |
| Invariant across rows, expressible as a constraint | A constraint |
| Invariant across rows, *not* expressible | Serializable, or materialize the conflict (lock a row that represents the invariant) |

Problem three in the opening is a two-line fix — the exclusion constraint — and needs no isolation change at all. Problem two isn't expressible as a constraint, and that's the case Serializable exists for.

The general principle: **push the invariant as far down as it will go.** A constraint is enforced for every writer including the ones you'll write next year, the migration script, and the person in a psql session. An invariant enforced by isolation level is enforced only for code paths that set the isolation level.

### Transaction scope

Isolation only means anything within a transaction's boundaries, so where those boundaries sit is a design decision, and two mistakes recur:

**Too long.** A transaction held open across a network call or a user's think time pins a snapshot, blocks vacuum from cleaning newer dead rows, holds locks, and — as 6.3b covered — stalls any DDL that arrives behind it. `idle in transaction` is one of the most consequential states in a production database.

**Too wide a promise.** Isolation covers one database. It does not cover your cache, your search index, your object storage, or another service. Two transactions on two systems is not a transaction (6.1), no matter how the code is indented.

## When It's Appropriate

- **Read Committed** — the default, and correct for the large majority of work: single-row writes with the arithmetic in SQL, CRUD, reads where seeing a slightly newer row is harmless.
- **Repeatable Read** — any transaction that reads several related things and must see one coherent picture. Exports, invoices assembled from multiple tables, reconciliation, anything that computes across queries. Also the cheapest protection against lost update if the write can't be expressed atomically.
- **Serializable** — invariants spanning rows that no constraint can express, where being wrong is expensive: scheduling and allocation of scarce capacity, on-call and approval rules, ledgers with balance conditions, anything where "two of these must never both happen." Concretely: a booking system doing 50 writes/second on a rule that can't be a constraint is a perfect fit, and the overhead will be invisible.

A calibration point for the fear of Serializable: **its cost is a function of the conflict rate, not the transaction rate.** Thousands of transactions per second that rarely touch the same rows produce almost no aborts. A hundred per second all contending on one row produce a lot — but so does every other approach to that situation, in the form of lock waits instead of retries.

## When It's Unnecessary or Overkill

- **Serializable globally, without a retry wrapper.** This converts a rare data corruption into a frequent user-visible error, which is worse in most people's judgement and definitely more visible.
- **Raising isolation to fix something a `UNIQUE` index fixes.** More cost, less coverage.
- **Long transactions "to keep things consistent."** A transaction that stays open for the length of a request or a user interaction buys weaker guarantees than you think and costs real operational harm.
- **Application-level locking for single-row updates** that a compare-and-set handles in one statement.
- **Two-phase commit / XA** to coordinate two services. It's available, it's rarely the right answer, and it converts two independent systems into one that is unavailable whenever either is (Modules 23 and 37).
- **Adding isolation to fix a duplicate caused by an unsafe retry.** That's an idempotency problem, and no isolation level makes a second, identical, legitimately-submitted request stop being a second request.

## Trade-offs

**Stronger isolation trades wrong answers for aborted transactions,** and aborts have to go somewhere. A retry adds latency to the tail, and a retry storm under contention adds load exactly when the system is least able to take it.

**Retries must be safe to run twice.** Which pushes side effects out of the transaction, which means a second mechanism (outbox, idempotency keys) that has to exist first. Adopting Serializable frequently turns out to be a three-week project rather than a configuration change, and most of the work is in that sentence.

**Serializable tracks read dependencies, which costs memory,** and can abort transactions that only read. A long-running report at Serializable can be killed by unrelated writers; the recommended escape is declaring it `READ ONLY DEFERRABLE`, which waits for a safe snapshot instead.

**Snapshot reads are stale by definition.** At Repeatable Read you get a consistent view of a moment that has already passed. For decisions about the current state, consistency and freshness are different properties and you have chosen the first.

**Row locks serialize hot rows.** Every mechanism here degrades to queueing behind the popular entity — the counter problem from 6.2a in a different costume.

**Read replicas break all of it.** A replica has its own lagging snapshot, so reading your own write can fail, and no isolation level on the primary changes that. Routing rules or causal tokens, not isolation, are the fix.

**Long transactions cost the whole system,** not just themselves: bloat, delayed vacuum, replication lag, and blocked DDL.

## Alternatives

- **Constraints** — unique, check, foreign key, exclusion. Race-free, enforced universally, cheap. Always the first question.
- **Single-statement atomic writes and compare-and-set** — the precondition in the `WHERE`, the outcome in the affected row count.
- **Optimistic concurrency with a version column**, and **pessimistic locking** with `SELECT … FOR UPDATE` or advisory locks. Both are ways of doing this work explicitly at Read Committed; that's 6.5b.
- **Serialize by design.** Route all writes for one entity through one consumer — a partitioned queue keyed by entity id — and concurrent conflict stops existing because concurrency stops existing for that key. A real architectural option with real costs (Module 10).
- **Append-only with expected version.** Write an event with the version you read; the write fails if anyone else wrote first. This is optimistic concurrency as a storage model (2.4).
- **Sagas and compensation** when the work genuinely spans services and no transaction is available (Module 37).
- **Idempotency keys** for the class of duplicate that isolation cannot prevent, because it isn't a race — it's the same request arriving twice.

## How to Achieve It

1. **Write the invariant as one sentence.** "No two bookings for the same room overlap." "The balance never goes below zero." "At least one doctor is on call." If you can't write it, you can't enforce it, and most concurrency arguments are really a disagreement about what the sentence is.
2. **Ask whether the database can enforce it directly.** Unique, check, exclusion, foreign key. If yes, stop here — that's the strongest and cheapest answer available.
3. **If it's one row, make the write atomic** and put the precondition in the `WHERE`. Then check the affected row count and treat zero as a real outcome, not an impossibility.
4. **If it spans rows and isn't expressible as a constraint**, choose between materializing the conflict (take a lock on a row representing the invariant — the shift, the account, the room) and Serializable. Materializing is more explicit and doesn't need retries; Serializable is less code and needs them.
5. **Build the retry wrapper before changing any isolation level.** Bounded, jittered, restarting the whole transaction, only on 40001 and 40P01.
6. **Set isolation per transaction, not globally.** It's a property of a piece of work, not of a connection or an application.
7. **Keep transactions short and free of network calls.**
8. **Test concurrently, or you have tested nothing.** Two connections, interleaved deliberately, asserting the invariant afterwards. Every failure in this article is invisible to a serial test suite.

## Implementation

TypeScript, alongside the `withLockTimeout` wrapper from 6.3b — the two belong in the same file.

The booking case first, because it's the one that needs no isolation change:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings ADD CONSTRAINT bookings_no_overlap
  EXCLUDE USING gist (room_id WITH =, period WITH &&);
```

Two concurrent inserts, one succeeds, the other gets a constraint violation to handle. No `SELECT` first, no race window, no isolation level involved, and it holds for the CSV importer and the admin console and anything else that ever writes to this table.

Now the case that can't be a constraint:

```ts
const RETRYABLE = new Set(['40001', '40P01']);  // serialization_failure, deadlock_detected

async function serializable<T>(sql, work: (tx) => Promise<T>, attempts = 5): Promise<T> {
  for (let i = 0; ; i++) {
    try {
      return await sql.begin(async (tx) => {
        await tx`SET TRANSACTION ISOLATION LEVEL SERIALIZABLE`;
        return work(tx);                       // reads AND writes, every attempt
      });
    } catch (e) {
      if (!RETRYABLE.has(e.code) || i >= attempts - 1) throw e;
      await sleep(Math.random() * 25 * 2 ** i);
    }
  }
}
```

```ts
await serializable(sql, async (tx) => {
  const [{ count }] = await tx`
    SELECT count(*)::int FROM doctors WHERE on_call AND shift_id = ${shift}`;
  if (count <= 1) throw new BadRequest('someone must remain on call');
  await tx`UPDATE doctors SET on_call = false WHERE id = ${me}`;
});
```

Four properties, each of which is a way this goes wrong when absent.

**The whole callback re-runs, count query included.** A retry that keeps the previously-read `count` is the original bug with extra steps. This is the single most common mistake in hand-rolled retry code, and structuring it as a callback rather than a loop around individual statements is what makes it hard to get wrong.

**Only two error codes are retried.** A unique violation, a check violation, or a bad request is a real answer; retrying it just delays the same failure five times.

**Backoff is jittered and bounded.** Contention is the reason you're being aborted, so retrying immediately and in lockstep with the transaction that beat you is how a contended row becomes a livelock. Exhausting the attempts should surface as an error and a metric, not as a silent failure.

**Side effects are absent.** No email, no webhook, no payment call inside the callback. If the shift change needs to notify someone, that's a row written in this transaction and a relay outside it (6.1). Anything else will fire twice, on the day the system is busiest.

One more line, for the case where the transaction only reads:

```ts
await tx`SET TRANSACTION ISOLATION LEVEL SERIALIZABLE, READ ONLY, DEFERRABLE`;
```

`DEFERRABLE` makes a long read-only transaction wait until it can get a snapshot guaranteed not to conflict, rather than running immediately and risking an abort halfway through a twenty-minute report. It trades start latency for never being aborted, which for a report is exactly the right trade.

## Further Reading

- **_Designing Data-Intensive Applications_, Martin Kleppmann, chapter 7.** The best available treatment of this material, and the source of the framing that write skew and lost update matter more than the standard's three anomalies. If you read one thing, read this.
- **"A Critique of ANSI SQL Isolation Levels," Berenson, Bernstein, Gray, Melton, O'Neil & O'Neil (1995).** The paper that established that the standard's definitions are ambiguous and incomplete, and introduced snapshot isolation into the vocabulary. Short and readable.
- **PostgreSQL documentation, chapter 13, "Concurrency Control."** Particularly 13.2 on the isolation levels — which contains the on-call example above — and 13.4, "Data Consistency Checks at the Application Level," which states plainly that Serializable requires a retry loop.
- **"Serializable Snapshot Isolation in PostgreSQL," Ports & Grittner (VLDB 2012).** How SSI actually detects the dependency cycles, and what it costs. Worth reading if you're deciding whether to trust it.
- **MySQL Reference Manual, "InnoDB Locking and Transaction Model."** Gap locks and next-key locks, which is how MySQL gets a different set of guarantees at the same level names. Necessary if you work across both engines.
- **jepsen.io/consistency.** A map of consistency and isolation models and how they relate, which is the clearest way to see that "serializable" and "linearizable" are different axes that get conflated constantly.
- **"When is 'ACID' ACID? Rarely," Peter Bailis.** A survey of what commercial databases actually default to, which is the empirical version of this article's opening.

A **Java** sibling would cover a trap this one can't reach: where the retry sits relative to the transaction. In Spring, `@Transactional` and `@Retryable` are both proxy-based, so a retry annotation on the same method — or a retry loop *inside* a transactional method — re-runs the work inside a transaction that is already marked rollback-only, achieving nothing. The retry has to wrap the transactional boundary from outside, which means a separate bean and an understanding of self-invocation. Add `@Transactional(isolation = Isolation.SERIALIZABLE)` interacting with connection pooling — the level is set on the connection and must be reset on return, which some pools do and some don't — and there's a full article's worth of things that are invisible in the annotations. Not yet written.

The habit: **name the invariant, then name who enforces it.** The database, via a constraint. The isolation level, via aborts you retry. Or nobody, via a comment that says the race is unlikely. Those are the three options, and only the first two survive contact with a second instance.
