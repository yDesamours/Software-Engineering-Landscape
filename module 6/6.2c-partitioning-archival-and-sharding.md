# Partitioning, Archival, and Sharding

_Module 6.2c — Database Design & Data Management_

## The Problem

An `events` table. Every user action in the product lands here: 4,000 rows a second, 350 million a day, and it has been running for three years. The table is 2.1 TB and its indexes are another 900 GB.

Retention policy says ninety days. Nobody has ever enforced it, and the reason is instructive. Somebody tried:

```sql
DELETE FROM events WHERE occurred_at < now() - interval '90 days';
```

It ran for six hours, produced 400 GB of write-ahead log, pushed replication lag to eleven minutes, was killed, and rolled back. The second attempt batched it into chunks of 10,000, which ran politely alongside production traffic and was still running two weeks later — deleting slightly slower than new rows arrived. And even where it succeeded, nothing got better:

- **The disk didn't shrink.** Deleted rows leave dead space that the table reuses for new rows. The 2.1 TB is still allocated.
- **The indexes are still huge.** Entries get marked dead, the trees don't get smaller.
- **`VACUUM` now has 400 million dead rows to clean up**, on a table where autovacuum was already struggling to finish a pass before the next one was due.

Meanwhile the table is causing problems that are all the same problem:

- 96% of reads touch the last seven days. Every one of them uses an index sized for three years of data, which no longer fits in memory, so a lookup that used to be a cache hit is now two disk reads.
- Every insert is a random write into those oversized trees (6.2b).
- The nightly backup takes nine hours and restoring it takes longer. A restore drill hasn't been attempted in a year, for reasons nobody says out loud.
- `ALTER TABLE events ADD COLUMN …` is a change request that gets deferred for a quarter.

Here is the shape of it: **the table contains two populations with nothing in common.** Seven days of hot data that everything reads, and three years of cold data that nothing reads and that policy says shouldn't exist. They're in one physical structure, so every index, every vacuum, every backup, and every migration is sized for the sum.

Now split the table by month, physically, while keeping it one logical table. Retention becomes:

```sql
DROP TABLE events_2026_05;
```

```
     DELETE 400M rows                    DROP one partition
     ───────────────                     ──────────────────
     six hours                           milliseconds
     400 GB of WAL                       one DDL statement
     bloat left behind                   disk returned immediately
     indexes unchanged in size           indexes dropped with it
     eleven minutes of replica lag       nothing to replicate but the DDL
```

That's the payoff, and it's not a performance trick. It's that a *lifecycle operation* stopped being expressed as row-by-row data manipulation and became a metadata change.

Then someone on the next team hears "partitioning made events fast," partitions `orders` by `hash(order_id)` into 64 pieces, and gets: queries that filter by `merchant_id` now touch all 64 partitions instead of one table, planning time triples, and every report needs to merge 64 sorted streams. Nothing improved and several things got worse.

Both outcomes come from the same question, asked or not asked: **partitioning only pays when the way data ages and the way queries filter agree on the same key.**

## What It Is

**Partitioning** splits one logical table into multiple physical tables — partitions — by the value of a partition key. The database routes inserts to the right partition and, crucially, excludes irrelevant partitions from queries. It's one database, one connection, one transaction manager; `SELECT … FROM events` still works and still means all of it.

Three flavours, and the choice is not stylistic:

- **Range** — by time, almost always. Gives both pruning for recent queries and cheap retention. This is the case worth designing for.
- **List** — by an enumerable value: region, plan tier, one enormous tenant pulled out into its own partition.
- **Hash** — even distribution by hash of the key. Reduces per-partition size and index depth, prunes only for equality on the key, and gives you nothing for retention, because a hash partition never becomes old.

**Sharding** splits data across *separate database servers*. That is a different thing wearing a similar word, and the difference is not one of degree:

```
  partitioning                          sharding
  ────────────                          ────────
  one server, one logical table         many servers, no shared anything
  transactions: normal                  cross-shard: no transaction exists
  joins: normal                          cross-shard: your application joins
  add a partition: one DDL              add a shard: a data movement project
  migration: one database               migration: N databases, partial failures
```

**Archival** is the third leg: deciding what happens to data once it's cold — deleted, rolled up into summaries, or moved somewhere cheaper with a different access path.

Two neighbours to separate immediately:

**Partitioning is not an isolation boundary.** Partitioning by `tenant_id` puts a tenant's rows in their own physical table and does nothing whatsoever to stop a query without a tenant predicate from reading all of them. 5.1 made this point; it's worth repeating exactly once because the mistake is common and the consequence is a data leak, not a slow query.

**Partitioning is not an index.** An index finds rows; partition pruning eliminates whole files before any index is consulted. They're complementary, and pruning is strictly coarser — it can skip a partition, never a row.

## Recognizing the Problem

Partitioning is likely to help:

- Retention is a `DELETE` that runs longer than the interval it runs on.
- The overwhelming majority of reads hit a narrow, recent slice of a very large table.
- Insert latency has grown steadily with table size, and the indexes no longer fit in memory.
- Autovacuum never finishes a pass on the table.
- Bulk loads or bulk deletes are done in chunks to avoid hurting production.
- One table is the reason schema migrations are scary.
- The backup is dominated by data nobody has queried in a year.

It probably won't help:

- The table is 20 GB. Most partitioning projects on tables under a few hundred gigabytes are solving a problem the buffer cache already solved.
- Queries don't share a common filter column, so pruning never happens.
- The real problem is a missing or wrong index (6.2b), or 600 queries per request (6.4).
- You need global uniqueness on a column that isn't the partition key. Read *Trade-offs* before committing.

You may be facing sharding rather than partitioning:

- A single primary is saturated on *writes*, not reads, after indexes have been trimmed and batching is in place.
- The working set exceeds what the largest machine you can rent will cache, economically.
- Regulation requires data for a region to be stored in that region.
- Replicas, caching, partitioning, and an index diet are all already done.

If the last bullet isn't true, the first three are probably misdiagnoses.

## How It Works

### Pruning

The planner reads the `WHERE` clause, compares it against each partition's declared bounds, and drops the ones that can't contain matches:

```
SELECT count(*) FROM events WHERE occurred_at >= '2026-09-01';

  events_2026_05   ✕  pruned  (bounds end before the filter starts)
  events_2026_06   ✕  pruned
  events_2026_07   ✕  pruned
  events_2026_08   ✕  pruned
  events_2026_09   ✓  scanned      1 of 40 partitions,
                                   and its index fits in RAM
```

This only works if the query mentions the partition key. A query filtering solely on `user_id` reads every partition — which is why the hash-partitioned `orders` table got slower: none of its queries mentioned `order_id`.

Pruning happens at plan time when the bounds are literal, and at execution time when they come from parameters or a join. Both work; execution-time pruning shows up differently in `EXPLAIN`, which confuses people into thinking it isn't happening.

### Everything else becomes per-partition

This is the underrated half. Once the table is split, so is all the machinery:

- **Indexes.** Each partition has its own, sized for its own rows. The hot partition's index is small enough to stay cached; the cold ones can have fewer indexes, or different ones.
- **Vacuum and statistics.** A finite job per partition instead of an infinite one per table. Read-only old partitions need vacuuming once, ever.
- **Bulk operations.** Load into a detached table, index it, validate it, attach it. The live table sees one metadata change.
- **Retention.** `DROP` or `DETACH` — constant time, regardless of row count.

### The constraint that surprises everyone

**A unique constraint on a partitioned table must include the partition key.** Not a Postgres quirk — a consequence: enforcing global uniqueness would require checking every partition on every insert, which would eliminate the independence that makes partitioning work.

So on a table partitioned by `occurred_at`, `UNIQUE (email)` is not available. You get `UNIQUE (email, occurred_at)`, which permits the same email in two months. Real options, all with costs: a separate small unlisted lookup table holding the unique values with a real constraint; enforcing uniqueness in the application (which means "not enforced", eventually); or accepting that this table isn't where that invariant lives. Find this out while designing, not after the backfill.

The same logic hits primary keys — the PK must contain the partition key, so entities get composite identity, which then propagates into every ORM mapping and every foreign key pointing at the table.

### Where sharding starts

Everything above happens inside one database. Sharding gives up that premise, and what's lost is specific:

- **No cross-shard transaction.** Two shards, two commits, and the mechanisms for making that safe (sagas, outbox, reconciliation) are the ones 6.1 introduced for two stores. It's the same problem with a more sympathetic-looking cause.
- **No cross-shard join.** Queries that span shards become scatter-gather in the application: send to all, merge the results, sort, paginate. The latency of that query is the latency of its slowest shard — so tail latency, not average, becomes the thing you feel.
- **Uniqueness and identity go global.** Auto-increment per shard collides; you need UUIDs, or Snowflake-style IDs, or a range allocator.
- **Rebalancing is a project.** Shards fill unevenly because tenants are unevenly sized, and moving one live requires the write-fence machinery from 5.4b rather than a script.
- **Migrations multiply,** with partial-failure states — which is the forty-deployments problem from 5.1, arriving through a different door.

Routing — hash versus a lookup directory, and why the directory is what makes a tenant movable — was settled in 5.4b and isn't re-derived here. The strategy detail (range versus hash versus geographic, consistent hashing, rebalancing algorithms) belongs to Module 38.2. The point worth leaving here is the threshold: **sharding is what you do when one machine genuinely cannot hold the writes or the working set, and almost everything that looks like that threshold from a distance turns out, on inspection, to be an index problem, a cache problem, or a query problem.**

### Archival: three different endings

Cold data has three fates, and they are not interchangeable.

**Delete it.** The cheapest possible answer, and the one nobody proposes because it feels like losing something. Ask what the data is *for*. "We might want it someday" has a price now, quoted in backup windows and restore times.

**Roll it up.** Keep hourly or daily aggregates, drop the raw rows. For telemetry and event data this usually preserves every question anyone actually asks at a fraction of a percent of the volume. The catch is that it forecloses questions you haven't thought of yet, so the rollup design is a product decision, not a storage one.

**Move it.** Detach the partition, export it to columnar files in object storage, drop it. Queryable later with an engine that reads Parquet, at a cost per query and a latency measured in seconds instead of milliseconds — perfectly acceptable for the audit request that arrives twice a year, unacceptable as a live code path. Whichever ending you choose, the export must be verified before the drop, because the drop is the irreversible half.

## When It's Appropriate

**Partition when:**

- The data is append-mostly and time-shaped, and retention exists. Range-partition by time, and do it *before* the table is huge — partitioning a 2 TB table in place is a migration project, while starting partitioned costs one line of DDL.
- The table is large enough that "large" is the problem: hundreds of gigabytes or hundreds of millions of rows, with queries that filter on the key.
- You need to load or delete in chunks without disturbing live traffic.
- One tenant is large enough to distort everything, and a list partition for that tenant plus a default for everyone else fixes it (this is the cheapest version of the cell idea from 5.1).
- Data residency requires rows for a region to sit in a specific tablespace or volume.

**Shard when** the single-primary write ceiling is genuinely reached, with numbers attached. Calibrate first: a well-configured Postgres on current hardware handles tens of thousands of small write transactions per second. If you're at 3,000 and struggling, the problem is eleven indexes, a synchronous replica in another region, or a lock. Vertical scaling is unglamorous and goes remarkably far — the largest cloud instances now carry hundreds of cores and terabytes of RAM, and "buy the next size up" costs a fraction of an engineer-quarter.

## When It's Unnecessary or Overkill

- **Hash partitioning "for performance."** Partitioning doesn't speed anything up by itself; pruning does. Hash prunes only on equality, never for ranges, and never lets you drop anything.
- **Partitioning a table that isn't big.** You added planning overhead and maintenance obligations to solve nothing.
- **Too many partitions.** Hundreds are fine. Daily partitions kept for ten years — 3,650 of them — make planning slow and consume memory and locks per partition on every query that can't prune. Pick the granularity so that retention has a useful resolution and the count stays in the low hundreds.
- **Sharding for read scale.** That's what replicas are for.
- **Sharding to fix a slow query.** The query will be slow on every shard.
- **"We'll shard eventually, so let's not use foreign keys / joins / transactions now."** Paying the costs of a distributed system while getting none of its benefits, often for years, sometimes forever.
- **Partitioning by tenant for isolation.** Covered above and in 5.1.

## Trade-offs

**Partition maintenance is a job that must never fail.** New partitions have to exist before rows need them. If September arrives and `events_2026_09` doesn't exist, inserts fail — not slowly, not partially, they fail — at midnight, on a weekend. A `DEFAULT` partition catches the rows instead, at the cost of a trap: attaching a new partition later requires scanning the default to prove no rows belong in the new range, which takes a strong lock on a table that may now be large.

**The partition key is close to irreversible.** Changing it is a full rewrite of the table. Choose it from the lifecycle first (what makes data droppable) and the query pattern second, and if those two disagree, partitioning is probably the wrong tool for this table.

**Cross-partition queries get more expensive, not less.** Anything that can't prune now opens every partition, and aggregates and sorts merge N streams. Planning time scales with partition count.

**Global constraints weaken,** as described above — the unique-key restriction is the one that most often invalidates a partitioning plan late.

**Migrations apply to N tables,** and tooling varies in how gracefully it handles that (6.3).

**For sharding, add:** no cross-shard atomicity, no cross-shard joins, tail-latency amplification on fan-out, a routing layer that is a new single point of failure, N backup and restore procedures with no consistent point in time across them (6.6), and hot shards caused by uneven tenants.

**For archival, add:** a second access path with a different SLA that someone will need urgently and that nobody has tested; and the genuine conflict between deletion obligations (a GDPR erasure request) and retention obligations (seven years of financial records) — which is a legal question that lands in your schema (Module 34).

## Alternatives

Roughly in order of cost, and the first three are the ones skipped too often:

- **Shorten retention.** Three months instead of three years is a policy change, not an engineering project. Ask who decided on three years; frequently nobody did.
- **Roll up and drop detail.** Continuous aggregates or a summary table, raw data expired. Usually a 100–1000× reduction.
- **Trim the indexes** (6.2b). Often reclaims more than partitioning would.
- **Buy a bigger machine.** Boring, immediate, reversible.
- **Read replicas** for read scale, and moving analytics off the primary entirely (6.1).
- **A time-series extension** — Timescale hypertables are partitioning with the maintenance, compression, and rollups already built, which for telemetry data is most of this article as a dependency.
- **Built-in TTL,** where the store has it: Cassandra's per-row TTL, Mongo's TTL index, DynamoDB's TTL. Retention as a column property rather than a job.
- **Distributed SQL rather than hand-rolled sharding** — Citus, Vitess, CockroachDB, Spanner, Aurora Limitless. You accept feature restrictions and cost, and avoid writing a routing layer, a rebalancer, and a scatter-gather query engine. If the shard-level decision is genuinely forced, this is almost always the better shape of it.

## How to Achieve It

1. **Measure the three numbers:** table size and growth rate, the fraction of reads landing in the recent window, and what retention *actually is* — which frequently means getting someone to decide it for the first time.
2. **Try the cheap things first.** Retention, rollups, index diet, a bigger instance. Each one may remove the need for the rest.
3. **Choose the key by lifecycle, then verify against queries.** The test: does the thing that makes a row droppable also appear in most `WHERE` clauses? For time-shaped data the answer is yes, which is why this is nearly always range-by-time.
4. **Decide granularity by how many partitions you'll have at steady state.** Retention divided by partition width should land in the tens or low hundreds. Ninety days of daily partitions: 90. Three years of monthly: 36. Both fine.
5. **Migrate without a big-bang rewrite.** The low-drama path for an existing table is to attach it as a single historical partition (it needs a matching check constraint, validated first) so that only new data flows into new partitions and the old data ages out naturally under the retention policy. The alternative — new partitioned table, batched backfill, swap — is a full 6.3-shaped project.
6. **Automate partition creation with a wide safety margin,** and alert on the *margin*, not the failure. "Fewer than three future partitions exist" is a ticket; "insert failed" is an incident.
7. **Archive before dropping, verify before dropping,** and make the retention job's first action a `DETACH` rather than a `DROP` so the last step is reversible for a day.
8. **Only then consider sharding**, and prefer an engine that does it over an application that does it.

## Implementation

Go, and mostly DDL — because the mechanism here really is DDL, and the code that matters is the part that has to run every month without anyone watching.

Declaring the table and its partitions:

```sql
CREATE TABLE events (
  id           bigserial,
  occurred_at  timestamptz NOT NULL,
  user_id      bigint      NOT NULL,
  payload      jsonb,
  PRIMARY KEY (id, occurred_at)      -- partition key must be in the PK
) PARTITION BY RANGE (occurred_at);

CREATE TABLE events_2026_09 PARTITION OF events
  FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
```

Note the primary key. `PRIMARY KEY (id)` is rejected, and that single line is what forces composite identity through the rest of the system.

The maintenance loop:

```go
func maintain(ctx context.Context, db *sql.DB, now time.Time) error {
    // Create partitions well ahead of need, not just-in-time.
    for i := 0; i <= 3; i++ {
        start := monthStart(now).AddDate(0, i, 0)
        name := fmt.Sprintf("events_%s", start.Format("2006_01"))
        _, err := db.ExecContext(ctx, fmt.Sprintf(
            `CREATE TABLE IF NOT EXISTS %s PARTITION OF events
               FOR VALUES FROM ('%s') TO ('%s')`,
            pq.QuoteIdentifier(name),
            start.Format("2006-01-02"),
            start.AddDate(0, 1, 0).Format("2006-01-02")))
        if err != nil {
            return err
        }
    }

    // Retire, in two steps, on different days.
    cutoff := monthStart(now).AddDate(0, -3, 0)
    old := fmt.Sprintf("events_%s", cutoff.Format("2006_01"))
    _, err := db.ExecContext(ctx, fmt.Sprintf(
        `ALTER TABLE events DETACH PARTITION %s CONCURRENTLY`,
        pq.QuoteIdentifier(old)))
    return err
}
```

Four things in there are load-bearing, and three of them are things that go wrong at 00:00 on the first of a month.

**Create three months ahead, and alert on the margin.** Just-in-time creation means the job failing once becomes an outage the moment the clock rolls over. With a three-month buffer, a failure is a ticket you have three months to notice — provided something checks the buffer rather than only checking that the job exited zero.

**Identifiers can't be parameters.** `$1` works for values and not for table names, so the partition name is string-interpolated into DDL. Here it's derived from a clock so it's safe, but the day someone makes it a request parameter it's SQL injection into DDL — hence `QuoteIdentifier` rather than bare `Sprintf`, as a habit.

**`DETACH … CONCURRENTLY` versus `DETACH`.** The plain form takes a lock that blocks every query against the parent table for its duration, which on a busy table is an outage measured in whatever your slowest running query is. The concurrent form doesn't, and in exchange can't run inside a transaction block.

**Detach and drop are separate days.** Detaching removes the partition from the logical table instantly and reversibly; the data is still there, under its own name, if someone discovers tomorrow that ninety days was the wrong number. The `DROP` — or the export to Parquet, verified, and *then* the drop — comes after. Merging the two steps into one job is how a retention policy becomes a data-loss incident.

## Further Reading

- **PostgreSQL documentation, "Table Partitioning."** Declarative partitioning, pruning (including the difference between plan-time and execution-time), `ATTACH`/`DETACH CONCURRENTLY`, and — read this part specifically — the declarative partitioning limitations section, which is where the unique-constraint rule and the default-partition behaviour are stated precisely.
- **pg_partman documentation.** Partition maintenance as a solved problem, including retention and pre-creation. Read it before writing the job above, then write a much smaller job.
- **_Designing Data-Intensive Applications_, Martin Kleppmann, chapter 6.** Partitioning at the conceptual level: key-range versus hash, skew and hot spots, rebalancing strategies, and request routing. The right preparation for Module 38.2.
- **Vitess documentation on resharding.** The clearest public description of moving live data between shards — the copy, the filtered replication catch-up, the cutover — and an excellent way to calibrate how large a sharding decision actually is.
- **Citus documentation on choosing a distribution column.** Written for distributed Postgres, but the reasoning about co-location and which queries survive is the best short treatment of "what does this key choice cost me later."
- **Timescale documentation on hypertables, compression, and continuous aggregates** — partitioning, columnar compression of old chunks, and rollups presented as one lifecycle, which is the shape most telemetry systems eventually need.
- **Apache Parquet and DuckDB documentation** for the archive path: what a detached partition should be exported as, and how it gets queried afterwards without restoring anything.

A **Java** sibling would surface a consequence this article can only name. The rule that the partition key must appear in the primary key means the entity has a composite identity, and in JPA that means `@IdClass` or `@EmbeddedId`, an `equals`/`hashCode` contract that now includes a timestamp, and every `@ManyToOne` pointing at the table becoming a composite join. Repository method signatures change, `findById` takes an object, and second-level caching behaves differently. None of that is visible from the DDL, and it's the part that turns a one-line partitioning decision into a two-week refactor in an ORM-heavy codebase. Not yet written.

---

The habit to take from this: **every large table has a lifecycle, whether or not anyone designed one.** Rows arrive, become interesting for some window, and then become weight — and the difference between a table that stays manageable at a terabyte and one that doesn't is whether someone named that window while the table was still small.

The diagnostic question is narrower than "should we partition": *what makes a row cold, and is that the same thing my queries filter on?* When the answers match, partitioning is nearly free and pays every day. When they don't, it's overhead with a maintenance job attached, and the real answer is somewhere else in this module.
