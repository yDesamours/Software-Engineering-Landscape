# Finding the Slow Query

_Module 6.4b — Database Design & Data Management_

## The Problem

"The app is slow." So the team does the obvious thing and turns on the slow query log with a one-second threshold.

It catches three queries a day, all from the nightly reconciliation report. Nothing on the checkout path, nothing on the dashboard, nothing that any user has ever waited for. The conclusion is that the database is fine.

Here's what the database actually spent the day doing:

```
  slow log (> 1 s)                    total database time, by statement
  ────────────────                    ─────────────────────────────────
  nightly report                      SELECT … FROM order_items WHERE order_id = $1
    4.2 s × 3 calls   = 13 s            0.8 ms × 41,000,000 calls   =  9.1 hours

                                      SELECT … FROM sessions WHERE token = $1
                                        0.3 ms × 88,000,000 calls   =  7.3 hours

                                      UPDATE users SET last_seen_at = $1 …
                                        1.1 ms × 12,000,000 calls   =  3.7 hours

                                      nightly report
                                        4.2 s × 3 calls             = 13 seconds
```

The slow log isn't wrong; it's sorted by the wrong key. It finds outliers, and the system's cost is in the aggregate. **The most expensive query in almost every production database is a fast one.**

That's the first way this goes wrong. There are two more.

**The plan gets misread.** Say you do find the query. The `EXPLAIN ANALYZE` output has a node in the middle of it reading `actual time=0.80..0.85 rows=3 loops=48213`. Almost everyone reads "0.85 ms" and moves on. The times in a plan node are *per loop*. That node cost 41 seconds.

**The measurement doesn't reproduce.** The query runs in 2 ms in `psql` and 400 ms from the application. Nothing about the query changed. What changed is everything around it: the connection had to be waited for, the parameter value was a merchant with four million orders instead of the one you tested with, the prepared statement is on its sixth execution and the planner switched to a generic plan, the result set is 8 MB and has to cross a network, and the application then mapped 40,000 rows into objects.

So the honest starting position: **"the database is slow" is not a measurement.** It's three separate questions — where did the time go, which statement consumed it, and why does that statement cost what it does — and each one has a standard way of being answered wrongly.

## What It Is

Query performance analysis is attributing latency to specific work and explaining why that work costs what it does. It needs two views, and most systems have neither.

**The workload view** answers *what is this database spending its time on*, aggregated across all executions: `pg_stat_statements` and its equivalents. Sorted by total time, not by mean.

**The execution view** answers *why does this one statement cost what it does*: the query plan.

You need both, in that order. The workload view tells you which query is worth understanding; the plan tells you what to do about it. Starting from a plan means you're optimizing whichever query someone happened to complain about.

Three distinctions that prevent common mistakes:

**`EXPLAIN` versus `EXPLAIN ANALYZE`.** The first shows the plan the planner chose and its *estimates*. The second runs the query and reports what actually happened. Only the second can tell you the planner was wrong, which is the thing you most often need to know. It also means running `EXPLAIN ANALYZE` on an `UPDATE` performs the update — wrap it in `BEGIN … ROLLBACK`.

**Cost units are not milliseconds.** `cost=0.43..7208` is in arbitrary units calibrated to an assumed page-fetch cost. They're comparable within one plan and meaningless across machines. Read the `actual time` numbers.

**A slow endpoint is not a slow query.** If the endpoint takes 900 ms and the database was busy for 40 ms of it, no query optimization will help. That's 6.4a's problem, or a pool wait, or the application. Attribution comes before optimization.

## Recognizing the Problem

You're measuring the wrong thing if:

- The slow log is empty and users are waiting.
- Someone says "the database is slow" and no statement has been named.
- The mean latency is 80 ms and p99 is 2.5 s — the average is describing a population that doesn't exist.
- The query is fast in `psql` and slow from the application.
- It's fast for most customers and terrible for one.

Signals that point at a specific cause once you're looking:

- **Suddenly slow with no deploy** — statistics went stale, the data crossed a size threshold, a plan flipped, or bloat accumulated.
- **Slow only for the first hour after a restart or failover** — cold cache.
- **Slow in proportion to result size** — transfer and client-side mapping, not execution.
- **Latency grew smoothly over months with no plan change** — the working set stopped fitting in memory, so the same plan now does physical reads.
- **The same query is sometimes 3 ms and sometimes 3 s** — parameter-dependent plans, or a lock wait (6.3b), or a cache miss.
- **High `stddev` in `pg_stat_statements`** for a statement, which is the numeric version of the previous bullet.

## How It Works

### Where a request's time actually goes

```
  app  →  [ wait for a connection ]  →  [ plan ]  →  [ execute ]  →  [ transfer ]  →  [ map rows ]
            5.4b: pool exhaustion        rarely      the part           bytes over       the part
            looks exactly like           matters,    everyone           the wire,        everyone
            a slow database              until it    measures           proportional     forgets
                                         does                           to result size
```

Every one of those is routinely misattributed to "the database." Pool wait especially: from the application's perspective, waiting 300 ms for a free connection and waiting 300 ms for a query are the same measurement unless something distinguishes them. If your instrumentation reports one number for "database time," it is probably reporting the sum of the first four boxes and calling it the third.

### The workload view

```sql
SELECT calls,
       round(total_exec_time::numeric, 0)     AS total_ms,
       round(mean_exec_time::numeric, 2)      AS mean_ms,
       round(stddev_exec_time::numeric, 2)    AS stddev_ms,
       rows / greatest(calls, 1)              AS rows_per_call,
       shared_blks_hit, shared_blks_read,
       query
  FROM pg_stat_statements
 ORDER BY total_exec_time DESC
 LIMIT 20;
```

Five columns and what each one tells you:

- **`total_exec_time`** — the only correct sort key. This is the question "what is this database for."
- **`calls`** — a huge number next to a tiny mean is an N+1 (6.4a) or a missing cache (Module 13). The fix isn't in the query.
- **`stddev_exec_time`** — instability. A high standard deviation means the same statement sometimes behaves very differently, which points at parameter-dependent plans or contention rather than at the query text.
- **`rows / calls`** — a query returning 40,000 rows per call to render a page of 20 is a client problem.
- **`shared_blks_read` versus `hit`** — reads are misses. A statement with a poor hit ratio is telling you its working set doesn't fit in memory, which no index will fix.

Statements are normalized — parameters become `$1` — which is what makes aggregation possible and also means **the workload view cannot show you the bad parameter value.** That's what the plan capture below is for.

### Reading a plan past the top line

A real shape, with the interesting parts marked:

```
Nested Loop  (cost=0.43..912 rows=12 width=88)
             (actual time=0.05..41230 rows=48213 loops=1)          ← est 12, actual 48,213
  ->  Seq Scan on merchants m  (cost=0..410 rows=12 width=32)
        (actual time=0.01..18 rows=48213 loops=1)
        Filter: (active AND plan_tier <> 'free')
        Rows Removed by Filter: 1204                                ← filter did almost nothing
  ->  Index Scan using orders_merchant_idx on orders o
        (cost=0.43..41 rows=3 width=56)
        (actual time=0.80..0.85 rows=3 loops=48213)                 ← 0.85 ms × 48,213 = 41 s
        Index Cond: (merchant_id = m.id)
Planning Time: 0.4 ms
Execution Time: 41231.2 ms
```

The index scan is perfect. It uses the right index, returns three rows, takes under a millisecond. It is also the entire 41 seconds, because it ran 48,213 times.

And the reason it ran 48,213 times is the first marked line: the planner expected the outer side to produce **twelve** rows. For twelve rows, a nested loop is the right choice — twelve index lookups is nothing. For 48,213 it's catastrophic, and a hash join would have finished in under a second.

So the most valuable comparison in any plan is **estimated rows versus actual rows.** When they're close, the planner made an informed decision and the plan is probably the best available; if it's still slow, you need a different index or a different query. When they're off by orders of magnitude, the planner was working from bad information, and **the fix is the information, not the plan** — run `ANALYZE`, raise the statistics target on the column, or declare extended statistics for correlated columns (`plan_tier` and `active` are correlated here, and Postgres assumes independence unless told otherwise).

The other things to read, in order of how often they matter:

- **`loops=N`.** Multiply. Always.
- **`Rows Removed by Filter`.** Work done and discarded — usually an index opportunity (6.2b), sometimes a sign the filter belongs in a different place.
- **`Buffers: shared hit=… read=…`** (from `EXPLAIN (ANALYZE, BUFFERS)`). Hits are memory, reads are not. This distinguishes "this query does too much work" from "this query's data isn't cached," which have completely different fixes.
- **`Sort Method: external merge  Disk: 240MB`.** The sort didn't fit in `work_mem` and went to disk. Either reduce what's being sorted or give it more memory — and note `work_mem` is per sort node per connection, so raising it globally multiplies in a way that has ended badly for many teams.
- **The join method.** Nested loop is excellent with a tiny outer side and ruinous otherwise; hash join wants memory; merge join wants sorted inputs. You rarely choose these directly — you fix the estimate and the planner chooses correctly.

Read the tree from the inside out. The top node's time includes everything below it, so scanning from the top tells you the total, not the cause.

### Why the plan changes when you aren't looking

- **Parameter-dependent plans.** `WHERE merchant_id = $1` has a different best plan for a merchant with four million orders than for one with two hundred. Postgres builds a custom plan per execution for the first five executions of a prepared statement, then decides whether a generic plan is close enough — and if it switches, every subsequent execution uses the plan that suits the average, which suits nobody in a skewed multi-tenant system.
- **Stale statistics.** A bulk load or a migration changes the distribution, autovacuum hasn't re-analyzed yet, and the planner is reasoning about last week's data. Bulk operations should be followed by an explicit `ANALYZE`.
- **Crossing a threshold.** Nothing changed except the table got 15% bigger, and the cost of an index scan crossed the cost of a sequential scan (6.2b). Latency does not degrade gracefully here; it steps.

### Capturing the plan you actually care about

The plan you can reproduce by hand is the plan for the parameter you chose. `auto_explain` logs the real plan for any execution exceeding a threshold, in production, with the parameters that caused it:

```
auto_explain.log_min_duration = '500ms'
auto_explain.log_analyze = on
auto_explain.log_buffers = on
```

`log_analyze` adds per-node timing instrumentation to every query, not only slow ones, which has real overhead — enable it deliberately, measure, and consider `auto_explain.sample_rate` on a busy system.

## When It's Appropriate

- **Before adding an index or changing a schema.** The plan tells you which of the two you need.
- **When an endpoint misses a latency budget** and attribution shows the time is genuinely in the database.
- **Monthly, as a habit:** pull the top twenty by total time, look at what's changed since last month, reset the statistics. Ten minutes, and it catches regressions before anyone reports them.
- **Before a launch or a migration,** against production-shaped data volumes.

The top five statements by total time typically account for most of a database's work. Going past the top twenty is rarely the best use of an afternoon.

## When It's Unnecessary or Overkill

- **`EXPLAIN` on a development database.** With 200 rows, a sequential scan *is* the right plan, and the output tells you nothing about production. Plans are a function of data volume and distribution.
- **Optimizing before attributing.** Twenty minutes reading a plan for a query that accounts for 4% of the request is twenty minutes.
- **Micro-benchmarking one statement** while the real cost is pool wait or 101 round trips.
- **Installing an APM before counting queries per request.** The cheap signal (6.4a) finds more problems per hour of effort than the expensive one.
- **Chasing p99.99 on an internal admin tool.**
- **Tuning against a synthetic workload** that doesn't share production's skew — which, in a multi-tenant system, is the whole story.

## Trade-offs

**`pg_stat_statements` costs a little and forgets a lot.** Overhead is small, but it tracks a bounded number of statements and evicts the least used, so a system generating unbounded distinct statement shapes — dynamically built SQL, `IN` lists of varying length — loses its long tail and can push out entries you needed. Normalization also means you never see the parameter that made it slow.

**`EXPLAIN ANALYZE` changes what it measures.** Timing instrumentation adds per-node overhead that is negligible for a node executed once and significant for one executed 48,213 times, which distorts exactly the plans you're most interested in. `EXPLAIN (ANALYZE, TIMING OFF)` gives accurate row counts without that distortion.

**Query logging at volume becomes the bottleneck.** Logging every statement on a busy database can consume more I/O than the statements do.

**Mean and tail pull in different directions.** A change that improves average throughput by batching can worsen p99 for whoever is at the back of the batch. Decide which number you're optimizing before you start, because you can't have both by default.

**Reproducing production plans requires production-shaped data,** and a copy of production data is a compliance object with retention and access rules attached (Module 34). Anonymized copies are correct and are a real project; synthetic data with uniform distributions will produce plans you can't learn from.

## Alternatives

- **Distributed tracing / APM** (Module 19). A span per query inside a span per request attributes time automatically and answers "where did the 900 ms go" without arithmetic. If you have it, start there.
- **Managed database insights** — RDS Performance Insights, Cloud SQL Query Insights, Datadog DBM. Mostly `pg_stat_statements` plus wait-event sampling with a UI, which is a genuine convenience.
- **Wait-event sampling** (`pg_wait_sampling`, or sampling `pg_stat_activity`). Answers a question the other tools don't: *what were sessions blocked on* — locks, I/O, or the CPU run queue.
- **`pgbadger`** for turning a log file into a report when you can't install extensions.
- **Plan visualizers** — explain.dalibo.com, pev2 — which make the inside-out reading and the loop multiplication visible instead of arithmetic you do in your head.
- **Load testing with realistic skew** (Module 22) to find the plans that only appear under concurrency and cold caches.
- **Counting queries per request** (6.4a) — the cheapest tool here, and the one that finds the most common bug.

## How to Achieve It

1. **Start at the edge.** Which endpoint, which percentile, what's the budget. "Slow" without a number isn't actionable.
2. **Attribute before optimizing.** How much of that latency was database execution at all? If it's 40 ms of 900, stop — the problem is round trips, pool wait, or the application.
3. **Find the statement by total time,** from the workload view, not by scrolling a slow log.
4. **Capture a real plan with real parameters** — `auto_explain` in production, or a reproduction against a production-shaped copy.
5. **Read estimate versus actual first.** A large gap is a statistics problem; a small gap with bad performance is an index, schema, or query-shape problem.
6. **Apply the fix the plan indicates** — index (6.2b), materialized value (6.2a), partition (6.2c), fetch strategy (6.4a), or a rewrite — rather than the fix you were already planning to apply.
7. **Verify the same way you measured,** and check the write side too. An index that halves a read and doubles an insert may be a bad trade at your read/write ratio.
8. **Reset the statistics after a change,** so next month's top twenty is a comparison rather than a cumulative blur.

## Implementation

Go, and the point is attribution: making every query carry the name of the request that caused it, so the workload view and the request view can be joined.

```go
type tracer struct{}

func (t *tracer) TraceQueryStart(ctx context.Context, _ *pgx.Conn,
    d pgx.TraceQueryStartData) context.Context {
    return context.WithValue(ctx, startKey{}, time.Now())
}

func (t *tracer) TraceQueryEnd(ctx context.Context, _ *pgx.Conn,
    d pgx.TraceQueryEndData) {
    started := ctx.Value(startKey{}).(time.Time)
    if s := statsFrom(ctx); s != nil {
        s.count.Add(1)
        s.dbNanos.Add(int64(time.Since(started)))
    }
}
```

and one line per request, at the edge:

```go
log.Info("request",
    "route", route,                    // GET /merchants/:id/orders
    "total_ms", total.Milliseconds(),  //  912
    "db_ms", stats.dbMillis(),         //   41
    "queries", stats.count.Load(),     //  103
    "pool_wait_ms", stats.waitMillis())//    6
```

Those four numbers together are the attribution step, and they answer the question no single tool answers on its own. `912 / 41 / 103` is an N+1 and no plan needs reading. `912 / 870 / 2` is a query to go look at. `912 / 40 / 2` with a pool wait of 400 is neither — it's capacity (5.4b). Teams that log this find the category of their problem in the first hour; teams that don't argue about it for a week.

The second half is carrying request context *into* the database, where the DBA-side tooling can see it:

```go
const q = `/*route='GET /merchants/:id/orders',rev='a41f2c'*/
           SELECT … FROM orders WHERE merchant_id = $1`
```

That comment shows up in `pg_stat_activity` while the query is running and in the logs when it's slow, so the person staring at a stuck statement at 14:34 (6.3b) can tell instantly which endpoint and which deploy produced it. It doesn't fragment `pg_stat_statements`, because the statement identifier is computed from the parse tree and comments aren't part of it. The convention has a name — sqlcommenter — and several ORMs and frameworks will inject it for you.

Two cautions. Build the comment from a fixed route template and a build identifier, never from user input or from formatted parameter values: the first is an injection vector, and the second makes every execution a distinct statement text in the logs. And keep it short — it's prepended to every statement your system issues.

## Further Reading

- **PostgreSQL documentation, "Using EXPLAIN"** in the Performance Tips chapter. Short, worked examples, and the authoritative statement of what each number means. Followed by the **Statistics Used by the Planner** section and **`CREATE STATISTICS`**, which is the fix for the correlated-columns estimate failure above.
- **PostgreSQL documentation for `pg_stat_statements` and `auto_explain`.** Read the normalization rules in the first and the overhead warnings in the second before enabling either in production.
- **"The Internals of PostgreSQL," Hironobu Suzuki** (interdb.jp, free). Chapter 3 walks the planner from parse tree to plan, including how selectivity estimates are computed — which is what turns "the estimate was wrong" from a mystery into something you can reason about.
- **explain.dalibo.com / pev2.** Paste a plan, see where the time is. Worth using for the first dozen plans you read, purely to build the instinct for inside-out reading and loop multiplication.
- **`pg_wait_sampling`, or the wait event documentation for your engine.** The view that tells you what sessions were *blocked on* rather than what they were running, which is the missing half when nothing is slow but everything is waiting.
- **sqlcommenter (google.github.io/sqlcommenter).** The convention above, its supported frameworks, and the reasoning about what's safe to include.
- **_Systems Performance_, Brendan Gregg** — not database-specific, and the best available statement of the discipline: measure, attribute, then change one thing. The USE method generalizes cleanly to a database's resources.

A **Java** sibling would add a layer this article assumes away: the driver. The PostgreSQL JDBC driver buffers an entire result set in memory unless autocommit is off *and* `setFetchSize` is set, so "the query took 3 ms" can be followed by forty seconds of the client materializing two million rows — a latency that appears in neither the plan nor `pg_stat_statements`. Around that sit Hibernate's `Statistics` API, `datasource-proxy` or p6spy for per-query logging, and Micrometer's connection-pool metrics, which together produce the four-number log line above without writing a tracer. The genuinely different content is that in a JVM stack, several of the biggest costs live between the driver and the ORM, where neither the database's tools nor the application's profiler is looking. Not yet written.

---

The habit: **name the statement and the number before changing anything.** Not "the orders page is slow" — "`GET /orders` is 910 ms at p95, 41 ms of it in the database across 103 queries." The second sentence contains its own diagnosis; the first one starts an argument.

And the sort order worth remembering, because it's the one the tools don't default to: by total time, not by duration. The query that hurts you is almost never the slow one.
