# Optimistic and Pessimistic Locking

_Module 6.5b — Database Design & Data Management_

## The Problem

A support ticket: *"I updated the client's billing address on Tuesday and it's back to the old one."*

Here's Tuesday:

```
  09:00   Dana opens client #412                GET  → address = "12 Mill St"
  09:02                                          Priya opens client #412
                                                 GET  → address = "12 Mill St"
  09:05                                          Priya changes the postcode, saves
                                                 PUT  → address = "12 Mill St, EC1 4XY"
  09:08   Dana changes the street, saves
          PUT → address = "40 Mill St"
```

Dana's form was built from a version of the record that was already stale by the time she submitted it. Her save didn't merge with Priya's; it overwrote it with everything her page had been holding since 09:00. Priya's postcode is gone, nothing errored, and no log line records that anything unusual happened.

Now look at where the transactions were:

```
  09:00 ──[tx: 3ms]──────────────────── 8 minutes of nothing ────────────[tx: 4ms]── 09:08
         read committed, fine                                             read committed, fine
```

Seven milliseconds of database work separated by eight minutes in which there was no transaction at all. **No isolation level can help here**, because isolation only describes what happens between `BEGIN` and `COMMIT`, and the conflict happened outside every transaction in the system. This is a different problem from the lost update in 6.5a, and it needs a different mechanism.

The obvious fix is to make the gap transactional — open a transaction when Dana loads the form, take a lock, hold it until she saves. That works exactly once before you notice what it costs: a database connection pinned for eight minutes per open form (5.2b), locks held for as long as somebody leaves a tab open, and a row that stays locked until a pool timeout when Dana closes her laptop instead of clicking save. Pessimistic locking across human time is not available at any price.

And a third shape, which looks unrelated and turns out to be the same subject. A nightly job updates `merchants` then `orders`; an API request updates `orders` then `merchants`. Under low traffic they never meet. Under load:

```
  ERROR: deadlock detected
  DETAIL: Process 8821 waits for ShareLock on transaction 41902; blocked by process 7734.
          Process 7734 waits for ShareLock on transaction 41905; blocked by process 8821.
```

One of them is killed. The bug isn't in either piece of code — it's in the relationship between them.

So: three failures, one subject. **When two writers can touch the same thing, something has to decide who wins, and the choice is where that decision happens** — before the read, at the write, or not at all.

## What It Is

**Pessimistic locking** assumes conflict is likely: take a lock before reading, hold it until commit, and make the second writer wait. `SELECT … FOR UPDATE` is the whole idea. The lock's lifetime is the transaction's lifetime — which is the property that makes it powerful inside a request and unusable across one.

**Optimistic concurrency control** assumes conflict is rare: read freely, and at write time verify that nothing changed since you read. Usually a version column, checked in the `WHERE` clause. Nothing is locked at any point, which is why "optimistic locking" is a misleading name that we're all stuck with — it's *conflict detection*, not locking, and that's exactly why it works across an eight-minute gap where no transaction exists.

**Advisory locks** are mutual exclusion on an arbitrary identifier rather than on a row, for coordinating work that isn't a row: one instance of a cron job, one import per tenant, one migration at a time.

Two disambiguations.

**This is not a replacement for 6.5a.** Isolation levels govern what happens inside a transaction. These mechanisms are how you make the decision explicit — and optimistic concurrency reaches somewhere isolation structurally cannot, which is across requests.

**A lock in your database is not the same as a lock in Redis.** A row lock and the data it protects share a fate: if the transaction dies, the lock dies, and the write doesn't happen. A lease held in another system has no such relationship — the lease can expire while your process is in a garbage-collection pause, after which two processes both believe they hold it and both write. The mitigation is a monotonically increasing fencing token that the storage layer checks, which is the same idea as a version column. If the thing you're protecting is rows in a database that has locks, use the database's locks.

## Recognizing the Problem

- Tickets that say a change "disappeared" or "reverted," with no error anywhere.
- Two users can edit the same record and the second save silently wins.
- `deadlock detected` in the logs, appearing under load and not in staging.
- Sessions sitting `idle in transaction` holding row locks for minutes.
- Lock wait timeouts, or queries whose *execution* time is fine and whose *response* time isn't (6.4b).
- One popular entity — a large merchant, a shared counter, a global settings row — has terrible write latency while everything else is fine.
- A scheduled job occasionally runs twice because two instances started it.
- A mobile client caches a record for an hour and then PUTs the whole thing back.
- A "last modified by" field that regularly names the wrong person.

## How It Works

### Pessimistic: the lock lives as long as the transaction

```sql
BEGIN;
SELECT * FROM inventory WHERE sku = 'A-19' FOR UPDATE;   -- others now wait here
-- decide
UPDATE inventory SET reserved = reserved + 1 WHERE sku = 'A-19';
COMMIT;                                                   -- lock released
```

The row-level modes are worth knowing by name because the wrong one blocks more than you intended:

- `FOR UPDATE` — the strongest. Blocks other `FOR UPDATE`, `FOR SHARE`, and any update or delete of the row.
- `FOR NO KEY UPDATE` — weaker, and what a plain `UPDATE` to a non-key column takes. Doesn't block foreign-key checks from child rows, which removes a surprisingly common source of blocking.
- `FOR SHARE` — several readers can hold it; writers wait. Easy to deadlock with if two holders both later want to upgrade.

Two modifiers change the failure mode rather than the semantics:

- `NOWAIT` — error immediately instead of queueing. Turns an invisible wait into a handled error, which pairs with the `lock_timeout` argument from 6.3b.
- `SKIP LOCKED` — skip rows someone else has locked and return the rest. This is how you build a job queue on a relational database: each worker claims rows nobody else has claimed, with no coordination and no contention.

```sql
-- N workers, no coordination, no duplicate delivery
UPDATE jobs SET status = 'running'
 WHERE id IN (SELECT id FROM jobs WHERE status = 'queued'
               ORDER BY priority, id
                 FOR UPDATE SKIP LOCKED
               LIMIT 10)
RETURNING *;
```

`SKIP LOCKED` changes what your query *means* — you no longer see a consistent set of matching rows — which is the point for a queue and wrong for anything reporting a total.

### Optimistic: verify at write time

```sql
UPDATE clients
   SET address = $1, version = version + 1
 WHERE id = $2 AND version = $3;
```

If the affected row count is one, you had the current version and now you don't. If it's zero, somebody else wrote between your read and your write, and the correct response is to tell the caller — not to retry blindly, because a blind retry re-applies the stale payload and you're back to Tuesday.

The version has to travel the whole way to whoever made the decision. In HTTP that's already a standard: the `GET` returns an `ETag`, the `PUT` sends `If-Match`, and a mismatch is `412 Precondition Failed` (Module 7). Any client that doesn't send it back gets last-write-wins, so the check is only as good as its weakest caller.

Three notes on the version column itself:

- **Use an integer, not `updated_at`.** Timestamps have precision limits, bulk updates that touch them for unrelated reasons, and clocks that disagree. An integer that only this mechanism increments has none of those properties.
- **`RETURNING version`** saves the client a round trip and lets a form stay open for a second edit.
- **Zero affected rows is ambiguous** — conflict, or the row was deleted. If the difference matters to the caller, follow up with an existence check.

And the part that gets skipped: **what happens on conflict is a product decision, not a technical one.** Reject and reload is the cheapest and is correct for most CRUD. Field-level merge — accept both edits because they touched different columns — is friendlier and much more work, and can produce a combined state neither person intended. Real collaborative editing needs operational transforms or CRDTs and is a different discipline entirely (Module 9). Pick one deliberately before shipping the version column, because "409 Conflict" with no UI behind it just moves the confusion.

### Deadlocks

```
   T1                              T2
   locks  merchants(7) ─────┐      locks  orders(88) ─────┐
   wants  orders(88) ←──────┼──────────────────────────────┘
                            └──────→ wants merchants(7)
```

A cycle. The database detects it, picks a victim, and aborts it with SQLSTATE `40P01`. The system is not broken; it just discovered that these two transactions cannot both proceed.

Three things fix deadlocks, in order of effectiveness:

1. **Acquire locks in a consistent order.** Sort the ids before locking them. Two transactions that both lock in ascending id order can queue but cannot cycle. This one rule removes most application-level deadlocks.
2. **Shorten the transaction.** Fewer locks held for less time is fewer chances to interleave.
3. **Lock one coarser thing instead of several fine ones** — the parent row, or an advisory lock representing the operation.

Some deadlocks come from locks you never wrote: foreign key checks taking locks on parent rows, unique-index conflicts during concurrent `INSERT … ON CONFLICT`, and index page contention. `SHOW ENGINE INNODB STATUS` on MySQL and the `DETAIL` line in Postgres's log tell you which statements were involved; both are the first place to look, and both are frequently the first time anyone realizes an `UPDATE` on a child row touched the parent.

### Contention is the ceiling that survives every correct answer

Suppose you get all of this right. Every writer to a hot row now serializes, by design:

```
   maximum writes/sec on one row  =  1 / (lock hold time)

   hold 50 ms (includes an API call inside the transaction)  →    20 /s
   hold  5 ms                                                →   200 /s
   hold  0.5 ms (single statement, no round trip)            → 2,000 /s
```

No hardware changes this. The only levers are: shorten the critical section (do everything that isn't the write outside it), split the row (sharded counters, 6.2a), coalesce writes (batch a hundred increments into one), or remove the concurrency by routing all writes for that entity through a single consumer (Module 10).

Notice the first line of that table. A network call inside a transaction is not merely poor style — it sets a throughput ceiling for every other writer to that row.

## When It's Appropriate

**Pessimistic** when the critical section is short, entirely server-side, and conflicts are likely:

- Consuming work: queue claims, `SKIP LOCKED`, exactly-once handoff.
- Allocating scarce things: the last unit of stock, a seat, a sequence number.
- Anywhere the work between read and write has side effects that make a retry expensive.

**Optimistic** when the gap spans requests, or conflicts are rare:

- Any form a human fills in. This is the only available mechanism, not a preference.
- Read-heavy systems with many actors who rarely touch the same entity.
- APIs where the client holds state — mobile apps, offline-capable clients, anything with a cache.

**Advisory** when the thing to serialize isn't a row: one instance of a nightly job, one import per tenant, one migration runner.

The crossover rule of thumb: **if two writers collide on the same entity more than a few percent of the time, optimistic retries become the dominant cost and pessimistic is cheaper.** Below that, optimistic wins because it holds nothing and scales without coordination.

## When It's Unnecessary or Overkill

- **Locking around a single-statement update.** A compare-and-set with the precondition in the `WHERE` (6.5a) is simpler and safe at Read Committed.
- **Version columns on entities only one actor ever writes** — a webhook-populated record, an append-only log table.
- **`SELECT … FOR UPDATE` on a read path**, which blocks writers to serve a report.
- **Holding any lock across a network call or user think time.**
- **A distributed lock service in front of a database that has locks.**
- **Table locks to avoid reasoning about row locks.** It works and it ends throughput.
- **Building merge UI** for two fields nobody ever edits simultaneously. Ship the 409 and see whether anyone hits it.

## Trade-offs

**Pessimistic locks make lock waits part of your latency, and lock waits are invisible in most measurements.** The query's execution time is unchanged; the time spent waiting to start it isn't attributed anywhere unless you look for it (6.4b). They also require a lock-acquisition discipline across the whole codebase — one function that locks in a different order reintroduces deadlocks for everybody.

**`SKIP LOCKED` changes query semantics,** and a report that accidentally inherits it silently omits rows.

**Optimistic concurrency wastes work on conflict,** and the waste is proportional to how long the user spent before the collision — potentially eight minutes of typing.

**The version has to be carried end to end,** through the API, the form, the mobile client, and every integration. A single caller that ignores it restores last-write-wins for everyone, silently. This is the most common way optimistic locking is implemented and doesn't work.

**Zero affected rows must be checked.** An `UPDATE` that matched nothing is not an error in SQL; it's a successful statement. Code that doesn't inspect the row count has the version column and none of the protection.

**Field-level merging can synthesize states nobody chose,** combining Dana's street with Priya's postcode into an address that doesn't exist.

**Advisory locks aren't attached to data,** so nothing forces a new code path to take one — the protection is a convention. Session-scoped ones are worse: on a pooled connection they outlive the request and get inherited by whoever gets that connection next. Use the transaction-scoped variant unless you have a specific reason not to.

**Deadlock retries need the same discipline as serialization retries** (6.5a): whole transaction, bounded, jittered, no side effects inside.

**And every correct answer keeps the contention ceiling.** Correctness gets you to one writer at a time on the hot entity; throughput after that is arithmetic.

## Alternatives

- **Constraints and compare-and-set** (6.5a). Always the first question; a `UNIQUE` index beats every mechanism here for the problems it covers.
- **Serializable isolation**, when the conflict lives inside one transaction and can't be expressed as a constraint.
- **Single-writer-per-entity.** Route all writes for an entity through one queue partition and concurrency stops existing for that key — no locks, no versions, at the cost of an asynchronous write path.
- **Append-only with expected version** (2.4): the version check *is* the storage model, and the conflict is detected by the append failing.
- **CRDTs and operational transformation** for genuinely concurrent collaborative editing (Module 9), where the goal is that neither edit is rejected.
- **Leases with fencing tokens** when mutual exclusion genuinely has to span systems.
- **Sharded counters** (6.2a) and batching, to remove the hot row rather than protect it.
- **Idempotency keys** for the duplicate that isn't a race at all — the same request submitted twice.

## How to Achieve It

1. **Locate the gap.** Between the read that informed the decision and the write that acts on it — how long is it, and does a transaction span it? Inside a transaction, 6.5a's tools apply. Across requests, optimistic concurrency is the only option.
2. **Estimate the conflict rate.** How often do two writers touch the same entity within the gap? This one number chooses between the two mechanisms.
3. **Rare, or cross-request → version column,** carried through the API as `ETag`/`If-Match`, with the affected-row-count check and a decided conflict behaviour.
4. **Likely, short, server-side → `FOR UPDATE`,** with a deterministic acquisition order, a `lock_timeout`, and everything that isn't the write moved outside the transaction.
5. **Not a row → transaction-scoped advisory lock.**
6. **Sort your ids before locking them.** Cheapest deadlock prevention available.
7. **Measure lock wait time and deadlock counts** as first-class metrics, not log lines.
8. **Decide the conflict UX before shipping the mechanism.**

## Implementation

Go, because the decisive part of optimistic concurrency is a return value that's easy to ignore, and explicit code makes it unignorable.

The write:

```go
const q = `UPDATE clients
              SET address = $1, version = version + 1, updated_at = now()
            WHERE id = $2 AND version = $3
        RETURNING version`

var newVersion int
err := db.QueryRowContext(ctx, q, addr, id, expectedVersion).Scan(&newVersion)

switch {
case errors.Is(err, sql.ErrNoRows):
    return ErrConflict          // someone wrote between their GET and this PUT
case err != nil:
    return err
}
```

Using `RETURNING` plus `QueryRow` rather than `Exec` is a small choice with a large effect: a conflict becomes `sql.ErrNoRows`, which the compiler's error handling pushes you to deal with. The `Exec` version returns `(0, nil)` — a successful statement that did nothing — and a codebase where nobody checks `RowsAffected` has a version column and no protection at all.

The HTTP end, where the version becomes the client's problem:

```go
func getClient(w http.ResponseWriter, r *http.Request) {
    c := load(r.Context(), id)
    w.Header().Set("ETag", fmt.Sprintf(`"%d"`, c.Version))
    writeJSON(w, c)
}

func putClient(w http.ResponseWriter, r *http.Request) {
    match := r.Header.Get("If-Match")
    if match == "" {
        http.Error(w, "If-Match required", http.StatusBadRequest)   // no silent fallback
        return
    }
    // … parse version out of match, call the update …
    if errors.Is(err, ErrConflict) {
        http.Error(w, "the record changed since you loaded it", http.StatusPreconditionFailed)
        return
    }
}
```

Rejecting a `PUT` with no `If-Match` is the decision that makes this real. The tempting alternative — treat a missing header as "no expectation" — means one forgetful client, one integration script, or one retry from a mobile app restores last-write-wins for everybody, and it will be the code path nobody tested.

For the server-side case, the lock, with the deadlock prevention on the line where it belongs:

```go
// Lock in a deterministic order. Sorting here is the whole fix.
sort.Slice(ids, func(i, j int) bool { return ids[i] < ids[j] })

tx, _ := db.BeginTx(ctx, nil)
defer tx.Rollback()

_, err = tx.ExecContext(ctx, `SET LOCAL lock_timeout = '2s'`)
for _, id := range ids {
    if _, err := tx.ExecContext(ctx,
        `SELECT 1 FROM accounts WHERE id = $1 FOR NO KEY UPDATE`, id); err != nil {
        return err       // 55P03 lock_not_available: fail fast rather than queue
    }
}
// … short critical section, no network calls …
return tx.Commit()
```

`FOR NO KEY UPDATE` rather than `FOR UPDATE` because nothing here changes a key, and the weaker mode lets foreign-key checks on child rows proceed instead of queueing behind it. `SET LOCAL lock_timeout` for the reason 6.3b gave: a bounded failure beats an unbounded wait, and on a hot row an unbounded wait is how one slow transaction becomes a pool outage.

And when the thing being protected isn't a row at all:

```go
// One importer per tenant, across every instance. Released automatically at commit.
_, err = tx.ExecContext(ctx, `SELECT pg_advisory_xact_lock($1, $2)`, importNamespace, tenantID)
```

The two-argument form gives you a namespace, which matters because advisory lock keys are a single global integer space shared by every feature in your application — and a collision between two unrelated subsystems is a bug that will take a very long day to find.

## Further Reading

- **_Patterns of Enterprise Application Architecture_, Martin Fowler** — Optimistic Offline Lock, Pessimistic Offline Lock, and Coarse-Grained Lock. This article's contents, named and analysed, from before any of these frameworks existed. The "offline" in the names is exactly the eight-minute gap.
- **PostgreSQL documentation, chapter 13.3 "Explicit Locking."** The full row-lock mode conflict table, the deadlock section (which states the consistent-ordering rule plainly), and the advisory lock functions with the session-versus-transaction distinction.
- **PostgreSQL documentation on `SELECT … FOR UPDATE SKIP LOCKED`,** and any of the several good write-ups on building a job queue with it. The cleanest demonstration that changing lock behaviour changes query semantics.
- **MySQL Reference Manual, "InnoDB Locking" and "Deadlocks in InnoDB,"** including how to read `SHOW ENGINE INNODB STATUS`. Necessary if you work on MySQL, because the lock set taken by a plain `UPDATE` is larger than most people expect.
- **"How to do distributed locking," Martin Kleppmann.** The Redlock critique and the fencing-token argument — the clearest statement of why a lock in one system doesn't protect data in another.
- **RFC 9110, sections on `ETag`, `If-Match`, and `412 Precondition Failed`.** Optimistic concurrency was standardized in HTTP decades ago; most APIs reimplement a worse version of it in a JSON field.
- **Hibernate documentation on optimistic and pessimistic locking** — `@Version`, `LockModeType`, and `OPTIMISTIC_FORCE_INCREMENT`, which is the mechanism for the case where a child's change must invalidate a parent's version.

A **Java** sibling would be worth writing for one specific reason: JPA implements all of this, and in doing so hides the failure. `@Version` adds the predicate and the increment to every update automatically, which is excellent — and it means the protection silently does not apply to native queries, bulk `UPDATE` statements, or anything written by another service against the same table. The conflict arrives as an `OptimisticLockException` thrown at *flush* time, which may be well after the line of code that caused it, inside a transaction that is now rollback-only. Add `LockModeType.PESSIMISTIC_WRITE` and the interaction between the persistence context's cached entity and a row someone else has since changed, and there's an article's worth of behaviour that has no visible presence in the code. Not yet written.

---

The habit: **find the gap.** Between the read that informed a decision and the write that acts on it, ask how long the interval is and whether a transaction spans it. Milliseconds inside one transaction is an isolation question. Minutes across two requests is a version-column question. Nothing else about the problem changes the answer as much as that one measurement.

And once it's correct, remember what correctness bought: one writer at a time on the contended thing. Everything after that is arithmetic on how long each one holds it.
