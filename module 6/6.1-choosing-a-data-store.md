# Choosing a Data Store

_Module 6.1 — Database Design & Data Management_

## The Problem

You're building a delivery-logistics product. Merchants place orders, drivers pick them up, everyone watches a map.

Someone asks which database to use, and the discussion that follows is about databases. Postgres is boring and safe. Mongo is flexible. Cassandra scales. Everyone uses Elastic for search. Ninety minutes later the decision is made by whoever spoke last with the most conviction, and it's written down as if it were one decision.

It can't be answered in that form, because *the application* doesn't have a workload. Its individual operations do, and they don't resemble each other. Six from the same product:

| # | Operation | Shape |
|---|---|---|
| 1 | Load driver 8842's profile and today's assignment | one known key, 12k/s, budget under 5 ms |
| 2 | "Pending orders for merchant M this week, by promised time" | filters change every sprint, must be exact |
| 3 | 20,000 vehicles report position every 5 seconds | 4k writes/s, append-only, never updated, worthless after 90 days |
| 4 | "Late deliveries per city per hour, last quarter" | scans ~2 billion rows, runs 40×/day |
| 5 | "that thai place on mill street" | fuzzy, ranked, typo-tolerant |
| 6 | Merchant suspended → cancel pending orders, refund, notify | three tables, all-or-nothing |

No engine is good at all six, and the reasons are structural rather than a matter of tuning. #6 wants a transaction across several records. #4 wants to read one column of two billion rows and none of the others. #3 wants to append and never seek. #5 wants a term-frequency index and a relevance model, which is a different data structure, not a different query.

So the obvious correction is six stores, one per shape. Now look at the bill for that: six backup-and-restore procedures, six upgrade paths, six sets of credentials, six on-call runbooks, six re-implementations of your tenant isolation boundary — and, structurally, **no join and no transaction between any pair of them**, forever. Plus a new class of bug you didn't have before, where the same fact disagrees with itself depending on which store you ask.

Both conclusions are wrong because the real question isn't *which store*, it's *in what order*. All six of those patterns run acceptably on one Postgres at the start. They stop at different, reasonably predictable points:

```
        one Postgres, and roughly where each pattern gives out

#1 key lookup    ──────────────────────────────────────────▶  fine indefinitely
#2 ad-hoc filter ──────────────────────────────────────────▶  fine indefinitely (this is what it's for)
#6 transaction   ──────────────────────────────────────────▶  fine indefinitely (nothing does it better)
#5 search        ─────────────────▶ when ranking, typos, and synonyms start mattering
#3 telemetry     ──────────▶ when retention becomes a DELETE that never finishes
#4 analytics     ────▶ when the scan and the checkout path fight over the same buffer cache
                 ↑
                 you are here, with four customers
```

That ordering is the actual content of the decision. The question worth asking is: **which access patterns must this store serve, what does it cost me while it's merely adequate at them, and what does adding a second store cost?**

## What It Is

Picking a data store is choosing which access patterns get first-class support and which get tolerated. Three pieces of vocabulary, because the rest of the article leans on them.

**System of record vs. derived store.** The system of record holds a fact authoritatively; a derived store holds a copy shaped for a particular query and can be thrown away and rebuilt from the system of record. The same physical Elasticsearch cluster can be either, and which one it is has nothing to do with the software and everything to do with whether anything writes to it that isn't a copy. This distinction does more work than any other in this article.

**Polyglot persistence** is the name for deliberately using several stores, each for what it's good at. It is a real strategy and it is also the most over-applied idea in this module.

**OLTP vs. OLAP.** Transactional workloads: many small operations, each touching a few records, latency-sensitive. Analytical workloads: few large operations, each touching a few columns of an enormous number of records, throughput-sensitive. This axis decides more about storage engine design than anything else.

One neighbour worth separating immediately: **"NoSQL" is not a category.** Redis, MongoDB, Cassandra, Neo4j and Elasticsearch have essentially nothing in common except a negation of a query language, and treating them as one bucket is why "should we use NoSQL?" is an unanswerable question. Whether the interface is SQL matters far less than the four engine-level choices in *How It Works* below — and note that several "NoSQL" systems now speak SQL, and Postgres has stored and indexed JSON documents for a decade. The label stopped tracking anything real a while ago.

## Recognizing the Problem

Signals that the store genuinely doesn't fit the pattern:

- You've read the query plan, the index is being used, and it's still reading 40 million rows — because the answer genuinely depends on 40 million rows.
- Your dashboard query and your checkout query visibly interfere. One of them is always the victim.
- You're storing trigrams in a table and hand-computing a relevance score.
- Retention is implemented as a `DELETE` that takes longer to run than the interval it runs on.
- One table is 85% of your storage, is never updated after insert, and dominates every backup.
- A query traverses "connections of connections of connections" where the number of levels is a runtime parameter, so the SQL has to be generated.
- Writes exceed what one primary can commit, and you've already batched and already checked the disk.
- Your largest column is a 4 MB PDF.

Signals you have a *different* problem, and a new store would just carry it somewhere else:

- The slow endpoint issues 600 queries (Module 6.4).
- The table has no index on the column you filter by.
- Every request opens a connection (Module 5.4b).
- The query is fast and the endpoint is slow.
- One report is slow and it runs twice a day.
- You have 40 GB of data and a performance problem. At 40 GB the problem is essentially never the engine.

That second list is most of the cases. The strongest predictor that someone should *not* change stores is that they can't name the specific query, its frequency, and its current latency.

## How It Works

Engines differ in strengths because they made different choices in four places. You can predict most of what a store is good and bad at from these, which is more durable than memorizing product comparisons.

**1. How records sit on disk.**

```
   row-oriented                         column-oriented
   ────────────────────────             ─────────────────────────────
   [ 1 | SF | 410 | ok   ]              id:     [ 1 , 2 , 3 , 4 … ]
   [ 2 | SF | 980 | late ]              city:   [ SF, SF, LA, NY … ]  ← one scan, one column,
   [ 3 | LA | 220 | ok   ]              ms:     [410, 980, 220 … ]      compresses ~10×
   [ 4 | NY | 130 | ok   ]              status: [ ok, late, ok … ]

   read one order:  1 page               read one order: 4 seeks
   average ms:      read everything      average ms:     read one array
```

Operation #1 and operation #4 want opposite physical layouts. No amount of indexing reconciles that, which is why analytical databases are a separate product category rather than a setting.

**2. How writes land.** A B-tree finds the right page and modifies it in place: random I/O, excellent for reads and updates, and the write cost grows with the number of indexes. An LSM tree appends to an in-memory table, flushes sorted files, and merges them in the background: writes become sequential and cheap, at the cost of reads touching several files and of compaction competing with your live traffic for I/O. Operation #3 — append-only, never updated — is the LSM shape precisely.

**3. What the index can answer.** A B-tree answers equality, range, and ordering on its key prefix. An inverted index maps term → documents plus per-term statistics, which is what relevance ranking and typo tolerance are computed from; you cannot derive ranking from a B-tree. An adjacency list stores each node's neighbours next to the node, so a hop is a pointer dereference instead of a join against an ever-growing edge table. An ANN index answers "nearest in vector space," approximately, which is a different question from any of the above.

**4. How it's distributed.** A single-leader system routes all writes through one node: transactions spanning anything are straightforward, and write throughput is capped by one machine. A partitioned or leaderless system scales writes horizontally, but atomicity and ordering exist only *within* a partition — anything crossing one becomes your problem. Operation #6 lives on one side of this and operation #3 on the other.

Every product is one point in that space. The families:

| Family | Layout | Writes | Index | Distribution | Exists for |
|---|---|---|---|---|---|
| Relational (Postgres, MySQL) | row | B-tree | B-tree, GIN, GiST | single leader | arbitrary queries over related records, with constraints and transactions |
| Document (MongoDB) | row (as docs) | B-tree/LSM | B-tree | partitioned | one aggregate read and written as a unit |
| Key-value (Redis, DynamoDB) | row | memory/LSM | hash | partitioned | known-key access at very high rate |
| Wide-column (Cassandra, Scylla) | row, partitioned | LSM | partition + clustering key | leaderless | huge write volume, known queries, multi-region writes |
| Search (Elasticsearch, OpenSearch) | documents | segments | inverted | partitioned | relevance, fuzziness, facets |
| Time-series (Timescale, Influx, Prometheus) | column-ish, chunked | append | time + tags | varies | append, range scan, downsample, expire |
| Columnar / OLAP (ClickHouse, BigQuery, DuckDB) | column | batch append | sparse/zone maps | partitioned | aggregate a few columns of billions of rows |
| Graph (Neo4j) | nodes + adjacency | B-tree | adjacency | mostly single leader | variable-depth traversal |
| Vector (pgvector, Qdrant, Pinecone) | row/column + index | varies | ANN graph | varies | semantic similarity (Module 39) |
| Object storage (S3, GCS) | blobs | append | key prefix | partitioned | bytes measured in megabytes |

Five places where the summary above hides a trap worth naming:

**Document stores are aggregate stores.** The real question isn't schema flexibility, it's whether your data has one dominant access path. If an order is always read and written whole, embedding line items inside it is genuinely better than five tables and a join. If half your queries want "all line items containing SKU X across all orders," you've embedded the data inside the wrong boundary and every such query is a collection scan. "Schemaless" is the marketing; there is always a schema, and the choice is whether it lives in the database or, undocumented, in every read path in your application plus six years of accumulated shape variants.

**Wide-column stores require you to design tables per query.** This is the part teams learn late. You don't model entities and then query them; you enumerate your queries and create a table for each, with the partition key chosen so that one query reads one partition:

```sql
-- not "the orders table" — one table per question you intend to ask
CREATE TABLE orders_by_merchant (
  merchant_id  uuid,
  promised_at  timestamp,
  order_id     uuid,
  status       text,
  PRIMARY KEY ((merchant_id), promised_at, order_id)
) WITH CLUSTERING ORDER BY (promised_at DESC);
```

Denormalized duplicates of the same order live in several such tables, kept consistent by your application. That's the actual trade: enormous write throughput and linear scaling, paid for with no ad-hoc queries, no joins, and no cross-table atomicity. Adopting it because "we might need to scale" while your product still discovers new query shapes every sprint is buying the bill without the benefit.

**A search index is a derived store, not a system of record.** Its consistency model, its restore story, and its data-loss behaviour are all fine for a rebuildable copy and unacceptable for the only copy. The day someone stores the canonical order status only in the index is the day the search cluster's reindex procedure becomes a data-loss event. Module 12 covers the search side properly.

**Graph databases are for variable-depth traversal specifically.** Two or three fixed hops is a join, and Postgres does joins well; recursive CTEs handle a surprising amount of genuinely recursive work. The case that actually breaks SQL is when depth is unbounded or data-dependent — shortest path, reachability, fraud rings — because the query must join a table to itself an unknown number of times, and each level multiplies the intermediate result.

**Redis's durability is a configuration decision you're making whether you know it or not.** Default persistence settings can lose the last seconds of writes on a crash, and eviction policies can silently discard keys under memory pressure (5.2a met that one as random logouts). Perfect for a cache. Read the persistence chapter before it holds anything you can't recompute.

## When It's Appropriate

Adding a specialized store earns its place when a specific access pattern has outgrown the general one. Rough thresholds, not laws:

- **Search.** You need relevance ranking, typo tolerance, synonyms, per-language analyzers, or facet counts across millions of documents. Postgres full-text search is genuinely good below that line and is one fewer system.
- **Analytics.** Dashboard queries scan more than ~100 million rows, or — often more urgent than volume — they need to stop competing with transactional traffic for the same cache and I/O. A columnar store is routinely 10–100× faster here, because it reads four columns instead of forty.
- **Time-series.** Sustained ingest in the tens of thousands of points per second, retention expressed as policy rather than as a `DELETE`, and queries that are always "this range, downsampled." A Postgres extension covers a lot of this without a new server.
- **Key-value.** Sub-millisecond reads of data you can recompute, at a rate that would otherwise dominate your primary's connection budget (Module 13).
- **Wide-column.** Write volume beyond a single primary, or genuine multi-region active-active writes, combined with a query set you can enumerate in advance and won't renegotiate.
- **Graph.** Depth is a runtime parameter.
- **Object storage.** Anything over a few hundred kilobytes of opaque bytes. Large blobs in rows bloat every backup, every replica, and every buffer cache in the system, to no benefit (Module 11).

The version of this that's easiest to justify and hardest to regret: **the second store serves a workload that was already isolated by nature** — reporting, search, telemetry — so a few seconds of staleness is invisible and a failure degrades one feature instead of the product.

## When It's Unnecessary or Overkill

- **Choosing for a scale you don't have.** Cassandra for 50 GB, Kafka-plus-ClickHouse for a dashboard four people open. You pay the modeling constraints immediately and collect the benefit hypothetically.
- **Adding a store to fix something an index fixes.** The most common version of this article's failure mode, and the most expensive relative to its cause.
- **Choosing by benchmark.** Published numbers measure a workload that is not yours on hardware that is not yours with a working set that fits in RAM. They reliably predict the winner of the benchmark.
- **Letting a service boundary pick your engine.** "Each service owns its database" is about ownership, not about variety. Four services that all want relational data should run four schemas on the same engine.
- **Underestimating what one Postgres now does.** JSONB documents with indexes, full-text search, `pgvector` for embeddings, PostGIS for geospatial, native partitioning, logical replication, and `SELECT … FOR UPDATE SKIP LOCKED`, which is a perfectly good job queue (Module 10). None of these is best-in-class. Being adequate at all of them inside one transaction, one backup, and one set of credentials beats being excellent at one of them in a separate system, until it measurably doesn't.
- **Ignoring who operates it.** Self-hosting a distributed store means someone understands its repair, compaction, rebalancing, and split-brain behaviour at 3am. With a small team, "is there a managed version we'd actually pay for?" belongs in the selection criteria, not after it.

## Trade-offs

The cost of the store you chose, and of each one after it.

**Cross-store atomicity does not exist.** The moment there are two stores, every operation touching both can half-succeed. There is no transaction to reach for, and the correct designs (idempotent retries, outbox, reconciliation) all exist because the easy one is unavailable. This is the dominant cost and it never goes away.

**Cross-store joins move into your application,** where they become a loop over the network with no query planner, no statistics, and no index the optimizer can choose. A join that Postgres does in 4 ms becomes 200 round trips.

**Staleness becomes a product decision.** "The order you just created doesn't appear in search for two seconds" has to be handled in the interface, not just tolerated in the backend. Someone will file it as a bug every few months forever.

**Operations multiply, and not linearly.** Backups, restores, version upgrades, certificate rotation, capacity planning, monitoring, and the runbook for each. Note especially that **your isolation boundary is per-store**: row-level security in Postgres (5.2a) means nothing to Elasticsearch, which has its own model, so the tenant predicate must be re-established — correctly — in every store you add.

**Restores stop lining up.** Recovering Postgres to 09:14 doesn't recover the search index to 09:14. After any real incident the stores disagree, and the only clean answer is rebuilding the derived ones from the system of record — which is only an answer if you've ever actually done it (Module 6.6).

**Testing and local development get heavier.** Every store is another container in CI, another fixture format, another thing that's flaky on someone's laptop. This tax is small per instance and genuinely demoralizing in aggregate.

**Reversibility is asymmetric.** Adding a *derived* store is nearly free to undo — stop writing to it, delete it. Moving a *system of record* is a months-long dual-write, backfill, shadow-read, and cutover project. These two decisions get discussed in the same meeting as though they carried the same risk, and they don't.

## Alternatives

Before a second store, in rough order of effort:

- **Fix the schema or the index** (6.2, 6.4). Most "we need a different database" conclusions die here honourably.
- **Materialized views or summary tables** in the same database. Precomputed aggregates on a refresh schedule solve a large share of "the dashboard is slow" without a new engine or a new consistency story.
- **A read replica.** The cheapest workload isolation available: analytics runs against a replica and stops evicting your transactional pages, using the same engine, the same SQL, and the same backups. The staleness is measured in milliseconds rather than seconds.
- **An extension rather than a server.** Timescale, pgvector, PostGIS, `pg_trgm`. Same connection, same transaction, same backup.
- **A cache** (Module 13), for the pattern where the problem is read rate rather than query shape.
- **An embedded engine.** SQLite, DuckDB, Bleve — a library, not an operational component. DuckDB reading Parquet handles analytical workloads that used to require a cluster, and nobody gets paged for it.
- **The managed version of your existing engine**, if the real problem was "nobody wants to own this."

## How to Achieve It

The path that keeps each step reversible:

**0. Name the pattern.** Which query, how often, what latency now, what latency needed, what's the actual data volume. Without these four numbers the rest is preference.

**1. Fix it in place.** Index, denormalized column, materialized view, partition. Cheap, no new failure mode. Move on when the fix would require an index that meaningfully slows every write, or when the query shape isn't expressible at all.

**2. Isolate it.** Read replica. No new consistency model, no new operational surface. Move on when the problem is the engine's shape, not contention.

**3. Add a derived store, read-only.** The new store is a projection. The system of record doesn't move. Nothing writes to it except the projector, and it can be dropped and rebuilt. This is where you can be wrong cheaply, which is the whole point of doing it in this order.

**4. Keep it fresh without dual writes.** Covered below.

**5. Move a system of record.** Rarely, and only when the primary is the bottleneck for *writes*. Dual-write, backfill, shadow-read with comparison, cut over one read path at a time. Budget months.

One rule holds the whole thing together: **every derived store must be reconstructible from the system of record by a script you have actually run.** Not a script you believe would work. If you can't rebuild it, then some fact lives only there, it's a second system of record, and you didn't decide that — you drifted into it.

```
        ┌──────────────────┐
        │ system of record │  ← every fact has exactly one home
        │    (Postgres)    │
        └────────┬─────────┘
                 │ outbox / CDC, asynchronous, replayable
      ┌──────────┼──────────┐
      ▼          ▼          ▼
   search    analytics    cache        ← all rebuildable, none authoritative
```

## Implementation

Java, for a reason specific to the language: Spring's `@Transactional` makes a non-transactional call look transactional, and this is the exact spot where teams lose data while reading code that appears to be correct.

```java
@Transactional
public Order place(NewOrder cmd) {
    Order order = orderRepository.save(Order.from(cmd));   // Postgres
    searchClient.index("orders", order.id(), toDoc(order)); // Elasticsearch
    return order;
}
```

Everything inside the annotation *looks* covered by one unit of work. One of those two lines is not a database call at all.

Three failures, all of them ordinary Tuesdays:

- The index call succeeds; a constraint violation later in the transaction rolls Postgres back. Elasticsearch has a document for an order that does not exist. Nothing will ever remove it, because the cleanup path also rolled back.
- The index call throws because the cluster is briefly unavailable. The transaction rolls back, so the *order the customer placed* is lost because the search cluster had a bad minute. A search outage just became a checkout outage.
- The transaction commits and the process is killed before the index call returns. The order exists and is unsearchable, permanently, with no record that it's missing.

There's also a quieter problem worth naming: an HTTP call is now inside the transaction, so a database connection is held for the duration of a network round trip to a different system. That's the connection-slot arithmetic from 5.2b, arriving from an unexpected direction — a slow search cluster drains the pool and takes down endpoints that never touch search.

The near-fix most teams reach for is moving the index call after commit:

```java
@TransactionalEventListener(phase = AFTER_COMMIT)
public void onOrderPlaced(OrderPlaced event) { … }
```

Better — no phantom documents, no rollback caused by a search outage — but it still loses events, because "after commit" runs in your process's memory and your process can die at any instant. It converts a frequent, visible failure into a rare, invisible one.

The durable version writes the intent to the same database, in the same transaction:

```java
@Transactional
public Order place(NewOrder cmd) {
    Order order = orderRepository.save(Order.from(cmd));
    outbox.save(new OutboxRecord(
        "order", order.id(), "placed", json(order), order.version()));
    return order;                       // one commit, both rows, or neither
}
```

A separate relay reads unprocessed outbox rows, pushes them to the derived store, and marks them done. Two properties make that safe:

- **Delivery is at-least-once,** so the projector must be idempotent. Sending the entity version and letting the index reject older versions is the usual way; blindly indexing is how an old snapshot overwrites a new one after a retry.
- **Ordering only matters per entity,** and the entity id gives you that for free — which is why the outbox row carries `("order", id)` rather than a global sequence you'd then have to preserve.

This is the transactional outbox pattern, and it's the mechanism behind step 4 above. The alternative — reading the database's replication log directly with change data capture — removes the application-side write entirely at the cost of an infrastructure component; Modules 37 and 38 cover both properly.

## Further Reading

- **_Designing Data-Intensive Applications_, Martin Kleppmann** — chapter 3 is the long version of this article's *How It Works*: B-trees versus LSM trees, row versus column layout, and why each one implies what it implies. Chapters 5 and 6 cover the distribution axis.
- **PostgreSQL documentation:** the JSON types and indexing chapter, full text search, table partitioning, and `SELECT … FOR UPDATE SKIP LOCKED` in the SELECT reference. Worth reading specifically to calibrate how much of the polyglot argument still applies.
- **Cassandra's data modeling documentation** — the query-first methodology stated plainly by the people who built it. Reading it is the fastest way to find out whether you want it.
- **ClickHouse's MergeTree documentation** — sparse indexes, part merges, and why "no updates" is the price of the scan speed.
- **Elasticsearch's guide to relevance scoring and analyzers** — the clearest demonstration that search is a different data structure rather than a faster `LIKE`.
- **Jepsen's analyses** (jepsen.io) — independent testing of what distributed stores actually guarantee versus what their documentation claims. Read the one covering any store you're seriously considering.
- **Debezium documentation** — change data capture in practice, and the operational obligations that come with it.
- **"Choose Boring Technology," Dan McKinley** — the innovation-token framing. The best short argument for why the third store needs a much stronger case than the second.

A **Go** sibling would show something this one structurally cannot. Without an annotation, the transaction is a variable you carry: `tx` is passed explicitly, `defer tx.Rollback()` sits at the top, and the commit is a line you can point at. The dual-write bug becomes visible on the page — the search call is plainly on one side or the other of `tx.Commit()`, and no framework is implying otherwise. The interesting content is the inverse risk: nothing prevents a function from taking `*sql.DB` instead of `*sql.Tx` and quietly escaping the transaction, which is a mistake Spring's proxying makes for you and Go lets you make by hand. Not yet written.

---

The habit worth carrying out of this article: **before naming any store, name the access pattern and its four numbers** — shape, rate, volume, latency budget. Almost every bad database decision is made in units where those numbers don't appear, which is why it can't be argued with and can't be checked afterwards.

And the shorter version, for reviewing an architecture someone else drew: count the systems of record. Every fact should have exactly one home you can point to. Everything else is a copy, and every copy needs a rebuild procedure that someone has run.
