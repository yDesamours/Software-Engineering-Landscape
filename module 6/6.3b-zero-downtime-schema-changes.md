# Zero-Downtime Schema Changes

_Module 6.3b — Database Design & Data Management_

## The Problem

The migration is three words long and adds a nullable column:

```sql
ALTER TABLE orders ADD COLUMN notes text;
```

On a modern Postgres this is a metadata change. It touches no rows, rewrites nothing, and takes about two milliseconds. It ran at 14:32, and by 14:32:04 the entire product was down.

```
14:29:10   analytics SELECT on orders begins (a 7-minute query)
           └─ holds ACCESS SHARE on orders

14:32:00   ALTER TABLE orders ADD COLUMN notes text
           └─ needs ACCESS EXCLUSIVE → conflicts → waits

14:32:00   every subsequent query on orders
           └─ queues BEHIND the waiting ALTER, because lock requests are FIFO

14:32:04   connection pool exhausted; endpoints that never touch orders
           start timing out too                                      (5.2b)

14:36:10   analytics query finishes
14:36:10   ALTER acquires the lock, runs in 2 ms, commits
14:36:10   4,000 queued queries stampede
```

Nothing in that timeline is a bug. The `ALTER` behaved exactly as documented, the analytics query was a legitimate report, and the outage lasted seven minutes for a two-millisecond statement.

The mechanism is the part worth internalizing: **a lock request that is waiting blocks everything queued behind it.** A brief exclusive lock is harmless. A brief exclusive lock that can't be acquired is a full outage on that table for as long as whatever is ahead of it runs — and then the pileup has to drain.

That's failure mode one: *waiting for a lock.* There are two more.

**Holding a lock.** Some statements really do take minutes. `ALTER TABLE … ALTER COLUMN id TYPE bigint` rewrites every row in the table while holding the exclusive lock the whole time. Here no amount of queue management helps; the table is unavailable for forty minutes because that's how long the work takes.

**Moving too much data.** The backfill that goes with a schema change:

```sql
UPDATE orders SET notes = '' WHERE notes IS NULL;   -- 200 million rows
```

One transaction, four hours, 300 GB of write-ahead log, replication lag in the tens of minutes, every updated row leaving a dead tuple behind for autovacuum to find later — and if the deploy pipeline's timeout kills it at hour three, all of it rolls back and nothing has happened.

Three distinct problems that get filed under one heading. The rest of this article is the defence against each, and they're different defences.

## What It Is

A zero-downtime schema change is one where **no statement is blocked for longer than the application can absorb.** Note what that is and isn't measuring.

`CREATE INDEX CONCURRENTLY` on a large table runs for four hours and is a zero-downtime operation, because it never blocks reads or writes. The two-millisecond `ALTER` above was a seven-minute outage. **The quantity that matters is lock duration, not statement duration**, and confusing the two is why migrations that "took 200 ms" show up in incident reviews.

The vocabulary, kept to what's needed:

- **Lock modes.** Reads take `ACCESS SHARE`. Writes take `ROW EXCLUSIVE`. Ordinary DDL takes `ACCESS EXCLUSIVE`, which conflicts with everything including reads. A few operations take `SHARE UPDATE EXCLUSIVE`, which conflicts with other DDL and with vacuum but *not* with reads or writes — that middle mode is what "concurrently" means.
- **Metadata-only versus rewrite.** Whether the statement changes a catalog entry or visits every row. This is version- and engine-specific and is the thing to look up rather than assume.
- **`NOT VALID`.** Adding a constraint that applies to new rows immediately and to existing rows only when you later validate it, under a weaker lock.

This article is written against Postgres, because its lock model is explicit and documented. MySQL differs in the details — `ALGORITHM=INSTANT` covers a growing set of operations, `INPLACE` avoids the full copy, `COPY` doesn't — but its metadata locks queue the same way, so the shape of failure mode one is identical.

## Recognizing the Problem

The signature of a lock problem, as distinct from the application-level failures in 6.3a: **nothing errors, everything hangs.** Specifically:

- A deploy occasionally produces a few minutes of total unavailability on one table, with timeouts rather than error messages.
- `pg_stat_activity` during the event shows one DDL statement in `ActiveLockWait` and hundreds of ordinary queries waiting behind it.
- The outage reaches endpoints that don't use the table, because the pool drained.
- A migration that took 40 ms in staging took 35 minutes in production. Staging's table has 1,200 rows.
- The pipeline killed a migration halfway and the database shows no trace of it having run.
- Replication lag spikes during every deploy.
- Disk usage and autovacuum activity jump after a migration and stay elevated for a day.
- You have long-running reports, exports, or `idle in transaction` sessions on the same tables you change — that last one is the usual culprit, and it's frequently a pooled connection that opened a transaction and then made an HTTP call.

## How It Works

### The lock queue

```
   orders

   holder:   [ analytics SELECT ]  ACCESS SHARE            running, 7 min

   queue:    [ ALTER TABLE ]       ACCESS EXCLUSIVE  ──┐   waiting
             [ SELECT … ]          ACCESS SHARE        │   waiting
             [ UPDATE … ]          ROW EXCLUSIVE       │   waiting   ← these do not
             [ SELECT … ]          ACCESS SHARE        │   waiting     conflict with
             …4,000 more                               │              the holder at all
                                                        └── they conflict with
                                                            the waiter
```

The queued `SELECT`s are compatible with the running one. They wait anyway, because granting them would starve the exclusive request forever. This is the correct design and it means the practical rule is inverted from intuition: **don't optimize how long you hold the lock; make sure you never wait for it.**

The defence is one line, and it's the single highest-value thing in this article:

```sql
SET lock_timeout = '2s';
```

Now the `ALTER` gives up after two seconds instead of queueing indefinitely, the pileup never forms, and the failure is a failed migration rather than an outage. Then retry — most of the time the long query has finished and the second attempt takes its two milliseconds.

### What actually rewrites the table

Failure mode two is about picking the right form of the statement. The specifics move between versions, so the durable skill is knowing which questions to look up; the current Postgres answers:

| Operation | Cost |
|---|---|
| `ADD COLUMN` nullable, or with a constant default | metadata only |
| `ADD COLUMN … DEFAULT` with a *volatile* expression | full rewrite |
| `DROP COLUMN` | metadata only (space reclaimed by vacuum later) |
| `varchar(50)` → `varchar(100)`, `varchar` → `text` | metadata only |
| `int` → `bigint`, most other type changes | full rewrite, exclusive lock throughout |
| `SET NOT NULL` | full scan under exclusive lock — unless a validated `CHECK (col IS NOT NULL)` already exists, which lets it skip |
| `ADD FOREIGN KEY` | scans the whole child table — unless added `NOT VALID` first |
| `ADD UNIQUE` / `ADD PRIMARY KEY` | builds an index under exclusive lock — unless built `CONCURRENTLY` first and adopted |
| `CREATE INDEX` | exclusive-ish: blocks writes for the whole build |
| `CREATE INDEX CONCURRENTLY` | weak lock, ~2× slower, safe |

The pattern across the bottom half of that table is the same trick every time: **split the operation into a cheap lock and an expensive scan, and take them separately.**

```sql
-- adding a foreign key without blocking anything
ALTER TABLE orders ADD CONSTRAINT fk_merchant
  FOREIGN KEY (merchant_id) REFERENCES merchants(id) NOT VALID;   -- brief lock
ALTER TABLE orders VALIDATE CONSTRAINT fk_merchant;               -- long, weak lock
```

```sql
-- adding NOT NULL without a blocking scan
ALTER TABLE orders ADD CONSTRAINT orders_notes_nn
  CHECK (notes IS NOT NULL) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_notes_nn;
ALTER TABLE orders ALTER COLUMN notes SET NOT NULL;   -- sees the validated check, skips the scan
ALTER TABLE orders DROP CONSTRAINT orders_notes_nn;
```

```sql
-- adding a unique constraint without a blocking index build
CREATE UNIQUE INDEX CONCURRENTLY orders_ref_uq ON orders (reference);
ALTER TABLE orders ADD CONSTRAINT orders_ref_uq UNIQUE USING INDEX orders_ref_uq;
```

`CONCURRENTLY` has its own rules, which surprise people mid-migration: it cannot run inside a transaction block — so your migration tool must support non-transactional migrations — it takes roughly twice as long, it waits for all transactions older than it to finish before each of its two passes, and **if it fails it leaves behind an `INVALID` index** that is maintained on every write and used by nothing. Dropping that index is a step someone has to remember.

### Backfills

Failure mode three is not a DDL problem at all; it's a long-running write, and it gets designed like one. Five properties:

- **Batched by primary key range, committed per batch.** Not one transaction. Each batch is short enough to be killed harmlessly.
- **Resumable.** The job will be restarted — by a deploy, a node eviction, or a person. Where it got to belongs in a table, not in memory.
- **Idempotent.** Re-running a batch must be free, which usually means the predicate excludes already-migrated rows.
- **Throttled by a real signal** — replication lag or an error budget — not a fixed sleep. Fixed sleeps are either too slow at 03:00 or too fast at 14:00.
- **Separate from the migration.** It runs after the deploy, on its own schedule, for as long as it needs. Putting it in a migration script guarantees the pipeline timeout finds it.

A detail that catches people: `UPDATE … WHERE notes IS NULL` with some kind of limit looks like batching and isn't. Each iteration scans from the beginning looking for unmigrated rows, and the scan gets longer as the job progresses — the classic accidentally-quadratic backfill. Range over the primary key instead, which is the keyset pattern from 6.2b applied to writes.

## When It's Appropriate

- **`lock_timeout` plus retry: always.** It costs nothing, it's one line, and it's the difference between a failed deploy and an incident. There is no table small enough to justify skipping it.
- **`CONCURRENTLY` and the split forms: on any table where a minute of blocked writes matters.** Roughly, tables with real traffic and more than a few million rows.
- **A batched backfill job: when the row count times the per-row cost exceeds a few seconds.** Below that, one `UPDATE` in the migration is correct and simpler.
- **Shadow-table tooling (gh-ost, `pt-online-schema-change`, `pg_repack`): when the operation genuinely requires a rewrite** — a type change on a large table, a primary key change, reclaiming space — and the table is too big to be unavailable for it.

And the honest counter-case: if the product is used by one time zone during business hours, a Sunday maintenance window removes most of this article. Say that out loud instead of performing zero-downtime ceremony nobody needs.

## When It's Unnecessary or Overkill

- **`CONCURRENTLY` on small tables.** Plain `CREATE INDEX` on 50,000 rows is 200 ms. The concurrent version is slower, can't be transactional, and can leave an invalid index — all costs, no benefit.
- **Shadow-table tooling for a metadata-only change.** Copying 400 GB to add a nullable column is a real thing that happens when a team adopts a tool as a policy instead of as a technique.
- **A backfill framework for 50,000 rows.**
- **Banning DDL during business hours** as a policy, when `lock_timeout` addresses the actual risk and the policy just batches twelve changes into one risky release.
- **Splitting a constraint into `NOT VALID` plus `VALIDATE`** on a table where the scan takes 40 ms.

## Trade-offs

**`lock_timeout` converts an outage into a failed deploy** — which is the right trade, and it isn't free. If the table always has a long-running query on it, the migration never succeeds, and you now need a story: cancel the blocking query, schedule the migration for a quieter period, or fix the report. Retrying forever with no alert just means the migration silently never ran.

**`CONCURRENTLY` builds are slower, non-transactional, and fail in a state that needs cleanup.** They're also still blocked by very long transactions — the index build waits for older transactions to finish, so an `idle in transaction` session stalls it indefinitely without ever conflicting on a lock in a way that's visible.

**`NOT VALID` constraints aren't enforced for existing rows until validated,** and the planner can't rely on them until then. If you never run the `VALIDATE`, you have a constraint that documents an invariant your data may violate.

**Backfills mean the system runs in a mixed state for hours or days** — half the rows migrated, both code paths live (6.3a). Every query written during that window has to tolerate both.

**Backfills generate garbage.** An update touching 200 million rows leaves 200 million dead tuples, which autovacuum must clean up, which competes with production I/O, and the table's disk usage stays elevated until it does. Lowering `fillfactor` beforehand helps updates stay on-page; nothing makes it free.

**Shadow-table tools double the disk requirement,** add trigger or binlog overhead on every write during the copy, take a brief exclusive lock at the rename, and have known rough edges around foreign keys. They solve a real problem and are not a default.

**All of this makes migrations non-atomic.** The history table records a migration as applied or not; reality is "the index is built, the constraint is not validated, and the backfill is 60% done." Your deploy state and your schema state have become different things, and someone has to track the second one.

## Alternatives

- **A maintenance window.** Legitimate, cheap, and often the right call for the shape of business you actually have.
- **Do the rewrite on a copy and switch.** Logical replication to a new instance with the new schema, then fail over — which is how managed blue/green database deployments work, and the standard answer for major version upgrades and unavoidable table rewrites.
- **Online schema-change tools** — gh-ost and `pt-online-schema-change` for MySQL, `pg_repack` for reclaiming space in Postgres, `pgroll` and Reshape for automating expand/contract behind views.
- **Avoid the ALTER entirely.** A new table with the desired shape, dual-written and swapped, is expand/contract at the table level (6.3a) and sometimes simpler than fighting a type change in place.
- **Partition first** (6.2c), so operations apply to chunks. Note the limit: DDL on the parent still needs a lock across partitions, but the per-partition work is bounded and can be done piecemeal.
- **Enforce the constraint in the application instead.** A real option with the real cost that application-level invariants are eventually violated by the one code path that forgot. Reasonable as a temporary state, poor as a destination.

## How to Achieve It

1. **Classify the statement before writing it:** metadata-only, rewrite, or scan. Check the documentation for your engine and version rather than repeating folklore — several of these answers changed in the last few releases.
2. **Set `lock_timeout` on every migration,** globally in the tool if possible, with a retry loop and backoff, and an alert after N failures.
3. **Check for long transactions before deploying.** A query against `pg_stat_activity` for transactions older than a minute, run as a pre-flight step, turns a coin flip into a decision.
4. **Use the split forms** — `CONCURRENTLY`, `NOT VALID` then `VALIDATE`, `CHECK` then `SET NOT NULL` — on anything large.
5. **Move backfills into jobs**: keyset-ranged, committed per batch, resumable, idempotent, throttled on replication lag.
6. **Test against a restored production-sized copy**, and measure *lock duration*, not wall-clock time.
7. **Know who cancels what.** `pg_cancel_backend` stops a query; `pg_terminate_backend` kills the connection. Decide in advance which one someone is allowed to run at 14:34, and on what.

## Implementation

TypeScript, continuing the backfill as the same seek pattern 6.2b used for pagination — because that's what it is.

First the wrapper every migration should have:

```ts
async function withLockTimeout(sql, ddl: string, attempts = 10) {
  for (let i = 0; i < attempts; i++) {
    try {
      await sql.begin(async (tx) => {
        await tx`SET LOCAL lock_timeout = '2s'`;
        await tx.unsafe(ddl);
      });
      return;
    } catch (e) {
      if (e.code !== '55P03') throw e;          // not a lock timeout
      await sleep(Math.min(2 ** i, 60) * 1000); // back off, try again
    }
  }
  throw new Error(`could not acquire lock for: ${ddl}`);
}
```

Three things about that are deliberate.

`SET LOCAL` scopes the timeout to this transaction, so it can't leak into unrelated work on a pooled connection — the same reasoning as the tenant context in 5.2a, for the same reason.

The retry gives up rather than escalating. After ten attempts across a few minutes, something is durably in the way, and the correct response is a human looking at `pg_stat_activity`, not a more aggressive lock request.

And it throws. A migration that quietly fails ten times and reports success is worse than the outage it avoided.

Now the backfill:

```ts
async function backfill(sql, batchSize = 5_000) {
  let cursor = await loadCursor(sql);           // resumable across restarts

  while (true) {
    const [row] = await sql`
      WITH batch AS (
        SELECT id FROM orders
         WHERE id > ${cursor}
         ORDER BY id
         LIMIT ${batchSize}
      )
      UPDATE orders o
         SET full_name = o.name
        FROM batch
       WHERE o.id = batch.id
         AND o.full_name IS NULL
      RETURNING (SELECT max(id) FROM batch) AS last_id`;

    if (!row?.last_id) break;                   // reached the end
    cursor = row.last_id;
    await saveCursor(sql, cursor);

    await throttle(sql);
  }
}

async function throttle(sql) {
  const [{ lag }] = await sql`
    SELECT coalesce(max(replay_lag), '0s') AS lag FROM pg_stat_replication`;
  if (lag > SECONDS(5)) await sleep(2_000);
}
```

The properties that make it survivable, each of which is one line above:

**The range comes from the primary key, not the predicate.** `WHERE full_name IS NULL LIMIT 5000` looks equivalent and degrades quadratically — every iteration rescans the rows it already migrated looking for the next unmigrated one. Ranging on `id` means each batch starts exactly where the last stopped.

**The cursor advances even when a batch updates nothing.** Rows already having `full_name` are skipped by the `AND` but still consumed by the range, so the job moves forward through them instead of retrying them. This is also what makes re-running the whole job from zero harmless.

**Each batch is its own transaction,** so a kill at any moment loses at most one batch, and no single transaction accumulates enough dead tuples or WAL to matter.

**The throttle reads a signal rather than sleeping a constant.** At 03:00 it runs flat out; at 14:00 it backs off exactly as much as the replicas require. If you have no replicas, throttle on whatever does hurt — checkpoint frequency, p99 write latency, or the error budget for the endpoints on that table.

The remaining decision is batch size, and it should be bounded by *time*, not rows: measure how long a batch takes and tune until it's under a second or so. Five thousand narrow rows and five thousand rows containing a 2 MB JSON document are very different transactions.

## Further Reading

- **PostgreSQL documentation, "Explicit Locking."** The lock conflict matrix, which is the source of everything in this article, plus the paragraph on lock queuing that explains the opening incident in two sentences. Read alongside the `ALTER TABLE` notes section, which states per-operation whether a rewrite occurs.
- **PostgreSQL documentation on `CREATE INDEX CONCURRENTLY`** — the two-pass algorithm, the transaction-block restriction, and what an `INVALID` index means.
- **"PostgreSQL at Scale: Database Schema Changes Without Downtime," Braintree.** The canonical public catalogue of safe and unsafe operations with the safe rewrite for each.
- **The `strong_migrations` README** (Ruby, but read it for the catalogue). Each entry names a dangerous statement, why it's dangerous, and the decomposed form — the most convenient reference of its kind regardless of your stack.
- **gh-ost documentation, particularly the design and cut-over pages.** Triggerless online schema change by tailing the binlog, and a genuinely interesting treatment of how to make the final rename atomic.
- **MySQL Reference Manual, "Online DDL Operations."** The per-operation table of which algorithm applies, which is MySQL's version of the rewrite table above.
- **`pgroll` documentation.** Expand/contract automated through versioned views, so old and new application versions each see a schema shaped for them — the most interesting current attempt at making 6.3a's six steps mechanical.

A **Java** sibling would cover the part this article assumes away: that your migration tool cooperates. Flyway wraps each migration in a transaction by default, which makes `CREATE INDEX CONCURRENTLY` fail outright until the migration is marked non-transactional, and Liquibase needs `runInTransaction="false"` on the changeset for the same reason. Both need care to apply `lock_timeout` — per-migration rather than per-connection — and Liquibase's own changelog lock interacts with a stalled migration in a way that requires manual clearing. Concrete, ubiquitous, and entirely absent from the SQL. Not yet written.

---

The habit: **before running any DDL, ask what the longest-running transaction on that table is right now.** Not what the statement costs — what's ahead of it in the queue. That single question would have prevented the opening incident, and it's answerable with one query against `pg_stat_activity` that takes three seconds.

And the sentence to carry into every migration review: a schema change is judged by how long it holds a lock, how long it waits for one, and how much data it moves — three separate numbers, three separate defences, and a plan that only addresses one of them isn't a plan.
