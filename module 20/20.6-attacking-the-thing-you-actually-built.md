# Attacking the Thing You Actually Built

_Module 20.6 — Security Best Practices_

## The Problem

A team does everything the last five articles asked. They threat-modeled the design (20.5) and caught the gift-card race. They parameterize and encode (20.2). CSRF tokens, security headers, the works. Code review is thorough, SAST runs in CI, dependency scanning is green. By every internal measure, this is a secure application.

Then they hire a security firm for a pre-launch assessment, because an enterprise customer's contract requires one. The tester spends four days. The report has eleven findings. The team recognizes none of them, and the reason is instructive — each one lived in a gap *between* the things they'd checked:

- The staging environment had a debug endpoint the production config was supposed to disable. The config was right in the repo; it was wrong on the actual server, and no code review reads the running server.
- The CDN in front of the app cached a page with a user-specific CSRF token, so under load, user B occasionally got user A's token. Every component was correct in isolation; the *composition* leaked.
- The password-reset flow, threat-modeled and clean, chained with an unrelated open-redirect on the marketing subdomain to produce an account-takeover neither flaw could achieve alone.
- A third-party analytics script, added after the threat model, loaded from a domain that had since been abandoned and re-registered — supply chain, but the runtime kind that no manifest scan catches.

Not one of these is a coding bug. Not one is a design flaw in any single component. They are **integration bugs, configuration drift, and emergent interactions** — vulnerabilities that exist only in the assembled, deployed, running system, and therefore cannot be found by looking at the design, the code, or the dependencies in isolation.

```
   what each technique examines            what it structurally cannot see
   ──────────────────────────────          ───────────────────────────────────
   threat model → the DESIGN               config drift, integration bugs, the
   code review / SAST → the CODE             gap between "the repo" and "the box"
   dependency scan → the MANIFEST          the running system as an assembled,
                                             deployed, composed whole
   ──────────────────────────────          ───────────────────────────────────
   attacking the running system            ← this, and only this, finds those
```

There is a category of vulnerability that only appears when you attack the thing you actually built, in the place you actually deployed it. Finding it requires doing exactly that.

## What It Is

This article covers a spectrum of techniques that share one defining move: **they test the running system by attacking it**, rather than by reading its design, code, or dependencies. From most automated to most human:

- **Vulnerability scanning (DAST — Dynamic Application Security Testing).** Automated tools that crawl and probe a running application, sending malformed inputs, testing for known vulnerability patterns, and flagging misconfigurations. Fast, cheap, repeatable, shallow.
- **Penetration testing.** A skilled human (or team) attempts to compromise the system as an adversary would — chaining flaws, testing business logic, using judgment a scanner lacks. Slow, expensive, deep, time-boxed.
- **Bug bounties.** A standing, open invitation for external researchers to find and report vulnerabilities for a reward. Continuous, diverse, unpredictable, adversarially incentivized.
- **Red teaming.** A goal-driven simulation of a real attacker ("exfiltrate customer data") that tests not just the application but detection and response — people and process, not only code. The most realistic and the most expensive.

The unifying name for the philosophy is **offensive security** or **black/grey-box testing**: you learn what's exploitable by trying to exploit it, on the real artifact.

The disambiguation that matters most, and the through-line from 20.5: these are the **third leg** of a stool, and the legs find different bugs.

```
  DESIGN-time     threat modeling (20.5)   → flaws in the idea
  BUILD-time      SAST, code review,       → flaws in the code &
                  dependency scanning         its declared dependencies
  RUN-time        DAST, pentest, bounty    → flaws in the composed,
                  (THIS ARTICLE)              deployed, running whole
```

None substitutes for another. A team with a pentest and no threat model ships design flaws the pentester happened not to try. A team with a threat model and no pentest ships the config drift the model couldn't predict. The gift-card bug (20.5) was cheapest to catch at design time; the CDN-token-caching bug in the Problem *could only* be caught at run time. Different bugs, different stages, and the mature answer is all three.

## Recognizing the Problem

You need run-time security testing — and are exposed without it — when:

- **Your security evidence is entirely design-time and build-time.** Green SAST, a threat model, and no one has ever attacked the deployed system.
- **The production environment differs from what's in the repo** in any way — and it always does. Config, secrets, infrastructure, CDN, load balancer, feature flags: none of it is in the code review.
- **Components are correct individually but compose in ways no one has tested** — a cache in front of personalized content, an auth proxy plus an app that also checks auth, two services that each assume the other validated something.
- **A contract, compliance regime, or enterprise customer requires it** (SOC 2, PCI-DSS, a security questionnaire with a "last pentest date" field). This is how most teams first encounter it, and the requirement is usually a proxy for a real gap.
- **You've shipped significant new attack surface** since the last time anyone tested — a new public API, a file-upload feature, a third-party integration.
- **You have no idea what an outsider sees.** You've never looked at your own system from the position of someone with no credentials and hostile intent.
- **"Has anyone tried to break this?" has the answer "no."**

## How It Works

### The automated end: scanners find the shallow, tirelessly

DAST tools work by treating the app as a black box: crawl every reachable URL, then for each input, send payloads that reveal known vulnerability classes — an injection probe, an XSS string, a traversal sequence — and watch the response for the tell-tale signature. Alongside them, **SCA** (software composition analysis) checks running dependencies against CVE databases, and infrastructure/config scanners check the deployed environment against hardening baselines.

Their value is coverage and tirelessness: a scanner tests every endpoint every night without getting bored, and catches the regressions a human would only find on the next expensive engagement. Their limit is that they find only what they have a pattern for. A scanner detects reflected XSS because reflected XSS has a signature; it cannot detect that your gift card can be double-redeemed, because "double-redeemed" isn't a pattern — it's a fact about *your* business logic that the tool has no way to know is wrong.

```
  a scanner is a metal detector on a beach:
    finds every buried coin (known patterns), tirelessly, cheaply
    walks straight past the drowning swimmer (the logic flaw it has
      no pattern for) — because it was never looking for one
```

This is the same buyable/unbuyable split from 20.1, now applied to *testing*: scanners cover the convergent, pattern-matchable vulnerabilities well and the design-specific ones not at all.

### The human end: pentesters find the deep, but only what they try

A penetration test is a human doing what a scanner can't: reasoning about *your* application's logic, chaining several low-severity issues into one high-severity exploit, and using intuition about where developers cut corners. The Problem's account-takeover — password reset chained with a marketing-subdomain open redirect — is the archetype: two findings a scanner would rate "informational" separately, combined by a human who asked "what can I do with *both*?"

The mechanism is worth understanding because it explains the technique's fundamental limitation. A pentest is:

- **Scoped.** It covers what the engagement defined — often not the whole system, and rarely the parts added after it started.
- **Time-boxed.** The tester has days or weeks. A real attacker has as long as they want. Anything the tester didn't reach in the window is untested, not proven safe.
- **A sample of one (team's) imagination.** The tester finds the attacks *they* think to try. A different tester finds a different set. Neither finds all of them, because "all of them" is unbounded.

Which produces the single most important idea in this article:

### Absence of findings is not evidence of security

A clean pentest report does not mean the system is secure. It means *this tester, in this window, within this scope, did not find a way in.* The set of vulnerabilities a test *didn't* find is invisible and unbounded — you cannot measure it, and a passing report is routinely misread as a security certificate.

```
   found by the test    ┌───────────────┐
                         │ ● ● ●         │  ← what the report lists
                         │               │
   NOT found, exists     │        ○  ○   │  ← invisible. unmeasured.
                         │   ○         ○ │     not zero. the report
                         │      ○        │     says nothing about these.
                         └───────────────┘
   the report describes the left dots. it is silent about the right circles,
   and their number is unknown — including "the ones the NEXT tester will find."
```

This is why "we passed our pentest" is the 20.1 checklist error in its most seductive form: a genuine, expensive, skilled assessment, mistaken for proof of a property it cannot establish. A pentest raises your confidence; it never reaches certainty, and treating it as a pass/fail gate teaches everyone to optimize for a clean report rather than a secure system.

### The continuous end: bounties turn "one tester, once" into "many, always"

A bug bounty attacks the time-box and single-imagination limits directly: instead of one team for two weeks, an open population of researchers, continuously, each with different skills and incentives, each paid only for real findings. It's the closest thing to "many attackers, all the time" you can buy on purpose.

Its trade is that you've invited the world to attack your production system and committed to triaging whatever comes back — including a flood of low-quality reports, duplicate findings, and the operational reality that you now have a *public* channel through which people demonstrate they've compromised you. A bounty is a sign of maturity precisely because it presupposes you can already handle the other end: fast triage, fast fixes, and a system hardened enough that the signal-to-noise is worth it. Running a bounty on an untested app just pays strangers to find the bugs your first scanner would have.

### The loop that makes any of it worth it

The finding is worthless until it changes something. Every technique here produces the same artifact — a vulnerability — and the same obligation: triage by real severity (not the scanner's CVSS guess, which doesn't know your context), fix or formally accept, and then **close the class, not just the instance.** A pentester found one endpoint missing an authorization check; the fix is not just that endpoint but the test that asserts *every* endpoint has one (20.1's L3). Otherwise you pay a pentester every year to re-find the same category, which is the most common way security spending produces motion without progress.

## When It's Appropriate

- **Automated scanning (DAST/SCA): continuously, in CI/CD, for everyone.** It's cheap and catches regressions and known-pattern issues nightly. There's no reason not to, and it's the run-time equivalent of the linters in Module 3 — a gate that shifts discovery earlier.
- **A penetration test: before a major launch, after significant new attack surface, and on the cadence a contract demands** (usually annual for compliance). The high-value moments are the same design inflection points as 20.5, one stage later — a new public API, a new auth path, a new way tenants' data can touch.
- **A bug bounty: once you're mature enough to feed it** — fast triage, fast fixes, a system already past the low-hanging fruit. Start with a private, invite-only program before going public.
- **Red teaming: when you have a security program to test, not just an app** — detection, response, and people. Overkill until there's a blue team for the red team to test against.
- **Whenever the honest answer to "has an adversary examined our running system?" is no,** and the system holds anything worth taking.

## When It's Unnecessary or Overkill

- **A pentest of a prototype or pre-launch spike** that will be rewritten. Test the real thing; attacking a throwaway wastes the budget on findings that evaporate.
- **A bug bounty before you can handle findings.** Inviting the world to attack a system you can't yet triage or fix fast produces public embarrassment and a backlog, not security. This is the most common bounty mistake.
- **Red teaming with no detection to test.** If you have no monitoring or response capability (Module 19), a red team just re-confirms you have none — a scanner and a pentest tell you that far more cheaply.
- **Treating an annual pentest as the whole security program.** The once-a-year assessment that finds issues, most of which are still open at the next one, is compliance theatre. The point is the fix loop, not the report.
- **Paying for a manual pentest of things a scanner covers.** Don't spend human-tester hours on reflected XSS a DAST tool finds in seconds; scope the humans onto the logic and the chains only a human can find.
- **A scanner's raw output as a to-do list.** DAST tools produce false positives copiously; shipping the unfiltered report to engineers as "fix all of these" burns trust and time. Triage first.

## Trade-offs

- **Scanners cost false positives; humans cost money and time.** The automated end floods you with noise you must filter; the human end is expensive, slow, and available only in windows. There is no cheap-fast-deep option — you're always trading two of the three.
- **A clean report creates false confidence, which is worse than no report.** The most dangerous outcome of a pentest is a team that now believes it's secure. Absence of findings is unmeasured, and the confidence it produces is unearned — a genuine cultural cost, not just an epistemic footnote.
- **Point-in-time testing goes stale the moment you deploy.** A pentest describes the system as it was during the engagement. The next deploy can introduce the very bug that was just cleared. This is why continuous scanning matters and why the annual-pentest-only model is so weak — it's a photograph of a moving thing.
- **You're attacking your own production system (or a staging clone that's never quite identical).** Testing against production risks real impact; testing against staging risks missing the config drift that *is* the bug (the Problem's debug endpoint). Neither choice is clean, and the difference between the two environments is itself an untested surface.
- **Bounties and pentests give outsiders a map of your weaknesses.** You are paying people to document how to compromise you, and that document exists. Handling it — disclosure timelines, fix windows, the researcher who goes public early — is operational overhead the finding itself doesn't include.
- **Findings without a fix loop are pure cost.** The entire value is in the remediation, and remediation competes with feature work every time. A drawer full of unremediated pentest reports is a liability (you're now on record as having known), not an asset.

## Alternatives

These techniques complement more than they compete, but the choices trade off against each other and against the other two legs:

- **Shift left (the other two legs).** The cheapest vulnerability is the one caught at design (20.5) or in code review before it ships. Run-time testing is the most expensive place to find a bug — it's already built and deployed. The alternative to *relying* on pentests is investing in the earlier stages so the pentest finds less. Best treated as "and," not "or": strong design and build practices make the run-time testing cheaper and its findings rarer and more interesting.
- **Purple teaming** — red and blue working together rather than adversarially. Cheaper and more educational than a pure red team, trading the realism of a genuine surprise attack for faster knowledge transfer to the defenders.
- **Automated-only, no humans.** For a low-risk app, continuous DAST/SCA plus the build-time legs may be a defensible whole program. You forgo the logic-flaw and chaining findings only a human gets — an honest choice for a to-do list app, a negligent one for a payments system.
- **Managed detection & response (MDR/SOC) instead of testing.** Investing in *catching* attacks rather than *pre-finding* holes. Different philosophy — assume-breach, detect-and-respond — and a complement, not a replacement: detection tells you when you're being attacked; testing tells you how you'd be attacked. Mature programs run both.
- **Compliance-driven testing as the floor.** Letting SOC 2 / PCI / ISO dictate the cadence. Fine as a *minimum* and a forcing function; dangerous as the *definition*, because the compliance calendar optimizes for the auditor's checkbox, not your actual attack surface (20.1's checklist trap, at the program level).

## How to Achieve It

There's no code here — the "implementation" is an engagement and a loop — so what's worth making concrete is the maturity path, because teams routinely start at the wrong end (an expensive pentest of an app riddled with findings a free scanner would have caught).

```
  L0  You have never looked at your running system as an attacker would.
        First move: run a free scanner (OWASP ZAP) against staging. The
        output is noisy and shallow and will still surprise you.

  L1  DAST + SCA in CI, triaged. A scan on every deploy, false positives
        filtered, real findings ticketed. Now the shallow, known-pattern
        bugs are caught continuously, and a human test won't waste its
        window on them.  Signal to move on: the scanner is quiet and you're
        still unsure about your logic and composition.

  L2  A scoped penetration test, at a real inflection point (pre-launch,
        new major surface). Scope it onto the business logic and the
        integrations — the things the scanner can't see. Feed every finding
        into the class-closing fix loop, not just the instance.
        Signal: a contract asks for it, or you've shipped major new surface.

  L3  Continuous external testing — a private bug bounty — once triage and
        fix velocity can feed it. Widen to public only when the signal is
        worth the noise.  Signal: pentests keep coming back mostly clean and
        you want coverage between them.

  L4  Red / purple teaming, testing detection and response, not just the
        app. Presupposes a blue team exists to be tested.
```

Two rules cut across the ladder. **Never buy human hours for what a scanner finds** — scope people onto what only people find. And **the finding is not the product; the fixed class is** — a program measured by findings-produced is measuring the wrong thing, because the number that matters is how few the *next* test finds.

## Further Reading

- **The OWASP Web Security Testing Guide (WSTG).** The comprehensive methodology for testing a running web app — what to test and how — useful both for running your own assessments and for judging the quality of a vendor's.
- **OWASP ZAP** (and Burp Suite). The free and the industry-standard interception/scanning tools; running ZAP against your own staging is the cheapest possible L0 and genuinely instructive about what your app exposes.
- **The Penetration Testing Execution Standard (PTES).** The phases of a professional engagement (scoping, intelligence, exploitation, reporting) — read it before commissioning a pentest so you can write a good scope and read the report critically.
- **`disclose.io` and a `security.txt` file** (RFC 9116). The standard for a coordinated vulnerability disclosure policy — the thing you need *before* a researcher finds a bug, so there's a defined channel that isn't Twitter.
- **The Building Security In Maturity Model (BSIMM)** and **OWASP SAMM.** Where run-time testing fits in a whole software-security program, for when the question grows from "should we pentest?" to "what should our security function look like?"
- Within this map: threat modeling and the three-legged-stool framing in **20.5**; the checklist-vs-thinking and buyable/unbuyable splits in **20.1**; SAST, linters, and CI gates in **Module 3 and 31**; dependency and supply-chain scanning in **Module 3.3**; the detection-and-response half in **Module 19 and 24**; and the class-closing test pattern in **20.1's** maturity ladder.

---

The habit to carry out of this article, and it's the counterweight to the whole module: **you do not know your system is secure; at best you know no one has found it insecure yet, in the time they had, within what they thought to try.** Every prior article told you how to build defenses. This one tells you to attack them, on the real artifact, and then reminds you that a quiet result is a measurement with enormous error bars, not a verdict. The teams that stay secure aren't the ones with the cleanest pentest report — they're the ones who treat every clean report as a question about what the *next* attacker will find, and spend accordingly.
