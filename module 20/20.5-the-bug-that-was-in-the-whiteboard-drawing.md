# The Bug That Was in the Whiteboard Drawing

_Module 20.5 — Security Best Practices_

## The Problem

A team builds a "gift card" feature. The design is clean. A card has a code and a balance. Redeeming applies the balance to an order. The code is checked server-side, the balance is decremented in a transaction, everything is parameterized, the endpoints have CSRF tokens and rate limits, the headers score an A. Every article in this module so far has been obeyed.

Three weeks after launch, the balance sheet is wrong. Someone figured out that the "check balance" endpoint and the "redeem" endpoint are separate calls, and that redemption doesn't re-verify the balance it read a moment earlier. They open two tabs, redeem the same $500 card against two orders in the same instant, and both succeed — the balance was $500 when each read it. Then they script it: one card, forty simultaneous redemptions, $20,000 of merchandise. No injection. No stolen session. No missing header. No CVE. Every request was authenticated, authorized, validated, and logged. The system did exactly what it was built to do. **It was built wrong.**

Look at what would have caught it, and what wouldn't:

```
   defense                        would it have caught this?
   ─────────────────────────      ────────────────────────────────────────
   parameterized queries (20.2)   no — no injection involved
   CSRF tokens (20.3)             no — attacker used their own real session
   security headers (20.4)        no — nothing about the browser's behaviour
   a dependency scanner           no — the code has no vulnerable library
   a WAF                          no — every request is well-formed and valid
   a pentest of the running app   maybe — if the tester happened to try it
   ─────────────────────────      ────────────────────────────────────────
   someone asking "what if two    YES — this is a design question, asked
   redemptions race?" at design      before a line of code was written
   time
```

The bug was never in the code. It was in the *design* — in the decision to model redemption as read-then-write without a concurrency guard, a decision made on a whiteboard weeks before anyone opened an editor. You cannot find this bug by looking at the code, because the code is a faithful implementation of a flawed idea. You can only find it by examining the idea.

This is the category the other four articles cannot reach, and it sits at #4 on the 2025 OWASP list under a name that says exactly what it is: **Insecure Design.**

## What It Is

**Insecure design** is a vulnerability in the *shape* of a system rather than in its implementation — a missing or flawed security control that no amount of correct coding can compensate for, because the flaw is in what was built, not in how well it was built. The distinguishing test, from OWASP's own framing: a secure design implemented with bugs still has an application security problem you can fix; an insecure design implemented perfectly has a problem you cannot code your way out of, because there is no control there to get right.

The technique that addresses it has a name too, and it's the real subject of this article: **threat modeling** — a structured examination of a design, before or alongside building it, that asks what an adversary could do to it. It is the *generative* counterpart to everything else in this module. Every previous article gave you a known failure mode to defend against — a list. Threat modeling is how you find the failure modes that aren't on anyone's list, because they're specific to *your* system's design.

This is the resolution of the tension 20.1 opened. The Top 10 is an aggregate of what hurt other people; it will never contain "your gift-card redemption has a race condition," because that threat exists only in your design. 20.1 said the list can't prompt you to look at your own worst risk. **Threat modeling is the thing that does.** Where the list is a lens you hold up to each endpoint, threat modeling is a method for deriving the threats the list doesn't know about.

One disambiguation up front, because these three get conflated and they catch different things:

```
  threat modeling    examines the DESIGN, before/during build.
                       Finds: missing controls, bad trust assumptions,
                       logic flaws. (This article.)
  code review /SAST   examines the CODE. Finds: injection, bad crypto
                       calls, the implementation bugs. (20.2, Module 31.)
  pentest / DAST      examines the RUNNING SYSTEM. Finds: what the first
                       two missed, plus config and integration bugs.
                       (The next article.)
```

They are complements, not substitutes, and they find largely disjoint sets of bugs. A team with all three scanners green and no threat model ships the gift-card race every time.

## Recognizing the Problem

You have an insecure-design gap — or an unexamined design that might hide one — when:

- **A security decision was made implicitly, by default, or by nobody.** "How does redemption handle concurrent requests?" was never asked; the answer is whatever the ORM happened to do.
- **The threat you're exposed to is a *sequence of legitimate actions*,** not a malformed input — the race above, an order shipped before payment clears, a refund that can exceed the original charge, a coupon that stacks with itself.
- **A trust boundary is crossed without anyone naming it as one.** User input becomes a filename; a webhook's claimed amount is believed; one microservice trusts another's assertion of who the caller is.
- **"Who could abuse this, and how?" has never been asked out loud** about a feature that moves money, data, or permissions.
- **The abuse case is missing from the requirements.** You have user stories for what the feature *should* do and none for what it should *refuse* to do.
- **The design assumes the client behaves.** Rate limits enforced only in the UI, a price sent from the browser, a "you can't do that" that's a disabled button rather than a server check.
- **A new feature crosses a boundary and shipped without a design conversation** that included "what's the worst a hostile user could do with this?"
- **Every scanner is green and you have never modeled a threat.** The most common state, and the one that feels safest while being blindest to this whole class.

## How It Works

### The four questions

Threat modeling, stripped of ceremony, is four questions asked about a design. This map already stated them, in the very first architecture article — "who might attack this, what are they after, how would they get it, and what happens if they succeed" — and the canonical form (Shostack's) is nearly identical:

```
  1. What are we building?        ── a shared picture of the system:
                                      components, data, who talks to whom,
                                      and where trust changes hands
  2. What can go wrong?           ── the adversarial pass: for each part,
                                      how could someone abuse it?
  3. What are we going to do?     ── per threat: mitigate, accept, transfer,
                                      or design it away
  4. Did we do a good enough job? ── check the model against the built system
```

Everything else — STRIDE, data flow diagrams, attack trees — is scaffolding that makes question 2 systematic instead of a vibe. The four questions are the whole method; a team that genuinely asks them about a new feature is threat modeling, whatever they call it.

### Why "what can go wrong?" needs structure

Question 2 is where the value is and where teams fail, because "think like an attacker" and "search your feelings" produce whatever threats the people in the room happen to imagine — which is exactly the blind-spot problem 20.1 diagnosed for individuals, now at the design level. You find the attacks you already know; you miss the categories you don't think to consider.

The fix is the same as it was for the Top 10: a structured prompt that walks you past your own gaps. The standard one is **STRIDE**, a mnemonic for six threat categories, and its cleverness is that each category is the *violation of a property you want*:

```
  threat                    violates          the question it forces
  ───────────────────       ─────────────     ───────────────────────────────────
  Spoofing                  authentication    can someone pretend to be another
                                                user / service / origin?
  Tampering                 integrity         can someone alter data or messages
                                                in transit or at rest?
  Repudiation               non-repudiation   can someone deny doing a thing, and
                                                would we have no record?
  Information disclosure     confidentiality   can someone read what they shouldn't?
  Denial of service         availability      can someone make it unavailable?
  Elevation of privilege     authorization     can someone do what they shouldn't?
```

You take each element of your design — each process, data store, and data flow — and run all six questions past it. Applied to the gift-card design, "Tampering" against the redemption flow asks "can someone alter the sequence of operations?" and the race condition surfaces the moment you're forced to think about the redeem flow as something an adversary controls the timing of. STRIDE didn't know about gift cards. It knew to make you ask.

The point is not to memorize STRIDE specifically — LINDDUN does the same job for privacy, PASTA for a risk-centric version, attack trees for a goal-first version. The point is that *any* structured prompt beats unstructured brainstorming, for the identical reason the Top 10 beats intuition: it enumerates the categories you reliably forget.

### The diagram is the thinking

Question 1 usually produces a **data flow diagram** — boxes for processes, cylinders for stores, arrows for data, and, critically, dashed lines for **trust boundaries**: the places where data crosses from something you control to something you don't, or from one privilege level to another.

```
   ┌─────────┐   order   ┌──────────────┐  SQL   ┌──────────┐
   │ browser │ ───────►  │  order API   │ ─────► │    DB    │
   └─────────┘           └──────────────┘        └──────────┘
        ╎                       │
        ╎ ← trust boundary      │ redeem(code)   ┌──────────┐
        ╎   (client is hostile) └──────────────► │ gift svc │
                                                 └──────────┘
                                                  ▲ is THIS flow a boundary too?
                                                    does gift svc trust the API's
                                                    claim of "already checked balance"?
```

The trust boundaries are where the threats cluster, because a boundary is exactly a place where one side's assumptions meet the other side's control. The single most productive act in a threat-modeling session is drawing the dashed lines honestly — because the gift-card bug lives on the boundary the team didn't draw: the one between "the API that checked the balance" and "the service that decrements it," where a concurrency assumption was silently trusted. The diagram doesn't have to be beautiful. It has to be honest about where trust changes hands.

### The output is decisions, not a document

Question 3 turns each identified threat into one of four decisions — the same vocabulary risk management uses everywhere:

- **Mitigate** — add the missing control (a `SELECT ... FOR UPDATE` lock or an optimistic-concurrency version check on the gift-card balance; Module 6's locking, now revealed as a *security* control, not just a correctness one).
- **Accept** — decide the risk is tolerable and *write down that you decided*. An accepted risk with a name and an owner is a decision; an unexamined risk is negligence wearing the same clothes.
- **Transfer** — push it to someone better placed (PCI scope to Stripe, DDoS to a CDN, the whole card-storage problem to a vault).
- **Avoid** — remove the feature or the exposure. The cheapest fix for a dangerous capability is often not building it.

The artifact that survives is a short table of threats and decisions — not a forty-page document. This map's first article was blunt about it: *three honest paragraphs beat a forty-page document nobody reads,* and the value is mostly in noticing your real adversary is a curious authenticated customer or a leaked API key, not a nation-state. A threat model that took an afternoon and changed one design decision has already outperformed every threat model that became a compliance PDF and changed nothing.

## When It's Appropriate

Threat modeling scales down; the question is never whether but how much:

- **A quick pass on every feature that crosses a trust boundary or touches money, auth, or personal data.** Fifteen minutes at the whiteboard, the four questions, STRIDE on the two riskiest flows. This is the high-value default and it's cheap.
- **A deeper session at real design inflection points** — a new external integration, a new authentication path, a new way for tenants' data to touch, splitting a monolith (every new service boundary is a new trust boundary). These are the irreversible-decision moments Module 1.2 flagged; the cost of getting them wrong is highest here.
- **Whenever "what's the worst a hostile user could do?" hasn't been asked** about a feature where the answer could be expensive. If you can't answer it, you haven't modeled it.
- **At design time, above all** — the entire economic argument is that a flaw caught on the whiteboard costs pennies and the same flaw caught in production costs an incident. Threat modeling done after launch is just an expensive pentest.

## When It's Unnecessary or Overkill

- **A formal, documented threat model for a CRUD screen inside an existing trust boundary.** Adding a "notes" field to a form the team already understands doesn't need a session. The judgment is "did we cross a boundary or add an abuse surface?" — if no, skip it.
- **A forty-page document, almost ever.** The heavyweight, tool-generated, compliance-driven threat model is the failure mode that gives the practice its bureaucratic reputation. If the model is longer than the design doc, it has become theatre. (There are regulated contexts that mandate the document — do it, but don't mistake the document for the thinking.)
- **Threat modeling a design you're about to throw away.** A spike, a prototype, a proof of concept that will be rewritten — model the *real* thing, not the sketch.
- **Modeling nation-state adversaries for a to-do list app.** Calibrate the adversary to reality (Module 1.2's point). Over-scoping the threat wastes the session on attacks that will never come while the curious customer walks in the front door.
- **Using it as a substitute for the other two.** A threat model does not find the injection bug or the misconfigured bucket; those need SAST and scanning. Modeling threats and skipping code review just moves the blind spot.

## Trade-offs

- **It requires expertise the room may not have.** The quality of question 2 depends on someone present being able to think adversarially, and that skill is unevenly distributed. A threat-modeling session with no one who thinks like an attacker produces a comfortable list of threats you already knew — the structured-prompt scaffolding (STRIDE) helps, but doesn't fully substitute.
- **It competes with delivery, visibly and immediately.** The cost is paid now, at design time, in a meeting; the payoff is a breach that doesn't happen, which is invisible and unattributable. This is the hardest security economics there is — you are spending certain time now against uncertain, uncountable savings later, and the pressure is always to skip it "just this once."
- **The model goes stale.** A threat model reflects the design at the moment it was made; the system evolves, boundaries move, and last quarter's model quietly stops matching reality (question 4 is the guard against this, and the one most often skipped). An unmaintained threat model can be worse than none, because it looks like coverage.
- **It can become the bureaucratic thing everyone hates.** Mandated, templated, tool-heavy threat modeling that produces documents nobody reads discredits the practice and trains engineers to treat it as a checkbox — the exact fate 20.1 warned about for the Top 10, arriving for the technique that was supposed to be the cure.
- **It surfaces threats you then have to decide about.** Once you've written "an insider could exfiltrate all tenant data and we'd have no record," you own that knowledge. "Accept" is a legitimate answer, but the model forces the decision into the open, which is uncomfortable and occasionally politically costly — and is precisely the point.

## Alternatives

Threat modeling is the generative method; the alternatives are either lighter-weight versions of it or the other two legs of the stool:

- **Abuse cases / evil user stories.** The lightest possible version: for each user story, write the adversarial mirror. "As an attacker, I redeem one card against many orders simultaneously." Cheaper than a full model, catches a surprising fraction of design flaws, and slots into an existing agile process without a new ceremony. Often the right starting point.
- **Security design review by a specialist.** Instead of a team session, one security-minded person reviews the design. Scales the scarce adversarial-thinking skill, at the cost of the shared understanding a group session builds (and the specialist becomes a bottleneck).
- **Security requirements / a design checklist (ASVS).** Rather than deriving threats, adopt a pre-built list of controls a design must have (the ASVS from 20.1). Complementary: the checklist ensures you didn't miss a *common* control; threat modeling finds the *uncommon* one specific to your design. Neither replaces the other.
- **Pentesting and DAST (the next article).** The after-the-fact alternative — find the design flaws by attacking the running system. Strictly more expensive per bug (the flaw is already built and shipped) and incomplete (a pentester tries what they think of in a fixed window), but it catches what modeling missed and needs no design-time discipline. The mature answer is both: model at design time, pentest before launch.
- **Reference architectures and secure-by-design frameworks.** Building on a foundation where the common design-level controls are already present (a framework that makes the safe concurrency pattern the default, a platform that enforces tenant isolation structurally). This doesn't remove the need to model; it raises the floor so the model has fewer basic gaps to find.

## Implementation

There is no code to implement threat modeling — the "implementation" is a practice, and forcing code here would be exactly the reference-implementation bloat the master prompt warns against. What's worth making concrete is the *shape* of a real session, so it's a thing you can run this week rather than a concept you admire.

The lightweight loop, on the gift-card feature, in about thirty minutes:

```
  1. DRAW (10 min)   Whiteboard the flow. Browser → order API → gift svc → DB.
                     Draw the dashed trust boundaries. Argue about where they
                     really are. (The argument is the work.)

  2. STRIDE the      Walk the six letters past the redeem flow specifically:
     riskiest flow     S — can someone redeem as another user?        (auth: yes, checked)
     (10 min)          T — can someone alter the redeem sequence?     ← RACE FOUND HERE
                       R — if a card is drained, is there a record?    (audit log?)
                       I — does the balance-check leak valid codes?    (enumeration?)
                       D — can someone lock a card by hammering it?
                       E — can a $10 card redeem for $500?             (server re-checks?)

  3. DECIDE (5 min)  Race → MITIGATE: version column on balance, redeem is a
                       compare-and-swap; concurrent redemption of the same card
                       now fails the second writer. (Module 6's optimistic lock,
                       reframed as the security control it always was.)
                     Enumeration → ACCEPT for now, add rate limit next sprint,
                       write it down with an owner.

  4. RECORD (5 min)  Five lines in the feature's design doc: the flow, the two
                     threats found, the two decisions. Not a PDF. Five lines.
```

The whole artifact:

```
  Feature: gift-card redemption
  Threats found (STRIDE on redeem flow):
    - Tampering/race: concurrent redemption double-spends a card
        → MITIGATE: optimistic-concurrency version check on balance   [owner: AK]
    - Info-disclosure: balance endpoint confirms valid codes
        → ACCEPT now, rate-limit next sprint                          [owner: JM]
  Reviewed against build: 2026-05, on the redeem PR.
```

That table is a complete threat model. It took half an hour, it caught a $20,000 bug before a line was written, and its entire value is in row two of the STRIDE walk — the question the team would not have asked on its own. Everything about threat modeling that matters is in the gap between "we built what we designed" and "we asked what our design lets an attacker do."

## Further Reading

- **Adam Shostack, _Threat Modeling: Designing for Security_.** The definitive book, and the source of the four-question framing. Longer than most teams need, but the STRIDE-per-element method and the trust-boundary discipline are worth the read for anyone who'll run sessions.
- **The Threat Modeling Manifesto** (threatmodelingmanifesto.org). A short, tool-agnostic statement of values and the four questions — the antidote to the forty-page-document version. Read this first; it's a page.
- **OWASP Threat Modeling Cheat Sheet, and OWASP pytm / Threat Dragon.** The practical how-to and two free tools (pytm for model-as-code, Threat Dragon for diagrams) when a team wants more structure than a whiteboard — with the caveat that the whiteboard is usually enough to start.
- **OWASP Top 10:2025 A04 (Insecure Design).** The category this article is the method for, including its examples of design-level flaws that no implementation fixes.
- **Microsoft's STRIDE documentation and the Elevation of Privilege card game** (Shostack). STRIDE in its original habitat, and a genuinely effective way to teach adversarial thinking to a team that lacks it — the card game turns question 2 into something a non-specialist room can actually do.
- **OWASP ASVS.** The design-checklist complement — the common controls a design should have, against which threat modeling finds the uncommon ones. 20.1 pointed here; this is where it pays off.
- Within this map: the irreversible-security-decisions and "three honest paragraphs" framing in **Module 1.2**; the checklist-vs-thinking argument in **20.1**; optimistic and pessimistic locking (the gift-card fix) in **Module 6.5**; abuse-surface validation and mass assignment in **7.3**; trust boundaries across services in **Module 23 and 36**; and the running-system counterpart, penetration testing, in the next article.
