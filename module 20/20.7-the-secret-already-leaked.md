# The Secret Already Leaked

_Module 20.7 — Security Best Practices_

## The Problem

March 2025. A widely-used GitHub Action, `tj-actions/changed-files`, is compromised. The malicious version does one thing: it prints the CI job's environment — every secret injected into the pipeline — into the build log, where the attacker can read it. Thousands of repositories run the action on their next push. Their secrets are now in logs an attacker controls.

Here is the part that matters for this article. Many of the affected teams *had done the thing everyone tells you to do.* They had rotation policies. Some of their tokens were set to expire in hours. It didn't help. In the seconds between the secret hitting the log and the token expiring, automated tooling used it — pulled data from storage buckets, spun up compute, pivoted deeper. A credential valid for a single CI run was valid long enough. The rotation schedule that was supposed to be the safety net was irrelevant, because the attacker didn't need days. They needed seconds, and they had them.

Set that against the number that frames the whole problem: breaches involving stolen credentials take, on average, **292 days** to identify and contain. And 70% of secrets leaked in one recent year were *still valid* years later. So the real picture of a leaked secret is not "we rotate every 90 days, so worst case it's exposed for 90 days." It's this:

```
   the story teams tell themselves        what actually happens
   ────────────────────────────────       ──────────────────────────────
   secret leaks                           secret leaks
   → rotation window bounds the damage     → attacker uses it in SECONDS
   → we rotate in 90 days, so ≤90 days     → we NOTICE in ~292 days (if ever)
      of exposure                          → 70% never get revoked at all
   → controlled, bounded                   → the window is "leak → detection",
                                              and detection is the slow part
```

Module 3.4 handled where a secret should *live* — the ladder from repository (never) up to leased, short-lived credentials — as a matter of configuration hygiene. This article starts one assumption later and asks the security question that hygiene alone can't answer: **the secret leaked anyway. Now what?** Because it will. The question that decides how bad it gets is not where you stored it. It's how fast you can make it worthless, and how little it could touch while it was alive.

## What It Is

The subject of this article is the **exposure lifecycle of a secret** and the two properties that govern how much a leak costs: the **window of exploitability** (how long a leaked secret stays usable) and the **blast radius** (how much it can reach while usable). Neither is about preventing the leak. Both are about the shape of the damage when prevention fails — which, at scale, it always eventually does.

Three terms, precisely:

- **Rotation** — replacing a secret with a new one on a schedule, invalidating the old. Routine, proactive, calendar-driven.
- **Revocation** — invalidating a secret *right now*, because you believe it's compromised. Reactive, incident-driven, and the one that actually bounds a breach.
- **Blast radius** — the set of things a single secret can access. A database password that can read one table has a small radius; a cloud root key has a catastrophic one.

The reframe that organizes everything below: a secret's lifecycle is *issued → live-and-usable → revoked*, and **rotation only touches the first and last steps.** The dangerous part is the middle — the span where the secret is alive and works — and rotation does nothing about the middle except cap its maximum length under the *optimistic* assumption that nothing went wrong in between. The security discipline is about the middle: making it short by design (short-lived credentials), making its contents small (least privilege), and shrinking the leak-to-revoke gap that determines its real length (detection).

The neighbour to distinguish, because 3.4 owns it: this is not a *storage* article. Where to keep a secret (env var, platform secret, Vault lease) is 3.4's subject and is upstream of this one. You can store a secret impeccably and still be destroyed by a slow revocation and a wide blast radius. Storage reduces the *chance* of a leak; this article is about the *cost* of one.

## Recognizing the Problem

Your exposure lifecycle is the weak point — regardless of how well secrets are stored — when:

- **You cannot revoke a specific secret quickly.** Revocation means rotating a shared credential that everything uses, in a careful order, so nobody does it. (Module 3.4's "password nobody can change" incident — the same fact, seen as a *response-time* liability.)
- **You don't know what a given secret can access.** If "what's the blast radius of this key?" has no ready answer, you can't scope an incident, so every leak is treated as either catastrophic or ignored.
- **Long-lived credentials dominate.** Static API keys and passwords with no expiry, some years old. The window of exploitability is "until someone notices," and nobody's watching.
- **You'd learn about a leak from the outside** — a researcher's email, an AWS abuse notice, a spike in your bill — rather than from your own detection. If you have no secret-scanning on commits and no anomaly alerting on credential use, your leak-to-detection time is unbounded.
- **One credential unlocks everything.** A single service account with broad permissions, shared across services, is a blast radius the size of your whole system in one string.
- **Secrets reach logs, error trackers, or CI output.** The exact `tj-actions` failure mode — and env-var secrets show up in stack traces and `/proc` by default (3.4).
- **"Has this secret ever leaked?" is unanswerable.** No audit trail of where a secret has been, so you can't reason about whether it's already compromised.
- **Rotation is your only story.** If the plan for a compromised secret is "well, it rotates eventually," you're relying on the one control the opening incident proved doesn't help.

## How It Works

### The window of exploitability is the metric that matters

The length of time a leaked secret is dangerous is not your rotation interval. It's:

```
  window of exploitability  =  time-to-detect  +  time-to-revoke

  leak ──────────────────────────────────► detection ──────► revocation
        │◄─── attacker's free run ────►│                     │
        │                              │◄── race to revoke ──►│
        └── usually the LONG part ─────┘   └─ the part you    │
            (avg ~292 days if you're         can make fast ───┘
             relying on noticing)
```

Two levers, and they're where the whole discipline lives:

- **Shrink time-to-revoke** by making revocation a single fast action instead of a cross-system rotation project. A secret you can kill in one API call in thirty seconds has a bounded window once you know; a shared password wired into six consumers does not, no matter how good your intentions.
- **Shrink time-to-detect**, because it's the part that's silently enormous. This is why detection is the missing half of every rotation strategy — rotation caps the window under the assumption of an orderly world, and detection is what bounds it in the disorderly one you actually live in.

The insight the opening incident hammers: **shortening the credential's lifetime helps only if the attacker needs longer than the lifetime.** For interactive human access, a 1-hour token genuinely limits damage. For an automated attacker with a fresh credential, one hour — or one CI run — is an eternity. Short-lived secrets are necessary and not sufficient; they bound the *tail* of exposure, not the *immediate* exploitation.

### Blast radius is decided before the leak, at grant time

You cannot change what a leaked secret can reach *after* it leaks — the permissions were baked in when you issued it. So blast radius is a design-time property, and the control is **least privilege** applied to every credential:

```
  one broad credential                    scoped credentials
  ────────────────────                    ──────────────────
  SERVICE_KEY: full DB, all buckets,      db-reader:  SELECT on 2 tables
    admin API, can create more keys       s3-uploads: PUT to one prefix
         │                                report-api: read-only, one endpoint
         ▼                                     │
  leak = total compromise                      ▼
                                          leak of any one = a contained,
                                            nameable, survivable incident
```

The same principle as the authorization work in Module 4.3 and the tenant isolation in Module 5, applied to *machine* identities rather than users: a credential should be able to do exactly what its holder needs and nothing more, so that its compromise is a scoped problem instead of an extinction event. The most consequential version is "can this credential mint other credentials or change permissions?" — because a key that can escalate has, effectively, infinite blast radius regardless of its nominal scope.

Dynamic secrets (3.4's leased credentials) are the strongest form: the store issues a credential scoped to one instance for one hour, then deletes it. That's short window *and* small radius *and* built-in revocation, in one mechanism — which is why it's the endpoint of the maturity path rather than a starting move.

### Detection closes the gap rotation can't

Because time-to-detect dominates the window, the highest-leverage investment is usually noticing faster. Three layers, each catching a different stage:

- **Prevent it reaching the repo.** Secret-scanning with *push protection* — GitHub's, GitGuardian, `gitleaks`, `trufflehog` — blocks a commit containing a credential before it lands. The caveat that's grown sharp: pattern-based scanners catch *specific* formats (an AWS key's `AKIA…` prefix) well, but the majority of leaked secrets are now *generic* — database URLs, custom tokens, `username:password` — which have no signature and slip past pattern matching. Push protection is necessary and increasingly incomplete.
- **Find what already leaked.** Scan history and, crucially, the places secrets sprawl *beyond* code — CI logs, Slack, wikis, container images, error trackers. The opening incident leaked into logs, not source; a repo-only scan would never have seen it.
- **Catch the *use*, not just the storage.** The backstop that works even for a secret you never knew leaked: anomaly detection on the credential's behaviour. A database account that reads two tables all year suddenly dumping every table, a key used from a new country, an off-hours spike — these are detectable at the point of *use*, which is the one place a leaked secret must eventually appear. This is where secret exposure rejoins Module 19's observability and Module 20.5's "would we even see it": the audit log nobody alerts on is not detection.

### The response runbook is the thing you write before you need it

When a secret leaks, the clock is the 292-day-vs-seconds asymmetry, so the response cannot be invented under pressure. The order is fixed and worth memorizing:

```
  1. REVOKE first, investigate second. Kill the credential now. A revoked
     secret that turns out fine costs a re-issue; a live secret you're still
     investigating costs the breach. Revocation is reversible; the leak isn't.
  2. ASSESS blast radius. What could this key touch? (You answer this fast
     only if you scoped it at grant time and wrote the scope down.)
  3. HUNT for use. Check the audit logs for what the credential did between
     leak and revoke. This is your incident scope.
  4. ERADICATE the source. Remove it from history/logs — knowing (3.4) that
     git-history removal doesn't un-leak it; every clone still has it, which
     is why step 1 is the only real fix.
  5. LEARN. Why was it long-lived / broad / undetected? Fix the class:
     make it short-lived, scope it down, add the detection that missed it.
```

Step 1 is the whole game. The single most common failure in secret-leak response is investigating before revoking — trying to confirm the leak is "real" while the attacker is already using it. Revoke on suspicion; the cost of a false alarm is a re-issue, and the cost of hesitation is unbounded.

## When It's Appropriate

- **Least-privilege scoping on every credential: always, from issue.** It's free at grant time and impossible to retrofit under incident pressure. There is no credential that should have more access than its holder uses.
- **A fast revocation path: for anything whose compromise is an incident** — which is most machine credentials. The test is "can I kill this specific secret in under a minute without taking down the system?" If no, that's the gap to close.
- **Secret-scanning with push protection: on every repo, now.** Cheap, prevents the most common leak, and the run-time equivalent of the CI gates from Module 3.
- **Short-lived / dynamic credentials: wherever the platform supports it** — cloud workload identity, Vault dynamic secrets, OIDC-federated CI (which removes the long-lived CI secret entirely). The highest-value shift for the highest-risk credentials.
- **Anomaly detection on credential use: for high-blast-radius secrets specifically** — the database, the cloud control plane, the payment key. You can't watch everything; watch what would hurt most.
- **A written revocation runbook: before your first incident.** The 3am version of "how do I rotate the DB password without an outage" should be a document, not a discovery.

## When It's Unnecessary or Overkill

- **A full dynamic-secrets platform (Vault) for a three-service app with five credentials.** The operational cost of running the secret store can exceed the risk it manages at small scale. Platform-injected secrets plus scoping plus scanning is a defensible whole program until you have enough secrets that manual rotation is the bottleneck.
- **Anomaly detection on every low-value credential.** Instrumenting use-detection on a read-only key to a public dataset is monitoring cost for no blast radius. Scope detection to secrets whose misuse matters.
- **Aggressive rotation as a substitute for scoping and detection.** Rotating a broad, undetected credential every 24 hours is expensive theatre — it addresses the one part of the window (the orderly tail) that wasn't your problem, and the opening incident is the proof.
- **Rotating a credential that should be *eliminated*.** The best secret is no secret: a CI job that federates to the cloud via OIDC has no long-lived key to rotate, scope, or leak. Reach for removal before management.
- **Treating every scanner hit as a fire drill without triage.** Generic-secret scanners produce false positives; a process that pages on each one trains people to ignore the channel — the same alert-fatigue failure as everywhere else.

## Trade-offs

- **Short-lived credentials add operational moving parts.** Something must fetch and refresh them; a credential that expires mid-job fails the job (3.4's lease-renewal problem). You trade a static-secret risk for a distributed-systems liveness concern — real, and usually worth it, but not free.
- **Least privilege fights velocity, credential by credential.** Every scoped-down key is a future moment where a new feature needs an access the key doesn't have, and someone under deadline widens it "temporarily." Scoping decays toward broad without a mechanism holding it, exactly like the boundary decay in Module 2.
- **Detection is probabilistic and noisy.** Anomaly detection on credential use produces false positives (a legitimate new deploy region looks like a compromise) and false negatives (a careful attacker mimicking normal use). It shrinks the window on average; it's not a guarantee, and treating an alert-free period as proof of safety is the 20.6 error in a new place.
- **Fast revocation requires the system to tolerate it.** "Kill any credential in thirty seconds" is only safe if the system degrades gracefully when a credential vanishes — which means every consumer needs to handle auth failure without cascading. Building for revocability is a design cost paid up front.
- **You can't un-leak.** The hardest truth: once a secret has been exposed, no action makes it un-exposed — revocation makes it *useless*, which is the best available outcome, but the 70%-still-valid statistic exists because teams treat cleanup (removing it from the file) as the fix and skip the only step that matters (revoking it). Effort spent scrubbing history is effort not spent revoking.
- **The whole discipline assumes leaks are inevitable, which is culturally hard.** "Assume breach" asks a team to invest in the aftermath of a failure they'd rather believe won't happen. The investment is invisible until the day it's the only thing that saved you, which makes it perpetually easy to defer.

## Alternatives

The approaches here compose; the meaningful alternatives are about *which lever* you invest in:

- **Eliminate the secret entirely (the strongest option).** Workload identity and OIDC federation let a service or CI job prove who it is to a cloud or another service *without a shared secret at all* — the platform vouches for the identity. No secret means nothing to leak, rotate, scope, or detect. Where available (CI-to-cloud, service-to-service in one cloud), this dissolves the problem rather than managing it, and it's underused because it's framed as an integration detail rather than the security win it is (the same "deliver into their cloud account" move from Module 17.1's webhook article).
- **Invest in prevention over response.** Heavy secret-scanning, developer training, pre-commit hooks — push the leak probability down instead of the leak cost. Complementary, but subject to diminishing returns and the generic-secret blind spot; prevention alone leaves you helpless the day it fails, which is why response can't be skipped.
- **Invest in response over prevention.** Fast revocation, tight blast radius, use-detection — accept that leaks happen and make them cheap. More robust (it survives the leak you didn't prevent) but requires the assume-breach posture. The mature answer weights both; a team forced to choose one should usually pick response, because prevention has a 100% failure mode and response degrades gracefully.
- **Centralized secrets management platform** (Vault, cloud secret managers). Buys rotation, leasing, audit, and dynamic secrets in one place — the operational backbone for all of the above at scale, at the cost of running (or paying for) the platform and making it a critical dependency whose own compromise is the nightmare scenario.

## How to Achieve It

No dominant implementation language here — the work is a posture and a lifecycle, not an algorithm — so the concrete artifact is the maturity path and the one code shape that captures the central shift.

The path, from "rotation is our only story" to "leaks are cheap":

```
  L0  Long-lived, broad, shared secrets; you'd hear about a leak from AWS.
        First move: turn on push protection + secret scanning. Free, today.

  L1  Scope every credential to least privilege, and write down each one's
        blast radius. Now a leak is a nameable, bounded incident.
        Signal to move on: you can't revoke a specific secret fast.

  L2  A fast revocation path per credential + a written runbook. The 3am
        "kill this key" is one action, not a project. Revoke-first drilled.
        Signal: manual rotation is the bottleneck, or CI holds static keys.

  L3  Short-lived / dynamic credentials and OIDC federation for the highest-
        risk secrets. The window's tail is now minutes, and CI has no static
        key to leak.  Signal: high-value secrets exist whose misuse is silent.

  L4  Anomaly detection on credential USE for high-blast-radius secrets.
        You now catch the leak you never knew happened, at the point of use.
```

The single most valuable code-level move is eliminating the long-lived CI secret via OIDC — the shift from "store a cloud key in CI" to "let CI prove its identity per-run":

```yaml
# Before: a long-lived cloud key sits in CI settings — the tj-actions target.
#   AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY  (static, broad, leakable)

# After: CI federates to the cloud per-run. No stored secret exists.
permissions:
  id-token: write            # CI mints a short-lived OIDC token for THIS run
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::…:role/ci-deploy   # scoped role
      aws-region: us-east-1
      # No key. The cloud trusts CI's signed identity token, issues a
      # credential valid for this job only, scoped to this role's permissions.
```

> The security win is in what *isn't* there: no `AWS_SECRET_ACCESS_KEY` in the repo, the CI settings, or the environment. The exact secret the opening incident exfiltrated does not exist to be exfiltrated. The credential CI receives is minted per-run, expires with the job, and is scoped to one role — short window, small radius, self-revoking, all at once. This is "eliminate the secret" made concrete, and it's the highest-leverage change most teams can make against the failure this article opens with.

---

The habit to carry out of this article, and the assumption to build on: **every secret you hold will eventually be exposed, so the security is not in the storing — it's in how little the secret can do and how fast you can make it do nothing.** Rotation is the control for the world where nothing went wrong. This article is about the other world, the real one, where the secret is already in a log the attacker is reading — and in that world the only numbers that matter are the size of the blast radius you set at grant time, and the seconds between when you suspect and when the credential stops working. Design for the leak. It's already on its way.
