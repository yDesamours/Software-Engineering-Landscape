# Telling the Browser What to Refuse

_Module 20.4 — Security Best Practices_

## The Problem

Two stories, a year apart, in the same product.

**Story one.** A marketing site and app share a domain. An engineer, doing the responsible thing before a security review, runs the site through a header scanner. It scores an F. So they copy a "security headers" snippet from a blog into the reverse proxy — a dozen headers, pasted whole — and the scanner goes green. Everyone moves on.

Six weeks later the app's charts stop rendering for some users and not others. The cause is buried in the pasted snippet: a `Content-Security-Policy` that allows scripts only from `'self'`. The charting library loads a worker from a CDN, which the policy silently blocks — but only in browsers that enforce the newest CSP directives, which is why it broke for "some users." The header meant to prevent script injection was quietly breaking the app's own scripts, and nobody connected the F-to-A change to the outage because the two were a month and a half apart.

**Story two.** A different endpoint, no headers involved. The app runs behind a cloud load balancer, and someone enables a new feature that needs a storage bucket. The bucket is created with the console's defaults. One default — "block public access" — was toggled off during debugging and never toggled back. For four months, an object-storage URL that anyone could guess served customer exports. No code was vulnerable. No dependency was outdated. No header was missing. A single configuration flag, set wrong, in a system nobody re-checked.

These look like different problems. They're the same one, and it's the category that jumped from fifth to **second** on the 2025 OWASP list: **the application's behaviour is decided as much by configuration as by code — and configuration is the part no compiler checks, no type system covers, and no code review reliably reads.**

```
   what teams inspect carefully          what actually ships the behaviour
   ────────────────────────────          ─────────────────────────────────
   the code (reviewed, typed, tested)     + the headers the server emits
                                          + the TLS and cookie settings
                                          + the cloud IAM and bucket flags
                                          + the framework's default config
                                          + the reverse-proxy rules
   ← this half gets the attention →       ← this half decides as much, unread →
```

This article is about the first, cheapest, most misunderstood corner of that half: the response headers that let you tell the browser what to refuse — and, through them, the broader discipline of not shipping a default someone set for a different purpose.

## What It Is

**Security headers** are HTTP response headers that instruct the browser to enforce a security policy at the user-agent layer — refusing to run inline script, refusing to be framed, refusing to downgrade to HTTP, refusing to leak the full URL to third parties. They are declarative: you state the policy, and the browser is the thing that enforces it, on the client, for free.

The broader category they sit inside is **security misconfiguration** — OWASP's A02 — which is every case where a system is insecure not because of a coding flaw but because of how it was set up: default credentials left in place, verbose error pages exposing stack traces, unnecessary features enabled, permissions too broad, a hardening control left unset. Headers are the most tractable slice of it, which is why they're where this article starts.

The single most important framing, and the one that connects to the rest of the module: **headers are defense in depth, not defense.** This map made the point in its very first architecture article — security headers are on the short list of controls that are *cheap, additive, and safe to add in month eight.* That's the correct mental model in both directions:

- **Cheap and additive** means: set them early, they cost almost nothing, and they turn a working exploit into a blocked one. A CSP doesn't fix an XSS bug; it means the injected script won't run. HSTS doesn't fix anything; it means a downgrade attack has nothing to downgrade.
- **Not defense** means: a green header score is not a secure application. This is the 20.1 checklist error in its purest form — the scanner grades the headers, the headers are one thin layer, and the workspace-id bug (20.1) and the injection (20.2) are entirely untouched by any header. A team that "did security" by getting an A on a header scanner has measured the one part that was already easy.

Both halves are true at once, and holding only one of them is how you get either story in the Problem.

## Recognizing the Problem

Header and misconfiguration gaps, as scannable signals:

- **No `Strict-Transport-Security` header**, so a user's first request (or any downgrade) can be intercepted over plain HTTP.
- **No `Content-Security-Policy`**, or one containing `'unsafe-inline'` in `script-src` — which is a CSP that permits exactly the thing CSP exists to block.
- **State-changing pages can be framed** — no `frame-ancestors` (or legacy `X-Frame-Options`), so a clickjacking overlay is possible.
- **Stack traces, framework banners, or `Server:` version strings** in production responses. Each one hands an attacker your exact software and version.
- **The app still emits deprecated headers** — `X-XSS-Protection`, `Expect-CT`, `Public-Key-Pins` — copied from an old guide. At best inert, at worst actively harmful (the XSS auditor these enabled had its own bypasses).
- **A default admin path, default credentials, or a debug endpoint** reachable in production.
- **Cloud storage, IAM roles, or database access set to the console default** rather than to what the feature needs.
- **CORS reflects the request's `Origin` with `credentials: true`** — the misconfiguration that reopens CSRF (20.3) and cross-origin data theft.
- **A header scanner score is the team's evidence of security.** The tell that headers have been mistaken for the work.

## How It Works

### The headers worth setting, and what each refuses

The current recommended set is smaller than the pile of headers older guides list, because several were deprecated as browsers changed. Six carry almost all the value:

```
  header                         what it tells the browser to refuse
  ────────────────────────────   ─────────────────────────────────────────────
  Strict-Transport-Security      refuse HTTP entirely for this domain, for
    (HSTS)                         max-age seconds — no downgrade, no clear-text
  Content-Security-Policy        refuse to run/load anything not on this
    (CSP)                          allowlist — the anti-XSS backstop (20.2)
  X-Content-Type-Options         refuse to MIME-sniff — treat declared types
    : nosniff                      literally, so a "text" upload can't run as JS
  Referrer-Policy                refuse to leak the full URL (with its tokens
                                   and IDs) to third parties in the Referer
  Permissions-Policy             refuse access to camera, mic, geolocation,
                                   etc. for features you don't use
  frame-ancestors (in CSP)       refuse to be embedded in a frame by other
    or X-Frame-Options            origins — the clickjacking defense
```

Notice what most of them are: not features you turn *on*, but capabilities you turn *off* — the browser's version of the least-privilege principle. `Permissions-Policy` that denies the camera means a compromised script can't reach the camera either. The whole set is "here is what this page legitimately needs; refuse everything else."

Three headers people still emit and shouldn't: **`X-XSS-Protection`** (the browser XSS auditors it controlled were removed by Chrome, Edge, and Firefox — the header is dead, and its filtering had exploitable side effects, so set it to `0` or remove it), **`Expect-CT`** (obsolete; certificate transparency is now enforced by browsers directly), and **`Public-Key-Pins`** (HPKP — abandoned because it was a foot-gun that could brick a site). If an old config emits these, removing them *is* the fix.

And one modernization worth knowing: **`X-Frame-Options` is superseded by CSP's `frame-ancestors`**, which is strictly more expressive (multiple sources, path support). Set `frame-ancestors` in your CSP; keep `X-Frame-Options` only as a fallback for genuinely old browsers, and know that where both appear, `frame-ancestors` wins.

### CSP: the one with real cost, and why

Five of the six headers above are a one-line paste-and-forget. **CSP is not**, and conflating it with the others is how Story One happened. It deserves its own mechanism because it's the only header that constrains *your own application's code*, and getting it right is a project, not a paste.

A CSP is an allowlist of where content may come from:

```
  Content-Security-Policy:
    default-src 'self';           ← everything must come from our own origin
    script-src 'self';            ← ...scripts specifically, no inline, no CDN
    object-src 'none';            ← no <object>/<embed> (a legacy XSS vector)
    frame-ancestors 'none';       ← we may not be framed (clickjacking)
    base-uri 'self';              ← <base> can't be hijacked to relocate URLs
```

The security is real: with a strict `script-src`, an injected `<script>alert(1)</script>` **does not execute**, because the browser only runs script from sources the policy named. That's the "turns a working exploit into a log line" property from 20.2.

The cost is two-sided and it's why teams get it wrong:

- **`'unsafe-inline'` defeats the entire purpose.** Most apps have some inline script or inline event handlers, and the path-of-least-resistance fix for "my CSP broke my page" is to add `'unsafe-inline'` to `script-src`. That single token re-permits exactly the injected inline script CSP was blocking — a CSP with `'unsafe-inline'` in `script-src` is decorative. The correct fix is **nonces or hashes**: the server puts a random `nonce` on each legitimate `<script>` and in the header, and only script carrying that nonce runs. An injected script has no nonce and is refused. This is the "single highest-leverage upgrade" for most sites, and it requires touching your templates, not just your proxy.
- **It fights your dependencies.** Every CDN script, every analytics snippet, every embedded widget must be named in the policy or it breaks — silently, in the browser, sometimes only in newer browsers (Story One). This is why CSP is rolled out in **report-only mode first**: `Content-Security-Policy-Report-Only` enforces nothing but reports what *would* have been blocked, so you discover every legitimate source over a week of real traffic before you turn on enforcement. Shipping an enforcing CSP without a report-only phase is how you break your own app.

### HSTS: cheap, powerful, and semi-permanent

HSTS is one line — `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload` — and it's genuinely valuable: after the first visit, the browser refuses to talk to your domain over HTTP at all, closing the downgrade-attack window. But it has a property none of the others share and that people set casually and regret:

- **`max-age` is a promise the browser keeps even after you stop sending the header.** Set two years, and a browser that saw it will refuse HTTP to your domain for two years, regardless of what you do next. If you ever need HTTP on a subdomain (a legacy service, a device that can't do TLS), `includeSubDomains` has already forbidden it in every browser that cached the policy.
- **`preload` is close to irreversible.** Adding your domain to the browser preload list means browsers refuse HTTP *before the first visit* — protection from the very first request. Removal from the list is slow (it ships in browser releases) and you can strand a subdomain for a long time. Preload is the right call for a domain you're certain is HTTPS-everywhere forever; it's a trap to enable "to get the A grade" without understanding you can't easily take it back.

The pattern to adopt is the ramp: short `max-age` first (minutes), then hours, then days, confirm nothing on any subdomain breaks, *then* two years and `preload`. The same "additive but check first" discipline as CSP, for the same reason — this header constrains you, not just the attacker.

### The rest of A02: defaults you didn't choose

Headers are the tractable slice; the rest of security misconfiguration is the same shape without a scanner to catch it:

- **Verbose errors.** A stack trace or a database error in a production response is reconnaissance handed to an attacker (Module 7.1a made this a `500`-hygiene point; here it's a security one). Production returns opaque errors; the detail goes to the logs (Module 19).
- **Framework and server defaults.** Default admin consoles, sample apps, debug modes, directory listing, and version banners. The hardening is "turn off what you don't use and don't announce what you're running."
- **Over-broad cloud permissions.** The bucket in Story Two, an IAM role with `*` actions, a database user that owns its tables (which silently disables the row-level security from Module 5). The default is usually "more access than the feature needs," and least privilege is the correction.
- **CORS.** The one that reaches back into 20.3: `Access-Control-Allow-Origin` reflecting the caller with `credentials: true` tells the browser every site may make authenticated requests to yours. It looks like it's working (your own frontend succeeds) and it's a hole.

The unifying rule: **a default is a decision someone else made for a different situation.** Misconfiguration is inheriting those decisions without checking whether they fit yours.

## When It's Appropriate

- **The six core headers: on every HTTPS site, from the start.** Five are free; set them and forget them. HSTS with a ramping `max-age`. This is the "month eight is fine, but there's no reason to wait" set.
- **CSP with nonces: when the app renders anything and an XSS would matter** — which is almost always. Budget it as a real task with a report-only phase, not a paste.
- **HSTS `preload`: only when you're certain the domain and all subdomains are HTTPS-forever.** The grade is not worth the irreversibility if you're not sure.
- **The cross-origin isolation trio (COOP/COEP/CORP): only if you need `SharedArrayBuffer`** or strong process isolation. Otherwise they're complexity for a capability you don't use — though `CORP` alone on private resources is cheap and worthwhile.
- **A hardening pass on defaults: before any production launch**, and repeated whenever a new piece of infrastructure (a bucket, a queue, a managed service) is added — because each one arrives with its own defaults.

## When It's Unnecessary or Overkill

- **A strict script CSP on a static page with no user input and no session.** Nothing to inject into, nothing to steal. The other headers are still cheap; the CSP-with-nonces machinery is effort for no threat.
- **Emitting the deprecated three to "cover all bases."** `X-XSS-Protection`, `Expect-CT`, `Public-Key-Pins` — these aren't harmless extra coverage; they're inert-to-harmful. More headers is not more security.
- **The cross-origin isolation trio on an app that doesn't use `SharedArrayBuffer`.** COOP/COEP break third-party embeds and are pure cost if you don't need the capability they gate.
- **HSTS `preload` on a domain still serving anything over HTTP.** You'll strand it. Ramp first, preload only when certain.
- **Chasing an A+ on a header scanner as a goal.** The grade optimizes a checklist (20.1). Past the core six done correctly, the marginal header buys ranking, not safety, and can buy outages (Story One).
- **A CSP you can't maintain.** A policy so tight that every dependency change breaks the app, maintained by nobody, gets `'unsafe-inline'` bolted on within a month — at which point it's worse than an honest looser policy, because it looks like protection.

## Trade-offs

- **CSP is ongoing maintenance, not a set-and-forget.** Every new script source, CDN, or widget is a policy edit. A policy that isn't maintained gets loosened until it's meaningless; the security is real but it's a standing cost, and pretending otherwise produces the decorative `'unsafe-inline'` version.
- **Headers can break your own app, silently and unevenly.** The failure is in the browser, not your server logs, and it varies by browser version (Story One). Report-only mode for CSP and a `max-age` ramp for HSTS exist precisely because the enforcing version's failures are hard to see and hard to undo.
- **HSTS and preload are semi-permanent.** You are configuring the *user's* browser for up to years, and you can't reach in and change your mind. Cheap to set, expensive to unset — the opposite of most config.
- **A green scanner score can mask everything that matters.** The most dangerous trade-off is cultural: headers are the visible, gradeable part of security, so they attract effort disproportionate to their share of the risk, and a good grade produces false confidence about the ungraded 90%.
- **Least-privilege config fights velocity.** Every tightened default is a thing that will, eventually, block a legitimate new feature and produce a confusing failure. That friction is the cost of the bucket in Story Two not being public — worth paying, and genuinely a cost.
- **Deprecated headers rot in configs.** The pasted snippet that scored an A in 2021 emits harmful headers in 2026. Config, unlike code, rarely gets re-reviewed, so it silently ages against a moving browser landscape.

## Alternatives

Headers aren't the kind of thing that has alternatives — you set them or you don't — but the surrounding job of "get the configuration right" has several complementary approaches:

- **A managed hardening baseline.** `helmet` (Node), Spring Security's header defaults, Django's `SecurityMiddleware`, or a CDN/WAF's header injection. These set sensible defaults so you don't hand-assemble the list — with the caveat that their default CSP is usually absent or permissive, because a real CSP can't be set generically without knowing your app.
- **Automated config scanning as a gate, not a grade.** `securityheaders.com`, Mozilla Observatory, and Google's CSP Evaluator for headers; cloud posture tools (AWS Config, `cloud-custodian`, `tfsec`/`checkov` on your IaC) for the bucket-and-IAM half. Run them in CI so a misconfiguration fails a build rather than being found in an incident — the same "shift the failure earlier" move as Module 3's linters.
- **Infrastructure as code with reviewed defaults.** The durable answer to Story Two: the bucket's public-access setting is in a Terraform module with a secure default and a code review, not a console toggle someone flips at 2am. Configuration becomes something a compiler-ish tool and a reviewer can see, which is exactly what was missing.
- **A strict CSP as the primary XSS defense.** Worth naming as a deliberate strategy: some teams treat a nonce-based CSP as the main control and output encoding as the backstop, rather than the reverse. Defensible — a good CSP blocks payloads encoding misses — but fragile as a *sole* control (a single `'unsafe-inline'` regression removes it silently), so the honest position is both, with encoding primary (20.2) and CSP the net beneath it.

## Implementation

TypeScript, showing the two headers with real substance — the nonce-based CSP and the HSTS ramp — rather than the trivial paste of the other four.

The nonce-based CSP, which is the version that actually stops XSS:

```ts
import { randomBytes } from "node:crypto";

app.use((req, res, next) => {
  // A fresh nonce per response. The same value goes in the header AND on every
  // legitimate <script> the template renders. Injected script has no nonce → refused.
  const nonce = randomBytes(16).toString("base64");
  res.locals.cspNonce = nonce;

  res.setHeader("Content-Security-Policy", [
    `default-src 'self'`,
    `script-src 'self' 'nonce-${nonce}'`,   // NOT 'unsafe-inline' — that would void it
    `object-src 'none'`,
    `base-uri 'self'`,
    `frame-ancestors 'none'`,
  ].join("; "));

  next();
});

// In the template, every first-party script carries the nonce:
//   <script nonce="{{ cspNonce }}"> ... </script>
// A script the attacker injected into the page has no nonce and does not run.
```

> The load-bearing line is `script-src 'self' 'nonce-...'` with no `'unsafe-inline'`. The instant someone adds `'unsafe-inline'` to make a stray inline handler work, the nonce becomes meaningless — the browser now runs *any* inline script, injected included — and the header still looks present and correct in every scan. This is the single most common way a "we have CSP" claim is false. If you cannot remove an inline script, give it the nonce; never give the whole policy `'unsafe-inline'`.

Roll it out without breaking the app:

```ts
// Phase 1: observe only. Enforces nothing; POSTs a report of what WOULD break.
res.setHeader("Content-Security-Policy-Report-Only",
  `default-src 'self'; script-src 'self' 'nonce-${nonce}'; report-uri /csp-reports`);
// Collect /csp-reports for a week of real traffic. Every legitimate CDN, widget,
// and inline handler shows up here as a violation. Add nonces/sources until quiet.
// THEN switch the header name to Content-Security-Policy to enforce.
```

The HSTS ramp, with the irreversibility called out where you set it:

```ts
// Start here. One hour. If a subdomain still needs HTTP, you find out cheaply.
res.setHeader("Strict-Transport-Security", "max-age=3600");

// Only after days of confirming every subdomain is HTTPS:
// res.setHeader("Strict-Transport-Security",
//   "max-age=63072000; includeSubDomains; preload");
//
// ⚠ Two years + preload is a near-permanent commitment burned into users'
//   browsers. You cannot shorten it remotely; a browser that saw max-age=2y
//   enforces HTTPS for this domain for two years no matter what you send next.
//   Earn it with the ramp; don't paste it for the scanner grade.
```

The other four are genuinely one-liners and are shown once for completeness, because their triviality is the point — they are not where the thought goes:

```ts
res.setHeader("X-Content-Type-Options", "nosniff");
res.setHeader("Referrer-Policy", "strict-origin-when-cross-origin");
res.setHeader("Permissions-Policy", "camera=(), microphone=(), geolocation=()");
res.setHeader("X-Frame-Options", "DENY");   // legacy fallback; frame-ancestors above is primary
```

## Further Reading

- **OWASP Secure Headers Project.** The authoritative, maintained list of which headers to set and which are deprecated — the source of truth that a 2021 blog snippet is not. Check your config against it, not against whatever you pasted years ago.
- **OWASP Top 10:2025 A02 (Security Misconfiguration).** The category this article is the tractable corner of, including the cloud-defaults and verbose-error cases beyond headers.
- **MDN — Content-Security-Policy, and the CSP nonce/hash guides.** The reference for every directive and, crucially, the report-only workflow and nonce mechanics that make a real CSP possible.
- **Google's CSP Evaluator and the "Strict CSP" guidance (csp.withgoogle.com).** Why nonce-based policies beat host allowlists, with a checker that flags the `'unsafe-inline'` and bypassable-allowlist mistakes automatically.
- **Mozilla HTTP Observatory and securityheaders.com.** The scanners — useful as CI gates, dangerous as goals. Read their output as "did I make an obvious mistake," not "am I secure."
- **The HSTS preload list submission site (hstspreload.org).** Read the removal section *before* the submission section, so the irreversibility is a decision rather than a surprise.
- Within this map: the "cheap, additive, reversible" framing in **Module 1.2**; XSS and why CSP is a backstop not a fix in **20.2**; the CORS-and-CSRF interaction in **20.3**; verbose-error hygiene in **7.1a**; secrets and config as the unreviewed layer in **3.4**; and IaC-reviewed defaults in **Module 30**.

A **Java/Spring Security** sibling would earn its place, because Spring's `HttpSecurity` DSL ships a secure header default set and a first-class CSP nonce mechanism — so the interesting content is the inverse of this article's manual assembly: what the framework sets *for* you (and the deprecated headers its older versions still emit unless you opt out), how its nonce integration wires into the templating layer, and the reverse-mistake of overriding the secure defaults to make something work. Seeing where the framework has already made these decisions, and what it costs to want a different one, is the other half. Not yet written.

---

The habit to carry into every deployment: **the browser will enforce rules you give it, and inherit defaults you don't — and the same is true of every bucket, role, and framework you stand up.** Security headers are the cheapest security control you will ever set and the easiest to mistake for the whole job. Set the core six correctly, ramp the two that constrain you, and then spend the attention the scanner grade tempts you to stop spending — because A01 and A05 are still sitting in the code, and no header on earth touches them.
