# The Request Your Server Can't Tell Apart

_Module 20.3 — Security Best Practices_

## The Problem

A bank's transfer endpoint, done carefully. It requires a logged-in session. It checks that the source account belongs to the caller. It validates the amount, logs the transfer, and emails a receipt. Authentication, authorization, validation, auditing — all present.

An attacker sets up a page somewhere unrelated — a forum post, an ad, an emailed "you've won" link — containing nothing but this:

```html
<form action="https://bank.example.com/transfer" method="POST" id="f">
  <input name="to" value="attacker-account">
  <input name="amount" value="5000">
</form>
<script>document.getElementById("f").submit();</script>
```

A logged-in customer visits that page. Their browser submits the form to the bank. And here is the part worth sitting with: **the browser attaches the bank's session cookie automatically**, because the request is going to `bank.example.com` and that's whose cookie it is. The bank receives a request that is authenticated (real session), authorized (the source account really is the victim's), valid (well-formed amount), and logged. Every check passes. The money moves.

The customer did nothing but open a web page. They never saw the bank. No credential was stolen, no password phished, no session hijacked, no vulnerability in the bank's code in any conventional sense. The attacker never learned the session cookie's value and didn't need to — they didn't steal the victim's identity, they **borrowed the victim's browser**, which carries that identity on every request without asking.

That's the whole attack, and its unnerving quality is that nothing in the request looks wrong:

```
   a legitimate transfer request        the forged transfer request
   ────────────────────────────         ────────────────────────────
   POST /transfer                       POST /transfer
   Cookie: session=<valid>              Cookie: session=<valid>   ← same cookie
   to=friend  amount=50                 to=attacker  amount=5000
   ↑ the user meant to send this        ↑ the user never intended this
```

Byte for byte, the server cannot distinguish them from the fields it was checking. The thing that differs — *did the user intend this request?* — is not in any field the endpoint validates. That is the problem this article is about, and the reason it needs its own name.

## What It Is

**Cross-Site Request Forgery (CSRF)** is an attack that makes a victim's browser send a state-changing request the victim didn't intend, using authority the browser attaches on its own. The server, seeing valid credentials, honours it.

The root cause has a name worth knowing: **ambient authority**. The session cookie is authority that travels with every request to your origin automatically, regardless of what *caused* the request. The browser doesn't distinguish "the user clicked a button on your site" from "a script on another site triggered this" — both are requests to your origin, so both get the cookie. CSRF is the exploitation of that gap between *whose credential this is* (the victim's) and *who decided to send it* (the attacker).

State this precisely, because it draws the boundary of the whole problem:

- CSRF requires the victim to be **already authenticated** to your site. It doesn't steal or guess credentials; it rides ones the browser already holds.
- It works **blind**. The attacker's page can *cause* the request but usually can't *read* the response (the same-origin policy stops that). So CSRF targets **actions**, not data: transfer money, change email, delete account, add an admin — anything where the doing is the damage, whether or not anyone reads the result.
- It's an attack on **anything that authenticates by something automatic**: cookies, HTTP Basic auth, client certificates, Windows integrated auth. The common thread is "the browser sends it without being asked."

The disambiguation that matters, because these two are constantly confused:

**CSRF is the mirror image of XSS.** XSS (20.2) is the attacker running *their* script on *your* site — it breaks the same-origin protection entirely, so it can read responses, steal tokens, and do everything CSRF can and far more. CSRF is weaker and narrower: the attacker's code runs on *their* site and can only fire blind requests at yours. The practical consequence is a hierarchy people miss: **if you have an XSS vulnerability, your CSRF defenses are irrelevant** — a script on your origin can read the CSRF token and forge a valid request. CSRF defense assumes you don't have XSS. Fix XSS first; CSRF protection is worthless without it.

## Recognizing the Problem

You have CSRF-exposed endpoints wherever an automatically-attached credential authorizes a state change. The signals:

- **You authenticate with cookies** (or Basic auth, or client certs) and any endpoint changes state.
- A state-changing action is reachable by **GET** — `GET /account/delete`, `GET /transfer?to=…`. This is the worst case: it can be triggered by an `<img src>`, a link, a prefetch, with nothing to submit.
- **`POST` forms with no CSRF token and no SameSite consideration** — the classic gap.
- Your cookies have **no explicit `SameSite` attribute**, so you're relying on inconsistent browser defaults (see below).
- An endpoint accepts **`application/x-www-form-urlencoded` or `text/plain`** bodies — these are "simple requests" that cross-site pages can send without a CORS preflight stopping them.
- You honour a **method-override** header or `_method` field, so a "simple" POST can become a DELETE.
- Your SPA's API trusts the session cookie and has **no custom-header requirement** on mutations.
- State-changing **GraphQL** over `text/plain` (Module 8 flagged this exact door).
- You added **`SameSite=None`** to make a third-party embed work, and forgot it reopened the whole class.

## How It Works

### Why the browser does this at all

It helps to see that CSRF isn't a browser bug — it's the browser working as designed, and the design predates anyone thinking about this attack. Cookies were built so a site could recognize a returning user across requests. "Attach this site's cookie to requests going to this site" is the entire point; without it you'd log in on every page load. The attack exists because "requests going to this site" turned out to include requests *initiated by other sites*, and the original cookie design had no concept of who initiated a request. Everything below is the industry retrofitting that missing concept.

### Defense one: SameSite, and exactly how far it goes

The `SameSite` cookie attribute is the browser-level retrofit. It tells the browser when to *withhold* the cookie on cross-site requests:

```
  SameSite value   cookie sent on a cross-site request to your origin?
  ──────────────   ─────────────────────────────────────────────────────
  Strict           never. Not even when the user CLICKS A LINK to your site
                     from elsewhere — they arrive logged out, which is why
                     it's usually too aggressive for the session cookie.
  Lax              only on "top-level" GET navigations (clicking a link,
                     typing the URL). NOT on cross-site POST, PUT, DELETE,
                     and NOT on background requests (img, fetch, form-POST).
  None             always (requires Secure). This is "old behavior" —
                     the setting that reopens CSRF, needed for real
                     third-party cookies.
```

`SameSite=Lax` closes the opening example completely: the forged cross-site `POST` doesn't carry the cookie, so it arrives unauthenticated and fails. This is why CSRF is far less prevalent than it was a decade ago — the default retrofit handles the common case. But treating "Lax handles it" as the end of the story is a trap with several sharp edges:

- **The default is not reliable across browsers.** As of the current major browsers, Chromium (Chrome, Edge, Opera) treats a cookie with *no* `SameSite` attribute as `Lax`. **Firefox and Safari do not** — an unset attribute means the old send-always behaviour. So "I didn't set anything, the browser defaults to Lax" protects some of your users and not others. **Set `SameSite` explicitly; never rely on the default.**
- **The 2-minute hole in the default.** To avoid breaking some SSO flows, Chromium's *default* Lax (not explicitly-set Lax) still sends the cookie on a top-level cross-site POST if the cookie is under 2 minutes old. A freshly-logged-in user is briefly exposed to exactly the classic attack. Setting `SameSite=Lax` explicitly removes this exception — another reason not to lean on the default.
- **Lax still allows GET.** If any state change is reachable by GET, Lax sends the cookie on a top-level navigation to it. `<a href>`, a redirect, or a typed URL to `GET /account/delete` still fires with the cookie. Lax assumes you obey HTTP semantics — GET is safe, POST changes state — and does nothing for you if you don't.
- **Subdomains are same-site.** `evil.yoursite.com` is "same-site" with `yoursite.com` for SameSite purposes. If an attacker controls or XSSes a subdomain (a user-content host, a stale marketing subdomain), SameSite offers no protection between them.
- **It's a defense-in-depth layer, not a complete control.** OWASP's own guidance is to use SameSite *and* a token-based defense for anything that matters, precisely because of the gaps above.

### Defense two: the token the attacker can't know

The complete defense doesn't rely on the browser's judgment about origins — it requires proof that the request came from *your* page, in the form of a secret the cross-site attacker cannot obtain. Because the attacker fires blind (they can't read your pages, thanks to same-origin policy), any unpredictable value your page includes and their page can't is sufficient. Three shapes:

**Synchronizer token (the classic, server-stateful).** The server generates a random token, stores it against the session, and embeds it in every form/page. A state-changing request must echo it back; the server compares. The attacker's page can't read your page to learn the token, so it can't include a valid one.

```
  your page:   <form><input type=hidden name=csrf value="a3f9…"></form>
                            ↑ server put this here and remembers it
  submit:      POST /transfer   csrf=a3f9…   → server checks it matches. ✓
  attacker:    POST /transfer   csrf=???     → can't read your page, can't guess. ✗
```

**Double-submit cookie (stateless).** The server sets the token as a *cookie* and the page also sends it as a *header or field*; the server checks the two match. No server-side storage needed — the check is "does the header equal the cookie." The attacker's page can cause the cookie to be sent (it's automatic) but **cannot read it to copy it into the header** (that's the point), and cannot set a matching header cross-site. The subtlety: this only holds if the token is bound so a subdomain can't forge both halves — the modern form is a *signed* double-submit, where the cookie value is HMAC'd to the session so a subdomain that can set a cookie still can't produce a matching valid pair.

**Custom-header requirement (the SPA-native version).** For a JSON API consumed by your own frontend, the cheapest robust defense is: require a custom header (e.g. `X-Requested-With` or a CSRF header) on every mutation. A cross-site page **cannot set a custom header on a simple request** — doing so triggers a CORS preflight, which your server refuses. So the mere *requirement* of a header your own fetch code adds, and a cross-site form cannot, is itself the defense. This is why many SPA APIs need no token machinery at all: `Content-Type: application/json` plus a custom header already can't be produced by a cross-site `<form>`.

### The unifying idea

All three tokens, and SameSite too, are answering one question the raw request can't: **did this come from a context that is actually mine?** SameSite answers it by origin, judged by the browser. Tokens answer it by possession of a secret only your page has. The custom header answers it by requiring something only a same-origin script can add. Same question, three proofs.

## When It's Appropriate

- **SameSite=Lax on the session cookie: always, explicitly.** It's free, it closes the common case, and setting it explicitly removes the browser-default inconsistency and the 2-minute hole. There is no reason not to.
- **A token or custom-header defense on top: for anything whose forgery is a real incident** — money movement, account/email/password changes, permission grants, deletions, admin actions. This is the "defense in depth" that covers the GET, subdomain, and SameSite=None gaps.
- **Custom-header requirement: the default for a same-origin SPA + JSON API.** It's the least machinery for the most coverage when your own code controls every request.
- **Synchronizer tokens: for server-rendered form apps**, where you're already rendering pages and embedding a hidden field is trivial and stateful storage is available.
- **Signed double-submit: when you want token protection without server-side token storage** — an API layer that can't easily keep per-session server state.
- **Re-authentication or a step-up (Module 4) on the highest-value actions specifically** — "enter your password to confirm." Not CSRF machinery, but it defeats CSRF on that action as a side effect, because the attacker can't supply the password.

## When It's Unnecessary or Overkill

- **An API authenticated only by a bearer token in an `Authorization` header** — no cookies. There is no ambient authority: the browser doesn't attach `Authorization` automatically, so a cross-site page can't make an authenticated request. CSRF tokens here are pure ceremony. (The catch: the moment you *also* accept the session via cookie, CSRF is back.)
- **A stateless read-only endpoint.** GET that changes nothing has nothing to forge. The whole defense is scoped to state changes — which is also the argument for keeping GET side-effect-free.
- **A CSRF token on a login form's… login** — with the usual caveat that login CSRF is a real, distinct thing (an attacker logs *you* into *their* account to capture what you do next), so login forms want the token for that reason, not the usual one.
- **Adding tokens while leaving XSS unaddressed.** Backwards priority. A stored XSS reads any token you add; the CSRF work is wasted until the XSS is closed.
- **Double-submit without signing, across subdomains.** The unsigned form is defeated by any subdomain that can set a cookie. If you have untrusted subdomains, unsigned double-submit is security theatre; use the signed form or a synchronizer token.
- **Token machinery on an endpoint already protected by a custom-header requirement.** Pick one; two is belt-and-suspenders that mostly adds failure modes.

## Trade-offs

- **SameSite=Strict logs users out of inbound links.** A user clicking your link from an email or search result arrives with no cookie and sees a logged-out page — a real UX regression, which is why Lax is the session default and Strict is reserved for cookies where that's acceptable (or a second "strict" cookie is used to gate the most sensitive actions).
- **Synchronizer tokens need per-session storage and careful lifecycle.** Token-per-session vs token-per-request, rotation on login, and the classic failure where a user opens two tabs and the second tab's token invalidates the first. Token-per-session avoids the multi-tab problem at a small replay-window cost.
- **Double-submit's security is subtle and easy to get wrong.** The unsigned version *looks* stateless and safe and is quietly defeated by subdomain cookie-setting. The subtlety is the cost: a mechanism that appears to work in every test and fails to a specific, non-obvious attacker capability.
- **Custom-header defenses depend on CORS being correctly restrictive.** They work because a cross-site request with a custom header triggers a preflight your server rejects. Misconfigure CORS to reflect arbitrary origins with credentials (20.2's neighbour, and a common mistake) and you've reopened the door you thought the header closed.
- **Every defense assumes no XSS.** Worth restating as a cost: none of this survives an attacker running script on your origin. CSRF protection is a layer on top of XSS protection, never a substitute, and a team that's proud of its CSRF tokens while shipping `dangerouslySetInnerHTML` on user input has mis-spent its effort.
- **`SameSite=None` for legitimate third-party use reopens the class.** Embeddable widgets, cross-site SSO, and payment iframes sometimes genuinely need `None`. When you set it, the cookie is CSRF-exposed again and a token defense becomes mandatory, not optional — the attribute quietly moved you back to 2010.

## Alternatives

CSRF defenses aren't really alternatives to each other — they compose — but there are architectural choices that change the problem:

- **Don't authenticate with cookies.** A pure bearer-token architecture (token in `Authorization`, held in memory) has no ambient authority and no CSRF surface — trading it, as Module 4 covered, for the XSS-exfiltration risk of a script-readable token. You don't remove risk, you move it from CSRF to token theft. The BFF (backend-for-frontend) pattern is the attempt to have neither: cookie to the BFF, token held server-side.
- **Origin/Referer header checking.** The server rejects state-changing requests whose `Origin` (or `Referer`) header isn't your own. Modern browsers send `Origin` on state-changing requests, making this a genuinely useful *additional* layer — cheap, stateless, no token. Weaknesses: `Origin` is occasionally absent (privacy tools, old clients), so a strict "reject if absent" policy has false positives, and it's a check, not a proof. Good as defense-in-depth, shaky as the sole control.
- **Re-authentication / step-up on sensitive actions.** Covered above — the strongest per-action defense, because it requires a secret the attacker fundamentally lacks. Reserved for the few actions that justify the friction.
- **Framework defaults.** Rails, Django, Spring Security, and most server frameworks ship CSRF protection on by default for form posts. The "alternative" for most teams is simply *not disabling it* — and the common bug is turning it off to make an API client work instead of exempting that route correctly.

## Implementation

TypeScript, showing the two defenses a modern app actually reaches for: the explicit SameSite cookie (which every app should have) and the custom-header check (the SPA-native defense). The synchronizer token is well-covered by every server framework; the interesting, under-explained cases are these.

The cookie, set so nothing is left to the browser's judgment:

```ts
res.cookie("__Host-sid", token, {
  httpOnly: true,      // 20.2: not readable by script (limits XSS blast radius)
  secure: true,        // required by __Host- and by SameSite=None if ever used
  sameSite: "lax",     // EXPLICIT — removes the Firefox/Safari default gap
                       //   and the 2-minute top-level-POST exception
  path: "/",
});
// Lax, explicitly, is the floor. It is NOT the whole defense — the header
// check below covers the GET, subdomain, and gaps Lax leaves open.
```

The custom-header check for a JSON API — the whole defense in a few lines, and why it works:

```ts
function requireSameOrigin(req: Request, res: Response, next: NextFunction) {
  if (SAFE_METHODS.has(req.method)) return next();   // GET/HEAD/OPTIONS change nothing

  // A cross-site <form> can send application/x-www-form-urlencoded or text/plain
  // with NO preflight. It CANNOT send a custom header or application/json without
  // triggering a CORS preflight — which our CORS config does not grant to other
  // origins. So requiring either is a wall a cross-site page cannot climb.
  const hasCustomHeader = req.get("X-Requested-With") === "fetch";
  const isJson = req.is("application/json");

  if (!hasCustomHeader && !isJson) {
    return res.status(403).json({ error: "csrf_check_failed" });
  }

  // Belt-and-suspenders, nearly free: reject a wrong Origin outright.
  const origin = req.get("Origin");
  if (origin && origin !== "https://app.example.com") {
    return res.status(403).json({ error: "bad_origin" });
  }
  next();
}
```

> The load-bearing insight is in the comment: the defense is not the *value* of the header, it's that a cross-site page is **structurally unable to set it** on a request the browser will send silently. Adding a custom header (or `Content-Type: application/json`) upgrades the request to one that requires a CORS preflight, and the preflight is where the browser asks your server "may this other origin do this?" — to which the answer is no. The attacker never gets to the actual request. This is why a SPA that sends `fetch` with a custom header and JSON body often needs no token at all — the header requirement *is* the token, provided by the browser's own preflight rules.

And the failure mode to call out where it lives — the CORS config this depends on:

```ts
// This defense is only as good as the CORS policy behind it.
app.use(cors({
  origin: "https://app.example.com",   // NOT true, NOT a reflected origin
  credentials: true,
}));
// If origin is set to reflect the request's Origin AND credentials:true,
// you've told the browser every site may make credentialed requests —
// which grants the preflight the header check was relying on it to deny.
// The CSRF hole reopens through the CORS config, invisibly.
```

The signed double-submit, for an API layer without server-side session storage, is the one remaining shape — the cookie value is `HMAC(sessionId)` so a subdomain that can set the cookie still can't produce a matching header without the server's key. Worth knowing it exists; reach for it only when you have neither server-side token storage nor a same-origin-only API.

## Further Reading

- **OWASP Cross-Site Request Forgery Prevention Cheat Sheet.** The definitive per-technique guide, including the signed double-submit construction and the explicit recommendation to combine SameSite with a token defense rather than choosing one.
- **PortSwigger Web Security Academy — CSRF, and "Bypassing SameSite restrictions."** Interactive labs that make the SameSite gaps (GET, subdomain, the method and content-type tricks) concrete rather than theoretical. The single best way to stop over-trusting SameSite.
- **RFC 6265bis (Cookies: HTTP State Management), the SameSite sections.** The specification of the attribute's three values and the same-site/cross-site definitions, including why a subdomain counts as same-site.
- **The Chromium SameSite FAQ.** The authority on the default behaviour, the 2-minute top-level-POST exception, and the `SameSite=None; Secure` requirement — the details that decide whether "the default protects me" is true for your users.
- **MDN, "SameSite cookies" and "CORS preflight."** The reference for what makes a request "simple" versus preflighted, which is the mechanism the custom-header defense rests on.
- Within this map: cookies, sessions, `HttpOnly`, and bearer-token trade-offs in **Module 4**; XSS and the "fix XSS before CSRF" priority in **20.2**; CORS misconfiguration in **20.2/20.4**; the GraphQL content-type angle in **Module 8**; and step-up authentication in **4.1c**.

A **Java/Spring Security** sibling would earn its place, because Spring inverts the "you must remember to add it" default: CSRF protection is *on* by default for state-changing requests, and the interesting content is the reverse mistake — teams disabling it wholesale (`.csrf().disable()`) to make a REST client or a webhook receiver work, instead of exempting the specific stateless, token-authenticated routes that genuinely don't need it. Seeing where a framework's secure default gets switched off under deadline pressure, and how to exempt narrowly instead, is the other half of this lesson. Not yet written.

---

The habit to carry into every endpoint: **separate "who is this?" from "did they mean to do this?"** Authentication and authorization answer the first; a valid cookie proves identity and nothing about intent. CSRF is the entire category of bug that lives in the gap — a real user's real credential, driving a request the real user never chose. Ask of every state-changing route: if someone put this exact request on a page across the internet and a logged-in user opened it, what would stop it? If the answer is "nothing," you've found the bug, and it doesn't matter how good the rest of the endpoint is.
