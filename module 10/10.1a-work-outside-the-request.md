# Work Outside the Request

_Module 10.1a — Background Jobs & Task Queues_

## The Problem

An expense-management product. At month end, finance uploads a CSV of card transactions; the app matches each row to a submitted receipt, converts foreign currency at the transaction date's rate, writes the expenses, and emails the submitter a summary.

One handler does all of it.

```
POST /imports
  ├─ parse CSV                          120ms
  ├─ for each of 480 rows
  │    ├─ fetch FX rate (3rd party)      90ms
  │    └─ match receipt + insert         15ms
  ├─ write import summary                 8ms
  └─ send confirmation email            600ms
                                      ───────
                                        ~51s
```

Things break in a predictable order.

**The load balancer gives up at 30 seconds.** The user sees a 504. The work carries on server-side, invisibly, and finishes fine — which is arguably worse, because now the UI and the database disagree.

**So the user clicks Import again.** The first run's inserts are already committed. Two hundred rows are now duplicated, and someone in finance finds out during a reconciliation three weeks later.

**A deploy lands at 14:03.** Three imports are mid-flight. They die at whatever row they'd reached, with no record of where that was, and nothing retries them.

**The FX provider has a bad ten minutes.** Requests fail at row 300. The endpoint returns 500, having already written 299 expenses, and the retry starts at row 1.

Then the one nobody predicts, which is the important one.

**Login gets slow.**

```
web tier: 50 request workers

  /imports          ████████████████████████████████████████  40 held for ~51s
  everything else                                   ██████████  10 left

  GET /login  →  queued behind an import  →  12s  →  spinner
```

A request worker occupied for 51 seconds is a worker not serving anything else, and the pool is a fixed size. The concurrency limit of the import feature was never chosen — it was inherited from an unrelated number picked when the app was scaffolded. **Slow work in the request path converts one feature's latency into everyone's availability.**

(If your stack is an event loop rather than a thread pool, the arithmetic differs but the shape doesn't: the 480 FX calls are I/O and interleave happily, while the CSV parse and the matching loop block every other request sharing that process.)

## What It Is

Instead of doing the work, the handler writes down that the work needs doing — a **job**: a durable, self-contained description of a task — returns immediately, and a separate process picks the job up and runs it. The thing jobs are pulled from is a **task queue** or **work queue**; the processes pulling are **workers**.

Two neighbours worth separating right away.

**This is not `async`/`await`.** Language-level asynchrony is concurrency *inside* the request — the handler interleaves I/O, but the client still waits and the work still dies when the process does. Firing a promise you never await is worse than either option: the work now has no error path, no retry, and no one watching it.

**This is not the pub/sub fan-out of 9.4.** Both often run on the same broker software, and they have opposite delivery semantics.

```
fan-out (9.4)                        work queue (here)

  event ──┬──▶ node A                  job 1 ──▶ worker A
          ├──▶ node B                  job 2 ──▶ worker B
          └──▶ node C                  job 3 ──▶ worker A

  everyone gets everything            each job goes to exactly one worker
  add a subscriber → more total work  add a worker → less work each
```

The work-queue pattern has a name worth knowing: **competing consumers**. Workers race for the same jobs, and the queue guarantees one of them wins. That single property is what makes horizontal scaling of the worker tier a matter of starting more processes.

## Recognizing the Problem

- An endpoint has a timeout override in your nginx/ALB config, and the number has been raised more than once.
- Gateway 504s on requests that nevertheless complete successfully on the server.
- The UI says "please don't refresh this page," or your support inbox has duplicate-record reports following user retries.
- Unrelated endpoints slow down when one endpoint gets busy.
- Deploys are scheduled for quiet hours because in-flight work is lost.
- There's a cron job that scans for rows stuck in a `pending` state and reprocesses them. That's a retry mechanism you built without deciding to.
- Fire-and-forget calls: an unawaited promise, a bare `go func()`, an after-commit hook that swallows its own errors.
- Your write endpoint's p99 tracks a third party's status page.
- A handler's last line is "send the email," and an email-provider outage fails the entire operation.

## How It Works

Three parts, and one mechanism that makes the whole thing safe.

**Enqueue.** The request handler writes a row (or a message) describing the work: a type, a payload, and when it's eligible to run. Then it returns — typically `202 Accepted` with a URL where the caller can watch progress.

The job is **data, not a closure**. It has to survive serialization, a process restart, and a code deploy. Payloads carry identifiers, not objects: `{ "importId": 8812 }`, never the whole import row. A snapshot of a record taken at enqueue time is already stale when the job runs, and a snapshot of a *user* is PII sitting in your queue's storage.

**The queue.** An ordered-ish store of eligible jobs. Redis, Postgres, RabbitMQ, SQS — the substrate varies, the contract doesn't: hand each job to exactly one worker at a time, and don't lose it if that worker dies.

**Workers.** A loop: claim a job, run it, report the outcome. The number of workers running concurrently is a dial you set deliberately, per queue — which is precisely the thing the request-path version didn't have.

**The lease is what makes it crash-safe.** A worker doesn't remove a job when it claims it; it takes an exclusive hold with an expiry (SQS calls this a *visibility timeout*). If the worker acknowledges before the lease expires, the job is done. If the worker is killed, the lease lapses and the job becomes eligible again.

```
                      ┌───── lease expires (worker died) ─────┐
                      ▼                                       │
  enqueue ──▶ [ ready ] ──claim──▶ [ leased, 60s ] ──ack──▶ [ done ]
                      ▲                   │
                      └── fail + backoff ─┤
                                          └── attempts > N ──▶ [ dead ]
```

This buys crash safety and charges a fixed price for it. A lease can expire because the worker died — or because the worker is alive and merely slow, in which case the job runs *twice, concurrently*. There is no configuration that prevents this; it's the shape of the problem. **Every job handler must be safe to run more than once.** Idempotency isn't a best practice here, it's the payment for durability, and §10.2a is where retries make that bill arrive in full.

**One subtlety at the enqueue end.** The enqueue is itself a write, and usually the *second* write in the handler — you insert the import row, then enqueue the job. If those go to different systems, neither order is safe:

```
commit DB, then enqueue   →  crash in between: the row exists, nothing ever processes it
enqueue, then commit DB   →  worker starts in 2ms, reads the row, it isn't there yet
```

The second failure mode is the one that produces ghost bug reports, because it only happens when the queue is fast. If the queue lives in the same database, you sidestep it entirely by enqueuing inside the same transaction. If it doesn't, this is the dual-write problem, and the fix is the transactional outbox (Module 37).

## When It's Appropriate

- **Work over roughly a second whose result the caller doesn't need in the response.** The import above; a 40-page PDF render; re-indexing a document after an edit.
- **Any call to a third party whose failure shouldn't fail your write.** The expense is saved; the email provider being down is not the user's problem and shouldn't roll back their work.
- **Per-request fan-out.** One "invite your team" click, 40 invitation emails. In the request that's 40 sequential failure points; as jobs it's 40 independently retryable units.
- **Work that must eventually happen even if everything crashes.** Billing runs, webhook delivery, provisioning. The durable record of intent is the point; the latency improvement is incidental.
- **Spiky arrival you'd rather smooth.** 4,000 receipt uploads land at 23:58 on the last day of the month against a pipeline that processes 50/s. Sized for the peak, that's an idle fleet for 29 days. Queued, it's 80 seconds of lag nobody notices — the queue is a shock absorber.
- **CPU-heavy work you want on other machines.** Video transcode, OCR, report generation. Separate worker instances can be sized differently, scaled independently, and run on interruptible capacity, because a killed worker just means an expired lease.
- **Anything periodic** — the scheduling half of this, covered in 10.3.

## When It's Unnecessary or Overkill

- **The work takes 80ms.** The enqueue is a write of its own, plus dispatch latency. You'd be adding a table, a process, a state machine, and a new class of production incident to save 80 milliseconds.
- **The user is going to sit and stare at the page until it's finished anyway.** Backgrounding a 4-second operation doesn't remove the 4 seconds; it replaces one 4-second request with a fast request, a polling loop, and a progress UI. Do it because you need the crash-safety and the isolation. Don't do it for latency you didn't actually remove.
- **Anything that must return an error to the caller.** Validation, authorization, uniqueness, payment authorization. A user can act on a 400 immediately; they can't act nearly as well on "your import failed" emailed 90 seconds later, and often won't see it at all.
- **Read-after-write matters.** If the user is expected to see the result on the next page load, eventual consistency is now a UI problem you have to solve on purpose.
- **Single-process deployments where losing the work is genuinely acceptable** — a best-effort analytics ping. Fire-and-forget is a legitimate choice. The failure mode is choosing it silently and then treating it as reliable.

## Trade-offs

- **You've made part of your system eventually consistent, and the UI has to admit it.** Statuses, progress, a page that says "processing," a way for a user to tell "queued" from "quietly failed." That's real product work, not plumbing.
- **Failures go silent.** A 500 reaches a human within seconds. A failed job reaches nobody unless you build the path: a dead-letter queue, alerting, and someone whose job is to look. The metric that matters is the *age of the oldest ready job*, not queue depth — depth of 10,000 draining fast is healthy; depth of 3 where the oldest is 40 minutes old means a worker is wedged.
- **Every handler must be idempotent**, and you'll need natural keys and unique constraints to make that enforceable rather than aspirational.
- **Two deployables, two versions, one queue.** Jobs enqueued by v34 get executed by v35. Payload fields must be added before they're required and removed at least one release after they stop being written — and a job sitting in a paused queue over a weekend will come back to code that no longer recognizes it.
- **Debugging crosses a process boundary.** A correlation id in every payload, propagated into every log line, is not optional; without it you have two log streams and no way to join them.
- **Ordering is gone by default.** Competing consumers process concurrently, so job B can finish before job A. If B depends on A, enqueue B *from* A rather than enqueuing both up front.
- **Backpressure moves; it doesn't vanish** (9.1b). A queue is a buffer, and a buffer only absorbs bursts. If the arrival rate exceeds the service rate on average, depth grows without bound and your fast endpoint is issuing promises the system can't keep. Latency didn't go away — it became unbounded and invisible.
- **More infrastructure to operate.** Redis persistence settings that actually persist, a broker to patch, a worker fleet to scale, local dev and tests that need an inline execution mode or they'll be flaky.

## Alternatives

- **Make it fast enough to stay in the request.** Frequently the right answer, and usually unexamined. Batch the 480 FX lookups into one call, replace 480 inserts with one bulk write, cache the day's rates — 51 seconds becomes 900ms and the article you needed was about N+1, not queues.
- **Stream the response.** SSE or chunked transfer keeps the connection honest and shows progress (Module 9). The user still waits and the request worker is still occupied, so this solves the UX and not the isolation.
- **A `status = 'pending'` column and a cron sweeper.** No queue at all: write the row, let a periodic task pick it up. Latency is the sweep interval, there's no per-job retry or priority, and it's completely adequate for work that runs hourly. Many teams need nothing more.
- **Hosted queues** — SQS, Cloud Tasks, Pub/Sub. Leases, retries, and dead-letter handling already built; no fleet if you pair them with functions (Module 41). You give up transactional enqueue with your database and accept payload size limits.
- **Broker work queues** — RabbitMQ competing consumers, Kafka consumer groups where a partition is both the unit of ordering and the unit of parallelism. Module 37 covers the durable-log end of this.
- **Don't do the work.** The confirmation email nobody opens is cheapest to delete.

## How to Achieve It

**Level 0 — measure the handler, split by phase.** Find out whether you have a queue problem or an N+1 problem. Time parse, external calls, writes, and notification separately.
_Signal you're here:_ a plan to "move imports to a background job" with no breakdown of where the 51 seconds went.

**Level 1 — one job type, one table, in the database you already have.** A `jobs` table, `FOR UPDATE SKIP LOCKED` to claim, enqueued in the same transaction as the write it belongs to. No new infrastructure, transactional enqueue for free, and it will comfortably carry hundreds of jobs a second.
_Signal you need it:_ one endpoint whose work doesn't belong in a request.

**Level 2 — make the handler idempotent and add retry with backoff.** Unique constraints on the natural key, attempt counting, a terminal failed state you can query.
_Signal you need it:_ the first duplicate email, or the first job that failed once and was gone forever.

**Level 3 — run workers as a separate deployment.** Own process, own image or entrypoint, own scaling, own connection-pool budget. Graceful shutdown on SIGTERM that stops claiming and drains in flight.
_Signal you need it:_ workers and web requests competing for CPU or database connections, or wanting more workers without more web capacity.

**Level 4 — split queues by class of work and set concurrency per queue.** Latency-sensitive jobs (password reset emails) don't share a queue with a nightly 90-minute export.
_Signal you need it:_ a report job starving user-facing notifications. This is the classic one, and it always arrives.

**Level 5 — dedicated queue infrastructure, dead-letter handling, autoscaling on oldest-job age**, and, if the queue no longer lives in your database, an outbox to restore transactional enqueue.
_Signal you need it:_ database contention from the queue table itself, or a scheduling need — priorities, rate limits, unique jobs — that you're now implementing by hand.

Levels 1 and 2 cover more production systems than the tooling ecosystem's marketing would suggest. Skipping to Level 5 on day one buys operational surface before there's load to justify it.

## Implementation

**TypeScript with Postgres.** Chosen because the mechanism should be visible: a library call like `queue.add('import', {...})` hides exactly the parts — the lease, the claim, the acknowledgement — that you need to understand to debug it at 3am.

```sql
create table jobs (
  id           bigserial   primary key,
  queue        text        not null default 'default',
  type         text        not null,
  payload      jsonb       not null,
  run_at       timestamptz not null default now(),
  leased_until timestamptz,
  attempts     int         not null default 0,
  last_error   text
);

create index jobs_claimable on jobs (queue, run_at);
```

The claim is one statement, and `skip locked` is the entire trick: concurrent workers running this simultaneously each get a *different* row instead of queueing behind the same one.

```sql
update jobs
   set leased_until = now() + interval '60 seconds',
       attempts     = attempts + 1
 where id = (
   select id from jobs
    where queue = $1
      and run_at <= now()
      and (leased_until is null or leased_until < now())
    order by run_at
      for update skip locked
    limit 1
 )
returning id, type, payload, attempts;
```

Enqueueing happens inside the transaction that creates the thing the job is about:

```ts
await tx.query("begin");
const { rows: [imp] } = await tx.query(
  `insert into imports (account_id, filename, status)
   values ($1, $2, 'queued') returning id`,
  [accountId, filename]
);
await tx.query(
  `insert into jobs (type, payload) values ('import.process', $1)`,
  [{ importId: imp.id, correlationId: req.id }]
);
await tx.query("commit");

res.status(202).location(`/imports/${imp.id}`).json({ status: "queued" });
```

> **Aside 1.** There is no window in which the import row exists without its job, or the job without its row — they commit together. That property is the main reason to start with a database-backed queue, and the first thing you lose when you move the queue to Redis. Notice also what the payload carries: two identifiers. Not the parsed CSV, not the user record.

The worker loop is unremarkable, which is the point:

```ts
let draining = false;
process.on("SIGTERM", () => { draining = true; });

async function worker() {
  while (!draining) {
    const job = await claim("default");
    if (!job) { await sleep(500); continue; }   // aside 2

    try {
      await handlers[job.type](job.payload);
      await db.query(`delete from jobs where id = $1`, [job.id]);
    } catch (err) {
      const backoff = Math.min(2 ** job.attempts, 300);
      await db.query(
        `update jobs
            set leased_until = null,
                run_at       = now() + ($2 || ' seconds')::interval,
                last_error   = $3
          where id = $1`,
        [job.id, backoff, String(err)]
      );
    }
  }
}

await Promise.all(Array.from({ length: 5 }, worker));  // the concurrency dial
```

> **Aside 2.** That `sleep(500)` is polling, with all the costs 9.1a laid out — an idle queue still runs two queries a second per worker. Postgres `LISTEN`/`NOTIFY` fired from the enqueue turns this into push and drops idle latency to near zero; keep the poll as a floor anyway, because notifications sent while a worker is between statements are simply missed.

And the handler, where idempotency has to be structural:

```ts
handlers["import.process"] = async ({ importId }) => {
  const rows = await parse(await fetchFile(importId));
  for (const [i, row] of rows.entries()) {
    await db.query(
      `insert into expenses (import_id, row_no, amount, currency, spent_on)
       values ($1, $2, $3, $4, $5)
       on conflict (import_id, row_no) do nothing`,
      [importId, i, row.amount, row.currency, row.date]
    );
  }
  await db.query(`update imports set status = 'done' where id = $1`, [importId]);
};
```

> **Aside 3.** `on conflict (import_id, row_no) do nothing` is doing the work that the application code isn't. A duplicate run is harmless because a unique constraint says so, not because the handler is careful — and a constraint keeps being true under concurrency, after a refactor, and when someone re-runs the job by hand. Re-running still repeats the FX lookups, though: for expensive external calls, checkpoint progress on the import row so a restart resumes rather than replays.

Two things about shutdown. `draining` stops the worker *claiming* new jobs, but an orchestrator that kills the pod 30 seconds later will still sever a 51-second job mid-flight. That's survivable precisely because of the lease: 60 seconds later the job is claimable again and runs to completion somewhere else. **The lease is what makes deploys safe; idempotency is what makes the lease safe.** Neither works without the other.

> **Aside 4.** Those five "workers" are five interleaved promises on one thread. For I/O-bound jobs — HTTP calls, database round trips — that's genuine concurrency and the dial means what it says. For a CPU-bound handler like parsing a 50MB CSV, the fifth worker doesn't merely fail to help; all five now block each other, and the worker process stops responding to its own health check. In Node, CPU-bound job concurrency means separate processes or `worker_threads`, and it's worth knowing which kind of work your queue carries before setting that number.

## Further Reading

- **PostgreSQL documentation — "The Locking Clause,"** on `FOR UPDATE ... SKIP LOCKED`. Short, and the semantics are exactly what the claim query depends on.
- **Craig Ringer, "What is SKIP LOCKED for in PostgreSQL 9.5?"** — the canonical write-up of why a queue on a relational database stopped being a bad idea.
- **Brandur Leach, "Transactionally Staged Job Drains in Postgres"** — the enqueue/commit ordering problem taken seriously, and the bridge to the outbox pattern.
- **Amazon SQS Developer Guide, "Visibility timeout" and "At-least-once delivery."** The clearest available statement that duplicate delivery is a property of the model rather than a defect.
- **Hohpe & Woolf, _Enterprise Integration Patterns_** — Competing Consumers, Guaranteed Delivery, Dead Letter Channel, Idempotent Receiver. Pre-dates every tool named here and explains all of them.
- **Sidekiq wiki, "Best Practices"** — three short rules (make jobs small, make arguments simple, make jobs idempotent) that took the Ruby ecosystem a decade of outages to compress.
- **Kleppmann, _Designing Data-Intensive Applications_, ch. 11** — specifically the section separating load balancing across consumers from fan-out to all consumers, which is the 9.4 distinction stated formally.

A Go sibling would earn its place here, because the language changes the shape of two things this article had to work around: a worker pool is genuinely parallel and CPU-bound jobs stop being a special case, and `context` cancellation makes lease expiry propagate into the handler's own I/O rather than being something you remember to check. Not yet written.

---

The habit to take away: for every write endpoint, sort what it does into two piles — what the user needs to have happened *before* they see a response, and what merely needs to be **guaranteed** to happen. Those are different requirements, and the request path can only deliver the first. Most handlers mix them by accident, and the mixture is what turns an email provider's bad afternoon into your own.
