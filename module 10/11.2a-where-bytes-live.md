# Where Bytes Live

_Module 11.2a — File Storage & Management_

## The Problem

A veterinary imaging platform. Clinics upload X-rays, CT series, and ultrasound clips; vets review them in the browser; regulation says the studies are kept for seven years. About 400 TB and growing.

Storage was budgeted from the number on the pricing page — around $0.023 per GB per month, so roughly $9,200. The first full invoice is a little over three times that, and storage is the *smallest* line on it.

```
storage        400 TB × $0.023                       ≈  $ 9,200
egress         180 TB viewed × $0.09                 ≈  $16,200
requests       410M GETs + 90M PUTs + LISTs          ≈  $ 2,400
retrieval      cold-tier restores nobody predicted   ≈  $ 3,100
                                                       ────────
                                                       ≈ $30,900
```

**Object storage is priced along at least four axes, and only one of them appears in the comparison tables.** Everything below follows from that.

**The saving that cost money.** Someone reads about archive tiers and writes a lifecycle rule: everything older than 30 days moves to a deep archive class. Three things then happen. A vet opens a two-year-old study and waits — first-byte latency for deep archive is measured in hours, not milliseconds. The retrieval itself is billed per gigabyte. And a nightly job that regenerates thumbnails across the corpus triggers restores on millions of objects, which produces a five-figure line item for reading data you already owned. The rule also caught 40 million small thumbnails, each of which is billed at a minimum object size and carries per-object archive overhead, so archiving them cost *more* than leaving them alone.

**The bucket that grows when you delete.** Versioning was enabled for safety, which was correct. Nobody added a rule to expire non-current versions, which was not. Deleting an object now writes a delete marker and retains the old version; a nightly job that overwrites derivatives creates a new version every night. Total bucket size is now substantially larger than the sum of everything you can list, and nobody can explain the gap.

**Egress, which is most of the bill, is the part nobody designed.** Every study view streams from the origin bucket to a vet's browser at full price. There is no CDN, because a CDN was filed under "performance" and the pages felt fast enough.

**And the rename.** A clinic reorganizes its folders. The code does what filesystem-shaped code does — and discovers that object storage has no rename. A "move" is a copy plus a delete: it transfers every byte, costs a request pair per object, takes minutes for a large study, and can fail halfway, leaving objects in both places or neither.

## What It Is

**Object storage** is a flat keyspace of immutable blobs behind an HTTP API. Not a filesystem: no directories, no partial writes, no append, no locking, no atomic rename, no transactions across objects. What it does offer is effectively unbounded capacity, very high durability, and a price per gigabyte that makes capacity planning mostly obsolete.

The vocabulary that ends up on your invoice: a **storage class** (or tier) trades resting cost against retrieval latency and a **retrieval fee**; a **lifecycle policy** is a standing program that moves and deletes objects on age; **versioning** retains superseded objects; **egress** is data leaving the provider's network; and **durability** — the eleven-nines figure — is a statement about hardware failure and nothing else.

Three distinctions worth fixing now, because each one is a recurring expensive mistake:

- **Object vs file vs block storage.** Block storage is a disk; file storage (EFS, NFS) is POSIX over a network; object storage is neither. Choosing file storage so that existing filesystem-shaped code runs unchanged is common and costs roughly five to ten times more per gigabyte — you are paying a large premium to preserve an API.
- **Durability is not backup.** Eleven nines means the provider will not lose your object to disk failure. It says nothing about your own code deleting it, a bad migration overwriting it, or a leaked credential destroying it — and those are how data is actually lost.
- **Replication is not backup either.** Replication faithfully propagates your mistake to the second region, on a delay measured in seconds.

## Recognizing the Problem

- The storage line is the smallest part of your storage bill.
- Bucket size exceeds the total size of everything you can enumerate.
- Retrieval or early-deletion charges appear on an invoice at all.
- A lifecycle rule that was written before anyone measured the access-age curve.
- A nightly job that lists or reads the entire bucket.
- Code that moves, renames, or reorganizes objects.
- Tens of millions of objects under 100KB.
- Egress per active user rising month over month.
- A proposal to use network file storage so existing code works unchanged.
- An incident whose mitigation was "restore from the bucket," with versioning off.
- No one can say what fraction of reads target objects older than 90 days.

## How It Works

**Price per business action, not per gigabyte.** The useful number is the cost of one study viewed, or one user-month — storage plus requests plus egress plus any retrieval. That figure tells you which axis to attack; `$/GB` tells you almost nothing, and in the example above it would have sent you after 30% of the bill while ignoring half of it.

**A storage class is a bet on the access-age curve.** So measure the curve first: what share of reads land on objects older than 30, 90, 365 days? Then the classes line up against it:

```
standard         instant, no retrieval fee                    the default, and usually right for hot data
infrequent       cheaper to rest, per-GB retrieval fee,       a win for large objects read a few times a year
                 ~30-day minimum billable duration
archive / deep   much cheaper, minutes-to-hours first byte,   a win only for genuinely cold, large, patient data
                 90–180-day minimums, per-object overhead
```

The wager is asymmetric. Being right saves a fraction of the smallest line on the bill; being wrong costs a retrieval fee *and* makes a user wait, at the exact moment they're waiting. Two rules of thumb keep most teams out of trouble: transition on an age well past where reads actually stop, not where they start declining; and don't tier small objects at all — below roughly a megabyte, minimum billable sizes and per-object overhead eat the saving and often invert it. If you can't measure the curve, an automatic tiering class that charges a small per-object monitoring fee is usually a better deal than guessing, because it removes the retrieval-latency risk entirely.

**Lifecycle rules are a program that runs on your data forever.** Transitions, expirations, non-current version expiry, and aborting incomplete multipart uploads (11.1a's abandoned parts, which are billed and invisible in a listing). They evaluate asynchronously — daily, not instantly — and they act on data you can't easily preview. Scope the first one to a prefix.

**Versioning needs a partner rule.** On its own it is the best protection you have against your own code, and it converts every overwrite into permanent growth. Pair it with non-current expiration from the start, and understand that deletion is now a two-step concept: a delete marker hides an object, and the versions underneath it are still there and still billed. That distinction also collides with erasure obligations — "delete this patient's data" means deleting *versions*, plus replicas, plus any backup, which is a Module 34 problem that begins here.

**Egress is where a CDN pays for itself before latency is even mentioned.** Data in is free; data out is the expensive direction. Origin-to-CDN transfer is frequently free or discounted, and CDN-to-user is cheaper at volume — so a cache hit ratio is a financial metric before it's a performance one.

```
no CDN     180 TB × $0.09           = $16,200
CDN @ 85%  27 TB origin (discounted) + 180 TB × ~$0.02  ≈ $ 3,800
```

One trap connects this directly to the next article: if every user gets a uniquely signed URL and the query string is part of the cache key, every request is a miss and the CDN is an expensive proxy. Signed cookies, or a cache key that excludes the signature, are what make the two features coexist.

**Design for a keyspace, not a tree.** There are no directories; a prefix is a naming convention that listing happens to sort by. Since there is no rename, **the storage key must be immutable identity, and everything mutable — folder, display name, ordering — belongs in your database.** Then reorganizing ten thousand files is one `UPDATE`: atomic, instant, free. The filesystem-shaped alternative is ten thousand copy-and-delete pairs that cost money, take minutes, and can fail in the middle.

```
key as identity        folders: one UPDATE, 0 bytes moved, atomic
key as path            folders: N copy+delete, N × size bytes moved, no atomicity
```

This is the same rule 11.1a arrived at from the security side — the server names the key, opaquely — reached here from the cost side.

## When It's Appropriate

- **When storage is a visible share of infrastructure spend**, or growing faster than your user count. Below that, this is all premature.
- **Large objects with a genuinely cold tail** — imaging, video masters, raw logs, database backups. Multi-megabyte objects with under a few percent of reads after 90 days are exactly what archive tiers were built for.
- **Read-heavy content served to many users** — that's the CDN case, and the arithmetic usually settles it without anyone arguing about latency.
- **Anything a bad deploy could destroy** — versioning, always, plus a copy under separate credentials.
- **Regulated retention.** Seven-year obligations want object lock or equivalent, deliberately and with the retention mode understood.

## When It's Unnecessary or Overkill

- **Under a few terabytes.** Two TB in a standard class is roughly $46 a month. No lifecycle policy is worth a day of engineering at that scale, and the risk of a wrong rule exceeds the saving.
- **Data that stays hot.** Avatars, thumbnails, current documents. Tiering them is a straight loss.
- **Corpora of tiny objects.** Millions of sub-100KB files are dominated by per-object costs; tiering makes it worse. If they're cold, packing them into archives changes the cost driver, and that's a bigger lever than any class.
- **Private, low-traffic downloads.** A CDN adds a second access-control surface and a cache-invalidation problem for traffic that wasn't costing anything.
- **When the real answer is deleting things.** Expired derivatives, abandoned uploads, superseded exports, logs nobody reads. Deletion beats every optimization in this article and needs no new concepts.

## Trade-offs

- **Tiering trades money for latency and for a bill you pay when a user is waiting.** The cost of a wrong guess is not symmetric with the saving from a right one.
- **Archive tiers leak into your product.** If objects can take hours to retrieve, the interface needs a "retrieving" state, a background poller, and an expectation set for the user. If the product can't say "check back later," it can't use deep archive, whatever the spreadsheet says.
- **Versioning makes deletion ambiguous.** "Is it gone?" becomes a question about markers and versions, and compliance deletion becomes a deliberate enumeration.
- **A CDN adds cache invalidation, a second authorization model, and stale-content confusion** to something that previously had one source of truth.
- **Cross-region replication doubles storage cost**, adds egress, and protects against a region outage rather than against you.
- **Object lock can make an expensive mistake permanent.** Compliance mode means nobody — including the account root — can delete those objects before the retention expires. Including the 400TB you wrote by accident.
- **Egress fees are the lock-in.** Data gravity isn't a metaphor; the cost of leaving scales with how much you've stored, which is a business model as much as a pricing table.
- **Object count is a cost driver independent of size**, and almost nothing in your monitoring shows it to you.

## Alternatives

- **Store less.** Shorter retention on derivatives, aggressive expiry on exports and temporary artifacts. Always available, always cheapest.
- **Regenerate instead of retaining.** Thumbnails, transcodes, and rendered PDFs can be recomputed. Store them only while recomputation is more expensive than storage — which, for a derivative read twice a year, it isn't.
- **Pack small objects.** Cold corpora of tiny files become one archive per day or per tenant, which collapses request counts, per-object overheads, and listing costs at once.
- **A provider whose pricing has a different shape.** Zero-egress object storage exists, and for egress-dominated workloads it changes the answer rather than trimming it. The trade is ecosystem integration and, usually, fewer storage classes.
- **Block or file storage** where POSIX semantics are genuinely required — random writes, memory-mapped access, legacy tooling that cannot be changed.
- **The database, for tiny objects** (11.1a) — one system, one transaction, no orphans, no lifecycle rules.
- **Self-hosting** — MinIO, Ceph. Real savings at real scale, paid for in people. Rarely the right call below petabytes.

## How to Achieve It

**Level 0 — get the bill broken down by axis, and measure two distributions:** reads by object age, and objects by size. Almost every wrong storage decision is made without these.
_Signal you're here:_ you can quote your cost per GB and not your cost per view.

**Level 1 — delete and expire.** Abort incomplete multipart uploads, expire non-current versions, expire quarantine and temp prefixes. Pure saving, no access-pattern bet, no risk.
_Signal you need it:_ bucket size exceeds what you can list.

**Level 2 — put a CDN in front of read-heavy content** and treat cache hit ratio as a cost metric. Fix the cache key so signed URLs don't defeat it.
_Signal you need it:_ egress is the largest line.

**Level 3 — one lifecycle transition, scoped by prefix and object size**, based on the measured curve — or automatic tiering if the curve is unknown.
_Signal you need it:_ a large, measurably cold tail.

**Level 4 — versioning with non-current expiry, plus a backup copy in a separate account** with separate credentials and its own lifecycle.
_Signal you need it:_ any data whose loss would be an incident rather than an inconvenience.

**Level 5 — archive tiers with a product-level restore flow, object lock for regulated retention, and packing for small-file corpora.**
_Signal you need it:_ multi-year retention on data that is genuinely never read.

## Implementation

Most of this is configuration rather than code, so the configuration is the artifact worth reading. Four lifecycle rules, in the order you'd adopt them:

```json
{ "Rules": [
  { "ID": "abort-incomplete-multipart", "Status": "Enabled",
    "Filter": { "Prefix": "" },
    "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 } },

  { "ID": "expire-noncurrent-versions", "Status": "Enabled",
    "Filter": { "Prefix": "" },
    "NoncurrentVersionExpiration": { "NoncurrentDays": 30 } },

  { "ID": "quarantine-cleanup", "Status": "Enabled",
    "Filter": { "Prefix": "quarantine/" },
    "Expiration": { "Days": 1 } },

  { "ID": "studies-to-archive", "Status": "Enabled",
    "Filter": { "And": { "Prefix": "studies/", "ObjectSizeGreaterThan": 1048576 } },
    "Transitions": [ { "Days": 150, "StorageClass": "GLACIER_IR" } ] }
] }
```

> **Aside 1.** The first three are free money: they delete things nobody wants, and none of them is a bet about the future. Only the fourth makes a prediction, and note the two constraints on it. `ObjectSizeGreaterThan` excludes the thumbnails, because tiering small objects loses once minimum billable sizes and per-object overhead are counted. And 150 days is chosen to sit safely past both the 90-day minimum duration and the age at which the measured read curve goes flat — not at 30 days, which is where reads merely start declining and where a transition would be followed by retrievals you paid to avoid.

The rule that makes structure cheap lives in the schema, not the bucket:

```sql
create table study_files (
  id           uuid primary key,
  storage_key  text not null unique,   -- opaque, immutable, never derived from anything mutable
  folder_id    uuid not null references folders(id),
  display_name text not null
);
```

Moving a clinic's entire archive between folders is `update study_files set folder_id = $2 where folder_id = $1` — atomic, instant, and it transfers nothing. The same operation against a bucket whose keys encode the folder path is N copy-and-delete pairs with no atomicity and a bill attached.

**Go** for the one piece that genuinely needs code: serving an object that may be in an archive class.

```go
func serveStudy(ctx context.Context, f StudyFile) (io.ReadCloser, error) {
	head, err := s3c.HeadObject(ctx, &s3.HeadObjectInput{Bucket: &bucket, Key: &f.StorageKey})
	if err != nil {
		return nil, err
	}

	archived := head.StorageClass == types.StorageClassGlacier ||
		head.StorageClass == types.StorageClassDeepArchive

	switch {
	case !archived:
		return open(ctx, f)

	case head.Restore != nil && strings.Contains(*head.Restore, `ongoing-request="false"`):
		return open(ctx, f) // restored copy is available

	case head.Restore != nil:
		return nil, ErrRestoreInProgress

	default:
		_, err := s3c.RestoreObject(ctx, &s3.RestoreObjectInput{
			Bucket: &bucket, Key: &f.StorageKey,
			RestoreRequest: &types.RestoreRequest{Days: aws.Int32(3)},
		})
		if err != nil && !isAlreadyInProgress(err) {
			return nil, err
		}
		_ = enqueue(ctx, "study.restore_poll", f.ID) // Module 10
		return nil, ErrRestoreInProgress
	}
}
```

> **Aside 2.** `ErrRestoreInProgress` is not an error condition, it's a product state — the handler turns it into a `202` and the interface has to say something honest about hours. That's the real cost of an archive tier and it doesn't appear in any pricing calculator: a UI state, a background poller, and a support answer. The `isAlreadyInProgress` branch matters because two vets opening the same old study is the normal case, not the edge case.

> **Aside 3.** `Days: 3` restores a *temporary copy* for three days; the archived object remains, and you are billed for both during the window. Restore is a read with a duration, not a move — and a job that "restores everything" therefore doubles your storage cost for as long as the window lasts, on top of the per-gigabyte retrieval fee.

A sibling article in another language wouldn't earn its place here: the content is economics and configuration, and the only code involved is an SDK call that looks the same everywhere. The forward references that do matter are 11.3 for derivative generation — which is where "regenerate instead of retain" becomes a design — and 11.4 for the signed-URL and cache-key interaction sketched above.

## Further Reading

- **AWS S3 documentation, "Using Amazon S3 storage classes"** and the pricing page's notes on **minimum storage duration and per-object overhead** — the two footnotes that decide whether tiering small objects saves or costs money.
- **AWS S3 documentation, "Managing the lifecycle of objects"** — the full element set, including `ObjectSizeGreaterThan`, non-current expiration, and abort-incomplete-multipart.
- **AWS S3 documentation, "Restoring an archived object"** — retrieval tiers, restore duration semantics, and the fact that you pay for both copies during the window.
- **AWS S3 documentation, "Amazon S3 data consistency model"** — what became strongly consistent in 2020 and what did not, which is the correction to most of what's written about S3 online.
- **AWS S3 Object Lock documentation** — governance versus compliance mode, and an unusually clear statement of what "nobody can delete this" means in practice.
- **Amazon CloudFront documentation, "Cache key and origin requests"** — how query strings enter the cache key, and therefore how signed URLs quietly defeat caching.
- **Cloudflare R2 documentation on egress pricing** — worth reading as a statement of the cost model rather than as a recommendation; it clarifies which of your costs are physics and which are pricing strategy.
- **Corey Quinn, "The Compelling Economics of AWS Data Transfer"** — the egress axis taken seriously, and funnier than it needs to be.
