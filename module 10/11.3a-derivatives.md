# Derivatives

_Module 11.3a — File Storage & Management_

## The Problem

A wedding-photography delivery platform. A photographer uploads three thousand images per event; clients browse a gallery, pick favourites, and download finals. Every source image needs six renditions: a grid thumbnail, a lightbox size, two retina variants, a watermarked proof, and a download-quality JPEG.

Three thousand photos becomes eighteen thousand files per event. That part is expected and works fine.

**Then the design changes.** The gallery grid goes from 400px to 480px and gains a new density variant. Two new renditions are now needed — not for new uploads, for everything. Forty million existing photos, eighty million new files, a backfill measured in weeks of compute and a five-figure bill. Most of those galleries were last opened two years ago and will never be opened again.

The uncomfortable observation underneath: **the renditions were pre-computed for a layout, and layouts change far more often than photographs do.** Eager generation quietly coupled the storage footprint to the CSS.

**Then the watermark changes.** Brand refresh, new logo, new opacity. The proofs are wrong — but *which* proofs? The key is `photo-8812-proof.jpg`. It was `photo-8812-proof.jpg` last year too, and it will be next year. There is nothing in the file, the key, or the database that records which watermark produced it, so there's no query that separates fresh from stale. The only available operation is "delete everything and regenerate."

That's the real defect, and it generalizes: **a derivative is a cache, and this one was built with no cache key.**

**Then a photographer re-uploads a corrected image** under the same record. The six renditions are now derived from an image that no longer exists. The bucket has them, the CDN has them cached for a year, and browsers have them too. Fixing it means purging three layers of cache for a set of objects you can't enumerate.

**And all of it costs.** Six times the object count — which 11.2a established is its own axis on the bill, independent of bytes — stored for seven years, when roughly 70% of galleries are viewed in their first fortnight and never again. Most of those renditions are generated once, stored forever, and read zero times.

## What It Is

A **derivative** (also rendition, variant, transcode, preview) is a pure function of a source file and a recipe:

```
derivative = render(source_bytes, recipe)
```

Taking that definition seriously answers most of the questions in this article. If it's a pure function, then the derivative is **reproducible**, which means it is a cache and not data — losing it is a cost event, not a data-loss event. And it means its correct identity is a function of both inputs: the source version *and* the recipe version.

Two neighbours worth separating. A derivative is not a source of truth, and the difference should show up in how you treat it: derivatives don't belong in backups, and "we lost the thumbnail bucket" should be a Tuesday, not an incident. And a derivative store is not a CDN cache — but it is the same kind of thing one layer down: a cache with an extremely long TTL and, by default, manual invalidation. Most of the pain above comes from having built the second one without admitting it was a cache at all.

## Recognizing the Problem

- A backfill job scheduled because a designer changed a breakpoint.
- Derivative keys containing no hash and no version.
- "Purge the prefix and regenerate" appearing in a deployment runbook.
- A frontend developer appending `?v=2` to an image URL by hand.
- Broken images on records that definitely exist.
- Object count growing by a multiple every time the UI changes.
- A CDN purge that can't be scoped, because nobody can list what went stale.
- A thumbnail that disagrees with its source, and no way to tell which is right.
- Derivatives included in backups, or restored during an incident.
- An image-processing queue that spikes into the millions after a product meeting.

## How It Works

**Put the identity in the key, and invalidation stops existing.**

```
d/{source_content_hash}/{preset_id}-{preset_version}.{ext}
```

Both halves are load-bearing. A re-uploaded source has a different content hash, so it lands on a different key. A changed recipe — new watermark, new dimensions, new quality setting — is a new preset version, so it lands on a different key. In both cases the URL changes, which means:

```
mutable key                              content-addressed key

/img/8812-thumb.jpg                      /d/9f2c…/grid-v3.webp
  same URL, different bytes over time      one URL, one set of bytes, forever
  → CDN purge, browser cache busting,      → cache immutably for a year
    "which ones are stale?"                → old renditions simply go unreferenced
```

Old derivatives become garbage rather than lies, and garbage is collectable by a lifecycle rule (11.2a) instead of by a purge API. **Invalidation becomes a write you never have to perform**, which is the single most valuable structural idea in this article.

**Then choose when to generate, along two axes: how expensive the render is, and how likely the variant is to be read.**

```
                    cheap to render            expensive to render

certain to be read  either; eager is simpler   eager, with a minimal variant set

rarely read         lazy — this is the         lazy, but it needs a job and a
                    default answer             "preparing" state, never a slow request
```

**Eager** generation on upload gives predictable read latency and a cost you pay at ingest. It also pays for every variant of every source whether or not anyone looks, and it is the reason a layout change becomes a backfill.

**Lazy** generation — an image endpoint that renders on the first request, stores the result, and serves it from storage thereafter — inverts that. Cost scales with *views* rather than uploads, new presets are free, and the back catalogue never needs touching: a photo nobody opens never costs a render. The price is a slow first request and the fact that rendering is now on the read path, where a traffic spike becomes a CPU spike.

The bottom-right cell is the one that bites. A twenty-minute video transcode triggered by a page load is not a cache miss, it's an outage. Expensive derivatives want eager generation of a deliberately small rendition set, with a background job and an honest "preparing" state — the same shape as 11.2a's archive restore, for the same reason.

**Expose presets, not a transform language.** A lazy endpoint that accepts arbitrary `w=`, `h=`, `q=`, and `fm=` is an unauthenticated compute endpoint with an unbounded keyspace: someone iterating widths from 1 to 4000 costs you four thousand renders and four thousand stored objects, and your cache hit ratio goes to zero because no two users request the same URL. A closed set of named presets fixes both problems at once. If you do want open parameters, the signature has to cover them.

**Correctness details that produce real bugs:**

- **EXIF orientation.** The canonical "why are all the thumbnails sideways" bug. Rotate according to the tag, then strip it.
- **Metadata stripping is a privacy control, not a size optimization.** A private source photo carries GPS coordinates; the public thumbnail derived from it carries them too, and now the location of someone's home is behind a CDN URL. The derivative is frequently *more* exposed than its source, and everything in it needs to be deliberate (Module 34).
- **Determinism.** A content-addressed key is a promise that the same inputs produce the same bytes. Upgrading the imaging library breaks that promise silently, so the library version belongs inside the preset version. Bump it when you bump the dependency.
- **Format negotiation.** Serving WebP or AVIF based on the `Accept` header requires `Vary: Accept`, which fragments every cache upstream of you. Encoding the format into the preset and choosing it in the markup (`<picture>`, `srcset`) keeps one URL meaning one thing.
- **Some derivatives are a set, not a file.** An HLS ladder is a manifest plus thousands of segments, and "is it ready" is a question about the whole set.

**The pipeline is a Module 10 pipeline.** Upload completes (11.1a) → enqueue one job per preset, so a failure in the watermark render doesn't discard five successful ones → each job is idempotent because its output key already encodes its identity, so "does the object exist" is the whole check → the source record carries a ready state, and the UI shows a placeholder rather than a broken image while it's false. A tiny blurred inline preview generated synchronously at upload covers that window for a few hundred bytes.

## When It's Appropriate

- **More than two renditions per source.** Below that, the machinery outweighs the problem.
- **Sources much larger than what's displayed** — a 12MB camera JPEG behind a 400px grid cell is a bandwidth problem measured in the egress terms of 11.2a.
- **Any video or audio.** There is no serving a master file to a browser and hoping.
- **Documents that need previewing without downloading** — first-page renders, extracted text for search (Module 12).
- **Format modernization as a cost lever.** AVIF at equivalent quality against JPEG is a large fraction of image egress, and it's a preset change rather than a product change.

## When It's Unnecessary or Overkill

- **One variant of a small source.** Serve the original.
- **Below a certain volume, buy it.** imgix, Cloudinary, Cloudflare Images and similar implement this entire article as a URL format. For most teams that is the correct answer, and building the pipeline is a decision that needs a reason beyond wanting to.
- **Resize before upload.** A phone photo downscaled in the browser to 2000px before it's sent removes the derivative problem, the upload duration problem from 11.1a, and most of the storage cost simultaneously.
- **Eight breakpoints where three would do.** Variant count is a choice, and every preset multiplies storage, object count, and cache misses. `srcset` with three widths is nearly always enough.
- **Documents a browser can render itself.** Client-side PDF rendering removes a whole server-side preview pipeline.

## Trade-offs

- **Lazy generation puts CPU on the read path.** A gallery going viral is now a compute event, needing a concurrency limit (10.4b) and a sensible answer when it's exhausted — a 503 with `Retry-After` or a placeholder, never an unbounded queue on the request path.
- **Cold misses stampede.** Sixty concurrent requests for the same uncached rendition render it sixty times unless something collapses them.
- **Content-addressed keys make enumeration harder.** "All derivatives of this photo" is no longer a prefix scan unless you keep the mapping in your database, so either keep it or accept sweep-based collection.
- **Preset proliferation is permanent.** Every design adds presets and nobody ever deletes one, so the multiplier only grows. Periodically measure which presets are actually requested; usually two of the six are 95% of traffic.
- **Derivatives can be more public than their sources**, and access control has to be applied to them explicitly (11.4).
- **Reprocessing the back catalogue is always expensive.** The design decision isn't how to make it fast; it's whether you ever have to do it.
- **Nondeterminism makes hashes lie.** A library upgrade that changes output bytes without a preset-version bump leaves you serving old renders from a key that claims to be the new recipe — a bug that is nearly impossible to spot by looking.

## Alternatives

- **A managed image or video pipeline.** URL-based transformation as a service, with the CDN, the cache, and the formats included.
- **Edge generation.** A worker or edge function that renders on the way out — lazy generation without operating a render fleet, and with the result cached at the edge by definition.
- **Client-side resizing at upload**, which moves the compute to the device that already has the pixels.
- **Fewer renditions plus responsive markup.** Let the browser choose from three widths instead of pre-rendering eight.
- **Compression at the CDN.** For small sources, serving the original with modern compression and no pipeline at all is a legitimate endpoint.
- **Ask for the variants.** Occasionally the uploader can provide them. Rarely practical, but worth checking before building anything.

## How to Achieve It

**Level 0 — count.** Renditions per source, request share per preset, render cost per preset, and the age distribution of reads. Most teams find two presets carrying nearly all traffic and one that is never requested at all.
_Signal you're here:_ nobody can say which of the six presets the app actually asks for.

**Level 1 — put source hash and preset version in the key**, and set long, immutable cache headers. Even with fully eager generation, this alone deletes the invalidation problem and the backfill-versus-purge dilemma.
_Signal you need it:_ a stale rendition you can't identify.

**Level 2 — one job per preset**, idempotent on the output key, retried independently, with a ready flag and a placeholder in the UI.
_Signal you need it:_ a failed render that shows as a broken image forever.

**Level 3 — go lazy for the long tail**, behind a closed preset list, with request collapsing and a concurrency limit.
_Signal you need it:_ a backfill proposal, or storage dominated by renditions nobody requests.

**Level 4 — expire cold derivatives** with a lifecycle rule and let them regenerate on demand. The bucket becomes what it always was: a cache with a TTL.
_Signal you need it:_ derivative storage growing faster than source storage.

**Level 5 — prune presets, adopt modern formats per preset, and delete the backfill tooling** because the key design means you no longer need it.
_Signal you need it:_ nothing. This is what "done" looks like.

## Implementation

**Go**, chosen for one specific reason: the stampede on a cold derivative has a clean, idiomatic answer in `singleflight`, and the render fleet is a CPU-bound concurrency problem of exactly the kind 10.4b was about.

The key function is the design:

```go
func derivativeKey(src Source, p Preset) string {
	return fmt.Sprintf("d/%s/%s-v%d.%s", src.ContentHash[:16], p.ID, p.Version, p.Ext)
}
```

> **Aside 1.** Both components are doing work. `src.ContentHash` means a re-uploaded source cannot collide with its predecessor. `p.Version` means a recipe change — new watermark, new quality, *or a new version of the imaging library* — produces a different key. That last one is the easiest to forget and the hardest to detect: upgrade libvips without bumping the preset version and you will serve last year's renders from a key that claims to be this year's recipe, with no symptom until someone compares two files by eye.

The lazy endpoint, with the two protections it can't go to production without:

```go
var renders singleflight.Group
var renderSlots = semaphore.NewWeighted(4) // 10.4b: CPU is the constrained resource

func handleDerivative(w http.ResponseWriter, r *http.Request) {
	preset, ok := presets[r.PathValue("preset")] // closed set, not a transform DSL
	if !ok {
		http.Error(w, "unknown preset", http.StatusNotFound)
		return
	}

	src, err := loadSource(r.Context(), r.PathValue("sourceID"))
	if err != nil {
		http.Error(w, "not found", http.StatusNotFound)
		return
	}
	key := derivativeKey(src, preset)

	if !exists(r.Context(), key) {
		_, err, _ = renders.Do(key, func() (any, error) {
			if err := renderSlots.Acquire(r.Context(), 1); err != nil {
				return nil, err
			}
			defer renderSlots.Release(1)

			if exists(r.Context(), key) { // another pod may have won
				return nil, nil
			}
			return nil, render(r.Context(), src, preset, key)
		})
		if err != nil {
			http.Error(w, "busy", http.StatusServiceUnavailable)
			return
		}
	}

	w.Header().Set("Cache-Control", "public, max-age=31536000, immutable")
	http.Redirect(w, r, cdnURL(key), http.StatusFound)
}
```

> **Aside 2.** `singleflight.Group` collapses concurrent misses for the same key into one render, which is what stops a gallery page loading sixty images at launch from rendering each one sixty times. It is deliberately *per-process*: across twelve pods you can still get twelve renders of the same key rather than one. That's fine, and the honest calculation is why — a fleet-wide lock would cost a coordination round trip on every request to save eleven duplicate renders on a cold start. Contrast 10.4b, where the in-process semaphore was the *wrong* scope because the resource was shared; here the resource is this process's CPU, and the duplicate work is bounded and cheap. The rule isn't "always coordinate fleet-wide," it's "match the scope to the resource."

> **Aside 3.** `immutable, max-age=31536000` is safe only because the key is content-addressed. On a key like `8812-thumb.jpg` the identical header is a year-long bug that you cannot fix without a purge, and it is the header most commonly copied from a blog post into exactly that situation.

> **Aside 4.** When the semaphore is exhausted, the request fails with a 503 rather than waiting. That's the right shape for a read path: queueing here converts a CPU shortage into held connections, which is 11.1a's slow-client problem arriving from the other direction. A client that gets a 503 shows the placeholder and retries; a client that waits nine seconds shows nothing and blames the site.

The eager path needs almost nothing on top of Module 10: on upload completion, enqueue one job per preset, where each job's first act is the same `exists(key)` check. The output key *is* the idempotency key, so a redelivered job costs one HEAD request, and 10.2a's retries become free to be generous with.

## Further Reading

- **libvips documentation and its benchmarks** — why the demand-driven, streaming architecture matters when rendering is on a request path, and the memory profile that follows from it.
- **MDN, "Responsive images"** — `srcset`, `sizes`, and `<picture>`. The cheapest way to reduce your rendition count is to let the browser choose from fewer of them.
- **RFC 8246, `Cache-Control: immutable`** — two pages, and the precise statement of what you're promising when you send it.
- **imgix or Cloudinary URL transformation reference** — read as a specification of the preset surface you'd otherwise design yourself, including the parameters they found necessary and the ones they gate.
- **Cloudflare Images / Image Resizing documentation** — lazy generation at the edge, and what the cost model looks like when the render is someone else's problem.
- **Netflix Technology Blog, "Per-Title Encode Optimization"** — how many video renditions to produce, argued from data rather than from a default ladder.
- **Go documentation for `golang.org/x/sync/singleflight`** — small enough to read in full, and the canonical answer to duplicate work under concurrency.
- **BlurHash** — a compact placeholder representation that fits in a database column, for the gap between upload and ready.

A TypeScript sibling would earn its place, because the concurrency story changes rather than the logic: `sharp` does its work off-thread in libuv's pool, so the render limit is `UV_THREADPOOL_SIZE` and not a semaphore you wrote, and getting that number wrong starves DNS and file I/O in the same process for reasons the code gives no hint about. The ecosystem hides the constraint that Go makes you declare. Not yet written.

---

The habit to carry out of this: whenever you find derived data, ask what its cache key is. If the answer is that it doesn't have one — if the name would be the same after the recipe changed — then it isn't a cache, it's a second source of truth, and it has already started drifting from the first.
