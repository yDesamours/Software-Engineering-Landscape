# Serving Files

_Module 11.4a — File Storage & Management_

## The Problem

An online course platform. Lessons are 40-minute videos plus downloadable workbooks, sold per course. The files went into object storage with opaque keys, the bucket was made public, and the player points straight at it:

```
https://assets.example.com/c/9f2c8ad1…/lesson-04.mp4
```

The reasoning was that nobody can guess a UUID. That's true and it's the wrong property. **The URL is the credential**, and URLs escape: browser history, `Referer` headers, a screenshot in a support ticket, a student pasting it into a study-group chat, a scraper that indexed a page it shouldn't have. Once out, it works for everyone, forever, anonymously, with no way to revoke it and no record that it happened.

**So: signed URLs**, with a seven-day expiry chosen because shorter values broke the page. Which changes the failure from permanent to weekly — one student shares a link and a Discord server watches the course for a week. The signature authorizes *the object*, not *the person*.

**So: five minutes.** Now playback breaks. A student seeks to 01:12:00 and the player issues a fresh range request against a URL that expired an hour ago, and gets a 403 in the middle of a lesson. Overnight downloads resumed in the morning fail the same way. The expiry was picked against the wrong quantity: not the duration of a request, but the duration of a *session*.

**So: proxy everything through the application.** Per-request authorization, a real audit trail, complete control. And 11.1a's problem arrives in reverse — every byte flows through a request worker, a 40-minute stream holds a connection for 40 minutes, there's no CDN, egress is billed at origin rates, and you now owe a correct implementation of HTTP range requests or seeking re-downloads the file from zero.

**So: put the CDN back, with signed URLs.** Every student gets a unique signature, the query string is part of the cache key, and the hit ratio collapses to approximately zero. You are now paying for CDN requests *and* full origin egress — the trap 11.2a flagged, met head-on.

**And the thing none of the above solves.** A student cancels at 14:00 and their link keeps working until it expires. Signed URLs are verified offline by the storage service, with no callback to you — which is exactly why they're cheap, and exactly why they cannot be taken back.

That last point is the one worth carrying: **a signed URL moves the authorization decision off the read path and into the issue path.** Everything gained and everything lost follows from that single relocation in time.

## What It Is

Serving a private file is the question of **where the authorization decision is enforced**. There are four places, and picking one is the whole design:

```
                     auth freshness    CDN-cacheable   bytes via you   audit
proxy through app    per request       hard            yes             exact
redirect + signed    at issue time     yes, if shared  no              issue-time only
signed cookie /      at issue time,    yes             no              CDN logs
  path token           short TTL
edge-evaluated       per request       yes             no              at the edge
```

The vocabulary: a **signed URL** is a bearer capability — a URL whose signature encodes an operation, an object, an expiry, and sometimes conditions, verifiable by the storage service without asking you. A **signed cookie** or **path token** moves that credential out of the URL so the URL itself can be shared by every entitled user and therefore cached once. **Revocation latency** is the TTL, because there is no other mechanism.

Two separations worth making immediately. Pre-signed *uploads* (11.1a) point the other way and carry a different risk — a leaked upload URL costs you storage, a leaked download URL costs you your content. And a signed URL is a **capability**, not an identity: a session cookie says who you are, a capability says what the holder may do, and capabilities travel in a way identities don't.

The third separation is the honest one: **none of this is DRM.** Nothing in this article stops a paying student from keeping the bytes. The threat model is casual sharing, enumeration, and access that outlives entitlement. If the actual requirement is that the user must not retain the file, that's device-bound DRM and a different product decision.

## Recognizing the Problem

- Storage URLs appearing in application logs, `Referer` headers, or support screenshots.
- A signature expiry chosen because a shorter one broke the video player.
- CDN hit ratio near zero on content that everybody watches.
- 403s partway through long videos, or on resumed downloads.
- "Who downloaded this?" has no answer.
- Revoking one user's access would require rotating a key that affects everyone.
- A cancelled subscriber whose links still work, and nobody knows for how long.
- A public bucket defended with "the key is a UUID."
- User-uploaded files served from the same domain as the application.
- Download counts materially higher than the number of humans.

## How It Works

**Never hand out storage URLs.** Every file is reached through an application URL — `/lessons/4/video` — which authenticates, checks entitlement, records the intent, and redirects to a short-lived signed URL. The stable URL is the one that gets shared, and sharing it sends the recipient to a login and an entitlement check. That single indirection removes most casual sharing before any cryptography is involved.

**Set the expiry from the revocation requirement, then check it survives the use.** The mechanical detail that resolves the earlier contradiction: a signature is validated **when a request begins**, not throughout. A 60-second URL can therefore serve a 2GB download that takes an hour — the transfer started in time. What breaks is anything that issues *new* requests later: range seeks, resumed downloads, HLS segment fetches. So:

```
one-shot download     60s is plenty — the transfer starts immediately
progressive video     TTL must cover the whole viewing session
segmented (HLS/DASH)  hundreds of requests over hours — use a cookie or token, not a URL
```

**For anything segment-heavy, move the credential out of the URL.** A signed cookie scoped to a path, or a token in a header, means the object URL is identical for every student — one cached copy at the edge, one origin fetch, and the entitlement still checked. This is the resolution of the freshness-versus-cacheability tension, and it's why CDN vendors ship it as a first-class feature.

**Narrow the capability, and know which narrowings are real.** Scoping to a path prefix and a method is genuinely useful. Binding to an IP breaks mobile networks and shared NAT and is usually more outage than defence. Referrer checks stop only the lazy. The strongest lever by a wide margin is a short TTL.

**Revocation is the TTL.** There is no callback, no denylist, no session invalidation — the storage service verifies the signature and serves the bytes. So choose the number by asking how long a cancelled user may retain access, and if the answer is "not at all," you need per-request evaluation at the edge rather than a signature.

**Serve user content from a different origin.** This is the security decision in this article that has nothing to do with signatures. An uploaded HTML file or SVG served inline from your application's domain executes with your cookies and your session — stored cross-site scripting delivered by your own file feature. A separate domain (not a subdomain sharing cookies) plus `X-Content-Type-Options: nosniff`, a `Content-Type` you determined by sniffing rather than by trusting the upload, and `Content-Disposition: attachment` for anything not deliberately rendered inline. 11.1a stored the original filename precisely so it can be returned here, RFC-encoded, without ever having been part of a key.

**Tracking depends on which question you're asking.** Issue-time events are cheap and overcount — prefetches, retries, and players that request a URL they never use. CDN access logs are accurate about bytes and requests, and arrive delayed, needing a pipeline. Client-side beacons are the only thing that knows whether anyone actually *watched*, and they're blockable. Billing and quotas want the logs; product analytics wants the beacons; neither substitutes for the other.

## When It's Appropriate

- **Redirect plus short-lived signature** — the default for private or paid content at any scale. Cheap, no bytes through your infrastructure, and the entitlement check is where it belongs.
- **Proxying through the application** — small files, strict per-request policy, or when the response must be transformed or redacted on the way out. A legal-hold document with a watermark bearing the viewer's name cannot be a redirect.
- **Signed cookies or edge tokens** — many objects per session: video segments, image galleries, a documentation site behind a paywall. Anywhere cache hit ratio has money attached.
- **Edge-evaluated authorization** — when revocation must be immediate, or entitlement is dynamic enough that a five-minute-old decision is wrong.
- **No protection at all** — genuinely public assets. Signing those is a cargo-cult that destroys your hit ratio and adds a failure mode for nothing.

## When It's Unnecessary or Overkill

- **Public content.** If the file is on a marketing page, it's public; treat it that way.
- **Low-stakes internal tools.** Ten employees and a VPN is a complete access-control design.
- **Per-object ACLs where a per-tenant prefix policy would do.** Granularity you don't need is configuration that will drift (Module 5).
- **DRM for a sharing problem.** If the requirement is "not trivially shareable," signatures and a stable app URL get you there; device-bound encryption is a different order of cost and support burden.
- **Edge functions before you've tried cookies.** Per-request evaluation at the edge is powerful and adds a deploy pipeline, a debugging surface, and a vendor coupling. Signed cookies solve a large share of the same problem with configuration.

## Trade-offs

- **A signed URL is a bearer token that looks like a link**, and it will end up in logs, analytics, and screenshots. Redact signature parameters wherever you log URLs, and assume leakage rather than hoping against it.
- **Auth freshness and cacheability genuinely conflict.** Every design here is a position on that trade; edge evaluation buys both and charges for it in operational complexity.
- **Short TTLs mean more signing traffic and more broken long operations. Long TTLs mean longer exposure.** There's no setting that avoids choosing.
- **Proxying reintroduces every problem 11.1a solved**, plus an obligation to implement range requests correctly — which the storage service already does, and which is a strong argument for redirecting.
- **A complete audit trail requires ingesting CDN logs**, which is a data pipeline with cost, delay, and its own failure modes. Issue-time logging is what most teams actually have, and it answers a different question than they think.
- **Key rotation is all-or-nothing.** Rotating a signing key invalidates every outstanding URL, including the ones mid-download.
- **A separate content domain costs a certificate, a CORS configuration, and cookie-scoping care** — and is still the right call.
- **Watermarking and forensics identify a sharer; they don't prevent sharing.** Sometimes attribution is the honest goal, and saying so is better than pretending a signature is protection it isn't.

## Alternatives

- **Vendor token authentication** — CloudFront signed cookies, Akamai token auth, Fastly's token validation. The same design, already built, already integrated with the cache key.
- **Edge middleware validating a JWT** — Workers, Lambda@Edge, Compute. Per-request authorization without an origin round trip.
- **Per-tenant buckets or prefixes with IAM policies** — coarse, simple, and often exactly right for B2B where the unit of access is the organization (Module 5).
- **DRM** — Widevine, FairPlay, PlayReady — when playback must be device-bound and the business genuinely requires it.
- **Forensic watermarking** — per-user marks in the rendered output, so a leaked copy identifies its source. Complements everything above rather than replacing it.
- **Make it public and price for it.** For content whose value is attention rather than scarcity, the entire mechanism is overhead.

## How to Achieve It

**Level 0 — classify.** Which files are public, which are private, and what it costs if each class leaks. Most buckets hold all three classes and treat them identically.
_Signal you're here:_ one bucket policy covering marketing images and paid video.

**Level 1 — stop handing out storage URLs.** Every file behind an app URL that checks entitlement and redirects to a short signature. User content on a separate domain, with `nosniff` and a server-determined content type.
_Signal you need it:_ a storage hostname anywhere in your frontend.

**Level 2 — set TTL from revocation, and match the credential shape to the content.** URLs for one-shot downloads, cookies or tokens for anything segmented.
_Signal you need it:_ an expiry value chosen to stop the player breaking.

**Level 3 — make the cached object URL identical for all entitled users**, with the credential out of band. Measure hit ratio as the confirmation.
_Signal you need it:_ near-zero hit ratio on popular content.

**Level 4 — ingest CDN logs** for byte-accurate accounting, and add client beacons if the question is about engagement rather than delivery.
_Signal you need it:_ a billing, quota, or royalty question the app can't answer.

**Level 5 — per-request evaluation at the edge, with a denylist**, and forensic watermarking if attribution matters commercially.
_Signal you need it:_ a revocation requirement measured in seconds.

## Implementation

**TypeScript**, because the interesting enforcement point in the modern version of this is an edge runtime, and edge runtimes are JavaScript-shaped.

The redirect handler — small, and with one header that matters enormously:

```ts
app.get("/lessons/:id/video", async (req, res) => {
  const lesson = await loadLesson(req.params.id);
  if (!(await hasEntitlement(req.user.id, lesson.courseId))) {
    return res.status(403).json({ error: "not enrolled" });
  }

  const url = await getSignedUrl(s3, new GetObjectCommand({
    Bucket: CONTENT_BUCKET,
    Key: lesson.storageKey,
    ResponseContentDisposition: `inline; filename*=UTF-8''${encodeRFC5987(lesson.title)}.mp4`,
  }), { expiresIn: 3600 });

  await recordAccessIntent(req.user.id, lesson.id);

  res.set("Cache-Control", "private, no-store");
  res.redirect(302, url);
});
```

> **Aside 1.** `Cache-Control: private, no-store` on the redirect is not a nicety. Without it, a CDN or a shared proxy is entitled to cache the 302 — and then every student who requests `/lessons/4/video` receives *one particular student's* signed URL, for as long as the cache holds it. It is a two-word bug that hands out a credential to strangers, and it is invisible in every test that runs against a single user.

> **Aside 2.** `ResponseContentDisposition` sets the filename at serve time from the database, which is why 11.1a insisted the storage key be opaque: the human-readable name lives where it can be changed, localized, and safely encoded, and never in a key. Note `inline` here because it's a video in a player; for anything a browser might execute, this must be `attachment` and served from a different domain.

For segmented playback, the credential leaves the URL entirely:

```ts
app.post("/courses/:id/session", async (req, res) => {
  if (!(await hasEntitlement(req.user.id, req.params.id))) return res.sendStatus(403);

  const token = await signJwt(
    { sub: req.user.id, scope: `/c/${req.params.id}/` },
    { expiresIn: "6h" }
  );

  res.cookie("ct", token, {
    domain: "content.example.net",   // separate origin, not a subdomain of the app
    path: `/c/${req.params.id}/`,
    httpOnly: true, secure: true, sameSite: "none",
  });
  res.sendStatus(204);
});
```

And the edge function that makes one cached copy serve everyone:

```ts
export default {
  async fetch(req: Request, env: Env) {
    const claims = await verifyJwt(tokenFrom(req), env.PUBLIC_KEY); // local, no origin call
    const path = new URL(req.url).pathname;

    if (!claims || !path.startsWith(claims.scope)) {
      return new Response("forbidden", { status: 403 });
    }

    return fetch(req, { cf: { cacheKey: path } }); // credential deliberately excluded
  },
};
```

> **Aside 3.** `cacheKey: path` is the whole point, and it's the line that resolves the tension 11.2a flagged. Authorization is evaluated per request, at the edge, with no origin round trip — and the cache key contains none of the credential, so ten thousand entitled students share one cached segment. The signed-URL design cannot do both of these things; this one can, at the cost of running and debugging code at the edge.

> **Aside 4.** Verification is local against a public key, which is what keeps it fast — and also what makes revocation the token's TTL again, one layer up. Six hours is a deliberate statement that a refunded student may finish the lesson they're watching. If that's unacceptable, the edge function needs a denylist lookup, and you're trading the round trip you just saved for a revocation window measured in seconds. That's a product decision with a latency price tag, not a security default.

## Further Reading

- **AWS CloudFront documentation, "Serving private content with signed URLs and signed cookies"** — including an unusually clear decision table for which of the two to use, which is the same trade this article's How It Works section is built on.
- **AWS S3 documentation, "Downloading an object using presigned URLs"** — in particular the statement that the signature is evaluated at request time, which is what makes short TTLs viable for large downloads and fatal for range requests.
- **RFC 9110 §14, "Range Requests"** — required reading before proxying media through your own application, and a good argument for not doing so.
- **RFC 6266 and RFC 5987** — `Content-Disposition` and the encoding rules for non-ASCII filenames, which is where the original filename from 11.1a finally gets used.
- **MDN, "X-Content-Type-Options"** and the OWASP guidance on serving user-uploaded content — the separate-origin rule and what it's actually defending against.
- **Cloudflare Workers documentation, "Custom cache keys"** — the mechanism in Aside 3, and the constraints on what may and may not be excluded.
- **Apple, "HTTP Live Streaming" and the FairPlay Streaming overview** — worth skimming to see where the boundary between access control and DRM actually falls, before deciding you need to cross it.

A Java sibling would earn its place, and it would change a recommendation rather than a syntax: Spring's resource handling implements conditional and range requests correctly out of the box, so the proxy option — dismissed here partly on the cost of implementing HTTP correctly — is materially cheaper in that ecosystem, and the per-request-audit design becomes more attractive relative to redirects. Not yet written.

---

The habit to carry out of this: for any URL that leads to a file, answer two questions out loud — who is this URL good for, and for how long. A bucket URL answers "anyone" and "forever," and it answers that way not because someone decided it should, but because nobody decided anything.
