# Stampedes and the Miss Path

_Module 13.2b — Caching Strategies_

## The Problem

A news site. Article pages are cached for 60 seconds, hit rate 99.4%, database comfortable, and it has been that way for two years.

Then one story goes viral. 30,000 requests a second, essentially all for the same URL.

For the first 60 seconds, this is fine — one key, one cached entry, 30,000 hits a second served from memory. The database sees nothing. The graphs look like a success story.

At t=60s the entry expires.

In the ~300ms it takes to run the article query, roughly 9,000 requests arrive, miss, and each one runs the same query. The connection pool holds 200, so 8,800 of them queue. Under that contention the query no longer takes 300ms; it takes four seconds. The requests waiting on it are holding application threads, so the app stops accepting new work, so the load balancer starts returning 502s. The first fill finally lands at t≈69s — and the site has been down for nine seconds.

Sixty seconds later it happens again.

The two obvious reactions both make it worse. Shortening the TTL to 10 seconds, to reduce staleness, produces six times as many stampedes. Lengthening it to ten minutes makes each one rarer and larger, since more traffic accumulates behind each expiry.

Then the deploy. The release changed the shape of the cached object and the epoch prefix was bumped (13.1a), so every key in the cache goes unreferenced at once. This time it isn't one hot key missing — it's *all* of them, on a system whose database has spent two years being sized against a 99.4% hit rate. The origin saturates, fills take seconds instead of milliseconds, so the cache stays mostly empty, so the origin stays saturated. Clients time out and retry, adding load. Traffic drops as users give up, and the site still doesn't recover — because the thing keeping it down is no longer the traffic, it's the empty cache and the retries.

The only way out is to put the site behind a maintenance page, let the queues drain, and admit traffic back in stages.

Nothing in this story is a caching *bug*. The keys were right, the invalidation was right, the hit rate was excellent. What failed is the part nobody designed: **the path taken when the cache doesn't answer.**

## What It Is

A cache doesn't reduce load on the origin so much as **change its shape**. Steady, uncorrelated read traffic goes in; rare, correlated, synchronized bursts come out. The average is small and the average is not what the origin has to survive.

```
requests/s reaching the origin

 9000 ┤    █             █             █
      │    █             █             █
      │    █             █             █
    2 ┼────█─────────────█─────────────█───── ← the number on the capacity plan
      └────┴─────────────┴─────────────┴────▶
          t=60          t=120         t=180
```

The failures in this family have names worth knowing, because they have different fixes:

- **Cache stampede** (thundering herd, dogpile) — many concurrent misses on *one* key, each doing the same work.
- **Synchronized expiry** — many *different* keys expiring together because they were filled together.
- **Cache penetration** — misses for keys that have no answer at all, so nothing ever gets cached and every request reaches the origin.
- **Hot key** — a single key whose traffic exceeds what one cache node can serve, so the cache itself becomes the bottleneck.
- **Cold start** — the cache is empty and the origin cannot serve the resulting traffic.
- **Metastable failure** — the state the news site ended in: the trigger has passed, the load is normal, and the system still can't recover, because being overloaded is what keeps it overloaded.

The last one is the reason this article exists rather than being three bullets in 13.2a. The others are performance problems. That one is an outage that doesn't end when the cause does.

## Recognizing the Problem

- Database load shows a sawtooth whose period exactly matches a TTL.
- p99 latency spikes at regular intervals while p50 is flat.
- Latency or error spikes a few minutes after every deploy, restart, or failover.
- One cache node at 95% CPU while its peers idle.
- Connection-pool exhaustion in bursts, with the pool empty and the database mostly idle.
- 404-generating traffic — a scanner, a bad client, a broken link — showing up as database queries.
- "We can't flush the cache" is true, and everybody knows it's true, and it isn't written down anywhere.
- Recovery from an incident required removing traffic rather than adding capacity.
- Nobody has ever started this system with an empty cache under real load.

That last one is the important one, and it's answerable this week rather than during an incident.

## How It Works

Eight mechanisms. Most are a few lines; the last is a capacity decision.

### 1. Coalesce concurrent misses (single-flight)

Only one caller per key should do the work; the rest wait for its result. Within a process this is a map of in-flight promises or a `singleflight.Group`, and it takes 9,000 misses down to one per instance.

```
without:  ████████████████ 9,000 identical queries
with:     █                1 query per process, 8,999 waiters
```

With forty instances you get forty queries instead of 9,000, which is almost always enough. Do this first: it's the cheapest item here by a wide margin, and it fixes the stampede in the opening for one key and for every key simultaneously.

### 2. A distributed lease, when one per instance is still too many

If the fill is genuinely expensive — a report that takes eight seconds, a third-party call you pay for — forty concurrent fills is forty too many. One caller takes a short-lived lock (`SET lock:key NX EX 10`), fills, and releases; the others wait briefly or serve something else.

Three constraints make the difference between this helping and this being the outage. The lock needs a TTL, or a crashed holder blocks the key forever. Waiters must never block indefinitely — they wait a bounded time and then either serve stale or fail fast, because a thread parked on a lock is the resource you ran out of in the opening. And a duplicate fill after a lock expiry must be harmless, which it is, since fills are idempotent.

### 3. Serve stale while revalidating

This is the highest-value technique in the article, and it removes the miss entirely rather than deduplicating it.

Store the entry with a **logical expiry inside the value** and a much longer physical TTL:

```
value = { data, freshUntil: t+60 }        physical TTL: 10 minutes
```

Before `freshUntil`, serve it. After `freshUntil`, **still serve it**, and have exactly one caller kick off a background refresh. Readers never wait for a fill, so there is no herd to protect against, and the origin sees one request per key per refresh interval regardless of traffic. It is the same idea as `stale-while-revalidate` in HTTP (RFC 5861, and Module 7.4a at the edge), applied to the object cache.

Two things it costs. Staleness is now bounded by the refresh succeeding rather than by the TTL — if the origin is down, readers get data of unbounded age, which is usually a feature (`stale-if-error`) and should be a deliberate one. And it interacts badly with the invalidation from 13.2a: **a deleted key cannot be served stale.** If you rely on serve-stale for your hot keys, invalidation should *mark entries stale* rather than delete them — write back the same value with `freshUntil` in the past — so that a write triggers a refresh instead of a miss storm.

### 4. Probabilistic early expiration

The lock-free version of the same idea. Each reader independently decides whether to refresh early, with a probability that rises as expiry approaches and scales with how expensive the last fill was:

```
refresh early if:   now − delta × beta × ln(rand())  ≥  expiry
                          │        │
                          │        └── tuning knob; 1.0 is a fine default
                          └── how long the last recompute took
```

Expensive entries start getting refreshed sooner, cheap ones closer to expiry, and the refreshes spread out across readers instead of arriving together. No coordination, no locks, a handful of lines. The derivation is in Vattani et al.'s paper, cited below; the formula is the whole implementation.

### 5. Jitter every TTL

`ttl * (0.85 + random() * 0.3)`. One line, and it addresses a different failure from everything above: keys that were *filled* together — after a deploy, a cold start, a cron job that warms a batch — otherwise *expire* together, producing a fleet-wide miss storm across thousands of unrelated keys. Single-flight does nothing for this, because the keys are all different.

Any process that populates many entries at once is manufacturing a future incident unless it jitters.

### 6. Negative caching, and knowing what doesn't exist

If `customer:99999` doesn't exist, cache-aside stores nothing, so every request for it reaches the database. A scanner walking the ID space, or one bad client in a retry loop, turns 100% of its traffic into origin traffic — the cache is in the path and doing nothing.

Cache the absence, with a **short** TTL — tens of seconds — and remember that the negative entry must be invalidated when the thing is created, or a newly-created record will appear missing to the user who just made it (which is the read-your-writes problem from 13.2a arriving through a different door).

When the key space is enumerable and the traffic might be hostile, a Bloom filter over existing IDs answers "definitely not present / possibly present" in memory, in front of the cache, and is the standard defence at large scale. It's also a real operational commitment — it has to be built, kept current, and rebuilt — so reach for it when you've seen the traffic, not before.

### 7. Hot keys, where the cache itself is the bottleneck

One key lives on one shard. If it's taking 30,000 requests a second at 40KB a response, that's 12 Gb/s out of one node, and no amount of sharding helps because sharding distributes *keys*, and there's one.

Two fixes, in order of preference:

- **A small in-process L1 cache in front of the shared cache**, with a TTL of a second or two. The hottest handful of keys get absorbed locally, the shared cache sees one request per instance per second, and staleness grows by at most the L1 TTL. This is nearly always the right answer, and it's the same structure a CPU's L1/L2 hierarchy uses for the same reason.
- **Split the key into N copies** — `article:9f21#0` … `#7` — with readers picking one at random and writers updating all of them. It works, it multiplies memory and invalidation cost by N, and it only makes sense for a key you've measured.

Measure before doing either: `redis-cli --hotkeys` and per-node CPU will tell you whether you have a hot key or just a busy cluster.

### 8. The cold start, and the number nobody computes

Everything above protects a *running* cache. None of it helps when the cache is empty, because there's no entry to serve stale and no fill to coalesce — every request is a legitimate, distinct miss.

The question to answer is: **what is the lowest hit rate this origin can survive at current traffic?** If peak traffic is 30,000 rps and the database saturates at 1,500 rps, the answer is 95%, and that means a cache that drops to 94% for any reason — an eviction storm, a failover, a deploy, a new feature with a cold key space — takes the site down. That's not an argument against caching; it's an argument for knowing the number and for having a recovery procedure that works.

What makes recovery possible:

- **Bounded concurrency at the origin, with timeouts.** A queue of 8,800 requests waiting on 200 connections is 8,600 requests whose clients have already given up. Work performed for a departed client is pure amplification. Bound the queue, fail fast beyond it, and the origin keeps serving *something*.
- **Load shedding.** Deliberately reject a fraction of requests to keep the rest fast enough to complete — a 503 for 30% of users beats 100% timeouts, and it lets the cache refill. This is the mechanism that ends a metastable failure, and it has to exist before the incident.
- **No blind retries.** Client retries during saturation are a multiplier on load exactly when load is the problem. Retries need budgets, backoff, and jitter (Module 36.3's circuit breaker is the related control).
- **Staged recovery.** Admit traffic back in steps, letting the cache fill at each step. This is what "maintenance page, then slowly remove it" actually is, and it works much better when it's a runbook rather than an improvisation.
- **Warming, for the head only.** Replaying the top few thousand keys before an instance joins the pool is cheap and effective. Warming the long tail is not worth the machinery — it's the hot keys that decide whether you survive.

## When It's Appropriate

- **Single-flight: always.** Any cached read path, any traffic level. It costs one wrapper and has no downside.
- **TTL jitter: always**, on anything that fills entries in batches.
- **Serve-stale: any key with meaningful concurrency** whose data tolerates seconds of extra age — feeds, article bodies, dashboards, pricing tables, config. Roughly the same set of keys 13.2a would have you invalidate explicitly, which is why the interaction between them matters.
- **Distributed leases: expensive fills with many instances.** Eight-second report generation across sixty pods. Not for a 5ms query, where the lock costs more than the thing it protects.
- **Negative caching: any endpoint reachable by a guessable identifier**, or any key space where "not found" is a normal outcome rather than an error.
- **L1 in front of the shared cache: measured hot keys, or anything read more than once per request.**
- **Cold-start work: as soon as the survivable hit rate is below your actual hit rate**, which for most caches of any age is already true.

## When It's Unnecessary or Overkill

- **A stampede needs concurrent misses.** A key read once a second with a 50ms fill has a herd size of one. Protecting it is ceremony.
- **Distributed locks on cheap fills** add a network round trip and a new failure mode to save a query that costs less than the lock.
- **Bloom filters before you've seen penetration traffic.** A negative cache entry is six lines and usually sufficient.
- **Key splitting before measuring.** Most "hot key" diagnoses are actually a hot *shard*, and the fix is different.
- **Warming the whole key space.** It lengthens every deploy to buy protection for keys nobody requests.
- **Serve-stale where staleness is a correctness problem.** Balances and permission checks shouldn't be quietly extended past their TTL because the origin is slow; they should fail closed.
- **All of it, below a certain scale.** If the origin can serve 100% of traffic on a cold cache, you don't have a miss path problem — you have a latency optimization, and it's allowed to simply be absent sometimes.

## Trade-offs

**Every protection is a new failure mode.** Lock holders die. Background refreshes accumulate unbounded if nothing caps their concurrency. An L1 cache adds a second layer that explicit invalidation doesn't reach (13.3a). Serve-stale extends the staleness contract you negotiated with the product, and it does so in exactly the circumstances — origin degraded — when nobody is watching the freshness graph.

**Serve-stale and delete-on-write are in tension**, and this is the sharpest interaction in the module. One wants entries to persist past expiry; the other removes them. Pick mark-stale over delete for keys you serve stale, and make sure everyone touching the invalidation code knows why it isn't a `DEL`.

**Load shedding is a product decision wearing engineering clothes.** Somebody is choosing which 30% of users get an error, and that choice is better made in advance, in writing, with the people who own the relationship.

**Single-flight converts throughput problems into latency problems.** 9,000 waiters on one fill all see the fill's latency, and if the fill hangs, they all hang. The wait needs a timeout.

**Admitting the cache is load-bearing costs money or credibility.** Either you provision the origin closer to the miss path, or you write down that a cold start is an outage with a documented recovery. The unacceptable option is the common one: not deciding, and finding out during a failover.

## Alternatives

- **Remove the miss path entirely for the hottest keys.** Compute the homepage, the top-stories feed, the leaderboard *on write* and push it into the cache with no expiry at all. Nothing to stampede on, nothing to serve stale, and the refresh rate is bounded by the publish rate rather than by read traffic. For a small set of extremely hot, expensive entries this beats every technique above, and it's underused because it inverts the direction the code already flows.
- **Push the problem to the edge.** A CDN with `stale-while-revalidate` collapses the herd before it reaches your infrastructure and does it in more places (Module 7.4a). It only applies to responses that are cacheable at the edge, which excludes anything per-user.
- **Size the origin for a full miss.** Unfashionable, entirely legitimate below a certain scale, and it makes every technique here optional rather than load-bearing.
- **Backpressure and admission control as the general answer.** Rather than protecting individual keys, bound concurrency at the origin and reject beyond it. Doesn't reduce the wasted work, but it does keep the system in a recoverable state, which is the property that actually matters.
- **A different storage layout.** Sometimes the reason a fill takes 300ms is worth fixing directly, at which point a 9,000-request herd is a 9,000-request spike the database absorbs (13.1a's first alternative, still the best one).

## How to Achieve It

**1. Find the sawtooth.** Overlay origin load with your TTL. If the period matches, you have stampedes today.
*Next when:* you can name the top three keys by request rate.

**2. Jitter your TTLs.** One line, no design work, prevents the fleet-wide version.
*Next when:* deployed.

**3. Wrap the read path in single-flight.** One wrapper, applies everywhere at once.
*Next when:* the sawtooth's peaks drop by roughly the concurrency factor.

**4. Add negative caching on the not-found path.** Short TTL, invalidated on create.
*Next when:* 404s stop reaching the database.

**5. Convert the hottest keys to serve-stale with background refresh** — and fix their invalidation to mark rather than delete.
*Next when:* those keys produce a constant, low, flat origin rate instead of spikes.

**6. Run a cold-start test.** Flush the cache during your lowest-traffic hour with a maintenance page ready. Measure what breaks and how long refill takes. Compute the survivable hit rate.
*Next when:* you have the number and it's written down where an on-call engineer will find it.

**7. Add concurrency limits, timeouts, and shedding at the origin**, and audit clients for unbudgeted retries.
*Next when:* a synthetic overload produces degradation rather than collapse.

**8. Only now consider distributed leases, key splitting, or Bloom filters** — each one against a measurement that names it.

## Implementation

TypeScript, because Node's event loop makes the coalescing structure almost disappear: a map of in-flight promises *is* single-flight, and it's worth seeing how little there is to it.

```ts
const inFlight = new Map<string, Promise<Entry>>();

function fillOnce(key: string, load: () => Promise<Entry>): Promise<Entry> {
  const existing = inFlight.get(key);
  if (existing) return existing;                    // join the fill already running

  const p = load().finally(() => inFlight.delete(key));
  inFlight.set(key, p);
  return p;
}
```

Two asides on those six lines.

*The `finally` is not optional.* Without it the map grows forever and, worse, a rejected promise is cached permanently — every future caller for that key gets the same failure with no attempt to retry. A cache of failures is a much better outage than a cache of successes.

*Everyone sharing one promise shares its latency and its timeout.* If `load()` hangs for thirty seconds, so do all 9,000 waiters. The timeout belongs inside `load`, not around the callers.

Now the read path with logical expiry, serve-stale, and probabilistic early refresh:

```ts
const BETA = 1.0;

async function read(key: string, load: () => Promise<Data>): Promise<Data> {
  const raw = await redis.get(key);

  if (raw) {
    const e: Entry = JSON.parse(raw);               // { data, freshUntil, fillMs }
    const early = e.fillMs * BETA * -Math.log(Math.random());

    if (Date.now() + early < e.freshUntil) {
      return e.data;                                // comfortably fresh
    }

    // Stale, or probabilistically close enough. Serve now, refresh behind.
    void refresh(key, load);                        // deduplicated by fillOnce
    return e.data;                                  // ← nobody ever waits for a fill
  }

  return (await fillOnce(key, () => refresh(key, load))).data;  // genuine cold miss
}

async function refresh(key: string, load: () => Promise<Data>): Promise<Entry> {
  return fillOnce(key, async () => {
    const started = Date.now();
    const data = await load();
    const fillMs = Date.now() - started;
    const entry: Entry = { data, fillMs, freshUntil: Date.now() + FRESH_MS };
    await redis.set(key, JSON.stringify(entry), "PX", jitter(PHYSICAL_TTL_MS));
    return entry;
  });
}
```

The shape to notice: **the only `await` on a fill is in the cold-miss branch.** Every other path returns immediately with data of some known age, which is what makes the opening scenario impossible — there is no moment at which 9,000 requests are all waiting on the same query.

Three more asides, each of which is a real production bug:

*`fillMs` is what makes the early-refresh term adaptive.* An expensive entry starts refreshing well before expiry; a cheap one waits. Storing it costs one integer and it's the difference between the formula and a random number.

*`void refresh(...)` is a promise nobody is awaiting*, which means an unhandled rejection takes down the process under Node's default. It needs a `.catch()` that records a metric. It also needs a concurrency cap in aggregate — a dependency that suddenly takes ten seconds will otherwise accumulate thousands of overlapping refreshes, which is the stampede you were preventing, relocated.

*In a serverless runtime the background refresh may be killed the moment the response is sent*, so entries go stale and never refresh, silently. Platforms expose something like `waitUntil` for exactly this; without it, serve-stale needs a different mechanism — a scheduled refresher, or refreshing synchronously under a lease.

## Further Reading

- **Vattani, Chierichetti & Lowenstein, "Optimal Probabilistic Cache Stampede Prevention" (VLDB 2015).** Short, and it derives the early-refresh formula above rather than asserting it. Reading the derivation is what makes `beta` a knob you can reason about instead of a constant you copied.
- **Bronson, Aghayev, Charapko & Zhu, "Metastable Failures in Distributed Systems" (HotOS 2021).** The vocabulary for the second half of the opening story: trigger versus sustaining effect, and why removing the trigger doesn't end the outage. It will change how you read your own incident reports.
- **RFC 5861, "HTTP Cache-Control Extensions for Stale Content."** Two pages defining `stale-while-revalidate` and `stale-if-error`. The object-cache technique in section 3 is this specification applied one layer down, and the RFC is clearer about the semantics than most implementations.
- **Amazon's Builders' Library: "Using load shedding to avoid overload"** and **"Timeouts, retries, and backoff with jitter."** Operational rather than academic, written by people who have run the recovery, and the second is the source for why jitter belongs on retries as well as TTLs.
- **Google's SRE book, "Addressing Cascading Failures" and "Handling Overload."** The standard treatment of the cold-start and recovery half of this article, including why a system that recovers only when traffic is removed needs a documented procedure rather than a heroic engineer.
- **`golang.org/x/sync/singleflight`** — about a hundred lines of readable source, and the clearest specification of what coalescing has to handle: panics, duplicate suppression, and `Forget`.
- **Redis documentation on `--hotkeys`, `OBJECT FREQ`, and `maxmemory-policy`** — the tooling that turns "we think we have a hot key" into evidence.
- **Module 13.2a** for the invalidation this article partially contradicts, **13.3a** for invalidating multi-layer caches, **Module 18** for rate limiting as the sibling control to shedding, **Module 36.3** for circuit breakers, and **Module 22.5** for the load testing that produces the survivable hit rate.

A **Go** sibling would be worth writing for one reason: the concurrency here is explicit rather than hidden behind an event loop. `singleflight.Do` returns a `shared` flag that tells you, per call, whether you were the filler or a waiter — which makes the herd visible in metrics instead of inferred — and the background refresh becomes a bounded worker pool with a real queue, so the "unbounded refresh accumulation" aside stops being an aside and becomes a channel with a capacity you have to choose. The `context` propagation also forces the timeout question the TypeScript version leaves to discipline: a waiter joined to someone else's fill inherits nothing about its own deadline, and Go makes you notice. Not yet written.

---

The habit to take from this one: **every cache hides a load pattern, and the pattern it hides is not the one it shows you.** Whenever you find a component that absorbs most of the work, ask what the system looks like in the moment it stops — and then, before that moment arrives on its own, go and create it deliberately at three in the afternoon on a Tuesday.
