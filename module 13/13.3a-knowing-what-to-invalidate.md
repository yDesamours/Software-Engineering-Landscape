# Knowing What to Invalidate

_Module 13.3a — Caching Strategies_

## The Problem

An e-commerce catalogue. 200,000 products, heavy read traffic, and caching in several places because each one was added by a different person solving a different complaint:

```
product:842                        the product record
category:audio:page:3              a paginated list containing it
search:{hash of query+filters}     result sets it appears in
home:featured                      the homepage block
fragment:product-card:842          the rendered HTML card
https://cdn.../p/842               the product image and the page at the edge
(in-process) product:842           an L1 copy in each of 12 app instances
```

A merchandiser changes the price of product 842.

13.2a already settled the mechanics of the write: commit first, then invalidate, in the repository, with a TTL as backstop. That article assumed the part this one is about was easy — that a row maps to *a key*. Here, one row maps to an unknown number of entries across four systems, and nobody in the building can list them.

So the invalidation function grows:

```
delete product:842
delete fragment:product-card:842
delete home:featured
delete category:audio:page:*     ← which pages? the product could be on any of them
delete search:*                  ← keyed by a hash of the query. no way to know.
```

The wildcards are where it comes apart. Someone reaches for `KEYS category:*`, which blocks Redis single-threaded for 400ms across 200,000 keys and takes the site down on the first busy afternoon. It gets replaced with `SCAN`, which doesn't block but is now a background job that takes twelve seconds and misses keys written while it runs. `search:*` gets given up on entirely and its TTL shortened to 30 seconds instead — which is a quiet admission that this cache is now doing much less than it was designed to.

Four months later, three things are true. A new "recently viewed" widget is stale for an hour, because whoever built it didn't know there was an invalidation function to edit. The deploy runbook says "flush the cache after a catalogue import", which is 13.2b's cold start scheduled as a routine operation. And the price shown on the category page disagrees with the price on the product page, which is the version of this bug that reaches customers, because a list and a detail view of the same row are invalidated by different code paths that drifted apart.

The hard part of cache invalidation isn't deleting the key. **It's knowing which keys.**

## What It Is

Invalidation is the answer to a *dependency* question: which cached entries does this write make wrong? The difficulty is that the dependency runs the wrong way for the code that needs it.

```
   known at fill time                          needed at write time
   ─────────────────                           ────────────────────
   home:featured ──reads──▶ product:842        product:842 ──?──▶ home:featured
   category:audio:page:3 ──reads──▶ 842                      ──?──▶ category:audio:page:3
   search:a91f… ──reads──▶ 842                               ──?──▶ search:a91f…
```

The reader knows exactly what it depended on, at the moment it depended on it, and then throws that knowledge away. The writer needs the same fact inverted and has no way to derive it. Every strategy below is a way of preserving one direction or avoiding the question:

- **Expiry (TTL)** — don't answer it; bound how long a wrong answer survives.
- **Direct invalidation** — answer it by hand, in the write path. Works when the mapping is 1:1 and stays that way.
- **Tags / dependency tracking** — record the reader's knowledge at fill time so the writer can look it up.
- **Generation keys** — change the key when the data changes, so old entries become unreachable rather than wrong.
- **Ban lists** — record a *rule* rather than acting on it, and evaluate it lazily on the next read.

One neighbour to separate before going further, because conflating them causes real bugs: **eviction is not invalidation.** Eviction is memory management — LRU, LFU, and whatever `maxmemory-policy` says — and it removes entries that are perfectly valid because it needs the space. Invalidation is correctness. They produce the same observable result (entry gone), which is why people say "it'll get evicted eventually" as though it were an invalidation strategy. It isn't one: eviction removes the *least* used entries, and the entry you need gone is very often the most used one.

## Recognizing the Problem

- An invalidation function that names more than about three keys, and grows with every feature.
- `KEYS` or a wildcard pattern anywhere near a write path.
- A `SCAN`-based deletion job.
- "Flush the cache" appearing in a runbook, a deploy step, or a data-import procedure.
- A list view and a detail view disagreeing about the same record.
- A TTL that was shortened because invalidation couldn't be trusted — and a hit rate that fell with it.
- Adding a new cached view requires editing a write handler in an unrelated module.
- Some layers get invalidated (Redis) and others don't (in-process, CDN).
- The question "what depends on this row?" has no answer anywhere in the codebase.
- One product update causing a visible latency spike — over-invalidation, and 13.2b's stampede arriving by a new route.

## How It Works

### Direct invalidation, and where it stops

For 1:1 entity caches, the write path knows the key and deletes it. This is the whole of 13.2a and it is completely adequate for a large fraction of real caches. The signal that you've outgrown it is precise: **when the write handler has to guess.** `delete product:842` is knowledge; `delete category:*` is a guess with a wildcard in it.

### Tags: record the dependency at fill time

At fill time, the reader knows what it read. Have it say so:

```
fill  home:featured   → depends on {product:842, product:19, promo:winter}
      SADD tag:product:842  home:featured
      SADD tag:product:19   home:featured
      ...

write product:842     → SMEMBERS tag:product:842 → delete every member, then the tag
```

This is the general solution, and it's what CDNs call surrogate keys or cache tags — the same idea at the edge, where `Surrogate-Key: product-842 category-audio` on a response lets you purge by tag instead of by URL.

It costs three things worth knowing in advance. The fill path now performs writes, so reads are no longer read-only. The tag sets accumulate members that have already expired, so they grow without bound unless they're given a TTL of their own (at least as long as the longest entry TTL) or trimmed. And deleting a tag with 50,000 members is a large synchronous operation against a single-threaded server — `UNLINK` rather than `DEL`, in batches, or it's the `KEYS` incident again wearing a different hat.

### Generation keys: make the old entries unreachable

The inverse move. Instead of tracking which keys to delete, put a version in the key so that a write produces *different* keys and the old ones are simply never requested again:

```
key = "v7:product:842:g{generation}"        INCR gen:product:842  → invalidates all of them
```

Nothing is deleted. The orphaned entries become garbage, and eviction — which is memory management, and is the right tool for garbage — reclaims them on its own schedule. Invalidation becomes a single atomic increment, regardless of how many entries existed, which also makes it immune to the over-invalidation stampede.

The cost is on the read path: you must know every generation your key depends on *before* you can build the key, which is an extra `MGET` per read. That's cheap when the generations are few or already at hand — and often they already are, because you loaded the parent row anyway and its `updated_at` *is* a generation. This is the mechanism behind Rails' nested fragment caching, where a child's timestamp is part of the parent's key and a change bubbles upward through the key rather than through a delete.

Composing the two is common and effective: tags for the wide, unpredictable dependencies, generations for the deep, nested ones.

### Ban lists: decide lazily

Varnish's model, and the odd one out. Instead of finding and removing the affected entries, record a predicate — "anything matching `/products/842` cached before now is invalid" — and check it when an entry is next looked up. Invalidation becomes O(1) at write time and the cost moves to reads, which now walk the ban list.

It's the right shape when the affected set is enormous and mostly cold (invalidating "everything for tenant X"), and it requires the ban list to be trimmed aggressively, since every read pays for its length.

### Event-driven invalidation: inverting who knows

Everything above assumes one codebase where the writer can reach the cache. Once a second service, a webhook, or a separate front-end owns some of the caches, the write path shouldn't know they exist.

Publish `ProductUpdated{id: 842}` and let each cache owner subscribe and decide what that means for its own keys. The dependency knowledge stays with the code that has it — the team that built "recently viewed" writes its own subscriber — and the catalogue service stops accumulating knowledge about downstream caches it doesn't own. This is the organizational fix for the drift in the opening story, and it matters more than the technical difference.

What it costs: invalidation is now asynchronous, so the staleness window is the bus's delivery latency rather than a millisecond. Delivery is at-least-once, which is harmless because deletes are idempotent — and is *not* harmless if a subscriber responds by writing a value instead of deleting one, for the ordering reason 13.2a gave. And you've made the message bus a dependency of correctness.

The completeness backstop remains the replication log (13.2a, Module 38.4): CDC catches every writer including the ones outside your code. Events are the pragmatic version; CDC is the complete one.

### Multi-layer: the L1 problem

A `DEL` in Redis does nothing to the in-process caches 13.2b told you to add, or to the CDN. Three approaches, usually combined:

- **Short L1 TTLs.** One to five seconds. Boring, reliable, and sufficient for most in-process caches, because their whole job is absorbing a burst rather than storing state.
- **Broadcast.** Publish the invalidation on Redis pub/sub or the message bus and have every instance clear its local copy. Redis 6 formalizes this as server-assisted client-side caching (`CLIENT TRACKING`), where the server remembers which clients read which keys and pushes invalidation messages to them.
- **CDN purge**, by URL or by surrogate key, which is Module 7.4a's territory.

The rule that makes broadcast safe: **pub/sub has no delivery guarantee, so a broadcast invalidation must always be paired with a TTL.** An instance that was reconnecting when the message went out never hears it, and without a TTL its local copy is wrong until the process restarts. Broadcast makes invalidation fast; the TTL makes it eventual.

### Granularity: the two ways to be wrong

```
under-invalidate  ──────────── granularity ──────────▶  over-invalidate
stale data                                              hit rate collapses,
(a correctness bug,                                     stampede on refill
 reaches customers)                                     (a performance bug)
```

Tagging every product page with `tag:catalog` is technically correct and means one price change invalidates 200,000 entries, all of which get re-requested at once. Tagging nothing means the category page is stale. Granularity is the knob, it's chosen per tag, and it should be chosen with the fan-out measured: how many keys does this tag actually hold?

## When It's Appropriate

- **TTL alone** — whenever the staleness budget exceeds the TTL that gives an acceptable hit rate. Still the answer for most caches, and the one to rule out first.
- **Direct invalidation** — entity caches with a stable 1:1 key, one or two views, one writer.
- **Tags** — derived entries: lists, search results, rendered fragments, aggregates, anything whose key can't be computed from the changed row. A catalogue, a CMS, a dashboard built from many sources.
- **Generation keys** — nested or hierarchical content where the parent already has the child's version in hand, and anywhere a single write would otherwise fan out to tens of thousands of deletes.
- **Ban lists** — "invalidate everything for this tenant" against a large, mostly-cold key space.
- **Events** — more than one service or codebase caches the same data.
- **CDC** — correctness matters more than a second of lag, and you cannot enumerate your writers.

## When It's Unnecessary or Overkill

- **The staleness budget is satisfied.** Half the invalidation machinery in production exists because nobody asked the product owner whether 60 seconds was fine. Ask first; it's a five-minute conversation that can delete a subsystem.
- **High-write entities.** An entry invalidated every two seconds is a two-second TTL implemented expensively, with a stampede attached. Use the TTL.
- **Tag bookkeeping on a cache that's barely hitting.** If the hit rate is 40%, the fill-path writes may cost more than the cache saves.
- **Precision invalidation of something you could recompute on write.** If the homepage block is one row of denormalized JSON updated when a product changes, there's nothing to invalidate.
- **CDC before a second writer exists.** A pipeline with one producer and one consumer that could have been a function call.
- **Broadcast invalidation for a one-second L1.** The TTL already did it.

## Trade-offs

**Reads become writes.** Dependency tracking means the fill path does bookkeeping, which costs latency on the miss path — the path 13.2b showed is already your worst one.

**Bookkeeping is garbage that must be collected.** Tag sets outlive their members, ban lists grow, generation counters are forever. Each needs a TTL or a sweeper, and each is a slow memory leak that surfaces months later as an eviction storm.

**Invalidation storms are self-inflicted stampedes.** A coarse tag turns one write into a synchronized mass expiry, and everything in 13.2b applies — which is why serve-stale pairs so well with tags, converting a mass delete into a mass *refresh trigger* that readers never wait for.

**Asynchronous invalidation widens the window you were trying to close.** If the bus is lagging five seconds, your invalidation is five seconds slower than the TTL-free ideal, and slower than some TTLs you could have just used.

**Staleness is the maximum across layers, and the user sees the maximum.** Redis invalidated in 1ms, L1 in 2 seconds, CDN in 30 — the customer's experience is 30 seconds. Multi-layer caching means the freshness promise is set by the slowest layer, not the fastest.

**Debuggability requires the record.** "Why is this stale?" is unanswerable unless you can see which tags an entry was registered under and which invalidations fired. Log both, or accept that every one of these bugs will be investigated by reading code and guessing.

**Some things cannot be invalidated by construction.** A key containing a hash (13.1a) or a query fingerprint isn't derivable from the data that changed. You either tag it at fill time or you give it a TTL and stop pretending.

## Alternatives

- **A shorter TTL.** The permanent competitor to all of this, and it wins more often than engineers like. It has no bookkeeping, no failure modes, no drift, and it's one number.
- **Immutable keys.** If the key changes whenever the content changes — content-addressed derivatives (11.3a), a `updated_at` in the key, an epoch prefix (13.1a) — invalidation is a write you never perform. The strongest option available when the version is cheaply at hand.
- **Recompute on write.** A denormalized row or a materialized view updated in the same transaction has nothing to invalidate, because there's no second copy with an independent lifetime. Costs write latency, buys away this entire article.
- **Serve stale and refresh (13.2b).** Reframes invalidation as "mark this for refresh" rather than "delete this", which removes the miss and keeps a wrong-but-recent answer available instead of no answer.
- **Don't cache the derived view.** Cache the entities and compose them per request. More work per request, one dependency layer instead of two, and frequently fast enough.

## How to Achieve It

**1. Write down the staleness budget for each cached view.** In seconds, from the person who owns the feature. This step deletes more work than any other.
*Next when:* some view's budget is shorter than the TTL it needs.

**2. Direct invalidation for that view, if its key is derivable from the write.**
*Next when:* a write handler contains a wildcard or a third key.

**3. Invert: tag at fill time.** Start with one entry type, the one that keeps going stale.
*Next when:* it works and the tag sets are bounded.

**4. Measure fan-out per tag before adding more.** Keys per tag, and invalidations per minute. A tag holding 40,000 keys is a scheduled incident.
*Next when:* the numbers are unsurprising.

**5. Add a staleness canary.** A job that writes a known value and polls each read path — API, list view, CDN URL — recording how long until the change appears. This turns "users say it's stale sometimes" into a graph per layer, and it's the single most useful piece of instrumentation in this module.
*Next when:* the graph exists and someone looks at it.

**6. Move the trigger to events when a second service or team starts caching this data.**
*Next when:* you can name a writer you don't control.

**7. Consider CDC.** Complete, asynchronous, and an operational commitment.

## Implementation

Java, because the two-layer arrangement this article ends on — Caffeine in front of Redis, with broadcast invalidation — is idiomatic there rather than assembled by hand, which makes the parts that *aren't* handled for you easier to see.

Tag registration at fill time:

```java
public <T> T get(String key, Set<String> tags, Duration ttl, Supplier<T> loader) {
    T cached = redis.get(key, type);
    if (cached != null) return cached;

    T value = loader.get();

    redis.pipelined(p -> {
        p.setex(key, ttl, value);
        for (String tag : tags) {
            p.sadd("tag:" + tag, key);
            p.expire("tag:" + tag, TAG_TTL);   // ≥ the longest entry TTL, or the set leaks
        }
    });
    return value;
}
```

Invalidation by tag, as one server-side operation:

```java
private static final String INVALIDATE = """
    local keys = redis.call('SMEMBERS', KEYS[1])
    for i = 1, #keys, 500 do
      redis.call('UNLINK', unpack(keys, i, math.min(i + 499, #keys)))
    end
    redis.call('UNLINK', KEYS[1])
    redis.call('PUBLISH', ARGV[1], KEYS[1])   -- tell the L1 caches
    return #keys
    """;
```

Three asides.

*The batching and `UNLINK` are not stylistic.* `DEL` on 50,000 keys blocks a single-threaded server for long enough to time out every other request; `UNLINK` frees memory on a background thread, and the chunking keeps any one command short. This is the same failure as the `KEYS` incident in the opening, reached by doing the right thing carelessly.

*The tag TTL is the leak.* A tag set accumulates every key ever registered under it, including the 99% that have long since expired. Without `expire`, a tag on a popular product grows until it's the largest object in the cache, and the invalidation that touches it is the one that stalls the server.

*`PUBLISH` here is best-effort and it has to be.* Nothing retries it, nothing confirms it, and an instance that's reconnecting won't hear it — which is why the local cache below cannot rely on it alone.

The L1 and its listener:

```java
Cache<String, Object> l1 = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofSeconds(5))  // ← the backstop; not an optimization
    .build();

redisPubSub.subscribe("cache-invalidations", message -> l1.invalidate(message));
```

`expireAfterWrite` is doing the load-bearing work in those four lines. The subscription makes invalidation *fast*; the five seconds make it *guaranteed*. Delete the TTL — which looks redundant once the broadcast works — and a single missed message means one instance serves a wrong answer indefinitely, to a fraction of users, depending on which pod the load balancer picked. That's among the worst bugs in this module to diagnose, and it's a one-line deletion away at all times.

## Further Reading

- **Fastly's documentation on surrogate keys**, and Cloudflare's on cache tags. The clearest production treatment of tag-based invalidation, including how many tags a response may carry and what purge latency actually looks like. Read it even if your tags are in Redis — the API design decisions are the same ones you're making.
- **Varnish's documentation on purges and bans.** The reference for lazy predicate invalidation, and specifically honest about the cost of a long ban list, which is the part every homegrown version forgets.
- **Redis: client-side caching (`CLIENT TRACKING`) and keyspace notifications.** The first is server-assisted L1 invalidation done properly, including the broadcast-versus-tracking modes; the second is tempting for invalidation and explicitly documented as fire-and-forget, which is exactly the guarantee you don't want to discover later.
- **Rails guides on fragment caching**, particularly `cache_key_with_version` and `touch: true` on associations. The best-known generation-key system in production, and reading it makes the "key changes instead of entry being deleted" idea concrete in about ten minutes.
- **Caffeine's documentation on eviction and refresh**, especially `refreshAfterWrite` versus `expireAfterWrite` — two lines apart in a builder, and a completely different behaviour under load.
- **Redis documentation on `UNLINK`, `SCAN`, and why `KEYS` is a production hazard.** Short, and it explains the single-threaded model that makes the opening incident inevitable rather than unlucky.
- **Module 13.2a** for the ordering and the trigger this article takes as given, **13.2b** for what a coarse tag does to your origin, **Module 7.4a** for the CDN layer, **Module 37** for the event bus, and **Module 38.4** for CDC.

A **TypeScript** sibling built on a modern React framework would show something this article can only describe: dependency tracking performed by the *runtime* rather than by the developer. Next.js's `unstable_cache` and `revalidateTag` make tags a first-class primitive — the render records which cached functions it called, so the tag registration in the Java code above disappears entirely, and invalidation is a single call from a server action. That's the good version of this idea, and it's worth seeing precisely because it also shows the cost: dependencies you didn't declare and can't see, a cache whose contents you can't enumerate, and a `revalidateTag` whose blast radius is decided by framework conventions rather than by your fan-out measurement. Not yet written.

---

The habit worth carrying: **whenever you store a derived value, write down what it was derived from — at the moment you derive it, while you still know.** Tags, generation keys, and provenance columns are all the same move, and the systems that are miserable to operate are invariably the ones where that knowledge existed for one instruction and was never recorded. It's the same reason a build system records its inputs and a data pipeline records its lineage: the question "what does this depend on?" is easy exactly once, and impossible forever after.
