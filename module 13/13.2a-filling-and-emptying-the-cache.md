# Filling and Emptying the Cache

_Module 13.2a — Caching Strategies_

## The Problem

A help-desk product. Every ticket view loads the customer record, which works out to about 500 reads a second against a table that takes a few hundred writes a *day*. Textbook caching territory, and 13.1a's advice was followed exactly: cache-aside, a five-minute TTL, no invalidation, keys built in one place. Hit rate 96%.

Then the first complaint, and it isn't about performance. An agent edits a customer's contact email, saves, reloads the ticket, and sees the old address. They edit it again. Now there are two support tickets about the support tool.

The fix is obvious and it's the one everybody writes:

```
UPDATE customers SET ... WHERE id = 42;
cache.delete("customer:42");
```

Edits appear instantly. Everyone moves on. Over the following six months, four bugs arrive, and they look unrelated to each other and to this change.

**Bug one: a stale value that outlives its own TTL.** A customer shows as `Free` for hours after being upgraded, in a cache whose TTL is five minutes. Nobody can reproduce it. What happened is a race between a reader and a writer, and it's inherent to cache-aside:

```
time ──────────────────────────────────────────────────────────────▶

reader   GET miss ─ SELECT → "Free" ─────────────────────────── SET "Free" (TTL 5m)
writer                     UPDATE → "Pro" ─ DEL customer:42 ─
cache    (empty)                              (empty)                "Free"  ← for 5m
```

The reader missed, read the old row, and was then descheduled — a GC pause, a slow network hop, a noisy neighbour. By the time it wrote its result into the cache, the writer had already updated the database *and* performed its delete. The delete removed nothing, because the entry didn't exist yet. The reader then installed a stale value with a fresh full TTL, and nothing will delete it again. It's rare, it scales with load and with how slow reads are, and it's invisible in every log.

**Bug two: the cache and the database disagree permanently.** Someone had noticed all the misses caused by deleting on every write and "optimized" it: instead of `delete`, write the new value straight into the cache. Two agents editing the same customer within a second of each other now produce this:

```
writer A   UPDATE → v1 ───────────────────── SET "v1"
writer B        UPDATE → v2 ─ SET "v2"
                                  database: v2     cache: v1   (forever)
```

Both writes reached the database in order. The cache writes arrived in the other order, and nothing will ever correct it — until the TTL, which someone had raised to an hour because of all the misses.

**Bug three: writers who never heard of the cache.** The plan field is also written by a billing webhook, a nightly CRM sync, and — twice that quarter — by an engineer running an `UPDATE` during an incident. None of them invalidate anything. The cache is correct with respect to exactly one write path out of four.

**Bug four: the delete that silently failed.** Redis failed over for eleven seconds during a maintenance window. Every `cache.delete` in that window threw, got swallowed by a `try/catch` written to make sure cache problems never break requests, and left a stale entry behind. Which is the right instinct and the wrong implementation.

The line `cache.delete(key)` looked like a one-line fix. It was actually a decision about **who is responsible for putting data into the cache, who is responsible for taking it out, and in what order relative to the database** — and each of those has more than one defensible answer.

## What It Is

The answers have names, and they divide along two axes.

**On the read path**, the question is who calls the database on a miss:

```
cache-aside (lazy loading)              read-through
  app ──▶ cache          miss            app ──▶ cache        miss
  app ──▶ database                                 cache ──▶ database
  app ──▶ cache.set                                cache.set
  app ◀── value                          app ◀── value
```

**On the write path**, the question is what a write does to the cached copy:

| pattern | on write | cache holds |
| --- | --- | --- |
| **TTL only** | nothing | whatever it had, until expiry |
| **write-around** | write store, delete key | nothing, until the next read fills it |
| **write-through** | write store, then write cache | the new value, immediately |
| **write-behind** (write-back) | write cache, queue store write | the new value; the store catches up later |

A few things follow that are worth getting straight before any of the mechanics.

*Cache-aside versus read-through is not a consistency decision.* It's a decision about where the loading code lives — in your service, or behind the cache's interface. Teams argue about it as though it affected correctness; it doesn't. What affects correctness is the write policy and the ordering, which is the rest of this article.

*"Cache-aside with a delete on write" is write-around.* Most systems described as cache-aside are really this pair, and the pair is the sensible default.

*Write-behind makes the cache authoritative*, which contradicts the definition in 13.1a — a cache is allowed to be missing. If losing the cache loses writes, you no longer have a cache; you have an unbacked-up database with an eviction policy. That's occasionally the right trade, and it should be made on purpose.

## Recognizing the Problem

You need a write policy beyond TTL when:

- Users edit something and then have to look at it.
- "Clear the cache" appears in a support runbook, or a "refresh" button exists purely to work around staleness.
- The TTL has been shortened repeatedly, each time in response to a complaint, and the hit rate has followed it down.
- Staleness is measured in "how long until someone notices".

Your write policy is already broken when:

- A stale value survives longer than the TTL.
- The cache and the database disagree and neither side is converging.
- Invalidation calls appear at call sites, and a grep finds three of them for the same key.
- A background job, migration, or admin tool writes the table.
- Cache errors are caught and ignored (correct) with no retry or backstop (not correct).
- A user's own edit is visible on one page and not another.
- Write-heavy keys are constantly being deleted and immediately re-read, so the hit rate on them is near zero and you're paying for the cache twice.

## How It Works

### Rule 1: write the store first, then invalidate

The ordering is not symmetric, and both orders have a window — they're just different windows.

**Delete first, then write the store:** between the delete and the commit, a concurrent reader misses, reads the *old* row, and caches it. You've created the exact race from bug one, deliberately, on every single write. Never do this alone.

**Write the store, commit, then delete:** between the commit and the delete, readers get a stale hit. The window is however long the delete takes — typically under a millisecond — and it closes on its own. This is the correct default.

The commit part matters. Invalidating inside the transaction means a reader can miss, read the pre-commit state from its own snapshot, and repopulate the cache with data that's about to become outdated — a version of bug one with a much wider window. Invalidation belongs to the commit, not to the write.

### Rule 2: prefer delete over set

Deleting is idempotent and order-insensitive: two deletes in any order leave the cache empty, and the next reader fills it from the database, which is the only authority. Setting is neither, which is bug two.

`set` on write buys you one thing — the next reader gets a hit instead of a miss — and costs you a correctness property. Take that trade only when the value is cheap to derive, single-writer, or version-guarded (below). It's also wasteful on keys that are written more often than they're read; you're populating entries nobody will read before the next write deletes them.

The cost of `delete` is real, though: **every write guarantees a miss for the next reader.** On a hot key with a meaningful write rate, that's a synchronized stampede at every write, which is 13.2b's subject.

### Rule 3: keep a TTL even when you invalidate explicitly

Deletes fail. Networks partition, Redis fails over, the process crashes between the commit and the delete, a new write path ships without the invalidation. Every one of those leaves an entry that nothing will ever remove.

A TTL converts "stale forever" into "stale for at most *N*". It's the only backstop that survives bugs you haven't found yet, and it costs you almost nothing on a key that's being explicitly invalidated anyway, because the explicit path is doing the real work. **An entry with no TTL and no successful delete is a permanent lie.**

### Rule 4: close the stale-fill race, or bound it

Bug one is not fixed by any of the above — the reader's `set` lands after the writer's `delete` in genuine wall-clock order. Three honest options, in increasing order of cost:

**Bound it with the TTL and move on.** The race requires a reader to be descheduled across a write to the same key. On most systems that's rare and the damage is one stale entry for one TTL. If the TTL is 60 seconds and the data isn't money, this is a reasonable place to stop — and it's the reason the hour-long TTL in bug two made everything worse.

**Version the entries.** Store `{version, value}` and refuse to overwrite a newer version with an older one. You usually already have a version: the row's `updated_at`, or the optimistic-locking column from Module 6.5. The read path reads the version along with the row, and the cache write becomes conditional. This turns last-writer-wins into monotonic and eliminates bugs one *and* two at once, which makes `set`-on-write safe as well. It's the implementation section below.

**Use leases.** The cache hands the missing reader a token, and only that token-holder may fill the key; a write invalidates outstanding tokens. This is what Facebook's memcache deployment does, it also solves the stampede, and it requires cache-side support that most deployments don't have.

There's also a widely-copied hack worth naming so you can recognize it: **delayed double delete** — invalidate, write, then invalidate again a second or two later, betting the second delete lands after any in-flight fill. It narrows the window rather than closing it, needs a reliable delayed-execution mechanism to be better than nothing, and is strictly worse than versioning if you have a version available. It shows up in a lot of production code; it should show up with a comment.

### Rule 5: invalidate where writes converge, not where they're called

Bug three is the one that gets systems in the end, because it's organizational rather than technical. **A cache is only as correct as the least disciplined thing that writes the table** — and that includes a webhook handler written by someone who's never read this code, a data migration, and a human with `psql` open at 3am.

Three places to put the invalidation, increasingly hard to bypass:

```
at the call site        in the repository / UoW        from the database log (CDC)
  ~~~~~~~~~~~~            ~~~~~~~~~~~~~~~~~~~            ~~~~~~~~~~~~~~~~~~~~~~~~
  every writer must       every writer using your        every writer, including
  remember                code is covered                psql, is covered
  ✗                       ✓ for your app                 ✓✓, plus an operational
                          ✗ for webhooks that            system to run, and
                            bypass it, jobs, and         invalidation that is
                            manual SQL                   now asynchronous
```

The middle option is where most teams should live: invalidation attached to the persistence layer (the Repository or Unit of Work, Module 2.5) so it happens by construction rather than by memory. The right-hand option — subscribing to the replication log with something like Debezium and invalidating from it — is the only one that's actually complete, and it belongs to systems where the cost of a stale read justifies running a CDC pipeline. Module 38.4 covers the mechanism; 13.3a covers what it looks like as an invalidation strategy.

### Refresh-ahead, briefly

One more read-path pattern: **refresh-ahead** re-computes an entry shortly *before* it expires, so readers never meet an expired key. It's a good fit for a small number of expensive, predictably-hot entries — a homepage feed, a leaderboard — and pointless for a long tail, where you'd be refreshing millions of entries nobody is going to read. Its main motivation is avoiding the synchronized miss when a popular key expires, so the detail lives with stampedes in 13.2b.

### Read-your-writes

The opening bug was never really about invalidation; it was about one specific reader — the person who just made the change — for whom *any* staleness is a bug rather than a trade-off. Deleting the key fixes it only if their next read reaches a database that already has the new value, which is not guaranteed when reads go to a replica (Module 23.2 replication lag) or when each app instance holds its own in-process copy.

The options, cheapest first:

- **Return the new representation from the write itself**, so the client doesn't need to re-read. Frequently the whole fix, and it's a `PUT` that responds with the updated resource rather than `204`.
- **Pin that user's reads to the primary for a few seconds** after a write, usually via a short-lived flag in their session.
- **Write-through for that entity**, accepting the versioning requirement from rule 4.

## When It's Appropriate

- **TTL only, no invalidation** — reference data where seconds of staleness are genuinely fine: country lists, plan catalogues, public content. It's the cheapest option and the most under-used, because writing an invalidation path feels more rigorous than deciding that 60 seconds is acceptable.
- **Cache-aside + delete on commit** — the default for entity reads in a read-heavy system: a few hundred writes a day against millions of reads, staleness tolerable for milliseconds but not minutes.
- **Read-through** — when many call sites read the same entity and you want one loading path, or when the library gives you stampede protection and metrics for free. Mostly an ergonomics choice.
- **Write-through** — when a read reliably follows every write and a miss is expensive: a session record written on every request and read on the next one (Module 4.4), a shopping cart. Pay the extra write latency, and pair it with versioning if concurrent writers to one key are possible.
- **Write-behind** — high-rate, low-value writes where a few seconds of loss is acceptable and the write rate would otherwise dominate the database: view counters, `last_seen_at`, analytics events, rate-limit counters. The question to answer out loud is "how many seconds of these writes may we lose", and if the answer is "none", pick something else.
- **Write-around with no fill** — write-heavy keys that are rarely read, where populating the cache on write would evict things people actually want.

## When It's Unnecessary or Overkill

- **The product tolerates the TTL.** Ask before building. A sixty-second staleness budget removes this entire article from your system.
- **Versioned entries for data with one writer.** If a row is only ever written by one job, last-writer-wins is fine and the version is ceremony.
- **CDC-driven invalidation before you have multiple write paths.** It's a pipeline to operate, and its payoff is proportional to the number of writers you don't control.
- **Write-behind for anything a user would notice losing.** The list of things people have implemented write-behind for and later regretted is mostly "things that turned out to be money".
- **Write-through everywhere.** It adds latency to every write to benefit readers who may never arrive, and on a write-heavy key it fills the cache with garbage.
- **Chasing the last race.** There is no ordering of two systems without a transaction across them that gives you a zero-width window. Past a point the correct engineering move is to bound the window, monitor it, and spend the remaining effort on something else.

## Trade-offs

**Writes are now coupled to the cache.** Every write path acquires a second responsibility and a second way to fail. The coupling is invisible in the type system and enforced only by convention, which is why rule 5 is about *where* the code lives.

**You've traded one failure mode for a rarer, stranger one.** Before invalidation, staleness was uniform, bounded, and boring. After it, staleness is rare, unbounded when it happens, and correlated with load, deploys, and failovers — which is to say it happens during incidents and not during testing.

**The hit rate on written keys collapses.** Delete-on-write means every write costs you the next reader, and possibly many readers at once.

**Errors have to be swallowed *and* recorded.** A cache failure must not fail the request, but a silently-dropped invalidation is bug four. The pattern is: catch, continue, increment a counter, and rely on the TTL. If the counter is non-zero and nobody has an alert on it, you have bug four with extra steps.

**Two caches means two invalidations.** An in-process cache in twelve app instances does not hear about a `DEL` in Redis. Either give local entries very short TTLs, or broadcast invalidations — which is a messaging system with delivery semantics, in 13.3a.

**None of this is transactional.** The database commits and the cache delete are two operations against two systems with no shared atomicity. This is the dual-write problem in miniature, and the mature answers are the same ones Module 37 gives for dual writes: make one of them the source of the other (CDC), or accept and bound the window.

## Alternatives

- **Don't invalidate — change the key.** If the key includes a version (`customer:42:v17`) or a content hash, a write produces a *different* key and the old entry simply becomes garbage for the eviction policy to collect. It's the strongest option available and the reason 11.3a and 13.1a both reach for it. The catch is that the reader must know the current version before it can build the key, so it works beautifully when the version is already at hand — in the URL, in a parent object you loaded anyway, in a per-tenant epoch counter — and badly when discovering it costs the query you were trying to avoid.
- **Invalidate from the replication log.** One subscriber, every writer covered, no discipline required — with an asynchronous pipeline to operate and a lag of its own.
- **Publish invalidation events on the bus you already have.** The pragmatic middle ground once more than one service writes the data, and the mechanism you need anyway for in-process caches.
- **Precompute instead of caching.** A summary table maintained inside the same transaction as the write has no window at all, because there is no second system. Covered as an alternative to caching in 13.1a, and it's the right answer more often than its unfashionability suggests.
- **Make the read fast enough not to cache.** Still the alternative that eliminates the most code.

## How to Achieve It

**1. Start with TTL only and find out whether anyone complains.** You'll learn the real staleness budget from the complaints rather than from a meeting.
*Next when:* a specific screen needs to reflect a specific write immediately.

**2. Add delete-after-commit in the repository for that one entity.** Not at call sites. Keep the TTL.
*Next when:* it's shipped and the hit rate hasn't collapsed.

**3. Count invalidation failures and alert on a non-zero rate.** Three lines, and it's the difference between bug four being a monitoring event and a customer escalation.
*Next when:* the counter exists.

**4. Fix read-your-writes by returning the new representation from the write.** Cheaper than everything else in this article and it solves the complaint that started it.
*Next when:* users still see their own edits missing — which now means replica lag or a local cache, not this cache.

**5. Add versioned entries when you observe staleness outliving the TTL.** Don't build it pre-emptively; build it when the evidence arrives, and you'll have the evidence in the same log line that told you the TTL was exceeded.
*Next when:* writers outside your codebase exist.

**6. Move invalidation to events or CDC when you can name three write paths.** Before that it's a pipeline with no users.

## Implementation

Go, because the ordering is explicit and the race is easy to show without framework machinery in the way.

The repository holds both halves, so no caller can do one without the other:

```go
func (r *CustomerRepo) Get(ctx context.Context, id int64) (Customer, error) {
	key := customerKey(id)

	if raw, err := r.cache.Get(ctx, key).Bytes(); err == nil {
		var e entry
		if json.Unmarshal(raw, &e) == nil {
			return e.Customer, nil
		}
		// a corrupt or stale-shaped entry is a miss, never an error
	}

	c, err := r.db.LoadCustomer(ctx, id) // also returns c.Version (updated_at or a counter)
	if err != nil {
		return Customer{}, err
	}
	r.fill(ctx, key, c) // best-effort, version-guarded
	return c, nil
}

func (r *CustomerRepo) UpdateEmail(ctx context.Context, id int64, email string) error {
	tx, err := r.db.Begin(ctx)
	if err != nil {
		return err
	}
	defer tx.Rollback(ctx)

	if err := tx.SetCustomerEmail(ctx, id, email); err != nil {
		return err
	}
	if err := tx.Commit(ctx); err != nil { // ← invalidate only after this succeeds
		return err
	}

	if err := r.cache.Del(ctx, customerKey(id)).Err(); err != nil {
		r.metrics.InvalidationFailures.Inc() // do not fail the request; do not stay silent
		log.Warn("cache invalidation failed", "key", customerKey(id), "err", err)
	}
	return nil
}
```

Two asides on this, both of which are the difference between the code working and appearing to work.

*The `defer tx.Rollback` plus post-commit delete is the entire ordering rule.* Move the `Del` above `Commit` and you have manufactured the stale-fill race on every write, because a concurrent reader will miss, read the pre-commit row, and cache it. The compiler is fine with either.

*The failure branch is the one to review.* Swallowing the error is correct — a cache outage must not fail writes — but a swallowed error with no counter is a stale entry with no evidence, and the evidence is what tells you whether your TTL is the backstop you think it is.

The fill is where the race gets closed, and it has to be atomic, which means it happens inside Redis rather than in Go:

```go
// Store only if the key is absent or holds an older version.
var fillIfNewer = redis.NewScript(`
  local cur = redis.call('GET', KEYS[1])
  if cur then
    local ok, decoded = pcall(cjson.decode, cur)
    if ok and decoded.version >= tonumber(ARGV[2]) then
      return 0
    end
  end
  redis.call('SET', KEYS[1], ARGV[1], 'EX', tonumber(ARGV[3]))
  return 1
`)

func (r *CustomerRepo) fill(ctx context.Context, key string, c Customer) {
	blob, err := json.Marshal(entry{Version: c.Version, Customer: c})
	if err != nil {
		return
	}
	if err := fillIfNewer.Run(ctx, r.cache,
		[]string{key}, blob, c.Version, int(r.ttl.Seconds()),
	).Err(); err != nil {
		r.metrics.FillFailures.Inc()
	}
}
```

The check-and-set has to be one round trip to mean anything — a `GET`, a comparison in Go, and a `SET` is the same race one level up, and it's a mistake that survives testing indefinitely because the window is microseconds wide.

With this in place, the bug-one timeline ends differently: the slow reader's fill carries version 17, the entry it would overwrite carries version 18, and the script returns 0. The cache stays empty and the next reader loads the truth. The same guard is what makes `set`-on-write safe if you later want it, which removes the delete-induced miss on hot keys.

Note what the version costs: the read path must return it, every writer must bump it, and a `version` that's really `updated_at` at second granularity will compare equal for two writes in the same second — so use a monotonic counter or a timestamp with real precision. Optimistic locking (Module 6.5) gives you this column for free if you already have it.

## Further Reading

- **Microsoft's Azure Architecture Center, "Cache-Aside pattern"** — the clearest short, vendor-neutral write-up of the pattern and its consistency caveats, and a good thing to link in a design review.
- **Nishtala et al., "Scaling Memcache at Facebook" (NSDI 2013)**, §3.2 in particular, for leases: the mechanism that closes the stale-fill race from the cache's side rather than the application's, and the most complete published treatment of why that race matters at scale.
- **Redis documentation on scripting and transactions** — `EVAL`, script atomicity, and why `WATCH`/`MULTI` is the wrong shape for this. Also the `SET` options (`NX`, `XX`, `KEEPTTL`), which cover the simpler guards without Lua.
- **Debezium's documentation**, particularly the connector guarantees and the at-least-once delivery model, before building log-driven invalidation. The lag and the duplicate deliveries are both fine for invalidation and fatal for other uses, which is worth understanding before the pipeline exists.
- **Spring Framework's cache abstraction reference** (`@Cacheable`, `@CachePut`, `@CacheEvict`) — worth reading even if you never use Spring, as the most widely deployed declarative version of the table in *What It Is*. Note `beforeInvocation` on `@CacheEvict` and what it implies about ordering.
- **Module 6.5** for the version column and optimistic locking, **Module 37** for the dual-write problem this article's window is an instance of, **Module 38.4** for CDC, and **Module 13.2b** for what a delete-induced miss does to a hot key.

A **Java** sibling would change this article's conclusion in one specific place. Spring's `@CacheEvict` fires around the method, not around the *transaction*, so the default annotation-driven setup performs its invalidation before the commit — precisely the ordering rule 1 forbids — and the correct construction is an eviction bound to a `@TransactionalEventListener` at `AFTER_COMMIT`. That's a case where a framework makes the wrong thing a one-word annotation and the right thing three classes, and seeing it is a better argument for understanding the ordering than any amount of prose. It would also let the versioned fill be written against `@Version`, which is already there for optimistic locking. Not yet written.

---

The habit worth carrying: whenever a system holds the same fact in two places, find the line of code where they diverge and ask how wide the window is, what closes it, and what happens if that thing fails. Cache and database is the instance you meet first. Database and search index, service and its local copy of another service's data, browser state and server state — all the same question, and the answers are always some combination of the three in this article: order the writes, version the values, or bound the staleness and watch it.
