# The Cache You Have to Operate

_Module 13.4a — Caching Strategies_

## The Problem

One team, three decisions, eighteen months.

**They moved a cache out of the process.** Plan configuration — forty rows, read on every request, changed weekly — lived in a `ConcurrentHashMap` behind a five-minute refresh. Someone pointed out that the twelve instances could briefly disagree after an edit, which was true, so it moved to Redis for consistency. Median latency rose by 1.2ms across every endpoint, the app acquired a hard dependency on a network service for data that fit in 400KB, and the instances still briefly disagreed — because the client-side connection pool and the refresh timing hadn't changed, only the storage. The consistency problem was real; this wasn't its fix.

**They left a cache in the process.** The product-object cache stayed local because it was already written. At twelve instances that was mildly wasteful. At forty — autoscaled, deployed six times a day — it was forty copies of the same 3GB working set, forty cold caches after every deploy, forty independent fill storms, and a support workflow where "try refreshing" worked because it sometimes landed on a different pod.

**They consolidated everything into one Redis.** Cache entries, sessions, the job queue, rate-limit counters, and a distributed lock. It worked for a year. Then a marketing import wrote 4 million product entries into the cache in twenty minutes, memory hit the instance limit, and `maxmemory-policy` was at its default of `noeviction` — so Redis began rejecting writes. Not slowing down: *rejecting*. The queue couldn't enqueue, the rate limiter couldn't count, sessions couldn't be written, and every one of those paths treated a write failure as a fatal error, because none of them had been written to expect one. An import job took down authentication.

In the post-mortem someone finally opened `INFO memory`:

```
used_memory              6.21G     ← what Redis thinks it's using
used_memory_rss          8.94G     ← what the OS has actually given it
maxmemory                8.00G
mem_fragmentation_ratio   1.44
keyspace_hits            —         nobody had ever graphed this
evicted_keys             0         because the policy forbade it
```

The actual JSON, added up, was about 3GB.

Everything in this module up to here has been about what a cache *does*. This article is about the fact that it is also a piece of infrastructure with a memory allocator, an eviction policy, a failure mode, and a bill — and that most cache incidents are incidents of that second kind.

## What It Is

"Which cache technology" is three separate decisions that usually get made as one:

- **Locality** — in the process, in a shared service, or both.
- **Data model** — an opaque blob store, or a server that understands structures and runs your logic next to the data.
- **Topology and durability** — one node, a replicated pair, a sharded cluster; persistence on or off.

A useful thing to settle early: for pure caching, Redis and Memcached are both excellent, and the choice is rarely decided by benchmarks. It's decided by whether you need the things Redis has that a blob store doesn't — the Lua script from 13.2a, the tag sets and pub/sub from 13.3a, per-key TTL semantics, replication — and by which eviction behaviour you want.

The neighbour to separate is not another technology but another *use*. Cache, session store, job queue, lock service, and rate-limit counter are five different workloads with five different durability and eviction requirements, and they are all commonly described as "we use Redis". They do not belong in one instance, because **`maxmemory-policy` is a property of the instance, not of the key**. A single setting has to be simultaneously right for data that may be discarded at any moment and data whose loss logs everyone out (Module 4.4 covers that side). There is no such setting. The opening incident is what its absence looks like.

## Recognizing the Problem

- One Redis holding cache, sessions, queues, and locks.
- `maxmemory` unset — in which case your eviction policy is the OS out-of-memory killer.
- `maxmemory-policy` at its `noeviction` default on something used as a cache.
- `used_memory_rss` substantially above `used_memory`, or a fragmentation ratio well over 1.
- Nobody can state the hit rate from memory, and nothing graphs `keyspace_hits`.
- `evicted_keys` climbing and unalerted — the cache is silently smaller than you think.
- Cache operations visible in the p99 of request latency.
- Values above ~100KB, or `MGET`s of several hundred keys.
- A cache client with no timeout, or with retries and no budget.
- A failover that caused an outage rather than a blip.
- Serialization showing up as a measurable share of CPU in a profile.
- An in-process cache that is a plain `Map` with no bound.

## How It Works

### The latency ladder decides locality

```
in-process hit (object already in heap)     ~0.1–1 µs
shared cache GET, same availability zone     ~200–500 µs   round trip
  + deserializing a 100KB JSON value         ~0.5–2 ms     ← often the largest term
cross-AZ round trip                          +0.5–1 ms
origin query                                 1–100 ms
```

Two things fall out of these numbers. The jump from a shared cache to local memory is roughly a thousandfold — a bigger relative improvement than the one you got by adding the shared cache in the first place, which is why 13.2b reached for an L1 to fix hot keys. And **the deserialization term is frequently larger than the network term**, which means a "cache hit" in your traces may be mostly your own CPU.

### In-process: fast, plural, and yours to bound

You get no network, no serialization if you store the object itself, and no operations. You pay for it in ways that scale with fleet size:

*Memory multiplies.* Forty instances, forty copies.

*Hit rate falls as the fleet grows.* This is the under-appreciated one. A cache's value depends on requests per key (13.1a), and a load balancer divides your traffic by N before it reaches any given instance's cache. The same total memory spread across forty processes gives a lower hit rate than one shared pool, because reuse is what you're buying and you just split it forty ways.

*Deploys are cold starts.* If you ship six times a day, your local caches are never more than a few hours old, and the cold-start arithmetic from 13.2b applies to every deploy rather than to rare incidents.

*Instances disagree*, and invalidation needs a broadcast with a TTL backstop (13.3a).

*Mutable values are a live hazard.* If you cache an object and hand the same reference to every caller, one caller mutating it has corrupted the cache for everyone, and the bug surfaces somewhere else entirely. Cache immutable values, or copies.

*Unbounded is a memory leak.* A `Map` used as a cache is a leak with a friendly name. Use a real library — Caffeine, Guava, Ristretto, `lru-cache` — for bounds, eviction, and stats. On a managed runtime, also remember that a large on-heap cache is pressure on the garbage collector, and the pause it lengthens is paid by every request, not just the cached ones.

### Shared: one copy, at the price of a round trip

You get one working set instead of N, survival across deploys, a size that isn't limited by one process's heap, and something you can inspect and flush centrally. You pay the round trip, the serialization, connection-pool management, and a new dependency on the critical path of every request.

### Redis or Memcached

| | Memcached | Redis |
| --- | --- | --- |
| model | key → blob | strings, hashes, sets, sorted sets, streams |
| execution | multi-threaded | single-threaded command execution |
| server-side logic | none | Lua, functions |
| eviction | LRU per slab class | LRU/LFU/TTL/random, per-instance policy |
| replication | none (client-side sharding) | replicas, Sentinel, Cluster |
| persistence | none (extstore for flash) | RDB, AOF |
| memory overhead per item | lower at scale | higher |

The decision procedure is short. If you use the techniques from the rest of this module — tag sets, atomic conditional fills, pub/sub invalidation, per-key TTL — you need Redis or a Redis-compatible server. If you need a very large, very simple blob cache and want predictable multicore throughput with minimal per-item overhead, Memcached is still an outstanding choice and quietly runs some of the largest caches in existence.

The single-threaded property deserves naming as a design constraint rather than a benchmark result: **in Redis, one slow command stalls every other client.** That is why `KEYS` is a hazard (13.3a), why an unbatched `DEL` of 50,000 members is an incident, and why a Lua script is a lock on the whole server for its duration. Memcached's threading means a slow operation is less contagious.

One piece of context that affects procurement more than engineering: Redis's licence changed in 2024, and Valkey exists as a Linux Foundation fork of the last BSD-licensed version, with managed offerings from several clouds. For cache purposes they are interchangeable today; it's worth knowing which one you're actually buying.

### Eviction is a policy you must choose

Redis's `maxmemory-policy` options, and what each one means in practice:

- **`noeviction`** — the default, and wrong for a cache. Writes fail once memory is full. This turns "the cache is full" into "the application is erroring", which is the opening incident.
- **`allkeys-lru`** — evict the least recently used of anything. The sane default for a pure cache instance.
- **`allkeys-lfu`** — evict the least *frequently* used. Better under scan-like workloads: a batch job that touches millions of keys once will, under LRU, evict your entire hot set on its way past. LFU resists that, and it's why in-process libraries reach for admission policies like TinyLFU.
- **`volatile-lru` / `volatile-ttl` / `volatile-lfu`** — evict only among keys that have a TTL. The trap: keys without a TTL are immortal, and if enough of them accumulate, eviction has nothing left to free and writes start failing exactly as in `noeviction`. Only sane if *every* entry is guaranteed to carry an expiry.

Redis's LRU and LFU are sampled approximations rather than exact orderings — it examines `maxmemory-samples` candidates and evicts the best of them. That's fine, and it's worth knowing before you reason too precisely about which key survives.

### Memory accounting, or where 3GB became 9GB

Four separate multipliers, none of them visible in your data model:

*Per-key overhead.* Every key carries bookkeeping — on the order of 50–100 bytes for the key object, expiry entry, and dictionary slot. Ten million small keys is a gigabyte before any values. Grouping related fields into a hash instead of ten keys is a real memory optimization at that scale.

*Serialized size.* JSON of an object is usually well over its in-memory size, and pretty-printing or including nulls makes it worse.

*Fragmentation.* The allocator doesn't give memory back in the shape you freed it, so RSS exceeds `used_memory`. `mem_fragmentation_ratio` above roughly 1.5 is worth investigating; `activedefrag` exists for it.

*Fork.* If persistence is enabled, `BGSAVE` forks, and copy-on-write means RSS can transiently approach double under write-heavy load. This is why `maxmemory` should sit meaningfully below the machine's RAM — 60–70% is a common rule — rather than at it.

### Serialization is your cost, not the cache's

It happens in your process, on every hit, and it's the term people forget when they compare "a cache hit" with "a query".

Choose the format deliberately. JSON is the default and is usually fine below a few kilobytes. MessagePack, Protobuf, or Avro are meaningfully faster and smaller for large values. Language-native serialization (Java's, Python's pickle) is tempting and a bad idea for cache blobs — it's brittle across deploys and, for Java, a well-known remote-code-execution surface if anything untrusted can reach the cache.

Compression above roughly 10KB is often a clear win: LZ4 or Zstd at a low level trades a little CPU for a large reduction in both network time and cache memory.

And the thing that bites during a deploy: **cached blobs outlive the code that wrote them.** A rolling release means old and new versions read each other's entries. Deserialization must never throw its way into a 500 — a failure to parse is a miss (13.2a's `Get` does this deliberately) — and any change to the stored shape should bump the epoch prefix from 13.1a rather than relying on tolerance.

### Topology and what failure looks like

*Single node.* Simplest, and its failure is the full cold start you sized for in 13.2b. For many systems this is the right answer, precisely because it forces that sizing to be honest.

*Primary with replica and automatic failover.* Removes the cold start at the price of seconds of unavailability during promotion, plus however long clients take to notice. Those seconds are survivable only if the client fails fast.

*Cluster.* Keys are distributed across hash slots, and multi-key operations must live in one slot — which constrains this module directly: the tag set and its members in 13.3a's Lua script have to hash together, using a hash tag like `{product:842}` in the key, or the script is rejected. Design keys for that before sharding, not after.

The client-side rule that matters more than any of the above: **a cache client must fail fast and fail open.** Connect and read timeouts in the tens of milliseconds, a bounded pool, no unbudgeted retries, and a code path where a cache error is a miss rather than an error. Fail-open is only safe if the origin can take the resulting traffic, which is the survivable-hit-rate number from 13.2b — the two decisions are the same decision.

### The numbers to graph

- **Hit rate per key prefix, measured client-side.** The server's global `keyspace_hits`/`keyspace_misses` tells you almost nothing once one instance serves several features.
- **`evicted_keys` and `expired_keys`.** Evictions mean the cache is smaller than your TTLs imply, and rising evictions explain a falling hit rate.
- **`used_memory`, `used_memory_rss`, fragmentation ratio.**
- **Cache operation latency percentiles from the client**, plus `SLOWLOG` and `LATENCY` on the server.
- **Connection pool saturation and wait time** — a frequent cause of "Redis is slow" that isn't Redis.
- **Value size distribution.** A p99 value size of 800KB is a problem you can see coming.
- **Invalidation failures (13.2a) and the staleness canary (13.3a).**

## When It's Appropriate

- **In-process only** — small, hot, read-mostly data: configuration, feature flags, reference tables, compiled permission structures, and anything read more than once within a single request. Also the correct home for a per-request memo, which has no staleness at all.
- **Shared only** — working sets larger than a process can hold, expensive fills you don't want repeated per instance, and anything where instances disagreeing is visible to a user.
- **Both** — the mature default for large fleets: an L1 with a one-to-five-second TTL absorbing hot keys, an L2 holding the real working set.
- **Memcached** — a large, simple blob cache where per-item memory overhead and multicore throughput matter more than features.
- **Redis or Valkey** — everything else in this module, which is most of it.
- **Managed** — nearly always. The operational work here is failover, upgrades, and memory tuning, and none of it is your product.

## When It's Unnecessary or Overkill

- **Cluster before one node is the constraint.** A single modern node serves well over 100,000 operations a second and holds tens of gigabytes. Most applications never approach either, and sharding costs you multi-key operations, which costs you 13.3a.
- **Persistence on a pure cache** — with one honest exception. RDB or AOF on a cache is not durability; it's cold-start insurance, letting a restarted node come back warm. That's a legitimate reason to enable it, and it should be justified that way rather than by "we didn't want to lose the data".
- **A custom binary format before profiling JSON.** Measure first; the answer is often that the value is too large, not that the encoder is too slow.
- **Compression on 200-byte values.** Pure overhead.
- **Cross-region cache replication.** Expensive, slow, and usually solved by a cache per region with its own fills.
- **An L1 layer on a small fleet with a healthy L2 hit rate.** It's a second invalidation path bought for microseconds nobody perceives.

## Trade-offs

**A shared cache is a new dependency on every request.** It needs the failure handling of any critical dependency, and "the cache is down" must be a tested path rather than a theoretical one.

**Separating instances by policy costs money and saves blast radius.** Four small instances cost more than one large one and cannot take each other down. The opening incident is the price of the other choice, paid once.

**Two layers means two of everything.** Two hit rates, two invalidation paths, two staleness windows, and a debugging question that starts with "which layer served this".

**Memory is expensive relative to what it replaces.** RAM costs roughly an order of magnitude more per gigabyte than the storage the database is using. A cache sized to hold the entire dataset is often more expensive than simply buying a larger database — and the hit-rate curve from 13.1a flattens long before that point anyway.

**Managed services take the tuning away along with the toil.** Some restrict configuration, scripting, or the commands you're allowed to run. Check before designing around a feature.

**Every knob here has a default, and the defaults are not chosen for your workload.** `noeviction` is a reasonable default for a database and a bad one for a cache. The general lesson is that the moment you call something a cache, you have opted into settings that nobody set.

## Alternatives

- **The database's buffer pool and a larger instance.** Still the first alternative in 13.1a, and it needs no new systems.
- **Flash-backed caches.** Memcached's extstore and similar designs keep hot keys in RAM and spill the rest to SSD, which changes the economics entirely for very large working sets with moderate latency requirements.
- **A replicated dataset instead of a cache.** For small, read-mostly data, publish an immutable snapshot to every instance and swap it atomically on change. No TTL, no invalidation, no misses, no network on the read path — and bounded staleness equal to publish latency. For the plan configuration in the opening story, this was the correct answer all along.
- **Push the caching outward.** A CDN or edge cache (Module 7.4a) removes traffic before it becomes your problem, for anything cacheable at that layer.

## How to Achieve It

**1. Split instances by workload.** Cache, sessions, queue, locks. Cheapest high-value change available, and it turns one shared blast radius into four small ones.
*Next when:* each instance has one job.

**2. Set `maxmemory` and an explicit policy on each.** `allkeys-lru` or `allkeys-lfu` for caches; something that never discards for the others. Alert on write errors.
*Next when:* the policy is explicit and the alert exists.

**3. Graph hit rate per prefix, evictions, memory, and client-side latency.** Four graphs; everything else in this module becomes measurable once they exist.
*Next when:* someone can answer "what's our hit rate" without logging into anything.

**4. Look at the value-size distribution and fix the outliers.** Usually a handful of endpoints caching far too much, and usually a five-line fix.
*Next when:* p99 value size is boring.

**5. Set client timeouts and test the cache being down**, at low traffic, with the survivable hit rate calculated in advance.
*Next when:* cache-down degrades instead of failing.

**6. Add an L1 for measured hot keys**, with a short TTL backstop.

**7. Only then** consider cluster, persistence, or a different serialization format — each against a measurement that names it.

## Implementation

Mostly configuration, so that's most of what's here; inventing an elaborate program for this would obscure the point.

```conf
# a cache instance — and only a cache instance
maxmemory 6gb               # well under the machine's 10GB: fragmentation and fork need room
maxmemory-policy allkeys-lfu
maxmemory-samples 10        # sampling accuracy; 5 is the default, 10 is measurably better

save ""                     # no RDB snapshots: no fork pauses, no COW spikes
appendonly no               # this data is reconstructible by definition

timeout 300                 # reap idle client connections
tcp-keepalive 60
activedefrag yes            # when mem_fragmentation_ratio stays above ~1.5
```

The session instance beside it disagrees on nearly every line — `maxmemory-policy volatile-ttl`, persistence on, a smaller `maxmemory` — which is the entire argument for it being a separate instance.

The client policy is the part that belongs in code. Go, because the deadline propagation and the fail-open branch are explicit rather than configured somewhere else:

```go
const (
	cacheTimeout = 25 * time.Millisecond  // ~50× the expected latency; anything slower is a miss
	maxValueSize = 256 * 1024
)

func (c *Cache) Get(ctx context.Context, key string) ([]byte, bool) {
	ctx, cancel := context.WithTimeout(ctx, cacheTimeout)
	defer cancel()

	b, err := c.rdb.Get(ctx, key).Bytes()
	switch {
	case err == nil:
		c.metrics.Hits.WithLabelValues(prefixOf(key)).Inc()
		return b, true
	case errors.Is(err, redis.Nil):
		c.metrics.Misses.WithLabelValues(prefixOf(key)).Inc()
	default:
		// Unreachable, slow, failing over: all of these are a miss, never an error.
		c.metrics.Errors.Inc()
	}
	return nil, false
}

func (c *Cache) Set(ctx context.Context, key string, val []byte, ttl time.Duration) {
	if len(val) > maxValueSize {
		c.metrics.Oversized.WithLabelValues(prefixOf(key)).Inc()
		return                                   // refuse, loudly, rather than degrade quietly
	}
	ctx, cancel := context.WithTimeout(ctx, cacheTimeout)
	defer cancel()
	_ = c.rdb.Set(ctx, key, val, jitter(ttl)).Err()
}
```

Three asides.

*The timeout is the whole failover story.* With 25ms, a ten-second promotion produces ten seconds of misses; with no timeout, it produces ten seconds of requests parked on a socket, which is an outage. The number should be a large multiple of normal latency and a small fraction of your request budget.

*`prefixOf(key)` is what makes the hit rate useful.* A single global number across every feature sharing the instance is an average of unrelated things, and it hides exactly the prefix whose hit rate just collapsed.

*The size guard exists because oversized values fail in someone else's request.* A 4MB entry consumes memory that evicts other keys, saturates the link, and — on a single-threaded server — occupies it while the bytes move. A counter and a refusal turn that into a metric with an owner.

## Further Reading

- **Redis documentation on key eviction** — the policy table, the sampled LRU/LFU implementation, and `maxmemory-samples`. The one page that would have prevented the opening incident.
- **Redis latency troubleshooting guide, plus `SLOWLOG` and `LATENCY DOCTOR`.** Written around the single-threaded model, and the fastest way to connect "our cache is slow" to the specific command doing it.
- **The Redis Cluster specification**, particularly hash slots and hash tags. Read it before your keys exist, because retrofitting hash tags onto a tag-based invalidation scheme is a migration.
- **The memcached wiki on memory allocation and slab classes, and the extstore documentation.** The slab model explains memory behaviour that looks like a bug, and extstore is the clearest example of the flash-backed alternative.
- **Valkey's project documentation**, for the fork's provenance and compatibility guarantees, if licensing is a consideration where you work.
- **OWASP's deserialization cheat sheet.** Short, and the reason native serialization does not belong in a cache blob.
- **Netflix's engineering writing on EVCache.** A long-running public account of caching at large scale, including multi-region replication and SSD tiering — useful mostly as a picture of what the far end of this road looks like, and how little of it most systems need.
- **Module 4.4** for why session storage wants the opposite settings, **13.1a** for the hit-rate arithmetic these knobs move, **13.2b** for the failure this article's timeouts are protecting, **13.3a** for what sharding does to tags, and **Module 19** for where these metrics belong.

A **TypeScript** sibling would show one thing this article can only state. On a single-threaded runtime, deserialization isn't merely a cost on the hit path — it's a *blocking* cost: `JSON.parse` of a 2MB cached value occupies the event loop for tens of milliseconds, during which every unrelated request on that instance waits. The size guard above stops being a memory-efficiency measure and becomes a latency isolation mechanism, and the fix list changes shape — streaming parsers, moving large values out of the cache entirely, or accepting that one endpoint's cache entry is a global tail-latency source. Java and Go hide this behind thread pools; Node makes it the first thing you measure. Not yet written.

---

Where this module leaves you: a cache is a bet on repetition (13.1a), a contract about staleness (13.2a), a reshaping of load (13.2b), a dependency graph you have to record (13.3a), and a piece of infrastructure with an allocator and a policy (this one). The habit that covers all five is to ask, of any component that makes your system faster, **what it does when it isn't there** — because that's the state you'll meet during the incident, it's a state you can create deliberately on a quiet afternoon, and almost nobody does until the first time it happens to them.
