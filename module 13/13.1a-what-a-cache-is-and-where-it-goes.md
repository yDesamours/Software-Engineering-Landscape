# What a Cache Is, and Where It Goes

_Module 13.1a — Caching Strategies_

## The Problem

A B2B analytics product. The main screen is `GET /dashboards/:id`, and it sits at about 600ms at p95. A representative trace:

```
auth + tenant resolution         40ms
9 database queries              430ms   ← one of them alone is 380ms
assembly + JSON serialization    90ms
                                ─────
                                560ms
```

Traffic doubled last quarter, database CPU is at 75%, and somebody says the word Redis. Everyone nods, because the 380ms query is obviously the problem — a six-table aggregate over the events table that runs on every page load.

So it gets cached, cache-aside: look in Redis, and on a miss run the query and store the result with a five-minute TTL. Fifteen lines. Ships on a Thursday.

**Monday's numbers: hit rate 4%.**

The key was `dash:{dashboard_id}:{from}:{to}`, where `from` and `to` are the charted time range. The UI offers "last 30 days", which the frontend resolves to an exact `to` of *now*, to the millisecond. Every request produces a key nobody will ever ask for again. The cache is a write-only store, and the 4% is double-clicks.

Rounding both timestamps down to five-minute boundaries collapses the key space from one entry per request to one per dashboard per five minutes. **Hit rate 81%.** And:

```
                     before      after
median latency        520ms      150ms
p95                   600ms      580ms
DB CPU                  75%        31%
```

The median moved and p95 did not, which surprises people every time. At an 81% hit rate, roughly one request in five is a miss, so the 95th-percentile request is a miss by definition — it pays the full 560ms. A cache improves the median first; it only improves p99 once the hit rate passes 99%. The thing that actually got better was the database, which is now running that aggregate a fifth as often. The cache paid off, just not in the currency anyone was measuring.

Next attempt: cache the whole response instead of one query, so a hit skips all nine queries and the serialization too. Except the dashboard shows different numbers to different people — a regional manager sees their region. The first version of that key didn't account for it, and for four minutes one manager saw another region's revenue. The fixed key includes the viewer's permission scope, 1,200 users across 40 tenants stop sharing entries, and the hit rate falls to 30%.

Then someone runs `EXPLAIN` on the 380ms query. It's a sequential scan over 40 million event rows. The right composite index takes it to 25ms.

The cache was paying rent on a bug — and hiding it. Worse: for three months the database had been provisioned on the assumption that it only sees 19% of that traffic. The day Redis restarts, 100% of it arrives at a query the database was never able to serve.

Fifteen lines of code made three separate decisions, and all three were wrong:

- **what** to cache — the cheapest third of the work
- **what the key is** — too precise to ever hit, then imprecise in the one dimension that was a data leak
- **whether to cache at all** — the expensive computation was avoidable, so the repeated part shouldn't have existed

Everything else in this module is a refinement of those three.

## What It Is

A cache is a copy of a result, kept somewhere cheaper to reach than whatever produced it, which is **allowed to be missing and allowed to be wrong**.

Both permissions are load-bearing. A copy you can't afford to lose is a database. A copy that has to be current is a replica. If deleting your entire cache would permanently change any answer the system gives, the thing you built is not a cache, and it needs backups, replication, and an on-call rotation to match.

Four neighbours are worth separating now, because the rest of the module assumes the distinction:

- **A read replica** is a full, authoritative copy maintained by the database itself. It's also stale, but you neither choose its contents nor control its lag.
- **A materialized view or summary table** is precomputed and *durable*. It has no misses and no eviction; the cost has moved to the write path or to a refresh job.
- **Denormalization** — storing an `order_count` on the customer row — is the same move made by hand. It's a write-side design decision, not a cache, and nothing here applies to it.
- **The database's buffer pool** is a cache, one you didn't build and mostly can't steer. It's why the second run of your slow query is fast, and why benchmarking without a cold cache lies to you.

## Recognizing the Problem

Signals that a cache is the right tool:

- The same query, with the same parameters, runs thousands of times a minute.
- Five query fingerprints account for most of the database's total time (`pg_stat_statements` answers this in one query).
- A table with a read-to-write ratio in the hundreds or thousands.
- An endpoint whose cost doesn't depend on anything the user did — a plan list, a config lookup, a public landing page.
- One page load fanning out into forty lookups of the same dozen rows.
- A third-party API you pay per call, or that rate-limits you, returning answers that change daily.
- Latency flat but database CPU climbing in lockstep with signups.

Signals that a cache you already have isn't working:

- Nobody can tell you the hit rate.
- The hit rate is under 50%, or it looks fine but latency didn't move.
- Cache keys containing a full-precision timestamp, a request ID, or a float.
- "Clear the cache" appears in a support script.
- Two users report different numbers for the same screen and neither is refreshing.

## How It Works

Every cache is three decisions — **what unit you store, what key you store it under, and how it stops being trusted** — plus one choice of location that quietly constrains all three.

### The ladder

The same result can be cached at several distances from the user, and the layers are not interchangeable:

```
         browser        CDN / edge      response cache   object cache     DB buffer
         cache          cache           (shared)         (Redis / heap)   pool
 user ─────▶ ┆ ─────────────▶ ┆ ─────────────▶ ┆ ──────────────▶ ┆ ─────────────▶ ┆ ──▶ disk

 a hit skips:  everything      everything      all queries +    one query        one disk
               incl. network   past the edge   serialization                     read
 shared by:    1 user          1 region        everyone with    everyone         everyone
                                               the same scope
 can you       no — it's       purge API,      yes              yes              not yours
 take it back: gone            seconds to
                               minutes
```

The pattern is a single trade: **the closer to the user a cache sits, the more work a hit skips, the fewer people share each entry, and the less able you are to take it back.** A browser cache is the fastest possible hit and completely beyond your reach for as long as its `max-age` says. A buffer-pool hit saves one disk read, is shared by everyone, and manages itself.

This module lives in the middle three rungs. The browser and CDN rungs are HTTP caching, which is Module 7.4a's territory and shouldn't be re-derived here; the buffer pool belongs to query tuning in Modules 6 and 22.

### Decision 1: the unit

Cache too deep and a hit saves a fraction of the request, as in the opening. Cache too shallow and the entry is shared by one person for one screen and never read twice.

The working rule: **cache at the outermost layer where the entry is still shared by enough traffic to be read again before it dies.** In the dashboard example, the per-query cache was shared by everyone and saved a third of the work; the per-response cache saved all of it and was shared by one permission scope. Neither is the obvious winner — which one is depends entirely on how many people occupy each scope, which is a fact about the product, not about caching.

### Decision 2: the key

**The key must contain everything that changes the answer, and nothing else.** Both errors are expensive and they fail in completely different ways.

Too much in the key and the hit rate goes to zero, loudly enough to notice — that's the millisecond timestamp. Too little and you serve one user's data to another, silently, intermittently, and only under load. The dimensions to walk through deliberately for every cached thing:

| dimension | belongs in the key when |
| --- | --- |
| tenant | always, on anything multi-tenant — no exceptions and no judgment calls |
| viewer / permission scope | the answer is filtered by who's asking |
| locale, currency, timezone | anything rendered or formatted |
| plan or feature flags | the answer differs by entitlement |
| time | rounded to the coarsest bucket the product tolerates |
| shape version | always — see the implementation section |

The tenant line is the one to make unskippable in review. It's a single missing field, it passes every test written against a single tenant, and its symptom in production is a customer seeing another customer's data.

### Decision 3: lifetime

An entry stops being trusted in one of three ways: a TTL expires it, memory pressure evicts it, or something explicitly deletes it. The first two happen whether you plan for them or not, which is why the rule about being *allowed to be missing* is absolute — any entry can vanish between the moment you wrote it and the next line of code. Explicit invalidation is Module 13.3's subject.

### The arithmetic that decides it

Two small calculations answer most "should we cache this" arguments before any code is written.

```
effective cost = hit_rate × hit_cost + (1 − hit_rate) × (miss_cost + fill_cost)
```

A miss is *more* expensive than no cache at all: you pay the lookup, miss, do the work anyway, then pay to serialize and store it. At low hit rates a cache is a straight loss.

And the rule that decides the hit rate itself:

> **An entry is only worth storing if it's read again before it expires or is evicted.**

That makes cache value a function of **request rate per key**, not of total traffic. A dashboard read once every five minutes with a 60-second TTL has a hit rate of zero no matter how much memory you buy. A site serving 50,000 requests a second spread over 50 million distinct keys is in the same position. Total traffic is the number everyone quotes and it's the wrong one.

## When It's Appropriate

- **A read-heavy hot set.** 2,000 reads/sec against a few hundred rows that change a handful of times an hour — a plan catalogue, feature configuration, a navigation tree. Even a 30-second TTL removes almost all of it.
- **Skewed access.** Real key distributions are Zipfian: the top 1% of keys are often half the reads. That's the case where 200MB of memory does the work of a much larger database, and it's worth measuring rather than assuming.
- **Fan-out inside one request.** A page that resolves the same twelve permission rows forty times. Here even a request-scoped in-process cache — a `Map` that lives and dies with the request — is a large win with no staleness whatsoever, and it should be the first thing tried.
- **Cost and quota, not latency.** A third-party enrichment API at $0.002 a call, rate-limited to 10/sec, returning company records that change monthly. A cache here is a billing decision; the latency improvement is incidental.
- **Expensive derivation from cheap inputs.** Rendered markdown, a compiled permission tree, a parsed and validated schema. The source row is one fast read; the transformation is the cost.
- **Absorbing an upstream you don't control.** If a dependency's p99 is unpredictable, a cache in front of it converts some of their bad minutes into your normal ones — and the serve-stale-on-error variant extends that to their outages.

## When It's Unnecessary or Overkill

- **The slow thing is slow for a fixable reason.** A missing index, an N+1, a query pulling 400KB to render twelve numbers. Fix it. A cache over a broken query is a bug with a 95% duty cycle, and the miss path is the one you'll meet during an incident.
- **The cached part isn't the expensive part.** Measure the breakdown before choosing the layer, or you'll build the opening section's first attempt.
- **The key space is the size of the request count.** No memory fixes this; only a different key does.
- **Traffic per key is below one read per TTL window.** Common in B2B, where "high traffic" is 300 requests a second spread across 4,000 tenants who each touch their own data.
- **The thing being cached is already fast.** A Redis round trip is roughly half a millisecond on a good day, plus serialization on the way in and deserialization on the way out. Caching a 200-microsecond in-memory computation makes it slower.
- **A user must immediately see their own write.** Cacheable in principle, but only with the read-your-writes handling in 13.2a, and never with TTL alone.
- **Correctness-critical reads.** The balance at the moment of debit, stock at checkout confirmation, whether a session was just revoked. Some of these *can* be cached with explicit invalidation and a fail-closed miss path, but none of them can be cached with a TTL and a shrug.
- **You have no traffic yet.** At 50 requests a second a cache is a second system to run, a new failure mode, and a new category of bug report, bought with latency the user can't perceive.

## Trade-offs

**You now have two answers and a window in which they disagree.** Permanently. Every subsequent bug report acquires a new first question, and "I can't reproduce it" becomes "which instance served you".

**The cache becomes load-bearing, and nobody decides this consciously.** Capacity gets sized against the miss traffic you currently have, not the miss traffic you'd have at a 0% hit rate. Once a cold start can't be survived, the cache is a hard dependency wearing an optimization's clothes, and the failure is non-linear: the moment the hit rate drops, the origin slows, which lengthens fills, which drops the hit rate further. That spiral is 13.2b's subject; the thing to carry from here is that it begins on the day you install the cache, not the day you notice.

**Hits are not free.** 400KB of JSON crossing a socket and being parsed can consume a real fraction of what the hit saved. Measure hit *latency*, not just hit rate.

**A cache key is a security boundary that doesn't look like one.** No type system, no test, and no code review checklist flags a missing tenant dimension by default. Put it in the key builder where it can't be forgotten, not at each call site.

**Operational surface.** Another service to run, monitor, secure, fail over, and upgrade — plus memory to size and an eviction policy to choose, both of which will be wrong the first time.

**Debuggability.** Reproducing a cache bug requires reproducing a *history*, not a state. This is why per-response headers or log fields naming which layer served a request pay for themselves within a week.

## Alternatives

A cache is the right answer when a computation is genuinely unavoidable and genuinely repeated. Attack either half instead:

- **Make it fast.** An index, a rewritten query, a covering index, a smaller payload. Permanent, no staleness, no new systems. Always price this first.
- **Precompute on write.** A counter column, a summary table, a materialized view refreshed on change. Moves cost to the write path, which is the right trade at 1000:1 read ratios, and produces a durable, queryable, joinable result — with no misses, no eviction, and no cold start. The invalidation problem doesn't disappear; it becomes a correctness problem on the write side instead, which is at least easier to test.
- **Read replicas.** Scale read capacity without any application-level staleness contract — at the price of replication lag you don't control and a routing decision per query.
- **Do less work.** Pagination, field selection, dropping the count query nobody reads. Frequently larger than any cache would have been.
- **Buy a bigger database.** Unfashionable, instantly reversible, and often cheaper than the engineering time of the alternatives for another year.

## How to Achieve It

**1. Measure before choosing a layer.** Get the per-request time breakdown and the top query fingerprints. You're looking for one number: what fraction of the request would a hit actually remove.
*Next when:* you can name the layer and the expected saving.

**2. Simulate the hit rate from logs.** Replay a day of real traffic through a candidate key and a bounded cache, offline. Costs an afternoon, needs no deploy, and kills bad ideas before they ship. The implementation below does this.
*Next when:* the simulated hit rate justifies the work.

**3. Cache one key, on one endpoint, with a TTL only and no invalidation, behind a flag.** Cache-aside, the pattern in 13.2a. Choose the shortest TTL that still gives the hit rate you modelled.
*Next when:* it's on in production and instrumented.

**4. Instrument four numbers: hits, misses, hit latency, miss latency.** Broken out by key prefix. Without these the next three steps are guesswork, and most caches never get them.
*Next when:* you can see the hit rate on a dashboard.

**5. Move outward or inward based on what the numbers say.** High hit rate and unchanged latency means you cached too deep — move toward the response. Low hit rate with heavy memory use means the key is too specific — coarsen it, checking each dimension you drop against the leak in decision 2.
*Next when:* the endpoint is where you want it.

**6. Only now consider explicit invalidation**, and only if the TTL that gives an acceptable hit rate is longer than the staleness the product tolerates. If a 60-second TTL is fine with everyone, you are done and you have avoided the hard part of this module entirely (13.3a).

**7. Recheck the miss path.** Can the origin serve 100% of this traffic? If not, you've crossed into load-bearing and owe yourself 13.2b.

## Implementation

TypeScript, in two parts: the key, and the thing to build *before* the cache.

### The key builder

Keys should be constructed in one place, never by string concatenation at call sites:

```ts
const CACHE_EPOCH = 7;           // bump when the stored shape changes
const BUCKET_MS = 5 * 60_000;

type Viewer = {
  tenantId: string;
  scopeHash: string;             // hash of *effective* permissions, not the role name
  locale: string;
};

function dashboardKey(v: Viewer, dashboardId: string, range: Range): string {
  const from = Math.floor(range.from / BUCKET_MS);
  const to   = Math.floor(range.to   / BUCKET_MS);
  return [
    `v${CACHE_EPOCH}`,
    "dash",
    v.tenantId,                  // the line whose absence was the leak
    v.scopeHash,
    dashboardId,
    `${from}-${to}`,
    v.locale,
  ].join(":");
}
```

Three things are doing real work here.

*The epoch prefix is how you avoid ever flushing the cache on deploy.* Change the stored shape, bump the number, and the new code simply never asks for the old keys, which go unreferenced and get evicted on their own schedule. This is the same trick as content-addressed derivative keys in 11.3a, and it converts a scary operation into an integer.

*`scopeHash` must be derived from effective permissions, not from the role name.* Two users can share a role and see different data — that's exactly the regional-manager bug. Hash the resolved set of visible region IDs, not the string `"manager"`.

*A hash in the key has a cost you're deferring.* You can no longer enumerate the keys affected by a change, because the key isn't derivable from the data that changed — only from the request. That's fine with TTL-only invalidation and it's a real obstacle later, which is why tag-based invalidation exists (13.3a).

### The simulator

Before writing any cache, find out what one would have done. Access logs already contain everything needed:

```ts
class SimCache {
  private entries = new Map<string, number>();  // key -> expiry (ms); Map keeps insertion order
  hits = 0;
  misses = 0;

  constructor(private capacity: number, private ttlMs: number) {}

  read(key: string, now: number): void {
    const expiry = this.entries.get(key);
    if (expiry !== undefined && expiry > now) {
      this.entries.delete(key);
      this.entries.set(key, expiry);            // re-insert = mark as most recently used
      this.hits++;
      return;
    }
    this.misses++;
    this.entries.set(key, now + this.ttlMs);
    if (this.entries.size > this.capacity) {
      this.entries.delete(this.entries.keys().next().value!);  // evict least recent
    }
  }
}

for (const capacity of [1_000, 10_000, 100_000, 1_000_000]) {
  for (const ttl of [10_000, 60_000, 300_000, 3_600_000]) {
    const sim = new SimCache(capacity, ttl);
    for (const { ts, viewer, dashboardId, range } of accessLog()) {
      sim.read(dashboardKey(viewer, dashboardId, range), ts);
    }
    report(capacity, ttl, sim.hits / (sim.hits + sim.misses));
  }
}
```

The output is a small grid, and **its shape tells you which knob you're actually holding**:

```
              ttl=10s   ttl=60s   ttl=5m    ttl=1h
cap=1k          0.31      0.52      0.68      0.71
cap=10k         0.33      0.57      0.79      0.86
cap=100k        0.33      0.57      0.80      0.91
cap=1M          0.33      0.57      0.80      0.91
```

Read along a row: TTL is buying you a lot, so the real negotiation is with the product about staleness, and the exchange rate is now a number instead of a hunch. Read down a column: past 10,000 entries, memory stops mattering — the working set fits, and provisioning ten times the memory buys nothing. If a column had been flat *everywhere*, the diagnosis would be the opening section's bug: the key space is too large and no cache configuration rescues it.

An honest caveat on the replay: it assumes reads are independent and ignores writes, so it gives you an upper bound on the hit rate, not a forecast. That's still the number that matters, because a disappointing upper bound is a decision you get to make for free.

## Further Reading

- **Nishtala et al., "Scaling Memcache at Facebook" (NSDI 2013).** The canonical paper on operating a cache at scale, and unusually honest about failure modes — leases, stampedes, regional pools, cold-cluster warmup. Everything in 13.2b is a footnote to it.
- **Redis documentation on key eviction** — `maxmemory`, `maxmemory-policy`, and the fact that Redis's LRU and LFU are sampled approximations rather than exact. Worth reading before choosing a policy, and required before putting a cache and anything durable in the same instance.
- **The memcached wiki, "Programming Tricks" and the tuning pages.** Written from operational scar tissue; the slab-allocator material in particular explains memory behaviour that looks like a bug.
- **Caffeine's efficiency documentation, and Einziger, Friedman & Manasse, "TinyLFU: A Highly Efficient Cache Admission Policy" (2015).** The argument that *admission* matters as much as eviction — that letting a one-off entry in is itself the mistake. It will change how you read the simulator output above.
- **PostgreSQL's `pg_stat_statements` documentation.** The fastest route from "the database is busy" to a ranked list of caching candidates.
- **RFC 9111 (HTTP Caching).** The two rungs of the ladder this article deliberately skipped, and the place where `stale-while-revalidate` and `stale-if-error` are specified. Pair it with Module 7.4a.
- **Module 7.4a** for the browser and CDN rungs, **Module 8.3c** for what GraphQL does to cache keys, **Module 11.3a** for content-addressing as invalidation-avoidance, and **Modules 6 and 22** for the query tuning that should usually be priced before any of this.

A **Java** sibling would show something this article can only describe. Caffeine turns each of the three decisions into a constructor argument — `maximumWeight` with a `Weigher` makes "capacity" mean bytes rather than entries, `expireAfterWrite` and `expireAfterAccess` split the TTL into two genuinely different policies, and `recordStats()` produces step 4's instrumentation without writing any. Most usefully, its `LoadingCache` collapses cache-aside into a single `get(key, loader)` call with stampede protection built in, which moves the next article's subject from application code into a library and makes it easy to stop thinking about. Seeing a mature in-process cache is also the cheapest way to notice how much of "we need Redis" is really "we needed a bounded map". Not yet written.

---

The habit to carry into the next cache you see: **a cache is a bet that the same question will be asked again soon, by someone who'll accept a slightly old answer.** Both halves are checkable before you write a line of code — how often does this key repeat, and how stale may it be — and almost every disappointing cache is one where nobody checked either.
