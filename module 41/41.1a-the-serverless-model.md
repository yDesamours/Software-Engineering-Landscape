# The Serverless Model: What Functions Buy, What They Cost, and When They Pay Off

_Module 41 · Serverless Patterns · 41.1a_

## The Problem

Suppose you run a receipt-processing product for accounting firms. Clients photograph receipts, the product reads them (OCR plus a classifier), and accountants review the results in a web app. Twelve engineers. It runs on a handful of containers: the web API, a worker pool reading a job queue, and a cron container for nightly exports.

The worker pool is the sore point. Receipts arrive in waves: almost nothing overnight, then thousands at 9 a.m. and a flood on the last three days of every month. The pool is sized for month-end, so it sits at 4% CPU most of the year. Someone moves OCR to AWS Lambda as an experiment. The results are excellent. Month-end spikes are absorbed automatically, the idle cost disappears, and the OCR bill drops from about $900 a month of mostly idle containers to about $60.

So the team moves **everything** to functions over one quarter. Six weeks later, the list of problems looks like this.

**The bill for the API went up, not down.** The web API serves a steady 150 requests a second during business hours and 40 overnight. As functions, it costs roughly three times the containers it replaced: per-request compute, plus an API Gateway charge per request that nobody had budgeted.

**Logins feel sluggish at 9 a.m.** The Java authentication service now starts a fresh JVM every time traffic grows, and at 9 a.m. traffic grows a lot. The p99 login time goes from 180 ms to 2.4 seconds.

**Some receipts are processed twice.** The classifier is triggered asynchronously by an upload event. When a classification call hangs and the function times out, the platform retries it, and the first attempt's result was already written. Some clients see duplicate expense lines.

**Some receipts are never processed.** Other asynchronous failures, a malformed image or a bug on one code path, fail three times, and then the event is simply dropped. There was no failure destination configured. Nothing alerts. Clients notice weeks later.

**The month-end export dies at 15 minutes.** The largest firm's export takes 22 minutes. Functions have a hard 15-minute limit, and the export is killed and retried until its queue gives up.

**Postgres runs out of connections.** On the first day of month-end, 700 function instances each open their own connection pool. (That one gets its own article, 41.3a.)

Nothing here is a bug in Lambda. The team adopted a compute model with specific properties, and applied it to workloads with the opposite properties. OCR fit perfectly: bursty, short, independent, nobody waiting. The API, the login path and the export didn't.

## What It Is

**Serverless** is a label for four separate properties that often come bundled together, and it helps to keep them apart:

| Property | Meaning |
|---|---|
| **No servers to manage** | No OS patching, capacity planning or instance sizing |
| **Scale to zero** | Nothing runs, and nothing is billed, when there's no work |
| **Pay per use** | Billing follows requests and execution time, not provisioned capacity |
| **Event-driven** | Code runs in response to an event (a request, a message, a file, a schedule), not as a long-lived process |

**Functions as a Service (FaaS)** (AWS Lambda, Google Cloud Run functions, Azure Functions) has all four. Other products have some of them: serverless containers (Fargate, Cloud Run services) remove servers but not always idle cost; serverless databases (41.3b) scale capacity with load. This article is about functions, using Lambda as the reference because its execution model is the most documented. 41.2a covers how the other platforms differ.

It's not the same as **"no operations work."** Serverless moves operational work from servers to configuration: retries, dead-letter queues, concurrency limits, timeouts, permissions. The receipt team discovered each of those by breaking it.

## Recognizing the Problem

Signs that a workload wants functions:

- A service sits mostly idle but is sized for peaks that come in bursts.
- Work arrives as discrete events (uploads, webhooks, messages, schedules) and each one is handled independently.
- You run cron containers or worker pools that are busy for minutes a day.
- Dev and staging environments cost nearly as much as production while nobody uses them.

Signs that functions are being used where they don't fit:

- The function bill grows linearly with traffic that's steady all day.
- Cold starts show up in user-facing p99 latency.
- Jobs hit the maximum duration, or are split into chains just to fit it.
- Duplicate processing or silently missing events, with no retries or dead letters in the design.
- The database's connection count follows the number of function instances.
- One function holds an internal router serving a whole API.

## How It Works

### 1. The execution environment's lifecycle

A function runs inside an **execution environment**: on Lambda, a small virtual machine with your runtime and code loaded. Its lifecycle explains almost every surprising behavior:

```
first request, no idle environment available
   │
   ▼
┌──────────────────────────── one execution environment ─────────────────────────┐
│  INIT ───────►  INVOKE ─►  INVOKE ─►  INVOKE ─► … ──────────────────► SHUTDOWN │
│  start runtime   handler runs, one request at a time (on standard Lambda)       │
│  load code       globals and /tmp survive between invokes                       │
│  run top-level   frozen between invokes: no CPU, timers don't fire              │
│  code                                                                           │
│  "cold start" = INIT + the first INVOKE                                         │
└─────────────────────────────────────────────────────────────────────────────────┘
10 simultaneous requests → 10 environments
```

Five consequences follow:

1. **Initialize expensive things once, outside the handler.** SDK clients, connection pools, parsed config and fetched secrets belong in INIT. Creating them per request repeats TLS handshakes and credential lookups on every call.
2. **Memory is a cache, never the truth.** Globals survive some invocations, in one environment, for an unknown time. A counter in a global isn't a counter.
3. **Nothing runs after the handler returns.** The environment is frozen. An un-awaited promise or background thread may run minutes later during someone else's request, or never.
4. **Concurrency means environments.** 700 simultaneous requests means up to 700 environments, each with its own clients and connections. The account has a regional concurrency limit (1,000 by default) shared by every function, and each function can add about 1,000 environments every 10 seconds.
5. **Cold starts cost latency and money.** Since August 2025 Lambda bills the INIT phase for all functions. A heavy runtime that initializes for two seconds pays for those two seconds every time traffic grows. 41.2a covers what to do about it.

### 2. Three ways to be invoked, three retry behaviors

How a function is triggered decides who retries, how often, and what happens to failures. This is where most duplicate and lost events come from:

| Invocation | Examples | Who waits | Retries | Where failures go |
|---|---|---|---|---|
| **Synchronous** | HTTP through API Gateway or a load balancer, direct invoke | The caller | None by the platform; the caller decides | Back to the caller |
| **Asynchronous** | Storage events, EventBridge, SNS | Nobody | The platform retries (2 retries by default) | An on-failure destination or DLQ, **if configured; otherwise dropped** |
| **Poll-based** | SQS, Kinesis, DynamoDB Streams, Kafka | Nobody | Until success or the source's limit | SQS: its dead-letter queue. Streams: **the shard blocks** until it succeeds, expires or is skipped |

Three rules follow:

- **Every function must tolerate duplicates.** Asynchronous and poll-based delivery are at-least-once, and producers retry too. Dedupe on a stable event ID in the same transaction as the side effect (37.2a covers the inbox pattern).
- **Every asynchronous path needs a failure destination with an alarm.** That was the receipt team's missing-receipts incident.
- **One bad message must not fail its neighbors.** With batches from a queue, report per-message failures so that only the failed ones are retried. Failed messages then come back out of order, so don't rely on ordering within a batch.

### 3. The shape of work that fits

Functions fit work that is **bursty, event-shaped, short and independent**:

- **Webhook intake.** Third parties send events on their schedule, in bursts, and retry if you're slow. The standard pattern is **thin ingress**: verify the signature, enqueue the raw event, return `200`, and do the real work from the queue. The response stays fast, and a synchronous invocation (no retries) becomes a queue-driven one (retries plus a dead-letter queue). If the enqueue fails, return `503` so the provider retries. Never acknowledge an event you didn't store.
- **File processing.** Thumbnails, OCR, imports. Zero cost when idle, huge parallelism at month-end. Watch for **recursive triggers**: a function that writes its output to the bucket that triggers it will run forever. Lambda detects and stops some loops (through SQS, SNS and Lambda itself) after about 16 iterations, but not every path.
- **Scheduled jobs.** A schedule invokes a function once, with no leader election and no idle container. If a run could exceed the time limit, have the scheduled function **fan out** work items to a queue instead of doing them itself.
- **Irregular background work.** Emails, report generation, calls to slow third-party APIs, when volume varies a lot.

### 4. The hard limits

| Limit (Lambda) | Value | Consequence |
|---|---|---|
| Maximum duration | 15 minutes | Longer work needs splitting, a workflow (37.4b) or a container task |
| Memory | 128 MB – 10,240 MB | CPU scales with memory; about 1,769 MB gives one full vCPU |
| Synchronous payload | 6 MB | Large files go through object storage, never through the function |
| `/tmp` | 512 MB – 10 GB | Scratch space only; not shared between environments |

### 5. Cost, and where it crosses over

```
monthly cost = requests × $0.20 per million
             + invocations × duration (s) × memory (GB) × price per GB-second
  price per GB-second: about $0.0000167 on x86, about 20% less on arm64
  free every month: 1M requests + 400,000 GB-seconds
  plus: API Gateway for HTTP (HTTP APIs about $1.00 per million requests)
```

The receipt team's two workloads, side by side (us-east-1 prices, x86, before the free tier):

| Workload | Shape | Monthly cost as functions |
|---|---|---|
| OCR | 900,000 receipts, 2 GB, 3 s each | 5.4M GB-s ≈ **$90** |
| Web API | 150 req/s by day, 40 by night ≈ 250M requests, 1 GB, 120 ms | 30M GB-s ≈ $500 + $50 requests + **$250 API Gateway** ≈ **$800** |

The API's containers had cost about $260. At steady load, paying per request is paying a premium for elasticity you aren't using. The same arithmetic in picture form:

```
cost
 │                                         functions (linear in traffic)
 │                                    ╱
 │                               ╱
 │ ─────────────────────────╳──────────── always-on containers (flat, then steps)
 │                     ╱   break-even
 │                ╱
 │           ╱
 │      ╱
 └────────────────────────────────────────► steady traffic
```

The rule of thumb: **if the always-on alternative would sit mostly idle, functions win. If it would be busy most hours of the day, containers win. In between, calculate.** And budget for the costs the formula hides: the API gateway, logs (a logged payload per request can cost more than the compute), NAT gateways for functions inside a VPC, and cold-start INIT time. 41.4b covers controlling them.

### 6. Tenants in an event-driven world

Multi-tenant request handling usually resolves the tenant in middleware from the request (Module 5). Functions triggered by events have no request, so:

- **The tenant travels in the event.** Every event that crosses a boundary carries a tenant ID, and for third-party events (a payment provider's webhook) you resolve it from metadata you set when you created the object. Fail loudly if it's missing; that message belongs in the dead-letter queue, not in some default tenant.
- **Isolation is enforced by data access, not trust.** Row-level security or tenant-scoped credentials (41.3c) protect tenant B from a bug processing tenant A's event.
- **Noisy tenants are stopped with concurrency limits.** One tenant bulk-uploading 50,000 receipts can use the whole account's concurrency and starve the login function. Reserve concurrency for critical functions, and cap how many consumers a queue can start.

## When It's Appropriate

- **Spiky, event-driven work with idle periods:** file processing, webhooks, notification fan-out, imports.
- **Low-volume endpoints and internal tools** that would otherwise need a container running all day for a few hundred requests.
- **Scheduled jobs** that run for minutes a day.
- **Development, staging and preview environments**, where scale to zero cuts most of the cost.
- **Glue between managed services**: react to an upload, transform a message, call an API.
- **Small teams** that would rather configure retries than patch servers, for workloads with the right shape.

## When It's Unnecessary or Overkill

- **Steady, high-throughput APIs.** The receipt team's API. Containers are cheaper and have no cold starts.
- **Long-running work:** exports, video transcoding, large ETL jobs, anything near 15 minutes.
- **Persistent connections:** WebSocket servers, gRPC streams. Functions are request-scoped.
- **Chatty relational access at high concurrency**, unless you add a proxy (41.3a).
- **Latency-critical paths on heavy runtimes**, unless you pay to keep environments warm (41.2a).
- **Moving a working system for the sake of it.** If the containers are cheap and the team knows them, "serverless" alone is not a reason.

## Trade-offs

- **Configuration becomes the system.** Retries, dead letters, timeouts, concurrency caps and permissions live in infrastructure definitions, and most failures come from getting them wrong.
- **Lock-in sits in the wiring, not the code.** A handler is easy to move. Event formats, triggers, IAM policies and failure destinations are specific to one cloud. Keeping business logic in plain modules that know nothing about the platform keeps the handler a thin adapter, and makes moving mostly an infrastructure job.
- **Cold starts** add latency when traffic grows or after deploys, exactly when load is highest.
- **Per-request pricing penalizes steady load**, and the gateway and logs add per-request costs on top.
- **Local development is harder.** Much of the behavior (triggers, retries, permissions) exists only in the cloud.
- **Observability is fragmented.** One user action can cross several functions and queues. Correlation IDs and tracing stop being optional (41.4a).
- **Every environment is its own client.** Databases and rate-limited APIs see hundreds of callers instead of a few pooled ones.

## Alternatives

- **Containers with autoscaling** (ECS, Kubernetes, Cloud Run services with minimum instances): steady cost, no cold starts, any runtime and duration, but you pay for idle capacity and manage more.
- **Serverless containers** (Fargate, Cloud Run): no servers, but longer-running processes and your own HTTP server. A middle ground for APIs that still want to scale down.
- **Worker pools on a queue** (Module 10): the classic answer for background work. Cheaper than functions at steady volume, more to operate when volume is spiky.
- **Lambda Managed Instances:** functions running on EC2 capacity in your account, with many requests per environment and EC2 pricing. For steady function workloads you don't want to move to containers (41.4a).

## How to Achieve It

**Step 1: move one bursty, independent workload.** File processing or a scheduled job. Give it a dead-letter queue, an alarm and a concurrency cap from the first deploy. _Signal to move on:_ it runs cheaply and you trust the failure path.

**Step 2: put webhooks behind thin ingress.** Verify, enqueue, acknowledge; process from the queue with per-message failure reporting and dedupe. _Signal:_ third-party bursts no longer affect the core API.

**Step 3: write down the boundary.** For each component, record its traffic shape, duration, state, latency needs and database access, and decide where it runs (41.4a turns this into a test). _Signal:_ more workloads are candidates, and the bill needs watching.

**Step 4: measure cost per function and per tenant**, and review it monthly (41.4b). Move functions back to containers when their traffic becomes steady.

## Implementation

TypeScript, in two pieces: the thin-ingress handler with its queue consumer, and a small cost model for deciding placement.

```ts
import { createHmac, timingSafeEqual } from "node:crypto";
import { SQSClient, SendMessageCommand } from "@aws-sdk/client-sqs";
import type { APIGatewayProxyEventV2, SQSEvent, SQSBatchResponse } from "aws-lambda";

// INIT: runs once per environment, not per request.
const sqs = new SQSClient({});
const QUEUE_URL = process.env.QUEUE_URL!;
const SECRET = process.env.WEBHOOK_SECRET!; // in production, fetched from a secrets store here

export async function ingress(event: APIGatewayProxyEventV2) {
  const raw = Buffer.from(event.body ?? "", event.isBase64Encoded ? "base64" : "utf8");
  if (!validSignature(raw, event.headers["x-signature"])) return { statusCode: 400 };

  const { id } = JSON.parse(raw.toString("utf8")) as { id?: string };
  if (!id) return { statusCode: 400 };

  try {
    await sqs.send(new SendMessageCommand({ QueueUrl: QUEUE_URL, MessageBody: raw.toString("utf8") }));
  } catch {
    return { statusCode: 503 }; // never acknowledge an event you didn't store
  }
  return { statusCode: 200 };
}

function validSignature(body: Buffer, header?: string): boolean {
  if (!header) return false;
  const expected = createHmac("sha256", SECRET).update(body).digest();
  const given = Buffer.from(header, "hex");
  return given.length === expected.length && timingSafeEqual(given, expected);
}
```

> **Aside: why the ingress never touches the database.** If it did, a database outage would make the provider's retries pile up against your API, and a slow query would turn into provider timeouts and duplicate deliveries. With only a queue behind it, the ingress stays fast when everything behind it is slow.

The consumer processes a batch and reports which messages failed, so only those are retried:

```ts
// processEvent is plain business code: it dedupes on the event ID and applies
// the change in one transaction (37.2a), and knows nothing about Lambda.
declare function processEvent(event: { id: string; tenantId?: string }): Promise<void>;

export async function consumer(event: SQSEvent): Promise<SQSBatchResponse> {
  const batchItemFailures: { itemIdentifier: string }[] = [];
  for (const record of event.Records) {
    try {
      await processEvent(JSON.parse(record.body));
    } catch (err) {
      console.log(JSON.stringify({ level: "error", messageId: record.messageId, error: String(err) }));
      batchItemFailures.push({ itemIdentifier: record.messageId });
    }
  }
  return { batchItemFailures }; // requires ReportBatchItemFailures on the event source mapping
}
```

> **Aside: the configuration is part of the code.** This handler is only correct together with its settings: per-item failure reporting enabled, a visibility timeout of at least six times the function timeout, a dead-letter queue after a few receives, an alarm on that queue, and a maximum concurrency that protects whatever `processEvent` calls. Put them in the same pull request as the handler.

The cost model is short, and running it before moving a workload settles most placement arguments:

```ts
type Workload = { requestsPerMonth: number; avgSeconds: number; memoryGb: number; viaHttpApi: boolean };

const PER_GB_SECOND = { x86: 0.0000166667, arm64: 0.0000133334 };

export function functionCostPerMonth(w: Workload, arch: keyof typeof PER_GB_SECOND = "arm64") {
  const compute = w.requestsPerMonth * w.avgSeconds * w.memoryGb * PER_GB_SECOND[arch];
  const requests = (w.requestsPerMonth / 1e6) * 0.2;
  const gateway = w.viaHttpApi ? (w.requestsPerMonth / 1e6) * 1.0 : 0;
  return { compute, requests, gateway, total: compute + requests + gateway };
}

// The receipt team's API: ≈ $400 compute + $50 requests + $250 gateway on arm64,
// against ≈ $260 of containers that already had headroom.
functionCostPerMonth({ requestsPerMonth: 250e6, avgSeconds: 0.12, memoryGb: 1, viaHttpApi: true });
```

> **Aside: what the model leaves out.** It ignores the free tier, logs, NAT and cold-start INIT time, all of which make functions look worse. It also ignores the containers' idle capacity and operations work, which make them look worse. It's a first cut to find which side of break-even you're on, not a forecast.

The habit to take from this: before moving a workload, describe its shape (how bursty, how long, how stateful, who waits, how it touches the database). The compute model should follow from that description, not from whichever model the team adopted last.
