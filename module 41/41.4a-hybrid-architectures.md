# Hybrid Architectures: Containers and Functions in One System

_Module 41 · Serverless Patterns · 41.4a_

## The Problem

Suppose you run a contract-review product for legal teams. Customers upload contracts; the product extracts clauses, flags risky terms and lets lawyers comment and approve. The core API is a TypeScript service on containers (ECS on Fargate) with Postgres. Over a year, the team adds functions around it, one at a time, each for a good reason: OCR on upload, clause extraction, email notifications, a search indexer, a webhook receiver for the e-signature provider, and a nightly usage report.

Each function works. The **system** develops problems that none of them has on its own.

**Two definitions of "authenticated."** The API validates access tokens with a shared library that checks issuer, audience and expiry. The comment-notification function, reached through its own endpoint for a mobile client, was written later with a quick JWT decode that checked the signature and expiry but not the audience. Tokens issued for the company's separate analytics product, signed by the same identity provider, are accepted. A security review finds it.

**Events that vanish around deploys.** The API updates Postgres and then publishes an event to EventBridge for the notification and search functions. When a container is stopped mid-request during a deploy, the database write sometimes lands and the publish doesn't. A few dozen approvals a month never send their notification. Nobody notices until a customer asks why they weren't told.

**One slow consumer stops the others.** All the functions were subscribed to events by EventBridge invoking them directly. When the search cluster slows down, the indexer's invocations fail. After two retries, the events are dropped, because no failure destination was configured. Separately, an early design had put notifications and indexing on one shared queue, so a backlog of index jobs delayed emails by hours.

**The database incident gets worse, not better.** When Postgres has a bad hour, every function that reads from it fails, retries, fails again and fills its dead-letter queue. When the database recovers, thousands of redriven messages arrive at once, and it falls over a second time.

**Nobody can follow one contract.** "Why didn't this contract's flags appear?" means searching six log groups by timestamp, because nothing links the upload request to the OCR, extraction and indexing that followed.

**The indexer should have been a container.** As usage grew, the search indexer became busy around the clock. It's now the most expensive function, costing about three times what a small container would.

The containers were fine and the functions were fine. The problems were all at the **seams**: routing and identity, events leaving the core, failure between components, visibility across them, and the decision about which side each piece belongs on.

## What It Is

A **hybrid architecture** runs a system's steady, stateful, latency-sensitive core on long-running containers, and its bursty, event-shaped edges on functions, with explicit designs for the seams between them.

Most real SaaS systems end up here: very few are "all functions" or "no functions." Deciding **which** components go where and designing the connections are the subject of this article. What makes functions work (41.1a–41.3c) and the patterns used at the seams (the outbox in 37.2a, sagas in 37.4a, workflow engines in 37.4b) are covered elsewhere and linked, not repeated.

## Recognizing the Problem

- Functions were added one at a time, and nobody has drawn the whole system.
- Authentication or tenant resolution is implemented separately in containers and in functions.
- Events are published after a database commit, as a separate step.
- Functions are invoked directly by an event bus, without a queue in between.
- Several consumers share one queue or one dead-letter queue.
- During a database incident, function retries make recovery harder.
- Tracing a user action across containers and functions is done by timestamp.
- A function's traffic has become steady, and nobody has re-checked its placement.

## How It Works

### 1. Deciding placement: five questions about shape

For each component, answer five questions:

| Question | Points to functions | Points to containers |
|---|---|---|
| **Traffic** | Bursty, irregular, often idle | Steady, busy most hours |
| **Duration** | Seconds to a few minutes | Long jobs, or always-on processes |
| **State** | Stateless per request | Long-lived connections, in-memory state |
| **Latency** | Background, or tolerant of cold starts | Strict p99 on user-facing paths |
| **Database access** | Light, through a proxy, or key-value | Heavy and chatty relational access |

Four or five answers on one side decide it. When the answers are mixed, put the component where the rest of its domain already lives, and revisit with real traffic data. For the contract-review product:

| Component | Placement |
|---|---|
| Core API, WebSocket updates for live comments | Containers |
| OCR, clause extraction, webhook intake, notifications | Functions |
| Nightly usage report | A scheduled function that fans out to a queue |
| Search indexer | Started as a function; now a container (steady load) |
| Contract approval workflow (multi-day waits) | A workflow engine (section 5) |

**Placement isn't permanent.** Move a function back to a container when its traffic becomes steady (check the break-even from 41.1a every quarter), when it needs a connection pool no proxy can reasonably serve (41.3a), or when it has grown into a router serving a whole API. If handlers are thin adapters over plain business code, moving is mostly an infrastructure change.

### 2. The reference shape

```
                             ┌─────────────┐
   browser, mobile ─────────►│  CDN / edge │  one entry point, routes by path
                             └──────┬──────┘
               /api/*  ┌────────────┴───────────┐  /webhooks/*
                       ▼                        ▼
             ┌──────────────────┐     ┌──────────────────┐
             │ CORE API         │     │ webhook intake λ  │─► queue ─► consumer λ
             │ (containers)     │     └──────────────────┘
             │ business write + │
             │ outbox row, one  │──── pooled connections ────► Postgres ◄── functions via proxy (41.3a)
             │ transaction      │
             └───────┬──────────┘
                     │ outbox relay (37.2a)
                     ▼
             ┌────────────────┐  rule per consumer   ┌─────────────────┐
             │   event bus    │────────────────────►│ queue + DLQ      │──► notifications λ
             │                │────────────────────►│ queue + DLQ      │──► extraction λ
             │                │────────────────────►│ queue + DLQ      │──► indexer (container)
             └────────────────┘                      └─────────────────┘
```

Three rules make it work:

1. **One entry point and one identity model.** Route by path at the edge (CDN behaviors, a load balancer rule with a function target, or an API gateway), so clients never know what runs where. Validate tokens once at the edge or with one shared library everywhere, and resolve the tenant the same way on both sides (Module 5). Webhooks are the exception: they authenticate with signatures (41.1a), on their own path.
2. **Events leave the core only through an outbox.** The business change and the event are written in one transaction, and a relay publishes afterwards (37.2a). That removes the deploy-time losses. Delivery is at least once, so every consumer dedupes. Several relay replicas using `SKIP LOCKED` give up per-entity ordering; 37.2a covers when that matters.
3. **Every consumer gets its own queue.** The bus delivers to a queue, and the function reads from the queue. Each consumer then has its own buffer, retry policy, dead-letter queue, concurrency cap and alarm, and a slow consumer only delays itself. A bus invoking functions directly is an asynchronous invocation: two retries and then, without a failure destination, silence (41.1a).

### 3. Failure across the seam

Functions multiply the effect of a shared dependency failing. When the database is down, every consumer that uses it fails, retries (paying for each attempt) and fills its dead-letter queue. Redriving afterwards sends the whole backlog at once.

Two controls help:

- **Pause consumers during an incident.** Disabling a queue's event source mapping stops the function from polling. Messages wait in the queue instead of burning through retries into the dead-letter queue. Re-enable them gradually afterwards, with concurrency caps, so the recovery isn't a second incident. This can be manual (a runbook), or automatic from a database health alarm.
- **Redrive at a controlled rate.** Move messages back from dead-letter queues in batches, not all at once.

### 4. One trace across both worlds

A correlation ID must survive every hop: the API reads it from the request (or creates one) and writes it into the outbox row. The event envelope carries it, and every function adds it to its log context. Then one log query across all log groups returns one action's whole story. For timing, use OpenTelemetry in containers and functions alike. Queues can carry trace context in message attributes, so one trace spans the seam (36.4 covers analysis).

### 5. Workflows that wait

Some processes span days: a contract waits for three approvers, with reminders and an expiry. Building that as functions calling each other through events and a status column works for two steps, and becomes invisible and fragile beyond that. That's the job of a workflow engine: sagas and compensation are 37.4a, and durable execution (Temporal, Step Functions, Lambda durable functions, with their determinism and versioning rules) is 37.4b.

Two points specific to the serverless side:

- **Waiting is free on the managed options.** A Step Functions Standard workflow paused for a week costs nothing while it waits; it's billed per state transition (about $0.025 per 1,000). Lambda durable functions bill compute only while code runs, plus about $8 per million durable operations and a small charge for stored checkpoint data. Neither pays for a container waiting.
- **Execution length and invocation length are different limits.** A durable function's individual invocation still has Lambda's 15-minute cap; the workflow can last up to a year. Step Functions Express workflows are limited to 5 minutes and run at least once, so they're for short, high-volume flows, not approvals.

### 6. Steady load: containers, or functions on your own capacity

When a function's traffic becomes steady, the options are to leave it, move it to a container, or run it on **Lambda Managed Instances**: Lambda functions on EC2 capacity in your account, with many requests per environment, billed at the EC2 price plus a 15% management fee, with no per-duration charge, and no scale to zero (a minimum of three environments).

A steady API at 200 requests a second, 100 ms each, at 1 GB, for comparison:

```
Standard Lambda:   518M requests × 0.1 s × 1 GB  ≈ $864 compute + $104 requests
                   + HTTP API ≈ $500                                        ≈ $1,470/month
Fargate:           ~20 requests in flight → 4 tasks (1 vCPU, 2 GB) for headroom and AZs
                   4 × ($0.04048 + 2 × $0.004445) × 730 h ≈ $144 + load balancer ≈ $170/month
```

At that shape, containers cost about a tenth. Managed Instances make sense for steady function workloads you want to keep on Lambda's triggers and deployment model, mainly with a Savings Plan commitment. One published comparison found that without a commitment, standard Lambda was cheaper at every volume it tested. Moving to Managed Instances also means moving to concurrency per instance, with all of 41.2a's rules about shared state.

## When It's Appropriate

- **A steady core plus bursty edges:** file processing, webhooks, notifications, scheduled jobs around an API with regular traffic.
- **A system already on containers** that wants cheaper, more elastic handling of its event-driven work.
- **A system already on functions** whose core has become steady, latency-sensitive or connection-heavy.
- **Teams large enough to own both models**, or small teams where the functions are few and simple.

## When It's Unnecessary or Overkill

- **Small products with modest, steady traffic.** A single container with a background worker is simpler than two compute models.
- **Everything bursty and event-shaped.** Then an all-function design may be right, with a small container only if something needs it.
- **Splitting a component across both worlds for its own sake.** A function that only calls the API, which only calls the database, adds a seam without removing any cost.
- **A workflow engine for a two-step reaction.** An event and a queue are enough.

## Trade-offs

- **Two deployment models, two sets of tooling, two mental models.** Engineers need to understand concurrency, retries and limits on both sides.
- **Local development is harder.** Running containers, functions, a bus and queues together on a laptop needs emulators or a personal cloud stack, and neither is identical to production.
- **More moving parts at the seams:** outbox relays, buses, queues per consumer, dead-letter queues, alarms. Each is simple; together they're a lot to operate.
- **At-least-once delivery everywhere.** Every consumer needs dedupe, and ordering has to be designed for explicitly.
- **Failure can amplify across the seam**, unless consumers can be paused and redrives throttled.
- **Cost is spread across many line items**, which makes it harder to see and to attribute (41.4b).

## Alternatives

- **All containers**, with worker pools for background work (Module 10). One model, predictable cost; pays for idle capacity in bursty work.
- **All functions**, with the core as functions behind an API gateway. Minimal operations for spiky products; expensive and cold-start-prone for steady, latency-sensitive cores.
- **Serverless containers throughout** (Cloud Run, Fargate with aggressive autoscaling), which get some of the elasticity of functions with the programming model of containers.
- **A platform that hides the choice** (a PaaS such as Render, Railway or Heroku-style services), trading control for simplicity.

## How to Achieve It

**Step 1: draw the system and apply the placement test** to every component, with its traffic data. _Signal to move on:_ you know what should move and what should move back.

**Step 2: fix the seams in order of risk:** one identity check at the edge or in one shared library, the outbox for every event that leaves the core, and a queue with a dead-letter queue and an alarm for every consumer. _Signal:_ events stop disappearing, but incidents still cascade.

**Step 3: add the incident controls**, a way to pause consumers and to throttle redrives, and propagate a correlation ID through every hop. _Signal:_ long processes are still built as event chains with status columns.

**Step 4: move multi-day processes to a workflow engine** (37.4b), and review placement quarterly against cost (41.4b).

## Implementation

TypeScript, in two pieces: a consumer that reads the event envelope the outbox relay publishes, carrying tenant and correlation ID, and a switch that pauses consumers during an incident.

```ts
import type { SQSEvent, SQSBatchResponse } from "aws-lambda";

// The envelope the outbox relay publishes in EventBridge's `detail` (37.2a).
type Envelope<T> = { eventId: string; tenantId: string; correlationId: string; data: T };
type BusEvent<T> = { "detail-type": string; detail: Envelope<T> };

declare function alreadyProcessed(consumer: string, eventId: string): Promise<boolean>;
declare function notify(tenantId: string, type: string, data: unknown): Promise<void>;

export async function notifications(event: SQSEvent): Promise<SQSBatchResponse> {
  const batchItemFailures: { itemIdentifier: string }[] = [];
  for (const record of event.Records) {
    const bus = JSON.parse(record.body) as BusEvent<unknown>; // the queue body is the whole bus event
    const { eventId, tenantId, correlationId, data } = bus.detail;
    const log = (msg: string, extra = {}) =>
      console.log(JSON.stringify({ msg, eventId, tenantId, correlationId, ...extra }));
    try {
      if (await alreadyProcessed("notifications", eventId)) continue; // at-least-once delivery
      await notify(tenantId, bus["detail-type"], data);
      log("notified");
    } catch (err) {
      log("failed", { error: String(err) });
      batchItemFailures.push({ itemIdentifier: record.messageId });
    }
  }
  return { batchItemFailures };
}
```

> **Aside: why the tenant comes from the envelope, not the data.** The relay copies `tenantId` from the outbox row, which the core API wrote from its own verified context. A consumer that read the tenant from the business payload would trust whatever shape that payload happens to have, and payload shapes change more often than envelopes do.

The pause switch disables every consumer that depends on a failing dependency, and re-enables them later with a lower concurrency cap:

```ts
import {
  LambdaClient, ListEventSourceMappingsCommand, UpdateEventSourceMappingCommand,
} from "@aws-sdk/client-lambda";

const lambda = new LambdaClient({});

// Which consumers stop when a dependency fails. Kept in code, reviewed like code.
const DEPENDS_ON: Record<string, string[]> = {
  postgres: ["notifications", "clause-extraction", "usage-report-worker"],
  search: ["search-indexer"],
};

export async function setConsumers(dependency: string, enabled: boolean, recoveryConcurrency = 2) {
  for (const fn of DEPENDS_ON[dependency] ?? []) {
    const { EventSourceMappings = [] } = await lambda.send(new ListEventSourceMappingsCommand({ FunctionName: fn }));
    for (const m of EventSourceMappings) {
      await lambda.send(new UpdateEventSourceMappingCommand({
        UUID: m.UUID!,
        Enabled: enabled,
        // Come back slowly: the backlog is waiting, and the dependency just recovered.
        ...(enabled ? { ScalingConfig: { MaximumConcurrency: recoveryConcurrency } } : {}),
      }));
    }
  }
}
```

> **Aside: the queue must outlast the incident.** Pausing only helps if messages survive the pause. A queue's retention period (up to 14 days on SQS) must be longer than your worst incident, and the visibility timeout doesn't matter while nothing is polling. Raise concurrency back to normal in steps once the backlog drains without errors.

---

The habit to take from this: when you add a function next to a running system, draw the arrows before writing the handler. For each one, ask how it authenticates, what happens when it fails, where its failures go, and how you'd see one request cross it. The handler is usually the easy part.
