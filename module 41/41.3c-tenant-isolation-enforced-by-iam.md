# Tenant Isolation the Cloud Enforces: Tenant-First Keys and Tenant-Scoped Credentials

_Module 41 · Serverless Patterns · 41.3c_

## The Problem

Suppose you run a developer platform that sells an API: geocoding, billed per call. Customers are tenants; each one has API keys, and every call is metered. Metering runs on functions: the API gateway emits a usage event per call to a queue, and a consumer function adds it to the tenant's monthly counter in DynamoDB. Invoices are generated from those counters. About 40 million events a month.

The table is well designed. Every item's partition key starts with the tenant (`TENANT#t_8f3a`), so one query fetches a tenant's usage and nothing crosses tenants by accident. Or so the team believed.

**A variable reused across a batch.** A refactor of the consumer moves the tenant lookup out of the per-message loop "for performance." It now reads the tenant from the **first** message in each batch of ten and uses it for all ten. For three days, whenever a batch mixes tenants, usage is added to the wrong customer's counter. Two customers are overbilled, and one large customer is underbilled by about $11,000. Every write passed code review, and every write was a perfectly valid DynamoDB request.

**A support tool that could read everything.** An internal "usage lookup" Lambda for the support team takes a tenant ID and returns that tenant's usage. Its IAM role allows `dynamodb:Query` and `dynamodb:Scan` on the whole table. A missing parameter check means that calling it without a tenant ID falls through to a `Scan`, which returns every customer's usage. It's found during a penetration test, not in production, this time.

**Isolation that was only a convention.** The post-incident review asks: what, besides the code being correct, stops a function processing tenant A's event from writing tenant B's data? The answer is nothing. Tenant-first keys make it **easy** to stay within a tenant. They don't make it **impossible** to leave one.

## What It Is

**Cloud-enforced tenant isolation** means the platform, not your application code, refuses any request that touches another tenant's data. For AWS's key-value store DynamoDB, the mechanism combines three pieces:

- **Tenant-first keys:** every item's partition key starts with the tenant ID, so each tenant's data lives under partition key values the platform can check.
- **The `dynamodb:LeadingKeys` condition:** an IAM policy can restrict which partition key values a principal may read or write.
- **Session tags:** when a function assumes a role, it attaches a tag (`tenant_id = t_8f3a`), and the policy refers to that tag. The resulting temporary credentials can only touch that tenant's partition keys.

The function's own role has **no** access to the table. To process tenant A's event, it obtains credentials for tenant A. A bug that then addresses tenant B gets `AccessDeniedException`.

This is the key-value counterpart of **row-level security** in PostgreSQL (5.2a), where the database checks every row against a tenant setting. The idea is the same (enforcement below the application), with a different enforcement point: the database engine for RLS, IAM for DynamoDB.

## Recognizing the Problem

- Tenant isolation depends on every query including the right key, and nothing checks it except review.
- Function or service roles have read and write access to entire multi-tenant tables.
- Internal tools can `Scan` multi-tenant tables.
- A batch or loop processes several tenants' records with shared variables.
- Audit or compliance questions ("prove tenant A's data can't be read by code handling tenant B") are answered with a description of your code.
- Enterprise customers ask about isolation, and the honest answer is "our code is careful."

## How It Works

### 1. Keys first

```
Table: usage (on-demand)

PK                SK                              attributes
────────────────  ──────────────────────────────  ─────────────────────────────
TENANT#t_8f3a     USAGE#2026-09#geocode           quantity=184223
TENANT#t_8f3a     EVENT#01J9ZK…                   quantity=1, expiresAt=…   ← idempotency marker
TENANT#t_19b4     USAGE#2026-09#geocode           quantity=2210
```

One `Query` on `PK = TENANT#t_8f3a` returns everything a tenant has, and the sort key encodes what and when, so `begins_with(SK, 'USAGE#2026-09')` returns one month. This is the **pooled** end of Module 5's spectrum: every tenant in one table. A table per tenant (**siloed**) is possible, but thousands of tables are hard to manage and each has its own limits. Reserve it for a few very large or regulated tenants.

### 2. Credentials that can only reach one tenant

```
usage event (tenant t_8f3a)
      │
      ▼
consumer function (its own role: NO table access)
      │  sts:AssumeRole on TenantUsageRole, with session tag tenant_id = t_8f3a
      ▼
temporary credentials, valid 15 minutes
      │  policy: allowed only if partition key = "TENANT#${aws:PrincipalTag/tenant_id}"
      ▼
DynamoDB
  PutItem  PK = TENANT#t_8f3a   → allowed
  PutItem  PK = TENANT#t_19b4   → AccessDeniedException   (the batch bug, stopped)
  Scan                          → AccessDeniedException   (not granted)
```

The role's permission policy:

```json
{
  "Effect": "Allow",
  "Action": ["dynamodb:GetItem", "dynamodb:PutItem", "dynamodb:UpdateItem",
             "dynamodb:ConditionCheckItem", "dynamodb:Query"],
  "Resource": "arn:aws:dynamodb:us-east-1:111122223333:table/usage",
  "Condition": {
    "ForAllValues:StringEquals": {
      "dynamodb:LeadingKeys": ["TENANT#${aws:PrincipalTag/tenant_id}"]
    }
  }
}
```

The role's trust policy must allow both `sts:AssumeRole` and `sts:TagSession` for the function's role.

### 3. The trap: conditions that pass when there's nothing to check

`ForAllValues` means "every value in the request must match." When a request has **no** partition key values at all, there's nothing that fails to match, so the condition is **true**. A `Scan` has no partition key. So if the policy allowed `Scan`, every tenant's credentials could read every tenant's data. The same caution applies to any action whose partition keys might not be evaluated the way you expect: batch and transactional writes, and queries on secondary indexes. Allow only the actions you've tested with a cross-tenant request, and never allow `Scan` to a tenant-scoped role.

That's also the fix for the support tool. It gets tenant-scoped credentials for the tenant being looked up, and no `Scan` permission anywhere. Cross-tenant reporting uses a separate export to an analytics store (Module 16), under a separate, audited role.

### 4. Idempotent counting

Delivery from a queue is at-least-once (41.1a), and `ADD` on a counter isn't idempotent: a redelivered event would count twice. The fix is to write a **marker** for the event ID and the counter update in **one transaction**. The marker's condition (`attribute_not_exists`) fails on a duplicate, which cancels the whole transaction. The marker carries a time-to-live, so DynamoDB deletes it after a retention period longer than any redelivery window.

A transactional write costs twice a normal one, and this transaction writes two items, so each event costs about four write units. At 40 million events a month, that's 160 million write units, about $100 a month on demand. If that's too much, aggregate in the producer, for example one event per tenant per minute carrying a quantity.

### 5. Hot tenants

Each partition key value has a throughput limit, about 1,000 write units a second. One very large tenant writing usage can exceed it and be throttled while everyone else is fine. For those tenants only, **shard the key**: write to `TENANT#t_8f3a#3` (a shard from 0 to 9) and read all ten shards to add up the total. The IAM condition then uses `StringLike` with `TENANT#${aws:PrincipalTag/tenant_id}#*`. Reads become ten times the work, so don't do it by default.

### 6. What it costs to get credentials

Assuming a role is an STS API call: a few tens of milliseconds, and subject to STS request quotas. Doing it for every event would add latency and could hit those quotas during bursts. Cache credentials **per tenant** in the function's environment until shortly before they expire. The cache must be keyed by tenant, so that tenant A's credentials can never be used for tenant B's event. That's the entire point.

## When It's Appropriate

- **Multi-tenant data in DynamoDB** where a cross-tenant write or read would be a billing error, a data leak or a compliance failure.
- **Enterprise or regulated customers** who ask how isolation is enforced, and need an answer that isn't "our code is careful."
- **Functions that process events from many tenants** in batches, where a shared variable is one refactor away.
- **Internal tools with broad access**, which are often the weakest point.

## When It's Unnecessary or Overkill

- **Single-tenant tables or data that isn't tenant-specific** (reference data, global configuration).
- **Very small products** where one table has a handful of tenants and a single service touches it. Tenant-first keys plus tests may be proportionate.
- **Siloed tenants with their own tables or accounts.** The boundary is already the resource.
- **Paths where role assumption latency matters more than the risk,** such as a hot synchronous read. Consider a per-tenant credential cache warmed in advance, or a different mechanism, rather than dropping enforcement entirely.

## Trade-offs

- **Every tenant switch needs credentials.** An STS call per tenant per environment, cached for up to the credentials' lifetime, adds latency and a dependency on STS.
- **Policies become part of your correctness.** A well-meant "simplification" (adding `Scan`, widening the condition) silently removes the protection. It needs a test that tries to break it, in CI.
- **Cross-tenant operations need a separate path.** Reporting, migrations and support tools can't use tenant-scoped roles, and that separate path must be narrow and audited.
- **The model constrains the key design.** Every item and every index needs a tenant-first partition key, and access patterns that don't start from a tenant don't fit.
- **Transactions for idempotency double write costs**, and sharding hot tenants multiplies read costs.
- **It protects data access, not logic.** Credentials for the right tenant don't stop a function from computing the wrong quantity. Enforcement narrows what a bug can damage; it doesn't remove bugs.

## Alternatives

- **Application-level enforcement:** a repository layer that requires a tenant and builds every key from it. Cheap and effective, but it's still code, and still bypassable by code that goes around it.
- **Table per tenant, or AWS account per tenant:** the strongest boundary, at the cost of managing thousands of resources, and of per-resource limits. Common for a few large enterprise tenants in an otherwise pooled design.
- **A relational database with row-level security** (5.2a), when the data is relational anyway.
- **A data-access service** that owns the table, and through which every other service goes. It centralizes enforcement, and becomes a bottleneck and a single point of failure.

## How to Achieve It

**Step 1: tenant-first keys everywhere**, including secondary indexes, and a repository that requires a tenant. _Signal to move on:_ tenant isolation is still enforced only by code review.

**Step 2: create the tenant-scoped role**, without `Scan`, and a test that tries a cross-tenant write, a cross-tenant read and a `Scan`, and requires all three to fail. _Signal:_ the test passes and runs in CI.

**Step 3: remove table access from function roles**, one function at a time, so each can only reach data through tenant-scoped credentials. Start with the functions that process batches from many tenants. _Signal:_ internal tools still have broad access.

**Step 4: move cross-tenant needs to a separate, audited path**: exports for reporting, and per-tenant lookups for support.

## Implementation

TypeScript, in two pieces: a per-tenant credentials cache with idempotent recording, and the test that keeps the policy honest.

```ts
import { STSClient, AssumeRoleCommand } from "@aws-sdk/client-sts";
import { DynamoDBClient } from "@aws-sdk/client-dynamodb";
import { DynamoDBDocumentClient, TransactWriteCommand } from "@aws-sdk/lib-dynamodb";

const sts = new STSClient({});
const TABLE = process.env.USAGE_TABLE!;
const TENANT_ROLE_ARN = process.env.TENANT_ROLE_ARN!;
const TENANT_ID = /^t_[a-z0-9]{4,32}$/; // validated before it goes into a tag or a key

// Keyed by tenant: credentials for one tenant are never used for another.
const clients = new Map<string, { client: DynamoDBDocumentClient; expiresAt: number }>();

export async function tenantClient(tenantId: string): Promise<DynamoDBDocumentClient> {
  if (!TENANT_ID.test(tenantId)) throw new Error(`invalid tenant id: ${tenantId}`);
  const cached = clients.get(tenantId);
  if (cached && cached.expiresAt - Date.now() > 60_000) return cached.client;

  const { Credentials: c } = await sts.send(new AssumeRoleCommand({
    RoleArn: TENANT_ROLE_ARN,
    RoleSessionName: `usage-${tenantId}`.slice(0, 64),
    DurationSeconds: 900,
    Tags: [{ Key: "tenant_id", Value: tenantId }],
  }));
  if (!c?.AccessKeyId || !c.SecretAccessKey || !c.SessionToken || !c.Expiration) throw new Error("no credentials");

  const client = DynamoDBDocumentClient.from(new DynamoDBClient({
    credentials: { accessKeyId: c.AccessKeyId, secretAccessKey: c.SecretAccessKey,
                   sessionToken: c.SessionToken, expiration: c.Expiration },
  }));
  if (clients.size >= 500) clients.delete(clients.keys().next().value!); // bound memory
  clients.set(tenantId, { client, expiresAt: c.Expiration.getTime() });
  return client;
}

export async function recordUsage(e: { eventId: string; tenantId: string; metric: string; quantity: number; month: string }) {
  const ddb = await tenantClient(e.tenantId); // per event, never per batch
  const pk = `TENANT#${e.tenantId}`;
  try {
    await ddb.send(new TransactWriteCommand({
      TransactItems: [
        { Put: { TableName: TABLE, ConditionExpression: "attribute_not_exists(SK)",
                 Item: { PK: pk, SK: `EVENT#${e.eventId}`, expiresAt: Math.floor(Date.now() / 1000) + 35 * 86400 } } },
        { Update: { TableName: TABLE, Key: { PK: pk, SK: `USAGE#${e.month}#${e.metric}` },
                    UpdateExpression: "ADD #q :q", ExpressionAttributeNames: { "#q": "quantity" },
                    ExpressionAttributeValues: { ":q": e.quantity } } },
      ],
    }));
    return "recorded";
  } catch (err) {
    const reasons = (err as { CancellationReasons?: { Code?: string }[] }).CancellationReasons;
    if (reasons?.[0]?.Code === "ConditionalCheckFailed") return "duplicate";
    throw err;
  }
}
```

> **Aside: the batch bug, revisited.** `tenantClient` is called inside `recordUsage`, once per event. If someone moves it out of the loop again, every event in a mixed batch after the first fails with `AccessDeniedException` and lands in the dead-letter queue. That's loud, immediate and harmless, instead of three days of wrong invoices.

> **Aside: the marker's time-to-live.** It must be longer than the longest time a duplicate could arrive: the queue's retention plus any replay from a dead-letter queue. Thirty-five days covers a queue with 14-day retention and a redrive a few weeks later. Shorter, and a late replay counts twice.

The test is the part that keeps the protection in place after the next "cleanup" of IAM policies:

```ts
import { ScanCommand, PutCommand, QueryCommand } from "@aws-sdk/lib-dynamodb";
import { test } from "node:test";
import assert from "node:assert/strict";

test("tenant credentials cannot leave their tenant", async () => {
  const a = await tenantClient("t_aaaa");
  const denied = (p: Promise<unknown>) =>
    assert.rejects(p, (e: Error) => e.name === "AccessDeniedException");

  await denied(a.send(new PutCommand({ TableName: TABLE, Item: { PK: "TENANT#t_bbbb", SK: "X" } })));
  await denied(a.send(new QueryCommand({ TableName: TABLE, KeyConditionExpression: "PK = :p",
                                         ExpressionAttributeValues: { ":p": "TENANT#t_bbbb" } })));
  await denied(a.send(new ScanCommand({ TableName: TABLE })));

  await a.send(new QueryCommand({ TableName: TABLE, KeyConditionExpression: "PK = :p",
                                  ExpressionAttributeValues: { ":p": "TENANT#t_aaaa" } })); // allowed
});
```

---

The habit to take from this: for every place tenant data is stored, ask what would stop a function processing tenant A from touching tenant B **if its code were wrong**. If the answer is "nothing but the code," the isolation is a convention, and conventions last until the next refactor.
