# Cold Starts and Concurrency per Instance: What One Function Environment Holds

_Module 41 · Serverless Patterns · 41.2a_

## The Problem

Suppose you run a timesheet product for staffing agencies. Temporary workers submit hours from their phones; agency coordinators approve them in a web app; approved hours feed payroll every Friday. The approval API is Java with Spring, running as AWS Lambda functions behind an HTTP API. Traffic is lumpy: quiet most of the week, heavy on Thursday afternoons and Friday mornings.

Over two months, the team fixes one problem and meets the next.

**Friday morning is slow.** When coordinators arrive, traffic grows from a trickle to a few hundred requests a second in minutes. Each new environment starts a JVM and a Spring context, which takes 4–6 seconds. The platform adds environments as fast as traffic grows, so for the first half hour a large share of requests hit a cold start. Coordinators see approvals hang and click twice.

**The fix breaks secret rotation.** The team enables SnapStart, which starts new environments from a memory snapshot instead of running initialization again. Cold starts drop to about 400 ms. Three weeks later, security rotates the database password on schedule. Environments restored from the snapshot still hold the old password, taken at snapshot time, and fail to connect until someone deploys a new version. Approvals are down for 50 minutes.

**Two environments share an identity.** The approval service generates an instance ID in a static initializer and uses it as the owner name for a Postgres advisory-lock-style lease on the payroll export. With SnapStart, every environment restored from the same snapshot has the **same** instance ID. Two environments both believe they hold the lease. Friday's export runs twice for one agency.

**A move for cost leaks data.** To cut cost, a teammate ports the least latency-sensitive function to Google Cloud Run functions with concurrency 40: one instance handles 40 requests at once. A helper class caches "the current agency" in a static field, set at the start of each request. That was harmless when an environment served one request at a time. Now two agencies' requests overlap in one instance, and a coordinator sees another agency's pending timesheets on a list page. It's reported by the customer.

The four problems share a cause. Each one comes from not knowing **what an execution environment contains, how many requests share it, and how it came to exist.**

## What It Is

A **cold start** is the time it takes the platform to create a new execution environment and run your initialization before it can serve a request. It happens whenever no idle environment is available: after idle periods, when traffic grows faster than existing environments can absorb, and after every deploy.

**Concurrency per instance** is how many requests one environment serves at the same time. Platforms differ here more than anywhere else:

- **Standard AWS Lambda:** one request per environment. 80 simultaneous requests means 80 environments.
- **Google Cloud Run functions and Azure Functions (Flex Consumption):** many requests per instance, configurable (Cloud Run allows up to 1,000).
- **Lambda Managed Instances:** many requests per environment, on EC2 capacity in your account.

The two ideas are connected. One request per environment means more environments, so more cold starts during growth, more database connections and more memory held. But nothing is shared between concurrent requests. Many requests per instance means fewer cold starts and connections. But every global variable is shared by requests running at the same moment.

## Recognizing the Problem

- User-facing p99 latency spikes when traffic rises and after deploys, not at steady load.
- Logs show `Init Duration` of several seconds on a large share of invocations.
- A heavy framework (Spring, Hibernate, a big dependency tree) starts inside a function.
- Anything created during initialization (secrets, IDs, connections) is assumed to stay valid forever.
- You enabled snapshots or pre-warming and later saw stale credentials, duplicate IDs, or dead connections.
- Static or module-level variables hold request data: the current user, tenant or locale.
- You're moving a function between platforms and haven't checked their concurrency models.
- Provisioned or minimum capacity is turned on everywhere "to be safe," and nobody knows what it costs.

## How It Works

### 1. Where a cold start's time goes

```
request arrives, no idle environment
   │
   ├─ platform: allocate and boot the environment          (tens to hundreds of ms)
   ├─ runtime: start the language runtime                  (JVM: hundreds of ms)
   ├─ your INIT: load classes, build clients, read config,  (often the largest part:
   │             fetch secrets, open connections             framework startup, network calls)
   └─ first INVOKE: first run of your code                  (JIT-cold on the JVM)
```

On Lambda, the `REPORT` log line for a cold start includes `Init Duration`, and since August 2025 that time is **billed**. Environments restored from a snapshot report `Restore Duration` instead. A query over those lines gives you the cold-start percentage and duration per function, which is the only number worth optimizing against.

Before optimizing, ask three questions:

1. **Is someone waiting?** A user-facing API: yes. A queue consumer: no. A 3-second cold start on a background job costs a little money and no user pain.
2. **How often?** A busy function might cold-start on under 1% of requests; one called every 20 minutes starts cold nearly every time. But **bursts and deploys** matter more than the average. The timesheet API's problem was the 9 a.m. ramp, when the share of cold starts was far higher than the monthly figure suggested.
3. **What does it cost?** Cold starts × init time × memory × price, now that INIT is billed.

### 2. Making INIT smaller

The cheapest fixes come first:

- **Load less.** A three-step function doesn't need a dependency-injection container. Plain code, a lighter HTTP client for the AWS SDK, and fewer libraries reduce class loading on the JVM. In Node.js, bundling into one file (esbuild) avoids reading thousands of files from `node_modules`.
- **Give it more memory.** CPU scales with memory on Lambda. A Java function at 1,024 MB often initializes and runs faster than at 512 MB, and can cost the same because it finishes sooner.
- **Move network calls out of the critical path** where you can. Fetching three secrets sequentially in INIT is three round trips on every cold start.
- **Choose the runtime deliberately.** Go and Rust binaries start in tens of milliseconds because there's no VM to boot. Java and .NET start slowest.

### 3. Snapshots: skip INIT by restoring memory

**SnapStart** (Lambda, for Java, Python and .NET) runs INIT once when you publish a version, takes a snapshot of the environment's memory and disk, and restores new environments from it. For Java, it costs nothing extra. For Python and .NET, there are charges for caching and restoring snapshots. It works only on published versions, and can't be combined with provisioned concurrency.

A snapshot copies **everything** in memory at snapshot time into **many** environments, possibly days later. Three things break because of that:

| Trap | What goes wrong | Fix |
|---|---|---|
| **Stale secrets** | A password or signing key fetched during INIT is frozen into the snapshot; after rotation, restored environments keep the old one | Re-fetch after restore; during rotation, accept both old and new for an overlap window |
| **Duplicated uniqueness** | IDs, random seeds or tokens generated during INIT are identical in every restored environment | Generate unique values during invocation or after restore. The JDK's `SecureRandom` and the AWS SDK handle this themselves; your own cached values don't |
| **Dead connections** | A database connection opened before the snapshot may be broken after restore | Don't open connections during INIT, or validate and reopen after restore |

Lambda exposes runtime hooks through the open-source **CRaC** API (Coordinated Restore at Checkpoint): code that runs just before the snapshot and just after each restore. The "before" hook is also where **priming** happens: running your hot code paths once before the snapshot, so the classes are loaded and some code is already compiled when environments are restored.

### 4. Keeping environments warm

When a snapshot isn't enough, the platforms let you pay for capacity that's always initialized:

| Platform | Mechanism | Cost model |
|---|---|---|
| Lambda | **Provisioned concurrency**: N environments kept initialized | Paid per second, whether used or not (about $0.0000042 per GB-second on x86), plus a lower rate for execution |
| Cloud Run | **Minimum instances**, and **startup CPU boost** during initialization | Idle instances billed at a reduced rate |
| Azure Functions (Flex) | **Always-ready instances** per function | Billed while ready |

Five 1 GB environments kept warm on Lambda cost about $54 a month before a single request. That's worth it for a strict latency target with predictable traffic, and wasteful everywhere else. Scheduling it (more during business hours, less at night) usually halves the cost.

**Ahead-of-time compilation** is the other path: a GraalVM native image (through Quarkus, Micronaut or Spring Native) removes the JVM at runtime and starts like a Go binary. The cost is build time, build complexity, and configuration for everything that uses reflection.

### 5. What concurrency per instance changes

The timesheet team's fourth incident is the one that surprises people most. Here's the same burst of 80 requests on two models:

```
One request per environment (Lambda)       Many requests per instance (Cloud Run, concurrency 80)
┌──┐┌──┐┌──┐        ┌──┐                   ┌───────────────────────────────┐
│r1││r2││r3│  ...   │r80│                  │  r1  r2  r3 … r80  (in parallel)│
└──┘└──┘└──┘        └──┘                   └───────────────────────────────┘
80 environments, 80 cold starts            1 instance, 1 cold start
80 connection pools of size 1              1 pool of ~10
globals: touched by one request at a time  globals: touched by 80 requests at once
```

| Concern | One request per environment | Many requests per instance |
|---|---|---|
| Database connections | Pool size 1; total = concurrency (41.3a) | Pool of 5–20; far fewer in total |
| Global and static state | Leaks only to **later** requests in that environment | Shared by requests running **right now**; must be thread-safe and free of request data |
| Cost for I/O-bound work | You pay for every environment while it waits | Waiting requests share one instance's CPU and memory |
| Cold starts in a burst | One per new environment | One per new instance |

So the rule for any code that might run on a concurrent platform: **request data lives in parameters and request-scoped objects, never in static fields or module-level variables.** Caches of shared, immutable data (parsed config, clients) are fine.

### 6. When tenants must not share an environment

Even with one request at a time, Lambda reuses a warm environment for later requests from **any** caller. Memory or `/tmp` left behind by tenant A's request can be read by tenant B's next one if the code is careless. For your own code and tenant-scoped data, careful coding is enough.

When tenants run **their own code** (automation scripts, templates with expressions, user-defined functions), Lambda's **tenant isolation mode** guarantees that an environment is only ever reused for the same tenant. You pass a tenant ID with each invocation. The mode is set when the function is created and can't be changed. It adds a charge for each environment created, and more tenants means more cold starts, since environments can't be shared. Use it where isolation is a requirement, not as a default.

## When It's Appropriate

Optimizing cold starts is worth it when:

- **Users or strict provider timeouts wait on the function**, and cold starts show up in p99 during ramps and deploys.
- **The runtime is heavy** (JVM, .NET) and the function must stay on functions for other reasons.
- **Traffic is predictable enough** that provisioned or minimum capacity can be scheduled rather than left on.

Choosing a concurrent platform is worth it when:

- **Work is I/O-bound**: most time is spent waiting on databases or APIs, which a concurrent instance shares.
- **Connection counts matter** more than per-request isolation.

## When It's Unnecessary or Overkill

- **Background consumers, scheduled jobs and batch work.** Nobody is waiting; accept the cold start.
- **Functions that are already fast to start** (Go, bundled Node.js with few dependencies). Measure before tuning.
- **Provisioned capacity "to be safe"** on every function. It often costs more than the cold starts it removes.
- **Native images for a three-step function.** Removing the framework is simpler than compiling it ahead of time.
- **Tenant isolation mode for your own code** processing tenant-scoped data.

## Trade-offs

- **Snapshots trade startup time for correctness hazards.** Every value computed during INIT is now shared across environments and frozen in time. Code that was correct before SnapStart can become wrong without changing.
- **Warm capacity is paid whether used or not**, and it doesn't help beyond its size: a burst larger than the provisioned count still cold-starts.
- **Native images move cost to the build**: longer builds, reflection configuration, libraries that don't support it, and differences between the JVM you test on and the binary you ship.
- **Concurrency per instance saves connections and money, and gives up isolation between concurrent requests.** Thread-safety bugs and cross-request leaks become possible.
- **More memory speeds up startup and costs more per millisecond.** Whether it's a net saving depends on the function, and only measurement tells.
- **JIT tuning such as `-XX:TieredStopAtLevel=1`** speeds up startup but caps peak performance for the life of the environment.

## Alternatives

- **Accept cold starts** and design around them: keep users out of the path with a queue, or give clients a retry with a short timeout.
- **Move the latency-sensitive part to a container** and keep functions for the bursty work behind it (41.4a).
- **Use a lighter runtime** for the latency-sensitive function: Go or bundled TypeScript.
- **Pre-warming by scheduled pings**, the old trick, keeps only one environment warm per ping and doesn't help with bursts. Provisioned concurrency replaced it.

## How to Achieve It

**Step 1: measure.** Query `Init Duration` and `Restore Duration` per function, by hour, including ramps and deploys. Find the functions where cold starts reach users. _Signal to move on:_ you know which two or three functions matter.

**Step 2: shrink INIT.** Remove the framework where it isn't needed, use lighter clients, raise memory, and remove sequential network calls. Measure again. _Signal:_ still too slow for a user-facing path.

**Step 3: add snapshots, with the hooks.** Enable SnapStart on the function, move secrets and connections to after-restore or first use, generate IDs at invocation, and prime the hot path before the snapshot. Test a secret rotation before relying on it. _Signal:_ p99 still misses the target during ramps.

**Step 4: pay for warm capacity where traffic is predictable**, scheduled to business hours, or move the path to a container.

**Before any move to a concurrent platform:** review every static and module-level variable for request data.

## Implementation

Java, since SnapStart's traps and the CRaC hooks are where snapshot restore becomes visible in code. The handler below refreshes its secret after every restore, generates its instance ID at first use rather than during INIT, and primes the hot path before the snapshot.

```java
import com.amazonaws.services.lambda.runtime.Context;
import com.amazonaws.services.lambda.runtime.RequestHandler;
import org.crac.Core;
import org.crac.Resource;

import java.util.UUID;

public class ApproveTimesheetHandler implements RequestHandler<ApprovalRequest, ApprovalResult>, Resource {

    // Safe to share: built once, immutable, no request data.
    private static final SecretStore SECRETS = SecretStore.fromEnvironment();
    private static final Approvals APPROVALS = Approvals.fromEnvironment();

    // Refreshed after every restore, so a rotated password is picked up (trap 1).
    private static volatile String dbPassword = SECRETS.fetch("db-password");

    // Created lazily per environment, never during INIT (trap 2).
    private static volatile String instanceId;

    public ApproveTimesheetHandler() {
        Core.getGlobalContext().register(this); // the handler is created once, during INIT
    }

    @Override
    public void beforeCheckpoint(org.crac.Context<? extends Resource> ctx) {
        // Priming: run the hot path on dummy data so its classes are loaded and JIT-warm
        // in the snapshot. It must not have side effects.
        for (int i = 0; i < 50; i++) APPROVALS.validate(ApprovalRequest.sample());
        APPROVALS.closeConnections(); // no live sockets inside the snapshot (trap 3)
    }

    @Override
    public void afterRestore(org.crac.Context<? extends Resource> ctx) {
        dbPassword = SECRETS.fetch("db-password");
        instanceId = null; // force a fresh ID in this environment
    }

    @Override
    public ApprovalResult handleRequest(ApprovalRequest request, Context context) {
        if (instanceId == null) instanceId = UUID.randomUUID().toString();
        // Tenant and user come from the request, and stay in local variables.
        return APPROVALS.approve(request.agencyId(), request.timesheetId(), request.approverId(),
                                 dbPassword, instanceId);
    }
}
```

> **Aside: what `afterRestore` costs.** Re-fetching the secret adds one network call to each restore, which is part of the restore time users feel. The alternative is caching it with a short time-to-live and refreshing on first use. What you can't do is trust the copy in the snapshot.

> **Aside: the lease owner.** In the timesheet incident, two environments claimed the same lease because they had the same "unique" ID. Generating it lazily fixes the ID. But a lease that correctness depends on also needs an expiry and a fencing token, because environments can be frozen mid-work and resumed later (10.3a).

The second snippet is the Cloud Run leak, reduced to its essence:

```java
// ❌ Harmless with one request per environment; a data leak with concurrency > 1.
final class AgencyContext {
    private static String currentAgency;               // shared by every request in the instance
    static void set(String agencyId) { currentAgency = agencyId; }
    static String get() { return currentAgency; }
}

// ✅ Request data travels with the request.
record RequestScope(String agencyId, String userId) {}

List<Timesheet> pending(RequestScope scope) {
    return timesheets.pendingFor(scope.agencyId());    // no static state involved
}
```

> **Aside: why `ThreadLocal` isn't the fix.** It works on a thread-per-request server, and breaks with virtual threads reused carelessly, async continuations on other threads, and code that forgets to clear it. Passing the scope explicitly is dull, and it's the version that can't leak. If a framework must hold it, use its request scope and test with concurrent requests from two tenants.

---

The habit to take from this: for every value your function creates during initialization, ask two questions. "Is it still valid when this environment is restored from a snapshot days later?" and "Is it safe when another request is running at the same moment?" Most serverless correctness bugs are a "no" to one of them.
