# Controlling a Serverless Bill: Measuring Cost and the Levers That Move It

_Module 41 · Serverless Patterns · 41.4b_

## The Problem

Suppose you run a photo-proofing product for wedding photographers. Photographers upload a shoot (often 2,000 images), and the product generates watermarked previews, thumbnails and a private gallery for the couple, who pick favorites. It's almost entirely functions and managed services, and for its first year the AWS bill hovers around $900 a month.

Then, in the busiest month of wedding season, the bill is **$6,800**. Uploads grew about 40%. Nothing else changed on purpose. The breakdown, once someone finally looks:

| Line | Last month | This month | Why |
|---|---|---|---|
| CloudWatch Logs | $60 | **$2,300** | A debugging change logged each image's full metadata, including embedded thumbnails, and it was never removed |
| NAT gateway | $110 | **$1,450** | The watermark function was moved into a VPC to reach a database; it downloads originals from S3 through the NAT gateway, paying per GB |
| Lambda compute | $420 | **$1,700** | Memory raised to 3 GB "to be safe" on an I/O-bound function; a poison image retried for hours; a new image library added 1.5 s of billed INIT |
| Lambda compute (wasted) | — | included above | The thumbnail function is triggered by every object written to the bucket, including its own thumbnails, which it then ignores |
| Provisioned concurrency | $0 | **$480** | Turned on in staging for a load test in March and never turned off |
| Everything else | $310 | $870 | Growth |

Every one of these is the kind of thing that happens in a serverless system, because every one is a configuration choice someone made in a moment, billed per use, and invisible until the invoice. Nobody had asked what each function cost, or which photographers generated the most cost.

## What It Is

**Serverless cost control** is the practice of measuring what each function and tenant costs, and applying the specific levers that change it. The levers are different from those for servers. You don't right-size a fleet. You tune memory, filter invocations, batch work, control logs, avoid per-GB network charges and remove idle provisioned capacity.

It builds on 41.1a's cost model, which answers whether a workload should be on functions at all. This article is about keeping a workload that belongs there from costing more than it should.

## Recognizing the Problem

- The bill jumps without a matching change in traffic, and it takes days to explain.
- Nobody can say what a given function costs per month, or per tenant.
- Log costs rival or exceed compute costs.
- Functions in a VPC read from S3 or DynamoDB through a NAT gateway.
- Memory settings were chosen once, by guess, and never revisited.
- Functions are invoked for events they immediately ignore.
- Dead-letter queues are empty because messages retry for hours before getting there.
- Provisioned concurrency or other warm capacity exists outside production.
- Log groups have no retention setting.

## How It Works

### 1. Find where the money is

Three views, from coarse to fine:

- **By component.** Tag every resource with `project`, `component` and `environment`, and activate them as cost allocation tags. The billing console can then break the bill down by component. Untagged resources are the first finding.
- **By function.** Each invocation's `REPORT` log line has its billed duration and memory. Summed per function, that's its compute cost. Add its log volume and its share of per-request charges.
- **By tenant.** The platform doesn't know your tenants, so each function writes one summary line per tenant it processed: tenant, measured duration, memory. A log query sums them. In a multi-tenant product, this tells you whether your top customers' plans cover what they cost (Module 15).

### 2. Memory is also CPU

On Lambda, CPU is allocated in proportion to memory. So memory is a price-performance setting, not just a limit:

- **CPU-bound functions** (image processing, compression, parsing) often finish twice as fast at twice the memory, for roughly the same cost, or less.
- **I/O-bound functions** (waiting on S3, an API or a database) don't get faster with more memory, so extra memory is wasted money. The watermark function at 3 GB spent 80% of its time downloading.

Don't guess. **AWS Lambda Power Tuning**, an open-source tool, runs a function at several memory sizes with a real payload and charts cost against duration. Re-run it when the code changes significantly.

**arm64** (Graviton) is about 20% cheaper per GB-second and often at least as fast. The main cost is testing native dependencies, which image libraries often have.

### 3. Don't run what you'll ignore, and batch what you run

- **Filter at the source.** S3 event notifications can be limited by prefix and suffix; queue and stream triggers accept **filter criteria**; event bus rules match specific event types. Invoking a function only for it to return early costs a request, a cold start sometimes, and a log line. The thumbnail function should never have been triggered by `thumbnails/`, which also removes the recursive-trigger risk (41.1a).
- **Batch.** A queue trigger with a batch size of 10 and a short batching window turns ten invocations into one. It's fewer requests and less INIT overhead. Per-message failure reporting keeps retries targeted.

### 4. Retries cost money

A function that fails and retries five times costs six times as much. Long-running failures are the worst case: an image that crashes a 60-second function after 55 seconds, with a queue that allows 20 receives, costs 20 minutes of compute before it reaches the dead-letter queue.

- Keep **timeouts** close to real durations, not at the maximum.
- Keep **maximum receives** low (3–5) for work that fails the same way every time.
- Detect **poison messages** (unparseable input, missing tenant) and fail them fast, before doing expensive work.
- Alarm on retry rates, not only on dead-letter queues.

### 5. Logs: the quiet line item

Logs are often the largest serverless cost after compute, and occasionally larger. Lambda's CloudWatch logs are billed per GB ingested: tiered since 2025, starting at about $0.50 per GB and falling only at very high volumes. They can also be sent directly to S3 or Firehose, from about $0.25 per GB. Stored logs are billed per GB-month, and **log groups never expire by default**.

Most of the saving comes from logging less:

- **Structured JSON logs with a level**, and a platform-level minimum (on Lambda, `ApplicationLogLevel`), so `DEBUG` lines are dropped before they're billed.
- **Log IDs and decisions, never payloads.** One 20 KB payload per event at 3 million events a month is 60 GB of logs.
- **Sample** detail for successful requests (say 1%), and keep 100% of failures.
- **Set retention** on every log group: 14–30 days for most, longer only where an audit requires it.

### 6. Network: the per-GB charges

Functions outside a VPC reach AWS services directly. Functions **inside** a VPC (needed to reach a private database or proxy, 41.3a) reach the internet, and by default AWS APIs, through a **NAT gateway**, which bills per hour (about $0.045 in us-east-1) plus about $0.045 per GB processed.

For S3 and DynamoDB, **gateway VPC endpoints** are free and route traffic privately. For other services, **interface endpoints** have an hourly and per-GB cost that's usually lower than NAT for heavy use. The watermark function's 30 TB a month of image downloads through NAT was about $1,350 that a free S3 gateway endpoint removes entirely. And functions that don't need the VPC shouldn't be in it.

### 7. Idle capacity and INIT

- **Provisioned concurrency, always-ready instances and minimum instances** bill whether used or not. Check utilization monthly, schedule them for business hours, and never leave them on outside production.
- **INIT is billed** (since August 2025). A dependency that adds 1.5 s to initialization is paid on every cold start. Heavy libraries belong only in the functions that need them (41.2a).
- **Compute Savings Plans** apply to Lambda and Fargate. Commit only to your steady baseline.

### 8. A monthly review

A 30-minute review, once a month, catches most of this before it compounds:

```
1. Top 10 functions by cost ─── any surprises? anything now steady enough for a container (41.4a)?
2. Top 10 tenants by cost ───── do their plans cover them?
3. Log GB by function ───────── anything logging payloads or at DEBUG?
4. Idle capacity ────────────── provisioned concurrency, NAT gateways, proxies, always-ready instances
5. Retries and DLQ depth ────── paid failures
6. One action item, with an owner and a date
```

## When It's Appropriate

- **Any serverless system past its first few hundred dollars a month.** Tags and log controls cost almost nothing to set up.
- **Multi-tenant products with usage-based or tiered pricing**, where cost per tenant informs pricing.
- **After an unexplained jump in the bill**, as the structure for finding the cause.
- **Before committing to Savings Plans**, to know your real baseline.

## When It's Unnecessary or Overkill

- **Tiny systems.** Power-tuning a function that costs $3 a month isn't worth an afternoon.
- **Optimizing compute when logs or network dominate.** Start from the breakdown; the largest line is usually not where you'd guess.
- **Per-tenant attribution for a product with flat pricing and similar customers.** Per-function cost may be enough.
- **Micro-optimizing memory on functions that are about to be rewritten or moved to containers.**

## Trade-offs

- **Measurement has its own cost.** Per-tenant summary lines are more log volume, and more code in every handler.
- **Lower logging means less to investigate with.** Sampling and shorter retention save money and occasionally lose the one log line you needed. Keep failures in full.
- **Memory tuning is a snapshot.** Code changes and traffic shifts invalidate it, and a tuned-down function can become slow after a dependency upgrade.
- **Batching adds latency**, up to the batching window, and larger batches mean more work redone if the whole batch fails.
- **VPC endpoints add infrastructure to manage**, and interface endpoints have their own costs.
- **Savings Plans trade flexibility for discount**: commit too much and you pay for capacity you no longer use.
- **Tight timeouts and low retry limits** can turn a transient slowdown into dead-letter messages that need redriving.

## Alternatives

- **Move steady workloads to containers** (41.4a). Often the biggest single saving, and it removes several of these levers from consideration.
- **Third-party cost tools** that attribute and alert automatically. Useful at scale, and they still depend on your tags and log structure.
- **Budgets and anomaly detection** (AWS Budgets, Cost Anomaly Detection) as a safety net. They catch the jump within a day instead of at month-end, and don't explain it.
- **Hard caps**: reserved concurrency as a ceiling on what a function can spend per hour. Crude, and effective against runaway loops.

## How to Achieve It

**Step 1: tags, log retention and log levels on everything**, plus a budget alert and anomaly detection. _Signal to move on:_ you can see cost by component, but not by function or tenant.

**Step 2: per-function cost from `REPORT` lines**, and filter or batch the top offenders' triggers. Put S3 and DynamoDB traffic behind gateway endpoints. _Signal:_ you know what each function costs, but not who drives it.

**Step 3: per-tenant summary lines** and a monthly query. Feed the results into pricing and plan limits. _Signal:_ the big items are fixed, and the remaining cost is compute.

**Step 4: power-tune the top functions**, move them to arm64, and commit a Savings Plan to the steady baseline. Hold the monthly review.

## Implementation

TypeScript, in two pieces: a wrapper that writes one cost-summary line per tenant from any handler, and the query that sums them.

```ts
import type { Context } from "aws-lambda";

// Wraps a per-item handler. Each processed item writes one small summary line:
// tenant, its measured duration and the function's memory. No payloads.
export function withCostSummary<I extends { tenantId: string }>(
  fn: (item: I, ctx: Context) => Promise<void>,
) {
  return async (item: I, ctx: Context) => {
    const started = performance.now();
    let outcome = "ok";
    try {
      await fn(item, ctx);
    } catch (err) {
      outcome = "error";
      throw err;
    } finally {
      console.log(JSON.stringify({
        msg: "cost-summary",
        tenantId: item.tenantId,
        function: ctx.functionName,
        durationMs: Math.round(performance.now() - started),
        memoryMb: Number(ctx.memoryLimitInMB),
        outcome, // failed attempts cost money too
      }));
    }
  };
}
```

> **Aside: why measure per item, not per invocation.** A batch of ten messages can belong to ten tenants. Attributing the whole invocation to the first one is the same mistake as 41.3c's batch bug, applied to the bill. The per-item durations don't add up exactly to the billed duration (INIT and overhead are left over), which is fine for comparing tenants. Spread the remainder proportionally if you need totals to match.

The query, in CloudWatch Logs Insights, turns those lines into approximate GB-seconds and cost per tenant for a period:

```
filter msg = "cost-summary"
| stats sum(durationMs / 1000 * memoryMb / 1024) as gbSeconds,
        count(*) as items,
        sum(outcome = "error") as failedItems
  by tenantId
| sort gbSeconds desc
| limit 25
```

> **Aside: compute is only one column.** Multiply `gbSeconds` by the per-GB-second price for the compute cost, then add the tenant's share of per-request, log and storage costs. For a product like the proofing one, storage and data transfer per photographer may matter more than compute. The query tells you who is expensive; the bill tells you in what.

---

The habit to take from this: when a serverless bill surprises you, don't look at compute first. Sort the bill by line item and start with the biggest one. In a system where everything is billed per use, the expensive thing is usually something that happens far more often than anyone intended.
