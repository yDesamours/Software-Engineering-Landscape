# Databases That Scale With the Load: Capacity on Demand, Scale to Zero, Branching and Distributed SQL

_Module 41 · Serverless Patterns · 41.3b_

## The Problem

Suppose you run a survey and feedback product for HR teams. Customers run employee engagement surveys: a few quiet weeks, then a launch day when 40,000 employees of one company open the same survey within an hour, then a trickle for two weeks while results are analyzed. The compute is functions (41.1a). The database is a provisioned Aurora PostgreSQL instance, and it causes four separate problems.

**It's sized for launch day.** The instance is large enough for the biggest customer's launch, a `db.r6g.2xlarge`. On an average day it runs at 6% CPU. Launch days are unpredictable, since customers schedule them, so nobody can resize ahead of time. The database is the largest line on the bill.

**Preview environments are expensive or fake.** Every pull request gets a preview deployment, but they all share one staging database. Two PRs with incompatible migrations break each other. A proposal to give each preview its own Aurora instance was dropped when someone multiplied 30 open PRs by an instance's monthly cost.

**Migrations are tested on toy data.** A migration adding a `NOT NULL` column with a default ran in 40 ms on staging's 3,000 responses. In production, on 90 million responses, it held a lock for 11 minutes during a customer's launch.

**A new customer needs writes in two regions.** A multinational wants its European employees' responses stored and writable in the EU, and its US employees' in the US, with the same survey open in both. The single-region database can't do that without a separate deployment and application-level routing.

Each of these is a mismatch between a database built around **a fixed-size server in one place** and a workload that is spiky, disposable, or spread out.

## What It Is

Several kinds of database now separate some of these properties from the fixed server. Three are relevant to relational data:

- **Capacity that follows load.** **Aurora Serverless v2** is ordinary Aurora (PostgreSQL or MySQL) whose instance resizes itself continuously between a minimum and maximum you set, and can pause to zero when idle.
- **Separated storage and compute, with branching.** **Neon** keeps data in a shared storage layer and runs PostgreSQL compute nodes on demand. That makes idle compute free, and makes **branches** possible: near-instant copy-on-write copies of an entire database at a point in time.
- **Distributed SQL with no instances at all.** **Aurora DSQL** is a PostgreSQL-compatible database with no capacity settings, which scales in both directions by itself and can accept writes in multiple regions at once. The price is optimistic concurrency and a narrower feature set.

For key-value data, DynamoDB is the fully serverless option. It's covered separately in 41.3c, because the interesting part there is tenant isolation.

These are not the same as the **connection** problem in 41.3a. A serverless database can still be overwhelmed by thousands of connections (Aurora Serverless v2 certainly can). The two problems are solved separately.

## Recognizing the Problem

- The database is sized for rare peaks and sits mostly idle.
- Peaks are unpredictable, so scheduled resizing doesn't work.
- Dev, staging and preview databases cost about as much as production, or are shared and break each other.
- Migrations are tested on data far smaller than production.
- Debugging a data bug means copying production data by hand.
- A requirement for active writes in more than one region.
- Nobody wants to own instance sizing, storage growth or version upgrades.

## How It Works

### 1. Aurora Serverless v2: an instance that resizes itself

Capacity is measured in **Aurora Capacity Units (ACUs)**. One ACU is roughly 2 GiB of memory, with matching CPU and network. You set a minimum and maximum (up to 256 ACUs), and capacity moves in steps of half an ACU, without restarts, as load changes. Pricing in us-east-1 is about **$0.12 per ACU-hour** on Aurora Standard, plus storage and I/O.

**Scale to zero.** Since late 2024, the minimum can be **0 ACUs**. After an idle period (5 minutes minimum, configurable up to 24 hours), the instance pauses and you pay only for storage. Resuming takes about **15 seconds**, longer after a long pause. Several things prevent pausing: any open connection (**including RDS Proxy's**, 41.3a), logical replication, being a Global Database primary, and maintenance.

So scale to zero suits dev, staging, preview environments and internal tools. It doesn't suit a user-facing production database: the first request after a quiet period waits 15 seconds, which for most users is a failure.

**When is it cheaper than a provisioned instance?** Compare an 8-ACU peak (16 GiB) with a provisioned instance of the same memory at about $0.26 an hour:

```
Serverless v2 at peak:   8 ACU × $0.12 = $0.96/hour
Provisioned (16 GiB):                   $0.26/hour, always

break-even: serverless is cheaper when average capacity < 0.26 / 0.96 ≈ 27% of peak
```

| Workload | Average ACUs | Serverless v2 / month | Provisioned / month | Cheaper |
|---|---|---|---|---|
| Business-hours B2B: 8 ACU for 10 h on weekdays, 1 ACU otherwise | ~3 (37% of peak) | ~$260 | ~$190 | Provisioned |
| Survey launches: 1 ACU most days, 8 ACU for ~15 launch hours a month | ~1.1 (14%) | ~$100 | ~$190 | Serverless |
| Staging: 2 ACU, 3 h a day on weekdays, paused otherwise | ~0.2 | ~$16 | ~$190 | Serverless |

The survey product lands in the middle row. Its peaks are unpredictable, and a provisioned instance would have to be sized for them all month. The first row shows the opposite case: steady business-hours traffic is cheaper provisioned, especially with reserved pricing. You can also mix both in one cluster: a provisioned writer with Serverless v2 readers to absorb read spikes.

Two settings matter. The **maximum ACU** is your cost ceiling, which a runaway query or noisy tenant can't exceed, and it's also a throughput ceiling. And `max_connections` depends on capacity, so a cluster that's scaled down accepts fewer connections.

### 2. Neon: compute on demand, and branches

Neon splits PostgreSQL into a storage layer that keeps all data and its history, and compute nodes (ordinary Postgres) that start when a connection arrives, resize, and stop when idle. Idle compute usually restarts in about a second or less, much faster than Aurora's resume. Compute is billed per CU-hour, storage per GB-month. A small development branch that's active 40 hours a month costs about a dollar.

Because storage keeps history, a **branch** is a copy-on-write copy of the entire database at a chosen point in time. Creating one takes seconds regardless of size, because nothing is copied until it changes. That changes several workflows:

| Workflow | Without branching | With branching |
|---|---|---|
| Preview environments | One shared staging database | A database per pull request, created in CI and deleted when the PR closes |
| Migration rehearsal | Toy data in staging | Branch a production-sized copy, run the migration, measure its time and locks, delete the branch |
| Data-bug investigation | Copy rows by hand | Branch at the timestamp just before the bug |
| Load tests | Risky on shared environments | Branch, test, discard |

**A branch of production contains production data**, including personal data. Preview and CI branches should come from a sanitized staging branch, never directly from production (34.1a applies to test databases too).

Neon also includes a PgBouncer pooler in transaction mode (so 41.3a's rules apply) and an HTTP-based driver for functions. Aurora has a partial equivalent to branching, **fast clones**: copy-on-write clusters that take minutes, and each clone is a cluster you pay for while it runs. That's fine for a nightly migration rehearsal, and heavy for every pull request.

### 3. Aurora DSQL: distributed SQL with optimistic concurrency

DSQL has no instances or capacity settings. It scales reads, writes, compute and storage independently, scales to zero when idle, and in multi-region configurations accepts writes in two regions with strong consistency. It speaks the PostgreSQL wire protocol, and connections authenticate with IAM tokens. Pricing is per **DPU**, a single unit of compute and I/O (about $8 per million DPUs), plus storage (about $0.33 per GB-month), with a small free tier.

The difference that matters most for application code is **optimistic concurrency control**. Transactions don't wait for locks. If two transactions touch the same rows, one of them **fails at commit** with a serialization error, and the application must retry the whole transaction:

```
T1: BEGIN ─ read row 42 ─ update row 42 ───────── COMMIT ✓
T2:    BEGIN ─ read row 42 ─ update row 42 ─────────────── COMMIT ✗ serialization failure → retry T2
```

That's efficient when conflicts are rare, and punishing when they aren't. A **hot row** that many transactions update (a global counter, a survey's response count) turns into a stream of retries. The fix is a different data model: append a row per response and aggregate, instead of incrementing one row.

DSQL also leaves out parts of PostgreSQL. Currently:

- no triggers, no PL/pgSQL, no temporary tables
- isolation fixed at Repeatable Read
- limits of 3,000 modified rows, 10 MiB and 5 minutes per transaction

It now supports foreign keys and sequences, which earlier versions didn't. The list is changing, so check it against your schema rather than relying on a summary.

So DSQL fits **new services** that need multi-region writes, very spiky traffic, or zero capacity management, with short transactions and data spread across many keys. It's a poor fit for an existing schema built on triggers and stored procedures, for large batch transactions, and for workloads with hot rows. For the survey product's multinational customer, DSQL is a candidate for a new response-ingestion service, not a drop-in replacement for the existing database.

### Choosing

```
Relational core data?
├─ steady load in production ──────────────► provisioned instance (+ proxy for functions, 41.3a)
├─ spiky, unpredictable production load ───► Aurora Serverless v2 with a max ACU
├─ dev, staging, preview, migration tests ─► Neon branches, or Serverless v2 paused at zero
└─ new service, multi-region writes ───────► consider Aurora DSQL; design for retries and no hot rows
Key-based, high-volume data ───────────────► DynamoDB (41.3c)
```

## When It's Appropriate

- **Unpredictable peaks** several times larger than the baseline, where a provisioned instance would be sized for the peak all month.
- **Many short-lived environments:** previews per pull request, CI databases, demos, per-developer databases.
- **Migration rehearsal on production-sized data** before running the migration for real.
- **New products** where nobody wants to manage capacity yet.
- **Active multi-region writes** with strong consistency, for a service designed around them.

## When It's Unnecessary or Overkill

- **Steady production load.** Provisioned instances, especially with reserved pricing, are cheaper.
- **Scale to zero behind a user-facing API.** A 15-second resume is a failed request.
- **Moving an existing schema to DSQL** that relies on triggers, stored procedures or large transactions, for "serverless" alone.
- **Branching production data into CI** for convenience. Use a sanitized parent branch.
- **Adding these to a small product whose database already costs little.** The simplest managed Postgres may be all it needs.

## Trade-offs

- **Serverless v2 costs more per unit of capacity** than a provisioned instance (about four times per GiB-hour at peak), and only saves money when average use is low.
- **Scaling isn't instant.** Capacity grows in seconds, and buffers and caches start cold after scaling up or resuming. A sudden 10x spike still feels slow at first.
- **Scale to zero trades cost for first-request latency**, and it's defeated by anything holding a connection open.
- **Branches are only as safe as their parent**, and copy-on-write branches that live long diverge and accumulate storage.
- **Neon is a third-party service** running outside your cloud account. That affects compliance, networking and vendor risk. (Neon was acquired by Databricks in 2025. Its exit path is standard `pg_dump`.)
- **DSQL moves concurrency handling into your code.** Every write path needs a retry loop, and data models must avoid hot rows. Its missing features can force schema redesign.
- **Everything with a maximum can hit it.** A maximum ACU or DPU budget protects the bill by throttling the workload.

## Alternatives

- **Provisioned instances, scheduled resizing, and read replicas** for predictable patterns. Old-fashioned and often cheapest.
- **Cache and queue in front of the database.** The survey launch is mostly reads of the same survey and writes of independent responses. A cache for the survey and a queue for responses can flatten the peak instead of scaling for it.
- **Database-per-tenant for the biggest customers** (Module 5), so one customer's launch doesn't size everyone's database.
- **CockroachDB, Spanner, YugabyteDB** for distributed SQL with more mature feature sets, at higher operational or financial cost.
- **Local Postgres in containers for CI** (Testcontainers). Free and isolated, but no production-sized data.

## How to Achieve It

**Step 1: branch-per-PR or scale-to-zero for non-production.** It's the safest place to start, and usually saves the most money. _Signal to move on:_ you trust the tools and want production savings.

**Step 2: measure production's capacity curve.** Average versus peak by hour for a month. Below about a quarter of peak, Serverless v2 will probably be cheaper. Set a maximum. _Signal:_ migrations still surprise you in production.

**Step 3: rehearse every non-trivial migration on a production-sized branch or clone**, and record its time and locks in the pull request. _Signal:_ a new requirement (multi-region writes) doesn't fit a single-writer database.

**Step 4: consider distributed SQL for the new service only**, designed for short transactions, retries and no hot rows.

## Implementation

TypeScript, in two pieces: the retry loop every write path needs on an optimistically concurrent database, and a break-even check to run before choosing Serverless v2.

```ts
import pg from "pg";

const SERIALIZATION_FAILURE = "40001"; // DSQL reports commit conflicts with this SQLSTATE

export async function withRetryingTx<T>(
  pool: pg.Pool,
  fn: (client: pg.PoolClient) => Promise<T>,
  maxAttempts = 5,
): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    const client = await pool.connect();
    try {
      await client.query("BEGIN");
      const result = await fn(client);
      await client.query("COMMIT"); // conflicts surface here, not at the UPDATE
      return result;
    } catch (err) {
      await client.query("ROLLBACK").catch(() => {});
      const retryable = (err as { code?: string }).code === SERIALIZATION_FAILURE;
      if (!retryable || attempt >= maxAttempts) throw err;
      const backoff = Math.random() * 25 * 2 ** attempt; // jitter, so retries don't collide again
      await new Promise((r) => setTimeout(r, backoff));
    } finally {
      client.release();
    }
  }
}

// A response is a new row, not an increment of a shared counter: no hot row, no conflicts.
export const recordResponse = (pool: pg.Pool, r: { id: string; surveyId: string; answers: unknown }) =>
  withRetryingTx(pool, (c) =>
    c.query("INSERT INTO responses (id, survey_id, answers) VALUES ($1, $2, $3) ON CONFLICT (id) DO NOTHING",
      [r.id, r.surveyId, JSON.stringify(r.answers)]));
```

> **Aside: the whole transaction is retried, including its reads.** `fn` runs again from the beginning, so it must not have side effects outside the database: no emails, no calls to other services. Those go after the commit, or through an outbox (37.2a). The `ON CONFLICT DO NOTHING` makes the insert idempotent, in case a commit succeeded but its acknowledgement was lost.

> **Aside: why counters are the classic failure.** `UPDATE surveys SET response_count = response_count + 1` from 40,000 employees in an hour means most transactions conflict with another one that's in flight. With locks, they'd queue. With optimistic concurrency, they fail and retry, and the retries conflict too. Count with `SELECT count(*)` over the responses, or maintain the count asynchronously.

The break-even check is a few lines, and settles most "should we go serverless?" discussions about the database:

```ts
type HourlyLoad = number[]; // ACUs needed for each hour of a typical month (length ≈ 730)

export function serverlessV2VsProvisioned(load: HourlyLoad, acuPrice = 0.12, provisionedHourly = 0.26) {
  const serverless = load.reduce((sum, acu) => sum + (acu === 0 ? 0 : Math.max(acu, 0.5)) * acuPrice, 0); // 0 = paused
  const provisioned = load.length * provisionedHourly;
  const peak = Math.max(...load);
  const averageShareOfPeak = load.reduce((a, b) => a + b, 0) / load.length / peak;
  return { serverless, provisioned, averageShareOfPeak, cheaper: serverless < provisioned ? "serverless" : "provisioned" };
}
```

> **Aside: where the hourly load comes from.** For an existing database, derive it from CPU and memory metrics for a representative month, including its worst week. For a new product, it's a guess, and the right answer is often "start on Serverless v2 with a maximum, measure for a quarter, then decide."

---

The habit to take from this: when a database is sized for its worst hour, ask how many hours a month look like that. If the answer is "a few, and we don't know which," the question is no longer which instance size to buy, but whether you should be buying an instance at all.
