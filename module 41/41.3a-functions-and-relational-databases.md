# Functions Meet Relational Databases: Connection Math, Proxies and Pinning

_Module 41 · Serverless Patterns · 41.3a_

## The Problem

Suppose you run booking software for fitness studios: class schedules, bookings, waitlists and memberships. The core API runs on four containers with a pool of 20 Postgres connections each: 80 connections in total, against an Aurora PostgreSQL instance with 16 GiB of memory. Background work runs as AWS Lambda functions: reminder emails, waitlist promotion, and monthly membership renewals.

Renewals run on the first of the month. A scheduled function puts one message per membership onto a queue, and a consumer function renews each one: charge the card, extend the membership, write an invoice. The consumer was built with the same database code as the API, including a pool of 10 connections.

**The first of the month.** 60,000 messages land on the queue. The platform starts consumers as fast as the queue allows. Within two minutes, 300 environments are running, each opening its own pool. The database reaches its connection limit, a little under 1,800, and starts refusing new connections. **Including the API's.** Studios can't check members in for their 7 a.m. classes. The renewals themselves fail and retry, which keeps the pressure on.

**The fix that didn't fix it.** The team adds Amazon RDS Proxy, which pools connections between functions and the database. Client connections to the proxy are cheap; the proxy keeps a smaller set of real database connections. Next month, the database is still overwhelmed. The proxy's metrics show `DatabaseConnectionsCurrentlySessionPinned` rising in step with client connections. Every function connection has been **pinned** to its own database connection, so the proxy isn't pooling anything.

Two things caused the pinning. The Go driver was caching **named prepared statements**, which exist in one database session. And the tenant context for row-level security was set with a session-level `SET app.studio_id = …` at the start of each request.

**The failover.** In the third month, the database fails over during maintenance. Every environment's connection breaks at once, and every environment reconnects at the same moment, each paying TLS and authentication. The connection storm takes longer to settle than the failover itself.

**The zombies.** Between invocations, Lambda freezes environments, and it shuts idle ones down without warning. Their connections aren't always closed cleanly. After a burst, the database holds hundreds of connections that nobody is using until they time out.

The database was never too small. The functions were written as if they were one long-running server, when in fact they were hundreds of short-lived clients that couldn't share anything.

## What It Is

This is the **connection problem** of serverless compute: relational databases are built for a small number of long-lived, pooled connections, and functions produce a large number of short-lived, unpooled ones.

In PostgreSQL every connection is a separate server process with its own memory. Opening one takes a TCP handshake, TLS, authentication and process start-up, which together cost tens of milliseconds. The server has a fixed `max_connections`, and performance degrades well before reaching it. A long-running server amortizes all of this with a pool. A function environment can only pool with itself.

This article is about functions specifically. How pools work in general, and why a connection held while waiting on something else causes exhaustion, is 38.3a. Transaction-mode poolers are covered in 5.4b, and why tenant context must be transaction-scoped with them in 5.2a. The rest of this article assumes both.

## Recognizing the Problem

- The database's connection count follows the number of running function environments.
- "Too many clients" or "remaining connection slots are reserved" errors during bursts, affecting services that did nothing different.
- A proxy is in place, and its pinned-connection metric tracks its client connections.
- Cold starts include tens of milliseconds for connecting, visible in traces.
- After a failover, errors last much longer than the failover.
- The database shows many idle connections after a burst ends.
- Function code copies pool settings from the API, such as a pool size of 10.
- Tenant context is set with a session-level `SET`.

## How It Works

### 1. The arithmetic

```
database connections = concurrent function environments × pool size per environment
```

| Situation | Environments | Pool size | Connections |
|---|---|---|---|
| Renewals consumer, capped | 10 | 1 | 10 |
| Same consumer, uncapped, on the 1st | 300 | 1 | 300 |
| Same, with the API's pool settings | 300 | 10 | 3,000 |
| Three consumers like that on one database | 900 | 10 | 9,000 |

For Aurora PostgreSQL, the default `max_connections` comes from a formula based on instance memory. For a 16 GiB instance it works out to roughly 1,700–1,800. The third row takes the database down, and the connections it takes are shared with everything else.

### 2. The first two fixes are free

**Pool size 1 on one-request-per-environment platforms.** Standard Lambda environments serve one request at a time (41.2a). A pool larger than 1 only helps if one request runs several queries in parallel, which is rare. On platforms that serve many requests per instance (Cloud Run, Azure Flex Consumption, Lambda Managed Instances), a pool of 5–20 is right, because concurrent requests share it.

**Cap concurrency.** A queue-triggered function can be limited in how many environments it may run (on Lambda, `MaximumConcurrency` on the event source mapping). Ten environments with one connection each is ten connections, whatever the queue depth. The queue absorbs the burst, and renewals take longer instead of failing. For work that isn't latency-sensitive, this is often the only fix needed.

A cap doesn't help synchronous functions. An HTTP request that finds no available environment gets throttled, not queued. That's where the next options come in.

### 3. Pool between the functions and the database

A **connection proxy** accepts many cheap client connections and lends a small number of real database connections to them, one transaction at a time:

```
300 environments ──300 client connections──►  RDS Proxy  ──30 database connections──►  Aurora
      (cheap: no database process each)       borrows a DB connection per transaction,
                                              returns it at COMMIT
```

The options are RDS Proxy (managed, for RDS and Aurora), PgBouncer in transaction mode (self-hosted, or built into providers such as Neon), and similar poolers. Besides multiplexing, RDS Proxy gives you:

- **Faster failover:** it holds client connections open while the database fails over, so functions don't all reconnect at once.
- **IAM authentication:** functions connect with a short-lived token signed with their role's credentials. Signing is local, with no network call. No database password reaches the function.
- **One place for the password:** only the proxy reads it from the secrets store.

### 4. Pinning: when the proxy stops pooling

A proxy can only give a database connection to another client between transactions if nothing in the session still matters. When a client changes session state, the proxy **pins** that database connection to that client until the client disconnects. A pinned connection is not pooled.

Common causes in PostgreSQL:

| Cause | Typical source | Fix |
|---|---|---|
| Session-level `SET` | Tenant context (`SET app.studio_id`), `search_path` | Set it inside the transaction with `set_config(name, value, true)` (5.2a) |
| Named prepared statements | Driver statement caches: pgx by default, JDBC after a statement runs 5 times | pgx: exec mode without a statement cache; JDBC: `prepareThreshold=0` |
| Driver start-up `SET` | Some drivers send settings on connect (the PostgreSQL JDBC driver sets `extra_float_digits`) | Driver options, or the proxy's initialization query |
| Temporary tables, `LISTEN`, cursors or advisory locks held across transactions | Specific jobs | Give those jobs a direct connection |

**Measure it.** RDS Proxy publishes `DatabaseConnectionsCurrentlySessionPinned`. If it tracks client connections, the proxy is adding cost and latency and nothing else. PgBouncer in transaction mode doesn't pin at all. It just hands the session, with its state, to the next client. That's how a session-level tenant setting becomes a cross-tenant leak there (5.2a, 5.4b).

### 5. Or don't hold a connection at all

**HTTP-based data APIs** run SQL over an HTTPS request, with no connection to manage: Aurora's **Data API**, and Neon's **serverless driver**, which uses HTTP for single queries and non-interactive transactions and WebSockets for sessions. They remove the connection problem entirely. In exchange, every query or batch pays a network round trip, interactive transactions are limited or unavailable, and some features are missing. They suit short functions that run one or two queries.

### 6. Or use a database built for it

DynamoDB and Aurora DSQL don't have the problem in this form: DynamoDB is HTTP-based, and DSQL is built for many short connections. Both come with other constraints, covered in 41.3b and 41.3c. Moving data to a different database only for its connection model is rarely worth it. Moving new, key-based, high-volume data there often is.

### Putting them together

Most real systems combine them:

```
queue consumers ── cap concurrency, pool size 1 ──────────────┐
HTTP functions ── pool size 1, via proxy, no session state ──┼──► RDS Proxy ──► Aurora ◄── API containers
tiny functions ── HTTP data API ─────────────────────────────┘                 (their own pools, or the proxy too)
high-volume key-based data ── DynamoDB (41.3c)
```

## When It's Appropriate

- **Any function that talks to a relational database** needs the arithmetic, a pool size of 1 on standard Lambda, and a concurrency cap on queue triggers. That part is never optional.
- **A proxy** when synchronous functions talk to the database, when concurrency can't simply be capped, or when failover behavior matters.
- **IAM authentication** when you'd rather not distribute a database password to every function.
- **HTTP data APIs** for small, infrequent functions: an admin action, a webhook that writes one row.

## When It's Unnecessary or Overkill

- **A handful of low-volume functions** with capped concurrency. Ten connections don't need a proxy.
- **A proxy in front of a database you want to pause.** Its open connections stop Aurora Serverless v2 from scaling to zero (41.3b), and on Serverless v2 it bills for a minimum of 8 ACUs, roughly $88 a month.
- **Rewriting data access to be connectionless** when a cap and a proxy already solve it.
- **Moving the core relational data to a key-value store** because the functions struggle with connections. Fix the connections instead.

## Trade-offs

- **Caps turn overload into delay.** Month-end renewals take an hour instead of ten minutes. That's usually right, but it needs to be a decision, with an alarm on queue age.
- **A proxy adds a hop, a cost and a component.** Every query pays a little latency. RDS Proxy is billed per vCPU (or ACU) of the database, about $0.015 per hour each, and it's another thing that can be misconfigured.
- **Avoiding pinning constrains your code.** No session-level settings, no named prepared statements, and no session features such as `LISTEN` or temporary tables through the proxy. Jobs that need them need a separate, direct connection.
- **Unnamed statements give up server-side plan caching.** Each query is parsed and planned every time. For short queries this rarely matters; for complex ones, measure.
- **IAM tokens expire after 15 minutes.** New connections must generate a fresh one, which drivers have to be set up to do.
- **HTTP data APIs trade connection management for per-query latency and fewer features.**
- **Functions inside a VPC** (required to reach a proxy) need VPC endpoints or a NAT gateway for other AWS APIs, and NAT gateways have their own hourly and per-GB costs (41.4b).

## Alternatives

- **Keep database-heavy work on containers** (41.4a). A container with a pool of 20 serves far more requests per connection than functions ever will.
- **Put a queue in front and let a small worker pool drain it** (Module 10). Same idea as a cap, with long-running pooled workers.
- **Read replicas for read-heavy functions.** Reports and exports read from a replica through a separate proxy endpoint, and leave the writer alone.
- **A serverless-native database for new data** (41.3b, 41.3c).

## How to Achieve It

**Step 1: do the arithmetic.** List every function that connects to the database, with its maximum concurrency and pool size, and add them up against `max_connections`, leaving room for the API. Set the pool size to 1 and cap concurrency on every queue trigger. _Signal to move on:_ synchronous functions or unavoidable bursts still push the total too high.

**Step 2: add a proxy for the functions**, and connect with IAM authentication. _Signal:_ check the pinned-connection metric under load. If it tracks client connections, go to step 3.

**Step 3: remove session state.** Transaction-scoped tenant context, driver settings that avoid named statements and start-up `SET`s, and a separate direct connection for jobs that truly need session features. _Signal:_ pinning stays near zero, and database connections stay flat during bursts.

**Step 4: move the smallest functions to an HTTP data API**, or new key-based data to a serverless-native store, where that's simpler than connecting at all.

## Implementation

Go, because pgx's default statement cache is one of the most common hidden causes of pinning, and the fix is one line that's easy to miss. The pool below has one connection, gets a fresh IAM token for every new connection, never creates named prepared statements, and scopes the tenant to each transaction.

```go
package db

import (
	"context"
	"fmt"

	"github.com/aws/aws-sdk-go-v2/aws"
	"github.com/aws/aws-sdk-go-v2/feature/rds/auth"
	"github.com/jackc/pgx/v5"
	"github.com/jackc/pgx/v5/pgxpool"
)

// NewProxyPool is called once from main(), during INIT.
func NewProxyPool(ctx context.Context, cfg aws.Config, host, user, dbname string) (*pgxpool.Pool, error) {
	pc, err := pgxpool.ParseConfig(fmt.Sprintf(
		"host=%s port=5432 user=%s dbname=%s sslmode=verify-full connect_timeout=10", host, user, dbname))
	if err != nil {
		return nil, err
	}

	pc.MaxConns = 1 // one request per environment on standard Lambda

	// pgx's default mode caches NAMED prepared statements, which pins RDS Proxy
	// connections. Exec mode sends unnamed statements instead.
	pc.ConnConfig.DefaultQueryExecMode = pgx.QueryExecModeExec

	// IAM tokens last 15 minutes: build a fresh one for every new connection.
	// Signing is local; it makes no network call.
	pc.BeforeConnect = func(ctx context.Context, cc *pgx.ConnConfig) error {
		token, err := auth.BuildAuthToken(ctx, host+":5432", cfg.Region, user, cfg.Credentials)
		if err != nil {
			return err
		}
		cc.Password = token
		return nil
	}
	return pgxpool.NewWithConfig(ctx, pc)
}
```

> **Aside: why a pool of one, not a single connection.** The pool gives you health checks and reconnection for free. When an environment is frozen for ten minutes and its connection is dropped by the proxy's idle timeout, the pool notices and reconnects with a new token, instead of the next invocation failing on a dead socket.

The tenant context lives inside the transaction, so nothing survives into the next client's borrow and nothing pins:

```go
// WithTenantTx runs fn in a transaction scoped to one studio.
func WithTenantTx(ctx context.Context, pool *pgxpool.Pool, studioID string, fn func(pgx.Tx) error) error {
	tx, err := pool.Begin(ctx)
	if err != nil {
		return err
	}
	defer tx.Rollback(ctx) // no-op after a successful commit

	// is_local = true: reset automatically at COMMIT or ROLLBACK.
	// A session-level SET would pin the proxy connection, or leak through PgBouncer.
	if _, err := tx.Exec(ctx, "SELECT set_config('app.studio_id', $1, true)", studioID); err != nil {
		return err
	}
	if err := fn(tx); err != nil {
		return err
	}
	return tx.Commit(ctx)
}
```

> **Aside: keep external calls outside the transaction.** The renewal charges a card. If that HTTP call happens inside `WithTenantTx`, the transaction holds a database connection for the length of the call, and the proxy can't lend it to anyone else. That's the exhaustion pattern from 38.3a. Charge first with an idempotency key, then open the transaction to record the result (or use the outbox, 37.2a).

To confirm the fix, run a burst in a test environment and compare the proxy's `ClientConnections`, `DatabaseConnections` and `DatabaseConnectionsCurrentlySessionPinned`. Client connections should rise to about your concurrency cap, database connections should stay well below it, and pinned connections should stay near zero.

---

The habit to take from this: whenever something new is going to connect to a database, multiply its maximum concurrency by its pool size before it ships. Most database outages caused by functions are that multiplication, done afterwards.
