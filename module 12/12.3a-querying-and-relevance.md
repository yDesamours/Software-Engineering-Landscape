# Querying and Relevance

_Module 12.3a — Search Functionality_

## The Problem

A marketplace. The index from 12.2 exists, the document model is sound, queries return in 30ms. Every remaining complaint is about *order*, which is the third of the three questions from 12.1a and the only one that doesn't have a mechanical answer.

Someone searches `wireless keyboard`:

```
  1.  Laptop Stand — Compatible with wireless keyboard…     8.4
  2.  Mouse Pad, Extra Wide (fits wireless keyboard + mouse) 8.1
  3.  USB-C Hub for Mac …                                    7.9
  …
  9.  K380 Multi-Device Bluetooth Keyboard                    4.2
```

The actual keyboards are on page two. Three unrelated causes produced one symptom:

- The mouse pad's description is 30 words long and contains the exact phrase. BM25's length normalization treats a match in a short field as stronger evidence — correctly, in general, and wrongly here.
- The K380's title says *Bluetooth*, not *wireless*. Nobody taught the index that those are the same thing for this catalogue. That's an **analysis** problem, and no amount of query tuning will fix it.
- The query searched one catch-all field, so a title match and a footnote match counted the same.

The team ships a fix: boost the title, `title^10`. `wireless keyboard` is now correct. Two weeks later, searching `case` returns every product whose title contains *case* — including a laptop *case* — above the phone cases that are the obvious intent, because a 10× title boost now overwhelms every other signal. A second boost gets added to compensate. Then a third. Six months on, the search query is 120 lines of JSON with a comment that says `# do not change, tuned 2024-03`.

Meanwhile, two other things have happened quietly.

The filters — `in_stock: true`, `category: electronics`, `price` range — were added to the same `must` clause as the text query, because that's where clauses go. So every one of them is computing a relevance contribution for a binary fact, none of them is cacheable, latency has roughly doubled, and an in-stock item now scores slightly higher than an out-of-stock one *for reasons unrelated to the search terms*.

And when someone asks "why is this product seventh," the honest answer is that nobody knows.

The failure here isn't any individual tuning decision. It's that **a search query is doing two jobs that have nothing in common, and relevance work is being done without a way to tell whether a change made things better.**

## What It Is

A query has two halves, and keeping them separate is most of the craft:

```
  ┌─ narrowing ────────────────┐   ┌─ ordering ──────────────────┐
  │  which documents are even  │   │  of those, which is the     │
  │  candidates?               │   │  best answer?               │
  │                            │   │                             │
  │  binary. yes or no.        │   │  continuous. a score.       │
  │  no opinion.               │   │  entirely opinion.          │
  │  cacheable.                │   │  not cacheable.             │
  │  tenant, stock, category,  │   │  text match, field weights, │
  │  price range, permissions  │   │  recency, popularity        │
  └────────────────────────────┘   └─────────────────────────────┘
```

Search engines name this explicitly: **filter context** and **query context**. A clause in filter context answers "does this document qualify" and contributes nothing to the score. A clause in query context answers "how well does this document match" and produces a number.

The second half — **relevance engineering** — is the activity of shaping that number. What makes it different from ordinary programming is that it has no correct answer, only better and worse ones, which means it is only an engineering discipline if you are measuring. Without measurement it's a sequence of confident adjustments, each fixing one reported query and silently breaking several unreported ones.

## Recognizing the Problem

- Filters (`status`, `tenant_id`, date ranges) sit in the same clause as the text query.
- Your search query contains a boost value nobody can justify, next to a comment warning people off.
- Fixing one query's ordering reliably breaks another, and you find out from a ticket.
- A `_score` is displayed to users as a percentage or a "match strength."
- There's a `min_score` threshold somewhere, tuned once, now cutting off good results.
- Nobody can answer "why did this rank here" without guessing.
- Multi-word queries return either everything or nothing — no middle setting exists.
- A name search fails because the first name is in one field and the surname in another.
- Relevance changes ship without any before/after comparison beyond one example query.
- The same product ranks differently on two page loads and nobody knows why.

## How It Works

### The bool structure

Almost every non-trivial query is one `bool` with four kinds of clause, and the four exist precisely to separate the two halves above:

| clause | must match? | affects score? | typical use |
|---|---|---|---|
| `must` | yes | **yes** | the user's text query |
| `should` | no* | **yes** | optional signals that promote |
| `filter` | yes | no | tenant, status, ranges, permissions |
| `must_not` | must not | no | exclusions |

\* with one trap: if a `bool` has no `must` and no `filter`, then at least one `should` must match. Add a `filter` later and that requirement silently vanishes — a `should`-only query that was behaving like an `OR` becomes a pure scoring hint that matches everything. It's a common and thoroughly confusing regression.

Moving filters out of `must` and into `filter` buys three things at once: correct scores (a binary fact stops contributing a number), lower latency (no scoring work), and cacheability.

**Filter caching** is worth understanding rather than assuming. Engines cache the bitset of documents matching a filter, but only for filters that are reused often enough and on segments large enough to be worth it. That has a practical consequence: `status: "active"` caches beautifully and is reused by every query; `user_id: 8812` is used once and caches nothing useful. And `range: { created_at: { gte: "now-7d" } }` is uncacheable as written, because `now` differs every millisecond — rounding it to `now-7d/d` makes the filter identical for every request that day and suddenly cacheable. That one character is a meaningful latency change on a busy index.

### Matching across fields

Real documents have several text fields, and the naive approach — one query per field, OR'd together — has a well-known failure. Search `Will Smith` against `first_name` and `last_name`:

- **`best_fields`** takes the single best-scoring field. No single field contains both terms, so a person named *Will Smithers* can outrank *Will Smith*. This is the right strategy when you expect the whole query to be found in one field (a title, a body) and wrong here.
- **`most_fields`** sums across fields, rewarding documents that match in many of them. Its real use is the same text indexed several ways — `title`, `title.stemmed`, `title.ngram` — where matching all three is genuinely stronger evidence.
- **`cross_fields`** treats the listed fields as one merged field, so terms may be satisfied from different places. Correct for `Will Smith`, and for addresses, and for anything where the query is a single concept spread across structured fields.

The choice is not a preference; it's a statement about how your content is organized, and picking wrong produces exactly the kind of "obviously wrong" result that gets escalated.

### The recall/precision dial

A multi-word query has to decide how many terms must match. Requiring all of them (`AND`) returns nothing the moment a user adds a descriptive word. Requiring one (`OR`) returns everything. Neither is usable, which is why `minimum_should_match` exists and why it takes percentages:

```
  "waterproof bluetooth speaker portable"     4 terms

  AND   → 0 results          user adds one word, gets nothing
  OR    → 90,000 results     matches anything "portable"
  75%   → 3 of 4 must match  the usable setting
```

This single parameter moves more traffic than most boost tuning does, and it's usually left at its default.

### Boosting, and why it's slippery

A field boost multiplies that field's contribution. The reason boosts feel unpredictable is that **BM25 scores have no absolute scale.** A score of 8.4 means nothing on its own — it depends on the corpus, the term's document frequency, the field's average length, and the query. So `title^10` isn't "titles are ten times more important"; it's "multiply a number whose magnitude varies by query by ten." A boost tuned on one query shape behaves differently on another, which is precisely the whack-a-mole in *The Problem*.

Practical consequences:

- Keep boosts few, small, and ordered by intent (`title^3, tags^2, body`), not large and precise. A 10× boost is almost always a symptom of something else being wrong — usually a missing synonym or an analysis problem.
- **Never expose `_score` to users** and never threshold on it. There is no "87% match." The same document, same query, different week, different corpus: different number.
- Scores are comparable *within one result set for one query*. That's it. Comparing across queries, across indexes, or across time is meaningless, and `min_score` is the most common way teams institutionalize that mistake.

### Signals that aren't text

Text relevance alone rarely produces a good ordering in a product. Recency matters for news, popularity for a marketplace, availability for a catalogue, an account's own documents for an internal tool. The mechanism is to combine the text score with other numbers — and the way you combine them matters more than the numbers.

**Multiplying** by a bounded factor is the well-behaved shape: a popularity multiplier between 1.0 and 1.5 tilts an already-relevant ordering without ever letting a popular-but-irrelevant document surface. **Adding** an unbounded term is how a product with 40,000 reviews outranks the item the user actually typed the name of, because the added value drowns a text score that lives in single digits.

Engines expose this as function scoring, script scoring, or — for the common "boost by a positive number that saturates" case — a dedicated field type that's far faster than a script because it can skip documents that can't make the top N. Prefer the specialized construct where it fits; a script that runs against every matching document is a per-document computation, and that's a latency conversation (12.4).

Two hazards that come with business signals and never leave:

- **Feedback loops.** Rank by popularity, and popular items get clicked, becoming more popular. New and good items never surface. Some counterweight — an exploration slot, a recency term, a decay on old signal — is a design requirement, not a refinement.
- **Personalization destroys reproducibility.** Once scores depend on who is asking, "why is this seventh" has a different answer per user, caching is far less effective, and your judgment set (below) no longer describes what users see.

### Why the same query can rank differently

Two mysteries worth knowing before you spend a day on either.

**Scores are computed per shard.** IDF — how rare a term is — is calculated from the documents on each shard, not the whole index. With plenty of documents the shards look statistically alike and nobody notices. With a small or unevenly distributed index, the same document can score differently depending on where it landed, and relevance looks unstable. There's a search type that gathers global statistics first at the cost of an extra round trip; the more common fix is fewer shards.

**Ties are broken arbitrarily.** Equal scores come back in whatever order the shards returned them, which can vary between requests. If the top of your results is full of identical scores, add a deterministic tiebreaker to the sort.

### Explain

Every engine can show the arithmetic behind a score:

```
  4.21  sum of:
    3.10  weight(title:keyboard)
            idf   2.4  (12,004 docs of 180,000 contain it)
            tf    0.61 (freq 1, field length 6, avg 8.2)
            boost 3.0
    1.11  weight(body:wireless) …
```

This converts "why is this seventh" from an argument into a lookup, and the same tool on a *non*-matching document tells you which clause excluded it. Between this and inspecting the analyzer's token output (12.1a), almost every relevance mystery is answerable in minutes. Most teams don't know the tool exists.

### Relevance is a measured activity or it isn't engineering

The structural problem with tuning is that the feedback signal is terrible. A change that helps the one complained-about query and harms fifty silent ones looks like a success.

The minimum viable fix is a **judgment list**: 30–50 real queries, each with the results a human says should be near the top. Run it in CI, report a score, and a relevance change becomes a diff you can argue about. The standard measures are precision@k (of the top 5, how many are good) and NDCG (position-weighted, so an improvement at rank 1 counts more than one at rank 9).

Where the queries come from matters. Take them from your logs, and take them from **both ends of the distribution**: the head, where volume is, and the tail, where the failures are. And include known failures — every escalated "search is broken" ticket should become a row in the file, which is the search equivalent of a regression test.

Beyond that sits behavioural measurement: click-through at position, queries with no clicks, queries with no results, and searches followed by immediate reformulation — that last one being the strongest available signal that search failed a user who didn't file a ticket. Then A/B testing, which is the only method that measures the thing you actually care about.

## When It's Appropriate

- **Search is how people find things in your product,** and the corpus is big enough that the answer isn't always visible in the first five results.
- **Queries are descriptive rather than navigational.** "Waterproof bluetooth speaker" needs ranking. "INV-2024-8871" needs a lookup, and no relevance work will improve it.
- **Vocabulary differs between your content and your users** — jargon, brand names, abbreviations. This is a synonym and analysis problem first, and it's the highest-return work in most catalogues.
- **Non-text signals genuinely predict a better answer**: recency for news and tickets, availability for commerce, an author's own documents in a workspace tool.
- **There's enough traffic to measure with.** A few hundred searches a day supports a judgment list; a few thousand supports click analysis; A/B testing needs considerably more.

## When It's Unnecessary or Overkill

- **Navigational search.** If most queries are exact names, ids, or codes, invest in exact matching, prefix matching, and a good "did you mean this specific record" jump. Ranking is irrelevant when there's one right answer.
- **Small corpora.** With 500 documents behind a couple of filters, users scan. Faceted filtering (12.3b) will do more for them than any scoring function.
- **Before fixing analysis.** Boosts applied on top of a missing synonym or a wrong analyzer are compensation for a defect, and they're load-bearing compensation — the day someone fixes the synonym, the boosts start misbehaving.
- **Learning-to-rank without data.** A ranking model needs judgments or click logs at volume. Adopted early, it's an unexplainable model trained on noise, and it replaces a query you could debug with one you can't.
- **Personalization as a first move.** It multiplies the cost of every subsequent debugging session and usually delivers less than a synonym file.
- **Head queries that would be better curated.** If 40 queries are 60% of traffic, pinning hand-picked results for those 40 beats any global tuning, and takes an afternoon. Algorithmic relevance is for the tail.

## Trade-offs

**Every boost is a regression somewhere.** Scoring is global; a change made for one query applies to all of them. Without a judgment set you are trading visible complaints for invisible ones.

**Tuned queries become unmaintainable.** A 120-line scoring query with historical boosts is code nobody will touch, and it outlives the person who wrote it. Fewer, justified signals beat many precise ones.

**Scoring costs latency in proportion to matches.** A script evaluated per matching document is fine over 500 hits and expensive over 500,000. Specialized scoring constructs exist mostly so the engine can skip documents that cannot reach the top N.

**Filter caching is not free memory.** Cached bitsets consume heap, and caching a high-cardinality filter (per-user, per-session) is pure waste with a cost.

**Judgment lists are subjective and go stale.** A human decided what "good" means; the catalogue then changed. They still beat nothing by a wide margin, but they encode one person's opinion as a build gate, and they need reviewing.

**Click data is biased.** People click what's at the top, so click-through rate partly measures your existing ranking. Correcting for position bias is a real discipline, and naive optimization against raw clicks reinforces whatever you already do.

**Business signals embed a policy.** Boosting popularity, margin, or recency is a product decision with winners and losers. Making it an implicit constant inside a query is how a business rule ends up undocumented in a JSON file.

**Personalized or freshness-weighted scores break caching and reproducibility together** — the two properties you most want while debugging.

## Alternatives

**Explicit sort.** Sometimes users don't want relevance; they want price ascending. Offering the sort is cheaper than approximating it in a scoring function, and a "sort by" control absorbs a surprising number of relevance complaints.

**Curation and pinning.** Hand-picked results for head queries. Unglamorous, immediately effective, and the standard practice in e-commerce for precisely the reason above.

**Reranking the top N.** Retrieve 100 cheaply with a simple query, then reorder those 100 with something expensive — a model, a cross-encoder, business rules, an LLM. The cost is bounded because it never touches the full corpus, and it cleanly separates "find candidates" from "order them well." This is the shape most modern relevance systems converge on.

**Learning to rank.** Train a model on judgments or click logs and let it combine signals instead of hand-tuning them. The right answer at sufficient scale, with the usual costs: a training pipeline, drift, and a ranking you can no longer explain to an account manager.

**Hybrid lexical + vector retrieval**, fused by reciprocal rank fusion or similar. This is the leading answer to the vocabulary-mismatch failure in *The Problem* — *bluetooth* versus *wireless* — without maintaining a synonym file by hand. It was introduced in 12.1a and belongs to Module 39.4; the note here is only that it replaces neither the filtering half nor the business-signal half of this article.

**Fixing analysis instead.** Repeated because it's the most common right answer: a synonym list, a better stemmer, a field indexed a second way. Cheaper than scoring work and it fixes the cause.

## How to Achieve It

**L0 — one `match` against a catch-all field.** Correct starting point; don't skip it.

**L1 — split filter context from query context.** An afternoon. Free latency, correct scores, and it's the precondition for every later step being interpretable.

**L2 — a deliberate field query**: the right multi-field strategy for your content, three or four modest boosts, and `minimum_should_match`. Stop here and stay here if search is working.

**L3 — a judgment list in CI.** 30 queries from your logs, expected results, precision@k printed on every pull request. The signal that you need it: the second time a relevance fix caused a regression someone else reported.

**L4 — business signals,** added one at a time, each justified by a movement in the judgment score rather than by one example. Bounded multipliers, not unbounded additions.

**L5 — behavioural measurement and A/B testing**, and only then reranking or learning to rank. The signal for L5 is that your judgment set has stopped disagreeing with your intuition — meaning it's now measuring your own assumptions back to you, and you need data from users.

Notice that L3 comes before L4. Adding signals without measurement is how *The Problem* happened.

## Implementation

TypeScript. The query is JSON in any language; the part worth writing in code is the harness at the end.

**The query, with the two halves separated:**

```ts
const results = await es.search({
  index: "products",
  query: {
    bool: {
      filter: [                                   // no score, cached
        { term:  { tenant_id: tenantId } },
        { term:  { in_stock: true } },
        { range: { created_at: { gte: "now-1y/d" } } }   // rounded → cacheable
      ],
      must: [
        {
          multi_match: {
            query: q,
            type: "cross_fields",                 // terms may span fields
            fields: ["title^3", "brand^2", "tags", "description"],
            minimum_should_match: "75%"
          }
        }
      ],
      should: [                                   // promotes, never excludes
        { rank_feature: { field: "popularity", boost: 1.4 } }
      ]
    }
  },
  size: 20
});
```

Three things are deliberate. The date range is rounded to the day, so every request that day produces an identical filter and the engine can cache it. The boosts are small and ordinal. `rank_feature` sits in `should` and saturates by design — a product with 40,000 reviews scores meaningfully but not unboundedly higher than one with 400, and the engine can skip documents that cannot reach the top 20, which a script could not.

The failure hiding here is the `should`/`must` interaction from *How It Works*: delete the `must` clause for an empty query — a reasonable-looking change, since an empty search should show everything — and the `rank_feature` in `should` becomes the only matching requirement. Empty searches now return only documents that have a popularity value. Nothing errors; the result set is just quietly incomplete.

**Asking why:**

```ts
const { explanation } = await es.explain({
  index: "products", id: "sku-4471",
  query: { match: { title: "wireless keyboard" } }
});
```

Run this against the document that *should* have won and the one that did. The difference is almost always visible immediately, and it's usually not the thing you assumed.

**The harness that makes the rest of it engineering:**

```ts
// judgments.json — real queries from logs, expected ids, graded 0–3
// [{ "q": "wireless keyboard", "relevant": { "sku-4471": 3, "sku-9120": 2 } }, …]

function ndcgAt(k: number, ranked: string[], grades: Record<string, number>) {
  const dcg = ranked.slice(0, k)
    .reduce((s, id, i) => s + (grades[id] ?? 0) / Math.log2(i + 2), 0);
  const ideal = Object.values(grades).sort((a, b) => b - a)
    .slice(0, k)
    .reduce((s, g, i) => s + g / Math.log2(i + 2), 0);
  return ideal === 0 ? 0 : dcg / ideal;
}

for (const { q, relevant } of judgments) {
  const ids = (await search(q)).hits.hits.map(h => h._id);
  report(q, ndcgAt(10, ids, relevant));
}
```

Twenty lines, and it changes the nature of the work: a boost change now produces a number that went up or down and a list of which queries moved. Print the per-query deltas, not just the average — the average hides the case where one query improved by a lot and six regressed slightly, which is the exact trade you keep making accidentally.

The thing to resist is adding a threshold that fails the build below some NDCG value too early. Early on the number is noisy and the list is small; its value is the *comparison between two runs*, not its absolute level.

## Further Reading

- **_Relevant Search_, Doug Turnbull & John Berryman.** The book this article compresses. Signal design, field strategies, the argument for treating relevance as an engineering discipline with feedback, and the clearest explanation of why boosts behave unintuitively.
- **Elasticsearch documentation: "Query DSL," specifically the `bool` query, `multi_match` types, and "Query and filter context."** The `multi_match` page contains the *Will Smith* worked example and is worth reading in full once.
- **Elasticsearch "Function score query," "Script score query," and the `rank_feature` field type.** Read `rank_feature` before writing a script; it covers the common case faster and with better skipping behaviour.
- **_Introduction to Information Retrieval_, Manning et al., chapters 8 and 11.** Evaluation done properly: precision, recall, NDCG, judgment pools, and why relevance measurement is hard rather than merely tedious.
- **Joachims et al., "Accurately Interpreting Clickthrough Data as Implicit Feedback."** The paper behind position bias — read before optimizing against click logs, because the naive version optimizes for your existing ranking.
- **Elasticsearch's Ranking Evaluation API and the Elasticsearch Learning to Rank plugin documentation.** The judgment harness above, as a built-in, and the path onward to LTR when there's data to support it.
- **Quepid (quepid.com)**, an open-source relevance testing workbench. Useful mainly because it makes judgment collection something non-engineers can do, which is where the domain knowledge lives.

A **Python** sibling would be worth writing, and not as a translation. Relevance work at L4 and beyond is largely offline data work — parsing query logs, building judgment sets from click streams with position-bias correction, computing NDCG across thousands of queries, training and evaluating an LTR model. That workflow is a notebook and a dataframe, not an application, and the ecosystem around it (the `rank_eval` tooling, LightGBM's LambdaMART implementation, the standard feature-logging pattern) has no real equivalent elsewhere. It would cover the measurement half properly, where this article only opens the door. Not yet written.

---

The habit: **separate the clauses that decide membership from the clauses that decide order, and never change the second kind without a number that tells you what happened.** The first half is a correctness and performance property you can get right permanently. The second half is never finished — which is exactly why it needs a test harness rather than a tuning session, and why the most valuable artifact in a mature search system isn't the query, it's the file of queries someone decided the right answers to.
