# Autocomplete and Typo Tolerance

_Module 12.3c — Search Functionality_

## The Problem

Search works. Somebody asks for search-as-you-type, and the obvious implementation is to fire the existing query on every keystroke and show the top five hits in a dropdown.

Here's what a user typing `logitec keybord` actually experiences.

**`l`, `lo`, `log` — nothing.** Not slow, not wrong: empty. The index holds whole terms, and `log` is not a term. The full-text machinery from 12.1a is doing exactly what it was built to do — match words — and a prefix of a word isn't one. The box looks broken for the first several keystrokes, which is the entire period during which autocomplete is supposed to be useful.

**`logitec` — still nothing,** because it's a typo and terms match exactly or not at all.

**Somewhere around `logitec keybo`, the dropdown flickers and then shows results for `logitec key`.** Six requests are in flight; they return out of order; the last one to arrive wins. This is a race condition in the browser, not a search problem, and it will survive every backend fix anyone applies.

**And the load graph.** A fast typist produces six or seven requests per second. The autocomplete endpoint is now doing ten times the query volume of search itself, against the same cluster, with a latency budget of about 100ms instead of 500ms — because a dropdown that arrives after you've finished typing never existed.

The first instinct is to patch the query: add a wildcard, turn on fuzziness. Both make things worse in characteristic ways — a leading wildcard forces a scan of the entire term dictionary, and global fuzziness makes `cat` match `car`, `can`, `cap`, `bat`, and `cot` in ordinary searches where nobody asked for it.

The patches fail for the same reason the patches in 12.1a failed: wrong question. **Search ranks documents against a query the user has finished writing. Autocomplete predicts what the user is about to write.** Different input, different success criterion, different latency budget, and — this is the part that surprises people — often a different *kind of answer*.

## What It Is

Three things get displayed in a dropdown under a search box, and they are not the same feature:

```
  what it returns          example                       built from
  ──────────────────       ───────────────────────       ────────────────────────
  query completion         "wireless key…"               past queries, or index
                           → "wireless keyboard"           terms; a dictionary

  instant results          "wireless key…"               a real search, run per
                           → [K380 product card]           keystroke

  entity lookup            "acme ho…"                    prefix match on a name
                           → jump to Acme Holdings         field; navigational
```

Query completion helps a user who doesn't know your vocabulary. Instant results skip a page load for a user who does. Entity lookup is a jump-to-record and isn't really search at all. Most teams build one of the three, then field complaints that it doesn't do the job of the other two.

**Typo tolerance** is the separate, orthogonal capability of matching terms that differ from what was typed. It applies to all three, and it's also where most of the damage gets done, because the natural implementation — widen everything — is the wrong one.

One neighbour to name and set aside: **"did you mean"** is post-hoc. It runs *after* a submitted search returned little or nothing, uses corpus statistics to pick a single likely correction, and offers it explicitly. That's a different mechanism from widening a query as it's typed, and it's covered at the end.

## Recognizing the Problem

- The dropdown is empty until the user completes a word.
- Suggestions flicker, or settle on results for a prefix the user typed two keystrokes ago.
- A leading-wildcard query (`*term*`) exists in the codebase.
- The autocomplete endpoint is the highest-volume query in your cluster.
- One transposed letter returns zero results, and users silently retype instead of reporting it.
- Fuzziness was enabled globally, and short queries now match half the index.
- Suggestions lead to pages with no results.
- The dropdown shows another tenant's terms, or a phrase a user typed that shouldn't be repeated back to anyone.
- `LIKE 'term%'` is not using the index, and nobody knows why.
- Accented input finds nothing, and this was filed as three separate bugs.

## How It Works

### The last-term rule

The structural insight, and the one that fixes the most:

```
  "wireless key"   →   term(wireless)  AND  prefix(key)
```

Everything the user has finished typing is a complete term. Only the final fragment is a prefix. Applying prefix semantics to *all* the words is wasteful and imprecise; applying them to none is the empty dropdown. Engines expose this directly — Elasticsearch's `match_bool_prefix` does exactly the above — and it's the correct default shape for both query completion and instant results.

### Four ways to match a prefix

**Query-time prefix matching.** Walk the term dictionary from the given prefix. No index cost, no extra storage, and the cost scales inversely with prefix length: `k` expands to an enormous set of terms, `keyboa` to a handful. Perfectly good for entity lookup over a low-cardinality field, and the reason minimum prefix lengths exist.

**Index-time expansion (edge n-grams).** Generate every prefix at write time:

```
  index time:  "Keyboard"  →  k  ke  key  keyb  keybo  keyboa  keyboar  keyboard
  query time:  "keyb"      →  keyb                        ← one term, exact hit
```

Now the lookup is an ordinary term match, which is as fast as this gets. **The asymmetry is the whole trick**, and it's where the classic bug lives: the field's index-time analyzer generates n-grams, and its search-time analyzer must *not*. If the query is also n-grammed, `keyb` becomes `k`, `ke`, `key`, `keyb` and matches anything starting with `k` — precision collapses, and the symptom ("my autocomplete suggests everything") looks nothing like its cause. The two analyzers are configured separately on purpose. Cost: a ten-character word becomes eight or nine tokens, so the field's index inflates substantially.

**Purpose-built suggesters.** A finite-state transducer held in memory, mapping prefixes to weighted completions in microseconds. This is what a dedicated completion suggester is. Very fast, supports weights and a limited form of filtering, and it comes with real constraints: it's memory-resident, it's built at index time, arbitrary filters generally can't be applied to it, and deleted documents can linger in results until segments merge. Excellent for a curated query dictionary; awkward the moment suggestions must respect per-user permissions.

**Infix matching.** Users often expect `board` to find `Keyboard`, and none of the above does — edge n-grams grow from the start of the token. The options are to index n-grams from every position (expensive, and the index size grows quadratically with token length), to index each word of a name as its own suggestion entry so any word can start a match, or to accept that mid-word matching is a substring problem and use trigrams. Purpose-built field types for this (Elasticsearch's `search_as_you_type`) combine prefix n-grams with shingles of adjacent words, which covers multi-word phrases well and is the right starting point before hand-rolling an analyzer.

### Typo tolerance, and why "just turn on fuzzy" fails

Fuzzy matching is **edit distance**: how many single-character insertions, deletions, substitutions — and, in the Damerau variant, transpositions — separate two strings. `keybord` is one deletion from `keyboard`. It's implemented by intersecting a Levenshtein automaton with the term dictionary, which is why it's viable at all; nothing is compared against every term.

The failure is that edit distance is meaningless without length context:

```
  allow 1 edit on "cat"       →  car can cap cot bat hat sat oat …
  allow 1 edit on "keyboard"  →  keybord keyboad keyboards
```

Hence the standard automatic policy: **zero edits below three characters, one edit up to five, two above.** Never a flat setting.

Three parameters do most of the remaining work:

- **`prefix_length`** — require the first character or two to match exactly. People rarely mistype the first letter, and this is simultaneously the largest precision win and the largest performance win available, because it collapses the candidate term set immediately.
- **`max_expansions`** — cap how many matched terms a fuzzy match may generate. Without it, one short fuzzy term can expand into a query with hundreds of clauses.
- **Score the exact match higher.** The usual shape is an exact clause and a fuzzy clause in the same boolean, with the exact one boosted, so typo tolerance adds a fallback rather than flattening the ordering. A fuzzy hit should never outrank a literal one.

And the two places to keep fuzziness away from entirely: **identifiers** (an order number one edit away is a different, real order — returning it is worse than returning nothing) and **very short queries**, which the automatic policy already handles if you let it.

### Not every typo is a typo

Before reaching for edit distance, check whether the mismatch is actually a normalization failure. `Müller` versus `Muller`, `CAFÉ` versus `cafe`, a curly apostrophe versus a straight one, two visually identical Unicode strings with different code-point sequences. Accent folding and Unicode normalization in the analyzer fix all of these exactly, at zero query cost, with no precision loss. A large fraction of what gets attributed to typos is this, and fuzziness is a far worse tool for it.

For **people's names** specifically, edit distance is also the wrong model. `Smith`/`Smyth` and `Schmidt`/`Schmitt` are spelling variants of the same sound, and phonetic analysis — Metaphone, Double Metaphone, Beider-Morse — encodes a term by how it's pronounced and matches on that. It's a separate analyzer on a separate subfield, and for a customer or contact search it outperforms fuzziness comfortably.

### "Did you mean"

The post-submission sibling. When a search returns zero or very few results, compare the query's terms against the corpus dictionary and propose the most likely correction, weighted by how common each candidate term is in your content. Per-term suggesters do this word by word; phrase suggesters score whole candidate phrases against a language model, which avoids proposing a correction that's individually plausible and collectively nonsense.

The interaction convention that works: for a high-confidence correction, run the corrected search and say *showing results for X — search instead for Y*. For a low-confidence one, offer the suggestion and change nothing. Silently rewriting a query the user is confident about is deeply annoying, and the escape hatch is what makes auto-correction acceptable.

### Where suggestions come from

For query completion, the dictionary is a content decision, not a technical one, and it's the difference between a good feature and a strange one.

- **Index terms** — always valid and sometimes bizarre, since your content contains words nobody would search for.
- **Past successful queries** — much better. Real phrasing, weighted by real frequency, and filterable to queries that ended in a click, which automatically excludes the ones that failed. This is the source most mature systems use.
- **Curated entries** for head terms and merchandising, sitting above the generated ones.
- **Entity names** for the navigational dropdown.

Query logs come with a safety requirement that is easy to overlook and embarrassing to discover late: **you are repeating user-typed text back to other users.** People type email addresses, order numbers, their own names, competitors' names, and abuse into search boxes. A suggestion dictionary built from logs needs a frequency threshold measured in *distinct users* rather than hits, a block list, a filter for anything shaped like an identifier or an address, and tenant scoping — the same boundary as everything else in Module 12, arriving at one more place people forget to check.

### The client is half the system

Three client-side behaviours matter as much as any query:

**Debounce.** Wait 100–150ms after the last keystroke. A fast typist's seven requests per second collapse to one or two, and the user notices nothing, because they weren't reading the dropdown mid-word anyway.

**Minimum length.** Don't query on one character. It's the most expensive prefix, the least informative, and the results are noise.

**Sequencing.** Responses arrive out of order. Either abort the in-flight request when a new one starts, or tag each request and discard any response older than the newest one already rendered — ideally both. This is the flicker in *The Problem*, it is not fixable on the server, and it is the single most common bug in shipped autocomplete.

Then caching. Prefix queries are unusually cacheable: the distribution of typed prefixes has a very fat head, and short prefixes — the expensive ones — are exactly the most repeated. A modest in-memory cache in front of the suggestion endpoint absorbs a large share of the traffic. And for small dictionaries, the strongest option is to skip the network: ship ten thousand entries to the browser and match locally, at zero latency and zero server cost.

## When It's Appropriate

- **Users don't know your vocabulary.** Query completion teaches them what's searchable, which is its underrated function.
- **Long or awkward-to-type identifiers with known names** — customers, projects, files, SKUs. Entity lookup here is one of the highest-value, lowest-effort features in an internal tool.
- **Mobile**, where every keystroke is expensive and typo rates are several times higher than on a keyboard.
- **Large catalogues** where the user has a vague target and needs to be steered toward a productive query.
- **Any search where zero-result rate is measurably high** and the cause is spelling or phrasing rather than missing content.

## When It's Unnecessary or Overkill

- **Dozens of options, not thousands.** That's a select element, or a client-side filter over a loaded list. Don't build a search feature for it.
- **Before the underlying search is good.** Autocomplete over a badly analyzed index delivers bad results faster and more often. Fix 12.1a first.
- **Fuzziness on identifier fields.** Repeated because it's the one that causes real damage rather than annoyance.
- **Instant results when the result card is expensive to render.** If each suggestion needs three joins and an image, per-keystroke execution is the wrong pattern; complete the query instead and let the user press Enter.
- **Query-log suggestions with low traffic.** A few hundred searches a day produces a dictionary of one-off queries, including one-off queries containing personal data. Below a real volume threshold, use index terms or a curated list.
- **Suggestions that can't be filtered to the user's permissions.** If the only fast mechanism available can't apply your tenant filter, the honest answer is a slower mechanism, not a leak.

## Trade-offs

**Index-time expansion costs storage and write throughput.** Edge n-grams multiply token count per field; full n-grams multiply it much harder. This is paid on every write and every reindex.

**Suggesters cost memory, permanently.** An FST lives in heap, sized by dictionary, and competes with everything else the node is doing.

**Request volume is an order of magnitude above search.** Capacity planning, rate limiting, and — most importantly — isolation: autocomplete should not be able to degrade the search it's attached to. A separate endpoint, and often a separate index, is what makes that enforceable.

**Fuzziness trades precision for recall, non-linearly.** Each additional allowed edit expands the candidate set dramatically, and the results that arrive are, by construction, the ones that matched less well.

**Suggestion dictionaries go stale** and need a rebuild job, with its own schedule, failure modes, and the possibility of serving suggestions for content that no longer exists.

**Autocomplete shapes the behaviour it learns from.** Users click what you suggest; those clicks become query-log frequency; that frequency drives suggestions. It's the same feedback loop as popularity ranking in 12.3a, and it needs the same counterweight, or your suggestions slowly converge on a small set and the tail becomes invisible.

**A suggestion that leads to zero results is worse than no suggestion.** It's 12.3b's dead-end principle in a different control: the dropdown is a promise about what happens if you click it. Suggestions should be generated from, or validated against, things that actually match.

**The interaction is harder than the query.** Keyboard navigation, screen-reader announcements, mobile keyboards covering the dropdown, and what Enter does when an item is highlighted versus not. None of it is search work, all of it is required.

## Alternatives

**A client-side index.** For under roughly ten thousand entries, ship the dictionary and match in the browser with a small library. Zero latency, zero server load, offline-capable, no race conditions. Genuinely the best answer more often than it gets chosen.

**Trigram matching in a relational database.** `pg_trgm` with a GIN index gives you substring matching *and* similarity-based typo tolerance in one structure, which is a good fit for name and SKU lookup and needs no second system. For pure prefix lookup, an ordinary B-tree on a lowercased name column serves `LIKE 'term%'` well — with one gotcha that wastes a lot of people's afternoons: in any non-C locale the index must be declared with a pattern-matching operator class, or the planner will ignore it and you'll conclude, wrongly, that prefix search needs a search engine.

**Hosted instant-search products** (Algolia, Typesense, Meilisearch). Worth being straightforward here: prefix matching and typo tolerance are their default behaviour rather than something you assemble from analyzers, and their latency budgets were designed for this. If autocomplete is the primary interaction in your product rather than an accessory to it, they'll get you further faster than tuning a general-purpose engine.

**No autocomplete, plus good "did you mean."** Cheaper, far simpler, and handles the actual failure — user typed something that didn't work — at the moment it happens.

**Structured suggestions.** Instead of completing text, suggest a *scoped* query: `keyboard in Electronics`, `invoices from Acme`. Converts vague input into a filter, which hands the user to 12.3b's facets with the work already done.

**Semantic suggestion** via embeddings, which can propose related queries rather than textual completions. Complementary, slower, and covered in Module 39.4.

## How to Achieve It

**L0 — nothing, or a client-side filter over a loaded list.** Correct for small option sets; stop here if that's what you have.

**L1 — decide which of the three dropdowns you're building.** Free, takes a meeting, and prevents the most common failure in this whole area. Write it down: are we completing queries, showing results, or jumping to records?

**L2 — prefix matching done properly plus the client-side three.** The last-term rule, a purpose-built field type or an edge-n-gram analyzer with a *different* search analyzer, and debounce, minimum length, and request sequencing on the client. This is the step that makes it feel like a real product.

**L3 — normalization, then typo tolerance.** Accent folding and Unicode normalization first, because they're free and exact. Then automatic fuzziness with a prefix length and an exact-match boost. Phonetic subfields if you're matching people's names.

**L4 — a real suggestion dictionary.** Built from query logs, thresholded by distinct users, filtered for identifiers and abuse, scoped per tenant, rebuilt on a schedule, with curated entries layered on top.

**L5 — isolation and measurement.** A separate endpoint and index, a cache in front, rate limiting, and metrics: suggestion click-through, the share of searches preceded by an accepted suggestion, zero-result rate for suggested queries, and how often typing continues *past* a suggestion that should have been accepted.

The ordering matters in one place particularly: L3 comes after L2 because fuzziness applied to a prefix problem produces nonsense, and teams that skip L2 usually conclude that typo tolerance doesn't work.

## Implementation

TypeScript. The mapping and the query are short; the client code is where the bug lives.

**The field, with the asymmetry made explicit:**

```ts
await es.indices.create({
  index: "suggestions_v1",
  settings: {
    analysis: {
      analyzer: {
        prefix_index: {                       // WRITE side: expand
          tokenizer: "standard",
          filter: ["lowercase", "asciifolding", "edge_ngram_2_20"]
        },
        prefix_search: {                      // READ side: do NOT expand
          tokenizer: "standard",
          filter: ["lowercase", "asciifolding"]
        }
      },
      filter: {
        edge_ngram_2_20: { type: "edge_ngram", min_gram: 2, max_gram: 20 }
      }
    }
  },
  mappings: {
    dynamic: "strict",
    properties: {
      tenant_id: { type: "keyword" },
      weight:    { type: "rank_feature" },    // query frequency, saturating
      text: {
        type: "text",
        analyzer: "prefix_index",
        search_analyzer: "prefix_search",     // ← the whole trick is this line
        fields: { exact: { type: "keyword" } }
      }
    }
  }
});
```

Delete `search_analyzer` and everything still works, in the sense that it returns results — just the wrong ones, with no error, for reasons that are invisible in the query. It's worth adding a test that asserts `key` matches `keyboard` and does *not* match `kitchen`.

`asciifolding` appears in both analyzers, which is not optional: normalization applied on only one side is the same class of mismatch as the analyzer asymmetry, in the opposite direction.

**The query**, combining the last-term rule with a bounded typo tolerance:

```ts
const res = await es.search({
  index: "suggestions",
  size: 8,
  query: {
    bool: {
      filter: [{ term: { tenant_id: tenantId } }],   // suggestions are scoped too
      should: [
        { match_bool_prefix: { text: { query: input, boost: 3 } } },
        { match: { text: { query: input,
                           fuzziness: "AUTO",        // 0 / 1 / 2 by term length
                           prefix_length: 2,         // first two chars exact
                           max_expansions: 20 } } },
        { rank_feature: { field: "weight", boost: 1.3 } }
      ],
      minimum_should_match: 1
    }
  }
});
```

`prefix_length: 2` is doing more here than it looks. It's the difference between intersecting the Levenshtein automaton with the whole term dictionary and intersecting it with the small branch under two fixed characters — a precision decision and a latency decision at once.

The `boost: 3` on the exact-prefix clause is what keeps typo tolerance as a fallback. Remove it and a fuzzy match can outrank a literal one, which users read as the box ignoring what they typed.

**The client, which is where the flicker actually lives:**

```ts
let controller: AbortController | null = null;
let latest = 0;

const onInput = debounce(async (input: string) => {
  if (input.length < 2) return setSuggestions([]);

  controller?.abort();                       // cancel the previous request
  controller = new AbortController();
  const seq = ++latest;                      // and guard against late arrivals

  try {
    const data = await fetchSuggestions(input, { signal: controller.signal });
    if (seq === latest) setSuggestions(data);   // ignore anything superseded
  } catch (e) {
    if ((e as Error).name !== "AbortError") throw e;
  }
}, 120);
```

Both guards are present deliberately. Abort stops the wasted work; the sequence check handles the response that was already in transit when abort was called, which is exactly the case that produces the stale dropdown. Implementing only one of the two fixes the bug in development, where the network is instant, and leaves it in production, where it isn't.

## Further Reading

- **Elasticsearch documentation: the `search_as_you_type` field type, `match_bool_prefix`, the `edge_ngram` token filter, and the Suggesters page** (completion, term, and phrase). Read the `edge_ngram` page for its explicit warning about search-time analysis — it's the documented version of the asymmetry above.
- **Elasticsearch's "Fuzzy query" reference,** for what `AUTO` resolves to and how `prefix_length` and `max_expansions` bound the expansion.
- **Schulz & Mihov, "Fast String Correction with Levenshtein-Automata."** The algorithm that makes fuzzy matching feasible against a term dictionary; worth reading once to stop thinking of it as a scan.
- **Peter Norvig, "How to Write a Spelling Corrector."** Twenty lines of Python and the clearest explanation anywhere of why correction is a probability problem — candidate generation weighted by how common each word actually is.
- **Lucene's `FST` package documentation and Mike McCandless's blog posts on finite-state automata in Lucene.** What a completion suggester *is*, and why it's measured in microseconds.
- **PostgreSQL documentation: `pg_trgm`, and the "Operator Classes and Operator Families" section on `text_pattern_ops`.** The second one is the fix for prefix queries that mysteriously ignore their index.
- **Algolia's and Typesense's documentation on typo tolerance.** Regardless of whether you use either, both are unusually clear public statements of a complete typo-tolerance policy — per-length thresholds, which fields tolerate typos, how exact matches are prioritized — and make a good checklist against your own.

A **Go** sibling would be worth writing, and would reveal the thing the cluster keeps hidden. A suggestion service built around an in-process trie or FST — loaded at startup from a generated dictionary, swapped atomically on rebuild, served in microseconds with no network hop — makes the real trade-offs of the completion-suggester approach tangible: memory is a number you can see, rebuild is a job you wrote, and the reason arbitrary permission filters are awkward becomes obvious the moment you try to add one to a prefix walk. It also lands in a place Go is genuinely good at, since the whole service is a concurrent read path over an immutable structure. Not yet written.

---

The habit: **the moment a feature's success criterion changes, stop reusing the machinery even when it appears to fit.** Search and autocomplete share an index, a query language, and a team, and they have different inputs, different latency budgets, different failure modes, and different definitions of a good answer. Most of the pain in this article came from the reasonable-looking assumption that autocomplete was search with a shorter string — and the same assumption is waiting in every system where a read path gets reused for a workload it wasn't measured against.

That closes the querying half of Module 12. What remains is the half that only shows up under load: index and query performance, caching, deep pagination, and how to tell whether any of it is working.
