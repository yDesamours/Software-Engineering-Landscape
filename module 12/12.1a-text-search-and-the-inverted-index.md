# Text Search and the Inverted Index

_Module 12.1a — Search Functionality_

## The Problem

A help center with 40,000 articles. The search box was built the obvious way, because it's the way that works on day one:

```sql
SELECT id, title
FROM articles
WHERE title ILIKE '%' || $1 || '%'
   OR body  ILIKE '%' || $1 || '%'
LIMIT 20;
```

It ships. Then support starts forwarding tickets, and they arrive in three flavours that look unrelated.

**"I searched for `resetting password` and got nothing."** The article is titled *How to reset your password*. The phrase `resetting password` does not occur in it — not in that order, not in those word forms, not anywhere. The query asked whether one exact byte sequence appears inside another. The user asked a question.

**"Searching for `invoice` takes nine seconds."** `ILIKE '%x%'` has no usable prefix, so no B-tree index applies; the database reads every row and scans every byte of every `body`. 40,000 articles of prose is a few hundred megabytes, and the cost grows exactly in step with the corpus. The search box gets slower every week that content is added, which is to say it gets slower the more useful the product becomes.

**"The right article was on page three."** Rows come back in whatever order the scan produced. A 40-word release note that mentions *billing* once ranks identically to the 2,000-word billing guide, and `LIMIT 20` means "twenty arbitrary matches," not "the twenty best."

So the patches start. Split the query on whitespace and `AND` the `ILIKE`s together, so multi-word queries stop returning nothing. Wrap everything in `unaccent()` after a customer named Müller can't find himself. Add `ORDER BY (title ILIKE $1) DESC, created_at DESC` to get something vaguely relevance-shaped. Six months later that `WHERE` clause is forty lines, still slow, and still can't find *How to reset your password*.

The patches fail because they're all corrections to the wrong question. A `WHERE` clause answers exactly one thing: **does this byte sequence occur inside that byte sequence.** Search needs three answers, and the byte comparison provides none of them:

1. **What counts as the same word?** `resetting` and `reset`. `Müller` and `Muller`. `INVOICES` and `invoice`. These are different bytes and the same search term.
2. **Which documents contain those terms** — found without reading the documents that don't.
3. **Which of the matches is the best answer**, since there are 300 of them and the user will look at four.

Each needs its own machinery. The second one is the most visible, because it's a different data structure entirely. What you have is a *forward* index — a table that maps a row to its text:

```
  row 17  →  "How to reset your password"
  row 18  →  "Billing FAQ"
  row 19  →  "Reset a team member's password"
```

To answer "which rows mention passwords," you must visit all of them. What you need is the map turned inside out:

```
  password  →  [17, 19, 402, 1150, …]
  reset     →  [17, 19, 88, …]
  billing   →  [18, 220, …]
```

Now the answer is a lookup, then an intersection of two sorted lists, and nothing else in the table was touched.

## What It Is

That inside-out map is an **inverted index**, and the whole approach is **full-text search**: at write time, run the text through a normalizing pipeline that turns it into a list of terms; store the term → document mapping; at query time, run the query through the *same* pipeline and score the documents that match.

Three moving parts, matching the three questions above — **analysis**, **the index**, **ranking**. Nearly every real search bug traces back to exactly one of them, which is why it's worth being able to name which one.

The neighbor to disambiguate immediately, because it's the one people substitute by accident: full-text search is **not** substring matching. It finds *words*, so it will never find `port` inside `airport` — and that's deliberate, not a gap. If what you actually need is "rows containing this character sequence anywhere," that's a different tool (trigram indexes, below), and reaching for full-text search will quietly disappoint you.

## Recognizing the Problem

- Your search clause contains `ILIKE '%' || $1 || '%'`, and `EXPLAIN` says `Seq Scan`.
- Search latency grows with the size of the table rather than the size of the result.
- Users report "it didn't find X," and X exists with a different word ending, case, or accent.
- Results are ordered by `created_at`, or by nothing, because nobody had a better idea.
- Someone has hand-written a `CASE` expression to approximate relevance.
- A two-word query returns everything (`OR`) or nothing (`AND` on the literal phrase).
- Plurals, accents, and hyphenation arrive as individual bug tickets over months.
- You fetch 5,000 candidate rows and rank them in application code.
- The product wants "search should handle typos" and there is nowhere to put that.

## How It Works

### Analysis: deciding what a term is

Text goes through a pipeline before anything is stored. The stages have different names in different systems, but the shape is universal:

```
  raw text
     │  character filters      strip HTML, fold accents, normalize unicode
     ▼
  "the reports are not loading in chrome"
     │  tokenizer              split into candidate tokens
     ▼
  [the] [reports] [are] [not] [loading] [in] [chrome]
     │  token filters          lowercase, drop stopwords, stem, add synonyms
     ▼
  [report] [load] [chrome]
```

Three of those filters do most of the work:

**Stemming** reduces word forms to a common root: `loading`, `loaded`, `loads` → `load`. It's a crude algorithmic chop (the Porter stemmer and its descendants), not a dictionary lookup, so the root is often not a word — `universities` → `univers`. Lemmatization is the dictionary-based alternative: slower, language-specific, more accurate, and available for fewer languages. Stemming is what makes `resetting password` find *How to reset your password*.

**Stopword removal** drops terms that appear nearly everywhere and therefore distinguish nothing: `the`, `is`, `not`, `in`. It shrinks the index and stops common words from dragging in the whole corpus.

**Synonyms** are an explicit mapping you maintain: `invoice → bill`, `k8s → kubernetes`, your product's old feature name → its new one. This is where domain vocabulary gets encoded, and it's usually the single highest-return piece of relevance work in a product with jargon.

All of this is **language-specific**. An English stemmer applied to German text produces noise. A corpus with mixed languages needs either language detection at index time, or one field per language, or a decision to stem nothing and accept it.

**The rule that causes the most confusion in practice:** query text must go through the *same* analysis as document text. The index holds `load`, so a query for `loading` only matches if the query is stemmed too. Analyzer mismatch between write and read is the classic "why does this return zero results" bug, and it's invisible — both sides look correct in isolation.

### The index: postings lists

For each term, store the list of documents containing it, usually with positions:

```
  term      postings (doc:positions)
  ───────────────────────────────────────────
  password  17:4  19:6  402:1,88  1150:12
  reset     17:2  19:1  88:30
  billing   18:1  220:3,9,44
```

Lists are kept sorted by document id, so `password AND reset` is a merge of two sorted lists — linear in the size of the two lists, not the corpus. Positions are what make phrase queries possible: `"reset password"` matches doc 17 only if the two terms appear at adjacent positions. Without positions, a phrase query degrades into an `AND`.

Everything after this point is compression and cleverness — skip lists to jump ahead during merges, delta encoding of document ids, term dictionaries stored as finite-state transducers — but the mechanism is that table.

### Ranking: which match is best

Boolean matching produces a set. Users need an ordering, and the ordering is where search stops being a data-structure problem and becomes a judgment problem.

The intuition everything is built on is two observations:

- A term that appears **often in this document** probably matters to it. (Term frequency.)
- A term that appears **in almost every document** tells you almost nothing. (Inverse document frequency — `the` is worthless, `phosphorylation` is decisive.)

Multiply them and you have TF-IDF. The scoring function actually used by Lucene, Elasticsearch, OpenSearch, and most modern engines is **BM25**, which is TF-IDF with two corrections that matter a great deal in practice:

- **Saturation.** The tenth occurrence of `invoice` adds much less than the second. Raw TF lets a keyword-stuffed page win; BM25 flattens out.
- **Length normalization.** A match in a 20-word title is stronger evidence than a match in a 5,000-word manual, so scores are adjusted for document length.

On top of the base score, engines let you **boost fields**: a title match counts for more than a body match. That single lever fixes a surprising share of "the obvious answer isn't first" complaints.

One property worth internalizing before you pick an implementation: **IDF is a corpus-wide statistic.** It requires knowing how many documents contain a term. An engine that maintains global term statistics can do this; a ranking function that only sees one row's terms cannot — which is exactly the limitation of Postgres's built-in ranking, discussed below.

### The index is derived

Everything above describes a second representation of data whose home is somewhere else. It has to be built from the source, rebuilt when the analysis changes, and kept in sync as rows change — which is its own problem with its own failure modes (dual writes, phantom documents, lost updates). Module 6 covers that machinery in the polyglot-persistence article; the transactional outbox is the durable answer. This article assumes the documents get there and concerns itself with what happens once they do.

## When It's Appropriate

- **A corpus of prose that people query in their own words** — articles, tickets, messages, product descriptions, comments — from a few thousand documents upward.
- **The right answer must be near the top,** not merely present in a set of 400 matches.
- **Word forms and vocabulary vary** between how content is written and how users type: plural/singular, verb forms, accents, jargon and its synonyms.
- **You need phrase queries, field weighting, or per-language handling** — none of which a `WHERE` clause can express.
- **Specifically for the database's built-in full-text search:** up to roughly the low millions of documents, one or two languages, modest ranking requirements, and queries that are already scoped by a tenant or an owner. This covers far more products than its reputation suggests, and it costs you no new system, no new backup, and no new consistency boundary.

## When It's Unnecessary or Overkill

- **A few thousand rows.** Loading them into memory and filtering in the application is faster than any index and takes an afternoon. A documentation site can ship its whole search index to the browser as a static file.
- **Identifier lookup.** Order numbers, SKUs, email addresses, usernames, API keys. These want exact or prefix matching on a B-tree. Worse, stemming actively corrupts them: `INV-2024-001` is not a sentence, and analyzing it is a way to lose it.
- **Substring search.** "Find every log line containing `ECONNRESET`," or code search. Full-text search matches token boundaries and will miss the match inside a longer token. Use trigrams or a regex-capable tool.
- **Filtering on structured attributes.** `status = 'open' AND assignee_id = $1` is a `WHERE` clause, and it will stay one. Search gets involved only when free text is part of the query.
- **A corpus small and stable enough to curate.** Forty documents where ten queries cover most traffic: a hand-maintained list of canned answers beats any relevance tuning, and takes a day.
- **Reaching for a search cluster to fix what an index fixes.** If the real complaint is that an unindexed `LIKE 'prefix%'` is slow, add the index.

## Trade-offs

**Analysis decisions are baked in at write time.** Change the stemmer, the stopword list, or the synonym set, and every document indexed under the old rules is now wrong. The fix is a full reindex — which on a large corpus is an operation with a duration, a load profile, and a cutover strategy (the alias-swap technique belongs to the dedicated-engine article). This is the cost people most reliably underestimate, and it's why relevance tuning is slower than it looks.

**Stemming is lossy, and its collisions are permanent.** The Porter stemmer maps `university`, `universe`, and `universal` to the same root; `organization` becomes `organ`. You cannot search for an exact word form once it's been stemmed — recovering that requires a second, unstemmed copy of the field, which is a real technique and also doubles that part of the index.

**Stopwords delete real queries.** *To be or not to be* analyzes to nothing. So do the band name *The Who*, the language *C*, and a search for the *IT* department. Systems handle this in different, imperfect ways; the point is that a query returning zero results isn't always a bug in your code.

**Writes get more expensive and storage roughly doubles.** Every insert and update now also updates an inverted index whose whole design favours reads. Under bulk load this is the dominant cost, and bulk imports usually want the index dropped and rebuilt afterwards.

**Results are stale by construction.** There is a window between the write and the document being findable — milliseconds if the index is updated in the same transaction, seconds if a refresh interval or a queue is involved. "I just created it and it doesn't appear in search" will be filed as a bug periodically, forever. It's a product decision to be handled in the interface, not a backend detail to be tolerated.

**Relevance has no compile error.** A wrong `WHERE` clause returns wrong rows and someone notices. A mediocre ranking function returns plausible rows in a slightly bad order, and nobody notices except through a slow drip of "search is bad" feedback. Tuning by anecdote — one complaint, one boost, one regression elsewhere — is the default failure mode, and the way out is measurement: a set of query/expected-result judgments, or click-through data, and a number that moves. That's its own topic (12.4), but knowing the trap exists should change how you respond to the first complaint.

**Permissions must be re-established inside the index.** Row-level security in your database means nothing to a search index. The tenant id, the visibility flag, and the ACL have to be fields *in the document* and filters *in the query*, or search becomes the hole through which one customer reads another's data. This is the most common serious security bug in search implementations.

**Debuggability drops.** "Why is this result seventh?" is answerable only if the engine can explain a score. Plan to use that tooling; it's usually there and usually unknown.

## Alternatives

**Prefix matching on a B-tree.** `LIKE 'inv%'` uses an ordinary index. Perfect for autocomplete over names and identifiers, useless for finding a word in the middle of a sentence.

**Trigram indexes** (`pg_trgm` in Postgres, similar ideas elsewhere) chop text into overlapping three-character sequences and index those. This makes `LIKE '%term%'` indexable and gives you fuzzy similarity for free, which makes it genuinely good at names, SKUs and typo tolerance on short strings. It has no notion of words, stemming, or relevance, and the index is large. Different guarantee, complementary rather than competing — plenty of systems run both.

**Embedded search libraries** — Lucene, Bleve, Tantivy, and the browser-side ones like Lunr and FlexSearch. A real inverted index and BM25 inside your process or your user's browser, with no server to operate. Excellent for documentation sites, desktop applications, and single-node services. The limit is that the index lives with the process: distribution, replication, and shared state are your problem.

**Dedicated search engines** — Elasticsearch, OpenSearch, Solr, Typesense, Meilisearch. BM25 by default, a rich analyzer toolkit, faceting, aggregations, typo tolerance, and horizontal scale. You pay in operations and in a permanent consistency boundary. Module 12.2 onward lives here.

**Search as a service** — Algolia and friends. Someone else runs it, latency is excellent, tuning tools are good. You pay per record and per operation, and your content leaves your infrastructure, which may be a compliance conversation rather than a technical one.

**Vector / semantic search.** Embeddings put documents and queries in a space where proximity means similar *meaning*, which solves the one thing every technique above fails at: vocabulary mismatch. A user typing *how do I stop paying you* finds *Cancelling your subscription* even though the two share no terms. It is correspondingly bad at what lexical search is good at — exact names, identifiers, rare codes, negation — and the state of the art is hybrid: run both, fuse the rankings. That's Module 39.4; the thing worth carrying from here is that vector search is an addition to an inverted index, not a replacement for one, and teams that skip straight to it usually come back and build the lexical half anyway.

## How to Achieve It

An adoption path with a signal for each step, starting from the `ILIKE` you already have.

**L0 — `ILIKE '%x%'`.** Where you are. Move when the plan shows a sequential scan on a table that's still growing, or the first "it didn't find it" ticket arrives.

**L1 — a stored `tsvector` column and a GIN index, over the one field that matters.** Minutes of work, one migration, no new infrastructure, and it fixes both the scan and the word-form problem. This is the step most systems should have taken and haven't.

**L2 — weighted fields, real query parsing, and highlighting.** Combine title and body into one vector with different weights; parse user input with a function that tolerates arbitrary text; return a highlighted snippet so users can see *why* something matched. Move here as soon as people complain about ordering rather than about missing results.

**L3 — a separate search table.** A denormalized row per searchable thing: the vector, the tenant id, the visibility fields, the few columns needed to render a result. It keeps a large index off your hot transactional table, lets you reindex without touching production rows, and makes "search over three different entity types" a single query instead of three. The signal: the index is now a significant fraction of the table's size, or you're `UNION`ing searches across entities.

**L4 — a dedicated engine.** The signals are specific, and none of them is "we have a lot of data":

- You need **facet counts** — "Open (312) · Closed (1,204)" — across millions of matching documents, computed per query.
- You need **per-language analyzers**, several of them, in one corpus.
- **Relevance tuning has become an ongoing activity** with an owner, requiring per-field boosts, function scoring by recency or popularity, and A/B tests.
- **Typo tolerance** is a product requirement rather than a nice-to-have.
- **Search load is competing with transactional load** on the same machine, and you'd like it to stop.
- Your ranking needs **corpus-wide term statistics** that your database's ranking function doesn't have.

Notice the shape: L1 through L3 are hours-to-days of work inside a system you already run. L4 is a new datastore, a new backup regime, a new failure mode, and a sync pipeline. Arriving there *after* exhausting L3 means you'll know exactly what you're buying.

## Implementation

Postgres, because it's where the majority of these systems actually start, and because its full-text machinery makes each of the three parts visible.

**Seeing the analysis.** Before anything else, look at what the pipeline produces:

```sql
SELECT to_tsvector('english', 'The Reports are not loading in Chrome');
--  'chrome':7 'load':5 'report':2
```

Four of the seven words vanished as stopwords; `reports` and `loading` were stemmed; the numbers are positions. Run this against your own content early — it answers a lot of "why didn't that match" questions before they're asked, and it makes the language choice concrete. Swap `'english'` for `'simple'` and nothing is stemmed or dropped at all.

**Storing it.** A generated column keeps the vector in sync with the row automatically, and `setweight` is where field weighting lives:

```sql
ALTER TABLE articles ADD COLUMN search tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('english', coalesce(title, '')), 'A') ||
    setweight(to_tsvector('english', coalesce(body,  '')), 'B')
  ) STORED;

CREATE INDEX articles_search_idx ON articles USING GIN (search);
```

The two-argument form of `to_tsvector` is required here: the single-argument version depends on a session setting, so it isn't immutable and a generated column will reject it. That error message is cryptic enough to be worth recognizing.

GIN is the right default for this — fast lookups, slower updates, larger on disk. GiST is smaller and lossy, rechecking candidates against the row, which suits write-heavy tables with a modest corpus.

**Querying it.** The query function matters more than it looks:

```ts
const rows = await sql`
  SELECT id, title,
         ts_rank_cd(search, query) AS rank,
         ts_headline('english', body, query,
                     'MaxWords=30, MinWords=15') AS snippet
  FROM articles, websearch_to_tsquery('english', ${q}) AS query
  WHERE tenant_id = ${tenantId}
    AND search @@ query
  ORDER BY rank DESC
  LIMIT 20`;
```

`websearch_to_tsquery` accepts whatever a user typed — quoted phrases, `or`, a leading `-` for exclusion — and never raises a syntax error, which is exactly what you want in front of a text box. `to_tsquery` will throw on the first apostrophe someone types.

The `tenant_id` predicate is in the same `WHERE` clause rather than applied afterwards, which is the whole security story in this design and the reason the L3 search table carries a tenant column.

**Two failure modes visible right here.**

The first is the analyzer mismatch from *How It Works*, and in this syntax it's a one-word typo: index with `'english'`, query with `'simple'`, and the query term `loading` will never meet the indexed term `load`. Nothing errors. Results are just quietly wrong, and only for inflected words, which is the worst possible symptom because it looks like a content problem.

The second is a performance cliff hiding in `ORDER BY rank DESC LIMIT 20`. The GIN index can tell you *which* rows match, but it holds no score — so ranking requires fetching every matching row and computing `ts_rank_cd` on each. A query matching 300 documents is instant; a query for a term appearing in 400,000 documents fetches 400,000 rows to return 20. The mitigations are ordinary once you know the shape: filter hard first (tenant, date range, type), cap the candidate set before ranking, or use the `RUM` index extension, which stores enough information to return rows in rank order.

**And the limitation that eventually pushes you off Postgres.** `ts_rank` and `ts_rank_cd` score using only the terms in that one row's vector. They have no access to how many documents in the table contain a term — no IDF. A match on `the` (had it not been a stopword) and a match on `phosphorylation` carry the same evidential weight. For a scoped corpus where most queries are already narrowed by tenant and filters, this matters less than it sounds. For open-ended search over a large heterogeneous corpus, it's a ceiling, and it's the most defensible technical reason on the L4 list.

## Further Reading

- **PostgreSQL documentation, chapter 12, "Full Text Search."** Read the sections on parsers, dictionaries, and ranking in order. The limits are stated precisely there and nowhere else: 1 MB per `tsvector`, 16,383 maximum position, at most 256 positions retained per lexeme.
- **_Introduction to Information Retrieval_, Manning, Raghavan & Schütze** (free online at nlp.stanford.edu). Chapters 1–6 are the canonical treatment of everything in *How It Works* — inverted index construction, postings intersection, tolerant retrieval, and scoring — and it's readable without a maths background.
- **Robertson & Zaragoza, "The Probabilistic Relevance Framework: BM25 and Beyond."** Where the scoring function comes from, what `k1` and `b` actually control, and why saturation and length normalization are the corrections that mattered.
- **_Relevant Search_, Doug Turnbull & John Berryman.** The best book on the part that isn't mechanical: field weighting, signal design, and how to make relevance an engineering process with measurements rather than an argument about anecdotes.
- **Lucene's `similarities` package documentation and the Elasticsearch "Theory Behind Relevance Scoring" guide.** The concrete version of BM25 as implemented, plus the `explain` API — the tool that turns "why is this seventh" into an answer.
- **`pg_trgm` documentation,** for the trigram alternative, and the `unaccent` extension, which is how accent folding gets into an analysis chain in Postgres.
- **Snowball (snowballstem.org),** the stemmer family behind almost every engine's default stemming, with the per-language algorithms written out. Worth ten minutes to see how blunt the instrument really is.

A **Go** sibling built on **Bleve** would show something this article can only describe. Postgres hands you an analysis pipeline as an opaque configuration name; Bleve makes it an assembled object — you construct the tokenizer, the token filter chain, and the analyzer explicitly, register them, and can print the token stream at each stage. The same is true of its BM25 parameters. Writing the pipeline by hand is the fastest way to stop treating analysis as a black box, and it also surfaces the embedded-index trade-offs — index files on local disk, no replication, snapshot-based backup — that neither the database nor the cluster version makes you think about. Not yet written.

---

The habit to carry into every search feature you touch: **every search system makes three separate decisions — what counts as a term, how matches are found, and how matches are ordered** — and almost every complaint about search is a complaint about exactly one of them. "It didn't find it" is nearly always analysis. "It's slow" is the index. "It found it, but not first" is ranking. Knowing which one you're looking at is most of the work, because the three have nothing to do with each other and the fixes are in different places.
