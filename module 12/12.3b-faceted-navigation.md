# Faceted Navigation

_Module 12.3b — Search Functionality_

## The Problem

The marketplace from 12.3a has a filter sidebar. It works the obvious way: take the current filters, run the search, and count the values in the results.

```
  Brand                    Price
  ☐ Logitech      (412)    ☐ under $50    (301)
  ☐ Keychron       (98)    ☐ $50–$150     (274)
  ☐ Apple          (64)    ☐ over $150     (91)
  ☐ Anne Pro       (12)
```

A user clicks **Logitech**. The results narrow correctly. And the sidebar becomes this:

```
  Brand                    Price
  ☑ Logitech      (412)    ☐ under $50    (180)
                           ☐ $50–$150     (201)
                           ☐ over $150     (31)
```

Every other brand is gone. Not hidden — counted at zero, because the counts were computed over a result set that now contains only Logitech products. Of course it did. The aggregation was honest.

But the user's next action was going to be "and also show me Keychron," and there is now no way to express that. To compare two brands they have to clear the filter, re-read the list, and start again. The Price facet, meanwhile, updated exactly as it should: those counts *are* prices within Logitech, which is useful.

So the rule isn't "count before filters" or "count after filters." The two facets need **different** answers, and the difference is which facet you're looking at.

Two more things are wrong, and they're quieter.

**The counts don't match.** Clicking a facet labelled `(412)` returns 380 results. Nobody can reproduce it reliably. It turns out to be two independent causes stacked: the permission filter is applied to the hit list but not to the aggregation, and a term-frequency approximation in a distributed index is off by a few dozen on high-cardinality fields.

**A facet on seller name took the p95 from 40ms to 2.1s.** It was added the same way as the others, but the field has 180,000 distinct values, and asking for the top 10,000 of them on every request is a different kind of operation than asking for the top 20 brands.

Underneath all three: **a facet count is a promise about what happens if you click.** It says "there are 98 Keychron products waiting behind this checkbox." Every failure above is that promise being broken — by vanishing, by being wrong, or by being too expensive to keep.

## What It Is

**Faceted navigation** is progressive narrowing through the structured dimensions of a result set, where the available values and their counts are *derived from the data currently in play* rather than hardcoded.

That derivation is the entire distinction from an ordinary filter. A filter is a predicate. A facet is a filter that shows you its own consequences before you commit to it — which is what makes exploratory search work, because the user never has to guess and never lands on an empty page.

It's also worth separating from the thing it superficially resembles: a **taxonomy** or category tree is a fixed, curated structure that exists independently of any query. A facet is computed per request against the current result set. Products can carry a taxonomy *and* be faceted; the taxonomy tells you where something lives, the facet tells you what's here right now.

## Recognizing the Problem

- Selecting one value in a facet makes every other value in that facet disappear.
- Users clear all filters to change one of them.
- Counts in the sidebar don't match the number of results returned.
- Checking two boxes in the same group returns zero results.
- The sidebar shows values with a count of zero — clickable dead ends.
- A facet shows ten values and the eleventh is unreachable.
- Selecting a value makes its own checkbox vanish, so it can't be unselected.
- The facet list is a hardcoded array; new values in the data never appear.
- Facet counts come from running one search per facet.
- Latency changed materially when a facet was added, and nobody linked the two.
- A facet reveals a value — a customer name, a project, a classification — for documents the user can't open.

## How It Works

### Counts are aggregations, not queries

The engine has already identified the matching document set. A terms aggregation walks the column-oriented doc values for a field across that set and tallies. That's one pass over data already in memory, which is why a search engine can produce eight facets in the same request that produced the hits, and why the naive alternative — one `GROUP BY` query per facet — scales so much worse.

This is also the first place the 12.2 mapping decisions come due. Facets need `keyword` fields with doc values. A `text` field can't be faceted, and a field that wasn't normalized at index time will produce `Logitech`, `logitech`, and `Logitech Inc.` as three separate facet values. Facets expose data quality immediately and publicly, which is both their main hidden cost and, honestly, one of their better side effects.

### The exclusion rule

The fix for the vanishing-brands problem generalizes cleanly:

> **A facet's counts are computed over the result set narrowed by every *other* facet's selections, but not its own.**

Laid out, with `brand=Logitech` and `price=under-$50` selected:

```
  what                filters applied when computing it
  ─────────────       ──────────────────────────────────────
  the hit list        query + brand + price
  Brand facet         query + price                 ← not brand
  Price facet         query + brand                 ← not price
  Rating facet        query + brand + price         ← nothing of its own selected
```

An unselected facet is constrained by everything, which is correct: "how many 4-star items are in what I'm currently looking at." A selected facet steps back one level so its siblings remain visible and reachable.

The mechanism is slightly counterintuitive, because aggregations are computed over the query's result set and a sub-filter can only narrow that set further — never widen it. So the facet selections cannot live in the main query at all. Instead:

```
  query        text + tenant + permissions        ← what aggregations see
  post_filter  brand ∈ {Logitech} ∧ price < $50   ← what the hit list sees
  aggs.brand     filter: price < $50              ← everything except brand
  aggs.price     filter: brand ∈ {Logitech}       ← everything except price
  aggs.rating    filter: brand ∧ price            ← everything
```

`post_filter` exists for exactly this: a filter applied to the hits *after* aggregations have run. Each facet's aggregation then re-applies the other facets' constraints itself. Solr expresses the same idea more directly, by letting you tag a filter query and exclude it by name from a specific facet — different syntax, identical semantics, and the tagging version is easier to read.

### What a click means

Two conventions, and they need stating out loud because the code won't tell you and users will assume one of them:

- **OR within a facet.** Logitech *or* Keychron. Checking a second box in a group should always widen.
- **AND across facets.** Logitech *and* under $50.

These pair with the exclusion rule: within-facet OR is only discoverable if the other values in the group are still visible and counted, which is precisely what excluding your own facet achieves.

The exception is multi-valued fields. For `tags`, a user checking *waterproof* and *portable* may well mean both at once, and "OR" gives them a pile of things that are only one. There's no universal right answer — it's a product decision, and whichever you pick, the interface has to say so, because a group that sometimes widens and sometimes narrows is unusable.

### Kinds of facet

- **Terms** — categorical, low cardinality. The default case.
- **Ranges** — price bands, ratings. Fixed buckets are predictable and cacheable; buckets derived from the data adapt to odd distributions and shift under the user as they filter, which is disorienting. Fixed is usually right.
- **Date histograms** — "posted this week / month / year," the natural facet for tickets, jobs, news.
- **Hierarchical** — `Electronics > Peripherals > Keyboards`, implemented by indexing each path prefix as a separate keyword so every level is countable.
- **Numeric stats for a slider** — a min/max aggregation, and this one should *not* exclude its own selection, or the slider's endpoints jump every time the user drags it.

### Counts are approximate, and it's structural

In a sharded index, each shard returns its own top-N terms and the coordinator merges them. A brand ranked eleventh on every shard but third overall can be under-counted or missed entirely. The engine tells you: the terms aggregation returns an error bound and a count of everything not included in the returned buckets. Almost nobody reads either.

Three practical points:

- Increasing how many terms each shard returns improves accuracy at a memory cost; fewer shards removes the problem entirely for indexes small enough to have that option.
- For a **known, small set of values** — five statuses, three plan tiers — you can ask for a count per explicit value instead of a top-N. Exact, and cost proportional to the number of values.
- **Counts are documents, not things.** If your document is a product variant, `(412)` is variants. If line items are nested, a naive aggregation counts nested documents rather than orders. Both produce a number that's internally consistent and answers a different question than the label implies.

### Two rules that fall out of the mechanism

**Never show a zero-count value.** It's a clickable dead end, and the whole point of the count was to prevent those.

**Always show a *selected* value, even at zero.** If a selection ends up matching nothing — usually in combination with other filters — and you hide zero-count values, the checkbox the user needs to click to escape disappears along with the results. The user is stranded on an empty page with no visible cause. Selected values are merged back into the displayed list unconditionally.

## When It's Appropriate

- **Result sets routinely in the hundreds or thousands**, where ranking alone can't surface the right one and the user knows something about what they want.
- **The content has stable, low-cardinality dimensions users actually think in** — brand, price, status, location, date, file type, assignee.
- **Exploratory intent.** "A waterproof speaker under $100" is a facet interaction. "INV-2024-8871" is not.
- **The canonical domains:** catalogues, job boards, property listings, ticket queues, document archives, observability UIs, media libraries.
- **As a substitute for relevance work at small scale.** Revisiting 12.3a's point: with a few thousand documents, good facets beat any amount of scoring tuning, and cost less.

## When It's Unnecessary or Overkill

- **Result sets under about fifty.** People scan. A sidebar is overhead.
- **Navigational search.** One right answer means nothing to narrow.
- **Free-text fields as facets.** Faceting on an unnormalized description field yields four thousand values with a count of one each. If the field wasn't designed as a facet in the mapping, it isn't one.
- **Very high cardinality.** 180,000 sellers is not a checkbox list under any configuration. Offer a type-ahead search *within* the dimension instead — that's a different query, and a cheap one.
- **Facets nobody clicks.** Every facet is latency on every request plus sidebar clutter. Instrument usage; delete the ones at 0.2%.
- **Exact counts where the architecture can't provide them,** if the domain genuinely can't tolerate approximation. Often the right move is to show the facet without a number rather than a number that's subtly wrong.

## Trade-offs

**Every facet is work on every request.** Aggregations are cheap relative to a second query and not free relative to nothing. Eight facets is eight passes, and multi-select facets each need their own filter context.

**`post_filter` costs what it sounds like it costs.** Deferring the facet filters means the query matches and collects a larger set of documents before they're removed. That's the price of the exclusion rule, and it's real on large result sets — which is why the pattern is worth reaching for when you have multi-select facets and not before.

**Exactness trades against memory.** Accuracy in a distributed terms aggregation is bought with per-shard term budgets, which is heap.

**Facets are a mapping commitment.** Keyword fields, doc values, normalized values, indexed path prefixes for hierarchies — all decided at index time, all requiring a reindex to change (12.2).

**Facets leak.** A count is information about documents. A facet showing `Acme Corp (3)` tells a user those documents exist even if they can never open one; a classification facet can reveal that a sensitive category is populated. The permission filter must sit in the base query *and* therefore inside every facet's context — which is the same denormalized-permissions requirement from 12.2, arriving at a place people forget to check.

**Counts create an expectation of precision** that approximate aggregations don't meet. Users do notice, they do report it, and "that's an estimate" is a hard answer to give about a number rendered as `(412)`.

**Facet combinations are cache-hostile.** Each distinct selection is a distinct request. Individual filter bitsets cache well; whole results don't.

**The interface gets complicated fast.** Value ordering, "show 12 more," counts shifting as selections change, and all of it on a phone screen. The mechanism is the easy half.

## Alternatives

**Filters without counts.** Dramatically cheaper — no aggregations at all — and you lose the preview, so users hit empty result pages and learn to distrust the sidebar. A reasonable trade when the dimensions are few and every value is always populated.

**Aggregating in SQL.** If search lives in your database (12.1a's L3), several facets can be counted in a single pass using per-value conditional aggregates, or in one statement with grouping sets. Counts are exact, there's no approximation to explain, and the ceiling arrives as the result set grows — you're scanning rather than reading a purpose-built column structure. For tens of thousands of rows behind a tenant filter, it's entirely adequate and one fewer system.

**Precomputed counts.** A nightly rollup per dimension. Fast, exact, and unable to reflect the current query — so it only works for a facet sidebar on an unfiltered browse page, not for progressive narrowing.

**A curated taxonomy.** Browse rather than filter. No counts, no aggregation, full editorial control. Complements facets rather than replacing them, and it's what you want for the landing pages a search engine indexes.

**Query understanding.** Parse "wireless keyboard under $50" and apply the price filter automatically. Reduces the work the sidebar has to do, and works best alongside facets — apply the filter *and* show it as a selected chip the user can remove, so the system's inference stays visible and reversible.

**Dynamic facet selection.** Show `screen size` only when the result set is mostly monitors. Keeps the sidebar short on a heterogeneous catalogue; costs you a stable interface, since the controls move around as the user navigates.

## How to Achieve It

**L0 — hardcoded checkboxes, no counts.** Works. The signal to move is the first user complaint about an empty result page.

**L1 — counts from aggregations, all facets constrained by all selections.** The naive version, and it is *correct* as long as every facet is single-select. Move when you add the first multi-select facet — that's the exact moment the brands start vanishing.

**L2 — the exclusion rule.** `post_filter` plus per-facet filter aggregations, with the OR-within/AND-across convention implemented in one place rather than per screen. Include the zero-count rules; they're four lines and they remove a whole class of stuck states.

**L3 — facets as configuration.** A declarative list — field, type, multi-select or not, how many values, sort order, label — that generates both the query and the sidebar. This is what stops facet logic from being copy-pasted across the three screens that need it, and it makes adding a facet a data change.

**L4 — measurement.** Which facets get clicked, which selections lead to zero results, which values are truncated away, and where the aggregation error bound is non-trivial. Facets are a product surface; they deserve the same instrumentation as the ranking in 12.3a.

## Implementation

TypeScript. The interesting part isn't any single call — it's the construction of the per-facet filter sets, which is where the exclusion rule becomes code.

```ts
const FACETS = ["brand", "price", "rating"] as const;
type Facet = typeof FACETS[number];

// always applied, everywhere: tenancy and permissions
const base = [
  { term:  { tenant_id: tenantId } },
  { terms: { visible_to: userGroups } }
];

// one clause list per facet, empty when nothing is selected there
const clauses: Record<Facet, object[]> = {
  brand:  selected.brand?.length  ? [{ terms: { "brand.raw": selected.brand } }] : [],
  price:  selected.price?.length  ? [{ bool: { should: selected.price.map(priceRange),
                                               minimum_should_match: 1 } }] : [],
  rating: selected.rating         ? [{ range: { rating: { gte: selected.rating } } }] : []
};

const allSelections = FACETS.flatMap(f => clauses[f]);
const except = (self: Facet) => FACETS.filter(f => f !== self).flatMap(f => clauses[f]);
```

Note `minimum_should_match: 1` inside the price clause: that's the OR-within-a-facet convention, written once, in the place where it's decided.

```ts
const res = await es.search({
  index: "products",
  query:       { bool: { must: [textQuery], filter: base } },  // aggs see this
  post_filter: { bool: { filter: allSelections } },            // hits see this too

  aggs: {
    brand: {
      filter: { bool: { filter: except("brand") } },
      aggs: { values: { terms: { field: "brand.raw", size: 20, shard_size: 200 } } }
    },
    price: {
      filter: { bool: { filter: except("price") } },
      aggs: { values: { range: { field: "price_cents", ranges: PRICE_BANDS } } }
    },
    rating: {
      filter: { bool: { filter: except("rating") } },
      aggs: { values: { range: { field: "rating", ranges: RATING_BANDS } } }
    }
  },
  size: 20
});
```

Three things worth noticing in that request.

**`base` is in `query`, not in `post_filter`.** This is not stylistic. Anything in `post_filter` applies only to the hit list — so a permission filter placed there would produce facet counts computed over documents the user cannot see. The counts would be larger than the results, which reads as a bug, and it *is* a bug: it's an information leak that announces itself as an off-by-a-few discrepancy. Tenancy and permissions belong in the query, where aggregations inherit them.

**`shard_size` is set well above `size`.** Twenty brands are displayed; each shard considers two hundred before reporting. The response carries `doc_count_error_upper_bound` next to the buckets — read it once against production data, then decide whether the default was ever adequate.

**The `filter` aggregation wrapper only narrows.** That's why the selections had to be lifted out of the main query into `post_filter` in the first place. Try to shortcut this by leaving the brand filter in `query` and the brand facet will collapse to a single value again, which is the original bug wearing a more sophisticated implementation.

Finally, the assembly step that prevents stranded users:

```ts
function buckets(agg, selectedValues: string[] = []) {
  const found = agg.values.buckets.filter(b => b.doc_count > 0);
  const missing = selectedValues
    .filter(v => !found.some(b => b.key === v))
    .map(v => ({ key: v, doc_count: 0 }));     // selected but empty — keep it visible
  return [...found, ...missing];
}
```

Six lines, and they're the difference between "no results, and here's the filter causing it" and a blank page with no way back.

## Further Reading

- **Elasticsearch documentation: "Post filter," the `filter` and `filters` aggregations, and the `terms` aggregation.** Read the terms page's section on document count accuracy specifically — it explains the shard merge and the error bound better than any secondary source.
- **Solr's faceting documentation, particularly local-param tagging and exclusion (`{!tag=…}` / `{!ex=…}`) and the JSON Facet API.** The same exclusion rule with markedly better ergonomics; worth reading even on Elasticsearch, because seeing the idea named makes the `post_filter` dance obvious rather than mysterious.
- **Daniel Tunkelang, _Faceted Search_.** The short canonical book. Covers the interaction model, hierarchical facets, and the design questions this article only gestures at.
- **Marti Hearst, _Search User Interfaces_, chapter 8** (free online). The research foundation, including the Flamenco studies that established why counts and no-dead-ends matter as much as they do.
- **Hearst, "Design Recommendations for Hierarchical Faceted Search Interfaces."** Specifically on hierarchies — the case this article compresses into one bullet, and the one most likely to go wrong in a real catalogue.
- **PostgreSQL documentation on aggregate `FILTER` and `GROUPING SETS`,** for the in-database version described under *Alternatives*.

A **Go** sibling built on **Bleve** would show something the cluster hides. Bleve computes facets during result collection, in-process, with the accumulator visible in the API — you can see that a facet is a tally maintained as documents are visited, which makes both the cost model and the approximation story concrete in a way a JSON request never will. It also lacks `post_filter`, so the exclusion rule has to be implemented by running separate collections per facet, which is exactly the naive approach the engines optimize away — useful to write once in order to understand what you're being sold. Not yet written.

---

The habit worth carrying beyond search: **a control that previews its own consequence eliminates a whole class of dead ends.** The facet count is one instance; a disabled option with a reason, a date picker that greys out unavailable days, a form that validates before submission, and a deploy plan that reports what it's about to change are all the same move. The engineering question that follows is always the one in this article — what does the preview have to be computed over in order to be true?
