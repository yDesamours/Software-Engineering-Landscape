# Index and Document Design

_Module 12.2 — Search Functionality_

## The Problem

The decision from 12.1a has been made: search moves to a dedicated engine. Elasticsearch is running, a sync pipeline pushes rows into it, and search is fast. Then, over about a month, three things happen.

**The filter that can't be expressed.** The orders screen needs "search order contents, filtered to customer *Acme Corp*, sorted by total." The index was built by mirroring the tables — an `orders` index, a `customers` index — so the customer's *name* isn't in the order document, only `customer_id`. There is no join. The only way through is to query customers, collect 400 ids, and feed them back as a filter, which works until Acme has a parent company and the list is 40,000 ids long.

**The field that was typed by accident.** Sorting by `total` returns nonsense. The mapping says `total` is a `text` field, because the very first document indexed during a test run happened to carry `"total": "4300.00"` as a string, and the engine inferred a type from it and made it permanent. Nobody wrote that down. Nobody chose it.

**The change that can't be made.** Relevance work needs the title field analyzed differently, and a new `status` field needs to be filterable. Adding the field is fine. Changing the analyzer is not: field mappings are immutable once created. The only path is to build a new index and move everything into it — and the index name `orders` is hardcoded in the application, so the migration involves downtime, a deploy, and a rollback plan for an operation that was supposed to be a tuning tweak.

Three failures, one cause. The index was treated as a copy of the database, and it isn't one:

```
  a table                        an index
  ─────────────────────────      ─────────────────────────────
  normalized                     denormalized
  joins at read time             no joins
  columns typed once, alterable  fields typed once, mostly not
  schema is a migration          analysis choices are baked into
                                   every document already written
  one shape, many queries        shape follows the queries
```

A search index is a **derived, query-shaped, largely immutable artifact**. Every one of those three words is doing work, and designing against any of them produces exactly the failures above. The design question is therefore not "how do I represent my data here" but **"what does one search result look like, and what does the engine need in order to find, filter, sort, and display it without asking anyone else?"**

## What It Is

**Index design** is three decisions made deliberately rather than by default:

1. **The document boundary** — what constitutes one searchable thing, and therefore what gets denormalized into it.
2. **The mapping** — the per-field declaration of type, analysis, and capability (searchable? sortable? aggregatable? merely stored?).
3. **The lifecycle** — treating reindexing as a routine operation, which in practice means one thing: applications talk to an *alias*, never to an index name.

The mapping is a schema, and calling it one is fine as long as you carry the differences: it is additive only, it attaches an analysis pipeline to each field individually, it enforces no constraints or relationships, and it is not the system of record, so getting it wrong is recoverable by rebuilding rather than by a data-repair script. That last difference is the one that makes the other three survivable.

## Recognizing the Problem

- Your indexes have the same names and shapes as your tables.
- A search returns ids, and then you filter or sort the results in application code.
- You can't aggregate or sort on a field because it's `text` when it needed to be `keyword`.
- Nobody can state the current mapping without asking the cluster; dynamic mapping has been on since day one.
- `GET /_mapping` returns hundreds of fields, many of them from a single JSON blob someone indexed wholesale.
- Documents are being silently rejected, and the sync pipeline's error log is where you found out.
- Your application config contains a literal index name.
- The plan for changing an analyzer is "delete and re-create the index at 2am on Sunday."
- A query for `sku:A AND qty>5` matches an order where item A has quantity 1 and item B has quantity 9.
- You created one index per tenant, and there are now 4,000 of them.

## How It Works

### The document is the unit of retrieval

Start from the screen, not the schema. If a result row in the UI reads:

```
  Order #1042 · Acme Corp · $4,300 · 3 items · Shipped · 12 Mar
```

…then a single document should contain all of it. Not `customer_id` — `customer_name`, because it's displayed and it's searched. Not a foreign key to a status table — the status string, because it's faceted on.

The general rule: a document carries everything needed to **match**, **filter**, **sort**, **authorize**, and **render** one result. Anything the query needs and the document lacks becomes an application-side join, and application-side joins in search are how you end up building a filter clause containing 40,000 ids.

This is the same discipline as designing tables in a wide-column store (Module 6): **enumerate the queries first, then design the document.** The difference from relational modelling is total — there, one normalized schema serves queries nobody has thought of yet; here, a query nobody anticipated may simply be unanswerable until the next reindex.

Boundary choices are real choices, and picking the wrong grain is the expensive mistake. For a document-management product: is the searchable thing the document, or the page? If users need to jump to the page where a term occurs, the page is the unit and the document's title has to be denormalized onto every page. Choose the grain that matches what you show in the result list.

### The mapping: types are capabilities

The central distinction, and the one behind most "I can't do that" moments:

- **`text`** is analyzed — tokenized, stemmed, stored in the inverted index. Matchable in a full-text sense. **Not** sortable or aggregatable in any sane way.
- **`keyword`** is stored whole, unanalyzed, one term. Exact match, sorting, aggregation, faceting. `"Acme Corp, Ltd."` stays a single value.

Most human-facing string fields need both, which is what multi-fields are for: `title` as `text` for searching, `title.raw` as `keyword` for sorting alphabetically and faceting. You're storing the field twice, and that's the intended design.

The rest of the mapping is about capability too:

- **Numeric, date, boolean, geo** types exist so that range queries, date maths, and distance sorting work. A date stored as a string is a date you can't range over.
- **`index: false`** for fields you only ever display — a thumbnail URL, a rendered excerpt. Stored, returned, never searched, no index cost.
- **Doc values** are the column-oriented structure that makes sorting and aggregation possible; they're on by default for everything except `text`. This is the actual mechanism behind "you can't aggregate a text field."
- **Per-field analyzers**, and separately a **search-time analyzer** that may differ from the index-time one. That asymmetry is not an edge case — it's the foundation of autocomplete, where you index aggressively (every prefix) and query plainly (12.3).
- **`copy_to`** funnels several fields into one catch-all field, so a single query can cover title, body, and tags without a multi-field query. Cheap, and it keeps query construction simple.

### Dynamic mapping is a loaded gun

By default, indexing a document with an unknown field creates a mapping for it, inferred from the value. That's why `total` became `text`: someone sent a string once.

The failure modes compound. Types are inferred from first sight and then fixed, so a later document with a conflicting type is **rejected** — and if your pipeline doesn't surface rejections loudly, documents go missing with no user-visible symptom until someone can't find something. And indexing an arbitrary JSON blob (a webhook payload, a metadata bag) creates a field per key, forever; the default limit of 1,000 fields per index exists precisely because people hit it.

For anything that outlives a prototype, set dynamic mapping to `strict` and write the mapping down. An unknown field then fails loudly at index time, which is the correct moment to find out.

### Arrays flatten, and that's a bug waiting

An array of objects is stored by flattening each sub-field into a parallel list. An order with two line items:

```json
"line_items": [ { "sku": "A", "qty": 1 }, { "sku": "B", "qty": 9 } ]
```

is indexed as:

```
  line_items.sku  →  ["A", "B"]
  line_items.qty  →  [1, 9]
```

The association between `A` and `1` is gone. So `sku:A AND qty>5` matches this order, because the index contains an `A` and it contains a `9`. The query is correct, the result is wrong, and it will be wrong intermittently in a way that depends on your data.

The fix is the **`nested`** type, which indexes each sub-object as its own hidden Lucene document so that per-object matching works. It costs: an array of 50 items is 51 documents, updating one item rewrites all of them, queries are slower, and there's a configured limit on how many nested objects a document may hold. Use it when cross-matching would actually be wrong for your queries, and flatten when it wouldn't — if you only ever match on `sku` without a second condition, the plain object is fine and cheaper.

**Parent-child (`join`) relationships** exist as the third option: real relational separation inside one index, so a child can be updated without rewriting the parent. Queries are substantially slower and the feature constrains routing and sharding. It earns its place in one shape — a small number of parents with very many, very frequently updated children — and is otherwise a way of importing relational habits at a price.

### Documents don't get updated, they get replaced

Lucene segments are immutable. An "update" writes a new version of the document and marks the old one deleted; the space comes back only when segments merge in the background. Three consequences you will meet:

- **Update-heavy indexes bloat** and spend real I/O on merging. An index whose documents change constantly is fighting its own storage model.
- **Writes aren't immediately visible.** New documents become searchable at the next refresh — one second by default, tunable. That's the staleness window from 12.1a, given a number and a knob.
- **A partial update is still a full rewrite** of that document internally, even when the API accepts one field.

### Denormalization's bill: fan-out

Acme Corp renames itself. In the database that's one `UPDATE`. In the index it's 40,000 documents carrying `customer_name`, all of which are now wrong, and correcting them is a long-running bulk operation with its own progress, failure, and conflict behaviour.

This is the permanent trade of the document model, and it is why the boundary decision matters so much. Denormalize what's queried and displayed; don't denormalize an entity's whole record because it was easy. And notice what it does to permissions: if ACLs live in the document, a permission change is a fan-out too, which is exactly why coarse denormalized fields (`tenant_id`, `visibility`, a small group-id list) work and per-document user lists don't.

```
  source of truth          index
  ───────────────          ─────────────────────────────
  customers                order  #1042  customer_name: "Acme Corp"
    #77 "Acme Corp"  ──┐   order  #1043  customer_name: "Acme Corp"
                       └─► order  #1044  customer_name: "Acme Corp"
     one row                         … × 40,000
     one update                 one bulk job, minutes, retryable
```

### Aliases, and reindexing as a normal event

Given that analysis choices are baked into written documents, and that mappings can't be changed, **you will rebuild indexes**. Not as an emergency — as a routine part of relevance work. The entire difficulty of that operation is decided by one early choice:

```
  application  ──►  alias "orders"  ──►  orders_v1        (today)

  build new index, backfill, verify:
                    alias "orders"  ──►  orders_v1
                                         orders_v2        (filling)

  one atomic alias update:
  application  ──►  alias "orders"  ──►  orders_v2
                                         orders_v1        (kept a week)
```

The swap is atomic and instantaneous; no client sees a moment without an index, and rolling back is the same operation in reverse. If instead the application holds the literal name `orders`, the same migration requires a deploy, and the rollback requires another.

The remaining question is the writes that happen *during* the backfill. Two workable answers: write to both indexes for the duration (simple, needs the write path to know about it), or backfill and then replay everything changed since the backfill started from the source of truth (needs a reliable `updated_at` or an event log — the outbox from Module 6 gives you this for free). What doesn't work is backfilling and hoping the window was short.

## When It's Appropriate

- **Any index that will outlive a prototype.** The alias costs one line on day one and is the difference between a routine reindex and an outage.
- **When search spans entities** — orders, customers, and documents in one result list — which requires deciding on a blended document shape or a set of indexes queried together.
- **When facets, sorting, or aggregations are part of the product.** These are mapping decisions, made before the data arrives.
- **When relevance is an ongoing activity.** Analyzer changes are reindexes; if you plan to tune, you're planning to reindex, and the lifecycle needs to be boring.
- **Multi-tenant search**, where the tenant field is both a filter and a security boundary and must exist in the mapping by design rather than by inference.

## When It's Unnecessary or Overkill

- **Ephemeral, time-sliced indexes** — logs, metrics, telemetry with rollover and retention. Dynamic mapping plus an index template is the normal and correct pattern there; the data ages out before a mapping mistake matters, and nobody reindexes a week-old log index.
- **Over-modelling relationships.** `nested` and `join` both have real costs. If no query combines two sub-fields of the same object, a flat object is right.
- **Denormalizing what nothing queries.** Every extra field is index size, fan-out surface, and reindex time. "It might be useful later" is paid for now.
- **One index per tenant, at scale.** Each index is at least one shard, each shard is a Lucene index with fixed memory and file-handle overhead. It's a reasonable choice for dozens of large tenants; it collapses at thousands of small ones, where a shared index with a `tenant_id` filter is the answer.
- **Designing for queries you don't have.** The whole method is query-driven; inventing hypothetical queries produces a document shape optimized for nothing.

## Trade-offs

**Denormalization buys query independence and sells update cost.** Fan-out is permanent, proportional to your reference count, and asynchronous — which means a window where different documents disagree about the same entity's name.

**Strict mappings turn new fields into migrations.** Adding a searchable attribute is now a mapping change plus a deploy, not a JSON key. This is a feature (you find out at index time, not at query time) with a real cost in velocity.

**Mapping immutability makes analysis decisions expensive to revisit.** You can add a field; you cannot retype one or re-analyze one. Every such change is a full rebuild whose duration scales with the corpus and which temporarily costs double the storage.

**Multi-fields and `copy_to` duplicate data on disk.** Title indexed three ways is title stored three ways. Usually worth it; not free, and it adds up across a wide document.

**`nested` multiplies document count.** The visible cost is query latency; the less visible one is that updating a single array element rewrites every nested document in the parent.

**Reindexing has a correctness question, not just a duration.** Anything relying on "we'll do it during a quiet period" is relying on a property of traffic rather than on a property of the procedure.

**Your security model does not come along.** Row-level security, database roles, and application-layer authorization mean nothing here. The filter must be in the document and in the query, and the fan-out cost of permission changes is part of the design, not an afterthought.

**Disabling `_source` to save space breaks reindexing.** Without the original document, you cannot rebuild a new index from the old one, and update APIs and some highlighting stop working. The saving is rarely worth losing the ability to migrate.

## Alternatives

**Index ids only; hydrate from the database.** Store just the searchable text, the filters, and the id; fetch display data from the source of truth after ranking. Eliminates most fan-out and all display staleness, at the cost of a round trip per result page and a hard rule that *nothing you filter or sort on may live only in the database*. A good fit when result rows are rich and mutable but searched on a narrow, stable set of fields.

**Parent-child instead of denormalization**, as above: cheaper updates, slower queries, structural constraints.

**The `flattened` field type** for arbitrary key-value bags — indexes the whole object as one field, avoiding mapping explosion, at the cost of everything being treated as keywords with no per-field analysis. The right answer for user-defined metadata you must filter on but never rank by.

**Runtime fields** — computed at query time from `_source`, no reindex required, queryable and aggregatable but slower. The escape hatch for "we need to filter on something we didn't index" without an immediate rebuild, and a useful way to prototype a field before committing it to the mapping.

**Separate indexes per entity, searched together.** Preserves clean per-entity mappings and avoids a blended super-document, at the cost of cross-entity relevance being hard to reason about — scores from different indexes with different field structures aren't directly comparable.

**Not moving to an engine at all.** Module 12.1a's L3 — a denormalized search table in your existing database — is the same document-modelling exercise with none of the mapping immutability and none of the second datastore. Everything in this article about choosing the document boundary applies there too.

## How to Achieve It

**L0 — dynamic mapping, index name used directly.** Fine for a spike. Nothing else.

**L1 — an alias, from the first commit.** `orders_v1` behind alias `orders`; the application never sees a version number. This is the single highest-leverage line in the entire module and it takes minutes.

**L2 — an explicit mapping in version control**, `dynamic: strict`, applied by a migration step in your deploy rather than by hand in a console. The mapping is now reviewable, diffable, and the same in every environment.

**L3 — a reindex procedure you have actually executed.** Create from the checked-in mapping, backfill from the source of truth, replay or dual-write the gap, verify document counts and spot-check a sample, swap the alias, keep the old index for a week. Run it once when nothing is wrong — the same logic as restore drills in Module 6.6. A procedure that has only ever been read is not a procedure.

**L4 — reindexing as an ordinary change.** Mapping changes arrive as pull requests, the rebuild is automated and observable, and relevance experiments stop being blocked on an operations conversation. The signal you've arrived: someone changes an analyzer on a Tuesday afternoon and nobody schedules anything.

## Implementation

TypeScript with the official client. Almost all of the substance is JSON — which is the point; the mapping is an artifact you own, review, and version, not something the library generates for you.

**The mapping**, for a blended order document:

```ts
await es.indices.create({
  index: "orders_v2",
  settings: { number_of_shards: 1, refresh_interval: "1s" },
  mappings: {
    dynamic: "strict",                       // unknown field → rejected, loudly
    properties: {
      tenant_id:     { type: "keyword" },    // filter + security boundary
      order_number:  { type: "keyword" },    // identifiers are never analyzed
      status:        { type: "keyword" },    // facet
      total_cents:   { type: "long" },       // sortable, range-queryable
      placed_at:     { type: "date" },

      customer_name: {                       // denormalized from customers
        type: "text",
        fields: { raw: { type: "keyword" } } // …and sortable/facetable
      },

      notes:         { type: "text", copy_to: "all_text" },
      all_text:      { type: "text" },       // one field to query

      receipt_url:   { type: "keyword", index: false },  // display only

      line_items: {
        type: "nested",                      // see below
        properties: {
          sku: { type: "keyword" },
          qty: { type: "integer" }
        }
      }
    }
  }
});
```

`line_items` is `nested` for exactly one reason: the product has a query that combines `sku` and `qty` in the same clause. Drop that requirement and the `nested` type should go with it — it's the most commonly over-applied type in the mapping vocabulary, and each nested array turns one document into many.

Note also that `tenant_id` is `keyword` rather than `text`. A tenant id that gets analyzed is a tenant id that can partially match another tenant's, which is a security bug wearing a relevance costume.

**The alias swap**, which is the whole reindex story compressed into one call:

```ts
await es.indices.updateAliases({
  actions: [
    { remove: { index: "orders_v1", alias: "orders" } },
    { add:    { index: "orders_v2", alias: "orders" } }
  ]
});
```

Both actions apply atomically. No request observes a missing alias, and reversing it is the same call with the names exchanged. Everything difficult about reindexing happens before this line; this line is the part that's easy *because* the alias existed.

Backfilling from the previous index is a single server-side call — and it should always be launched asynchronously, because for anything real it will outlive your HTTP client's timeout:

```ts
const { task } = await es.reindex({
  source: { index: "orders_v1" },
  dest:   { index: "orders_v2" },
  wait_for_completion: false          // returns a task id; poll it
});
```

One caveat worth carrying: reindexing *from the old index* only works if `_source` is enabled, and it replays documents as they were — including any that were wrong. Rebuilding from the system of record is slower and is the version that fixes data problems rather than copying them forward.

**The fan-out**, when Acme renames:

```ts
await es.updateByQuery({
  index: "orders",
  conflicts: "proceed",               // don't abort the batch on a version clash
  query: { term: { customer_id: "77" } },
  script: {
    source: "ctx._source.customer_name = params.name",
    params: { name: "Acme Holdings" }
  },
  wait_for_completion: false
});
```

The failure mode lives in `conflicts`. The default aborts the whole operation the first time a document is modified by your normal sync pipeline mid-run — leaving the rename half-applied, with no obvious marker of where it stopped. `proceed` skips those documents and reports the count, which is the right behaviour only if something re-applies them afterwards. In practice the durable version is to let the ordinary indexing pipeline handle it: emit a "customer renamed" event, and have the projector re-index the affected orders from the source of truth. Slower, idempotent, and it uses machinery you already have rather than a one-off script someone runs from a laptop.

## Further Reading

- **Elasticsearch documentation: "Mapping," "Field data types," and "Nested field type."** Read the nested page specifically for the worked cross-matching example and the configured limits; it's the clearest statement of why arrays of objects behave the way they do.
- **Elasticsearch documentation: "Aliases" and the "Reindex API,"** plus the guidance on reindexing from a remote cluster. The alias-swap pattern is documented but easy to miss until you need it.
- **OpenSearch documentation** covers the same ground for the forked lineage; if you're on OpenSearch, prefer it, since the APIs have diverged since 7.10.
- **_Elasticsearch: The Definitive Guide_ (Gormley & Tong).** Dated against current versions, and still the best long-form explanation of document modelling, denormalization, nested and parent-child, and the reasoning behind each. Read it for the *why* and check current docs for the *how*.
- **Lucene's index format documentation.** Segments, immutability, tombstones, and merging — the layer that explains refresh intervals, update costs, and index bloat, none of which make sense from the Elasticsearch API alone.
- **Elastic's "Size your shards."** Concrete numbers for the index-per-tenant question and for shard-count planning generally, which is otherwise an area of pure folklore.
- **Martin Fowler, "Aggregate" (DDD)** — the boundary question in this article is the aggregate question from Module 2.3 in a different setting: what cluster of data is treated as one unit. Reading them together makes both clearer.

A **Java** sibling built on Spring Data Elasticsearch would be a genuinely different article rather than a translation, because it inverts the central claim here. Annotating an entity with `@Document` and `@Field` derives the mapping from code, which is appealing — one definition, type-checked — and moves the failure mode somewhere new: the annotations and the live index drift apart, since the framework will create a mapping from annotations for an index that doesn't exist but will not alter one that does. The interesting content is what disciplined reindexing looks like when the mapping is a compiled artifact, and how index name resolution and aliases work through the repository abstraction. Not yet written.

---

The habit worth taking from this: **anything derived should be cheap to rebuild, and the cost of rebuilding it is decided long before you need to.** An alias, a mapping in version control, and a backfill that reads from the system of record are three small decisions that convert "we can't change the analyzer" into a Tuesday afternoon. The same shape shows up in caches, materialized views, read models, and projections — a derived store you can't confidently rebuild has quietly become a system of record, and it will be treated like one at the worst possible moment.
