# Search Performance and Operations

_Module 12.4 — Search Functionality_

## The Problem

The search from 12.1a through 12.3c is correct. Three million documents, good relevance, facets that behave. Then four incidents arrive in a quarter, and none of them is "we need more servers."

**Page 500.** A customer's export script walks `?page=1..2000`. Each request asks for results 10,000 to 10,020 — which means every shard collects and sorts its top 10,020 hits, ships them to the coordinating node, and the coordinator merges 100,200 results in order to return twenty. Memory spikes, a node drops out of the cluster. Someone had already raised the result-window limit from its default to 100,000 six months earlier, to close a support ticket.

**p50 is 25ms and p99 is 3.4 seconds.** CPU sits at 30%. This is not a capacity problem, and adding nodes does nothing. Two separate things are producing it: a handful of query *shapes* that cost a hundred times the median — a fuzzy term expanding into hundreds of clauses, a facet on a 180,000-value field, a script score evaluated over 400,000 hits — and the structural fact that a search waits for its slowest shard.

**The cache that never hits.** The request cache was enabled and changed nothing. Separately, someone added a 60-second application-level cache on search results, and the "I created it and can't find it" complaints from 12.1a got substantially worse.

**The reindex that took the site down.** A mapping change from 12.2 was rolled out at 2pm. Bulk indexing at full speed, segment merges competing with queries for the same I/O, and search latency tripled for forty minutes.

Four incidents, and the thing they have in common is that **search latency isn't one number with one cause.** It decomposes, and the decomposition is what tells you which lever to pull:

```
  latency  ≈  fan-out  ×  ( match  +  score  +  aggregate  +  fetch )

     how many              how many        how much        how much
     shards must           documents       work per        work per
     answer                are considered  document        returned document
```

Plus a fifth term that isn't in the formula and dominates in practice: **whether the data you're reading is in memory or on disk.** A search engine is an I/O-bound system pretending to be a CPU-bound one. Most surprising latency is a working set that stopped fitting in RAM.

## What It Is

Search performance work is controlling the four terms above, deciding what can be reused instead of recomputed, and operating an index that is being continuously rewritten underneath the queries reading it.

That last clause is what makes this different from tuning a database. Lucene segments are immutable (12.2), so writes constantly create new segments and background merges constantly consolidate them — meaning your query load and your write load contend for the same disk and the same page cache, always, by design. A lot of "search got slow" is really "search got slow while something was being indexed."

## Recognizing the Problem

- p99 is an order of magnitude above p50.
- CPU is low and latency is high.
- The result-window limit has been raised, by someone, for a reason nobody remembers.
- Users — or crawlers — can reach page 500.
- One tenant's query pattern degrades everyone.
- Heap sits above 80% and GC pauses are visible in the latency histogram.
- You have 900 shards holding 40 GB of data.
- Latency spikes correlate with bulk indexing or reindex jobs.
- Request cache hit rate is approximately zero.
- Nobody can name your three most expensive query shapes, and slow logs are off.
- Latency is measured inside the engine, and the number users experience is different.
- Search sometimes returns fewer results than it should, and nobody noticed that responses are flagged as timed out.

## How It Works

### Consider fewer documents

Everything downstream is proportional to the size of the matching set, so the cheapest optimization is always to match less.

**Filters shrink the set before scoring** — the filter-context split from 12.3a, which is a correctness decision that happens to be the largest performance decision too. Beyond that, filter *cost* varies enormously: a term filter on a low-cardinality keyword is nearly free, a script filter is evaluated per document. Engines estimate and reorder, but they can only do that for constructs they understand; a script is opaque and runs.

**Some query shapes have unbounded cost**, and they're the ones behind most incidents:

- leading wildcards and unanchored regex — the term dictionary cannot be walked from a known point, so it's scanned
- fuzzy matching without a prefix length (12.3c)
- `terms` queries carrying tens of thousands of values
- phrase-prefix queries with large expansion limits
- scripts anywhere in the query

The right response is a guardrail at the API boundary, not a convention. A search endpoint that accepts an arbitrary query body from a client is an endpoint where any user can write a query that takes the cluster down, and "we told everyone not to" is not a control.

**Work moved to index time is work not done per query.** A field computed during indexing (12.2's denormalization) beats a script computing it across every hit, every time, by a margin that isn't close.

### Do less work per matching document

**Scoring is per-hit**, and the modern engines are much better at avoiding it than most deployments let them be. Lucene can skip documents that provably cannot enter the top N — but only when it doesn't have to count every match. That's why the total-hit-count setting matters far more than it looks: asking for an exact count of a query matching 400,000 documents forces a full visit, while accepting "10,000+" lets the engine stop early. It's a one-line change, it's frequently a several-fold improvement on broad queries, and the product cost is a result header that says *about 10,000 results* instead of *10,412 results* — which users do not read.

The same skipping is unavailable whenever **aggregations** are present, because a facet count has to visit every match by definition. This is the performance restatement of 12.3b: your facets, not your search, are usually why search is slow.

**The fetch phase is separate and separately expensive.** Retrieving stored source for twenty documents is cheap unless the documents are large; highlighting is not, because highlighting re-analyzes the field text at query time. Highlighting a 500 KB body for twenty hits is real work that has nothing to do with matching. Source filtering — returning only the fields the result card renders — and a shorter dedicated field for highlighting are the fixes, and they belong to the document design decisions from 12.2.

### Fan-out, and why the tail is structural

A search goes to one copy of every shard and returns when the **slowest** one returns.

```
  shard latencies:  12  14  11  13  15  90  12  13  11  14   (ms)
  request latency:  90                       ↑
                                             one shard decides
```

With ten shards, a request effectively samples the upper reaches of the shard-latency distribution; with fifty, it samples further out still. A per-shard p99 of 90ms becomes a *typical* request latency once you have enough shards. This is the "tail at scale" effect, and it means shard count is a latency decision, not just a capacity decision.

Which inverts the usual instinct: for latency-sensitive search, **fewer, larger shards are better.** More shards buy parallelism for a single expensive query and ingest throughput; they cost tail latency, per-shard fixed overhead, and heap. The common guidance — shards in the tens of gigabytes, not hundreds of megabytes — exists because over-sharding is the most frequent self-inflicted wound in this space, and it's usually a 12.2 decision (an index per tenant) coming due a year later.

**Replicas add throughput, not speed.** A single query isn't faster with more replicas; more queries fit. What replicas do help with is routing around a struggling node, which most engines now do automatically by preferring copies that have been responding quickly.

**Routing is the lever that removes fan-out entirely.** If documents are placed on a shard by a routing key — the tenant id — then a query scoped to that tenant touches *one* shard instead of all of them. Fan-out goes from N to 1, tail amplification disappears, and throughput multiplies because each query occupies a fraction of the cluster. For multi-tenant search this is the single highest-leverage configuration available, and it's badly underused.

Its cost is skew: one enormous tenant lands entirely on one shard and can't be split without changing the routing scheme, which is a reindex. The usual accommodation is to route by tenant generally and give the handful of giant tenants their own index.

### Reuse instead of recompute

Four caches, doing different jobs:

- **The filesystem cache** — the one that matters most and gets managed least. Segment files are memory-mapped; if the hot portion of the index fits in the RAM left over after heap, reads are memory reads. If it doesn't, they're disk. This is why the standard advice is to give the JVM no more than half the machine's memory and never more than about 31 GB (above which pointer compression is lost and you get *less* usable heap). The other half isn't spare — it's the cache doing the real work.
- **Filter bitsets**, covered in 12.3a: cached per filter clause, worth understanding for which filters reuse and which don't.
- **The request cache**, which caches a whole shard-level response and, by default, only for requests that return no hits — that is, aggregation-only requests. A facet-count sidebar for an unfiltered browse page caches beautifully. A normal search with hits doesn't.
- **Application-level result caching**, which is the dangerous one. Per-user filtering explodes the key space, and any TTL is added directly onto the staleness window from 12.1a. Cache the expensive, *shared*, impersonal parts — head-query results, unfiltered facet counts, category landing pages — and leave personalized result sets alone.

### The index is being rewritten while you read it

**Refresh interval** controls how often new documents become visible, and the default of one second means constant small-segment creation. During a bulk load or a full reindex, turning refresh off and dropping replicas to zero, then restoring both afterwards, is a large ingest win — often several-fold — for a staleness cost that doesn't matter because nobody's querying the new index yet.

**Merges** consolidate segments in the background, and they compete with queries for I/O. A completed, no-longer-written index — a reindexed version about to receive the alias — benefits from an explicit merge down to one segment: fewer files to consult per query, measurably faster. On a live, actively-written index the same operation is harmful, because the giant segment it creates will have to be merged again later.

**Bulk indexing needs backpressure, not retries.** A rejection from a full queue is the cluster telling you it's saturated; hammering it with immediate retries converts a slowdown into an outage. Exponential backoff with jitter and a concurrency limit is the correct response — the machinery from Module 10, applied here.

**Circuit breakers** abort requests that would consume too much memory. A tripped breaker is an error, and it's also a *diagnostic*: something in your query mix is asking for an aggregation the cluster can't hold.

### Deep pagination

`from` and `size` cost O(from + size) *per shard* plus a merge across all of them, which is the first incident in *The Problem*:

```
  from=10000  size=20,  10 shards
     each shard:   collect and sort 10,020
     coordinator:  merge 100,200
     returned:     20
```

The default limit on this exists to protect the cluster, and raising it is almost always the wrong response to the ticket that prompted it.

The correct mechanism is a **cursor**: `search_after` takes the sort values of the last result on the previous page and resumes from there, at constant cost per page. It requires a **totally ordered sort** — append a unique tiebreaker, or two documents with the same score will be skipped or duplicated across a page boundary. It cannot jump to page 500, and that's a product decision worth making explicitly: no human reads page 500. The traffic asking for it is crawlers and scripts, and their real requirement is a complete export, not pagination.

For exports specifically, a cursor alone isn't enough — documents change between pages, so a consistent **point-in-time snapshot** paired with the cursor gives a stable view. It holds segments open for its lifetime, which costs disk, so it needs an explicit close. Better still: don't paginate search for exports at all. Give exports their own path with its own limits, its own queue (Module 10), and its own rate limit (Module 18), so a customer's data dump can't share a latency budget with the search box.

### Measurement

**Measure at the client.** The engine reports its own processing time, which excludes queue wait, network, coordination overhead, and your application's serialization. The number that matters is the one the user experiences, and the gap between the two is itself a useful signal — a large gap means queuing, not query cost.

**Slow logs are per-shard and split by phase.** A slow *query* phase points at matching and scoring; a slow *fetch* phase points at source retrieval and highlighting. That split routinely saves a day of investigation, and it's off by default.

**Profile a single query** when you need the breakdown — it attributes time to individual clauses and aggregations, and the answer is regularly not what anyone predicted.

**Segment the metrics by query shape,** not by endpoint. An overall p99 mixing autocomplete, faceted search, and exports describes nothing. Per-shape percentiles, plus the distribution of *how many documents each query matched*, is where expensive shapes become visible before they become incidents.

Finally, the trap in timeouts: a search timeout typically returns **partial results** flagged as timed out, rather than an error. If nothing checks the flag, the symptom is a result list that's quietly incomplete, intermittently, under load — which will be reported as a relevance bug and investigated in the wrong module entirely.

## When It's Appropriate

- **Search is user-facing and latency is a product property.** Above roughly 200ms, interaction quality degrades; autocomplete's budget (12.3c) is far tighter.
- **The index has outgrown RAM**, or is about to. This is the threshold where performance behaviour changes character rather than degrading smoothly.
- **Multi-tenant search with uneven tenants**, where one customer's query pattern can degrade everyone — routing and per-tenant limits earn their place here.
- **Crawler, export, or integration traffic** shares the search path with interactive users.
- **Before a growth event** rather than during one, because most of these levers (shard count, routing key) are reindexes.

## When It's Unnecessary or Overkill

- **Before measuring.** Every list above is a menu, and choosing from it without slow logs and per-shape percentiles is guessing at which of five candidate causes you have.
- **Sharding early.** A single shard serves a surprisingly large index, and an unnecessary shard count is permanent until a reindex.
- **Optimizing p50 when the complaint is p99.** These have different causes; median work rarely moves the tail.
- **Force-merging a live index.** A good operation on a completed one and a harmful one on an index still being written.
- **Adding nodes to fix a query shape.** Capacity doesn't fix a leading wildcard.
- **Caching results before understanding the staleness cost.** The freshness complaint you'll cause is harder to diagnose than the latency you'll fix.
- **Tuning that the product will invalidate.** A configuration balanced for today's query mix goes stale the moment someone adds a facet; prefer structural fixes over numeric ones where both are available.

## Trade-offs

**Every lever here is paid for in freshness, accuracy, or flexibility.**

- Longer refresh interval → larger staleness window.
- Skipping exact hit counts → "about 10,000 results," and no reliable total to paginate against.
- Routing by tenant → shard skew, and a reindex to change the key.
- Fewer shards → less parallelism for a single query, and a harder growth path later.
- Result caching → staleness added directly on top of index staleness.
- Force-merge → only valid for indices that will never be written again.

**Isolation costs money.** Separating autocomplete, interactive search, exports, and analytics onto different indices or clusters is the most reliable fix for cross-workload interference, and it's more infrastructure and more operational surface.

**Tail latency is bought with capacity that sits idle.** Headroom is the mechanism; a cluster running hot has no tail budget, and the only way to have one is to pay for a machine that's mostly not busy.

**Guardrails reject legitimate queries.** A limit on fuzzy expansions or terms-query size will eventually block something a user genuinely wanted. That's the correct trade against an unbounded query taking down search for everyone, and it needs an error message that says so.

**Tuning expires.** Shard counts, cache sizes, and thresholds encode assumptions about a query mix and a corpus size, both of which move. Anything tuned needs a note saying what it was tuned against.

## Alternatives

**Search less data.** Time-based indices with retention, and hot/warm tiering that keeps recent data on fast storage and older data on cheaper storage, mean most queries touch a fraction of the corpus. For anything with a time dimension — tickets, logs, orders, messages — this beats every tuning parameter in this article combined.

**Take the workload off search.** Reporting and analytics queries against a search cluster are the most common source of unexplained load. They belong in a column store (Module 6). Exports belong in a job queue (Module 10).

**Cache at the edge.** Anonymous, shared result pages — category listings, public search landing pages — are ordinary HTTP responses and can be cached by a CDN, removing the request entirely rather than making it faster.

**Scale up rather than out.** For search specifically, a larger machine with more filesystem cache frequently outperforms more small machines, because it changes whether the working set is in memory. This runs against the usual horizontal-scaling reflex and is worth testing before accepting it.

**Separate storage from compute.** Managed tiers that query data directly from object storage make cold data cheap to retain and slow to query, which is the right trade for an archive nobody searches interactively.

**Go back to the database.** If the workload turned out to be filter-dominated with little real ranking — most queries are `status` plus `assignee` plus a date range — a well-indexed relational query may be faster and considerably cheaper than a search cluster. Descending 12.1a's ladder is a legitimate move, and it happens more often than anyone writes up.

## How to Achieve It

**L0 — no measurement.** Anything done from here is guesswork. Don't tune; instrument.

**L1 — measure.** Client-side latency percentiles segmented by query shape, slow logs on with sane thresholds, and a dashboard showing hits-per-query distribution alongside latency. This step is the precondition for all the others, and it's usually a day's work.

**L2 — the structural cheap wins.** Stop tracking exact totals, replace deep pagination with a cursor, filter the source fields you return, and put a guardrail at the API boundary against unbounded query shapes. None of these requires a reindex and together they typically move p99 more than anything that does.

**L3 — workload isolation.** Separate indices or endpoints for autocomplete, interactive search, and exports; per-tenant rate limiting (Module 18); a dedicated path for bulk reads. This is what stops one customer from being everyone's problem.

**L4 — the structural changes that need a reindex.** Right-sized shards, routing by tenant, and a document model trimmed of fields nothing queries. Plan these together, since they share one rebuild — and by now the alias-and-reindex procedure from 12.2 is routine, which is the point of having made it routine.

**L5 — continuous.** Replay real query logs as a load test, and put a latency budget next to the relevance score in CI. That's the same judgment file from 12.3a, used a second way: one run reports whether results got better, the other whether they got slower. A relevance change that improves NDCG by two points and doubles p99 is a change you want to know about before it ships, and at that point you have the two numbers to make the trade with.

## Implementation

TypeScript. Three short pieces, each carrying one of the levers above.

**The query, with the cheap wins applied:**

```ts
const res = await es.search({
  index: "products",
  track_total_hits: 1000,          // "1000+" is enough; enables top-k skipping
  timeout: "800ms",                // bounded — but see below
  _source: ["title", "price_cents", "thumb_url"],   // not the 40 KB description
  size: 20,
  query: { /* filter + must, as in 12.3a */ }
});

if (res.timed_out) {
  metrics.increment("search.partial_results");   // NOT silently fine
}
```

The `timed_out` check is the point of that block. A timeout here does not throw; it returns whatever was collected, and a result list that is quietly incomplete under load is a far worse failure than an error, because it presents as a relevance problem and gets investigated in the wrong place.

**Pagination that doesn't degrade:**

```ts
async function* pages(query: object, pit: string) {
  let after: unknown[] | undefined;
  while (true) {
    const res = await es.search({
      pit: { id: pit, keep_alive: "2m" },        // stable snapshot
      query,
      size: 1000,
      sort: [{ updated_at: "desc" }, { _shard_doc: "asc" }],  // ← tiebreaker
      search_after: after
    });
    const hits = res.hits.hits;
    if (hits.length === 0) return;
    yield hits;
    after = hits[hits.length - 1].sort;         // cursor = last row's sort values
  }
}
```

`_shard_doc` is not decoration. Without a unique final sort key, two documents sharing a timestamp sit either side of a page boundary in an undefined order, and an export silently duplicates one and drops the other. That bug surfaces as a customer reconciling a spreadsheet three weeks later.

**The guardrail**, because the API boundary is the only place this can be enforced:

```ts
const LIMITS = { maxTerms: 1024, maxFrom: 1000, maxFacets: 8 };

function validate(req: SearchRequest) {
  if (req.ids && req.ids.length > LIMITS.maxTerms)
    throw new BadRequest(`At most ${LIMITS.maxTerms} ids; use the export API.`);
  if ((req.from ?? 0) > LIMITS.maxFrom)
    throw new BadRequest("Deep pages are unavailable; use the cursor parameter.");
  if (req.q?.startsWith("*"))
    throw new BadRequest("Leading wildcards are not supported.");
  if (req.facets && req.facets.length > LIMITS.maxFacets)
    throw new BadRequest(`At most ${LIMITS.maxFacets} facets per request.`);
}
```

Unremarkable code, and it's the difference between a user writing a slow query and a user taking search down for everyone. The error messages matter as much as the checks: each one names the supported alternative, because a guardrail that blocks a real need without pointing somewhere becomes a ticket asking you to raise the limit — which is how the result window reached 100,000 in *The Problem*.

**And the bulk-load recipe,** which is settings rather than code: disable refresh and drop replicas to zero before a full reindex, restore both afterwards, then merge the finished index down before swapping the alias. Three settings changes, frequently a several-fold difference in rebuild time, and the reason the 12.2 reindex can happen on a Tuesday afternoon instead of at 2am.

## Further Reading

- **Elastic's "Tune for search speed," "Tune for indexing speed," and "Size your shards."** Short, specific, and the closest thing to an authoritative checklist. Read all three before changing anything.
- **Elasticsearch documentation: "Paginate search results"** (`search_after`, point-in-time), **`track_total_hits`,** the **Profile API,** and **slow log settings.** The first two are the highest-value paragraphs in the whole reference for most deployments.
- **Dean & Barroso, "The Tail at Scale" (CACM, 2013).** Why fan-out amplifies tail latency and what the standard mitigations are — hedged requests, tied requests, micro-partitioning. The conceptual foundation for the shard-count discussion here, and it applies far beyond search.
- **Adrien Grand's writing and talks on Lucene's block-max WAND and top-k skipping.** The mechanism behind why an exact hit count is expensive and why giving it up is such a large win.
- **Lucene's `MergePolicy` documentation, and Mike McCandless's posts on merges and indexing throughput.** The layer that explains I/O contention between indexing and search, which nothing at the cluster API makes visible.
- **Brendan Gregg, _Systems Performance_, on the USE method.** The right frame for "CPU is low and latency is high" — utilization, saturation, errors, per resource. Search clusters reward this frame because the bottleneck is usually memory or disk, not the thing you were watching.
- **Module 22 (performance profiling) and Module 19 (observability)** in this collection cover the general practice that this article specializes; Module 18 covers the rate limiting that L3 depends on.

A **Go** sibling would be worth writing, and the interesting version isn't a translation of the queries above — it's the **search gateway** sitting in front of the cluster: request budgets, per-tenant rate limits, circuit breaking, and timeout propagation. The specific thing Go surfaces is `context` cancellation carried end to end, so that a browser abandoning an autocomplete request (12.3c) cancels the downstream call instead of leaving the cluster to finish work nobody will read — which at autocomplete's request volume is a material share of total load, and is invisible in runtimes where cancellation isn't threaded through the call chain. It would also cover hedged requests against replicas, which is the direct implementation of the Dean & Barroso mitigation. Not yet written.

The habit, and it's the one that generalizes furthest out of this module: **when a system gets slow, find out which term in the cost model grew before touching any of them.** Search makes this unusually explicit — fan-out, matched documents, work per document, work per returned document, and whether the bytes are in memory — but every read path has a decomposition like it, and the reason performance work so often fails is that people optimize the term they understand rather than the one that changed.
