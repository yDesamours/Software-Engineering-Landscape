# Splitting for Scale: Where to Cut, and What the Network Costs

_Module 23.5 — Scalability Patterns_

## The Problem

Suppose you run a podcast hosting platform with about 40,000 shows. Its traffic comes in very different shapes:

```
work                    rate            cost per unit        shape
──────────────────────  ──────────────  ───────────────────  ─────────────────────────
RSS feeds (apps poll)   25,000 req/s    ~2 ms, mostly cache  spikes 3× when a big show
                                                             publishes
creator dashboard       400 req/s       ~60 ms, DB-heavy     office hours
audio transcoding       ~30 uploads/min 2 CPU-minutes each   bursty
download analytics      6,000 events/s  tiny writes          follows listening
```

All of it runs as one Java monolith, which 23.1a made stateless, on 40 instances. Every instance is sized for the heaviest thing any instance might do:

- **2 GB of memory and a 90-second startup,** because every instance loads the transcoding libraries and warms every cache.
- **A database pool of 20,** so the fleet holds 800 connections, though feeds barely touch the database.
- **Transcoding on the same instances,** so a burst of uploads pushes feed p99 from 30 ms to 900 ms.

When a big show publishes, the autoscaler needs about three minutes to add capacity: 90 seconds per instance plus warm-up. The spike is over by then.

So the team splits the monolith, and to do it properly they split it into five services in one quarter: `feeds`, `media` (episodes, audio, transcoding), `accounts`, `analytics` and `dashboard`. The feeds service is a success. It's a 30 MB image that starts in 2 seconds, uses a database pool of 2, and scales from 4 to 60 instances in under a minute. The rest of the quarter goes less well:

- **The feed path got slower and less reliable.** A feed request now asks `accounts` whether the show is private and asks `media` for signed audio URLs, once per episode. A 300-episode feed makes 300 calls. Feed p99 goes from 30 ms to 380 ms, and any slowdown in either service now breaks feeds.
- **Every `media` deploy broke feeds for minutes.** The feeds service's media client resolved `media.internal` to a list of pod addresses once, at startup. After a rolling deploy replaced every media pod, feeds held a list of addresses that no longer existed, until someone restarted it.
- **The creator app got slow.** Its dashboard screen now makes 14 calls to four services over a mobile connection and takes 6 seconds to load. Each service also handles authentication, CORS and rate limiting in its own slightly different way.
- **"Top episodes by downloads" stopped working.** Episodes live in `media` and download counts in `analytics`. The dashboard fetches all 2,000 of a show's episodes, then 2,000 counts, and sorts in memory. Pagination is broken.

Looking back, only two of the splits were about scale: feeds, and transcoding. Those are the parts whose load looked nothing like the rest. The others were answers to a question about team boundaries (2.1) that nobody had asked, and each added network hops to paths that had worked fine in-process.

## What It Is

**Splitting for scale** means giving part of a system its own deployment and scaling unit because its load differs from the rest: its rate, resource profile, spikiness or startup needs. Module 2.1 covered the general question of monoliths and services, and its short version applies here: a service boundary is a module boundary plus a network. This article is about the scale case, where the reason for paying for the network is that one part needs to grow, shrink or fail independently.

Once parts of the system live in different processes, three pieces of machinery appear:

- **Inter-service communication:** synchronous calls (HTTP with JSON, gRPC) or asynchronous messages (queues, events).
- **Service discovery:** how a caller finds the current addresses of a service whose instances come and go.
- **An API gateway:** a single entry point that routes external traffic to the right service and handles shared concerns at the edge. A **backend for frontend** (BFF) is a gateway, or a small service behind one, built for one kind of client.

Module 36 goes deeper on service meshes, gateways, circuit breakers and tracing across many services. This article covers the decisions that come first.

## Recognizing the Problem

- One endpoint or job accounts for most of your traffic or CPU, while the fleet is sized for the rest.
- Scaling for one feature's spike means starting copies of the whole application, and they start too slowly to help.
- One workload's resource use (CPU, memory, connections) degrades an unrelated one on the same instances.
- Instances carry large memory, dependencies or connection pools that most of their traffic never uses.

**Signs that a split was made in the wrong place, or without the machinery it needs:**

- A request path's p99 grew after a split, and its availability now depends on several services.
- Calls between services scale with the size of the data: once per item, per row, per episode.
- Errors spike during another service's deploys.
- Mobile or browser clients call several of your services to render one screen.
- A list sorted or filtered by data from two services can't be paginated.
- Each service implements authentication and rate limiting slightly differently.

## How It Works

### Where to cut

For scale, cut where the **load profile changes** and where **little traffic crosses the cut**. A table like the one in the opening, per endpoint and per job, usually makes the candidates obvious. For each one, ask:

- Is its rate or spikiness very different from the rest?
- Does it need different resources: CPU, memory, GPU, connections?
- Can its hot path run **without synchronous calls** back into the rest of the system?
- How many calls would cross the cut per request, and does that number grow with data size?

Feeds pass all four tests, once the data they need is copied to them rather than fetched per request. The dashboard fails the third and fourth: it needs data from everywhere, on every request.

There's a cheaper step before any extraction. **Run the same build in different roles.** Deploy the monolith's image several times with a role setting: one pool serves only `/feeds/*`, another serves the dashboard, a third runs only transcoding workers. A path rule at the load balancer routes traffic to the right pool (23.1b), and each pool gets its own configuration, instance size and autoscaling:

```
                 load balancer (path rules)
       /feeds/*  │           │ everything else
                 ▼           ▼
   [same image, ROLE=feeds]   [same image, ROLE=web]   [same image, ROLE=transcode]
    small DB pool, big cache   normal settings          queue consumers only
    scales on req/s            scales on CPU            scales on backlog (23.4)
```

This gets you isolation and independent scaling in days, with no new network hops and no new failure modes. It doesn't get you a smaller image, a faster startup, or independent deploys, because every pool still ships the whole application. When those matter, which for feeds they did, it's time to extract.

### What a network hop costs

Every synchronous call across a boundary adds serialization, a network round trip, and a new way to fail. Three effects matter at scale:

**Latency adds up along a chain.** A request that calls A, then B, then C pays each one's latency in turn, and its availability is roughly the product of theirs (1.2).

**Tails amplify with fan-out.** If each call has a 1% chance of being slow, a request that makes N such calls is slow whenever any one of them is:

```
chance that a request hits at least one slow call = 1 − 0.99^N

N = 1     1%
N = 10    10%
N = 100   63%
```

So a dependency's p99 becomes the median experience of a caller that fans out widely. This is the main point of Dean and Barroso's "The Tail at Scale."

**Chattiness scales with data.** A call per item turns a 300-episode feed into 300 round trips. That's the N+1 query problem (6.4), moved onto the network.

The responses, roughly in order of value:

- **Remove synchronous calls from the hot path.** Keep a local copy of the data the hot path needs, fed by the owning service's events (23.2b), or precompute the response. Feeds don't need to ask `accounts` whether a show is private on every request if they hold a copy of that flag that's updated within seconds.
- **Make calls coarse.** Send one batch request for all 300 episodes instead of 300 single ones.
- **Fan out in parallel, not in sequence,** when calls are independent.
- **Hedge slow reads.** If an idempotent read hasn't answered by about its p95 latency, send a second copy to another instance and use whichever answers first. Only about 1 in 20 requests pays for a second copy, and the slowest tail is cut sharply.
- **Degrade instead of failing.** Serve the last good response when a dependency is slow (13.2b's serve-stale), if the data allows it.

### Choosing how services talk

```
channel               caller waits?   good for                         costs
────────────────────  ──────────────  ───────────────────────────────  ──────────────────────────────
HTTP + JSON           yes             external APIs, low-volume         text parsing, looser contracts
                                      internal calls, HTTP caching
gRPC                  yes             high-volume internal calls,       needs L7 or client-side
                                      streaming, typed contracts,       balancing (23.1b); limited
                                      built-in deadlines                browser support
queue / event stream  no              commands that can wait (23.4),    eventual consistency, no
                                      facts other services react to     immediate answer
```

A workable default: **queries go synchronous, commands that can wait go through a queue, and facts about what happened are published as events.** Publishing an event reliably along with a database change needs an outbox or change data capture (Module 37, 38.4).

**Every synchronous call needs a deadline, and deadlines must travel.** If the feed handler has a 200 ms budget and has already used 150 ms, a call it makes now should get 50 ms, not a fresh 2 seconds. gRPC carries the remaining deadline to the server automatically, and the server's own calls inherit it. With plain HTTP you have to pass it yourself, for example in a header. Without it, a downstream service keeps working on requests whose callers gave up long ago, which is how one slow service fills the whole system with abandoned work.

Retry at one layer only, with a budget (23.1b, 18.3), and stop calling a dependency that's clearly failing (circuit breakers, 36.3).

### Service discovery

Instances of a service change constantly: autoscaling adds and removes them, and every deploy replaces them. A caller needs the *current* addresses, and there are four common ways to get them:

- **A load balancer behind a stable name** (server-side discovery). The caller resolves one name that points at a balancer, and the balancer tracks healthy instances. It's simple, at the cost of an extra hop.
- **The platform's discovery.** A Kubernetes Service gives a stable virtual IP, and connections to it are spread across ready pods at the connection level (L4), so long-lived HTTP/2 connections stay pinned (23.1b). A *headless* Service returns the pod addresses themselves through DNS, for callers that balance client-side.
- **A registry** such as Consul or Eureka. Instances register with health information, and clients fetch or watch the list and balance across it.
- **A service mesh** (36.1), which moves discovery and balancing into a proxy next to each caller.

The failure modes are the same whichever you pick:

- **Stale lists.** A client that resolves once, like the media client in the opening, or a runtime that caches DNS answers for a long time, keeps using addresses that no longer exist. Re-resolve on a schedule, and give pooled connections a maximum age so traffic moves to new instances (23.1b). gRPC's DNS resolver re-resolves when connections fail, and its `round_robin` policy balances across the results.
- **The registry is a dependency.** If it goes down, callers should keep using the last good list rather than dropping to nothing. This is often called *failing static*.
- **Propagation delay.** A terminating instance may keep receiving traffic for a few seconds after it starts shutting down, which is why 23.1a's shutdown sequence fails readiness first and waits.

### The gateway

When external clients need several services, a gateway gives them one entry point:

- **Routing** by path or host to the right service, which also lets you move a route from the monolith to a new service without clients noticing.
- **Edge concerns handled once:** TLS, authentication, rate limits (Module 18), request size limits.
- **Aggregation.** The gateway, or a BFF behind it, makes the 14 dashboard calls on the fast internal network and returns one response to the mobile app. GraphQL servers often play this role (Module 8).

Its risks are predictable. Business logic creeps into it until it's a new monolith that every team must change. It's in the path of every request, so it must be redundant and fast. And a single gateway configuration owned by one team becomes a queue for everyone else. A BFF per client type, owned by the team that builds that client, limits the creep. 36.2 covers gateway patterns in depth.

### Data after a split

A service that scales independently must own its data; a shared table ties the services' schemas and loads back together (2.1). Other services then have three ways to read that data:

```
option                          freshness    runtime coupling    cost
──────────────────────────────  ───────────  ──────────────────  ──────────────────────────
call the owner's API            current      high: owner must    latency, fan-out
                                             be up and fast
keep a local copy from events   seconds old  low                 storage, projector,
                                                                 staleness (23.2b)
read the owner's database       current      schema coupling:    the distributed monolith
directly                                     owner can't change   (2.1)
```

Lists that combine data from several services, like "top episodes by downloads," become a read model owned by the service that needs them: `dashboard` subscribes to episode events from `media` and count updates from `analytics`, and keeps one sortable, pageable table (23.2b). Changes that must update several services together become sagas (37.4).

### Scaling each piece

Once split, each service scales on the signal that matches its load: feeds on request rate, transcoding on backlog age (23.4, 10.4b), the dashboard on CPU. Two costs come with it:

- **A floor per service.** Two instances per service for availability (23.1a), times every service, running all night.
- **The split only helps if startup is fast.** Feeds scale quickly because the extracted service starts in 2 seconds. An extracted service that still takes 90 seconds to start gains little from autoscaling.

## When It's Appropriate

- **Role-based pools of one build** as soon as one workload's load differs sharply from the rest or disturbs it, such as feeds at 25,000 req/s next to a dashboard at 400, or transcoding next to either.
- **Extracting a service** when a role pool isn't enough: the component needs a much smaller or faster-starting deployable, different hardware, or its own deploy cadence, and its hot path can run without synchronous calls to the rest.
- **gRPC** for high-volume or streaming calls between services, especially across languages.
- **Events and local copies** when a service needs another service's data on its hot path and can tolerate seconds of staleness.
- **Hedged reads** when a request fans out to many backends and tail latency dominates, as in search or feed assembly.
- **A registry or mesh** when many services change often and need client-side balancing. Otherwise the platform's discovery or a load balancer is enough.
- **A gateway** once external clients call more than one service. **A BFF** once client types need clearly different responses, such as a mobile app and a web dashboard.

## When It's Unnecessary or Overkill

- **Splitting when the whole application already scales horizontally** and no single part has a distinct load. Scale the monolith (23.1a).
- **Extracting several services at once for scale.** Extract the one outlier, learn what it costs, then decide about the next.
- **Extracting a component that needs synchronous data from several others on every request.** It will be slower and less available than it was in-process.
- **gRPC for a 20 req/s internal call** between two teams that already know HTTP well.
- **A registry** when Kubernetes Services or a load balancer already cover your needs.
- **A gateway in front of a single service.**
- **Hedging writes,** or hedging at volumes where tail latency isn't the problem.

## Trade-offs

- **Each hop adds latency, a failure mode and a serialization cost.** At high volume, encoding and decoding can take a noticeable share of CPU.
- **Partial failure becomes normal.** Timeouts, retries, deadlines, fallbacks and circuit breakers are now required code, not refinements.
- **Versions skew.** Services deploy independently, so every API and event must work with both the previous and the next version of its callers (Module 33).
- **Operations multiply:** pipelines, dashboards, alerts, on-call rotations, and a per-service instance floor.
- **Debugging needs distributed tracing** (19.2b) to follow one request across services.
- **Data consistency weakens.** Local copies are stale, cross-service writes need sagas, and cross-service queries need read models.
- **Discovery and the gateway become critical infrastructure,** with their own failure modes and owners.
- **Role pools are cheap but partial.** Every pool still carries the whole application's size, startup time and deploy cadence.

## Alternatives

- **Scale the monolith** (23.1a) when nothing has a distinct load profile.
- **Cache the hot path at the edge.** Feeds are cacheable: with `ETag` and conditional requests, most polls end as `304 Not Modified` at a CDN and never reach your servers (13.1a, 7.4a). That alone might have removed the need to extract feeds.
- **Move heavy work to queues and workers** (23.4). A worker pool is itself a split by load, and usually the first one worth making.
- **Isolate inside the process** with separate thread or connection pools per workload (bulkheads, Module 10), when the problem is interference rather than scaling.
- **Split into cells** (23.6) when the pressure is total size or customer isolation rather than one component's load.

## How to Achieve It

**1. Build the load-profile table** per endpoint and per job: rate, cost, resources, spikiness, startup needs. *Move on when* one workload clearly stands apart.

**2. Try the cheaper fixes first:** edge caching, moving work to queues, fixing the expensive code (Module 22). *Move on when* the outlier still dominates.

**3. Deploy role-based pools of the same build,** with path routing and per-pool configuration and autoscaling. *Move on when* the pool still carries weight it doesn't need (image size, memory, startup time), or deploy coupling hurts.

**4. Remove synchronous dependencies from the candidate's hot path** while it's still in-process. Give it local copies of the data it needs and batch any remaining calls. *Move on when* the hot path touches nothing outside its own module per request.

**5. Extract that one service** with its own data. Route its traffic to the new service at the load balancer or gateway, compare responses on shadowed traffic, and shift traffic gradually (the strangler fig approach).

**6. Put the communication basics in place before a second extraction:** deadlines that propagate, one retry layer with a budget, per-service timeouts, discovery that re-resolves and fails static, and distributed tracing.

**7. Add a gateway** when external clients need more than one service, and **a BFF** when client types diverge.

**8. Extract the next service only when the next outlier appears** in the table.

## Implementation

The code is Go, because its `context` package carries deadlines and cancellation through every call, and gRPC-go sends that deadline to the server automatically. That makes deadline propagation visible in a few lines. The two snippets show the cheapest split and the most useful habit for a hot path that does call another service.

### One build, several roles

```go
func main() {
	role := envOr("ROLE", "all") // "all", "feeds", "web", "transcode"
	app := newApp(configFor(role)) // pool sizes, cache sizes, which clients to open

	mux := http.NewServeMux()
	if role == "all" || role == "feeds" {
		mux.Handle("GET /feeds/{show}", app.feedHandler())
	}
	if role == "all" || role == "web" {
		mux.Handle("/dashboard/", app.dashboardHandler())
		mux.Handle("/api/", app.apiHandler())
	}
	if role == "all" || role == "transcode" {
		go app.runTranscodeWorkers(context.Background()) // queue consumers, no HTTP routes
	}
	mux.Handle("GET /ready", app.readiness())

	log.Fatal(http.ListenAndServe(":8080", mux))
}

func configFor(role string) Config {
	switch role {
	case "feeds":
		return Config{DBPool: 2, FeedCacheMB: 1024, OpenMediaClient: true}
	case "transcode":
		return Config{DBPool: 4, TranscodeConcurrency: 2}
	default:
		return Config{DBPool: 10, FeedCacheMB: 64}
	}
}
```

Each role is deployed separately, scaled on its own signal, and receives traffic through path rules at the load balancer. The feeds pool no longer holds 20 database connections per instance, and transcoding can no longer slow feeds down.

> **What this doesn't change.** Every pool still ships the full binary with every dependency, starts as slowly as the whole application, and deploys together with everything else. If those costs matter, as they did for feeds, extraction is the next step. `role == "all"` keeps local development and small environments as a single process.

### A hot-path call with a budget

```go
// The feed handler has 200 ms in total. Every call gets only what's left.
func (a *App) feedHandler() http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		ctx, cancel := context.WithTimeout(r.Context(), 200*time.Millisecond)
		defer cancel()
		show := r.PathValue("show")

		// One batched call for all episodes, hedged at about media's p95.
		urls, err := hedged(ctx, 25*time.Millisecond, func(ctx context.Context) (map[string]string, error) {
			return a.media.SignedURLs(ctx, show) // gRPC: the remaining deadline travels with ctx
		})
		if err != nil {
			if last, ok := a.lastGoodFeed(show); ok { // serve stale rather than fail
				metrics.StaleFeedsServed.Inc()
				w.Write(last)
				return
			}
			http.Error(w, "feed unavailable", http.StatusServiceUnavailable)
			return
		}
		a.renderFeed(w, show, urls) // privacy flag comes from a local copy kept current by events
	})
}

// hedged starts a second identical call if the first hasn't answered after delay,
// and returns the first success. Use it only for idempotent reads.
func hedged[T any](ctx context.Context, delay time.Duration, call func(context.Context) (T, error)) (T, error) {
	ctx, cancel := context.WithCancel(ctx)
	defer cancel() // whichever call is still running is cancelled

	type result struct {
		v   T
		err error
	}
	results := make(chan result, 2) // buffered, so the losing call never blocks
	launch := func() {
		go func() { v, err := call(ctx); results <- result{v, err} }()
	}

	launch()
	pending := 1
	timer := time.NewTimer(delay)
	defer timer.Stop()

	var last result
	for pending > 0 {
		select {
		case <-timer.C:
			launch() // the first call is slow: race a second one
			pending++
		case r := <-results:
			pending--
			if r.err == nil {
				return r.v, nil
			}
			last = r
		}
	}
	return last.v, last.err
}
```

> **Why it's written this way.**
>
> - **The deadline is set once, at the edge of the request,** and everything downstream inherits it. If `media` calls another service, that call gets whatever is left of the 200 ms, and when the feed request gives up, the work below it is cancelled instead of finishing for nobody.
> - **Hedging isn't retrying.** A call that fails quickly isn't repeated here; that's the retry layer's job, and it should exist in only one place. Hedging only races a *slow* call. With the delay near media's p95, about 1 in 20 requests sends a second copy, so budget that extra load and cap it if media gets slow across the board, when every request would otherwise hedge.
> - **The second copy only helps if it reaches a different instance.** With client-side balancing it usually does; behind a single pinned connection it may not (23.1b).
> - **Serving stale is a per-data decision.** A feed that's a few minutes old is fine. The privacy flag is different: it comes from a local copy, and a show just made private must not keep being served. That copy's maximum acceptable lag should be monitored, and the handler should refuse to serve a private-capable show if the copy is too far behind.
> - **The call is already batched.** One `SignedURLs` call per feed, not one per episode, is what took the call count from 300 to 1.

A **Java** sibling would be worth writing, because the JVM makes two of this article's problems easy to hit. The JVM caches DNS lookups according to the `networkaddress.cache.ttl` security property, which caches forever when a security manager is installed and otherwise defaults to 30 seconds in OpenJDK, so the stale-address problem depends on configuration most teams never look at. And Java has no built-in context that carries a deadline through every call, so deadline propagation depends on gRPC's own context, framework support, or careful plumbing. A Java article could compare those options with Go's `context`. Not yet written.

The habit to take from this: **before splitting something out, count the calls that would cross the cut on its hottest path.** If that number isn't close to zero, make it so first, or don't split there.
