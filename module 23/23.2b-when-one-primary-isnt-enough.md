# When One Primary Isn't Enough: Read Models and the Decision to Partition

_Module 23.2b — Scalability Patterns_

## The Problem

Suppose you run a customer-support platform. About 6,000 companies use it to answer their customers' emails and chats, and at peak around 12,000 support agents are logged in. Everything lives in one Postgres cluster: a primary with three read replicas, set up the way 23.2a describes. The database holds 1.8 TB, and 1.4 TB of that is one table, `messages`.

Two separate kinds of trouble arrive in the same quarter.

**The read that replicas can't fix.** Every agent's inbox refreshes every 15 seconds, which is about 800 inbox queries a second at peak. The query joins tickets, their latest message, assignments, customers, tags and SLA policies. It sorts by "time until this ticket breaches its SLA", a value computed from the policy and the company's business hours, so no index can serve the sort. On a replica it takes about 60 ms at the median and 2.5 seconds for the largest companies. The inbox alone keeps roughly 50 cores busy across the replicas.

The obvious move is a fourth replica. It would be another full 1.8 TB copy, and it would run the same 60 ms query 800 times a second. Replicas share the cost of an expensive query out; they don't make it any cheaper. Meanwhile, across all 6,000 companies, only about 40 ticket changes per second affect anyone's inbox. A typical agent's inbox is recomputed four times a minute and actually changes about once.

**The writes that one server can't absorb.** Incoming email, chat, automations and webhooks write about 3,500 rows a second at peak, and `messages` grows by 90 GB a month. The primary is already one size below the largest instance the team is willing to buy. And the size itself is causing problems that more CPU wouldn't solve:

- Autovacuum on `messages` takes more than 20 hours to finish a pass, and table and index bloat keep growing.
- Every night, a job deletes messages older than 24 months (they've already been archived to object storage). The `DELETE` runs for four hours and produces a burst of WAL that the replicas replay slowly.
- When one large company runs a bulk macro on 300,000 tickets, commit latency p99 goes from 8 ms to 140 ms for every other company.
- A test restore from backup takes 11 hours. The recovery-time objective is 4.

```
replica lag, one day
00:00  ▏                        20 ms
03:00  ████████████████████     90 s    ← retention DELETE
09:30  ████                     18 s    ← one company's bulk macro
14:00  ▏                        25 ms
```

The architecture meeting produces two proposals. One engineer wants more replicas. Another wants to shard the database by company, now. Neither covers both problems. More replicas copy the expensive inbox query and do nothing for writes. Sharding would split the writes, but every shard would still run the same 60 ms inbox query, and the four-hour `DELETE` would simply run on six servers instead of one.

## What It Is

These are two different tools for two different pressures, and they're often confused because both involve "splitting the database."

A **read model** is data derived from your main tables and stored in the shape one particular screen or query needs, so that answering the query is cheap. The inbox becomes a single table, one row per open ticket, already joined, with the SLA deadline already computed and an index that matches the sort. Keeping the model you *write* to separate from the models you *read* from is called **CQRS**, Command Query Responsibility Segregation. At this scale, the practical meaning is simple: stop computing the inbox on every read, and compute it when a ticket changes.

This is different from a read replica. A replica is the *same* schema, copied. A read model is a *different* shape, computed. CQRS is also independent of event sourcing (2.4, Module 37). You can build read models from ordinary tables without ever storing events as your source of truth.

**Partitioning** splits one dataset into pieces by a key, so each piece is smaller. It comes in two very different strengths:

- **Partitioning in place** divides a table into pieces inside one database server. Maintenance gets easier, but the server's CPU and write limit stay the same.
- **Splitting across servers** puts pieces on different databases. When the split is by a key such as the company, it's called **sharding**, and it's the only tool here that raises the write limit.

This article is about recognizing which pressure you have and making the decision to partition. How shards are assigned, moved and rebalanced is 38.2's subject.

## Recognizing the Problem

**Read-shape pressure:**

- The top queries by total time are joins or aggregations whose results change far less often than they're read.
- Adding replicas lowered the primary's load, but the same query costs the same on every replica.
- Sorts or filters use computed values that no index can serve.
- A screen's query touches five or more tables and gets slower as a customer's data grows.

**Write and size pressure:**

- `INSERT`s and `UPDATE`s dominate `pg_stat_statements` on the primary, and WAL volume grows month over month.
- Replica lag follows the write rate even when the replicas are idle.
- The primary is at or near the largest instance you'll pay for.
- Autovacuum on the biggest table takes hours, and bloat keeps growing.
- Bulk deletes for retention run for hours and cause lag.
- A test restore takes longer than your recovery objective.
- One customer's activity changes every other customer's latency.

**A signal that partitioning is possible:** almost every query already filters by the same column, such as `tenant_id` or `user_id`.

## How It Works

### Two pressures, four tools

```
pressure                              tool                        raises write limit?
────────────────────────────────────  ──────────────────────────  ───────────────────
many reads of cheap queries           replicas (23.2a)            no
reads that are expensive to compute   read models (CQRS)          no (adds some writes)
one table too big to maintain         partitioning in place       no
writes or size beyond one server      splitting across servers    yes
```

Most systems need the first rows long before the last one, and many never need the last one at all.

### Read models

The mechanism has three parts: capture every change on the write side, apply each change to the read model, and query the read model.

```
ticket update ──▶ primary (tickets, messages, …)
                     │ change captured in the same commit
                     ▼
                change feed ──▶ projector ──▶ inbox_items
                                                 ▲
agent's inbox ───────────────────────────────────┘
   one index range scan: (tenant_id, team_id, status, sla_due_at)
```

The component that applies changes is usually called a **projector** or **projection**. For the inbox, it turns a 60 ms query into a ~2 ms index scan. The work moves from 800 reads a second to 40 changes a second.

**Where a read model can live**, from least to most machinery:

1. **A materialized view** in the same database. Postgres's `REFRESH MATERIALIZED VIEW CONCURRENTLY` recomputes the whole view without blocking readers. That's fine for a small view that can be minutes stale. Its cost grows with the size of the view, not with the number of changes, because Postgres has no built-in incremental refresh.
2. **A table maintained in the same transaction** as the write, by application code or a trigger. It's never stale, but every write pays for it, and it stays inside the same server.
3. **A table maintained asynchronously** by a projector, in the same database or a different one. This is the usual CQRS read side.
4. **A different kind of store** entirely: a search index (Module 12), sorted sets in Redis, a columnar store for analytics. Each is a read model shaped for one kind of question.

**Capturing changes reliably is the hard part.** Application code that commits to the database and then publishes to a message broker will eventually do one without the other, and the read model silently drifts. The two reliable options are a **transactional outbox**, where the change is written as a row in the same transaction and relayed afterwards (Module 37), and **change data capture**, which reads the database's own log (38.4).

**A projector has four rules:**

- **Idempotent.** Change feeds deliver at least once, so applying the same change twice must do nothing.
- **Safe against reordering.** Each change carries the entity's version, and the projector ignores anything older than what it already has.
- **Checkpointed with its writes.** The position it has processed is saved in the same transaction as the rows it wrote.
- **Rebuildable.** A read model is derived data. You must be able to delete it and rebuild it from the write side, which is also how you change its schema: build the new version beside the old one, switch reads, drop the old one.

**Read models bring back 23.2a's problems.** A projector has lag, just as a replica does, so read-your-writes breaks again. An agent assigns a ticket to herself, and it's missing from her "Mine" tab for half a second. The fixes are the same ones: the write returns the feed position, and the read waits until the projector's checkpoint has passed it. For a single user's own action, many UIs simply update the screen optimistically.

**Some changes fan out.** When a company renames a tag, 200,000 inbox rows need updating. Denormalizing is what made the read cheap, and it's also what makes this write expensive. Such changes need a set-based update in the projector, run in batches.

### Partitioning in place

Postgres's declarative partitioning divides one logical table into child tables by a key. For `messages`, partitioning by month changes the retention problem completely:

```sql
CREATE TABLE messages (
  tenant_id  bigint      NOT NULL,
  id         uuid        NOT NULL,
  ticket_id  bigint      NOT NULL,
  created_at timestamptz NOT NULL,
  body       text,
  PRIMARY KEY (tenant_id, created_at, id)   -- must include the partition key
) PARTITION BY RANGE (created_at);

CREATE TABLE messages_2026_09 PARTITION OF messages
  FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');

-- Retention becomes a metadata change instead of a four-hour DELETE
ALTER TABLE messages DETACH PARTITION messages_2024_08 CONCURRENTLY;
DROP TABLE messages_2024_08;
```

**What it gives you:**

- Retention by dropping a partition, with no bloat and no WAL burst.
- Vacuum and index maintenance that run per partition, on pieces small enough to finish.
- Smaller indexes, and recent partitions that fit in memory.
- **Partition pruning:** queries that filter on the key skip partitions they can't match.

**What it doesn't give you:** more CPU, less WAL, or a higher write limit. The server is the same server.

**What it demands:** unique constraints and primary keys must include the partition key, queries that don't filter on the key visit every partition, and future partitions must exist before rows arrive. A missing partition makes inserts fail, so creation is automated (for example with `pg_partman`), with a default partition as a safety net.

Time is a good key for in-place partitioning, because retention and hot data follow time. It's a poor key for spreading writes across servers, because every new write lands in the newest partition.

### Splitting across servers

There are three ways to split, in rough order of cost:

- **By function.** Move one domain to its own database: messages and attachments, audit logs, analytics events. Joins and foreign keys across the boundary become application code, but each database stays an ordinary single-server database. This is often the first cross-server split, and it lines up with splitting services (23.5).
- **By key (sharding).** Each company's rows live on one of several databases, and a router picks the database from the company ID. All shards have the same schema.
- **By cell.** Split the whole stack, application and database together, by groups of customers (23.6).

**Choosing the shard key is the decision that's hardest to reverse.** A good key:

- **Appears in nearly every query and every transaction.** In B2B SaaS the tenant is the classic key. In consumer apps it's often the user; in some systems, the region.
- **Keeps transactions inside one key.** A ticket, its messages and its assignments all belong to one company.
- **Keeps the largest key comfortably small.** If the biggest company is 4% of all writes, it fits on one shard. If it's 40%, sharding by company won't help it, and that company needs its own splitting.
- **Spreads new writes.** Unlike time, a company ID sends today's writes to every shard.

**What becomes an application problem after sharding:**

- **Cross-shard queries.** "Every ticket about to breach its SLA, across all companies" for the internal operations team now spans every shard. Either scatter the query and gather the results, with timeouts and partial answers, or feed a global read model from all shards. This is where CQRS and sharding meet: a partitioned write side and an unpartitioned read side.
- **Cross-shard transactions.** Merging two companies' accounts touches two shards. Either disallow it, or run it as a saga with compensating steps (37.4).
- **Unique IDs.** Each shard's sequences produce the same numbers. Use UUIDv7 or IDs that embed the shard.
- **Global uniqueness.** "An agent's email must be unique across the platform" needs a small global database that isn't sharded.
- **Reference data.** Tables every shard joins against, such as plans or time zones, are copied to every shard.
- **Operations times N.** Every migration, backup, upgrade and dashboard now runs across N databases.
- **Moving tenants.** When a shard fills up, moving a company to another shard while it's writing is a project of its own (38.2). Many teams map many small *logical* shards onto fewer physical servers so that a move relocates a whole logical shard.

You can build the routing yourself with a directory table, as in the Implementation below, or use a system that does it for you. Citus distributes Postgres tables by a distribution column, Vitess does the same for MySQL, and distributed SQL databases such as CockroachDB, YugabyteDB and Spanner partition automatically, with different latency, cost and compatibility trade-offs. None of them removes the need for a good key.

### The combined picture

```
                 writes
                   │
          ┌────────▼────────┐        global DB:
          │ router (tenant) │◀────── tenant → shard, agent emails
          └──┬─────┬─────┬──┘
             ▼     ▼     ▼
          [ s1 ][ s2 ][ s3 ]    each shard: messages partitioned by month,
             │     │     │                  its own replicas
             └─────┼─────┘
                   ▼ change feeds
              projectors
            ┌──────┴───────┐

     inbox read model   ops read model
     (per shard)        (global, all companies)
```

## When It's Appropriate

- **A read model** when one query sits near the top of total database time and its result changes far less often than it's read. The inbox is the case: 800 reads a second against about 40 relevant changes a second, with a sort no index can serve.
- **A materialized view first** when a few minutes of staleness is fine and a full refresh takes seconds, such as a daily-stats panel on an admin dashboard.
- **An asynchronous projection** when the view is large, must be fresh within seconds, and is expensive to recompute.
- **Partitioning in place** when one table is hundreds of gigabytes or more and has time-based retention, or when vacuum on it no longer finishes in reasonable time. `messages` at 1.4 TB with 24-month retention qualifies.
- **Splitting by function** when one domain dominates size or writes and is only loosely joined to the rest.
- **Sharding** when, after all of the above, writes or data size will outgrow the largest server you'll run within a year or so, nearly every query already carries the tenant ID, the largest tenant is a small share of the total, and isolating customers from each other is worth something.

## When It's Unnecessary or Overkill

- **Sharding at 50 GB and 300 writes a second.** A single well-tuned Postgres server on large hardware handles far more than that. Scale up first (23.1a).
- **Sharding to fix read load.** Replicas, read models and caches are far cheaper, and sharding doesn't make an expensive query cheap.
- **CQRS as an architecture for every screen.** A read model is justified per query. A settings page with a simple indexed lookup needs nothing.
- **An asynchronous projection where a better index would do.** Try `EXPLAIN` before building a pipeline (22.3).
- **A separate read store when a table in the same database would do.** A new technology adds a new failure mode and a new on-call skill.
- **Partitioning a 20 GB table.** You pay the constraint and planning costs and get nothing back.
- **Sharding when most queries don't carry the key.** You'll end up building a distributed database, badly, one scatter-gather query at a time.

## Trade-offs

**Read models cost:**

- **Staleness,** and the session-guarantee work that comes with it.
- **Drift.** Two copies of the truth can disagree. You need a reconciliation check and a rebuild command, and you need them before the first incident.
- **Write amplification,** worst for fan-out changes.
- **More code per feature.** A new field on the inbox touches the write model, the change payload, the projector, the read schema and a backfill.
- **Pipeline operations.** Projector lag needs monitoring and alerting, and one change the projector can't apply blocks everything behind it unless it's moved to a dead-letter queue (10.2).

**Partitioning in place costs:**

- **Constraints that must include the key,** which can force changes to primary keys and foreign keys.
- **Slower queries without the key,** and planning overhead with very many partitions.
- **Partition management** that must never fall behind.

**Sharding costs:**

- **Cross-shard queries, transactions and uniqueness** move from the database into your code.
- **Every operational task multiplies** by the number of shards.
- **Rebalancing and tenant moves** are projects, not settings.
- **The key is close to permanent.** Changing it later means moving every row.
- **Hot shards** appear when one tenant grows faster than expected.
- **Harder testing.** A development database is one shard, so bugs that need data on two shards never show up. Run CI with at least two.

## Alternatives

- **Scale up and fix the write path.** Batch inserts, drop unused indexes on hot tables, and let updates stay on the same page where possible. A large modern server goes a long way (23.1a).
- **Keep less hot data.** Archive old rows to object storage and query them through a separate path. A smaller database is faster to vacuum, back up and restore.
- **Move a workload to a store built for it:** search to a search engine (Module 12), time-series data to a time-series database (38.5), analytics to a columnar warehouse (6.1).
- **Cache instead of projecting** when results can be keyed and briefly stale (23.3).
- **Use a distributed SQL database** instead of sharding by hand, accepting its latency, cost and compatibility profile.
- **Split into cells** (23.6) when isolating groups of customers matters as much as capacity.

## How to Achieve It

**1. Name the pressure.** Split `pg_stat_statements` into reads and writes, and list each large table's size, write rate and vacuum duration. Find the largest tenant's share of writes. *Move on when* you know which row of the four-tools table you're on.

**2. For expensive reads, climb one step at a time:** a better index or query, then a materialized view, then a table maintained in the same transaction, then an asynchronous projection. *Move up when* refresh cost grows with the view, or synchronous maintenance shows up in write latency.

**3. Before the first asynchronous projection, capture changes reliably** with an outbox or CDC. Make the projector idempotent and version-guarded from its first day, and write the rebuild command before you need it. *Move on when* you can delete the read model and rebuild it without an outage.

**4. Partition the largest table in place.** Choose time if retention is the pain, or a hash of the tenant if even-sized pieces matter more. *Move on when* maintenance and retention are no longer the problem and the server itself is.

**5. Put the partition key everywhere.** Add `tenant_id` to every table, primary key and query. Enforce it with row-level security in tests, so a query that forgets the key returns nothing. This is valuable even if you never shard. *Move on when* no query runs without the key.

**6. Split by function** if one domain dominates.

**7. Shard by key, starting with one shard.** Put the tenant-to-shard directory and the routing code into production while every tenant still maps to shard 0. Then add a second database and move a few small tenants, then larger ones. Serve cross-tenant views from global read models. *Go further (38.2) when* moves become routine or a single tenant approaches a shard's capacity.

## Implementation

The code is Go, because both halves of this article are long-running infrastructure code where Go is at home: a projector that applies changes in a loop with explicit transactions, and a router that holds a pool per database. The SQL for partitioning appears above; here it's the application side.

### A projector that can't go backward

```go
// One change, delivered in commit order by the feed (CDC or an outbox relay).
type TicketChanged struct {
	Position  int64 // the feed's position: an offset, a log sequence number, ...
	TenantID  int64
	TicketID  int64
	Version   int64 // incremented by every write to the ticket, in the same transaction
	Deleted   bool
	Team      string
	Status    string
	Subject   string
	Customer  string
	SLADueAt  time.Time
	LastMsgAt time.Time
}

const upsertInboxItem = `
INSERT INTO inbox_items AS i
  (tenant_id, ticket_id, version, team, status, subject, customer, sla_due_at, last_msg_at)
VALUES ($1, $2, $3, $4, $5, $6, $7, $8, $9)
ON CONFLICT (tenant_id, ticket_id) DO UPDATE SET
  version = EXCLUDED.version, team = EXCLUDED.team, status = EXCLUDED.status,
  subject = EXCLUDED.subject, customer = EXCLUDED.customer,
  sla_due_at = EXCLUDED.sla_due_at, last_msg_at = EXCLUDED.last_msg_at
WHERE i.version < EXCLUDED.version` // repeated or older changes do nothing

func (p *Projector) apply(ctx context.Context, batch []TicketChanged) error {
	return pgx.BeginFunc(ctx, p.readDB, func(tx pgx.Tx) error {
		for _, c := range batch {
			status := c.Status
			if c.Deleted {
				status = "deleted" // a tombstone, so a late older change can't bring it back
			}
			if _, err := tx.Exec(ctx, upsertInboxItem, c.TenantID, c.TicketID, c.Version,
				c.Team, status, c.Subject, c.Customer, c.SLADueAt, c.LastMsgAt); err != nil {
				return err
			}
		}
		_, err := tx.Exec(ctx,
			`UPDATE projector_checkpoints SET position = $1
			 WHERE name = 'inbox' AND position < $1`,
			batch[len(batch)-1].Position)
		return err // rows and checkpoint commit together, or neither does
	})
}
```

The inbox query is now `WHERE tenant_id = $1 AND team_id = $2 AND status = 'open' ORDER BY sla_due_at LIMIT 50` against an index on those columns.

> **Where this breaks.**
>
> - **The version must come from the write side,** incremented under the ticket's row lock in the same transaction as the change. A timestamp won't work: two writes can share a millisecond, and clocks on different servers disagree.
> - **Save the position after the rows, never before.** If the checkpoint were saved first (for example, by committing a broker offset before the database transaction), a crash in between would skip changes forever. Saved together, a crash just replays the batch, and the version guard absorbs the repeats. With a partitioned feed, keep one checkpoint per feed partition.
> - **Polling an outbox with `WHERE id > last_seen_id` loses changes.** A `bigserial` value is assigned when the row is inserted, not when the transaction commits. A slow transaction can commit id 41 after the projector has already read id 42 and moved its checkpoint past 41. CDC avoids this by reading in commit order; Module 37 covers safe ways to poll.
> - **Fan-out changes need their own path.** A tag rename arrives as one change but must touch 200,000 rows, so it belongs in a batched, set-based update, not in this per-ticket loop.

### A router that can't forget the key

```go
// Every data access starts from a tenant. There's no way to query without one.
type Scope struct {
	TenantID int64
	Tx       pgx.Tx
}

type Router struct {
	directory *pgxpool.Pool         // small global DB: tenant_id → shard_id
	shards    map[int]*pgxpool.Pool // with one database, this map has one entry: shard 0
	cache     sync.Map              // tenant_id → shard_id
}

func (r *Router) InTenant(ctx context.Context, tenantID int64, fn func(Scope) error) error {
	shard, err := r.shardFor(ctx, tenantID)
	if err != nil {
		return err
	}
	return pgx.BeginFunc(ctx, r.shards[shard], func(tx pgx.Tx) error {
		// Row-level security policies filter on this setting, so a query that
		// forgets tenant_id returns nothing instead of another company's rows.
		if _, err := tx.Exec(ctx, "SELECT set_config('app.tenant_id', $1, true)",
			strconv.FormatInt(tenantID, 10)); err != nil {
			return err
		}
		return fn(Scope{TenantID: tenantID, Tx: tx})
	})
}

func (r *Router) shardFor(ctx context.Context, tenantID int64) (int, error) {
	if v, ok := r.cache.Load(tenantID); ok {
		return v.(int), nil
	}
	var shard int
	if err := r.directory.QueryRow(ctx,
		"SELECT shard_id FROM tenant_shards WHERE tenant_id = $1", tenantID).Scan(&shard); err != nil {
		return 0, err
	}
	r.cache.Store(tenantID, shard)
	return shard, nil
}
```

**Three things to notice.**

- **The `true` in `set_config` matters.** It scopes the setting to the transaction, which keeps it safe behind a transaction-mode pooler (23.2a). A plain `SET` would leak to whichever client gets that server connection next.
- **Row-level security only helps if it applies.** Postgres skips policies for the table's owner unless the table has `FORCE ROW LEVEL SECURITY`, so the application should connect as a role that doesn't own the tables (Module 5).
- **The cache is the risk during a tenant move.** An instance holding an old entry keeps writing to the old shard. Moves need a way for the old shard to refuse those writes, which is part of 38.2.

A cross-company query has no `InTenant` to call, and that's deliberate. It goes to a global read model. Looping over every shard is reserved for rare jobs that can accept timeouts and partial results.

## Further Reading

- **Martin Fowler, "CQRS"** (martinfowler.com, 2011). A short statement of the idea, with an explicit warning that it adds risk and suits only some parts of a system.
- **Greg Young, "CQRS Documents"** (2010). The original, longer treatment, including why read and write models diverge.
- **Martin Kleppmann, _Designing Data-Intensive Applications_,** chapter 6 (Partitioning) for keys, skew and request routing, and chapters 11 and 12 on change data capture and derived data. The best single explanation of why a read model is "just a derived view."
- **Microsoft Azure Architecture Center:** the "CQRS", "Materialized View" and "Sharding" pattern pages. Concise, and each lists its own issues and considerations.
- **PostgreSQL documentation:** "Table Partitioning", including its limitations section, and `REFRESH MATERIALIZED VIEW`.
- **Citus documentation** on choosing a distribution column for multi-tenant applications, and **Vitess documentation** on sharding keys. Two concrete views of the key decision.
- **Notion Engineering, "Herding elephants: lessons learned from sharding Postgres at Notion"** (2021), and **Figma Engineering, "How Figma's databases team lived to tell the scale"** (2024). Two real migrations; Figma's shows the split-by-function step before sharding.
- **Chris Richardson, microservices.io:** the "Transactional outbox" and "Transaction log tailing" patterns.
- **In this collection:** 23.2a (replicas and session guarantees), 2.4 (CQRS and event sourcing), Module 37 (outbox, event sourcing, sagas), 38.2 (sharding mechanics), 38.4 (change data capture), Module 5 (multi-tenancy and row-level security), Module 12 (search as a read model), 23.5 (splitting services), 23.6 (cells).

A **Java** sibling would be worth writing, because Spring and Hibernate each offer something that looks like a shortcut here. Spring's `@TransactionalEventListener(phase = AFTER_COMMIT)` seems to solve change capture, but an event published after commit is lost if the process dies at the wrong moment, which is exactly why the outbox exists. Hibernate 6.2's `@PartitionKey` adds the partition key to the `WHERE` clause of updates and deletes, which in-place partitioning needs for pruning and which is easy to miss when an ORM writes the SQL. Go has neither abstraction, so this article can't show where they help and where they mislead. Not yet written.

---

The habit to take from this: **for every expensive read, ask how often its answer really changes; for every write, ask which key it belongs to.** The first question leads to read models, the second to partitioning, and they're different questions.
