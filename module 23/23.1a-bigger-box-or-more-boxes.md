# Bigger Box or More Boxes: Scaling Up, Scaling Out, and the State That Decides

_Module 23.1a — Scalability Patterns_

## The Problem

Suppose you run the API behind a ticketing site for small music venues. It's a single TypeScript process on Node.js, running on a 2-vCPU VM. On a normal day it handles about 150 requests per second. When a popular show goes on sale, traffic jumps to about 1,500 requests per second for twenty minutes. p99 latency then climbs past 3 seconds, right when people are trying to buy.

**Attempt one: a bigger machine.** The team moves to an 8-vCPU VM at four times the price. At the next on-sale, p99 is still 3 seconds, and the dashboard says CPU peaked at 27%, which looks like plenty of headroom. The per-core view shows otherwise: one core at 100% and seven nearly idle. By default, Node runs your JavaScript on one thread. The extra cores only help with the few jobs Node hands to background threads, such as password hashing, compression, file access, some DNS lookups and parts of garbage collection. The upgrade bought almost nothing, and the averaged graph hid that.

**Attempt two: use the whole machine.** They turn on Node's cluster mode. It runs eight worker processes on the same machine and spreads incoming connections across them. Throughput rises about 6.5×, and the next on-sale holds. Then the Monday bug reports arrive:

- **Random logouts.** Customers are signed out without warning. Sessions were stored in a `Map` inside the process, and each worker has its own `Map`.
- **A looser login limit.** "5 attempts per 15 minutes" now allows 40, because each worker counts separately.
- **Duplicate reminder emails.** Everyone with a show tonight got eight identical "doors open in two hours" emails. The reminder job runs on a `setInterval`, and there are now eight intervals.
- **Stale prices.** After an organizer lowers a price, some page loads show the old price for up to five minutes, depending on which worker's cache answers.

None of this code was wrong with one process. Each piece silently assumed it was the only copy running.

**Attempt three: more machines.** With those fixed, two problems remain that no single machine can solve. Every deploy restarts all eight workers at once, which causes about 20 seconds of errors. And when the cloud provider took the host down for maintenance, the site was down for four minutes during a presale. So the team runs four machines behind a load balancer. A new bug appears: ticket PDFs are written to local disk and downloaded moments later, and three out of four downloads return 404 because the download lands on a different machine.

The team learned the same lesson twice, at two different scopes:

```
state lives in…   breaks when you add…
───────────────   ─────────────────────────────
process memory →  a second process (same box)
local disk     →  a second machine
shared store   →  nothing (until it's the limit)
```

## What It Is

Adding capacity to one machine (more CPU, more memory, faster disks) is **vertical scaling**, or *scaling up*. Adding more machines and spreading work across them is **horizontal scaling**, or *scaling out*.

Scaling out has a requirement that scaling up doesn't: the copies must be **interchangeable**. Any request can go to any instance, and any instance can disappear without losing anything that matters. Such an instance is usually called **stateless**, which is a misleading name. The system still has sessions, counters, files and schedules. They've moved out of the process into shared *backing services* (Redis, Postgres, object storage) that every instance uses.

This is a different lever from Module 22. Performance work makes each request cheaper, while scaling adds room for more requests. The two interact: 22.1a's regex bug doubled a fleet, and scaling "fixed" it at twice the price.

## Recognizing the Problem

- Peak CPU or memory is near the limit on the largest instance you're willing to pay for.
- A bigger instance didn't raise throughput. Check per-core CPU: one core pegged with the rest idle means the runtime isn't using the machine.
- Every deploy, restart or host maintenance is a visible outage.
- You pay for peak capacity all day to survive a spike that lasts minutes.
- After adding a second process or instance, you see random logouts, limits that loosen, duplicate scheduled emails, data that changes between refreshes, or files that sometimes 404.
- Changing the instance count requires someone to edit config, or it can't be done without breaking something.

## How It Works

### Scaling up, and where it stops

Scaling up needs no code changes, which is its great strength. It stops paying off at four kinds of limit.

**The software can't use the machine.** Some runtimes use one core per process: Node, and CPython under its global interpreter lock. A multithreaded runtime can still be held back in other ways:

- a single lock that every request takes
- a connection pool sized for the old machine
- garbage-collection pauses that grow with the heap

Neil Gunther's **Universal Scalability Law** describes the shape of this. Added capacity carries two penalties:

- **Contention:** work waits in line for something shared. This flattens the throughput curve.
- **Coherency:** parts of the system spend effort keeping each other in agreement. This can bend the curve downward, so past some point more capacity gives *less* throughput.

The same law applies when scaling out, where the shared thing is usually the database.

**The biggest machine is only so big.** Cloud catalogs go very high, but they end.

**Cost.** Within one cloud instance family, price is roughly proportional to size. That weakens the old argument that big machines cost disproportionately more. The real costs are paying for peak capacity around the clock and the premium on the largest specialized sizes.

**One machine is one failure.** Resizing usually means a restart, a host failure takes everything down, and every deploy happens on the only machine you have.

### Scaling out

```
             clients
                │
         ┌──────▼──────┐
         │load balancer│
         └──┬──┬──┬──┬─┘
            ▼  ▼  ▼  ▼
          [a1][a2][a3][a4]   interchangeable,
            │  │  │  │       disposable
            └──┴┬─┴──┘
                ▼
   Redis · Postgres · object store
                     shared, stateful
```

A load balancer spreads requests across instances; how it chooses is covered in 23.1b. Capacity grows roughly with instance count, but only while the instances aren't all waiting on the same shared resource, and they always share something. Scaling out the app tier moves the bottleneck down into the shared tier.

The database usually shows this first, through connections. In the ticketing setup, four machines with eight workers each and a pool of 10 per worker open 320 Postgres connections. That's more than three times Postgres's default `max_connections` of 100. Adding app instances during a database slowdown can turn a slow database into one that refuses connections.

This is why most systems settle into the same shape for a long time: **a stateless tier that scales out, in front of a stateful tier that mostly scales up.** Adding stateless instances is easy. Adding database capacity isn't (23.2 and Module 38 cover why).

Scaling out also brings two benefits beyond capacity:

- **Availability.** If you run N instances and N−1 can carry the peak, losing one is a non-event.
- **Elasticity.** You can add and remove instances as demand changes, which is autoscaling. Removing instances safely depends on graceful shutdown, covered below.

### The state inventory

To make an instance interchangeable, find every kind of state it holds and decide where each belongs. Six kinds keep showing up.

**Sessions and login state** go to a shared session store, or into a signed token the client carries (4.1 and 4.4 compare the two). A memory lookup becomes a network call, typically under a millisecond.

**Caches** can stay per-instance if a stale read lasting up to the TTL is acceptable. Otherwise, use a shared cache or broadcast invalidations (13.3). Don't move a cache just to follow a rule. A 30-second per-process cache of the venue list is harmless.

**Counters and limits** (rate limits, quotas, attempt counts) must be shared. If they aren't, the effective limit is the configured limit times the instance count (Module 18).

**Files** that a later request will read go to object storage (Module 11). Scratch files used within a single request can stay local.

**Scheduled and background work** started by a timer inside the web process runs once per instance. It needs a claim that only one instance can win, or it belongs in a job system with its own scheduler (10.3).

**Connection-bound state** can't be moved: a WebSocket lives on one instance. What you can share is the *messages*. Instances fan them out through pub/sub, so a notification reaches the user whichever instance holds their socket (9.1, 9.4).

One test covers all six: *if the next request goes to a different instance, or this instance is killed right now, does anyone notice?*

## When It's Appropriate

**Scale up first when the software can use the machine and there's room left.** Suppose Postgres runs at 70% CPU on 8 vCPUs and load grows about 5% a month. Moving to 16 vCPUs buys over a year of room for an afternoon's work and one failover window. No application change will do that as cheaply.

**Scale out the app tier when any of these apply:**

- **The runtime can't use a bigger machine.** A Node service with one pegged core is the ticketing case. First run one process per core, then add machines.
- **Load is spiky.** With 150 req/s normally and bursts to 1,500 req/s, a machine sized for the peak sits about 90% idle most of the time. Adding instances for the peak and removing them afterward costs less.
- **Availability matters more than load.** A checkout at 20 req/s still wants two instances in two zones. The first reason to scale out is often surviving a host failure, not a shortage of capacity.
- **Deploys must not cause downtime.** Rolling deploys replace instances a few at a time, which needs at least two.

## When It's Unnecessary or Overkill

- **Before profiling.** Scaling out a CPU bug multiplies its cost. 22.1a's regex compilation doubled a fleet from 6 to 12 instances, and a one-line fix shrank it back.
- **When the database is the bottleneck.** More app instances mean more connections and more queries against the resource that's already saturated. Find out what the database is waiting on first (22.3).
- **With flat, low traffic.** An internal admin tool with 30 users can run on one instance and accept a few seconds of downtime on restart. Autoscaling a flat traffic line adds scale events, cold caches and one more thing to debug, and gains nothing.
- **For purity.** Moving a harmless per-process cache into Redis adds a network hop and a dependency. Move the state that breaks correctness, and leave the state that only goes slightly stale.

## Trade-offs

**Scaling up costs:**

- **A hard ceiling.** You may hit it at the worst possible moment.
- **Shared fate.** Everything fails together, and resizing means downtime.
- **New tuning problems.** Very large heaps and very large machines bring their own issues, such as garbage-collection behavior and NUMA effects.

**Scaling out costs:**

- **A network call and a failure mode for every piece of externalized state.** A session read that was a memory lookup is now a Redis call, and a Redis outage logs everyone out at once. The shared store becomes part of your availability story, and it must be monitored, sized, and backed up where that matters.
- **Consistency questions.** Per-instance caches disagree with each other, locks expire while their holder is still working, and instance clocks drift apart.
- **Debugging across machines.** A single request's story is spread over instances, so you need correlation IDs and centralized logs (19.1).
- **Two versions live at once.** During a rolling deploy, old and new code serve traffic together for a few minutes. Migrations and API changes must work with both (6.3, Module 33).
- **More moving parts.** The load balancer, health checks and autoscaling policies can each be misconfigured.
- **Autoscaling reacts late.** A new instance takes a minute or more to start and warm up, so a spike that arrives in 30 seconds is over before the capacity is. That's why ticketing sites scale up *before* a scheduled on-sale.
- **A cost floor.** Availability means at least two instances, even at 3 a.m.

## Alternatives

- **Make each request cheaper** (Module 22). This usually gives the best return, and it's often the fix that makes scaling unnecessary.
- **Don't serve the request from your app at all.** Cache the event listing at a CDN (13.1), and most on-sale traffic never reaches Node.
- **Flatten the peak instead of provisioning for it.** A virtual waiting room admits buyers at a rate the backend can handle, which is why real ticketing sites use them. It combines load leveling (23.4) with explicit backpressure (22.2b), and it accepts some user waiting in exchange for a much smaller fleet.
- **Sticky sessions.** The load balancer keeps sending each client to the same instance, so in-memory state appears to work. The costs are uneven load, sessions lost when that instance dies, and disruptive scale-in. It's a reasonable stepping stone, and some connection-oriented protocols require it (23.1b).
- **Serverless functions** (Module 41). This is scaling out taken to its extreme, and the platform enforces statelessness because every instance is disposable.
- **Scale out whole stacks.** Split customers into independent *cells*, each with its own database. That scales the stateful tier horizontally too, which is the subject of 23.6 and 38.2.

## How to Achieve It

**1. Measure before choosing.** Look at per-core CPU, memory, and what the database is waiting on, and profile the hot path (22.1a).
*Move on when* the bottleneck is real work in the app tier, not a bug or the database.

**2. Scale up, and make the software use the machine.** On a VM, run one process per core. In containers, the usual pattern is one process per container, with the orchestrator setting the count.
*Move on when* you're near the largest size you'll pay for, or availability becomes a requirement.

**3. Take the state inventory.** Search the codebase for:

- module-level `Map`s and arrays
- `setInterval` or cron libraries in the web process
- local disk writes
- in-memory session stores
- in-process rate limiters

Move whatever affects correctness.
*Move on when* the list is empty or every remaining item is deliberately accepted.

**4. Run two instances permanently, even if one is enough.** This keeps the design honest, because a stateful regression surfaces within days instead of during an incident. Kill one on purpose during business hours.
*Move on when* nobody notices.

**5. Add graceful shutdown and rolling deploys.**
*Move on when* deploys produce no errors.

**6. Autoscale on the signal that matches your bottleneck.**

- **CPU-bound services:** CPU utilization.
- **I/O-bound Node services:** event-loop lag or in-flight requests.
- **Workers:** queue depth.
- **Known events:** scale up ahead of time.

*Move on when* the app tier stops being the constraint, which usually means the database has become it (23.2).

## Implementation

The code is TypeScript on Node, because Node makes the vertical ceiling impossible to miss: one process uses one core, so even a single machine has to be run as a small cluster.

### The inventory, as it usually looks

```ts
// server.ts — correct on one process, wrong on two
const sessions = new Map<string, Session>();          // sessions: per process
const loginAttempts = new Map<string, number>();      // limits: per process
const priceCache = new Map<string, CachedPrice>();    // cache: per process (maybe fine)
const upload = multer({ dest: "/var/app/tickets" });  // files: per machine
setInterval(sendShowReminders, 60_000);               // schedule: per process
```

Each line is a decision the code made without saying so:

- **Sessions and the limiter** move to Redis.
- **The price cache** can probably stay, with a short TTL.
- **Uploads** move to object storage.
- **The scheduled job** is the interesting one, covered next.

### Running a scheduled job once across the fleet

The obvious fix is a lock: acquire it, run the job, release it. Here's why that fails:

```
A: 12:00:00 lock → send (2 s) → release
B: 12:00:10 lock → send again
```

Timers on different instances aren't aligned, so releasing the lock just hands the job to the next instance whose timer fires. What each instance should claim is a *time slot*, not the job:

```ts
import { createClient } from "redis";
import { hostname } from "node:os";

const redis = createClient({ url: process.env.REDIS_URL });
await redis.connect();

async function oncePerPeriod(job: string, periodMs: number, run: () => Promise<void>) {
  const slot = Math.floor(Date.now() / periodMs);   // every instance computes the same slot
  const claimed = await redis.set(`sched:${job}:${slot}`, hostname(), {
    NX: true,            // only the first instance to ask wins
    PX: periodMs * 2,    // outlives the slot, so a late instance can't reclaim it
  });
  if (claimed !== "OK") return;
  await run();
}

// Check more often than the period so no slot is missed; one instance wins each slot.
setInterval(() => oncePerPeriod("show-reminders", 60_000, sendShowReminders), 10_000);
```

> **Where this still fails.**
>
> - **Crashes lose a slot.** If the winning instance dies mid-run, nothing retries that slot. So write `sendShowReminders` to process *everything due and not yet sent*, not just "shows this minute", and the next slot will catch up.
> - **Overlapping runs can double-send.** Mark each reminder with a conditional update, `UPDATE … SET sent_at = now() WHERE id = $1 AND sent_at IS NULL`, so a run that overlaps a slow previous run can't send twice.
> - **Clock skew is harmless here.** It only shifts which instance wins a slot and when. It can't cause a double send, because each slot key can be claimed once.
>
> Once several jobs need this treatment, move them to a real scheduler (10.3).

### Using the whole machine, and leaving it cleanly

```ts
import cluster from "node:cluster";
import { availableParallelism } from "node:os";

// In a container, the visible core count may not match your CPU limit, so make it configurable.
const workers = Number(process.env.WEB_CONCURRENCY ?? availableParallelism());

if (cluster.isPrimary) {
  let stopping = false;
  for (let i = 0; i < workers; i++) cluster.fork();
  cluster.on("exit", (_w, code) => { if (!stopping && code !== 0) cluster.fork(); });

  // Signals arrive at the primary, which must pass them on. This is one reason
  // containers usually run a single process and let the orchestrator count.
  process.on("SIGTERM", () => {
    stopping = true;
    for (const w of Object.values(cluster.workers ?? {})) w?.process.kill("SIGTERM");
    // …exit once every worker has exited
  });
} else {
  let draining = false;
  app.get("/ready", (_req, res) => res.sendStatus(draining ? 503 : 200));
  const server = app.listen(3000);

  process.on("SIGTERM", () => {
    draining = true;                                    // 1. fail readiness
    setTimeout(() => {                                  // 2. let the LB notice
      server.close(() => process.exit(0));              // 3. finish in-flight, exit
    }, 10_000);
    setTimeout(() => process.exit(1), 25_000).unref();  // 4. never hang a deploy
  });
}
```

> **The order matters.** If a process closes its listener before failing readiness, the load balancer keeps routing requests to it for a few seconds. Those requests fail, and that's where most deploy-time 502s come from. Also, `server.close()` waits for open connections. On older Node versions, idle keep-alive connections can hold it open unless you call `server.closeIdleConnections()`.

## Further Reading

- **The Twelve-Factor App** (12factor.net), factors VI (Processes), VIII (Concurrency) and IX (Disposability). The shortest statement of the stateless-process contract, including why fast startup and graceful shutdown belong to it.
- **Neil J. Gunther, _Guerrilla Capacity Planning_** (Springer, 2007). The Universal Scalability Law, and how to fit it to your own load-test measurements (see 22.5).
- **Martin Kleppmann, _Designing Data-Intensive Applications_.** Chapter 1 on describing load and on shared-nothing architectures; the later chapters explain why the stateful tier is the hard part.
- **Node.js documentation:** the `cluster` module, and the guide "Don't Block the Event Loop (or the Worker Pool)". The guide explains exactly which work leaves the main thread.
- **Martin Kleppmann, "How to do distributed locking"** (2016), read alongside **the Redis documentation on distributed locks**. Together they explain why a lock with a timeout can't guarantee mutual exclusion on its own, and what fencing tokens add.
- **Kubernetes documentation:** Horizontal Pod Autoscaling, and the termination section of "Pod Lifecycle". They show how SIGTERM, readiness and endpoint removal line up, which is why the drain delay above exists.

A **Go** sibling would be worth writing, because it shows the mirror image of this article's vertical-scaling problem. Node uses too few cores by default, while Go historically tried to use too many. Before Go 1.25, a Go service in a container limited to 2 CPUs on a 64-core host still ran with `GOMAXPROCS=64`. The container's CPU quota then throttled it in bursts that showed up as latency spikes, and many teams worked around this with Uber's `automaxprocs` library. Go 1.25 made the default respect the container's CPU limit. A Go article could also show the USL's contention penalty, lock contention, in a real profile, which a single-threaded Node process can't demonstrate. Not yet written.
