# Trading Time for Capacity: Load Leveling, Waiting Rooms, and Queue-Driven Scaling

_Module 23.4 — Scalability Patterns_

## The Problem

Suppose you run an online tax-filing service. For most of the year it's quiet, with about two returns submitted a minute. Deadline day is different. Last year, submissions peaked at 50 a second.

Submitting a return has three steps: validate it (about 1 second of CPU), render the signed PDF (about 3 seconds), and transmit it to the tax authority's e-filing gateway (1 to 3 seconds). The gateway accepts at most **20 transmissions a second** from each provider. In this scenario, the authority counts a return as on time if the provider recorded the user's signed submission before midnight and transmits it within 24 hours.

Last year all three steps ran inside the request, and the site fell over at 21:40. This year the team followed Module 10: the request validates the return, stores the signed submission with its timestamp, and answers "Received" in 300 ms. Workers render and transmit afterwards. Submitting stayed fast all day. Four other things went wrong.

**More workers changed nothing.** The autoscaler watched the queue grow and took the worker fleet from 10 to 300. Throughput stayed at 20 returns a second, because that's what the gateway accepts. The other 280 workers spent the evening collecting `429 Too Many Requests` and retrying (10.2a, 10.4b). Arrivals averaged 40 a second from 16:00 to midnight, so the backlog grew by about 20 a second for eight hours:

```
returns/s
 50 ┤              ╭──╮
 40 ┤       ╭──────╯  ╰──────╮                         arrivals
 20 ┼═════════════════════════════════════════════     gateway limit
    │       ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░      backlog
  0 ┼───────┴──────────────────┴─────────────────┴──▶
          16:00             midnight            ~09:00
                        576,000 waiting        empty again
```

It drained by about 09:00, inside the 24-hour window. The design worked only because the window was long. With a 4-hour window, no number of workers would have been enough. And the gateway's documentation, which nobody had reread, says one transmission can carry up to 50 returns.

**The status page became the busiest endpoint.** "Received" isn't "accepted by the authority," so the confirmation screen said "Transmitting…" and polled every 2 seconds. At 23:00 about 250,000 people had that screen open:

```
250,000 open tabs ÷ 2 s  =  125,000 status requests/s
peak submissions          =          50 requests/s
```

Each poll was a database query. Moving the work out of the request didn't remove load; it turned one slow request into thousands of fast ones.

**The front door fell over at 18:00.** A reminder email ("6 hours left!") went to 3 million users at once. About 180,000 of them tried to open the tax editor in the next ten minutes. The editor is interactive, so it can't be queued like a job, and the system supports about 40,000 active editing sessions. Logins took 30 seconds, sessions timed out mid-edit, and people lost unsaved work.

**After an outage, the queue did the least useful work first.** At 22:00 the gateway went down for 70 minutes. The same queue also held "refresh refund status" jobs, one for every dashboard view, and confirmation emails. When the gateway came back, FIFO order sent the workers through 40 minutes of status refreshes that were an hour old, many of them the same return refreshed 30 times, while signed submissions waited behind them.

## What It Is

Putting a durable queue between arriving work and the capacity that processes it is called **load leveling**. It lets you size processing for the real constraint and the average load instead of the peak. The price is delay, so every leveled workload needs a **time budget**: how old work may get before the delay itself is a failure. For tax submissions the budget is 24 hours. For a "your photo is ready" notification it might be 2 minutes.

Two related techniques come from the same trade:

- A **waiting room** applies it to people. Users who can't be served yet wait *before* they start, instead of failing halfway through.
- **Queue-driven scaling** adjusts processing capacity from the backlog and the time budget, within the limits of whatever is actually scarce.

10.1a moved work out of the request to protect latency and isolate features. This article is about the other reason: **not paying for the peak.**

Leveling is one of four answers to "more work is arriving than we can handle," and the right one depends on what can wait:

```
arrivals > capacity
 ├─ can the work itself wait?             → level it: queue + time budget
 ├─ can the sender slow down?             → backpressure (9.1b)
 ├─ can the person wait before starting?  → waiting room
 └─ none of these                         → shed load, and choose whom (Module 5, 18)
```

## Recognizing the Problem

- Peak load is many times the average, and capacity sized for the peak sits idle most of the year.
- A downstream system, often a third party, has a hard limit below your peak arrival rate.
- Adding workers doesn't increase throughput.
- A backlog graph exists, but nobody can say how old is too old.
- After moving work to a queue, status or polling endpoints became your top traffic.
- Spikes happen on known dates: deadlines, on-sales, launches, enrollment windows.
- Users are dropped in the middle of a flow during spikes: carts, drafts, forms.
- After an outage, workers are busy but the important work isn't moving, and the queue holds many jobs for the same entity.
- Traffic spikes line up with your own emails, push notifications or scheduled jobs.

## How It Works

### The arithmetic of a backlog

While arrivals (λ) exceed processing capacity (μ), the backlog grows at λ − μ. With FIFO order, work arriving *t* seconds into a surge waits roughly:

```
wait ≈ t × (λ − μ) / μ
```

For the tax surge, T = 8 hours, λ = 40/s and μ = 20/s, so the last return before midnight waits about 8 hours. The time budget decides which μ is enough:

```
budget 24 h  →  μ = 20/s is fine        (half the average arrival rate)
budget  1 h  →  μ ≥ 35.6/s              (8 × (40 − μ) ≤ μ)
```

This is the most useful fact about leveling: **it saves capacity only when the time budget is long compared with the surge.** With a 1-hour budget on an 8-hour surge, you still need almost the full average capacity, plus all of the queue's complexity. With a 24-hour budget you can run at half.

Two numbers make a backlog readable at a glance:

```
wait for work arriving now  ≈ backlog ÷ drain rate
time until the backlog is empty ≈ backlog ÷ (drain rate − arrival rate)
```

Alert when the first approaches the budget, not when the backlog passes an arbitrary count. The oldest job's age (10.2b) tells you where you are, and these projections tell you where you're heading.

### What to acknowledge, and what to defer

Leveling splits a request into a part that must happen now and a part that can happen later. The "now" part has to create a **durable, meaningful acknowledgment**: the signed return and its timestamp are stored before "Received" is shown, and storing the record and the job must not be able to diverge (10.1a, Module 37). Everything after that is a promise, and the system owns it. Every item that fails after acknowledgment needs retries, a dead-letter path, and eventually a person, because the user has already been told it's handled.

The API changes shape too. The standard form is `202 Accepted` with a link to a status resource, sometimes called asynchronous request-reply.

### The constraint sets the rate, not the worker count

A queue drains at the rate of its slowest required step. Workers beyond that rate only add contention and retries (10.4b). So before scaling workers, name the constraint and look for ways to raise it:

- **Batch.** If the limit is per call and the downstream accepts batches, 20 calls a second × 50 returns a call is 1,000 returns a second. Batching also moves the constraint back to something you control: rendering PDFs at 3 seconds each now needs about 120 workers for 40 returns a second, and CPU can be scaled.
- **Do work before the peak.** Render the PDF as the user finishes each section, not at submission, and the surge has less to do.
- **Ask for a higher limit.** Sometimes the fix is a conversation with the provider before deadline week.

**Ordered work limits parallelism.** When messages for the same key must be processed in order, the queue is usually partitioned by key: Kafka partitions, SQS FIFO message groups. Parallelism is then capped by the number of partitions or active keys, and a hot key is a hot partition. Choose partition counts for the peak you expect, because increasing them later changes which partition each key maps to.

### Status traffic is the bill for going async

People waiting on asynchronous work ask how it's going, and polling load is simple arithmetic:

```
polling load = people waiting ÷ poll interval
```

**Make the answer cheap.** Status should be a single key or row, written when the state changes and served from a cache (23.3), not assembled from the job tables on every request.

**Let the server set the pace.** Return a `pollAfterSeconds` field or a `Retry-After` header that grows with the expected wait. Nobody needs a 2-second poll when the answer is 3 hours away. At a 60-second interval, the same 250,000 tabs make about 4,200 requests a second instead of 125,000.

**Push instead of polling** where people stay on the page: server-sent events or WebSockets (Module 9) for open tabs, and email or a mobile notification when the work completes, so people can close the tab.

**Show an honest estimate.** "About 3 hours; we'll email you" stops refreshing better than a spinner does. Estimate it from the backlog ahead of this item and the recent drain rate.

### Backlogs that serve the wrong work

A queue that holds work for hours has to care about what hours do to that work's value. Work falls into three kinds:

| Kind | Example | What delay does | Treatment |
|---|---|---|---|
| Must complete | signed submissions | nothing, until the deadline | own queue; earliest deadline first if deadlines differ |
| Latest wins | refund status refresh | makes it worthless; only current state matters | coalesce by key; newest first |
| Decays | "we received your return" email | makes it less useful, then misleading | expiry time; drop or replace when stale |

The techniques:

- **Separate queues** so one kind never waits behind another (10.2b).
- **Coalescing.** Instead of one job per event, mark the entity as needing work and let the worker process its current state. Thirty refresh requests become one refresh.
- **Expiry.** Each message carries the time after which it's no longer worth doing, and workers acknowledge expired messages without doing them.
- **Newest first** for latest-wins work. After an outage, the most recent requests come from people who are still looking at the screen.

AWS calls a backlog you can't work through in useful time an *insurmountable* backlog. These techniques are what keep a backlog from becoming one.

### Waiting rooms

Some work can't wait once it has started. A person halfway through a tax form needs the editor to respond now. A waiting room applies leveling *before* the flow starts:

```
arrive ──▶ take a number ──▶ wait (static page, from the CDN)
                                  │ your number ≤ admitted?
                                  ▼
                           receive a signed access token ──▶ editor (protected)
```

**Admit by the flow's real capacity.** The limit here is 40,000 active editing sessions, not requests per second. A controller watches active sessions and admits more people as sessions end. With sessions lasting about 25 minutes, that's roughly 1,600 new admissions a minute once the room is full.

**Keep the waiting room's state tiny.** A queue of 140,000 people doesn't need a list. Each arrival takes the next number from a counter, and admission is a second counter: everyone whose number is at or below it may enter. A person's position is their number minus the admission counter.

**Enforce admission at the edge.** Admitted users get a short-lived signed token, and the protected paths reject requests without one. Otherwise anyone who knows the editor's URL skips the queue.

**Decide what's fair.** First-come-first-served rewards whoever refreshes at the right second, and bots. Many waiting rooms randomize the order of everyone who arrived *before* the opening time, then serve later arrivals in order.

**Be honest about the wait.** Show position and an estimate, say that refreshing keeps your place, and keep the page lightweight.

**Plan for the deadline itself.** Near a hard deadline, a waiting room needs a rule for people who won't get in in time: a lighter submission path, or recording their arrival time if the rules allow it.

Managed waiting rooms exist at several CDNs and specialist vendors. They implement this model at the edge.

### Scaling on the backlog

10.4b set the rules for autoscaling workers: scale on the oldest job's age, and cap the replica count at what the constraint and the connection budget allow. The time budget turns that into a target:

```
workers needed ≈ λ ÷ r            (keep up with arrivals)
               + B ÷ (r × D)      (clear backlog B within target time D)
capped at      constraint ÷ r
```

Here r is one worker's throughput. For rendering at 3 seconds each, r ≈ 0.33/s. Keeping up with 40 returns a second takes about 120 workers, and clearing a 100,000-return backlog within an hour adds about 83 more.

Three more scaling habits fit queue workers especially well:

- **Scale ahead for known dates.** Autoscaling reacts in minutes; a deadline arrives on schedule (23.1a).
- **Use interruptible capacity.** Spot or preemptible instances are cheap, and an interrupted worker's job simply returns to the queue after its lease expires. That's safe only because the jobs are idempotent (10.1a).
- **Scale to zero when idle** if a cold start of a minute or two fits the time budget. Tools such as KEDA do this for Kubernetes.

### The load you cause yourself

The 18:00 surge was self-inflicted. Emails, push notifications, scheduled jobs and mobile apps that sync "on the hour" all create synchronized arrivals. **Spread your own demand:** send reminders over several hours, by time zone or in batches; add jitter to client schedules; move reports and reindexing away from known peaks. The cheapest peak to handle is the one you didn't create.

## When It's Appropriate

- **Load leveling** when peak load is five or more times the average, the work's time budget is at least comparable to the surge, and a constraint makes peak capacity expensive or impossible. Tax submissions with a 24-hour window and a 20/s gateway fit well.
- **Batching** whenever the downstream limit is per call and a batch API exists.
- **Server-directed polling, push and notifications** as soon as more than a few thousand people wait on asynchronous work at once.
- **Separate queues, coalescing and expiry** when a queue holds work with different value decay, especially if it can back up for more than a few minutes.
- **A waiting room** for interactive flows with surges at known times, where capacity can't be added fast enough (a database, licences, a third party), and where failing halfway is worse than waiting: checkout during an on-sale, course registration, deadline day.
- **Backlog-based scaling with a cap** when the work scales with CPU and surges last longer than it takes to add workers.

## When It's Unnecessary or Overkill

- **Leveling work that must finish before the user can continue,** such as a payment authorization whose result decides the next screen. A queue can't help; you need capacity, or you need to shed.
- **Leveling when the time budget is shorter than the surge.** You still need nearly peak capacity, and you've added a queue to operate.
- **A waiting room when the stateless tier autoscales in time** and nothing behind it has a hard limit, or when traffic is flat.
- **Randomized fair ordering for a small launch** of a few thousand people.
- **Backlog formulas for a five-worker fleet** that drains in minutes. Oldest-job age and a fixed cap are enough.
- **Coalescing work whose every event matters.** Each receipt email must be sent; merging them loses messages.

## Trade-offs

- **Delay is a product change.** People see "pending," support gets "where is my…" questions, and the product needs states it didn't have before.
- **Acknowledgment creates obligations.** Everything accepted must eventually complete or be explicitly failed, with someone watching the dead-letter queue.
- **Status traffic can exceed the original load** unless it's designed.
- **A backlog hides overload.** The system looks healthy while work ages, so alerts must be on age and projected wait, not on errors.
- **The queue itself needs capacity.** 576,000 messages with 30 KB payloads is 17 GB, which is a problem for a Redis-backed queue. Keep payloads in object storage or the database and put references in messages.
- **Batching adds per-item latency and widens failures.** One malformed return can fail a batch of 50; batches need partial-failure handling.
- **Coalescing and expiry drop work by design,** so they're safe only for work whose value really is "latest" or "timely."
- **Waiting rooms are unpopular and add machinery at the edge.** They need bot handling and honest estimates. A badly set admission target either wastes capacity or lets overload in.
- **Interruptible capacity adds churn:** redelivered jobs, repeated partial work, and warm-up costs.

## Alternatives

- **Buy the peak.** If capacity can be added quickly and no hard downstream limit exists, a larger fleet for one day may cost less than the engineering.
- **Shed load** (Module 5, Module 18) when the work can't wait at all.
- **Spread demand before it arrives:** incentives to file early, booked time slots, staged launches by region. A booked slot is a waiting room scheduled in advance.
- **Precompute** during quiet periods so the peak has less to do.
- **Backpressure** (9.1b) when the producer is your own system and can slow down.
- **Serverless workers** (Module 41), which scale quickly but still meet every downstream limit.

## How to Achieve It

**1. Measure the peak-to-average ratio and name the constraint.** Include third parties, the database, and anything licensed. *Move on when* you can say what limits throughput per second.

**2. Write down a time budget for each kind of work.** *Move on when* every queue has one and an alert that compares projected wait against it.

**3. Split acknowledge-now from finish-later,** make the acknowledgment durable, and return `202` with a status link.

**4. Design status before launch:** a cheap read, server-directed poll intervals, push for open pages, and a notification on completion. *Revisit when* status traffic exceeds the work traffic.

**5. Raise the constraint:** batch, precompute, or negotiate. Then size and cap workers from it (10.4b).

**6. Separate queues by how delay affects value,** and add coalescing and expiry. *Do this when* a queue can back up for longer than its cheapest work stays useful.

**7. Prepare for known dates:** scale ahead, spread your own notifications, and load-test the drain, not just the peak (22.5).

**8. Add a waiting room last,** for interactive flows that still exceed capacity at known moments. Rehearse it with the admission target set low.

## Implementation

The code is TypeScript. Waiting rooms usually run at the edge, where JavaScript runtimes are the norm, and the worker side reuses the same Redis client. It shows two things: a waiting room that fits in two counters, and a worker loop that batches to the gateway and skips stale work.

### A waiting room in two counters

```ts
const NEXT = "wr:deadline:next";          // last number handed out
const ADMITTED = "wr:deadline:admitted";  // everyone at or below this may enter
const ACTIVE = "sessions:active";         // sorted set: session id → last activity time

// Arrival: take a number once. It lives in a signed cookie, so refreshing keeps your place.
export async function join(): Promise<string> {
  const n = await redis.incr(NEXT);
  return sign({ n });
}

// Controller, every 5 seconds: admit as many as there is room for, in bounded steps.
export async function tick() {
  const now = Date.now();
  await redis.zremrangebyscore(ACTIVE, 0, now - SESSION_IDLE_MS);  // idle sessions free their place
  const active = await redis.zcard(ACTIVE);
  const step = Math.min(Math.max(0, TARGET_ACTIVE - active), MAX_ADMIT_PER_TICK);
  if (step > 0) await redis.incrby(ADMITTED, step);
}

// Waiting page asks this every pollAfterSec.
export async function check(cookie: string) {
  const { n } = verify(cookie);                                  // throws if forged
  const admitted = Number((await redis.get(ADMITTED)) ?? 0);
  if (n <= admitted) {
    const sessionId = crypto.randomUUID();
    await redis.zadd(ACTIVE, Date.now(), sessionId);
    return { status: "admitted", access: sign({ sid: sessionId, exp: Date.now() + 15 * 60_000 }) };
  }
  const ahead = n - admitted;
  const perSec = Math.max(await recentAdmissionsPerSec(), 0.1);
  return { status: "waiting", ahead, etaSec: Math.round(ahead / perSec), pollAfterSec: 30 };
}
```

Every request to the editor passes through edge middleware that verifies `access` and refreshes the session's activity time in `ACTIVE`.

> **Why this works, and where it doesn't.**
>
> - **Abandoned numbers correct themselves.** Many people leave the queue, so `ADMITTED` passes numbers that will never become sessions. The controller counts real active sessions, not admitted numbers, so the unused room remains and it admits more on the next tick.
> - **`MAX_ADMIT_PER_TICK` protects the editor from a flood** when many sessions end at once. Admitting 20,000 people in one tick recreates the 18:00 spike on a smaller scale.
> - **An access token can be shared,** which is why it's bound to a session ID that counts against capacity and expires when idle.
> - **Counters give strict arrival order.** To randomize everyone who arrived before the opening, collect those arrivals without numbers, shuffle them once at opening time, assign their numbers, and only then start handing out numbers to later arrivals.
> - **The waiting page must not touch the origin.** It's served from the CDN, and only `check` runs, at the edge, against the counters.

### A worker that batches and skips stale work

```ts
interface Envelope<T> { body: T; enqueuedAt: number; expiresAt?: number }

// Submissions: the gateway allows 20 calls/s and 50 returns per call.
export async function transmitLoop(queue: Queue<Envelope<SignedReturn>>) {
  for await (const batch of queue.batches({ max: 50, maxWaitMs: 500 })) {
    await gatewayCalls.acquire();                                // token bucket, 20/s, fleet-wide
    const results = await gateway.transmit(batch.map((m) => m.body.body));
    for (const [i, r] of results.entries()) {
      if (r.accepted) await batch[i].ack();
      else if (r.retryable) await batch[i].retryLater();         // backoff, 10.2a
      else await batch[i].deadLetter(r.reason);                  // someone must follow up
    }
  }
}

// Refund status: latest wins. Thirty dashboard views mark the return once.
export const markStatusStale = (returnId: string) => redis.sadd("stale:refund-status", returnId);

export async function statusLoop() {
  for (;;) {
    const ids = await redis.spop("stale:refund-status", 100);
    if (ids.length === 0) { await sleep(1_000); continue; }
    for (const id of ids) await refreshRefundStatus(id);        // reads current state, writes the status key
  }
}

// Confirmation emails: worth sending for a few hours, then misleading.
export async function noticeHandler(msg: Envelope<Notice>) {
  if (msg.expiresAt !== undefined && Date.now() > msg.expiresAt) {
    metrics.increment("jobs.expired", { type: "notice" });
    return;                                                      // acknowledged, not sent
  }
  await sendNotice(msg.body);
}
```

> **Where this breaks.**
>
> - **Per-item results are what make batching safe.** A gateway that rejects a whole batch for one bad return needs a different loop: retry the batch split in half until the bad item is isolated, then dead-letter only that one.
> - **The token bucket must be shared across the fleet** (18.2a). A per-process limiter at 20/s across 12 workers sends 240 calls a second.
> - **`SPOP` loses IDs if the worker crashes mid-batch.** For latest-wins work that's acceptable, because the next dashboard view marks the return again. It's never acceptable for submissions, which is why they use a queue with leases and acknowledgments.
> - **An expired message should still count.** Silently dropping work hides overload. The `jobs.expired` metric is how you notice that the queue is running past its budget.
