# The Cache Is Now a Distributed System: Placement, Failure, and Warm-up at Scale

_Module 23.3 — Scalability Patterns_

## The Problem

Suppose you run an online course platform. At peak it serves about 60,000 cacheable reads a second: course pages, lesson metadata, enrollment checks. The cache hit rate is 97%, so only about 1,800 of those reads a second reach the database. The team has load-tested the database and knows it can absorb about 4,800. That gives them a number Module 13.2b asked every team to compute, the **survivable hit rate**:

```
1 − 4,800 / 60,000 = 92%
```

Below 92%, the database falls over. Module 13 made the cache correct and protected its miss path. This quarter's incidents come from somewhere else: the cache stopped being one box.

**Adding a node took the site down.** The single Redis node was at 90% CPU at peak and evicting keys it still needed, so the team split the keys across four nodes with `hash(key) % 4`. It worked for six months. Then they added a fifth node and changed the code to `% 5`. A key stays on the same node only when `h % 4 == h % 5`, which is true for 1 key in 5. Four-fifths of the cache became unreachable at once:

```
hit rate:           97% ──▶ 19%
reads reaching DB:  1,800/s ──▶ 48,600/s      (capacity 4,800/s)
```

A planned capacity increase became a 40-minute outage.

**Losing a node took it down again.** The team moved to Redis Cluster: six primaries, no replicas, "because it's only a cache." Then one node's host failed. A sixth of the keys were gone, and the hit rate fell to about 81%. That's about 11,400 reads a second at the database, more than twice what it can take. The replacement node started empty, and filling it needed exactly the database capacity that wasn't there. The site stayed degraded until the team shed traffic by hand.

**One node was busy while five were idle.** To use multi-key commands (fetching a course's lessons in one `MGET`, and 13.3a's tag sets), the team gave keys a hash tag like `{course:1017}`, which tells Redis Cluster to store them together. Course 1017, a free introduction to Python, gets about 30% of all course-page reads. Every key with its tag, including every learner's progress record for it, lives on one node. That node sits at 100% CPU while the other five idle at 20%, and adding more nodes changes nothing.

**The cache went stale after invalidation "worked."** After 23.2a, database reads go to replicas. An instructor fixes a typo in a lesson. The app commits to the primary and deletes the cache key, exactly as 13.2a prescribes. A moment later a learner opens that lesson, misses, and refills the cache from a replica running 800 ms behind. The old typo is now cached for an hour, and staging never showed the bug, because staging has no replica lag.

None of these is a caching bug in Module 13's sense. The keys, the TTLs and the invalidation logic were all right. What went wrong was how keys map to machines, what happens when a machine disappears, and where the cache gets its data from.

## What It Is

At small scale a cache is a component: one process whose design questions are about the data (13.1a to 13.4). At scale it becomes a **cache tier**, a distributed system with its own placement scheme, failure modes, network footprint and warm-up time. Two properties make it different:

- **It's distributed.** Keys are spread across nodes by some rule, and changing the set of nodes moves keys.
- **It's load-bearing.** Once the hit rate is above the survivable floor, the cache is part of the system's capacity. Losing cache data isn't a correctness problem, but it can still be an outage.

This looks like 23.2b's partitioning, and many ideas carry over: keys, skew, rebalancing. The difference is that a cache is allowed to lose data. Losing a database shard loses records. Losing a cache shard loses nothing permanent, but sends that shard's traffic to the origin all at once. So the design question for a cache tier is **how much miss traffic each change or failure creates**, and whether the origin can take it.

13.2b covered one key missing at a time: stampedes, serve-stale, single-flight. This article is about many keys missing together because of the tier's shape.

## Recognizing the Problem

- A single cache node is near its CPU limit, or evicting keys that are still requested.
- Adding or removing a cache node causes a drop in hit rate and a spike in database load.
- One cache node's failure shows up as a database incident.
- Per-node CPU or operations per second are very uneven across a cluster.
- `CROSSSLOT` errors appear, or hash tags are spreading through the key naming.
- Cache latency spikes line up with network throughput on the cache nodes, not with their CPU.
- The cache bill includes a large cross-zone data transfer line.
- Stale values appear shortly after edits, only in production, and more often when replica lag is high.
- Nobody knows how long it takes a new cache node, cluster or region to warm up, or what the database sees meanwhile.

## How It Works

### How keys find nodes

The placement rule decides how many keys move when the set of nodes changes:

```
rule                        adding a 5th node to 4     losing 1 of 4
─────────────────────────   ────────────────────────   ─────────────────────
hash % N                    ~80% of keys move          ~75% of keys move
consistent / rendezvous     ~20% move (the new share)  25% (only the lost ones)
fixed slots (Redis Cluster) only slots you move        that node's slots
```

**Modulo hashing** is the rule to never use for a cache that matters. A failed node doesn't just lose its own quarter; removing it from the list reindexes everything, and a 25% cold start becomes a 75% one.

**Consistent hashing** places nodes at many points on a ring (virtual nodes) and assigns each key to the next node clockwise. Adding a node takes over only the keys it now covers. Memcached clients have used a version of it, Ketama, for years. **Rendezvous hashing** (highest random weight) gets the same property differently: every node scores the key, and the highest score wins. It's simpler to implement and needs no ring, at the cost of scoring every node on each lookup, which is fine for tens of nodes.

**Redis Cluster** uses a fixed set of 16,384 hash slots. Each key's slot is a hash of its name, each node owns ranges of slots, and resharding moves slots between nodes while the cluster runs. Clients cache the slot map, and a node that no longer owns a slot answers with a `MOVED` redirect, which the client follows before refreshing its map.

**Where the rule runs:**

- **In smart clients,** which know the topology and connect directly to each node.
- **In a proxy** such as mcrouter, twemproxy or Envoy's Redis proxy, which keeps clients simple and centralizes routing and failover policy, at the cost of a hop.

**Multi-key operations limit where keys can live.** In Redis Cluster, `MGET`, transactions and Lua scripts only work when all their keys share a slot; otherwise they fail with `CROSSSLOT`. A **hash tag**, the part of a key inside `{…}`, makes Redis hash only that part, so keys sharing a tag share a slot. That's how the Python course ended up on one node. The rules:

- **Tag at the smallest group that truly needs atomicity,** such as one learner's session, never a whole popular entity.
- **Prefer pipelines of single-key commands** to multi-key commands where atomicity isn't needed. Cluster-aware clients spread a pipeline across nodes.
- **A slot can't be split.** If one tag is hot, moving slots won't help; only changing the keys will.

### Blast radius and the survivable floor

Without replicas, losing one of N equally loaded nodes removes about 1/N of cached traffic:

```
hit rate after losing one node  ≈  H × (1 − 1/N)

H = 97%, floor = 92%
N = 6   →  81%   below the floor: outage
N = 20  →  92%   just survivable
```

So node count is a reliability decision, not just a capacity one. Few large nodes each carry a large share of the traffic. There are four ways to keep a single failure above the floor:

- **More, smaller nodes,** so each one's share is small.
- **Replicas.** A Redis replica holds a warm copy, and Redis Cluster promotes it automatically when its primary stops responding (after `cluster-node-timeout`, 15 seconds by default). A failure then costs seconds of errors instead of a cold shard. It doubles memory cost, and replication is asynchronous, so writes from the last moments before failover can be lost. For a cache, that usually doesn't matter, with one exception: a lost *invalidation*. That's one more reason every entry keeps a TTL.
- **Spreading across zones,** so a zone failure costs a third or less, and placing each replica in a different zone from its primary.
- **A gutter pool.** Facebook's memcache paper describes it: when a node fails, clients send that node's keys to a small spare pool with short TTLs, instead of rehashing them onto the healthy nodes. Rehashing would spread the cold start across nodes that were fine and, if the failed node flaps, make keys bounce between homes.

The same arithmetic applies to planned changes. A deploy that flushes a node, a version upgrade that restarts nodes without replicas, or a resharding that moves too many slots at once are all "node losses" as far as the database is concerned.

### Hot keys and hot shards

13.2b warned that most "hot key" diagnoses are really hot shards. They look alike, one node much busier than the rest, but they have different fixes:

- **A hot shard** has many ordinary keys that happen to land together: an unlucky slot distribution, a big hash tag, or one tenant's keys. Rebalance slots, or change the tags.
- **A hot key** is one key, or a handful, carrying a large share of all traffic. Moving it just moves the problem. Serve it from an in-process L1 cache (13.2b), read it from replicas, or split it into several copies.

Per-node operations and CPU show which one you have. `redis-cli --hotkeys` (which needs an LFU eviction policy) or sampled client-side counts show which keys are responsible. Keep in mind that Redis executes commands on one core per node. I/O threads help with network work, but a node's command throughput has a ceiling that more cores don't raise.

**Reading from replicas** spreads read load on hot shards. In Redis Cluster a client connection opts in with `READONLY`, and most clients have a setting for it. The replica may be slightly behind its primary, which is usually fine for a cache, but it means an invalidation on the primary can take a moment to reach the replica you read from.

### The network is part of the cache

At scale, a cache node often hits its network limit before its CPU or memory:

```
bandwidth ≈ value size × reads per second
120 KB course outline × 3,000 reads/s ≈ 360 MB/s ≈ 2.9 Gbps from one node
```

That can exceed the sustained network allowance of the node type, and the result looks like "Redis is slow" while CPU is low. Large values also hurt tail latency for everyone, because a single-threaded server spends time writing them out. The fixes:

- **Keep large, hot values in L1,** so they don't cross the network on every read.
- **Compress values above a size threshold,** not every value.
- **Split large values** so a page fetches the part it needs.

**Zones cost money and time.** Most clouds bill data transfer between zones per gigabyte, and a cross-zone round trip adds latency. Clients that read from a replica in their own zone cut both, at the price of replica lag on reads.

**Connections multiply here too.** Each app instance holds connections to every cache node, so 200 instances and 12 nodes is at least 2,400 connections. Redis handles many connections well, but each has buffers, and after a failover every client reconnects at once. Reconnects need jittered backoff (23.1b), and clients need to refresh their topology promptly, or they keep sending requests to the node that just failed.

### Caches in front of replicas

The stale typo is 13.2a's fill race with a much bigger window. With a primary-only database the window is a few milliseconds. With replicas, it's the replication lag, which 23.2a showed can reach 40 seconds:

```
t = 0 ms     instructor saves      → primary commits, cache key deleted
t = 30 ms    learner opens lesson  → cache miss → replica (800 ms behind) → old row
t = 35 ms    old row written to cache, TTL 1 hour
t = 800 ms   replica catches up; the cache never hears about it
```

The rule: **a fill must come from a source at least as fresh as the invalidation that emptied the key.** There are four ways to enforce it:

- **Fill from the primary for a short window after an invalidation.** Leave a marker when invalidating, and have misses that find the marker read from the primary. Facebook's paper calls these *remote markers* in its multi-region setup. It's simple, but it adds primary load on busy keys.
- **Version-gated fills.** Replace the deleted value with a small tombstone carrying the row's new version, and accept a fill only if the row being cached is at least that version. A replica that's behind produces an older version, the fill is refused, and the caller reads the primary. This is exact, and it's what the Implementation shows.
- **Delete twice.** Delete on commit, and delete again after a delay longer than typical lag. It's cheap and common, but it's a probability, not a guarantee: a lag spike longer than the delay still leaves a stale entry.
- **Invalidate from the replica's own change stream.** If each region's cache is invalidated by a process reading its local replica's change log (38.4), the invalidation can't arrive before the data does. This is the usual multi-region design. It still has 13.2a's ordering race, so it's often combined with version checks.

In multi-region systems each region usually has its own cache pool. Invalidations must reach every region, and each region's cache must be filled from data that's at least as fresh as the invalidation it received.

### Replacing or adding a whole cache

Some events empty a whole cache at once: a new region, a migration to a new cluster or provider, a change to the key format (13.1a's version prefix). The survivable floor turns each of these into a rate problem:

```
origin load = (1 − hit rate of the new cache) × traffic sent to it
            must stay below origin capacity
```

Techniques, roughly from cheapest to most involved:

- **Shift traffic gradually.** Send 5% of reads to the new cache, let it fill, then 20%, then more, watching origin load against its capacity at each step. It works for new clusters and new regions.
- **Warm from the old cache.** On a miss in the new cache, read the old one before the origin, for a limited period. Facebook's paper calls this cold cluster warm-up, and mcrouter has a route for it. During the migration, invalidations must go to both caches, or the new one fills with stale copies.
- **Restore a snapshot.** Loading an RDB file gives a new node its data in minutes, but the data is as old as the snapshot, so it's only safe with short TTLs or version-gated reads.
- **Replay recent traffic** for the hottest keys (13.2b's head-only warming).
- **Migrate key formats lazily.** When the format changes from `v3` to `v4`, read `v4`, fall back to `v3` and convert on a miss, and write `v4`. The cold start spreads out over one TTL instead of landing at deploy time.

### Planning capacity for the tier

A load-bearing cache needs the same capacity plan as a database:

- **Memory:** the working set, plus fragmentation, replication buffers, and headroom for snapshots. Redis forks to write RDB and AOF files, and under heavy writes copy-on-write can nearly double memory use during the fork.
- **CPU per node,** against the single-threaded ceiling.
- **Network per node,** from value size × rate.
- **Evictions,** the leading indicator that the working set no longer fits.
- **Failure headroom:** the tier must stay above the survivable floor with one node, or one zone, gone.

## When It's Appropriate

- **Replicas for cache nodes** as soon as losing one node would push the hit rate below the survivable floor. With H = 97% and a 92% floor, that's any cluster of fewer than about 20 nodes.
- **Sharding the cache** when one node's CPU is above roughly 60% at peak, it evicts keys still in use, or its network is near its allowance. Use slots or consistent hashing, never modulo.
- **Hash tags** only for small groups that need atomic multi-key operations, such as one user's session and rate-limit keys.
- **Zone-affinity reads** when cross-zone transfer is a visible cost or cache latency matters at the millisecond level, and the data tolerates replica lag.
- **Version-gated fills** when the database reads that fill the cache go to replicas with real lag, and a stale entry lasting a full TTL would be noticed. Lesson content an instructor just fixed qualifies; a trending-courses list doesn't.
- **A gradual traffic ramp or warm-from-old** for any planned cold start, whenever the new cache's initial miss rate times traffic exceeds origin capacity.
- **Per-region pools with local invalidation** once you serve from more than one region.

## When It's Unnecessary or Overkill

- **Clustering before one node is the constraint.** A single modern node with a replica serves well over 100,000 operations a second (13.4). A cluster adds slots, redirects and `CROSSSLOT` errors for nothing.
- **Gutter pools and replicas when the origin can serve everything.** If the database survives a 0% hit rate at peak, a cache failure is a latency event, not an outage, and the machinery isn't worth it.
- **Version-gated fills when fills come from the primary,** or when a few seconds of extra staleness is acceptable. Delete twice, or accept the TTL.
- **Hash tags as a naming convention.** They're a placement instruction, and a broad one creates the hot slot.
- **Warm-up machinery for small caches** that refill in seconds from an origin with room to spare.
- **Cross-region replication of a cache.** Replicating the source data and filling each region's cache locally is usually simpler and more correct.

## Trade-offs

- **Replicas double memory cost** and still lose recent writes on failover, including invalidations.
- **More nodes mean more connections, more topology changes and more to monitor,** while shrinking each failure's blast radius.
- **Cluster mode restricts commands.** Multi-key operations, scripts and transactions only work within a slot, so some 13.3a techniques need redesigning.
- **Smart clients and proxies both have costs.** Smart clients spread topology logic into every language you use, and a stale slot map causes errors after failover. Proxies add a hop and a component to run.
- **Zone-affinity and replica reads trade freshness for cost and latency,** which widens every invalidation window.
- **Version-gated fills add a Lua call per fill, a version column on every cached row, and more primary reads during lag spikes.** A tombstone's TTL is also a lag budget: when lag exceeds it, the guard quietly stops protecting you.
- **Every warm-up plan slows down a change** that could otherwise be instant, and the old cluster has to keep running during the migration.
- **The cache tier becomes something you capacity-plan, upgrade carefully and page on,** which is operational weight you took on when the hit rate passed the survivable floor.

## Alternatives

- **Lower the floor instead of protecting the cache.** A larger or better-tuned origin (Module 22), or cheaper queries, makes a cold cache survivable. If the origin can take 30% misses, most of this article becomes optional.
- **Cache further out.** Public content served from a CDN (13.1a, 7.4a) never reaches your cache tier, and CDNs handle placement and failure for you.
- **Use a durable read model instead of a cache** (23.2b) when the system can't survive losing the data. A projection that's persisted and rebuilt deliberately doesn't vanish when a node dies.
- **Use a managed, serverless cache** that handles sharding and scaling. You still own the key design, hash tags and the survivable floor.
- **Keep hot values in-process** with server-assisted invalidation (13.3a) to take the heaviest keys off the network entirely.

## How to Achieve It

**1. Compute the survivable hit rate and write it next to the current one.** Load-test the origin to find its capacity (22.5). *Move on when* both numbers are on the cache dashboard.

**2. Run one managed node with a replica in another zone, and test failover** during business hours. *Move on when* node CPU passes about 60% at peak, evictions hit keys still in use, or network nears its allowance.

**3. Prepare keys for sharding before sharding.** Remove multi-key operations that don't need atomicity, limit hash tags to small groups, and confirm the client supports cluster mode or consistent hashing. *Move on when* nothing in the code depends on two unrelated keys living together.

**4. Shard, and choose the node count from the blast radius,** not just capacity: H × (1 − 1/N) must stay above the floor, or every primary needs a replica. Spread nodes across zones.

**5. Add per-node dashboards** for operations, CPU, network, memory and evictions, and sample hot keys. *Act when* one node diverges: rebalance for a hot shard, use L1 or replicas for a hot key.

**6. If the fills read from database replicas, add version-gated fills** or fills from the primary after invalidation. *Do this when* stale-after-edit reports appear or lag spikes are routine.

**7. Write runbooks for the big cold starts:** node loss, cluster replacement, key-format change, and new region, each with a traffic ramp tied to origin load. Rehearse one.

**8. For multiple regions,** give each region its own pool, invalidated from its own replica's change stream (38.4).

## Implementation

The code is TypeScript, using ioredis, which supports Redis Cluster and custom Lua commands. It shows two things: why the placement rule decides the size of a cold start, and how to stop a lagging replica from refilling the cache with old data.

### Measuring what a node change moves

```ts
import { createHash } from "node:crypto";

const h = (s: string) => createHash("md5").update(s).digest().readUInt32BE(0);

const modulo = (key: string, nodes: string[]) => nodes[h(key) % nodes.length];

// Rendezvous hashing: every node scores the key, and the highest score wins.
// A new node takes only the keys it now outscores everyone for, about 1/N of them.
const rendezvous = (key: string, nodes: string[]) =>
  nodes.reduce((best, n) => (h(`${n}:${key}`) > h(`${best}:${key}`) ? n : best));

function movedShare(assign: typeof modulo, before: string[], after: string[], samples = 100_000) {
  let moved = 0;
  for (let i = 0; i < samples; i++) {
    const key = `lesson:${i}`;
    if (assign(key, before) !== assign(key, after)) moved++;
  }
  return moved / samples;
}

const four = ["c1", "c2", "c3", "c4"];
const five = [...four, "c5"];
const withoutC3 = ["c1", "c2", "c4"];

console.log(movedShare(modulo, four, five));           // ≈ 0.80
console.log(movedShare(rendezvous, four, five));       // ≈ 0.20
console.log(movedShare(modulo, four, withoutC3));      // ≈ 0.75, though only 0.25 was lost
console.log(movedShare(rendezvous, four, withoutC3));  // ≈ 0.25
```

Multiply each number by your traffic and compare it with origin capacity. That's the cost of the change before you make it. Running this against real key names, weighted by real traffic, also shows skew that uniform test keys hide.

### Fills that can't go backward

The write side replaces the cached value with a tombstone carrying the row's new version. The read side accepts a fill only if the row it read is at least that fresh.

```ts
import { Cluster } from "ioredis";

const redis = new Cluster(CACHE_NODES, { scaleReads: "master" }); // read primaries: see the aside

// Only ever raise the version: post-commit calls can arrive out of order.
redis.defineCommand("markChanged", {
  numberOfKeys: 1,
  lua: `
    local cur = redis.call('GET', KEYS[1])
    if cur and cjson.decode(cur).v >= tonumber(ARGV[1]) then return 0 end
    redis.call('SET', KEYS[1], cjson.encode({tomb = 1, v = tonumber(ARGV[1])}), 'PX', ARGV[2])
    return 1`,
});

// 1 = stored, 0 = the cache already has this version or newer,
// -1 = the source is older than the last write: read the primary instead.
redis.defineCommand("fillIfFresh", {
  numberOfKeys: 1,
  lua: `
    local cur = redis.call('GET', KEYS[1])
    if cur then
      local c = cjson.decode(cur)
      local v = tonumber(ARGV[1])
      if c.tomb then
        if v < c.v then return -1 end
      elseif v <= c.v then
        return 0
      end
    end
    redis.call('SET', KEYS[1], ARGV[2], 'PX', ARGV[3])
    return 1`,
});
// (TypeScript typings for custom commands come from module augmentation, omitted here.)

const key = (id: string) => `lesson:v3:${id}`;
const entry = (l: Lesson) => JSON.stringify({ v: l.version, data: l });

export async function updateLesson(id: string, patch: LessonPatch) {
  const version = await primaryDb.updateLesson(id, patch); // bumps version in the same transaction
  await redis.markChanged(key(id), version, TOMBSTONE_TTL_MS);
}

export async function getLesson(id: string): Promise<Lesson> {
  const cached = await redis.get(key(id));
  if (cached) {
    const e = JSON.parse(cached);
    if (!e.tomb) return e.data;
  }
  const row = await replicaDb.lesson(id); // fast, possibly behind
  if ((await redis.fillIfFresh(key(id), row.version, entry(row), TTL_MS)) !== -1) return row;

  const fresh = await primaryDb.lesson(id); // the replica hasn't seen the edit yet
  await redis.fillIfFresh(key(id), fresh.version, entry(fresh), TTL_MS);
  return fresh;
}
```

> **Where this still breaks.**
>
> - **The tombstone's TTL is your lag budget.** Once it expires, the key is simply absent and fills are unguarded again. Set it well above normal lag, such as 60 seconds, and alert on replica lag well below it.
> - **The cache must answer from its primary.** `scaleReads: "master"` is deliberate. Reading the key from a cache replica that hasn't received the tombstone yet would skip the guard. If you read cache replicas for load, accept that gap or apply the guard only to keys that are edited.
> - **A cache failover can lose the tombstone,** because cache replication is asynchronous. The entry's TTL is still the last line of defense.
> - **A tombstone on a hot key sends every reader down the miss path,** and during lag every one of them to the database primary. Put 13.2b's single-flight around the whole fill, including the primary fallback, or one edit to a popular lesson becomes a herd on the primary.
> - **Tombstones can carry the old value.** Store the previous `data` inside the tombstone, and hot keys can keep serving it while the fill runs. That's 13.2b's mark-stale-instead-of-delete, now with a version attached.
> - **If `markChanged` fails,** the old entry stays until its TTL, exactly as in 13.2a. Count those failures.

## Further Reading

- **Nishtala et al., "Scaling Memcache at Facebook"** (NSDI 2013). Gutter pools, regional pools, invalidation from the database's log, remote markers, and cold cluster warm-up, all from one production system. Most of this article's techniques are described there first.
- **Redis documentation: "Redis cluster specification"** and the cluster scaling tutorial. Hash slots, hash tags, `MOVED` and `ASK` redirects, replica promotion, and `READONLY`.
- **Karger et al., "Consistent Hashing and Random Trees"** (STOC 1997), and **Thaler & Ravishankar, "Using Name-Based Mappings to Increase Hit Rates"** (IEEE/ACM Transactions on Networking, 1998), the origin of rendezvous hashing.
- **mcrouter documentation** (Meta, on GitHub). A production routing proxy for memcached, including failover and warm-up routes.
- **AWS Builders' Library, "Caching challenges and strategies"** (Matt Brinkley and Jas Chhabra). Cold starts, cache sizing and the danger of a cache the system can't live without.
- **Bronson et al., "Metastable Failures in Distributed Systems"** (HotOS 2021). Why a system that lost its cache can stay down after the trigger is gone.
- **Yang et al., "A Large Scale Analysis of Hundreds of In-Memory Cache Clusters at Twitter"** (OSDI 2020). Real value sizes, TTLs and workload shapes, useful for checking your own capacity assumptions.
- **In this collection:** 13.1a (key versions), 13.2a (the fill race), 13.2b (the survivable hit rate, single-flight, hot keys), 13.3a (multi-layer invalidation), 13.4 (Redis or Memcached, client settings), 23.1b (consistent hashing and reconnects), 23.2a (replica lag), 23.2b (partitioning), 38.4 (change data capture), 22.5 (load testing), 24.2 (regions and failover).
