# What Actually Travels: Physical, Logical and Statement-Based Replication

_Module 38.1a — Advanced Database Techniques_

## The Problem

Suppose you run a scheduling platform for physiotherapy clinics. It has one Postgres 14 cluster holding 2.1 TB. There's a primary, a physical standby for failover (24.2a), and two read replicas (23.2a). Postgres 14 stops receiving fixes on November 12, 2026, so the team plans a move to Postgres 18 on new hosts. The business sets two conditions: under five minutes of write downtime, and a way back if the new version misbehaves.

**Attempt one: add a replica running 18.** That's how the team adds read replicas, and it's how failover works. Point a new server at the primary, let it catch up, promote it. The Postgres 18 server refuses to start streaming. Streaming replication requires the same major version on both sides.

**Attempt two: dump and restore.** The rehearsal takes 9 hours 40 minutes. The limit is five minutes.

**Attempt three: logical replication.** It's designed for exactly this, and over the next three weeks it produces four incidents.

**Day 1: the migration breaks production.** The team creates a publication `FOR ALL TABLES`. Within the hour, the retention job that trims `sms_delivery_log` starts failing on the production primary:

```
ERROR:  cannot delete from table "sms_delivery_log" because it does not have
        a replica identity and publishes deletes
```

The table has no primary key. Turning on a migration tool broke a production write path.

**Day 4: the disk fills over a weekend.** The initial copy is still running when a developer ships an ordinary migration: `ALTER TABLE appointments ADD COLUMN cancellation_reason text`. On the new cluster, the process that applies incoming changes hits a row with a column it doesn't have. It logs an error, restarts, fails again, and applies nothing. The old primary keeps every byte of change log since the failure, because the subscriber hasn't confirmed it:

```
                 WAL held for the stalled subscriber     primary disk
Fri 17:00        12 GB   ▓░░░░░░░░░                        61%
Sat 17:00       170 GB   ▓▓▓▓░░░░░░                        79%
Mon 08:00       380 GB   ▓▓▓▓▓▓▓▓▓░                        94%
```

**Week 3: the cutover rehearsal.** On staging, every table matches row for row. The team switches traffic to the new cluster, and the first new booking fails:

```
ERROR:  duplicate key value violates unique constraint "appointments_pkey"
DETAIL:  Key (id)=(1) already exists.
```

The rows came across. The sequences that generate their IDs stayed at their starting values.

None of these is a Postgres bug. Each follows from *what the replication stream carries*. Articles 23.2a and 24.2a used replicas for read scaling and failover, where that question never came up, because the answer there is "everything, byte for byte." Here the answer is different.

## What It Is

A replication stream is a log the leader writes and followers replay. Older documentation calls the pair **master and slave**; current usage is **primary and replica**, or **leader and follower**. The topology in all three articles so far (one writer, many copies) is the same. What changes is the payload. There are three kinds:

- **Statement-based:** the leader ships the SQL it ran, and the follower runs it again.
- **Logical (row-based):** the leader ships the effect on each row, such as "row 881 in `appointments`: `status` changed from `pending` to `cancelled`." The follower applies that change through its own tables and indexes.
- **Physical:** the leader ships changes to storage, such as "these bytes changed on page 48,213 of this file." The follower writes the same bytes to the same place.

**The payload determines what the follower is allowed to be.** A physical follower has to be an identical twin: same major version, whole cluster, read-only. A logical follower can be a different database: another version, a subset of tables, extra indexes, and even writable. The cost is that it doesn't receive anything that isn't a row change.

Two points of disambiguation:

- **Payload is independent of timing.** Synchronous or asynchronous commit (24.2a) is a separate setting from physical or logical. Both kinds of stream can run in either mode.
- **Logical replication and change data capture (CDC) share a foundation.** Both decode the write-ahead log into row changes. Logical replication delivers those changes to another Postgres. CDC (38.4) delivers them to anything else, such as Kafka, a search index or a warehouse. This article covers the database-to-database case.

## Recognizing the Problem

- You need to change major version, hosts or platform, and dump/restore takes longer than your downtime budget.
- You want a copy that differs from the source: only some tables, one tenant's rows, different indexes or a longer retention period.
- `cannot update/delete from table … does not have a replica identity` appears on the **publisher**.
- `pg_replication_slots` shows a slot with `active = false`, or retained WAL grows while traffic is flat.
- Primary disk use climbs steadily and nothing in the application explains it.
- Subscriber logs show `missing replicated column` or unique violations, and lag grows without limit.
- The first insert after switching to a logically replicated copy fails with a duplicate key.
- After a failover, logical subscribers or CDC connectors lost their position and needed a full resync.
- On MySQL, a replica's rows differ from the source with no error, the log shows "Unsafe statement written to the binary log", or `binlog_format` is `STATEMENT` or `MIXED`.

## How It Works

### One statement, three payloads

Take one statement run on the leader:

```sql
UPDATE appointments
SET    status = 'expired'
WHERE  status = 'pending' AND starts_at < now() - interval '1 day';
```

Here's what each payload sends to the follower:

```
statement   the SQL text above (≈110 bytes)
            → follower re-runs it: its own now(), its own row order, its own triggers

logical     3,412 row changes, keyed by primary key:
            appointments id=881   status: pending → expired
            appointments id=904   status: pending → expired   …
            → follower applies each one against its own tables and indexes

physical    WAL records for every page touched: heap pages, each index page,
            visibility-map bits, full-page images after a checkpoint
            → follower writes the same bytes to the same pages
```

As you move down the list, the stream gets larger and less ambiguous. The statement leaves the follower to reproduce the result. The row changes state the result. The page changes state it at the level of bytes.

### Statement-based: small, and quietly wrong

Shipping SQL is compact, and the log is easy to read. Its weakness is that it only works if running the statement again gives the same result, which holds less often than it seems.

MySQL used statement-based replication for years and kept patching the gaps. It logs the timestamp and random seed alongside each statement so that `NOW()` and `RAND()` come out the same on the replica. It still has a list of statements it considers **unsafe**:

- `UUID()` and `SYSDATE()`
- `UPDATE … LIMIT` without an `ORDER BY`, because the replica may pick different rows
- functions and triggers with side effects
- floating-point math, which can depend on the hardware

When one of these runs, the replica stays healthy and replication keeps running, but the replica now holds different data. Nothing reports it.

The industry has moved away from this approach. MySQL has defaulted to row-based logging since 5.7 and deprecated the `binlog_format` setting in 8.0.34, planning row-based as the only format. Redis made the same shift for Lua scripts: it now replicates the effects of a script rather than the script itself. If you find `STATEMENT` or `MIXED` in a MySQL configuration, treat it as legacy that needs migrating. Don't treat it as a performance optimization.

### Physical: an identical twin

Postgres's standard streaming replication sends the write-ahead log (WAL) itself. The replica is a copy of the primary's data files, kept up to date by replaying the same WAL records. That gives it some strong properties:

- **Everything replicates.** DDL, sequences, indexes, large objects, roles and every database in the cluster all come along, because they all live in the files.
- **Replay is cheap.** Writing bytes onto pages is less work than running SQL, and there is no per-table setup.
- **No primary keys are needed.** Pages are addressed by location, not by row identity.

The same design imposes limits:

- **Same major version, same binary format.** On-disk layout changes between major versions, so 14 can't stream to 18.
- **The whole cluster or nothing.** You can't replicate one table or one tenant.
- **Read-only, and identical.** The replica can't hold an index the primary lacks, or keep rows the primary deleted.
- **It copies mistakes faithfully.** A bad `DELETE` reaches the replica in milliseconds. This is 24.1a's reason why a standby isn't a backup.

For high availability and read scaling, these limits are exactly what you want: a twin can take over because it is a twin. For moving between versions or hosts, the same limits rule it out.

Managed databases such as Aurora and Neon go one layer lower. Replicas share the storage and replicate it underneath the database engine. It's the same idea, with the same rigidity.

### Logical: decode, ship, apply

Logical replication in Postgres is physical WAL decoded back into row changes:

```
 PUBLISHER                                           SUBSCRIBER
 ┌──────────┐   ┌──────────────┐  walsender  ┌────────────────┐   ┌──────────┐
 │  WAL     │──▶│ logical      │────────────▶│ apply worker   │──▶│ its own  │
 │ (pages)  │   │ decoding     │  row changes│ INSERT/UPDATE/ │   │ tables & │
 └──────────┘   │ (pgoutput)   │  in commit  │ DELETE by key  │   │ indexes  │
      ▲         └──────────────┘    order    └────────────────┘   └──────────┘
      │                                              │
      └────────── replication slot: "subscriber has confirmed up to LSN X" ◀───┘
```

The publisher needs `wal_level = logical` so that the WAL carries enough detail to rebuild rows. Postgres 19, now in beta, can switch this on automatically when it's needed.

A **publication** lists the tables to send. A **subscription** on the other side connects to it, copies each table's existing rows, and then streams changes made since the copy began. Changes arrive and are applied in **commit order**, one transaction at a time. The Implementation section relies on that ordering.

Each consequence below matches one of the incidents.

**Rows are found by key.** An `UPDATE` arrives as "change the row identified by X". The publisher has to write X into the WAL, and it uses the table's **replica identity** to do so. By default that's the primary key. A table without one can't describe which row changed, so Postgres refuses to run `UPDATE` or `DELETE` on it once it's published. The error appears on the publisher, which is how the Day 1 incident happened. The fallback, `REPLICA IDENTITY FULL`, logs the entire old row. That inflates the WAL and makes the subscriber search for each row, which is slow on large tables unless a suitable index exists. Postgres 16 and later can use such an index for this. The real fix is to add a primary key.

**Only row changes are sent.** Anything that isn't a row change doesn't travel:

- **DDL.** Schema changes don't replicate. A column the publisher starts sending, and the subscriber lacks, stops the apply worker, as on Day 4. The reverse case works: a subscriber may have extra columns. So additive changes go to the subscriber first and the publisher second.
- **Sequences.** Row values replicate, but the counters that generate them don't, as in the Week 3 rehearsal. Postgres 19 adds `FOR ALL SEQUENCES` and `REFRESH SEQUENCES`, but these copy values at particular moments rather than continuously, and they require the *publisher* to run 19. An upgrade from 14, 16 or 18 still has to move sequences by hand.
- **Large objects and materialized views** don't replicate either. `TRUNCATE` does, as of Postgres 11.

**The subscriber is an ordinary database.** It's writable and has its own indexes, triggers and constraints. That's what makes filtering possible. Postgres 15 added row filters (`WHERE tenant_id = 42`) and column lists, and you can publish only some operations, for example `publish = 'insert, update'` so deletes never reach a reporting copy. It's also a hazard. If anyone writes to a table that is also being replicated, an incoming row can collide with theirs. The apply worker then stops on a unique violation and retries, and nothing gets applied until someone intervenes. Postgres 18 counts these conflicts by type in `pg_stat_subscription_stats`, but it doesn't resolve them. Making two writers agree is 38.1b's subject.

**The slot keeps the stream's position, and it holds WAL.** A **replication slot** on the publisher records how far the subscriber has confirmed. The publisher keeps every WAL segment after that point, so a stalled subscriber doesn't lose changes. It also means a stalled subscriber can fill the publisher's disk, as on Day 4, and the publisher's availability now depends on a machine that isn't serving any traffic. There are two guards, each with a cost:

- `max_slot_wal_keep_size` (Postgres 13+) caps how much WAL a slot may retain.
- `idle_replication_slot_timeout` (Postgres 18) invalidates slots that stay inactive for too long.

Either way, the slot gets invalidated, and the subscriber has to start over with a full copy. You're choosing which failure you'd rather have: a full disk on the primary, or a resync. Pick one deliberately, and alert well before either happens.

**The initial copy is a long read on the publisher.** Each table is copied inside a transaction that holds a snapshot. A 10-hour copy of one large table keeps vacuum from cleaning up anything newer than that snapshot, so tables that change often bloat during the copy. For Postgres 17 and later sources, `pg_createsubscriber` avoids the bulk copy entirely: it turns an existing physical standby into a logical subscriber.

**Apply speed is limited too.** Commit order means changes are applied more or less in sequence. A publisher with 200 concurrent writers can produce changes faster than one apply process can apply them. Large transactions used to wait until commit before being sent at all. Postgres 16 added parallel apply for large transactions, and 18 made it the default for new subscriptions. The limit is lower than it was, but it hasn't gone away. Measure it under your peak write load before you depend on it.

**Failover can lose the slot.** The slot lives on the primary. Before Postgres 17, a physical failover (24.2a) left logical subscribers without their position, and they had to resync. Postgres 17 can keep logical slots synchronized to standbys (the `failover` option), provided you enable it.

### Positions, not time

Every point in the stream has a log sequence number (LSN). "The subscriber is caught up" is a claim about LSNs or markers, not about how many seconds of lag a dashboard shows. A lag figure reports what happened a moment ago. An LSN comparison, or a marker row that has arrived on the other side, shows that a specific change has been applied. Cutovers rely on the second kind.

## When It's Appropriate

- **Major-version upgrades where the downtime budget is minutes and dump/restore takes hours.** The scenario above: 2.1 TB, a 9-hour restore and a 5-minute limit. Logical replication lets the new version catch up while the old one keeps serving traffic, and the write pause covers only the final catch-up.
- **Moving hosts, platforms or providers.** Managed services generally don't accept an external physical replica, and different hardware, operating systems or storage rule out byte-level copies. Row changes work across those boundaries.
- **Extracting a tenant or a bounded context.** You can move one large tenant to a dedicated database (5.3), or move a module's tables to the service that now owns them (2.1), using a row filter or a table list. The source keeps running until the switch.
- **A copy that should differ on purpose.** For example, a reporting database that keeps seven years of history while production purges after 90 days (publish inserts and updates, but not deletes), with its own analytical indexes that would slow writes on the primary.
- **Rollback after an upgrade.** After cutover, a reverse subscription from the new cluster back to the old one keeps the old one current. If the new version misbehaves on day two, you switch back without losing a day of writes.

## When It's Unnecessary or Overkill

- **High availability and read replicas.** Physical replication is simpler and complete, needs no primary keys, and has no DDL rules. Using logical replication for a standby gives you all of its gaps and nothing in return.
- **Databases that fit the maintenance window.** A 40 GB database that dumps and restores in 15 minutes during a Sunday window doesn't need a three-week project.
- **Same-host major upgrades.** `pg_upgrade --link` reuses the data files and takes minutes of downtime. It has real downsides (see Alternatives), but if they're acceptable, it's much less work.
- **Feeding Kafka, search or a warehouse.** That's CDC (38.4). A Postgres subscriber is the wrong consumer when the target isn't Postgres.
- **A permanent link between two services' databases.** A logical subscription that stays in place turns one team's table schema into an API for another team, with no versioning and a slot that can fill the owning team's disk. If two services need to share data long-term, publish events (Module 37).

## Trade-offs

- **The schema becomes a contract between two databases for as long as replication runs.** Every migration needs an order: subscriber first for additions, publisher first for removals. Someone has to enforce that for the duration of the project.
- **The publisher's disk depends on the subscriber.** A slot turns "the subscriber is broken" into "the primary is running out of disk." Caps turn that into a full resync. There is no setting that avoids both.
- **Every table needs a row identity.** Tables without primary keys need a key or `REPLICA IDENTITY FULL`, which increases WAL volume and slows apply.
- **Gaps you have to cover yourself:** sequences (unless the publisher runs 19), DDL, large objects and materialized views. None of them fails loudly while replication runs. They fail at cutover.
- **Apply throughput is limited.** Commit-order apply can fall behind a busy publisher. Measure it under peak load in a rehearsal, not on migration day.
- **A writable follower can conflict.** An accidental write on the subscriber stops replication. Nothing resolves the conflict for you.
- **The initial copy has a cost.** It means hours of read load and held-back vacuum on the publisher, which leads to bloat in tables that change often.
- **Correctness is your job to check.** Nothing confirms that the copy is complete. Row counts and per-table checksums are work you add.
- **The alternatives have costs of their own.** Physical replication is rigid and copies mistakes. Statement-based replication can diverge silently. Each payload has its own failure mode.

## Alternatives

- **`pg_upgrade` in place.** With `--link`, the new version reuses the old data files, and downtime is minutes regardless of size. The downsides: it only works on the same host, rolling back after new writes means restoring from backup, physical standbys have to be rebuilt afterwards, and before Postgres 18 the new cluster started without planner statistics until `ANALYZE` finished. For many teams this is the right answer, and logical replication is justified only when one of those downsides is unacceptable.
- **Dump and restore.** It's the simplest option and the most thorough check, since everything is rebuilt from scratch. Downtime grows with database size.
- **Managed blue/green upgrades.** Several cloud providers offer a packaged cutover for major versions. Many are built on logical replication, so the same rules about primary keys, DDL and sequences apply, with a more convenient interface.
- **Trigger-based replication** (Slony, Bucardo, Londiste). This was the pre-Postgres-10 way to get row-level replication. Every write fires extra triggers on the primary. It's mostly relevant now for understanding older systems.
- **A CDC pipeline** (Debezium into a sink). It's the right tool when the target isn't Postgres, or when many consumers need the same changes (38.4).
- **Application dual writes.** Writing to both databases from the application has the dual-write problem from 37.2a: one write succeeds, the other fails, and nothing reconciles them. Don't use it.

## How to Achieve It

This is the path for an upgrade or migration. A tenant extraction follows the same steps with a row filter added.

**1. Take inventory.** List tables with no replica identity, all sequences, large objects, materialized views and extensions, and check that the extensions exist on the target version. Measure the peak WAL rate.
_Move on when_ you have the list and an owner for each item on it.

**2. Add the guards before creating any slot.** Set `max_slot_wal_keep_size`, alert on retained WAL per slot and on apply errors, and page on `wal_status` moving past `reserved`.
_Move on when_ an alert has fired in a test in which you deliberately stopped a subscriber.

**3. Fix replica identity on the publisher.** Add primary keys. Use `REPLICA IDENTITY FULL` only for tables that rarely receive updates or deletes.
_Move on when_ the preflight query below returns nothing.

**4. Build the schema on the target, then freeze or order DDL.** Use `pg_dump --schema-only`. Announce a rule for the rest of the project: additions go to the subscriber first, removals go to the publisher first, and CI checks the order.

**5. Copy and stream.** Create the publication and subscription. For very large sources on 17 or later, consider `pg_createsubscriber`. Watch bloat on tables that change often during the copy.
_Move on when_ all tables report ready (`pg_subscription_rel`) and apply keeps up at peak load.

**6. Verify.** Compare row counts, and checksums on key ranges, for every table. Then leave it running for a few days and verify again.

**7. Rehearse the cutover on staging, including sequences and rollback.** Time each step.
_Move on when_ the rehearsal fits the downtime budget with room to spare, and the rollback has been run at least once.

**8. Cut over, then reverse.** Pause writes, confirm the last change has arrived, move sequences, switch traffic, and immediately start replication from the new cluster back to the old one. Remove the reverse link only after the new version has been through a full business cycle, such as a month-end.

## Implementation

The implementation is in Go. The interesting part is a small operational tool, the cutover, where the order of steps and the abort path matter more than any single query. Go suits a short program that operators run once, under pressure, with clear failure handling.

### Preflight and guards

These are the two queries that would have prevented the first two incidents.

```sql
-- Tables whose UPDATE/DELETE will fail on the publisher once published.
SELECT c.oid::regclass AS table_without_identity
FROM   pg_class c
JOIN   pg_namespace n ON n.oid = c.relnamespace
WHERE  c.relkind IN ('r', 'p')
  AND  n.nspname NOT IN ('pg_catalog', 'information_schema')
  AND  (c.relreplident = 'n'
        OR (c.relreplident = 'd' AND NOT EXISTS (
              SELECT 1 FROM pg_index i
              WHERE  i.indrelid = c.oid AND i.indisprimary)));

-- What each slot is making the publisher keep. Alert on this, not on lag.
SELECT slot_name, active, wal_status,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM   pg_replication_slots;
```

> **Why retained WAL rather than lag.** On Day 4, lag dashboards measured on the subscriber showed "last applied: Friday 17:00," which looks like a stale metric, not an emergency. Retained WAL is measured on the primary, in bytes, next to the disk it's filling, which is where the danger is.

### The cutover

```go
// Cutover moves writes from oldDB to newDB. Every early return leaves the
// old primary serving traffic again: the abort path is the default path.
func Cutover(ctx context.Context, oldAdmin, newDB *pgx.Conn, pool Pooler, newDSN string) (err error) {
	// 1. Stop new writes at the one place every client passes through.
	//    PgBouncer's PAUSE waits for in-flight transactions to finish.
	pauseCtx, cancel := context.WithTimeout(ctx, 30*time.Second)
	defer cancel()
	if err := pool.Pause(pauseCtx, "app"); err != nil {
		return fmt.Errorf("pause: %w", err) // a long transaction is holding us; abort cleanly
	}
	defer func() {
		if err != nil {
			pool.Resume(context.Background(), "app") // back to the old primary
		}
	}()

	// 2. Write a marker through a direct admin connection, then wait for it
	//    to appear on the new side.
	token := uuid.NewString()
	if _, err := oldAdmin.Exec(ctx,
		`INSERT INTO cutover_marker (token) VALUES ($1)`, token); err != nil {
		return err
	}
	if err := waitForRow(ctx, newDB, token, 60*time.Second); err != nil {
		return fmt.Errorf("subscriber never caught up: %w", err)
	}

	// 3. Carry the sequences across. Before a 19 publisher, nothing else will.
	if err := syncSequences(ctx, oldAdmin, newDB, 1000); err != nil {
		return err
	}

	// 4. Send traffic to the new primary and let it through.
	if err := pool.Retarget(ctx, "app", newDSN); err != nil {
		return err
	}
	return pool.Resume(ctx, "app")
}
```

> **Why a marker row and not a lag reading.** Changes are applied in commit order, so once the marker is visible on the subscriber, every transaction committed before it has been applied too. That's a proof. "Lag is 0 s" is a sample taken a moment ago, and it can read zero while a large transaction is still being applied. The marker table has to be in the publication and have a primary key, which the preflight query checks.

> **Where the pause leaks.** The pause covers only clients that go through the pooler. A cron job, a migration runner or an engineer's `psql` session connected directly can still commit after the marker, and that change is lost at cutover. Before the real run, list `pg_stat_activity` on the old primary grouped by `client_addr` and `application_name`, and block the app role's direct access (`ALTER ROLE app NOLOGIN`) for the duration of the cutover.

```go
// syncSequences copies each sequence's position with a safety margin.
// Skipped IDs are harmless: sequences already leave gaps on rollback.
// Reused IDs are the Week 3 incident.
func syncSequences(ctx context.Context, from, to *pgx.Conn, margin int64) error {
	rows, err := from.Query(ctx, `
		SELECT format('%I.%I', schemaname, sequencename), last_value
		FROM   pg_sequences
		WHERE  last_value IS NOT NULL`) // NULL: never used, nothing to carry
	if err != nil {
		return err
	}
	defer rows.Close()

	for rows.Next() {
		var name string
		var last int64
		if err := rows.Scan(&name, &last); err != nil {
			return err
		}
		if _, err := to.Exec(ctx, `SELECT setval($1::regclass, $2)`, name, last+margin); err != nil {
			return fmt.Errorf("setval %s: %w", name, err)
		}
	}
	return rows.Err()
}
```

> **The same step runs in reverse.** Once the reverse subscription (new → old) is running for rollback, the old cluster's sequences fall behind in the same way. If you ever roll back, run `syncSequences` in the other direction before sending traffic back. Rolling back is a second cutover, and it should be rehearsed like one.

## Further Reading

- **PostgreSQL documentation, chapter "Logical Replication"**, especially the *Restrictions*, *Conflicts* and (for 19) *Replicating Sequences* sections. The restrictions section lists what doesn't travel.
- **PostgreSQL documentation: `pg_replication_slots`, `max_slot_wal_keep_size` and `idle_replication_slot_timeout`.** Read them together. They are the two guards and the view that shows whether you need them.
- **PostgreSQL documentation: `pg_upgrade`** (the `--link` mode and its warnings) and **`pg_createsubscriber`** (17+). These are the alternative, and the tool that shortens the logical path.
- **Martin Kleppmann, _Designing Data-Intensive Applications_, chapter 5, "Implementation of Replication Logs."** It covers statement-based, WAL shipping, logical and trigger-based replication, the same four-way taxonomy as this article, from first principles.
- **MySQL Reference Manual: "Replication Formats"** and **"Determination of Safe and Unsafe Statements in Binary Logging."** The unsafe-statement list is the best evidence for why statement-based replication was abandoned.
- **pgEdge, "Looking Forward to Postgres 19: Logically Sequenced"** (2026). A clear walkthrough of what sequence synchronization in 19 does, and that it runs at particular moments rather than continuously.
- **In this collection:** 23.2a (replicas, lag and session guarantees), 24.1a (a standby is not a backup), 24.2a (synchronous modes, failover, fencing), 24.2b (multi-region), 6.3 (expand–contract migrations: the same ordering rule as DDL on a subscriber), 5.3 (tenant data migration), 37.2a (the dual-write problem), 38.1b (multiple writers and conflicts), 38.2 (sharding, whose resharding moves rows the same way), 38.4 (CDC).

A sibling in another language wouldn't add much here. The substance is in the database and the order of operations, not in the client code.

---

The habit to take from this: whenever you rely on a copy of your data, ask what the stream actually carries. That determines what the copy can be, what it silently lacks, and what it costs the primary to keep it.
