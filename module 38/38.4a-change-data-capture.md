# Change Data Capture: Reading the Database's Own Log

_Module 38.4a — Advanced Database Techniques_

## The Problem

Suppose you run an online learning platform: about 40,000 courses, 3 million learners, and one Postgres database. Several other systems need to know when that data changes:

- **search**, an Elasticsearch index of courses
- **the warehouse**, where analysts study enrollments and completions
- **a cache** of course pages
- **a new recommendations service**, being built by another team, which needs its own copy of enrollments

The first version copies changes by polling: every night, and every minute for search, a job runs `SELECT * FROM courses WHERE updated_at > $last_run` and sends the results on. Then four things go wrong, spread over a year.

**The polling misses things.** A data fix runs `UPDATE courses SET category_id = 12 WHERE category_id = 7`, written by hand, which doesn't touch `updated_at`. 900 courses never move categories in search. Courses that authors delete don't show up in any query, since there's no row left to select, so search keeps showing them for months. Two transactions committing out of order (37.2a) make the job skip a few rows per week. And the nightly warehouse query takes 40 minutes on the primary.

**The disk fills up.** The team replaces polling with Debezium, which reads Postgres's write-ahead log. It works well for five months. Then Kafka Connect is being upgraded over a long weekend and the connector stays stopped. Postgres keeps every byte of WAL the connector hasn't confirmed, as promised. By Monday morning that's 1.9 TB, the disk is full, and the primary stops accepting writes. A data pipeline for search took down the product.

**Search shows placeholder text.** After an edit to a course's price, its description in search becomes `__debezium_unavailable_value`. Postgres stores large text values separately (TOAST) and doesn't include unchanged ones in the log. The connector fills the gap with a placeholder, and the search consumer indexes the placeholder as the description. 2,300 course descriptions are overwritten before anyone notices.

**The failover gap.** The primary fails over to a standby (24.2). The standby, on Postgres 16, has no copy of the connector's replication slot, so the connector creates a new one on the new primary, starting from now. Six minutes of changes between the last confirmed position and the failover are never read. Search, the cache and the warehouse are silently missing them, and nothing reports an error.

Polling asks the tables what changed, and tables don't remember. The log remembers everything, but reading it means taking on its operational rules.

## What It Is

**Change data capture (CDC)** turns committed changes in a database into a stream of events, one per row inserted, updated or deleted, in commit order. **Log-based CDC** reads the database's own transaction log (Postgres's write-ahead log, MySQL's binlog, MongoDB's oplog through change streams), so it sees every committed change, including deletes and changes made by scripts, with no change to application code and little load on the tables themselves.

Three ways to capture changes, compared:

- **Query-based** (polling `updated_at`): simple, and misses deletes, changes that don't touch the column, and out-of-order commits. It also adds query load.
- **Trigger-based:** triggers write changes to a table. Complete, and it adds a write to every transaction and couples capture to the schema.
- **Log-based:** complete, in commit order, cheap for the source. It needs a connector and careful operation of the log position it holds.

Tools: **Debezium** is the common open-source choice, running on Kafka Connect, as a standalone server, or embedded in a Java application. Managed options include AWS Database Migration Service, Google Datastream and Confluent's connectors. Some databases offer it natively: MongoDB change streams, DynamoDB Streams, and Postgres logical replication between Postgres databases.

Neighbors:

- **Physical replication** (23.2a) copies the WAL byte for byte to another Postgres server. **Logical decoding**, which CDC uses, turns the WAL into row-level changes any consumer can read.
- **The outbox** (37.2a) is a table of events the application writes deliberately. CDC can be its relay. Pointed at business tables instead, CDC gives you row changes, not business facts: `status` went from 2 to 3, not that a learner completed a course. 37.2c's advice applies: raw table changes aren't a contract for other teams.

## Recognizing the Problem

- Jobs copy data by querying `updated_at > last_run`.
- Deleted rows linger in search, caches or the warehouse.
- Changes made by scripts, bulk updates or other applications don't reach downstream systems.
- An application writes to the database and to a search index or cache in the same request (37.2a's dual write).
- A migration to a new database or service needs data kept in sync while both run.
- A replication slot exists and nobody monitors how much WAL it holds.
- Downstream copies drift slightly and are periodically rebuilt from scratch.

## How It Works

### Where the changes come from

```
  application ──► Postgres ──WAL──► logical decoding (pgoutput) ──► replication slot
                                     filtered by a publication        │  remembers the last
                                                                      │  confirmed position
                                                                      ▼
                                               Debezium connector ──► Kafka: one topic per table
                                                                      keyed by primary key
```

- **The WAL** records every change before it's applied, for crash recovery and replication.
- **Logical decoding** turns WAL records into row changes. `pgoutput` is the built-in output plugin.
- **A publication** chooses which tables are included.
- **A replication slot** is the consumer's bookmark. Postgres keeps all WAL from the slot's position onward until the consumer confirms it has processed it. That promise is what makes CDC complete, and it's what filled the disk.

MySQL works similarly with a row-based binlog and GTIDs as positions. MongoDB change streams give each event a resume token.

### Snapshot, then stream

The log only contains recent changes, so a new consumer first needs the existing data. The connector:

1. creates the slot, which fixes a position in the log;
2. reads every existing row in a consistent snapshot as of that position, emitting each as a read event (`op: "r"`);
3. streams changes from the slot's position onward.

Because the snapshot and the slot start at the same point, nothing is missed or counted twice. A full snapshot of a large table can take hours, though, and a new table added later needs its own. **Incremental snapshots** read a table in chunks while streaming continues, interleaving the two safely. Netflix described the technique in its DBLog paper, and Debezium implements it, triggered by writing a signal row into a table.

### What a change event contains

```json
{
  "op": "u",
  "before": { "id": 881, "title": "Intro to SQL", "category_id": 7, "price_cents": 4900 },
  "after":  { "id": 881, "title": "Intro to SQL", "category_id": 12, "price_cents": 4900,
              "description": "__debezium_unavailable_value" },
  "source": { "table": "courses", "lsn": 20834417664, "txId": 771203, "ts_ms": 1790071234000 }
}
```

- **`op`:** `c` create, `u` update, `d` delete, `r` a snapshot read.
- **`before` depends on replica identity.** By default, Postgres logs only the old primary key, so `before` is mostly empty. `REPLICA IDENTITY FULL` logs the whole old row, at the cost of more WAL for every update and delete. Consumers that need the old value, such as removing a course from its old category's count, need `FULL` on that table.
- **Unchanged TOAST values are missing.** Large values that an update didn't change aren't in the log, and Debezium substitutes a placeholder. Consumers must treat the placeholder as "unchanged," never as a value. `REPLICA IDENTITY FULL` also provides the old values, at its WAL cost.
- **Deletes** produce a `d` event with `before`, then, by default, a **tombstone**: the same key with a null value, so a compacted topic (37.2b) eventually drops the key. Consumers must handle both.
- **`source.lsn`** is the change's position in the log. For one row, positions increase in commit order, which makes it the natural version for idempotent writes downstream.

Ordering holds per row: events are keyed by primary key, so a row's changes land in one partition, in order. There's no order across tables, since each table is its own topic. A transaction that changed a course and its lessons appears as separate events in separate topics. Debezium can publish transaction boundaries on a separate topic for consumers that need to reassemble them, and most consumers shouldn't need to.

### The slot is a promise the database keeps at any cost

A slot holds back WAL until its consumer confirms it. If the consumer stops, slows down, or is abandoned after a proof of concept, WAL piles up until the disk is full. A logical slot also holds back cleanup of system catalog rows, which bloats the catalog. Four guards, all worth having:

- **Cap retained WAL.** `max_slot_wal_keep_size` (Postgres 13+) invalidates a slot that falls further behind than the limit. The database survives, and the connector needs a fresh snapshot.
- **Cap idle time.** `idle_replication_slot_timeout` (Postgres 18+) invalidates slots inactive for longer than the limit, which catches forgotten slots that the size cap might not.
- **Monitor every slot:** WAL retained, whether it's active, and how long it's been inactive (see the Implementation). Alert long before either limit.
- **Keep quiet slots moving.** If the captured tables rarely change but the rest of the database is busy, the slot has nothing to confirm and its position doesn't advance, while WAL for other tables piles up. Debezium's heartbeats fix this by periodically writing to a small table included in the publication.

Invalidating a slot trades one outage for another: the database stays up, and every consumer of that connector needs a re-snapshot. Decide in advance which one you'd rather have, for how long.

Long-running transactions also matter. Decoding emits a transaction only when it commits, so one large, slow transaction delays everything behind it and holds WAL while it runs. Keep batch jobs and backfills in small transactions.

### Failover

Before Postgres 17, logical slots existed only on the primary. After a failover, the slot was gone: the connector either started a new slot from the current position, losing everything in between (the six-minute gap), or needed a new snapshot.

Postgres 17 added **failover slots.** A slot created with the `failover` option is synchronized to standbys. On the standby, `sync_replication_slots = on` and `hot_standby_feedback = on` keep the copy current. On the primary, `synchronized_standby_slots` stops logical consumers from receiving changes the standby hasn't received yet, so after promotion the consumer can't be ahead of the new primary. Debezium 3.0.5 and later create failover slots with `slot.failover=true`. Synchronization is still asynchronous, so check that the standby's slot is ready before a planned promotion.

On older versions, plan failover explicitly: tooling that copies slot state, or a re-snapshot after every failover, with consumers built to handle it.

### Schema changes flow downstream

CDC events carry each table's shape, so schema changes reach every consumer. A column rename is a breaking change for every consumer, exactly as in 37.2c, and the connector registers the new shape without asking. Treat CDC-captured tables as having consumers: use expand-and-contract migrations (33.1a, 6.3), add columns as nullable, and don't rename in place.

### Delivery

Connectors are at-least-once. After a restart, they resume from the last position they recorded, which may be slightly behind the last event they sent. Consumers must be idempotent, and the LSN makes that straightforward: write a change only if its LSN is newer than the one already applied for that row (37.2a). Deletes must leave a marker with their LSN, so a delayed older update can't bring a deleted row back.

### What CDC is used for

- **Outbox relay** (37.2a): Debezium's outbox event router publishes outbox rows as proper events, without a polling relay.
- **Search indexes and caches** (Module 12, Module 13): every change, including deletes and script changes, reaches them without application code.
- **Warehouses and lakes** (16.4): complete, low-latency copies without heavy queries on the primary.
- **Live migrations:** copy a table to a new database or service with a snapshot, keep it current by streaming, then switch over (38.2b, Module 5).
- **History:** a record of every row change, without intent (2.4).

## When It's Appropriate

- **Downstream copies must be complete,** including deletes and changes made outside the application. Search showing deleted courses for months is the case.
- **Several systems need the same changes.** Four consumers from one connector, rather than four polling jobs.
- **Application code can't be changed,** or changes are made by many writers: scripts, other applications, the database console.
- **A live migration** needs a table kept in sync while both old and new systems run.
- **Polling load or latency** is a problem: 40-minute warehouse queries on the primary, or search a minute behind.

## When It's Unnecessary or Overkill

- **One consumer the application already writes to reliably,** through an outbox (37.2a), with no out-of-band writes.
- **Small tables that can be copied in full.** A table of 400 categories can be re-exported every few minutes.
- **Nobody to operate it.** A slot nobody monitors is a disk-full outage waiting for a long weekend. Without that ownership, polling with its known gaps can be the safer choice.
- **Cross-team integration.** Other teams should get curated integration events (37.2c), not your tables' change stream. Use CDC to feed an outbox, or transform raw changes into designed events first.
- **Analytics that tolerate daily, approximate data,** where a nightly export from a replica does the job.

## Trade-offs

- **The source database takes on risk.** Slots can fill the disk and hold back catalog cleanup. Every guard against that invalidates the slot and forces a re-snapshot.
- **Another system to run:** connectors, Kafka Connect or its equivalent, offsets, snapshots and upgrades, plus the monitoring above.
- **Your schema becomes a published interface.** Consumers depend on table shapes, and ordinary refactors become breaking changes.
- **Row changes, not meaning.** Consumers reconstruct business events from row diffs, with the problems 37.2c described.
- **Database-specific quirks:** replica identity, TOAST placeholders, transaction handling and failover support all differ between databases and versions.
- **`REPLICA IDENTITY FULL`** increases WAL volume for every update and delete on that table.
- **Snapshots of large tables** take hours and add load, and invalidated slots mean doing them again.

## Alternatives

- **The outbox** (37.2a): deliberate events written by the application, relayed by polling or by CDC on the outbox table alone. Intent included, schema decoupled.
- **Polling, done carefully:** a monotonic column maintained by a trigger, soft deletes instead of hard deletes, and reading only below the oldest open transaction (37.2a). It gets close, with query load.
- **Triggers into a change table,** read by a relay. Complete and simple, and it adds write cost to every transaction.
- **Native logical replication** between Postgres databases, for migrations or read copies where both ends are Postgres.
- **Managed CDC** (AWS DMS, Datastream, vendor connectors): someone else runs the connector. The source-side rules (slots, replica identity) still apply.
- **Periodic full exports** for small tables, or for consumers that only need daily data.

## How to Achieve It

1. **Prepare the source.** A publication for only the tables needed, replica identity decided per table, `max_slot_wal_keep_size` set (and `idle_replication_slot_timeout` on Postgres 18), and slot monitoring with alerts, before the first connector exists.
2. **One connector, one consumer.** Snapshot plus streaming for one table into one consumer, such as the search index, with LSN-versioned idempotent writes, deletes, tombstones and TOAST placeholders all handled. _Next when:_ it has survived a connector restart and a deliberate pause.
3. **Plan failover.** On Postgres 17+, failover slots with standby synchronization and readiness checks. On older versions, a written procedure with a re-snapshot. Rehearse it.
4. **Add consumers and heartbeats.** Heartbeats if captured tables are quiet, incremental snapshots for adding tables, and schema changes going through expand and contract.
5. **Curate for other teams.** Feed an outbox through CDC, or transform raw changes into integration events, rather than publishing table topics to other teams.

## Implementation

TypeScript for the consumer, plus the SQL and connector configuration the source needs. Most of what makes CDC safe is configuration and a few lines in the consumer; TypeScript keeps those lines readable.

### Preparing Postgres

```sql
-- Only the tables this pipeline needs, not FOR ALL TABLES.
CREATE PUBLICATION search_sync FOR TABLE courses, course_categories, cdc_heartbeat;

-- Consumers need old category_id to update counts, and old TOAST values.
ALTER TABLE courses REPLICA IDENTITY FULL;

-- A tiny table that heartbeats write to, so the slot advances when courses are quiet.
CREATE TABLE cdc_heartbeat (id int PRIMARY KEY, beat_at timestamptz NOT NULL);
```

```ini
# postgresql.conf, on the primary
wal_level = logical
max_slot_wal_keep_size = 200GB          # invalidate a slot before the disk fills
idle_replication_slot_timeout = 3d      # Postgres 18+: catch forgotten slots
synchronized_standby_slots = 'standby1_slot'   # Postgres 17+: consumers never ahead of the standby

# on the standby
sync_replication_slots = on
hot_standby_feedback = on
```

The 200 GB cap is a decision, not a default. It means a stopped connector is invalidated after roughly half a day of normal traffic, and costs a re-snapshot, instead of taking the primary down after three days. Choose the number from the disk's free space and the time it takes someone to respond to the alert.

### Watching the slots

```sql
SELECT slot_name,
       active,
       wal_status,                                                     -- 'lost' = invalidated
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS wal_retained,
       pg_size_pretty(safe_wal_size)                                   AS before_invalidation,
       now() - inactive_since                                          AS inactive_for,  -- 17+
       failover, synced
FROM pg_replication_slots
WHERE slot_type = 'logical';
```

Alert on `wal_retained` rising and `before_invalidation` falling, on any slot inactive for more than a few minutes, and on `wal_status` changing from `reserved`. Every one of this article's incidents except the placeholder would have shown up here first.

### The connector

```json
{
  "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
  "plugin.name": "pgoutput",
  "publication.name": "search_sync",
  "publication.autocreate.mode": "disabled",
  "slot.name": "search_sync",
  "slot.failover": "true",
  "snapshot.mode": "initial",
  "table.include.list": "public.courses,public.course_categories,public.cdc_heartbeat",
  "heartbeat.interval.ms": "10000",
  "heartbeat.action.query": "INSERT INTO cdc_heartbeat VALUES (1, now()) ON CONFLICT (id) DO UPDATE SET beat_at = now()",
  "tombstones.on.delete": "true",
  "topic.prefix": "learning"
}
```

`publication.autocreate.mode: disabled` means the connector uses the publication a person reviewed, instead of creating one for every table. `slot.failover` makes the slot survive promotion on Postgres 17+. The heartbeat query writes every 10 seconds, so the slot's position advances even when no course changes.

### An idempotent consumer

```ts
const UNAVAILABLE = "__debezium_unavailable_value";

type Change<T> = {
  op: "c" | "u" | "d" | "r";
  before: T | null;
  after: T | null;
  source: { lsn: number; table: string };
};

export async function onCourseChange(
  key: { id: number },
  change: Change<CourseRow> | null,
): Promise<void> {
  if (change === null) return; // tombstone: the delete event before it did the work

  const version = change.source.lsn; // increases per row in commit order

  if (change.op === "d") {
    // Leave a marker at this version, so an older update that arrives late can't resurrect it.
    await search.deleteAtVersion(key.id, version);
    return;
  }

  const fields = present(change.after!); // drop unchanged TOAST values
  await search.applyIfNewer(key.id, fields, version);

  if (change.op === "u" && change.before && change.before.category_id !== change.after!.category_id) {
    await categoryCounts.move(change.before.category_id, change.after!.category_id, key.id, version);
  }
}

// "__debezium_unavailable_value" means "didn't change", never "this is the new value".
function present<T extends object>(row: T): Partial<T> {
  return Object.fromEntries(
    Object.entries(row).filter(([, v]) => v !== UNAVAILABLE),
  ) as Partial<T>;
}
```

`applyIfNewer` applies a partial update only if the stored version is older than `version`. In Elasticsearch, that's an update script comparing a stored `cdc_lsn` field; for full documents, external versioning with the LSN as the version does the same check natively. Snapshot reads (`op: "r"`) go through the same path and carry the snapshot's position, so a streamed change that arrived first is never overwritten by the snapshot's older copy.

The category move needs `before.category_id`, which only exists because of `REPLICA IDENTITY FULL` on `courses`. Without it, `before` would hold only the primary key, and the count for the old category would never go down.

---

A database's log already knows every change ever made. CDC lets you read it, on one condition: the database keeps the log for you until you've read it, and it will keep that promise until its disk is full. Watch what you've asked it to keep.
