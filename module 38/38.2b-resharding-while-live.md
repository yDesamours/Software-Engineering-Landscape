# Resharding While Live: Copy, Catch Up, Fence, Switch

_Module 38.2b — Advanced Database Techniques_

## The Problem

Suppose you run the chat platform from 38.2a, with direct messages stored in application-sharded Postgres: 8 shards, 4,096 slots, and the slot-to-shard map from 38.2a's implementation. The shards are running out of room at 6 TB of messages and about 30,000 writes per second at peak. The plan is to go from 8 shards to 16, moving half of each shard's slots to a new one.

Module 5 moved single tenants: a few seconds of read-only for one tenant, a whole-database fence, and a flip. That doesn't fit here, and the team finds out how, one attempt at a time.

**A maintenance window that's too long.** The first plan copies each shard's outgoing slots during a read-only window. Copying 375 GB per shard pair takes about three hours. A chat product can't stop accepting messages for three hours, even at night, even for half its users.

**Dual writes that disagree.** The second plan writes new messages to both the old and new shard for slots being moved, while a background job copies history. Weeks later, a comparison finds about one message in 50,000 missing on the new side, lost to crashes between the two writes (37.2a's dual write), and some edited messages with different text on each side, because two edits arrived in different orders.

**Writes to a shard nobody reads.** For the first real move, the team switches the map for 256 slots and invalidates the cached maps. Some application instances keep their cached map for up to 30 seconds and write to the old shard. Module 5's fence, revoking write access to the source database, isn't possible: the source still owns the other 256 of its slots and has to keep accepting their writes. 1,400 messages land on the old shard after the switch and are never seen.

**Verification that passed.** Row counts matched on both sides. 312 edited messages still had old text on the new shard. Counting rows doesn't compare what's in them.

**No way back.** Two days after a move, the new shard's storage starts failing. The old shard still has the data, but it's two days stale, because nothing copied changes back to it after the switch. Rolling back would lose two days of messages in those slots.

Each problem has a well-known fix, and together they make up the standard shape of an online move.

## What It Is

**Online resharding** changes which database or node owns a set of keys while those keys keep being read and written, without a global read-only window. The standard sequence:

```
 1. COPY      snapshot the moving slots to the target, throttled
 2. CATCH UP  stream changes made since the snapshot (CDC, 38.4a); lag falls to seconds
 3. VERIFY    compare contents, not counts, while writes continue
 4. SWITCH    per batch of slots: fence the source, drain the stream, own on the target,
              publish the map. Reads first, then writes
 5. REVERSE   stream target → source for the moved slots, so rollback stays possible
 6. CLEAN UP  after the rollback window, delete moved rows from the source
```

The key difference from Module 5 is **per-slot fencing**: the source keeps serving its other slots, so ownership has to be checked per slot on every write. Each slot carries an **epoch**, a number that increases every time the slot changes owner, and a write is accepted only if it names the current owner and epoch. That's Martin Kleppmann's **fencing token** idea applied to shards: a writer with a stale map is refused, not trusted.

Variations covered below:

- **Same store, same schema:** splitting or moving shards, as here. Vitess's Reshard and MoveTables workflows are a production implementation of these six steps.
- **A different store or schema:** migrating messages to a new database or data model, with dual writes and shadow reads, as Stripe described.
- **Stores that move data themselves:** consensus-replicated databases change ownership through the consensus protocol, so there's nothing to fence in application code.

Neighbors: Module 5 is the single-tenant case with a brief read-only window. 38.2a is the map this changes. 38.4a is the stream step 2 uses. A move this long, with pauses and retries, is itself a workflow (37.4b).

## Recognizing the Problem

- A shard is approaching its storage or write capacity, and the only plan involves downtime.
- A migration plan relies on writing to two databases from the application.
- The migration's verification step is row counts, or "no errors reported."
- The switch depends on every application instance refreshing a cached map in time.
- The source database can't be made read-only because it still serves other keys.
- After a move, there's no way to switch back without losing writes.
- Moves are run by hand from a terminal and can't be paused or resumed.

## How It Works

### Move slots, not databases

The unit of movement sets the size of every pause. Fencing a whole database pauses everyone on it. Fencing a batch of 16 slots pauses about 0.4% of keys, for the second or two it takes to drain the stream. Moving 2,048 slots in batches of 16 is 128 short pauses, each affecting a small, different group of users, instead of one long one affecting everyone.

Put the slot number in every row as a column, indexed. It costs a few bytes per row, and every later step (filtering the stream, copying, verifying, cleaning up) becomes a query on `slot = ANY($1)` instead of recomputing hashes.

### Copy while it's written

1. **Start capturing first.** Create the CDC slot on the source before copying, so every change made during the copy is in the stream (38.4a).
2. **Copy in chunks** of rows ordered by primary key, throttled by the source's load and replication lag, so the copy doesn't become the incident.
3. **Apply the stream to the target,** filtered to the moving slots, with writes that apply a change only if its LSN is newer than what the row already has (38.4a). Copy and stream can then overlap safely: whichever arrives with the newer version wins, and the target converges on the source.

Once the copy finishes and the stream is applied, the target is seconds behind the source for the moving slots, and stays there.

### Verify contents while writes continue

Counts miss exactly what went wrong in the edited messages. Compare **contents** in chunks: a hash of each chunk's rows, ordered by key, computed on both sides.

Writes are still happening, so some chunks will differ simply because the target hasn't applied the latest changes. Two ways to handle that:

- **Compare at the same position.** Pause applying the stream at a known source position, compare, and resume. Vitess's VDiff does this with replication positions on both sides.
- **Re-check differences.** Compare everything, then re-check only the chunks that differed after the stream has caught up. Real divergence persists across re-checks; in-flight changes don't.

Add **business invariants** alongside hashes: message counts per channel, the latest message ID per conversation. They catch errors in a transformation that hashes of transformed rows can't.

### Switch per batch, with epochs

Each shard has a `slot_ownership` table: slot, epoch, and state (`owned`, `moving`, `gone`). Every write transaction takes a shared lock on its slot and checks that its slot is `owned` with the epoch the client expects. The switch for a batch:

```
source                          stream              target                 map
1. lock the batch's slots exclusively (waits for in-flight writes)
   set state = 'moving', epoch = E+1
   note the current log position P
   ── writes to these slots are now refused here ──
2.                              apply up to P ────►
3.                                                  set state = 'owned',
                                                    epoch = E+1
4.                                                                        publish: slots → target, E+1
   clients with stale maps: refused at source → refresh map → write to target
```

- **The exclusive lock in step 1** waits for writes already in progress on those slots to commit. After it, no write to those slots can commit on the source.
- **Step 2 is the pause.** Writes to the batch are refused and retried until the target has applied everything up to position P, typically well under a second when lag is healthy. If it takes too long, give the slots back to the source under the new epoch and try again later.
- **A stale client gets a refusal, never a success in the wrong place.** That's the 1,400 lost messages, prevented by the database instead of by cache invalidation.

**Switch reads before writes.** Before fencing, point reads for the batch at the target (it's seconds behind, which suits reads that tolerate replica-like staleness, 23.2a). Real read traffic exercises the target's indexes and capacity while the source is still authoritative, and an overloaded target is found before it matters. Vitess switches traffic in the same order, for the same reason.

### Keep a way back: reverse replication

Right after switching writes, start streaming changes for the moved slots from the target back to the source. For the rollback window, days rather than hours, the source stays current. Rolling back is the same switch in reverse: fence on the target, drain the reverse stream, own on the source, publish. The failing storage two days after the move becomes a planned switch back instead of lost data.

When the window ends, stop the reverse stream (and drop its replication slot, or it will hold WAL on the target, 38.4a), mark the slots `gone` on the source, and delete their rows in throttled chunks. Deleting 375 GB at once would create hours of vacuum work and replication lag.

### A different store or schema: dual writes and shadow reads

When the target is a different database, or the data model changes (for example, moving messages to 38.2a's `(channel, bucket)` layout in a wide-column store), streaming rows from source to target needs a translation, and some teams do it in the application instead. Stripe described a four-phase approach:

1. **Dual write,** with the old store authoritative.
2. **Backfill** history, then **read from both and compare** (shadow reads), serving the old store's answer. GitHub's Scientist library is built for this comparison.
3. **Switch reads** to the new store once mismatches are near zero and explained, still writing both.
4. **Switch writes** to the new store as authoritative, keep writing the old one for rollback, then stop.

Dual writes can diverge, as the second attempt found. The fixes are to write the second store through an outbox or CDC rather than directly (37.2a), and to run a reconciliation job that compares and repairs throughout. Shadow reads measure divergence continuously instead of discovering it weeks later.

### Stores that move data themselves

Consensus-replicated databases such as CockroachDB, Spanner, TiDB and YugabyteDB move a range by changing its replica set: a new replica joins as a non-voting learner, catches up from a snapshot and the log, is promoted, and an old replica is removed. Ownership (the leaseholder) changes through the consensus protocol, so there's no stale owner to fence. Citus rebalances shards between Postgres nodes using logical replication, and Vitess runs Reshard as a managed workflow. If your store already does this, use it: the steps above are what you'd be rebuilding.

Everything else that remembers where a key lives (caches, queued jobs, open connections, per-tenant sequences) needs the same attention as in Module 5.

## When It's Appropriate

- **Application-sharded databases** that must split or move while serving: the 8-to-16-shard split, with no acceptable downtime window.
- **Moving between stores or data models** with live traffic, such as Postgres to a wide-column store.
- **Moves that will happen repeatedly,** where building the machinery once pays for every future rebalance.
- **Data too large to copy during any window:** hundreds of gigabytes per move, and more each year.

## When It's Unnecessary or Overkill

- **A short read-only window is acceptable,** such as one tenant for a few seconds (Module 5), or an internal system at night.
- **The data is small** enough to dump and restore in minutes.
- **The store rebalances itself** (Vitess, Citus, CockroachDB and similar). Operate its workflow instead of writing one.
- **Growth without moving:** new tenants or users placed on new shards, while existing ones stay put (23.2b's directory). If old data ages out through time-based partitions, capacity can often be added without moving anything.
- **Cells** (23.6): add a cell for new customers instead of splitting existing ones.

## Trade-offs

- **Complexity.** Ownership tables, epoch checks, copy and stream tooling, verification, reverse streams, and an orchestrator to run them, all of which must be correct in failure cases.
- **Extra load during the move:** copy reads, CDC, WAL retention on the source, and write amplification on the target.
- **Double storage** for the rollback window, and throttled cleanup afterwards.
- **A check on every write.** A shared lock and an ownership lookup per write transaction is cheap, but not free, and it's permanent.
- **Short pauses per batch.** Writes to the batch are retried for a second or two, which clients must tolerate.
- **Long-running operations** that span days and need pausing, resuming, progress tracking and alerts, which is a workflow in its own right (37.4b).

## Alternatives

- **A maintenance window,** per tenant or per shard, when the business can tolerate it.
- **A database that moves data itself,** above.
- **Placing new data on new capacity** instead of moving old data.
- **Vertical scaling** (23.1a) to postpone the move, sometimes for years.
- **Rebuilding instead of moving,** for derived stores such as search indexes and caches, which are cheaper to rebuild on the new layout than to migrate (Module 5).

## How to Achieve It

1. **Prepare the write path** before any move: a slot column on every row, a `slot_ownership` table per shard, and ownership and epoch checks on every write. Deploy it while every slot is simply `owned` with epoch 1, so it's proven before it matters.
2. **Build copy and catch-up:** CDC started first, chunked throttled copy, LSN-guarded apply on the target. Rehearse with one slot in staging, then one quiet slot in production. _Next when:_ lag stays in seconds under peak load.
3. **Build verification:** chunk hashes and business invariants, with re-checks. Run it continuously during catch-up. _Next when:_ it reports zero persistent differences.
4. **Switch in small batches,** reads first, then writes, with a maximum pause after which the batch is given back. Start the reverse stream immediately after each write switch.
5. **Keep the rollback window,** then clean up in throttled chunks, and drop reverse replication slots.
6. **Orchestrate it** as a workflow (37.4b) that can pause, resume, stop on errors, and report progress per slot.

## Implementation

Go, with pgx, continuing 38.2a's slot map. Three pieces carry the correctness: the guarded write, the per-batch fence and switch, and the content comparison.

### Every write checks ownership

```go
var ErrNotOwner = errors.New("slot not owned here at this epoch") // client refreshes its map and retries

func (s *Shard) WriteGuarded(ctx context.Context, slot int, epoch int64,
	write func(pgx.Tx) error) error {

	return pgx.BeginFunc(ctx, s.db, func(tx pgx.Tx) error {
		// Shared: writers don't block each other. A fence takes the same lock
		// exclusively, so it waits for writes in progress, and later writes wait for it.
		if _, err := tx.Exec(ctx, `SELECT pg_advisory_xact_lock_shared($1)`, slotLock(slot)); err != nil {
			return err
		}
		var ok bool
		err := tx.QueryRow(ctx, `
			SELECT state = 'owned' AND epoch = $2 FROM slot_ownership WHERE slot = $1`,
			slot, epoch).Scan(&ok)
		if err != nil {
			return err
		}
		if !ok {
			return ErrNotOwner
		}
		return write(tx)
	})
}
```

Transaction-scoped advisory locks live in memory, so thousands of writers taking the shared lock cost almost nothing, and they're released at commit, which keeps them safe behind a transaction-mode pooler (23.2a). A row lock (`FOR SHARE`) on `slot_ownership` would do the same job but writes lock information to the row, which becomes contention at 30,000 writes per second.

The epoch comes from the client's map. A client with a stale map but the correct owner still has the correct epoch; a client with a stale map pointing at the old owner has an old epoch and is refused.

### Fencing and switching one batch

```go
func (m *Mover) SwitchBatch(ctx context.Context, slots []int, src, dst *Shard) error {
	epoch := m.catalog.NextEpoch()

	// 1. Fence on the source. Returns only when no write to these slots can commit there.
	fenceLSN, err := src.Fence(ctx, slots, epoch)
	if err != nil {
		return err
	}

	// 2. Drain: the target must have applied everything the source committed before the fence.
	if err := m.stream.WaitApplied(ctx, dst, fenceLSN, 5*time.Second); err != nil {
		return src.Reown(ctx, slots, epoch) // give the batch back under the new epoch; retry later
	}

	// 3. Own on the target, then tell everyone.
	if err := dst.Own(ctx, slots, epoch); err != nil {
		return err
	}
	if err := m.catalog.Publish(ctx, slots, dst.ID, epoch); err != nil {
		return err
	}
	return m.reverse.Start(ctx, dst, src, slots) // keep the source current for rollback
}

func (s *Shard) Fence(ctx context.Context, slots []int, epoch int64) (lsn string, err error) {
	slices.Sort(slots) // same lock order everywhere, so two fences can't deadlock
	err = pgx.BeginFunc(ctx, s.db, func(tx pgx.Tx) error {
		for _, sl := range slots {
			if _, err := tx.Exec(ctx, `SELECT pg_advisory_xact_lock($1)`, slotLock(sl)); err != nil {
				return err
			}
		}
		_, err := tx.Exec(ctx, `
			UPDATE slot_ownership SET state = 'moving', epoch = $2 WHERE slot = ANY($1)`,
			slots, epoch)
		return err
	})
	if err != nil {
		return "", err
	}
	// Taken after the fence committed: every accepted write to these slots is before this position.
	err = s.db.QueryRow(ctx, `SELECT pg_current_wal_lsn()::text`).Scan(&lsn)
	return lsn, err
}
```

The order of steps is the design. Fence before draining, so the drain has a fixed end. Drain before owning on the target, so the target never accepts a write while missing an earlier one. Own before publishing, so a client that sees the new map finds the target ready. Publishing last means the only thing a stale client can meet is a refusal.

If the drain takes longer than 5 seconds, the batch returns to the source under the new epoch. Clients refresh their maps once and carry on, and the pause for that batch was 5 seconds at most.

`Reown` and the reverse stream are the rollback path, in small form. A move you can't undo is a move you'll hesitate to start.

### Comparing contents, not counts

```sql
-- Run on source and target for the moving slots; compare row by row in the mover.
SELECT slot,
       id / 50000                                             AS chunk,
       count(*)                                               AS rows,
       md5(string_agg(id::text || ':' || md5(m::text), ',' ORDER BY id)) AS digest
FROM messages m
WHERE slot = ANY($1)
GROUP BY slot, chunk;
```

`md5(m::text)` hashes each row's full contents, so an edited message with old text changes its chunk's digest even though the count is the same, which is the 312 messages row counts missed. The mover compares digests, waits for the stream to catch up, and re-checks only the chunks that differed. Chunks still different after a few re-checks are real divergence, and the batch doesn't switch until they're explained.

Hashing text representations assumes both sides render rows identically: the same column order, types and collations. Moves between different schemas or stores need a normalized form defined by the mover instead.

Moving live data safely comes down to one rule: at every moment, exactly one place may accept writes for a key, and every other place must refuse them. Build the refusal first; everything else in the move is copying.
