# The Life of a Pooled Connection: Hold Time, Leaks, Pool Deadlocks and Dead Sockets

_Module 38.3a — Advanced Database Techniques_

## The Problem

Suppose you run the ordering API for a food-delivery platform: TypeScript on Node, 12 instances, each with a `pg` pool of 20 connections, in front of one Postgres primary. 23.2a's connection budget holds: 240 client connections, an external pooler, and a database that isn't struggling. Over two months, four incidents show that sizing the pool was only half the job.

**Friday, 19:40: everything times out, and the database is idle.** The payment provider's latency rises from 300 ms to about 4 seconds. Checkout calls the provider *inside* its database transaction:

```
BEGIN                                   ─┐
SELECT … FROM orders WHERE id=$1 FOR UPDATE   ≈ 3 ms
await payments.charge(…)                 ≈ 4,000 ms   ← connection held, row locked
UPDATE orders SET status='paid' …             ≈ 2 ms
COMMIT                                  ─┘   hold time ≈ 4.2 s for 5 ms of database work
```

Each instance handles about 6 checkouts a second. Six a second, each holding a connection for 4.2 seconds, needs 25 connections, and the pool has 20. The pool's wait queue grows. Browsing menus, which needs a connection for 2 ms, now waits behind checkouts too. `connectionTimeoutMillis` is at its default of 0, meaning wait forever, so requests hang until the load balancer gives up at 60 seconds. Database CPU is at 15% throughout.

**Tuesday, lunch rush: a stall with no locks and no load.** A new audit helper writes to `audit_log` using `pool.query`, which borrows its *own* connection, from inside a transaction that already holds one. Each checkout now needs two connections at the same time. During a burst, 20 checkouts on one instance each hold one connection and wait for a second. None can finish, so none releases anything. Postgres shows 20 sessions `idle in transaction` and no lock waits, because the wait is inside the application, where the database can't see it.

**Every few days: one instance slowly dies.** A handler borrows a client, looks up an order, and throws `NotFound` before reaching `client.release()`. Each 404 leaks one connection. A crawler probing old order IDs empties an instance's pool within 20 requests. Restarting fixes it, and the restart gets recorded as the fix.

**Monday, 07:05: the first orders of the day hang for 15 minutes.** To avoid reconnect costs, someone set `idleTimeoutMillis: 0` so idle connections are never closed. Overnight, the NAT gateway between the app and the database dropped every connection that had been idle for 350 seconds, without telling either side. At 07:05, the first query on each connection is written into a socket that no longer leads anywhere. Linux retransmits for about 15 minutes before declaring the connection dead.

None of these is a sizing problem. A bigger pool would have delayed the first incident, hidden the third for longer, made the second rarer but no less deadly, and done nothing about the fourth.

## What It Is

A pooled connection has a **lifecycle**: it's created, set up, lent out and returned many times, and eventually retired. Three parties each control part of that life:

```
           the application decides           the pool decides            the network and server decide
           ────────────────────────          ────────────────            ─────────────────────────────
create ─▶ setup ─▶ idle ⇄ borrowed ─▶ … ─▶ retired (lifetime, idle timeout, error)
                          │
                          └─ how long it's held, what's left on it, whether it comes back
```

- **The application** decides the **hold time** (how long a connection is borrowed), what state is left on it, and whether it's returned at all.
- **The pool** decides how long borrowers wait when all connections are in use, and when connections are retired.
- **The network and the server** decide when a connection is dead, often without telling anyone.

Most pool incidents come from the first column. Most pool tuning happens in the second.

This article sits between two others. **23.2a** sized the pool and budgeted connections across a fleet, including the external pooler and its modes. **24.2a** covered getting connections to follow a failover: host lists, DNS caching and maximum lifetime for that purpose. This article is about everything that happens to a connection between being borrowed and being returned, and about the ways it dies in between.

## Recognizing the Problem

- Requests time out waiting for a connection while database CPU is low. `pool.waitingCount` (or your pool's equivalent) is above zero.
- Endpoints that barely use the database slow down whenever one external dependency slows down.
- `pg_stat_activity` shows many sessions `idle in transaction`, with `xact_start` seconds or minutes old.
- An instance degrades gradually and a restart fixes it.
- The pool stalls under bursts but not under steady load, and the database shows no lock waits.
- The first requests after a quiet period hang for minutes, or fail with `ETIMEDOUT` or `ECONNRESET`.
- A database restart or failover crashed application processes rather than failing some requests.
- The database's connection count spikes after deploys or restarts, and authentication or TLS CPU spikes with it.
- A setting from one request shows up in another request's query: a `search_path`, a role, a tenant ID.

## How It Works

### Demand is rate times hold time

The number of connections in use equals the rate at which requests borrow them multiplied by how long each holds one. This is Little's law, and it applies to every pool:

```
connections in use  =  borrows per second  ×  hold time
checkout, normal:           6/s            ×   0.3 s   ≈  2
checkout, provider slow:    6/s            ×   4.2 s   ≈ 25   > pool of 20
```

Hold time counts every millisecond between borrowing and returning, not just time spent in queries. It includes calls to other services, `await`ing unrelated promises, serializing responses, CPU work in your own code, and waiting for a second connection. In the Friday incident, the database needed 5 ms, but the pool saw 4.2 seconds.

This gives the most important rule in this article: **acquire late, release early, and never hold a connection while waiting on something else.** It applies twice as strongly inside a transaction, because a transaction also holds row locks and keeps vacuum from cleaning up. If a step needs an external call between two database steps, split it into two transactions with the call in between, and make the second transaction check that nothing changed. The Implementation section shows this for checkout. Splitting gives up atomicity, which then has to come back as idempotency and a reconciler (37.2a, 17.1). That's usually a better trade than a pool that depends on a partner's latency.

### The wait queue is a queue

When every connection is in use, borrowers wait. Without a limit on waiting, which is the `pg` default, the wait queue has no bound. Requests pile up in memory and eventually fail somewhere else, such as at the load balancer or the client, after using resources the whole time.

Set an **acquisition timeout** well below the request's own deadline, for example 1 second for an API with a 5-second budget, and turn that timeout into a fast 503. The pool then becomes a point of backpressure (Module 18, 36.3) instead of a place where requests wait to die.

If one kind of work can still starve another, split the pool. Give checkout its own small pool and browsing its own, so a slow payment provider can use up only checkout's connections. These are **bulkheads**. Each one takes part of the connection budget, so they belong in the 23.2a arithmetic, and each costs you the ability to lend idle capacity between workloads.

### One unit of work, one connection

The Tuesday incident is a **pool deadlock**. If each unit of work needs two connections at the same moment, and every connection is held by a unit waiting for its second, none of them can proceed:

```
request 1: holds c1 ──waits for──▶ any free connection
request 2: holds c2 ──waits for──▶ any free connection
   …
request 20: holds c20 ─waits for─▶ any free connection        pool: 20/20 borrowed, 0 free
```

It's worse when the second connection needs a row the first has locked, for example an audit insert with a foreign key to a row the transaction is updating. The database sees one session waiting on a lock held by another session that is idle, not waiting. Postgres's deadlock detector only sees waits between sessions, so it finds nothing. The cycle runs through your application's pool, where the database can't see it.

HikariCP's pool-sizing notes give the minimum pool size that avoids this when every task needs C connections at once and T tasks run concurrently: T × (C − 1) + 1. It's worth knowing mainly as an argument for keeping C at 1. The usual causes of two connections per unit of work:

- helpers that call `pool.query` inside a transaction
- ORM features that open their own connection (lazy loading outside the session, "requires new" transaction propagation)
- background tasks started from a request that inherit nothing from it

The fix is structural. The transaction's client is passed along, explicitly or through async context, and any attempt to borrow a second connection while holding one fails loudly in development.

### Every borrow needs a guaranteed return

A **leak** is a borrowed connection that never comes back. Leaks almost always happen on the error path: an exception thrown between borrowing and returning. The fix is also structural. Application code never calls `connect()` and `release()` itself. A single helper owns the lifecycle, returns the connection in a `finally` block, and is the only place that can borrow.

Returning a connection correctly has two parts:

- **After an error inside a transaction, roll back before returning.** Otherwise the next borrower inherits an aborted transaction.
- **If the rollback fails, or a query timed out partway through, destroy the connection** rather than returning it (`release(true)` in `pg`). A connection in an unknown state costs one reconnect to replace, and a lot more if it's reused.

For detection, record the stack trace at borrow time and log it if the connection hasn't come back after a threshold (HikariCP's `leakDetectionThreshold` does exactly this). A leak then shows up as a line number instead of a restart.

### What's left on a connection travels with it

Anything a request changes on a session is still there for the next borrower:

- settings such as `search_path`, role, `timezone`, and a tenant ID stored in a session variable
- session-level advisory locks
- temporary tables and prepared statements
- an open transaction

The rules:

- **Scope settings to the transaction.** `SET LOCAL` and `set_config(…, true)` end at commit or rollback (23.2b).
- **Put setup that's the same for every borrower in the connection-creation hook** (`onConnect` in `pg`).
- **If code must change session state, reset it on return.** `RESET ALL` covers settings, `DISCARD ALL` covers everything but is heavier, and a transaction-mode external pooler forces you to get this right (23.2a).

### Connections die without saying so

A connection can be dead long before anything reports it. The three usual causes:

- **The server goes away.** A restart or failover closes every connection. Idle ones report this as an error event on the pool. In Node, an `error` event with no listener crashes the process, so a 20-second failover can take down every instance. Always attach a listener.
- **Something in the network forgets the connection.** NAT gateways, load balancers and firewalls drop idle TCP connections after a timeout (350 seconds on several AWS network services) and tell neither side. The next write goes into a void, and the kernel retransmits for its full timeout (about 15 minutes with Linux defaults) before reporting an error. That was the Monday incident.
- **The server ends the session on purpose.** Postgres can close connections that have been idle (`idle_session_timeout`, 14+) or idle inside a transaction (`idle_in_transaction_session_timeout`). The pool finds out on the next use.

The defenses, cheapest first:

- **An idle timeout shorter than the shortest one in the network path.** The pool closes idle connections before anything else forgets them. `pg`'s default of 10 seconds is fine; turning it off is not.
- **TCP keepalive** with a first probe well inside that network timeout, for connections that must stay open.
- **Query and statement timeouts**, so a query on a dead socket fails in seconds rather than after the kernel's retransmission timeout.
- **Validation when a connection is borrowed**, a cheap check before handing it out. Some pools do this automatically. It costs a round trip per borrow, so use it where the other defenses can't reach.
- **A maximum lifetime with jitter.** Rotating connections periodically lets DNS and failover changes take effect (24.2a) and releases per-connection server memory. Jitter keeps a fleet's connections from all expiring at the same moment.

### Reconnect storms

After a database restart, every instance reconnects at once: 12 instances × 20 connections, each needing a new server process, a TLS handshake and SCRAM authentication. That's 240 expensive connection setups in the same second, against a database that's just starting and has an empty cache. Setting pools to keep their maximum size open at all times ("minimum idle equals maximum") guarantees the storm.

Let pools grow on demand. Retry failed connection attempts with jittered backoff. Watch connection rate, not just connection count, after every deploy and restart.

### The server protects itself

The database can enforce limits the application forgot:

- `statement_timeout` ends queries that run too long.
- `idle_in_transaction_session_timeout` ends sessions that left a transaction open. It's the server-side backstop for both the Friday and Tuesday incidents.

Set both **per role**: short for the web application's role, long or off for the reporting job's role. That way the backstop doesn't kill legitimate long-running work.

## When It's Appropriate

This isn't a pattern to adopt. Every application with a pool already has these behaviors, and the question is which ones deserve attention. Four situations make them urgent:

- **Request handlers call other services.** If any request calls a payment provider, email service or internal API while holding a connection, hold-time discipline is the first thing to fix, before any pool setting.
- **Traffic is idle between bursts, behind NAT or a load balancer.** Overnight lulls, batch windows or low-traffic tenants mean the dead-socket defenses matter. Measure the idle timeouts on your actual network path.
- **ORMs with lazy loading or nested transaction propagation, or helpers that borrow independently.** Any of these makes pool deadlock possible. Check that one unit of work uses one connection.
- **Traffic is bursty.** Lunch rushes, flash sales and 09:00 logins are when leaks, deadlocks and acquisition timeouts show up. Steady load hides them.

## When It's Unnecessary or Overkill

- **Tuning pool settings before measuring hold time.** Most pool incidents are hold-time incidents, and settings can't fix them.
- **Raising the pool maximum to fix exhaustion.** It moves the limit to the database (23.2a) and delays the next incident without explaining it.
- **A separate pool per endpoint in a small application.** Bulkheads earn their cost when one workload has shown it can starve another. Before that, they only divide capacity.
- **Validating every borrow when idle timeout and keepalive already cover your network path.** It adds a round trip to every request to guard against something already handled.
- **Long-lived pools in short-lived serverless functions.** That environment has different rules: an external pooler or an HTTP-based driver (Module 41).

## Trade-offs

- **Acquisition timeouts turn slowness into errors.** That's their purpose, but it means dashboards show errors where they used to show latency, and callers need retry and backoff that doesn't make things worse (10.2).
- **Splitting transactions around external calls gives up atomicity.** Consistency then depends on idempotency keys, compare-and-set updates and a reconciler for work left half-done.
- **Bulkheads divide capacity.** Idle connections in one pool can't help another, and each pool adds to the fleet's connection budget.
- **Short idle timeouts and lifetimes mean more reconnecting.** Each new connection costs a server process, a TLS handshake and authentication. Too short, and the churn becomes its own load.
- **Validation and keepalive add traffic.** A round trip per borrow, and periodic probes on every connection.
- **Server-side timeouts are blunt.** Set per role, they're safe. Set globally, they kill the monthly report.
- **Enforcing one connection per unit of work constrains code structure.** The transaction client has to be passed along everywhere, which some teams find awkward and some ORMs resist.

## Alternatives

- **An external pooler** (23.2a) multiplexes many client connections onto few server connections. It doesn't reduce hold time: in transaction mode, a transaction held open across a 4-second call still occupies a server connection for 4 seconds. It hides a hold-time problem behind a larger pool.
- **HTTP or serverless database drivers** avoid long-lived connections entirely, at the cost of per-query overhead and fewer session features (Module 41).
- **Queues instead of synchronous work.** Moving the external call out of the request, into a job that runs after commit (Module 10, 37.2a), removes the hold-time problem instead of managing it.
- **Optimistic concurrency instead of `SELECT … FOR UPDATE`.** Reading without locking and writing with a version check shortens both lock time and hold time, and suits flows with a slow step in the middle (6.5).

## How to Achieve It

**1. Instrument the pool.** Record, per pool: the number of waiting borrowers, time to acquire a connection, a histogram of hold time, and the borrower's stack for any hold over a threshold.
_Move on when_ you can name the three endpoints with the longest hold times.

**2. Add limits on both sides.** Set an acquisition timeout that fails fast, and per-role `statement_timeout` and `idle_in_transaction_session_timeout` on the database. Attach a pool `error` listener.
_Move on when_ a slow dependency in staging produces fast 503s instead of hung requests.

**3. Make leaks impossible.** Route every borrow through one lifecycle helper, and ban direct `connect()` calls with a lint rule.

**4. Fix the worst hold times.** Move external calls out of transactions. Split transactions around slow steps, with idempotency and compare-and-set updates.
_Move on when_ p99 hold time is close to p99 query time.

**5. Enforce one connection per unit of work.** Pass the transaction client along, and fail in development if a second connection is borrowed while one is held.

**6. Match lifecycle settings to your network.** Find the shortest idle timeout on the path between app and database. Set the pool's idle timeout and TCP keepalive inside it, and set a jittered maximum lifetime.

**7. Add bulkheads if one workload still starves another** after step 4.

**8. Restart the database under load in staging.** Watch for process crashes, the reconnect storm, and how long it takes to recover.

## Implementation

The implementation is TypeScript with `node-postgres`. Node makes the hold-time problem easy to write by accident: `await` inside a transaction looks the same whether it's waiting on the database or on another service. Its single-process, async-context model also makes it easy to catch a second borrow at runtime.

### A pool configured on purpose

```ts
import { Pool } from "pg";

export const pool = new Pool({
  max: 20,                          // per instance; budgeted fleet-wide in 23.2a
  connectionTimeoutMillis: 1_000,   // default is 0 (wait forever); fail fast, return 503
  idleTimeoutMillis: 30_000,        // well inside the NAT's 350 s: we close idle connections first
  maxLifetimeSeconds: 900,          // rotate every 15 min (24.2a); keep it below any server-side lifetime limit
  keepAlive: true,                  // TCP keepalive for connections that stay busy but quiet
  keepAliveInitialDelayMillis: 60_000,
  statement_timeout: 5_000,         // a query on a dead socket fails in seconds, not 15 minutes
  idle_in_transaction_session_timeout: 10_000, // the database's backstop for held transactions
  application_name: `ordering-api:${process.env.HOSTNAME}`, // readable in pg_stat_activity
});

// Idle connections report server restarts here. Without a listener, Node treats
// the error as unhandled and the process exits: a 20-second failover becomes a fleet restart.
pool.on("error", (err) => log.warn({ err }, "idle connection lost; pool will replace it"));
```

### The only way to borrow

```ts
import { AsyncLocalStorage } from "node:async_hooks";
import type { PoolClient } from "pg";

const holding = new AsyncLocalStorage<{ since: number; stack?: string }>();
const HOLD_WARN_MS = 500;

export async function withTransaction<T>(work: (tx: PoolClient) => Promise<T>): Promise<T> {
  // One unit of work, one connection: a second borrow while holding one is the Tuesday deadlock.
  if (holding.getStore()) throw new Error("nested connection borrow; pass the transaction client instead");

  const client = await pool.connect();          // throws after connectionTimeoutMillis
  const held = { since: Date.now(), stack: new Error().stack };
  let destroy = false;
  try {
    return await holding.run(held, async () => {
      await client.query("BEGIN");
      const result = await work(client);
      await client.query("COMMIT");
      return result;
    });
  } catch (err) {
    // Roll back before returning; if that fails, the connection's state is unknown.
    await client.query("ROLLBACK").catch(() => { destroy = true; });
    throw err;
  } finally {
    const heldFor = Date.now() - held.since;
    if (heldFor > HOLD_WARN_MS) log.warn({ heldFor, stack: held.stack }, "long connection hold");
    client.release(destroy);                    // runs on every path, including NotFound
  }
}
```

> **What this doesn't catch.** The nested-borrow check works only if `pool.query` and `pool.connect` are called nowhere else, which is what the lint rule in step 3 enforces. A plain `pool.query` for a single statement outside any transaction is fine. To keep it without reopening the hole, expose it only through the helper's module, forbid it elsewhere, and have helpers such as the audit writer take a `tx` parameter.

> **The stack is captured at borrow time on purpose.** A leak is found where the connection was taken, not where it was lost. This one line replaces "restart fixes it" with a file and a line number. Capturing a stack on every borrow has a small cost; if profiling shows it matters, sample it.

### Checkout without holding a connection across the payment call

```ts
export async function checkout(orderId: string, idemKey: string) {
  // 1. Short transaction: claim the order and record intent. No external calls.
  const order = await withTransaction(async (tx) => {
    const { rows } = await tx.query(
      `UPDATE orders SET status = 'paying', payment_key = $2, version = version + 1
        WHERE id = $1 AND status = 'pending'
        RETURNING id, amount_cents, version`,
      [orderId, idemKey]);
    if (rows.length === 0) throw new Conflict("order is not payable");
    return rows[0];
  });

  // 2. The slow part, with no connection held. The idempotency key makes a retry
  //    after a crash or timeout charge at most once.
  const charge = await payments.charge({ amount: order.amount_cents, idempotencyKey: idemKey });

  // 3. Short transaction: record the result, only if nobody changed the order meanwhile.
  await withTransaction(async (tx) => {
    const { rowCount } = await tx.query(
      `UPDATE orders SET status = 'paid', charge_id = $3, version = version + 1
        WHERE id = $1 AND version = $2 AND status = 'paying'`,
      [orderId, order.version, charge.id]);
    if (rowCount === 0) await flagForReconciliation(tx, orderId, charge.id); // e.g. cancelled mid-payment
  });
}
```

> **What the split costs.** Hold time drops from 4.2 seconds to two transactions of a few milliseconds each, and a slow provider now uses up request time instead of connections. The price is a new state: if the process dies after the charge succeeds but before step 3 commits, the order stays in `paying` with money taken. A reconciler that sweeps old `paying` orders, looks up the charge by idempotency key and finishes or refunds the order is now part of the design. It isn't optional.

---

The habit to take from this: when a pool runs out, look at how long connections are held before touching any pool setting. A connection held across something that isn't the database is the most common cause, and a larger pool only hides it.
