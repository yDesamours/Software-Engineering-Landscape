# Partitioning Schemes: Placing Keys, Moving Partitions, and Hot Spots

_Module 38.2a — Advanced Database Techniques_

## The Problem

Suppose you run a chat platform: communities with channels, direct messages, about 20 million monthly users, and 4 billion messages. Messages live in a distributed database partitioned across 24 nodes, and several other stores (sessions, presence, a cache of recent messages) are partitioned across their own clusters. 23.2b settled the key question for tenant data; this platform's keys are channels and users. Over a year, four things go wrong, each in the part of partitioning that sits below the key: how keys are placed, and how placement changes.

**Adding a cache node empties the cache.** The recent-messages cache places each channel on node `hash(channel) % 8`. Traffic grows, and operations adds a ninth node. With `% 9`, almost every channel maps to a different node: 89% of keys move. For twenty minutes the cache is effectively cold, every read falls through to the database, and the database, sized for a warm cache, falls over.

**One node takes every write.** An early version of message storage partitions by message ID in sorted ranges, so a channel's history can be read with one range scan. Message IDs are time-ordered, so every new message has the largest ID yet, and all writes go to whichever node holds the last range. One node runs at 95% CPU while 23 sit mostly idle.

**One channel melts one node.** Messages are then partitioned by channel ID, which spreads writes well. Then a streamer's community channel reaches 800,000 members. Its partition takes about 40% of all message reads during streams, and its node is saturated while the others are fine. The partition also keeps growing, past 200 GB, because a channel's history has no end, and compaction and repair on that node take hours.

**A question that asks every node.** Trust and safety needs "every message by this user in the last 30 days" for abuse reports, and privacy requests need it too. Messages are partitioned by channel, so the query goes to all 24 nodes and waits for the slowest. Its p99 latency is 4 seconds, and running it during peak hours makes everyone else's reads slower.

Even hashing, a good key and enough nodes are all necessary, and none of them decides where keys go when the cluster changes, or what happens when one key outweighs a node.

## What It Is

A **partitioning scheme** is really two maps:

```
key ──(1)──► partition ──(2)──► node
     stable                changes as nodes join, leave and fill up
```

1. **Key to partition:** a function of the key alone, such as a hash, or which sorted range it falls into. It should change rarely, if ever.
2. **Partition to node:** an assignment that changes whenever capacity changes. Moving a partition to another node is **rebalancing.**

Keeping the two maps separate is the most important design decision in this article. `hash(key) % nodes` merges them, which is why adding one node moved 89% of the cache. Every scheme below is a way of keeping map 1 stable while map 2 changes.

Around that core, this article covers the problems placement creates: **hot spots** (one partition doing far more than its share), **unbounded partitions** (one key's data growing forever), and **secondary indexes** (finding data by something other than the partition key).

23.2b covered choosing the key, directory-based routing and cross-shard queries for tenant data. 38.2b covers actually moving data while it's being written.

## Recognizing the Problem

- Placement is `hash(key) % number_of_nodes` anywhere, including in caches.
- Adding or removing a node causes a burst of misses, moves or errors out of proportion to its size.
- One node is much busier than the others, and it's the one holding the newest data.
- A single key (a channel, a celebrity, a big customer) drives a large share of the traffic.
- Some partitions grow without limit because their key's data never ends.
- Queries that don't include the partition key are slow, and get slower as nodes are added.
- Rebalancing happens automatically when a node restarts, and restarts cause load spikes.

## How It Works

### Map 1: range or hash

**Range partitioning** keeps keys sorted and gives each partition a contiguous range: A–F, G–M. Range scans on the key are efficient, because neighbors are stored together. Partitions split when they grow, which Bigtable, HBase, CockroachDB, Spanner and MongoDB all do automatically. Its weakness is **monotonic keys**: timestamps, auto-increment IDs, and time-ordered IDs such as UUIDv7 or Snowflake IDs all send every new write to the last range. That was the second incident.

**Hash partitioning** places each key by a hash of it, which spreads keys evenly, including monotonic ones, and gives up range scans on the key: neighbors are scattered.

Most real systems combine them with a **compound key**: hash the first part to pick the partition, and keep rows sorted by the second part within it. Cassandra calls these the partition key and clustering columns; DynamoDB calls them the partition key and sort key. `(channel_id, message_id)` puts each channel on one partition, spread by hash, with its messages sorted by time inside it, so "the latest 50 messages in this channel" is one sequential read on one node.

For monotonic keys in range-partitioned databases, the fix is a hashed prefix: a small bucket number derived from the key and placed in front of it, spreading writes across that many ranges. CockroachDB builds this in as hash-sharded indexes. The cost is that a scan across the whole key range now reads every bucket.

### Map 2: assigning partitions to nodes

| Scheme | Keys moved when one node is added | State to keep | Notes |
|---|---|---|---|
| **`hash % N`** | about N/(N+1): 89% going from 8 to 9 | none | Only for clusters that never change size |
| **Many fixed partitions** (e.g. 4,096 slots) | about 1/(N+1), moved as whole slots | slot → node table | Redis Cluster uses 16,384 hash slots. Choose a count far above the maximum node count, because it can't easily change |
| **Consistent hashing** (a ring, with virtual nodes) | about 1/(N+1) | node positions on the ring | Dynamo and Cassandra. Virtual nodes, meaning many ring positions per node, even out the shares |
| **Rendezvous hashing** | about 1/(N+1) | the list of nodes | Each key goes to the node with the highest `hash(key, node)`. No ring, and weights are easy |
| **Jump consistent hash** | about 1/(N+1) | none, only a node count | Very fast and even, but buckets must be numbered 0..N−1, so only the last node can be removed |
| **Dynamic ranges** | only the range being split | range → node table | Partitions split and merge by size or load. Bigtable, CockroachDB, Spanner |
| **Directory** (23.2b) | whatever you choose to move | key → partition table | Most control, most state. Good for tenants of very different sizes |

Two patterns cover most systems. Hash into a large fixed number of partitions and keep a small table from partitions to nodes; or use dynamic ranges and let the database split and move them. Both keep map 1 stable. Consistent hashing and its relatives suit caches and stateless routing, where no table is wanted (23.1b used the same idea for load balancing).

With fixed partitions, choose the count once, for the largest cluster you can imagine. Each partition is the smallest unit you can move or give its own node. 4,096 partitions on 24 nodes is about 170 each, and still dozens each on 100 nodes. 64 partitions would cap you at 64 useful nodes, and make each move large.

### Geographic partitioning

Partitioning by region puts each user's or tenant's data near them for latency, and keeps it in a jurisdiction for residency (34.1b). The region becomes part of the key, a directory records each entity's home region, and anything global (usernames, cross-region communities) needs either a global table replicated everywhere or a clear home region with remote reads. Moving an entity between regions is a live migration (38.2b), not an update to one field.

### Hot keys and partitions that never stop growing

Even hashing spreads keys, not load. One key that's hotter than a whole node's capacity can't be fixed by any placement scheme, because a key lives on one partition. The options, roughly from simplest:

- **Absorb reads before they reach the partition.** Cache the hot key, and coalesce concurrent identical reads into one database request. During a stream, thousands of clients asking for the same channel's latest messages become one query every few hundred milliseconds. For read-heavy hot keys, this is usually enough.
- **Split the key by time.** Partition messages by `(channel_id, bucket)`, where the bucket is a fixed time window such as 10 days. Writes for a busy channel still go to one partition at a time, but that partition's size is bounded, and older history spreads across the cluster. Discord described doing this for messages. It also solves the unbounded partition: no single partition holds a channel's entire history.
- **Salt write-hot keys.** Spread writes for one key across `key#0` to `key#7`, and have reads gather from all eight. It fits counters and append-only feeds, where readers can combine the pieces.
- **Isolate known giants.** Give the largest keys their own partitions or nodes through a directory override, as 23.2b did for its largest tenant.
- **Limit it.** Rate limits on a hot key protect everyone else, at the cost of that key's users (Module 18).

Watch for skew by measuring load per partition and per key, not only per node. A node at 60% can be carrying one partition at 100% of what a single partition can handle.

### Secondary indexes across partitions

When data is partitioned by channel, "messages by this user" is a secondary-index question, and there are two ways to partition the index:

- **Local indexes:** each partition indexes only its own data. Writes stay on one partition, but queries by user must ask every partition and wait for all of them (**scatter-gather**).
- **Global indexes:** the index is itself partitioned by the indexed value, the user ID. A query asks one index partition. But a single message write now touches two partitions, its channel's and its author's index entry, so global indexes are usually updated asynchronously and are briefly stale. DynamoDB's global secondary indexes are eventually consistent for this reason.

Scatter-gather gets worse as the cluster grows, because a request is as slow as its slowest partition. If each partition answers within 50 ms 99% of the time, a request that needs all 24 gets every answer within 50 ms only 0.99²⁴ ≈ 79% of the time. At 64 partitions it's 53%: nearly half of all requests see some partition's worst-case latency. That's why the abuse query's p99 was 4 seconds.

For queries that matter, the common answer is to maintain a separate read model partitioned by the other key, fed by change data capture (38.4a) or the outbox, which is a global index built deliberately (23.2b). For rare queries, keep scatter-gather, but give each partition a deadline, return partial results with an explicit flag, and run them off-peak or against replicas.

### Rebalancing

Moving a partition means copying its data to the new owner, catching up on writes made during the copy, and switching ownership. 38.2b covers doing that safely. Three policies around it matter here:

- **Automatic or approved.** Systems that rebalance automatically when a node looks dead can turn a brief network blip into a mass data movement, which adds load, which causes more timeouts, which causes more movement. Many operators prefer automatic detection with a human, or at least a delay, before large moves.
- **Throttle it.** A rebalance competes with live traffic for disk and network. Moves should be rate-limited, and paused under load.
- **Route with a versioned map.** Clients or a routing tier hold the partition map with a version. When a partition moves, a request to the old owner is answered with a redirect naming the new one, and the client refreshes its map (Redis Cluster's `MOVED` reply works this way). A stale map should cost one extra hop, never a wrong answer.

## When It's Appropriate

- **A fixed-partition or consistent scheme** whenever the number of nodes will ever change, which includes every cache cluster that autoscales.
- **Compound keys** when reads are "recent items for this entity": messages per channel, events per device, orders per customer.
- **Time-bucketed partition keys** when an entity's data grows without end, or a few entities are far larger than the rest.
- **A global index or a separate read model** when a query by a secondary attribute is frequent or latency-sensitive: moderation, user exports, anything user-facing.
- **Dynamic range partitioning** when range scans on the key matter and the database can split automatically, provided keys aren't monotonic.

## When It's Unnecessary or Overkill

- **Before a single node is outgrown.** A well-sized database with partitioned tables (23.2b) handles far more than most products need.
- **A custom placement scheme on a database that already has one.** Cassandra, DynamoDB, CockroachDB, MongoDB and Redis Cluster already implement map 2. The design work is the key, not the placement.
- **Consistent hashing for a fixed-size cluster** that's rebuilt rather than resized.
- **A global index for a rare admin query,** where a slow, deadline-bounded scatter-gather off-peak is enough.
- **Salting keys that aren't hot.** It makes every read gather from many partitions to fix a problem one key has.

## Trade-offs

- **Hash placement gives up range scans** on the key, and range placement gives up even writes for monotonic keys. Compound keys soften both, within an entity only.
- **More partitions means more overhead** per partition, and fewer means coarser moves and a lower ceiling on nodes.
- **Time buckets complicate reads:** "latest messages" may span several buckets, and quiet channels need a way to skip empty ones.
- **Global indexes add write cost and staleness;** local indexes add fan-out, and the tail latency of fan-out grows with the cluster.
- **Automatic rebalancing can amplify incidents,** and manual rebalancing needs people and runbooks.
- **Routing maps are shared state,** with versioning, caching and redirect handling in every client or router.

## Alternatives

- **Scale one node further** (23.1a), and partition tables within it (23.2b).
- **A distributed SQL database** (CockroachDB, YugabyteDB, Spanner) that splits and rebalances ranges itself, including hash-sharded indexes for monotonic keys.
- **A directory** (23.2b) instead of hashing, when entities vary enormously in size and must be moved individually.
- **Separate stores per access pattern:** messages by channel in one store, messages by author in a search index or read model, rather than one store serving both.
- **Cells** (23.6): split the whole stack by groups of users, so each cell's database stays small enough not to need fine-grained partitioning.

## How to Achieve It

1. **Separate the two maps.** Replace any `% nodes` placement with a fixed number of slots and a slot-to-node table, or with consistent hashing for caches. This is cheap, and it removes the worst resize incident.
2. **Choose compound keys for per-entity reads,** and check whether any key's data grows without bound. If so, add a time bucket to the partition key before the largest one becomes a problem.
3. **Measure load per partition and per key.** Alert on skew, not only on node CPU. _Next when:_ one key's traffic approaches a partition's capacity.
4. **Treat hot keys explicitly:** read coalescing and caching first, then splitting or isolating the largest keys.
5. **Build secondary access paths deliberately:** a read model or global index for frequent queries by another key, fed by CDC (38.4a); deadline-bounded scatter-gather for rare ones.
6. **Set a rebalancing policy:** throttled moves, a delay before moving data off a node that might come back, and versioned routing with redirects. The mechanics of each move are 38.2b.

## Implementation

Go, because placement is small, pure functions over hashes, and Go keeps them close to the arithmetic. The first piece measures exactly the incident that opened this article.

### How many keys move?

```go
// Jump consistent hash (Lamping and Veach, 2014): no state beyond the bucket count.
func jump(key uint64, buckets int) int {
	var b, j int64 = -1, 0
	for j < int64(buckets) {
		b = j
		key = key*2862933555777941757 + 1
		j = int64(float64(b+1) * (float64(int64(1)<<31) / float64((key>>33)+1)))
	}
	return int(b)
}

func modN(key uint64, n int) int { return int(key % uint64(n)) }

func movedFraction(keys []uint64, place func(uint64, int) int, from, to int) float64 {
	moved := 0
	for _, k := range keys {
		if place(k, from) != place(k, to) {
			moved++
		}
	}
	return float64(moved) / float64(len(keys))
}

// With a million hashed channel IDs, going from 8 nodes to 9:
//   movedFraction(keys, modN, 8, 9)  ≈ 0.889   the cold-cache incident
//   movedFraction(keys, jump, 8, 9)  ≈ 0.111   only the ninth node's new share
```

The number is worth computing for your own system before adding a node, not after. `% N` moves almost everything because every key's position depends on N. Consistent schemes move only the keys the new node takes over, which is the smallest possible fraction.

### Fixed slots, and a versioned map that can redirect

```go
const Slots = 4096 // chosen once; far more than we will ever have nodes

func SlotOf(key string) int { return int(xxhash.Sum64String(key) % Slots) } // map 1: never changes

type SlotMap struct {
	Version int64
	Owner   [Slots]NodeID // map 2: changes when slots move
}

type Moved struct {
	Slot    int
	Owner   NodeID
	Version int64
}

// On each node: serve the slot, or tell the client where it went.
func (n *Node) Handle(req Request) (Response, error) {
	slot := SlotOf(req.Key)
	if owner := n.slots.Load().Owner[slot]; owner != n.ID {
		return Response{}, Moved{Slot: slot, Owner: owner, Version: n.slots.Load().Version}
	}
	return n.serve(req)
}
```

A client with a stale map sends a request to the old owner, gets `Moved`, refreshes its map if the version is newer, and retries at the new owner. A moved slot costs one extra hop, never a wrong answer.

The node answering with `Moved` has to have actually handed the slot over, which means the move protocol in 38.2b must fence the old owner before the map changes. Otherwise both nodes accept writes for the same slot.

### A partition key that stops growing

```go
const bucketSpan = 10 * 24 * time.Hour // 10-day buckets

type MessageKey struct {
	ChannelID int64
	Bucket    int64 // partition key: (ChannelID, Bucket)
	MessageID int64 // sorted within the partition; time-ordered
}

func bucketOf(t time.Time) int64 { return t.Unix() / int64(bucketSpan/time.Second) }

// Latest messages: walk buckets backwards until the page is full.
func (s *Store) Latest(ctx context.Context, ch Channel, limit int) ([]Message, error) {
	var out []Message
	for b := bucketOf(time.Now()); b >= bucketOf(ch.CreatedAt) && len(out) < limit; b-- {
		msgs, err := s.readBucket(ctx, ch.ID, b, limit-len(out)) // one partition, one sorted read
		if err != nil {
			return nil, err
		}
		out = append(out, msgs...)
	}
	return out, nil
}
```

The streamer's channel now writes to one bucket at a time, and each bucket holds at most 10 days of its history, so no single partition grows past what one node can compact and repair. Older buckets are spread across the cluster by the hash of `(channel, bucket)`.

A quiet channel created three years ago with its last message a year ago would read about 36 empty buckets before reaching it. Keep a `last_message_bucket` per channel, updated on write, and start from there. That's a small cost paid on writes to avoid many empty reads.

Hot reads during a stream are still one partition. Coalesce them in front of the store: concurrent requests for the same `(channel, latest)` share one in-flight read, which `golang.org/x/sync/singleflight` does in a few lines.
