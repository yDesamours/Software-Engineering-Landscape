# Build Tools & Dependency Management

_Module 3.3 — Project Setup & Development Environment_

## The Problem

11pm. Production is broken. The fix is one line, and you need to ship it against exactly what's running.

```bash
git checkout v2.4.1
./build
```

The build fails. A library three levels down published a patch release two weeks ago, your manifest asks for `^1.2.0`, and the patch removed a function that something else was using. You pin it. Now a different package refuses to resolve. Forty minutes later you have a build.

It is not the same build. Fourteen transitive dependencies are at versions that didn't exist when v2.4.1 shipped. You're about to deploy a one-line hotfix bundled with an uncontrolled upgrade of fourteen packages, at midnight, to a system that is currently on fire.

The commit was pinned. The build was not. **Your build was a function of what day you ran it**, and nobody noticed until the day that mattered.

### The version nobody chose

A second failure, from the same root. Your service depends on two libraries, and both depend on a third:

```
   your-app
   ├── report-kit   → widgets ^2.0
   └── billing-kit  → widgets ^3.0
```

Only one of `widgets` 2.x and 3.x can be on a Java classpath. Something has to decide, and what it decides is not obvious:

```
  npm / yarn   nest both copies — report-kit gets 2.x, billing-kit gets 3.x
  Maven        nearest-wins: whichever is declared at the shallower depth
  Gradle       highest: 3.x, and report-kit may break
  Go           v2 and v3 are different modules with different import paths,
               so both load and the conflict doesn't arise
```

Four ecosystems, four different answers, and in the Maven case the answer depends on the *shape of your dependency tree*, not on the versions. Nothing warns you. `billing-kit` gets `widgets` 2.x, compiles fine because it was compiled against 3.x elsewhere, and throws `NoSuchMethodError` in production, from a library you have never heard of, on a code path you didn't write.

### The question you can't answer

Security emails on a Friday: *do we ship log4j, and at what version?*

You have 1,847 packages in the dependency graph. Twelve are direct. The rest arrived because something else wanted them. Nobody on the team has read any of them, nobody approved them, and there's no artifact anywhere that lists them.

Meanwhile a maintainer of a forty-line utility deep in that graph got tired and handed the package to a volunteer who offered. The new owner published a patch release. Your range permits patch releases. Your CI installs fresh on every run.

Three failures, one cause: **the set of code you ship is decided by an algorithm you didn't read, over inputs you don't control, at a time you didn't choose.**

## What It Is

Two jobs get bundled into "the build," and separating them makes everything downstream clearer:

**Resolution** decides *which versions of which packages* constitute your dependency set. **Execution** turns source plus dependencies into an artifact, ideally incrementally.

The concepts that matter:

**Manifest versus lockfile.** The manifest (`pom.xml`, `package.json`, `go.mod`) states your *intent*, usually as ranges: "some 2.x of this." The lockfile (`package-lock.json`, `go.sum`, a Gradle lock file) records the *resolved reality*: exact versions, exact sources, exact checksums. Running resolution again with the same manifest can produce a different answer next month. Running a build from the same lockfile cannot.

That's the central idea of the article. A manifest without a lockfile is a description of a build you'd like to have. A lockfile is the build you actually had.

**Direct versus transitive.** You choose your direct dependencies. Your transitive dependencies choose themselves, and there are typically a hundred times more of them.

**Semantic versioning is a social contract, not a guarantee.** The entire range system rests on maintainers correctly classifying their own changes as breaking or not. They often can't: per Hyrum's law, with enough users, every observable behaviour of a system ends up being depended on by someone, so "not breaking" is a property of your users rather than of your diff. A patch release can break you and the maintainer did nothing wrong.

**Reproducibility, in degrees.** Same lockfile → same package versions. Plus pinned toolchain → same compiler behaviour. Plus checksum verification → same bytes from the registry. Plus a hermetic build with no clock, network, or environment leakage → byte-identical output. Most teams need the first two, benefit from the third, and will never need the fourth.

Two neighbours worth separating:

**Build tool, task runner, and package manager are three roles.** Maven is all three. Gradle is a build tool with dependency management and a general task graph. npm is a package manager with a script runner attached. Go splits them: the toolchain builds, `go mod` resolves, and there's no task runner at all — which is why Go projects have Makefiles. Knowing which role a tool is playing explains most of its design choices.

**Lockfiles and vendoring solve overlapping problems differently.** A lockfile says "these exact versions, fetched from the registry." Vendoring says "these exact bytes, in our repository." The lockfile assumes the registry will still be there and still have that version. Vendoring doesn't.

## Recognizing the Problem

- A build that worked last week fails today with no code change.
- You cannot rebuild a released version and get what you released.
- CI and local machines produce different results from the same commit.
- Nobody can answer "do we ship package X, and at what version?"
- Upgrading one dependency has become a multi-day project, so upgrades get deferred, so they get worse.
- The lockfile is in `.gitignore`, or gets regenerated as part of CI.
- Version conflicts are resolved by trial and error until the tests go green.
- A `NoSuchMethodError` or `undefined is not a function` appears at runtime, in a library you never called directly.
- Both `package-lock.json` and `yarn.lock` are committed, and nobody knows which one CI uses.
- Your build depends on a network fetch that isn't cached, so a registry outage stops deploys.
- Build times have grown to where people batch work to avoid rebuilding.

## How It Works

### Resolution strategies, and why they disagree

**Flat versus nested** is the first fork. The JVM classpath allows exactly one version of a class, so Maven and Gradle must pick a single winner per artifact. Node's module resolution allows nesting, so npm can install two copies and give each consumer the version it asked for. Nesting avoids the conflict and pays for it elsewhere: larger installs, and — the subtle one — two copies of a library are two separate module instances, so singletons aren't single, `instanceof` fails across the boundary, and two copies of a UI framework break in ways that are extremely hard to diagnose.

**Maven: nearest-wins.** The version at the shallowest depth in the dependency tree wins; ties break by declaration order. Note what this is *not* — it isn't "highest version." A 2.x declared two levels down beats a 3.x declared three levels down. The winner depends on tree shape, which changes when any dependency changes.

**Gradle: highest wins.** Given the same POMs, Gradle resolves the same graph differently from Maven. Teams migrating between them discover this the hard way.

**npm: highest compatible, nested when incompatible**, plus hoisting — flattening what it can into the top-level directory for efficiency. Hoisting is why the directory layout is unspecified and why *phantom dependencies* exist: you can `import` a package you never declared, because something else pulled it up to where your code can see it. It works until the day that other package drops it. This is also what quietly corrupts the affected-target detection from Module 3.1, since the dependency graph the tool reads is the declared one. pnpm's content-addressed store with symlinks exists specifically to make phantom imports fail.

**Go: minimal version selection.** Each module declares a *minimum* version it needs; the build selects, for each module, the maximum of all the minimums requested anywhere in the graph. It never picks something newer than anything asked for. The consequence is unusual and worth sitting with: adding a dependency cannot silently upgrade an unrelated one, and the resolution is a pure function of the requirement graph, so it's reproducible without a resolver lockfile at all. Major versions are separate import paths (`widgets/v2`, `widgets/v3`), so the diamond at the top of this article simply isn't a diamond — both load, side by side.

The trade is that you stay on old versions until someone deliberately moves, which is a feature if you value stability and a liability if you value patches arriving on their own.

### Lockfiles, and the command that matters

A lockfile records exact versions, the resolved source, and an integrity hash per package. Committing it is table stakes — Module 3.1 noted that in a monorepo there's exactly one, for the whole tree.

The part that gets missed is the *install command*. There are two:

- One that **resolves**: `npm install`, `gradle build` with dynamic versions. It may update the lockfile to satisfy the manifest.
- One that **obeys**: `npm ci`, `yarn --immutable`, `pnpm --frozen-lockfile`, `go build` with `-mod=readonly` (the default), Gradle with `--write-locks` absent. It fails if the manifest and the lockfile disagree.

CI must use the second. Using the first means CI can resolve differently from your machine, from yesterday, and from the deploy that follows — which returns you to the Problem section with extra steps.

### Integrity, and what checksums don't cover

Lockfile hashes verify that the bytes you got match the bytes that were published. That defeats tampering in transit and after the fact — Go's checksum database exists precisely so that a rewritten tag can't go unnoticed.

It does not defeat a *legitimately published* malicious version. If the maintainer's account is compromised, or the maintainer is the attacker, the hash matches perfectly. That's the event-stream pattern, the attempted xz backdoor, and every typosquat.

The defences are layered, and none is complete:

- **Ranges that don't float.** A lockfile already gives you this, as long as CI obeys it.
- **Review the lockfile diff.** New transitive packages appearing in a PR is a signal worth looking at, even if the diff is tedious.
- **A cooldown.** Configure your update bot to ignore anything published in the last few days. Most malicious packages are pulled within hours of discovery, and you gain nearly all the security benefit of fast patching while skipping the window where compromises are live. Underused, and close to free.
- **A private proxy or mirror.** Artifactory, Nexus, Verdaccio, Athens, or Go's module proxy. Caches everything you've used, so an unpublished or deleted package doesn't break your builds, and gives you a place to enforce an allowlist.
- **An SBOM.** A machine-readable list of everything in the artifact, generated at build time and stored with it. This is what turns the Friday security email into a grep instead of an investigation.

### Execution: caching and hermeticity

**Incrementality** works by hashing inputs — source files, dependency versions, compiler flags, environment — and reusing cached outputs when the hash matches. It's the same machinery as Module 3.1's affected-target detection, one level down: a task graph plus input hashing. Remote caches share those outputs across machines, so CI and your laptop benefit from each other's work.

The correctness risk is real and worth naming: if a task's declared inputs don't include something it actually reads, the cache returns a stale output and the build is silently wrong. Cache-invalidation bugs are among the least pleasant things to debug, because the symptom is code that doesn't match its source.

**Hermeticity** is the property that a build depends on nothing outside its declared inputs. Most builds aren't hermetic — they read the system clock, resolve DNS, use whatever compiler is on `PATH`, embed an absolute path. **Reproducible builds** go further and demand byte-identical output, which requires removing timestamps, fixing file ordering, and stripping build paths. Go is unusually close to this by default and gets the rest with `-trimpath`.

## When It's Appropriate

**Always, on every project:** a committed lockfile and an obey-the-lockfile install in CI. There is no project small enough for this not to pay.

**Always:** pin the build tool itself, not just the language. The Gradle and Maven wrappers, a `packageManager` field, Go's toolchain directive. Module 3.2 pinned the runtime; the build tool is the other half, and a Gradle 8 versus Gradle 9 difference produces the same "works on my machine" class of failure.

**Any project with more than a handful of dependencies:** automated update PRs, grouped so that twenty patch bumps arrive as one reviewable change rather than twenty.

**When registry availability matters:** a proxy. If a failed `npm install` can block a deploy during an incident, or if you build in a network-restricted environment, the cache is the point. The allowlist is a bonus.

**When you sell to enterprises or operate under regulation:** SBOM generation, stored alongside the artifact. It's increasingly contractual rather than optional, and generating it at build time costs a CI step.

**When builds exceed a few minutes and the team is more than a few people:** a remote build cache. The arithmetic is direct — ten engineers, thirty builds a day, four minutes saved each is two person-hours a day.

**When provenance verification matters:** reproducible builds and signed attestations. Relevant if you distribute binaries that others need to trust, and rarely otherwise.

## When It's Unnecessary or Overkill

**Pinning everything exactly and never updating.** This feels like the safe end of the spectrum and isn't. Frozen dependencies accumulate unpatched vulnerabilities, and the eventual upgrade — four major versions at once, across a graph that has reshaped underneath you — is the most expensive form the work can take. Stability comes from *reproducible* builds plus *frequent small* updates, not from standing still.

**Vendoring everything by default.** Repository bloat, noisy diffs, and updates that are invisible in review because nobody reads a 40,000-line vendor diff. Vendor selectively, for reasons.

**An internal registry for five engineers.** Another service to run, another thing to be down, in exchange for solving a problem you don't have yet.

**Byte-reproducible builds nobody verifies.** If no one ever rebuilds the artifact and compares hashes, the property is unused and its cost is ongoing.

**Auto-merging bot PRs on green.** Only as good as the tests, and it converts your dependency update process into "whatever the registry says, immediately." Combine with a cooldown at minimum.

**Heavy build systems at small scale.** Module 3.1 made this argument about monorepo tooling and it applies identically here: adopt Bazel-class tooling when correctness or build time actually hurts.

## Trade-offs

**Pinned versus current is a genuine tension, not a solved problem.** Pinned means reproducible and stale. Floating means current and non-deterministic. The standard resolution — lock, then update deliberately on a schedule — resolves it only by converting it into recurring work that has to be somebody's job.

**Update cost compounds superlinearly.** One month behind is a bot PR. Two years behind is a project with a kickoff meeting. This is the strongest practical argument for a boring weekly cadence, and it's why deferring feels cheap and isn't.

**Lockfile diffs are unreviewable at size.** A dependency update can produce a 2,000-line diff that nobody reads, which is exactly the place a supply-chain attack would prefer to live. Partial mitigations: review the *set* of new package names rather than the diff, and treat new transitive packages as more interesting than version bumps of existing ones.

**Caching trades correctness risk for speed.** Mostly a good trade, occasionally a very bad afternoon.

**A proxy is another dependency.** You've added a service whose outage stops all builds, in exchange for surviving the registry's outages. Worth it at scale, not at three people.

**Every dependency is a permanent liability.** Not just the install: the upgrade path, the security surface, the maintainer's continued interest, and the day it's abandoned and you own it. The question at the moment of adding one isn't whether it saves time today — it always does — but whether you're willing to own it in three years.

## Alternatives

**Fewer dependencies.** The most effective intervention available and the least discussed. A standard library function, or forty lines you write and test, has no version, no registry, no maintainer, and no CVE feed. Module 3.1's note about small-scale copying applies directly.

**Vendoring instead of trusting a registry.** Offline builds, immunity to unpublishing, and third-party changes that appear in review as actual code. Costs repository size and diff noise.

**Live at head.** The Google approach: no version ranges at all internally, one version of everything, everyone on the newest, breaking changes fixed by whoever makes them across the whole repository at once. It requires a monorepo and enormous test coverage, and it eliminates the diamond problem by eliminating versions — the same move Module 3.1 described for internal packages, taken to its conclusion.

**Make as the build tool.** Universal, knows nothing about your ecosystem, gives you a task graph and file-timestamp incrementality, and is still the thing most projects actually use to tie the ecosystem tools together.

**Ecosystem-native versus general-purpose build tools** is a spectrum: Maven and npm are convenient and single-language; Bazel and Pants are hermetic, correct, polyglot, and heavy. Pick the lightest one that solves a problem you actually have.

## How to Achieve It

**L1 — Commit the lockfile, and make CI obey it.** `npm ci` rather than `npm install`, `--frozen-lockfile`, dependency locking switched on. One line of CI configuration, and it removes the failure at the top of this article.

*Next when:* two machines with the same lockfile still behave differently.

**L2 — Pin the build tool and toolchain.** Wrappers, toolchain directives, checksums on the wrapper distribution itself.

*Next when:* dependencies have started drifting behind because updating is manual.

**L3 — Automated update PRs, grouped, with a cooldown.** Weekly, batched by ecosystem, ignoring anything published in the last few days.

*Next when:* someone asks what's in your artifact and you can't say.

**L4 — Generate an SBOM in CI and store it with the artifact**, then scan it. The scan is only useful because the SBOM exists; do them in that order.

*Next when:* registry availability or package provenance becomes a real risk.

**L5 — A proxy or mirror**, with an allowlist if compliance requires it.

*Next when:* build times are costing measurable engineering hours.

**L6 — Build caching, local first, then remote.**

*Next when:* somebody outside your team needs to verify that a binary matches its source.

**L7 — Hermetic and reproducible builds**, with signed provenance attestations.

Most projects should be at L4 and stop.

## Implementation

Java with Gradle, because the JVM is where flat resolution makes conflicts unavoidable, and because Gradle exposes two mechanisms — dependency locking and API-versus-implementation scoping — that directly address the failures above and that most users never switch on.

### One place where versions live

```toml
# gradle/libs.versions.toml — a version catalog
[versions]
spring-boot = "3.3.4"
jackson     = "2.17.2"

[libraries]
spring-boot-web  = { module = "org.springframework.boot:spring-boot-starter-web", version.ref = "spring-boot" }
jackson-databind = { module = "com.fasterxml.jackson.core:jackson-databind", version.ref = "jackson" }

[bundles]
web = ["spring-boot-web", "jackson-databind"]
```

In a multi-module build this is the difference between one version of Jackson and eleven subtly different ones. It's also what makes an upgrade a one-line diff in a file a human can read, rather than a search across twenty build scripts.

### Controlling what leaks to your consumers

```kotlin
// build.gradle.kts
plugins { `java-library` }

dependencies {
    // Part of this module's public API: types appear in exported signatures.
    // Consumers get this on their compile classpath, transitively.
    api(libs.jackson.databind)

    // An internal implementation detail. Consumers never see it.
    implementation("org.apache.commons:commons-lang3:3.17.0")
}

dependencyLocking {
    lockAllConfigurations()      // ← off by default. This is the lockfile.
}
```

The `api`/`implementation` distinction is the only real defence against transitive sprawl, and choosing wrong is close to irreversible. Declare something `api` and it lands on every consumer's compile classpath — at which point, per Hyrum's law, someone starts using it, and removing it later is a breaking change to *your* library caused by a dependency you never meant to expose. Declare it `implementation` and it stays yours. When in doubt, `implementation`: widening later is easy, narrowing is not.

`dependencyLocking` deserves a flag of its own. Unlike npm and Go, **Gradle does not lock by default**. A build with dynamic versions, no lock file, and no verification is not reproducible, and nothing about it looks unusual — which is how a project reaches the 11pm scenario without anyone having made a bad decision.

### Verifying and obeying

```xml
<!-- gradle/verification-metadata.xml (generated, then committed) -->
<verification-metadata>
  <configuration><verify-signatures>true</verify-signatures></configuration>
  <components>
    <component group="com.fasterxml.jackson.core" name="jackson-databind" version="2.17.2">
      <artifact name="jackson-databind-2.17.2.jar">
        <sha256 value="a1b2c3…"/>
      </artifact>
    </component>
  </components>
</verification-metadata>
```

```bash
# CI: obey, don't resolve.
./gradlew build --no-daemon        # fails if the lock file and manifest disagree

# Humans, deliberately, on update day:
./gradlew build --write-locks
```

Gradle's dependency verification checks signatures and checksums for every artifact, including transitive ones, and refuses to build on a mismatch. This is the layer that catches tampering — and, per the earlier caveat, not the layer that catches a maintainer who publishes something malicious under their own key. For that, the cooldown and the lockfile-diff review are the tools available.

One detail that's easy to skip and shouldn't be: `gradle/wrapper/gradle-wrapper.properties` takes a `distributionSha256Sum`. Without it, the first thing your hermetic, verified, locked build does is download a build tool over the network and run it unverified.

## Further Reading

- **Russ Cox, "Our Software Dependency Problem" (research.swtch.com, 2019).** The best essay written on dependency trust — what you're actually taking on, and how to evaluate it. Read this one even if you read nothing else here.
- **Russ Cox, "Minimal Version Selection" (research.swtch.com, 2018).** Why Go picks the maximum of the minimums, and what that buys. Genuinely changes how you read other ecosystems' resolvers.
- **Winters, Manshreck & Wright, _Software Engineering at Google_ (O'Reilly, 2020), chapter 21.** Dependency management at scale, the argument against version ranges, and the live-at-head model. Strongly opinionated and worth engaging with even where you disagree.
- **Hyrum Wright, "Hyrum's Law" (hyrumslaw.com).** One sentence, and it explains most of why semantic versioning under-delivers.
- **semver.org.** Short. Read it once so you know precisely what maintainers are and aren't promising.
- **Gradle documentation — dependency locking, dependency verification, and the `java-library` plugin's API/implementation separation.** All three are off or misunderstood by default.
- **Maven documentation — dependency mediation and `dependencyManagement`.** Specifically the nearest-wins rule, which surprises nearly everyone.
- **pnpm documentation on the content-addressable store**, for the clearest explanation of phantom dependencies and why hoisting causes them.
- **The Go Modules Reference**, particularly the checksum database and `GOFLAGS=-mod=vendor`.
- **slsa.dev** for supply-chain integrity levels, and **CycloneDX** or **SPDX** for SBOM formats.
- **reproducible-builds.org**, especially the documentation of what makes builds non-deterministic — a good checklist even if byte-identical output isn't your goal.
- **The xz-utils backdoor (CVE-2024-3094) post-mortems.** The most instructive recent case study in maintainer trust, social engineering, and why "the checksum matched" isn't a defence.

A TypeScript sibling would show a genuinely different set of problems rather than the same ones in other syntax. Node's nested resolution means the diamond is solved by duplication instead of arbitration, which trades a loud classpath conflict for a quiet one: two copies of a library with separate module state, singletons that aren't, `instanceof` failing across the boundary, and two copies of a UI framework producing errors that point nowhere near the cause. Hoisting adds phantom dependencies, which have no JVM equivalent at all. And the ecosystem's norm of many small packages means the graph is an order of magnitude larger, which changes the supply-chain calculus from "review the additions" to "you cannot review the additions." Not yet written.

---

The habit worth carrying out of this article is the one that would have prevented all three failures at the top: **know what decides your versions.** Not what they are — what *decides* them. If the answer is a lockfile you commit and a command that obeys it, you can rebuild anything you shipped. If the answer is "whatever the resolver felt like on the day CI ran," then every deploy contains an upgrade nobody reviewed, and you'll find out which one it was at the worst possible moment.
