# Layered Architecture

_Module 2.2 — Software Architecture Patterns_

## The Problem

A booking product for fitness studios. Members reserve spots in classes. The endpoint that does it looks like this:

```ts
app.post("/classes/:id/bookings", async (req, res) => {
  const member = await prisma.member.findUnique({ where: { id: req.session.memberId } });
  if (!member) return res.status(401).json({ error: "unauthenticated" });
  if (member.membershipStatus !== "active") return res.status(403).json({ error: "membership inactive" });

  const cls = await prisma.class.findUnique({
    where: { id: req.params.id },
    include: { bookings: true },
  });
  if (!cls) return res.status(404).json({ error: "not found" });
  if (cls.bookings.length >= cls.capacity) return res.status(409).json({ error: "class full" });
  if (cls.bookings.some((b) => b.memberId === member.id))
    return res.status(409).json({ error: "already booked" });

  if (member.plan === "basic") {
    const upcoming = await prisma.booking.count({
      where: { memberId: member.id, startsAt: { gt: new Date() } },
    });
    if (upcoming >= 3) return res.status(409).json({ error: "basic plan allows 3 upcoming bookings" });
  }

  const booking = await prisma.booking.create({ /* ... */ });
  await sendEmail(member.email, "booking-confirmed", { class: cls.name });
  await analytics.track("booking_created", { memberId: member.id });
  res.status(201).json(booking);
});
```

This is fine. It's readable, it works, and a reviewer would approve it.

Four months later the studio owners want to book members in from the admin panel. Same rules, different entry point. Nobody is going to make an admin panel call its own public HTTP API, so the logic gets copied into `adminBookMember()`.

Then the old system's bookings need importing. A script, third copy.

Then: when someone cancels, the first person on the waitlist should be promoted automatically. That's a background job, fourth copy.

Now count what you have. Four copies of four business rules, in four files, invoked from four places. Six months after that, someone tightens the basic plan from three upcoming bookings to two. They find it in the route handler, change it, ship it. The admin panel, the importer, and the waitlist promoter still say three.

Nobody notices for a year, because there is no error. Basic-plan members who happen to get promoted from waitlists accumulate seven upcoming bookings and the studio slowly loses money on them.

There's a second, quieter symptom. That capacity rule has eight branches. How do you test it? Boot an HTTP server, seed a database with a member and a class and two existing bookings, stub an email provider, issue a request, assert on a status code. Each case is twenty lines of setup and takes 400 ms. So in practice the rule gets two tests — the happy path and one refusal — and the other six branches are verified by hope.

Both symptoms have the same cause. **The business rules are welded to the mechanism that delivered the request.** They can only be invoked the way HTTP invokes them, and they can only be observed the way HTTP observes them. Everything else — a second entry point, a fast test, a change in one place — is blocked by that welding.

## What It Is

A **layer** is a group of code with a single kind of responsibility, plus a rule about which other groups it's allowed to depend on. Layering is the practice of choosing those groups and enforcing that rule.

The usual set, from outside in:

- **Presentation** — how a request arrives and how a result is rendered. HTTP handlers, CLI commands, job consumers, GraphQL resolvers. Anything that knows about status codes, serialization formats, or request objects.
- **Application** — one function per use case. Orchestration: load what's needed, ask the domain to decide, persist, emit events, manage the transaction. It contains sequencing, not rules.
- **Domain** — the rules and invariants. A class cannot be overbooked. A basic plan holds at most three upcoming bookings. These are true regardless of whether the request arrived over HTTP or from a CSV.
- **Infrastructure** — the implementations that touch the outside world: the ORM, the email provider, the object store, the clock.

Data access is sometimes listed as its own layer between domain and infrastructure. That's a detail of taxonomy; the interesting question is not how many boxes there are but **which way the arrows point.**

That question is the actual content of this topic. In the layering most people are first taught, dependencies point straight down:

```
Controller → Service → Repository → ORM → Database
```

Which means the service — the place your business rules live — depends on the repository, which depends on the ORM, which depends on the database. Your rules transitively depend on Postgres. The welding from the Problem section hasn't gone away; it's been moved down two floors and given nicer names.

The fix is one move, applied at the bottom: **the interface belongs to the inside.** The application layer declares what it needs from storage; infrastructure implements it. The arrow at the bottom of the stack flips.

```
        ┌─────────────────────────────────────────────┐
        │ Presentation    HTTP, CLI, jobs, webhooks   │
        └────────────────────┬────────────────────────┘
                             │ calls
        ┌────────────────────▼────────────────────────┐
        │ Application     use cases, transactions     │
        └─────┬───────────────────────────┬───────────┘
              │ calls                     │ declares
        ┌─────▼──────────────┐    ┌───────▼───────────┐
        │ Domain             │    │ Ports             │
        │ rules, invariants  │    │ (interfaces)      │
        │ imports NOTHING    │    └───────▲───────────┘
        └────────────────────┘            │ implements
                                  ┌───────┴───────────┐
                                  │ Infrastructure    │
                                  │ Prisma, SES, S3   │
                                  └───────────────────┘
```

Everything points inward. The domain imports nothing — not the framework, not the ORM, not even the system clock.

Worth clearing up immediately, because this is where the terminology gets noisy: **hexagonal architecture, ports and adapters, onion architecture, and clean architecture are the same idea.** Cockburn drew it as a hexagon to stop people thinking "top" and "bottom" mattered; Palermo drew concentric rings; Martin added a naming scheme and a dependency-rule slogan. They differ in vocabulary and in how many rings they draw. They do not differ in mechanism. If you understand "the interface belongs to the inside," you understand all four, and you can stop reading comparisons of them.

Two smaller distinctions:

**Layers are not tiers.** Layers are a code-organization concept; tiers are machines. All five layers normally run in one process. Deploying them separately is a different decision entirely, and Module 2.1 covered what it costs.

**Layers are not modules.** Layering slices horizontally by technical role; the modules from Module 2.1 slice vertically by domain. They compose: a well-structured system has a `bookings` module and a `billing` module, each with its own internal layering. A system with layers but no modules is the one where the `services` folder has ninety files in it and every one can call every other.

## Recognizing the Problem

- The same business rule exists in a route handler and in a background job, and you're not certain they still agree.
- Testing a rule requires a database, an HTTP client, or both.
- `import { prisma }` (or `db`, or `knex`) appears in a file named after a business noun.
- Your domain objects *are* ORM entities — they have decorators, a `save()` method, or a lazy-loaded relation.
- A function in the business layer takes a `Request` or returns a `Response`.
- An API field changed because someone renamed a database column, or a database column can't be renamed because it's in the API.
- Someone asks "where's the rule about X?" and the answer requires a grep.
- A new entry point — a CLI, a webhook consumer, a gRPC service — means reimplementing logic rather than calling it.
- Swapping any infrastructure component (email provider, storage, ORM) would be a multi-week project touching hundreds of files.

The strongest single signal is the first one. Duplicated rules across entry points means the rules have no home, and everything else in this article follows from giving them one.

## How It Works

### The rule that does the work

One constraint, stated once: **source code dependencies point inward only.** Presentation may import application, application may import domain, nobody imports outward. An inner layer must never name an outer one.

When an inner layer needs something an outer layer has — a database, an email sender, the current time — it declares an interface describing what it needs, and the outer layer provides an implementation. Wiring happens once, at startup, in the outermost place (`main`, a composition root, a DI container).

This is dependency inversion, and it's doing two things at once. It removes the compile-time dependency, which is what lets you test and swap. It also puts the *shape* of the interface under the control of the code that uses it: the application asks for the four operations it actually needs, not the forty the ORM offers. Module 2.1 made the same argument for module boundaries. It's the same argument.

### Where the boundary between application and domain goes

This is the boundary people get wrong, and getting it wrong is what produces an "anemic" domain — layers everywhere, rules still nowhere.

The test that works: **would this statement still be true if the system had no database and no network?**

- "A class with capacity 12 cannot hold a 13th booking." True in a paper ledger. Domain.
- "Basic plans allow three upcoming bookings." True in a paper ledger. Domain.
- "Load the member, check the rules, insert a row, then send an email." Meaningless without infrastructure. Application.
- "Refusals map to HTTP 409." Only meaningful over HTTP. Presentation.

Rules are decisions. Use cases are sequences. If your `BookingService` is 300 lines of `await` with four `if` statements sprinkled through it, the sequence and the decisions are still tangled — you have one layer wearing two hats.

### Data crossing boundaries

Each layer works in its own representation. A request body becomes a validated command; the command becomes domain input; the domain's output becomes a persistence model; the persistence model becomes an API response.

This is the part practitioners resist hardest, and the resistance is reasonable — for a six-column settings table it is genuinely four near-identical shapes and three pointless mapping functions. But the shapes are what stop a database migration from silently changing your public API, and they're what let the API keep a field the database no longer has. The judgment call is per-feature, not per-codebase: map where the representations have reasons to differ, and don't where they don't.

The thing to avoid is the middle path where people "solve" the boilerplate with an automatic mapper that copies fields by name. That restores the coupling exactly — rename a column, and the API response changes — while adding a layer of reflection that makes it invisible.

## When It's Appropriate

**Rules with real branching.** Pricing with tiers and proration. Scheduling with capacity, blackout dates, and cancellation windows. Permissions with roles, ownership, and delegation. Anywhere the decision logic has more than a handful of interacting conditions, isolating it pays for itself the first time you need to change one condition without disturbing the others.

**More than one entry point.** The moment a rule is reachable from HTTP *and* a worker *and* an admin tool, it needs a single home. This is the most common trigger in practice, and it usually arrives four months into a project rather than at the start.

**Long-lived systems with staff turnover.** The rules in a payroll system outlive two or three framework generations. Code where the rules are separable from the framework survives that; code where they're welded into controllers gets rewritten instead of migrated.

**Where test cost is the bottleneck.** A pricing engine with forty cases: through HTTP, that's forty integration tests at 400 ms and twenty lines of setup each. As pure functions, it's forty object literals running in under a second, and people actually write all forty. The change in economics is the point, not the architecture diagram.

**Where infrastructure is genuinely likely to change.** Not the mythical "what if we switch databases," which mostly doesn't happen — but the ones that do: an email provider, a payment processor, a search backend, a file store, moving from one queue to another. If a component is behind a port, that's a day. If it's called directly from sixty files, it's a quarter.

## When It's Unnecessary or Overkill

**Most CRUD is genuinely CRUD.** If the use case is "save what the user typed, subject to a required-field check," then a full stack of handler → use case → domain object → port → adapter produces four files that exist solely to forward a call to the next one. That isn't architecture, it's a relay race. A handler that validates input and runs a query is the correct amount of structure for that endpoint, and a large fraction of any application's endpoints are that endpoint.

The failure mode here is applying uniform depth across the whole codebase. Real systems are lumpy: the billing module has dense invariants and deserves every layer; the notification-preferences screen has none and deserves a query. Layering per feature, matched to that feature's complexity, is both cheaper and clearer than a repo-wide ceremony.

**The domain isn't known yet.** Early on, the rules change weekly because you're still learning them. Fixing them into a carefully designed domain layer means rewriting that layer weekly. A thinner structure is easier to reshape.

**One entry point, short life.** An internal tool, a migration script, a service with one caller that you'll delete in a year. The duplication problem never arrives.

**Layers as folders with no rule attached.** If `domain/` imports from `infrastructure/` because nothing stops it, you have the indirection cost and none of the benefit. Either enforce the direction with a lint rule or an architecture test, or don't claim to have layers.

## Trade-offs

**Indirection has a real price.** Adding one field to one endpoint means touching the request type, the command, the domain object, the persistence model, the response, and the mapper. Six files for a string. That cost is paid on every trivial change, forever, while the benefit only shows up on the non-trivial ones.

**Navigation gets harder.** Jump-to-definition lands on an interface. Finding the real implementation means knowing the wiring. In a codebase with three adapters per port, tracing a request end-to-end is a genuinely slower activity than it was in the original handler.

**Reads suffer more than writes.** The pattern is shaped for writes — load a consistent object, enforce invariants, save. Reads usually want a denormalized, joined, paginated projection that no domain object corresponds to. Forcing every read through repositories that return whole aggregates produces N+1 queries and a lot of discarded data. The standard escape is to let the read path skip the domain entirely and query directly, which is the mild version of CQRS (Module 2.4). Permitting that is not cheating; insisting on symmetry is where layered architectures acquire their reputation for slowness.

**It can fail while looking successful.** The most common outcome of an attempted layering is: five folders, correct dependency directions, and all the business rules still sitting in `services/` with the domain objects reduced to field bags. Fowler named this the anemic domain model. From the outside it's indistinguishable from the real thing — same folder structure, same interfaces — and it delivers none of the benefit, because the rules are still in the orchestration layer where they can't be tested or reused independently.

**Onboarding cost.** More concepts to hold before the first commit, and a plausible-looking wrong place to put code at every step.

**It does not solve concurrency, consistency, or performance.** Layering is about where code lives. A race condition is still a race condition with beautiful layers. This is worth saying because layering is often proposed as a general-purpose fix for systems that are actually suffering from something else.

## Alternatives

**Transaction script.** One procedure per use case, top to bottom, doing its own data access. Fowler's name for the shape the Problem section started with — minus the duplication, because the procedure is called from all four entry points rather than copied. This is dramatically better than the original and dramatically simpler than full layering, and for applications whose logic is mostly sequential it's often the right final answer. If you only take one step from this article, take this one.

**Active Record.** Rules live on objects that also know how to persist themselves — Rails, Laravel, Django. You trade testability-without-a-database and infrastructure independence for a very large amount of speed, and the trade is honest. It goes bad specifically when the rules grow past what fits comfortably on a single row's object, at which point the model class hits 2,000 lines and starts reaching into other models' tables.

**Vertical slice architecture.** Organize by feature rather than by technical role: everything for "book a class" lives in one folder, including its query. Each slice chooses its own depth, so the complex ones get a domain layer and the simple ones don't. This directly addresses the uniform-depth problem above, at the cost of some duplication across slices and a weaker story about where shared rules live. Increasingly the default in .NET and TypeScript codebases, and it composes well with the modules from Module 2.1.

**Functional core, imperative shell.** Same dependency rule, no ceremony: the rules are pure functions taking plain data and returning plain data, and all I/O is in a thin outer shell that calls them. You get the testability benefit immediately and skip most of the interface machinery, because a pure function's "port" is its parameter list. In TypeScript and Go this is frequently the better-fitting version of the same idea, and the Implementation below leans that way.

## How to Achieve It

Per feature, not per repository. A ladder:

**L0 — Rules live in handlers.** The Problem section.

**L1 — Extract a use-case function.** One function per operation, taking plain arguments and returning plain data. No `Request` in, no `Response` out. The handler parses, calls, and maps the result to a status code.

*This is the step that pays.* Four entry points now call one function. Tests stop needing an HTTP client. Everything after this is refinement.

*Move on when:* the use-case function is mostly `if` statements about the business rather than sequencing, or you want to test a rule without a database.

**L2 — Separate decisions from sequencing.** Pull the rules out into pure functions or domain objects that take data and return a verdict. The use case loads, asks, and acts on the answer.

*Move on when:* you want those functions to run without infrastructure at all, or the persistence details are leaking into their signatures.

**L3 — Invert the persistence dependency.** Declare the interface the use case needs, next to the use case. Implement it in an infrastructure package. Wire it in `main`.

*Move on when:* an API response has changed because of a schema migration, or vice versa.

**L4 — Separate representations at each boundary.** API types, domain types, and persistence types stop being the same objects. Add this where the shapes have a reason to diverge, not everywhere.

*Move on when:* reads are being distorted to fit domain shapes, with N+1s or over-fetching as the symptom.

**L5 — Let the read path go direct.** Queries bypass the domain and return projections shaped for their consumer. Writes keep the full stack. (Module 2.4 takes this further.)

Different features will sit on different rungs indefinitely, and that's the correct end state rather than an unfinished one.

## Implementation

TypeScript. Refactoring the endpoint from the top of the article to L3.

### The rules, with nothing attached

```ts
// domain/booking.ts — imports nothing. Not Express, not Prisma, not Date.now().

export type Plan = "basic" | "unlimited";

export type Refusal =
  | { reason: "class_not_found" }
  | { reason: "membership_inactive" }
  | { reason: "class_full" }
  | { reason: "already_booked" }
  | { reason: "plan_limit_reached"; limit: number };

export const PLAN_LIMITS: Record<Plan, number> = { basic: 3, unlimited: Infinity };

export function canBook(ctx: {
  membershipActive: boolean;
  plan: Plan;
  capacity: number;
  seatsTaken: number;
  alreadyBooked: boolean;
  upcomingBookings: number;
}): Refusal | null {
  if (!ctx.membershipActive) return { reason: "membership_inactive" };
  if (ctx.alreadyBooked) return { reason: "already_booked" };
  if (ctx.seatsTaken >= ctx.capacity) return { reason: "class_full" };

  const limit = PLAN_LIMITS[ctx.plan];
  if (ctx.upcomingBookings >= limit) return { reason: "plan_limit_reached", limit };

  return null;
}
```

Two details are load-bearing.

The refusals are **domain values, not HTTP status codes**. `409` appears nowhere, because "conflict" is a fact about HTTP and "this class is full" is a fact about the studio. That's what lets the CSV importer report a useful error and the waitlist job log a useful reason — neither of them has a status code to return.

The function takes data and returns a verdict. Eight branches, eight tests, each one an object literal, all of them running in under a millisecond with no setup. The economics that kept those tests from being written in the Problem section are now different.

### The port and the use case

```ts
// application/bookClass.ts
import { canBook, type Refusal, type Plan } from "../domain/booking";

export interface BookingStore {
  loadContext(memberId: string, classId: string): Promise<{
    membershipActive: boolean; plan: Plan; email: string;
    capacity: number; seatsTaken: number; alreadyBooked: boolean;
    upcomingBookings: number; className: string; startsAt: Date;
  } | null>;

  insert(b: { memberId: string; classId: string; startsAt: Date }): Promise<Booking>;
}

export interface Notifier {
  bookingConfirmed(email: string, className: string): Promise<void>;
}

type Deps = { store: BookingStore; notify: Notifier };

export async function bookClass(
  { store, notify }: Deps,
  cmd: { memberId: string; classId: string },
): Promise<{ ok: true; booking: Booking } | { ok: false; refusal: Refusal }> {
  const ctx = await store.loadContext(cmd.memberId, cmd.classId);
  if (!ctx) return { ok: false, refusal: { reason: "class_not_found" } };

  const refusal = canBook(ctx);
  if (refusal) return { ok: false, refusal };

  const booking = await store.insert({ ...cmd, startsAt: ctx.startsAt });
  await notify.bookingConfirmed(ctx.email, ctx.className);

  return { ok: true, booking };
}
```

`BookingStore` is declared here, by its consumer. It has two methods, not the whole of Prisma, and `loadContext` returns exactly the fields `canBook` asks for — which means the adapter can satisfy it with one hand-written join instead of four round trips. An interface owned by the caller gets shaped by the caller's needs; one owned by the ORM gets shaped by the ORM's.

Three problems are visible in these fifteen lines, and none of them were created by the layering — they were hidden by the original handler and are now merely legible.

**There's a race.** `canBook` reads `seatsTaken`, then `insert` writes. Two members booking the last seat concurrently both pass the check. Structure does not fix this; a unique constraint on `(classId, memberId)` and a conditional insert that fails when the class is full do. The useful thing about the port is that the check now has an obvious single place to live.

**Nothing here defines a transaction.** The use case owns the boundary conceptually, but the database is behind an interface, so the layer that decides what's atomic can't open a transaction without knowing about the layer that has one. The usual resolutions are a `withTransaction(fn)` method on the port, or a unit-of-work object passed through (Module 2.5, Part 5). Whichever you pick, pick deliberately — this is the most common place a clean-looking layered design quietly loses atomicity.

**The email is a dual write.** Inside a transaction, a rollback sends a confirmation for a booking that doesn't exist. Outside it, a crash between commit and send loses the email permanently. There is no arrangement of these two lines that's correct, which is why the transactional outbox exists (Modules 10 and 37).

### The edges

```ts
// infrastructure/prismaBookingStore.ts
export const prismaBookingStore: BookingStore = {
  async loadContext(memberId, classId) { /* one query, mapped to the shape above */ },
  async insert(b) { return prisma.booking.create({ data: b }); },
};
```

```ts
// presentation/http/bookings.ts
const STATUS: Record<Refusal["reason"], number> = {
  class_not_found: 404,
  membership_inactive: 403,
  class_full: 409,
  already_booked: 409,
  plan_limit_reached: 409,
};

app.post("/classes/:id/bookings", async (req, res) => {
  const result = await bookClass(deps, {
    memberId: req.session.memberId,
    classId: req.params.id,
  });

  if (!result.ok) return res.status(STATUS[result.refusal.reason]).json({ error: result.refusal });
  res.status(201).json(toResponse(result.booking));
});
```

The handler is now six lines, and every one of them is about HTTP. `STATUS` is the entire translation between the domain's vocabulary and the protocol's — and because `Refusal` is a discriminated union, adding a new refusal reason makes TypeScript demand a status code for it rather than letting it fall through as a 500.

The admin panel, the importer, and the waitlist job all call `bookClass` with different `Deps`. When the basic-plan limit changes from three to two, it changes in `PLAN_LIMITS`, once.

## Further Reading

- **Martin Fowler, _Patterns of Enterprise Application Architecture_ (Addison-Wesley, 2002).** The chapters on Domain Model, Transaction Script, Service Layer, and Active Record. Old, and still the most useful thing written on when each shape is appropriate.
- **Alistair Cockburn, "Hexagonal Architecture" (alistair.cockburn.us, 2005).** The original. Short, and clearer than most of what has been written about it since.
- **Jeffrey Palermo, "The Onion Architecture" (2008), parts 1–4.** The same idea presented as rings, with the dependency rule stated explicitly.
- **Robert C. Martin, "The Clean Architecture" (2012) and _Clean Architecture_ (2017).** The most widely read version. Read the blog post first; the book adds the SOLID framing and a lot of opinion.
- **Vaughn Vernon, _Implementing Domain-Driven Design_, chapter 4 ("Architecture").** Layers, hexagonal, CQRS, and event-driven treated as one continuum in one chapter, which is exactly the right way to see them.
- **Gary Bernhardt, "Boundaries" (talk, 2012).** Functional core, imperative shell. Half an hour, and it makes the testability argument more convincingly than any amount of prose about interfaces.
- **Martin Fowler, "AnemicDomainModel" (bliki, 2003).** Two pages on the failure mode described in Trade-offs.
- **Jimmy Bogard, "Vertical Slice Architecture" (jimmybogard.com, 2018).** The case against uniform layering, from someone who spent a decade building layered systems.
- **Scott Wlaschin, _Domain Modeling Made Functional_ (Pragmatic Bookshelf, 2018).** F#, but the ideas transfer directly to TypeScript: making illegal states unrepresentable is a stronger form of what `canBook` above is doing by hand.

A Java sibling would be worth writing and would not be a translation. Spring inverts the usual tension: the framework pushes you into layers by default (`@Service`, `@Repository`, `@Controller`), so the folders are free — but Spring Data generates the repository implementation *from* the interface, which means the port is no longer yours. Its method names are a query DSL, its return types are JPA-shaped, and `@Transactional` puts the transaction boundary in an annotation on the service method rather than in code the use case controls. That produces a genuinely different set of trade-offs around the two problems flagged above, and a different set of ways to get it wrong. Not yet written.

---

The habit worth carrying out of this article is a one-line test you can run on any codebase in thirty seconds: **open the file containing your most important business rule and read its import list.** If it imports the ORM, the web framework, or the email client, those rules can only run the way that infrastructure runs them — and every future entry point, every fast test, and every provider change is priced accordingly. The number of layers was never the question.
