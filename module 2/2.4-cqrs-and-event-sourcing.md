# CQRS and Event Sourcing

_Module 2.4 — Software Architecture Patterns_

## The Problem

An expense-management product. Employees submit expenses, managers approve them, finance reimburses them, and the whole thing has to survive an audit.

Two complaints arrive in the same sprint, and they look unrelated.

### The dashboard is slow, and fixing it keeps breaking other things

The main screen shows an employee's last fifty expenses: date, merchant name, category, amount in the employee's currency and in the company's, approval status, approver's display name, and a running total against their monthly budget.

The query behind it joins six tables and takes 900 ms. It runs on every page load. Reads outnumber writes roughly 400 to 1 — an employee submits a handful of expenses a month and refreshes that page dozens of times a week.

Three attempts to fix it, in order:

The team adds four indexes. Reads get faster. The bulk import that finance runs monthly goes from four minutes to eleven, because every insert now maintains four more index entries, and the migration that added them locked the table for ninety seconds in production.

Then someone notices the join to `users` exists only to get the approver's name, which never changes. So `approverDisplayName` gets copied onto the expense row. It works. Six weeks later a second field is copied for the same reason, then a third, and now the `Expense` class — the one that Module 2.3 would call an aggregate root, the one that enforces "an approved expense cannot be edited" — has five fields on it that exist purely because a screen wanted them and that no business rule will ever read. The write model is being deformed by read requirements.

Then reporting gets moved to a read replica. This helps until finance's month-end report starts running, at which point the replica falls behind by eight minutes and employees start seeing expenses they submitted vanish and reappear.

Nothing here is a mistake. Each step is what you'd do. The underlying situation is that **the shape that's good for enforcing rules and the shape that's good for answering questions are different shapes**, and one table is being asked to be both.

### Nobody can explain how a number got that way

An employee disputes a reimbursement. Their February total says £1,847.20. They believe it should be £1,912.00.

Finance opens the database. `expense_totals.february_2026 = 184720`. That's all the row says. The system stores the conclusion and nothing about how it was reached.

There is an audit log. It was added in year two, it's written by application code, and it is missing entries from the bulk importer and from the admin correction tool, because whoever wrote those forgot. There's also an `updated_by` column, which tells you who touched a row last and nothing about who touched it before that.

Then it gets worse. The company changed its mileage rate on 1 March. Finance asks: what would February's totals have been under the new rate? The answer is unobtainable, because the February rows store computed amounts, and the inputs that produced them were overwritten.

The common thread: **`UPDATE` is destructive.** Every write keeps the consequence and throws away the fact. Once `balance = 100` becomes `balance = 80`, the reason — a withdrawal? a fee? a correction of an earlier mistake? — exists only if somebody separately remembered to record it somewhere else, in a place nothing enforces.

Two problems, two different answers, and they're constantly taught as one thing.

## What It Is

**CQRS — Command Query Responsibility Segregation.** Use one model to change state and a different model (or several) to read it. Commands go through the rich write model that enforces invariants. Queries go to read models shaped exactly like the thing asking for them — flat, denormalized, no domain objects. The dashboard gets a table that is literally the dashboard.

**Event sourcing.** Store the sequence of things that happened as the system of record, and derive current state by replaying them. The log is the truth; state is a cache of the log.

```
  AccountOpened(GBP) → Deposited(500) → Withdrawn(120) → FeeCharged(2.50)
        │                    │               │                │
        ▼                    ▼               ▼                ▼
     0.00                 500.00          380.00           377.50
                                                        ↑ current state,
                                                          derived not stored
```

Nothing was overwritten, so every intermediate value is still available, and so is the reason for every transition.

### What these are not, and how they relate

**CQRS and event sourcing are independent.** You can use either without the other, and the first is far more common on its own. CQRS with a perfectly ordinary `UPDATE`-based database is a normal, unremarkable design that many systems should adopt. Event sourcing does create real pressure toward CQRS — once your storage is a log, answering "show me fifty expenses sorted by date" by replaying streams is untenable, so you build read models, and that *is* CQRS — but the dependency runs one way and only one way. If you take one thing from this article: **you are allowed to do CQRS without event sourcing, and you probably should.**

**CQRS is not CQS.** Command-Query Separation is Bertrand Meyer's method-level rule: a method either changes state or returns a value, not both. CQRS lifts the same instinct up to the model level. Useful lineage, different scope.

**Event sourcing is not "publishing events."** A system that emits `ExpenseApproved` to Kafka after committing an `UPDATE` is event-*driven*, not event-*sourced*. The distinction is where the truth lives: in event-driven systems the database is authoritative and events are notifications; in event sourcing the events are authoritative and everything else is derived. Teams routinely believe they've adopted event sourcing when they've adopted message publishing, and they get none of the audit properties they were after — because if the publish fails, or a consumer is missing, the history has a hole and the database doesn't care.

**CQRS does not mean two databases**, and it does not inherently mean eventual consistency. Both are options further along a spectrum, covered under How to Achieve It.

## Recognizing the Problem

**You want CQRS when:**

- Reads and writes differ by orders of magnitude in volume, in shape, or in both.
- Indexes added for reporting have made writes slower, or you're now reluctant to add an index at all.
- Fields exist on your domain objects only because a screen needed them.
- The slowest query in the application is a six-table join that feeds one page.
- You maintain a denormalized "summary" table updated by triggers, by a cron job, or by hand.
- Different clients — mobile, web, CSV export, a partner API — each want the same data in a different shape, and you're building mappers for all of them out of the same objects.
- Reporting was moved to a replica and replica lag is now a user-facing bug.

**You want event sourcing when:**

- Someone asks why a value is what it is and you cannot answer from the database.
- You have an audit log maintained by application code, and you know it's incomplete.
- You've added `previous_value`, `changed_by`, or a history table with triggers — you're building a partial event log, badly.
- Regulators, auditors, or finance ask for point-in-time reconstruction: what did this look like on 31 December?
- The business asks questions about *transitions* rather than states: how many expenses were rejected and then resubmitted? How long between submission and approval, historically?
- A rule changed and someone wants to know what the numbers would have been under the old one, or under the new one applied retroactively.
- A bug corrupted data and there's no way to determine what it was before.

The two lists overlap in exactly one place: both are signals that one table is being asked to do a job it's badly shaped for. Beyond that they're separate diagnoses.

## How It Works

### CQRS

The write side stays as Module 2.3 described it: aggregates, invariants, one transaction per aggregate, a repository per root. It exists to make illegal states impossible. It is not optimized for reading and shouldn't be.

The read side is a different thing entirely. Read models are per-question, not per-entity: `employee_dashboard_rows`, `month_end_report_lines`, `pending_approvals_for_manager`. They're flat, pre-joined, and carry the exact columns the consumer displays. Queries against them don't load domain objects, don't go through repositories, and don't enforce anything — they have nothing to enforce.

The interesting question is how the two stay in agreement, and there's a spectrum:

```
  same tables,          purpose-built           separate store,
  query bypasses        read tables,            updated async
  the domain            same transaction        by a projector
  ──────────────────────────────────────────────────────────────▶
  strongly consistent   strongly consistent     eventually consistent
  no new infra          no new infra            new infra, new failure modes
```

**Eventual consistency enters only at the right-hand end.** The first two columns are CQRS, they're fully consistent, and they cost approximately nothing. This matters because "CQRS means your reads are stale" is one of the most common and most damaging misconceptions about it.

Once you *are* at the right-hand end, three mechanisms become mandatory rather than optional:

**Idempotent, ordered projectors.** Events will be delivered at least once and occasionally out of order. The standard fix is to store the projector's last-processed position *in the same transaction* as the projection update, so replaying a batch is harmless and progress can never be recorded for work that didn't happen.

**Replay.** Projections are derived, so they should be rebuildable from scratch. This is what lets you fix a projection bug, add a column, or spin up a new read model — delete it and rebuild. A projection you can't rebuild has quietly become a second system of record.

**A read-your-writes answer.** The user submits an expense and the list doesn't show it yet. The options, roughly in order of cost: have the command return the resulting data so the UI can display it directly; render optimistically from what the user just typed; return a version token and have the query wait until the projection has reached it; or design the interaction so the user isn't looking at the list at that moment. Pick one deliberately. "It'll be fine, it's only 200 ms" is how you get a bug report six months later from a customer whose projector was lagging.

### Event sourcing

**Writing.** Load the event stream for one aggregate, fold it into current state, decide whether the command is allowed, and append new events — with an expected-version check, so that if another writer appended in the meantime, the append fails and you retry. Optimistic concurrency comes for free and lands exactly where Module 2.3 said it belonged: on the aggregate.

**Reading current state.** Fold the events. That's it — the entire mechanism is a `reduce`. Long streams get expensive, so periodically store a snapshot and fold only the events after it. Snapshots are an optimization of one line of code, and they bring their own invalidation problem when the fold logic changes; Module 37 handles that properly.

**Correcting mistakes.** You don't edit or delete an event. You append a compensating one — `FeeReversed`, `AmountCorrected` — the way a ledger never erases a line, it posts a counter-entry. This is unfamiliar at first and then becomes the most obviously-right part of the model, because "we fixed the data" stops being a thing that happens silently.

**Answering queries.** You build read models by projecting the event stream. This is the pressure toward CQRS, and it's not optional: the alternative is loading every stream and folding it to answer a list query.

**The hardest part** is event schema versioning. Events are immutable and permanent, so the shape you wrote in 2021 is still in the log and still has to be foldable in 2029. You cannot `ALTER` an event. The strategies — upcasting on read, weak schemas, versioned event types — are a whole subject, and Module 37 covers them. Know now that this is the ongoing cost, not the initial build.

## When It's Appropriate

**CQRS**, with the read/write split at whatever depth the pressure justifies:

- Read and write volumes genuinely diverge: 3,000 reads/sec against 15 writes/sec, and they're contending for the same indexes.
- The write model is genuinely rich — real invariants, a real aggregate — *and* the reads want flat shapes. If your write model is anemic CRUD, the two models will be the same model and you'll have split nothing.
- Reads need a different storage technology: full-text search in Elasticsearch (Module 12), sub-millisecond lookups in Redis (Module 13), analytical rollups in a columnar store, while writes stay in Postgres.
- Several consumers want the same underlying data in genuinely different shapes, and the mapping code between them has become a significant share of the codebase.

**Event sourcing:**

- Audit is a functional requirement with a regulator attached: financial services, insurance, healthcare, anything with a retention mandate.
- The history has direct business value — the product sells analysis of transitions, or the business routinely recalculates the past under new rules.
- The domain's own mental model is already a log. Accounting ledgers, order lifecycles, insurance policy endorsements, warehouse inventory movements, version control. In these, event sourcing isn't an imposed pattern; it's what the domain experts already draw on whiteboards.
- Debugging value is high: replaying the exact sequence that produced a bad state, in a test, is an unusually powerful capability in complex domains.
- Temporal questions are routine rather than exceptional.

Note the shape of that list: it's narrow, and every item names something the business asks for. That's deliberate.

## When It's Unnecessary or Overkill

**CQRS applied uniformly.** The same lumpiness argument as Module 2.2. Split the two or three areas where reads and writes genuinely diverge; leave the settings page alone. A codebase with a command model and a query model for every entity has doubled its surface area to solve a problem three entities had.

**CQRS at low scale.** Forty requests per second against a well-indexed table is not a problem that needs an architecture. Module 1.2's arithmetic applies: check the number before designing for it.

**Async projection where a view would do.** If the read model can be a database view or a materialized view refreshed on commit, take that. It's CQRS, it's strongly consistent, and it's zero new infrastructure.

**Event sourcing for typical business CRUD.** This is the big one. The costs below are permanent and substantial, and for a system whose interesting questions are all about current state, there's little to show for them.

**Event sourcing adopted "for audit" when audit is all you need.** If the requirement is "we must be able to show who changed what, when," there are three cheaper answers: an append-only audit table written in the same transaction as the change; database-native system-versioned/temporal tables; or change data capture streaming your write-ahead log somewhere durable (Module 38). All three give you history without restructuring the application. What they don't give you is *intent* — CDC can tell you `status` went from 2 to 3, but only an event can tell you it was because the manager approved it rather than because the nightly job auto-approved it. If intent matters, that's an argument for events. If it doesn't, you were about to pay a great deal for a log you could have had for a week's work.

**Event sourcing with a right-to-erasure requirement and no plan.** GDPR's deletion right collides directly with an immutable log. The workable answer is crypto-shredding — personal data encrypted with a per-subject key, the key destroyed on request — which needs designing in from the start, not retrofitted. Module 34 covers the obligation; the point here is that "we'll figure out deletion later" is not a viable position.

**Event sourcing without the operational appetite.** Versioning, replay, projection rebuilds, snapshot invalidation, and onboarding are ongoing work forever. A team that can't currently keep a cron job healthy should not take this on.

**Event-sourcing half the system.** The worst place to sit is a codebase where some aggregates are event-sourced and the rest aren't, with no principle governing which. If you adopt it, adopt it for *one* aggregate where the history is the product — the ledger, the policy, the order — and leave the rest as ordinary CRUD deliberately and explicitly.

## Trade-offs

**CQRS costs:**

- Two models to keep conceptually aligned. A new field often means changing both, plus the projection between them.
- Projections are code, and code fails: they crash, lag, and drift. "The dashboard is wrong" now has three possible causes instead of one.
- Once asynchronous, eventual consistency becomes a product concern, not just an engineering one — somebody has to decide what the screen says during the gap.
- Staleness bugs are hard to reproduce, because they depend on timing you don't control locally.
- Rebuilding projections needs a mechanism you have to build and keep working before you need it.

**Event sourcing costs:**

- **Your events are your schema, permanently.** Getting them wrong early — too fine-grained, too coarse, carrying data that should have been a reference — is expensive in a way a wrong column isn't, because you can't migrate what you've promised never to change.
- Ad-hoc querying disappears. There is no `SELECT * FROM accounts` for support, ops, or an analyst. Everything anybody wants to look at must exist as a projection, including the ones you didn't anticipate.
- Streams grow without bound, so snapshots become necessary, and snapshots need invalidating whenever the fold changes.
- Deletion is genuinely hard.
- Every engineer who joins has to learn it, and the local mental model ("read the row") no longer works anywhere.
- Storage grows monotonically, which is usually cheap and occasionally not.

One framing that helps with both: these are *capability* trades, not performance trades. CQRS buys you the ability to shape reads independently. Event sourcing buys you the ability to answer questions about the past. Neither is faster in any general sense, and adopting either for speed alone usually disappoints.

## Alternatives

**Read replicas.** Scale reads without splitting models. Cheap, well-understood, and sufficient surprisingly often — though as the Problem section showed, it doesn't help when the query itself is the problem.

**Database views and materialized views.** The lowest-cost read model in existence. A materialized view refreshed concurrently gives you a pre-joined, indexed, purpose-shaped read model with no application code and no projector to operate. This should be the first thing tried, and for many systems it's also the last.

**Denormalized columns maintained in the same transaction.** A `running_total` updated alongside the write. Strongly consistent, trivially understood, and adequate until the number of such columns gets embarrassing.

**Caching.** If the read is expensive but rarely changes, a cache with a sensible invalidation story may close the gap entirely (Module 13).

**A dedicated search or analytics store** fed by CDC rather than by application-level projections (Modules 12 and 38). You get a differently-shaped read model without the write side knowing anything about it.

**An events table alongside normal state — "event sourcing lite."** Keep ordinary tables as the system of record, *and* write a domain event row in the same transaction as every meaningful change. You get intent, ordering, a real audit trail, and something to project from — without giving up ad-hoc SQL, without a fold, and without permanent event versioning obligations. It isn't event sourcing, because the state is authoritative and the log is derived rather than the reverse, so the log can drift if someone writes state without an event. In exchange, it costs a week instead of a quarter. For the large majority of teams who read about event sourcing and find it appealing, this is the thing they actually wanted.

## How to Achieve It

**L0 — One model.** All reads and writes go through the domain objects and the ORM.

**L1 — Split the code paths.** Queries stop going through the domain and hit the database directly, returning shapes built for their consumer. Same database, same tables, no new infrastructure, no consistency change. This is genuinely CQRS, it takes an afternoon per query, and it removes most of the pressure that was deforming the write model.

*Next when:* the queries are direct but still slow, because the tables aren't shaped for them.

**L2 — Purpose-built read models, same database.** Materialized views, or denormalized tables written in the same transaction as the command. Still strongly consistent. Still no new moving parts.

*Next when:* reads need a different storage technology, or the maintenance cost inside the write transaction has become the bottleneck.

**L3 — Separate store, asynchronous projection.** Writes to Postgres, reads from Elasticsearch or Redis, kept current by a projector consuming events. This is a real step change: eventual consistency arrives, and with it idempotent projectors, offset tracking, replay tooling, lag monitoring, and a read-your-writes decision. Take this rung deliberately, not by drift.

*Next when:* you need the history itself, not just a differently-shaped present.

**L4 — Event-sourced write side.** The log becomes the system of record for one aggregate. Not for the system — for one aggregate, chosen because its history has business value.

Most systems should stop at L1 or L2. Stopping is a legitimate outcome at every rung, and nothing about the earlier steps commits you to the later ones.

## Implementation

TypeScript, because a discriminated union expresses the event model directly and the compiler enforces exhaustiveness over it — which makes the central idea, that state is a fold over events, visible in about fifteen lines.

Deliberately short. Event sourcing invites reference implementations; Module 37 is where the depth belongs.

### Events, and the fold

```ts
// The storage format. These values outlive every version of the code that reads them.
type AccountEvent =
  | { type: "Opened";      currency: "GBP" | "USD"; at: string }
  | { type: "Deposited";   minorUnits: number; reference: string; at: string }
  | { type: "Withdrawn";   minorUnits: number; reference: string; at: string }
  | { type: "FeeCharged";  minorUnits: number; schedule: string; at: string }
  | { type: "Frozen";      reason: string; at: string };

type Account = {
  opened: boolean;
  currency: "GBP" | "USD";
  balanceMinor: number;
  frozen: boolean;
};

const EMPTY: Account = { opened: false, currency: "GBP", balanceMinor: 0, frozen: false };

function apply(s: Account, e: AccountEvent): Account {
  switch (e.type) {
    case "Opened":     return { ...EMPTY, opened: true, currency: e.currency };
    case "Deposited":  return { ...s, balanceMinor: s.balanceMinor + e.minorUnits };
    case "Withdrawn":  return { ...s, balanceMinor: s.balanceMinor - e.minorUnits };
    case "FeeCharged": return { ...s, balanceMinor: s.balanceMinor - e.minorUnits };
    case "Frozen":     return { ...s, frozen: true };
  }
}

const rebuild = (events: AccountEvent[]) => events.reduce(apply, EMPTY);
```

That last line is the whole of event sourcing. Snapshots are an optimization of it: fold from a stored state at position N instead of from `EMPTY` at zero.

The union is doing real work beyond documentation. With `noImplicitReturns` on, adding a sixth event type makes `apply` fail to compile until it's handled — the compiler will not let a new fact enter the log without someone deciding what it means for state. That guarantee is the reason this article is in TypeScript, and it's worth noticing how much of the design's safety is resting on it.

### The command side

```ts
async function withdraw(
  store: EventStore,
  cmd: { accountId: string; minorUnits: number; reference: string },
): Promise<number> {
  const { events, version } = await store.read(cmd.accountId);
  const account = rebuild(events);

  if (!account.opened) throw new NoSuchAccount(cmd.accountId);
  if (account.frozen) throw new AccountFrozen(cmd.accountId);
  if (account.balanceMinor < cmd.minorUnits) {
    throw new InsufficientFunds(account.balanceMinor, cmd.minorUnits);
  }

  // Fails if anything else appended to this stream since we read it.
  await store.append(cmd.accountId, version, [
    { type: "Withdrawn", minorUnits: cmd.minorUnits, reference: cmd.reference,
      at: new Date().toISOString() },
  ]);

  return version + 1;
}
```

Three things here that aren't obvious from the shape:

**`version` is the concurrency control.** Two concurrent withdrawals both read version 7, both check the balance, both try to append at 8; one wins and the other retries against the new state. This is Module 2.3's optimistic locking, except it isn't a column someone remembered to add — the stream position *is* the version, so the check is structural.

**No balance is stored anywhere.** The overdraft rule reads a value computed from history. There's no row to get out of sync with the events, which is the same trick as deriving `total()` from lines in Module 2.3, applied to the whole aggregate.

**The returned version is the read-your-writes token.** Hand it to the client, and the client can ask the query side for data at least that fresh — or the UI can simply display what it knows happened.

### The read side

```ts
// Projector. Runs behind the write side, consuming events in order.
async function project(batch: { position: bigint; streamId: string; event: AccountEvent }[]) {
  await db.transaction(async (tx) => {
    for (const { streamId, event } of batch) {
      switch (event.type) {
        case "Opened":
          await tx.exec(`insert into account_summary (account_id, currency, balance_minor)
                         values ($1, $2, 0) on conflict do nothing`, [streamId, event.currency]);
          break;
        case "Deposited":
        case "Withdrawn":
        case "FeeCharged":
          await tx.exec(`update account_summary
                            set balance_minor = balance_minor + $1, last_activity_at = $2
                          where account_id = $3`,
                        [signed(event), event.at, streamId]);
          break;
        case "Frozen":
          await tx.exec(`update account_summary set frozen = true where account_id = $1`, [streamId]);
      }
    }

    // In the SAME transaction as the writes above.
    await tx.exec(`update projection_offsets set position = $1 where name = 'account_summary'`,
                  [batch.at(-1)!.position]);
  });
}
```

The offset update being inside the transaction is the entire correctness argument for the projector. Delivery is at-least-once, so the same batch can arrive twice; because progress is only recorded when the effects commit, a redelivered batch either finds work already done or redoes it atomically. That converts at-least-once delivery into exactly-once *effect*, which is the only version of "exactly once" that's actually achievable.

And the query that replaces the six-table join from the Problem section:

```ts
const rows = await db.query(
  `select * from account_summary where account_id = $1`, [accountId]);
```

No aggregate, no repository, no domain object. Nothing to enforce, because enforcement already happened on the way in. This is the part that makes CQRS worth it and the part teams skip when they build the command side first and then get tired.

## Further Reading

- **Greg Young, "CQRS Documents" (2010).** The origin, free, and still the clearest statement of what the separation is and isn't.
- **Greg Young, _Versioning in an Event Sourced System_ (Leanpub, free).** The problem that dominates years two through ten of an event-sourced system. Read this *before* deciding to adopt, not after.
- **Udi Dahan, "Clarified CQRS" (2009).** Written specifically to slow down the hype, by one of the people who started it. The best available antidote to adopting this for the wrong reasons.
- **Martin Fowler, bliki entries "CQRS", "EventSourcing", and "CommandQuerySeparation".** Short, and useful for handing to someone who needs the distinctions in five minutes.
- **Martin Kleppmann, _Designing Data-Intensive Applications_, chapter 11.** Stream processing, derived data, and the general principle that a database can be understood as a fold over a log. The best conceptual framing of why projections work.
- **Martin Kleppmann, "Turning the Database Inside Out" (talk, 2015).** The same idea in forty minutes.
- **Oskar Dudycz, event-driven.io.** Consistently practical writing on event sourcing, including several posts arguing against adopting it. "Should you throw away your database?" and the event-versioning material are the ones to start with.
- **Vaughn Vernon, _Implementing Domain-Driven Design_, chapter 4 and appendix A.** Connects this directly to the aggregates from Module 2.3.
- **PostgreSQL documentation — materialized views and `REFRESH MATERIALIZED VIEW CONCURRENTLY`.** The L2 rung, in full, for free.
- **Module 37** for event store design, snapshotting, and replay at depth; **Module 38** for CDC as the alternative history mechanism.

A Go sibling would reveal something this TypeScript version conceals. Almost all of the safety above rests on discriminated unions and exhaustiveness checking — the compiler refusing to let an unhandled event type through `apply`. Go has no sum types. Events become an interface satisfied by structs, the fold becomes a type switch, and the compiler will say nothing at all when a new event type is added and one of four projectors forgets to handle it. That pushes the design somewhere genuinely different: a registry keyed by event name, explicit tests that assert every registered type is handled, and a much heavier reliance on the deserialization boundary — where unknown event names have to be an error rather than a silently ignored default. Worth writing for that reason alone. Not yet written.

---

The habit worth carrying out of this article is smaller than either pattern: **notice what your writes destroy.** Every `UPDATE` keeps a conclusion and discards the reason for it, and in most systems that's fine — nobody will ever ask. The engineering judgment is knowing which handful of values in your system are the ones somebody will eventually need explained, and making sure that for those, the explanation is written down somewhere by the same code that made the change, rather than by a developer who remembered to.
