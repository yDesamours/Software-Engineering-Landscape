# Development Environment

_Module 3.2 — Project Setup & Development Environment_

## The Problem

A twelve-line change. Here is what it actually cost.

```
  09:14  Write the code. Run it locally. Works.
  09:20  Push.
  09:31  CI fails: unused import.
  09:33  Fix, push.
  09:46  CI fails: formatting. Their editor indents with 2 spaces, the repo uses 4.
  09:48  Fix, push.
  10:01  CI passes. Open PR.
  11:40  Reviewer leaves six comments. Four are about naming and import order.
  14:20  Fix, request re-review.
  Next day, 10:15  Merged.
  Next day, 10:32  A test fails on main. It passed locally, because their
                   Postgres is 15 and CI's is 16.
```

Six hours of elapsed time and four context switches, of which roughly eleven minutes was the actual work. Nothing here is anyone's fault. Every individual step is what you'd do.

Now the second scene. A new engineer joins. The README says: install Node, Postgres, and Redis, run the migrations, start the server. They have Node 22 (the project needs 20), Homebrew's Postgres 17 (the project needs 16), and a Redis that happens to be fine. Three days to first commit, two colleagues pulled in to help, and one of the fixes — an environment variable nobody had documented — was found by reading a colleague's shell history.

Their machine is now *almost* the same as everyone else's. For the next two years, a small number of tests will behave differently for them, and nobody will ever work out why.

Then the third scene, which is the one that does the real damage.

Over eighteen months the team added tools to fix all of this. There's a linter now. It reports 412 warnings, all pre-existing, so nobody reads its output and new warnings arrive unnoticed. There's a pre-commit hook that runs the full test suite and takes 40 seconds, so everybody has `--no-verify` in their muscle memory — including for the formatter check that takes 200 milliseconds. CI got a security scan that produces a false positive every third run, so the team learned to re-run CI rather than read it.

Each of those was added by someone trying to help. Each is now something to route around.

Three distinct failures are tangled here:

- **Feedback arrives late**, so mistakes cost a context switch instead of a keystroke.
- **Machines disagree**, so results are non-deterministic and "works on my machine" is literally true.
- **Checks lost trust**, and a check nobody reads is worse than no check, because it occupies the slot where a working one could have gone.

## What It Is

The development environment is the machinery that determines **when you find out you're wrong, and whether everyone finds out the same thing.**

The useful frame is loops. The **inner loop** is edit → check → know, and it runs hundreds of times a day. The **outer loop** is push → CI → review → merge → deploy, and it runs a few times a day at best. Every check you own sits somewhere on a ladder between them, and the cost of a defect roughly multiplies at each rung it survives:

```
  editor, as you type       ~0 s       free
  on save                   ~1 s       free
  pre-commit hook           ~5 s       you're still holding the context
  local test run           ~30 s       you're still holding the context
  CI                      ~10 min      context switch, queue, re-push
  code review               ~4 h       another person's attention
  production                days       customers, incident, rollback
```

The design goal follows directly: **put each check at the earliest rung that can run it reliably, and at exactly one rung beyond that as a backstop.** The backstop exists because local checks are skippable; it should almost never fire, and when it does, that's information about your tooling rather than about the developer.

Three distinctions worth making now, because conflating them causes most of the arguments in this area.

**Formatters are not linters.** A formatter makes deterministic layout decisions — indentation, line breaks, quote style — and has no opinions worth discussing. A linter flags patterns that might be wrong and requires judgment about which rules to enable. The practical consequence: formatting should never be a review comment or a manual fix. It should be applied, silently, by a machine. `gofmt`'s most important contribution to Go was social rather than technical — it ended a category of argument by removing the decision.

**Linters are not type checkers or tests.** They overlap, and the overlap matters: a lint rule enforcing something a type could enforce is a weaker version of the same check, because it can be suppressed with a comment and a type can't. When both are available, prefer the type.

**Containerizing your dependencies is not the same as containerizing your code.** Running Postgres and Redis in Docker while your application runs natively is a cheap, high-value decision. Running your application inside a container too is a much larger decision with real costs. The phrase "Docker for local development" covers both, and they should be decided separately.

## Recognizing the Problem

- CI fails for formatting or lint more often than for tests.
- Most code review comments are about style rather than substance.
- Onboarding to first merged commit takes more than a day.
- Someone says "works on my machine" and is correct.
- `--no-verify` is routine.
- The linter reports hundreds of pre-existing issues, so its output carries no signal.
- Two engineers run the same command and get different results.
- The README's setup section is stale, and each engineer has a private list of undocumented extra steps.
- CI is the first place anyone runs the full test suite.
- A runtime version upgrade requires a coordinated day across the whole team.
- There's a Slack channel for environment problems, and it has recurring questions.

## How It Works

### Formatting: delete the decision

One formatter, as close to zero configuration as the ecosystem allows, applied automatically. Format-on-save in the editor, a pre-commit hook for anyone whose editor isn't configured, and a CI check as the backstop.

The mechanism that makes this stick is that the configuration lives in the repository — `.editorconfig`, a committed editor settings file, the formatter's own config — so a fresh clone is already correct. The mechanism that breaks it is per-developer editor settings that nobody can see.

Adopting a formatter on an existing codebase means one enormous reformatting commit. Do it in isolation, with no logic changes, and then add its hash to `.git-blame-ignore-revs` so `git blame` skips past it. That file costs one line and preserves the history everyone is about to need.

### Linting: the baseline problem

Turning a linter on in a mature codebase produces hundreds of findings. The team fixes none of them, output becomes noise, and new violations arrive invisibly among old ones. The linter is now installed and doing nothing, which is the worst of both.

The fix is a **ratchet**: fail only on *new* violations. Lint the changed lines, or keep a baseline file of known issues that is permitted to shrink but never grow. Existing debt stays visible without blocking anyone, new debt can't be added, and the number goes down as files are touched for other reasons. This is the single most useful technique in this article, and most teams don't know their linter supports it.

The second rule is about severity: **a warning that nobody fixes is noise.** Either the rule is worth failing the build over, or it should be deleted. A permanently-yellow output trains people to ignore the whole thing, including the red.

Worth noting what a linter can do that isn't style: it's where the architectural boundaries from earlier modules get enforced. "The domain layer may not import the database driver" (Module 2.2) and "this module's internals are private" (Module 2.1) are both lint rules, and a lint rule failing the build is exactly what those articles meant by "enforced by something mechanical."

### Hooks: the last cheap checkpoint

Git hooks run on the developer's machine and can be skipped with a flag. That makes them a convenience, never a control — anything that must hold has to also run in CI.

Two design rules follow, and violating either destroys the hook's usefulness permanently:

**Fast.** Under about five seconds. Past that, people start bypassing, and bypassing is a habit rather than a per-case decision — once they've learned `--no-verify`, you've lost the fast checks too.

**Never spuriously failing.** A hook that occasionally blocks a legitimate commit teaches people to distrust it, and the trust doesn't come back.

Practically, that means: run the formatter and the linter on *staged files only*, and leave tests to pre-push or CI. Hooks also aren't shared by git itself — they live in `.git/hooks`, which isn't versioned — so a manager (`lefthook`, `husky`, `pre-commit`) or a committed `core.hooksPath` is needed to make them a team artifact rather than a personal one.

Some teams skip client-side hooks entirely, relying on editor integration plus fast CI. That's a legitimate position, especially where CI is under three minutes.

### Making machines agree

A spectrum, in increasing order of reproducibility and of cost:

| Approach | Reproduces | Inner-loop cost |
|---|---|---|
| README instructions | nothing, reliably | none |
| Version managers (`.nvmrc`, `.tool-versions`, toolchain directives) | language versions | none |
| Dependencies in Compose, code native | services, versions, seed data | small |
| Everything in containers / dev containers | most of the machine | moderate to large |
| Nix or similar declarative environments | nearly everything | large upfront |
| Cloud dev environments | everything, centrally | network-bound |

The central tension: **reproducibility and inner-loop speed pull against each other.** Containers make machines identical and make file watching, debugger attachment, and rebuild times worse — sometimes dramatically, on macOS, where bind-mounted source directories are notoriously slow.

For most teams the optimum sits on the third row: language version pinned by a file in the repo, dependencies in Compose with pinned image tags, application code running natively. That gets the failures that actually happen — wrong Postgres version, missing Redis, different timezone — without paying the file-watching tax.

Two details that decide whether this works in practice:

**Health conditions, not just startup order.** `depends_on` without a health condition starts the app before Postgres is accepting connections, and everyone quietly learns to run the command twice. That's a broken environment people have adapted to.

**Seed data is part of the environment.** If everyone's database has different rows, results still differ between machines, just more subtly. A committed seed script matters as much as the Compose file.

### The editor

Editor choice is personal, and mandating one produces resentment for little gain. The useful line is about output rather than tools:

**Anything that affects what lands in a commit is team property; anything that only affects your experience is yours.** Formatter config, lint config, `.editorconfig`, and language-server settings go in the repository. Keybindings, themes, and which editor you opened do not.

A recommended-extensions list is the right middle ground: it makes the team's setup discoverable without making it compulsory.

### Where each check belongs

|  | Editor | Pre-commit | CI |
|---|---|---|---|
| Format | apply on save | apply to staged | verify (should never fail) |
| Lint | show inline | block, changed files only | verify, ratcheted |
| Type check | show inline | — | block |
| Unit tests | run on demand | — | block |
| Integration tests | — | — | block |
| Security / dependency scan | — | — | block |

The rows get less frequent as they get more expensive. The one to look at hardest is the top-right cell: if the CI format check fires regularly, the two cells to its left aren't working, and fixing those is more valuable than anything else in the table.

## When It's Appropriate

This is a question of degree, not of whether, so the useful framing is what to adopt at what point.

**From day one, on any project including solo ones:** a formatter and a pinned language version. Both are close to zero cost and both prevent a category of problem outright.

**As soon as there's a second contributor:** a linter with a ratchet, and committed editor config.

**As soon as there's a database or a second service:** dependencies in Compose with pinned tags and a seed script. The arithmetic here is easy — a team of twelve losing an average of ten minutes a week each to environment differences is two person-days a month.

**When CI is slow or expensive:** pre-commit hooks for the checks that fail most often. If your pipeline is fifteen minutes and thirty PRs a day hit lint failures, you're burning hours of wall-clock time on something a five-second hook catches.

**When onboarding cost is measurable:** dev containers. A team hiring steadily, or working with contractors who need to be productive in a day, gets real value from a clone-and-run environment. A stable team of three that hasn't hired in two years does not.

**When you've been burned by drift repeatedly and someone will own it:** declarative environments like Nix. The reproducibility is genuinely better than containers. The learning curve is genuinely steep, and it needs a champion who'll still be there in a year.

## When It's Unnecessary or Overkill

**Dev containers for a project with no native dependencies.** A single-binary Go service needs a Go toolchain and nothing else. Adding a container layer makes the inner loop slower to solve a problem that doesn't exist.

**Slow pre-commit hooks.** Worth restating as its own item because the damage is disproportionate: a 40-second hook doesn't just fail to help, it teaches the bypass habit and takes the 200-millisecond checks down with it.

**Lint rules that encode one person's taste.** Every rule has an ongoing cost in arguments, suppression comments, and false positives. Rules that catch bugs earn that; rules that enforce a preferred loop construct usually don't.

**Mandating an editor.** You'll get compliance and lose goodwill, for a benefit that committed configuration already provides.

**Bespoke setup tooling.** A hand-rolled `setup.sh` that grows into a small program is a project nobody budgeted for, and it will be subtly broken on someone's machine forever. Prefer boring standard tools with documentation you didn't have to write.

**Containerizing the application on macOS without measuring.** Bind-mount performance is bad enough that teams routinely end up with a twelve-second rebuild loop and treat it as normal. If you do this, measure the inner loop before and after, and be willing to reverse it.

## Trade-offs

**Every check adds latency to the loop it lives in.** A 400-millisecond lint on save is invisible; a four-second one gets disabled. The budget is real and small.

**Tooling is code you now maintain.** Configs drift, plugins break on upgrades, and a formatter's major version bump reformats the entire repository on someone's random Tuesday. Budget for a maintainer, or pick tools with a reputation for stability over ones with the best feature set.

**Duplicated definitions drift.** The same checks running in hooks and in CI means two places to change. The mitigation is that both invoke the *same* script — one definition, two call sites — and it's worth setting up on day one because the alternative is CI surprising people again.

**Reproducible environments reduce flexibility.** The engineer who can't install a profiler inside the container will work around the container, and now their environment differs in an undocumented way. Escape hatches are a feature.

**Ratcheting makes debt permanent-looking.** A baseline that never shrinks is a lie the team tells itself. It needs a review at some interval, or a rule that touching a file means cleaning it.

**Onboarding investment only pays back with turnover.** A week spent on a dev container for a stable team of three may never be recovered.

**And the meta-cost:** development tooling is unusually pleasant to work on, produces visible progress, and has no customer waiting for it. It's one of the easier ways for an engineer to spend a month without shipping anything.

## Alternatives

**Very fast CI instead of local checks.** If the pipeline runs in under three minutes and costs little, pushing everything to it is a coherent strategy: an empty local loop, no hooks, no per-machine configuration to drift. It works best with good caching and a team that doesn't mind the round trip.

**Server-side enforcement instead of client-side hooks.** Branch protection rules and required status checks can't be bypassed, which is the property hooks lack. Slower feedback, stronger guarantee — a fine trade for things that genuinely must hold.

**Cloud development environments.** Codespaces, Gitpod, and similar move reproducibility to a machine you control centrally. Onboarding becomes a URL. The costs are money, a hard dependency on connectivity, and the latency of editing over a network.

**Convention and code review instead of linters.** Works at genuinely small scale with stable membership. Fails at the first hire, because the conventions were never written down.

**A monorepo as the delivery mechanism.** Module 3.1's arrangement means one formatter config, one lint config, one Compose file — configured once rather than N times, and impossible to drift. If you already have one, most of this article becomes a single set of files at the root.

**Choosing a language with less of this problem.** Go ships formatting, vetting, testing, dependency management, and the build tool in the toolchain, with no selection or integration to do. That's the same ecosystem-tax argument Module 1.3 made about stack selection, showing up as a concrete daily cost rather than an abstract one.

## How to Achieve It

**L1 — Formatter and editor config, committed.** One bulk reformat commit, its hash in `.git-blame-ignore-revs`, format-on-save documented. An afternoon, and it removes a whole category of review comment.

*Next when:* people are on different language versions.

**L2 — Pin the language version in a file.** `.nvmrc`, `.tool-versions`, `.sdkmanrc`, a toolchain directive. Near-zero cost, and it makes the version a reviewable change rather than an ambient fact.

*Next when:* setup requires installing a database, or two machines disagree about a service's behaviour.

**L3 — Dependencies in Compose, with pinned tags, health conditions, and a seed script.** Target: clone plus one command gets a running system.

*Next when:* you want to start catching code problems rather than environment ones.

**L4 — Linter with a ratchet.** New violations fail; existing ones are visible and don't block. Include the architectural rules from Modules 2.1 and 2.2 here rather than relying on review to catch them.

*Next when:* CI is regularly failing on things a local check could have caught.

**L5 — Pre-commit hooks, under five seconds, on staged files, installed automatically.** Same script CI runs.

*Next when:* onboarding or native-dependency pain is measurable and recurring.

**L6 — Dev containers or a declarative environment.** The big one. Take it deliberately, with someone owning it.

The target to keep in mind throughout: **clone, one command, running system.** Every rung above is in service of that, and a team that has it has solved most of this article whatever tools they used.

## Implementation

Go, because its toolchain makes two of this article's central mechanisms unusually visible: formatting with nothing to configure, and a linter with a built-in ratchet.

### Dependencies containerized, code native

```yaml
# compose.yaml — services only. The application runs on the host.
services:
  postgres:
    image: postgres:16.4-alpine          # pinned: "16" would drift between machines
    environment:
      POSTGRES_PASSWORD: dev
      POSTGRES_DB: acme
    ports: ["5432:5432"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 2s
      timeout: 3s
      retries: 15
    volumes:
      - ./scripts/seed.sql:/docker-entrypoint-initdb.d/10-seed.sql:ro

  redis:
    image: redis:7.4-alpine
    ports: ["6379:6379"]
```

```makefile
dev: ## clone → one command → running system
	docker compose up -d --wait          # --wait blocks until healthchecks pass
	go run ./cmd/api
```

Three details carry most of the value. The image tags are fully pinned, because `postgres:16` is a moving target and two machines that pulled it a month apart are running different builds. The healthcheck plus `--wait` is what stops the application racing the database — without it, the first `make dev` fails, everyone learns to run it twice, and the environment is quietly broken in a way people have adapted to. And the seed file is mounted into the init directory, so everybody's database has the same rows rather than whatever each person happened to create while debugging.

Note what isn't here: the Go code. `go run` on the host keeps the edit-to-running loop at a second or two, with the debugger attaching normally. Containerizing the application as well would buy a little more reproducibility for a much slower loop — the third-row-versus-fourth-row trade from the table above.

### A linter with a ratchet

```yaml
# .golangci.yml
run:
  timeout: 2m

linters:
  enable:
    - errcheck        # unchecked errors — correctness, not style
    - govet
    - staticcheck
    - depguard        # architectural boundaries, below

issues:
  new-from-rev: origin/main    # ← the ratchet
  fix: false

linters-settings:
  depguard:
    rules:
      domain:
        files: ["**/internal/domain/**"]
        deny:
          - pkg: "database/sql"
            desc: "domain must not know about persistence — see ADR-0004"
          - pkg: "net/http"
            desc: "domain must not know about transport — see ADR-0004"
```

`new-from-rev` is the whole baseline strategy in one line: existing findings are reported but don't fail, new ones do. Two caveats worth knowing before relying on it — it compares against a revision, so a stale local `main` produces confusing results, and it works on changed lines, so a problem introduced by *deleting* code elsewhere can slip past. Neither is a reason to skip it; both are reasons to keep CI's full run as a periodic job rather than dropping it entirely.

The `depguard` block is where Module 2.2's dependency rule stops being an agreement and becomes a build failure. Note the `desc` fields pointing at an ADR: someone hitting this at 11pm gets told both what the rule is and where the reasoning lives, which is Module 2.5's code-links-back mechanism in its most useful form.

Formatting doesn't appear in this file at all, because `gofmt` has no configuration to have an opinion about. That absence is the point — it's the version of "delete the decision" that other ecosystems have to assemble by hand.

### Hooks that call the same script CI calls

```yaml
# lefthook.yml
pre-commit:
  parallel: true
  commands:
    fmt:
      glob: "*.go"
      run: gofmt -l -w {staged_files}
      stage_fixed: true              # re-stage after rewriting
    lint:
      glob: "*.go"
      run: golangci-lint run --new-from-rev=HEAD --fast
```

```makefile
check:                                  # ← CI runs exactly this
	gofmt -l . | tee /dev/stderr | (! read)
	golangci-lint run --new-from-rev=origin/main
	go test ./...
```

Both run on staged files with `--fast`, which keeps the hook comfortably inside the five-second budget; the full suite waits for CI. `stage_fixed` matters more than it looks — without it, the formatter rewrites files that aren't in the commit you just made, and people discover the discrepancy later while confused.

The `check` target is the single definition. CI calls it; a developer can call it before pushing. When someone adds a check, it lands in one place and both call sites get it — which is the difference between a pipeline that mirrors local behaviour and one that surprises people.

One last thing about that first line: `gofmt -l` in CI should never produce output. If it does, the cause is that somebody's editor isn't formatting on save. Treat that as a bug in the setup instructions, not as a mistake by the person who pushed — and fix it by making the tooling correct on a fresh clone, which is where this article started.

## Further Reading

- **Humble & Farley, _Continuous Delivery_ (Addison-Wesley, 2010), chapter 3.** The deployment pipeline and the ten-minute build rule. The source of the feedback-ladder framing used above.
- **Winters, Manshreck & Wright, _Software Engineering at Google_ (O'Reilly, 2020), chapter 20 ("Static Analysis").** The best available treatment of why developers ignore warnings and what actually fixes it — including the finding that false-positive rate matters more than coverage. Read this before choosing lint rules.
- **The Go blog, "go fmt your code" (2013).** Short, and the clearest statement of why removing the formatting decision was worth more than getting the format right.
- **golangci-lint documentation**, specifically `issues.new-from-rev` and `depguard`. The ratchet and the boundary rule, in full.
- **pre-commit.com.** Language-agnostic hook framework with a large catalogue of existing checks; the right choice for polyglot repositories.
- **lefthook** and **husky + lint-staged** documentation, for Go and JavaScript ecosystems respectively.
- **Docker Compose specification — healthchecks, `depends_on` conditions, and `--wait`.** The part most Compose files get wrong.
- **The Development Containers specification (containers.dev).** Vendor-neutral, and worth reading before adopting Codespaces or similar so you know what's portable.
- **devenv.sh** as an approachable entry point to Nix-based environments, if the declarative end appeals.
- **EditorConfig specification (editorconfig.org).** Ten minutes, supported nearly everywhere, and it solves the two-spaces-versus-four problem for every tool at once.

A TypeScript sibling would reveal something this article's Go conceals. Go ships formatting, vetting, testing, and dependency management in one toolchain, with nothing to select and nothing to integrate — which quietly does most of the work above. In the Node ecosystem, every one of those is a choice: a formatter, a linter, a type checker, a test runner, a package manager, and a version manager, each with its own config, each with major versions that break the others. The classic ESLint-versus-Prettier rule conflict is the emblematic case, and keeping six tools mutually compatible across upgrades is ongoing work that has no equivalent here. That makes the TypeScript version of this article a different subject: it's about *integration* cost rather than *configuration* cost, and it's where Module 1.3's platform-tax argument becomes a weekly experience. Not yet written.

---

The habit worth carrying out of this article is a question to ask after anything goes wrong: **what is the earliest stage that could have caught this, and why didn't it?** A production incident traced back to a missing null check has an answer — a type could have. A CI failure on formatting has an answer — an editor setting could have. Most of the time the tool already exists, already sits in the right place, and simply isn't switched on. Moving one check one rung down the ladder is small, unglamorous work, and it compounds every single day for as long as the project lives.
