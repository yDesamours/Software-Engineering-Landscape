# Project Structure & Organization

_Module 3.1 — Project Setup & Development Environment_

## The Problem

A team ships three deployables: a public API, a background worker, and an internal admin tool. All three understand the same domain, so they share two pieces of code — a `domain` package with the core types and their validation rules, and a `db` package with the schema and query helpers.

Someone needs to add a value to an enum. `SubscriptionStatus` gains `paused`. It's a one-line change to a union type, plus handling in three places.

### With five repositories

The sequence is:

1. PR to `domain`. Review, merge, bump to 2.3.0, publish to the registry.
2. PR to `api` bumping `@acme/domain` to 2.3.0, plus the handling code. Review, merge, deploy.
3. Same for `worker`.
4. Same for `admin`.

Four PRs, four review cycles, four CI runs, and an ordering constraint between them. That's tedious but survivable. The interesting part is what's true in between:

```
  t0    domain 2.2.1   api 2.2.1   worker 2.2.1   admin 2.2.1    consistent
  t1    domain 2.3.0   api 2.3.0   worker 2.2.1   admin 2.2.1    ← 40-minute window
  t2                   api 2.3.0   worker 2.3.0   admin 2.2.1    ← admin PR stalled
  t3    (three weeks later)                       admin 2.2.1    ← still
```

At `t1`, the API can write `paused` to a row that the worker will read and fail to parse. That bug exists only in the window, only in production, and cannot be reproduced locally because locally everything is on the same version.

At `t3`, the admin tool is three weeks behind because its PR needed a reviewer from a team that was busy. Nobody is tracking this. Six months on, `admin` is four minors behind and upgrading it is now its own project, so it stays behind.

Then a `CVE` lands in a transitive dependency of `domain`. The fix is one line. Shipping it requires the whole dance again, and by now there are eleven consumers, two of which are on a major version that no longer receives the patch.

### With one repository

Same change: one PR, one commit, every consumer updated atomically. There is no window, no version, and no skew. The compiler checks all three call sites in one CI run. The `CVE` fix is one PR.

This is obviously better, so the team consolidates, and six weeks later:

- CI takes 26 minutes for every PR, including a one-line CSS change in the admin tool, because the pipeline runs everything.
- A new engineer edits a helper in `packages/domain` for their feature. It compiles. Two other teams' tests break, and nobody warned them, because nothing marks that file as anyone's.
- `pnpm install` resolves 2,800 packages. The IDE takes ninety seconds to index.
- When two teams want different major versions of a testing library, one of them loses.

Both shapes fail, and they fail for the same underlying reason. A repository boundary makes changes that cross it *expensive*. Polyrepo priced the enum change at four PRs and three weeks of skew, when it should have been free. Monorepo priced everything at zero, including the changes that should have cost something — like a junior quietly editing a package that three teams depend on.

The decision isn't "which is better." It's **which changes in your system should be expensive to make.**

## What It Is

A **monorepo** is a single version-control repository containing multiple projects with one shared commit history, where a single commit can atomically change any number of them. A **polyrepo** is one repository per project.

Two things this decision is not:

**A monorepo is not a monolith.** This is the most common confusion in the topic and it's worth killing outright. A monolith is one *deployable*. A monorepo is one *repository*. Google's monorepo produces thousands of independently deployed binaries. A tiny startup can have one deployable spread across four repositories for no reason at all. All four combinations exist and are found in the wild.

Module 2.1 established that deployment topology and module structure are independent axes. Repository topology is a third, independent of both:

```
  module structure      tangled        ←→  enforced boundaries    (Module 2.1)
  deployment topology   one deployable ←→  many deployables       (Module 2.1)
  repository topology   one repo       ←→  many repos             (this article)
```

**It is not primarily about code organization.** It's about coordination. A repository boundary determines what can change in one atomic commit, who must approve, what gets versioned, and what can drift. Those are questions about people and time, not about where files live.

That framing also explains why this article covers directory structure alongside it. Both are boundaries; they differ enormously in price. A directory boundary costs a `git mv` and is worth revisiting often. A repository boundary costs coordination on every cross-cutting change, forever, and per Module 2.5 is very much a one-way door. **The cost of a boundary determines how carefully you should decide it and how freely you should move it.**

## Recognizing the Problem

**Signals you have too many repositories:**

- A routine change requires PRs in three or more repos in a specific order.
- You've hit a bug that only exists between two deploys, caused by two components disagreeing about a shared type.
- Some consumer of a shared library is several versions behind, and nobody knows how far or why.
- A security patch in shared code takes weeks to reach every consumer.
- You maintain deprecation shims for internal-only interfaces, because you can't change producer and consumer atomically.
- Tooling config has drifted: four repos, four slightly different ESLint configs, four different Node versions in CI.
- "Where's the code for X?" is a question people ask in Slack.
- Running the system locally requires cloning six repositories and getting their branches into a compatible state.

**Signals you have too few:**

- CI runs everything on every change, and the runtime is why people batch work into large PRs.
- A change in shared code broke a team that didn't know it was a consumer.
- Nobody can say who owns a given directory.
- Two teams are blocked on each other over a dependency version neither cares about.
- Git operations, installs, or IDE indexing have become a daily friction.
- You need to give an external contractor access to one component and can't, without giving them everything.

**Signals your directory structure has failed** (independent of either):

- A new engineer can't tell where a new feature's files should go.
- There are top-level directories named `utils`, `common`, `shared`, `core`, or `misc`.
- The top level of the repo tells you which framework it uses and nothing about what the system does.
- Generated code is checked in next to hand-written code with no marker.
- Finding the entry point of a service requires grepping for `main` or reading the Dockerfile.

## How It Works

### What a repository boundary actually gives you

Five things, and every argument in this topic is about one of them:

1. **An atomic change unit.** One commit, one revert. Across repos, neither exists.
2. **A version boundary.** Code inside is referenced by path; code outside is referenced by version. Versions are what allow drift — which is sometimes the entire point, and sometimes the entire problem.
3. **A CI trigger surface.** By default, any change runs the whole pipeline.
4. **An access-control unit.** Read and write permissions are granted per repo.
5. **A dependency-resolution unit.** One lockfile, one resolved version of each third-party package.

Point 2 is where the skew in the Problem section comes from. Versioning internal code is how you buy independent lifecycles, and the bill is that consumers can be on different versions — including versions with a bug you fixed last quarter.

### What makes a large monorepo work

Left alone, a monorepo produces the 26-minute CI run and the unowned shared package. Three mechanisms fix that, and teams that adopt monorepos without them are the ones who write the blog posts about why monorepos don't work.

**A build graph with affected-target detection.** The tool knows which packages depend on which, computes what changed since the merge base, and runs only the affected tasks. A CSS change in `admin` runs `admin`'s tests and nothing else. This is the single mechanism that determines whether a monorepo scales, and it's what Bazel, Nx, Turborepo, Gradle, and `go build`'s cache all exist to provide. Without it, CI cost grows with the repo and every engineer pays for every other engineer's code.

**Ownership, added back explicitly.** A repo boundary gives you ownership for free — the people with write access own it. Inside a monorepo, everyone has write access to everything, so ownership becomes a file: `CODEOWNERS`, mapping paths to teams and requiring their review. This is not bureaucracy; it's the restoration of a property you deleted.

**Visibility rules.** Same problem, different half: in a polyrepo, a package can only be imported if it's published. In a monorepo, anything can import anything. The answer is the same mechanism Module 2.1 used for module boundaries — Go's `internal/`, Bazel's `visibility` attribute, an import-restriction lint rule — and it's needed *more* here, not less, because the physical barrier is gone.

### What makes a polyrepo work

**Automated dependency updates.** Renovate or Dependabot opening the version-bump PRs automatically, with auto-merge on green for internal packages. This doesn't eliminate the window at `t1`; it shrinks it from weeks to hours, which for most teams is the difference between a real problem and a theoretical one.

**Contract tests at the boundaries.** If `api` and `worker` can't be changed atomically, then something has to catch the disagreement before production. Consumer-driven contract tests are the standard answer, and they're work you don't have to do in a monorepo because the compiler does it.

**Actual versioning discipline.** Semantic versioning only helps if breaking changes really do get a major bump, which requires judgment on every release. Most internal libraries get this wrong, and the resulting mistrust is why consumers pin exact versions and then never upgrade.

### Scale limits, honestly

Git handles repositories far larger than most teams will ever produce. The genuine limits appear in the hundreds of thousands of files, and by then the answers exist: partial clone (`--filter=blob:none`), sparse checkout, and Scalar/VFS for Git. Facebook and Microsoft's monorepos required custom filesystems; yours almost certainly will not. Repository size is the most-cited and least-relevant objection in this debate — CI time and ownership are where real teams actually get hurt.

### The directory half

The top level of a repository has one job: **tell a newcomer what this is and where to put things.**

A tree whose top level reads `controllers/ models/ services/ views/` tells you the framework. A tree that reads `billing/ scheduling/ notifications/ reporting/` tells you what the system does. The second is what Robert Martin called screaming architecture, and the practical version of it is a test: hand the tree to a new engineer, describe a feature, and ask where the files go. If they can't answer in under a minute, the structure is failing at its only job.

Module 2.2 covered the layer-versus-feature question inside `src/`, so the thing left for the repository root is everything that *isn't* application code, and the rule there is simpler than it looks: **follow your ecosystem's convention rather than inventing one.** Maven's `src/main/java` and `src/test/java`, Go's `cmd/` and `internal/`, Node's `src/` and `dist/` — these are not better designs than what you'd come up with, but every tool, template, and contributor already assumes them, and the cost of deviating is paid by everyone who arrives later.

A few placement questions that recur:

- **Infrastructure-as-code** lives with the code it deploys, not in a separate repo, so a change to a service and its deployment can be one commit.
- **Documentation that decays** (current-state descriptions) belongs wherever your team will maintain it. Documentation that *shouldn't* decay — the ADRs from Module 2.5 — belongs in the repo, in `docs/adr/`, reviewed as code.
- **Generated code** goes in a directory that says so, ignored by linters and marked in `.gitattributes` so it doesn't dominate diffs. Whether to commit it at all is a real trade-off: committing it makes builds reproducible without the generator; not committing it prevents it drifting from its source.
- **Junk drawers.** Module 2.1 already covered why `common` and `shared` packages become unowned dependency magnets. The root-level version is the same failure at larger scale: a top-level directory named after nothing accumulates everything.

## When It's Appropriate

**A monorepo, when:**

- Shared code changes frequently *and* its consumers must change with it. This is the dominant factor. If `domain` changes weekly and all three apps care, versioning it is pure overhead.
- One team, or several teams that release together and trust each other.
- You want atomic cross-cutting refactors — renaming a field everywhere in one commit, with the compiler verifying it.
- You're willing to invest a few days in build tooling. The first time CI hurts, you'll need the build graph; budget for it rather than discovering it.
- Consistency is valuable: one lint config, one formatter, one Node version, enforced by being the only one present.

**Separate repositories, when:**

- **Lifecycles are genuinely independent.** A client SDK versioned for external consumers, with its own release cadence and support window, is a different thing from your API.
- **Access control differs.** An open-source component, a contractor's workspace, a repository under regulatory restriction. This is the one reason that a monorepo simply cannot accommodate, and it's often decisive on its own.
- **Toolchains are wildly different.** A Rust data pipeline, an iOS app, and a Node API can share a repo, but the build tooling that makes a monorepo worthwhile gets much harder across ecosystems, and the benefit shrinks because they share almost no code.
- **Teams are genuinely autonomous** with real contracts between them — the organizational conditions from Module 2.1 that justify separate services in the first place.

## When It's Unnecessary or Overkill

**Heavy monorepo tooling at small scale.** Bazel for three services and six engineers is weeks of setup, a new language to learn, and a permanent tax on every new dependency. pnpm workspaces and a task runner cover this case in an afternoon. Adopt the heavy tool when CI time or build correctness actually hurts, and not before.

**Splitting repositories to enforce boundaries.** This is Module 2.1's mistake in cheaper clothing. If two components are so entangled that developers keep reaching across the line, moving them to separate repositories doesn't decouple them — it means the entanglement now has version numbers and a publishing step. The boundary you can't hold with a lint rule is not one you'll hold with a registry.

**One repo per service because you have microservices.** These are separate decisions. Plenty of organizations run many services out of one repository, and it's often the better arrangement precisely because the services share types.

**Consolidating repos without adding ownership and visibility.** You'll get the merge, then discover you deleted the only thing preventing arbitrary coupling. Do the merge and the `CODEOWNERS` file in the same week.

**Agonizing over directory structure early.** It's the cheapest boundary in this article. Pick your ecosystem's convention, start, and move things when the shape is obvious. Time spent designing a folder taxonomy before you know the domain is time spent designing the wrong one.

## Trade-offs

**Monorepo costs:**

- CI expense scales with the repository unless you build the dependency graph — and that graph is real infrastructure you now own and debug.
- Everyone can change everything, so blast radius is large by default and ownership has to be reconstructed with tooling.
- One lockfile means one version of each third-party dependency across all projects. That's genuinely valuable for consistency and genuinely painful the day one app needs React 19 and another isn't ready.
- Git operations, installs, and IDE indexing get slower, gradually, in a way nobody notices until it's bad.
- Access control is all-or-nothing at the repository level.
- Extracting a component later — to open-source it, to hand it to another company — is real work.

**Polyrepo costs:**

- Version skew, which is not a nuisance but a class of production bug that can't be reproduced locally.
- Cross-cutting changes cost N pull requests and cannot be reverted atomically. When something goes wrong mid-sequence, you're in a state no single commit describes.
- Tooling configuration drifts. Four repos become four slightly different CI setups, and the differences are discovered during incidents.
- Dependency upgrades lag, and the lag compounds until upgrading is a project.
- Discovery suffers: newcomers can't find things, and code gets reimplemented because nobody knew it existed.
- Local development requires orchestrating several checkouts, which is a recurring tax on every engineer every week.

One asymmetry worth naming, since it mirrors Module 2.1: monorepo costs are mostly *ceilings* you hit as you grow, and they have known engineering solutions. Polyrepo costs are mostly *recurring*, paid on every cross-cutting change regardless of scale, and their solutions are process rather than tooling. That's why the common advice is to start with one repository — not because it's superior, but because the failure mode arrives later and is fixable with money.

## Alternatives

**A small number of repositories, drawn around teams or products.** The shape most real organizations converge on: not one repo for the company, not one per service, but one per product area or per team, each containing several deployables and their shared code. It gets most of the atomicity benefit where coupling is tightest and keeps the access-control and tooling boundaries where organizational lines actually fall. If you don't want to think hard about this, this is the default to land on.

**Git submodules.** Technically the middle ground; in practice widely disliked. Detached HEADs, updates that look like normal commits but aren't, and a workflow that every new team member gets wrong at least once. Occasionally the right tool for vendoring a pinned external dependency. Rarely the right tool for your own code.

**Git subtree.** Copies content in with history, no client-side ceremony. Better than submodules for the common case, at the cost of a larger repo and an unfamiliar merge workflow.

**Vendoring.** Copy the dependency in and own it. Honest, and correct more often than it's fashionable — particularly for small, stable dependencies where the maintenance is less than the supply-chain surface.

**Duplication instead of a shared package.** The Go proverb — *a little copying is better than a little dependency* — is a real answer for small shared helpers. A 30-line utility copied into two services costs almost nothing and couples nothing. A shared package costs a version, a release process, and a permanent coordination link. The instinct to deduplicate is strong and frequently wrong at small sizes; the question is whether the two copies would ever need to change together, and for genuinely generic helpers the answer is no.

**Meta-tooling over many repos** (`meta`, `mu-repo`, Google's `repo`). Scripts that run the same command across a set of checkouts. Reduces the local-development friction without changing any of the versioning problems.

## How to Achieve It

**Toward fewer repositories:**

**L1 — Unify tooling first, while still separate.** Same formatter, same lint config, same Node/JDK/Go version, same CI template across all repos. This is independently valuable and removes most of the merge's friction before you do it.

*Next when:* the remaining pain is version skew and multi-PR changes rather than configuration drift.

**L2 — Merge, preserving history.** `git subtree add` or `git-filter-repo` to bring each repo in under its own directory with its commits intact. Losing history is avoidable and you'll want it during the first post-merge incident.

**L3 — Add `CODEOWNERS` in the same week.** Not later. This restores the ownership property the merge deleted, and retrofitting it after six months of unowned changes is much harder than declaring it upfront.

*Next when:* CI time is annoying people, which usually takes a month or two.

**L4 — Introduce a build graph.** Start with the lightest tool that gives affected-target detection for your ecosystem. Heavier tools exist for when correctness and remote caching matter more than setup cost.

*Next when:* someone imports something they shouldn't have, and nothing stopped them.

**L5 — Enforce visibility.** Import restrictions between packages, using the mechanism from Module 2.1.

**Toward more repositories:** extract one, for a named reason from the "When It's Appropriate" list — almost always access control or a genuinely independent release cadence. Extract the second only when it has its own reason. A repository split justified by "it feels cleaner" is the thing this article is arguing against.

## Implementation

TypeScript, with pnpm workspaces and a task runner, because the mechanisms are visible in configuration rather than hidden in a tool's behaviour — and because this is where most readers will meet the problem.

### The layout

```
acme/
  apps/
    api/            package.json  → @acme/api
    worker/         package.json  → @acme/worker
    admin/          package.json  → @acme/admin
  packages/
    domain/         package.json  → @acme/domain
    db/             package.json  → @acme/db
  infra/            terraform, deployed alongside the code it deploys
  docs/adr/         Module 2.5's decision records, reviewed as code
  pnpm-workspace.yaml
  turbo.json
  CODEOWNERS
```

`apps/` are things that get deployed; `packages/` are things that get imported. That one distinction answers most "where does this go?" questions on its own, and it's worth preferring over a cleverer taxonomy for exactly that reason.

### Removing versions entirely

```yaml
# pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"
```

```json
// apps/api/package.json
{
  "name": "@acme/api",
  "dependencies": {
    "@acme/domain": "workspace:*",
    "zod": "^3.23.0"
  }
}
```

`workspace:*` means *whatever is in this repository right now* — pnpm symlinks the local directory instead of resolving from a registry. There is no version number, so there is no version to be behind on, and the `t1`/`t3` rows from the Problem section cannot occur. That is the whole mechanism, and it's worth being explicit that it's a *removal* rather than an addition: the monorepo doesn't solve version skew, it deletes the versions that made skew possible.

The bill arrives at publish time. If `@acme/domain` is ever published externally, `workspace:*` must be rewritten to a real version on release — pnpm does this automatically, but it means the internal and external stories genuinely differ, and a package that is both is the awkward case.

Note also what the single lockfile does: `zod` resolves to one version for the entire repository. Every app gets consistency for free and gives up the ability to upgrade independently. That's a real trade, and it's the one most likely to cause an argument in month six.

### Limiting what CI runs

```json
// turbo.json
{
  "tasks": {
    "build": { "dependsOn": ["^build"], "outputs": ["dist/**"] },
    "test":  { "dependsOn": ["build"] },
    "lint":  {}
  }
}
```

```bash
# In CI: only packages affected by this branch's changes, plus their dependents.
turbo run lint test --filter="...[origin/main]"
```

`dependsOn: ["^build"]` means "build my dependencies first" — the task graph follows the dependency graph, so ordering is derived rather than declared. The `--filter` is what turns the 26-minute pipeline back into a 90-second one: a change confined to `apps/admin` runs `admin`'s tasks, and a change in `packages/domain` runs everything that imports it, which is correct in both directions.

One thing to get right early: the filter is only as trustworthy as the dependency declarations. If a package imports something it doesn't list in its `package.json`, the graph is wrong, affected-detection silently under-runs, and CI passes on a broken build. An `import/no-extraneous-dependencies` lint rule is not optional infrastructure here — it's what makes the rest of this correct.

### Restoring what the merge deleted

```
# CODEOWNERS
/packages/domain/   @acme/platform
/packages/db/       @acme/platform
/apps/admin/        @acme/internal-tools
/infra/             @acme/platform @acme/security
```

Before consolidation, the `domain` repo's write permissions expressed this and enforced it absolutely. Afterwards, this file is the only thing that does, and it enforces it through review rather than access. That's weaker, and it's the honest cost of the merge — worth stating plainly rather than discovering when someone merges past a stale review.

The complementary half is import restrictions between packages, which is the same mechanism Module 2.1 used inside a single service, applied one level up. Both are needed for the same reason: removing a physical barrier means the logical one has to be built.

## Further Reading

- **Potvin & Levenberg, "Why Google Stores Billions of Lines of Code in a Single Repository" (CACM, July 2016).** The definitive account of monorepo at the extreme, including the tooling it requires. Read it for the mechanisms, not as a model to copy.
- **Matt Klein, "Monorepos: Please don't!" (2019).** The best-argued counter-case, from someone with large-scale experience on both sides. The section on hidden coupling is the part worth sitting with.
- **Bazel documentation — `visibility` and the concept of build targets.** Even if you never adopt Bazel, its model of an explicit dependency graph with enforced visibility is the clearest statement of what monorepo tooling is for.
- **Nx and Turborepo documentation on affected/filtered task running.** The practical version of the same idea for JavaScript ecosystems.
- **pnpm workspaces documentation**, particularly the `workspace:` protocol and how it's rewritten on publish.
- **Git documentation on partial clone (`--filter`) and sparse checkout**, plus Microsoft's Scalar. The actual answers to repository-size objections, most of which are cited long before they apply.
- **The Maven Standard Directory Layout** and **the Go blog's "Organizing a Go module."** Two ecosystems' official conventions. Note that the widely-linked `golang-standards/project-layout` repository is community-produced, not official, and its `pkg/` convention is genuinely contested — the official doc is the better starting point.
- **Robert C. Martin, "Screaming Architecture" (2011).** Two pages on what the top level of a tree should communicate.
- **Rob Pike, "Go Proverbs" (talk, 2015).** For "a little copying is better than a little dependency," and the reasoning behind it.
- **Module 29** for branching strategy and **Module 30** for pipeline construction, both of which interact heavily with this choice without being part of it.

A Go sibling would show something this article's TypeScript conceals. In Go, a monorepo needs no workspace tool, no `workspace:*` protocol, and no package manager involvement at all: one `go.mod` at the root, and sharing code between `cmd/api` and `cmd/worker` is an import path. Versions don't need deleting because they were never introduced. Affected-target detection is largely the build cache doing its job. The interesting consequence is that Go's default answer to this entire article is "one module, one repo," and the tooling pressure runs the opposite way — it's *multi*-module repositories that need `go.work` and careful thought. That inversion is worth seeing. Not yet written.

---

The habit worth carrying out of this article: **price your boundaries before you draw them.** A directory boundary costs a `git mv`, so draw it early, draw it wrong, and move it. A repository boundary costs coordination on every change that crosses it, for as long as both sides exist — so draw it only where you *want* changes to be expensive, which is a much shorter list than it first appears. Module 2.1 made the same argument about services, and 2.5 said to write the reasoning down. The recurring lesson of the last several articles is that most architectural regret comes from boundaries drawn at a price the team didn't realize they were agreeing to.
