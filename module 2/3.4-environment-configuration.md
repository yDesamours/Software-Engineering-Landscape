# Environment Configuration

_Module 3.4 — Project Setup & Development Environment_

## The Problem

Three incidents from the same system, over eighteen months.

### The key that wasn't there

The service reads settings from `config/dev.yaml`, `config/staging.yaml`, and `config/prod.yaml`. Over two years they drifted: dev has 52 keys, staging 41, prod 47. Six keys exist only in production. Two share a name and mean different things.

A retry feature ships. It works in staging. In production, the downstream call fails once and gives up, because `retry.maxAttempts` was never added to `prod.yaml`, and the code does this:

```ts
const attempts = config.retry?.maxAttempts ?? 1;
```

No error. No warning. The service started cleanly, passed its health check, ran for nine days, and then quietly stopped retrying during the one window it mattered. The failure wasn't at deploy time, it was on a code path, in production, a week and a half later.

### The password nobody can change

In 2022 someone put the production database password into `prod.yaml` as a temporary measure. It's still there, and it's in git history, which means it's on every laptop that has ever cloned the repository.

It's also in three CI logs, because a debugging session added `console.log(config)` and nobody thought about what was in `config`.

Rotating it requires finding every consumer — two services, a cron job, a Metabase instance, and an analyst's saved connection — and changing them in an order that doesn't cause an outage. Nobody has ever attempted this. The password has been the same for four years.

### The flag that outlived everyone

`NEW_CHECKOUT_ENABLED` was added in 2023 for a gradual rollout. The rollout finished in three weeks. The flag is still in the code.

There are now 180 flags. Forty have been at 100% for over a year. The checkout path has eleven of them, which is 2,048 theoretical combinations, of which about six are ever exercised by tests. A bug arrives that reproduces only for users who have flags 3, 7, and 9 on simultaneously, and reproducing it locally takes two days because nobody knows how to put a test account into that state.

### What these have in common

Every tool you own inspects code. The compiler checks types. The linter checks patterns. Review checks intent. Tests run the code.

None of them see the *values*. Config is the part of your program with no compiler, no type checker, no review, and no test coverage — and it's the part that differs between the environment where you verified the software and the environment where it runs.

## What It Is

Configuration is everything that varies between deployments of the same artifact. The Twelve-Factor formulation is a useful starting point: if it changes between deploys, it's config; otherwise it's code.

But lumping it all together is what produced all three incidents. The distinctions that matter are **who changes it, how fast it takes effect, and what happens when it's wrong:**

```
                    changes      by whom        takes effect      when wrong
  code constant     with code    engineer       next deploy       tests catch it
  deploy config     per env      engineer/ops   restart           startup fails*
  dynamic config    any time     ops            seconds           live incident
  feature flag      any time     PM or eng      seconds, per user partial incident
  secret            rarely       platform       restart or lease  breach

  * only if you validate at startup — otherwise it fails much later, as above
```

Five rows, five different sets of requirements. A mechanism designed for the second row will not give you rotation (row five) or per-user targeting (row four), and using it for those is how each of the three incidents happened.

Three neighbours worth separating explicitly:

**Feature flags are not environment config.** Config is a property of the *environment*: this deployment talks to that database. A flag is a property of the *request*: this user, on this plan, in this region, gets the new checkout. They look alike because both are booleans read from outside the code, and they diverge the moment you need targeting rules, because a config system asked to grow them becomes a bad flag system.

**Secrets are not config with extra care.** They have three requirements ordinary config doesn't: they must be rotatable without a coordinated outage, access to them must be auditable, and their exposure must be limited to what needs them. A mechanism that can't do those three isn't a secret mechanism, however carefully you use it.

**And flags themselves are several things.** Pete Hodgson's taxonomy is the useful one, because the categories have different lifespans:

- **Release toggles** hide incomplete work. Temporary — days to weeks — and must be removed.
- **Experiment toggles** split traffic for A/B tests. Temporary, and owned by whoever reads the results.
- **Ops toggles** are kill switches and limits. Long-lived by design, owned by whoever carries the pager.
- **Permission toggles** decide what a customer's plan includes.

That last one is the trap, and it's worth stating plainly: **plan entitlements are not feature flags, they're business rules.** They're permanent, they're part of what the customer bought, and they belong in the domain model with the rest of the billing logic (Modules 1.1 and 15). Putting them in a flag service means your pricing is configured in a console with no review and no tests.

## Recognizing the Problem

- A missing or malformed config value produces a runtime failure rather than a failed startup.
- Per-environment config files have diverged and nobody can say which keys are actually read.
- You can't determine what configuration a running instance is using.
- A credential appears in git history, a CI log, or an error report.
- No credential has ever been rotated.
- Flags have been at 100% for more than six months.
- A bug reproduces only under a particular combination of flags.
- Config changes are made by editing a file on a server, or by a console with no audit trail.
- The same value is defined in three places — application config, Terraform, and CI — and they sometimes disagree.
- Running the application locally requires production credentials.
- "It works in staging" is a sentence people say often.

## How It Works

### Parse at startup, into types

The highest-value technique in this article, and the cheapest: read *all* configuration once, at boot, into a typed structure, and refuse to start if anything is missing or malformed — reporting every problem at once rather than the first.

Two properties fall out of this, and they're both worth more than they look.

**Failures move from the code path to the deploy.** A bad value now means the process doesn't start, the health check never passes, and the rollout halts automatically. The first incident above becomes a failed deploy at 10am instead of a silent behaviour change discovered nine days later.

**Config stops being stringly-typed.** Environment variables are always strings. `PORT` is `"3000"`, not `3000`, and `DEBUG=false` is a non-empty string, which is truthy. Parsing at the boundary converts these once, in a place you can test, rather than at every use site.

This is the same discipline as Module 2.2's parse-at-the-edge and Module 2.3's value objects, applied to a boundary people forget is a boundary. Configuration is untrusted input that arrives from outside your program. Treat it like a request body.

### Layer, don't duplicate

The file drift in the first incident came from three complete copies of the configuration. The fix is a base plus overrides: defaults in code, a base file, then environment-specific overrides containing *only* what differs, then environment variables, then command-line flags — each layer winning over the previous.

Prod's file shrinks from 47 keys to the six that are genuinely different, and the divergence becomes visible because it's the entire content of the file.

### Environment variables: where they work and where they don't

Twelve-Factor's advice to keep config in the environment is good and widely over-applied. Environment variables are universal, supported by every platform and orchestrator, and require nothing. They're also:

- flat strings, so any structure has to be encoded and decoded;
- inherited by every child process you spawn;
- visible in `/proc`, in `ps` output, and in most crash and error reporters;
- untracked — there's no record of who changed one or when.

The first three are tolerable for a log level. For a database password, the last two are the problem: a secret in an environment variable is a secret you cannot audit and will find in a stack trace.

### Secrets, in increasing order of strength

**In the repository.** Never, and the corollary is important: once a secret reaches git history, rotation is the only remedy. Rewriting history doesn't help, because every existing clone still has it. Scan for this in CI, and scan the history once, and treat every hit as compromised rather than as a cleanup task.

**A gitignored `.env` file for local development**, with a committed `.env.example` listing the required keys and fake values. The example file also doubles as documentation of what the application needs.

**Platform-injected at deploy.** Kubernetes Secrets, ECS task secrets, and equivalents. Better, because the value isn't in your repository — and worth knowing that Kubernetes Secrets are base64-encoded rather than encrypted unless you've enabled encryption at rest. The secret is still long-lived and still sitting in the process environment.

**Fetched at runtime with a lease.** The application authenticates to a secret store and receives a credential with a time limit. The powerful version is *dynamic* secrets: the store creates a database user per instance, valid for an hour, and deletes it afterwards. Rotation stops being a project and becomes the default behaviour — there's nothing to rotate, because nothing lives long enough to need it. The second incident becomes structurally impossible.

**No secret at all.** Workload identity: the platform attests what your service is, and the database or cloud API grants access to that identity. There is no string to leak, log, or rotate. Where it's available, this is strictly better than everything above it, and it's the direction the whole area is moving.

Whichever rung you're on, one defence is worth building early: make secrets a *type* whose serialization is redacted, so that logging the config object — which somebody will do — prints placeholders. Most secrets leak through logs and error reports rather than through attacks.

### Feature flags

**Evaluation happens locally.** The SDK holds a ruleset, streamed or polled from the service, and evaluates against a context you pass in — user ID, plan, region. A network call per flag check would put a third party in the latency path of every request, and in the availability path too.

**The default is the most important line of code.** When the flag service is unreachable — and it will be — the SDK returns a default. Write the code so that default is the *safe, existing* behaviour, not the new one. A flag system that can take your application down with it is worse than having no flags.

**Bucketing must be stable.** Hash the user identifier so the same user gets the same answer every time. A flag that flips per request produces users who see a feature appear and vanish, and bug reports nobody can reproduce.

**Debt needs a mechanism, not discipline.** Every temporary flag gets an owner and an expiry date at creation. A check in CI fails the build when a flag passes its expiry. Without something automatic, the third incident is the default outcome — not because anyone is careless, but because removing a finished flag is never the most urgent thing on anyone's list.

**You cannot test the combinations.** Eleven flags is 2,048 states. The realistic approach is to test the default path and the new path for each flag, and to limit how many concurrent flags touch any one area — which is a design constraint, and a reason to remove flags promptly rather than a reason to write more tests.

## When It's Appropriate

**Typed, startup-validated config: every project, from the first commit.** It costs twenty lines and removes a whole class of late failure.

**A real secret store: as soon as there are production credentials and more than one person.** The threshold isn't scale, it's the existence of a credential whose compromise would matter.

**Dynamic config: when you need to change behaviour faster than you can deploy.** Make this concrete — if a deploy takes 25 minutes and an incident requires a change in 2, then for *those specific values* you need a runtime mechanism. That's usually a short list: kill switches for risky integrations, rate limits, timeouts, sampling rates. Everything else can wait for a deploy, and should.

**Feature flags: when you want to merge before a feature is finished, or roll out to a fraction of users.** The alternative to the first is long-lived branches, which are worse in every respect (Module 29). The alternative to the second is shipping to everyone at once and finding out.

**Dynamic secrets: when rotation is a requirement or breach blast radius matters.** Regulated environments, or anywhere a leaked credential would mean notifying customers.

## When It's Unnecessary or Overkill

**Making everything configurable.** This is the default failure mode and it looks like good engineering. Every knob is a branch in behaviour space that nothing tests, a question every future reader has to answer ("does anyone set this?"), and a value that can be wrong in production. Hardcode by default; promote to config the moment a second environment genuinely needs a different value, and not in anticipation of one.

**A flag platform for a team of three.** Start with a boolean in your typed config. Adopt a service when you need per-user targeting or non-engineers changing values — not before.

**Dynamic config for things that should require review.** Changing a business rule through a web console, with no diff, no review, and no test run, is an unreviewed production change with a friendly UI. If a value encodes a decision rather than an operational limit, it belongs in code.

**Flags for permanent entitlements.** Covered above, and worth repeating because it's so common: that's pricing logic living outside your codebase.

**Per-environment files that are near-identical copies.** Use overrides. Three full copies will drift; there's no discipline that prevents it.

**Vault for a side project.** The operational cost is real, including the question of whether your application can start while the vault is unavailable.

## Trade-offs

**Every config value is untested behaviour.** Your test suite runs with one set of values. Production runs with another. The more values that vary, the larger the gap between what you verified and what you shipped.

**Dynamic config breaks reproducibility.** With deploy-time config, artifact version plus environment determines behaviour, so you can reproduce production by checking out a commit. Once values change at runtime, you can't — and during an incident, "what was the state of the system at 14:02?" becomes unanswerable without an audit log of config changes. The mitigation is to treat config changes as deploys, because that's what they are: versioned, logged, attributable, and revertible.

**A central config or flag service has a larger blast radius than a deploy.** One bad change reaches every service at once, in seconds, with no canary and usually no review. Deploys are slow partly on purpose.

**Secret stores are an availability dependency.** Can your service start during a vault outage? Can it restart? Teams usually find out the answer during the outage. Caching leases and degrading deliberately are design decisions to make in advance.

**Flags cost complexity in the hot path and in the head.** Every flag makes the code harder to read and reason about, and flag evaluation isn't free in a tight loop.

**Local-versus-production config differences hide bugs.** A local setup using SQLite, an in-memory cache, and a stubbed payment provider is fast and productive, and it guarantees a category of failure that only appears in production. Module 3.2's containerized dependencies narrow this gap; config differences reopen it.

## Alternatives

**Config in code, per environment.** A typed map keyed by environment name, compiled in. You give up "same artifact, any environment," and you gain review, types, tests, version history, and the impossibility of drift. For systems with a handful of environments and no per-deployment secrets, this is underrated — and it means a config change goes through exactly the same process as a code change, which is usually what you wanted.

**Infrastructure-as-code as the source of truth.** Terraform knows the database endpoint because it created it; wiring its outputs into the application's environment removes the duplication where the same value is written down in three places and can disagree.

**Branch by abstraction instead of release toggles.** For large refactors, an abstraction layer with two implementations, switched at wiring time, is often cleaner than scattering conditionals — and it deletes cleanly when finished.

**Dark launching and shadow traffic** validate new code paths by running them without using their results, which answers "does it work under real load" without needing per-user targeting.

**Separate deployments instead of configuration.** For genuinely divergent needs — per-region, per-large-tenant — running a separate deployment can be simpler than a configuration matrix inside one (Module 5).

**No secret at all**, where workload identity is available. Worth listing as an alternative rather than a rung, because it removes the problem rather than managing it.

## How to Achieve It

**L1 — One typed config object, parsed and validated at startup.** Every problem reported at once. Nothing else in the codebase reads the environment directly.

*Next when:* you find a credential where it shouldn't be — which, if you haven't looked, you will.

**L2 — Get secrets out of the repository.** Scan history and CI logs, rotate everything found, move to platform-injected values, and add scanning to CI so it can't recur.

*Next when:* environment files have started to diverge.

**L3 — Layer the config.** Base plus overrides, with a schema so that a key which is read is a key which is declared.

*Next when:* rotation is required, or a leaked credential would be a reportable incident.

**L4 — A secret store with leases**, then dynamic secrets, then workload identity where the platform supports it.

*Next when:* an incident needed a change faster than a deploy could deliver it.

**L5 — Dynamic config for a short, explicit list of operational values**, with an audit log from day one.

*Next when:* you want to merge unfinished work, or roll out gradually.

**L6 — Feature flags with typed accessors, owners, and enforced expiry.** The expiry check goes in at the same time as the first flag, not after the hundredth.

## Implementation

TypeScript, because a schema library makes the central mechanism — config as parsed, typed, validated input — visible in about fifteen lines, and because it's the ecosystem where scattered `process.env` lookups are most tempting.

### One boundary, all errors at once

```ts
// config.ts — the only file in the application that reads process.env.
import { z } from "zod";

const Schema = z.object({
  NODE_ENV: z.enum(["development", "staging", "production"]),
  PORT: z.coerce.number().int().positive().default(3000),
  DATABASE_URL: z.string().url(),
  REDIS_URL: z.string().url(),
  RETRY_MAX_ATTEMPTS: z.coerce.number().int().min(1).max(10).default(3),
  LOG_LEVEL: z.enum(["debug", "info", "warn", "error"]).default("info"),
  STRIPE_SECRET_KEY: z.string().startsWith("sk_"),
});

const parsed = Schema.safeParse(process.env);

if (!parsed.success) {
  // Every problem, not just the first one.
  for (const issue of parsed.error.issues) {
    console.error(`config: ${issue.path.join(".")}: ${issue.message}`);
  }
  process.exit(1);
}

export const config = Object.freeze(parsed.data);
```

`z.coerce.number()` is doing quiet but essential work. Environment variables are strings, always — `PORT` arrives as `"3000"`, and without coercion you get a string where the type says number, which TypeScript will cheerfully believe because `process.env` is typed as strings the compiler can't see into. This is also why `DEBUG=false` is a classic bug: it's a non-empty string, and therefore truthy.

`safeParse` with the full issue list matters more than it looks. Failing on the first error means a deploy with four missing variables takes four attempts to fix, each one a full round trip.

The first incident in this article cannot happen against this file. `RETRY_MAX_ATTEMPTS` is declared with a default, so it's never absent; if it were declared required and were absent, the process would exit at boot, the health check would never pass, and the rollout would stop.

The rule that makes it hold is that **nothing else reads `process.env`**, and that's a lint rule rather than a convention — the `no-restricted-globals` and import-boundary machinery from Module 3.2 applied to one specific object. Without it, the second `process.env.SOMETHING` appears within a month and the schema stops describing reality.

### Making leaks harder

```ts
class Secret {
  constructor(private readonly value: string) {}
  expose(): string { return this.value; }
  toString() { return "[redacted]"; }
  toJSON()   { return "[redacted]"; }
  [Symbol.for("nodejs.util.inspect.custom")]() { return "[redacted]"; }
}

const stripeKey = new Secret(config.STRIPE_SECRET_KEY);

console.log({ stripeKey });        // { stripeKey: '[redacted]' }
JSON.stringify({ stripeKey });     // {"stripeKey":"[redacted]"}
stripe(stripeKey.expose());        // deliberate, greppable, reviewable
```

This doesn't protect against an attacker. It protects against the second incident in this article, which is how secrets actually escape: a debug log, a serialized error object, an APM trace payload. The `expose()` call is deliberately ugly so that it shows up in review and in `grep`.

### A flag, with the failure case written first

```ts
type FlagKey = "new-checkout" | "async-invoicing";

// Declared here, with an owner and an expiry the build enforces.
const FLAGS: Record<FlagKey, { owner: string; expires: string; fallback: boolean }> = {
  "new-checkout":    { owner: "@payments", expires: "2026-11-01", fallback: false },
  "async-invoicing": { owner: "@billing",  expires: "2026-10-15", fallback: false },
};

export function isEnabled(key: FlagKey, ctx: RequestContext): boolean {
  try {
    return client.booleanValue(key, FLAGS[key].fallback, {
      targetingKey: ctx.userId,     // stable bucketing: same user, same answer
      plan: ctx.plan,
      region: ctx.region,
    });
  } catch {
    return FLAGS[key].fallback;     // provider down → old behaviour, not new
  }
}
```

Three deliberate choices. `FlagKey` is a union rather than a string, so a typo is a compile error and finding every use of a flag is a real search rather than a grep for a quoted string. `fallback` is declared next to the flag, which forces the question "what happens if the provider is unreachable?" at creation time rather than during the outage. And the context is passed in per request, which is what keeps flags from drifting into globals and becoming the environment config they aren't.

The expiry date is inert on its own. What makes it work is a CI check that reads this map, compares against today, and fails the build:

```
✗ flag "new-checkout" expired 2026-11-01 (owner @payments) — remove it or move the date
```

Failing the build feels aggressive for a stale boolean. It is the only thing that has ever worked. The third incident isn't caused by carelessness; it's caused by flag removal never being the most urgent task available, which is true every single day until something makes it urgent.

## Further Reading

- **The Twelve-Factor App, factor III (Config).** Short, influential, and worth reading alongside its critics — the advice is sound for deploy-time configuration and routinely over-extended to secrets.
- **Pete Hodgson, "Feature Toggles (aka Feature Flags)" (martinfowler.com, 2017).** The canonical taxonomy used above, plus practical guidance on managing toggle debt. The single most useful thing written on the subject.
- **Alexis King, "Parse, don't validate" (lexi-lambda.github.io, 2019).** The idea behind treating config as input to be parsed into a type rather than checked in place. Written about Haskell, applies everywhere.
- **OpenFeature (openfeature.dev).** A vendor-neutral flag API under the CNCF. Useful even if you're building your own, as a description of the interface a flag system should present.
- **HashiCorp Vault documentation — dynamic secrets and leases.** Read the dynamic database credentials guide specifically; it's the clearest explanation of why short-lived credentials change the rotation problem rather than easing it.
- **Kubernetes documentation — Secrets**, including the section on encryption at rest, which explains what the default does and doesn't give you. Then the **External Secrets Operator** docs for connecting it to a real store.
- **SPIFFE/SPIRE (spiffe.io)**, or your cloud provider's workload identity documentation, for the no-secret-at-all model.
- **gitleaks** or **trufflehog** for scanning repositories and history. Run one against your history today; the results are usually educational.
- **Beyer et al., _The Site Reliability Workbook_, chapter 16 ("Canarying Releases").** How gradual rollout actually works operationally, which is the discipline that makes flags useful rather than just available.
- **Module 15** for entitlements as domain logic, **Module 29** for why trunk-based development needs flags, and **Module 34** for the audit requirements that shape secret handling.

A Java and Spring Boot sibling would be worth writing, because the framework changes the shape of the problem rather than the syntax. Spring's `@ConfigurationProperties` with JSR-303 validation gives you the typed, fail-at-startup binding above essentially for free, along with profiles and relaxed binding — arguably a better default than anything hand-assembled here. But it also offers `@Value("${some.key}")`, which injects individual values directly into any class, anywhere, and that affordance reintroduces precisely the scattered-lookup problem this article argues against, with framework blessing. An article about Spring config is therefore largely about which of the framework's two answers to use and why, plus `@RefreshScope` and the genuinely different failure modes of rebinding configuration in a running application. Not yet written.

---

The habit worth carrying out of this article is a question to ask of any value that varies: **what has to be true for this to change safely?** If the answer is "a code review and a test run," it belongs in code. If it's "an ops engineer at 3am with the site down," it belongs in dynamic config with an audit log. If it's "a product manager, for 5% of users," it's a flag with an expiry date. If it's "the platform, automatically, every hour, without anyone noticing," it's a leased secret.

Most configuration problems come from a value sitting one or two rows away from where its change process actually lives — and the cost of that mismatch is paid at the worst moment, because that's the only moment anybody looks.
