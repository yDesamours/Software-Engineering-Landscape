# Monolith vs Microservices

_Module 2.1 — Software Architecture Patterns_

## The Problem

A payroll product, four years old, nine engineers, one deployable. A customer asks for something that sounds small: when a contractor is marked inactive, exclude them from the next payroll run and send them a final payslip.

Two days of work, maybe three. Then someone opens the code to check.

`Contractor.Deactivate()` lives in the models package. It's called from four places: the admin console, the CSV importer, the nightly HR sync, and a support script. Nobody knows which of those should trigger a final payslip and which shouldn't, and the function has no way to tell them apart.

The payroll run selects its payees with a query assembled by a shared query builder. Reporting uses the same builder. Adding a status filter to the payroll path changes the shape of the builder, and two reporting columns depend on the current shape.

The payslip email lives in the notifications package, which imports payroll to format currency amounts. Payroll imports notifications to send the "run complete" email. That cycle was broken two years ago by moving both sets of interfaces into a package called `common`, which now has forty-one files in it and is imported by everything.

The estimate goes from three days to three weeks, and most of those three weeks is not writing code. It's establishing what else breaks.

Nothing here is bad code, exactly. Every individual step was reasonable at the time. The result is still that no one can predict the consequences of a change, which means every change is priced as if it might be catastrophic.

So the team does what teams do. They split it up. Six months later there are four services — `contractors`, `payroll`, `notifications`, `reporting` — each with its own repo, pipeline, and database.

Here is the same feature request, in the new world:

- It still touches four subsystems. Now they're four repos with four pull requests.
- The deploys have an ordering constraint: `contractors` must ship the new status field before `payroll` can read it, and `notifications` must accept the new payslip type before `payroll` sends it.
- Rolling back the middle one is a coordination exercise rather than a button.
- Payroll's run loop calls `contractors` once per payee. A 1,400-person run is now 1,400 round trips, and it fails halfway through on a timeout, leaving some payslips sent and some not. There is no transaction to roll back.

The split did not remove the coupling. It converted local coupling into remote coupling, and remote coupling is the same coupling with latency and partial failure added.

The thing that made the original change hard was that "a contractor is inactive" had no owner. It was a fact smeared across four subsystems, each of which had its own opinion about what it meant. A network hop does not give a fact an owner. It just makes the smear expensive.

## What It Is

Two different questions have been collapsed into one, and separating them is most of the value of this article.

**How is the code organized?** Is there a clear internal structure with owned responsibilities and enforced boundaries, or does everything reach into everything?

**How is it deployed?** Does the whole system ship as one unit, or as many units that can be released independently?

These are independent axes:

```
                    │  one deployable       │  many deployables
  ──────────────────┼───────────────────────┼──────────────────────
   enforced         │   MODULAR MONOLITH    │     MICROSERVICES
   boundaries       │   (boring, effective) │  (autonomy, at a price)
  ──────────────────┼───────────────────────┼──────────────────────
   no real          │    BIG BALL OF MUD    │  DISTRIBUTED MONOLITH
   boundaries       │   (where most start)  │  (worst square on the grid)
```

Most teams who say "we need microservices" are in the bottom-left square and want to be in the top-right. The move they actually need is upward. Moving right without moving up lands you in the bottom-right, which has every cost of distribution and none of the independence, because you still can't deploy any one piece on its own.

So, the names:

A **monolith** is a system deployed as a single unit. That's all the word means. It says nothing about size, quality, or internal structure. A well-structured 400,000-line monolith is a monolith; a 3,000-line tangle is also a monolith.

A **modular monolith** is a single deployable whose internals are divided into modules with explicit public surfaces, private internals, and owned data — where "explicit" means something mechanical enforces it, not that the team agreed to be careful.

**Microservices** are modules that have been given their own process, deployment pipeline, and (critically) their own data. A service that shares a database table with another service is not independent; it's two processes wearing one module's clothes.

The cleanest way to hold all three: **a service boundary is a module boundary plus a network.** The network is not a feature. It's the price. You pay it to get independent deployment, independent scaling, and independent failure. If you don't need those three things, you are paying and receiving nothing.

One neighbor worth disambiguating now, since it's the most common confusion in this module: **modularity is not layering.** Layering (Module 2.2) slices horizontally — controllers, services, repositories — so that every feature is spread thinly across all layers. Modularity slices vertically by domain, so `billing` owns its own controller, service, and repository. They compose fine, and most well-built systems have both. But a strictly layered codebase with no vertical boundaries is exactly the payroll system above: the `services` package has ninety files in it and every one of them can call every other.

## Recognizing the Problem

Two separate diagnoses, and they lead to different treatments.

**Your boundaries have failed** (the treatment is modularization, not services):

- Estimating a small change requires grepping the whole repo to find out what else touches it.
- A one-sentence feature request routinely touches code owned by three teams.
- There is a package called `common`, `shared`, `utils`, or `core` that everything imports and nobody owns.
- Merge conflicts cluster in the same four files, and they're the ones named after your central nouns: `User`, `Order`, `Account`.
- A schema change requires asking around, because five subsystems read that table and two of them write it.
- New hires take months to become productive, and the reason is not domain complexity — it's that no one can draw the system on a whiteboard.

**You need separate deployables** (modularization alone won't fix these):

- One subsystem's resource profile poisons the others: the PDF renderer pegs eight cores for forty seconds and API p99 goes from 80 ms to 2 s.
- The scaling unit is wrong: webhook ingestion takes 3,000 requests/sec while the rest of the app takes 40, and scaling for the spike means running thirty copies of the entire application.
- Deploy cadence genuinely conflicts: one part ships twenty times a day, another is in regulatory scope and needs sign-off per release.
- An availability requirement differs: the webhook receiver must keep accepting during the main app's deploys, or you lose events permanently.
- A subsystem genuinely needs a different runtime — GPU inference, a library that only exists on the JVM.
- The deploy pipeline has become a queue. Eight teams, a 45-minute merge queue, and a revert from one team blocks four others.

If you have signals only from the first list, extracting services will make your week worse and your year worse. If you have signals from the second list, no amount of internal tidiness will help, because the problem is physical.

## How It Works

### What a module boundary actually consists of

Four things, and the fourth is the one people skip:

1. **A public surface.** A small set of types and functions that outsiders may use. Everything else is invisible to them.
2. **Private internals.** Enforced by the compiler, the build system, or a lint rule that fails the build. A convention documented in the README is not a boundary; it's a wish.
3. **An explicit dependency direction.** Module A may depend on B, or B on A, but ideally not both. Cycles are how boundaries die: the moment you need a cycle, someone creates `common` and dumps the shared types there, and now every module depends on a package that belongs to no one.
4. **Owned data.** No other module reads or writes your tables. This is the one that gets skipped, and skipping it makes the other three cosmetic — if `reporting` can `SELECT` from `payroll_runs`, then payroll's schema is a public API whether or not anyone said so, and you will find out the day you try to change a column.

### What changes when a boundary becomes a network

The call looks identical in the calling code. Everything underneath it changes:

| In-process | Across a network |
|---|---|
| ~100 ns | ~1–10 ms, and occasionally 30 seconds |
| Succeeds or throws | Succeeds, fails, **or doesn't answer** — and "didn't answer" is not "didn't happen" |
| Arguments are just objects | Arguments must be serialized, versioned, and kept backward-compatible across deploys |
| One transaction spans both sides | No shared transaction. Consistency becomes something you design. |
| Rename a function: the compiler finds every caller | Rename a field: you find out in production, from a different team |
| Deploy together, always | Deploy independently — **this is what you're buying** |
| One scaling unit, one runtime | Scale, tune, and fail independently — **also what you're buying** |

Notice that the top five rows are costs and the bottom two are benefits. That ratio is the whole decision.

The corollary matters more than the table: **a boundary you can't hold in-process is one you definitely can't hold over a network.** If two modules are so entangled that you can't stop them reaching into each other inside a single process — where the compiler is on your side and refactoring is an afternoon — putting HTTP between them doesn't fix the entanglement. It just means the entanglement now has retry logic.

### Finding the boundaries

The hard part isn't enforcing boundaries, it's knowing where to draw them. Four sources of evidence, roughly in order of reliability:

**Data ownership.** For every table, ask who writes it. If exactly one subsystem writes a table and others only read, you've found a boundary and a candidate API. If three subsystems write the same table, you've found the thing preventing a boundary from existing.

**Change coupling.** Your git history already knows. Take the last year of commits and count, for each pair of top-level directories, how often a commit that touched one also touched the other:

```
  payroll/     ↔ contractors/     68%   ← not two modules; one module in two folders
  payroll/     ↔ notifications/   41%   ← leaky; probably a missing event
  reporting/   ↔ contractors/      4%   ← genuinely separate
```

High co-change means the boundary isn't where the directory names claim it is. This is the single cheapest diagnostic in this article and almost nobody runs it.

**Language drift.** When the same word means different things in two parts of the system — "account" is a login to one team and a billing entity to another — that's a boundary announcing itself. The systematic version of this idea is the bounded context, covered in Module 2.3.

**Team ownership.** Conway's law is not a warning, it's an observation: a system's structure tends to mirror the communication structure of the organization that built it. A boundary that cuts across a team will be violated, because violating it is a one-line change and respecting it requires a meeting. A boundary that matches team ownership maintains itself.

## When It's Appropriate

The default for essentially every new system, and for most existing ones, is a modular monolith. One deployable, real internal boundaries. It gives you the thing you actually wanted — changes with predictable blast radius — at roughly zero operational cost, and it keeps every boundary cheap to move while you're still wrong about where they go.

Extraction earns its cost in specific, nameable situations:

**Resource isolation.** A media-processing feature does 40-second CPU-bound transcodes. In-process, those compete with request handling; p99 latency triples during any batch. Moving transcoding to its own service lets it run on four large instances that can be starved, queued, and restarted without anyone noticing. The trigger is measurable interference, not the belief that CPU-heavy work "feels like" it belongs elsewhere.

**Scaling-unit mismatch.** Webhook ingestion is 2% of the codebase and 95% of the request volume, spiky to 3,000/sec. Scaling the monolith to absorb that means running thirty copies of a process that holds a large heap, a full connection pool, and a scheduler you only need one of. A 200-line receiver that writes to a queue can run on two small instances and scale to fifty in seconds.

**Availability isolation.** Payment provider webhooks must be accepted during deploys and during incidents in unrelated subsystems, because the provider retries a limited number of times and then gives up. A separate receiver whose only job is "write to durable storage, return 200" has an availability profile you can actually defend.

**Runtime or compliance boundaries.** An ML scoring path needs Python and a GPU. Or: card handling is in PCI scope, and keeping it inside the main deployable drags the entire codebase and every engineer with commit access into audit scope. Shrinking the audited surface from 400,000 lines to 6,000 is a real, quantifiable win that has nothing to do with performance.

**Organizational contention.** Somewhere around eight to ten teams on one pipeline, the queue itself becomes the bottleneck, and one team's bad merge blocks everyone. Below that, the pipeline is usually not your problem and splitting it will not make you faster.

Note what these have in common: every one of them names a specific pressure, and in most cases you can put a number on it. "We might need to scale someday" is not on the list. Module 1.2's point applies directly — a claim that can't be falsified can't be used to make a decision.

## When It's Unnecessary or Overkill

**You don't know where the boundaries go yet.** This is the big one, and it's about the asymmetry of mistakes. Moving a responsibility between packages in one codebase is an afternoon and a compiler. Moving a responsibility across a service boundary is a data migration, a contract change, a dual-write period, two deploys, and a rollback plan. Early-stage products get boundaries wrong constantly — not from carelessness, but because the domain isn't understood yet. Being wrong inside a monolith is cheap. Being wrong across services is a quarter.

**Your team is smaller than your service count.** Five engineers and twelve services means every engineer context-switches across several, no service has an owner, and you've taken on all the coordination cost of distribution while getting none of the team autonomy that justifies it. The benefit of microservices is organizational before it is technical, and if there's no organization to serve, there's no benefit.

**The numbers don't support it.** A million requests a day is twelve per second. Any of the stacks from Module 1.3 handles that on the smallest instance a cloud will rent you, with the machine mostly idle. Splitting for throughput at that volume is solving a problem you don't have with a tool that creates several you will.

**You'd be lowering your availability.** Module 1.2 covered the arithmetic: independent components multiply. A request path that fans out synchronously across four services, each at 99.9%, is a 99.6% path — worse than any individual part, and worse than the monolith it replaced. Distribution buys you *isolated* failure only when the interactions are asynchronous or the callers degrade gracefully. A synchronous call chain is just a longer fuse.

**You're doing it to use more languages.** Module 1.3's language N+1 argument applies with force here: every additional runtime multiplies build tooling, base images, dependency scanning, observability wiring, and the set of people who can be on call. Polyglot is a cost you should pay for a disqualifier, not a preference.

**The database stayed shared.** If the extracted services still read each other's tables, you have a distributed monolith: coordinated deploys, shared schema migrations, and network latency in between. This is the bottom-right square, and it is strictly worse than where you started.

## Trade-offs

Both end states cost something once you have them. Neither is free, and the comparison is only honest if you look at both.

**What a modular monolith costs:**

- **Boundaries decay unless something mechanical holds them.** The compiler, an import-restriction lint rule, an architecture test in CI. Without one, the boundary lasts until the first deadline.
- **One blast radius for deploys.** A bad migration or a memory leak in the reporting module takes down checkout. You can mitigate with feature flags and careful rollouts, but the coupling is real.
- **One scaling unit.** You scale the slowest thing by replicating everything, including the parts that didn't need it.
- **One runtime.** One language, one heap, one GC pause, one set of library versions. A dependency conflict between two modules is your problem to resolve, not something you can route around.
- **The database is the leak.** Unless you separately enforce table ownership — separate schemas, separate DB roles, per-module credentials — modules will quietly join across each other and you'll have a distributed monolith without even getting the distribution.

**What microservices cost:**

- **A platform tax, paid before the first service is useful.** Service discovery, per-service pipelines, secret distribution, a way to run a realistic subset locally, and distributed tracing — because without tracing, "which of the nine hops was slow" is unanswerable (Module 19).
- **Partial failure everywhere.** Every call gains a timeout, a retry policy, and a decision about what to do when the answer never comes. Retries require idempotency, which is a design constraint on every write endpoint you own.
- **Transactions become workflows.** "Deactivate the contractor and issue the final payslip" was one transaction; now it's a multi-step process with compensations, which is the saga pattern (Modules 2.4 and 37). It's a substantially harder thing to get right and to test.
- **Data gets duplicated and goes stale.** Payroll needs a contractor's name on the payslip. Calling for it on every render is a latency and availability coupling; caching it means displaying a name that changed an hour ago. There is no option that is both fast and fresh.
- **Contracts need versioning and ordered rollout.** Any change to a shared type is a two-phase deploy: add the new field, deploy consumers, then remove the old. Every time.
- **On-call surface grows with service count**, and cross-cutting changes ("add a tenant ID to every log line") become a campaign rather than a commit.

One asymmetry is worth stating plainly: the monolith's costs are mostly *ceilings* — limits you hit as you grow. The microservices costs are mostly *floors* — paid on day one, every day, regardless of scale. That asymmetry is why "start with the monolith" is the standard advice, and it's not conservatism. It's that you can convert a monolith into services later with effort, but you cannot un-pay the platform tax you spent your first year on.

## Alternatives

**Fix the coupling in place.** The most common right answer, and the one nobody presents at conferences. Introduce a module boundary, move the shared types into the module that owns them, delete `common`, add an import rule to CI. This addresses the actual complaint in the Problem section and requires no new infrastructure.

**One codebase, multiple entry points.** Underrated and often exactly enough. Build one binary from one repo with one pipeline, but run it in several modes: `serve api`, `serve webhooks`, `run worker`. You get independent scaling and resource isolation — the top two reasons in the "When It's Appropriate" list — without independent deployment, without contracts, without a second database, without distributed transactions. Deploys remain atomic across all modes, which is a real limitation, but you'd be surprised how often the thing you needed was a separate process rather than a separate service.

**Enforce data ownership inside one database.** Give each module its own schema and its own database role, granted access only to its own tables. Cross-module reads then fail at the database, immediately and loudly, instead of being discovered years later. This is often the highest-value single change available to an existing monolith, and it's also the step that makes a future extraction tractable.

**Extract to a library instead of a service.** Separates code and version lifecycles without adding a network. Good for genuinely reusable infrastructure; bad for domain logic, because you gain version skew across consumers and still share the runtime.

**Serverless functions for the isolated, spiky piece.** If the case for extraction is one specific stateless workload with a bursty profile, a function may cost less to operate than a service (Module 41).

And the hybrid, which is where most mature systems actually land: **a substantial modular monolith surrounded by a small number of extracted services**, each extracted for a reason you could write on one line. Not a transitional state on the way to "full microservices" — a stable, deliberate end state. The question is never "monolith or microservices." It's "which specific pieces have earned their own deployment, and what does the rest stay as."

## How to Achieve It

A ladder, in an already-running system. Each rung is independently valuable, and the point is that you stop when the pain stops — not that you climb to the top.

**L0 — One package, free imports.** Everything can reach everything. Where most systems are.

**L1 — Directories by domain.** Move files so that top-level folders are `billing`, `payroll`, `contractors` rather than `controllers`, `services`, `models`. Imports are still unrestricted, so this changes nothing mechanically — but it makes the violations visible, and it's the cheapest step you will ever take. Run the change-coupling analysis afterward to see which of your new boundaries are fiction.

*Move on when:* the folder structure looks clean but co-change percentages say otherwise.

**L2 — Enforced internals.** Each module gets one public file; everything else becomes private, enforced by the language or by a build-failing lint rule. This is where the real work is, because every violation you fix is a design decision about who owns what. Expect `common` to fight back.

*Move on when:* imports are clean but modules still read each other's tables.

**L3 — Owned data.** Each table gets exactly one owning module. Cross-module joins get replaced by calls to the owner's public API, or by a read model the owner maintains. Enforce it with per-module database roles so violations fail rather than accumulate. This is the hardest rung and the one that determines whether extraction is ever possible.

*Move on when:* a module needs to react to something rather than ask about it.

**L4 — In-process events.** Where a module currently calls another to say "this happened," publish an event on an in-memory bus instead. Same process, same transaction boundary initially, but the shape of the dependency inverts: `payroll` no longer imports `notifications`, it emits `PayrollRunCompleted`. The cycle in the Problem section dissolves at this rung. Keep the bus's interface shaped like a real broker's, because that's what it becomes later.

*Move on when:* a specific module hits one of the pressures in "When It's Appropriate" — and not before.

**L5 — Extract one module.** One. The interface already exists and has exactly one consumer-facing shape, so the change is swapping the implementation behind it. Run both paths in parallel behind a flag, compare results, then cut over and delete the old one. Extract the next one only when it has its own reason.

The reason this ladder works is that rungs 1 through 4 pay for themselves whether or not you ever reach 5 — and if you do reach 5, extraction is a week instead of a quarter, because the work microservices demand *up front* has already been done incrementally under compiler supervision.

## Implementation

Go, because its `internal` rule enforces module boundaries at compile time with no framework, no build plugin, and nothing to configure — which makes the mechanism unusually visible.

### The layout

```
cmd/
  app/main.go                  ← one binary, one deploy
internal/
  payroll/
    payroll.go                 ← the entire public surface of this module
    internal/
      run/                     ← importable ONLY from internal/payroll/...
      rates/
  contractors/
    contractors.go             ← public surface
    internal/
      store/
  platform/
    db/
    events/
```

Go's rule: a package inside a directory named `internal` may only be imported by code rooted at that directory's parent. So `internal/payroll/internal/run` is reachable from `internal/payroll/...` and from nowhere else in the program. If someone in `contractors` tries to import it, the build fails. Not a review comment — a build failure.

That's rung L2, achieved by naming directories carefully.

### The public surface, and who defines it

```go
// internal/payroll/payroll.go
package payroll

// Contractors is what payroll needs from the contractor module.
// It is declared HERE, by the consumer — four methods, not the forty
// that the contractors module actually exposes.
type Contractors interface {
	ActiveOn(ctx context.Context, orgID string, day time.Time) ([]Payee, error)
}

// Payee is payroll's own type. It is deliberately not contractors.Contractor.
type Payee struct {
	ID        string
	Name      string
	RateCents int64
}

type Service struct {
	contractors Contractors
	db          *db.Pool
}

func (s *Service) Run(ctx context.Context, orgID string, period Period) (Summary, error) {
	payees, err := s.contractors.ActiveOn(ctx, orgID, period.End) // one call, not one per payee
	if err != nil {
		return Summary{}, fmt.Errorf("payroll: fetching payees: %w", err)
	}
	// ...
}
```

Two things are doing the work here, and both are about limiting what a future change can break.

The interface is declared by the **consumer**, not the provider. Payroll states what it needs; the contractors module satisfies it. That means adding the thirty-seventh method to `contractors` cannot affect payroll, and it means you can read `payroll.go` and know the complete set of things this module depends on.

`Payee` is payroll's own struct. If it were `contractors.Contractor`, then every field of that struct — including the ones payroll never touches — would be part of the contract between them, and payroll would break when contractors renamed something irrelevant. Copying three fields into a local type feels like duplication; it's actually the boundary.

### The same interface, two implementations

```go
// In-process. A function call: ~100ns, and it cannot fail on its own.
type localContractors struct{ svc *contractors.Service }

func (l localContractors) ActiveOn(ctx context.Context, orgID string, day time.Time) ([]payroll.Payee, error) {
	cs, err := l.svc.ActiveOn(ctx, orgID, day)
	if err != nil {
		return nil, err
	}
	out := make([]payroll.Payee, len(cs))
	for i, c := range cs {
		out[i] = payroll.Payee{ID: c.ID, Name: c.DisplayName(), RateCents: c.Rate.Cents()}
	}
	return out, nil
}
```

```go
// Over HTTP. Same signature. Entirely different failure model.
type remoteContractors struct {
	base string
	http *http.Client // with a timeout — the zero-value client waits forever
}

func (r remoteContractors) ActiveOn(ctx context.Context, orgID string, day time.Time) ([]payroll.Payee, error) {
	req, _ := http.NewRequestWithContext(ctx, "GET",
		fmt.Sprintf("%s/orgs/%s/contractors/active?on=%s", r.base, orgID, day.Format(time.DateOnly)), nil)

	resp, err := r.http.Do(req)
	if err != nil {
		return nil, fmt.Errorf("contractors unavailable: %w", err)
	}
	defer resp.Body.Close()
	// decode, map to []payroll.Payee ...
}
```

Wiring in `main.go` picks one. That's L5: a line of configuration, because the boundary was already real.

Three things worth noticing right where they appear, rather than saving them for a trade-offs section:

**`err` changed meaning.** In `localContractors`, an error means the database said no — the call definitively did not happen. In `remoteContractors`, an error can mean "I sent the request and never heard back," which is not the same as "it didn't happen." For a read like this one it's merely annoying. For a write, it's the central difficulty of distributed systems: you must either make the operation idempotent (send a client-generated request ID and have the server deduplicate) or accept that retrying may do it twice.

**Interface granularity is now load-bearing.** `Run` fetches all payees in one call. If the loop had been written the other way — `for each payee: contractors.Get(id)` — the in-process version would be indistinguishable in a profile, and the remote version would be 1,400 sequential round trips, exactly the failure from the Problem section. An interface shaped for in-process calls is frequently the wrong shape for a network, and the difference is invisible until the day you extract.

**Nothing in `payroll` changed.** Not the business logic, not the tests, not the import list. That's the payoff of rungs 1 through 4: extraction became a configuration change because all the design work had already happened where the compiler could check it.

## Further Reading

- **Sam Newman, _Building Microservices_ (2nd ed., O'Reilly, 2021).** The reference text. Chapters on decomposition and on the costs of distribution are the relevant ones here.
- **Sam Newman, _Monolith to Microservices_ (O'Reilly, 2019).** Specifically about extraction from a running system: strangler fig, branch by abstraction, and the database decomposition patterns that L3 above is a summary of.
- **Martin Fowler, "MonolithFirst" and "Microservice Premium"** (martinfowler.com/bliki). Two short pieces that make the cost-asymmetry argument better than anything of comparable length.
- **Simon Brown, "Modular Monoliths"** (talk and the accompanying material in _Software Architecture for Developers_). The clearest statement of the two-axis framing this article opens with.
- **Shopify Engineering, "Deconstructing the Monolith" (2019).** A large, genuinely modular Rails monolith and the tooling they had to build to keep it modular. Concrete about what enforcement costs.
- **Amazon Prime Video Tech Blog, "Scaling up the Prime Video audio/video monitoring service and reducing costs by 90%" (2023).** A distributed pipeline consolidated back into a single process. Useful mainly as an antidote to the assumption that decomposition is a one-way ratchet.
- **Eric Evans, _Domain-Driven Design_, Part IV.** Bounded contexts and context maps — the systematic version of the "language drift" heuristic above. Module 2.3 covers this directly.
- **Skelton & Pais, _Team Topologies_ (IT Revolution, 2019).** Conway's law treated as a design input rather than a warning, which is what makes the team-ownership heuristic usable.
- **Kleppmann, _Designing Data-Intensive Applications_, chapter 8.** "The Trouble with Distributed Systems." Read this before you extract anything, particularly the sections on unreliable networks and unbounded delays.
- **The Go Modules Reference, "internal" directories** (go.dev). Two paragraphs, and it's the whole enforcement mechanism used above.

A Java sibling to this article would be worth writing, and it wouldn't be a translation. Spring Modulith takes the opposite approach to enforcement: instead of a compile-time rule, it verifies module boundaries with a **test** that inspects package structure and dependencies at build time, and it provides module-level application events with `@ApplicationModuleListener` — meaning rung L4 arrives as a framework feature rather than something you build. That's a genuinely different answer to the same problem, with its own failure mode: a test can be skipped, ignored, or annotated away in a manner a compiler error cannot, and the boundary is only as strong as the discipline around the suite. It also brings transactional event publication into the picture, which changes the reliability story for L4 considerably. Not yet written.

---

The habit worth carrying out of this article is the two-axis check itself. When someone proposes infrastructure to solve a problem, ask which axis the problem is on. "We can't change anything safely" is a design problem, and no deployment topology fixes it. "We can't deploy without blocking four teams" is a topology problem, and no amount of refactoring fixes that one. Most bad architecture decisions are a correct diagnosis of one axis treated with a remedy from the other.
