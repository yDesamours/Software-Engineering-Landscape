# Converging a Release: Bug Bars, Freezes and Cutting Scope

_Module 43 · Finishing Software · 43.1a_

## The Problem

Suppose you build scheduling software for secondary schools: timetables, room bookings, cover for absent teachers. Schools build next year's timetable over the summer, so this year's big release, a new timetable builder with a constraint solver, 11 features in all, is promised for **June 2**. Fourteen engineers in three teams, one QA engineer, and sales has told forty districts the date.

On **April 14** the last feature merges and the team declares "feature complete." Status reports say 90% done. They keep saying it for nine weeks.

**The bug count goes the wrong way.** Now that every feature exists, people can finally use them together, and testing finds about 35 bugs a week. The team fixes about 25. The open count climbs from 60 to 110 while everyone works flat out.

```
open bugs
 110 |                          ●●●
     |                     ●●●●
  80 |               ●●●●●
     |         ●●●●●
  60 | ●●●●●●●
     +--------------------------------→ weeks after "feature complete"
       1   2   3   4   5   6   7   8
     found ≈ 35/wk   fixed ≈ 25/wk   nothing converges
```

**Everything is P1.** The triage question is "is this bad?", and for 70% of bugs the honest answer is yes. A misaligned column header and a solver that double-books a teacher carry the same label. Engineers pick whichever P1 looks quickest.

**Fixes make new bugs.** A fix to the period-overlap check breaks double-period science labs. A fix to that breaks the export. By week 3, a third of each week's new bugs are in code changed the previous week.

**Features keep arriving.** A large district needs split-site support, "just a toggle," and it merges on May 20. It touches the solver, the room model and the export. Eleven new bugs follow.

**The freeze hurts everyone.** On May 12 the release manager freezes `main`. The two teams not on the timetable builder stop merging; their pull requests pile up. When the freeze lifts, 60 of them merge in two days and the week's regressions triple.

**The date moves a week at a time.** June 2 becomes June 9, then June 16. On June 18 a vice-president cuts three features in one meeting. They're removed by reverting commits, and the reverts cause bugs of their own. The release ships on June 23 with a CSV-export bug that one district's payroll import depends on. Schools lose three weeks of the summer they needed.

Nobody was lazy, and the code wasn't unusually bad. The release never had a way to **converge**: no shared answer to "which bugs stop us shipping?", no signal showing whether the pile was shrinking, no limit on what could still change, and no plan for what to drop.

## What It Is

Getting a set of changes from "all written" to "shippable" is called **stabilization**, and the practices that make it finish on purpose are sometimes called **release convergence**. The main tools:

- **Exit criteria**: what must be true to ship, agreed before stabilization starts.
- **A bug bar**: a written rule, based on impact, for which bugs block the release, which ship as known issues and which wait. It **rises** as the date approaches, so fewer changes qualify.
- **Freezes**: points after which certain kinds of change (new features, user-facing text, any code) stop entering the release without an exception.
- **A cut line**: a ranked list, decided early, of what gets dropped if time runs out.

This is not the same as a **production readiness review** (35.1a), which asks whether the system can be operated safely: alerts, capacity, runbooks. Convergence asks whether this particular set of changes has stopped generating problems. A release needs both answers, and a good readiness review can't rescue a change set that's still churning.

## Recognizing the Problem

- "90% done" has been the status for weeks.
- After feature complete, the open bug count is flat or rising.
- Most bugs share the top priority label.
- Whether a bug blocks the release is argued case by case, and the answer depends on who's in the room.
- Recent fixes keep causing new bugs, or bugs get reopened.
- Features are still merging in the final week or two.
- The release date moves in one-week steps.
- Freezing the release freezes everyone, including teams not in it.
- Scope gets cut late, all at once, by someone who wasn't in the details.

## How It Works

### 1. Why the last 10% expands

Tom Cargill's joke, the "ninety-ninety rule," is that the first 90% of the code takes 90% of the time and the remaining 10% takes the other 90%. There's a mechanical reason for it. Before feature complete, most work is building things, and progress is visible. After it, the work is discovering what's wrong with things that exist, and you can't estimate what you haven't found yet. Integration, edge cases and features meeting each other only become testable at the end. So "90% done" measures code written, not problems remaining.

The practices below don't make the unknown work disappear. They make it **visible**, **bounded**, and **decided in advance** where possible.

### 2. Measure convergence, not effort

The one question that matters during stabilization is whether the pile is shrinking. Track, weekly:

- **Found**: new bugs opened.
- **Fixed**: bugs closed as actually fixed. Closing as "won't fix" or moving to a later release is a separate count.
- **Reopened**: fixes that didn't hold.
- **Fix-induced**: new bugs caused by recent fixes.

The release converges when **fixed exceeds found plus reopened**, week after week. Microsoft teams named the moment when the backlog first hits zero **zero bug bounce (ZBB)**: every bug is either fixed or explicitly deferred, and new ones get handled as they arrive. It "bounces" because testing keeps finding more. Reaching it means the fix rate has overtaken the find rate. The planned downward line to ZBB is called the **glide path**.

```
open bugs
   ▲        find > fix              fix > find
   │          ╱‾‾‾‾‾‾╲
   │        ╱          ╲          glide path
   │      ╱              ╲  ·  ·  ·
   │    ╱                  ╲ ·
   │  ╱                      ╲·      ZBB   bounce
   └──────────────────────────────────●─╱╲─╱╲──→ time
        feature complete ▲
```

A rising fix-induced rate is the most important early warning. It means the codebase is too unstable for the changes being made to it, and the answer is fewer changes, not faster ones.

### 3. A bug bar decides in advance

Priority labels fail because they're relative ("more urgent than that one") and assigned under pressure. A bug bar replaces them with questions about **impact** that anyone can answer the same way:

| Question | Examples of answers that raise severity |
|---|---|
| What's affected? | Data loss or corruption, security, money, a legal obligation |
| How central is it? | Core flow every user takes vs. a rarely used setting |
| How many users? | Every school vs. schools with split sites |
| Is there a workaround? | None vs. a documented one |
| Is it a regression? | It worked in the last release |

The bar maps those answers to an outcome: **block**, **fix if the fix is safe**, **ship as a known issue**, or **next release**. Microsoft's Security Development Lifecycle publishes a well-known example for security bugs, with severities defined by effect (remote code execution, elevation of privilege, and so on) rather than by gut feel. Your product bar does the same for your domain. For the timetable builder: "double-books a teacher or room" always blocks, and "cosmetic, with no effect on data" never does.

The bar **rises over time**. Early in stabilization, most real bugs get fixed. Near the end, only bugs meeting the release's most critical criteria do, because every change now carries risk the release can't absorb. At the very end, a fix needs approval to land at all, and the approver asks whether **the fix is riskier than the bug**. A cosmetic bug whose fix touches the solver waits for the next release, even though it's easy to fix.

The top category deserves a name. Raymond Chen describes Microsoft's "recall class" bugs, severe enough that the product would be recalled if it shipped with them. Writing yours down ("wrong timetable data, lost edits, one school seeing another's data") keeps the most important argument from happening at 11 p.m. before release.

Deferring is a real decision, not a way of hiding bugs. Every "known issue" goes on a list that support, sales and release notes see before launch.

### 4. Narrow what can still change

Freezes limit what enters the release, in stages from least to most restrictive:

- **Feature freeze**: no new features, only fixes to existing ones. This is where the split-site toggle should have been refused or sent to the next release.
- **String freeze**: user-facing text stops changing, so translators and documentation can finish (Module 25).
- **Code freeze**: only fixes that meet the current bar, each approved.

Large projects stage these on a published calendar. Kubernetes runs roughly 15-week release cycles with separate deadlines for production readiness review, enhancements, code and tests, and documentation, with exceptions requested explicitly. The staging matters: each freeze removes one source of churn while leaving time for the work that depends on it.

### 5. Freeze a branch, not the team

Freezing `main` stops every team to protect one release. The alternative is a **release branch**: at the branch point, the release is copied to its own branch and stabilized there, while `main` keeps moving.

```
main    ──●──●──●──●──●──●──●──●──●──●──→   (next release keeps going)
               ╲         ↓ cherry-pick
release         ●────●───●────●──●  → ship
             branch   fixes land on main first,
              point   then get copied here if they pass the bar
```

Chromium works this way. A new milestone is developed on `main` for four weeks, then branched and stabilized for four more before shipping, with a new stable release every four weeks. Fixes land on `main` first and are copied (cherry-picked) to the release branch only after a merge review weighs the fix's risk against its benefit.

This keeps the freeze where it belongs and makes the bar concrete: the question for every change becomes "does this get copied onto the branch?" The cost is that every fix is applied and tested twice, so it pays off only when stabilization takes long enough for teams to otherwise sit idle.

### 6. Separate deploying from releasing

For continuously deployed services, **feature flags** (30.2) change the whole picture. Code for unfinished features can ship turned off, so the "release" becomes a decision about which flags to turn on, and for whom. Stabilization then happens per feature, often through staged exposure (35.2a), rather than for a whole batch at once.

It also changes how scope gets cut. Turning a flag off is fast, reversible and doesn't touch code. Reverting commits under deadline pressure touches code and causes new bugs, as it did in June.

Flags don't remove the need to converge. A flag that's on for a district is released for that district, and its bugs count.

### 7. Cut scope early, whole, and from a list

When a fixed date is at risk, only three levers exist: the date, the scope, and the quality. Adding people late mostly doesn't help. Fred Brooks's observation that adding people to a late project makes it later holds because newcomers need the attention of the people doing the fixing. Lowering quality means shipping bugs from the recall class. That leaves scope and the date.

Cutting scope works when it follows three rules:

- **Decide what's cuttable before you need to.** Rank features at planning time, "must, should, could" (MoSCoW) or simply an ordered list, with the reason each is where it is. The cut line then moves along a list that was agreed in calmer times, instead of being drawn in one tense meeting.
- **Cut whole features, not a bit of everything.** Eleven features each 90% finished ship nothing. Eight finished features and three cut ones ship eight.
- **Cut early.** A feature cut in week 2 of stabilization frees its bugs and its testing time for everything else. A feature cut in the last week has already consumed both, and removing it is risky too.

If a fixed date is truly immovable, the list is your plan. If it isn't, **say so early** and move the date once, by a realistic amount. Three one-week slips cost more trust than one three-week slip.

### 8. Exit criteria, written first

All of this depends on exit criteria set before stabilization begins, because the criteria define the bar and the bar defines the work. Typical criteria:

- No open bugs in the recall class; no open regressions in core flows.
- Fixed exceeds found for two consecutive weeks, and the fix-induced rate is low.
- The known-issues list has been reviewed by support and sales.
- The cut line has been applied and the release notes match what ships.
- Operational readiness is signed off (35.1a).

## When It's Appropriate

- **An immovable external date**: the school year, tax season, a regulatory deadline, a conference keynote.
- **Releases shipped as a batch that users install**: mobile apps going through store review, desktop software, on-premises products, SDKs, firmware. Rolling back these means asking every user to update.
- **Several teams landing work into one release**, where each team's changes can break the others'.
- **Expensive mistakes**: payroll, billing, anything where a bug turns into wrong data for many customers at once.
- **A stabilization phase that already exists and keeps overrunning.** Most teams need a bug bar and a find/fix chart more than a new process.

## When It's Unnecessary or Overkill

- **Small changes deployed continuously**, behind flags, with fast rollback. Each change is stabilized on its own, and formal freezes would only slow it down.
- **Teams small enough to discuss every bug together.** With three engineers, a whiteboard does what a bug bar does.
- **Internal tools** with a handful of users and no deadline.
- **"Hardening sprints" as a routine.** If every release needs a dedicated stabilization period, quality work is being postponed from the rest of the cycle. A permanent hardening phase is usually a symptom (28.4, Definition of Done) rather than a process to perfect.

## Trade-offs

- **Freezes queue work.** Anything blocked by a freeze builds up and lands together afterwards. The post-freeze merge storm is a predictable source of regressions. Release branches reduce it at the cost of doing each fix twice.
- **Cherry-picks drift.** A fix copied to a branch can behave differently there, because the surrounding code differs. The release branch needs its own testing.
- **The bar ships known bugs.** That's the point, and it still has costs: support tickets, users who hit them, and a known-issues list that must actually be read.
- **Triage takes time.** Daily triage in the final weeks means several senior people spend an hour a day on it.
- **Numbers invite gaming.** If ZBB is a celebrated milestone, severities get downgraded and bugs get closed as "can't reproduce." Watch the reclassification rate along with the count.
- **Deferral piles up.** Everything "moved to the next release" becomes the next release's first problem unless someone triages it again.
- **Cutting scope has political costs.** Customers were promised things. Cutting early reduces the damage, and it doesn't eliminate it.
- **Flags add states.** Every flag doubles the number of combinations that could be tested, and flags left on permanently become debt (31.3a).

## Alternatives

- **Small batches, shipped continuously.** Avoid the convergence problem by never letting changes pile up. For SaaS backends this is often the better answer, and it doesn't work well for installed software or big-bang external dates.
- **Release trains.** Fixed dates, variable scope: whatever meets the bar by the branch point ships, and everything else catches the next train. Chromium and Kubernetes both work this way. Trains take away the "which date?" argument and make the cut line automatic, at the cost of never promising a specific feature on a specific date.
- **Move the date.** Sometimes correct, especially early and once. It has to be decided on evidence (the find/fix trend), not hope.
- **Ship with known issues, then limit exposure.** Staged rollouts (35.2a) and post-launch triage (35.4a) can take some pressure off stabilization. They don't help with the recall class.

## How to Achieve It

**Step 1: write the bar and the exit criteria before feature complete.** Even half a page. Name the recall class. _Signal to move on:_ triage arguments get shorter, and they're about facts ("how many schools use split sites?") rather than feelings.

**Step 2: track find, fix, reopened and fix-induced every week,** in one chart everyone sees. Give triage a single owner. _Signal:_ you can tell whether you're converging, and when you aren't, you need something to change the trend.

**Step 3: make a ranked cut line at planning time**, and use it at the first sign the glide path isn't on track. _Signal:_ cuts are happening, but stabilization still stalls other teams.

**Step 4: stabilize on a release branch,** with a fix-first-on-main rule and merge review against the bar. Stage feature and string freezes on a calendar. _Signal:_ the process works, but every release is still a large batch.

**Step 5: decouple release from deploy with flags,** and consider a train with a fixed schedule. Stabilization becomes routine rather than an event.

## Implementation

TypeScript, in two pieces. The first is a bug bar as code, so every bug gets the same answer regardless of who's triaging. The second is a weekly convergence report.

```ts
type Phase = "stabilizing" | "lockdown";

type Bug = {
  id: string;
  impact: "wrong-data" | "security" | "core-flow" | "secondary-flow" | "cosmetic";
  regression: boolean;          // worked in the last release
  workaround: boolean;          // documented, usable by a school admin
  affectedShare: number;        // 0..1 of schools that can hit it
  fixRisk: "low" | "medium" | "high"; // judged from what the fix touches
};

type Outcome = "block" | "fix-if-safe" | "known-issue" | "next-release";

// The recall class never depends on phase or on how risky the fix is.
const RECALL_CLASS = new Set<Bug["impact"]>(["wrong-data", "security"]);

export function bugBar(bug: Bug, phase: Phase): Outcome {
  if (RECALL_CLASS.has(bug.impact)) return "block";

  const coreBreak = bug.impact === "core-flow" && !bug.workaround;
  if (coreBreak && (bug.regression || bug.affectedShare > 0.1)) return "block";

  if (phase === "stabilizing") {
    return bug.impact === "cosmetic" ? "next-release" : "fix-if-safe";
  }

  // lockdown: the bar has risen. A fix must be both needed and low-risk.
  if (bug.impact === "core-flow" && bug.fixRisk === "low") return "fix-if-safe";
  return bug.workaround ? "known-issue" : "next-release";
}
```

> **Aside: where the outcome goes.** "known-issue" isn't a quieter "won't fix." Each one should generate an entry on the release's known-issues list, with the workaround, before launch. That list is what support reads on the first day, and it's what keeps the bar honest: a bug nobody wants to explain to customers tends to be moved back up.

> **Aside: the bar is in code, the judgment isn't.** `affectedShare`, `workaround` and `fixRisk` are still judgments. Putting the rule in code makes those inputs the thing people discuss, and it makes changes to the rule itself visible in review. Changing `0.1` to `0.3` the week before launch should need a reason.

The report answers the one question that matters: is the pile shrinking, and is it safe to keep changing code?

```ts
type Week = {
  found: number;
  fixed: number;       // actually fixed, not deferred
  reopened: number;
  fixInduced: number;  // new bugs traced to last week's fixes
  downgraded: number;  // severity lowered after filing
  open: number;
};

export function convergence(weeks: Week[]) {
  const recent = weeks.slice(-3);
  const netBurn = recent.map(w => w.fixed - w.found - w.reopened);
  const converging = netBurn.every(n => n > 0);

  const last = weeks[weeks.length - 1];
  const warnings: string[] = [];

  if (last.fixInduced / Math.max(last.found, 1) > 0.25)
    warnings.push("Fixes are causing bugs: raise the bar, fewer changes");
  if (last.downgraded / Math.max(last.found, 1) > 0.2)
    warnings.push("Many severity downgrades: check the bar isn't bending");

  // Only project a date when the trend supports one.
  const avgBurn = netBurn.reduce((a, b) => a + b, 0) / netBurn.length;
  const weeksToZero = converging ? Math.ceil(last.open / avgBurn) : null;

  return { converging, weeksToZero, warnings };
}
```

> **Aside: why no projection when it isn't converging.** A straight line through a rising count predicts "never," and a straight line through one good week predicts "Tuesday." Both get repeated in status meetings as if they were estimates. Refusing to project until three consecutive weeks of positive burn is a small way to keep a hopeful number out of a slide deck.

For the schools release, this report would have shown a negative burn and a fix-induced rate over 30% by week 3, about a month before the first slip. That was the moment to apply the cut line and refuse the split-site toggle, while both were still cheap.

## Further Reading

- **Chromium: Chrome Release Cycle** and **Merge Request Process** (chromium.googlesource.com, `docs/process/`). A long-running example of a train with a branch point, a stabilization period, and a merge review that weighs fix risk against benefit.
- **Kubernetes SIG Release: release information for each version** (github.com/kubernetes/sig-release, `releases/`). A public calendar of staged freezes and the exception process.
- **The Linux kernel development process** (kernel.org documentation, "How the development process works"). A two-week merge window followed by weekly release candidates, with a strict rule against regressions.
- **Microsoft Security Development Lifecycle: SDL Bug Bar** (microsoft.com/msrc/sdlbugbar) and the sample bug bar on Microsoft Learn. The model for defining severity by effect.
- **Raymond Chen, "Microspeak: ZBB, recall class, glide path, and RTM"** (The Old New Thing). Short definitions of the vocabulary used here, from inside Microsoft.
- **Eric Lippert, "Bouncing Zero Bugs, Together"** (Microsoft Learn archive). What reaching ZBB meant on a very large product.
- **Frederick P. Brooks, _The Mythical Man-Month_**. The origin of Brooks's law, and still the best account of why late projects get later.
- **Pete Hodgson, "Feature Toggles (aka Feature Flags)"** (martinfowler.com). The categories of flags and how to keep them from becoming debt.
- **In this collection:** 28.4 (Definition of Done), 29.1 (trunk-based development and branching), 30.2 (flags and canary releases), 31.3a (flags and deferrals as debt), 35.1a (production readiness reviews), 35.2a (staged launches), 35.4a (triage after launch).

No sibling in another language is proposed: the substance is a process, and the code would say the same thing in any language.

---

The habit to take from this: when someone says a release is "nearly done," ask for the find/fix chart and the cut line. If neither exists, the release has no way of finishing on purpose.
