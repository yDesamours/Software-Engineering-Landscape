# Authorization in the Graph

_Module 8.4 — GraphQL APIs_

## The Problem

An HR platform. Employees, teams, performance reviews, compensation. The rule about compensation is written down and everyone knows it: **you can see your own, your direct and indirect reports', and HR can see everyone's.** Peers cannot see each other's.

In the REST API this was one guard on one route:

```
GET /employees/{id}/compensation
    → requester is {id}, or is in {id}'s manager chain, or has role HR
```

One place. Reviewable in thirty seconds. Nothing else in the system returns compensation.

The GraphQL schema is a faithful translation of the domain:

```graphql
type Employee {
  id: ID!
  name: String!
  title: String!
  compensation: Compensation      # guard lives in this resolver
  manager: Employee
  directReports: [Employee!]!
  team: Team
}

type Team  { name: String!  members: [Employee!]! }
type Query { viewer: Employee!  employee(id: ID!): Employee  search(q: String!): [Employee!]! }
```

Someone writes the guard on `Query.employee`, because that's where the REST guard was, and ships.

Now count the ways to reach an `Employee` node:

```
  viewer
  viewer.manager
  viewer.manager.directReports      ← every one of your peers
  viewer.team.members               ← your entire team
  viewer.directReports[*].manager
  search(q: "…")
  employee(id: …)                   ← the only one that was guarded
```

And the type is cyclic, so `viewer.manager.directReports[2].manager.directReports[0]` walks sideways and upward as far as anyone cares to type. A junior engineer reads the whole company's salaries in one query, over a field nobody thought of as an entry point, because it isn't one — it's an edge.

That's failure mode one, and it's *the* GraphQL authorization bug: **the guard was placed at the entry point rather than at the data.** In REST, reaching a peer's compensation required calling their URL, and the URL had the guard on it. Here, reaching it requires traversal, and traversal doesn't pass through `Query.employee`.

The team fixes it by moving the check into `Employee.compensation`. Two more failures follow.

**The check is about the actor, not the relationship.** The new resolver asks "does the viewer have permission to view compensation?" — and a manager does, so it returns true, for every employee in the company. The correct question was never about the viewer alone; it was about the viewer *and this particular employee*. Operation-level permission answered where an object-level question was asked. This is the most common vulnerability class in all of web APIs, and a graph gives it far more surface.

**The field nobody guarded.** Six months later a different team adds `Employee.equityGrants`. They copy the resolver next to it, which happened to be `title`. There's no guard, nothing requires one to exist, and no test fails. The field ships.

That third one is the important one. The first two are bugs; the third is a property of the design. Any scheme where a guard is something a developer remembers to write will eventually meet a developer who didn't.

(Denial of service — depth, aliases, cost — is also a security concern, and it's 8.3b's. It won't be repeated here.)

## What It Is

The underlying problem isn't new: it's **broken object-level authorization**, the top item on OWASP's API list for years. What GraphQL changes is arithmetic. REST gave you *n* routes and *n* places to check. A graph gives you a number of paths that grows with the connectivity of your schema, and the check has to hold on all of them.

Which forces one rule:

> **Authorize where the data is produced, not where the query entered.**

Beyond that, it helps to separate three questions that are usually run together, because they're enforced in different places and fail differently:

| Layer | Question | Depends on | Where enforced |
|---|---|---|---|
| **Operation** | May this actor run this operation at all? | actor, operation | before execution |
| **Field / type** | May this actor select this field anywhere? | actor, schema | declaratively, per field |
| **Object** | May this actor see this field *on this object*? | actor, **parent object**, data | inside the field's resolution |

Layer 1 is what a route guard used to be, and it still matters for mutations and admin queries. Layer 2 is static and can be declared in the schema and checked in CI. Layer 3 is dynamic, needs the object in hand, and is where every serious bug lives — including all three in the opening.

Most published advice covers layers 1 and 2 and calls it authorization. The manager-chain rule is layer 3, and no directive can express it.

## Recognizing the Problem

- Your authorization checks live in root-field resolvers only.
- A sensitive type is reachable by more than one path and you can't list them.
- A resolver checks `actor.hasRole(...)` and never looks at its parent object.
- Your schema has a cycle through a type that carries sensitive fields.
- A new field can be added by copying a neighbouring resolver and nothing objects.
- "Who can see X?" requires grepping resolvers.
- List fields return every element regardless of the viewer, and the per-element fields do the filtering.
- Your permission check does a database lookup, inside a resolver, inside a list.
- The same rule is implemented in a REST controller and in a resolver.
- Introspection is on, and so are field suggestions.

## How It Works

### Guard the node, not the entry

```
     Query.employee(id:)  ──guard──┐
                                   ▼
     viewer.team.members ─────────► Employee.compensation ◄── one check, here
     viewer.manager.directReports ─┘        ▲
     search(q:).…  ────────────────────────┘
```

Putting the check on the field means every arrival at that field pays it, regardless of route. Guards on entry points remain useful — refusing early is cheaper and produces better errors — but they are never sufficient, and treating them as sufficient is failure mode one.

### Layer 3 needs the parent, and that's the whole trick

```
allowed(actor, action, resource)
                          ▲
                          └── the object the field belongs to, not the viewer
```

`Employee.compensation`'s resolver receives the employee as its parent argument (8.1a: every field is a function of its parent). That parent *is* the resource. A check that ignores it is answering a question nobody asked.

This is also why the rule can't be declarative. "HR, or the employee, or anyone in their manager chain" requires walking data. Directives can say *that* a field is protected and by which policy; the policy itself is code.

### Fail closed, or the third failure will happen

The structural fix for "nobody remembered the guard" is to make the guard the default. Wrap every field in the schema at construction time, deny unless the field carries an explicit policy or an explicit exemption, and the new `equityGrants` field fails on its first request in development rather than leaking for six months in production.

Then add the CI rule that makes the exemptions visible: *every field on a type marked sensitive must carry an `@auth` directive or appear on a reviewed allowlist.* That check takes an hour to write and it's the only thing in this article that scales with team size, because it converts a thing people must remember into a thing the build enforces.

### Lists: filter, or null?

The question most treatments skip. `team.members` returns forty employees, of whom the viewer may see the compensation of three.

**Filter the list** — return only permitted elements. Existence is hidden, which is sometimes the requirement. But `totalCount` now either lies or leaks, cursor pagination across a filtered set returns short pages and confuses clients, and "you asked for 20 and got 14" is indistinguishable from the end of the list.

**Return everything, null the forbidden fields** — shape and counts stay honest, clients render a row with a redacted column, and existence is disclosed.

There's no universally right answer, only a question to ask per relationship: **is existence itself sensitive?** Team membership usually isn't; the existence of a disciplinary record usually is. Decide deliberately, write it down, and be consistent within a type — because inconsistency is itself a leak, discoverable by comparing two responses.

### Authorization is in the hot path now

Layer 3 runs **once per object**. A team page with forty members runs it forty times, and if each run does a database lookup to walk the manager chain, you've built exactly the N+1 from 8.3a — on the security check, which is the one nobody wants to be slow, because slow security checks get optimized away by someone in a hurry.

So: load the actor's permission-relevant data once per request into the context (the manager chain, role set, team memberships), and batch anything relational through a loader. The permission check itself should be a pure function over data already in memory.

One caveat inherited from 8.3a: per-request caching of permissions means a mutation that changes permissions won't be reflected later in the same request. Rare, and worth knowing when it happens.

### What the response says when it refuses

Three decisions.

**The field must be nullable.** `compensation: Compensation!` plus a denial means null in a non-null position, which nulls `Employee`, which nulls the list, which nulls the page (8.1a). Anything that can be refused has to be declared nullable, and that's a schema-wide consequence of the authorization model.

**Null with an error, or null silently?** An entry in `errors` with `code: FORBIDDEN` alongside partial `data` is the right shape for most cases — it's exactly the partial-success model 8.1b established, and it lets the client render "—" with a tooltip instead of a blank. Silent null hides the existence of the rule.

**Forbidden versus non-existent.** `FORBIDDEN` confirms the resource exists; returning it as if absent doesn't. Pick per type according to the same existence question as list filtering, and apply it uniformly — differential responses are a side channel.

### The schema is also information

**Introspection.** This came up twice already, from two angles: 8.1a called disabling it a weak security control, 8.3b called it a reasonable cost control. The resolution is that both are right. It isn't a security boundary — a determined attacker recovers your schema from your client bundle — but it is reconnaissance, and once you're on trusted documents (8.3c) turning it off costs you nothing. Do it then, for that reason, and don't count it as a control.

**Field suggestions are the leak people miss.** Send a typo and a default server replies: *Cannot query field "sallary" on type "Employee". Did you mean "salary"?* That's schema disclosure with introspection disabled, one request at a time, and it's on by default in most implementations. Turn it off in production.

**Reduced schemas per audience.** Partners see a schema without the sensitive types at all. You cannot ask for what isn't there, and it shrinks the surface you have to reason about — the one control on this list that makes the problem smaller rather than better-defended.

### Three more, briefly

**Aliased brute force.** Per-request rate limiting counts this as one request:

```graphql
mutation { a: login(u:"x", p:"1") { … }  b: login(u:"x", p:"2") { … }  … }
```

Login throttling, MFA attempts, coupon validation, anything you count per request — count per *field execution* instead, and cap aliases (8.3b).

**Typed arguments are not sanitized arguments.** A `String!` is a string, not a safe string. The risk concentrates in arguments that become query fragments — a `sortBy` or a filter DSL that's interpolated into SQL. Module 20's problem, arriving through a new door.

**CSRF.** A JSON `POST` triggers a preflight and is largely safe. A GraphQL request sent as `text/plain` or form-encoded is a *simple* request and can be forged cross-origin — as can a GET query once you adopt 8.3c. Require a content type that forces preflight or a custom header, and refuse mutations over GET at the server.

## When It's Appropriate

Authorization isn't optional, so the real question is when the centralized, declarative machinery earns its cost over checks written in resolvers.

- **A handful of roles, a small schema, two sensitive fields.** Resolver-level checks plus a test per field are honestly fine. Don't build a framework.
- **Several roles and relationship-dependent rules** (manager chains, project membership, tenant scoping). This is where a policy module plus directives plus the CI rule become the cheapest option rather than the fanciest.
- **More than one transport** (8.2). Push object-level checks below the transport so REST and GraphQL cannot disagree.
- **Regulated data** — health, financial, personnel. Enforcement at the data layer, where it can't be bypassed by a new code path.
- **More than one team writing resolvers.** The fail-closed wrapper and the CI rule exist entirely for this case.

## When It's Unnecessary or Overkill

- **A policy engine for three roles.** OPA or a Zanzibar-style service is a real dependency with real latency; it earns that when your rules are relationship graphs, not when they're a role check.
- **Directives on every field.** Annotate the exceptions. If everything authenticated is visible to everyone authenticated, the interesting information is which fields aren't.
- **Filtering lists when existence isn't sensitive.** Nulling the field is simpler, keeps counts honest, and doesn't break pagination. Reach for filtering when hiding existence is an actual requirement.
- **Designing an attribute-based model before writing the rules down.** Module 4.3 covers RBAC and ABAC; the failure here is picking a mechanism before anyone can state, in a sentence, who may see what.
- **Per-field checks on public data.** A wrapper that runs on `Employee.name` for forty rows is overhead on a field with no rule. Mark whole types public explicitly — which keeps the default closed while paying nothing.

## Trade-offs

**Checks run per object, in the request path.** Permission data has to be in memory or batched, and the check has to be fast enough that nobody proposes skipping it.

**Two mechanisms, and a seam.** Declarative directives cover layers 1–2; code covers layer 3. Every real system has both, and the bugs live where they meet — a field with a directive whose policy function silently ignores the parent looks protected in review.

**Nullable-on-deny is a schema-wide tax.** Every field that can be refused is nullable, so every client handles a null it will mostly never see. That's the price of not nuking the page, and it's paid by people who don't know why.

**Filtering and nulling both cost something.** Broken counts and pagination, or disclosed existence. There is no third option, and picking neither means picking one accidentally.

**Enforcement below the transport gives the best guarantee and the worst diagnostics.** If the repository simply doesn't return rows the actor can't see, nothing can bypass it — and nothing can distinguish "no such employee" from "not yours," which makes partial rendering and useful error messages hard. (8.2's Java example put `@PreAuthorize` on the service for exactly this guarantee, and named the same cost: invisibility at the call site.)

**Auditability depends on uniformity.** "Who can see compensation?" is answerable in seconds if there's one mechanism and unanswerable if there are four.

**Per-request permission caching can go stale** within the request, after a mutation that changes what the actor may see.

## Alternatives

- **Row-level security in the database.** Postgres RLS with policies on the tables, so no code path — GraphQL, REST, a migration script, an analyst with psql — can read what it shouldn't. The strongest available guarantee. Two real costs: the session-variable mechanism it depends on interacts badly with transaction-mode connection pooling (Module 5.2a covers exactly this trap), and the errors it produces are empty result sets rather than explanations.
- **A policy engine** — OPA, Cedar, casbin — with a decision point per field. Centralizes and externalizes the rules, makes them testable in isolation, adds a hop or an embedded engine and a new language to learn.
- **Relationship-based authorization services** — OpenFGA, SpiceDB, and the Zanzibar design they derive from. This is the right shape for "manager chain," "project member," "folder inherits from parent," and it's worth knowing about before you hand-roll a recursive permission query.
- **Schema variants per audience**, as above.
- **Resolver checks plus a CI lint** — the pragmatic middle, and where most teams should start: one policy module, called explicitly, with a build rule that no sensitive field escapes it.

## How to Achieve It

**1. Write the rules down as (actor, action, resource) sentences.** "A manager may view compensation for anyone in their reporting chain." If you can't write them, no mechanism will save you, and this is Module 4.3's work, not GraphQL's.
*Next when:* the list exists and someone who knows the domain has signed off.

**2. Inventory the paths.** For each sensitive type, list every field in the schema that returns it. This is the step people skip and it's the one that would have caught the opening bug in an afternoon.
*Next when:* the list is longer than you expected, which it will be.

**3. Put one check function in one module** and call it from the resolvers that need it. Not a framework — a function that takes actor, action, and resource.
*Next when:* more than a few fields call it, or more than one person is adding fields.

**4. Wrap every field, default deny, annotate exceptions, and add the CI rule.** This is the step that converts remembering into enforcement.
*Next when:* the wrapper is live and no field can escape it.

**5. Move object-level checks below the transport**, so a REST endpoint can't route around them (8.2).
*Next when:* both transports call the same function and neither has its own copy.

**6. Batch the permission data** through request-scoped loaders, and make the check pure.
*Next when:* the check no longer appears in your latency profile.

**7. For the highest-value data, consider RLS or a relationship service.** Last, not first, and only for the fields that justify it.

## Implementation

TypeScript, because the fail-closed property is the thing worth seeing, and transforming a schema so that *every* field is wrapped is most directly expressed there.

The schema declares intent; it never contains the rule:

```graphql
directive @auth(policy: String!) on FIELD_DEFINITION | OBJECT
directive @public on FIELD_DEFINITION | OBJECT

type Employee @auth(policy: "employee:read") {
  id: ID!
  name: String! @public
  title: String! @public
  compensation: Compensation @auth(policy: "compensation:read")   # nullable — see aside 3
  manager: Employee
  directReports: [Employee!]!
}
```

The wrapper, applied once at schema construction:

```ts
export const withAuthorization = (schema: GraphQLSchema) =>
  mapSchema(schema, {
    [MapperKind.OBJECT_FIELD]: (field, fieldName, typeName) => {
      const policy = policyFor(field, typeName);          // field directive, else type directive

      if (policy === PUBLIC) return field;
      if (policy === undefined) {
        return denyAlways(field, `${typeName}.${fieldName} has no policy`);  // ← aside 1
      }

      const original = field.resolve ?? defaultFieldResolver;
      field.resolve = async (parent, args, ctx, info) => {
        const decision = await policies[policy](ctx.actor, parent, ctx);     // ← aside 2
        if (!decision.allowed) {
          throw new GraphQLError("Not authorized", {
            extensions: { code: "FORBIDDEN", policy },                       // ← aside 3
          });
        }
        return original(parent, args, ctx, info);
      };
      return field;
    },
  });
```

The policy, which is where layer 3 actually lives:

```ts
policies["compensation:read"] = (actor: Actor, employee: Employee, ctx: Ctx) => {
  if (actor.roles.has("HR"))            return allow();
  if (actor.employeeId === employee.id) return allow();
  if (ctx.permissions.reportingChain.has(employee.id)) return allow();   // ← aside 4
  return deny();
};
```

**Aside 1 — the `undefined` branch is the entire article.** A field with no policy and no `@public` is denied, loudly, with the field name in the message. `equityGrants` from the opening now fails the first time anyone selects it, in development, with a message that says exactly what to do. Invert this branch — return the field unwrapped when no policy is found — and you've written a system that is secure only for the fields someone remembered, which is the system you already had.

**Aside 2 — the policy receives `parent`.** That argument is the resource. A policy signature that omits it cannot express object-level rules and will quietly answer a different question, and every one of the opening's leaks reduces to that. Make the parameter required in the type so a policy *can't* be written without it.

**Aside 3 — deny produces a null plus an error, which means the field must be nullable.** `compensation: Compensation!` would turn a denial into a nulled `Employee`, a nulled list, and a blank page (8.1a). Note also that throwing here yields partial data with a `FORBIDDEN` entry in `errors` — the right shape for a UI that wants to render a redacted cell rather than nothing. Where existence is itself sensitive, return null without an error instead, and do it for the whole type rather than field by field.

**Aside 4 — `ctx.permissions` is loaded once per request, not per object.** The reporting chain is fetched in the middleware that builds the context, beside the actor and the loaders (8.1a's aside 2). Do the walk inside this function and a forty-member team page issues forty recursive queries — the check becomes the slowest thing on the page, and the fix someone reaches for at 5pm is to cache it somewhere it shouldn't be cached.

## Further Reading

- **OWASP API Security Top 10**, particularly API1:2023 (Broken Object Level Authorization) and API5:2023 (Broken Function Level Authorization) — the vendor-neutral names for layer 3 and layer 1, and the evidence that these are the two most exploited API flaws in existence.
- **OWASP GraphQL Cheat Sheet** — a compact checklist covering introspection, field suggestions, batching, and CSRF; the fastest way to audit an endpoint you inherited.
- **`graphql-shield`** and **`@graphql-tools` directive documentation** — two idioms for the wrapper above; worth reading both to see the trade between a rule tree and per-field annotation.
- **GraphQL Armor** (`@escape.tech/graphql-armor`) — a set of production defaults including blocking field suggestions, which almost nobody configures manually.
- **Google's Zanzibar paper**, *"Zanzibar: Google's Consistent, Global Authorization System"* (USENIX ATC 2019) — the reference design for relationship-based permissions, and the right thing to read before hand-rolling a recursive "is this person in my chain" query.
- **OpenFGA** and **SpiceDB** — open implementations of that model, if the reporting-chain problem turns out to be your whole domain.
- **PostgreSQL Row-Level Security documentation** — the database-enforced option, best read alongside Module 5.2a on why session variables and transaction-mode pooling fight each other.
- **Module 4.3** for RBAC and ABAC themselves, which this article assumes rather than teaches.

A Java sibling would land differently, and the difference is instructive. With Spring Security's method security the check moves onto the service (8.2), which makes it uniform across transports and impossible to bypass — but a denial there is an exception, not a null, so the graph loses the ability to return *partial* results with a `FORBIDDEN` entry beside the data the viewer may see. Field-level redaction and service-level enforcement pull in opposite directions, and which one you want depends on whether your UI wants to render a greyed-out cell or a missing page. Not yet written.

---

The habit worth carrying: for any piece of sensitive data, ask how many distinct code paths can return it, and whether the check is on all of them or on the one you were thinking about. REST kept that number small by accident — one resource, one route, one guard. A graph makes it large on purpose, and everything in this article is a way of putting the check somewhere the number stops mattering.
