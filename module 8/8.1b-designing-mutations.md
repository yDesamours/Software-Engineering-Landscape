# Designing Mutations

_Module 8.1b — GraphQL APIs_

## The Problem

An applicant tracking system. Candidates apply, applications move through stages, interviews get scheduled, offers get made and accepted or declined.

The team adopted GraphQL for reads (8.1a) and it went well. Now writes. The obvious move is to translate the REST write endpoints one for one, and `PATCH /applications/{id}` translates to this:

```graphql
type Mutation {
  updateApplication(id: ID!, input: ApplicationInput!): Application
}

input ApplicationInput {
  stage: Stage
  assignedRecruiterId: ID
  rejectionReason: String
  offerSalary: Int
  offerStartDate: Date
  archived: Boolean
}
```

Every field optional, because it's a partial update. One mutation covers everything a client might do to an application. It ships, and it works, and then over the next two quarters it produces five separate problems that all have the same root.

**The schema stopped describing what's possible.** Moving a candidate to onsite, rejecting them, reassigning the recruiter, and extending an offer are four different things with four different rule sets. They are now one field. The type system cannot say that `rejectionReason` is required exactly when `stage` becomes `REJECTED`, or that `offerSalary` is meaningless unless an offer is being made, or that you can't move from `REJECTED` back to `PHONE_SCREEN`. So every combination is expressible, most are invalid, and all the validation that used to be visible in the schema now lives in a four-hundred-line resolver full of conditionals.

**Authorization became unanalyzable.** Who may call `updateApplication`? It depends on what's inside `input`. A coordinator may reassign a recruiter. Only a hiring manager may reject. Only finance may set a salary above band. One field, three permission models, and the only way to know which applies is to inspect the input object at runtime. "Which roles can reject a candidate?" is no longer answerable by reading the schema.

**Null acquired two meanings.** A client sends `rejectionReason: null`. Does that mean "leave it alone" or "clear it"? The GraphQL spec distinguishes a field that was omitted from one supplied as null — but most server libraries decode the input object into a struct or a plain object where both arrive as the same nothing. The team hit this when a coordinator edited a recruiter assignment and silently wiped a rejection reason written the day before.

**The audit trail became a diff log.** Every write emits `application.updated` with a before/after map. "When was this candidate rejected, and by whom?" requires reconstructing intent from field diffs, and the answer is wrong for the three applications that were edited by a bulk script in March.

**Two recruiters clobber each other.** Both open the application, one moves it to onsite, the other rejects it four seconds later without having seen the move. Last write wins. In the REST version there was an `If-Match` header (7.4a) and the second write got a `412`. There is no `If-Match` here — there is one POST to `/graphql` and no preconditions anywhere in the protocol.

Then a sixth problem, which is about failures rather than shape. A hiring manager rejects a candidate who already has an accepted offer. The resolver throws. The response:

```json
{
  "data": { "updateApplication": null },
  "errors": [
    { "message": "Cannot reject an application with an accepted offer",
      "path": ["updateApplication"] }
  ]
}
```

`200 OK`. The web client shows a red toast by reading `errors[0].message`. The mobile client, which needs to show a different screen for this case than for "you lack permission," matches on the substring `"accepted offer"`. Module 7.3b spent an entire article establishing that the code is the contract and the message is not, and within three weeks of moving to GraphQL the team is branching on English prose again.

And a seventh, which only shows up in the UI. After the mutation, the pipeline counts in the sidebar are wrong, the recruiter's task badge is wrong, and the candidate's status chip on the previous screen is wrong. The REST app refetched everything after a write. The GraphQL client has a normalized cache that can update itself — but only from data the mutation actually returned, and this one returned a single `Application`.

## What It Is

Mutations are not a separate mechanism. Everything from 8.1a still applies: a root type, a selection set, a resolver per field. The single difference the engine enforces is that top-level mutation fields execute serially rather than concurrently.

What's being designed here is something else. A mutation set is the **published list of operations your domain supports** — and the whole argument of this article is that it should be written that way, in the type system, rather than flattened into a generic update and reassembled at runtime from an input object.

Three conventions carry it, and they're near-universal in production schemas:

1. **One mutation per domain operation**, named as a verb phrase: `rejectApplication`, `moveApplicationToStage`, `extendOffer`.
2. **A single argument named `input`**, of a type dedicated to that mutation.
3. **A payload type** returned by that mutation, carrying the changed entities *and* the expected failures as data.

The third is the one people skip and the one the rest of the article is mostly about.

## Recognizing the Problem

- You have a mutation whose name is a verb like `update` or `save` followed by a type name.
- Its input type has every field optional.
- Its resolver opens with a chain of `if (input.x !== undefined)`.
- Answering "who is allowed to do X?" requires reading resolver code, not the schema.
- Clients branch on `errors[0].message`.
- A successful-looking response (`200 OK`, no `errors`) sometimes means the operation was refused.
- Your UI goes stale after a write and the fix was "refetch the whole screen."
- Your event stream is full of `*.updated` with diffs, and nobody can reconstruct why a change happened.
- Two users editing the same record silently overwrite each other, and you've noticed but not fixed it because there's nowhere obvious to put a version check.
- A mutation returns the entity it changed, and nothing else, and three other parts of the screen are now lying.

## How It Works

### Name the operation, not the table

```graphql
type Mutation {
  rejectApplication(input: RejectApplicationInput!): RejectApplicationPayload!
  moveApplicationToStage(input: MoveApplicationToStageInput!): MoveApplicationToStagePayload!
  assignRecruiter(input: AssignRecruiterInput!): AssignRecruiterPayload!
  extendOffer(input: ExtendOfferInput!): ExtendOfferPayload!
}

input RejectApplicationInput {
  applicationId: ID!
  reason: RejectionReason!      # required — the schema says so
  note: String
  notifyCandidate: Boolean! = true
  expectedStage: Stage!         # optimistic concurrency; see below
  clientMutationId: String      # idempotency; see below
}
```

Every problem in the first half of this article dissolves at this line. `reason` is required because rejection requires a reason — enforced by the executor before your code runs. The permission question has a single answer per mutation, so authorization is declarable and reviewable. The audit event writes itself: the operation *is* the event name. There is no partial-update ambiguity because there are no optional-meaning-unchanged fields.

The honest cost: a domain with forty operations now has forty mutations and eighty supporting types. That's a lot of schema. It is, though, the same forty operations that were previously hiding inside conditionals in one resolver — you are paying in schema surface for something you were already paying for in branching complexity, and only one of the two is readable by a client.

There's a sane middle. Genuinely free-form fields with no rules attached — an internal note, a display title, a tag list — don't need their own operation each. A small `updateApplicationDetails(input:)` covering exactly those fields is fine. The test is whether the field's change has *rules or consequences*. A stage change has both. A note doesn't.

### The input and payload convention

```graphql
type RejectApplicationPayload {
  application: Application
  pipeline: Pipeline
  viewer: Viewer
  userErrors: [UserError!]!
}
```

A single `input` argument and a dedicated payload type look like ceremony, and for the first mutation they are. They pay off in the second year: both types can gain fields additively without breaking any client, and codegen produces one named input type and one named result type per operation rather than a widening pile of positional arguments.

This is also the part that's genuinely hard to retrofit. Changing `rejectApplication` from returning `Application` to returning `RejectApplicationPayload` is a breaking change for every existing client. Adding a field to a payload never is. That asymmetry is the argument for using the wrapper even on mutations that look too simple to need it — the wrapper's value is that it can grow, and you can't add the ability to grow later.

(Note that input types are a separate world from output types: they can't contain unions or interfaces, and you cannot reuse `Application` as an input. That's deliberate — an input type describes what a client may send, which is rarely the same shape as what it may read.)

### Return everything the screen needs, not just the thing you changed

This is the payload field people get wrong, and the resulting bug is invisible in tests.

Rejecting an application changes more than the application:

```
what the screen shows              what a naive payload returns

  ┌──────────────────────────┐
  │ Sidebar                  │
  │   Phone screen     14 ───┼──── stale
  │   Onsite            6 ───┼──── stale
  │   Rejected         92 ───┼──── stale
  ├──────────────────────────┤
  │ Application: A. Okafor   │
  │   Stage: REJECTED   ─────┼──── correct  ◄── application
  ├──────────────────────────┤
  │ Your tasks (7)      ─────┼──── stale
  └──────────────────────────┘
```

A normalized client cache updates any entity the mutation returns, keyed by id and `__typename`. Return the `Pipeline` and the `Viewer` and the sidebar and the badge correct themselves in the same round trip, with the client choosing which of their fields it cares about — because the payload fields are ordinary selectable fields, subject to everything in 8.1a.

You can't return *everything*; at some point the honest answer is that the client refetches. The workable rule of thumb is: **return the entities displayed on the screen that triggered the mutation.** Beyond that, refetch.

The failure mode when you get this wrong is the nastiest kind. Nothing errors. The data is simply wrong on screen until the user navigates away and back, and QA won't catch it because QA navigates.

### Two error channels, and which belongs where

GraphQL gives you two places to report a failure, and almost every mutation design mistake is using the wrong one.

**The top-level `errors` array** is the executor's channel. The field resolves to null (and that null may bubble — 8.1a), and an untyped entry with a string `message` appears alongside `data`. It is outside the type system, so no client can be type-checked against it.

**Errors as data** means the payload carries the failure as a typed, selectable field. The operation executed successfully; its business outcome was a refusal.

The dividing line:

| | Channel | Examples |
|---|---|---|
| **Expected outcomes of a valid request** | payload | already rejected, position closed, salary above band, candidate withdrew |
| **The request should not have been made** | `errors` | unauthenticated, query too complex, unknown field |
| **Something broke** | `errors` | timeout, downstream 500, panic |

The test is whether a client would *do something specific* about it. That is exactly Module 7.3b's rule, arriving in a place where the type system can enforce it — instead of a string code in a JSON body, you get an actual type.

There are three ways to express payload errors, in increasing strength:

**A list of coded errors.** The common one, popularized by Shopify:

```graphql
type UserError {
  code: RejectApplicationErrorCode!
  message: String!
  field: [String!]
}
```

Cheap, uniform across every mutation, one client-side handler for the "show a toast" case. The weakness is that `userErrors` is always present and always possibly empty, so nothing forces a client to check it — and the client that doesn't check reports success on a refusal.

**A result union.** The strong version:

```graphql
union RejectApplicationResult =
    RejectApplicationSuccess
  | ApplicationAlreadyRejected
  | PositionClosed
  | OfferAlreadyAccepted
```

Now the client *cannot* read the application without first discriminating on `__typename`, and with generated types that check is a compile-time obligation. Each error type can carry its own fields — `OfferAlreadyAccepted { offer: Offer! }` lets the UI link straight to it.

The cost is real and worth stating plainly: this is three to five extra types per mutation, and it makes the overwhelmingly common "just show the message" path verbose at every call site. It also has a sharp edge — **adding a member to a union is a breaking change** for clients that switch exhaustively. Mitigate by giving every union a catch-all member from day one, or by making the error types implement a shared `interface Error { message: String! }` so a `... on Error { message }` selection handles anything new.

**Interface-based**, which is the middle ground: concrete error types implementing `Error`, returned in a payload list. Clients can handle the two cases they care about specifically and the rest generically, and new error types don't break anyone.

Most schemas should start at the coded list, and promote to unions for the handful of mutations where clients genuinely branch — payment, checkout, anything where the refusal has a screen of its own.

One consequence to make peace with: **a refused mutation returns `200 OK` with populated `data` and no `errors`.** That's correct — a valid operation was executed and the domain said no. It also means the transport layer no longer knows whether anything succeeded, which is precisely the failure Module 7.1a opened with: a green dashboard during a fifty-hour outage. GraphQL reintroduces it deliberately, and the only fix is application-level telemetry that counts payload error codes per operation name. Build it when you build the first result union, not after the first incident.

### Serial is not transactional

Top-level mutation fields execute in order. This is easy to over-read.

```graphql
mutation {
  rejectApplication(input: {...})    { userErrors { code } }
  assignRecruiter(input: {...})      { userErrors { code } }
}
```

The second starts after the first finishes. If the second fails, the first has already committed. There is no rollback, no two-phase anything, and no way to express "both or neither" across two mutation fields. If an operation must be atomic, it must be **one** mutation — the transaction boundary is the resolver, not the request.

Two smaller facts in the same area: the serial guarantee applies only to the root selection set, not to fields nested beneath it; and aliases mean the same mutation can legally appear several times in one request, which is occasionally useful and occasionally how someone runs `deleteEverything` fifty times.

### Idempotency and preconditions have to come back as data

Both of these were solved problems at the HTTP layer, and adopting GraphQL threw the HTTP layer away.

**Idempotency.** Every mutation is a POST to one URL; nothing in the protocol says whether retrying is safe, and a flaky mobile connection retries. The answer is the one from 7.1a, relocated into the schema: a client-generated key as an input field (`clientMutationId`, by convention), stored with the result, returned unchanged on a replay. Needed on anything that creates.

**Optimistic concurrency.** There is no `If-Match`, so the precondition becomes an input field: `expectedStage: Stage!` or `version: Int!`, compared inside the transaction, with a mismatch returned as a typed payload error carrying the current value so the client can show what changed. The mechanism is identical to 7.4a's; only its location moved, from a header the protocol understood to a field you have to remember to add.

That relocation is worth noticing as a pattern rather than two separate tips. Anything HTTP was doing for you — conditional requests, retry safety, status semantics — is now yours to model explicitly. Nothing is lost that you can't rebuild; nothing is rebuilt that you don't remember to.

## When It's Appropriate

The full ceremony — operation-named mutations, dedicated inputs, payload wrappers, typed errors — earns its cost when:

- **The domain has real state transitions with rules.** Applications, orders, subscriptions, shipments, anything with a lifecycle. Signal: your update resolver has more than about five conditional branches keyed on which fields were supplied.
- **Different operations on the same entity have different permissions.** This alone justifies splitting, because a single mutation makes the permission model unreviewable.
- **More than one client must enforce identical rules.** Typed errors are how the rules get transmitted instead of reimplemented; a second client is when the coded-string version starts failing.
- **The write path feeds an event stream or audit log** that people will actually read. Operation-named mutations produce intent-shaped events for free.
- **Writes drive UI that shows derived data** — counts, badges, aggregates. This is what makes payload design load-bearing rather than cosmetic.

## When It's Unnecessary or Overkill

- **Genuinely free-form fields.** A notes field, a display name, a tag list. `updateApplicationDetails` covering the fields with no rules is correct, and inventing `setApplicationNote` alongside `setApplicationTags` alongside `setApplicationTitle` is the same mistake inverted — mutation-per-field rather than mutation-per-operation.
- **Result unions everywhere.** In a sixty-mutation schema where fifty-five have exactly one failure mode — "invalid input" — a union per mutation produces a switch statement at every call site to display one toast. Use the coded list there and spend the unions where clients actually branch.
- **Maximal payloads.** Returning the entity, its parent, its siblings, and the viewer from every mutation "so the cache stays fresh" reintroduces 8.1a's over-fetching on the write path, and it's worse there because the client isn't choosing it — except that it is, because payload fields are selectable. Put the fields in the payload; let clients omit them.
- **Internal admin tools over a config table.** One client, one team, CRUD semantics that match the domain exactly. `updateFeatureFlag(input:)` returning the flag is fine and always will be.
- **A schema whose mutations mirror a workflow diagram nobody has agreed on yet.** Operation-named mutations encode domain decisions into a published contract. If the domain model is still in flux weekly, a coarser mutation buys time — just know that's what you're buying.

## Trade-offs

**Schema surface grows substantially.** Roughly three types per operation once you count input, payload, and error types. Forty operations is a schema large enough that discoverability becomes its own problem, and `Mutation` becomes a wall of text in every introspection tool.

**Failure stops being visible at the transport layer.** Load balancers, gateways, and any dashboard keyed on status code report success on refusals. You must build per-operation success/failure metrics that read inside payloads, and until you do, your monitoring is lying in the specific way 7.1a warned about.

**Typed errors are a contract with the same rigidity as any other type.** Adding a union member breaks exhaustive clients. Removing an error code breaks clients that handle it. Error taxonomies are now subject to deprecation discipline, which is more governance than "throw an exception" required.

**Cache correctness becomes a shared responsibility** split between what the server returns and what the client requests, with no mechanism that detects a mismatch. A missing payload field produces stale UI, silently, forever, and the bug reports say "sometimes the numbers are wrong."

**Duplication across resolvers.** Forty mutations means forty places that load the application, check permissions, open a transaction, and emit an event. Without a shared command layer underneath, that boilerplate is where the inconsistencies breed — one mutation forgetting the tenant check is a Module 5-grade incident.

**Idempotency and concurrency are now opt-in per mutation.** The protocol used to make them available to everyone by default; now they exist only where someone remembered to add a field.

## Alternatives

**Keep writes in REST.** GraphQL for reads, HTTP endpoints for writes. This is a real architecture that real teams run deliberately, and it keeps status codes, `Idempotency-Key`, `If-Match`, and file upload working as designed. The cost is two authentication paths, two error formats, and a client cache that has no idea a write happened — so you're back to manual refetching, which was one of the seven problems at the top. 8.2 takes this up properly.

**Command endpoints alongside a read-only schema.** `POST /applications/{id}/reject` with a read-only GraphQL API. Cleaner than mixed CRUD, and a reasonable stopping point for systems whose write volume is low and whose clients are few.

**Throw-only, no payload errors.** Every failure goes to the `errors` array with a code in `extensions`. Less machinery, and genuinely fine for internal tools with one client. The `extensions` field is unstructured, so no client can be type-checked against it — which is exactly the property you're trading away.

## How to Achieve It

Starting from a CRUD-shaped mutation set, without breaking anyone:

**1. Add the operation-named mutation beside the generic one.** Same service call underneath, no behavior change. `rejectApplication` and `updateApplication` coexist.
*Next step when:* the new mutation is in use by at least one client and the shape feels right.

**2. Wrap every new mutation in a payload type from the first one.** Even when it has nothing but the entity and an empty `userErrors`. Retrofitting the wrapper is breaking; adding fields to it never is.
*Next step when:* a second client appears, or a client starts branching on failure.

**3. Move expected failures out of the `errors` array into `userErrors` with an enum code.** Ship the codes before any client needs them; clients can ignore a field they don't select.
*Next step when:* a specific failure needs its own screen, or carries data the UI wants to link to.

**4. Promote that mutation's errors to a result union.** One mutation at a time, not schema-wide. Include a catch-all or a shared `Error` interface.
*Next step when:* the operational metrics exist — promote the telemetry in the same change, because this is the point where `200 OK` starts hiding real failures at volume.

**5. Deprecate the generic mutation.** `@deprecated(reason: "Use rejectApplication")`, then watch per-field usage. Remove when it reaches zero, which will take longer than you expect and is the entire reason field usage tracking exists (8.1a).

## Implementation

TypeScript, because the point of typed errors is what they do on the *client*, and discriminated unions on `__typename` are where that becomes a compiler obligation rather than a convention.

The schema:

```graphql
type Mutation {
  rejectApplication(input: RejectApplicationInput!): RejectApplicationResult!
}

union RejectApplicationResult =
    RejectApplicationSuccess
  | ApplicationAlreadyRejected
  | OfferAlreadyAccepted
  | StageChangedSinceLoad

type RejectApplicationSuccess {
  application: Application!
  pipeline: Pipeline!
  viewer: Viewer!
}

type OfferAlreadyAccepted implements Error {
  message: String!
  offer: Offer!               # so the UI can link to it
}

type StageChangedSinceLoad implements Error {
  message: String!
  currentStage: Stage!        # so the UI can show what happened
}
```

The resolver:

```ts
const rejectApplication: MutationResolvers["rejectApplication"] = async (
  _parent, { input }, ctx,
) => {
  await ctx.authz.require("application.reject", input.applicationId); // ← aside 1

  return ctx.db.tx(async (tx) => {                                    // ← aside 2
    const app = await tx.applications.forUpdate(input.applicationId);

    if (app.stage !== input.expectedStage) {
      return { __typename: "StageChangedSinceLoad",
               message: "This application moved while you were viewing it.",
               currentStage: app.stage };
    }
    if (app.acceptedOffer) {
      return { __typename: "OfferAlreadyAccepted",
               message: "This candidate has already accepted an offer.",
               offer: app.acceptedOffer };
    }

    const rejected = await tx.applications.reject(app, input.reason, input.note);
    await ctx.events.record(tx, "application.rejected", {               // ← aside 3
      applicationId: app.id, reason: input.reason, actor: ctx.actor.id,
    });

    return { __typename: "RejectApplicationSuccess",
             application: rejected,
             pipeline: await tx.pipelines.byId(app.pipelineId),
             viewer: ctx.actor };
  });
};
```

And the client, with generated types:

```ts
const result = await rejectApplication({ variables: { input } });

switch (result.__typename) {
  case "RejectApplicationSuccess":
    return close();                                   // cache updated by the payload
  case "StageChangedSinceLoad":
    return showConflict(result.currentStage);
  case "OfferAlreadyAccepted":
    return navigateToOffer(result.offer.id);
  case "ApplicationAlreadyRejected":
    return close();
}
```

No `default` branch. Add a fifth union member to the schema, regenerate, and this file fails to compile — which is the entire argument for unions over coded strings, and also, precisely, why adding a union member is a breaking change.

**Aside 1 — authorization runs before anything loads.** There's no route to guard (8.1a), so the first line of the resolver is the guard, and "the one mutation that forgot" is a real vulnerability rather than a hypothetical. That repetition across forty resolvers is what a shared command layer exists to eliminate; the check must still be per-operation, but it shouldn't be per-author.

**Aside 2 — the transaction is the resolver, and only the resolver.** Two mutations in one request are serial, not atomic (above). Anything that must be all-or-nothing has to fit inside this one function. The `forUpdate` row lock plus the `expectedStage` comparison is 7.4a's precondition rebuilt out of parts, because the header it used to live in no longer exists.

**Aside 3 — the event is written inside the transaction, and it names the operation.** `application.rejected` with a reason, not `application.updated` with a diff. That's the audit-trail problem from the opening solved as a side effect of naming the mutation properly. Note that writing to an event table inside the transaction and publishing to a broker afterward are two different things, and doing the second without the first is a dual-write — the transactional outbox, which Module 37 owns.

**Aside 4 — the payload is why the sidebar stays correct.** `pipeline` and `viewer` are in the success type solely so a normalized cache can update the counts and the task badge. Clients that don't display them simply don't select them. Leave them out of the type and no client can ever fix its own staleness.

## Further Reading

- **The GraphQL specification**, §6.2.2 *Mutation* — the serial execution rule, in about a paragraph. Worth reading precisely because it's so much narrower than people assume.
- **Shopify's GraphQL Design Tutorial** (github.com/Shopify/graphql-design-tutorial) — sections on mutation naming, input objects, and `userErrors`. The clearest published rationale for operation-named mutations, from a schema with several hundred of them.
- **Sasha Solomon, "Handling GraphQL errors like a champ"** — the canonical argument for errors as data with union results, including the exhaustiveness point.
- **Marc-André Giroux, _Production Ready GraphQL_**, chapters on mutation design and error handling — treats the union-versus-list trade-off honestly rather than picking a side.
- **The GraphQL Relay Server Specification** — the origin of `clientMutationId` and the single-`input`-argument convention, useful as history even if you never adopt Relay.
- **Apollo Client documentation on the normalized cache** — specifically cache normalization and mutation result handling, which is the mechanism the payload design above is written against.
- **Stripe's idempotent requests documentation** — still the reference implementation of the key-and-store pattern, unchanged by the transport it rides on.

A Java sibling would show something this one can't: Spring GraphQL sits on top of Spring's declarative transaction and method-security annotations, so `@PreAuthorize` and `@Transactional` move the first two asides above out of the resolver body and into metadata — which makes them uniform across forty mutations, and correspondingly makes it harder to see, at the call site, that they are happening at all. Not yet written.

---

The habit worth taking from this: a write API's schema should read like a list of things that can happen in your business, and a reader who knows nothing about your database should be able to learn the domain from it. When it instead reads like a list of tables with an `update` beside each one, the domain hasn't disappeared — it's been moved somewhere no client can see it, and every client will eventually reimplement its own guess at it.
