# Schemas and Client-Specified Queries

_Module 8.1a — GraphQL APIs_

## The Problem

A podcast platform. One backend, and over four years it grew four client surfaces: a web player, an iOS app, an Android app, and a car head-unit integration. A partner widget makes five.

The API started clean.

```
GET /shows/{id}
GET /shows/{id}/episodes
GET /episodes/{id}
GET /people/{id}
```

Here is what it looks like now.

```
GET /shows/{id}
GET /shows/{id}/episodes
GET /episodes/{id}
GET /people/{id}
GET /home                          web home
GET /mobile/home                   iOS shipped, different shape
GET /mobile/v2/home                the 2024 redesign
GET /mobile/v2/home?lite=1         Android Go devices, smaller payload
GET /auto/continue-listening       head unit needs three fields
GET /auto/continue-listening/v2    head unit needed a fourth field
GET /embed/show-card/{id}          partner widget
```

None of those were unreasonable when they were added. Each one exists because of one of three pressures, and it's worth separating them, because they have different fixes.

**Over-fetching.** `GET /shows/{id}` returns forty-odd fields: the description as 4KB of sanitized HTML, artwork in six sizes, category taxonomy, RSS metadata, publisher contact info. The car head unit renders a row with a title, one artwork URL, and a resume position. It uses about 0.4% of the bytes it receives, on the worst connection any of the clients has. So `/auto/continue-listening` was born, and now there are two endpoints that mean "shows."

**Under-fetching, which shows up as a waterfall.** The episode detail screen needs the episode, its show, the show's hosts, and each host's other shows. In REST that's four sequential round trips, because each one needs an id from the previous response. At a realistic 180ms mobile round trip, that's roughly 720ms of pure latency before anything can render. Module 7.4b made the point that HTTP/2 made *parallel* requests close to free; it did nothing for dependent ones, and this is a dependent one.

**Release coupling, which is the expensive one.** Design adds episode duration to the car row. The data is sitting in the database. The change is one line in a serializer. But it's a backend ticket, a backend deploy, and a coordination problem — and because the previous head-unit build will be in cars for three more years, `/auto/continue-listening` has to keep returning exactly what it returns today, forever. That's why there's a `/v2`.

Multiply: five surfaces, a dozen screens each, each screen's data needs changing every few sprints. Every cell in that matrix is a backend change, and the endpoint count only ever goes up.

So the team does the reasonable thing. Rather than one endpoint per screen, they let the client say what it wants:

```
GET /shows/42?fields=title,artwork&include=episodes.guests
```

This is where Module 7.4b stopped, with a warning. Two quarters later that query parameter has grown a nesting syntax, a depth limit (someone requested `include=episodes.show.episodes.show`), per-field argument support because the car needs `artwork` at one size and the web player needs three, an aliasing rule so the same field can be requested twice, and a hand-written parser with no test coverage that nobody wants to touch. It has no type information, so no editor completion and no way to validate a client's request before shipping it. And there's still no answer for the waterfall, because `include=` only reaches one level of your own data.

The team has built a query language. It's just a bad one, and it's private, so no tooling will ever exist for it.

## What It Is

The thing they were building already exists and is specified: **GraphQL**.

Three parts, and it's worth being precise about which is which:

1. A **type system** describing your data and how it connects — written in a schema definition language (SDL), published, and machine-readable.
2. A **query language** in which a client names exactly the fields it wants, at any depth, with arguments anywhere.
3. An **execution engine** that walks the query against the schema, calls a function per requested field, and assembles a response whose shape mirrors the request.

One HTTP endpoint. The client's request describes the response.

Two clarifications before going further, because the name misleads people:

**"Graph" is not about graph databases.** It refers to the fact that the types in your schema point at each other — a show has hosts, a host hosts shows — so the whole schema forms a graph rather than a tree. GraphQL has no opinion about storage. It does not generate SQL, it doesn't know your database exists, and it works equally over Postgres, three microservices, or a pile of REST calls.

**GraphQL is a specification, not a product.** Apollo, Relay, gqlgen, and Spring GraphQL are implementations of and tooling around it. A lot of advice about "GraphQL" is actually advice about one vendor's client cache.

The comparison everyone wants — GraphQL versus REST, and whether one replaces the other — is a whole argument with a real answer, and it's 8.2. This article is about what the thing *is*.

## Recognizing the Problem

- You have a `/mobile/` route prefix, or a `/v2/` that exists only because one client couldn't update.
- Two endpoints return the same entity in two shapes, and a third is being proposed.
- A screen's load is four sequential requests deep and the waterfall is visible in the network panel as a staircase.
- "Add a field to this screen" is the most common ticket type crossing between the frontend and backend teams.
- You have a `fields=`, `include=`, `expand=`, or `embed=` query parameter, and it has grown a syntax.
- The mobile app ships a feature two weeks after the backend is ready, because of app-store review and staged rollout.
- Nobody can tell you whether it's safe to remove a response field, so no response field has ever been removed.
- Your backend team maintains serializers per client rather than per resource.
- A client requests an endpoint, discards 95% of the body, and the endpoint can't be changed because another client uses the rest.

If most of these are absent — one client, one team, one deploy — the pressure this solves isn't on you. Skip to *When It's Unnecessary*, it's a short section and it's aimed at you.

## How It Works

### The schema is the API

```graphql
type Show {
  id: ID!
  title: String!
  description: String!
  artwork(size: ArtworkSize! = MEDIUM): String!
  hosts: [Person!]!
  episodes(first: Int! = 20, after: String): EpisodeConnection!
}

type Episode {
  id: ID!
  title: String!
  durationSeconds: Int!
  publishedAt: DateTime!
  show: Show!
  guests: [Person!]!
}

type Person {
  id: ID!
  name: String!
  hostOf: [Show!]!
}

type PlaybackPosition {
  positionSeconds: Int!
  updatedAt: DateTime!
  episode: Episode!
}

enum ArtworkSize { SMALL MEDIUM LARGE }

type Query {
  show(id: ID!): Show
  episode(id: ID!): Episode
  continueListening(first: Int! = 10): [PlaybackPosition!]!
}
```

Read that as a graph, not a list of endpoints. `Episode.show` points at `Show`, `Show.hosts` points at `Person`, `Person.hostOf` points back at `Show`. There is a cycle in there, and that's fine — it's the thing a resource tree can't express without either duplicating representations or refusing to go deeper.

`Query` is the entry point: its fields are the places you're allowed to enter the graph. Everything else is reachable only by traversal from one of them.

### A query is a tree cut out of that graph

```graphql
query CarPlayRow($count: Int!) {
  continueListening(first: $count) {
    positionSeconds
    episode {
      title
      durationSeconds
      show {
        artwork(size: SMALL)
      }
    }
  }
}
```

```
schema — a graph                        query — one tree cut from it

  Query                                   Query
   ├─ show ───────────► Show               └─ continueListening
   ├─ episode ────────► Episode                 ├─ positionSeconds
   └─ continueListening                         └─ episode
            │                                        ├─ title
            ▼                                        ├─ durationSeconds
     PlaybackPosition ──► Episode ──► Show            └─ show
                             │          │                  └─ artwork
                             └──► Person ┘
                                    │
                                    └──► Show   (cycle)
```

And the response:

```json
{
  "data": {
    "continueListening": [
      {
        "positionSeconds": 1841,
        "episode": {
          "title": "The Long Way Round",
          "durationSeconds": 3120,
          "show": { "artwork": "https://cdn…/s/42.jpg" }
        }
      }
    ]
  }
}
```

Nothing the client didn't ask for. More importantly: the client knows the response shape *before sending the request*, because it wrote it. No spec to consult, no optional fields that might or might not appear, no "the mobile endpoint returns `imageUrl` but the web one returns `artwork`."

That mirroring is the property everything else is built on. It's why generated client types are possible, and it's why the frontend can change what it fetches without telling anybody.

### Every field is a function

The engine doesn't execute a query against a data structure; it executes it against a set of **resolvers**, one per field. `Episode.show` is a function that receives the already-resolved episode and returns a show. `Show.artwork` is a function that receives the show and the `size` argument and returns a string.

Execution is depth-first from the root: resolve `continueListening`, then for each result resolve `episode`, then for each of those resolve `show`, and so on. Sibling fields at the same level have no ordering guarantee and may run concurrently.

Two consequences fall straight out of that, and it's worth sitting with them because they shape the rest of the module:

- A resolver only ever sees **one** parent object. `Episode.show` is called once per episode, with no knowledge that nineteen other episodes are being resolved beside it. That is an N+1 query problem by construction, not by accident — it's the default, and it's what Module 8.3a exists for.
- There is no route to attach middleware to. Authentication, authorization, rate limiting, and tracing were per-endpoint concerns; now the only endpoint is `/graphql`, and the interesting decisions happen per field, deep inside execution. Module 8.4.

### Arguments belong to fields, not to endpoints

This is the line between GraphQL and the `fields=` parameter the team was building. `artwork(size: SMALL)` parameterizes a field four levels deep. `episodes(first: 20, after: "…")` paginates a nested list. Field selection alone can't do that — it can only include or exclude.

The same field can appear twice with different arguments, distinguished by an **alias**:

```graphql
show(id: "42") {
  thumb: artwork(size: SMALL)
  hero:  artwork(size: LARGE)
}
```

The response carries `thumb` and `hero`. Aliases are also the reason the response shape is fully determined by the query text — the client picks the key names.

### Nullability is part of the contract, and it propagates

`String` may be null. `String!` may not. `[Episode!]!` is a non-null list of non-null episodes. This is not decoration; the executor enforces it, and it changes failure behavior.

If a resolver for a non-null field returns null or raises an error, the engine cannot put null there, so it **nulls the parent instead** — and keeps climbing until it reaches a field that is allowed to be null. In the query above, every field in the chain is non-null: if the CDN lookup behind `Show.artwork` fails for one item, the null bubbles through `show` → `episode` → the list → `continueListening`, and `data` comes back null. One failing thumbnail erased the entire screen.

The practical rule: **be generous with `!` on fields that come from the same row you already loaded, and conservative on fields that cross a network boundary.** A title read from the same record as its id will never independently fail. A signed CDN URL, a field backed by another service, or anything behind a cache lookup will.

Related, and easy to miss: `[Episode!]!` and `[Episode]!` differ in whether one bad element destroys the list. The first nulls the whole list; the second leaves a hole in it.

This is the schema decision teams most often regret, and it's asymmetrically hard to undo. For an output field, going from `String` to `String!` is safe for existing clients — they were already handling null and now never see it. Going from `String!` to `String` is a breaking change. (For arguments and input fields it's the reverse: relaxing `String!` to `String` is safe, tightening is breaking.) So the cautious default costs you nothing later, and the confident one locks you in.

### Fragments, and why frontends adopted this

A fragment is a named, reusable selection set bound to a type:

```graphql
fragment EpisodeRow on Episode {
  title
  durationSeconds
  show { artwork(size: SMALL) }
}

query CarPlayRow($count: Int!) {
  continueListening(first: $count) {
    positionSeconds
    episode { ...EpisodeRow }
  }
}
```

That looks like a deduplication feature. It isn't, quite. It's what lets each UI component declare its own data requirements next to the component, and lets the build tooling compose all of them into one request per screen. A component that starts rendering a new field adds it to its own fragment and the query changes automatically — no coordination with the screen above it, and no backend involvement at all.

That, not payload size, is the reason GraphQL spread through frontend teams. Bytes were the pitch; decoupling was the product.

### Introspection

The schema is itself queryable at runtime. Ask the server what types it has and what fields they carry, and it will tell you. Everything downstream comes from this: GraphiQL's interactive explorer, editor autocomplete over your actual API, generated TypeScript or Swift or Kotlin types for every query in a codebase, and CI checks that fail a build when a query references a field that no longer exists.

You will see "disable introspection in production" recommended as a security measure. It's a weak control — the schema is inferrable by other means and your client bundles contain the queries anyway — and it costs you tooling. There are better answers in 8.4.

### Mutations and subscriptions, in one paragraph each

`Mutation` is a second root type, and everything above still applies: same type system, same selection sets, same resolvers. One rule differs — **top-level mutation fields execute serially, in the order written**, so two mutations in one request can't race each other. Nested fields underneath them resolve normally. Note that nothing stops a `Query` field from writing or a `Mutation` field from only reading; serial execution is the only difference the engine enforces, the rest is convention you should keep. Mutations also return data, which is how a client updates its local cache in the same round trip. 8.1b covers shape, errors, and why "return the mutated object" is the beginning of the design rather than the end.

`Subscription` is a third root type for a long-lived stream of results driven by server-side events. The spec deliberately says nothing about transport; in practice it's WebSockets or SSE, which is Module 9's territory, and the interesting problems are there rather than in the query language.

### Lists need pagination, and there's a de facto standard

`episodes(first: 20, after: "…")` returning an `EpisodeConnection` is the Relay Connections shape — `edges { cursor node { … } }` plus `pageInfo { hasNextPage endCursor }`. It is more ceremony than it looks like it needs, and it exists so that generic client caches can paginate any list without knowing the domain. Module 7.3c covers why cursors beat offsets in the first place; that reasoning is unchanged here. Adopt the shape early — retrofitting a list from `[Episode!]!` to a connection is a breaking change.

## When It's Appropriate

- **Several client surfaces on release cycles you don't control.** The sharpest signal is an installed base where a meaningful fraction of users — say a fifth or more — are running a build older than six months. That population is exactly what turns "add a field" into "add an endpoint version."
- **Screens that compose four or more related entities**, where REST gives you a dependent waterfall rather than parallel fetches.
- **A BFF layer that already exists** and is mostly hand-written aggregation code — GraphQL is a generic version of what that layer is doing by hand, and replacing it is a fair trade rather than net-new complexity.
- **A genuinely relational domain with multiple entry points into the same data.** Shows, episodes, people, playlists, all reachable from each other, and different screens entering at different nodes.
- **Frontend and backend as separate teams** with separate backlogs, where cross-team tickets are the bottleneck rather than the work itself.
- **Aggregation over several internal services** where clients would otherwise be taught the service topology.

## When It's Unnecessary or Overkill

- **One client, one team, deployed together.** The coupling GraphQL removes is the coupling you can break for free every Tuesday. You'd be paying for an executor, a batching layer, a cost limiter, and a field-level authorization design to solve a problem you don't have. A typed RPC layer or generated clients from an OpenAPI document give you the type safety without any of that.
- **Mostly-flat data.** A reporting API, a metrics endpoint, a webhook receiver. If there are no traversals, the query language has nothing to express and you've added a parser between HTTP and your handlers.
- **Bulk and binary.** File uploads, CSV exports, and streaming downloads go over plain HTTP. Multipart upload specs for GraphQL exist and are uniformly unpleasant.
- **A small team.** Everything in 8.3 and 8.4 becomes mandatory the moment a GraphQL endpoint is exposed to anyone you don't employ. That's a standing maintenance commitment, not a one-time setup.
- **Public APIs where predictable cost matters more than flexibility.** This one is genuinely arguable — GitHub and Shopify both run large public GraphQL APIs — but note what they had to build to do it: published cost models, per-query budgets, and rate limits denominated in complexity points rather than requests. That's the price of admission, covered in 8.3b.
- **"It's modern."** The endpoint sprawl at the top of this article is a symptom. If yours has three endpoints and a happy frontend team, there's no symptom.

## Trade-offs

These are what it costs *after* you've adopted it and everything is working.

**You lose HTTP caching.** Every request is a `POST` to one URL with a body. Browser caches, CDNs, and reverse proxies can do nothing with that — the entire apparatus Module 7.1a spent its length justifying goes dark. You get it back in pieces: a normalized client-side cache (which is powerful, and which you now have to understand and debug), and persisted queries sent as `GET` with the query hash in the URL, which restores CDN caching at the cost of a build step and an operation registry. Both are real work, and neither is optional at scale.

**Performance is no longer a property of an endpoint.** With REST you can profile `/shows/42` once and know what it costs. With GraphQL the client composes the query, so the space of possible queries is unbounded, and a legal query can be catastrophically expensive. Static analysis of query cost stops being a nice-to-have. (8.3b.)

**N+1 is the default, not the exception.** Per-field resolvers mean batching has to be engineered in, and the code that causes the problem looks completely innocent — a single-object fetch in a single-object function. (8.3a.)

**Authorization moves into the graph.** There is no route to guard. The same `Episode` type may be reachable from six different paths, and each one needs to enforce the same rules. This is a genuine re-architecture of how permissions are expressed, and it's the most common source of serious GraphQL vulnerabilities. (8.4.)

**Errors get more complicated, not less.** A GraphQL response is usually `200 OK` even when things failed, with an `errors` array alongside a partially-populated `data`. Partial success is now a first-class state your clients must handle, which is a real step back from Module 7.3b's story where the status code told you what happened. And the nullability rules above mean the blast radius of one failure is a schema design decision you made months earlier.

**Observability degrades unless you rebuild it.** Every dashboard keyed on URL now shows one line. You need per-operation-name metrics, per-field timings and error rates, and per-field usage tracking — the last of which isn't optional, because it's the only thing that ever lets you delete a field.

**The schema becomes an organizational asset.** There are no versions; the intended path is additive change plus `@deprecated` plus eventual removal. That's a better model than `/v2`, but it requires knowing who uses what, forever, which means the usage tracking above, a deprecation policy, and someone who owns schema review. Without that, you get a schema that only grows — which is the same disease as the endpoint list, relocated.

**One more runtime in the path.** An executor sits between HTTP and your domain code. It has its own failure modes, its own performance characteristics, and its own version upgrades.

## Alternatives

The full REST comparison is 8.2 — including the case that you should keep both, which is what most large systems actually do. Briefly, the other things that address parts of the same problem:

- **A BFF endpoint per client surface.** Solves over-fetching and waterfalls completely, keeps HTTP caching, keeps per-endpoint cost predictability. What it doesn't solve is the release coupling — every client-side change is still a backend deploy. That's two of the three pressures for a fraction of the complexity, and for a lot of teams it's the right answer.
- **Sparse fieldsets and `include=`** (7.4b). Cheap, incremental, standardized by JSON:API if you want a spec rather than a house convention. Handles over-fetching, doesn't handle arguments at depth or deep traversal, and tends to grow toward a worse GraphQL.
- **Typed RPC** — tRPC in a TypeScript monorepo, gRPC with generated clients, or OpenAPI codegen. Delivers the type safety and the editor experience, not the client-specified selection. Excellent when the clients ship with the server.
- **OData.** A full query specification over HTTP with filtering, projection, and expansion, and genuine tooling in the Microsoft ecosystem. Rare elsewhere.

## How to Achieve It

Nobody rewrites a working REST API. The path that works is additive, and each step has a signal that says the next one is due.

**Level 0 — one screen, read-only, over your existing API.** Stand up a GraphQL endpoint whose resolvers call your own REST endpoints over HTTP. It is architecturally ugly and it is the fastest way to prove or disprove the client-side benefit. Point one painful screen at it.
*Move on when:* the extra HTTP hop is your latency floor and batching can't cross it.

**Level 1 — resolvers talk to the domain layer.** Repositories and services directly, same process. Add request-scoped batching now rather than later (8.3a), because retrofitting it means touching every resolver.
*Move on when:* reads are working and clients are doing GraphQL for reads and REST for writes, and the cache-update story between them is incoherent.

**Level 2 — mutations move over.** REST stays for file upload, webhook receipt, OAuth callbacks, and anything a machine consumes. This is a permanent split, not a transitional one.
*Move on when:* the schema is what frontend teams design against.

**Level 3 — the schema becomes the contract.** Generated client types, CI checks that validate every query in every client repo against the schema, `@deprecated` with per-field usage metrics behind it.
*Move on when:* someone proposes removing a field and the honest answer to "who uses this?" is a shrug.

**Level 4 — trusted operations and cost control.** Persisted queries (which also restore CDN caching), complexity limits, per-client budgets. Mandatory before external exposure. Then, if and only if separate teams own separate parts of the graph, composition across services — Module 40.

Most systems should stop at 2 or 3. Level 4 is a response to scale and exposure, not a destination.

## Implementation

Go, with gqlgen — chosen because it is schema-first with code generation, which makes the two claims of this article checkable by a compiler: the schema is the source of truth, and every field is a function.

You write the SDL. `gqlgen generate` produces the models and, for every field it can't satisfy from a plain struct field, a method on an interface you are required to implement:

```go
// Generated. You implement this.
type EpisodeResolver interface {
	Show(ctx context.Context, obj *model.Episode) (*model.Show, error)
	Guests(ctx context.Context, obj *model.Episode) ([]*model.Person, error)
}

type QueryResolver interface {
	Show(ctx context.Context, id string) (*model.Show, error)
	Episode(ctx context.Context, id string) (*model.Episode, error)
	ContinueListening(ctx context.Context, first int) ([]*model.PlaybackPosition, error)
}
```

Fields that map cleanly onto struct fields — `Episode.title`, `Episode.durationSeconds` — get no method at all. Only the edges and the computed fields need code, which is a useful visual: the methods you have to write are exactly the places where the graph is stitched together.

```go
func (r *queryResolver) ContinueListening(
	ctx context.Context, first int,
) ([]*model.PlaybackPosition, error) {
	user := auth.FromContext(ctx)           // ← see aside 2
	return r.Playback.Recent(ctx, user.ID, first)
}

func (r *episodeResolver) Show(
	ctx context.Context, obj *model.Episode,
) (*model.Show, error) {
	return r.Shows.ByID(ctx, obj.ShowID)    // ← see aside 1
}

func (r *showResolver) Artwork(
	ctx context.Context, obj *model.Show, size model.ArtworkSize,
) (string, error) {
	return r.CDN.SignedURL(ctx, obj.ArtworkKey, size)  // ← see aside 3
}
```

That's the whole mechanism. Four small functions and the query at the top of this article resolves.

**Aside 1 — the N+1 is right there and it's invisible.** `episodeResolver.Show` is a correct, clear, single-purpose function. Ten `continueListening` results call it ten times, which is ten `SELECT … WHERE id = ?` queries. Nothing in the signature hints at this; the resolver is *structurally forbidden* from seeing its siblings. The fix is a request-scoped loader that collects ids within a tick and issues one `WHERE id = ANY($1)` — 8.3a — and the reason to install it at Level 1 rather than later is that every resolver's body changes when you do.

**Aside 2 — `ctx` is the only channel you have left.** There's no route, so there's no place to hang middleware that knows which field is executing. Auth identity, loaders, tracing spans, and the tenant context from Module 5.2a all ride in the context, injected by one HTTP middleware in front of the executor and read individually by every resolver that needs them. That is a meaningful architectural consequence: a cross-cutting concern that used to be declared once per route is now a line inside each function that cares, and "the one resolver that forgot" is a real vulnerability class rather than a hypothetical one.

**Aside 3 — this is the field that shouldn't be `String!`.** `SignedURL` crosses a network boundary. If it returns an error, the executor cannot write null into a non-null field, so it nulls `show`, then `episode`, then the whole `continueListening` list, and the car displays nothing because one thumbnail signature failed. Declaring it `artwork(size: …): String` instead costs the client a null check and contains the failure to one image. The schema decided the blast radius, months before this code existed.

**Aside 4 — resist returning database rows.** It is tempting to point gqlgen's model mapping straight at your persistence structs, and it works until either the schema needs a field the table doesn't have or the table gets a column you didn't intend to publish. The second direction is the dangerous one, because it fails silently and in the direction of exposure. Map explicitly, the way Module 7.4b argued for separate list and detail representations — the schema is a published contract and the table is not.

## Further Reading

- **The GraphQL specification** (spec.graphql.org, October 2021 edition). Genuinely readable. Section 6, *Execution*, is the part worth an hour — field collection, resolution order, and the error-propagation rules that produce the nullability behavior above.
- **graphql.org/learn** — the official tutorial; the right place to send someone who needs the syntax rather than the argument.
- **Lee Byron and Nick Schrock, "GraphQL: A data query language"** (Facebook engineering blog, 2015) — the original announcement. Short, and useful for seeing that the motivation was mobile release cycles from the start, not payload size.
- **_Production Ready GraphQL_, Marc-André Giroux** — the single best book on the subject. Schema design, versioning by deprecation, security, and performance, all from someone who ran GitHub's public schema.
- **Shopify's GraphQL Design Tutorial** (github.com/Shopify/graphql-design-tutorial) — free, and the best writing anywhere on how to model a domain as a schema rather than as a transcript of your tables.
- **GraphQL Cursor Connections Specification** (relay.dev) — the connections/edges/pageInfo shape and why it's built the way it is.
- **The gqlgen documentation** (gqlgen.com) — particularly the model binding and resolver configuration pages.
- **GitHub's GraphQL API docs** — a large public schema you can introspect in a browser today; their rate-limit page describes a real cost model, which sets up 8.3b.

A TypeScript sibling would earn its place here, and not for parity. Code-first builders like Pothos invert this article's central claim — the schema is *derived* from your TypeScript types rather than being their source — which removes the codegen step and the SDL file entirely, and correspondingly removes the artifact that schema review and CI schema-diffing operate on. That's a genuine trade, and it's the dominant style in the Node ecosystem. Not yet written.

---

The habit to carry out of this: whenever a client and a server disagree about the shape of a response, ask which side is allowed to decide — and then ask what it costs the other side to change its mind. In the endpoint list at the top of this article, the server decided, and the cost to change was a deploy plus an app-store review plus three years of cars on the old build. Every technique in this module is a different answer to that second question.
