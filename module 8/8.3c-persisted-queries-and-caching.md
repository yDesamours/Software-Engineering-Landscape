# Persisted Queries and Caching

_Module 8.3c — GraphQL APIs_

## The Problem

A news reader. Web, iOS, Android. The top-stories feed is the same for everybody who isn't signed in, and most people aren't signed in.

Before the GraphQL migration, the feed was `GET /feed/top`, returning JSON with `Cache-Control: public, max-age=30`. A CDN served it from edge nodes at about 5ms. At 40,000 requests per minute, origin saw roughly two — one per TTL window per region. The database saw almost nothing. Nobody thought about it, because nobody had to.

After the migration, the same feed is:

```
POST /graphql
Content-Type: application/json

{"query":"query TopStories($n:Int!){ topStories(first:$n){ … } }","variables":{"n":20}}
```

Origin now sees all 40,000 requests per minute. Not because anything is slower — the resolvers are fine, the loaders from 8.3a are doing their job — but because **no cache can key on this request.** Caches identify a response by method and URL. This is a POST, and everything that distinguishes one request from another is in the body. Every CDN node, every reverse proxy, and the browser's own cache all do the only thing they can: forward it.

The infrastructure didn't degrade. It went dark. Module 8.2's left-hand column, in production.

Three smaller things came along with it.

**The document is sent every time.** That feed query with its fragments is 4.1KB of text. The response is 8KB. Roughly a third of the bytes on the wire are the client re-explaining, on every request, a question it has asked ten thousand times. On mobile uplink — slower and higher-latency than downlink — that's a measurable part of time-to-first-byte.

**Anyone can send anything.** The endpoint accepts arbitrary documents from strangers, so 8.3b's cost analysis is the only thing standing between the public internet and the database — and its budget has to be loose enough not to break the app's own largest screen.

**The app refetches constantly.** Navigate into an article and back, and the feed loads again. The browser cache used to absorb that. Now there is nothing between the component and the network unless something was built.

Four symptoms, one root: **GraphQL removed the name of the thing being fetched.** A URL was an identity — for a cache, for a log, for a CDN rule. One endpoint and a body isn't. Most of this article is about inventing a name back, and it turns out the mechanism that does that also solves the other three.

## What It Is

**Persisted queries**: the client sends an identifier for a document instead of the document. The server resolves the identifier against a registry and executes what it finds.

There are two things called this and they are not the same thing. Conflating them is how teams end up believing they've locked down an API they haven't.

**Automatic Persisted Queries (APQ)** is a negotiation protocol. The client sends a SHA-256 hash of its query. If the server doesn't recognize it, it replies `PersistedQueryNotFound`; the client retries with the full document and the hash, and the server stores the pairing for next time. Purely a **bandwidth and cacheability** optimization. The server will register and execute whatever it's handed, so it grants exactly zero security.

**Trusted documents** (also "persisted operations," "the safelist") invert the registration. A build step extracts every document from your client source, hashes them, and publishes the manifest to the server. The server executes registered documents and **refuses everything else**. This is a security control, and it's the strongest one available for a first-party API.

Same wire format, opposite trust model. The difference is entirely in who is allowed to add to the registry.

And one small thing with outsized effect: once the client sends a short hash instead of a 4KB document, the request fits comfortably in a URL — so it can be a `GET`, and it has an identity again.

## Recognizing the Problem

- A significant share of your traffic is anonymous, and your origin sees all of it.
- CDN hit rate on `/graphql` is zero, because everything is a POST.
- Your largest query document is bigger than the response it produces.
- The same operation, with the same variables, runs thousands of times a minute and returns the same bytes.
- Navigating back in the app refetches everything.
- You can't answer "which queries can clients send?" with a list.
- Your cost limits are tuned around your own heaviest screen, so they're generous for everyone.
- Mobile time-to-first-byte is worse than the response size explains.
- Introspection is enabled in production because a client library needs it.

## How It Works

There are four distinct caches involved and conflating them is the standard failure. Taken in order from the edge inward.

### 1. Giving the request an identity again

```
before                                      after

 browser ──POST /graphql {4.1KB}──► origin   browser ──GET /graphql?id=a3f…&variables=…──►
   CDN:  can't key on a body                   CDN:  keyed on the URL ──► HIT 99.4%
   40,000 req/min at origin                    ~2 req/min at origin
```

The mechanics:

- Queries go over `GET` with the hash, operation name, and variables in the query string. **Mutations always stay POST**, and the server must enforce that rather than trusting clients to — a mutation reachable by GET is a cross-site request forgery waiting to happen, and it's also cacheable, which is worse.
- The CDN's cache key must include the full query string. This is a configuration change, not a default.
- URLs have practical limits — 2KB is safe, 8KB is where servers start rejecting. Sending the whole document in a GET works right up until a fragment pushes you over, which is another reason the hash is the right payload.
- The server sets `Cache-Control` **per operation**. This is the subtle win: one endpoint can still emit different caching policy per request, because the resolved document tells it which operation ran. `TopStories` gets 30 seconds; `MyReadingList` gets `private, no-store`.

### 2. The registry, and its operational shape

A build step scans client source for GraphQL documents, hashes each one, and publishes a manifest. The client bundle ships hashes rather than query text.

Two operational facts do most of the damage when missed:

**Publish the registry before the client that uses it.** If a deploy ships the app bundle first, every request from it is a `PersistedQueryNotFound` (or a refusal, with trusted documents) until the manifest lands. Registry publication belongs earlier in the pipeline than client release, and a rollback of the server must not roll back the registry.

**The registry is append-only in practice.** An iOS build from two years ago is still sending its hashes. Removing a document breaks exactly the clients you can't reach — 8.1a's long tail, in a new costume. Entries leave the registry only when usage metrics show nobody has used them in months.

### 3. What can actually be cached, and the rule that spoils it

Now the honest accounting, because response caching in GraphQL under-delivers for a structural reason people rarely name.

Anonymous and identical → full win. Per-user → `private`, no shared caching, exactly as Module 7.4a concluded for REST. Nothing new so far.

The new thing is **mixed documents**:

```graphql
query ArticlePage($slug: String!) {
  article(slug: $slug) {       # public, safely cacheable for minutes
    title body author { name }
  }
  viewer {                     # private, per-user, uncacheable
    bookmarked(slug: $slug)
    remainingFreeArticles
  }
}
```

A response cache caches *responses*. It cannot serve half of one. So the cache policy for the whole response is the **minimum** across everything in it — one private field makes the entire response private, and one 10-second field caps the whole thing at 10 seconds.

This is a direct consequence of letting clients compose queries: they will compose public and private data into one request, because that's the point of the feature. Two remedies:

- **Split the document.** A public `ArticlePage` query and a private `ArticleViewerState` query, issued in parallel. Costs one extra round trip, which HTTP/2 makes cheap (7.4b), and recovers the CDN hit on the 95% of bytes that are public. For content sites this is usually the correct answer and it's worth designing the screens around.
- **Move down a layer** to caching fields rather than responses.

### 4. Caching fields and entities

Instead of caching whole responses, cache what individual resolvers return, keyed by field and arguments. `Article:9f21` is cached once and serves every query selecting any subset of its fields.

That last clause is the one place in this module where GraphQL is straightforwardly *better* than REST at caching. A REST cache stores `/articles/9f21` and `/articles/9f21?fields=title` as two unrelated entries in two shapes. An entity cache stores the article once, normalized, and every shape is a projection of it. Field selection, which broke response caching, makes entity caching work better.

The natural home for this is underneath the loaders from 8.3a: the loader batches, a shared cache absorbs the repeats across requests. Invalidation is Module 13's problem and is not made easier by any of this — TTLs in the tens of seconds remain the honest answer for most content.

Servers that support cache hints (`@cacheControl(maxAge: 60, scope: PUBLIC)` on fields and types) use them for both purposes: the hints drive field-level caching *and* the engine computes the response's overall `Cache-Control` as the minimum over every field touched. That automates the rule above, which is good, and hides it, which is the risk — see the asides.

### 5. The client's normalized cache

The last cache is in the app, and it's the replacement for the browser cache you lost.

Responses are flattened into a store keyed by `__typename` plus id, so `Person:41` is one record no matter which of eight queries fetched it. Any component asking for a field already in the store reads it without a network call.

What it needs: stable ids on every object, `__typename` on every selection (clients add these automatically), and an explicit key configuration for types that have no id.

What it buys, beyond offline reads: a mutation payload updates every screen holding those entities at once. That's 8.1b's payload design finally paying out — return the `Pipeline` and the sidebar corrects itself, because the cache recognized the entity.

Where it hurts:

- **Lists are not entities.** Adding an article to a reading list doesn't update the list, because the list is a field result, not a record. You write an explicit cache update or you refetch. This is the single largest source of "why is the UI stale" bugs.
- **Pagination needs merge policies**, or page two replaces page one.
- **Fetch policy is a real per-screen decision** — cache-first, cache-and-network, network-only — and picking one globally is how you get either stale dashboards or a cache you paid for and disabled.

### What else the registry buys

Once the set of executable documents is known and closed, four things that had nothing to do with caching fall out:

- **Arbitrary queries are refused**, so 8.3b's runtime cost analysis becomes a backstop rather than the primary control.
- **Cost is computable at build time**, so an expensive query fails CI instead of a user's screen.
- **Field usage is exact**, not sampled — which is the thing 8.1a said you need before you can ever delete a field.
- **Introspection can be switched off** without hurting anyone, since no client explores at runtime.

That cluster is why a trusted document registry is the highest-leverage single change available to a first-party GraphQL API, and why it's worth more than the caching that motivated it.

## When It's Appropriate

- **Anonymous, high-volume, identical responses.** GET plus a hash plus a CDN is the largest single performance win available to a GraphQL API, and it's a week of work. Do it before anything else in this module.
- **Mobile clients on poor uplinks.** APQ alone, for the bandwidth, is worth it even with zero cacheable traffic — a 4KB document replaced by a 64-character hash on every request.
- **A first-party-only API.** Trusted documents change your security posture more than any other single control.
- **Concretely:** any operation requested more than about a thousand times a minute with identical results, or any document over ~2KB sent more than a few times per session.

## When It's Unnecessary or Overkill

- **A public API third parties write queries against.** You cannot safelist documents you've never seen. This is the same fork as 8.3b: strangers get cost analysis, first-party clients get a registry.
- **Everything is authenticated and per-user.** There is no shared cache to recover. APQ still saves bandwidth; the CDN work saves nothing, and the build-step complexity buys only the security properties — which may still justify it, but on different grounds than the ones in this article's opening.
- **Low traffic.** Forty thousand requests a minute makes this urgent; four hundred makes it a preference.
- **Field-level cache hints before measuring.** Most schemas have three genuinely cacheable fields. Annotating a hundred of them is busywork, and every `scope: PUBLIC` you write is a chance to leak.
- **A normalized client cache with `network-only` everywhere.** Some apps really do need that — live dashboards, trading, anything where staleness is a defect — and then a simpler HTTP client is the better tool.

## Trade-offs

**The client build now produces an artifact the server depends on.** Deployment order matters, rollbacks get subtler, and CI grows a publish step. For a team shipping a web app and two mobile apps from three repos, this is real coordination cost.

**The registry is permanent.** Append-only, forever, with retirement gated on usage data you have to collect.

**APQ's miss path costs a round trip**, and on a cold edge or a new deploy that's every first request. Worse, a naive APQ implementation lets anyone register documents into an unbounded server-side map, which is a memory exhaustion vector. Bound the store, give it a TTL, or don't accept runtime registration at all.

**GET puts variables in URLs, and URLs go in logs.** Every proxy, load balancer, and CDN access log along the path now records your variables — which may contain email addresses, document ids, or search terms. This is a genuine privacy regression over POST bodies and it needs a decision, not a discovery during an audit.

**A wrong cache scope is a cross-user data leak.** A field annotated `PUBLIC` that should have been `PRIVATE` gets one reader's data served to another from an edge node. This is the highest-severity failure in the article, it will not show up in tests, and it's a one-word mistake in a schema file.

**Four caches, one symptom.** "The UI showed old data" now has an edge cache, a server field cache, a client normalized cache, and a fetch policy as candidate causes. Budget for the debugging, and make each layer observable — a response header naming the cache that served it is cheap and pays for itself immediately.

**Invalidation is unchanged.** Nothing here makes Module 13's hard problem easier; it just gives you more places to have it.

## Alternatives

- **Use POST and scale the origin.** Entirely legitimate. Caching is not free, and for a mid-traffic authenticated app the origin capacity is cheaper than the pipeline complexity.
- **One REST endpoint for the hot anonymous query.** `GET /feed/top` beside the GraphQL API, CDN-cacheable, boring, and it solves the opening problem in an afternoon. 8.2's "keep both," applied narrowly and on purpose. Unglamorous and frequently correct.
- **Cache the rendered page, not the data.** For content sites, server-side or edge rendering with a cached HTML response sidesteps this layer entirely and usually beats it on time-to-first-paint.
- **CDN configurations that key on POST bodies.** Some edge platforms can hash a request body into the cache key. It works, it's non-standard, it breaks when a client reorders JSON keys, and it's a worse version of sending a hash yourself.

## How to Achieve It

**1. Measure the split.** What fraction of traffic is anonymous, and what are your top five operations by volume? If anonymous traffic is a rounding error, stop — the rest of this is a security project, not a performance one, and should be justified that way.
*Next when:* you have a number.

**2. Turn on APQ.** A client-library flag and a bounded server-side store. Bandwidth win immediately, no build changes.
*Next when:* hashes are flowing and the store is capped.

**3. Move queries to GET; keep mutations on POST and enforce it server-side.** Configure the CDN cache key to include the query string.
*Next when:* you can see GET requests for `/graphql` at the edge.

**4. Set `Cache-Control` per operation, starting with the single hottest anonymous one, at 30 seconds.** One operation, one number, measurable the same day.
*Next when:* the hit rate on that operation is where you expected.

**5. Split public and private documents** where the minimum-TTL rule is eating your hit rate.
*Next when:* the remaining uncacheable traffic is genuinely per-user.

**6. Move from APQ to build-time extracted trusted documents, and refuse the unregistered.** Registry publish goes before client release in the pipeline.
*Next when:* refusal rate in production is zero for a full release cycle — which is also the point at which the 8.3b backstop can be loosened and introspection can go off.

**7. Only then, field-level hints and a shared cache under the loaders**, for the fields measurement says are worth it.

## Implementation

Go, because all of this is transport-layer work that happens *before and after* the executor — which is the structural point. None of it belongs in a resolver.

Document resolution, with the trust model as an explicit switch:

```go
func (h *Handler) resolveDocument(r *http.Request, req *gqlRequest) (string, error) {
	hash := req.Extensions.PersistedQuery.Sha256Hash
	if hash == "" {
		if h.trustedOnly {
			return "", errUnregisteredDocument          // ← aside 1
		}
		return req.Query, nil
	}

	if doc, ok := h.registry.Get(hash); ok {
		return doc, nil
	}
	if h.trustedOnly {
		return "", errUnregisteredDocument
	}
	// APQ negotiation: accept a document the client offers, once.
	if req.Query == "" {
		return "", errPersistedQueryNotFound            // client will retry with text
	}
	if sha256Hex(req.Query) != hash {
		return "", errPersistedQueryHashMismatch        // ← aside 2
	}
	h.registry.PutWithTTL(hash, req.Query, time.Hour)   // ← aside 3
	return req.Query, nil
}
```

Routing, where the method rule is enforced rather than assumed:

```go
func (h *Handler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	req, err := parseRequest(r)                         // GET → query string, POST → body
	// …
	if r.Method == http.MethodGet && isMutation(doc, req.OperationName) {
		http.Error(w, "mutations must use POST", http.StatusMethodNotAllowed) // ← aside 4
		return
	}
	// …
}
```

And the response policy, computed as the minimum over every field that ran:

```go
type cachePolicy struct {
	maxAge  time.Duration
	private bool
}

func (p *cachePolicy) observe(hint fieldHint) {         // called per resolved field
	if hint.Scope == ScopePrivate {
		p.private = true
	}
	if hint.MaxAge < p.maxAge {
		p.maxAge = hint.MaxAge                            // ← aside 5
	}
}

func (p cachePolicy) header() string {
	if p.private || p.maxAge == 0 {
		return "private, no-store"
	}
	return fmt.Sprintf("public, max-age=%d", int(p.maxAge.Seconds()))
}
```

**Aside 1 — one boolean is the entire difference between APQ and a safelist.** With `trustedOnly` false, this handler will execute any document a stranger sends and remember it. With it true, the registry is the complete set of executable queries. Teams deploy the first, read the words "persisted queries" in their architecture doc, and reason about their security posture as though they had the second.

**Aside 2 — verify the hash before storing.** Skipping this lets a client register arbitrary text under a hash that a *different* client will later request by hash, which is cache poisoning with extra steps.

**Aside 3 — the TTL and a bounded store are not optional in APQ mode.** An unbounded map that anyone on the internet can insert into is a memory exhaustion vector reachable without authentication. If you can't bound it, don't accept runtime registration.

**Aside 4 — the client is not the enforcement point.** A client library that sends mutations over POST is a convention; a server that accepts them over GET is a vulnerability. GET is cacheable, prefetchable by browsers and link scanners, and triggerable cross-origin — three separate ways for a mutation to run without anyone meaning it to.

**Aside 5 — this `<` is where a data leak lives.** The minimum has to win on both axes: one private field makes the whole response private, and one short TTL caps the whole response. Get the comparison backwards, or forget to call `observe` for a field resolved through an unusual path, and an edge node serves one reader's bookmarks to the next reader with a well-formed `public, max-age=60`. Default `maxAge` to zero and `private` to true, so that a field nobody annotated makes the response uncacheable rather than public.

## Further Reading

- **The GraphQL over HTTP specification** (graphql.github.io/graphql-over-http) — how GET and POST are meant to work, parameter names, content types, and status codes. Short, and the thing to standardize on rather than inventing your own query-string format.
- **Apollo's Automatic Persisted Queries documentation** — the negotiation protocol in detail, including the miss path.
- **Apollo's persisted queries / trusted documents documentation** — the build-time extraction flow and the safelist model. Read both and the distinction in this article becomes concrete.
- **Apollo Server caching documentation** — `@cacheControl`, `scope`, and the computation of a response's overall policy as the minimum over fields. The reference for the rule in aside 5.
- **The Relay compiler's persisted query support** — Relay has shipped hash-only clients since the beginning, and its docs describe the deploy-ordering constraints from experience.
- **`graphql-java`'s `PersistedQuerySupport`** — the same mechanism as a pluggable document provider, useful for seeing where the seam belongs.
- **Module 13** for cache invalidation, which none of this improves, and **Module 18** for the rate limiting that a registry lets you relax.

A TypeScript sibling would show the version most teams actually run: Apollo Server computes the min-over-fields policy automatically from schema directives, so aside 5's comparison disappears into the framework. That's better — and it relocates the highest-severity decision in this article from a line of code into a one-word annotation in a schema file, where it's reviewed by whoever is reviewing schema changes that week. Whether that's an improvement depends entirely on whether that reviewer knows what `scope: PUBLIC` means. Not yet written.

---

The habit worth carrying: a cache needs a name for the thing it's caching, and that name has to be derivable from the request alone. REST handed you one for free and you never had to think about it. GraphQL takes it away, and everything in this article — hashes, registries, cache keys, `__typename:id` — is a way of inventing a name back. When you next design any interface where the request is a description rather than an address, that's the question to ask first: what will the cache call this?
