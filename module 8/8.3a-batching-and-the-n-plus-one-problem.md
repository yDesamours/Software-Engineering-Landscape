# Batching and the N+1 Problem

_Module 8.3a — GraphQL APIs_

## The Problem

A developer community forum. Questions, answers, comments, people. The thread page is one query:

```graphql
query ThreadPage($id: ID!) {
  question(id: $id) {
    title
    tags { name }
    author { name avatarUrl reputation }
    answers(first: 30) {
      body
      votes
      author { name avatarUrl reputation }
      comments(first: 5) {
        body
        author { name }
      }
    }
  }
}
```

Nine fields. It reads like one screen's worth of data, and it is.

Here's the database log for a single execution:

```
SELECT … FROM questions WHERE id = $1
SELECT … FROM tags WHERE question_id = $1
SELECT … FROM people WHERE id = $1
SELECT … FROM answers WHERE question_id = $1 ORDER BY votes DESC LIMIT 30
SELECT … FROM people WHERE id = $1        ×30
SELECT … FROM comments WHERE answer_id = $1 LIMIT 5   ×30
SELECT … FROM people WHERE id = $1        ×112
```

Roughly 214 queries for one page view. Of those, 143 are the same `SELECT … FROM people WHERE id = $1` with different ids — and in a community forum the same twenty regulars write most of the answers, so those 143 lookups cover about 40 distinct people. A hundred of them are literally duplicate work.

Two costs, and the second is the one that takes the site down.

**Latency.** At 0.8ms per round trip to a database on the same network, 214 queries is roughly 170ms of pure waiting, before any of the actual work. The page felt fine in development against a local socket and got noticeably worse in production, for no reason anyone could point at.

**Connection pressure.** GraphQL resolves sibling fields concurrently (8.1a), so those thirty `author` lookups don't queue politely — they go out together and each wants a connection. A pool of 20 handles that by making 10 of them wait. Now run 50 of these requests at once, which is a modest thread page on a modest forum, and the pool is the bottleneck for the entire application. Requests that have nothing to do with this page start timing out. The alert that fires says "database connection pool exhausted," which sends someone to tune the pool, which is the wrong place.

And notice what makes this hard to see coming. Here is the resolver responsible for 143 of those queries:

```go
func (r *answerResolver) Author(ctx context.Context, obj *model.Answer) (*model.Person, error) {
	return r.People.ByID(ctx, obj.AuthorID)
}
```

It is correct. It fetches one person by id, which is exactly what it was asked to do. There is no version of this function that is better, because **the function cannot see that it is one of thirty**. 8.1a put this structurally: a resolver receives exactly one parent object and has no knowledge of its siblings. The pathology is not in the function; it's in the aggregate, and the aggregate has no code.

### Why the ORM remedy doesn't transfer

This is the same N+1 that Module 6.4 covered for ORMs, with one difference that changes the entire solution.

With an ORM, the fix is at the call site. The code that's about to iterate over thirty answers knows it's about to iterate over thirty answers, so it says so:

```
answers = Answer.where(question_id: id).includes(:author, comments: :author)
```

The caller knows the whole shape in advance, so it can declare it in advance.

In GraphQL there is no such caller. The shape is chosen by the client, assembled by the executor, and never visible in one place to any piece of your code. The `answers` resolver doesn't know whether the client asked for authors. The `author` resolver doesn't know how many siblings it has. Nobody is in a position to write `includes`.

So the fix has to work the other way round: instead of declaring the batch before it happens, **collect the individual requests as they happen and defer them until you know how many there are.**

## What It Is

The technique is **per-request batching**, and its canonical implementation is called a **DataLoader** — an object that sits between resolvers and your data source.

A resolver never fetches. It asks:

```go
return r.Loaders.Person.Load(ctx, obj.AuthorID)
```

The loader records the key, returns a pending result, and waits. When the batching window closes, it calls one batch function with every key collected in that window:

```
people.ByIDs(ctx, [41, 7, 41, 902, 7, 41, 88, …])
```

which becomes one `SELECT … WHERE id = ANY($1)`, and the results are distributed back to the thirty resolvers waiting on them.

```
without a loader                      with a loader

 author(answer 1) ──► SELECT id=41     author(answer 1) ──┐
 author(answer 2) ──► SELECT id=7      author(answer 2) ──┤
 author(answer 3) ──► SELECT id=41     author(answer 3) ──┤ collect
      …                    …                 …           ├──► dedupe 30 → 12 keys
 author(answer 30)──► SELECT id=88     author(answer 30)──┘         │
                                                                    ▼
        30 round trips                                  SELECT … WHERE id = ANY($1)
                                                                    │
                                                          distribute to all 30
```

Two mechanisms are bundled in that object and it's worth separating them, because they fail differently:

1. **Batching** — many individual key requests become one bulk call.
2. **Per-request memoization** — the same key requested twice resolves once. That's what turns 143 lookups into 40.

One disambiguation that matters more than it sounds: **a loader is not a cache** in the sense of Module 13. Its lifetime is exactly one request, deliberately. The memoization exists to deduplicate *within* one response, not to serve the next user faster. Sharing a loader across requests is the single most common serious bug in GraphQL servers — it leaks one user's authorized data into another user's response, it serves arbitrarily stale values with no invalidation path, and it grows without bound. Construct loaders per request, in the middleware that builds your context, always.

## Recognizing the Problem

- Query count per HTTP request is in the hundreds, or you don't know what it is.
- The same `SELECT` appears dozens of times in a trace with only the parameter varying.
- A distributed trace for one request is a wall of identical 0.9ms spans.
- Response time scales linearly with list length — 10 items is 90ms, 50 items is 430ms.
- "Connection pool exhausted" under concurrency that shouldn't be a problem.
- Adding one nested field to a client query doubled p99 latency, and no server code changed.
- Your database's `pg_stat_statements` is topped by a single-row primary-key lookup, by call count, by an order of magnitude.
- Local development is fast and production isn't, and the difference is larger than the data volume explains.

## How It Works

### The batching window is the hard part, and it differs by runtime

"Wait until you know how many there are" is easy to say and is where implementations diverge. You need a moment that reliably falls *after* all thirty `author` resolvers have asked and *before* anything is blocked waiting.

**In JavaScript**, it's the microtask queue. `Loader.load()` enqueues the key and returns a promise; the batch function is scheduled with `process.nextTick` / a resolved-promise continuation, so it runs once the current synchronous execution — during which all thirty resolvers ran — has drained. The window is exact and invisible, which is why DataLoader feels magical in Node and why nobody there can explain what it's doing.

**In Go**, there is no event loop. Resolvers run in goroutines, concurrently and unpredictably. So loaders use a **time window plus a size cap**: collect keys for 1–2ms or until 100 keys arrive, then dispatch. It works, and it costs you that 1–2ms on the critical path of every level, including levels with a single key.

**In Java**, `graphql-java` cooperates explicitly. The executor knows when it has finished collecting all fields at one level of the query and signals the `DataLoaderRegistry` to dispatch then. Exact, like JavaScript, without the time penalty of the Go approach — but only because the executor was instrumented to make it possible.

Which points at the property that makes any of this work:

### Batching depends on breadth-first execution

The executor resolves every field at one level before descending. All thirty `Answer.author` fields are visited before any `Person.badges` beneath them. If execution were depth-first per item — finish answer 1 completely, then answer 2 — there would never be more than one key in flight and nothing to batch.

That's also why batching flattens a query *by level*, not to one query:

```
level 1   question           ─► 1 query
level 2   tags, author, answers ─► 3 queries   (batched within each field)
level 3   answer authors, comments ─► 2 queries
level 4   comment authors    ─► 1 query
                                ────────────
                                  7 queries, 4 sequential round trips
```

214 becomes 7. The remaining floor is **depth**, and no amount of batching removes it. That's the first hint that query cost has a second dimension, which is 8.3b's subject.

### The batch function, and the contract that bites

```
ByIDs(ctx, keys []uuid.UUID) ([]*Person, []error)
```

The returned slice must be **the same length as `keys`, in the same order**, with a nil (or an error) in the position of anything not found. That sounds like an implementation detail. It is the highest-severity footgun in this entire technique.

A batch function that does the obvious thing — `SELECT … WHERE id = ANY($1)` and return the rows — returns them in whatever order the database produced, and returns fewer rows than keys when one id is missing or one row was deleted between levels. Both cases shift the results by one, and every resolver downstream of the shift receives **a different person's record than the one it asked for**. No error is raised. The response is well-formed. One user's name, avatar, and reputation are attached to another user's answers, and if the entity involved had been something private, you've published it.

Treat this as a security-grade invariant: the batch function re-associates rows to keys by building a map and indexing it, never by relying on result order, and never by returning a compacted slice.

The same class of bug appears with deduplication keys. If the loader key is a struct or an object rather than a scalar, most implementations compare by identity, so nothing ever deduplicates and you quietly get the batching without the memoization — 143 lookups become one query of 143 ids instead of 40. Supply an explicit cache-key function whenever the key isn't a primitive.

### The three loader shapes

Most explanations cover the first and stop, which leaves you stranded at the second field you try.

**By id.** `Person.ByIDs(ids)` → `WHERE id = ANY($1)`, map by id, return in key order. Mechanical.

**One-to-many by parent.** `question.answers`, `person.badges`. The key is the *parent* id; one query fetches all children for all parents, and you group in memory:

```sql
SELECT … FROM answers WHERE question_id = ANY($1)
```

The trap here is the empty case: a parent with no children must get an empty slice, not a nil and not a missing entry. Non-null list fields (`[Answer!]!`) will otherwise null out and take their parents with them (8.1a).

**One-to-many with arguments.** `answers(first: 5, orderBy: VOTES)` is the case where naive batching fails outright, because each parent needs its own `LIMIT`. Two real answers:

*Include the arguments in the batch key.* Only requests with identical arguments batch together. Correct, trivially, and effective in practice because a given screen sends the same arguments for every sibling.

*Do top-N-per-group in one query* with a window function:

```sql
SELECT * FROM (
  SELECT a.*, ROW_NUMBER() OVER (
           PARTITION BY a.question_id ORDER BY a.votes DESC) AS rn
  FROM answers a
  WHERE a.question_id = ANY($1)
) t
WHERE t.rn <= $2
```

or a `LATERAL` join against the parent ids. One query, correct per-parent limits, and it's the technique most teams don't know exists — they conclude the field "can't be batched" and leave the N+1 in place.

**Aggregates** are a fourth, easy shape: `question.answerCount` batches to one `GROUP BY question_id` and maps back, with zero for parents absent from the result.

### What batching doesn't fix

- **Depth.** Four levels is four sequential round trips no matter how wide each one is. 8.3b.
- **Volume.** You still fetch and serialize every row. A batch of 5,000 is one query and an enormous one — cap batch size, and prefer `= ANY($1::uuid[])` over `IN (…)` with 5,000 placeholders, which blows past parameter limits and defeats plan caching.
- **Remote fan-out.** If `author` comes from a user service over HTTP, batching only helps if that service has a bulk endpoint. If it doesn't, you're stuck at 30 HTTP calls, and the fix is a conversation with another team. This is the most under-appreciated argument for putting bulk lookups on internal services: someone else's GraphQL layer will need them.

### The alternative family: look-ahead

The other approach doesn't defer anything. It **inspects the query** and issues one statement for a whole subtree.

A resolver can ask the executor what was selected beneath it — `DataFetchingFieldSelectionSet` in graphql-java, `graphql.ResolveFieldContext` in others — and if it sees that `author` and `comments` were requested, it issues a single joined query for the whole thing. Taken to its conclusion, this becomes whole-query compilation: Hasura, PostGraphile, and Join Monster translate an entire GraphQL query into one SQL statement.

The trade is clear once stated:

- **Fewer round trips still** — one query, not seven. For deep queries against a single database, this wins decisively.
- **Resolvers become coupled to query shape.** A function that reads the selection set and branches is no longer a simple field resolver, and it gets complicated fast.
- **It only works within one data source.** The moment `author` lives behind another service, the join isn't available and you need loaders anyway.
- **Generated SQL can be pathological**, and it's generated, so nobody reviews it until it's in a slow query log.

Most systems end up with loaders as the default and look-ahead applied surgically to two or three known-hot fields. Systems whose data is entirely in one Postgres instance and whose schema is largely a projection of it are the ones that should look seriously at full compilation.

There's also a free option people skip: **if the parent already has the data, read it off the parent.** When `answers` was fetched through a service call that embedded authors, `Answer.author` should return `obj.Author` and nothing else. Adding a loader to fetch something you're already holding is a surprisingly common way to create work.

## When It's Appropriate

- **Any GraphQL schema where a list field has object-typed children.** That's essentially all of them; the question is only when you install it. The concrete threshold: the first time a query returns a list of more than about ten items whose children resolve independently.
- **Fields backed by a shared entity.** Authors, tenants, users, categories — anything that repeats across a result set. These get the memoization win on top of the batching win, and it's usually the larger of the two.
- **Before the schema grows,** not after. Converting twenty resolvers to loaders is mechanical but touches every one of them, which is why 8.1a's adoption path puts it at Level 1.
- **Outside GraphQL too.** A REST BFF assembling a screen from three services, a background job enriching rows one at a time, any `for` loop with a fetch inside it. The technique isn't GraphQL's — GraphQL just makes the loop invisible, which is why it needed a name there first.

## When It's Unnecessary or Overkill

- **Single-object queries with no lists.** One question, one author, no fan-out, nothing to batch.
- **Data the parent already holds.** See above.
- **In-process lookups that are already cheap.** Feature flags, enum tables, currency codes held in a map. The loader's bookkeeping — allocation, scheduling, promise or channel machinery — costs more than the map access it replaces.
- **When the backing store has no bulk read.** A loader over a data source that can only fetch one at a time is pure overhead. The fix there is a cache (Module 13), a denormalized read model (Module 2.4), or a bulk endpoint.
- **As a reflex on every field.** Routing everything through deferred loaders makes traces harder to read and adds latency in the Go-style time-window model, on levels where a single direct call would have done.

## Trade-offs

**Everything becomes deferred, and debugging gets harder.** The stack trace at the point of failure is inside a batch dispatcher, not inside the resolver that asked. "Which field caused this query" stops being obvious, and you need per-loader instrumentation to get it back.

**Correctness now depends on an ordering contract** that no type system checks. The failure mode is silent misattribution of data across entities, which is the worst kind of bug to ship — it looks like working software. Unit-test every batch function specifically for a missing key and for out-of-order database results.

**Per-request memoization can serve stale data to a mutation's own payload.** This one catches everybody. A mutation updates a question, then its payload resolves `question { title }` through a loader that already cached the pre-mutation row earlier in the same request. The response reports the old value, immediately, in the response to the write that changed it. Loaders need a `Clear(key)` or `Prime(key, value)` call after every write — which is a small amount of code and one line in the checklist for every mutation you write (8.1b).

**Time-window batching adds latency everywhere** in runtimes without an exact dispatch signal, including on the many levels that only ever have one key.

**Memory grows with query breadth.** A loader holds every entity it touched for the duration of the request. A query that reads 5,000 rows keeps 5,000 objects live until the response is written.

**It hides the remaining problem.** Once query count drops from 214 to 7, the graph looks healthy and nobody looks again — but a client can still write a query that fetches a hundred thousand rows in seven statements. Batching removes round trips; it does nothing about cost. That's why it is not a substitute for 8.3b, and why teams that install loaders and stop are the ones who get surprised.

## Alternatives

- **Look-ahead and whole-query compilation** — covered above; the genuine competitor.
- **Denormalized read models.** If the thread page is 60% of your traffic, a projection maintained by domain events (Module 2.4, Module 37) collapses the whole query into one read of one row. Highest ceiling, highest cost, and the right answer for a small number of very hot screens.
- **A shared cache under the batch function.** Redis in front of `ByIDs`, so repeats *across* requests are cheap too. This is Module 13 territory, with all of its invalidation obligations, and it composes with loaders rather than replacing them: the loader batches, the cache absorbs.
- **Bulk endpoints on internal services.** Not an alternative so much as the prerequisite for batching across a network boundary.

## How to Achieve It

**1. Measure first.** Count database queries per HTTP request, tagged by GraphQL operation name. If you can't produce that number today, build it before anything else — it's the metric that tells you whether any of the following worked.
*Next when:* you have a ranked list of operations by query count.

**2. Build the per-request loader registry and wire it into context.** One place constructs all loaders, in the middleware that builds the request context, next to the authenticated actor (8.1a's aside 2). Convert the single worst field.
*Next when:* that field's query count is 1 and the pattern is established.

**3. Convert the by-id edges.** Mechanical, high value, low risk. Test each batch function against a missing key.
*Next when:* the remaining offenders are all list fields.

**4. Convert one-to-many with grouping,** minding the empty-slice rule.
*Next when:* what's left are list fields taking arguments.

**5. Handle argument-bearing lists** — arguments in the batch key first, window functions where the volume justifies it.

**6. Add a query-count assertion to tests** for your top operations: "ThreadPage issues at most 8 queries." This is the step people skip, and it's the one that matters over time, because the next nested field a frontend team adds will reintroduce the problem silently and nothing else will notice.
*Next when:* never — this is permanent.

**7. Only then consider a shared cache or a read model,** for the fields where the same keys keep recurring across requests.

## Implementation

Go, because the batching window has to be built by hand here rather than inherited from an event loop — which makes visible the thing every JavaScript explanation of this skips.

The loader, in outline:

```go
type PersonLoader struct {
	fetch  func(ctx context.Context, ids []uuid.UUID) ([]*model.Person, error)
	mu     sync.Mutex
	batch  *batch            // keys collected in the current window
	cache  map[uuid.UUID]*result
	wait   time.Duration     // 1–2ms
	maxBatch int             // 100
}

func (l *PersonLoader) Load(ctx context.Context, id uuid.UUID) (*model.Person, error) {
	l.mu.Lock()
	if r, ok := l.cache[id]; ok {     // per-request memoization
		l.mu.Unlock()
		return r.await()
	}
	l.appendToBatch(id)               // starts a timer if this is the first key
	l.mu.Unlock()
	return l.cache[id].await()
}
```

The timer is the whole difference from the JavaScript version: `appendToBatch` starts a `time.AfterFunc(l.wait, dispatch)` when it opens a new batch, and `dispatch` also fires early if `maxBatch` is reached. That 1–2ms is a real, unavoidable cost per level here, and it's the price of not having an execution model that can tell you when a level is done.

The batch function, written so the ordering contract cannot be violated:

```go
func (r *PersonRepo) ByIDs(ctx context.Context, ids []uuid.UUID) ([]*model.Person, error) {
	rows, err := r.db.Query(ctx,
		`SELECT id, name, avatar_key, reputation FROM people WHERE id = ANY($1)`,
		ids)                                              // ← aside 1
	if err != nil {
		return nil, err
	}
	byID := make(map[uuid.UUID]*model.Person, len(ids))
	for rows.Next() {
		var p model.Person
		if err := rows.Scan(&p.ID, &p.Name, &p.AvatarKey, &p.Reputation); err != nil {
			return nil, err
		}
		byID[p.ID] = &p
	}

	out := make([]*model.Person, len(ids))               // ← aside 2
	for i, id := range ids {
		out[i] = byID[id]                                 // nil for misses, in key order
	}
	return out, nil
}
```

And the one-to-many shape, where the empty case is the part to get right:

```go
func (r *AnswerRepo) ByQuestionIDs(ctx context.Context, qids []uuid.UUID) ([][]*model.Answer, error) {
	// … SELECT … WHERE question_id = ANY($1) …
	grouped := make(map[uuid.UUID][]*model.Answer)
	// … fill grouped …

	out := make([][]*model.Answer, len(qids))
	for i, qid := range qids {
		out[i] = grouped[qid]
		if out[i] == nil {
			out[i] = []*model.Answer{}                     // ← aside 3
		}
	}
	return out, nil
}
```

**Aside 1 — `= ANY($1)`, not `IN (…)`.** One bound parameter carrying an array, rather than N placeholders. With N placeholders you get a distinct SQL text for every batch size, so the plan cache is useless, and past roughly 65,000 parameters the Postgres wire protocol simply refuses. The array form has one plan and one parameter regardless of batch size — which is also what makes capping `maxBatch` a performance decision rather than a correctness one.

**Aside 2 — this loop is the security boundary.** Returning `rows` directly would be shorter and would work in every test where nothing is missing. The first deleted row in production shifts every subsequent person by one position, and the forum starts showing one member's name and reputation on another member's answers, with no error anywhere. Build the map, index by key, accept nil. There is no shortcut here worth taking.

**Aside 3 — the empty slice is not optional.** `Question.answers` is `[Answer!]!`. A nil returned for a question with no answers becomes null in a non-null position, the executor nulls `question`, and the entire response is null because one thread had no replies (8.1a). One line, and it's the difference between a blank page and a working one.

**Aside 4 — the loaders are built per request, and nothing else is acceptable.** Construct them in the middleware that builds the context, beside the authenticated actor. A loader hoisted to a package-level variable "for efficiency" is an authorization bypass and a stale-data source, and it will pass every test you have, because tests run one request at a time.

## Further Reading

- **graphql/dataloader** (github.com/graphql/dataloader) — the reference implementation. The README is short and the source is about 300 lines; reading it is the fastest way to understand the microtask-based batching window.
- **Lee Byron, "DataLoader — Source Code Walkthrough"** — a 30-minute video by its author, mostly about why the scheduling works, which is the part that's hard to infer.
- **Marlow et al., "There is no Fork: An Abstraction for Efficient, Concurrent, and Concise Data Access" (ICFP 2014)** — Facebook's Haxl paper, the origin of the idea. Worth reading for the framing that batching and concurrency fall out of the *structure* of the computation rather than from manual scheduling.
- **graphql-java's DataLoader documentation**, specifically on per-level dispatch — the clearest description of exact dispatch without an event loop.
- **gqlgen's dataloaders guide** — the Go-specific practicalities, including generated loaders.
- **PostgreSQL documentation on `LATERAL` joins and window functions** — the top-N-per-group problem, which is the loader case people give up on.
- **Join Monster** and the **Hasura** or **PostGraphile** architecture notes — the compile-to-SQL family, and the best places to see what look-ahead looks like taken all the way.
- **Module 6.4** for the ORM form of the same problem, and why its remedy doesn't transfer.

A TypeScript sibling would be worth writing, precisely because the window is invisible there. The microtask-tick scheduling makes DataLoader effortless and un-debuggable: when batching silently fails, it's almost always an `await` in the wrong place splitting one tick into two, or a non-primitive key with no `cacheKeyFn`. Both are failures the Go version can't have, and the ergonomics/opacity trade is a real one. Not yet written.

---

The habit worth carrying: when a function is correct in isolation and pathological in aggregate, the fix is never in the function. Look for the place where the aggregate becomes visible — and if there isn't one, that absence is the actual design problem, and the technique you need is one that manufactures a moment where the whole set can be seen at once.
