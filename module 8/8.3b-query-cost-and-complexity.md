# Query Cost and Complexity

_Module 8.3b — GraphQL APIs_

## The Problem

A music catalogue API. Artists, albums, tracks, and a `featuredArtists` field on tracks, because guest appearances are a thing people search for.

The schema is unremarkable:

```graphql
type Artist  { id: ID!  name: String!  albums(first: Int! = 20): [Album!]! }
type Album   { id: ID!  title: String! tracks(first: Int! = 20): [Track!]! }
type Track   { id: ID!  title: String! featuredArtists: [Artist!]! }
```

Note the cycle: `Artist → Album → Track → Artist`. Nothing wrong with it — it's the honest shape of the domain, and it's the reason anyone chose GraphQL here (8.1a).

Now a fifteen-line query:

```graphql
query {
  artist(id: "1f0e") {
    albums(first: 50) {
      tracks(first: 50) {
        featuredArtists {
          albums(first: 50) {
            tracks(first: 50) { title }
          }
        }
      }
    }
  }
}
```

Count it:

```
  1 artist
 ×50 albums               =         50
 ×50 tracks               =      2,500
 × 3 featured artists     =      7,500
 ×50 albums               =    375,000
 ×50 tracks               =  18,750,000
```

Roughly nineteen million rows, from a request that fits on a screen and contains no repetition, no recursion directive, and nothing a reviewer would flag. The server spends forty seconds and several gigabytes of heap assembling a response nobody will read.

Here is the part that matters, and it's the reason this article follows 8.3a rather than preceding it: **after batching, that query is seven database statements.** Query count is 7. The N+1 dashboard is green. Everything 8.3a taught you to measure says this request is healthy.

Three more shapes of the same problem, because the fix has to cover all four.

**Aliases.** No nesting required:

```graphql
query {
  a1: artist(id: "1f0e") { ...Big }
  a2: artist(id: "1f0e") { ...Big }
  …
  a100: artist(id: "1f0e") { ...Big }
}
```

One HTTP request, a hundred times the work. A rate limiter counting requests per minute records this as one request, which it is.

**Introspection.** `__schema { types { fields { type { fields { type { … } } } } } }` is a legitimate query against a meta-schema that is itself cyclic, it's usually available before authentication, and it's expensive on a large schema.

**Your own frontend.** A developer adds `album { label { artists { name } } }` inside a list inside a list, because it renders one line of text. Nothing errors. p99 climbs 300ms over a week and nobody connects it to that PR.

That last one is the common case. Most GraphQL cost incidents are not attacks — they're first-party clients writing queries whose cost nobody could see. Which is what makes this a performance article that also happens to be a security one.

The underlying change from Module 7 is precise. With REST, **cost was a property of the endpoint.** You profiled `/artists/{id}/albums` once and knew what it did, forever. With GraphQL the space of possible requests is infinite and the client picks from it, so cost is a property of a request you haven't seen yet. You need to be able to say, *before running it*, roughly what a query will cost — and refuse the ones you can't afford.

## What It Is

**Query cost analysis** is walking a query document against the schema before execution, computing a number that estimates the work it will cause, and enforcing a budget against that number.

The family of controls is broader than the scoring:

- **Static structural limits** — maximum depth, maximum aliases, maximum total nodes.
- **Weighted complexity scoring** — a cost per field, multiplied down the tree by list sizes.
- **Cost-denominated rate limiting** — budgets measured in points rather than requests.
- **Runtime backstops** — timeouts with real cancellation, result-size caps, request body limits.

Two disambiguations:

**Cost analysis is not rate limiting**, though they compose. Analysis answers "how expensive is this one query." Rate limiting answers "how much has this client spent lately." Module 18 owns the second mechanism entirely; what changes here is only the unit.

**Cost analysis is not authorization.** A query can be cheap and forbidden, or expensive and entirely permitted. Field-level permissions are 8.4, and the only overlap is that both are things a single `/graphql` endpoint made harder.

## Recognizing the Problem

- Your schema contains a cycle, or any list field whose type contains another list field.
- A list field somewhere takes no pagination argument, or takes an optional one.
- You cannot answer "what is the most expensive query a client could send today?"
- p99 latency for `/graphql` has a long tail and the operation names in the tail change weekly.
- Query count per request is healthy and CPU or heap isn't.
- Your rate limit is requests-per-minute.
- A single request has been observed returning a response measured in megabytes.
- The server accepts an array of operations in one HTTP body and nobody decided that.
- Introspection is enabled and unauthenticated.
- A frontend PR that added one nested field changed your infrastructure bill.

## How It Works

### Cost has three dimensions, and depth is the least important

```
       depth                 multiplicity              field weight

  artist                artist                    title          → free
    albums                albums(first: 50)   ×50  (already loaded)
      tracks                tracks(first: 50) ×50
        featuredArtists       featuredArtists ×3   similarArtists → 1 search
          albums                albums(first:50)×50  query, 80ms
            tracks                tracks(first:50)×50
                                                   ─────────
       6 levels              18,750,000 nodes      not all nodes equal
```

**Depth** is nesting levels. It's trivial to limit, it catches the pathological recursion, and it catches almost nothing else — a depth-3 query can return a million rows. "We added a depth limit" is the most common place teams stop, and it's about 20% of the problem.

**Multiplicity** is the product of list sizes along a path. This is where essentially all the cost lives, and it's the dimension a depth limit doesn't see.

**Field weight** is that not all fields cost the same. `title` off a row you already loaded is free. `similarArtists` backed by a vector search is a network call and 80ms. Treating both as one unit produces a budget that's wrong in both directions.

### The multiplier model

The standard scoring, used in various forms by GitHub, Shopify, and every cost-analysis library:

- Every field has a cost — commonly 1 for object fields, 0 for scalars on an already-loaded parent.
- Every list field has a **multiplier**, taken from its pagination argument.
- A node's cost is `own cost + multiplier × sum(children's costs)`.

Evaluate the opening query bottom-up and you get a number in the millions, against a budget of, say, 1,000. Refused, in under a millisecond, before a single resolver runs.

The model imposes one hard requirement that reshapes your schema:

> **The multiplier has to be knowable statically, so every list field needs a required, bounded pagination argument.**

`albums(first: Int! = 20)` is analyzable. `albums: [Album!]!` is not — the analyzer has to assume either 1 (and the limiter lies) or infinity (and everything is refused). In the opening schema, `featuredArtists` is exactly that field, and it's the one that makes the arithmetic unbounded.

This is why the Relay connections shape (8.1a) keeps turning out to be worth its ceremony, and it's also a reason to adopt it early: adding a required argument to an existing field is a breaking change.

Variables complicate this slightly. `albums(first: $n)` can only be analyzed once `$n` is bound, so analysis runs per request with variables in hand — which means you cannot cache a cost per document hash. Worth knowing before you try.

### Assigning weights without fooling yourself

Two approaches, and you want both.

**Declarative.** A directive on the schema:

```graphql
type Artist {
  similarArtists(first: Int! = 10): [Artist!]! @cost(weight: 20)
}
```

Readable, reviewable, lives next to the field. It drifts from reality the moment the implementation changes, and nothing detects the drift.

**Derived from measurement.** Cost reflects what the field actually does — how many backend calls, whether it touches a search cluster, what its measured p50 is.

The practical advice: start at 1 per object field and 0 for scalars, hand-weight the ten fields you already know are expensive, and then **check your points against measured latency.** Plot cost against duration for a week of real traffic. If they don't correlate, your budget is theatre: it refuses cheap queries and admits expensive ones, and the people it inconveniences will correctly conclude it's arbitrary.

### Estimate to admit, actual to account

Static cost is an upper bound based on what was *requested*. A query asking `first: 100` that matches three albums was cheap. Charging it 100 is defensible for admission control and indefensible as accounting.

Mature implementations run both:

```
  ┌─ parse ─ validate ─┬─ estimated cost  ──► over budget? refuse, 0 resolvers run
  │                    │
  │                    └─ under budget    ──► execute
  │                                             │
  └────────────────────────────────────────────┴─► actual cost (nodes returned,
                                                    calls made) ──► charge bucket,
                                                                    refund difference
```

Shopify's Admin API is the clearest public example: a query is admitted on its requested cost and the leaky bucket is settled against what it actually consumed. The pattern generalizes well — admission control is necessarily pessimistic, accounting should be honest.

### Rate limiting, in the right unit

Requests per minute is meaningless when one request can be nineteen million rows. Module 18's mechanisms are unchanged — token bucket, sliding window, per-key — but the unit becomes cost points:

- GitHub: a points budget per hour, plus a hard cap on nodes requested per query.
- Shopify: a bucket with a restore rate, in cost points per second.

The part that turns this from punishment into a usable API is **telling the client where it stands**, in the response:

```json
{ "data": { … },
  "extensions": {
    "cost": { "requested": 812, "actual": 44, "remaining": 4_913, "budget": 5_000 }
  } }
```

Without that, a developer hitting the limit has no path forward except guessing. With it, the expensive query is visible in their own dev tools the first time they write it, which is where you want the feedback.

### The backstops, which are not optional

Static analysis can be wrong — a weight is stale, a field got slower, a page of 20 rows turned out to join against everything. So:

**An execution timeout that actually cancels.** This is the one people get wrong. A timeout that abandons the response but leaves the database query running has freed a socket and nothing else; under load you accumulate orphaned work until the pool dies. The request's cancellation signal must propagate into every downstream call.

**A result-size or node cap** enforced during execution, so a query that slipped through the estimate still stops.

**Alias and batch limits.** Cap the number of aliases for the same field. And decide explicitly whether your server accepts an array of operations in one body — many do by default, and it's a clean multiplier on every other limit you set.

**Request body size and parser limits**, enforced *before* parsing. A megabyte of `{{{{{{{` is a denial-of-service against the parser, and no validation rule helps because validation runs after parsing.

**Introspection.** Here's a better justification than the usual one. 8.1a called disabling introspection a weak *security* control — the schema leaks anyway, and you lose your tooling. As a *cost* control it's more defensible: introspection queries are recursive over a cyclic meta-schema and can be genuinely expensive. Restrict it to authenticated clients, or bound its depth, and you've made an argument that survives scrutiny.

### Where the checks belong

Order matters, because each stage is cheaper than the one after it:

```
body size limit ─► parse ─► validate (cost rules here) ─► execute (timeout, node cap)
```

Cost analysis is a **validation rule**. It runs on the AST with variables bound, before a single resolver fires, and it returns a well-formed GraphQL error. Implementing it as instrumentation partway through execution means you've already paid for whatever ran.

### First-party clients are a different problem

Rejecting your own frontend at runtime is a bad outcome: the query was legitimate, the user sees a broken screen, and the frontend developer gets an error about points.

For clients you control, the better answer is to move the check left. If every query is registered ahead of time — which is what persisted documents give you (8.3c) — then you know the complete set of queries your clients can send, you can compute their cost at build time, and you can **fail the build** instead of the request. Same analysis, radically better moment.

So the shape most systems land on: build-time budgets for first-party traffic, runtime enforcement for everyone else.

## When It's Appropriate

- **Mandatory before any GraphQL endpoint is reachable by someone you don't employ.** Not "on the roadmap" — before.
- **Whenever the schema has a cycle**, or any list field whose type contains another list field. That's the structural condition that makes unbounded cost possible; without it the ceiling is low by construction.
- **Whenever a field is backed by something expensive** — search, an external API, an aggregate over a large table. Weighted scoring pays for itself with three such fields.
- **When p99 is dominated by queries you didn't write.** The signal that first-party cost visibility is missing.
- **Concretely:** if you can construct a legal query that returns more than ~100,000 nodes, you need this now, whoever your clients are.

## When It's Unnecessary or Overkill

- **A schema with no list-of-list nesting and no cycles.** Flat resources with bounded children have a cost ceiling you can compute once on paper.
- **When only registered documents are accepted.** If arbitrary queries are rejected outright (8.3c), runtime complexity analysis is largely redundant — the set of possible queries is finite and you checked it in CI. This is the case where the two techniques are alternatives rather than layers, and for a purely first-party API the registry is the better buy.
- **Elaborate weighted models before any measurement.** A node cap, a depth limit, required pagination arguments, and a timeout take an afternoon and cover most of the exposure. Points and budgets are the second afternoon, and calibration is forever.
- **Charging points to a single internal client.** You'll spend more time tuning the model than the incidents would have cost. Give that client observability and a build-time budget instead.

## Trade-offs

**Legitimate queries get refused, and the error is cryptic.** A real dashboard that happens to be large hits the budget and a frontend developer sees "query exceeds maximum complexity of 1000." Unless you publish the model, echo cost in `extensions`, and expose it in development, you've built something that reads as arbitrary — and teams route around things that seem arbitrary.

**The cost model becomes part of your compatibility surface.** Re-weighting a field can push queries that worked yesterday over the budget today, which is a breaking change delivered without a schema change. Public APIs publish their cost model for exactly this reason, and are then stuck with it.

**Estimates that correlate poorly with reality are worse than no limit**, because they create confidence. Calibration is ongoing work that nobody is assigned.

**Required pagination arguments constrain schema design**, and retrofitting them onto existing list fields is breaking. This is a decision you want to have made in week one.

**Per-request analysis cost.** Walking the AST with variables bound is small but real, and it can't be cached across requests with the same document. On a high-QPS endpoint, measure it.

**It bounds cost; it doesn't reduce it.** A query inside the budget can still be slow, and a budget generous enough not to annoy anyone is generous enough to hurt. The limits are a ceiling, not an optimization.

**Backstops have their own failure modes.** An aggressive timeout turns a slow query into a failed query plus wasted work. A node cap produces truncated results, and clients need to be told which.

## Alternatives

- **Accept only registered documents** (8.3c). The strongest control available, and it removes the problem rather than managing it — at the cost of an API that third parties can't explore. This is the main fork in the road, and which side you're on is decided by who your clients are.
- **Timeouts and bulkheads only.** Let queries run, kill them at N seconds, and isolate untrusted traffic onto its own connection pool or read replica (Module 5.4) so it can't starve first-party requests. Crude, cheap, and genuinely effective at protecting the *rest* of the system — it just does nothing for the requester or for the wasted work.
- **Per-field quotas** rather than a whole-query model. Simpler to reason about when three fields account for all your expense, and it sidesteps calibration entirely.
- **Schema variants per audience.** Expose a reduced schema to partners — no cycles, no expensive fields. You cannot ask for what you cannot see, and this is the only control on the list that also reduces your support surface.

## How to Achieve It

**1. Cap the cheap things first.** Request body size, a required and bounded `first` on every list field, an execution timeout that propagates cancellation. No model, no calibration, one afternoon.
*Next when:* those are deployed and you haven't broken anything.

**2. Add structural limits as validation rules, in log-only mode.** Depth, alias count, total nodes. Do not enforce yet.
*Next when:* a week of logs exists.

**3. Look at the histogram before choosing a number.** This is the step that gets skipped, and skipping it is why so many limits are either decorative or hostile. Set the threshold above your real p99.9, not at a round number someone liked.
*Next when:* you can name the operations that would have been refused, and you agree with the list.

**4. Enforce — untrusted traffic first.** Public and partner clients get the limit; first-party clients stay in log-only while their queries get fixed.
*Next when:* refusals are rare and explicable.

**5. Weight the expensive fields and calibrate.** Plot cost against measured duration. Adjust until they correlate.
*Next when:* the correlation is good enough that you'd defend a refusal to the person who received it.

**6. Denominate rate limits in cost, and return the budget in `extensions`.** Module 18's bucket, new unit.

**7. For first-party clients, move the check to CI** via a document registry (8.3c), and turn runtime enforcement for them back down to a generous backstop.

## Implementation

TypeScript, because cost analysis belongs in the validation phase and `graphql-js` exposes that phase directly — which makes the "nothing has run yet" property visible in the code rather than asserted about it.

The schema declares its own weights and requires its multipliers:

```graphql
directive @cost(weight: Int! = 1) on FIELD_DEFINITION

type Artist {
  id: ID!
  name: String!                                          # scalar, weight 0
  albums(first: Int! = 20): [Album!]!                    # multiplier: first
  similarArtists(first: Int! = 10): [Artist!]! @cost(weight: 20)
}
```

The walk, which is the whole idea in fifteen lines:

```ts
function costOf(
  selectionSet: SelectionSetNode,
  parentType: GraphQLObjectType,
  vars: Record<string, unknown>,
): number {
  let total = 0;

  for (const field of fieldsOf(selectionSet, parentType)) {
    const def = parentType.getFields()[field.name.value];
    const weight = costDirective(def)?.weight ?? (isLeafType(def.type) ? 0 : 1);

    const multiplier = listMultiplier(def, field, vars);          // ← aside 1
    const children = isCompositeType(namedType(def.type))
      ? costOf(field.selectionSet!, namedType(def.type), vars)
      : 0;

    total += weight + multiplier * children;
  }
  return total;
}
```

Wired as a validation rule, plus the accounting afterwards:

```ts
const costRule = (vars: Record<string, unknown>, budget: number) =>
  (ctx: ValidationContext): ASTVisitor => ({
    OperationDefinition(node) {
      const cost = costOf(node.selectionSet, rootTypeFor(node, ctx), vars);
      ctx.getContext().estimatedCost = cost;
      if (cost > budget) {
        ctx.reportError(new GraphQLError(
          `Query cost ${cost} exceeds the budget of ${budget}. ` +
          `See https://docs.example.com/graphql/cost`,            // ← aside 2
          { nodes: [node], extensions: { code: "QUERY_TOO_COMPLEX", cost, budget } },
        ));
      }
    },
  });
```

```ts
// after execution
const actual = ctx.nodesReturned;                                  // ← aside 3
await limiter.settle(ctx.clientId, ctx.estimatedCost, actual);
result.extensions = {
  cost: { requested: ctx.estimatedCost, actual, remaining: await limiter.remaining(ctx.clientId) },
};
```

**Aside 1 — `listMultiplier` is where the model lives or dies.** It reads the field's pagination argument, resolving it through `vars` if it's a variable. If the argument is absent or optional, there is no honest answer: returning 1 makes the analyzer systematically underestimate exactly the queries that are dangerous, and returning `Infinity` refuses everything. Both are bugs, and the real fix is in the schema — make the argument required and capped. A limiter that silently defaults to 20 is worse than no limiter, because it reports a number that people trust.

**Aside 2 — the error carries a link and the arithmetic.** A refused query is a conversation with a developer who has no visibility into your cost model. `code`, `cost`, and `budget` in extensions let their tooling show it; the link lets them fix it. Omit these and you've built something that reads as capricious, which is how limits get routed around rather than designed for.

**Aside 3 — the estimate and the actual are different numbers on purpose.** The first refused the nineteen-million-row query without touching the database. The second says the admitted query asked for 100 albums and got 3, so charge for 3. Running only the estimate makes you unfairly expensive for sparse data; running only the actual means you learn the cost after paying it.

**Aside 4 — none of this is the timeout.** Everything above is a ceiling on *requested* work. The backstop for work that turns out to be expensive anyway is a cancellation-propagating deadline on the request context, threaded into every database call and HTTP fetch. A deadline that only abandons the response is not a backstop; under load it's a way to accumulate orphaned queries faster than the pool can recover.

## Further Reading

- **GitHub, "Resource limitations"** (GraphQL API docs) — a published, live cost model: node limits per query, a points budget per hour, and the rationale. The clearest thing to read first because you can test it against a real endpoint.
- **Shopify, "GraphQL Admin API rate limits"** — the estimate-then-reconcile pattern in production, including how requested and actual costs settle against a leaky bucket. The best public description of the two-number model.
- **Apollo's demand control documentation** — the `@cost` and `@listSize` directives, and the argument for making list sizes declarable in the schema rather than inferred.
- **`graphql-query-complexity`** (npm) — a small, readable implementation of the multiplier walk; worth reading the source even if you write your own.
- **`graphql-java`'s `MaxQueryComplexityInstrumentation` and `MaxQueryDepthInstrumentation`** — the same controls as configuration, and a useful contrast in where the mechanism sits.
- **OWASP API Security Top 10, API4:2023 — Unrestricted Resource Consumption** — the vendor-neutral framing, useful for the conversation where someone asks why this needs to be done before launch.
- **The GraphQL specification, §5 (Validation)** — what runs before execution and what a validation rule is permitted to do.
- **Module 18** for the rate-limiting mechanisms themselves, which are unchanged here; only the unit differs.

A Java sibling would show something worth seeing: `graphql-java` ships depth and complexity instrumentation in the box, so this becomes three lines of configuration and a `FieldComplexityCalculator`. That's better ergonomics and it hides the part that actually matters — nothing in the configuration prompts you to calibrate the weights, so the default model gets deployed unexamined and refuses queries for reasons no one can reconstruct. Not yet written.

---

The habit worth carrying: any interface where the *caller* chooses how much work the server does needs a unit of account and a budget. That's true of a query language, a report generator, a search API with an unbounded date range, and a webhook that accepts a filter expression. GraphQL just makes it impossible to pretend otherwise, because the arithmetic is right there in the shape of the request.
