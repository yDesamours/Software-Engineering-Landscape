# GraphQL and REST

_Module 8.2 — GraphQL APIs_

## The Problem

A fleet-maintenance platform. Vehicles, service schedules, work orders, parts. Four things consume the API: a web dashboard used by fleet managers, a mobile app used by drivers and technicians, a partner API that dealership systems integrate with, and a nightly data export into customers' warehouses.

Take one small feature and price it in both worlds.

**The feature:** the vehicle list row should also show the next service due date.

**In the REST API.** `GET /fleets/{id}/vehicles` returns a list representation that doesn't include service data. So: a backend ticket to add `nextServiceDueAt` to the list serializer, a decision about whether that's a breaking change (it isn't — it's additive), a deploy, and then the web app renders it. Two days end to end, most of it waiting.

Then the mobile app wants it too. Same field, already deployed. Zero backend work. The mobile team adds it to their model, ships, and waits three weeks for app-store review and staged rollout — during which the field is being returned to every old build that ignores it. Fine.

Then the partner API wants it, and now it's a real decision, because dealership integrations parse responses with code written years ago and some of them break on unknown fields. So the field goes behind a version, or a header, or a query parameter, and there's a migration note in the changelog.

**In a GraphQL API.** The web team adds `nextServiceDueAt` to its fragment and ships. No backend ticket, assuming the field exists in the schema. If it doesn't, it's one resolver and one SDL line — but then it's in the schema for everyone, permanently, and removing it later requires knowing who selected it.

The mobile team does the same, and still waits three weeks for app-store review.

The partner integration does not benefit at all. A dealership's integration engineer wants a stable, documented, cacheable endpoint they can point a scheduled job at. Handing them a query language means handing them the ability to write a query that costs you forty seconds of database time, on a schedule, forever.

And the nightly export benefits negatively. It wants every field of every vehicle in bulk, which is the one access pattern where "ask for exactly what you need" describes a problem rather than a solution.

Look at what actually differed. It wasn't effort — both versions were a few hours of work. It was **who had to be involved**, and that answer was different for each of the four consumers. The web app and the mobile app wanted the server to stop being in the loop. The partner API and the export wanted the server to stay in the loop, because a fixed, known response is exactly what makes them cheap to run and safe to depend on.

Which means "should we use GraphQL or REST" has no answer at the company level. It has four answers.

## What It Is

Underneath every difference between the two is one bet, and it's worth stating as a single sentence:

> **REST bets that the shape of a response is knowable before the request is made. GraphQL bets that it isn't.**

That's it. Everything else — caching, cost control, authorization, monitoring, versioning, error handling, tooling — is a consequence that falls out of which side of that bet you took.

```
        is the response shape knowable in advance?

 REST — yes                            GraphQL — no
   │                                     │
   ├─ a URL identifies bytes             ├─ one POST, body varies
   │    └─► CDN, ETag, browser cache     │    └─► normalized client cache,
   │                                     │        persisted queries
   ├─ cost is a property of the route    ├─ cost is a property of the query
   │    └─► rate limit by request count  │    └─► complexity budgets (8.3b)
   │                                     │
   ├─ one route per operation            ├─ any type reachable by many paths
   │    └─► authorize at the route       │    └─► authorize at the field (8.4)
   │                                     │
   ├─ metrics key on URL                 ├─ every request is /graphql
   │    └─► works by default             │    └─► per-operation instrumentation
   │                                     │
   └─ the server owns the shape          └─ the client owns the shape
        └─► change = deploy, /v2              └─► change = free; removal = forever
```

Read the left column as a set of things you get without asking, and the right column as a set of things you must build. Read it in the other direction and the left column is a set of decisions you must take on behalf of clients who will disagree with them, and the right column is a set of decisions you never have to take.

Neither column is better. They're the two halves of one trade.

Two clarifications, because the argument is usually conducted in a fog:

**This is not a comparison of technologies, it's a comparison of coupling.** A REST API with sparse fieldsets, `include=` expansion, ETags, cursor pagination, and RFC 9457 problem details is not "simpler" than GraphQL. It's the same total complexity, relocated: distributed across conventions the server chose rather than concentrated in a schema and an executor. Module 7.4b's warning — that a field-selection DSL grows toward a worse GraphQL — is the same observation from the other end.

**"When should I use GraphQL?" was 8.1a's question, and it's not this one.** This article is about the comparison itself and about running both, which is what most systems of any size end up doing.

## Recognizing the Problem

You may have chosen wrong in the GraphQL direction if:

- Your schema has one client and that client ships from the same repository as the server.
- Most of your traffic is anonymous and identical across users, and your cache hit rate is zero because it's all POSTs.
- The most common query is the same query, every time, from a job.
- You have no complexity limit and no per-field authorization, and the endpoint is public.
- Nobody owns the schema, and it only grows.

You may have chosen wrong in the REST direction if:

- You have a `/mobile/` prefix, or a `/v3/` that exists because one client couldn't update.
- Adding a field to a screen means a cross-team ticket, and that ticket type is the most common one you file.
- Your list endpoint returns forty fields and your busiest client uses four.
- A screen's load is a four-deep dependent waterfall.
- Different clients want the same entity in shapes you can't reconcile, so you maintain serializers per client.

And in either direction: if you're arguing about performance, or about which one "has types," you're arguing about something that doesn't decide this.

## How It Works

### The arguments that don't decide anything

Clearing these out first makes the real decision short.

**"GraphQL is faster."** Not intrinsically. Both hit the same database with the same queries; a GraphQL server usually issues *more* of them unless batching is engineered in (8.3a). The genuine wins are round trips and bytes — and a purpose-built REST endpoint for a specific screen matches both exactly. What GraphQL removes is not latency, it's the backend ticket required to create that purpose-built endpoint.

**"REST over-fetches."** Less than the pitch suggests. Module 7.4b took this apart: gzip collapses repetitive JSON by roughly 85%, so the wire cost mostly evaporates. What survives is server-side serialization work and client-side parse cost on low-end devices — real, worth fixing, and much smaller than the "1.4MB response" framing implies.

**"GraphQL gives you types."** So does an OpenAPI document with codegen. Generated clients, editor completion, and CI contract checks are available in both worlds, and a team that won't maintain an OpenAPI spec will not maintain a GraphQL schema either. What GraphQL adds is that the schema is *executable* — it can't drift from the implementation, because it is the implementation's interface. That's a real difference, and it's narrower than "types."

**"GraphQL means one request."** Only when the data lives in one graph. A GraphQL gateway over six services makes six internal calls, exactly as a hand-written BFF endpoint would. You moved the fan-out inside your perimeter, which is usually worth a lot — but it's aggregation, not elimination.

**"You lose HTTP caching."** True, and worth less than it sounds for most SaaS. Module 7.4a's arithmetic applies: if responses are per-user, they're `Cache-Control: private` already, and no CDN was ever going to serve them. This argument is decisive for anonymous, high-volume, identical content — a public catalogue, documentation, a marketing site's data — and close to irrelevant for an authenticated dashboard.

### What actually decides it

Six facts. Most teams can answer all six in ten minutes, and usually two of them are decisive.

**1. Do you control when your clients deploy?** The single strongest predictor. A web app you deploy yourself has no release coupling problem worth solving. A mobile app with a long tail of old installs, or a partner integration you have no authority over, has the problem permanently. GraphQL's core benefit is denominated in this one fact.

**2. Who is the consumer — a UI, or a program?** UIs have screens, screens have wildly different data needs, and those needs change weekly. Programs have one stable need and want it to never change. Field selection is worth a great deal to the first and roughly nothing to the second.

**3. Are frontend and backend the same people?** If yes, the coupling GraphQL removes is coupling you can break for free every Tuesday, and you're buying a schema, an executor, a batching layer, and a governance process to solve a problem you resolve in Slack. If they're different teams with different backlogs, that coupling *is* your cycle time.

**4. Is your data relational with several entry points?** Vehicles → work orders → parts → suppliers → vehicles, entered from four different screens. That's a graph and it wants a graph. A flat resource with no traversals gives a query language nothing to express.

**5. Is public cacheability load-bearing?** Anonymous, high-traffic, identical-for-everyone responses are the case where the left column's free CDN is worth more than anything in the right column.

**6. Do you have the headcount for the things that become mandatory?** Cost limits, field-level authorization, per-operation telemetry, schema review, and field-usage tracking are not optional extras once a GraphQL endpoint is exposed to anyone you don't employ. That's an ongoing commitment, not a setup task.

Notice there's no scoring matrix here, for the reason Module 1.3 gave: a weighted matrix is how a strong score in an irrelevant column outvotes a hard requirement. These are disqualifiers and enablers, not points.

### The third option people forget

The choice isn't binary. For internal service-to-service traffic, the default answer is usually neither — it's **gRPC**, or another schema-first RPC. Both of the options in this article's title are shaped by the needs of *external* consumers over an untrusted network with heterogeneous clients. Two of your own services, in your own network, deployed by your own CI, have none of those constraints, and they want the thing that's fastest to define and cheapest to call.

Putting GraphQL between two backend services is a common and expensive mistake: you take on the executor, the N+1 risk, and the cost analysis in exchange for flexibility that the caller — which you also own and deploy — did not need.

### Running both

Most systems that adopt GraphQL do not remove REST, and the plan to "migrate fully" should be treated as aspirational from the start. Some things will be HTTP endpoints for the life of the system:

- **File upload and download.** Multipart specifications for GraphQL exist and are uniformly unpleasant; signed URLs to object storage (Module 11) work today.
- **Webhooks you receive.** Somebody else's server is the client, and it speaks HTTP.
- **OAuth callbacks, health checks, and anything an ops tool curls.**
- **Bulk export.** "Ask for exactly what you need" is the wrong instruction for "all of it."
- **Server-rendered HTML,** if you do any.
- **Machine-facing partner APIs,** for the reasons in the opening.

Which leaves the interesting question: how do two APIs over the same domain avoid becoming two different systems?

One rule does most of the work:

> **Two transports, one everything else.** One domain service layer, one authorization implementation, one error taxonomy, one set of domain events.

If the GraphQL resolvers and the REST controllers each enforce permissions independently, you have two security models and one of them is wrong — and you will find out which the way people usually do. The same applies to validation, to tenant scoping (Module 5.2), and to event emission: any rule that lives in a transport layer is a rule that exists in one of the two APIs.

The two transports should be thin. A resolver and a controller both do the same three things: translate an input into a command, call the service, translate the result outward. Everything else belongs underneath both.

Three coexistence patterns are worth naming:

**Reads in GraphQL, writes in REST.** Common, defensible, and it keeps status codes, `Idempotency-Key`, and `If-Match` doing their jobs (8.1b spent a section rebuilding all three as schema fields). The cost is that the client cache has no idea a write happened, so you're back to manual refetching — which was one of the problems GraphQL was adopted to remove. Good transitional state, unsatisfying destination.

**GraphQL as a BFF over REST services.** The Level 0 path from 8.1a, kept permanently. Internal services stay REST or gRPC; one GraphQL layer faces UIs. This is the most common shape in large systems, and it's the one where the internal/external boundary lands somewhere sensible.

**Both public, for different audiences.** GitHub does this: REST v3 and GraphQL v4, both public, both supported, neither deprecated. Not duplication for its own sake — an integration that reads one repository's metadata on a schedule wants the REST endpoint, and a dashboard that assembles issues, reviews, and check runs wants the graph. Two audiences, two answers, one domain.

## When It's Appropriate

This decision is worth genuinely deliberating when:

- **A second or third client surface is arriving**, on a release cadence you don't control. This is the moment the answer changes, and it's the cheapest moment to act on it.
- **You're about to build a BFF layer.** GraphQL is a generic version of the thing you were going to hand-write, so it's net-neutral rather than net-new complexity — the best possible circumstances for adopting it.
- **You're standing up a new consumer-facing surface** over an existing domain, and the existing API stays put regardless. Additive decisions are reversible; replacements aren't.
- **Your `include=`/`fields=` parameter has grown a grammar** (7.4b). You're paying GraphQL's costs already without any of its tooling.
- **Different consumers have visibly divergent needs** — a UI and a partner integration and an export, as in the opening. Then the answer is "both," and the work is deciding where the seam goes.

## When It's Unnecessary or Overkill

- **Greenfield, one client, one team.** The answer is whatever that team already knows. Both options work; only one of them requires a decision meeting.
- **A working API and no new consumer.** Migrating a healthy REST API to GraphQL with the same single frontend is a large project whose deliverable is a different set of problems. The strongest signal that this is happening is that the justification is phrased in adjectives.
- **Internal service-to-service.** See gRPC above.
- **When the six facts already decide it.** If your only consumers are scheduled jobs and dealership integrations, there is nothing to deliberate. Most of the long meetings about this happen in rooms where the answer was already determined by facts nobody had put on the table.
- **Relitigating.** If both exist and both work, the pressure to unify is usually aesthetic. Unify the layer *underneath* them instead; that's where duplication actually costs you.

## Trade-offs

The costs of each style individually are in 8.1a and Module 7. What running both costs, specifically:

**Two surfaces to secure, and the weaker one sets your security posture.** The rule above exists because this is the most common serious failure — a field exposed in GraphQL that the REST serializer had been carefully omitting for two years.

**Two error formats, permanently.** RFC 9457 problem details on one side, payload errors and the `errors` array on the other (8.1b). Clients that touch both must handle both. The mitigation is to keep one internal taxonomy and map it twice, but the clients still see two shapes.

**Documentation divides.** Introspection documents the schema; OpenAPI documents the endpoints; nothing documents which one you should be using for what. Somebody has to write that page, and it's the page nobody owns.

**The migration never finishes**, and half-migrated is a real steady state with real costs — two auth paths, two rate limiters, two sets of dashboards. Plan for it as a permanent architecture rather than a phase, and it's fine. Plan for it as a phase and you'll under-invest in the half you intended to delete.

**Domain logic drifts upward.** Every deadline produces one small rule implemented in a resolver or a controller because it was faster. Each is invisible; collectively they're how the two APIs stop agreeing.

## Alternatives

- **gRPC / Connect** for internal traffic, as above. Schema-first, codegen on both ends, streaming, and far cheaper per call than either option here.
- **tRPC** in a TypeScript monorepo — end-to-end types with no schema artifact at all, which is superb when client and server ship together and worthless when they don't.
- **OpenAPI plus codegen** as the "typed REST" position. It answers the tooling argument entirely and none of the coupling argument.
- **JSON:API** — a full specification covering sparse fieldsets, includes, pagination, and errors. If the reason GraphQL is being proposed is "our field-selection parameter is a mess," this is the smaller answer to that specific problem.
- **Server-driven UI**, where the server returns a description of the screen rather than data. The extreme of the left column — the server owns everything, including layout — and it solves the release-coupling problem more completely than GraphQL does, at the cost of a client that's a rendering engine for your private format.

## How to Achieve It

8.1a gave the adoption levels. What's specific to coexistence is the order in which you make the two sides share a spine — and it's worth doing *before* the second transport exists, because it's much harder afterward.

**1. Extract the domain service layer first.** If controllers currently contain business logic, no amount of care at the GraphQL layer will keep the two consistent. This is the prerequisite, and it's valuable even if GraphQL never happens.
*Ready when:* a controller method is three lines — translate, call, translate.

**2. Move authorization below the transport.** Permission checks live in or beside the service, keyed on the operation and the actor, not on the route.
*Ready when:* you can answer "who may reject a work order?" by reading one module.

**3. Define one internal error taxonomy, mapped twice.** A domain refusal becomes a `409` with a problem-details body on one side and a typed payload member on the other, from one source.
*Ready when:* adding a new failure case requires touching one enum and two mappers.

**4. Add the GraphQL transport** over exactly that service layer, for one screen.

**5. Draw and write down the seam.** Which consumers use which, and why. This document is what prevents the partner integration from being pointed at `/graphql` by someone who wasn't in the original discussion.
*Revisit when:* a new consumer type appears — that's the only event that should reopen the decision.

## Implementation

Java with Spring, because the article's central practical claim — one core, two thin transports — is one the framework can enforce rather than merely encourage.

The service is the only place with rules:

```java
@Service
public class WorkOrderService {

  @PreAuthorize("hasPermission(#id, 'WorkOrder', 'close')")   // ← aside 1
  @Transactional
  public WorkOrder close(UUID id, CloseReason reason, Actor actor) {
    var order = repo.findForUpdate(id)
        .orElseThrow(() -> new NotFound("WorkOrder", id));
    if (order.hasOpenParts())
      throw new DomainRefusal(Code.PARTS_OUTSTANDING, order);   // ← aside 2
    order.close(reason, actor);
    events.record("work_order.closed", order, actor);
    return order;
  }
}
```

Both transports are translation and nothing else:

```java
@RestController
class WorkOrderController {
  @PostMapping("/work-orders/{id}/close")
  ResponseEntity<WorkOrderView> close(@PathVariable UUID id,
                                      @RequestBody CloseRequest body) {
    return ResponseEntity.ok(WorkOrderView.of(
        service.close(id, body.reason(), Actor.current())));
  }
}

@Controller
class WorkOrderGraphQlController {
  @MutationMapping
  CloseWorkOrderResult closeWorkOrder(@Argument CloseWorkOrderInput input) {
    return CloseWorkOrderResult.success(
        service.close(input.workOrderId(), input.reason(), Actor.current()));
  }
}
```

And the one taxonomy is mapped twice, in two adapters that are the only place either protocol's vocabulary appears:

```java
@RestControllerAdvice
class RestErrors {
  @ExceptionHandler(DomainRefusal.class)
  ProblemDetail handle(DomainRefusal e) {            // RFC 9457 — see 7.3b
    var p = ProblemDetail.forStatus(HttpStatus.CONFLICT);
    p.setType(URI.create("https://errors.example.com/" + e.code()));
    p.setProperty("code", e.code().name());
    return p;
  }
}

@ControllerAdvice
class GraphQlErrors {
  // same DomainRefusal → a typed member of the mutation's result union  ← aside 3
}
```

**Aside 1 — the annotation is on the service, and that placement is the entire point.** Put `@PreAuthorize` on the controller and the GraphQL path is unguarded; put it on both and you have two policies that will diverge within a year. On the service, both transports inherit it and neither can forget. The cost, noted honestly: authorization is now invisible at the call site, which makes it harder for a reviewer reading a resolver to see that a check is happening at all. That's the trade the Java sibling note in 8.1b predicted.

**Aside 2 — `DomainRefusal` is not an HTTP concept and not a GraphQL concept.** It carries a code from one enum and the entity involved. If this class imported anything from either protocol, the taxonomy would have a preferred transport, and the other one would get the lossy translation.

**Aside 3 — the two mappings are deliberately not symmetric.** REST reports a refusal as `409` with a problem body. GraphQL reports it as `200 OK` with a typed union member, because in that world a refusal is a successful execution (8.1b). Same event, two vocabularies — which is exactly why the taxonomy has to live below both, and also why "we'll just proxy one to the other" produces an API that reads like a translation, because it is one.

## Further Reading

- **GitHub's "The GitHub GraphQL API" (2016)** and their current API documentation side by side — the clearest public example of running both deliberately, with a stated rationale for each.
- **Netflix Technology Blog, "How Netflix Scales its API with GraphQL Federation" (2020)** — a large system's account of the BFF-to-graph path, including what it cost.
- **Phil Sturgeon, "GraphQL vs REST" series** — the most useful skeptical treatment; the caching instalment in particular is a corrective to the enthusiastic version of that argument.
- **Matt Bessey, "Why, after 6 years, I'm over GraphQL" (2024)** — a considered retrospective from someone who shipped it; worth reading precisely because most of its complaints are about authorization and cost control rather than about the query language.
- **RFC 9111, _HTTP Caching_** — what you're actually giving up, in specific terms rather than in adjectives.
- **The OpenAPI Specification** plus any generator — the concrete form of the "typed REST" counterargument.
- **gRPC documentation**, and the Connect protocol as its browser-friendly variant — the third option, for the traffic that is neither of the two in this title.
- **Marc-André Giroux, _Production Ready GraphQL_**, on public GraphQL APIs — the chapter that makes clear how much infrastructure "just expose the schema" implies.

A TypeScript or Go sibling would show something this one hides. Without annotations and an AOP container, the shared-core arrangement has to be wired by hand — every resolver and every handler explicitly calling the same authorization function — which is more code and no framework guarantee, but it also puts the check back where a reviewer can see it. Whether uniformity or visibility matters more is a real argument, and the Java version only shows one side of it. Not yet written.

---

The habit worth carrying: when someone proposes an API style, ask what happens the first time a client needs a field that isn't there. Who files the ticket, who deploys, how long until the user sees it, and what breaks for everyone else. The answer to that question is the decision — the style is just the name of the answer.
