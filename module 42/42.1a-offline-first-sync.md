# Offline-First Sync: Cursors That Don't Skip, Pushes That Apply Once, Scopes That Shrink

_Module 42 · Mobile Backend Development · 42.1a_

## The Problem

Suppose you run maintenance software for elevator companies. Technicians spend their days in machine rooms and basements, often without signal, working through task lists: inspect, repair, record parts, write notes. The mobile app has to work offline, so it keeps a local database and syncs with the server when it can.

The first sync design is the obvious one:

- **Pull:** `GET /tasks?updatedSince=<timestamp>`, where the app remembers the time of its last sync.
- **Push:** for each task edited offline, `PUT /tasks/:id` with the whole task.
- **Delete:** `DELETE /tasks/:id`.

Over two months, support collects these tickets.

**Changes that never arrive.** A dispatcher reassigns a task at 10:14:03. A technician's phone syncs at 10:14:05 and never receives the change. Hours later, the task is still on the wrong person's phone. It happens a few times a week, never reproducibly.

**Duplicate work orders.** A technician creates a task offline ("found a worn cable"). The phone reconnects in a lift shaft, the create reaches the server, and the response is lost. The app retries, and the server creates a second task. Parts get ordered twice.

**Deleted tasks that come back.** A dispatcher deletes a duplicate. The row is gone, so no `updatedSince` query ever returns it, and every phone that had it keeps it.

**Notes that disappear.** A technician offline since 8 a.m. edits a task's notes. Meanwhile, the dispatcher changed the task's status on the web. At 2 p.m. the phone pushes the whole task, with its morning copy of the status, and the dispatcher's change is overwritten. Another day, the reverse: the server keeps "the last write," judged by the phone's clock. One phone's clock is set to 2027, so it wins everything.

**Tasks that stay on the wrong phones.** A task moves from one crew's building to another's. The first crew's phones never learn it moved, because the pull only returns tasks in projects they belong to, and the task isn't in one any more. They keep an outdated copy indefinitely. And a technician who left the company still had every customer's building access codes on a personal phone.

Each ticket is a different consequence of the same fact: **the device and the server are two copies of the same data, updated independently, over a network that loses messages.** Keeping them in agreement needs a protocol, not a pair of REST endpoints.

## What It Is

**Offline-first** means the app reads and writes a **local database** all the time, and a background **sync engine** exchanges changes with the server whenever it can. The UI never waits for the network. The server remains the **source of truth**: the device holds a copy plus a queue of changes it would like to make, and the server decides whether each change is allowed and how it merges.

A **sync protocol** has two directions:

- **Pull:** "What has changed since I last asked?" The device keeps a **cursor**, a position in the server's history of changes.
- **Push:** "Apply my queued changes, each exactly once." The device sends **mutations**, each with its own ID.

Offline support is a spectrum, and you choose per feature, not per app:

| Level | Behavior | Example |
|---|---|---|
| Online only | Error without network | Payments, admin actions, anything involving other tenants |
| Cached reads | Shows last loaded data, marked possibly stale | Reports, dashboards |
| Offline reads | Chosen data downloaded ahead and fully readable | Manuals, building details |
| Queued writes | Creates and edits offline, sent later | Comments, time entries |
| **Offline-first** | Local database always; background sync | Task lists in the field (this article) |
| Local-first, CRDTs | Devices merge with each other, even without a server | Collaborative documents (Module 9) |

This article covers the offline-first level for structured records. **Conflict resolution** in general (clocks, version vectors, merge policies) is 38.1b, and collaborative text is covered with CRDTs and operational transforms in Module 9. Here, conflicts come up only as far as a sync protocol needs them.

## Recognizing the Problem

- Sync uses timestamps or database sequences as the cursor.
- Changes occasionally never reach some devices, with no error anywhere.
- Retried requests create duplicate records.
- Deleted records reappear, or never disappear from devices.
- Devices push whole records, and fields changed by others get overwritten.
- Conflicts are resolved by comparing device timestamps.
- Records that move to another team or project stay on the old team's devices.
- Users removed from a project, or from the company, keep its data on their phones.
- Temporary client IDs have to be remapped after the server assigns real ones.

## How It Works

### 1. The shape

```
┌────────────────────────── DEVICE ──────────────────────────┐
│ UI ─reads/writes─► local DB ─every write also appends to─► │
│                                pending mutations (a local  │
│                                outbox)                     │
│ sync engine: 1. push pending mutations, in order           │
│              2. pull changes since cursor, page by page    │
│              3. apply scope changes (joined, left, moved)  │
└───────────────────────────┬────────────────────────────────┘
                            │
┌───────────────────────────▼────────────────────────────────┐
│ SERVER  POST /sync/push   validate, authorize, merge, once  │
│         GET  /sync/pull   changes with version > cursor     │
│         GET  /sync/bootstrap?project=…  full current state  │
│         per-tenant version counter · field versions ·       │
│         tombstones · scope-exit log                         │
└─────────────────────────────────────────────────────────────┘
```

**Push first, then pull.** If the device pulled first, it could overwrite a local edit with an older server value just before sending that edit.

### 2. Pull, and the commit-order trap

Every write gives the row a new, higher **version**. The device asks for rows with `version > cursor`, in version order, and stores the new cursor. That's correct only if versions **become visible in order**. Timestamps and database sequences don't:

```
Transaction A:  gets version 101 ─── (slow) ─────────────────────── COMMIT
Transaction B:          gets version 102 ── COMMIT
Device pull:                                 sees 102, cursor = 102
                                                             version 101 becomes visible now…
Next pull:                                                              cursor 102 → never sees 101
```

A sequence hands out numbers in the order transactions **start**; they **commit** in any order. A device can read 102 before 101 is visible, move past it, and never receive it. That's the elevator company's missing reassignment: no error, no log, just a change that never arrives.

The fix used here is a **per-tenant version counter**: one row per tenant, incremented with `UPDATE … RETURNING` inside the writing transaction. That update **locks the tenant's row until the transaction ends**, so the next writer in the same tenant waits, and versions within a tenant commit in order. The options:

| Approach | Correct? | Cost |
|---|---|---|
| Timestamps, global sequences | No: commit-order trap (timestamps also have precision and clock problems) | — |
| **Per-tenant counter row** | Yes | Writes within one tenant are serialized. Keep those transactions short, and measure for your largest tenants |
| Transaction snapshots (`pg_current_snapshot()`) | Yes | Harder to implement correctly; no write serialization |
| Logical replication / change data capture (38.4a) | Yes | What sync engines such as PowerSync and Electric use; the most infrastructure |

Three more rules make pull complete:

- **Deletes are rows too.** A deleted row can't be returned if it doesn't exist. Deletes are soft: `deleted_at` is set (a **tombstone**) and syncs like any other change.
- **Pages.** A phone offline for a month may have thousands of changes. Return pages, and let the device keep pulling while `hasMore` is true, saving its cursor after each page.
- **Tombstones are eventually purged,** after 30 days or more. A device whose cursor is older than the purge gets `resetRequired` and downloads everything again.

### 3. Push: mutations applied once

```json
{ "mutationId": "6f1c2a0e-…", "op": "upsert", "id": "0b7a4c1e-…",
  "baseVersion": 1840, "fields": { "notes": "Replaced the seal" } }
```

- **`mutationId`** is a UUID created on the device when the user acted. The server records processed mutation IDs and returns the stored result for a repeat. The lost response in the lift shaft becomes a harmless retry (the same idempotency pattern as 37.2a's inbox).
- **`id`** is also created on the device, so new records have their real ID before the server sees them. No temporary IDs to remap.
- **`baseVersion`** is the version the device had when the user made the edit.
- **`fields`** contains only what the user changed, never the whole record. That's what makes field-level merging possible.

The server authorizes every mutation itself: tenant and user come from the access token, never from the body, and the allowed fields come from a server-side list.

### 4. Conflicts: server versions, per field

Device clocks can't order edits (38.1b explains why at length; the 2027 phone shows it in one line). The server does know the order in which it accepted changes, and `baseVersion` tells it what the device had seen.

Each row keeps `field_versions`: for every field, the version at which it last changed, maintained by a database trigger, so every write path keeps it correct. A pushed field is accepted if the server hasn't changed **that field** since `baseVersion`; otherwise the server's value stays and the field is reported as a conflict:

```
server row v1904: status "in_progress" (changed at 1901), notes "" (changed at 1800)
device, base 1840: status "done", notes "Replaced the seal"
→ status: 1901 > 1840 → conflict, server value kept
→ notes:  1800 ≤ 1840 → applied
```

The technician's notes survive, and the dispatcher's status isn't silently overwritten. Fields that must change together (street, city, postal code) are merged as a **group**: if any conflicts, none are applied. Deletes follow the same logic: a delete whose base is older than the row's latest version is rejected and the current row returned, since deleting someone's fresh work unseen is worse than asking again.

Field-level, server-ordered merging suits most business records. Where the domain allows it, merge by meaning (add to sets, keep the more advanced status); for free text edited concurrently, CRDTs (Module 9).

### 5. Scope: what each user may see, and when that changes

Users don't sync the whole tenant, only projects they're members of. Scope changes three ways, and each needs handling:

- **Joined a project.** Its tasks have versions older than the cursor, so a normal pull won't return them. The pull reports `addedProjects`, and the device downloads each with `/sync/bootstrap`.
- **Left a project.** The pull reports `removedProjects`, and the device deletes that project's data. For this to work, membership rows are versioned and soft-deleted too. This is also how access revocation reaches devices.
- **A record moved out of a project the user can see.** This is the case the elevator company missed. The task's new version is in a project the technician isn't a member of, so the pull's membership filter hides it, and the old copy stays forever. The fix is a **scope-exit log**: when a task's project changes, the trigger records the task, its **old** project and the new version. A pull also returns `removedTasks`: exits in the cursor's range from projects the user can see, unless the task is also visible in its new place.

### 6. Starting and restarting

A new device, or one told to reset, doesn't pull history from version 0. It bootstraps each project's **current state**, which includes the version it's current as of, then tails changes from there. For very large tenants, bootstrap from a snapshot file rather than paged queries.

## When It's Appropriate

- **Users who work without reliable connectivity** and must not lose work: field service, inspections, logistics, healthcare visits, sales on the road.
- **Structured records** edited by a few people, where field-level rules resolve most conflicts.
- **Apps where instant UI matters**, even with a connection, since reads and writes hit the local database.
- **Scoped data**: each user needs a bounded subset (their projects, routes or accounts).

## When It's Unnecessary or Overkill

- **Features that must be online anyway:** payments, approvals with legal weight, anything checked against other tenants or live inventory.
- **Read-mostly apps.** Cached reads with ETags (42.1b) are far simpler.
- **Collaborative text**, where field-level merging is the wrong granularity (CRDTs, Module 9).
- **Apps with reliable connectivity** and a queue of a few writes. Idempotency keys on ordinary requests (42.3a) may be enough.

## Trade-offs

- **The per-tenant counter serializes writes within a tenant.** Any slow work inside those transactions delays every other writer in the tenant. Keep HTTP calls and heavy computation out of them.
- **Tombstones and scope-exit logs grow** and need purging, with a reset path for devices that fall behind.
- **Every write path must go through the triggers.** Bulk loads that bypass them (copying data in with triggers disabled) break sync silently.
- **Field-level merging can split intent**: a device's status change rejected while its notes are accepted may leave a record that neither person intended. Groups and user-visible conflict notices reduce this.
- **The server does more work per write**: versions, field versions, exit logs, processed-mutation records.
- **Schema changes to synced entities** affect every installed app version (42.3a).
- **Data lives on devices you don't control** (42.1b covers protecting it).

## Alternatives

- **Sync engines.** PowerSync (streams Postgres changes into SQLite on the device, sends writes through your API), ElectricSQL (streams subsets of Postgres, writes through your API), Couchbase Mobile (its own database and sync on both sides), Firebase Firestore (offline persistence in its SDKs, as part of a BaaS decision, 42.4a). The Postgres-based engines take over the hard read side and still send writes through your backend, where validation and authorization stay.
- **Queued writes without full sync:** the app stores a few actions offline and replays them with idempotency keys. Enough when offline reads aren't needed.
- **CRDT-based local-first stores** (Automerge, Yjs) for documents and whiteboards.
- **Managed device-sync products have disappeared before**: MongoDB ended Atlas Device Sync (formerly Realm) in September 2025, and its users had to rebuild their sync layers. Whatever you choose, write the exit plan down.

## How to Achieve It

**Step 1: choose the offline level per feature.** Most features need cached reads at most. _Signal to move on:_ one or two features truly need offline writes.

**Step 2: idempotent push with device IDs** for those features: mutation IDs, device-generated record IDs, changed fields only, and server-side authorization. _Signal:_ devices also need to read other people's changes offline.

**Step 3: versioned pull**: the per-tenant counter, tombstones, pages, reset, and field-level merge with base versions. Test the commit-order case explicitly. _Signal:_ membership and ownership change while devices are offline.

**Step 4: scope handling**: versioned memberships, bootstrap, and the scope-exit log. Then decide, with the build-or-buy table above, whether to keep owning this or move to a sync engine.

## Implementation

TypeScript for the service, with the SQL it depends on. The code was run against PostgreSQL 16 and passes the scenarios listed at the end.

The database does the ordering, the field tracking and the exit log, so no write path can forget them:

```sql
-- One counter per tenant; the row lock is held until the writing transaction ends.
CREATE FUNCTION next_sync_version(t text) RETURNS bigint LANGUAGE sql AS $$
  INSERT INTO tenant_sync_state AS s (tenant_id, version) VALUES (t, 1)
  ON CONFLICT (tenant_id) DO UPDATE SET version = s.version + 1
  RETURNING s.version $$;

CREATE TABLE task_scope_exits (tenant_id text, task_id uuid, old_project_id uuid, version bigint,
                               PRIMARY KEY (tenant_id, task_id, version));

CREATE FUNCTION tasks_versions() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE f text;
BEGIN
  NEW.version := next_sync_version(NEW.tenant_id);
  NEW.field_versions := CASE WHEN TG_OP = 'INSERT' THEN '{}'::jsonb ELSE OLD.field_versions END;
  FOREACH f IN ARRAY ARRAY['project_id','title','status','notes','deleted_at'] LOOP
    IF TG_OP = 'INSERT' OR to_jsonb(NEW) -> f IS DISTINCT FROM to_jsonb(OLD) -> f THEN
      NEW.field_versions := NEW.field_versions || jsonb_build_object(f, NEW.version);
    END IF;
  END LOOP;
  IF TG_OP = 'UPDATE' AND NEW.project_id <> OLD.project_id THEN   -- left a project's scope
    INSERT INTO task_scope_exits VALUES (NEW.tenant_id, NEW.id, OLD.project_id, NEW.version);
  END IF;
  RETURN NEW;
END $$;
CREATE TRIGGER tasks_versions BEFORE INSERT OR UPDATE ON tasks FOR EACH ROW EXECUTE FUNCTION tasks_versions();
-- project_members gets a similar trigger that only sets its version.
```

The pull reads everything from one snapshot, so the head, the changes, the exits and the memberships agree:

```ts
import pg from "pg";

export async function pull(pool: pg.Pool, q: { tenantId: string; userId: string; cursor: number; limit?: number }) {
  const limit = Math.min(q.limit ?? 500, 500);
  const c = await pool.connect();
  try {
    await c.query("BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY");
    const { rows: [s] } = await c.query(
      "SELECT version, min_valid_version FROM tenant_sync_state WHERE tenant_id = $1", [q.tenantId]);
    if (q.cursor > 0 && q.cursor < Number(s?.min_valid_version ?? 0)) return { resetRequired: true as const };
    const head = Number(s?.version ?? 0);

    const { rows } = await c.query(                       // tasks in projects the user belongs to now
      `SELECT t.* FROM tasks t
         JOIN project_members m ON m.tenant_id = t.tenant_id AND m.project_id = t.project_id
                               AND m.user_id = $2 AND m.removed_at IS NULL
        WHERE t.tenant_id = $1 AND t.version > $3 ORDER BY t.version LIMIT $4`,
      [q.tenantId, q.userId, q.cursor, limit + 1]);
    const hasMore = rows.length > limit;
    const page = rows.slice(0, limit);
    const upTo = hasMore ? Number(page[page.length - 1].version) : head;   // this page covers (cursor, upTo]

    const { rows: exits } = await c.query(                // tasks that left a project the user can see
      `SELECT DISTINCT e.task_id FROM task_scope_exits e
         JOIN project_members m ON m.tenant_id = e.tenant_id AND m.project_id = e.old_project_id
                               AND m.user_id = $2 AND m.removed_at IS NULL
        WHERE e.tenant_id = $1 AND e.version > $3 AND e.version <= $4`,
      [q.tenantId, q.userId, q.cursor, upTo]);

    const { rows: membership } = await c.query(          // projects joined or left
      `SELECT project_id, removed_at FROM project_members
        WHERE tenant_id = $1 AND user_id = $2 AND version > $3 AND version <= $4`,
      [q.tenantId, q.userId, q.cursor, upTo]);
    await c.query("COMMIT");

    const visible = new Set(page.map((r) => r.id));
    return {
      cursor: Math.max(upTo, q.cursor),
      hasMore,
      changes: page.map(toWire),
      removedTasks: exits.map((e) => e.task_id as string).filter((id) => !visible.has(id)),
      addedProjects: membership.filter((m) => !m.removed_at).map((m) => m.project_id as string),
      removedProjects: membership.filter((m) => m.removed_at).map((m) => m.project_id as string),
    };
  } catch (err) {
    await c.query("ROLLBACK").catch(() => {});
    throw err;
  } finally {
    c.release();
  }
}

const toWire = (r: any) => ({ id: r.id, projectId: r.project_id, title: r.title, status: r.status,
  notes: r.notes, deleted: r.deleted_at !== null, version: Number(r.version) });
```

> **Aside: why the cursor jumps to the head.** When a page isn't full, the cursor moves to the tenant's head version, not the last row returned. The versions in between belong to projects this user can't see, and there's no reason to ask about them again. It's safe only because the head was read in the same snapshot as the rows; a head read in a later transaction could include a version the row query didn't see.

> **Aside: bounding exits and memberships by `upTo`.** A page covers the version range `(cursor, upTo]`. Exits and memberships outside that range belong to a later page. Reporting them early could tell a device to delete a task before it has received the change that put it somewhere visible.

The merge is a pure function, called inside the push transaction after the row is locked with `SELECT … FOR UPDATE`:

```ts
export function mergeFields(
  fieldVersions: Record<string, number>,   // from the locked row
  baseVersion: number,                     // what the device had seen
  changed: Record<string, unknown>,        // only the fields the user changed
  groups: string[][] = [],                 // fields accepted or rejected together
) {
  const conflicted = new Set(Object.keys(changed).filter((f) => (fieldVersions[f] ?? 0) > baseVersion));
  for (const group of groups) {
    if (group.some((f) => conflicted.has(f))) group.forEach((f) => f in changed && conflicted.add(f));
  }
  const accepted = Object.fromEntries(Object.entries(changed).filter(([f]) => !conflicted.has(f)));
  return { accepted, conflicts: [...conflicted] };
}
```

The surrounding push transaction does the rest: insert the mutation ID (on conflict, return the stored result), lock the row, authorize the user for its project (and the new project, if it's changing), merge, update, store the result with the mutation ID, and commit.

**Scenarios run against PostgreSQL 16:**

| Scenario | Result |
|---|---|
| A task moves from P1 to P2; Ana is in P1 only; Bo is in both | Ana's pull: `removedTasks: [task]`, no changes. Bo's pull: the change, no removal |
| Offline edit of status and notes, base older than a later status change | Notes accepted; `conflicts: ["status"]` |
| Street and city grouped; city changed on the server | Neither accepted |
| Second writer in the same tenant while the first is uncommitted | Waits for the first to commit (a 500 ms lock timeout fires) |
| 8 changes pulled with pages of 3 | 3 pages, all 8 tasks, final cursor equals the tenant's head |
| Cursor older than purged tombstones | `resetRequired` |

---

The habit to take from this: whenever a client keeps a copy of server data, ask what happens to that copy when a row is created elsewhere, changed twice, deleted, or moved somewhere the client can no longer see. A sync design is correct only when each of those reaches every device that needs it.
