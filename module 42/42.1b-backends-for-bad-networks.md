# Backends for Bad Networks and Small Batteries

_Module 42 · Mobile Backend Development · 42.1b_

## The Problem

Suppose you run software for home-healthcare agencies. Nurses visit patients on rural routes, with a phone or tablet: they check the day's schedule, open each patient's care plan, record vital signs and notes, and photograph wounds for the care record. About 20,000 nurses across 300 agencies. The app worked well in testing, in an office with good Wi-Fi. In the field:

**The home screen takes six seconds.** It makes seven requests: the nurse's profile, today's visits, each visit's patient summary, unread messages, announcements. Each round trip on a weak 4G signal takes 300–800 ms, and some run one after another. Nurses stand in patients' driveways waiting.

**Batteries don't last a shift.** The app checks for new messages every 30 seconds, all day. Each check wakes the phone's radio, which stays in a high-power state for several seconds afterwards. Almost every check returns "nothing new." Meanwhile, 40% of all API traffic is these polls.

**After an outage, the API goes down again.** A 20-minute database incident ends. Every phone retries immediately, and the scheduled hourly sync fires at :00 on all 20,000 devices at once. The recovered API is flattened within a minute. Later, a buggy app release retries failed uploads in a tight loop. There's no way to slow the phones down except shipping a fix and waiting days for the app stores and for people to update.

**Photos cost a fortune.** Wound photos upload at full resolution (5 MB each) over cellular. The care-plan screen downloads every photo at full size to show 120-pixel thumbnails.

**A lost tablet.** A shared tablet, used by three nurses on different shifts, is left in a patient's house. It contains a local copy of every patient visited that week, in plain SQLite, and the previous nurse's session was still valid.

None of this is about sync correctness (42.1a). It's about designing a backend for clients with **high latency, costly bandwidth, limited battery, operating-system control over when they run, and data stored on devices anyone could pick up.**

## What It Is

This article collects the backend techniques for **mobile network and device constraints**:

| Constraint | Backend consequence |
|---|---|
| High latency (100–800 ms per round trip) | Fewer, larger requests; screen-level endpoints |
| Expensive, slow bandwidth | Compression, conditional requests, only the fields and image sizes needed |
| Radio power costs | Batching; push instead of polling |
| The OS decides when apps run | Designs that tolerate long, unpredictable gaps |
| Thousands of identical clients | Jitter, backoff, `Retry-After`, server-side controls |
| Data on devices you don't control | Encryption, per-tenant storage, wipe on logout and revocation |

Unreliable networks also make **every write potentially retried**, which calls for idempotency. That's covered for sync in 42.1a, and for other writes with idempotency keys in 42.3a.

## Recognizing the Problem

- Screens need several sequential API calls to render.
- Response times look fine in server metrics but the app feels slow in the field.
- The app polls for changes on a timer.
- A large share of API traffic returns "nothing changed."
- Traffic spikes at round times (on the hour), or right after incidents end.
- Images are served at a single size.
- Responses aren't compressed, or cacheable responses have no ETags.
- There's no server-side way to make installed apps back off.
- Local data isn't encrypted, isn't separated by tenant, or survives logout.
- Removing a user doesn't remove data from their devices.

## How It Works

### 1. Fewer round trips: endpoints shaped like screens

On a 400 ms connection, seven sequential requests cost nearly three seconds before any server time. A **screen-level endpoint** returns what a screen needs in one response:

```
GET /mobile/v1/screens/today
{ "me": {…}, "visits": [ { "id": …, "time": "09:30", "patient": { "name": …, "address": … } } ],
  "unreadMessages": 3, "announcements": [] }
```

This is the **Backend for Frontend (BFF)** pattern: endpoints owned by the client team, composing the general services underneath. Keep them thin, composition and shaping only, so business rules aren't implemented twice. **GraphQL** reaches the same goal differently, with the app asking for exactly a screen's fields. On mobile, use it with **persisted queries** (Module 8), so apps send a query ID and the server only runs queries it knows.

### 2. Fewer bytes

| Technique | How | Effect |
|---|---|---|
| **Compression** | gzip or Brotli on JSON at the load balancer or API; mobile HTTP clients accept it by default | JSON typically shrinks 70–90% |
| **Conditional requests** | `ETag` on responses; the app sends `If-None-Match`; unchanged → `304` with an empty body | An unchanged care plan costs a few hundred bytes |
| **Field selection** | `?fields=name,status`, checked against an allow-list | Smaller payloads; no internal fields exposed |
| **Right-sized images** | Resize at upload and on demand (Module 11); request by display size; WebP or AVIF | Usually the biggest saving by far |
| **Client-side resizing before upload** | The app compresses photos to what the record needs | Uploads 10x smaller |
| **Incremental sync** | Only changes since the cursor (42.1a) | A daily sync costs kilobytes |
| **HTTP/2 and HTTP/3** | One connection for many requests; HTTP/3 (QUIC) survives Wi-Fi ↔ cellular switches | Fewer slow handshakes |

For multi-tenant data, cacheable responses must be `Cache-Control: private`. Without it, a CDN or proxy could cache one tenant's response and serve it to another.

A few conventions prevent whole classes of mobile bugs: IDs as strings (64-bit integers lose precision in JavaScript), times in UTC ISO 8601 and dates as `YYYY-MM-DD`, money as integer minor units with a currency, and **cursor pagination** everywhere (offset pagination skips or repeats items when data changes between pages).

### 3. Battery: the radio is the expensive part

A phone's cellular radio has a high-power state it enters for any request, and stays in for several seconds afterwards before dropping back. Ten small requests spread over a minute cost far more energy than one request carrying the same data.

- **Batch.** One push with 50 changes, one pull page with 500. Queue non-urgent uploads (analytics, logs) and send them together.
- **Don't poll.** Checking every 30 seconds keeps the radio up all day, mostly to learn nothing changed.
- **Push, then pull.** The server sends a **silent push** when something relevant changes, and the app syncs then (42.2a). Silent pushes are throttled and sometimes dropped, so the app also syncs on open and when the network returns (14.3 covers why).
- **Let the OS schedule background work.** Android's **WorkManager** runs work with constraints (unmetered network, charging) and batches it with other apps; **Doze** defers it when the phone is idle. iOS's **BGTaskScheduler** grants background time when it decides to. Either way, the backend must expect devices to go **days** without syncing: cursors must stay valid for weeks, and the reset path must exist (42.1a).

### 4. Protecting the server from its own clients

Thousands of copies of the same app behave in lockstep. Design for that:

- **Jitter everything scheduled.** "Sync every hour" must mean "every hour plus a random 0–15 minutes," or all devices arrive at :00.
- **Exponential backoff with jitter on errors**, capped, so a failing server sees retries spread out rather than in waves.
- **`Retry-After` on overload.** Answer `503` or `429` with `Retry-After`, and add jitter to the value itself, so returning clients don't arrive together. The app must respect it; that's part of the first-version checklist (42.3a).
- **Rate limits per device and per tenant** (Module 18), so one broken release stuck in a loop can't take the API down.
- **A server-side brake.** A remote-config value (42.3a) that sets the sync interval, pauses optional uploads, or turns a feature off, reachable in minutes without an app release. It has to be in the first version of the app to exist at all.

### 5. Data on devices you don't control

Offline support puts tenant data on phones that get lost, shared and resold. Treat each as a small, untrusted copy of your database:

| Risk | Protection |
|---|---|
| Lost or stolen device | Encrypt the local database (iOS Data Protection, SQLCipher or Android encrypted storage); keep tokens in the **Keychain** or **Keystore**, never plain preferences |
| Shared device | Logout **deletes** the local database and tokens; the next user starts empty |
| One user in several tenants | A **separate local database per tenant**, so switching never mixes data and removing a tenant deletes exactly its data |
| User removed from a team | Scope removal in sync deletes it at the next pull (42.1a) |
| User leaves, device lost | **Remote wipe**: an admin revokes the device; its next request gets a wipe instruction instead of data |
| Modified app | The server validates and authorizes everything; nothing from the device is trusted |
| Too much data | Sync only what the user needs (this week's patients, not the agency's) |

Remote wipe needs a `devices` table (device ID generated by the app on first launch, user, tenant, platform, app version, last seen, revoked at) and a check on every authenticated request. The same table later holds push tokens (42.2a) and binds sessions (42.3b).

## When It's Appropriate

- **Any mobile app used away from good Wi-Fi**: field work, travel, rural areas, emerging markets.
- **Screens that aggregate several resources**, where round trips dominate load time.
- **Large user bases** (thousands of devices), where synchronized behavior becomes an outage risk.
- **Apps that store tenant or personal data locally**, especially in healthcare, finance or field service.

## When It's Unnecessary or Overkill

- **Internal tools used on office Wi-Fi.** Compression and sane pagination may be all you need.
- **A BFF for an app with three screens** that map one-to-one to existing resources.
- **Remote wipe for apps that store nothing sensitive locally** and don't work offline.
- **Per-field selection** for small, stable payloads. Screen endpoints already cover most of the need.

## Trade-offs

- **Screen endpoints couple the backend to the UI.** Every screen redesign may need a backend change, and several app versions each need their shape (42.3a).
- **Caching and ETags need care with tenant data.** A missing `private` is a data leak through a shared cache.
- **Push-triggered sync is best-effort.** You still need sync on open and on reconnect, so push adds a path rather than replacing one.
- **Jitter and backoff make recovery slower on purpose.** Clients take longer to come back after an outage, in exchange for not causing a second one.
- **Encryption and per-tenant databases add app complexity** and some performance cost, and key management on the device has its own failure modes (a lost key means a lost local database, which must be re-synced).
- **Remote wipe works only when the device next connects.** A device kept offline keeps its data until then, so minimizing what's stored matters as much as wiping it.

## Alternatives

- **GraphQL with persisted queries** instead of hand-written screen endpoints (Module 8): one flexible endpoint, at the cost of query-cost control.
- **Server-driven UI**, where the server sends screen layouts as data. It lets teams change screens without app releases, at the cost of a constrained UI and a complex contract.
- **Progressive web apps** for simpler cases, with service-worker caching and background sync, though with less control over background execution on iOS.
- **A mobile device management (MDM) product** for company-owned devices, which provides remote wipe, encryption policies and app configuration outside your app.

## How to Achieve It

**Step 1: compression, ETags with `private`, cursor pagination and image sizes.** Mostly configuration. _Signal to move on:_ screens still feel slow because of round trips.

**Step 2: screen-level endpoints for the heaviest screens**, and an end to polling in favor of sync on open, on reconnect and on silent push. _Signal:_ the app is fast, but incidents cause stampedes.

**Step 3: jitter, backoff, `Retry-After`, per-device limits and a remote brake.** Test by replaying a mass reconnect against staging. _Signal:_ the remaining risk is data on devices.

**Step 4: encrypted, per-tenant local storage, logout wipe and remote wipe**, and a review of what each role actually needs stored on the device.

## Implementation

TypeScript (Express), in two pieces: a screen endpoint that's cheap when nothing changed, and middleware that sheds load with jittered `Retry-After` and enforces device revocation.

```ts
import { createHash } from "node:crypto";
import type { Request, Response } from "express";

declare function loadTodayScreen(tenantId: string, userId: string): Promise<unknown>;

export async function todayScreen(req: Request, res: Response) {
  const { tenantId, userId } = req.auth; // from the verified access token
  const body = await loadTodayScreen(tenantId, userId); // composition only: no business rules here
  const etag = `"${createHash("sha256").update(JSON.stringify(body)).digest("base64url")}"`;

  res.set("ETag", etag);
  res.set("Cache-Control", "private, no-cache"); // private: never stored by a shared cache
  if (req.get("If-None-Match") === etag) return res.status(304).end(); // a few hundred bytes
  res.json(body);
}
```

> **Aside: this ETag saves bandwidth, not server work.** The server still builds the whole response to hash it. That's the right first step, because bandwidth and radio time are the mobile costs. If building the screen is expensive too, derive the ETag from version numbers (the tenant's sync version from 42.1a, or the latest `updated_at` of the parts), so an unchanged screen can be answered without being built.

```ts
import type { NextFunction, Request, Response } from "express";

declare function isOverloaded(): boolean;                  // e.g. queue depth or p99 above a threshold
declare function deviceStatus(tenantId: string, deviceId: string): Promise<"active" | "revoked" | "unknown">;

export async function mobileGuard(req: Request, res: Response, next: NextFunction) {
  if (isOverloaded()) {
    const seconds = 30 + Math.floor(Math.random() * 90);   // spread returning clients over 30–120 s
    return res.status(503).set("Retry-After", String(seconds)).json({ type: "overloaded", retryable: true });
  }

  const deviceId = req.get("X-Device-Id");
  if (!deviceId) return res.status(400).json({ type: "device-id-required" });
  if ((await deviceStatus(req.auth.tenantId, deviceId)) === "revoked") {
    // The app's first-version contract: on this response, delete all local data and log out.
    return res.status(403).json({ type: "device-revoked", wipe: true });
  }
  next();
}
```

> **Aside: why the jitter is in the header.** If every overloaded response said `Retry-After: 60`, the clients refused in the same second would all return in the same second a minute later. Randomizing the value spreads them out, and it works even for app versions whose own backoff has no jitter.

> **Aside: the wipe is only as good as the app.** The server can refuse data to a revoked device, but deleting what's already on it depends on the app obeying `wipe: true`, which is why it belongs in the first-version checklist (42.3a). A modified app can ignore it. That's the argument for storing as little as possible on the device in the first place.

A **Kotlin** sibling for the device side would be worth writing, though it isn't yet: WorkManager's constraints, backoff policies and unique work are where most of this article's client obligations are implemented on Android, and seeing them makes clear which guarantees the backend can and can't assume.

The habit to take from this: test the app on a throttled, lossy network, with a phone that sleeps, before calling a feature done. Most mobile backend problems aren't visible from an office on Wi-Fi.
