# Backend-as-a-Service: When the Database Is Your API

_Module 42 · Mobile Backend Development · 42.4a_

## The Problem

Suppose you're a four-person startup building food-safety checklists for restaurant chains. Managers at each location complete daily checks on a phone (fridge temperatures, cleaning, allergen labeling), and head office sees every location's results. To ship quickly, you build on Supabase: its authentication, its PostgreSQL database, its storage for photos, and its client library called directly from the React Native app. There's no backend of your own. The first version ships in six weeks, and three chains sign up.

The next year's surprises:

**A table anyone could read.** A developer adds a `supplier_contacts` table for a new feature and forgets to enable row-level security on it. With RLS off, Supabase's API serves the table to anyone holding the project's public API key, which is inside the app. A customer's contractor finds it with a browser.

**A tenant chosen by the user.** The first version stored each user's company in `user_metadata`, and every policy compared rows against it. Users can edit their own `user_metadata` from the client library. A manager who had worked for two chains changes hers and sees the competitor's inspection results.

**Removed, but still in.** A chain fires a manager. Head office removes her from the company. For up to an hour she can still read everything, because her access token still says which company she belongs to, and the policies trusted the token alone.

**A rule the database couldn't express.** The free plan allows three locations. That limit was enforced in the app. A customer's IT person creates twelve locations with a script against the API.

**Logic in two apps.** "A failed fridge check creates a corrective action and notifies the regional manager" is implemented in the iOS and Android code paths of the app, slightly differently. Some corrective actions are never created.

**Wanting out, and finding the app is the API.** When an enterprise customer requires EU data residency and an audit trail the team can't build in database rules, the team decides to move to its own backend. Then they realize that every installed copy of the app talks to Supabase directly, and keeps doing so until users update. Leaving takes a year.

None of this makes Supabase a bad choice. It was the right choice for six weeks to launch. These are the consequences of a specific trade: **removing your own server from between the app and the data.**

## What It Is

A **Backend-as-a-Service (BaaS)** provides authentication, a database, file storage, realtime updates and often push, which apps use directly through the provider's SDK. The best-known are **Firebase** (Firestore, plus SQL Connect for PostgreSQL), **Supabase** (PostgreSQL with generated APIs) and **AWS Amplify** (DynamoDB behind AppSync GraphQL, with Cognito).

The defining property is architectural:

```
YOUR OWN BACKEND                               BaaS
app ─► your API ─► database                    app ─► provider API ─► RULES ─► database
       validation, authorization,                                     the only server-side gate
       business rules, versioning                                     between any client and the data
```

With your own backend, the app talks to code you control. With a BaaS, **the app's queries are your API**, and **security rules evaluated next to the data** (Postgres row-level security on Supabase, Security Rules on Firebase, schema authorization rules on Amplify) are the only server-side check. Anything a rule can't express must move to server-side functions that the app calls instead of writing data directly.

## Recognizing the Problem

- The app calls the database through a vendor SDK, and there's no server of your own in between.
- Tables or collections exist without security rules or RLS.
- Authorization reads values the user can change (profile metadata, client-set fields).
- Plan limits, cross-record constraints or business workflows are enforced in the app.
- The same business logic exists in several client codebases.
- Users removed from a tenant keep access until their token expires.
- The bill grows with reads caused by listeners or dashboards.
- Nobody knows what leaving the provider would take.

## How It Works

### 1. What you gain, and what moves into rules

| You gain | You give up |
|---|---|
| Auth, database, storage, realtime and often offline support in days | A place for business logic between the app and the data |
| No servers to run; scaling handled | Control over query shapes: the app decides what to ask |
| Low cost at small scale | API versioning: installed apps' queries are the contract (42.3a) |
| Realtime subscriptions built in | Predictable cost at scale, for per-operation pricing |

Every security decision must be expressible as a rule checked on each read and write. Rules are good at "this row belongs to your tenant," "only these fields may change," "this field must equal the caller's ID." They're poor or incapable at counting across records, calling external services, multi-step workflows and anything needing a secret. Those go into **server-side functions** (Supabase Edge Functions or database functions, Firebase Cloud Functions, Lambda for Amplify), which the app calls instead.

### 2. The three platforms, briefly

| | Firebase | Supabase | AWS Amplify (Gen 2) |
|---|---|---|---|
| Data | Firestore documents; SQL Connect (PostgreSQL) | PostgreSQL | DynamoDB via AppSync (GraphQL) |
| Security | Security Rules (own language) | Postgres row-level security | Authorization rules in the TypeScript schema |
| Auth | Firebase Auth; Identity Platform for per-tenant sign-in and SSO | Supabase Auth (JWTs) | Cognito |
| Offline | Firestore SDK cache with offline writes | Not built in; add a sync engine (42.1a) | Not in Gen 2 (DataStore was Gen 1 only) |
| Exit path | Hardest: proprietary data model and rules | Easiest: it's Postgres (`pg_dump`) | Medium: standard AWS services |

Platform details change often. In 2026 alone, Firebase renamed Data Connect to SQL Connect, Supabase announced it's replacing its `anon` and `service_role` keys with publishable and secret keys, and Amplify Gen 1 entered maintenance mode ahead of its end of life in May 2027.

### 3. Tenant isolation in rules (Supabase)

On Supabase, the app sends queries with the user's access token. Supabase switches to the `authenticated` database role, exposes the token's claims to SQL through `auth.jwt()` and `auth.uid()`, and runs the query. Row-level security is all that stands between that query and every row. So:

- **Every table in an exposed schema needs RLS**, with no exceptions. Supabase's security advisor flags tables without it; treat its warnings as build failures. That was the supplier-contacts incident.
- **The tenant must come from something the user can't change.** `user_metadata` is editable by the user through the client library. Authorization data comes from `app_metadata` (writable only by server code), or from a **custom access-token hook**: a database function Supabase Auth calls before issuing each token, which reads the user's active tenant from tables the user can't modify, and adds it as a claim.
- **Policies check the membership table too, not just the token.** Access tokens live up to an hour. Checking current membership in the policy means removal takes effect on the next query.
- **The secret key bypasses RLS** entirely. It belongs on servers you control, never in an app.

### 4. The same idea on Firebase

Firestore data is laid out with the tenant in the path (`tenants/{tenantId}/checks/{checkId}`), and your backend records each user's tenants as **custom claims** on their token. Rules then check the path against the token, allow-list writable fields (`request.resource.data.keys().hasOnly([...])`), and require server-set fields such as `createdBy == request.auth.uid`. Four limits shape designs:

- **Rules aren't filters.** A query must be written so that every possible result is allowed; a query across tenants fails entirely rather than returning the allowed subset.
- **Custom claims are limited to 1,000 bytes and are stale for up to an hour**, the same removal problem. An `exists()` check on a members document in the rule is always current, and each such check is a billed read.
- **Rules can call `get()` and `exists()` only a limited number of times** per evaluation, so complex permission models don't fit.
- **No constraints across documents**, such as a plan's location limit, without a Cloud Function or a counter document updated in a transaction.

**Identity Platform multi-tenancy** is a different thing: separate user pools and sign-in methods per tenant (SAML SSO for one chain, Google sign-in for another). It's about who can log in and how. Data isolation is still the rules' job.

### 5. Combining a BaaS with your own backend

It isn't all or nothing. Four combinations work well:

- **BaaS for authentication only.** Supabase Auth, Firebase Auth or Cognito handles sign-up, social login and SSO; your own API does the rest, verifying the provider's tokens with its public keys (JWKS).
- **Read-only realtime projections.** Your backend stays the only writer. After each change, it writes a denormalized projection into Firestore or a Supabase table, and the app subscribes to it for instant updates. Rules allow reads only. You get realtime and offline reads without handing over your business rules, and leaving means deleting a projection.
- **A BaaS for one self-contained feature**: chat, presence, collaborative cursors. Its own data and rules, sharing only IDs with your system.
- **BaaS first, own backend later.** A reasonable path for new products, if planned from day one (section 7).

### 6. Cost

Firestore bills per document operation (in 2026, for Standard edition in a US region, about $0.03 per 100,000 reads and $0.09 per 100,000 writes, with a daily free quota; multi-region locations cost more). Every document returned is a read, and listeners re-read on reconnect. A dashboard that listens to a 50,000-document collection costs 50,000 reads every time someone opens it. Supabase bills for plans and compute size, so heavy queries mean a bigger instance rather than a bigger per-query bill. Amplify bills the underlying AWS services. At small and medium scale, a BaaS is usually far cheaper than running your own backend; read-heavy patterns at scale are where that flips.

### 7. Leaving: installed apps make it slow

With your own backend, changing databases is a server change. With a BaaS, the app talks to the provider directly, and installed versions keep doing so for as long as they're installed (42.3a):

```
month 0      release app 5.0, which uses your new backend
months 0–12  4.x apps (BaaS) and 5.x apps (your backend) both in use:
             keep the data consistent between them, or proxy one to the other
month 12     raise the minimum version to 5.0; only now can the BaaS be switched off
```

Preparing from day one makes it a project instead of a crisis:

- **Hide the SDK behind your own interfaces in the app** (`ChecksRepository`, `AuthService`), so a switch changes implementations, not every screen.
- **Ship the forced-upgrade mechanism in version 1** (42.3a). Without it, you can never switch the BaaS off.
- **Rehearse a full data export and import.** For Supabase, `pg_dump`. For Firestore, managed exports or an Admin SDK script.
- **Plan for passwords.** Supabase Auth stores bcrypt hashes you can take. Firebase Auth exports its own scrypt variant with the parameters, so your new system must verify that format or re-hash at next login.
- **Keep a written list of what each rule enforces.** On your own backend, each becomes authorization code, and the list is its test plan.
- **Keep business logic in server-side functions**, not in the apps. Functions move to your backend almost unchanged.

## When It's Appropriate

- **Prototypes, MVPs and small teams** with mostly create-read-update-delete data and simple permissions.
- **Realtime-heavy features**: live dashboards, chat, presence, with rules that fit.
- **Apps that need offline support quickly** (Firestore's SDK) and can accept its data model.
- **Authentication alone**, especially social login and SSO, next to your own API.
- **Read-only projections** that add realtime updates to an existing backend.

## When It's Unnecessary or Overkill

- **B2B products with strict isolation, audit, residency or compliance requirements** that rules can't express or prove. Use your own backend, perhaps with BaaS authentication.
- **Complex business rules, integrations and long workflows.** They'll end up in server functions anyway, at which point the BaaS mostly adds a second place for logic.
- **High, steady read volumes on per-operation pricing.**
- **Teams already running a backend** that fits, where a BaaS would be a second system to secure.

## Trade-offs

- **Rules are your whole authorization layer.** A missing or wrong rule is a data leak, with no API layer behind it to catch it. The rules need tests like any authorization code.
- **Direct database access means the app's queries are the contract.** Schema changes affect every installed version, and changing providers takes as long as the app's version tail.
- **Business logic tends to leak into apps**, and then diverges between platforms.
- **Token-based authorization is stale** until tokens refresh, unless policies check current data, which costs a lookup on each query.
- **Per-operation pricing is easy to blow up** with listeners, dashboards and client bugs that re-subscribe in a loop.
- **Abuse protection is thinner.** Without your own API, the provider's quotas and tools such as Firebase App Check (42.3b) are the main defenses against scripted clients.
- **Vendor change is a real risk.** Products are renamed, repriced and retired: Fauna shut down (41.3b), Atlas Device Sync ended (42.1a), and Amplify Gen 1 is nearing end of life. An exit plan written early is cheap.

## Alternatives

- **Your own backend** (the rest of Module 42), with managed pieces where they help: a managed Postgres, a managed auth service, a sync engine.
- **Managed auth alone** (Auth0, Clerk, Cognito, Firebase Auth) with your own API.
- **A sync engine** (PowerSync, ElectricSQL) on top of your own Postgres for offline and realtime reads, with writes through your API (42.1a).
- **Self-hosted Supabase**, for the same model inside your own infrastructure. The architecture's trade-offs stay the same; the vendor risk shrinks.

## How to Achieve It

**Step 1: before the first table, decide where authorization data lives** (a token hook or server-set metadata, never user-editable fields), turn RLS or rules on for everything, and hide the SDK behind interfaces in the app. _Signal to move on:_ the first plan limit or workflow appears.

**Step 2: move rules that don't fit into server functions**, and have the app call them. Add rules tests to CI: cross-tenant reads and writes, forged fields, removed members. _Signal:_ you need things rules can't provide (audit trails, residency, complex permissions) or costs are growing fast.

**Step 3: pick a combination.** BaaS auth with your own API, or read-only projections, rather than all or nothing. Ship the forced-upgrade mechanism if it isn't there. _Signal:_ a decision to leave, or to shrink the BaaS's role.

**Step 4: rehearse the exit**: export and import, password migration, the rules-to-code list, and a version-tail plan measured in months.

## Implementation

SQL, for Supabase, because the entire authorization layer lives in the database. It was run on PostgreSQL 16 with Supabase's `auth.jwt()`, `auth.uid()` and roles recreated, and passes ten scenarios, listed at the end.

The access-token hook puts the user's **active** tenant in every token, but only if they're a member of it:

```sql
CREATE FUNCTION public.custom_access_token_hook(event jsonb) RETURNS jsonb
LANGUAGE plpgsql STABLE AS $$
DECLARE claims jsonb := event -> 'claims'; v_tenant uuid; v_role text;
BEGIN
  SELECT m.tenant_id, m.role INTO v_tenant, v_role
    FROM public.user_settings s
    JOIN public.memberships m ON m.tenant_id = s.active_tenant_id AND m.user_id = s.user_id
   WHERE s.user_id = (event ->> 'user_id')::uuid;
  claims := CASE WHEN v_tenant IS NULL THEN claims - 'tenant_id' - 'tenant_role'
                 ELSE claims || jsonb_build_object('tenant_id', v_tenant, 'tenant_role', v_role) END;
  RETURN jsonb_set(event, '{claims}', claims);
END $$;

GRANT EXECUTE ON FUNCTION public.custom_access_token_hook TO supabase_auth_admin;
REVOKE EXECUTE ON FUNCTION public.custom_access_token_hook FROM authenticated, anon, public;
GRANT SELECT ON public.user_settings, public.memberships TO supabase_auth_admin;
-- Both tables have RLS enabled, so the hook's role needs its own policies, or it sees no rows
-- and silently issues tokens with no tenant.
CREATE POLICY hook_reads_settings    ON public.user_settings FOR SELECT TO supabase_auth_admin USING (true);
CREATE POLICY hook_reads_memberships ON public.memberships   FOR SELECT TO supabase_auth_admin USING (true);
```

> **Aside: the bug the tests caught.** The first version of this schema had the grants but not the two policies. Every token came out with no tenant, and every user saw nothing. Nothing failed loudly: the hook simply found no rows. It's exactly the kind of error rules tests exist for.

The policies check the token **and** current membership, and fail closed:

```sql
CREATE FUNCTION public.current_tenant() RETURNS uuid LANGUAGE sql STABLE AS $$
  SELECT nullif(auth.jwt() ->> 'tenant_id', '')::uuid $$;

-- Current membership, from the table, so removal works before the token expires.
-- SECURITY DEFINER: reads memberships without recursing into memberships' own RLS.
CREATE FUNCTION public.current_member_role() RETURNS text
LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public AS $$
  SELECT role FROM public.memberships WHERE tenant_id = public.current_tenant() AND user_id = auth.uid() $$;

ALTER TABLE public.checks ENABLE ROW LEVEL SECURITY;

CREATE POLICY checks_read ON public.checks FOR SELECT TO authenticated
  USING (tenant_id = (SELECT public.current_tenant()) AND (SELECT public.current_member_role()) IS NOT NULL);
CREATE POLICY checks_write ON public.checks FOR INSERT TO authenticated
  WITH CHECK (tenant_id = (SELECT public.current_tenant()) AND (SELECT public.current_member_role()) IS NOT NULL);
CREATE POLICY checks_update ON public.checks FOR UPDATE TO authenticated
  USING      (tenant_id = (SELECT public.current_tenant()) AND (SELECT public.current_member_role()) IS NOT NULL)
  WITH CHECK (tenant_id = (SELECT public.current_tenant()));             -- can't move a row to another tenant
CREATE POLICY checks_delete ON public.checks FOR DELETE TO authenticated
  USING (tenant_id = (SELECT public.current_tenant()) AND (SELECT public.current_member_role()) IN ('owner','admin'));

-- Switching tenant: only to one you belong to. The app then refreshes its session to get a new token.
CREATE POLICY settings_own ON public.user_settings FOR ALL TO authenticated
  USING (user_id = (SELECT auth.uid()))
  WITH CHECK (user_id = (SELECT auth.uid()) AND (active_tenant_id IS NULL OR EXISTS (
    SELECT 1 FROM public.memberships m WHERE m.tenant_id = active_tenant_id AND m.user_id = (SELECT auth.uid()))));
```

> **Aside: `(SELECT …)` around the functions.** Written bare, `current_member_role()` would be evaluated for every row the query examines. Wrapped in a subquery, Postgres evaluates it once per query and reuses the result. On a large table, that's the difference between milliseconds and seconds.

And the policy that must never be written, because users can set `user_metadata` themselves:

```sql
-- ❌ Any user can put any tenant ID into their own user_metadata, refresh, and read that tenant.
CREATE POLICY never_do_this ON public.checks FOR SELECT TO authenticated
  USING (tenant_id = (auth.jwt() -> 'user_metadata' ->> 'tenant_id')::uuid);
```

**Scenarios run against PostgreSQL 16:**

| Scenario | Result |
|---|---|
| The hook issues a token | Contains the active tenant and role |
| Two users in different tenants read | Each sees only their own tenant's rows |
| No token (`anon`) | Sees nothing |
| Insert into another tenant; move a row to another tenant | Both rejected by RLS |
| Member deletes; admin deletes | Member: 0 rows; admin: 1 row |
| User removed from the tenant, still holding its token | Sees nothing; the next token has no tenant |
| Switch to a tenant you're not in; then to one you are | First rejected; second accepted and used by the hook |
| Forged `user_metadata.tenant_id` | Leaks through the bad policy; blocked by the real ones |
| `service_role` (the secret key) | Sees everything, which is why it never ships in an app |
| The two hook policies removed | Tokens come out with no tenant |

---

The habit to take from this: with a BaaS, look at every rule as if it were your API's entire authorization code, because it is. For each table or collection, ask who can read it with only the app's public key, and what a user could change about themselves to see more.
