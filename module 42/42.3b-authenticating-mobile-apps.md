# Authenticating Mobile Apps: Public Clients, Rotation on Bad Networks, Device Binding and Attestation

_Module 42 · Mobile Backend Development · 42.3b_

## The Problem

Suppose you run a corporate-card and spend-management product. Employees use a mobile app to see their card, photograph receipts and approve colleagues' spending; finance teams use the web app. Many customers sign in through their own identity provider (Okta, Microsoft Entra ID). Over eighteen months, authentication is rebuilt three times.

**Version one: a login form and a secret.** The app shows its own username and password screen, and for SSO customers, a web view that loads the identity provider's page inside the app. The app calls the token endpoint with a client ID and **client secret** compiled into it. Then:

- A customer's security team rejects the app: their identity provider blocks sign-in from embedded web views, because the app could read the password as it's typed.
- A researcher extracts the client secret from the Android package in ten minutes.
- Refresh tokens last a year and never change. One employee's token, copied from an unencrypted phone backup, is used for four months before anyone notices unusual approvals.

**Version two: rotation.** Following current guidance, every refresh returns a new refresh token and invalidates the old one. If an old token is ever presented again, someone has a copy, so the whole session is revoked. Within a week, support is flooded: about 3% of users are logged out every day. The cause is mobile networks. The refresh request reaches the server, which rotates the token, but the response is lost in a lift or a tunnel. The app retries with the old token, which now looks stolen, and the session dies.

**Version three: a grace window.** Retries within 30 seconds are accepted when the replacement token was never used. Logouts drop sharply but don't stop. Some users are still logged out at random, usually right after opening the app. When the app resumes, three screens each get `401` at once and each starts its own refresh. The server issues two new tokens; the app keeps whichever arrived last, which may be the one already replaced. Its next refresh looks like reuse.

**Meanwhile, sign-up abuse.** A referral program pays a credit per new company. Scripts create hundreds of fake companies from emulators. The team adds device attestation and blocks every request that fails it. A week later, sales escalates: legitimate customers on older or uncertified Android devices can't sign up at all.

## What It Is

Mobile apps are **public clients** in OAuth terms: anything shipped inside them, including a client secret, can be extracted. This article covers the pieces of authentication that are specific to such clients:

- **Login for native apps**: the authorization code flow with **PKCE**, run in the **system browser**, as RFC 8252 describes.
- **Refresh tokens on unreliable networks**: rotation with reuse detection, plus the **grace window** and **single-flight refresh** that mobile networks require.
- **Device binding**: tying a session to one installation, so a copied token can't be used from another.
- **Sender-constrained tokens (DPoP)**: tokens that are useless without a private key held on the device.
- **App attestation** (Play Integrity, App Attest): evidence that a request comes from your genuine app on a genuine device, used as a **risk signal**.

What refresh tokens are, why they're rotated and how sessions end are covered in 4.1a and 4.4, and aren't repeated here. OAuth and identity federation in general are 4.1b.

## Recognizing the Problem

- The app contains a client secret or API key it uses to authenticate itself.
- Login happens in a native form or an embedded web view.
- Refresh tokens are long-lived and never change.
- Users report being logged out at random, often after poor connectivity or on app resume.
- Refresh-token reuse detection fires far more often than theft could explain.
- A refresh token works from any device.
- Abuse (fake sign-ups, scraping) comes from scripts pretending to be your app.
- Attestation failures are blocked outright, and real customers complain.

## How It Works

### 1. Native login: code flow with PKCE in the system browser

RFC 8252 ("OAuth 2.0 for Native Apps") sets out the pattern:

```
app ── opens system browser (ASWebAuthenticationSession / Custom Tabs) ──► authorization server
        with code_challenge = SHA256(code_verifier)                      (or the customer's IdP via SSO)
user signs in, in the browser (password manager, passkeys, existing SSO session all work)
browser ── redirect with ?code=… ──► app (claimed https link or custom scheme)
app ── POST /token  code + code_verifier ──► authorization server ──► access + refresh tokens
```

- **The system browser, never an embedded web view.** The app can't read what the user types there, the user's existing SSO session and password manager work, and identity providers that block embedded views accept it.
- **PKCE instead of a client secret.** The app creates a random `code_verifier` per login and sends only its hash first. An attacker who intercepts the redirect's code can't exchange it without the verifier. The app has no secret, because it can't keep one.
- **Tokens stored in the Keychain or Keystore**, never in plain preferences. Biometrics can unlock the stored refresh token on the device; they don't replace server authentication.

### 2. Rotation on a network that loses responses

Rotation with reuse detection (4.4) makes a stolen refresh token a detectable event: if a replaced token comes back, two parties hold copies, so the session is revoked. RFC 9700, the OAuth security best practice published in January 2025, requires either that or sender-constrained tokens for public clients.

On mobile networks, though, the most common "reuse" isn't theft. It's a **lost response**:

```
app ── refresh(R1) ──► server rotates: R1 used, R2 issued
app ✗ response lost in a lift
app ── refresh(R1) again ──► R1 is already used … theft? or a retry?
```

The **grace window** tells them apart: if a used token returns within a short window (30 seconds is typical), **and** the token that replaced it has never been used, it's almost certainly a retry. The server rotates again and retires the replacement the app never received. If the replacement **has** been used, someone else holds a copy, and the session is revoked as before. The window is short because it's a small opening for an attacker who copies a token and uses it within seconds.

### 3. Single-flight refresh on the device

The grace window can't fix concurrent refreshes from the same app. If three requests fail with `401` together and each refreshes, the app receives several tokens, and at most one is current. Keeping the wrong one causes a reuse detection on the next refresh. The fix is on the client: **one refresh at a time**. The first caller starts it; everyone else waits for its result. This belongs in the first-version checklist (42.3a), because the server can't enforce it.

### 4. Device binding

Each session belongs to one installation's `device_id` (42.1b). The app sends it with every refresh, and a token presented with a different device ID revokes the session. That stops a token copied from one phone being used from another, **unless the attacker also copies the device ID**, which is just a value the app sends.

Stronger binding needs a key the attacker can't copy. **DPoP** (RFC 9449) binds tokens to a key pair generated on the device, ideally in the Secure Enclave or Android's hardware keystore: every request carries a proof signed with the private key, and a stolen token is useless without it. It costs more work on both sides, and suits high-risk tenants once rotation works well.

Two more controls complete the session: an **idle timeout** (a refresh token unused for, say, 30 days dies) and an **absolute lifetime** (log in again after 90 days, whatever happens). And a remotely wiped device (42.1b) gets a wipe instruction on its next refresh, not a new token.

### 5. Attestation as a risk signal

**Google Play Integrity** and **Apple App Attest** let your server ask the platform whether a request comes from your genuine, unmodified app on a genuine device. (Play Integrity replaced SafetyNet Attestation, which has been shut down.)

- **Play Integrity:** the app requests a token that includes a hash of the request it's about to make, and sends it along. Your server has Google decode it into a verdict, then checks, **in this order**: that the verdict is about **this** request, for **your** package, and recent (otherwise it's a replay and nothing else in it can be trusted); that the app is recognized by Play and signed with your certificate; and what the device integrity labels say. On Android 13 and later, the strongest label also requires a security patch from the last year.
- **App Attest:** the app generates a key pair in the Secure Enclave, and Apple attests to it once. Later requests carry **assertions** signed with that key, with a counter that must increase, which blocks replays. Verifying the attestation means parsing CBOR and X.509 chains; use a maintained library. **Firebase App Check** wraps both platforms behind one token.

What attestation **doesn't** do: prove the user is honest, replace authentication or rate limits, or pass on every legitimate device. Old, uncertified or custom-ROM phones fail, and so do some real customers. So the result is a **risk signal** with three outcomes: allow, **step up** (email verification, a CAPTCHA, manual review), or deny. It belongs on the endpoints abuse targets: sign-up, login, password reset, and high-value actions such as payouts or full data exports. Not on every call, which would cost quota, latency and battery. Roll it out in **monitor mode** first: record decisions for a few weeks, look at who would have been blocked by tenant, device model and country, and only then enforce.

## When It's Appropriate

- **Every native app** that authenticates users: PKCE in the system browser, no secrets, secure storage.
- **Apps with long-lived sessions**, which is most mobile apps: rotation with a grace window, single-flight, device binding, idle and absolute limits.
- **Products with valuable accounts** (payments, health, business data): consider DPoP for high-risk tenants.
- **Endpoints targeted by automation**: attestation as a signal on sign-up, login, reset and high-value actions.

## When It's Unnecessary or Overkill

- **DPoP for low-risk consumer apps** that already rotate refresh tokens well.
- **Attestation on every API call.** The access token already identifies the session.
- **Hard-blocking attestation failures** anywhere legitimate users might be on older or uncertified devices.
- **Very short absolute lifetimes** that force frequent logins, which push users toward weaker habits.

## Trade-offs

- **The grace window is a small, deliberate hole.** A token copied and used within 30 seconds of the real user's refresh can look like a retry. Shorter windows log out more real users; longer ones help attackers more.
- **Revoking the whole session on reuse punishes the real user** along with the attacker, because the server can't tell which one used the token first.
- **Device IDs are weak binding on their own.** They stop casual token reuse, not an attacker who copies the device's storage.
- **DPoP adds a signature per request** and key management on the device, and needs support in your API gateway and resource servers.
- **Attestation depends on Google and Apple**: their availability, quotas, rules and verdict formats, which change over time.
- **Step-up flows add friction** for the legitimate users who trigger them, and need support processes for people who can't pass.
- **The system-browser flow feels less seamless** than a native form, and some product teams resist it. It's the only flow that SSO customers and current security guidance accept.

## Alternatives

- **Sender-constrained tokens instead of rotation** (DPoP, or mutual TLS with client certificates), as RFC 9700 allows. Stronger, with more implementation work.
- **Short-lived access tokens with no refresh token**, requiring frequent re-authentication. Rarely acceptable on mobile.
- **Passkeys** for the sign-in itself, which remove passwords from the flow entirely and work with the system browser pattern.
- **A managed identity service** (Auth0, Cognito, Firebase Authentication, Supabase Auth) that implements rotation, PKCE and often attestation integration, with its own reuse-detection and grace-window settings.
- **Rate limits and behavioral detection** for abuse, instead of or alongside attestation (Module 18).

## How to Achieve It

**Step 1: move login to PKCE in the system browser, and remove any secret from the app.** Store tokens in the Keychain or Keystore. _Signal to move on:_ SSO customers and security reviews accept the flow.

**Step 2: rotate refresh tokens with reuse detection and a grace window**, and ship single-flight refresh in the app before turning detection on. Watch revocations by reason. _Signal:_ reuse revocations are rare and explainable.

**Step 3: bind sessions to devices**, with idle and absolute limits and the remote-wipe check. _Signal:_ abuse, not account theft, is the remaining problem.

**Step 4: add attestation in monitor mode on abuse-prone endpoints**, analyze the results, then enforce with step-up. Consider DPoP for high-risk tenants.

## Implementation

TypeScript, in three pieces: the server's handling of an already-used refresh token, the app's single-flight refresher, and the attestation decision. The refresh handling was run against PostgreSQL 16: a lost response followed by a retry, a replay of an old token after its successor was used (the session is revoked and the newest token stops working), use of a retired successor, and two simultaneous retries of one lost response.

The normal rotation (look up the token by its hash, lock it and its session, check expiry and device, issue a successor, mark the old one used) follows 4.4. The mobile-specific part is what happens when the token has already been used:

```ts
import type pg from "pg";

const GRACE_SECONDS = 30;

type Token = { id: string; session_id: string; used_at: Date | null; retired_at: Date | null;
               replaced_by: string | null; db_now: Date };
declare function issue(c: pg.PoolClient, sessionId: string): Promise<{ id: string; value: string }>;
declare function revokeSession(c: pg.PoolClient, sessionId: string, reason: string): Promise<void>;

// Called inside the refresh transaction, with the token and its session locked (FOR UPDATE).
export async function handleUsedToken(c: pg.PoolClient, t: Token) {
  if (t.retired_at) {
    // A successor retired after a lost response was never delivered to the app. Whoever holds it intercepted it.
    await revokeSession(c, t.session_id, "retired refresh token used");
    return { outcome: "reuse-detected" as const };
  }
  const { rows: [successor] } = await c.query(
    "SELECT used_at FROM refresh_tokens WHERE id = $1 FOR UPDATE", [t.replaced_by]);
  const secondsSinceUse = (t.db_now.getTime() - t.used_at!.getTime()) / 1000;

  if (secondsSinceUse <= GRACE_SECONDS && successor && successor.used_at === null) {
    // Lost response: the app never received the successor. Issue a new one and retire the unseen one.
    const fresh = await issue(c, t.session_id);
    await c.query("UPDATE refresh_tokens SET used_at = now(), retired_at = now(), replaced_by = $2 WHERE id = $1",
                  [t.replaced_by, fresh.id]);
    await c.query("UPDATE refresh_tokens SET replaced_by = $2 WHERE id = $1", [t.id, fresh.id]);
    return { outcome: "rotated-after-lost-response" as const, refreshToken: fresh.value };
  }
  // The successor was used, or the retry came too late: two parties hold this session.
  await revokeSession(c, t.session_id, "refresh token reuse");
  return { outcome: "reuse-detected" as const };
}
```

> **Aside: why retired tokens are marked.** Setting `used_at` on the unseen successor sends any later use of it down this path, and `retired_at` makes that path treat it as reuse instead of another lost response. Without the mark, a copy of the lost response's token could be exchanged within the grace window. Two retries of the same lost response arriving together both succeed, and the second retires the token the first returned. An app that keeps the first one is logged out on its next refresh, which is what the next snippet prevents.

On the device, one refresh runs at a time, and every request that needs a token waits for it:

```ts
let inFlight: Promise<string> | null = null;

declare function readRefreshToken(): Promise<string>;            // from Keychain / Keystore
declare function saveRefreshToken(token: string): Promise<void>;
declare function callRefreshEndpoint(refreshToken: string, deviceId: string): Promise<{ accessToken: string; refreshToken: string }>;
declare const deviceId: string;

export function refreshAccessToken(): Promise<string> {
  inFlight ??= (async () => {
    try {
      const result = await callRefreshEndpoint(await readRefreshToken(), deviceId);
      await saveRefreshToken(result.refreshToken); // save before anyone else can start a refresh
      return result.accessToken;
    } finally {
      inFlight = null;
    }
  })();
  return inFlight;
}
// The HTTP client calls refreshAccessToken() on a 401, retries the request once with the new
// access token, and sends the user to login if the refresh itself fails.
```

> **Aside: where this lives.** Every request path in the app must go through this function, including background sync and push-triggered work (42.1a, 42.2a). One code path that refreshes on its own, a background task written by another team for example, brings the random logouts back.

The attestation decision, for a Play Integrity verdict the server has already decoded through Google's API:

```ts
type Verdict = {
  requestDetails?: { requestPackageName?: string; requestHash?: string; timestampMillis?: string };
  appIntegrity?: { appRecognitionVerdict?: string; certificateSha256Digest?: string[] };
  deviceIntegrity?: { deviceRecognitionVerdict?: string[] };
};

export function assess(v: Verdict, expect: { pkg: string; requestHash: string; certs: string[]; now: number }) {
  const rd = v.requestDetails ?? {};
  const age = expect.now - Number(rd.timestampMillis);
  // 1. About this request, for this app, and fresh — or nothing else in it can be trusted.
  if (rd.requestPackageName !== expect.pkg || rd.requestHash !== expect.requestHash || !(age >= 0 && age <= 60_000)) {
    return { decision: "deny" as const, reason: "replayed or mismatched verdict" };
  }
  // 2. Our genuine app.
  const app = v.appIntegrity ?? {};
  if (app.appRecognitionVerdict !== "PLAY_RECOGNIZED" || !app.certificateSha256Digest?.some((d) => expect.certs.includes(d))) {
    return { decision: "deny" as const, reason: "unrecognized app" };
  }
  // 3. A doubtful device gets extra checks, not a wall.
  if (!v.deviceIntegrity?.deviceRecognitionVerdict?.includes("MEETS_DEVICE_INTEGRITY")) {
    return { decision: "step-up" as const, reason: "device integrity not met" };
  }
  return { decision: "allow" as const, reason: "ok" };
}
```

> **Aside: monitor mode is the same function.** During the first weeks, record `decision` and `reason` with the tenant and device model, and let every request through. The sign-up abuse above would have shown up as a cluster of `deny` from emulators, and the blocked customers as `step-up` on a few older device models. That's the evidence for setting the enforcement policy, instead of discovering it from sales.

- **RFC 8252, "OAuth 2.0 for Native Apps"**, and **RFC 7636, "Proof Key for Code Exchange" (PKCE)**.
- **RFC 9700, "Best Current Practice for OAuth 2.0 Security"** (January 2025), especially the requirements for refresh tokens issued to public clients.
- **RFC 9449, "OAuth 2.0 Demonstrating Proof of Possession (DPoP)."**
- **Auth0 documentation: "Refresh Token Rotation"**, including its reuse interval, a production example of the grace window.
- **AppAuth for iOS and Android** (openid.net/code/AppAuth), reference libraries for the native login flow.
- **Android Developers: "Play Integrity API"**, including the verdict format and the Android 13+ patch requirement, and **Apple Developer Documentation: "Establishing your app's integrity"** (App Attest).

A **Kotlin** sibling for Android would be worth writing, though it isn't yet: an OkHttp `Authenticator` is the natural place for single-flight refresh, the hardware keystore is where a DPoP key would live, and Play Integrity's request-hash binding is done in the app, where getting it wrong silently weakens the server's checks.

---

The habit to take from this: whenever you design an authentication rule, run it against a phone in a lift. A request that arrives while its response doesn't, retries that overlap, and an app resumed after a week are normal events for a mobile client. Security rules that treat them as attacks will be switched off by the people who have to answer support calls.
