# APIs for Apps You Can't Update: Compatibility Layers, Forced Upgrades and Version-Aware Config

_Module 42 · Mobile Backend Development · 42.3a_

## The Problem

Suppose you run an expense-reporting product for companies. Employees photograph receipts and submit expenses from a mobile app; managers approve them; finance exports them. The web app and the API are deployed together several times a day. The mobile apps ship every two weeks through the app stores. One year's incidents:

**A new status crashes an old app.** The team adds an expense status, `needs_receipt`. The web app handles it. iOS versions older than 4.2 decode `status` into a Swift enum with no fallback case, so a single expense in the new status fails to decode, and the expense list fails to load. For two weeks, until most users update, those users can't see any of their expenses.

**Stricter validation destroys offline work.** Merchant names get a new maximum length of 60 characters, down from 100, to fit an accounting export. Expenses drafted offline with longer names are rejected when the app syncs. The app, which never expected that error for that field, discards them. Employees lose receipts they've already thrown away.

**A security fix nobody can require.** A bug in versions 3.x stores tokens insecurely, and the team needs everyone off 3.x. The API starts returning `410 Gone` to those versions. The 3.x app has no idea what that means, and shows "Something went wrong, try again" forever. Users email support, who can't explain it either, because the app has no way to say "please update."

**A flag turned on for apps without the code.** "Receipt scanning v2" is rolled out with a feature flag. Someone turns it on for 100% of users. The server starts sending the v2 response shape to every app, including versions that don't contain the v2 code. The scan screen breaks for them.

**The enterprise customer on version 4.0.** A 2,000-employee customer manages phones through MDM and approves app updates quarterly. The team raises the minimum version to 4.3 on the 28th. On the 30th, month-end, 2,000 employees can't submit expenses.

The web frontend never had any of these problems, because it's deployed with the API. **Mobile apps are clients you wrote, running code you can no longer change, on devices you can't reach.**

## What It Is

This article is about **API evolution for installed clients**: keeping every app version still in use working while the API changes, and having server-side levers (upgrade prompts, feature flags, kill switches) that were built into the app before you needed them.

Several neighbors are already covered elsewhere. What counts as a breaking change in general is 33.1a; versioning schemes (URL, header, date-based) are 33.1b; deprecating and retiring API versions for external integrators is 33.2a and 33.2b. Feature flags in code are 3.4, and managing them as production changes is 26. This article covers what's different when the client is **your own app**, installed on phones.

## Recognizing the Problem

- A backend change breaks an app version that was released months ago.
- Adding an enum value or tightening validation is treated as safe.
- Some installed app versions can't be told to update.
- Feature flags have no notion of app version.
- You can't say how many active users are on each app version, by tenant.
- Offline work is lost when the server rejects requests an old app considered valid.
- Raising the minimum version surprises customers.
- Response shapes are changed "for the web app" and mobile breakage is found by users.

## How It Works

### 1. The long tail

After a release, traffic from each app version decays slowly, and never reaches zero:

```
share of requests
100% │█
     │█▇▆
 50% │█▇▆▅▄▃
     │█▇▆▅▄▃▂▂▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁  ← old versions linger for months, some for years
   0 └──────────────────────────── weeks after a new release
```

Automatic updates are off on some phones, or run only on Wi-Fi while charging. Old devices can't install versions that require a newer OS. Company-managed phones hold versions until IT approves them. Store review delays even urgent fixes, and staged rollouts take days to reach everyone. So two rules follow:

1. **The server adapts to the app, never the other way around.**
2. **Every lever you might need later must be in the first version you ship.** You can't add an upgrade prompt to apps that are already installed.

### 2. Safe and breaking, for installed apps

| Change | Safe for installed apps? |
|---|---|
| New endpoint, new optional request field | Yes |
| New optional response field | Yes, if the app ignores unknown fields (check your decoder's configuration) |
| **New enum value in a response** | **No**, unless the app maps unknown values to a fallback |
| Removed, renamed or retyped response field | No |
| Optional request field made required | No |
| **Tightened validation** | **No**, and worse with offline queues: work already done is rejected |
| Same shape, different meaning (cents → units) | Worst case: nothing fails, the numbers are just wrong |
| New error codes | Risky, unless the app has a generic fallback |

The first-version checklist that makes most future changes survivable:

- Send `X-App-Platform`, `X-App-Version` and `X-App-Build` on every request.
- Recognize an **upgrade-required** response and show a blocking screen with a store link.
- Fetch **remote config** on start and periodically, with safe built-in defaults.
- Ignore unknown fields; map unknown enum values to an `unknown` case; show a generic message for unknown error codes.
- Respect `Retry-After`, with jittered backoff (42.1b).
- Obey a **wipe** instruction (42.1b).
- Send an `Idempotency-Key` on every non-sync write, since mobile networks lose responses (the pattern is 17.1).
- Refresh tokens one at a time (42.3b).

### 3. Two layers of versioning

| Layer | Mechanism | When |
|---|---|---|
| **Major API version** | In the path: `/mobile/v1/…`, `/mobile/v2/…`, both running until v1 traffic is gone | Rarely: redesigns where translation isn't practical |
| **Per-app-version compatibility** | The server translates responses (and requests) at the edge, based on `X-App-Version` | Every smaller breaking change |

The second layer is how Stripe has kept years of API versions working: each breaking change is recorded **once**, with a transformation from the new shape to the old one. Services always work with the current shape; only the edge translates. Apply the translation everywhere a resource leaves the server, **including sync pulls (42.1a) and push payloads (42.2a)**, which are easy to forget.

Some translations lose information. An old app shown `in_progress` for a `needs_receipt` expense doesn't know about the new status, and if it edits the status, it overwrites `needs_receipt` without meaning to. Two defenses: send only changed fields (42.1a), so editing the notes doesn't touch the status, and make fields read-only for app versions older than the change that introduced them.

Each translation is code and tests. When the minimum supported version rises above a change's version, delete the translation. Raising the minimum regularly keeps the list short.

### 4. Minimum versions and forced upgrades

Decide the policy before you need it, and write it down:

| Question | Typical B2B answer |
|---|---|
| How long is a version supported? | 12 months, or the last 6 releases, whichever is longer |
| When is the minimum raised? | When versions below it fall under ~2% of active users, or immediately for security |
| Warning before blocking? | A soft "please update" banner for 30 days first |
| Who approves a hard block? | Product and support together |
| How do enterprise customers hear? | Tenant admins notified 30 days ahead, so MDM approvals can happen |

A **soft upgrade** (version below the latest) shows a dismissible banner. A **hard upgrade** (version below the minimum) returns the upgrade-required response to every API call except the config and health endpoints, which outdated apps must still reach to learn what to show. On Android, Google Play's in-app updates API supports both flows; on iOS, the app links to the App Store.

**What to keep accepting from blocked versions:** an outdated app may hold hours of offline work. Consider accepting sync pushes from blocked versions (upgraded through the compatibility layer), and blocking pulls and everything else. The user's work is saved, and then they're asked to update.

**The status code.** Many APIs use `426 Upgrade Required`. HTTP defines 426 for switching **protocols**, and requires an `Upgrade` header naming the protocol, so it's a misuse, and some libraries and proxies handle it oddly. What actually matters is a **stable, machine-readable problem type** (RFC 9457) that the app has matched on since its first version, and a status that the app's HTTP layer won't treat as something else. In particular, not `401`, which triggers a token refresh. Pick one, document it, and never change it.

Before blocking anyone, look at the version mix by tenant. If one enterprise customer is stuck on 4.0 because of MDM, you want to call their IT team, not block 2,000 of their employees at month-end.

### 5. Server-side behavior: version-aware remote config

Once an app is installed, the only way to change its behavior without a release is for it to ask the server. A remote-config document, evaluated per request, lets you:

- roll a feature out to one tenant, then 20% of users, then everyone
- turn a broken feature **off** in minutes (a **kill switch**)
- slow down or pause sync during an incident (42.1b)
- announce the minimum and latest versions

Flag evaluation and stable bucketing are covered in 3.4, and governing flags as production changes in 26. The mobile-specific rule is: **every flag rule that enables new behavior carries a minimum app version**. The receipt-scanning incident was a flag with no version condition, and turning it on for everyone enabled it for apps without the code. Kill switches often need the opposite, a **maximum** version, to disable a feature only in releases that have a known bug.

App-store review makes kill switches your only reliable fast lever. Expedited review exists, but isn't guaranteed, and users still have to update.

### 6. Knowing your version mix

Log platform, app version and tenant on every request. A dashboard of active users by version and tenant is what makes the minimum-version policy workable. It also answers "who still calls this endpoint?" before you delete an endpoint or a compatibility entry, and turns a spike in errors from one version right after release into "the bug is in the app," not the API.

## When It's Appropriate

- **Any native or React Native app** with users who don't update instantly, which is all of them.
- **B2B apps on managed devices**, where the tail is longest.
- **Offline-capable apps**, where rejected requests mean lost work.
- **Apps with feature flags**, which need version conditions from the start.

## When It's Unnecessary or Overkill

- **Web frontends** deployed with the API. They're always current.
- **Internal apps distributed through MDM with forced updates**, where you control the version mix directly.
- **A compatibility layer for an app with a few hundred users** and a policy of forcing updates quickly. A strict minimum version may be simpler.
- **Major path versions for every breaking change.** Translation at the edge is usually cheaper than running two APIs.

## Trade-offs

- **Every translation is permanent until the minimum rises.** Each one adds code, tests and a combination to reason about.
- **Lossy translations can corrupt data** when old apps write back what they were shown. Read-only fields and changed-fields-only writes reduce the risk; they don't remove it.
- **Forced upgrades cost goodwill and support time**, and are hard on customers with managed devices.
- **Protecting pushes from blocked versions** means keeping old request shapes working a little longer than old response shapes.
- **Remote config is a production control plane.** A bad value (a sync interval of 18 seconds instead of 1,800) reaches every phone. It needs schema validation, an audit trail and gradual rollout (26).
- **Headers can be forged.** Version headers are for compatibility, not security. A modified app can claim any version; the server still validates everything.

## Alternatives

- **Strict minimum version, raised often.** Simple, and workable for consumer apps with quick update rates. Hard for B2B.
- **Server-driven UI**, where screens are described by the server and rendered by a generic client. Changes skip the app store, at the cost of a constrained UI and a complex, versioned contract of its own.
- **GraphQL**, where clients ask for fields explicitly, so adding fields is always safe. Enum values and removed fields still break old clients, and deprecation still takes the tail's full length.
- **Web views for fast-changing parts of the app.** They update with the server, at the cost of a less native experience.

## How to Achieve It

**Step 1: the first-version checklist**, in the next release, before anything else. Every month without it adds installed apps you can't steer. _Signal to move on:_ the app sends versions, reads config and understands the upgrade response.

**Step 2: a version-mix dashboard** by platform, version and tenant, and a written support policy. _Signal:_ you can see the tail, and a breaking change is coming.

**Step 3: the compatibility layer at the edge**, applied to REST responses, sync pulls and push payloads, with read-only fields for older versions. _Signal:_ you need to require an upgrade.

**Step 4: the version gate**, with exemptions and protected sync pushes, used only after the soft banner and customer notice. Add version conditions to every flag, and review translations for deletion whenever the minimum rises.

## Implementation

TypeScript, in three pieces: the compatibility layer, the version gate, and version-aware flag matching. The compatibility layer and flag rules were tested for a 3.9 app, a 4.1 app and the web client, and for a kill switch aimed at one release.

```ts
export type Client = { platform: "ios" | "android"; appVersion: string } | null; // null: web, always current

export function compareVersions(a: string, b: string): number { // "3.10.0" > "3.9.2"
  const [pa, pb] = [a.split(".").map(Number), b.split(".").map(Number)];
  for (let i = 0; i < 3; i++) if (pa[i] !== pb[i]) return pa[i] < pb[i] ? -1 : 1;
  return 0;
}

type Change<T = any> = {
  id: string; resource: string; introducedIn: string;
  downgrade: (current: T) => T;          // current shape → what older apps understand
  upgradeRequest?: (old: T) => T;        // older apps' requests → current shape
  readOnlyForOlder?: string[];           // fields older apps must not write
};

// Recorded once each, newest first. Delete an entry when the minimum version passes it.
export const CHANGES: Change[] = [
  { id: "expense-status-needs-receipt", resource: "expense", introducedIn: "4.2.0",
    downgrade: (e) => (e.status === "needs_receipt" ? { ...e, status: "submitted" } : e),
    readOnlyForOlder: ["status"] },
  { id: "expense-amount-minor-units", resource: "expense", introducedIn: "4.0.0",
    downgrade: ({ amountMinor, ...e }) => (amountMinor === undefined ? e : { ...e, amount: amountMinor / 100 }),
    upgradeRequest: ({ amount, ...e }) => (amount === undefined ? e : { ...e, amountMinor: Math.round(amount * 100) }) },
];

const olderThan = (client: Client) => (c: Change) => client !== null && compareVersions(client.appVersion, c.introducedIn) < 0;

export function downgrade<T>(resource: string, obj: T, client: Client): T {
  return CHANGES.filter((c) => c.resource === resource).filter(olderThan(client))
    .reduce((acc, c) => c.downgrade(acc), obj);                         // newest change undone first
}

export function upgradeRequest<T extends Record<string, unknown>>(resource: string, body: T, client: Client): T {
  const applicable = CHANGES.filter((c) => c.resource === resource).filter(olderThan(client));
  const blocked = new Set(applicable.flatMap((c) => c.readOnlyForOlder ?? []));
  const filtered = Object.fromEntries(Object.entries(body).filter(([k]) => !blocked.has(k))) as T;
  return applicable.filter((c) => c.upgradeRequest).reverse()          // oldest change applied first
    .reduce((acc, c) => c.upgradeRequest!(acc), filtered);
}
```

> **Aside: why the order reverses.** Responses are undone newest-first, so a 3.9 app gets `needs_receipt` turned into `submitted` before `amountMinor` becomes `amount`. Requests from that app are upgraded oldest-first, so `amount` becomes `amountMinor` before any later change sees the body. Each change only ever has to know its own before and after.

The gate blocks outdated apps everywhere except the endpoints they need to recover, and keeps accepting their offline work:

```ts
import type { Request, Response, NextFunction } from "express";

const EXEMPT = ["/mobile/config", "/health"];
const ACCEPT_FROM_BLOCKED = ["/mobile/v1/sync/push"]; // offline work is saved before the upgrade screen

export function versionGate(getMinimum: (platform: "ios" | "android") => Promise<string | null>) {
  return async (req: Request, res: Response, next: NextFunction) => {
    const client = req.client as Client;               // parsed from X-App-* headers earlier
    if (!client || EXEMPT.some((p) => req.path.startsWith(p))) return next();

    const min = await getMinimum(client.platform);
    if (!min || compareVersions(client.appVersion, min) >= 0) return next();
    if (ACCEPT_FROM_BLOCKED.includes(req.path)) { res.set("X-Upgrade-Required", "true"); return next(); }

    res.status(403).type("application/problem+json").json({
      type: "https://api.example.com/problems/upgrade-required", // what the app has matched on since 1.0
      title: "This version of the app is no longer supported",
      status: 403,
      minSupportedVersion: min,
    });
  };
}
```

> **Aside: the protected push still goes through the compatibility layer.** The sync handler calls `upgradeRequest` on every mutation from an old app, and the validation rules applied are the ones that app was built against, where that's safe. The merchant-name incident is what happens when today's stricter rule meets yesterday's queued work. Old versions get the old limit, with the value truncated or flagged for review on the server rather than rejected.

Version-aware flag rules take a few lines on top of ordinary flag evaluation (3.4):

```ts
type Rule = { if: { minAppVersion?: string; maxAppVersion?: string; tenants?: string[]; percent?: number }; value: boolean };
type Ctx = { appVersion: string; tenantId: string; bucket: (flag: string) => number }; // stable 0–99 per user (3.4)

export function evaluateFlag(flag: string, rules: Rule[], fallback: boolean, ctx: Ctx): boolean {
  const hit = rules.find(({ if: c }) =>
    (!c.minAppVersion || compareVersions(ctx.appVersion, c.minAppVersion) >= 0) &&  // never enable for apps without the code
    (!c.maxAppVersion || compareVersions(ctx.appVersion, c.maxAppVersion) <= 0) &&  // kill switch for one bad release
    (!c.tenants || c.tenants.includes(ctx.tenantId)) &&
    (c.percent === undefined || ctx.bucket(flag) < c.percent));
  return hit ? hit.value : fallback;
}
```

> **Aside: make the minimum version mandatory.** A config schema that rejects any rule setting a flag to `true` without `minAppVersion` would have stopped the receipt-scanning incident at publish time. Validation of config documents belongs with the rest of flag governance (26).

---

The habit to take from this: before shipping any API change, ask which installed app versions will receive it, and what each of them will do with it. The newest app is the one you tested; the oldest one still in use is the one that breaks.
