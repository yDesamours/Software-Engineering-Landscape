# Push in a Multi-Tenant Mobile App: Devices, Tenants, Fan-Out and What Reaches the Lock Screen

_Module 42 · Mobile Backend Development · 42.2a_

## The Problem

Suppose you run a staffing app for hotels. Hotel groups are tenants. Housekeepers, maintenance staff and supervisors use it to see shifts, pick up open shifts, report room issues and receive instructions. Many housekeepers work through an agency for several hotel groups at once. On many floors, staff share a tablet kept at the linen station. Push notifications carry shift changes, urgent room requests and announcements.

The push basics are in place: tokens stored, an inbox as the record, collapse keys, silent pushes treated as hints (14.3). The problems come from what 14.3 didn't have to consider: **devices shared between users, users shared between tenants, and tenants sharing one push pipeline.**

**The shared tablet.** A supervisor logs in on a floor tablet to approve a timesheet, then logs out. The app's unregister call fails because the tablet is on a flaky Wi-Fi connection. Next, a housekeeper logs in on the same tablet, and the server now has the same push token under both users. That evening, the supervisor's notification about a disciplinary meeting appears on the linen-station tablet.

**The agency worker who stopped hearing from one hotel.** The first fix made registration clear the token from every other row with that token. For a housekeeper working for two hotel groups on her own phone, logging into group B's workspace cleared the token from her group A row. She stops receiving group A's shift changes and misses two shifts.

**The topic anyone could join.** To notify all supervisors of a hotel, the app subscribed supervisors' devices to an FCM topic named `hotel_4821_supervisors`. Topics are joined by the app itself. During a security review, a tester with a modified app subscribes to another hotel group's supervisor topic and receives its notifications.

**One tenant's announcement delays everyone else.** A large hotel group sends a benefits announcement to 30,000 staff. It goes through the same queue and the same Firebase project as everything else, which has one quota. For 20 minutes, urgent "room 512 needs towels now" alerts for other hotel groups wait behind it.

**The tap that lands in the wrong place.** A housekeeper signed into group B taps a notification from group A. The link says `/tasks/8812`. The app opens it in group B's context and shows "not found."

**The lock screen.** Room-issue notifications include the guest's name ("Mr. Okafor in 512 reports a leak"). One hotel group's privacy policy forbids guest names outside its systems, and push text passes through Apple's and Google's servers and appears on lock screens.

## What It Is

This article is about the parts of a push system that come from **multi-tenancy and shared devices**:

- **Token binding:** which (tenant, user, device) a push token belongs to, and how that changes on login, logout, reinstall and tenant switching.
- **Fan-out:** turning one domain event into per-device sends, with retries per device and fairness between tenants.
- **Recipient resolution:** deciding recipients on the server, from your data, at send time.
- **Tenant context in deep links**, so a tap opens the right tenant.
- **Content policy per tenant:** how much of a notification's content reaches the lock screen and the push providers.

The general mechanics of push (providers, delivery truth, the inbox as the record, collapse keys and TTLs, silent pushes, permission prompts, token decay) are in 14.3, and the inbox in 14.2. This article assumes both.

## Recognizing the Problem

- Tokens are stored per user, not per device.
- Logout doesn't reliably remove the token, or does so only when the request succeeds.
- The same token appears under more than one user.
- Users in several tenants on one device miss notifications from some of them.
- Group notifications use client-subscribed topics that contain tenant or role names.
- One tenant's large send delays everyone else's urgent notifications.
- Deep links don't identify the tenant.
- Notification text includes personal or confidential data, whatever the tenant's policy.
- Sends happen in a loop inside the function that handles the event.

## How It Works

### 1. Bind tokens to devices, and release them on registration

A push token identifies an **app installation**, not a person. So the row that holds it is keyed by device:

```
devices(tenant_id, device_id, user_id, platform, push_token, push_environment, revoked_at, …)
```

`device_id` is a UUID the app generates on first launch (42.1b). The lifecycle:

| Event | What happens |
|---|---|
| App start, or the OS issues a new token | `PUT /devices/{id}/push-token`: store it for this tenant, user and device |
| Logout | The app deletes the token **before** wiping local data |
| Registration by a **different user** on the same device | The server removes the token from every row belonging to **other users**, in **every tenant** |
| Registration by the **same user in another tenant** | The token stays in both tenants' rows, so both keep notifying her |
| Reinstall (new `device_id`, same token) | The old row for that token is cleared |
| The provider reports the token dead | Remove it, but only if it's still the same token (the app may have sent a newer one) |
| Device revoked (remote wipe) | Registration is refused; senders skip it |

The fix for the shared tablet lives in the fourth row, and it has to work even when the logout request never arrives. That's why the release happens at registration, on the server. It crosses tenants, and row-level security would hide the other tenants' rows from the request, so it runs as one narrow function with elevated rights that can only clear tokens. The fifth row is what the first, over-eager fix broke.

### 2. Plan, then send: two stages

```
domain event (outbox → bus, 41.4a)
      │
      ▼
PLANNER  (one event → many jobs)
  1. resolve recipients from your data (project members, role, tenant)
  2. write inbox rows              — idempotent per (event, user)
  3. check preferences             — the inbox row is written regardless
  4. one delivery row per device with a token — idempotent per (notification, device)
  5. debounced sync hints for devices that should pull (42.1a)
      │ after commit: jobs to a send queue chosen by category
      ▼
SENDER   (one job → one push)
  load delivery → render for the tenant's policy and the user's locale → send → record outcome
```

Two stages give each device its own retry (a transient error for one phone doesn't resend to 3,000 others), let planning (database work) and sending (HTTP to providers with their own limits) scale separately, and make announcements to large tenants safe: the planner writes rows quickly, and senders work through them.

Delivery is **at least once**: a sender that crashes after the provider accepted a message retries it. The collapse key makes a duplicate replace the first on the phone. For the planner, jobs are enqueued after its transaction commits. If the function dies in between, the event is redelivered, and the planner re-enqueues deliveries still marked `queued`. That replay is the mechanism, and it's worth a test.

### 3. Resolve recipients on the server, never through client-joined groups

Recipients come from your data at the moment you plan: the assignee, a project's current members, a tenant's supervisors. **FCM topics are joined by the app**, so a modified app can join any topic whose name it can guess. Topics are fine for genuinely public broadcasts (service status). For anything tenant-specific, resolve on the server and send to tokens.

### 4. Fairness between tenants

A push provider's quota is per project, shared by all your tenants: FCM's default is 600,000 messages a minute, and devices have their own limits. So is your send queue, unless you split it. This is the noisy-neighbor problem again (41.1a):

- **Transactional** categories (shift changes, urgent requests, security) go on one queue; **bulk** categories (announcements, digests) on another, with lower concurrency.
- **Plan large tenants in pages** (for example 500 users per planner run, continuing via a follow-up message), so one announcement isn't one giant transaction.
- **Cap bulk sends per tenant per hour**, and say so in your plans (Module 15).

### 5. Deep links that carry the tenant

Use ordinary `https` links that open the app when installed (Universal Links on iOS, App Links on Android):

```
https://app.example.com/t/grand-harbor/tasks/8812
                          └─ tenant slug (public; not the internal tenant ID)
```

On tap, the app switches to that tenant (opening its local database, 42.1b), checks the session is still valid, and **fetches the resource from the server, which authorizes it again**. A user removed from that hotel since the push was sent should see "no access," not the task. The link is a pointer, never a permission. Including the notification ID lets the app mark the inbox row read and report the open, which gives open rates per category.

### 6. Content policy per tenant

Push content passes through Apple's or Google's servers and is shown on lock screens, so tenants need a say in how much it contains:

| Level | The push contains | Typical tenants |
|---|---|---|
| **Detailed** | "Room issue in 512: leak reported by Mr. Okafor" | Default |
| **Generic** | "New room issue on floor 5" | Hospitality, healthcare, legal, finance |
| **Fetched on device** | Only an ID; the app fetches the text from your API before displaying (an iOS Notification Service Extension, or an Android data message the app renders) | Customers that allow no content through third parties |

Render on the server per recipient: the tenant's content level, the user's locale, and never other people's personal details unless the tenant allows them. Log notification IDs and categories, never payloads.

## When It's Appropriate

- **Any multi-tenant product with push**, and especially one where users belong to several tenants.
- **Shared devices**: kiosks, floor tablets, shift phones, family tablets.
- **Tenants with privacy or regulatory constraints** on what leaves your systems.
- **Tenants of very different sizes** sending through one pipeline.

## When It's Unnecessary or Overkill

- **Single-tenant apps with personal devices**, where 14.3's design is enough.
- **Two-stage fan-out for low volume**, when an event notifies one or two users. A single function that writes the inbox row and sends is fine until volumes grow.
- **Per-tenant content levels** when no tenant has asked for them and nothing sensitive is sent. A single generic policy may do.
- **Separate queues per tenant**, rather than per category, unless one tenant's volume dominates everything.

## Trade-offs

- **Cross-tenant token release needs elevated database rights.** It's a deliberate hole in row-level security, kept safe by being narrow (it can only clear a token) and tested.
- **Two stages mean more rows and more moving parts**: inbox, deliveries, two queues, two functions, and their dead-letter queues.
- **At-least-once delivery means occasional duplicates**, softened by collapse keys, never eliminated.
- **Server-side recipient resolution costs queries at send time** that topics would have avoided. For very large broadcasts, that's the planner's paging.
- **Generic or fetched content lowers engagement.** "New room issue" gets fewer immediate taps than one with details, and fetched content adds a network call before display that can fail.
- **Fairness controls delay bulk sends on purpose.** An announcement to 30,000 people may take many minutes.

## Alternatives

- **Push services** (OneSignal, Braze, Airship, Expo's push service) for segmentation and campaigns. For tenant-private transactional notifications, keep recipient logic in your backend and send only tokens and generic or policy-rendered text through them.
- **Amazon SNS mobile push** or **AWS End User Messaging** (the successor to Amazon Pinpoint's push channel; Pinpoint itself reaches end of support on October 30, 2026) for AWS-only stacks, which still leave token binding to you.
- **Per-tenant apps** (white-label builds per enterprise customer), which separate push credentials and tokens entirely, at the cost of building and shipping many apps.
- **No push for some categories**: badges and in-app indicators from the inbox (14.2) where interruption isn't needed.

## How to Achieve It

**Step 1: key tokens by device and release them at registration**, with the multi-tenant exception and a test for both the shared-device and the agency-worker cases. _Signal to move on:_ tokens are right, but sends are loops inside event handlers.

**Step 2: split planning from sending**, with inbox rows first, delivery rows per device, and server-side recipients. Remove tenant-specific topics. _Signal:_ large tenants' sends affect others.

**Step 3: separate transactional and bulk queues**, page large plans, and cap bulk sends per tenant. _Signal:_ taps land in the wrong tenant, or tenants ask about content.

**Step 4: tenant slugs in deep links with re-authorization on open, and per-tenant content levels** rendered in the sender.

## Implementation

TypeScript, with the one SQL function everything else depends on. The function releases a token from anyone else who holds it, without breaking multi-tenant users:

```sql
-- SECURITY DEFINER: runs as its owner, which must be a role that bypasses RLS (BYPASSRLS),
-- because the other rows may be in other tenants. It can only clear tokens.
CREATE FUNCTION release_push_token(p_token text, p_tenant text, p_user text, p_device uuid)
RETURNS void LANGUAGE sql SECURITY DEFINER SET search_path = public AS $$
  UPDATE devices SET push_token = NULL, push_token_updated_at = now()
   WHERE push_token = p_token
     AND (user_id <> p_user                                  -- another person on this device
          OR (tenant_id = p_tenant AND device_id <> p_device)) -- an old install of this app
$$;
REVOKE ALL ON FUNCTION release_push_token FROM PUBLIC;
GRANT EXECUTE ON FUNCTION release_push_token TO app_user;
```

The token binding, the planner and the rendering below were run against PostgreSQL 16 with fail-closed row-level security, covering the shared tablet (only the current user keeps the token), the agency worker (her token stays in both tenants), a reinstall (the old row in that tenant is cleared), a redelivered event (only still-queued deliveries are enqueued again, and sync hints are debounced) and the three content levels.

> **Aside: why "same user, other tenant" keeps the token.** The agency housekeeper's phone has one token and two tenant rows, both hers. Clearing rows only where `user_id` differs keeps both. The shared tablet has one token and two users' rows, and the supervisor's is cleared the moment the housekeeper registers, whether or not the supervisor's logout ever reached the server.

The planner resolves recipients from the database, writes the inbox before anything else, and routes jobs by category:

```ts
import type pg from "pg";

type Job = { kind: "alert" | "sync"; tenantId: string; deviceId: string; notificationId?: string };
const BULK = new Set(["announcements", "digests"]); // everything else is transactional

export async function plan(
  tx: pg.PoolClient, // a transaction already scoped to the event's tenant (5.2a)
  e: { eventId: string; tenantId: string; tenantSlug: string; category: string; projectId: string;
       taskId: string; actorId: string; mandatory: boolean },
) {
  const jobs: Job[] = [];
  const { rows: recipients } = await tx.query(          // from our data, at planning time
    `SELECT user_id FROM project_members
      WHERE tenant_id = $1 AND project_id = $2 AND removed_at IS NULL AND user_id <> $3`,
    [e.tenantId, e.projectId, e.actorId]);

  for (const { user_id } of recipients) {
    const { rows: [n] } = await tx.query(                // inbox first; idempotent per (event, user)
      `INSERT INTO notifications (tenant_id, user_id, source_event_id, category, deep_link, collapse_key)
       VALUES ($1, $2, $3, $4, $5, $6)
       ON CONFLICT (tenant_id, source_event_id, user_id) DO UPDATE SET category = EXCLUDED.category
       RETURNING id`,
      [e.tenantId, user_id, e.eventId, e.category,
       `https://app.example.com/t/${e.tenantSlug}/tasks/${e.taskId}`, `${e.category}:${e.taskId}`]);

    if (!e.mandatory && !(await wantsPush(tx, e.tenantId, user_id, e.category))) continue;

    const { rows: devices } = await tx.query(            // one delivery per device; idempotent
      `INSERT INTO notification_deliveries (tenant_id, notification_id, device_id)
       SELECT tenant_id, $2, device_id FROM devices
        WHERE tenant_id = $1 AND user_id = $3 AND push_token IS NOT NULL AND revoked_at IS NULL
       ON CONFLICT (tenant_id, notification_id, device_id)
       DO UPDATE SET status = notification_deliveries.status   -- no-op, so RETURNING includes existing rows
       RETURNING device_id, status`,
      [e.tenantId, n.id, user_id]);
    for (const d of devices) {
      if (d.status === "queued") jobs.push({ kind: "alert", tenantId: e.tenantId, deviceId: d.device_id, notificationId: n.id });
    }
  }

  const { rows: hints } = await tx.query(                // at most one sync hint per device per 2 minutes
    `UPDATE devices d SET last_sync_hint_at = now()
       FROM project_members m
      WHERE d.tenant_id = $1 AND m.tenant_id = d.tenant_id AND m.project_id = $2
        AND m.user_id = d.user_id AND m.removed_at IS NULL
        AND d.push_token IS NOT NULL AND d.revoked_at IS NULL
        AND (d.last_sync_hint_at IS NULL OR d.last_sync_hint_at < now() - interval '2 minutes')
      RETURNING d.device_id`, [e.tenantId, e.projectId]);
  for (const h of hints) jobs.push({ kind: "sync", tenantId: e.tenantId, deviceId: h.device_id });

  return { jobs, queue: BULK.has(e.category) ? "push-bulk" : "push-transactional" };
}

async function wantsPush(tx: pg.PoolClient, tenantId: string, userId: string, category: string) {
  const { rows: [p] } = await tx.query(
    "SELECT push FROM notification_preferences WHERE tenant_id = $1 AND user_id = $2 AND category = $3",
    [tenantId, userId, category]);
  return p ? p.push : true; // no row: the category's default
}
```

> **Aside: why existing deliveries are returned too.** If the planner dies after committing but before enqueueing, the event is redelivered and the planner runs again. The no-op `DO UPDATE` makes `RETURNING` include deliveries created the first time, and any still `queued` are enqueued again. The sender skips deliveries already `sent`, so a job enqueued twice sends once. A small sweeper that re-enqueues `queued` deliveries older than a few minutes catches any other path that loses a job.

The sender renders per tenant policy. The content decision happens here, once, for every channel that uses it:

```ts
type Policy = "detailed" | "generic" | "fetch";

export function renderAlert(
  n: { id: string; category: string; deepLink: string; collapseKey: string; params: { room?: string; guest?: string } },
  policy: Policy,
  t: (key: string, vars?: Record<string, string>) => string, // the recipient's locale
) {
  const data = { notificationId: n.id, link: n.deepLink }; // enough for the app to open and fetch
  if (policy === "fetch") return { data, mutableContent: true, collapseKey: n.collapseKey }; // text fetched on device
  const body = policy === "generic"
    ? t(`${n.category}.generic`)                                   // "New room issue"
    : t(`${n.category}.detailed`, { room: n.params.room ?? "" });  // "Room issue in 512" — no guest name
  return { title: t(`${n.category}.title`), body, data, collapseKey: n.collapseKey };
}
```

> **Aside: the guest's name is never in the template.** Even at the "detailed" level, the template for room issues takes the room, not the guest. Personal data of people other than the recipient is opt-in per tenant, with its own template, not a default that tenants have to discover and turn off.

---

The habit to take from this: for every notification, ask three questions. On which device could this appear, and who is holding it right now? Who decided the recipients, and could the app have influenced that? What does the lock screen show, and has this tenant agreed to it?
