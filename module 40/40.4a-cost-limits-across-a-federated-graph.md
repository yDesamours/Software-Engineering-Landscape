# Cost Limits Across a Federated Graph

_Module 40.4a — GraphQL Advanced Patterns_

## The Problem

Suppose you run the API for a property listings platform. It's a federated graph (40.1a) with six subgraphs, and the ones that matter here are:

- **listings**: the database of homes for sale. Cheap per field, large capacity.
- **search**: an Elasticsearch cluster behind a subgraph. Expensive per query, and sized for about 400 searches a second.
- **mortgage**: estimates monthly payments by calling an external rates provider, which bills $0.002 per call.
- **commute**: travel times from a home to a place the user chooses, backed by a routing API.

The router enforces the cost limit from 8.3b: every operation is scored before it runs, and anything over 1,000 points is rejected. The weights were set once, graph-wide, by the platform team, using the usual defaults: each object costs 1, scalars cost 0, and list sizes come from pagination arguments.

In one quarter, three things went wrong that the limit was supposed to prevent.

**A bill.** A partner's integration ran this query 200,000 times a day:

```graphql
query {
  search(filter: $f, first: 50) {
    listings { id price photos(first: 3) { url } mortgageEstimate { monthly } }
  }
}
```

It scored about 250 points, well under the limit. The score counted `mortgageEstimate` as one object per listing, the same as a photo. It was actually one paid external call per listing:

```
200,000 queries/day × 50 listings × $0.002   = $20,000 per day
```

**A saturated cluster.** The web app added a filter panel with facet counts (`search { facets { name buckets { value count } } }`). Facet buckets are small objects and counts are scalars, so the query scored about 60. Each one ran several aggregations across the whole index. At peak, the search cluster hit 100% CPU while the router's dashboard showed average operation cost at a comfortable 120.

**A cost the client never asked for.** `Listing.commuteTime(to:)` comes from the commute subgraph, which `@requires` the listing's coordinates from listings (40.1a). A query for 50 listings with `commuteTime` produced one fetch to search, one `_entities` fetch to listings for the coordinates, and one to commute with 50 routing calls. The client's query selected none of the coordinates, and the score counted `commuteTime` as a scalar: zero.

The single score failed in the same way each time. It measured the *shape of the query* in one currency and compared it with one limit, while the cost actually landed in *specific subgraphs*, each with its own capacity, its own unit of cost, and fetches the query itself didn't mention.

## What It Is

What these incidents call for is **federation-aware cost control**: estimating an operation's cost *per subgraph*, from weights that each subgraph's owners declare, and enforcing a budget per subgraph as well as for the whole operation.

It rests on 8.3b's ideas, which aren't repeated here: cost comes from multiplicity more than depth, estimates admit and actuals account, and checks belong before execution. What federation adds is three things:

- **The weights belong to the subgraphs.** The team that runs the mortgage subgraph knows a field costs a paid call. The platform team doesn't.
- **The estimate has to follow the query plan, not the query.** The plan contains fetches the client never selected (the coordinates for `commuteTime`), and multiplies entity fetches by the list sizes above them.
- **Limits are per subgraph.** A query can be cheap for the graph and still too expensive for one subgraph.

There's a standard for the weights. The **IBM GraphQL Cost Directive specification** defines `@cost` (a weight on a type, field, or argument) and `@listSize` (how to size a list from its arguments or an assumed size). Apollo's router, WunderGraph Cosmo, and Hive's router and gateway all implement it, and at least Apollo's and Hive's routers now support per-subgraph limits on top of the operation-wide one.

## Recognizing the Problem

- One cost limit protects the whole graph, and its weights were set centrally.
- A subgraph with small capacity or a per-call bill has been overloaded or overspent while the router reported normal costs.
- Expensive fields are scalars or small objects, so they score close to zero.
- Fields with `@requires` or on entities reached through lists trigger fetches no cost estimate accounts for.
- Subgraph teams can't say what a field costs in the graph's cost units, or whether it has a weight at all.
- A subgraph accepts `_entities` requests with any number of representations.
- Estimated and actual costs have never been compared.

## How It Works

### Weights live with the subgraph that pays

In a federated graph, the schema's cost annotations should be written by the teams who know the costs, in their own subgraph schemas, and composed into the supergraph like any other directive:

```graphql
# mortgage subgraph
type Listing @key(fields: "id") {
  id: ID!
  mortgageEstimate: MortgageEstimate @cost(weight: 50)       # one paid external call
}

# search subgraph
type Query {
  search(filter: SearchFilter!, first: Int!): SearchResult
    @cost(weight: 20)                                         # one Elasticsearch query
    @listSize(slicingArguments: ["first"], sizedFields: ["listings"])
}
type SearchResult {
  listings: [Listing!]!
  facets: [Facet!]! @cost(weight: 40)                         # aggregations over the index
}
```

Weights are in the graph's shared unit, "points," but what a point *means* differs by subgraph, which is exactly why a single limit can't be right for all of them. That's the subject of the next sections. For now, the change is who writes the numbers: the mortgage team puts 50 on `mortgageEstimate` because they know it's a paid call, and a schema change that adds an expensive field without a weight can be caught by a lint rule in 40.1b's pipeline.

One composition detail matters. If two subgraphs can both resolve a field (`@shareable`), their costs may differ, since one might read from a cache and the other from a slow database. Some routers keep weights per subgraph for the same field, so the estimate follows whichever subgraph the plan actually uses. If yours merges them into one weight, use the higher one.

### Estimate from the plan, per subgraph

A query-only estimate, which is what 8.3b built, walks the client's query and multiplies weights by list sizes. In a federated graph, that misses what the router adds. The estimate that matches reality walks the **query plan** (40.3b) and assigns each fetch's cost to the subgraph that serves it:

```
search(first: 50) { listings { mortgageEstimate { monthly }  commuteTime(to: $w) } }

plan                                          multiplier   weight        cost → subgraph
Fetch(search)     search(first: 50)                 1       20             20 → search
Flatten(listings.@) Fetch(listings)  lat, lng       50       1 × 50         50 → listings   (from @requires)
Flatten(listings.@) Fetch(mortgage)  estimate       50      50 × 50      2,500 → mortgage
Flatten(listings.@) Fetch(commute)   commuteTime    50      30 × 50      1,500 → commute
                                                                     ─────────
                                                    operation total   4,070
```

Two things show up that a query-only estimate hides. The `listings` fetch comes entirely from `@requires`: the client didn't select latitude or longitude, but the plan fetches them for 50 listings. And each entity fetch is multiplied by the list size above it: the `Flatten` path `listings.@` means "once per item of `listings`," which is 50.

This has a practical consequence: the estimate must run *after planning*. Planning is cached (40.3b), so that's usually cheap, but it means cost checks can't live in the validation step where 8.3b put them for a single server. They move to the point where the router has the plan and hasn't yet made the first fetch.

### Limits per subgraph, and what "over" means

With cost per subgraph, each subgraph can have its own budget per operation: mortgage 500, commute 800, search 400, and so on, reflecting what each can afford. The partner's query now fails because mortgage's share is 2,500, even though its operation total might have passed a generous graph-wide limit.

When one subgraph's share is over budget, the router has two choices:

- **Reject the whole operation.** Simple and predictable: the client gets an error and no data, as with 8.3b's limit.
- **Skip that subgraph.** Execute the rest of the plan, return `null` for the over-budget subgraph's fields, and include an error explaining why. Apollo's router does this for its per-subgraph limits. The listings arrive, and `mortgageEstimate` is `null` on each.

Skipping is better for the user when the expensive part is optional, and it's where 8.1a's nullability decision comes back: if `mortgageEstimate` were declared non-null, skipping it would null each listing, and possibly the whole search result. Fields served by subgraphs with tight budgets should be nullable, which 40.1a already recommended for fields that cross subgraph boundaries.

### Budgets over time, per subgraph

A per-operation limit stops one huge request. It doesn't stop 200,000 moderate ones. For that, 8.3b's cost-denominated rate limits apply, with the same federation twist: the budget is per account *per subgraph*. The partner gets, say, 50,000 mortgage points per hour and a much larger allowance for listings. When mortgage's budget runs out, the partner's queries either lose that field (skip) or are rejected, and nothing else about their usage is affected.

For subgraphs whose cost is money, like mortgage, the budget is effectively a spending limit, and it's worth stating it that way to the partner and in your plan tiers. "You may request 25,000 mortgage estimates per day" is clearer than a number of points.

### Actual cost, and which "actual"

After execution, the router can measure what actually happened, using real list sizes instead of estimates. In a federated graph there are two reasonable definitions, and Apollo's router offers both:

- **By response shape:** apply the cost rules to the final response the client received. This matches what the client asked for.
- **By subgraph:** apply them to each subgraph's actual responses and add them up. This includes `@requires` fetches, extra entity fetches, and anything the router did on the client's behalf.

For protecting subgraphs, "by subgraph" is the one that matters, because it's what each subgraph actually served. Comparing it with the estimate (routers typically report both, and the difference) is how you find weights that are wrong: a field whose actual cost is consistently five times its estimate needs a higher weight or a better `@listSize`.

### Subgraphs protect themselves too

The router's estimate is only as good as its weights and list-size guesses, and 40.1a's rule that subgraphs accept traffic only from the router can fail through a misconfiguration. So each subgraph keeps its own hard limits, which don't depend on the router being right:

- **Cap representations per `_entities` request.** A plan over a list of 5,000 can send 5,000 representations in one request, and a subgraph that loads each one is doing 5,000 units of work from one call. Reject or split above a fixed number.
- **Cap page sizes and require slicing arguments.** The same rule 8.3b gave for list fields, enforced in the subgraph's own resolvers.
- **Budget expensive resolvers per request.** The mortgage subgraph can refuse to make more than, say, 100 rate calls per request, however it was asked.
- **Signal overload clearly.** When a subgraph is saturated, a fast `503` or `429` lets the router fail those fields quickly, or trip a circuit breaker (36.3), instead of queueing work that will time out anyway.

This is defense in depth in the ordinary sense: the router makes the good decision most of the time, and the subgraph makes sure the bad decision can't be catastrophic.

### What stays at the router

Some checks don't need federation awareness and belong at the router only: request body size, parser limits, depth, alias counts, and operation batch size. 8.3b covered them. They run once, on the client's document, before any planning, and there's no reason for each subgraph to repeat them on the router's generated fetches.

### Keeping weights honest

Weights drift. A field that was cheap becomes expensive when its implementation changes, and nobody updates the directive. The same pipeline that governs the schema (40.1b) can govern costs:

- **Lint:** every list field has `@listSize` or a required slicing argument, and fields in subgraphs marked as expensive (external calls, aggregations) have explicit weights.
- **Cost regression checks:** estimate every trusted document's per-subgraph cost against the proposed supergraph, as 40.3b did for plan depth, and flag changes that raise any subgraph's share significantly.
- **Calibration:** review fields where actual cost diverges from estimated cost, from the router's telemetry, on a schedule.

## When It's Appropriate

- **Subgraphs with very different capacities or unit costs.** A search cluster sized for hundreds of queries a second next to a database that handles tens of thousands, or a subgraph that pays per call. One limit can't be right for both.
- **Open or partner APIs on a federated graph.** External clients will find the expensive combination, and per-subgraph budgets let you sell access to expensive subgraphs separately.
- **Heavy use of `@requires` or entities in long lists.** The plan-level estimate is the only one that sees the hidden fetches.
- **Subgraph teams that own their capacity.** When teams are paged for their subgraph's load, they should own the weights and budgets that protect it.

## When It's Unnecessary or Overkill

- **First-party clients only, with trusted documents.** If every operation is known in advance, per-subgraph costs can be checked at build time (40.1b, 40.3b), and runtime enforcement is a backstop that rarely fires. Keep hard subgraph-side caps anyway.
- **Subgraphs with similar, generous capacity.** If no subgraph is much more fragile or expensive than the others, one well-calibrated operation-wide limit, as in 8.3b, does most of the job.
- **Weights before measurement.** Detailed per-field weights set by guesswork give false precision. Start in measure mode, look at actual costs, and add weights where the data shows expensive fields.

## Trade-offs

**Estimation moves later and costs more.** A per-subgraph estimate needs the query plan, so it runs after planning instead of during validation. That's usually fine with cached plans, but a rejected operation has now consumed planning time, and a flood of distinct, expensive-to-plan operations costs more before it's rejected.

**Weights become a shared responsibility that can be neglected.** Distributing weights to subgraph teams puts them in the right hands, and also in eleven places where they can be forgotten. Lint rules and calibration reviews are what keep it from decaying.

**Skipping subgraphs produces partial data.** Returning `null` for an over-budget subgraph is friendlier than rejecting, but clients must handle it, and nullability choices across subgraphs determine whether a skip removes one field or a whole page.

**Budgets per subgraph per account multiply the configuration.** Six subgraphs times four plan tiers is 24 numbers to set, explain, and change, plus the support conversations when a partner hits one. Keep most subgraphs on a default and set explicit budgets only where capacity or money demands it.

**Estimates will be wrong sometimes.** List sizes are guesses until execution. A generous estimate rejects legitimate queries, and a stingy one lets expensive ones through. Measure mode, the estimate-versus-actual comparison, and subgraph-side caps are all there because the estimate can't be trusted on its own.

**Router-specific behavior.** The directives are standardized, but how routers compose weights across subgraphs, compute actual cost, and act on per-subgraph limits differs between vendors. Migrating routers means re-verifying all of it.

## Alternatives

**One operation-wide limit, carefully weighted.** 8.3b's approach with better weights: put 50 on `mortgageEstimate` and 40 on `facets` in a single scoring model. It catches much of the opening's trouble. It can't express that search has a tenth of listings' capacity, and it still misses fetches added by the plan unless it walks the plan.

**Subgraph-local limits only.** Each subgraph protects itself with request caps and rate limits, and the router does nothing cost-related. It's robust and simple to reason about, but the client learns about limits only from partial failures during execution, and the router can't reject a hopeless operation before it has already loaded work onto three subgraphs.

**Trusted documents only.** Allow only registered operations (8.3c), and review their cost when they're registered. For first-party APIs, this removes most of the problem. It doesn't apply to partners and public APIs, which is where cost problems usually come from.

**Separate products for expensive capabilities.** Instead of exposing `mortgageEstimate` on every listing in a search result, offer it as a single-listing field or a separate, metered endpoint. Sometimes the right fix for an expensive field is to make it impossible to request in bulk.

## How to Achieve It

**Level 0: measure per subgraph.** Turn on the router's cost calculation in measure mode, with actual cost by subgraph, and add each subgraph's request volume and latency alongside. Find the fields and subgraphs where cost concentrates. *Next step when:* you know which subgraphs are fragile or expensive, and which fields drive their load.

**Level 1: subgraph self-protection.** Cap `_entities` representations, page sizes, and expensive calls per request in each subgraph, and make overloaded subgraphs fail fast. *Next step when:* no single request can do unbounded work in any subgraph.

**Level 2: weights from owners.** Have each subgraph team add `@cost` and `@listSize` where the data from Level 0 shows expensive fields, and add lint rules for new ones. Compare estimated with actual cost and adjust. *Next step when:* estimates track actuals within a small factor for your main operations.

**Level 3: per-subgraph limits.** Enforce an operation-wide limit plus per-subgraph limits for the fragile and expensive subgraphs, choosing reject or skip per subgraph. Make those subgraphs' fields nullable if they aren't. *Next step when:* the remaining problem is volume over time rather than single expensive operations.

**Level 4: per-subgraph budgets over time.** Cost-denominated rate limits per account per subgraph, published as part of your plan tiers, especially for subgraphs with per-call costs.

## Implementation

TypeScript, in two places: a per-subgraph estimate computed from the query plan, which is the mechanism routers implement and a useful CI check in its own right, and a subgraph-side guard that doesn't trust anyone's estimate. Routers with per-subgraph demand control do the first at runtime; the code shows what they're doing.

The per-subgraph estimate, walking the plan from 40.3b:

```ts
type Costs = Map<string, number>;   // subgraph name → estimated points

function estimatePlan(node: PlanNode, multiplier: number, ctx: EstCtx, out: Costs): void {
  switch (node.kind) {
    case "Sequence":
    case "Parallel":
      for (const n of node.nodes) estimatePlan(n, multiplier, ctx, out);
      return;
    case "Flatten": {
      const m = multiplier * listMultiplier(node.path, ctx);        // ← aside 1
      estimatePlan(node.node, m, ctx, out);
      return;
    }
    case "Fetch": {
      const schema = ctx.subgraphSchemas.get(node.serviceName)!;
      const perItem = estimateSelection(schema, node.operation, ctx.variables); // IBM cost rules
      out.set(node.serviceName, (out.get(node.serviceName) ?? 0) + perItem * multiplier); // ← aside 2
      return;
    }
    default:
      if ("node" in node && node.node) estimatePlan(node.node, multiplier, ctx, out);  // Condition, Defer
  }
}

function overBudget(costs: Costs, budgets: Budgets) {
  return [...costs].filter(([subgraph, cost]) => cost > budgets.perOperation(subgraph));
}
```

**Aside 1: the multiplier is where entity fetches get expensive.** A `Flatten` path like `["search", "listings", "@"]` means "run this fetch for each item of `search.listings`." `listMultiplier` sizes each `@` segment from the client's query: here, `search`'s `@listSize(slicingArguments: ["first"])` resolves to the `first: 50` the client sent. A path with two `@` segments multiplies twice, which is how a query that looks like "50 results with 3 photos each" becomes 150 representations to the media subgraph. Without `@listSize` on a list, the multiplier falls back to a default guess, which is why the lint rule in 40.1b's pipeline asks for it.

**Aside 2: costs are charged to the subgraph that does the work.** The coordinates fetch for `commuteTime` is charged to listings even though the client never selected coordinates, because listings is what serves it. That's what makes per-subgraph budgets protect the right thing, and it's the part a query-only estimate can't do. The per-item estimate uses the *subgraph's* schema, so a `@cost` that the mortgage team put on `mortgageEstimate` applies when the plan fetches it from mortgage, and a different weight for the same field in another subgraph applies there.

A guard inside the mortgage subgraph, which doesn't depend on the router's estimate being right:

```ts
const MAX_REPRESENTATIONS = 200;
const MAX_RATE_CALLS_PER_REQUEST = 100;

const guardPlugin: ApolloServerPlugin<Ctx> = {
  async requestDidStart() {
    return {
      async didResolveOperation({ request }) {
        const reps = request.variables?.representations;
        if (Array.isArray(reps) && reps.length > MAX_REPRESENTATIONS) {        // ← aside 3
          throw new GraphQLError(`too many representations: ${reps.length}`, {
            extensions: { code: "SUBGRAPH_LIMIT" },
          });
        }
      },
    };
  },
};

// in the resolver, a per-request budget for the paid call
async function mortgageEstimate(listing: ListingRef, _: unknown, ctx: Ctx) {
  if (++ctx.rateCalls > MAX_RATE_CALLS_PER_REQUEST) return null;             // ← aside 4
  return ctx.loaders.rate.load({ price: listing.price, region: listing.region });
}
```

**Aside 3: the representations cap is the subgraph's own depth limit.** Clients can't send `_entities` requests (only the router can, if 40.1a's network rule holds), so the representation count is set by the router's plan, which is set by the client's list sizes. A client that finds a way to make a list of 10,000 produces a 10,000-representation request here. The cap turns that into an error in one field, not 10,000 paid calls. Choose the number from what the subgraph can serve within its timeout, not from what clients usually need.

**Aside 4: returning `null` instead of throwing keeps the rest of the response.** When the per-request budget runs out, the remaining listings get `null` for `mortgageEstimate`, and the ones already estimated keep their values. That's only safe because `mortgageEstimate` is nullable. If it weren't, this line would null each listing and possibly the whole search result, so the nullability of expensive fields is as much a cost-control decision as a schema one.

## Further Reading

- **The IBM GraphQL Cost Directive specification** (ibm.github.io/graphql-specs/cost-spec.html): `@cost`, `@listSize`, default weights, and how slicing arguments and sized fields work. The common language every router's cost control uses.
- **Apollo router documentation, "Demand Control"**: estimated and actual cost, `by_subgraph` versus `by_response_shape` actual cost, measure and enforce modes, cost telemetry, and per-subgraph limits that skip the subgraph instead of rejecting the operation.
- **Hive Router, "Demand Control" documentation and its June 2026 product update**: per-subgraph budgets with their own enforcement modes, and actual cost as observability only.
- **WunderGraph Cosmo documentation, "Cost Control"**: estimated and actual cost headers, and per-subgraph weights for the same field coordinate.
- **Shopify's GraphQL Admin API documentation on calculated query costs**: the best-known public example of charging operations in points against a refilling budget, which is the model for Level 4.
- **In this collection:** 8.3b (the cost model this article extends: multiplicity, estimate-then-account, where checks belong), 40.1a (`@requires`, entity fetches, and network isolation of subgraphs), 40.1b (lint and regression checks), 40.3b (query plans and planning budgets), 8.1a (nullability as blast radius), 36.3 (circuit breakers for overloaded subgraphs), Module 18 (rate limits).

A Go sibling isn't needed: the estimate is a tree walk and the guard is a counter, and both look the same in any language. What would be worth writing is a short piece on setting weights from measurements, turning a subgraph's latency and resource profile into `@cost` values, but that's a calibration guide rather than a sibling.

---

The habit to take from this: whenever one limit protects many resources, check whether they share a currency. A single score in points worked while every subgraph cost roughly the same per point. It stopped working when one resource was a search cluster and another was an invoice. Limits should be expressed in the currency of the thing they protect, and enforced where that thing can see them.
