# Incremental Delivery: `@defer` and `@stream`

_Module 40.3a — GraphQL Advanced Patterns_

## The Problem

Suppose you run the storefront API for an online retailer. The product page is one query, assembled from each component's fragment the way 8.1a described:

```graphql
query ProductPage($id: ID!) {
  product(id: $id) {
    ...ProductHeader        # name, images, rating          ~20 ms
    ...PriceAndStock        # price, stock, delivery badge  ~40 ms
    ...ShippingEstimate     # carrier API                   ~400 ms, p99 2 s
    ...Recommendations      # ML ranking service            ~300 ms, p99 1.8 s
    ...ReviewList           # first page of reviews         ~60 ms
  }
}
```

A GraphQL response is one JSON object, sent when every field is resolved. So the whole page waits for its slowest part:

```
field ready at   20  40  60 ms .............................. 400 ms (p50) ... 2 s (p99)
                 │   │   │                                     │
response sent    ───────────────────────────────────────────────►  one payload, at the slowest field
what the user    blank .......................................  everything at once
needs first:     header + price (ready at 40 ms)
```

The part a shopper needs to decide anything, the name, photos, price, and "in stock," is ready in 40 ms. They wait 400 ms at the median and two seconds at the p99 for the carousel below the fold and a shipping estimate they may never scroll to.

The team tried the obvious fixes, and each cost something.

**Split the query.** Three queries instead of one: the top of the page, shipping, and recommendations. The fast part now arrives quickly. But the page lost 8.1a's main benefit: components no longer contribute fragments to one screen query, because someone has to decide which component goes in which query and keep that decision current. On mobile, each query also pays its own connection and request overhead, and the three queries share nothing on the server, so the product is loaded three times.

**Time out the slow fields.** Give recommendations 250 ms and return `null` if they aren't ready. The page is fast, and the carousel is empty for one visitor in five, including on the high-traffic days when recommendations are worth the most.

What the page actually wants is to **keep one query, but send the fast parts as soon as they're ready and the slow parts when they're ready.**

## What It Is

That's **incremental delivery**, and GraphQL has two directives for it. **`@defer`** on a fragment says "don't hold the response for this; send it later." **`@stream`** on a list field says "send the first few items now, and the rest as they're ready." The response then becomes a sequence of payloads over one HTTP response: an initial payload with everything not deferred, followed by patches that fill in the rest.

```graphql
query ProductPage($id: ID!) {
  product(id: $id) {
    ...ProductHeader
    ...PriceAndStock
    ...ReviewList
    ...ShippingEstimate @defer(label: "shipping")
    ...Recommendations  @defer(label: "recs")
  }
}
```

Two status notes matter before going further. First, **`@defer` and `@stream` are not yet in the GraphQL specification.** They've been in development for years, and the proposal is an open spec draft. `graphql-js` v17, released in June 2026, ships them as an explicitly experimental execution function. Second, **the response format changed along the way**, and at least two formats are in production use: the one from the August 2022 draft, which Apollo's router and many clients implement, and the newer format with deduplication that `graphql-js` v17 implements. Client and server must agree on which one they speak. This article describes the newer format and points out where the older one differs.

The neighbor to separate is a **subscription** (40.2a). Both produce several payloads, but a subscription is open-ended and driven by events, while an incremental response is one operation whose result is split in time and ends when the result is complete.

## Recognizing the Problem

- A screen's response time is dominated by one or two fields, and those fields aren't what users need first.
- Field-level traces show a long tail on a few resolvers (external APIs, ML services, aggregates) and fast everything else.
- Teams have split screen queries into several to get the fast parts out, and now coordinate which fragment goes where.
- Resolvers have timeouts that return `null`, and users see empty sections under load.
- p99 response time is several times the p50, and the difference is always the same few fields.
- Server-side rendering waits for data the first viewport doesn't show.
- Long lists are paginated only to get the first items out quickly, not because users page through them.

## How It Works

### The directives

```graphql
directive @defer(if: Boolean! = true, label: String) on FRAGMENT_SPREAD | INLINE_FRAGMENT
directive @stream(if: Boolean! = true, label: String, initialCount: Int! = 0) on FIELD
```

`@defer` goes on a fragment, spread or inline. Everything inside it may arrive after the initial payload. `@stream` goes on a list field. The first `initialCount` items come in the initial payload, and the rest arrive in later payloads. Both take `if`, so a client can turn them off with a variable (for example, for a server-rendered page that should arrive whole, or for a crawler), and `label`, which is only there to help the client identify which pending piece is which.

### The response: an initial payload, then patches

With the newer format, the product page's response arrives as three payloads:

```json
{ "data": { "product": { "name": "Trail Runner 3", "price": { "amount": 129 }, "inStock": true, "reviews": [ … ] } },
  "pending": [ { "id": "0", "path": ["product"], "label": "shipping" },
               { "id": "1", "path": ["product"], "label": "recs" } ],
  "hasNext": true }

{ "incremental": [ { "id": "0", "data": { "shippingEstimate": { "days": 2 } } } ],
  "completed":   [ { "id": "0" } ],
  "hasNext": true }

{ "incremental": [ { "id": "1", "data": { "recommendations": [ … ] } } ],
  "completed":   [ { "id": "1" } ],
  "hasNext": false }
```

The initial payload has the non-deferred data, plus a `pending` list announcing what's still coming and where it will go (`path`). Each later payload carries `incremental` entries, which are data to merge at a pending entry's path, and `completed` entries, which say a pending piece is finished. `hasNext: false` ends the response. For `@stream`, an incremental entry carries `items` to append to the list instead of `data` to merge.

The older 2022 format differs in shape rather than idea: each patch carries its own `path` and `label` instead of referring to a `pending` ID, and there's no `completed` notice. It also has one practical difference, covered next.

### Deduplication

A field can be selected both inside and outside a deferred fragment. `ProductHeader` selects `name`, and so might `Recommendations`. The newer format never sends a field twice: if `name` was in the initial payload, the deferred patch doesn't repeat it, and an entry's `subPath` says where within the pending path its data belongs. The 2022 format could resend overlapping fields, which on pages with heavy fragment reuse meant noticeably larger responses. If you're choosing a format, this is the main reason the newer one exists.

### Transport: one HTTP response, several parts

Over HTTP, the usual transport is a `multipart/mixed` response: one response, streamed with chunked transfer encoding on HTTP/1.1 or as a normal stream on HTTP/2, with each payload as a part separated by a boundary. The GraphQL-over-HTTP working group has a draft describing it. The client asks for it in `Accept` (with the older format, Apollo's convention is `multipart/mixed;deferSpec=20220824`), and a server that can't do incremental delivery falls back to a single JSON response. Server-sent events and the `graphql-ws` WebSocket protocol can carry the same payloads.

Everything between server and client has to pass the parts through as they arrive. That's the most common reason incremental delivery "doesn't work" in production after working locally: a reverse proxy buffers the response, a compression middleware waits for the whole body before compressing, or a CDN collects the full response before forwarding it. The user then gets all three payloads at once, at the time of the slowest one, which is the original problem with extra overhead.

### Deferred means sent later, not necessarily started later

`@defer` controls when data is *delivered*. When the deferred work *starts* is a separate question, and implementations differ:

- **Start after the initial payload.** Simple, and the initial payload gets all the server's attention. But the slow work only begins once the fast work is finished, so the deferred part arrives at *initial time + slow time*, which is later than without `@defer`.
- **Start immediately, deliver later ("early execution").** The deferred work runs in parallel with everything else, and the deferred part arrives at about the same time it would have without `@defer`, while the initial payload goes out as soon as it's ready. `graphql-js` v17 offers this as an option, off by default.

```
                        0 ms       40 ms                         440 ms
without @defer          [header+price ····· waiting for recs ··· ]  → one payload at 400 ms
@defer, late start      [header+price]→ sent at 40   [recs ··················]→ sent at 440
@defer, early start     [header+price]→ sent at 40
                        [recs ·······························]→ sent at 400
```

For slow fields that call other services, early execution is almost always what you want. The cost is that the initial payload's resolvers share the server with work that used to be serialized after them.

### A deferred fragment is also a failure boundary

Once the initial payload has been sent, the server can't take it back. So errors inside a deferred fragment can't propagate outside it. If a non-null field inside `Recommendations` fails, null propagation stops at the fragment: the fragment's data is not delivered, and its `completed` entry carries the errors instead. The product, already on the user's screen, is unaffected.

That's a useful property. 8.1a treated nullability as the decision about how far a failure spreads, and `@defer` adds a boundary without changing the schema. A slow, flaky field inside a deferred fragment can't blank the page. The flip side is that the HTTP status was `200` when the first part went out, so a failure in a later part can only be reported in the body, and monitoring that looks at status codes won't see it.

### `@stream` only helps if items arrive at different times

`@stream(initialCount: 5)` on a list sends five items first and the rest later. But if the list's resolver fetches all fifty items in one query that takes a second, the first five aren't ready any earlier than the fiftieth. Streaming then only changes how the finished list is split up. `@stream` pays off in two cases:

- **The source produces items over time.** The resolver returns an async iterator: results from a search backend that yields matches as it finds them, or pages fetched from an external API one after another.
- **Each item has slow nested fields.** The list itself is fast, but each item's `shippingEstimate` or `availability` takes a separate call. Streaming lets the first items, with their nested fields, go out before the rest are resolved.

`@stream` doesn't replace pagination. It still sends the whole list, just not all at once. For lists users may never scroll through, pagination (7.3c) is still the tool.

### Incremental delivery in a federated graph

In a federated graph (40.1a), the router can implement `@defer` on its own: it splits the query plan into an initial part and deferred parts, and fetches deferred entity fields with follow-up `_entities` requests to subgraphs. Subgraphs don't need to support `@defer` themselves. Apollo's router works this way, with a limit that follows from the mechanism: only root query fields and entity fields can actually be deferred, because those are the places where the router can start a separate fetch. Other fields inside a deferred fragment are resolved with the initial data and only *sent* separately.

That design fits especially well because the slow fields in a federated graph usually belong to a different subgraph. On the product page, `shippingEstimate` comes from the logistics subgraph and `recommendations` from the ML team's subgraph, so deferring them keeps their latency out of the initial payload without any change to those subgraphs.

### What the client has to do

A client has to merge patches into its store, track which pending pieces are outstanding, and render something reasonable for parts that haven't arrived. With fragment-per-component clients, this falls out naturally: a component whose fragment is deferred renders its loading state until its data arrives, and nothing else needs to know. Relay has supported `@defer` and `@stream` this way for years. Apollo Client supports several incremental formats but requires you to configure which one, because the format isn't standardized yet.

The UI design matters as much as the plumbing. Deferred sections need reserved space, or the page jumps when they arrive. And the order in which sections appear should look deliberate. Deferring the price and showing the reviews first would be a poor page, however fast.

## When It's Appropriate

- **A few slow, non-critical fields on an otherwise fast screen.** The example's shape: 90% of the page resolves in 40 ms, and one or two sections take hundreds of milliseconds to seconds.
- **Slow parts you can't make fast.** External APIs, ML inference, cross-region calls, expensive aggregates, where caching isn't possible or not fresh enough.
- **High-latency clients.** On mobile networks, where a second request costs a full round trip, one incrementally delivered response beats two separate queries.
- **Server-side rendering with streaming.** When the renderer can flush HTML for the first viewport while deferred data is still arriving.
- **Federated graphs where slow fields belong to other subgraphs.** The router can defer them without the subgraphs changing.

## When It's Unnecessary or Overkill

- **When the fields are uniformly fast.** If the whole response takes 80 ms, splitting it adds overhead and client complexity for nothing.
- **When the slow part is what users need first.** Deferring the price doesn't make the page usable sooner. Make that field faster, or cache it.
- **When the slow field can be made fast.** A precomputed recommendation list, or a cached shipping estimate by postcode and warehouse, removes the problem instead of arranging around it. Check this first.
- **When your infrastructure buffers.** If you can't get multipart responses through your proxies and CDN unbuffered, `@defer` adds cost and delivers nothing.
- **When clients can't handle the format.** Old app versions, third-party clients, or tools that expect one JSON body. The `if` argument and content negotiation help, but every client that sends `@defer` must support the format you serve.

## Trade-offs

**The format isn't standardized yet.** There are at least two formats in production, and clients must be configured to match the server. Adopting now means committing to a format that may change once more before it's in the spec, and planning a migration if it does.

**Intermediaries can silently undo it.** Buffering proxies, compression middleware, API gateways, and CDNs that don't stream will deliver everything at once. It fails without errors, so it has to be tested end to end in production-like infrastructure and monitored with time-to-first-payload metrics.

**Request metrics get two meanings.** "Response time" is now the time to the first payload *and* the time to the last. Dashboards, SLOs, and alerts need both, or a regression in the deferred part becomes invisible because the first-payload time looks great.

**Errors arrive after success.** The status code is `200` before a deferred part fails. Error monitoring has to read payload bodies, and clients have to handle failures per section.

**Server resources are held longer.** A connection that used to finish at 400 ms may now stay open, streaming, for the same 400 ms or longer, and early execution runs work in parallel that used to be sequential. Capacity per connection and per request changes.

**Caching gets harder.** A multipart response is awkward to cache at an HTTP cache (8.3c), and the client's normalized cache must merge patches correctly, including when a patch for an old request arrives after a newer request has updated the same object.

**It doesn't reduce cost.** The server does the same work, and in a federated graph it may do more (an extra fetch per deferred part). Cost analysis (8.3b) should count deferred fields fully.

**Layout shift and loading states.** Every deferred section is a loading state someone has to design, and each one that arrives late can move content under the user's finger.

## Alternatives

**Make the slow part fast.** Precompute, cache, or move it off the request path. When it's possible, it beats every other option here, because it removes the latency instead of hiding it.

**Separate queries, issued in parallel.** The first fix from the opening. It works everywhere with no special format or infrastructure, and each query is independently cacheable. The costs are client-side orchestration of which fragments go in which query, and repeated server work for shared data.

**Nullable fields with timeouts.** Return what's ready by a deadline and `null` for the rest, possibly with a follow-up query for the missing parts. It's simple and needs no client changes, but a timed-out section is simply missing, and choosing the deadline trades completeness against speed.

**Streaming at the rendering layer.** Frameworks that stream server-rendered HTML (for example, React's streaming server rendering with suspense boundaries) can send the first viewport while slower data loads, using ordinary queries per boundary. This moves incremental delivery from the API to the page, which works well when the server renders, and doesn't help native apps.

## How to Achieve It

**Level 0: find the slow fields.** Turn on field-level tracing (Module 19, 36.4) and look at which resolvers dominate p50 and p99 per screen. Try to make them fast or cached first. *Next step when:* the slow fields are both slow and hard to fix, and not what users need first.

**Level 1: prove the transport.** Enable incremental delivery on the server or router, pick the format your clients support, and verify with a test query that parts arrive separately *through production infrastructure*: every proxy, the CDN, compression. Add time-to-first-payload and time-to-last-payload metrics. *Next step when:* a test request shows distinct arrival times in production.

**Level 2: defer one screen.** Choose the screen with the clearest split, add `@defer` to the slow fragments, design the loading states, and turn on early execution if your server supports it. Compare first-payload time, last-payload time, and user-facing metrics. *Next step when:* the screen's metrics improved and nothing got worse.

**Level 3: make it a component-level habit.** Let component authors put `@defer` on their own fragments, with guidance on when it's appropriate, and make sure error handling is per section. *Next step when:* you have lists whose items arrive at different times.

**Level 4: `@stream` for lists with incremental sources.** Convert resolvers to async iterators where the source really produces items over time, and use `@stream` there.

## Implementation

TypeScript with `graphql-js` v17's experimental incremental execution, served as `multipart/mixed` from a plain Node HTTP handler. The HTTP layer is where most production problems are, so it's shown in full.

The server handler:

```ts
import { experimentalExecuteIncrementally, parse, validate } from "graphql";

async function handle(req: IncomingMessage, res: ServerResponse) {
  const { query, variables } = await readJson(req);
  const document = parse(query);
  const errors = validate(schema, document);          // schema includes GraphQLDeferDirective,
  if (errors.length) return sendJson(res, 400, { errors });   // GraphQLStreamDirective + specifiedDirectives

  const result = await experimentalExecuteIncrementally({
    schema, document, variableValues: variables,
    contextValue: createContext(req),
    enableEarlyExecution: true,                                           // ← aside 1
  });

  if (!("initialResult" in result)) return sendJson(res, 200, result);   // no @defer/@stream active
  if (!acceptsMultipart(req)) return sendJson(res, 200, await collectAll(result)); // ← aside 2

  res.writeHead(200, {
    "Content-Type": 'multipart/mixed; boundary="-"',
    "Cache-Control": "no-store",
    "X-Accel-Buffering": "no",                                            // ← aside 3
  });
  writePart(res, result.initialResult);
  for await (const patch of result.subsequentResults) {
    writePart(res, patch);                                                // ← aside 4
  }
  res.end("\r\n-----\r\n");
}

function writePart(res: ServerResponse, payload: unknown) {
  res.write("\r\n---\r\nContent-Type: application/json; charset=utf-8\r\n\r\n");
  res.write(JSON.stringify(payload));
}
```

**Aside 1: without this flag, `@defer` can make the slow part slower.** Early execution is off by default in `graphql-js` v17, which means deferred fragments start only after the initial payload's work is done. With it on, the recommendations call starts at 0 ms instead of 40 ms. The difference is small here and large when the initial payload itself is slow, and it's the first thing to check when deferred sections arrive later than they did before `@defer`.

**Aside 2: a client that didn't ask for multipart still gets a correct answer.** `collectAll` merges every patch into one JSON result, which is what the client would have received without `@defer`, only at the slowest part's time. This is how old clients, tools like `curl`, and crawlers keep working when a query they send happens to contain `@defer`. It's also what happens, unintentionally, when a proxy buffers: the fallback is the same result, just without the benefit.

**Aside 3: this header is for one specific buffer.** `X-Accel-Buffering: no` tells nginx not to buffer this response. Other proxies, load balancers, and CDNs have their own settings, and compression middleware must be configured to flush per write rather than per response, or it will quietly collect the whole body before compressing. None of these fail with an error. They just deliver every part at the end, so the only reliable check is to measure part arrival times from the client side, through the real path.

**Aside 4: once the first part is written, errors live in the body.** If `Recommendations` fails, the patch carries `completed: [{ id: "1", errors: [...] }]`, while the response status is still the `200` sent with the headers. Error metrics that count status codes will report this request as a success, so the handler (or the logging around `writePart`) should count errors in patches as well.

A streamed list, where `@stream` actually helps because the resolver yields as it goes:

```ts
const resolvers = {
  Query: {
    // Search backend returns matches in ranked batches; yield each as it arrives.
    search: async function* (_: unknown, { q }: { q: string }, ctx: Ctx) {
      for await (const batch of ctx.search.query(q, { batchSize: 10 })) {
        yield* batch;                                                     // ← aside 5
      }
    },
  },
};
// client: search(q: $q) @stream(initialCount: 10) { id title price }
```

**Aside 5: the async generator is what makes `@stream` worth using.** If this resolver awaited the whole result and returned an array, `@stream` would split an already-complete list. With a generator, the first ten results go out with the initial payload as soon as the backend's first batch arrives, and later batches follow. Without `@stream` in the query, `graphql-js` simply collects the generator into a list, so the same resolver serves both kinds of client.

## Further Reading

- **"Introducing GraphQL.js v17"** (graphql.org blog, June 2026) and **the GraphQL.js "Enabling Defer and Stream" guide**: the current experimental API, early execution, and the legacy function for the older format.
- **The incremental delivery spec draft** (graphql/graphql-spec pull request #1110) and **the `defer-stream-wg` repository and discussions** on GitHub, particularly the discussion that introduced the `pending`/`incremental`/`completed` format and its reasoning on deduplication.
- **GraphQL-over-HTTP working group, `rfcs/IncrementalDelivery.md`**: the `multipart/mixed` framing, boundaries, and transfer encoding on HTTP/1.1 vs HTTP/2.
- **Apollo router documentation, "Router Support for @defer"**: how a federated router defers entity and root fields by splitting the query plan, and the 2022 format it uses.
- **Apollo Client documentation, "Using the @defer directive"**: configuring an incremental handler per format, which shows concretely what "not yet standardized" means for a client.
- **Relay documentation on `@defer` and `@stream`**: the longest-running client implementation, and a good model of per-component loading states.
- **In this collection:** 8.1a (fragments and nullability as blast radius), 8.3b (cost analysis still counts deferred fields), 8.3c (caching, which multipart complicates), 40.1a (router query plans), 40.2a (subscriptions, the other multi-payload operation), Module 19 and 36.4 (tracing to find slow fields).

A sibling in another server language wouldn't add much, since the format and the transport are the same everywhere. What would add something is a client-side article: how a normalized cache merges patches, handles a late patch for a superseded request, and renders loading states per fragment. That's a different topic rather than a sibling, and it isn't in the map yet.

---

The habit to take from this: when a response is as slow as its slowest part, ask whether every part is needed at the same moment. Often the answer is no, and the fix is to separate when data is needed from when it's requested. Sometimes the answer is that the slow part should just be made fast, and that's worth checking first.
