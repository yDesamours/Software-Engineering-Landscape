# Governing a Federated Schema: Checks Instead of Gatekeepers

_Module 40.1b — GraphQL Advanced Patterns_

## The Problem

Suppose you run the API side of a travel marketplace. Last year the company moved its GraphQL server to federation (40.1a): fourteen subgraphs owned by eleven teams, one router, one registry. The review queue disappeared the way it was supposed to. Teams ship schema changes on their own, about sixty a week.

Then came one month with three incidents, none of which any single team did wrong by its own rules.

**Incident 1: a field "nobody used."** The hotels team renamed `Hotel.starRating` to `Hotel.stars`. They did it properly by the book they had: add `stars`, mark `starRating` `@deprecated`, wait thirty days, remove it. Composition passed, since nothing else referenced the field. But iOS app versions 5.2 through 5.4 still asked for `starRating` on the hotel details screen, and a third of iOS users hadn't updated. The router didn't return `null` for the missing field. It rejected the whole operation at validation, because a query that names a field the schema doesn't have is invalid. For those users, every hotel page was an error screen for the nine hours it took to put the field back.

**Incident 2: a composition break that blocked everyone.** The pricing team changed the shared `Money.amount` from `Float` to a new `Decimal` scalar, to stop rounding errors on currency conversion. Their pull request composed cleanly against the published schemas at the time. Meanwhile the loyalty team merged a change that added `Money` to their own subgraph, still with `amount: Float`. Both merged within an hour. Whichever published second broke composition. The router kept serving the last good supergraph, so customers saw nothing, but the registry now held a set of subgraph schemas that couldn't compose, and every other team's publish failed against it. Nobody could ship a schema change for two days while the two teams argued, reasonably, about whose change should be reverted.

**Incident 3: a change no check could see.** The bookings team changed `Booking.totalPrice` to include taxes, which it hadn't before, to match what the checkout page showed. Same field, same type, same nullability. Every schema check passed, because the schema didn't change. Two partner integrations that added taxes on top now double-counted them on invoices for eleven days.

Before federation, all three would probably have been caught by the same thing: the API team's slow review, where four people who'd seen every change for three years would have said "iOS still uses that," "loyalty is adding `Money` too," and "partners compute tax themselves." Federation removed that review because it was a queue. It didn't replace the knowledge the review contained.

So the requirement is: **catch what the old reviewers caught, without bringing back the queue.** Most of it has to be automatic, and the part that can't be should go only to the people it concerns.

## What It Is

This is **schema governance**: the rules and checks that decide which schema changes may reach production, and who decides when a rule should bend. In a federated graph it's built around a **schema registry**, which stores every subgraph's published schema and the composed supergraph, and **schema checks**, which run on every proposed change before it merges.

The checks that matter most go beyond "is this change breaking?" to "whom does it break?" A breaking change is only a problem if some client, or some other subgraph, depends on the thing being broken. The checks answer that from evidence: which operations clients have actually sent, and which operations first-party clients are known to send.

The neighbor to separate is **API versioning and deprecation**, covered in Module 33. That module is about the lifecycle of retiring something: announcing it, reaching the people who use it, and turning it off. This article is about the checks that decide whether a given change is allowed today, and it relies on Module 33's lifecycle whenever the answer is "not yet."

## Recognizing the Problem

- Clients discover breaking changes before your CI does.
- Deprecated fields stay in the schema for years because nobody can say who still uses them.
- A composition failure in one subgraph has blocked other teams' publishes.
- Naming and conventions have drifted: `createdAt`, `created_at`, and `creationDate` on neighboring types; some lists paginated, some not.
- A central group has quietly started reviewing every schema change again, and lead times are creeping back up.
- Schema changes are approved by someone who can't tell you which clients the change affects.
- Nobody knows which client versions are still sending traffic, or clients aren't identified at all.
- A field's meaning has changed without its name or type changing.

## How It Works

### Two contracts, not one

A federated graph has two audiences for every change, and they break in different ways.

```
                      ┌───────────────── client-facing contract ─────────────────┐
  iOS 5.2 … 6.1  ─┐   │  the API schema: types, fields, arguments,               │
  Android        ─┼──►│  enum values                                             │
  web            ─┤   │  broken by: removals, type changes, new required args    │
  partners       ─┘   └─────────────────────────────┬────────────────────────────┘
                                                    │ router
                      ┌── inter-subgraph contract ──┴────────────────────────────┐
                      │  @key, @requires, @external, shared value types,         │
  14 subgraphs   ───► │  @override                                               │
                      │  broken by: key changes, required-field changes, drift   │
                      └──────────────────────────────────────────────────────────┘
```

The client-facing contract is what 8.1a and Module 33 describe: remove a field or narrow an input and some client stops working. The inter-subgraph contract is new with federation. If catalog changes `Restaurant.latitude` from `Float` to a `Coordinates` object, no client may notice, but logistics' `@requires(fields: "latitude longitude")` no longer makes sense. Composition catches most structural inter-subgraph breaks. Operation checks catch client-facing ones. Neither catches the third kind, changes of meaning, which comes up at the end of this section.

### The pipeline every schema change goes through

```
 subgraph PR
     │
     ▼
 1. lint ─────────────── conventions, as code; fails fast, needs no other subgraph
     │
     ▼
 2. compose ──────────── this subgraph's proposed schema + everyone else's published
     │                   schemas → does a valid supergraph come out?
     ▼
 3. diff ─────────────── old supergraph vs new: every change, classified
     │                   safe / dangerous / breaking
     ▼
 4. check against usage ─ for each breaking change: which clients, which versions,
     │                   which operations would stop validating?
     ▼
 5. route review ──────── by what changed, not by who changed it
     │
     ▼
 merge → deploy subgraph → publish schema (from main only)
```

Each step exists because the one before it can't answer its question. The order matters too: it runs from cheapest to most expensive, and from "needs nothing" to "needs production telemetry."

### Keeping the published set composable

Composition in CI checks your proposed schema against the others' *published* schemas, at the moment the check runs. Incident 2 is what happens when two changes each pass against the same starting point and conflict with each other. That's the same race as two pull requests that each pass tests against `main` and fail together. The fixes are the same too:

- **Re-check at merge time.** Run composition again when the pull request actually lands, against whatever is published then, with a merge queue so changes that touch the schema land one at a time.
- **Publish only from `main`, after deploy.** Never from a branch, and never before the subgraph can serve what it declares (40.1a's deploy ordering).
- **Make the failure rule explicit.** When a publish fails composition anyway, decide in advance whose job it is to fix. The simplest rule that holds up: *what's published stands, and the publish that failed is the one that gets fixed or reverted.* It's arbitrary, which is the point. Incident 2's two days were spent arguing a question that had no right answer, and a pre-agreed rule turns it into a thirty-minute revert (see 32.4b on settling recurring disputes through ownership rules rather than case by case).

It also matters what your registry does with a schema that fails composition. The router is safe either way: it keeps the last supergraph that composed successfully. But some registries still record the failed schema as that subgraph's latest, and from then on every other team's publish composes against it and fails too. That's what turns one team's mistake into everyone's outage for schema changes. Know which behavior yours has, and treat "composition is failing on `main`" as an incident with an owner and a clock, not a background annoyance.

### From "is it breaking?" to "does it break anyone?"

A schema diff tool can tell you that removing `Hotel.starRating` is breaking. It can't tell you whether it matters. The answer comes from two sources of evidence, and GraphQL makes both unusually good.

33.1a pointed out that in a REST API, usage of individual response fields is invisible: the server sends the whole representation and has no idea which fields the client reads. GraphQL reverses that. Every operation names every field it wants, so the router can record usage per **schema coordinate** (`Hotel.starRating`, `Query.search(filter:)`, `Currency.JPY`), per client, per client version.

**Usage reporting.** The router records, for each operation it executes, a normalized signature with literals stripped and the coordinates it touched, tagged with the client's name and version from request headers the clients send (Apollo's convention is `apollographql-client-name` and `apollographql-client-version`). An operation check then asks: over the last *N* days, which clients sent operations that the proposed schema would no longer validate?

**Trusted documents.** For first-party clients using the registry from 8.3c, you don't have to infer anything. The registry holds every operation each client build can send. A check against it is exact: if any registered document for a supported build would fail validation against the new schema, the change is breaking for that build, whether or not anyone used that screen this week.

The two complement each other. Trusted documents are complete for your own apps. Usage reporting covers everyone else (partners, third-party developers, internal scripts), but only as far back as its window and only for what it measures. Incident 1 would have been caught by either: `starRating` appeared in the registered documents for iOS 5.2 through 5.4, and in a week of usage.

Two policy decisions make this work, and both are really Module 33's decisions expressed as check configuration:

- **The window.** Seven days of usage misses the monthly invoice export and the partner that only syncs at quarter end. Pick the window from your slowest legitimate client's cycle, not from the default, and use trusted documents where you can, since they have no window.
- **The support floor.** Some client versions are old enough that you've decided they no longer block changes. That decision should be a published policy ("iOS versions older than 12 months, or below 2% of iOS traffic, are unsupported") that the check reads, not a reviewer's judgment in the moment.

### What counts as breaking in a federated graph

8.1a covered the general rule: output types may get stricter and input types may get looser, and not the reverse. Federation adds a few cases worth knowing by name:

| Change | Breaks | Caught by |
|---|---|---|
| Remove or rename a field, argument, or enum value | clients that use it | diff + usage |
| Add a value to an output enum | clients with exhaustive `switch` statements (dangerous, not breaking) | diff, flagged for review |
| Change a `@key` | other subgraphs that reference the entity by that key | composition |
| Change or remove a field another subgraph `@requires` | that subgraph | composition |
| Change a shared value type (`Money`) in one subgraph | composition, until every definer agrees | composition |
| Remove `@inaccessible` from a field | nothing breaks; something internal becomes public | lint / review |
| Move a field with `@override` | nothing, if both implementations agree; clients if they don't | nothing automatic |
| Change a field's meaning | whoever relied on the old meaning | nothing automatic |

The last two rows are the reason the pipeline ends with review.

### Lint rules instead of reviewers

Most of what a central reviewer checks is mechanical: naming (`camelCase` fields, `Input` suffixes), every list field paginated with a required, bounded `first` (8.3b's rule), descriptions on public types, no new non-null fields on cross-subgraph entities without a reason (40.1a's blast radius), `@deprecated` always with a reason that names the replacement. Every one of those can be a lint rule, and a lint rule runs in two seconds on every pull request, never goes on holiday, and applies the same judgment to the eleventh team as the first.

The rules should be owned by a small group (often called graph stewards or a schema working group), and changing a rule should go through them. What they review is the rules, not the changes.

### Routing the review that's left

Some changes still need a person. The trick is to decide which ones by what the change touches, not by which team made it:

- **Adding fields to your own subgraph's types:** owner review only. This is the bulk of changes and should be fast.
- **New entities, new keys, new root fields:** graph stewards, because these shape how every other team will extend the graph, and they're expensive to undo.
- **Changes to shared value types or to fields other subgraphs `@require`:** the owners of every affected subgraph, found from the supergraph, not from memory.
- **Breaking changes the usage check allows** (unused, or only used by unsupported versions): owner review, plus a record of the decision.
- **Breaking changes the usage check blocks:** not approved in review. They go through Module 33's lifecycle: deprecate, reach the clients, wait for usage to reach the floor, then remove.

With routing like this, the stewards see perhaps one change in twenty, and every one they see is one where their knowledge is actually needed.

### What no check sees

Incident 3 changed meaning without changing shape, and nothing in the pipeline can see that. Two habits reduce the risk. First, **new meaning gets a new field**: `totalPriceInclTax` next to `totalPrice`, with the old one deprecated through the normal lifecycle, so the change becomes a shape change the checks *can* see. Second, **descriptions are part of the contract**: a field's description states units, inclusions, and time zones, and a description change on a field with external consumers is routed for review like a breaking change. Neither is enforceable in general. Both turn "we didn't know" into "we didn't follow the rule," which is a much easier conversation to have.

### One graph, several audiences

A related governance tool is worth one paragraph. Registries can produce **contract variants**: filtered supergraphs built by including or excluding fields by tag (`@tag(name: "partner")`), so partners get a smaller, more stable schema than your own apps do, with its own checks and its own clients. It's useful when the partner API should promise less than the internal one. It's also one more supergraph to keep composable and one more tag for every team to remember, so it's worth it only once a partner audience actually exists.

## When It's Appropriate

- **Several teams publishing to one graph.** Around five subgraphs owned by different teams, or tens of schema changes a week, is where informal coordination stops catching incidents 1 and 2.
- **Clients you don't deploy.** Mobile apps with a long tail of old versions, partner integrations, and third-party developers. Operation checks pay for themselves the first time they block a removal like Incident 1, and this applies to a single-server GraphQL API too, federation or not.
- **Cross-subgraph dependencies.** As soon as one subgraph `@requires` another's fields or several define a shared value type, composition checks in CI and a failure rule stop being optional.
- **A central review has crept back.** If the old queue is re-forming under a new name, it's usually because the knowledge it holds hasn't been turned into checks yet.

## When It's Unnecessary or Overkill

- **One team, one subgraph.** Composition checks against yourself are trivial, and routing review by change type means routing it to the same five people. Lint and a diff in CI are enough. Keep the operation check if you have mobile clients.
- **All clients deploy with the server.** If the only client is a web app deployed from the same repository in the same pipeline, a breaking change and its client fix ship together. Type-checking the client against the new schema does the operation check's job.
- **Buying the platform before having the data.** An enterprise registry with proposals, contracts, and custom checks, for three subgraphs and clients that don't send identification headers, gives you configuration without evidence. Get clients identified and usage recorded first.
- **Review boards for additions.** Requiring stewards to approve every new field recreates 40.1a's queue with a more respectable name. Additive changes to your own types should need nothing but lint and your own team.

## Trade-offs

**Usage data is an operational system with its own costs.** Recording per-coordinate usage for every request means a reporting pipeline, storage, and retention decisions. Operation signatures must have literals stripped, or you'll be storing email addresses and search terms from query strings (19.1 on PII in telemetry). And it only works if clients identify themselves, which means changing every client and chasing the partners who don't.

**"Checks passed" becomes a claim people trust too much.** The checks see only what's measured, inside the window, in the shape of the schema. An unmeasured coordinate (input fields and argument values often aren't tracked by default), a quarterly client, or a change of meaning all pass. The pipeline's output should be read as "no evidence of breakage," and people should be taught that it means exactly that.

**The registry becomes deploy-critical.** If schema publishing requires the registry and checks require usage data, an outage in either blocks every schema change. You need a documented break-glass path for publishing in an emergency, and someone who owns the registry's uptime.

**Overrides become reflexes.** Every check platform has an "approve anyway" button. If it's clicked weekly, the check has become a formality. Track override rates per team, and treat a rising rate as a sign that either the rules or the support floor is wrong.

**The stewards can become the queue again.** A small group owning the lint rules and reviewing new entities is healthy. The same group gradually taking on "just a quick look" at every change is 40.1a's problem returning. Watch their share of reviews.

**Rules ossify.** A lint rule written for a real reason in year one ("all IDs are opaque strings") may block a legitimate design in year three. Rules need owners, an exception process, and occasional deletion.

**Workflow lock-in.** Checks, proposals, and contracts are platform features, and they're less standardized than the federation directives. Moving from one registry to another means rebuilding the pipeline, not just changing the router.

## Alternatives

**A central review board.** The API team from 40.1a, or a schema council that approves changes. It works, because experienced reviewers carry a lot of context, and it's the right choice when changes are few. It fails when changes are many, and it keeps the knowledge in people's heads rather than in checks others can run.

**Versioning the whole graph.** Publish `/graphql/v2` and freeze v1. GraphQL's usual practice is continuous evolution of one schema, because clients select fields and additions don't affect them, so graph-wide versions are rare and expensive: every subgraph must serve both. It can make sense for a partner API with contractual stability guarantees, which is where contract variants usually do the same job more cheaply. 33.1b covers versioning schemes in general.

**Consumer-driven contract tests.** Each client publishes the interactions it depends on, and the provider's CI verifies them (Pact is the common tool). For GraphQL, trusted documents are essentially this, with the registry as the broker, so separate contract tests mostly duplicate them. They're still worth considering for non-GraphQL consumers of the same services.

**Trust and conventions, without automated checks.** Teams follow a written guide and are careful. It works for a handful of teams who talk often. It fails as the graph grows because the guide can't say which clients use a field, and no amount of care can answer that without data.

## How to Achieve It

**Level 0: lint and diff on every change.** Add a schema linter and a schema diff tool to each subgraph's CI. The diff shows every change's classification in the pull request, even before anything blocks on it. *Next step when:* the diff output is being read, and people ask "is this breaking change safe?"

**Level 1: identify clients and record usage.** Make every first-party client send its name and version. Ask partners to do the same, and give unidentified traffic a label of its own so its size is visible. Turn on usage reporting at the router. Don't block anything yet: collect a full business cycle of data first. *Next step when:* you can answer "who uses `Hotel.starRating`?" in under a minute.

**Level 2: composition checks and a failure rule.** Run composition in every subgraph's CI against published schemas, re-check at merge, publish only from `main` after deploy, and write down the "what's published stands" rule. *Next step when:* composition on `main` hasn't broken for a few weeks, or has broken and been reverted within the hour.

**Level 3: blocking operation checks.** Fail pull requests whose breaking changes affect supported clients, using the usage window and the support floor as published policy. Add trusted-document checks for your own apps. *Next step when:* breaking changes are reaching Module 33's deprecation lifecycle instead of reaching clients, and override rates are low.

**Level 4: routed review and the extras.** Route new entities, keys, and shared value types to stewards, and cross-subgraph changes to affected owners. Add contract variants if a partner audience needs its own schema, and schema proposals if new entities need design discussion before code exists.

## Implementation

TypeScript, as a CI step that sits between the diff and the review. It uses `@graphql-inspector/core` for the diff, because its changes carry a schema path you can join against usage data. The usage store and support policy are your own; their interfaces are shown as types.

The check itself:

```ts
import type { GraphQLSchema } from "graphql";
import { diff, CriticalityLevel, type Change } from "@graphql-inspector/core";

type Usage = { client: string; version: string; requests: number; lastSeen: Date };

interface UsageStore {
  // null means "this coordinate isn't measured," not "unused"
  clientsUsing(coordinate: string, since: Date): Promise<Usage[] | null>;
}
interface TrustedDocs {
  // registered operations for supported builds that fail to validate
  failingDocuments(newApiSchema: GraphQLSchema): Promise<{ client: string; version: string; name: string }[]>;
}

async function operationCheck(oldApi: GraphQLSchema, newApi: GraphQLSchema, deps: Deps) {
  const since = new Date(Date.now() - deps.policy.windowDays * DAY);      // ← aside 2
  const blocking: Finding[] = [];
  const allowed: Finding[] = [];

  for (const change of await diff(oldApi, newApi)) {
    if (change.criticality.level !== CriticalityLevel.Breaking) continue;

    const usage = await deps.usage.clientsUsing(change.path!, since);
    if (usage === null) {                                                   // ← aside 1
      blocking.push({ change, reason: "not measured; treat as used" });
      continue;
    }
    const supported = usage.filter((u) => deps.policy.isSupported(u.client, u.version));
    (supported.length > 0 ? blocking : allowed).push({ change, clients: supported });
  }

  for (const doc of await deps.trusted.failingDocuments(newApi)) {         // ← aside 3
    blocking.push({ document: doc, reason: "registered operation no longer validates" });
  }
  return { blocking, allowed };
}
```

**Aside 1: unmeasured is not unused.** Usage reporting often doesn't record input fields, argument values, or enum values passed as input, and a coordinate that was never measured returns no usage. A check that treats "no data" as "no users" will approve removing `Currency.JPY` from an input enum while every Japanese booking still sends it. The store distinguishes `null` (can't say) from `[]` (measured, and nobody), and only the second one allows a removal.

**Aside 2: the threshold is clients, not requests.** Notice there's no "less than 0.1% of traffic" rule here. A removed field doesn't fail 0.1% of requests randomly; it fails every request from the clients that use it, and because validation rejects the whole operation, those users lose the whole screen, as in Incident 1. So the question is which client versions are affected, and whether each is above the support floor. If you do use a traffic threshold, apply it per client version, and let `isSupported` read a published policy so that "iOS 5.2 no longer counts" is a decision someone made and dated, not one the check makes silently.

**Aside 3: trusted documents catch what the window misses.** The usage loop only sees operations sent within the window. The support team's in-app "report a problem" screen on iOS might be opened twice a month, but its registered document is in the registry for every supported build, so the check sees it regardless. For first-party clients, this loop is the exact answer, and the usage loop is the fallback.

Routing the review, by what changed:

```ts
function reviewersFor(change: Change, sg: SupergraphIndex, author: Team): Team[] {
  const coord = change.path ?? "";
  if (sg.isNewEntity(change) || sg.isKeyChange(change) || sg.isNewRootField(change)) {
    return ["graph-stewards", author];
  }
  if (sg.isSharedValueType(coord)) return sg.subgraphsDefining(coord);   // every definer
  const dependents = sg.subgraphsRequiring(coord);                         // @requires / @provides
  return dependents.length > 0 ? [author, ...dependents] : [author];     // ← aside 4
}
```

**Aside 4: reviewers come from the supergraph, not from memory.** The loyalty team in Incident 2 would have been asked to review pricing's `Money` change, and vice versa, because `subgraphsDefining("Money")` returned both. Nobody needed to remember who else defines `Money`. The same lookup is what makes routing cheap enough to use: the author's own team is the only reviewer for the vast majority of changes, and extra reviewers appear only when the supergraph says someone else depends on the thing that changed.

## Further Reading

- **Apollo GraphOS documentation, "Schema Checks"**: build (composition), operations, linter, contract, proposal, and custom checks, including operation-check windows and excluded clients. A clear description of the full pipeline, whichever tool you use.
- **Apollo documentation, "Segmenting Metrics by Client" (client awareness)**: the client name and version headers that make per-client usage possible.
- **GraphQL Hive documentation, schema registry and "Conditional Breaking Changes"**: an open-source, self-hostable registry, with breaking-change rules based on usage thresholds, time windows, and excluded clients.
- **GraphQL Inspector documentation, "Diff"**: change classification, and rules such as `considerUsage` and `suppressRemovalOfDeprecatedField` for customizing it.
- **GraphQL ESLint** (the-guild.dev/graphql/eslint): lint rules for schemas and operations, and how to write your own, which is where most of a steward group's rules end up.
- **Marc-André Giroux, _Production Ready GraphQL_** (2020): the chapters on schema evolution and deprecation, from someone who worked on GitHub's and Shopify's public GraphQL APIs.
- **_Principled GraphQL_** (principledgraphql.com): the principles on tracking the schema in a registry and on agile schema development, as the case for this model.
- **In this collection:** 40.1a (federation, deploy ordering, cross-subgraph nullability), 8.1a (safe and unsafe changes in general), 8.3c (trusted documents), 33.1a and 33.2a (breaking changes and the deprecation lifecycle this article defers to), 32.4b (decision rights, for the failure rule and the stewards' role), 19.1 (PII in telemetry).

A sibling in another language wouldn't add much. The substance is policy expressed as CI configuration and a join against usage data, and that looks the same in Go or Java.

---

The habit to take from this: when you remove a gatekeeper, list what the gatekeeper actually knew. Each item is either a rule you can write down and check, a fact you can look up from data, or a judgment that belongs to a specific person. The first two become automation. The third gets routed to that person and nobody else. What you must not do is let the list disappear along with the queue.
