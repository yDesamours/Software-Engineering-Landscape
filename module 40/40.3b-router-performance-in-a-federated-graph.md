# Router Performance: Where a Federated Request Spends Its Time

_Module 40.3b — GraphQL Advanced Patterns_

## The Problem

Suppose you run the API for a ticket marketplace. Last year its single GraphQL server became a federated graph (40.1a): twelve subgraphs, one router. The move did what it was for: teams ship independently, and a slow review queue is gone. It also made the most important page slower.

The event page, which shows the event, the venue's seating map, prices per section, available listings, and seller ratings, used to take 90 ms at the median and 400 ms at the p99. After federation:

```
                          single server     federated
event page p50                90 ms           310 ms
event page p99               400 ms          2,300 ms
p99 for 3 min after each supergraph publish        ~6 s     (about 30 publishes a day)
```

Nobody's resolver got slower. The time went to four places.

**Planning.** Before the router can fetch anything, it has to work out a query plan: which subgraph supplies each field, in what order. For the event page this takes about 40 ms, and the router caches the plan. But the cache is keyed to the supergraph, and every one of the thirty daily schema publishes empties it. For three minutes after each publish, thousands of distinct operations are planned from scratch. One of them, the seller dashboard, with fourteen fragments on interface types, took nearly four seconds to plan.

**Plan depth.** The event page's plan has five sequential levels: events, then venues, then pricing (which `@requires` section capacities from venues), then inventory, then seller ratings. Each level waits for the one before it, and each costs a network hop plus the subgraph's own time:

```
events ──► venues ──► pricing ──► inventory ──► sellers
  35 ms      45 ms      60 ms        50 ms        40 ms    = 230 ms before merging
```

**Repeated work.** When a big concert goes on sale, 900 people load the same event page within a second. The router sends 900 identical requests to the events subgraph and 900 to venues for the same venue, whose data changes about once a week. They aren't even identical enough to share: each carries the user's `Authorization` header, which venues doesn't read but which makes every request unique.

**The network.** Three of the subgraphs run in a different availability zone from the router, adding a few milliseconds per hop, and the router opens new connections to one of them under load because its connection pool is too small.

The team's first instinct was to make subgraphs faster, and that's where most of the time *isn't*. The time is in the router's planning, the plan's shape, and the work nobody noticed was being repeated.

## What It Is

This is the performance of the **router tier**: the part of a federated request between receiving the client's query and returning the merged response. Its cost has a few distinct parts, and each has its own technique:

| Cost | Technique |
|---|---|
| Planning | plan caching, warm-up on schema change, planning budgets in CI |
| Sequential plan levels | changing the plan's shape: keys, `@provides`, fewer `@requires` chains |
| Identical concurrent fetches | subgraph request deduplication |
| Repeated fetches of slow-changing data | entity (response) caching at the router |
| Many small operations per screen | operation batching |
| Per-hop network cost | co-location, connection pooling, per-subgraph timeouts |

The neighbor to separate is 8.3c's caching, which is about responses and HTTP: CDNs, persisted `GET`s, and the client's normalized cache. Router caching sits behind all of that, caches pieces of responses by entity rather than whole responses, and works even for requests that can never be cached as a whole because they contain one user's data.

## Recognizing the Problem

- Latency went up when you federated, and subgraph dashboards all look healthy.
- p99 spikes right after schema publishes or router deploys, then recovers.
- A few operations take seconds to plan, and planning time isn't something you measure.
- Traces show long chains of sequential subgraph fetches for your most important screens.
- Subgraphs see many identical requests at the same moment during traffic peaks.
- Slow-changing data (venues, product catalogs, user profiles) is fetched from its subgraph on every request.
- The router forwards every client header to every subgraph.
- Some subgraphs are in a different zone or region from the router.

## How It Works

### Where the time goes

A federated request's latency breaks down like this:

```
client ─► [ parse + validate ] ─► [ plan ] ─► [ level 1 ] ─► [ level 2 ] ─► … ─► [ merge ] ─► client
              ~1–3 ms            0–40 ms       hop + work     hop + work          ~5–10 ms
                                (cached: ~0)   └────────── critical path of the plan ──────────┘
```

Two things follow. The plan's **critical path**, meaning the sequence of levels that must run one after another, usually dominates. And **planning** is either nearly free (cached) or suddenly large (not cached), which is why it shows up as spikes rather than as a steady cost. The techniques below target one or the other.

### Planning: cache it, warm it, bound it

Query planning is a search: for each field, which subgraphs can supply it, and which combination of fetches reaches all of them with the fewest sequential steps. The search grows with the number of subgraphs that can resolve the same types (every `@shareable` field is a choice) and with abstract types (fragments on interfaces and unions can split into one path per concrete type). Most operations plan in milliseconds. A few, with many fragments on abstract types across many subgraphs, take seconds.

Routers cache plans, keyed by the operation and the supergraph. That has three consequences:

- **Every supergraph change empties the cache.** A new supergraph means every plan must be recomputed. With frequent publishes (40.1b made publishing easy), that's frequent cold starts. The fix is **warm-up**: when a new supergraph arrives, the router plans the most-used operations *before* switching traffic to it. Apollo's router does this by default for a share of the cached operations, with a setting to warm more.
- **Every new router instance starts cold.** Autoscaling adds instances with empty caches during exactly the traffic spikes that caused the scaling. A **shared plan cache** (Apollo's router can use Redis for this) lets a new instance fetch plans that other instances already computed.
- **The set of operations should be known.** With trusted documents (8.3c), you know every operation your clients can send, so you can plan all of them in CI against the proposed supergraph, as one more check in 40.1b's pipeline. That catches the four-second plan in a pull request instead of in production, and lets you set a budget: fail a schema change that makes any registered operation's plan slower than, say, 200 ms or deeper than, say, four levels.

Apollo's own documentation makes a useful point about expectations here: plan caching mostly buys *stability* rather than speed. For a typical operation, planning is a small part of the request, and the cache keeps it small consistently. The large wins are in the cold cases: after publishes, on new instances, and on the few pathological operations.

### Plan shape: shorten the critical path

After planning, a request's latency is roughly the sum of its sequential levels. Adding parallel fetches is cheap. Adding a level is expensive. So the question for a slow plan is: *why must this fetch wait for that one?* There are usually four reasons, each with its own fix.

**The key isn't available yet.** Inventory needs `sectionId`s, and only venues knows the sections, so inventory waits for venues. If the events subgraph also stores the section IDs for its event, which it may well do, since it assigns them when the event is created, inventory can get them from level 1 and run in parallel with venues. Keys chosen from data every subgraph already has (40.1a) keep levels parallel.

**A field `@requires` another subgraph's data.** Pricing needs section capacity from venues. 40.1a's aside 3 covered the trade: either pay the sequential hop for current data, or keep a local copy updated by events and drop the dependency.

**A field is reached through the wrong subgraph.** If both orders and catalog can resolve `Product.name` (it's `@shareable`) but the plan reaches it through catalog, that's an extra fetch. `@provides` on the path that already has the data tells the planner it can take it from there.

**Abstract types fan out.** A list of `Listing` that's an interface with `ResaleListing` and `PrimaryListing`, whose fields come from different subgraphs, turns one fetch into one per concrete type, and nested fields on each can add further levels. Sometimes that's inherent. Often a field that every implementation has belongs on the interface, resolved by one subgraph.

Changing a plan's shape usually means changing schemas, so it's a conversation between teams, and it's much easier to have with a plan to point at. A plan-depth report for your top operations, updated on each publish, turns "the event page is slow" into "these two levels could be one."

### Deduplicate identical fetches

When 900 requests for the same event arrive together, the router makes the same `_entities` fetch to events 900 times. **Subgraph request deduplication** collapses identical fetches that are in flight at the same moment into one: the first one goes to the subgraph, the rest wait for its result. It's the router-level version of what a DataLoader does inside one request (8.3a), applied across requests.

It only works if the requests are actually identical, and in Apollo's router that means the same path, body, *and headers*. That's where the venues example failed: the router forwarded each user's `Authorization` header to every subgraph, so no two requests matched. The fix is **header discipline**: forward to each subgraph only the headers it uses. A subgraph that serves public venue data should receive no user identity at all, and its requests become identical and deduplicable. A subgraph that needs identity should get a small, normalized claim (a user ID, a tenant ID) rather than the raw token, so that at least requests from the same user or tenant can match.

Deduplication is only safe for reads. Mutations must never be collapsed, because two identical mutations are two actions.

### Cache entities at the router

Venue data changes once a week and is fetched on every event page. That's what a router-level entity cache is for: store each subgraph's answer for each entity (`Venue:v_88` from the venues subgraph) and reuse it across requests and users until it expires.

Apollo's router calls its current version of this **response caching**. It was released in January 2026, replacing an earlier "entity caching" feature, and it caches both root fields and entity representations per subgraph, in Redis. Other routers and gateways have their own versions. The mechanics that matter are the same everywhere:

- **Granularity is the entity, per subgraph.** The venues subgraph's fields for `Venue:v_88` are one cache entry, the pricing subgraph's fields for the same venue another. A query that needs both can hit one and miss the other.
- **Partial hits shrink fetches.** If 40 of 50 representations in an `_entities` fetch are cached, the router fetches only the 10 misses. If all of them hit, the fetch disappears, and if every fetch at a level disappears, the level does too, which shortens the critical path.
- **TTL is the minimum over the fields.** Subgraphs declare lifetimes per type or field (in Apollo Server with `@cacheControl`), and an entry lives as long as its shortest-lived field, the same minimum rule 8.3c used for whole responses.
- **Scope is part of the key.** Public data is shared across users. Private data, such as a user's own listing prices or a seller's dashboard figures, must be keyed by the user, or not cached. As in 8.3c, the dangerous mistake is marking private data as public, and the safe default is private.
- **Invalidation beats waiting.** TTLs alone mean a venue change takes up to a TTL to appear. Tag-based invalidation lets the owning subgraph say "`venue-v_88` changed" and remove every entry tagged with it right away. Apollo's version uses a `@cacheTag` directive on entities and an invalidation endpoint on the router, much like surrogate keys at a CDN.

Router caching is also where federation can end up *faster* than the old single server. A single server's resolvers each had their own caching, or none. The router can cache every subgraph's slow-changing entities uniformly, with one policy language and one invalidation mechanism.

### Batch operations when clients are chatty

Some clients, especially ones built from independent components that each run their own small query, send many operations per screen. On a high-latency link, that's many round trips. **Operation batching** lets the client send several operations in one HTTP request as a JSON array, and lets the router execute them together and, where possible, combine their fetches to the same subgraph into one HTTP request.

It's worth it for chatty clients on slow networks, and it has costs. The response waits for the slowest operation in the batch unless the router streams results. A batch of 50 operations is 50 times the work in one request, so cost analysis (8.3b) must count the whole batch, which 8.3b flagged as an easily missed multiplier. And one operation's failure mustn't fail the others. For most clients, combining components' fragments into one query (8.1a) is the better answer, and batching is for the cases where that isn't possible.

### The network underneath

Each plan level pays a network hop, so the network is multiplied by plan depth:

- **Co-locate the router with its subgraphs.** A cross-zone hop costs single-digit milliseconds, and a cross-region hop tens of milliseconds, per level. Five levels across regions can cost more than all the subgraphs' work.
- **Keep connections warm.** Size the router's connection pools for peak concurrency per subgraph, use keep-alive, and prefer HTTP/2 where subgraphs support it, so a traffic spike doesn't also become a connection-setup spike.
- **Think about compression per hop.** Compressing small responses inside one zone often costs more CPU than it saves in transfer time. Compress to clients, and measure before compressing to subgraphs.
- **Set timeouts as a hierarchy.** Each subgraph's timeout should be shorter than the router's overall timeout, which should be shorter than the client's, so a slow subgraph fails its own fetch (and its fields become `null` with errors) instead of failing the whole request.

### Measure the router, not just the subgraphs

The dashboards that find these problems are router-side: planning time and plan-cache hit rate (especially after publishes), plan depth per operation, time per plan level, deduplication rate, entity cache hit rate per subgraph and type, and connection pool waits. Traces should show one span per fetch node (Module 19, 36.4), so a slow request's critical path can be read directly.

## When It's Appropriate

- **Federated latency is noticeably worse than before, with healthy subgraphs.** The gap is in the router tier, and this is the list of places to look.
- **Frequent schema publishes on a large graph.** Tens of publishes a day and thousands of distinct operations make cold plan caches a daily event, and warm-up plus a shared plan cache fix it.
- **Traffic concentrated on a few popular entities.** Launches, sales, live events: deduplication and entity caching turn the concentration into an advantage.
- **Slow-changing data on hot paths.** Catalogs, venues, profiles, configuration: entity caching removes whole plan levels.
- **Deep plans on important screens.** Four or more sequential levels on the pages that matter most justify schema changes to flatten them.

## When It's Unnecessary or Overkill

- **Small graphs with few operations.** With three subgraphs and fifty operations, planning is trivially cached and plans are shallow. Measure first; there may be nothing to fix.
- **Entity caching for data that's always personal or always fresh.** A user's cart, live inventory counts, or balances gain little from caching and add risk. Leave them uncached.
- **Operation batching for clients that can combine their queries.** Fix the client's query composition instead.
- **Tuning plans before fixing co-location.** If the router and subgraphs are in different regions, no plan change will make up for it. Move them first.

## Trade-offs

**Caches make changes slower to appear.** Entity caching trades freshness for speed, and invalidation only works if every place that changes data sends it. A missed invalidation shows stale data for a full TTL, and "why does the venue page still show the old seating map?" becomes a debugging question with more places to look.

**Router caching is a new place for data leaks.** A private field marked public, or a cache key that leaves out the user, shares one user's data with another, and silently. Scope rules and their defaults need review as carefully as authorization rules (8.4).

**Header discipline is a contract.** Forwarding only the headers each subgraph needs makes deduplication and caching work, but a subgraph that later starts depending on a header it no longer receives breaks. The forwarding rules must be owned and changed deliberately, not left as a router default.

**Warm-up and shared caches add moving parts.** Warm-up delays each schema switch while plans are computed. A shared plan cache means Redis is now on the path to planning, and needs to be operated. Both are cheap compared with the spikes they prevent, but they're still more to run.

**Flattening plans couples subgraphs.** Removing a `@requires` usually means a local copy of another subgraph's data, kept current by events. Using `@provides` means one subgraph promises to supply another's fields. Each makes one subgraph faster and ties it more closely to another team's data.

**Deduplication makes subgraph metrics lie a little.** Subgraphs see fewer requests than clients sent, and a failed shared fetch fails every request waiting on it. Both are fine, but on-call engineers need to know they happen.

**Planning budgets can block legitimate changes.** A CI rule that fails schema changes that deepen plans will eventually block a change whose deeper plan is acceptable. It needs an override path, like every rule in 40.1b.

## Alternatives

**Faster subgraphs.** The first instinct from the opening. It helps when a subgraph really is slow, and it's always worth checking a trace to confirm where the time goes. It doesn't fix planning spikes, plan depth, or repeated fetches.

**Whole-response caching in front of the router.** A CDN or HTTP cache for persisted `GET` queries (8.3c) can serve the most popular public pages without reaching the router at all. It's the cheapest option where it applies, and it applies only to responses that are entirely public and identical across users.

**Precomputed read models.** For a page that's always slow to assemble, a service can listen to events from the relevant subgraphs and maintain a denormalized view, exposed as one subgraph field (2.4 on CQRS). The page becomes one fetch. The cost is a new service, eventual consistency, and a view that must be kept in step with every source.

**Fewer, larger subgraphs.** If plans are deep because domains are split more finely than the teams are, merging subgraphs removes hops. It's the right fix when 40.1a's warning about splitting before ownership exists applies.

## How to Achieve It

**Level 0: measure the router.** Add planning time, plan-cache hit rate, plan depth per operation, per-fetch spans, and per-level timing. Find your top operations' critical paths. *Next step when:* you can say for your most important screen how much time is planning, how much is each level, and how much is network.

**Level 1: the cheap fixes.** Co-locate the router and subgraphs, size connection pools, set timeouts as a hierarchy, forward only needed headers, turn on deduplication for queries, and turn on plan warm-up. *Next step when:* the remaining latency is in plan depth and repeated fetches of slow-changing data.

**Level 2: plan budgets in CI.** Plan every trusted document against each proposed supergraph, report depth and planning time, and fail changes over budget. Add a shared plan cache if you autoscale. *Next step when:* new regressions are caught before merge, and existing deep plans are listed.

**Level 3: entity caching.** Declare TTLs and scopes per type in each subgraph, starting with public, slow-changing entities. Add tags and invalidation from each owning subgraph. Watch hit rates, and test scope rules the way you test authorization. *Next step when:* the remaining deep plans are inherent in how the domains are split.

**Level 4: reshape.** Work with owning teams to flatten the deepest important plans: move keys, add `@provides`, replace `@requires` chains with local copies, or merge over-split subgraphs.

## Implementation

The router is configured rather than programmed, so most of this lives in router configuration and subgraph schemas. The code that's worth showing is the CI check that keeps plans shallow: TypeScript, using Apollo's JavaScript query planner packages to plan every registered operation against a proposed supergraph. First, the two configuration pieces the article relies on.

The router settings for warm-up, a shared plan cache, and deduplication, in Apollo's router configuration format:

```yaml
supergraph:
  query_planning:
    warmed_up_queries: 500            # plan the 500 most-used operations before switching supergraphs
    cache:
      redis:
        urls: ["redis://plan-cache:6379"]   # new instances fetch plans others already computed
traffic_shaping:
  all:
    deduplicate_query: true           # collapse identical in-flight subgraph queries  ← aside 1
```

A venues subgraph declaring what the router may cache, and how to invalidate it:

```graphql
type Venue @key(fields: "id")
  @cacheControl(maxAge: 86400)                 # public by default: same for every user
  @cacheTag(format: "venue-{$key.id}") {
  id: ID!
  name: String!
  seatingMap: SeatingMap!
  boxOfficePhone: String
  holdsForViewer: [Hold!]! @cacheControl(scope: PRIVATE, maxAge: 0)   # ← aside 2
}
```

**Aside 1: deduplication only matches if headers match.** Apollo's router deduplicates requests with the same path, body, and headers. If the router forwards every client header to every subgraph, `Authorization` alone makes every request unique and this setting does nothing. Pair it with header rules that send venues no user identity at all.

**Aside 2: one private field changes the whole entity's cacheability.** `holdsForViewer` is per user and uncacheable. Because an entry's lifetime and scope come from the most restrictive field in it, selecting `holdsForViewer` makes that fetch private and uncached, while queries that don't select it still share cached venues. Often it's better to move per-user fields to a different type or subgraph, so hot public entities stay entirely public.

The CI check, planning every trusted document against the proposed supergraph:

```ts
import { parse } from "graphql";
import { Supergraph, operationFromDocument } from "@apollo/federation-internals";
import { QueryPlanner, type PlanNode } from "@apollo/query-planner";

function depth(node: PlanNode | undefined): number {        // sequential fetch levels
  if (!node) return 0;
  switch (node.kind) {
    case "Fetch":     return 1;
    case "Flatten":   return depth(node.node);
    case "Sequence":  return node.nodes.reduce((sum, n) => sum + depth(n), 0);
    case "Parallel":  return Math.max(0, ...node.nodes.map(depth));
    default:          return depth((node as any).node);       // Condition, Defer, …
  }
}

async function checkPlans(supergraphSdl: string, documents: TrustedDocument[], budget: Budget) {
  const supergraph = Supergraph.build(supergraphSdl);
  const planner = new QueryPlanner(supergraph);
  const failures: string[] = [];

  for (const doc of documents) {
    const started = performance.now();
    const plan = planner.buildQueryPlan(operationFromDocument(supergraph.schema, parse(doc.body)));
    const ms = performance.now() - started;
    const levels = depth(plan.node);

    if (ms > budget.planMs) failures.push(`${doc.name}: planning took ${ms.toFixed(0)} ms`);   // ← aside 3
    if (levels > budget.levelsFor(doc.name)) failures.push(`${doc.name}: ${levels} sequential levels`); // ← aside 4
  }
  return failures;
}
```

**Aside 3: planning time measured here is a proxy.** The production router may use a different planner implementation than these JavaScript packages (Apollo's current router has its own), so absolute times won't match. What matters is the relative signal: an operation whose planning time jumps from 5 ms to 900 ms after a schema change has a problem in any planner. Treat the number as a regression detector, not a production measurement, and confirm large changes against a real router in staging.

**Aside 4: depth budgets belong to screens, not to the graph.** `levelsFor` returns a per-operation budget, because the event page's four levels matter and an admin report's six may not. The defaults can be generous; the operations on critical screens get tight ones, owned by the teams whose pages they are. A single graph-wide number either blocks harmless changes or lets important pages degrade.

- **Apollo router documentation, "Query Plan Caching"**: in-memory and Redis plan caches, warm-up on schema reload, and the point that caching buys stability more than speed.
- **Apollo router documentation, "Traffic Shaping"**: subgraph deduplication and its exact matching rules, timeouts, compression, HTTP/2, and batching.

- **Hive Gateway and WunderGraph Cosmo documentation on caching and deduplication**: how other routers approach the same problems, useful for seeing which parts are universal and which are one vendor's design.
- **Marc Brooker, "Caches, Modes, and Unstable Systems"** (brooker.co.za): why a system that depends on a warm cache behaves differently when it's cold, which is the planning-cache spike from the opening.

---

The habit to take from this: when you put a coordinator in front of many services, its costs don't appear on any one service's dashboard. Planning, waiting between steps, and repeating the same request are all the coordinator's own costs. Measure them where they happen, or you'll keep optimizing the services that aren't slow.
