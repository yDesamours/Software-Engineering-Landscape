# Scaling Subscriptions: Admission, Bursts, and Reconnects

_Module 40.2b — GraphQL Advanced Patterns_

## The Problem

Suppose you run the API behind a sports app. The match page shows the score, the clock, key events, and live stats, and during a match it updates through one subscription:

```graphql
subscription Match($id: ID!) {
  matchUpdated(id: $id) {
    score { home away }
    clock
    events(last: 5) { minute type player { name } }
    stats { possession shots shotsOnTarget corners }
  }
}
```

The team did everything 40.2a describes. Events carry the fields filters need, executions are grouped so all anonymous viewers share one, loaders are fresh per execution, and payloads carry versions. The transport follows Module 9. On a normal Saturday it's unremarkable.

Then came the cup final: 400,000 people on one match page, spread over 40 pods at about 10,000 connections each. Three things went wrong in one evening, and grouping helped with none of them.

**A burst from upstream.** In the 30th minute, the stats provider started sending updates 40 times a second instead of once every 10 seconds, because of a bug in its retry logic. Grouping meant each pod ran only three executions per event (anonymous, signed in, subscriber), so execution was fine. But every event still had to reach every viewer:

```
normal:   0.1 events/s × 400,000 viewers   =     40,000 sends/s
burst:     40 events/s × 400,000 viewers   = 16,000,000 sends/s   (×400)
```

Outbound buffers filled. Module 9's slow-consumer policy disconnected clients whose buffers overflowed (9.1b), which it's supposed to do. About a third of viewers were disconnected within a minute, and they all reconnected.

**One account, 30,000 subscriptions.** A betting-odds partner, integrated through the public API, subscribed to `oddsUpdated(matchId, market)` for 10 markets on each of 3,000 matches that evening, over 300 connections. Every subscription passed the query cost limit from 8.3b, because each one was small. None could be grouped with anyone else's, because nobody else sent those exact variables. At five odds updates per second per market, one account was costing 150,000 executions per second, more than all 400,000 match viewers put together.

**A deploy at halftime.** The team had a fix for the stats burst and rolled it out at halftime, one pod at a time. Each restarted pod dropped its 10,000 connections. The client, on reconnect, did what most clients do: re-run the match page query to get a fresh snapshot, then resubscribe. The snapshot query touches about a dozen tables, and it's a POST with cookies, so nothing in front of the origin could cache it:

```
10,000 reconnects × 12 queries   = 120,000 queries in ~5 s, per pod restarted
```

The database fell over while the seventh pod was restarting. The second half started with the match page showing the halftime score.

None of this is fixed by making each execution cheaper. It's about what a system accepts, how it behaves when more arrives than it can send, and what happens when everyone comes back at once.

## What It Is

Scaling subscriptions is mostly three kinds of control, applied at different points:

- **Admission control** decides which subscriptions a client may hold, and how much ongoing work each may cost.
- **Burst control** decides what happens when events arrive faster than the system can execute and send them: coalesce, degrade, reset, or disconnect.
- **Reconnect control** makes the moment when many clients return at once, after a deploy or a network blip, cheap instead of catastrophic.

The neighbor to separate is 8.3b's query cost analysis. It works because a query's cost is known, or estimable, before it runs. A subscription's cost is its per-event cost multiplied by an event rate that won't be known until later, and possibly never with certainty. So the tools here borrow 8.3b's static analysis for one part and replace it with ongoing accounting for the rest.

## Recognizing the Problem

- One client or account holds thousands of active subscriptions, and you only found out from a memory graph.
- Subscription costs are checked when the subscription starts, and never again.
- An upstream bug or a bulk job can multiply your send rate, and nothing limits it.
- Load on the servers follows event bursts, and slow-consumer disconnects spike during them.
- Deploys cause a visible load spike on the database or the query path, not just on the connection layer.
- Clients re-run their full page query every time they reconnect.
- Nobody can say how many sends per second the system can handle, or what it currently does.
- Events that happen between a client's snapshot query and its subscription are silently missed.

## How It Works

### Why the door can't see the cost

A query's cost is roughly fixed when it arrives. A subscription's isn't:

```
query cost         = f(document, variables)                                    known at the door
subscription cost  = f(document, variables) × event rate(topic, time)          known afterwards
                     └──── per execution ────┘  └──── set by producers ────┘
                   × (1 / group size)          executions shared with other subscribers
                   + sends                     always one per subscriber per event
```

Three of those four factors change after admission: the event rate depends on what happens in the world (a quiet midweek match vs. a final), the group size depends on who else subscribes, and the sends scale with the event rate. So subscription limits come in two kinds: static limits checked at the door, and running budgets accounted as the subscription lives.

### Limits at the door

These are cheap, and they stop the partner in the opening:

- **Per-execution cost.** Run 8.3b's analyzer on the subscription document, with a lower ceiling than for queries, because the result will be paid for repeatedly. A subscription that selects `events(last: 500)` with nested players is fine as a query and expensive as a subscription.
- **Subscriptions per connection and per account.** A match page needs two or three. A limit of 50 per connection and a few hundred per account, higher for partners on a plan that pays for it, rules out the 30,000 case at subscribe time.
- **Topic breadth.** A subscription to "all odds for all matches" is a firehose. Either don't offer it, or offer it only to accounts on a plan built for it, with a dedicated path (below).
- **Who may subscribe at all.** Anonymous subscriptions are the hardest to limit per account. Many systems let anonymous clients poll a cacheable query, or subscribe only to a small set of public topics, and reserve open-ended subscriptions for identified clients.

The rejection should be specific. The `graphql-ws` protocol lets the server reject a single subscribe request with GraphQL errors while the connection stays open, so the client learns which limit it hit ("subscription limit: 50 per connection") rather than seeing a closed socket.

### Running budgets

The door can't see event rates, so the rest is accounting: measure the executions and sends each account actually causes, and act when it exceeds a budget. That's 8.3b's split between estimating to admit and measuring to account, stretched over time. Useful budget units:

- **Executions per second attributed to an account.** A shared execution is split among its group, so a viewer in a group of 10,000 costs almost nothing, and a subscription whose variables nobody else uses carries its full cost. That attribution is exactly what surfaces the partner.
- **Sends per second per connection.** This catches a client whose subscriptions all happen to be on busy topics.

When a budget is exceeded, the options are the same as for rate limits in Module 18: reject new subscriptions, slow the existing ones down (coalesce more aggressively for that account), or end the most expensive ones. For partners, the better long-term answer is usually a different product: a bulk feed, a webhook (Module 17), or a Kafka topic they read directly, built for machine consumers that want everything.

### Limit the producers, not only the consumers

The stats burst started upstream. Every consumer-side limit reacts after the event is already in the system, multiplied by the audience. It's cheaper to limit where events enter:

- **Per-topic event rate limits.** "At most 2 events per second per match" enforced at the publisher, with coalescing: when the limit is hit, keep the latest state and publish it at the next allowed moment. For state-like topics (scores, stats, positions), nothing is lost, since the latest state supersedes the rest.
- **Bulk operations emit summaries.** A job that updates 50,000 records should publish one `bulkChanged(scope)` event, telling clients to refetch, not 50,000 item events multiplied by every subscriber.
- **Separate topics by rate.** Put the goal feed and the per-second stats on different topics, so a client that only shows the score isn't paying for stats, and so a burst on one doesn't affect the other.

### Bursts inside the server: a bounded queue and a ladder

Even with producer limits, events sometimes arrive faster than a pod can execute and send them. 9.1b gave the general backpressure menu (block, reject, drop, degrade, explicit demand). For subscriptions, the natural unit to apply it to is the group from 40.2a: each group gets a bounded queue of pending events, and as the queue fills, the pod moves down a ladder of cheaper behaviors:

```
queue depth   behavior                         what clients see
───────────   ──────────────────────────────   ─────────────────────────────────────
  0 – 8       normal: execute every event      every update
  8 – 32      coalesce per entity              skipped intermediate states
 32 – 128     invalidation only: {id,version}  "something changed"; client refetches
   > 128      reset                            "resync": client drops state, re-snapshots
```

The middle steps are specific to GraphQL subscriptions. **Coalescing** keeps only the latest event per entity (40.2a), which is free for state-like topics. **Invalidation mode** stops executing selection sets at all and sends only the ID and version, which pushes the work to the query path, where it can be cached and where the client fetches it at its own pace. **Reset** tells the client its view is no longer reliable and it should re-snapshot, which is better than a stream of stale updates, but it's the most expensive step for everyone, so it's the last one.

Two properties make the ladder safe. It must move back up once the queue drains, with some hysteresis so it doesn't flap between steps. And it must be visible: the time spent in each mode is a metric, because a system that spends every big match in invalidation mode has a capacity problem, not a burst problem.

### The send path is its own bottleneck

Grouping collapses executions, but not sends: 400,000 viewers still means 400,000 messages per event. Two details make each send cheaper:

- **Serialize once per group.** The payload is identical for every member, so encode it to JSON once. The only per-member part of a `graphql-ws` `next` message is the subscription ID, and that can be spliced into a pre-built envelope instead of re-encoding the whole object 10,000 times.
- **Compression, carefully.** Per-message compression (`permessage-deflate`) cuts bytes but costs CPU per connection, and with context takeover it costs memory per connection too. For large audiences and small payloads, it often costs more than it saves. Measure before enabling it.

### Reconnect storms are snapshot storms

The halftime deploy wasn't a connection problem. Module 9 covered reconnect jitter and backoff, and the reconnections themselves were fine. It was a *query* problem: every reconnecting client re-ran its snapshot query, and the snapshot path had been sized for people arriving gradually, not for 10,000 at once.

Three changes address it, in increasing order of effort:

**Make the snapshot cacheable.** The match page snapshot is the same for every anonymous viewer. Served as a persisted `GET` with a short `max-age` (8.3c), a reconnect storm becomes a CDN hit-rate spike. This is the cheapest fix by far, and it only works for data that's shared.

**Resume instead of re-snapshot.** If events live in a log (9.4) and payloads carry versions, the client can resubscribe with the last version it saw, `matchUpdated(id: $id, since: $version)`, and the server replays what it missed. There's no snapshot query at all unless the gap is too old for the log's retention, in which case the server says so and the client falls back to a snapshot.

**Drain deploys slowly and spread reconnects.** Close connections on a pod gradually over a minute or two instead of all at once, and have the server include a suggested retry delay when it closes a connection for a deploy. Module 9 covered the client side of this; the server side is choosing the drain rate so the snapshot path, not just the connection layer, can absorb it.

There's also a correctness problem hiding in the snapshot pattern. If the client queries first and subscribes second, any event that happens between the two is lost: the snapshot was taken before it, and the subscription started after it. On a quiet page this is rare. During a reconnect storm, when snapshot queries are slow, the gap is seconds wide, and a goal can fall into it. The fix is to **subscribe first, buffer, then query**, and apply buffered events whose version is newer than the snapshot's. With versions on every payload (40.2a), that reconciliation is a comparison.

```
wrong:   query ─────── snapshot@v41 ──── subscribe ─── events from v44 on     (v42, v43 lost)
right:   subscribe (buffer) ── query ── snapshot@v41 ── apply buffered v42, v43, then live
```

### Knowing your numbers

Capacity planning for subscriptions comes down to a few rates, and all of them should be dashboards:

```
executions/s  = Σ over topics ( events/s × groups subscribed to that topic )
sends/s       = Σ over topics ( events/s × subscribers to that topic )
group ratio   = subscribers / groups          (how much grouping is saving)
```

Watch them per topic and per account, alongside queue depth, time spent on each ladder step, slow-consumer disconnects, and snapshot query rate. Load tests should model the worst plausible combination: the largest audience on the busiest topic during a producer burst, followed by a deploy. That's the evening in the opening, and it's the one that decides capacity.

## When It's Appropriate

- **Large audiences on shared topics.** Tens of thousands of subscribers on one topic, where sends dominate and one burst is multiplied by the whole audience.
- **Open APIs with subscriptions.** Partners and third-party developers will subscribe to whatever you allow, as broadly as you allow. Per-account limits and running budgets are necessary before the first one integrates.
- **Upstream sources you don't control.** Data providers, devices, or other teams' services that can emit bursts. Producer-side limits pay for themselves the first time one misbehaves.
- **Frequent deploys during peak usage.** If you ship during the hours when most clients are connected, the reconnect path needs to be sized for it.

## When It's Unnecessary or Overkill

- **Small audiences per topic.** With tens of subscribers per topic and a few hundred connections per pod, sends aren't a bottleneck and a degrade ladder is machinery with nothing to do. Door limits are still worth having.
- **Internal apps with known clients.** If every client is yours and deploys with the server, limits on subscriptions per connection are a sanity check, not a policy system.
- **When polling would do.** If the ladder spends most of its time in invalidation mode, the feature is effectively polling with extra infrastructure. A cacheable query with a refresh interval may be the honest design (40.2a's Alternatives).

## Trade-offs

**Limits break legitimate clients.** Every limit will eventually be hit by someone with a real use case, like a broadcaster's dashboard that watches 200 matches. Limits need a documented way to ask for more and a plan tier that allows it, or they become a support queue.

**Degradation changes what clients must handle.** A client that assumed every update arrives now has to handle coalesced updates, invalidations, and resets. Each is simple, but all of them have to be implemented and tested, including in old app versions that predate the ladder. A server can't send invalidation-only payloads to a client that doesn't understand them.

**Running budgets need attribution infrastructure.** Splitting a shared execution's cost across its group, per account, per second, is real accounting work, and it's easy to get attribution subtly wrong in ways that make a heavy account look cheap.

**Producer limits move the delay upstream.** Coalescing at the publisher means some consumers get state that's up to one interval old. For a score, a second is fine. For a bid at an auction's closing seconds, it may not be, and such topics need their own limits.

**Resume needs a log.** Replaying from a version means retaining events long enough to cover typical disconnections, which is a storage and operations cost, and a retention window that's shorter than a deploy makes resume fail exactly when it's needed.

**More moving parts during incidents.** Queues, ladder states, budgets, and drain rates are all things an on-call engineer must understand at 21:30 on cup final night. Each needs a clear metric and a documented meaning.

## Alternatives

**Overprovision for the peak.** Size for the largest known event and don't build limits or ladders. It's reasonable when peaks are predictable and infrequent (a few finals a year), and the cost of idle capacity is smaller than the cost of engineering. It doesn't protect against the partner or the upstream bug, which aren't about peak audience.

**Managed real-time services.** Hosted pub/sub services handle connection scale and fan-out, and some offer GraphQL subscription layers. They move the send path and connection handling off your servers, but not the cost of executing selection sets, not per-account limits on your API, and not the snapshot path.

**Separate products for machine consumers.** Instead of limiting partners inside the subscription API, give them a feed built for them: a Kafka topic, a webhook stream, or a bulk endpoint. This is often better than any limit, because a partner who wants every odds change for every match is a data-integration customer, not a viewer.

## How to Achieve It

**Level 0: measure.** Add the rates above as metrics, per topic and per account: events, groups, subscribers, executions, sends, queue depth, slow-consumer disconnects, snapshot queries. You can't set limits without knowing normal. *Next step when:* you can see which accounts and topics drive load.

**Level 1: limits at the door.** Cap subscriptions per connection and per account, and run the cost analyzer on subscription documents with its own ceiling. Reject with specific errors. *Next step when:* the remaining load spikes come from event bursts or reconnects rather than from what clients subscribe to.

**Level 2: control producers and fix snapshots.** Add per-topic event rate limits with coalescing, bulk summary events, and a cacheable snapshot path. Switch clients to subscribe-then-query. *Next step when:* bursts still reach the send path, or deploys still spike the snapshot path for data that can't be cached.

**Level 3: the ladder and resume.** Bounded group queues with coalescing, invalidation, and reset, plus resume from a version against a log. Update clients to handle all three and to resume. *Next step when:* expensive accounts are still hard to see or control.

**Level 4: running budgets.** Attribute executions and sends to accounts, enforce budgets, and move heavy machine consumers to dedicated feeds.

## Implementation

TypeScript with `graphql-ws`, continuing 40.2a's server. The first snippet is admission at the door. The second is the group queue with its ladder, including the send path.

Admission, in `graphql-ws`'s `onSubscribe` hook:

```ts
useServer({
  schema,
  onSubscribe: async (ctx, msg) => {
    const doc = parse(msg.payload.query);
    if (!isSubscription(doc)) return;                        // queries and mutations: normal path

    const conn = ctx.extra.state;
    if (conn.subscriptionIds.size >= LIMITS.perConnection) {
      return [new GraphQLError(`subscription limit reached: ${LIMITS.perConnection} per connection`)];
    }
    if ((await accounts.activeSubscriptions(conn.accountId)) >= limitFor(conn.plan)) {
      return [new GraphQLError("subscription limit reached for this account")];   // ← aside 1
    }
    const cost = estimateCost(schema, doc, msg.payload.variables);   // 8.3b's analyzer
    if (cost > LIMITS.subscriptionExecutionCost) {
      return [new GraphQLError(`subscription too expensive: ${cost} > ${LIMITS.subscriptionExecutionCost}`)];
    }
    conn.subscriptionIds.add(msg.id);                          // admitted
  },
  onComplete: (ctx, msg) => { ctx.extra.state.subscriptionIds.delete(msg.id); },
}, wsServer);
```

**Aside 1: returning errors rejects one subscription, not the connection.** `graphql-ws` sends these as an `error` message for that subscription ID, and the client's other subscriptions keep running. Account-level counts live in a shared store because an account's connections are spread over many pods, which means the count can briefly overshoot when two pods admit at the same moment. That's acceptable for a limit meant to stop 30,000, not 51.

The group queue, with the ladder and a shared serialized payload:

```ts
class GroupQueue {
  private pending = new Map<string, Event>();     // keyed by entity: coalescing is built in
  private mode: "normal" | "coalesce" | "invalidate" = "normal";

  push(e: Event) {
    if (this.mode === "normal" && this.pending.size >= 8) this.mode = "coalesce";
    if (this.pending.size >= 128) return this.reset();                     // ← aside 2
    if (this.pending.size >= 32) this.mode = "invalidate";
    this.pending.set(this.mode === "normal" ? e.id + ":" + e.version : e.entityId, e);
    this.schedule();
  }

  private async drain() {
    for (const [key, e] of this.pending) {
      this.pending.delete(key);
      const payload = this.mode === "invalidate"
        ? { data: null, extensions: { invalidate: { id: e.entityId, version: e.version } } }
        : await this.group.execute(e);                                    // one execution per group
      const body = JSON.stringify(payload);                               // ← aside 3
      for (const m of this.group.members) {
        m.socket.send(`{"id":${JSON.stringify(m.opId)},"type":"next","payload":${body}}`);
      }
    }
    if (this.pending.size < 4) this.mode = "normal";                      // hysteresis: back up only when nearly empty
  }

  private reset() {
    this.pending.clear();
    for (const m of this.group.members) m.sendReset();   // client drops state and re-snapshots (or resumes)
  }
}
```

**Aside 2: reset is a message, not a disconnect.** Closing sockets at this point would turn a burst into a reconnect storm, which is the halftime incident started from the other end. A reset tells clients to resynchronize on the connection they already have, ideally by resuming from their last version, which costs far less than a snapshot. Clients stagger it themselves if they fall back to a snapshot.

**Aside 3: one `JSON.stringify` per event, not per member.** At 10,000 members per group, encoding the payload per member is 10,000 identical encodings. Here it's encoded once, and only the subscription ID is spliced into each envelope. This bypasses the library's normal per-message formatting, so any per-subscriber hook (such as `onNext`) won't run on this path. That's the point of it, but it means per-subscriber transformations can't live there anymore.

The invalidation payload shape needs to be agreed with clients before the ladder ships. A client that doesn't recognize it would treat `data: null` as "the match disappeared," which is worse than a late update.

## Further Reading

- **The `graphql-ws` server documentation and `PROTOCOL.md`** (github.com/enisdenjo/graphql-ws): `onSubscribe` rejections, `onNext`, `onComplete`, and per-operation errors, which are the hooks admission control uses.
- **RFC 7692, "Compression Extensions for WebSocket"**: `permessage-deflate` and context takeover, to understand the per-connection memory and CPU cost before enabling it for large audiences.
- **Shopify's GraphQL Admin API documentation, "rate limits" and "calculated query costs"**: the published model for charging queries in cost points against a refilling bucket, the closest public analogue to per-account subscription budgets.
- **Hasura, "Scaling to 1 million active GraphQL subscriptions (live queries)"**: capacity numbers and how grouping changes them; useful as a reference point for what the execution side can do once sends are the limit.
- **_Site Reliability Engineering_ (Google), chapter 22, "Addressing Cascading Failures"**: load shedding, graceful degradation, and why retries and reconnects make overloads worse. The ladder and the reconnect advice are specific cases of it.
- **In this collection:** 40.2a (grouping, coalescing, versions), 8.3b (cost analysis and estimate-then-account), 8.3c (cacheable persisted queries for the snapshot), 9.1b (backpressure menu, reconnect behavior), 9.4 (logs for resume), Module 18 (rate-limit algorithms for budgets), Module 17 (webhooks as a partner alternative).

A Go sibling would be worth writing for the send path. In Go, a group's fan-out to 10,000 per-connection writer goroutines (9.1b's single-writer pattern) makes the cost of each send, and the effect of a full per-connection channel, explicit in a way the Node event loop hides. It would show where aside 3's savings actually come from. Not yet written.

---

The habit to take from this: for any system that multiplies (one event to many subscribers, one deploy to many reconnects, one bulk job to many events), find the multiplication and put a limit on each side of it. Limit what goes in, bound what's queued, and make what comes back cheap. The failures in the opening each came from one side of a multiplication with no limit on it.
