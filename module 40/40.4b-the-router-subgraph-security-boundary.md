# The Router–Subgraph Security Boundary

_Module 40.4b — GraphQL Advanced Patterns_

## The Problem

Suppose you run the API for a field-service platform: companies use it to schedule technicians, track jobs at customers' sites, and invoice for the work. It's multi-tenant (Module 5), and it's a federated graph (40.1a) with subgraphs for jobs, scheduling, customers, and billing. The router validates each user's login token and tells the subgraphs who's calling by adding two headers, `x-tenant-id` and `x-user-id`. Every subgraph scopes its queries by the tenant in that header.

A security review in one month found four problems. None of them was a bug in a resolver in the usual sense.

**A header anyone could set.** The router's header configuration forwarded all client headers to subgraphs, a convenience added early so teams could pass tracing and feature-flag headers without asking. The router set `x-tenant-id` from the token, but only if the header wasn't already present. A client that sent its own `x-tenant-id: t_other` was, as far as every subgraph could tell, a member of another company.

**A path the billing team didn't know about.** Billing guarded its root field carefully: `Query.invoice(id:)` requires the `billing:read` permission, which technicians don't have. But the jobs team had added `Job.invoice`, returning the `Invoice` entity by key, so the job page could show whether the job had been billed. Composition passed, as it should. From then on, a technician could query `job(id: "j_1") { invoice { total lineItems { description amount } } }`. The router fetched the invoice from billing through `_entities`, and billing's reference resolver and field resolvers checked tenant but not permission, because the permission check lived on the root field.

**A subgraph on the internet.** A change to the ingress configuration gave the billing subgraph a public hostname. The subgraph trusted the `x-tenant-id` header, since only the router was supposed to reach it. A penetration tester asked it for `_service { sdl }`, which returned the full subgraph schema, including fields hidden from clients with `@inaccessible`. Then they called `_entities` directly with invoice IDs from their own account's URL pattern and a different tenant header.

**An error that said too much.** During an incident, someone turned on full subgraph error pass-through at the router to debug a failure, and left it on. For three weeks, a malformed filter returned a Postgres error to clients that included the table name, a column list, and part of the SQL.

The common thread is that the team treated the router as the security boundary, and everything behind it as trusted. In a federated graph, that's four assumptions: that only the router can reach subgraphs, that what the router forwards is what the router meant, that authorization on the paths you know covers the paths you don't, and that what subgraphs say is fit for clients to see.

## What It Is

This article is about the **router–subgraph boundary**: how subgraphs know that a request came from the router, how they know which user it's for, which authorization happens at the router and which in the subgraph, and what crosses the boundary in each direction.

It builds on two earlier pieces. 8.4 established that GraphQL authorization has no route to guard, and that checks belong where the number of paths stops mattering, which is on types and fields, failing closed. 40.1a noted that entity resolvers are entry points that bypass root fields, and that `@requires` data arrives on trust. Federation adds a twist to both: **other teams can create paths to your types without touching your code.** The jobs team created a path to `Invoice.total` by adding one field to their own schema.

## Recognizing the Problem

- Subgraphs read the user or tenant from plain headers, and would believe anyone who sent them.
- The router forwards client headers by pattern, or all of them.
- Nothing stops a request to a subgraph that didn't come from the router, except network configuration nobody tests.
- Authorization checks are on root fields, and entity reference resolvers check tenant or nothing.
- You can't list every path in the supergraph that reaches your sensitive types.
- Another subgraph uses `@provides` for fields you consider sensitive.
- Subgraph schemas, including `@inaccessible` fields, are retrievable from subgraphs through `_service`.
- Subgraph error details are passed to clients, or can be switched on without review.

## How It Works

### Two layers, each with a job

```
client ──► ROUTER ─────────────────────────────────────────► SUBGRAPH
           · authenticate the user (validate the token)       · authenticate the caller: is this the router?
           · strip identity headers the client sent            · authenticate the user: verify the identity it was given
           · coarse authorization: scopes, roles, policies     · object-level authorization, on every path,
             (fields removed before planning)                    including entity resolution
           · cost, depth, rate limits (40.4a)                  · tenant scoping inside data access
           · redact subgraph errors                            · its own limits (40.4a)
                  │
                  └─ one identity, stated once, in a form the subgraph can verify ─┘
```

The router is the right place for everything that can be decided from the request and the user's claims alone. The subgraph is the only place for decisions that need the data: *is this invoice in this user's tenant, for a customer this user may see?* Neither layer can do the other's job, and a failure in the opening came from each layer assuming the other was doing more than it was.

### Only the router gets in

Subgraphs aren't designed to face clients. They expose `_entities`, which returns any entity for any key the caller supplies, and `_service`, which returns the subgraph's full schema, including fields the supergraph hides. Apollo's own security guidance is direct about this: only the router should query subgraphs.

Network placement is the first control: subgraphs in a private network, reachable only from the router's network. But the third incident shows why it can't be the only one. Network configuration changes, often in a different repository from the one where anyone reviews GraphQL security, and a subgraph that's safe only while the network is right is one ingress change away from being public.

So the subgraph should also **authenticate its caller**:

- **Mutual TLS** between router and subgraphs, usually provided by a service mesh (36.1), gives each subgraph a verified identity for the caller. The subgraph (or its sidecar) accepts only the router's identity.
- **Signed requests** do the same without a mesh: the router signs each subgraph request (Apollo's router supports AWS SigV4 for subgraphs hosted behind AWS services, for example), or presents a token that proves it's the router.

Either way, a request that reaches the subgraph from anywhere else fails authentication, whatever the network does.

### Identity: stated once, verifiable, and never taken from the client

Once the subgraph knows the router sent the request, it needs to know which user the request is for. There are three common designs, and the choice decides how much a subgraph must trust:

| Design | What subgraphs receive | Risk |
|---|---|---|
| Forward the user's own token | the client's login token | Every subgraph validates it (fine), but the token's audience is your public API, so any service that receives it can replay it anywhere else that audience is accepted. Subgraphs also handle raw credentials. |
| Router validates, sends claims as headers | `x-tenant-id`, `x-user-id` in plain text | Only as safe as the network *and* the router's header rules. Anyone who reaches a subgraph, or gets a header past the router, is whoever they say they are. The opening's design. |
| Router issues an internal token | a short-lived token signed by the router, for one subgraph | The subgraph verifies the signature and audience. A reachable subgraph still can't be fooled without the router's key, and a token captured in one subgraph can't be used in another. |

The third design is the standard pattern for this, generally called **token exchange** (RFC 8693 describes a protocol for it): the router exchanges the user's external token for an internal one that carries only what subgraphs need (user, tenant, scopes, a request ID), expires in a minute or two, and names the subgraph it's for as its audience. The router can mint it itself or ask an internal token service. Either way, every subgraph gets the same verified statement of identity and has to trust nothing else.

Whatever the design, one rule is absolute: **the router must remove any identity-bearing header the client sent** before adding its own. The first incident was a router that *added* `x-tenant-id` only when it was absent. The correct order is: strip first, then set. And it's much safer to forward headers by an allowlist (the specific tracing and locale headers subgraphs need) than by a pattern or blocklist, because a blocklist doesn't know about the header someone invents next year. 40.3b made the same argument for performance; here it's a security requirement.

### Coarse authorization at the router

Some authorization needs only the user's claims: "only users with `billing:read` may see invoice amounts," "only authenticated users may see customer addresses." These can be declared in subgraph schemas and enforced by the router before any fetch happens.

Apollo's router offers three directives for this: `@authenticated`, `@requiresScopes`, and `@policy` (which delegates the decision to custom logic). Subgraph teams put them on their own types and fields, composition carries them into the supergraph, and the router removes unauthorized fields from the query *before planning*. The response has `null` for those fields with an authorization error, or the router rejects the whole operation, depending on configuration. When two subgraphs put different requirements on the same shared field, composition combines them with AND, so the stricter one wins.

The important property is that these checks are **on the type or field, not on the path**. If billing had put `@requiresScopes(scopes: [["billing:read"]])` on `Invoice.total`, the router would have removed `total` from the technician's query whether it arrived through `Query.invoice` or through `Job.invoice`. That's 8.4's principle, enforced before any subgraph is called.

### Object-level authorization in the subgraph, on every path

Claims alone can't answer "may *this* user see *this* invoice?" The answer depends on the invoice's tenant, the customer it belongs to, and maybe the user's assignment to that customer. That check has to happen where the data is, in the subgraph.

In a federated graph, the part that's easy to miss is *where in the subgraph*. A subgraph serves its entities through two kinds of entry point: its own root fields, and entity resolution (`_entities`, or `@lookup` fields in the Foundation spec). Root fields are the paths the owning team designs. Entity resolution is the path every other team uses, and it's where the jobs team's `Job.invoice` arrived. So object-level checks belong in something both entry points go through:

- **In data access.** The loader that fetches invoices takes the caller's tenant and applies it in the query itself, so an invoice from another tenant simply isn't found, from any path. This is the tenant scoping from Module 5, and it's the strongest version because nothing above it can forget.
- **On the type.** A fail-closed field policy for `Invoice`, as in 8.4, applied to the type's fields regardless of how the object was reached.
- **In the reference resolver, too.** If an entity must not be visible at all to some users, check it where entities are resolved, not only where root fields return them.

### Other teams can add paths to your types

This is the part that's genuinely new with federation. In a single server, a new path to `Invoice` was a code change someone reviewed. In a federated graph, any subgraph can reference your entity by key, and composition will happily build the path. Composition checks that the schemas fit together; it doesn't check that the new path is authorized.

Three practices follow:

- **Assume every entity is reachable from anywhere.** Design your entity's authorization as if any other subgraph might link to it tomorrow, because one will.
- **Route new references to sensitive entities for owner review.** 40.1b's review routing can include this: a schema change that adds a field returning `Invoice`, in any subgraph, requests review from billing.
- **Never let another subgraph `@provides` your sensitive fields.** `@provides` lets a subgraph return another subgraph's fields itself, on its own path. If jobs declared `Job.invoice @provides(fields: "total")` and stored a copy of the total, the router would take `total` from jobs, and billing's authorization would never run at all. For sensitive fields, the owning subgraph must be the only one that serves them. A lint rule can enforce it.

### Data from other subgraphs is input, not authority

40.1a's aside 2 made the point that `@requires` fields arrive in the representation, supplied by the router from another subgraph, and the receiving subgraph can't verify them. Put in security terms: **never make an authorization decision from a `@requires` field.** If scheduling needs to know whether a technician is certified for a job type before showing hazardous-site details, it should look up the certification itself, or get it from the verified identity token, not require `Technician.certifications` from another subgraph and believe what arrives.

The same applies to anything a subgraph receives from the router that the router didn't generate and sign itself. The internal identity token is authority. Representations are input.

### What leaves the subgraph

The last boundary runs in the other direction: what subgraphs say, and how much of it reaches clients.

- **Errors.** Subgraph errors can contain SQL, stack traces, internal hostnames, or data from another tenant in a message. Apollo's router redacts subgraph error details by default, and can allow specific error codes and extension keys per subgraph. Keep the default, allow only what clients need (an error code, a safe message), and treat turning on full pass-through as a change that needs review and an expiry, like the fourth incident should have had.
- **Schemas.** `_service { sdl }` returns everything, including fields the supergraph hides with `@inaccessible`. Introspection being disabled at the router doesn't disable it at subgraphs. Only the router, and the schema registry, should be able to fetch subgraph schemas.
- **Hidden isn't secured.** `@inaccessible` removes a field from the client-facing schema. It doesn't stop a subgraph from serving it to anyone who reaches the subgraph. It's a design tool, not an access control.

### Callbacks and other inbound paths

Some federation features make the router a server for subgraphs. Subscription callbacks (40.2a) have subgraphs send events to an endpoint on the router, and cache invalidation (40.3b) has subgraphs call the router's invalidation endpoint. Each of those endpoints needs its own authentication, the reverse direction of everything above. A public, unauthenticated invalidation endpoint is a way for anyone to empty your cache, and an unauthenticated callback endpoint is a way to inject events into other users' subscriptions.

## When It's Appropriate

- **Every federated graph that holds data some users mustn't see.** Which is nearly every one. The router layer and subgraph authentication are baseline, not optional.
- **Multi-tenant graphs.** Tenant scoping in each subgraph's data access, from a verified identity, is the control that makes a cross-tenant leak require several independent failures instead of one.
- **Graphs where many teams contribute.** The more teams can add paths to each other's entities, the more type-level and data-level authorization matters compared with root-field checks.
- **Internal token issuance, specifically,** when subgraphs run on shared infrastructure, when network isolation is hard to guarantee, or when compliance requires that each service verify identity itself.

## When It's Unnecessary or Overkill

- **Signed internal tokens for a small graph on an isolated network.** Two subgraphs and a router on one private network, with mTLS from a mesh and header stripping at the router, is a defensible design. Token exchange adds a key to manage and a signature to verify on every request, and may be more than that setup needs.
- **Router-level policies for decisions that need data.** Pushing object-level checks into router policies, by having the router fetch data to decide, duplicates the subgraph's logic in a place that doesn't own the data. Keep the router's checks to claims.
- **Per-field scope directives on everything.** Annotating every field with scopes produces an unreadable schema and permission sprawl. Use them on the sensitive types and fields, and rely on tenant scoping and type-level policies for the rest.

## Trade-offs

**Two layers means two places to keep consistent.** A scope check at the router and an object check in the subgraph can disagree, and each team may assume the other is the real control. The division has to be explicit: the router handles claims and removes fields; subgraphs handle objects and tenancy; neither relies on the other for its own job.

**Internal tokens add key management.** The router's signing key becomes one of the most sensitive secrets in the system, since whoever has it can impersonate any user to every subgraph. It needs rotation, storage in a secrets manager (20.3), and subgraphs that accept both old and new keys during rotation.

**Header allowlists create friction.** Teams that need a new header must ask for it to be allowed, which is slower than a pattern that forwards everything. That friction is the point, but it needs a quick, clear process or teams will route around it.

**Type-level authorization runs more often.** Checking on every field of every entity, from every path, costs more than one check on a root field, especially for lists. Loaders and cached permission lookups (8.4) keep it affordable.

**Redacted errors slow down debugging.** Clients and developers see "Subgraph errors redacted" where they used to see the cause. Structured error codes, request IDs that link a client error to router and subgraph logs, and good tracing (36.4) are what make redaction bearable.

**Reviewing new references slows some changes.** Requiring the owner's review whenever another subgraph links to a sensitive entity adds a step for exactly the kind of change federation was supposed to make independent. Limiting it to sensitive entities keeps the cost small.

## Alternatives

**Network isolation alone.** Private network, no subgraph authentication, identity in plain headers. It's the most common setup and the one in the opening. It works while the network is right and the router strips headers correctly, and it fails completely when either is wrong. Treat it as a first layer, not the design.

**Every subgraph validates the user's token directly.** No router-issued identity: each subgraph checks the client's token against the identity provider. It removes trust in the router for identity, which is sometimes a compliance requirement, but it spreads token handling and audience confusion across every subgraph, and subgraphs still need to know the router is the caller.

**Authorization only in subgraphs.** No router directives; every decision in the owning subgraph. It keeps authorization in one place per type, and it's robust if done on types and in data access. What it loses is early removal of unauthorized fields: the router fetches data that will be denied, and clients get less consistent errors.

**A central authorization service.** Router and subgraphs both ask a policy service (for example, one based on Open Policy Agent or a relationship-based system like Zanzibar-style services) for decisions. It centralizes policy for many services, not only GraphQL, and fits organizations that already run one. The data-dependent checks still happen where the data is, because the policy service has to be given or fetch the facts.

## How to Achieve It

**Level 0: close the obvious holes.** Strip identity headers from client requests at the router, and switch header forwarding to an allowlist. Confirm subgraph error redaction is on, and put any exceptions under review. Check that no subgraph is reachable from outside the router's network, from the outside. *Next step when:* a client can't set its own identity, and a scan from the internet reaches no subgraph.

**Level 1: authenticate the caller.** Add mTLS between router and subgraphs, through a mesh or directly, or signed router requests. Subgraphs reject anything else. *Next step when:* a request to a subgraph from anywhere but the router fails even if the network allows it.

**Level 2: move authorization onto types and into data access.** Tenant scoping in every subgraph's data layer, from the verified identity. Type-level policies for sensitive entities, applied on entity resolution as well as root fields. Scope directives on sensitive fields so the router removes them early. *Next step when:* every sensitive type is safe from any path, which you can test by querying it through every reference in the supergraph.

**Level 3: verifiable identity.** Replace plain identity headers with a short-lived, per-subgraph internal token issued by the router or a token service. Subgraphs verify signature, audience, and expiry, and read identity only from it. *Next step when:* a request that reaches a subgraph without the router can't impersonate anyone.

**Level 4: govern new paths.** Add review routing for new references to sensitive entities, a lint rule against `@provides` on sensitive fields, and a periodic check that lists every path to each sensitive type. Authenticate the router's inbound endpoints (callbacks, invalidation).

## Implementation

TypeScript for the subgraph side, where most of the work is, with the router's part shown as configuration and schema. The subgraph code is the billing subgraph from the opening, fixed.

The router's part: strip client identity headers, forward by allowlist, and keep subgraph errors redacted. In Apollo's router configuration:

```yaml
headers:
  all:
    request:
      - remove:
          named: "x-tenant-id"          # never let a client state its own identity   ← aside 1
      - remove:
          named: "x-user-id"
      - propagate:
          named: "traceparent"           # allowlist: only what subgraphs actually need
      - propagate:
          named: "accept-language"
include_subgraph_errors:
  all: false                             # the default; exceptions per subgraph, reviewed
```

And billing's schema, putting the permission on the field rather than the root:

```graphql
type Invoice @key(fields: "id") {
  id: ID!
  status: InvoiceStatus!                                        # visible to anyone who can see the job
  total: Money!       @requiresScopes(scopes: [["billing:read"]])
  lineItems: [LineItem!]! @requiresScopes(scopes: [["billing:read"]])
}
```

**Aside 1: removing is only half of it.** These rules stop the client's headers from reaching subgraphs. The identity the subgraphs *do* use comes from the internal token the router attaches (through a coprocessor or plugin that validates the user's token and signs a new one), in the next snippet's `authorization` header. Once subgraphs read identity only from that token, a stray `x-tenant-id` does nothing, and these `remove` rules become a second line of defense rather than the only one.

The billing subgraph's context, which trusts only a verified token:

```ts
import { jwtVerify, createRemoteJWKSet } from "jose";

const ROUTER_KEYS = createRemoteJWKSet(new URL(process.env.ROUTER_JWKS_URL!));

async function context({ req }: { req: IncomingMessage }): Promise<Ctx> {
  if (!req.socket.authorized) throw unauthenticated("caller is not the router");   // mTLS  ← aside 2

  const token = bearer(req.headers.authorization);
  const { payload } = await jwtVerify(token, ROUTER_KEYS, {
    issuer: "router.internal",
    audience: "billing",                   // a token minted for another subgraph fails here
    maxTokenAge: "2m",
  });

  const viewer = { userId: payload.sub!, tenantId: claim(payload, "tenant"), scopes: scopesOf(payload) };
  return { viewer, loaders: createLoaders(viewer) };        // headers like x-tenant-id are never read
}
```

**Aside 2: two separate questions, answered by two mechanisms.** mTLS answers "is the caller the router?" The token answers "which user is this request for?" A subgraph reachable from the internet, like billing in the opening, would now fail the first check. A request that came through the router but carried a forged identity header would fail the second, because the identity isn't in a header anymore. Either failure alone no longer exposes anything.

Tenant scoping in data access, and authorization on the type, so every path is covered:

```ts
function createLoaders(viewer: Viewer) {
  return {
    invoice: new DataLoader<string, InvoiceRow | null>(async (ids) => {
      const rows = await db.query(
        "SELECT * FROM invoices WHERE id = ANY($1) AND tenant_id = $2",     // ← aside 3
        [ids, viewer.tenantId],
      );
      return ids.map((id) => rows.find((r) => r.id === id) ?? null);
    }),
  };
}

const resolvers = {
  Query: {
    invoice: (_: unknown, { id }: { id: string }, ctx: Ctx) => ctx.loaders.invoice.load(id),
  },
  Invoice: {
    __resolveReference: (ref: { id: string }, ctx: Ctx) => ctx.loaders.invoice.load(ref.id),  // ← aside 4
    total: guarded("billing:read", (inv: InvoiceRow) => inv.total),
    lineItems: guarded("billing:read", (inv: InvoiceRow, _: unknown, ctx: Ctx) =>
      ctx.loaders.lineItems.load(inv.id)),
  },
};
```

**Aside 3: the tenant is in the query, not in a check after it.** An invoice from another tenant isn't fetched and then rejected; it's never found. That holds for `Query.invoice`, for `Job.invoice` through `_entities`, and for any path another team adds next year. It's also why the tenant has to come from the verified token: if it came from a header, this line would faithfully scope the query to whatever tenant the attacker named.

**Aside 4: the reference resolver goes through the same loader.** This is the line that closes the second incident's gap for tenancy. Entity resolution uses the same scoped loader as the root field, so there's no second, less careful way to get an invoice. The scope checks on `total` and `lineItems` then cover the permission gap, both here with `guarded` and at the router with `@requiresScopes`. The duplication is deliberate: the router's check removes the field before any fetch, and the subgraph's check holds even if the router's directive is missing or misconfigured.

---

The habit to take from this: whenever you put a gateway in front of services, write down exactly what the services believe because the gateway exists. Here it was four beliefs: that only the gateway can reach them, that identity headers came from the gateway, that the paths the gateway knows about are the only ones, and that clients never see what services say. Each belief is either enforced somewhere you can test, or it's a hole that hasn't been found yet.
