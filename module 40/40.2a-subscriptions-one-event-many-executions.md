# Subscriptions: One Event, Many Executions

_Module 40.2a — GraphQL Advanced Patterns_

## The Problem

Suppose you're building an issue tracker. Teams watch a project board, and when someone changes an issue, everyone looking at the board sees it move. The GraphQL API already serves the board as a query, so the live updates are a subscription:

```graphql
subscription BoardUpdates($projectId: ID!) {
  issueUpdated(projectId: $projectId) {
    id
    title
    status
    assignee { name avatarUrl }
    labels { name color }
    commentCount
  }
}
```

The transport was done properly, following Module 9: WebSockets with heartbeats and resume (9.1b), a Redis backplane with one channel per project so every pod gets only the events it needs (9.1c), and sequence numbers for gap detection. In testing with twenty people, it was perfect.

Then the company held its quarterly planning day. 1,800 people had the main roadmap board open at once.

**Load.** Each `issueUpdated` event has to be turned into a GraphQL response, and that means running the selection set above: the `assignee` resolver, the `labels` resolver, and a `COUNT(*)` for `commentCount`. With per-request loaders (8.3a), that's three database queries per execution. But each subscriber's execution is a separate request, so loaders can't batch across subscribers. One edit:

```
1 event × 1,800 subscribers × 3 queries           =      5,400 queries
a PM drags 200 issues into the next sprint
200 events × 5,400                                 =  1,080,000 queries in ~2 s
```

The database pinned at 100% CPU for four minutes, and everything slowed down, including people who weren't using the board at all. The transport delivered all 360,000 messages without complaint. The cost was entirely in executing the same selection set 1,800 times per event.

**Authorization.** A contractor was removed from a confidential project at 10:00. The subscription's resolver had checked access when the subscription started, at 09:12, and never again. The contractor's laptop kept receiving that project's issue updates, titles and all, until it went to sleep at 18:40.

**Order.** Two edits to the same issue arrived 30 ms apart: status to "In review," then status to "Done." They were executed on the same pod, but the first execution missed the cache on `assignee` and took 60 ms, while the second took 12 ms. The second payload was sent first. Clients applied "Done," then "In review," and the board showed the older status until someone reloaded.

None of these is a transport problem, and Module 9 didn't claim to solve them. They're what happens between the event arriving at the right pod and the bytes leaving for the client: the part that's specific to GraphQL.

## What It Is

A GraphQL **subscription** is an operation that returns a stream of results instead of one. 8.1a introduced it in a paragraph; the part that matters here is how the spec defines its execution, because it has two stages:

1. The **source stream.** When a client subscribes, the server calls the subscription root field's resolver once. It returns a stream of events, usually by subscribing to a topic on a broker.
2. The **response stream.** For *each* event in the source stream, the server executes the operation's selection set with the event as the root value, and sends the result.

```
          subscribe once                      execute per event, per subscriber
client ──────────────────► source stream ──► event ──► [selection set] ──► payload ──► client
                              (a topic)       event ──► [selection set] ──► payload ──►
                                              event ──► [selection set] ──► payload ──►
```

Everything in the opening follows from that second stage. The selection set runs once per event per subscriber; authorization in resolvers runs on each of those executions, but authorization in the subscribe step runs once; and executions of different events aren't ordered with respect to each other.

The neighbor to separate is a **live query**: a query marked (often with a `@live` directive) that the server re-sends whenever its result would change. A subscription is about events: "tell me when an issue is updated." A live query is about state: "keep this result current." Live queries aren't in the GraphQL spec, but several servers implement them, and they come back in Alternatives.

## Recognizing the Problem

- Database load or CPU jumps in proportion to the number of connected subscribers, not the number of events.
- A bulk operation (import, bulk edit, bulk status change) makes the whole system slow for minutes.
- Subscription resolvers check permissions in the subscribe step only.
- Users who lost access keep receiving updates until they reload or reconnect.
- Clients occasionally show an older state after a newer one, and it fixes itself on reload.
- Loaders or caches are created when the WebSocket connects and live for the whole connection.
- You filter events by running the full execution and then discarding the result.
- In a federated graph, one subgraph's event rate shows up as request load on other subgraphs.

## How It Works

### Where the cost is

The spec's two-stage design gives three places to spend work, with very different multipliers:

```
                     runs                          multiplier
subscribe step       once per subscription         subscribers
filter               once per event per subscriber events × subscribers   (cheap if on the event)
execute              once per event per subscriber events × subscribers   (expensive: resolvers)
serialize + send     once per event per subscriber events × subscribers
```

The design goal is to make as much work as possible happen once per event instead of once per event per subscriber, and to make the per-subscriber part cheap. Each technique below does one of those.

### Filter on the event, before executing

Topic granularity is the first filter, and it happens in the broker: a channel per project means an event for project A never reaches subscribers to project B (9.1c). Most subscriptions also take arguments that narrow further, such as `issueUpdated(projectId: $p, assigneeId: $me)`.

The expensive way to apply those is to execute the selection set and then drop results that don't match. The cheap way is to decide from the event itself, before any resolver runs. That only works if the event carries the fields the filters need, so design events for it: an `issue.updated` event should include `projectId`, `assigneeId`, `labelIds`, and `status`, even though the subscription's resolvers could fetch them. A filter that needs a database lookup per event per subscriber is an execution in disguise.

### Fat events, thin events, and what the resolvers do

When the selection set executes, the event is its root value, and the resolvers decide how much comes from the event and how much from the database.

**Thin events** carry an ID and a version, and resolvers fetch everything. The payload is always current and complete, and the cost per subscriber is a full set of fetches, as in the opening.

**Fat events** carry the entity's fields, and resolvers read them from the root value. The per-subscriber cost can drop to nearly zero for top-level fields. Nested fields (`assignee { name }`) either come from the event too, which makes events large and couples them to the schema, or get fetched, in which case one payload mixes the event's version of the issue with the database's current version of the assignee.

Most systems end up in between: the event carries the entity's own fields and the IDs of related entities, and resolvers fetch related entities through loaders. The important part is to decide which it is deliberately, per field, rather than letting it fall out of whatever the query resolvers happened to do.

### Loaders belong to an execution, not a connection

8.3a's loaders are per request, because a loader caches what it loads for as long as it lives. A subscription has no "request" in that sense: the connection lasts hours. Creating the loaders when the socket connects, which is the natural place because that's where the context is built, means an assignee's name loaded at 09:00 is still served at 17:00. Each event's execution needs its own fresh loaders, which also means batching only happens within one execution, not across subscribers. That limit is what the next technique addresses.

### Execute once per group, not once per subscriber

Look at the 1,800 subscribers in the opening. They sent the same document with the same variables, and most of them have the same permissions on that project. Their payloads are byte-for-byte identical. Executing 1,800 times produces 1,800 copies of one answer.

The fix is to group subscribers by everything that can change the result, execute once per group per event, and send the one result to every member:

```
group key = hash(document, operationName, variables, authorization scope)

1,800 subscribers ──► 3 groups  (viewer / editor / admin on this project)
1 event            ──► 3 executions  ──►  1,800 sends
```

The hard part is the group key. It has to include everything that affects the output, and that's more than it looks like. Different variables produce different results. Different permissions can too, since field-level authorization (8.4) may null a field for one role and not another. And any field that depends on who is asking, such as `viewerHasStarred` or `viewerCanEdit`, makes every user's result different, so a subscription that selects such a field can't be grouped beyond one user. A key that leaves something out doesn't cause an error. It sends one user's result to another, which is a data leak with no error message, the same failure 8.3c described for shared caches.

Hasura's subscription engine is a well-documented example of the same idea at the database level: it groups subscriptions that share a query shape and runs one SQL query for the whole group with each subscriber's variables as rows. Routers and servers differ in how much of this they do for you, so check what yours does before building it.

### Coalescing bursts

The 200-issue sprint move is 200 events in two seconds. Even with grouping, a client that receives 200 separate payloads re-renders 200 times. And if the same issue is edited three times in 100 ms, the first two payloads are obsolete before they arrive. Coalescing, from 9.1b, applies here with a GraphQL-specific twist: coalesce per entity, within a short window (100–300 ms), keeping only the latest event for each issue, *before* execution. That cuts both the executions and the sends. It's only valid when later events supersede earlier ones for the same entity, which is true for "issue updated" and false for "comment added."

### Authorization on every event

A subscription is a long-lived grant. Checking permission once, in the subscribe step, is checking it at the moment the grant is made and never again. The contractor in the opening is the result.

Three approaches, which can be combined:

- **Check per event, cached briefly.** Before sending (or before executing, in the grouped version), check the subscriber's access to the event's project, with a cache of a few seconds to a minute. The staleness window is the cache TTL, and you choose it.
- **Push revocations.** When access is removed, publish a revocation event. Every pod holding subscriptions for that user and project ends them. This gives near-instant revocation, but a missed revocation event means access never ends, so pair it with a per-event check.
- **Bound the lifetime.** End every subscription when the credentials it was started with expire, and let the client resubscribe with fresh ones. It doesn't make revocation fast, but it caps how long a stale grant can last.

When access ends, end the *operation*, not the socket. The widely used `graphql-ws` protocol lets the server send an `error` or `complete` for one subscription ID while the connection stays open, so the user's other subscriptions keep working.

Field-level authorization (8.4) still runs inside each execution, which is correct. What changes is that "the viewer's permissions" have to be reloaded at least as often as your staleness window, not taken from a context built when the socket connected.

### Ordering: versions, not arrival order

Executions of different events run concurrently and finish in whatever order their resolvers allow. 9.1c's sequence numbers ordered messages on a stream, but here the reordering happens *after* sequencing, inside the server, so sequence numbers assigned at send time can't restore it.

The dependable fix is to give entities a version (a counter incremented on every write, or the database row's update timestamp), include it in the payload, and have the client ignore any payload for an entity whose version is lower than the one it already has. This also makes coalescing and redelivery harmless, since an old version is simply dropped. It's the same rule as optimistic concurrency, applied on the reading side.

### Subscriptions in a federated graph

In a federated graph (40.1a), one subgraph owns the subscription root field, because it's the one that knows when issues change. But the selection set can include fields from other subgraphs: `assignee` from the people subgraph, `labels` from the taxonomy subgraph. So on every event, the router has to fetch those entity fields from their subgraphs, just as it would for a query:

```
issues subgraph ──event──► router ──► _entities(User) ──► people subgraph
                                  └─► _entities(Label) ─► taxonomy subgraph
                                  └─► merge ──► payload ──► 1,800 clients
```

That's the opening's multiplication again, now crossing team boundaries: the issues team's event rate becomes the people team's request rate. Grouping at the router, and fat events that carry fields the router would otherwise fetch, matter even more here.

The transport between router and subgraph also changes. Routers commonly hold a WebSocket to the subgraph per subscription. Apollo's router can instead use an HTTP callback protocol, where the subgraph POSTs events to a callback URL on the router, so subgraphs don't hold long-lived connections; its client-facing transport is multipart HTTP responses rather than WebSockets. WunderGraph's Cosmo takes a further step with Cosmo Streams (formerly EDFS): subgraphs publish events to Kafka, NATS, or Redis, the router subscribes to the broker directly, and it fetches entity fields from subgraphs over plain HTTP. That makes the event source a schema declaration rather than a server, which suits subgraphs that run stateless or serverless.

## When It's Appropriate

- **Many viewers of the same changing data, with a latency need in seconds.** A board, a dispatch map, an auction lot: tens to thousands of subscribers per topic, a few events per second, and users who notice a five-second delay.
- **Payloads that vary by client.** Different screens select different fields from the same event. That's where a GraphQL subscription earns its place over a fixed-format event channel.
- **A federated graph where the event and its related data belong to different teams.** The router's ability to join entity fields onto events is hard to replicate with raw channels.
- **Grouping, specifically, when subscribers per topic are high and selections are shared.** Hundreds of subscribers on the same document with a handful of permission scopes. With five subscribers per topic, it isn't worth building.

## When It's Unnecessary or Overkill

- **Freshness measured in tens of seconds.** A dashboard refreshing every 30 seconds is a polling query, which gets 8.3c's caching for free and costs nothing when nobody is looking.
- **One subscriber per topic.** A user's own notifications have no fan-out to optimize. A subscription is fine, and none of the grouping machinery is needed.
- **High-frequency streams.** Cursor positions, typing indicators, market ticks at 50 per second: running a GraphQL execution per message spends CPU on selection-set machinery that the payload doesn't need. Use a plain channel (Module 9) with a fixed message format.
- **When clients would refetch anyway.** If every client reacts to an update by re-running its query, the subscription's selection set is wasted work. Send an invalidation and let the query path, with its caching, do the fetching (see Alternatives).

## Trade-offs

**The cost scales with subscribers, not events.** That's the core trade. A query costs what one client asks for. A subscription costs what one event triggers, multiplied by everyone listening, and a bulk operation by one user can generate more work than all your normal traffic. Capacity planning has to model the worst event burst against the largest audience, not the average.

**Grouping trades CPU for a correctness risk.** A group key that misses a dimension leaks data between users, silently. It needs tests that specifically try to make two subscribers who should differ share a group.

**Per-event authorization costs a lookup per event, or a staleness window.** You choose between database load and how long a revoked user keeps receiving data. There's no setting that's free and instant.

**Fat events couple producers to the schema.** Every field the event carries is a field the producing service must keep populated, and a schema change may mean changing an event format consumed by other systems too (37.1 on event versioning).

**Coalescing and versions change what clients may assume.** Clients must tolerate skipped intermediate states and discard old versions. That's usually fine for UI state and wrong for anything that needs every change, such as an audit feed.

**Debugging is harder than for queries.** A wrong payload came from a particular event, a particular group, and a particular execution, possibly on a router merging three subgraphs. Tracing (Module 19, 36.4) needs to link the event, the execution, and the sends, or incidents become guesswork.

**Stateful infrastructure.** Subscriptions keep state on servers or routers for hours. Deploys, autoscaling, and failover all have to deal with it, which Module 9 covered for connections and which now applies to subscription groups and their filters too.

## Alternatives

**Polling queries.** The client re-runs its query every *n* seconds. Stateless, cacheable, trivially authorized (every request is checked), and costs nothing between polls for users who aren't looking. It's wasteful when data rarely changes and slow when it changes often, but for many "live" features, a 10-second poll is indistinguishable to users and far simpler.

**Subscriptions as invalidation.** The subscription payload is only `{ id, version }`, and the client refetches with its normal query when it sees a newer version. Server-side execution per subscriber becomes trivial, authorization and caching happen on the query path, and clients fetch exactly what their screens need. The cost is a round trip per update and a burst of refetches after each event, which needs jitter so 1,800 clients don't query in the same millisecond.

**Live queries.** The client declares the query it wants kept current, and the server re-sends results when they change, either by watching data or by polling and diffing. It's the right shape when clients care about current state rather than events, and servers that implement it can group and deduplicate by query. It isn't standardized, so it ties you to a server implementation.

**A plain real-time channel.** Skip GraphQL for the live part: typed events over the WebSocket or SSE infrastructure from Module 9. It's the best fit for high-frequency or fixed-format streams. You lose field selection and, in a federated graph, the router's joins.

## How to Achieve It

**Level 0: poll.** Ship the board with a query and a poll interval. Measure how often data actually changes and how many viewers each project has. *Next step when:* users notice the delay, or polling traffic is mostly unchanged responses.

**Level 1: subscribe for invalidation.** Add a subscription that sends `{ id, version }` and have clients refetch. You've built the event path, the topic structure, and per-event authorization, with none of the execution cost. *Next step when:* the refetch burst after each event is a measurable load, or the extra round trip is visible to users.

**Level 2: payload subscriptions, done carefully.** Move to full payloads, with events designed for filtering, filters on the event before execution, fresh loaders per execution, per-event authorization with a chosen staleness window, and entity versions on every payload. *Next step when:* execution cost tracks subscriber count and your largest topics dominate database load.

**Level 3: group and coalesce.** Execute once per group of identical subscriptions, and coalesce superseding events per entity. Add tests for group-key correctness before you ship it. *Next step when:* you're federated, and one subgraph's events are driving load on others.

**Level 4: move subscriptions to the router.** Let the router own subscriptions, joining entity fields per group, and connect it to subgraphs by callback or directly to the broker, so subgraphs stay stateless. This is also the point to check what your router already groups and deduplicates, so you don't build Level 3 twice.

## Implementation

TypeScript with `graphql-js` and `graphql-ws`, because `graphql-js` exposes the spec's two stages directly: the `subscribe` resolver returns an async iterator (the source stream), and `execute` runs the selection set per event (the response stream). The first snippet is the per-subscriber path done carefully. The second is the grouped path that replaces it at scale.

The subscription resolver, with filtering and per-event authorization:

```ts
const resolvers = {
  Subscription: {
    issueUpdated: {
      subscribe: async function* (_: unknown, args: { projectId: string; assigneeId?: string }, ctx: Ctx) {
        await ctx.authz.assertCanRead(ctx.viewer, args.projectId);        // at subscribe time
        for await (const event of ctx.bus.topic(`project:${args.projectId}`)) {
          if (args.assigneeId && event.assigneeId !== args.assigneeId) continue;   // ← aside 1
          if (!(await ctx.authz.canReadCached(ctx.viewer, args.projectId, { ttlSeconds: 30 }))) {
            return;                                                              // ← aside 2
          }
          yield event;
        }
      },
      resolve: (event: IssueEvent) => event.issue,   // root value for the selection set
    },
  },
  Issue: {
    assignee: (issue: IssueFields, _: unknown, ctx: ExecCtx) =>
      issue.assigneeId ? ctx.loaders.user.load(issue.assigneeId) : null,
  },
};

// graphql-ws server, with the spec's two stages written out by hand
useServer({
  schema,
  context: (conn) => ({ viewer: conn.extra.viewer, bus, authz }),          // once per connection
  subscribe: async (args) => {
    const source = await createSourceEventStream(args);                     // stage 1: the source stream
    if (!isAsyncIterable(source)) return source;                            // subscribe step failed
    return mapAsync(source, (event) =>                                      // stage 2: execute per event
      execute({ ...args, rootValue: event,
                contextValue: { ...args.contextValue, loaders: newLoaders() } })); // ← aside 3
  },
}, wsServer);
```

**Aside 1: this filter costs nothing because the event carries `assigneeId`.** If the event only had the issue ID, this line would need a lookup per event per subscriber, which is an execution in disguise. The event format is where filtering cost is decided, so the team producing the events has to know which fields subscriptions filter on.

**Aside 2: returning ends this operation, not the connection.** When the source stream ends, the server sends `complete` for this subscription's ID, and the client's other subscriptions on the same socket continue. Ending cleanly matters: an exception thrown mid-stream may be treated by the server library as an internal error and close the whole socket. The client should treat an unexpected `complete` as "resubscribe," and that resubscribe fails at the subscribe-time check with a proper `error`, which is what tells the user their access changed. The check runs on each event through a 30-second cache, so a removed user stops receiving data within about 30 seconds, instead of never. That number is a product decision: it's how long a revoked user may see confidential data, and it should be written down somewhere other than this line.

**Aside 3: the one line that fixes stale data.** `context` is called once per connection, and `graphql-js`'s built-in `subscribe` reuses that same context for every event it executes, so loaders created there would cache for the life of the socket. Writing the two stages out with `createSourceEventStream` and `execute` gives each event's execution its own loaders, and it makes the spec's structure visible in the code. The cost is that nothing is shared between executions, which is exactly the gap grouping fills.

The grouped path, where executions are shared across subscribers:

```ts
type Member = { opId: string; send: (payload: ExecutionResult) => void };
type Group  = { doc: DocumentNode; variables: Record<string, unknown>; scope: Scope; members: Set<Member> };

function groupKey(docHash: string, variables: object, scope: Scope, doc: DocumentNode, viewerId: string) {
  const perViewer = selectsViewerDependentField(doc);                        // ← aside 4
  return hash(docHash, stableJson(variables), scope.role, scope.fieldGrants, perViewer ? viewerId : "");
}

async function onEvent(event: IssueEvent, groups: Map<string, Group>) {
  for (const g of groups.values()) {
    if (!matches(g.variables, event)) continue;                              // filter on the event
    const result = await execute({
      schema,
      document: g.doc,
      rootValue: event,
      variableValues: g.variables,
      contextValue: { scope: g.scope, loaders: newLoaders() },               // one execution per group
    });
    const payload = { ...result, extensions: { version: event.issue.version } }; // ← aside 5
    for (const m of g.members) m.send(payload);
  }
}
```

**Aside 4: the group key is where a leak would live.** `viewerHasStarred` in the selection set makes each viewer's result different, so `selectsViewerDependentField` walks the document for fields marked as viewer-dependent (a schema directive works well) and puts the viewer's ID in the key when it finds one. Get this wrong in the other direction, by forgetting to mark a field, and one user's starred issues appear for everyone in the group. Default to treating unmarked fields as viewer-dependent if you can't be sure, the same fail-closed rule 8.4 used for authorization.

**Aside 5: the version travels with the payload.** Clients drop any payload whose version is lower than the one they hold for that issue, which fixes the out-of-order problem from the opening and makes coalescing and redelivery safe. Putting it in `extensions` keeps it out of the schema; putting it in the schema as a field (`Issue.version`) works equally well and lets clients select it. What matters is that it comes from the database write, not from the order in which the server happens to send.

## Further Reading

- **The GraphQL specification, the "Subscription" section of "Execution"**: `CreateSourceEventStream` and `MapSourceToResponseEvent`, the two stages this article is built on, plus the rule that a subscription has exactly one root field.
- **The `graphql-ws` protocol document** (`PROTOCOL.md` in github.com/enisdenjo/graphql-ws): message types, per-operation `complete` and `error`, and close codes such as `4403 Forbidden`.
- **Apollo router documentation, "GraphQL Subscription Support" and "HTTP Callback Protocol"**: subscriptions in a federated router, multipart HTTP to clients, and the callback alternative to per-subscription WebSockets to subgraphs.
- **WunderGraph Cosmo documentation, "Cosmo Streams (EDFS)"**: broker-driven federated subscriptions, where the router consumes Kafka, NATS, or Redis directly.
- **Hasura, "Scaling to 1 million active GraphQL subscriptions (live queries)"** (the `live-queries.md` architecture note in the graphql-engine repository): multiplexing many subscribers into one database query, the clearest public write-up of the grouping idea.
- **Laurin Quast, `graphql-live-query`** (github.com/n1ru4l/graphql-live-query): a `@live` directive implementation and a good explanation of how live queries differ from subscriptions.
- **In this collection:** Module 9 for everything about the connection (9.1b lifecycle and coalescing, 9.1c cross-node fan-out, 9.4 brokers); 8.3a for loaders; 8.3c for why a wrong cache key is a leak; 8.4 for field-level authorization; 40.1a for entity resolution in the router.

A Go sibling with gqlgen would show a different default worth seeing: gqlgen's subscription resolvers return a channel, and the per-event execution happens in generated code, so where loaders are created and whether executions can be shared depends on middleware rather than on a visible `execute` call. It would make aside 3's problem easier to miss and grouping harder to add, which is itself a useful lesson. Not yet written.

---

The habit to take from this: for anything long-lived, such as a subscription, a stream, a session, or a cached grant, ask which decisions were made once at the start and are still being relied on hours later. Permissions, loaded data, and assumptions about order are all made at a moment. A subscription keeps using them long after that moment has passed.
