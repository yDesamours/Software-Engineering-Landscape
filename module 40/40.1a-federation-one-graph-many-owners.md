# Federation: One Graph, Many Owners

_Module 40.1a — GraphQL Advanced Patterns_

## The Problem

Suppose you work on a food-delivery platform. Three years ago it adopted GraphQL the way 8.2 recommended for a company its size: one GraphQL server, `graph-api`, owned by a small API platform team, sitting in front of the domain services as a backend-for-frontend. The web app, the iOS app, the Android app, and the courier app all talk to it. It worked well.

It still works. What changed is the number of people who need to touch it.

**Year 1: two teams.** The API team and the checkout team. Schema changes are a conversation across a desk. `graph-api` deploys twice a day.

**Year 3: nine product teams.** Catalog, reviews, logistics, orders, payments, promotions, loyalty, courier ops, search. Every one of them ships features that need new fields, and every new field is a pull request into a repository four people own. The numbers the API team pulled for their quarterly review:

```
commits to graph-api last quarter          1,140
  … from the API team                        310   (27%)
  … from the other eight teams               830   (73%)

median time from "schema PR opened" to "in production"    6 days
  … of which waiting for API-team review                  4.5 days

teams with changes in a typical Tuesday deploy            6
```

Three things are going wrong, and they're different things.

**The API team is a queue.** Its four engineers are reviewing resolver code for loyalty-point calculations they don't understand, for a domain whose rules they can't judge. Their review is mostly "does it follow our conventions," which is worth something, but not four and a half days.

**Ownership has blurred.** Look at one type:

```graphql
type Restaurant {
  id: ID!
  name: String!            # catalog team's data
  menu: [MenuSection!]!    # catalog team's data
  rating: Float            # reviews team's data
  reviewCount: Int!        # reviews team's data
  etaMinutes(to: ID!): Int # logistics team's routing engine
  activePromotion: Promotion  # promotions team
}
```

Four teams' data, one type, one process. The resolver for `etaMinutes` lives in `graph-api` and calls the logistics service, and has grown some caching and fallback logic of its own. When it returns nonsense at 2 a.m., the API team is paged for a routing bug in code they neither wrote nor understand.

**Failures share a process.** Last month the reviews team changed `Restaurant.rating` to include a per-review sentiment weighting, and the new resolver loaded reviews one restaurant at a time. On the home screen, which lists sixty restaurants, that's the N+1 from 8.3a in a process that also serves checkout. Checkout's p99 went from 180 ms to 2.4 s for forty minutes. The rollback reverted six teams' changes, including a payments fix that had to be re-shipped the next day.

The obvious fix is to let each team run its own GraphQL server. It fails immediately, and the reason is instructive. To the iOS app, `Restaurant` is one thing. With four servers, the app would query catalog for the name and menu, then reviews for the rating, then logistics for the ETA, joining the results by `id` on the phone. That's the waterfall 8.1a described as one of the reasons GraphQL was adopted in the first place, now rebuilt in every client.

So the requirement is specific: **split ownership and deployment by team, while clients keep seeing one graph in which a single type can carry fields from several teams.**

## What It Is

That arrangement is called **federation**. Each team runs its own GraphQL service, called a **subgraph**, which declares the types and fields it is responsible for, including fields it adds to types that other subgraphs also contribute to. A build-time step called **composition** validates the subgraphs against each other and merges them into one schema, the **supergraph**. A **router** (sometimes called a gateway) serves that supergraph to clients: it takes each incoming query, works out which subgraphs can supply which fields, and executes a **query plan** that fetches from them and assembles one response.

The shared types, like `Restaurant` above, are called **entities**: types that have a key, so that any subgraph can say "I have more fields for the restaurant whose `id` is `r_81`" and the router can join them.

The name most people know is **Apollo Federation**, which defined the model and is the de facto standard, with its own router plus compatible routers from other vendors. The GraphQL Foundation has a working draft of a vendor-neutral version, developed under the name Composite Schemas and renamed the GraphQL Federation specification in September 2026. It uses different vocabulary for the same pieces (source schemas, composite schema, distributed executor) and a few different mechanisms, which come up below. The ideas in this article apply to both.

The neighbor that most needs separating is **schema stitching**, which also produces one schema from several GraphQL services. The difference is where the knowledge of how types join together lives. In stitching, the gateway holds that configuration: the services don't know they're being combined, and someone edits the gateway's config to say "`Restaurant` from reviews joins `Restaurant` from catalog on `id`." In federation, each subgraph declares its own contribution and keys in its own schema, and the gateway derives everything from those declarations. The Alternatives section comes back to why that difference decides who becomes the bottleneck.

## Recognizing the Problem

- Most commits to your GraphQL server come from teams that don't own it.
- Schema changes have a lead time measured in days, and most of it is waiting for review.
- The GraphQL server contains business logic that duplicates, caches, or patches logic in the services behind it.
- One type's fields are owned by several teams, and nobody can say quickly who is on call for a given field.
- A single deploy routinely contains changes from many teams, so rollbacks revert unrelated work.
- A slow resolver from one team degrades unrelated operations from another.
- Some teams have given up and stood up their own GraphQL endpoints, and clients now call two or three of them and join results by ID.

If the first five don't describe you, you don't have the problem federation solves, whatever the size of your schema.

## How It Works

### Entities: shared types, owned fields

In federation, types are shared and fields are owned. Each subgraph declares only the fields it can resolve, and marks the entity with a key:

```graphql
# catalog subgraph
type Restaurant @key(fields: "id") {
  id: ID!
  name: String!
  menu: [MenuSection!]!
  latitude: Float!
  longitude: Float!
}

# reviews subgraph
type Restaurant @key(fields: "id") {
  id: ID!
  rating: Float
  reviewCount: Int!
}
```

The key is a contract: "given `{ __typename: "Restaurant", id }`, this subgraph can return its fields for that restaurant." The object `{ __typename, id }` is called a **representation**, and it's the currency the router trades in.

To make that contract executable, each subgraph that contributes to an entity exposes a way to resolve representations. In Apollo Federation this is a generated root field, `_entities(representations: [_Any!]!)`, which takes a list of representations and returns the matching objects, backed by a **reference resolver** you write per entity. The draft Foundation spec takes a more explicit route: you mark ordinary query fields such as `restaurantById(id: ID!)` with `@lookup`, and the executor calls those. The mechanism is the same. The spec's version is more visible in the schema, and it lets a subgraph offer several lookups by different keys.

Two properties of this design matter later. The `_entities` field takes a *list*, so the router resolves sixty restaurants in one request to each subgraph, not sixty requests. And whatever resolves those representations is an entry point into the subgraph that doesn't pass through any root field you wrote, so none of your root-field authorization runs on it.

### Composition: where the safety lives

Every subgraph publishes its schema (usually to a registry, on every deploy or pull request). Composition merges them and fails if they don't fit together. Among other things, it catches:

- Two subgraphs defining the same field with incompatible types (`rating: Float` in one, `rating: String` in another).
- Two subgraphs both resolving the same ordinary field without saying that's intended. In Apollo Federation 2, a field that several subgraphs can resolve, such as the fields of a `Money { amount currency }` value type that everybody defines, must be marked `@shareable`. Otherwise it's an error, because it usually means two teams think they own the same thing.
- A field that exists in the supergraph but can't actually be reached. If logistics adds a field to `Restaurant` but no subgraph offers a way to get a `Restaurant` by the key logistics uses, no query plan could ever resolve that field. Apollo calls this check **satisfiability**.

This is what makes federation more than "a proxy that forwards to several servers." Conflicts that would otherwise be runtime errors, discovered by a client, become failed builds, discovered by the team that caused them before they merge.

### Query planning: turning one query into fetches

When a client sends a query, the router consults the supergraph to find out which subgraph can supply each field and what it needs to be given. Take the order-tracking screen:

```graphql
query Track($id: ID!, $to: ID!) {
  order(id: $id) {
    status
    restaurant { name rating etaMinutes(to: $to) }
    courier { name vehicle }
  }
}
```

`order` and `status` come from orders. `name` comes from catalog, `rating` from reviews. `etaMinutes` comes from logistics and, as we'll see, needs the restaurant's coordinates, which only catalog has. The router produces a plan like this:

```
Sequence
 ├─ Fetch(orders)     order(id) { status  restaurant { id }  courier { id } }
 ├─ Parallel
 │   ├─ Fetch(catalog)    _entities(Restaurant{id})  { name latitude longitude }
 │   ├─ Fetch(reviews)    _entities(Restaurant{id})  { rating }
 │   └─ Fetch(couriers)   _entities(Courier{id})     { name vehicle }
 └─ Fetch(logistics)  _entities(Restaurant{id latitude longitude}) { etaMinutes(to: $to) }

  orders 25 ms ──► max(catalog 20, reviews 35, couriers 15) ──► logistics 30 ms
                                                        critical path ≈ 90 ms + router
```

Each step depends on keys returned by the step before it. Steps that don't depend on each other run in parallel. The latency of the whole query is the length of the critical path through this tree, which is why plan shape, not only subgraph speed, becomes something you watch.

Note the last step. Catalog had to answer before logistics could start, because logistics' field depends on data catalog owns. That dependency is declared in the schema, which brings us to the finer-grained directives.

### Declaring dependencies between subgraphs

A handful of directives describe how fields relate across subgraphs. You'll meet these four in almost every federated graph:

- **`@external` + `@requires`**: "to compute this field, I need these fields of the entity, which another subgraph owns." Logistics declares `latitude` and `longitude` as external and `etaMinutes` as requiring them. The router fetches them first and includes them in the representation it sends to logistics. The draft spec expresses the same thing with `@require` on a field argument.
- **`@provides`**: "along this particular path, I can return some of another subgraph's fields myself, so don't make an extra fetch." If orders stores a denormalized copy of the restaurant name for receipts, `Order.restaurant` can declare `@provides(fields: "name")`, and the plan above drops catalog from queries that only need the name. It's an optimization with a consistency cost: orders' copy may be stale.
- **`@override(from: "…")`**: "this subgraph now resolves this field instead of that one." It's the tool for moving a field between subgraphs without a client-visible change, and the backbone of the adoption path below.
- **`@inaccessible`**: "compose this field, and let the router use it, but hide it from clients." Useful for keys and coordinates that exist for joining rather than for display.

A subgraph that only *references* an entity, without adding fields to it, can declare a stub. Orders holds a restaurant ID and nothing else, so it declares `type Restaurant @key(fields: "id", resolvable: false) { id: ID! }`, meaning "I can hand out restaurant keys, but don't ask me to resolve restaurants."

### Split by domain, not by type

The mistake that makes federated graphs painful is assigning each *type* to a team: "catalog owns `Restaurant`, so every restaurant field goes through catalog." That recreates the bottleneck one level down, with catalog now reviewing reviews' pull requests. Subgraph boundaries should follow the bounded contexts from Module 2.3, which already describe who owns which decisions. The entity is the place where contexts meet, and each context contributes the fields it's the authority on.

A practical rule for keys follows from this. The key should be an identifier that every contributing subgraph already stores, usually one minted by the context that creates the entity. A key that only one subgraph knows how to compute forces everyone else to call it first.

## When It's Appropriate

- **Several teams, one graph, and the graph's owner is the queue.** Something like five or more teams contributing, dozens of schema changes a month, and review-wait time dominating lead time. The numbers in the opening are a typical shape.
- **Entities genuinely span domains.** `Restaurant` or `Product` or `Account` carries fields from three or more teams, each of which is the authority on its fields.
- **Teams already own services, deploys, and on-call.** Federation extends an ownership model you have; it doesn't create one.
- **Failure isolation between domains matters.** You need a slow reviews resolver to be unable to take checkout down with it.
- **Clients need one graph.** Several client surfaces rely on fragments and normalized caching (8.1a, 8.3c) across types that span teams, so separate per-team APIs would push the join onto every client.

## When It's Unnecessary or Overkill

- **One or two teams.** The coordination cost federation removes is small, and the operational cost it adds is not. A well-organized single server is simpler to run, debug, and change.
- **Splitting before the ownership exists.** If one team would own all six subgraphs, you've built a distributed system with a network hop between every pair of related fields and gained nothing in ownership. This is the most common way federation gets adopted too early: it's chosen as a microservices architecture for the graph rather than as a response to a team-scaling problem.
- **Subgraphs that all read the same database.** If the "reviews subgraph" queries the same tables as the "catalog subgraph," the domains aren't actually separated. You get federation's latency and operational overhead with none of the isolation.
- **For performance.** Federation adds hops. It can isolate a slow domain, but it doesn't make any query faster than the same query against a single server with the same data.
- **When the real complaint is code organization.** If the pain is "the resolver files are a mess" rather than "we wait for another team," modules with clear owners inside one server (see Alternatives) fix it at a fraction of the cost.

## Trade-offs

**Latency grows with plan depth.** Each sequential step in a plan is a network round trip plus the subgraph's own work. `@requires` in particular serializes fetches that would otherwise be parallel. A query that took one hop through `graph-api` to a service now takes the router's planning time, then a fetch per plan level. If `graph-api` previously read a database directly, federation adds hops rather than replacing them. Plan depth becomes a metric, and teams need a way to see the plans their changes produce.

**The router is a new tier-0 component.** Every client request goes through it. It needs capacity planning, its own deploys, its own observability, and a rollout process for new supergraph versions. Composition and a schema registry become deploy-blocking infrastructure: if composition is down, nobody ships schema changes.

**Deploy ordering is now a thing you can get wrong.** The router plans against the published supergraph, and subgraph code is deployed separately. Adding a field means deploying the subgraph first and publishing the schema second; publish first and the router will ask a subgraph for a field it can't resolve yet. Removing a field is the reverse: stop publishing it (after clients have stopped using it), then remove the code. Get the order wrong and some requests fail for the minutes between the two steps.

**Partial failure is visible to clients.** If reviews is down, `rating` comes back null with an error, and the rest of the response is fine. That's the point of isolation. But nullability decides how far a failure spreads (8.1a): if `Restaurant.rating` were declared `Float!`, reviews being down would null the whole restaurant, and possibly the whole order above it. Fields that cross subgraph boundaries should usually be nullable, and the teams choosing nullability are now different from the teams that own the parent types. The Implementation's schema has exactly this chain: `Order.restaurant` is non-null in orders and `Restaurant.name` is non-null in catalog, so a catalog outage nulls the entire order on the tracking screen. That might be the right behavior, but it should be a decision someone made, not something two teams produced separately.

**Debugging a request means following it across services.** One client error can involve four subgraphs, each with its own logs. Distributed tracing through the router (Module 19, 36.4) stops being optional.

**Coordination moves; it doesn't disappear.** Shared value types, naming conventions, key choices, and what counts as a breaking change still need agreement. What changes is that the agreement is enforced by composition checks instead of one team's review, and a composition error introduced by one team blocks every other team's schema changes until it's fixed.

**Authorization gets new entry points.** Each subgraph's entity resolver accepts representations from whoever calls it, and a subgraph trusts whatever fields arrive in them, including the `@requires` data. A subgraph reachable from outside the router can be asked for any entity by any key, bypassing every check on the root fields. Subgraphs must accept traffic only from the router, and authorization has to hold at the entity level, not only at the root. This is 8.4's rule again (put the check where the number of paths stops mattering), and the entity resolver is one more path. 40.4b covers the whole router–subgraph boundary.

**Tooling and licensing.** Apollo's router and composition libraries are source-available under the Elastic License 2.0, not an OSI open-source license, and some features (schema registry, some access-control directives) are part of Apollo's commercial platform. Alternatives exist, including Hive Gateway from The Guild, WunderGraph Cosmo, Grafbase, and ChilliCream's Fusion, which implements the Foundation's draft. Directive semantics largely agree, but not entirely, so switching routers later is a real migration.

## Alternatives

**A modular monolith graph.** Keep one server, but split the schema and resolvers into per-team modules with enforced owners (a CODEOWNERS file, lint rules against cross-module imports) so teams review their own changes. This fixes the review queue and the ownership blur at low cost. It doesn't fix shared deploys or shared failure, since it's still one process. For many organizations this is enough, and it's the first step of the adoption path below anyway.

**GraphQL as a BFF over services, kept central.** What the platform had: one team owns the graph, and domain services stay REST or gRPC (8.2). It's the right answer until the BFF team becomes the queue. Federation is what you move to when it does.

**Schema stitching.** The gateway merges several GraphQL services using its own configuration. Its real advantage is that the services don't need to know they're being combined, so it can include GraphQL APIs you don't control, like a vendor's API or a legacy service nobody will modify. Its cost is that the gateway config becomes the one place every cross-service join is described, so whoever owns it becomes the queue again. Stitching is a good fit for integrating services you can't change, and a poor fit for scaling many teams' contributions.

**Separate graphs per domain or per client.** Each team, or each client, gets its own GraphQL API, and clients join what they need. It's simple to operate and gives complete team independence, and it's reasonable when clients rarely need data from several domains at once. When they often do, as with `Restaurant`, it pushes the join into every client.

## How to Achieve It

Most teams arrive at federation with an existing graph. The migration can be done without a single client noticing.

**Level 0: modules with owners inside the monolith.** Split `graph-api`'s schema and resolvers by domain, give each module an owning team, and let owners approve their own changes. This is useful on its own, and it rehearses the subgraph boundaries before any network is involved. *Next step when:* shared deploys and shared failures are still hurting after the review queue is gone.

**Level 1: the monolith becomes a subgraph.** Put a router in front of `graph-api`, which is now the one and only subgraph. Wire up composition and schema publishing in CI. Nothing about the graph changes, and you learn the router's operational cost (latency overhead, deploys, monitoring) with nothing else in flight. *Next step when:* the router has been boring in production for a while.

**Level 2: move one domain out with `@override`.** Pick the domain with the clearest boundary and the most pain; reviews, from the opening, is a good candidate. The reviews team stands up a subgraph declaring `rating` and `reviewCount` on `Restaurant` with `@override(from: "graph-api")`. Composition now routes those fields to the new subgraph. Once it's stable, delete the old resolvers from `graph-api`. Some routers can move a percentage of traffic at a time with a label on the directive, which makes this reversible mid-flight. *Next step when:* the first extraction has run cleanly, and the team that moved can ship schema changes without the API team.

**Level 3: repeat, and let the monolith shrink.** Each team extracts its fields on its own schedule. Every subgraph's CI runs composition against the others' published schemas, plus a check against recent client operations so a field still in use can't be removed. That second check, and schema governance generally, is the subject of the next article, 40.1b. It's fine for a residual `graph-api` subgraph to remain, holding the fields nobody has a strong reason to move.

**Level 4: optimize plans.** Once the structure is stable, look at the slowest operations' query plans. Add `@provides` where a denormalized copy is acceptable, reconsider `@requires` chains that serialize common queries, and add entity caching at the router where fields tolerate staleness, using the same min-TTL rule 8.3c set out for whole responses.

## Implementation

TypeScript with Apollo's `@apollo/subgraph` library, because its resolver-map style puts the reference resolver right next to ordinary field resolvers, which makes the two traps below easy to see. The router itself is configuration, not code, so it doesn't appear here.

First, the subgraph schemas that produced the plan above. Catalog is as shown earlier; here are orders, reviews, and logistics:

```graphql
# orders subgraph
extend schema @link(url: "https://specs.apollo.dev/federation/v2.7",
                    import: ["@key"])

type Order @key(fields: "id") {
  id: ID!
  status: OrderStatus!
  restaurant: Restaurant!
  courier: Courier
}
type Restaurant @key(fields: "id", resolvable: false) { id: ID! }
type Courier    @key(fields: "id", resolvable: false) { id: ID! }
type Query { order(id: ID!): Order }

# reviews subgraph
extend schema @link(url: "https://specs.apollo.dev/federation/v2.7",
                    import: ["@key"])

type Restaurant @key(fields: "id") {
  id: ID!
  rating: Float          # nullable on purpose: reviews down ≠ restaurant gone
  reviewCount: Int!
}

# logistics subgraph
extend schema @link(url: "https://specs.apollo.dev/federation/v2.7",
                    import: ["@key", "@external", "@requires"])

type Restaurant @key(fields: "id") {
  id: ID!
  latitude: Float! @external
  longitude: Float! @external
  etaMinutes(to: ID!): Int @requires(fields: "latitude longitude")
}
```

The reviews subgraph's resolvers:

```ts
const resolvers = {
  Restaurant: {
    // Called once per representation in an _entities request.
    __resolveReference: (ref: { id: string }) => ({ id: ref.id }),   // ← aside 1

    rating: (r: { id: string }, _: unknown, ctx: Ctx) =>
      ctx.loaders.ratingSummary.load(r.id).then((s) => s?.average ?? null),

    reviewCount: (r: { id: string }, _: unknown, ctx: Ctx) =>
      ctx.loaders.ratingSummary.load(r.id).then((s) => s?.count ?? 0),
  },
};

// ratingSummary is a per-request DataLoader (8.3a):
//   SELECT restaurant_id, avg(stars), count(*) FROM reviews
//   WHERE restaurant_id = ANY($1) GROUP BY restaurant_id
```

**Aside 1: the router batches, but your subgraph has to as well.** The home screen's sixty restaurants arrive as one `_entities` call with sixty representations, which is the router doing its part. The library then calls `__resolveReference` sixty times, once per representation. If this function queried the database, the N+1 from the opening would be back, one subgraph further down, invisible from the router's metrics because the router still made one call. Keep the reference resolver trivial when the fields can be loaded lazily, and put the data access behind a loader that the field resolvers share. Only query in the reference resolver when you have to decide whether the entity exists at all, and then batch that too.

The logistics subgraph's resolvers:

```ts
type RestaurantRef = { id: string; latitude: number; longitude: number };

const resolvers = {
  Restaurant: {
    // The router fetched latitude/longitude from catalog and put them
    // in the representation, because of @requires.
    __resolveReference: (ref: RestaurantRef) => ref,                 // ← aside 2

    etaMinutes: (r: RestaurantRef, args: { to: string }, ctx: Ctx) =>
      ctx.loaders.eta.load({ from: [r.latitude, r.longitude], to: args.to }), // ← aside 3
  },
};
```

**Aside 2: this subgraph believes whatever arrives in the representation.** `latitude` and `longitude` are not looked up here. They're taken on trust from the caller, on the assumption that the caller is the router and the router got them from catalog. Anyone else who can reach this subgraph can call `_entities` with any ID and any coordinates. Here that yields a wrong ETA; in a subgraph where `@requires` pulls an account's plan tier or a user's role, it yields whatever the attacker wants. This is why subgraphs must not be reachable except through the router, and why data that drives authorization decisions should be looked up by the subgraph that uses it, not required from another one (40.4b).

**Aside 3: `@requires` bought correctness with a sequential hop.** Every query that asks for `etaMinutes` now waits for catalog before logistics can start, which is the last level of the plan above. That's the right trade when the coordinates change and must be current. If they rarely change, logistics could store its own copy of each restaurant's location (updated from catalog's events, Module 37), drop `@requires`, and run in parallel with everything else. Which one is right is a question about staleness, not about GraphQL.

## Further Reading

- **Apollo Federation documentation**: the sections on entities, the directive reference (`@key`, `@shareable`, `@requires`, `@provides`, `@override`, `@inaccessible`), and composition rules. It's the most complete description of the model most routers implement.
- **Apollo's documentation on query plans**: how to read the plans the router produces, and how `@requires` and `@provides` change them. The fastest way to build intuition for Trade-offs' latency point.
- **The GraphQL Federation specification** (working draft, formerly the Composite Schemas specification; repository `graphql/graphql-federation-spec` on GitHub): the vendor-neutral version, with `@lookup` fields instead of `_entities`. Worth reading for its design principles section even if you use Apollo, since it explains which choices it makes differently and why.
- **Netflix Technology Blog, "How Netflix Scales its API with GraphQL Federation"** (parts 1 and 2, 2020): a large migration from a central graph owned by one team to federated domain graphs, with the organizational reasons stated plainly.
- **_Principled GraphQL_** (principledgraphql.com): Apollo's short statement of the "one graph, federated implementation" position. Read it as the case for the model, not as neutral analysis.
- **GraphQL Tools documentation on schema stitching and type merging**: the main alternative, and a useful contrast for seeing where each approach puts the join configuration.
- **Module 2.3** for bounded contexts, which should decide subgraph boundaries; **8.3a** for the loaders both asides depend on; **8.1a** for nullability as blast radius; **8.4** for authorization that holds on every path, including entity resolvers; **40.1b** for schema checks and governance; **40.3b** for plan shape and router performance; **40.4b** for securing the router–subgraph boundary.

A Go sibling with gqlgen's federation support would be worth writing. gqlgen can generate a batched entity resolver, one function that receives all the representations for a type at once, so aside 1's trap becomes something the generated signature steers you away from rather than something you have to remember. Seeing the same subgraph in both styles makes it clear how much of federation's performance depends on the subgraph library's defaults. Not yet written.

---

The habit to take from this: when a shared artifact becomes a queue (a schema, a config repo, a gateway), ask whether the problem is that the thing is *shared* or that it's *owned and deployed as one unit*. Often only the second needs to change. Federation keeps one graph that everyone shares, and removes the single owner and single deploy that everyone waited on.
