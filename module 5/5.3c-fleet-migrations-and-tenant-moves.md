# Fleet Migrations and Tenant Moves

_Module 5.3c — Multi-Tenancy Architecture_

## The Problem

You need to add a column.

In a pooled database that's one `ALTER TABLE` — with its own hazards, covered in Module 6.3, but one statement with one outcome. With a database per tenant and four hundred tenants, it's four hundred statements, and the difference is not that it takes four hundred times longer. It's a categorically different operation, because **it cannot be atomic.**

Here's the run.

```
  09:00   start
  09:41   tenant 218 fails — lock timeout
          (they were running a 6-minute report; the ALTER queued behind it)
  ──────────────────────────────────────────────────────────────
  217 tenants   schema v43   ─┐
  183 tenants   schema v42   ─┴─ one deployed binary must serve both
```

The runner stops. Someone restarts it from the top, and it fails immediately on tenant 1 because the column already exists — the migration wasn't idempotent. Someone adds `IF NOT EXISTS` and restarts. Tenant 301 fails: out of disk. Tenant 344 takes forty minutes because they have ninety million rows and the median tenant has two hundred thousand. The maintenance window was an hour.

Meanwhile the release containing the code that *uses* the new column is blocked, because deploying it would break 183 tenants.

**A fleet migration is never atomic, so partial completion is not an incident — it's the normal state.** The application has to tolerate schema skew by construction, not by luck, and the migration has to be designed for a world in which it stops halfway and stays there for a week.

### The other operation

5.1 promised that a tenant could be moved out of the pool once they outgrew it, and 5.3a promised the states needed to do it safely. Here's what the promise costs.

Moving one tenant to a dedicated database means copying forty tables that are being written to the whole time, cutting over without losing a write, dealing with their object storage, their search index, their cached data, and their in-flight background jobs, being able to reverse the whole thing at 3am, and doing it without the customer filing a ticket.

The naive version — announce a window, `pg_dump`, restore, update the placement row — is genuinely fine at two gigabytes. At four hundred gigabytes it's a six-hour outage for your largest customer, which is precisely the customer you're moving, because that's why you're moving them.

And the second realization: **the hard part isn't copying the data. It's the cutover** — the moment writes must stop going to the old home and start going to the new one, exactly once, with nothing in flight and no router anywhere still holding the old answer.

### One shape, two problems

Both of these are the same thing: for some period, **two versions of the truth exist simultaneously** — two schema versions, or two homes for one tenant's data — and you need a safe, reversible path from one to the other while serving traffic throughout.

The technique is the same in both cases, at different granularities. Add the new thing alongside the old, get both working, move the traffic, then remove the old thing. What changes is how long the overlap lasts and what can go wrong inside it.

## What It Is

**Fleet migration** is applying a schema or data change across many independently-versioned tenant databases, schemas, or partitions, where the operation is not atomic and partial completion is expected.

**Tenant move** — also called relocation or rebalancing — is relocating one tenant's data from one placement to another: pool to dedicated database, cell A to cell B, region to region.

Three things get called "migration" and it's worth keeping them apart, because they fail differently:

- **Schema migration** changes structure. Fast per statement, dangerous because of locks.
- **Data migration** backfills or transforms rows. Slow, restartable, and its danger is duration rather than locking.
- **Tenant migration** relocates. Its danger is entirely in the cutover.

**Expand and contract** — also published as *parallel change* — is the discipline underneath all of it: never let a single deploy both add a requirement and remove an assumption.

And the property that makes any of this safe, stated precisely: a change is deployable when **old code works against the new schema, and new code works against the old schema.** Both directions, because at fleet scale the deploy order and the migration order are independent and you don't control the interleaving.

One boundary: Module 6.3 covers database migrations in general — versioning, tooling, zero-downtime `ALTER` techniques for a single database. This article is about what changes when there are N of them, owned by different customers, with different data volumes, different SLAs, and different time zones.

## Recognizing the Problem

- Your migration runbook says "if it fails partway, call Priya."
- Migrations run in a maintenance window and the window keeps growing.
- A release is blocked until every tenant has migrated.
- You cannot say, right now, which schema version each tenant is on.
- One tenant's migration takes fifty times longer than the median and you find out during the run.
- Rolling back a migration means restoring a backup.
- No migration has ever been tested against your largest tenant's data volume.
- A migration has never been run against a database that was serving traffic.
- Moving a tenant is a bespoke project with a named owner and a spreadsheet.
- You've sold a customer a dedicated database and haven't scheduled it, because nobody knows how long it takes.
- Your migration tool takes a single connection string.
- Backfills are written as one large `UPDATE`.
- You have a tenant in a timezone where there is no acceptable window at all.
- "How long will this take across the fleet?" has no answer.

## How It Works

### Part 1: Fleet schema migrations

**Fleet state is a histogram, not a number.** The first thing to build is a per-tenant schema version that's recorded and queryable, because every decision below depends on knowing the distribution:

```
  v43  ████████████████████  217 tenants
  v42  ██████████████        183 tenants
       ↑ the deployed binary must serve both, today
```

**Expand, migrate, contract.** Three separately deployable phases, days or weeks apart:

```
  1. EXPAND     add the new structure; require nothing
                nullable column, new table, new index (concurrently)
                old code: unaffected.  new code: writes both shapes.

  2. MIGRATE    backfill in bounded batches while dual-writing
                both shapes readable; reads switch to the new one
                only where it's guaranteed populated

  3. CONTRACT   stop writing the old shape, drop it
                only after every tenant in the fleet is on the new one
```

A column rename becomes: add the new column, write both, backfill, read the new one, stop writing the old one, drop it. Six steps for a rename, which feels absurd until the alternative is 183 tenants whose application no longer boots.

The single rule that generates all of it: **one deploy never both adds a requirement and removes an assumption.**

**Properties a migration needs at fleet scale**, none of which matter with one database:

- **Idempotent per tenant.** It will be re-run. Not "might be."
- **Resumable per tenant**, with status recorded per tenant — not a single global cursor that restarts from zero.
- **Bounded lock time, with `lock_timeout` set short.** This is the footgun that produced the 09:41 failure above and it's worth being explicit about: in PostgreSQL, an `ALTER TABLE` waiting for a lock does not wait politely. It sits at the head of the lock queue, and every subsequent query on that table queues behind *it*. A DDL statement that waits thirty seconds for a long report to finish will stall every query against that table for thirty seconds. Set `lock_timeout` to a few seconds, let the statement fail, and retry with backoff. Failing fast repeatedly is far safer than waiting once.
- **Rate-limited across the fleet.** Migrating four hundred tenants concurrently against shared storage, a shared pooler, or a shared instance makes the migration itself the noisy neighbour from 5.2b.
- **Ordered by risk**, which deserves its own diagram.

```
  internal tenants → 1% canary → small tenants → medium → large → named accounts
        ↑ discover a broken migration here, where nobody is watching
```

- **A circuit breaker.** Stop the run after some number of consecutive failures. A systematically broken migration should be discovered at tenant 3, not tenant 300 — and without a breaker, an orchestrator that retries diligently will grind through the whole fleet doing damage.

**Handling skew in the application.** Two approaches, and you want the second wherever possible:

- Branch on the tenant's schema version. Explicit, honest, and it leaves conditional code that must later be removed.
- Write version-agnostic code: read nullable columns tolerantly, don't assume a table exists, treat absent as a valid value. No branch to remove.

The reason expand/contract matters so much is that it minimizes the window in which either is needed.

**The long tail.** The three tenants that are fifty times the median will dominate your wall-clock time, and your migration cadence is set by them, not by the median. Options: give them their own scheduled window, migrate them with an online schema-change technique (a shadow table built alongside, dual-written, backfilled, then swapped — which is exactly a tenant move at table granularity), or accept that the fleet sits in skew for longer and make sure the application is genuinely fine with that.

### Part 2: Moving a tenant

Three phases, and the shape of them is the entire point:

```
  1. BACKFILL   bulk copy source → target while source serves normally
                hours if necessary; zero customer impact

  2. SYNC       stream the delta continuously (logical replication or CDC)
                target converges; measure lag in seconds

  3. CUTOVER    READ_ONLY → drain in-flight writes → wait for lag 0
                → verify → fence the source → flip placement → lift READ_ONLY
                seconds to a minute
```

**The outage is proportional to the replication lag, not the data size.** That sentence is why this structure exists. A four-hundred-gigabyte tenant and a four-gigabyte tenant have nearly the same cutover window; only phase 1 differs, and phase 1 is invisible to the customer.

For the sync phase, prefer replication from the database's own write-ahead log — PostgreSQL logical replication, or CDC via Debezium (Module 38) — over application-level dual-writing. Dual-writing from the application means writing to two systems with no shared transaction, which is the dual-write problem in its purest form: a failure between the two leaves them permanently divergent, silently.

**What else moves, and what doesn't.** The database is the part everyone plans for:

- **Object storage** often shouldn't move at all. Re-pointing is usually cheaper and safer than copying terabytes, and the tenant's storage prefix can stay where it is unless the reason for the move was residency.
- **Search indexes** are cheaper to rebuild from the new source than to migrate. Rebuild after cutover; accept briefly stale search.
- **Caches** just get invalidated. A cold cache is a performance event, not a correctness one.
- **In-flight background jobs** are the one people miss. A job enqueued before cutover, picked up after it, still holding the old placement, will write to the old database. Drain the tenant's queue before cutover — which is a second payoff from the per-tenant queues in 5.2b — or make jobs resolve placement at execution time rather than at enqueue time.
- **Per-tenant sequences** need their high-water mark carried across. Globally unique ids make this a non-issue; per-tenant counters — invoice numbers, ticket numbers — will silently start reissuing numbers if you forget.
- **Open WebSocket connections and active sessions** need to be dropped at cutover so clients reconnect through the new placement.

**Verify before you flip.** Row counts per table, checksums over a sample, and at least one business-level invariant — total invoiced amount, count of active users, sum of a ledger. "The copy completed without error" is not verification; a replication slot that silently stopped applying also completes without error.

**The fence.** This is the most important safety mechanism in the whole operation. After cutover, some instance somewhere is still holding a cached placement pointing at the old database. If the old database still accepts writes, that instance will write to it, and those writes will be lost silently — the worst possible outcome, discovered weeks later.

So don't rely on cache invalidation being complete. **Make the old placement refuse writes** before flipping: revoke the application role's write privileges on the source, or set the source database to read-only. A stale router then gets a loud, immediate error and a retry that resolves correctly, rather than a successful write into a database nobody reads any more.

Make the wrong answer impossible rather than unlikely.

**Rollback has a deadline.** Keeping the source intact and read-only for a few days makes rollback a single row update — right up until the moment the target accepts its first write. After that, rolling back means migrating in reverse, and the only real question is whether you'd notice the problem before that point. Verification is what buys you that window.

### Part 3: Rebalancing

Cell-to-cell moves use identical machinery with a different trigger: capacity rather than a customer requirement. What's additionally needed is a **placement policy** — where does a new tenant go? Least-loaded cell, hash of tenant id, or manual assignment for named accounts. Automate the policy only after moves are routine, because a rebalancer that can move tenants automatically is a rebalancer that can move them wrongly, automatically, at scale.

## When It's Appropriate

- **Expand/contract: for every schema change, once you have more than one application instance.** The fleet case makes it mandatory; rolling deploys make it a good idea anyway.
- **A per-tenant schema version ledger: with the first tenant that has its own database or schema.** It's one table and it's the prerequisite for everything else.
- **Canary ordering and a circuit breaker: from the first fleet run.** Both are an afternoon of work and they're what stops a bad migration at tenant 3.
- **`lock_timeout` and retry on all DDL: always.** There is no size of system where waiting indefinitely for a lock is the better choice.
- **Online moves with replication: when the tenant's data won't fit in an acceptable window**, when their contract forbids one, or when they're in a timezone that has no quiet hours.
- **Maintenance-window moves: genuinely fine for small tenants with a quiet period.** A ten-gigabyte tenant moved in twenty minutes on a Sunday is not a failure of engineering.
- **Online schema-change techniques: when a single `ALTER` on your largest tenant would hold a lock longer than your error budget allows.**

## When It's Unnecessary or Overkill

**One pooled database and a nightly window.** Run the `ALTER`. Building a fleet orchestrator to drive a single database is an elaborate way to not add a column.

**A CDC pipeline to move four hundred megabytes.** Dump, restore, flip. Four minutes of read-only, nobody notices, and you didn't introduce a replication slot into your production database for a Tuesday afternoon.

**Expand/contract for something genuinely new.** A brand-new table that nothing reads yet has no old assumption to preserve. The ceremony exists to protect compatibility; where there's nothing to be compatible with, skip it and say why.

**Automated rebalancing before you've done two moves by hand.** The manual runs are where you discover the per-tenant sequence, the job queue, and the cached placement. Automating before that encodes the gaps.

**Zero-downtime machinery for an internal tool** used by forty people in one timezone who would rather you shipped the feature.

## Trade-offs

- **Expand/contract turns a one-line change into three deploys over two weeks.** The cost is discipline rather than code, which is precisely why it gets skipped under pressure — and the skip is invisible until the day it isn't.
- **Contract phases get forgotten.** Dual-write code, unused columns, and "temporary" compatibility shims accumulate and outlive their authors. The only defence is a tracked ticket with a date on it, created at the same moment as the expand.
- **Skew means conditional behaviour in the application**, which is a permanent readability tax on code that's otherwise about the domain.
- **Fleet wall-clock time is set by your largest tenant, not your median.** Your ability to ship schema changes is therefore governed by your biggest customer's data volume, which is a coupling nobody chooses deliberately.
- **The migration competes with production traffic.** It is itself a workload, and at fleet scale it's a significant one; without rate limiting it becomes the 5.2b incident.
- **Replication slots are dangerous infrastructure.** A PostgreSQL slot that stops being consumed — because a move was abandoned, a consumer crashed, or someone forgot cleanup — causes the source to retain WAL indefinitely and eventually fills its disk, which takes the database down. This is a real and recurring way that migration tooling causes outages in systems it isn't even touching. Alert on slot lag; clean up slots in the failure path, not just the success path.
- **Verification costs cutover time**, and it's the first thing cut when the window is tight. Skipping it is how silent corruption ships with a green checkmark.
- **Rollback windows mean paying for both placements** for the duration, and remembering to decommission the source afterwards.
- **Every move is a project until it's automated**, and automating it well requires having done several manually — so the cost curve is front-loaded and lumpy.

## Alternatives

- **Stay pooled.** The best migration story available is one database and one `ALTER`. Nearly everything in this article is the ongoing cost of isolation you bought in 5.1, and it's worth restating honestly: this is the bill, arriving monthly, for the rest of the system's life.
- **Blue/green at the database level.** Replicate the entire database, verify, cut everything over at once. Excellent for whole-fleet operations — a major version upgrade, a region move — and no help at all for relocating one tenant.
- **Copy-on-write clones or database branching.** Some managed platforms make creating a full copy nearly instantaneous, which changes the economics of a move from hours of copying to seconds of metadata. Worth checking whether your platform has this before building a pipeline.
- **Shadow reads and dual-run.** Serve from the old placement, execute against the new one in parallel, compare results, and cut over when they agree for long enough. Expensive, slow, and the right call when the move is high-stakes enough that verification-by-sampling isn't sufficient.
- **Accept a maintenance window.** A twenty-minute window announced three weeks in advance is acceptable to far more B2B customers than engineers assume, and it removes an entire class of infrastructure from your life. Ask before you build.
- **Application-level dual-write** rather than replication. Cheapest to start, and it puts the correctness burden entirely on your code at exactly the point where correctness is hardest. Reasonable for small tenants; a trap for large ones.

## How to Achieve It

**Level 0 — know the fleet's state.** A per-tenant schema version, recorded, queryable, on a dashboard.
*Signal you're behind:* "who's on what?" takes more than a query.

**Level 1 — make migrations survivable individually.** Idempotent, batched, resumable per tenant, `lock_timeout` set with retry, and tested against a copy of your largest tenant's data volume.
*Signal:* a migration failed and re-running it failed differently.

**Level 2 — expand/contract as the default**, with a contract ticket created alongside every expand.
*Signal:* a deploy was blocked by an in-progress migration, or vice versa.

**Level 3 — an orchestrator.** Ordering policy, bounded concurrency, circuit breaker, per-tenant status, and a report you can read at a glance.
*Signal:* fleet runs need a human watching a terminal.

**Level 4 — the first move, by hand.** A small, willing tenant. `READ_ONLY`, dump, restore, verify, fence, flip. Write down everything that surprised you — that list is the specification for level 5.
*Signal:* a customer has bought a dedicated database.

**Level 5 — online moves and placement automation.** Replication-based sync, verification with business invariants, a fenced cutover, a rollback window, and eventually a placement policy that assigns new tenants without a human.
*Signal:* moves are frequent enough that the manual runbook is a bottleneck, or capacity rebalancing has become routine.

## Implementation

Go, for the orchestrator and the cutover — the parts where policy matters more than SQL.

**The migration contract, per tenant.**

```sql
-- every migration: idempotent, bounded lock wait, small blast radius
SET lock_timeout = '3s';
ALTER TABLE projects ADD COLUMN IF NOT EXISTS archived_at timestamptz;
```

```go
type Migration interface {
    Version() int
    Apply(ctx context.Context, db *sql.DB) error   // idempotent; retried
}
```

**The orchestrator is mostly policy.**

```go
func (o *Orchestrator) RunFleet(ctx context.Context, m Migration) error {
    tenants := o.catalog.Pending(m.Version())      // ordered: internal → small → large
    sem := semaphore.NewWeighted(o.concurrency)    // migration is itself load
    var consecutiveFailures atomic.Int32

    for _, t := range tenants {
        if consecutiveFailures.Load() >= o.breakerThreshold {
            return fmt.Errorf("circuit open after %d consecutive failures", 
                consecutiveFailures.Load())        // ← stop at tenant 3, not 300
        }
        if err := sem.Acquire(ctx, 1); err != nil { return err }

        go func(t Tenant) {
            defer sem.Release(1)
            err := o.applyWithRetry(ctx, m, t)     // retries lock_timeout failures
            o.ledger.Record(t.ID, m.Version(), err)
            if err != nil {
                consecutiveFailures.Add(1)
            } else {
                consecutiveFailures.Store(0)
            }
        }(t)
    }
    return o.wait(sem)
}
```

> **The breaker is the part that isn't optional.** Without it, a migration with a syntax error that only manifests on tenants with a particular index will be retried patiently across four hundred databases, and the orchestrator will report it as four hundred failures rather than as one problem. Threshold of three consecutive failures is a reasonable default, and the ordering policy is what makes those three cheap.
>
> **Concurrency is a shared-resource decision, not a speed dial.** Twenty concurrent migrations against twenty separate database instances is fine. Twenty concurrent migrations against twenty schemas in *one* instance is the 5.2b incident, self-inflicted, during a maintenance window when nobody is watching latency graphs.

**The cutover, in order, with the fence.**

```go
func (m *Mover) Cutover(ctx context.Context, tenantID string) error {
    if err := m.state.Set(tenantID, ReadOnly); err != nil { return err }
    if err := m.jobs.DrainTenant(ctx, tenantID); err != nil { return err }
    if err := m.replication.WaitForZeroLag(ctx, tenantID, 60*time.Second); err != nil {
        return m.abort(ctx, tenantID, err)         // abort MUST drop the slot
    }
    if err := m.verify(ctx, tenantID); err != nil { // counts, checksums, invariants
        return m.abort(ctx, tenantID, err)
    }

    // fence first, flip second — never the other way round
    if err := m.source.RevokeWrites(ctx, tenantID); err != nil { return err }
    if err := m.catalog.SetPlacement(ctx, tenantID, m.target); err != nil { return err }

    m.state.Set(tenantID, Active)
    return nil
}
```

> **Fence before flip.** Between revoking writes on the source and every instance noticing the new placement, requests fail loudly and retry into the right database. Flip first and that same interval is a window in which a stale router writes successfully into a database nobody will ever read again. One ordering produces errors and retries; the other produces silent data loss, and they differ by two adjacent lines.
>
> **`abort` must drop the replication slot.** An abandoned logical replication slot causes the *source* database — the one still serving the customer — to retain WAL forever until its disk fills. A failed migration that takes down the production database it was migrating away from is an outage nobody forgets, and it happens because the failure path was written after the happy path.
>
> **Draining the job queue is a correctness step, not tidiness.** A job enqueued five minutes ago and picked up thirty seconds after cutover, holding a placement it resolved at enqueue time, writes to the old database and passes the fence check only if it acquired the connection before the revoke. Either drain first, or resolve placement at execution time — and resolving at execution time is the better fix, because it's a property of the system rather than a step in a runbook.

## Further Reading

- **Danilo Sato, "ParallelChange" on martinfowler.com.** The canonical statement of expand/contract, short and complete. The framing of a change as three independently revertible steps is the whole idea.
- **Braintree's "PostgreSQL at Scale: Database Schema Changes Without Downtime."** The best public catalogue of which PostgreSQL DDL operations take which locks and how to avoid each one, including the lock-queue behaviour that makes `lock_timeout` mandatory rather than advisory.
- **PostgreSQL documentation on `ALTER TABLE` lock levels, `lock_timeout`, and `CREATE INDEX CONCURRENTLY`.** The primary source for everything in the paragraph above.
- **PostgreSQL documentation on logical replication and replication slots** — particularly the warnings about slot retention and WAL accumulation. Read the operational caveats before the tutorial.
- **gh-ost (GitHub) and pt-online-schema-change (Percona).** MySQL tools, and their design documents are worth reading regardless of your database: they're the clearest available explanations of shadow-table migration, cut-over locking strategies, and why the naive approaches fail.
- **pg_repack**, for the PostgreSQL equivalent of table rewrites without a long exclusive lock.
- **Debezium documentation**, for CDC-based sync when native logical replication isn't available or the target isn't the same engine. Module 38 covers the pattern properly.
- **The Google SRE Workbook chapter on canarying releases.** The ordering policy above is a canary policy applied to migrations rather than deploys, and the reasoning about population selection and failure criteria transfers directly.
- **Shopify's engineering writing on its podded architecture and moving shops between pods.** One of the few public accounts of routine, automated tenant relocation at large scale, including what they had to build before it became routine.

A **Java** sibling would surface something this implementation never has to confront. Flyway and Liquibase are built around one database with one version table, so the fleet case means driving them programmatically per tenant and reimplementing their reporting — but the more interesting reveal is Hibernate's startup schema validation. It exists to protect you from running against an unexpected schema, and during a fleet migration that's exactly the state you're deliberately in, so the framework refuses to boot against the 183 tenants still on v42. The options are to disable validation and lose the protection permanently, or to validate per tenant at connection time against the version ledger, which is a different design entirely. A safety feature that actively prevents the tolerance of skew is a good lesson about framework assumptions, and it's invisible from Go. Not yet written.

---

The habit worth carrying is a question to ask before any change to a running system: **what is the state of the world halfway through, and can the system serve traffic in it?**

With one database, halfway through is a few hundred milliseconds and the question is academic. Across a fleet, halfway through is Tuesday through Friday — two schema versions, two placements, two shapes of the same row, all live, all serving customers. That interval isn't a transition between two designs. For most of the time that matters, it *is* the design, and it deserves to be designed rather than endured.
