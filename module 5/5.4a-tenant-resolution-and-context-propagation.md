# Tenant Resolution and Context Propagation

_Module 5.4a — Multi-Tenancy Architecture_

## The Problem

Every mechanism in this module so far has assumed a tenant context already exists. 5.1's Hibernate resolver called `TenantContext.get()`. 5.2a's `withTenant(req.tenant.id, …)` took it as an argument. 5.2b keyed its limiters on `TenantFrom(ctx)`. Each one deferred the same two questions: where does that value come from, and what happens when it isn't there.

Both answers are usually accidents.

### The identifier the client supplied

An engineer adds `X-Tenant-Id` so internal services can call the API on a tenant's behalf. It's documented on a wiki page. The gateway strips the header from external requests — except on one route added eight months later that reaches the service directly, because it needed a longer timeout than the gateway allowed.

```
GET /api/projects
Authorization: Bearer <valid token, tenant 42>
X-Tenant-Id: 43
```

Row-level security works perfectly. The repository layer works perfectly. The runtime assertion from 5.2a passes, because every row returned genuinely does belong to tenant 43. Every isolation mechanism in the system performs exactly as designed, and the caller reads another company's data.

**Every isolation mechanism in this module trusts the tenant identifier.** Resolution is the root of that trust chain, and it's the step most often written as a one-liner by whoever needed it to work.

### The context that went missing

The request handler sets a `ThreadLocal`. Then the code does something ordinary:

- Hands work to `CompletableFuture.supplyAsync(…)`, which runs on the common pool. Different thread, no context.
- Calls an `@Async` method. Different thread, no context.
- Enqueues a background job. Different process, an hour later, no context.
- Registers a callback, switches coroutine dispatchers, maps over a parallel stream.

What happens next was decided casually, months earlier, by whoever wrote the accessor:

```
  get() returns null      →  WHERE tenant_id IS NULL  →  zero rows
                             looks exactly like "this tenant has no data"

  get() returns a default →  writes land in the wrong tenant
                             discovered by a customer, eventually

  require() throws        →  a loud 500 in a background job
                             found on the first test run
```

Only the third is acceptable, and it's the one that looks worst on a dashboard.

### The request that belongs to three tenants

A consultant belongs to three workspaces. They're browsing `acme.yourapp.com`. Their session says tenant 7. Their access token was minted for tenant 12 an hour ago. They just clicked a link to `/projects/9931`, which belongs to tenant 7. A second browser tab is open on `fabrikam.yourapp.com`.

Which tenant is this request for?

Systems without an explicit answer resolve this by accident, and the accident is different on different endpoints — which is how you end up with a product where switching tenants in one tab silently changes what the other tab writes.

## What It Is

**Tenant resolution** is determining, for each unit of work, which tenant it belongs to — in a way the caller cannot influence beyond what they're authorized to.

**Context propagation** is carrying that decision to every component that needs it, including components many frames away that never took it as a parameter, without it being droppable along the way.

The distinction that prevents the first failure above:

**Identifying a tenant is not authorizing a claim to it.** Parsing `acme` out of a hostname identifies a tenant. It establishes nothing about whether the authenticated principal may act inside it. Two steps, and the second gets skipped constantly because the first one appeared to work.

So resolution is three operations, not one:

```
  derive a candidate   →   verify the principal belongs to it   →   bind it
```

The second distinction is about propagation style, and it's a real trade-off rather than a right answer:

**Ambient context** — a `ThreadLocal`, Node's `AsyncLocalStorage`, an implicit request scope — is ergonomic. Nothing takes a tenant parameter; it's just *there*. And it is droppable at every boundary, silently.

**Explicit context** — a value threaded through every signature, as Go's `context.Context` convention enforces — is verbose and colonizes your API surface. It also cannot be dropped without someone writing the code that drops it.

Most systems choose ambient and then spend years discovering where it leaks away. The failure modes are what differ: ambient fails silently at runtime, explicit fails visibly at compile time.

## Recognizing the Problem

- A tenant identifier can arrive in a header or query parameter from outside.
- Resolution logic exists in more than one place, and the copies have drifted.
- Somewhere in the codebase is a line that sets a default or "system" tenant.
- A request with no tenant returns an empty list instead of an error.
- Background jobs run without a tenant, or all under one system tenant.
- Async code paths behave differently from synchronous ones for reasons nobody has characterized.
- Some log lines have no tenant field.
- Tenant switching is implemented as "log out and log back in."
- Custom domains go through different resolution code from subdomains.
- An internal service accepts a tenant header with no proof attached.
- Tests pass because the test harness sets context manually and production derives it from a request.
- Two browser tabs on two different tenants interfere with each other.

## How It Works

### Candidates and authorities

Every source of tenant identity is one of two things, and conflating them is the vulnerability at the top of this article.

```
  SOURCE                        CLIENT-CONTROLLED?      ROLE
  subdomain  acme.app.com              yes              candidate
  path       /t/acme/projects          yes              candidate
  header     X-Tenant-Id               yes              never, from outside
  custom domain  app.acme.com          no (DNS + cert)  candidate (strong)
  ─────────────────────────────────────────────────────────────────────
  session (server-side)                no               authority
  signed token claim (verified)        no               authority
  API key → tenant mapping             no               authority
  mTLS client certificate              no               authority
```

**Candidates come from routing. Authority comes from credentials.** A subdomain tells you which tenant the user *wants*. A session or verified token tells you which tenants they *may have*. Resolution is the intersection of the two, and an empty intersection is a 404 — not a 403, for the reason given in 5.2a.

The full sequence:

```
  1. derive candidate     from host / path (or a signed assertion, internally)
  2. resolve principal    from session / verified token / API key
  3. verify membership    principal ∈ candidate?   → else 404
  4. check lifecycle      active? read-only? suspended?   (5.3a)
  5. bind                 context = { tenant, principal, entitlements }
```

Step 4 earns its place here. Suspension, read-only mode, and pending deletion are enforced once, at resolution, rather than being checked — or forgotten — in forty endpoints. If a tenant is suspended, the request should never reach a handler.

### The user who belongs to several tenants

Three designs, and the difference between them shows up in a specific bug.

**A session per tenant**, using subdomain-scoped cookies. Setting a cookie on `acme.yourapp.com` rather than `.yourapp.com` means the browser will not send it to `fabrikam.yourapp.com` at all. Clean isolation, two tabs work correctly, and switching requires re-authentication unless you have SSO or silent token exchange to make it invisible.

**One session, tenant taken from the URL on every request**, with membership re-verified each time. Ergonomic, tabs work, and the cost is a membership check on the hot path.

**One session with an "active tenant" stored server-side**, changed by an explicit switch. Simplest to build, and it is broken by two tabs: switching in one tab silently redirects the other tab's next write into the new tenant. This bug reaches production regularly because nobody tests with two tabs.

The general lesson: **if tenant is session state, tenant is global mutable state shared across every tab.** Putting it in the URL makes it per-request, which is what it actually is.

### Machine clients

An API key maps to exactly one tenant, and that mapping is authoritative — no candidate needed, no ambiguity. This is the simplest correct design in the article and worth preferring wherever possible.

A key that can act across tenants is a different privilege class and needs its own model: which tenants, granted by whom, revocable, audited. Don't let it happen by extension of an existing key.

### Service to service

Internal calls still need a tenant, and "we're on a trusted network" stops being true the first time one service becomes reachable from somewhere unexpected — or the first time an SSRF bug turns a user-supplied URL into an internal request with attacker-chosen headers.

Two workable options: propagate the end user's token so each service independently verifies it (token exchange, RFC 8693, is the standardized version of this), or propagate a short-lived signed assertion minted by the caller. Both give the receiving service something it can *check*. An unsigned header gives it something it must *believe*.

### Where context dies

```
  edge ──bind──► handler ──┬──► repository ──► pooled connection
                           │                    (must be reset on release)
                           ├──► executor / thread pool
                           │     (wrap the executor, not each task)
                           ├──► job enqueue ──► worker, later, elsewhere
                           │     (context must become data, then be re-bound)
                           └──► outbound HTTP / gRPC
                                 (context must become a verifiable credential)
```

The principle underneath: **context is ambient within a unit of work, and must be explicitly serialized at every boundary between units.** A thread hop, a queue, and a network call are all the same kind of boundary, and each needs its own carrier — a wrapper, a payload field, a header.

The specific drop sites, by runtime:

- **Thread pools.** `ThreadLocal` does not cross. The fix is wrapping the executor once at construction, not remembering to wrap each submission.
- **Reactive and streaming pipelines.** Operators may execute on other threads; frameworks provide their own context mechanism (Reactor's `Context`, for instance) that doesn't automatically inherit thread-local state.
- **Node's event loop.** `AsyncLocalStorage` handles promises and timers well, and still loses context across some native callbacks and long-lived listeners registered outside the store.
- **Go.** Nothing gets dropped implicitly, and `context.Background()` appears in goroutines launched without a parent and inside libraries that decided they didn't need yours.
- **Job queues, message consumers, webhooks, scheduled tasks.** These have no ambient context to inherit — ever. They must construct it from data, and that's a feature: the boundary is explicit and unmissable.

### Make absence loud

- The accessor is `require()`, and it throws. There is no `get()` that returns null, because a nullable accessor is an invitation.
- There is no default tenant. A "system" context exists only as a distinct, explicit type, constructed in one named module — the same shape as 5.2a's bypass role, for the same reason.
- Every request that reaches a handler without a bound tenant is logged as an error and alerted on, not swallowed.
- A CI check greps for context construction outside the sanctioned entry points.

## When It's Appropriate

- **Candidate/authority separation: always, from the first tenant.** There is no scale at which trusting a client-supplied tenant identifier is acceptable, and retrofitting the check means auditing every endpoint.
- **`require()` semantics with no default: always.** It costs nothing and it converts an entire class of silent bug into a test failure.
- **Subdomain routing: when tenants are organizations** and you want per-tenant branding or cookie isolation. Budget for wildcard DNS, a wildcard certificate, CORS configuration, and a local development story.
- **Path-prefix routing: early-stage products and internal tools.** No DNS work, trivially debuggable, and it forecloses cookie-scoped isolation between tenants.
- **Custom domains: a priced enterprise tier**, because the certificate lifecycle is real work (5.3b).
- **Token claims as authority: when you already issue verified tokens**, with a deliberate decision about staleness — see below.
- **Explicit context: new services, and anywhere correctness matters more than ergonomics.** Greenfield Go services get this free; greenfield services in other languages can choose it.
- **Ambient context: existing systems** where threading a parameter through four hundred call sites isn't a realistic proposal. Then invest in closing the boundaries.

## When It's Unnecessary or Overkill

**A full token-exchange flow between two of your own processes** that share a deployment boundary and a deploy cadence. A signed internal assertion with a short lifetime achieves the security property; standing up an authorization server between two services you deploy together is a large answer to a small question. The line that isn't negotiable is that *something* must be verifiable — the shortcut to avoid is the unsigned header, not the ceremony.

**Subdomain routing before you need branding or cookie isolation.** It's DNS, certificates, CORS, and a development environment problem in exchange for a nicer URL.

**A tenant-switching UI when 98% of your users belong to exactly one tenant.** Put it in a menu and move on; the design effort belongs in the product.

**Reimplementing propagation your framework already provides.** Hibernate, Spring, Rails, ASP.NET, and Node all ship request-scoped mechanisms, and your distributed tracing system already propagates context across threads, processes, and services. Extending what's there beats parallel machinery — with one caveat in the alternatives below.

**Per-request membership verification against the database when a token already carries a verified claim** and you've accepted its TTL. Pick one source of truth and know which staleness you're living with.

## Trade-offs

- **Ambient context is convenient and silently droppable.** You will find new drop sites for years, usually via a bug report about missing data. Explicit context is undroppable and appears in every signature, including the ones that don't care.
- **A `require()` that throws will take down a background path that "worked" for months.** That's the correct trade and it is still an outage. Sweep the drop sites in pre-production before enabling it; don't soften the accessor in response.
- **Subdomains cost more than they look.** Wildcard certificates, cookie `Domain` scoping subtleties, CORS preflight on every cross-subdomain call, `*.localhost` in development, and every generated email link having to be tenant-correct.
- **Token claims go stale.** A membership revoked at 10:00 remains valid until the token expires at 10:15. Short TTLs cost refresh traffic; revocation checks cost a lookup per request. Choose deliberately and write down which you chose, because someone will eventually ask how quickly access is removed.
- **Membership verification per request is a database lookup on the hot path.** Caching it reintroduces exactly the staleness you were avoiding, at a different layer.
- **Serialized context in job payloads must be re-verified, not trusted.** Your own code wrote it, which makes it trustworthy — right up until some payload field is derived from user input. Re-check the tenant's lifecycle state at execution time too: a job enqueued before a suspension should not run after it.
- **Wrapping executors is a recurring tax.** Every new executor, scheduler, or thread pool is a new opportunity to forget, and the failure is silent.
- **Pooled resources outlive requests.** Threads, connections, and clients all get reused, and every one of them must be reset on release. This is the module's most repeated failure: the `search_path` left set in 5.1, the session variable left set in 5.2a, and the `ThreadLocal` left set below are the same bug three times. **Anything pooled must be cleared on return, in a `finally`.**

## Alternatives

- **Put the tenant in the URL path, always, everywhere, with no ambient state at all.** Ugly URLs, zero ambiguity, trivial debugging, two tabs work, and every log line and stack trace tells you the tenant. Genuinely underrated, and the simplest thing that removes an entire category of bug.
- **Don't have the problem: a deployment per tenant** (5.1's silo). Resolution becomes DNS, and there is no context to propagate because the process serves one tenant. The strongest version of every argument in this article is "the request can't be ambiguous if the process only knows one answer."
- **Separate identity realms per tenant** — a distinct OAuth client, issuer, or directory per tenant. Heavier to operate, and clean for enterprise SSO where the customer owns the identity provider anyway (Module 4.1).
- **Framework-native request scopes.** Hibernate's `CurrentTenantIdentifierResolver`, Rails' `CurrentAttributes`, ASP.NET's middleware pipeline. Use them; they've already solved the boundaries their framework creates.
- **Piggyback on distributed tracing context.** W3C Trace Context and OpenTelemetry baggage already propagate across threads, processes, and services, and your system probably already runs it. Use it to carry the tenant for *observability* — every span tagged, every log correlated. Do not use it as an authority: baggage is unauthenticated, and it propagates outward to third parties by design. It's a convenient carrier and it is not a credential.

## How to Achieve It

**Level 0 — inventory the sources.** List every place tenant identity enters your system and classify each as candidate or authority.
*Signal you're behind:* you find a header, or two endpoints that resolve differently.

**Level 1 — one resolver, at the edge.** All other code reads the bound context. Delete every duplicate resolution path.
*Signal:* the same parsing logic exists in three places with three behaviours.

**Level 2 — make absence an error.** `require()` only, no default tenant, system context confined to one named module, and an alert on any unbound request reaching a handler.
*Signal:* a query returned zero rows and the cause turned out to be a missing context.

**Level 3 — close the boundaries.** Wrapped executors, tenant in every job payload with re-binding and re-verification at execution, verifiable credentials on outbound calls, pooled resources reset on release.
*Signal:* an async path behaved differently from its synchronous equivalent.

**Level 4 — verify membership and lifecycle at resolution**, with a caching and staleness policy you chose on purpose rather than inherited from a token library's defaults.
*Signal:* revoking a user's access didn't take effect immediately and nobody could say how long it should have taken.

**Level 5 — multi-tenant users properly.** Tenant in the URL, explicit switching with an audit record, and two tabs on two tenants behaving correctly.
*Signal:* a support ticket that begins "I had two tabs open."

## Implementation

Java, because the drop sites are most vivid where the context is a `ThreadLocal` and the runtime hands your work to other threads without asking.

**The resolver, at the edge.**

```java
@Component
public class TenantFilter extends OncePerRequestFilter {

    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws IOException, ServletException {
        String candidate = candidateFrom(req);            // host or path — never a header
        Principal principal = principals.resolve(req);    // session / verified token / API key

        Tenant tenant = memberships.find(principal, candidate)
            .orElseThrow(NotFoundException::new);         // 404, not 403

        if (tenant.state() == SUSPENDED || tenant.state() == PENDING_DELETION) {
            throw new TenantUnavailableException(tenant.state());
        }

        TenantContext.bind(tenant, principal);
        try {
            chain.doFilter(req, res);
        } finally {
            TenantContext.clear();                        // ← not optional; see below
        }
    }
}
```

> **The `finally` is the whole safety of this design.** Servlet container threads are pooled. A context left bound when the request ends is inherited by *the next request on that thread*, which belongs to a different tenant. It will not reproduce in development, where one request runs at a time, and it will read and write across tenants under production concurrency. This is the same failure as the unreset `search_path` in 5.1 and the session-scoped `SET` in 5.2a: **pooled resources must be cleared on release.** Three articles, three appearances, one rule.

**The accessor makes absence impossible to ignore.**

```java
public final class TenantContext {
    private static final ThreadLocal<Binding> CURRENT = new ThreadLocal<>();

    public static Binding require() {
        Binding b = CURRENT.get();
        if (b == null) throw new IllegalStateException("no tenant context bound");
        return b;
    }
    // deliberately no get(), no getOrDefault(), no orElse(SYSTEM_TENANT)
}
```

**Wrap the executor once, so nobody has to remember.**

```java
public static ExecutorService tenantAware(ExecutorService delegate) {
    return new DelegatingExecutorService(delegate) {
        @Override public <T> Future<T> submit(Callable<T> task) {
            Binding captured = TenantContext.require();       // capture on the caller's thread
            return delegate.submit(() -> {
                TenantContext.bind(captured);
                try { return task.call(); }
                finally { TenantContext.clear(); }            // the pool thread, again
            });
        }
    };
}
```

> **Wrap at construction, not at each call site.** A helper that developers must remember to apply is a convention; an executor bean that is already wrapped is a mechanism. The distinction is the same one 5.2a made about enforcement points, and it decides whether this holds in two years.
>
> On recent JDKs, `ScopedValue` with structured concurrency is a better primitive than `ThreadLocal` for exactly this: values are inherited by forked subtasks automatically and are immutable for the scope's duration, which removes both the propagation problem and the clear-on-release problem. It doesn't help across a queue or a network hop — nothing does.

**At a queue boundary, context becomes data and is re-verified on the way out.**

```java
// enqueue: serialize
jobs.enqueue(new ExportJob(TenantContext.require().tenantId(), reportId));

// dequeue: rebind, and re-check — the tenant may have been suspended since
Tenant tenant = tenants.load(job.tenantId());
if (!tenant.canRunJobs()) { jobs.discard(job, "tenant " + tenant.state()); return; }
TenantContext.bind(tenant);
try { handler.run(job); } finally { TenantContext.clear(); }
```

> Re-binding without re-checking is the subtle version of this bug. A bulk export enqueued on Monday, executed Wednesday, for a tenant suspended on Tuesday, will happily generate and email the export — because the payload was written by trusted code and nothing revisited the question.

## Further Reading

- **OWASP API Security Top 10, API1:2023 "Broken Object Level Authorization."** The industry's name for the header-spoofing failure that opens this article, with the general form: an identifier from the request used to select data without checking the caller's relationship to it.
- **RFC 8693, OAuth 2.0 Token Exchange.** The standardized way for one service to obtain a token to act on behalf of a user when calling another. Worth reading even if you implement something lighter, because it names the parties and the failure modes precisely.
- **RFC 6265 on cookies, particularly the `Domain` attribute**, plus the Public Suffix List. The difference between a cookie on `.yourapp.com` and one on `acme.yourapp.com` is the entire isolation story for subdomain-based tenancy, and it's a single character in a `Set-Cookie` header.
- **W3C Trace Context and the OpenTelemetry baggage specification.** The mechanism referenced in the alternatives, including the explicit warning that baggage is neither authenticated nor confidential — the sentence that decides whether you may use it as an authority.
- **The JDK's Scoped Values JEPs, and the structured concurrency proposals alongside them.** The modern answer to the propagation half of this article in Java, and a clear statement of what was wrong with `ThreadLocal` for this purpose.
- **Node.js documentation for `AsyncLocalStorage`.** The equivalent mechanism in the other major runtime, along with an honest list of the cases where it still loses context.
- **The Go blog's article on `context.Context`.** The clearest argument for explicit propagation, including the convention that context is the first parameter and is never stored in a struct.

A **TypeScript/Node** sibling would show how differently this decomposes when the runtime is a single event loop. `AsyncLocalStorage` propagates automatically through promises, timers, and most of the async surface, which eliminates the majority of Java's drop sites without any wrapping — and replaces them with a worse failure mode. A leaked context in Java contaminates *the next request on that thread*, which is at least reproducible under a load test. A leaked context in Node contaminates whichever concurrently-interleaved request happens to resume next, which is nondeterministic and effectively untestable. The interesting content is that trade: automatic propagation buys ergonomics and pays for it with a failure that cannot be reproduced on demand, plus the specific corners where the store is still lost — native addons, listeners registered outside the store, and pooled clients that outlive the run. Not yet written.

---

The habit to carry: for any piece of ambient state in any system, ask two questions. **What happens when it's missing?** and **where does it stop travelling?**

Nearly always, nobody decided either one. The first answer became whatever the accessor's author typed on an afternoon — and returning null is a decision to fail silently, made by someone who wasn't thinking about failure. The second answer is a list of boundaries: a thread pool, a queue, a network call, a connection returned to a pool. Every one of them is a place where ambient state quietly stops being ambient, and the code on the far side has no way to know that it's running without something it assumes it has.
