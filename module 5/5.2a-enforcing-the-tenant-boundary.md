# Enforcing the Tenant Boundary

_Module 5.2a — Multi-Tenancy Architecture_

## The Problem

The previous article ended on an uncomfortable observation: in a pooled system, every query is a place to get the tenant boundary wrong. This one is about what to do with that.

Start with the arithmetic, because it settles the argument before any of the examples do.

Suppose a query site is written correctly — with the tenant filter, on the right column, joined the right way — with probability 0.99. A developer who gets it right ninety-nine times out of a hundred is a good developer. Your application has 340 query sites.

```
  P(no leak anywhere) = 0.99 ^ 340 ≈ 0.03
```

Three percent. And the exponent grows every sprint while the base stays where it is, because the base is a property of human attention and doesn't improve with tenure.

That number is abstract, so here are three leaks that actually look like this. None of them is careless.

**The reasonable inference.** A new endpoint returns comments on a project:

```sql
SELECT * FROM comments WHERE project_id = $1
```

No tenant filter, and the author's reasoning was sound: comments belong to a project, the project is already tenant-scoped, so the comments must be too. That holds — *if* `project_id` was checked against the current tenant. It came out of the URL path. `GET /projects/8842/comments` now returns another company's discussion thread, with a 200, and the test suite passes because the fixture has one tenant in it.

The missing `WHERE` clause isn't really the bug. The bug is that the query's correctness depended on an argument about a value supplied by the caller.

**The job that predates tenancy.** The nightly digest emailer iterates users who have digests enabled and, for each, includes their five most recently active projects. The project query was written when the product had one customer and reads "ORDER BY updated_at DESC LIMIT 5". It has been correct for two years because it was only ever called with one tenant's data in the database. Now the digest goes out with another company's project names in it, to customers, in writing, at 6am, before anyone is awake to stop it.

**The report that moved.** An analyst writes a query against a read replica for an internal revenue dashboard. It's cross-tenant on purpose, and that's fine. Eighteen months later someone embeds a panel from that dashboard into the customer-facing admin page, because it already existed and it looked right.

What the three have in common: each was locally reasonable, and in all three the enforcement lived in the author's head. The author is a different person every time, and about a third of them no longer work there.

### And the over-correction

The instinct after the first incident is to check everywhere. A filter in the repository, a guard in the service layer, an assertion in the controller, a check in the serializer. Six months later nobody can say which one is authoritative, every one of them is frightening to remove, two of them are subtly inconsistent about what an admin can see, and the system's actual guarantee is unknown — because a guarantee you can't state isn't one.

Both failures come from the same gap. There is no single answer to the question **"what mechanism makes this impossible?"** — only a set of habits, and then a set of overlapping habits.

## What It Is

**Tenant isolation** is the property that a request executing in one tenant's context cannot read, modify, or detect the existence of another tenant's data — enforced by a mechanism rather than by convention.

The word doing the work is *mechanism*. "Developers know to filter by tenant" is a description of a culture. "The database refuses to return rows outside the current tenant" is a property of a system, and only the second kind survives a new hire, a deadline, or a stack trace at midnight.

Two neighbours worth separating immediately.

**Isolation is not authorization.** Authorization asks whether this user may perform this action on this resource (Module 4.3). Isolation asks whether the resource is in scope at all. A flawless RBAC implementation with no tenant boundary means an admin of tenant A is an admin of everything. They compose in a fixed order: isolation establishes which universe the request operates in, authorization decides what's permitted inside it. Conflating them produces permission models that accidentally grant cross-tenant reach through a role nobody audited.

**Unguessable identifiers are not isolation.** Switching from sequential ids to UUIDs makes the comments leak above harder to *find* and does not make it not exist. Anyone who obtains an id — from a shared link, a webhook payload, a support ticket, a browser history, an old export — walks straight through. This matters because "we use UUIDs" is a common answer to the isolation question on security questionnaires, and it's an answer about discoverability, not about access control.

One related detail worth fixing now: when a request references another tenant's resource, return **404, not 403**. A 403 confirms the resource exists, which is itself a cross-tenant disclosure — small, but it's the primitive attackers use to enumerate.

## Recognizing the Problem

- Your isolation guarantee is a sentence beginning "developers know to…"
- Your test fixtures contain one tenant.
- Code review is the control. Someone has to *remember* the rule for it to be applied.
- You can't enumerate the places that talk to the database.
- Background jobs, exports, reports, and migrations are written outside whatever data layer you do have.
- A resource belonging to another tenant returns 403.
- You have an admin tool that can read any tenant, and no record of when it has been used.
- Support engineers run ad-hoc SQL in production.
- Your cache keys, search document ids, or object storage paths are built from values that are unique per tenant rather than globally — slugs, invoice numbers, email addresses.
- "Can you prove tenant A can't read tenant B's data?" is answered with incident history rather than with a mechanism.
- Your ORM has a global scope for tenancy, and there's at least one place where someone dropped to raw SQL to make a query fast.

## How It Works

### Four strengths of enforcement

```
  1. CONVENTION       each query carries its own filter
                      strength = the weakest query ever written

  2. DATA ACCESS      one layer injects the filter
     LAYER            strength = how hard it is to go around

  3. DATABASE         the engine appends the predicate itself
     POLICY           strength = holds for anything using that role

  4. TOPOLOGY         the connection can't reach other tenants' rows
                      strength = structural; nothing to forget
```

Level 4 is the previous article — schema or database per tenant. If you chose it, most of this section is already done for your relational data, and you can skip to "the boundary is not only the database," which is where the interesting failures live regardless of pattern.

Level 2 is where most teams land, and it's a genuine improvement: a repository or query builder that adds the tenant filter without the caller mentioning it. Its weakness is stated in its definition — it protects the queries that go through it. Raw SQL for the slow report, a `jdbcTemplate` in one service, a migration script, a psql session — all outside.

Level 3 is the one worth understanding in detail, because it's the only application-level option where being outside your code doesn't mean being outside the boundary.

### Row-level security, concretely

PostgreSQL can attach a predicate to a table that the planner adds to every query against it, for every role that isn't exempt.

```sql
ALTER TABLE projects ENABLE ROW LEVEL SECURITY;
ALTER TABLE projects FORCE  ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON projects
  USING      (tenant_id = current_setting('app.tenant_id')::bigint)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);
```

Four details, each of which is load-bearing:

**`FORCE`, not just `ENABLE`.** Policies do not apply to the table's owner. If your application connects as the role that ran the migrations — extremely common — then `ENABLE` alone buys you nothing at all, and it buys you nothing *silently*, with the feature apparently turned on. `FORCE` makes the owner subject to policies too.

**The application role must not be exempt.** Superuser and any role with `BYPASSRLS` ignores policies entirely. The application connects as a plain, unprivileged role that owns nothing.

**`WITH CHECK`, not only `USING`.** `USING` filters what you can see. `WITH CHECK` constrains what you can write. Without it, a request in tenant 42's context can insert a row stamped `tenant_id = 43` — which is a quieter and nastier bug than reading, because it plants data inside someone else's account.

**The context comes from a setting, and the setting must be transaction-scoped.**

```
  BEGIN;
  SET LOCAL app.tenant_id = '42';
     ← every statement in this transaction is confined
  COMMIT;
     ← the setting is gone; the pooled connection carries nothing forward
```

A session-scoped `SET` survives on the connection after it returns to the pool, and the next request — a different tenant — inherits it. That's the same failure as the unreset `search_path` from the previous article, in a new costume, and it's the single most common way an RLS deployment ends up producing cross-tenant reads. Transaction-scoped settings are also what makes RLS compatible with a transaction-mode connection pooler such as PgBouncer; session-scoped settings are not.

**Fail closed, loudly.** `current_setting('app.tenant_id')` raises an error when the setting is absent. `current_setting('app.tenant_id', true)` returns NULL instead, and a policy comparing against NULL matches nothing — so the query silently returns zero rows. Both are safe; only one is debuggable. Choose the loud one deliberately, because the second variant produces the single most confusing bug class in RLS systems: a correct query returning an empty result, in production, for reasons entirely invisible in the query.

**Keep the predicate simple.** A policy of the form `tenant_id = <constant>` against a tenant-leading index is close to free. A policy containing a subquery — `tenant_id IN (SELECT tenant_id FROM memberships WHERE user_id = …)` — is evaluated per row scanned and will quietly change the cost of every query in the system. Resolve membership once, at the edge of the request, and put the resolved answer in the setting.

### Applying it uniformly

You'll have tables with no tenant column: currency codes, feature definitions, country lists. The temptation is to leave RLS off for those, which is correct on the merits and bad for auditing, because "RLS is enabled on every table" is a one-line invariant you can check in CI, and "RLS is enabled on every table except these nineteen, for reasons documented in a wiki page from 2023" is not.

The better shape is to enable it everywhere and give global tables an explicit permissive policy:

```sql
CREATE POLICY global_read ON currencies FOR SELECT USING (true);
```

Now the exception is a line of SQL a reviewer can see, and a new table with no policy fails closed instead of being invisible.

### The boundary is not only the database

This is the part that distinguishes an isolation design from an RLS tutorial. Your strongest enforcement point covers exactly one store, and a request touches many:

```
                       ┌──── request in tenant 42 ────┐
                       │                              │
        ┌──────────────┼──────┬───────┬───────┬───────┼────────┐
        │   cache    search   object  queue   logs   email/    │  ← no policy
        │                     store                  export    │     applies here
        └──────────────┬──────┴───────┴───────┴───────┬────────┘
                       ▼                              ▼
                 ┌───────────────────────────────────────┐
                 │        PostgreSQL + RLS               │  ← the strong boundary
                 └───────────────────────────────────────┘
```

**Cache.** A cache hit never reaches the database, which means it never reaches the policy. Your cache is, by construction, a bypass of your strongest enforcement point. Every key needs the tenant in it, and the risk concentrates where the rest of the key is unique *within* a tenant rather than globally — slugs, invoice numbers, usernames, external reference ids.

**Search.** One index with a tenant field is fine as long as the filter is applied server-side, by your code, on every query. The failure is the search endpoint that forwards a client-supplied query object to Elasticsearch with a tenant clause merged in — merged in a way a crafted `should` clause can neutralize. Build the tenant filter into a wrapper the client can't reach, or use per-tenant indices or routing.

**Object storage.** Prefix per tenant, and pre-signed URLs scoped to a single object rather than to a prefix. The classic leak is an endpoint that takes a storage key from the request and signs it — the application holds credentials for the whole bucket, so signing a supplied key signs whatever the caller names.

**Queues and background jobs.** The job payload must carry the tenant, and the worker must establish context from it before any query. With RLS in place, a worker that forgets returns zero rows or errors — which is the good failure. Workers that connect using a privileged role because "it's internal" convert that good failure into an unrestricted one, and that role choice is usually made once, early, by someone solving an unrelated problem.

**Logs, traces, and error reporting.** Exception payloads contain rows. If your error tracker is shared and your support team can see everything, that's a decision; it should be a decision.

**The analytics pipeline.** The ETL job connects with a bypass role because it has to. Everything downstream of it — the warehouse, the BI tool, the embedded dashboard — is outside every mechanism discussed so far, and it's the most common place where cross-tenant data ends up somewhere customer-facing.

### The privileged paths you cannot avoid

Migrations, support tooling, backfills, and admin dashboards all need to cross the boundary. Isolation designs fail when this is treated as an embarrassing exception rather than a designed feature. Three rules make it survivable:

1. **A separate role.** `app_user` cannot bypass. `app_admin` can. They are different credentials, and the application's normal path has no access to the second.
2. **A separate code path.** Bypass is reachable from one module that is small enough to read in an afternoon.
3. **Always audited.** Every use records who, when, which tenant, and why — the "why" as a required free-text field, because it makes casual use feel like what it is.

Support impersonation deserves a specific note: it should mint a *tenant-scoped* context for the target tenant, not a bypass context. The support engineer gets exactly what a user of that tenant would get, which is usually what they needed, and the difference between those two designs is whether a support session can accidentally span tenants.

### Detection, because prevention is never complete

**The isolation test suite.** Two tenants, every endpoint, assert 404. This is mechanical, it's the test nobody writes, and it's the only one that would have caught the comments endpoint. Generate it from your route table so it grows automatically; a suite that must be extended by hand decays the week someone is in a hurry.

**The runtime assertion.** Twenty lines, and it catches everything the policy doesn't:

after any result set is materialized, assert that every row's `tenant_id` matches the current context; in non-production, throw; in production, log and alert. It costs a comparison per row, it needs no foresight about which queries are risky, and it catches raw SQL, ORM escapes, and cache hits alike.

**A canary tenant.** A tenant with recognizable data that no real user should ever see. If its marker strings appear in another tenant's response, an export, or an email, you find out from an alert instead of from a customer.

**A CI check** that fails the build when a query is issued outside the sanctioned data layer, and a **periodic alert on bypass-role usage** that goes to a human rather than a dashboard.

## When It's Appropriate

- **Database-enforced policies (RLS): any pooled multi-tenant system with more than two or three people writing queries.** The threshold isn't tenant count or revenue; it's the number of query sites and the rate of new ones.
- **The runtime assertion and a route-generated isolation suite: always.** Together they're a few days of work and they're the highest-value items in this article. Do them before RLS if you have to choose an order — they tell you where you already stand.
- **A single enforcing data-access layer: when you can't use database policies** — a managed database that restricts roles, an ORM that fights connection-level settings, or a non-Postgres store. It's weaker, and it's much better than convention.
- **Per-tenant connections or schemas: when you already chose that pattern.** The isolation is a free side effect; spend the saved effort on the non-database stores instead.
- **Signed, capability-style resource references: for specific surfaces** — public share links, embedded widgets, unauthenticated download endpoints — where there's no session to carry a tenant at all.

## When It's Unnecessary or Overkill

**Single-tenant systems, and products where the tenant is the user.** The boundary is `user_id` and standard authorization covers it.

**Per-tenant encryption keys as an answer to missing `WHERE` clauses.** They defend against a stolen backup or a compromised storage layer, which is a real threat and a different one. Against an application bug they do nothing at all, because the application holds the keys and will happily decrypt whatever it fetched.

**A bespoke policy engine** when the requirement is "rows belong to one tenant." Relationship-based authorization systems are excellent and they solve a harder problem; reaching for one to express a single equality predicate buys you a new distributed dependency on the request path.

**Six overlapping checks.** Belt and braces sounds prudent and produces a system whose guarantee nobody can state. One authoritative mechanism, plus detection that verifies it, is both stronger and smaller.

**Applying strict policies to reference tables** in a way that makes global lookups require a tenant context. Currency codes don't belong to anyone; use the explicit permissive policy above.

## Trade-offs

- **RLS is invisible, and invisibility cuts both ways.** The predicate that protects you doesn't appear in your source code, your ORM logs, or the query you paste into a console. New engineers hit "why is this empty" and have nowhere to look. Document it where people will trip over it, and prefer the error-on-unset variant.
- **You've coupled your data layer to your connection management.** Transaction-scoped settings mean every query must run inside a transaction with the context set, which constrains lazy connection acquisition, ORM session handling, connection pooler mode, and any library that grabs its own connection.
- **Policy cost is real and easy to get wrong.** A simple indexed equality is nearly free. A subquery predicate is per-row. Plans can change in ways that are hard to attribute, because the predicate isn't in the query you're reading.
- **The bypass role becomes the crown jewels.** You've concentrated risk rather than eliminated it: one credential, held by migrations and ETL, that ignores everything. That's a better place to be — one thing to guard, audit, and rotate — but it's a thing.
- **Non-database stores are N separate mechanisms.** There's no single switch for cache, search, object storage, queues, and the warehouse, and each has its own idioms. The database is the easy part of this problem.
- **Legitimate cross-tenant features fight the model.** Shared template libraries, partner access, parent–child organization hierarchies, marketplace listings, cross-workspace search for a user who belongs to several tenants. Each needs an explicit, narrow escape hatch, and each hatch is a thing to review. Design the boundary so the hatches are visible rather than pretending they won't exist.
- **The test suite must be generated, not written.** A hand-maintained isolation suite covers the endpoints that existed when someone cared.
- **Existence leaks through channels a row policy can't see** — timing differences, distinct error messages, rate-limit counters shared across tenants, id-collision behaviour on create. Usually minor; occasionally the finding on a penetration test.

## Alternatives

- **Isolation by topology** — schema or database per tenant, from the previous article. Strictly stronger for relational data, and the reason to choose it is usually something else entirely (residency, restore, contracts) with isolation as the bonus.
- **ORM-level global scopes** — Hibernate's `@TenantId` or `@Filter`, Rails' `default_scope`, Django managers, Prisma client extensions. Easiest to adopt, applies to everything the ORM generates, and bypassed by every line of raw SQL. A reasonable level 2 and a poor terminal state.
- **A database user per tenant with grants**, or per-tenant views with `security_barrier`. Genuine engine-level separation without policies. Both founder on connection pooling and on the operational sprawl of thousands of roles or views.
- **Relationship-based authorization services** (Zanzibar-style: OpenFGA, SpiceDB, and similar). The right tool when access is a graph — nested teams, shared documents, delegated access — with tenancy as the outermost relation. Substantial infrastructure, and a check on the request path you now depend on. Module 4.3 territory.
- **Capability tokens instead of identifiers.** Hand out signed references that encode what they grant. Removes the lookup-then-check pattern entirely, which is elegant for share links and download URLs, and doesn't answer "list everything in my workspace."

## How to Achieve It

**Level 0 — measure what you have.** Generate the isolation suite from your route table: two tenants, every endpoint, expect 404. Run it. The failures are your actual list, ranked by how quickly you should stop reading and go fix something.
*Signal you're behind:* you can't answer "prove it" without describing your code review process.

**Level 1 — one path in, one assertion out.** Every query goes through a single data-access layer, raw SQL is confined to a module that reviewers watch, and the runtime assertion checks every returned row against the current context. This is cheap and it's diagnostic: the assertion tells you where your real query sites are.
*Signal:* a near-miss in code review, or the assertion firing in staging from somewhere you didn't know existed.

**Level 2 — push it into the database.** RLS with `FORCE`, an unprivileged application role, `WITH CHECK` as well as `USING`, transaction-scoped context, and the error-on-unset variant. Roll it out one table at a time, with the assertion from level 1 still running as a second opinion.
*Signal:* you have more query authors than you can name, or a customer asks how segregation is enforced and "in the application" isn't an acceptable answer.

**Level 3 — extend past the database**, in order of what a leak would cost: cache keys, background job context, object storage paths, search filters, then exports and outbound email.
*Signal:* the first incident that didn't involve SQL at all.

**Level 4 — make the privileged paths explicit.** Separate role, one small module, mandatory audit with a reason, impersonation that is tenant-scoped rather than unrestricted.
*Signal:* someone asks who looked at a specific customer's data last month and the answer takes more than a minute.

**Level 5 — continuous verification.** Canary tenant, CI invariant that every table has a policy, alerting on bypass-role usage, isolation tests in the deploy pipeline rather than nightly.
*Signal:* you're being audited, or you've grown past the point where anyone reads every migration.

## Implementation

TypeScript and node-postgres, because the entire mechanism is visible in one function and the dangerous variations of it are one character apart.

**The context boundary.**

```ts
const pool = new Pool({ /* connects as app_user — no BYPASSRLS, owns nothing */ });

export async function withTenant<T>(
  tenantId: string,
  fn: (db: PoolClient) => Promise<T>,
): Promise<T> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    // third argument `true` = local to this transaction
    await client.query("SELECT set_config('app.tenant_id', $1, true)", [tenantId]);
    const result = await fn(client);
    await client.query("COMMIT");
    return result;
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}
```

> **Why `set_config` rather than `SET LOCAL`.** `SET` is not a parameterized statement — its argument can't be bound, so using it means interpolating a value into SQL. If the tenant identifier ever comes from a subdomain, a header, or a JWT claim you haven't validated as tightly as you think, you have string concatenation into SQL at the exact point where your security boundary is established. `set_config` takes a bound parameter and does the same thing.
>
> **Why the third argument matters more than anything else here.** `true` means transaction-local, so the setting vanishes at `COMMIT` and the connection returns to the pool clean. Pass `false` — or use session-level `SET` — and the next request to borrow that connection inherits the previous tenant's context. It will work perfectly in development, where the pool has one connection and one tenant, and it will produce cross-tenant reads under concurrency in production.

**Don't export the pool.** The function above is only a boundary if there's no way around it. `pool` stays module-private; handlers receive a client, never a pool; the type of a database handle in the rest of the codebase is something you can only obtain from `withTenant`. This is the part that's a design decision rather than a snippet, and it's what makes the mechanism hold.

```ts
app.get("/projects/:id/comments", async (req, res) => {
  const rows = await withTenant(req.tenant.id, (db) =>
    db.query("SELECT * FROM comments WHERE project_id = $1", [req.params.id]),
  );
  res.json(rows.rows);           // ← the query from the top of this article
});
```

That's the original leaking query, unchanged, now safe — because the policy on `comments` confines it regardless of what the author was thinking about. That's the whole argument for level 3 in one example: the fix applies to code that hasn't been written yet.

**The second opinion.**

```ts
export function assertTenant<T extends { tenant_id?: string }>(
  rows: T[],
  expected: string,
): T[] {
  const stray = rows.find((r) => r.tenant_id !== undefined && r.tenant_id !== expected);
  if (stray) {
    if (process.env.NODE_ENV !== "production") {
      throw new Error(`cross-tenant row: expected ${expected}, got ${stray.tenant_id}`);
    }
    logger.error({ expected, actual: stray.tenant_id }, "cross-tenant row returned");
    metrics.increment("isolation.violation");
  }
  return rows;
}
```

> Keep this even after RLS is deployed. It covers the paths RLS doesn't: cache hits, search results, the ORM's second-level cache, anything reading a replica through a different role, and the one report that runs as `app_admin` because it legitimately has to. It also covers the window where RLS is enabled on forty tables and not yet on the forty-first.

**And the store that isn't the database.**

```ts
const cacheKey = (tenantId: string, ...parts: string[]) =>
  ["t", tenantId, ...parts].join(":");

await cache.set(cacheKey(tenant.id, "project", "slug", slug), project);
```

A one-line helper, and the rule is that raw string keys don't appear anywhere else. The same shape applies to search document ids, object storage prefixes, idempotency keys, and queue job payloads — one constructor per namespace, tenant first, no exceptions, because the exception is where the collision happens.

## Further Reading

- **PostgreSQL documentation: `CREATE POLICY`, and the "Row Security Policies" section of the DDL chapter.** Short, complete, and the source for the owner-bypass behaviour that quietly defeats half of all RLS deployments. Read `ALTER TABLE … FORCE ROW LEVEL SECURITY` specifically.
- **PostgreSQL documentation on `set_config` and `current_setting`.** Two paragraphs that determine whether your context is transaction-scoped, and whether an unset context fails loudly or silently.
- **Supabase's RLS guides, particularly the performance notes.** The most practical public writing on running RLS at scale: indexing policy columns, why wrapping a function call in a `SELECT` changes its evaluation, and what the plans look like when it goes wrong.
- **PgBouncer documentation on pooling modes.** Explains exactly why transaction-scoped settings are the only ones compatible with transaction pooling, which is a constraint that will find you eventually whether or not you go looking for it.
- **OWASP Top 10 A01: Broken Access Control**, and the **Authorization Cheat Sheet.** The industry's framing of what this article calls a tenant leak, plus the 404-versus-403 reasoning stated more carefully than above.
- **AWS, _SaaS Tenant Isolation Strategies_.** Cited in the previous article for vocabulary; the chapter that matters here is the distinction between isolation enforced at deployment time and isolation enforced at runtime, and its treatment of scoping credentials per request.
- **The Google Zanzibar paper.** For when tenancy stops being an equality check and becomes a graph — nested organizations, delegated access, resources shared between tenants. Worth reading before choosing to build that yourself.

A **Java** sibling would show something structural that this one can't. Spring's transaction management already owns the moment a connection is acquired and a transaction begins, which is exactly where the tenant setting must be applied — so a `TransactionSynchronization` or a connection-preparer makes the context binding automatic for every `@Transactional` method, including ones written by people who have never heard of RLS. That's a stronger guarantee than an exported function that developers must remember to call. It also introduces a trap with no equivalent here: propagation settings and lazy connection acquisition can produce a transaction whose connection is obtained outside the synchronization, silently unsettled, and the failure is intermittent and load-dependent. Framework ownership of the seam is the whole story, in both directions. Not yet written.

---

The habit to carry forward is a single question, asked of any multi-tenant system including your own: **what is the one mechanism, and what goes around it?** There is always a list on the right-hand side — the cache, the search index, the nightly job, the export, the replica, the admin tool, the pipeline into the warehouse. The mechanism is the easy half of the work and the list is where the incidents come from, and a team that can recite its own list is in dramatically better shape than one that believes there isn't one.
