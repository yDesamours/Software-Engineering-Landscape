# Refactoring Safely: Changing Structure Without Changing Behavior

_Module 31 · Code Quality & Technical Debt · 31.3b_

## The Problem

Suppose 12 engineers build a freight-quoting platform. Shippers enter a load (origin, destination, stops, weight, equipment type) and get a price for trucking it. Pricing lives mostly in one function, `quote()`, in `pricing/quote.ts`. Over five years it has grown to 1,400 lines: base rates by lane, fuel surcharges, per-stop fees, carrier contract overrides, weekend adjustments, and a dozen special cases for large customers. It's the top hotspot in the repository (31.1), and the debt register (31.3a) says adding any pricing rule takes three to four times the estimate.

Over one year, three attempts to improve it go wrong in three different ways.

**Refactor and feature in one change.** An engineer needs to add regional fuel surcharges and decides to clean up `quote()` on the way. Three weeks later, the pull request changes 3,100 lines. Reviewers can't tell which changes are meant to alter prices and which are only moving code around, so they review the parts they understand and approve. The merge breaks pricing for multi-stop loads: an extracted helper applies the per-stop fee before the fuel surcharge instead of after, and multi-stop quotes come out 4–11% low. It takes nine days to notice. The company honors the booked loads, at a cost of about $60,000, and reverts the change, losing the regional surcharges too.

**Fear.** After that, the unwritten rule is "don't touch `quote.ts`." New pricing rules are added as `if` blocks near the top of the function, where they're least likely to disturb anything. The function gets longer and harder to change, which is the opposite of what anyone wanted.

**A change across 180 files.** Distances are passed around as plain numbers, in miles, and a new European customer needs kilometers. The team decides to replace `calculateDistance(from, to): number` with a function returning a `Distance` value that knows its unit. It's called in 180 places. An engineer does it with search and replace. Two files had their own local function named `calculateDistance`, for a different purpose; one test file imported it under an alias the search missed. Type errors catch some of this, and a quoting bug in the admin estimator catches the rest, a week later.

None of these were caused by a lack of skill or care. Each was a missing technique: a way to separate structural changes from behavior changes, a way to change code nobody fully understands without fear, and a way to change something used in hundreds of places without doing it by hand.

## What It Is

**Refactoring** is changing the internal structure of code without changing its observable behavior, in small steps that each leave the system working. Martin Fowler's definition stresses both halves: it's _behavior-preserving_, and it's done through a sequence of small, safe transformations, not one large rewrite.

The word is often used loosely for any code change, and the confusion causes real problems. Three things are commonly called refactoring:

- **Refactoring proper:** extract a function, rename a type, move a module. Behavior stays the same at every step.
- **A rewrite:** build a new implementation and replace the old one. Behavior is supposed to match, but nothing guarantees it step by step.
- **A redesign with behavior changes:** the code is restructured _and_ does something different afterwards.

The first pull request in the problem was all three at once. The techniques in this article make it practical to keep them apart.

**Code smells** (a term from Kent Beck and Fowler) are surface features that often indicate a structural problem: a very long function, a class that changes for many unrelated reasons, the same `switch` on a type repeated in five places. They're prompts to look, not rules to enforce. Whether a smell is worth fixing depends on whether anyone needs to change that code, which is what 31.1 and 31.3a established.

## Recognizing the Problem

- Pull requests mix cleanup and feature work, and reviewers can't tell which changes are meant to alter behavior.
- A "refactoring" caused a production bug.
- Some files have an unwritten "don't touch" rule.
- New logic gets added at the edges of a function (top, bottom, new flags) rather than where it belongs, to avoid disturbing anything.
- A change to a widely used function or type is done by search and replace, or keeps being postponed because it touches too many files.
- The only tests around a hotspot are a few happy-path cases, or none at all.
- A replacement for an old module has been "almost ready" on a branch for months.
- Refactoring efforts don't finish: they stop halfway, leaving two ways of doing the same thing.

## How It Works

### 1. Two hats

Kent Beck describes development as wearing one of two hats. When adding behavior, you add behavior and don't restructure. When refactoring, you restructure and don't change behavior. You switch hats often, sometimes every few minutes, but you're never wearing both at once.

The practical consequence is separate commits, and usually separate pull requests. A reviewer checking a pure refactoring asks only "is the behavior unchanged?", which tests and careful reading can answer. A reviewer checking a behavior change sees a small diff with only the intended difference in it. The 3,100-line PR asked reviewers to answer both questions about every line at once.

The most useful form of this is **preparatory refactoring**. Before adding regional surcharges, first restructure `quote()` so that surcharges live in one clearly defined step. That's one or two pure-refactoring PRs. Then the feature itself becomes a small change in an obvious place. Beck's phrasing: make the change easy (this may be hard), then make the easy change.

### 2. A safety net that pins current behavior

Refactoring is only safe if you can tell when behavior changed. For code with good tests, that's the tests. For a 1,400-line function with a few happy-path tests, you need to create the net first.

**Characterization tests**, a term from Michael Feathers, record what the code does now, not what it should do. You don't need to understand every rule in `quote()` to write them; you need inputs and the outputs the current code produces. A good source is production: take a few thousand real quote requests (anonymized), run them through the current code, and store the results as the expected outputs. These are also called **golden master** or **approval** tests.

Two properties make them different from ordinary tests:

- **They pin bugs too.** If the current code charges weekend fees on Friday nights, the characterization test expects that. When you find such a bug during refactoring, don't fix it in the same change. Write it down, finish the refactoring, then fix it as a separate behavior change and update the expected outputs on purpose.
- **Their coverage comes from input variety.** A thousand ordinary single-stop loads won't exercise the multi-stop path. Check which branches the recorded inputs actually reach (a coverage report is useful for exactly this, 21.4), and add inputs for the paths they miss.

Often the code can't be tested as it is, because it reads the current time, calls a fuel-price API, or queries the database directly. Feathers calls the places where you can change what code depends on without editing its logic **seams**. Creating them is itself a refactoring, done carefully with minimal edits: pass in a clock and a rates source instead of reading them directly. Getting code under test is often the hardest part of the whole effort.

### 3. Small steps, mostly automated

The refactoring catalog is a list of named, small transformations: extract function, inline function, rename, move function, introduce parameter object, split phase, replace conditional with polymorphism, and dozens more. Each has a mechanical recipe that preserves behavior.

Many of them are built into editors. The TypeScript language service, IntelliJ, and `gopls` can rename symbols, extract functions and move code using the compiler's understanding of the program, which is far safer than editing by hand. Use the automated version where it exists. Do the rest in steps small enough that each one compiles and passes the tests, commit after each, and merge often. If a step breaks something, you lose minutes, not days.

AI coding assistants can propose larger refactorings quickly. Unlike an editor's rename, nothing guarantees their output preserves behavior, so treat it as a manual refactoring: in small pieces, checked against the safety net.

### 4. Smells point to specific refactorings

| Smell | What it usually means | Typical refactoring |
| --- | --- | --- |
| Long function | Several steps tangled together | Extract function; split phase (compute, then apply) |
| Long parameter list | Values that travel together without a name | Introduce parameter object |
| Primitive obsession (`miles: number`, `cents: number`) | Missing domain types; units and rules scattered | Replace primitive with a value object (`Distance`, `Money`) |
| Repeated `switch` on the same type | Behavior per variant spread across files | Replace conditional with polymorphism, or a lookup table |
| Shotgun surgery (one change touches ten files) | One concept spread across modules | Move function; gather into one module |
| Divergent change (one file changes for many reasons) | Several concepts in one place | Split module or class |
| Feature envy (a function mostly uses another module's data) | Logic in the wrong place | Move function to the data |

`quote()` has most of these. The regional-surcharge feature only needs two: split phase, so that surcharges become one step, and introduce parameter object for the load's details. That's where to start; the rest can wait until something needs it.

### 5. Changes too large for one step

Some refactorings can't be done in one pull request: replacing a module, changing a signature used in hundreds of places, moving to a new library. Four techniques keep these incremental.

**Parallel change** (also called expand–migrate–contract). To change an interface, don't edit it in place. _Expand:_ add the new version alongside the old. _Migrate:_ move callers to it, a few at a time, in separate PRs. _Contract:_ remove the old version once nothing uses it. Mark the old one `@deprecated` so editors show it struck through and new code avoids it. The same pattern applied to database schemas is in 6.3.

**Branch by abstraction.** To replace an implementation, first put an interface in front of the old one and move all callers to the interface. Then build the new implementation behind the same interface, on `main`, switched off. Switch traffic over with a flag, gradually, and delete the old implementation when the new one has proven itself. This is how the pricing engine could be replaced without a long-lived branch (Module 29 covers why those fail).

**Parallel run.** Before switching over, run both implementations on real traffic, return the old one's result, and record every difference:

```
request ──► old engine ──► response to user
    │
    └─────► new engine ──► compare with old ──► log differences
                            (sampled; errors swallowed; no side effects)
```

For pricing, where "almost the same" means lost money, this finds the multi-stop ordering bug before any customer sees it. GitHub built a library for this pattern (Scientist) to replace its merge implementation. It only works for code without side effects, or whose side effects you can suppress for the second run: you can't send an email twice to compare.

**Codemods.** For mechanical changes across many files, write a program that edits the program. A codemod parses the code into a syntax tree, finds matches using the compiler's knowledge of types and imports, and rewrites them. That's what search and replace couldn't do for `calculateDistance`: tell the imported function apart from a local one with the same name. Tools include `ts-morph` and `jscodeshift` for TypeScript and JavaScript, OpenRewrite for Java, Comby and Semgrep's autofix for many languages, and `gofmt -r` and `gopls` for Go. Google's large-scale change process, where one change touches thousands of files, is built on the same idea: automate the edit, split it into independently reviewable pieces, and let tests catch what the tool can't.

The system-level version of these, replacing a whole service by routing traffic away from it piece by piece (the strangler fig pattern), is covered in 2.1 and 23.5.

### 6. When to stop

Refactor until the change you need is easy, and then stop. The goal is making the next change cheap, not reaching an ideal design. A refactoring with no deadline tends to expand, since there is always more that could be improved, and then stall halfway, leaving two patterns where there used to be one. Timebox it. If a parallel change or branch by abstraction can't be finished, deciding to finish the migration is as important as starting it: the half-migrated state is the worst of both.

## When It's Appropriate

- **Before changing a hotspot.** Preparatory refactoring pays for itself in the change it enables, which is the funding model from 31.3a.
- **When a debt-register item is marked "pay down."** Incremental refactoring is how most of them get paid.
- **When the same bug keeps appearing in duplicated logic.** Gather the logic into one place first.
- **When a type or function used widely needs to change,** such as units, money, identifiers, or error handling. Parallel change and codemods make this routine rather than heroic.
- **When a dependency or framework must be replaced.** Branch by abstraction plus a parallel run is how to replace an engine of any kind without a risky switch-over.
- **During code review of new code.** Small refactorings are cheapest before anything else depends on the code.

## When It's Unnecessary or Overkill

- **Code nobody is going to change.** A smelly module that's stable has almost no interest (31.3a). Refactoring it spends effort and adds risk for nothing.
- **Code about to be deleted or replaced.**
- **Refactoring to taste.** Changing working code to match a personal preference, or a pattern read about last week, costs review time and churn and helps no one.
- **Characterization tests for trivial code.** A ten-line function with an obvious behavior can be refactored with its ordinary tests.
- **A parallel run for a change the tests fully cover.** It's valuable where behavior is hard to specify and mistakes are expensive, like pricing, tax and permissions, not for every change.
- **A codemod for twelve call sites.** Editing them with the editor's help is faster than writing and testing a program.

## Trade-offs

**It takes more steps.** Parallel change and branch by abstraction are more total work than a big-bang change: more PRs, and two implementations to keep working in the meantime. That extra work is what buys safety and the ability to stop at any point.

**Characterization tests pin everything, including what you want to change.** They make intended behavior changes noisy, because every one requires updating expected outputs. Large snapshot files are also easy to approve without reading. Keep them focused, and delete them once real specification tests exist.

**Seams change the code before any tests protect it.** The first edits to get code under test are the riskiest ones. Keep them minimal and mechanical, and prefer automated refactorings for them.

**Parallel runs cost capacity and need care.** They double the compute for sampled requests, need result normalization (rounding, ordering) to avoid false differences, and must not let the new path's errors or side effects leak into the real response.

**Half-finished migrations are debt.** Two ways of doing the same thing are worse than either. Every incremental technique needs an owner who finishes it.

**Codemods are code.** They have bugs, miss edge cases, and generate large diffs that are hard to review. Run them in batches and review a sample carefully, rather than skimming thousands of changed lines.

**Refactoring is invisible to users.** The benefit arrives as later changes that are cheaper, which is harder to see than a new feature. That's why it's easier to justify tied to a feature (31.3a).

## Alternatives

**Rewrite.** Sometimes correct: when the old code can't be tested at all, when its platform is gone, or when what it does is no longer what's needed. Done safely, it looks like branch by abstraction with a parallel run anyway, so the difference is mostly how much old code survives.

**Contain it instead.** Wrap the messy code behind a clean interface and leave its insides alone. New code uses the interface; the mess stops spreading. This is the "contain" decision from 31.3a, and often the right one for stable code.

**Delete it.** A special case for a customer who left two years ago doesn't need refactoring. Usage data, logs or feature-flag telemetry can show what's no longer used.

**Leave it and work around it.** A legitimate choice when the code rarely changes. The workaround is where the interest gets paid, so it should be a decision, not a default.

## How to Achieve It

**Step 1: separate refactoring from behavior changes.** Separate commits at least, separate PRs where possible, labeled as such. _Signal to move on:_ reviews improve, but people still avoid the riskiest code.

**Step 2: build safety nets around hotspots.** Before the next change to a top hotspot, add characterization tests from recorded real inputs, checking which branches they reach. Create seams where needed. _Signal:_ the team can change the hotspot, but slowly.

**Step 3: make small steps the norm.** Use automated refactorings, commit and merge frequently, and do preparatory refactoring before each feature in the area. _Signal:_ some changes are too large for this, such as replacing a module or changing a widely used interface.

**Step 4: use parallel change and branch by abstraction for larger changes,** with a parallel run where behavior is hard to specify and mistakes are costly. Give each migration an owner and an end date. _Signal:_ a change needs to touch more files than people can edit by hand.

**Step 5: write codemods** for codebase-wide mechanical changes, split into batches that can be reviewed and reverted independently.

## Implementation

TypeScript, following the freight-pricing example through the three scales: a safety net for one function, a parallel run for replacing an engine, and a codemod for a change across the codebase.

First, a characterization test. Recorded, anonymized production requests, each with the fuel price and date it was quoted with, run through the current code; the first run writes the expected outputs, later runs compare against them:

```ts
// pricing/quote.characterization.test.ts
import { describe, expect, it } from "vitest";
import { readFileSync } from "node:fs";
import { quote } from "./quote";
import { fixedClock, fixedRates } from "../testing/seams";

type Recorded = { id: string; request: QuoteRequest; quotedAt: string; fuelIndex: number };
const cases: Recorded[] = JSON.parse(readFileSync(new URL("./fixtures/recorded-quotes.json", import.meta.url), "utf8"));

describe("quote() characterization", () => {
  it.each(cases)("$id", async ({ id, request, quotedAt, fuelIndex }) => {
    const result = quote(request, { clock: fixedClock(quotedAt), rates: fixedRates({ fuelIndex }) });
    const group = request.stops.length > 1 ? "multi" : "single";
    // Money in integer cents, so there's no rounding noise in the snapshot.
    await expect({ totalCents: result.totalCents, lines: result.lines })
      .toMatchFileSnapshot(`./__golden__/${group}/${id}.json`);
  });
});
```

> **The seam came first.** `quote()` originally read `new Date()` and called the fuel-price service itself, so the same input gave different prices on different days and no snapshot could be stable. The only change made before these tests existed was adding the optional second parameter, defaulting to the real clock and rates. It was a small, mechanical change, reviewed on its own. Everything after it was protected by these tests.
>
> **Check what the fixtures reach.** The first set of 2,000 recorded quotes contained only 31 multi-stop loads and none with more than three stops, so the snapshots would have missed the ordering bug from _The Problem_. Running them with coverage showed the untouched branches, and the team added recorded cases until those branches were exercised. Splitting snapshots into `single/` and `multi/` makes that gap easy to see.

Second, branch by abstraction with a parallel run. Both engines sit behind one interface; the comparing engine always answers with the legacy result:

```ts
// pricing/engine.ts
export interface PricingEngine {
  quote(req: QuoteRequest, ctx: PricingContext): Quote;
}

export class ComparingEngine implements PricingEngine {
  constructor(
    private legacy: PricingEngine,
    private candidate: PricingEngine,
    private sampleRate: number,
    private report: (diff: { req: QuoteRequest; legacy: Quote; candidate?: Quote; error?: unknown }) => void,
  ) {}

  quote(req: QuoteRequest, ctx: PricingContext): Quote {
    const legacy = this.legacy.quote(req, ctx);
    if (Math.random() < this.sampleRate) {
      try {
        const candidate = this.candidate.quote(req, ctx);
        if (candidate.totalCents !== legacy.totalCents || !sameLines(candidate.lines, legacy.lines)) {
          this.report({ req, legacy, candidate });
        }
      } catch (error) {
        this.report({ req, legacy, error });   // the candidate's failure must never reach the user
      }
    }
    return legacy;
  }
}

// Wiring, controlled by a flag: "legacy" → "compare" → "candidate" → delete the legacy engine.
export const pricingEngine: PricingEngine = selectEngine(flags.get("pricing-engine"));
```

> **Compare what matters, normalized.** `sameLines` compares line items by type and amount, ignoring their order, because the new engine lists surcharges in a different order without changing any price. Without that, every quote would be reported as different and the real differences would be lost. Deciding what counts as "the same" is most of the work of a parallel run.
>
> **This works because pricing is pure.** `quote()` computes and returns; it doesn't book, charge or notify. For code with side effects, the candidate would need those suppressed or redirected, and some code can't be compared this way at all.

Third, a codemod for the distance change. It replaces calls to the imported `calculateDistance` with the new function, and only where the call resolves to the real module:

```ts
// codemods/distance.ts
import { Project, SyntaxKind } from "ts-morph";

const project = new Project({ tsConfigFilePath: "tsconfig.json" });
const legacy = project.getSourceFileOrThrow("src/geo/distance.ts").getFunctionOrThrow("calculateDistance");

for (const ref of legacy.findReferencesAsNodes()) {
  const call = ref.getParentIfKind(SyntaxKind.CallExpression);
  if (!call || call.getExpression() !== ref) continue;        // an import, re-export or type use: handled separately

  // calculateDistance(a, b)  →  distanceBetween(a, b).miles   (same number, same behavior)
  call.replaceWithText(`distanceBetween(${call.getArguments().map((a) => a.getText()).join(", ")}).miles`);

  const file = call.getSourceFile();
  if (!file.getImportDeclaration((d) => d.getNamedImports().some((n) => n.getName() === "distanceBetween"))) {
    file.addImportDeclaration({ moduleSpecifier: "@/geo/distance", namedImports: ["distanceBetween"] });
  }
}
await project.save();
```

> **Why this is safe where search and replace wasn't.** `findReferencesAsNodes` uses the compiler's symbol resolution, so the two local functions that happen to share the name are never touched, and the aliased import in the test file is found even though the text `calculateDistance` doesn't appear at the call. It's also a pure refactoring: every call site still receives a number of miles. Changing callers to use kilometers where needed is a separate behavior change, made one area at a time. Unused imports of the old function are left behind for the linter to report; the contract step removes `calculateDistance` itself once nothing references it.

## Further Reading

- Martin Fowler, _Refactoring: Improving the Design of Existing Code_ (2nd ed., Addison-Wesley, 2018). The catalog, with examples in JavaScript. The online catalog at refactoring.com lists every refactoring.
- Michael Feathers, _Working Effectively with Legacy Code_ (Prentice Hall, 2004). Characterization tests, seams, and dozens of techniques for getting untested code under test.
- Kent Beck, _Tidy First?_ (O'Reilly, 2023). Small structural changes, separating them from behavior changes, and when they're worth doing.
- Martin Fowler, "Branch By Abstraction," and Danilo Sato, "Parallel Change" (both on martinfowler.com).
- GitHub's Scientist library (github.com/github/scientist), and the GitHub engineering post "Move Fast and Fix Things" (2015) on using it to replace merge code safely.
- Titus Winters, Tom Manshreck and Hyrum Wright (eds.), _Software Engineering at Google_ (O'Reilly, 2020), chapter 22, "Large-Scale Changes."
- Tool documentation: `ts-morph` and `jscodeshift` for TypeScript and JavaScript; OpenRewrite for Java; Comby for structural search and replace in many languages; ApprovalTests for golden-master testing.

A sibling in **Java** would be worth writing, though it isn't yet. OpenRewrite performs codemods on a type-attributed syntax tree that keeps formatting intact, and publishes reusable recipes for entire migrations, such as moving an application between major Spring Boot versions. That turns large-scale refactoring from something each team writes into something an ecosystem shares. Together with IntelliJ's structural search and replace, it shows how much further automated refactoring goes when the language's type information is complete.

---

The habit to take from this: before any change to code you're nervous about, ask two questions. _How would I know if I changed its behavior?_ If you can't answer, build that first. _Am I restructuring or changing behavior right now?_ If the answer is "both," split the change.
