# Documentation Close to Code: Writing Down What the Code Can't Say

_Module 31 · Code Quality & Technical Debt · 31.4a_

## The Problem

Suppose 40 engineers build a fleet-telematics platform. GPS trackers in delivery vans send a position ping every few seconds. The platform turns those pings into trips, mileage, geofence alerts and driver-behavior scores, and bills fleet operators per mile tracked. A new backend engineer joins and, like the last five, takes about three weeks to open a meaningful pull request. The reasons are all documentation.

**The README lies.** It says to run `docker-compose up`, but the team moved to `make dev` a year ago. It lists a `geocoder` service that was deleted in 2024. The new engineer spends a day and a half getting the stack running, mostly by asking in Slack.

**The wiki answers everything, four times.** Searching the wiki for "run the ingestion pipeline locally" returns four pages. They disagree. The newest is 14 months old. None says which is current.

**Comments narrate the obvious and skip the important.** Most comments restate the line below them: `// loop over pings`, `// increment counter`. Meanwhile, `dedupePings()` has no comment at all. It treats two pings from the same tracker as duplicates if their timestamps are within two seconds, not only if they're identical. In week three, the new engineer "fixes" this to exact matching, because two seconds looks like a bug. It wasn't. One widely deployed firmware version resends buffered pings after a reconnect with timestamps shifted by up to a second. With exact matching, those pings get counted twice, trips double in length for fleets on that firmware, and the per-mile bill goes up with them. Three customers notice before the team does.

**A comment that was once true.** Above the ingestion retry loop: `// retries 3 times`. The constant was changed to 5 two years ago; the comment wasn't. Another team set its alert thresholds based on the comment.

**Knowledge that lives in people.** Two senior engineers estimate they spend a third of their time answering questions. The answers are good, and they're gone as soon as the Slack thread scrolls away.

The team doesn't have too little documentation. It has a wiki with 600 pages. What it lacks is documentation of the right kind, in the place where a reader actually looks, and some reason for any of it to stay true when the code changes.

## What It Is

**Documentation close to code** means the explanations that live in the repository next to what they explain: comments, interface documentation on functions and types (docstrings, TSDoc, godoc), READMEs for each repository and package, and guides in a `docs/` folder. It's versioned with the code, reviewed in the same pull requests, and read at the moment someone is working on that code.

A useful way to think about any document is by three questions: _who reads it, what are they trying to do, and how fast does it go out of date?_ A comment explaining a two-second window is read by whoever is about to change that line, and it's accurate for as long as the firmware behaves that way. A setup guide is read by new engineers once, and it goes stale with every change to the dev environment.

Several neighbors are covered elsewhere: reference documentation for an external API, such as OpenAPI specifications, is 7.2; architecture documentation and diagrams are 31.4b; recording decisions as ADRs is 2.5; commit messages as a history of _why_ are 29.1b; incident runbooks are 24.3.

## Recognizing the Problem

- New engineers take weeks to make their first real change, and spend much of that time asking questions.
- Setup instructions don't work as written, and everyone has private fixes.
- Searching the wiki returns several conflicting pages for one topic.
- Comments describe what the next line does; nothing explains why unusual code is the way it is.
- Someone "fixed" code that was deliberately strange, and caused an incident.
- A comment, README or doc states something the code no longer does.
- The same questions get asked in chat every month, and answered by the same people.
- Using a shared package means reading its implementation, because nothing says what its functions promise.

## How It Works

### 1. Why documentation goes stale

Documentation is a second copy of knowledge whose first copy is the code, or the behavior of the world the code deals with. Any two copies drift apart unless something forces them to change together. The further a document is from the code, in location and in process, the less likely anyone is to notice when they diverge.

```
closer to the code                                                 further away
│ names and types │ comment on the line │ doc on the function │ package README │ docs/ folder │ wiki │
  checked by the     seen by whoever       shown in editors       reviewed with     reviewed if     not reviewed with
  compiler           edits the line        on hover               the package       someone checks  code at all
◄── more likely to stay accurate                              reaches more readers, and more topics ──►
```

The principle that follows: put each piece of knowledge as close to the code as it can go and still reach the reader who needs it. Explanations of a single line belong on that line. Promises a function makes belong on the function. How to run a service belongs in its README. Only things that aren't about any particular code belong on a wiki: team processes, who's on call, how to request access.

### 2. What code can't say

Code says precisely what it does and how. What it can't say:

- **Why.** Why two seconds, and not exact matching.
- **Why not.** The obvious approach that was tried and failed, so that nobody tries it again.
- **What it assumes about the outside world.** Firmware behavior, a vendor's rate limit, a regulation.
- **Consequences that aren't visible locally.** "This number feeds billing."
- **The contract.** What a function promises its callers: units, valid ranges, errors, side effects, whether it's safe to call twice.

These are what comments are for. The missing comment on `dedupePings()` needed two sentences:

```ts
// Treat pings within 2s as duplicates, not only identical timestamps: firmware 3.x
// resends buffered pings after reconnecting with timestamps shifted by up to ~1s.
// Exact matching double-counts those and inflates billed mileage (INC-2231).
```

Comments that hurt more than help:

- **Narration** that repeats the code (`// increment counter`). It adds reading time and trains people to skip comments.
- **Copies of facts the code states.** `// retries 3 times` duplicates a constant, and whichever copy changes second is wrong. Refer to it (`// retries up to MAX_ATTEMPTS`) or say nothing.
- **Commented-out code.** Version control has it.
- **Change history** ("2023-04: added X"). That's what commit messages and `git blame` are for.

The best way to explain _what_ is usually to improve the code itself: a better name, an extracted function, a type like the `Distance` from 31.3b instead of a bare number. "Self-documenting code" is a good goal for _what_. It can't express _why_, and the dedupe window is the proof: no name for that function would have explained the firmware.

### 3. Interface documentation: the contract, where callers read it

Documentation on exported functions, types and modules (TSDoc or JSDoc in TypeScript, docstrings in Python, doc comments in Go and Java) is shown by editors when someone hovers over a call. That's where most of it gets read, so it should answer what a caller needs without opening the implementation:

- What it does, in a sentence.
- Parameters, especially units and valid ranges.
- What it returns, and in what cases it returns nothing.
- What it throws or rejects with.
- Side effects: writes, network calls, caching.
- Anything non-obvious about calling it: idempotency, ordering, thread safety, cost.
- An example, when usage isn't obvious from the signature.

Tags like `@deprecated`, `@throws` and `@see` are understood by editors and documentation generators. For libraries used by other teams, a generator such as TypeDoc produces browsable reference documentation from these comments.

Require interface documentation where it pays off: exported symbols of shared packages, which have many callers who don't own the code. Requiring it on every private helper produces comments like `/** Gets the user. */` above `getUser()`, which is narration again.

### 4. READMEs: the front door

A README is the first thing someone reads when they arrive at a repository, or at a package or service inside a monorepo. It should answer, in this order:

1. **What this is,** and who uses it, in two or three sentences.
2. **How to run it,** ideally with one command.
3. **How to test it.**
4. **Where it runs and how it's deployed.**
5. **Who owns it** and how to get help.
6. **Where to go next:** links to deeper docs, architecture (31.4b), runbooks.

Keep it short; a README that tries to explain everything won't be kept up to date. And turn instructions into scripts wherever possible. "Run `make dev`" backed by a script that CI also runs can't silently become wrong the way seven manual steps can. A dev container or a setup script (Module 3.2) is documentation that's tested every time someone uses it.

### 5. Guides: four kinds, kept apart

The Diátaxis framework (Daniele Procida) distinguishes four kinds of documentation, each serving a different need:

| Kind | The reader wants to… | Example |
| --- | --- | --- |
| **Tutorial** | learn, by doing something guided | "Your first week: run the stack, send a fake ping, watch it become a trip" |
| **How-to guide** | accomplish a specific task | "Replay a day of pings for one tracker" |
| **Reference** | look something up | Interface docs; configuration options; event schemas |
| **Explanation** | understand why things are the way they are | "How trips are built from pings, and why pings arrive out of order" |

Most documentation that nobody can use mixes these: a tutorial interrupted by reference tables, a how-to that stops to explain history. The four conflicting wiki pages were each part tutorial, part how-to, part explanation, written for different readers at different times.

Onboarding works best as a tutorial with a concrete goal: set up the environment, make a small change, get it reviewed and deployed, and trace one real request through the system. Ask each new engineer to fix whatever was wrong with it as they go. They're the only readers who follow it exactly, so they're the best test it gets.

### 6. Keeping documentation alive

Nothing keeps documentation accurate by default. Some mechanisms help:

- **Same pull request.** Documentation changes in the PR that changes the behavior it describes, and reviewers look for it. A bot can help by noticing when code in an area changed and its docs didn't, and asking; an advisory nudge, not a gate.
- **Execute what can be executed.** Setup instructions as scripts run in CI; code examples compiled or run as tests; links checked automatically. Anything that runs can't drift silently.
- **Owners and review dates** on guides, and a periodic report of what hasn't been reviewed in a year.
- **One page per topic.** When there are four pages on the same subject, merge them into one and delete the others. A wrong document is worse than a missing one, because the reader has no reason to doubt it.
- **Link, don't copy.** A wiki page that needs to mention setup should link to the README, not paraphrase it.

### 7. A new kind of reader

Coding assistants and agents now read repositories too, and many tools look for context files in the repository (`AGENTS.md`, `CLAUDE.md` and similar) describing how to build, test and work in the codebase. Those files are documentation, with the same properties as a README: they're most useful when short, accurate, and made of commands that work, and they go stale the same way. They also make one old rule more important: an agent can't ask in Slack why the dedupe window is two seconds. If the reason isn't written down near the code, the agent will "fix" it as confidently as the new engineer did.

## When It's Appropriate

- **More than a handful of engineers, or any turnover.** Knowledge in people's heads scales with the number of heads, and leaves when they do.
- **Deliberately unusual code:** workarounds for hardware, vendor or regulatory behavior; performance tricks; anything someone might reasonably "fix."
- **Shared packages and internal libraries** with callers in other teams.
- **Onboarding more than two or three people a year.** A tested onboarding path pays for itself in senior engineers' time.
- **Areas where mistakes are expensive,** like billing, permissions and data deletion, where a sentence of warning can prevent an incident.
- **Repositories where AI coding agents work,** which rely entirely on what's written down.

## When It's Unnecessary or Overkill

- **Comments on code that explains itself.** Clear names and simple logic need no narration.
- **Interface docs required on every private function.** It produces boilerplate that nobody reads and nobody updates.
- **Long READMEs.** Past a page or two, move content to linked docs and keep the README as the entry point.
- **Documenting a prototype in depth.** It may not exist next month. A short README with how to run it is enough.
- **Duplicating what tools already show.** A table of every configuration option, maintained by hand next to a typed configuration schema, will diverge. Generate it, or point to the schema.

## Trade-offs

**Every document is a maintenance commitment.** Written once, it has to be kept true for as long as it exists. More documentation means more to keep accurate, and wrong documentation is actively harmful.

**Writing takes time from people who know the most.** The engineers who could write the best explanations are the ones answering questions all day. Documentation is an investment that pays off only if it's read and trusted.

**Proximity limits reach.** Docs in the repository are hard to find for people who don't work in it (support, product, other teams). The wiki reaches them and rots faster. Most teams need both, with the repository as the source for anything coupled to code.

**Enforcement produces ritual.** Required doc comments and "docs updated?" checkboxes are easy to satisfy with filler. Mechanisms that execute documentation are better than mechanisms that demand it.

**Comments can mislead.** A stale comment is trusted more than it deserves, because readers can't tell it's stale. The same applies to generated reference docs built from wrong comments.

## Alternatives

**Tests as documentation.** Well-named tests describe behavior precisely and fail when it changes: `it("treats pings within 2s from the same tracker as duplicates")`. They're excellent reference for _what_, and weak on _why_, unless the reason is written into the test.

**Mentoring and pairing.** New engineers learn fastest working alongside someone. It doesn't scale, and it doesn't leave anything behind for the next person, unless what comes up gets written down.

**Recorded walkthroughs.** A 20-minute video tour of the system is quick to make and useful once. Videos can't be searched or partially updated, and they go stale all at once.

**Asking an AI assistant about the code.** Tools that answer questions from the codebase are good at _what_ and _where_. They can only report intent that's written down somewhere; asked why the window is two seconds, they'll guess.

## How to Achieve It

**Step 1: fix the front door.** Each repository and service gets a README answering the six questions, with setup reduced to one command that CI also runs. _Signal to move on:_ new engineers get running in hours, then get stuck understanding the code.

**Step 2: write down the why in hotspots.** For the top hotspots (31.1) and anything deliberately unusual, add comments explaining why, why not, and consequences. Add interface docs to exported symbols of shared packages. Delete narration and stale comments while you're there. _Signal:_ questions shift from "how do I run it" to "how does this work overall."

**Step 3: an onboarding path.** A tutorial with a concrete goal, owned by one person, fixed by every new engineer who follows it. Add explanation docs for the two or three concepts everyone asks about. _Signal:_ docs are good now, and you can see them starting to drift.

**Step 4: keep it alive automatically.** Compile or run documented examples, check links, nudge when code changes without its docs, and report stale guides.

**Step 5: prune the wiki.** Move anything that describes code into the repository, merge duplicates, delete what's wrong, and leave the wiki for what isn't about code.

## Implementation

TypeScript, where doc comments are read by the editor on every hover, but where, unlike Go or Rust, nothing runs the examples in them by default. Three pieces: interface documentation for the dedupe function, a check that its examples still compile, and a nudge when code changes without its docs.

First, the function's contract, written for a caller who shouldn't need to read the implementation:

```ts
/**
 * Removes duplicate pings from a batch received from one or more trackers.
 *
 * Two pings from the same tracker are duplicates if their timestamps are within
 * {@link DEDUPE_WINDOW_MS} of each other. Of each group, the earliest is kept.
 * See the comment in the implementation for why the window isn't zero.
 *
 * @param pings - Pings in any order; may contain several trackers. Not mutated.
 * @returns Deduplicated pings, sorted by tracker, then timestamp.
 * @throws {InvalidPingError} If a ping has no tracker ID or a timestamp before 2015.
 *
 * @example
 * ```ts
 * const out = dedupePings([
 *   { trackerId: "T1", ts: 1_700_000_000_000, lat: 51.5, lng: -0.12 },
 *   { trackerId: "T1", ts: 1_700_000_000_900, lat: 51.5, lng: -0.12 }, // resent after reconnect
 * ]);
 * out.length; // 1
 * ```
 */
export function dedupePings(pings: readonly Ping[]): Ping[] { /* ... */ }
```

> **What goes where.** The doc comment says _what_ the function promises, including the window, by reference to the constant rather than by copying its value, so it can't become the next `// retries 3 times`. The _why_ (firmware 3.x, INC-2231) stays as the comment on the implementation, where the person about to change the window will read it. Callers need the contract; maintainers need the reason.

Second, keep examples honest. This script finds every `@example` in the exported declarations of a package and type-checks it against the package's real API, so an example that uses a renamed function or a removed field fails CI:

```ts
// tools/check-doc-examples.ts
import { Project } from "ts-morph";

const project = new Project({ tsConfigFilePath: "packages/ingest/tsconfig.json" });
const entry = project.getSourceFileOrThrow("packages/ingest/src/index.ts");
let failures = 0;

for (const [name, decls] of entry.getExportedDeclarations()) {
  for (const decl of decls) {
    const docs = "getJsDocs" in decl ? (decl as any).getJsDocs() : [];
    const examples = docs.flatMap((d: any) => d.getTags()).filter((t: any) => t.getTagName() === "example");

    examples.forEach((tag: any, i: number) => {
      const code = (tag.getCommentText() ?? "").replace(/^```\w*\n?|```$/gm, "");
      const file = project.createSourceFile(`__doc_examples__/${name}.${i}.ts`,
        `import * as api from "../packages/ingest/src/index";\nconst { ${name} } = api;\n${code}`,
        { overwrite: true });
      for (const d of file.getPreEmitDiagnostics()) {
        failures++;
        console.error(`@example ${i + 1} on ${name}: ${d.getMessageText().toString()}`);
      }
    });
  }
}
process.exit(failures ? 1 : 0);
```

> **Compiling isn't running.** This catches the most common rot: examples that call functions or pass fields that no longer exist. It doesn't check that `out.length` is really 1. Running examples as tests needs more machinery (turning the `// 1` annotations into assertions), which some teams build and most don't. The Go sibling below shows what a toolchain that runs examples by default looks like.

Third, an advisory nudge for co-changing docs. A small map says which documentation describes which code; if a pull request changes the code but not the docs, a bot comments:

```ts
// tools/doc-nudge.ts
import { execFileSync } from "node:child_process";

const DOCS_FOR: Record<string, string[]> = {
  "services/ingest/src/":  ["services/ingest/README.md", "docs/explanation/pings-to-trips.md"],
  "services/billing/src/": ["docs/explanation/mileage-billing.md"],
  "Makefile":              ["README.md"],
};

const changed = execFileSync("git", ["diff", "--name-only", "origin/main...HEAD"], { encoding: "utf8" })
  .split("\n").filter(Boolean);

const missing = Object.entries(DOCS_FOR)
  .filter(([code]) => changed.some((f) => f.startsWith(code)))
  .filter(([, docs]) => !docs.some((d) => changed.includes(d)))
  .map(([code, docs]) => `- \`${code}\` changed; do any of these need updating? ${docs.join(", ")}`);

if (missing.length) console.log(["Docs check (advisory):", ...missing].join("\n"));
```

> **Advisory on purpose.** Most code changes don't affect the documentation, so a blocking check would fail constantly and train people to add meaningless doc edits to get past it. As a question, it costs a few seconds to dismiss and occasionally catches the change that did matter. Following 29.2b, the bot should update one comment in place rather than adding a new one on every push.

## Further Reading

- John Ousterhout, _A Philosophy of Software Design_ (2nd ed., Yaknyam Press, 2021), chapters 12–16 on comments. The clearest argument for what comments are for and where to write them first.
- Daniele Procida, _Diátaxis_ (diataxis.fr). The four kinds of documentation, in detail.
- Titus Winters, Tom Manshreck and Hyrum Wright (eds.), _Software Engineering at Google_ (O'Reilly, 2020), chapter 10, "Documentation."
- Write the Docs, "Docs as Code" (writethedocs.org). Treating documentation with the same tools and review as code.
- Jeff Atwood, "Code Tells You How, Comments Tell You Why," _Coding Horror_ (2006).
- The TSDoc specification (tsdoc.org), TypeDoc, and `eslint-plugin-jsdoc`, which can require documentation on exported symbols only.
- Andrew Gerrand, "Testable Examples in Go," _The Go Blog_ (2015); the Rust book's section on documentation tests. Two toolchains where examples are tests.
- The `AGENTS.md` convention (agents.md), for repository instructions aimed at coding agents.
- Within this map: developer environment and setup scripts in **3.2**, ADRs in **2.5**, API reference docs in **7.2**, commit messages in **29.1b**, runbooks in **24.3**, and architecture documentation in **31.4b**.

A sibling in **Go** would be worth writing, though it isn't yet. Go's documentation conventions are part of the toolchain: a doc comment starts with the name it describes, `go doc` and pkg.go.dev render it without configuration, and `Example` functions in test files are compiled, run by `go test`, and checked against their `// Output:` comments. An example that stops being true fails the build. Seeing documentation that the toolchain executes by default shows how much of this article's keep-alive machinery exists only because TypeScript leaves it out.

---

The habit to take from this: whenever you write code that looks wrong but is right, or learn a reason that isn't visible in the code, write it down in the one place the next person will be looking when they need it. Usually that's right next to the line they're about to change.
