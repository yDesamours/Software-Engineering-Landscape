# Code Quality Metrics: Numbers That Point, Not Numbers That Judge

_Module 31 · Code Quality & Technical Debt · 31.1_

## The Problem

Suppose 14 engineers work on a property-management platform: leases, rent billing, deposits, maintenance requests, monthly owner reports. It's a six-year-old TypeScript monorepo of about 180,000 lines. Deliveries have been slowing for a year, and the VP of Engineering asks a reasonable question: _is the code getting worse, and should we spend next quarter cleaning it up?_

The tech lead installs SonarQube to get an answer. The first scan says:

```
Issues                 2,340   (38 critical)
Technical debt         212d
Maintainability        A
Coverage               61.2%
Duplications           4.8%
```

Nobody knows what to do with this, so the VP turns it into goals: 80% coverage, zero critical issues, duplication under 3% by the end of the quarter. The team delivers all three.

- **Coverage** reaches 80% mostly through tests on mappers and DTO factories, which are easy to call. Many of the new tests assert almost nothing (Module 21.4 covers why coverage can't tell).
- **The critical issues** are fixed, and most of them sit in `reports/legacy-export/`, a module used by three customers and last changed meaningfully in 2021. One of the fixes reorders a CSV column and breaks a customer's import.
- **Duplication** drops partly because two near-identical late-fee calculators, one for residential and one for commercial leases, get merged into one function with a `kind` flag. Three weeks later a legal change affects commercial late fees only, and the merged function acquires four more flags.

Meanwhile, `billing/leaseBilling.ts` doesn't get touched. It is 1,900 lines long. It was changed in 212 commits over the past year and appears in 9 of the last 14 incident postmortems. Its `applyProration` function has 58 independent paths through it. Every estimate for work involving proration runs two to three times over. But the file had only 40 issues, none critical, so it never made the list.

At the end of the quarter every number is green, and nothing feels different. The dashboard wasn't lying; each number measured exactly what it says it measures. The mistake was using them as targets, and as a map of where to work, when none of them includes the thing that makes bad code expensive: **how often you have to change it**.

## What It Is

**Code quality metrics** are measurable properties of source code, or of its history, used as proxies for how hard the code is to change correctly. That property is usually called **maintainability**, or _internal_ quality. It's distinct from _external_ quality, meaning the bugs, slowness and outages users see, although the two are connected, since hard-to-change code is where bugs get introduced.

The key word is _proxy_. Nobody can measure maintainability directly. Every metric measures something narrower (branches, nesting, repeated tokens, change frequency) that correlates with it under some conditions. Using metrics well is mostly a matter of knowing what each one sees and what it can't.

One neighbor is worth separating early: **delivery metrics** such as the DORA four (lead time, deployment frequency, change failure rate, time to restore) measure outcomes of the whole engineering system. Code metrics measure the code. The first tells you something is wrong; the second can help tell you where. Both come back in _Alternatives_.

## Recognizing the Problem

- A quality dashboard exists, and nobody can say which file to fix first.
- Planning meetings quote "212 days of technical debt," and nobody knows what would change the number or what it would mean if it did.
- Metric targets are met, and estimates don't improve.
- Everyone knows the scary file, and no metric the team watches ranks it first.
- Cleanup work lands in code that nobody was going to change anyway.
- Tests are written to raise coverage rather than to catch a specific failure.
- Complexity rules have been switched off with dozens of `eslint-disable` comments, because they fire on everything.
- Metrics are shown per team or per person, and people have started structuring commits around them.

## How It Works

Metrics fall into a few families. For each: what it measures, and what it misses.

### Size

Lines of code, function length, file length, parameter count. Size is the crudest metric and one of the best predictors available: larger files and functions tend to have more defects. The less comfortable finding is that many sophisticated metrics mostly measure size too. El Emam and colleagues showed in 2001 that once class size is controlled for, several popular object-oriented metrics lose much of their association with faults. So before trusting a clever metric, check whether it tells you anything that line count doesn't.

### Cyclomatic complexity

Thomas McCabe's 1976 metric counts the linearly independent paths through a function. In practice it's the number of decision points plus one: each `if`, loop, `case`, `catch`, ternary, `&&` and `||` adds one. McCabe suggested 10 as an upper bound per function.

It has a precise meaning: it's the minimum number of test cases needed to exercise every branch. It's a weak measure of how hard the function is to _read_, though, because it treats all decisions as equal, however deeply nested.

### Cognitive complexity

Cognitive complexity (G. Ann Campbell, SonarSource, 2017) was designed to fix that. It adds one for each break in linear flow, adds more the deeper that break is nested, and counts a `switch` once no matter how many cases it has. Two functions show the difference:

```ts
// Flat dispatch. Cyclomatic 6, cognitive 1.
function feeLabel(kind: FeeKind): string {
  switch (kind) {
    case "late":    return "Late fee";
    case "pet":     return "Pet fee";
    case "parking": return "Parking";
    case "utility": return "Utilities";
    case "storage": return "Storage";
    default:        return "Other";
  }
}

// Nested logic. Cyclomatic 6, cognitive 11.
function prorate(lease: Lease, month: Month) {
  if (lease.active) {                                       // +1
    for (const charge of lease.charges) {                   // +2 (nested once)
      if (charge.recurring) {                               // +3 (nested twice)
        if (starts(charge, month) && !ends(charge, month)) { // +4 (nested three times), +1 for &&
          // ...
        }
      }
    }
  }
}
```

Cyclomatic complexity rates them the same. Anyone who has reviewed both knows they aren't. Sonar's default threshold for cognitive complexity is 15 per function.

Both metrics share a limit: they're per-function. A module of forty tidy functions that call each other in a tangle scores well on both.

### Duplication

Clone detectors look for repeated sequences of tokens, either exactly the same or the same apart from renamed identifiers or small edits. They find real problems: a bug fixed in one copy and not the other.

They also find **coincidental duplication**, code that looks the same today but exists for different reasons and will change for different reasons. The late-fee merge in _The Problem_ is the classic case. Removing that kind of duplication couples two things that should stay independent. And clone detectors can't see the duplication that matters most: the same business rule implemented once in a SQL query and once in TypeScript, with no shared text at all.

### Coupling and structure

These metrics work at the level of modules rather than functions:

- **Fan-in and fan-out**: how many modules depend on this one, and how many it depends on.
- **Dependency cycles** between packages.
- **Instability** (Robert Martin's term): the share of a module's dependencies that point outward. A module many others depend on is expensive to change and should be stable.

They catch architectural problems the per-function metrics miss entirely: a "utils" package everything depends on, or two packages that each import the other.

### Composite scores

Some tools combine several metrics into one number.

The **Maintainability Index** (Oman and Hagemeister, 1992) is a regression formula over Halstead volume, cyclomatic complexity and lines of code. Visual Studio rescales it to 0–100. Its weights were fitted to a handful of 1990s C and Pascal systems, and when the score moves you can't tell which input moved it. Arie van Deursen's 2014 critique is a good summary of why to be careful with it.

**Technical debt in days**, as SonarQube shows it, is the sum of estimated fix times for every rule violation, following the SQALE method. It measures the cost of silencing the analyzer, not the cost the code imposes on the team. The **maintainability rating** is that estimate divided by an estimate of what the codebase cost to write. At the default of 30 minutes per line, 180,000 lines "cost" 11,250 days, so 212 days of debt is under 2%, which is an A. Both numbers on the dashboard were correct, and neither said anything about `leaseBilling.ts`.

Composites are useful for spotting that _something_ changed. They're poor at telling you what.

### History: the metrics most teams don't collect

Everything above is computed from a single snapshot of the code. A second family comes from version control:

- **Change frequency (churn)**: how many commits touched a file in a period.
- **Code age**: how long since a file last changed.
- **Authorship**: how many people changed a file, and how much of it the main author wrote. This shows where knowledge is concentrated in someone who might leave.
- **Change coupling**: files that change together in the same commits. If `leaseBilling.ts` and `ownerStatements.ts` change together 70% of the time and nothing in the import graph explains it, there's a hidden dependency: a shared assumption, a duplicated rule, or a boundary drawn in the wrong place.

Research has repeatedly found that history predicts defects at least as well as the code itself. Nagappan and Ball (2005) found that relative churn predicted defect density in Windows Server 2003. Moser, Pedrycz and Succi (2008) found change metrics outperformed static code attributes for defect prediction. Nagappan, Murphy and Basili (2008) found that organizational factors, such as how many people and teams touched a component, predicted failures in Windows Vista better than code metrics did. Bird and colleagues (2011) linked many minor contributors to more defects.

The intuition is simple. Complex code that never changes costs almost nothing: nobody has to understand it. Complex code that changes every week charges the team every week.

### Hotspots: complexity × change

Adam Tornhill's **hotspot** analysis combines the two families. Plot each file by how often it changes and how complex it is:

```
 complexity
      │
 high │  stable but ugly         │  HOTSPOT
      │  leave it; wrap it if    │  every change pays the
      │  you ever have to touch  │  complexity again
      │──────────────────────────┼──────────────────────────
  low │  quiet and simple        │  busy but simple
      │  ignore                  │  routes, config, flags:
      │                          │  healthy churn
      └──────────────────────────┴────────────────────────── change
                  low                        high           frequency
```

In most codebases the top-right corner is small. Change concentrates in a minority of files, and that's where complexity actually costs money. `reports/legacy-export/` sits top-left: ugly, rarely touched, and the wrong place for the quarter's effort. `leaseBilling.ts` is alone in the top right.

The analysis then narrows. Within a hotspot file, which _functions_ are complex and change often? A 1,900-line file doesn't have to be rewritten; often three functions inside it account for most of the pain.

### Trends beat levels

A single snapshot says little. "Cognitive complexity 212" means nothing without something to compare it to. Its direction over the last six months means a lot: a hotspot that's getting simpler shows the refactoring is working, and one that's getting worse shows where new debt is accumulating. Measure the same few things the same way on a schedule, and read the slope.

### Pick the metric by the question

| Question | Useful signal |
| --- | --- |
| Where should the refactoring budget go? | Hotspots, then the worst functions inside them |
| Is this function too hard to review? | Cognitive complexity, length, nesting depth |
| Are our module boundaries wrong? | Change coupling, dependency cycles |
| Is knowledge concentrated in one person? | Authorship per hotspot |
| Did the cleanup work? | Complexity trend of the targeted hotspot, and lead time for changes in that area |
| Is the codebase getting worse? | Trends in the top hotspots plus delivery metrics, not whole-codebase totals |

### How metrics get used, and how they break

The same number can play three roles:

1. **A diagnostic**: it tells you where to look, and a person decides what it means.
2. **A gate**: it blocks a change that crosses a threshold.
3. **A target**: someone is rewarded for moving it.

The first is almost always safe. The second can work when it's narrow and applies only to new or changed code: "no new function above cognitive complexity 15" is enforceable, while "the codebase must be under X" isn't. Module 31.2a covers gates and ratchets properly.

The third is where Goodhart's law applies: once a measure becomes a target, people optimize the measure rather than the thing it stood for. The coverage tests on DTO mappers and the late-fee merge are both examples. Neither was dishonest; people did what the number rewarded. The worst version is **per-person metrics**. People start splitting or batching commits to look productive, avoid touching risky code, and stop trusting the numbers entirely. Martin Fowler's short "Cannot Measure Productivity" makes the case.

## When It's Appropriate

- **The codebase outgrew shared memory.** Around 50,000 lines and more than one team, nobody knows every file. Metrics recover a map everyone used to carry in their head.
- **You have a limited refactoring budget.** Say two engineers for six weeks. A hotspot list tells you which 1% of the code will return the most for that time.
- **You need to justify debt work to non-engineers.** "This file was in 9 of 14 postmortems and changed 212 times last year" is an argument a VP can weigh. "It's messy" isn't.
- **Before splitting a monolith or redrawing modules** (Module 2.1). Change coupling shows which parts actually move together, as opposed to which ones the diagram says belong together.
- **To check a cleanup worked.** Track the targeted hotspot's complexity and the lead time of changes touching it.
- **Onboarding.** Knowing which files are hotspots, and who knows them, tells a new engineer where to be careful and whom to ask.
- **Review-time prompts.** A complexity warning on a new function can start a useful conversation, as long as it's advisory.

## When It's Unnecessary or Overkill

- **A small codebase where everyone knows everything.** Four engineers on 20,000 lines already know where the pain is. Ask them.
- **Prototypes and throwaway code.** If it gets deleted in two months, its maintainability doesn't matter.
- **Codebase-wide numeric targets.** "80% coverage" or "under 3% duplication" everywhere invites gaming in the easy places and ignores the costly ones.
- **Comparing teams or individuals.** Codebases differ too much in age, domain and history for the numbers to be comparable, and the comparison damages the data.
- **Dashboards with forty metrics.** If nobody makes a decision from a metric, stop collecting it.
- **Generated, vendored or migration code.** Exclude it. Otherwise it dominates every ranking and teaches the team to ignore the output.

## Trade-offs

**False precision.** "212d" looks like a measurement. It's a sum of per-rule estimates, and treating it as the cost of the codebase leads to wrong decisions. Any composite number carries this risk.

**Distortion.** Every metric used as a target changes the behavior it was meant to observe. Even as diagnostics, metrics shift attention toward whatever is easy to measure. Misleading names, wrong abstractions and a domain model that no longer matches the business don't show up in any number, and they are often the most expensive problems in a codebase.

**Noise and fatigue.** A complexity rule that fires on 600 existing functions gets disabled, and then it doesn't fire on the new ones either.

**Tooling cost.** A SonarQube server is another service with a database, upgrades and rule configuration to maintain. Scripts are cheaper but need an owner.

**History metrics depend on clean history.**
- A file that was moved or renamed loses its history unless the tool follows renames.
- A repository migrated from another version control system may start its history on the migration date.
- A bulk formatting commit touches every file once and inflates every count.
- Merge strategy changes the unit: with squash merges one pull request counts as one change; with merge commits each small commit counts. Compare numbers only within one repository's convention.

**Churn has innocent causes.** A file under active feature development changes often because the product is growing. High churn alone isn't a problem. It becomes one only combined with complexity, or when the changes are repeated fixes to the same area.

**Correlation is not a diagnosis.** A hotspot tells you where cost concentrates. It doesn't say what's wrong or whether a rewrite would help. That still takes someone reading the code.

## Alternatives

**Ask the team.** A short survey ("where do you slow down? which areas do you avoid?") is cheap and catches things metrics can't, such as a confusing domain model or a missing test harness. It's biased toward recent and loud pain, and toward the areas the most vocal people work in. The strongest approach uses both: metrics to check the survey, and the survey to explain the metrics.

**Measure outcomes instead.** Delivery metrics (lead time, change failure rate) and incident attribution measure the effect of bad code rather than its shape. They're harder to game and tell you _that_ something is wrong. Broken down by area of the code, they can tell you roughly _where_, too. They say nothing about _why_.

**Mine defect data.** Linking bug-fix commits to the issues they fix gives defect counts per file. That's closer to what you care about than complexity. It requires disciplined commit messages or issue links, and it only sees bugs that were reported.

**Rely on code review.** Review is where quality is actually enforced, one change at a time. It's good at local judgment and blind to trends: no reviewer sees that a file has been changed 212 times.

## How to Achieve It

**Step 1: one afternoon, no tools.** Count commits per file over the last 12 months from `git log`, and join the counts with each file's line count. Look at the top 20 together as a team and ask one question: _does this match where you feel pain?_ Where it does, you have evidence. Where it doesn't, find out why. Maybe a generated file needs excluding, or maybe the survey was wrong.

**Step 2: add a real complexity measure.** Replace line count with function-level cognitive or cyclomatic complexity, from ESLint's `complexity` rule, `eslint-plugin-sonarjs`, `gocognit` or `lizard`. Rank hotspots, then drill into the worst functions inside the top few files. _Move on when_ the list stops surprising anyone and you need to decide what to do about the top entries.

**Step 3: add change coupling and authorship** when the question becomes structural (should these modules be split or merged?) or organizational (what happens if the person who knows billing leaves?).

**Step 4: track trends.** Record the complexity of the top 10 hotspots monthly, and connect them to the debt register in 31.3a so that each hotspot has an owner and a decision (fix, contain, or accept).

**Step 5: only now, gates.** Add thresholds that apply to new and changed code, tuned to where your existing code actually sits (31.2a). Never make the absolute totals a goal.

## Implementation

TypeScript, because the TypeScript compiler API makes the complexity half of the analysis short and readable. This is a first-pass hotspot report, not a replacement for a proper tool.

First, change frequency from version control:

```ts
import { execFileSync } from "node:child_process";
import { readFileSync } from "node:fs";

export function changeFrequency(since: string, maxFilesPerCommit = 40): Map<string, number> {
  const ignored = new Set(
    readFileSync(".git-blame-ignore-revs", "utf8")
      .split("\n").map((l) => l.trim()).filter((l) => /^[0-9a-f]{40}$/.test(l)),
  );
  const log = execFileSync(
    "git", ["log", `--since=${since}`, "--no-merges", "--name-only", "--format=%x00%H"],
    { encoding: "utf8", maxBuffer: 512 * 1024 * 1024 },
  );

  const counts = new Map<string, number>();
  for (const entry of log.split("\0").slice(1)) {
    const [sha, ...files] = entry.split("\n").filter(Boolean);
    if (ignored.has(sha) || files.length > maxFilesPerCommit) continue;
    for (const f of files) counts.set(f, (counts.get(f) ?? 0) + 1);
  }
  return counts;
}
```

> **Two history traps.** `git log` doesn't read `.git-blame-ignore-revs`; only `git blame` does. Reusing the list here keeps bulk reformatting commits out of the counts, and the per-commit file limit catches large mechanical changes nobody listed. Second, `--name-only` reports each commit under the path at that time. When a file is renamed, its earlier history stays attached to a path that no longer exists, and the file looks newer and quieter than it is. `--name-status` with rename detection (`-M`) reports renames, if you need to join the two histories.

Second, cyclomatic complexity per function, by walking the syntax tree and counting decision points:

```ts
import ts from "typescript";

const BRANCHES = new Set([
  ts.SyntaxKind.IfStatement, ts.SyntaxKind.ConditionalExpression, ts.SyntaxKind.CaseClause,
  ts.SyntaxKind.ForStatement, ts.SyntaxKind.ForInStatement, ts.SyntaxKind.ForOfStatement,
  ts.SyntaxKind.WhileStatement, ts.SyntaxKind.DoStatement, ts.SyntaxKind.CatchClause,
]);
const SHORT_CIRCUIT = new Set([
  ts.SyntaxKind.AmpersandAmpersandToken, ts.SyntaxKind.BarBarToken, ts.SyntaxKind.QuestionQuestionToken,
]);

const isDecision = (n: ts.Node) =>
  BRANCHES.has(n.kind) || (ts.isBinaryExpression(n) && SHORT_CIRCUIT.has(n.operatorToken.kind));

export type FnComplexity = { name: string; complexity: number };

export function functionComplexities(path: string, source: string): FnComplexity[] {
  const file = ts.createSourceFile(path, source, ts.ScriptTarget.Latest, true);
  const results: FnComplexity[] = [];

  const measure = (body: ts.Node): number => {
    let count = 1;
    const walk = (n: ts.Node) => {
      if (n !== body && ts.isFunctionLike(n)) return; // nested functions are measured on their own
      if (isDecision(n)) count++;
      ts.forEachChild(n, walk);
    };
    walk(body);
    return count;
  };

  const visit = (n: ts.Node) => {
    if (ts.isFunctionLike(n) && "body" in n && n.body) {
      const name = n.name?.getText(file)
        ?? (ts.isVariableDeclaration(n.parent) ? n.parent.name.getText(file) : "<anonymous>");
      results.push({ name, complexity: measure(n.body) });
    }
    ts.forEachChild(n, visit);
  };
  visit(file);
  return results;
}
```

> **Numbers from different tools don't compare.** Tools disagree on details: whether `??`, optional chaining or default parameters count; whether a nested callback's complexity belongs to its parent. This version counts `??` and measures nested functions separately. Neither choice is wrong, but a threshold only means something relative to the tool that produced it. Pick one tool and keep it.

Third, combine them:

```ts
import { existsSync, readFileSync } from "node:fs";

const percentile = (xs: number[]) => (x: number) => xs.filter((v) => v <= x).length / xs.length;

const measured = [...changeFrequency("12 months ago")]
  .filter(([p]) => /\.tsx?$/.test(p) && !p.endsWith(".d.ts") && existsSync(p))
  .filter(([p]) => !/(^|\/)(generated|vendor|migrations)\//.test(p))
  .map(([path, changes]) => {
    const fns = functionComplexities(path, readFileSync(path, "utf8"));
    const total = fns.reduce((sum, f) => sum + f.complexity, 0);
    const worst = fns.reduce((a, b) => (b.complexity > a.complexity ? b : a), { name: "-", complexity: 0 });
    return { path, changes, total, worst };
  });

const changeRank = percentile(measured.map((m) => m.changes));
const complexityRank = percentile(measured.map((m) => m.total));

const hotspots = measured
  .map((m) => ({ ...m, score: changeRank(m.changes) * complexityRank(m.total) }))
  .sort((a, b) => b.score - a.score)
  .slice(0, 20);

console.table(hotspots.map((h) => ({
  file: h.path, changes: h.changes, complexity: h.total, worst: `${h.worst.name} (${h.worst.complexity})`,
})));
```

> **Why percentiles, not a raw product.** Multiplying raw changes by raw complexity lets one extreme value dominate: a 5,000-line file changed twice can outrank a genuine hotspot. Ranking each dimension first means a file has to be high on _both_ to reach the top, which is the point of the quadrant.

On the property-management repository, the top of the report looks like this:

```
file                          changes  complexity  worst
billing/leaseBilling.ts           212       1,140  applyProration (58)
billing/deposits.ts               164         610  reconcileDeposit (41)
api/routes/leases.ts              301         180  buildLeaseQuery (12)
maintenance/workOrders.ts          97         540  assignVendor (33)
```

This is where judgment takes over. `api/routes/leases.ts` ranks third, but its worst function scores 12. It's busy but simple, bottom-right in the quadrant, and not worth refactoring. `reports/legacy-export/` isn't in the top 20 at all. For the first file, `git log -L :applyProration:billing/leaseBilling.ts` shows the history of that one function: who changed it, how often, and whether the changes are features or repeated fixes. That's the conversation to have before deciding anything (31.3b covers what to do next).

## Further Reading

- Adam Tornhill, _Your Code as a Crime Scene_ (2nd ed., Pragmatic Bookshelf, 2024) and _Software Design X-Rays_ (Pragmatic Bookshelf, 2018). The source of hotspot and change-coupling analysis. His open-source `code-maat` tool computes most history metrics from a git log.
- Thomas J. McCabe, "A Complexity Measure," _IEEE Transactions on Software Engineering_, 1976.
- G. Ann Campbell, "Cognitive Complexity: A New Way of Measuring Understandability," SonarSource white paper. Includes the full counting rules.
- Nachiappan Nagappan and Thomas Ball, "Use of Relative Code Churn Measures to Predict System Defect Density," ICSE 2005.
- Raimund Moser, Witold Pedrycz and Giancarlo Succi, "A Comparative Analysis of the Efficiency of Change Metrics and Static Code Attributes for Defect Prediction," ICSE 2008.
- Nachiappan Nagappan, Brendan Murphy and Victor Basili, "The Influence of Organizational Structure on Software Quality," ICSE 2008.
- Christian Bird et al., "Don't Touch My Code! Examining the Effects of Ownership on Software Quality," ESEC/FSE 2011.
- Khaled El Emam et al., "The Confounding Effect of Class Size on the Validity of Object-Oriented Metrics," _IEEE Transactions on Software Engineering_, 2001.
- Arie van Deursen, "Think Twice Before Using the Maintainability Index" (blog post, 2014).
- Martin Fowler, "Cannot Measure Productivity" (bliki). Why per-person numbers fail.
- Tool documentation: ESLint's `complexity` rule, `eslint-plugin-sonarjs` (`cognitive-complexity`), `gocyclo` and `gocognit` for Go, and `lizard` for many languages at once.

A sibling in **Java** would be worth writing, though it isn't yet. Class-heavy languages have their own metric family, the Chidamber–Kemerer suite (coupling between objects, lack of cohesion, depth of inheritance), which barely applies to function-oriented TypeScript. Java also makes package-level coupling measurable and enforceable, with instability metrics from JDepend and dependency rules written as ArchUnit tests. That's where structural metrics stop being a report and become a build failure, which TypeScript tooling only partly reproduces.

---

The habit to take from this: when someone shows you a quality number, ask two questions before anything else. _How often does the code behind this number change?_ And _what decision would we make differently if it moved?_ If the answer to the second is "none," the number is decoration.
