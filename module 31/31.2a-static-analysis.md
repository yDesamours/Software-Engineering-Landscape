# Static Analysis: Tools People Actually Listen To

_Module 31 · Code Quality & Technical Debt · 31.2a_

## The Problem

Suppose 30 engineers build a platform for medical clinics: appointment booking, reminders, and secure messaging between patients and staff. It's TypeScript throughout, with a Node API and a React front end. The company runs ESLint on every pull request and bought a commercial security scanner last year. In one year, four things go wrong anyway.

**Audit entries disappear.** A handler writes to the audit log inside a `try` block without `await`:

```ts
try {
  auditLog.write({ actor, action: "record.viewed", recordId }); // returns a Promise
  return await records.get(recordId);
} catch (err) { ... }
```

When the audit database is slow and the write fails, the rejection isn't caught by that `catch`, because nothing waited for it. For three weeks, some views of patient records go unrecorded, which is a compliance problem for a healthcare product. ESLint was running the whole time. The rule that catches this, `@typescript-eslint/no-floating-promises`, needs type information to know that `write` returns a promise, and type-aware linting had been left off two years earlier because it was "too slow."

**The scanner found it, and nobody saw.** A reporting endpoint builds SQL with a template string: `` ORDER BY ${req.query.sort} ``. A penetration tester finds the injection. The security scanner had flagged it eleven months earlier, as one of 1,400 open findings in a dashboard nobody opens.

**The gate that lasted a month.** After the pen test, the security lead makes the scanner block pull requests. Every PR that touches an old file now fails on findings the author didn't write. Within a month there are 300 new `// nosemgrep` comments, none with a reason, and the gate is switched off.

**A bug no tool knows about.** Every query on patient data must filter by `clinic_id`. It's the platform's multi-tenancy rule (Module 5). A new messaging query forgets it, and for two hours staff at one clinic can see message previews from another. Reviewers have been writing "remember to scope by clinic" on pull requests for years. No off-the-shelf rule knows the convention.

The company had the tools. What it lacked was the right _depth_ of analysis for its bugs, a way to show findings where people would act on them, a way to adopt strict checks without blocking on old code, and a way to turn its own recurring mistakes into rules.

## What It Is

**Static analysis** means examining source code without running it, to find defects, security vulnerabilities, or violations of a team's conventions. The term covers a wide range, from a linter that spots `==` to tools that trace a value from an HTTP request through a dozen functions into a database call. Security-focused static analysis is usually sold as **SAST** (static application security testing), but it's the same technique pointed at a different class of bugs.

Its counterpart is **dynamic analysis**: tests, fuzzing, runtime sanitizers, and scanning a running application (DAST). Dynamic analysis observes some executions exactly. Static analysis reasons about all executions approximately. Neither replaces the other.

Two neighbors are covered elsewhere. Module 3.2 covers formatting, editor and hook setup, and the basic idea of a lint ratchet; this article assumes those and goes deeper. Scanning the _dependencies_ you import for known vulnerabilities is a different technique with different problems, and it's 31.2b.

## Recognizing the Problem

- Nobody on the team can say which lint rules are on, or why.
- A scanner dashboard has hundreds or thousands of open findings and no owner.
- Suppression comments (`eslint-disable`, `nosemgrep`, `@SuppressWarnings`) keep growing, mostly without reasons.
- Postmortems describe bugs a tool could have caught: a missing `await`, unescaped input, an unhandled `switch` case.
- Type-aware or deep rules are off because they were slow once.
- Security findings reach engineers as a report from another team, weeks after the code merged.
- Pull requests fail on findings in lines their authors didn't write.
- The same review comment appears again and again.

## How It Works

### 1. What each depth of analysis can see

Analyzers differ mainly in how much of the program they model. Each step down the list catches more and costs more.

**Syntax patterns.** The analyzer parses one file into a syntax tree and matches shapes: a call to `eval`, an unused variable, an empty `catch`. It's fast and precise about structure, and it knows nothing about types or values. To a syntactic rule, `auditLog.write(...)` is just a call; it can't know a promise comes back.

**Type-aware rules.** The analyzer asks the compiler for type information: this expression is a `Promise`, this value is `any`, this `switch` doesn't cover every member of a union. This catches whole bug classes the language itself lets through, like floating promises. The cost is that the compiler must build a model of the whole project first, which in a large repository takes seconds to minutes.

**Data flow and taint.** The analyzer tracks how values move through assignments and calls. **Taint analysis** is the security application: mark where untrusted data enters (_sources_), where it becomes dangerous (_sinks_), and what makes it safe (_sanitizers_), then report any path from source to sink without a sanitizer in between:

```
req.query.sort ──► const sort = ... ──► buildReport(sort) ──► db.query(`... ORDER BY ${sort}`)
   SOURCE                                   (other file)              SINK
                  no sanitizer on this path  ═══►  finding
```

Tracking within one function is cheap. Following values across functions and files is expensive and is what separates serious SAST tools (CodeQL, Semgrep's cross-file mode, Sonar, Snyk Code, and others) from pattern matchers.

**Proof-oriented analysis.** Tools based on abstract interpretation or formal methods can show that a bug class is _absent_, such as null dereferences or buffer overflows. They're common in safety-critical embedded code and rare in web applications, where the cost of setting them up rarely pays off.

### 2. Every analyzer is wrong sometimes, on purpose

A general result from computability theory (Rice's theorem) says that no program can decide an interesting property of every other program's behavior. So every analyzer approximates, and it has to choose which way to be wrong:

- A **false positive** is a finding that isn't a real problem.
- A **false negative** is a real problem the tool doesn't report.

A **sound** analyzer reports everything that _might_ be a problem. It misses nothing in its class and produces many false positives. Most practical tools lean the other way. They skip paths they can't reason about confidently and accept false negatives to keep the noise low. Researchers call this "soundiness." In practice it means a clean scan is evidence, not proof: the SQL injection above would slip past any tool that loses track of the value when it passes through a helper function it doesn't model.

### 3. What counts as a false positive is decided by the reader

Google's static analysis team (Sadowski et al., 2018) described a definition that changes how to think about noise. An **effective false positive** is any finding a developer doesn't act on, whether or not it's technically correct. A correct warning about unreachable code in a test helper is, for practical purposes, a false positive. Google aimed to keep the effective false-positive rate for any check under about 10%, and removed checks that couldn't meet it.

The reason is trust. Developers don't evaluate each finding on its merits; they learn how much a tool's findings are worth in general. A tool that's usually right gets read. A tool that's usually irrelevant gets ignored, including the findings that matter. The 1,400-finding dashboard wasn't a data problem. It was a tool nobody believed any more.

### 4. Where findings appear decides whether anyone acts

The same finding gets very different treatment depending on when and where it shows up:

| Where | Acted on? |
| --- | --- |
| In the editor, while typing | Usually. The author is in context, and fixing costs seconds. |
| On the changed lines of a pull request | Usually. The author owns the code and is waiting for review anyway. |
| As a CI failure | Often, if the failure is clearly about the change. |
| In a dashboard or a report | Rarely. No one owns it, and the author has moved on. |

Both Google's and Facebook's published experience converge on the same point: surface findings during code review, on the diff, attributed to the change. Dashboards are useful for tracking a burn-down of old findings, not for delivering new ones.

### 5. Adopting strict checks on existing code

Turning on a strict analyzer in a mature codebase produces hundreds of findings on day one. There are three ways to avoid blocking everyone on old code.

**Report only on changed lines.** The analyzer runs on everything, but only findings on lines the PR changed are shown. This is simple and many tools support it. It misses findings created by a change but reported elsewhere: a new source feeding an old sink produces a taint finding on the old line, which the filter hides.

**A baseline of known findings.** Record every existing finding in a committed file, and fail only on findings not in it. The hard part is identifying a finding across changes. A line number is useless, since inserting a line above shifts every finding below it. Practical tools fingerprint a finding by its rule, its file, and the normalized text of the code involved, so it survives unrelated edits. The baseline may shrink but never grow: when someone fixes an old finding, the entry goes, and it can't be added back.

**A gate on new code.** Some platforms (SonarQube calls this "Clean as You Code") evaluate the quality gate only on code added or changed in a period, while tracking totals separately.

All three share the property that made 3.2's ratchet work: existing debt stays visible without blocking anyone, and new debt can't slip in. Old findings still need a plan. Rank them by risk, fix high-severity ones in the hotspots from 31.1 first, and accept that low-severity findings in code nobody changes may stay forever.

### 6. Suppressions are decisions, so record them

Some findings are wrong for a specific case, and suppressing them is correct. What went wrong at the clinic platform was suppression without reasons. Make every suppression name the rule and say why:

```ts
// eslint-disable-next-line @typescript-eslint/no-floating-promises -- fire-and-forget metrics; failures are logged inside send()
metrics.send(event);
```

Enforce that mechanically (ESLint can require descriptions on disable comments and report unused ones), review suppressions like code, and track their count over time. A rising count means either the rule is wrong or people are routing around it; either way, somebody should look.

### 7. Choosing rules

Start from a tool's recommended set rather than enabling everything. Then use two sources to add rules:

- **Postmortems.** For every incident, ask whether the bug belongs to a class a tool could detect. The floating promise is a rule that already exists; turning it on is the fix.
- **Repeated review comments.** A comment that appears on every third PR is a rule nobody has written yet.

And one source to remove them: for each rule, watch how often its findings get fixed versus suppressed. A rule that's mostly suppressed is costing attention and should be tuned or dropped.

### 8. Custom rules: encoding what only your team knows

The tenancy bug is the kind of problem that off-the-shelf rules can't catch, because the rule is yours. Three levels of tooling can express it:

- **Linter plugins** (ESLint, and equivalents in most languages). You walk the syntax tree yourself, with access to type information if needed. Best for rules that live next to other lint rules and run in the editor.
- **Pattern-matching tools** like Semgrep, where a rule is written as a code-shaped pattern with placeholders, and matches code of that shape. The lowest effort for many rules:

  ```yaml
  rules:
    - id: raw-sql-template
      languages: [typescript]
      severity: ERROR
      message: Build SQL with parameters, not template strings.
      pattern: db.query(`...${$X}...`)
  ```

- **Query languages over a code database**, like CodeQL, which compiles the program into a relational model you query. It's the most powerful for interprocedural data flow, and the hardest to learn.

Custom rules are code. They have bugs, need tests, and need updating when the codebase's patterns change.

## When It's Appropriate

- **Bug classes the language allows but your team shouldn't write.** Floating promises in TypeScript, unchecked errors in Go, ignored return values in C. Type-aware rules close those gaps for almost no ongoing effort.
- **Code that handles untrusted input and reaches a database, a shell, or HTML output.** Taint analysis earns its cost where injection is plausible, which for a web platform with patient data is most of the API.
- **A codebase with more contributors than any reviewer can track.** Around 15–20 engineers, the conventions stop spreading by word of mouth, and rules become the way they're kept.
- **After an incident with a mechanical cause.** Adding the rule is often the cheapest durable fix a postmortem can produce.
- **Recurring review comments.** Automating them frees reviewers for design and logic.
- **Compliance requirements.** Frameworks such as SOC 2, PCI DSS and HIPAA-oriented audits often expect evidence of security scanning. That's a legitimate reason to run a tool, as long as it doesn't become the only reason: a scanner that exists for the auditor and not the engineers is how the 1,400-finding dashboard happens.

## When It's Unnecessary or Overkill

- **Enabling every available rule.** Most rules in large rule sets don't match your risks. Each one costs attention.
- **An enterprise SAST platform for a three-person team.** A linter with type-aware rules and a pattern-matching tool on PRs covers most of the value for a fraction of the cost and setup.
- **Blocking on legacy findings.** It fails, reliably and quickly, as the clinic platform's gate showed.
- **Writing a CodeQL query for something a ten-line lint rule catches.** Match the tool to the depth the rule actually needs.
- **A rule for something a type can enforce.** As 3.2 put it, a type can't be suppressed with a comment. The _Alternatives_ section has an example.
- **Proof-oriented tools for ordinary application code.** Unless the domain is safety-critical, the setup cost rarely pays back.

## Trade-offs

**Time.** Type-aware and interprocedural analysis is slow on large codebases. It adds minutes to CI and lag to editors, which is exactly why teams switch it off. Caching, analyzing only changed files on PRs, and moving the deepest scans to a nightly run all help, and all mean some findings arrive later.

**False confidence.** A clean scan means the tool didn't find anything it looks for, in paths it could follow. Teams that treat "SAST passed" as "secure" stop looking for the bugs tools can't see: broken authorization logic, business-rule flaws, anything that depends on what the code is _supposed_ to do.

**Noise and trust.** Every false positive spends trust, and trust is slow to rebuild. One noisy rule can make people ignore a whole tool.

**Upgrades change results.** A new analyzer version adds rules and changes how it matches. A PR that upgrades the tool can surface hundreds of findings, or silently change fingerprints and invalidate the baseline. Pin analyzer versions and upgrade deliberately, in their own PRs.

**Maintenance.** Custom rules, baselines, suppression policies and rule tuning all need an owner. Without one, the configuration decays into the state of the clinic platform's ESLint: on, and unexamined.

**Cost.** Commercial SAST is priced per developer or per line of code, and some tools lock rules and results into their platform.

## Alternatives

**Make the bug impossible with types.** For the tenancy rule, a type-level design can do what a lint rule only approximates. If tenant-scoped repositories can only be obtained through a function that takes a `ClinicId`, a query without one doesn't compile, and there's no comment to suppress it with. Branded types (a `ClinicId` that isn't interchangeable with a plain string) and exhaustive unions work the same way. This requires designing the API for it, which is harder to retrofit than a rule.

**Enforce it at runtime or in the platform.** Postgres row-level security (Modules 4.3 and 5.2) enforces tenant scoping in the database itself, whatever the application code does. It's stronger than any static rule, and it costs query-planning complexity and a new class of configuration mistakes.

**Tests, fuzzing and dynamic scanning.** These find bugs that actually happen on the paths they exercise, with no false positives in the static sense. They can't cover paths nobody thought to exercise, which is where static analysis helps.

**Review checklists.** Cheap and flexible, and they catch what no tool models. Humans skip checklist items under time pressure, which is exactly when mistakes happen.

**AI-assisted review.** Language-model reviewers catch some issues that rules can't express. Their findings vary between runs and are hard to baseline, so they work best as advisory comments rather than gates (Module 29 covers this).

## How to Achieve It

**Level 0: one linter, trusted.** Recommended rules only, every rule either blocking or removed, suppressions require a reason. Findings shown in the editor and on the PR's changed lines. _Signal to move on:_ incidents or review comments involve bug classes the current rules can't see.

**Level 1: type-aware rules** for the gaps your language leaves: floating promises, unsafe `any`, non-exhaustive switches. Add caching and scope PR runs to changed files if time grows. _Signal:_ the codebase handles untrusted input and nobody knows where it flows.

**Level 2: taint analysis on PRs, with a baseline.** Findings appear as review annotations on the diff. The dashboard exists only to track the burn-down of old findings, ranked by risk and by hotspot. _Signal:_ the same team-specific mistake keeps appearing.

**Level 3: custom rules** from postmortems and repeated review comments, each with tests. For the most important ones, ask whether a type or a platform guarantee would be better. _Signal:_ nobody knows which rules still earn their keep.

**Level 4: measure the rules.** Track fix and suppress rates per rule, prune the noisy ones, and move the slowest deep analysis to a nightly run that files findings to the owning team.

## Implementation

TypeScript, because its type system leaves a well-known gap (promises nobody awaits) that type-aware analysis closes, and because ESLint's plugin model makes custom rules short. Three pieces: the configuration that would have caught the audit bug, a custom rule for the tenancy convention, and a baseline filter showing what "only new findings" means under the hood.

The configuration turns on typed linting and requires reasons for suppressions:

```ts
// eslint.config.mjs
import tseslint from "typescript-eslint";
import comments from "@eslint-community/eslint-plugin-eslint-comments/configs";
import clinic from "./tools/eslint-plugin-clinic/index.js";

export default tseslint.config(
  ...tseslint.configs.recommendedTypeChecked,
  comments.recommended,
  {
    languageOptions: { parserOptions: { projectService: true } }, // gives rules access to types
    linterOptions: { reportUnusedDisableDirectives: "error" },
    plugins: { clinic },
    rules: {
      "@typescript-eslint/no-floating-promises": "error",
      "@typescript-eslint/switch-exhaustiveness-check": "error",
      "@eslint-community/eslint-comments/require-description": "error",
      "clinic/tenant-scoped-query": "error",
    },
  },
);
```

The custom rule assumes queries use a Kysely-style builder, like `db.selectFrom("messages").where("clinic_id", "=", clinicId)`. It flags any query on a tenant-scoped table whose call chain has no `where` on `clinic_id`:

```ts
// tools/eslint-plugin-clinic/tenant-scoped-query.ts
import type { Rule } from "eslint";
import type { CallExpression, Node } from "estree";

const TENANT_TABLES = new Set(["patients", "appointments", "messages", "records"]);

const methodName = (call: CallExpression) =>
  call.callee.type === "MemberExpression" && call.callee.property.type === "Identifier"
    ? call.callee.property.name : undefined;

const isLiteral = (n: Node | undefined, value: string) => n?.type === "Literal" && n.value === value;

export const tenantScopedQuery: Rule.RuleModule = {
  meta: { type: "problem", messages: { unscoped: "Query on '{{table}}' has no where('clinic_id', ...)." } },
  create(context) {
    return {
      CallExpression(call) {
        if (methodName(call) !== "selectFrom") return;
        const table = call.arguments[0];
        if (table?.type !== "Literal" || !TENANT_TABLES.has(String(table.value))) return;

        // Walk up the chain: db.selectFrom(...).where(...).select(...).execute()
        let node: Node & Rule.NodeParentExtension = call;
        while (node.parent?.type === "MemberExpression" && node.parent.parent?.type === "CallExpression") {
          const next = node.parent.parent as CallExpression & Rule.NodeParentExtension;
          if (methodName(next) === "where" && isLiteral(next.arguments[0], "clinic_id")) return;
          node = next;
        }
        context.report({ node: call, messageId: "unscoped", data: { table: String(table.value) } });
      },
    };
  },
};
```

> **Both kinds of error, in twenty lines.** If someone writes a helper, `scoped(db.selectFrom("messages"), clinicId)`, that adds the `where` inside another function, the rule can't see it and reports a false positive; the team will either adapt the rule or suppress it, with a reason. If someone writes `.where("clinic_id", "=", otherClinicId)`, the rule is satisfied and the bug ships: a false negative. The rule checks the _shape_ of the convention, not its meaning. That's usually worth having, and it's why the stronger fixes in _Alternatives_ exist.

Finally, a baseline filter. Most analyzers can export results in SARIF, a standard JSON format for static analysis results (ESLint through a formatter, Semgrep and CodeQL natively). This script compares a SARIF file against a committed baseline and fails only on new findings:

```ts
// tools/baseline.ts
import { createHash } from "node:crypto";
import { readFileSync, writeFileSync } from "node:fs";

type Finding = { ruleId: string; path: string; line: number; message: string };

function fingerprints(findings: Finding[]): Map<string, Finding> {
  const byKey = new Map<string, Finding>();
  const seen = new Map<string, number>();
  for (const f of findings) {
    const lines = readFileSync(f.path, "utf8").split("\n");
    const code = (lines[f.line - 1] ?? "").replace(/\s+/g, " ").trim();   // what, not where
    const base = `${f.ruleId}|${f.path}|${code}`;
    const n = (seen.get(base) ?? 0) + 1;                                   // same line text twice in a file
    seen.set(base, n);
    byKey.set(createHash("sha256").update(`${base}|${n}`).digest("hex").slice(0, 16), f);
  }
  return byKey;
}

export function check(current: Finding[], baselinePath: string, update: boolean): number {
  const baseline = new Set<string>(JSON.parse(readFileSync(baselinePath, "utf8")));
  const now = fingerprints(current);
  const added = [...now].filter(([key]) => !baseline.has(key));

  for (const [, f] of added) console.error(`${f.path}:${f.line}  ${f.ruleId}  ${f.message}`);
  if (update) {
    // Keep only baseline entries still present: fixed findings leave and can't come back.
    const kept = [...baseline].filter((key) => now.has(key)).sort();
    writeFileSync(baselinePath, JSON.stringify(kept, null, 2) + "\n");
  }
  return added.length === 0 ? 0 : 1;
}
```

> **Why the fingerprint uses the code, not the line number.** Adding an import at the top of a file shifts every line below it; a baseline keyed by line number would report every old finding in that file as new, which is how blocking-on-legacy failures start. Keying on the normalized code text survives that. It doesn't survive edits to the flagged line itself, which is usually correct: if you changed the line, the finding is yours now. The occurrence counter handles the same line text appearing twice in one file.
>
> **Keeping the baseline honest.** `--update` only removes entries. To make sure nobody regenerates the baseline from scratch to hide new findings, CI can check that the committed baseline has no entries that weren't in `main`'s version. Recent ESLint versions have bulk suppressions built in, and Semgrep, SonarQube and CodeQL have their own baseline or new-code modes; use those where they exist. This script shows what they do.

A sibling in **Java** would be worth writing, though it isn't yet. Error Prone runs checks inside the Java compiler, so a finding is a compile error rather than a separate CI step, which is the strongest place analysis can sit. NullAway, built on it, makes a clear trade: developers annotate what may be null, and in exchange the checker catches null dereferences quickly, with few false positives, while accepting some unsound gaps. Seeing analysis built into compilation shows a different answer to "where should findings appear" than anything TypeScript's separate linter can.

---

The habit to take from this: when a bug escapes, ask whether its _class_ could be detected mechanically. If it could, write the rule, and make its findings appear on the pull request that introduces the next one. If the rule would be noisy or easy to satisfy wrongly, ask the harder question: could a type or the platform make the bug impossible instead?
