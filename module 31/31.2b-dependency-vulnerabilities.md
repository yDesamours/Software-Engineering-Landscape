# Dependency Vulnerabilities: From 412 Alerts to the Two That Matter

_Module 31 · Code Quality & Technical Debt · 31.2b_

## The Problem

Suppose 20 engineers build an applicant tracking system: companies post jobs, candidates apply and upload résumés, and recruiters move candidates through interview stages. There are nine TypeScript services and a React front end, each in its own repository, and Dependabot is enabled on all of them.

Dependabot reports 412 open alerts, 38 of them marked critical. Nobody reads them. The first few the team investigated turned out to be a regular-expression denial of service in a glob library used only by the build, a flaw in a test runner's file watcher, and a vulnerability in a CLI tool used by one script nobody runs any more. After enough of those, the alerts became background.

Over one year:

**The real one was in the pile.** The résumé service extracts text from uploaded documents. Four levels down its dependency tree sits an XML parser with a published flaw: a crafted document makes it resolve external entities, which lets an attacker read files from the server. Candidates upload documents, so the attacker-controlled input is the service's main job. The alert had been open for five months, sorted somewhere between the glob library and the test runner.

**The fix couldn't be applied.** When a security researcher reported it, the team found the patched XML parser required a newer major version of the document library that depended on it. The résumé service was two major versions behind on that library, and the upgrade path involved API changes across 40 call sites. The fix took two weeks. For those two weeks the mitigation was to reject all `.docx` uploads, which recruiters noticed immediately.

**"Are we affected?" took three days.** When a widely publicized vulnerability hit a popular logging library, three enterprise customers sent security questionnaires the same afternoon. Answering required someone to check every service's lockfile and every container image by hand. Nobody had a list of what was deployed where.

**An update was the attack.** The team, following good advice about keeping up to date, merges patch updates automatically when tests pass. One morning a patch release of a small utility package arrives, published an hour earlier from a maintainer's stolen account. It contains an install script that reads environment variables and sends them to a remote server. It runs on a developer's laptop and in CI before anyone notices.

The team didn't lack tools; it had alerts from the first day. It lacked a way to separate reachable risk from noise, a habit of staying close enough to current that fixes are cheap, an inventory, and a policy that treated updates as both the cure and a possible attack.

## What It Is

**Software composition analysis (SCA)** is the practice of keeping an inventory of the third-party components your software includes, direct and transitive, matching it against databases of known vulnerabilities, and running a process to decide what to fix, when, and how.

Two kinds of problems arrive through dependencies, and they need different responses:

- A **vulnerable** package has an honest bug with security consequences. It's published in an advisory; you find it by matching versions; you fix it by updating.
- A **malicious** package was built or altered to cause harm: a typosquatted name, a hijacked maintainer account, a protest payload. It usually has no CVE when it matters most, since the damage happens at install time. Updating quickly can make it _worse_.

Neighbors covered elsewhere: static analysis of your own code is 31.2a. The mechanics of update pull requests (grouping, scheduling, automatic merging) are in 29.2b; pinning CI actions and pipeline trust are in 30.3a; operating-system packages inside container images are in 30.4a. License compliance is often done by the same SCA tools but is a legal question rather than a security one, and isn't covered here.

## Recognizing the Problem

- Dependency alerts number in the hundreds, and nobody triages them.
- Critical alerts stay open for months because "most of them don't apply."
- Nobody can answer "do we use library X, and which version, in production?" in under an hour.
- A security fix requires a major-version upgrade the team has been putting off.
- The vulnerable package is transitive, and nobody knows how to change its version.
- Dev-only and production dependencies show up in the same list with the same urgency.
- Dependency updates are either never merged or always merged automatically, with nothing in between.
- Install scripts run on every `npm install`, in CI and on laptops, and nobody has looked at what they do.

## How It Works

### 1. Know what you actually ship

A typical Node service declares 30–50 direct dependencies and installs over a thousand packages once transitive dependencies are resolved. The manifest (`package.json`) lists what you asked for. The **lockfile** lists what was resolved, including every transitive package and its exact version, and it's the only reliable source for matching against advisories.

Even the lockfile overstates what reaches production. It includes dev dependencies: build tools, test runners, linters. For a service, those never run in production, though they do run in CI and on laptops, which matters for malicious packages. A bundler may include only part of a package. And the deployed container image adds its own operating-system packages.

A **software bill of materials (SBOM)** records the result: a machine-readable list of every component in a built artifact, in a standard format (CycloneDX or SPDX), with each component identified by a **package URL** such as `pkg:npm/fast-xml-parser@4.2.4`. Generating one per build and storing it with the artifact is what turns "are we affected?" from three days into a query.

### 2. Where advisories come from, and how matching works

A vulnerability is usually published as a **CVE**, a global identifier. For package ecosystems, the useful data is in ecosystem-aware databases: the **GitHub Advisory Database** (GHSA IDs), and **OSV**, an open, machine-readable format and aggregator that combines advisories from many ecosystems. The US National Vulnerability Database (NVD) enriches CVEs with scores and product identifiers, but it's built around products rather than packages, and since 2024 its enrichment has lagged far behind new CVEs. For open-source packages, ecosystem databases are more accurate and faster.

Matching is simple: a package name and ecosystem, and a range of affected versions. That simplicity is also its limit. The advisory says "versions below 4.2.5 are affected," not "and only if you call `parse` with `processEntities: true`." Every user of the package gets the alert, regardless of how they use it.

### 3. Prioritizing: severity is not risk

The alert list sorts by severity, usually a **CVSS** score. CVSS describes the vulnerability in the worst case: how it's exploited, and what an attacker gains. It says nothing about whether the vulnerable code runs in your system, or whether anyone is exploiting it anywhere. That's why the glob library and the XML parser both showed as "critical."

Four more questions narrow the list, roughly in order of cost:

1. **Does it ship?** A vulnerability in a dev dependency of a server application isn't reachable in production. It still runs in CI and on laptops, so it's low priority, not no priority.
2. **Is anyone exploiting it?** **EPSS** (from FIRST) estimates the probability that a vulnerability will be exploited in the next 30 days, based on observed activity. The **CISA KEV** catalog lists vulnerabilities known to be exploited in the wild. A vulnerability in KEV moves to the front of the queue regardless of its CVSS score.
3. **Is the vulnerable code reachable?** Reachability analysis asks whether your code can actually call the vulnerable function. It comes in levels: is the package imported at all; is the vulnerable module imported; does the call graph from your entry points reach the vulnerable function. The last level requires advisories that name the affected functions, which some ecosystems provide (Go's vulnerability database does, and `govulncheck` uses it) and many don't.
4. **Can an attacker control the input?** An XML parser that only reads a config file you ship isn't the same risk as one parsing uploaded résumés.

Applied to the 412 alerts, the funnel looks like this:

```
412  open alerts across 9 services
 │   ship to production?  (drop dev-only)
170
 │   package actually imported?
 61
 │   vulnerable function reachable from entry points?
  9
 │   attacker-controlled input reaches it?
  2  ◄── the XML parser in the résumé service, and one other
```

Reachability is an approximation, with the same limits as any static analysis (31.2a). Dynamic imports, reflection and plugin loading hide calls from it. "Not reachable" means "probably not," so a vulnerability that's being actively exploited gets patched even when analysis says it's unreachable.

### 4. Recording "not affected"

When the team concludes a vulnerability doesn't apply, that decision should be written down, with a reason and an expiry date, rather than just dismissed in a tool. Otherwise it gets investigated again by the next person, or silently becomes wrong when the code changes to call the vulnerable function.

**VEX** (Vulnerability Exploitability eXchange) is a standard way to record this: a statement that a product is `not_affected` by a vulnerability, with a justification such as `vulnerable_code_not_in_execute_path`. It can be published to customers alongside an SBOM, which answers their questionnaire before they send it. For internal use, a simpler exceptions file with the same fields works, as long as entries expire and get reviewed.

### 5. Ways to fix a vulnerable dependency

From cheapest to most expensive:

- **Remove it.** Many dependency trees include packages nothing uses any more. Tools like `knip` or `depcheck` find unused direct dependencies. A removed package can't be vulnerable.
- **Update within the range.** A patch or minor update of a direct dependency is usually a lockfile change.
- **Update the parent.** For a transitive vulnerability, a newer version of the direct dependency often pulls in the fixed version.
- **Force the transitive version.** npm's `overrides`, pnpm's `overrides` and Yarn's `resolutions` pin a transitive package to a version the parent didn't ask for. It's fast, and it runs the parent with a version its authors never tested. Fine for a patch release; risky across a major version.
- **Patch it locally.** `patch-package` or `pnpm patch` apply a diff to the installed package. It's an emergency measure that has to be removed later, and it needs an owner.
- **Mitigate around it.** Disable the feature, validate or reject the input, add a WAF rule. Rejecting `.docx` uploads was a mitigation; it bought time at a cost users saw.
- **Replace it** with a different library, or with a few lines of your own code.

### 6. Staying current is the real defense

The résumé service's two-week fix wasn't a vulnerability problem; it was a drift problem. A team two majors behind can't take a security patch that ships only on the latest major, and security patches increasingly ship only there. A team that takes small updates every week pays a small, predictable cost; a team that takes none pays it all at once, during an incident.

Drift can be measured. **Libyears** sum, across dependencies, how far each installed version is behind the latest release in time. It's crude, like the size metric in 31.1, but its trend shows whether a service is keeping up. The update mechanics (grouping, scheduling, automatic merging of minor and patch updates) are covered in 29.2b.

### 7. When the update is the attack

Automatic updates are what let the stolen-account release through. In September 2025, compromised maintainer accounts published malicious versions of widely used npm packages, including `chalk` and `debug`, and a self-replicating worm spread through hundreds of others by stealing tokens from the machines that installed it. These releases have no CVE when they're installed; by the time an advisory exists, the damage is done.

Defenses work at different points:

- **A minimum release age.** Don't install routine updates until they've been public for several days; most malicious releases are detected and removed within hours or days. Renovate and recent versions of pnpm support this. Security fixes bypass the delay, which is why the two kinds of update need separate policies.
- **Don't run install scripts by default.** Most packages don't need them. pnpm since version 10 doesn't run dependency lifecycle scripts unless they're explicitly allowed; npm has `--ignore-scripts`.
- **Strict lockfile installs** in CI (30.1a), so nothing changes without a reviewed commit.
- **Malicious-package advisories.** OSV publishes known malicious packages with `MAL-` identifiers. If one was installed, the response isn't an update: it's incident response. Treat every secret on that machine or CI runner as stolen, and rotate it.
- **Provenance.** npm can show that a package was built from a specific repository and commit by a specific CI workflow. That makes some attacks harder, like publishing from a laptop with a stolen token, but it doesn't prove the code is benign.
- **Fewer dependencies.** Every package is a set of maintainers you trust with install-time code execution.

### 8. A policy, not a pile

Everything above becomes a policy that runs in CI and decides what each finding means:

| Finding | Response |
| --- | --- |
| Malicious package installed | Block; incident response; rotate secrets |
| Exploited (KEV) or high EPSS, in production code | Block the next deploy until fixed or mitigated; fix within 48 hours |
| Critical/high, ships to production, reachable or unknown | Fix within 14 days, owned by the service's team |
| Ships to production, not reachable | Recorded exception with expiry; fixed in routine updates |
| Dev-only | Batched into routine updates |

The exact numbers are a team choice. What matters is that every finding has one of a few outcomes, each with an owner and a deadline, and that nothing sits in a list without one.

## When It's Appropriate

- **Any service in production that handles untrusted input.** Which is most services.
- **More than a handful of services or repositories.** Past about five, "are we affected?" can't be answered from memory, and an SBOM per build pays for itself the first time a major vulnerability is announced.
- **B2B products.** Enterprise customers send security questionnaires; an SBOM and VEX statements answer many of their questions directly.
- **Regulated or contract-bound environments.** Many security frameworks and some procurement rules require vulnerability management with defined response times. US federal procurement, for instance, now asks software suppliers for SBOMs.
- **Ecosystems with deep dependency trees,** npm most of all, where transitive packages outnumber direct ones twenty to one.

## When It's Unnecessary or Overkill

- **A commercial SCA platform for one service with twenty dependencies.** The ecosystem's own audit command, Dependabot or OSV-Scanner, and a short policy cover it.
- **Function-level reachability everywhere** when most findings are dev-only or already fixed by a routine update. Do the cheap filters first.
- **Publishing VEX documents** for an internal tool with no external customers. A simple exceptions file is enough.
- **Blocking every build on any vulnerability.** That's the gate that gets switched off (31.2a). Block on the top of the policy table only.
- **Chasing zero findings.** Some findings will always be open. The measure is how long exploitable ones stay open, not how many exist.

## Trade-offs

**Updating has costs and risks of its own.** Each update can break something, and automatic merging bets that your tests exercise what changed. A minimum release age delays security fixes too, unless those are handled separately.

**Reachability can be wrong.** It's static analysis, and it misses dynamic calls. Trusting a "not reachable" result on an actively exploited vulnerability is a gamble with bad odds.

**Advisory data is imperfect.** Version ranges are sometimes wrong, some vulnerabilities never get advisories, and different databases disagree. Two scanners on the same lockfile often give different counts.

**Forced transitive versions are untested combinations.** Overrides fix the alert and occasionally break the parent in ways only production shows. They also accumulate, because nobody remembers to remove them once the parent catches up.

**Process costs.** Triage takes engineering time every week. SLAs need owners, exceptions need review, and SBOMs need storing somewhere they can be queried. Without that, the tools produce the 412-alert pile again.

**Noise erodes trust.** The same effect as in 31.2a: a list full of irrelevant criticals trains people to ignore the whole list, including the real one.

## Alternatives

**Fewer, larger dependencies.** Prefer the standard library and a few well-maintained libraries to many small ones. Go and the JVM lean this way by culture. It cuts both vulnerability exposure and malicious-package risk, and costs you writing and maintaining code a package would have provided.

**Vendoring.** Copy dependencies into your repository and update them deliberately. Every change is reviewable, and nothing changes without a commit. It makes updates heavier, so drift grows unless someone owns them.

**Relying on a platform.** Managed runtimes and distributions (a serverless platform, a maintained base image, a distro's security team) take on part of the patching. It covers what the platform provides and nothing you install on top.

**Runtime protection.** WAF rules and application self-protection can block exploitation of known vulnerabilities while a fix is prepared. It's useful as a mitigation, and it isn't a substitute for fixing.

## How to Achieve It

**Level 0: see production findings only.** Run a scanner on each service's lockfile in CI, separating production from dev dependencies. Assign each service's findings to its team. _Signal to move on:_ findings get seen, but nobody can say which ones matter.

**Level 1: a policy with priorities.** Add KEV and EPSS to severity, block only on the top tier, give the rest deadlines, and record exceptions with reasons and expiry dates. _Signal:_ fixes are slow because updates are hard.

**Level 2: stay current.** Grouped weekly updates (29.2b), a minimum release age for routine updates, security updates on a fast path, install scripts off by default, and unused dependencies removed. Track libyears per service. _Signal:_ a big vulnerability announcement still means a manual hunt.

**Level 3: an inventory.** Generate an SBOM per build, store it with the artifact, and make it searchable across services. _Signal:_ too many findings remain "reachable or unknown."

**Level 4: reachability and VEX.** Add function-level reachability where your ecosystem's data supports it, and publish VEX statements to customers who need them.

## Implementation

TypeScript, since npm's deep trees and install-time scripts make it the ecosystem where this problem is sharpest. The script reads a lockfile, looks up each installed package in OSV, and applies the policy from §8. It's the core of what commercial tools do, without their reachability analysis.

First, the inventory. npm's lockfile (version 2 and later) lists every installed package under `packages`, marks dev-only ones, and records nested copies separately:

```ts
import { readFileSync } from "node:fs";

type Installed = { name: string; version: string; dev: boolean; path: string };

export function inventory(lockfilePath = "package-lock.json"): Installed[] {
  const lock = JSON.parse(readFileSync(lockfilePath, "utf8"));
  return Object.entries<any>(lock.packages)
    .filter(([path]) => path.startsWith("node_modules/"))
    .map(([path, meta]) => ({
      // "node_modules/a/node_modules/@scope/b" → "@scope/b"
      name: meta.name ?? path.slice(path.lastIndexOf("node_modules/") + "node_modules/".length),
      version: meta.version,
      dev: meta.dev === true,
      path,
    }));
}
```

> **The same package, several times.** Nested paths mean one package can be installed at three different versions in one tree, because different parents asked for different ranges. Fixing the vulnerable copy under one parent doesn't fix the others. That's why an alert can survive an update that seemed to fix it.

Second, the lookup, using OSV's batch API, plus the KEV catalog and EPSS scores for anything that has a CVE:

```ts
type Vuln = { id: string; aliases?: string[]; database_specific?: { severity?: string } };

async function osvLookup(pkgs: Installed[]): Promise<Map<Installed, Vuln[]>> {
  const res = await fetch("https://api.osv.dev/v1/querybatch", {
    method: "POST",
    body: JSON.stringify({
      queries: pkgs.map((p) => ({ package: { name: p.name, ecosystem: "npm" }, version: p.version })),
    }),
  }).then((r) => r.json());

  const found = new Map<Installed, Vuln[]>();
  for (const [i, result] of res.results.entries()) {
    if (!result.vulns?.length) continue;
    const details = await Promise.all(
      result.vulns.map((v: { id: string }) => fetch(`https://api.osv.dev/v1/vulns/${v.id}`).then((r) => r.json())),
    );
    found.set(pkgs[i], details);
  }
  return found;
}

async function exploitSignals(cves: string[]) {
  const kev = await fetch("https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json")
    .then((r) => r.json());
  const kevIds = new Set<string>(kev.vulnerabilities.map((v: { cveID: string }) => v.cveID));
  const epss = await fetch(`https://api.first.org/data/v1/epss?cve=${cves.join(",")}`).then((r) => r.json());
  const epssById = new Map<string, number>(epss.data.map((d: any) => [d.cve, Number(d.epss)]));
  return { kevIds, epssById };
}
```

> **In CI, cache these.** The batch query is one request per few hundred packages, but vulnerability details, the KEV feed and EPSS scores change at most daily. Fetching them fresh on every build is slow and turns an outage at any of those services into a failed build. A nightly job that refreshes a local copy is the usual shape.

Third, the policy. Exceptions live in a committed file, each with a reason and an expiry date:

```ts
type Exception = { vuln: string; package: string; reason: string; expires: string };
type Verdict = "incident" | "block" | "fix-14d" | "exception" | "routine";

function decide(pkg: Installed, v: Vuln, s: Awaited<ReturnType<typeof exploitSignals>>, exceptions: Exception[]): Verdict {
  if (v.id.startsWith("MAL-")) return "incident";              // installed malware: rotate secrets, don't just update

  const ex = exceptions.find((e) => e.vuln === v.id && e.package === pkg.name);
  if (ex && new Date(ex.expires) > new Date()) return "exception";

  if (pkg.dev) return "routine";                                  // runs in CI and on laptops, not in production

  const cves = (v.aliases ?? []).filter((a) => a.startsWith("CVE-"));
  const exploited = cves.some((c) => s.kevIds.has(c) || (s.epssById.get(c) ?? 0) >= 0.1);
  if (exploited) return "block";

  const severity = v.database_specific?.severity ?? "UNKNOWN";
  return severity === "CRITICAL" || severity === "HIGH" || severity === "UNKNOWN" ? "fix-14d" : "routine";
}
```

> **Two details that are policy, not code.** An expired exception doesn't silently disappear: it falls through to the normal rules, so the finding comes back with its original priority and someone has to look again. And `UNKNOWN` severity is treated as high on purpose. Some advisories arrive before anyone has scored them, and the most dangerous ones are often among those.
>
> **Where "ships to production" is wrong.** The `dev` flag describes the lockfile, not the artifact. A front-end bundle built by a dev-dependency bundler ships code that came from "dev" packages, and a build tool can inject its own runtime helpers. For bundled front ends, the SBOM of the built output, not the lockfile, is the honest source.

The runner around these three pieces is short: build the inventory, look it up, decide, print a table grouped by verdict, and exit non-zero if anything is `incident` or `block`.

## Further Reading

- OSV: the schema and database at osv.dev, and **OSV-Scanner** (github.com/google/osv-scanner) for scanning lockfiles and SBOMs across ecosystems.
- **GitHub Advisory Database** documentation, including how advisories are reviewed and how Dependabot matches them.
- FIRST: the **CVSS v4.0** specification, and the **EPSS** model documentation and API.
- CISA's **Known Exploited Vulnerabilities** catalog, and CISA's guidance on minimum requirements for **VEX**. **OpenVEX** (github.com/openvex) for a compact format.
- **CycloneDX** and **SPDX** specifications for SBOMs; the **package URL (purl)** specification.
- Go's **govulncheck** documentation, for what function-level reachability looks like when advisories name symbols.
- **Renovate** documentation on `minimumReleaseAge`, and **pnpm**'s settings for minimum release age and allowed build scripts; npm's documentation on `overrides` and provenance.
- Markus Zimmermann et al., "Small World with High Risks: A Study of Security Threats in the npm Ecosystem," USENIX Security 2019. How a few maintainer accounts can reach most of the ecosystem.
- Ivan Pashchenko et al., "Vulnerable Open Source Dependencies: Counting Those That Matter," ESEM 2018. How many reported vulnerable dependencies don't actually affect the application.
- **libyear** (libyear.com), for the drift metric.
- **OpenSSF Scorecard** and **SLSA**, for evaluating dependencies' maintenance practices and build provenance.

A sibling in **Go** would be worth writing, though it isn't yet. The Go vulnerability database records which functions each vulnerability affects, and `govulncheck` combines that with a call graph of your program, so by default it reports only vulnerabilities your code can actually reach. Seeing how much of the funnel in §3 disappears when the advisory data and the toolchain are designed for reachability shows what the npm ecosystem's alert noise is really made of. Go's module proxy and checksum database also make the "update was the attack" story different: a published version can't be silently replaced.

---

The habit to take from this: for every dependency alert, ask three questions before its severity. _Does this code run in production? Can an attacker reach it? How far behind are we on this package?_ The first two decide whether it matters. The third decides whether fixing it will take an hour or two weeks, and that one is under your control before any vulnerability is announced.
