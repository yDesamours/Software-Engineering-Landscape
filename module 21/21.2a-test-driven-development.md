# Test-Driven Development as a Design Loop

_Module 21.2a — Testing Strategies_

## The Problem

A support-desk product promises each customer's tickets a first response within a set number of business hours. A ticket's deadline depends on the tenant's opening hours, weekends, and public holidays.

A developer writes `responseDue(ticket)` in an afternoon. It is 140 lines long. It calls `new Date()`, loads the tenant's hours and holidays from the database, converts time zones, and loops forward through the calendar. Then the developer writes tests for it.

Getting the function into a test takes some effort. The database module has to be mocked with `vi.mock("../db")`, and the clock has to be frozen with `vi.useFakeTimers()`. The developer writes four tests. For each one, they run the function, copy its output into `expect(...)`, and move on. All four pass on the first run. The code ships.

Three weeks later, a Monday is a public holiday. Tickets created on the Friday before, shortly before closing time, get deadlines on the holiday itself. On Tuesday morning, 300 tickets are flagged as breached and support leads get paged. The loop checked the holiday list when deciding where the clock *starts*, but it never checked it when *moving to the next day*.

The post-incident review finds four separate problems:

- **The expected values came from the code's own output.** Whatever the code did, including its bugs, became the expectation.
- **Nobody had seen any of the tests fail.** Two of the four couldn't fail. They mocked the holiday query to return `[]`, and one computed its expected value with the same helper the function uses. If you deleted the holiday logic completely, both still passed.
- **The list of edge cases existed only in the developer's head,** and "Friday before a holiday" wasn't on it.
- **The difficulty of testing was a warning about the design that arrived too late.** Needing to mock a module and freeze global time showed that one function was doing I/O and calculation together. By the time the tests revealed that, the design was finished and nobody wanted to reopen it.

## What It Is

**Test-driven development (TDD)** is a way of writing code in short cycles. You write a failing test for the next small piece of behavior. You write just enough code to make it pass. Then you improve the design while all the tests stay green. The cycle is called *red, green, refactor*, and Kent Beck's work established it as a practice.

TDD is a way of working, not a kind of test. It is easy to confuse with nearby ideas:

- **Having unit tests** is not TDD.
- **High coverage** is not TDD.
- **Writing every test up front and then implementing** is test-first, but it isn't TDD either. The loop depends on one test at a time, with the design allowed to change between tests.

A few related practices, including BDD, acceptance-test-driven development, and property-based testing, are compared under Alternatives.

## Recognizing the Problem

- Expected values in tests were copied from the program's output.
- There are tests nobody has ever seen fail.
- Testing a function requires mocking modules, patching globals, or faking timers.
- Edge cases reach production that nobody had ever listed.
- Pull requests say "tests in a follow-up."
- Bug fixes are merged without a test that reproduces the bug.
- People avoid refactoring because they don't trust the suite to catch a mistake.

## How It Works

### The loop

Kent Beck's 2023 restatement, "Canon TDD," has five steps:

1. **Write a list** of the behaviors and cases you expect to need.
2. **Turn exactly one item into a concrete, runnable test.** Run it, and watch it fail *for the reason you expect*.
3. **Make it pass**, along with all previous tests, in whatever way is simplest. When you notice a new case, add it to the list instead of handling it now.
4. **Refactor** the code and the tests while everything is green.
5. **Repeat** until the list is empty.

```
        ┌──────── test list ◀────────── new cases you noticed ───┐
        ▼                                                         │
  RED: one failing test ──▶ GREEN: simplest pass ──▶ REFACTOR ────┘
       │                          │                      │
       └ proves the test          └ proves the code      └ where the design
         can fail                   meets it               actually improves
```

### Why each step matters

**Red.** A test you've never seen fail hasn't been checked. It might assert on a mock, call the wrong function, or compare two values that are always equal. Watching it fail shows it can fail. Reading the failure message shows it fails *for the right reason*. A "not a function" error is a legitimate first red, but it tells you less than an assertion failure that shows the wrong date.

**Green.** The simplest code that passes can seem naive. Beck describes three ways to get there:

- **Fake it:** return the constant the test expects.
- **Triangulate:** add a second example that the fake can't satisfy, which forces a general solution.
- **Obvious implementation:** when the answer is clear, just write it.

How big a step you take is your choice. Take big steps while things are going smoothly, and smaller ones as soon as something surprises you.

**Refactor.** This step is where the design improves, and it's the one people skip most often. TDD without refactoring gives you a pile of special cases, each added to satisfy one test. The tests get refactored here too. Duplicated setup and unclear names in tests make the suite harder to maintain, just as they do in production code.

### Design pressure from the first caller

A test is the first code to call a function, and it calls it before the function exists. If that test would need a database and a frozen clock, the test is telling you the function mixes two jobs, and it tells you at the point where changing the design costs nothing.

The usual fix is to pass in the things that vary, such as the current time and the calendar data. That leads to what Gary Bernhardt calls **functional core, imperative shell**:

- **A pure core** makes the decisions. It receives time and data as arguments and returns results.
- **A thin shell** fetches inputs, calls the core, and stores the results.

TDD is cheap in the core, where tests are plain function calls. The shell gets a few integration tests (21.3a).

### Two schools

**The classicist school** (also called Chicago or Detroit) works inside out. It starts from domain logic, uses real collaborators wherever they are fast, and asserts on returned values and resulting state. Its tests survive refactoring well.

**The mockist school** (also called London) works outside in. It follows *Growing Object-Oriented Software, Guided by Tests*. It starts from a failing acceptance test at the system's edge, then works inward. Test doubles stand in for collaborators that don't exist yet, so the tests help design those collaborators' interfaces. Its tests assert on interactions. The school is known for the **double loop**: an outer acceptance test stays red while many inner unit cycles run, until the whole feature works.

Mockist TDD puts useful pressure on interface design, and its tests break more easily when internals change. Module 21.2b explains which interactions are worth asserting on and which only make the suite brittle.

### Start bug fixes with a failing test

This is the part of TDD that every team should adopt, whatever it thinks of the rest. **Before fixing a bug, write a test that reproduces it and watch it fail.**

- Seeing it fail proves you understood the bug.
- Seeing it pass after the fix proves the fix works.
- The test then stays in the suite and prevents the bug from coming back.

A fix without a reproducing test is based on a guess.

### Legacy code

Code without tests needs **characterization tests** first (Michael Feathers). These tests deliberately record what the code currently does, bugs included, so that you can change the code safely. They are written after the code, and that's fine, because their job is different. New behavior added to that code can then be developed with TDD.

## When It's Appropriate

- **Logic with many cases**, such as rules, calculators, parsers, state machines, and date arithmetic. The deadline function has about ten cases, and each one is a single line of test.
- **Every bug fix**, without exception.
- **Code whose interface you are designing**, such as library APIs and domain services, where the first caller's point of view helps.
- **Requirements clear enough to state as examples**, like "a ticket at 16:59 on Friday with an 8-hour budget is due at …"
- **Refactoring**, where a trustworthy suite is what makes it safe to change things.

## When It's Unnecessary or Overkill

- **Spikes and exploration.** When you don't yet know what to build, or how an API behaves, write throwaway code to find out. Delete it, then build the real version with tests.
- **Layout and visual work.** A test that asserts on pixel positions only restates the stylesheet.
- **Glue code with no decisions in it**, such as passing a handler's arguments to a service. A broader test (21.3b) covers it.
- **Tests that would only restate the implementation**, such as a configuration mapping tested by repeating the mapping.
- **TDD as an enforced metric.** Rules like "every commit must show a failing test first" produce ceremony rather than design. People write the red step to satisfy the check.

## Trade-offs

- **A slower start.** The early cycles feel slow. The time is paid back later, when requirements change and the suite catches mistakes. If the code never changes again, that payback never comes.
- **Results depend heavily on skill.** Skipping the refactor step, or taking tiny steps that each pin an internal detail, produces a large, brittle suite that makes change harder.
- **It focuses attention on local design.** TDD says little about performance, concurrency, or how components fit together at the system level.
- **Research results are mixed.** Controlled studies disagree about TDD's effect on quality and productivity. One well-known analysis (Fucci et al., 2017) found that outcomes were associated with working in small, steady steps, not with whether the test came before the code. That suggests the rhythm of the loop may matter more than the ordering people argue about.
- **You still only test the cases you thought of.** Writing the test list forces you to think about cases, but it doesn't generate them. Property-based testing (21.3c) complements TDD here.

## Alternatives

- **Writing tests after the code, carefully.** Write the case list anyway. Then make each test fail on purpose by breaking the code temporarily, which is a manual version of mutation testing (21.4). You get most of the benefit of the red step without changing the order you work in.
- **Behavior-driven development (BDD).** Dan North's reframing of TDD in terms of behavior ("should …") and Given/When/Then scenarios, often as executable specifications written in Gherkin and shared with people who aren't developers. The value is the conversation that produces the scenarios. Gherkin files written without that conversation are just a slower test framework.
- **Acceptance-test-driven development / specification by example.** The team agrees on concrete acceptance examples before development starts. This is the outer loop of the double loop, pursued as a practice of its own.
- **Property-based testing (21.3c).** Instead of listing cases, you state rules that hold for all inputs and let a tool generate the cases.
- **Types and design by contract.** Some tests become unnecessary when the compiler or runtime rejects the invalid states outright.
- **REPL-driven development.** You get fast feedback while exploring, but it leaves no tests behind for later changes.

## How to Achieve It

**Level 0: every bug fix starts with a failing test.** This needs no training and no buy-in beyond the pull-request template.
_Signal you need it:_ any bug fix.

**Level 1: write the case list, even when you aren't writing tests first.**
_Signal you need it:_ edge cases reaching production that nobody had listed.

**Level 2: use TDD for new pure logic.**
_Signal you need it:_ a new rule, calculation, or parser.

**Level 3: separate pure cores from their shells**, so existing logic becomes easy to test. Write characterization tests first.
_Signal you need it:_ tests that require module mocks or fake timers.

**Level 4: use the double loop for features.** Write an acceptance test at the API level first, and work inward until it passes.
_Signal you need it:_ features that every unit test says are done, but that don't work end to end.

## Implementation

This section uses TypeScript with Vitest, and redoes the deadline function test-first. Times are local to the tenant. Converting them from UTC is the shell's job and never reaches this function.

The test list comes first. It changes as the work goes on:

```ts
// sla.test.ts
// [x] 10:00 on a working day, 2h budget → 12:00 the same day
// [x] a budget that runs past closing continues at the next opening
// [x] created before opening → the clock starts at opening
// [x] created after closing → the clock starts at the next working day's opening
// [x] created on a weekend → the clock starts on the next working day
// [x] moving past a holiday skips it           ← added while doing the weekend case
// [x] budget exactly equal to what's left today → due at closing, not the next morning
// [ ] zero budget → due at the (adjusted) start time
// [ ] tenant time zones                        → the shell's job; moved to shell tests
```

The first test, and the design change it forces:

```ts
import { it, expect } from "vitest";
import { responseDue } from "./sla";
import { weekdays, at } from "./test-helpers";

it("adds the budget within one working day", () => {
  expect(responseDue(at("2026-10-01", "10:00"), 120, weekdays())).toEqual(at("2026-10-01", "12:00"));
});

it("skips a holiday when moving to the next day", () => {
  const calendar = weekdays({ holidays: ["2026-10-05"] }); // a Monday
  // Friday 16:59, 8h budget: 1 minute on Friday, then 7h59m on the next working day, which is Tuesday
  expect(responseDue(at("2026-10-02", "16:59"), 480, calendar)).toEqual(at("2026-10-06", "16:59"));
});
```

> **Aside: the calendar is an argument because the first test had nowhere else to get one.** The original version loaded holidays itself. Here, the test, as the first caller, created the seam before any implementation existed. Nothing was mocked. `weekdays()` is a real, three-line calendar.

The implementation after the refactor step:

```ts
export type LocalTime = { date: string; minute: number }; // minute of the day, in the tenant's zone

export interface WorkCalendar {
  opens: number;  // minute of the day
  closes: number;
  isWorkingDay(date: string): boolean;
  nextWorkingDay(date: string): string;
}

export function responseDue(created: LocalTime, budget: number, cal: WorkCalendar): LocalTime {
  let { date, minute } = clockStart(created, cal);
  let remaining = budget;
  while (remaining > cal.closes - minute) {
    remaining -= cal.closes - minute;
    date = cal.nextWorkingDay(date); // the only place the day advances
    minute = cal.opens;
  }
  return { date, minute: minute + remaining };
}

function clockStart({ date, minute }: LocalTime, cal: WorkCalendar): LocalTime {
  if (!cal.isWorkingDay(date) || minute >= cal.closes) {
    return { date: cal.nextWorkingDay(date), minute: cal.opens };
  }
  return { date, minute: Math.max(minute, cal.opens) };
}
```

> **Aside: the loop is what refactoring produced.** After the weekend test passed, the code had three `if` branches that each moved to the next day in its own way, and one of them ignored holidays. That is exactly the shape of the production bug. Merging them into the single line marked "the only place the day advances" was the refactor. After that, the holiday test passed without any new code.

> **Aside: a test that passes immediately still needs checking.** A green test with no new code means one of two things. Either the design already handles the case, or the test is wrong. To tell which, temporarily make `nextWorkingDay` ignore holidays and confirm the test fails with `expected '2026-10-05' to equal '2026-10-06'`. Only then trust it. That failure message describes the production incident, before any code for the case was written.

> **Aside: the `>` in the `while` condition is a boundary.** An 8-hour budget starting at 09:00 has to finish at 17:00 on the same day, not at 09:00 the next morning. The "exactly equal" item on the list is there to catch that, and it's the kind of case Module 21.4 shows a suite can execute without ever checking.

## Further Reading

- **Kent Beck, _Test-Driven Development: By Example_ (2002).** The original description, worked through in full. Still the best way to see the rhythm of small steps.
- **Kent Beck, "Canon TDD"** (_Software Design: Tidy First?_, 2023). A short restatement written because the term had drifted. The test list is the step most often left out.
- **Steve Freeman & Nat Pryce, _Growing Object-Oriented Software, Guided by Tests_ (2009).** The outside-in, mockist approach and the double loop, applied to a real application.
- **Michael Feathers, _Working Effectively with Legacy Code_ (2004).** Characterization tests, seams, and how to get untested code into a state where TDD is possible.
- **Gary Bernhardt, "Boundaries"** (talk, 2012). Functional core, imperative shell, and why it leaves fewer things to test with doubles.
- **Dan North, "Introducing BDD"** (2006). Where BDD came from, and what it was trying to fix in how people learned TDD.
- **Davide Fucci et al., "A Dissection of the Test-Driven Development Process: Does It Really Matter to Test-First or to Test-Last?"** (IEEE TSE, 2017). A careful look at which parts of TDD are associated with better outcomes.

No sibling is proposed. The loop works the same way in any language. What does vary between languages is how test doubles are created, including whether a module can be replaced without any seam. That question belongs to 21.2b and its sibling.

---

The habit to take from this: before trusting any test, including one you didn't write, check that you've seen it fail. A test that has only ever passed hasn't yet shown that it can detect anything.
