# What Coverage Measures, and What Mutation Testing Adds

_Module 21.4 — Testing Strategies_

## The Problem

A consumer-lending platform charges late fees under a written policy:

- There are three days' grace.
- After that, the fee is a flat 5.00 plus 0.1% of the balance per chargeable day.
- The fee is capped at 25.00.

The organization requires **80% line coverage** in CI. This team is at 86%.

A refactor of the fee module changes `daysLate <= GRACE_DAYS` to `daysLate < GRACE_DAYS`. Coverage stays at 86%, every test passes, and the change ships. For six weeks, customers who pay on the last day of their grace period are charged 5.00. That affects 4,100 accounts. Refunds follow, and because this is a regulated product, so does a report to the regulator.

The test for late fees ran every line of the fee calculation. Its only assertion was that the result was not null.

Meanwhile, the coverage gate had been causing problems of its own:

- **Tests that assert nothing.** One test calls every controller method with mocks and never checks a result. It adds 4% to the number.
- **Tests of trivial code.** Getters, setters, and `toString` all have tests.
- **A growing exclusions list.** The coverage configuration now excludes 37 packages.
- **Deleting code got harder.** A pull request that removed a retired feature, along with its well-tested code, dropped coverage below 80% and was blocked. Its author added getter tests until the build passed.

The number went up every quarter. What it measured was never the thing that mattered.

## What It Is

**Code coverage** measures which parts of the code *executed* while the tests ran. It doesn't tell you whether any test checked the result.

**Mutation testing** makes small, deliberate changes to the code, called **mutants**, and runs the tests against each one. A mutant is *killed* if some test fails, and *survives* if every test still passes. The share of mutants killed measures whether the suite *notices* when the code changes.

In short: "covered" means the code ran, and "killed" means a test noticed the change.

Two other meanings of "test coverage" are worth separating. Requirements coverage (is every requirement tested?) is a different question. And coverage is not a quality score, even though a gate turns it into one.

## Recognizing the Problem

- Bugs reach production in code the coverage report shows as covered.
- Tests have no meaningful assertions, or assert only `isNotNull` or "doesn't throw."
- Tests exist mainly to raise the percentage.
- The coverage exclusion list keeps growing.
- Pull requests that delete code get blocked by the gate.
- Code reviews argue about the percentage instead of about the tests.
- Modules report 100% line coverage and still have bugs in branches that no test checks.

## How It Works

### How coverage is collected

Coverage tools **instrument** the code. They insert probes during the build or when code loads, record which probes fire during the test run, and map the probes back to lines and branches. Some examples:

- JaCoCo's Java agent rewrites bytecode as classes load.
- Istanbul rewrites JavaScript source.
- V8 has built-in coverage support.
- Go's `-cover` flag rewrites Go source.

The overhead is modest. It can still change the timing of tests that depend on timing.

### What the counters count

```java
if (daysLate <= GRACE) return ZERO;       // one decision, two outcomes
return fee.compareTo(CAP) > 0 ? CAP : fee; // one decision, two outcomes

tests: daysLate = 1, daysLate = 10 (fee below cap)
  lines executed:     all of them     → 100% line coverage
  outcomes observed:  3 of 4          → 75% branch coverage   (the cap was never hit)
```

- **Line or statement coverage:** was each line executed?
- **Branch or decision coverage:** did each decision go both ways?
- **Condition coverage:** did each boolean sub-expression evaluate both true and false?
- **MC/DC (modified condition/decision coverage):** was each condition shown to affect the outcome on its own? Aviation's DO-178C standard requires this for its most critical software.
- **Path coverage:** was every route through the code taken? The number of paths grows combinatorially, and many are impossible, so this is rarely achievable.
- **Function or method coverage:** was each function called at all?

Branch coverage is almost always more informative than line coverage for code that makes decisions.

### What a coverage number can and can't tell you

Coverage gives you much more information in one direction than the other.

- **Low coverage is informative.** It points to specific code that no test ran, and code that never runs can't be checked.
- **High coverage says almost nothing** about whether the tests check results.

Research agrees. Inozemtseva and Holmes (2014) found that once you control for the number of tests, coverage is only weakly correlated with how well a suite detects faults. Brian Marick made the same point in 1997: a coverage tool is for finding what you forgot to test, not a goal to aim for.

### Why a global gate backfires

Once a number becomes a target, people improve the number (Goodhart's law, 16.2). The Problem shows the usual results: tests that assert nothing, tests of trivial code, a long exclusion list, blocked deletions, and review time spent arguing about percentages.

Several practices give you the useful part without those side effects:

- **Show coverage on the lines a pull request changed.** Highlight new lines that no test ran. A person decides whether that matters.
- **Use branch coverage for code that makes decisions.**
- **Treat published numbers as rough guides, not thresholds.** Google's testing blog describes 60% as acceptable, 75% as commendable, and 90% as exemplary, and puts much more weight on coverage of changed code during review.

### Mutation testing

**Mutation operators** make small, typical mistakes:

- Change a boundary: `<=` becomes `<`.
- Negate a condition.
- Swap arithmetic operators: `-` becomes `+`.
- Replace a return value with `null`, zero, or an empty value.
- Remove a call to a method that returns nothing.

Each mutant runs against the tests. There are several possible outcomes:

- **Killed:** at least one test failed.
- **Survived:** every test passed.
- **No coverage:** no test executed the mutated line.
- **Timed out:** usually counted as killed, since the change made something loop.

**Cost.** Roughly, it's the number of mutants multiplied by the tests that run for each one. Tools reduce this in several ways. They run only the tests that cover the mutated line (PIT does this). They reuse results from earlier runs (incremental analysis). They limit mutation to code that changed. And they run under a time budget.

**Equivalent mutants.** Some mutations change the code without changing its behavior, so no test can kill them. A person has to recognize these, and they are why a 100% mutation score is usually impossible. The Implementation section has an example.

**What a surviving mutant tells you.** It usually means one of four things:

1. An assertion is missing or too weak.
2. A boundary case has no test.
3. The mutant is equivalent.
4. The mutated code is redundant or dead, and should be deleted.

**Google's approach.** Petrović and Ivanković (2018) describe Google showing surviving mutants as code-review comments, only on the lines a change touched, and filtering out mutant types that reviewers had found unhelpful. It worked because it appeared as a review comment rather than a score.

## When It's Appropriate

- **Coverage as a search tool.** Look for untested areas in modules that matter, and show coverage of changed lines in review.
- **Branch coverage** for logic-heavy modules such as fees, eligibility, and pricing.
- **Mutation testing on critical code**, such as money calculations, authorization rules, and anything regulated. The late-fee module is a clear example.
- **Mutation testing before a risky refactor.** It tells you whether the suite would notice if you broke something.
- **Mutation testing on a suite you inherited**, to find out quickly how much you can trust it.

## When It's Unnecessary or Overkill

- **A 100% coverage target.** The last few percent go to trivial code and to tests written only to reach the number.
- **A global coverage ratchet on legacy code.** It blocks deletions and rewards gaming.
- **MC/DC outside safety-critical domains.**
- **Nightly mutation runs over a whole CRUD codebase.** Hours of compute go to mutants in mapping code that nobody will ever review.
- **A mutation-score gate set near 100%.** Equivalent mutants make that threshold unreachable, and people eventually start excluding code to meet it.

## Trade-offs

- **Instrumentation overhead**, and timing changes in timing-sensitive tests.
- **Gates distort behavior**, as described above.
- **Exclusions need upkeep.** Each one is a decision, and nobody remembers why it was made.
- **Mutation testing is expensive.** A run can take minutes or hours, depending on how tightly it's scoped.
- **Equivalent mutants cost review time.** Someone has to reason through each one.
- **Tool maturity varies by language.** PIT for the JVM and Stryker for JavaScript, TypeScript, and C# are mature. Other languages have fewer options.
- **Noisy reports teach people to ignore them.** A thousand survivors with no triage is worse than no report.

## Alternatives

- **Escape analysis.** For each area of the code, count the defects that reached production. It measures what you actually care about, and it only tells you after the fact.
- **Review checklists** that ask "which test would fail if this line were wrong?"
- **Property-based tests (21.3c) and contract tests (21.1b).** These make a suite better at catching faults without adding a metric.
- **Requirements traceability**, in regulated settings, where auditors need to see a requirement linked to a test.
- **Fault injection and chaos experiments**, which apply the same "does anything notice?" question to the whole running system.

## How to Achieve It

**Level 0: collect coverage without a gate.** Read the list of uncovered code for your critical modules.
_Signal you're here:_ nobody knows what isn't tested.

**Level 1: show coverage of changed lines in pull requests**, as information only.
_Signal you need it:_ new code landing with no tests.

**Level 2: report branch coverage instead of line coverage, broken down by module.** If you set floors at all, set them for critical modules only.
_Signal you need it:_ modules at 100% line coverage with bugs in their branches.

**Level 3: run mutation testing on one or two critical modules**, and review the surviving mutants once.
_Signal you need it:_ a bug that escaped through covered code, like the late fee.

**Level 4: run mutation testing on changed lines in pull requests**, reported as review annotations.
_Signal you need it:_ Level 3 found enough to be worth continuing.

If an organization-wide gate is required and you can't remove it, keep its threshold modest, apply it to changed code rather than the whole codebase, and add mutation testing for the code where mistakes are costly.

## Implementation

This section uses Java with PIT, the most mature mutation-testing tool. Here is the fee policy and the test that gave it 100% line coverage:

```java
public Money lateFee(Money balance, int daysLate) {
    if (daysLate <= GRACE_DAYS) {                                   // line 21
        return Money.ZERO;                                          // line 22
    }
    Money fee = FLAT_FEE.plus(balance.times(DAILY_RATE).times(daysLate - GRACE_DAYS)); // line 24
    return fee.compareTo(CAP) > 0 ? CAP : fee;                      // line 25
}
```

```java
@Test void noFeeInsideGrace() { assertThat(policy.lateFee(Money.of("500.00"), 1)).isEqualTo(Money.ZERO); }
@Test void chargesAFeeWhenLate() { assertThat(policy.lateFee(Money.of("500.00"), 10)).isNotNull(); }
```

PIT's results for these tests (abridged):

```
line 21  changed conditional boundary          SURVIVED
line 21  negated conditional                   KILLED
line 22  replaced return value with null       KILLED
line 24  replaced integer subtraction with add SURVIVED
line 25  negated conditional                   SURVIVED
line 25  changed conditional boundary          SURVIVED
line 25  replaced return value with null       KILLED    ← the only thing isNotNull() checks

Line coverage 100%   ·   Generated 7 mutations, killed 3 (43%)
```

> **Aside: the first surviving mutant is the incident.** Changing `<=` to `<` on line 21 is exactly the refactor that shipped. PIT, run against the code *before* the incident, would have reported that the suite couldn't detect that change. The coverage report showed line 21 as covered the whole time.

Tests that kill the mutants that matter:

```java
@ParameterizedTest
@CsvSource({
    "3,  0.00",   // last day of grace: kills the boundary mutant on line 21
    "4,  5.50",   // first chargeable day: 5.00 + 1 × 0.1% × 500.00
    "10, 8.50",   // 7 chargeable days: kills subtraction → addition (which would give 11.50)
    "60, 25.00",  // 5.00 + 28.50 = 33.50, capped: kills the negated cap check
})
void lateFeeOnABalanceOf500(int daysLate, String expected) {
    assertThat(policy.lateFee(Money.of("500.00"), daysLate)).isEqualTo(Money.of(expected));
}
```

After adding these, PIT kills 6 of the 7 mutants. The survivor is the boundary change on line 25, which turns `> 0` into `>= 0`, and it's **equivalent**. When the fee exactly equals the cap, the original code returns `fee` and the mutant returns `CAP`, and those are the same amount. No test can tell them apart. One way to recognize an equivalent mutant is to write the test at the boundary, watch it still pass, and then work out why.

> **Aside: the three new rows are not a coverage improvement.** Line coverage was already 100%, and branch coverage only moves from 3/4 to 4/4 because of the capped case. Almost all of the gain is in what the tests *check*, and only mutation testing shows that.

Scoped configuration, so mutation testing runs only where it's worth the cost:

```xml
<plugin>
  <groupId>org.pitest</groupId>
  <artifactId>pitest-maven</artifactId>
  <version>${pitest.version}</version>
  <dependencies>
    <dependency>
      <groupId>org.pitest</groupId>
      <artifactId>pitest-junit5-plugin</artifactId>
      <version>${pitest-junit5.version}</version>
    </dependency>
  </dependencies>
  <configuration>
    <targetClasses><param>com.example.lending.fees.*</param></targetClasses>   <!-- critical code only -->
    <targetTests><param>com.example.lending.fees.*</param></targetTests>
    <withHistory>true</withHistory>   <!-- incremental: reuse results for code that hasn't changed -->
  </configuration>
</plugin>
```

```bash
mvn test-compile org.pitest:pitest-maven:mutationCoverage      # nightly, on the critical packages
mvn test-compile org.pitest:pitest-maven:scmMutationCoverage   # locally or in a PR: only files your change touched
```

> **Aside: there is no `mutationThreshold` in this configuration, on purpose.** A threshold turns mutation testing into another number to game, and because of equivalent mutants, a high threshold can't be met honestly. Let people review the surviving mutants, the way Google does, instead of gating the build on a score. `scmMutationCoverage` needs the POM's `<scm>` section, and the PIT documentation describes how to compare against a base branch in CI.

## Further Reading

- **Brian Marick, "How to Misuse Code Coverage"** (1997). The original warning, and still the clearest statement of what coverage is for.
- **Martin Fowler, "TestCoverage"** (bliki, 2012). A short account of why high coverage says little and low coverage says a lot.
- **Laura Inozemtseva & Reid Holmes, "Coverage Is Not Strongly Correlated with Test Suite Effectiveness"** (ICSE 2014). The study behind the claim, with a careful method.
- **Marko Ivanković et al., "Code Coverage at Google"** (ESEC/FSE 2019), and the Google Testing Blog post **"Code Coverage Best Practices"** (2020). Coverage at scale, the rough guideline numbers, and the focus on changed code.
- **Goran Petrović & Marko Ivanković, "State of Mutation Testing at Google"** (ICSE-SEIP 2018). Mutants on changed lines, shown in code review, with filtering for unhelpful mutants.
- **PIT documentation** (pitest.org), especially the pages on mutators, incremental analysis, and the SCM goal.
- **Stryker Mutator** (stryker-mutator.io). The equivalent tool for JavaScript, TypeScript, and C#, with good introductory material.
- **JaCoCo documentation, "Coverage Counters."** Exactly what each counter measures on the JVM.

A Go sibling would reveal something this article doesn't show. Go's built-in coverage counts only statements. It has no branch coverage, so `if a && b { … }` shows as covered after a single test in which the condition is true. The sibling would show which conclusions that report can't support, and how Go 1.20's coverage for whole compiled binaries (`go build -cover`) lets integration tests contribute to the number. Not yet written.

The habit to take from this: when you look at a test, ask which change to the code would make it fail. If you can't name one, the test only executes the code, and a coverage report can't tell the difference.
