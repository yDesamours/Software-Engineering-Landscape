# Tests That Choose Their Own Inputs: Property-Based Testing and Fuzzing

_Module 21.3c — Testing Strategies_

## The Problem

An invoicing service applies an order-level discount by spreading it across the line items in proportion to each line's value. It has to spread it this way because tax is calculated per line. The function is short:

```go
func Allocate(total int64, weights []int64) []int64 {
	sum := sumOf(weights)
	parts := make([]int64, len(weights))
	for i, w := range weights {
		parts[i] = total * w / sum // integer division: rounds each share down
	}
	return parts
}
```

It has six example tests: `Allocate(1000, [1, 1])` gives `[500, 500]`, `Allocate(900, [1, 2])` gives `[300, 600]`, and so on. The author picked every example so the division comes out exact. All six pass.

A quarter later, finance reconciliation finds that on 0.8% of invoices, the line discounts add up to one or two cents less than the order discount. The tax authority's e-invoicing validator rejects those invoices because the totals don't match. Each invoice has to be corrected by hand.

The same service has a pagination cursor. It's a base64 encoding of `"<created_at_micros>|<id>"`, decoded by splitting on `|` and reading `parts[1]`. Its tests round-trip three cursors and check that one obviously invalid string is rejected. Then a crawler starts sending truncated cursors. Some of them are still valid base64, but they decode to a string with no `|`. Reading `parts[1]` panics, the recovery middleware turns the panic into a `500`, and the crawler retries aggressively. For a week, the on-call engineer's alerts are mostly noise.

Neither bug is exotic. Both occur on inputs the author never chose. Example-based tests check the examples someone thought of, and these bugs were in cases nobody thought of.

## What It Is

Two related techniques move the job of choosing inputs from the author to a tool.

**Property-based testing** comes from QuickCheck (Claessen and Hughes, 2000). You state a **property**, a rule that should hold for *every* input of a given shape. The framework generates many inputs and checks the rule against each one. When one fails, the framework **shrinks** it to the smallest input that still fails, and reports that.

**Coverage-guided fuzzing** starts from a set of seed inputs and repeatedly mutates them. It keeps any mutation that reaches code the tool hasn't reached before, and it runs until a time budget is used up. Fuzzing is best at finding crashes, hangs, and assertion failures in code that parses untrusted input. Go has built-in support for it.

The two are converging. Property-based frameworks increasingly use coverage feedback, and fuzz targets increasingly assert properties beyond "doesn't crash."

The word "fuzz" is sometimes used loosely for "random input." In this article it means the coverage-guided kind. Also, **mutation testing** (21.4) is unrelated despite the similar name. It modifies your *code*, to check whether your tests notice. Fuzzing modifies *inputs*.

## Recognizing the Problem

- Every number in a test was chosen so the arithmetic comes out even.
- Production bugs occur on inputs that make testers say "nobody would send that."
- A function parses, decodes, or deserializes input from outside your system.
- There's an encode/decode pair, and it's tested with only a handful of round trips.
- Money, rounding, dates, or time zones are involved.
- A rewrite needs to behave exactly like the old implementation.
- A data structure or state machine has operations whose order matters.
- A panic or `500` comes from malformed input sent by a client.

## How It Works

### Choosing properties

This is the hard part. A few patterns cover most useful cases:

- **Round trip.** `decode(encode(x)) == x`. Also works for serialize/parse and compress/decompress.
- **Invariants.** A condition that always holds for the output: the parts add up to the total, the output is sorted, no value is negative, the length is unchanged.
- **Oracle, or differential.** Compare the result with a slow, obviously correct implementation, with the old version during a rewrite, or with another library.
- **Metamorphic.** State how outputs relate when the input changes in a known way. Adding a search filter never increases the number of results. Multiplying every weight by the same factor doesn't change the allocation.
- **Idempotence.** Applying the function twice gives the same result as applying it once: `normalize(normalize(x)) == normalize(x)`.
- **No crash.** The function rejects bad input with an error instead of panicking. This is the baseline for fuzzing.

The trap is a property that recomputes the expected result the same way the implementation does. That test agrees with the code whether the code is right or wrong.

Properties also need to be specific enough. "The parts add up to the total" is also true of `[total, 0, 0]`, which is not a proportional allocation.

### Generators and distribution

Plain random integers almost never land on boundaries. Good frameworks deliberately favor edge values such as zero, the maximum, empty collections, and repeated values.

Writing a generator for your domain (valid dates, amounts of money, identifiers, well-formed requests) is where most of the effort goes. A generator is part of the test, and it can hide bugs. If its range is too narrow, integer overflow never happens during testing.

### Shrinking

A failing input might be a 37-element slice of large numbers. Shrinking reduces it to something like `total=1, weights=[1, 1]`, which is small enough to understand at a glance and can be pasted directly into a bug report.

Frameworks with *integrated* shrinking (Hypothesis, rapid) shrink the random choices that produced the value, not the value itself. As a result, the shrunk input still satisfies the generator's constraints.

### Reproducibility

- **Seeds.** Frameworks print the random seed when a test fails.
- **Saved failures.** Failing cases are written to disk and replayed on later runs. Hypothesis keeps a database, rapid writes fail files, and Go writes to `testdata/fuzz/`.
- **Permanent regression tests.** Once you've understood a counterexample, turn it into a named example test so it stays in the suite.

### Stateful, or model-based, testing

Generate *sequences of operations* (put, get, delete, expire) and apply each one to both the real implementation and a trivially simple model, such as a map. After every step, compare the two. This finds bugs that depend on operation order, which example tests almost never reach.

It suits caches, queues, rate limiters (18.1), and state machines.

### How fuzzing works

1. You provide a seed corpus of valid inputs.
2. The engine mutates those inputs, and instrumentation reports which code each mutation reached.
3. Inputs that reach new code are saved and mutated further.

In Go, failing inputs are written to `testdata/fuzz/<FuzzName>/`, and a plain `go test` replays every seed and every saved failure. So once the fuzzer finds a failure, it's a regression test from then on.

The fuzzing itself (`-fuzz`) runs for a time budget, usually on a schedule rather than on every pull request. Services such as OSS-Fuzz and ClusterFuzzLite run fuzzers continuously.

## When It's Appropriate

- **Parsers and decoders of untrusted input:** cursors, webhook payloads (17.2b), uploaded files (11.1a), and query languages. Fuzz them.
- **Serialization and encoding pairs.** Check round trips.
- **Money, rounding, and allocation.** Check invariants. A one-cent discrepancy on 0.8% of invoices is a typical bug this finds.
- **Date and time arithmetic**, including the deadline calculator from 21.2a. Check that deadlines never land on a non-working day, and that a longer budget never gives an earlier deadline.
- **Rewrites and migrations.** Compare the old and new implementations directly.
- **Data structures and state machines.** Use model-based testing.

## When It's Unnecessary or Overkill

- **Glue code and simple CRUD** have no interesting input space.
- **UI layout.**
- **Cases where the only property you can state is the implementation.** Write examples instead.
- **One-off scripts.**
- **Requiring fuzzers everywhere with no time budget.** They consume compute time for code that never sees hostile input.

## Trade-offs

- **Properties are harder to write than examples.** Expect the first few to take a while, and expect some to turn out wrong.
- **Slower tests.** A property typically runs 100 or more cases, so budget for it, or run large case counts on a schedule.
- **Results can differ between runs** unless seeds are logged and failures saved. A test that fails once and never again, with no seed recorded, wastes an afternoon.
- **Generators need maintenance** as the domain changes, and a stale generator silently tests less.
- **Limited reach.** Random inputs rarely reach deep states unless the generator is shaped for them. Coverage guidance helps, but it doesn't fully solve this.
- **Compute cost.** Continuous fuzzing is real CPU time.
- **Readability.** A property test is harder for a newcomer to follow than a table of examples.

## Alternatives

- **Example tables with boundary-value analysis.** Enumerate the edges on purpose. This is cheaper, and it only covers what you thought of.
- **Exhaustive testing of small domains.** Every date in a four-year span is 1,461 cases, and a computer checks them in a fraction of a second.
- **Model checking (TLA+) and formal methods.** Use these for designs, such as protocols and concurrency, not for code.
- **Static analysis.** Linters and type systems catch some of the same bugs, like unchecked indexing and unhandled errors, without running anything.
- **Mutation testing (21.4).** It measures how strong your example suite is instead of generating inputs, and the two work well together.

## How to Achieve It

**Level 0: add one round-trip property** for a serializer or encoder you already have.
_Signal you're here:_ you've never seen a shrunk counterexample.

**Level 1: add invariant properties for money, time, and allocation code.**
_Signal you need it:_ a rounding or boundary bug reaching production.

**Level 2: fuzz the parsers that handle untrusted input.** Commit the seeds and saved failures, and run `-fuzz` on a nightly budget.
_Signal you need it:_ panics or `500`s caused by client input.

**Level 3: add differential tests for rewrites and model-based tests for stateful components.**
_Signal you need it:_ a rewrite in progress, or bugs that depend on the order of operations.

**Level 4: fuzz continuously**, with a triage process for new findings.
_Signal you need it:_ a parser whose failures would be security-relevant.

## Implementation

This section uses Go, which has built-in fuzzing in the standard toolchain. For property-based testing it uses `pgregory.net/rapid`, which provides integrated shrinking.

A property test for `Allocate`, with an invariant plus a check that each part is near its proportional share:

```go
func TestAllocate(t *testing.T) {
	rapid.Check(t, func(t *rapid.T) {
		total := rapid.Int64Range(0, 10_000_000).Draw(t, "total") // cents
		weights := rapid.SliceOfN(rapid.Int64Range(0, 1_000_000), 1, 50).Draw(t, "weights")

		parts, err := Allocate(total, weights)
		sumW := sumOf(weights)
		if sumW == 0 {
			if !errors.Is(err, ErrNoWeight) {
				t.Fatalf("all-zero weights: want ErrNoWeight, got %v", err)
			}
			return
		}
		if err != nil {
			t.Fatalf("unexpected error: %v", err)
		}

		if got := sumOf(parts); got != total {
			t.Fatalf("parts sum to %d, want %d", got, total)
		}
		for i, p := range parts {
			// Exact share is total*w/sumW. Each part must be within one cent of it.
			if d := p*sumW - total*weights[i]; d <= -sumW || d >= sumW {
				t.Fatalf("part %d = %d is more than a cent from its share", i, p)
			}
		}
	})
}
```

Run against the original implementation, the test fails almost at once. Shrinking reduces the failure to a minimal case (output abridged):

```
--- FAIL: TestAllocate
    [rapid] draw total: 1
    [rapid] draw weights: []int64{1, 1}
    parts sum to 0, want 1
```

That is the production bug, shown with the smallest possible input: one cent split between two equal lines disappears. The fix is the **largest remainder method**. Round each share down, then give the leftover cents, one each, to the parts with the largest remainders. After the fix the property passes, and the saved fail file keeps replaying this case.

> **Aside: each check guards against a different wrong implementation.** With only the sum check, `[total, 0, 0, …]` would pass. With only the closeness check, the original truncating version would pass most of the time. Most useful properties are a small set of checks like this, each one ruling out a particular incorrect answer.

> **Aside: the generator's ranges make a claim about your inputs.** `total*weights[i]` stays well within `int64` here only because the ranges keep it there. Widen the weights to the full `int64` range and the test finds an overflow. That might be a real bug, if some caller passes weights in micro-units. Either document the limit and enforce it in `Allocate` by returning an error, or widen the range and fix the arithmetic. Don't let a narrow generator hide the question.

A fuzz target for the cursor decoder, checking both "never panics" and "anything it accepts survives a round trip":

```go
func FuzzDecodeCursor(f *testing.F) {
	f.Add(EncodeCursor(Cursor{CreatedAtMicros: 1_790_000_000_000_000, ID: 42}))
	f.Add("")
	f.Add("%%%")

	f.Fuzz(func(t *testing.T, s string) {
		c, err := DecodeCursor(s) // a panic anywhere in here fails the test
		if err != nil {
			return // rejecting garbage is correct; crashing on it is not
		}
		back, err := DecodeCursor(EncodeCursor(c))
		if err != nil || back != c {
			t.Fatalf("round trip changed %+v into %+v (err: %v)", c, back, err)
		}
	})
}
```

```
$ go test -run='^$' -fuzz=FuzzDecodeCursor -fuzztime=60s ./pagination
--- FAIL: FuzzDecodeCursor
    panic: runtime error: index out of range [1] with length 1
    Failing input written to testdata/fuzz/FuzzDecodeCursor/8b1e0c4a…
    To re-run:
    go test -run=FuzzDecodeCursor/8b1e0c4a…
```

(Output abridged.)

> **Aside: commit `testdata/fuzz/`.** After the fix, a plain `go test ./...` in CI replays that input on every run, without the fuzzing engine. The larger corpus the engine builds up is kept in `GOCACHE` and isn't committed. Only the seeds and the failures belong in the repository.

> **Aside: the round-trip check catches a quieter bug.** A lenient decoder might accept `"12|42x"` by parsing only the leading digits. That doesn't panic, but it means two different strings refer to the same page. A cache keyed on the cursor, or an audit log, would then disagree with itself. Requiring accepted input to round-trip makes "accepted" mean "exactly the kind of cursor we produce."

## Further Reading

- **Koen Claessen & John Hughes, "QuickCheck: A Lightweight Tool for Random Testing of Haskell Programs"** (ICFP 2000). The origin, and still very readable.
- **John Hughes, "Experiences with QuickCheck: Testing the Hard Stuff and Staying Sane"** (2016). Stateful testing applied to real systems, including the famous AUTOSAR and Dropbox case studies.
- **Hypothesis documentation and articles** (hypothesis.readthedocs.io, hypothesis.works). The best practical writing on generators, shrinking, and choosing properties, useful in any language.
- **Scott Wlaschin, "Choosing properties for property-based testing"** (fsharpforfunandprofit.com). A catalogue of property patterns with worked examples.
- **Go documentation, "Go Fuzzing"** (go.dev/doc/security/fuzz). The native fuzzing model, corpus layout, and command-line flags.
- **`pgregory.net/rapid`** documentation. Go property-based testing with integrated shrinking and state-machine support.
- **Fred Hebert, _Property-Based Testing with PropEr, Erlang, and Elixir_ (2019).** The most thorough book on the subject. The chapters on stateful testing are useful regardless of language.
- **OSS-Fuzz** documentation. What continuous fuzzing looks like in practice, and the kinds of bugs it finds.

A TypeScript sibling using fast-check would show something Go handles differently. fast-check's `scheduler` controls the order in which promises resolve, so a property can explore many interleavings of asynchronous operations, for example two form submissions racing against one response. That turns "an async race condition in the UI" into a reproducible, shrunk counterexample, which neither example tests nor Go's race detector give you for JavaScript. Not yet written.

---

The habit to take from this: whenever you choose an example input, ask what rule makes its expected output correct, and whether that rule could be checked across all inputs. Often it can, and a tool will find the inputs you would never have picked.
