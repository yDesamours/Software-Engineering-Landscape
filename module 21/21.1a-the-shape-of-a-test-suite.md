# The Shape of a Test Suite

_Module 21.1a — Testing Strategies_

## The Problem

Two teams build the same kind of product: appointment booking for a chain of physiotherapy clinics. Patients book, reschedule, and cancel. A cancellation made at least 24 hours before the appointment is refunded.

**Team A has 2,300 tests, and they run in 70 seconds.** Every test builds the booking service with mocks for the repository, the payment client, and the clock. The suite has been green for months. In one quarter, two incidents get through it:

- A migration renamed `appointments.starts_at` to `start_time`. One repository method still used the old name. Every test that touched that method mocked the repository, so all of them passed. The cancel endpoint returned 500s for 40 minutes.
- Someone renamed the environment variable for the refund provider's URL in the deploy manifest but not in the code. The code quietly fell back to its default, which was the provider's sandbox. For two days every refund succeeded, in test mode. No customer received any money.

**Team B learned the opposite lesson from an earlier outage.** It has 260 browser tests that drive the real stack in a staging environment. The suite takes 55 minutes, and roughly one run in four fails for a reason unrelated to the change being tested. A typical failure reads:

```
Timeout 30000ms exceeded waiting for locator('#confirm')
```

That message fits a CSS change, a slow staging database, another team's deploy, or a real bug in the refund logic. The refund rule has eleven edge cases: the exact 24-hour boundary, clinic time zone versus patient time zone, partially paid bookings, package deals, and more. Each one is tested by clicking through a whole booking in a browser, at about three minutes per case.

```
Team A                                   Team B

                                         ████████████████████  browser   260
                                                  ██           API        20
                                                  ▏            unit       30
▏ browser   0
▏ real DB   0
████████████████████  mocked unit 2,300

fast, green, blind at every seam         realistic, slow, can't say where
```

Both teams have plenty of tests, and neither suite can quickly answer the question that matters: *is this change safe to ship, and if not, where is the problem?* The number of tests isn't what's wrong. What's wrong is the mix, because each kind of test can only notice certain failures, and each costs something different to run.

## What It Is

A test suite is a portfolio. Each test has a position on a few axes, and no kind of test does well on all of them:

- **Speed:** how long it takes to get an answer.
- **Fidelity:** how much of the real system takes part, such as the real database, real network, real configuration, and real browser.
- **Precision:** how narrowly a failure points at its cause.
- **Determinism:** whether the same code always gives the same result.
- **Resistance to refactoring:** whether the test survives internal changes that don't change behavior. This term comes from Vladimir Khorikov, and it's the axis on which Team A's suite did worst without anyone noticing.

The best-known guide to balancing that portfolio is the **test pyramid**, from Mike Cohn: a broad base of fast, narrow tests, fewer broader tests above them, and only a few end-to-end tests at the top. Other shapes compete with it. Kent C. Dodds's **testing trophy** puts static analysis at the base and puts the most weight on the middle. Spotify's **honeycomb** makes integration tests the bulk of the suite for microservices. The **ice-cream cone** is the name for Team B's shape, the one you get when most of your confidence comes from the top.

These shapes disagree less than they seem to. They use the words "unit" and "integration" to mean different things, and sorting out those words does most of the work.

## Recognizing the Problem

- The fast suite is green, yet bugs reach production at the seams: SQL, serialization, configuration, wiring.
- A refactor that doesn't change behavior breaks dozens of tests.
- Mock setup is longer than the assertions, and the mocks return whatever the test author assumed.
- The slow suite takes long enough that people push without waiting for it, or batch changes to avoid it.
- Re-running a failed pipeline is routine, and it usually passes the second time.
- A failure message says *that* something broke, not *what*.
- One business rule is tested through the browser many times over.
- No one on the team can say how many tests touch the network.

## How It Works

### Scope and size are different axes

People usually treat these as one thing.

**Scope** is how much code a test exercises: one function, one component, or the whole system. Scope determines fidelity and precision.

**Size** is what resources a test is allowed to use. Google's test sizes are the most useful definition:

| Size | Allowed | Typical runtime |
|---|---|---|
| **Small** | One process. No network, no sleeping, no real disk or clock. | Milliseconds |
| **Medium** | One machine. `localhost` networking, a database in a container, multiple processes. | Seconds |
| **Large** | Multiple machines, real networks, deployed environments. | Minutes |

Size determines speed and flakiness, because the sources of nondeterminism (network, timing, shared state) only become available as size grows.

The two axes vary independently. A test can have wide scope and small size: the whole cancellation use case, running in memory with fakes. A test can have narrow scope and medium size: one SQL query against a real Postgres. Once you separate the two, "we need more integration tests" turns into two questions. Do you want more of the system in each test, or more real infrastructure in each test? The answers are often different.

### "Unit test" has two meanings

A **solitary** unit test isolates one class or function and replaces every collaborator with a test double. A **sociable** unit test uses the real collaborators and replaces only the ones that are slow or nondeterministic.

Team A wrote solitary tests of everything, so each test was tied to exactly which collaborator got called and how. The pyramid never required that. A sociable test of "cancel an appointment," using an in-memory store and a fixed clock, is still small. It runs in a millisecond, and it keeps passing when the internals are rearranged. Much of what the trophy calls "integration tests" is this kind of test, which is how the trophy and the pyramid end up closer together than their diagrams suggest.

### Match each class of bug to the cheapest test that can catch it

| Bug class | Cheapest test that catches it | Size |
|---|---|---|
| Refund rule wrong at the 24-hour boundary | Example or property test of the rule (21.3c) | Small |
| Use case wires its own components together incorrectly | Sociable test through the service | Small |
| SQL wrong, column missing, constraint not handled | Repository test against the real engine (21.3a) | Medium |
| Handler skips auth, returns wrong status, emits wrong JSON | HTTP test through the full middleware stack (21.3b) | Small or medium |
| Two services disagree about a payload | Contract test (21.1b) | Small or medium, per side |
| Config, environment, or wiring wrong in the deployed artifact | Smoke test against the deployment | Large |
| A user journey broken in the browser | A few end-to-end journeys (21.3b) | Large |

No row can be replaced by adding more tests from a different row. All of Team A's 2,300 tests were in the first two rows, and both of its incidents came from rows three and six.

The working rule, from Fowler and Vocke's writing on the pyramid, has two parts. First, **push each check down to the lowest level that can catch its class of bug.** Second, **when a high-level test catches something that no lower-level test caught, write the lower-level test**, then ask whether the high-level test still earns its cost. The same assertion shouldn't be repeated at every level. Team B's eleven refund cases belong at the bottom, where they take milliseconds. The browser suite needs one refunded cancellation, to prove the journey is connected.

### Set a feedback-time budget

```
where it runs          budget      what fits in it
──────────────────────────────────────────────────────────────────────
editor / pre-commit    < 30 s      small tests for the packages you touched
pull request           < 10 min    all small and medium tests, contract verification
after merge / deploy   < 30 min    large tests: deployed smoke tests, E2E journeys
scheduled              hours       stress runs, fuzzing (21.3c), mutation runs (21.4)
```

The numbers are examples. What matters is that the budgets come first and the shape of the suite follows from them. Feedback that arrives after the developer has switched to something else gets ignored, or it pushes people to batch changes into larger and riskier PRs. If the PR stage takes 40 minutes, the portfolio is telling you something is too high in the pyramid.

### Why the top has to stay small

Flakiness multiplies. Suppose each browser test passes 99.9% of the time on unchanged code. The whole suite passes only when all of them pass:

```
0.999 ^ 260  ≈  0.77      about one run in four fails for no reason
```

That is Team B's experience, and no single test is badly flaky. Precision also gets worse toward the top, because a large test has many possible causes for any failure. A small number of large tests is a practical requirement for a suite that people keep believing. Module 21.5 covers the flakiness side in detail.

## When It's Appropriate

Thinking about the suite as a portfolio pays off once shipping a wrong change costs something real, or once CI time does.

- **Domains dense with logic**, such as pricing, scheduling, eligibility, and billing, suit a bottom-heavy shape. Eleven refund cases at 2 ms each take 22 ms. Through a browser, the same cases take 33 minutes.
- **Thin services whose logic lives in SQL** suit the trophy or honeycomb shape. The unit worth testing is the query, so medium tests against the real engine form the base.
- **Many services owned by different teams** should use contract tests to replace most cross-service end-to-end tests. Otherwise the top of the pyramid grows with every new integration.
- **Products with a lot of UI and a thin backend** get the most value from component tests in the middle.

## When It's Unnecessary or Overkill

- **Target ratios enforced by counting**, such as "70% unit, 20% integration, 10% E2E." The shape is a diagnostic tool, and counting tests treats a thousand trivial tests as worth more than one test that matters.
- **A prototype with no users.** Two broad tests may be all it needs. Portfolio thinking starts to matter when a mistake has a real cost.
- **Building a staging end-to-end environment before any journey is worth protecting.** That environment has an operating cost from the first day.
- **Rewriting a working suite to match a diagram.** If the suite catches what you ship wrong and fits your feedback budget, its shape is fine.

## Trade-offs

- **Several test harnesses to maintain.** Each level has its own tooling, setup, and approach to test data, and each is one more thing a new engineer has to learn.
- **Gaps between levels.** Each level assumes the one below it is correct. Bugs hide in those assumptions, for example a fake that behaves differently from the real dependency. Module 21.2b covers the fix.
- **More low-level tests means more coupling to structure.** Solitary tests especially must be updated whenever the design changes, and that cost grows with the size of the base.
- **Fewer end-to-end tests means some bug classes are found only in production.** You need monitoring and canary releases to cover that risk (Modules 19 and 30.2).
- **Classifying tests takes ongoing work.** Deciding sizes is easy. Keeping a "small" test from quietly opening a socket requires tooling.

## Alternatives

Other sources of confidence change how much each layer has to carry, but none of them replaces the portfolio.

- **Static types and static analysis** remove entire categories of bugs at no runtime cost. That's why they form the base of the trophy.
- **Testing in production** means canary releases, synthetic monitoring, and feature flags. These give real confidence from real traffic, and the cost is that some users see a bug before you do.
- **Manual exploratory testing** finds what nobody thought to automate. It works best as a supplement to automation, not something automation replaces.
- **Formal methods** apply to small, critical cores such as a consensus protocol or an allocation invariant, where exhaustive reasoning is worth the effort.

## How to Achieve It

**Level 0: take inventory.** Label every test with its size. Measure runtime and failure rate for each size. List the last ten bugs that reached production, and for each one, note the level that should have caught it.
_Signal you're here:_ nobody can say how many tests touch the network.

**Level 1: make small tests actually small.** Inject the clock and the random source. Allow no network. Set a timeout that fails any small test that runs slowly.
_Signal you need it:_ the "unit" suite takes minutes, or fails when your laptop is offline.

**Level 2: add medium tests at the seams your production bugs came through.**
_Signal you need it:_ your list of escaped bugs is mostly SQL, serialization, and configuration.

**Level 3: prune and push down.** Each large test must protect a user journey. Move rule checks to lower levels.
_Signal you need it:_ top-level failures that nobody can pin down, or a PR stage that exceeds its budget.

**Level 4: enforce sizes mechanically.** Use build tags, separate CI jobs, per-stage timeouts, and an alert when a stage goes over budget.
_Signal you need it:_ tests drifting to a larger size than they're labeled, such as a small test that opens a connection.

## Implementation

This section uses Go, because the standard library already has vocabulary for the ideas above: build tags, `httptest`, and per-run timeouts.

First, the same behavior tested at two scopes. Both tests are small.

```go
// Narrow scope: the rule itself. Adding a table row costs almost nothing, so every edge case belongs here.
func TestRefundPolicy(t *testing.T) {
	start := time.Date(2026, 11, 3, 9, 0, 0, 0, time.UTC)
	cases := []struct {
		name     string
		cancelAt time.Time
		want     Refund
	}{
		{"well ahead", start.Add(-72 * time.Hour), FullRefund},
		{"exactly 24h before", start.Add(-24 * time.Hour), FullRefund},
		{"one second inside 24h", start.Add(-24*time.Hour + time.Second), NoRefund},
		{"after the start", start.Add(time.Minute), NoRefund},
	}
	for _, tc := range cases {
		t.Run(tc.name, func(t *testing.T) {
			if got := RefundFor(start, tc.cancelAt); got != tc.want {
				t.Fatalf("got %v, want %v", got, tc.want)
			}
		})
	}
}

// Wide scope: real router, middleware, handler, and service, all in one process with no socket.
func TestCancelEndpointRefunds(t *testing.T) {
	store := memstore.New() // in-memory fake, checked against Postgres elsewhere (21.2b)
	payments := &paymentsSpy{}
	now := time.Date(2026, 11, 1, 9, 0, 0, 0, time.UTC)
	appt := store.MustCreate(Appointment{StartsAt: now.Add(48 * time.Hour), PaidCents: 6000})

	router := NewRouter(NewService(store, payments, func() time.Time { return now }), fakeAuth("patient-1"))
	rec := httptest.NewRecorder()
	router.ServeHTTP(rec, httptest.NewRequest(http.MethodPost, "/appointments/"+appt.ID+"/cancel", nil))

	if rec.Code != http.StatusOK {
		t.Fatalf("status %d: %s", rec.Code, rec.Body)
	}
	if got := payments.RefundedCents(appt.ID); got != 6000 {
		t.Fatalf("refunded %d, want 6000", got)
	}
}
```

> **Aside: `ServeHTTP` on a recorder, not `httptest.NewServer`.** `NewServer` opens a real socket on `localhost`, which makes the test medium-sized by the definition above. Calling the handler directly exercises the same routing and middleware without the socket. That one-line choice moves a test to a different size class.

> **Aside: the "exactly 24h before" row is the one people forget.** That boundary is where `<` and `<=` differ. Module 21.4 comes back to it, because a suite can execute this line without ever checking it.

> **Aside: the wide test catches neither of Team A's incidents.** It proves that the pieces inside the process fit together. The renamed column needs a medium test, and the wrong refund URL needs a large one. The sociable test is valuable, but it belongs to a different row of the table.

Second, sizes enforced by the build rather than by convention:

```go
//go:build integration

package store_test // compiled only with: go test -tags=integration

func TestAppointmentRepository(t *testing.T) { /* real Postgres in a container, real migrations (21.3a) */ }
```

```go
//go:build smoke

package smoke_test // runs against a deployed environment, after each deploy

func TestRefundProviderIsLive(t *testing.T) {
	info := getJSON(t, os.Getenv("BASE_URL")+"/internal/buildinfo")
	if info["payments_mode"] != "live" {
		t.Fatalf("production is talking to the payment provider in %q mode", info["payments_mode"])
	}
}
```

```
pre-commit     go test -timeout 30s ./...
pull request   go test -tags=integration -timeout 10m ./...
after deploy   BASE_URL=https://… go test -tags=smoke ./smoke/...
```

> **Aside: the smoke test checks what actually went wrong.** Team A's configuration incident could only be seen from the deployed artifact, so the check runs against the deployed artifact and asserts the exact fact that was wrong. A smoke test that only checks for `200 OK` on `/health` would have passed throughout those two days. Each large test should earn its cost by checking something no smaller test can see.

The `-timeout` on the first line is a blunt enforcement tool. It applies to each package's whole test binary, so a supposedly small test that quietly waits on the network makes the pre-commit run fail. `testing.Short()` is the other common convention. It works too, but it depends on each test remembering to check it.

## Further Reading

- **Mike Cohn, _Succeeding with Agile_ (2009).** The origin of the test pyramid, in the chapter on test automation.
- **Ham Vocke, "The Practical Test Pyramid"** (martinfowler.com, 2018). The most thorough practical treatment, including the rules for pushing tests down and avoiding duplication.
- **Martin Fowler, "UnitTest"** (bliki). The solitary/sociable distinction, and why "unit" was never well defined.
- **Titus Winters, Tom Manshreck & Hyrum Wright (eds.), _Software Engineering at Google_ (2020), ch. 11, "Testing Overview."** Test size versus test scope, and the reasoning behind Google's size limits.
- **Kent C. Dodds, "The Testing Trophy and Testing Classifications"** (kentcdodds.com). The case for weighting the middle, and a useful account of why the categories are confusing.
- **André Schaffer, "Testing of Microservices"** (Spotify Engineering, 2018). The honeycomb, and why a thin service's "unit" is often an integration.
- **Mike Wacker, "Just Say No to More End-to-End Tests"** (Google Testing Blog, 2015). The feedback-loop argument against an ice-cream-cone suite, with numbers.
- **Vladimir Khorikov, _Unit Testing Principles, Practices, and Patterns_ (2020).** The four properties of a good test, including resistance to refactoring, and an extended argument for testing observable behavior.

A Java sibling would add something here. Maven's Surefire and Failsafe plugins run unit tests and integration tests in different lifecycle phases, with different naming conventions, so the build tool itself encodes a two-level pyramid. It's worth seeing how that helps (a medium test can't slip into the fast phase by accident) and how it gets in the way (there's no natural place for large tests). Not yet written.

---

The habit to take from this: when a bug reaches production, ask which is the *cheapest* test that could have caught it, and write that one. Don't ask whether you have enough tests. Over time, answering the first question gives you a suite whose shape reflects the failures your system actually has, which no diagram can do.
