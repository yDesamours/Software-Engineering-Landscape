# Tests That Touch the Database

_Module 21.3a — Testing Strategies_

## The Problem

An inventory service for a chain of warehouses runs on Spring Boot and JPA, with Postgres 16 in production. Its tests run against H2 in PostgreSQL compatibility mode, with the schema created from the entity classes (`ddl-auto=create-drop`). There are 1,100 tests, they take three minutes, and they pass.

Over one quarter, three production incidents turn out to be database problems:

- **A constraint that didn't exist in tests.** A Flyway migration added a partial unique index, `ON reservation (order_line_id) WHERE status = 'active'`. The test schema came from the entities, not the migrations, so the index wasn't there. The code that catches the violation and returns `409 Conflict` had never run. During a flash sale it returned 500s instead.
- **An oversell.** The query that allocates the last unit of stock read the row without locking it. Two concurrent reservations both succeeded, and over one weekend the warehouse promised 212 units it didn't have. The test "can't reserve more than is on hand" passed, because it ran its two reservations one after the other, inside a single transaction.
- **A query that was never tested.** A `jsonb` query, `attributes @> '{"hazmat": true}'`, couldn't run on H2, so its test was annotated `@Disabled("H2 doesn't support jsonb")`. The query had a typo in the key, `hazmats`, and had returned nothing since the day it was written.

The team switches to a shared Postgres instance in the development cluster. The escaped bugs stop, and a new problem starts:

- Concurrent CI jobs share the same database.
- Tests pass on their own and fail when run together.
- Rows left behind by one run break assertions in the next.
- A developer's local run truncates a table while CI is using it.

Fixing fidelity created an isolation problem.

## What It Is

The practice is to test data-access code **against the same database engine, version, and schema as production**, in a **throwaway instance that belongs to the test run**, with a **deliberate strategy for keeping each test's data separate**.

The most common tool is **Testcontainers**. From your test code, it starts a real database in a container, tells the tests how to connect, and removes the container when the run ends.

In 21.1a's terms, these are *medium-sized* tests with a *narrow* scope. The scope might be a single query, but the engine running it is the real one.

## Recognizing the Problem

- Tests use a different database engine or major version than production.
- The test schema is built differently from production's, for example by ORM auto-DDL instead of migrations.
- Some tests are `@Disabled` or skipped because the test database can't run the query.
- Repository tests replace the database with a double.
- Tests fail when run in a different order or in parallel, or pass only when run alone.
- CI jobs share one database.
- Production bugs involve constraints, locking, JSON, collation, time precision, or migrations.

## How It Works

### Fidelity: engine, version, schema, settings

- **Use the same engine and version as production.** Pin the container image tag to production's version (`postgres:16.4`, not `postgres:latest`), and upgrade both together.
- **Build the schema from the real migrations.** Never let the ORM generate it. The tests then also check your migrations. With `ddl-auto=validate`, startup fails whenever the entities and the schema disagree.
- **Match production's extensions and settings**, such as `pg_trgm`, time zone, and collation.
- **Know what a container still won't reproduce.** Managed-service features (IAM authentication, parameter groups), replica lag and failover, and production data volumes are all missing. Data volume matters most, because query plans depend on table statistics, so a query that's fast on 40 rows can still be slow in production (22.3).

### Lifecycle: one container per run, not per test

A Postgres container starts in one to three seconds. Migrations take longer as they accumulate. Start the container once per test JVM, run the migrations once, and share the database across all test classes. A container per test gives the strongest isolation, but it's far too slow for a suite with hundreds of tests.

### Isolation: five strategies

This choice shapes everything else in the suite.

**1. Roll back each test's transaction.** This is Spring's default for `@Transactional` tests and for `@DataJpaTest`. It's fast and needs no cleanup. It has specific blind spots:

- Code that commits on its own (`REQUIRES_NEW`, `TransactionTemplate`) escapes the rollback.
- Work on another connection or thread, such as async listeners, concurrency tests, or `SKIP LOCKED`, can't see the test's uncommitted data.
- Anything that happens *at commit* never happens. That includes deferred constraints, `@TransactionalEventListener(AFTER_COMMIT)`, and commit-time triggers.
- The persistence context stays open for the whole test. So a lazy load that throws `LazyInitializationException` in production works fine in the test. And if nothing flushes, no SQL reaches the database, so a constraint violation never fires.

The last point produces a whole category of tests that pass only because nothing was ever written to the database.

**2. Commit, then clean up.** After each test, truncate the tables it used (`TRUNCATE … RESTART IDENTITY CASCADE`). Commits are real, and so are separate connections. It costs tens of milliseconds per test, and tests in the same database have to run one at a time.

**3. Give each test its own data.** Each test creates its own tenant or IDs and only asserts on those, for example "count where tenant = mine." No cleanup is needed and tests can run in parallel. The cost is that every assertion must be scoped to the test's own data, and tables grow during the run. That's fine for a database that gets thrown away afterwards.

**4. A database per worker, copied from a template.** Migrate once into `app_template`, then have each parallel worker run `CREATE DATABASE worker_3 TEMPLATE app_template`. Postgres copies the files, which is fast for a small schema. No one can be connected to the template while it's being copied. Each worker ends up with a database to itself.

**5. A container per test class.** Use this for tests that change server-wide state, such as roles, settings, or extensions.

Most suites combine these: rollback for simple repository reads and writes, commit plus truncate for concurrency and commit-listener tests, and per-test data or template databases once the suite runs in parallel. Choose deliberately for each test class. Don't let the framework default choose for you.

### Test data: builders instead of shared fixtures

A shared seed file ties every test to rows it didn't create. Change one row and unrelated tests break. Instead, have each test create the rows it needs, using builders with sensible defaults: `aLot().sku("SKU-1").onHand(1).build()`. The test then states exactly the data its assertion depends on.

### Speed settings for a throwaway database

`fsync=off`, `synchronous_commit=off`, `full_page_writes=off`, and a data directory on `tmpfs` together remove most of the write cost. Any of these would be unsafe for real data. Here the database is deleted within minutes, so they're the right choice.

Locally, `testcontainers.reuse.enable=true` keeps the container running between runs. The downside is that state also persists between runs, so tests must not depend on starting from an empty database.

### Other infrastructure works the same way

- **Redis.** Atomic scripts and TTL behavior can't be convincingly faked with a mock. This is the Module 18.2a handoff: run the limiter's Lua against a real Redis.
- **Kafka and RabbitMQ.** Real brokers exercise serialization, partitioning, and redelivery.
- **Object storage.** MinIO provides an S3-compatible API.
- **Cloud services.** Emulators such as LocalStack implement the API. How faithfully they reproduce edge behavior (limits, consistency, error codes) varies from service to service.

### What CI needs

The test process needs access to a Docker-compatible runtime. Some hosted runners and Kubernetes-based CI need Docker-in-Docker or a remote Docker daemon. Testcontainers Cloud is a hosted option. Pull images through a registry mirror so that public registry rate limits don't make your builds flaky.

## When It's Appropriate

- **Repository code that uses engine-specific SQL**, such as `jsonb`, upserts, window functions, `SKIP LOCKED`, partial indexes, and full-text search (12.1a).
- **Migrations**, including checking that the entities still match the schema.
- **Concurrency guarantees**, such as preventing overselling, enforcing uniqueness under load, or claiming a job exactly once.
- **Behavior that happens at commit**, such as transactional event listeners and the outbox pattern (Module 37).
- **Any team whose production bugs involve constraints, locking, or SQL.**

## When It's Unnecessary or Overkill

- **Pure domain logic.** It doesn't touch the database, so its tests shouldn't either (21.1a).
- **Service-layer tests, when a verified fake covers the store (21.2b).** The database belongs in the contract suite, not in every test.
- **A test for every derived `findByX` method.** Test a representative few, plus every hand-written query.
- **Starting Kafka to check that a message was published.** A spy on your own publisher interface answers that question. Save the real broker for serialization and delivery behavior.

## Trade-offs

- **Slower.** Startup takes seconds, and each query takes milliseconds instead of microseconds. A suite that used to finish in three minutes may now take seven.
- **Docker is required** on every developer machine and every CI runner. Some environments restrict it.
- **The isolation strategy affects how tests are written.** Scoped assertions, commit-mode cleanup, and choosing a strategy per test class are all extra work.
- **Parallel execution takes deliberate effort.** Template databases or per-test data don't set themselves up.
- **A container is still not the managed production database**, and it doesn't have production's data volume.
- **Image drift.** An unpinned tag lets the test engine change version without anyone noticing.
- **Resource-related flakiness.** On overloaded CI runners, container startup can time out (21.5).

## Alternatives

- **In-memory engines (H2, SQLite).** They're fast, and they're a different engine. They're acceptable only if the application uses a strictly portable subset of SQL and you accept the risk that brings.
- **Embedded Postgres binaries** (for example, zonky's `embedded-postgres`). A real engine without Docker, at the cost of a platform-specific binary.
- **A shared test database with a schema per run.** Cheaper than containers, as long as every run really does get its own schema.
- **Database branching services**, which create a copy-on-write branch per pipeline. Useful for preview environments and for tests that need production-like data.
- **Verified fakes (21.2b)** for everything above the repository layer.
- **Testing query plans separately** against production-like data volumes (22.3). This catches what a small test database can't.

## How to Achieve It

**Level 0: count your database-related escapes** and your `@Disabled`-for-H2 tests.
_Signal you're here:_ the Problem sounds familiar.

**Level 1: run one container with real migrations and `ddl-auto=validate`.** Start with repository tests only.
_Signal you need it:_ that list of escapes.

**Level 2: choose an isolation strategy for each test class.** Add commit-mode tests for concurrency and commit listeners.
_Signal you need it:_ code that commits on its own or does work asynchronously.

**Level 3: run in parallel**, using per-test data or template databases.
_Signal you need it:_ the medium-test stage exceeds its PR time budget (21.1a).

**Level 4: tune the database for speed** (tmpfs, `fsync`), reuse containers locally, and keep the image tag in one property that matches production.
_Signal you need it:_ startup and write time dominate the stage.

**Level 5: apply the same approach to Redis and your message broker.**
_Signal you need it:_ production bugs coming from those systems.

## Implementation

This section uses Java with Spring Boot and JUnit 5. Testcontainers started in the Java ecosystem, and Spring's transactional test support is exactly where the rollback blind spots show up.

A container shared by the whole run, started once per JVM:

```java
public abstract class PostgresTest {

  static final PostgreSQLContainer<?> POSTGRES =
      new PostgreSQLContainer<>(DockerImageName.parse("postgres:16.4"))      // same version as production
          .withTmpFs(Map.of("/var/lib/postgresql/data", "rw"))
          .withCommand("postgres", "-c", "fsync=off", "-c", "synchronous_commit=off", "-c", "full_page_writes=off");

  static {
    POSTGRES.start();   // once per JVM; Testcontainers removes it when the JVM exits
  }

  @DynamicPropertySource
  static void datasource(DynamicPropertyRegistry registry) {
    registry.add("spring.datasource.url", POSTGRES::getJdbcUrl);
    registry.add("spring.datasource.username", POSTGRES::getUsername);
    registry.add("spring.datasource.password", POSTGRES::getPassword);
    registry.add("spring.jpa.hibernate.ddl-auto", () -> "validate");   // Flyway builds the schema, Hibernate only checks it
  }
}
```

> **Aside: a static field, not a `@Container` field on each class.** A container declared per test class starts again for every class. A single static field is shared by every Spring test context in the JVM, whether it comes from `@DataJpaTest` or `@SpringBootTest`, so the whole suite starts one database and runs Flyway against it once. On Spring Boot 3.1 and later, `@ServiceConnection` can replace the `@DynamicPropertySource` block for a single class. The static-field approach is what keeps one container shared across the whole suite.

A rollback-mode repository test, for the query that used to be disabled:

```java
@DataJpaTest
@AutoConfigureTestDatabase(replace = Replace.NONE)   // never swap in an embedded database
class StockLotRepositoryTest extends PostgresTest {

  @Autowired StockLotRepository lots;
  @Autowired TestEntityManager em;

  @Test
  void findsHazmatLotsByAttribute() {
    em.persist(aLot().sku("SKU-1").attributes(Map.of("hazmat", true)).build());
    em.persist(aLot().sku("SKU-2").attributes(Map.of("hazmat", false)).build());
    em.flush();   // send the SQL now: constraints fire, and the native query sees the rows

    assertThat(lots.findHazmat()).extracting(StockLot::sku).containsExactly("SKU-1");
  }
}
```

> **Aside: `flush()` matters.** In rollback mode, nothing reaches Postgres until something flushes. A test that persists an entity violating a unique index, and never flushes, passes. Flushing explicitly makes the test send the same SQL that production sends.

A commit-mode concurrency test, for the oversell:

```java
@SpringBootTest
class ReservationConcurrencyTest extends PostgresTest {

  @Autowired ReservationService reservations;
  @Autowired StockLotRepository lots;
  @Autowired JdbcTemplate jdbc;

  @AfterEach
  void cleanUp() {
    jdbc.execute("TRUNCATE reservation, stock_lot RESTART IDENTITY CASCADE");
  }

  @RepeatedTest(20)   // deliberately not @Transactional: each attempt commits on its own connection
  void theLastUnitCanOnlyBeReservedOnce() throws Exception {
    lots.save(aLot().sku("SKU-1").onHand(1).build());

    var start = new CountDownLatch(1);
    Callable<Boolean> attempt = () -> { start.await(); return reservations.tryReserve("SKU-1", 1); };

    try (var pool = Executors.newFixedThreadPool(2)) {
      var a = pool.submit(attempt);
      var b = pool.submit(attempt);
      start.countDown();
      assertThat(List.of(a.get(), b.get())).containsExactlyInAnyOrder(true, false);
    }
  }
}
```

> **Aside: this is the test the original suite couldn't write.** With `@Transactional` on the test, both attempts would run in the test's own transaction, on one connection, and they could never race. Removing that annotation means two real transactions compete, so cleanup has to be done by hand. That's why this class truncates its tables and the previous one doesn't.

> **Aside: a concurrency test is probabilistic, so repeat it.** Without the row lock, the two threads still sometimes run one after the other by chance, and the test passes. `@RepeatedTest(20)` makes a real race very likely to appear at least once. When this test fails in one run out of thirty, it isn't flaky. It's catching the bug one time in thirty. Module 21.5 explains how to tell those two cases apart. The fix itself is a `SELECT … FOR UPDATE` on the stock row, or a conditional `UPDATE stock_lot SET on_hand = on_hand - 1 WHERE sku = ? AND on_hand >= 1`, which reserves only if a row was actually updated.

## Further Reading

- **Testcontainers for Java documentation** (java.testcontainers.org), especially "Singleton containers," the JDBC module, and reusable containers.
- **Spring Boot reference documentation, "Testing," the sections on test slices and Testcontainers support** (`@DataJpaTest`, `@AutoConfigureTestDatabase`, `@ServiceConnection`).
- **Spring Framework reference documentation, "Transaction Management" in the testing chapter.** The rollback default, how to turn it off, and the note on false positives from unflushed state.
- **PostgreSQL documentation, "Template Databases"** and **"Non-Durable Settings."** The two Postgres features this article relies on for isolation and speed.
- **Martin Fowler, "IntegrationTest"** (bliki, 2018). Narrow versus broad integration tests. This article is entirely about the narrow kind.
- **Vladimir Khorikov, _Unit Testing Principles, Practices, and Patterns_ (2020), ch. 10, "Testing the database."** A careful treatment of isolation strategies and test data.

A Go sibling would reveal something this article hides. `go test ./...` runs each package's test binary as a separate process, in parallel, by default. A shared database therefore fails in Go under default settings, whereas a single Maven Surefire JVM runs test classes one after another and can get away with it. Isolation becomes mandatory from the start, and the idiomatic solution is template databases created with `t.Cleanup`. Not yet written.

---

The habit to take from this: every time a test swaps a piece of real infrastructure for a stand-in, write down which of that infrastructure's behaviors your code depends on, and check that the stand-in reproduces each one. Most bugs that get past a green database suite involve a behavior nobody listed.
