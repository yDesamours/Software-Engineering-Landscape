# Tests in CI and the Flaky-Test Problem

_Module 21.5 — Testing Strategies_

## The Problem

A product team shares one repository that holds a web app and six services. It has 11,000 tests, and the pipeline takes 42 minutes. Some other numbers from the team:

- On `main`, 27% of pipelines fail even when no relevant code changed.
- The median pull request runs the pipeline 2.6 times before it merges.
- "Re-run failed jobs" is the most-clicked button in the CI interface.
- A Slack channel called `#known-flakes` has 400 messages. Most of them say "that one again."

One of those known flakes is `checkout › applies a coupon only once`. It failed about one run in forty, for three weeks. Everyone re-ran it, and it passed on the re-run.

The test was catching a real bug. If a customer submitted the order form twice quickly, both requests passed the "coupon already used?" check before either one recorded the coupon. The race shipped. Over one weekend, 2,300 orders received the discount twice.

Some other things nobody could answer at the time:

- **Which tests are flaky?** The Slack channel was the only list.
- **Why did a job fail?** The test report was an 18,000-line log. A failure in shard 3 of 8 appeared only as "job failed."
- **Is `main` actually broken?** It was red often enough that red no longer meant anything.

The arithmetic explains why this happens even when no individual test is bad:

```
tests that each fail 1 time in 1,000    pipeline green on unchanged code
                  10                             99%
                 100                             90%
                 300                             74%
               1,000                             37%
```

A pipeline passes only if every test passes, so the chances multiply. A large suite of mostly reliable tests still produces a pipeline that fails often. Once people learn that a failure usually means nothing, they stop reading failures, including the ones that matter.

## What It Is

This article covers two practices that depend on each other:

- **Running tests in CI.** What runs at which stage, how the work is split across machines, how much of the suite each change runs, and how results are reported.
- **Managing flaky tests.** A flaky test passes and fails on the same code. Managing flakes means detecting them, containing them, and fixing them, with a policy that stops the team from getting used to failures.

A flaky test is different from a **broken** test, which fails every time. It is also different from a **flaky product**, where the nondeterminism is in the system itself, as with the coupon race.

A flaky result tells you that something is nondeterministic. It doesn't tell you where. The cause can be in the test, the environment, or the code under test, and the triage process has to rule out the code first.

## Recognizing the Problem

- Re-running failed jobs is a habit, and people rarely read the failure first.
- Fewer than about 90% of pipelines on unchanged `main` pass.
- The team has a shared list of "known flaky" tests, and nobody owns them.
- Retries are configured, and nobody records which tests needed one.
- Some failures can't be reproduced locally.
- The same suite's run time varies widely from run to run.
- A test fails differently when run alone than when run with the others.
- You can't name the flakiest test without searching chat history.

## How It Works

### Stages by feedback budget

Section 21.1a set the budgets. In CI they turn into stages:

- **Fast checks** run first: lint, type checks, small tests.
- **Medium tests and contract verification** run on the pull request.
- **Large tests** run after merge or after deploy.

Within a stage, run the fastest tests and the tests most likely to fail first. Developers then learn about a likely failure in minutes instead of at minute 40.

### Parallelism and sharding

Split the suite across machines using **historical timing data**, not file counts. Test files vary enormously in how long they take, so equal file counts give unequal shards, and the slowest shard sets the wall-clock time.

Sharding also works as a test of isolation. Tests that quietly depend on running in a particular order, or on sharing state, start failing once they're split up. Treat those failures as bugs in the test (21.3a, 21.3b), not as a problem with sharding.

### Running less: impact analysis

On pull requests, run only the tests affected by the change, using the dependency graph. Tools include `nx affected`, Bazel, Gradle's build cache, Jest's `--changedSince`, and Go's test result cache.

The risk is **dependencies the graph doesn't know about**: config files, SQL migrations, fixtures, and environment variables. The standard backstop is to run the whole suite on `main` and on a schedule, so anything impact analysis skipped is caught within hours.

### Merge queues

Two pull requests can each pass on their own and still break `main` when combined. A merge queue tests each pull request against the latest `main` plus everything ahead of it in the queue. GitHub calls this a merge queue, and GitLab calls it merge trains.

It costs extra time and compute for every merge. In exchange, `main` stays green, which is what makes a red `main` meaningful.

### Reporting

- **Use JUnit XML** as the common output format. Nearly every test runner and CI system reads and writes it.
- **Put failures on the pull request.** Show the failing test's name and first error line on the PR itself, not only in a job log.
- **Keep per-test history:** duration, outcome, number of attempts, and commit. Flaky tests can't be detected without it. This is the piece most often missing.
- **Link artifacts from the failure:** logs, traces, and screenshots (21.3b).

One caveat: many JUnit reporters don't record retry attempts. Check what yours does before relying on it for flake data.

### Where flakiness comes from

Luo et al. (2014) analyzed flaky tests in open-source projects. The three most common causes were asynchronous waits, concurrency, and dependence on test order.

| Cause | Typical fix |
|---|---|
| Waiting a fixed time instead of for a condition | Wait for the condition (21.3b) |
| Concurrency: a race in the test, or in the product | Find out which. A race in the product is a bug. Use race detectors and stress runs. |
| Dependence on test order: shared state, static variables, leftover rows | Isolate the test (21.3a). Randomize order to expose the dependence. |
| Time: dates, time zones, DST, midnight | Inject the clock (21.2b) |
| Unseeded randomness | Seed it and log the seed (21.3c) |
| Network calls and external services | Replace them with doubles (21.2b) or cover them with contract tests (21.1b) |
| Resource limits: fixed ports, open file handles, an overloaded CI runner | Use dynamic ports, clean up, set timeouts sized for CI |
| Unordered results: map iteration, SQL without `ORDER BY` | Assert without depending on order, or specify the order |
| Platform differences: floating point, filename case, locale | Pin the environment |

Google has published numbers on this. Micco (2016) reports that about 1.5% of all test runs gave a flaky result, and about 16% of tests showed some level of flakiness. Listfield (2017) found that larger tests, measured by binary size and memory use, were more likely to be flaky. That matches the pyramid argument in 21.1a.

### Detecting flaky tests

- **Pass on retry.** A test that fails and then passes on the same commit is flaky by definition. Record every occurrence. This signal is free, and most teams throw it away.
- **Failures that clear on their own.** In `main`'s history, look for failures that go away on the next commit even though that commit changed nothing related.
- **Deliberate stress runs** on a schedule: run the suite many times, randomize the order, run under CPU load, and run with race detectors enabled. Don't do this on every pull request.

### A policy that works

1. **Use retries to detect flakes, not to excuse them.** One retry keeps the pipeline moving. Every pass-on-retry gets recorded against the test ID and commit.
2. **Quarantine known flakes.** A quarantined test still runs, but its failures don't block merges. Each quarantine entry has an **owner**, an **issue**, and an **expiry date**.
3. **Enforce the expiry.** When an entry expires, someone has to fix the test, delete it, or deliberately renew the quarantine. Letting it sit is not an option.
4. **Check the product first.** Before treating a flake as a test problem, rule out a real bug. The coupon test was the only thing reporting the race.
5. **Track a reliability target**, for example "95% of `main` pipelines pass on the first attempt," and review it the way you would any other service-level objective.

Quarantine has a real downside. A quarantined test no longer blocks anything, including a genuine regression that happens to make it fail. Keep quarantines short, cap how many tests can be quarantined at once, and alert when a quarantined test's failure rate changes sharply. A test that goes from failing 1 run in 40 to failing every run is telling you something new.

## When It's Appropriate

- **Suites over about 10 minutes, teams over about 20 engineers, or `main` passing less than 90% of the time.** The whole policy pays for itself here.
- **Many services in one repository.** Impact analysis and timing-based sharding save the most time.
- **High merge rates.** Merge queues are worth their added delay once pull requests regularly break each other.
- **Any team that retries tests**, which needs pass-on-retry recording from the first day.

## When It's Unnecessary or Overkill

- **A five-minute suite and four engineers.** Fix each flake when it appears. A quarantine system with expiry dates is more process than the problem needs.
- **Impact analysis in a small repository.** Maintaining the dependency graph costs more than running everything.
- **A custom flake dashboard when your CI provider already offers one.**
- **A merge queue when merges are rare.** The queue adds delay and prevents very little.

## Trade-offs

- **Retries hide nondeterminism in the product** unless every pass-on-retry is recorded and looked at.
- **Quarantine reduces coverage** of whatever the quarantined test protected.
- **Sharding costs** extra compute and orchestration, and shards need rebalancing as tests change.
- **Impact analysis can skip tests that should have run**, which is why a full-suite backstop is required.
- **Merge queues add delay** to every merge.
- **History needs storage.** Per-test results over time need somewhere to live and someone to maintain them.
- **Process has a cost.** Owners, expiry dates, and reliability targets take attention. Without them, the quarantine list only grows.

## Alternatives

- **Hermetic builds** (Bazel and similar). Environment-caused flakes become much rarer, and impact analysis becomes precise. Adoption is expensive.
- **Moving tests down the pyramid (21.1a).** The most effective fix, because small tests have far fewer sources of nondeterminism.
- **Running large tests after merge, without blocking**, with alerts on failure. Their flakiness stops blocking developers, and their findings arrive later.
- **Deleting tests** that cost more attention than the risk they protect against. This is legitimate, as long as someone decides it deliberately.
- **Flaky-test features in CI and test-analytics tools.** Several vendors detect and quarantine flaky tests automatically. The policy questions above still apply.

## How to Achieve It

**Level 0: measure.** Track `main`'s first-attempt pass rate, how often jobs are re-run, and which tests fail most.
_Signal you're here:_ the Problem's numbers are estimates or unknown.

**Level 1: publish JUnit reports, show failures on the pull request, and keep per-test history.**
_Signal you need it:_ failures are found by searching logs.

**Level 2: record pass-on-retry, add a quarantine file with owners and expiry dates, and add a gate step that enforces it.**
_Signal you need it:_ a list of known flakes in chat.

**Level 3: shard by timing; run affected tests on pull requests and the full suite on `main`.**
_Signal you need it:_ the pull-request stage exceeds its time budget (21.1a).

**Level 4: schedule stress runs** with randomized order, repeated runs, and race detection.
_Signal you need it:_ flakes appearing faster than you find their causes.

**Level 5: add a merge queue.**
_Signal you need it:_ `main` breaking from pull requests that each passed on their own.

For pipeline design beyond testing (build caching, deploy stages, environment promotion), see Module 30.

## Implementation

This section uses TypeScript for the gate script, and GitHub Actions for the pipeline. The gate is a small, policy-bearing piece of code that decides the build result. The runner's exit code doesn't.

The quarantine file lives in the repository:

```json
[
  {
    "id": "checkout › applies a coupon only once",
    "owner": "payments-team",
    "issue": "PAY-2231",
    "expires": "2026-10-01"
  }
]
```

The gate:

```ts
// ci/gate.ts
type Outcome = "passed" | "failed";
export type Result = { id: string; attempts: Outcome[] }; // one entry per attempt, oldest first
export type Quarantined = { id: string; owner: string; issue: string; expires: string };

export function gate(results: Result[], quarantine: Quarantined[], today: string) {
  const seen = new Set(results.map((r) => r.id));
  const quarantined = new Set(quarantine.map((q) => q.id));

  const blocking = results.filter((r) => r.attempts.at(-1) === "failed" && !quarantined.has(r.id));
  const flaky = results.filter((r) => r.attempts.includes("failed") && r.attempts.includes("passed"));
  const expired = quarantine.filter((q) => q.expires < today);
  const stale = quarantine.filter((q) => !seen.has(q.id)); // renamed or deleted tests

  return {
    ok: blocking.length === 0 && expired.length === 0 && stale.length === 0,
    blocking, flaky, expired, stale,
  };
}
```

```ts
// ci/gate-main.ts
const results = await loadJUnitResults("reports");            // runner-specific: attempts must be preserved
if (results.length < EXPECTED_MIN_TESTS) fail("missing or truncated reports");

const report = gate(results, quarantine, new Date().toISOString().slice(0, 10));
for (const r of report.flaky) await recordFlake(r.id, process.env.GITHUB_SHA!); // a table, a file, or your vendor's API
await writeJobSummary(report);                                                   // on the PR, not only in the log
process.exit(report.ok ? 0 : 1);
```

> **Aside: `flaky` includes tests whose final attempt passed.** The build stays green, and the event is still recorded against the commit. That single `filter` is the difference between the Problem's three weeks and a ticket on the first day. The coupon test would have appeared in the flake history within a day, with a rate of one in forty and an owner assigned.

> **Aside: an expired entry fails the build, even for unrelated pull requests.** That's deliberately inconvenient. Without it, the quarantine list only ever grows, and each entry amounts to deleting a test without anyone agreeing to it. Some teams fail only on `main`, or notify the owner instead. Either is fine, as long as expiry has a consequence someone has to act on.

> **Aside: stale entries matter in both directions.** If a test is renamed, it silently leaves quarantine and starts blocking merges again. If a test is deleted, its entry lingers and nothing checks it. Either way, a person should look.

> **Aside: count the results, not just the failures.** With `continue-on-error` on the test step, a runner that crashes before writing its report would otherwise look like a run with zero failures. The minimum-count check turns "no report" into a failure.

The pipeline shards the tests, lets them fail without stopping, and hands the decision to the gate:

```yaml
jobs:
  test:
    strategy:
      fail-fast: false
      matrix: { shard: [1, 2, 3, 4] }
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: >
          npx vitest run --shard=${{ matrix.shard }}/4 --retry=1
          --reporter=junit --outputFile=reports/unit-${{ matrix.shard }}.xml
        continue-on-error: true            # the gate decides the result, not this exit code
      - uses: actions/upload-artifact@v4
        with: { name: results-${{ matrix.shard }}, path: reports/ }

  gate:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v4
        with: { path: reports, merge-multiple: true }
      - run: npx tsx ci/gate-main.ts
```

A scheduled stress job exposes flakes before they reach a pull request:

```yaml
  stress:
    if: github.event_name == 'schedule'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: |
          for i in $(seq 1 20); do
            npx vitest run --sequence.shuffle --retry=0 \
              --reporter=junit --outputFile=reports/stress-$i.xml || true
          done
      - run: npx tsx ci/flake-report.ts reports   # a test that failed in some runs and passed in others is a flake
```

> **Aside: shuffling finds order dependence, and repetition finds races.** Both are slow, which is why they run nightly with retries off. The coupon race, failing one run in forty, would almost certainly have shown up across twenty shuffled runs of that suite. It would then have gone to triage, where the first question is whether the bug is in the product.

## Further Reading

- **John Micco, "Flaky Tests at Google and How We Mitigate Them"** (Google Testing Blog, 2016). The numbers, and the policies of a large organization.
- **Jeff Listfield, "Where do our flaky tests come from?"** (Google Testing Blog, 2017). The link between test size and flakiness.
- **Qingzhou Luo, Farah Hariri, Lamyaa Eloussi & Darko Marinov, "An Empirical Analysis of Flaky Tests"** (FSE 2014). The taxonomy of causes that most later work builds on.
- **Owain Parry, Gregory Kapfhammer, Michael Hilton & Phil McMinn, "A Survey of Flaky Tests"** (ACM TOSEM, 2021). A broad review of detection and repair techniques.
- **Martin Fowler, "Eradicating Non-Determinism in Tests"** (2011). The practical guide to quarantine and to each cause, still accurate.
- **Titus Winters, Tom Manshreck & Hyrum Wright (eds.), _Software Engineering at Google_ (2020), ch. 23, "Continuous Integration."** Presubmit and postsubmit, test selection, and keeping a large `main` branch green.
- **GitHub documentation, "Managing a merge queue,"** and **GitLab documentation, "Merge trains."**
- **Playwright** and **Vitest** documentation on retries, sharding, and randomized ordering.

A Go sibling would reveal something TypeScript doesn't have. `go test -race` turns a large class of concurrency flakes into deterministic failures that report the conflicting memory accesses, and `-shuffle=on` and `-count=N` are built into the standard tool. The sibling would show how much of this article's detection machinery the Go toolchain already provides, and what it still doesn't: races across processes, like the coupon bug, which happened between two HTTP requests hitting a database. Not yet written.
