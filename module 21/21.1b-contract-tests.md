# Contract Tests: Checking a Seam Without Running Both Sides

_Module 21.1b — Testing Strategies_

## The Problem

An online pharmacy has three teams. **Orders** owns the order service. **Fulfilment** owns the service that picks, packs, and books couriers. **Notifications** sends the "your prescription is on its way" messages. Each service deploys on its own, several times a day.

Fulfilment reads orders over HTTP. Its tests use a fixture, `order-1042.json`, which someone copied from a real response in February.

On a Tuesday in October, the Orders team tidies its response model. It renames `deliveryAddress.postcode` to `postalCode`, since the business now ships to Ireland. All of Orders' tests pass because they were updated with the rename. Fulfilment's tests also pass, because they still run against the February fixture.

The change deploys at 15:10. From then on, Fulfilment rejects every new order as having no postcode and puts it in a retry queue. By the evening courier cut-off, 1,900 prescriptions have missed collection.

The post-mortem produces an action item: *add end-to-end tests across services.* A shared staging environment is set up with an E2E suite that runs all six services together. Three months later:

- **Staging runs whatever each team deployed most recently**, so it is red about 30% of the time because of someone else's half-finished change.
- **The suite takes 45 minutes.** Teams queue for it, then start batching changes to avoid queueing.
- **Release coordination creeps back in.** People start saying "don't deploy Fulfilment until Orders ships 4.12."
- **It still doesn't cover the postcode case.** Nobody on the Orders team knew Fulfilment read that field. It wasn't written down anywhere, so nobody thought to test it.

That last point is the real failure. The Orders team had no way to find out who depended on `postcode`. The only record of that dependency was the Fulfilment codebase.

Adding cross-service E2E tests also doesn't scale. The number of meaningful combinations grows multiplicatively with services and code paths, while the number of tests you can afford to run together grows slowly. J.B. Rainsberger's name for this effect is *integrated tests are a scam*: each additional integrated test feels like progress, but the proportion of combinations actually covered keeps shrinking.

## What It Is

A **contract test** checks each side of an integration separately against a shared, explicit description of their interaction. That description is versioned, so a change on either side can be checked against what the other side really does, before deploying and without running the two services together.

Contract tests come in two main families. They answer different questions.

- **Provider-driven (schema-first).** The provider publishes a specification, such as an OpenAPI document (7.2). Consumers generate clients from it or validate against it, and a breaking-change diff guards changes to it. This answers *"did the provider change its promise?"* It can't answer *"does anyone rely on this field?"*, because the specification lists everything the provider offers, not what consumers actually use.
- **Consumer-driven.** Each consumer records the requests it sends and the parts of each response it reads. The provider then checks that it satisfies every consumer's recorded expectations. This answers *"will this change break a consumer that exists?"* Ian Robinson described the pattern in 2006. Pact is the most widely used implementation.

A hybrid called **bi-directional contract testing** compares consumer expectations directly against the provider's OpenAPI document. It is cheaper for the provider, and it is only as trustworthy as the provider's specification. That's why 7.2 insisted on checking real responses against the specification.

Contract tests are also easily confused with functional tests of the provider, and they are a different thing. A contract test checks that the provider *can respond in the shape the consumer needs*, given a named starting state. It doesn't check that the provider's business rules are correct. Once a contract suite starts asserting "a refunded order has status `refunded` and a credit note," it duplicates the provider's own tests, and it breaks whenever those business rules change.

## Recognizing the Problem

- Your repository holds JSON fixtures copied from another team's responses, and nothing updates them.
- A shared staging environment is the only place integrations get checked, and it is often red for reasons unrelated to your change.
- Nobody can answer "who uses this field?" without searching other teams' code.
- Breaking changes between your own services are found in production.
- Release notes include ordering instructions, such as "deploy X before Y."
- A provider team avoids removing any field, ever, because it can't tell which fields are safe to remove.
- Old mobile app versions break when a backend changes, and nobody predicted it.

### The interaction

The consumer's test declares one interaction in four parts:

- **Provider state:** a named starting condition, such as *"order 1042 is paid."*
- **Description:** what is being asked for.
- **Request:** the request the consumer will send.
- **Response:** the minimum response the consumer needs.

The test then exercises the consumer's **real client code** against a mock server that answers only the declared requests. Any request that doesn't match fails the test. When the tests pass, the tool writes every interaction to a pact file.

### Matchers: describe types, not values

If the response specifies exact values, the provider can never change them, even when no consumer cares about the value. If it specifies too little, the contract says nothing useful.

The usual approach is type matching: *"a string," "an integer," "at least one item shaped like this."* Use exact values or patterns only where the consumer actually branches on them. An enum the consumer switches on is a good example.

### Record only what you read

A consumer lists only the fields its code uses. This is the property that would have prevented the Orders incident. The collected pacts give the provider a list of which consumer relies on which field. `deliveryAddress.postcode` would have appeared under Fulfilment, and removing it would have failed Orders' build.

### Provider states

The consumer only names the state it needs. The provider owns the code that sets that state up, such as inserting a paid order with id 1042. The two teams agree on state names, never on how each other's databases are arranged. The provider has to maintain its state handlers, and they are the most common place for provider verification to go wrong over time.

### The matrix and `can-i-deploy`

The broker records which consumer version and provider version were verified together, and whether verification passed. Before a deploy, `can-i-deploy` asks one question: *is the version I'm about to deploy compatible with every version currently deployed in the target environment?*

This also handles rollout order. If a consumer starts expecting a field the provider hasn't shipped to production yet, the consumer can't deploy until the provider does. `record-deployment` keeps the broker's view of each environment accurate. Without it, the broker answers questions about an environment that no longer matches reality.

### Pending and work-in-progress pacts

When a consumer adds a new expectation, the provider's build shouldn't start failing immediately. Otherwise any consumer could break another team's main branch.

- **Pending pacts** don't fail provider builds until the provider has verified them successfully at least once. After that, a failure is a real regression.
- **Work-in-progress pacts** are pacts from consumers' feature branches. The provider verifies them too, so consumers learn early whether a change they plan will work.

### Asynchronous messages

The same approach works for events. The consumer declares a message it can handle, and the provider verifies that it can produce that message. When services communicate through a broker (Modules 17 and 37), this is often where contracts matter most, because nothing at runtime returns a `400` to warn anyone.

## When It's Appropriate

- **Several teams with separate deploy pipelines.** For example, an internal API with four consuming services, each deploying several times a day.
- **Integrations between services you own on both sides**, or where every consumer is willing to publish pacts.
- **Mobile and desktop clients whose old versions stay in use for months.** Each released app version counts as a deployed consumer version, and the provider verifies all of them.
- **Event payloads between teams**, where a mismatch fails silently rather than returning an error.
- **Replacing a slow, shared cross-service E2E suite.** Contract tests cover the seams, and a thin end-to-end smoke set covers the journeys.

## When It's Unnecessary or Overkill

- **One repository with atomic deploys.** If both sides change in one commit and ship together, shared types and the compiler already do this job (Modules 3.1 and 29.4).
- **One team that owns both sides and deploys them together.** An in-process test covers the seam more cheaply.
- **A public API with unknown consumers.** They won't publish pacts. Use a specification, breaking-change diffs, and a versioning policy instead (7.2 and 33).
- **An integration that changes once a year.** The broker, the state handlers, and the CI wiring cost more than the occasional coordinated change.

## Trade-offs

- **Infrastructure.** You either run a Pact Broker yourself or pay for a hosted one. Either way it becomes a dependency of every deploy pipeline.
- **Both sides have to take part.** A pact that no provider verifies is just documentation. Adoption depends on the organization as much as on tooling.
- **Provider states need maintenance.** Schema changes break state handlers, and "state not found" failures are a common source of friction.
- **Contracts don't check meaning.** Changing `amount` from cents to dollars keeps it an integer, so every matcher still passes. Contract tests check shape and the interactions that were declared.
- **Contracts only cover what the consumer's tests exercise.** A client code path that no consumer test reaches is missing from the pact, and so is its dependency.
- **Version and branch bookkeeping.** Every pipeline has to publish versions, branches, and deployments correctly, or the matrix becomes wrong.
- **A learning curve.** Verification failures can be hard to read until people are familiar with the tool.

## Alternatives

- **A thin end-to-end suite in a shared environment.** Keep a few journeys as smoke tests. Just don't rely on them to protect the seams.
- **Specification first, with diffs and response validation (7.2).** This is the right choice for public APIs, and it pairs well with bi-directional contracts internally.
- **Shared generated types or client libraries.** These catch mismatches at compile time, as long as consumers upgrade. They also couple teams' release cycles.
- **Provider-driven contracts**, such as Spring Cloud Contract. The provider writes the contracts and generates stubs that consumers test against. Consumers get a stub that is guaranteed to match the provider, but the provider no longer learns which fields consumers actually use.
- **Tolerant readers plus expand-and-contract changes.** Consumers ignore fields they don't use, and providers add the new field, migrate consumers, then remove the old one. This discipline lowers the chance of a break, but it doesn't detect one.

## How to Achieve It

**Level 0: map the integrations.** Draw who calls whom and which integrations have broken.
_Signal you're here:_ you can't draw that graph.

**Level 1: start with one consumer and one provider.** The consumer publishes its pact file as a CI artifact, and the provider verifies it from a URL in its own build.
_Signal you need it:_ a break between teams in the last quarter.

**Level 2: add a broker.** Use the git SHA as the version, publish branches, and add provider state handlers.
_Signal you need it:_ a second consumer, or a second pair of services.

**Level 3: gate deploys on `can-i-deploy`.** Run `record-deployment` in every pipeline.
_Signal you need it:_ the first time a pact failed and someone deployed anyway.

**Level 4: add pending pacts, WIP pacts, and a webhook** that starts provider verification whenever a consumer's pact changes.
_Signal you need it:_ consumer changes breaking the provider's main branch, or consumers waiting a day to hear back.

**Level 5: add message pacts and released mobile versions.**
_Signal you need it:_ events flowing between teams, or app versions in the stores that you can't force users to upgrade.

## Implementation

This section uses TypeScript, with Pact JS on both sides. The consumer is Fulfilment:

```ts
// fulfilment-service/test/orders-client.pact.test.ts
import { PactV3, MatchersV3 } from "@pact-foundation/pact";
import { OrdersClient } from "../src/clients/orders-client";

const { like, eachLike, regex, string } = MatchersV3;
const pact = new PactV3({ consumer: "fulfilment-service", provider: "orders-service" });

it("reads what fulfilment needs from a paid order", () => {
  pact
    .given("order 1042 is paid")
    .uponReceiving("a request for a paid order")
    .withRequest({ method: "GET", path: "/orders/1042", headers: { Accept: "application/json" } })
    .willRespondWith({
      status: 200,
      headers: { "Content-Type": "application/json" },
      body: {
        id: string("1042"),
        status: regex("paid|part_refunded", "paid"), // we branch on this, so its values matter
        deliveryAddress: like({ line1: "1 Park Row", city: "Leeds", postcode: "LS1 5HN" }),
        items: eachLike({ sku: "AMOX-500", quantity: 2, coldChain: false }),
      },
    });

  return pact.executeTest(async (mock) => {
    const client = new OrdersClient({ baseUrl: mock.url }); // the production client, not a hand-written fetch
    const order = await client.getOrder("1042");
    expect(order.deliveryAddress.postcode).toBe("LS1 5HN");
    expect(order.items[0].coldChain).toBe(false);
  });
});
```

> **Aside: fields that aren't listed matter as much as fields that are.** Order totals, the customer's email, and payment details don't appear, because Fulfilment never reads them. The Orders team can now change those freely. If Orders renames `postcode`, verification fails in Orders' own pull request and names `fulfilment-service` and this interaction. The break appears in the changing team's build, along with the name of the team to talk to.

> **Aside: the test must go through the real client.** If the test built its own `fetch` call, the pact would describe the test rather than the code. The client could then drop the `Accept` header, or read `postCode` with a different capitalization, and the contract would still pass. Because the mock server rejects requests that don't match, using the real client also checks the requests Fulfilment actually sends.

> **Aside: `like()` covers everything nested inside it.** `city: "Leeds"` means *any string*, not that exact value. Only `status` is pinned to specific values, because it is the only field Fulfilment uses to decide what to do.

The provider is Orders, which verifies every relevant pact from the broker:

```ts
// orders-service/test/pact.verify.test.ts
import { Verifier } from "@pact-foundation/pact";

it("satisfies its consumers", () =>
  new Verifier({
    provider: "orders-service",
    providerBaseUrl: `http://localhost:${port}`, // the real app, started with a test database
    pactBrokerUrl: process.env.PACT_BROKER_BASE_URL,
    pactBrokerToken: process.env.PACT_BROKER_TOKEN,
    consumerVersionSelectors: [{ mainBranch: true }, { matchingBranch: true }, { deployedOrReleased: true }],
    enablePending: true,
    includeWipPactsSince: "2026-09-01",
    publishVerificationResult: process.env.CI === "true",
    providerVersion: process.env.GIT_SHA,
    providerVersionBranch: process.env.GIT_BRANCH,
    stateHandlers: {
      "order 1042 is paid": async () => {
        await db.orders.insert(anOrder({ id: "1042", status: "paid" })); // Orders decides what "paid" means in its own schema
      },
    },
  }).verifyProvider());
```

> **Aside: `deployedOrReleased` is what protects old app versions.** Without it, the provider only checks consumers' main branches, which leaves out the mobile build that 30% of users still have installed.

The deploy gate runs in every service's pipeline:

```bash
# consumer CI, after tests pass
pact-broker publish ./pacts --consumer-app-version "$GIT_SHA" --branch "$GIT_BRANCH"

# every service, before deploying anywhere
pact-broker can-i-deploy --pacticipant fulfilment-service --version "$GIT_SHA" \
  --to-environment production --retry-while-unknown 10 --retry-interval 30
./deploy.sh production
pact-broker record-deployment --pacticipant fulfilment-service --version "$GIT_SHA" --environment production
```

> **Aside: without `can-i-deploy`, pacts are only documentation.** Everything before it produces information, and this line is where that information stops a deploy. `--retry-while-unknown` covers the window where the provider's verification of a newly published pact is still running. Without it, the gate either fails for no real reason or has to be made optional, which defeats its purpose.

## Further Reading

- **Pact documentation** (docs.pact.io), especially "Contract tests vs functional tests," "Consumer version selectors," "Pending pacts," and "Can I Deploy." These are unusually clear about what the tool is and isn't for.
- **Ian Robinson, "Consumer-Driven Contracts: A Service Evolution Pattern"** (martinfowler.com, 2006). The original description, written before any tool existed, and still the clearest explanation of why consumers should own their expectations.
- **Martin Fowler, "ContractTest"** and **"TolerantReader"** (bliki). The short versions of both halves of the approach.
- **J.B. Rainsberger, "Integrated Tests Are a Scam"** (talk and blog series). The combinatorial argument against relying on integrated tests for correctness at seams.
- **Spring Cloud Contract reference documentation.** The provider-driven alternative, where contracts are written by the provider and published as stubs.
- **Sam Newman, _Building Microservices_, 2nd ed. (2021), ch. 9, "Testing."** Contract tests in the context of a whole microservice testing strategy, including where end-to-end tests still belong.

A Java sibling using Spring Cloud Contract would be worth writing, because it takes the opposite approach. The provider writes the contracts, the build generates tests that verify them, and consumers receive stub JARs through their dependency manager. Comparing the two shows what each gives up. Here the consumer's stub is guaranteed to be accurate, but the provider no longer learns which fields anyone relies on. Not yet written.

---

The habit to take from this: whenever two deployable units talk to each other, ask where the list of what the consumer depends on is written down. If the only answer is "in the consumer's code," then the provider can't safely change anything, and the first sign of a problem will come from production.
