# Testing Through the Front Door: API and Browser Tests

_Module 21.3b — Testing Strategies_

## The Problem

A holiday-rental site built on Express and React has two suites that look healthy. Each fails in its own way.

**The API suite tests handlers directly.** Each test builds a request object by hand and calls `bookingController.create(req, res)`. Authentication is Express middleware, registered in `app.ts`.

A new route, `GET /api/listings/:id/payouts`, went onto a router that is mounted *before* the auth middleware. Anyone could call it and read a host's payout history. Every handler test passed, because none of them ran the middleware. A security researcher reported the problem three weeks later (20.5).

**The browser suite has 180 tests.** It takes 38 minutes, and about one run in five fails for no apparent reason. The causes, found once someone looked:

- **Fixed waits.** `await page.waitForTimeout(2000)` appears 140 times. Two seconds is longer than needed on a fast day and too short on a slow one.
- **Selectors tied to layout and styling,** such as `.card:nth-child(2) .btn-primary`. A redesign that changed no behavior broke 64 tests.
- **Logging in through the form every time.** Every test fills in the login form first. At about nine seconds each, that is 27 minutes spent logging in.
- **One shared account.** Every test books as `guest@example.com`, so parallel runs cancel each other's bookings.
- **Business rules tested through the browser.** Thirty tests check the price calculation (cleaning fee, weekly discount, tourist tax) by driving the date picker.

A failure typically reads `Timeout 30000ms exceeded`. The trace isn't recorded, and nobody can reproduce the failure locally.

## What It Is

These are tests that use the system through its **public interfaces**, the HTTP API and the rendered UI, the way a real client would.

They are the only tests that see the system assembled: middleware order, routing, error handlers, serialization, the JavaScript bundle, and the browser's rendering. That is what they're good for. In exchange, they're slower and they point less precisely at the cause of a failure (21.1a).

The two kinds cost very different amounts:

- **API tests** can run in-process and in milliseconds.
- **Browser tests** need a real browser against a running app, and each takes seconds.

Treat them as two separate decisions, not one "end-to-end" category.

Load testing and security testing also go through the public interfaces, but they ask different questions. They're handed off at the end of How It Works.

## Recognizing the Problem

- Handlers or controllers are tested without the real middleware stack.
- Nobody can confirm that every route requires authentication without reading the router by hand.
- The browser suite takes up most of your CI time.
- `sleep` or `waitForTimeout` calls appear in the tests.
- Selectors refer to CSS classes or positions in the DOM.
- A visual redesign breaks tests even though behavior didn't change.
- Tests share accounts or data, or only pass in a certain order.
- Every browser test starts by logging in through the form.
- A business rule has many browser tests.
- A browser failure can't be diagnosed without rerunning it.

## How It Works

### API tests: the whole stack, in-process

Build the real application object, with its routing, middleware, error handler, and serializers, using test configuration. Send requests to it with a library like supertest. Nothing is deployed and nothing is mocked above your own adapters.

This level is the right place to check the **API's contract**:

- Status codes, headers, and the error format.
- Response shape, validated against the OpenAPI document (7.2).
- Pagination, idempotency keys, and conditional requests.
- Above all, **authorization boundaries**: unauthenticated requests, the wrong tenant, and an insufficient role (Modules 4 and 5).

Business rules belong further down the pyramid.

**Generate the boundary tests; don't write them one by one.** A test per route, written by hand, depends on someone remembering to add one for each new route. That's how the payouts route slipped through. Instead, build a matrix of *every route × every identity that should be refused*, generated from a single list of routes: the OpenAPI document, or the router's own route table. A new route is then covered automatically, and the payouts route would have failed the build on the day it was added.

After each deploy, run a **small smoke subset** against the deployed URL. This is the large-test counterpart from 21.1a.

### Browser tests: few, stable, and easy to diagnose

**Scope: journeys, not rules.** Search → book → pay. A host publishes a listing. A guest cancels. Test one path through each journey, plus the one failure that matters most. The thirty price combinations belong in unit or component tests. The browser test checks that one total appears.

**Find elements the way a user does.** Locate by role and accessible name, by label, or by visible text. Use `data-testid` only when nothing a user sees is stable. CSS classes and DOM position are implementation details, and a redesign changes them.

**Wait for conditions, never for a fixed time.** Assertions like `await expect(locator).toBeVisible()` keep retrying until the condition is met or a timeout expires. A fixed sleep is always the wrong length: longer than needed on fast runs, too short on slow ones.

**Set up state through the API, not the UI.** Create the listing and the user with API calls. Log in once, save the session state, and reuse it. Only the test for the login journey should use the login form.

**Each test creates its own data.** A unique user and a unique listing per test let tests run in parallel and in any order.

**Control what you don't own.** Route browser requests to third-party services (maps, analytics, a payment widget's scripts) to stubs, so the run is deterministic. Keep one unstubbed journey in a smoke set that runs against the provider's test mode, so you find out when the real integration changes.

**Make every failure readable without rerunning.** Record a trace, screenshot, video, and network log on failure, and attach them to the CI result.

**Use page objects in moderation.** Helpers for repeated flows are useful. Assertions hidden inside helpers make tests harder to read.

### The middle layer: component tests

Render a single component, such as the price-breakdown widget, with the props you choose, in a real browser or a DOM implementation. Tools include Testing Library and Playwright's component testing. The thirty price cases run here in seconds, and they still check what the user sees. For most UI logic, this is the right level.

### Visual and accessibility checks

**Screenshot comparison** catches CSS regressions that no assertion describes. It's also noisy, because font rendering and anti-aliasing vary between machines. Run it in a pinned container, on a few important pages.

**Automated accessibility scans**, such as axe, catch a meaningful subset of WCAG problems at almost no cost. They can't catch everything that matters (34.3).

### What this article doesn't cover

- **Load testing** uses the same interfaces to ask a different question: how much traffic, and how fast, before the system degrades? That belongs to Module 22.5.
- **Security testing** (DAST scanners, penetration tests, bug bounties) belongs to Module 20.5. The authorization matrix above is a functional check of *your own* rules. It doesn't replace security testing.

## When It's Appropriate

- **API tests through the full stack:** every HTTP service. A matrix of 40 routes × 3 identities is 120 tests that run in about two seconds.
- **Generated authorization matrices:** any multi-tenant or role-based API. This is the cheapest high-value security check you can own.
- **Browser tests:** the handful of journeys that make money or would cause support tickets if broken, typically 5 to 30 tests, not hundreds.
- **Component tests:** any UI with logic, such as price breakdowns, form validation, or conditional display.
- **Smoke tests after deploy:** every deployment, checking the things only the deployed artifact can show.

## When It's Unnecessary or Overkill

- **Business rules tested through the browser.** Push them down (21.1a).
- **Browser tests for every page variant or every validation message.** Use component tests.
- **A browser suite for an internal tool with five users.** A few API tests and a manual check before release may be enough.
- **Pixel-comparison tests on pages whose design changes weekly.** Every design change means reviewing and approving new screenshots, and the tests don't protect anything that stays stable.
- **Stubbing your own backend in browser tests** and still calling them end-to-end. That's a component test with extra steps. It's fine to do on purpose, but call it what it is.

## Trade-offs

- **Speed.** Browser tests take seconds each, and even well-built suites take minutes.
- **Infrastructure.** Browsers, a running app, test data, and often a deployed environment.
- **Asynchronous UIs are inherently prone to flakiness.** Good practices reduce it without eliminating it (21.5).
- **Diagnosis costs more.** Traces help, and a failure can still have many possible causes.
- **Stubs of third parties drift** from the real services' behavior, which is why one journey should stay unstubbed.
- **Locating by role and text ties tests to user-visible text.** That's arguably correct, since users see that text. With translations, use test IDs or translation keys.
- **Generated matrices need a single, complete list of routes.** A route missing from the OpenAPI document won't be covered, so pair the matrix with a check that every mounted route appears in the document.

## Alternatives

- **Component tests** for most UI logic.
- **Synthetic monitoring in production**: the same journeys, run on a schedule against production, with alerts (Module 19).
- **Canary analysis** (30.2), which gives confidence from real traffic in place of some pre-release browser coverage.
- **Contract tests (21.1b)** for API consumers you own, in place of cross-service end-to-end tests.
- **Manual exploratory testing** before major releases. It finds what nobody wrote a script for.
- **Visual review tools** that show screenshot differences to a person instead of failing the build.

## How to Achieve It

**Level 0: measure.** Record each test's duration and failure rate. Count browser tests per journey.
_Signal you're here:_ the browser stage takes up most of your CI time.

**Level 1: run API tests through the real app, with a generated authorization matrix.**
_Signal you need it:_ handler tests that skip the middleware, or any multi-tenant API.

**Level 2: move rule checks down to unit or component tests,** and delete browser tests that duplicate them.
_Signal you need it:_ many browser tests for a single journey.

**Level 3: fix the mechanics.** Use role-based locators and no sleeps, set up state through the API, save session state, and give each test its own data.
_Signal you need it:_ failures with no apparent cause, or tests broken by redesigns.

**Level 4: run in parallel or in shards,** and record traces on failure.
_Signal you need it:_ the stage exceeds its time budget, or failures can't be diagnosed.

**Level 5: run the same journeys as synthetic checks in production.**
_Signal you need it:_ incidents that users report before your monitoring does.

## Implementation

This section uses TypeScript, with supertest and Playwright, since that's where most browser testing tools are strongest.

A generated authorization matrix, built from the committed OpenAPI document:

```ts
// test/api/authz-matrix.test.ts
import request from "supertest";
import spec from "../../openapi.json";
import { buildApp } from "../../src/app";

const app = buildApp(testConfig());                   // real routing, middleware, error handler
const PLACEHOLDER = "00000000-0000-0000-0000-000000000000";

const operations = Object.entries(spec.paths).flatMap(([path, ops]) =>
  Object.entries(ops).map(([method, op]: [string, any]) => ({ method, path, op })),
);
const protectedOps = operations.filter(({ op }) => op.security?.length !== 0); // `security: []` marks a public route

describe.each(protectedOps)("$method $path", ({ method, path }) => {
  const url = path.replace(/\{[^}]+\}/g, PLACEHOLDER);

  it("rejects requests with no credentials", async () => {
    const res = await (request(app) as any)[method](url);
    expect(res.status).toBe(401);
  });

  it("rejects a token from another tenant", async () => {
    const res = await (request(app) as any)[method](url).set("Authorization", `Bearer ${tokenFor("tenant-b")}`);
    expect([403, 404]).toContain(res.status);          // 404 is acceptable: don't reveal that the resource exists
  });
});
```

> **Aside: the placeholder ID also checks middleware order.** If a route looks up the resource before authenticating, a nonexistent ID produces `404`, and the first test fails with `expected 401, received 404`. That failure is useful. Code that runs before authentication is where information leaks begin.

> **Aside: this matrix only covers routes the document lists.** A route that was mounted but never added to `openapi.json` escapes it. Pair the matrix with 7.2's check that responses conform to the document, or with a test that compares the router's route table against the document's paths.

A browser journey that sets up its data through the API, uses role-based locators, and waits on conditions:

```ts
// e2e/booking.spec.ts
import { test, expect } from "@playwright/test";
import { createListing } from "./support/api";

test("a guest books an available night", async ({ page, request }) => {
  const listing = await createListing(request, { nightlyPrice: 120, availableFrom: "2026-11-02" }); // API, not the UI
  await page.route("https://maps.example.com/**", (route) => route.fulfill({ status: 204 }));    // not ours, not under test

  await page.goto(`/listings/${listing.id}`);
  await page.getByLabel("Check-in").fill("2026-11-02");
  await page.getByLabel("Check-out").fill("2026-11-03");
  await page.getByRole("button", { name: "Reserve" }).click();

  await expect(page.getByRole("heading", { name: "Booking confirmed" })).toBeVisible(); // retries; no sleep
  await expect(page.getByText("Total €120.00")).toBeVisible();                          // one total, not thirty
});
```

```ts
// playwright.config.ts
export default defineConfig({
  fullyParallel: true,                              // safe only because each test creates its own data
  retries: process.env.CI ? 1 : 0,                  // a retry that passes is still recorded as flaky (21.5)
  use: { baseURL: process.env.BASE_URL, trace: "retain-on-failure" },
  projects: [
    { name: "setup", testMatch: /auth\.setup\.ts/ }, // logs in once, saves storage state
    {
      name: "chromium",
      use: { ...devices["Desktop Chrome"], storageState: ".auth/guest.json" },
      dependencies: ["setup"],
    },
  ],
});
```

> **Aside: `page.route` only intercepts requests the browser makes.** Your server's own call to the payment provider isn't affected. For server-to-server calls, run the app against the provider's test mode, or configure the server to use a stub. Otherwise the "stubbed" journey quietly charges a real sandbox, or a real card.

> **Aside: one saved session is shared across workers,** which works only if the tests don't change the account's own state. Tests that do, such as changing a password or deleting the account, need an account per worker. Playwright supports that with a worker-scoped fixture keyed on `testInfo.parallelIndex`.

## Further Reading

- **Playwright documentation**: "Best Practices," "Locators," "Auto-waiting," "Authentication," and "Mock APIs." These are more opinionated, and more correct, than most tool documentation.
- **Testing Library, "Guiding Principles"** and **"Which query should I use?"** The case for locating elements the way users do, stated clearly.
- **Mike Wacker, "Just Say No to More End-to-End Tests"** (Google Testing Blog, 2015). Why the browser suite should stay small, with the arithmetic.
- **Martin Fowler, "PageObject"** (bliki, 2013). What page objects are for, including the advice to keep assertions out of them.
- **supertest** (GitHub README). In-process HTTP assertions against an Express app or any Node HTTP handler.
- **axe-core** (Deque). The engine behind most automated accessibility checks, with an honest account of what automation can and can't detect.
- **Martin Fowler, "Eradicating Non-Determinism in Tests"** (2011). The general treatment of what the browser section fixes. Module 21.5 continues from here.

A Java sibling would reveal a gap this article doesn't show. Spring's `MockMvc` runs requests through the `DispatcherServlet` without a servlet container, so filters registered with the container rather than with Spring, container-level error pages, and some security filter setups aren't exercised. `@SpringBootTest(webEnvironment = RANDOM_PORT)` with REST Assured runs them all. The sibling would show which bugs each approach can miss. Not yet written.

---

The habit to take from this: for every check in a browser test, ask whether a user could only see this problem through the browser. If not, move the check to a faster level, and keep browser tests for what only a browser shows.
