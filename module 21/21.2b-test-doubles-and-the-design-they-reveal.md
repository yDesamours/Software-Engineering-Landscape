# Test Doubles and the Design They Reveal

_Module 21.2b — Testing Strategies_

## The Problem

A meal-kit company renews subscriptions every night at midnight. `Renewer.RenewDue` does four things for each subscription that is due:

1. Loads it from the store.
2. Charges the customer through the payment provider.
3. Extends the subscription period.
4. Emails a receipt.

The tests use generated mocks. Each test begins with setup like this:

```go
store.EXPECT().FindDue(gomock.Any(), now).Return([]Subscription{sub}, nil)
gateway.EXPECT().Charge(gomock.Any(), "cus_1", int64(4999), "renew-sub_1-2026-10").Return(ChargeResult{ID: "ch_1"}, nil)
store.EXPECT().ExtendPeriod(gomock.Any(), "sub_1", periodEnd).Return(nil)
mailer.EXPECT().SendReceipt(gomock.Any(), "sub_1", "ch_1").Return(nil)
```

There are 146 tests in this style. Over one quarter, three things happen.

**A refactor breaks everything.** To save a database round trip, `ExtendPeriod` is replaced by `SaveRenewal`, which writes the new period and the charge ID in one call. Customers see no difference. All 146 tests fail. Ninety percent of the pull request's diff is test edits. The reviewer can't tell whether behavior changed, because every test that could have shown a change was rewritten in the same PR.

**A query bug escapes.** The Postgres query behind `FindDue` used `renews_at < $1`, when it should have been `<=`. Almost every subscription renews at exactly midnight, which is exactly the batch's `now`, so they were all picked up a day late. That was after the kitchen's order cut-off, so a week's worth of boxes went unordered. No test caught it, because every test stubbed `FindDue` to return whatever the test wanted. The query had never run under test.

**A decline bug escapes.** A test for declined cards set the mock to return `ErrDeclined`, a sentinel error the team had defined. The real payment adapter never returns that error. It wraps provider errors in its own type. In production, `errors.Is(err, ErrDeclined)` was never true, so declined renewals went down the generic "retry later" path. The job ran hourly, so each declined card was charged 24 times a day, until the payment provider flagged the merchant account.

The mocks encoded two kinds of assumption, and no test checked either:

- **How the code calls its dependencies.** This made the tests fragile, and the refactor exposed it.
- **What the author believed each dependency does.** These beliefs drifted from reality, and the two production bugs came from that drift.

## What It Is

A **test double** is any object that takes the place of a real dependency during a test. Gerard Meszaros named five kinds:

- **Dummy.** Passed in to satisfy a signature and never used.
- **Stub.** Returns pre-set answers to queries.
- **Spy.** Records the calls it receives, so the test can check them afterward.
- **Mock.** Configured in advance with expected calls, and fails the test if the actual calls don't match. This is called *behavior verification*.
- **Fake.** A real working implementation that takes a shortcut, such as an in-memory store or a local mail sink.

In everyday speech, "mock" is used for all five. The differences matter because each kind fails in a different way. A mock fails when *the interaction* changes, even if the outcome is the same. A test that uses stubs and fakes and then checks the result fails only when *the outcome* changes. That checking style is called *state verification*.

## Recognizing the Problem

- Refactors that don't change behavior break many tests.
- Mock setup is longer than the assertions.
- Tests assert on which internal collaborators were called, in what order, and with what arguments.
- Some adapter or repository code has never run under test, because every test replaces it with a double.
- Doubles return errors or values the real dependency never produces.
- A mock returns another mock, which returns a third.
- Testing something requires patching a module, a global, or the system clock.
- One unit under test needs five or more doubles.

## How It Works

### Only use a double when there's a reason

There are five good reasons to replace a real dependency:

- **It's slow**, like a network call.
- **It's nondeterministic**, like the clock or a random source.
- **It's unavailable or costly**, like a third party, or anything that moves real money.
- **It's hard to push into a particular state**, like a timeout, a decline, or a full disk.
- **Its effect can't be observed any other way**, like an email being sent.

If none of these apply, use the real thing. Value objects, pure functions, and fast in-process domain services should stay real. Doubling them adds coupling and removes no risk.

### Which interactions deserve an assertion

Sandi Metz's rules, slightly condensed:

```
                            query                          command
                            (returns data,                 (changes something
                             no side effects)               outside the unit)
─────────────────────────────────────────────────────────────────────────────────────
incoming (the unit's API)   assert on the return value     assert on the public effect
outgoing (to a dependency)  stub it; don't assert          spy or mock it; assert it was sent,
                            that it was called             with the arguments that matter
private / internal          don't test directly            don't test directly
```

Most fragile tests are **assertions on outgoing queries**, like `FindDue was called with now`. If the unit's result is correct, the query was correct enough. If the result is wrong, the assertion on the result will catch it. Outgoing **commands** are different, because sending them *is* the behavior. For example, "charge exactly once, with this idempotency key" deserves an assertion.

### Use fakes for dependencies you own, and verify them

An in-memory store takes a little effort to write once. After that, it replaces thousands of lines of expectations. Tests that use it read like ordinary usage, and they keep passing when the code changes *how* it calls the store.

The risk is that the fake behaves differently from the real store. The fix is a **shared contract suite**: one set of tests, run against both the fake and the real implementation. The real run is a medium-sized test against a real database (21.3a). A fake that passes the same suite as the real store is a **verified fake**, and it's exactly as trustworthy as that suite.

The `<` versus `<=` bug would have failed a contract case named "a subscription renewing exactly now is due," but only in the Postgres run. That's the kind of case this suite exists for.

### Don't mock what you don't own

This rule comes from *Growing Object-Oriented Software, Guided by Tests*.

If you double a third-party SDK directly, you are writing down a guess about its behavior, and nothing checks that guess. Instead:

1. **Wrap the third party in an adapter** whose interface uses your domain's terms. For example, `Charge` returns an outcome of `Approved` or `Declined`.
2. **Test that adapter against the real provider**, using its sandbox or recorded responses.
3. **Double the adapter everywhere else.**

The `ErrDeclined` bug was in the adapter's translation of provider errors into domain results. That translation had no test. Once the adapter's own integration test checks that a decline comes back as `Declined`, a double that returns `Declined` means the same thing as the real adapter returning it.

### Seams

A **seam** is a place where a test can substitute a double without editing the code under test. Michael Feathers introduced the term. In practice, seams take a few forms:

- Dependencies passed in through a constructor.
- In Go, small interfaces declared by the code that uses them, rather than by the code that implements them.
- Function values for single operations, such as `now func() time.Time`.
- Configuration.

Some languages let you replace a module at runtime, for example Jest's `jest.mock` or Python's `patch`. That lets you substitute a double with no seam at all. It's convenient, but it hides the design problem that the missing seam would have revealed.

### What your doubles say about your design

- **Five doubles for one unit** means the unit has five reasons to change.
- **A mock that returns a mock** means the unit reaches through one object into another.
- **Needing to double a pure type you own** means that type isn't actually pure.

When doubles are painful to set up, that pain is usually information about the design.

## When It's Appropriate

- **Network boundaries**, such as payment providers, email, and other teams' services. Double them through adapters you own.
- **Time and randomness.** Always inject them. Among causes of unreliable tests that are cheap to fix, this is the most common (21.5).
- **Failure injection**: declines, timeouts, `503`s, and partial writes. These are hard to trigger for real and important to handle correctly.
- **Effects you need to observe**, such as an email sent, an event published, or a charge made.
- **Fast tests of use cases** that would otherwise need a database, using a fake that passes the contract suite.

## When It's Unnecessary or Overkill

- **Doubling value objects or pure functions.** It adds coupling and removes no risk.
- **An interface for every struct "for testability."** Declare an interface when a consumer needs one, and not before.
- **Doubling the database when testing a repository**, when the repository's whole job is its SQL. The query itself is what needs testing (21.3a).
- **Strict call-order expectations on queries.** They make tests fragile and protect nothing.
- **Doubling fast in-process collaborators.** Use the real ones and write a sociable test (21.1a).

## Trade-offs

- **Drift is the main risk.** Every double encodes a claim about the real dependency. A claim nobody verifies will eventually be wrong.
- **Fakes are code too.** They need maintenance and their own tests, which is what the contract suite provides.
- **Indirection costs readability.** Every seam is one more place a reader has to look to see what really runs.
- **Strict mocks make tests fragile, and loose mocks make them weak.** No setting avoids both. Choosing *which* interactions to assert on matters more than the setting.
- **Doubles can't reveal performance or concurrency problems.** An in-memory store never deadlocks and never takes 800 ms.
- **Generated mocks add a lot of code**, and it grows every time an interface changes.

## Alternatives

- **The real dependency in a container (21.3a).** High fidelity, at the cost of medium-sized tests.
- **Provider sandboxes and test modes.** The best way to test an adapter, but too slow and too dependent on the network for every test.
- **Record and replay** (go-vcr, WireMock, Polly.js). Real responses, captured once. They go stale silently unless you re-record them on a schedule.
- **Emulators** (LocalStack, cloud-vendor emulators). They implement the API. How faithfully they reproduce edge cases such as errors, limits, and consistency varies from service to service.
- **Contract tests (21.1b)**, for doubles that stand in for your other services.
- **Restructuring into a functional core (21.2a).** Code that receives data instead of fetching it needs fewer doubles.

## How to Achieve It

**Level 0: find the fragile tests.** Look for tests that changed in pull requests that only refactored. Compare the number of mock-setup lines with the number of assertion lines.
_Signal you're here:_ refactors are slow and their diffs are mostly test changes.

**Level 1: inject time and randomness.**
_Signal you need it:_ tests that use fake timers, or occasional failures around midnight.

**Level 2: wrap third parties in adapters you own**, and give each adapter an integration test against the provider's sandbox.
_Signal you need it:_ doubles of SDK types, or production bugs in how responses are translated.

**Level 3: replace expectation-heavy tests of your own stateful dependencies** with a fake plus a contract suite. Delete the assertions on outgoing queries.
_Signal you need it:_ the refactor problem above, or query bugs that no test runs.

**Level 4: reserve mocks and spies for outgoing commands at boundaries.** Be strict only where the call is itself the behavior.
_Signal you need it:_ everything up to Level 3 is done and some tests are still fragile.

## Implementation

This section uses Go, where the ideas above are the normal way of writing code. Interfaces are satisfied implicitly, so consumers declare small ones, and fakes are ordinary structs.

The interfaces are declared by the code that uses them, and each is only as wide as that code needs:

```go
// renewals/renewer.go
type Store interface {
	DueAt(ctx context.Context, now time.Time) ([]Subscription, error)
	SaveRenewal(ctx context.Context, r Renewal) error
}

type Payments interface {
	Charge(ctx context.Context, c Charge) (ChargeOutcome, error) // a decline is an outcome, not an error
}

type ChargeOutcome struct {
	Status   ChargeStatus // Approved | Declined
	ChargeID string
}

func NewRenewer(s Store, p Payments, r ReceiptSender, now func() time.Time) *Renewer { /* ... */ }
```

> **Aside: making a decline an outcome is a design fix, not only a testing fix.** When the result type has a `Declined` status, the error channel is left for real failures: timeouts, and the provider being down. A double can no longer invent a sentinel error the real adapter never returns, because the type has no place for one. The adapter's integration test, run against the provider's test mode with its documented decline test cards, is where "provider decline → `Declined`" gets verified.

A shared contract suite, run against both the fake and the real store:

```go
// renewals/storetest/contract.go
type NewStore func(t *testing.T, seed ...renewals.Subscription) renewals.Store

func RunStoreContract(t *testing.T, newStore NewStore) {
	midnight := time.Date(2026, 10, 1, 0, 0, 0, 0, time.UTC)

	t.Run("a subscription renewing exactly now is due", func(t *testing.T) {
		s := newStore(t, renewals.Subscription{ID: "sub_1", RenewsAt: midnight})
		due, err := s.DueAt(context.Background(), midnight)
		require.NoError(t, err)
		require.Len(t, due, 1) // the `<` vs `<=` bug fails here, in the Postgres run
	})

	t.Run("a saved renewal is no longer due", func(t *testing.T) { /* ... */ })
	t.Run("a past-due subscription is not due again the same day", func(t *testing.T) { /* ... */ })
}
```

```go
// memstore/memstore_test.go
func TestMemStore(t *testing.T) { storetest.RunStoreContract(t, memstore.NewSeeded) }
```

```go
// pgstore/pgstore_test.go
//go:build integration

func TestPGStore(t *testing.T) {
	storetest.RunStoreContract(t, func(t *testing.T, seed ...renewals.Subscription) renewals.Store {
		return pgstore.New(freshDatabase(t, seed...)) // container plus real migrations (21.3a)
	})
}
```

> **Aside: the contract suite is what makes the fake trustworthy.** Without it, `memstore` is a second implementation that has never been compared with the first. With it, any behavior the service tests rely on is behavior Postgres has been shown to have. When a new rule is added to the real store, the contract case gets added first, and the fake has to pass it too.

A service test that uses the fake store, a scripted payment adapter, a spy for receipts, and a fixed clock:

```go
func TestDeclinedRenewalIsNotChargedAgainTheSameDay(t *testing.T) {
	now := time.Date(2026, 10, 1, 0, 0, 0, 0, time.UTC)
	store := memstore.NewSeeded(t, renewals.Subscription{ID: "sub_1", RenewsAt: now, PriceCents: 4999})
	payments := &scriptedPayments{outcomes: []renewals.ChargeOutcome{{Status: renewals.Declined}}}
	receipts := &receiptSpy{}

	r := renewals.NewRenewer(store, payments, receipts, func() time.Time { return now })
	require.NoError(t, r.RenewDue(context.Background()))
	require.NoError(t, r.RenewDue(context.Background())) // the hourly job runs again

	require.Equal(t, 1, payments.calls)                          // outgoing command: check how many
	require.Empty(t, receipts.sent)                              // outgoing command: check it wasn't sent
	require.Equal(t, renewals.PastDue, store.Get("sub_1").State) // incoming command: check the public effect
}
```

> **Aside: notice which assertions are missing.** Nothing checks that `DueAt` was called, with which arguments, or in what order relative to `SaveRenewal`. The Problem's refactor changes none of the three assertions that remain. `store.Get` is an inspection method that exists only on the fake. The interface stays narrow, and the test can still see the stored state.

> **Aside: this test would have caught the 24-charges-a-day incident.** It checks the outcome that matters, "one charge per day," instead of the path through the code. Checking a path would have required the test author to already know the bug existed.

## Further Reading

- **Gerard Meszaros, _xUnit Test Patterns_ (2007).** The source of the names for test doubles, and a thorough catalogue of test smells.
- **Martin Fowler, "Mocks Aren't Stubs"** (martinfowler.com, 2007). State verification versus behavior verification, and the classicist and mockist schools.
- **Steve Freeman & Nat Pryce, _Growing Object-Oriented Software, Guided by Tests_ (2009).** Where "don't mock what you don't own" comes from, along with mocks used well as a design tool.
- **Sandi Metz, "The Magic Tricks of Testing"** (RailsConf 2013). The query/command rules, explained in about half an hour.
- **Titus Winters, Tom Manshreck & Hyrum Wright (eds.), _Software Engineering at Google_ (2020), ch. 13, "Test Doubles."** Google's preference for real implementations, then fakes, then mocks, and the reasons for that order.
- **Michael Feathers, _Working Effectively with Legacy Code_ (2004).** Seams, and how to create them in code that has none.

A TypeScript sibling would show something Go doesn't allow. `vi.mock` and `jest.mock` replace a module when it's imported, so a test can double a dependency that has no seam. That makes testing easier, and it removes the design feedback that Go forces on you. The sibling would compare module mocking with explicit injection in the same codebase, and follow what happens to each approach at the first refactor. Not yet written.

---

The habit to take from this: treat every double as a claim about something real, and ask where that claim is checked. If the answer is "nowhere," the test only checks that the code agrees with the test author's assumptions.
