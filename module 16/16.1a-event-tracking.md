# Event Tracking

_Module 16.1a — Analytics & Metrics_

## The Problem

Three months after a redesigned onboarding flow ships, someone asks five questions in a planning meeting. The production database is healthy, fully backed up, and cannot answer any of them.

**"How many people who started onboarding finished it?"** `users.onboarding_completed_at` is populated for 4,200 accounts. Nobody knows how many started, because starting leaves no row. The denominator does not exist.

**"Where do they drop off?"** There are five screens. Reaching screen three writes nothing, reaching screen four writes nothing, and abandoning writes nothing. The only observable states are *never began* and *finished*, which are also the only two states the schema was ever asked to represent.

**"Did the accounts that churned last month use the export feature?"** Exports stream a file and return. They leave no trace anywhere except an nginx access line that rotated out sixteen days ago. And the accounts are gone — the deletion job did its job.

**"Is the new flow better than the old one?"** The old flow was deleted in the same PR that added the new one. There is no before.

**"Which of these two features should we build next?"** Both have advocates. Both arguments are about which users *would* want it. The meeting resolves by seniority, because there is nothing else available to resolve it with.

So the team does the reasonable thing incrementally. An engineer adds `logger.info('onboarding step', { step })`, and for a while questions are answered by grepping. A counter column appears — `users.export_count` — incremented in the export handler, which answers *how many* and never *when*, and cannot distinguish one person exporting forty times from forty people exporting once. A nightly cron writes a `daily_stats` row, which is fine until the definition of "active" needs to change and the last six months were computed under the old one. Each step is cheap, each answers the question in front of it, and none of them compose.

The shape underneath all five questions:

```
what the database knows              what you are being asked
-----------------------              ------------------------
user.plan = 'pro'                    when did they upgrade, and what did
                                     they do in the hour before deciding?

project.count = 4                    how many did they create, and how many
                                     did they create and then delete?

user.last_seen_at = 2026-09-11       which 6 of the last 30 days, doing what,
                                     and was that pattern changing?

(row deleted)                        what did they do in the month before
                                     they left?
```

Your operational database stores **the current state of the world**. Product questions are almost always about **the sequence of events that produced it**. A state row is a fold over a history — and by default, nobody keeps the history.

There is a second failure, and it arrives later and does more damage. The team eventually starts emitting events properly, and within a year the data is worse than useless, because it is confidently wrong: three names for the same action (`signup`, `user_signed_up`, `Sign Up Completed`), a `source` property that meant "referrer" until March and "UI location" after, a funnel showing 112% conversion from step two to step three because a retry emitted twice, and a sharp drop in a chart in June that turns out to be a component rewrite that dropped a `track()` call.

And the asymmetry that makes all of this urgent in a way most engineering decisions are not: **you cannot backfill behaviour.** A schema mistake can be migrated. A missing index can be added. A week you did not instrument is simply gone, and no amount of engineering next quarter will produce it.

## What It Is

This is **behavioural event tracking**: an append-only stream of facts about what people did, recorded with a deliberately designed schema — a **tracking plan** — and stored separately from the database that runs the product.

Three neighbours are worth separating now, because conflating any of them with this produces a specific, recognisable mess.

**It is not event sourcing.** Event sourcing (Modules 2.4 and 37) makes events the authoritative source of application state; the system rebuilds itself by replaying them, so losing one corrupts the product. Analytics events are derived, lossy, and read by humans. Nothing in the product should decide anything by reading them. That difference sets every other parameter: durability bar, schema evolution rules, whether they belong in a transaction.

**It is not logging, and it is not metrics.** These three get built by the same people and stored in similar-looking places, and they answer different questions for different readers:

```
                  logs             metrics           analytics events
primary reader    an engineer      an alert          an analyst or PM
                  mid-incident     or dashboard      asking "why"
granularity       per line         pre-aggregated    per actor, per action
identity          incidental       none              the entire point
cardinality       unbounded        must be bounded   unbounded by design
one goes missing  fine             fine              a slightly wrong chart
retention         days to weeks    months, rolled up years
schema            loose            label contract    strict contract
```

The middle column is Module 16.3 and Module 19. The right column is this one. The practical consequence of the "cardinality" row is that the instincts you build doing observability work will actively mislead you here: in metrics, attaching a user id to a counter is a mistake that will take down your time-series database. In analytics, attaching the user id *is* the record.

## Recognizing the Problem

- A product question requires an engineer to write a one-off query, and the answer takes days.
- Two people run "the same" query and get different numbers.
- You can count outcomes but not attempts — finishers but not starters, purchases but not abandoned carts.
- Feature usage is inferred from proxies: rows created, a counter column, a log grep.
- "Did anyone use X?" is answered with "let me add some logging and check next week."
- Deleting a user deletes all evidence of what they did before they left.
- A funnel step shows more events than the step above it, or conversion above 100%.
- Your in-app dashboard, your analytics tool, and your warehouse report three numbers for the same metric.
- Event names were chosen by whoever added them, and nobody can list what exists.
- A property changed meaning at some point and nobody knows when.
- A chart moved and nobody can tell whether users changed or a deploy broke the tracking.
- Signed-out and signed-in activity for the same human are two unconnected series.
- In B2B: you can describe a user's behaviour but not an account's, because events carry `user_id` and not `tenant_id`.

## How It Works

### The event

An event is a past-tense fact with an actor and a timestamp:

```
{
  message_id:   "req_8f3c91…",          // for deduplication
  name:         "report_exported",
  occurred_at:  "2026-09-14T09:12:04Z", // event time
  received_at:  "2026-09-14T09:12:06Z", // ingest time
  anonymous_id: "a_7f3d…",
  user_id:      "usr_912",
  tenant_id:    "acct_44",
  properties:   { format: "csv", row_count: 18422, source: "sidebar" },
  context:      { app_version, platform, session_id, referrer, ip }
}
```

Four decisions inside that shape carry most of the value.

**Name events after what the person accomplished, not what they touched.** `button_clicked` with `{ button: "export" }` looks flexible and is a trap: it moves the meaning of the event into a string property, so every analysis becomes a filter on free text, and when the button is renamed or moved in a redesign the historical series silently changes shape. `report_exported` survives the redesign, because the fact survives the redesign. The test: *would this name still be correct if the UI were rebuilt from scratch?*

**Pick one naming convention and write it down.** `object_action`, past tense, lowercase — `project_created`, `invite_sent`, `subscription_started`. The convention matters less than its uniformity; the cost of mixed conventions is not aesthetic, it is that nobody can guess an event name, so everyone adds a new one.

**Properties are the dimensions you will want to slice by, and they must be chosen in advance.** You cannot add a property retroactively to events already emitted. This pushes toward recording everything, which fails differently: each property is a standing promise to keep it meaning the same thing forever. The workable middle is to ask, for each candidate, *what question would I answer by splitting on this?* — and to drop it if there isn't one.

**Keep both timestamps.** `occurred_at` is when it happened; `received_at` is when you got it. A mobile client that was offline for two days uploads its queue on Thursday; if your analysis keys off ingest time, Tuesday's activity appears on Thursday and both days are wrong. Analyses key off event time. And because a client's clock is not trustworthy — user-set clocks, timezone bugs, deliberate skew — the standard correction is to record the client's own clock, the server's receive time, and the difference, so an obviously wrong client clock can be adjusted rather than believed.

### Identity, which is the hard part

Most of a funnel happens before anyone has an account. Someone reads the landing page, compares pricing, leaves, comes back three days later on a different browser, then signs up. Your event stream must connect those pieces or the entire acquisition funnel is invisible.

```
anon_7f3d ──page_viewed(/)──page_viewed(/pricing)──signup_started──┐
                                                                   │  alias:
                                                                   │  anon_7f3d → usr_912
usr_912   ──────────────────────────────────signup_completed───────┴──project_created──…
```

Two implementations, and the choice is permanent enough to be worth a minute. **Rewriting** attaches the user id to the historical anonymous events at merge time — queries stay simple, history changes underneath anyone who looked at it yesterday, and the rewrite is expensive and hard to undo. **Aliasing** stores the mapping and resolves at query time — history is immutable, queries carry the join forever, and every analysis must remember to do it. Vendors differ on this, most of them have changed their answer at least once, and the migration between the two is genuinely painful. Decide deliberately.

Three failure modes are worth knowing before you meet them. A shared device merges two humans into one identity and neither's history is real afterwards. A user who signs in on a laptop and a phone is two anonymous identities until both are aliased, so "unique users" is an overcount until it isn't. And merges are frequently irreversible in hosted tools, which means an identity bug in a release is not a bug you can fix by deploying a fix.

**B2B has a third level, and it is usually the important one.** Device, user, and account. Nearly every question a B2B company actually asks — is this account healthy, is this account adopting the feature, which accounts are at renewal risk — is an account question. If `tenant_id` is not on every event, those questions require a join to a user table whose membership has since changed, and the answer will be wrong for exactly the accounts that churned. Put the account id on the event, at emit time.

### Where events are emitted

A real fork, and the two sides see different worlds.

**Client-side** sees everything, including what never reaches your server: page views, scroll depth, a form field filled in and abandoned, a search with no results, a button clicked three times in frustration. It is also blocked by ad blockers and tracking protection for a share of your audience that varies enormously by who your audience is — technical audiences block far more than consumer ones — delivered unreliably from flaky networks, trivially spoofable, and in many jurisdictions gated behind consent.

**Server-side** is reliable, unblockable, and trustworthy, and is blind to anything that does not produce a request.

The rule that resolves most cases: **any fact you would be embarrassed to be wrong about should be emitted server-side.** `signup_completed`, `subscription_started`, `export_completed`, `invite_accepted`. Intent, interaction and navigation come from the client, where the alternative is nothing.

The one thing not to do is emit the same fact from both "for redundancy." Two emitters for one fact is a duplicate-counting bug wearing a safety costume, and it fails intermittently — only for the users whose client succeeded *and* whose server call also completed — which is the hardest kind of data bug to see. One fact, one owner.

### Delivery, duplicates, and where the call goes

Analytics is allowed to lose events. That single permission is what makes the engineering tractable: you do not need an outbox, you do not need two-phase anything, and you must never make a user's request fail because your analytics sink is unreachable. Fire and forget, into a bounded in-process buffer, dropping on overflow.

It buys that simplicity at a price you have to pay elsewhere: **if you drop silently, you must monitor the drop rate**, because unmonitored loss is indistinguishable from users doing less.

Delivery is at-least-once, so ingest dedupes on `message_id` — and the message id should be derived from the cause (the request id, the job id) rather than generated at emit time, or a retry of the same logical action produces a new id and the deduplication has nothing to work with.

Where the call goes relative to your transaction matters more than it looks:

```
❌ inside the transaction   → rolled-back work emits events; your funnel counts
                              things that did not happen
❌ awaited in the handler   → analytics latency becomes user-facing latency, and
                              an analytics outage becomes a product outage
✅ after commit, not awaited → a crash in the gap loses the event
```

That third case is a real loss and an acceptable one — and noticing *why* it is acceptable here is the clearest statement of the line between this system and a domain event. If losing the record would leave the system wrong, it is a domain event and it needs the transactional outbox (Module 37). If losing it leaves a chart slightly low, it is an analytics event. Ask which one it is once, per event, and the answer tells you which machinery it deserves.

### The tracking plan is a contract, not a document

A tracking plan lists every event: its name, its properties and their types, who owns it, what it means, and what it does *not* mean. Written down, versioned, reviewed when it changes.

Every team that writes one in a wiki watches it drift within two quarters. The version that works is enforced in two places: **at authoring time**, by a typed wrapper where an unknown event name or a missing property does not compile, and **at ingest**, by validating against the registered schema and quarantining violations instead of accepting them quietly. Data quality here is an enforcement problem wearing the costume of a documentation problem, and documentation loses.

The whole pipeline, sketched — the detail belongs to 16.4:

```
client SDK ─┐
            ├─► collector ─► validate vs plan ─► queue ─► raw, append-only store
server SDK ─┘                      │                              │
                                   └─► quarantine                 ├─► warehouse models
                                       (+ alert)                  └─► product analytics tool
```

### Why this cannot stay in your production database

50,000 daily actives generating 40 events each is 2 million events a day, 60 million a month, and at roughly a kilobyte apiece about 60 GB of raw events a month. A funnel query reads a month of that, five times, while a PM iterates on the definition.

Row-store OLTP databases are not built for that scan and your production traffic is sharing the box. This is why analytics data ends up in a column store or a warehouse, and why the retention question ("how far back do we keep raw events?") shows up on a budget line about eighteen months in.

## When It's Appropriate

- **You have two plausible things to build next and the argument is settled by seniority.** This is the base case, and it is the one that repays instrumentation fastest.
- **A funnel of three or more steps that people actually fall out of** — onboarding, checkout, upload → process → share. Two-step funnels can be counted from state; three-step funnels cannot.
- **Self-serve products where you never speak to the vast majority of users.** The event stream is the only conversation you get to have with them.
- **Before pricing or packaging work.** You need usage distributions across the customer base to choose a value metric — which is the same point 15.1 makes from the billing side: instrument the candidate metric long before a cent depends on it.
- **B2B where customer success needs account health before a renewal conversation**, not after.
- **Before starting any experimentation programme.** An A/B test without an event stream measures the metric you happened to have a column for, which is rarely the one the experiment is about.
- **Before retention or churn analysis** (16.1b). Retention needs per-user activity per day; a `last_seen_at` column has been overwritten.
- **Ahead of when you need it, for a small set of events.** Because history cannot be backfilled, the five events describing your core loop are worth emitting before anyone asks. That is an argument for five, not for five hundred.

## When It's Unnecessary or Overkill

- **Pre-product-market-fit with forty users you could call.** Ten conversations beat a funnel with n=9, and cost a week of one person's time rather than a quarter of a team's.
- **Volumes where the chart is noise.** Twelve signups a week, eight activations, then five: the standard deviation of that count is about 1.6, so 8 and 5 are inside two standard deviations of each other. That is an ordinary fortnight, not a regression, and a dashboard will present it with exactly the same authority as a real one.
- **Instrumenting everything "so we have it later."** The cost is not storage. A plan with 400 events has no owner, 30 of them are used, and the other 370 create the impression that anything can be answered — so people answer questions with whichever event is nearest, and the answers are wrong in ways nobody checks.
- **Building the pipeline before you know the question.** The five-event version in your existing Postgres answers the first year's questions. Build-versus-buy is 16.4 and is a decision you are allowed to make later.
- **Anything the product reads to make a decision.** Entitlements, billing quantities, security audit trails, compliance records. Analytics events are sampled, lossy, blockable, and deletable on request — every property you want in an analytics stream is disqualifying for a system of record. This one bites hardest in metered billing, where the analytics event and the billing meter look identical and are not: one is allowed to be 0.5% low, and the other is a refund.
- **Behavioural detail the person would be unsettled to learn you keep.** Keystroke-level capture, session recording without consent, tracking employees inside a B2B customer's account beyond what the account admin has agreed to. Legality varies; the trust cost does not.

## Trade-offs

- **Every event name is a permanent public interface.** Renaming breaks the history; not renaming means the code keeps a name that no longer matches the product. Instrumentation makes refactors more expensive, permanently and in small increments.
- **Instrumentation rots silently and no test catches it.** A rewritten component drops a `track()` call; nothing fails, nothing errors, and the chart bends. Broken tracking looks exactly like changed behaviour — the single worst property of this whole system, and the reason instrumentation needs its own volume-anomaly monitoring rather than only error monitoring.
- **It creates the ability to be precisely wrong at scale.** A dashboard confers authority independent of whether the metric was defined sensibly, and "the data says" ends arguments that should have continued. The measurement now needs as much scrutiny as the decision.
- **Data quality is a standing tax, not a project.** Schema review on every feature, an owner per event, a deprecation process, and someone whose job includes noticing when a number stops making sense.
- **Cost scales with your success**, quietly: events per user per day, times users, times retention, times however many vendors you send it to.
- **You are now holding a per-person behavioural record**, which brings access and deletion rights into scope for a dataset that is deliberately append-only and copied into a warehouse and two vendors. Deletion must reach all of them. The routine incident is not a breach but PII arriving accidentally in properties — query strings, page titles, free-text search terms, an email address in a `name` field — where it is nearly impossible to remove afterwards.
- **Client SDKs cost your users something real**: bytes, main-thread time, and a consent banner that measurably reduces how many people you can measure at all.
- **Once a metric exists, it gets targeted.** The moment activation rate is on a wall, it stops being a measurement of the product and starts being an objective of the team. That is Module 16.2's problem, and it begins here.

## Alternatives

**Query the production database, or a read replica.** Free, no new systems, and it answers more than people expect — especially in B2B, where a few hundred accounts and some well-written views cover the real questions for a long time. It cannot answer sequence, cannot answer attempts, and cannot see anything that doesn't write a row.

**Change data capture into a warehouse** (Module 38.4). Stream the row changes out of Postgres and model them downstream. Genuinely strong as a complement: it requires no instrumentation, so it cannot be forgotten in a rewrite or blocked by an extension, and it gives you accurate entity history for free. It is blind to intent — a search with no results, an abandoned form, a page nobody clicked through from. The pairing that works well is CDC for what the entities did and events for what the humans tried.

**Autocapture and session replay** (PostHog, Heap, FullStory). Capture the DOM broadly and define events retroactively against it. This attacks the single worst property of manual tracking — that unrecorded history is gone — and it is the right answer more often than purists admit, particularly early. The costs are a heavier client payload, a large privacy surface that must be masked field by field, and retroactive definitions bound to CSS selectors, which means a redesign can quietly redefine a metric. A common and sensible shape is autocapture for exploration plus a small manually-tracked set of events for the numbers that matter.

**Server logs plus a log analytics tool.** You already emit the lines; structure them and query. Fine for coarse questions, and it falls apart on identity, on sessionization, and on anything requiring the ordered behaviour of one person over weeks.

**Talking to users.** Support tickets, sales calls, five scheduled conversations. The event stream will tell you that 60% abandon on step three and will never tell you why. These are not competing methods, and at small scale the qualitative track is both cheaper and more informative — which is exactly the situation most teams that are about to build a data pipeline are in.

## How to Achieve It

**L0 — nothing; ad hoc SQL against production.** Correct at the start, and correct for longer than most teams believe.

**L1 — one events table, server-side, five events.** `events(message_id, occurred_at, user_id, tenant_id, name, properties jsonb)` in the Postgres you already run, appended from the server, covering the core loop: signed up, activated (pick a definition and write it down), the central action of your product, invited a teammate, started paying. A day's work, and it starts accumulating the thing that cannot be backfilled. *Signal to start:* the first time someone says "let me add some logging and check next week."

**L2 — a tracking plan and a typed wrapper.** Names, properties, types and owners in a file in the repo; `track()` typed so an unknown event doesn't compile; changes reviewed in the PR that makes them. *Signal:* the second argument about naming, or the first analysis that turned out wrong because a property's meaning drifted.

**L3 — identity and client-side events.** Anonymous ids, the alias decision made deliberately, session context, page views. *Signal:* the first question about the pre-signup funnel or about which acquisition channel converts.

**L4 — move the storage off your OLTP database.** A column store or warehouse, batched ingest, an explicit retention policy. *Signal:* the events table is your largest table, or an analytics query has paged someone.

**L5 — validate at ingest, and monitor the instrumentation itself.** Schema enforcement with quarantine rather than silent acceptance, per-event volume anomaly alerts, and a health dashboard for tracking itself. *Signal:* the first time a chart moved because of a deploy rather than a user.

Most teams should buy L3 through L5 rather than build them (16.4). L1 and L2 are worth owning regardless of what you buy, because they are decisions about your product's vocabulary rather than infrastructure, and no vendor will make them for you.

## Implementation

TypeScript, because the tracking plan wants to be a type before it is a wiki page.

```ts
// The tracking plan, as types. Adding an event means adding a line here;
// an unknown name or a missing property is a compile error, not a
// discovery made three weeks later in a dashboard.
type Events = {
  signed_up:            { method: "password" | "google" | "sso"; invited: boolean };
  project_created:      { template: string; source: "sidebar" | "empty_state" | "api" };
  report_exported:      { format: "csv" | "pdf"; row_count: number };
  subscription_started: { price_id: string; cycle: "monthly" | "annual" };
};

type EventName = keyof Events;

type Identity = {
  anonymousId: string;        // from the client cookie, carried through signup
  userId?: string;
  tenantId?: string;          // on every event, or B2B questions are unanswerable
};
```

```ts
function track<N extends EventName>(
  name: N,
  properties: Events[N],
  id: Identity,
  cause: { requestId: string; occurredAt: Date },
) {
  buffer.offer({
    // Derived from the cause, not generated here. A retried request emits
    // the same message_id, so ingest can drop the duplicate. Generating a
    // fresh uuid at emit time gives deduplication nothing to work with.
    messageId: `${cause.requestId}:${name}`,
    name,
    properties,
    occurredAt: cause.occurredAt,
    ...id,
  });
  // No await, and no promise returned. If the sink is down, events are
  // dropped on buffer overflow — which is fine, and is fine only because
  // the drop rate is a monitored number. Unmonitored loss reads as users
  // doing less.
}
```

The call site, where the ordering decision is the whole point:

```ts
const project = await db.transaction(async (tx) => {
  const p = await tx.projects.insert({ tenantId, template });
  await tx.auditLog.insert({ action: "project.created", projectId: p.id });
  // track() does NOT go here. A transaction that rolls back would still
  // have emitted, and the funnel would count projects that do not exist.
  return p;
});

track("project_created", { template, source: "sidebar" }, id, cause);
// After commit. A crash in this gap loses the event. That is acceptable
// for analytics and would not be for the audit row above — which is
// exactly why the audit row is inside the transaction and this is not.
```

Identity, which is three lines of code and one decision:

```ts
// At signup, the anonymous history has to be connected to the new account.
function alias(anonymousId: string, userId: string) {
  return identities.insert({ anonymousId, userId, at: new Date() });
}
```

Storing the mapping keeps events immutable and pushes a join into every query that spans signup. The alternative — an `UPDATE events SET user_id = $1 WHERE anonymous_id = $2` — makes those queries trivial and makes history mutable, so a report run today no longer matches the one run last week, and a bad merge cannot be undone. Both are defensible; picking one accidentally is not, because the migration between them is a rewrite of every analysis you have.

## Further Reading

- **The Segment Spec** — `track`, `identify`, `group`, `page`, and the reserved context fields. Worth reading even if you never use Segment; it is the vocabulary the industry converged on, and the `group` call is the clearest statement of why B2B needs an account layer distinct from the user.
- **Amplitude's data taxonomy guides.** The object-action naming framework and the argument for a small, owned event set, written by people who watch customers get this wrong at scale.
- **Mixpanel's identity management documentation** (simplified vs original ID merge). The clearest public account of the anonymous-to-identified merge problem, including what their own earlier design got wrong — which is the useful part.
- **Kleppmann, _Designing Data-Intensive Applications_, chapter 11** — event time versus processing time, windows, and stragglers. The same chapter 15.1 leans on for metering; the problems are identical and only the consequences differ.
- **Kimball & Ross, _The Data Warehouse Toolkit_** — fact and dimension modelling. An event table is a fact table, this has thirty years of prior art, and the grain discussion in particular will save you a redesign.
- **Snowplow's open-source documentation**, especially the schema registry and validation model. A concrete implementation of the tracking-plan-as-enforced-contract idea, useful as a shape to compare against without adopting it.
- **PostHog's documentation on autocapture versus manual events.** Unusually honest about the trade-offs in both directions, because they ship both.
- **Chad Sanderson's writing on data contracts.** Generalises the tracking plan to the wider data platform, and makes the case that the producer, not the consumer, owns correctness.
- **Your jurisdiction's regulator guidance on cookies, consent and deletion rights** — the ICO's and the EDPB's are the most readable. Skim it before designing the client SDK layer, not after, because consent gating changes what you can collect and deletion rights change how you must store it.

A **Java sibling** would be worth writing, and would not be a translation. The TypeScript above makes the tracking plan a types file, which enforces the contract inside one repository and nowhere else. The JVM ecosystem's answer is code generation from a schema registry — Avro or Protobuf definitions, compiled event classes shared by producers and consumers, and registry-level compatibility checking that rejects a backwards-incompatible property change at publish time rather than at read time. That turns "we agreed on a naming convention" into a build-time obligation across service boundaries, and it brings schema evolution — adding a property, deprecating one, changing a type — into a versioned process rather than a decision someone makes in a PR. Different answer, same problem. Not yet written.

---

The habit worth carrying past analytics: **a stored value is a fold over a history someone chose whether to keep.** `status = 'churned'` is the answer to *what*, and it has quietly discarded *when*, *from what*, *how many times it nearly happened first*. Any question shaped like why, when, how often, or in what order needs the transitions, not the value — and the transitions only exist if you wrote them down while they were happening. The systems that can explain themselves later are the ones that recorded what happened, not just what is.
