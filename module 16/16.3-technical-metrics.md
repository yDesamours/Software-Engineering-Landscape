# Technical Metrics

_Module 16.3 — Analytics & Metrics_

## The Problem

Support has eleven tickets this week saying the app is slow. The engineering dashboard is entirely green.

```
CPU                34%  ████░░░░░░░░
memory             51%  ██████░░░░░░
avg response time 178ms
error rate        0.4%
uptime          99.98%
```

Every one of those numbers is correctly computed, and every one of them is answering a question nobody asked.

**The average.** In an average second the service handles 950 static and health-check requests at 40ms and 50 report requests at 2,800ms:

```
(950 × 40ms) + (50 × 2,800ms)
────────────────────────────── = 178ms
            1,000
```

The mean is 178ms and one request in twenty takes nearly three seconds. The average isn't wrong; it's dominated by the cheapest, most frequent thing the system does, which is the thing nobody complains about.

**The error rate.** 0.4% across all traffic. The export endpoint is failing 22% of the time and is 1.8% of traffic, so it contributes 0.4 points and vanishes. Worse, exports are used almost exclusively by the enterprise tier — so a number that reads as "four users in a thousand" is actually "a fifth of the requests made by the customers who pay the most."

And that 0.4% only counts responses the server produced. The endpoint that returns `200 OK` with `{"error": …}` in the body is invisible. So is the request that never arrived because the client timed out, or the CDN served a cached error, or the user's connection dropped mid-upload. **A server can only measure requests it received**, which is precisely the wrong population when the complaint is about people.

**Uptime, 99.98%.** Measured by a health check that returns 200 whenever the process is running. It does not open a database connection. The forty minutes last month when every real request failed with a connection-pool timeout — while the process sat there, healthy — are not in the number.

**CPU at 34%**, averaged over twenty hosts and over five-minute windows. Two hosts pinned at 100% for ninety seconds out of every five minutes disappear under both averages, and those two hosts are where the report queue lives.

Then the fix that makes things worse. Someone reasonably asks "which customers are slow?" and adds `customer_id` as a label on the request-duration metric. It works beautifully in staging. Nine days later the metrics backend runs out of memory at 3am, taking the alerting path down with it, and the incident is invisible because the thing that detects incidents is the thing that died.

The thread: **every technical metric is an aggregate, and an aggregate is an answer about a population measured at a place.** The dashboard's population is "requests this process received," measured at the process. The question being asked is "how is this customer's experience," measured at their laptop. Four of the five green numbers fail because of the gap between those, and the fifth fails because closing the gap naively is what kills the database.

## What It Is

**Technical metrics** are numeric time series describing the behaviour of the system: request rates, latencies, error counts, queue depths, resource utilisation.

The defining property — the one everything else follows from — is that they are **aggregated at write time**. The application does not record that request #84,119 took 312ms; it increments a bucket. That is what makes metrics cheap enough to keep at one-second resolution for a year, and it is the same fact that makes them unable to answer a question you didn't anticipate when you wrote the instrumentation.

16.1a put metrics in a table beside logs and analytics events, and flagged one row as the important one: cardinality. This article is what that row means in practice.

The neighbour worth separating here is **monitoring versus observability**. Monitoring answers questions you knew to ask — dashboards and alerts for failure modes someone anticipated — and metrics are its natural instrument, because pre-aggregation is cheap exactly to the extent that the questions are fixed. Observability is the ability to ask a new question of a running system without shipping code, which pre-aggregated series structurally cannot support: the detail that would answer the new question was discarded at write time. That is why traces and structured logs exist alongside metrics rather than being replaced by them, and Module 19 is where that stack lives. This article is about the numbers themselves and about the one thing Module 19 doesn't cover: what they have to do with the product.

## Recognizing the Problem

- Dashboards are green and customers are unhappy.
- The headline latency number is an average.
- Error rate is a single number over all traffic.
- Uptime is measured by a health check that touches no dependency.
- "Is it slow for this specific customer?" requires a log search and twenty minutes.
- You learned about the last incident from a customer email.
- A metrics query that used to return instantly now times out — and it's the one with a high-cardinality label.
- Someone in finance has asked about the observability bill.
- Adding a dimension to a metric requires negotiating with whoever runs the time-series database.
- People have muted the alerts channel.
- You alert on CPU and disk, and on nothing that indicates whether the product works.
- Nobody can say what the latency target is or where the number came from.
- Your p99 is computed by averaging the p99s of each host.
- The system was unusable for forty minutes and the reliability number didn't move.

## How It Works

### Three instrument types, and what each one silently loses

**Counters** only increase. You never read the value; you read its rate, because the process restarts and the counter resets, and `rate()` handles that while a raw difference doesn't.

**Gauges** are a point-in-time reading — queue depth, memory in use, open connections. They are *sampled*, so everything between samples is gone. A queue that spikes to 50,000 and drains in twenty seconds does not exist in a sixty-second scrape interval, and that queue is usually the thing you most wanted to see.

**Histograms** pre-bucket a distribution so quantiles can be computed from it. The bucket boundaries are chosen at instrumentation time and permanently cap the resolution of every percentile you will ever derive. If your buckets top out at ten seconds and your slow path is fourteen, every interesting request lands in the overflow bucket and your p99 is a number the library made up by interpolating a range it can't see into.

### You cannot average a percentile

This is violated constantly and it can be wrong by orders of magnitude in either direction.

```
host A   1,000 req/s, all ≈ 50ms       → p99 =   50ms
host B       5 req/s, all ≈ 5,000ms    → p99 = 5,000ms

mean of the two p99s                   = 2,525ms   ← what the dashboard shows
true p99 of the combined 1,005 req/s   =    50ms   ← only ~5 requests are slow,
                                                     which is under 1% of traffic
```

Fifty times wrong, and it errs the other way as soon as the traffic mix flips. Percentiles are not linear and there is no arithmetic that recovers the combined quantile from the individual ones.

The correct operations are to **merge the underlying distributions**: add the histogram bucket counts across hosts and compute the quantile from the sum, or use a mergeable sketch (t-digest, DDSketch, HDR histogram) designed for exactly this. This is why `histogram_quantile(0.99, sum(rate(bucket[5m])) by (le))` sums first and takes the quantile second, and why exporting a pre-computed p99 from each instance as a gauge produces a number that cannot be aggregated, compared, or trusted.

### RED and USE

Two checklists that between them cover most of what a service needs, and they answer different questions.

**RED**, per service and per endpoint: **R**ate, **E**rrors, **D**uration. The request-centric view — what is happening to the work users asked for.

**USE**, per resource: **U**tilisation, **S**aturation, **E**rrors. Applied to CPU, memory, disk, network, and — more usefully — to the resources people forget are resources: connection pools, thread pools, worker queues, file descriptors, rate-limit allowances.

The pairing is the point. RED tells you that something is wrong for users; USE tells you which resource explains it. A dashboard with only USE is the CPU-at-34% failure: it reports on the machine and says nothing about the product. A dashboard with only RED tells you there's a problem and gives you nowhere to look.

**Saturation is the most neglected of the six** and usually the earliest warning. Utilisation at 70% with a stable queue is a healthy system; utilisation at 70% with a queue growing by fifty items a minute is a system that will fall over at a predictable time, and utilisation alone cannot distinguish them. Queue depth, time spent waiting for a pool, and the number of waiters are the signals that see it coming. (Module 23 is where the responses to saturation live.)

Google's four golden signals — latency, traffic, errors, saturation — are the same material rearranged: RED plus the one thing RED leaves out.

### Rates need a denominator that matches the question

"Error rate" is four different metrics and teams publish one of them:

```
errors / all requests            "is the system broken"
errors / requests on endpoint    "is this feature broken"
affected users / active users    "how many people had a bad time"
affected accounts / active accts "who is going to escalate"
```

The first is what the dashboard shows and the last is what determines whether tomorrow is a bad day. The bottom two require identity attached to the measurement — which is exactly what cardinality forbids. That tension has an honest resolution rather than a clever one: the top two come from metrics, the bottom two come from logs, traces, or the analytics stream. Knowing which instrument answers which question is most of the skill.

### Cardinality is a hard budget, not a guideline

A time series is one unique combination of metric name and label values, held in a memory-resident index. Cost is roughly linear in the number of active series, and because the index is resident, the failure mode is a cliff rather than a slope: everything is fine, and then the process is dead.

```
http_request_duration_seconds
   route      200 values
   method       5
   status      12
   instance    20
                    = 240,000 series          fine

   + customer_id   40,000 values
                    = 9.6 billion at the ceiling
```

Not every combination occurs, so reality is somewhere below the ceiling — and still catastrophic. The rules that follow are mechanical:

- **Labels must be bounded and enumerable before you deploy.** No user ids, emails, session ids, request ids, error message strings, or free text.
- **Route templates, never raw paths.** `/projects/:id`, not `/projects/8471`. Mislabelling one handler turns every project id into a permanent series, and this is the single most common way a team takes down its own metrics backend.
- **When you need per-entity granularity, leave the metrics system.** Exemplars — a sampled trace id attached to a histogram observation — give you a link from a slow bucket to one real slow request without adding a single series. Traces and logs handle the rest.
- **A bounded allowlist is a legitimate compromise.** Your twenty largest accounts as a label, everything else bucketed as `other`, is a cost you can write on a page and defend.

The contrast with 16.1a is the whole design in one line:

```
metrics     emit ──aggregate──► store ─────────────► query    bounded, cheap,
                                                              fixed questions
analytics   emit ─────────────► store ──aggregate──► query    unbounded, costly,
                                                              open questions
```

Same raw reality, opposite decision about *when* to aggregate. Attaching a user id is the point of one system and fatal to the other, and an engineer carrying the wrong instinct across that line does damage in both directions.

### SLIs, SLOs, and the error budget

This is where technical numbers become decisions, which is why the topic sits in this module and not only in Module 19.

An **SLI** is a measurement of one aspect of the service from the user's side, and the durable formulation is a ratio: **good events over valid events**. Requests served under 300ms, over requests that were legitimate to serve. Expressing it as a ratio rather than a raw latency is what makes it aggregatable, comparable across services, and immune to the averaging problem above.

An **SLO** is a target for that ratio over a window: 99.9% over a rolling 28 days. An **SLA** is a contract with financial consequences, and should always be set looser than the SLO — the SLO is where you start worrying, the SLA is where you start paying.

The **error budget** is what's left: 100% minus the SLO, expressed as time you are allowed to be bad.

```
SLO       budget per 30 days
99%       7h 12m
99.5%     3h 36m
99.9%     43m 12s
99.95%    21m 36s
99.99%     4m 19s     ← roughly one bad deploy per quarter, total
```

That table is the argument. It turns "should we spend this quarter on reliability or features" from a values dispute into arithmetic: budget remaining, ship; budget exhausted, stop and fix. It also runs in the neglected direction — a budget that is never spent means you are over-invested in reliability and could be moving faster.

Two implementation points carry most of the value. **Measure the SLI where the user is**: at the load balancer at minimum, and in the browser where you can. A server-side latency SLI excludes DNS, TLS negotiation, the user's network, the render, and every request that never arrived — all the things the tickets are about. And **alert on burn rate rather than on thresholds**: a five-minute blip consuming 2% of the month's budget should not page anybody, while a sustained burn that would exhaust the budget in six hours should page immediately. Threshold alerts fire on both and teach people to mute the channel.

### Where the user actually is

Field measurement — real user monitoring — closes the last part of the gap. Page load, interaction latency, layout stability, and client-side errors, collected from actual devices on actual networks, typically through the same client SDK that carries the analytics events from 16.1a. Synthetic checks from a datacentre tell you about your service; field data tells you about a mid-range phone on mobile data, which is where the difference between a 200ms server and a four-second experience lives. It inherits every client-side limitation from 16.1a: blockable, consent-gated, and a biased sample of exactly the users most likely to block it.

## When It's Appropriate

- **Anything in production with users who are not you.** The floor is RED per endpoint, a handful of USE signals including at least one queue or pool, and one black-box check that exercises a real dependency.
- **Before a capacity decision.** Saturation signals over a month are the only honest input to "do we need bigger machines or a different design."
- **Before signing an SLA**, because you are about to commit to a number you currently cannot measure at the place the contract describes.
- **At traffic volumes where percentiles mean something.** A p99 over 100 requests a day is one request.
- **When performance work needs prioritising against features.** A measured relationship between latency and conversion is the argument that wins that meeting; an engineer's conviction is not.
- **When the same failure has happened twice.** The second occurrence is the point at which a detection signal pays for itself.

## When It's Unnecessary or Overkill

- **A full observability stack for an internal tool with twelve users.** A log file and an uptime checker, and the users will tell you.
- **SLOs before anyone cares about reliability.** An SLO with no consequence attached is paperwork, and worse, it trains everyone that the numbers are decorative.
- **p99.9 at low traffic.** At 10,000 requests a day it is the ten slowest requests, which is a fine thing to look at and a terrible thing to alert on.
- **Dashboards nobody reads.** Sixty graphs on a wall is a museum. The useful artifact is a small number of dashboards plus alerts that mean something; if a graph has never once changed a decision, delete it.
- **Instrumenting every function.** The useful granularity is the service boundary and the outbound dependency call. Below that, use a profiler when you need it.
- **Alerting on causes rather than symptoms.** High CPU is not a problem; users waiting is a problem. Cause-based alerts are the main source of alert fatigue, and they fire hardest during the routine events — deploys, backups, batch jobs — that are not incidents.

## Trade-offs

- **Cheapness and blindness are the same property.** Pre-aggregation is why you can keep a year of one-second data, and why you cannot ask a question you didn't plan for. You are buying storage economics with future questions.
- **Cardinality is a permanent constraint on what you may ever ask**, enforced by an operational cliff rather than an error message.
- **Cost scales with series × resolution × retention × vendors**, and observability spend reaching a noticeable fraction of the infrastructure it observes is common rather than exceptional.
- **Instrumentation is not free at runtime.** Histograms with many buckets, label lookups in hot paths, and high-frequency counters all cost something small and real, and they cost it in the code path you most care about.
- **Every alert is a claim on someone's sleep.** Alert quality is a budget, it depletes silently, and the failure mode is a muted channel rather than a complaint.
- **Dashboards encode the last incident's failure mode**, not the next one's, and they rot quietly because nothing fails when they become wrong.
- **An SLO creates an obligation to say no.** If the organisation won't honour the budget when it's exhausted, the SLO is worse than having none, because it launders a decision that was made on other grounds.
- **Aggregation removes the individual by design**, so every escalation ends with dropping to traces or logs. That path needs to exist and be practised; it's the step teams skip until they need it at 2am.
- **Sampling means sometimes the honest answer is "we don't have that request."**

## Alternatives

**Wide structured events, aggregated at query time.** One very rich event per request — hundreds of fields, including user and account ids — stored raw and aggregated when queried. This is exactly the analytics model from 16.1a applied to systems, and it is a coherent alternative rather than a supplement: no cardinality limit, arbitrary new questions, per-customer slicing for free. The costs move to volume-based storage and query cost, which scales worse at very high request rates, and to a less mature alerting story. This is the substantive argument against the metrics model and it deserves reading in the original rather than in summary.

**Distributed tracing as the primary instrument** (Modules 19 and 36.4). Unbeatable for "where did the time go inside this request" and for dependency topology; weak as a long-horizon trend instrument, because sampling means your historical view is partial in a way that trend lines hide.

**Continuous profiling.** Answers "which code is burning the CPU," which no metric ever will. Narrow, and complementary rather than competing.

**Synthetic monitoring.** A scripted transaction executed from outside every minute — log in, create a thing, delete it. Catches the entire class of failure where the process is healthy and the product is useless, which health checks structurally cannot. Doesn't scale to per-customer and tells you nothing about real devices.

**Support tickets as the monitoring system.** Humans as the detector, with the latency and coverage that implies. Honest at small scale and worth saying out loud, because a team of four with ten customers genuinely does find out faster this way than by building dashboards.

## How to Achieve It

**L0 — logs and an uptime checker.** Adequate for an internal tool.

**L1 — RED per endpoint, a few USE signals, one black-box check that touches a real dependency.** *Signal to start:* an incident you found out about from a customer.

**L2 — percentiles from merged histograms, and no averages left on any latency dashboard.** *Signal:* the average is flat and the tickets aren't.

**L3 — one SLI measured at the edge, one SLO, an error budget, and burn-rate alerts replacing threshold alerts.** *Signal:* a muted alerts channel, or a reliability-versus-features argument with no mechanism to settle it.

**L4 — a cardinality budget with a named owner, exemplars linking dashboards to traces, and a practised path from an aggregate to a single request.** *Signal:* the first metrics-backend incident, or the first invoice someone questions.

**L5 — correlate the technical numbers with the product ones.** Latency against conversion by segment, error rate against churn, SLIs per plan tier. *Signal:* performance and reliability work cannot be prioritised against features because nobody can price it.

L5 is the level that makes this an analytics article rather than an operations one, and it is the level almost nobody reaches — which is why performance work is usually funded by an outage rather than by evidence.

## Implementation

Go, because the Prometheus client is idiomatic there and because cardinality mistakes are visible in the code rather than in a config file.

```go
var reqDuration = prometheus.NewHistogramVec(
	prometheus.HistogramOpts{
		Name: "http_request_duration_seconds",
		// Chosen here, at instrumentation time, and they cap the resolution
		// of every percentile anyone will ever compute from this metric.
		// The defaults top out around 10s — if the slow path is 14s, every
		// interesting request lands in +Inf and the p99 is interpolation
		// over a range the histogram cannot see.
		Buckets: []float64{.01, .05, .1, .3, 1, 3, 10, 30},
	},
	[]string{"route", "method", "status"},
	// customer_id does not go here. 200 routes × 5 methods × 12 statuses
	// × 40,000 customers is 480 million series before the scrape target
	// multiplies it by the instance count. This is not a slow dashboard.
)
```

```go
func Instrument(route string, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK}

		next.ServeHTTP(rec, r)

		// route is the TEMPLATE — "/projects/:id" — taken from the router,
		// never r.URL.Path. One handler registered with the raw path turns
		// every project id into a permanent time series, and the damage is
		// not visible until the index no longer fits in memory.
		reqDuration.
			WithLabelValues(route, r.Method, strconv.Itoa(rec.status)).
			Observe(time.Since(start).Seconds())
	})
}
```

Note what this deliberately does *not* do: compute a percentile in the process and export it as a gauge. That produces a number that cannot be merged across instances, cannot be re-windowed, and cannot be compared — the averaging failure from earlier, baked in at the source.

The SLI, counted in the same place so the ratio stays defensible:

```go
// good events / valid events. Health checks and bot traffic are excluded
// from BOTH numerator and denominator — a request you would never promise
// to serve well should not be inflating your compliance either.
if isValidForSLO(r) {
	sloValid.Inc()
	if rec.status < 500 && time.Since(start) < 300*time.Millisecond {
		sloGood.Inc()
	}
}
```

And the escape hatch for the question the metric refuses to answer:

```go
// "Is it slow for Acme?" — two bounded ways to keep this answerable.

// 1. An exemplar. The histogram stays low-cardinality; the dashboard gets
//    a link from the slow bucket to one real trace.
if obs, ok := observer.(prometheus.ExemplarObserver); ok {
	obs.ObserveWithExemplar(seconds, prometheus.Labels{"trace_id": traceID})
}

// 2. An explicit allowlist, which is a cost you can write down and defend.
tier := "other"
if watchedAccounts[customerID] {   // ~20 entries, reviewed quarterly
	tier = customerID
}
```

The allowlist looks like a hack and is the right answer more often than the elegant alternatives. Twenty named accounts is twenty series per combination — a number you can multiply out in your head before you deploy it, which is the only property that matters here.

## Further Reading

- **Beyer et al., _Site Reliability Engineering_ (Google), chapters 4 and 6.** Free online. The four golden signals and the original statement of the error budget. Chapter 6's argument against alerting on causes is the one to read twice.
- **_The Site Reliability Workbook_, chapters 2 and 5.** The practical follow-up: how to actually choose an SLI, the good-events/valid-events formulation, and multi-window burn-rate alerting with worked parameters.
- **Tom Wilkie's RED method talk and Brendan Gregg's USE method page.** Both short, both better in the original than in any summary.
- **Prometheus documentation on histograms and summaries**, particularly the section on why quantiles can't be averaged and what native histograms change about bucket choice.
- **Gregg, _Systems Performance_.** For saturation, and for what the resource-side numbers mean underneath the abstraction.
- **Majors, Fong-Jones & Miranda, _Observability Engineering_.** The wide-events position and the case against pre-aggregation — the opposing brief to this article's model, and worth reading as one.
- **The t-digest and DDSketch papers.** Short, and they explain precisely why mergeable quantile sketches exist and what accuracy guarantee you're getting.
- **Google's Core Web Vitals documentation**, for the field-measurement side and for metric definitions that were designed to be comparable across sites.
- Module 19 for the stack that surrounds these numbers, and Module 24 for what an SLA obligates you to once it exists.

A **TypeScript/Node sibling** would be worth writing, and it would not be a translation. Go's runtime makes saturation legible through familiar signals — goroutine counts, pool waiters, GC pause — and CPU utilisation is a roughly honest proxy for how busy the process is. In a single-threaded event loop it is not: a process can sit at 40% CPU while every request waits, because the queue that matters is the event loop's and nothing in the USE checklist points at it. `perf_hooks.monitorEventLoopDelay` measures the saturation signal directly, and an article built around it would show a resource whose utilisation number is actively misleading and whose queue is invisible unless you instrument it deliberately. Different lesson, same checklist. Not yet written.

---

The habit worth carrying past operations: **every number was measured somewhere, and everything between that point and the user is invisible to it.** Process, then load balancer, then CDN, then network, then device — each step outward catches failures the previous one structurally cannot see, and the moment two of them disagree you have learned something neither could tell you alone. So when a dashboard is green and the tickets are not, the useful question is rarely "is the metric wrong." It is: *where is this measured, and what lives outside it?*
