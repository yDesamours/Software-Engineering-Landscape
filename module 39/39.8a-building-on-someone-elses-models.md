# Building on Someone Else's Models: Providers, Cloud AI Platforms and Managed Agents

_Module 39.8a — Machine Learning & LLM-Powered Systems_

## The Problem

Suppose you build contract-review software for in-house legal teams. It extracts clauses and dates from contracts, flags risky terms against each customer's playbook, suggests redlines, and has a "contract Q&A" feature where lawyers ask questions about a set of documents. It was built in 2024, quickly, on whatever was easiest:

- Extraction and risk flags call one provider's API directly.
- Contract Q&A was built on a provider's hosted assistants product. The provider stored the conversation threads and the uploaded documents, ran retrieval over them, and managed the conversation state. It took two weeks to build.

Over the next two years:

- **The hosted product was retired.** OpenAI announced in August 2025 that its Assistants API would shut down on August 26, 2026, replaced by its Responses and Conversations APIs. By then, the Q&A feature held 180,000 conversation threads and 2.3 million uploaded files in the provider's storage. Migrating meant exporting every thread, re-uploading and re-indexing every file, rebuilding the retrieval and rewriting the conversation handling. It took most of a quarter, for a feature that had taken two weeks to build.
- **A model was retired, and its replacement behaved differently.** The extraction model reached its retirement date. The recommended replacement was better on paper, but it split clauses differently and wrote dates in a different format, and the downstream code assumed the old behavior. There was no evaluation set (39.7a), so the migration was tested by hand in the final weeks before the deadline.
- **A customer's requirements ruled out the provider.** A European bank required all processing in the EU, under its existing cloud contract, with only approved subprocessors. The provider's own API wasn't on the approved list, although the same model family was available through the bank's cloud platform. Moving the feature there revealed that a caching option and one API feature the code relied on weren't available on that platform yet.
- **A three-hour outage on a deadline day.** The provider had a major incident on the last day of a quarter, when legal teams were finalizing contracts. Nothing else could serve the requests.
- **An abstraction that cost more than it saved.** In response, a team moved everything behind a generic library that made every provider look the same. It supported only what all providers had in common, which ruled out schema-constrained output (39.3a) and prompt caching (39.3b). Costs rose, and extraction quality dropped.

Each decision made sense on its own. Together, they left the product tied to one provider's roadmap in places where that mattered, and uselessly generic in places where it didn't.

## What It Is

Almost every AI feature is built on models, and often services, that someone else runs. This article is about choosing among them and staying in control. It covers three kinds of offering:

- **Model providers' own APIs:** Anthropic, OpenAI, Google (the Gemini API), Mistral and others. New models and features usually appear here first.
- **Cloud AI platforms,** which host many vendors' models under your existing cloud account: Amazon Bedrock, Google's Gemini Enterprise Agent Platform (the successor to Vertex AI, announced April 2026), and Microsoft Foundry (formerly Azure AI Foundry). They offer the same model families, with your cloud's regions, identity, networking, billing and compliance, sometimes with a lag on new models and features.
- **Managed agent platforms,** which run more of the agent (39.6) for you: the loop, the tool sandbox, sessions and memory, tracing and connectors. Examples include Anthropic's Claude Managed Agents, OpenAI's agent tools built on the Responses API, Amazon Bedrock AgentCore, Google's agent runtime in the Gemini Enterprise Agent Platform, and Microsoft Foundry Agent Service.

Alongside these sit **gateways and aggregators** that put several providers behind one API (39.7c), and **open-weight models** you host yourself or through an inference provider (39.3b).

The idea underneath is to **know what each dependency owns**. Model calls are easy to move if your prompts, evaluations and state are yours. Hosted state (threads, files, vector stores, memory, agent sessions) is where moving becomes a project. The skill is choosing where to accept that lock-in because it buys something, and where to keep ownership because it's cheap to keep.

## Recognizing the Problem

- Conversation history, uploaded files or agent memory exist only in a provider's hosted storage.
- A model retirement notice would start an unplanned project, because nothing measures whether a replacement is good enough.
- There's no answer to "what happens if our provider is down for three hours?"
- Customers' requirements (region, cloud account, approved subprocessors, retention) are handled one exception at a time.
- Prompts are shared across providers unchanged, and nobody has checked them on each one.
- A generic abstraction layer hides provider features the product would benefit from.
- Provider-specific code is scattered across the codebase instead of behind one interface.
- Vendor comparisons are based on public benchmarks and list prices, not on your tasks and volumes.

## How It Works

### What actually differs between offerings

At the level of "send messages, get a response," providers look alike. The differences that matter in production are elsewhere:

- **Quality on your tasks.** Rankings on public benchmarks often don't hold for contract extraction in your customers' documents. The only reliable comparison is your own evaluation set (39.7a), run on each candidate.
- **Features and their details.** Structured output, tool use, prompt caching, batch processing, server-side tools (web search, code execution), file handling, citations and MCP connectors all exist on several providers, with different parameters, limits, prices and edge cases (39.3a, 39.3b, 39.5b).
- **Data handling.** Retention periods, zero-data-retention options, commitments on training use, where processing happens, and which subprocessors are involved. These decide whether some customers can use the feature at all.
- **Limits and capacity.** Rate limits by usage tier, and how quickly they can be raised for your volume (39.7c).
- **Price per task, not per token.** A cheaper per-token model that needs longer prompts, more retries or more agent steps can cost more per completed task.
- **Model lifecycle.** How much notice you get before a model is retired. OpenAI's policy is at least six months for generally available models, and Anthropic's is at least 60 days for publicly released models. How long do dated snapshots last, and how often do "latest" aliases move?
- **Availability.** Status history, regional redundancy, and whether the same model is available through a second route.
- **Cloud platform differences.** The same model on a cloud platform may arrive later, lack some features at first, and have different quotas and prices. In exchange, it sits inside an agreement, region and set of security controls your customers may already have approved.

### Where lock-in actually lives

Portability varies a great deal between the parts of an AI feature:

```
 easy to move                                                          hard to move
 ─────────────────────────────────────────────────────────────────────────────────────▶
 a stateless        prompts          fine-tuned   embeddings &    hosted threads,     managed agent
 model call         (need re-eval    models       vector indexes  files, vector       sessions, memory,
                    per model)       (retrain)    (re-embed all,  stores, memory      platform-specific
                                                  39.4b)          (export, rebuild)   tools & workflows
```

- **Stateless model calls** are the easy part. The request and response formats differ, but an adapter handles that.
- **Prompts** are only partly portable. A prompt tuned for one model family often needs changes for another. Keep prompts per model family, each checked against the evaluation set.
- **Embeddings** tie your vector index to one embedding model (39.4b). Changing means re-embedding everything, which is manageable if you planned for it.
- **Hosted state** is where the Q&A migration hurt. Threads, files, vector stores and memory kept only in a provider's storage have to be exported and rebuilt, on the provider's deadline.

The rule that follows: **own your state, and rent computation.** Keep conversation history, documents, indexes and memory in your own database and storage, and send the model what it needs for each call. Model calls can then move between providers. Hosted state is worth accepting only where it buys something substantial, and even then, keep a copy you can rebuild from.

### A thin abstraction, shaped by what you use

The fix for the generic library isn't to drop abstraction. It's to abstract **your** capabilities, not everyone's lowest common denominator:

- Define an internal interface for the operations the product uses (a chat call with structured output, tool use and cache hints, for instance), with **capability flags** per model.
- Write one **adapter** per provider that maps the interface onto that provider's features, including the provider-specific ones, like cache markers or schema parameters.
- Let tasks declare what they need ("structured output, EU processing, zero retention"), and choose among models that have it.
- Keep **prompts and evaluation results per model**, and treat "this model passes this task's evals" as a fact recorded in a registry, not an assumption.

Libraries such as the Vercel AI SDK, LangChain, LiteLLM and Spring AI provide multi-provider adapters, and can serve as the adapter layer. Check how each exposes provider-specific features, since that's where generic layers usually fall short.

### Fallback and routing

With models behind one interface, and evaluation results recorded per task, several things become routine:

- **Failover.** When the primary model's provider is failing (timeouts, 5xx errors, capacity errors), route to a secondary that has passed the same task's evaluations. It could be the same model through a different route (the provider directly, or a cloud platform) or a different model. A circuit breaker (Module 36) stops sending traffic to a failing provider and tries it again periodically.
- **Per-customer routing.** The bank's requests go only to models processed in the EU, under an approved agreement. Other customers use whatever scores best.
- **Per-task routing.** A small model handles classification and a large one drafts redlines (39.3b). The router picks by task.
- **Planned migrations.** When a retirement notice arrives, the evaluation set says which replacement passes, and the registry switches traffic gradually, starting with a canary (39.2a).

Fallback isn't free. Every secondary model needs its own prompt tuning, evaluations, data-processing agreement and monitoring, and customers may notice differences in output. Many teams keep one fallback for critical features, and accept degraded service (a smaller model, or queued processing) for the rest.

### Managed agent platforms: what you get and what you give

Managed agent platforms take on much of 39.6: running the agent loop, executing tools in sandboxes, storing sessions and memory, tracing, connectors and identity for tools. Some also manage long-running runs and human approvals. What they're good at, and what they cost:

- **Good for:** internal tools and prototypes, standard agent patterns (research, coding, document work), teams without the capacity to build and operate durable execution (39.6b), and organizations whose security review already covers their cloud's platform.
- **What you give up:**
  - control over the loop and its failure handling
  - where state lives, and how easily it moves
  - the ability to enforce your own permission and approval model exactly (39.5a)
  - portability across clouds
  - some predictability in pricing
- **The platform-lifecycle risk.** A managed platform is a product with its own roadmap. The Assistants API retirement is the example: a hosted abstraction that was the recommended approach in 2024 had a shutdown date announced in 2025. Newer platforms may prove more durable, but the risk is structural, and it's the same for every vendor.

A middle path is increasingly common: **agent SDKs** (the OpenAI Agents SDK, the Claude Agent SDK, Google's Agent Development Kit, LangGraph and others) running on your own infrastructure. You get the loop and tool patterns ready-made, and you keep state, permissions and durability under your control. That's often combined with a durable execution engine (39.6b). Some managed platforms also let the sandbox run on your own infrastructure. Claude Managed Agents supports self-hosted sandboxes, for example.

### Evaluating vendors

Compare offerings the way the product will use them:

- **Your evaluation set,** run on each candidate with a prompt tuned for it, reporting intervals (39.7a).
- **Latency percentiles and throughput** at your expected volume, in the regions you'll use.
- **Cost per completed task,** including retries, caching and agent steps.
- **Data terms:** retention, training use, regions, subprocessors, and the data-processing agreement (Module 34).
- **Lifecycle terms:** deprecation notice, snapshot availability, and the provider's track record on retiring products.
- **Operational fit:** rate-limit tiers, support, status history, and whether a second route to the same model exists.

## When It's Appropriate

- **A provider's direct API:** the fastest access to new models and features, for teams without customer requirements that rule it out.
- **A cloud AI platform:** customers requiring processing within an existing cloud agreement, region or network boundary, or organizations that want one bill and one security review for many models.
- **A thin capability-based abstraction:** as soon as a second provider or route is plausible, whether for failover, a customer requirement or a model migration.
- **Fallback routing:** features where an outage has a real cost, such as deadlines, live customer interactions, or contractual uptime.
- **Managed agent platforms:** internal tools, prototypes, and standard agent tasks where speed of delivery matters more than control, especially inside a cloud your organization has already approved.
- **Agent SDKs on your own infrastructure:** agents that are central to the product, need your own permission and approval model, or must run across clouds.

## When It's Unnecessary or Overkill

- **Multi-provider fallback for low-stakes features.** A summary that's unavailable for an hour can wait, and a second provider doubles prompt tuning, evaluation and contracts.
- **A heavy internal AI platform at the start.** One adapter, one registry and the evaluation set are enough until real requirements arrive.
- **A generic layer that hides provider features you need.** If structured output and prompt caching matter, the abstraction has to expose them.
- **Avoiding every hosted feature on principle.** A provider's server-side web search or code execution may be worth depending on, if you'd otherwise build and operate it yourself. Decide deliberately, and note the dependency.
- **Self-hosting to avoid lock-in** when the real exposure is hosted state. Moving the model in-house doesn't help if conversations still live in someone else's product.

## Trade-offs

- **Speed now versus control later.** Hosted features (threads, file search, managed agents) ship features in days, and every one of them is state and behavior someone else controls.
- **Abstraction versus features.** A thin layer takes work per provider. A generic one loses the features that make providers different.
- **Redundancy multiplies work.** Each extra provider or route adds prompt tuning, evaluation runs, contracts, monitoring and a different set of edge cases.
- **Cloud platforms trade immediacy for compliance.** They fit enterprise requirements, sometimes a little behind the providers' own APIs on models and features.
- **Evaluations are the price of flexibility.** Switching models safely requires an evaluation set. Without one, portability is theoretical.
- **Vendor landscapes change quickly.** Product names, features and deprecations shift within months, as this article's own sources show. Anything built on a specific product needs an owner who watches its lifecycle.

## Alternatives

- **Single-provider commitment,** deliberately, with an enterprise agreement, higher rate limits and support, and an evaluation set ready for migrations. For many companies this is the right choice, as long as state stays portable.
- **An AI gateway product or aggregator** (39.7c) that provides routing, fallback and keys across providers as a service, instead of building your own registry and router.
- **Open-weight models on your own infrastructure** (39.3b), which remove provider lifecycle and data-policy concerns for the tasks where they're good enough, at the cost of operating them.
- **Buying the finished capability.** Contract-analysis vendors, document-AI services and support-automation products provide the whole feature. You give up control over it in exchange for not building it.

## How to Achieve It

**1. Inventory dependencies by layer:** model calls, prompts, embeddings, hosted state, managed services. Note what each would take to move.
_Move on when_ every piece of hosted state has either an owner-controlled copy or a documented reason to accept the dependency.

**2. Build the evaluation set** for each AI task (39.7a). It's the precondition for everything else here.

**3. Put a thin, capability-based interface in front of model calls,** with one adapter per provider, and provider-specific features exposed.

**4. Record models in a registry:** capabilities, regions, data terms, retirement dates, and evaluation results per task and prompt version.

**5. Route by requirements,** and add a tested fallback for critical tasks, with a circuit breaker.
_Move on when_ a simulated outage of the primary provider moves critical traffic to the fallback, and its quality stays within your evaluation thresholds.

**6. Decide build or buy for agents deliberately.** Choose a managed platform, or an SDK on your own infrastructure, based on how central the agent is, where its state must live, and whose permission model it has to follow.

**7. Watch the lifecycle.** Track retirement notices and product changes, run evaluations on replacements as soon as they're announced, and migrate on your schedule, not the deadline.

## Implementation

The implementation is TypeScript. It has three pieces: a model registry with capabilities, data terms and evaluation results; two adapters showing how the same structured-output request maps onto different providers' APIs; and a router that picks eligible models for a task and fails over with a circuit breaker.

### A registry of what each model can do and has proven

```ts
type Capability = "structured_output" | "tool_use" | "prompt_cache" | "batch";
type TaskName = "clause_extraction" | "risk_flags" | "redline_draft" | "contract_qa";

interface ModelEntry {
  id: string;                                   // "anthropic:claude-x", "bedrock-eu:claude-x", "openai:gpt-y"
  adapter: "anthropic" | "openai";
  route: "direct" | "bedrock";                  // same model family, different way of reaching it
  model: string;                                // the route's model identifier, pinned (39.3a)
  processingRegions: ("us" | "eu")[];
  zeroDataRetention: boolean;
  capabilities: Set<Capability>;
  retiresAt?: string;                           // from the provider's deprecation notice
  evals: Partial<Record<TaskName, { passRate: number; promptVersion: string; evaluatedAt: string }>>;
}

interface Requirements { task: TaskName; needs: Capability[]; region?: "us" | "eu"; zeroRetention?: boolean; minPassRate: number }

export function eligible(reqs: Requirements, registry: ModelEntry[], today = new Date()): ModelEntry[] {
  return registry
    .filter((m) => reqs.needs.every((c) => m.capabilities.has(c)))
    .filter((m) => !reqs.region || m.processingRegions.includes(reqs.region))
    .filter((m) => !reqs.zeroRetention || m.zeroDataRetention)
    .filter((m) => !m.retiresAt || new Date(m.retiresAt) > today)
    .filter((m) => (m.evals[reqs.task]?.passRate ?? 0) >= reqs.minPassRate)   // no evals, no traffic
    .sort((a, b) => (b.evals[reqs.task]!.passRate) - (a.evals[reqs.task]!.passRate));
}
```

> **Why "no evals, no traffic."** A model enters the eligible list for a task only after it has passed that task's evaluation set with a specific prompt version. That's what turns a retirement notice into a routine change: evaluate the candidates, record the results, and the router starts using whichever passes. It's also what makes the bank's requirement a filter (`region: "eu"`), not a special project.

### One request, two providers

```ts
import Anthropic from "@anthropic-ai/sdk";
import { AnthropicBedrock } from "@anthropic-ai/bedrock-sdk";
import OpenAI from "openai";

interface StructuredRequest { system: string; user: string; schema: Record<string, unknown>; schemaName: string; maxTokens: number; cacheSystem?: boolean }

const anthropic = new Anthropic();
const anthropicBedrock = new AnthropicBedrock({ awsRegion: "eu-central-1" });   // the bank's EU route
const openai = new OpenAI();

export const adapters = {
  async anthropic(m: ModelEntry, r: StructuredRequest): Promise<unknown> {
    const client = m.route === "bedrock" ? anthropicBedrock : anthropic;   // same Messages format
    const res = await client.messages.create({
      model: m.model, max_tokens: r.maxTokens,
      system: [{ type: "text", text: r.system,
                 ...(r.cacheSystem ? { cache_control: { type: "ephemeral" as const } } : {}) }],
      messages: [{ role: "user", content: r.user }],
      output_config: { format: { type: "json_schema", schema: r.schema } },
    });
    if (res.stop_reason !== "end_turn") throw new IncompleteOutput(String(res.stop_reason));
    const text = res.content.find((b) => b.type === "text");
    return JSON.parse(text && text.type === "text" ? text.text : "");
  },

  async openai(m: ModelEntry, r: StructuredRequest): Promise<unknown> {
    const res = await openai.responses.create({     // OpenAI caches long prefixes automatically (39.3b)
      model: m.model, max_output_tokens: r.maxTokens,
      instructions: r.system, input: r.user,
      text: { format: { type: "json_schema", name: r.schemaName, schema: r.schema, strict: true } },
    });
    if (res.status !== "completed") throw new IncompleteOutput(res.status ?? "unknown");
    return JSON.parse(res.output_text);
  },
};
```

> **What the adapter hides and what it doesn't.** It hides parameter names: `output_config.format` versus `text.format`, explicit cache markers versus automatic caching, and different ways of reporting incomplete output. It doesn't hide behavior. The two models may still split a clause differently, which is why the router only uses models with recorded evaluation results for the task, and why each model family gets its own prompt version. The output is validated against the same schema afterwards, whichever adapter produced it (39.3a).

### Routing with failover

```ts
const breaker = new CircuitBreaker({ failureThreshold: 5, windowMs: 60_000, cooldownMs: 120_000 });  // Module 36

export async function runTask(reqs: Requirements, build: (m: ModelEntry) => StructuredRequest) {
  const options = eligible(reqs, registry);
  if (options.length === 0) throw new NoEligibleModel(reqs);   // e.g. no EU model has passed this task yet

  let lastError: unknown;
  for (const m of options.slice(0, 2)) {                         // primary, plus one tested fallback
    if (breaker.isOpen(m.id)) continue;
    try {
      const out = await adapters[m.adapter](m, build(m));
      breaker.recordSuccess(m.id);
      return { output: out, modelId: m.id };                     // logged and traced with the model used (39.7c)
    } catch (err) {
      lastError = err;
      if (!isProviderFailure(err)) throw err;                    // bad input or invalid output: failover won't help
      breaker.recordFailure(m.id);
    }
  }
  throw new AllModelsUnavailable(reqs, lastError);               // caller degrades: queue it, or tell the user
}
```

> **Why only provider failures trigger failover.** Timeouts, 5xx responses and capacity errors mean "try somewhere else." A validation failure or an oversized input would fail on the fallback too, and hide the real problem.

> **The cheapest fallback is often a second route to the same model.** The Bedrock entry uses the same adapter, prompts and message format as the direct one, just a different client, so its evaluation results are usually close. What can differ is features. That's why each route has its own `capabilities` set in the registry. When a caching option or API feature isn't available on a route yet, the entry says so, and `eligible()` won't send a task that needs it there. That's the bank incident, caught by a filter instead of discovered in production.

---

The habit to take from this: for every AI dependency, ask what you'd do if it disappeared in six months. If the answer is "switch the model and rerun the evals," you're renting computation, which is fine. If the answer is "export and rebuild our customers' data," you've handed someone else part of your product, and that should be a decision you made on purpose.
