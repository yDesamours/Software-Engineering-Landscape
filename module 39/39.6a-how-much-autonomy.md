# How Much Autonomy? Workflows, Agents, Planning and Multi-Agent Designs

_Module 39.6a — Machine Learning & LLM-Powered Systems_

## The Problem

Suppose you build an analytics product for online stores. Merchants see dashboards of traffic, conversion and revenue, and the question they ask most often, usually in a support ticket, is some version of "Why did my numbers drop yesterday?" Answering it takes an analyst 30 to 60 minutes: check whether traffic fell or conversion fell, break it down by device, country and channel, look at what changed (a deploy, a new marketing campaign, a price change), check whether the payment provider had an outage.

You build an investigation assistant. It has 14 tools: run a read-only SQL query against the merchant's data, list deploys to their storefront, list marketing campaigns, read the payment provider's status history, read the merchant's own incident notes, and so on. It runs the standard agent loop from 39.5a (think, call a tool, read the result, repeat) with a 40-step limit. On the first demo question, it finds a checkout bug in eight steps, and everyone is impressed.

In the beta with 300 merchants:

- **Simple questions take the long way.** "What was revenue last week?" is one SQL query. The agent takes nine steps and 40 seconds, because it also checks deploys and campaigns "for context."
- **Hard questions wander.** On a genuine investigation, the agent runs variations of the same breakdown query 12 times, gets distracted by a small dip in tablet traffic, and hits the 40-step limit without a conclusion in about a quarter of cases.
- **The context fills up.** Every SQL result stays in the conversation. By step 25 the prompt is 150,000 tokens, each step costs more than the last, the average investigation costs $4, and the model starts losing track of things it found early on.
- **The multi-agent rewrite makes it worse.** The team splits the work across five agents (a planner, a data analyst, a deploy checker, a marketing checker and a report writer) that pass messages to each other. Cost triples. The deploy checker and the data analyst assume different time windows. In one case, the report writer blames a marketing campaign while the data analyst had found a payment-provider outage, because the writer only saw the checkers' summaries.
- **Conclusions can't be checked.** The final report says "the drop was caused by Tuesday's checkout deploy," with confidence and no trail. When merchants push back, nobody can see which queries supported the claim.

The model was capable of each individual step. What went wrong was how much freedom it was given, how the work was structured, and what it was asked to keep in its head.

## What It Is

An **agent** is a system in which the model decides what to do next: which tool to call, with what arguments, whether to keep going or stop. It's contrasted with a **workflow**, where your code decides the sequence of steps and the model performs individual steps within it. This article uses Anthropic's definitions from "Building effective agents": workflows are "systems where LLMs and tools are orchestrated through predefined code paths," and agents are "systems where LLMs dynamically direct their own processes and tool usage."

That's not a binary choice. It's a dial, and the main design decision in this area is **how much autonomy each part of a feature needs**:

```
 less autonomy ◀──────────────────────────────────────────────────────────────▶ more autonomy
 single call      workflow:            planner/executor:        agent loop:        multi-agent:
 (39.3a)          code fixes the       model makes a plan,      model picks each   several agents,
                  steps; model         code runs it, model      step as it goes    each with its own
                  does each one        re-plans on surprises    (ReAct)            loop and context
 cheap, predictable, testable                                   flexible, costly, harder to test
```

More autonomy handles more varied tasks, at the cost of more calls, more tokens, more variance and harder testing. The rule that follows is simple and widely ignored: **use the least autonomy that handles the task.**

Three other ideas from this article come up at every point on the dial:

- **ReAct** is the basic agent loop: reason about what to do, act (call a tool), observe the result, repeat.
- **Planning** separates deciding what to do from doing it.
- **Context engineering** decides what the model sees at each step, since everything it has seen stays in its context and costs attention, tokens and money.

Tool calling itself is 39.5a. Making agents survive restarts, wait days for human approval and remember across sessions is 39.6b. Evaluating agents is 39.7.

## Recognizing the Problem

- Simple, predictable requests go through an open-ended agent loop.
- Agents hit their step limit regularly, or repeat the same tool calls.
- Cost and latency per task vary by 10× or more between similar requests.
- Conversations accumulate large tool results, and later steps ignore early findings.
- Several agents with human job titles (planner, researcher, critic, writer) pass messages to each other.
- Agents working in parallel make inconsistent assumptions, and the final output contradicts parts of the work.
- Final answers can't be traced to the specific tool results that support them.
- Nobody can say which part of the system is a workflow and which is an agent.

## How It Works

### Why autonomy is expensive: errors compound

Each step an agent takes is a chance to go wrong: a misread result, a wrong argument, a distraction. If each step succeeds 95% of the time and a task needs every step right, then:

```
 per-step success      5 steps   10 steps   20 steps   40 steps
 99%                   95%       90%        82%        67%
 95%                   77%       60%        36%        13%
 90%                   59%       35%        12%         2%
```

Real agents recover from some mistakes, so it's not quite this bad. But the shape is right: **long, unstructured chains of model decisions fail more often than short ones**, and a task that needs 40 free-form steps is fragile. Every technique below either shortens the chain, moves decisions from the model to code, or makes mistakes recoverable.

### Workflows first

Most of the value in LLM features comes from workflows: fixed sequences with a model at specific steps. Anthropic's taxonomy names the common shapes:

- **Prompt chaining:** a fixed sequence of calls, each using the previous output, with checks in between. For example: draft a summary, check it against the source, then format it.
- **Routing:** classify the request first, then send it to a specialized path. "What was revenue last week?" goes to a one-query path. "Why did conversion drop?" goes to the investigation path. This alone fixes the first incident.
- **Parallelization:** run independent calls at once and combine them, either by splitting a task into sections or by asking the same question several times and voting.
- **Orchestrator–workers:** a model breaks a task into subtasks that can't be known in advance, workers handle them, and the orchestrator combines the results. This is where workflows start to become agents.
- **Evaluator–optimizer:** one call produces a result, another critiques it against criteria, and the first revises. It helps when criteria are clear and a critique genuinely improves the result.

Workflows are cheaper, faster and far easier to test than agents, because the paths are known. Reach for an agent loop only for the part of a task where the path genuinely can't be known ahead of time.

### ReAct: the basic agent loop

The **ReAct** pattern (Yao et al., 2023) is the loop from 39.5a, seen as a way of working. The model reasons about the situation, takes an action, observes the result, and reasons again. It fits when the next step depends on what was just learned: an investigation, debugging, research, a support conversation that needs lookups.

Left alone, ReAct agents show the failures from the Problem:

- **Tunnel vision:** following the first interesting signal (the tablet dip) without checking whether it explains the whole effect.
- **Repetition:** retrying slight variations of a query, because nothing records what's already been tried and learned.
- **No stopping rule:** continuing to gather context "to be thorough" long after the answer is clear, or giving up at the step limit with nothing.

Structure fixes these: a plan, a record of findings, and explicit stop conditions.

### Planning: decide, then do

**Planner/executor** (also called plan-and-execute) splits the loop:

1. **Plan.** One model call produces an explicit plan: for an investigation, a list of hypotheses to test, each with the evidence that would confirm or rule it out.
2. **Execute.** Each step of the plan is carried out, by code, by a narrow worker agent, or by a workflow.
3. **Re-plan.** When results are surprising (every hypothesis ruled out, or a new lead), the planner revises the plan with the findings so far.

For "why did conversion drop yesterday," a plan might be:

```
 H1  traffic fell, not conversion         → compare sessions vs. the same weekday, 4 weeks
 H2  checkout broke for a segment          → conversion by device, browser, payment method
 H3  a deploy changed checkout             → deploys in the last 48 h touching checkout
 H4  payment provider problems             → provider status + declined-payment rate by hour
 H5  campaign mix changed                  → sessions and conversion by channel/campaign
```

Planning helps in several ways:
- **The work becomes visible.** A user, or an evaluator, can see the plan, and a person can approve or edit it before anything expensive or consequential happens.
- **The chain gets shorter and more parallel.** Five hypotheses are five short, independent investigations, not one 40-step wander.
- **The plan is a checklist.** "Every hypothesis has a verdict" is a clear stopping condition.
- **It's also a security pattern.** Fixing the plan before reading untrusted content limits what injected text can make the agent do (39.5b).

The cost is rigidity. A plan made before seeing any data can miss the real cause, which is why re-planning on surprise matters.

### Single agent or several?

There are two very different reasons to use more than one agent, and only one of them usually works.

**Parallel workers with isolated contexts: often worth it.** When a task splits into independent parts, each part can be handled by its own worker with its own context window, its own small set of tools and its own budget. The worker returns a **condensed result**, not its whole transcript. The detailed exploration stays in the worker's context, and the lead agent sees only the conclusions. Anthropic's multi-agent research system, in which a lead agent directs parallel search subagents, outperformed a single agent by 90.2% on their internal research evaluation. It also used about 15 times as many tokens as a chat interaction, against about 4 times for a single agent. That's a good trade for broad research questions worth the cost, and a bad one for most product features.

**Agents as a simulated team: usually not.** Agents with job titles (planner, analyst, critic, writer) passing messages to each other recreate the problems of a team with poor communication, without the benefits. Each agent sees a partial, reworded picture. Cognition's essay "Don't Build Multi-Agents" states the failure precisely: "actions carry implicit decisions," and parallel agents that can't see each other's decisions make conflicting ones. That's the report writer blaming the campaign.

The rules that follow:

- **Parallelize reading, not deciding.** Workers gather and test (check H3, check H4), and one agent, or code, makes decisions and writes the result.
- **Give workers the full task context,** not a one-line instruction. Each worker needs the question, the time window, the definitions and what other workers are checking, so they make compatible assumptions.
- **Return evidence, not prose.** A worker's result is a verdict plus the specific evidence (query IDs and key numbers), so the lead can check and combine it.
- **Default to one agent** when the subtasks depend on each other, as in most coding and most writing. Anthropic notes the same limit.

### State and context within a task

Everything an agent has seen stays in its context: every tool result, every intermediate thought. Context is a budget: large contexts cost more per step (39.3b), and models use long contexts less reliably. **Context engineering** for agents means deciding what stays in view:

- **Trim tool results at the source.** A SQL tool returns the first 20 rows plus a row count and summary statistics, not 5,000 rows. The full result is stored with an ID, and the agent can fetch more if it needs to (the "just-in-time" approach).
- **Keep an explicit record of state.** Maintain a structured record (the plan, each hypothesis's status, the evidence found and queries already run) that your code stores and the model reads and updates. That turns "what have I tried?" from a memory test into a lookup, and it's what lets a new context, or a new process after a restart (39.6b), continue the task.
- **Clear or compact old results.** Once a result has been summarized into the record, drop the raw result from the conversation. When the context still grows too large, **compaction** replaces the history with a faithful summary and continues.
- **Isolate exploration in workers.** A worker's 30 queries never enter the lead agent's context. Only its finding does.
- **Detect loops.** Refuse, or at least flag, a tool call identical to an earlier one in the same task.

### Evidence, verification and stopping

Two practices make agent output trustworthy enough to show a merchant:

- **Claims cite evidence.** Every statement in the final report references the query or tool result that supports it, and the UI links to it. The synthesis step is instructed, and checked, to use only findings that exist in the record.
- **An explicit stopping rule.** Stop when every hypothesis in the plan has a verdict, or when a confirmed cause explains the size of the drop. When budgets run out, stop and report what was established and what wasn't. "H4 confirmed: declined payments rose from 3% to 41% between 14:10 and 16:30; H1–H3 ruled out; H5 not checked" is useful. "I couldn't finish" isn't.

**Budgets** (steps, tokens, time and cost) belong at every level: per worker, per task and per customer (39.7).

## When It's Appropriate

- **Workflows:** anything with a predictable sequence, such as extract–check–format, classify-and-route, or summarize-then-translate. That's most LLM features.
- **Routing in front of everything:** whenever requests vary in difficulty, so easy ones take the cheap path.
- **A single ReAct agent:** open-ended tasks where each step depends on the last, with a modest number of steps, such as troubleshooting a customer's integration, or a support conversation that needs several lookups.
- **Planner/executor:** investigations and analyses with a natural set of hypotheses or sub-questions, where a visible plan helps users trust the result and lets a person approve it first.
- **Parallel workers:** questions that split into independent, read-heavy parts, like the five hypotheses, or broad research across many sources, where the value of the answer justifies several times the tokens.

## When It's Unnecessary or Overkill

- **An agent where a workflow would do.** If you can draw the flowchart, write it as code. The model does the steps, not the routing.
- **Multi-agent role-play.** Planner, critic and writer personas exchanging messages add cost and inconsistency. One agent with a good prompt and a plan usually does better.
- **Parallel workers for dependent tasks.** When step two needs step one's decisions, workers either wait for each other or guess, and guessing produces conflicts.
- **Long autonomous loops for high-stakes actions.** Where mistakes are expensive, shorten the chain and add approvals (39.5a, 39.6b), rather than trusting 30 unreviewed decisions.
- **Evaluator–optimizer loops without clear criteria.** A critic with no concrete standard produces different opinions, not better output, and doubles the cost.

## Trade-offs

- **Autonomy costs predictability.** The same request can take very different paths, costs and times. Testing becomes statistical (39.7).
- **Token costs multiply.** Agents use several times the tokens of a single call, and multi-agent systems several times more again. Every structural choice here is also a cost decision.
- **Latency grows with steps.** Sequential steps add up to tens of seconds or minutes. Parallel workers help with wall-clock time, not with cost.
- **Planning can be wrong early.** A plan made before any data is seen can miss the real cause. Re-planning adds calls and complexity.
- **Context management loses information.** Trimming, clearing and compaction all discard detail. Occasionally, the detail discarded is the one that mattered.
- **Multi-agent designs add coordination failures:** conflicting assumptions, duplicated work, and synthesis from summaries that lost nuance.
- **Debugging is harder.** A bad answer might come from the plan, a worker, a tool, a trimmed result or the synthesis. Traces of every step are essential (39.7).

## Alternatives

- **A single well-prompted call** with the right data in the context (39.3a, 39.4), for questions that don't actually need exploration.
- **Precomputed analysis.** For "why did my numbers drop," scheduled jobs (Module 10) can compute standard breakdowns and anomaly flags (39.1a) every night, so an investigation starts from facts, not from zero. Often, a dashboard of those breakdowns answers the question without any model at all.
- **Deterministic diagnostics with an LLM narrator.** Code runs a fixed battery of checks (the five hypotheses as queries), and a model writes the explanation from the results. This is a workflow, and it's much more predictable.
- **Human analysts with AI assistance,** for rare, high-value investigations where judgment matters more than speed.

## How to Achieve It

**1. Map the requests.** Collect real requests and group them by how predictable their path is.
_Move on when_ you know what share could be served by a fixed workflow.

**2. Build the workflows and a router.** Handle the predictable majority with fixed paths, and route only genuinely open-ended requests further.

**3. For open-ended requests, start with one agent, and add structure.** Add trimmed tool results, a state record, loop detection, budgets and an explicit stopping rule.

**4. Add planning where tasks have natural parts.** Make the plan visible, and re-plan on surprise.
_Move on when_ runs reliably end with every plan item resolved or explicitly left open.

**5. Parallelize independent, read-heavy parts with workers.** Give each worker full task context and a budget, and have it return verdicts with evidence. Keep decisions in one place.
_Move on when_ measured quality improves enough to justify the measured cost.

**6. Require evidence for every claim** and check citations against the record before showing the result.

**7. Trace and evaluate every run** (39.7), and revisit the autonomy level as models improve. Some agent steps become workflow steps over time, and some workflows can take on more autonomy.

## Implementation

The implementation is TypeScript. It shows the structure, not a framework: a router in front, then a planner that produces hypotheses as structured output, parallel workers with isolated contexts and budgets, and a synthesis step that may only use recorded evidence. Model calls go through two helpers: `structured()` (39.3a) and `runAgentLoop()` (the loop from 39.5a, with budgets).

### Route, then plan

```ts
const Route = z.object({ kind: z.enum(["metric_lookup", "investigation", "other"]) });
const Plan = z.object({
  hypotheses: z.array(z.object({
    id: z.string(),                      // "H1"
    claim: z.string(),                   // "Checkout broke for a segment"
    check: z.string(),                   // what evidence would confirm or rule it out
  })).min(1).max(6),
});

export async function answer(merchant: Merchant, question: string, window: TimeWindow) {
  const { kind } = await structured(Route, ROUTER_PROMPT, question);        // one cheap call
  if (kind === "metric_lookup") return metricWorkflow(merchant, question, window);
  if (kind === "other") return helpWorkflow(merchant, question);

  const plan = await structured(Plan, PLANNER_PROMPT, { question, window, metricsGlossary });
  const record = await investigations.create(merchant, question, window, plan);   // the state record
  return investigate(merchant, record);
}
```

> **The router is the biggest single saving.** In the beta, most questions were lookups. Sending them down a one-query workflow makes them fast and cheap, and leaves the agent budget for questions that need it. The router can be a small model. When unsure, it should choose `investigation`, since the costly mistake is treating a real investigation as a lookup.

### Workers with isolated context, returning evidence

```ts
const Finding = z.object({
  hypothesis: z.string(),
  verdict: z.enum(["confirmed", "ruled_out", "inconclusive"]),
  evidence: z.array(z.object({ resultId: z.string(), fact: z.string() })),  // resultId: a stored tool result
  magnitude: z.string().nullable(),        // "explains ~80% of the drop", if measurable
});

async function investigate(merchant: Merchant, record: Investigation) {
  const shared = {                          // every worker gets the same framing
    question: record.question, window: record.window, glossary: metricsGlossary,
    otherHypotheses: record.plan.hypotheses.map((h) => `${h.id}: ${h.claim}`),
  };

  const findings = await Promise.all(record.plan.hypotheses.map((h) =>
    runAgentLoop({
      system: WORKER_PROMPT,               // "Test ONE hypothesis. Return a Finding. Cite resultIds."
      input: { ...shared, hypothesis: h },
      tools: readOnlyTools(merchant),       // SQL (read replica), deploys, campaigns, provider status
      output: Finding,
      budget: { steps: 10, tokens: 60_000, seconds: 90 },
      onToolResult: (r) => results.store(record.id, r),   // full result stored; model sees a trimmed view
    }).catch((err) => ({ hypothesis: h.id, verdict: "inconclusive" as const, evidence: [],
                         magnitude: null, error: String(err) }))));

  await investigations.saveFindings(record.id, findings);
  return synthesize(record, findings);
}
```

> **Why every worker sees the other hypotheses and the same window.** This is what prevents the conflicting assumptions from the multi-agent rewrite. The workers can't see each other's progress, but they share the question, the exact time window and the definitions, and each knows what the others are checking. A worker that finds something relevant to another hypothesis records it as evidence, and the synthesis step reconciles it.

> **A failed worker is a finding, not a failure.** If one hypothesis times out or its tool errors, the investigation still reports the other four, with that hypothesis marked inconclusive. A report that says what wasn't checked is more useful than no report.

### Synthesis that can only cite what exists

```ts
async function synthesize(record: Investigation, findings: FindingT[]) {
  const report = await structured(Report, SYNTHESIS_PROMPT, { question: record.question, findings });

  const known = new Set(findings.flatMap((f) => f.evidence.map((e) => e.resultId)));
  const unsupported = report.claims.filter((c) => c.resultIds.length === 0 || c.resultIds.some((id) => !known.has(id)));
  if (unsupported.length) {
    return { status: "needs_review" as const, report, unsupported };   // shown to support, not the merchant
  }
  return { status: "ready" as const, report };   // each claim links to its stored query and result
}
```

> **Why synthesis gets findings, not transcripts.** The lead step reads five structured findings, a few thousand tokens, instead of five workers' worth of raw SQL output. It can't be distracted by the tablet dip unless a worker judged it relevant, and every claim it makes has to point at a stored result. This is the fix for "caused by Tuesday's deploy" with no trail: either the claim cites the deploy list and the conversion-by-hour query, or it doesn't reach the merchant.

---

The habit to take from this: before building an agent, draw the task. Mark every step whose path you could write down in advance, and make those code. What's left, the steps where the next move really depends on what was just learned, is where a model should choose. Keep that part as small as the task allows, give it a plan and a record, and make it show its evidence.
