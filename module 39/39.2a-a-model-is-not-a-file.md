# A Model Is Not a File: Serving, Versioning and Rolling Out Classical Models

_Module 39.2a — Machine Learning & LLM-Powered Systems_

## The Problem

Suppose you run a food-delivery app. At checkout, customers see an estimate: "Arrives in 35–45 min." Today that number comes from a formula: the restaurant's average prep time plus distance divided by an average courier speed. It's wrong often enough that late deliveries are the top reason for refunds.

A data scientist trains a gradient-boosted tree model on six months of orders. It uses 40 features: the restaurant's recent prep times, how many orders it has open right now, distance, hour of day, weather, how many couriers are nearby. In her notebook, the model cuts the average error from 11 minutes to 6. She sends the backend team a file, `eta_model.pkl`, and a notebook showing how the features are computed.

That's where the model's real journey starts, and over the next six weeks it goes wrong four times.

**Week 1: the model can't run where the app runs.** The checkout service is written in TypeScript. A `.pkl` file is a Python pickle, so it only loads in Python, with the same library versions it was saved with. The team wraps it in a small Flask service. The estimate is requested on every cart view, 1,200 times a second at dinner time, with a 30 ms budget. The Flask service answers in 400 ms at p99, and checkout pages start timing out.

**Week 3: the live estimates are wrong in a way the notebook never was.** After a rewrite for speed, the service returns in 4 ms, but its estimates run 6 minutes too long at lunchtime, and checkout conversion drops 3%. Nothing is broken; the backend team re-implemented the features from the notebook, and two of them came out different:

```
feature                      notebook (training)              service (live)
restaurant_prep_p50_7d       ready_at − accepted_at,          ready_at − created_at,
                             rolling 168 hours                calendar days in UTC
hour_of_day                  restaurant's local time          server time (UTC)
```

Each difference looks like a detail. Together, they mean the model is being shown inputs it never saw during training.

**Week 4: new restaurants get impossible promises.** A restaurant that joined yesterday has no prep-time history. In training, missing values were filled with the median, 14 minutes. The service fills them with 0. New restaurants get estimates of 11 minutes, almost every one of those orders arrives late, and the refunds land on the restaurants the business most wants to keep.

**Week 6: nobody can tell which model said what.** Version 7 of the model is copied over `eta_model.pkl` in the storage bucket. The service loads the file at startup, so for a day, pods that restarted run version 7 while the rest run version 6. The refund rate climbs. Rolling back means finding the old file, and the logs record estimates without saying which model produced them, so nobody can even measure whether version 7 was the cause.

None of these is a modeling problem. The model was good. What went wrong is everything between the notebook and the checkout page.

## What It Is

**Model serving** is running a trained model inside a production system: taking a request, building the model's inputs, producing a prediction within a latency budget, and recording what happened. Around it sit three related practices:

- **Versioning** treats each trained model as an immutable, named release, with its feature definitions and preprocessing attached.
- **Feature consistency** makes sure the model sees the same inputs in production that it saw in training. When it doesn't, that's **training–serving skew**, and it was the cause of weeks 3 and 4.
- **Rollout** puts a new version in front of real traffic in steps (shadow, canary, A/B test) so you learn whether it's better before it's everywhere.

The idea that ties these together is in the title: the thing you deploy isn't a file of weights. It's a **bundle**: the weights, the exact feature definitions and preprocessing they expect, the data they were trained on, and a version that every prediction carries with it.

Keeping a model healthy after launch (monitoring, drift, retraining and checking for bias) is 39.2b.

## Recognizing the Problem

- The model's output format only loads in one language, and that isn't the language of the service that needs it.
- Feature logic exists twice: once in a notebook or training pipeline, and again in the application.
- Offline accuracy is good, and live accuracy is worse, with no leakage to explain it (39.1a covers leakage).
- Predictions for new users, new items or rows with missing data are strange or extreme.
- Prediction logs don't say which model version made each prediction.
- A new model is deployed by overwriting a file or changing a path, and rollback means finding the old one.
- The model endpoint has no timeout, or the caller has no answer when it fails.
- "The new model is better" means it scored better offline, and nobody measured what it did to the product.

## How It Works

### Four places a model can run

The first decision is where predictions are computed. That decision depends mostly on when the inputs are known and how fast the answer is needed.

```
                  when it runs              latency         good for
 batch            nightly / hourly job      none at read    churn scores, lead scores,
                  writes scores to a table  (a DB lookup)   "customers like you" lists
 embedded         inside the app process    < 1 ms          small models, strict budgets,
                  (ONNX, native library)                    one consuming service
 model server     separate service,         a network hop   big or GPU models, many callers,
                  called over HTTP/gRPC     + inference     independent release cadence
 streaming        consumer on an event      seconds         scoring as events happen
                  stream (Kafka, 37.2)                      (a transaction, a sensor reading)
```

**Batch prediction** is the most underrated option. If the inputs don't change between the scoring run and the moment the score is used, you can compute every score ahead of time and store them. A churn score used by the account team the next morning, or a weekly "invoices likely to be paid late" list, needs no serving infrastructure at all: a scheduled job (Module 10) writes a table, and the app reads it like any other table. The cost is freshness. A score computed at 2 a.m. doesn't know what happened at 9 a.m. It also wastes work on entities nobody looks at. The delivery estimate can't be batch: it depends on the cart, the address and how busy the restaurant is right now.

**Embedded (in-process) serving** loads the model into the application itself. The enabler is a portable model format. **ONNX** is the common one: models from scikit-learn, LightGBM, XGBoost and PyTorch can be converted to it, and ONNX Runtime runs them from Python, Java, C#, C++, JavaScript and (through community bindings) Go. A tree model with 40 features scores in well under a millisecond on a CPU, with no network hop and nothing new to operate. That's what fixed week 1. The costs:

- The model shares CPU and memory with the app.
- Every service that needs the prediction has to load and update the model separately.
- If the model is baked into the app's container image, a new model means a new app release. Loading it from a registry at startup or on a signal avoids that.

**A model server** is a separate service whose only job is inference. You give it a model artifact, and it exposes an HTTP or gRPC endpoint. Options include:

- general-purpose servers: TensorFlow Serving, and NVIDIA's Triton Inference Server (now branded Dynamo-Triton), which serves many formats and batches requests on GPUs
- Python-first frameworks: BentoML, Ray Serve and LitServe
- KServe, which runs any of these on Kubernetes with a standard inference protocol
- managed platforms: SageMaker, Vertex AI and Databricks Model Serving

TorchServe, the PyTorch project's server, has been in limited maintenance since 2025, so it's a poor choice for new work.

A model server makes sense when the model needs a GPU, is too big to load into every app instance, is called by several services, or is released on a different schedule from the apps. You pay for it with a network hop, another service to scale and monitor, and a new failure mode: the model can be down while the app is up.

**Streaming** scores events as they arrive, by running the model inside a consumer on an event stream. It fits when the prediction triggers an action (flag this payment, alert on this reading) rather than answering a user who is waiting.

Many systems use more than one. A recommendation feature might compute candidates in batch overnight and rank them with an embedded model at request time.

### The endpoint is a product API

Whether the model is in-process or behind a server, the rest of the product calls it through an interface. A few decisions make that interface survivable:

- **Return the model version and a prediction ID with every answer.** The ID is what joins this prediction to its outcome later (the actual delivery time), which you need for monitoring and training (39.2b). The version is what makes week 6 debuggable.
- **Decide who computes the features.** If callers send finished features, every caller holds a copy of the feature logic, and every copy can drift. If callers send IDs and context (`restaurantId`, `dropoff`, `cartTotal`) and the prediction service builds the features itself, there's exactly one implementation. The second design is almost always better, because it makes skew a single-team problem.
- **Keep the contract stable across model versions.** Output a number in product units (minutes, or a calibrated probability), not raw model scores that change meaning when the model is retrained. The API has its own version (Module 33). A new model is not a new API.
- **Always have a fallback.** Set a strict timeout, and when the model fails or times out, answer from a simple heuristic: the old formula. Mark the response `source: "fallback"` so fallbacks are counted and don't pollute training data. A slow model should cost accuracy, not checkout.
- **Offer a batch form when callers need many predictions.** Ranking 200 restaurants one HTTP call at a time is 200 network hops. One call with 200 rows is one hop, and model servers can batch the inference itself too.

### Training–serving skew

Skew is any difference between what the model saw in training and what it sees in production. The week 3 and week 4 incidents show its most common causes:

- **Two implementations of a feature.** One is written in pandas for training and one in TypeScript for serving, and they differ in time windows, time zones, which timestamp counts as "start," or how they round.
- **Different data sources.** Training reads the warehouse, which is cleaned and deduplicated overnight. Serving reads the production database or a cache, which isn't.
- **Preprocessing outside the model.** Scaling, encoding categories and filling missing values were done in the notebook and never saved with the model, so serving guesses.
- **Missing values encoded differently.** A missing value became the median in training and 0 in serving, as in week 4. Tree libraries can learn from "missing" as its own signal, but only if serving passes it as missing (`NaN` or null) in the same way.

There are four fixes, each covering more than the one before:

1. **Put preprocessing inside the model artifact.** A scikit-learn `Pipeline` that includes its scaler and imputer can be exported as one ONNX graph. The bundle then carries its own preprocessing, and serving can't guess wrong.
2. **Compute features in one place, and train on what serving logged.** The prediction service writes the exact features it used next to each prediction (the decision log from 39.1a). Training reads that log instead of recomputing features. Google's _Rules of ML_ calls this the best way to make sure you train like you serve. Its limitation: a brand-new feature has no logged history, so you have to wait for data to accumulate or backfill it carefully.
3. **Use a feature store** when many models and teams share features (next section).
4. **Test for skew continuously.** Take a sample of logged live predictions, recompute their features offline for the same entity and moment, and compare them feature by feature. A feature whose values differ, or which is null in one place and not the other, has skew. This check would have caught week 3 in shadow mode, before any customer saw an estimate.

### Feature stores

A feature store is a system that manages feature definitions and serves their values in two ways:

```
           feature definition (one, versioned)
           "restaurant_prep_p50_7d = median(ready_at − accepted_at),
            rolling 168 h, by restaurant_id"
                 │                                   │
     batch/stream computation              materialization
                 ▼                                   ▼
  OFFLINE STORE (warehouse)               ONLINE STORE (key-value, ms reads)
  full history, every value with          latest value per key
  the time it became true
                 │                                   │
  point-in-time join for training:        lookup at request time:
  "values as of each order's              "values for restaurant 812, now"
   checkout moment"
```

It provides two things that are hard to build yourself. First, **one definition** produces both the training values and the serving values. Second, **point-in-time-correct joins** mean that when you build a training set for orders from March, each row gets feature values as they were at that order's moment, not today's values. That's the leakage from 39.1a, prevented by the storage layer rather than by care.

Options include Feast (open source; it uses your own warehouse and a key-value store such as Redis), Hopsworks, and the feature stores in cloud ML platforms (SageMaker, Vertex AI, Databricks, which acquired Tecton in 2025).

A feature store is a platform, and you have to run it. For one team with two models, a well-kept logged-features table and the skew test above usually do the same job at a fraction of the cost. Feature stores earn their place when several teams reuse the same features across many models, or when features need streaming freshness.

### Versioning: bundles and a registry

Each training run produces an **immutable bundle**, stored under its version and never overwritten:

- the weights, in a portable format
- the feature spec: names, order, and a version of the feature definitions it expects
- preprocessing, ideally inside the model graph
- where its training data came from and the date range it covers
- its offline evaluation results

A **model registry** (MLflow's is the most common, and cloud platforms have their own) records the versions and lets you point named **aliases** such as `champion` and `challenger` at them. Serving loads "whatever `champion` points to." Promoting a model moves the alias, and rolling back moves it back. Nothing is overwritten, so rollback takes seconds and history is kept.

The feature-spec version has one job: to refuse to run a model with features it wasn't trained on. If the service's feature code changes `restaurant_prep_p50_7d`, it bumps its spec version, and a model that expects the old version won't load. That turns a silent week-3 problem into a deployment error.

### Rollout: shadow, canary, A/B

A model that looks better offline can still be worse for the product. Offline evaluation can't measure what the model does to users, and live data always differs from historical data in some way. So new versions go through steps:

```
 shadow            canary               A/B test                 champion
 scores live       serves 1–5% of       serves a random 50%,     serves everyone;
 traffic, result   users; watch         measure the product      old model kept
 only logged       latency, errors,     metric for weeks         as the fallback
                   fallback rate
 ───────────────▶ ─────────────────▶ ────────────────────────▶
 catches: skew,    catches: load,       catches: "more accurate
 crashes, latency  memory, edge cases   but worse for the business"
```

- **Shadow mode** runs the new model on every request (or a sample) and logs its output without using it. It catches crashes, latency problems and skew with no user impact. Compare its predictions with the champion's, and once outcomes arrive, compare their errors.
- **A canary** serves the new model to a small, fixed slice of users to check that it behaves under real load.
- **An A/B test** splits users at random and compares a **product metric**, not model accuracy. In the delivery scenario, version 7 had a lower average error but was more often too optimistic, and late deliveries cost far more than early ones. Refunds went up even though the "better" model was more accurate on average. Only a test measuring refunds and conversion shows that. Experiment design, sample sizes and sticky assignment belong to Module 26. The ML-specific points are to randomize by user rather than by request (so each customer sees consistent estimates), and to decide the success metric before the test starts.

For rankers and recommenders, **interleaving** compares two models faster than A/B tests do: each user sees one list that mixes results from both, and clicks show which model's items people prefer. **Multi-armed bandits** shift traffic toward the better model as evidence arrives, trading a clean measurement for less time spent on the loser.

## When It's Appropriate

This is about which serving pattern fits which situation, since any model in production needs some version of all of the above.

- **Batch:** a churn score for 30,000 accounts, used by the success team each morning. A nightly job writes a table, and there's nothing to serve.
- **Embedded:** the delivery estimate. It's a 40-feature tree model, 1,200 requests a second at peak, a 30 ms budget, and one service that needs it.
- **Model server:** an image-moderation model that needs a GPU and is called by the upload service, the profile service and the admin tool. Or a model the ML team retrains weekly while the apps release on their own schedules.
- **Streaming:** scoring each payment event for risk within seconds of it arriving, so a hold can be placed before the payout job runs.
- **A feature store:** four teams building a dozen models that share the same restaurant, courier and customer features, some of which need to be fresh within minutes.
- **A full rollout sequence:** any model whose mistakes cost money or trust, such as prices, estimates shown to customers, or fraud blocks.

## When It's Unnecessary or Overkill

- **A model server for one small model with one caller.** Embedding it avoids a service, a network hop and a failure mode.
- **Real-time serving for scores that are read once a day.** Batch is cheaper and has no latency or uptime concerns.
- **A feature store for one team and one or two models.** Logged features and a skew check give most of the benefit.
- **Kubernetes-based serving platforms before you have more than a couple of models.** KServe and similar tools pay off with many models and teams. For one, a container with a model file and a health check is enough.
- **Long A/B tests for low-stakes internal tools.** A shadow comparison and a short canary are enough when mistakes are cheap and easy to notice.
- **GPU serving for tabular models.** Tree models run fast on CPUs. GPUs matter for large neural networks, which includes most image, audio and language models.

## Trade-offs

- **Every serving pattern adds a moving part.** Batch adds a job that can fail silently and data that goes stale. Embedding adds memory and CPU load to the app and couples the model to every service that uses it. A model server adds a network hop, capacity planning and a way for the model to be down while the app is up.
- **Converting models has limits.** Not every operation or custom preprocessing step converts to ONNX, and conversions can change results slightly. Check converted predictions against the originals on real data before trusting them.
- **One feature implementation means one owner.** Centralizing features in a prediction service or feature store removes skew, but every model now depends on that service's latency and availability.
- **Training on logged features slows down new features.** A new feature has no logged history, so it either waits for data to accumulate or gets backfilled, which brings back the risk of skew for that one feature.
- **Rollout takes time.** Shadow, canary and an A/B test can take weeks before a better model reaches everyone. Shadow also doubles the inference cost while it runs.
- **Fallbacks can hide failure.** A model that times out 20% of the time still returns answers, just worse ones. The fallback rate has to be monitored and alerted on like an error rate.
- **Version bookkeeping is real work.** Registry, aliases, feature-spec versions and a version on every prediction are process and tooling someone has to keep up.

## Alternatives

- **A managed ML platform** (SageMaker, Vertex AI, Databricks, Azure ML) provides the registry, serving, feature store and monitoring together. You trade control and portability for not building them, and you pay per endpoint, which adds up with many small models.
- **Rewriting the model in the application language.** A logistic regression is a list of weights and a dot product. A small decision tree is a set of `if` statements. For very simple models, generating code from the model (or writing it by hand) removes the runtime dependency. It breaks down beyond simple models, and every retrain means regenerating code.
- **Rules or heuristics that the model's findings inform.** Sometimes the model's main value is showing which signals matter. A formula using the top three features might capture most of the gain with none of the serving cost.
- **An LLM called over an API** (39.3). For text or image tasks, a hosted model removes your serving problem entirely, replacing it with per-call cost, latency and a dependency on the provider.

## How to Achieve It

**1. Choose where the model runs.** Pick batch, embedded, server or streaming using the questions above: when are the inputs known, how fast must the answer be, and how many services need it.
_Move on when_ the choice is written down with the latency budget and expected request rate.

**2. Define the bundle and the registry.** Export to a portable format with preprocessing inside. Store bundles immutably with their feature spec and training data range. Load by alias, never by overwritten path.
_Move on when_ a rollback is a single alias change and you've done one in staging.

**3. Build the endpoint with one feature implementation.** Callers send IDs and context, the service computes features, and every response carries a prediction ID, model version and source. Add a timeout and a heuristic fallback.

**4. Log every prediction with its features.** This is the input for skew checks, monitoring and the next training set.

**5. Run in shadow mode and test for skew.** Compare logged live features with offline recomputation, and the new model's predictions with the current method's.
_Move on when_ skew is near zero for every feature and latency is inside the budget at peak traffic.

**6. Canary, then A/B test on a product metric.** Pick the metric before starting. Keep the old model as the fallback for a while after promotion.

**7. Add a feature store only when features are shared.** Move to one when several models or teams reuse the same features, or need them fresher than your logs can provide.

## Implementation

The implementation is TypeScript, serving an ONNX model in-process with `onnxruntime-node`, the embedded option that fixed week 1. It shows the bundle that refuses mismatched features, an endpoint with a single feature implementation and a fallback, and a router for canary and shadow traffic.

### A bundle that checks its features

```ts
import * as ort from "onnxruntime-node";

interface ModelBundle {
  version: string;                            // "eta-2026-09-14.3": immutable, never overwritten
  onnxPath: string;                           // preprocessing is inside the graph
  featureSpec: { version: string; names: string[] };
}

export class EtaModel {
  private constructor(readonly bundle: ModelBundle, private session: ort.InferenceSession) {}

  static async load(bundle: ModelBundle): Promise<EtaModel> {
    if (bundle.featureSpec.version !== FEATURE_SPEC_VERSION) {
      throw new Error(
        `model ${bundle.version} was trained on features ${bundle.featureSpec.version}; ` +
        `this service computes ${FEATURE_SPEC_VERSION}`);
    }
    return new EtaModel(bundle, await ort.InferenceSession.create(bundle.onnxPath));
  }

  async predict(features: EtaFeatures): Promise<number> {
    // Order comes from the bundle, not from the object's key order.
    // Missing stays missing (NaN): the trees learned what "no history" means.
    const row = this.bundle.featureSpec.names.map((n) => features[n] ?? NaN);
    const input = new ort.Tensor("float32", Float32Array.from(row), [1, row.length]);
    const out = await this.session.run({ [this.session.inputNames[0]]: input });
    return (out[this.session.outputNames[0]].data as Float32Array)[0];
  }
}
```

> **Why `NaN` and not a default.** This line is week 4. Filling with 0 (or any number) tells the model "this restaurant's prep time is 0 minutes." Passing missing as missing lets the trees take the branch they learned for new restaurants in training. That only works if training also left the value missing. If training filled it with the median, that fill has to be inside the ONNX graph too, which is the reason preprocessing belongs in the bundle.

### The endpoint

```ts
app.post("/v1/eta", async (req, res) => {
  const { restaurantId, dropoff } = req.body;            // IDs and context, never features
  const predictionId = crypto.randomUUID();
  const features = await computeEtaFeatures(restaurantId, dropoff, new Date()); // the only copy

  const model = router.modelFor(req.user.id);
  let minutes: number;
  let source: "model" | "fallback" = "model";
  try {
    minutes = await withTimeout(model.predict(features), 15);
  } catch {
    minutes = heuristicEta(features);                    // yesterday's formula, still useful
    source = "fallback";
  }

  router.shadow(features, predictionId);                 // never awaited, never used
  await predictionLog.append({
    predictionId, at: new Date(), features, minutes, source,
    modelVersion: model.bundle.version, featureSpec: FEATURE_SPEC_VERSION,
  });

  res.json({
    predictionId,
    estimate: { low: Math.round(minutes - 5), high: Math.round(minutes + 5) },
    modelVersion: model.bundle.version,
    source,
  });
});
```

> **What the log makes possible.** When the order is delivered, the actual time joins to `predictionId`. That single join gives 39.2b its accuracy monitoring, gives the next model its training data (features exactly as served), and gives the skew check its live side. Without `modelVersion` on each row, week 6's question ("was version 7 the cause?") can't be answered.

> **Where the timeout leaks.** `withTimeout` stops waiting after 15 ms, but ONNX Runtime keeps computing on its thread pool. For a sub-millisecond tree model that doesn't matter. For a heavy model, timed-out work piles up under load and makes the next requests slower, which is one reason heavy models go behind a server with its own capacity and queue limits.

### Canary and shadow

```ts
import { createHash } from "node:crypto";

export class ModelRouter {
  constructor(
    private champion: EtaModel,
    private canary?: { model: EtaModel; percent: number; salt: string },
    private shadowModel?: EtaModel,
  ) {}

  modelFor(userId: string): EtaModel {
    if (this.canary && bucket(userId, this.canary.salt) < this.canary.percent) {
      return this.canary.model;
    }
    return this.champion;
  }

  shadow(features: EtaFeatures, predictionId: string): void {
    const m = this.shadowModel;
    if (!m) return;
    setImmediate(() =>
      m.predict(features)
        .then((minutes) => shadowLog.append({ predictionId, modelVersion: m.bundle.version, minutes }))
        .catch(() => { /* a failing shadow is a finding, not an outage: count it */ }));
  }
}

// Same user, same bucket, every request: estimates don't flip between models
// mid-session. A new salt per experiment reshuffles who is in the canary.
function bucket(userId: string, salt: string): number {
  return createHash("sha256").update(`${salt}:${userId}`).digest().readUInt32BE(0) % 100;
}
```

> **Shadow shares the machine.** An in-process shadow model uses the same CPU as the champion. For a tree model at 1,200 requests a second that's a rounding error. For a larger model, shadow a sample of requests, or run the shadow in a separate consumer that reads the prediction log, so the experiment can never slow down checkout.

- **Chip Huyen, _Designing Machine Learning Systems_** (O'Reilly, 2022), chapter 7, "Model Deployment and Prediction Service." Batch versus online prediction and model compression, in more depth than here.
- **Martin Zinkevich, "Rules of Machine Learning"** (Google), rules #29–#37 on training–serving skew, including logging features at serving time.
- **Eric Breck et al., "The ML Test Score: A Rubric for ML Production Readiness and Technical Debt Reduction"** (IEEE Big Data 2017). A checklist of tests for features, models and serving, including skew tests.
- **Jeremy Hermann and Mike Del Balso, "Meet Michelangelo: Uber's Machine Learning Platform"** (Uber Engineering blog, 2017). The design that popularized the feature store, with the problem it solved.
- **Feast documentation**, especially "Point-in-time joins." The clearest explanation of what makes training data from a feature store correct.
- **MLflow documentation, "Model Registry"**: versions, aliases and promotion.
- **ONNX Runtime documentation** and the **skl2onnx** / **onnxmltools** converters, including their lists of supported operators.
- **KServe documentation** and **NVIDIA Dynamo-Triton (Triton Inference Server) documentation**, for serving many models, or GPU models, behind a standard protocol.
- **Ron Kohavi, Diane Tang and Ya Xu, _Trustworthy Online Controlled Experiments_** (Cambridge, 2020). The standard reference on A/B testing, which model rollouts depend on.
- **Olivier Chapelle et al., "Large-Scale Validation and Analysis of Interleaved Search Evaluation"** (ACM TOIS, 2012). Why interleaving detects ranking differences with far less traffic than A/B tests.
- **In this collection:** 39.1a (framing, leakage and the decision log), 39.2b (monitoring, drift, retraining and bias), 39.3 (hosted LLM APIs), Module 10 (scheduled jobs, for batch scoring), Module 26 (feature flags and A/B testing), Module 33 (API versioning), 37.2 (event streams, for streaming scoring), 36.3 (circuit breakers, for a remote model server).

---

The habit to take from this: when someone says "the model is ready," ask what they're handing over. If the answer is a file, the work of making it a product hasn't started. The model is ready when it comes with its feature definitions, a version that every prediction carries, and a way back to the previous one.
