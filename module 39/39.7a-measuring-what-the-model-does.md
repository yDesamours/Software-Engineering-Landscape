# Measuring What the Model Does: Evaluating LLM Features

_Module 39.7a — Machine Learning & LLM-Powered Systems_

## The Problem

Suppose you run a video-meeting product for businesses, and you've added **meeting notes**: after each call, the model reads the transcript and produces a short summary, a list of decisions, and action items with an owner and a due date. Customers like it, and it's a reason people upgrade.

Quality was checked the way most teams start: the product manager ran five favorite meetings through each new prompt and read the results. That worked until four things happened.

**A model upgrade that looked fine.** The provider released a new model version. The PM tried it on the usual five meetings, liked the tighter summaries, and it shipped. A week later, support noticed a pattern: action items were being assigned to the wrong person. "Priya will send the contract" became an item for Marco, who had asked Priya to do it. Once someone counted, it was about 8% of action items, up from under 2%. None of the five test meetings had that pattern.

**A judge that liked the wrong things.** The team built an evaluation: 40 meetings, with a second model scoring each set of notes from 1 to 10. The new prompt scored 8.7 and the old one 8.6. When an engineer read the scored notes, the judge had given 9/10 to notes that included a decision nobody had made, and consistently scored longer notes higher, whether or not the extra length added anything.

**A difference that wasn't there.** A prompt change scored 86% "acceptable" against the old prompt's 82% on 50 meetings, so it shipped. Rerunning the same evaluation the next week gave the new prompt 80%. Nothing had changed except the random variation in the model's output.

**Feedback that described a minority.** The thumbs-up and thumbs-down buttons on the notes were used on about 4% of meetings, mostly by people who were annoyed. The feedback rate was not a quality measure. It measured how often people were annoyed enough to click.

Every change to this feature (prompt, model, retrieval, tools) changes its behavior, and nothing in an ordinary test suite would notice. The team had no way to answer the question every change raises: is this better or worse than before, and by how much?

## What It Is

An **evaluation** (usually shortened to **eval**) is a repeatable measurement of how well an LLM feature does its job. It has three parts:

- A **dataset** of realistic inputs, often with reference answers or labels.
- **Criteria** that define what good output means for this feature, written down specifically enough that two people would apply them the same way.
- **Graders** that apply those criteria to outputs: code, a model (**LLM-as-judge**) or people.

Evals are the test suite for components whose output isn't deterministic and can't be fully specified. They answer the question a unit test can't: not "does it return exactly this?" but "how often does it do the right thing, and is that more or less often than last week?"

The work around the eval is as important as the eval itself:

- **Error analysis:** reading real outputs to find out how the feature actually fails, before deciding what to measure.
- **Statistics:** knowing whether a difference between two versions is real or noise.
- **Online evaluation:** measuring quality in production, where the inputs are real and changing.

39.2b covered monitoring for classical models, where labels eventually arrive and accuracy can be computed. Most LLM features have no such label: "is this summary good?" has no ground truth waiting in a database. That's why grading is the hard part. Guardrails, which block bad outputs at runtime rather than measuring them, are 39.7b. Tracing, which records what happened in each call, is 39.7c, and it's where eval data comes from.

## Recognizing the Problem

- Prompt or model changes are approved by someone reading a handful of outputs.
- Nobody can say what fraction of outputs are good, or which kinds of failures are most common.
- A model upgrade or prompt change caused a regression that users found first.
- Quality is measured by a single score from a judge model that nobody has checked against human judgment.
- Evaluation results move by several points between runs with no change.
- Two versions are compared on a few dozen examples and the higher number wins.
- The only production signal is a feedback button used by a small, unrepresentative fraction of users.
- Agents are evaluated by whether they called the expected tools in the expected order.

## How It Works

### Start by reading outputs

The most useful first step isn't a metric. It's **error analysis**: take 50–100 real outputs, read each one, and note what's wrong in your own words. Then group the notes into failure modes and count them:

```
 100 meeting notes, read and annotated
  action item assigned to the wrong person                 9
  decision stated that wasn't actually made                6
  due date missing although one was said                   5
  summary misses the main topic of a two-topic meeting     4
  notes in English for a meeting held in Spanish           3
  fine                                                    71
```

That table does three things. It turns vague "quality" into specific failure modes you can measure. It tells you which to fix first. And it shows which **criteria** matter for this feature: correct attribution, no invented decisions, complete due dates, right language. A generic "rate this summary 1–10" would never have found the attribution problem.

Criteria change as you look at more outputs, a phenomenon Shreya Shankar and colleagues call **criteria drift**: people discover what they care about by grading. Expect to revise criteria after the first rounds, and treat that as progress, not failure.

### The dataset

Build the dataset from real inputs wherever you can, with consent and appropriate redaction (Module 34). Invented examples miss what real users do. Then shape it:

- **Cover the variety.** Include short and long meetings, several speakers and two, multiple languages, meetings with no decisions, and the specific patterns that caused past failures ("Marco asked Priya to…").
- **Label what can be labeled.** For action items, record the correct owners and due dates. For free text like the summary, a reference isn't always needed. The criteria and the transcript are enough to judge against.
- **Keep two kinds of sets.** A **regression set** holds cases the feature must keep getting right, and should pass nearly 100%. A **capability set** holds hard cases you're working toward, and starts low. Anthropic's guidance on agent evals recommends the same split.
- **Grow it from failures.** Every production failure, once understood, becomes a new case. The attribution bug becomes 20 cases of "A asked B to do X."
- **Guard against overfitting.** If you tune prompts against the same 50 cases for months, the prompt gets good at those 50. Keep part of the dataset aside for occasional checks.

### Graders: code first, then models, then people

Use the cheapest grader that can reliably apply each criterion:

- **Code-based graders** check what can be checked exactly: the output matches the schema, every action-item owner is a participant in the meeting, every due date is a valid date after the meeting, the notes are in the meeting's language, every quoted decision appears in the transcript. They're fast, free, deterministic and precise, and they can't judge meaning.
- **Model-based graders (LLM-as-judge)** apply criteria that need understanding: "Is each action item assigned to the person who agreed to do it?" "Does the summary cover every major topic?" They scale, and they need calibrating (next section).
- **Human graders** are the reference for everything else: they label the calibration set, review ambiguous cases, and do periodic spot checks. They're slow and expensive, so use them where their judgment is needed.

A single feature usually uses all three. Most of the meeting-notes criteria can be graded by code, two need a judge, and a person reviews a sample every week.

### LLM-as-judge, done so it can be trusted

A judge model is a classifier, and like any classifier it has error rates, which you have to measure. The 1-to-10 judge failed for predictable reasons:

- **Scales are vague.** Nobody, human or model, applies "7 out of 10" consistently. Use **binary pass/fail per criterion**, with a written definition of pass and fail and a few examples of each.
- **One judge, one criterion.** "Is every decision in the notes actually made in the meeting?" is a question a judge can answer. "Are these notes good?" isn't.
- **Evidence before verdict.** As in 39.3a's schema design, ask for the supporting quotes from the transcript first, then the verdict. It improves accuracy, and gives you something to check.
- **Known biases.** Zheng and colleagues documented them in 2023: judges prefer the first of two options shown (**position bias**), longer answers (**verbosity bias**), and output that resembles their own (**self-preference**). For pairwise comparisons, run each comparison twice with the order swapped. Keep criteria specific so length can't substitute for quality. Where possible, use a different model family from the one being evaluated.

Then **calibrate**: have people label 100 or so outputs against the criterion, run the judge on the same outputs, and measure agreement separately for passes and fails:

```
                        human: pass    human: fail
 judge: pass                  62              7        judge misses 7 of 34 real failures
 judge: fail                   4             27        judge flags 4 of 66 good outputs
 true positive rate (catches failures)  27/34 = 79%
 true negative rate (passes good ones)  62/66 = 94%
```

Overall agreement (89%) hides what matters: this judge misses about one failure in five. Revise the judge's definition and examples, focusing on the cases it got wrong, until the rates are good enough for the decisions you'll base on it. Then re-check periodically, especially when the judge model changes. Hamel Husain's writing on evals describes this loop in practical detail.

### Is the difference real?

Evals are measurements with noise from two sources: which examples happen to be in the dataset, and the model's randomness on each run. Anthropic's "A statistical approach to model evaluations" (Miller, 2024) sets out the practice, and the numbers make the case:

```
 50 examples, 84% pass:        95% confidence interval ≈ ±10 points  (74%–94%)
 400 examples, 84% pass:       95% confidence interval ≈ ±3.6 points
 82% vs 86% on 50 each:        difference ±14 points (unpaired). 4 points is well inside the noise.
 to detect a 4-point change    ≈ 1,300 examples per version compared unpaired,
 with the usual confidence:    ≈ 660 if paired and results correlate at 0.5
```

That's why 82% versus 86% on 50 examples meant nothing. Four habits help:

- **Report an interval, not a number.** "84% ± 10" makes the uncertainty visible, and stops small differences from being treated as wins.
- **Compare versions on the same examples, and analyze the paired differences.** Each example's result under version A and version B is compared directly. Because examples that are hard for one version tend to be hard for the other, this removes much of the noise.
- **Run each example several times** and average, which reduces the model's own randomness. It matters most for agents and long outputs.
- **Size the dataset for the decisions you make.** If you need to detect 2-point regressions, you need a large set. If you only need to catch 10-point drops, a few hundred examples are enough.

When examples come in groups (several questions about the same meeting), they aren't independent, and the intervals are wider than the simple formula says. The same article covers **clustered standard errors** for this case.

### Evaluating agents

Agents (39.6) add two problems: many valid paths lead to the same result, and runs vary more.

- **Grade outcomes, not exact paths.** Check what the agent achieved (the final state, the report and its evidence) rather than requiring an exact sequence of tool calls. An investigation that finds the payment outage in six steps instead of eight isn't wrong.
- **Check path constraints that matter.** Some parts of the path are requirements: no write action without approval, no tool outside the allowed set, no step over budget. Test those explicitly.
- **Measure reliability, not just possibility.** **pass@k** is the chance at least one of k runs succeeds. **pass^k** is the chance all k succeed. An agent that succeeds 90% of the time has a pass@5 of nearly 100% and a pass^5 of 59%. For a feature customers use repeatedly, pass^k is the number that matches their experience.
- **Record cost and latency per task** alongside success. A change that raises success by 2 points while doubling cost is a decision, not a win.
- **Run in a controlled environment,** with fixed data, fake external services and a reset between runs, so failures come from the agent, not from yesterday's data.
- **Read the transcripts.** A passing score from a broken grader, or a failure caused by a broken test fixture, only shows up when someone reads what the agent actually did.

### Evaluating in production

Offline evals test known cases. Production brings new ones, so measure there too:

- **Sample production outputs and run the same graders.** Code checks can run on every output. Judges can run on a sample. Track results over time, by customer segment and by language.
- **Use behavioral signals, not just ratings.** How often notes are edited, and how much, whether action items are accepted or deleted, whether users regenerate. These cover everyone, not the 4% who click a thumb. The suggestion-and-accept design from 39.3a produces these signals naturally.
- **A/B test changes that matter** (Module 26), measuring product outcomes as well as graded quality.
- **Close the loop.** Production failures, once understood, go into the dataset. The evaluation grows with the product.

Tools help with datasets, grading, experiment tracking and dashboards. Examples include Promptfoo (open source; OpenAI announced its acquisition in March 2026), Braintrust, LangSmith, Langfuse, Arize Phoenix, and Inspect from the UK AI Security Institute. They make the workflow easier. The decisions about criteria, graders and statistics are still yours.

## When It's Appropriate

- **Any LLM feature that will change:** a new prompt, a model upgrade, a retrieval change. That's every LLM feature.
- **Code-graded checks:** structured output, extraction, classification, and anything with verifiable facts such as dates, names, IDs and quotes. Run them on every change and, cheaply, on production output.
- **LLM-as-judge:** criteria that need understanding, such as faithfulness to a source, coverage, tone and correct attribution, once it's been calibrated against human labels.
- **Large, statistically sized evals:** decisions with real consequences, such as switching models, launching to all customers, or changing something safety-relevant.
- **Agent evals with pass^k:** agents customers rely on repeatedly, where occasional failure is the real cost.

## When It's Unnecessary or Overkill

- **A statistically rigorous eval for a prototype.** Early on, error analysis on 50 outputs teaches more than any metric. Build the measurement when the feature is worth protecting.
- **LLM-as-judge for what code can check.** Using a model to confirm that output is valid JSON, or that a date is a date, adds cost and error for nothing.
- **Chasing small differences on small sets.** If the dataset can only detect 10-point changes, don't make decisions on 2-point ones.
- **Generic benchmark scores as your eval.** Public benchmarks measure general capability, not whether your meeting notes attribute action items correctly. They help shortlist models, and they don't replace your own evals.
- **Grading exact agent trajectories.** Requiring one specific tool sequence fails good runs, and makes the eval a record of one path rather than a measure of success.

## Trade-offs

- **Evals take real effort.** Error analysis, labeling, calibrating judges and maintaining datasets are ongoing work, often by the people who best understand the product.
- **Judges cost money and have error rates.** Every judged example is another model call, and a judge's mistakes become your measurement errors.
- **Noise requires size.** Detecting small changes reliably takes hundreds or thousands of examples, which means more cost and time per run.
- **Datasets age.** Users, languages and use cases shift, and a dataset built last year can report "no regressions" while production quality falls.
- **Overfitting to the eval.** A team optimizing a number can improve the number without improving the product, especially with small, fixed datasets.
- **Privacy constraints.** Real inputs make the best test cases, and they're personal data, with consent, retention and access obligations.
- **Metrics can mislead confidently.** A high score from a grader nobody has checked is worse than no score, because people act on it.

## Alternatives

- **Manual review.** Experts read outputs before each release. It's thorough on what's read, small in coverage, and it doesn't scale to frequent changes. Good as a complement, not a replacement.
- **Production A/B tests only.** Measuring real outcomes is the final word, but it's slow, exposes users to regressions, and needs traffic. Offline evals catch most problems before users see them.
- **User feedback only.** It's cheap and real, and sparse and biased. Useful as one signal among several.
- **Public benchmarks,** for choosing which models to consider, never for deciding whether your feature works.
- **Classical labeled test sets,** when the task really is classification or extraction with ground truth. Then 39.1a's and 39.2b's accuracy measurement applies directly, and no judge is needed.

## How to Achieve It

**1. Do error analysis.** Read 50–100 real outputs, annotate failures in plain words, group and count them.
_Move on when_ you have a ranked list of failure modes and written criteria for the top ones.

**2. Build a first dataset from real inputs,** covering the variety and past failures, with labels where facts are checkable.

**3. Write code graders for everything checkable.** Run them on every change, in CI.

**4. Add a judge per remaining criterion,** binary, with evidence first and written definitions. Calibrate on human labels, and measure true positive and negative rates.
_Move on when_ each judge's error rates are known and acceptable for the decisions it supports.

**5. Add statistics.** Report intervals, compare versions on the same examples, repeat runs, and size the dataset to the smallest change you need to detect.

**6. Gate changes.** No prompt, model or retrieval change ships without a regression-set pass and a paired comparison against the current version.

**7. Evaluate in production** with sampled grading and behavioral signals, and feed every understood failure back into the dataset.

## Implementation

The implementation is TypeScript: a small harness, not a framework. It shows a code grader for attribution, a calibrated binary judge, and a paired comparison of two versions with an interval. Model calls go through the `structured()` helper from 39.3a.

### Code graders for what can be checked

```ts
interface EvalCase {
  id: string;
  meetingId: string;                      // cases from the same meeting are correlated
  transcript: TranscriptTurn[];
  participants: string[];
  expected?: { actionItems?: { owner: string; task: string }[] };   // labeled where possible
}

type Grade = { criterion: string; pass: boolean; detail?: string };

export function codeGrades(c: EvalCase, notes: MeetingNotes): Grade[] {
  const grades: Grade[] = [];
  const people = new Set(c.participants.map((p) => p.toLowerCase()));

  const strangers = notes.actionItems.filter((a) => !people.has(a.owner.toLowerCase()));
  grades.push({ criterion: "owners_are_participants", pass: strangers.length === 0,
                detail: strangers.map((a) => a.owner).join(", ") || undefined });

  const text = c.transcript.map((t) => t.text).join(" ").toLowerCase();
  const unquoted = notes.decisions.filter((d) => !text.includes(d.quote.toLowerCase()));
  grades.push({ criterion: "decision_quotes_in_transcript", pass: unquoted.length === 0 });

  if (c.expected?.actionItems) {
    const want = new Map(c.expected.actionItems.map((a) => [normalizeTask(a.task), a.owner.toLowerCase()]));
    const wrong = notes.actionItems.filter((a) => {
      const owner = want.get(normalizeTask(a.task));
      return owner !== undefined && owner !== a.owner.toLowerCase();
    });
    grades.push({ criterion: "owners_match_labels", pass: wrong.length === 0 });   // the model-upgrade bug
  }
  return grades;
}
```

> **Why `owners_match_labels` needs labels and `owners_are_participants` doesn't.** Checking that owners are real participants catches invented people without any labeling. It doesn't catch Priya's task going to Marco, because Marco is a participant. That failure needs a labeled answer, or a judge. Twenty labeled "A asked B" cases would have caught the upgrade regression before release, in seconds, for free.

### A binary judge, with evidence first, and its calibration

```ts
const AttributionVerdict = z.object({
  evidence: z.array(z.object({ item: z.string(), quote: z.string() })),  // written BEFORE the verdict
  wrongly_attributed: z.array(z.string()),
  pass: z.boolean(),
});

const ATTRIBUTION_JUDGE = `You check action items from meeting notes against the transcript.
An action item PASSES if the owner is the person who agreed or was assigned to do it in the transcript.
It FAILS if the owner is someone else, including the person who asked for it.
For each item, quote the transcript lines that show who took it on. Then list any wrongly attributed items.
pass is true only if no item is wrongly attributed.
${JUDGE_EXAMPLES}`;                        // 3 passing and 3 failing examples, including "A asked B to…"

export async function judgeAttribution(c: EvalCase, notes: MeetingNotes) {
  return structured(AttributionVerdict, ATTRIBUTION_JUDGE, { transcript: c.transcript, actionItems: notes.actionItems });
}

// Run on ~100 outputs that people have labeled pass/fail for this criterion.
export async function calibrate(labeled: { c: EvalCase; notes: MeetingNotes; humanPass: boolean }[]) {
  let tp = 0, fn = 0, tn = 0, fp = 0;               // "positive" = a failure, the thing we want caught
  for (const x of labeled) {
    const judgePass = (await judgeAttribution(x.c, x.notes)).pass;
    if (!x.humanPass) judgePass ? fn++ : tp++;
    else judgePass ? tn++ : fp++;
  }
  return { catchesFailures: tp / (tp + fn), passesGood: tn / (tn + fp), n: labeled.length };
}
```

> **Why report two rates.** A judge that passes everything agrees with humans whenever outputs are mostly good, which they usually are. Reporting how often it catches real failures, separately from how often it wrongly flags good output, exposes that immediately. Recalibrate whenever the judge prompt or judge model changes, and keep the disagreement cases. They're the best examples to add to the judge prompt.

### Comparing two versions, honestly

```ts
// Each case run several times per version, scored 1 (all criteria pass) or 0.
export function pairedComparison(results: { caseId: string; meetingId: string; a: number[]; b: number[] }[]) {
  const mean = (xs: number[]) => xs.reduce((s, x) => s + x, 0) / xs.length;

  // Per-case difference, averaging over repeats (reduces the model's own noise).
  const perCase = results.map((r) => ({ meetingId: r.meetingId, d: mean(r.b) - mean(r.a) }));

  // Cases from one meeting aren't independent: aggregate to one difference per meeting.
  const byMeeting = new Map<string, number[]>();
  for (const x of perCase) byMeeting.set(x.meetingId, [...(byMeeting.get(x.meetingId) ?? []), x.d]);
  const clusters = [...byMeeting.values()].map(mean);

  const n = clusters.length;
  const diff = mean(clusters);
  const sd = Math.sqrt(clusters.reduce((s, x) => s + (x - diff) ** 2, 0) / (n - 1));
  const halfWidth = 1.96 * sd / Math.sqrt(n);
  return {
    difference: diff,                                  // B minus A, in pass-rate points
    interval: [diff - halfWidth, diff + halfWidth],
    verdict: diff - halfWidth > 0 ? "B better" : diff + halfWidth < 0 ? "B worse" : "no detectable difference",
  };
}
```

> **What this would have said about 82% versus 86%.** The same examples under both versions, averaged over three runs each and grouped by meeting, give an interval such as −4 to +11 points. The verdict is "no detectable difference," which is the truth. Averaging per meeting is a simple, conservative way to handle correlated cases. Anthropic's statistics article explains clustered standard errors, which use the data more efficiently. For a release gate, add a separate rule: the regression set must still pass completely, whatever the average says.

The habit to take from this: before trusting any claim that an LLM feature got better, ask three things. What exactly was measured, and who checked the grader? How many examples, and what's the interval? And did anyone read the outputs? A number without those answers is an opinion with decimals.
