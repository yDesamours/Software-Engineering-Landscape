# Retrieval That Holds Up: Hybrid Search, Re-ranking, Vector Indexes, Freshness and Permissions

_Module 39.4b — Machine Learning & LLM-Powered Systems_

## The Problem

Suppose you build a team workspace product: pages, docs, runbooks, meeting notes and project tickets, used by 12,000 companies. You add an assistant that answers questions from a workspace's content, built the way 39.4a describes. Documents are parsed and split along their structure, each chunk carries its heading path, every search is filtered to one workspace, and answers cite their sources. In the pilot with 20 workspaces it's excellent.

Rolling it out to every workspace brings five new problems.

**Exact terms don't match.** An engineer pastes an error, `AADSTS50011`, and asks what to do. The runbook that names that exact code isn't in the results. The top results are general pages about single sign-on, which are semantically close to anything about login errors. The same happens with ticket IDs (`INC-2291`), product SKUs, people's names and config keys: the things people most often search for by exact text.

**The right chunk is found, but too low.** The search returns 50 candidates, and the prompt takes the top 5. In the retrieval test set, the chunk that answers the question is somewhere in the top 50 for 94% of questions, but in the top 5 for only 68%.

**Scale breaks the search, then the fix breaks filtering.** There are now 40 million chunks. Scanning every vector in a large workspace takes seconds, so the team adds an approximate vector index. Queries get fast, and small workspaces start getting zero or one result. The index returns the 40 nearest chunks across *all* workspaces, and then the workspace filter removes nearly all of them.

**Answers lag behind edits.** The index is rebuilt every night. At 10:00, the on-call page is updated with a new escalation phone number. At 15:00, the assistant gives the old one. A page deleted in the morning is still being quoted in the afternoon.

**Private pages leak.** An HR lead keeps a private page with notes on an employee's performance plan. It's in the same workspace, so it passes the workspace filter. A teammate asks "What's happening with Sam's role?" and the assistant quotes the private notes.

The first two are about finding the right text. The third is about the vector index. The last two are about the index being a *copy* of the workspace, one that has to stay as current and as access-controlled as the original.

## What It Is

This article covers the parts of retrieval that 39.4a left out, which become necessary as content grows, changes and gets sensitive:

- **Hybrid search** runs keyword search and vector search for the same question and combines the results, so exact terms and meaning both count.
- **Re-ranking** takes a few dozen candidates from the first search and re-scores them with a slower, more accurate model, so the best ones end up in the prompt.
- **Vector indexes** make nearest-neighbor search fast over millions of vectors by giving up exactness. The kind of index, and how it handles filters, decides whether a filtered query returns anything. That includes the choice between pgvector and a dedicated vector database.
- **Freshness** keeps the index in step with the source content through incremental updates, instead of periodic rebuilds.
- **Permissions** ensure that retrieval only ever returns content the person asking is allowed to read.

The ideas in keyword search itself (analyzers, relevance scoring, facets) are Module 12. This article uses keyword search as one half of retrieval.

## Recognizing the Problem

- Searches for error codes, IDs, names or exact phrases miss documents that contain them word for word.
- The right passage appears in the retrieved candidates, but not among the few that go into the prompt.
- Filtered vector queries return fewer results than requested, or none, for small tenants or narrow filters.
- Vector search latency climbs with total data size, even for tenants with little data.
- Edited content appears in answers hours later, and deleted content keeps appearing.
- The index is rebuilt from scratch on a schedule.
- Documents with restricted access are indexed with nothing but a tenant ID.
- Changing embedding models is being planned as "re-run the indexer," with no plan for the time in between.

## How It Works

### Hybrid search: two ways of matching

Vector search matches meaning, and keyword search matches text. They fail in opposite ways:

```
 question                         keyword search            vector search
 "AADSTS50011 on login"           ✓ exact code match        ✗ general SSO pages rank higher
 "users can't sign in with SSO"   ✗ runbook says "SAML      ✓ close in meaning
                                    assertion rejected"
 "INC-2291 postmortem"            ✓                         ✗ IDs carry little meaning
 "why was the launch delayed?"    ~ depends on wording      ✓
```

**Keyword search** usually means **BM25**, the standard relevance formula in search engines. It scores documents higher when they contain the query's terms, especially rare terms, and it adjusts for document length. It's exact about identifiers and rare words, and blind to synonyms and paraphrase. Elasticsearch, OpenSearch and most dedicated search engines use it. Postgres's built-in full-text search uses a similar but simpler ranking (`ts_rank`), and extensions such as ParadeDB's `pg_search` add true BM25 to Postgres.

**Hybrid search** runs both searches and merges the two ranked lists. The scores aren't comparable (a BM25 score of 14.2 and a cosine similarity of 0.83 are on different scales), so the common method ignores scores and uses **ranks**. **Reciprocal rank fusion (RRF)** gives each document `1 / (60 + rank)` from each list it appears in, and adds them up:

```
 chunk   keyword rank   vector rank   RRF score
 A       1              —             1/61            = 0.0164
 B       3              2             1/63 + 1/62     = 0.0320   ← in both lists: first
 C       —              1             1/61            = 0.0164
```

A document near the top of both lists beats one at the top of only one. The constant 60 comes from the paper that introduced RRF, and it keeps a single first place from dominating. Weighted combinations of normalized scores are an alternative when you have data to tune the weights.

A third option is a **learned sparse** model such as SPLADE. It produces keyword-like vectors in which each dimension is a word, with learned weights that also include related words. It sits between the two approaches, and some vector databases store these vectors alongside dense ones.

### Re-ranking: a second, more careful look

The first search has to be fast over millions of chunks, so it compares a precomputed vector for the question with precomputed vectors for each chunk. The question and a chunk are never examined together. A **re-ranker** does exactly that: a model (usually a **cross-encoder**) reads the question and one candidate together and outputs a relevance score. It's far more accurate, and far too slow to run on millions of chunks, so it runs only on the first stage's candidates:

```
 40M chunks ──▶ hybrid search: top 50 ──▶ re-ranker scores 50 pairs ──▶ top 5 into the prompt
               (fast, ~20 ms)             (accurate, ~100–300 ms)
```

This is what moves the answering chunk from 14th to 1st. Re-rankers are available as APIs (Cohere and Voyage offer them) and as open-weight models you can host. A general LLM can also do this job, by asking it to pick the relevant passages, at higher cost.

Two numbers become worth tracking separately:

- **Recall of the first stage** (is the answer anywhere in the top 50?) sets the ceiling. Re-ranking can't find what the first stage missed.
- **Precision of the final few** (is the answer in the top 5 after re-ranking?) is what the model actually sees.

Anthropic's contextual retrieval study (39.4a) measured how these combine. Retrieval failures fell 35% with contextual embeddings alone, 49% when keyword search was added, and 67% when re-ranking was added on top.

### Vector indexes: fast by being approximate

Finding the nearest vectors exactly means comparing the question with every vector. That's fine for tens of thousands of vectors and too slow for tens of millions. **Approximate nearest-neighbor (ANN)** indexes make search fast by checking only a promising fraction:

- **HNSW** (hierarchical navigable small world) links each vector to its near neighbors in a layered graph. A search starts at the top layer and walks toward the question, layer by layer. It's fast and accurate, and it's the most common choice. Its costs are memory (the graph and the vectors want to be in RAM), slow index builds, and degradation under heavy updates and deletes until it's rebuilt.
- **IVF** (inverted file) groups vectors into clusters and searches only the clusters nearest the question. It's quicker to build and smaller, and usually slightly less accurate at the same speed.
- **Disk-based indexes** (DiskANN and its derivatives, including the `pgvectorscale` extension) keep most of the index on SSD, trading some latency for much lower memory cost at large scale.

Each has a setting that trades speed for **recall**, the fraction of the true nearest neighbors the search actually returns. In pgvector's HNSW, that's `hnsw.ef_search` (default 40). Measure recall against exact search on a sample of your queries when you set it, since "approximate" can quietly mean missing 10% of the right answers.

**Memory is the scaling cost.** A 1,024-dimension vector stored as 32-bit floats is 4 KB. Forty million of them are 164 GB before the graph. Two common reductions:

- **Half-precision** (16-bit) halves the size with almost no loss in accuracy.
- **Binary quantization** keeps one bit per dimension (5 GB for all 40 million), searches that small copy for a few hundred candidates, then re-scores those candidates with the full vectors.

### Filtering: where approximate indexes surprise you

Filters are where 39.4a's advice (filter inside the query) meets approximate indexes. An HNSW search collects its `ef_search` nearest candidates, *then* applies the `WHERE` clause. If a workspace owns 0.01% of the chunks, few or none of the 40 global nearest neighbors belong to it, and a query asking for 20 results returns 1. Nothing errors; the answer is just built from almost nothing.

The fixes, roughly in order of how directly they address the problem:

- **Iterative scans.** pgvector 0.8 can keep walking the graph until enough rows pass the filter, up to a limit (`hnsw.max_scan_tuples`, 20,000 by default). Turn it on with `hnsw.iterative_scan`. It solves moderate filtering. For very selective filters, it can hit the limit and still come up short.
- **Exact search for small tenants.** Tenant sizes are usually very uneven. Most of the 12,000 workspaces have a few thousand chunks, where an exact scan filtered by an ordinary B-tree index on the workspace is fast and perfectly accurate. When the planner uses the tenant index instead of the vector index, that's what happens. Reserve the ANN index for the large tenants.
- **Partitioning.** Give each large tenant (or group of small ones) its own partition, collection or namespace with its own index. The index then only contains that tenant's vectors, and the filter is implicit. Dedicated vector databases call these namespaces or collections, and multi-tenancy features are built around them.
- **Filter-aware indexes.** Several dedicated vector databases (Qdrant, Weaviate, Milvus and others) apply filters during the graph search itself, using payload indexes, rather than after it. That's their main technical advantage for heavily filtered, multi-tenant search.

### pgvector or a dedicated vector database?

The question is the same as for any specialized datastore (Module 6): what does the new system do that the existing one can't, and is that worth another system to run?

**Stay with pgvector** (or your existing search engine's vector support) when:
- the data is in the millions of vectors, not billions
- you want transactions, joins and access rules alongside the vectors (the permissions below are ordinary SQL)
- you already run Postgres well
- query volume is moderate

Elasticsearch and OpenSearch deserve the same consideration if you already run them for keyword search: they do vector search and built-in hybrid fusion in one place.

**Consider a dedicated vector database** (Pinecone, Qdrant, Weaviate, Milvus, turbopuffer and others) when:
- vectors number in the hundreds of millions or more
- query volume is high
- filtered multi-tenant search is central
- you want storage separated from compute, or serverless scaling

The cost is a second store to keep in sync (below), to secure, and to pay for.

Neither choice is permanent if the index is treated as a rebuildable copy of the source content, which it should be anyway.

### Freshness: the index is a derived copy

The workspace's pages are the source of truth. The chunk index is **derived data**, like a cache or a search index (Module 12): it must be updated when the source changes, and it's always a little behind. Nightly rebuilds make "a little" mean up to 24 hours, and waste work re-embedding pages that didn't change.

**Incremental indexing** updates only what changed, driven by change events:

- **Where the events come from.** Either the application publishes a `document.changed` event through a transactional outbox (Module 37), or change data capture reads the database's log (38.4a). Either way, no edit is missed, even if the indexer is down for a while.
- **Idempotent, ordered updates.** Events can arrive twice or out of order. Each document carries a version, and the indexer ignores events older than the version it has already indexed.
- **Re-embed only what changed.** Store a hash of each chunk's text. When a page is edited, re-chunk it, and reuse the stored embedding for any chunk whose hash is unchanged. A typo fix re-embeds one chunk, not forty.
- **Deletes are first-class.** Deleting a page deletes its chunks immediately. Retention and deletion obligations (Module 34) apply to the index, and a deleted page that can still be quoted is a data-handling failure, not a stale cache.
- **Measure the lag.** Track the time from an edit to its chunks being searchable. That number is the freshness you actually provide.

### Changing the embedding model

Vectors from different embedding models can't be compared. A new, better model means re-embedding everything, and until that finishes, queries must be embedded with whichever model built the index they're searching. Treat it like a database migration:

1. **Store the model with every vector** (a column, or a separate index per model).
2. **Build the new index alongside the old one.** The indexer writes both for new changes, while a backfill re-embeds existing chunks. At 40 million chunks of about 400 tokens, that's 16 billion tokens: about $960 at an illustrative $0.06 per million tokens. More constraining is throughput: at 500 chunks a second, within provider rate limits, it takes about 22 hours. Storage is doubled for the duration.
3. **Compare** recall on the retrieval test set with the new index against the old.
4. **Switch** queries to the new model and index, keep the old one briefly for rollback, then drop it.

### Permissions: filter by who's asking

Tenant filtering (39.4a) keeps companies apart. Inside a company, documents have their own access rules: private pages, restricted spaces, HR folders, shared-with-specific-people. **Retrieval must enforce those rules for the person asking, before anything reaches the model.** Once text is in the prompt, it can appear in the answer, and no instruction reliably prevents that.

There are two ways to apply permissions, and robust systems use both:

- **Early binding: permissions stored in the index.** Each chunk carries the list of principals (users and groups) allowed to read its document, and the search filters on it (`allowed_principals && user's principals`). It's fast, and it works with ANN filtering. Its weakness is lag: when a page's sharing changes, the stored lists are wrong until the indexer catches up, and group membership changes can affect thousands of documents.
- **Late binding: check the source of truth after retrieval.** Before the retrieved chunks go into the prompt, ask the authorization system whether this user can read each document (Module 4). It's always current, but it only filters what was retrieved, so if most candidates are removed, the answer is built from very few sources.

Using early binding to find candidates and late binding to confirm them gives both speed and correctness: the index narrows to probably-allowed content, and the check removes anything whose access changed since indexing. Permission changes are also events for the indexer. They update the stored lists without re-embedding anything, since the text didn't change.

Two further rules:

- **Everything derived from the text carries the source's permissions.** That includes chunks, generated chunk context, summaries and cached answers. A cached answer built from a private page must not be served to someone who can't read that page.
- **Test for leaks directly.** Keep test cases that ask about restricted content as a user without access, and fail the build if any restricted chunk is retrieved.

## When It's Appropriate

- **Hybrid search:** content full of identifiers, codes, names and jargon, like engineering docs, support tickets, product catalogs and legal references. That's most business content.
- **Re-ranking:** when first-stage recall is good but the right chunk often isn't in the top few. It's worth measuring whenever answers depend on picking three to five passages from dozens.
- **ANN indexes:** a single search space above roughly a few hundred thousand vectors, or strict latency targets at lower sizes.
- **A dedicated vector database:** hundreds of millions of vectors, high query volume, or heavily filtered multi-tenant search where Postgres's filtering falls short.
- **Incremental indexing:** content people edit during the day and expect answers to reflect, and anything with deletion obligations.
- **Document-level permissions:** any content with access controls finer than the tenant, which in a workspace product means almost all of it.

## When It's Unnecessary or Overkill

- **Hybrid search for purely conversational content** with few identifiers, where vector search's recall is already high on your test set. Measure before adding a second index.
- **A re-ranker when the first stage is already precise,** or when the prompt can simply take all 20 candidates. Re-ranking adds latency and cost to every question.
- **An ANN index for small search spaces.** Exact search over 50,000 vectors is fast and has perfect recall. Most tenants in a multi-tenant product are small.
- **A dedicated vector database at modest scale.** A second system to sync, secure and pay for, to avoid a pgvector index that would have worked.
- **Event-driven indexing for content that changes monthly.** A nightly job is simple and adequate when nobody edits during the day and deletions aren't urgent.
- **Per-document permissions when every document is visible to everyone in the tenant.** Tenant filtering is enough. Revisit as soon as private content appears.

## Trade-offs

- **Two indexes instead of one.** Hybrid search means maintaining a keyword index and a vector index, with their own analyzers, languages and tuning.
- **Re-ranking adds latency and cost per question,** typically 100–300 ms and a per-search fee or a model to host.
- **Approximate means approximate.** ANN indexes miss some true neighbors. Their recall depends on settings, data and filters, and it drifts as data changes.
- **Memory and build costs.** HNSW wants the index in RAM, builds slowly, and degrades under heavy update and delete traffic until rebuilt.
- **Filtered vector search is hard.** Every fix (iterative scans, partitioning, filter-aware databases) adds configuration or architecture.
- **Incremental indexing is a streaming system** with the usual problems: ordering, duplicates, poison messages, backfills and lag.
- **Permissions in two places.** Early binding duplicates access rules into the index, where they can go stale. Late binding adds a call on every question. Both need testing.
- **Embedding model changes are migrations:** double storage, a long backfill, and dual writes during the transition.
- **More moving parts to debug.** When an answer is wrong, the cause might be in parsing, chunking, either index, fusion, re-ranking, permissions or indexing lag.

## Alternatives

- **A search engine you already run.** Elasticsearch or OpenSearch with vector fields gives BM25, vectors, hybrid fusion and filters in one system, with mature operations.
- **Managed retrieval services.** Cloud platforms offer managed "knowledge base" services that handle parsing, chunking, embedding, indexing and retrieval. They trade control over each stage for not building it. Check how they handle permissions and freshness before relying on them.
- **Agentic search** (39.6). Instead of one retrieval pass, the model issues searches, reads results and searches again, including exact keyword searches when it sees an identifier. That's more robust on complex questions, and slower and costlier per question.
- **Long context for small tenants** (39.3b, 39.4a). Many tenants' content fits in a cached prompt, and no retrieval can fail for them.
- **Scoping the feature.** Limiting the assistant to specific spaces or document types (public runbooks, the handbook) avoids permission complexity and makes quality easier to get right.

## How to Achieve It

**1. Extend the retrieval test set.** Add questions with identifiers, questions for small tenants, questions about recently edited pages, and questions a user shouldn't be able to answer.
_Move on when_ you can measure first-stage recall@50, final recall@5 and leak cases separately.

**2. Add keyword search and fuse with RRF.** Measure the change on identifier questions and overall.

**3. Add a re-ranker if recall@50 is much higher than recall@5.**
_Move on when_ the gap has narrowed, and the added latency fits the budget.

**4. Add permissions: early binding in the index and late binding before the prompt.** Add the leak tests to CI.
_Move on when_ every leak test passes, including after a sharing change that the indexer hasn't processed yet.

**5. Replace scheduled rebuilds with incremental indexing** from outbox or CDC events, with versions, hashes and deletes. Measure edit-to-searchable lag.

**6. Add ANN indexing when exact search gets slow for large tenants.** Turn on iterative scans, set recall targets, and consider partitioning the largest tenants.

**7. Consider a dedicated vector store only when measurements say Postgres can't meet the latency, recall or cost targets.** Keep the index rebuildable from source, so the move is a backfill, not a rewrite.

## Implementation

The implementation is TypeScript with PostgreSQL, pgvector and built-in full-text search. There are three pieces: the hybrid query with permissions, re-ranking with a late permission check, and an incremental indexer.

The chunk table extends 39.4a's with `workspace_id`, `document_id`, `document_version`, `content_hash`, `allowed_principals uuid[]` (GIN-indexed), `embedding_model`, `embedding vector(1024)` (HNSW-indexed), and a generated `tsv tsvector` for keyword search (GIN-indexed).

### Hybrid retrieval, permission-filtered

```ts
const HYBRID_SQL = `
WITH vec AS MATERIALIZED (           -- nearest by meaning, among chunks this user may read
  SELECT id, embedding <=> $1 AS distance
    FROM chunks
   WHERE workspace_id = $2 AND allowed_principals && $3 AND embedding_model = $5
   ORDER BY embedding <=> $1
   LIMIT 50
),
vec_ranked AS (SELECT id, row_number() OVER (ORDER BY distance + 0) AS r FROM vec),
kw AS (                              -- exact terms: error codes, IDs, names
  SELECT id, row_number() OVER (ORDER BY ts_rank_cd(tsv, q) DESC) AS r
    FROM chunks,
         (SELECT replace(plainto_tsquery('english', $4)::text, ' & ', ' | ')::tsquery AS q) AS query  -- ANY term
   WHERE workspace_id = $2 AND allowed_principals && $3 AND tsv @@ q
   ORDER BY ts_rank_cd(tsv, q) DESC
   LIMIT 50
)
SELECT c.id, c.document_id, c.heading_path, c.content,
       COALESCE(1.0 / (60 + v.r), 0) + COALESCE(1.0 / (60 + k.r), 0) AS rrf
  FROM vec_ranked v
  FULL OUTER JOIN kw k USING (id)
  JOIN chunks c USING (id)
 ORDER BY rrf DESC
 LIMIT 50`;

export async function hybridCandidates(user: User, question: string) {
  const [q] = await embed([question], { inputType: "query", model: EMBED_MODEL });
  return db.tx(async (t) => {
    // Keep walking the HNSW graph until 50 rows pass the filters (pgvector ≥ 0.8).
    await t.query(`SET LOCAL hnsw.iterative_scan = relaxed_order`);
    const { rows } = await t.query(HYBRID_SQL,
      [toSql(q), user.workspaceId, user.principalIds, question, EMBED_MODEL]);
    return rows;
  });
}
```

> **Why `MATERIALIZED` and `distance + 0`.** With `relaxed_order`, the index may return rows slightly out of distance order. Materializing the vector results and re-sorting them before assigning ranks keeps the ranks honest. The `+ 0` stops Postgres 17 and later from reusing the index order instead of re-sorting. pgvector's README gives the same pattern.

> **Why "any term."** Postgres's query parsers (`plainto_tsquery`, `websearch_to_tsquery`) require *every* word to match. That's right for a search box, and wrong for a question. "What does AADSTS50011 mean on login?" becomes `aadsts50011 & mean & login`, and the runbook, which never says "login," doesn't match. With questions phrased naturally, the keyword half often returns nothing at all, silently turning hybrid search back into vector-only search. Joining the terms with `|` matches any of them, and `ts_rank_cd` still ranks chunks that match more of the terms higher. It doesn't give extra weight to rare terms like the error code, which is one of the ways it falls short of BM25.

> **Where the keyword half is weaker than it looks.** `'english'` stems words and drops stop words, which is right for prose and wrong for some identifiers and for non-English workspaces. A workspace in French needs the `'french'` configuration, or a `'simple'` configuration for a second, exact-token index. Postgres's `ts_rank_cd` is also not BM25. For heavy keyword needs, `pg_search` or a search engine does better.

### Re-rank, then confirm access

```ts
export async function retrieve(user: User, question: string) {
  const candidates = await hybridCandidates(user, question);
  if (candidates.length === 0) return [];

  const ranked = await rerank(question, candidates.map((c) => `${c.heading_path}\n${c.content}`), { topN: 12 });
  const top = ranked.map((r) => candidates[r.index]);

  // Late binding: the index's permission lists may be minutes old. The source of truth is not.
  const readable = await authz.filterReadable(user.id, [...new Set(top.map((c) => c.document_id))]);
  return top.filter((c) => readable.has(c.document_id)).slice(0, 6);
}
```

> **Why re-rank twelve and keep six.** The late check can remove some chunks (a page un-shared since it was indexed). Re-ranking a few more than needed means the prompt still gets enough sources afterwards. If the check removes a lot, that's a signal: either permission events are lagging, or the early-binding lists are wrong. Count the removals and alert on them.

### An incremental indexer

```ts
// Consumes document events from the outbox or CDC stream (Module 37, 38.4a).
export async function onDocumentEvent(evt: DocumentEvent) {
  switch (evt.type) {
    case "deleted":
      await db.query(`DELETE FROM chunks WHERE document_id = $1`, [evt.documentId]);
      return;

    case "permissions_changed":                    // text unchanged: no re-embedding
      await db.query(`UPDATE chunks SET allowed_principals = $2 WHERE document_id = $1`,
        [evt.documentId, await authz.principalsFor(evt.documentId)]);
      return;

    case "content_changed": {
      const doc = await documents.load(evt.documentId);
      const indexed = await db.oneOrNone(
        `SELECT max(document_version) AS v FROM chunks WHERE document_id = $1`, [doc.id]);
      if (indexed?.v != null && indexed.v >= doc.version) return;     // duplicate or stale event

      const chunks = chunkDocument(doc).map((c) => ({ ...c, hash: sha256(c.headingPath + c.content) }));
      const known = await existingEmbeddings(doc.id, EMBED_MODEL);    // hash → vector
      const fresh = chunks.filter((c) => !known.has(c.hash));
      const vectors = await embed(fresh.map((c) => `${c.headingPath}\n${c.content}`),
                                  { inputType: "document", model: EMBED_MODEL });
      fresh.forEach((c, i) => known.set(c.hash, vectors[i]));

      const principals = await authz.principalsFor(doc.id);
      await db.tx(async (t) => {                  // readers see the old chunks or the new ones, never a mix
        await t.query(`DELETE FROM chunks WHERE document_id = $1`, [doc.id]);
        for (const c of chunks) await insertChunk(t, doc, c, known.get(c.hash)!, principals, EMBED_MODEL);
      });
      return;
    }
  }
}
```

> **Why load the document instead of trusting the event.** The event says *that* something changed. Reading the current document and its version means a burst of ten edits can be processed as one, and an old event arriving late does nothing. The embedding call happens outside the transaction, so a slow embedding API never holds database locks. The one remaining race, two workers indexing the same document at once, is handled by partitioning the event stream by document ID so one document's events are processed in order by one consumer.

---

The habit to take from this: treat a retrieval index the way you'd treat any copy of production data. Ask how it finds things (by meaning, by exact text, or both), how far behind the source it can fall, and whether it enforces the same access rules as the original. An index that's accurate but stale, or fast but leaky, is still a production defect.
