# Tokens, Time and Money: Streaming, Context Windows, Cost and Where the Model Runs

_Module 39.3b — Machine Learning & LLM-Powered Systems_

## The Problem

Suppose you build a customer-support platform used by software companies. You add a **Draft reply** button: a support agent opens a ticket, clicks it, and the model writes a proposed reply using the ticket thread, the customer's account details and the company's help-center articles. The agent edits it and sends it.

The first version is simple. The model has a context window of a million tokens, so the developer skips the work of choosing what to include. Every call gets the whole help center (180,000 tokens), the ticket thread and the account details. The demo is impressive: the model finds the right article on its own.

Then it meets real use, and four things go wrong.

**Agents stop clicking the button.** The spinner runs for about 20 seconds. Nine of those pass before the model produces its first word, while it reads 186,000 tokens of input. Another twelve pass while it writes a 700-token reply, one token after another. Agents type their own reply instead.

**Finance asks what the feature costs.** At an illustrative mid-range price of $3 per million input tokens and $15 per million output tokens:

```
per draft     186,000 input tokens × $3/M   = $0.558
                  700 output tokens × $15/M = $0.011
                                              ──────
                                              $0.569
40,000 drafts a day                         ≈ $22,700 a day, $680,000 a month
```

That's more than the feature's customers pay for the whole product.

**The drafts get worse, not better.** The help center includes three versions of the pricing page: current, 2025 and 2024. Drafts sometimes quote the 2024 prices. Having everything in the context didn't mean the model used the right thing.

**Long tickets lose their beginning.** A year-long enterprise escalation has 400 messages. Each email quotes the entire thread below it, so the thread comes to about 12 million tokens and doesn't fit. A quick fix keeps the most recent 20 messages. The first message, which had the contract number and the original problem, is dropped, and the draft asks the customer to explain their issue again.

Then a hospital-network customer says its support data can't be sent to an outside AI provider, and asks whether you can run the model yourselves.

Each of these is a question about the same few quantities: how many tokens go in, how many come out, how long each takes, what each costs, and where the model runs.

## What It Is

Every LLM call is measured in **tokens**, the chunks of text the model reads and writes (roughly three-quarters of an English word each). Tokens set three things at once:

- **Cost.** APIs charge per million input tokens and per million output tokens, with output typically priced several times higher than input.
- **Latency.** Input is processed quickly and in parallel. Output is generated one token at a time, so it dominates the time a response takes.
- **Limits.** The **context window** is the most tokens a model can handle in one call, counting input and output together. Separately, there's a maximum output length, and there are provider **rate limits** on requests and tokens per minute.

On top of those quantities sit four practices: **streaming** (showing output as it's generated), **context engineering** (choosing what goes into the window), **prompt caching** (reusing the processed form of a prompt prefix that repeats between calls), and the decision about **where the model runs**: a provider's API, the same models through your cloud account, or open-weight models on hardware you control.

Writing the prompt itself is 39.3a. Retrieving the right documents for the context is 39.4. Limiting and budgeting your own users' AI spending is 39.7.

## Recognizing the Problem

- Users wait more than a few seconds for any text to appear.
- Nobody can say what a single call to the feature costs, or what the feature costs per customer per month.
- Prompts include whole documents, full histories or entire knowledge bases "because the window is big enough."
- Answer quality drops as more material is added to the prompt.
- Long conversations or threads are truncated by cutting from one end.
- The same long instructions and documents are sent at full price on every call.
- The feature returns errors at peak times with HTTP 429 responses.
- Background work (nightly summaries, bulk classification) uses the same real-time API calls as interactive features.
- A customer or regulator asks where the model runs and who can see the data, and there's no clear answer.

## How It Works

### Where the time goes

A call's latency has three parts:

```
 request ─▶ queue ─▶ PREFILL ───────────────▶ first token ─▶ DECODE ─────────────────▶ done
                     reads every input token,               writes one token at a time;
                     largely in parallel;                   time ≈ output tokens ÷ speed
                     grows with input length                (tens of tokens per second
                     (a cached prefix skips most of it)      for large models)
          └───────────── time to first token (TTFT) ────┘└──────── generation time ────┘
```

- **Time to first token (TTFT)** depends mostly on input length and on provider load. The draft's nine seconds came from reading 186,000 tokens.
- **Generation time** is output length divided by speed. A 700-token reply at around 60 tokens per second takes about 12 seconds, and no amount of infrastructure changes the arithmetic much.

That gives three latency levers, in order of impact:

1. **Write less.** Asking for a reply "under 120 words" (about 250 tokens) instead of letting the model ramble cuts generation from 12 seconds to about 4. It also cuts the most expensive tokens.
2. **Read less.** A smaller input means a shorter prefill.
3. **Use a smaller or faster model** for tasks that don't need a large one. Smaller models generate faster and cost less. Many products route easy requests to a small model and hard ones to a large model.

**Reasoning models** add a fourth consideration. When a model "thinks" before answering, that thinking is output tokens: billed at output prices and generated at output speed, even when you don't see them. Most APIs let you set how much reasoning to allow. Turn it up for hard judgment calls, and turn it off for drafting and extraction.

### Streaming: perceived speed

**Streaming** sends tokens to the client as they're generated instead of waiting for the whole reply. The total time is the same, but the agent sees the first words after TTFT and reads while the rest arrives. For any output a person reads, this is the single biggest improvement in how fast the feature feels.

Providers stream over **server-sent events** (SSE): a long-lived HTTP response that delivers a series of small events such as "message started," "text delta," "message finished, with usage." Your server usually relays these to the browser over its own SSE connection (Module 9). A few details decide whether it works in production:

- **The status code is sent before the content.** Once the response has started with `200 OK`, an error halfway through can't change the status. Errors have to be sent as events in the stream, and the client has to handle a stream that ends with an error after showing half a reply.
- **Stop generating when nobody is reading.** If the agent closes the ticket, abort the upstream request. Tokens generated before the abort are still billed, but the rest aren't, and the provider's capacity is freed.
- **Intermediaries buffer.** Reverse proxies and compression can hold chunks until a buffer fills, which turns a stream back into one delayed response. Nginx, for example, needs buffering switched off for the route (`X-Accel-Buffering: no`).
- **Validation happens at the end.** You can't check a reply before showing it if you show it as it's written. Structured output (39.3a) can be streamed with a parser for incomplete JSON, but the schema check only means something once the reply is complete. When output must be validated or filtered before a person sees it, streaming conflicts with that. Output guardrails are 39.7.

Streaming is for people waiting on text. Background jobs, classification and anything feeding code rather than a reader don't need it.

### The context window, and why bigger isn't better

Context windows have grown from a few thousand tokens to hundreds of thousands, and to a million or more for some models. That changes what's possible: a whole contract, a long codebase or hours of transcript can fit in one call. It doesn't make "put everything in" a good default:

- **Cost is paid on every call.** A 180,000-token help center included 40,000 times a day is 7.2 billion input tokens a day.
- **Latency grows with input,** through the prefill.
- **Quality degrades with irrelevant material.** Models use information near the beginning and end of a long input more reliably than information in the middle (Liu et al., "Lost in the Middle"). Chroma's 2025 "Context Rot" study found performance falling as inputs grow, even on simple tasks, and falling faster when the input contains passages that look relevant but aren't, like the 2024 pricing page.

So **context engineering**, deciding what goes into each call, is the main lever for cost, speed and quality together. Its tools:

- **Select.** Include the five help articles most relevant to this ticket, not all 600. Finding them is retrieval (39.4).
- **Remove duplication.** Emails quote the whole thread below them, so a 400-message thread contains its early messages hundreds of times. Stripping quoted text shrinks the thread from about 12 million tokens to about 60,000 without losing anything.
- **Keep what matters from both ends.** When a history still doesn't fit, cutting from one end loses either the setup or the current state. Keep the first message (the original problem), the most recent messages, and a marker or summary for what was skipped.
- **Summarize (compact).** Replace the middle of a long history with a summary, generated once and stored, and refresh it as the thread grows.
- **Use structured facts instead of transcripts.** The contract number, the plan and the open incident belong in the account record, fetched from your database and included as a few lines of facts, not recovered from message 1 of 400.

Count tokens before sending when you're near a limit. Providers offer token-counting endpoints. Estimating four characters per token works for English, but other languages and code usually take more tokens per character.

### Prompt caching

Many calls share a long, identical beginning: the instructions, the examples, a document being discussed across several questions. Processing that prefix is most of the prefill work. **Prompt caching** lets the provider keep the processed prefix for a few minutes and reuse it when the next call starts with exactly the same tokens.

The effects are large. Cached input is billed at a fraction of the normal price (a tenth is typical, and lower on some models), and TTFT drops because most of the prefill is skipped. The details differ by provider:

- OpenAI caches automatically for prompts over about 1,024 tokens.
- Anthropic caches when a request marks it, either on the whole request or at chosen breakpoints. Writing to the cache costs a little more than normal input (1.25× for the default five-minute lifetime, 2× for one hour). Reading costs a tenth or less.
- Google's Gemini API offers both automatic (implicit) caching and caches you create and manage explicitly.

Caching only works on an **exact prefix match**. One changed character early in the prompt (a timestamp in the system prompt, a reordered example, a tool definition that varies between calls) invalidates everything after it. That's why 39.3a put stable content first and changing content last: it's what makes the prefix cacheable. And a cache only helps if calls arrive often enough to hit it before it expires. At 40,000 drafts a day, the shared instructions are almost always cached. For a feature used a few times an hour, the five-minute cache mostly expires unused, and the extra cost of writing it is wasted.

Applied to the draft feature, together with selection and a shorter reply:

```
                          before                     after
input                     186,000 tokens             3,000 cached (instructions, examples)
                                                     10,000 fresh (5 articles, thread, account)
output                    700 tokens                 250 tokens (under 120 words)
cost per draft            $0.569                     $0.035
40,000 drafts a day       ≈ $22,700                  ≈ $1,400
time to first word        ~9 s                       ~1 s
full reply                ~20 s                      ~5 s, streamed as it's written
```

### Other cost levers

- **Batch APIs.** Anthropic, OpenAI and Google offer batch interfaces that process requests within 24 hours at about half the price. Nightly summaries of closed tickets, bulk classification and backfills don't need an answer in seconds.
- **Model tiers.** Use the smallest model that passes your example set (39.3a) for each task, and route only the hard cases to a larger model.
- **Fewer calls.** One call that returns a summary, a category and a draft is cheaper than three calls that each re-send the same thread.
- **Measure cost per feature and per customer.** Record the token usage every response reports, with the feature and customer, and multiply by the prices. This is what turns "the AI bill went up" into a specific cause. Budgets and limits built on these numbers are 39.7.

**Provider rate limits** are measured in requests per minute and in input and output tokens per minute. Exceeding them returns HTTP 429 with a hint of when to retry. For interactive features, retry once or twice with backoff (Module 18), then show "Draft unavailable" instead of making someone wait. For background work, a queue that drains within the limit is the right structure (Module 10). Limits usually rise with your spending tier, so plan for peaks, such as Monday morning when every agent opens their queue at once.

### Where the model runs

There's a range of options, from someone else running everything to you running everything:

```
 provider API          your cloud's              hosted open-weight      self-hosted              on-device
 (Anthropic,           AI platform               inference               open weights             / local
 OpenAI, Google)       (Bedrock, Vertex AI,      (specialist providers   (vLLM, SGLang on         (llama.cpp,
                       Azure / Microsoft         serving open models)    your GPUs)               Ollama, MLX)
                       Foundry)
 ◀────────── less to operate, frontier models ──────────── more control, data stays yours ──────────▶
```

**Provider APIs** have the most capable models and nothing to operate. You pay per token, share capacity (and rate limits), send your data to the provider, and follow its schedule for model updates and retirements. Enterprise terms usually include commitments not to train on your data, limited or zero retention, and sometimes regional processing.

**The same models through your cloud platform** (for example, Claude on Amazon Bedrock and Google Vertex AI, or OpenAI's models on Azure) run under your existing cloud agreement, region and access controls. That's often enough to satisfy a data-residency requirement without running anything yourself. Ask this question first when a customer like the hospital network raises concerns.

**Open-weight models** are models whose weights are published for anyone to run: families such as Llama, Qwen, Mistral, DeepSeek, Gemma and OpenAI's gpt-oss. Licenses vary, from permissive (Apache 2.0, MIT) to custom licenses with conditions, so read the one you pick. You can use them through hosted inference providers or run them yourself:

- **Serving engines.** vLLM and SGLang are the standard open-source servers. They get high throughput from GPUs by batching many requests together continuously. Hugging Face's TGI is now in maintenance mode, and its maintainers point to vLLM and SGLang. llama.cpp, Ollama and MLX run smaller models on laptops and single machines, which is useful for development and for on-device features.
- **What you gain.** The data never leaves your infrastructure. The weights never change unless you change them, so a model you've validated keeps behaving the same indefinitely. You can fine-tune for a narrow task.
- **What it costs.** GPUs are billed by the hour whether they're busy or not. A single H100 rents for roughly $2–4 an hour on demand, depending on the provider. Larger models need several GPUs, and production needs redundancy.

For the hospital network, the draft feature at 2,000 drafts a day costs about $70 a day through an API, roughly $2,100 a month. Two rented GPUs at $3 an hour cost about $4,300 a month before anyone's time is counted. Self-hosting costs more here, and the model has to be tested against the same example set to see whether its drafts are good enough. It may still be the right decision: the contract may be worth it, or the same GPUs may serve several customers with the same requirement. What changes the economics is **utilization**. A GPU that's busy around the clock with steady work can undercut API prices. One that's idle at night and on weekends usually can't.

## When It's Appropriate

- **Streaming:** any reply a person waits to read that takes more than a second or two, such as drafts, answers or summaries.
- **Context engineering:** as soon as prompts include documents, histories or search results. That's most real features.
- **Prompt caching:** long, stable instructions or documents reused across calls, at a rate that keeps the cache warm. A support tool making 40,000 calls a day with the same 3,000-token instructions is the textbook case.
- **Batch APIs:** work that can wait hours, such as nightly summaries, backfills and bulk classification.
- **Model tiering:** features with a mix of easy and hard requests at volume. Routing the easy 80% to a small model cuts the bill substantially.
- **Your cloud's AI platform:** when customers or regulators need processing to stay within an agreement or region you already have.
- **Self-hosting open weights:** strict requirements that data can't reach any outside processor, steady high volume that keeps GPUs busy, a narrow task where a fine-tuned open model is good enough, or a need for weights that never change.

## When It's Unnecessary or Overkill

- **Streaming structured output that code consumes.** Nobody reads a JSON object as it's written. Wait for it, then validate it.
- **Careful context trimming for small, occasional calls.** A 2,000-token prompt used a few hundred times a day costs a few cents. Optimize where the tokens are.
- **Caching prompts that are short or rarely repeated.** Below the provider's minimum length, or with calls spaced beyond the cache lifetime, you pay the write premium and get nothing back.
- **Self-hosting for cost at low or bursty volume.** Idle GPUs are more expensive than API calls, and running inference well takes specialist skills.
- **The largest model for every task.** Extraction, classification and short drafts often work as well on a smaller, faster, cheaper model. Check against your example set.
- **Filling a million-token window because it's there.** Long context is for cases where the task genuinely needs the whole input at once, like reviewing one long contract, not a replacement for selecting what's relevant.

## Trade-offs

- **Streaming complicates errors and validation.** Mid-stream failures, partial replies, cancellation and proxies that buffer are all extra work, and you can't filter what you've already shown.
- **Context engineering adds a retrieval and assembly layer** that can fail in its own ways: it can leave out the one document that mattered, or its summaries can lose details.
- **Caching constrains prompt design.** Everything variable has to go after everything stable, and a small edit to the stable part invalidates the cache for every user until it warms again.
- **Cheaper models and shorter outputs can cost quality.** Every saving needs checking against the example set, not just the invoice.
- **Batch processing gives up immediacy** in exchange for price.
- **Provider APIs mean shared capacity and someone else's roadmap.** That includes rate limits at peak times, outages, and models retired on the provider's timeline.
- **Self-hosting means owning everything the provider did.** GPU capacity planning, serving-engine upgrades, security, monitoring, model evaluation, and a model that may be less capable than the frontier. The cost is fixed whether traffic comes or not.

## Alternatives

- **A trained classical model** (39.1a) when the task is narrow and high-volume enough that per-token costs dominate. LLM outputs corrected by people can become its training data.
- **Fine-tuning a small model** on your task, hosted by a provider or yourself. This trades training work for much cheaper, faster calls on that one task.
- **Precomputing instead of generating on demand.** Summaries of tickets or documents can be generated once when the content changes, stored, and shown instantly, rather than generated on every view.
- **Templates with generated slots.** For replies that are mostly fixed text, the model fills in a few fields and a template supplies the rest. That means fewer output tokens and more predictable results.

## How to Achieve It

**1. Measure first.** Log input, cached and output tokens, TTFT and total time for every call, with the feature and customer. Compute cost per call and per feature.
_Move on when_ you can name your most expensive feature and what drives its cost.

**2. Cut output.** Ask for the length the task needs, and set `max_tokens` just above it. Turn reasoning off or down where it doesn't help.

**3. Stream anything people wait to read.** Relay the provider's stream, abort on disconnect, send errors in the stream, and check that proxies don't buffer.
_Move on when_ the first words appear within about a second at normal load.

**4. Engineer the context.** Remove duplication, select what's relevant (39.4), keep both ends of long histories, and move stable facts into structured fields.

**5. Order for caching, then turn it on.** Put stable instructions and examples first and varying content last. Confirm cache hits in the usage numbers.
_Move on when_ most of the stable prefix is billed as cache reads.

**6. Move non-interactive work to batch, and route easy tasks to smaller models,** each checked against your example set.

**7. Decide where the model runs based on requirements.** Start with a provider API. Move to your cloud's platform for residency and contract reasons, and to self-hosting only when data rules, steady volume or model stability require it, with a cost comparison that includes idle time and people.

## Implementation

The implementation is in TypeScript with Express and the Anthropic SDK. There are three pieces: a streaming endpoint that relays tokens and cleans up after itself, prompt assembly with a cacheable prefix and a thread that keeps both ends, and cost accounting from the usage the API reports.

### A streaming endpoint

```ts
app.post("/tickets/:id/draft", async (req, res) => {
  const prompt = await buildDraftPrompt(req.params.id);

  res.writeHead(200, {
    "Content-Type": "text/event-stream",
    "Cache-Control": "no-cache",
    "X-Accel-Buffering": "no",              // stop nginx from holding chunks back
  });
  const send = (event: string, data: unknown) =>
    res.write(`event: ${event}\ndata: ${JSON.stringify(data)}\n\n`);

  const stream = client.messages.stream({ model: DRAFT_MODEL, max_tokens: 400, ...prompt });

  let clientGone = false;
  res.on("close", () => {                    // browser tab closed or ticket left
    if (!res.writableFinished) { clientGone = true; stream.abort(); }
  });

  stream.on("text", (delta) => send("delta", delta));

  try {
    const final = await stream.finalMessage();
    recordUsage({ feature: "draft_reply", ticketId: req.params.id, usage: final.usage });
    send("done", { stopReason: final.stop_reason });
  } catch (err) {
    if (!clientGone) send("error", { message: "Draft unavailable. Try again or write the reply." });
  } finally {
    res.end();
  }
});
```

> **Why `res.on("close")` and not `req.on("close")`.** In current Node versions, the request's `close` event fires as soon as the request body has been read, which for a POST is almost immediately, so aborting there would cancel every draft. The response's `close` event, checked against `writableFinished`, means the connection ended before you finished writing. That's the case where generation should stop.

> **The error arrives as an event.** By the time the model fails, the browser has already received `200` and maybe half a draft. The client must treat an `error` event as final and keep what it received visibly marked as incomplete, not as an agent-ready reply.

### Prompt assembly: stable first, both ends kept

```ts
async function buildDraftPrompt(ticketId: string) {
  const ticket = await tickets.get(ticketId);
  const [account, articles] = await Promise.all([
    accounts.facts(ticket.accountId),          // plan, contract no., open incidents: a few lines
    helpCenter.relevant(ticket, 5),            // retrieval (39.4), not the whole help center
  ]);
  const thread = fitThread(ticket.messages.map(stripQuotedReply), 6_000);

  return {
    // Identical on every call, so it's cached once and read at a fraction of the price after.
    system: [{ type: "text" as const, text: DRAFT_INSTRUCTIONS, cache_control: { type: "ephemeral" as const } }],
    messages: [{
      role: "user" as const,
      content: [
        `<account>\n${account}\n</account>`,
        `<articles>\n${articles.map((a) => `<article title="${a.title}" updated="${a.updatedAt}">\n${a.body}\n</article>`).join("\n")}\n</articles>`,
        `<thread>\n${thread}\n</thread>`,
        "Draft the agent's next reply in under 120 words.",
      ].join("\n\n"),
    }],
  };
}

const approxTokens = (s: string) => Math.ceil(s.length / 4); // English estimate; count exactly near hard limits

// Keep the first message (the original problem) and as many recent ones as fit.
function fitThread(msgs: Message[], budget: number): string {
  const fmt = (m: Message) => `[${m.sentAt.toISOString()}] ${m.author}: ${m.body}`;
  const first = fmt(msgs[0]);
  let used = approxTokens(first);
  const kept: string[] = [];
  for (let i = msgs.length - 1; i > 0; i--) {
    const line = fmt(msgs[i]);
    if (used + approxTokens(line) > budget) {
      kept.unshift(`[${i} earlier messages omitted]`);
      break;
    }
    used += approxTokens(line);
    kept.unshift(line);
  }
  return [first, ...kept].join("\n");
}
```

> **What breaks the cache.** Anything that varies placed before the cached block: a timestamp in the instructions ("Today is…"), the agent's name, a per-customer tone setting. Each belongs in the user message, after the cached prefix. The `updated` attribute on each article serves the quality problem, not caching: with dates in view, the instructions can tell the model to prefer the most recently updated article when two disagree, which addresses the 2024 pricing page.

### Cost from reported usage

```ts
interface Prices { inputPerM: number; outputPerM: number; cacheWriteX: number; cacheReadX: number }

function callCostUsd(u: Anthropic.Usage, p: Prices): number {
  const input =
    u.input_tokens * p.inputPerM +                                  // fresh, uncached input
    (u.cache_creation_input_tokens ?? 0) * p.inputPerM * p.cacheWriteX +
    (u.cache_read_input_tokens ?? 0) * p.inputPerM * p.cacheReadX;
  return (input + u.output_tokens * p.outputPerM) / 1_000_000;
}
```

> **Why compute it per call.** The provider's invoice is one number a month. Recording `callCostUsd` with the feature, ticket and customer on every call shows which feature, which customer and which change made it grow. It also shows whether caching is working: a steady share of `cache_read_input_tokens` means the prefix is stable, and a sudden return to `cache_creation_input_tokens` on every call means something started varying at the top of the prompt. Prices change and differ by model, so keep them in configuration, not code.

## Further Reading

- **Anthropic documentation: "Prompt caching"** and **OpenAI documentation: "Prompt caching."** The exact rules for prefixes, minimum lengths, lifetimes and pricing, which differ in ways that matter.
- **Anthropic, OpenAI and Google documentation on streaming** (server-sent event types) and **batch processing** (the batch APIs and their turnaround).
- **Nelson F. Liu et al., "Lost in the Middle: How Language Models Use Long Contexts"** (TACL, 2024). Why position in a long context matters.
- **Chroma Research, "Context Rot: How Increasing Input Tokens Impacts LLM Performance"** (2025). Measurements across many models showing quality falling as input grows, especially with distracting material.
- **Woosuk Kwon et al., "Efficient Memory Management for Large Language Model Serving with PagedAttention"** (SOSP 2023). The paper behind vLLM, explaining why batching many requests is what makes self-hosting efficient.
- **vLLM** and **SGLang** documentation, for serving open-weight models, and the **TGI repository's maintenance notice** for where that project stands.
- **Chip Huyen, _AI Engineering_** (O'Reilly, 2025). Chapters on inference optimization and on the cost and latency trade-offs of building on foundation models.
- **MDN Web Docs, "Using server-sent events,"** for the browser side of the stream.
