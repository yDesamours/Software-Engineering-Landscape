# Where the CPU Actually Goes: Sampling Profilers and Flame Graphs

_Module 22.1a — Performance Profiling_

## The Problem

A reporting service renders tenant usage reports as JSON. After a Tuesday release, its p99 climbs from 180ms to 1.4s and pod CPU sits at 85%. Nobody changed the report endpoint directly, so the team reasons about it.

1. **Guess one:** "JSON encoding is slow for big reports." Someone swaps `encoding/json` for a faster third-party encoder. Two days of work, a new dependency, p99 goes from 1.4s to 1.38s.
2. **Guess two:** "GC pressure." GOGC gets raised. Memory use rises 40%, latency doesn't move.
3. **Guess three:** "The database." The query log (6.4b) shows `db_ms` at 22ms per request, the same as last week.

Then someone takes a 30-second CPU profile from one pod under live traffic.

```
Go samples at 100 Hz per busy thread.
4 cores × 85% busy × 30 s × 100 samples/s  ≈ 10,200 samples

flat%   cum%   function
 1.8%  61.4%   report.sanitizeLabel
 0.9%  58.7%   regexp.MustCompile
 ...
 3.1%   4.2%   encoding/json.(*encodeState).marshal
```

61% of all CPU time is in `regexp.MustCompile`, called from a label sanitizer that the release moved inside a loop. It runs once per row, and reports have 30,000 rows. JSON encoding — the thing optimized for two days — was 4%.

```
Amdahl's law, applied to guess one:
  JSON = 4% of time.  Make it 2× faster → save 2%.   Best case.
  regexp = 61%.        Hoist it out of the loop → save ~61%.
```

One line of code fixed it. Three guesses cost most of a week, and all three were plausible. **That is the whole argument for profiling: intuition about where time goes is reliably wrong, and it's wrong in a way that feels like expertise.**

## What It Is

A **profiler** tells you where a program spends a resource — here, CPU time — broken down by function and call path.

A **sampling profiler** does it by interrupting the program at a fixed rate (Go: 100 times per second) and recording the stack of whatever is running. Functions that appear in many samples are where the time goes. It doesn't observe every call, it takes a statistical picture, which is why it can run in production with low overhead.

The usual picture is a **flame graph**: each stack is a tower of boxes, callers below callees, and a box's *width* is the share of samples it appeared in.

The obvious neighbor is **tracing** (Module 19): a trace tells you *which operation* in a request was slow — "the render step took 1.2s." A profile tells you *which code* burned the CPU inside that step. Traces locate; profiles explain. You usually need both, in that order.

## Recognizing the Problem

- CPU is high, and nobody can say which function is responsible without guessing.
- A trace shows a long span with no child spans inside it — time spent in your own code, not waiting on anything.
- A release made things slower and the diff is too large to reason about.
- An optimization shipped and the metric didn't move.
- Throughput stops rising while CPU approaches 100% (22.5b).
- Your cloud bill is dominated by compute and you have never looked at what that compute does.
- Performance discussions in review sound like "I think X is expensive."

And one signal that means *this is not your tool*: latency is high but **CPU is low**. The request is waiting — on a network call, a lock, a pool, the event loop. A CPU profile will look boring. That's 22.1c.

## How It Works

### Sampling, not counting

An **instrumenting** profiler wraps every function call with timing code. It's exact, and it distorts what it measures: small, frequently-called functions get slowed down far more than large ones, so the profile overstates them.

A **sampling** profiler takes a snapshot of the stack at intervals. A function that uses 30% of CPU appears in about 30% of samples. Precision grows with sample count: 10,000 samples give a clear picture of anything above about 1%; 200 samples give you only the top few functions. So **profile long enough and under real load**. A 5-second profile of an idle pod is noise.

### Flat versus cumulative

Two numbers per function, and confusing them sends people to the wrong code.

```
flat  = samples where this function was at the top of the stack
        (its own code was running)
cum   = samples where this function was anywhere in the stack
        (it, or something it called, was running)
```

`sanitizeLabel` above has 1.8% flat and 61.4% cum: its own code is cheap, but it *calls* something expensive. Sort by `cum` to find the responsible caller; sort by `flat` to find the leaf doing the work.

### Reading a flame graph

```
┌───────────────────────────────────────────────────────────────┐
│ http.(*conn).serve                                            │
├───────────────────────────────────────────────────┬───────────┤
│ report.Handler                                    │ other     │
├─────────────────────────────────────────┬─────────┤           │
│ report.render                           │ json    │           │
├─────────────────────────────────────────┤ .Marsh  │           │
│ report.sanitizeLabel                    │         │           │
├─────────────────────────────────────────┤         │           │
│ regexp.MustCompile          ← wide = hot│         │           │
└─────────────────────────────────────────┴─────────┴───────────┘
```

- **Width is time.** The x-axis is *not* time order; boxes are sorted alphabetically or by size. A wide box is expensive regardless of where it sits.
- **Look for wide plateaus near the top.** A wide box with nothing on top of it is a function doing the work itself.
- **Look for the same function in many towers.** A utility called from twenty places may be 3% in each and 60% overall. Most tools can merge by function name (pprof's "focus" and the flat view) to reveal it.
- **Ignore narrow spikes.** Deep, thin stacks are visually loud and cheap.

### Profile the workload, not the code

The same code has a different profile under different input. The regexp only dominated because real reports have 30,000 rows; a unit test with 10 rows would show `regexp.MustCompile` as a rounding error. Profiles from production (or from a load test with production-shaped data — 22.5a) are the ones that count.

### On-CPU is one kind of time

A CPU profiler only sees threads that are running. A goroutine blocked on a socket, a mutex, or a channel contributes nothing to it. Go has separate profiles for the waiting kinds — `block` and `mutex` — and Node and Java have wall-clock modes. If CPU is low and latency is high, switch profile type rather than staring harder at the CPU one.

## When It's Appropriate

- **CPU utilization above ~60% on a service where latency or cost matters.** That's where CPU is plausibly the constraint.
- **Any "we made it faster" change**, before and after. The profile is the evidence the change mattered.
- **A performance regression between releases.** A *differential* profile (before minus after) points straight at what changed.
- **Compute-heavy paths:** rendering, serialization of large payloads, compression, image work, search scoring, pricing calculations, report generation.
- **Before scaling out.** If 40% of CPU is wasted in one function, eight more pods is a 40% overspend on eight more pods.

## When It's Unnecessary or Overkill

- **I/O-bound requests with low CPU.** Wrong profile type (22.1c).
- **Before you know which request is slow.** Profile after the trace or the RED metrics (16.3) have pointed at a route; a whole-process profile of a service with forty endpoints blends them together (though labels help — see Implementation).
- **Micro-tuning code that's 0.5% of samples.** Amdahl's law says the ceiling is 0.5%.
- **A service at 5% CPU with a comfortable latency budget.** The cost of the machine is not the cost of your time.
- **Fleet-wide continuous profiling for a three-service system** where an on-demand profile takes two minutes to grab.

## Trade-offs

- **Overhead is small but not zero.** Sampling at 100 Hz typically costs a few percent while active. Continuous profilers work around this by sampling a fraction of the time or a fraction of the fleet.
- **Statistics lie at low sample counts.** A 3% function in a 300-sample profile could be 1% or 6%. Decisions about small differences need either longer profiles or benchmarks.
- **Inlining and optimization blur attribution.** The compiler inlines small functions into their callers, so their time appears under the caller. JIT runtimes (JVM, V8) do this dynamically, and some JVM profilers additionally only sample at safepoints, which biases results toward certain code — a known distortion that tools like async-profiler exist to avoid.
- **Profile endpoints are an attack surface.** They expose internals, can be used to burn CPU, and heap profiles can contain data. They belong on an internal port.
- **Profiles show symptoms of design, not design.** "60% in JSON encoding" might mean the encoder is slow, or that you're returning 8MB responses nobody reads. The profile says where; deciding what to change is still your job.
- **Continuous profiling is another telemetry pipeline** (19.x): storage, retention, symbol handling, access control.

## Alternatives

- **Timing logs and spans.** Wrapping sections with timers is instrumenting by hand. Fine for a known suspect; useless for finding one you don't suspect.
- **Benchmarks.** Precise measurement of one function under controlled input. Complementary: the profile finds the hot function, the benchmark proves the fix and guards it. A benchmark alone optimizes whatever you thought to benchmark.
- **System-wide profilers** (`perf`, eBPF-based tools). They see everything on the host, including the kernel and other processes — useful when the time is in syscalls, TLS, or a noisy neighbor, less convenient for mapping back to your source.
- **APM "code-level" views.** Many APM agents include profilers. Convenient if already deployed; same underlying technique.

## How to Achieve It

**Level 0 — Guessing.** Optimizations are chosen by intuition and justified afterward.

**Level 1 — On-demand profiles.** Expose the runtime's profiler on an internal port, and know the one command that grabs a 30-second profile from a live instance. Write it in the runbook.
_Signal you need it:_ the first time a CPU-related incident is resolved by a guess, or not resolved.

**Level 2 — Benchmark plus profile in development.** Hot paths have benchmarks with production-sized inputs; changes to them come with before/after numbers.
_Signal you need it:_ a fix got reverted because it didn't help, or a regression reached production.

**Level 3 — Labeled profiles.** Samples carry route, tenant tier, or job type, so a whole-process profile can be sliced to "just `/reports`."
_Signal you need it:_ profiles from a multi-endpoint service are too blended to act on.

**Level 4 — Continuous profiling.** A low-overhead agent profiles the fleet all the time; you can compare this week to last week, or this release to the previous one, after the fact.
_Signal you need it:_ regressions are found days late, or the slow period is over before anyone could grab a profile.

**Level 5 — Profiles as input.** Profile-guided optimization feeds production profiles to the compiler; CI compares benchmark results against a baseline and flags regressions.
_Signal you need it:_ compute is a significant cost line and single-digit percentages are worth engineering time.

## Implementation

**Go**, because profiling is built into its standard library and toolchain — there's nothing to install — and because the `flat`/`cum` vocabulary above comes directly from `pprof`.

### Exposing the profiler — on its own port

```go
package main

import (
	"net/http"
	_ "net/http/pprof" // registers /debug/pprof/* on http.DefaultServeMux
)

func main() {
	// Internal listener: only the DefaultServeMux, which now has pprof.
	go func() {
		_ = http.ListenAndServe("127.0.0.1:6060", nil)
	}()

	// Public listener: a separate mux that never sees pprof.
	api := http.NewServeMux()
	api.HandleFunc("/reports/", reportHandler)
	_ = http.ListenAndServe(":8080", api)
}
```

> **Aside: the blank import is a side effect with a security consequence.** `net/http/pprof` registers its handlers on the *default* mux. If your public server also uses `http.DefaultServeMux` — which it does whenever you pass `nil` as the handler — you have just published your profiler to the internet. Keep the public API on its own mux, as above.

Grab a profile from a live instance and open the interactive view:

```bash
go tool pprof -http=:8081 'http://localhost:6060/debug/pprof/profile?seconds=30'
```

In the UI, the flame graph, `top` sorted by `cum`, and `source` (line-level costs for one function) are the three views that do most of the work.

### Labels: slicing a profile by route

```go
import "runtime/pprof"

func withProfileLabels(route string, next http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		pprof.Do(r.Context(), pprof.Labels("route", route), func(ctx context.Context) {
			next(w, r.WithContext(ctx))
		})
	}
}
```

Every sample taken while this handler runs carries `route=/reports`. In pprof, `-tagfocus=route=/reports` narrows the whole profile to that endpoint.

> **Aside: labels are a cardinality decision.** Route and tenant *tier* are safe. Tenant *ID* or user ID multiplies the profile's size by the number of tenants — the same trap as metric labels in 16.3.

### The bug and the proof

```go
// Before: compiles the pattern on every call — 30,000 times per report.
func sanitizeLabel(s string) string {
	re := regexp.MustCompile(`[^\p{L}\p{N} _.-]+`)
	return re.ReplaceAllString(s, "")
}

// After: compiled once. Regexp is safe for concurrent use.
var labelDisallowed = regexp.MustCompile(`[^\p{L}\p{N} _.-]+`)

func sanitizeLabel(s string) string {
	return labelDisallowed.ReplaceAllString(s, "")
}
```

A benchmark proves the fix and keeps it fixed:

```go
func BenchmarkSanitizeLabel(b *testing.B) {
	in := "Q3 — Seat usage (EU) / tenant #4411"
	for b.Loop() { // Go 1.24+; use `for i := 0; i < b.N; i++` on older versions
		sanitizeLabel(in)
	}
}
```

```bash
go test -bench=SanitizeLabel -benchmem -cpuprofile=cpu.out ./report
go tool pprof -top cpu.out
```

To see what a release changed, compare two profiles directly — positive values are new cost:

```bash
go tool pprof -top -diff_base=before.pprof after.pprof
```

> **Aside: the benchmark measures the function; only the profile says it matters.** A 20× speedup on a function that's 1% of CPU is a 1% improvement. Keep both numbers in the PR description.

## Further Reading

- **Go documentation, "Diagnostics"** (go.dev/doc/diagnostics) — the map of profile types (CPU, heap, block, mutex, goroutine) and when each applies, plus the execution tracer.
- **The `pprof` README and `go tool pprof -help`** — flags for focus, ignore, tag filtering, and diffing that the web UI doesn't advertise.
- **Brendan Gregg, "Flame Graphs"** (brendangregg.com/flamegraphs.html) — the origin of the visualization, and the on-CPU/off-CPU distinction that 22.1c picks up.
- **Brendan Gregg, _Systems Performance_ (2nd ed.)** — the reference text for profiling methodology at every layer, from application to kernel.
- **Go documentation, "Profile-guided optimization"** — how to feed production profiles back into the compiler, and what gains to expect.
- **Grafana Pyroscope and Parca documentation** — two open-source continuous profilers, useful for seeing what Level 4 involves operationally.
- **async-profiler README** (github.com/async-profiler/async-profiler) — the clearest explanation of safepoint bias and why it matters.

A **Java** sibling would be worth writing: the JIT makes profiles change shape as code warms up, inlining is dynamic rather than fixed at compile time, and the choice between JFR and async-profiler is really a choice about which biases you can tolerate — none of which Go's ahead-of-time compiler exposes. Not yet written.
