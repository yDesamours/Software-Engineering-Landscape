# Doing Less Work on the Hot Path

_Module 22.2 — Application-Level Optimization_

## The Problem

A ticketing platform sells seats for concerts and sports events. Its seat-map endpoint, written in TypeScript on Node.js, returns every seat in a venue with its status (open, held, or sold) and its price. The front end draws the map from that response.

The endpoint was built and tested against a 400-seat theater, where it responded in 4 ms. Its core looked like this:

```ts
const map = seats.map((s) => ({
  ...s,
  status: held.includes(s.id) ? "held" : sold.includes(s.id) ? "sold" : "open",
  price: priceBands.find((b) => b.sectionId === s.sectionId)?.price,
}));
```

Then the platform sold tickets for a 42,000-seat stadium. Ten minutes into the on-sale, 14,000 seats were held in carts and 20,000 were sold. For every seat that's still open, `includes` scans both arrays to the end without finding it:

| | Seats | Held + sold | Comparisons per request |
|---|---|---|---|
| Test theater | 400 | 30 | about 12,000 |
| Stadium on-sale | 42,000 | 34,000 | about 1.4 billion |

The venue was 105 times larger, and the work was about 119,000 times larger. On the production instances, each request took about 2.8 seconds of pure CPU time.

That alone would be a slow endpoint. What turned it into an outage is that **Node runs JavaScript on a single thread.** For those 2.8 seconds, the process did nothing else: no other request, no health check, no timer.

1. About 30 seat-map requests per second arrived, spread over six instances, so each instance received five per second and could complete about 0.36.
2. The event loop was blocked continuously. Requests to *other* endpoints on the same instances, such as checkout, queued behind the seat maps.
3. The Kubernetes liveness probe had a one-second timeout. It failed three times in a row, and Kubernetes restarted the pod.
4. The restarted pod's traffic moved to the other five, which blocked faster. Within four minutes, every instance was restarting in a loop.

The fix took an afternoon: lookups through a `Set` and a `Map` instead of arrays, which reduced the core work to about 84,000 hash lookups and 2 ms. The team also stopped sending all 42,000 seats at once, which is covered below.

## What It Is

**Application-level optimization** is reducing the work your own code does per request, before anyone reaches for more hardware, a cache, or a new architecture.

It isn't one technique. It is a small set of questions you ask of a hot path, each with its own kind of fix:

1. Is the work growing faster than the data? (algorithmic cost)
2. Is the same work being done more than once? (repeated work)
3. Are there more round trips than necessary? (I/O shape)
4. Is anyone reading the result? (unnecessary work)
5. Does it need to happen now? (deferral)
6. Is this work stopping other work? (shared execution resources)
7. Are expensive resources being recreated? (reuse)

This article covers the first six in turn. The seventh, connection pools, is covered in depth in Module 5 and 22.3. Profiling (22.1a) tells you *which* code path to ask these questions about.

## Recognizing the Problem

- An endpoint that's fast in tests and slow for your largest customers.
- Latency that grows faster than the data does, for example ten times more rows making a request a hundred times slower.
- One slow endpoint making *unrelated* endpoints on the same instance slow.
- Health checks failing under load while the process is still running.
- In Node: event-loop delay above a few tens of milliseconds, or event-loop utilization near 100%.
- Paginated lists that get slower the further users page.
- More queries or downstream calls per request than there are things on the screen (6.4a).
- Response payloads measured in megabytes.

## How It Works

The idea behind all of these is one line:

```
cost of a request  =  Σ (number of times each operation runs × cost of one run)
```

Most slow code is not slow because one operation is expensive. It's slow because a cheap operation runs a number of times that nobody calculated, and that number depends on production data.

### 1. Work that grows faster than the data

`array.includes` inside `array.map` is a loop inside a loop: n × m. Nobody wrote a nested loop on purpose. It's hidden behind two method calls, each of which looks cheap on its own. Common places where this happens:

- `includes`, `find`, `indexOf`, or `filter` inside a loop;
- string concatenation in a loop, in languages where strings are immutable;
- removing items from the front of an array one at a time;
- a sort inside a loop;
- a query or HTTP call inside a loop, the same shape with network latency added (6.4a).

The fix is almost always to build an index once (a `Set` or `Map`) and look things up in it. This is the only item in the list that is purely a matter of "use a better data structure."

When reviewing code, the useful question isn't "what's the complexity?" It's "**what is n for our largest customer?**" O(n²) is fine for twelve pricing plans and a disaster for 42,000 seats.

### 2. Work done more than once

- **Constant work inside a function** that doesn't depend on its arguments: the regex compiled per call in 22.1a, a date formatter built per row.
- **The same lookup made several times in one request**, for example loading the current tenant's settings in five different services. A per-request memo removes it and has no staleness problem, because it lasts only for that request.
- **Values derived at read time that could be computed at write time.** A venue's price bands change a few times a day and are read thousands of times a minute. Computing a section-to-price map when they change moves the work to the rare path. This is the materialized-value idea from 6.2a, applied in memory.

### 3. More round trips than necessary

Network calls are expensive mostly because of the round trip, not the work. Three fixes:

- **Batch:** one query with `WHERE id = ANY($1)` instead of fifty queries (6.4a), or one call to a bulk API.
- **Run independent calls in parallel:** the seat-map handler awaited seats, holds, and sales one after another, 40 ms each. Running them concurrently cut 120 ms to about 40.
- **Bound the concurrency:** `Promise.all` over 500 items starts 500 operations at once. That can exhaust a connection pool (5.4b), trigger a downstream rate limit (Module 18), or overload the dependency. Cap it.

### 4. Work that nobody reads

- **Unused columns and fields.** `SELECT *` into an object that's serialized in full, when the client uses four fields.
- **Payloads larger than the screen.** The stadium map sent 42,000 seats (6 MB of JSON) when the first screen showed section-level availability. The redesigned endpoint returns about 60 sections with counts, and a second endpoint returns seats for one section when the user zooms in. This is lazy loading at the API level.
- **Pagination that reads what it skips.** `OFFSET 100000 LIMIT 50` makes the database produce 100,050 rows and discard 100,000 of them. Page 2,000 costs 2,000 times as much as page 1. **Keyset (cursor) pagination** asks for the rows after the last one seen, `WHERE (created_at, id) < ($1, $2)`, which uses an index and costs the same on every page. The trade-off is that you can't jump to page 37. Module 7.3 covers the API side.

### 5. Work that doesn't need to happen now

Sending the confirmation email, generating a PDF, updating search indexes, and recalculating a dashboard don't need to finish before the response is sent. Moving them to a background job (Module 10) removes their cost from request latency. The trade-off is that they can fail independently and need retries and monitoring.

### 6. Work that stops other work

Every runtime has a shared resource that one request can take away from all the others:

| Runtime | Shared resource | How it runs out |
|---|---|---|
| Node.js | The single JavaScript thread (event loop) | Any synchronous CPU work: loops, `JSON.parse` of large bodies, synchronous crypto, regex backtracking |
| Java (thread-per-request) | The request thread pool | Threads blocked on slow calls; the pool fills and new requests queue |
| Go | Mostly nothing at the language level | Shared connection pools and mutexes instead |
| Any | Connection pools, locks | Long transactions and slow queries holding them |

In Node the effect is the most dramatic, because the pool has a size of one. Three ways to handle CPU-heavy work there:

- **Make it smaller** (sections 1–4). Always try this first.
- **Break it up.** Process in chunks and yield to the event loop between them, so other requests get a turn. The total time stays the same, and the chunked request itself gets a bit slower. What improves is everyone else's latency.
- **Move it off the loop.** Worker threads (`worker_threads`, or a pool library such as Piscina) run JavaScript on other cores. Passing data to a worker copies it, so this pays off for work that is much more expensive than copying its input.

> **Aside: a liveness probe on a blocked event loop makes things worse.** A process that is slow because it's overloaded is not a process that's broken. Restarting it throws away its in-flight work and pushes its load onto the other instances, as in the outage above. Liveness probes should detect deadlock, with generous timeouts. Readiness probes are the ones that should take an overloaded instance out of rotation temporarily. Module 23 covers load shedding.

## When It's Appropriate

- A profile (22.1a) or the per-request attribution line (6.4b) points at your own code.
- Performance varies by customer size, which usually means some n is hidden in the code.
- Before scaling out. Ten instances running quadratic code are ten times as expensive as necessary, and they still fall over for the next larger customer.
- Reviewing code that loops over data whose size you don't control: tenants, venues, catalogs, imports.

## When It's Unnecessary or Overkill

- **Replacing `map` with a `for` loop** or similar micro-optimizations, unless a profile shows that exact code is hot. JavaScript engines optimize both well, and the readable version is almost always fine.
- **Indexes for collections that are small by definition.** `plans.find(...)` over twelve plans needs no `Map`.
- **Worker threads for work that takes a few milliseconds.** Copying the input to the worker can cost more than the work.
- **Keyset pagination for a list that never exceeds a few pages.** Offset pagination is simpler and supports page numbers.
- **Deferring work the user is waiting to see.** If the next screen shows the PDF, making PDF generation asynchronous only moves the waiting into polling.

## Trade-offs

- **Indexes cost memory.** A `Set` of 34,000 IDs is small; an in-memory index over millions of records is not, and it needs to be kept up to date.
- **Computing at write time adds a consistency problem.** The precomputed map has to change when the source changes, which is the invalidation problem from Module 13.
- **Parallel I/O concentrates load.** Fifty concurrent queries from one request need fifty connections at the same moment. Unbounded concurrency can move the bottleneck to the database or cause it to reject connections.
- **Lazy APIs cost round trips.** A client that ends up requesting every section makes 60 calls instead of one. Design around what users actually do.
- **Chunking and worker threads add complexity.** Chunked work can be interrupted between chunks, so its data can change while it runs. Worker threads have their own error handling, their own memory, and the cost of copying data in and out.
- **Deferred work can fail after the user was told it succeeded.** It needs retries, idempotency, and monitoring (Module 10).
- **Optimized code is often less obvious.** Leave a comment that says why, so the next person doesn't "simplify" it back.

## Alternatives

- **More hardware.** It helps with linear costs. It doesn't help with quadratic ones: doubling the instances bought the stadium nothing, because each request still blocked its instance for 2.8 seconds.
- **Caching the result** (Module 13). Useful when the result is expensive and read often. A cache in front of quadratic code still pays the full cost on every miss, and at on-sale time the data changes every second.
- **Moving computation into the database.** A join or aggregation in SQL uses the database's indexes instead of the application's loops, as long as the database isn't already the constraint.
- **A different runtime for CPU-heavy components.** A service in Go or Java for the CPU-bound part, when a Node service's work is mostly computation rather than I/O. This is a real option, but it's a service boundary, with everything that implies (Module 2).
- **Rate limiting and load shedding** (Modules 18 and 23). These protect the other requests when a hot path is expensive. They don't make it cheaper.

## How to Achieve It

**Level 0 — know n.** For each hot endpoint, know the size of the largest customer's data, and test with data of that size (22.3a).
_Signal you're here:_ tests use a handful of records, and production has tenants with millions.

**Level 1 — fix what the profile points at.** Replace hidden nested loops with indexes, and move constant work out of loops.
_Signal you need it:_ a profile or attribution line that points into your code.

**Level 2 — fix the I/O shape.** Batch queries, run independent calls concurrently with a cap, and count queries per request.
_Signal you need it:_ more database or downstream calls per request than items on the screen.

**Level 3 — send and compute only what's used.** Trim payloads, add keyset pagination for deep lists, and split large responses into lazily loaded parts.
_Signal you need it:_ multi-megabyte responses, or pages that slow down as users go deeper.

**Level 4 — protect the shared resource.** Monitor event-loop delay (or thread-pool saturation), and move CPU-heavy work to workers or background jobs.
_Signal you need it:_ one endpoint's slowness showing up in other endpoints' latency.

**Level 5 — make cost a review question.** Code review asks "what is n here for our largest customer?", and load tests (22.5) use data at that scale.
_Signal you need it:_ the second time an incident is caused by a customer bigger than the test data.

## Implementation

TypeScript on Node.js, because Node's single thread makes the cost of CPU work on the hot path visible at the level of the whole process, which is the most important lesson here.

### Indexes instead of scans

```ts
// Build each index once per request: O(n + m) instead of O(n × m).
const heldIds = new Set(held.map((h) => h.seatId));
const soldIds = new Set(sold.map((s) => s.seatId));
const priceBySection = new Map(priceBands.map((b) => [b.sectionId, b.price]));

function statusOf(seatId: string): SeatStatus {
  if (soldIds.has(seatId)) return "sold";
  if (heldIds.has(seatId)) return "held";
  return "open";
}
```

### Concurrent I/O, with a cap

```ts
import pLimit from "p-limit";

// Independent reads: run them concurrently (about 40 ms instead of 120).
const [seats, held, sold] = await Promise.all([
  seatRepo.forSection(venueId, sectionId),
  holdRepo.active(eventId, sectionId),
  saleRepo.completed(eventId, sectionId),
]);

// Fan-out over a list whose size you don't control: cap it.
const limit = pLimit(8); // well below the connection pool size (Module 5)
const quotes = await Promise.all(
  cartItems.map((item) => limit(() => pricing.quote(item))),
);
```

> **Aside: the cap is related to the pool size.** If the pool has 10 connections and each of 20 concurrent requests fans out 8 queries at once, requests wait for connections from each other. Their latency includes pool wait (the fourth number in 6.4b's log line), and a single request can starve the rest. Keep per-request fan-out small relative to the pool, and watch pool-wait time.

### Keyset pagination

```ts
type Cursor = { createdAt: string; id: string };

async function listOrders(tenantId: string, after?: Cursor, pageSize = 50) {
  // Requires an index on (tenant_id, created_at DESC, id DESC).
  const rows = await db.query<Order>(
    `SELECT id, created_at, total_cents, status
       FROM orders
      WHERE tenant_id = $1
        AND ($2::timestamptz IS NULL OR (created_at, id) < ($2, $3::uuid))
      ORDER BY created_at DESC, id DESC
      LIMIT $4`,
    [tenantId, after?.createdAt ?? null, after?.id ?? null, pageSize],
  );
  const last = rows.at(-1);
  return { rows, next: last ? { createdAt: last.created_at, id: last.id } : null };
}
```

The `id` in the cursor breaks ties between rows with the same timestamp. Without it, rows that share a `created_at` at a page boundary can be skipped or repeated.

### Watching and protecting the event loop

```ts
import { monitorEventLoopDelay, performance } from "node:perf_hooks";
import { Piscina } from "piscina";

// Delay: how late the loop runs scheduled work. Utilization: how busy it is.
const delay = monitorEventLoopDelay({ resolution: 20 });
delay.enable();
let lastElu = performance.eventLoopUtilization();

setInterval(() => {
  const elu = performance.eventLoopUtilization(lastElu); // since the last sample
  lastElu = performance.eventLoopUtilization();
  metrics.gauge("event_loop_delay_p99_ms", delay.percentile(99) / 1e6); // ns → ms
  metrics.gauge("event_loop_utilization", elu.utilization);
  delay.reset();
}, 10_000).unref();

// CPU-heavy work that is legitimately large goes to a worker pool.
const pool = new Piscina({
  filename: new URL("./render-worker.js", import.meta.url).href,
  maxThreads: 2, // leave cores for the main loop and the rest of the node
});

export async function renderVenueSvg(layout: VenueLayout): Promise<string> {
  return pool.run(layout); // the layout is copied to the worker; worth it only for big jobs
}
```

Event-loop delay is the Node-specific signal that belongs on the dashboard next to latency. A p99 delay of 2,800 ms would have explained the outage in one graph.

## Further Reading

- **Nelson Elhage's "Accidentally Quadratic" blog**, and **Bruce Dawson's posts on O(n²) bugs in Windows and Chrome.** Catalogs of real quadratic bugs in widely used software, mostly hidden behind innocent-looking library calls.
- **The Node.js documentation: "Don't Block the Event Loop (or the Worker Pool)"**, plus the `perf_hooks` and `worker_threads` references. The first is the clearest explanation of why the single thread matters and what blocks it.
- **Markus Winand, _SQL Performance Explained_** and use-the-index-luke.com, especially the "no offset" pages on pagination. The standard explanation of why offset gets slower and how keyset avoids it.
- **The Piscina documentation**, for worker pool sizing and the cost of passing data.
- **Jon Bentley, _Programming Pearls_.** Old, short, and still the best book on thinking about the cost of code in terms of the data it processes.
- **Module 6.4a** (N+1 queries), **Module 5** (pool sizing), **Module 10** (background jobs), and **Module 7.3** (pagination in API design).
