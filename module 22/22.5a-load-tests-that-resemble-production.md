# Load Tests That Resemble Production

_Module 22.5a — Load Testing_

## The Problem

A city launches an online portal for school enrolment. Applications open at 9:00 on a Monday in March, and the city expects a rush: parents who want popular schools believe, wrongly, that applying first helps.

The team estimates a peak of 900 requests per second and runs a load test two weeks before launch:

```ts
export const options = { vus: 500, duration: "10m" };

export default function () {
  http.get(`${BASE}/api/schools/42`, { headers: { Authorization: `Bearer ${TOKEN}` } });
}
```

Result: 2,400 requests per second, p95 latency 110 ms, no errors. The team reports "we can handle more than 2.5 times the expected peak."

At 9:00 on launch day, about 900 requests per second arrive. Within four minutes, p95 is 6 seconds and 18% of requests fail. The database is at 100% CPU. The portal is unusable for most of the first hour.

The test was accurate. It measured exactly what it did. Almost nothing it did resembled launch day:

| | The test | Launch day |
|---|---|---|
| Endpoints | One: a school's detail page | Search with filters 35%, login 20%, school pages 15%, saving the application form 20%, document uploads 10% |
| Keys | School 42, every time | 2,100 schools, heavily skewed toward a few dozen popular ones |
| Cache | Warm, with a 100% hit rate on one key | Cold: deployed at 8:30. Search results with filter combinations are mostly uncacheable |
| Authentication | One token issued before the test | 180 logins per second, each a bcrypt hash |
| Writes | None | 180 form saves per second |
| Data | 5,000 applications in staging | 60,000 new applications in the first hour, on top of last year's 400,000 |
| Load model | 500 users, each waiting for a response before sending the next request | Parents arriving at their own pace, regardless of how slow the site is |
| Load generator | A 2-core CI runner, at 100% CPU | n/a |

Two lines of that table did most of the damage:

- **Logins.** The password hash (Module 4.2) is deliberately slow: about 250 ms of CPU at the configured cost. 180 logins per second × 0.25 s = **45 CPU cores** of hashing. The API tier had 24 cores in total. The test never logged anyone in.
- **The load model.** When the server slowed down, the test's 500 virtual users simply waited, so the test *sent fewer requests*. It could never create a queue. Real parents kept arriving.

## What It Is

**Load testing** is generating traffic against a system to learn how it behaves under a given load: latency, errors, resource use, and where it breaks.

A load test answers a question only if its traffic resembles the traffic you care about. That description of the traffic is the **workload model**:

- which operations run, and in what proportions;
- which data they touch, and how skewed that is;
- how fast requests arrive, and whether arrivals depend on response times;
- what state the system is in (data volume, cache warmth);
- what users do between requests (think time, sessions, logins).

A test with the wrong workload model produces precise answers to a question nobody asked. This article is about building a workload model that resembles production. 22.5b covers the kinds of tests you run with it: stress, spike, soak, and finding the limit.

A distinction worth making early: **load testing isn't benchmarking.** A benchmark (22.1a) measures one piece of code in isolation. A load test measures the whole system, including queueing, contention, and every dependency, which are the things a benchmark leaves out.

## Recognizing the Problem

- Load tests that call one or two endpoints.
- Tests that reuse the same IDs, the same user, or the same search query.
- A load test that passed before an incident at a lower load than the test used.
- Test results that report requests per second achieved, with no record of what was intended.
- Tests using a fixed number of virtual users with no think time.
- Load generators whose own CPU isn't monitored.
- Staging data orders of magnitude smaller than production, or evenly distributed.
- Tests that always run against a warm cache.
- Third-party dependencies (payments, email) either called for real during tests, or stubbed with zero latency.

## How It Works

### Open and closed workload models

This is the most important idea in load testing, and the one most tools get wrong by default.

- **Closed model:** a fixed number of users. Each sends a request, waits for the response, optionally thinks, and sends the next. The rate of requests depends on how fast the system responds. If the system slows down, load drops.
- **Open model:** requests (or sessions) arrive at a rate that doesn't depend on the system. If the system slows down, requests pile up.

```
Closed: 500 users, server slows from 0.2 s to 2 s per request
  offered load:  2,500 req/s ─────────▶ 250 req/s      the test backs off by itself

Open: 900 arrivals per second, same slowdown
  offered load:  900 req/s ───────────▶ 900 req/s      the queue grows every second
  in progress:   180 ────────────────▶ 1,800 ─▶ 3,600 ─▶ ... ─▶ timeouts
```

Traffic from the public internet is mostly open: new visitors arrive regardless of how slow the site is for everyone else. Inside a session, a person behaves more like a closed model, because they wait for a page before clicking. The realistic combination is **sessions arriving at an open rate, each following a script with think times.**

A closed test can't reproduce the most important failure of an overloaded system, which is a queue that grows faster than it drains. Most tools default to closed models, because "number of virtual users" is easy to understand.

### Coordinated omission

A closed test also measures latency wrongly, in a specific way. Suppose the server stalls for 5 seconds once during a 60-second test at 1,000 requests per second:

- **What really happened (open):** about 5,000 requests arrived during the stall and waited an average of 2.5 seconds. That's 8% of all requests, so p95 is well over a second.
- **What a closed test with 100 users records:** only the 100 requests that were in flight during the stall. The users waited instead of sending more. 100 slow samples out of about 55,000 is 0.2%, so p95 and p99 look perfectly healthy.

The load generator "coordinated" with the server by not sending requests while it was slow, and so it omitted the requests that would have measured the stall. The name comes from Gil Tene, and the fix is an open model: send requests on schedule whether or not earlier ones have finished, and measure latency from when each request *should* have been sent.

### Building the workload model from production

When the system already has traffic, production tells you the model:

- **Operation mix:** count requests by route from access logs, for the peak hour, not the daily average.
- **Key distribution:** how often each school, tenant, product, or query is requested. Real distributions are skewed. A few keys get most of the traffic, and a long tail gets the rest. Cache hit rate, lock contention, and hot partitions all depend on that skew. A test that picks keys uniformly makes caches look worse and hot spots look better than reality; a test with one key does the reverse.
- **Session shape:** how many requests per session, how much time between them, and what share of sessions log in.
- **Payload sizes:** uploads, response sizes, and page sizes, which drive network, memory (22.1b), and serialization cost.
- **Tenant skew:** in a multi-tenant system, the largest tenants' requests are more expensive (22.3a). Include them.

For something new, like the enrolment launch, there's no production traffic. Estimate the model from comparable events, write down the assumptions, and **test a range** around each uncertain number. The login rate on launch day was the least certain number and the most expensive one, and it was the one the test left out.

### The system's state

- **Data volume and shape.** Load tests need production-sized, production-shaped data, for the reasons in 22.3a. Plans that only appear with skew and concurrency, sorts that spill to disk under concurrent load, and lock contention between writers only show up with realistic data and realistic concurrency together. Capture `pg_stat_statements` before and after each run, and run `auto_explain` during it (6.4b).
- **Cache warmth.** Test with a warm cache *and* a cold one. Production has cold caches after deploys, restarts, failovers, and at launch. Module 13.2b's **survivable hit rate**, the lowest hit rate the origin can serve at peak load, is found with a load test; 22.5b shows how.
- **Test data accumulates.** A test that creates 50,000 applications changes the data for the next test. Use dedicated test tenants and clean up, or restore a snapshot before each run.

### Reusing files you already have

Some realistic inputs already exist:

- **A search relevance judgment file** (12.4) is a list of real queries. Replayed as load, it exercises the search engine with realistic queries instead of `q=test`. Judgment files over-represent interesting or difficult queries, so weight each query by how often it appears in production logs.
- **Sampled production requests,** with personal data removed, can be replayed directly. That's the most realistic input, and it needs the same privacy handling as any copy of production data (Module 34).
- **Contract test fixtures and API examples** (21.1b) give valid request bodies without inventing them.

### The environment

- **Size.** A test against a staging environment at a quarter of production's size doesn't tell you what production can do. Scaling is rarely linear (22.5b explains why). Test against production-sized infrastructure, or in production itself with synthetic tenants and a way to stop quickly.
- **Third parties.** Don't load-test someone else's API. Payment providers' sandboxes have rate limits, and sending them thousands of requests may break their terms. Replace third-party calls with stubs that reproduce their *latency and error rates*, not stubs that answer instantly.
- **The load generator is part of the test.** If the generator is out of CPU or network capacity, it sends requests late and measures its own delays as server latency. Monitor its resources, run it close to (but not on) the system under test, and use several generators when one isn't enough. With an open-model executor, k6 reports `dropped_iterations` when it couldn't start requests on schedule; any nonzero value means the test didn't apply the load it claims.

### Reading the results

- **Record the intended rate next to the achieved rate.** If they differ, the test didn't test what it says.
- **Report percentiles per operation, not one number for everything.** A p95 across all endpoints mixes 5 ms health checks with 800 ms searches, and describes neither.
- **Separate failures from successes.** A server returning errors in 3 ms can make latency look better while it's failing. Latency percentiles should be for successful requests, and error rates reported alongside them.
- **Watch the system as well as the client.** The test tells you that p95 rose. CPU, pool wait, event-loop delay (22.2), GC (22.1b), and database load tell you why.

## When It's Appropriate

- Before a known traffic event: a launch, a sale, a deadline, a marketing campaign.
- Before changes that affect capacity: a new database, a new region, a framework upgrade, a caching change.
- When capacity planning is based on assumptions nobody has checked.
- To reproduce a production incident under controlled conditions.
- To take profiles (22.1) and capture query plans (22.3a) under realistic concurrency.

## When It's Unnecessary or Overkill

- **Systems whose load is far below their capacity** and grows slowly, where production metrics already show plenty of room. Watching production trends is cheaper.
- **A production-scale environment for a small internal tool.**
- **Replaying production traffic** when a simple, well-reasoned model of the top five operations would answer the question. Realism has diminishing returns, and the first few realistic features (mix, skew, logins, open arrivals) provide most of the value.
- **Load testing as a substitute for measuring production.** A load test is a model; production is the fact. Where production traffic exists, its metrics (Module 16, 19) come first.

## Trade-offs

- **Realism costs effort.** Every feature of the workload model has to be discovered, built, and kept current as the product changes. A load test that isn't maintained drifts into testing an application that no longer exists.
- **Production-sized environments cost money,** and production-shaped data carries compliance obligations (Module 34).
- **Testing in production is the most realistic option and the riskiest.** It needs synthetic tenants that are excluded from billing, analytics, and emails, a way to stop immediately, and agreement from whoever is on call.
- **Open-model tests can overwhelm the system and the generator.** That's the point, and it means tests need stop conditions.
- **Stubbed dependencies are a guess.** If the real payment provider slows down on launch day, the stub didn't test that (22.5b's failure scenarios cover some of this).
- **Load tests find problems late.** They run against a whole system, so by the time they show a problem, the design is often fixed. They complement, and don't replace, the per-change attention from 22.2 and 22.3a.

## Alternatives

- **Production metrics and capacity trends** (Modules 16 and 19). For steady growth, watching utilization and latency against traffic is enough.
- **Canary releases** (Module 30). A small share of real traffic to a new version tests performance with real workload, without a model, for changes that don't need peak load to reveal problems.
- **Shadow traffic.** Copying production requests to a new system and discarding its responses tests it with real traffic, for read paths. Writes are hard to shadow safely.
- **Queueing and capacity models.** Arithmetic from measured per-request costs, like the 45 cores of bcrypt, finds some problems with no test at all. The login problem was visible on paper.
- **Waiting rooms and admission control.** For a known spike, a queue in front of the site (Module 23) limits the load instead of trying to serve all of it.

## How to Achieve It

**Level 0 — smoke tests.** A few requests through the main flows, checking that nothing is broken, with the generator and the metrics working.
_Signal you're here:_ no load test exists.

**Level 1 — the main operations, with an open model.** Arrival-rate executors, the top operations in production proportions, per-operation percentiles, and the achieved rate recorded next to the intended one.
_Signal you need it:_ a coming traffic event, or a closed-model test that has passed before an incident.

**Level 2 — realistic data and keys.** Production-sized, production-shaped data; skewed key selection; real logins; payload sizes from production.
_Signal you need it:_ tests pass and production still has problems at similar load.

**Level 3 — realistic state and dependencies.** Cold-cache runs, stubs with realistic latency, query-plan capture during runs, and profiles under load.
_Signal you need it:_ incidents after deploys or restarts, or dependencies that fail under load.

**Level 4 — a workload model derived from production.** Generate the operation mix, key distribution, and session shape from recent logs, and refresh it on a schedule.
_Signal you need it:_ the product changes faster than anyone updates the test by hand.

**Level 5 — production-scale testing, possibly in production.** Synthetic tenants, stop conditions, and a rehearsal before every known event.
_Signal you need it:_ staging can't be made production-sized, and the stakes of a known event are high.

## Implementation

TypeScript with k6. k6 scripts are JavaScript-based, current k6 releases run TypeScript files directly (older ones needed a bundler), and its arrival-rate executors make the open model the explicit choice. That choice is what this article is about.

### An open model with a realistic mix

```ts
import http from "k6/http";
import { check, sleep } from "k6";
import { SharedArray } from "k6/data";
import type { Options } from "k6/options";

const BASE = __ENV.BASE_URL;

export const options: Options = {
  scenarios: {
    parents: {
      executor: "ramping-arrival-rate",  // open model: sessions start on schedule, whatever the latency
      timeUnit: "1s",
      startRate: 5,
      stages: [
        { target: 180, duration: "2m" },  // ramp to 180 new sessions per second
        { target: 180, duration: "15m" }, // × 5 requests per session ≈ 900 requests/s
      ],
      preAllocatedVUs: 2000,
      maxVUs: 8000,                       // enough VUs to hold slow sessions without falling behind
    },
  },
  thresholds: {
    "http_req_duration{op:search}": ["p(95)<800"],
    "http_req_duration{op:login}": ["p(95)<1500"],
    "http_req_duration{op:save}": ["p(95)<500"],
    http_req_failed: ["rate<0.01"],
    dropped_iterations: ["count<1"],     // the generator kept up, or this run proves nothing
  },
};
```

The rate is in *sessions*, not requests. Each session is a short script with think time, which gives the realistic combination: open arrivals, closed behavior within a session.

### Skewed keys and real queries

```ts
// Search queries from the relevance judgment file (12.4), each weighted by
// how often it appears in production logs. Loaded once and shared across VUs.
const queries = new SharedArray("queries", () =>
  JSON.parse(open("./data/search-queries.weighted.json")) as { q: string; weight: number }[],
);
const accounts = new SharedArray("accounts", () =>
  JSON.parse(open("./data/test-parents.json")) as { email: string; password: string }[],
);

// Zipf-like popularity: school rank r is chosen with weight 1 / r^s.
function zipfPicker(n: number, s: number): () => number {
  const cumulative: number[] = [];
  let total = 0;
  for (let rank = 1; rank <= n; rank++) {
    total += 1 / Math.pow(rank, s);
    cumulative.push(total);
  }
  return () => {
    const x = Math.random() * total;
    let lo = 0, hi = n - 1;
    while (lo < hi) {                       // binary search for the first cumulative ≥ x
      const mid = (lo + hi) >> 1;
      if (cumulative[mid] < x) lo = mid + 1; else hi = mid;
    }
    return lo;                              // index into the schools, most popular first
  };
}

const pickSchool = zipfPicker(2100, 1.1);   // exponent fitted to production logs, or estimated
const schoolIds: string[] = JSON.parse(open("./data/school-ids-by-popularity.json"));

// SharedArray supports indexing and length; compute the total once, at init.
let queryWeightTotal = 0;
for (let i = 0; i < queries.length; i++) queryWeightTotal += queries[i].weight;

function pickQuery(): string {
  let x = Math.random() * queryWeightTotal;
  for (let i = 0; i < queries.length; i++) {
    x -= queries[i].weight;
    if (x <= 0) return queries[i].q;
  }
  return queries[queries.length - 1].q;
}
```

### One session

```ts
export default function () {
  const account = accounts[Math.floor(Math.random() * accounts.length)];

  // A real login, with its real cost (the line the original test left out).
  const login = http.post(`${BASE}/api/login`, JSON.stringify(account), {
    headers: { "Content-Type": "application/json" },
    tags: { op: "login" },
  });
  if (!check(login, { "logged in": (r) => r.status === 200 })) return;
  const auth = { headers: { Authorization: `Bearer ${login.json("token")}` } };
  sleep(2 + Math.random() * 3);             // think time between pages

  // Two searches and one school page: the launch-day mix of 20% login, 40% search,
  // 20% school pages, 20% saves. Uploads run as a separate scenario (not shown).
  for (let i = 0; i < 2; i++) {
    const q = pickQuery();
    http.get(`${BASE}/api/schools?q=${encodeURIComponent(q)}`, { ...auth, tags: { op: "search" } });
    sleep(3 + Math.random() * 5);
  }

  const school = schoolIds[pickSchool()];
  http.get(`${BASE}/api/schools/${school}`, { ...auth, tags: { op: "school" } });
  sleep(5 + Math.random() * 10);

  const save = http.put(`${BASE}/api/applications/draft`, JSON.stringify(draftFor(account)), {
    headers: { ...auth.headers, "Content-Type": "application/json" },
    tags: { op: "save" },
  });
  check(save, { "saved": (r) => r.status === 200 });
}
```

> **Aside: count what this session costs before running it.** One login, two searches, one school page, and one save is 5 requests, with 13–36 seconds of think time (about 25 on average). At 180 sessions per second, that's about 900 requests per second, 180 of them logins, and about 180 × 25 = 4,500 sessions in progress at once, which is why `maxVUs` is 8,000. Doing this arithmetic before the test tells you what it will apply and whether the generator can apply it. The same arithmetic for logins alone (180/s × 250 ms of CPU = 45 cores) predicted the launch-day outage without running anything.

Run it with the generator's own resources visible:

```bash
k6 run --out experimental-prometheus-rw enrolment-launch.ts   # results next to the server metrics
```

Sending k6's metrics to the same place as the system's metrics (Module 19) lets one dashboard show offered load, achieved load, per-operation latency, and the resource that ran out.

## Further Reading

- **Gil Tene, "How NOT to Measure Latency"** (talk, several recorded versions). The origin of the term *coordinated omission*, and the clearest explanation of why most latency measurements under load are wrong.
- **Schroeder, Wierman, and Harchol-Balter, "Open Versus Closed: A Cautionary Tale"** (NSDI 2006). Shows that the same system gives very different results under open and closed models, and how to decide which one your traffic resembles.
- **The k6 documentation on executors** ("Open and closed models," `ramping-arrival-rate`, `dropped_iterations`) and on TypeScript support. Precise about what each executor does.
- **Google SRE book, "Handling Overload" and "Addressing Cascading Failures."** What a system should do when load exceeds capacity, which is what these tests reveal.
- **Brendan Gregg, _Systems Performance_,** on the USE method. The way to read system metrics during a test and find which resource ran out.
- **Module 12.4** for the relevance judgment file, **13.2b** for the survivable hit rate, **22.3a** for production-shaped data, and **Module 4.2** for why password hashing is deliberately expensive.

A **Java sibling** would be worth writing with Gatling, whose injection DSL separates open profiles (`injectOpen`) from closed ones (`injectClosed`) at the type level, so the model choice can't be made by accident. It would also cover Gatling's session-based feeders for realistic per-user data. Not yet written.

---

The habit to take away: **before trusting a load test, compare its traffic with production's, line by line.** The result can only be as realistic as the traffic.
