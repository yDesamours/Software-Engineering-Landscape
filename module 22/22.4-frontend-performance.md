# Frontend Performance: What Users' Devices Experience

_Module 22.4 — Frontend Performance_

## The Problem

A property-management SaaS serves landlords who manage anywhere from one flat to a few thousand units. Its web app, a React single-page application, runs Lighthouse in CI on each pull request, on a developer's laptop over office fiber. The score has been above 95 for a year.

Then churn interviews keep producing the same sentence: "the app is slow on my phone." The team adds real-user monitoring (RUM), which measures the page on customers' own devices, and gets numbers nobody had seen before, at the 75th percentile of mobile page loads:

| Metric | "Good" threshold | Lab (CI laptop) | Field (real phones) |
|---|---|---|---|
| Largest Contentful Paint (LCP) | ≤ 2.5 s | 0.9 s | **4.8 s** |
| Interaction to Next Paint (INP) | ≤ 200 ms | 60 ms | **620 ms** |
| Cumulative Layout Shift (CLS) | ≤ 0.1 | 0.02 | **0.27** |

Every number is fine in the lab and poor in the field. Three separate causes:

**Loading.** The app ships one JavaScript bundle: 2.1 MB uncompressed, 640 KB compressed. It includes a charting library used only on the Reports page, a date library with every locale, and a rich-text editor used only for messages. On a slow mobile connection (Lighthouse's mobile preset simulates about 1.6 Mbps), 640 KB takes about 3.2 seconds to download. A mid-range phone then parses and runs it several times more slowly than a laptop. The dashboard's largest element, a photo of the property, only exists once that JavaScript has run and the dashboard data has arrived. On top of that, a lint rule had added `loading="lazy"` to every image, so the browser deliberately delayed the most important one. The photo is a 2.4 MB JPEG displayed 400 pixels wide.

LCP broken into its parts, from RUM attribution data:

```
TTFB            ██████                                           600 ms
load delay      ███████████████████████████                    2,700 ms   waiting for JS + data + lazy
load duration   ███████████                                    1,100 ms   2.4 MB image
render delay    ████                                             400 ms
                                                              ─────────
                                                               4,800 ms
```

**Responsiveness.** The tenant list has a search box. Every keystroke filters 3,000 tenants and re-renders the whole list, synchronously. On a phone each keystroke takes about 450 ms, during which the page can't respond to anything, including the next keystroke.

**Stability.** A "rent due" banner is inserted above the content once an API call returns, pushing everything down. Images have no dimensions, so the layout jumps as each one loads. A web font swaps in late and changes line lengths.

The laptop hid all of this. It had a fast CPU, a fast network, a warm cache, and a developer who never typed quickly into a list of 3,000 tenants.

## What It Is

**Frontend performance** is how fast a page becomes useful, and stays responsive, *on the user's device.* Unlike server performance, most of the work happens on hardware you don't control and can't observe unless you measure it there.

Google's **Core Web Vitals** are the most widely used set of measurements, each assessed at the 75th percentile of page loads:

- **LCP (Largest Contentful Paint):** when the largest image or text block in the viewport was rendered. A proxy for "the main content has appeared."
- **INP (Interaction to Next Paint):** how long the page takes to visibly respond to clicks, taps, and key presses, reported for (roughly) the slowest interaction during the visit. It replaced First Input Delay in 2024.
- **CLS (Cumulative Layout Shift):** how much visible content moves unexpectedly while the page is in use.

One disambiguation matters more than the others: **lab data versus field data.**

- **Lab data** (Lighthouse, WebPageTest, DevTools) is one simulated visit under chosen conditions. It is repeatable and good for debugging.
- **Field data** (RUM, and Chrome's user experience report) is what real users experienced, on their devices, networks, and cache states. It is the only data that tells you whether you have a problem.

A good Lighthouse score is not a measurement of your users' experience. In the story above, it was a measurement of the team's laptops.

## Recognizing the Problem

- No field data at all, or field data much worse than lab data.
- p75 LCP above 2.5 s, INP above 200 ms, or CLS above 0.1 in field data, especially on mobile.
- JavaScript bundles measured in megabytes, or one bundle for the whole app.
- Libraries in the initial bundle that only one page uses.
- Typing or scrolling that feels sluggish on a phone and fine on a laptop.
- Content that jumps while loading, or users clicking the wrong thing because a button moved.
- Pages that stay blank until JavaScript runs.
- Long tasks (main-thread work over 50 ms) in performance recordings.
- Complaints that correlate with device type, country, or network.

## How It Works

### How a page loads

```
HTML ─▶ discover CSS/JS ─▶ download ─▶ parse/compile JS ─▶ run app ─▶ fetch data ─▶ render ─▶ LCP
 │           │                 │               │                          │            │
TTFB    what the HTML      bytes over      CPU on the                API latency   image download,
        references         the network     user's phone              (server side)  fonts, layout
```

In a single-page app, the main content usually waits for *every* step. Each step is its own optimization target, and RUM's LCP breakdown says which one to work on:

- **TTFB (time to first byte):** server and network latency for the HTML. Server-side work (22.1–22.3), CDNs, and caching (13.1) help.
- **Resource load delay:** the time between TTFB and the start of the LCP resource's download. This is usually the largest part in client-rendered apps, because the browser can't request an image until JavaScript has created the tag for it.
- **Resource load duration:** the size of the LCP resource and the network.
- **Element render delay:** anything that holds rendering after the resource arrives: main-thread work, fonts, or render-blocking CSS.

### The main thread

A browser tab runs JavaScript, style calculation, layout, and painting on one **main thread**. While a task runs, input waits. Any task over 50 ms is a **long task**.

INP measures an interaction in three parts:

```
tap ──▶ [ input delay ][ processing (your handlers) ][ presentation (render, paint) ] ──▶ next frame
        busy with       e.g. filtering 3,000 rows     re-rendering 3,000 rows
        other work
```

- **Input delay** is high when the thread was already busy (for example, still running the initial bundle).
- **Processing** is high when event handlers do too much work.
- **Presentation** is high when the update requires a lot of rendering.

Node's event loop from 22.2 is the same problem on a different machine: one thread, and any long synchronous job makes everything else wait.

### Variations: the families of fixes

**1. Ship less JavaScript.** JavaScript is the most expensive kind of byte, because it has to be downloaded, parsed, compiled, and executed on the main thread.

- **Code splitting by route:** each page's code loads when the user navigates there.
- **Code splitting by interaction:** the rich-text editor loads when the user clicks "Reply."
- **Remove what nobody uses:** bundle analyzers show which dependencies take the most space. Locale data, icon sets, and utility libraries are common offenders.
- **Target modern browsers** where your users allow it, so the bundle isn't full of polyfills.

**2. Load the right things first.**

- **Never lazy-load the LCP image.** Give it `fetchpriority="high"`, and make sure it's discoverable in the HTML, or preload it.
- **Lazy-load what's below the fold** (images, iframes, and heavy components).
- **Size images for their display size** with `srcset`, and use modern formats. The 2.4 MB JPEG became a 60 KB AVIF.
- **Load fonts deliberately:** preload the one or two that render above the fold, and use `font-display` so text isn't invisible while they load.

**3. Don't make the first view wait for JavaScript.** Server-side rendering (SSR), static generation, or streaming send meaningful HTML, so the main content can appear before the app has loaded. The cost is hydration: the browser still runs the JavaScript to make the page interactive, which can harm INP in the first seconds. Frameworks differ mostly in how they manage that cost.

**4. Keep the main thread free.**

- **Break up long tasks** and yield to the browser between chunks, so input can be handled.
- **Defer non-urgent updates:** update the input immediately and the filtered list afterward (React's `useDeferredValue` and `startTransition` do this).
- **Render only what's visible:** list virtualization renders the 20 rows on screen instead of 3,000.
- **Move computation off the main thread** to a Web Worker when it's large and doesn't need the DOM.
- **Load third-party scripts** (analytics, chat widgets, tag managers) after the page is interactive. They are often the largest source of main-thread work, and nobody on the team wrote them.

**5. Reserve space.** Give images and embeds `width` and `height` (or `aspect-ratio`), render placeholders with the final size for content that loads later, and insert banners into space that already exists, or below the viewport.

**6. Make repeat visits fast.** Put a content hash in each asset's filename and serve it with `Cache-Control: public, max-age=31536000, immutable`. A new release has new filenames, so the long cache can never serve stale code (13.1 covers HTTP caching). A **service worker** can go further, serving the app's shell from a local cache for near-instant repeat loads and offline support. The costs are real: a service worker is a proxy between your users and your site that you have to deploy, update, and occasionally debug on devices you can't access. A bug in it can keep serving an old version of the app until the worker updates.

**7. Budget and watch.** Set a size budget for the initial bundle and fail CI when it's exceeded. Lab checks catch regressions early; field data confirms whether users noticed.

## When It's Appropriate

- Any product used on phones, on slower networks, or by customers whose devices you don't choose.
- Public pages where search ranking and conversion depend on speed: marketing sites, sign-up flows, and public listings.
- When field data shows p75 above the thresholds, or a large gap between lab and field.
- Apps with large lists, dashboards, or editors, where interaction cost grows with the customer's data (22.2's question about n applies here too).
- When bundle size has grown release by release without anyone deciding it should.

## When It's Unnecessary or Overkill

- **Internal tools used on fast desktops** by a few people. Measure first; the numbers are often fine.
- **Chasing a perfect Lighthouse score.** Past the thresholds, lab score improvements rarely change what users experience. Field data at p75 is the goal.
- **SSR for an app behind a login** whose users open it once and keep it open all day. Load time matters less than responsiveness there, and SSR adds a server tier to operate.
- **A service worker for an app without an offline or repeat-load problem.** HTTP caching with hashed filenames gets most of the benefit with none of the update risk.
- **Micro-optimizing render code** before removing the megabyte of JavaScript nobody uses.

## Trade-offs

- **Code splitting adds network requests** and a loading state at each split point. Split too finely and navigation feels slower; split too coarsely and the initial load stays heavy.
- **Lazy loading moves the wait.** Content that loads on scroll or on click can appear late if the user gets there quickly.
- **SSR adds a server, a second rendering environment, and hydration costs.** Bugs that only appear when server and client render differently are hard to find.
- **Deferring updates shows stale content briefly.** The filtered list lags one keystroke behind; that's usually right, but it's a design decision.
- **Virtualization breaks things users expect,** such as the browser's find-in-page for rows that aren't rendered, and it needs care for accessibility (Module 34).
- **Service workers add a caching layer you control poorly** once it's on users' devices.
- **RUM costs something:** a script on every page, data collection with privacy implications (Module 34), and a pipeline to store and query it (Module 16).
- **Image pipelines** (resizing, format conversion) are infrastructure: a build step, or a service or CDN feature (Module 11).

## Alternatives

- **Server-rendered HTML with little JavaScript.** Traditional server-rendered pages, possibly with small interactive islands, avoid most of this article's problems. For content-heavy products, this is often the simplest high-performing design.
- **Native mobile apps.** They avoid downloading the app on every visit, and they cost a separate codebase per platform (Module 42).
- **CDNs and edge rendering.** They reduce TTFB, and don't help with main-thread work.
- **Synthetic monitoring** (scheduled lab tests from several locations). It catches regressions consistently, but it isn't a substitute for field data.
- **Buying a faster server.** This helps TTFB only. It does nothing for a phone's CPU.

## How to Achieve It

**Level 0 — measure in the field.** Collect Core Web Vitals from real users, segmented by device type and page.
_Signal you're here:_ the only performance number is a Lighthouse score.

**Level 1 — fix the LCP element and the largest dependencies.** Remove lazy loading from the LCP image, size and compress it, split the bundle by route, and remove unused libraries.
_Signal you need it:_ p75 LCP above 2.5 s, or an initial bundle over a few hundred kilobytes compressed.

**Level 2 — reserve space and fix the worst interactions.** Add dimensions to media, find the slowest interactions using RUM attribution, and defer, virtualize, or yield in those handlers.
_Signal you need it:_ CLS above 0.1, or INP above 200 ms.

**Level 3 — budgets in CI.** Set initial-bundle size budgets and lab checks that fail pull requests on regressions.
_Signal you need it:_ improvements that erode over the following releases.

**Level 4 — render the first view without waiting for the app.** Use SSR, static generation, or streaming for the pages where load time matters most, and manage hydration cost.
_Signal you need it:_ LCP dominated by resource load delay even after the bundle is small.

**Level 5 — repeat-visit and offline performance.** Add a service worker, with a tested update path, where the product needs it.
_Signal you need it:_ users on unreliable networks, or a product people open many times a day on mobile.

## Implementation

TypeScript with React, because the browser runs JavaScript, and because most of the problems in this article come from how single-page app frameworks are used.

### Measuring what users experience

```ts
import { onCLS, onINP, onLCP, type Metric } from "web-vitals/attribution";

// Field names follow web-vitals v4's attribution build; check the changelog for your version.
function report(metric: Metric & { attribution?: Record<string, unknown> }) {
  const a = metric.attribution ?? {};
  const body = JSON.stringify({
    name: metric.name,                 // "LCP" | "INP" | "CLS"
    value: metric.value,
    rating: metric.rating,             // "good" | "needs-improvement" | "poor"
    page: location.pathname.replace(/\/\d+/g, "/:id"),   // keep cardinality bounded (16.3)
    device: navigator.maxTouchPoints > 0 ? "touch" : "desktop",
    // Which part to fix:
    ttfb: a.timeToFirstByte,
    loadDelay: a.resourceLoadDelay,
    loadDuration: a.resourceLoadDuration,
    renderDelay: a.elementRenderDelay,
    inputDelay: a.inputDelay,
    processing: a.processingDuration,
    presentation: a.presentationDelay,
    target: a.interactionTarget ?? a.largestShiftTarget,  // a CSS selector
  });
  // sendBeacon survives the page being closed, which is when these are often reported.
  navigator.sendBeacon("/rum", new Blob([body], { type: "application/json" }));
}

onLCP(report);
onINP(report);
onCLS(report);
```

The attribution fields turn "LCP is 4.8 s" into "resource load delay is 2.7 s," which is the difference between a metric and a task.

### Loading less, and the right things first

```tsx
import { lazy, Suspense, useDeferredValue, useMemo, useState } from "react";

// Route-level splitting: the chart library is only downloaded on /reports.
const ReportsPage = lazy(() => import("./routes/ReportsPage"));

// Interaction-level splitting: the editor loads when someone clicks Reply.
async function openReplyEditor(container: HTMLElement) {
  const { mountEditor } = await import("./editor/mountEditor");
  mountEditor(container);
}

function PropertyHero({ photo }: { photo: ResponsivePhoto }) {
  return (
    <img
      src={photo.url(800)}
      srcSet={`${photo.url(400)} 400w, ${photo.url(800)} 800w, ${photo.url(1200)} 1200w`}
      sizes="(max-width: 600px) 100vw, 400px"
      width={400}
      height={267}               // reserves space: no layout shift when it arrives
      fetchPriority="high"       // the LCP element: ask for it early (React 19; older versions
                                 // need the lowercase `fetchpriority` attribute)
      // no loading="lazy" here, ever
      alt={photo.alt}
    />
  );
}
```

> **Aside: blanket rules hurt here.** The lint rule that added `loading="lazy"` to every image was a good rule for 95% of images and the worst possible rule for the one that mattered. The same pattern shows up with "preload everything," which makes every resource high priority, which means none of them is. Priorities only work if few things have them.

### Keeping typing responsive

```tsx
function TenantSearch({ tenants }: { tenants: Tenant[] }) {
  const [query, setQuery] = useState("");
  // The input updates immediately; the list re-renders when the browser has time.
  const deferredQuery = useDeferredValue(query);

  const matches = useMemo(() => {
    const q = deferredQuery.trim().toLowerCase();
    return q ? tenants.filter((t) => t.searchKey.includes(q)) : tenants;  // searchKey precomputed
  }, [tenants, deferredQuery]);

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      {/* Renders only the rows in view, not all 3,000. */}
      <VirtualList items={matches} rowHeight={56} renderRow={(t) => <TenantRow tenant={t} />} />
    </>
  );
}
```

For work outside React's scheduling, the general tool is to yield between chunks:

```ts
// scheduler.yield() is available in Chromium-based browsers; fall back elsewhere.
function yieldToMain(): Promise<void> {
  const s = (globalThis as { scheduler?: { yield?: () => Promise<void> } }).scheduler;
  return s?.yield ? s.yield() : new Promise((resolve) => setTimeout(resolve, 0));
}

async function importRows(rows: RawRow[], apply: (r: RawRow) => void) {
  let lastYield = performance.now();
  for (const row of rows) {
    apply(row);
    if (performance.now() - lastYield > 40) {   // stay under the 50 ms long-task mark
      await yieldToMain();
      lastYield = performance.now();
    }
  }
}
```

After these changes, the team's field numbers at p75 on mobile were: LCP 2.1 s, INP 140 ms, CLS 0.03. The lab score barely moved, because it had been measuring a laptop all along.

## Further Reading

- **web.dev's articles on LCP, INP, and CLS**, including "Optimize LCP" (the four subparts), "Optimize INP," and "Optimize long tasks." These define the metrics and are kept current as the metrics change.
- **The `web-vitals` library README**, especially the attribution build. It documents exactly which fields are available and what they mean for your version.
- **Ilya Grigorik, _High Performance Browser Networking_** (free online). How TCP, TLS, and HTTP/2 affect load time, which explains why round trips matter more than bandwidth on mobile.
- **Addy Osmani, "The Cost of JavaScript"** (and its later updates). Why JavaScript bytes cost more than image bytes of the same size, measured on real phones.
- **The MDN pages on `fetchpriority`, `loading`, responsive images, and service workers.** Accurate references for the browser features used above.
- **Jake Archibald's "The Offline Cookbook."** Service worker caching strategies, and what each one costs.
- **Module 13.1** for HTTP caching, **Module 11** for image processing, **Module 16** for storing RUM data, and **Module 34** for accessibility and privacy constraints on the techniques here.

No sibling in another language is proposed, since the browser runs JavaScript.
