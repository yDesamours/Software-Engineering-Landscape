# Query Plans at Production Volume

_Module 22.3a — Database Optimization_

## The Problem

A project-management SaaS stores tasks in one PostgreSQL table shared by all tenants. A new "My open tasks" widget adds this query:

```sql
SELECT id, title, status, updated_at
  FROM tasks
 WHERE tenant_id = $1 AND status = 'open'
 ORDER BY updated_at DESC
 LIMIT 50;
```

The table already has indexes on `(tenant_id)` and on `(updated_at)`.

In staging, `tasks` has 20,000 rows spread evenly across 10 tenants. The query takes 4 ms, the integration tests pass, and the change ships.

Production looks different:

| | Staging | Production |
|---|---|---|
| Rows in `tasks` | 20,000 | 180 million |
| Tenants | 10, equal size | 26,000 |
| Largest tenant | 2,000 rows | 41 million rows (23% of the table) |
| Median tenant | 2,000 rows | about 900 rows |
| Share of tasks that are open | 50% (random seed data) | 8% overall; 0.05% for the largest tenant |
| Fits in memory | Entirely | About 15% of the table |

For most tenants the widget is fast. For the largest tenant, a construction firm with years of closed tasks, it takes **14 seconds**. The firm's users open the dashboard all day, so those queries hold connections and push pool wait up for every other tenant on the same database.

The plan for that tenant:

```
Limit  (actual time=14212..14230 rows=50 loops=1)
  Buffers: shared hit=1204331 read=2873102
  ->  Index Scan Backward using tasks_updated_at_idx on tasks
        (cost=0.57..8467310 rows=3312040) (actual rows=50 loops=1)
        Filter: ((tenant_id = 1) AND (status = 'open'))
        Rows Removed by Filter: 38911207
Execution Time: 14231 ms
```

The planner reasoned like this: "About 3.3 million rows match. If I walk the `updated_at` index from newest to oldest, I'll find 50 matches within the first few thousand entries, and I won't need to sort." That reasoning assumes two things that are false for this tenant:

- **Its tenant and status are independent.** The planner estimated 23% × 8% of the table. The real number of matching rows is 20,500, about 160 times fewer.
- **The matches are spread evenly through time.** This tenant's open tasks are an old backlog, so the newest matches are months deep in the index.

The backward scan read 39 million index entries, mostly from other tenants, to find 50 rows. 2.9 million of the pages it needed weren't in memory.

None of this was visible in staging. Staging had the right query and the wrong data. **A query plan is a function of the data's shape, not just the SQL**, and staging had a different shape in every dimension that mattered.

## What It Is

PostgreSQL, like most relational databases, has a **cost-based planner.** For each query it considers several ways to execute it, estimates how many rows each step will produce using stored **statistics** about the data, converts those estimates into costs, and runs the cheapest plan.

Three consequences follow, and the rest of this article builds on them:

1. **The same query gets different plans as the data changes.** A sequential scan is correct for 20,000 rows and disastrous for 180 million.
2. **The plan is only as good as the row estimates.** When estimates are far off, the planner picks a plan that would have been right for the data it imagined.
3. **Testing query performance means testing against data with production's shape**: size, distribution, correlation, and physical layout, not just production's schema.

Module 6.4b covered *finding* the slow query and reading its plan once it's slow. This article is about why plans change with data, how to see the change before it ships, and how index design and statistics fix it.

## Recognizing the Problem

- A query that's fast in staging and slow in production, or fast for most tenants and slow for a few.
- A large gap between estimated and actual rows in `EXPLAIN ANALYZE`, such as `rows=3312040` estimated against 20,500 real.
- `Rows Removed by Filter` in the millions for a query that returns a handful of rows.
- A query that becomes slow after roughly its sixth execution in a session (see generic plans below).
- Plans that change after `ANALYZE`, after a bulk import, or with no deploy at all.
- A query that's fast the second time you run it (a cold cache the first time).
- Latency that's fine in a single-user test and bad under concurrency.
- Indexes that exist and aren't used, or are used in a way you didn't expect.

## How It Works

### What the planner knows

For each column, `ANALYZE` samples the table and stores, among other things:

- **`n_distinct`:** how many distinct values the column has.
- **Most common values (MCV) and their frequencies:** by default up to 100 values. With 26,000 tenants, only the largest 100 get their own entry. All the others are estimated from what's left over.
- **A histogram** of the remaining values.
- **Correlation:** how closely the column's order matches the table's physical order, which affects the cost of index scans.

For a single column, this is usually good enough. Estimates break down in three predictable places:

- **Columns that depend on each other.** By default, the planner multiplies selectivities as if columns were independent. `tenant_id = 1 AND status = 'open'` is estimated as P(tenant 1) × P(open). **Extended statistics** (`CREATE STATISTICS`) record combined frequencies for chosen column groups.
- **Skewed values outside the MCV list.** A mid-sized tenant that isn't in the top 100 is estimated as an average one.
- **Stale statistics.** Autovacuum re-analyzes a table after about 10% of its rows change, by default. On a 180-million-row table, that is 18 million changes. A new tenant can import 5 million tasks and be invisible to the planner for days. Large tables need a lower per-table threshold.

### Plan choices matter only at scale

Each strategy's cost grows differently with the number of rows. Roughly, for this query:

```
strategy                              staging (20k rows)    production, largest tenant
------------------------------------  ------------------    --------------------------
seq scan, then sort                        ~4 ms                 minutes
index on (tenant_id), then sort            ~2 ms                 tens of seconds
index on (updated_at), walked backward     ~1 ms                 14 s
index on (tenant_id, status, updated_at)   <1 ms                 <1 ms
```

At staging's size, every strategy takes milliseconds, so the planner's choice makes no visible difference and tests can't tell good from bad. The differences only appear at production size. That's why "it was fast in staging" says almost nothing about a query.

### Generic and custom plans

Most drivers use **prepared statements**, which lets the database reuse plans. PostgreSQL plans the first five executions of a prepared statement with the actual parameter values (**custom plans**). After that, it may switch to a single **generic plan** made without knowing the parameters, if that plan's estimated cost isn't worse than the average of the custom plans.

A generic plan is planned for the *average* tenant: 180 million rows ÷ 26,000 tenants, about 6,900 rows. It uses the `(tenant_id)` index and sorts, which is fine for the median tenant. For the largest tenant, it fetches 41 million rows and sorts them.

So a skewed table gives you two ways to get a bad plan: a custom plan built on wrong estimates, or a generic plan built on an average that describes nobody. Both can be tested for (see Implementation). The setting `plan_cache_mode` can force custom planning when a query's best plan depends on its parameters.

### The index that removes the choice

The plan above was bad because no index let the database find exactly the rows the query wanted in the order it wanted them. An index on `(tenant_id, status, updated_at DESC)` does. The database seeks to the entries for tenant 1 with status `open`, reads the first 50 in `updated_at` order, and stops. No filtering, no sort, and 50 entries read instead of 39 million. The row estimates stop mattering much, because every reasonable estimate leads to the same plan.

The rules for multi-column indexes:

- **Equality columns first** (`tenant_id`, `status`), then **the range or sort column** (`updated_at`). An index on `(updated_at, tenant_id)` can't seek to one tenant.
- **Match the sort direction** used by the query, when multiple columns are sorted in different directions.
- **Partial indexes** cover only the rows a query can match: `WHERE status = 'open'` makes the index a tiny fraction of the table's size, as long as the queries always include that condition.
- **Covering indexes** (`INCLUDE (title)`) let the database answer from the index alone (an index-only scan), as long as vacuum keeps the visibility map current.
- **Leading-column overlap.** An index on `(tenant_id, status, updated_at)` also serves queries on `tenant_id` alone, which makes the old `(tenant_id)` index a candidate for removal.

Each index costs something on every write. It must be updated on insert, and on updates to its columns. An index on a column that's updated often, such as `updated_at`, also prevents PostgreSQL's cheaper "HOT" updates for those rows. Indexes that are never used cost writes, disk, and cache memory, and should be dropped.

### What else changes in production

Even with the right plan, production conditions differ from a single test query in ways that affect its speed:

- **Cache state.** `Buffers: shared hit` counts pages found in memory; `read` counts pages read from disk. A query that's fast on its second run was probably slow on its first. Production for a rarely active tenant is often the first run.
- **Memory per operation, times concurrency.** `work_mem` is a limit *per sort or hash operation, per query*. A sort that fits in memory alone can spill to disk when 200 queries run it at once and the planner's estimates are off. `log_temp_files` shows when this happens.
- **JIT compilation.** PostgreSQL compiles expressions for queries it expects to be expensive. With a bad estimate, a query that takes 5 ms can spend 80 ms compiling. If `EXPLAIN ANALYZE` shows a `JIT:` section on a fast query, the estimate is off.
- **Locks and contention**, which a single-user test never produces (22.5).

## When It's Appropriate

- Tables large enough that plan choice matters: millions of rows, or any table where a sequential scan doesn't fit in memory.
- Multi-tenant tables, or any data with heavy skew (one customer, one region, one status dominating).
- Before shipping queries against large tables, especially queries with `ORDER BY ... LIMIT`, which are the most sensitive to wrong estimates.
- After bulk imports, large deletes, or changes to how data is distributed.
- When 6.4b's workload view shows a query whose mean is fine and whose maximum is terrible. That pattern usually means the plan or the cost depends on the parameter.

## When It's Unnecessary or Overkill

- **Small tables.** For tables of a few thousand rows that fit in memory, every plan is fast. A production-shaped test environment for them is wasted effort.
- **An index for every query.** A new query that shares an index prefix with an existing index usually doesn't need its own.
- **Hints and forced plans** as a first response. They fix today's data and break when it changes again.
- **A full production copy for plan testing** when a replica or a synthetic data set with realistic skew answers the same question at a fraction of the cost and compliance burden.
- **Raising statistics targets everywhere.** It makes `ANALYZE` and planning slower for every query. Raise it for the specific columns whose estimates are wrong.

## Trade-offs

- **Every index slows writes and uses memory.** A table with twelve indexes pays twelve index updates per insert. Composite indexes can replace several single-column ones, but they're larger.
- **Building indexes on large tables takes time and resources.** `CREATE INDEX CONCURRENTLY` avoids blocking writes, but it takes longer, can fail and leave an invalid index behind, and can't run inside a transaction (6.3).
- **Extended statistics and higher statistics targets** make `ANALYZE` slower and give the planner more to consider.
- **Forcing custom plans** (`plan_cache_mode = force_custom_plan`) spends planning time on every execution. It's worth it for queries whose best plan depends on the parameter, and a waste for simple lookups.
- **Production-shaped test data is a project.** A masked copy of production is a compliance object (Module 34). Synthetic data only helps if it copies the skew and correlation that matter, and deciding what matters requires knowing production.
- **Plan regression tests can be brittle.** Assert on the things that matter (no sequential scan on large tables, no sort of millions of rows), not on the exact plan, which can change for harmless reasons.

## Alternatives

- **`auto_explain` in production** (6.4b). Logs the plans of slow queries as they happen. It's the backstop for everything this article tries to catch earlier.
- **Query hints** (`pg_hint_plan` for PostgreSQL). Useful in an emergency, and a maintenance burden if left in place.
- **Isolating the largest tenants.** Moving them to their own partitions, schemas, or databases (Module 5) removes the skew from everyone else's plans. It's a real option when a few tenants are a large share of the data.
- **Partitioning** (6.2c). Partitioning by tenant or time lets the planner skip irrelevant partitions and keeps each partition's statistics closer to its own data.
- **Precomputing the result.** A counter or materialized list for "open tasks" (6.2a) avoids the query entirely, at the cost of keeping it current.
- **Archiving old data** (6.2). The largest tenant's 41 million rows are mostly closed tasks from years ago that nobody queries.

## How to Achieve It

**Level 0 — capture production plans.** Enable `pg_stat_statements` and `auto_explain` (6.4b), so slow plans are recorded when they happen.
_Signal you're here:_ you learn about slow queries from customers.

**Level 1 — design indexes for the query, equality columns first.** Review new queries on large tables against the indexes that exist, and check `EXPLAIN` on a replica with production data before shipping.
_Signal you need it:_ a query that's slow only in production.

**Level 2 — fix the statistics.** Lower autovacuum's analyze threshold on large tables, raise statistics targets on skewed columns, add extended statistics for correlated columns, and run `ANALYZE` after bulk loads.
_Signal you need it:_ large gaps between estimated and actual rows.

**Level 3 — test with representative parameters, including generic plans.** For each important query, test the smallest, median, and largest tenant, and test the generic plan too.
_Signal you need it:_ queries that are fast for most tenants and slow for a few, or slow after several executions.

**Level 4 — plan regression checks in CI** against a data set with production's shape, whether masked or synthetic with realistic skew.
_Signal you need it:_ the second time a plan problem reaches production through a normal release.

**Level 5 — maintain indexes deliberately.** Review unused and duplicate indexes regularly, and measure the write side of index changes.
_Signal you need it:_ write latency rising, or index size approaching table size.

## Implementation

SQL for PostgreSQL. Every step here is something you run against the database itself, so no application language would add anything.

### Making staging look like production

Uniform random data hides exactly the problems that matter. This generates the skew and correlation from the story:

```sql
-- power(random(), 6) concentrates values near 0: tenant 1 gets about 18% of rows,
-- and most of the 26,000 tenants get very few.
INSERT INTO tasks (tenant_id, status, updated_at, title)
SELECT t.tenant_id,
       CASE WHEN random() < (CASE WHEN t.tenant_id = 1 THEN 0.0005 ELSE 0.08 END)
            THEN 'open' ELSE 'done' END,
       -- the largest tenant's tasks are older, like its real backlog
       now() - (CASE WHEN t.tenant_id = 1 THEN 900 ELSE 60 END) * random() * interval '1 day',
       'task ' || g
  FROM generate_series(1, 20000000) AS g
 CROSS JOIN LATERAL (
       SELECT 1 + floor(26000 * power(random(), 6))::int AS tenant_id
       WHERE g IS NOT NULL   -- makes the subquery reference g, so random() runs per row
 ) AS t;

ANALYZE tasks;
```

> **Aside: what matters is the shape, not the size.** Twenty million rows with production's skew and correlation reproduce the bad plan. Two hundred million uniform rows don't. Compare the distribution of your synthetic data with production using `pg_stats` on both, and copy what's different.

### Looking at what the planner believes

```sql
SELECT attname, n_distinct, most_common_vals, most_common_freqs, correlation
  FROM pg_stats
 WHERE tablename = 'tasks' AND attname IN ('tenant_id', 'status');
```

### Testing both kinds of plan

```sql
-- Custom plan for the largest tenant. BUFFERS shows how much was read from disk
-- (newer PostgreSQL versions include it automatically with ANALYZE).
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title, status, updated_at FROM tasks
 WHERE tenant_id = 1 AND status = 'open'
 ORDER BY updated_at DESC LIMIT 50;

-- The generic plan, which applications using prepared statements can get
-- after a few executions (PostgreSQL 16+).
EXPLAIN (GENERIC_PLAN)
SELECT id, title, status, updated_at FROM tasks
 WHERE tenant_id = $1 AND status = 'open'
 ORDER BY updated_at DESC LIMIT 50;
```

Run the first query for the smallest, median, and largest tenant, not one "typical" tenant.

> **Aside: `EXPLAIN ANALYZE` runs the statement.** For a `SELECT` on a replica, that's what you want. For an `UPDATE` or `DELETE`, it modifies data. Wrap those in `BEGIN; ... ROLLBACK;`, and never run them on a primary casually.

### The fix

```sql
-- Equality columns first, then the sort column in the query's direction.
-- Partial: the widget only ever asks for open tasks.
CREATE INDEX CONCURRENTLY tasks_tenant_open_updated_idx
    ON tasks (tenant_id, updated_at DESC)
    INCLUDE (title)
    WHERE status = 'open';

-- Better estimates for the correlated pair, which other queries also need.
CREATE STATISTICS tasks_tenant_status (mcv) ON tenant_id, status FROM tasks;

-- Re-analyze after about 1% of rows change, instead of 10% (18 million).
ALTER TABLE tasks SET (autovacuum_analyze_scale_factor = 0.01);
ALTER TABLE tasks ALTER COLUMN tenant_id SET STATISTICS 1000;

ANALYZE tasks;
```

`status` doesn't need to be an index column because the index only contains open tasks, and `INCLUDE (title)` allows an index-only scan when the visibility map is current. After the change:

```
Limit  (actual time=0.041..0.188 rows=50 loops=1)
  Buffers: shared hit=54
  ->  Index Only Scan using tasks_tenant_open_updated_idx on tasks
        (actual rows=50 loops=1)
        Index Cond: (tenant_id = 1)
        Heap Fetches: 3
Execution Time: 0.214 ms
```

From 14 seconds to under a millisecond, and the same plan for every tenant, whether custom or generic.

### A plan regression check for CI

Run this against the production-shaped data set for each important query and each representative parameter. It checks for the things that matter, not the whole plan:

```sql
CREATE OR REPLACE FUNCTION assert_plan_ok(query text, max_cost numeric)
RETURNS void LANGUAGE plpgsql AS $$
DECLARE
  plan jsonb;
BEGIN
  EXECUTE 'EXPLAIN (FORMAT JSON) ' || query INTO plan;

  IF jsonb_path_exists(plan,
       '$.** ? (@."Node Type" == "Seq Scan" && @."Relation Name" == "tasks")') THEN
    RAISE EXCEPTION 'sequential scan on tasks: %', query;
  END IF;

  IF (plan -> 0 -> 'Plan' ->> 'Total Cost')::numeric > max_cost THEN
    RAISE EXCEPTION 'estimated cost % exceeds % for: %',
      plan -> 0 -> 'Plan' ->> 'Total Cost', max_cost, query;
  END IF;
END $$;

SELECT assert_plan_ok($q$SELECT id FROM tasks WHERE tenant_id = 1     AND status = 'open'
                         ORDER BY updated_at DESC LIMIT 50$q$, 1000);
SELECT assert_plan_ok($q$SELECT id FROM tasks WHERE tenant_id = 18422 AND status = 'open'
                         ORDER BY updated_at DESC LIMIT 50$q$, 1000);
```

The cost threshold is a rough guard, not a measurement. Costs are in the planner's arbitrary units, so pick the threshold by looking at known-good plans.

### Finding indexes that cost without helping

```sql
SELECT s.relname AS table_name, s.indexrelname AS index_name,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS size, s.idx_scan
  FROM pg_stat_user_indexes s
  JOIN pg_index i ON i.indexrelid = s.indexrelid
 WHERE s.idx_scan = 0
   AND NOT i.indisunique          -- unique indexes enforce constraints even if never scanned
 ORDER BY pg_relation_size(s.indexrelid) DESC;
```

Check these counters on every server, including replicas, before dropping anything. Each server keeps its own counts, and an index unused on the primary may serve every query on a replica.

## Further Reading

- **The PostgreSQL documentation: "Using EXPLAIN," "Statistics Used by the Planner," "Extended Statistics," and the `plan_cache_mode` and `PREPARE` references.** The chapter on planner statistics explains exactly how estimates are computed, including why independent columns multiply.
- **Markus Winand, _SQL Performance Explained_** (and use-the-index-luke.com). The best explanation of multi-column index ordering and why equality columns come first. It covers several databases, not just PostgreSQL.
- **Leis et al., "How Good Are Query Optimizers, Really?"** (VLDB 2015). A measurement of how far cardinality estimates are off in real systems, and how much that matters compared to cost models.
- **The `auto_explain` and `pg_hint_plan` documentation**, for recording plans in production and, in emergencies, overriding them.
- **The PostgreSQL 18 release notes**, which added functions for exporting and importing planner statistics. That makes it possible to experiment with production's statistics on a much smaller database; check the documentation for what it can and can't reproduce.
- **Module 6.4b** for finding the slow query and reading plans, **6.2b** for index fundamentals, **Module 5** for isolating large tenants, and **22.5** for testing plans under concurrency.

A **Go sibling** would be worth writing, because the generic-plan problem depends on the driver. `pgx` prepares and caches statements by default, so a Go service can hit generic plans that a service using a different driver or mode never sees. The sibling would show how to choose the query execution mode per query and how to test for it. Not yet written.
