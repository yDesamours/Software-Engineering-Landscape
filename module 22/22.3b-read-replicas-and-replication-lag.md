# Read Replicas and Replication Lag

_Module 22.3b — Database Optimization_

## The Problem

A job board runs on Spring Boot and one PostgreSQL primary. At peak hours the database runs at 85% CPU. `pg_stat_statements` shows that 92% of statements are reads: search results, job pages, and employers' dashboards. The team adds a read replica and routes every `@Transactional(readOnly = true)` method to it. The change is a small configuration class.

What followed, over five weeks:

**Week 1: nothing changed.** The replica sat at 2% CPU and the primary stayed at 85%. Every query still went to the primary. The routing code read the transaction's read-only flag correctly, but it read it *before Spring had set it*. The cause is covered in the Implementation section.

**Week 2: the routing worked.** Primary CPU fell to 45% and the replica ran at 48%. Then the support tickets started: "I published a job and it's not in my list." An employer clicks Publish, the write commits on the primary, the browser follows a redirect to "My postings" about 30 ms later, and that read goes to the replica. Replication lag was normally 20–80 ms, so the new job was often not there yet.

**Week 3: duplicate applications.** A candidate double-clicked Apply. The service checked "has this candidate already applied?" in a read-only method, which went to the replica. Neither request saw the other's insert, and both inserted. The table had no unique constraint, because the check was supposed to prevent duplicates.

**Week 4: lag of 40 seconds.** A nightly job expires about 3 million old listings in one `UPDATE`. The primary produced write-ahead log faster than the replica could replay it, and lag climbed to 40 seconds. For those minutes, employers editing jobs saw old versions after saving, and some saved again on top of their own changes.

**Week 5: cancelled reports.** A monthly analytics query that runs for several minutes on the replica started failing with `canceling statement due to conflict with recovery`. Vacuum on the primary had removed row versions the query was still reading, and after 30 seconds the replica cancelled the query so that replay could continue.

The replica did its job, which was to take read load off the primary. What the team hadn't planned for was that **a replica is a copy of the database as it was a short, variable time ago**, and part of the application assumed it was reading the present.

## What It Is

A **read replica** is a copy of the primary database that receives a continuous stream of the primary's changes and serves read-only queries. In PostgreSQL, the stream is the write-ahead log (WAL): the primary writes each change to the WAL, sends it to the replicas, and each replica replays it.

By default, replication is **asynchronous**. The primary confirms a commit to the application without waiting for any replica. The time between a commit on the primary and its replay on a replica is **replication lag**. It is usually milliseconds and has no upper limit.

Two neighbors are often confused with replicas:

- **Replicas aren't backups.** A `DELETE` without a `WHERE` clause replicates in milliseconds. Backups and point-in-time recovery are Module 24's subject.
- **Replicas don't scale writes.** Every write still goes to the one primary. Scaling writes means sharding (Module 38) or a different database design.

Replicas also serve as failover targets for high availability (Module 24). This article is about the other use: moving read load off the primary.

## Recognizing the Problem

Signs you need a replica:

- Database CPU or I/O is the constraint, and most of the load comes from reads.
- Long-running reports or analytics queries slow down transactional traffic.
- Queries are already well indexed (22.3a) and caching doesn't fit (Module 13).

Signs a replica is causing problems:

- "I saved it and it's not there" reports that nobody can reproduce.
- Items that appear, disappear on refresh, and reappear.
- Duplicate records where the code checks before inserting.
- Problems that cluster around batch jobs, migrations, or bulk imports.
- Queries on the replica cancelled with "conflict with recovery."
- A replica with low load despite routing that should send it traffic.

## How It Works

### What lag looks like to a user

```
time ──────────────────────────────────────────────────────────────▶

primary   [ INSERT job 812 ][ COMMIT ]
                                  │   WAL shipped and replayed ...
replica                           │ ─────────────────────▶ [ job 812 visible ]
                                  │
browser               POST /jobs ─┘── 302 ──▶ GET /my-jobs ─▶ replica: no job 812
                                              (30 ms later)
```

Lag has several sources: the network between the servers, replay speed (PostgreSQL replays WAL in a single process, so one busy replica can fall behind a primary with many cores), bursts of WAL from bulk writes, and replay paused by conflicting queries on the replica (below). Most of the time these add up to milliseconds. Occasionally they add up to minutes, and the occasional case is the one to design for.

### The guarantees a replica removes

With one database, every read sees every committed write. With replicas, three guarantees disappear unless you add them back:

- **Read-your-writes:** a user sees their own changes. (Week 2.)
- **Monotonic reads:** a user never sees data go backward. If requests go to two replicas with different lag, a new item can appear on one page load and vanish on the next.
- **Read-then-write safety:** a decision made from a read is valid when the write happens. (Week 3.)

### Ways to handle lag

| Strategy | How it works | Cost |
|---|---|---|
| **Primary for reads that guard writes** | Any read used to decide a write goes to the primary, in the same transaction as the write | Some read load stays on the primary. Enforce invariants with constraints anyway |
| **Sticky window after writes** | For N seconds after a user writes, send that user's reads to the primary | Simple. N is a guess: too short fails during lag spikes, too long keeps load on the primary |
| **Position (LSN) tokens** | After a write, record the primary's WAL position. Read from a replica only if it has replayed past that position; otherwise use the primary or wait | Precise. Requires carrying a token (cookie, header, or session) and tracking each replica's position |
| **Synchronous replication** (`synchronous_commit = remote_apply`) | The primary waits until a replica has *applied* the commit before confirming | Replicas are always current for confirmed commits. Every write gets slower, and writes stop if the synchronous replica is unavailable (unless more replicas are configured) |
| **Session pinning** | Each user's reads go to the same replica | Restores monotonic reads, not read-your-writes. Rebalancing breaks it |
| **Lag-aware routing** | Stop routing to a replica whose lag exceeds a threshold | Protects against large lag. Needs a fallback when every replica is behind |

Most systems combine the first with one of the next two. Correctness-critical reads go to the primary, user-visible freshness is handled with a sticky window or tokens, and lagging replicas are taken out of rotation.

> **Aside: the duplicate application was two bugs.** Routing the check to the replica made the race likely, but the race existed with one database too: two concurrent transactions can both check before either inserts. The real fix is a unique constraint on `(job_id, candidate_id)`. A check in code improves the error message; only the database can enforce the rule.

### Conflicts between replay and queries

When the primary's vacuum removes old row versions, the replica has to remove them too. If a query on the replica is still reading those rows, PostgreSQL has three choices, each set by configuration:

- **Cancel the query** after `max_standby_streaming_delay` (30 seconds by default). This is what happened in week 5.
- **Pause replay** longer, by raising that setting. Queries survive and lag grows for everyone reading from that replica.
- **Stop the primary from removing those rows** with `hot_standby_feedback = on`. Queries and lag both survive, and the primary accumulates dead rows (bloat) while long queries run on the replica.

A common arrangement is to separate the two workloads: application replicas with short delays and fast replay, and a separate analytics replica with long delays, where lag doesn't matter.

### What a replica costs to operate

- **Connections multiply.** Each application instance now has a pool per database, so pool sizing (Module 5) applies to each replica.
- **Failover changes topology.** When a replica is promoted to primary, routing has to follow.
- **Monitoring doubles.** Lag becomes a metric that needs an alert.
- **Schema changes replicate too**, and a long migration on the primary produces a burst of WAL that becomes a burst of lag (6.3).

## When It's Appropriate

- The primary is constrained, most of its load is reads, and indexes and queries are already reasonable (22.3a).
- Reports, exports, and analytics that can tolerate data a few seconds or minutes old.
- Read-heavy pages where freshness isn't critical: search results, public listings, and catalog pages.
- Geographic distribution, with a replica near users far from the primary, for reads that tolerate lag.
- A replica already exists for high availability, and it can take some read load.

## When It's Unnecessary or Overkill

- **The primary has room.** A replica adds a consistency problem to every read path; don't take that on before you need it.
- **The load is a few bad queries.** Fixing an index (22.3a) or an N+1 (6.4a) is cheaper than a second database for those queries to be slow on.
- **The bottleneck is writes, locks, or connection count.** A replica doesn't help with any of those.
- **Most reads need to be fresh.** If nearly every read follows a write by the same user, most traffic ends up on the primary anyway.
- **A cache would do.** For a few hot, rarely changing objects, a cache (Module 13) removes more load with less infrastructure, and it has its own staleness to manage.

## Trade-offs

- **Every read path now has a consistency decision.** Someone has to decide, per query, whether stale data is acceptable. Defaults decide it for you, often wrongly.
- **Lag is unbounded.** It's milliseconds almost always, and minutes during exactly the events (bulk jobs, migrations, incidents) when users are least forgiving.
- **Freshness strategies move load back to the primary.** A sticky window sends a share of all reads to the primary. Tokens are more precise but add code on every request path.
- **Synchronous replication couples availability.** The primary's writes depend on a replica being healthy.
- **Long queries on replicas cost something somewhere:** cancelled queries, lag, or bloat on the primary.
- **More infrastructure:** another server to pay for, patch, monitor, and include in failover planning.
- **Harder debugging.** "It works when I try it" is often "your read went to the primary this time."

## Alternatives

- **Query and index work** (22.3a, 6.4). Often removes the load that motivated the replica.
- **Caching** (Module 13). For hot reads, cheaper per request than a database round trip, with its own staleness.
- **A bigger primary.** Vertical scaling has limits, but it adds no consistency problems, and those limits are further out than many teams assume.
- **CQRS with separate read models** (2.4, Module 37). Builds read-optimized views asynchronously. The staleness is the same kind as a replica's, and it's designed in explicitly instead of discovered.
- **A separate analytics store.** A data warehouse fed by change data capture (38.4) takes reporting off the operational database entirely.
- **Managed database reader endpoints.** Cloud databases offer a reader endpoint that balances across replicas. It handles routing and failover, and does nothing about read-your-writes.

## How to Achieve It

**Level 0 — measure the read share of load, not of statements.** Use `pg_stat_statements` total time by statement type. 92% of statements can be 60% of load.
_Signal you're here:_ "we're read-heavy" is an assumption.

**Level 1 — one replica, for reports and exports only.** Route explicitly chosen, staleness-tolerant workloads to it.
_Signal you need it:_ long reports slowing transactional traffic.

**Level 2 — route read-only transactions, with rules.** Reads that guard writes stay on the primary, invariants are enforced with constraints, and replica lag is monitored and alerted on.
_Signal you need it:_ general read load is the constraint.

**Level 3 — read-your-writes.** Add a sticky window, then position tokens if the window is too blunt.
_Signal you need it:_ "I saved it and it's not there" reports.

**Level 4 — lag-aware routing and workload separation.** Remove lagging replicas from rotation, and use a separate replica for long analytics queries.
_Signal you need it:_ incidents during batch jobs, or cancelled queries.

**Level 5 — several replicas, possibly in several regions,** with session pinning for monotonic reads and failover-aware routing.
_Signal you need it:_ one replica is no longer enough, or users far from the primary.

## Implementation

Java with Spring, because Spring's declarative transactions make replica routing look like one annotation, and the ways that goes wrong are instructive for any framework.

### Routing by transaction type

```java
public class ReplicaRoutingDataSource extends AbstractRoutingDataSource {

    private final ReplicaPosition replica;   // polls the replica's replay position (below)

    ReplicaRoutingDataSource(ReplicaPosition replica) { this.replica = replica; }

    @Override
    protected Object determineCurrentLookupKey() {
        if (!TransactionSynchronizationManager.isCurrentTransactionReadOnly()) {
            return Route.PRIMARY;
        }
        long required = ReadYourWrites.requiredLsn();     // 0 if this user hasn't written recently
        if (required > replica.replayedLsn() || replica.isLagging()) {
            return Route.PRIMARY;
        }
        return Route.REPLICA;
    }
}

@Configuration
class DataSourceConfig {

    @Bean
    @Primary
    DataSource dataSource(DataSource primaryPool, DataSource replicaPool, ReplicaPosition position) {
        var routing = new ReplicaRoutingDataSource(position);
        routing.setTargetDataSources(Map.of(Route.PRIMARY, primaryPool, Route.REPLICA, replicaPool));
        routing.setDefaultTargetDataSource(primaryPool);
        routing.afterPropertiesSet();

        // Without this wrapper, every transaction goes to the primary. See the aside.
        return new LazyConnectionDataSourceProxy(routing);
    }
}
```

> **Aside: why week 1 routed nothing.** When a transaction starts, Spring's transaction manager gets a connection *first*, and only afterward records the transaction's read-only flag where `isCurrentTransactionReadOnly()` can see it. So when the routing data source is asked for a connection, the flag is still `false`, and the answer is always "primary." `LazyConnectionDataSourceProxy` hands out a placeholder connection and only asks the routing data source for a real one when the first statement runs, by which time the flag is set. The code in the first class was correct. The problem was *when* it ran, which is the most common way routing configurations fail silently. Check the replica's load after enabling routing, rather than trusting the configuration.

### Reads that guard writes stay on the primary

```java
@Transactional   // read-write: the check and the insert are on the primary, in one transaction
public Application apply(long jobId, long candidateId) {
    if (applications.existsByJobIdAndCandidateId(jobId, candidateId)) {
        throw new AlreadyAppliedException();   // a friendly message for the common case
    }
    return applications.save(new Application(jobId, candidateId));
    // A concurrent duplicate still fails here, on the unique constraint:
    //   ALTER TABLE applications ADD CONSTRAINT applications_job_candidate_uq
    //     UNIQUE (job_id, candidate_id);
}
```

### Read-your-writes with position tokens

After a write commits, record the primary's WAL position and give it to the client. Then route that client's reads to the replica only once the replica has replayed past it.

```java
@Component
class WritePositionRecorder {
    private final JdbcTemplate primary;   // a template on the primary pool, not the routing one

    /** Call after a write transaction commits. */
    String currentPrimaryLsn() {
        return primary.queryForObject("SELECT pg_current_wal_lsn()::text", String.class);
    }
}

// In the controller that handles the write:
String lsn = positions.currentPrimaryLsn();
response.addCookie(freshnessCookie(lsn, Duration.ofMinutes(2)));   // e.g. "16/B374D848"
```

A servlet filter reads the cookie on each request and stores the parsed value where the routing data source can see it:

```java
final class ReadYourWrites {
    private static final ThreadLocal<Long> REQUIRED = ThreadLocal.withInitial(() -> 0L);

    static void require(String lsn) { REQUIRED.set(Lsn.parse(lsn)); }
    static long requiredLsn()      { return REQUIRED.get(); }
    static void clear()            { REQUIRED.remove(); }   // in the filter's finally block
}

final class Lsn {
    /** PostgreSQL prints LSNs as two hex numbers, "hi/lo". */
    static long parse(String text) {
        int slash = text.indexOf('/');
        long hi = Long.parseUnsignedLong(text.substring(0, slash), 16);
        long lo = Long.parseUnsignedLong(text.substring(slash + 1), 16);
        return (hi << 32) | lo;
    }
}
```

The replica's position is polled in the background rather than checked on every request:

```java
@Component
class ReplicaPosition {
    private final JdbcTemplate replica;   // a template on the replica pool
    private final JdbcTemplate primary;   // a template on the primary pool
    private volatile long replayed = 0;
    private volatile long lagMillis = Long.MAX_VALUE;

    @Scheduled(fixedDelay = 100)
    void poll() {
        try {
            replayed = Lsn.parse(replica.queryForObject(
                "SELECT pg_last_wal_replay_lsn()::text", String.class));
            // Lag as the primary sees it (see the aside below). One replica here;
            // filter by application_name when there are several.
            Long lag = primary.queryForObject("""
                SELECT (EXTRACT(EPOCH FROM coalesce(replay_lag, interval '0')) * 1000)::bigint
                  FROM pg_stat_replication LIMIT 1""", Long.class);
            lagMillis = lag == null ? Long.MAX_VALUE : lag;
        } catch (DataAccessException e) {
            replayed = 0;                   // unknown position: fresh reads go to the primary
            lagMillis = Long.MAX_VALUE;     // and the replica leaves rotation
        }
    }

    long replayedLsn() { return replayed; }

    boolean isLagging() { return lagMillis > 5_000; }
}
```

The polled position is always at or behind the replica's real position, so this check errs toward the primary, which is the safe direction. A user who hasn't written recently has no token and reads from the replica. A user who just published a job reads from the primary until the replica has caught up, which is usually on the next request or two.

> **Aside: measuring lag from the replica alone is misleading.** `now() - pg_last_xact_replay_timestamp()` is the time since the replica last replayed a transaction. If the primary is idle, that number grows even though the replica is fully caught up. Measure lag on the primary, where `pg_stat_replication` reports `replay_lag` for each replica, or compare WAL positions, which doesn't depend on activity.

## Further Reading

- **The PostgreSQL documentation: "High Availability, Load Balancing, and Replication,"** especially "Hot Standby" and its section on handling query conflicts, and the `synchronous_commit`, `hot_standby_feedback`, and `max_standby_streaming_delay` references.
- **Martin Kleppmann, _Designing Data-Intensive Applications_,** chapter 5 ("Replication"). The clearest treatment of read-your-writes, monotonic reads, and consistent prefix reads, and the source of this article's vocabulary.
- **Doug Terry et al., "Session Guarantees for Weakly Consistent Replicated Data"** (1994). The paper that defined read-your-writes and monotonic reads as guarantees a client session can have.
- **The Spring Framework Javadoc for `AbstractRoutingDataSource` and `LazyConnectionDataSourceProxy`.** The second one's documentation explains the connection-timing problem directly.
- **Module 24** for replicas as part of high availability and failover, **Module 38** for replication topologies and sharding, and **Module 5** for pool sizing per database.

A **Go sibling** would be worth writing. Without a framework's declarative transactions, routing in Go is explicit: separate pools, and a choice made in code at each call. The interesting part is carrying the freshness token through `context.Context` from the HTTP handler to the repository, which makes it obvious which reads have a freshness requirement and which don't. Not yet written.

---

The habit to take away: **every read from a replica is a read from the past.** For each one, decide how far in the past is acceptable, and make the reads that can't accept any go to the primary.
