# Finding the Limit: Capacity, Overload, and Recovery

_Module 22.5b — Load Testing_

## The Problem

A delivery-tracking API has two kinds of clients. Couriers' apps post their location every few seconds, and customers' apps poll the status of their orders. It's written in Go and runs behind a load balancer.

Before a holiday promotion, the team plans capacity:

> One instance at 200 requests per second runs at 50% CPU. So one instance can handle about 400 requests per second. The promotion should peak at 3,000 requests per second, so 10 instances gives us 25% headroom.

On the day, at about 2,300 requests per second (230 per instance), this happened:

1. p99 latency went from 90 ms to 4 seconds, while CPU was at 58%.
2. The customer app retries a failed or slow request up to three times, immediately. Offered load rose to about 5,000 requests per second, although the number of customers hadn't changed.
3. *Successful* throughput fell to about 1,700 requests per second. The system was doing more work and completing less of it.
4. The push notification campaign ended and real traffic dropped to 1,500 requests per second, below what the system had handled comfortably that morning. **It stayed broken for 40 minutes**, until the team blocked the retrying app versions at the load balancer.

Three separate mistakes were in the plan:

- **CPU wasn't the limit.** Each order-status request holds a database connection for about 60 ms, and each instance has a pool of 16 connections. The pool can serve at most 16 ÷ 0.06 ≈ 267 requests per second per instance, no matter how much CPU is left. At 230, the pool was 86% busy.
- **Latency doesn't grow linearly with utilization.** At 86% utilization, requests spend most of their time waiting in line for a connection. The next section shows the arithmetic.
- **Nobody had tested what happens past the limit, or after it.** Retries turned a slowdown into an overload, and the overload persisted after its cause was gone.

A load test that stepped up the rate until something broke, then dropped the rate and watched, would have shown all three.

## What It Is

**Capacity testing** finds how much load a system can serve within its latency and error targets, which resource limits it, and how it behaves beyond that point.

22.5a covered making test traffic resemble production. This article covers the kinds of tests to run with that traffic, and how to read them:

| Test | Load shape | Question it answers |
|---|---|---|
| **Load** | Expected peak, held | Do we meet the SLO at the load we expect? |
| **Stress / step** | Increasing steps past the expected peak | Where is the knee, and which resource limits us? |
| **Breakpoint** | Increase until failure | What fails, and how? |
| **Spike** | Sudden jump, e.g. 5× for a minute | Do queues, autoscaling, and caches cope with abruptness? |
| **Soak** | Moderate load for many hours | What accumulates? Leaks (22.1b), connections, disk, bloat |
| **Recovery** | Overload, then back below capacity | Does the system return to normal on its own? |
| **Failure under load** | Normal load while something breaks | Can we survive a cold cache, a lost instance, a slow dependency? |

## Recognizing the Problem

- Capacity plans extrapolated linearly from CPU at low load.
- Nobody can name which resource runs out first.
- Autoscaling based on CPU for a service whose limit isn't CPU.
- Incidents where latency rose sharply at a load only slightly above normal.
- Incidents that continued after the traffic that caused them was gone.
- Clients that retry immediately, or several layers that each retry.
- Adding instances didn't increase throughput, or reduced it.
- No test has ever run for more than an hour.
- A cache whose failure has never been tested at peak load.

## How It Works

### Utilization and waiting

Any resource that serves requests one at a time per slot (a CPU core, a connection, a worker thread) forms a queue once requests arrive faster than it can finish them. Simple queueing theory gives a rule of thumb for how long a request spends in the system, as a multiple of its service time, at utilization ρ:

```
response time ≈ service time ÷ (1 − ρ)

utilization   50%   70%   80%   86%   90%   95%   99%
multiplier    2×    3.3×  5×    7×    10×   20×   100×
```

This is an approximation from the simplest model, and real systems differ in the details. The shape is what matters: **latency is flat until utilization gets high, and then rises very steeply.** The tail (p99) rises earlier and faster than the mean.

So "50% CPU at 200 requests per second" doesn't mean "400 requests per second at 100% CPU with the same latency." Even if CPU had been the limit, latency near 100% would have been unacceptable long before. Capacity has to be defined as **the highest load that still meets the SLO**, not the load at which a resource reaches 100%.

### The knee

Stepping the offered load up and plotting two things shows the system's behavior:

```
successful throughput                          p99 latency
     │            ┌────────╮                       │                     ╱
     │          ╱           ╲  collapse           │                    ╱
     │        ╱               ╲                    │                   ╱
     │      ╱                                      │                 ╱
     │    ╱                                        │   ____________╱
     │  ╱                                          │  ╱
     └──────────────────────────▶ offered          └──────────────────────────▶ offered
                  ▲ knee                                          ▲ knee
```

Below the knee, throughput follows offered load, and latency is flat. At the knee, some resource is nearly saturated. Beyond it, latency grows without bound, and in a badly behaved system, successful throughput *falls*.

The step test's job is to find the knee and name the resource responsible. At each step, look at the saturation of every resource (the USE method): CPU, pool wait time, database CPU and locks, GC (22.1b), event-loop delay (22.2), thread pools, network, and the load generator itself (22.5a). **The first resource to saturate is the bottleneck.** Fixing it moves the knee to wherever the next resource saturates, so the test is repeated after each fix.

### Why adding instances stops helping

Neil Gunther's **Universal Scalability Law** describes how throughput grows as you add capacity N (instances, threads, or connections):

```
             N
X(N) = ─────────────────────────   (relative to one unit)
        1 + σ(N − 1) + κN(N − 1)
```

- **σ (contention):** the fraction of work that has to wait for something shared, such as a lock, a database, or a single queue. Contention alone makes throughput level off.
- **κ (coherency):** the cost of keeping units consistent with each other, such as cross-instance coordination, cache invalidation, or lock negotiation. It grows with N², so it makes throughput eventually *decrease* as you add more.

In the delivery API, ten instances with 16 connections each meant 160 connections to a database with 16 cores. Past some number of instances, more connections only produce more contention inside the database. Measuring throughput at several instance counts and fitting σ and κ gives an estimate of where adding instances stops paying off, before a promotion discovers it.

### What happens past the limit

A system beyond its knee does one of two things:

- **Degrades gracefully.** It serves what it can within its targets and rejects the rest *quickly*, with 429 or 503 responses (Modules 18 and 23). Successful throughput stays near capacity.
- **Collapses.** Requests wait in queues until they time out, after the server has already spent work on them. Clients retry, which adds load. Successful throughput falls, while the system is at full utilization serving requests that nobody is waiting for any more.

Retries are the usual amplifier. Three immediate retries can turn one request into four, *precisely when the system is already overloaded*. With several layers each retrying (the app, the API gateway, the service's database client), the multipliers compound. Retries need backoff, jitter, and a budget (Module 2.5's retry pattern, when written).

### Why the system didn't recover

The most dangerous behavior in the story is the last one: load dropped below the level the system had handled that morning, and the system stayed broken. This is a **metastable failure**. The system has two stable states at the same load:

- **Healthy:** queues are short, requests finish quickly, clients don't retry.
- **Overloaded:** queues are long, requests time out, clients retry, and the retries keep the queues long.

A trigger (the promotion's peak) pushes the system from the first state to the second. Removing the trigger isn't enough, because the retries, not the original traffic, now sustain the overload. Recovery takes an action that breaks the loop: shedding load, blocking retries, or restarting with traffic held back.

A **recovery test** checks for this directly: overload the system for a few minutes, then drop to well below capacity, and measure how long latency takes to return to normal. "It never does" is a result you want from a test, not from production.

### Failure under load, and the survivable hit rate

Some failures only matter at peak load:

- **A cold or failed cache.** Module 13.2b defined the **survivable hit rate**: the lowest cache hit rate at which the origin can still serve peak traffic. Find it by holding peak load and lowering the hit rate in steps (flushing, or bypassing the cache for a growing share of keys through a feature flag) until the origin reaches its knee. Compare that number with the hit rate you actually see after a deploy, a restart, or a cache failover. If the survivable hit rate is 80% and a restart drops the hit rate to 30%, a restart at peak is an outage.
- **A lost instance or zone.** Capacity with one unit missing is the capacity that matters (N+1).
- **A slow dependency.** Adding 500 ms to a stub's latency shows whether timeouts, pools, and circuit breakers contain it, or whether connections pile up (Module 5's isolation controls).
- **A database failover** during load, which tests reconnection and retry behavior.

### Soak tests

Some problems need time, not load: memory leaks (22.1b), connection or file-handle leaks, log volumes filling disks, table bloat from long transactions, token or certificate expiry, and caches that slowly fill and start evicting. A soak test runs moderate load (well below the knee) for hours, and passes if every resource that should be flat stays flat, especially memory after GC.

### Capacity planning from test results

1. **Measure capacity per instance at the SLO**, from a step test with a realistic mix (22.5a).
2. **Leave headroom** for the queueing curve. Planning to run at the knee means any fluctuation crosses it.
3. **Plan for losing a unit:** capacity with one instance or zone gone must still cover peak.
4. **Account for scaling lag.** Autoscaling takes minutes: launching instances, starting them, and warming their caches. Spikes shorter than that are served by the capacity already running.
5. **Scale on the resource that saturates.** CPU-based autoscaling for a service limited by its connection pool scales at the wrong time.
6. **Re-measure after significant changes.** A new query, a framework upgrade, or a new dependency changes the knee.

## When It's Appropriate

- Before events with known peaks, and before any capacity plan is trusted.
- When a service's limiting resource is unknown.
- After changes to pools, timeouts, retries, caching, or instance sizes.
- For systems with retries at several layers, where overload behavior needs to be known in advance.
- Periodically for services on a growth curve, to see how close the knee is.
- Soak tests before releases that change memory, connection, or caching behavior.

## When It's Unnecessary or Overkill

- **Services running at a small fraction of capacity** with slow, steady growth, where production metrics already show the headroom.
- **Breakpoint tests in production.** Finding the failure point is the purpose of the test, and production is not where to do it.
- **Fitting scalability models to a service with three instances** and no plans for thirty.
- **Daily full-scale capacity tests** when the system changes monthly. Run small regression checks often and full tests when something significant changes.

## Trade-offs

- **Step tests take hours.** Each step has to run long enough to reach a steady state (minutes, not seconds), and the test is repeated after each fix.
- **Breaking things is the point, and it has a blast radius.** Shared staging environments, shared databases, and shared third-party sandboxes all feel your stress test.
- **Queueing models are approximations.** The 1/(1 − ρ) rule assumes simple, random arrivals and service times. It tells you the shape, and the test tells you the numbers.
- **Load shedding and retry budgets are design work,** not a configuration flag, and they need testing of their own.
- **Soak tests tie up environments** for a day, and their failures take a long time to reproduce.
- **Performance regression checks in CI are noisy.** Shared runners vary by 10% or more between runs. Compare against a baseline on the same hardware, use tolerances, and look at trends rather than single failures.

## Alternatives

- **Capacity from production metrics.** Plotting latency against throughput from production over weeks shows the start of the knee without a test, as long as production has come close to it.
- **Arithmetic.** 16 connections ÷ 60 ms per request = 267 requests per second. The pool limit in the story was calculable without any test, once someone asked what each request holds and for how long.
- **Load shedding and admission control** (Module 23). They don't tell you where the limit is, but they make being past it much less damaging.
- **Chaos engineering in production** (Module 24). Injects failures into real traffic. It's the natural next step after "failure under load" tests pass in a test environment.
- **Autoscaling on the right signal.** It reduces how precisely you need to know capacity, as long as spikes are slower than scaling.

## How to Achieve It

**Level 0 — know what each request holds.** For the main operations, write down the resources each request holds, and for how long: connections, threads, and locks.
_Signal you're here:_ capacity plans based only on CPU.

**Level 1 — step tests on one instance.** Find the per-instance knee with a realistic mix, and name the saturated resource.
_Signal you need it:_ a capacity plan you're about to rely on.

**Level 2 — overload and recovery tests.** Go past the knee, then drop back, and fix retries and shedding until the system degrades gracefully and recovers on its own.
_Signal you need it:_ retries at more than one layer, or an incident that outlived its cause.

**Level 3 — failure under load.** Measure the survivable hit rate, capacity with one instance lost, and behavior with a slow dependency.
_Signal you need it:_ a cache, a zone, or a dependency whose failure at peak has never been tried.

**Level 4 — soak tests and scaling measurements.** Run multi-hour tests before significant releases, and measure throughput at several instance counts.
_Signal you need it:_ problems that appear after days of uptime, or instance additions that didn't add capacity.

**Level 5 — continuous capacity tracking.** Small, fixed-rate regression tests in CI against a stable baseline, with full step tests on a schedule, and capacity numbers recorded in the capacity plan with their dates.
_Signal you need it:_ capacity regressions found in production more than once.

## Implementation

Go, with the `vegeta` library. vegeta sends requests at a fixed rate whether or not earlier ones have finished (the open model from 22.5a), and as a library it makes it easy to write the step-and-recover logic as ordinary code instead of configuration.

### A weighted request mix

```go
import (
    "fmt"
    "math/rand/v2"
    "net/http"
    "time"

    vegeta "github.com/tsenart/vegeta/v12/lib"
)

func mixTargeter(base, token string, orders, couriers []string) vegeta.Targeter {
    hdr := http.Header{
        "Authorization": {"Bearer " + token},
        "Content-Type":  {"application/json"},
    }
    return func(t *vegeta.Target) error {
        t.Header = hdr
        switch r := rand.Float64(); {
        case r < 0.70: // customers polling order status (holds a DB connection ~60 ms)
            t.Method, t.Body = "GET", nil
            t.URL = base + "/orders/" + orders[rand.IntN(len(orders))] + "/status"
        default: // couriers posting locations
            t.Method = "POST"
            t.URL = base + "/couriers/" + couriers[rand.IntN(len(couriers))] + "/location"
            t.Body = []byte(fmt.Sprintf(`{"lat":%.5f,"lng":%.5f}`,
                51.4+rand.Float64()*0.2, -0.2+rand.Float64()*0.3))
        }
        return nil
    }
}
```

For brevity, order IDs are picked uniformly here; a real test would use the skewed picker from 22.5a.

### One step, measured

```go
type result struct {
    Offered    int
    Sent       float64 // what vegeta actually managed to send
    Throughput float64 // successful responses per second
    Success    float64
    P50, P99   time.Duration
}

func runStep(tr vegeta.Targeter, rps int, warmup, measure time.Duration) result {
    atk := vegeta.NewAttacker(vegeta.Timeout(5*time.Second), vegeta.MaxWorkers(20_000))
    rate := vegeta.Rate{Freq: rps, Per: time.Second}

    if warmup > 0 { // note: a duration of 0 would mean "attack forever" in vegeta
        for range atk.Attack(tr, rate, warmup, "warmup") { // reach steady state; discard
        }
    }

    var m vegeta.Metrics
    for res := range atk.Attack(tr, rate, measure, fmt.Sprint(rps)) {
        m.Add(res)
    }
    m.Close()
    return result{rps, m.Rate, m.Throughput, m.Success, m.Latencies.P50, m.Latencies.P99}
}
```

> **Aside: two numbers keep the test honest.** First, `Sent` should match `Offered`. If vegeta runs out of workers, it can't send on schedule, and the test silently becomes a lower-rate test, the same problem as `dropped_iterations` in k6. Second, vegeta's latency percentiles include failed requests. A server rejecting requests in 2 ms can pull p99 *down* while it fails, so read `Success` next to every latency number.

### Finding the knee, then testing recovery

```go
func main() {
    tr := mixTargeter(baseURL, token, loadIDs("orders.txt"), loadIDs("couriers.txt"))
    const slo = 300 * time.Millisecond

    // 1. Step up against ONE instance until the SLO breaks.
    var knee int
    fmt.Println("offered  sent   ok/s   success  p50     p99")
    for rps := 100; rps <= 600; rps += 25 {
        r := runStep(tr, rps, time.Minute, 2*time.Minute)
        fmt.Printf("%7d  %5.0f  %5.0f  %6.2f%%  %-6v  %v\n",
            r.Offered, r.Sent, r.Throughput, r.Success*100, r.P50.Round(time.Millisecond), r.P99.Round(time.Millisecond))
        if r.P99 > slo || r.Success < 0.99 || r.Sent < 0.98*float64(rps) {
            break
        }
        knee = rps
    }
    fmt.Printf("\ncapacity at SLO: %d req/s per instance\n\n", knee)

    // 2. Overload at 1.5× for three minutes, then drop to 0.6× and watch recovery.
    runStep(tr, knee*3/2, 0, 3*time.Minute)
    for window := 1; window <= 10; window++ {
        r := runStep(tr, knee*6/10, 0, 30*time.Second)
        fmt.Printf("recovery t+%3ds  p99=%-7v success=%.2f%%\n",
            window*30, r.P99.Round(time.Millisecond), r.Success*100)
        if r.P99 <= slo && r.Success >= 0.999 {
            fmt.Println("recovered")
            return
        }
    }
    fmt.Println("DID NOT RECOVER within 5 minutes at 60% of capacity: metastable")
}
```

Against the delivery API as it was before the promotion, the output looked like this:

```
offered  sent   ok/s   success  p50     p99
    100    100    100  100.00%  41ms    88ms
    150    150    150  100.00%  43ms    97ms
    200    200    200  100.00%  47ms    131ms
    225    225    225   99.97%  58ms    244ms
    250    250    247   98.91%  112ms   1.84s

capacity at SLO: 225 req/s per instance

recovery t+ 30s  p99=5s       success=61.20%
recovery t+ 60s  p99=5s       success=64.85%
recovery t+ 90s  p99=4.98s    success=66.02%
...
DID NOT RECOVER within 5 minutes at 60% of capacity: metastable
```

225 per instance, not 400, and a system that stays broken at 135 requests per second after a few minutes of overload. vegeta itself never retries, so to reproduce the incident the team pointed it at a small proxy that retried the way the real app did: three immediate retries on a timeout or a 5xx. Without that proxy, the same test recovered in the first window, which is itself the finding: the retries, not the load, kept the system down. The dashboards during the 250 step named the resource: pool wait time rose from under 1 ms to over a second, while CPU stayed below 60%.

The fixes were a larger pool paired with a lighter status query (moving the knee), exponential backoff with jitter and a retry budget in the app (breaking the retry loop), and fast rejection when pool wait exceeds 200 ms (graceful degradation). After them, the same program printed a capacity of 410 per instance and "recovered" within the first window.

## Further Reading

- **Neil Gunther, _Guerrilla Capacity Planning_.** The Universal Scalability Law, how to fit it from a few measurements, and how to use it for planning.
- **Bronson, Aghayev, Charapko, and Zhu, "Metastable Failures in Distributed Systems"** (HotOS 2021), and the follow-up study by Huang et al. (OSDI 2022). The definition of metastable failure and a catalog of real incidents caused by retry loops and similar feedback.
- **Mor Harchol-Balter, _Performance Modeling and Design of Computer Systems_.** Queueing theory for engineers, including why latency rises so sharply near full utilization.
- **Google SRE book, "Handling Overload"** and **"Addressing Cascading Failures,"** and the AWS Builders' Library article **"Timeouts, retries, and backoff with jitter."** Practical guidance on shedding load and making retries safe.
- **Brendan Gregg, "The USE Method"** (and _Systems Performance_). The checklist for finding which resource saturated at the knee.
- **The vegeta README and library documentation**, for attack options, pacers, and the exact meaning of each metric.
- **Module 13.2b** for the survivable hit rate, **Module 18** and **Module 23** for rate limiting and load shedding, **Module 5** for pool sizing, and **Module 24** for chaos engineering.

A **TypeScript sibling** with k6 would be worth writing for the same step-and-recover procedure expressed as scenarios with `startTime` offsets, plus k6's thresholds with `abortOnFail` as the stop condition. Its interesting difference is that the steps become declarative configuration, which is easier to run in CI and harder to adapt mid-test. Not yet written.
