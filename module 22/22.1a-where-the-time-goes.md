# Where the Time Actually Goes: Profiling

_Module 22.1a — Performance Optimization_

## The Problem

Suppose you run a freight-quoting service written in Go. `POST /quotes` takes a shipment and prices it against about 300 rate lines. A release adds promotional pricing rules, and the next morning looks like this:

- p50 latency went from **40 ms to 210 ms**.
- CPU per instance went from about 30% to **80%**.
- Traffic is flat, but the autoscaler doubled the fleet from **6 to 12 instances**.

The team does what most teams do: it guesses.

**Guess one: "The responses got bigger, so JSON encoding is slow."** Someone swaps in a faster encoder. Its benchmark is 2.1× faster than the standard library. Production p50 moves from 210 ms to 204 ms.

**Guess two: "It's the database."** The per-request attribution line from 6.4b settles that in one glance: `total_ms=212 db_ms=9 queries=3`. The database is doing almost nothing.

Two days are gone. Then someone captures a 30-second CPU profile from one production instance, and the answer is on the first screen: **61% of all CPU time is inside `regexp.MustCompile`**, called from the new promo-matching function. It compiles each rule's pattern for every rate line on every request, which comes to 300 lines × 40 rules = 12,000 regex compilations per quote. Moving the compilation to rule-load time takes one line. p50 returns to 44 ms and the fleet shrinks back to six instances.

The JSON guess wasn't wrong about encoding being slow. It was wrong about encoding *mattering*: encoding was about 5% of the request's CPU, so making it twice as fast could never save more than about 2.5%.

A week later a different complaint arrives. `GET /quotes/{id}/pdf` has a **p99 of 2.3 seconds**, and CPU on those instances is **12%**. The team, now converted, takes a CPU profile. It shows PDF layout at 38%, font handling, some compression, and nothing that stands out. Every function in it is fast.

The profile is not lying. It is answering a different question. A CPU profile records what the program was doing *while it was running on a CPU*, and these requests are mostly not running. They're waiting. A dump of all goroutines shows 183 of 412 parked on the same line: a `sync.Mutex` inside the exchange-rate cache, which holds its lock while it refreshes a rate over HTTP, a call that takes 300–900 ms. Every PDF for every currency pair queues behind that one call.

Both incidents turned on the same two lessons. Measure before changing anything. And know which measurement answers which question.

## What It Is

What resolved both incidents is **profiling**: measuring where a running program spends a resource (CPU time, wall-clock time, memory, lock waits) and attributing it to the code that spent it, usually as call stacks.

A profile is an aggregate. It adds up everything a process did over a window, across all requests, and tells you which code accounts for which share. That is the main difference from a **trace** (Modules 16 and 19), which follows one request across services and records its spans in order. A trace can tell you that the slow request spent 800 ms inside the pricing service. A profile can tell you which function inside the pricing service eats the CPU for everyone. The other neighbors (benchmarks, metrics, execution tracers, system-wide profilers) are compared together under Alternatives.

## Recognizing the Problem

- Performance discussions begin with "I think it's…"
- An optimization was merged with no before-and-after number from production.
- CPU is high, and nobody can name the function responsible.
- **Latency is high and CPU is low.** Something is waiting, and a CPU profile will look innocent.
- The fleet grew after a deploy that didn't change traffic.
- Request attribution (6.4b) says "not the database," and the investigation stalls there.
- A microbenchmark improved and production didn't.
- Cost per request rises slowly across releases, and no single change is to blame.
- Slowness appears only in production, only under load, or only for one customer.

## How It Works

### Sampling versus instrumentation

There are two ways to find out where time goes.

**Instrumentation** records every function entry and exit. The counts are exact, but the recording itself costs time on every call, so small functions that are called millions of times look far more expensive than they are. The measurement distorts the thing measured, and the distortion is worst exactly where hot spots tend to live.

**Sampling** interrupts the program at a fixed rate and records the current call stack. Go's CPU profiler does this 100 times per second. Nothing is recorded between samples, so the overhead is small (typically low single-digit percent) and profiling is safe to run in production. The result is statistical: if a function appears in 20% of samples, it accounts for roughly 20% of CPU time.

A 30-second profile of a process using 1.5 cores holds about 4,500 samples, which is plenty to find anything above a percent or two. What sampling misses is the short and rare: a 5 ms stall that happens twice a minute barely registers. Most production profilers sample. Instrumentation survives where exact call counts matter, and in coarse form as tracing spans.

### Which clock you're reading

A request's wall-clock time splits into time on a CPU and time waiting:

```
one request, 400 ms of wall-clock time

on CPU    ███████░░░░░░░░░░░░░   70 ms   ← a CPU profile sees only this
off CPU   ░░░░░░░█████████████  330 ms   ← and is blind to all of this
            ├─ waiting on the network (database, HTTP calls)
            ├─ waiting for a lock or a channel
            ├─ waiting for a pool connection or a queue slot
            └─ runnable, but not scheduled (CPU saturated, or container CPU-throttled)
```

Different profiles read different clocks, and choosing the wrong one produces a confident, useless answer:

- **CPU profile:** on-CPU time. Finds hot code. Blind to waiting.
- **Wall-clock profile:** on-CPU plus off-CPU time for each stack. Finds where requests *spend their lives*, including waiting. Go doesn't ship one, but third-party ones exist (`fgprof`).
- **Goroutine or thread dump:** where every goroutine is *right now*. A crude but powerful off-CPU tool. If 183 goroutines are on the same line, that line is the answer.
- **Contention profiles** (Go's mutex and block profiles): how long code waited on locks and channels, and which code held them.
- **Allocation profile:** where memory is allocated, whether or not it is still live. Heavy allocation shows up as garbage-collector CPU.
- **Heap (in-use) profile:** what is still live. This is where leaks show up. 22.1b covers both memory profiles.

The last bullet in the diagram deserves attention in containers. When a pod hits its CPU limit, the kernel stops scheduling it for the rest of the period. Requests wait while the process looks idle. Throttling counters (`nr_throttled` in the cgroup's `cpu.stat`) are the signal, and no in-process profiler will show it.

### Reading a profile

Every sampled stack contributes to two numbers per function:

- **flat:** samples where the function itself was on top of the stack. This is time spent in its own code.
- **cum** (cumulative): samples where the function was anywhere on the stack. This is its own time plus everything it called.

Sort by flat to find leaf hot spots: hashing, regex, encoding, copying. Sort by cum to find the expensive subtree and its entry point. In the quote incident, `regexp.MustCompile` had almost no flat time of its own. Its children did the parsing, but its cum was 61%, and its caller identified the feature.

A **flame graph** draws the same data as stacked boxes:

```
[                           ServeHTTP  96%                                  ]
[          pricing.Compute  82%                     ][ json.Encode 5% ][...]
[      pricing.matchPromo  66%          ][applyTax 9%]
[   regexp.MustCompile  61%          ][.]
[ syntax.Parse 33%  ][ compile  24% ]
```

Each box is a function, stacked on top of its caller. **Width is share of samples**, and it is the only dimension that matters. The horizontal order carries no meaning (it's often alphabetical, so identical stacks merge), and there is no time axis. Look for wide boxes, especially wide boxes near the top: those are functions that burn CPU themselves. A *flame chart*, like the one in a browser's performance panel, looks similar but does put time on the x-axis. Don't read one as the other.

A **differential profile** subtracts a baseline from a new profile, which is how you answer "what got more expensive in this release?" without eyeballing two pictures.

### What a profile can't tell you

**It says where, not why.** The profile said `MustCompile`. Nothing in it said "compile once at load time." That came from reading the code the profile pointed to. The best fix for a hot function is often not calling it at all.

**Your gains are bounded by the share (Amdahl's law).** If a function is 5% of CPU, making it infinitely fast saves 5%. That is the whole story of the JSON guess. Before optimizing something, read its share, and you'll know the most you can win.

**A flat profile means there's no single hot spot.** When the top function is 3% and the next hundred are each 1–2%, the cost is spread out: too many layers, allocations everywhere, work done per request that could be done once. The fix is structural (removing work), not a faster function.

**It shows the average, not the tail.** A profile aggregates every request in the window. If 1% of requests are slow for a reason the other 99% don't share, they contribute 1% of samples and disappear. Tail latency is a tracing question first. A profile helps once you know which kind of request to look at (see labels, below).

**It reflects the workload it saw.** A profile of an idle instance shows idle work. A profile taken under a load test with uniform synthetic data misses the one customer whose 40,000-line quotes drive the real cost. A profile from your laptop shows a different CPU, a different data set, and none of production's contention.

**The compiler rearranges the evidence.** Inlined functions vanish into their callers. In JIT-compiled runtimes the frames you see depend on what got compiled when. System-wide profilers need frame pointers or unwinding information to reconstruct stacks at all.

### Attribution: labels

"61% of CPU is in promo matching" is more useful as "61% of CPU is in promo matching, *on `POST /quotes`, for enterprise-tier accounts*." Most profilers let you attach key-value labels to the work a request does, so a profile can be filtered or split by route, tenant tier, or job type. This is how you find the noisy neighbor in a multi-tenant system (Module 5) with a profiler rather than a hunch.

### Continuous profiling

On-demand profiling answers "what is it doing now?" **Continuous profiling** samples every instance all the time, at a low rate, and stores the results with labels such as service, version, and region. Then "what changed since Tuesday's deploy?" becomes a diff between two time ranges. Google described running this across its fleet in 2010 (Google-Wide Profiling). Today it's available as open source (Grafana Pyroscope, Parca), from cloud providers, and from APM vendors. Some of these use eBPF to profile every process on a host with no code changes. OpenTelemetry has been adding profiles as a signal alongside traces, metrics and logs, so check its current status before building on it.

## When It's Appropriate

- **Before any performance work.** A 30-second profile costs less than the first meeting about what to optimize.
- **CPU per request rose after a deploy** while traffic stayed flat: the fleet doubling from 6 to 12 instances above.
- **Latency rose and request attribution says it's application time**, not database or round trips.
- **Compute is a large line on the bill.** At 200 instances, a 10% CPU reduction is 20 instances, every month, indefinitely.
- **One tenant, route, or job type seems to consume a disproportionate share,** and you want a number rather than a suspicion.
- **Latency is high with CPU low.** Reach for a goroutine dump, a contention profile, or a wall-clock profile, not a CPU profile.
- **Continuous profiling** earns its keep with a fleet of dozens of instances or more, with daily deploys where small regressions accumulate unnoticed, or when compute cost is actively managed.

## When It's Unnecessary or Overkill

- **The problem is already attributed elsewhere.** `total 912 / db 870` means go read the query plan (6.4b). A CPU profile of the application will show a process waiting on a socket.
- **The latency is round trips.** An N+1 (6.4a) spends almost no CPU. Count the queries per request instead.
- **The code is fast enough.** An internal tool handling two requests a minute, where the "slow" function takes 3 ms, doesn't need optimizing.
- **Chasing a function at 2% flat.** Amdahl says the ceiling is 2%. Unless you're running a very large fleet, you have better uses for the afternoon.
- **A continuous-profiling platform for three instances.** An on-demand endpoint and one command are enough.
- **Profiling on a laptop to diagnose production.** Different data, different hardware, no concurrency. Whatever it finds may not be what's happening.

## Trade-offs

**Overhead is small but not zero, and some profiles are expensive.** CPU sampling at the default rate is cheap. Contention profiling that records every event, or allocation profiling at a very fine rate, is not. Heap dumps pause the process and can be large. Every profile type has a sampling knob, and the production setting is not the maximum.

**A profiling endpoint is an attack surface.** It reveals your code structure. It lets anyone who can reach it run a long CPU profile or trigger heap dumps, which is a cheap denial of service. Heap contents can include tokens and personal data (Module 20). It belongs on an admin listener that the public network can't reach.

**Statistical results need enough samples.** A 5-second profile of a quiet instance is noise that looks like data. Short, rare events vanish. A profile shows the average, and the tail needs tracing (above).

**Labels have a cardinality cost.** The same lesson as metrics in Module 16 applies. Labeling on-demand profiles by tenant ID is fine. Labeling a year of continuous profiles by tenant ID makes storage and query cost scale with your customer count. Prefer bounded values such as tier, route, or job type.

**Continuous profiling is another data pipeline**, with storage, retention and cost that grow with fleet size and label count.

**Interpretation takes skill, and runtimes make it harder.** Inlining, JIT compilation, garbage-collector threads, and async runtimes whose stacks don't show which request scheduled a callback all make profiles harder to read correctly. The first few profiles someone reads are usually misread somewhere.

**Profile-driven code is less obvious code.** A regex hoisted to load time, a hand-rolled parser, a pooled buffer: each is a small readability cost, and without context the next engineer "simplifies" it back. Keep a benchmark next to the optimization, and put the before-and-after numbers in the commit.

## Alternatives

Profiling is one of several measurement tools, and each answers one question well:

```
question                                         tool
───────────────────────────────────────────────  ────────────────────────────────────
is something wrong, and in which resource?       metrics: RED per endpoint, USE per resource (16)
where did this one request spend its time?       distributed tracing (19)
which category: database, round trips, app?      per-request attribution (6.4b)
which code burns CPU, across all requests?       CPU profile
where are requests waiting?                      goroutine dump, contention or wall-clock profile
did my change make this function faster?         benchmark
what happened, in order, in these two seconds?   execution tracer
what is the whole machine doing, kernel too?     system profiler (perf, eBPF)
```

- **Metrics and tracing** come first when you don't yet know which service or resource is involved. A profile only helps once you know which process to profile.
- **Benchmarks** (`go test -bench`, compared across runs with `benchstat`) confirm that a fix works on the code you already suspect. They don't find the problem, and a microbenchmark that improves while production doesn't is usually measuring something production doesn't spend time on.
- **Execution tracers** (`go tool trace`, a browser's performance panel) record a timeline of scheduling, garbage collection, and blocking events. They're the tool for latency that comes from *when* things ran rather than *what* ran. Go 1.25 added a flight recorder that keeps the last few seconds of trace in memory so you can save it when something goes wrong.
- **System-wide profilers** (`perf`, eBPF-based tools) see every process and the kernel, regardless of language. They're the right tool when the cost is in syscalls, page faults, or a process you didn't write. The cost is needing symbols and stack-unwinding information.
- **Reading the code** is sometimes enough. An O(n²) loop is visible without a profiler, if you know where to look. The profiler's job is to tell you where to look (22.2a).

## How to Achieve It

**Level 0: make a production profile obtainable in one command.** Expose profiling on an admin port, document the command, and try it once when nothing is wrong.
_Signal you're here:_ nobody on the team has ever looked at a production profile.

**Level 1: profile before and after every performance change.** Put both numbers in the pull request, and add a benchmark for the hot path you fixed.
_Signal you need it:_ optimizations get merged because someone believed in them.

**Level 2: add the off-CPU tools.** Enable contention profiling at a modest sampling rate. Learn to read a goroutine dump, and keep a wall-clock profiler available.
_Signal you need it:_ an incident where latency was high, CPU was low, and the CPU profile said nothing.

**Level 3: label the work.** Attach route and a bounded tenant or job attribute to profiles.
_Signal you need it:_ the question has become "which endpoint?" or "which customer?"

**Level 4: profile continuously.** Record deploy versions as labels and diff across releases.
_Signal you need it:_ regressions are discovered by the cloud bill or the autoscaler, weeks after they shipped.

**Level 5: feed profiles back into the build.** Go (1.21 and later) supports profile-guided optimization: commit a representative production CPU profile as `default.pgo` and the compiler inlines and devirtualizes based on it. The Go team reports gains from a few percent to low double digits on its benchmark set.
_Signal you need it:_ CPU is a major cost and Level 4 already collects the profiles. This level is optional.

## Implementation

Go, because its profiling is built into the standard library and the toolchain, and the mechanics are visible without any vendor setup. Setting up the other runtimes differs, but reading the output is the same skill everywhere.

**An admin listener, and only an admin listener:**

```go
import (
    "net/http"
    httpprof "net/http/pprof"
    "runtime"
)

func startAdmin() {
    runtime.SetMutexProfileFraction(100)   // record ~1 in 100 lock-contention events
    runtime.SetBlockProfileRate(10_000_000) // record ~1 blocking event per 10 ms spent blocked

    mux := http.NewServeMux()
    mux.HandleFunc("/debug/pprof/", httpprof.Index)          // heap, goroutine, mutex, block, allocs
    mux.HandleFunc("/debug/pprof/profile", httpprof.Profile) // CPU
    mux.HandleFunc("/debug/pprof/symbol", httpprof.Symbol)
    mux.HandleFunc("/debug/pprof/trace", httpprof.Trace)     // execution trace
    // no /cmdline: it would expose command-line flags, which sometimes contain secrets

    go http.ListenAndServe("127.0.0.1:6060", mux) // reachable by port-forward, not by the internet
}
```

> **Aside: the blank import is the classic leak.** The usual tutorial line, `import _ "net/http/pprof"`, registers these handlers on `http.DefaultServeMux`. If your public server also uses `DefaultServeMux` (and `http.ListenAndServe(":8080", nil)` does), you've just published your profiler. Registering on a private mux avoids that.

**Capturing and reading the quote incident:**

```bash
go tool pprof -http=:8080 'http://localhost:6060/debug/pprof/profile?seconds=30'
```

This opens a browser with a flame graph view. The text view of the same profile:

```
Duration: 30s, Total samples = 47.20s (157.33%)
(pprof) top 5 -cum
      flat  flat%        cum   cum%
     0.02s  0.04%     45.10s 95.55%  net/http.(*conn).serve
     0.04s  0.08%     39.80s 84.32%  quotes.(*Handler).Create
     0.21s  0.44%     38.60s 81.78%  pricing.Compute
     0.35s  0.74%     31.20s 66.10%  pricing.matchPromo
         0     0%     28.70s 60.81%  regexp.MustCompile
```

`Total samples` exceeding 100% just means more than one core was busy: 47.2 seconds of CPU in 30 seconds of wall time is about 1.6 cores. The code behind the last two lines:

```go
func matchPromo(line RateLine, rules []PromoRule) bool {
    for _, r := range rules {
        re := regexp.MustCompile(r.LanePattern) // compiled for every line × every rule, every request
        if re.MatchString(line.Lane) {
            return true
        }
    }
    return false
}
```

The fix stores a compiled `*regexp.Regexp` on `PromoRule` when rules are loaded. To confirm it, capture the same profile afterward and compare with `go tool pprof -diff_base=before.pb.gz after.pb.gz`.

**Labels, so the profile can be split by route and tier:**

```go
import "runtime/pprof"

func profileLabels(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        labels := pprof.Labels("route", routeOf(r), "tier", tierOf(r)) // bounded values only
        pprof.Do(r.Context(), labels, func(ctx context.Context) {
            next.ServeHTTP(w, r.WithContext(ctx))
        })
    })
}
```

```bash
go tool pprof -tags cpu.pb.gz                          # CPU share per label value
go tool pprof -tagfocus=tier=enterprise cpu.pb.gz      # only enterprise-tier work
```

> **Aside: labels cover less than you might expect.** Go attaches them to CPU and goroutine profiles, and goroutines started inside `pprof.Do` inherit them. They don't appear in heap or allocation profiles, so "which tenant allocates the most?" needs a different approach (22.1b).

**The PDF incident, which the CPU profile couldn't see:**

```bash
curl -s 'http://localhost:6060/debug/pprof/goroutine?debug=1' | head -12
```

```
goroutine profile: total 412
183 @ 0x43e8d6 0x44f1c5 0x44f1a5 0x46b2a4 0x9a1f02 0x9a3310 …
#   0x46b2a3   sync.(*Mutex).lockSlow+0x163       …/sync/mutex.go
#   0x9a1f01   fxrates.(*Cache).Get+0x41          …/fxrates/cache.go:31
#   0x9a330f   pdf.(*Renderer).Totals+0x8f        …/pdf/render.go:118
…
```

`debug=1` groups goroutines with identical stacks and prints a count first. 183 identical stacks all waiting at the same lock is about as unambiguous as diagnostics get. The code at line 31:

```go
func (c *Cache) Get(ctx context.Context, pair string) (Rate, error) {
    c.mu.Lock()
    defer c.mu.Unlock()
    if e, ok := c.entries[pair]; ok && time.Since(e.at) < c.ttl {
        return e.rate, nil
    }
    rate, err := c.client.Fetch(ctx, pair) // 300–900 ms of HTTP while holding the only lock
    // …
}
```

The fix is to never hold a lock across I/O. Deduplicate concurrent refreshes per key (`golang.org/x/sync/singleflight`) and serve the stale value while one refresh runs. This is the stampede and refresh-ahead material from Module 13. The mutex profile would have found the same line, with the holder's stack included. The goroutine dump found it with nothing enabled in advance, which is why it's worth learning first.

## Further Reading

- **Go documentation, "Diagnostics"** (go.dev/doc/diagnostics). The official map of profiling, tracing, and debugging in Go, including which profile answers what.
- **Package docs for `runtime/pprof` and `net/http/pprof`**, and the **`google/pprof` README** for the flags used here (`-tags`, `-tagfocus`, `-diff_base`) and the web UI.
- **Russ Cox, "Profiling Go Programs"** (The Go Blog). The classic walkthrough: take a real program, profile it, and fix what the profile shows, several times over.
- **Go documentation, "Profile-guided optimization"** (go.dev/doc/pgo), for Level 5.
- **Brendan Gregg, "The Flame Graph"** (ACM Queue, 2016), plus his pages on flame graphs and **off-CPU analysis** at brendangregg.com. The origin of the visualization and the clearest explanation of the on-CPU/off-CPU split.
- **Brendan Gregg, _Systems Performance_, 2nd edition** (2020). The methodology chapters, especially the USE method and the "anti-methods" such as guessing and blaming the tool you already know, are the discipline this article assumes.
- **Felix Geisendörfer, `fgprof`** (github.com/felixge/fgprof). The README is a short, precise explanation of why Go's CPU profiler misses I/O-bound work and what a wall-clock profile adds.
- **Ren et al., "Google-Wide Profiling: A Continuous Profiling Infrastructure for Data Centers"** (IEEE Micro, 2010). The case for always-on fleet profiling, written before the tools existed outside Google.
- **Mytkowicz, Diwan, Hauswirth & Sweeney, "Evaluating the Accuracy of Java Profilers"** (PLDI 2010). Four profilers disagreed about the same program's hot spots. Read it before trusting any single profile completely.
- **Grafana Pyroscope and Parca documentation**, for continuous profiling you can run yourself.

A **Java** sibling would be worth writing, because the JVM changes what a profile can be trusted to say. Many traditional JVM sampling profilers can only take a sample at a *safepoint*, so hot loops without one are invisible and the time gets attributed elsewhere (safepoint bias, which is what the Mytkowicz paper found). JIT compilation means the same code profiles differently during warm-up and at steady state. And async-profiler and Java Flight Recorder work around the first problem in different ways. The Go profiler in this article doesn't have safepoint bias, so an article in Go can't teach any of this. Not yet written.

---

The habit to take from this: **before changing code for speed, get a number and a map.** And when the map shows nothing, ask what the program is waiting for, not what it is doing.
