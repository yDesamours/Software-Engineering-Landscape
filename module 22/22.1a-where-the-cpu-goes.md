# Where the CPU Actually Goes

_Module 22.1a — Performance Profiling_

## The Problem

A team runs the pricing API for a hotel-booking site. Given a hotel, dates, and a guest count, it returns room rates. It is written in Go and runs on 12 instances.

Over one quarter, p99 latency climbed from 80 ms to 310 ms, and average CPU across the fleet rose from 40% to 70%. Traffic grew only 15% in that time. Nobody could point to a change that caused it.

The team tried three fixes over two weeks, each based on a reasonable guess:

| Guess | Fix | Result |
|---|---|---|
| "JSON encoding is slow, the responses are big" | Swapped in a faster JSON library | CPU −3%, p99 unchanged |
| "It's the database" | Added a Redis cache in front of the rates query | p99 unchanged. The 6.4b log line showed `db_ms` was 9 of 310 |
| "The instances are too small" | Doubled the instance size | CPU fell to 38%, the bill doubled, p99 fell to 240 ms |

Then someone took a 30-second CPU profile from one production instance. The top of it read:

```
      flat  flat%        cum   cum%
     0.9s   6.1%      6.2s  41.3%   regexp.MustCompile
     ...
     0.1s   0.7%      6.3s  42.0%   pricing.validSKU
     2.1s  14.0%      2.1s  14.0%   runtime.gcBgMarkWorker
     0.4s   2.7%      2.7s  18.0%   fmt.Sprintf
     0.3s   2.0%      0.9s   6.0%   encoding/json.(*encodeState).marshal
```

41% of all CPU was spent compiling the same regular expression, on every call, inside a validation function added in a refactor two months earlier. Another 18% went to building cache keys with `fmt.Sprintf`. Both allocated heavily, which explains much of the 14% spent in the garbage collector.

The JSON encoder had been 6% of CPU the whole time. Making it twice as fast could save at most 3%, and that's what happened. This is Amdahl's law applied to a guess: **the gain from speeding up one part is capped by that part's share of the total.** The team spent two weeks optimizing parts whose shares nobody had measured.

Moving the regex to a package-level variable took one line. Fleet CPU fell from 70% to 36% on the *original* instance size, and p99 returned to 90 ms.

## What It Is

**Profiling** is measuring where a program spends a resource (CPU time, memory, time spent waiting) and attributing it to the code responsible, using stack traces.

Most production profilers are **sampling profilers.** Many times a second, they interrupt the program, record the current call stack, and let it continue. A function that appears in 30% of the samples was running about 30% of the time. The alternative, an **instrumenting profiler**, records every function entry and exit. That is exact, but the overhead is large enough to change what you are measuring, so it is mostly used on small pieces of code.

Two neighbors are easy to confuse with profiling:

- **Distributed tracing** (Module 19) tells you *which service and which span* the time went to. Once a span says "320 ms inside the pricing service, no child calls," the trace has nothing more to say. The profile takes over from there and tells you which function inside the process was responsible.
- **Benchmarks** measure a function you already chose. A profile tells you which function to choose. Benchmark after profiling, to confirm a fix, not instead of it.

## Recognizing the Problem

- CPU utilization is high, and the per-request log line shows little database or downstream time.
- Trace spans show large gaps with no child spans inside a single service.
- Latency rises with load while every dependency's latency stays flat.
- Optimizations that "should" help don't move the number.
- Instance count or size grows faster than traffic.
- A deploy made things slower and the diff doesn't show why.
- Time spent in garbage collection is a noticeable share of CPU (22.1b covers this case).

## How It Works

### Reading a profile

A profile is a set of stack samples. Every tool shows two numbers per function:

- **Flat (self) time:** samples where this function was the one actually executing.
- **Cumulative time:** samples where this function was anywhere on the stack, meaning it or something it called was executing.

`validSKU` above has 0.7% flat and 42% cumulative. It does almost nothing itself, but it calls something expensive. Sort by cumulative to find the *entry point* responsible for a cost, and by flat to find the *code* where the cost is incurred.

### Flame graphs

A **flame graph** draws the same samples as stacked boxes:

```
[             regexp.compile               ][  json.marshal ]
[             regexp.MustCompile           ][ json.Marshal  ][ fmt.Sprintf ]
[             pricing.validSKU             ][ writeResponse ][ cache.key   ]
[                          pricing.QuoteHandler                            ]
[                          net/http.(*conn).serve                          ]
```

- **Width** is the share of samples. Wide boxes are where time goes.
- **Height** is stack depth. The bottom is the entry point, the top is what was executing.
- **Left-to-right order means nothing.** It's usually alphabetical, not chronological. A flame graph has no time axis.

The thing to look for is a **wide plateau**: a box near the top that is wide and has nothing above it. That is code burning CPU itself. A wide box that is covered by many narrow boxes is a function whose cost is spread across its callees, and the fix is usually further up, for example calling it less often.

A **differential flame graph** compares two profiles, before and after a deploy, and colors the boxes that grew. It is the fastest way to answer "this release got slower, where?"

### On-CPU and off-CPU time

A CPU profile only sees code that is *running on a CPU.* Time spent waiting is invisible to it: waiting on a lock, a channel, a network read, a pool connection, or the scheduler. A request that takes 300 ms, of which 280 ms is waiting for a mutex, looks cheap in a CPU profile.

So "slow" splits into two questions, and each has its own tools:

| Question | Tool |
|---|---|
| What is burning CPU? | CPU profile |
| What is allocating memory, and what is holding it? | Heap and allocation profiles (22.1b) |
| Where are threads blocked waiting? | Block, mutex, and goroutine profiles in Go; thread dumps and lock profiling in Java; off-CPU analysis with eBPF |
| Where is time going across services? | Tracing (Module 19) |

A useful first check before choosing: compare wall-clock time with CPU time for a request. If a request takes 300 ms and uses 15 ms of CPU, a CPU profile won't find the problem.

### How many samples you need

Go's CPU profiler samples 100 times per second per running goroutine. A 30-second profile of a process using one full core yields about 3,000 samples. A function at 1% has about 30 samples, which is enough to see but too few to compare with confidence across two profiles. A function at 0.1% is noise.

The practical rules: profile under real load, profile long enough, and don't draw conclusions from small differences between two single profiles. Profiling an idle development server shows startup code and the profiler itself.

### Continuous profiling

A single profile is a snapshot you have to remember to take, usually during an incident. **Continuous profiling** samples every instance at a low rate all the time, stores the results, and lets you query them by service, version, and time range. Pyroscope, Parca, Google Cloud Profiler, and most APM vendors provide this.

This changes profiling from something you do during an incident into a record you can check afterward. "Which function's CPU share grew between last Tuesday's release and this one?" becomes a query. The regex in the opening story would have appeared as a wide new box in a differential view the day it shipped.

## When It's Appropriate

- CPU is the constraint: utilization is high, or you are paying for cores you can't explain.
- Tracing or the per-request log line shows that the time is spent inside one process.
- A release made a service slower and the diff doesn't make the cause obvious.
- A hot service at scale, where 10% of CPU across 200 instances is 20 instances' worth of money.
- Before any optimization work that isn't already backed by a measurement.

## When It's Unnecessary or Overkill

- **The time is somewhere else.** If the 6.4b log line reads `912 total / 870 db`, you have a query problem, and the profile will show a process mostly idle. Attribute first.
- **The service is I/O-bound and CPU is low.** Reach for tracing, pool-wait metrics, and off-CPU tools instead.
- **There is no number to hit.** Profiling a service that meets its SLO at a reasonable cost produces a list of things you *could* optimize. That list doesn't justify doing any of them.
- **Continuous profiling for a handful of small services.** On-demand profiles cover you until an incident teaches you that you needed yesterday's profile.

## Trade-offs

- **Overhead is small but not zero.** Sampling at 100 Hz typically costs a few percent while active. Continuous profilers keep this low by sampling briefly and rotating across instances. Block and mutex profiling can cost more, depending on the rate you set.
- **Profiles show where, not why.** A wide `regexp.MustCompile` box says compilation is expensive. It doesn't say that it's being called per request, and you have to go read the caller to find out.
- **Inlining and optimization blur stacks.** Compiled code inlines small functions into their callers, so time can be attributed to a caller that doesn't appear to do much. JIT-compiled runtimes add their own distortions (see the Java sibling below).
- **A profiling endpoint is an attack surface.** It reveals code structure, and a long profile request uses resources. It belongs on an internal port.
- **Continuous profiling is another telemetry pipeline** with storage, retention, and cost, like everything in Module 19.
- **Micro-optimizations found by profiling can cost readability.** A 2% gain in a function that runs once a minute is not worth a harder-to-read implementation.

## Alternatives

- **Timing spans and log lines** (Module 19, 6.4b). Coarse and cheap. They tell you which step of a request is slow, which is often enough.
- **Microbenchmarks.** Precise for one function you already suspect. They can't find the function for you.
- **System-wide profilers** such as Linux `perf` and eBPF tools. They see every process, including the kernel and native libraries, and don't require any code changes. They are the right tool when the cost is outside your code, in syscalls, TLS, or compression libraries.
- **APM products** with built-in code-level profiling, which bundle continuous profiling with tracing.
- **Buying bigger machines.** This really is an alternative, and at small scale it's often the cheapest one. In the opening story it cut p99 by less than a quarter and doubled the bill, while a one-line fix did far better.

## How to Achieve It

**Level 0 — know what "slow" means in numbers.** Have a latency target and a per-request attribution line (6.4b) so you know whether the time is in the process at all.
_Signal you're here:_ performance discussions start with "it feels slow."

**Level 1 — on-demand CPU profiles from production, on an internal port.** Take one when CPU or latency looks wrong, and read the top entries by cumulative time.
_Signal you need it:_ the first time a guess about the cause turns out to be wrong.

**Level 2 — confirm fixes with benchmarks and repeated profiles under load.** Benchmark the hot function before and after a change, and take the profile during a load test (22.5) rather than on an idle instance.
_Signal you need it:_ a fix that "should" have helped and didn't.

**Level 3 — profile the waiting, too.** Enable block and mutex profiling at a modest rate, and learn to read goroutine dumps.
_Signal you need it:_ requests that are slow while CPU is low.

**Level 4 — continuous profiling with release comparisons.** Keep profiles for every service and compare them per release.
_Signal you need it:_ regressions you find weeks after the release that caused them.

**Level 5 — feed production profiles back into the build.** Go's profile-guided optimization (PGO) uses a representative CPU profile to guide inlining and other decisions. Typical gains are a few percent, for the cost of committing and refreshing one file.
_Signal you need it:_ a large fleet where a few percent of CPU is real money, and the obvious hot spots are already fixed.

## Implementation

Go, because its profiler is part of the standard library and exposing it takes a few lines. That makes it easy to see exactly what you're turning on.

### Exposing profiles safely

```go
import (
    "net/http"
    "net/http/pprof"
    "runtime"
    "time"
)

func startDebugServer() {
    // Block and mutex profiles are off by default. These rates are illustrative:
    // report about 1 in 5 mutex contention events, and sample roughly one
    // blocking event per millisecond spent blocked.
    runtime.SetMutexProfileFraction(5)
    runtime.SetBlockProfileRate(int(time.Millisecond))

    mux := http.NewServeMux()
    mux.HandleFunc("/debug/pprof/", pprof.Index)
    mux.HandleFunc("/debug/pprof/profile", pprof.Profile)
    mux.HandleFunc("/debug/pprof/symbol", pprof.Symbol)
    mux.HandleFunc("/debug/pprof/trace", pprof.Trace)

    // Internal interface only; never the public listener.
    go http.ListenAndServe("127.0.0.1:6060", mux)
}
```

> **Aside: the one-line version has a trap.** The common idiom is `import _ "net/http/pprof"`. That import registers the profiling handlers on `http.DefaultServeMux`. If your application also serves its public API from `DefaultServeMux`, which many small services do, your profiling endpoints are now public. Registering them on a separate mux, as above, avoids that.

Taking and reading a profile:

```bash
# 30 seconds of CPU samples from a production instance, opened in a browser UI
go tool pprof -http=:8081 'http://10.0.4.17:6060/debug/pprof/profile?seconds=30'

# Where are goroutines blocked right now? (debug=2 prints full stacks)
curl -s 'http://10.0.4.17:6060/debug/pprof/goroutine?debug=2' | less

# Compare two saved profiles: what grew?
go tool pprof -http=:8081 -diff_base=before.pb.gz after.pb.gz
```

### The bug and the fix

```go
// Before: compiles the pattern on every call. The function looks trivial,
// which is why nobody suspected it.
func validSKU(s string) bool {
    re := regexp.MustCompile(`^[A-Z]{3}-\d{4,8}$`)
    return re.MatchString(s)
}

// After: compiled once, at package initialization.
var skuPattern = regexp.MustCompile(`^[A-Z]{3}-\d{4,8}$`)

func validSKU(s string) bool { return skuPattern.MatchString(s) }
```

Confirming the fix with a benchmark:

```go
func BenchmarkValidSKU(b *testing.B) {
    for b.Loop() { // Go 1.24+; use a `for i := 0; i < b.N; i++` loop on older versions
        validSKU("HTL-00421")
    }
}
```

```bash
go test -bench=ValidSKU -benchmem -count=10 > old.txt   # on the old code
go test -bench=ValidSKU -benchmem -count=10 > new.txt   # on the new code
benchstat old.txt new.txt
```

```
            │   old.txt    │              new.txt               │
            │    sec/op    │   sec/op     vs base               │
ValidSKU-8    4.12µ ± 2%     0.14µ ± 1%  -96.60% (p=0.000 n=10)

            │   old.txt    │              new.txt               │
            │  allocs/op   │  allocs/op   vs base               │
ValidSKU-8     31.00 ± 0%     0.00 ± 0%  -100.00% (p=0.000 n=10)
```

> **Aside: run benchmarks more than once and compare with statistics.** A single run of each version can differ by 5–10% from noise alone: CPU frequency scaling, other processes, and thermal throttling. `benchstat` reports the variation and whether the difference is significant. A benchmark that says "3% faster" from one run hasn't told you anything.

The benchmark measures the function. The profile under production load is what confirms that the function mattered. Take a second profile after deploying: `validSKU` should have disappeared from the top of the list, and the garbage collector's share should have dropped too, since 31 allocations per call are gone.

## Further Reading

- **Brendan Gregg, "The Flame Graph"** (ACM Queue / CACM, 2016), and his flame graph pages, including off-CPU and differential flame graphs. The original explanation, and still the clearest one.
- **Brendan Gregg, _Systems Performance_** (2nd ed.), the chapters on CPUs and methodology. It covers on-CPU versus off-CPU analysis and the USE method, which tell you which kind of profile to reach for.
- **The Go documentation: "Diagnostics"** and **"Profile-guided optimization."** The first covers all of Go's profile types and what each measures; the second explains when PGO pays off and how to keep the profile representative.
- **The `pprof` README and the `go tool pprof` help text.** The options for focusing, ignoring, and comparing profiles are worth reading once.
- **Mytkowicz, Diwan, Hauswirth, and Sweeney, "Evaluating the Accuracy of Java Profilers"** (PLDI 2010). Shows that different profilers can disagree about the hottest method in the same program. It's the reason to treat any single profiler's output with some suspicion.
- **Pyroscope and Parca documentation**, for how continuous profiling stores and queries profiles across a fleet.
- **Module 19** (tracing) for the step before this one, and **22.5** for the load under which profiles should be taken.

A **Java sibling** would be worth writing, because the JVM changes the story in ways Go hides. Traditional JVM profilers can only sample threads at *safepoints*, which biases results toward certain code. async-profiler avoids this, and the JIT compiler changes which code is hot as the program warms up, so a profile taken in the first minute describes a different program from the one running an hour later. Not yet written.

The habit to take away: **before optimizing anything, find out what share of the total it is.** No improvement to a part can save more than that part costs.
