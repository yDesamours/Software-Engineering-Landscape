# Where the Memory Goes

_Module 22.1b — Performance Profiling_

## The Problem

An accounting SaaS has a reporting service written in Java with Spring Boot. Customers export ledgers, trial balances, and aged-receivables reports as CSV files. It runs in containers with a 6 GiB memory limit and `-Xmx4g`.

Two symptoms appear in the same month:

1. **Latency spikes.** p99 for *every* endpoint on an instance, not just exports, jumps to around 1.8 s every 30 to 60 seconds during business hours. The GC log shows the cause: normal young-generation pauses of 20–40 ms, then occasional full collections of about 1.4 s.
2. **Crashes.** Every six days or so, each pod is killed with `OOMKilled` and restarts.

The team concludes that the service needs more memory. They raise the heap to 8 GiB and the container limit to 10 GiB. A month later:

- Pods are killed every twelve days instead of six.
- The full collections now pause for 2.9 s instead of 1.4 s.

More memory halved the crash rate and doubled the worst pause. That result is the clue: **there are two different memory problems here, and adding memory affects them in opposite directions.**

**Problem one: churn.** An allocation profile of the export endpoint shows it allocating about 2.2 GB per second while an export runs. It builds the whole report in memory as a `List<Map<String, Object>>` before writing any of it. A 250,000-row, 30-column export is 7.5 million map entries with boxed values, which is close to a gigabyte of live objects while the report is being built. Those objects live long enough to be copied into the old generation, where only expensive collections can reclaim them.

**Problem two: a leak.** A heap dump shows one object retaining 2.3 GB, a static `ConcurrentHashMap` used to cache compiled report templates. Its key includes the report's filter as JSON, and the filter includes a date range. Almost every export creates a new key, and nothing is ever removed. The map grows by about 600 MB a day. With a 4 GiB heap it fills in six days; with 8 GiB, in twelve.

A bigger heap gives the leak more room, so the crash takes longer to arrive. It also gives the full collector more live data to trace, so each full collection takes longer.

## What It Is

**Memory profiling** attributes memory to the code responsible for it. There are two different questions, and they need two different kinds of profile:

- **Who is allocating?** An **allocation profile** samples allocations and records the stack that made each one. It shows *churn*: objects created and discarded at a high rate. Churn costs CPU (22.1a showed the garbage collector at 14%) and causes frequent collections.
- **Who is holding on?** A **heap profile**, or a full **heap dump**, shows what is live right now and what keeps it alive. It shows *retention*: objects that should have become garbage but are still reachable. When retention grows without bound, you have a leak.

A leak in a garbage-collected language is not memory the runtime forgot about. It's memory the program can still reach: from a static field, a cache, a listener list, a thread-local, or a queue that nobody drains. The collector is working correctly, because the object really is reachable.

## Recognizing the Problem

- A memory graph where the level *after* each collection keeps rising (a leak).
- A memory graph with a flat floor but very frequent collections (churn).
- Periodic latency spikes that affect every endpoint on an instance, not one endpoint.
- The garbage collector's share of CPU is above roughly 5–10%.
- Containers killed with `OOMKilled`, sometimes with no Java `OutOfMemoryError` in the logs.
- Process memory (RSS) well above the configured heap size.
- Restarting "fixes" the problem for a predictable number of days.
- Raising the heap delays crashes without stopping them.

## How It Works

### Two shapes of the same graph

Heap usage over time, for each problem:

```
Churn: steep sawtooth, flat floor          Leak: rising floor

heap                                        heap
4G |                                        4G |                     /|  OOM
   |  /| /| /| /| /| /| /| /| /|               |              /|  /| / |
   | / |/ |/ |/ |/ |/ |/ |/ |/ |               |       /|  /| / | / |/
   |/  '  '  '  '  '  '  '  '  '               |  /|  / | / |/  |/
1G |_______________________________         1G | / | /  |/
   +------------------------------> time       +------------------------------> time
    collections every few seconds               each collection recovers less
```

The **floor**, meaning heap usage right after a collection, approximates the live set. A flat floor means retention is stable, and the problem, if any, is the rate. A rising floor means something is accumulating.

### Why churn is not free

Most collectors are **generational**. They rely on the observation that most objects die young, so they collect the young generation often and cheaply. For a copying collector, the cost of a young collection depends mostly on how many objects *survive*, not how many die.

This gives you two different kinds of allocation:

- Objects that die within one request are nearly free to collect.
- Objects that live for a few seconds and then die are expensive. They survive several young collections, get copied each time, get *promoted* into the old generation, and can only be reclaimed there by the collections that cause long pauses.

The export in the opening story is the second kind: a gigabyte of objects that live for as long as the export takes. So "allocate less" is incomplete advice. Allocations that die immediately cost little. The expensive allocations are large structures that live for a medium length of time, and the fix is usually to not materialize them: stream the data instead.

### Finding what keeps a leak alive

A heap dump is a snapshot of every live object and every reference between them. Two concepts make it readable:

- **Retained size:** the memory that would be freed if this object became unreachable. A `HashMap` with a shallow size of 48 bytes can retain 2.3 GB.
- **Dominator tree:** object A *dominates* object B if every path from the GC roots to B goes through A. Sorting the dominator tree by retained size puts the few objects responsible for most of the heap at the top.

Once you have the suspect, the **path to GC roots** shows *why* it is still alive, for example: static field `TemplateCache.CACHE` → `ConcurrentHashMap` → 1.9 million entries.

A single dump can mislead, because a big cache might be big on purpose. **Two dumps taken hours apart** answer the real question, which is what grew.

### Heap is not the whole process

In a container, the kernel kills the process when its total memory exceeds the limit, and it doesn't care how much of that was heap. A JVM process also uses memory for:

- metaspace (class metadata);
- thread stacks (one per thread; hundreds of threads add up);
- direct byte buffers, which networking libraries such as Netty use heavily;
- the JIT compiler's code cache;
- the garbage collector's own data structures.

A container with a 6 GiB limit and a 6 GiB heap *will* be killed eventually. If the process is killed with `OOMKilled` and there is no Java `OutOfMemoryError` in the logs, the memory growth was probably outside the heap, or the heap was sized too close to the limit.

The JVM reads the container's memory limit and, by default, sizes the maximum heap to 25% of it (`-XX:MaxRAMPercentage=25`). That default is conservative for a container dedicated to one JVM. Something like 60–75% is common, which leaves the rest for non-heap memory.

### Choosing what to trade

Garbage collectors trade among three things: **pause time**, **throughput** (the share of CPU left for your code), and **memory overhead**. You can improve any two at the cost of the third.

- **G1**, the default, balances the three and aims for a configurable pause target.
- **ZGC** keeps pauses in the low milliseconds regardless of heap size, and pays with more CPU and a larger heap.
- **Parallel GC** maximizes throughput and accepts long pauses, which suits batch jobs.

Changing collectors can fix a pause problem. It cannot fix a leak, and it only hides churn.

## When It's Appropriate

- Memory usage after collections rises over hours or days.
- GC pauses show up in latency, or the collector's CPU share is significant.
- Containers are killed for memory, or memory limits keep being raised.
- Endpoints that handle large results: exports, reports, bulk imports, and anything that returns "all of" something.
- Before load-testing for hours (22.5): a soak test is how you find leaks before production does.

## When It's Unnecessary or Overkill

- **A flat floor, a low GC share, and latency within target.** A busy sawtooth is simply what a healthy generational collector looks like.
- **Object pooling to "reduce allocation"** of short-lived objects on a modern JVM. Pools turn cheap, short-lived objects into long-lived ones (the expensive kind), and bring back use-after-release bugs that the garbage collector had eliminated. Pools are justified for objects that are expensive to *create*, such as connections and large direct buffers, not for ordinary objects.
- **Collector flag tuning before fixing the code.** If the allocation profile shows a gigabyte-sized report built in memory, no flag fixes that.
- **Heap dumps of a service that restarts daily by design** and never gets close to its limit.

## Trade-offs

- **Heap dumps are expensive and sensitive.** Taking one pauses the JVM for a time that grows with heap size. The file is about as large as the live heap. It also contains *everything in memory*: customer records, tokens, and credentials. Treat a heap dump like a production database export (Module 34, and 19.1's PII handling): restricted access, encrypted storage, and deletion when the investigation ends.
- **Allocation sampling has a cost.** JFR's allocation sampling is designed for production, but higher sampling rates cost more, and older instrumenting allocation profilers are too slow to use in production.
- **A larger heap is a trade, not a fix.** Collections happen less often, but full collections take longer, and a leak takes longer to show up, which means it gets found later.
- **Low-pause collectors cost CPU and memory headroom.** Moving to ZGC can require a bigger heap and more cores for the same traffic.
- **Streaming instead of materializing makes code less convenient.** You can't sort, total, or retry what you've already written. Some reports really need the whole data set, and for those the answer is usually to do the work in the database, or to move it to a background job (Module 10).
- **Bounded caches evict.** Fixing the leak by limiting the cache means some lookups miss and recompute. That is the correct trade, and it should be sized deliberately (Module 13).

## Alternatives

- **Restart on a schedule.** Honest, cheap, and common as a stopgap. It does not tell you what is leaking, and the schedule has to stay ahead of the growth rate.
- **Memory metrics and GC logs only** (16.3). These show that there is a problem and what kind (churn or leak). They don't show where it is.
- **Moving the work out of the request path** (Module 10). Large exports as background jobs that write to object storage (Module 11) remove the memory spike from the latency-sensitive path entirely.
- **Pushing aggregation into the database** (Module 6). A total computed in SQL doesn't need a million rows in the application's memory.
- **A different collector.** Sometimes the correct fix for a pause problem, as long as the allocation profile has already been checked.

## How to Achieve It

**Level 0 — GC logs and a memory graph that shows the floor.** Turn on unified GC logging and graph heap usage after collections, not just total usage.
_Signal you're here:_ nobody can say whether memory is growing.

**Level 1 — size the heap for the container.** Set the heap as a percentage of the container limit, leave room for non-heap memory, and write a heap dump automatically on `OutOfMemoryError`, to a restricted location.
_Signal you need it:_ `OOMKilled` without an `OutOfMemoryError`, or a heap fixed at a size that ignores the container limit.

**Level 2 — allocation profiling with JFR under real load.** Find the top allocating stacks, and look first for large structures that live for a medium length of time.
_Signal you need it:_ GC time is a visible share of CPU, or pauses show up in latency.

**Level 3 — compare heap dumps to find leaks.** Take two dumps hours apart and compare the dominator trees.
_Signal you need it:_ a rising floor, or crashes on a schedule.

**Level 4 — native memory tracking.** Turn it on when RSS and heap diverge.
_Signal you need it:_ RSS well above heap, or container kills with a healthy heap.

**Level 5 — continuous allocation profiling and soak tests in CI.** Keep allocation profiles per release, and run an hours-long load test that fails if the post-GC floor keeps rising.
_Signal you need it:_ leaks that reach production through releases more than once.

## Implementation

Java, because the JVM's memory tooling (JFR, `jcmd`, and heap dump analyzers) is the most complete of any mainstream runtime, and all of it ships with the JDK.

### Seeing what the collector does

```bash
java \
  -XX:MaxRAMPercentage=70 \
  -Xlog:gc*:file=/var/log/app/gc.log:time,uptime,level,tags:filecount=5,filesize=20m \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/secure-dumps/ \
  -XX:NativeMemoryTracking=summary \
  -jar reporting.jar
```

`NativeMemoryTracking` has some overhead. Enable it when you're investigating native memory, not permanently.

### Finding the churn

```bash
# 2 minutes of the JDK's "profile" settings, which include allocation sampling
jcmd <pid> JFR.start name=alloc settings=profile duration=120s filename=/tmp/alloc.jfr

# Raw allocation samples with stacks
jfr print --events jdk.ObjectAllocationSample --stack-depth 10 /tmp/alloc.jfr | less
```

JDK 21 added `jfr view`, which prints prebuilt summaries of a recording. Run it with no arguments to list the views your JDK provides. JDK Mission Control opens the same file in a GUI with allocation flame graphs.

The code the profile pointed at:

```java
// Before: materializes the entire report, then writes it.
public void export(ReportRequest req, Writer out) {
    List<Map<String, Object>> rows = jdbc.queryForList(sql(req), params(req)); // ~1 GB for a big tenant
    for (Map<String, Object> row : rows) {
        out.write(formatRow(row)); // String.format per cell: more churn
    }
}
```

```java
// After: rows flow from the database cursor to the output, one at a time.
@Transactional(readOnly = true)   // see the aside: the transaction is required
public void export(ReportRequest req, Writer out) {
    jdbc.setFetchSize(1_000);     // illustrative; set this on a dedicated JdbcTemplate
    jdbc.query(sql(req), rs -> {  // RowCallbackHandler: called once per row
        writeRow(rs, out);        // writes each cell straight to the Writer
    }, params(req));
}
```

> **Aside: the PostgreSQL JDBC driver ignores the fetch size unless autocommit is off.** With autocommit on, it reads the *entire* result set into memory before returning the first row, and the "streaming" version allocates exactly what the old one did. That's why the method runs inside a transaction. This is a good example of why you verify a memory fix with a second allocation profile instead of trusting the code change.

### Finding the leak

```bash
# Quick look: instance counts and bytes per class. Triggers a full GC first
# (add -all to skip the GC and include unreachable objects).
jcmd <pid> GC.class_histogram | head -20

# Full dump of live objects. Pauses the JVM, produces a file about the size of the
# live heap, and contains production data.
jcmd <pid> GC.heap_dump /secure-dumps/reporting-$(date +%s).hprof
```

Open two dumps, taken hours apart, in Eclipse MAT (or a similar analyzer) and compare their dominator trees. In this case, the top entry in both is the same map, and it grew from 1.1 GB to 2.3 GB.

```java
// Before: unbounded, and the key is effectively unique per export.
private static final Map<String, CompiledTemplate> CACHE = new ConcurrentHashMap<>();

String key = tenantId + ":" + locale + ":" + toJson(filter);   // filter includes dates

// After: key only on what affects compilation, and bound the cache.
private final Cache<TemplateKey, CompiledTemplate> cache = Caffeine.newBuilder()
        .maximumSize(10_000)
        .expireAfterAccess(Duration.ofHours(6))
        .recordStats()                        // so the hit rate is visible (Module 13)
        .build();

record TemplateKey(String tenantId, Locale locale, String templateVersion) {}
```

The bounding matters, but the key fix matters more. The date range never affected the compiled template, so every entry after the first for a given template was a duplicate. Including a field in a cache key that doesn't affect the cached value is one of the most common ways to build a leak.

### When RSS and heap disagree

```bash
jcmd <pid> VM.native_memory summary
```

This breaks down the process's committed memory by category (Java heap, class metadata, threads, code, GC, internal, and others). If the heap is 2.8 GB and the process is 5.9 GB, this output shows where the rest went.

## Further Reading

- **The JDK's JFR documentation and the `jfr` and `jcmd` tool references.** Everything in the Implementation section comes from these, and both tools are part of every modern JDK.
- **Oracle's "HotSpot Virtual Machine Garbage Collection Tuning Guide."** Explains G1, ZGC, and Parallel GC, their goals, and which flags matter.
- **Eclipse Memory Analyzer (MAT) documentation**, especially dominator trees, retained sizes, and the "Leak Suspects" report.
- **Richard Jones, Antony Hosking, and Eliot Moss, _The Garbage Collection Handbook_** (2nd ed.). The reference for why generational collection works and what each collector trades.
- **Aleksey Shipilëv's "JVM Anatomy Quarks"** series. Short, precise articles on specific JVM memory behaviors, including allocation and object layout.
- **The PostgreSQL JDBC driver documentation, "Getting results based on a cursor."** The conditions under which the fetch size is honored.
- **Module 13** for sizing and observing bounded caches, and **Module 10** for moving large exports out of the request path.

A **Go sibling** would be worth writing, because Go changes both levers. Escape analysis decides whether a value goes on the heap at all, and `go build -gcflags=-m` shows you those decisions. The garbage collector isn't generational, and it's tuned with just two settings, `GOGC` and `GOMEMLIMIT`, the second of which exists largely because of the container problem described above. Not yet written.

The habit to take away: **when memory is the problem, first decide whether the issue is objects being created too fast or objects not being released.** The two look alike on a dashboard and need opposite fixes.
