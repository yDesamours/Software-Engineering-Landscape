# The Connection Lifecycle

_Module 9.1b — Real-Time Communication_

## The Problem

A field-service dispatch product. Technicians carry a phone app that streams location every three seconds and receives job assignments; dispatchers watch a map of everyone. WebSockets, both directions, and it works beautifully in development.

Four production incidents, all in the first month, none of them in your message handling.

**The technician who was never disconnected.** A van drives into an underground car park. The phone's radio drops. Nothing tells the server: TCP has no idea a peer has vanished until it tries to send and the retransmits eventually fail, and Linux's default keepalive doesn't start probing for **two hours** — and is usually not enabled on the socket anyway. So the server's connection sits in `ESTABLISHED`, the dispatcher's map shows the technician parked at the entrance, and the assignment sent at 11:04 goes into the void with no error. The phone, meanwhile, also reports `readyState === OPEN`. Both ends believe in a connection that does not exist.

**The reconnect that lost three jobs.** A different technician, a tunnel, eight seconds. The app reconnects immediately and cleanly. But the new connection starts empty — it's a new socket, the server has no idea it's the same person, and the three assignments dispatched during those eight seconds were written to a socket that was closing. She sits idle for twenty minutes while dispatch assumes she's working.

**The deploy that took itself down.** 14:00, rolling restart, three pods. Twelve thousand phones lose their connection within the same second and every one of them retries after exactly one second, because that's what the reconnect code says. The new pods take 12,000 simultaneous upgrade requests, each doing a token verification and a session lookup. Latency climbs, the clients' five-second connect timeout fires, and they all retry again — now faster, because the retry counter reset on what looked like a fresh failure. The outage lasts eleven minutes and nothing was wrong with the new build.

**The dispatcher on hotel wifi.** One dispatcher subscribed to all 500 technicians, so roughly 170 messages a second. Her uplink can't absorb it. The server's outbound buffer for that one socket grows, and grows, and the fan-out loop — the one that writes to every dispatcher — starts blocking on her. Now every dispatcher is behind, and server memory is climbing at 40MB a minute. **Your memory and your latency have become functions of your worst client.**

There's a fifth, quieter one. The app's access token expires after eight hours, and the server correctly closes the socket. The client sees a disconnect with no information — close code `1006`, which means "it just ended" — so it does the only thing it knows how to do: reconnect. Which fails. Which it retries. Forever, until the user force-quits. The server was trying to say *refresh your token*, and the transport had no way to carry that sentence.

None of this is exotic. It is the standard set, and it has one cause: **HTTP came with a lifecycle and WebSockets don't.** A request begins, ends, reports a status, and releases everything it held — the framework does that for you, and it's why you never thought about it. A socket gives you `open` and `close` and nothing in between. Every property you were relying on is now something you write.

## What It Is

What's missing is a **session over the connection**, and the discipline is **connection lifecycle management**: liveness detection, a close vocabulary, a reconnect policy, resumption, and a backpressure policy.

The distinction that organizes everything below:

> The **connection** is transport. It will die, repeatedly and without warning, and that is normal rather than exceptional.
> The **session** is the user's continuous experience, and it has to survive an unbounded number of connections.

A technician on a six-hour shift might have forty sockets. If your server treats each one as a fresh start, the product is broken in a way no amount of message-handling correctness can fix.

One protocol detail worth clearing up now, because it drives the design: RFC 6455 includes ping and pong **control frames**, and they work — but browsers don't expose them to JavaScript. A browser will automatically pong a server's ping, and it cannot initiate one. So server-side liveness detection (is this client still there?) can use protocol pings; client-side liveness detection (is this *server* still there?) needs either an application message or a silence timer. Asymmetric, and the asymmetry is why most client libraries have their own heartbeat on top.

## Recognizing the Problem

- Your connection count is higher than your plausible user count, and it only resets on deploy.
- A user says "it just stops updating" and there is no error anywhere, on either side.
- Reconnection works, and something that happened during the gap is missing.
- Every deploy produces a latency spike shaped like a spike, not a ramp.
- Memory grows over the day and drops to zero on restart, and heap profiles point at outbound buffers.
- One slow client demonstrably affects other clients.
- Your client's reconnect logic is `setTimeout(connect, 1000)`.
- Close code `1006` is the only close code in your logs.
- A logged-out or downgraded user keeps receiving messages until they close the tab.
- Nobody can say what happens if the same user opens the app on two devices.

## How It Works

### The handshake is the last moment HTTP is helping you

The upgrade is an ordinary HTTP request: cookies, headers, TLS, your existing auth middleware, your rate limiter. Everything after it is not. So the handshake is where authentication belongs — read the cookie or the token, resolve the user and tenant, attach them to the connection, and reject with a normal HTTP status if it fails, because that's the last time a status code is available to you.

Two things bite here specifically:

**There is no same-origin policy on WebSockets.** A page on `evil.example` can open a socket to your origin and the browser will attach your cookies, because the `Upgrade` request is not subject to CORS. Nothing stops it except you: **validate the `Origin` header at the handshake, explicitly.** This is cross-site WebSocket hijacking, and it is the most common serious WebSocket vulnerability precisely because the defence that protects your REST endpoints doesn't apply here.

**`EventSource` and `WebSocket` both refuse custom headers.** No `Authorization` on the upgrade from a browser. The options are a cookie, or a short-lived single-use ticket fetched over HTTPS and passed as a query parameter (accepting that it lands in access logs, hence single-use and 30-second expiry), or an authentication message sent as the first frame after connecting — in which case the server must refuse to do anything else until it arrives, and time out connections that never authenticate.

### Close codes are the only structured thing left

When a socket closes properly, the closing side can send a code and a short reason. RFC 6455 defines a handful — `1000` normal, `1001` going away (use this on deploy), `1011` internal error — and reserves `4000–4999` for you.

`1006` is special and worth knowing: it is never transmitted. It's what your local end reports when the connection died without a close frame ever arriving — a dropped radio, a killed process, a proxy timeout. **`1006` means "I don't know," and it's the only thing you'll see for genuine network failures.**

That makes your `4xxx` codes load-bearing, because they're how the server tells a client what to do next:

```
4001  authenticate first, you sent something else
4401  token expired          → refresh, then reconnect immediately
4403  no longer permitted    → do not reconnect; show the login screen
4008  too slow               → reconnect and resynchronize from scratch
4029  too many connections   → reconnect after a long delay
1001  going away (deploy)    → reconnect with jitter, resume from your cursor
1006  (no frame)             → back off and retry; assume nothing
```

That table is the fifth incident, fixed. The client's reconnect logic needs exactly one thing from the transport — *should I try again, and how soon* — and this is the only place to put it.

### Liveness: making a half-open connection fail

```
   normal                          half-open
   ──────                          ─────────
   client ──── msg ───► server     client  ✗    ✗    server
   client ◄─── msg ──── server       (radio gone)
                                    both ends: readyState OPEN
                                    TCP: ESTABLISHED, no error, for hours
```

The mechanism that fixes this is one idea, applied on both sides: **treat silence as failure.**

Server side: send a ping every ~25 seconds, and keep a read deadline about 2.5× that far in the future. Every pong received pushes the deadline out. If pongs stop, the deadline fires, the read fails, and a half-open socket has become an ordinary disconnect that your existing cleanup path handles. No extra timers, no reaper goroutine scanning connections.

Client side: if nothing at all has arrived for two heartbeat intervals, stop trusting `readyState`, close the socket yourself, and reconnect. Browsers will not do this for you, and `readyState === OPEN` is exactly as trustworthy as the server's `ESTABLISHED` was.

Pick the interval below the most aggressive idle timeout in the path — 25 seconds clears the common 30-second proxy defaults and the 60-second load balancer defaults with room. There is a cost: on mobile, every heartbeat wakes the radio. Two pings a minute is fine; two a second is a battery complaint.

### Reconnection is a policy, not a retry

Three rules, and the third is the one that's usually missing.

**Back off exponentially, with jitter.** 12,000 clients reconnecting at the same instant is a self-inflicted denial of service, and the fix is not "a longer delay" — it's *randomness*, because a fixed delay reconnects the same herd, just later. Full jitter — sleep a random duration between zero and the current cap — spreads the herd across the window and is what you want:

```
attempt 1:  random(0, 1s)
attempt 2:  random(0, 2s)
attempt 3:  random(0, 4s)          cap at ~30s
```

**Reset the counter on a connection that *worked*, not on one that opened.** This is the deploy incident's real bug: the client counted "connected" as success, but the connection failed immediately afterwards, so the backoff never grew. Reset after the connection has been alive and authenticated for, say, ten seconds.

**Let the close code decide whether to retry at all.** A client that retries a `4403` forever is generating load that can never succeed, and the user is staring at a spinner instead of a login screen.

### Resumption: the session outliving the socket

Reconnecting isn't the goal; arriving back at the correct state is. Same idea as 9.1a's cursor, now something you have to carry yourself because WebSockets have no `Last-Event-ID`.

Give every server→client message a per-session sequence number. The client remembers the last one it processed and sends it on the next connect:

```
→ {"type":"hello","resume":"sess_9f2","last_seq":4471}
← {"type":"resumed","from":4472}       … then 4472, 4473, 4474
   or
← {"type":"resync"}                    … then a full snapshot, seq restarts
```

Two things make this work in practice.

**The replay buffer is bounded**, so "you're too far behind" is a normal outcome, not an error. Keep the last few thousand messages or the last five minutes per session; beyond that, send a snapshot of current state instead of a delta. Systems that lack the snapshot path end up keeping unbounded history to avoid ever needing it, which is how a reconnect design becomes a memory leak.

**The client can detect gaps before the server can fix them.** Even with no replay capability at all, a client that notices `4471 → 4473` knows it missed something and can request a full refresh. That's a genuinely useful half-step: it converts silent wrongness into visible, recoverable wrongness, and it's a day of work.

### Backpressure: choosing what to drop

The dispatcher on hotel wifi is not an edge case; it's arithmetic. Your producer's rate is set by the world, and one consumer's rate is set by their uplink. When they differ, something must give, and *you* decide what — because if you don't decide, the default is "buffer forever," which spends your memory and, if the fan-out path blocks, everyone else's latency.

Four policies, and the right one depends on what the messages mean:

- **Block** — never do this in a fan-out loop. It converts one slow consumer into a global stall, and it's the most common real WebSocket outage.
- **Drop oldest** — fine for a firehose of samples, wrong for chat, silently wrong for anything a user acts on.
- **Coalesce by key** — keep only the latest message per technician, per symbol, per cell. Correct and cheap for **state**: a position update supersedes the previous one, so a slow client gets fewer updates, not wrong ones. This should be your default for anything that looks like "current value of X."
- **Disconnect with `4008` and let them resync** — the honest fallback when the queue exceeds its bound and coalescing doesn't apply. Brutal-looking, entirely correct, and bounded.

Notice that coalescing and replay pull in opposite directions: coalescing says messages supersede each other, replay says every message matters. Which one applies is a property of the *stream*, not the connection — which is why real systems label streams and treat them differently on the same socket.

### One writer per connection

A WebSocket connection is not safe for concurrent writes. Two goroutines (or two `send()` calls racing with a library's internal ping) can interleave frames and corrupt the stream. Every design below funnels all outbound traffic — application messages, pings, close frames — through a single writer. That constraint is the reason the per-connection queue exists at all; buffering is a consequence, not the motivation.

## When It's Appropriate

You're already on WebSockets — 9.1a covered that choice. The question here is which parts of this machinery you need, and the answer varies more than the literature suggests.

- **Heartbeats and close codes: always.** Any deployment behind any proxy, on any network. This is a day of work and it removes two of the four opening incidents.
- **Jittered backoff: as soon as you have more than a few hundred clients**, because the trigger is your own deploy and it arrives on a schedule you control.
- **Sequence numbers and gap detection: when a missed message has a consequence.** A dispatched job, a chat message, an order fill. Not needed for a cursor position or a live viewer count.
- **Replay with snapshot fallback: when clients disconnect routinely and reconnect into a long-lived state** — mobile clients, always; office desktops on wired networks, rarely.
- **Coalescing: when your stream is state rather than events**, and especially when fan-out is wide. Map positions, prices, sensor readings, progress percentages.
- **Acknowledgements from the client: only when the server must know a specific message was processed** — a command, a job assignment, a payment. They double your message count and add a retry path; most streams don't need them.

## When It's Unnecessary or Overkill

- **Use SSE and you get two-thirds of this for free.** Automatic reconnection with backoff, `Last-Event-ID` resumption, and no framing to design. If your client→server traffic fits in ordinary requests, the correct response to this entire article is "9.1a, level 2."
- **Ephemeral single-purpose streams.** A socket that exists to stream progress for one four-minute export needs no resume, no replay, no session. If it drops, reconnect and ask for the current percentage.
- **Data with no history worth replaying.** Live cursors, presence dots, typing indicators. Late is worse than missing. Building a replay buffer for them is work that makes the product worse.
- **A managed service or a mature framework.** Phoenix Channels, Socket.IO, Centrifugo, Ably, Pusher — all of them have shipped this, and their versions have been debugged by more people than yours will be. Writing it yourself is justified by a genuine constraint, not by the belief that it's a weekend.
- **Internal tools on a LAN.** Heartbeats, and stop.

## Trade-offs

**You have written a protocol, and protocols have versions.** Your envelope, your close codes, your resume handshake are now a contract with an installed base of mobile apps you don't control. Adding a field is easy; changing the meaning of `4008` two years from now is not. Version the envelope from message one.

**Heartbeats cost the client.** Every ping wakes a mobile radio. The interval is a negotiation between proxy timeouts (shorter) and battery (longer), and there's no setting that's right for both a phone and a wall display.

**The replay buffer is memory priced in convenience.** Per session, times concurrent sessions, times retention. It is also the thing most likely to be sized once at launch and never revisited, which is how it becomes an incident during your next traffic peak.

**Jittered backoff means someone reconnects late.** Spreading 12,000 clients over 30 seconds protects the server by making the unluckiest user wait 30 seconds. That's the right trade, and it's still a trade — the fix when it matters is a shorter cap for the first attempt, not removing the jitter.

**Backpressure policy is user-visible.** Coalescing means a client on a bad connection sees fewer intermediate states; dropping means it sees an inconsistent history; disconnecting means it sees a spinner. You are choosing which degradation your worst-connected users experience, so choose deliberately rather than discovering it from a support ticket.

**Debuggability is genuinely worse.** You can't `curl` a resume handshake. Reproducing "duplicate assignment after reconnect during a deploy" needs a test harness that can sever connections on demand, and you will build it after the first incident rather than before.

**Every one of these mechanisms is state on a server**, which is the same bill 9.1a introduced: connections are no longer interchangeable and deploys are no longer free.

## Alternatives

- **SSE plus ordinary POSTs.** The strongest alternative and the one most teams should take first: the browser implements reconnection and resumption, and you write neither.
- **MQTT**, usually over WebSockets in a browser. Worth knowing because it addresses exactly this article's problems in a published spec rather than in your codebase: persistent sessions that survive disconnects, QoS levels 0/1/2 giving you at-most-once through exactly-once, and session expiry as a protocol field. If your product is fleets of intermittently-connected devices, this is a serious option rather than an exotic one.
- **A framework that owns the lifecycle** — Phoenix Channels, Socket.IO, Action Cable, SignalR, Centrifugo. You inherit their heartbeat, their reconnect policy, and their resume semantics, which is the point; verify the resume semantics specifically, because that's the part implementations differ on most.
- **A managed realtime provider** (Ably, Pusher, PubNub, Supabase Realtime). Moves the stateful tier out of your deployment entirely — no connection drain on deploy, no fan-out backplane to run. You pay per connection-minute and per message, and you inherit someone else's availability.
- **gRPC bidirectional streaming**, for non-browser clients. Gives you framing, flow control (HTTP/2's, which is real backpressure rather than a policy you invent), and codegen. Browser support requires a proxy, which is usually the disqualifier.

## How to Achieve It

Ordered by value per day of work. Most products should do the first three and stop until something forces the rest.

**Level 0 — say why you closed, and prove you're alive.** Server ping with a read deadline, client silence timer, and a documented close-code table. Removes ghost connections and infinite reconnect loops. Two days.
*Next when:* you deploy and watch the reconnect spike.

**Level 1 — reconnect policy.** Full jitter, capped, counter reset on a connection that survived ten seconds, and `shouldRetry(closeCode)`. One day, entirely on the client.
*Next when:* someone reports missing something that happened while they were away.

**Level 2 — sequence numbers and gap detection.** Number every server→client message; the client tracks the last one and requests a full refresh when it sees a gap. No server-side buffer yet. This converts silent data loss into a visible, self-healing refresh.
*Next when:* full refreshes are too expensive or too frequent to keep doing on every brief drop.

**Level 3 — bounded replay with a snapshot fallback.** The resume handshake, a bounded per-session buffer, and an explicit `resync` when the client is too far behind.
*Next when:* memory or fan-out latency starts tracking your slowest clients.

**Level 4 — per-stream delivery policy.** Bounded outbound queue per connection, coalescing for state streams, drop or disconnect for the rest, acknowledgements only on the streams that command something.

**Level 5 — across nodes.** None of the above survives a second server, because a resume handshake that lands on a different pod finds no buffer and no session. That's 9.1c.

## Implementation

Go, with `gorilla/websocket`, because the read-deadline mechanism and the single-writer constraint are explicit in the API rather than hidden — the liveness design ends up being three lines of timeout configuration rather than a subsystem.

```go
const (
	pingEvery  = 25 * time.Second
	pongWait   = 60 * time.Second   // > 2× pingEvery
	writeWait  = 10 * time.Second
	sendBuffer = 256
)

type conn struct {
	ws   *websocket.Conn
	send chan []byte      // bounded; the only path to the socket
	sess *session         // survives this conn: seq, replay buffer, subscriptions
}
```

The reader, where liveness lives:

```go
func (c *conn) readPump() {
	defer c.close()
	c.ws.SetReadLimit(64 << 10)
	c.ws.SetReadDeadline(time.Now().Add(pongWait))
	c.ws.SetPongHandler(func(string) error {
		return c.ws.SetReadDeadline(time.Now().Add(pongWait))   // ← aside 1
	})

	for {
		_, raw, err := c.ws.ReadMessage()
		if err != nil {
			return                                              // ← aside 2
		}
		c.handle(raw)
	}
}
```

The writer, which is also the only writer:

```go
func (c *conn) writePump() {
	ping := time.NewTicker(pingEvery)
	defer func() { ping.Stop(); c.ws.Close() }()

	for {
		select {
		case msg, ok := <-c.send:
			if !ok {
				c.ws.WriteMessage(websocket.CloseMessage,
					websocket.FormatCloseMessage(1001, "going away"))
				return
			}
			c.ws.SetWriteDeadline(time.Now().Add(writeWait))
			if err := c.ws.WriteMessage(websocket.TextMessage, msg); err != nil {
				return
			}
		case <-ping.C:                                          // ← aside 3
			c.ws.SetWriteDeadline(time.Now().Add(writeWait))
			if err := c.ws.WriteMessage(websocket.PingMessage, nil); err != nil {
				return
			}
		}
	}
}
```

And the fan-out, which is four lines and contains the entire backpressure decision:

```go
func (c *conn) deliver(m Message) {
	b := c.sess.number(m)          // assign seq, append to replay buffer

	select {
	case c.send <- b:
	default:                                                    // ← aside 4
		c.closeWith(4008, "too slow")
	}
}
```

**Aside 1 — the pong handler is the whole liveness mechanism.** Every pong pushes the read deadline 60 seconds out. If the van is in the car park, no pongs arrive, the deadline passes, and `ReadMessage` returns an error. A half-open socket has become a normal disconnect travelling through the normal cleanup path. There is no reaper goroutine, no connection table scan, no separate timer to leak — and the whole thing is two lines. The constraint that makes it work is `pongWait > 2 × pingEvery`, so a single lost ping doesn't kill a healthy connection.

**Aside 2 — this bare `return` is the lifecycle.** Deadline expiry, a TCP reset, a close frame, and a malformed message all arrive here as the same error, which is exactly right: the only correct response to any of them is to run `c.close()` and release the session's connection slot. Resist the urge to branch on error type — log it, then treat them identically, because your client's behaviour is driven by the close code you *sent*, not by the error you *received*.

**Aside 3 — pings go through the same channel discipline as data.** Not because of a Go quirk: concurrent writes to a WebSocket interleave frames on any platform, and a ping written from a background timer while a fan-out goroutine is mid-message produces a corrupted stream and a client that disconnects with a protocol error nobody can reproduce. One writer, always. This is why `send` exists even in designs that never buffer.

**Aside 4 — `default:` *is* your backpressure policy, written down.** Replace it with a plain `c.send <- b` and the fan-out goroutine blocks on the hotel-wifi dispatcher, and every other dispatcher waits behind her — the opening incident, in one character of difference. The version here is the blunt policy (disconnect and force a resync); the coalescing version replaces the channel with a small per-key map plus a dirty set, so a slow client receives every technician's *latest* position rather than a backlog of stale ones. Which is right depends on whether your messages supersede each other, and that's a property of the stream, not of the connection.

**What's deliberately missing.** `c.sess` is doing quiet work here — assigning sequence numbers, retaining a bounded replay window, and surviving this `conn` so the next one can resume against it. And every bit of that is in-process: a resume handshake that lands on another pod finds no session and has no choice but a full resync. Everything in this file is correct for one server, which is the same sentence 9.1a ended on, and 9.1c is where it stops being true.

## Further Reading

- **RFC 6455, §5.5 (control frames) and §7.4 (status codes)** — ping/pong semantics and the close-code ranges, including why `1006` is never sent on the wire. Ten minutes, and it settles most arguments.
- **IANA WebSocket Close Code Number Registry** — what's actually reserved, so your `4xxx` choices don't collide with something standardized later.
- **Marc Brooker, "Exponential Backoff And Jitter"** (AWS Architecture Blog, 2015) — the measurements behind full jitter, and the reason "add a longer delay" doesn't fix a herd.
- **`gorilla/websocket`'s chat example** (github.com/gorilla/websocket, `examples/chat`) — the read-pump/write-pump split above is theirs, and the comments explain the timing relationships more precisely than most prose does.
- **MQTT 5.0 specification**, sections on Session State, Clean Start, and Session Expiry Interval — a fully worked answer to this article's problems, useful even if you never deploy a broker, because it shows what the complete version of resumption looks like.
- **Phoenix Channels documentation**, the "Client-server communication" and resumption sections — an opinionated implementation with the reconnect and rejoin semantics documented rather than implied.
- **OWASP, "Testing WebSockets"** — cross-site WebSocket hijacking and the `Origin` check, worth reading once because the vulnerability is easy to ship and invisible in a code review that assumes CORS applies.

A TypeScript sibling would reveal something this one hides rather than repeat it: in a browser you cannot send a ping at all, so the heartbeat must be an application message; and `bufferedAmount` is the only backpressure signal you get, which turns aside 4's `default:` branch into a number you have to poll. Both constraints change the design rather than the syntax. Not yet written.

---

The habit to carry out of this: whenever a system holds something across time — a socket, a lease, a lock, a subscription — ask what happens when one side disappears without saying so. HTTP answered that question for you with a timeout and a status code. Almost nothing else does, and "the other end is gone and hasn't mentioned it" is the failure mode that produces the incidents with no errors in them.
