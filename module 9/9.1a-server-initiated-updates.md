# Server-Initiated Updates

_Module 9.1a — Real-Time Communication_

## The Problem

A support-desk product. Agents work a shared escalation queue: a ticket appears, someone claims it, the contract says a human acknowledges it within sixty seconds.

The queue screen polls.

```
GET /queue  →  every 5 seconds
```

At peak there are 400 agents with that screen open. New escalations arrive at roughly one a minute.

Do the arithmetic on that, because the shape of it is the whole article.

```
requests     400 agents ÷ 5s        =  80 req/s   =  288,000 / hour
news          60 escalations/hour × 400 watchers  =   24,000 informative responses
                                                      ─────────
                                        92% of all polls say "nothing changed"
```

Ninety-two percent is not a scandal on its own — polls are cheap. What makes it a problem is what the number is a function of. It goes up when you hire agents. It goes up when someone opens a second tab. It does not go down on a quiet Sunday. **The load is proportional to how many people are watching, and completely independent of whether anything is happening.**

Then the latency side, which is worse than the average suggests:

```
                                        ticket #8812 created
                                               │
  agent A   ●────●────●────●────●────●────●────┼●──────    sees it at +0.4s
  agent B   ──●────●────●────●────●────●────●──┼──●────    sees it at +2.1s
  agent C   ────●────●────●────●────●────●────●┼────●──    sees it at +4.6s
            0s                                 │
                                        a 5-second window in which three
                                        agents learn the same fact at three
                                        different times
```

Mean latency is 2.5 seconds, which sounds fine against a 60-second SLA. The bug report that actually lands is different: two agents open the same ticket and both start typing, because their poll cycles are offset by four seconds and the claim happens in between. Polling doesn't just add delay, it adds *skew*, and skew turns a queue into a race.

So the team optimizes, in the order everyone optimizes.

**Poll every second instead of five.** Load goes to 400 req/s. Mean latency goes to 500ms. Five times the cost for five times the freshness — perfectly linear, and the floor is always the interval.

**Add validators** (Module 7.4a). `If-None-Match` on the queue endpoint, and now 92% of responses are a 304 with no body. This is a real win: bytes drop by an order of magnitude, JSON serialization mostly disappears, and if you keep a cheap `queue_version` per tenant the database barely gets touched. But the request count is *identical*. Four hundred TLS records per second, 400 auth checks, 400 tenant resolutions, 400 rate-limit decrements, 400 access-log lines.

**Cache the query in Redis with a one-second TTL.** Postgres is now safe. The request count is still identical, and you've added a second of staleness on top of the interval.

Every one of those makes each poll cheaper. None of them makes there be fewer polls, and none of them gets latency below the interval. That's the ceiling on the whole family of fixes.

Now flip the question. The server knows the instant ticket #8812 exists — it wrote the row. There are 400 connections' worth of people who want to know. If it could simply say so:

```
polling:  288,000 requests/hour, 2.5s mean latency, 5s of skew
telling:   24,000 messages/hour, ~20ms, no skew
```

Nothing in HTTP forbids this. Nothing in HTTP helps, either: the client speaks first, always. The server has no channel to an idle browser. Everything in this module is a way around that one sentence.

## What It Is

The general capability is **server push** — server-initiated delivery — and there are four mechanisms in wide use: short polling, long polling, Server-Sent Events, and WebSockets. All four are workarounds for the same constraint, and they differ mainly in who is waiting and for how long.

Three things this is not, because the vocabulary is crowded:

**"Real-time" here means low latency, not bounded latency.** A chat app and a flight-control system use the same word for completely different guarantees. Nothing in this module promises a deadline; it promises milliseconds instead of seconds, most of the time.

**Push notifications are a different problem.** APNs, FCM, and Web Push deliver to a device whose app is *closed*, via an OS-mediated channel you don't operate. That's Module 14. This article assumes a client that is currently open and connected.

**GraphQL subscriptions, Socket.IO, Phoenix Channels, Action Cable, and SignalR are not alternatives to these four.** They are libraries layered on top of them, usually WebSockets with a long-polling fallback. Choosing one of those is a separate decision from the one this article is about, and it goes better once you've made this one.

## Recognizing the Problem

- The poll interval is a number the team argued about, and nobody is happy with the compromise.
- More than 80% of responses on some endpoint are 304s or empty deltas.
- Backend load tracks logged-in users rather than activity — traffic graphs look like a headcount chart.
- Two users act on the same item because they saw it at different moments.
- A product requirement is written in seconds: "within 10 seconds of the payment clearing."
- The UI has a refresh button whose purpose is "see if anything happened."
- Mobile users report battery drain, and the radio is waking every few seconds for a 304.
- Someone declined a feature because "we'd have to poll for that one too."
- You have a progress bar that is really a status endpoint being hit every second for four minutes.
- A tab left open overnight is indistinguishable, to your backend, from an agent working.

If none of these bite — fifty users, a ten-second tolerance, data that changes hourly — the rest of this module is Explorer reading. Polling is the correct answer far more often than the amount written about WebSockets would suggest.

## How It Works

HTTP's exchange is fixed: the client sends a request, the server responds, the exchange is over. Each technique below bends exactly one of three knobs — **how often the client asks, how long the server waits before answering, and whether anything stays open afterward.**

```
short poll   C ──req──► S   "nothing"                    repeat every 5s
             C ──req──► S   "nothing"
             C ──req──► S   "ticket 8812"

long poll    C ──req──► S   ·······waits 24s·······  "ticket 8812"
             C ──req──► S   ·······waits·······           one request per event

SSE          C ──req──► S   ═══ one response, never ends ═══►
                              id:8812   id:8813   id:8814 …

WebSocket    C ─upgrade─► S  ◄═══ framed messages, both ways ═══►
```

**Short polling** is the baseline above. Its one virtue is enormous: it is ordinary HTTP, so caching, load balancing, retries, auth, logging, and every debugging tool you own work unchanged. Its cost model is `clients ÷ interval`, forever.

**Long polling** (the "hanging GET") has the server hold the request open until either something happens or a timeout fires — typically 20–30 seconds, deliberately below the idle timeouts of the proxies in between. Then it answers and the client immediately asks again. One request per event instead of one per tick, and latency is the delivery time rather than the interval.

The subtlety is the gap. Between "server responds" and "client's next request arrives" there is a window of a few milliseconds where an event can happen with nobody listening. If the response and the next request don't share a position marker, that event is simply lost — rarely, non-deterministically, and never in testing. This is the reason a **cursor** shows up in every design below, and it's the single most important idea in this article.

**Server-Sent Events** is one HTTP response that never finishes. The server sets `Content-Type: text/event-stream` and writes records into the body as they occur:

```
id: 8812
event: ticket.created
data: {"id":8812,"priority":"P1"}

id: 8813
event: ticket.claimed
data: {"id":8812,"by":"dana"}
```

It is server→client only; the client talks back over ordinary requests, which is usually exactly right for the "watch a queue" shape. The browser's `EventSource` reconnects on its own after a few seconds (the server can tune it with a `retry:` field), and on reconnect it sends back the last `id:` it saw in a `Last-Event-ID` header — so the cursor is part of the standard rather than something you invent. Payloads are text; binary needs base64. Over HTTP/1.1 a stream occupies one of the browser's ~6 connections per origin, which is where SSE's old reputation for being unusable with multiple tabs came from; over HTTP/2 it's one multiplexed stream among a hundred, and the objection is mostly gone.

**WebSockets** start as an HTTP request and stop being HTTP. The client sends `GET` with `Upgrade: websocket` and a `Sec-WebSocket-Key`; the server answers `101 Switching Protocols`; from that moment the same TCP connection carries a symmetric, message-framed, bidirectional channel with a few bytes of overhead per message and no further HTTP involvement.

That last clause is the trade in one line. After the upgrade there are no status codes, no per-message headers, no `Authorization`, no conditional requests, no caching, no correlation between a thing you sent and a thing you got back. Every one of those you still need, you now build: your own message envelope, your own auth handshake, your own error taxonomy, your own reconnect, your own resume. Frameworks exist precisely because that list is long.

A fifth category, briefly, for completeness: **WebTransport** over HTTP/3 offers multiple streams plus unreliable datagrams, which matters for games and media and very little for CRUD products; **gRPC server streaming** is the usual answer for service-to-service and non-browser clients; and inside your own network, a plain TCP or NATS connection has none of the browser's constraints.

### The cost model, stated plainly

```
polling:   requests/sec  =  clients ÷ interval             (events don't appear)
push:      messages/sec  =  events/sec × watchers per event
           plus a standing cost per idle connection: memory, a file descriptor,
           a slot in every load balancer and proxy in the path
```

Push is dramatically cheaper when watchers are many and news is rare — the support desk, at 12:1. It is *not* automatically cheaper, and the standing cost is the part people forget: 50,000 idle connections is real resident memory, real descriptors, and a connection table on the load balancer, all of it paid whether or not anyone sends anything. Polling bills you per client per tick; push bills you per client per second plus per event.

The rule that falls out: **polling only stays cheap while clients are few or news is frequent.** Check which side of that you're on before choosing anything.

### The cursor is not part of the transport

Clients disconnect. Laptops sleep, trains enter tunnels, you deploy. Whatever mechanism you pick, the client eventually reappears and asks the same question: *what did I miss?*

The answer is always the same shape — a monotonically increasing position that the client hands back on reconnect. A sequence number, a ULID, a log offset, a `(timestamp, id)` pair. SSE standardizes it as `Last-Event-ID`. Long polling needs it most acutely, because of the gap. WebSockets have nothing for it and you build it yourself, which is why WebSocket implementations lose messages on reconnect more often than SSE ones do.

It's worth separating this from the transport in your head, because the cursor is the part you'll keep. Transports get swapped; the "give me everything after X" contract survives all four.

## When It's Appropriate

- **The latency requirement is below the interval you can afford.** Concretely: if satisfying the product means polling faster than about every ten seconds, and there are more than a few hundred concurrent clients, push is already cheaper and gets more so.
- **Many watchers, rare events.** 5,000 open dashboards and an event every two minutes is 500 req/s of polling to deliver 40 messages/s of actual news.
- **Skew causes real bugs.** Shared queues, claim-based workflows, seat selection, auction bids, inventory that can go to zero — anywhere "who saw it first" determines who acts.
- **The client needs to talk back at rate.** Chat typing indicators, presence heartbeats, cursor positions in a collaborative document, multiplayer input. This is the case that genuinely wants WebSockets rather than SSE; one HTTP request per keystroke is not a design.
- **Long-running operations with progress** (Module 10): a four-minute export, a progress bar, a result. Polling the job endpoint is fine for a handful of jobs; a stream is better once every user in the system has one running.
- **Fan-out is large and events are small.** A price tick going to 20,000 subscribers is one event and 20,000 tiny frames, versus 20,000 clients each polling.

## When It's Unnecessary or Overkill

- **Fewer than a hundred clients.** Fifty users polling every ten seconds is 5 req/s. There is no problem here to solve, and every trade-off below is pure cost.
- **Data that changes on a human schedule.** Reports, billing summaries, anything computed nightly. A socket to deliver something that changes at 3 a.m. is theatre.
- **The only person who needs to see the change is the person who made it.** This is the big one. A large share of "we need real-time" requirements evaporate under optimistic UI — the client applies its own mutation locally and reconciles with the response. No server push involved, no new infrastructure, and it's *faster* than push because there's no round trip at all.
- **Internal admin tools.** Refresh is an acceptable UI affordance for eleven people.
- **No appetite for a stateful tier.** Everything in the next section is ongoing operational work. If there's no one to own connection metrics and deploy behaviour, polling is the honest choice.
- **Platform constraints.** Functions billed per invocation-second, edge runtimes that cap response duration, corporate proxies that eat `Upgrade` headers. Check before designing, not after.
- **"Users expect live updates now."** Possibly true, but it isn't a latency requirement. Ask for the number of seconds; sometimes it comes back as "a minute or so is fine," and you're done.

## Trade-offs

What it costs once you have it and it works.

**You are now running a stateful tier.** Application servers stopped being interchangeable the moment one of them holds something a client cares about. Every deploy severs every connection, so 40,000 clients reconnect within the same second — a thundering herd that, without jittered backoff on the client, turns each of your deploys into a small self-inflicted outage.

**One process stops being enough, and the second one silently breaks fan-out.** Agent A's connection lives on node 1. The ticket is created by a request served on node 2. Node 2 has no way to reach A. This is not a scaling refinement to do later; it is broken at N=2, it works perfectly in development, and it half-works in staging with two pods, which is the worst possible way to find out. The fix is a backplane — Redis Pub/Sub, NATS, Kafka — and it's 9.1c and 9.4.

**The network path has opinions.** An AWS ALB closes idle connections after 60 seconds by default, so quiet streams need heartbeats. Nginx buffers proxied responses unless told otherwise, so SSE appears to hang until several kilobytes accumulate. Some corporate proxies strip `Upgrade` entirely, which is the entire reason fallback ladders exist.

**Auth outlives its token.** A request is authorized once and finishes. A connection authorized at 09:00 may still be open at 17:00, long after the access token expired, after the user's role changed, after they logged out on another device. You need a maximum connection lifetime, re-authentication on the live connection, or both — and a logout that doesn't close sockets is not a logout. Module 4.4's revocation design has to reach in here.

**Backpressure becomes yours to police.** A client on hotel wifi cannot absorb 200 messages a second. Its share of your send buffer grows, and your server's memory becomes a function of your slowest user. You must pick a policy — block, drop, coalesce to latest, or disconnect — and "coalesce to latest" is very often right for dashboards and very wrong for chat.

**Observability degrades.** Dashboards keyed on request rate and p99 latency show almost nothing about a tier whose traffic is one request per user per day. You need connection count, connection age distribution, messages per second, per-connection send lag, and disconnect reasons — and until you have them, a bug affecting only long-lived connections is invisible.

**Delivery semantics are no longer given to you.** HTTP handed you exactly one response per request with a status code attached. A pushed message has no acknowledgement unless you invent one. What you can realistically build is at-least-once plus a cursor, which means **the client must tolerate duplicates** — that requirement propagates into every handler on the receiving end.

**Debugging gets meaningfully harder.** `curl` reproduces a polling bug. Reproducing "a message arrives twice when a reconnect lands during a rolling deploy" requires deliberate tooling that you will build after the first incident.

## Alternatives

- **Polling, done properly.** A cursor endpoint, validators, jitter so clients don't synchronize, and an adaptive interval driven by `visibilitychange` — poll at 3 seconds when the tab is focused, 60 when it's hidden, never when it's been hidden an hour. On a typical product that's an 80% cost reduction with no new infrastructure and no stateful tier. It is the most underrated item in this module and should be attempted before anything else here.
- **Optimistic UI with reconciliation.** Removes the self-caused half of the requirement entirely, which is frequently the half anyone actually complains about.
- **Web Push / APNs / FCM.** For clients that aren't open. Complementary rather than competing: the usual production design pushes in-app when connected and falls back to a notification when not (Module 14).
- **Digests and batching.** "Within seconds" is sometimes an assumption rather than a requirement; a five-minute digest costs nothing and is often a better experience.
- **Server-driven rendering over a single connection** — LiveView, Hotwire, Livewire. A different shape of the same trade: you get push and lose client-side flexibility, and the connection concerns in this article apply identically, because underneath it's a WebSocket.

None of these are exclusive. Mature systems poll for some surfaces, push on one or two, and send email for the rest of it.

## How to Achieve It

Four levels, and the first one is worth more than it looks.

**Level 0 — make the read incremental.** Replace "give me the current queue" with "give me what happened after cursor X":

```
GET /events?since=8811  →  { events: [...], cursor: 8814 }
```

Keep polling exactly as you are. Nothing operational changes, no new failure modes, and you now own the contract that every level above uses. Teams that skip this and jump to WebSockets end up retrofitting it after their first "messages disappear sometimes" incident.
*Move on when:* you're polling faster than every ten seconds, or empty responses are a visible line item in your infrastructure bill.

**Level 1 — hold the request open.** Same endpoint, same contract: if there's nothing after `since`, wait up to 25 seconds before answering. Long polling traverses every proxy in existence, needs no client library, requires no protocol negotiation, and degrades to short polling under anything that times it out. Best value-per-unit-of-risk step on this ladder by a wide margin.
*Move on when:* holding thousands of concurrent requests is expensive in your server model (thread-per-request, notably), or you need to deliver many messages per second to one client.

**Level 2 — one stream instead of many responses (SSE).** Same endpoint, chosen by content negotiation; `Last-Event-ID` *is* the cursor you already built. Reconnection becomes the browser's job rather than yours.
*Move on when:* the client needs to send at rate, you need binary frames, or you're building a genuinely bidirectional protocol.

**Level 3 — WebSockets**, with your own envelope, heartbeat, and resume-by-cursor — and only for the surfaces that need them. Chat over a socket and dashboards over SSE in the same product is a normal, healthy architecture, not an inconsistency to clean up.

**Level 4 — fan out across nodes.** A backplane so any node can reach any connection, then per-topic registries so a node only receives what its own connections care about. 9.1c and 9.4.

The property that makes this ladder work: levels 0 through 2 share one URL and one cursor contract. Moving between them is a server change plus a client transport swap, not a redesign — which is exactly what you want when you discover at level 2 that level 1 was sufficient.

## Implementation

TypeScript, because one endpoint can demonstrate all three of the first levels, and because the browser half of SSE is where the reconnection semantics actually live — showing both ends in one language is the point.

An append-only log with a position, which is all a cursor needs:

```ts
type Event = { id: number; type: string; payload: unknown };

const log: Event[] = [];
const waiters = new Set<() => void>();

function append(type: string, payload: unknown) {
  log.push({ id: log.length + 1, type, payload });
  for (const wake of waiters) wake();      // ← aside 1
  waiters.clear();
}

const since = (cursor: number) => log.filter(e => e.id > cursor);
```

One handler, three transports:

```ts
app.get("/events", async (req, res) => {
  const cursor = Number(req.header("last-event-id") ?? req.query.since ?? 0);

  if (req.accepts("text/event-stream")) return stream(req, res, cursor);

  const backlog = since(cursor);
  if (backlog.length) return res.json(backlog);   // short poll with news
  await waitForEvent(25_000);                     // long poll
  return res.json(since(cursor));                 // ← aside 2
});
```

The stream:

```ts
function stream(req: Request, res: Response, cursor: number) {
  res.writeHead(200, {
    "Content-Type": "text/event-stream",
    "Cache-Control": "no-cache, no-transform",
    "X-Accel-Buffering": "no",                    // ← aside 3
  });

  const send = (e: Event) => {
    res.write(`id: ${e.id}\n`);                   // ← aside 4
    res.write(`event: ${e.type}\n`);
    res.write(`data: ${JSON.stringify(e.payload)}\n\n`);
  };

  for (const e of since(cursor)) send(e);         // catch up, then follow
  const unsubscribe = subscribe(send);

  const beat = setInterval(() => res.write(": beat\n\n"), 20_000);  // ← aside 5
  req.on("close", () => { clearInterval(beat); unsubscribe(); });   // ← aside 6
}
```

And the client, which is four lines and one of them is the interesting one:

```ts
const es = new EventSource("/events");

es.addEventListener("ticket.created", (e) => {
  const ticket = JSON.parse(e.data);
  if (seen.has(ticket.id)) return;                // ← aside 7
  seen.add(ticket.id);
  queue.insert(ticket);
});
```

**Aside 1 — the notify is the optimization; the cursor is the correctness.** It's tempting to read `waiters` as the mechanism that makes this work. It isn't. If the wake-up never fired, every client would still converge on the right state at the next poll. What makes the design *correct* is that every response carries a position and every request resumes from it. Remove the cursor and keep the notify and you have a system that works beautifully except for events landing in the microseconds between a response and the next request.

**Aside 2 — this line is the long-poll gap, closed.** After waiting, the handler re-reads from the client's original `cursor`, not from "whatever arrived while I was waiting." If a second event lands between the wake-up and the query, it's included; nothing is skipped. The version of this that queues up "the event that woke me" and returns only that is the bug you'll be chasing in three months.

**Aside 3 — nginx buffers proxied responses by default.** Without `X-Accel-Buffering: no` (or `proxy_buffering off`), the stream stays invisible until several kilobytes accumulate. On a busy production box that's imperceptible; on a quiet staging environment it presents as "SSE just doesn't work," and it has ended more than one evaluation prematurely.

**Aside 4 — `id:` is the entire resume story.** The browser records it and sends it back as `Last-Event-ID` on automatic reconnection, which the handler reads on line one. Omit it and reconnects silently restart from empty: every laptop lid, every tunnel, every deploy drops whatever happened while the client was away, with no error anywhere.

**Aside 5 — the heartbeat is for the intermediaries, not the client.** An ALB with a 60-second idle timeout will close a stream that has been quiet for 60 seconds. What the user sees is a reconnect loop; what the logs show is nothing at all on either end. A comment line every 20 seconds sits below every default worth worrying about and costs eight bytes.

**Aside 6 — this is the connection's entire lifecycle.** There's no request/response cycle to hang cleanup on and no framework hook that fires for you. Forget it and the subscriber set grows by one on every reconnect — and since reconnects happen on every deploy and every closed laptop, this is not a slow leak.

**Aside 7 — duplicates are guaranteed, so idempotence isn't optional.** Reconnection replays from the last id the client *received*, and "received" and "processed" are not the same instant. At-least-once is what this design gives you; exactly-once would need an acknowledgement protocol that doesn't exist here. The bounded `seen` set is the honest price of that, and it belongs in the client from the first day, not after the first duplicate-row bug.

**What this code cannot do, and why it matters now.** `waiters` and `subscribe` are in-process. Two nodes, and an event appended on node 2 wakes nobody on node 1 — those clients hang until their 25-second timeout, then poll and quietly catch up, which means the symptom is *intermittent slowness* rather than a visible failure. Everything above is correct and complete for one process, and one process is not a deployment. That gap is what 9.1c is for.

## Further Reading

- **RFC 6202, _Known Issues and Best Practices for the Use of Long Polling and Streaming in Bidirectional HTTP_** — short, old, and still the most useful single document on this topic. Written by people who had already hit every failure mode in the trade-offs section.
- **The HTML Living Standard, §"Server-sent events"** (html.spec.whatwg.org) — the normative behaviour of `EventSource`: reconnection timing, `Last-Event-ID`, and the exact wire grammar. Worth reading over MDN once, because the reconnect rules are the part everyone assumes rather than checks.
- **MDN, _Using server-sent events_** — the practical companion, including the `EventSource` caveat that bites everyone: no custom headers, so no `Authorization`, so cookie auth or a short-lived ticket in the URL.
- **RFC 6455, _The WebSocket Protocol_** — sections 1 and 5 (handshake and framing). Section 5.5's ping/pong frames are the thing browsers don't expose to JavaScript, which is why application-level heartbeats exist.
- **RFC 8441 / RFC 9220** — bootstrapping WebSockets over HTTP/2 and HTTP/3. Useful for understanding why most WebSocket deployments still terminate on HTTP/1.1.
- **Socket.IO documentation, the "How it works" and "Upgrade mechanism" pages** — regardless of whether you'd use it, it documents a real fallback ladder honestly, including why it opens with long polling and upgrades afterwards rather than the reverse.
- **_Designing Data-Intensive Applications_, Martin Kleppmann, ch. 11** — push versus pull, consumer offsets, and why "what did I miss" has the same answer in a message broker as in the cursor above.

A Go sibling would earn its place, and specifically because the cost model changes: goroutine-per-connection makes 50,000 held requests a different arithmetic problem than an event loop does, and `context` cancellation makes the aside-6 cleanup structural rather than something you remember. Not yet written.

---

The habit to carry out of this: before choosing a transport, write down two numbers — how many clients are watching, and how often something actually happens. Nearly every decision in this module is a function of the ratio between them, and the number that makes polling look silly at 400 agents makes WebSockets look silly at twelve.
