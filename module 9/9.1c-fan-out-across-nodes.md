# Fan-Out Across Nodes

_Module 9.1c — Real-Time Communication_

## The Problem

A virtual-events platform. Attendees join a session room and get live chat, Q&A upvotes, and a reaction stream. It's one Node process holding WebSocket connections, and the fan-out is exactly what you'd write:

```ts
const rooms = new Map<string, Set<Conn>>();

function broadcast(roomId: string, msg: Message) {
  for (const c of rooms.get(roomId) ?? []) c.send(msg);
}
```

That code is correct, fast, and about to stop working.

The first real conference books 9,000 attendees, so you scale the deployment to two replicas. Nothing errors. Nothing appears in the logs. What arrives instead is a support ticket that reads: *"I can see Ana's messages but she can't see mine."*

Ana is on pod 1. The complainant is on pod 2. `rooms` is a `Map` in a process, and there are now two of them, each holding half a conversation. Everyone in the room is having a slightly different conversation with a different subset of the room, and which subset depends on load-balancer arithmetic nobody can see. This is the worst possible failure shape: it works in development, it works in staging with one replica, and in production it is *partially* correct, which reads as flakiness rather than as a missing component.

Then come the four fixes, in the order teams actually try them.

**Sticky sessions.** The load balancer is configured for session affinity, because that's the answer every "scaling WebSockets" article gives. It changes nothing about the bug. Affinity pins a *client* to a node; the problem is that a *room* is spread across nodes. Stickiness is genuinely useful — it's what lets a reconnecting client land back on the pod holding its replay buffer — but it is not a fan-out mechanism, and an afternoon gets spent discovering that.

**Route rooms to nodes.** Hash the room id, send everyone in room 42 to pod 1. Now fan-out is local again and there's no cross-node messaging at all. This is a real architecture and it survives production — until the keynote room has 40,000 attendees and doesn't fit on one pod, until one hot room makes one node the only busy node, and until an attendee in three rooms needs to be in three places. It also makes every scale-up a rebalancing event.

**A broadcast bus.** Every message goes to Redis; every pod subscribes; every pod filters for rooms it holds. Ten lines, deployed in an afternoon, and the bug is gone.

Six months later there are twelve pods and a big event running reactions at 3,000 messages a second:

```
published                              3,000 msg/s
delivered by broker  3,000 × 12 pods = 36,000 msg/s
useful for the receiving pod          ~3,000 msg/s
discarded after deserialization       ~33,000 msg/s   (92%)
```

Every pod is deserializing every message for every room, including the 400 rooms it has nobody in. Adding a thirteenth pod to handle more connections *increases* the per-pod message-processing load. You have built a system where scaling out makes each node work harder — which is not scaling, it's multiplication.

**Subscribe only to what you hold.** A pod subscribes to `room:42` when its first local connection joins that room and unsubscribes when the last one leaves. Broker traffic drops back to roughly what's useful. This is the right answer, and it brings its own set of problems — subscription churn, a race on that last-one-leaves check, and the question of what happens to a user who is targeted directly rather than by room.

And underneath all four, the thing 9.1b left open: the replay buffer lived in the process. A client whose connection dropped reconnects, lands on a different pod by design, presents a sequence number that pod has never seen, and gets a full resync — every time.

## What It Is

The mechanism is a **fan-out plane**: a way for the node that *receives* a message to reach the nodes that *hold* the connections interested in it, without either of them knowing about the other.

Once you have more than one process holding connections, a real-time system has three layers rather than one:

```
  connection plane   pods holding sockets; stateful; scales with connections
  fan-out plane      how a message reaches the pods that need it
  routing/registry   optional: who is where, for directed sends and presence
```

The first two are mandatory at N=2. The third is frequently built and rarely needed, and it's worth asking whether you can avoid it — a lot of "which node is user U on?" turns out to be answerable as "publish to the topic `user:U` and let whoever has them pick it up."

One disambiguation, because the same infrastructure keeps showing up: **this is not your application's event bus.** A business event ("payment captured") is durable, ordered, consumed once by each service, and must survive a broker restart — Module 37's territory. A fan-out message ("Ana is typing") is ephemeral, delivered to every interested socket, and worthless three seconds later. They can ride on the same technology, and mixing them up is how you end up either paying for durability you don't need or losing messages you thought were safe.

## Recognizing the Problem

- It works with one replica and half-works with two.
- "I can see them, they can't see me."
- A message shows up after a refresh but not live.
- Broker traffic grows when you add pods, without any new users.
- CPU on your real-time pods is dominated by deserializing messages nobody wanted.
- One room, game, or document makes one node hot while the rest idle.
- Reconnection loses history *sometimes* — specifically, whenever the reconnect lands on a different pod.
- Your autoscaler is configured on CPU, and CPU stays flat while connections climb toward a limit nobody has measured.
- Deploys produce a visible gap in a live feed even though the client reconnects in under a second.

## How It Works

### Three shapes, and the arithmetic that separates them

```
partition by topic     broker deliveries = 0
                       one node owns a room; fan-out is a local loop

broadcast bus          broker deliveries = messages/s × nodes
                       every node gets everything and filters

topic subscription     broker deliveries = messages/s × nodes holding that topic
                       a node receives only what it has subscribers for
```

**Partitioning** — consistent-hash the room id to a node, and route connections there. Nothing crosses the network after that, per-message cost is the lowest available, and you get something extra that matters for some domains: a single owner per room means a single place to assign ordering and resolve conflicts, which is why collaborative editing and multiplayer games gravitate here (and why 9.3's editing article will end up back at this idea).

The costs are structural. A room must fit inside one node. Hot partitions are a hot *node*, not a hot key. A client in several rooms either holds several connections or you build a gateway tier that fans out internally — at which point you have a backplane again, just one you wrote. And scaling the pool reshuffles ownership, which means dropping connections on purpose.

**A broadcast bus** is the simplest thing that works, and its N×M cost is fine far longer than the arithmetic above suggests. At 500 messages a second and 6 pods, that's 3,000 deliveries a second of small payloads, which is nothing. Don't skip it out of aesthetics; skip it when the number gets large.

**Topic subscription** is the general answer: the node tracks, for each topic, how many local connections care, and subscribes on the transition from 0→1 and unsubscribes on 1→0. It requires a broker where topics are cheap and numerous — which is a real technology constraint. Redis channels and NATS subjects are essentially free and you can have millions; Kafka topics are files with metadata and partitions, and 50,000 of them is an operational problem rather than a design. That's why Kafka is a poor fit for this specific job despite being excellent at Module 37's job, and it's the single most useful thing to know before reading 9.4.

### Directed delivery without a registry

"Notify user U" doesn't have a room. The obvious design is a registry — `user:U → pod-7`, kept in Redis with a TTL and refreshed by heartbeat — and then a directed send to that pod.

Usually you don't need it. Treat the user as a topic: the pod holding U's connection subscribes to `user:U`, and anyone can publish there without knowing where U is. No registry, no staleness window, no cleanup job, and it works correctly when U is connected twice from two devices, which is the case that breaks most registries.

Build the registry only when you need to *query* it — "is this user online right now," "how many people are in this room," "force-disconnect this session." Presence is a genuinely harder problem than it looks and gets its own article; the point here is that it's a separate requirement from fan-out and shouldn't be smuggled in as a prerequisite.

### The backplane's delivery guarantee becomes the system's

This is the part most designs get wrong by omission.

Redis Pub/Sub is **at-most-once with no buffering on the publisher's side and a hard limit on the subscriber's**. If a subscriber can't keep up, Redis doesn't slow down — it disconnects it. The default for the pubsub class is a 32MB hard limit and 8MB sustained for 60 seconds, and when it trips, that pod loses every message for every client it holds, silently, for as long as it takes to resubscribe. A 400ms garbage-collection pause during a traffic peak is enough.

So: with pub/sub as your backplane, your system's guarantee is "usually." Which is fine — for reactions and typing indicators it's exactly right — as long as you know it, and as long as anything that matters is protected by something else. The something else already exists: 9.1b's per-message sequence numbers and client-side gap detection turn a silent backplane drop into a client noticing `4471 → 4489` and asking for a resync. **That's the layer that makes an unreliable fan-out plane safe to use**, and it's why gap detection is worth building before you think you need it.

If you need better than "usually," the backplane has to be a log rather than a bus.

### Tailing a log instead of broadcasting

The variant worth knowing: instead of publishing messages to subscribers, append them to a per-room stream (Redis Streams, NATS JetStream, a Postgres table with a monotonic column), and have each pod *tail* the streams for rooms it holds.

Fan-out cost has the same shape as topic subscription, and you get two things pub/sub can't give you. The entry id is a cursor, so a pod that fell behind resumes exactly where it stopped instead of losing the gap. And the replay buffer stops being per-process — any pod can serve any client's resume request by reading from the stream, which deletes the "reconnect lands elsewhere, full resync" problem outright.

The cost is that the stream is now state with a retention policy, a trimming job, and a memory bill that's proportional to rooms × retention rather than to connections. Details in 9.4.

### What sticky sessions are actually for

Not fan-out. What affinity buys you is that a reconnecting client returns to the pod that already holds its session state — its replay buffer, its subscription set, its decrypted context. That's a meaningful latency and complexity win, and it's why it's worth configuring.

What it can't do is survive the event that most often causes reconnection: the pod going away. Affinity is an optimization over a system that must already be correct without it. If your resume path only works when the client lands on the same pod, you don't have a resume path — you have one that's untested on the exact occasion it's needed.

### Deploys, drains, and the ceiling you haven't measured

Two operational facts that only exist once connections are long-lived.

**Draining is your job, and it's better done slowly.** On shutdown, don't close 12,000 sockets at once and rely on client jitter — close them at a controlled rate, a few percent a second, with close code `1001`. The server knows more about the herd than any individual client does, and spreading the reconnect over sixty seconds costs users nothing.

**You scale on connections, not CPU.** A pod holding 30,000 idle sockets may sit at 3% CPU right up to the moment it runs out of file descriptors or memory (budget single-digit-to-tens of KB per connection, and measure it, because it varies by an order of magnitude across runtimes and TLS settings). An autoscaler keyed on CPU will never add a pod. There's also a ceiling most people meet by surprise: a proxy or load balancer connecting to a target from one source address can hold on the order of tens of thousands of simultaneous connections to it before ephemeral ports run out — which puts a hard cap on connections-per-pod that has nothing to do with your pod's capacity.

## When It's Appropriate

- **Two or more processes holding connections.** There is no threshold to reach; the moment a second replica exists, a fan-out plane is mandatory. The only question is which shape.
- **Broadcast bus:** total real-time message rate under a few thousand a second and fewer than about ten nodes. Most B2B SaaS lives here permanently and should not build anything more.
- **Topic subscription:** many topics with sparse membership — thousands of rooms, documents, or tenants where any given pod holds a handful. This is the default for a product with per-customer or per-object streams.
- **Partitioning:** when a single topic needs an owner for reasons beyond fan-out — total ordering, conflict resolution, a live in-memory model of a document or game state — and when a topic's traffic and membership comfortably fit one node.
- **A log-based backplane:** when a reconnecting client must not lose messages, and full resync is too expensive to do on every subway tunnel.

## When It's Unnecessary or Overkill

- **One node is a legitimate architecture for longer than you'd think.** Tens of thousands of concurrent connections on a modest box is ordinary. If your peak is 3,000, a fan-out plane is a component you're operating for no reason — though note the honest catch: one node means deploys are outages, so the usual forcing function isn't load, it's uptime.
- **A registry you never query.** Building `user → node` before you have a feature that needs it is pure maintenance, and stale entries are a source of confusing bugs.
- **Shared replay before you've measured resync cost.** If a full room snapshot is 8KB and reconnections are rare, per-process buffers plus resync is correct and much simpler.
- **Per-topic subscription at small scale.** The refcounting and its race conditions are real complexity; take them when the broadcast arithmetic actually hurts.
- **Kafka because it's the message broker you already run.** The topic model doesn't fit; you'll end up with one topic that every pod reads in full, which is a broadcast bus with a heavier operator manual.

## Trade-offs

**Every message gets an extra hop.** Publisher → broker → subscriber pod → socket. Sub-millisecond within an availability zone, several milliseconds across, and it's now on the path of every interaction in your product. Real-time latency is no longer a property of your application.

**The broker is in the hot path and fails quietly.** If Redis is unreachable, HTTP still works, health checks still pass, and the live parts of the product simply stop updating. This is the outage where nothing is red. It needs its own alert — publish-to-receive latency measured end to end, not broker uptime.

**Global ordering is gone.** Two pods publishing to the same room concurrently have no order between them; each publisher's own messages stay in order and that's all you get. If a room needs a total order, it must be assigned at a single point — a per-room counter, a stream entry id, or a partition owner — and if it doesn't need one, say so explicitly, because someone will assume it later.

**Duplicates become normal.** A user with two tabs, a zombie connection that hasn't timed out yet, or a resync overlapping live delivery all produce the same message twice. Message ids and client-side dedup stop being optional, which is the same conclusion 9.1a reached from a different direction.

**Subscription churn is load.** A user opening and closing rooms generates broker subscribe/unsubscribe traffic, and the 1→0 transition has a race that will bite you (see the implementation). A small unsubscribe delay is a cheap and effective smoothing device.

**Observability now spans pods.** One user's session touches several pods over its life. Without a session id propagated into every log line and metric, "why did this user miss a message" is unanswerable. Per-node connection counts, per-topic subscription counts, and broker fan-out ratio are the dashboard; request rate tells you nothing.

**You're operating another stateful system** — with its own memory limits, failover semantics, and, if it's Redis Cluster, a pub/sub model with its own surprises (pre-7.0, `PUBLISH` is broadcast to every node in the cluster, which quietly reintroduces the N×M problem; sharded pub/sub in 7.0 fixes it and changes the client API).

## Alternatives

- **Vertical scaling plus a second node only for availability.** Two large pods with a broadcast bus is a fine terminal state for a great many products. Not everything needs a topology.
- **A purpose-built real-time server** — Centrifugo, Soketi, NATS with a thin gateway. You keep your application stateless and hand the connection plane to something whose entire job is this, including topic subscription and message recovery.
- **Managed realtime** — Ably, Pusher, PubNub, Supabase Realtime. The whole plane leaves your deployment: no drain problem, no broker to run, no connection ceiling to measure. You pay per connection-minute and per message, and your live features now have someone else's availability.
- **Runtime-native clustering.** Elixir/Phoenix does cluster-wide fan-out with `Phoenix.PubSub` over distributed Erlang — no external broker at all, which is why Phoenix comes up in every conversation about this. The cost is the BEAM, and it's a real cost only if you weren't already there.
- **Object-affine platforms.** Cloudflare Durable Objects is the partitioning model sold as a product: one single-threaded object per room, connections routed to it by id, fan-out is a local loop again. Genuinely elegant for room-shaped domains, and a strong platform commitment.
- **Don't fan out — let clients read a shared log.** With SSE and a cursor (9.1a), each pod can serve its own clients by tailing a shared stream, and no node ever needs to reach another. Fewer moving parts than it sounds, and a good fit when messages are already being persisted for other reasons.

## How to Achieve It

**Level 0 — one node, deliberately, with the ceiling measured.** Know your connections-per-pod limit from a load test rather than from folklore.
*Next when:* you need a deploy that isn't an outage. That, not load, is what usually forces the step.

**Level 1 — broadcast bus.** One channel, every pod subscribes, filter locally. An afternoon. Ship it and stop.
*Next when:* discarded-message rate is a visible share of pod CPU, or node count is heading past ten.

**Level 2 — per-topic subscription with refcounts.** Subscribe on 0→1, unsubscribe on 1→0 with a short grace delay.
*Next when:* you need to target individual users, or presence becomes a feature.

**Level 3 — `user:{id}` topics for directed sends.** Still no registry. Add one only when a feature queries it.
*Next when:* clients are resyncing on every brief disconnect and the snapshot is expensive.

**Level 4 — move the replay buffer out of the process.** Per-room streams with entry ids as cursors; any pod can now serve any resume. This is also the point at which sticky sessions stop being load-bearing, which is a good property.
*Next when:* a single topic's ordering or state model needs an owner.

**Level 5 — partition topics to nodes.** Gateway routing by consistent hash, with a rebalancing plan you've actually run once in staging.

Most products should land at 2 or 3 and stay there for years.

## Implementation

TypeScript with `ioredis`, because the whole mechanism is a refcount map and the interesting parts are two failure modes that look like nothing in review.

```ts
const sub = redis.duplicate();            // ← aside 1
const localRooms = new Map<string, Set<Conn>>();

async function join(room: string, c: Conn) {
  let set = localRooms.get(room);
  if (!set) {
    set = new Set();
    localRooms.set(room, set);
    await sub.subscribe(`room:${room}`);   // 0 → 1
  }
  set.add(c);
}

async function leave(room: string, c: Conn) {
  const set = localRooms.get(room);
  if (!set) return;
  set.delete(c);
  if (set.size > 0) return;

  setTimeout(async () => {                 // ← aside 2
    if (localRooms.get(room)?.size) return;
    localRooms.delete(room);
    await sub.unsubscribe(`room:${room}`);
  }, 5_000);
}
```

Delivery, in both directions:

```ts
sub.on("message", (channel, payload) => {
  const room = channel.slice("room:".length);
  const msg = JSON.parse(payload);
  for (const c of localRooms.get(room) ?? []) c.deliver(msg);   // ← 9.1b's queue
});

async function publish(room: string, msg: Message) {
  msg.seq = await redis.incr(`seq:${room}`);                    // ← aside 3
  await redis.publish(`room:${room}`, JSON.stringify(msg));     // ← aside 4
}
```

**Aside 1 — the duplicated connection isn't tidiness.** A Redis connection in subscribe mode accepts almost nothing else; issue an `INCR` on it and it errors. You need two: one subscriber, one for everything the application does. Nearly every implementation of this has a comment above this line, because the failure appears the first time a publish and a subscribe share a client, which is often not until the second feature.

**Aside 2 — the five-second delay fixes a race that produces "the room went silent."** Without it: the last connection leaves, `unsubscribe` is awaited, and in that window the same user rejoins — `set` already exists so no `subscribe` is issued, and then the in-flight unsubscribe completes. The pod is now holding connections for a room it isn't subscribed to, and it will never recover, because the only code path that subscribes is the 0→1 transition that already happened. The delay also removes most subscription churn for free, since a page navigation typically re-joins within a second.

**Aside 3 — ordering has to come from one place.** Two pods publishing to the same room have no order relative to each other, so the sequence number 9.1b relies on cannot be assigned per-pod. A Redis counter is the cheap fix; it costs a round trip per message and it is the only reason a client's gap detection means anything now. If you'd rather not pay it, use a stream and take the entry id — same property, one operation instead of two.

**Aside 4 — the message goes to the broker and comes back to you.** Local clients are served by the subscription callback, not directly, which adds a round trip to your own users. The tempting optimization is to deliver locally and publish for everyone else — and it's a real latency win — but it means local clients see a different ordering than remote ones under concurrency, because the local copy skips the point where order is decided. If you take the optimization, take it knowingly and only where ordering doesn't matter.

**What this code is quietly relying on.** Redis Pub/Sub is at-most-once, and if this pod stalls long enough to breach the pubsub output-buffer limit, Redis disconnects it and every message for every room it holds is gone with no error on this side. The `seq` in aside 3 is what makes that survivable: the client sees a gap and resyncs. Delete the sequence number and the same event is an invisible, unreportable data loss — which is the real reason the two articles belong next to each other.

## Further Reading

- **Redis Pub/Sub documentation**, plus the `client-output-buffer-limit` section of `redis.conf` — the second one is where the at-most-once behaviour becomes concrete, and it's the paragraph most teams have never read.
- **Redis Streams introduction** (`XADD`, `XREAD`, consumer groups) — the log-shaped backplane, and the cleanest way to get replay and fan-out from one mechanism.
- **Redis sharded Pub/Sub** (`SSUBSCRIBE`/`SPUBLISH`, Redis 7.0 release notes) — why cluster-mode pub/sub behaved surprisingly before it, and what changed.
- **NATS documentation on subjects and wildcards** — the best model in common use for hierarchical topics (`events.room.42.chat`), and worth reading even if you deploy Redis, because it shapes how you name channels.
- **"How Discord Scaled Elixir to 5,000,000 Concurrent Users"** (Discord engineering, 2017) — the fan-out problem at a scale where the N×M arithmetic dominates everything, including the part where the fan-out itself had to be moved off the hot path.
- **Centrifugo documentation**, particularly the "Engines" and "Message recovery" pages — an off-the-shelf implementation of this entire article, with the design decisions written down.
- **Cloudflare Durable Objects documentation**, including WebSocket hibernation — partitioning-as-a-platform, and the hibernation model is an interesting answer to the idle-connection cost from 9.1a.
- **`Phoenix.PubSub` documentation** — cluster-native fan-out with adapters, useful as a comparison point for what the interface looks like when the broker is optional.

A Java sibling would be worth writing and would show something this article can't: Spring's STOMP support has a **broker relay** mode where the entire fan-out plane becomes a configuration line — the framework subscribes, routes, and refcounts on your behalf against a real STOMP broker. That's the opposite end of the abstraction range from the map above, and the interesting question is what it hides when the broker misbehaves. Not yet written.

---

The habit to carry out of this: whenever you add a node to a system, check whether the work *per node* went down. If it stayed flat, you bought availability. If it went up — as it does with a broadcast bus, a cluster-wide `PUBLISH`, or any design where everyone sees everything — you didn't scale the system, you multiplied it, and the ceiling is now closer than it was before.
