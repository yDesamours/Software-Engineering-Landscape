# Server-Sent Events in Practice

_Module 9.2 — Real-Time Communication_

## The Problem

A CI product. A build runs for eleven minutes and the user watches its log scroll by. This is the textbook case for SSE — server to client, text, long-lived — so the team takes 9.1a's advice, stops at level 2, and ships about forty lines of code.

It works locally. Here is the first month in production.

**The log appears in bursts.** Nothing for thirty seconds, then two hundred lines at once, then nothing. The server is writing each line the moment it arrives; nginx is buffering the proxied response and flushing when its buffer fills. Then the same bug again one layer out, from a different cause: the CDN compresses `text/event-stream` with gzip, and the compressor has its own buffer. Two independent buffering layers, identical symptom, neither visible in development where there's no proxy at all.

**The stream dies every sixty seconds** on the dot, reconnects, and repeats. The load balancer's idle timeout, closing a connection that hasn't sent a byte in a minute — which is every connection during the two-minute `npm install` phase when the build produces no output.

**The token is in the URL.** `EventSource` cannot set request headers, so `Authorization` is unavailable and the JWT went into the query string. It is now in the access log of every proxy in the path, in the CDN's cache key, and in the `Referer` header of anything the page links to. It's also an eight-hour token, because that's what the rest of the app uses.

**A bad deploy turns into a self-inflicted load test.** A config error makes the stream endpoint throw, returning 500. Every connected browser retries after three seconds. Forever. No backoff, no jitter, no ceiling — 4,000 clients at 1,300 requests a minute against an endpoint that can only fail. Nobody wrote that retry loop; it's the browser's, and it is doing exactly what it's specified to do.

**Reconnects skip lines.** The `id:` field was the line number within the current connection, so after a reconnect the client says "I have up to 412" and the server, having restarted its own counter, resumes from a different 412.

**And the seventh tab freezes the whole app.** A developer watching several builds opens seven tabs. In the seventh, nothing loads — not the stream, not the API calls, not the avatars. Six open streams have consumed the browser's entire per-origin connection budget for HTTP/1.1, and every other request to that origin is queued behind them.

None of these are bugs in the forty lines. Every one of them is a property of the protocol, the browser's implementation of it, or the infrastructure between them — and every one is invisible until there's a proxy, a load balancer, a CDN, an expiring token, or a user with tabs.

## What It Is

**Server-Sent Events** is a one-way message stream from server to client carried inside a single, never-ending HTTP response, plus — and this is the part that matters — **a client implementation that lives in the browser and is specified**.

The wire format is almost too simple to describe. The valuable half is `EventSource`: it reconnects when the stream ends, it remembers the last message id and sends it back, and it does this identically in every browser because the HTML standard says exactly how. That is the entire 9.1b article — liveness, reconnection policy, resumption — delivered as a built-in.

The catch, and the subject of this article: **you didn't write those behaviours, but you still own their consequences.** The reconnection interval is the browser's. The retry decision is driven by your status codes whether or not you chose them deliberately. The resumption only works if your ids mean something. And the whole thing travels over HTTP, which means every intermediary between you and the user gets an opinion about buffering, compression, and idle timeouts.

Two quick placements, since the neighbours were settled elsewhere: whether to use SSE at all versus WebSockets or polling is 9.1a, and this article assumes you've made that call. And SSE is not the same as "streaming an HTTP response" — you can stream newline-delimited JSON through `fetch` and many systems do, but that gets you bytes over time without the framing, the ids, or the client contract. More on that trade in *Alternatives*, because it's the choice that most SSE deployments eventually face.

## Recognizing the Problem

- Output arrives in bursts rather than continuously, and only in deployed environments.
- The stream drops at a suspiciously round interval — 30, 60, or 300 seconds.
- Your access logs contain tokens.
- A failing endpoint receives more traffic than a working one.
- Some lines or events are missing after a reconnect, and only after a reconnect.
- Opening several tabs of your app makes the app stop working.
- `EventSource` fires `error` and the event object contains nothing useful.
- A `curl` against the origin streams perfectly; the same request through the load balancer doesn't.
- The stream works until your framework's async timeout, then dies with a server-side exception nobody can explain.

## How It Works

### The format, precisely

UTF-8 text. Fields are `field: value` lines; a blank line dispatches the accumulated event. Lines beginning with `:` are comments and do nothing.

```
: heartbeat

id: 4471
event: line
data: {"stream":"stdout","text":"npm WARN deprecated ..."}

data: first line
data: second line

retry: 15000
```

Four fields exist and nothing else. `data` accumulates — multiple `data:` lines are joined with a newline, which is the only way to send a multi-line payload. `event` names the event type the client listens for; without it, the client's `message` handler gets it. `id` sets the connection's *last event id*, which the browser will echo on reconnect. `retry` sets the reconnection delay in milliseconds, and is the only tuning knob the server has over client behaviour.

There's no framing to design, no length prefix, no binary. JSON payloads are safe because `JSON.stringify` never emits a literal newline; anything else you send needs the `data:` repetition rule applied by hand.

### The status code is your reconnection policy

The browser's behaviour on a failed or ended stream is specified, and it splits three ways:

```
200 + text/event-stream            → stream opens
stream ends (network, close, EOF)  → wait `retry`, reconnect with Last-Event-ID
500, 502, 503, 504                 → wait `retry`, reconnect          ← the loop
any other status (401, 403, 404,
204, or a wrong Content-Type)      → fail permanently: `error`, CLOSED, no retry
```

Read that table twice, because it explains the fourth incident exactly. A crashing endpoint returning 500 gets retried forever by every client; a 401 stops cleanly and lets your app show a login prompt. **The distinction between "retry forever" and "give up" is a status code you may have chosen carelessly**, and the correct instinct is the one 9.1b arrived at with close codes: the transport's error vocabulary is how you tell a client what to do next, so pick the values deliberately.

Two consequences worth internalizing:

Your expired-token path must return **401, not 500**. An auth middleware that throws — and therefore 500s — converts every expired session into an infinite retry loop against your auth system, which is the worst possible traffic to generate at the worst possible time.

There is **no backoff and no jitter**. The browser waits a fixed interval (a few seconds by default) and reconnects. A deploy that drops 20,000 streams brings them all back inside one window, repeatedly, if the new pods aren't up. The only lever is `retry:`, and it can only be sent on a stream that successfully opened — which suggests a genuinely useful trick for incidents and drains: respond **200 with `text/event-stream`**, emit `retry: 30000` and a single event telling the client what's happening, then close. You've used the protocol to reprogram the client's retry interval on the way out.

### Resumption, and the id you should have chosen

On reconnect the browser sends `Last-Event-ID: <the last id it dispatched>` as a request header. Your handler reads it, resumes from there, and the user never notices the gap. That's the whole mechanism, and the design decision inside it is what the id *is*.

The rule: **an id must be meaningful to a server that has no memory of the previous connection.** It may land on a different pod (9.1c), a different process, a different deploy. So:

- A per-connection counter is wrong. It's the fifth incident.
- A log line offset scoped to the build in the URL is right, because the URL supplies the rest of the identity.
- For a multiplexed feed, the id needs global meaning: a stream entry id, a monotonic sequence from a shared counter, or an opaque cursor you can decode.

And since no server can keep history forever, resumption needs the same escape hatch 9.1b needed: when the id is older than your retention, don't fail — send a snapshot of current state and continue from now. A resume path without a snapshot fallback is a resume path that breaks precisely when a client has been away longest.

One thing the client won't do: it sends the id of the last event it *dispatched*, so if your handler crashes while processing an event, the browser still counts it as delivered. At-least-once with a client-side dedupe remains the honest model.

### Everything in the path wants to buffer

```
your process ──► app server ──► reverse proxy ──► load balancer ──► CDN ──► browser
     flush?         flush?        buffers!          idle timeout    compresses!
```

The fixes are short, and all of them are required rather than optional:

- **`Cache-Control: no-cache, no-transform`** — the second directive is the one that matters here; it asks intermediaries not to re-encode the body, which is what stops a well-meaning gzip layer from buffering your stream.
- **`X-Accel-Buffering: no`** — nginx-specific, honoured by several other proxies, and equivalent to `proxy_buffering off` for that response only.
- **Disable compression for `text/event-stream`** at the CDN and the app server. SSE payloads are small and repetitive, so compression is genuinely attractive, and it costs you liveness unless the compressor flushes per event. Most don't by default.
- **Flush after every event.** Framework-dependent, always necessary, and easy to lose when someone adds a response wrapper.
- **A heartbeat comment every 15–25 seconds**, below the shortest idle timeout in the chain. `: \n\n` is eight bytes and prevents the second incident.

And the operational rule that saves the most time: **test with `curl -N` through the real ingress path, not against localhost.** A stream that behaves on `127.0.0.1` and batches through the load balancer is the default outcome, not an unusual one. That `curl` works at all is a real advantage of SSE over WebSockets — your transport is inspectable with tools you already have.

### Authentication, and the three bad options

`EventSource` sends no custom headers. There is no fourth option, so pick knowingly:

**Cookies.** Correct and simple when the stream is same-origin: the browser attaches them. Cross-origin requires `new EventSource(url, { withCredentials: true })`, an explicit `Access-Control-Allow-Origin` (not `*`), `Access-Control-Allow-Credentials: true`, and `SameSite=None; Secure` on the cookie. Test resumption cross-origin specifically — it's a separate request with a header on it, and it's where CORS configurations turn out to be incomplete.

**A ticket in the query string.** Fetch a short-lived, single-use token over an authenticated request, then open the stream with it. This is fine if and only if it's genuinely short-lived (tens of seconds), single-use, and scoped to the one resource. What makes the opening incident bad isn't the query string, it's that the thing in it was a general-purpose eight-hour credential.

**Drop `EventSource`.** Use `fetch` with a `ReadableStream`, set whatever headers you like, and implement reconnection and `Last-Event-ID` yourself. You keep the wire format and lose the built-in client. This is more common than it sounds — see *Alternatives*.

Whichever you choose, the 9.1b problem remains: a stream authorized at 09:00 can still be open at 17:00. Cap the connection lifetime server-side — close with a normal end-of-stream after an hour and let the browser reconnect, which re-runs your auth path for free. Reconnection being cheap and automatic is exactly what makes this practical.

### The connection budget

Over **HTTP/1.1**, browsers allow about six connections per origin, *shared across all tabs*. Each open stream takes one. Six streams and the origin is saturated — not just for streams, for everything, which is why the seventh tab appears completely broken rather than merely missing its log.

Over **HTTP/2** a stream is one multiplexed stream among a hundred on a single connection, and the problem is essentially gone. This is the single most important deployment fact about SSE, and it comes with a caveat: it must be HTTP/2 all the way to the browser, so a local dev server on plain HTTP/1.1 will reproduce the old behaviour and mislead you in both directions.

Two design habits follow regardless:

**One stream per tab, multiplexed.** Don't open a stream per widget. Open one, use `event:` types to route, dispatch internally. This is free and it's the difference between one connection and five.

**Consider one stream per *browser*.** With several tabs of the same app, elect a leader (a `SharedWorker`, or a lock plus `BroadcastChannel`) that holds the only connection and rebroadcasts to the others. Real work, real payoff for products where users keep tabs open — and a decision that's much easier to make before the client code has five direct `EventSource` consumers.

### The thread you're holding

An SSE response occupies a connection for its entire lifetime. Whether it also occupies a **worker thread** depends entirely on your runtime, and this is where the same code has wildly different ceilings:

- Event-loop runtimes (Node, Go, async Python) hold a socket and a small amount of state. Thousands of streams per process is routine.
- Thread-per-request models hold a worker for the duration — a pool of 200 means 200 concurrent viewers and then a hung application. This is the failure mode in classic Spring MVC without async, sync gunicorn workers, Puma, and PHP-FPM, and it doesn't degrade gracefully; it stops.

The fix in JVM-land is the servlet async context, which is precisely what the implementation below is about.

## When It's Appropriate

- **Server-to-client text, and the client's replies fit in ordinary requests.** Build logs, job progress, an export that finishes, a notification feed, a dashboard refreshing every few seconds, generated tokens streaming into a UI.
- **Long-lived streams where disconnection is routine** — a laptop lid, a train, an eleven-minute build. Free resumption is worth the most here, and it's the thing you'd otherwise spend a sprint on.
- **You're behind infrastructure you don't fully control.** SSE is an HTTP response; corporate proxies that break `Upgrade` don't break this.
- **You want your existing HTTP machinery to keep working**: auth middleware, rate limiting, access logs, tracing, `curl`. Everything that 9.1b said you'd have to rebuild for WebSockets, you keep.
- **Concretely:** hundreds to low tens of thousands of concurrent viewers, a few messages per second each, HTTP/2 available, an async-capable server runtime.

## When It's Unnecessary or Overkill

- **The client needs to send at rate.** Typing indicators, cursor positions, game input. One HTTP request per message is not a design; that's the WebSocket case.
- **Binary payloads.** Base64 over SSE is a 33% tax and a bad smell.
- **Message rates below one per minute with a tolerant UI.** Polling (9.1a, level 0 or 1) has fewer failure modes than anything described above.
- **A blocking runtime you can't make async.** A stream per worker thread is a ceiling measured in hundreds; long polling costs the same per client but frees the worker between events.
- **Sub-50-millisecond round trips both ways.** The return path is a fresh HTTP request each time.
- **Stuck on HTTP/1.1 with a multi-tab product.** The six-connection budget will produce bug reports you can't fix in application code.

## Trade-offs

**The return path is a separate channel.** Every client action is an ordinary request, and now you have a correlation problem: the user clicks "cancel build," the POST returns 202, and the *stream* eventually says the build stopped. Which is fine, but the UI has two sources of truth and needs to decide what to show in between. The usual answer — client-generated request ids echoed back through the stream — is work that a bidirectional transport wouldn't need.

**Client behaviour is mostly not yours.** Fixed retry interval, no jitter, no exponential backoff, no way to distinguish "server restarting" from "your network died" beyond a contentless `error` event. You get `retry:` and status codes, and that's the whole control surface.

**Compression is effectively off.** Your payloads travel uncompressed unless you flush per event, which costs bandwidth on repetitive text — and log lines are extremely repetitive text.

**One held connection per viewer, always.** The standing cost from 9.1a applies in full: memory, file descriptors, a slot in every proxy, and in some runtimes a thread. Idle viewers cost the same as active ones.

**Header-based auth is unavailable** without giving up the built-in client, and the workarounds each have a specific sharp edge.

**Debuggability is unusually good.** Worth stating as a trade-off in your favour, since it's rare: `curl -N` shows exactly what a browser would see, the format is human-readable, and your existing HTTP observability keeps working. When something is wrong, you can look at it.

## Alternatives

- **Long polling** (9.1a, level 1). If your event rate is low, this delivers the same latency with no held connections and no buffering hazards.
- **WebSockets** (9.1b). The answer when the client needs to talk back at rate, at the cost of rebuilding everything this article gets for free.
- **`fetch` + `ReadableStream`, keeping the SSE wire format.** Full control of headers and method, works with a POST body, and you write the reconnection and `Last-Event-ID` logic yourself — or use a library that does (`@microsoft/fetch-event-source` exists for precisely this and documents the gaps well). Worth knowing: **the largest SSE deployment most developers touch today doesn't use `EventSource` at all** — streaming LLM APIs send SSE framing in response to a POST with an `Authorization` header, which `EventSource` can do neither of. The wire format is the durable part; the client is swappable.
- **NDJSON over a streamed response.** Newline-delimited JSON, no framing rules, no ids. Simpler, and you've given up resumption — which is exactly what you were buying.
- **A managed provider or a real-time server** (Ably, Pusher, Centrifugo). They terminate connections for you and usually speak SSE as one of several transports.

## How to Achieve It

**Level 0 — the endpoint, correctly.** `id:` on every event, a heartbeat comment, `Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no`, compression disabled for the content type, and a flush per event. Verify with `curl -N` through the real ingress.
*Next when:* it's live and someone's token expires.

**Level 1 — status codes as policy.** 401 for auth failures so clients stop; a considered decision about what your 5xx path does; a capped connection lifetime so auth is re-evaluated.
*Next when:* a reconnect visibly loses data.

**Level 2 — resumption that survives a different pod.** Ids meaningful without session state, a retention window, and a snapshot response when `Last-Event-ID` is too old.
*Next when:* users keep multiple tabs, or the connection budget shows up in support tickets.

**Level 3 — one stream per tab, multiplexed by event type.** Then, if it's warranted, one per browser via a leader election.
*Next when:* you need headers, a POST body, or reconnection behaviour the browser won't give you.

**Level 4 — a fetch-based client.** Same wire format, same server, a client you control. Deliberately last: you're giving up the specified behaviour that was the reason to choose SSE.

## Implementation

Java with Spring's `SseEmitter`, because the JVM is where the thread-model question is sharpest — a servlet container makes the difference between "async" and "not" visible as a class you must return, and the framework supplies a construct whose entire purpose is to hold a connection without holding a worker.

```java
@GetMapping(value = "/builds/{id}/log", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter stream(
        @PathVariable String id,
        @RequestHeader(value = "Last-Event-ID", required = false) Long lastEventId,
        HttpServletResponse response) {

    response.setHeader("Cache-Control", "no-cache, no-transform");
    response.setHeader("X-Accel-Buffering", "no");          // ← aside 1

    SseEmitter emitter = new SseEmitter(0L);                // ← aside 2
    long from = lastEventId != null ? lastEventId + 1 : 0;

    registry.add(id, emitter);                              // ← aside 4
    emitter.onCompletion(() -> registry.remove(id, emitter));
    emitter.onError(e     -> registry.remove(id, emitter));
    emitter.onTimeout(()  -> registry.remove(id, emitter));

    catchUp(emitter, id, from);                             // ← aside 3
    return emitter;
}
```

Sending one event, and the heartbeat that keeps the path open:

```java
void send(SseEmitter emitter, LogLine line) {
    try {
        emitter.send(SseEmitter.event()
                .id(Long.toString(line.offset()))           // ← aside 3
                .name("line")
                .data(line.json(), MediaType.APPLICATION_JSON));
    } catch (IOException e) {
        emitter.completeWithError(e);                       // ← aside 5
    }
}

@Scheduled(fixedRate = 20_000)
void heartbeat() {
    for (SseEmitter e : registry.all()) {
        try { e.send(SseEmitter.event().comment("beat")); }
        catch (IOException ex) { e.completeWithError(ex); } // ← aside 6
    }
}
```

**Aside 1 — headers must be set before the emitter is returned.** Once Spring starts writing the stream the response is committed and header changes are silently ignored. The version of this bug that costs an afternoon is setting them in a filter that runs *after* the controller, producing a stream that works in tests and buffers in production.

**Aside 2 — `new SseEmitter()` with no argument is a timer on your feature.** The default falls through to the container's async timeout, which on Tomcat is thirty seconds; the stream dies with an `AsyncRequestTimeoutException` that reads like a server fault and is actually configuration. Passing `0L` means no timeout under the Servlet contract — and it makes the heartbeat mandatory rather than merely advisable, because nothing else will now detect a dead peer.

**Aside 3 — catch-up before subscribe, and the id is an offset.** The handler reads `Last-Event-ID`, replays from that offset, *then* joins the live stream. Because the id is the byte or line offset within the build named in the URL, it's meaningful to any pod on any deploy — nothing about it depends on the connection that produced it. The failure mode this avoids is subscribing first and then replaying, which delivers lines out of order, and ordering is the one thing a log viewer cannot tolerate.

**Aside 4 — the registry is a leak waiting for a missing callback.** All three of `onCompletion`, `onError`, and `onTimeout` must remove the emitter, because they're mutually exclusive and you don't get to choose which one fires. Forget `onTimeout` and you accumulate dead emitters at exactly the rate your network drops connections.

**Aside 5 — a write to a dead client is how you learn it's dead.** There's no other signal: the peer vanishing produces nothing until you try to send. That's why the heartbeat is doing two jobs — keeping intermediaries from closing the connection, and being the periodic write that surfaces a client that left twenty minutes ago.

**Aside 6 — this loop is the backpressure problem again, in Java.** `send` blocks on a slow client's socket, so one viewer on a bad connection stalls the scheduler thread and delays every other heartbeat behind it. The same shape as 9.1b's fan-out, the same fix: a bounded per-client queue and a dedicated writer, or at minimum a thread pool sized so one slow client can't monopolize it. Framework convenience does not remove the constraint; it just moves it somewhere less obvious.

**What's not here.** `registry` is in-process, so a client that reconnects onto another pod finds nobody holding its build — which is survivable *only* because `Last-Event-ID` is an offset into durable storage rather than a pointer into memory. That's 9.1c's problem solved by choosing the id well, which is the cheapest form of distributed design available.

## Further Reading

- **HTML Living Standard, §"Server-sent events"** (html.spec.whatwg.org) — normative and short. The paragraph enumerating which status codes reconnect and which fail permanently is the one to read; almost no tutorial mentions it and it determines your worst-case traffic.
- **MDN, _Using server-sent events_** — the practical companion, with the `withCredentials` and cross-origin details spelled out.
- **nginx documentation on `proxy_buffering` and `X-Accel-Buffering`** — and, if there's a CDN, its documentation on compressing `text/event-stream`, which is where the second buffering layer hides.
- **RFC 9111 §5.2.2, `no-transform`** — what you're actually asking intermediaries not to do, and why it's a different request from `no-cache`.
- **Spring's `SseEmitter` javadoc and the Spring MVC asynchronous requests chapter** — particularly the interaction between emitter timeouts, container async timeouts, and `spring.mvc.async.request-timeout`.
- **`@microsoft/fetch-event-source`** (GitHub) — read the README even if you don't use it; it's an honest catalogue of what `EventSource` can't do and why teams leave it.
- **Any major LLM provider's streaming API documentation** — a live example of SSE framing over a POST with header auth, which is the deployment shape this article's *Alternatives* section is pointing at.

A TypeScript sibling would carry the client half, which is a genuinely different article: leader election across tabs so one connection serves many, a fetch-based reader that keeps the wire format while adding headers, and reconnection tied to `visibilitychange` so a backgrounded tab isn't retrying against a server that's already under load. Not yet written.

---

The habit to carry out of this: when a protocol gives you behaviour for free, find out precisely what triggers it before you rely on it. The browser's reconnection is excellent and it is not configurable — which means your status codes, your ids, and your heartbeat interval stopped being implementation details and became the API you present to a client you didn't write.
