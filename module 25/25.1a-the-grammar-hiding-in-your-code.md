# The Grammar Hiding in Your Code: Messages, Plurals, and Select

_Module 25.1a — Internationalization & Localization_

## The Problem

Suppose you build a document-sharing product for architecture practices. Firms upload drawing sets, organize them into folders, share them with clients, and leave review comments on individual sheets. The front end is React, the API is TypeScript, and there are about 1,400 pieces of user-visible text, all in English. Then the company signs a reseller in Poland and a large client in Germany, and localization gets a quarter.

The plan sounds reasonable. Move every string literal into `en.json`, send the file to a translation agency, get back `pl.json` and `de.json`, and load one by locale. Two engineers spend three weeks on the extraction. Here's a representative handful of lines, before and after:

```tsx
// before
`${count} file${count === 1 ? "" : "s"} deleted`
`${user.name} shared ${n} files with you`
`Delete this ${item.kind}?`
<Button>Open</Button>        {/* on a file row */}
<Badge>Open</Badge>          {/* on a comment thread */}

// after
`${count} ${t(count === 1 ? "file_deleted" : "files_deleted")}`
`${user.name} ${t("shared")} ${n} ${t("files_with_you")}`
`${t("delete_this")} ${t(item.kind)}?`
<Button>{t("open")}</Button>
<Badge>{t("open")}</Badge>
```

The agency receives 1,400 entries, many of them two or three words long, with no screenshots. It sends back accurate translations of every one. The Polish and German releases ship, and the reports start the next morning:

- **Polish counts are wrong most of the time.** Deleting five files says "5 pliki usunięte". It should say "5 plików zostało usuniętych". Twenty-two files comes out right and twelve comes out wrong again. The code knows two forms, "one" and "not one". Polish uses three for whole numbers, chosen by the last digits, and the verb changes along with the noun.
- **German folder deletion asks the wrong question.** "Delete this" came back as "Löschen Sie diese", which works before *Datei* (file, a feminine noun) and fails before *Ordner* (folder, masculine), which needs *diesen*. "Löschen Sie diese Ordner?" is grammatical German, but it means "Delete these folders?", plural, which is not what the user is doing.
- **German sharing notifications are word salad.** German puts the past participle at the end of the clause: "Anna hat 3 Dateien mit Ihnen geteilt." The code puts `t("shared")` second, so the best the translator can manage produces "Anna hat geteilt 3 Dateien mit Ihnen".
- **Unresolved comment threads say "Öffnen".** That's the verb, "to open". The status is *Offen*. English uses one word for both, the code used one key for both, and the translator picked the button.
- **Half of Polish users are announced with the wrong grammar.** Polish past-tense verbs agree with the subject's gender: *Anna udostępniła*, *Piotr udostępnił*. The translator of "shared" had to pick one ending, picked the masculine, and every woman who shares a file gets it.

By the end of the first month there are 71 bug reports from the two new locales, and 64 of them need a code change: a new key, a new branch, a new argument, a new deploy. None of them is a translation mistake. Every entry was translated correctly as given. The extraction produced a file that looked internationalized, but the grammar of English — how many plural forms exist, where the verb goes, which words agree with which — was still written in TypeScript, where no translator can reach it.

## What It Is

**Internationalization** (i18n: an *i*, eighteen letters, an *n*) is the engineering work that lets a product be adapted to a language or region without changing its code. **Localization** (l10n) is the adaptation itself for one locale: the translations, the formats, sometimes the content. The team above localized a product that hadn't been internationalized. The distinction matters because the failures showed up in the translations while the causes sat in the code.

This article covers the text part of i18n, usually called **message externalization**. Its unit is the **message**: a complete, translatable piece of user-visible text (a sentence, a label, a button) with named placeholders for the values the code supplies. Any grammar that depends on those values is expressed *inside* the message, where each language can write its own. The code passes an ID and a set of facts, and the translator owns every word and the order they come in.

```
 a strings file (what the team built)        a message catalog (what they needed)

 code     decides the plural form            code     passes facts: count, kind,
          decides the word order                      actor, actorGender
          glues fragments together                    names each message by meaning
             │                                           │
             ▼                                           ▼
 catalog  one word or phrase per key         catalog  one whole sentence per message,
          (translators fill in blanks)                with plural and select branches
                                                      (translators own the grammar)
```

The most widely supported syntax for messages is **ICU MessageFormat**, named after the ICU libraries that popularized it, and this article uses it throughout:

```
{count, plural, one {# file was deleted.} other {# files were deleted.}}
```

Its successor, Unicode MessageFormat 2, is covered under Alternatives. Three neighbors get their own articles in this module: formatting the numbers and dates that appear inside messages (25.1b), deciding which locale a request is in (25.3a), and the pipeline that gets messages translated and back into the product (25.2a).

## Recognizing the Problem

- `count === 1 ?`, `+ "s"`, or a `pluralize()` helper anywhere near user-visible text.
- Template literals or `+` joining translated pieces into a sentence.
- Catalog entries that aren't sentences: "by", "and", "of", "shared", or keys ending in `_prefix`, `_suffix`, `_part2`.
- A translated noun passed into a translated sentence: `t("delete_this", { thing: t(kind) })`.
- One key with several call sites that play different roles.
- A link or a bold word in the middle of a sentence, held together by three keys.
- Every locale file has exactly the plural keys that English has.
- `.toUpperCase()`, `capitalize()`, or enum names shown as text (`status.replace("_", " ")`).
- Translators asking what a string refers to, or, worse, never asking.
- Bugs filed against a translation that can only be fixed with a deploy.

## How It Works

### A whole sentence is the smallest unit

The smallest thing you send a translator should be the smallest thing that's grammatically complete in every language you'll support. In practice that's a sentence, a label, or a button. Placeholders are named, never positional and never concatenated, so the translator can move them anywhere the language needs:

```
en  {actor} commented on {sheet}.
de  {actor} hat {sheet} kommentiert.
ja  {actor}さんが{sheet}にコメントしました。
```

Nothing in the code decides where `{sheet}` goes. Named placeholders also document themselves: `{actor}` tells a translator it's a person, while `{0}` tells them nothing.

### Plurals are categories, not "is it one?"

Languages group numbers into grammatical forms in different ways. The Unicode Common Locale Data Repository (CLDR) defines, for each language, which of six **plural categories** it uses (`zero`, `one`, `two`, `few`, `many`, `other`) and a rule that maps any number to one of them:

```
language   categories                        how numbers map
English    one, other                        1 → one; 0, 2, 5, 1.5 → other
French     one, many, other                  0, 1, 1.5 → one; 2, 5 → other; 1 000 000 → many
Polish     one, few, many, other             1 → one; 2–4, 22–24, 32–34… → few;
                                             0, 5–21, 25–31… → many; 1.5 → other
Arabic     zero, one, two, few, many, other  0, 1, 2 each their own; 3–10 → few;
                                             11–99 → many; 100–102 → other
Japanese   other                             everything → other
```

French treats zero as singular ("0 fichier"). Japanese doesn't inflect nouns for number at all. A message system that only asks "is it one?" is wrong for all of these, in different places.

Four consequences follow.

**The code never picks the form; it passes the number.** Each translation contains the categories its own language uses. The English message has two branches, the Polish one has four, and the Japanese one has a single `other`. The catalog is asymmetric by design, so "every locale has the same keys as English" is exactly the wrong thing to check.

**The whole sentence goes inside each branch**, because the rest of the sentence often changes with the number. English does it too: *was* versus *were*. Polish does it more:

```
1   plik został usunięty         one
2   pliki zostały usunięte       few
5   plików zostało usuniętych    many
```

So the messages look like this, with a complete sentence at every leaf:

```
en  {count, plural, one {# file was deleted.} other {# files were deleted.}}

pl  {count, plural,
      one   {# plik został usunięty.}
      few   {# pliki zostały usunięte.}
      many  {# plików zostało usuniętych.}
      other {Usunięto pliki: #.}}
```

`#` is replaced by the number, formatted for the locale. Polish `other` only fires for fractions, which can't happen with files, but ICU requires an `other` branch in every plural, so the translator writes a safe "Deleted files: #." label for it.

**Exact matches aren't categories.** `=0 {No files}` matches the number zero in every language. `zero {…}` is a grammatical category that only some languages have (Arabic, Latvian, Welsh), and English's rules never choose it. An English message that uses `zero` to mean "none" silently never shows that branch.

**Choose the category from the number as displayed.** If 1.04 is rounded to "1" on screen, the plural has to be chosen for 1. If 1 is shown as "1.0", CLDR puts English in `other`. When you round or fix decimal places for display, pass the rounded number, or give the plural rules the same fraction-digit options (`Intl.PluralRules` accepts `minimumFractionDigits` and `maximumFractionDigits` for this). Otherwise the digits say one thing and the grammar says another.

Ordinals (1st, 2nd, 3rd, 4th, 11th, 21st) are a separate rule set with their own categories. English uses four for them (`one`, `two`, `few`, `other`); many languages use one. ICU spells this `{place, selectordinal, …}`.

### Select: facts that English doesn't need

Some grammar depends on things that aren't numbers. `select` branches on a string:

```
en  {kind, select, folder {Delete this folder and everything in it?} other {Delete this file?}}
de  {kind, select, folder {Diesen Ordner und seinen gesamten Inhalt löschen?} other {Diese Datei löschen?}}
```

That fixes the German "this" problem at its root. The code no longer inserts a translated noun into a translated sentence. It passes the *kind*, and each language writes a whole sentence for each kind, with whatever agreement it needs. The general rule: **never interpolate one translated string into another.** The outer sentence can't know the inner word's gender, case, or number, and in many languages it has to.

The same mechanism covers people. Polish past-tense verbs agree with the subject's gender, and so do French past participles after *être* ("Marie a été ajoutée au projet", "Paul a été ajouté au projet"). This leads to the principle the opening team was missing: **the code passes every grammatically relevant fact it has, even when English ignores it.** English doesn't care about the actor's gender, and Polish does, so the argument has to exist. Adding it after launch is a code change and a deploy in every call site, which is precisely the failure from the opening.

In ICU MessageFormat the only way to tell translators and tooling that an argument exists is to use it in the source message. So the English source contains a `select` with a single branch. It looks odd, but it's the standard idiom:

```
en  {actorGender, select, other {{count, plural,
      one   {{actor} shared # file with you.}
      other {{actor} shared # files with you.}}}}
```

The Polish translation uses what English declined to:

```
pl  {actorGender, select,
      female {{count, plural,
        one   {{actor} udostępniła Ci # plik.}
        few   {{actor} udostępniła Ci # pliki.}
        many  {{actor} udostępniła Ci # plików.}
        other {{actor} udostępniła Ci pliki: #.}}}
      male {{count, plural,
        one   {{actor} udostępnił Ci # plik.}
        few   {{actor} udostępnił Ci # pliki.}
        many  {{actor} udostępnił Ci # plików.}
        other {{actor} udostępnił Ci pliki: #.}}}
      other {{count, plural,
        one   {{actor} udostępnił(a) Ci # plik.}
        few   {{actor} udostępnił(a) Ci # pliki.}
        many  {{actor} udostępnił(a) Ci # plików.}
        other {{actor} udostępnił(a) Ci pliki: #.}}}}
```

Two honest things about that message. First, most products don't know a user's gender and shouldn't demand it, so `other` is the branch most people will see, and it has to read acceptably. The "udostępnił(a)" form is a common Polish convention for exactly this case. Pass `female` or `male` only when the user has actually told you, for example by choosing pronouns. Second, it's twelve sentences. Every selector multiplies the branches, and translators start making inconsistent small edits somewhere around the tenth. A workable limit is two selectors per message; past that, split the message or change the UI so it needs less grammar.

### Meaning, not English, identifies a message

"Open" the button and "Open" the status are different messages that happen to share English text. They need different IDs (`file.action.open`, `thread.status.open`), because German, and most other languages, will translate them differently. Deduplicating messages because their English matches is a false economy that creates bugs in every other language. gettext has a dedicated field for this (`msgctxt`) for the same reason.

Each message also carries a **description** for the translator: what the placeholders are, where the text appears, and any length limit. "Open" with the description "Status badge on a comment thread: not yet resolved" can't be mistranslated as the verb. The description is what screenshots are too expensive to provide for 1,400 strings.

### Markup, components, and lists stay inside the message

A link inside a sentence is still one sentence:

```
en  By continuing you agree to the <terms>Terms of Service</terms>.
de  Mit dem Fortfahren stimmen Sie den <terms>Nutzungsbedingungen</terms> zu.
```

The code maps `<terms>` to a real link at render time, and the translator moves the tag along with the phrase. Splitting this into `agree_prefix`, `terms_link` and `agree_suffix` is the concatenation bug again, since the German sentence ends with a separable prefix (*zu*) after the link. The same applies to a control in the middle of a sentence, such as "Show [10 ▾] per page": pass the dropdown as a placeholder value and let the translator place it.

Lists of names are grammar too. "Anna, Piotr, and Eva" in American English is "Anna, Piotr and Eva" in British English and "Anna, Piotr und Eva" in German. `Intl.ListFormat` produces the right conjunction and punctuation for the locale. A truncated list ("Anna, Piotr, and 3 others") is a plural message with two names and a count as arguments, not a list with a suffix appended.

### Numbers and dates are arguments, not strings

`#`, `{count, number}` and `{due, date, medium}` are formatted by the message library for the message's locale: 1,250 in English, 1.250 in German, 1 250 in Polish. Formatting itself belongs to 25.1b. The rule that belongs here is **never format a number into a string and then pass the string.** Plural selection needs the number, and the formatter needs the locale.

Case changes are the same kind of mistake. `.toUpperCase()` on translated text breaks German nouns, which are always capitalized, and Turkish, whose dotted and dotless *i* uppercase differently. If the design calls for capitals, use CSS `text-transform` with the correct `lang` attribute on the page, or let the translator write the text in capitals.

### What happens at runtime

```
code                            catalog["pl"]                      formatter
t("file.deleted", {count: 5})   "{count, plural, one {…}           Intl.PluralRules("pl")
          │                       few {…} many {…} other {…}}"       .select(5) → "many"
          └──── id ─────────▶           │                                  │
                                        └──── parse (or precompiled) ──────┴──▶ "5 plików zostało usuniętych."
```

Two paths need deliberate decisions. **A missing message** falls back along a chain, typically to the source language, and gets reported. How to build the chain (`pt-BR` → `pt` → `en`) is 25.3a's job. **A broken message** — a translator's unbalanced brace, or a translation that references an argument the code stopped passing — must not throw. In a render path, an exception can blank the whole screen for every user in that locale. Fall back to the source message for that one string, report it, and find the problem in CI next time rather than in production.

Parsing message syntax at runtime also costs time and bundle size. Most toolchains can precompile messages at build time, which removes the parser from the browser bundle and turns syntax errors into build failures.

## When It's Appropriate

- **A second language is on the roadmap within a year or so.** Retrofitting cost the team above six engineer-weeks of extraction and a month of bug fixes for 1,400 strings. Writing messages from the start costs a function call and a description line per string.
- **You have one language and a count anywhere in the UI.** "1 files" and "0 file" are English bugs, and fixing them properly uses the same machinery.
- **Text generated away from the browser:** emails, push notifications, PDF invoices, CSV headers. A server renders these, it has to use the *recipient's* locale rather than the request's (Module 14, 25.3a), and it's the text most often forgotten during extraction.
- **Target languages with rich grammar**, such as Slavic and Baltic languages, Arabic, or Hebrew, or a product that is mostly sentences about people and counts: activity feeds, notifications, audit trails.

## When It's Unnecessary or Overkill

- **Text for developers.** Logs, exception messages, metric names and internal CLI output stay in one language. Translated logs can't be grepped or correlated across instances, and the person reading them at 3 a.m. is an engineer, not a customer. For APIs, Module 7's split applies: a stable error code plus a default message, which clients translate.
- **An internal admin tool for 15 people in one office.** Routing strings through a function is cheap, so do that. Select branches, descriptions and CI validation aren't worth it until a second language is real.
- **Arguments for facts you don't have.** If the product will never know the actor's gender, don't add `actorGender` for completeness. Say so in the description and let translators write around it. An argument that's always `other` is noise in every locale.
- **A full translation workflow before anything has been translated.** The levels below, and the tooling in 25.2a, come in order.
- **User-generated or catalog content**, such as product descriptions, help articles, or comments. That's data, not UI, and translating it is a different problem (25.3b).

## Trade-offs

- **Indirection.** `t("file.deleted", { count })` hides the words. Finding the code behind a string you can see on screen now goes through the catalog, and reviewers need to read message diffs alongside code diffs. Editor plugins that show the English inline help a lot.
- **Translators write code that you ship.** A missing brace in `pl.json` is a runtime error written by someone who can't run your test suite. You need validation in CI and a non-throwing fallback at runtime, or both failures reach users.
- **Arguments are an API.** Rename `{count}` to `{n}` and every locale breaks. Add `actorGender` and every locale needs retranslation. Changing a message's arguments has the cost of a breaking change, spread across every language you support.
- **Stale translations, one way or another.** With meaning-based IDs, an English copy change leaves the Polish text saying the old thing, silently, unless the pipeline flags changed source text (25.2a). With the English text as the key (gettext's approach), every copy tweak orphans the translation. You choose which failure you prefer, not whether to have one.
- **Asymmetry makes checking harder.** You can't compare keys with English. You have to check each locale against its own CLDR rules, which is what the implementation below does.
- **Combinatorial growth.** Nested selects produce messages that are hard to review and easy to get slightly inconsistent. The cost lands on translators and reviewers, not on the developer who added the second selector.
- **Size and speed.** Catalogs for every locale, plus a message parser, can add measurably to a front-end bundle. Precompiling and loading one locale at a time fixes most of it, at the price of more build configuration.
- **Tests that match on English text break when copy changes.** Select elements by role or test ID instead, and run a pseudo-locale (below) so tests don't quietly depend on English.

## Alternatives

**Designing the grammar out of the UI.** "Files: 5" and "Shared by: Anna" need no plurals or agreement in almost any language. It's cheap and robust, and it reads as stilted. It suits dense UIs such as tables and metadata panels well, and it suits notifications and anything people read as prose badly. Most products use it in some places, and that's a legitimate choice rather than a failure.

**gettext.** The English source text is the key (`msgid`), `msgctxt` separates homonyms like the two "Open"s, and each language's `.po` file declares its own plural formula in a header (`Plural-Forms: nplurals=3; plural=…`). It's mature, with a huge base of translator tooling, and it's standard in C, PHP, Python, Django and WordPress. Plurals work well. Select has no built-in syntax, so gender and kind end up encoded as separate contexts. Source text as key makes catalogs readable and turns copy edits into orphaned translations, which fuzzy matching partly recovers.

**Key-suffix plurals** (the i18next style: `file_deleted_one`, `file_deleted_few`, `file_deleted_many`, `file_deleted_other`). Plural categories still come from CLDR through `Intl.PluralRules`, but each form is its own key in plain JSON, which some translators and tools prefer to nested braces. The cost is that one message is spread over several keys, and select is expressed through more suffixes. It works if the tooling understands the grouping.

**Project Fluent** (from Mozilla) was designed around the asymmetry this article keeps running into: a translation can branch on things the source language doesn't. Its **terms** can carry attributes, so a translator can define `-folder` once with `.gender = masculine` and have other messages select on it. That solves the German "this" problem without adding a select to every message. The ecosystem is smaller than ICU's.

**Unicode MessageFormat 2 (MF2)** is the successor to ICU MessageFormat, and it became a stable part of the Unicode standard in 2025. It matches several variables in one flat table instead of nested selects, which directly addresses the twelve-sentence Polish message above, and it has a cleaner syntax with extensible formatting functions. The mainstream JavaScript libraries and most translation-management systems still use the original format, and the proposal to build MF2 into JavaScript as `Intl.MessageFormat` isn't expected to land soon. Adopting it today means a thinner toolchain. Conversion tools from the original syntax exist.

**Machine or LLM translation of the UI** changes who fills the catalog, not how the code has to be written. A model handed the word "shared" guesses exactly as the agency did. Handed a full ICU message and a description, it does much better. That belongs in the pipeline (25.2a), and it depends on everything in this article already being in place.

## How to Achieve It

**Level 0: literals in code.** Where most products start.

**Level 1: a message function, English only, with real plurals.** Install a message library, provide the locale at the app root, and route new text through messages, fixing English plurals as you go. Nothing is translated yet.
_Next when:_ a decision to localize, or the third "1 files" bug.

**Level 2: stop the inflow, then convert.** Add a lint rule that flags string literals in UI components (most i18n ecosystems have one), make it an error for new code, and convert existing screens in order of traffic. Give every message an ID based on meaning and a description as you go, because adding descriptions to 1,400 strings later is a week nobody gets.
_Next when:_ new code passes the lint and the count of remaining literals is falling.

**Level 3: a pseudo-locale.** Generate a fake locale that brackets each message, swaps in accented letters, and pads length by 30–40%: `[Ƒîļé ŵåš ðéļéţéð·········]`. Unbracketed text on screen is still hard-coded. Brackets in the middle of a sentence reveal concatenation. Clipped text shows where layouts will break (25.2b).
_Next when:_ core flows look clean in the pseudo-locale.

**Level 4: extraction and validation in CI.** Extract messages into a catalog, and check every locale on every build: it parses, it uses only arguments the code passes, and its plurals cover its own language's categories. The implementation below is this step.
_Next when:_ it's time to send the catalog to translators.

**Level 5: the first real locale, then server-rendered text.** If you get any say in which language comes first, don't pick the easiest one. A language with four plural forms and gender agreement finds more problems in one round than three Romance languages do. Then move emails and notifications onto the same catalog, rendered in the recipient's locale (25.3a).

## Implementation

TypeScript, using FormatJS's `intl-messageformat` for formatting and its parser for the CI check. JavaScript is where most ICU messages are rendered today, and `Intl.PluralRules` exposes CLDR's plural data directly, which is what the check needs. In a React app you'd normally reach these through `react-intl`; the code below uses the underlying packages so the policy decisions stay visible.

The source catalog holds English text and the translator's context together:

```ts
// i18n/source.ts
export const source = {
  "file.deleted": {
    message: "{count, plural, one {# file was deleted.} other {# files were deleted.}}",
    description: "Toast after a bulk delete. count ≥ 1.",
  },
  "share.received": {
    message:
      "{actorGender, select, other {{count, plural, " +
      "one {{actor} shared # file with you.} other {{actor} shared # files with you.}}}}",
    description:
      "Notification. actor = the sharer's display name. actorGender = 'female' | 'male' | 'other'; " +
      "usually 'other', since we only know it when the user has chosen pronouns. English ignores it.",
  },
  "file.action.open":   { message: "Open", description: "Button on a file row. Opens the file." },
  "thread.status.open": { message: "Open", description: "Status badge on a comment thread: not yet resolved." },
} as const;

export type MessageId = keyof typeof source;
```

`MessageId` makes a typo in an ID a compile error. The two "Open" entries are the fix for the German badge.

The lookup function is where the runtime policy lives:

```ts
// i18n/t.ts
import { IntlMessageFormat } from "intl-messageformat";
import { source, type MessageId } from "./source";

type Catalog = Partial<Record<MessageId, string>>;
declare const catalogs: Record<string, Catalog>;   // loaded one locale at a time in real code
const compiled = new Map<string, IntlMessageFormat>();

export function t(locale: string, id: MessageId, args: Record<string, unknown> = {}): string {
  const translated = catalogs[locale]?.[id];
  if (translated !== undefined) {
    try {
      return String(compile(locale, translated).format(args));
    } catch (err) {
      // A translator's unbalanced brace, or an argument the code stopped passing.
      // Throwing here would blank the screen for everyone in this locale.
      report("broken-message", { locale, id, err });
    }
  } else {
    report("missing-message", { locale, id });
  }
  return String(compile("en", source[id].message).format(args));
}

function compile(locale: string, message: string): IntlMessageFormat {
  const key = `${locale}\u0000${message}`;
  let fmt = compiled.get(key);
  if (!fmt) {
    fmt = new IntlMessageFormat(message, locale);
    compiled.set(key, fmt);
  }
  return fmt;
}
```

> **Aside: the fallback is formatted as English, not as Polish.** Plural rules belong to the language of the *text*, not the user. Formatting the English source with Polish rules would pick `few` or `many`, and the English message has neither. Here it would fall through to `other` and look fine for integers, which is exactly how this bug hides until a fraction or an exact match shows up.

> **Aside: `report` needs deduplication, and a different mode in tests.** A missing message on a list page fires once per row, so collapse repeats before they reach your error tracker (Module 19). In development and CI, make `report` throw: the silent fallback exists to protect users, not to hide problems from you.

The CI check is the part most teams skip, and it's what makes asymmetric catalogs safe. It parses every translation and compares it against the source's arguments and the target language's own plural categories:

```ts
// scripts/check-messages.ts
import {
  parse, isArgumentElement, isNumberElement, isDateElement, isTimeElement,
  isSelectElement, isPluralElement, isTagElement, type MessageFormatElement,
} from "@formatjs/icu-messageformat-parser";

type Shape = { args: Set<string>; plurals: { arg: string; keys: string[]; ordinal: boolean }[] };

function shape(els: MessageFormatElement[], out: Shape = { args: new Set(), plurals: [] }): Shape {
  for (const el of els) {
    if (isArgumentElement(el) || isNumberElement(el) || isDateElement(el) || isTimeElement(el)) out.args.add(el.value);
    if (isSelectElement(el) || isPluralElement(el)) {
      out.args.add(el.value);
      if (isPluralElement(el)) {
        out.plurals.push({ arg: el.value, keys: Object.keys(el.options), ordinal: el.pluralType === "ordinal" });
      }
      for (const option of Object.values(el.options)) shape(option.value, out);
    }
    if (isTagElement(el)) shape(el.children, out);
  }
  return out;
}

export function check(locale: string, id: string, sourceText: string, translated: string): string[] {
  let tr: Shape;
  try {
    tr = shape(parse(translated));
  } catch (e) {
    return [`${locale}/${id}: does not parse: ${(e as Error).message}`];
  }
  const src = shape(parse(sourceText));
  const problems: string[] = [];

  for (const a of tr.args) {
    if (!src.args.has(a)) problems.push(`${locale}/${id}: uses {${a}}, which the code never passes`);
  }
  for (const p of tr.plurals) {
    const needed = new Intl.PluralRules(locale, { type: p.ordinal ? "ordinal" : "cardinal" })
      .resolvedOptions().pluralCategories;
    for (const cat of needed) {
      if (!p.keys.includes(cat)) problems.push(`${locale}/${id}: {${p.arg}, plural} has no "${cat}" branch`);
    }
    for (const k of p.keys) {
      if (!k.startsWith("=") && !needed.includes(k as Intl.LDMLPluralRule)) {
        problems.push(`${locale}/${id}: "${k}" branch can never be chosen in ${locale}`);
      }
    }
  }
  return problems;
}
```

Run it over the catalogs from the opening and it reports what 64 bug reports took a month to find. The Polish `file.deleted` has no `few` or `many` branch. An English message that says `zero {No files}` has a branch that can never be chosen. A translation that references `{name}` when the code passes `{actor}` is caught before it ships. The check deliberately *doesn't* require translations to use every source argument, because a language that has no use for `actorGender` is correct to ignore it.

> **Aside: CLDR's rules change, and your CI runtime may not match your users' browsers.** `pluralCategories` comes from whatever CLDR data the runtime was built with. French gained a `many` category for exact millions in a CLDR release some years ago, so an old runtime won't ask for it and an old browser won't choose it. Pin the Node version in CI, and remember that `other` is always the fallback when a runtime chooses a category the message lacks. That's one more reason every `other` branch has to read well on its own.

## Further Reading

- **Unicode CLDR, "Language Plural Rules"** (the plural rules chart at unicode.org/cldr): every language's categories with example numbers. Check it before arguing with a translator about Polish.
- **Unicode Technical Standard #35 (LDML), Part 3, "Language Plural Rules"**: how the rules are written, including the operands (`i`, `v`, `f`…) that explain why "1.0" and "1" can land in different categories.
- **ICU User Guide, "Formatting Messages"**: the reference for the syntax used here, including ICU's own recommendation to keep complete sentences inside each branch.
- **FormatJS documentation, "Message Syntax"**, plus the `@formatjs/cli` `extract` and `compile` commands for extraction and precompilation.
- **MDN, `Intl.PluralRules` and `Intl.ListFormat`**: the built-in JavaScript APIs for plural categories (cardinal and ordinal) and locale-correct lists.
- **Mozilla, "Localization content best practices"** (Firefox source documentation): the practical rules on concatenation, reuse, and comments for localizers, written by people who ship in over a hundred locales.
- **Project Fluent, the syntax guide**, especially the sections on selectors and terms, to see asymmetric localization designed in from the start.
- **The Unicode MessageFormat specification** (unicode-org/message-format-wg on GitHub, published as part of UTS #35): the successor syntax and the problems with the original that it was designed to fix.
- **GNU gettext manual, "Plural forms" and "Contexts"**: the other major lineage, and a clear account of per-language plural formulas.
- **In this collection:** Module 7 (error codes that clients translate), Module 13 (locale belongs in the cache key), Module 14 (email templates rendered in the recipient's locale). Later in this module: 25.1b (formatting what goes into the placeholders), 25.2a (the translation pipeline and pseudo-localization), 25.2b (text expansion and right-to-left layout), 25.3a (choosing the locale and the fallback chain).

A **Java** sibling would be worth writing, because the standard library's answer to this article is a trap. `java.text.MessageFormat`, which Spring's `MessageSource` uses by default, has no CLDR plural support. Its `choice` format selects on numeric ranges (`0#no files|1#one file|1<{0} files`), and no set of ranges can say that 22 is `few` while 12 is `many` in Polish. ICU4J's `com.ibm.icu.text.MessageFormat` supports `plural`, `select` and `selectordinal` properly, and swapping it into Spring's message resolution is a small, instructive change. The same article could cover resource-bundle encoding: properties files were read as ISO-8859-1 before Java 9, which is why older codebases are full of `\u0142` escapes. Not yet written.

---

The habit to take from this: whenever you write a sentence with a variable in it, ask what another language might need to know about that variable — how many, what kind, whose — and pass it in, even if English never uses it.
