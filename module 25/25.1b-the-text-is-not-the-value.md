# The Text Is Not the Value: Formatting and Parsing Numbers, Money, and Dates

_Module 25.1b — Internationalization & Localization_

## The Problem

Suppose you run an expense-reporting product. An employee photographs a receipt, types in the amount, currency and date, and submits a report. A manager approves it, and finance exports the approved lines each night and pays them. The product was built for US companies, and it shows: amounts are typed into a text field and read with `parseFloat`, money is displayed with `toFixed(2)` next to a currency symbol, receipt dates are typed as `MM/DD/YYYY` and read with a regular expression, and finance gets a CSV file.

Then a customer with 3,000 employees in Germany, Poland and the UK signs. The interface text is translated properly, with messages and plural rules (25.1a). Nobody touches the numbers. In the first month:

- **A €1,234.50 hotel bill is reimbursed as €1.23.** An employee in Munich types "1.234,50", the German way. `parseFloat` reads "1.234", stops at the comma, and returns 1.234. The validation only checks for a positive number, so it passes. Small amounts fail more quietly: "12,50" becomes 12, and 400 taxi receipts lose their cents before anyone notices.
- **The hotfix breaks the Americans.** Someone adds `.replace(",", ".")` before parsing. German "12,50" now works. American "1,234.50" becomes "1.234.50", which `parseFloat` reads as 1.234. The bug has moved to a different continent.
- **A British receipt is rejected as too old.** A London employee types 03/04/2026, meaning 3 April. The regex reads it as March 4. The report is submitted on April 10, and the policy engine rejects any expense older than 30 days.
- **A Polish manager approves a $1,450 hotel as 1,450 złoty.** The currency symbol was chosen from the *employee's* country, so a New York receipt in dollars displays as "1 450,00 zł": the same number with a different label, never converted. 1,450 złoty is a normal hotel bill, so it's approved without a second look. The same code shows a ¥12,000 Tokyo dinner as "12000.00".
- **Finance's export opens as a single column.** German Excel expects semicolons between fields in a CSV, so every row lands in column A. After an accountant splits the columns by hand, amounts like 12.05 turn into dates (12 May).

None of this is a translation problem; every label on the screen was correct. It's one mistake made five ways: **treating the text of a value as the value.** `parseFloat` assumed text written in one convention. The date regex assumed one field order. The currency symbol assumed that currency belongs to a person rather than to an amount. The CSV assumed the reader's spreadsheet uses the writer's conventions.

## What It Is

**Locale-sensitive formatting** turns a value into text using the conventions of a locale: which digits, which decimal and grouping separators, how digits are grouped, where the currency symbol goes, which order day, month and year come in, what the months are called, which calendar and which clock. The conventions for several hundred locales are collected in Unicode CLDR, the same repository that supplied the plural rules in 25.1a, and every mainstream platform ships a formatter that reads it: `Intl` in JavaScript, and ICU or the standard libraries built on CLDR data elsewhere. **Parsing** is the reverse, turning text a person typed back into a value, and it is much harder than formatting. Most platforms don't even offer it for numbers.

The model that prevents all five bugs is that a displayed value has three independent inputs:

```
 the value                      the viewer's locale           the viewer's other settings
 1450.00 USD                    pl-PL                         time zone: Europe/Warsaw
 2026-04-03T14:20:00Z           (digits, separators, order,   clock: 24-hour
                                 month names, calendar)       units: metric
          └─────────────────────────────┼──────────────────────────────┘
                                        ▼
                         "1450,00 USD"    "3 kwi 2026, 16:20"
```

The currency is part of the value, not the locale. The time zone is a setting of the viewer, not a feature of the language (25.1c covers where it comes from and how to store times). And the text at the bottom is **output only**, meant for a person to read. It isn't something to store, compare, or parse back.

One neighbor to separate from this: **formatting never changes the quantity.** Showing a dollar amount to a Polish user in Polish conventions gives "1450,00 USD", not złoty. Converting currencies, units or time zones is a different operation with its own data (exchange rates, conversion factors, the time zone database), and charging different prices in different markets is a pricing decision (Module 15).

## Recognizing the Problem

- `parseFloat`, `Number()` or unary `+` applied to text a person typed.
- `.replace(",", ".")` anywhere near parsing.
- `toFixed(2)` next to a currency symbol, or a symbol chosen from the user's country.
- Hard-coded date patterns: `"MM/dd/yyyy"`, `"DD.MM.YYYY"`, `` `${d.getMonth() + 1}/${d.getDate()}` ``.
- `toLocaleString()` or `toLocaleDateString()` with no arguments, especially on a server.
- A yen amount with ".00", or any code that assumes every currency has two decimals.
- APIs, events or database columns holding "€1,234.50" or "Apr 3, 2026" instead of values.
- Money stored or summed as floating-point numbers.
- European customers reporting that exports open in one column.
- Tests that fail after a Node, browser or JDK upgrade, with a diff where both sides look identical.
- Hydration warnings in server-rendered pages that point at dates or numbers.
- Support tickets about amounts off by a factor of 10 or 1,000, or missing their cents.

## How It Works

### Numbers: more varies than the separator

The same number, formatted with each locale's defaults:

```
locale    1234567.891              1234.5        50%
en-US     1,234,567.891            1,234.5       50%
de-DE     1.234.567,891            1.234,5       50 %
fr-FR     1 234 567,891            1 234,5       50 %
pl-PL     1 234 567,891            1234,5        50%
de-CH     1’234’567.891            1’234.5       50%
en-IN     12,34,567.891            1,234.5       50%
ar-EG     ١٬٢٣٤٬٥٦٧٫٨٩١            ١٬٢٣٤٫٥       ٥٠٪؜
tr-TR     1.234.567,891            1.234,5       %50
```

Several different things vary in that table.

- **Separators swap roles.** A comma is the decimal separator in German and the grouping separator in English. Neither character means anything on its own.
- **Some "spaces" aren't spaces.** French groups with a narrow no-break space (U+202F), Polish with a no-break space (U+00A0). They look like spaces and they aren't equal to `" "`, which matters the moment anything compares, splits or parses formatted text.
- **Group sizes differ.** Indian English groups the first three digits and then pairs (12,34,567: twelve lakh, thirty-four thousand...).
- **Some locales don't group short numbers.** Polish and Spanish leave four-digit numbers ungrouped (1234,5) and group from five digits up (12 345). Code that "detects the grouping separator" by formatting 1234 gets nothing back.
- **Digits themselves differ.** Egyptian Arabic uses Arabic-Indic digits by default; Persian uses a different set again.
- **Signs move.** Turkish puts the percent sign first. Accounting formats in some locales show negatives in parentheses (`currencySign: "accounting"` in `Intl`).

A formatter handles all of it if you give it the locale. The only mistakes available are not using one, or using one without saying which locale you mean. `toLocaleString()` with no argument uses the runtime's default, which in a browser is roughly the user's language, and on a server is whatever the process happened to start with — usually `en-US`.

### Money: the currency is part of the value

A monetary amount is a pair: a decimal quantity and an ISO 4217 currency code. The viewer's locale decides how that pair is *written*, never which currency it *is*:

```
EUR 1234.50 in    en-US  €1,234.50        de-DE  1.234,50 €       nl-NL  € 1.234,50
                  fr-FR  1 234,50 €       pl-PL  1234,50 €

USD 1234.50 in    en-US  $1,234.50        en-CA  US$1,234.50      pl-PL  1234,50 USD
CAD 1234.50 in    en-US  CA$1,234.50      en-CA  $1,234.50
```

Three consequences.

**Symbols depend on both the locale and the currency.** "$" means US dollars to an American and Canadian dollars to a Canadian, so a good formatter disambiguates for you ("US$" for a Canadian viewer, "CA$" for an American one). `currencyDisplay: "narrowSymbol"` undoes that and prints a bare "$" for every dollar, which is fine in a single-currency product and dangerous in a multi-currency one. When several currencies can appear side by side, as in an expense report, showing the code (`currencyDisplay: "code"`, which gives "USD 1,234.50") is the least ambiguous choice.

**Currencies have different numbers of decimal places.** ISO 4217 assigns each currency its minor-unit exponent: two for the euro and the dollar, zero for the yen and the Korean won, three for the Kuwaiti and Bahraini dinars. `toFixed(2)` is wrong for all of the second and third groups. `Intl` knows the right number for each currency. One caveat: payment providers sometimes treat a handful of currencies differently from ISO, so check your provider's list before converting to its integer minor units (Module 15).

**The formatter must never be the thing that rounds money.** Give `Intl` 12,000.5 JPY and it prints "¥12,001", silently, because yen has no decimals. When the screen and the ledger disagree by a yen, the ledger's number was wrong upstream, and the formatter hid it. Rounding money is a business rule with a defined point and a defined mode (Module 15). By the time a value reaches the formatter, it should already have the currency's precision, and the implementation below refuses to format one that doesn't.

Money also shouldn't be a float at any point. `0.1 + 0.2` is `0.30000000000000004`, and JSON numbers become floats in JavaScript the moment they're parsed. Carry amounts as decimal strings (`"1450.00"`) or as integers in minor units, and keep arithmetic in a decimal type (Module 15).

### Dates and times: options, not patterns

A date pattern such as `MM/dd/yyyy` is one locale's convention written into code. Ask for *components* or a *style* instead, and let the locale decide the order, the separators, and the names:

```
                    dateStyle "short"   dateStyle "medium"   {day: "numeric", month: "long"}
en-US               4/3/26              Apr 3, 2026          April 3
en-GB               03/04/2026          3 Apr 2026           3 April
de-DE               03.04.26            03.04.2026           3. April
pl-PL               3.04.2026           3 kwi 2026           3 kwietnia
ja-JP               2026/04/03          2026/04/03           4月3日
th-TH               3/4/69              3 เม.ย. 2569         3 เมษายน
```

The first two rows are the British receipt from the opening, one line apart.

Several things in that table would break code that assembles dates from parts.

- **Month names change form in context.** On its own, April is *kwiecień* in Polish. In a date it's *kwietnia*, the genitive case. Russian does the same (*апрель* and *3 апреля*). Formatting the day and the month name separately and joining them with a space produces the wrong form. It's the concatenation bug from 25.1a again.
- **Calendars differ.** Thai defaults to the Buddhist calendar, in which 2026 is 2569, and Persian defaults to the Solar Hijri calendar. That's correct for those users. What breaks is code that takes `getFullYear()` (Gregorian) and puts it next to a formatter's month name (Buddhist).
- **The clock varies.** Some locales use a 12-hour clock and some a 24-hour one, and CLDR occasionally changes which (a 2023 update moved Spanish-speaking locales in the Americas to 12-hour). The locale's default is a good start, and "24-hour time" is among the most requested preferences, so keep it overridable (`hourCycle`).
- **Weeks start on different days.** Sunday in the US, Monday in most of Europe, Saturday in parts of the Middle East. Calendars, date pickers and "this week" reports need the locale's first day. `Intl.Locale` exposes week data in runtimes that support it, and CLDR-based libraries provide it elsewhere.
- **Every formatted time has a time zone.** `Intl.DateTimeFormat` takes a `timeZone` option, and if you don't pass one it uses the runtime's zone, which on a server is usually UTC. Which zone is right, and how to store the time in the first place, is 25.1c.

### Relative times, units, and compact numbers

The same principle covers the formats that seem too small to need it.

- **Relative time**: "3 days ago", "vor 3 Tagen", "3 dni temu". `Intl.RelativeTimeFormat` includes the plural rules, and with `numeric: "auto"` it produces "yesterday", "gestern" and "wczoraj" instead of "1 day ago". Deciding *which* unit to show (minutes, hours or days) is still your job, and the arithmetic behind it depends on time zones (25.1c).
- **Units**: `style: "unit"` gives "12 km" or "5 GB" with the right spacing and unit names. It only labels. Showing miles to Americans is a conversion plus a stored preference for the measurement system, not a formatting option.
- **Compact numbers**: 1,234,567 becomes "1.2M" in English, "1,2 Mio." in German, and "123万" in Japanese, where the natural unit is ten thousand. A hand-written `(n / 1e6).toFixed(1) + "M"` is wrong in most of the world.

### Parsing is a different, harder problem

Formatting has one correct answer per locale. Parsing has to deal with what people actually type: the other convention, spaces where the locale uses no-break spaces, native digits, stray symbols. And some inputs are genuinely ambiguous. "1,234" is one thousand two hundred thirty-four in English and one point two three four in German. No parser can tell which one a person meant without knowing the locale, and even then a person sometimes types the other convention.

JavaScript has no built-in locale-aware number parser, which is why `parseFloat` gets used in the first place. The workable design has four parts.

1. **Parse in the viewer's locale, using that locale's own symbols.** The formatter can tell you what they are: format a known number with `formatToParts` and read off the group separator, the decimal separator, the minus sign and the digits.
2. **Be strict where a guess could be expensive.** In German, "12.5" could only mean 125 if the dot is read as a grouping separator. But grouping separators are followed by exactly three digits (or two, in Indian grouping), so "12.5" doesn't fit the format. Reject it with a message ("Use a comma for decimals: 12,5") rather than accepting a 10× error. Many locales use `.` for nothing at all (Polish, for instance). There you can safely accept "12.5" as twelve and a half, and doing so helps people whose phone keypad shows a dot.
3. **Echo the interpretation back.** When the field loses focus, reformat the parsed value in the locale: the person who typed "1.234" sees "1.234,00 €" and can tell whether that's what they meant. This is the only defense against the truly ambiguous case.
4. **Return a value, not a float.** A parsed amount is a decimal string or an integer in minor units, so no precision is lost between the keystroke and the ledger.

Dates are harder still, so avoid parsing free-text dates altogether. A date picker, or separate day, month and year fields with labels (the pattern the UK government's design system uses for dates people know, such as a birth date), removes the ambiguity rather than resolving it. `<input type="date">` shows the date in the browser's format but always gives your code an ISO value (`2026-04-03`). `Date.parse("03/04/2026")` is implementation-defined, and its result shouldn't be trusted with anyone's money.

`<input type="number">` is less helpful than it looks for decimals. Which separators it accepts depends on the browser, and in some browsers on the browser's own language rather than your page's. It also accepts `e`, and the scroll wheel changes its value. A text input with `inputmode="decimal"` plus your own parser gives you control. Note that the decimal key on a mobile keypad follows the *device's* region, which may not match the locale your page is in. That's one more reason to accept the unambiguous alternative separator.

### Values on the wire, text at the edge

Everything above only works if values stay values until the last moment:

```
 database / API / queue           the edge (knows the viewer)          the person
 ───────────────────────          ───────────────────────────          ─────────────────
 {"amount": "1450.00",      ──▶   formatMoney(value, viewer)     ──▶   "1450,00 USD"
  "currency": "USD"}
 "2026-04-03T14:20:00Z"     ──▶   formatDateTime(value, viewer)  ──▶   "3 kwi 2026, 16:20"
                            ◀──   parseDecimal(text, locale)     ◀──   "1 234,50"

 values only                      the only place a locale is used      text only
```

APIs, events, queues and databases carry values in invariant formats: decimal amounts with a `.` and a currency code, and instants in ISO 8601 (RFC 3339). An API that returns "€1,234.50" has formatted for one viewer and made the value unusable for every other client, which can't sort it, sum it, or show it in another locale without parsing it back.

**Some edges are on the server.** Emails, PDFs and push notifications are formatted by a backend for someone who isn't making the request. When a manager in London approves a report, the email goes to an employee in Warsaw, and it has to be formatted in the *recipient's* stored locale and time zone (Module 14, 25.3a). This is where argument-less `toLocaleDateString()` calls do the most damage, because the server's defaults are nobody's preference.

**Exports are an edge too, and CSV is text.** There are three honest options. A machine CSV uses ISO dates, `.` decimals and UTF-8, and is documented as such; it's right for pipelines and irritating in Excel. A locale CSV uses semicolons and comma decimals for a German user; it's right for that user and breaks every pipeline. An `.xlsx` file stores typed numbers and dates, and each reader's spreadsheet displays them in that reader's own conventions, because it holds values rather than text. For exports that people open by double-clicking, it's usually the answer.

**Formatted output isn't stable.** CLDR is revised twice a year, and formatting changes with it. CLDR 42 (2022) replaced the ordinary space before "AM" and "PM" in English with a narrow no-break space. Tests that compared formatted strings failed with diffs that looked identical, server-rendered pages disagreed with browsers, and code that parsed its own output broke. Browsers eventually patched their date formatting back to a plain space to keep websites working, while Java 20 shipped the change and Java applications had to adapt. The lesson isn't that CLDR is careless. Formatted text is for people, and anything a program stores, compares or parses should be the value.

## When It's Appropriate

- **Any product with users in more than one country, including English-only ones.** American and British users disagree about 03/04/2026. Indian users group digits differently, and Canadians need "$" disambiguated. An English-only product with 30% of its users outside the US is already showing wrong dates to some of them.
- **Anywhere people type numbers or dates.** Parsing matters even in a single-market product: a Polish-only app still can't use `parseFloat`.
- **Money in more than one currency**, even for a single locale: the expense report, a marketplace, travel, anything with imports.
- **Server-generated documents**: invoices, receipts, statements, notification emails.
- **Exports that people open in a spreadsheet.**

## When It's Unnecessary or Overkill

- **Text for machines.** Logs, API payloads, message queues, config files, file names, data-pipeline CSVs and database columns stay in invariant formats: ISO 8601, `.` decimals, ISO 4217 codes. Localizing any of them is the bug, not the feature.
- **Technical audiences who read ISO fluently.** Observability tools, admin consoles and developer products often show `2026-04-03 14:20:00Z` everywhere on purpose. It's unambiguous and sortable, and their users prefer it.
- **Per-user overrides for every convention** (a custom decimal separator, a custom date pattern) before anyone asks for them. The locale's defaults plus a 12/24-hour choice cover nearly everyone.
- **Non-Gregorian input.** `Intl` displays a Thai or Persian user's dates in their calendar for free. Building date pickers and scheduling rules in the Hijri calendar is a project, worth it only for a market that needs it.
- **A money library in a single-currency product that does no arithmetic on the client.** Decimal strings and `Intl` are enough.
- **Writing your own formatting tables.** The data runs to hundreds of locales and changes twice a year. Use the platform's.

## Trade-offs

- **Output changes under you.** Runtime upgrades change formatted strings in small ways: spaces, abbreviations, clock defaults. Tests should assert on values, or build their expected text with the same formatter, or compare `formatToParts` output. Cached HTML rendered by an older runtime will differ slightly from fresh output.
- **The server and the browser can disagree.** They may have different CLDR versions and certainly have different default time zones. In a server-rendered React app, that shows up as a hydration mismatch and text that changes a moment after the page loads. Pass the locale and time zone explicitly on both sides, or format on only one of them.
- **Strict parsing turns some people away; lenient parsing misreads others silently.** The echo reduces both, at the cost of screen space and a moment of the user's attention.
- **Values on the wire push formatting into every client.** Each client needs the viewer's locale and time zone, and its own formatting code. Very thin clients (a watch face, an SMS gateway, an e-ink display) sometimes genuinely need the server to format for them, which means the server must know the viewer.
- **Width and alignment vary by locale.** "1.234.567,89 €" and "€1,234,567.89" have different lengths and put the symbol at different ends. Columns need room. Right-align amounts and use `font-variant-numeric: tabular-nums`, and accept that decimal points won't line up perfectly across locales.
- **Formatters are expensive to create.** Building an `Intl.NumberFormat` per table cell is slow for 10,000 rows. Cache formatters by locale and options.
- **Newer features aren't everywhere.** Formatting decimal strings exactly, rounding modes and week data arrived in `Intl` over the last few years. Older runtimes need polyfills, which add weight to the bundle.
- **Better exports cost more.** An `.xlsx` writer is heavier than string concatenation, and offering both CSV styles means one more thing to explain.

## Alternatives

**Invariant display.** Show ISO dates and `.` decimals to everyone. This is right for technical tools, as noted above. For a general audience it's unambiguous and alien, and it fails the German accountant as badly as the American default does.

**Unambiguous but unlocalized.** An English-only product can remove the worst ambiguity cheaply by always spelling out the month ("3 Apr 2026") and using a 24-hour clock with a time zone label. It's not localization, but it's a sound interim step and costs an afternoon.

**Date, number and money libraries.** Luxon builds on `Intl`. date-fns ships its own locale data, which can drift from the platform's CLDR. Moment.js is in maintenance mode, and its own documentation recommends moving on. For money, libraries such as Dinero.js pair amounts with currencies and handle allocation and rounding. For decimal arithmetic there's decimal.js or big.js. These complement CLDR-backed formatting: they help with arithmetic, parsing and older runtimes, not with having your own conventions table.

**Server-formatted strings** for thin clients, as described under trade-offs. It's legitimate when the client can't format, provided the server knows exactly whose locale it's formatting for.

**Native platform formatters on mobile.** iOS and Android formatters respect the user's operating-system overrides, such as an `en-US` user who chose 24-hour time or a different date order. Browsers generally don't expose those overrides, so a web app that wants to honor them needs its own preference setting.

**Constrained input instead of parsing.** Date pickers, separate day, month and year fields, steppers, sliders and currency pickers all avoid parsing by removing free text. For dates this is usually the right call. For amounts, which people copy from receipts and bank statements, free text plus a strict parser and an echo is friendlier.

## How to Achieve It

**Level 0: `toFixed`, `parseFloat`, and hand-written patterns.** Where most single-market products are.

**Level 1: one formatting module, with the locale always explicit.** Route every user-visible number, amount and date through one small module that takes a viewer (locale, time zone, preferences) and caches its formatters. Lint against argument-less `toLocale*` calls, `toFixed` in UI code, and `getMonth()`-style date assembly.
_Next when:_ the first complaint about date order or decimals, or the first user outside your home market.

**Level 2: values on the wire.** Audit APIs, events and database columns for formatted strings. Money becomes `{ amount, currency }` with a decimal string, and instants become ISO 8601. Remove floats from money wherever you find them.
_Next when:_ a second client, a second currency, or an export.

**Level 3: parse input properly.** Use strict locale-aware parsing with an echo for amounts, and pickers or separate fields for dates. Test with at least one comma-decimal locale, one space-grouping locale, and one with non-Latin digits.
_Next when:_ any of your users are in a comma-decimal locale, which, worldwide, is most of them.

**Level 4: server-side edges.** Store each user's locale and time zone, and have every email, PDF and notification take a viewer object explicitly. For server-rendered pages, send the locale and time zone the server used to the client.
_Next when:_ the first email or invoice goes to someone abroad, or the first hydration warning.

**Level 5: exports and preferences.** Offer `.xlsx` with typed cells for people and a documented machine CSV for systems. Add preferences (12/24-hour clock, measurement system, sometimes date order) when users ask for them.

## Implementation

TypeScript. `Intl` is the most complete built-in formatting API of any mainstream platform, and most formatting for the web happens in the browser. JavaScript's lack of a number parser also makes the parsing half explicit, which is the part people get wrong.

The formatting module takes an explicit viewer, caches formatters, and treats money as a value with its own currency:

```ts
// fmt.ts
export type Viewer = { locale: string; timeZone: string; hourCycle?: "h12" | "h23" };
export type Money = { amount: string; currency: string };   // "1450.00", "USD": never a float

const cache = new Map<string, Intl.NumberFormat | Intl.DateTimeFormat>();
function cached<T>(kind: string, locale: string, opts: object, make: () => T): T {
  const key = `${kind}|${locale}|${JSON.stringify(opts)}`;
  if (!cache.has(key)) cache.set(key, make() as never);
  return cache.get(key) as T;
}

export function formatMoney(m: Money, v: Viewer, display: "symbol" | "code" = "symbol"): string {
  const opts = { style: "currency", currency: m.currency, currencyDisplay: display } as const;
  const f = cached("num", v.locale, opts, () => new Intl.NumberFormat(v.locale, opts));

  const allowed = f.resolvedOptions().maximumFractionDigits ?? 2;  // 2 for EUR, 0 for JPY, 3 for KWD
  const given = m.amount.split(".")[1]?.length ?? 0;
  if (given > allowed) {
    // 12000.5 JPY: something upstream skipped the rounding step. Formatting it
    // would print ¥12,001 and the screen would silently disagree with the ledger.
    throw new RangeError(`${m.amount} ${m.currency} has more decimals than the currency allows`);
  }
  // Runtimes with Intl.NumberFormat v3 format decimal strings exactly, with no float in between.
  return f.format(m.amount as unknown as number);
}

export function formatDateTime(instant: Date, v: Viewer): string {
  const opts = { dateStyle: "medium", timeStyle: "short", timeZone: v.timeZone, hourCycle: v.hourCycle } as const;
  return cached("dt", v.locale, opts, () => new Intl.DateTimeFormat(v.locale, opts)).format(instant);
}
```

The `Viewer` parameter is the design. Every call site has to say whose conventions and whose time zone it means, so an approval email formatted in the approver's request context fails review instead of reaching the employee in the wrong format.

> **Aside: server rendering needs the same viewer on both sides.** If the server formats with `{ locale: "pl-PL", timeZone: "Europe/Warsaw" }` and the browser re-renders with its own defaults, React reports a hydration mismatch, and a user in Warsaw on a laptop set to London time sees the time jump by an hour after the page loads. Serialize the viewer into the page and use it on both sides.

The parser reads the locale's own symbols from the formatter and is strict exactly where a guess would cost a factor of ten:

```ts
// parse.ts
type Syntax = { group: string[]; decimal: string; minus: string[]; digits: string[]; primary: number; secondary: number };
export type Parsed = { ok: true; value: string } | { ok: false; hint: string };

const BIDI = /[\u200e\u200f\u061c]/g;   // direction marks some locales put around signs

function syntaxFor(locale: string): Syntax {
  // Ten integer digits: enough to see both group sizes (3/3, or 3/2 in en-IN), and past
  // the rule in Polish and Spanish that leaves four-digit numbers ungrouped.
  const parts = new Intl.NumberFormat(locale, { maximumFractionDigits: 1 }).formatToParts(-1234567890.5);
  const pick = (t: string) => (parts.find(p => p.type === t)?.value ?? "").replace(BIDI, "");
  const sizes = parts.filter(p => p.type === "integer").map(p => p.value.length);
  const g = pick("group");
  return {
    // People type ordinary spaces and apostrophes, not U+202F or U+2019.
    group: /^[\s\u00a0\u202f]$/.test(g) ? [" ", "\u00a0", "\u202f"] : g === "’" ? ["’", "'"] : [g],
    decimal: pick("decimal") || ".",
    minus: [...new Set([pick("minusSign") || "-", "-"])],
    digits: [...new Intl.NumberFormat(locale, { useGrouping: false }).format(9876543210)].reverse(),
    primary: sizes.at(-1) ?? 3,
    secondary: sizes.length > 2 ? sizes.at(-2)! : 3,
  };
}

export function parseDecimal(input: string, locale: string): Parsed {
  const s = syntaxFor(locale);                     // cache per locale in real code
  let text = input.trim().replace(BIDI, "");
  text = [...text].map(ch => (s.digits.includes(ch) ? String(s.digits.indexOf(ch)) : ch)).join("");

  const sign = s.minus.find(m => text.startsWith(m));
  if (sign) text = text.slice(sign.length).trimStart();

  const [intPart, frac, ...extra] = text.split(s.decimal);
  const groups = intPart.split(new RegExp(`[${s.group.map(c => "\\" + c).join("")}]`));
  const hint = `Use "${s.decimal}" for decimals, for example 12${s.decimal}5`;

  if (extra.length || (frac !== undefined && !/^\d+$/.test(frac))) return { ok: false, hint };
  if (!groups.every(g => /^\d+$/.test(g))) return { ok: false, hint };  // e.g. "12.5" in pl-PL
  if (groups.length > 1) {
    const [first, ...rest] = groups;
    const last = rest.pop()!;
    const fits = last.length === s.primary && rest.every(g => g.length === s.secondary) && first.length <= s.secondary;
    if (!fits) return { ok: false, hint };                                  // e.g. "12.5" in de-DE
  }
  return { ok: true, value: `${sign ? "-" : ""}${groups.join("")}${frac ? "." + frac : ""}` };
}
```

Here's what it does with the opening's inputs:

```
input        de-DE                          en-US                          pl-PL
"1.234,50"   1234.50                        rejected: use "." ...          rejected: use "," ...
"12,50"      12.50                          rejected: use "." ...          12.50
"12.5"       rejected: use "," ...          12.5                           rejected: use "," ...
"1,234.50"   rejected: use "," ...          1234.50                        rejected: use "," ...
"1 234,50"   rejected: use "," ...          rejected: use "." ...          1234.50
"1.234"      1234  (echo: 1.234,00 €)       1.234                          rejected: use "," ...
```

Every input that `parseFloat` got silently wrong is now either right or refused with a hint, except "1.234" in German. That one is ambiguous in principle, which is what the echo is for.

> **Aside: the Polish `.` is a policy choice.** Polish uses `.` for nothing, so accepting "12.5" as twelve and a half can't be mistaken for anything else, and it helps people whose phone keypad shows a dot because the device is set to another region. To allow it, add `.` as a second decimal separator for locales whose group separator is a space. Never do that for German, where the dot is the group separator. Ambiguity is a property of the locale, so the leniency has to be too.

> **Aside: the parser returns a string on purpose.** `"1234.50"` goes to the server as it is and becomes a decimal there. Converting it to a JavaScript number "just for validation" puts the float back into the path the rest of this design keeps it out of.

> **Aside: test the formatting module with values, not with hard-coded output.** An assertion like `expect(formatMoney(m, pl)).toBe("1234,50 €")` contains a no-break space you can't see, and it will break on the day CLDR decides that space should be narrower. Assert that formatting and then parsing gets back the original value, or compare against a string built by the same `Intl` call. Keep one small, deliberately pinned set of golden strings, so that upgrades show you exactly what changed.

## Further Reading

- **Unicode CLDR charts**, by locale: the number, currency and date conventions for every locale in one place. They're the fastest way to settle an argument about how Poles write money.
- **Unicode Technical Standard #35 (LDML), Part 3 "Numbers" and Part 4 "Dates"**: patterns, symbols, minimum grouping digits, and the difference between "format" and "stand-alone" month names that produces *kwietnia* and *kwiecień*.
- **MDN: `Intl.NumberFormat`** (including `formatToParts`, `currencyDisplay`, `currencySign` and `roundingMode`), **`Intl.DateTimeFormat`** (`dateStyle`, `timeStyle`, `hourCycle`, `calendar`, `timeZone`), **`Intl.RelativeTimeFormat`**, and **`Intl.Locale`**.
- **ISO 4217**, the currency code list with minor units, maintained by SIX on behalf of ISO. Also your payment provider's currency documentation (Stripe's "zero-decimal currencies" and special cases, for example), where its idea of minor units differs.
- **RFC 3339**, the profile of ISO 8601 to use for timestamps on the wire.
- **GOV.UK Design System, the "Dates" pattern and the guidance on asking for numbers**: why it uses separate day, month and year fields, and why it avoids `type="number"`.
- **Nicolai Parlog, "JDK 20-23: Support For Unicode CLDR Version 42"** (nipafx.dev): the narrow no-break space change as it hit Java, and a clear demonstration of why formatted text isn't a stable interface.
- **In this collection:** 25.1a (numbers inside messages, and plurals chosen from the displayed number), 25.1c (time zones and how to store times), Module 15 (money arithmetic, rounding and tax), Module 14 (emails formatted for the recipient), 21.5 (pinning `TZ` in CI and running in an unusual zone on purpose), 25.3a (where the viewer's locale comes from).

A **Java** sibling would earn its place, because Java offers both a parser and more ways to get it wrong. `NumberFormat.parse` stops at the first character it can't use and returns what it has, unless you check the `ParsePosition`. `DecimalFormat` ignores where grouping separators sit, so "12,5" in `en-US` parses as 125, which is the same 10× error this article's parser refuses. Java 20's move to CLDR 42 broke `DateTimeFormatter` parsing of times written with ordinary spaces. The temporary workaround flag was removed in Java 23, which added lenient space parsing instead. And `BigDecimal` with JSR 354 (`javax.money`) gives money a real type, something JavaScript doesn't have. Not yet written.

---

The habit to take from this: when a number or a date crosses a boundary, ask whether it's crossing as a value or as text. It should be text only at the one edge where you know exactly who is reading it.
