# Twenty Thousand Moving Parts: The Translation Pipeline

_Module 25.2a — Internationalization & Localization_

## The Problem

Suppose you run a project-management app on the web, iOS and Android, in English, German, French, Polish, Japanese and Brazilian Portuguese. The messages are written properly (25.1a): whole sentences, plural and select branches, a description on each one. There are about 4,000 of them. The web app ships twice a week and the mobile apps every two weeks. Translation works like this: before each release, a developer exports new strings to a spreadsheet, emails it to five freelance translators, and pastes their answers back into the locale files.

Over one quarter:

- **Releases either wait or ship half-translated.** Translations come back three to five days after the export, and the web app ships twice a week. So the team alternates between holding finished features ("the German isn't back yet") and shipping them with English falling back in the middle of other languages. The Japanese settings page has three English rows for a month.
- **The German pricing page keeps an old promise.** Marketing changes "Cancel anytime." to "Cancel anytime. The current month isn't refunded." The message ID stays `pricing.cancel`, so the change never appears in the "new strings" export, and the German page keeps saying *Jederzeit kündbar* with no condition. Four months later, a German customer's refund demand quotes the page, and that's how legal finds out.
- **Two feature branches, two spreadsheets.** Two features in flight each export their strings. The second paste overwrites part of the first, and 40 French messages quietly revert to English. The validation from 25.1a catches a Polish translator's `{liczba}` in place of `{count}`, which is good, but it blocks a Friday release until someone can reach the translator.
- **"Workspace" has three German names.** It's *Arbeitsbereich* in onboarding, *Workspace* in settings and *Arbeitsplatz* in emails, because three different translators handled those files and nobody gave them a glossary. Support tickets ask how to move a project from the *Arbeitsplatz* into the *Arbeitsbereich*.
- **A Polish typo needs an app-store release.** Translations are bundled into the mobile builds, so fixing one word takes a two-week release cycle and a store review. Meanwhile, 30% of Android users are on versions from six months ago that will show the typo for as long as they keep them.

The messages were fine. What moved them was a person and a spreadsheet, and the amount of state involved is larger than it looks: 4,000 messages times five target languages is 20,000 message-and-locale pairs. Each one can be missing, current, or out of date with the English it was translated from. Nobody could say which was which, so nobody could say whether French was ready to launch.

## What It Is

A **localization pipeline**, often called translation management, is the system that moves messages from the source code to translators and moves translations back into the product, while tracking the state of every message-and-locale pair. Its usual parts:

- **Extraction**: the source messages, with IDs and descriptions, pulled from the code, which is their single source of truth.
- A **translation management system (TMS)**: where translators work. It holds the translations, their states, and the context that goes with each message. Crowdin, Lokalise, Phrase and Smartling are hosted examples; Weblate and Mozilla's Pontoon are open-source ones.
- **Translation memory (TM)**: a record of past translations that the TMS suggests when the same or similar text appears again.
- A **glossary** (or termbase): the approved translation of each product term, plus the terms that must never be translated, such as brand names.
- **Review**: a second person checks the translation, or a person checks a machine's.
- **Delivery**: translations reach users, either bundled into a build or fetched at runtime.

The approach most teams move towards is **continuous localization**. New and changed messages flow to translators as they're merged, translations flow back as they're finished, and releases ship whatever is ready, with explicit rules for what isn't. The older alternative is a *string freeze* before each release, and it's still right in some places, as discussed below.

This article is about UI messages. Translating content that lives in your database, such as product descriptions, help articles or user posts, is a different pipeline with different owners (25.3b). How messages are written so they *can* be translated is 25.1a.

## Recognizing the Problem

- Spreadsheets or JSON files emailed to translators and pasted back by developers.
- Developers editing non-English locale files by hand ("I ran it through a translator, it's probably fine").
- Merge conflicts in locale files.
- A "localization week" before each release, or features held back waiting for translations.
- Nobody can say what is missing or outdated in a given language without counting rows.
- English copy changed and the other languages still say the old thing.
- The same product term translated differently on different screens.
- Translators asking questions by email that nobody answers.
- Screens that mix languages after a release.
- A translation fix that needs a mobile release to reach users.

## How It Works

### Every message-and-locale pair has a state

The core of the pipeline is a small state machine, run 20,000 times:

```
   source added
        │
        ▼
   ┌─────────┐   draft (human or machine)   ┌────────────┐   reviewed   ┌──────────┐
   │ missing │ ───────────────────────────▶ │ translated │ ───────────▶ │ approved │
   └─────────┘                              └────────────┘              └──────────┘
        ▲                                         │   source text changes    │
        │                                         ▼                          │
        │                                    ┌─────────┐ ◀──────────────────┘
        └──── source deleted                 │  stale  │ ─── retranslated ──▶ translated
             (keep the text in the TM)        └─────────┘
```

The transition that the opening's team never had is **stale**. A translation must record *which version of the source* it translated. The simplest way is a fingerprint (a hash) of the source text stored alongside the translation. When the English changes, the fingerprint no longer matches, and every translation of that message becomes stale in every locale at once, without anyone needing to remember to export it.

Two refinements make that usable.

**Not every English edit changes the meaning.** Fixing a typo or a curly quote shouldn't send twelve translations back to be redone. The author of the change needs a way to say "this doesn't need retranslation", which re-stamps the existing translations with the new fingerprint. Every serious TMS has some form of this. Mozilla's convention is the mirror image, and it's worth copying for the other case: **if the meaning changes, change the ID.** A new ID can't inherit an old translation by accident, and reviewers see that the meaning changed.

**Stale translations need a display policy.** While a message is stale, you can show the old translation (the right language, possibly the wrong meaning) or fall back to English (the right meaning, the wrong language). Neither is always right. For most interface text, the old wording is the lesser harm. For anything that is a promise, such as prices, refund terms, consent text or legal copy, the old wording is the dangerous one. Mark those messages as critical in the source catalog, and let the build fall back to the source language rather than ship an outdated promise. The German pricing page would have shown English for a few days, which is embarrassing and not actionable.

### One source of truth, one direction of flow

Most pipeline pain comes from files that two parties edit. The durable arrangement is:

```
      code repository                         TMS                              product
 ┌──────────────────────────┐   push on   ┌──────────────────────┐   pull    ┌──────────────────┐
 │ source messages (en)     │ ──merge───▶ │ translations, states,│ ────────▶ │ built catalogs   │
 │ IDs, descriptions,       │             │ TM, glossary,        │  (PR/bot  │ (or runtime      │
 │ critical flags           │             │ screenshots, review  │  or OTA)  │  delivery)       │
 └──────────────────────────┘             └──────────────────────┘           └──────────────────┘
   developers edit this                     translators edit this              nobody edits this
```

English is edited in code and pushed to the TMS automatically. Translations are edited in the TMS and pulled back, by a bot's pull request or at build time. The locale files in the repository, if there are any, are generated artifacts. They can be regenerated, and they don't get merge conflicts because nobody merges them by hand. A developer who wants to fix a German string fixes it in the TMS like everyone else.

**Branches** need a decision. You can push strings only from the main branch, which is simple, but translation then starts after merge, so new features ship with fallbacks for a few days. Or you can push from pull requests (most TMSs support branches), so translators start before merge, at the cost of translating text that may still change in review. Continuous-delivery teams usually push from pull requests for large features and from main for everything else.

### Context is what a translator works from

Translators are skilled and can't see your screen. The pipeline's job is to send them what they need along with each message:

- **Descriptions**, the ones 25.1a made a lint rule for.
- **Screenshots.** Most TMSs can attach them per message, and some can capture them automatically from end-to-end tests run in a special mode that records which message IDs appear on screen. Of all the context you can supply, a screenshot does the most to prevent the "Open" and "Öffnen" mistake.
- **Length limits** for buttons, tabs and mobile labels, enforced by the TMS rather than discovered in the layout. Expect text to grow: German and French typically run 20–35% longer than English, and short labels can double (25.2b).
- **A glossary** with the approved translation of each product term, and the terms that stay untranslated. The TMS highlights glossary terms in the source text and warns when a translation doesn't use them. That's the fix for the three German workspaces.
- **A style guide per language.** It settles things like formal or informal address (German *Sie* or *du*, French *vous* or *tu*), tone, punctuation, and how to handle English loanwords. Nobody can guess these consistently across four translators.
- **A way to ask.** A comment thread on the message in the TMS, routed to someone on the product team who answers within a day.

**Translation memory** builds on all of this. Once "Delete this file?" has an approved German translation, the TMS proposes it the next time the same text appears, which cuts cost and keeps wording consistent. It can also spread mistakes. Unless the memory takes context into account, it will happily offer the button's "Öffnen" for the status badge's "Open". TMSs that match on ID and description, not just on text, avoid this.

### Who translates, by risk

Different text deserves different translators, and tiering by the cost of a mistake is how teams afford six languages:

```
tier      examples                                    who
promise   prices, refund and cancellation terms,      professional translator + review;
          consent, legal, security warnings           critical flag (fall back rather than go stale)
core      onboarding, main flows, marketing pages,    professional or in-house translator;
          notifications                               review by sampling
long tail settings, rare errors, admin screens,       machine or LLM draft + glossary + validation;
          empty states                                human review when time allows
none      internal tools, debug screens               stays in English
```

**Machine translation**, whether a dedicated MT engine or a large language model, is now good enough to draft most interface text, and a lot of professional translation is machine drafts edited by a person (post-editing). For UI messages, three details decide whether it helps:

- **Give it the whole message and its context.** A model given the word "shared" guesses exactly as the agency did in 25.1a. Given the full ICU message, the description, the relevant glossary entries, the formality from the style guide, and the target language's plural categories, it does far better.
- **Validate its output the same way you validate people's.** Models translate placeholder names, drop tags, and invent plural branches. The 25.1a check catches all of these mechanically. Output that fails goes back to missing, not to production.
- **Label it.** Machine translations get their own state, `machine`, so the build can treat them differently (never for critical messages) and reviewers can find them. Fluent machine output that is wrong is harder to spot than clumsy human output, because it reads well.

Translating at build or pipeline time and storing the result is very different from translating each page at runtime. Runtime translation costs money and latency on every request, varies between requests, and can't be reviewed. Keep models in the pipeline, not in the page (Module 39 covers evaluating model output generally).

Sending unreleased interface text to a vendor or a model provider also discloses your roadmap. Treat it like any other data-processing agreement.

### When translations arrive: freeze or flow

**A string freeze** means new and changed strings must be merged by a cutoff, some days before the release, so translations are complete when it ships. It's predictable and simple, and it works well where releases are expensive and infrequent anyway: mobile release trains, boxed software, regulated releases. It slows everything else down, because developers wait for the freeze window and product can't change copy late.

**Continuous flow** means strings go to translators as they're merged, translations arrive over the following days, and every release ships whatever is ready. The question is what happens to what isn't ready, and there are three answers, from crudest to best:

1. **Fall back** to the source language for missing messages (25.3a's fallback chain). It's fine for a stray string. It's the Japanese settings page if it happens to half a screen.
2. **Block** the release until a locale is complete. That's a string freeze with extra steps.
3. **Gate the feature per locale.** Group messages by feature (a namespace such as `billing.*`), measure completeness per locale and namespace, and have the feature flag that controls the new billing page (Module 3's feature flags) enable it only in locales where its messages are complete. Polish users get the new page when its Polish is ready. Everyone else gets it now.

Gating by feature is what lets a team shipping twice a week support six languages without ever showing a half-translated screen. It needs the pipeline to publish completeness data that the application can read, which the implementation below produces.

### How translations reach users: bundled or over the air

**Bundled at build time.** Translations are part of the release artifact: reproducible, testable, and they work offline. A translation fix is a deploy. That's no cost for a web app that deploys ten times a day, and two weeks for a mobile app.

**Delivered over the air (OTA).** The app fetches catalogs at runtime from a CDN or the TMS provider's delivery service, so fixes reach users without a release. The failure modes are new:

- **A broken translation reaches production instantly.** The publish step has to run the same validation as the build, because there is no build anymore.
- **Old app versions receive new catalogs.** A catalog published today may contain a message that uses an argument, such as `actorGender`, that a six-month-old app never passes. OTA catalogs must be versioned by the *shape* of the messages (which IDs exist, and which arguments each takes) so that each app version gets translations it can format.
- **Caching and offline behavior.** The app still has to ship a bundled catalog as a fallback, and decide how often to check for updates.

Most mobile teams end up with a hybrid: catalogs bundled at build time, plus OTA overrides for fixes, validated at publish and restricted to messages whose shape is unchanged.

### Measuring it

Per locale and per namespace, track the percentage approved, the percentage machine-only, the number of stale messages and the age of the oldest, and the missing-message reports coming from production (25.1a's `report("missing")`). Put it where release decisions are made. "Is French ready?" becomes a number instead of a spreadsheet count, and "Polish has had critical messages stale for 40 days" becomes a line item with an owner.

**Pseudo-localization** belongs in the pipeline too (25.1a, level 3). A pseudo-locale is generated on every build, with every message bracketed, accented and lengthened, and a screenshot or end-to-end test run in it catches hard-coded strings, concatenation and truncation before any translator sees them. A mirrored pseudo-locale does the same for right-to-left layout (25.2b).

## When It's Appropriate

- **More than one target language and releases weekly or faster.** Coordinating by hand breaks down somewhere around the second language and the tenth release.
- **More than a few hundred messages, several translators, or several platforms sharing strings.** Web, iOS and Android translated three times over is the most common waste in localization.
- **Text that carries promises in several languages:** prices, cancellation terms, consent. Here stale tracking and critical flags protect you legally, not just cosmetically.
- **Mobile apps**, where the gap between a fix and its arrival is measured in weeks and old versions live for years.

## When It's Unnecessary or Overkill

- **One extra language, a small app, infrequent releases.** A catalog in the repository, the validation from 25.1a, and a translator who opens pull requests is a perfectly good pipeline. Adopt a TMS when coordination starts to cost more than the tool.
- **Internal tools.** Leave them in one language.
- **OTA delivery for a web app that already deploys several times a day.** The deploy *is* the fast path, and OTA only adds a second way to break production.
- **Human review of every long-tail string.** Tier by risk. Reviewing a rarely seen error message with the same care as the refund policy spends the budget in the wrong place.
- **Building your own TMS.** The workflow, memory, glossary, screenshot and review features take years to get right. Buy one, or run an open-source one.

## Trade-offs

- **The TMS is on your critical path.** Its outages, pricing and API changes affect releases. Keep your translation memory exportable, in TMX, and your catalogs exchangeable, in XLIFF or plain JSON, so you can leave.
- **Continuous doesn't mean instant.** For a few days after each merge, some locales lag. You pay for that either with fallbacks, with per-locale gates, or with holding features back. The pipeline makes the cost visible; it doesn't remove it.
- **Every copy change has a price in every language.** With per-word pricing and stale tracking, product teams start avoiding English copy improvements because they "cost six translations". Re-stamping trivial edits helps, and so does budgeting for copy changes explicitly.
- **Policy metadata is more to maintain.** Critical flags, namespaces, length limits and descriptions all have to be kept up to date by the people writing code. Without lint rules, they drift.
- **OTA brings runtime risk and version compatibility** into what used to be a build-time concern.
- **Machine output is fluent and sometimes wrong.** Errors that read naturally survive casual review. Sampling and user reports catch what validation can't.
- **Unreleased text leaves the building.** Every vendor and model provider in the pipeline sees your roadmap before your customers do.

## Alternatives

**Developers translate with a machine and commit the result.** It's fine for a tiny team supporting a language no one on the team speaks, as long as everyone understands the quality. It quietly becomes permanent if nobody plans the step after it.

**Batch translation through an agency.** Export everything, send it, import it, once per release. This is right for infrequent releases, with one improvement over the opening: send files in an exchange format such as XLIFF that carries IDs, descriptions and source fingerprints, rather than a spreadsheet.

**Community translation.** Volunteers translate through an open TMS, as Mozilla and many open-source projects do. It reaches languages no budget would cover. It needs moderation, review and patience, and it doesn't suit text that carries legal promises.

**Git-based localization.** Translators work directly in the repository, through pull requests or a TMS such as Weblate that reads from and writes to Git. There's one fewer system, and translation history lives with the code. It suits technical translators and open-source projects.

**Letting the browser translate.** Users in unsupported languages will do this anyway, since browsers offer to translate your English interface. That rewrites the page's DOM, which is known to break frameworks like React that expect to own the DOM (React's issue tracker has a long thread about crashes caused by Google Translate). Mark elements that must not be translated, such as names, codes and editable fields, with `translate="no"`. For languages you do support, serving your own translation stops users from reaching for the browser's.

**Supporting fewer languages.** It's a business decision, not an engineering one, but it's the most effective way to reduce pipeline cost. Each additional locale costs something for every message you write from then on.

## How to Achieve It

**Level 0: files by email.** Developers export, paste and hand-edit.

**Level 1: one source of truth.** Extract source messages from code into a catalog with IDs, descriptions and critical flags. Make locale files generated artifacts that nobody edits by hand, and run 25.1a's validation on every build.
_Next when:_ the first external translator, or the first merge conflict in a locale file.

**Level 2: a TMS and stale tracking.** Push source messages automatically on merge, and pull translations by bot or at build time. Store a fingerprint of the source with every translation, add a glossary for product terms, and a style guide per language.
_Next when:_ more than one locale plus weekly releases, or the first outdated translation a user notices.

**Level 3: policies and gates.** Critical messages fall back instead of going stale. Completeness is measured per namespace, and features are gated per locale. A pseudo-locale runs in CI.
_Next when:_ the first mixed-language screen complaint, or the first feature held back for one language.

**Level 4: machine drafts by tier.** Machine or LLM drafts for the long tail, with context, glossary and validation, and human review by risk tier. Measure error rates by sampling.
_Next when:_ translation lag exceeds your release cadence, or cost becomes the constraint.

**Level 5: over-the-air delivery where releases are slow.** For mobile, bundle catalogs at build and allow OTA overrides, validated at publish and versioned by message shape.
_Next when:_ the first translation fix held up by app review.

## Implementation

TypeScript, continuing from 25.1a's catalogs and validation. The pipeline is mostly scripts that run in CI and on the TMS's webhooks, and this is where its logic lives: state per pair, the build-time policy, and a machine draft that is checked before anyone relies on it.

State is derived, not stored as a flag someone has to remember to update:

```ts
// i18n/state.ts
import { createHash } from "node:crypto";

export type SourceEntry = {
  message: string;
  description: string;
  namespace: string;          // "billing", "onboarding": the unit of per-locale gating
  critical?: boolean;         // a promise: never show an outdated translation of it
};

export type TranslationEntry = {
  text: string;
  sourceHash: string;         // fingerprint of the English this was translated from
  state: "machine" | "translated" | "approved";
};

export type Status = "missing" | "stale" | TranslationEntry["state"];

export const fingerprint = (s: SourceEntry) =>
  createHash("sha256").update(s.message).digest("hex").slice(0, 16);

export function statusOf(src: SourceEntry, tr?: TranslationEntry): Status {
  if (!tr) return "missing";
  if (tr.sourceHash !== fingerprint(src)) return "stale";
  return tr.state;
}
```

> **Aside: only the message text is fingerprinted.** Editing a description to add context shouldn't send every translation back. If a clarification reveals that translators misunderstood the message, that's a meaning change, so give the message a new ID. The re-stamp command for trivial English edits sets `sourceHash` to the new fingerprint without touching `text`, and it should record who did it and why, because it's a claim that five languages are still correct.

The build turns states into what actually ships, according to policy, and publishes completeness for the feature flags:

```ts
// scripts/build-catalog.ts
import { check } from "./check-messages";            // 25.1a: parse, arguments, plural categories
import { statusOf, type SourceEntry, type TranslationEntry } from "../i18n/state";

export function buildCatalog(
  locale: string,
  source: Record<string, SourceEntry>,
  translations: Record<string, TranslationEntry>,
) {
  const messages: Record<string, string> = {};
  const coverage: Record<string, { total: number; shipped: number; stale: string[] }> = {};

  for (const [id, src] of Object.entries(source)) {
    const tr = translations[id];
    const status = statusOf(src, tr);
    const ns = (coverage[src.namespace] ??= { total: 0, shipped: 0, stale: [] });
    ns.total++;
    if (status === "stale") ns.stale.push(id);

    let ship =
      status === "approved" || status === "translated" ||
      (status === "machine" && !src.critical) ||      // no unreviewed machine text in a promise
      (status === "stale" && !src.critical);          // an old wording beats English, unless it's a promise

    if (ship && check(locale, id, src.message, tr!.text).length > 0) {
      ship = false;                                   // broken: fall back to source rather than crash
      report("invalid-translation", { locale, id });
    }
    if (ship) {
      messages[id] = tr!.text;
      ns.shipped++;
    }
  }
  return { messages, coverage };                      // coverage goes to the flag service and the dashboard
}
```

Anything not shipped is simply absent from the catalog, and 25.1a's `t()` falls back to the source message for it. The feature flag for the new billing page then reads one condition per locale: `coverage.billing.shipped === coverage.billing.total`. That's the whole mechanism that keeps a half-translated billing page away from Polish users.

A machine draft is a translation like any other, with the same validation and a state that tells everyone what it is:

```ts
// scripts/draft.ts
export async function draft(
  locale: string, id: string, src: SourceEntry, glossary: Glossary, style: StyleGuide,
): Promise<TranslationEntry | null> {
  const plurals = new Intl.PluralRules(locale).resolvedOptions().pluralCategories;
  const prompt = [
    `Translate one user-interface message from English into ${locale}.`,
    `It uses ICU MessageFormat. Keep every {placeholder} and <tag> exactly as written; translate only the words.`,
    `Wherever the source has a plural, write these ${locale} branches: ${plurals.join(", ")}.`,
    `Address the user ${style.formality[locale]}.`,                  // e.g. "formally, with Sie"
    `Required terms: ${glossary.entriesFor(src.message, locale)}.`,  // e.g. workspace → Arbeitsbereich
    `Where it appears: ${src.description}`,
    `Reply with the translated message only.`,
    ``,
    src.message,
  ].join("\n");

  const text = (await complete(prompt)).trim();       // whichever model API you use
  const problems = check(locale, id, src.message, text);
  if (problems.length > 0) {
    report("draft-rejected", { locale, id, problems });
    return null;                                      // stays missing; a person will see it in the queue
  }
  return { text, sourceHash: fingerprint(src), state: "machine" };
}
```

> **Aside: add a glossary check next to the syntax check.** If the source contains "workspace" and the German draft contains none of the approved term's forms, flag it for review rather than rejecting it outright. German declines nouns, so an exact string match is only a hint, but that hint would have caught the three German workspaces.

> **Aside: drafts are cheap, so draft early.** Running `draft` when a pull request pushes new strings means that a reviewer, or a German-speaking colleague, can read a German version of the feature before it merges. Problems with the English, such as ambiguity, missing descriptions or fragments, often show up first as bad drafts. The drafts stay in the `machine` state, so none of this bypasses human translation where the tier requires it.

## Further Reading

- **Mozilla, "Localization content best practices"** and the Firefox localization documentation: the rule to change the ID when the meaning changes, and a lot of practical experience from shipping in over a hundred locales.
- **OASIS XLIFF 2 specification**: the standard exchange format for localizable content, which carries IDs, notes, states and source text together.
- **TMX (Translation Memory eXchange)**: the format for taking your translation memory with you when you change vendors.
- **Weblate documentation**, especially the sections on continuous localization and its Git integration. It's open source, so the workflow is visible in detail.
- **Android developer documentation, "Test your app with pseudolocales"**: Android ships the `en-XA` (accented and lengthened) and `ar-XB` (mirrored right-to-left) pseudo-locales, which are good references for building your own.
- **ISO 17100** (requirements for translation services) and **ISO 18587** (post-editing machine translation output): worth knowing when you write a contract with a language-services provider.
- **React issue #11538**, on crashes caused by browser translation extensions rewriting the DOM: a concrete account of what happens when users translate your interface for you.
- **In this collection:** 25.1a (writing messages that can be translated, and the validation used here), 25.2b (text expansion and right-to-left pseudo-locales), 25.3a (fallback chains), 25.3b (translating database content, a different pipeline), Module 3 (feature flags, used here as per-locale gates), Module 39 (evaluating and guarding model output).

A **Swift** sibling would be worth writing, because on iOS the platform has built much of this pipeline into the toolchain. Xcode's String Catalogs track a state for every string and language, including stale strings and strings that need review, extract strings automatically, and hand XLIFF to translators, which leaves over-the-air delivery against app review as the central remaining decision. Not yet written.

The habit to take from this: whenever you change a piece of English on the screen, ask what happens to that message in every other language between now and when its translation catches up. Make that answer a policy the build enforces, not something you hope someone remembers.
