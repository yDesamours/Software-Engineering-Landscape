# Same, Before, and How Long: Comparing, Sorting, and Counting Text

_Module 25.2c — Internationalization & Localization_

## The Problem

Suppose you build the people directory inside an HR platform. Every employee has a profile with a display name and a chat handle (`@anna.berg`), and the directory offers search-as-you-type and an alphabetical list. A multinational customer imports 40,000 employees from Sweden, Germany, Spain, Turkey, Vietnam and Japan, using spreadsheets exported from its old HR system.

- **Some people exist twice.** Part of the import was exported on a Mac, which wrote accented letters in decomposed form: "José" as `Jose` followed by a combining acute accent. It looks exactly like the "José" typed on a Windows laptop, and it isn't byte-for-byte equal. The unique constraint on handles accepts both `@josé` spellings. Mentions go to whichever account autocomplete happens to suggest, and the real José misses half his messages.
- **Turkish colleagues can't find each other.** Search lowercases the query with the browser's locale (`toLocaleLowerCase()`), while the server lowercased the index with `toLowerCase()`. In a Turkish browser, "IŞIK" becomes "ışık" with a dotless ı, and the index holds "işık". Anyone in the Istanbul office who types Işık Yılmaz's name in capitals gets no results. German users typing "muller" don't find Müller either.
- **The alphabetical list is wrong for everyone, in different ways.** It's sorted by the database's byte-order ("C") collation, so capitals come before lowercase letters ("de Vries" after "Zoltán") and accented letters come after Z. German users expect Ärla among the A's. Swedish users *do* expect Å, Ä and Ö after Z, but in that order, and byte order puts Ä before Å. The office list also shows "Floor 10" before "Floor 2".
- **Names are cut into pieces.** Avatars show the first letter of the name as `name[0]`. For the decomposed "Émilie" that's a bare E, with the accent left behind on the next character. An employee whose display name starts with a Swedish flag emoji gets half a flag, which renders as a boxed letter S. The sidebar truncates names with `slice(0, 12)`, which sometimes cuts an emoji in half and leaves a "�".
- **After a server upgrade, lookups start missing people.** Operations moves the PostgreSQL database onto a new operating-system image. The system's C library brings new collation rules, and indexes on name columns that were built under the old rules are now out of order under the new ones. Some searches return nothing although the rows exist, and the unique index starts letting duplicates in. Nothing logged an error.

Every one of these is a question the code answered in terms of bytes or code units: are these two equal, which comes first, how long is this, where can I cut it? The person asking meant something else each time, and several of the right answers depend on the language.

## What It Is

Computers store text as a sequence of **code points**, the numbered characters of Unicode such as U+00E9, é. Those are encoded as **bytes** (UTF-8) or as 16-bit **code units** (UTF-16, which is what JavaScript and Java strings are made of). People don't see any of those. They see **characters**: "é", "日", "🇸🇪", each of which may be one code point or several. Nearly every text operation a product performs — equality, ordering, case changes, length, truncation, search — has a byte-level answer and a human answer, and bugs live in the gap between them.

Four standard tools close the gap, each defined by Unicode and implemented in ICU and in the platforms built on it:

- **Normalization** makes text that is *canonically equivalent* (the same characters, written with different code points) identical in code points.
- **Case folding** makes text compare equal regardless of case. It's different from **case mapping** (converting to upper or lower case for display), and the difference matters.
- **Collation** defines the order of text, and optionally its equality at different strengths, according to a language's rules.
- **Segmentation** finds the boundaries of user-perceived characters, words and sentences.

A fifth concern sits on top of these: **confusables**, strings made of different characters that look the same, which turns "is this the same?" into a security question.

This article is about the correctness underneath text handling. Relevance, ranking and search engines are Module 12, and rendering text in both directions is 25.2b.

## Recognizing the Problem

- Two strings that look identical and aren't equal, or duplicates that got past a unique constraint.
- `toLowerCase()` used to make comparisons case-insensitive, or `toLocaleLowerCase()` called without an explicit locale.
- `ORDER BY name` or `array.sort()` with no collation specified.
- `.length`, `slice`, `substring`, `charAt(0)` or `name[0]` used for anything a user sees.
- "�" characters or stray accents at the ends of truncated text.
- Search that can't find accented names, or finds "Muller" but not "Müller".
- Usernames or workspace names that look identical to each other.
- Unique violations or missing rows right after an operating-system or database upgrade.
- Case-insensitive uniqueness implemented differently in different places.
- Japanese, Chinese or Thai search that only matches whole strings.

## How It Works

### "The same" has several levels

Consider what can be said about whether two strings are equal:

```
level                          equal?                          example
code units / bytes             identical encoding              "José" (NFC) ≠ "José" (NFD)
canonical (after NFC)          same characters                 "José" (NFC) = "José" (NFD)
compatibility (after NFKC)     same "meaning" of characters    "ﬁle" = "file", "Ｊｏｓé" = "José", "x²" = "x2"
case-insensitive (folded)      same letters, any case          "JOSÉ" = "josé", "STRASSE" = "straße"
accent-insensitive             same base letters               "Jose" = "José"
language-specific              equal to a speaker              "Mueller" = "Müller" (German)
visually confusable            looks the same                  "pаypal" (Cyrillic а) looks like "paypal"
```

Each level is looser than the one above it, and the right one depends on what the comparison is for. A display name should be stored as the person wrote it, normalized only canonically. A handle that must be unique should be compared in a much looser form, so that `@José`, `@josé` and a decomposed `@josé` can't coexist. Search should be looser still. The design pattern that follows is **keep the original, derive keys**: store the text as written (normalized to NFC), and store one derived key per purpose, computed by one function that's used both on write and on lookup.

### Normalize at the boundary

Unicode allows many characters to be written in more than one way: "é" is either the single code point U+00E9 (composed) or "e" followed by U+0301 COMBINING ACUTE ACCENT (decomposed). The standard normalization forms make the choice consistent:

- **NFC** composes wherever possible. It's what most keyboards produce, what the W3C recommends for the web, and the right form for storing text.
- **NFD** decomposes. macOS file names and text copied from some Mac applications arrive this way, which is where the opening's duplicate José came from.
- **NFKC** and **NFKD** also apply *compatibility* mappings: the "ﬁ" ligature becomes "f" and "i", full-width "Ａ" becomes "A", "²" becomes "2", and circled "①" becomes "1". That's useful for identifiers and matching keys, and wrong for stored display text, because it destroys distinctions people sometimes chose deliberately.

Normalize to NFC once, where text enters the system (the API layer, imports and file uploads), and every comparison further in can rely on it. That's the same place to strip directional control characters (25.2b), since both are properties of the text rather than of any feature.

### Case: mapping for display, folding for comparison

Changing case for display is language-dependent and not always one character to one:

- German "ß" uppercases to "SS", so the text gets longer. (There is now an uppercase ẞ, but "SS" is the default mapping.)
- Greek capital sigma lowercases to "σ" in the middle of a word and to "ς" at the end.
- Turkish and Azerbaijani have four i's. Dotted İ pairs with i, and dotless I pairs with ı. English case rules turn "IŞIK" into "işık", which to a Turkish reader is a different word.

For **display**, map case using the language of the text: `toLocaleUpperCase("tr")` for Turkish text, or CSS `text-transform` with the right `lang` attribute (25.2b). For **comparison**, don't lowercase with any locale. Use **case folding**, a mapping defined for comparison that is (almost) the same everywhere, and apply it identically on both sides. The opening's Turkish bug came from lowercasing the query and the index with *different* rules. Either rule applied to both sides would have worked.

JavaScript has no case-folding function. Uppercasing and then lowercasing with the root locale is a close practical approximation: it maps "ß" to "ss" and all four Turkish i's to one form. That's slightly looser than Unicode's own folding, which keeps dotless ı separate. For search, looser is what you want. For identity, it's a decision to make consciously. Libraries built on ICU, and databases with ICU collations, provide exact folding.

**Accent-insensitivity is not "remove all marks".** Removing combining marks after NFD turns "José" into "Jose", as intended. In Devanagari, Thai or Bengali, the same combining marks are vowels, and removing them destroys the word. Remove only the combining diacritics used by Latin, Greek and Cyrillic (the U+0300–U+036F block), or use a collator at base strength, which applies each language's own notion of what an accent is. Language-specific equivalences, such as German "ue" for "ü", aren't Unicode equivalences at all. They belong in search analyzers (Module 12's German normalization filters), not in a general key.

### Collation: order is a language's decision

The same names, sorted three ways:

```
code-unit order (JS default sort,     English and German          Swedish
database "C" collation)

Adam                                  Adam                        Adam
Oskar                                 Ärla                        de Vries
Zoltán                                Åsa                         Émilie
de Vries                              de Vries                    Oskar
Ärla                                  Émilie                      Zoltán
Åsa                                   Oskar                       Åsa
Émilie                                Östen                       Ärla
Östen                                 Zoltán                      Östen
```

Code-unit order is an accident of where letters landed in the Unicode tables: capitals first, then lowercase, then accented letters. English and German collation treat Ä, Å and É as accented variants of A and E, so they sort among them. Swedish treats Å, Ä and Ö as separate letters after Z, in that order, and treats É as a variant of E. **Neither of the last two columns is more correct.** Each is correct for its readers, which is why a sorted list shown to people needs the viewer's locale, just like a formatted date (25.1b).

The **Unicode Collation Algorithm** compares strings at several strengths. Primary compares base letters (a = á = A). Secondary adds accents (a ≠ á). Tertiary adds case (a ≠ A). CLDR provides tailorings for each language on top. `Intl.Collator` exposes all of this: `sensitivity` selects the strength, `numeric: true` sorts "Floor 2" before "Floor 10", and `ignorePunctuation` does what its name says. A collator at `sensitivity: "base"` is also the easiest correct way to compare two strings case- and accent-insensitively in one language's terms.

### Collation in the database

Lists longer than a page are sorted in the database, so the database's collation decides the order. In PostgreSQL:

- Every text column has a collation, either the database default or one you name. With ICU support, predefined collations such as `"sv-x-icu"` and `"de-x-icu"` are available, and a query can name one: `order by display_name collate "sv-x-icu"`. The collation can't be a query parameter, so map locales to collation names through an allowlist.
- **An index is sorted in one collation.** An `ORDER BY` in a different collation can't use it. For large tables sorted per locale, create one index per supported collation. Otherwise, filter first and sort the small result.
- **Machine columns should use `"C"`.** Handles' keys, email keys, codes and IDs compare fastest and most predictably byte by byte, and their order never changes. Use human collations only where humans read the order.
- **Case-insensitive uniqueness** can be a unique index on an expression (`lower(...)`), the `citext` extension, a *nondeterministic* ICU collation (which makes `=` itself case- or accent-insensitive, at the cost of slower comparisons and restrictions on some operators), or a derived key column computed by the application. The implementation uses the last, because the same function then governs lookups in the application and in the database.

**Collation rules change between library versions, and indexes don't notice.** A B-tree index assumes the order it was built with. When the C library or ICU is upgraded and the rules change, the existing index is silently out of order: lookups miss rows that are there, and unique indexes admit duplicates. That's the opening's last bug. The best-known case is the glibc 2.28 release in 2018, which changed the sort order for a large number of strings and corrupted indexes on many databases moved to newer operating systems. PostgreSQL records the collation version an object was built with and warns when the library's version differs. The fix is to rebuild the affected indexes and then tell PostgreSQL the new version is accepted. This belongs in the upgrade runbook, including for replicas: a physical replica on a different operating-system version has the same problem. Using ICU collations with a pinned ICU version and `"C"` for machine columns keeps the blast radius small.

### Counting and cutting: graphemes

What a person sees as one character (a **grapheme cluster**) can be several code points, and each code point can be several code units or bytes:

```
text            UTF-8 bytes   JS .length   code points   graphemes
é (NFC)             2              1            1            1
é (NFD)             3              2            2            1
日本                6              2            2            2
👍🏽                 8              4            2            1        thumbs up + skin tone
👨‍👩‍👧               18              8            5            1        three people joined by two zero-width joiners
🇸🇪                 8              4            2            1        two regional indicator letters
```

Each unit is right for something:

- **Limits a person sees** ("display name, up to 30 characters") should count graphemes, because that's what the person counts. Counting code units rejects a name of 20 emoji and accepts 30 accented letters in one normalization form but not the other.
- **Storage and protocol limits** count in their own units. PostgreSQL's `varchar(n)` counts code points, network protocols count bytes, and SMS counts 7-bit characters or 16-bit units depending on its encoding (25.2b). Make storage limits generous enough that the user-facing grapheme limit is always the one that binds, and let storage reject only what's genuinely too large.
- **Truncation, initials and cursor movement** must happen on grapheme boundaries, or they produce half a flag, an orphaned accent, or "�" from half a surrogate pair. `Intl.Segmenter` with `granularity: "grapheme"` provides them. Also, initials are a Latin-script convention: many Chinese, Japanese and Korean interfaces show the family name's first character or a different avatar convention altogether, which is a design question to ask users in those markets.

`Intl.Segmenter` also finds **word** boundaries in scripts without spaces, using dictionaries for Thai, Japanese and Chinese. That's useful for highlighting matches in the browser. Server-side search does the same job with language-specific analyzers (Module 12).

Grapheme rules change with Unicode versions, as new emoji sequences are added and rules for some scripts are refined, so a browser and a server a few versions apart can count the same string differently. Validate on the server, and allow a little tolerance, or use the same segmentation library on both sides.

### When "looks the same" is an attack

`@pаypal` with a Cyrillic "а" (U+0430) is a different string from `@paypal` at every level above, and indistinguishable on screen. For identifiers that carry trust, such as handles, workspace names, organization slugs and domain names, uniqueness has to include visual similarity. Unicode Technical Standard #39 defines two tools for this:

- A **confusable skeleton**: a mapping that turns lookalikes into one representative string. Two identifiers whose skeletons match are refused as duplicates, or flagged for review.
- **Restriction levels** for mixing scripts. Latin mixed with Cyrillic in a single handle is almost always a trick. Japanese mixing Han, Hiragana, Katakana and Latin is completely normal, and the "highly restrictive" level allows exactly those combinations.

ICU implements both (as its spoof checker). Browsers apply similar rules when they decide whether to show an internationalized domain name or its punycode form. The PRECIS framework (RFC 8264 and RFC 8265) specifies how to prepare usernames and passwords for comparison, and it's the reference to follow if you design an identifier scheme from scratch.

## When It's Appropriate

- **Any user-entered text that you search, sort, deduplicate or limit**: names, titles, tags, file names, comments. That covers essentially every product.
- **User-facing lists shown to people in more than one language**: directories, contact lists, catalogs, file browsers.
- **Identifiers people choose and others rely on**: handles, workspace and team names, custom domains. Here confusables matter.
- **Databases with text indexes that will outlive their operating system**, which is all of them.

## When It's Unnecessary or Overkill

- **Machine identifiers.** UUIDs, enum codes, API keys and ASCII-only tokens should compare byte by byte under `"C"` collation and be validated as ASCII. Applying human rules to them only adds cost and ambiguity.
- **Per-locale database indexes for small lists.** If a sorted list never exceeds a few hundred rows, sort it in the application with `Intl.Collator` and skip the indexes.
- **Confusable checks on display names.** Names aren't unique anyway, and two real people can have names that look alike. Reserve skeleton checks for identifiers used to establish trust.
- **Your own normalization, folding or collation tables.** They're large, subtle and revised with every Unicode release. Use ICU, the platform, or the database.
- **NFKC on stored display text.** It belongs in keys only.

## Trade-offs

- **Every comparison level is a product decision.** Are "José" and "Jose" the same handle? Two different real people may have those names. Looser keys prevent impersonation and cause collisions, and tighter keys do the reverse.
- **Normalizing at input changes what people typed**, occasionally in ways they notice: NFKC flattens "²", and case folding merges handles someone thought were distinct. NFC is almost never noticed. Anything stronger should go into keys, not into the stored text.
- **Human collation is slower than byte comparison.** Sorts and index builds cost more, per-locale indexes cost storage, and nondeterministic collations restrict some operations. Machine columns under `"C"` keep that cost where it's needed.
- **Data is now tied to library versions.** Collation and segmentation change with ICU, the C library and Unicode. Upgrades need reindexing and verification, and replicas on mismatched operating systems are a hazard.
- **Derived keys are a migration to change.** Changing the key function means backfilling every row, and a stricter key can make existing handles collide, so plan how those collisions get resolved *before* the migration runs.
- **Pagination has to share the collation.** Cursor pagination by name only works if every page uses the same collation. A user who switches locale mid-list needs a fresh cursor.
- **Mixed-script restrictions can refuse legitimate identifiers**, depending on the level you choose. Test against real names from your markets.

## Alternatives

**ASCII-only identifiers.** Allowing only `[a-z0-9_]` in handles removes normalization, case, confusable and collation problems in one rule. It also excludes most of the world's people from writing their names in their own script. It's reasonable for technical handles, such as repository names and API slugs, and unfriendly for anything that represents a person.

**Transliteration keys.** ICU's transliterators can produce Latin-script keys for search ("Москва" becomes "Moskva", "Müller" becomes "Muller"), so a user typing in Latin letters finds names written in other scripts. It's a search feature with real value for mixed-script directories, and it's lossy, so it's never a key for identity.

**A search engine's analyzers.** Elasticsearch and OpenSearch provide ICU-based normalization, folding and collation-aware sorting as analysis components. For full-text search, relevance and language-specific rules like German "ue" for "ü", this is the right home (Module 12). The key functions in this article still govern uniqueness and exact lookups in the primary database.

**Case-sensitive everything.** It's the simplest option and genuinely right for some identifiers, such as file paths on case-sensitive systems and some codes. Users resent it for emails and handles, where they expect `Anna.Berg` and `anna.berg` to be the same account.

## How to Achieve It

**Level 0: bytes.** Code-unit equality, default sorts, `.length`.

**Level 1: NFC at the boundary.** Normalize to NFC and strip directional control characters in the API layer, imports and uploads. Backfill existing rows.
_Next when:_ the first duplicate that "looks the same", or now, because it's cheap.

**Level 2: one key function per purpose.** A handle key for uniqueness and login, and a search key for search, each stored as a derived column with an index and used on both write and lookup.
_Next when:_ complaints about case-sensitive logins, or search that misses accented names.

**Level 3: locale-aware ordering.** `Intl.Collator` for lists sorted in the browser, explicit ICU collations in `ORDER BY` for lists sorted in the database, per-locale indexes where the lists are large, and `numeric` sorting where names contain numbers.
_Next when:_ users in Nordic, German, Spanish or other non-English markets, or the first "Floor 10 before Floor 2" report.

**Level 4: graphemes.** Count user-facing limits in graphemes, truncate and build initials on grapheme boundaries, and make storage limits generous.
_Next when:_ the first emoji in a display name, which has probably already happened.

**Level 5: operations and trust.** `"C"` collation for machine columns, ICU collations with pinned versions for human ones, collation-version checks and reindexing in the upgrade runbook (replicas included), and confusable checks for trust identifiers.
_Next when:_ the next operating-system or database upgrade, or the first impersonation report.

## Implementation

TypeScript and PostgreSQL. JavaScript's built-in `Intl.Collator`, `Intl.Segmenter` and `normalize()` cover collation, segmentation and normalization without libraries. Its lack of a case-folding function makes it clear what a key function has to decide. The database side shows where those keys and collations live.

One module holds the key functions, and every write and every lookup goes through it:

```ts
// text/keys.ts
const BIDI_CONTROLS = /[\u202a-\u202e\u2066-\u2069]/g;       // 25.2b
const LATIN_GREEK_CYRILLIC_MARKS = /[\u0300-\u036f]/g;        // accents, not Indic or Thai vowels

/** What we store: the text as written, made canonical. */
export const clean = (s: string) => s.normalize("NFC").replace(BIDI_CONTROLS, "").trim();

/** Uniqueness and login for handles: compatibility-normalized, case-insensitive. */
export const handleKey = (s: string) =>
  clean(s).normalize("NFKC").toUpperCase().toLowerCase();     // ß→ss; all four Turkish i's → one form

/** Search: additionally ignores Latin, Greek and Cyrillic accents. */
export const searchKey = (s: string) =>
  handleKey(s).normalize("NFD").replace(LATIN_GREEK_CYRILLIC_MARKS, "").normalize("NFC");
```

`handleKey("@IŞIK")`, `handleKey("@Işık")` and `handleKey("@ışık")` are all `"@işik"`, so the Istanbul office's search works no matter who types what. `searchKey("Émilie")` in either normalization form is `"emilie"`. `searchKey("नमस्ते")` is unchanged, because its vowel signs aren't in the stripped range.

> **Aside: `toUpperCase().toLowerCase()` is deliberately not the locale-aware version.** Both calls use the root locale, so the key is the same on every server and in every browser, whatever their default language. Unicode's recommended form for identifiers is NFKC with full case folding (NFKC_Casefold), available through ICU. This approximation differs from it mainly in merging dotless ı with i, which suits search and should be a conscious choice for identity.

Sorting and cutting for display use the viewer's locale for order, and grapheme boundaries for everything else:

```ts
// text/display.ts
const collators = new Map<string, Intl.Collator>();
export const collatorFor = (locale: string) => {
  let c = collators.get(locale);
  if (!c) collators.set(locale, (c = new Intl.Collator(locale, { numeric: true })));  // "Floor 2" < "Floor 10"
  return c;
};

export const sortByName = <T extends { name: string }>(rows: T[], locale: string) =>
  [...rows].sort((a, b) => collatorFor(locale).compare(a.name, b.name));

const graphemes = new Intl.Segmenter(undefined, { granularity: "grapheme" });

export function graphemeCount(s: string): number {
  let n = 0;
  for (const _ of graphemes.segment(s)) n++;
  return n;
}

export function truncate(s: string, max: number): string {
  const parts: string[] = [];
  for (const { segment } of graphemes.segment(s)) {
    if (parts.length === max) return parts.join("") + "…";
    parts.push(segment);
  }
  return s;
}

export const initial = (name: string) =>
  graphemes.segment(name.normalize("NFC"))[Symbol.iterator]().next().value?.segment ?? "";
```

`initial("🇸🇪 Anna")` is the whole flag, and `initial` of a decomposed "Émilie" is "É". Validation uses `graphemeCount(name) <= 30` both in the form and on the server. The server's check is the one that counts, and the column behind it is a plain `text` so storage never refuses what the product allows.

The database stores originals, derived keys under byte collation, and human order under explicit ICU collations:

```sql
create table person (
  id            bigint generated always as identity primary key,
  display_name  text not null,                    -- clean(): NFC, as the person wrote it
  handle        text not null,                    -- clean(): as chosen
  handle_key    text collate "C" not null unique, -- handleKey(handle), computed by the application
  search_key    text collate "C" not null         -- searchKey(display_name)
);
create index person_search on person (search_key);     -- "C" collation: prefix LIKE can use it

-- Per-locale order for the directory list. Collation names come from an allowlist, never from input.
create index person_name_sv on person (display_name collate "sv-x-icu");
create index person_name_de on person (display_name collate "de-x-icu");

select id, display_name
from person
where search_key like $1 || '%'                   -- $1 = searchKey(query)
order by display_name collate "sv-x-icu"
limit 50;
```

> **Aside: why the application computes the keys.** PostgreSQL has `normalize()` and `lower()`, and could compute a key in a generated column. But the lookup in the application, the search box in the browser and the import script all need exactly the same function. With one TypeScript function used everywhere, "the database thinks these are different and the application thinks they're the same" can't happen. The cost is that anything writing to the table without going through the application has to call it too.

The upgrade runbook gets one query and one procedure:

```sql
-- Collations whose library version differs from the one recorded when objects were built.
select collname, collversion as recorded, pg_collation_actual_version(oid) as actual
from pg_collation
where collversion is distinct from pg_collation_actual_version(oid);

-- For each one: rebuild the indexes that use it, then accept the new version.
-- reindex index concurrently person_name_sv;
-- alter collation "sv-x-icu" refresh version;
```

Run it after every operating-system, ICU or major PostgreSQL upgrade, on the primary and on every replica, *before* sending traffic back. If the opening's operations team had had it, it would have listed exactly the indexes that later lost people.

## Further Reading

- **Unicode Standard Annex #15, "Unicode Normalization Forms"**: NFC, NFD, NFKC and NFKD, with examples of what each one changes.
- **Unicode Technical Standard #10, "Unicode Collation Algorithm"**, and the **CLDR collation charts**, which show each language's tailoring. That's how you check what Swedish users expect before shipping a sort order.
- **Unicode Standard Annex #29, "Unicode Text Segmentation"**: the definition of grapheme clusters, words and sentences.
- **Unicode Technical Standard #39, "Unicode Security Mechanisms"**, and **Technical Report #36, "Unicode Security Considerations"**: confusable skeletons, restriction levels and mixed-script detection. **Annex #31, "Unicode Identifiers"**, is the source of NFKC_Casefold.
- **RFC 8264 and RFC 8265 (PRECIS)**: preparing, enforcing and comparing internationalized usernames and passwords.
- **MDN: `Intl.Collator`, `Intl.Segmenter`, `String.prototype.normalize`, and `toLocaleUpperCase`.**
- **PostgreSQL documentation, "Collation Support"** (ICU collations, nondeterministic collations and version tracking), and the **PostgreSQL wiki page "Locale data changes"**, which is the account of the glibc 2.28 problem and how to detect it.
- **Henri Sivonen, "It's Not Wrong that "🤦🏼‍♂️".length == 7"**: a careful explanation of why every string length is right for something and none is right for everything.
- **In this collection:** Module 12 (search analyzers, including ICU and language-specific normalization), 25.2b (the directional controls stripped by the same `clean()`), Module 4 (normalizing passwords before hashing), Module 6 (indexes and migrations, for changing a key function), Module 24 (restoring onto newer operating systems, where collation versions change).

A **Go** sibling would be worth writing, because Go shows every layer of this with no abstraction on top. A Go string is bytes, so `len("é")` is 2 or 3 depending on normalization. `range` iterates over code points, and grapheme segmentation isn't in the standard library at all. Normalization and collation live in `golang.org/x/text`, which makes the choice to use them explicit. Not yet written.

---

The habit to take from this: whenever code asks whether two pieces of text are equal, which comes first, or how long one is, ask whether it means bytes or what a person sees — and if it's a person, which person, reading in which language.
