# The Deprecation Lifecycle: Retiring What Clients Still Use

_Module 33.2a — API Versioning & Deprecation_

## The Problem

Suppose you run a transactional email API. Applications call it to send password resets, receipts, appointment reminders, and shipping notifications. There are about 6,000 active API accounts.

Two old things need to go. API version `2019-06-01` — the oldest one still pinned — accounts for 14 of the `ctx.version <` branches in your core (33.1b) and is the reason two recent features took twice as long as planned. And that same version allows the API key to be passed as a query parameter, `?api_key=…`, which means keys end up in proxy logs, analytics tools, and browser histories. The security team has asked for it to be removed.

The first attempt goes like this:

**The announcement.** A changelog entry, a blog post, and an email to every account on the old version: "Version 2019-06-01 and query-string authentication will be removed on March 1." The emails go to each account's primary contact, which for most old accounts is whoever signed up — often a founder or a finance person. Many of the integrations were built by contractors who are long gone. The open rate is 31%.

**The day.** On March 1, it's switched off. About 1,100 accounts start getting errors. A clinic-booking platform stops sending appointment reminders. Around 300 SaaS applications stop sending password-reset emails, so *their* users are locked out — and those users contact the SaaS vendors, who contact you. The change is rolled back within four hours.

**The aftermath.** The rollback fixed the outage and created a quieter, longer-lasting problem: every client now knows the date wasn't real. The next announced date will be treated as a suggestion.

**What the data showed.** Afterward, someone checks what was known beforehand. The dashboard tracked requests per endpoint, not per account, so the only visible signal was "v1 traffic is down 80% since last year" — which looked like nearly done. In fact, 80% of the old version's traffic came from 12 large accounts, all of which had migrated. The remaining 20% was spread across roughly 1,400 accounts. Many of them sent password resets, which happen a few times a week per application. Some sent quarterly statements, which hadn't gone out in the 30-day window the dashboard showed at all.

The team announced a date and flipped a switch, and in between did almost nothing that would tell them who was going to break. **Deprecation isn't an announcement and a date. It's a process that ends with knowing, account by account, who is still depending on the thing — and having reached them before you remove it.**

## What It Is

**Deprecation** is declaring that something should no longer be used and will be removed — while it keeps working exactly as before. **Sunset** (or removal) is the moment it stops working. The time between them is the migration window, and nearly all the work happens there.

It helps to keep the states apart, because they're often blurred:

- **Deprecated** — still works, still supported, still gets security fixes; new use is discouraged or blocked.
- **End of support** — still works, but no fixes or help. Some organizations use this as an intermediate step; for an API it's usually a bad idea, because "running but unfixed" is exactly the state you don't want a payment or email endpoint in.
- **Removed** — requests fail, on purpose, with an explanation.

And one relationship: versioning (33.1b) is what *creates* old versions, by letting clients stay where they are. Deprecation is what *retires* them. A versioning scheme without a deprecation process grows without limit.

## Recognizing the Problem

- The list of supported versions or endpoints only ever gets longer.
- "Who still uses this?" produces a traffic graph, not a list of accounts.
- A removal has been rolled back after it broke people.
- Deprecations are announced in a changelog and a blog post, and nowhere else.
- The only contact you have for most accounts is the billing contact.
- There's code for old versions with almost no traffic that nobody dares delete.
- A deadline has slipped at least once, and clients know it.
- Clients learn something was deprecated when it disappears.

## How It Works

### The lifecycle

```
 active ──► deprecated ─────────────────────────────► sunset ──► removed
              │  works exactly as before                │       410 + pointer
              │  signaled in every response             │       to the guide
              │  new adoption blocked                   │
              │                                         │
              └──────────── migration window ───────────┘
                  per-account tracking, outreach,
                  exceptions, brownouts (33.2b)
```

Two preconditions, before the word "deprecated" is published anywhere:

- **The replacement exists and has been proven.** Deprecating something whose replacement is still in beta, or can't handle a use case the old thing handles, turns a migration into a negotiation. Check the replacement against how the old thing is *actually used* — the usage data below — not against its documentation.
- **You know how to measure who's left.** If you start the clock before you can see the population, you'll spend the window finding out what you should already know.

### First, stop the population growing

The cheapest step, and the one most often skipped: make sure no *new* client can start depending on the deprecated thing. New accounts can't pin to the old version. The old endpoint disappears from the getting-started docs and is marked deprecated in the OpenAPI description, so generated clients flag it. Query-string authentication is refused for API keys created after the deprecation date.

Without this, you're emptying a bath with the tap running — and the newest clients, who are the easiest to move, keep arriving.

### Measure accounts and recency, not traffic

The question you need to answer at the end is "which accounts will break?" So record usage per account, and record **when each account last used the thing** — not just how often.

```
 old-version requests by account, last 90 days

 top 12 accounts    ████████████████████████████████   80% of volume
 next 180           ██████                             15%
 remaining 1,400    ██                                  5%  ← 88% of the accounts
```

A volume-weighted dashboard says you're almost finished when you've migrated a dozen accounts. A per-account view shows you've barely started.

**Recency needs a long window.** Many important flows are low-frequency: password resets, monthly invoices, quarterly reports, annual renewals, year-end tax documents. An account that last used the old version 70 days ago isn't gone; it may be a quarterly job that will run again next month. Choose a lookback longer than the longest business cycle you can imagine a client having — 90 days at minimum, a year for anything touching accounting or compliance — and never sample this data, because sampling loses exactly the rare callers you're looking for.

**Identify the integration, not just the account.** An account is often several integrations. The user agent, the SDK name and version, the key's label, and the source network together often identify "their old PHP plugin" versus "their new service," which is the difference between a useful email and a useless one.

**Response-side usage stays invisible** (33.1a). You can see who calls an old version, but not who reads a deprecated response field. If a field needs to be retired, tie it to a version or make reading it an explicit request, so that its use becomes something you can count.

### Signal in-band

An email reaches a person. A response header reaches the code — and, through the right tooling, the person who owns the code. Two standard headers exist for this:

```
Deprecation: @1775001600
Sunset: Thu, 01 Oct 2026 00:00:00 GMT
Link: <https://docs.example.com/migrate/2019-06-01>; rel="deprecation"
```

`Deprecation` (RFC 9745, 2025) carries the date something was or will be deprecated, as a structured-field date — seconds since the epoch with an `@` in front. `Sunset` (RFC 8594) carries the date it's expected to stop working, as an ordinary HTTP date. The `deprecation` link relation points to the explanation. Both header dates can be in the future, so they can go out as soon as the plan is decided.

Be honest about their reach: almost nobody reads response headers directly. They're worth sending because tooling can read them. Your own SDKs should log a warning — once per process, not once per request — when they see them. API gateways and monitoring can alert on them. Client test suites can fail on them. A header nobody's tooling reads does nothing; a header your SDK surfaces in the client's logs every morning does a great deal.

The same signal belongs in every surface the client touches: `deprecated: true` in the OpenAPI description, `@deprecated` in a GraphQL schema, compiler warnings in typed SDKs, a banner in the account dashboard showing exactly what that account still uses.

### Signal out-of-band — to the right person

The out-of-band channel fails mostly on addressing, not wording. Two fixes:

- **Collect a technical contact** for every account, separately from billing, and ask for it again whenever an account creates an API key. Having one before your first deprecation is worth more than any email template.
- **Send each account its own facts.** "Your account called version 2019-06-01 from `acme-shop-plugin/2.3` 1,240 times in the last 30 days, most recently yesterday at 14:02" gets acted on. "We're retiring some older API versions" gets filed.

What those messages say, how often, and how to escalate is the subject of 33.2b.

### Warnings alone don't move people

*Software Engineering at Google* distinguishes **advisory** deprecation — warnings, docs, a deprecated flag — from **compulsory** deprecation, which has a deadline and someone enforcing it. Their observation, borne out almost everywhere, is that advisory deprecation on its own rarely finishes. It moves the motivated and the well-staffed, and the long tail stays where it is indefinitely, because staying costs them nothing.

So a deprecation that's meant to end needs a date and a credible intention to keep it. A deprecation without a sunset date is just a warning people learn to ignore.

### Choosing the window, and keeping the date

The window length is set by your **slowest legitimate client**, not your average one:

- mobile apps, where you have to wait for app-store review and then for users to update (42.3);
- enterprises with quarterly release trains and year-end change freezes;
- plugins, which reach the store owner only when they update, which may be never;
- regulated clients whose changes need validation or sign-off.

Publish a minimum in advance as a policy — "deprecated versions remain available for at least 12 months after deprecation" — so each deprecation isn't a fresh argument. Security-driven removals can justify shorter windows, and saying why is part of making them credible.

**Pick a date you will keep.** A long date that holds is worth more than a short one that slips, because a slipped date damages every future deprecation, not just this one. When a specific client can't make the date, give *them* an exception — a recorded extension with its own expiry, perhaps a contract term or a fee — rather than moving the date for everyone.

### Deciding to turn it off

The go/no-go question is not "is traffic near zero?" It's a question about the remaining accounts:

- Every account active within the lookback window is known by name.
- Each one has either been reached, with a documented response, or been attempted through every channel you have.
- Each account you've agreed to wait for has a recorded exception with an expiry date.
- The breakage has been rehearsed — brownouts (33.2b) have shown who breaks, and they've had a chance to fix it.
- You can reverse the removal quickly, with a single switch, if you've misjudged.

### What removal looks like

Removal isn't deleting the route. A deleted route returns `404`, which reads like a typo or a bug, and sends a client's developer to debug their URLs. Return **`410 Gone`** with a body that names what was removed, when, and where the migration guide is. Keep that stub for a long time — it costs almost nothing — and keep recording who hits it, because post-removal requests tell you whom you missed and whether a rollback is warranted.

Then, once the stub has been quiet for a while, delete the old code: the version branches, the transforms, the special cases. That's the payoff the whole process was for, and it's worth doing promptly, before the deleted code's absence starts to feel risky too.

## When It's Appropriate

Any time you need to remove something that clients you don't control might depend on:

- **old API versions**, once their cost shows up in planning — the 14 branches in the email API;
- **endpoints, fields, and parameters** replaced by better ones;
- **authentication methods** — query-string keys, basic auth, old signature schemes, older TLS versions;
- **webhook formats and event types** (17.1b), which reach clients through a path they didn't call;
- **SDK versions and language runtimes** you no longer want to support.

And for anything with a real cost to keep: security exposure, operational burden, a vendor contract expiring underneath it, or engineering time spent working around it.

## When It's Unnecessary or Overkill

- **Nothing uses it.** If per-account data over a long window shows no callers, a short notice and removal is fine. The lifecycle is for things people depend on.
- **Known internal consumers.** Five teams can agree on a date in a meeting. Headers and outreach campaigns for them are theater.
- **Unstable surfaces** clearly labeled as such (33.1a) can change with short notice — that's what the label was for.
- **It costs nothing to keep.** If an old endpoint is a thin adapter over the new one, with no security risk and no maintenance, the cheapest option may be to leave it running indefinitely. Deprecating things that aren't costing you anything spends client goodwill for nothing.
- **Emergencies.** A vulnerability that requires disabling something today can't wait for a migration window. Disable it, then communicate. The lifecycle is for planned removals; don't pretend an emergency is one.

## Trade-offs

- **Long windows mean long dual maintenance.** Twelve months of deprecation is twelve months of running, testing, and fixing both the old path and the new one.
- **Per-account usage tracking is real infrastructure.** Upserted last-seen records per account and integration are cheap compared with full request logs, but they still need to be built, retained for the lookback window, and handled as the account data they are (19.1).
- **Headers are mostly unread.** Their value depends on your SDKs and your clients' tooling. They're cheap to send, but don't count them as having reached anyone.
- **Exceptions become permanent.** An extension granted without an expiry, or renewed every time it expires, is just a second, quieter support policy.
- **Some breakage is unavoidable.** Unreachable accounts, abandoned integrations still running on someone's server, clients who ignored every message. The process reduces breakage; it doesn't eliminate it, and the support spike on the day should be planned for.
- **Credibility is cumulative.** Every slipped date makes the next deprecation slower. Every date kept makes the next one faster.
- **Your engineers end up doing other people's migrations.** For high-value accounts, the fastest route is often your team helping write their fix. Budget for it.

## Alternatives

**Never remove.** Freeze the old thing and keep it running forever. Honest, and sometimes right — particularly for a cheap shim. The costs are the branches in the core, the security surface, and the drag on every future change, all of which grow.

**A permanent adapter.** Rebuild the old endpoint as a thin translation over the new one, delete its original implementation, and keep the adapter. This gets most of the cleanup benefit without breaking anyone, and it works whenever the old contract can be expressed in terms of the new one — the transform chain in 33.1b is a systematic version of this.

**Migrate clients yourself.** Where you control the client-side configuration — hosted plugins, a managed integration, SDKs that auto-update — change it on their behalf. Clients never have to act. This works only for the part of the client base you can actually reach this way.

**Paid extended support.** Charge accounts that want to stay on the old thing past the sunset date. This puts a price on the real cost of supporting them, converts an argument into a decision the client makes, and funds the maintenance. It fits enterprise APIs well and consumer APIs badly.

**Hard cutover.** A date and a switch, with no lifecycle in between. Appropriate for a small, engaged client base; the problem above is what it looks like with a large one.

## How to Achieve It

**Level 0 — A policy and a contact.** Publish what "deprecated" means, the minimum window, and where deprecations will be announced. Start collecting a technical contact for every account. *Do this before your first deprecation — ideally before your first external client.*

**Level 1 — Per-account usage with last-seen.** For each thing you might deprecate — versions, endpoints, auth methods, SDK versions — record which accounts and integrations use it and when they last did. *Move here when:* you're planning your first real deprecation, and it needs to be in place before the clock starts.

**Level 2 — In-band signals and a frozen population.** `Deprecation` and `Sunset` headers, SDK warnings, deprecation flags in your API descriptions, a per-account dashboard view, and no new adoption. *Move here when:* the deprecation is announced.

**Level 3 — Removal as a rehearsed runbook.** A readiness check over remaining accounts, an exception registry with expiries, brownouts (33.2b), a `410` stub, and a switch that reverses the removal. *Move here when:* the sunset date is close enough to schedule.

## Implementation

TypeScript. Three pieces: marking and measuring, deciding, and removing.

### A registry of deprecations, and a middleware that measures and signals

Deprecations are data, with a predicate that says which requests they apply to:

```ts
interface Deprecation {
  id: string;           // "version:2019-06-01", "auth:query-key"
  deprecatedAt: Date;
  sunsetAt: Date;
  guide: string;
  applies: (req: ApiRequest) => boolean;
}

const DEPRECATIONS: Deprecation[] = [
  {
    id: "auth:query-key",
    deprecatedAt: new Date("2026-04-01T00:00:00Z"),
    sunsetAt: new Date("2026-10-01T00:00:00Z"),
    guide: "https://docs.example.com/migrate/auth-header",
    applies: (r) => r.url.searchParams.has("api_key"),
  },
  // "version:2019-06-01" applies when r.version === "2019-06-01", and so on.
];

async function deprecationSignals(req: ApiRequest, res: ApiResponse) {
  const hits = DEPRECATIONS.filter((d) => d.applies(req));
  if (hits.length === 0) return;

  for (const d of hits) {
    // Upsert (account, deprecation, integration) -> last_seen. Never sampled.
    await usage.touch(req.accountId, d.id, req.integration);
  }

  const soonest = hits.reduce((a, b) => (a.sunsetAt <= b.sunsetAt ? a : b));
  res.setHeader("Deprecation", `@${Math.floor(soonest.deprecatedAt.getTime() / 1000)}`);
  res.setHeader("Sunset", soonest.sunsetAt.toUTCString());
  res.appendHeader("Link", `<${soonest.guide}>; rel="deprecation"`);
}
```

> **One request, several deprecations.** A request on the old version using a query-string key hits both, but the headers carry one date each. Send the soonest sunset, and make the linked page account-specific (or link the account's dashboard view), so the header points to the full list rather than trying to be it.

> **The header's scope is a resource; yours may not be.** RFC 9745 describes the deprecation of the resource the response came from. "Query-string authentication is deprecated" isn't about any one resource. The RFC allows a broader scope as long as you document it, so say plainly in your docs what your `Deprecation` header refers to.

> **`touch` is an upsert, not a log line.** One row per account, deprecation, and integration, with a last-seen timestamp and a count, keeps the data small enough to keep for a year, and makes "who's left?" a cheap query instead of a log search.

### The go/no-go decision as a query

The readiness question from "Deciding to turn it off," written as code:

```ts
async function readiness(depId: string, now = new Date()) {
  const lookback = 365 * DAY; // longer than any client's business cycle
  const rows = (await usage.forDeprecation(depId))
    .filter((r) => now.getTime() - r.lastSeen.getTime() < lookback);

  const excepted = rows.filter((r) => r.exceptionUntil && r.exceptionUntil > now);
  const unreached = rows.filter((r) => !r.exceptionUntil && !r.acknowledgedAt);

  return {
    remainingAccounts: new Set(rows.map((r) => r.accountId)).size,
    withException: excepted.length,
    unreached, // named, with integration and last-seen; the list the go/no-go is about
    ready: unreached.length === 0,
  };
}
```

`ready` is deliberately strict. In practice some accounts will never respond, and the decision becomes "we've tried every channel for these 40 accounts and accept that they'll break" — but that should be a decision someone makes looking at 40 named rows, not an accident discovered on the day.

### After the sunset

```ts
app.all("/v/2019-06-01/*", async (req, res) => {
  await usage.touch(req.accountId, "removed:version:2019-06-01", req.integration);
  res.status(410).json({
    error: {
      code: "version_removed",
      message: "API version 2019-06-01 was removed on 2026-10-01.",
      guide: "https://docs.example.com/migrate/2019-06-01",
    },
  });
});
```

(With header- or pin-based versions, the same check lives in the version-resolution step from 33.1b instead of a route.)

> **Keep counting after removal.** The post-removal record is the list of everyone you missed. It tells support who's about to call, tells you whether the damage justifies flipping the switch back, and — weeks later, when it's been silent — tells you it's safe to delete the old code for good.

## Further Reading

- **RFC 9745, "The Deprecation HTTP Response Header Field"** (2025) — the `Deprecation` header and `deprecation` link relation, including scope and how it relates to `Sunset`.
- **RFC 8594, "The Sunset HTTP Header Field"** — the removal-date header and `sunset` link relation.
- **Winters, Manshreck & Wright, _Software Engineering at Google_, chapter "Deprecation"** — advisory versus compulsory deprecation, why deprecations stall, and why removing things should be designed for from the start. Written about internal code, and almost entirely applicable to APIs.
- **Zalando RESTful API Guidelines, "Deprecation" section** — a concrete set of rules (obtain client consent on timelines, reflect deprecation in the spec, monitor usage, send the headers) that works well as a starting policy.
- **Stripe, "Versioning and support policy"** — an example of a published support policy tied to a versioning scheme.
- **OpenAPI Specification, the `deprecated` field** on operations, parameters, and schemas — the machine-readable flag that makes generated clients warn.
- **In this collection:** 33.1a (why response-field usage is invisible), 33.1b (the versions and branches deprecation retires), 33.2b (outreach, migration guides, and brownouts), 17.1b (deprecating webhook formats), 19.1 (handling per-account usage data), 42.3 (forced upgrades for mobile clients).

The Java sibling proposed in 33.1b, on Spring Framework 7's versioning support, would cover the server side of this too: Spring can attach deprecation and sunset hints to responses for deprecated versions through its version strategy, which is a useful contrast to the hand-built middleware here. No separate sibling is needed for this article.

---

The habit to take from this: **when you add something to an API, ask how you would remove it** — who you'd need to reach, how you'd know who they are, and what they'd see on the day it's gone. If you can't answer, the removal will be hard long before it's necessary.
