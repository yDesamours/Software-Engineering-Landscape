# Breaking Changes: What a Version Is Protecting

_Module 33.1a — API Versioning & Deprecation_

## The Problem

Suppose you run a payroll platform with a public API. About 340 integrations use it: accounting tools, HR systems, time trackers, and a long tail of scripts that customers' own IT teams wrote years ago. You deploy the API several times a week. None of those 340 clients deploy when you do.

Over one quarter, five changes ship. Each was reviewed. Each seemed safe.

**The new enum value.** The product starts supporting contractors, so `employment_type` gains `"contractor"` alongside `"full_time"` and `"part_time"`. Nothing was removed. An accounting integration maps each type to a ledger account with a `switch` whose `default` branch throws. Its nightly export fails for every company that has hired a contractor — 212 of them — and nobody notices until month-end close.

**The new validation.** A state law requires tax residency on file, so `POST /employees` now rejects requests without `tax_residency`. Every integration that creates employees starts getting `422`. The team knew this one was a change; they didn't think of it as *breaking*, because the field was legally required.

**The smaller page.** To protect the database, the default `limit` on `GET /employees` drops from 500 to 100. Pagination was always documented. A time-tracking integration never followed the `next` link, because none of its test customers had more than 500 employees. Its sync now silently stops at employee 100. No errors anywhere — just missing hours on payslips.

**The order.** A query refactor drops an `ORDER BY id` that was never in the docs. Results used to come back in creation order; now they don't. An HR system that diffed consecutive syncs by position decides every employee changed and sends 9,000 "your profile was updated" emails.

**The added field.** `preferred_name` appears on the employee object. A customer's in-house script, generated from your OpenAPI spec with strict validation that rejects unknown properties, now fails on every response.

The retro concludes: *we need versioning. Put everything new behind `/v2` and never touch `/v1` again.*

Walk that back through the five incidents. Versioning would have helped with exactly one of them — the validation change, which the team already knew was a change. The other four would have shipped straight into `/v1`, because nobody classified them as breaking. And the one it would have helped with can't actually be sheltered: the tax law applies to `/v1` callers too. A version number doesn't exempt anyone from a statute.

So versioning isn't the missing piece. The missing piece is upstream of it: **nobody could say, before shipping, whether a change would break a client** — because nobody had written down what the API promises, and nobody had a way to check a change against it.

## What It Is

A change is **backward compatible** if every client that worked before it keeps working after it, without changing anything. A change that can make a working client fail is **breaking**.

What decides that is the API's **compatibility contract**: what you promise not to change, and — just as important — what you tell clients they must tolerate. Much of this article is about the second half, because it's the half that makes evolution possible at all.

Two neighbors are worth separating:

- **Backward vs forward compatibility.** Backward compatibility is the server's job: new server, old client, still works. Forward compatibility is the client's job: old client code, faced with data from a newer server (fields it has never seen, values it doesn't know), still works. Most of the five incidents were forward-compatibility failures on the client side that became the server's problem anyway.
- **Compatibility vs versioning.** Versioning is what you do when you *can't* stay compatible — a mechanism for shipping a known break without forcing it on everyone at once. It's covered in 33.1b. This article is about everything before that: knowing what breaks, avoiding it where you can, and recognizing when you can't.

## Recognizing the Problem

- Release notes say "no API changes" and integration tickets arrive anyway.
- "Is this breaking?" is decided in code review, by whoever happens to be reviewing, from memory.
- You find out a field is used when you remove it.
- Partners ask what changes they should expect without notice, and there's no page to link them to.
- "Additive only" is the rule, and there's an unrecorded list of exceptions to it.
- Nobody can answer "which clients send parameter X?" in under an hour.
- After an incident, the proposed fix is "we need `/v2`" — for a change nobody knew was breaking.
- Integrators pin an old SDK version because the last upgrade broke them.

## How It Works

### Direction decides the verdict

The same change can be safe or breaking depending on which way the data flows.

In a **request**, the client produces data and you consume it. Anything you do that makes you accept *more* — a new optional field, a longer maximum length, a newly allowed value — can't hurt a client that was already sending valid requests. Anything that makes you accept *less* breaks someone who was sending what used to be valid.

In a **response**, you produce and the client consumes. Now the logic flips. Emitting *less* variety — fewer possible values, a narrower range, a field that's now always present — can't surprise a client that handled the wider set. Emitting *more* can: a value the client's code has never seen, a string longer than the column it's stored in, a field that's now sometimes missing.

The one-line version: **accept wider, emit narrower.**

```
                              in a REQUEST          in a RESPONSE
                              (you consume)         (they consume)
add optional field            compatible            compatible*
add required field            BREAKING              compatible*
remove field                  BREAKING†             BREAKING
optional → required           BREAKING              compatible
required → optional           compatible            BREAKING
add enum value                compatible            BREAKING*
remove enum value             BREAKING              compatible
widen (longer max, new fmt)   compatible            BREAKING
narrow                        BREAKING              compatible

 * compatible only by contract — safe because you told clients to expect it
 † even if you silently ignore it: the client still thinks it's doing something
```

The incident list maps straight onto this table. The new validation is "optional → required" in a request. The new enum value is "add enum value" in a response — breaking by default.

### Compatible by contract

Look at the starred rows. Adding a field to a response and adding an enum value to a response are both, strictly, emitting *more*. By the rule above they're breaking. Yet every API that has ever evolved does both constantly. If they counted as breaking, you could never add anything.

They're safe for one reason only: **you told clients in advance to tolerate them.** A compatibility contract typically says something like:

- New fields may appear in any response object. Ignore fields you don't recognize.
- Enum values may be added. Handle unknown values with a sensible fallback.
- New event types, error codes, and response headers may appear.
- Object key order and array order are not guaranteed unless documented.
- Pagination sizes and defaults may change; always follow `next`.

This is a transfer of cost. Every line on that list is something you get to change freely because the client agreed to absorb it. Stripe publishes such a list of changes it considers backward compatible; Zalando's API guidelines go further and mark extensible enums explicitly in the schema. The list only works if it exists *before* the first client writes a `switch` statement — publish it later and you've published it to people who've already written the code it forbids.

It also only works to the extent clients actually comply, which is why a contract usually comes with enforcement you control: SDKs that are tolerant by construction, generated types that model enums as open (a union plus an "unknown" case), and — cheaply and effectively — a sandbox environment that occasionally adds unknown fields and enum values to its responses, so strict clients fail in testing rather than in production. 17.1b applies the same rules to webhook payloads.

### The part the schema doesn't show

Three of the five incidents — the page size, the ordering, and (arguably) the field that clients assumed was always present — involve nothing a schema diff would flag. They're **behavioral** changes, and the contract covers them too, whether you wrote it down or not.

```
                what you documented
         ┌──────────────────────────────┐
         │ paths, fields, types,        │   ← a schema diff sees this
         │ required, enum values,       │
         │ status codes                 │
  ───────┴──────────────────────────────┴───────  waterline
         │ defaults, ordering, page     │
         │ sizes, error wording, timing,│   ← clients depend on this too
         │ side effects, rounding,      │
         │ which "optional" fields are  │
         │ in practice always present   │
         └──────────────────────────────┘
                 what you actually do
```

Common behavioral breaks: a changed default (page size, sort, currency, time zone); a synchronous operation becoming asynchronous (`201` with the resource becoming `202` with a job); a new side effect (the endpoint now sends an email); a different status code for the same failure (a client's retry logic branches on it); rounding or precision changes; weaker consistency (a read immediately after a write no longer sees it); a tighter rate limit.

This is **Hyrum's Law**: with enough users, every observable behavior of your system will be depended on by somebody, regardless of what you promised. The contract says what you're *entitled* to change. Hyrum's Law says what it will *cost*. They're different questions, and "compatible" in practice is a judgment that answers both — is this allowed, and how many people will it hurt anyway?

### What you can and can't observe

Answering "how many people will it hurt" runs into an asymmetry that shapes everything downstream, including deprecation (33.2).

You can observe requests. Which clients call which endpoints, send which parameters, set which fields, use which values — all of it passes through your server and can be logged per API key.

You cannot observe responses being consumed. You send `name` to 340 clients; you have no idea which of them read it. The only way to find out is to stop sending it.

So request-side changes can be sized with data, while response-side changes can only be sized with guesses — unless you convert reads into requests. Field selection (`?fields=`), expansion parameters (`?expand=manager`), and GraphQL's per-query field lists all do exactly that: the client has to *ask* for the data, and asking is visible.

### Changing things without breaking them

When a change you need is on the breaking side of the table, there's usually a compatible route to the same place, at the price of carrying both shapes for a while:

- **Add, don't alter.** A new field, parameter, or endpoint alongside the old one, rather than a change to the old one's meaning.
- **Expand, then contract** (also called parallel change). To rename `name` to `given_name` + `family_name`: accept both on requests, emit both on responses, move clients across, and only then remove the old one — which *is* a breaking change, handled through deprecation (33.2). It's the same sequencing as a zero-downtime database migration (6.3), applied to a contract instead of a table.
- **Opt in.** New behavior behind an explicit parameter or header, so only clients who ask for it get it. The page-size change could have been "default stays 500; clients may request up to 1,000, and new API keys get 100" — which is the idea that 33.1b turns into version pinning.

### The breaks you can't avoid

Some changes are breaking and mandatory: a legal requirement (the tax field), a security fix (you must stop returning full account numbers, or stop accepting a weak signature scheme), a dependency you don't control disappearing. These apply to every client on every version at once. No versioning scheme shelters them. What you have is notice, clear communication, telemetry to find who's affected, and time — the subject of 33.2.

## When It's Appropriate

This discipline is for any API with consumers you don't deploy:

- **A public or partner API.** The payroll platform: 340 integrations, some written by people who've since left their companies. You can't coordinate a change with them; you can only avoid breaking them or warn them.
- **Mobile backends.** If 15% of sessions come from app builds more than six months old, every response shape you've ever shipped is still being parsed somewhere. Module 42.3 goes deeper.
- **An internal platform service with many consumer teams.** Twenty teams calling a shared identity service is a public API in every way that matters, just with better phone numbers.
- **Anything asynchronous.** Webhook payloads, queue messages, and events sit in retries and logs long after they're produced. A consumer may read a message written by code you deleted last month.

And in a lighter form, for your own frontend. A web app deployed with its API still has a skew window: users keep tabs open for days, running JavaScript from the previous release against the new server. The contract there only needs to hold across one or two releases, but it needs to hold.

## When It's Unnecessary or Overkill

- **One consumer, same repository, same deploy** — beyond that skew window, just change both sides together. A compatibility policy for an API with one caller you control is ceremony.
- **Explicitly unstable surfaces.** A beta endpoint that's genuinely labeled as such (a `/beta/` path, a preview header, a line in the docs that says "may change without notice") can move fast. The label has to be real, though: a "beta" endpoint that's been stable and heavily used for two years has a contract whether you like it or not.
- **Heavy tooling for a handful of known consumers.** If you have five integrators and can email all of them, email them. Traffic replay and usage dashboards (the later levels below) pay off at dozens or hundreds of consumers, not five.
- **Permanent conservatism.** Refusing ever to fix a genuine design mistake because someone *might* depend on it is its own failure. Sometimes the right answer is a managed break with notice. Compatibility is the default, not a vow.

## Trade-offs

- **Cruft accumulates.** Additive evolution means the old shape never quite leaves. `name` and `given_name` coexist; three ways of filtering by date all work. Every one is surface area to document, test, and keep behaving identically.
- **Compatibility shims are lossy.** Mapping old input onto a new model often can't be exact — see the name-splitting aside in the implementation. The shim keeps clients running while quietly degrading their data.
- **The contract pushes cost onto clients.** "Treat enums as open" means integrators can't write exhaustive switches, and generated SDK types get weaker (a union plus `unknown` instead of a closed set). Some clients won't comply, and when they break, it's still your support ticket.
- **Detection has false positives and blind spots.** A schema-diff gate flags changes that are technically breaking but harmless in practice, so it needs an exception process — which itself needs discipline, or the exception becomes the path of least resistance. And it's blind below the waterline, which is where the costliest breaks live.
- **Telemetry costs something.** Per-client usage records of fields and parameters are more data, more storage, and more personal-data handling than ordinary request logs (19.1).
- **It slows design.** Every field you add is a field you may be supporting for years. Teams that take compatibility seriously become, correctly, more hesitant to add things — which is sometimes exactly the friction you want and sometimes just friction.

## Alternatives

**Version first, compatibility second.** Treat every non-trivial change as a new version and let clients migrate at their own pace. This moves the cost from design time to operations — you run and test several versions at once — and still doesn't help with changes nobody recognized as breaking. 33.1b covers when it's worth it.

**Consumer-driven contract tests.** With Pact or similar tools, each consumer publishes the exact requests it makes and the fields it reads, and the provider's build verifies it still satisfies all of them. This solves the observability asymmetry directly — you *know* who reads `name`. The limit is that it only covers consumers who participate, which makes it excellent for internal services (21.1) and nearly useless for a public API.

**Client-selected fields.** GraphQL (Module 8), or REST with mandatory field selection. Clients declare what they read, so response-side usage becomes measurable and removing a field becomes a data-driven decision. The cost is a more complex API and the loss of simple, cacheable fixed responses.

**The SDK as the contract.** Some platforms support only their official client libraries and treat the wire format as private. The wire can then change freely, and breaking changes move into the SDK, governed by semantic versioning. This works when you can realistically require SDK use; it fails the moment someone calls the API with `curl`, and someone always does.

**Freeze.** Some interfaces simply never change once published — many protocols and file formats work this way. A legitimate choice when stability is the whole product, and a painful one everywhere else.

## How to Achieve It

**Level 0 — Write the contract down.** One page: what you may change without notice (the "compatible by contract" list), what clients must do to be safe, and what you'll treat as breaking. Link it from the API docs' front page. *Do this before the first external consumer exists; after that, you're negotiating with code already written.*

**Level 1 — Check schema changes mechanically.** Compare every change's API description (OpenAPI, protobuf, GraphQL schema) against the *released* one in CI, and fail the build on breaking changes unless someone explicitly approves the exception. This needs a spec that's actually authoritative — either generated from code or validated against real responses in tests (7.2), otherwise you're diffing a document nobody follows. *Move here when:* a reviewer misses a breaking change, or you have more than one team changing the API.

**Level 2 — Record usage per client.** For every request, log the API key, endpoint, which optional parameters and request fields were present, notable values, and the SDK name and version from the user agent. Aggregate it so "who sends `name`?" is a query, not an investigation. *Move here when:* meetings about removing something end with "we don't know if anyone uses it."

**Level 3 — Catch behavioral changes.** Replay a sample of sanitized production requests against the new build and diff the responses against the current one, ignoring the differences your contract allows (new fields, timestamps, IDs). This is the only level that sees below the waterline. *Move here when:* you've had an incident from a change that passed the schema check — the ordering incident is the classic trigger.

When a change is breaking and you've decided it's necessary anyway, you're out of this article and into versioning (33.1b) and deprecation (33.2).

## Implementation

TypeScript, because the ideas here are mostly about data shapes, and TypeScript's type system makes the shapes and their asymmetries easy to see.

### The asymmetry, as code

Tools like oasdiff (for OpenAPI) and `buf breaking` (for protobuf) encode hundreds of rules. Under all of them is a small table that fits in one function:

```ts
type Side = "request" | "response";
type Verdict = "compatible" | "by-contract" | "breaking";

type Change =
  | { kind: "field-added"; required: boolean }
  | { kind: "field-removed" }
  | { kind: "made-required" }
  | { kind: "made-optional" }
  | { kind: "enum-value-added" }
  | { kind: "enum-value-removed" }
  | { kind: "limit-widened" }   // longer maxLength, larger maximum, new format
  | { kind: "limit-narrowed" };

// Request: the client produces, you consume — accept wider, never narrower.
// Response: you produce, the client consumes — emit narrower, never wider,
// except where the published contract told clients to expect more.
function classify(c: Change, side: Side): Verdict {
  switch (c.kind) {
    case "field-added":
      if (side === "request") return c.required ? "breaking" : "compatible";
      return "by-contract";
    case "field-removed":      return "breaking";
    case "made-required":      return side === "request" ? "breaking" : "compatible";
    case "made-optional":      return side === "request" ? "compatible" : "breaking";
    case "enum-value-added":   return side === "request" ? "compatible" : "by-contract";
    case "enum-value-removed": return side === "request" ? "breaking" : "compatible";
    case "limit-widened":      return side === "request" ? "compatible" : "breaking";
    case "limit-narrowed":     return side === "request" ? "breaking" : "compatible";
  }
}
```

A `"by-contract"` verdict resolves to `"breaking"` if your published contract doesn't cover that case. That's the practical consequence of Level 0: without it, the two most common changes you make are technically breaking ones.

> **Notice what the `Change` type can't express.** There's no `default-changed`, `order-changed`, or `now-sends-email`. They aren't missing from this toy; they're missing from every schema-diff tool, because they don't appear in a schema. That's the waterline, in type form.

### A rename, expanded before it's contracted

Replacing `name` with `given_name` and `family_name`. On the request side, accept both and record who still uses the old one:

```ts
function readEmployeeInput(body: EmployeeInput, client: ClientId): NormalizedInput {
  if (body.name !== undefined && body.given_name === undefined) {
    usage.record(client, "request:employee.name");
    const [given, ...rest] = body.name.trim().split(/\s+/);
    return { ...body, given_name: given, family_name: rest.join(" ") };
  }
  return body;
}
```

> **The shim is quietly lossy.** "Mary Ann Smith" becomes given name "Mary," family name "Ann Smith." A mononym gets an empty family name. The old field simply can't carry what the new ones can, so clients that stay on it keep running while their data gets subtly worse. This is common: compatibility layers preserve *availability*, not always *meaning*. Say so in the migration guide, and it becomes a reason for clients to move rather than a surprise later.

On the response side, emit both:

```ts
function renderEmployee(e: Employee): EmployeeResponse {
  return {
    id: e.id,
    given_name: e.givenName,
    family_name: e.familyName,
    name: [e.givenName, e.familyName].filter(Boolean).join(" "), // deprecated
  };
}
```

> **Here the asymmetry bites.** The request-side counter will one day read zero, and that will mean something. There's no equivalent line to write in `renderEmployee` — you can't record who reads `name`. Your options are to make reading it an explicit request (`?fields=name`, or tying the old field to a version pin, 33.1b), to broadcast a deprecation signal and watch who reacts (33.2), or to remove it and find out. Decide which before you start the rename, not when you're trying to finish it.

### The CI gate

The mechanical check from Level 1, sketched as a GitHub Actions step (check the tool's docs for the current flags):

```yaml
- name: Compare against the released contract
  run: |
    git show origin/production:api/openapi.yaml > released.yaml
    oasdiff breaking released.yaml api/openapi.yaml --fail-on ERR
```

> **Compare against what's released, not against `main`.** If two PRs each make a breaking change and the first merges, the second one's base already includes the first — and the first is never checked against what clients actually have. The baseline should be the contract in production. The exception path — a label like `breaking-change-approved` that requires a linked deprecation plan — belongs in the same workflow, so approving a break and planning for it are one step.

## Further Reading

- **Hyrum Wright, "Hyrum's Law"** (hyrumslaw.com), and **Winters, Manshreck & Wright, _Software Engineering at Google_**, especially the chapters on dependency management — the most careful treatment of why "compatible" is a claim about users, not about diffs.
- **Google API Improvement Proposals, AIP-180 "Backwards compatibility"** (google.aip.dev/180) — a precise, public catalogue of what Google treats as breaking, including the behavioral cases.
- **Zalando RESTful API Guidelines, "Compatibility" section** — a strong example of a written contract, including the extensible-enum convention and the rule that clients must tolerate new fields.
- **Stripe API documentation, "Upgrades"** — a real, published list of changes a major API considers backward compatible. Useful as a template for your own Level 0 page.
- **Martin Fowler, "TolerantReader"**, and **Danilo Sato, "ParallelChange"** (both at martinfowler.com) — the client-side half of the contract, and the expand-then-contract sequence.
- **RFC 9413, "Maintaining Robust Protocols"** — a critique of "be liberal in what you accept," arguing that tolerance which is never exercised hides bugs until it's too late to fix them. Good counterweight to everything in the "compatible by contract" section, and the reason the sandbox that injects unknown values is worth building.
- **oasdiff** and **Buf's `buf breaking`** documentation — the rule catalogues are worth reading just to see how many ways a schema can break.
- **Pact documentation** — for consumer-driven contract testing where you know your consumers.
- **In this collection:** 6.3 (expand-and-contract for database schemas), 7.2 (keeping the spec authoritative), 17.1b (compatibility rules for webhook payloads), 21.1 (contract tests), Module 8 (GraphQL field selection), 42.3 (mobile clients that never update), 33.1b (versioning schemes), 33.2 (deprecation).

A **Go sibling built on gRPC and protobuf** would be worth writing, because protobuf splits compatibility into two layers this article collapses into one. *Wire* compatibility depends on field numbers, not names — so renaming a field is free on the wire but breaks generated Go code, while reusing a deleted field's number compiles fine and silently corrupts data. That's why `.proto` files carry `reserved` declarations, and why `buf breaking` has separate rule sets for wire and source compatibility. Not yet written.

---

The habit to take from this: **before you ship a change, ask who reads what you're changing — and whether you'd be able to find out.** If you can't, that's the first thing to fix, well before you choose a version number.
