# Versioning Schemes: Where the Version Lives and What It Pins

_Module 33.1b — API Versioning & Deprecation_

## The Problem

Suppose you run a shipping API. Online stores call it to compare carrier rates, buy labels, and track parcels. There are about 2,000 active API accounts. Around 300 are custom integrations maintained by developers. The rest are e-commerce plugins — some yours, some third parties' — installed on stores whose owners have never read an API doc and update plugins only when something forces them to.

You've done the work from 33.1a: you have a compatibility contract and a CI check, and you know exactly which of your planned changes are breaking. Three of them are, and all three are necessary:

- **Errors need structure.** Errors are currently `{ "error": "Invalid postcode" }` — a bare string. Integrators parse the English text to decide what to show the user. You need `{ "error": { "code", "message", "param" } }`. The type of an existing field changes; there's no additive route.
- **A delivery status needs splitting.** `delivered` has to become `delivered` and `delivered_to_locker`, because stores send different customer emails for each. Your early docs listed the statuses as a closed set, so a new value breaks clients with exhaustive `switch` statements.
- **Label purchase needs to go asynchronous.** Some carriers now take 20–40 seconds to issue a label, and synchronous requests are timing out. `POST /labels` should return `202` with a job to poll or a webhook to wait for, instead of `201` with the label.

The team does what most teams do. They copy `routes/v1/` to `routes/v2/`, make all three changes in the copy, and announce `/v2`. Eighteen months later:

**The fork has drifted.** The two route trees share services, but each has its own controllers, validation, and serializers. Of 40 bug fixes since the split, 11 were applied only to v2. One of them corrected a fuel-surcharge calculation, so v1 clients are still being quoted the wrong price.

**The break arrived anyway, through the side door.** Webhooks were never versioned — there's one payload format. When v2 introduced `delivered_to_locker`, the webhook sender started emitting it to everyone, including v1 integrations with the closed `switch`. The exact break the version was meant to prevent happened through a path the version didn't cover.

**Nobody moved.** 70% of traffic is still on v1. Moving meant rewriting error handling, status handling, and the label flow in one go, because v2 bundled all three changes. A plugin maintainer who could have handled the status split in an afternoon couldn't take it without also taking the async rework — so they took neither.

**A fourth breaking change is now needed.** The proposal is `/v3`. That's three route trees.

Nothing here is wrong with the *idea* of versioning. What went wrong is a set of choices made without noticing they were choices: that a version is a fork of the code, that a version is a whole new API, that a version belongs to a URL rather than to a client, and that versions accumulate without end.

## What It Is

**API versioning** lets each client choose which contract it gets, so a breaking change can ship without forcing every client to absorb it at the same moment.

A versioning scheme is really four separate decisions, which teams tend to make together without realizing they're separable:

1. **Where the version travels** — in the path, a header, the media type, a query parameter, or the account's settings.
2. **What an unversioned request gets** — the latest, the oldest, a pin, or an error.
3. **What a version is** — a whole new API every few years, or a dated step containing one or two changes.
4. **How the server serves several at once** — separate code per version, or one core with translation at the edges.

The v2 story is decision 4 made by copying a directory, decision 3 made by bundling, and decision 1 treated as the whole question.

One neighbor to separate: **API versions are not semantic versions.** Semantic versioning (major.minor.patch) is designed for packages, where each consumer installs a specific release and upgrades when they choose. A web API has one deployed instance; every client gets your minor and patch changes the moment you deploy them, whether they asked or not. The only number a client can meaningfully choose is the one that controls breaking changes. That's why web APIs use `v1`, `v2`, or dates — and why semver belongs on your SDKs, which *are* packages. The two need to be mapped to each other, which comes up below.

## Recognizing the Problem

- You have a known breaking change and no way to give it to some clients but not others.
- `v2` is a copied directory, and fixes land in one copy and not the other.
- A "version" covers request paths but not webhooks, events, or files you generate.
- Most traffic sits on the old version, and the migration guide is long enough that you understand why.
- Requests without a version get "the latest," and a release broke clients who never opted into anything.
- Logs don't record which version a request was served at, so support can't reproduce what a customer saw.
- Someone asks when v1 will be turned off, and nobody can answer.
- Proposing a new breaking change means proposing a new major version, so needed changes get postponed.

## How It Works

### Where the version travels

```
path          GET /v2/labels/123                 visible, trivially routable, cacheable
header        Api-Version: 2025-09-01            URLs stay stable; invisible in a browser
query         GET /labels/123?api-version=…      visible, easy; mixes with real parameters
media type    Accept: application/vnd.ship.v2+json    per-resource; awkward tooling
account pin   (nothing in the request)           the account's saved version applies
```

**Path** versioning is the most common and the easiest to operate: you can see the version in any log line, route it at a load balancer, and paste a URL into a browser. Its quiet cost is that a global prefix invites a global fork. When `/v2/` is a prefix on every URL, "v2" naturally becomes a copy of everything under it. It also makes links awkward — does a v1 response link to `/v1/labels/123` or to `/v2/`?

**Headers** — `Stripe-Version`, `X-GitHub-Api-Version` — keep URLs identical across versions, so an ID or link means the same thing everywhere. The costs are visibility (you won't see the version in a browser or in a proxy log unless you log it deliberately) and caching: any cache between you and the client must include the header in its cache key, via `Vary: Api-Version`, or it will serve one version's response to another version's client (13.1).

**Query parameters** — Azure's required `api-version` is the best-known example — are as visible as paths without implying a fork, at the price of a version sitting among ordinary filters.

**Media types** version each representation independently through content negotiation. It's the most principled option on paper and the least used in practice, because every client and tool has to construct custom `Accept` headers correctly.

**Account pins** put nothing in the request: the version is stored against the API key and applied automatically. Usually combined with a header that overrides it.

The honest summary is that this choice matters less than the argument it usually generates. Any of these works. The decisions below are where schemes succeed or fail.

### What an unversioned request gets

Some clients will never send a version. Whatever you do for them *is* your real default versioning policy:

- **Latest** defeats the whole scheme. Every breaking change reaches every client who didn't opt out, which is exactly the set of clients least likely to be paying attention.
- **Oldest** is safe but means new integrations start on your worst API, and have to know to ask for a better one.
- **Pinned at first use** records the current version on the account when it makes its first request, and serves that version to it from then on unless it asks otherwise. New accounts get the latest; nobody gets moved without acting. Stripe works this way.
- **Required** — reject the request with a clear `400` naming the supported versions. The most explicit option, and a reasonable one for a new API, but a hard change to introduce to an existing one (you'd be breaking everyone to protect them from breaks).

For an existing API adding versioning for the first time, the usual move is to call today's behavior the first version, pin every existing account to it, and pin new accounts to the latest at creation.

### What a version is

**Major versions** — `v1`, `v2`, every few years, each bundling many changes. Easy to explain and document. The problem is the cliff: a client can't take one change without taking all of them, so migration becomes a project, and projects get postponed. That's the 70%.

**Dated versions** — each breaking change (or small group of them) gets a date, like `2025-09-01`. A client pinned at `2025-03-01` can move forward one step at a time, taking the status split without the async rework. Upgrades become small and frequent instead of large and rare. The cost is that there are many versions, and your documentation and changelog have to make "what changes if I move from here to there" easy to answer.

**Hybrids** group dated steps into a named, predictable cadence. Stripe, since late 2024, publishes breaking changes in named major releases twice a year, with monthly releases in between that contain only backward-compatible changes. Clients get small steps *and* a rhythm they can plan around.

**Per-resource versions** — each resource or media type versioned on its own. Maximum flexibility, and a combinatorial explanation problem: which label version works with which shipment version?

### How the server serves several versions

This is the decision that determines whether versioning is sustainable.

**Forking** — a copy of the controllers, serializers, and validation per version — is what the v2 story did. Its cost grows with every version and every fix, and fixes drift, because nothing forces a change in one copy to be made in the other.

The alternative is **one core, translated at the edges.** The core only ever speaks the latest version. Each breaking change is written as a small, self-contained *version change*: a function that upgrades an old-shape request to the next shape, and a function that downgrades a new-shape response to the previous one. A request pinned at an old version walks the chain forward on the way in and backward on the way out:

```
 request pinned at 2025-03-01
   │
   │  upgrade:   2025-03-01 ─► 2025-09-01 ─► latest
   ▼
 ┌─────────────────────────────┐
 │ core: validation, business  │   knows only the latest shape;
 │ logic, persistence          │   bug fixes land once, for everyone
 └─────────────────────────────┘
   │
   │  downgrade: latest ─► 2025-09-01 ─► 2025-03-01
   ▼
 response shaped as the client expects
```

A new breaking change adds one link to the chain. Retiring the oldest version removes the link at the bottom. The surcharge fix lands once, in the core, and reaches every version, because there's only one core.

The chain has two limits worth knowing before you rely on it:

- **A downgrade can only produce what the latest shape still contains.** If the new representation drops information an old version needs, the transform has nothing to work with. So the core sometimes has to keep producing data purely for old versions — a cost that should show up when you plan the change.
- **Behavior can't be translated.** Turning a `202` job back into a synchronous `201` isn't a reshaping of JSON; it's a different thing happening. Behavioral changes need version checks *inside* the core, and each one is a permanent branch there until the version it serves is retired. Keeping them few and visible is most of the discipline.

### The version belongs to the client, not the request

The webhook incident is the general lesson: a client's version has to govern **everything that client receives**, not just responses to requests that happened to carry a version.

- **Webhooks and events** are rendered at the version pinned on the receiving endpoint or account, using the same downgrade chain as responses. The events are stored in the latest shape and translated on delivery, which is also why 17.1b's event store needs to keep enough data for old versions to be rendered.
- **Generated files, exports, and emails with embedded data** follow the same rule if clients parse them.
- **SDKs pin a version.** A common, sound pattern: each SDK release sends the API version it was built against, so its types always match the responses it receives. A breaking API version then becomes a new *major* SDK version, and semver does what it's good at. Stripe's newer SDKs work this way.
- **Logs record the version served**, so "what did this customer see?" has an answer.

### What doesn't get a version

Only breaking changes create a new version. Compatible changes (33.1a) ship to every version immediately — otherwise old versions freeze, and clients who pinned for safety miss fixes and features for no reason.

And some breaking changes bypass versions entirely: security fixes, legal requirements, a carrier discontinuing a service. They reach every version at once. Versioning manages the breaks you choose; it does nothing for the ones you don't.

## When It's Appropriate

- **A known breaking change, many unmanaged clients.** The shipping API: 2,000 accounts, most running plugins that update on their owners' schedule, not yours. Without versioning, the only options are breaking them all on a date or never making the change.
- **Dated versions with pinning** when breaking changes are frequent (several a year), the client base is large, and client code is expensive to change — payments, logistics, accounting, anywhere integrations are business-critical and owned by people who aren't watching your changelog.
- **Major versions** when breaking changes are rare and structural: a new authentication model, a redesigned resource model, a move from one paradigm to another. If you break things once every five years, a clean `v2` with a good migration guide is simpler than a chain of transforms.
- **Mobile clients** (42.3), where the "unmanaged client" is your own app, frozen on devices that haven't updated in a year.

## When It's Unnecessary or Overkill

- **You can stay compatible.** Most changes can be made additively (33.1a). A version is the tool for changes that genuinely can't, not a substitute for the effort of finding a compatible route.
- **Known, coordinated consumers.** Five internal teams calling a service can agree on a migration date and move together. A version scheme for them is permanent machinery for a temporary coordination problem.
- **Building the machinery before the first break.** It's worth reserving a place for a version on day one — a `v1` path segment or an accepted header, recorded in logs — because retrofitting a default is awkward. Building a transformation chain with no transformations in it is not worth anything.
- **Versioning as a way to avoid saying no.** If every stakeholder's preferred redesign becomes a new version, you'll have a matrix of versions and no one who can support all of them.

## Trade-offs

- **Every supported version is a product.** It needs tests, docs, support staff who can reason about it, and examples. Supporting "every version since 2019" has a cost that grows every time you add one.
- **Transformation chains accumulate.** They're cheaper than forks, but each link is code that runs on every old-version request, written by someone who may have left, against data shapes they may have forgotten. Test each link with fixtures at both of its boundaries.
- **Behavioral branches leak into the core.** Each `if version < X` is a place where the core isn't really version-agnostic. They're the part of versioning that doesn't stay at the edges.
- **Debugging needs the version.** "It works for me" is often "it works at my version." Support tooling has to show which version a request was served at and make it easy to replay at another.
- **Headers and caches.** Header-based versions require `Vary` everywhere a cache sits, and a missed `Vary` produces cross-version responses that are very hard to diagnose.
- **Versions don't retire themselves.** Pinning protects clients from breaks so effectively that they never move. Without a deprecation process (33.2), versioning turns into unlimited support.

## Alternatives

**No versioning, compatible evolution only.** Covered in 33.1a, and the stance GraphQL takes: fields are added and deprecated, never versioned (Module 8). This works well until the first genuinely unavoidable break, at which point you need a plan — even if that plan is a new field or endpoint rather than a version.

**New resources instead of new versions.** Rather than `v2` of `/labels`, introduce `/label_purchases` with the async semantics and leave `/labels` alone. This is versioning scoped to one resource, with a clearer name. It works well for one or two changes and becomes confusing when the API has four ways to do each thing.

**Break on a date.** Announce, give notice, and change for everyone at once. Honest and cheap to run, and appropriate when the client base is small, engaged, or internal. With 2,000 unmanaged plugins it simply transfers the cost to your support team on the cutover day.

**The SDK as the contract.** If clients must use your SDK, the SDK can absorb breaking wire changes and express them through its own semver majors. Works only as far as you can actually require SDK use.

## How to Achieve It

**Level 0 — A slot for the version, and a default.** Accept a version (path segment or header), log the version served on every request, and decide what unversioned requests get — for an existing API, today's behavior, pinned on every existing account. *Do this before the first external client, or as soon as you realize you've already got some.*

**Level 1 — The first break as a version change, not a fork.** When the first genuinely breaking change arrives, implement it as a request upgrade and response downgrade at the edge, with the core moved to the new shape. Pin new accounts to the new version. *Move here when:* you have a breaking change you can't route around.

**Level 2 — The version governs everything the client receives.** Webhooks and events rendered at the client's pin; SDK releases pinned to an API version; a changelog that says exactly what changes between any two versions; a test fixture for each link in the chain. *Move here when:* you have a second version in production — which is the moment the side doors (webhooks, exports) start leaking.

**Level 3 — A cadence and a support window.** Group breaking changes into predictable releases, and publish how long each version is supported after its successor ships. *Move here when:* the chain has enough links that its maintenance shows up in planning, or clients start asking how long they can stay where they are. The support window is where 33.2 begins.

## Implementation

TypeScript, because a version change is essentially a pair of functions over data shapes, and the chain is a fold over a list.

### Version changes as data

Each breaking change is one entry, newest first. The description doubles as the changelog entry.

```ts
type Version = string; // ISO date, "2025-09-01" — compares correctly as a string

interface VersionChange {
  version: Version; // the first version with the new shape
  description: string;
  upgradeRequest?: (resource: string, body: any) => any;    // old shape -> this version
  downgradeResponse?: (resource: string, body: any) => any; // this version -> previous
}

const CHANGES: VersionChange[] = [
  {
    version: "2025-09-01",
    description: "Shipment status `delivered_to_locker` split out of `delivered`.",
    downgradeResponse: (res, b) =>
      res === "shipment" && b.status === "delivered_to_locker"
        ? { ...b, status: "delivered" }
        : b,
  },
  {
    version: "2025-03-01",
    description: "Errors are objects with `code`, `message`, `param`.",
    downgradeResponse: (res, b) =>
      res === "error" ? { error: b.error.message } : b,
  },
];
```

Applying the chain is a filter and a fold:

```ts
function requestToLatest(pinned: Version, resource: string, body: unknown) {
  return [...CHANGES].reverse()                       // oldest first
    .filter((c) => c.version > pinned && c.upgradeRequest)
    .reduce((b, c) => c.upgradeRequest!(resource, b), body);
}

function responseToPinned(pinned: Version, resource: string, body: unknown) {
  return CHANGES                                      // newest first
    .filter((c) => c.version > pinned && c.downgradeResponse)
    .reduce((b, c) => c.downgradeResponse!(resource, b), body);
}
```

The same `responseToPinned` renders webhook payloads, using the version pinned on the receiving endpoint. That one line of reuse is what would have prevented the locker-status leak.

> **The status downgrade is lossy, and that's acceptable only because it's deliberate.** A client pinned before `2025-09-01` sees `delivered` for a locker delivery — true, but less precise. Decide per change whether the old shape can carry an honest approximation. If it can't — if the only faithful old-version answer would be wrong — that's a sign the change should also be announced as a mandatory migration rather than hidden behind a pin.

> **Real resources nest.** A shipment embeds addresses, a tracking object, and sometimes a label. Transforms keyed on "the response body" miss every embedded occurrence. Production implementations apply transforms per resource type during serialization, so a shipment embedded in a tracking event gets the same treatment as a shipment fetched directly. This is where most of the real engineering in a chain goes.

### Resolving the version

Header first, then the account's pin; never "latest" by accident:

```ts
function resolveVersion(req: Request, account: Account): Version {
  const requested = req.headers["api-version"];
  if (requested) {
    if (!SUPPORTED_VERSIONS.has(requested)) {
      throw new ApiError(400, "unsupported_version",
        `Supported versions: ${[...SUPPORTED_VERSIONS].join(", ")}`);
    }
    return requested;
  }
  return account.pinnedVersion; // set when the account was created
}
```

The resolved version is attached to the request context, logged, and echoed in a response header, so both sides can always see which contract was used.

### The change a transform can't express

The async label purchase isn't a reshaping of JSON, so it lives in the core:

```ts
async function purchaseLabel(ctx: RequestContext, input: LabelInput) {
  if (ctx.version < "2026-02-01") {
    // Old contract: the label comes back in this response, however long it takes.
    return { status: 201, body: await buyLabelNow(input) };
  }
  const job = await enqueueLabelPurchase(input);
  return { status: 202, body: job };
}
```

> **Count these.** Every branch like this is a permanent fork inside the core, and it's the part of versioning that doesn't stay at the edges. A simple search for `ctx.version <` is a decent measure of how much old versions actually cost you — and the most persuasive argument, when it's time, for retiring them (33.2). The old path here also carries the timeout problem that motivated the change, so v-old clients are still getting a worse service; say so in the migration guide.

## Further Reading

- **Brandur Leach, "APIs as infrastructure: future-proofing Stripe with versioning"** (Stripe blog, 2017) — the canonical description of dated versions, account pinning, and version changes as transformation modules. Most of the architecture above is a simplified version of it.
- **Stripe documentation, "Versioning" and "Versioning and support policy"** — the current model, with named major releases twice a year, monthly compatible releases, SDKs pinned to API versions, and webhooks rendered at the endpoint's version.
- **GitHub REST API documentation, "API versions"** — calendar-dated versions in a header, with a published support window after a successor ships.
- **Microsoft Azure REST API Guidelines** — the required `api-version` query parameter, and a thorough treatment of what constitutes a breaking change across a very large API surface.
- **Google AIP-185, "API versioning"** — major versions in the path plus channel-based stability levels (alpha, beta, stable), a different answer to "how do we ship things that aren't ready to be promised yet."
- **Cadwyn** (open source, Python/FastAPI) — a working implementation of Stripe-style version changes worth reading even if you never use Python, because it shows how nested resources and request migrations are handled in practice.
- **Rossen Stoyanchev, "API Versioning in Spring"** (spring.io blog, 2025) — useful for its candor that there's no standard answer, and for seeing what a mainstream framework chose to build in.
- **In this collection:** 33.1a (deciding what's breaking in the first place), 13.1 (HTTP caching and `Vary`), 17.1b (webhook payloads and why the event store has to support old renderings), Module 8 (versionless evolution in GraphQL), 42.3 (mobile clients), 33.2 (retiring versions).

A **Java sibling on Spring Framework 7's built-in versioning** would be worth writing, because it makes the opposite architectural choice from this article. Spring routes requests to *different handler methods* by version — the `version` attribute on `@GetMapping`, with baseline versions that carry a handler forward until it's replaced — which is structured, framework-supported forking rather than a transformation chain. Seeing where that model is cleaner (behavioral changes, which are awkward here) and where it isn't (shared fixes, nested representations) would make the fork-versus-translate decision much more concrete. It also ties versions to deprecation hints out of the box, which sets up 33.2. Not yet written.

---

The habit to take from this: **a version is a promise to a client, not a label on a URL.** Ask of any scheme whether it covers everything that client receives, whether it lets them move one step at a time, and whether a bug fix still lands in one place.
