# In-App Notifications

_Module 14.2 — Email & Notification Systems_

## The Problem

A team collaboration product. People comment, mention each other, assign tasks, request reviews. All of it currently goes out by email, and the loudest customer complaint is that the product sends too much email.

So the team builds a bell icon. The design is the obvious one: when something happens, push it down the WebSocket connection the app already has open; the client keeps the list in state and renders it.

It demos beautifully. Then it meets users.

**The first bug report is a refresh.** A user sees "Priya mentioned you," gets distracted, reloads the page, and the notification is gone. It was never anywhere but browser memory. There is no record that it existed, so there is no way to tell the user what they missed, and no way to tell whether the feature is working.

**The second is absence.** Notifications only reach people who were connected when the event happened. Close your laptop at 6pm and everything that happens overnight is delivered to nobody. The bell is empty every morning, which users read as "nothing happened."

**The third is disagreement.** A user reads a notification on their laptop. Their phone still shows the badge. Their second browser tab still shows the badge. The bold-versus-not state has three independent copies and no arbiter.

**The fourth is volume.** Someone comes back from two weeks away. The bell says "99+". Inside is a chronological list of 4,300 rows, 800 of which are "Alice edited Spec v2" from a single afternoon of typing. Nothing in there is findable, so the user clicks "mark all read" and the entire feature has just been declared useless by its own audience.

**The fifth is cost.** Each page load runs `SELECT COUNT(*) FROM notifications WHERE user_id = ? AND read_at IS NULL`. That is now the most frequently executed query in the system, and the table it hits is the fastest-growing one you own.

Look at what those five have in common. Only the first two are about delivery. The rest are about **storage, state, and editorial judgment** — and the one everybody builds first, the real-time push, isn't the hard part of any of them.

## What It Is

A **notification inbox** (or notification center) is a durable, per-user, ordered collection of records describing things that happened which concern that user, carrying per-user state about whether they've been seen and acted on.

The important word is *durable*. Real-time push is a freshness optimization layered on top of something that would still work correctly if the client simply polled. Build it the other way around — the socket as the delivery mechanism and storage as an afterthought — and every problem above follows automatically.

Two neighbours are worth separating here, because they have different storage models and get conflated constantly.

An **activity feed** is "what happened in this space": one shared timeline, the same for everyone who can see it, no per-recipient rows and usually no read state. A project's history page is an activity feed. A notification inbox is "what happened that concerns *you*" — the recipient list is computed, and each recipient carries their own state. You can build the second on top of the first, but they are not the same object, and a lot of half-working notification systems are activity feeds with a bell icon on them.

A **toast** — the thing that slides in at the corner of the screen and fades — is neither. It's a transient render of an event the user happens to be present for. If a toast is the only place a notification exists, you've built the bug from paragraph three of the Problem.

## Recognizing the Problem

- Notifications live in client state and vanish on refresh.
- Users who were offline when an event happened never receive it at all.
- The unread badge disagrees between a phone and a desktop tab, and there's no rule for which one is right.
- The unread-count query appears in your top five by execution count, or your slow query log.
- "99+" is the permanent state of the badge for your most active users.
- A single editing session produces a dozen near-identical rows.
- Rendering the inbox joins five tables, and deleting a project makes someone's notification list return a 500.
- A notification is still visible to a user who has since lost access to the thing it's about.
- "Mark all as read" is a full-table update that times out for your heaviest accounts.
- The only code path that creates a notification lives inside the WebSocket handler, so a socket outage loses notifications permanently rather than delaying them.
- Nobody can answer "how many people saw the maintenance announcement" without asking them.

## How It Works

### Write first, then hint

The correct shape is two steps that fail independently:

```
event ──► notification rows written durably ──► (commit)
                                                  │
                                                  └─► "something changed" ping
                                                           over socket/SSE
                                                                 │
                                                                 ▼
                                                       client refetches inbox
```

The ping carries no payload — just an invalidation signal, at most a cursor. If it's dropped, if the connection was down, if the user was on a plane, nothing is lost: the next fetch reconciles from the table. This makes the real-time transport genuinely optional and genuinely swappable, which is the property you want from a subsystem that will be your least reliable one. (The transport itself — WebSockets, SSE, connection management, scaling — is Module 9's subject and this article takes it as given.)

Pushing full payloads is the tempting alternative and it costs you the same guarantees email cost you in the last article: the client now has notifications the server doesn't know it has, deduplication becomes the client's job, and a dropped frame is a permanently missing notification.

### Fan-out: one row per recipient, or one row per event

When an event concerns 40 people, you either write 40 rows or you write one and figure out the 40 at read time.

**Fan-out on write** materializes a row per recipient. Reads are trivial — an index on `(user_id, created_at desc)` and you're done — and per-user state is just a column on the row. Writes multiply by audience size, and so does storage.

**Fan-out on read** stores the event once and computes each user's inbox by joining their subscriptions at query time. Writes stay cheap regardless of audience. Reads get complex, pagination across multiple subscription sources is genuinely hard, and per-user read state now needs somewhere else to live.

For almost every B2B product this is not a close call: fan-out on write, and the numbers are unthreatening. A 500-person workspace announcement is 500 inserts, once. That's a rounding error, and you should not design around it. The hybrid — fan-out on write normally, fan-out on read for the handful of enormous-audience event types — is a real technique borrowed from social feeds, and it starts making sense somewhere around audiences of tens of thousands. If you're not there, writing the rows is correct and everything downstream gets simpler.

### Read state is at least three things

Teams model one boolean and then discover they needed to distinguish:

- **Seen** — the notification appeared in the user's view. This is what should usually clear the badge.
- **Read** — the user opened this specific item.
- **Acted on / dismissed** — the user did the thing, or explicitly decided not to.

Which one drives the badge determines how the feature feels. Badge-on-seen means opening the bell clears the count, which is right for ambient awareness. Badge-on-read means each item must be individually dispatched, which is right when notifications carry work — approvals, review requests — and wrong when they're mostly informational, because then the badge becomes a chore.

There's a cheap trick worth knowing for the seen case. Instead of writing a `read_at` to every row when the user opens the bell, store **one timestamp per user**: `notifications_seen_at`. The unread count is then "rows newer than that cursor," and opening the bell is a single-row update rather than a bulk one. It scales beautifully and it costs you per-item state — no "mark this one unread," no per-item read analytics. Many products want exactly that and pay for the full version anyway.

### Counting

`COUNT(*)` over unread rows is fine at small scale and becomes a problem at exactly the moment you'd rather not be refactoring. Three ways out, roughly in order of how much they cost you:

- **Cap it.** Count with `LIMIT 100` and render "99+" beyond that. Nobody has ever needed to know they have 3,412 unread notifications, and this takes ten minutes.
- **Derive it from the seen cursor**, as above.
- **Denormalize a counter** updated in the same transaction as the insert. Fastest, and now you own a counter that can drift, which it will.

### Grouping, supersession, and debounce

The step that separates a notification system from an event log: **events and notifications are not 1:1.** Three distinct collapse mechanisms, and products need all three eventually.

**Aggregation** merges by target: "Alice and 4 others commented on Spec v2." The mechanism is a group key — something like `(user_id, verb, object_id, time_bucket)` — with an upsert that appends to an actor list and bumps a timestamp instead of inserting a new row.

**Supersession** deletes or stales a notification a later event made irrelevant. You were assigned a task; you were unassigned. The first notification is not history, it's a lie sitting in someone's inbox.

**Debounce** collapses a burst: twelve edits in three minutes become one notification emitted after things go quiet. Implemented as a delayed job keyed by the group, rescheduled on each new event — which requires the background job machinery from Module 10.

This is where the inbox stops being infrastructure and becomes a product decision, and it's the work that determines whether users keep the feature turned on.

### Storing the message: text or references?

An underrated fork with permanent consequences.

**Store rendered text** at write time ("Priya mentioned you in *Q3 Planning*"). Fast reads, no joins, survives the deletion of everything it mentions. It cannot be re-localized when the user switches language, and it goes stale — the document gets renamed and the notification keeps the old name forever.

**Store structured references** (`verb: "mention", actor_id, object_type, object_id`) and render at read time. Always current, localizable, small rows. Now your inbox reads from every table in the system, an N+1 by default, and a deleted object either 500s the list or needs a fallback path in every renderer.

The workable middle is a structured payload carrying **denormalized display snapshots alongside the ids**: actor name and object title as they were, plus the ids for linking and for re-resolution when they still exist. Renames show stale text in old rows, which is almost always acceptable, and deletions degrade to a non-clickable row rather than an error.

### Retention

The notifications table grows with every interesting event in your product multiplied by audience size, and essentially nothing older than 90 days is ever read. Time-based partitioning or a TTL job should exist before this becomes the largest table in your database, because by then dropping rows is a scary operation rather than a boring one.

## When It's Appropriate

- **Collaborative products where things happen to you while you're away** — comments, mentions, assignments, approvals, review requests. The inbox is the structural answer to "we send too much email."
- **When routine activity email exceeds two or three messages per user per day.** Below that, email is genuinely fine. Above it, you're training people to filter you, and — per the previous article — engagement decline on your bulk stream is also a deliverability problem for your transactional one.
- **When the notification carries work.** An approval request belongs next to the approve button, not in a mail client that can only link back.
- **Long-session products** — dashboards, ops consoles, IDEs, support tooling — where the user is present for hours and an email about something visible on screen is noise.
- **When you need to know what was communicated.** Compliance and support both benefit enormously from a queryable record of what a user was shown and when, which email cannot give you.

## When It's Unnecessary or Overkill

- **Single-player products.** If nothing changes except when the user changes it, there is nothing to notify. A bell icon on a personal finance app is decoration.
- **Low-frequency events.** A monthly invoice doesn't need an inbox. An inbox that's empty every time someone checks it is worse than no inbox — it trains people to stop checking, which is the opposite of the goal.
- **Real-time push on day one.** Polling every 30–60 seconds is imperceptible for this feature and removes an entire subsystem. The signal to upgrade is users manually refreshing to check, or the feature being sold as live collaboration.
- **Per-item read state when a seen cursor would do.** Don't build the expensive version to support a "mark unread" affordance nobody asked for.
- **Grouping before you have one noisy notification type.** Group keys and supersession are real complexity. Earn them with an actual complaint.
- **Preferences before the inbox exists.** Users asking to turn off *everything* means your volume is wrong. Users asking to turn off *one type* is the signal that preferences are worth building — and that's orchestration, which is §14.5.

## Trade-offs

- **You've added a write amplifier.** Every interesting event now writes N rows, and your highest-volume table is one nobody considers part of the core domain. Its growth is driven by other teams' feature decisions.
- **The inbox is a covert authorization surface.** A notification that says "Bob commented on *Compensation 2026*" leaks a title and an activity pattern to someone who may have lost access since fan-out. Permissions must be re-checked at render time, not only at write time — and that check is easy to forget precisely because the notification row looks like it's already been authorized.
- **Grouping is where the bugs live.** Concurrent upserts on the same group key produce duplicate groups without the right constraint; a collapsed group that later needs to split is fiddly; and a supersession rule that's slightly too aggressive silently deletes things people needed.
- **Both message-storage options age badly**, in opposite directions. Rendered text goes stale; references make your inbox depend on the availability and deletion semantics of every other table.
- **Read state must be reconciled across devices**, which means the client can never own it and every device needs a refetch-on-focus path. Multi-tab is its own small nightmare.
- **The real-time path introduces connection state**: reconnection, backfill for the gap, and the question of whether a client that's been disconnected for an hour refetches or resyncs.
- **Volume grows monotonically.** Every team wants to add a notification type and nobody ever asks to remove one. Without an owner and a bar for what qualifies, the inbox degrades toward the thing it was built to replace.

## Alternatives

**Email only.** Durability for free, universal reach, no new tables. You give up read state, grouping, and any control over presentation — and you pay for it in deliverability, as the previous article covered.

**A shared activity feed with a per-user cursor.** One timeline per project or workspace, one `last_read_at` per user per feed. Dramatically cheaper — no fan-out at all — and it can't express "this specifically concerns you," so mentions and assignments get lost in ambient noise. Good for history, weak for attention.

**Ambient indicators instead of an inbox.** A dot on the "Reviews" tab; a count on "Assigned to me" derived from a query against data you already have. Zero new tables, never out of sync, no read state to manage, and it disappears on its own when the work is done. This is the genuinely underrated option and it's the right answer more often than it's chosen, because it isn't a feature anyone gets to demo.

**Third-party notification infrastructure** — Knock, Courier, Novu, MagicBell. You get the inbox, preferences, and multi-channel routing without building them. The cost is that notification content is deeply entangled with your domain model, so you're synchronizing user data, subscription state, and object references to a system outside your database — and the permissions problem above becomes harder, not easier, because the render happens somewhere you don't control.

**Chat as the inbox.** Route notifications to Slack or Teams, where your users already are. Real reach and zero UI to build, and you inherit that platform's grouping, preferences, and rate limits — which may be better than what you'd build. You lose the ability to keep state, and anything requiring action bounces the user back to your app anyway.

## How to Achieve It

**L1 — one table, one type, polling.** `notifications(id, user_id, type, payload, created_at, read_at)` with an index on `(user_id, created_at desc)`. Rows written in the same transaction as the event that caused them, or via the outbox if the causing event is external. Client polls on page load and on an interval. *Signal to start:* you're emailing the same routine event more than a couple of times per user per day.

**L2 — cheap counting.** Cap the count, or switch to a seen cursor. *Signal:* the badge query appears in throughput or latency monitoring.

**L3 — push invalidation.** SSE or the WebSocket you already have, carrying a signal rather than content. Postgres `LISTEN`/`NOTIFY` is a legitimate way to wire this at modest scale without adding a broker. *Signal:* users refreshing manually.

**L4 — grouping and supersession.** Group keys and upserts for your noisiest type first, not all types at once. *Signal:* a single user action produces more than a couple of rows, or the phrase "it's too noisy" in a support ticket.

**L5 — preferences and cross-channel routing.** Which notifications reach which channel, quiet hours, digests. This is a different problem and it gets §14.5.

**L6 — partitioning and retention.** *Signal:* the table enters your top three by size, which it will.

Most products are well served stopping at L4.

## Implementation

Go, for the write path — the grouped fan-out is where the interesting decisions concentrate.

The schema first, since it's carrying most of the design:

```sql
create table notifications (
  id          bigserial primary key,
  user_id     uuid        not null,
  group_key   text        not null,  -- "mention:doc_88:2026-09-14T10"
  verb        text        not null,
  object_type text        not null,
  object_id   uuid        not null,
  actors      jsonb       not null,  -- [{id, name_snapshot}, ...]
  payload     jsonb       not null,  -- title snapshot, excerpt, deep link
  count       int         not null default 1,
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now(),
  read_at     timestamptz
);

create unique index on notifications (user_id, group_key);
create index on notifications (user_id, updated_at desc);
```

That unique index is not an optimization — it's what makes the upsert safe. Two concurrent comments on the same document race on the same group key, and without the constraint you get two groups that both claim to be the aggregate.

```go
func (s *Inbox) Notify(ctx context.Context, tx pgx.Tx, ev Event) error {
    recipients, err := s.recipients(ctx, tx, ev) // subscribers, minus the actor
    if err != nil {
        return err
    }

    actor := actorSnapshot{ID: ev.ActorID, Name: ev.ActorName}
    key := groupKey(ev.Verb, ev.ObjectID, ev.At.Truncate(time.Hour))

    for _, userID := range recipients {
        _, err := tx.Exec(ctx, `
            insert into notifications
              (user_id, group_key, verb, object_type, object_id, actors, payload)
            values ($1, $2, $3, $4, $5, $6, $7)
            on conflict (user_id, group_key) do update set
              actors     = notifications.actors || excluded.actors,
              count      = notifications.count + 1,
              updated_at = now(),
              read_at    = null,          -- new activity re-surfaces the group
              payload    = excluded.payload
        `, userID, key, ev.Verb, ev.ObjectType, ev.ObjectID,
           []actorSnapshot{actor}, ev.Payload)
        if err != nil {
            return err
        }
    }
    return nil
}
```

Three things there are load-bearing. The whole loop runs **inside the caller's transaction**, so a comment that rolls back doesn't leave notifications about it — the same coupling problem the last article solved with an outbox, solved here by staying local because both writes are in the same database. The `read_at = null` on conflict is a deliberate product choice: new activity un-reads the group, which is usually right and occasionally infuriating, so it's worth being conscious that you're choosing it. And `actors` accumulates unbounded — a document with 400 commenters produces a 400-element array you only ever render three of, so this wants a cap in anything long-lived.

The read path, where the authorization re-check lives:

```go
func (s *Inbox) List(ctx context.Context, userID uuid.UUID, before time.Time) ([]Item, error) {
    rows, err := s.db.Query(ctx, `
        select id, verb, object_type, object_id, actors, payload, count, read_at
          from notifications
         where user_id = $1 and updated_at < $2
         order by updated_at desc
         limit 30
    `, userID, before)
    // ...

    // The row was authorized when it was written. That was possibly months ago,
    // and access may have been revoked since — the payload carries a document
    // title. Filter before rendering, not after fan-out.
    return s.authz.FilterVisible(ctx, userID, items)
}
```

And the count, using the cursor rather than per-row state:

```sql
select count(*) from (
  select 1 from notifications
   where user_id = $1 and updated_at > $2   -- $2 = user.notifications_seen_at
   limit 100                                -- "99+" is a feature
) t;
```

Note what the filter in `List` does to pagination: if authorization removes 4 of 30 rows, the page is short, and a naive client treats a short page as the end of the list. Either over-fetch and trim, or accept variable page sizes and paginate strictly on the cursor. It's a small thing that produces a confusing bug — "my notifications stop loading after the third scroll" — a long way from its cause.

## Further Reading

- **Martin Kleppmann, _Designing Data-Intensive Applications_, Chapter 1** — the Twitter home-timeline example is the clearest short treatment of fan-out on write versus read anywhere, and the arithmetic transfers directly.
- **Silberstein et al., "Feeding Frenzy: Selectively Materializing Users' Event Feeds" (SIGMOD 2010)** — the actual research behind hybrid push/pull fan-out, and worth reading if your audience sizes are genuinely skewed.
- **Raffi Krikorian, "Timelines at Scale" (InfoQ, 2012)** — the production version of the same problem, including why the celebrity case needed a different path.
- **PostgreSQL documentation on `INSERT ... ON CONFLICT`** and on **declarative partitioning** — the two mechanisms this article leans on hardest, and the conflict-handling semantics repay careful reading before you trust an upsert under concurrency.
- **PostgreSQL `LISTEN`/`NOTIFY`** — an unglamorous, genuinely sufficient invalidation channel for products that don't yet need a broker, with documented limits worth knowing before you rely on it.
- **Novu** (open source) — reading its notification and subscriber data model is a fast way to see which distinctions a mature system ends up needing. Useful even if you never adopt it.

A **TypeScript sibling** would reveal something this one can't, and it belongs on the client rather than the server: multi-tab read-state reconciliation, `BroadcastChannel` and the `visibilitychange`-triggered refetch, optimistic read marking that has to survive a failed request, and the reconnect-and-backfill gap. The server side of this feature is mostly schema design; the part that actually frustrates users is state synchronization in the browser, and that's a different article. Not yet written.

---

The transferable habit: whenever a feature gives each user their own state over a shared stream of events, the same three questions decide the design. Where does the truth live — and is the transport allowed to be lossy, or is it the only copy? Who owns the per-user state, the server or the device? And at what point do raw events stop being the right unit, and need to be collapsed into something a human would have written? Inboxes, feeds, unread counts, "new since your last visit" markers, and sync indicators are all the same shape wearing different clothes.
