# Whose Budget Is This?

_Module 18.2b — API Rate Limiting & Throttling_

## The Problem

A forms-and-surveys product with three kinds of traffic:

- Anonymous respondents submitting public forms.
- Signed-in users working in the web app.
- Customers' integrations calling the public API with API keys.

It sells Free, Team, and Business plans, plus Enterprise contracts.

The limiter is now in good shape. After 18.1 and 18.2a it's a fleet-wide token bucket: atomic, one clock, a failure policy per route. It takes one argument on trust, `key`, and every incident this quarter involves that argument.

**The campus.** Public form submissions are limited to 10 per minute per IP. At 09:00 a university sends a course-evaluation survey to 30,000 students. All of campus leaves the network through eight public IPv4 addresses. Thousands of students each open the form once, submit it once, and get `429 Too Many Requests`. The same week, mobile users on a carrier that shares addresses between subscribers hit the same wall every evening.

**The rotator.** Also that week, a bot submits 40,000 junk responses to a customer's lead-capture form, over IPv6. Every request comes from a different address inside one `/64`. The limiter sees 40,000 keys with one request each, and Redis gains 40,000 keys.

**The header.** Login is limited per IP. The first version keyed on the socket address. Behind a load balancer, that address is always the load balancer, so everyone shared one bucket and at 09:05 login stopped working for everyone. The fix read `X-Forwarded-For`, took the first entry, and called it the client. The first entry is whatever the client decided to send:

```
X-Forwarded-For: 6.6.6.6, 203.0.113.9, 198.51.100.4          socket: 10.0.3.12
                 │        │            │                             │
                 │        │            └ added by your load          └ your load balancer
                 │        │              balancer: the CDN edge
                 │        │              that connected to it
                 │        └ added by your CDN: the real client
                 └ sent by the client: anything it likes
```

A credential-stuffing tool puts a random value there on every request, so every attempt gets a fresh bucket.

**Forty keys.** API traffic is limited to 1,000 requests per minute per API key, and keys are self-serve. A Team customer's sync tool creates one key per worker. With forty workers, that's 40,000 per minute on a plan priced for 1,000. The following week the opposite happens: a Business customer shares a single key across twelve integrations, a nightly backfill spends the whole budget, and their live webhook processing fails until morning.

**The exceptions.** Sales promises an Enterprise prospect 5,000 per minute. An engineer adds `if (tenantId === "t_8812")` to the middleware. A year later there are 23 such lines. Three belong to customers who have churned, and two to customers who downgraded but still get Business limits. Nobody can say what a given customer's limit is without reading the code.

The algorithm decides *how much*. All five incidents are about *who*: which identity a request is charged to, and how large that identity's allowance is.

## What It Is

The **limit key** is the attribute of a request that determines whose budget it spends: an IP address, an API key, a user, a tenant, a target phone number, a route. The **budget**, or policy, is the burst and rate attached to that key. Usually it comes from the customer's plan.

A good key has three properties:

1. **Attributable.** It belongs to whoever actually controls the traffic.
2. **Expensive to multiply.** One actor can't cheaply obtain many of them.
3. **Unshared.** Unrelated callers don't end up in the same bucket.

No single identifier has all three. Real systems therefore apply **several limits to each request, each keyed differently**. This is called multi-dimensional or hierarchical rate limiting. Coarse, early keys act as ceilings, and precise, late keys carry the actual policy.

Login-specific layering (per account, per IP, and across the whole endpoint) was covered in Module 4. This article covers the general version.

## Recognizing the Problem

- Complaints about 429s cluster by network: a campus, a corporate office, a mobile carrier, a VPN provider.
- The number of limiter keys grows much faster than your user count.
- Most IPv6 keys in the limiter's store have been seen exactly once.
- The IP your limiter records is private (`10.x`, `172.16–31.x`, `192.168.x`) or belongs to your own infrastructure. That means everyone shares a bucket.
- IPs in rejection logs don't match what your CDN or load balancer logged for the same requests.
- A tenant creates dozens of API keys in a short window, and each key sits just under its limit.
- One integration's traffic starves others belonging to the same customer.
- Tenant IDs appear in limiter code, or sales asks engineering what a customer's limit is.
- A plan change takes an unpredictable amount of time to affect limits.
- An expensive endpoint drives database load while every key is well under its limit.
- Requests carrying invalid credentials are never rate limited.

## How It Works

### The candidates

| Key | Known at | Shared by unrelated callers? | Can one actor cheaply get many? | Good for |
|---|---|---|---|---|
| IPv4 address | Connection | Often (NAT, carrier NAT, VPNs, relays) | Moderately (proxies, botnets) | Anonymous traffic, coarse ceilings |
| IPv6 address | Connection | Rarely | Yes: a `/64` holds 2⁶⁴ | Nothing, on its own |
| IPv6 prefix (`/64`, `/48`) | Connection | Sometimes | Much less | The IPv6 counterpart of an IPv4 address |
| API key | After key lookup | Only if the customer shares it | Yes, if creation is self-serve | Fairness between integrations |
| User | After authentication | No | As cheaply as signing up | Web app traffic, per-person abuse |
| Tenant / organization | After authentication | No | As cheaply as creating an organization | The budget you sell |
| Target (phone, email, account) | Request body | — | — | Protecting the person on the receiving end |
| Route | Routing | — | — | Expensive operations, per-endpoint ceilings |
| Global | Always | Everyone | — | Protecting an endpoint from aggregate load |

Two columns drive most design decisions. **"Known at"** determines where in the request pipeline a limit can run. **"Can one actor cheaply get many"** determines whether a limit needs another limit above it.

### Deriving the client IP

Behind a CDN or load balancer, the socket address is your own infrastructure. The client's address has to come from a header, and headers can be forged.

`X-Forwarded-For` is a list. Each proxy appends the address that connected to it, but the client can send any starting value it likes. The only entries you can trust are the ones **your own infrastructure added**, and those are at the right-hand end. So read it from the right. If you operate N proxies, the Nth entry from the right was written by your outermost proxy, and it's the address that connected to that proxy: the client. In the example, N = 2 (CDN and load balancer), which gives `203.0.113.9`. Everything to its left is unverified.

This couples correctness to your network topology:

- **Count too few hops**, and the "client" is your CDN's edge. A few hundred buckets end up shared by the entire internet.
- **Count too many hops**, and the client chooses its own key.

Both failures are silent. Adding a CDN layer next year changes the correct count.

Two things make this sturdier:

- **Restrict your origin to accept connections only from your CDN.** Otherwise a client can skip the CDN and forge a whole chain.
- **Prefer a single header your outermost proxy sets and overwrites.** Several CDNs provide one. The standardized `Forwarded` header (RFC 7239) has the same trust problem as `X-Forwarded-For`, just with clearer syntax.

**Normalize the address.** Convert IPv4-mapped IPv6 addresses (`::ffff:203.0.113.9`) to IPv4. For native IPv6, key by prefix rather than full address. A household or small network is typically assigned a `/64` or larger, and every address inside it belongs to the same subscriber. A `/64` is the usual starting point. Some providers assign a `/56` or `/48`, so a second, looser limit at `/48` catches rotation across subnets.

### Shared addresses

The reverse problem is many people behind one IPv4 address. Carriers put large numbers of subscribers behind shared public addresses (the `100.64.0.0/10` range in RFC 6598 exists for this). Universities, corporate offices, VPNs, and privacy relays do the same. An IP key can't tell a busy campus from one abusive client.

Useful responses, roughly in order of preference:

- **Switch to a stronger key as soon as one exists.** Once a user signs in, limit by user and relax the IP limit.
- **Treat IP limits as ceilings, not policy.** Set them generously enough that a campus survey passes and a flood doesn't. The principle: **the less a key tells you about who is behind it, the more generous its limit must be.**
- **Combine the IP with the target.** Five submissions per minute *per IP per form* lets a campus answer many different forms while still stopping one address from flooding one form.
- **Challenge instead of rejecting** when a shared-address limit trips. A person on campus can pass a challenge; a script usually can't.

### Keys that can be multiplied

If a caller can create keys freely, a per-key limit isn't a limit on that caller. It's a limit multiplied by however many keys they're willing to create. This applies to self-serve API keys, free accounts, and IPv6 addresses.

The fix is always **a limit at the level above**: per tenant above per key, per prefix above per address, and limits on key and account creation themselves. Stopping mass signups is fraud prevention more than rate limiting, but the principle carries over. Enforce at the level where creating another identity has a real cost.

### Before and after authentication

A key can only be used once it's known, and learning some keys costs work. Looking up an API key is a database or cache read. Verifying a password is deliberately slow. That fixes the order of the pipeline:

```
request
  │
  ├─ 1. per-route ceiling        known immediately · local is fine (see below)
  ├─ 2. per-IP / prefix ceiling  known at connection · generous
  │
  ├─ authenticate ──── fails ──► spend from a strict per-IP failure budget (fail closed)
  │
  ├─ 3. per-key limit            fairness between one customer's integrations
  ├─ 4. per-tenant limit         the budget the plan pays for
  └─ 5. cost-weighted limits     expensive routes spend more (18.1, Module 8)
```

Cheap, coarse checks go first, so a request rejected early never pays for a later check. Two rules keep the pipeline sound:

- **Never key a limit on an unverified credential.** An attacker sending random API keys would get a fresh bucket for each one. Failed authentication spends from the IP's budget. Cache negative key lookups too, so random keys don't turn into database load.
- **The one limit where divide-by-N works well is the per-route ceiling.** 18.2a showed that load balancers distribute *per-client* traffic unevenly. Aggregate traffic for a route is what they do distribute well. A route-wide limit in Redis is also a single hot key that every request touches. Enforce it locally, as each instance's share of the total.

### Hierarchies and overbooking

When a tenant has several API keys, give each key its own limit *below* the tenant limit, and require a request to pass both. The tenant limit is what the customer bought. The per-key limit keeps one integration from consuming all of it.

Per-key limits usually add up to more than the tenant limit on purpose. For example: tenant limit 1,000 per minute, per-key limit 400. Dividing evenly (1,000 / 40 keys = 25 each) would strand capacity in idle keys. **Overbooking** keeps capacity usable, and the tenant limit remains the binding one. The cost is confusion: a request can be rejected while its own key shows headroom, because the tenant as a whole has none. The response has to say which limit was hit (18.3).

The same structure applies inside the web app. A per-user limit under a per-tenant limit means one colleague's browser script can't lock the rest of the team out.

From 18.2a: checking two buckets in two calls can spend a key token and then get rejected by the tenant bucket. Either put both keys on the tenant's Redis Cluster slot and check them in one script, or accept the small leak.

### Target keys

Some limits protect a third party rather than your service:

- SMS codes per destination number.
- Password-reset emails per address.
- Invitations per recipient.

These are keyed by the **target** and apply regardless of who is sending. They exist because an attacker's cheapest weapon against someone is often your product. It's the same reasoning as keying a login limit by the targeted account.

These keys contain personal data: phone numbers, email addresses, IPs. Store them in the limiter as a keyed hash (an HMAC with a secret), not raw and not as a plain hash. A plain hash of a phone number can be reversed by hashing every possible number.

### Budgets as data

Store limits as **configuration with one source of truth**, not as conditions in code:

- **Plans define defaults**: a burst and a rate for each dimension on each plan. Plans can differ in burst, not only in sustained rate.
- **Overrides are records** with a tenant, a limit, an owner, a reason, and an expiry date. The expiry matters most. An override without one becomes a permanent, unpaid entitlement, like the two downgraded customers in the problem.
- **Resolution** is override, then plan, then default. It reads from the cached tenant context (Module 5), so a limit check doesn't cost a database query. The cache TTL is how long a plan change takes to apply. Invalidate on plan-change events if that delay matters.
- **Route costs** are a table. Changing a cost is a breaking change for clients who tuned against the old value.

The 18.2a script receives burst and rate as arguments on every call, so a plan change applies on the very next request. A downgrade clips existing tokens to the new capacity, because refill is capped with `min`. An upgrade doesn't fill the bucket instantly; it starts refilling at the new rate.

Limits you sell appear on a pricing page, in API documentation, and in response headers. All three should read the same configuration that enforcement reads. Otherwise, the first time they diverge, a customer will point to the documented number.

## When It's Appropriate

- **Anonymous public endpoints** (form submission, signup, search) need IP and prefix ceilings, generous enough for a shared network, combined with a target such as the form ID.
- **A public API with self-serve keys** needs per-key limits under a per-tenant limit. Otherwise key creation becomes a way around the plan.
- **Tiered pricing** makes limits part of the product, and they need to live as data that sales, support, and documentation can all see.
- **Anything that sends messages to people** needs per-target limits, in addition to per-sender limits.
- **Shared organization accounts in a web app**, where one member's automation shouldn't lock out colleagues, need per-user limits under per-tenant limits.

## When It's Unnecessary or Overkill

- **An internal single-tenant tool.** A per-user limit on login is all it needs.
- **Five-level hierarchies for twenty customers.** A per-tenant limit plus a local per-route ceiling covers it until someone actually abuses key creation.
- **Per-key limits when each tenant has exactly one key** and can't create more.
- **IPv6 prefix hierarchies with no IPv6 traffic.** Check your logs first, but check them: many mobile networks are majority-IPv6.
- **An override admin UI for your first three exceptions.** A config file with owners and expiry dates is enough. The requirement is that overrides are data, not that they have an interface.
- **Device fingerprinting as a rate-limit key.** It carries real privacy cost and starts an arms race. Leave it to dedicated abuse tooling, if you use it at all.

## Trade-offs

- **Every added dimension has a cost.** Each one adds store operations per request, configuration to maintain, another way a legitimate request can be rejected, and another answer to "which limit did I hit?"
- **IP keys can't be tuned for both failure modes.** A limit loose enough for a campus is loose for a rotator, and one tight enough for a rotator breaks the campus. Layering and challenges reduce the conflict; no single setting removes it.
- **Trusting proxy headers ties the limiter to your network topology.** Infrastructure changes can silently break it in either direction.
- **Late keys mean work before limiting.** Everything before authentication is protected only by the weak keys.
- **Hierarchies overbook, and overbooking confuses people.** A key with headroom gets rejected, and support has to explain why.
- **Configuration as data needs governance.** Overrides need owners, audits, and expiry, or they accumulate like the `if` statements did.
- **Plan resolution is cached.** A limit change takes effect only after the cache TTL, unless you build invalidation.
- **Limiter keys are personal data.** They have to be hashed, and they fall under your retention and deletion policies (Module 34).
- **Attacker-controlled key cardinality is a memory attack** on the limiter's store. Prefix normalization and expiry are part of the defense.

## Alternatives

- **Require identity.** Where friction is acceptable, authenticate before doing anything worth limiting, and the IP problem mostly disappears. A public form can't do this; an API can.
- **Challenges instead of rejections.** On anonymous routes, serve a CAPTCHA or proof-of-work challenge when a limit trips. People on shared networks can pass; scripts pay a cost.
- **Session tokens issued on page load.** Issue a signed, short-lived token when the form renders, rate-limit token issuance by IP, and then limit submissions per token. This turns a weak key into one that has a cost to obtain.
- **Reputation and bot management.** Score requests by network, behavior, and history instead of only counting per key. CDNs and WAFs offer this, and it's the answer to distributed abuse that stays under every per-key limit.
- **Charge instead of limit.** For the budget you sell, usage-based pricing lets customers exceed a soft limit and pay for it (Module 15). Hard limits remain for protection, set well above billed usage.
- **Concurrency limits per tenant.** Where fairness is about shared worker capacity rather than request rate, see the scheduling discussion in Module 10.

## How to Achieve It

**Level 0 — log every candidate key on every request.** Record the socket address, the derived client IP, key ID, user, and tenant. Then check the derived IP: are any values private, from your own ranges, or impossible? Does it match your CDN's logs?
_Signal you're here:_ nobody can say which IP your limiter uses.

**Level 1 — derive the client IP correctly, and add generous per-IP ceilings to anonymous routes.** Count proxy hops explicitly, restrict the origin to your CDN, and normalize IPv6 to `/64`.
_Signal you need it:_ any public endpoint, or any limit keyed by IP.

**Level 2 — add per-tenant limits after authentication, from plan configuration, plus a strict failure budget for authentication.**
_Signal you need it:_ plans that differ in what they allow, or unauthenticated traffic you can't stop.

**Level 3 — add per-key limits under tenants, overrides as data with expiry, and cost-weighted routes.**
_Signal you need it:_ self-serve keys, a noisy integration starving its siblings, or the first `if (tenantId === …)` in a pull request.

**Level 4 — add per-target limits, hashed keys, a second IPv6 prefix level, and one configuration read by enforcement, documentation, and the admin panel.**
_Signal you need it:_ SMS or email abuse, a privacy review, or a customer quoting documentation that doesn't match enforcement.

**Level 5 — add challenges, reputation-adjusted limits, and signed session tokens for anonymous traffic.**
_Signal you need it:_ abuse spread across more addresses than any per-IP limit can catch.

## Implementation

**TypeScript with Express**, reusing `take()` from 18.2a. The algorithm and store code don't change. Everything below decides what to pass to them.

**Deriving the IP key.**

```ts
import { isIPv4, isIPv6 } from "node:net";

// Express derives req.ip from X-Forwarded-For, reading from the right and trusting only
// the number of hops you declare. Count your proxies: CDN → load balancer → app = 2.
// Never `true`, which trusts the whole chain and hands the client its own key.
app.set("trust proxy", 2);

export function ipKey(req: Request): string {
  let ip = req.ip ?? "unknown";
  if (ip.startsWith("::ffff:")) ip = ip.slice(7);           // IPv4-mapped IPv6
  if (isIPv4(ip)) return `v4:${ip}`;
  if (isIPv6(ip)) return `v6:${ipv6Prefix(ip, 64)}`;        // one subscriber, not one address
  return "ip:unknown";
}

function ipv6Prefix(ip: string, len: 48 | 64): string {
  const [head, tail] = ip.split("%")[0].split("::");         // drop zone id, split at "::"
  const h = head ? head.split(":") : [];
  const t = tail ? tail.split(":") : [];
  const groups = tail === undefined ? h : [...h, ...Array(8 - h.length - t.length).fill("0"), ...t];
  return groups.slice(0, len / 16).map(g => parseInt(g, 16).toString(16)).join(":") + `::/${len}`;
}
```

> **Aside — `2` is a fact about your network, not about this code.** When someone adds a WAF in front of the CDN, the correct value becomes 3. If this line isn't updated, the limiter keys every request by a CDN edge address, and nothing will error. Keep the hop count in infrastructure configuration next to the topology it describes, and alert when the derived IP falls inside your own or your CDN's published ranges.

**Resolving budgets from plans and overrides.**

```ts
type Limit = { burst: number; ratePerSec: number };

const PLANS: Record<PlanId, { tenant: Limit; perKey: Limit }> = {
  free:     { tenant: { burst: 20,   ratePerSec: 1   }, perKey: { burst: 20,  ratePerSec: 1  } },
  team:     { tenant: { burst: 200,  ratePerSec: 20  }, perKey: { burst: 100, ratePerSec: 8  } },
  business: { tenant: { burst: 1000, ratePerSec: 100 }, perKey: { burst: 400, ratePerSec: 40 } },
};

// Rows in a table, loaded with the tenant context and cached briefly. Never branches in code.
interface Override { limit: Limit; owner: string; reason: string; expiresAt: Date }

const ROUTE_COST: Record<string, number> = { "POST /exports": 50, "GET /responses": 5 };

export function budgetsFor(tenant: TenantContext) {
  const plan = PLANS[tenant.plan];
  const o = tenant.override;
  return {
    tenant: o && o.expiresAt > new Date() ? o.limit : plan.tenant,
    perKey: plan.perKey,        // Team: 8/s per key under 20/s per tenant — overbooked on purpose
  };
}
```

**Composing the checks, cheapest first.**

```ts
interface Check { dim: string; id: string; limit: Limit; cost: number; onStoreFailure: FailurePolicy }

async function enforce(checks: Check[], res: Response): Promise<boolean> {
  for (const c of checks) {
    const d = await take(c.id, { name: c.dim, capacity: c.limit.burst,
                                 ratePerSec: c.limit.ratePerSec, onStoreFailure: c.onStoreFailure }, c.cost);
    if (!d.allowed) {
      // record which dimension rejected the request; 18.3 turns this into the response
      res.locals.rateLimited = { dim: c.dim, limit: c.limit, retryAfterMs: d.retryAfterMs, source: d.source };
      return false;
    }
  }
  return true;
}

// Before authentication: coarse, generous, keyed by what's known at the connection.
app.use(async (req, res, next) => {
  if (!routeCeiling.take(routeId(req), performance.now()).allowed)   // local, per instance
    return rejectRateLimited(res, "route");
  const ok = await enforce([
    { dim: "ip", id: hmac(ipKey(req)), limit: { burst: 300, ratePerSec: 50 }, cost: 1, onStoreFailure: "local" },
  ], res);
  ok ? next() : rejectRateLimited(res);
});

// Failed credentials spend from `authfail:<ip>` inside authenticate() and fail closed.
// Nothing below this line is keyed on a credential that hasn't been verified.
app.use(authenticate);

// After authentication: the budget the customer bought.
app.use(async (req, res, next) => {
  const b = budgetsFor(req.tenant);
  const cost = ROUTE_COST[routeId(req)] ?? 1;
  const ok = await enforce([
    { dim: "key",    id: req.apiKey.id, limit: b.perKey, cost, onStoreFailure: "local" },
    { dim: "tenant", id: req.tenant.id, limit: b.tenant, cost, onStoreFailure: "local" },
  ], res);
  ok ? next() : rejectRateLimited(res);
});
```

> **Aside — two costs hiding in that loop.** First, each check is a separate round trip, so three dimensions triple the limiter's share of latency. When that matters, send one script call that checks all of a tenant's keys on a single hash-tagged slot (18.2a). Second, the per-key check runs first and spends its tokens even when the tenant check then rejects. Over time that drains keys belonging to a tenant that's already at its cap. Order checks so the one most likely to reject runs first, or refund the tokens on rejection.

`routeId(req)` has to return the route *template* (`POST /forms/:id/submit`), not the raw path. Keying by raw path gives every form ID its own ceiling and quietly removes the limit.

## Further Reading

- **Adam Pritchard, "The perils of the 'real' client IP."** The most thorough treatment of `X-Forwarded-For` parsing, including the rightmost-trusted-hop rule and the ways each alternative breaks.
- **MDN, "X-Forwarded-For"** (the security and parsing sections), and **Express's guide "Express behind proxies."** The exact semantics of `trust proxy` values.
- **RFC 7239, "Forwarded HTTP Extension."** The standardized header, and its explicit warnings about trusting it.
- **RFC 6598** (shared address space for carrier-grade NAT) and **RFC 6177** (IPv6 address assignment to end sites). Why many users share one IPv4 address, and why the right IPv6 prefix length is a judgment call.
- **GitHub REST API documentation, "Rate limits for the REST API."** A clear production example of layered keys: small per-IP limits for anonymous callers, larger per-user and per-app limits once authenticated, plus separate secondary limits.
- **Cloudflare documentation on rate limiting rule "characteristics."** Key composition (IP, header, cookie, path, and combinations) as configuration, useful for seeing the full design space.
- **AWS Builders' Library, "Fairness in multi-tenant systems."** Worth rereading after 18.1 for the per-tenant sections: quotas per customer, and fairness beneath the tenant level.
- **Envoy documentation, rate limit "descriptors."** The most general model of hierarchical, multi-dimensional keys: an ordered list of key-value pairs, each level matched to its own budget.
- **OWASP Credential Stuffing Prevention Cheat Sheet.** The authentication-specific end of this article, and why per-IP limits alone don't stop distributed attacks.

No language sibling is planned for this one. Nothing here depends on the language: the decisions are about identity, topology, and configuration, and they would read the same in any stack.

---

The habit to carry out of this: whenever an identifier is used for enforcement — a rate limit, a quota, a ban, a "one per customer" rule — ask three questions. Who controls its value? How many of them can one actor obtain? How many unrelated people share one? An identifier that fails any of those isn't wrong to use, but it needs a generous limit and another limit above it.
