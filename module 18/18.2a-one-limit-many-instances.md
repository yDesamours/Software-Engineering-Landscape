# One Limit, Many Instances

_Module 18.2a — API Rate Limiting & Throttling_

## The Problem

An address-autocomplete API. Customers embed it in signup and checkout forms, and every keystroke is a request. The Pro plan promises 50 requests/second per key, with bursts to 100. Behind it, every request calls a map-data provider that bills per call and caps your whole account at 2,000 requests/second. The API runs as 3 pods on a normal day, and the autoscaler takes it to 12 at peak.

The token bucket from 18.1 ships inside each pod. It's correct, and it's tested. Four incidents follow anyway.

**The limit multiplies.** The load balancer spreads each key's traffic across pods, and every pod has its own bucket for that key.

```
                          load balancer
               ┌───────────────┼───────────────┐
               ▼               ▼               ▼
            pod A           pod B           pod C
         [K: 50/s]        [K: 50/s]       [K: 50/s]

   key K admitted:   50/s  +   50/s   +   50/s   =  150/s
   at 12 pods:                                      600/s
```

A customer scraping the address database through a Pro key discovers this before you do. On the busiest shopping day of the year, the autoscaler reaches 12 pods and that key is admitted at 600 requests/second. Your aggregate traffic crosses the provider's 2,000 cap. The provider starts returning 429s to your whole account, and autocomplete breaks for every customer at once.

**The obvious fix punishes the wrong people.** You divide each limit by the replica count: 50 / 12 ≈ 4.2 per pod. On normal days, with 3 pods running, every Pro customer now gets about 12.5/s, a quarter of what they bought. So you read the live replica count instead. That helps until the largest customer complains. They call from a backend service holding one keep-alive connection, and the load balancer balances connections, not requests.

```
12 pods, 4.2 req/s per pod per key

  customer's one keep-alive connection ─────────────► pod F only
  pod F sees 30 req/s from K, admits 4.2    →  86% rejected
  K is using 60% of the 50 req/s it pays for
```

**Shared state, shared race.** You move the bucket into Redis. Each pod reads the bucket, computes the refill, decides, and writes the new value back. The scraper opens 200 concurrent connections:

```
pod A:  HMGET → tokens = 1 ──────── decide ── HSET tokens = 0 ── admit
pod B:     HMGET → tokens = 1 ── decide ─────── HSET tokens = 0 ─────── admit
pod C:        HMGET → tokens = 1 ─ decide ── HSET tokens = 0 ── admit
                                       three admitted, one token spent
```

Its bursts of 100 come through as 300 to 400. Meanwhile each pod computes elapsed time from its own clock. One node has drifted two seconds ahead, so every bucket it touches receives two extra seconds of refill.

**The limiter becomes the outage.** The Redis primary fails over, and connections error for twelve seconds. The middleware throws, and every request in those twelve seconds returns 500, including requests from customers nowhere near their limits. A component that exists to protect availability has just removed it.

None of these incidents is about the algorithm. Each one comes from a single assumption that stopped being true: that one process sees all of a key's traffic.

## What It Is

This is **distributed rate limiting**: enforcing one budget per key when many processes each see part of that key's traffic. Getting it right takes four things that a single process gave you for free.

- **Coordinated state.** The budget is either shared or divided in a way that holds up under uneven traffic.
- **An atomic decision.** Reading the budget, deciding, and spending from it happen as one indivisible step.
- **One clock.** Refill is computed from a single time source, not one clock per machine.
- **A failure policy.** A defined answer to "the coordinator is unavailable, now what?"

Two terms come up throughout. A **global** limit is enforced against fleet-wide state. A **local** limit is enforced inside one process. Most mature setups use both.

One neighbor is worth separating early: **you don't need a distributed lock.** Taking a lock (Redlock or similar) around read-compute-write adds two round trips and a lease-expiry failure mode, and it fixes the race only as long as the lock actually holds. What the problem needs is an operation the store runs atomically. That's cheaper, and it has no lease to expire.

The outbound version of this problem, a fleet sharing one budget toward a third-party API, was Module 17. It uses the same mechanism with the direction reversed.

## Recognizing the Problem

- Customers exceed their limit by a factor close to your instance count.
- The effective limit changes when the autoscaler scales up or down.
- A rejected request succeeds when retried immediately, because the retry landed on a different pod.
- Clients using keep-alive connections, HTTP/2, or gRPC are rejected well below their limit, while clients opening fresh connections aren't.
- Admitted traffic overshoots the limit during concurrent bursts, even with a shared store.
- API p99 latency across every endpoint rises and falls with the latency of the limiter's store.
- A failover in the limiter's store shows up either as an API outage or as a window during which limits vanish.
- Request volume spikes right after each deploy, because in-memory buckets restart full.
- The same key receives different decisions in different regions.

## How It Works

### Why local state fails in two directions

With N instances and an unmodified local limit L, a key can be admitted at anything up to N × L. Dividing by N (L / N per instance) is correct only if the load balancer delivers each key's traffic evenly across instances. Load balancers don't promise that, for several reasons:

- Connection-level balancing pins a keep-alive connection to one instance.
- Least-connections and latency-aware algorithms deliberately send traffic unevenly.
- Autoscaling changes N faster than configuration propagates.
- A newly started pod receives traffic before its view of N is current.

So local limits err on both sides. They are too loose for clients that spread out and too strict for clients that don't.

Local-only limiting is still a legitimate choice when **the limit is a safety net**: a ceiling ten times above normal usage, meant to stop runaway scripts. Admitting 3× a ceiling is still a ceiling. The bill only arrives when the limit is what you sell, what protects a paid dependency, or what stops brute force.

### A central store, with atomic updates

Keep the state in one place, usually Redis because it's fast, already in the stack, and has atomic primitives. Then make each decision indivisible. There are three ways to get atomicity.

**A single atomic command.** `INCR` is atomic, which makes a fixed window almost free: increment `rl:K:<window>`, compare the result with the limit, and set an expiry on the key.

> **Aside — the fixed-window key that never expires.** `INCR` followed by a separate `EXPIRE` has a gap. If the process dies between the two commands, the key has no TTL. The counter sits at the limit forever, and that customer is locked out until someone deletes the key by hand. Set the expiry inside the same atomic unit, either in a script or with `SET key 0 EX 60 NX` before the `INCR`.

**A server-side script.** Redis runs a Lua script (`EVAL`/`EVALSHA`, or Redis Functions on 7+) without interleaving other commands. Read, refill, decide, and write all happen in one round trip, with no race. This is how token buckets, sliding counters, and GCRA are usually built on Redis.

> **Aside — the sliding log that locks retrying clients out forever.** A common Redis sliding-log recipe in a `MULTI` block adds the current timestamp to the sorted set *before* counting it. Rejected requests therefore still occupy slots in the window. A client that retries every second while limited keeps its own window full indefinitely. Count first, and add the timestamp only when admitting, which requires a script.

**Optimistic concurrency.** `WATCH` the key, read, compute, and commit with `MULTI`/`EXEC`, retrying if the key changed in the meantime. This is correct, but under contention it retries most on the hottest keys, which are exactly the ones you're limiting. It's a reasonable choice for stores without scripting, and a poor choice for a busy Redis.

A few details decide whether the scripted approach holds up in production:

- **Read time inside the store.** Calling `TIME` inside the script gives the whole fleet one clock. It's safe to mix with writes on Redis 5 and later, which replicate a script's effects rather than re-running the script on replicas. Redis 7 only works that way. Passing each pod's `Date.now()` instead brings back clock skew as a correctness bug.
- **Clamp elapsed time at zero.** After a failover, the new primary's clock may be slightly behind the old one. A negative elapsed time would drain buckets.
- **Redis Cluster places each key on one slot.** Every key a script touches must hash to the same slot. When one request checks a per-API-key bucket and a per-tenant bucket together, put both keys on the tenant's slot with a hash tag (`{t:42}:key:abc`, `{t:42}:tenant`). The trade-off is that each tenant's limiter state lives on one shard.
- **Checking several limits is itself a consistency problem.** If the per-key check and the per-tenant check are separate calls, a request can spend a per-key token and then be rejected by the tenant limit. That's usually acceptable. When it isn't, run both checks in one script, or refund the spent token.
- **Replication is asynchronous.** After a failover, the promoted replica may be missing the last few hundred milliseconds of decrements, so for a moment some keys are admitted more generously than they should be. That's tolerable for rate limiting. Losing a few counter updates doesn't lose money the way a lost ledger write would, which is why a fast, eventually replicated store is the right tool here and a serializable database transaction per request isn't.
- **No persistence required.** Losing limiter state gives everyone a fresh bucket. That's usually mild, unless you rely on the limiter for long windows such as "3 OTP sends per hour."

### Leasing and periodic sync: trading precision for round trips

A script call on every request costs a network hop, typically well under a millisecond within one availability zone. Across a fleet it also costs Redis capacity: limiter operations equal the request rate multiplied by the number of limits checked per request. When that cost becomes significant, there are two ways to reduce it.

**Token leasing.** An instance takes a batch of K tokens from the central bucket in one call, spends them locally, and asks for more when they run out. You make one round trip per K requests. The overshoot is bounded by the tokens outstanding in leases, at most N × K. Pods that die take their unspent tokens with them, so leases should be small and short-lived.

**Local counting with periodic sync.** Each instance counts locally and pushes its counts to the shared store every 100ms or so, reading back the fleet total. The overshoot is bounded by what the fleet can admit in one sync interval. Several API gateways offer this as a configuration option alongside strict per-request coordination.

```
precision ◄──────────────────────────────────────────────────► latency, store load
 script per request     leased tokens          local + sync         local ÷ N
 +1 hop per request     overshoot ≤ N × K      ≤ one interval       no coordination
```

A related layering puts a **local limit in front of the global one**: a generous per-instance ceiling that rejects obvious floods before they reach the shared store. Envoy documents exactly this, using its local rate-limit filter to protect its global rate-limit service.

### Routing each key to an owner

Another option is to make local state authoritative by always routing a key to the same instance, using consistent hashing at the load balancer. This avoids a shared store entirely. It breaks during rebalancing, loses all state when an instance restarts, and puts a hot key's entire load on one instance. Some systems use it internally. For an HTTP API behind ordinary load balancers, it's rarely worth the fragility.

### A dedicated rate-limit service

At some scale, rate limiting becomes a service of its own. The limiter is a gRPC service (Envoy's reference `ratelimit` service, originally from Lyft, is the well-known example) with its own store and its own team, and gateways call it. This doesn't remove any problem described above. It moves them into one place where specialists handle them.

Managed gateways make the same trade-off on your behalf and are candid about it. AWS API Gateway, for example, documents usage-plan throttling and quotas as best-effort rather than hard limits. **Distributed limits are approximate.** The design choice is how approximate, and whether customers are told.

### What happens when the store is unavailable

Every request now depends on the limiter's store, so its failure behavior has to be designed. Three settings matter.

**A tight timeout.** Give the limiter call a budget in tens of milliseconds. A limiter that is slow but still up does more damage than one that is down, because it adds its latency to every request.

**A circuit breaker around the store.** After repeated failures, skip the store entirely for a few seconds. Otherwise every request pays the full timeout before falling back.

**A per-route failure policy.** Choose one of three behaviors for each route:

- **Fail open** by admitting everything. This fits general API traffic, where the limiter protects fairness and a few minutes without it is survivable. The cost is that protection disappears precisely during an incident.
- **Fail closed** by rejecting everything. This fits routes where an unlimited window is a security or financial problem: OTP verification, SMS sending, password reset. Respond with `503`, not `429`, because the caller did nothing wrong (18.3).
- **Fall back to a local limit**, using the divide-by-N limiter. Its known inaccuracy is acceptable during degraded operation, and it keeps a ceiling in place while the store recovers. This is usually the best default.

### Multiple regions

A single global limit across regions means a cross-region round trip, often tens of milliseconds or more, on every request. That's rarely acceptable. The workable options are:

- Split each budget between regions by traffic share, and rebalance periodically.
- Enforce per-region limits and state that in the contract.
- Replicate counters asynchronously between regions (some Redis offerings provide CRDT-based counters for this) and accept a larger overshoot.

For most APIs, "your limit applies per region" is simply the honest contract.

## When It's Appropriate

- **More than one instance, and the limit protects something with a hard edge.** Examples: a per-call bill, a provider's account-wide cap, a contractual plan limit, or a brute-force defense where 12× overshoot turns 5 attempts into 60.
- **Autoscaled fleets.** When N ranges from 3 to 40 over a day, local limits don't enforce any single number.
- **Limits you sell.** Customers compare the limits you enforce with the limits on their invoice. Being too loose loses revenue, and being too strict creates support tickets.
- **Client populations using keep-alive connections, HTTP/2, or gRPC.** Traffic skew per instance is the norm there, so divide-by-N rejects your best-integrated customers.

## When It's Unnecessary or Overkill

- **Safety-net ceilings.** A runaway-script limit set far above normal use tolerates N× overshoot. Keep it local.
- **Small fixed fleets with generous limits.** Two instances and a limit nobody approaches don't justify a new dependency on the hot path.
- **A gateway or CDN that already enforces the limit globally.** Doing it again in the application adds a second place to configure it and a second thing that can disagree.
- **Leasing, sync, or routing ownership before per-request scripts have caused a problem.** A Redis script call per request is fast enough for most systems.
- **Exact global enforcement across regions.** If nobody would notice per-region limits, don't pay cross-region latency to avoid them.

## Trade-offs

- **A new hop on the hot path.** Every request pays the limiter's latency, and your API's p99 is now bounded below by the store's p99.
- **A new critical dependency.** You have to pick which failure you prefer. Failing open means protection disappears exactly when things go wrong. Failing closed means a limiter outage becomes an API outage.
- **Store capacity grows with traffic.** Limiter operations scale with request rate multiplied by limits checked per request. A single very hot key can overload one shard.
- **The result is approximate anyway.** Replication lag, failovers, leases, and sync intervals all leak a little. Describe distributed limits as approximate, internally and to customers.
- **Cluster slot rules shape your key design.** Checking several limits atomically forces them onto one shard, which pushes against spreading load.
- **Rolling deploys can run two script versions at once.** If a new script changes the state format (field names, units), old and new pods interpret the same key differently. Put a version in the key prefix and let the old keys expire.
- **Testing needs a real store.** Atomicity and TTL behavior can't be faked convincingly with a mock. Test against a Redis container (Module 21).

## Alternatives

- **Local limits divided by N.** No coordination. Acceptable for safety nets. Wrong for anything that sees skewed traffic.
- **Enforce at the single choke point.** An edge, CDN, or API gateway already sees all traffic, and many provide global rate limiting as configuration. You give up per-request context your application has, such as plan, tenant, or endpoint cost, unless the gateway can look it up.
- **Counters in your relational database.** `UPDATE … SET count = count + 1 … RETURNING count` is atomic and needs no new infrastructure. It's fine for login attempts at tens per second and wrong for general API traffic at thousands.
- **Detect after the fact.** Count from logs or an event stream and block keys asynchronously. Minutes of lag make this detection rather than prevention, but it catches slow, distributed abuse that per-request limits miss.
- **A Redis module command.** redis-cell exposes GCRA as one atomic command, with no script to maintain, if your Redis deployment allows loading modules. Many managed services don't.

## How to Achieve It

**Level 0 — measure your overshoot.** For your top keys, compare the admitted rate with the configured limit, and find out how your load balancer actually distributes requests (per connection or per request).
_Signal you're here:_ you know the configured limits but not the enforced ones.

**Level 1 — local limits, deliberately.** Keep safety-net ceilings in memory. If you divide by N, read N live, and accept that skewed clients will suffer.
_Signal you need it:_ a second instance, and limits that only need to be approximately right.

**Level 2 — a Redis script per request, with a tight timeout and fail-open.** Run it in shadow mode alongside the local limiter first, and compare decisions for a week.
_Signal you need it:_ overshoot that costs money or security, or keep-alive customers rejected below their plan.

**Level 3 — per-route failure policy.** Add a local fallback limiter, fail-closed behavior for sensitive routes, a circuit breaker around the store, and dashboards for limiter latency, errors, and fallback rate.
_Signal you need it:_ your first store failover. Ideally this level lands before it.

**Level 4 — reduce round trips.** Put a local limit in front of the global one, lease tokens for hot keys, and design hash tags for Redis Cluster.
_Signal you need it:_ limiter traffic dominating store CPU, or one tenant's keys overloading a shard.

**Level 5 — a dedicated service, or per-region budgets.**
_Signal you need it:_ several teams building their own limiters, or regions that must share one budget.

## Implementation

**TypeScript with Redis, via ioredis.** The decision logic runs inside Redis as a Lua script. It's embedded in the TypeScript module as a string, the way a SQL statement would be, because atomicity is the point and only the store can provide it.

First, the version that looks correct:

```ts
// ❌ Correct in one process, wrong in a fleet
const s = await redis.hmget(key, "tokens", "ts");                 // pods A and B both read 1 token
const tokens = refill(s, Date.now());                             // each using its own clock
if (tokens < 1) return reject();
await redis.hset(key, "tokens", tokens - 1, "ts", Date.now());    // both write 0, both admit
```

**The token bucket from 18.1, inside the store.** The logic is the same as the in-memory version. What's new is that the store runs it as one step and supplies the clock.

```ts
const TOKEN_BUCKET_LUA = `
local capacity = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])            -- tokens per second
local cost     = tonumber(ARGV[3])

local t   = redis.call('TIME')                -- one clock for the whole fleet
local now = tonumber(t[1]) + tonumber(t[2]) / 1000000

local s      = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(s[1]) or capacity
local ts     = tonumber(s[2]) or now

-- clamp: a promoted replica's clock may be slightly behind the old primary's
tokens = math.min(capacity, tokens + math.max(0, now - ts) * rate)

local allowed, retry = 0, 0
if tokens >= cost then
  tokens, allowed = tokens - cost, 1
else
  retry = (cost - tokens) / rate
end

redis.call('HSET', KEYS[1], 'tokens', tostring(tokens), 'ts', tostring(now))
-- a full bucket is the default state, so let idle keys expire
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000) + 1000)

-- Lua numbers are truncated to integers on the way out; send fractions as strings
return { allowed, tostring(tokens), tostring(retry) }
`;
```

> **Aside — the expiry is load-bearing.** Without it, every key that ever made a request stays in Redis permanently. That's the memory leak from 18.1's in-memory `Map`, now shared by the whole fleet. Expiring once the bucket would be full again is lossless, because a missing key and a full bucket mean the same thing.

**Calling it, with a failure policy per route.**

```ts
import Redis from "ioredis";

const redis = new Redis(process.env.REDIS_URL!, {
  commandTimeout: 25,          // a slow limiter must not become a slow API
  enableOfflineQueue: false,   // while disconnected, fail now instead of queueing
});
redis.defineCommand("tokenBucket", { numberOfKeys: 1, lua: TOKEN_BUCKET_LUA });

type FailurePolicy = "open" | "closed" | "local";
interface Policy { name: string; capacity: number; ratePerSec: number; onStoreFailure: FailurePolicy }

export const POLICIES = {
  api:     { name: "api", capacity: 100, ratePerSec: 50,     onStoreFailure: "local"  },
  otpSend: { name: "otp", capacity: 3,   ratePerSec: 1/1200, onStoreFailure: "closed" },
} satisfies Record<string, Policy>;

type Outcome = Decision & { source: "global" | "local" | "unavailable" };

export async function take(key: string, p: Policy, cost = 1): Promise<Outcome> {
  if (!storeBreaker.isOpen()) {
    try {
      // "v2" versions the state format, so a rolling deploy never mixes two script generations
      const [ok, , retry] = await (redis as any).tokenBucket(
        `rl:v2:${p.name}:${key}`, p.capacity, p.ratePerSec, cost);
      storeBreaker.recordSuccess();
      return { allowed: ok === 1, retryAfterMs: Number(retry) * 1000, source: "global" };
    } catch {
      storeBreaker.recordFailure();   // after a few failures, skip Redis for a few seconds
    }
  }

  metrics.increment("ratelimit.store_unavailable", { policy: p.name });
  switch (p.onStoreFailure) {
    case "open":
      return { allowed: true, retryAfterMs: 0, source: "unavailable" };
    case "closed":
      // respond 503, not 429: the caller did nothing wrong (18.3)
      return { allowed: false, retryAfterMs: 5000, source: "unavailable" };
    case "local":
      // 18.1's in-memory bucket, sized at capacity / expected replicas.
      // Knowingly the divide-by-N limiter: inaccurate, but a ceiling while the store recovers.
      return { ...localFallback(p).take(key, performance.now(), cost), source: "local" };
  }
}
```

> **Aside — watch the fallback rate, not just the errors.** A limiter that has quietly served from `local` for three days has been enforcing the wrong limits for three days, and the API's own error rate won't show it. The `source` field exists so dashboards can alert on this.

The one thing this code still takes as given is `key`: whose budget a request spends, and how large that budget is. That's 18.2b.

## Further Reading

- **Redis documentation: "Scripting with Lua" and "Redis Functions."** Atomicity guarantees, `EVALSHA` and script caching, and the section on script replication that explains why `TIME` is safe on modern versions.
- **Redis Cluster specification, "Hash tags."** How to place several keys on one slot, and what that costs.
- **Envoy documentation: "Global rate limiting" and the local rate limit filter**, plus the **`envoyproxy/ratelimit`** repository. A dedicated rate-limit service, with local limits layered in front of it.
- **AWS API Gateway documentation on usage plans and throttling.** A production system stating plainly that its distributed limits are best-effort.
- **`rate-limiter-flexible` documentation** (Node.js). Redis- and cluster-backed limiters, including an "insurance" limiter option that serves the fallback role in the code above.
- **Martin Kleppmann, "How to do distributed locking."** Why a lock is the wrong tool when you can ask the store for an atomic operation instead.
- **_Designing Data-Intensive Applications_, Martin Kleppmann, ch. 5 and ch. 8.** Replication lag and unreliable clocks, the two properties that make every distributed limiter approximate.

A Java sibling would add something this article doesn't show. Bucket4j's distributed mode offers compare-and-swap and lock-based backends side by side, across Redis, JCache-style grids, and relational databases. That makes the optimistic-concurrency approach, which this article mentions in one paragraph, a concrete choice with visible costs, and shows how the same bucket behaves on stores with very different consistency models. Not yet written.

The habit to carry out of this: whenever you see state held in a service's memory, such as a counter, a cache, a map, or a "last seen" timestamp, ask what that state means when there are twelve copies of the process and the load balancer decides which copy each request reaches. Rate limiters are just where that question costs money fastest.
