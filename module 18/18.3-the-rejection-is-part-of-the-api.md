# The Rejection Is Part of the API

_Module 18.3 — API Rate Limiting & Throttling_

## The Problem

A transactional-email API. Customers' backends call `POST /messages` to send receipts, password resets, and alerts. By now the limiting is in good shape: per-key token buckets under per-tenant limits, enforced consistently across the fleet (18.1–18.2b). Each over-limit request gets a `429`, and nothing else.

The incidents that follow all happen *after* a request is rejected.

**The storm.** A large customer's traffic briefly exceeds its limit. Their HTTP client retries any failure immediately, up to three times. Their job framework also retries failed jobs, up to five times. Neither layer knows about the other:

```
1 logical send
 └─ job attempts       × 5
     └─ SDK attempts   × 4   (1 + 3 immediate retries)
                       ────
                        up to 20 requests within a few seconds, most rejected
```

A spike of 400 over-limit sends per second becomes up to 8,000 requests per second, nearly all of them rejected. Each rejection still pays for TLS, authentication, a limiter round trip, and a log line. The fleet is now mostly busy telling one customer no.

**The synchronized return.** The fix is to tell clients when to come back. You add `X-RateLimit-Reset`, a Unix timestamp for when the window resets. Customers' SDKs do exactly what the header says:

```
X-RateLimit-Reset: 1789567260

rejected at    :12  :19  :25  :31  :40  :47  :55        spread across the minute
come back at   ───────────────────────────────────► :00  every one of them, in the same second
```

The rejections were spread out, and the header gathered them into a single herd (the same `:00` herd from 18.1, recreated by your own response). A second problem appears alongside it. One customer's server clock is 40 seconds fast. Its computed wait comes out negative, so it retries in a tight loop.

**The wrong code.** During a limiter-store failover, the SMS-verification route fails closed (18.2a) and returns `429`. Customers' on-call engineers spend the night searching their own code for a traffic spike that never happened. One SDK treats `429` as "slow down for an hour" and does. An older endpoint still returns `403` for rate limits. One integration platform reads `403` as revoked credentials, disables the customer's connection, and emails their admin.

**The mystery.** A customer opens a ticket: *"We got 429s but our dashboard shows we're at 40% of our limit."* Their dashboard shows the per-key limit. The request was rejected by the per-tenant limit, because a sibling integration had spent the tenant's budget (the overbooking described in 18.2b). The response said "Rate limit exceeded" and nothing about which limit. The ticket takes three days to resolve.

A rejection is still a response, and clients write code against it. When the response doesn't say what happened and what to do next, clients guess. Their guesses tend to be the same guess, made at the same moment, by thousands of clients at once.

## What It Is

This is the **rate-limit contract**: everything a client receives, and everything it's expected to do, when a limit applies.

On the server side, it has four parts:

- **A status code** that says whose problem this is.
- **`Retry-After`**, which says when to try again.
- **Informational headers** that describe the limits before the client hits them.
- **A body** that names the limit that was hit and says what to do about it.

On the client side, it's the retry behavior you document and ship in your SDKs: honor the server's hint, back off with jitter, and retry at only one layer.

The standards involved:

- `429 Too Many Requests` (RFC 6585).
- `Retry-After` (RFC 9110).
- Problem-details bodies (RFC 9457).
- A family of rate-limit headers. Today these are the de facto `X-RateLimit-*` headers and an IETF draft that defines `RateLimit` and `RateLimit-Policy`. As of revision 11 (May 2026), that draft is still an Internet-Draft, not an RFC.

One distinction matters more than the rest. **`429` means *you* sent too much. `503` means *we* can't serve anyone right now.** Clients, dashboards, and on-call engineers respond to those two answers differently, so the code has to be the correct one.

## Recognizing the Problem

- Your `429` count is several times the number of distinct requests that were actually limited. This is retry amplification.
- Rejected traffic from many keys spikes at the same second, often `:00`.
- Some clients retry faster than your `Retry-After` allows, or you don't send `Retry-After` at all.
- Tickets that read "we're under our limit" arrive with no way to tell which limit was hit.
- Customers' SDKs hardcode their own backoff schedules, because you never told them one.
- Your `429`s include infrastructure failures, or your `503`s include per-customer limits.
- The rejection path runs database queries, renders templates, or writes a full log line per request.
- Customers ask what their limits are, or scrape your documentation to find out.
- Integrations disable themselves after being rate limited, because the status code looked like an authorization failure.
- Rate-limit headers report one limit while enforcement applies a different one.
- A CDN or proxy cache sits in front of an endpoint that can return `429`.

## How It Works

### Choosing the status code

Pick the code by asking two questions: who caused this, and will retrying help?

| Situation | Status | `Retry-After` | Will retrying help? |
|---|---|---|---|
| Per-key or per-tenant rate exceeded | `429` | Yes, from the limiter | Yes, after waiting |
| Period quota exhausted (monthly cap) | `429`, with a distinct problem type | Time until reset, or omitted | Not until reset or upgrade |
| Abusive pattern detected | `429` (abnormal usage) | Often omitted | Not by waiting alone |
| Access revoked for abuse | `403` | No | No, it's a permission change |
| Load shedding, or reduced capacity | `503` | Yes, short and jittered | Yes |
| Limiter store down and the route fails closed | `503` | Yes | Yes |
| A provider *you* call is rate-limiting you | `503` | Yes | Yes |

The last row is a common bug. Passing a provider's `429` straight through tells your customer that *they* exceeded a limit they've never heard of. Translate it into a `503`, and carry the provider's retry hint across (Module 17).

Avoid three other codes for rate limiting:

- **`403`** tells clients their permissions changed, and some will disable themselves. Some large APIs have historically returned `403` for exceeded limits and documented that clients should handle it. That's a compatibility burden to support, not a pattern to copy.
- **`400`** tells clients never to retry.
- **`402`** is reserved by the HTTP specification. It's tempting for exhausted paid quotas, but clients don't agree on what it means.

### `Retry-After`

`Retry-After` takes one of two forms: **delay-seconds** (`Retry-After: 12`) or an **HTTP-date**. Prefer delay-seconds. A date only works if the client's clock agrees with yours, and the negative-wait client in the problem shows what happens when it doesn't.

A few rules make the hint trustworthy:

- **Round up, never down.** The header only carries whole seconds. A token bucket that could admit the next request in 20ms still has to say `1`. That's the right trade-off, because a hint shorter than the real wait guarantees another rejection. The same applies to 18.1's sliding-counter hint, which is a lower bound; add a margin to it.
- **Add jitter on the server.** Spread the value so that clients rejected in the same second don't all return in the same second. Adding up to a quarter of the base delay is usually enough. The IETF draft recommends jitter for exactly this reason.
- **Send it on `503` too.** It's the most useful thing a load-shedding response can include.

### Advertising limits before they're hit

A `429` tells the client it has already gone too far. Informational headers on *successful* responses let a well-built client slow down before that happens.

**The de facto headers** are `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset`, with many variations. They're widely used and inconsistent: across APIs, `Reset` might be seconds remaining, milliseconds remaining, a Unix timestamp, or a date string. Clients have to be written separately for each API.

**The IETF draft** (`draft-ietf-httpapi-ratelimit-headers`) replaces them with two structured fields. Both are lists, so one response can describe several policies.

```
RateLimit-Policy: "key";q=100;w=10, "tenant";q=1000;w=60
RateLimit:        "key";r=37;t=6, "tenant";r=12;t=41
```

- **`RateLimit-Policy`** describes each named policy. `q` is the quota. `w` is an informational window in seconds. The optional `qu` gives the unit: requests, content-bytes, or concurrent-requests. The optional `pk` is a partition key. This field is meant to stay stable from one response to the next.
- **`RateLimit`** reports the current state per policy. `r` is the quota remaining, and `t` is an effective window in delay-seconds. It can change on every response.

The draft sets expectations that are worth copying into your own documentation:

- A positive `r` is a hint, not a promise.
- If `Retry-After` is also present, `Retry-After` wins.
- Servers may send these fields only when a client is close to a limit.
- Servers may lower the advertised values under load.
- Earlier revisions used separate `RateLimit-Limit`, `RateLimit-Remaining`, and `RateLimit-Reset` fields, and you'll still see those in production.

Because it's still a draft, the syntax may change again before publication. A practical approach is to keep emitting whatever `X-RateLimit-*` headers your existing clients parse, add the draft fields next to them, and version the draft fields with your API.

**Mapping a token bucket onto window-shaped headers is approximate.** The draft doesn't require any particular algorithm, and it describes `w` as informational. A reasonable mapping:

- `q` = burst capacity.
- `w` = seconds to refill from empty.
- `r` = whole tokens remaining.
- `t` = seconds until the bucket is full again.

Document which mapping you chose.

**Report every policy that applied to the request**, not only the tightest one. That alone would have closed the three-day ticket: the client would have seen that `tenant` was nearly exhausted while `key` still had room. You already computed these values when enforcing the limits (18.2b), so reporting them costs only header bytes.

**Don't advertise limits on endpoints that attackers probe.** On login, password reset, and verification, the headers tell an attacker exactly how fast they can go without being stopped. The draft's security considerations raise the same concern about disclosing capacity to untrusted callers.

**Don't let a cache store a `429`.** A `429` belongs to one client. A cache that stores it and serves it to everyone behind the same cache key has turned one customer's limit into an outage. `429` isn't cacheable by default, but "cache everything" CDN rules override that default. Send `Cache-Control: no-store` on every rejection, and check those rules.

### The body: which limit, and what to do

Use a problem-details body (RFC 9457) with a stable machine-readable type. The IETF draft proposes three problem types:

- `quota-exceeded` (`429`)
- `temporary-reduced-capacity` (`503`)
- `abnormal-usage-detected` (`429`)

Each carries a `violated-policies` array. The IANA registrations are only requested so far, so until they're final, use your own type URIs with the same shape.

The body should contain:

- **Which policy was violated**, using the same names as `RateLimit-Policy` and your documentation.
- **Whether the request was processed.** For a limiter rejection, the answer is "no," and saying so tells clients that even a non-idempotent `POST` is safe to retry.
- **What the client can do**: wait, spread requests out, or, for plan limits, upgrade.
- **A documentation link** and a **request ID** for support.

### Keep rejections cheap

During a traffic spike, rejections are most of your traffic. The rejection path should:

- **Skip anything that touches the database** and skip template rendering.
- **Reject before reading large request bodies.** When refusing a 50 MB upload, close the connection rather than reading the whole body first.
- **Log in aggregate.** Write one line per key per minute with a count, not one line per rejection. Emit metrics by dimension, since those are what the dashboards and the three-day ticket needed.

Per-rejection logging during a retry storm is how a limiter incident turns into a logging-pipeline incident.

### What a well-behaved client does

Whatever your SDK does is what most of your customers will do, so this section is really about what to build into it and what to state in your documentation.

- **Treat `Retry-After` as a floor.** Never retry sooner than it says. If the value is absurd (hours, when the call is inside a user request), give up and surface the error rather than sleeping.
- **Otherwise, use exponential backoff with full jitter.** Wait a random amount between zero and `min(cap, base × 2^attempt)`. Without randomness, clients rejected together retry together.
- **Retry at exactly one layer.** The storm in the problem came from multiplying retry layers. Pick either the HTTP client or the job framework, and turn retries off in the other.
- **Use a retry budget.** Allow retries only while they stay a small fraction of recent traffic. The budget can itself be a token bucket (18.1): each success earns a fraction of a token, and each retry spends one. gRPC's retry throttling works this way. When the budget is empty, fail immediately.
- **Throttle on the client under sustained rejection.** The Google SRE book describes clients that start rejecting their *own* requests locally, with a probability that grows as the server's acceptance rate falls. The overloaded server then stops paying for requests it would refuse anyway.
- **Pace ahead of time.** When `r` is low, spread the remaining requests across `t` instead of spending them all at once and waiting.
- **Retry `503`s from proxies carefully.** A `429` from your limiter means the request wasn't processed. A `503` from a gateway timeout might mean it was. Retry non-idempotent calls only with an idempotency key (Module 17).

### Beyond the response

Some of the contract lives outside HTTP:

- **Documented limits per plan**, generated from the same configuration the limiter enforces (18.2b).
- **A usage dashboard**, and a notification when a customer reaches something like 80% of a limit.
- **Advance notice before limits get stricter.** Lowering a limit is a breaking change, and it deserves the deprecation process from Module 33.
- **A usage endpoint.** GitHub's `/rate_limit`, which doesn't count against the primary limit, lets clients check their standing without spending quota to find out.

## When It's Appropriate

- **Any API with third-party clients** needs the full contract: correct codes, `Retry-After`, a body that names the policy, and documented limits.
- **Any API that ships an SDK.** The SDK's retry behavior is your largest lever over aggregate client behavior. Build the backoff into it, not just into the documentation.
- **High-volume integrations that sit near their limits** benefit from informational headers and proactive pacing. Their alternative is repeatedly overshooting and being rejected.
- **Internal service-to-service traffic** needs at least correct codes and `Retry-After`, honored by a shared client library. Many cascading failures are retry storms between your own services.
- **Browser clients** need a human-readable version: a clear message, a disabled button, and a countdown, rather than a generic error.

## When It's Unnecessary or Overkill

- **Full policy headers on an internal API with one caller.** `Retry-After` and a shared client library are enough.
- **Informational headers on login, reset, and verification endpoints.** Here, disclosing the limit is the cost, not a benefit.
- **A taxonomy of problem types before you have more than one limit.** One type with a `violated-policies` field can grow into more later.
- **Sub-second pacing hints for limits nobody approaches.**
- **Dropping the `X-RateLimit-*` headers your clients already parse** in favor of the draft. Emit both until your clients have moved.

## Trade-offs

- **Transparency is disclosure.** Published limits and remaining counts help customers, and they also help anyone trying to stay just under your limits or estimate your capacity.
- **Headers are a contract.** Changing what `Reset` means breaks clients. Emitting both the de facto and draft forms means maintaining two, and the draft may change before it becomes an RFC.
- **Remaining counts are estimates.** In a distributed, approximate limiter (18.2a), a client told `r=5` can still be rejected. Document this, or expect tickets about it.
- **Bytes on every response.** Several policies per response adds up. HTTP/2 header compression helps, and sending the fields only near exhaustion helps more.
- **Jitter slows down well-behaved clients** slightly more than strictly necessary. That's the price of not getting a herd.
- **Whole-second `Retry-After` over-waits for high-rate limits.** Clients that pace from `RateLimit` do better, but only if they implement it.
- **Clients may ignore all of it.** Server-side protection must never depend on clients cooperating. The contract reduces load from well-behaved clients; it doesn't defend against the rest.
- **SDK retry logic is code you maintain in every language you ship**, and old SDK versions keep running long after you've fixed them.

## Alternatives

- **A bare `429`.** No hints: clients guess. It's acceptable for internal callers that share one well-behaved client library.
- **Tarpitting or dropping connections.** For clearly abusive traffic, slow responses or closed connections cost the attacker more than a `429` does. They also hold your own resources. Use them for abuse, never for customers.
- **Shaping instead of rejecting** (18.1). Queue the request and serve it late. No client contract is needed, but latency grows and connections stay open while requests wait.
- **Asynchronous acceptance and batch endpoints.** Return `202 Accepted`, or accept 500 messages in one call. Both reduce how many requests a client needs, which is often better than helping it pace more requests.
- **Usage notifications and a usage endpoint** instead of headers on every response. Coarser, but cheap, and enough for clients that run far below their limits.

## How to Achieve It

**Level 0 — audit what you return today.** For a limit, an overload, and a limiter-store failure, record the status code, headers, and body. Check whether any cache layer can store them. Compute the ratio of `429` responses to distinct limited requests; that's your amplification factor.
_Signal you're here:_ nobody knows what a rate-limited client actually receives.

**Level 1 — correct codes, and a hint clients can trust.** Return `429` for customer limits and `503` for everything that's your side's problem. Send `Retry-After` in delay-seconds, rounded up and jittered. Add `Cache-Control: no-store`, a problem body that names the policy and states the request wasn't processed, and a rejection path that does no expensive work.
_Signal you need it:_ any external client, or any retry storm.

**Level 2 — document limits and ship the client behavior.** Generate plan limits in the documentation from configuration. Commit to "a `429` was not processed" and verify that it's true. Publish an SDK that honors `Retry-After`, uses full jitter, and retries at one layer.
_Signal you need it:_ an amplification factor above roughly 2, or recurring "which limit?" tickets.

**Level 3 — advertise limits in advance.** Send informational headers on successful responses, in both the de facto and draft forms, covering every policy that applied. Add a usage dashboard and threshold notifications.
_Signal you need it:_ customers building their own pacing, or asking what their limits are.

**Level 4 — adaptive clients and servers.** Add retry budgets and local throttling in the SDK, proactive pacing from `RateLimit`, and server-side lowering of the advertised limits under load, which the draft explicitly permits.
_Signal you need it:_ large integrations repeatedly bouncing off their limits, or overload events where client retries are a measurable share of traffic.

## Implementation

**TypeScript with Express on the server**, continuing from 18.2b's `res.locals.rateLimited`, **and a `fetch` wrapper for the client.** Both sides are in one language because the contract only works when both sides implement it.

**Reporting every policy that applied.** This assumes `take()` also returns the remaining tokens, which the 18.2a script already computes.

```ts
interface PolicyState { name: string; burst: number; ratePerSec: number; tokens: number }

export function setRateLimitHeaders(res: Response, applied: PolicyState[]) {
  // Draft syntax. Keep any X-RateLimit-* headers your existing clients parse, alongside these.
  res.set("RateLimit-Policy", applied.map(p =>
    `"${p.name}";q=${p.burst};w=${Math.max(1, Math.ceil(p.burst / p.ratePerSec))}`).join(", "));
  res.set("RateLimit", applied.map(p =>
    `"${p.name}";r=${Math.floor(p.tokens)};t=${Math.ceil((p.burst - p.tokens) / p.ratePerSec)}`).join(", "));
}
```

> **Aside — `w` and `t` are a translation, not a truth.** A token bucket has no window. This mapping reports "time to refill from empty" and "time until full," which is honest and approximate, and the draft allows exactly that. Whichever mapping you choose, write it down in your documentation. Clients will reverse-engineer it otherwise.

**Rejecting.**

```ts
type Rejection =
  | { kind: "limit";    policy: string; retryAfterMs: number }
  | { kind: "overload"; retryAfterMs: number };   // shedding, fail-closed limiter, upstream limiting *us*

function retryAfterSeconds(ms: number): number {
  const base = Math.max(1, Math.ceil(ms / 1000));                   // whole seconds; never round down
  return base + Math.floor(Math.random() * (Math.ceil(base / 4) + 1)); // spread the return
}

export function reject(res: Response, r: Rejection) {
  const retryAfter = retryAfterSeconds(r.retryAfterMs);
  const status = r.kind === "limit" ? 429 : 503;

  res.status(status)
    .set("Retry-After", String(retryAfter))
    .set("Cache-Control", "no-store")   // a cached 429 is an outage for everyone behind that cache
    .type("application/problem+json")
    .json(r.kind === "limit"
      ? {
          type: "https://api.example.com/problems/rate-limited",  // same shape as the draft's quota-exceeded
          title: "Rate limit exceeded",
          status,
          "violated-policies": [r.policy],                        // same names as RateLimit-Policy and the docs
          detail: `The '${r.policy}' limit is exhausted. This request was not processed; ` +
                  `it is safe to retry after ${retryAfter} seconds.`,
          docs: "https://docs.example.com/rate-limits",
          requestId: res.locals.requestId,
        }
      : {
          type: "https://api.example.com/problems/temporarily-unavailable",
          title: "Temporarily unable to accept requests",
          status,
          detail: "This is not caused by your usage. The request was not processed.",
          requestId: res.locals.requestId,
        });
}
```

> **Aside — "was not processed" is a promise, so check the pipeline.** It holds only if every limit runs before any side effect. That includes a body parser streaming an upload to disk, an idempotency-key record being written, and an audit log entry. A limiter placed after any of those turns "safe to retry" into a source of duplicates.

**The client side, as the SDK should ship it.**

```ts
const RETRYABLE = new Set([429, 503]);

export async function send(url: string, init: RequestInit,
                           { maxAttempts = 4, baseMs = 250, capMs = 20_000 } = {}): Promise<Response> {
  for (let attempt = 1; ; attempt++) {
    const res = await fetch(url, init);
    if (res.ok) retryBudget.earn(0.1);                      // successes refill the budget
    if (!RETRYABLE.has(res.status) || attempt >= maxAttempts) return res;
    if (!retryBudget.trySpend(1)) return res;              // retrying too much lately: surface it

    const floor  = parseRetryAfter(res.headers.get("Retry-After")) ?? 0;
    const jitter = Math.random() * Math.min(capMs, baseMs * 2 ** attempt);   // full jitter
    const wait   = Math.max(floor, jitter);
    if (wait > capMs) return res;                          // don't sleep for minutes inside a request

    await new Promise(r => setTimeout(r, wait));
  }
}

function parseRetryAfter(v: string | null): number | null {
  if (!v) return null;
  if (/^\d+$/.test(v)) return Number(v) * 1000;            // delay-seconds: no clock involved
  const at = Date.parse(v);                                // HTTP-date: depends on our clock agreeing
  return Number.isNaN(at) ? null : Math.max(0, at - Date.now());   // clamp: never a negative wait
}
```

> **Aside — this function is safe only as the only retry layer.** If the job framework calling `send()` also retries, you've rebuilt the 20× storm from the problem. Ship the SDK with its retries on and document that callers must turn theirs off, or the reverse. Also, `503` is in `RETRYABLE` for your own API, where a `503` carries the "not processed" promise. A generic client pointed at arbitrary proxies should retry non-idempotent calls only with an idempotency key.

## Further Reading

- **RFC 6585, §4** (`429 Too Many Requests`) and **RFC 9110, §10.2.3** (`Retry-After`) and **§15.6.4** (`503`). The primary definitions, short enough to read in full.
- **RFC 9457, "Problem Details for HTTP APIs."** The body format, including extension members like `violated-policies`.
- **`draft-ietf-httpapi-ratelimit-headers`** (revision 11, May 2026). `RateLimit` and `RateLimit-Policy`, the proposed problem types, and an unusually practical security-considerations section. Check the Datatracker for its current status before adopting it, since the syntax has changed between revisions.
- **RFC 9111, "HTTP Caching."** Which status codes are cacheable by default, and why a CDN override can make a `429` cacheable anyway.
- **Marc Brooker, "Exponential Backoff And Jitter"** (AWS Architecture Blog), and **"Timeouts, retries, and backoff with jitter"** (AWS Builders' Library). The simulations that made full jitter the default recommendation, and the case for retrying at one layer only.
- **_Site Reliability Engineering_ (Google), ch. 21, "Handling Overload,"** and **ch. 22, "Addressing Cascading Failures."** Client-side adaptive throttling, retry budgets, and how retries turn overload into outages.
- **gRPC proposal A6, "gRPC Retry Design."** Retry throttling as a token budget, specified precisely.
- **GitHub REST API documentation, "Rate limits for the REST API."** A mature public contract: `x-ratelimit-*` headers including which resource the limit applies to, secondary limits with `retry-after`, and a `/rate_limit` endpoint that doesn't spend quota.

A Go sibling would be worth writing for the client side. `x/time/rate`'s `Wait` accepts a `context.Context`, so "the caller's deadline is shorter than `Retry-After`" is handled by the language's cancellation model rather than by an `if` statement. Proactive pacing, meaning spreading `r` requests across `t` seconds, also becomes a few lines of limiter configuration. This article mentions both only in passing. Not yet written.

This closes Module 18. The algorithm decides how much, the shared store makes that decision true across the fleet, and the key decides who pays. The response decides what thousands of other programs do next. The habit to carry out of this: treat every error response you design as an instruction to someone else's code, and ask what happens when all of that code follows the instruction at once. Most retry storms and thundering herds were created by a response that told a large number of clients the same thing.
