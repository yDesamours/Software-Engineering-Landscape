# Webhook Security

_Module 17.1c — Webhooks & Integration APIs_

## The Problem

Three incidents at three different companies, all running the delivery pipeline from 17.1a.

**The forged order.** A customer's receiving endpoint is `https://shop.example.com/hooks/orders`. It accepts JSON, marks orders as paid, and releases them to the warehouse. It is a publicly routable URL with no authentication, because the URL was treated as the secret. Someone finds it — in a JavaScript bundle, in a subdomain enumeration, in a screenshot in a support ticket — and sends this:

```
POST /hooks/orders
{"type":"order.paid","data":{"object":"order","id":"ord_88421","version":99}}
```

Goods ship. Nothing in the system was compromised, nothing was exploited. A public endpoint was asked to do the thing it was built to do, by someone who wasn't you. **A webhook receiver is an unauthenticated public API that performs privileged actions**, and that's true on day one whether or not anyone has thought about it.

**The wrong fix.** The team responds by letting customers configure `Authorization: Bearer <token>` per endpoint. This is a real improvement, and it's also the moment to notice what it doesn't do. The token is a credential you hand to the customer's server, in full, on every single request — so it exists in their access logs, in whatever proxy sits in front of them, and in the request dump their error tracker captured last Tuesday. It's static, so anyone who captures one request can replay it a thousand times. And it proves only that the sender possessed a token. It says nothing about whether the body arrived as you sent it.

**The request that read the metadata service.** A user registers this as their webhook URL:

```
http://169.254.169.254/latest/meta-data/iam/security-credentials/
```

Your delivery worker dutifully POSTs to it from inside your VPC, gets back a document containing temporary IAM credentials, truncates it to 2KB, stores it as the response body in the delivery log — and renders it in the customer-facing dashboard you built in 17.1a so customers could debug their integrations.

You have built a credential exfiltration tool and shipped the user interface for it.

The variants are worse than the original. `http://127.0.0.1:9200/_search` against an Elasticsearch that trusts localhost. `http://admin.internal.svc/users` against a service whose entire authorization model is "it's not reachable from outside." A perfectly ordinary public URL that returns `302 Found` pointing at any of the above, because your HTTP client follows redirects by default and nobody told it not to. Or a hostname that resolves to a public address when you validate it at registration and to `127.0.0.1` six hours later when you actually dial.

Two completely different problems live in this article, and teams almost always ship the first one and forget the second. **Outbound, the consumer needs to prove the request came from you, unmodified and recently. Inbound, you are making network requests, from inside your perimeter, to addresses chosen by strangers.**

## What It Is

The outbound half is **payload signing**: you compute a message authentication code over the request using a secret shared with that one endpoint, and send it in a header. The consumer recomputes it and compares. It gives them three properties at once — the request came from someone holding the secret (authenticity), the body wasn't altered in transit (integrity), and, with a timestamp folded into the signed material, that it isn't a recording of an old request (freshness).

The inbound half rarely gets named at all in webhook documentation, but it has a name: **server-side request forgery**, SSRF. It's the general class of "my server dereferences a URL an attacker supplied," and a self-serve webhook registration form is the most direct instance of it that exists. The defence is **egress control**.

One confusion worth clearing immediately, because it derails design discussions: **TLS does not solve the outbound half.** When you POST to a customer's HTTPS endpoint, the certificate authenticates *them to you* and the channel is encrypted. Nothing in that handshake tells the receiving application who the client was. "We use HTTPS" is a correct answer to a different question. mTLS is the version that answers this one, and it's a real option (below) — plain TLS isn't.

Second: the payload is **signed, not encrypted**. TLS provides confidentiality on the wire; the signature provides authenticity and integrity at the application layer, where the receiving code can actually check it.

## Recognizing the Problem

- Your documentation, or your own mental model, treats the webhook URL as a secret.
- There's no signature header — or there is one, but it's computed over a parsed-and-re-serialized body.
- A consumer asked how they can tell a request is really from you, and the answer involved source IP addresses.
- One signing secret is shared across all of an account's endpoints, or the signing secret *is* the account's API key.
- There is no way for a customer to rotate a secret without a window where deliveries fail.
- Nothing in the signed material expires, so a captured request is valid forever.
- Your HTTP client follows redirects, and nobody made that decision on purpose.
- You have never tried registering `http://127.0.0.1:6379/` as a webhook endpoint against your own staging environment. (Do this today. It takes four minutes and the result is not usually reassuring.)
- `InsecureSkipVerify`, or its equivalent, was switched on once to help a customer with an expired certificate and never switched back.
- Response bodies from arbitrary hosts are stored and rendered in a UI.
- Your delivery workers can reach your internal network, because everything in that VPC can.

## How It Works

### The signature

Sign a string that contains the event id, the timestamp, and the exact body bytes:

```
signed_content = "{webhook_id}.{timestamp}.{raw_body}"
signature      = base64( HMAC-SHA256(endpoint_secret, signed_content) )

Webhook-Id:        evt_01HXQ7M3F2K8
Webhook-Timestamp: 1772623924
Webhook-Signature: v1,k8Yz3…==
```

Each part is doing a job:

**HMAC, not a plain hash of secret-plus-body.** `SHA256(secret || body)` is vulnerable to length-extension: an attacker who has one valid signature can append data and compute a valid signature for the extended message without knowing the secret. HMAC's nested construction exists precisely to prevent that, it's in every standard library, and there is no reason to hand-roll the alternative.

**Over the raw bytes**, exactly as they go on the wire — which is why 17.1b insisted the body be rendered once and stored as text. Any re-serialization anywhere in the chain changes key order or whitespace and invalidates the signature.

**The timestamp is inside the signed string**, not merely a header alongside it. A header the attacker can edit freely isn't a constraint. Inside the MAC, it binds the message to a moment, and the consumer rejects anything outside a tolerance window — five minutes is the common choice. That bounds replay to a window rather than eliminating it; the event id is what closes the rest, by letting the consumer dedupe (17.2b).

**The `v1,` prefix** is the cheapest thing in this article and the one most often omitted. It's how you migrate to a different algorithm later without a flag day. Adding a version prefix after the fact breaks every consumer doing an exact string comparison, which is most of them.

**Multiple signatures in one header**, space-separated, is what makes rotation possible. More on that next.

The consumer verifies with a constant-time comparison. Byte-by-byte comparison of MACs leaks information through timing, and while remotely exploiting that over the internet is difficult, using the constant-time function your language already ships is free.

### Secret lifecycle

Generate the secret yourself — at least 32 bytes of CSPRNG output — one per endpoint, not per account. Per-endpoint matters because a customer's marketing-automation integration and their fulfilment service are different blast radii, and because revoking one shouldn't disturb the other.

Store it so you can read it back. This one catches people, because the reflex from password storage is to hash it — but you have to *compute* the HMAC, so the secret must be recoverable. Encrypt it at rest with a key from a KMS, and treat that as the boundary. It's a different storage problem from passwords and deserves a different answer, not the same answer applied out of habit.

**Rotation only happens if it's free.** Give an endpoint two active secrets during an overlap window, sign with both, and send both signatures in the header. The consumer accepts if any signature matches, so they can deploy the new secret any time inside the window with no coordinated cutover. After the window, drop the old one. Without dual-signing, rotating a secret means scheduled downtime for the customer, which means nobody ever rotates, which means the secret leaked into a Slack channel in 2023 is still valid.

Worth stating plainly in your documentation: if an endpoint secret leaks, the exposure is that someone can forge events *to that consumer*. It is not a credential to your API and it gives no access to your system. Customers ask, and the precise answer is calming and also true.

### Endpoint verification at registration

Before you start delivering to a newly registered URL, prove the registrant controls it. Send a challenge — an event the receiver must echo a token from, or a specific response header — and enable the endpoint only on success. AWS SNS's subscription-confirmation step is the widely-seen version of this.

This exists for two reasons. Typos, which otherwise deliver one customer's data to whatever happens to be at the mistyped host. And deliberate misdirection: someone pointing your delivery pipeline at a third party they don't control, using your infrastructure as the sender.

It also blocks the naive SSRF attempt, since the metadata service will not echo your challenge token. It does not block blind SSRF where the side effect is the goal, and it does nothing about a host that behaves one way at registration and another at delivery. Necessary, not sufficient.

### Egress control

This is the half that gets skipped, and the rules are specific.

**HTTPS only, standard ports.** A plaintext webhook URL is a payload readable by every network between you, and an `http://` scheme is also how most of the internal-service attacks are written.

**Check the resolved IP at connect time, not the hostname at registration time.** This is the load-bearing rule:

```
at registration:   hooks.example.com  →  93.184.216.34     ✓ public, allowed
                   (endpoint saved, enabled)

six hours later, at delivery:
   DNS lookup      hooks.example.com  →  127.0.0.1
   socket dial     ────────────────────▶  ⛔ refused: loopback
```

Validating the hostname when it's typed in is checking a promise that the attacker renews every 30 seconds. The check has to happen against the address you are actually about to connect to, after resolution, before any bytes move.

**Block the whole list, in both address families.** Loopback, RFC 1918 private ranges, link-local `169.254.0.0/16` (this is the cloud metadata service), CGNAT `100.64.0.0/10`, `0.0.0.0/8`, multicast — and on the IPv6 side unique-local `fc00::/7`, link-local `fe80::/10`, and IPv4-mapped addresses like `::ffff:127.0.0.1`, which is the single most common bypass of a filter that only checked IPv4.

**Don't follow redirects** — or re-run the full check on every hop. A `302` is how every URL-validation scheme that runs once gets defeated.

**Disable or harden the metadata endpoint.** On AWS, IMDSv2 requires a `PUT` to obtain a token before any read, and a webhook POST cannot obtain one. Enforcing IMDSv2 removes the highest-value target in this article and costs nothing.

**Treat the response as hostile data.** Cap the body (17.1a), cap decompressed size if you accept compressed responses, and when you render it in the delivery log, render it as text — a stored response containing HTML or SVG shown inline in your dashboard is stored XSS delivered by your own debugging feature. And recognise that showing the response body at all is what upgrades blind SSRF into a read channel; it's a genuinely useful feature and a genuinely real trade.

**Rate-limit per destination host.** Otherwise anyone can point a hundred endpoints at a third party and use your fleet, with your source IPs and your reputation, to hammer them.

**Publish your egress IPs** so security-conscious consumers can firewall their receiver. Useful defence in depth — and say clearly in the same paragraph that IP origin is not authentication, because otherwise some fraction of consumers will use it *instead of* verifying signatures.

The honest framing: everything above is a mitigation implemented in your application. The actual control is topological — **run delivery workers in a subnet with no route to anything internal, egressing through a forward proxy that enforces this policy in one place.** Application-level filtering is what you build first because it ships this week; network isolation is what makes the next bypass someone discovers irrelevant.

### Certificates, and the pressure to turn verification off

Verify certificates, always. The pressure to disable it is specific and recurring: a customer's certificate expired, or is self-signed, or their chain is missing an intermediate, and deliveries are failing, and they're loud about it. The answer is that this is their problem, and the thing you owe them is an error message in the delivery log precise enough to fix it — `x509: certificate has expired or is not yet valid` costs you nothing and saves the support thread. One global flag switched on for one customer applies to every customer.

### Tenancy, which is where the worst outcome lives

The fan-out query in 17.1a joined endpoints on `tenant_id`. If that join is ever wrong — a missing predicate, a subscription created under the wrong account, an admin tool that copies endpoints between tenants — you deliver one customer's data to another customer's server, signed, over TLS, with every security control in this article working perfectly. It is the highest-severity failure the module contains and no amount of signing detects it.

Two defences. Test it directly, with a fixture that asserts an endpoint belonging to tenant A never receives an event from tenant B. And include the account identifier in every payload, telling consumers to verify it matches the account they expect — Slack's documentation asks receivers to check `team_id` for exactly this reason. It converts a silent disclosure into a rejected request at the far end.

Related and less dramatic: decide whether a subscription inherits the permissions of the user who created it or the account's full scope. Nearly all systems do the latter, and nearly all users assume the former.

## When It's Appropriate

- **Signing: from the first external endpoint, with no exceptions.** It's about thirty lines on your side, it's unretrofittable, and every alternative is weaker.
- **Connect-time IP filtering and no-redirects:** as soon as any URL is supplied by anyone outside your team. That's the day self-serve registration ships.
- **Challenge verification at registration:** when customers register their own URLs without review.
- **Dual-secret rotation:** as soon as you have a customer who will still be integrated in two years, which is every customer you want.
- **Asymmetric signing** (Ed25519 or ECDSA, public key published at a stable URL): when consumers are numerous enough that provisioning and protecting a shared secret per endpoint is itself the risk, or when a third-party platform verifies on many consumers' behalf — with a public key, anyone can verify without being trusted with anything.
- **mTLS:** when enterprise or regulated consumers ask for it and can operate a client certificate. A minority, but a well-resourced one.
- **Network isolation for delivery workers:** by the time you have a security review, and ideally before.

## When It's Unnecessary or Overkill

- **Internal service-to-service calls.** If both ends are yours, mTLS or your mesh's workload identity already establishes who's calling. Bolting HMAC on top adds a secret to manage and proves nothing new.
- **Encrypting the payload on top of TLS.** Rarely justified — you take on key distribution to buy confidentiality you already have. The exceptions are real but narrow: the payload passes through an intermediary aggregator the customer uses, or a regulation names encryption at the application layer.
- **Bespoke schemes.** Nonce servers, per-event derived keys, challenge-response before each delivery. Nearly all real-world failures here are consumer-side implementation mistakes, and every increment of cleverness produces more of them. Boring HMAC that a hundred consumers implement correctly beats an elegant protocol that forty implement wrong.
- **Blocking every private range with no escape hatch,** when you have on-prem customers delivering through a tunnel or a private-link arrangement. Build the allowlist path with human review rather than pretending the case doesn't exist.
- **Asymmetric signing by default** for a small, ordinary integrator base. HMAC verification is four lines of copy-paste in every language; you'll get more consumers actually verifying.

## Trade-offs

- **The security depends on people who don't work for you.** A consumer who skips verification gets no protection from any of this, and you will never know. What you can control is making verification easy: documentation with working snippets in several languages, official libraries, and a "send test event" button that fails loudly when the signature is wrong.
- **Raw-body access fights frameworks.** Middleware that parses JSON before your handler sees it, gateways that re-serialize, serverless proxy integrations that base64-encode — all of these break verification in a way that looks like your bug. Expect this to be a standing share of your integration support load.
- **Timestamp tolerance produces clock-skew tickets.** Legitimate deliveries rejected because a consumer's VM drifted eleven minutes. There's no fix, only a window size and an error message that names the cause.
- **Rotation adds branching** to the signing path and list-parsing to every consumer's verification.
- **Recoverable secret storage is a real key-management dependency,** with all the rotation, access-control, and audit obligations that implies. It is genuinely harder than storing a hash.
- **Egress filtering breaks legitimate integrations** and generates a support path that involves a human deciding whether a private address is allowed.
- **The delivery log is in tension with data minimization.** It contains payloads, which contain customer data, and responses, which may contain anything. It needs retention limits and access controls, and it's the table most likely to be over-shared internally because it's so useful.
- **Every control here is one your consumers can decline.** You can refuse to deliver to unverified endpoints; you cannot make anyone check a signature.

## Alternatives

**A static bearer token per endpoint.** Simpler for consumers — a string comparison, with no raw-body subtlety — and genuinely better than nothing. Weaker in three specific ways: it's replayable, it provides no integrity, and the credential travels to their server on every request. Reasonable as an *additional* option for consumers who can't do HMAC; not as a replacement.

**A signed JWT in a header**, or the whole payload as a JWT. This is the same cryptography in a standard container, and it comes with `exp` and `jti` — expiry and a unique id — solving freshness and dedupe by convention rather than by your documentation. RFC 8935 specifies exactly this for security event delivery. The cost is that JWT libraries have a long history of verification footguns (`alg: none`, algorithm confusion), and you'd be moving that risk onto consumer implementations you can't review.

**mTLS.** The strongest mutual authentication available, with no application-layer secret at all. Certificate lifecycle on both sides, and most small consumers cannot operate it — which makes it an enterprise option rather than a default.

**A capability URL** — the secret embedded in the path, generated by you. Zero implementation work for the consumer. It leaks through their access logs, their referrer headers, and their browser history, and it provides no integrity. Fine as a secondary layer; never the only one.

**Deliver into the consumer's cloud account** — the EventBridge partner source or Pub/Sub topic from 17.1a. This dissolves most of this article rather than solving it: authentication is IAM, there is no user-supplied URL, and therefore no SSRF surface, no secret to rotate, and no signature for anyone to skip verifying. It's the strongest available answer to the security problem and is underused mainly because it's discussed as an integration convenience rather than a security control.

**A managed webhook provider.** You inherit a signing scheme and egress policy that have been attacked more than yours has, and you accept a vendor in the path of your customer data.

## How to Achieve It

**L0 — Before the first external endpoint.** HTTPS-only URLs, a random per-endpoint secret, HMAC-SHA256 over `id.timestamp.raw_body`, a `v1,` prefix, and documentation with verification code in at least three languages. Nothing here can be added later without breaking every consumer at once.

**L1 — The day registration becomes self-serve.** Connect-time IP filtering in both address families, redirects disabled, response size caps, certificate verification confirmed on. *Signal you skipped this:* you can register `http://127.0.0.1:6379/` and see something in the delivery log.

**L2 — Lifecycle.** Dual-secret rotation with a customer-facing "roll secret" control, challenge-response verification at registration, published egress IPs, account id in every payload. *Move when:* a customer asks how to rotate, or a security questionnaire arrives.

**L3 — Isolation and containment.** Delivery workers on an egress-only network path behind a forward proxy, per-destination-host rate limits, access controls and retention on the delivery log, and a test asserting cross-tenant delivery is impossible.

**L4 — Optional stronger schemes.** Asymmetric signing with a published key set, mTLS for consumers who require it, and the `v2` migration path your prefix left open.

## Implementation

Go, because the egress control is a dialer hook and the signing is four lines of standard library — and because this is where `guardedDialer` from 17.1a gets written.

**Signing, with rotation built in:**

```go
func signatureHeader(secrets []Secret, id string, ts int64, body []byte) string {
	signed := fmt.Sprintf("%s.%d.%s", id, ts, body)
	sigs := make([]string, 0, len(secrets))
	for _, s := range secrets { // active, plus previous during a rotation window
		mac := hmac.New(sha256.New, s.Key)
		mac.Write([]byte(signed))
		sigs = append(sigs, "v1,"+base64.StdEncoding.EncodeToString(mac.Sum(nil)))
	}
	return strings.Join(sigs, " ")
}
```

Three things in this function cannot be added later: the id and timestamp inside the signed string, the version prefix, and the fact that the header is a *list*. A consumer who wrote `if header == expected` works fine until the day you send two signatures, so the list has to be there from the first delivery even when it always has one element.

**Verification — the code you publish, not code you run:**

```go
func Verify(secret []byte, sigHeader, id, tsHeader string, raw []byte, now time.Time) error {
	ts, err := strconv.ParseInt(tsHeader, 10, 64)
	if err != nil {
		return errBadTimestamp
	}
	if d := now.Sub(time.Unix(ts, 0)); d > 5*time.Minute || d < -5*time.Minute {
		return errStale // bounds replay to the tolerance window
	}

	mac := hmac.New(sha256.New, secret)
	fmt.Fprintf(mac, "%s.%d.%s", id, ts, raw) // raw: the bytes off the wire
	want := "v1," + base64.StdEncoding.EncodeToString(mac.Sum(nil))

	for _, got := range strings.Fields(sigHeader) {
		if hmac.Equal([]byte(got), []byte(want)) {
			return nil
		}
	}
	return errBadSignature
}
```

`raw` is the entire article's most expensive footnote. It must be the bytes as received — not a struct that was decoded and re-encoded, not a map that went through a JSON round trip. Any of those change key order, whitespace, or number formatting, and verification then fails on every single request, which the consumer reports as your signature being broken. A meaningful fraction of all webhook integration support is this one sentence, which is why it belongs in the first paragraph of your documentation and not in a troubleshooting section.

**The guarded dialer:**

```go
var guardedDialer = &net.Dialer{
	Timeout: 3 * time.Second,
	Control: func(network, address string, _ syscall.RawConn) error {
		host, _, _ := net.SplitHostPort(address)
		ip := net.ParseIP(host) // already resolved — this is the real destination
		if ip == nil || isBlocked(ip) {
			return fmt.Errorf("refusing to connect to %s", host)
		}
		return nil
	},
}

func isBlocked(ip net.IP) bool {
	if v4 := ip.To4(); v4 != nil {
		ip = v4 // ::ffff:127.0.0.1 is 127.0.0.1
	}
	switch {
	case ip.IsLoopback(), ip.IsPrivate(), ip.IsUnspecified(),
		ip.IsLinkLocalUnicast(), ip.IsLinkLocalMulticast(), ip.IsMulticast():
		return true
	}
	return cgnat.Contains(ip) // 100.64.0.0/10
}
```

`Control` runs after DNS resolution and immediately before the socket is used, which is the only point where the check is sound. A hostname validated at registration is a statement about what DNS said once; this is a statement about where the packet is going. The four-line `To4()` normalization is what stops `::ffff:127.0.0.1` from walking straight through a filter that only knows IPv4.

And the client that uses it:

```go
var client = &http.Client{
	Timeout:   8 * time.Second,
	Transport: &http.Transport{DialContext: guardedDialer.DialContext},
	CheckRedirect: func(*http.Request, []*http.Request) error {
		return http.ErrUseLastResponse // a 302 must not skip the check above
	},
}
```

Worth being clear about what this is: a mitigation, written in application code, that a sufficiently creative bypass will eventually get past. The control is a network in which the delivery workers have no route to anything internal in the first place. Build the dialer this week and the network boundary this quarter.

---

The habit worth taking away: **any time your infrastructure accepts a URL from a user and dereferences it, this exact list applies.** Webhook registration is the obvious case, but it's the same surface as an avatar "import from URL" field, a PDF renderer that fetches images, an RSS importer, an OAuth issuer discovery document, a link preview generator, and an SSO metadata endpoint. Teams secure the webhook feature carefully and ship the link-preview service six months later with a bare `http.Get`. Whenever you see a user-controlled URL reaching a fetch, the question to ask is what address that actually resolves to at the moment of connection, and whether anything would stop it if the answer were `169.254.169.254`.

## Further Reading

- **OWASP Server Side Request Forgery Prevention Cheat Sheet** — the canonical list of blocked ranges, bypass techniques, and why allowlisting by hostname doesn't hold up.
- **Standard Webhooks** (standardwebhooks.com) — the signature scheme, header names, and tolerance window this article follows.
- **Slack's "Verifying requests from Slack"** — the clearest published description of a versioned signature with a replay window, and a good model for how to document one.
- **Stripe's and GitHub's webhook signature documentation** — two mature variants, including how they present secret rotation to customers.
- **RFC 2104** (HMAC) for why the construction is what it is, and **RFC 8935** (Push-Based Security Event Token Delivery) for the JWT-based alternative discussed above.
- **AWS IMDSv2 documentation** — the session-token requirement and why enforcing it removes the highest-value SSRF target in a typical deployment.
- PortSwigger's research write-ups on **DNS rebinding** — the clearest demonstration that time-of-check and time-of-use are different moments.
- Within this map: delivery mechanics in **17.1a**, byte-stable payloads in **17.1b**, receiver-side verification and dedupe in **17.2b**, the broader application security surface in **20**, and data handling obligations in **34**.

A TypeScript sibling would earn its place, and for an unusual reason: Node has no equivalent of Go's `Dial` control hook, so the connect-time IP check has to be assembled from a custom `lookup` on the agent or an undici dispatcher, and the raw-body problem is sharper because `express.json()` is the default everyone starts with and `express.raw()` has to be mounted on the webhook route specifically, before it. The security properties are identical; the amount of code required to not get them wrong is not. Not yet written.
