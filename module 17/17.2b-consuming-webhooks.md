# Consuming Webhooks

_Module 17.2b — Webhooks & Integration APIs_

## The Problem

Now you're on the other end. A payment provider sends you events, and the handler is the obvious one:

```ts
app.post("/webhooks/acme", async (req, res) => {
  const event = req.body;
  if (event.type === "invoice.payment_succeeded") {
    await extendSubscription(event.data.object.customer_id);
    await sendReceipt(event.data.object);
  }
  res.sendStatus(200);
});
```

It works in staging on the first try, which is part of the problem. Here's the order things go wrong.

**Anyone can call it.** The URL is public and unauthenticated, and the endpoint's function is to grant paid access. Someone who guesses or finds it — from a JavaScript bundle, a subdomain scan, a screenshot — can extend their own subscription indefinitely by sending a JSON object. There is no exploit here; the endpoint does what it was built to do.

**So verification gets added, and it never passes.** The team computes the HMAC over `JSON.stringify(req.body)` and compares. It fails on every request, one hundred percent of the time, because `express.json()` is mounted globally and `req.body` is a parsed object that re-serializes with different whitespace and key order than the bytes that arrived. After ninety minutes of debugging, somebody wraps the check in a `try/catch` that logs a warning and continues. The code now contains a signature verification that verifies nothing, which is worse than not having one, because it appears in the security review as a checkmark.

**A customer gets two receipts and two months.** The provider timed out at eight seconds; the handler had finished at 8.4. The provider retried. The subscription extension ran twice. The provider's documentation said, in bold, that events may be delivered more than once.

**The handler becomes the bottleneck.** Four API calls and a PDF render, twelve seconds per event. The provider's per-endpoint concurrency (17.1a) is one, so their queue for you grows faster than it drains, every event is late, and their retry machinery keeps two copies of the same work running concurrently.

**The subscription silently downgrades.** `subscription.updated` with `plan: pro` and `subscription.updated` with `plan: free` were emitted 200 milliseconds apart and delivered in parallel. The `free` one landed second. The customer is paying for pro and using free.

**Then everything stops.** A new event type ships — `refund.partially_settled` — and falls through the switch into code that throws. The handler returns `500` for it. The provider retries it for three days, the failure rate crosses their threshold, and the endpoint is auto-disabled. Not for that event type. For all of them.

Six failures, one cause: **the endpoint was written as an RPC call, and it is not one.** It's an intake for messages that arrive from an untrusted source, possibly twice, possibly in the wrong order, possibly never, from a sender that will never know whether you did anything with them.

## What It Is

A **webhook receiver** is a message consumer wearing an HTTP request handler's clothes. The framing that fixes most of the above:

> **The endpoint's job is to authenticate the message, record it durably, and acknowledge. Processing happens somewhere else.**

Three properties the sender structurally cannot provide, which you must supply:

- **Authenticity** — the sender can sign, but only you can verify, and only you find out if you don't.
- **Exactly-once *effect*** — the network guarantees at-least-once delivery; making the consequences happen once is entirely a property of your code.
- **Order independence** — events reflect a sequence of facts; the transport does not preserve it.

Worth separating two things that get conflated: an *idempotent endpoint* (returning `200` twice is trivial) and *idempotent processing* (the money moves once). Only the second one is work, and it's most of this article.

## Recognizing the Problem

- Your handler does the work inline and takes more than a second.
- There's no signature check, or there is one inside a `try/catch` that logs and proceeds.
- You can't answer "have we already processed event `evt_X`?" with a query.
- Your handler returns non-`2xx` for event types it doesn't recognize.
- The provider's dashboard shows retries you didn't know were happening.
- You have seen a duplicate side effect: two emails, two shipments, a doubled credit.
- Your code treats the payload as current state rather than as a past fact.
- You found out about a webhook outage from a customer rather than a metric.
- Your handler opens a database transaction and then calls a third-party API inside it.
- You keep no copy of the payloads you receive, so every investigation depends on the provider's dashboard.
- Developing the integration requires deploying.

## How It Works

### The three-step handler

```
POST /webhooks/acme
  1. read the raw bytes            (size-capped)
  2. verify signature + timestamp  → 401 and stop
  3. INSERT event id … ON CONFLICT DO NOTHING
  4. 200 OK                        ← target: under 100ms
─────────────────────────────────────────────────
  later: a worker claims the row, processes it idempotently
```

The reason to acknowledge before processing isn't performance, it's control. The sender's timeout is theirs to choose and you cannot negotiate it. Their per-endpoint concurrency means your handler's latency directly sets their throughput to you. And their retry of a request that's still executing gives you two workers running the same side effect at the same time — the hardest bug in this article, produced entirely by doing the work inline.

The objection to answer honestly: if you acknowledge and then crash, you've told the sender something is done that isn't. That's why **the acknowledgement comes after a durable write, not before.** The `200` doesn't mean "handled"; it means "this is now my responsibility, and I have it written down."

### Verify before you parse

Verification runs on the raw bytes, before any framework touches them. In Node the trap is middleware ordering; in other stacks it's a request body that can only be read once, or a gateway that re-encodes. The symptom is identical everywhere and unusually misleading: verification fails *every single time*, which reads like the sender's signature being broken rather than a local bug, which is why so many teams end up disabling the check rather than suspecting their own framework.

A few details around it:

- **Cap the body size before buffering.** This endpoint is public and unauthenticated; the parser must not be the first thing that meets a hostile request.
- **Return `401` with no detail.** Don't explain to an unauthenticated caller which part of their forgery was wrong.
- **Count verification failures and alert on a spike.** It's either a secret rotation you missed or someone probing. Both are things you want to know within minutes.
- **Hold two secrets during rotation** — the mirror image of 17.1c. The sender may send several signatures; accept if any matches.
- **Use the provider's own library** if they ship one. It exists because this specific class of bug is their most common support ticket.

### Idempotency, properly

Start with a unique constraint on the sender's event id:

```sql
CREATE TABLE received_events (
  source       text        NOT NULL,
  id           text        NOT NULL,       -- the sender's event id
  type         text        NOT NULL,
  payload      text        NOT NULL,       -- raw bytes, as received
  received_at  timestamptz NOT NULL DEFAULT now(),
  processed_at timestamptz,
  PRIMARY KEY (source, id)
);
```

`INSERT … ON CONFLICT DO NOTHING` makes redelivery free: the second copy inserts zero rows and you return `200` anyway. Storing the raw payload rather than parsed JSON matters for the same reason it did on the sending side — it's the only artifact that can settle a disagreement later, and you cannot reconstruct what you never kept.

But this only handles *redelivery*. It does not make the processing idempotent, because your own worker can crash after the side effect and before recording success. So the effect itself needs a guarantee, and there's a ladder of them:

- **Naturally idempotent** — `UPDATE subscriptions SET status = 'active'`. Running it twice is running it once. Prefer expressing work this way whenever the domain allows.
- **Made idempotent by a constraint** — appending a credit or an audit entry becomes safe with a unique key on `(event_id, action)`. The second attempt violates the constraint and you treat that as success.
- **Made idempotent by delegation** — for outbound calls, pass the event id as the downstream idempotency key. The payment API you call has the same machinery (15.2a); use it rather than reimplementing it.
- **Irreversible and unkeyed** — sending an email, printing a label, opening a door. These cannot be made idempotent after the fact, so they must be moved behind one of the mechanisms above: enqueue the job keyed on the event id, inside the same transaction as everything else.

### Order independence

Two mechanisms, and you need whichever one the sender's payload supports.

**If the payload carries a version** (17.1b), guard on it: `WHERE version < $new`. Reordered events become no-ops and the replica converges.

**If it doesn't, refetch.** Treat the event as a notification that something changed and read current state from the sender's API. Costs an API call and a rate-limit slot, and buys correctness so completely that reordering stops being a concept you have to think about. For any resource the sender exposes, this is the default worth reaching for.

A few cases where neither is needed: events that are facts about discrete occurrences — a payment attempt, a message sent, a scan recorded — append rather than overwrite, so order doesn't affect the outcome. And one case where both are insufficient: a delete reordered before a create. Keep a tombstone so that a `created` event for an id you already saw deleted doesn't resurrect it.

### Unknown event types return 200

Small rule, disproportionate consequences. An event type you don't handle is not an error; it's information you don't need. Log it, increment a counter, return `200`.

Returning `5xx` for unrecognized types pushes your endpoint's failure rate up, consumes the sender's retry budget on events nobody wants, and eventually trips their auto-disable rule (17.2a) — which stops the events you *do* handle. It's the failure in the Problem section, it's entirely self-inflicted, and the fix is a `default` branch.

The same logic applies to a payload that verified correctly but doesn't parse or is missing fields you expect: that's the sender's bug, and retrying it will produce an identical failure forever. Record it, acknowledge it, and alert your own team.

### The one legitimate non-2xx

This is the cleanest rule in the article:

> **If you could not record the event, return `503` and let them retry. If you recorded it but cannot process it, return `200` and retry it yourself.**

Your database being down is a good reason to use the sender's retry machinery — it's free, it's already built, and the event is genuinely not yet your responsibility. A downstream API failing during processing is not, because the sender's retries expire in days, can't be triggered on demand, and redeliver the whole event rather than the step that failed. Once the event is in your table, your retries, your backoff, and your dead-letter queue own it (Module 10).

### Reconciliation, and the failure with no error message

Webhooks will miss events. Your endpoint gets auto-disabled during a bad week. The sender has an incident. The retry budget expires while you're down for four days. A subscription filter is wrong. None of these produce an error in your system, because **the event that never arrives generates no log line anywhere.** Silence and health are byte-identical.

Two defences, and any integration with money or access attached needs both:

**A periodic sync against the sender's list or log API**, feeding the exact same ingestion path so the unique constraint no-ops everything you already have. "Webhooks for latency, polling for completeness" is the arrangement every mature integration converges on, and it's the reason 17.1a argued for shipping a log endpoint alongside the webhooks.

**An absence alert.** If you normally receive four hundred events an hour and have received zero for three, something is wrong. This single alert catches auto-disablement, expired certificates, rotated secrets, DNS changes, and sender outages — the entire category that otherwise gets discovered by a customer.

### Local development

Three things make integration development tolerable, and all of them are cheap: a tunnel forwarding the endpoint to `localhost`, the sender's trigger tooling if they have it (17.2a), and — the one people skip — **saving real received payloads as test fixtures.** A fixture captured from the wire can't drift from the documentation the way a hand-written one does. Three tests catch most of this article: the same event delivered twice, two events applied in reverse order, and an event type you've never seen.

## When It's Appropriate

The full pipeline — verify, record, acknowledge, process asynchronously, reconcile — is worth it when:

- The side effect costs money, sends a message, or grants access.
- The work takes more than roughly 200ms, or calls anything over the network.
- You handle more than one or two event types, so the "unknown type" case is real.
- Missing an event has material consequences — billing, entitlement, fulfilment — which is what makes the reconciliation job worth building rather than just sensible-sounding.
- The sender retries, which is to say always.

## When It's Unnecessary or Overkill

- **A single low-stakes notification** — post to Slack when a build finishes. Verify the signature, do the work inline, accept an occasional duplicate message. A queue and a reconciliation job for this is machinery serving nothing. Note what survives even here: verify, and return `200` for unknown types.
- **Your own retry stack when the operation is naturally idempotent** and the sender retries for three days. Let them.
- **Reconciliation polling for events with no material consequence.** If a missed event means a slightly stale dashboard, an absence alert alone is enough.
- **A generic multi-provider ingestion framework** written for your first provider. Write the second one before you abstract.
- **Refetching state on every event** when the payload already carries a version and the sender charges you for API calls.

## Trade-offs

- **`200` no longer means done.** You've moved the failure from a place the sender monitors to a place only you monitor, so you now owe yourself a metric: the age of the oldest unprocessed event. Without it, the async design is strictly worse than the inline one it replaced.
- **You are now storing their data.** Raw payloads contain whatever the sender put in them, including PII, in your database, with retention and access consequences (Module 34).
- **Debugging becomes two-hop** — received but not processed, processed but failed, failed and dead-lettered. More states, more places to look.
- **Refetching costs API calls** against the sender's rate limits, at exactly the moments when you're receiving the most events.
- **Reconciliation is a second code path computing the same thing**, and it can drift from the first one or contain its own bugs. It needs tests, and it needs a stated rule for what happens when the poll and the webhook disagree — normally "higher version wins."
- **Verification couples you to the sender's operations.** Their secret rotation, their signature scheme version bump, their gateway change are all now events in your incident history.
- **You remain blind to their side.** You can observe what arrives; you cannot observe what they decided not to send, or sent to a URL that hasn't been yours since 2024. Absence alerting is the only lever, and it's a coarse one.

## Alternatives

**Poll their API instead.** If the sender offers a cursor-paginated log, consuming it gives you completeness by construction, no public endpoint, no signature verification, no duplicates, and no reordering. You give up latency and spend requests. For low-volume, low-urgency integrations this is honestly the better engineering decision and it's routinely passed over because webhooks feel more modern.

**A dedicated intake function.** A tiny serverless function whose entire job is verify-and-enqueue, deployed separately from your application. Your main app can then be down, deploying, or slow without the sender seeing a single failure, and the availability requirement lands on fifteen lines of code rather than your monolith. Cheap, and the most under-used option in this list.

**A managed inbound gateway** — Hookdeck, Svix's ingest side, or a queue-backed edge worker. They terminate, verify, buffer, retry into your system, and give you a searchable history and a replay button you didn't build. Worth it when your application can't offer the availability the sender expects, or when you consume from many providers and want one intake discipline instead of five.

**Ask the sender to deliver into a queue.** Increasingly senders offer SQS, Pub/Sub, or EventBridge destinations as an alternative to HTTP. This deletes the entire article: no public endpoint, no signature scheme, no SSRF-adjacent surface, authentication by IAM, and retries and dead-lettering provided by infrastructure that already does it well. If it's on the menu, take it.

**Use the sender's SDK** rather than implementing verification yourself. Not an alternative to the architecture, but an alternative to the most bug-prone twenty lines in it.

## How to Achieve It

**L0 — Verify and process inline.** One event type, low stakes, signature checked, `200` for anything unrecognized. Defensible, and the two habits it establishes are the ones that would otherwise never get added. *Move when:* the first duplicate side effect, or the first timeout in the sender's dashboard.

**L1 — Record, acknowledge, process later.** A `received_events` table with a unique `(source, id)`, the raw payload stored, and a worker that claims rows. The table is the queue; don't insert a row and enqueue a job separately, or you've built a dual write inside the system that exists because of dual writes. *Move when:* an event is processed twice, or arrives out of order.

**L2 — Make the effects safe.** Idempotent operations or unique constraints, downstream idempotency keys on outbound calls, a version guard or a refetch, and your own retry and dead-letter path with alerting. *Move when:* the integration carries money or access.

**L3 — Close the loop.** A reconciliation job reusing the ingestion path, absence alerting, and recorded payloads as test fixtures. *Move when:* you discover a gap you can't explain, which will happen.

**L4 — Generalize.** A shared intake path with per-provider adapters, a replay capability over your own stored events, and per-provider dashboards. *Move when:* the third provider arrives.

Two things are effectively unretrofittable: **storing the raw payload** (you cannot go back and keep what you discarded) and **the unique constraint on event id** (adding it later means reconciling whatever duplicate side effects already happened).

## Implementation

TypeScript and Express, chosen because the middleware-ordering trap is the single most common real failure in this article and it's visible in three lines.

```ts
// Mounted BEFORE any global express.json().
app.post(
  "/webhooks/acme",
  express.raw({ type: "application/json", limit: "1mb" }),
  async (req, res) => {
    const raw = req.body as Buffer; // a Buffer here, not an object

    try {
      verifySignature(SECRETS, req.headers, raw);
    } catch {
      metrics.increment("webhook.verify_failed", { source: "acme" });
      return res.sendStatus(401);
    }

    const evt = JSON.parse(raw.toString("utf8"));

    try {
      await db.query(
        `INSERT INTO received_events (source, id, type, payload)
         VALUES ('acme', $1, $2, $3)
         ON CONFLICT (source, id) DO NOTHING`,
        [evt.id, evt.type, raw.toString("utf8")],
      );
    } catch {
      return res.sendStatus(503); // couldn't record → their retry, not mine
    }

    return res.sendStatus(200);
  },
);
```

If `express.json()` runs before this route, `req.body` is a parsed object and the original bytes are gone — unrecoverably, because re-serializing produces different bytes. Signature verification then fails on every request forever, and the failure looks like the sender's problem. This one ordering decision accounts for a remarkable share of all webhook integration support, on both sides.

The `INSERT` is the enqueue. There's no separate job push, deliberately: a row in a table the worker polls is one durable write, whereas inserting and *then* enqueuing is a dual write with the same failure mode this module has been avoiding since 17.1a.

```ts
async function processInvoicePaid(evt: ReceivedEvent): Promise<void> {
  await db.tx(async (tx) => {
    const claim = await tx.query(
      `UPDATE received_events SET processed_at = now()
        WHERE source = $1 AND id = $2 AND processed_at IS NULL
        RETURNING 1`,
      [evt.source, evt.id],
    );
    if (claim.rowCount === 0) return; // another worker has it, or it's done

    const applied = await tx.query(
      `UPDATE subscriptions SET status = 'active', version = $2
        WHERE id = $1 AND version < $2`,
      [evt.payload.data.id, evt.payload.data.version],
    );
    if (applied.rowCount === 0) return; // an older event; nothing to do

    await enqueue(tx, "send_receipt", { idempotencyKey: evt.id, invoice: evt.payload.data });
  });
}
```

Three guards, three different jobs. The claim stops two workers from processing the same event concurrently. The `version <` predicate makes reordering a no-op rather than a corruption. And the receipt is enqueued inside the transaction rather than sent inline, because sending an email is the one irreversible thing here — keying that job on the event id is what stops a retried transaction from producing two receipts. Note that the claim is *inside* the transaction, so a crash rolls it back along with everything else and the event is retried cleanly; that's correct, and it's also exactly why the email had to be enqueued rather than sent.

```ts
// Hourly.
async function reconcileAcme(): Promise<void> {
  let cursor = await getCursor("acme");
  for await (const page of acme.listEvents({ after: cursor })) {
    for (const e of page.data) await ingest("acme", e); // same path; conflicts no-op
    cursor = page.data.at(-1)?.id ?? cursor;
  }
  await setCursor("acme", cursor);

  if (await hoursSinceLastEvent("acme") > 3) {
    alert("No events received from acme in 3 hours");
  }
}
```

It reuses `ingest`, which is the entire point — a reconciliation job with its own processing logic is a second implementation of your business rules that will drift from the first one and be wrong in a way nobody notices for a year. The absence check at the bottom is four lines and catches the failure mode with no error message: auto-disablement, a rotated secret, an expired certificate, a DNS change, or the sender simply having stopped.

---

The habit to generalize: **every inbound asynchronous integration needs the same four properties, and the transport is incidental.** Webhooks, queue consumers, S3 event notifications, SFTP file drops, device telemetry, partner batch feeds — all of them arrive from outside, all of them can arrive twice, out of order, or not at all. The three questions worth asking of any intake before it ships are: what happens if this arrives twice, what happens if it arrives out of order, and what tells me if it never arrives at all. The third one is the one nobody asks, and it's the one that fails quietly for six weeks.
