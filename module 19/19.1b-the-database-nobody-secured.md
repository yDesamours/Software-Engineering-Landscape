# The Database Nobody Secured

_Module 19.1b — Logging, Monitoring & Observability_

## The Problem

A booking platform for physiotherapy clinics. About 400 clinics use it to schedule patients, take intake forms, and send appointment reminders by SMS. The team has done the data-protection work on its database carefully: patient notes are encrypted per column, row-level security isolates clinics from each other, four engineers have production access and every query they run is audited, and a deletion workflow erases a patient on request.

Then a hospital group asks, in a security questionnaire, a question nobody had thought hard about: *"List every system in which patient data is stored."*

To answer honestly, an engineer searches the log store for a test patient, `jane.doe@example.com`. There are 14,000 hits, spread across eleven fields.

**The request log records full URLs.** `GET /v1/patients/search?q=jane.doe@example.com` is every search a receptionist ever ran. `GET /reset-password?token=7Hq…` is a live reset token, valid for an hour, and searchable by everyone with log access.

**A debug line never went away.** During an incident six months ago, someone added `slog.Debug("intake payload", "body", body)` and enabled DEBUG for one clinic using the scoped-debug switch from 19.1a. Nobody switched it back. The body includes the intake form's free-text field: *"post-surgical ACL reconstruction, anxious about returning to work."*

**The database writes its own logs.** A duplicate signup produces a Postgres error whose detail line reads `Key (email)=(jane.doe@example.com) already exists`. The managed database ships its server logs to the same store.

**An HTTP client error carries a credential.** When the SMS provider times out, Go's client error reads `Post "https://sms.example.com/v2/send?api_key=sk_live_4f…": context deadline exceeded`. It's logged at ERROR, a few hundred times a week.

**Someone added a convenience field.** Support wanted to find requests by patient without a database lookup, so the wide event from 19.1a gained `patient_email`.

Then the engineer lines up the two stores side by side:

```
                     Postgres                          log store
who can read it      4 engineers, audited              60 people incl. contractors,
                                                       plus the vendor's support staff
clinic isolation     row-level security                one index for every clinic
encryption           per-column keys for notes         at rest, vendor-managed key
retention            policy-driven, with deletion      400 days, no deletion path
location             eu-central                        vendor's default region (US)
```

The same week, a patient invokes her right to erasure. The database delete takes one call. Her email is in 400 days of append-only log indexes, in the S3 archive behind them, in the error tracker, and in two incident tickets where someone pasted log lines.

Every control on the database, the logs routed around. The team had built a second copy of production data, less protected than the first, one convenient field at a time.

## What It Is

This is **sensitive-data handling for logs**: treating the log store as a data store subject to the same classification as your primary database. That means controlling what enters it (minimization, redaction, pseudonymization) and governing what is there anyway (access, retention, location, deletion).

Two kinds of sensitive data leak into logs, and they call for different responses:

- **Secrets**, such as passwords, session and API tokens, reset links, and private keys. The harm is *access*: anyone who reads the line can act as the owner. There is never a legitimate reason to log one, and once one is logged, the fix is rotation.
- **Personal and customer data**, such as emails, names, health details, and the content of customers' documents. The harm is *disclosure*, plus the legal obligations that follow it. Some of it has a legitimate diagnostic use, so the goal is to minimize and govern it rather than ban every trace.

A handful of terms get used loosely enough to need pinning down:

- **Redaction** removes the value (`"[REDACTED]"`).
- **Masking** removes part of it (`•••• 4242`).
- **Pseudonymization** replaces it with a consistent stand-in that can't be reversed without extra information, such as a key or a lookup table.
- **Anonymization** makes re-identification impossible by any reasonable means.

The legal difference matters. Under GDPR, pseudonymized data is still personal data. Only genuinely anonymous data falls outside the regulation, and a log line with a stable user ID, an IP address, and a timestamp is rarely anonymous.

## Recognizing the Problem

The fastest diagnosis is a search. Look in your log store for:

- a known test user's email and phone number;
- `password`, `Bearer `, `eyJ` (the start of every JWT), `sk_live_`, `AKIA`, `ghp_`, `xoxb-`, and your own key prefixes.

Hits mean you have the problem. Beyond the search, watch for these signals:

- Request logging records full URLs, raw paths, or all headers.
- Code logs request bodies, whole structs, or `%+v` of domain objects.
- ORM or HTTP-client debug logging is enabled in production.
- DEBUG was turned on "temporarily" somewhere, and nobody knows whether it's still on.
- More people can read the logs than can read the production database.
- Log retention was chosen for debugging convenience, and your deletion workflow doesn't mention logs.
- Your log vendor, or its region, is missing from the subprocessor list you give customers.
- A security questionnaire asks where personal data lives, and the honest answer takes a week.

## How It Works

### Where it gets in

Almost nobody writes `log.Info("password", pw)`. Sensitive data arrives through side doors:

- **URLs.** Query strings carry search terms, reset and magic-link tokens, OAuth authorization codes, and API keys. Raw paths carry them too (`/reset/{token}`, `/patients/by-email/{email}`), which is one more reason 19.1a logs the route template. Proxies, load balancers, and CDNs keep their own access logs with full URLs, outside your application entirely.
- **Headers.** `Authorization`, `Cookie`, `Set-Cookie`, and `X-Api-Key`, usually via a helper that "logs the whole request when something fails."
- **Whole objects.** Request bodies, domain structs, and ORM entities are serialized by reflection, so every field present today and every field added next year is logged.
- **Error messages that echo input.** Validation errors ("invalid phone number +44…"), JSON parse errors that quote the payload, constraint violations, and HTTP client errors that include the URL.
- **Other people's logging.** ORM query logging with bound values (GORM's logger interpolates values by default), HTTP-client wire logging, and the database server's own error log. Error-tracking SDKs may capture request bodies and stack-frame local variables by default (Sentry's Python SDK does), and their built-in scrubbing is a denylist of key names.
- **Convenience fields.** `user_email` on the wide event, added because it saved support a lookup.
- **Memory dumps.** Core dumps and heap dumps contain everything the process held, including decrypted secrets. Treat them as production data.

### Classify, then decide per class

| Class | Examples | In diagnostic logs? |
|---|---|---|
| Secrets | Passwords, session tokens, API keys, reset tokens, OAuth codes, full JWTs, private keys | Never. If one gets in, rotate it. |
| Payment data | Full card number, CVV | Never. PCI DSS forbids storing the CVV after authorization and requires the card number masked, to at most the first six and last four digits. |
| Special-category data | Health details, biometrics, government IDs, precise location | Never. |
| Direct identifiers | Email, phone, name, postal address | Avoid. Use internal IDs instead. |
| Network identifiers | IP address | Where there's a reason (security, abuse, rate limiting per 18.2b), with short retention. It's still personal data. |
| Internal identifiers | `user_id`, `clinic_id`, `booking_id` | Yes. This is what makes logs useful. |
| Customer content | Documents, messages, form payloads | Not by default. |

The internal identifier does most of the work. `patient_id=p_8812` lets support find the patient through the access-controlled database, and the log line alone says nothing about who she is. Erasure also gets easier: once the patient row is deleted, `p_8812` no longer resolves to anyone. That ID is still personal data while the mapping exists, and whether an orphaned ID plus the other fields on the line is sufficiently anonymous is a question for whoever owns compliance (Module 34). It is still a far better position than 14,000 copies of an email address.

### Allowlists beat denylists

The instinctive control is a **denylist**: redact any field named `password`, `token`, `authorization`, or `email`. It fails in three predictable ways.

- **New names.** `pwd`, `passphrase`, `secret_answer`, and `recovery_code` all pass straight through.
- **Nesting.** A rule that inspects keys sees `body`, not `body.password`. The whole object goes through untouched, which the Implementation below shows.
- **Values in the wrong place.** An email typed into a search box lands in a field called `q`. A token lives inside a URL string. Key names can't catch either.

An **allowlist** reverses the default: only explicitly permitted things are logged.

- **Headers:** log `User-Agent`, `Content-Type`, `Content-Length`, and `X-Request-Id`, and nothing else.
- **Query strings:** log the parameter *names*, and values only for approved parameters such as `page`, `limit`, and `sort`. `q=[REDACTED]` still tells you a search happened.
- **Bodies:** never by default. When a failure needs diagnosing, log the body's *shape* (which fields were present, their types and lengths) rather than its contents.

Module 16.4 made the same argument for analytics properties. Logging adds a twist of its own. Log parameter names as a list value (`query_keys: ["q", "page"]`), never as field names. Otherwise a caller who sends `?a1=&a2=&a3=…` creates a new field in your index with every request. Elasticsearch caps each index at 1,000 mapped fields by default, and once the cap is reached, new documents that introduce fields are rejected.

### Redact in layers, most precise first

```
source             logger              agent                 store
types, allowlists  key-based rules     pattern scrubbing     access, retention, region
──────────────────────────────────────────────────────────────────────────────────►
knows meaning      knows field names   knows shapes          limits the damage
needs discipline   misses nesting      misses meaning        of whatever got through
```

**At the source**, a value's type can make leaking hard: a `Sensitive` wrapper whose every serialization prints `[REDACTED]` (see Implementation). Allowlists for requests live here too. This is the only layer that knows what a value *means*.

**In the logger**, a key-based rule catches the obvious names. It's cheap, and it's a denylist, with the weaknesses above.

**In the pipeline**, the agent scrubs by pattern: email shapes, JWTs (three dot-separated segments starting `eyJ`), card numbers that pass a Luhn check, and known key prefixes. Vector's `redact` function, the OpenTelemetry Collector's redaction processor, and vendors' sensitive-data scanners all do this. It's the backstop for code you didn't write, with three limits:

- **It costs CPU** on every line.
- **It produces false positives.** An order number that happens to look like a card number gets mangled.
- **It can't recognize meaning.** No pattern matches "anxious about returning to work."

It also runs *after* the data has left the process. By then the line is already in the agent's disk buffer and in the files where the container runtime writes stdout (under `/var/log/pods` on Kubernetes).

**In the store**, controls limit the damage from whatever gets through. That's the governance section below.

Treat the layers as defense in depth, not alternatives. A team that relies on the pipeline scrubber has handed its privacy posture to a regex.

### Pseudonymize when you need "same person" without "who"

Sometimes the correlation matters and the identity doesn't. Counting failed logins per submitted email to spot credential stuffing (18.2b) is the classic case, because an unknown email has no user ID.

The tempting answer is `sha256(email)`. It's reversible in practice: emails are low-entropy, and anyone holding a list of candidate addresses can hash the list and compare. Use a keyed hash instead, `HMAC-SHA256(key, normalize(email))`, with the key held like any other secret. Rotating the key breaks correlation across the rotation boundary, which is useful: it limits how long any one pseudonym can be linked to activity. Remember that the result is still personal data. Pseudonymization reduces risk; it doesn't remove the data from scope.

Truncation serves a similar purpose for network identifiers: an IPv4 address cut to its /24 or an IPv6 address to its /48 still supports regional analysis.

### Govern what gets through anyway

Assume leaks will happen, and design the store so a leak is survivable.

- **Access parity.** Nobody should read in logs what they can't read in the database. Role-based access, audited queries, separate indexes for security logs, and clinic-scoped views if support needs them (Module 5's isolation, applied to the log store).
- **Retention as the erasure mechanism.** Log stores delete well by time and badly by record. Deleting individual records means expensive delete-by-query jobs in a search index, and rewriting files in an object-storage archive. So design for time-based expiry to be sufficient: if logs hold no direct identifiers, a short retention window may be your whole answer to erasure requests. Write that answer down. Logs that must keep identities longer, like security logs, need their own store, tighter access, and possibly crypto-shredding (16.4).
- **Location and subprocessors.** A hosted log vendor processes your customers' data, and its region counts toward any data-residency promise you've made. Agents can route logs to a store in each region.
- **Every copy.** Inventory the error tracker, the APM tool, the SIEM, archives, backups, and the human copies: log lines pasted into tickets, chat, and downloaded files on laptops. Module 17 made the point about webhook payloads, and it applies equally here: redaction can't be retracted from a system you don't control.

### When a secret leaks

The order matters.

1. **Rotate first.** A secret is compromised the moment it lands somewhere others can read it. Deleting the lines doesn't undo that exposure.
2. **Check exposure.** Find how long the secret sat there and who queried it, using the log store's own audit trail.
3. **Purge** the lines from the store, the archive, and every copy you inventoried.
4. **Close the path** that let it in, and add a test for it (below).

### Test for it

Leaks come from new code paths, so the defense has to run on every change.

**Canary values.** Seed test fixtures with distinctive values: an email like `canary.patient@example.test`, a password, a unique marker string in free-text fields, and the test configuration's API keys. Run the test suite with logging at DEBUG, exercise the *failure* paths as well as the happy ones, and fail the build if any canary appears in the captured output.

**In production**, give synthetic-monitoring accounts (16.3) their own canary values, and run a scheduled search that alerts if one ever appears in the log store. Secret scanners such as gitleaks and TruffleHog can also run over log exports.

## When It's Appropriate

- **Secrets: always.** Every system, from day one. Header redaction and query-string allowlists take an hour to set up and prevent the most damaging class of leak.
- **Regulated data.** Health data, payment data, children's data, and anything covered by HIPAA, PCI DSS, or GDPR's special categories. The intake-form note in the Problem is a reportable incident, not merely untidy logging.
- **B2B products that sign data-processing agreements.** Once a customer asks where their data goes, "and also the logs, for 400 days, in another region" is an answer you'd rather fix than give.
- **Log access broader than database access.** Sixty readers against four is the common shape, and it makes every leaked field sixty times more exposed.
- **Pseudonymization in particular** when a security or abuse use case needs per-identity counting without the identity, like credential-stuffing detection keyed on submitted emails.

## When It's Unnecessary or Overkill

- **A 200-rule scrubbing pipeline for an internal build tool** that handles no personal data. Do the secrets part and stop there.
- **Stripping internal IDs "to be safe."** Logs without `user_id` and `clinic_id` can't answer the questions 19.1a was about. Govern the IDs; don't delete them.
- **Per-field encryption or crypto-shredding for diagnostic logs with 14-day retention.** Time already does the job.
- **A tokenization vault for debug output.** The infrastructure outweighs the risk it addresses.
- **Hashing everything and calling it anonymous.** Unkeyed hashes of emails can be reversed, and keyed ones are still personal data. Hashing that makes a team feel finished is worse than none.
- **Removing IP addresses from security logs.** Abuse investigation and rate limiting need them, and short retention is the proportionate control.

## Trade-offs

- **The redacted field is sometimes the one you needed.** "Did she mistype her email, or does the account really not exist?" Log facts about the value instead: `email_matched_account=false`, `email_len=20`. Even an email's domain can identify someone when the domain belongs to a five-person company.
- **Allowlists add friction.** Every new header, parameter, or field needs a decision, and developers will feel it.
- **Typed redaction only covers the paths it implements.** A new encoder, or a vendor SDK that serializes by reflection, can walk straight past it.
- **Pattern scrubbing costs CPU and accuracy.** It spends agent CPU on every line, mangles identifiers that look sensitive, and gives false confidence about the data it can't recognize.
- **Pseudonymization needs key management.** Rotation breaks correlation, and the output is still regulated.
- **Short retention loses slow investigations.** Security incidents are often discovered months after they began. Security logs need their own, longer, tighter-controlled retention, and that retention has a cost.
- **Restricted access slows incident response.** You'll need a break-glass path, and it needs auditing too.
- **Every control multiplies across copies.** One destination you forgot, such as the error tracker or the APM tool, undoes the rest.

## Alternatives

- **Regulate the log store instead of cleaning the logs.** Customer-managed keys, strict access, residency, and deletion tooling, treating the log store exactly like the database. Some heavily regulated organizations do this. It's expensive, and it accepts the copy rather than preventing it.
- **A restricted sensitive-debug sink.** A separate destination with short retention (hours to days), approval-gated access, and an audit trail, reserved for the rare investigation that genuinely needs payload data. The normal pipeline stays clean.
- **Customer-initiated diagnostics.** A "share diagnostics with support" action that captures detail for one session, with the customer's consent and a clear expiry.
- **Reactive DLP scanning as the primary control.** Vendor scanners that find and mask sensitive data after ingestion. Useful as detection, and weak as prevention for the reasons pattern scrubbing is weak.
- **Schema-level classification.** A data catalog or schema annotations mark fields as sensitive once, and redaction rules are generated for logs, traces, analytics, and exports together. Heavy to adopt, and the only approach that scales across many teams.
- **Audit logs (Modules 24 and 26).** Records of who accessed what legitimately contain identities. They belong in a separate store with its own controls, not in diagnostic logs.

## How to Achieve It

**Level 0 — search.** Run the test-identity and token-prefix searches from *Recognizing the Problem*, and count hits by field.
_Signal you're here:_ nobody has ever run that search.

**Level 1 — stop the secrets.** Redact `Authorization`, `Cookie`, and `Set-Cookie`. Allowlist query parameters, log route templates rather than raw paths, and rotate everything the search found.
_Signal you need it:_ a single credential hit.

**Level 2 — replace identifiers and ban whole objects.** Internal IDs instead of emails, no bodies or struct dumps, `Sensitive` types for the fields that must never print, and ORM and HTTP-client debug logging off in production.
_Signal you need it:_ emails, names, or free text among the hits.

**Level 3 — backstops and tests.** Pattern scrubbing in the agent, canary tests in CI, and a scheduled canary search in production.
_Signal you need it:_ a second leak through a path nobody anticipated.

**Level 4 — govern the store.** Access parity with the database, retention aligned with your deletion policy, residency, the vendor on your subprocessor list, and an inventory of every copy.
_Signal you need it:_ a data-processing agreement, an audit, or your first erasure request.

**Level 5 — classify once, enforce everywhere.** Field classification in schemas driving redaction across logs, traces, and exports, plus a restricted sink for the rare case that needs payloads.
_Signal you need it:_ many teams, many services, or expansion into a regulated market.

## Implementation

**Go again, because Go shows precisely where each defense stops working.** 19.1a's `slog` setup carries over.

First, the leak, and a denylist that looks as if it should stop it:

```go
type IntakeRequest struct {
	Email    string `json:"email"`
	Password string `json:"password"`
	Notes    string `json:"notes"`
	ClinicID string `json:"clinic_id"`
}

opts := &slog.HandlerOptions{
	ReplaceAttr: func(_ []string, a slog.Attr) slog.Attr {
		switch strings.ToLower(a.Key) {
		case "password", "token", "authorization", "email", "notes":
			return slog.String(a.Key, "[REDACTED]")
		}
		return a
	},
}

log.ErrorContext(ctx, "intake failed", "req", req, "err", err)
```

```json
{"level":"ERROR","msg":"intake failed",
 "req":{"email":"jane.doe@example.com","password":"hunter2",
        "notes":"post-surgical ACL reconstruction, anxious about…","clinic_id":"c_31"},
 "err":"Post \"https://sms.example.com/v2/send?api_key=sk_live_4f…\": context deadline exceeded"}
```

`ReplaceAttr` was called with two keys, `req` and `err`, and neither is on the list. The struct was serialized afterward by `encoding/json`, which never consults the rule. The error string came from `*url.Error`, which includes the full URL. Four sensitive values got through without a single redaction.

Second, a type that doesn't know how to print itself:

```go
// Sensitive wraps a value that must never be serialized.
// The field is unexported, so encoding/json can't see it,
// and every formatting path returns the placeholder.
type Sensitive[T any] struct{ v T }

func Hide[T any](v T) Sensitive[T]   { return Sensitive[T]{v: v} }
func (s Sensitive[T]) Reveal() T     { return s.v } // the one deliberate exit; easy to grep for

const redacted = "[REDACTED]"

func (_ Sensitive[T]) LogValue() slog.Value         { return slog.StringValue(redacted) } // slog, top level
func (_ Sensitive[T]) MarshalJSON() ([]byte, error) { return []byte(`"` + redacted + `"`), nil } // nested in JSON
func (_ Sensitive[T]) Format(f fmt.State, _ rune)   { io.WriteString(f, redacted) } // every fmt verb, incl. %+v, %#v
func (_ Sensitive[T]) String() string               { return redacted }

// It still decodes, so request bodies can be unmarshalled into it.
func (s *Sensitive[T]) UnmarshalJSON(b []byte) error { return json.Unmarshal(b, &s.v) }

type IntakeRequest struct {
	Email    Sensitive[string] `json:"email"`
	Password Sensitive[string] `json:"password"`
	Notes    Sensitive[string] `json:"notes"`
	ClinicID string            `json:"clinic_id"`
}
```

Now the same log call writes `"req":{"email":"[REDACTED]","password":"[REDACTED]","notes":"[REDACTED]","clinic_id":"c_31"}`.

> **Aside — each method covers one path, and all four are needed.** `LogValue` only applies where slog resolves values: the top level of an attribute. Nested inside a struct, `encoding/json` takes over, which is what `MarshalJSON` is for. The text handler falls back to `fmt`'s `%+v`, and `fmt` prints unexported fields through reflection unless `Format` intercepts it. Remove any one method and one path leaks. Anything that walks memory by reflection while ignoring these interfaces will still see the value. The type changes the default from "leak" to "redact"; it doesn't make leaking impossible.

> **Aside — the asymmetry is the point, and it will bite.** `Sensitive` decodes but won't encode. Reuse this struct to *call* another API and you'll send `"[REDACTED]"` as the patient's email. Keep inbound and outbound types separate, and call `Reveal()` exactly where the real value must cross a boundary.

The URL leak needs its own fix: move the key into a header, where the provider supports it, or wrap client errors so that the logged form uses only scheme, host, and path.

Third, a test that fails when any of this regresses:

```go
var canaries = []string{
	"canary.patient@example.test",
	"CanaryPassw0rd!",
	"canary-note-7f3a",         // stands in for free text no pattern would catch
	"sk_test_CANARY000000000",  // the SMS key in the test config
}

func TestIntakeFailureLogsNoCanaries(t *testing.T) {
	var out bytes.Buffer
	log := slog.New(slog.NewJSONHandler(&out, &slog.HandlerOptions{Level: slog.LevelDebug}))
	slog.SetDefault(log) // library and stdlib `log` output land in the same buffer

	srv := httptest.NewServer(newApp(log, smsProviderThatTimesOut())) // exercise the error path
	defer srv.Close()

	body := fmt.Sprintf(`{"email":%q,"password":%q,"notes":%q,"clinic_id":"c_1"}`,
		canaries[0], canaries[1], canaries[2])
	http.Post(srv.URL+"/v1/intake?ref="+canaries[0], "application/json", strings.NewReader(body))

	for _, c := range canaries {
		if strings.Contains(out.String(), c) {
			t.Errorf("log output contains canary %q", c)
		}
	}
}
```

> **Aside — run it at DEBUG, on the failure path.** A leak test at INFO on the happy path passes while the Problem's debug line and timeout error both leak. The configuration that matters is the most verbose one anyone can switch on, exercising the path that runs during an incident. `slog.SetDefault` also routes the standard library's `log` package through this handler, so libraries that log via `log.Printf` get checked too. Libraries that write directly to `os.Stderr` still escape it.

## Further Reading

- **OWASP Logging Cheat Sheet**, particularly the "Data to exclude" section. A compact list of what never belongs in logs, and why.
- **OWASP Top 10 (2021), A09: Security Logging and Monitoring Failures.** The other side of the balance: logging too little is also a finding.
- **NIST SP 800-122, _Guide to Protecting the Confidentiality of Personally Identifiable Information_**, and **NIST SP 800-92, _Guide to Computer Security Log Management_.** Classification by impact, and log management as a security function.
- **GDPR Articles 4(5), 5(1)(c) and (e), and 17, with Recital 26.** The definition of pseudonymisation, the data-minimisation and storage-limitation principles, the right to erasure, and why pseudonymized data is still personal data. The **EDPB's Guidelines 01/2025 on pseudonymisation** develop that last point in practical detail.
- **PCI DSS v4.0, Requirement 3.** What may be stored from a payment card, and how it must be masked.
- **OpenTelemetry Collector redaction processor** and **Vector's `redact` function** documentation. Two concrete pipeline scrubbers, with their configuration models.
- **gitleaks** and **TruffleHog.** Secret scanners whose rule sets double as a catalogue of credential shapes worth scrubbing.
- **Go `log/slog` documentation on `LogValuer` and `HandlerOptions.ReplaceAttr`.** Precisely where each hook is applied, which is where the gaps above come from.
- **Public incidents:** Twitter's and GitHub's 2018 disclosures of passwords written to internal logs, and the Irish Data Protection Commission's 2024 fine against Meta over passwords stored in plaintext in internal systems. Useful for making the case internally.

A Java sibling would be worth writing, because Java's leak paths are different and in some ways worse. Records generate a `toString()` that prints every component, and Lombok's `@Data` does the same for ordinary classes, so logging an object is an implicit dump. PgJDBC includes the server's detail line, constraint values and all, in exception messages by default, controlled by its `logServerErrorDetail` property. Hibernate's bind-parameter logging is one logger setting away. The defenses (overridden `toString`, encoder-level masking in logstash-logback-encoder, driver configuration) sit in different places than they do in Go. Not yet written.

---

The habit to carry out of this: whenever data leaves the place where you control it, whether into a log, a trace, an error report, a webhook, or a support ticket, list the controls the original had (who can read it, where it lives, how long it stays, how it's deleted) and check which of them came along. Usually none did, and the copy is where the incident will happen.
