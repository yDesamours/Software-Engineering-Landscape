# A Log Line Is a Record, Not a Sentence

_Module 19.1a — Logging, Monitoring & Observability_

## The Problem

A ticketing API for concert venues. About 300 venues sell through it, and checkout calls an external payment provider. It runs as eight pods at around 400 requests/second, and every pod writes logs the way most services start out: a timestamp, a level, and a sentence.

Thursday, 14:20. Support forwards a ticket. A venue called Northgate says some of its checkouts have been failing "since lunch." The on-call engineer opens the logs.

```
2026-09-10 14:02:11 INFO  Processing order 88213
2026-09-10 14:02:11 INFO  Processing order 88214
2026-09-10 14:02:11 INFO  Payment started
2026-09-10 14:02:12 WARN  Retrying...
2026-09-10 14:02:12 INFO  Payment started
2026-09-10 14:02:21 ERROR Payment failed: timeout
2026-09-10 14:02:21 INFO  Order 88214 confirmed
2026-09-10 14:02:22 ERROR User not found
```

Everything needed to diagnose the incident was written down somewhere. Very little of it can be used.

**Nothing says which venue.** No line mentions Northgate. Order numbers are the only identifier, and turning an order number into a venue takes a database lookup per line.

**Adjacency means nothing.** Two requests were in flight at 14:02:11. Which "Payment started" belongs to order 88213, and which request is retrying? Timestamp order on a busy server interleaves every concurrent request, and across eight pods the engineer is merging eight streams by eye.

**The same event has three spellings.** Searching for payment failures turns up `Payment failed: timeout`, `payment timeout for order 88102`, and `PSP call timed out after 10000ms`. Three developers wrote three phrasings. A regex broad enough to catch all three also catches `Payment failed validation`, which is unrelated. Worse, the alert meant to fire on payment failures matched the text `Payment failed`, and a refactor last week reworded the message in one code path. The alert has been silently blind to that path ever since.

**ERROR has stopped meaning anything.** `User not found` is a 404 on a profile lookup, logged at ERROR about 3,000 times an hour. Nobody reads the ERROR stream anymore, which is how a real failure ran for two hours unnoticed.

**The stack trace is forty events.** The log collector splits on newlines, so each frame of a multi-line stack trace arrives as its own entry, interleaved with other requests' lines.

Two hours in, the answer surfaces. On Tuesday, Northgate's payments were moved to the provider's EU endpoint, and that endpoint was timing out. The fact was in the logs all along, as `using endpoint eu-west for merchant m_4471`. It was one of roughly 200 million lines that day, logged at INFO, and keyed by the provider's merchant ID rather than anything the failure lines contained.

```
what the question needed:                 what the logs held:

  failures WHERE venue = Northgate          "Payment failed: timeout"
           GROUP BY payment endpoint        "using endpoint eu-west for merchant m_4471"
                                            "Processing order 88213"
                                             …no field shared by any two of them
```

The information existed. It was written as prose, for a person reading one line at a time, and the question needed a query.

## What It Is

This is **structured logging**. Every log entry is a record with named, typed fields, usually one JSON object per line, rather than a formatted sentence. The message shrinks to a short, fixed event name, and everything that varies moves into fields.

```json
{"time":"2026-09-10T14:02:21.481Z","level":"ERROR","msg":"payment authorization failed",
 "service":"checkout","version":"4.12.0","pod":"checkout-7f9c-2",
 "request_id":"req_8Hq2Lm","trace_id":"4bf92f3577b34da6a3ce929d0e0e4736",
 "venue_id":"v_northgate","order_id":"ord_88213",
 "psp_endpoint":"eu-west","attempt":2,"duration_ms":10004,"error_type":"timeout"}
```

Every question from the incident is now a filter or a group-by.

One distinction is worth making up front, because the two ideas usually arrive together. **Structured logging** is about the shape of a record where it's written. **Log aggregation** is about where records go afterward: collected from every instance into one searchable store. Either can exist without the other. You can have JSON files that nobody collects, or a central store full of prose. The incident needed both, and structure is the half that has to be fixed in code.

The neighbors that answer overlapping questions (metrics, traces, error trackers, audit logs) are grouped in *Alternatives*.

## Recognizing the Problem

- Investigations start with `grep`, or with `kubectl logs` against one pod at a time.
- An alert or saved search matches on message text, and it has broken at least once when the wording changed.
- Answering "how many X for customer Y in the last hour?" means writing a parser.
- You reconstruct a single request by reading lines with nearby timestamps.
- Stack traces appear as dozens of separate entries in your log tool.
- The ERROR stream fires thousands of times an hour, and nobody reads it.
- One failure produces four ERROR lines, one per layer it passed through.
- A customer pastes a request ID from an error response (7.3b), and you can't search by it.
- Changing the log level requires a redeploy.
- The logging bill grows faster than traffic, and nobody can say which lines cost the most.

## How It Works

### Three layers of fields

The fields in that JSON record come from three places, and each is attached at a different moment:

```
┌─ resource ─────────── service, version, env, pod, region
│                       attached once, at startup
├─ request context ──── request_id, trace_id, venue_id, user_id, route
│                       bound once, at the edge; carried onto every line of the request
└─ event ────────────── order_id, psp_endpoint, attempt, duration_ms, error_type
                        specific to this one line
```

The first two layers are what make lines joinable. They're also what gets forgotten when every call site assembles its own fields. That's why both are attached by infrastructure (the logger's setup and the request middleware) rather than by the code that writes each line.

### Messages are constants

`msg` should be the same string every time the event happens: `"payment authorization failed"`, not `"Payment for order 88213 failed after 10004ms"`. An interpolated message is unique on every occurrence, so it can't be grouped or counted, and it invites people to alert on text.

With a constant message and the variables in fields, you can count the event, group it by any field, and never break a search by rewording a sentence. The cost is that the event name itself is now an interface. Renaming it is a breaking change and should be treated as one.

### A schema, even an informal one

Structure only helps if everyone agrees on names and types. If one service writes `duration_ms`, another `latency`, and a third `took: "1.2s"`, cross-service queries fall apart the same way the prose did. Three rules cover most of it:

- **One name per concept, with the unit in the name.** `duration_ms`, `size_bytes`.
- **One type per field, everywhere.** Search engines like Elasticsearch fix a field's type from the first document they see. If `error` is a string in one service and an object with `type` and `message` in another, one of them is rejected at indexing, usually without anyone being told.
- **Borrow a convention instead of inventing one.** OpenTelemetry's semantic conventions and the Elastic Common Schema both define names for the common fields (HTTP method, status code, error type, user ID). Adopting either costs nothing, and tools that already know those names can use your logs without configuration.

### Levels are a contract with the reader

Levels help only if each one tells the reader what to do. A workable definition:

| Level | Means | Example |
|---|---|---|
| ERROR | This operation failed, and someone on the team may need to act | Payment authorization failed after all retries |
| WARN | Something unexpected happened and was handled; worth noticing if it trends | A retry succeeded; fell back to cached prices |
| INFO | A significant event, or the one-per-request summary | Request completed; order confirmed |
| DEBUG | Detail for a targeted investigation; off in production by default | Cache key computed; provider response headers |

Three rules keep ERROR meaningful:

- **The client's mistake isn't your error.** A 404 or a failed validation is the service working correctly. Record it at INFO in the request summary, or not at all. `User not found` at ERROR is what trained the team to ignore the stream.
- **Retries are WARN until you give up.** Three attempts that end in failure should produce two WARNs and one ERROR, not three ERRORs.
- **Log where you handle, not where you throw.** When every layer logs an error and rethrows it, one failure becomes four ERROR lines with four partial stack traces. Lower layers should wrap the error with context and return it. The layer that decides what happens next (turning it into a response, swallowing it, retrying) logs it once.

The level should also be changeable without a redeploy. Most loggers support a level that can be switched at runtime. The more useful refinement is *scoped* debug: enabling DEBUG for one venue or one flagged request, so that investigating Northgate doesn't multiply log volume for all 300 venues.

### Binding context once, carrying it everywhere

The request ID is the backbone. Generate it at the edge, or accept one from your own gateway. Return it in a response header and in error bodies (7.3b), and bind it into a request-scoped context. From then on, every line written while handling that request carries it.

"Every line" is the hard part, because most of the code writing lines knows nothing about HTTP. There are three ways to get the context to it:

- **Pass it explicitly.** Go threads `context.Context` through every call. Nothing is hidden, and forgetting it is visible in the code.
- **Store it implicitly per request.** Node's `AsyncLocalStorage` and Java's MDC (backed by a `ThreadLocal`). Call sites stay clean, and the context silently disappears at any boundary the runtime doesn't track.
- **Hand down a child logger.** A logger pre-bound with the request's fields, passed along or attached to the request object.

Whichever you choose, context drops at the same boundaries Module 5 found for tenant context: new goroutines and thread pools, callbacks from pooled clients, and background jobs. For jobs, put `request_id` and `trace_id` into the job payload (Module 10) and re-bind them when a worker picks the job up, so the worker's lines join the request that caused them. Across service boundaries the carrier is trace context, which is 19.2b. If you already run tracing, the trace ID can serve as the correlation ID. If customers see a separate request ID, log both.

Two cautions apply to IDs that arrive from outside. First, an `X-Request-Id` header from the public internet is attacker-controlled. Validate its length and character set, or generate your own and record the inbound value in a separate field. Second, plain-text logs have a quieter weakness: a user-supplied value containing a newline can forge a complete fake line, such as `\n2026-09-10 14:05:00 INFO admin login succeeded`. A JSON encoder escapes the newline, so structured logging closes this hole (CWE-117) as a side effect.

### One wide event per unit of work

The incident needed a join between "which endpoint" and "which requests failed." Structured fields make that join possible. A different habit makes it unnecessary.

Instead of scattering a request's facts across many lines, accumulate them while the request runs and write **one line at the end** that holds all of them:

```
many narrow lines                            one wide event

INFO  request received                       INFO  http request
INFO  venue resolved     venue=…               route=/orders/{id}/pay  method=POST
INFO  using endpoint     psp=eu-west           status=502  duration_ms=10112
WARN  retrying           attempt=2             venue_id=v_northgate  plan=pro
ERROR payment failed     error=timeout         psp_endpoint=eu-west  psp_ms=10004
INFO  request completed  status=502            attempt=2  db_queries=4  db_ms=31
                                               cache_hit=false  error_type=timeout
```

Stripe calls these **canonical log lines**, and Honeycomb and others call them **wide events**. One row now answers "what do the failing requests have in common?" Group the failures by `psp_endpoint`, and the Northgate incident becomes a single query.

Two properties of this style are easy to miss.

First, a wide event *welcomes* high-cardinality fields such as venue ID, user ID, and order ID, which are exactly what 16.3 banned from metric labels. Metrics aggregate at write time, so every distinct label value creates a new time series. A log event is stored as written, so a unique value costs only a few bytes.

Second, it doesn't replace every other line. Errors with stack traces, state transitions, and anything that matters partway through a long operation still get lines of their own. The wide event is the line you query first.

### Errors as fields

An error record needs a stable, groupable type (`error_type: "timeout"`), the message, and, for unexpected failures, the stack trace **as a single string field**. Written to stdout as multiple lines, a stack trace turns into dozens of unrelated entries in any collector that splits on newlines.

Grouping the same error across thousands of occurrences, tracking which release introduced it, and noticing that it's new are the job of error tracking, covered in 19.2c.

### Getting logs out of the process

The usual pipeline looks like this:

```
app ──JSON lines──► stdout ──► agent on each node ──► buffer ──► log store ──► query UI
                               (Fluent Bit, Vector,    (memory,    (Elasticsearch,
                                OTel Collector)         disk)       OpenSearch, Loki,
                               parse · add pod and                  ClickHouse, a vendor)
                               region · filter ·
                               redact · sample
```

The application writes to stdout and knows nothing about where logs end up. That's the Twelve-Factor App's rule, and a good one: the app never blocks on, authenticates to, or retries against the log backend. The agent adds infrastructure fields the app can't know (node, cluster, region) and can filter or scrub records before anything leaves the machine.

Logging is still I/O on the request path, though. A synchronous logger writing to a slow pipe stalls the request that's logging. An asynchronous logger buffers in memory, and loses that buffer if the process crashes, which means losing the lines you'd most want to read. Further down, some buffer between the app and the store fills up during an incident, and the pipeline faces the same choice as any system under backpressure (9.1b): block the producer, drop records, or spill to disk. Most agents spill to disk and then drop. Find out which yours does before the day it matters.

The store determines what queries cost. Engines that index every field, like Elasticsearch and OpenSearch, make arbitrary searches fast and large volumes expensive. Loki indexes only a small set of labels and scans the rest, which is cheap to store and slower for ad-hoc searches. Its labels also carry the same cardinality limit as metrics, so `venue_id` belongs in the JSON body, never in a Loki label. Columnar stores designed for wide events sit between the two. Choosing among them is 19.3a.

### Volume is a design decision

Volume is roughly requests × lines per request × bytes per line, and all three grow unless someone pushes back. The levers, roughly in order of how much they save:

- **Don't emit what nobody reads.** DEBUG-grade detail logged at INFO is the most common waste. Not emitting a line also saves the CPU spent serializing it.
- **Write fewer, wider lines.** One 1.5 KB event usually costs less than twelve 300-byte lines, because JSON repeats every key and every resource field on every line.
- **Sample the unremarkable requests.** Keep every error and every slow request, and keep 1 in 10 (or 1 in 100) of the fast successful ones. Record the rate in a `sample_rate` field so counts can be scaled back up.
- **Rate-limit repeating lines.** A line inside a retry loop can multiply volume a hundredfold during an outage, which is exactly when the pipeline is already strained.
- **Tier retention.** Keep seven days searchable and ninety days in cheap archive, and require a reason for anything longer. What the logs *contain* also constrains retention, which is 19.1b.

## When It's Appropriate

- **More than one instance.** Eight pods means eight streams, each with interleaved concurrent requests. Request IDs and a central store turn a manual merge into a filter.
- **Multi-tenant products with a support team.** With 300 venues and tickets that each name one of them, a venue ID on every line (bound once, from Module 5's tenant context) is the difference between one query and an afternoon.
- **Any concurrent server.** Even a single process at 50 requests/second interleaves lines enough that adjacency tells you nothing.
- **Requests that fan out into background work.** An import that enqueues 2,000 jobs needs the originating request ID in every payload, or job failures can't be traced back to the upload that caused them.
- **Public APIs that return request IDs.** Once customers can paste an ID into a ticket, you need to find it in seconds.
- **Wide events in particular:** when incidents keep coming down to "what do the bad requests have in common?", whether that's a region, a plan, a feature flag, or a dependency endpoint.

## When It's Unnecessary or Overkill

- **CLI tools and scripts a person watches.** Readable text is the right output. Most loggers can switch between text and JSON by configuration, so use text locally and JSON in production. Structure is the storage format, not necessarily the display format.
- **A full aggregation stack for one small service.** Your platform's built-in log viewer, which already parses JSON, is enough until there are several services or several people debugging them.
- **An organization-wide log schema before a second service exists.** Pick a convention, use it, and formalize it when there's someone to disagree with.
- **Wide events with hundreds of fields nobody queries.** Every field is paid for on every request.
- **Logs as your metrics system.** Counting requests by scanning logs to draw a dashboard is slow and expensive. The metrics in 16.3 do the same job for a fraction of the cost.
- **Application logs as an audit trail.** Diagnostic logs are sampled, dropped under pressure, and deleted on a schedule. That's correct for diagnostics and disqualifying for records that must be complete.

## Trade-offs

- **Bytes.** JSON repeats every key on every line, and the resource fields repeat too. Expect lines two to three times larger than terse text. Compression helps in storage, but not with the agent's CPU or the network.
- **Raw readability.** `kubectl logs` now shows walls of JSON. Developers need a pretty-printer locally and `jq` in their muscle memory.
- **The schema is an API.** Renaming a field breaks saved searches, alerts, and dashboards just as silently as rewording a message did. The problem has moved, not vanished, and it needs an owner.
- **Type conflicts between services** break indexing, and the symptom is usually a field that quietly stops being searchable.
- **Context propagation is a discipline, and its failures are silent.** A goroutine or job that drops the context writes lines that are perfectly valid and impossible to join.
- **More context means more personal data.** Every field you add is another place a user ID, an email address, or a token can end up. That's the subject of 19.1b.
- **Synchronous logging adds latency, and asynchronous logging loses the last lines on a crash.** Flush on shutdown, and know which trade your logger made.
- **Wide events arrive late.** They're written when the request ends. A request that hangs, or a process that dies mid-request, writes nothing. Timeouts and traces cover that gap, and a start line for long operations helps.
- **Sampling discards rare successes.** The one request that succeeded strangely is often the one you later need. Sample with a recorded rate, and keep anything unusual.
- **It's a standing bill.** Log volume grows with traffic, and logs are often the largest line in an observability budget.

## Alternatives

- **Unstructured text, parsed at ingest.** Grok patterns or regex parsers in the pipeline turn prose into fields. This is the right answer for software you can't change (NGINX, PostgreSQL, a vendor appliance) and a fragile one for your own code, where every reworded message breaks a parser.
- **logfmt.** `level=error msg="payment authorization failed" venue_id=v_northgate duration_ms=10004`. It's structured, readable by eye, and widely supported; Heroku popularized it, and Loki parses it natively. A legitimate middle ground, weaker than JSON at nesting and types.
- **Metrics (16.3).** For anything you want to count, graph, or alert on continuously. Cheaper and faster than log queries, and unable to hold per-request detail.
- **Distributed tracing (19.2b).** Records the causal structure and timing of one request across services. Span attributes and span events can replace many log lines, and some teams make traces their primary record, keeping logs for what happens outside a request.
- **Error tracking (19.2c).** For exceptions: grouping, deduplication, release tracking, and alerting on new errors, all of which log search does poorly.
- **Product analytics events (Module 16).** Different consumers, different retention, and different correctness requirements. Don't build a product dashboard on diagnostic logs.
- **Audit logs (Modules 24 and 26).** For who-did-what records that must be complete, tamper-evident, and retained on a legal schedule. They need a separate path that is deliberately not lossy.

## How to Achieve It

**Level 0 — write down the questions your last incident couldn't answer.** "Which tenant?" "Which endpoint?" "Which request?" Each answer is a field you're missing.
_Signal you're here:_ the incident review says "it took a while to find."

**Level 1 — switch the output to JSON and add resource fields.** Most logging libraries do this through configuration. Keep every existing message, write to stdout, and let the platform collect.
_Signal you need it:_ you're grepping more than one instance.

**Level 2 — request IDs at the edge.** Bind them to request context, return them to clients, and copy them into job payloads. Fix the goroutine, thread-pool, and job boundaries as you find them.
_Signal you need it:_ interleaved lines, or a support ticket with an ID you can't search for.

**Level 3 — make levels mean something.** Write the level contract down, move 4xx responses out of ERROR, remove log-and-rethrow, and make the level changeable at runtime.
_Signal you need it:_ nobody reads the ERROR stream.

**Level 4 — a shared schema and one wide event per request.** Adopt OpenTelemetry or ECS names, make messages constant, and move alerts from text matching to field queries, or to metrics.
_Signal you need it:_ a second team, a broken saved search, or an incident that came down to a group-by.

**Level 5 — manage volume and connect the signals.** Add sampling with recorded rates, retention tiers, per-event cost attribution, and a `trace_id` on every line so you can move from a log line to its trace.
_Signal you need it:_ the bill, or an investigation that bounced among three tools with no shared key.

## Implementation

**Go, with the standard library's `log/slog`.** Go makes context explicit, which makes it the clearest place to see what a structured logger actually does, and slog has one behavior that surprises almost everyone.

The setup attaches resource fields once and exposes the level as a variable that can change at runtime:

```go
var level = new(slog.LevelVar) // INFO by default; an admin endpoint can call level.Set

func newLogger(version string) *slog.Logger {
	json := slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: level})
	return slog.New(ctxHandler{json}).With(
		"service", "checkout",
		"version", version,
		"pod", os.Getenv("POD_NAME"),
	)
}
```

Here's the surprise. `logger.InfoContext(ctx, ...)` passes the context to the handler, and **the built-in handlers ignore it**. Nothing stored in `ctx` reaches the output unless a handler you wrote puts it there. Request context therefore needs a small wrapper:

```go
type ctxKey struct{}

type reqState struct {
	mu    sync.Mutex
	attrs []slog.Attr // bound at the edge, plus anything added along the way
	debug bool        // this request (or its venue) is flagged for DEBUG
}

func stateFrom(ctx context.Context) *reqState {
	s, _ := ctx.Value(ctxKey{}).(*reqState)
	return s
}

type ctxHandler struct{ slog.Handler }

func (h ctxHandler) Enabled(ctx context.Context, l slog.Level) bool {
	if s := stateFrom(ctx); s != nil && s.debug {
		return true // scoped debug: one request, not the whole fleet
	}
	return h.Handler.Enabled(ctx, l)
}

func (h ctxHandler) Handle(ctx context.Context, r slog.Record) error {
	if s := stateFrom(ctx); s != nil {
		s.mu.Lock()
		r.AddAttrs(s.attrs...)
		s.mu.Unlock()
	}
	return h.Handler.Handle(ctx, r)
}

// Without these two, logger.With(...) returns the inner handler and the wrapper vanishes.
func (h ctxHandler) WithAttrs(a []slog.Attr) slog.Handler { return ctxHandler{h.Handler.WithAttrs(a)} }
func (h ctxHandler) WithGroup(n string) slog.Handler      { return ctxHandler{h.Handler.WithGroup(n)} }

// Annotate adds fields to the current request. Every later line gets them,
// and so does the wide event at the end.
func Annotate(ctx context.Context, attrs ...slog.Attr) {
	if s := stateFrom(ctx); s != nil {
		s.mu.Lock()
		s.attrs = append(s.attrs, attrs...)
		s.mu.Unlock()
	}
}
```

> **Aside — calls without `Context` lose everything.** `logger.Info(...)` and the package-level `slog.Info(...)` hand the handler `context.Background()`, so those lines carry no request ID. They're valid and unjoinable. A lint rule catches this more reliably than code review does; sloglint, which ships with golangci-lint, can require the `Context` variants.

The middleware binds the request ID and writes the wide event when the request finishes:

```go
func Observe(log *slog.Logger, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()

		id := r.Header.Get("X-Request-Id")
		if !validRequestID(id) { // from the internet, this header is attacker-controlled
			id = newRequestID()
		}
		w.Header().Set("X-Request-Id", id)

		s := &reqState{attrs: []slog.Attr{slog.String("request_id", id)}, debug: debugFlagged(r)}
		ctx := context.WithValue(r.Context(), ctxKey{}, s)
		sw := &statusWriter{ResponseWriter: w, status: http.StatusOK}

		defer func() {
			dur := time.Since(start)
			lvl, rate := slog.LevelInfo, 1 // keep every failure and every slow request
			switch {
			case sw.status >= 500:
				lvl = slog.LevelError
			case dur < 2*time.Second:
				rate = 10 // fast and fine: keep 1 in 10
				if rand.IntN(rate) != 0 {
					return
				}
			}
			// The route template (/orders/{id}/pay, never the raw path) and the
			// venue were Annotated by the router and tenant middleware downstream.
			log.LogAttrs(ctx, lvl, "http request",
				slog.String("method", r.Method),
				slog.Int("status", sw.status),
				slog.Int64("duration_ms", dur.Milliseconds()),
				slog.Int("sample_rate", rate),
			)
		}()

		next.ServeHTTP(sw, r.WithContext(ctx))
	})
}
```

> **Aside — this line lies about panics.** If the handler panics, the deferred function still runs, with `status` still at its default of 200, so the wide event records a success. net/http then recovers the panic and writes its own unstructured line. Recover in the middleware, record `status=500` with the stack as a field, and then re-panic or respond. A request that *hangs* has the opposite problem: its deferred line is never written at all.

> **Aside — sampling one line creates orphans.** This sampler drops only the summary. A WARN written mid-request is still kept, so a sampled-out request can leave a line whose summary doesn't exist. Deciding once at the start and applying the decision to every line is consistent, but at the start you don't yet know whether the request will fail. Deciding at the end is informative but too late for lines already written. That tension is head versus tail sampling, and it returns in 19.3a.

Deeper in the call stack, code adds facts and returns errors instead of logging them:

```go
func (c *Checkout) authorize(ctx context.Context, o Order) error {
	ep := c.psp.EndpointFor(o.VenueID)
	Annotate(ctx, slog.String("psp_endpoint", ep.Name))

	start := time.Now()
	err := c.psp.Authorize(ctx, ep, o)
	Annotate(ctx, slog.Int64("psp_ms", time.Since(start).Milliseconds()))

	if err != nil {
		// No log here. Wrap and return; the layer that turns this into a
		// response logs it once, with error_type as a field.
		return fmt.Errorf("authorize order %s via %s: %w", o.ID, ep.Name, err)
	}
	return nil
}
```

With that one `Annotate` call, the Northgate incident is a group-by on `psp_endpoint`.

> **Aside — goroutines that outlive the request.** A handler that starts `go sendReceipt(ctx, o)` passes a context that's cancelled as soon as the response is written. `context.WithoutCancel(ctx)` (Go 1.21+) keeps the values, including the request ID, without the cancellation. Anything that goroutine `Annotate`s after the response is missing from the wide event, which has already been written. Work that must survive a restart belongs in a job with the request ID in its payload (Module 10).

## Further Reading

- **Go blog, "Structured Logging with slog"** (Jonathan Amsterdam). The design rationale for slog: attributes, handlers, and why the standard library took this shape.
- **"A Guide to Writing slog Handlers"** (in the `golang/example` repository). Covers the wrapper handler above properly, including `WithGroup` semantics and record ownership.
- **Stripe blog, "Fast and flexible observability with canonical log lines"** (Brandur Leach). The origin of the one-line-per-request habit, with the queries it makes possible.
- **_Observability Engineering_** (Charity Majors, Liz Fong-Jones, George Miranda; O'Reilly). The case for wide, high-cardinality events as the primary record, and where that view departs from classic logging.
- **The Twelve-Factor App, "XI. Logs."** Logs as event streams written to stdout, with routing left to the environment.
- **OpenTelemetry Logs Data Model** and **OpenTelemetry semantic conventions.** A vendor-neutral record shape and shared field names. Worth adopting before inventing your own.
- **Elastic Common Schema (ECS) reference.** The other widely used field convention, with good guidance on types.
- **Grafana Loki documentation, label best practices.** Why labels must stay low-cardinality, and where high-cardinality fields belong instead.
- **OWASP Logging Cheat Sheet** and **CWE-117 (Improper Output Neutralization for Logs).** What to log for security purposes, and the log-forging attack that structured encoding closes.
- **Dave Cheney, "Let's talk about logging."** A deliberately contrarian argument that only two levels are needed. Useful for testing whether your level contract earns its complexity.

A TypeScript sibling would be worth writing, because Node inverts this article's main failure mode. With Pino and `AsyncLocalStorage`, context is implicit, so "forgot to pass `ctx`" can't happen. What happens instead is that context silently vanishes when a library resumes work from a callback queue the runtime doesn't track, and call sites give no hint of it. The same wide-event design would need a different set of defenses. Not yet written.

---

The habit to carry out of this: before writing a log line, write the query that will find it. If the query needs a regex, the line is prose. If it needs a join, the missing field belongs on the line. And if no query would ever look for it, the line probably shouldn't be written.
