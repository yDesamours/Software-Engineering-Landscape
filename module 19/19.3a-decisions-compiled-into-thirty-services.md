# Decisions You Compiled Into Thirty Services

_Module 19.3a — Logging, Monitoring & Observability_

## The Problem

A shipment-tracking platform for freight forwarders. Thirty services in three languages, built over five years. Each was instrumented with whatever was current when it was written:

```
                    where telemetry goes      how much is kept     what gets removed    format
billing (Java)      vendor APM agent          vendor default       nothing              proprietary
tracking (Node)     vendor tracing SDK        5% head sampling     3 regexes            proprietary
customs-gw (Go)     vendor tracing SDK        5% head sampling     2 different regexes  proprietary
routing (Go)        Prometheus scrape         —                    —                    exposition format
…                   Fluentd → Elasticsearch,  …                    …                    …
                    some to CloudWatch
```

Four events in one quarter show what that table costs.

**The renewal.** The observability vendor's contract comes up for renewal at 2.4 times the previous price. The team wants to evaluate an alternative, but thirteen services use the vendor's proprietary SDK, and re-instrumenting them is estimated at two quarters of work. They renew. The lock-in wasn't in the contract. It was in the code.

**The missing trace.** A customs-API integration fails on 0.2% of requests. In the worst hour, about 400 shipments fail. Head sampling at 5% kept roughly 20 of those traces, and not the one belonging to the customer who escalated. Two services sample independently, so several of the traces that were kept have holes in them.

**The debug deploy.** A deploy of `customs-gw` accidentally ships with DEBUG logging enabled. Log volume from that service rises thirtyfold for nine hours. Rolling back is blocked by a database migration, and the logging configuration can only change through a redeploy. The month's log bill rises by $18,000.

**The privacy review.** After an audit (19.1b's search), the team agrees on scrubbing rules. Applying them means changes in thirty services, in three languages, feeding two log stores. Six weeks later, four services still aren't done.

In all four cases, the problem wasn't the instrumentation. Each service correctly produced telemetry. The problem was that every decision *about* that telemetry had been compiled into each service: where it goes, how much of it is kept, what's removed from it, and what format it's in. Changing any of those decisions required a coordinated code change across thirty codebases.

## What It Is

The fix is a **telemetry pipeline**: a layer between the code that *produces* telemetry and the systems that *store* it. Services emit logs, metrics, and traces in a vendor-neutral format. The pipeline receives them, processes them (batching, enriching, filtering, redacting, sampling, transforming), and routes them to one or more backends.

The **OpenTelemetry Collector** is the reference implementation, and **OTLP** (the OpenTelemetry Protocol) is the vendor-neutral format. Vector, Fluent Bit, and Grafana Alloy (which is built on the Collector) fill the same role, and most vendor agents now accept OTLP as input.

The complete **observability stack** is this pipeline plus the backends that store each signal, the query and visualization layer, and alerting (19.3b).

One disambiguation, because the name causes confusion: **OpenTelemetry is not a backend.** It's a specification, a set of APIs and SDKs, a wire protocol, a set of attribute conventions, and the Collector. It stores nothing. Prometheus, Loki, Tempo, Jaeger, Elasticsearch, and the commercial vendors store and query what OpenTelemetry produces.

The maturity of each signal varies. Traces and metrics are stable across the major SDKs. Logs usually enter OpenTelemetry through bridges from existing logging libraries rather than through a new logging API, and SDK support varies by language. A profiling signal is in development.

## Recognizing the Problem

- Changing your observability vendor means changing application code.
- Nobody can say what telemetry costs per service, or per team.
- Stopping a noisy service's telemetry requires redeploying that service.
- Scrubbing rules, sampling rates, or resource attributes are implemented separately in each service, and they differ.
- Rare failures are missing from your sampled traces.
- Traces have holes because services make their own sampling decisions.
- Telemetry was lost during an incident, and nobody noticed until they went looking for it.
- Security wants a copy of certain logs, and the only way to provide it is a second agent on every host.
- A metrics or logs bill jumped, and finding the source took days.

## How It Works

### The shape

A typical Kubernetes deployment has two tiers of Collectors between the services and the backends:

```
 services — OTel SDKs, or existing logging libraries writing to stdout
     │  OTLP (gRPC :4317, HTTP :4318), to an agent on the same node
     ▼
 ┌─ agent Collector (one per node) ──────────────────────────────────────┐
 │  receive quickly · add pod, namespace, node · tail container logs      │
 │  scrape Prometheus endpoints · limit memory · batch · queue to disk    │
 └────────────────────────────────────────────────────────────────────────┘
     │  OTLP, traces routed by trace ID
     ▼
 ┌─ gateway Collectors (a scaled pool) ──────────────────────────────────┐
 │  central policy: redact · filter · derive metrics from spans          │
 │  tail sampling · route by team or tenant · attribute cost              │
 └────────────────────────────────────────────────────────────────────────┘
     │               │                │                 │
     ▼               ▼                ▼                 ▼
  metrics          logs            traces       archive / SIEM / second vendor
  backend          backend         backend
```

Inside a Collector, **receivers** accept data, **processors** transform it, and **exporters** send it. They're wired into a **pipeline** for each signal. **Connectors** join pipelines together, for example by turning spans into metrics. The Collector ships as a core distribution and a much larger *contrib* distribution, and you can build a slimmer one containing only the components you use.

### Two tiers, two jobs

**The agent** runs close to the application, usually as one pod per node, sometimes as a sidecar. Services export to it over the local network, so exporting stays cheap and fast even when the backend is slow. The agent knows things the application doesn't (which pod, namespace, deployment, and node produced the data) and attaches them. It's also where host metrics are collected, container log files are tailed, and existing Prometheus endpoints are scraped, so services that haven't adopted OpenTelemetry still join the pipeline.

**The gateway** is a central pool of Collectors, and it's where cross-cutting policy lives: redaction, filtering, routing, sampling, and cost attribution. A policy change becomes a configuration deploy to one pool rather than a code change to thirty services. The debug deploy from the Problem becomes a filter rule applied in minutes. The scrubbing project becomes a single pull request, with 19.1b's caveat that pipeline scrubbing is a backstop, not the primary defense.

Small systems often skip the gateway, and some skip the agent too, exporting from the SDK directly to a backend. That's fine until the first cross-cutting decision needs to change.

### What the middle is for

- **Protection.** A memory limiter runs first in every pipeline and refuses data before the Collector runs out of memory. Batching runs near the end and reduces the number of requests sent to backends.
- **Enrichment.** Kubernetes metadata, cloud region, and deployment environment, attached consistently rather than hand-coded per service.
- **Redaction and filtering.** One place to apply 19.1b's pattern scrubbing, drop known noise, or remove an attribute everywhere at once.
- **Normalization.** Renaming attributes so that services on different semantic-convention versions (19.2b) can be queried together.
- **Volume control.** Dropping DEBUG logs from one service, rate-limiting a noisy source, and sampling.
- **Derivation.** Computing request, error, and duration metrics (16.3's RED) from spans, and building service dependency graphs from spans, so those views exist even for services with no metrics instrumentation.
- **Routing.** Sending security-relevant logs to the SIEM, sending one team's data to its own tenant, or sending everything to two vendors during a migration so you can compare them.

Order matters within this list. Derived metrics must be computed **before** sampling, from 100% of spans. Otherwise they count only the traces that happened to be kept, and every rate and percentile they produce is quietly wrong.

### Sampling: head, tail, and where each belongs

19.2b introduced **head sampling**: the decision is made once, at the root span, and passed downstream. It's cheap and consistent, and it's blind to what happens next, so it discards errors and slow requests at the same rate as everything else. That's the Problem's missing trace.

**Tail sampling** waits until a trace is complete, then decides:

```
spans arrive ──► buffer, grouped by trace ID ──► wait (e.g. 30s) ──► apply policies ──► keep or drop
                                                                         │
                                            any error?  ──────────── keep
                                            root span > 2s? ──────── keep
                                            watched tenant? ──────── keep
                                            everything else ──────── keep 5%
```

The costs are real, and they're easy to underestimate:

- **It saves storage, not instrumentation.** Services must export every span to the gateway so the sampler can see them. CPU and network costs of generating and sending 100% of spans remain. If that cost is the problem, only head sampling helps.
- **Memory.** The buffer holds every span of every in-progress trace for the whole wait. At 20,000 spans per second with a 30-second wait and about 1 KB per span, that's roughly 600 MB of buffered spans spread across the gateway pool.
- **Every span of a trace must reach the same gateway instance.** Ordinary load balancing spreads a trace's spans across instances, and each instance then sees fragments. The agent tier needs a trace-ID-aware load balancer, and scaling the gateway pool reshuffles which instance owns which traces.
- **Late spans miss the decision.** A span that arrives after the wait (from a slow consumer, or a long asynchronous step) gets decided separately, or orphaned. Long-running traces need a longer wait, which means more memory.
- **The kept set is biased by design.** It over-represents errors and slow requests, so rates computed from sampled traces are wrong. Record the sampling probability on kept data so it can be reweighted, and take rates from metrics (derived before sampling, as above).
- **Traces show up later.** A trace becomes queryable only after the decision wait has passed.

The two methods combine in a specific way: **a head sampler that drops data prevents the tail sampler from ever seeing it.** Once a tail sampler exists, 19.2b's 10% head sampler usually becomes "keep everything," with the reduction happening at the gateway. If generating 100% of spans is unaffordable, keep a head rate and accept that rare errors will sometimes be missed.

Logs have a sampling question of their own, left open in 19.1a. A practical policy is to keep every log at WARN and above, and keep lower-severity logs only when their `trace_sampled` flag says the trace was kept. That way, a trace you can open still has its logs.

### The pipeline is production infrastructure

Once telemetry flows through Collectors, their reliability becomes your visibility.

**Where data waits.** The SDK buffers in memory, and that buffer dies with the process. The agent can queue to disk, so a restart or a slow gateway doesn't lose data. The gateway queues again before each backend. Each queue has a size limit and a policy for what happens when it's full.

**Telemetry fails open.** When the pipeline falls behind, the memory limiter refuses data, receivers return errors, and SDKs drop what they can't send. That's deliberate: telemetry must never block the application. The consequence is that the pipeline's failures are silent, and a dashboard with no data looks remarkably like a dashboard with no errors.

**Watch the watcher.** Collectors expose their own metrics, including accepted, refused, and failed-to-send counts, and queue sizes (`otelcol_exporter_send_failed_spans`, `otelcol_exporter_queue_size`, and so on). Alert on them through a path that doesn't depend on the pipeline being healthy. A dead-man's-switch alert, which fires when an expected signal *stops* arriving, is the standard tool, and it's covered in 19.3b.

**Don't share fate.** An observability stack running in the same cluster and region as the systems it observes goes down with them, at exactly the moment you need it. Keep at least alerting and meta-monitoring somewhere else.

**Size for incidents, not for normal days.** Errors produce more logs, retries produce more spans, and engineers switch on DEBUG. Telemetry volume peaks during incidents, so a pipeline sized for an average Tuesday drops data during the outage.

### Backends: what each signal needs from storage

**Metrics** need a time-series database. Prometheus is the common starting point: it pulls (scrapes) metrics, stores them locally on one node, and typically keeps a couple of weeks. Long retention and high availability come from Thanos, Cortex, Grafana Mimir, VictoriaMetrics, or a managed service. Prometheus 3.0 can also ingest OTLP directly. One pitfall worth knowing is **temporality**. Prometheus expects cumulative counters, some vendors prefer delta counters, and the pipeline sometimes has to convert between them. The cardinality constraints from 16.3 apply to every one of these backends.

**Logs** need a store whose indexing matches how you query, as 19.1a outlined:

- **Arbitrary search across many fields:** a full-index engine such as Elasticsearch or OpenSearch. Fast for any query, and expensive at volume.
- **Filtering by service and time, then scanning:** a label-indexed store such as Loki. Cheap to store, and slower for ad-hoc searches.
- **Aggregations over wide events:** a columnar store, typically built on ClickHouse.
- **Cloud-native stores** such as CloudWatch Logs and Cloud Logging, which trade flexibility for zero operation.

**Traces** raise a different question: do you mostly *find traces by ID* (from a log line, an exemplar, or an error report), or do you need to *search spans by attribute*? Lookup by ID is cheap. Grafana Tempo was designed around it, storing traces in object storage, and has since added attribute search through its TraceQL query language. Rich attribute search costs more storage and indexing, which is what Jaeger with an Elasticsearch backend, columnar stores, and most commercial products provide.

**Whole-stack choices** fall into three groups: a commercial vendor that covers all signals in one product; a self-hosted open-source stack (the Grafana family of Loki, Grafana, Tempo, and Mimir is a common combination); or a mix, such as self-hosted metrics with vendor traces. The factors that decide it:

| Factor | Question to ask |
|---|---|
| Operating capacity | Can the team run stateful storage at your volume, including upgrades and incidents? That's a team's work, not a side project. |
| Query patterns | Mostly known dashboards, or open-ended investigation? |
| Correlation | How easily can you move from a metric to a trace to its logs? |
| Pricing model | What does it charge for, and how will that grow with you? |
| Residency and retention | Where does the data live, and for how long, per signal? |

Pricing deserves a closer look, because each model penalizes a different kind of growth. **Per-host** pricing penalizes many small nodes. **Per-GB ingested** penalizes verbose logs. **Per-GB indexed** penalizes searchability. **Per custom metric or active series** penalizes cardinality (16.3). **Per user seat** discourages giving everyone access, and incidents go better when everyone has access. The Problem's 2.4× renewal came from a pricing model interacting with growth that nobody had modeled.

### Cost control as a pipeline feature

With a pipeline in place, cost becomes something you can manage instead of something that happens to you:

- **Attribute usage** by `service.name` and team at the gateway, so every bill can be traced back to its sources.
- **Set per-team budgets,** with automated guardrails: a service that exceeds its log budget gets its DEBUG logs dropped and its owners notified.
- **Tier storage.** Keep a short hot window in the expensive backend, and archive raw OTLP to cheap object storage so it can be reloaded for an investigation or an audit.
- **Set retention per signal,** and per environment. Staging rarely needs 30 days of traces.

## When It's Appropriate

- **More than a handful of services, or more than one language.** Instrument once with OpenTelemetry, and set policy in one place instead of thirty.
- **A vendor migration, planned or possible.** Sending the same data to both vendors for a month is how you compare them honestly, and it's only a configuration change once a pipeline exists.
- **Rare outcomes that matter.** When 0.2% of requests fail and those are the traces you need, tail sampling is the tool.
- **Cost pressure.** Attribution, filtering, and tiering all live in the pipeline.
- **Data governance.** One redaction point, one routing point for security logs, and residency enforced by routing.
- **Kubernetes.** An agent on each node supplies pod and deployment metadata that applications can't easily provide for themselves.

## When It's Unnecessary or Overkill

- **One service, one vendor, modest volume.** Exporting from the SDK directly to the backend over OTLP is a legitimate architecture. Add a Collector when the first cross-cutting decision appears.
- **Tail sampling at low volume.** At 50 requests per second, keep every trace.
- **Self-hosting the full stack for a small team at small scale.** Operating stateful storage has a large fixed cost, and a managed backend is usually cheaper until volume is substantial.
- **A message queue such as Kafka between Collector tiers** before the volume or the number of consumers requires it. Some very large organizations need it; most don't.
- **Permanent dual-shipping "just in case."** It doubles cost for a benefit that only exists during a migration.
- **"Single pane of glass" as a goal in itself.** Consolidating tools helps when moving between signals is actually slowing investigations, not merely because fewer tools sounds tidier.

## Trade-offs

- **Another critical system to run,** and its failures are silent by design.
- **Added delay.** Telemetry takes longer to reach backends, and tail-sampled traces appear only after the decision wait.
- **Tail sampling is expensive in its own ways.** Memory, trace-aware load balancing, late spans, biased data, and no reduction in instrumentation cost.
- **Configuration is code without tests.** A filter with a wrong condition drops data silently. Collector configuration deserves review, version control, and a test environment that sends known data through it.
- **Component maturity varies.** Contrib components carry individual stability levels, and a component in development can change or be removed.
- **Neutral instrumentation reduces lock-in without eliminating it.** Dashboards, alert rules, saved queries, and the team's familiarity with a query language are all backend-specific, and they are often the larger part of a migration.
- **OpenTelemetry itself keeps evolving.** Semantic conventions get renamed, and SDK maturity differs by language and signal.
- **Central policy creates a central team.** Every team now depends on the people who own the gateway configuration, and that team can become a bottleneck.
- **Migrations cost double for a while.** Sending everything to two backends means paying for both.

## Alternatives

- **Direct export from SDKs** to a single backend. No pipeline to run, and every policy decision lives in application configuration.
- **Vendor agents.** Polished, deeply integrated, and tied to one vendor, although many now accept OTLP, which softens the tie.
- **Other pipeline tools.** Vector and Fluent Bit are strong on logs and increasingly handle other signals. Grafana Alloy packages the Collector with Grafana-oriented defaults. Commercial telemetry pipelines focus on routing and cost reduction across many destinations.
- **A message queue as the telemetry backbone.** At very large scale, a queue between tiers decouples producers from many consumers and absorbs bursts, at the cost of running it.
- **An all-in commercial platform.** One agent, one product, and one bill, with the least operational work and the most dependence on a single vendor.
- **A single wide-event store** (19.1a) instead of three separate backends. Traces, logs, and metrics become views over one kind of rich event, which removes most of the correlation problem and changes the cost model.

## How to Achieve It

**Level 0 — inventory.** For every service, list each signal, the library producing it, its destination, and its monthly cost.
_Signal you're here:_ nobody can say what telemetry costs by service.

**Level 1 — new instrumentation in OpenTelemetry, through a Collector that changes nothing.** New services use the OpenTelemetry SDKs and export OTLP to a Collector, which forwards to your current backends unchanged.
_Signal you need it:_ the next new service, or the next vendor renewal.

**Level 2 — an agent tier that protects and enriches.** A memory limiter, batching, disk-backed queues, Kubernetes metadata, container log collection, and scraping of existing Prometheus endpoints. Move redaction and filtering here, and monitor the pipeline through an independent path.
_Signal you need it:_ scrubbing rules implemented in many places, or telemetry lost during an incident.

**Level 3 — a gateway tier for central policy.** Routing, cost attribution, metrics derived from spans, and service-by-service migration of older instrumentation, sending to both old and new destinations to compare.
_Signal you need it:_ several backends, a migration, or a policy change that took weeks.

**Level 4 — tail sampling.** Trace-aware load balancing, policies that keep errors and slow traces, recorded sampling probabilities, and head sampling raised to 100%.
_Signal you need it:_ the traces you needed weren't kept, or tracing storage costs are climbing.

**Level 5 — budgets and tiers.** Per-team telemetry budgets with automated guardrails, a hot window in the backend, a raw archive in object storage, and retention set per signal and environment.
_Signal you need it:_ telemetry cost has become a line item leadership asks about.

## Implementation

**OpenTelemetry Collector configuration.** A pipeline's implementation *is* its configuration: YAML, with OTTL (the OpenTelemetry Transformation Language) for conditions and transformations. Services only need two standard environment variables: `OTEL_EXPORTER_OTLP_ENDPOINT` pointing at the node's agent, and `OTEL_TRACES_SAMPLER=parentbased_always_on` so the tail sampler sees everything.

The agent, one per node:

```yaml
receivers:
  otlp:
    protocols:
      grpc: { endpoint: 0.0.0.0:4317 }
      http: { endpoint: 0.0.0.0:4318 }
  filelog:                                  # stdout from pods that don't speak OTLP (19.1a)
    include: [/var/log/pods/*/*/*.log]
    operators:
      - type: container                     # unwrap the container runtime's log format
      - type: json_parser                   # the application's own structured line
        parse_from: body

processors:
  memory_limiter:                           # first, always
    check_interval: 1s
    limit_percentage: 80
    spike_limit_percentage: 20
  k8sattributes: {}                         # pod, namespace, deployment, node
  batch: {}

exporters:
  loadbalancing:                            # all spans of one trace → the same gateway instance
    routing_key: traceID
    protocol:
      otlp: { timeout: 1s }                 # queue and retry options: see the exporter's README
    resolver:
      k8s: { service: otel-gateway.observability }
  otlp/gateway:
    endpoint: otel-gateway.observability:4317
    sending_queue: { storage: file_storage } # survives an agent restart or a slow gateway
    retry_on_failure: { enabled: true }

extensions:
  file_storage: { directory: /var/lib/otelcol/queue }

service:
  extensions: [file_storage]
  pipelines:
    traces:  { receivers: [otlp],          processors: [memory_limiter, k8sattributes, batch], exporters: [loadbalancing] }
    metrics: { receivers: [otlp],          processors: [memory_limiter, k8sattributes, batch], exporters: [otlp/gateway] }
    logs:    { receivers: [otlp, filelog], processors: [memory_limiter, k8sattributes, batch], exporters: [otlp/gateway] }
```

The gateway, where the four problems from the opening are solved:

```yaml
receivers:
  otlp:
    protocols: { grpc: { endpoint: 0.0.0.0:4317 } }

connectors:
  spanmetrics: {}                           # RED metrics from 100% of spans
  forward: {}                               # hands traces from the intake pipeline to the sampling one

processors:
  memory_limiter: { check_interval: 1s, limit_percentage: 80, spike_limit_percentage: 20 }

  transform/scrub:                          # 19.1b's backstop, once, for every service
    error_mode: ignore
    trace_statements:
      - context: span
        statements:
          - replace_pattern(attributes["url.full"], "\\?.*$", "?[REDACTED]")
    log_statements:
      - context: log
        statements:
          - replace_all_patterns(attributes, "value", "[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\\.[A-Za-z]{2,}", "[EMAIL]")

  filter/noisy:                             # the debug deploy, stopped without a redeploy
    error_mode: ignore
    logs:
      log_record:
        - resource.attributes["service.name"] == "customs-gw" and severity_number < SEVERITY_NUMBER_INFO

  tail_sampling:                            # policies are OR'd: any match keeps the trace
    decision_wait: 30s
    num_traces: 200000                      # per instance; this is the memory bill
    policies:
      - { name: errors,   type: status_code,      status_code: { status_codes: [ERROR] } }
      - { name: slow,     type: latency,          latency: { threshold_ms: 2000 } }
      - { name: watched,  type: string_attribute, string_attribute: { key: tenant.id, values: [t_4471] } }
      - { name: baseline, type: probabilistic,    probabilistic: { sampling_percentage: 5 } }

  batch: {}

exporters:
  otlp/tempo:        { endpoint: tempo.observability:4317 }
  otlphttp/mimir:    { endpoint: http://mimir.observability:8080/otlp }
  otlphttp/loki:     { endpoint: http://loki.observability:3100/otlp }

service:
  pipelines:
    traces/intake:
      receivers:  [otlp]
      processors: [memory_limiter, transform/scrub]
      exporters:  [spanmetrics, forward]       # metrics see everything; sampling happens next
    traces/sampled:
      receivers:  [forward]
      processors: [tail_sampling, batch]
      exporters:  [otlp/tempo]
    metrics:
      receivers:  [otlp, spanmetrics]
      processors: [memory_limiter, batch]
      exporters:  [otlphttp/mimir]
    logs:
      receivers:  [otlp]
      processors: [memory_limiter, filter/noisy, transform/scrub, batch]
      exporters:  [otlphttp/loki]
```

> **Aside — why there are two trace pipelines.** A Collector pipeline runs all of its processors before *any* of its exporters. With `tail_sampling` and `spanmetrics` in one pipeline, the span metrics would be computed from the sampled 5% plus errors, so every error rate would be wildly inflated and every latency percentile skewed toward slow requests. The `forward` connector splits the flow: intake exports to `spanmetrics` with all spans, and to the sampling pipeline, which keeps only some.

> **Aside — `num_traces` is a memory limit, and it bites quietly.** When more traces are in flight than `num_traces`, the oldest are evicted before their decision, including ones that would have been kept for an error. Size it from your traces-per-second rate × `decision_wait` × a safety margin, per gateway instance. The processor reports evictions as metrics, and they belong on the pipeline's own dashboard.

> **Aside — a filter's mistakes don't look like mistakes.** A typo in `filter/noisy`, such as `<=` instead of `<` or a misspelled service name, drops exactly the data you'd look for when checking whether the filter works. Test configuration changes by sending known records through a staging Collector and asserting what comes out, and keep the Collector's refused and dropped counts on a dashboard.

> **Aside — the scrubbing is only as good as the attribute names.** `url.full` is the current semantic-convention name. A service on an older convention version sends `http.url`, and this rule never touches it. That's the normalization job from *What the middle is for*: rename first, then scrub.

## Further Reading

- **OpenTelemetry Collector documentation:** architecture, configuration, deployment patterns (agent and gateway), scaling, and the pages on resiliency, queues, and persistent storage.
- **OpenTelemetry documentation on sampling,** plus the READMEs for the **tail sampling processor** and the **load-balancing exporter**. The operational details of this article, including how scaling the gateway pool affects trace routing.
- **OTTL and the transform and filter processor documentation.** The language used above, with the full list of functions and contexts.
- **Ted Young and Austin Parker, _Learning OpenTelemetry_** (O'Reilly). Written by OpenTelemetry co-founders, covering instrumentation and pipeline design together.
- **Charity Majors, Liz Fong-Jones, and George Miranda, _Observability Engineering_** (O'Reilly), the chapters on sampling and on telemetry pipelines. Cited in 19.1a; these chapters are the relevant ones here.
- **Prometheus documentation on OTLP ingestion and remote write,** including the notes on metric temporality.
- **Grafana Loki, Tempo, and Mimir documentation.** One concrete self-hosted stack, including each component's storage model and OTLP endpoints.
- **Jaeger documentation on sampling,** including its adaptive sampling, which adjusts head-sampling rates per endpoint from observed traffic. A middle ground between fixed head rates and tail sampling.
- **Vector documentation.** An alternative pipeline tool with a different configuration model, useful for comparison.

No language sibling is planned for this one. The implementation is configuration, and it would read the same whichever language the services are written in.

---

The habit to carry out of this: when a decision is written into many codebases, ask how often the decision changes compared with how often those codebases deploy. Where to send data, how much to keep, and what to remove all change on a business timescale: a contract renewal, an audit, a bad deploy. If changing them requires a coordinated release of thirty services, the decision is in the wrong place, and the same applies to feature flags, rate limits, and routing rules.
