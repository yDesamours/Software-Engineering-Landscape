# Three Questions Named "Health"

_Module 19.2a — Logging, Monitoring & Observability_

## The Problem

A reservations API for restaurants. Twelve pods run behind a Kubernetes Service. They serve booking requests, which need the database, and restaurant pages and availability widgets, which are served mostly from an in-memory cache. Every pod exposes `/health`, copied from a tutorial:

```ts
app.get("/health", async (_req, res) => {
  await db.query("SELECT 1");
  res.send("ok");
});
```

The same endpoint is configured as the liveness probe and as the readiness probe. Three incidents follow over two months.

**Friday, 19:02 — the database fails over.** The managed Postgres instance loses its primary, and failover takes about 90 seconds.

```
19:02:00  primary fails; managed failover begins (~90s)
19:02:20  SELECT 1 in /health times out on all 12 pods
19:02:40  readiness: 0 of 12 pods ready → the Service has no endpoints → every request gets 503
19:02:50  liveness (same endpoint): all 12 pods are killed and restarted
19:03:30  database available again
19:03:35  12 pods start at once: 240 new connections and 12 cache-warming queries
          against a database whose buffer cache is cold after failover
19:04:25  startup needs ~70s; liveness starts checking at 30s → every pod is killed again
   …      CrashLoopBackOff: restart delays double each time, up to 5 minutes
19:16:10  last pod ready
```

A 90-second database failover became a 14-minute outage. The restaurant pages, which never needed the database, were down the whole time.

**Three weeks later — one pod goes quietly wrong.** The postmortem's action item was "health checks caused the outage; make them trivial." `/health` now returns 200 unconditionally. Then a code path on pod 7 leaks database connections until its pool is empty. Every request routed to pod 7 waits 30 seconds and fails. Pod 7 is still Ready, because its health check doesn't touch the pool, so it keeps receiving one twelfth of the traffic. About 8% of bookings fail for three hours.

**Every deploy — a burst of 502s.** When a rolling update terminates a pod, the process exits on SIGTERM. For the next few seconds, the ingress controller keeps sending requests to an address where nothing is listening. Twenty deploys a day, a few dozen failed requests each time, and nobody connects the support tickets to the deploy log.

The team swung from a health check that checked everything to one that checked nothing, and both failed. The mistake underneath both is treating "is this instance healthy?" as one question. The platform is asking three different questions, and each answer triggers a different action.

## What It Is

These are **health probes**: endpoints or commands the platform calls to decide what to do with *one instance*. A probe isn't really asking "is it healthy?" It's asking "should I take this specific action on this instance?"

| Probe | The question | Action on failure | Must never check |
|---|---|---|---|
| **Liveness** | Is this process stuck in a way only a restart can fix? | Kill it and start a new one | Anything outside the process |
| **Readiness** | Should this instance receive traffic right now? | Stop routing to it; don't restart it | Dependencies that every instance shares |
| **Startup** | Has it finished starting? | Keep waiting, up to a limit, then kill it | — |

The companion mechanism is **graceful shutdown**: the sequence by which an instance leaves rotation without dropping the requests it's already handling.

Kubernetes names these three probes explicitly. Load balancers (AWS target groups, Envoy, NGINX), ECS, Docker, and systemd each implement some subset under their own names, with different consequences, and those differences matter below.

One disambiguation, stated once: a probe drives *automation about an instance*. It is not a measure of whether customers are being served. That's an SLI measured on real requests (16.3), and 1.2 already showed why an uptime dashboard built on a health endpoint is misleading.

## Recognizing the Problem

- The same endpoint is configured as both the liveness probe and the readiness probe.
- A probe queries the database, the cache, or another service.
- Every pod restarted at the same moment, and the moment matches a dependency blip.
- CrashLoopBackOff appears after a dependency outage, or during startups under load.
- 502s or 503s spike during every deploy or scale-down.
- A pod was serving errors while showing Ready.
- Pods restart during traffic peaks with no crash in the logs, and events show `Liveness probe failed: … context deadline exceeded`.
- Every pod takes exactly `terminationGracePeriodSeconds` to terminate, which means the process is ignoring SIGTERM.
- Probe requests show up in your rate-limit rejections, auth failures, or request logs.
- Liveness has a large `initialDelaySeconds` "because startup is slow."

## How It Works

### Liveness: only what a restart fixes

A restart fixes a narrow set of problems: a deadlock, a wedged event loop, corrupted in-process state, or resources leaked inside the process. It does nothing for a dependency that's down, a bad configuration, or a broken deploy, which will just fail again after restarting. For overload it's actively harmful: restarting removes capacity at the moment it's most needed, pushes that pod's traffic onto the others, and can tip them over too.

So a liveness check should fail only when the process itself is stuck. The simplest version is often right: answer an HTTP request. In Node, that proves more than it seems to, because the handler can only run if the event loop is turning. In a multi-threaded runtime, a trivial handler proves only that one thread works. There, liveness should test whatever can actually wedge, usually through a **heartbeat**: the important loop records a timestamp each time it makes progress, and liveness fails when that timestamp goes stale.

A false liveness failure costs more than a missed one. A wrong restart kills every in-flight request on that pod and removes capacity. A missed wedge serves errors until something else notices. Tune liveness to be slow and certain, as the configuration below shows.

Not having a liveness probe at all is a legitimate choice. A process that reliably exits when it hits an unrecoverable state is already giving the platform the clearest possible signal, and the Kubernetes documentation says as much. Liveness probes exist for processes that can get stuck without dying.

### Readiness: local conditions only

Readiness should report conditions that are **specific to this instance**, and that another instance may not share:

- still starting up or warming caches;
- draining for shutdown;
- a sidecar or local agent that isn't ready yet;
- a local resource that's exhausted, such as a full disk.

The rule that would have prevented the Friday outage: **a check that every instance will fail at the same moment must not be allowed to remove instances from rotation.**

```
12 pods, each checking the database in readiness

 database down ──► pod 1  unready ┐
               ──► pod 2  unready ├──► Service: 0 endpoints ──► 100% of requests fail,
               ──►   …            │                              including the ones that
               ──► pod 12 unready ┘                              never needed the database
```

Removing every pod doesn't route traffic somewhere better, because there's nowhere else. It converts a partial failure (bookings fail) into a total one (everything fails). Recovery then synchronizes too: all twelve pods become ready in the same few seconds and hit the recovering database together, the same herd shape as 18.1's cron jobs at `:00`.

Shared-dependency failures belong on the request path instead. Let requests that need the database fail fast or degrade, using a circuit breaker (36.3), a stale cached response, or a `503` with `Retry-After` from the handler itself. Let requests that don't need the database keep working. Alert on the dependency through metrics.

**Who fails open and who fails closed.** Routers disagree about what "no healthy instances" means, and it's worth knowing which one sits in front of you:

- **Kubernetes Services fail closed.** With zero ready endpoints, connections are refused.
- **AWS load balancers fail open.** When every target in a target group is unhealthy, the load balancer routes to all of them anyway.
- **Envoy has a panic threshold** (50% by default). Once the healthy share of hosts drops below it, Envoy ignores health and balances across all hosts.

Failing open exists precisely because correlated health-check failures are common. A router that fails open would have kept the restaurant pages up.

### Catching pod 7

Pod 7 is the opposite case: a genuinely local failure that a trivial check can't see. You could teach readiness to detect it, for example "connections have been checked out and not returned for longer than any query should take." But pool trouble also appears on every pod when the database is down, so such a check needs care to avoid rebuilding the Friday problem.

Often the better tool is **passive health checking**, also called outlier detection. The router watches the real responses from each instance and ejects one that fails much more than its peers. Envoy's outlier detection does this and caps ejections at 10% of hosts by default. NGINX's `max_fails` does a simpler version. Evidence from real traffic beats a self-report, and the ejection cap stops a shared failure from ejecting everyone.

### Startup: protecting slow starts

A startup probe runs first, and liveness and readiness are disabled until it succeeds. That lets you give a JVM service or a cache-heavy process three minutes to start without making liveness slow for the rest of its life. The Friday restart loop came from using `initialDelaySeconds` on liveness as a stand-in for a startup probe: a fixed delay sized for a normal start is too short for a start under load.

How an instance starts matters as much as how long it takes. Twelve pods that each open 20 connections and run a heavy warm-up query at the same instant will stampede any dependency that's recovering. Grow connection pools lazily, add random jitter before expensive warm-up, and when a dependency is unavailable at startup, retry with capped backoff *inside the process* while the startup probe waits. Exiting instead puts the pod into CrashLoopBackOff, whose delay keeps growing (up to five minutes) and can outlast the dependency's outage.

### Leaving gracefully

Deploy-time 502s come from a race that's easy to miss: when Kubernetes terminates a pod, it removes the pod from routing *and* signals the process at the same time.

```
t = 0   pod marked Terminating
        ├──► endpoint removed from EndpointSlice ──► kube-proxy, ingress controllers,
        │                                            cloud load balancers update
        │                                            (asynchronously, over seconds)
        └──► kubelet runs the preStop hook, then sends SIGTERM
                      │
                      └── new requests keep arriving until every router has caught up

t = G   SIGKILL     (G = terminationGracePeriodSeconds, 30 by default,
                     counted from t = 0, so preStop time is included)
```

A process that exits on SIGTERM leaves a window in which routers still send it traffic. The correct sequence is:

1. **Keep serving, and report not-ready.** Kubernetes already stops routing to terminating pods, but external load balancers that poll your readiness endpoint only learn about the shutdown from it.
2. **Wait for routers to catch up.** A few seconds is usually enough. This can happen in the app or in a `preStop` sleep. Pick one; if you use both, the waits add up.
3. **Stop accepting new connections.** Close idle keep-alive connections, and send `Connection: close` on in-flight responses so clients don't reuse the socket.
4. **Let in-flight requests finish**, up to a deadline.
5. **Close long-lived work.** Tell WebSocket clients to reconnect elsewhere (Module 9), and stop claiming jobs, relying on leases for anything interrupted (Module 10).
6. **Release resources and flush.** Close connection pools and flush asynchronous log buffers (19.1a), then exit.

The budget is the preStop wait, plus the drain deadline, plus cleanup, which together must fit inside `G`. Outside Kubernetes the pieces have different names, but the shape is the same. AWS target groups, for example, have a *deregistration delay* (300 seconds by default) during which the load balancer stops sending new requests to the target while existing ones finish.

### Probe hygiene

Probe configuration is where most of the tuning happens, and the defaults are rarely what you want:

```yaml
startupProbe:
  httpGet: { path: /startupz, port: 9090 }
  periodSeconds: 5
  failureThreshold: 36        # up to 180s to start; liveness and readiness wait for this
livenessProbe:
  httpGet: { path: /livez, port: 9090 }
  periodSeconds: 10
  timeoutSeconds: 3           # the default is 1 second
  failureThreshold: 6         # about 60s of silence before a restart
readinessProbe:
  httpGet: { path: /readyz, port: 9090 }
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 2         # about 10s to leave rotation
terminationGracePeriodSeconds: 30
# The app waits for routers itself (see Implementation). Alternatively, add
# lifecycle.preStop with a short sleep (a native `sleep` action in Kubernetes 1.30+)
# and drop the app's wait. Don't use both.
```

A few rules behind those numbers:

- **Detection time is roughly `periodSeconds × failureThreshold`.** Make readiness fast to react and liveness slow and certain.
- **The default one-second timeout is a trap.** A probe that does any real work will fail occasionally under load, and liveness will count those failures.
- **Serve probes on a separate port.** Probes then bypass authentication, rate limiting (Module 18), and request logging (19.1a). They also keep answering after the main server stops accepting connections during a drain; every probe is a new connection.
- **Don't expose probe endpoints publicly.** A detailed status page reveals versions and dependencies.
- **Avoid transitive checks.** A health endpoint that calls other services' health endpoints, which call theirs, turns one failing leaf into an unhealthy graph.

### A deep check still has a place

Knowing whether each dependency is reachable is useful. It just shouldn't drive the orchestrator. Expose a `/status` endpoint behind authentication for people, dashboards, and synthetic monitors (16.3). It should report each dependency's state and latency, the build version, and the uptime. Run its checks in the background every few seconds and serve the cached result, so that someone refreshing the page can't turn it into load on the database.

## When It's Appropriate

- **Any orchestrated or load-balanced deployment with more than one instance.** Split liveness from readiness from day one; it costs minutes.
- **Slow starters.** JVM services, processes that load large models or caches, anything that needs more than about 20 seconds before it can serve. These need a startup probe, not a long liveness delay.
- **Processes that can wedge without crashing.** Node services with CPU-heavy paths, runtimes with lock-heavy code, and queue workers whose loop can hang on one job. These need liveness, often based on a heartbeat.
- **Frequent deploys and autoscaling.** Graceful shutdown matters in proportion to churn. Twenty deploys a day across twelve pods is 240 terminations a day, each of which is a chance to drop requests.
- **Long requests or long-lived connections.** Uploads, exports, streaming, and WebSockets need real drain deadlines and reconnect behavior.
- **Large fleets with partial failures.** Once "one instance in forty is quietly broken" is a recurring pattern, outlier detection pays for itself.

## When It's Unnecessary or Overkill

- **Liveness probes for processes that crash cleanly.** If fatal errors already end the process, a liveness probe only adds ways to restart it by mistake.
- **Deep dependency checks wired into probes.** This is the anti-pattern the whole article is about, however thorough it looks.
- **A startup probe for a Go binary that's serving within 200 milliseconds.** Readiness alone covers it.
- **Elaborate drain logic for batch jobs or a single-instance internal tool** whose users can tolerate a brief error during a deploy.
- **Readiness as a load-shedding mechanism.** Overload usually affects every instance at once, which recreates the Friday failure. Shed load on the request path (18.1's alternatives) instead.
- **A service mesh adopted only for outlier detection.** Most load balancers and ingress controllers offer some form of passive health checking already.

## Trade-offs

- **Shallow and deep checks each fail a different way.** Shallow checks miss real local failures (pod 7). Deep checks create correlated failures (Friday). No single probe avoids both, so you need complementary mechanisms: outlier detection, request-path degradation, and dependency alerts.
- **Safe thresholds mean slow detection.** A liveness probe tuned not to misfire takes a minute to notice a wedged process.
- **Graceful shutdown slows deploys and scale-downs.** A five-second wait and a fifteen-second drain per pod add up across a rolling update.
- **Long grace periods slow everything that drains nodes.** Cluster upgrades, spot instance reclaims, and maintenance all wait on the slowest pod.
- **Failing open is deliberate, and it routes to broken instances.** When everything really is broken, a fail-open router sends traffic to broken targets instead of returning a clean error.
- **Health logic is rarely exercised.** Its important paths only run during incidents, which is the worst time to discover they're wrong.
- **Semantics differ by platform.** The same service behind a Kubernetes Service, an AWS load balancer, and Envoy has three different failure behaviors, and a readiness endpoint that's right for one may be wrong for another.
- **Separate probe ports add configuration surface.** One more port to expose to the kubelet, and to keep away from the public ingress.

## Alternatives

- **Crash-only design.** Make "stop" and "crash" the same path, exit on any unrecoverable state, and let the supervisor restart the process. It removes most of the need for a liveness probe, and it requires startup to be safe to repeat.
- **Push-based watchdogs.** The process reports that it's alive, and silence is the failure. systemd's `WatchdogSec` with `sd_notify` works this way, as does an exec probe checking a heartbeat file (see Implementation).
- **Passive health checking.** Covered above. It judges instances by real outcomes instead of self-reports, and it's the better tool for partial failures.
- **Client-side retries to another instance**, within a retry budget (Modules 17 and 36). They absorb a single bad instance without anyone ejecting it, at the cost of extra load.
- **The gRPC Health Checking Protocol.** A standard health service for gRPC servers, with per-service status. Kubernetes can probe it natively.
- **Platform-managed instances.** Serverless and managed container platforms handle much of this for you, with fewer knobs, and with less visibility when their defaults don't suit your service.

## How to Achieve It

**Level 0 — inventory.** For each service, write down what each probe checks, what action its failure triggers, and its timeout and thresholds.
_Signal you're here:_ one endpoint serving both probes, or nobody knows the timeout.

**Level 1 — split and simplify.** A trivial `/livez`, and a `/readyz` that reports only local state (started, not draining). Remove shared dependencies from both.
_Signal you need it:_ restarts or unready periods that line up with dependency blips.

**Level 2 — graceful shutdown.** Handle SIGTERM, flip readiness, wait for routers, drain with a deadline, close long-lived work, and make sure the process actually receives the signal.
_Signal you need it:_ errors during deploys, or pods that always take the full grace period to die.

**Level 3 — startup probes and tuned thresholds.** Replace liveness delays with a startup probe, raise timeouts above one second, and add jitter and lazy pool growth to startup.
_Signal you need it:_ CrashLoopBackOff under load, or liveness restarts at traffic peaks.

**Level 4 — catch what shallow probes miss.** Heartbeat-based liveness for loops that can wedge, outlier detection from real traffic, a cached `/status` for people and synthetic monitors, and alerts on dependencies.
_Signal you need it:_ a pod that was Ready and failing.

**Level 5 — exercise it on purpose.** Fail the database in staging and watch what the probes do. Deploy during a load test and count errors. Treat "zero 5xx during a rollout" as a release check.
_Signal you need it:_ your probes have only ever been tested by real incidents.

## Implementation

**TypeScript on Node's built-in `http` module.** Node makes two things vivid: liveness means something real on a single event loop, and shutdown has specific connection-handling steps that frameworks usually hide.

The probe server is separate from the application server. It opens first and closes last:

```ts
import http from "node:http";

type Phase = "starting" | "serving" | "draining";
let phase: Phase = "starting";
let inFlight = 0;

const probes = http.createServer((req, res) => {
  switch (req.url) {
    case "/livez":    // reaching this line proves the event loop is turning; that's the check
      return res.writeHead(200).end("ok");
    case "/startupz":
      return res.writeHead(phase === "starting" ? 503 : 200).end(phase);
    case "/readyz":   // local state only; no database, no downstream calls
      return res.writeHead(phase === "serving" ? 200 : 503).end(phase);
    default:
      return res.writeHead(404).end();
  }
});

const server = http.createServer((req, res) => {
  inFlight++;
  res.on("close", () => inFlight--);                         // finished or aborted
  if (phase === "draining") res.setHeader("Connection", "close");
  app(req, res);
});

async function start() {
  probes.listen(9090);          // answer "not yet" while starting
  server.listen(8080);
  await sleep(Math.random() * 10_000);                       // jitter: 12 pods, not all at once
  await retryWithBackoff(() => db.connect({ min: 2 }), { maxDelayMs: 10_000 });
  await warmCache();
  phase = "serving";
}
```

> **Aside — the retry is deliberate.** If the database is down at startup, `retryWithBackoff` keeps the process alive and not-started, and the startup probe's 180-second allowance bounds the wait. Exiting instead would hand the pod to CrashLoopBackOff, whose growing delay can keep it down long after the database recovers. `min: 2` is the lazy pool: connections grow with real demand, not all at startup.

Shutdown follows the six steps:

```ts
const ROUTER_CATCH_UP_MS = 5_000;  // time for routers to stop sending new requests
const DRAIN_MS = 15_000;           // in-flight deadline; 5 + 15 + cleanup < 30s grace

process.once("SIGTERM", async () => {
  phase = "draining";                          // 1. readiness is now 503; keep serving
  await sleep(ROUTER_CATCH_UP_MS);             // 2. let routers catch up

  server.close();                              // 3. no new connections
  server.closeIdleConnections();               //    keep-alive sockets with nothing in flight

  const deadline = Date.now() + DRAIN_MS;      // 4. let in-flight requests finish
  while (inFlight > 0 && Date.now() < deadline) await sleep(100);
  server.closeAllConnections();                //    whatever's left loses now, not at SIGKILL

  await Promise.allSettled([                   // 5. long-lived work
    sockets.closeAll({ code: 1012 }),          //    WebSocket 1012 = "service restart"
    worker.stop(),                             //    stop claiming; leases cover the rest
  ]);
  await db.end();                              // 6. resources, then logs
  await logger.flush();
  probes.close();
  process.exit(0);
});
```

> **Aside — make sure the signal arrives.** If every pod takes exactly 30 seconds to terminate, SIGTERM probably never reached Node. A shell-form `CMD`, or a package-manager script used as the container's entrypoint, can end up as PID 1 and fail to forward the signal. Run `node` directly as the command, and add a minimal init such as `tini` if the process spawns children.

> **Aside — a CPU-heavy request can still get this pod killed.** A synchronous 20-second parse blocks the event loop, so `/livez` can't answer, and with a one-second timeout and three failures, the kubelet restarts the pod in the middle of the traffic that caused the problem. The thresholds above tolerate about a minute of blocking. The actual fix is moving CPU-bound work off the event loop, into `worker_threads` or a job queue (Module 10).

A queue worker has no HTTP server, but it still needs a liveness signal, and the obvious one is wrong:

```ts
// Wrong: a timer proves the event loop is turning, not that the worker is working.
// setInterval(() => touch("/tmp/heartbeat"), 5_000);

// Right: beat on progress, inside the loop that can get stuck.
const beat = () => fs.promises.utimes("/tmp/heartbeat", new Date(), new Date()).catch(() => {});

async function workLoop() {
  while (phase !== "draining") {
    const job = await claim();                 // Module 10's SKIP LOCKED claim
    beat();                                    // a completed poll is progress
    if (job) await run(job, { onProgress: beat });
    else await sleep(500);
  }
}
// exec liveness probe: sh -c 'find /tmp/heartbeat -mmin -2 | grep -q .'
```

A job hung on a network call with no timeout stops the heartbeat, and two minutes later the kubelet restarts the worker. The job's lease expires, and another worker picks it up. The staleness threshold has to exceed your longest legitimate gap between heartbeats, which is why long jobs report progress through `onProgress` instead of relying on a large threshold. (Create the file once at startup so `utimes` has something to update.)

## Further Reading

- **Kubernetes documentation, "Configure Liveness, Readiness and Startup Probes"** and **"Pod Lifecycle,"** particularly the section on pod termination. The authoritative source for defaults and for the order of events during shutdown.
- **AWS Builders' Library, "Implementing health checks"** (David Yanacek). Shallow versus deep checks, failing open, and why correlated health-check failures are the thing to design against.
- **Colin Breck, "Kubernetes Liveness and Readiness Probes: How to Avoid Shooting Yourself in the Foot."** A careful catalogue of the failure modes in this article, with the reasoning behind each.
- **Envoy documentation on health checking, the panic threshold, and outlier detection.** The most complete model of active and passive health checking working together.
- **AWS Elastic Load Balancing documentation on target group health checks and deregistration delay.** Where fail-open behavior and connection draining are specified for AWS load balancers.
- **gRPC Health Checking Protocol** (`doc/health-checking.md` in the grpc repository). The standard health service and its serving-status semantics.
- **George Candea and Armando Fox, "Crash-Only Software"** (HotOS 2003). The argument for making crash and restart the only way to stop, which removes much of what liveness probes exist for.
- **Node.js documentation for `http.Server`:** `close()`, `closeIdleConnections()`, and `closeAllConnections()`. The exact behavior the shutdown code depends on.
- **Learnk8s, "Graceful shutdown and zero downtime deployments in Kubernetes"** (Daniele Polencic). Illustrates the endpoint-propagation race in detail.

A Go sibling would be worth writing, because Go moves both halves of this article. `http.Server.Shutdown` makes `ListenAndServe` return `ErrServerClosed` *immediately*, so a program that treats that return as "done" exits before its drain completes. `Shutdown` also doesn't wait for hijacked connections such as WebSockets, which need their own handling via `RegisterOnShutdown`. And because goroutines keep serving a trivial `/livez` while a worker pool sits deadlocked on a mutex, heartbeat-based liveness stops being a niche technique for workers and becomes necessary in the web process too. Not yet written.

---

The habit to carry out of this: whenever an automated system asks a component a yes-or-no question, ask two more. What will it *do* with a "no"? And what happens if every instance answers "no" at the same moment? Most health-check outages come from a sensible answer to the first question and nobody asking the second.
