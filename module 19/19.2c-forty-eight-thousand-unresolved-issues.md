# Forty-Eight Thousand Unresolved Issues

_Module 19.2c — Logging, Monitoring & Observability_

## The Problem

A project-management product: a React single-page app backed by a Node API, with about 40,000 daily users and a deploy most days. Two years ago someone installed an error tracker on both the frontend and the backend, with default settings.

Friday, 16:40. Release `a91f3c2` ships a refactor of the settings page. By Monday morning, support has 23 tickets saying the settings page is blank. The API's error rate is 0.1%, unchanged, and the server logs are clean. The failing code runs in the browser: users with no saved timezone preference hit `preferences.timezone` on an undefined object, and the page crashes before it makes any request.

The error tracker recorded all of it: 11,300 events from 2,100 users since Friday. Nobody saw any of it, for five reasons.

**The list was unreadable.** The project had 48,000 unresolved issues. The alert channel for new issues had been muted in March, after it started posting 300 times a day.

**Every deploy created fake "new" issues.** No source maps were uploaded, so stack frames looked like `at e (main.8f3a2c.js:1:48213)`. The bundle's filename is a content hash, which changes with every build, so each release gave old bugs new fingerprints. Friday's crash was one of 41 "new" issues that day, and most of the other 40 were old bugs wearing new filenames.

**One bug became three small issues.** Each browser words the same failure differently:

```
Chrome    TypeError: Cannot read properties of undefined (reading 'timezone')
Safari    TypeError: undefined is not an object (evaluating 'e.preferences.timezone')
Firefox   TypeError: e.preferences is undefined
```

With unreadable frames, grouping fell back to the message, which produced three mid-sized issues and nothing at the top of the list.

**The top of the list was permanently occupied.** The largest issue was `ApiError: Request failed`: 1.9 million events over 14 months. Every failed request from the shared API client shared the same top frames, so this one issue held thirty-odd distinct bugs plus every flaky mobile connection. Nobody could ever resolve it, and it sat first in every sort.

**The weekend's data was missing.** A browser extension deployed across one customer's company injected a script that threw on every page load. By Saturday 09:00 it had generated 400,000 events and exhausted the monthly quota. Everything after that was dropped.

The tool did its job: it captured the crash. Everything around capture, meaning symbols, grouping, noise, triage, and alerting, had been left at defaults, and the result was a list nobody could act on.

## What It Is

This is **error tracking**. Exceptions from servers and clients are captured with their stack traces and context, then grouped by a **fingerprint** into **issues**, where each issue is meant to be one defect. Issues are then managed through a lifecycle: new, assigned, resolved in a specific release, and reopened if they regress.

Sentry, Rollbar, Bugsnag, Honeybadger, and Datadog's error tracking are common hosted tools. GlitchTip is an open-source, Sentry-compatible option, and Firebase Crashlytics covers mobile crashes.

The distinction that matters most is between an **event** (one occurrence) and an **issue** (one defect, however many times it occurred). Everything valuable about these tools depends on that grouping being right.

Error tracking overlaps with three signals this module already covers, and each answers a different question:

- **Error-rate metrics** (16.3) say *how much* is failing.
- **Error logs** (19.1a) say *what happened* during one request.
- **Error tracking** says *which distinct defects exist*, which are new, which release introduced them, how many users they affect, and whether a fixed one has come back.

It's also the only one of the three that sees code running on devices you don't control, such as browsers, phones, and desktop apps.

## Recognizing the Problem

- Users report errors that your server logs and metrics don't show.
- Stack traces look like `at e (main.8f3a2c.js:1:48213)`.
- Nobody can answer "is this error new?" or "which release introduced it?"
- A bug you fixed comes back, and nobody notices until a customer reports it.
- The tracker has thousands of open issues, and its alerts are muted.
- Every deploy produces a wave of "new" issues that aren't really new.
- One enormous issue has been open for a year, and nobody can close it.
- The event quota runs out before the month does.
- Browser errors arrive as `Script error.` with no stack at all.
- Code is full of `catch (e) { console.log(e) }`.
- Unhandled promise rejections disappear without a trace.

## How It Works

### Anatomy of an event

An error event carries far more than a log line:

- **The exception:** type, message, and stack frames. Each frame records the file, function, line, column, surrounding source, and whether it's your code or a library's (**in-app**). If the error wraps another one, the **cause chain** is included too.
- **Where it ran:** release, environment, platform, and browser, OS, or device.
- **Who and what it affected:** a user ID and tags such as tenant, plan, route template, and active feature flags.
- **Breadcrumbs:** a trail of what happened just before the error, such as navigations, clicks, console output, and network requests. This is often what makes a client-side bug reproducible.
- **Links:** the `trace_id` (19.2b), and the request with its sensitive parts scrubbed.

Breadcrumbs and captured requests are also where sensitive data enters: URLs with tokens, console output, and the text of clicked elements. Server-side SDKs may capture local variables as well. Everything in 19.1b applies here. Scrub before sending, send user IDs rather than emails, and keep server-side scrubbing as a backstop.

### Capture: unhandled, handled, and swallowed

Errors reach a tracker by three routes, and one of them is a dead end:

- **Unhandled errors** are caught by global hooks: `window.onerror` and `unhandledrejection` in browsers, `uncaughtException` and `unhandledRejection` in Node, and framework boundaries such as React error boundaries and Express error middleware. SDKs install most of these for you.
- **Handled errors** that still deserve a developer's attention are reported explicitly, at the layer that handles them and only there. That's the same rule 19.1a gave for logging, for the same reason: reporting at every layer turns one defect into several events with partial stacks.
- **Swallowed errors**, caught and neither rethrown nor reported, are invisible. A `catch` that only calls `console.log` is the most common way a real bug stays hidden.

Not every error belongs in the tracker. The test is 19.1a's ERROR contract: *should a developer look at this?* An expired session or a declined card is an expected outcome, not a defect. A 400 or 422 from your own API to your own frontend is different, though: it means the client sent something the server rejects, which is a bug in one of them.

Two capture details are easy to miss:

- **Throwing something that isn't an `Error`** (`throw "not found"`, or rejecting a promise with a plain object) produces an event with no stack trace. Lint rules such as `prefer-promise-reject-errors` and typescript-eslint's `only-throw-error` prevent it.
- **After `uncaughtException`, a Node process is in an undefined state**, and Node's documentation says not to resume. Report the error, flush the SDK's send buffer, and exit, letting the orchestrator restart the process (19.2a). Since Node 15, unhandled promise rejections take the same path by default.

### Grouping: the fingerprint is the product

A tracker's default grouping roughly works like this. It takes the top in-app stack frames and identifies each by module and function name, ignoring line numbers where it can. If the frames are unusable, it falls back to the exception type plus a normalized message. Both steps can go wrong, in opposite directions:

```
                            under-grouping                     over-grouping
                            one bug → many issues              many bugs → one issue

what you see                duplicates, "new" issues           one giant issue nobody can close
                            after every deploy

typical causes              minified frames, hashed            a shared helper at the top of every
                            filenames, variable text in        stack (API client, logging wrapper),
                            messages, per-browser wording      one generic error type thrown centrally,
                                                               stacks captured at a central handler

fix                         symbolication; normalize or        treat the helper as not in-app;
                            avoid variable messages            custom fingerprints; keep the cause
```

Both failures appeared in the Problem. Missing source maps split one crash into three issues and gave old bugs new identities every day. The shared API client merged thirty bugs into `ApiError: Request failed`.

The fixes are all ways of telling the tracker what "the same defect" means for your code:

- **Symbolicate** (next section), so frames have real names and paths that stay stable across builds.
- **Mark frames as in-app or not.** Once the API client is marked as infrastructure, grouping uses the *caller's* frames, and the single giant issue splits along the call sites that actually differ.
- **Set custom fingerprints** where the stack can't tell defects apart. All API failures pass through the same code, but "`POST /projects/:id/members` returned 422" and "`GET /reports/:id` returned 500" are different bugs.
- **Keep messages constant** and put variable data in tags. `User 8812 not found` creates a new message for every user.
- **Wrap errors with a cause** (`new Error(msg, { cause })`) rather than replacing them, so the original stack survives and the tracker can group on it.

One warning: changing grouping rules changes fingerprints, and every affected defect then starts over as a "new" issue with no history. Make those changes deliberately, and expect a noisy day afterward.

### Symbolication: source maps and their equivalents

Production JavaScript is minified and bundled, so a raw stack frame points at column 48,213 of a one-line file, in a function called `e`. A **source map** maps positions in the built file back to the original source. The tracker applies the map to each event, which gives you readable frames and stable grouping.

The pipeline has one job: at build time, upload the maps for exactly the bundle being deployed, tagged with the release identifier the running app will report. The ways it fails are mundane, and all of them are silent:

- the maps were uploaded under a different release name;
- they were generated for a different build;
- nobody uploaded them at all.

Newer tooling embeds a **debug ID** in both the bundle and its map, so matching no longer depends on file URLs or release names. Either way, a CI check that sends a test error and confirms it resolves to real source is worth adding.

Whether to also *serve* source maps publicly is a separate decision. Maps usually embed the full original source (`sourcesContent`). Uploading them only to the tracker keeps them private.

Other platforms have the same step under other names: dSYM files for iOS, ProGuard or R8 mapping files for Android, and debug symbols (DWARF, PDB) for native code. Node services written in TypeScript can run with `--enable-source-maps` so their own stack traces point at `.ts` files.

### Releases: what makes "new" mean something

Tag every event with a **release** (usually the git SHA) and an **environment**. Several features depend on that tag:

- **First seen in:** each issue records the release where it first appeared. "New in `a91f3c2`" is how Friday's crash should have surfaced.
- **Resolve in next release:** marking an issue fixed *as of a release* means events from older builds, still running in open browser tabs, don't reopen it.
- **Regression detection:** an issue resolved in one release that appears again in a later one reopens automatically. That's usually the single most valuable alert a tracker can send.
- **Release health:** the share of sessions or users that completed without a crash, compared across releases. Mobile teams usually call this the crash-free rate.
- **Suspect commits:** with a repository integration, the tracker can link the frames in a new issue to recent commits that touched those files.

Release tagging also connects error tracking to deployment. A canary release (30.2) whose new-issue count or crash-free rate is worse than the previous release's is a reason to stop the rollout before every user has it.

### Triage is a workflow, not a list

A tracker without a workflow turns into the Problem's 48,000 issues. The workflow needs four parts:

- **States.** New, assigned, resolved (now, or in the next release), and ignored. Ignoring should usually be conditional ("until it affects 50 more users," "for a week," "until it escalates"), so a quiet issue that suddenly grows comes back.
- **Ownership.** Rules that route issues by file path, URL, or tag to a team, the tracker's equivalent of a CODEOWNERS file.
- **A cadence.** Someone reviews new issues every day. The goal is *zero unreviewed new issues*, not zero issues; a backlog of known, deliberately ignored problems is fine.
- **The right sort order.** Rank by **users affected**, not event count. A single tab stuck in a retry loop can produce 50,000 events from one person.

Link issues to your ticket tracker, and link events to their traces and logs through the `trace_id`, so that reviewing an issue leads directly to the requests behind it.

### Alert on change, not on existence

With thousands of browsers running your code, some error is always happening somewhere. Useful alerts fire on *changes*:

- a new issue first seen in the release that was just deployed;
- a resolved issue that regressed;
- an issue affecting more than N users, or more than X% of sessions, within an hour;
- an existing issue spiking well above its own baseline;
- a release's crash-free rate falling below the previous release's.

"Notify on every new issue" is the alert that got muted in March. SLO burn-rate alerts (16.3) answer a different question, namely whether users are being hurt right now. Route both kinds, and decide which one is allowed to page someone (19.3b).

### Noise and volume

Much of what a browser reports isn't your bug:

- **Browser extensions and injected scripts** throw errors inside your page. Restrict capture to errors whose frames come from your own origins.
- **`Script error.`** is what a browser reports for an error in a cross-origin script, deliberately hiding the details. Loading your own scripts from a CDN with `crossorigin="anonymous"`, and serving them with a matching `Access-Control-Allow-Origin` header, restores the real message and stack.
- **Benign browser messages**, such as `ResizeObserver loop …`, and **aborted requests** when a user navigates away (`AbortError`), are noise.
- **Network failures** (`Failed to fetch`, Safari's `Load failed`) usually reflect the user's connection. Track their rate rather than each occurrence.
- **Chunk-load failures after a deploy are real,** even though they look like network noise. A tab still running the old bundle requests a code-split chunk that no longer exists on the server. The fix is to keep old assets available for a while and prompt long-lived tabs to reload.

Keep filters few and reviewed. Filtering by message text is 19.1a's regex problem in a new place: a broad pattern can silently swallow real bugs.

Volume needs its own controls, because one broken client can exhaust a quota for everyone:

- **Deduplicate on the client,** so the same error thrown in a loop is sent once.
- **Rate-limit per issue** and enable spike protection on the tracker's side.
- **Be careful with sampling.** Keeping 10% of error events cuts cost evenly, but it can make a rare defect disappear entirely. Deduplication and per-issue limits reduce volume without losing the rare issues.

## When It's Appropriate

- **Any client-side code in production,** whether browser, mobile, or desktop. Nothing else sees those errors, and the Problem's API metrics never moved.
- **Frequent releases.** Daily deploys make "first seen in" and regression detection worth more than any other feature.
- **Many distinct, individually small defects.** A 40,000-user app across five browsers has a long tail of bugs that each affect a few hundred people. They need a queue, not an outage process.
- **Several teams.** Ownership rules route each issue to someone who can fix it.
- **Servers whose unhandled exceptions currently exist only as log lines,** with no grouping, no release history, and no way to see whether a fix worked.

## When It's Unnecessary or Overkill

- **An internal tool with twenty users** who will message you when something breaks.
- **Reporting expected outcomes.** Expired sessions, declined cards, and not-found lookups flood the tracker and bury the defects.
- **Session replay on every session.** It's expensive and sensitive. Enable it for sampled or error-bearing sessions if at all.
- **Building your own tracker.** Capture is easy; grouping, symbolication, and the workflow are the hard parts. If compliance requires self-hosting, run an open-source option.
- **Tracking failures that already have a queue.** A background job system with a failed state and a dead-letter view (Module 10) is already a defect list for those jobs.
- **Alerting on every new issue.** See the Problem.

## Trade-offs

- **Grouping is a heuristic, and it's wrong in both directions.** Tuning it is ongoing work, and every rule change resets the history of the issues it touches.
- **It's one more copy of sensitive data.** Breadcrumbs, request bodies, local variables, and replays all need 19.1b's treatment.
- **Cost scales with events,** and a single misbehaving client can spend your quota for everyone.
- **Client SDKs have weight.** They add bundle size, main-thread work, and network calls, and ad blockers block known tracker domains. Sending events through your own endpoint helps with blocking and adds a server path you now operate.
- **Symbolication adds build complexity,** and when it breaks, everything keeps working with less useful data and no error.
- **The tool needs a process.** Without daily triage and ownership, the backlog grows until nobody reads it, which is exactly the Problem.
- **Some browser errors are beyond your control.** Extensions, old devices, and hostile environments will always contribute noise.
- **Issue history is vendor-specific.** OpenTelemetry can record exceptions as span events and log records, but grouping and workflow aren't standardized, so switching tools means starting the history over.
- **Self-hosting is heavy.** Full-featured open-source trackers depend on several data stores and a message queue.

## Alternatives

- **Log-based error analysis** (19.1a). Group-by queries on `error_type` and route fields work well for server-side errors. There's no release history, no regression detection, and no view of client code.
- **Error-rate metrics and SLO alerts** (16.3). They measure user impact precisely and say nothing about which defect caused it.
- **Exceptions on traces** (19.2b). Span events record errors in the context of a request, and some APM products build error-tracking views from them.
- **Real user monitoring (RUM).** Browser performance data plus errors, from the same script. It overlaps heavily with client-side error tracking, and some products combine them.
- **Session replay.** It shows what the user did before an error, which is powerful for reproduction and heavy on cost and privacy.
- **User feedback** (Module 27). An in-app "report a problem" button, and support tickets, catch what instrumentation misses. They were the signal that finally worked in the Problem.
- **Canary analysis** (30.2). It compares a new release against the old one before full rollout, so fewer regressions ever reach the backlog.

## How to Achieve It

**Level 0 — capture unhandled errors, tagged with release and environment,** on both servers and clients.
_Signal you're here:_ users report errors your systems don't show.

**Level 1 — symbolication in CI.** Upload source maps (or dSYMs, or mapping files) for each release, and verify that a test event resolves to real source.
_Signal you need it:_ frames named `e` and `t`, or "new" issues after every deploy.

**Level 2 — control noise and data.** Restrict capture to your own origins, add `crossorigin` to your scripts, drop expected outcomes and known benign messages, deduplicate on the client, and scrub sensitive data.
_Signal you need it:_ an exhausted quota, or a muted alert channel.

**Level 3 — fix grouping.** In-app rules for shared helpers, custom fingerprints for wrapper errors, cause chains, constant messages, and lint rules against throwing non-errors.
_Signal you need it:_ one giant issue, or the same defect listed three times.

**Level 4 — a working triage process.** Ownership rules, a daily review of new issues, resolve-in-release, regression alerts, and links to traces, logs, and your ticket tracker.
_Signal you need it:_ the backlog keeps growing, or a regression went unnoticed.

**Level 5 — release gates.** Compare crash-free rate and new-issue count against the previous release during a canary, and stop or roll back automatically.
_Signal you need it:_ frequent deploys, and regressions reaching all users before anyone notices.

## Implementation

**TypeScript, in the browser.** Client-side code is where error tracking has no substitute, and it's where source maps, noise, and grouping are hardest.

First, a simplified version of what default grouping does, which explains most of what follows:

```ts
interface Frame { module?: string; function?: string; inApp: boolean }
interface CapturedError { type: string; message: string; frames: Frame[] }

function defaultFingerprint(e: CapturedError): string {
  const inApp = e.frames.filter((f) => f.inApp);                // your code, not libraries
  const top = (inApp.length ? inApp : e.frames).slice(0, 5);
  if (top.every((f) => f.module && f.function)) {
    // No line numbers, no hashed file names: those change on every build.
    return hash(e.type, ...top.map((f) => `${f.module}:${f.function}`));
  }
  return hash(e.type, normalize(e.message));                    // frames unusable: fall back
}

const normalize = (m: string) =>
  m.replace(/[0-9a-f]{8}-[0-9a-f-]{27}/gi, "<uuid>")
   .replace(/\d+/g, "<n>")
   .replace(/(["']).*?\1/g, "<str>");
```

This is why the Problem went wrong. Without source maps, `module` is a hashed filename and `function` is `e`, so either the fingerprint changes every build or grouping falls back to a message that each browser words differently. With source maps, the three browser messages collapse into one issue keyed on `settings/TimezoneField:render`. `normalize` also shows why `User 8812 not found` groups acceptably while `User jane@example.com not found` doesn't: numbers are stripped, but an unquoted email address survives.

Second, an API error designed to group well:

```ts
export class ApiError extends Error {
  constructor(
    readonly method: string,
    readonly route: string,       // the template: "/projects/:id/members"
    readonly status: number,      // 0 = no response
    options?: ErrorOptions,
  ) {
    super(`${method} ${route} failed with ${status}`, options); // constant per route and status
    this.name = "ApiError";
  }
}

export async function request<T>(method: string, route: string, params: Params, body?: unknown): Promise<T> {
  let res: Response;
  try {
    res = await fetch(fill(route, params), { method, body: body && JSON.stringify(body) });
  } catch (cause) {
    throw new ApiError(method, route, 0, { cause }); // keep the original network error
  }
  if (!res.ok) throw new ApiError(method, route, res.status);
  return res.json() as Promise<T>;
}
```

> **Aside — the message uses the route template, never the filled URL.** `GET /projects/8471 failed` would create a separate message per project and, if grouping falls back to messages, a separate issue per project. It would also put identifiers into a field that's hard to scrub (19.1b). The template keeps the message constant, just as 19.1a's event names were.

Third, SDK configuration that applies the rest of the article. Sentry's browser SDK is used here, but other trackers have equivalent options:

```ts
Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,
  release: import.meta.env.VITE_RELEASE,   // the same SHA the source maps were uploaded under
  environment: import.meta.env.MODE,
  allowUrls: [/^https:\/\/app\.example\.com\//],  // drop errors whose frames all come from elsewhere
  ignoreErrors: [/^ResizeObserver loop/],
  tunnel: "/api/error-events",                    // same-origin relay; fewer events lost to ad blockers

  beforeSend(event, hint) {
    const err = hint.originalException;

    if (err instanceof DOMException && err.name === "AbortError") return null; // navigated away
    if (err instanceof ApiError) {
      if (err.status === 401) return null;     // expired session: handled by redirecting to login
      if (err.status === 0) return null;       // offline or flaky network: track as a rate, not issues
      // Every ApiError shares the client's frames. Group by what actually failed.
      // A 400 or 422 is kept: our own client sent something our own API rejects.
      event.fingerprint = ["api-error", err.method, err.route, String(err.status)];
    }

    if (event.request?.url) event.request.url = stripQuery(event.request.url);   // 19.1b
    return event;
  },
});

Sentry.setUser({ id: session.userId });   // an ID, never the email
Sentry.setTag("tenant", session.tenantId);
Sentry.setTag("trace_id", currentTraceId()); // jump from the issue to the request (19.2b)
```

> **Aside — the fingerprint replaces the default entirely.** With this rule, two different call sites that both hit `POST /projects/:id/members` with a 422 become one issue, even if they are different bugs in different components. When the caller matters, add the SDK's default-grouping placeholder (`"{{ default }}"`) to the array, or mark the API client's module as not in-app so the default grouping reaches the caller. Either way, you're choosing what "one defect" means, and no setting can choose it for you.

> **Aside — dropping status 0 hides real outages.** If your API goes down, every client sees network failures, and this filter sends none of them to the tracker. That's acceptable only because server-side SLO alerts (16.3) will catch an outage. If the browser is your only vantage point, for example for a third-party API called directly from the client, count these failures as a metric instead of discarding them.

## Further Reading

- **Sentry documentation on grouping, fingerprint rules, and stack trace rules.** The most detailed public explanation of how a tracker decides that two events are the same defect, and how to override it.
- **Sentry documentation on source maps and debug IDs, releases and release health, filtering, and ad-blocker tunneling.** The practical configuration behind most sections of this article.
- **ECMA-426, the Source Map Format specification.** The now-standardized format underneath every JavaScript symbolication pipeline.
- **MDN: `Error.cause`, the `crossorigin` attribute, and `window.onerror`** (including the `Script error.` explanation). The browser behavior this article depends on.
- **Node.js documentation, `process` events (`uncaughtException`, `unhandledRejection`)** and the `--enable-source-maps` flag. Includes the explicit warning against resuming after an uncaught exception.
- **React documentation on error boundaries.** Where rendering errors are caught, and what an unhandled one does to the page.
- **_The Site Reliability Workbook_ (Google), "Canarying Releases."** How to compare a new release against the old one before it reaches everyone, and why error signals belong in that comparison.
- **Firebase Crashlytics documentation.** Crash-free users as a release metric, and symbol upload for iOS and Android.
- **GlitchTip.** An open-source, Sentry-compatible tracker, useful for costing the self-hosted option.
- **ESLint `prefer-promise-reject-errors` and typescript-eslint `only-throw-error`.** The two rules that keep stack-less events out of your tracker.

A Go sibling would be worth writing, because Go breaks the assumption this whole article rests on. Go errors are values without stack traces. A tracker's Go SDK captures the stack at the point where you *report* the error, which is usually one central handler, so every error reported there shares the same frames and over-groups into one issue, much like `ApiError` here. Grouping then depends on wrapped message chains, where `fmt.Errorf` with variable data splits one defect into thousands. Panics carry stacks and ordinary errors don't, so the article would be about recovering what JavaScript provides for free. Not yet written.

---

The habit to carry out of this: whenever a tool produces a list for people to act on, ask what one row represents, and whether a person can ever close it. A list whose top row can never be closed teaches everyone to stop reading the list, and the next real problem arrives in a list nobody reads.
