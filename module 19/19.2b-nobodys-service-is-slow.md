# Nobody's Service Is Slow

_Module 19.2b — Logging, Monitoring & Observability_

## The Problem

A food-delivery platform. Placing an order touches four services. The `orders` service receives `POST /orders`, asks `restaurant` whether each item is available, asks `payments` to authorize the card, writes the order, and publishes an `order.placed` message that a `dispatch` worker picks up to find a courier. Each service belongs to a different team, and each team has good dashboards: request rate, errors, and latency percentiles per endpoint (16.3).

Tuesday afternoon, the p99 of `POST /orders` climbs from 400ms to 2.8 seconds. The incident call starts with every team's dashboard:

```
orders       POST /orders             p99  2,810ms   ▲ was 400ms
restaurant   GetAvailability          p99    150ms   ─ unchanged
payments     Authorize                p99    300ms   ─ unchanged
postgres     orders INSERT            p99     25ms   ─ unchanged
```

Every downstream service is exactly as fast as it was yesterday. Each team says, accurately, that the problem isn't theirs. The orders team can see that its endpoint is slow, but its own code does almost nothing except call the others.

Logs don't help either. Each service generates its own request ID at its own edge (19.1a), so a log line in `restaurant` can't be tied to the order that caused it. Two hours of the call are spent adding timing log lines and redeploying.

Here is what the answer looks like once the request is traced:

```
POST /orders                                       ████████████████████████████  2,810ms
├─ auth.verify                                     █                                18ms
├─ restaurant GetAvailability   item 1              █                              118ms
├─ restaurant GetAvailability   item 2               █                             121ms
│    … items 3–11, one after another …
├─ restaurant GetAvailability   item 12                        ████████  timeout  1,000ms
├─ restaurant GetAvailability   item 12 (retry)                        █           160ms
├─ payments Authorize                                                   ███        290ms
└─ postgres INSERT orders                                                  █        21ms
```

No call is slow. A refactor on Tuesday replaced one batched availability call with a call per cart item, made one after another. A twelve-item cart now makes twelve network round trips in series, and whenever one of them hits the 1-second client timeout, a retry is added on top. Latency grows with cart size, and the per-call latency on `restaurant`'s dashboard never moves, because every individual call is still fast.

A second question from the same week goes unanswered for days: couriers are sometimes assigned 40 seconds after an order is placed. The dispatch worker's own timing says it processes a message in 200ms. Nothing records how long the message waited in the queue before the worker started.

Aggregate metrics describe each service separately. The question was about *one request's path through all of them*: how many calls, in what order, how long each took, and where the remaining time went.

## What It Is

This is **distributed tracing**. A **trace** records one request's journey through a system as a tree of **spans**. A span is a single named, timed operation: an incoming HTTP request, an outgoing call, a database query, a message being processed. Each span records:

- a **trace ID**, shared by every span in the trace;
- its own **span ID**, and its **parent's span ID**;
- a name, a start time, and a duration;
- **attributes**, such as `http.response.status_code=200` or `cart.items=12`;
- a **status** (ok or error), and optional timestamped **events**, such as a recorded exception.

The parent pointers are what build the tree. **Context propagation** is what makes those pointers possible across process boundaries: each service passes the trace ID and its current span ID to the next one, typically in an HTTP header.

One disambiguation, since 19.1a made it tempting to think this problem was already solved. A **correlation ID** in logs tells you *which* lines belong to the same request. A **trace** tells you the request's *causal structure and timing*: who called whom, in what order, in series or in parallel, and how long each step took. A correlation ID would have let the team find all of the Tuesday request's log lines. Only the trace shows the staircase.

Two naming notes. **OpenTelemetry** (OTel) is the vendor-neutral standard for the instrumentation side: the API, the SDKs, the wire protocol, and the attribute conventions. **Jaeger, Zipkin, Grafana Tempo**, and commercial APM products are backends that store and display traces. Choosing a backend is 19.3a.

## Recognizing the Problem

- An endpoint is slow while every service it depends on looks normal on its own dashboard.
- Incident calls turn into a round of "not us" across teams.
- Latency grows with the size of the input (cart items, page size, number of recipients), which suggests hidden fan-out.
- Nobody can say how many downstream calls a given endpoint makes.
- Request IDs stop at the service boundary.
- Work behind a queue is slow, and you can't tell whether it's waiting or working.
- Calls succeed, but slowly, and nobody can see the retries inside them.
- A caller logs a timeout at 1 second while the callee logs a success at 1.2 seconds, and nobody can line the two up.
- A p99 regression appears after a deploy, and aggregate metrics can't say which step got slower.

## How It Works

### Spans, trees, and gaps

A waterfall view draws each span as a bar on a shared timeline, indented under its parent. The shape tells you things before you read any numbers:

- **Siblings that overlap** ran in parallel. **Siblings in a staircase** ran in series.
- **A parent much longer than its children** spent the difference somewhere uninstrumented: its own CPU work, a garbage-collection pause, a lock, or, very often, **waiting for a connection from a pool**. A `db.query` span of 20ms under a 400ms parent with nothing else in it usually means 380ms of waiting that nobody recorded.
- **A span that ends in error, followed by a similar span,** is a retry. The caller may report success for the whole operation.

A missing child is dangerous precisely because it doesn't look like anything. Time spent in an uninstrumented downstream call appears as the parent's own time, so an incomplete trace points confidently at the wrong code.

### Propagation: in the process and on the wire

Inside a process, the current span lives in the same request-scoped context 19.1a used for log fields: Go's `context.Context`, Node's `AsyncLocalStorage`, a `ThreadLocal` in Java. It drops at the same boundaries too (Module 5's list): new goroutines and thread pools, pooled-client callbacks, background jobs.

Between processes, the caller **injects** the context into a carrier, and the callee **extracts** it and starts a child span. For HTTP, the W3C Trace Context standard defines the header:

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                └─ flags: 01 = sampled
             │  │                                └─ parent span ID (the caller's span)
             │  └─ trace ID, shared by the whole trace
             └─ version
```

A companion `tracestate` header carries vendor-specific data. A separate W3C standard, `baggage`, carries arbitrary application key-value pairs. Module 5's warning applies to baggage: it's unauthenticated, and it travels to every downstream hop, including third parties.

```
orders                               restaurant
┌──────────────────────────┐         ┌────────────────────────────┐
│ span: GetAvailability    │  HTTP   │ extract traceparent        │
│ (CLIENT)                 │────────►│ span: GetAvailability      │
│ inject traceparent ──────┼─header─►│ (SERVER), parent = caller  │
└──────────────────────────┘         └────────────────────────────┘
```

A trace is only as complete as its weakest hop. A proxy that strips unrecognized headers, an HTTP client created without instrumentation, a service in a language nobody instrumented, or a vendor API all break the chain. A broken chain doesn't produce an error. It produces two separate traces, and the second one's root span is really somebody's child.

A service mesh doesn't remove this requirement. A sidecar sees an inbound request and, later, an outbound request, but it can't know they're related unless the application copies the context from one to the other. Istio's documentation says so explicitly.

### Trust at the edge

Propagation headers from the public internet are untrusted input. A client can set the sampled flag on every request to force you to record all of its traffic, which multiplies your tracing costs. It can also choose trace IDs that collide with or pollute other traces. The usual policy is to ignore inbound context at public edges and start a new trace there, optionally recording the caller's context as a **link** (below). Honor inbound context from your own gateways and first-party clients.

The same caution applies outbound. Sending `traceparent` and `baggage` to third-party APIs reveals internal identifiers and whatever baggage holds. Strip them unless you've agreed with that party to trace across the boundary.

### Instrumentation: automatic, then manual

**Automatic instrumentation** wraps the libraries every request passes through: HTTP servers and clients, gRPC, database drivers, and queue clients. Depending on the language, this is an agent that rewrites bytecode (Java), module patching at load time (Node, Python), or wrapper libraries you apply explicitly (Go). It gives you the skeleton of every trace for almost no effort. It tells you *where* the time went.

**Manual instrumentation** adds the spans and attributes only your code can supply: a span around "check availability" that groups the twelve calls, `cart.items=12`, `restaurant.id`, the customer's plan, which feature flag was on. It tells you *why*. With `cart.items` recorded, "latency rises with cart size" is a query rather than a hunch.

A few rules for what to record:

- **Span the meaningful units, not every function.** Network calls, queue operations, and named business steps deserve spans. A loop over 10,000 items does not get 10,000 spans. Record a count, or one span for the batch.
- **Use the OpenTelemetry semantic conventions** for common attributes (`http.request.method`, `db.system`, `server.address`). Backends and dashboards understand them without configuration. They have been renamed between versions, so pin the version you use.
- **High-cardinality attributes are welcome, personal data is not.** Order IDs and tenant IDs make traces searchable, just as they do for 19.1a's wide events. Everything in 19.1b applies here too. Check what your auto-instrumentation records by default: full URLs with query strings, and database statements, which can include literal values.
- **Record errors on the span** where they happen, with status set to error. A parent that handles a child's error, for example by retrying, can reasonably report success.

### Asynchronous work: queues, batches, and delays

A message is just another carrier. The producer injects context into message headers or attributes, and the consumer extracts it. How the consumer's span relates to the producer's depends on the shape of the work:

```
one message, one request              a batch of many messages           work days later

POST /orders                          trace A ─ publish ┐                trace A: POST /bookings
└─ publish order.placed (PRODUCER)    trace B ─ publish ┼─ links ─┐        └─ schedule reminder
   ···· queue wait ····               trace C ─ publish ┘         │      trace B (new root):
   └─ process order.placed            ─────────────────────────   │        send reminder
      (CONSUMER, child)               trace D: process batch ◄────┘        └ link → trace A
                                      (new root, 3 links)
```

- **One message, handled on behalf of one request:** make the consumer's span a child of the producer's. The gap between them is queue wait, which answers the 40-second courier question at a glance. Also record the wait as an attribute, so it can be queried across many traces.
- **A batch built from many messages:** a span can have only one parent, so the batch span starts a new trace and carries **links** to each message's context.
- **Work that runs much later:** a reminder email three days after a booking makes a useless waterfall, and many backends cap trace duration anyway. Start a new trace and link it to the original.
- **Scheduled jobs:** each run is a new root trace.

Module 10 asked for `trace_id` in job payloads. The propagator's inject and extract calls are the mechanism for that.

### Sampling, briefly

Recording every span of every request is usually unaffordable. At 2,000 requests per second with 30 spans per request, you're writing 60,000 spans per second. **Head sampling** makes the keep-or-drop decision once, at the root, and sends it downstream in the `sampled` flag. Downstream services then use a **parent-based** sampler and follow that decision, so each trace is either complete or absent.

A ratio sampler keyed on the trace ID keeps, say, 10% of traces, and every service computes the same answer for the same trace ID. A service that makes its own independent decision produces traces with holes, which is the misleading kind of incomplete trace described above.

Head sampling decides before anything interesting has happened, so it discards most errors and slow requests along with everything else. **Tail sampling** buffers whole traces and decides afterward (keep all errors, all slow traces, and a fraction of the rest). That requires collector infrastructure, which is 19.3a.

Either way, sampled traces can't tell you *how many*. Rates and percentiles come from metrics (16.3), traces supply examples, and exemplars connect the two.

### Joining traces and logs

Put `trace_id` and `span_id` on every log line; 19.1a's context handler can read them from the same context. From a trace you can then jump to exactly its logs, and from a log line you can open its trace.

The two overlap, and it's worth choosing deliberately. A span event and a log line can record the same fact. Detail about a specific operation within a request often reads best as span attributes and events. Anything outside a request, or anything that must survive trace sampling, belongs in logs.

### Clocks

Spans from different machines are timestamped by different clocks. Each duration is measured on a single clock, so durations are trustworthy. Placing spans from different hosts on one timeline is approximate, though, and clock skew can make a child appear to start before its parent. Some backends, Jaeger among them, adjust for skew. Don't read meaning into cross-host ordering at the millisecond level.

### Reading a trace

Most slow traces match one of a handful of shapes:

- **The staircase:** serial calls that could run in parallel or be batched. That was Tuesday's problem.
- **The comb:** many identical child calls, the network version of the N+1 query from 6.4 and 8.3.
- **The gap:** parent time with no children. Look for pool waits, locks, GC pauses, or a missing instrumentation hop.
- **The retry pair:** an error, then the same call again. Timeouts shorter than the callee's p99 make this constant.
- **The deep chain:** A calls B calls C calls D. Latency adds up and availability multiplies (1.2).
- **The mismatch:** a client span much longer than its server span.

The mismatch deserves a picture, because it's where two teams' logs disagree:

```
orders      ├── CLIENT  restaurant GetAvailability ───────────── 480ms ──┤
restaurant       ├── SERVER GetAvailability ── 60ms ──┤
            └────┘                                     └──────────────────┘
            waiting before the server began:           after the server finished:
            client pool, DNS, TLS, the callee's        response transfer, a slow proxy,
            accept queue                               client-side processing
```

Both teams are telling the truth. The 420ms belongs to the space between them, and only the pair of spans reveals that it exists.

## When It's Appropriate

- **Requests that cross more than two or three services,** especially services owned by different teams, where "which step got slower" otherwise takes a meeting.
- **Fan-out endpoints.** GraphQL resolvers (Module 8), aggregators, and anything whose downstream call count depends on input size.
- **Asynchronous pipelines.** Producer, queue, consumer, and further publishes, where queue wait is part of the user's experience.
- **Latency SLOs that depend on other teams' services.** Attributing an error-budget burn to a specific hop requires per-request paths.
- **A monolith with many external calls.** A span per query and per outbound call inside a span per request answers "where did the 900ms go" without arithmetic, even with one deployable.
- **Partial failures and retries,** where a call that "succeeded" hid two failed attempts.

## When It's Unnecessary or Overkill

- **Extensive manual instrumentation for a single service with one database,** where per-request query counts (6.4) and the slow-query log already answer the questions. Automatic instrumentation may still be worth its near-zero effort.
- **Spans for every item in a batch job.** A million-row import doesn't need a million spans. Count items and span the batches.
- **Recording 100% of traces at high volume** for the sake of completeness. Sample, and use metrics for totals.
- **Building your own tracing library.** OpenTelemetry exists, and every backend accepts its format.
- **Traces as your alerting source.** Sampled, delayed, and expensive to query. Alert on metrics.
- **A span for every function call.** It makes traces unreadable and adds overhead without adding insight.

## Trade-offs

- **Runtime overhead.** Every span costs allocations, clock reads, and export work. It's small per request, and not small inside hot loops.
- **Storage cost.** At scale, traces are often the largest observability bill. Sampling reduces it and gives up data.
- **Weakest-hop completeness.** One unpropagating proxy or client produces partial traces, and a partial trace misattributes time without any visible error.
- **Instrumentation upkeep.** Library upgrades change span names, and semantic-convention versions rename attributes (`http.method` became `http.request.method`), silently breaking saved queries.
- **Sensitive data by default.** Auto-instrumentation can record URLs, query strings, and statements. The review 19.1b describes has to cover traces too.
- **Propagation is an attack and disclosure surface.** Inbound context can force sampling, and outbound context can leak identifiers and baggage.
- **Async shapes don't fit a tree.** Links are the right model for batches and delayed work, and many UIs display them poorly.
- **Timelines across hosts are approximate** because of clock skew.
- **Sampled traces can't count.** "How often does this happen?" still needs metrics.
- **Lock-in moves rather than disappears.** OpenTelemetry standardizes the instrumentation, but each backend's query language and UI are its own.

## Alternatives

- **Correlation IDs in logs** (19.1a). Cheap, and the right first step. They tell you which lines belong together, not how long each step took or what caused what.
- **Wide events with trace IDs** (19.1a). One rich event per service per request, joined by trace ID. A trace is essentially a set of wide events with parent pointers, and some teams find wide events alone sufficient.
- **Per-dependency metrics** (16.3). RED metrics on each client call show that `restaurant` is slow, or called more often, in aggregate. They can't show a single request's path.
- **Service-mesh telemetry.** Network-level spans without code changes, as long as the application still forwards the context headers.
- **eBPF-based observability.** Kernel-level capture of network calls with no code changes, and limited ability to connect them causally across a process.
- **Continuous profiling.** Answers where CPU time goes *inside* one process, which traces show only as an unexplained gap.
- **Timing log lines.** What the Tuesday call did for two hours. It works, slowly, and must be redone for each incident.

## How to Achieve It

**Level 0 — propagate one ID across calls.** Even before tracing, forward the request ID to downstream services and log it there.
_Signal you're here:_ request IDs stop at the service boundary.

**Level 1 — OpenTelemetry with automatic instrumentation on the main request path.** Add the SDK to each service, use a parent-based ratio sampler, and export to any backend, even a single-container Jaeger.
_Signal you need it:_ cross-service latency questions are being answered in meetings.

**Level 2 — close the gaps.** Make gateways and proxies forward `traceparent`, inject and extract context around every queue, carry context in job payloads, and decide trust at the edge.
_Signal you need it:_ traces that end at a queue, a gateway, or a particular service.

**Level 3 — add meaning.** Manual spans for business steps, attributes such as `cart.items`, spans around pool acquisition, pinned semantic conventions, and a sensitive-data review of attributes.
_Signal you need it:_ waterfalls with unexplained gaps, or slow traces you can't group by anything useful.

**Level 4 — join the signals.** Trace IDs on every log line, exemplars on latency histograms, and links from dashboards into traces.
_Signal you need it:_ investigations that bounce between tools with no shared key.

**Level 5 — sample for value and analyze in aggregate.** Tail sampling, metrics and service graphs derived from spans (19.3a), and cross-service trace analysis (36.4).
_Signal you need it:_ the tracing bill, or interesting traces that head sampling threw away.

## Implementation

**Go with OpenTelemetry.** Go carries context explicitly, so every propagation step is visible in the code, including the ways it breaks.

Setup: a sampler that follows the caller's decision, W3C propagation, and a shutdown hook.

```go
func initTracing(ctx context.Context) (shutdown func(context.Context) error, err error) {
	exp, err := otlptracegrpc.New(ctx) // endpoint from OTEL_EXPORTER_OTLP_ENDPOINT
	if err != nil {
		return nil, err
	}
	tp := sdktrace.NewTracerProvider(
		sdktrace.WithBatcher(exp),
		sdktrace.WithResource(resource.NewWithAttributes(semconv.SchemaURL,
			semconv.ServiceName("orders"))),
		// Follow the caller's decision; decide 10% ourselves only at a root.
		sdktrace.WithSampler(sdktrace.ParentBased(sdktrace.TraceIDRatioBased(0.10))),
	)
	otel.SetTracerProvider(tp)
	otel.SetTextMapPropagator(propagation.TraceContext{})
	return tp.Shutdown, nil // call during graceful shutdown (19.2a), or the last batch is lost
}
```

Automatic spans on the server and client, a manual span that explains the staircase, and a trust decision at the public edge:

```go
var tracer = otel.Tracer("orders")

// Public edge: start a new trace here and link to any inbound context
// instead of adopting it as the parent.
mux.Handle("POST /orders", otelhttp.NewHandler(
	http.HandlerFunc(srv.placeOrder), "POST /orders", otelhttp.WithPublicEndpoint()))

restaurantClient := &http.Client{Transport: otelhttp.NewTransport(http.DefaultTransport)}

func (s *Server) checkAvailability(ctx context.Context, cart Cart) error {
	ctx, span := tracer.Start(ctx, "check availability",
		trace.WithAttributes(attribute.Int("cart.items", len(cart.Items))))
	defer span.End()

	for _, item := range cart.Items { // Tuesday's staircase: one call per item, in series
		if err := s.restaurant.Available(ctx, item); err != nil {
			span.RecordError(err)
			span.SetStatus(codes.Error, "availability check failed")
			return err
		}
	}
	return nil
}
```

> **Aside — three ways to break the tree without an error.** First, `tracer.Start` returns a *new* context holding the new span. Keep passing the old one and the twelve calls become siblings of "check availability" instead of its children. Shadowing `ctx`, as above, is the idiom that prevents this. Second, the instrumented transport reads the span from `req.Context()`, so a request built with `http.NewRequest` or sent with `http.Get` carries `context.Background()` and starts an unrelated trace. Use `http.NewRequestWithContext`. Third, a goroutine given `context.Background()` "because the request might finish first" becomes an orphan root; `context.WithoutCancel(ctx)` keeps the span without the cancellation (19.1a).

Across the queue, the producer injects and the consumer extracts. The same carrier supports links for batches:

```go
func (p *Publisher) OrderPlaced(ctx context.Context, o Order) error {
	ctx, span := tracer.Start(ctx, "publish order.placed",
		trace.WithSpanKind(trace.SpanKindProducer))
	defer span.End()

	headers := map[string]string{}
	otel.GetTextMapPropagator().Inject(ctx, propagation.MapCarrier(headers))
	return p.queue.Send(ctx, "order.placed", o, headers)
}

func (c *Consumer) handle(msg Message) error {
	parent := otel.GetTextMapPropagator().Extract(context.Background(),
		propagation.MapCarrier(msg.Headers))
	ctx, span := tracer.Start(parent, "process order.placed",
		trace.WithSpanKind(trace.SpanKindConsumer),
		trace.WithAttributes(attribute.Int64("app.queue_wait_ms",
			time.Since(msg.SentAt).Milliseconds()))) // the 40-second courier question
	defer span.End()
	return c.dispatch(ctx, msg.Body)
}

func (c *Consumer) handleBatch(batch []Message) error {
	links := make([]trace.Link, 0, len(batch))
	for _, m := range batch {
		mctx := otel.GetTextMapPropagator().Extract(context.Background(),
			propagation.MapCarrier(m.Headers))
		links = append(links, trace.LinkFromContext(mctx))
	}
	ctx, span := tracer.Start(context.Background(), "process order.placed batch",
		trace.WithSpanKind(trace.SpanKindConsumer), trace.WithLinks(links...))
	defer span.End()
	return c.dispatchAll(ctx, batch)
}
```

> **Aside — queue wait inherits clock skew.** `msg.SentAt` should come from the broker (most brokers stamp messages on arrival) rather than the producer's clock. Even then, it's compared against the consumer's clock, so treat small values as approximate and large ones as real.

Finally, the join with 19.1a. Its context handler gains a few lines:

```go
if sc := trace.SpanContextFromContext(ctx); sc.IsValid() {
	r.AddAttrs(slog.String("trace_id", sc.TraceID().String()),
		slog.String("span_id", sc.SpanID().String()),
		slog.Bool("trace_sampled", sc.IsSampled()))
}
```

> **Aside — unsampled requests have trace IDs too.** A request that head sampling dropped still gets a valid trace ID, and its log lines carry it, so following that ID to the tracing backend finds nothing. `trace_sampled` tells the reader in advance whether a trace exists. (The OpenTelemetry slog bridge, `otelslog`, does this wiring for you if you'd rather not maintain it.)

## Further Reading

- **W3C Trace Context** and **W3C Baggage** recommendations. Short, precise, and the definition of the headers above, including the rules for mutating `tracestate`.
- **OpenTelemetry documentation:** the *Traces* and *Context propagation* concept pages, and the semantic conventions for HTTP, databases, and messaging. The messaging conventions cover producer and consumer spans and when to use links.
- **Benjamin Sigelman et al., "Dapper, a Large-Scale Distributed Systems Tracing Infrastructure"** (Google, 2010). The paper most modern tracing descends from, including its arguments for low-overhead sampling.
- **Yuri Shkuro, _Mastering Distributed Tracing_** (Packt). From the creator of Jaeger; strong on propagation, sampling, and the organizational side of instrumenting many services.
- **Austin Parker et al., _Distributed Tracing in Practice_** (O'Reilly). A practical guide to rolling tracing out across an existing system.
- **Cindy Sridharan, _Distributed Systems Observability_** (O'Reilly report). A short treatment of how logs, metrics, and traces relate, and what each can't do.
- **OpenTelemetry Go contrib, `otelhttp` package documentation.** Including `WithPublicEndpoint` and how span names and attributes are chosen.
- **Istio documentation, "Distributed Tracing"** (the FAQ on header propagation). The authoritative statement that a mesh can't join spans unless the application forwards context.
- **Jaeger** and **Grafana Tempo** documentation. Two open-source backends, including Jaeger's approach to clock-skew adjustment.

A Java sibling would be worth writing, because the OpenTelemetry Java agent inverts this article's experience. It rewrites bytecode at startup, instruments common executors so context crosses thread pools automatically, and covers most popular libraries with no code changes. Many of the "broken tree" failures above never appear. What appears instead is instrumentation you can't see or easily reason about, gaps in reactive pipelines and less common libraries that the agent doesn't cover, and the question of how to add business attributes to spans you didn't create. Not yet written.

---

The habit to carry out of this: when something is slow, ask *how many times, and in what order* before asking *which call is slow*. Per-call latency rarely changes much between Monday and Tuesday. Call counts and call shapes change with every refactor, and no per-service dashboard will show you either one.
