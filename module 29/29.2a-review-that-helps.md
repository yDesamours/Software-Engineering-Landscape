# Review That Helps: Code Review as a Fast Feedback Loop

_Module 29.2a — Version Control & Collaboration_

## The Problem

Suppose you're on a team of eight building practice-management software for independent veterinary clinics: appointments, medical records, prescriptions, stock of medicines, and billing. About 900 clinics use it. Every change needs one approval before it can merge. Everyone agrees review matters. Here's what it looks like in practice:

**Changes wait longer than they take to write.** The median pull request waits 26 hours for a first comment, and a typical one goes through three rounds. A change that took half a day to write takes four days to merge. While waiting, authors start something else, so when comments arrive they've lost the context, and branches live far longer than the team's two-day target (29.1a).

**Big changes get less scrutiny than small ones.** An 1,800-line pull request reworking prescription labels is approved in eleven minutes with "LGTM" (looks good to me). Buried in it, a dose calculation takes the weight from a form that records pounds and treats it as kilograms, which is what the rest of the system stores. A clinic catches it when a label for a 20 kg dog, entered as 44 lb, shows a dose sized for a 44 kg dog. The same week, a 12-line change to appointment reminders gets 40 comments, most of them about variable names.

**One person reviews most of the code.** The most senior developer reviews 60% of all pull requests. She's the only one who understands the stock and controlled-drugs code, so everything touching it waits for her. When she's on holiday, the review queue doubles.

**Comments land badly.** "Why would you do it this way?" and "This is wrong" are common. A junior developer stops opening pull requests until her work is "finished," which means large, late pull requests, which get the least useful review.

**Nobody knows which comments matter.** A pull request has fourteen comments. Two are real problems, nine are preferences, three are questions. The author can't tell which is which, so either fixes all of them or argues with all of them.

**Design problems surface too late.** A developer spends three days building a new invoicing export. The reviewer's first comment is that it should reuse the existing reporting pipeline. He's right, and three days of work are thrown away.

Review is working as a gate here: a checkpoint changes must pass. Almost none of the problems are about people doing review wrong. They come from nobody treating review as a feedback loop with a purpose, a size, and a speed.

## What It Is

**Code review** is someone other than the author reading a change before it's merged, to catch problems and to share understanding of the code. On most teams today it happens through pull requests (or merge requests) on a hosting platform, which is sometimes called **modern code review**, as opposed to older formal inspections done in meetings.

What review actually produces is broader than bug-finding. A frequently cited Microsoft study (Bacchelli and Bird, 2013) found that developers' main stated reason for review was finding defects, but that most review comments were about readability, maintainability and alternative approaches, and that knowledge transfer and team awareness were major outcomes. That matches most teams' experience: review is one of the main ways people learn a codebase, and one of the main ways a team keeps shared standards.

Nearby practices it's often confused with:

- **Automated checks** (tests, linters, type checkers, security scanners) catch what machines can. Review should rely on them, not repeat them. That's 29.2b.
- **Design review** happens before code is written, when changing direction is cheap. Code review is a poor place to discover the design was wrong.
- **Pair and ensemble programming** (32.2) review code as it's written, and can replace a separate review step.
- **Approval as a control.** In regulated or audited environments, "every production change was reviewed by a second person" is a compliance requirement (separation of duties). It's a legitimate reason to require review, and it's a different purpose from feedback, with different needs.

## Recognizing the Problem

- Pull requests wait longer for a first review than they took to write.
- Large pull requests are approved quickly; small ones collect many comments.
- One or two people do most reviews, and some code can only be reviewed by one person.
- Review comments are mostly about formatting, naming, or style a tool could enforce.
- Authors can't tell which comments are blocking.
- People avoid opening pull requests until work is "done," or avoid reviewing certain colleagues.
- Pull requests go through many rounds, and threads turn into arguments.
- Bugs that reach production were in approved pull requests that nobody looked at closely.
- Big design changes are requested at review, after the work is finished.

## How It Works

### 1. Decide what review is for

A short list, roughly in the order worth spending attention:

1. **Does it do what it claims, including when things go wrong?** Edge cases, error paths, concurrency, units and time zones. Especially where tests are thin.
2. **Is it risky?** Data migrations, authentication and permissions, personal or medical data, money, anything irreversible.
3. **Does it fit the design** of the surrounding code, or introduce a second way of doing something the codebase already does?
4. **Will the next person understand it?** Names, structure, comments where the code can't explain itself.
5. **Do the tests prove the behavior**, and would they fail if it broke?

What review is **not** for: formatting, import order, lint rules, and personal taste. Anything a tool can check should be checked by a tool (29.2b), so human attention goes to the list above.

A useful standard for approval, from Google's public review guidelines: **approve when the change clearly improves the overall health of the code, even if it isn't perfect.** Review aims for better, not for the reviewer's ideal version. Without that standard, every review becomes a negotiation about preferences.

### 2. Size and speed are the main levers

**Size.** Reviewers can hold only so much in their heads. Industry studies of review, including a well-known Cisco study, found that the rate of problems found drops sharply once a review goes beyond a few hundred lines, or is read too fast. The 1,800-line prescription change was reviewed in eleven minutes because nobody can review 1,800 lines properly; the reviewer skimmed and approved. **The biggest improvement to review quality is usually smaller pull requests**, which is the slicing work of 28.4a and the short branches of 29.1a.

**Speed.** Look at where a pull request's time goes:

```
 writing   ██████                         4 h
 waiting   ████████████████████████████   26 h   ← first review
 fixing    ██                             1 h
 waiting   ██████████████                 12 h   ← second round
 fixing    █                              0.5 h
 waiting   ████████                       7 h    ← approval
```

Nearly all of it is waiting. Every wait is also a context switch for the author, and a reason to batch more into the next pull request. Google's published research on its own review process reported median review times of a few hours, with most changes small and reviewed by one person; its guidelines ask reviewers to respond within a working day at most, and sooner if possible.

A workable norm for most teams: **reviewing is higher priority than starting new work.** When you finish a task, or come back from a break, check the review queue before picking up something new. First responses within a few working hours. It feels slower for the reviewer and is much faster for the team.

When a thread goes back and forth more than twice, **move to a call** or sit together. Five minutes of conversation resolves what ten comments won't.

### 3. The author's job

Most of what makes a review good is decided before the reviewer opens it:

- **Keep it small and single-purpose.** Separate mechanical changes (renames, formatting, moves) from behavior changes, in different commits or pull requests (29.1b).
- **Write a description** that says why the change exists, what it does, what the reviewer should look at closely, how it was tested, and any risk. "Converts weight to kg before dose calculation; please check the rounding in `doseFor()`; tested with the three species in the fixtures" gets a better review than a title alone.
- **Review it yourself first.** Reading your own diff in the review tool catches leftover debug code and unclear names before anyone else spends time on them.
- **Ask early for anything large or uncertain.** A draft pull request with a sketch, or a short design note, gets the "reuse the reporting pipeline" comment on day one instead of day three.
- **Respond to every comment,** even with "done" or "leaving as is because …", so the reviewer doesn't have to check.

### 4. The reviewer's job

**Read in a useful order.** The description first, then the tests (they show what the author thinks the change does), then the core of the change, then the rest. For big changes, first check whether the overall approach is right before commenting on details; there's no point polishing lines that should be deleted.

**Say how much each comment matters.** The single change that most improves review threads is labeling comments. **Conventional Comments** is one widely used scheme:

```
 issue (blocking):  weight is in lb here but doseFor() expects kg. This would
                    over-dose. Convert at the boundary where the form value is read?
 suggestion:        splitting this into two functions would make the rounding
                    easier to test, but fine as is.
 question:          is this path reachable for exotic species with no weight recorded?
 nit:               typo in the log message.
 praise:            the fixtures for each species make this really easy to check.
```

The author can now see at a glance that one comment blocks the merge, one is optional, one needs an answer, and one is trivial. Teams that don't adopt a full scheme usually adopt the "nit:" prefix at least.

**Write comments about the code, with a reason.** Compare:

```
 ✗  Why would you do it this way?
 ✓  I think this queries the database once per prescription. With 200 items on a
    stock take that's 200 queries. Could we load them in one query? (6.4 has the pattern)
```

The second says what the problem is, why it matters, and what might fix it. Phrasing as a question when you're unsure ("Is this reachable when…?") invites the author's knowledge, which is often better than the reviewer's. Being specific about what's good matters as well; it's how the team learns what to keep doing, and it makes criticism easier to hear.

**Keep standards in shared places, not in individuals.** If a comment is really "we always do it this way," it belongs in a style guide, a linter rule, or an architecture decision record (2.5), so it stops depending on who reviews. Disagreements about preferences default to the author; disagreements about correctness or standards go to the written standard or, failing that, to the tech lead, and then the team moves on.

### 5. Who reviews, and how deeply

**Spread the load.** If one person reviews most changes, the team's speed is her speed, and her knowledge never spreads. Deliberately route reviews to other people, including less experienced developers: reviewing is one of the fastest ways to learn a codebase, and a junior reviewer's "I don't understand this" is useful information about readability. For areas only one person understands, pair a second reviewer with the expert for a while until they can review alone.

**Match depth to risk.** Not every change needs the same review:

- A typo in help text, a dependency bump with passing checks, or a change behind a switched-off flag can be reviewed lightly, or merged and reviewed afterwards.
- Most changes: one reviewer, normal attention.
- Controlled-drugs records, dose calculations, payments, permissions, migrations on large tables: a reviewer who knows the area, and perhaps two. Code owners (29.2b) can make this automatic.

## When It's Appropriate

- **Teams where review wait dominates cycle time,** visible in 29.1a's branch lifetimes.
- **Codebases with high-risk areas** (medical, financial, security-sensitive), where who reviews what matters.
- **Growing teams,** where review is how new people learn the codebase and its standards.
- **Teams with review threads that turn into arguments,** or where some people avoid reviewing or being reviewed.
- **Environments where review is a compliance control,** which need it to be real review and not a formality.

## When It's Unnecessary or Overkill

- **Two required approvals on every change** in a team of four. One person reading carefully is better than two skimming.
- **Mandatory review for trivial changes** like text fixes, generated files, or version bumps with passing checks, unless a compliance rule requires it.
- **Long review checklists.** A 40-item checklist is read once and then ignored. A short list of what matters most, plus automation, works better.
- **Formal comment labeling for a pair who talk all day.** They can just say which things matter.
- **Separate review for code written in a pair or ensemble** (32.2), unless compliance requires a second record.

## Trade-offs

- **Review costs time from the people who are often busiest.** Fast turnaround means reviewers interrupt their own work. Protecting focus time and responding promptly pull against each other, and the team has to choose a balance explicitly.
- **Review can create false confidence.** "Approved" is read as "checked," even when the reviewer skimmed. For a large change, an approval is weak evidence.
- **It can become a power structure.** Senior reviewers blocking on preferences, or reviews used to score points, teach people to avoid review, which leads to large pull requests and less review, not more.
- **Small pull requests mean more reviews,** each with its own switching cost. Reviewers who are asked for ten small reviews a day need a quick, reliable way to see them.
- **Spreading reviews to less experienced reviewers** may slow things down and miss issues at first. It's an investment in not depending on one person.
- **Risk-based depth needs judgment,** and occasionally a "light" change turns out to matter. Some teams decide that's a price worth paying; regulated teams usually can't.

## Alternatives

**Pair or ensemble programming** (32.2). Two or more people write the code together, so review happens continuously. It removes waiting entirely and spreads knowledge faster, at the cost of more people's time per change and a way of working not everyone enjoys.

**Ship / Show / Ask.** A pattern described by Rouan Wilsenach (martinfowler.com, 2021): *ship* straightforward changes straight to `main`, *show* changes you want others to see by merging and opening a pull request for after-the-fact discussion, and *ask* for review before merging only when you want input first. It needs strong tests and trust, and fits teams practicing trunk-based development (29.1a).

**Design review before code.** A short written proposal or a whiteboard session for any change that alters structure (2.5 on ADRs). It doesn't replace code review, but it moves the expensive comments to when they're cheap.

**Post-merge review.** The change merges once checks pass, and review happens within a day afterwards, with fixes in follow-up changes. Faster than pre-merge review, and acceptable when deploys are safe and reversible. It's usually not acceptable where review is a compliance control.

## How to Achieve It

**L0 — Measure where time goes:** time to first review, number of rounds, and pull request size. *Signal to move on:* waiting is most of the total.

**L1 — Agree on turnaround and size.** Review before starting new work, first response within a few hours, and a target size for pull requests. *Signal:* threads are long, and authors can't tell which comments block.

**L2 — Improve the conversation:** a pull request description template (29.2b), comment labels such as "nit:", and moving to a call after two rounds. Move recurring style comments into tools. *Signal:* one or two people do most reviews.

**L3 — Spread the load:** deliberately assign reviews across the team, pair up on areas only one person knows, and give code ownership to groups rather than individuals. *Signal:* everything gets the same review whether it's a typo or a dose calculation.

**L4 — Match depth to risk:** light or post-merge review for low-risk changes where allowed, expert review for high-risk areas, possibly Ship/Show/Ask.

## Implementation

TypeScript, one small report that makes the loop visible: how long pull requests wait, how size relates to review time, and who's doing the reviewing.

```ts
type PR = {
  number: number; linesChanged: number;
  openedAt: Date; firstReviewAt?: Date; approvedAt?: Date;
  reviewers: string[]; rounds: number;
};

const hours = (a: Date, b: Date) => (b.getTime() - a.getTime()) / 3_600_000;
const median = (xs: number[]) => [...xs].sort((a, b) => a - b)[Math.floor(xs.length / 2)] ?? 0;

export function reviewReport(prs: PR[]) {
  const reviewed = prs.filter((p) => p.firstReviewAt && p.approvedAt);

  // Large changes approved faster than anyone could read them.
  const skimmed = reviewed.filter((p) =>
    p.linesChanged > 400 && hours(p.firstReviewAt!, p.approvedAt!) < 0.5);

  // Share of reviews done by each person.
  const load = new Map<string, number>();
  for (const p of prs) for (const r of p.reviewers) load.set(r, (load.get(r) ?? 0) + 1);
  const total = [...load.values()].reduce((a, b) => a + b, 0);
  const share = [...load].map(([who, n]) => ({ who, share: n / total }))
                         .sort((a, b) => b.share - a.share);

  return {
    medianHoursToFirstReview: median(reviewed.map((p) => hours(p.openedAt, p.firstReviewAt!))),
    medianRounds: median(reviewed.map((p) => p.rounds)),
    largeButQuicklyApproved: skimmed.map((p) => p.number),
    reviewShare: share, // e.g. [{ who: "priya", share: 0.6 }, ...]
  };
}
```

On the vet team's data, this would show the 26-hour wait, the prescription pull request in `largeButQuicklyApproved`, and one reviewer at 60%.

> **Aside — use it to change the system, not to judge people.** Hours to first review include nights and weekends, and are distorted across time zones; working hours are fairer if your platform can compute them. "Large but quickly approved" can be legitimate: a generated file, or a change the reviewer paired on. Treat it as a question, not an accusation. And as with velocity (28.5a), these numbers stop meaning anything once individuals are ranked on them: reviewers will leave quick approvals, and authors will split changes to look fast rather than to be reviewable.
