# Before a Human Looks: Checks, Code Owners, Templates and Bots

_Module 29.2b — Version Control & Collaboration_

## The Problem

Suppose you're on a team of ten building ticketing software for small music venues and festivals: ticket sales, seating plans, door scanning on phones, and payouts of ticket money to organizers. About 2,000 organizers use it, and on a busy Friday it sells tens of thousands of tickets.

The team reviews every pull request (29.2a) and has a CI pipeline. Over six months, both are working against them:

**Reviewers spend their attention on things a machine could check.** About a third of review comments are about formatting, import order, or unused variables. The formatter is set up, but only some people's editors run it.

**CI runs, but nothing requires it to pass.** Two end-to-end tests fail about one run in five for no real reason, so people have learned to merge with a red build. In March, a real failure in the door-scanning tests was merged alongside the usual flaky ones. That Friday, scanners at three venues rejected valid tickets for 40 minutes.

**Risky code is reviewed by whoever's free.** A change to how card fees are deducted from payouts was approved by a developer who had never worked on payments. It rounded fees per ticket instead of per order, and organizers were paid slightly less than they should have been for two weeks. Afterwards, the team added a `CODEOWNERS` file listing the lead developer as owner of everything. Now every pull request waits for him.

**Bots talk more than people.** Every pull request gets a coverage comment, a bundle-size comment, a lint comment, a preview-deployment comment and, recently, an AI review bot that leaves fifteen to twenty suggestions. Each push adds a new set. Nobody reads them, including the one comment that mattered: a warning that a migration would lock the `tickets` table during a sale.

**The pull request template is fifteen sections long.** Most people delete it and write one line.

**A secret reaches the repository.** A developer commits a payment provider's API key in a test file. Secret scanning flags it an hour after the push. By then it's in history, and the key has to be rotated during a festival weekend.

**Dependency updates pile up.** The dependency bot opens about forty pull requests a week, one per package. They're ignored, and six months later the team is several major versions behind on the web framework.

Each tool here is a good idea. None of them was set up with a clear answer to what it should stop, what it should only point out, and who should be told.

## What It Is

The **merge gate** is everything that runs on a change before it can be merged, apart from the human reviewer: automated **checks** (build, tests, linters, scanners), **branch protection rules** that say what must be true before merging, **code owners** who are automatically asked to review changes to certain files, **pull request templates**, and **bots** that comment on or update pull requests.

The principle behind it is the division of labor from 29.2a: **machines check what can be checked mechanically, so people can spend their attention on judgment.** Every check that runs reliably is a comment no reviewer has to write, and a problem no reviewer can miss.

Two things this is often confused with:

- **Local Git hooks** (3.2) run on the developer's machine before a commit or push. They're a convenience for fast feedback, and they can be skipped. The merge gate is where rules are actually enforced.
- **The CI/CD pipeline as a whole** (Module 30) includes building artifacts and deploying. This article covers only the part that decides whether a change may merge.

## Recognizing the Problem

- Review comments regularly point out formatting, lint or typing problems.
- People merge with failing checks, or say "that test always fails."
- Checks take so long that people stop waiting for them.
- Changes to sensitive code (payments, authentication, migrations) are sometimes reviewed by people unfamiliar with it.
- One person is a required reviewer on most pull requests.
- Pull requests have more bot comments than human ones, and bot comments go unread.
- The pull request template is routinely deleted.
- Secrets have been found in the repository after being pushed.
- Dependency update pull requests accumulate unmerged.

## How It Works

### 1. Sort every check: blocking, advisory, or gone

For each check, decide which of three things it is:

- **Required (blocking).** The change can't merge unless it passes. A check belongs here only if it's **deterministic** (same code, same result), **fast enough** that people will wait for it, **meaningful** (a failure means a real problem), and **fixable by the author**.
- **Advisory.** Visible on the pull request, not blocking. Coverage changes, bundle size within limits, performance hints, AI review suggestions.
- **Not worth running.** Checks nobody acts on. Removing them makes the others easier to notice.

Flaky tests fail the first test, which is why the team learned to ignore red builds. The fix is to take them out of the required set and quarantine them (21.5), not to leave them required and train everyone that red means nothing. **A required check that sometimes fails for no reason is worse than no check,** because it teaches people to ignore the rest.

### 2. Fix automatically where you can

A check that says "formatting is wrong" costs the author a round trip. A tool that simply formats the code costs nothing. Where fixes are mechanical and safe, apply them:

- **Formatters** run on save or in a pre-commit hook, with a required check in CI that the code is formatted. The check fails only for people whose editors didn't run it, and the fix is one command.
- **Autofixable lint rules** (import order, unused imports) fixed the same way.
- Some teams let a bot push formatting commits to the pull request. It works, but it surprises people whose next push then conflicts.

What's left for humans after this is the list from 29.2a.

### 3. Keep it fast, and order it

People wait for checks that take a few minutes and stop waiting for checks that take forty. Rough guidance:

- **Fail fast.** Run type checking, lint and unit tests first, in parallel. Slow integration and end-to-end tests run after, or in parallel, so a typo fails in one minute, not twenty.
- **Run only what the change can affect** where tooling allows, for example only the services touched in a monorepo (29.4a).
- **Cache** dependencies and build outputs between runs.

One common trap with the last two: if a required check is configured to run only when certain paths change, on some platforms (GitHub, notably) a pull request that doesn't touch those paths never reports that check at all, and waits forever for a result that isn't coming. The usual fix is a job that always runs and reports success when there's nothing to check, or making the path decision inside the job.

### 4. Rules for merging

Hosting platforms let you encode merge rules as **branch protection** or **rulesets** on `main` and release branches. A reasonable default set:

```
 □ changes arrive through pull requests; no direct pushes
 □ required checks must pass (only the ones from section 1)
 □ at least one approval; code owner approval for owned paths
 □ no force-pushes or deletion of the branch (29.1b)
 □ rules apply to administrators too; bypass is logged
```

Two settings need a deliberate choice:

- **Requiring branches to be up to date with `main` before merging** catches two changes that pass separately and break together (29.1a). With many merges an hour, it forces everyone to rebase and rerun checks over and over. A **merge queue** gives the same protection without that churn.
- **Dismissing approvals when new commits are pushed** stops someone getting approval and then changing the code. It also means a one-line fix after review needs a second approval. Many teams keep it for owned, sensitive paths only.

### 5. Code owners for the risky parts

A `CODEOWNERS` file maps paths to the people or teams who must review changes to them. The platform requests their review automatically and, if configured, requires it.

```
# .github/CODEOWNERS — the last matching pattern wins

*                         @venuehub/engineering        # anyone on the team
/src/payouts/             @venuehub/payments
/src/scanning/            @venuehub/door-app
/db/migrations/           @venuehub/data
/src/auth/                @venuehub/security
/.github/CODEOWNERS       @venuehub/leads              # who can change the rules
```

How this avoids the bottleneck from the problem:

- **Own risky areas, not everything.** Payments, scanning, migrations and authentication need someone who knows them. A text change on the marketing page doesn't.
- **Owners are teams, not individuals.** Any member of `@venuehub/payments` can approve, so nobody's holiday blocks the queue. A team of one is a warning sign about knowledge concentration (29.2a), not a solution.
- **Protect the ownership file itself,** or anyone can remove themselves from review.

Code owners route review to people who know the area. They don't make those people review well; that's still 29.2a.

### 6. A template people will fill in

A pull request template should ask for what the reviewer needs and nothing else:

```
## Why
<!-- the problem or goal, and a link to the issue -->

## What to look at
<!-- the risky or tricky part; what you're unsure about -->

## How it was tested

## Risk
<!-- migrations, data changes, payments, rollout or feature flag -->
```

Four sections that take two minutes get filled in. Fifteen get deleted. Leave out anything a machine already checks ("I ran the linter," "tests pass"); checkboxes for those are just ritual. With squash merging, this description becomes the commit message on `main` (29.1b), so the "why" section is also what `git blame` will show in a year.

### 7. Bots that are worth reading

A bot comment competes for the same attention as a reviewer's. Rules that keep bots useful:

- **One comment per bot, updated in place,** not a new comment on every push.
- **Speak only when there's something to act on.** "Coverage unchanged" is noise; "coverage for `src/payouts` dropped from 91% to 64%" is information.
- **Use check statuses and line annotations for results,** and comments only for summaries. Annotations appear next to the relevant line in the diff, which is where people are looking.
- **Keep AI review advisory, and watch what it costs.** Limit the number of suggestions, and track how many are actually accepted. A bot whose suggestions are rarely taken is teaching people to ignore the pull request's comments.

**Checks that encode knowledge about risk** are where bots earn their place. The migration warning in the problem is an example: a migration linter (such as Squawk for PostgreSQL, or strong_migrations for Rails) knows which operations lock large tables (6.3). Others: a breaking-change check on the API specification (7.2, 33.2); a rule that payouts code must change with its tests; a warning on very large pull requests. These catch problems a reviewer might not know to look for, so they're often worth making required.

**Dependency updates.** One pull request per package per week is how updates get ignored. Group related updates into one pull request, schedule them weekly, and merge minor and patch updates automatically when all required checks pass. Major updates stay separate, since they're the ones that need reading. Renovate and Dependabot both support grouping and automatic merging.

**Secrets.** Scanning after a push is too late: the secret is in history and must be treated as leaked, rotated, and checked for misuse. **Push protection**, which rejects a push containing a recognized secret, and a local pre-commit scanner stop it before it gets there. Scanning afterwards remains useful as the backstop.

## When It's Appropriate

- **Any team where review comments repeat things a tool could check.**
- **Codebases with areas where mistakes are expensive:** money, access control, data migrations on large tables, systems used at a live event.
- **Teams growing past the point where everyone knows who understands what,** which is when code owners start to pay.
- **Repositories with many dependencies,** where update pull requests otherwise pile up.
- **Anything handling credentials,** where push protection is cheap insurance.

## When It's Unnecessary or Overkill

- **Code owners for a team of three** who all know the whole codebase.
- **Branch protection with two approvals, up-to-date branches and dismissed approvals** on a small internal tool. One required check and a pull request is plenty.
- **Custom rule bots** before the basics are in place. A formatter and a reliable required test run come first.
- **Making every advisory check required** because it exists. Coverage thresholds, in particular, invite trivial tests written to satisfy the number (21.4).
- **AI review on every pull request** when the team hasn't checked whether its suggestions get used.

## Trade-offs

- **Every required check is a way to be blocked.** A broken scanner or an outage at the CI provider stops all merges. You need a documented, logged way to bypass in an emergency, and the discipline not to use it routinely.
- **Checks take maintenance.** Rules go stale, linters get new versions with new complaints, and custom bots need an owner. Unowned checks become the noise in the problem.
- **CI time costs money and waiting.** Parallel, cached, selective runs help, and take engineering work to set up.
- **Code owners can become gatekeepers.** A team that owns a path can slow everyone else down, and ownership files can drift from who really knows the code.
- **Automation can replace thinking.** A green set of checks is easy to read as "safe," and reviewers may skip what they assume the tools covered.
- **Automatic merging of dependency updates** occasionally ships a broken release of a library, if tests don't exercise the part that broke. It's a bet that your tests are good enough; for critical dependencies, it may not be.
- **Stricter rules slow urgent fixes.** Dismissing approvals and requiring owners for a one-line hotfix at 2 a.m. has a real cost, which needs a decided answer before the incident, not during it (24.3).

## Alternatives

**Rely on local hooks only.** Pre-commit hooks for formatting, lint and secret scanning, with CI running tests. Faster feedback and simpler setup, but hooks can be skipped, and not everyone installs them. Fine for small teams; not enforcement.

**Trust and repair.** Few required checks, fast deploys, strong monitoring, and fixing forward when something breaks. Viable where mistakes are cheap and reversible, and part of the Ship/Show/Ask idea in 29.2a. It isn't viable for payouts or live-event scanning.

**Pairing instead of routing.** Rather than code owners, pair the author with someone who knows the area while writing the change (32.2). Knowledge spreads faster, and review is built in.

## How to Achieve It

**L0 — Make one test run required and trustworthy.** Quarantine flaky tests, require the rest, and stop merging on red. *Signal to move on:* review comments still cover formatting and lint.

**L1 — Automate formatting and lint:** fix on save and in hooks, with a required check in CI. Add secret push protection. *Signal:* risky areas get reviewed by people who don't know them.

**L2 — Add branch protection and code owners** for the risky paths, owned by teams. Shorten the pull request template. *Signal:* bots and dependency updates produce more noise than value.

**L3 — Reduce noise:** one comment per bot, updated in place; group and automatically merge low-risk dependency updates; make AI review advisory and measured. *Signal:* problems still slip through that a rule could have caught.

**L4 — Encode risk as checks:** migration linting, API breaking-change detection, rules for sensitive paths, and a merge queue when concurrent merges start breaking `main`.

## Implementation

TypeScript, one small rules script in the style of Danger JS. It runs in CI on each pull request, applies a few rules that encode the team's knowledge of risk, and keeps a single comment up to date instead of adding new ones.

```ts
type Finding = { level: "block" | "warn"; message: string };
type PRInfo = { files: { path: string; added: string[] }[]; linesChanged: number };

const rules: Array<(pr: PRInfo) => Finding | null> = [
  (pr) => {
    const src = pr.files.some((f) => f.path.startsWith("src/payouts/") && !f.path.includes(".test."));
    const tests = pr.files.some((f) => f.path.startsWith("src/payouts/") && f.path.includes(".test."));
    return src && !tests ? { level: "block", message: "Payouts code changed without payouts tests." } : null;
  },
  (pr) => {
    const risky = pr.files.filter((f) => f.path.startsWith("db/migrations/") &&
      f.added.some((l) => /ALTER COLUMN .* SET NOT NULL/i.test(l) || /CREATE (UNIQUE )?INDEX(?! CONCURRENTLY)/i.test(l)));
    return risky.length
      ? { level: "block", message: `Migration may lock a large table: ${risky.map((f) => f.path).join(", ")} (see 6.3)` }
      : null;
  },
  (pr) => pr.linesChanged > 600
    ? { level: "warn", message: `${pr.linesChanged} lines changed. Could this be split? (28.4a)` } : null,
];

export async function runRules(pr: PRInfo, upsertComment: (body: string) => Promise<void>) {
  const findings = rules.map((r) => r(pr)).filter((f): f is Finding => f !== null);
  // One comment, identified by a hidden marker and edited on each run.
  // With no findings it's replaced with a one-line "all clear" (or removed), never left stale.
  const body = "<!-- pr-rules -->\n" + (findings.length
    ? findings.map((f) => `${f.level === "block" ? "⛔" : "⚠️"} ${f.message}`).join("\n")
    : "✅ No rule findings.");
  await upsertComment(body);
  process.exit(findings.some((f) => f.level === "block") ? 1 : 0); // blocking rules fail the check
}
```

> **Aside — rules written as text patterns are crude, and that's a choice.** The migration rule matches SQL with regular expressions, looking for two PostgreSQL operations that block writes on the whole table while they run: `SET NOT NULL`, which scans every row under a lock, and an index built without `CONCURRENTLY`. It misses statements split across lines or generated by an ORM, and flags harmless ones on tables with ten rows. A proper migration linter parses SQL and knows more cases; use one where it exists, and keep hand-written rules for knowledge specific to your codebase, like "payouts need payouts tests." Every blocking rule also needs an escape hatch for the case it gets wrong, such as a label an owner can add, and that escape hatch should be visible in the pull request, so its use gets noticed.

---

The habit to take from this: **every time a reviewer writes the same comment twice, ask whether a tool should be writing it instead, and every time a tool speaks, ask whether anyone needs to hear it.** A merge gate is good when both answers are yes.
