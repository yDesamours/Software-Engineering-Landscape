# One Home for Each Thing: Docs in the Repo, Wikis, Trackers and Chat

_Module 29.3a — Version Control & Collaboration_

## The Problem

Suppose you're in an engineering group of fourteen, in two teams, building field-service software for heating engineers: job scheduling, the stock in each engineer's van, boiler service records, and invoicing. About 4,000 small heating businesses use it, and the busiest weeks are the first cold spells of autumn, when boilers break down everywhere at once.

The group uses GitHub for code, Confluence as the wiki, Jira for work, and Slack. The newer team prefers Notion and has started keeping its pages there. Everything technically exists somewhere. On the first cold Monday of October:

**The runbook is wrong.** The job-sync service, which sends new jobs to engineers' phones, stops processing. The on-call developer opens the Confluence runbook. It says to run `scripts/replay-sync.sh`. That script was renamed and rewritten eight months ago; the page was never updated. It takes 50 minutes to find the new script by searching the repository, while engineers across the country can't see their jobs.

**Setup instructions disagree with each other.** A developer who joined last week took four days to get the system running locally. The README says Node 18, a Confluence page says Node 20, the `.nvmrc` file says 22, and a Notion page from the other team has a different list of environment variables from both.

**A decision has disappeared.** The team wants to change how van stock is tracked: per van, rather than per depot. Somebody remembers there was a good reason it's per van. The discussion happened in a Slack thread two years ago, which the workspace's retention policy has since deleted. The two people involved have left.

**Hand-written API docs drifted.** A boiler manufacturer integrates with the warranty-registration API using a Notion page the team wrote for them. The page says the field is `serialNo`; the API has used `serialNumber` since March. The manufacturer's integration fails in testing, and their developers lose a week.

**The same page exists three times.** "How deployment works" is in Confluence, in Notion, and in the repository's `docs/` folder. They describe three different stages of the pipeline's history. Search in any one tool finds only its own copy.

**People outside engineering keep their own copies.** Support and product staff can't easily edit Markdown in the repository, so they write their own versions of how features behave, which drift from the product.

No single tool here is the wrong tool. The problem is that nobody decided which kind of knowledge lives where, so each piece ended up wherever its author happened to be.

## What It Is

A team's knowledge lives in several **collaboration tools**: the code host (GitHub, GitLab, Bitbucket), a wiki or workspace (Confluence, Notion), an issue tracker (Jira, Linear, GitHub Issues), and chat (Slack, Teams). Each has different properties: who can edit it, whether changes are reviewed, whether it's versioned with the code, how long it's kept, how searchable it is.

The practice this article is about is giving each **kind of knowledge one home**, chosen by how that knowledge changes, and linking to it from everywhere else rather than copying it. The home for knowledge that changes with the code is usually the repository itself, an approach called **docs-as-code**: documentation written in plain text (Markdown or similar) next to the code, changed in the same pull requests, reviewed the same way, and published by the same pipeline.

Related topics covered elsewhere in the map:

- **What to write** in a README, runbook or architecture document, and how to write it well, is 31.4.
- **Documentation-first culture** (writing things down by default, especially for remote teams) is 32.1.
- **Architecture decision records** as a format are 2.5. This article is about where they, and everything else, live.

## Recognizing the Problem

- Instructions that fail when followed: scripts, commands or settings that no longer exist.
- Two documents answer the same question differently, and nobody knows which is current.
- "Why is it built this way?" gets answered with "there was a thread about that somewhere."
- New developers take days to set up, mostly by asking people.
- The same page exists in more than one tool.
- Searching in one tool doesn't find what you need, because it's in another.
- Hand-written reference docs (APIs, configuration) disagree with the code.
- Non-engineers maintain their own copies of technical information.
- Nobody can say who owns a given page.

## How It Works

### 1. Sort knowledge by how it changes

The question that decides where something should live is: **what has to happen for this to become wrong?**

| Kind of knowledge | Becomes wrong when… | Home |
|---|---|---|
| Setup, build and run instructions; configuration reference; runbooks that call scripts; a service's architecture; ADRs about the code | the code changes | The repository, reviewed with the code |
| API references, CLI help, config schemas | the code changes, and they can be derived from it | Generated from the code, published by CI |
| Product specs, team processes, meeting notes, research, onboarding for non-engineers | people decide something new | Wiki or workspace |
| What's being worked on, status, who's doing what | work moves | Issue tracker |
| Discussion, questions, quick coordination | immediately | Chat, treated as temporary |

The runbook and the setup instructions in the problem were code-shaped knowledge living in a wiki: they became wrong when code changed, and nothing connected the two. The product behavior support needed was wiki-shaped knowledge the team had tried to keep in the repository, where the people who needed to edit it couldn't.

### 2. Docs-as-code for code-shaped knowledge

When documentation lives next to the code it describes:

- **It changes in the same pull request.** Renaming `replay-sync.sh` and updating the runbook are one change, and a reviewer can see if the second is missing.
- **It's reviewed** by the same people, with the same code owners for sensitive areas (29.2b).
- **It's versioned with the code.** Checking out last year's release gives you last year's instructions, which is what you want when maintaining a release branch (29.1a).
- **It can be checked by CI:** broken links, references to files that don't exist, formatting.

Plain Markdown in the repository is enough to start. As the amount grows, a static site generator (MkDocs, Docusaurus) or a developer portal (Backstage's TechDocs, for example) builds the Markdown from many repositories into one searchable site.

**Generate what can be derived.** Anything that can be produced from the code shouldn't be written by hand, because hand-written copies drift. The warranty API's reference should come from its OpenAPI specification (7.2), published on each release; configuration docs from the configuration schema; command-line docs from the tool's own help text. People write the explanations around the reference, not the reference itself.

**Make instructions executable where possible.** A runbook step that is a command should be a script in the repository, with the runbook linking to it. Setup instructions can be tested: a CI job that follows the README in a clean container fails when the README stops working. The strongest documentation is the kind that breaks the build when it's wrong.

### 3. Wikis for everything else, run deliberately

Wikis are the right home for knowledge written by many roles and changed by decisions rather than code: they're easy to edit, easy to comment on, and usable by people who don't use Git. They go stale for a different reason than repository docs: nothing links a page to the thing it describes. So they need habits that replace that link:

- **Every page has an owner,** a team rather than a person, shown on the page.
- **Pages carry a review date,** and owners are reminded to confirm or update them. Some tools support this directly (verified pages, page status), and a scheduled report of pages past their date works anywhere.
- **Structure is predictable:** one space per team or product area, with templates for recurring kinds of page (specs, meeting notes, post-mortems).
- **Archiving is normal.** A page nobody maintains is worse than no page, because people trust it. Moving it to an archive, marked as such, is maintenance, not loss.

### 4. Chat is where things are discussed, not where they're kept

Chat is where most decisions actually get made, and it's the worst place to keep them: threads are hard to find later, context is scattered, and retention policies delete old messages. The rule that fixes it: **a decision made in chat isn't finished until it's written somewhere durable.** Depending on the decision, that means:

- an ADR in the repository (2.5), for decisions about architecture, such as tracking stock per van;
- a comment on the ticket, for decisions about a piece of work;
- an update to the relevant page, for decisions about process or product.

Link back to the thread for context, but don't rely on it surviving. A lightweight habit helps: whoever closes a discussion with "OK, let's do X" writes it up, or asks someone to.

### 5. One home, many links

Once something has a home, every other tool **links to it rather than copying it.** The Notion page for the other team says "Deployment: see the docs site" with a link, instead of its own version. The Confluence onboarding page links to the README's setup section. A copy is a second page that will start drifting on the day it's made.

Links only help if people can find the starting point:

- **One entry point per product or service,** usually the repository README or a developer-portal page, that links to everything else: runbooks, ADRs, dashboards, the team's wiki space, the on-call rota.
- **Consistent names** across tools, so searching for "job-sync" finds the repository, the docs, the wiki space and the Jira project.
- **Cross-tool search**, which many organizations add once there are more than two or three tools, helps, but it can't fix duplicates; it just finds all three versions faster.

### 6. Detecting staleness

Some staleness can be checked mechanically:

- **Broken links**, inside the docs and to external sites.
- **References to things that no longer exist:** scripts, file paths, npm scripts, environment variables, API fields mentioned in docs but gone from the code (see Implementation).
- **Contradictions with the source of truth,** such as a documented Node version that doesn't match `.nvmrc`. Better still is not stating it twice: the README can say "the version in `.nvmrc`."
- **Age.** Pages past their review date, and repository docs untouched while the code around them changed a lot.

Much can't be checked: instructions that still run but no longer do the right thing, or explanations of design that's since changed. Those rely on docs being updated in the same pull request as the code, which is why the placement in section 1 matters more than any checker.

### 7. Choosing the platforms

The choice between GitHub, GitLab and Bitbucket, or between Confluence and Notion, matters less than having **one of each kind** and connecting them well. Things that genuinely differ and are worth weighing:

- **Integration** with what you already use: CI (GitHub Actions and GitLab CI are built in; Bitbucket pairs naturally with Jira and Confluence), the issue tracker, identity and single sign-on.
- **Hosting**: whether you need to run it yourself for regulatory or data-residency reasons (GitLab and the Atlassian Data Center products can be self-managed).
- **Permissions for non-engineers**: whether product, support and design staff can edit comfortably.
- **Migration cost**: moving later breaks links, loses history, and costs weeks. A second wiki "for our team" usually becomes a permanent split, as in the problem.

## When It's Appropriate

- **Any team where instructions have failed when followed,** especially runbooks used under pressure.
- **Groups using more than one wiki or workspace,** or where the same topic is documented in several places.
- **Teams whose reasoning is disappearing with chat history** or with people leaving.
- **Products with external integrators,** where reference docs must match the API exactly.
- **Codebases with release branches or several supported versions,** where docs need to match each version.
- **Onboarding that takes days of asking people,** at any team size above a handful.

## When It's Unnecessary or Overkill

- **A documentation site generator and developer portal** for one repository and three developers. A README and a `docs/` folder are enough.
- **Review dates and owners on every wiki page,** including meeting notes and one-off plans that were never meant to be maintained. Apply them to pages people rely on.
- **Writing an ADR for every decision made in chat.** Small decisions belong in the ticket or the commit message (29.1b).
- **Moving product and process knowledge into the repository** so that "everything is in one place," if the people who write it don't use Git.
- **Migrating wiki tools** to fix a problem that's really about ownership. The same pages will go stale in the new tool.

## Trade-offs

- **Docs-as-code excludes people.** Markdown, branches and pull requests are a barrier for product, support and design staff. Web editors on the code host lower it, but not completely.
- **Docs in the same pull request make changes bigger** and slower to review, and reviewers often skim the docs part.
- **Generated references can be complete and useless.** An OpenAPI page listing every field without explaining when to use them still needs human writing around it.
- **Tested instructions cost CI time** and need maintaining themselves; a test that runs the README in a container breaks for reasons unrelated to the README.
- **Ownership and review dates are ongoing work,** and they get skipped first when a team is busy.
- **Linking instead of copying makes pages depend on each other.** When the linked page moves or its tool is replaced, many links break at once.
- **Getting decisions out of chat takes discipline** at the moment people want to move on.

## Alternatives

**Everything in one tool.** Some organizations keep all documentation, including product and process, in a single wiki or in the repository (GitLab's public handbook is a well-known example of the second). One home is simpler; the cost is that it fits some kinds of knowledge and some roles badly.

**Rely on people rather than documents.** Small, stable teams can function with little written documentation, relying on asking each other and on pairing. It fails as people leave, as the team grows, and during incidents at 3 a.m.

**Recorded walkthroughs.** Short screen recordings of setup, architecture or incident procedures are quick to make and easy to follow. They're hard to search and update, so they work best alongside written docs, not instead of them.

## How to Achieve It

**L0 — Fix what's used under pressure.** Move runbooks into the repository next to the scripts they call, and replace commands in them with links to scripts. *Signal to move on:* setup and configuration docs disagree with each other.

**L1 — Give code-shaped docs one home:** the repository. Delete or redirect the wiki copies, and make the README the entry point. *Signal:* reference docs drift from the code.

**L2 — Generate references** (API, configuration, CLI) and publish them from CI. Add link and reference checks. *Signal:* reasoning keeps disappearing.

**L3 — Get decisions out of chat:** ADRs for architecture, tickets for work, and a habit of writing up conclusions. *Signal:* the wiki has pages nobody trusts.

**L4 — Run the wiki deliberately:** owners, review dates, archiving, and one workspace rather than two. Consider a developer portal once there are many services.

## Implementation

TypeScript, one CI check that finds documentation referring to things that no longer exist: scripts, files, npm scripts and environment variables. It's the check that would have flagged `replay-sync.sh` eight months before the incident.

```ts
import { readFileSync, existsSync } from "node:fs";
import { globSync } from "glob";

const pkg = JSON.parse(readFileSync("package.json", "utf8"));
const envVars = new Set(
  readFileSync(".env.example", "utf8").split("\n").map((l) => l.split("=")[0].trim()).filter(Boolean));

type Problem = { doc: string; line: number; message: string };

export function checkDocs(): Problem[] {
  const problems: Problem[] = [];
  for (const doc of globSync("{README.md,docs/**/*.md,**/RUNBOOK.md}", { ignore: "node_modules/**" })) {
    readFileSync(doc, "utf8").split("\n").forEach((text, i) => {
      const at = (message: string) => problems.push({ doc, line: i + 1, message });

      for (const [, path] of text.matchAll(/`((?:scripts|src|db|config)\/[\w./-]+)`/g))
        if (!existsSync(path)) at(`refers to ${path}, which doesn't exist`);

      for (const [, script] of text.matchAll(/npm run ([\w:-]+)/g))
        if (!pkg.scripts?.[script]) at(`refers to "npm run ${script}", which isn't in package.json`);

      for (const [, name] of text.matchAll(/`([A-Z][A-Z0-9_]{3,})`/g))
        if (!envVars.has(name)) at(`mentions ${name}, which isn't in .env.example`);
    });
  }
  return problems;
}
```

> **Aside — this catches references, not truth.** A runbook that says to run a script that still exists but no longer fixes the problem passes. The environment-variable rule flags any capitalized word in backticks, so it will need an allow-list. And it only covers docs in the repository: the Confluence copy of the runbook, which is the one the on-call developer actually opened, is invisible to it. That's the strongest argument for moving code-shaped docs into the repository in the first place. Checking a wiki the same way is possible through its API, but a failing check on a wiki page has no pull request to block and often no owner to tell.

The habit to take from this: **when you write something down, ask what will make it wrong, and put it where that change will be seen.** Docs rarely go stale because people are careless; they go stale because they live somewhere the change never passes through.
