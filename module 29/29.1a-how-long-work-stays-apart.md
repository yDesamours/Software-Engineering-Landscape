# How Long Work Stays Apart: Branching Strategies from Git Flow to Trunk-Based Development

_Module 29.1a — Version Control & Collaboration_

## The Problem

Suppose you're on a team of nine building booking software for physiotherapy clinics: appointment calendars, online booking, SMS reminders, and invoicing to health insurers. About 1,200 clinics use it. It's a web application with one production version.

The team uses Git Flow, set up years ago by a previous tech lead. There's a `main` branch that mirrors production, a `develop` branch where features are combined, a feature branch per piece of work, a release branch cut from `develop` each month for a week of testing, and hotfix branches for urgent fixes. Everyone follows the rules. Over one year, this happens:

**A merge that took two days and still went wrong.** Insurer invoicing lived on its own branch for five weeks. Meanwhile, `develop` gained group classes: Pilates sessions with up to eight patients. To avoid breaking old code, the group-classes work kept `appointment.patientId` (now meaning "first attendee") and added `appointment.attendees`. Merging invoicing took two days of conflict resolution in the scheduling code. The invoicing files themselves merged cleanly. They still billed `patientId`, so each group class invoiced one patient out of eight. Both branches had passed their tests. The combination was never tested until it shipped.

**A fix that disappeared.** During March's release testing, a developer fixed reminders being sent an hour early after the clocks change. The fix went onto the release branch, which shipped. The rule says release fixes are merged back into `develop`; that merge was forgotten. April's release was cut from `develop`, and the bug came back.

**A hotfix that was undone by the next release.** An invoice rounding error was hotfixed straight to `main` and merged into `develop`, as the rules say. A release branch was already in testing, and nobody merged the hotfix into that too. When the release shipped, rounding broke again.

**Nobody is sure what's running.** Asked "is the rounding fix in production?", people check four branches and a spreadsheet of hotfixes.

**Refactoring stops.** A developer wants to rename the confusing `Slot` model. Three long feature branches touch it. The rename is postponed, again.

So the team decides to "go trunk-based": everyone commits straight to `main`, which deploys automatically. Within three weeks, a half-built online-payment screen appears for clinics because the feature was only half finished when its commits reached `main`. Twice, `main` is broken for most of a day because the test suite takes 40 minutes and people push without waiting.

Git Flow wasn't followed badly, and trunk-based development wasn't a bad idea. Both failed for reasons the team never named: how long work stayed apart, and what was missing to make short-lived work safe.

## What It Is

A **branching strategy** (or Git workflow) is a team's agreement on how changes move from one person's work into what users run. Every strategy, whatever it's called, answers three questions:

1. **How long does work stay apart** from the shared line before it's integrated?
2. **What do you release from**: the main line, a release branch, or tags on the main line?
3. **How do fixes reach code that's already released?**

The named strategies are particular sets of answers. **Git Flow** (Vincent Driessen, 2010) uses long-lived `main` and `develop` branches plus feature, release and hotfix branches. **GitHub Flow** has one long-lived branch, `main`, always deployable, with short feature branches merged by pull request. **GitLab Flow** adds environment or release branches to GitHub Flow, with a rule that fixes go to `main` first. **Trunk-based development** means everyone integrates into one main line (the trunk) at least daily, either by committing directly or through branches that live a day or two.

Two nearby things are often confused with a branching strategy:

- **Merge strategy** (merge commits, rebasing, squashing) decides what history looks like once work is integrated. It's a separate choice, covered in 29.1b. You can squash-merge in Git Flow or keep merge commits in trunk-based development.
- **Feature flags** (26.2b) decide whether users *see* a change. Branches decide whether the code is *integrated*. Much of the move to short-lived branches is moving the "not ready yet" decision from branches to flags.

## Recognizing the Problem

- Branches older than a week are normal, and some are older than a month.
- Merging into the shared branch regularly takes hours and needs the original author.
- Tests pass on every branch and fail, or behavior breaks, after merging.
- There's a "merge freeze" or a stabilization week before each release.
- Fixes reappear as bugs because they weren't merged in every direction the rules require.
- Someone keeps a list of what's been cherry-picked where.
- "What exact commit is in production?" takes more than a minute to answer.
- Refactors are postponed because they would conflict with someone's open branch.
- The opposite failure: `main` is often broken, or unfinished features leak to users.

## How It Works

### 1. The cost is in the gap

Work on a branch is a bet that nothing it depends on will change before it's merged. The longer the branch lives and the busier the rest of the codebase is, the worse the bet:

```
 main   ──●──●──●──●──●──●──●──●──●──●──●──●──●──●──●──   (others' changes pile up)
           \
 branch     ●────●─────●──────●───────●───────────●──→ merge
            └──────────────── 5 weeks ────────────┘
            divergence ≈ days apart × rate of change elsewhere
```

That cost appears in two forms.

**Textual conflicts** are the visible ones: Git can't combine two edits to the same lines. They're annoying but safe, because Git stops and asks.

**Semantic conflicts** are the dangerous ones. Each side is correct alone; the combination is wrong, and Git merges it without complaint because the edits don't overlap. Group classes changing what `patientId` means, while invoicing relied on it, is a semantic conflict. The only thing that catches these is building and testing the combined code, which means the earlier and more often you combine, the sooner you find them.

This is the same batch-size argument as 28.1a, applied to code: integrate a small change daily and each merge is trivial; integrate five weeks of change at once and you get one large, risky merge with feedback five weeks late. The term **continuous integration** originally meant exactly this practice (everyone merging to the main line at least daily) before it came to mean a CI server.

### 2. Four sets of answers

| | How long work stays apart | Release from | Fixes to released code |
|---|---|---|---|
| **Git Flow** | Feature branches for the whole feature, often weeks | `main`, after a release branch from `develop` | Hotfix branch from `main`, merged into `main`, `develop` and any open release branch |
| **GitHub Flow** | Short feature branches, merged by pull request | `main`, usually deployed on merge | Another short branch into `main`; roll forward |
| **GitLab Flow** | Short feature branches | `main`, promoted through environment branches, or release branches for versioned software | Fix on `main` first, then cherry-pick to release branches |
| **Trunk-based** | Hours to a day or two | Trunk, or a release branch cut from it just in time | Fix on trunk, cherry-pick to the release branch; never merge the release branch back |

**Git Flow** was designed for software shipped as numbered versions on a schedule, with a testing phase in between. Its two long-lived branches let the team keep building on `develop` while a release stabilizes. The price is that fixes must travel in several directions, and each direction is a manual step someone can forget, which is exactly how the physio team lost two fixes. In 2020 Driessen added a note to his original post saying that for continuously delivered web applications, a simpler workflow like GitHub Flow is usually a better fit.

**GitHub Flow** removes `develop`, release and hotfix branches. There's `main`, which is always deployable, and short branches reviewed by pull request. It assumes one production version and cheap deploys: if something is wrong, you fix it on a new branch and deploy again.

**GitLab Flow** is GitHub Flow plus downstream branches where you need them: `staging` and `production` branches that code is merged into to deploy, or `release/3.2` branches for software with several supported versions. Its key rule is **upstream first**: fix on `main`, then cherry-pick the fix to each release branch. Fixes flow in one direction only.

**Trunk-based development** is the strictest about the first question. Small teams may commit straight to trunk; larger ones use branches that live a day or two, with a pull request. Release branches, if any, are cut from trunk shortly before a release, receive only cherry-picked fixes, and are thrown away, never merged back.

Look at the table by column rather than by row. The first column is where the physio team's two-day merge and semantic conflict came from. The third column is where the lost fixes came from. Changing one column doesn't require changing the others: a team can shorten branches dramatically and still keep release branches.

### 3. Short-lived branches need somewhere else to put "not ready"

Long feature branches do a real job: they keep unfinished work away from users. The physio team's trunk experiment failed because it removed the branches without replacing that job. The replacements:

- **Feature flags** (26.2b). Merge the online-payment code to trunk daily, switched off. It's integrated and tested with everything else; clinics don't see it until the flag is on.
- **Build the entry point last** (sometimes called a *keystone interface*). Build the invoicing engine, its data and its API first, merged and deployed but unreachable. Add the button or menu item that exposes it as the final change. For many features this avoids a flag entirely.
- **Branch by abstraction** for large changes to existing code. To replace how reminders are scheduled: put an interface in front of the current scheduler, move callers to the interface, build the new scheduler behind the same interface, switch over (often behind a flag), then delete the old one. Each step is a small merge, and trunk works throughout. It's the answer to "this refactor is too big for a short branch."
- **Dark launching.** Run new code in production against real traffic without showing its results, for example computing new invoice totals alongside the old ones and logging differences. Useful when correctness is the risk.

And short branches need a **main line that stays green**:

- **Fast, required checks before merge.** If the test suite takes 40 minutes, people will push without waiting; making it faster and requiring it to pass (Module 21, Module 30) is part of adopting short branches, not a later nice-to-have.
- **A merge queue** once many people merge each hour. Two pull requests can each pass against yesterday's `main` and break it together, the semantic conflict again, in miniature. A merge queue tests each change against `main` plus everything queued ahead of it, and merges only if that passes. GitHub, GitLab and several standalone tools offer one.
- **Fast review.** A two-day branch waiting three days for review is a five-day branch. Small changes only help if review keeps up, which is 29.2.

### 4. Releases and fixes

**What do you release from?** For a web application with one production version, from `main`, with every deploy tagged or recorded so "what's running?" is a lookup. Environment branches (`staging`, `production`) are a weaker version of this: the code in `production` was produced by a merge, so it isn't necessarily the exact build that was tested in staging. Building once and promoting the same artifact between environments (Module 30) gives the same control without branches.

Release branches earn their place when **more than one version is in use at once**:

- A mobile app, where app-store review takes days and users run last month's version.
- On-premise software where customers are contractually supported on 3.x and 4.x.
- A library whose users pin versions (33.1 on semantic versioning).
- A regulated product where a specific build is validated and must be fixed without new features.

**How do fixes reach released code?** Two options:

- **Roll forward.** Fix on `main` and release `main` again. Simple, and right when deploys are cheap and there's one version.
- **Upstream first, then cherry-pick.** Fix on `main`, then copy the fix to each release branch that needs it, with `git cherry-pick -x` so the copy records where it came from. Never fix only on the release branch, and never merge the release branch back into `main`.

Fixes flowing one way is what makes them hard to lose: every fix is on `main` by construction, and the only question for each release branch is "did it get the copy?", which can be checked (see Implementation). Git Flow's two-way rule asks people to remember; upstream first makes forgetting visible.

## When It's Appropriate

Choosing a strategy is choosing answers to the three questions for your situation:

- **A web SaaS deploying several times a day, one production version, a team of 5 to 50:** GitHub Flow or trunk-based with short branches, flags for unfinished features, roll forward for fixes.
- **A mobile app released every two weeks, with 20% of users still on older versions:** trunk-based development, a release branch cut per version shortly before submission, fixes upstream first and cherry-picked to the versions still in use.
- **On-premise software with three supported major versions:** long-lived maintenance branches per version, upstream first. Here long-lived branches are the product's reality, not a process failure.
- **A team that currently releases monthly with a manual test week and can't yet test automatically:** a short-lived release branch for stabilization is honest. Shorten feature branches anyway, since that column doesn't depend on the release process.
- **An open-source project with outside contributors:** forks and pull requests are unavoidable; the maintainers can still keep changes small and merge frequently.

## When It's Unnecessary or Overkill

- **Git Flow's full set of branches for a small team deploying a web app daily.** `develop` becomes a second `main` that's always slightly different, and hotfix rules add merges nobody needs.
- **Release branches with a single production version and 15-minute deploys.** Roll forward.
- **Environment branches** when you can promote one build through environments.
- **Committing straight to `main` without fast checks, flags or tests.** Removing branches without their replacements just moves the failures to users, as the physio team found.
- **Strict branch-lifetime rules for one or two people** working on separate parts of a codebase. Keep it simple and merge often.
- **A formal written strategy for a prototype.** Anything that reliably reaches `main` will do until people depend on it.

## Trade-offs

**Short-lived branches and trunk-based development:**

- **They depend on engineering investment you may not have yet:** tests fast and trustworthy enough to gate every merge, and fast review. Without those, trunk breaks often and everyone is blocked.
- **Flags add cost.** Each flag is a second code path to test, and flags left in place become their own debt (26.2b covers cleaning them up). Several interacting flags create combinations nobody tested.
- **Unfinished code runs in production.** It's switched off, but it's deployed. A misconfigured flag, or an API endpoint that's unreachable from the interface but still callable, can expose half-built features or data.
- **Incremental techniques take more steps.** Branch by abstraction is more total work than a big-bang rewrite on a branch, and requires people to keep old and new working side by side.
- **More, smaller merges mean more reviews.** Reviewers context-switch more, and slow review quietly turns short branches into long ones.

**Long-lived branches and Git Flow:**

- **Merge cost grows with branch age**, and semantic conflicts surface late, often in production.
- **Multi-direction merge rules lose fixes**, because each rule is a manual step.
- **Integration feedback is delayed** until the branch merges, so problems are found when they're most expensive to fix.

**Release branches, where needed:**

- **Every fix is done more than once** and may need adapting to each version's code. The more versions supported, the more this costs, which is why the number of supported versions is also a product decision.
- **Each version needs its own test runs**, and old branches' build tooling decays.

## Alternatives

These change *how* changes are integrated rather than picking a different named workflow.

**Stacked changes.** Instead of one large branch, a sequence of small dependent pull requests, each reviewed and merged in order. Gerrit and Phabricator have long worked this way; tools such as Graphite, Sapling and ghstack bring it to GitHub. It keeps review units small when a feature can't be split into independent pieces, at the cost of tooling and rebasing the stack when an early change is revised.

**Pair or ensemble programming with direct commits.** When two or more people write the code together, review happens as it's written (32.2), and some teams commit straight to trunk many times a day without pull requests. It removes review waiting entirely, and depends on a team that works this way consistently.

**Hierarchical integration.** Large projects like the Linux kernel integrate through layers of maintainers, each collecting changes for one area in their own tree before passing them upward. It scales review to thousands of contributors, and is rarely needed inside a company.

## How to Achieve It

This path assumes a team like the physio one, starting from Git Flow or long-lived branches.

**L0 — Measure and make releases traceable.** Tag every production deploy. Measure how long branches live before merging and how often merges cause failures. *Signal to move on:* branches regularly live more than a few days.

**L1 — Shorten branches without changing anything else.** Agree a target (say, merged within two days), protect `main` or `develop` with required checks, and slice work smaller (28.4a). Make the checks fast enough that nobody is tempted to skip them. *Signal:* people say "I can't merge yet, it's not finished."

**L2 — Add the replacements for long branches:** feature flags for unfinished features, entry points built last, branch by abstraction for large refactors. *Signal:* `develop` and `main` differ only by what's waiting for release.

**L3 — Collapse to one main line.** Remove `develop`. Release from `main` with tags. Keep release branches only where several versions are in use, cut them late, and apply fixes upstream first. *Signal:* several merges an hour, and `main` sometimes breaks from two changes that passed separately.

**L4 — Add a merge queue**, and move toward deploying every merge (Module 30).

## Implementation

TypeScript, two small scripts that make the three questions measurable. They run in CI or on a schedule.

The first checks the rule that fixes flow upstream first: every commit on a release branch should also be on `main`.

```ts
import { execFileSync } from "node:child_process";

const git = (...args: string[]) => execFileSync("git", args, { encoding: "utf8" }).trim();

// Commits on the release branch with no equivalent change on main.
// --cherry-pick drops commits whose diff matches one on the other side,
// so fixes copied with `git cherry-pick` don't show up here.
export function fixesMissingFromMain(release: string): string[] {
  const out = git("log", "--cherry-pick", "--right-only", "--no-merges",
                  "--format=%h %s", `main...${release}`);
  return out ? out.split("\n") : [];
}

const missing = fixesMissingFromMain("release/2026.09");
if (missing.length) {
  console.error("On the release branch but not on main:\n" + missing.join("\n"));
  process.exit(1);
}
```

On the physio team's March release, this would have flagged `Fix reminder time after clock change` the day it was committed.

> **Aside — when "the same change" isn't detected.** `--cherry-pick` compares diffs. If a cherry-pick needed conflict resolution, the copy's diff differs from the original and both appear as unmatched, a false alarm. The reverse can also happen: a fix written independently on `main` with identical content is counted as a copy. Recording origins with `git cherry-pick -x`, which adds a "cherry picked from commit" line, gives a second check that doesn't depend on diffs matching. And the check only protects one direction: it tells you a fix reached `main`, not whether each release branch that needs the fix received it.

The second measures how long work stays apart, from merged pull requests:

```ts
type MergedPR = { number: number; firstCommitAt: Date; mergedAt: Date };

const hours = (a: Date, b: Date) => (b.getTime() - a.getTime()) / 3_600_000;

export function branchLifetimes(prs: MergedPR[]) {
  const h = prs.map((p) => hours(p.firstCommitAt, p.mergedAt)).sort((a, b) => a - b);
  const pct = (q: number) => h[Math.min(h.length - 1, Math.floor(q * h.length))];
  return {
    p50Hours: pct(0.5),
    p85Hours: pct(0.85),
    olderThan3Days: prs.filter((p) => hours(p.firstCommitAt, p.mergedAt) > 72).map((p) => p.number),
  };
}
// Fed from the hosting platform's API: each merged PR's merge time,
// and the author date of its earliest commit.
```

> **Aside — what this number hides.** Measuring from when the pull request was opened misses the days before anyone saw the branch, which is why this uses the first commit. Commit dates can still mislead: rewriting history can reset or backdate them. Like velocity (28.5a), this describes how the team's work flows, and it stops meaning anything once it's used to rank individuals, because people then split pull requests to hit the number rather than to integrate sooner. The 85th percentile matters more than the median: a few five-week branches cause most of the painful merges.
