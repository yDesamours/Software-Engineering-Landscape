# History You Can Use: Merge, Rebase, Squash, and Commits Worth Reading

_Module 29.1b — Version Control & Collaboration_

## The Problem

Suppose you're on a team of seven building payroll software for restaurants and cafés: shift hours, tip pooling, payslips and tax filings. About 3,000 venues use it. The team uses short-lived branches and pull requests (29.1a), and nobody has ever agreed how branches get merged. Each person clicks whichever merge button they like.

In September, a venue's accountant notices that staff at a café have been underpaid on tips by a few cents per shift for about two months. Across all venues, it adds up to thousands of pounds owed. The team needs to find the change, understand why it was made, and undo it safely. Every tool they reach for fails.

**`git bisect` can't find it.** Bisect checks out commits halfway between a known good and a known bad version, and narrows down which one introduced the bug. About a third of the commits it lands on don't build: they're from branches merged with all their intermediate commits, with messages like `wip`, `fix tests`, and `oops`. Each one has to be skipped. The history also contains fourteen commits called `Merge branch 'main' into feature/tips`, and bisect wanders into the middle of those branches. After an hour, it reports a range of eleven possible commits.

**`git blame` points at the wrong thing.** On the line that rounds each person's share, blame shows `Apply prettier to entire codebase`. Going back past that, the previous change is a commit called `fix`, which changed `Math.round` to `Math.floor`. Nobody knows why. The author has left the company.

**The change can't be reverted on its own.** The commit that finally turns out to be responsible is inside a squash-merged pull request of 2,400 lines. It also contains a database migration and a refactor of how shifts are stored, both now relied on by later work. Reverting the squash commit would undo all of it.

**And, the month before, work was lost.** A developer rebased a branch two people were sharing and force-pushed it. Her colleague's two days of commits disappeared from the remote. They were recovered from his laptop's reflog, by luck, because he hadn't deleted his local branch yet.

None of these were Git's fault. History is a tool with several users, and the team had never decided what those users needed from it.

## What It Is

**Git history** is the record of changes on your main branch, and several tools read it to answer questions:

- **`git bisect`** finds which change introduced a bug, by testing commits.
- **`git revert`** undoes a change by creating a new commit that reverses it.
- **`git blame`** shows which change last touched each line, and so the message explaining why.
- **`git cherry-pick`** copies a change to another branch, such as a release branch (29.1a).
- **`git log`** and release notes show what changed between two versions.

What they can do depends on two choices.

**The merge strategy** is how a pull request's work lands on `main`:

- a **merge commit**, which keeps the branch's commits and joins them with a commit that has two parents;
- **rebase and merge**, which replays the branch's commits on top of `main` so history stays a straight line;
- **squash and merge**, which combines the whole branch into one new commit.

**Commit hygiene** is how the commits themselves are made: what each contains and what its message says. This includes **rewriting your own history before sharing it** with interactive rebase.

Two terms are easy to mix up here. `git rebase` is a command that rewrites commits by replaying them onto a new base; "rebase and merge" is one merge strategy that uses it. And none of this is the branching strategy from 29.1a, which decides *how long* work stays apart; this article is about what the result looks like once it's joined.

## Recognizing the Problem

- `git bisect` often lands on commits that don't build or whose tests fail for unrelated reasons.
- Reverting one bad change would also undo unrelated changes.
- `git blame` mostly points at formatting commits, renames, or messages like `fix` and `changes`.
- `git log` on `main` is dominated by `Merge branch 'main' into …` and `address review comments`.
- Commit messages say what changed but never why.
- Cherry-picking a fix to a release branch drags unrelated changes with it.
- Someone has lost work after another person force-pushed.
- The team's pull requests are merged in two or three different ways, depending on who clicks.

## How It Works

### 1. Decide the unit on `main`

The most useful single decision is: **what is one unit of change on `main`?** Everything else follows from it. There are two reasonable answers.

**The unit is the pull request.** Each merged pull request is one entry in the history that matters. Squash-merging produces this directly. Merge commits produce it too, if you read history by following only the first parent of each merge (`git log --first-parent`, `git bisect --first-parent`), which shows one entry per merged pull request.

**The unit is the commit.** Each commit on `main` is a small, deliberate change. Rebase-and-merge produces this, but only if the commits are worth keeping. It asks more of authors, and gives finer-grained history.

What the tools need, in either case:

- **Bisect needs every unit to build and pass tests.** Otherwise it has to skip, and the answer becomes a range.
- **Revert needs each unit to be one logical change.** Undoing it shouldn't undo something unrelated.
- **Blame needs each unit's message to say why.**

The payroll team's mixed history fails all three: some units are `wip` commits that don't build, some are 2,400-line squashes containing three unrelated changes, and many messages say nothing.

### 2. The three merge strategies

```
 before:   main   A──B──C
                   \
           branch   x──y──z         (x: refactor, y: wip, z: fix + tests)

 merge commit:     A──B──C───────M       first-parent view: A B C M
                    \           /
                     x────y────z

 rebase & merge:   A──B──C──x'──y'──z'   every commit lands on main

 squash & merge:   A──B──C──S            S = x+y+z as one new commit
```

**Merge commits** keep everything, including when work diverged and came back. With first-parent reading, `main` has one entry per pull request; drilling into a merge shows its individual commits. The cost is a busier graph, and if people update branches by merging `main` into them repeatedly, the branch side becomes tangled. Bisect without `--first-parent` wanders into those branch commits, which is what happened to the payroll team.

**Rebase and merge** gives a straight line with every commit individually on `main`. That's the best history for bisect and blame, **if** every commit builds and has a clear purpose. It's the worst if they don't: `y'` (`wip`) is now a permanent, unbuildable commit on `main`. CI usually tests only the tip of the pull request, so nobody has checked that `x'` and `y'` build on their own.

**Squash and merge** gives one commit per pull request, with a message usually taken from the pull request's title and description. It hides messy intermediate commits, which is why it's the most common choice. Its costs:

- The branch's individual commits are gone from `main`. If `x` was a refactor and `z` was the fix, you can no longer revert just the fix. A squash is only as good a unit as the pull request is small.
- Git doesn't recognize the branch as merged (`git branch --merged` won't list it), because `S` is a new commit unrelated to `x`, `y` and `z`. Branches built on top of it need `git rebase --onto` to move across, which is painful with stacked changes (29.1a).
- Authorship is reduced to one commit. Platforms add `Co-authored-by:` lines for other contributors, but per-commit attribution is lost.

A team should pick one, and configure the hosting platform to allow only that button. The strategy matters less than being consistent, because every tool above reads history the same way regardless of who clicked.

### 3. Rebase, safely

`git rebase` replays commits onto a new starting point, creating new commits with new IDs. That's what makes it useful, for bringing a branch up to date with `main` without merge commits, or tidying commits before review. It's also what makes it dangerous: anyone who had the old commits now has a history that no longer exists on the remote.

The rule that prevents lost work: **don't rewrite commits other people have built on.** Rewriting your own unshared branch is fine. Rewriting a branch you've pushed but nobody else uses is fine. Rewriting a branch someone else is committing to, as in the problem, is how work disappears.

Habits that help:

- **Use `git push --force-with-lease`**, never plain `--force`. It refuses to overwrite the remote if someone else has pushed since you last fetched. (`--force-if-includes` closes a gap where a background fetch would otherwise make the lease pass.)
- **Protect `main`** and release branches against force-pushes on the hosting platform.
- **Know the reflog.** `git reflog` records where your branches pointed recently, so a bad rebase on your machine is almost always recoverable. It's local only: it can't recover someone else's commits.
- **`git rerere`** ("reuse recorded resolution") remembers how you resolved a conflict and reapplies it, useful when rebasing a branch repeatedly over the same conflicting change.

Merging `main` into your branch instead of rebasing is also a legitimate choice. It never rewrites anything, at the cost of those `Merge branch 'main' into …` commits, which disappear anyway if the pull request is squashed.

### 4. Commits worth keeping

If the unit is the commit, or if you want reviewers to read your pull request commit by commit (29.2), the commits need to be deliberate. Interactive rebase (`git rebase -i`) is the tool for turning what you did into what you want to show: reorder, combine, split, reword.

What a good commit is:

- **One logical change, which builds and passes tests.** The fix and its test belong together; a rename belongs apart.
- **Mechanical changes separate from behavior changes.** A formatting pass, a rename or a file move in its own commit means reviewers can skim it and blame can skip it.
- **A refactor before the change that needed it.** "Extract rounding into `splitCents`" then "Distribute remainder cents in tip pools" is two commits that each make sense, and the second is small enough to revert.

Tools that make this cheap: `git add -p` to stage part of a file; `git commit --fixup=<commit>` to record a correction to an earlier commit, then `git rebase -i --autosquash` to fold it in before merging.

**Messages.** The subject line says what the change does, in the imperative and short enough to read in a one-line log. The body says **why**: the problem, the reason for this approach, anything surprising. The diff already shows *what*; only the message can say *why*, and it's the only explanation guaranteed to travel with the code when issue trackers are migrated and chat history expires.

```
Distribute remainder cents in tip pools

Shares were floored to avoid paying out more than the pool, but the
remainder was dropped, so staff were underpaid by up to (n-1) cents
per pool. Remainder cents now go one each to the largest fractional
shares, so shares always sum to the pool total.

Fixes PAY-1841
```

With squash merging, the pull request's description becomes this message, so the template for pull request descriptions (29.2b) is effectively the commit-message convention. Structured conventions like **Conventional Commits** (`fix(tips): …`, `feat: …`) help when you generate changelogs or version numbers from history; they don't make a message explain why.

**Keeping blame useful after mechanical changes.** List the IDs of formatting and mass-rename commits in a `.git-blame-ignore-revs` file and run `git config blame.ignoreRevsFile .git-blame-ignore-revs`. Blame then looks past them to the real change. GitHub and GitLab read the same file in their blame views.

### 5. Using the history

**Bisecting.** `git bisect run <script>` automates the search: the script exits 0 if the commit is good, 1 if it's bad, and 125 if the commit can't be tested (it doesn't build), which tells bisect to skip it. With merge commits, `git bisect start --first-parent` tests only the merges into `main`, one per pull request. Finding the pull request first and then the commit inside it is usually quicker than bisecting everything at once. Each skipped commit widens the final answer; this is where unbuildable commits on `main` cost you.

**Reverting.** Reverting a normal or squash commit is one command. Reverting a merge commit needs `git revert -m 1 <merge>` to say which parent is the mainline. That revert has a trap: Git still considers the branch's commits merged. If the branch is fixed and merged again later, the original changes don't come back, only the new fixes. To bring them back, revert the revert first. Teams that revert as a first response to incidents (24.3) should know this before they need it.

## When It's Appropriate

- **Squash and merge:** most teams with small pull requests (29.1a), where one pull request is one change. Also projects with outside contributors, whose commit habits you can't control.
- **Rebase and merge:** teams willing to curate commits, where pull requests are often a natural series (refactor, then change, then cleanup) and individual reverts are valuable. Codebases that bisect often, such as those with hard-to-reproduce numeric or performance bugs.
- **Merge commits read by first parent:** when branch structure carries information, for example release branches merged into a maintenance line, or when you want one entry per pull request but keep the detail inside it.
- **Curated commits for review** are worth it on any strategy when pull requests are large enough that reviewing commit by commit helps, typically above a few hundred lines.
- **A written message convention:** any codebase that outlives its authors, which is nearly every production codebase.

## When It's Unnecessary or Overkill

- **Asking contributors to polish every commit** when you squash-merge. The polish is discarded. Pick one: squash and care about the pull request description, or rebase-merge and care about commits.
- **Enforcing linear history, commit-message linting and Conventional Commits** on a two-person repository. A shared understanding and a readable log are enough.
- **Rewriting shared history to make it tidy.** Mess in the past costs less than lost work in the present.
- **Squashing a 2,000-line pull request** to get "clean" history. It produces one enormous, unrevertable commit. The problem is the pull request's size (28.4a), not the merge button.
- **Treating `git log` as the only record** when the team genuinely documents decisions elsewhere and has no plans to migrate tools. Messages still need a why, but they needn't be essays.

## Trade-offs

- **Curating commits takes time and Git fluency.** Interactive rebase, fixups and splitting commits are skills some developers don't have yet, and a failed rebase can cost an afternoon.
- **Rebase-and-merge puts untested commits on `main`** unless CI checks each commit, which multiplies CI time by the number of commits.
- **Squash merging loses detail and complicates stacked work.** Individual commits, per-commit authorship and Git's knowledge of what's merged all go.
- **Merge commits make raw history harder to read** and make bisect wander, unless everyone knows to use `--first-parent`.
- **Any rewriting has a lost-work failure mode.** Protected branches and `--force-with-lease` reduce it; they don't remove it.
- **Messages that explain why take effort** at exactly the moment the author wants to be done.
- **A single strategy is a constraint.** Some pull requests would be better merged differently; consistency wins because the tools read history uniformly.

## Alternatives

**Rely on the pull request, not the commit.** Many teams treat commits as disposable and put all explanation in the pull request and linked issue, with the commit linking to it. Hosting platforms make this easy to navigate. The cost is dependence on the platform: links break on migration, and the reasoning isn't available offline or in `git blame` without a click.

**Change-based review.** Gerrit and Phabricator treat each commit as the reviewed unit, with an ID that survives rewriting, so curating commits and reviewing them are the same act (stacked changes in 29.1a).

**Version control that makes rewriting safe.** Jujutsu (`jj`) works on top of Git repositories and records how each change evolved, so rewrites can be undone and descendants are rebased automatically. Mercurial's changeset evolution does something similar. They reduce the danger in section 3, at the cost of a tool the team has to learn.

## How to Achieve It

**L0 — Choose the unit and enforce one strategy.** Decide pull request or commit, then restrict the platform to the matching merge button. Protect `main` against force-pushes. *Signal to move on:* bisect and revert work, but blame and log don't explain anything.

**L1 — Make messages carry the why.** For squash teams, a pull request template with a "why" section (29.2b); for rebase teams, a short message guide. *Signal:* blame keeps landing on formatting commits.

**L2 — Separate mechanical changes** into their own commits or pull requests, and add them to `.git-blame-ignore-revs`. *Signal:* rebase-merged commits on `main` sometimes don't build.

**L3 — Check commits, not just tips,** if you rebase-merge: reject leftover `fixup!` and `wip` commits and build each commit. *Signal:* bugs arrive that are only reproducible in production data, and bisect is the fastest route to the cause.

**L4 — Make bisect a routine tool:** keep test fixtures stable enough to run against old commits, and write down how to run `git bisect run` for the codebase.

## Implementation

TypeScript, two small scripts.

The first is the script the payroll team needed for `git bisect run`: it builds the commit, runs one known-bad case, and reports good, bad or untestable.

```ts
// Run with:  git bisect start HEAD <known-good> && git bisect run npx tsx ../bisect-tips.ts
// Exit codes: 0 = good, 1 = bad, 125 = can't test this commit (skip).
import { execSync } from "node:child_process";

try {
  execSync("npm ci && npm run build", { stdio: "ignore" });
} catch {
  process.exit(125); // doesn't build: every one of these widens the answer
}

const { poolTips } = await import(process.cwd() + "/dist/payroll/tips.js");
const shares: Record<string, number> = poolTips({ totalCents: 10_000, hours: { a: 6, b: 6, c: 6 } });
const paid = Object.values(shares).reduce((s, x) => s + x, 0);

process.exit(paid === 10_000 ? 0 : 1);
```

> **Aside — bisect checks out old code, including old versions of your script.** Keep the script outside the repository (here, `../`), or bisect will replace it with whatever existed at each commit, or delete it. The script also has to work across the whole range: if `poolTips` was renamed or moved in the middle, older commits fail for the wrong reason and are reported as bad. Test through the most stable interface available (a public function, a CLI command, an HTTP endpoint), and treat "can't run this test here" as 125, not 1.

The second is a pre-merge check for teams that rebase-merge, where every commit will land on `main`:

```ts
import { execFileSync } from "node:child_process";
const git = (...a: string[]) => execFileSync("git", a, { encoding: "utf8" }).trim();

export function checkCommits(base = "origin/main") {
  const problems: string[] = [];
  const shas = git("rev-list", "--reverse", `${base}..HEAD`).split("\n").filter(Boolean);

  for (const sha of shas) {
    const subject = git("log", "-1", "--format=%s", sha);
    if (/^(fixup!|squash!|amend!)|^wip\b/i.test(subject)) problems.push(`${sha.slice(0, 8)} not squashed: ${subject}`);
    if (subject.length > 72) problems.push(`${sha.slice(0, 8)} subject over 72 characters`);
    try {
      execFileSync("sh", ["-c", `git checkout -q ${sha} && npm run build && npm test`], { stdio: "ignore" });
    } catch {
      problems.push(`${sha.slice(0, 8)} doesn't build or pass tests: ${subject}`);
    }
  }
  return problems;
}
```

> **Aside — the cost is real.** Building every commit multiplies CI time by the number of commits: ten commits and a twelve-minute suite is two hours. Teams typically run only the build and fast unit tests per commit, and the full suite on the tip. Squash teams don't need this at all, since only the tip lands. The check also can't tell whether a commit is *one logical change*; that's for review (29.2).

The habit to take from this: **before you merge, ask how someone will bisect, revert and blame this change in a year**, when neither you nor your memory of it is around. History is written once and read under pressure.
