# Screen Readers, ARIA, and Testing Accessibility

_Module 34.3b — Legal & Compliance Considerations_

> Builds on 34.3a, which covered WCAG, semantic HTML, keyboard access and focus. This article is about the layer screen readers see, the ARIA attributes that shape it, and how to know — rather than hope — that the product works with assistive technology.

## The Problem

Suppose you build a customer-support help desk: an inbox of tickets updating in real time, a ticket view with tabs, an assignee picker that searches as you type, a toolbar of icon buttons, toast notifications. One of your largest customers runs a support center that employs several blind agents, who use the JAWS and NVDA screen readers all day.

Last year an audit tool flagged hundreds of issues, and a team spent a sprint "adding ARIA" until the automated checks passed. The dashboard went green.

Then the customer's accessibility lead sends a recording of an agent trying to reassign a ticket. What the screen reader says:

- **Toolbar:** "button, button, button, button." Icon buttons with no names. On one, "btn-assign-3" — someone set `aria-label` to a test ID.
- **Ticket list:** "Edit, button. Edit, button. Edit, button." Forty identical names, no way to tell which ticket each belongs to.
- **Tabs:** announced as "tab, 1 of 3," but arrow keys do nothing; Tab moves through every tab in turn and then into a hidden panel.
- **Assignee picker:** the agent types "mar", results appear visually, and the screen reader says nothing. Arrow keys move the page, not the options.
- **Real-time updates:** every new ticket triggers "New ticket received" — dozens of times a minute during a busy hour, interrupting whatever the agent was listening to.
- **Toasts:** "Ticket assigned to Maria" appears for three seconds and is never announced. The agent can't tell whether the assignment worked.
- **A collapsed sidebar** was hidden with `aria-hidden="true"` while its links stayed focusable. The agent tabs into it and hears nothing at all.

Every one of these passed the automated checks, and several were introduced by the ARIA sprint. The customer's contract requires WCAG 2.1 AA; the renewal is in question.

## What It Is

A **screen reader** turns an interface into speech or braille. It doesn't read pixels. It reads the **accessibility tree** — a parallel structure the browser builds from the DOM and exposes through the operating system's accessibility API (UI Automation on Windows, the macOS accessibility API, AT-SPI on Linux). Each node in the tree has:

- a **role** — button, link, checkbox, tab, dialog, heading;
- a **name** — "Assign ticket";
- sometimes a **description** — "Assigns this ticket to another agent";
- **states and properties** — expanded, selected, checked, disabled, invalid, level 2;
- sometimes a **value** — the text in a field, a slider's position.

Native HTML elements populate the tree correctly on their own; that was 34.3a's main lesson. **ARIA** (Accessible Rich Internet Applications) is a W3C specification of attributes — `role`, `aria-label`, `aria-expanded`, `aria-live` and others — that let you set or override what goes into the tree when native elements can't express what you've built.

The key thing to understand about ARIA: **it changes what the screen reader is told, and nothing else.** `role="button"` doesn't make an element focusable or clickable by keyboard. `role="tab"` doesn't add arrow-key navigation. ARIA is a promise to the user about how something behaves, and the code has to keep the promise. That's why the W3C's own guidance starts with "don't use ARIA if a native element will do," and why WebAIM's annual scan of a million home pages keeps finding that pages using ARIA have substantially _more_ detected errors than pages without it.

Two disambiguations:

- **Passing automated checks is not conformance, and conformance is not usability.** Tools verify the mechanical subset of WCAG. Conformance also requires human judgment. And a conformant product can still be exhausting to use with a screen reader. The Problem's product passed the first and failed the other two.
- **ARIA is not accessibility.** It's one tool for one layer. Keyboard behavior, focus management, contrast and clear language are all outside its reach.

## Recognizing the Problem

- Automated checks pass, but nobody on the team has used the product with a screen reader.
- `aria-label` values that don't match visible text, or look like identifiers.
- Lists of identically named controls: "Edit, Edit, Edit."
- `role="tab"`, `role="menu"` or `role="listbox"` on elements that don't support the arrow-key behavior those roles promise.
- `role="menu"` used for site navigation.
- `aria-hidden="true"` on anything that contains focusable elements.
- Toasts or inline messages that appear and disappear without being announced.
- A live region that fires on every real-time update.
- `aria-expanded`, `aria-selected` or `aria-checked` set once in markup and never updated.
- Component tests that select elements by class name or test ID, never by role and name.
- An Accessibility Conformance Report written without testing.

## How It Works

### How screen-reader users move through a page

Sighted users scan. Screen-reader users navigate by structure: jump to the next heading, list all links, jump to the main landmark, list form fields, move by table cell. Screen readers on Windows also switch between a **browse mode** — where letter keys jump between element types (H for heading, B for button) — and a **focus mode**, where keys go to the application, which is what happens inside text fields and many widgets.

The consequence is that **structure is the table of contents**. Headings, landmarks, lists and names aren't decoration. They're how a blind user finds the ticket list among the toolbar, sidebar and tabs. A page that makes perfect visual sense can be an undifferentiated stream of "button, link, button" in the tree.

### Accessible names

Every interactive element needs a name, and the browser computes it from several sources in a fixed order of precedence:

1. `aria-labelledby` — the text of other elements, referenced by ID;
2. `aria-label` — a string;
3. the native mechanism — a `<label>` for inputs, `alt` for images, the text content for buttons and links, a `<caption>` or `<legend>`;
4. `title` — a last resort, and unreliable.

The rules that follow from this:

- **Visible text is the best name.** A button whose text is "Assign" is named "Assign" without any ARIA.
- **Icon-only controls need a name** — `aria-label` on the button, or visually hidden text inside it.
- **The name should contain the visible label.** An `aria-label` that replaces visible text with something different breaks voice control, because users say what they see (WCAG's "Label in Name"). It's also how "btn-assign-3" happened.
- **Repeated controls need context.** "Edit" is fine visually because the ticket is right next to it. In a list of links or buttons, the context is gone. Add it: "Edit ticket #4521," with the extra words visually hidden if the design doesn't want them.
- **`aria-label` on a generic element does nothing useful.** A `div` or `span` with no role isn't named by it reliably. Names belong on elements with interactive or landmark roles.

**Descriptions** — via `aria-describedby` — carry secondary information: help text, format hints, and especially error messages, so that a field is announced as "Email, edit text, invalid entry, Enter an address like name@example.com."

Counts and status belong in names when they matter: an inbox link named "Inbox, 3 unread" rather than "Inbox" next to a visual badge that's absent from the tree.

### Roles, states and properties are promises

When you set a role, you promise the interaction model that goes with it:

| Role | What users will expect |
|---|---|
| `button` | Enter and Space activate it |
| `link` | Enter follows it; it goes somewhere |
| `tablist` / `tab` | Arrow keys move between tabs; Tab moves into the panel |
| `menu` / `menuitem` | An application menu: arrow keys, Escape closes, focus returns. Not site navigation |
| `combobox` | Typing filters, arrow keys move through options, Enter selects |
| `dialog` | Focus is inside; Escape closes |
| `grid` | Arrow keys move between cells |

And states must stay in sync with reality: `aria-expanded` on a disclosure button toggles when the section opens; `aria-selected` moves with the selected tab; `aria-pressed` on a toggle button reflects whether it's on; `aria-current="page"` marks the current navigation item; `aria-sort` on a column header says how the table is sorted; `aria-invalid` marks a field with an error. A state that's wrong is worse than none: the user is confidently told something false.

Prefer native equivalents where they exist: the `disabled` attribute over `aria-disabled` (unless you deliberately want the control to stay focusable so people can discover it), `<details>`/`<summary>` for simple disclosure, a real `<select>` when styling allows.

### Hiding things: from whom?

Several techniques hide content, and each hides it from different people:

| Technique | Hidden visually | Hidden from screen readers | Focusable |
|---|---|---|---|
| `display: none`, `hidden` attribute | yes | yes | no |
| `visibility: hidden` | yes | yes | no |
| `aria-hidden="true"` | **no** | yes | **still yes** |
| visually-hidden CSS class | yes | **no** | yes if focusable |
| `inert` attribute | no | yes | no |

The dangerous row is `aria-hidden`: it removes content from the tree but not from the Tab order, so keyboard focus lands on something the screen reader won't describe — the Problem's silent sidebar. Use it only for decorative or duplicated content (an icon next to text), never on anything containing focusable elements. For a collapsed or off-screen panel, use `hidden` or `inert`.

The visually-hidden class is the opposite tool: text that's only for screen readers, like the "ticket #4521" context above.

### Live regions: telling people what changed

When content changes without focus moving — a toast, a search-results count, a saved confirmation, a real-time update — a screen reader user hears nothing unless the change is inside a **live region**. WCAG calls these "status messages" and requires them to be announced.

- `aria-live="polite"` (or `role="status"`) announces changes when the user pauses. The default choice.
- `aria-live="assertive"` (or `role="alert"`) interrupts. Only for things that need immediate attention: an error that stopped the action, a session about to expire.
- `role="log"` for streams like chat, where new entries are appended.

Practical rules, most learned the hard way:

- **The region must exist before its content changes.** A live region inserted into the DOM already containing a message is often not announced. Render empty regions at startup and put messages into them.
- **Announce outcomes, not activity.** "Ticket assigned to Maria," "3 results," "Saved" — not every keystroke or background refresh.
- **Coalesce and throttle real-time updates.** "3 new tickets" once every few seconds, or a quiet count in a heading the user can check, instead of an announcement per event. Let users choose the verbosity if updates matter to their work.
- **Don't make toasts the only record.** A message that vanishes after three seconds is gone before some users have read it or had it read. Keep the outcome visible somewhere persistent, and don't auto-dismiss messages that contain actions.

### Widget patterns: don't invent keyboard models

For composite widgets — comboboxes, menus, tabs, listboxes, trees, grids, date pickers — the **ARIA Authoring Practices Guide** (APG) documents the expected roles, states and keyboard behavior. Users of screen readers learn these conventions once and expect them everywhere, the same way sighted users expect a dropdown to open on click.

Two techniques underpin most patterns:

- **Roving tabindex:** one item in the widget has `tabIndex={0}`, the rest `-1`; arrow keys move the 0 and call `focus()`. The widget is a single Tab stop.
- **`aria-activedescendant`:** focus stays on a container or input (the combobox's text field) while an attribute points at the "active" option. Used when focus must stay in a text input while the user moves through suggestions.

These patterns are genuinely hard to implement across browsers and screen readers. A combobox that works in NVDA with Firefox may be silent in VoiceOver with Safari. For anything beyond tabs and disclosures, **use a component library that has already done the testing** — React Aria, Radix, Ariakit, Headless UI and similar — and put your effort into using it correctly.

### Dynamic content without disorientation

Real-time applications add their own hazards:

- **Don't move focus when data arrives.** A new ticket should never pull focus away from what the agent is doing.
- **Don't reorder or remove the focused item.** If the list re-sorts under someone's focus, they lose their place. Pause live reordering while focus is inside the list, or insert new items where they don't displace the focused one.
- **Mark loading regions** with `aria-busy="true"` while content is being replaced, and announce completion ("Loaded 25 tickets") politely.
- **Infinite scroll** makes the footer unreachable and gives no sense of size. Offer a "Load more" button, or at least announce how many items were added.

### Testing: layers, each catching what the others miss

No single method finds all accessibility problems, so testing is layered:

1. **Static checks while coding** — lint rules (`eslint-plugin-jsx-a11y`) catch missing alt text, labels, invalid ARIA attributes and `div` buttons as they're written.
2. **Automated runtime checks** — axe-core in component tests and end-to-end runs catches contrast, missing names, invalid role structures, broken ID references, duplicate IDs. Useful and cheap, and it finds only a portion of issues — the mechanical ones — with most WCAG criteria needing human judgment.
3. **Role-based tests** — tests that find elements the way assistive technology does, by role and accessible name (`getByRole("button", { name: "Assign ticket" })`). If the test can't find the button by its name, neither can a screen reader. Keyboard interactions tested the same way: press ArrowRight on a tab and assert the next tab is selected. Playwright's ARIA snapshots can assert the shape of the accessibility tree for a region.
4. **Manual checks per feature** — a keyboard-only walkthrough and a check at 200% zoom (34.3a). Minutes per feature, and they catch focus and order problems that no tool sees.
5. **Screen-reader testing** — on the combinations your users actually use. Across surveys of screen-reader users, JAWS and NVDA dominate on Windows desktops and VoiceOver on iOS, with TalkBack on Android. A reasonable core matrix: NVDA with Chrome or Firefox, JAWS with Chrome, VoiceOver with Safari on macOS and iOS. Test the critical flows each release; the full matrix less often.
6. **Expert audits and testing with disabled users** — periodically, and before major releases. Experts find conformance failures; users find where a conformant product is still too slow or confusing to use.

The layers compound. Automation keeps the mechanical failures from coming back; role-based tests make components' accessibility contracts regression-tested; human testing finds everything else.

### Honest conformance reports

An **Accessibility Conformance Report** — usually built on the VPAT template — lists each WCAG criterion with a conformance level ("Supports," "Partially Supports," "Does Not Support," "Not Applicable") and remarks. Enterprise and public-sector customers rely on it in procurement, and it's a representation you can be held to.

So write it from testing, not memory: which flows, which assistive technologies, which dates. Where you partially support a criterion, say where and what the plan is. EU rules add their own requirements for accessibility statements and feedback mechanisms. An honest "Partially Supports, with a dated roadmap" survives procurement far better than a "Supports" that the customer's own tester disproves in twenty minutes, as happened in the Problem.

## When It's Appropriate

- **ARIA belongs where native HTML can't express what you've built**: custom composite widgets, live updates, relationships between elements (`aria-controls`, `aria-describedby`), current and sort states. Everywhere else, native elements first.
- **Live-region infrastructure** is worth building in any app with asynchronous feedback — saves, background jobs, real-time updates, notifications (9.x, 14.2).
- **Role-based testing** is appropriate for every component library and every front end with tests at all; it costs nothing extra once the habit is set.
- **Regular screen-reader testing** is essential when conformance is contractual, when you know you have blind users, or when your product is a tool people use all day at work.
- **Expert audits** before a public-sector or large enterprise deal, and periodically after.

## When It's Unnecessary or Overkill

- **ARIA on everything.** `role="button"` on a `<button>`, `aria-label` duplicating visible text, `role="navigation"` on `<nav>`: redundant at best, and every extra attribute is one more thing to keep correct.
- **Hand-building complex widgets** when a tested library exists. The keyboard model is the easy part; cross-screen-reader behavior is where the time goes.
- **Announcing everything.** A live region that talks constantly is as unusable as one that never talks.
- **The full browser-and-screen-reader matrix on every release.** Critical flows on the core combinations per release; everything else periodically.
- **Chasing a perfect automated score** at the expense of manual testing. The score measures what's easy to measure.

## Trade-offs

- **ARIA must be maintained.** Every state attribute is a piece of UI state that must be updated in code, and drift is invisible to sighted developers and tests that don't check it.
- **Assistive technology is inconsistent.** Screen readers and browsers differ in what they support and how they announce it. Something correct by the specification can still fail for real users, and workarounds are sometimes needed.
- **Manual testing costs time and skill.** Screen-reader fluency takes weeks to develop; most teams have little. Expert audits cost money.
- **Live-region tuning is subjective.** Too quiet and changes are missed; too chatty and the product is exhausting. It needs feedback from actual users.
- **Libraries constrain design.** Accessible component libraries encode interaction models, and design deviations can break them.
- **Conformance reports are liabilities.** They must be updated as the product changes, and every claim has to be defensible.

## Alternatives

**Accessible component libraries** (React Aria, Radix, Ariakit, Headless UI, and design systems like GOV.UK's) — the most effective single choice for composite widgets. You own styling and product logic; they own the interaction model and its cross-assistive-technology testing.

**Native elements, more often than people expect.** `<dialog>`, `<details>`, native form controls, and — as browser styling support for form controls improves — native selects where you'd have built a custom one.

**Outsourced audits and testing** from accessibility specialist firms, and user-testing services that recruit disabled participants. They don't replace in-house practice, but they bring expertise most teams lack.

**Simpler interaction design.** A searchable page of results instead of a combobox, a plain list instead of a drag-and-drop grid. The most accessible widget is often a less clever one.

## How to Achieve It

**L0 — Remove the harm.** Audit for `aria-hidden` on focusable content, `aria-label` overriding visible text, `role="menu"` on navigation, and redundant roles; name every icon button; add context to repeated controls; add axe to component and end-to-end tests. *Signal to move on:* checks pass, but you don't know what the product sounds like.

**L1 — Make changes audible and widgets standard.** A shared announcer with polite and assertive regions; status messages for every asynchronous outcome; composite widgets replaced with a tested library; role-based queries as the default in tests. *Signal:* conformance is contractual, or a customer's tester is coming.

**L2 — Test with real assistive technology.** Screen-reader walkthroughs of critical flows on the core combinations each release; keyboard behavior asserted in tests; an ACR written from that testing. *Signal:* blind or keyboard-dependent users rely on the product for their jobs.

**L3 — Close the loop with people.** Disabled users in research and usability testing, periodic expert audits, an accessibility feedback channel with an owner, and training so screen-reader fluency isn't concentrated in one person.

## Implementation

TypeScript with React, in three pieces: names, announcements, and tests that exercise the accessibility tree.

### Names that work out of context

```tsx
// Visually hidden, still in the accessibility tree.
const srOnly = "sr-only"; // position:absolute; width:1px; height:1px; overflow:hidden; clip-path:inset(50%); white-space:nowrap;

function TicketRow({ ticket }: { ticket: Ticket }) {
  return (
    <li>
      <a href={`/tickets/${ticket.id}`}>{ticket.subject}</a>
      <button type="button" onClick={() => edit(ticket.id)}>
        Edit<span className={srOnly}> ticket #{ticket.number}</span>
      </button>
    </li>
  );
}

// Icon-only toolbar button: the name comes from aria-label; the icon is decorative.
<button type="button" aria-label="Assign ticket" onClick={openAssign}>
  <UserPlusIcon aria-hidden="true" />
</button>

// A count that the visual badge shows must be in the name too.
<a href="/inbox" aria-current={isInbox ? "page" : undefined}>
  Inbox{unread > 0 && <span className="badge"><span className={srOnly}>, </span>{unread}<span className={srOnly}> unread</span></span>}
</a>
```

> **The name starts with the visible label.** "Edit ticket #4521" still begins with "Edit," so a voice-control user saying "click Edit" gets a sensible set of matches, and the screen-reader user in a list of forty rows knows which ticket each button belongs to.

### One announcer for the whole app

```tsx
// Rendered once at the app root, empty, so the regions exist before any message.
export function Announcer() {
  const { polite, assertive } = useAnnouncerState();
  return (
    <>
      <div role="status" aria-live="polite" className={srOnly}>{polite}</div>
      <div role="alert" aria-live="assertive" className={srOnly}>{assertive}</div>
    </>
  );
}

// Coalesce bursts: many events in a short window become one message.
export function useCoalescedAnnouncement(windowMs = 4000) {
  const { announce } = useAnnouncer();
  const pending = useRef(0);
  const timer = useRef<number | null>(null);

  return useCallback(() => {
    pending.current += 1;
    if (timer.current !== null) return;
    timer.current = window.setTimeout(() => {
      const n = pending.current;
      announce(n === 1 ? "1 new ticket" : `${n} new tickets`, "polite");
      pending.current = 0;
      timer.current = null;
    }, windowMs);
  }, [announce, windowMs]);
}

// Usage:
// on assignment success:    announce(`Ticket assigned to ${agent.name}`, "polite")
// on real-time ticket event: announceNewTicket()   // coalesced
// on a failed save:          announce("Couldn't save. Your changes are still in the form.", "assertive")
```

> **Why the announcer clears and re-sets.** Screen readers announce _changes_ to a live region, so the same message twice in a row ("Saved", "Saved") may be read once. `announce` should briefly empty the region before writing the new text. This is the kind of detail that differs across screen readers, and a reason to take the announcer from a library if yours has one.

### Tests that query the accessibility tree

```tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { axe } from "jest-axe";

test("ticket tabs follow the tabs pattern", async () => {
  const user = userEvent.setup();
  const { container } = render(<TicketTabs ticket={fixture} />);

  const conversation = screen.getByRole("tab", { name: "Conversation" });
  const details = screen.getByRole("tab", { name: "Details" });
  expect(conversation).toHaveAttribute("aria-selected", "true");

  await user.click(conversation);            // puts focus on the tab
  await user.keyboard("{ArrowRight}");
  expect(details).toHaveFocus();
  expect(details).toHaveAttribute("aria-selected", "true");
  expect(screen.getByRole("tabpanel", { name: "Details" })).toBeVisible();

  await user.tab();                          // one Tab stop for the tablist, then into the panel
  expect(screen.getByRole("tabpanel", { name: "Details" })).toContainElement(document.activeElement as HTMLElement);

  expect(await axe(container)).toHaveNoViolations();
});
```

> **What this proves, and what it doesn't.** It proves the component exposes the right roles, names and states, and keeps the keyboard promise its roles make. That turns a whole class of Problem-style bugs into test failures. It doesn't prove how JAWS or VoiceOver will announce it, whether announcements are too verbose, or whether the flow makes sense by ear. That still needs a person with a screen reader.

## Further Reading

- **WAI-ARIA 1.2** — the specification: every role, state and property, and which elements they may apply to.
- **ARIA Authoring Practices Guide (APG)** — the expected keyboard behavior and markup for common widgets, with working examples. Treat the examples as illustrations of the pattern, and prefer a library's tested implementation in production.
- **W3C, "Using ARIA"** — the short list of rules for ARIA, starting with "don't use it if native HTML will do."
- **Accessible Name and Description Computation 1.2** — exactly how names are computed, for when the result surprises you.
- **WebAIM Screen Reader User Survey** — which screen readers and browsers people actually use, and how they navigate.
- **WebAIM Million** — including its recurring finding about ARIA and error rates.
- **a11ysupport.io** — community data on how ARIA features are supported across screen readers and browsers.
- **Testing Library, "Which query should I use?"** — why `getByRole` is the recommended default, and **Playwright's ARIA snapshot testing** for asserting tree structure end to end.
- **axe-core rule descriptions (Deque)** — what automated checks cover, which also shows what they can't.
- **The VPAT template (ITI) and EN 301 549** — the formats and standard behind conformance reports.
- **In this collection:** 34.3a (the semantic HTML and focus foundation), 9.x (real-time updates this article makes audible), 14.2 (in-app notifications), 21.3 (UI testing), 30.1 (running these checks in CI).

No sibling article is proposed. The mechanisms are defined by the web platform and assistive technology, not by the implementation language.
