# The Launch Plan: Runbooks, Rehearsals and Points of No Return

_Module 35 · Launch Checklist & Go-Live · 35.1b_

## The Problem

Suppose you run booking software for a chain of fitness studios: class schedules, bookings, memberships with recurring billing, a web app and a mobile app. After eighteen months of work, a rebuilt platform replaces the old one. It has a new data model, a new mobile app, and memberships moving to a new billing engine. About 180,000 members. The switch is planned for a Saturday night, with a two-hour maintenance window announced to members.

The launch plan is a page in the wiki:

```
Launch night
1. Put old site into maintenance mode
2. Run data migration (~40 min in staging)
3. Switch DNS for app.studio.example to new platform
4. Smoke test
5. Announce!
Rollback: restore old DB and revert DNS
```

Here's how the night goes.

**22:00.** Maintenance mode on. The migration starts.

**22:40.** The migration is 18% done. Staging had about 5% of production's data, and one step, rebuilding booking history per member, turns out to scale much worse than linearly. Nobody knows how long it will take. There's no rule about what to do if it runs long, so they wait.

**23:05.** The new mobile app goes live in the app stores. It was approved on Thursday and set to release automatically on approval; a store-side delay meant approval came through tonight. Members start updating. The new app can only talk to the new platform, which isn't up.

**02:10.** The migration finishes, three and a half hours late. DNS is switched. Smoke tests pass on the paths someone thought to click. Members, most of them now on the new app, start booking classes for Sunday morning.

**03:00.** A reconciliation someone runs by hand shows that for members in one time zone, the next billing date moved a day earlier. Several thousand members would be charged a day early on Monday. Someone says the obvious thing: _roll back._

That's when the team learns what "rollback" means tonight:

- **Restoring the old database** discards 50 minutes of bookings made on the new platform. Studios would open on Sunday to classes whose rosters don't match.
- **Reverting DNS** doesn't take effect for most members. The record's TTL is 24 hours, and nobody lowered it in advance. Resolvers will keep sending members to the new platform until Sunday night.
- **Members on the new app** can't use the old platform at all. The app can't be recalled from their phones.
- **The announcement email** is scheduled in the marketing tool for 06:00. Nobody on the launch call owns it. It goes out to 180,000 people saying the new app is live, whatever happens.

So they roll forward. They write a billing fix at 04:00, run a correction script at 07:00, and spend Sunday answering members whose Monday charges they have to explain anyway.

In the postmortem, the most telling finding is that **the team had passed the point of no return around 23:05, three hours before they realized there was one.** The "plan" was a list of intentions. It had no owners, no measured durations, and no conditions for stopping. It didn't cover things that would happen on their own, and it said nothing about which steps could be undone and at what cost.

## What It Is

A **launch plan** (or cutover runbook) is the ordered procedure for changing a system's state from "before" to "after" on launch day. Each step names an owner, how long it's expected to take (measured, not guessed), how you'll verify it worked, and whether it can be undone. Among the steps, the plan marks **checkpoints** where someone decides whether to continue, and the **point of no return**: the first step after which going back is no longer possible, or no longer worth its cost. It includes the rollback procedure for everything before that point, and the roll-forward options for everything after. And it has been **rehearsed**.

It sits between two neighbors. The **readiness review** (35.1a) asks whether the system can be operated once it's live. The launch plan is about getting there safely. An **incident runbook** (Module 24.3) responds to something unplanned; a launch plan is a planned change, so you get to decide the order of operations in advance, and that's where most of its value comes from. It also isn't the **deployment pipeline** (Module 30). Pipelines ship code. A launch usually changes things no pipeline touches: DNS, data, vendor accounts, app stores, emails to customers.

## Recognizing the Problem

- The launch doc is a numbered list without owners, durations or "verify by" for each step.
- Rollback is one line.
- Nobody can say which step is the last one you could still undo.
- Durations come from estimates, or from rehearsals on a small fraction of production data.
- Some things will happen on launch day that aren't in the plan: scheduled emails, app store auto-release, cron jobs, a vendor's cutover on their side.
- There are no conditions written down for stopping. "We'll see how it goes."
- DNS and cache TTLs haven't been checked.
- It's unclear who can say "abort", or everyone on the call assumes someone else will.
- The plan needs the same four people awake for fourteen hours straight.

## How It Works

### Inventory every state change, including the ones that aren't yours

Start by listing everything that will change on launch day, not just the steps someone will run. For the studio launch, the full list looks very different from the wiki page:

| Change | Who or what does it | In the original plan? |
| --- | --- | --- |
| Old platform goes read-only | Engineer | Yes |
| Data migrated to new schema | Migration job | Yes |
| Memberships move to new billing engine | Migration job + billing config | Implicitly |
| DNS for `app.studio.example` points to new platform | Engineer | Yes |
| New mobile app available in stores | **App store, on approval** | No |
| Old app versions stop working | Minimum-version flag | No |
| First charges on the new billing engine | **Billing scheduler, Monday 06:00** | No |
| Announcement email | **Marketing tool, scheduled** | "Announce!" |
| Studio staff trained on new rosters | Operations | No |

The ones in bold are the dangerous kind: **automatic actions**, triggered by a clock or an external event rather than by anyone on the launch call. They need to either become explicit, owned steps in the plan, or be deliberately disabled until the plan reaches them. The app store release should be set to manual. The marketing email should be a step owned by someone on the call, sent only after a checkpoint.

### Classify every step by reversibility

For each change, ask: _if we had to undo this an hour later, what would it cost?_ The answers fall into roughly three classes:

| Class | Meaning | Examples |
| --- | --- | --- |
| **Reversible** | Undo is quick and loses nothing | Maintenance mode, a feature flag, DNS _with a low TTL_, routing traffic between two live systems |
| **Reversible at a cost** | Undo is possible but loses data, time or money, or needs a procedure of its own | Switching back after new writes have landed on the new system; restoring from a snapshot; reversing a vendor configuration |
| **Irreversible** | Can't be undone, only compensated for | Emails and push notifications sent; app binaries on users' phones; charges made; data deleted from the old system; public announcements; legal notices |

Two things to notice. First, the class of a step often depends on _preparation_. DNS with a 24-hour TTL is effectively irreversible for a day; the same change with a 60-second TTL is trivially reversible. Second, a step can change class as time passes. Switching traffic back is reversible at 02:10 and becomes "reversible at a cost" the moment the first member books a class on the new system.

### Find the point of no return, and move it as late as you can

The **point of no return** is the first step in the sequence that isn't cheaply reversible. Everything before it is a rehearsal you can still abandon. Everything after it can only be fixed forward.

The main design move in a launch plan is to **push the point of no return as late as possible**, and to put a deliberate checkpoint right before it. Here's the studio launch, reordered:

```
 Days before          Launch night                                          Days after
 ───────────          ──────────────────────────────────────────────────   ──────────
 lower DNS TTL        maintenance  migrate   verify     ◆ GO?   switch     ◆ GO?   announce
 to 60s               on           (timed)   reconcile         traffic,             email;
 set app release                                               new app              enable
 to manual            ◄──────── all reversible ─────────►      release,             min-version
 ship old-platform                                             new writes           flag later
 reverse sync                                                   (reverse sync       still
                                                                keeps old usable)   later
                                                        ▲                     ▲
                                                 checkpoint 1           checkpoint 2
                                              (data correct?)     (stable for N hours?)
                                                                      = point of no return
```

The reordering and preparation did three things:

1. **Moved automatic actions under control.** The app release is manual, the announcement is a step after a checkpoint, and the minimum-version flag that locks out old apps waits days, until the new platform has proven itself.
2. **Made a costly step cheaper to reverse.** Lowering the TTL days in advance makes the DNS switch reversible. A **reverse sync**, which copies new bookings from the new platform back into the old one for a few days, means switching back no longer throws away members' bookings. That's the most expensive preparation on the list, and it's what turns "reversible at a cost" into "reversible."
3. **Put decisions right before the commitments.** Checkpoint 1 asks whether the migrated data is correct before any member touches it. Checkpoint 2 asks whether the system is stable before the irreversible announcement.

A detail about TTLs that bites teams: lowering a TTL only takes effect once caches have expired the _old_ value. If the record's TTL is 24 hours, the lowered TTL must be published at least 24 hours before the switch. It belongs in the plan's "days before" column, not on launch night.

Not everything can be made reversible. Some launches are inherently one-way: an email announcement, a regulatory filing, a payment processor migration where the old account is being closed. For those, the plan's job is to make sure the irreversible step is taken _knowingly_, at a checkpoint, by the person with the authority to take it.

### Rollback and roll-forward, decided in advance

"Should we roll back?" is a terrible question to answer at 03:00 with tired people and customers waiting. The plan answers it in advance:

- **Before the point of no return, the default is rollback,** and each reversible step has its undo written down, with its own verification. "Restore old DB and revert DNS" isn't a procedure. "Run `restore.sh` with snapshot X (38 min in rehearsal), verify booking count matches the pre-launch count, set DNS back (effective within 60s), take the old platform out of maintenance mode" is.
- **After it, the only option is forward,** so the plan lists how. Which features can be turned off by flag? Who can ship a hotfix at 4 a.m. and through what pipeline? What's the compensation for a wrong charge, and who approves it?

Then write **abort triggers**: specific, measurable conditions under which you stop, decided when everyone is calm.

```
Abort if, before checkpoint 1:
  • migration is not complete by 00:30 (rehearsed: 01:35 duration, started 22:15, +45 min margin)
  • reconciliation shows >0 mismatches in members, active memberships, or next billing dates
  • any step's verification fails and can't be fixed within 15 minutes
```

A trigger isn't automatic. The launch lead can still decide to continue, but continuing past a trigger becomes a deliberate, recorded decision rather than drift. This matters because of how launches really fail: nobody decides to press on past the point of no return. The group just keeps waiting, one more fifteen minutes at a time, until the scheduled email decides for them.

### What a step looks like

Each step in the runbook carries enough that someone who didn't write it could run it:

```
Step 7 — Reconcile migrated data                        Owner: Ana   Backup: Kofi
  Precondition:  Step 6 (migration) reports complete
  Action:        run reconcile job (link), compare old vs new
  Verify:        0 mismatches on: member count, active memberships,
                 next billing date per membership, future bookings per class
  Rehearsed:     22 min (dress rehearsal 2, prod-sized data)
  Reversible:    yes (read-only)
  If it fails:   → abort trigger; do not proceed to checkpoint 1
```

Notice what the verification compares. Row counts would have passed on the studio launch. The billing-date bug shows up only when you compare _derived_ values, the things the system will act on, like the date each member will be charged. Verification should be defined in terms of the outcomes that would hurt someone if wrong.

Communications are steps too. The status-page update when maintenance starts, the support briefing, the message if you abort ("we've postponed the switch and everything is back as it was"): write them in advance, as steps with owners.

### Rehearse until the plan runs without edits

A plan that has never been executed is a hypothesis. There are three kinds of rehearsal, from cheap to expensive:

- **Tabletop walk-through.** Read the runbook aloud, step by step, with everyone who owns a step. For each one ask: what if it fails? What if it takes three times as long? Who else needs to know it happened? This finds missing steps, missing owners and automatic actions, and costs an hour.
- **Pre-mortem.** Before the walk-through ends, the group imagines it's Monday morning and the launch went badly, and each person writes down why. (The technique is Gary Klein's.) People who wouldn't raise a doubt about "the plan" will readily write a story about how it failed. On the studio team, someone would likely have written "the app came out early" or "billing dates."
- **Dress rehearsal.** Run the actual runbook, end to end, against an environment with **production-sized data** (anonymized, if it's personal data) and production-like configuration. Time every step. Run the rollback too, because a rollback that has never run is the step most likely to fail. Repeat until the runbook runs from top to bottom without anyone editing it mid-run.

The dress rehearsal is where the durations in the plan come from, and so where the maintenance window comes from. "40 minutes in staging" on 5% of the data was never a measurement of the production migration. It was a measurement of a different, smaller system.

### Launch-day roles and timing

A launch is a planned incident, and borrows the same roles (Module 24.3):

- **Launch lead:** runs the sequence, calls each checkpoint, and is the only person who says "continue" or "abort." Usually the go/no-go decider from 35.1a. Doesn't run steps personally.
- **Operators:** own and run steps.
- **Scribe:** timestamps every step, decision and deviation. The log is how you'll know tomorrow what actually happened, and it's the raw material for the next rehearsal.
- **Communications owner:** status page, support, studio staff, and the announcement when it's time.

**Timing** is a trade-off rather than a rule. Low traffic argues for the middle of the night. But you also want people rested, vendors' support lines open, and a full team available the next day, when the problems that need real users to surface will appear. Avoid Fridays before long weekends and dates when key people are away, and freeze unrelated changes for a window around the launch so the only thing changing is the thing you're watching. Plan shifts for long launches. The people who start at 22:00 shouldn't be the ones making decisions at 05:00.

## When It's Appropriate

- **Big-bang cutovers:** replacing a platform, migrating data to a new system, switching a payment processor, auth provider or email provider, moving to a new domain. Anything where the old and new can't simply run side by side with traffic gradually shifting.
- **Launches with several irreversible steps,** such as public announcements, app releases or billing changes, especially when they're owned by different teams.
- **Coordinated launches with external parties:** vendors doing their side of a migration, partners switching integrations, marketing on a fixed calendar.
- **Anything with a maintenance window promised to customers,** where the durations need to be real.

## When It's Unnecessary or Overkill

- **Routine deploys through a pipeline with automated rollback** (Module 30.2b). The pipeline is the plan, and it's been rehearsed thousands of times.
- **Launches that are a flag flip.** If the new feature is already deployed, dark, and the launch is turning it on for a cohort, the plan is three lines: flip, watch, flip back if needed. Getting a launch into this shape is the subject of 35.2a, and it's usually a better investment than a better runbook.
- **Early products with few users,** where rollback is easy and the cost of an hour of downtime is an apologetic email. A short plan with one checkpoint is enough.
- **Rehearsing everything.** A dress rehearsal with production-sized data is expensive. Spend it on the launches with irreversible steps and long-running data work, not on every release.

## Trade-offs

- **Rehearsal is expensive.** A production-sized, production-like environment, anonymized data, and two or three evenings of the launch team's time. For a big cutover it's cheap next to a failed launch; for smaller ones it isn't.
- **Reversibility is engineering you'll throw away.** Reverse sync, an app build compatible with both backends, keeping the old platform running warm: all temporary, all needing testing, and each one delays the day you can decommission the old system. You're paying real money to buy an option you hope never to use.
- **Pushing the point of no return later stretches the launch.** Keeping both systems viable for days means more days of running two systems, and a longer period in which neither team has fully moved on.
- **Precision can be false.** A runbook with timestamps and triggers looks rigorous, and teams can follow it past the point where reality has diverged from it. The plan is a tool for the launch lead's judgment, not a substitute for it.
- **Checkpoints add time and decision load.** Every checkpoint is a pause with people waiting. Too many and the launch takes all night; too few and you're back to drifting.

## Alternatives

**Don't do a big-bang launch.** The most effective alternative is to avoid a single cutover at all. Migrate studio by studio, or member cohort by cohort, with both platforms live and each cohort's traffic routed to wherever its data lives (the strangler-fig approach, and staged launches in 35.2a). Each small cutover still needs a plan, but a short one, rehearsed by the previous cohort. The price is running both systems in parallel for longer and building the routing and sync that make it possible. For the studio platform, this would likely have been the better choice. Some changes can't be split, though: a domain move, a single shared billing run, or a vendor contract that ends on a date.

**Blue-green at the application layer** (Module 30.2b) makes the traffic switch instantly reversible. It doesn't help with the parts of a launch that aren't traffic: data, clients, vendors and communications.

**Roll-forward only, deliberately.** Some teams decide that building rollback isn't worth it and invest instead in fast fixing: small reversible steps, feature flags to turn off anything broken, and a hotfix path that works at 4 a.m. This is rational when the launch is inherently irreversible or rollback would cost more than the likely failures. It should be a decision made in advance, not the discovery the studio team made at 03:00.

## How to Achieve It

**Step 1: Turn the list into a plan.** Take the existing launch doc and add, to each step, an owner, a verification and a reversibility class. Then list every state change on launch day, including automatic ones, and make each an owned step or disable it. Mark the point of no return. _Next-step signal:_ you can't fill in expected durations with any confidence.

**Step 2: Tabletop and pre-mortem.** Walk through the plan aloud with every step owner, and run a pre-mortem. Add the abort triggers, the rollback steps, and the communications steps that come out of it. _Next-step signal:_ the plan includes long-running data work or several irreversible steps.

**Step 3: Dress rehearsal with production-sized data.** Run the whole thing, including rollback, and time it. Use the timings for the maintenance window and the abort triggers. Repeat until it runs without edits.

**Step 4: Engineer reversibility where it's worth it.** For the costly and irreversible steps, decide whether to prepare (lower TTLs, reverse sync, dual-compatible clients) or reorder (announcement and lock-outs last). Move the point of no return later.

**Step 5: Make it executable, or make it small.** If you launch cutovers repeatedly, turn the runbook into code that runs steps, pauses at checkpoints and logs everything. Or reshape your launches so they're incremental, and the runbook shrinks to a few lines.

## Implementation

TypeScript. The code treats the plan as data: first a check that rejects an unsafe plan before launch night, then a small executor that runs it with checkpoints and triggers. Most teams will stay at a written runbook; the point of showing it as code is that the rules become explicit.

### The plan as data, and a check that catches unsafe ordering

```ts
type Reversibility = "reversible" | "costly" | "irreversible";

interface Step {
  id: string;
  title: string;
  owner: string;
  kind: "action" | "checkpoint";
  reversibility: Reversibility;   // for checkpoints: "reversible"
  rehearsedMinutes?: number;      // from the dress rehearsal, not a guess
  run?: () => Promise<void>;
  verify?: () => Promise<{ ok: boolean; detail: string }>;
  undo?: () => Promise<void>;     // required for reversible steps before the PONR
}

interface AutomaticAction {       // things that happen without anyone on the call
  what: string;                   // e.g. "app store release on approval"
  controlledBy?: string;          // the step id that now owns it, if any
  disabled?: boolean;
}

function checkPlan(steps: Step[], automatic: AutomaticAction[]): string[] {
  const problems: string[] = [];
  const ponr = steps.findIndex(s => s.kind === "action" && s.reversibility !== "reversible");

  if (ponr === -1) problems.push("no point of no return found; is every step really reversible?");
  else if (steps[ponr - 1]?.kind !== "checkpoint")
    problems.push(`step ${steps[ponr].id} is the point of no return but isn't preceded by a checkpoint`);

  steps.forEach((s, i) => {
    if (s.kind !== "action") return;
    if (!s.verify) problems.push(`${s.id}: no verification`);
    if (s.rehearsedMinutes === undefined) problems.push(`${s.id}: duration not measured in rehearsal`);
    if (i < ponr && !s.undo) problems.push(`${s.id}: before the PONR but has no undo`);
  });

  for (const a of automatic)
    if (!a.controlledBy && !a.disabled)
      problems.push(`automatic action not under control of the plan: ${a.what}`);

  return problems;
}
```

> **Aside: the check can only see what you declared.** `checkPlan` would have caught the studio launch's app store release and scheduled email, but only if someone had listed them in `automatic`. The inventory in How It Works is what fills that list, and the tabletop walk-through is how you find what's missing from it. A green `checkPlan` means the plan is internally consistent, not that it's complete.

### Running it: checkpoints, triggers, and a log

```ts
interface Trigger { description: string; tripped: (ctx: RunContext) => boolean; }

interface RunContext {
  startedAt: Date;
  elapsedMinutes: () => number;
  log: (entry: string) => void;            // the scribe, automated
  confirm: (question: string) => Promise<"continue" | "abort">; // asks the launch lead
}

async function runLaunch(steps: Step[], triggers: Trigger[], ctx: RunContext) {
  const done: Step[] = [];

  for (const step of steps) {
    const tripped = triggers.filter(t => t.tripped(ctx));
    if (tripped.length) {
      ctx.log(`TRIGGER: ${tripped.map(t => t.description).join("; ")}`);
      if (await ctx.confirm(`Abort trigger(s) tripped before ${step.id}. Continue?`) === "abort")
        return rollback(done, ctx);
      ctx.log(`launch lead chose to continue past trigger(s)`);  // a recorded decision
    }

    if (step.kind === "checkpoint") {
      if (await ctx.confirm(`${step.title}: go?`) === "abort") return rollback(done, ctx);
      ctx.log(`checkpoint ${step.id}: GO`);
      continue;
    }

    ctx.log(`start ${step.id} (${step.owner}), rehearsed ${step.rehearsedMinutes} min`);
    await step.run!();
    const result = await step.verify!();
    ctx.log(`end ${step.id}: ${result.ok ? "verified" : "FAILED"}: ${result.detail}`);
    if (!result.ok && await ctx.confirm(`${step.id} failed verification. Continue?`) === "abort")
      return rollback(done, ctx);
    done.push(step);
  }
  ctx.log("launch sequence complete");
}

async function rollback(done: Step[], ctx: RunContext) {
  const irreversible = done.find(s => s.reversibility !== "reversible");
  if (irreversible) {
    ctx.log(`cannot roll back: ${irreversible.id} is past the point of no return. Switch to roll-forward plan.`);
    return;
  }
  for (const step of [...done].reverse()) {
    ctx.log(`undo ${step.id}`);
    await step.undo!();
  }
  ctx.log("rollback complete; run abort communications");
}
```

> **Aside: rollback refuses rather than pretends.** If the run is past a costly or irreversible step, `rollback` says so and stops, rather than undoing the reversible steps and leaving the system half-reverted. That's exactly the state the studio team would have produced at 03:00: an old database restored underneath members still using the new app. Knowing you're in roll-forward territory is itself the useful output.

> **Aside: time triggers come from rehearsal.** A trigger like "migration not done by 00:30" is `ctx.elapsedMinutes() > rehearsed + margin`. Without a rehearsed duration there's nothing to compare against, which is why `checkPlan` rejects steps without one. An abort trigger based on a guess mostly tells you your guess was wrong.

The verification for the migration step is where the billing bug would have been caught, and it's worth writing with care: compare what the system will _do_, not just what it stores.

```ts
async function verifyMigration(): Promise<{ ok: boolean; detail: string }> {
  const checks = [
    compare("members", oldDb.count("members"), newDb.count("members")),
    compare("active memberships", oldDb.activeMemberships(), newDb.activeMemberships()),
    // Derived values the system will act on: this is what row counts miss.
    compareSets("next billing date per membership",
      oldDb.nextBillingDates(),          // Map<membershipId, "YYYY-MM-DD" in studio's time zone>
      newDb.nextBillingDates()),
    compareSets("future bookings per class", oldDb.futureRosters(), newDb.futureRosters()),
  ];
  const results = await Promise.all(checks);
  const failures = results.filter(r => !r.ok);
  return { ok: failures.length === 0, detail: results.map(r => r.summary).join("\n") };
}
```

## Further Reading

- **Google, _Site Reliability Engineering_ (O'Reilly, 2016), Chapter 27, "Reliable Product Launches at Scale."** Launch techniques including gradual rollouts, feature flags and dealing with client behavior you can't control. Free at sre.google/books.
- **Jeff Bezos, 2015 letter to Amazon shareholders.** The source of "one-way door" vs "two-way door" decisions, the vocabulary behind reversibility classes.
- **Gary Klein, "Performing a Project Premortem," _Harvard Business Review_, September 2007.** Short and practical; the technique used in the tabletop section.
- **Stripe Engineering, "Online migrations at scale" (2017).** A four-phase pattern (dual write, change reads, change writes, remove old) for migrating data without a big-bang cutover, which is the incremental alternative in concrete form.
- **Martin Fowler, "StranglerFigApplication" (martinfowler.com).** Replacing a system gradually instead of in one launch.
- **Michael Nygard, _Release It!_, 2nd edition (Pragmatic Bookshelf, 2018).** The chapters on deployment and on keeping old and new versions working together.
- **RFC 1035, section on TTL,** and your DNS provider's docs on propagation. Why the old TTL decides how early the new one has to be set.
