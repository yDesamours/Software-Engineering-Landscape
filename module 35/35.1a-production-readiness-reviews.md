# Production Readiness Reviews: Checklists That Verify Instead of Attest

_Module 35 · Launch Checklist & Go-Live · 35.1a_

## The Problem

Suppose you're building an e-signature product for small businesses: upload a PDF, place signature fields, send it to signers, get back a signed copy with an audit trail. For a year it has been sold by hand to 60 design partners. Now it's going self-serve, with public signup and a free tier, announced in a keynote at an industry conference on a fixed date. Eight engineers.

Six weeks out, the team creates a "Launch Readiness" spreadsheet. It starts from a template found in a blog post, and the team adds its own rows. By the end it has 47. Each row has a task, an owner column ("Backend", "Infra", "Product") and a status. Three days before launch every row is green. At the go/no-go meeting, someone mentions an open bug: uploads over about 40 MB time out and leave a half-created envelope behind. People agree that's rare and fine. The launch goes ahead.

The first week goes like this.

**Launch day, hour 3.** Verification emails stop arriving after roughly 200 signups. The transactional email account had only ever sent to design partners, and it was still under the provider's new-account sending limits. The row said _"Email provider configured ✅"_, and it was configured. Nobody had compared its quota to the expected signup volume. The worker gets throttling errors, retries, and moves jobs to a dead-letter queue. No alert watches that queue. The team finds out from a user complaining publicly, and signups can't verify for six hours.

**Day 3, 02:10.** An alert does fire, on elevated signing errors. It pages an escalation policy whose primary is an engineer who moved to another team two weeks earlier and has muted the app. The secondary is paged 30 minutes later. The row _"Alerting set up ✅"_ was checked by that same engineer in week 3.

**Day 5.** A customer deletes a folder of signed contracts by mistake and asks for them back. The row _"Backups configured ✅"_ was checked in week 2, and the Postgres backups are fine. The signed PDFs, though, live in an object storage bucket added in week 8, without versioning and outside the backup policy. They can't be restored. The customer happens to have copies in their email.

**All week.** Support answers a stream of "my upload failed and now there's a broken envelope I can't delete" tickets without knowing the problem was known and accepted. Nobody told them. Nobody could say who had accepted it, either; "the meeting" did.

The postmortem finds something uncomfortable. **Every row was true when someone checked it, and every person who checked one believed it.** The spreadsheet had faithfully recorded that people had said yes. What it never recorded was whether the system could, _right now_, detect a failure, reach a human, limit the damage, and recover.

```
What the spreadsheet measured:          What launch needed to know:

  "Did someone say yes to X?"             "Is X true of production, today?"
   ├─ at some point                        ├─ checked recently
   ├─ about the system as it was then      ├─ against the system as it is now
   ├─ phrased as a task                    ├─ phrased as a testable property
   └─ owned by a team                      └─ owned by a person who'd notice
```

## What It Is

A **production readiness review** (PRR) is a structured check, done before a system takes real traffic, of whether the team can _operate_ it. Can they detect problems, respond to them, limit their damage, recover from them, and sustain the load? AWS calls its version an **Operational Readiness Review** (ORR). Google's SRE teams run PRRs before taking on a service, and have a dedicated launch-coordination function for product launches.

It has three parts that are easy to confuse:

- **The checklist** is the artifact: a set of claims about the system.
- **The review** is the process: gathering evidence for each claim, early enough to fix what fails.
- **The go/no-go decision** is the output, made by one named person using the review as input.

Two neighbors are worth separating now. A **Definition of Done** (Module 28) is per work item: this story is finished. Readiness is per system: this thing can be run in production by these people. A story can be done while the service it lives in is nowhere near ready. And a **security audit or load test** (Modules 20, 22) is an _input_ to readiness. The review asks whether that input exists, is recent, and covered what's actually launching.

## Recognizing the Problem

- Checklist items are verbs ("set up alerting", "configure backups") rather than statements that could be false today.
- Every row is green, but ask for the evidence behind any three and it takes an afternoon.
- Rows were checked weeks ago, and the system has changed since (new bucket, new queue, new vendor).
- The owner column names teams, not people.
- The checklist came from a template, and no item traces back to one of your own incidents.
- The same 50-row checklist is used for an internal admin page and for a payments flow, so everyone skims it.
- "Who can say no to launching?" gets silence, or "the CEO, I suppose."
- Known issues are "accepted" by a meeting, with no name, no expiry, and nobody telling support.
- The review happens the week before launch and finds things there's no time left to fix.

## How It Works

### Organize around operational questions, not tools

A template that asks "is Prometheus installed?" checks tooling. What you actually want to know is whether the team can run the system. Organize items around the questions an incident will ask of you:

| Question | Example claims |
| --- | --- |
| **Detect:** will we know? | User-visible failure of each critical journey pages someone. Queues that can silently fill (dead-letter, retry) have depth alerts. |
| **Respond:** who, with what? | Every critical alert reaches a current on-call person. A runbook exists for each paging alert. The on-call has production access they have actually used. |
| **Limit:** can we stop the bleeding? | The launch is behind a flag that can be turned off in under a minute. Signup can be rate-limited or paused without a deploy. Rollback of the last release has been done in staging. |
| **Recover:** can we undo damage? | Every datastore with customer data has backups and a recent successful restore test. Deleted user content is recoverable for N days. |
| **Capacity:** will it hold? | Load tested at expected peak × a stated headroom, with the traffic _mix_ of launch (signup-heavy, not browse-heavy). Every third-party quota covers the expected peak. |
| **Dependencies:** what else fails us? | Each external dependency has a known failure behavior (timeout, fallback). Status pages of critical vendors are subscribed to. |
| **People:** is everyone else ready? | Support knows the launch date, the known issues, and how to escalate. The status page exists and someone is allowed to post to it. |

The last row is the one engineering checklists most often lack. A launch involves support, sales and whoever writes the status update, and their unreadiness hurts users just as directly.

Notice where the scenario's failures land: an email quota (capacity, third party), a dead-letter queue nobody watched (detect), a stale on-call rotation (respond), an unbacked bucket (recover), an uncommunicated known issue (people). None of them was an exotic failure. All five were things a question-shaped checklist asks about.

### Write items as claims, with evidence

The single biggest change is rewriting each item from a task into a **claim**: a statement about production that is either true or false today, and could be checked by someone who wasn't there when it was set up.

```
Task (can only be "done"):         Claim (can be true or false now):

"Set up alerting"            →     "A synthetic failure of signup in production pages
                                    the primary on-call within 5 minutes."

"Configure backups"          →     "Every production datastore with customer data has a
                                    backup policy and a successful restore test in the
                                    last 30 days."

"Email provider configured"  →     "The email provider's sending quota is at least
                                    2× the expected peak hourly signup volume."
```

A claim needs **evidence**, and evidence comes in grades:

```
weakest ──────────────────────────────────────────────────────────────▶ strongest

 "yes"         link to a doc      artifact of a test        automated check
 (attestation) (config, runbook)  (restore log, page        (queries production
                                   receipt, load report)     now, re-runs itself)
```

An attestation isn't worthless. Sometimes a person's judgment is the evidence, as in "the security engineer reviewed the share-link design." But it should be a deliberate choice for items that can't be checked any other way, not the default for everything. Push each item as far right as it will reasonably go.

### Evidence expires

Evidence is about the system _as it was when checked_. It goes stale two ways: through age, and through change. The backup row in the scenario was true in week 2 and false from week 8, when the bucket arrived. So each item carries a maximum age, and ideally a list of the components it covers. Evidence gathered before any of those components last changed doesn't count. Automated checks sidestep most of this by simply re-running, which is why they're worth building for the items that matter most.

### Scale the review to the risk

A 47-item review for every launch guarantees two outcomes: small launches get blocked by irrelevant items, and big launches get skimmed because everyone has learned the checklist is mostly noise. Instead, assign each launch a **risk tier** from a few questions:

- **Exposure:** how many users, and are they external?
- **Reversibility:** can it be turned off in a minute, or does it write data or make promises that can't be undone?
- **Sensitivity:** does it touch money, credentials, personal or legally significant data?
- **Novelty:** new service, new datastore, new vendor, or a change to a well-trodden path?

Items declare which tiers they apply to. Google's launch coordination described this as a checklist of _questions_ where the answer triggers further items. "Does this launch add a new external dependency?" If yes, a specific set of follow-ups apply; if no, they vanish. That keeps the average review short and the relevant one thorough.

### A few killer items, clearly marked

Atul Gawande's work on checklists in surgery and aviation makes a point that transfers directly. A good checklist is short, used at a defined pause point, and focuses on the items that are both dangerous and easy to skip. They are not a complete procedure. Experts don't need to be told how to do their job; they need a check at a moment when a missed step is catastrophic.

In a readiness review that means separating **blocking** items, where a failure is a no-go unless someone with authority explicitly accepts it, from **advisory** items, which get an owner and a date and don't hold the launch. For the e-signature launch, the blocking items would be few: critical journeys page a real person, customer documents are recoverable, the launch can be switched off, capacity covers the expected peak including vendor quotas, and support knows the known issues. Everything else can be advisory.

### Start early; confirm late

A review done the week before launch is an audit of decisions that can no longer be changed. The review works better in stages:

```
T-6 weeks            T-2 weeks              T-2 days            Launch      T+30 days
    │                    │                      │                  │            │
    ▼                    ▼                      ▼                  ▼            ▼
 Design-time         Full review:           Final confirm:      Go/no-go     Re-run:
 walkthrough:        gather evidence,       re-verify stale     decision     catch drift,
 tier the launch,    file gaps with         and blocking        by the       close advisory
 surface the         owners and dates       items only;         named        items, retire
 expensive items                            record accepted     decider      accepted risks
 (restore tests,                            risks
 load tests, quota
 requests)
```

The design-time pass exists for the items with long lead times. Raising an email quota can take days of back-and-forth with a vendor, and a realistic load test needs an environment and a traffic model. Those have to surface at T-6 weeks, not T-3 days.

### Go/no-go: one decider, owned risks

The go/no-go meeting fails in a predictable way. Everyone is present, nobody is responsible, and the known issue gets waved through by collective shrug. Two rules fix most of it:

1. **One named decider**, agreed before the meeting (Module 32.4b covers decision rights generally). Item owners report status. The decider decides. For a tier-1 launch that might be the engineering lead together with the product owner. The point is that it's known in advance, not settled during the meeting.
2. **Every accepted risk is a record, not a mood.** It has the item, the person accepting it (who must have authority for that tier), the consequence in plain words, the mitigation, who needs to be told, and an expiry date by which it's either fixed or re-accepted.

The 40 MB upload bug was a reasonable thing to launch with. What went wrong was that no one accepted it _as someone_, so the consequences (support not knowing, no workaround published, no fix date) were nobody's job.

The criteria for go should be written before the meeting too. That turns the meeting into "here's where we stand against the criteria we agreed" rather than a debate about what "ready" means, held under deadline pressure with the keynote booked.

Finally, a no-go has to be survivable, or it's not a real option. If the only launch date is the public keynote, the decider is choosing between a known risk and public embarrassment, and the embarrassment usually wins. Separating the _technical_ launch from the _announcement_, by going live quietly days earlier, is the subject of 35.2a. For this article, the point is that readiness reviews are only honest when the calendar leaves room for a "not yet."

### The checklist learns from your incidents

AWS built its ORR program by taking lessons from its own post-incident reviews and turning them into questions that every other team would then be asked. That's what keeps a checklist relevant. It stops being a template from a blog post and becomes a record of the specific ways _your_ systems have hurt you.

The mechanism is simple. Every postmortem includes the question _"which readiness claim would have caught this, and did we have it?"_ If the answer is "none," a new claim gets written, tagged with the incident it came from. If a claim existed but passed anyway, its evidence was too weak, and gets strengthened. After this launch week, the team's checklist gains "every dead-letter queue has a depth alert", "every third-party quota covers expected peak", and a backup claim that iterates the infrastructure inventory rather than a list someone typed.

Pruning matters too, though it takes care. An item that hasn't caught anything in two years might be noise, or it might be guarding against a rare, severe failure. Retire items that are now **true by construction** first. If the service template ships every new bucket with versioning and a backup policy, the claim stops needing a human.

### Readiness doesn't end at launch

The system keeps changing after launch, so every claim that was true on launch day will drift. AWS re-runs ORRs on a schedule for this reason. Automated claims can simply keep running as a **scorecard** per service, visible to the team, which also makes the next launch's review mostly a matter of reading the dashboard. (What to watch in the first days after launch, while the system has no normal baseline yet, is 35.3a.)

## When It's Appropriate

- **A first public launch.** A product moving from 60 hand-held design partners to open signup, where the expected first week is 10,000–50,000 signups driven by one announcement. The traffic shape, user population and support load all change at once.
- **A new service taking production traffic** whose operators aren't the people who built it, or whose on-call rotation is new.
- **A launch tied to an external commitment:** a conference date, a customer contract, a regulatory deadline. Anything that makes backing out expensive is exactly when the checks need to be early and honest.
- **Launches that touch money, credentials, or legally significant data,** where the "recover" questions have real consequences.
- **Organizations with many teams shipping services,** where a shared set of incident-derived claims is how one team's painful lesson reaches the others.

## When It's Unnecessary or Overkill

- **Small, reversible changes behind progressive delivery.** If a change ships behind a flag to 1% of traffic with automated rollback (Module 30.2b), the pipeline _is_ the readiness check for that change. A review adds ceremony and nothing else.
- **Internal tools for a handful of colleagues,** where a failure means someone messages you on Slack.
- **Very early products with a few dozen friendly users.** A one-page version with five killer items is plenty. The full apparatus would take longer than the product is likely to exist in its current form.
- **A review board that can only block.** If passing takes three meetings and the reviewers carry no operational responsibility, teams learn to launch "experiments" that never get reviewed. A review people route around is worse than none, because the organization believes it's being done.

## Trade-offs

- **Time, especially from the most experienced people.** Evidence gathering, restore tests and realistic load tests are real work. A tier-1 review can cost a week of engineering across the team. That's why tiering matters.
- **Checklist fatigue.** Every incident adds an item. Without pruning and tiering, the list grows until people skim it, and a skimmed checklist is an attestation machine again.
- **False confidence.** A fully green review says you've guarded against the failures you thought of. The first week of any launch surfaces at least one you didn't. The review reduces known risks; it doesn't certify safety, and should never be presented as if it did.
- **Maintaining automated checks.** Checks that query production configuration break when APIs, tags or inventories change. A check that silently errors and reports "pass" is worse than a manual item. Checks need to fail closed.
- **Gatekeeping dynamics.** When one group reviews and another launches, the review can become adversarial: builders see a hurdle, reviewers see recklessness. It works best when the reviewers share the pager, or when teams self-review against a shared checklist with spot checks.
- **Political cost of no-go.** Even with a named decider, saying no against a public date takes nerve. The process makes the decision explicit; it can't make it easy.

## Alternatives

These mostly complement a readiness review rather than replace it, and it's worth knowing where each is stronger.

**Progressive exposure as the check.** Instead of predicting whether the system is ready, expose it to 1%, then 10%, and let production tell you (Module 30.2b; 35.2a for launches). This is better than any checklist at finding capacity and correctness problems under real traffic. It's useless for the failures that only matter when you need something, such as restoring a bucket or paging a human at 2 a.m. Those stay silent until the moment they're required, at any rollout percentage.

**Rehearsal: game days and drills.** Actually injecting a failure and watching the team respond (35.1b, and Module 24's restoration drills) produces the strongest evidence there is. Rehearsal is expensive, so it's best spent on the few blocking items where a document or config link isn't convincing.

**Paved roads: true by construction.** A service template that provisions every datastore with backups, every queue with a depth alert, and every service with an on-call route makes those claims true by default. This is the best long-term answer, and it's how a mature checklist shrinks. Its limit is that it only covers what the template anticipated. The new vendor, the unusual datastore and the launch-specific traffic shape still need a human question.

**Embedded ownership.** Some teams skip formal review and rely on the builders being the on-call. You-build-it-you-run-it gives strong incentives, but incentives aren't coverage: the on-call engineer who set up the alerts is exactly the person least likely to notice a gap in them. An outside pair of eyes on the checklist is cheap even for teams that run their own services.

## How to Achieve It

**Step 1: Rewrite what you have.** Take your current checklist, even the template spreadsheet, and turn each row into a claim. Add four columns: owner (a person), evidence (a link or artifact), verified at (a date), blocking (yes/no). Name the go/no-go decider. This costs an afternoon and fixes the worst of the attestation problem. _Next-step signal:_ you notice rows that don't apply to this launch, or rows every launch passes trivially.

**Step 2: Tier it and seed it from your incidents.** Add the tiering questions, mark which items apply at which tier, and go through your last ten postmortems asking which claim would have caught each one. Keep blocking items to a handful per tier. Start the review at design time for anything tier 1. _Next-step signal:_ the same items keep going stale between the full review and launch, or collecting evidence for them takes hours each time.

**Step 3: Automate the checkable claims.** The claims that are queries against production state become code: inventory-driven backup coverage, on-call routing, vendor quotas, alert existence, flag kill-switch presence. Evidence becomes "the check passed at 09:14 today." _Next-step signal:_ several teams run reviews, and you find the same gaps across services.

**Step 4: Continuous scorecards and paved defaults.** The automated checks run continuously for every service, not just before launches. Recurring failures turn into platform defaults that make the claim true by construction, and the item retires. A launch review now mostly consists of the tier questions, the manual items, and reading the scorecard.

Most teams launching one product need Steps 1 and 2. Steps 3 and 4 pay off when you're launching often, or running many services.

## Implementation

TypeScript, since this is glue over the APIs of your infrastructure inventory, paging tool and backup system. The clients below are stand-ins for whatever you use.

### Items as claims, with their own verification

```ts
type Risk = "low" | "medium" | "high";
const RANK: Record<Risk, number> = { low: 0, medium: 1, high: 2 };

interface CheckResult {
  passed: boolean;
  detail: string;
}

interface ReadinessItem {
  id: string;
  claim: string;            // true or false of production *now*
  category: "detect" | "respond" | "limit" | "recover" | "capacity" | "dependencies" | "people";
  requiredFrom: Risk;       // applies to launches at this risk and above
  blocking: boolean;        // failing = no-go unless explicitly accepted
  owner: string;            // a person
  origin?: string;          // the incident that taught us this
  maxAgeDays: number;       // older evidence is stale
  covers: string[];         // components whose change invalidates evidence
  verify?: (ctx: LaunchContext) => Promise<CheckResult>; // absent = manual evidence
}

const customerDataRestorable: ReadinessItem = {
  id: "recover.restore-tested",
  claim:
    "Every production datastore holding customer data has a backup policy " +
    "and a successful restore test in the last 30 days",
  category: "recover",
  requiredFrom: "low",
  blocking: true,
  owner: "maya",
  origin: "INC-212: signed-documents bucket outside backup policy",
  maxAgeDays: 1,
  covers: ["infra"],
  async verify({ inventory, backups }) {
    const stores = await inventory.datastores({ env: "prod", customerData: true });
    const gaps: string[] = [];
    for (const store of stores) {
      const policy = await backups.policyFor(store.id);
      const restored = await backups.lastSuccessfulRestoreTest(store.id);
      if (!policy) gaps.push(`${store.id}: no backup policy`);
      else if (!restored || daysSince(restored) > 30) gaps.push(`${store.id}: no restore test in 30 days`);
    }
    return gaps.length
      ? { passed: false, detail: gaps.join("\n") }
      : { passed: true, detail: `${stores.length} datastores covered` };
  },
};
```

> **Aside: iterate the inventory, not a list.** The check asks the infrastructure inventory for _every_ production datastore marked as holding customer data, so the bucket added in week 8 shows up automatically and fails. A check that loops over a hard-coded list of stores has the original bug built in. The corollary is that the inventory itself must be trustworthy. That's why infrastructure as code (Module 30.4b) and a required `customer-data` tag matter here: if the bucket can be created without the tag, the check can't see it. Consider a companion check that fails on any prod datastore _without_ the tag set either way.

```ts
const criticalAlertsReachAPerson: ReadinessItem = {
  id: "respond.alert-routing",
  claim:
    "Every launch-critical alert routes to a schedule whose on-call for the " +
    "next 14 days are current members of the owning team",
  category: "respond",
  requiredFrom: "low",
  blocking: true,
  owner: "tomás",
  origin: "INC-209: page went to an engineer who had changed teams",
  maxAgeDays: 1,
  covers: ["alerting", "paging"],
  async verify({ alerts, paging, directory }) {
    const problems: string[] = [];
    for (const alert of await alerts.withLabel("launch-critical")) {
      const schedule = await paging.scheduleFor(alert.route);
      if (!schedule) { problems.push(`${alert.name}: routes nowhere`); continue; }
      for (const shift of await paging.shifts(schedule.id, { days: 14 })) {
        if (!(await directory.isMember(shift.userId, alert.ownerTeam))) {
          problems.push(`${alert.name}: ${shift.userId} on call ${shift.start} but not in ${alert.ownerTeam}`);
        }
      }
    }
    return { passed: problems.length === 0, detail: problems.join("\n") || "all routes staffed" };
  },
};
```

> **Aside: what this check proves, and what it doesn't.** It proves routing: pages for these alerts will reach someone who belongs to the team. It doesn't prove the alerts fire on the conditions that matter. The launch-day dead-letter queue had no alert at all, so there was nothing to route. That needs a separate claim ("a synthetic signup failure pages on-call within 5 minutes"), whose evidence is a dated record of actually doing it. Automated checks are best at configuration properties; behavioral ones usually need an exercise.

### Turning evidence into a go/no-go input

```ts
interface Evidence { itemId: string; verifiedAt: Date; passed: boolean; detail: string; }

interface RiskAcceptance {
  itemId: string;
  acceptedBy: string;
  consequence: string;   // in plain words, e.g. "uploads >40MB fail and leave a broken envelope"
  mitigation: string;
  notify: string[];      // e.g. ["support", "status-page-owner"]
  expires: Date;
}

interface Launch {
  name: string;
  risk: Risk;
  decider: string;                         // agreed before the meeting
  canAcceptBlocking: string[];             // people with authority at this risk level
  lastChanged: (component: string) => Date | undefined; // from the deploy/IaC log
}

type Finding = { item: ReadinessItem; reason: "failed" | "stale" | "missing"; detail: string };

function assess(items: ReadinessItem[], evidence: Map<string, Evidence>,
                acceptances: RiskAcceptance[], launch: Launch, now = new Date()) {
  const blocking: Finding[] = [], accepted: Array<Finding & { by: RiskAcceptance }> = [], advisory: Finding[] = [];

  for (const item of items.filter(i => RANK[launch.risk] >= RANK[i.requiredFrom])) {
    const finding = problemWith(item, evidence.get(item.id), launch, now);
    if (!finding) continue;
    if (!item.blocking) { advisory.push(finding); continue; }

    const acceptance = acceptances.find(a =>
      a.itemId === item.id && a.expires > now && launch.canAcceptBlocking.includes(a.acceptedBy));
    if (acceptance) accepted.push({ ...finding, by: acceptance });
    else blocking.push(finding);
  }

  return {
    launch: launch.name,
    decider: launch.decider,
    status: blocking.length ? "not-ready" : accepted.length ? "ready-with-accepted-risks" : "ready",
    blocking, accepted, advisory,
  };
}

function problemWith(item: ReadinessItem, ev: Evidence | undefined, launch: Launch, now: Date): Finding | null {
  if (!ev) return { item, reason: "missing", detail: "no evidence recorded" };
  if (!ev.passed) return { item, reason: "failed", detail: ev.detail };
  if (daysBetween(ev.verifiedAt, now) > item.maxAgeDays)
    return { item, reason: "stale", detail: `verified ${ev.verifiedAt.toISOString()}, max age ${item.maxAgeDays}d` };
  const changedAfter = item.covers.find(c => (launch.lastChanged(c) ?? new Date(0)) > ev.verifiedAt);
  if (changedAfter)
    return { item, reason: "stale", detail: `${changedAfter} changed after verification` };
  return null;
}
```

> **Aside: the tool reports; the decider decides.** The output's status is `"not-ready"`, never `"no-go"`. A blocking finding might be a real problem, or a flaky check, or evidence nobody got around to uploading. Deciding which is exactly the judgment the named decider is for. What the code guarantees is that nothing is waved through silently. A blocking failure either appears in `blocking`, or appears in `accepted` with a name, a consequence and an expiry beside it. Paste the `accepted` section into the launch channel verbatim. The `notify` list is how support learns about the 40 MB bug on day zero instead of from customers on day two.

> **Aside: "changed after verification" is the check people skip.** Age alone would have passed the week-2 backup evidence if `maxAgeDays` were generous. Tying evidence to the components it covers is what catches "true when checked, false since." It's only as good as `lastChanged`, so feed it from the deploy log and IaC applies, not from memory.
